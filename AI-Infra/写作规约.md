**本文件是本目录内容写作与结构的唯一依据。** `Linux/写作规约.md` 与 `Kubernetes/写作规约.md` 的写法可以借鉴，但不作为本目录的规则——三个主题域的知识对象不同（见第二节），规则必须各自成文。

本目录的写作规则、12 章结构与判断性版本表收在本文件；仓库总览见根 `README.md`。

## 一、定位与读者

- 定位：面向「GPU 集群 / AI 训练平台运维」的生产判断力，覆盖**主机、网络与存储数据面**，也就是 Kubernetes 编排层不负责的那一层。验收标准是能不能在事故现场用出来，不是能不能复述概念。
- 读者：会基本 Shell 与 Linux 系统管理（内核模块、PCIe/NUMA、网络排障），跑过 CUDA 程序，但没有系统学过 GPU 驱动栈与高速网络这两块机制；它们由本目录负责补。
- **本目录与 Linux、Kubernetes 两个主题域的读者起点不同**：后两者的机制（内核、网络、编排）读者在工作里大多已有印象，写作可以默认心智模型在场；本目录的对象（RDMA、GPUDirect、NVLink、集合通信、XID）对目标读者是第一次系统接触的前沿技术，**前置知识必须在正文内置，不能默认读者自带**。内置的形式是第二节「前置依赖与坡度」规定的结构性手段，不是降低结论密度，也不是加科普铺垫。
- 各章各篇都不写「这一章写给谁」「读完能回答什么」，也不出现应试口径（「脱稿讲 3~5 分钟」「错题本」「正确率」「面试加分」）。「需要什么基础」不再以读者画像的形式出现，而是改写成可核对的**前置依赖声明**（形式见第二节「前置依赖与坡度」）。需要说追问时写值班口径，需要说演练时写限时推演。
- 通用主机能力（systemd、内存与 OOM、文件系统、TCP 排障、性能方法论、IRQ 亲和、软中断、MTU、网卡环形缓冲）归 Linux 主题域，编排与控制面归 Kubernetes 主题域；本目录对这两块只作排除式划界，不重复展开。

## 二、知识体系怎么组织

### 主线：一条数据路径

Linux 的知识对象是**一台机器上的一个机制**，证据在 `/proc`、`sysctl`、man。Kubernetes 的知识对象是**一条声明怎么被收敛成事实**，证据在 API 契约、`status` 与事件。**本目录的知识对象是一次数据搬运走的路径**——主机内存与 GPU 显存之间、GPU 与 GPU 之间、跨机与跨轨道之间的搬运——以及这条路径上每个环节的证据落在哪个计数器、哪个字段、哪份日志里。

因此每章内部统一跟**一条完整链路**走：

> 这个环节在做什么、代价落在哪里（机制）→ 它要成立必须先有什么（前置条件）→ 出问题时现场留下什么（字段、计数器、日志文本）→ 读到的值说明走的是哪条路径 → 代价与失败形态

每一章都有自己的「一次搬运」：第 02 章是一次驱动安装或升级在主机上改动了哪些对象，第 03 章是一次 GPU 间或 GPU 到网卡的搬运走哪条路径，第 04 章是一次 RDMA 传输从建链到落到线缆上，第 05 章是一次跨机集合通信在 fabric 上经过哪些跳，第 08 章是一次集合通信从初始化到完成。链路的名称写在下面的结构表「主链」一列里。

**由这条主线派生的三条硬规定**：

1. **每条链路在「体系」层至多一篇，且必须是这条链路的完整展开**；压缩成多篇短篇会让链路断裂。一章里存在多条链路时（例如第 04 章既有主机侧的 QP 建链，也有 fabric 侧的轨道选路），每条链路各有一篇体系篇；本章以哪条链路为主，写在结构表的「主链」一列里。
2. **运维与收口两章的主链不是数据路径**：可观测性章的知识对象是「一次告警到复盘」的时间线，按「看清 → 判定 → 隔离 → 处置 → 复测」展开；第 12 章的对象是读者脑中的模型。两章都不套分层，但都不得因此省掉代价与失败形态。
3. **一个动作牵动几处，就要在几处分别给判据**：升一次驱动会同时牵动内核模块、设备节点、用户态库、容器注入与 NCCL 的传输路径，分布在不同章就各写各的，不能只在一处写。

### 层的判定

沿链路依次问下面几句，问到哪句就落在哪层：

| 问句 | 落层 |
| --- | --- |
| 这句话在讲**这个机制为什么存在、代价落在哪里**（为什么 RDMA 要绕过内核、为什么丢包对它是致命的、为什么轨道要对齐） | 原理 |
| 在讲**一条链路上各环节怎么接起来、`status` 与计数器怎么从一件事变成另一件事** | 体系 |
| 在讲**用哪把工具看哪个字段、怎么读、先看什么** | 实操 |
| 在讲**看起来是这个原因、其实是那个原因** | 判例 |
| 在讲**上限配在哪一层、交什么产物、和别的领域怎么接** | 治理 |

每层的**排除项**（越界即拆篇）：原理不写处置动作与现场案例；体系不写制度设计与参数怎么配；实操不写机制推演与制度设计；判例不写完整流程；治理不写机制原理。

原理篇与体系篇不写动手章节、不放脚本、不报告个人实测值。**需要读者自己验证的地方，在正文里可以少量命令演示，或者用一句话给思路。** 这两条都要按下面的限度执行：

- 正文里的命令是**判据的兑现方式**，不是工具清单。判据仍只写一次：已在读法表里写过的判据，命令侧只写清它取的是哪个字段、对照哪一条判据，不把判据重述一遍。
- **少量**按篇计：一篇之内点到为止，只在读者读到这里会产生「我凭什么信」或「我怎么确认」的地方给；凡不是判据兑现点的命令，一律挪到实操篇。
- 命令演示只给一行到两行，注释写 `# 验证：…`，只在可丢的实验节点执行的要当段标明并在同处给回滚步骤；贴输出要声明「数值仅示意」，并说明结果与机型、驱动四元组、网卡固件强相关。
- 只给思路的那一种是完整写法，不是省略写法：写清用哪个工具、读哪个字段、对照哪条判据即可，不承诺读者会看到什么数值。
- 原理篇的排除项仍然有效：**处置动作与现场案例不写进原理篇**。命令演示只服务于「确认机制确实这样工作」，不是为了指导现场动手。

### 章内构成与导航

- 篇目顺序固定：`原理 → 体系 → 实操 → 判例 → 治理`，篇名形如 `NN_层_关键词.md`；层名只有这五个、顺序不得变，**不规定每层或每章的篇数**。某层确实没有有出处的素材就整层不写，并在该章导读的篇目索引里留一行说明。
- 每章 `00_导读与知识地图.md` 写五块：前置依赖、知识地图（本章主链与横向关系）、术语速查（只收本章新引入的词）、关键字段的读法、篇目索引；**故障现场定位表放在本章实操篇**。导读不写参考文档，参考文档放各篇末尾。前置依赖块的写法见下面「前置依赖与坡度」。
- **未成章的导读按「目标形态」写**：篇目索引列出规划篇目（篇名、层级、一句话），数量与篇名在写作过程中可以调整，但层名与顺序不得变。此时篇目尚不存在，因此索引里写纯文本篇名、**不建 wikilink**；篇目写成后再把它改成链接。
- 第 12 章不套分层（对象是读者脑中的模型），篇名用 `NN_收口_关键词.md`，内部结构按收口需要自定。
- 每篇具体的节与顺序不在这里规定，写作时按已成章的写法自行把握；每篇结尾必备一句 `**第一反应不要做什么**：…`。
- 根目录下的 `NN_主题.md` 是**重写期间的旧稿**，逐章替换后删除，见下面的「重写进度」。`99_AI-Infra笔记模板.md` 已废弃，新增篇目按本文第三节与各章导读的篇目索引写，不再复制模板。

### 前置依赖与坡度

本目录的机制对目标读者是第一次系统接触的新技术，因此坡度不是写作风格问题，而是内容完整性问题：缺了前置，判据就没有可以挂上去的对象。以下五条是硬规定，违反视同内容缺失。

1. **章导读的前置依赖块**：放在知识地图之前，只写「进入本章前应当已经成立的结论与字段口径」，逐条列出；每条写清两件事——这个前提在本章的哪一段被当作已成立使用、它由前面哪一章负责（章名可写，篇名不写）。本章自身才展开的概念不列入；第 01 章无前置依赖块。
2. **篇内的最小重述是义务**：一篇用到同章前一篇或前置章的结论时，在用到的那一段用一句话把该结论重述（带字段名与单位），再继续展开；不展开教第二遍，也不默认读者记得。重述必须给出结论本身，只指路不重述仍属违规。
3. **负载术语的回指解释**：术语「首次」仍以章为界；但前面章或别的主题域展开过、而本章某个判据直接以它为对象的词（例如 MTU、ethtool 计数、环形缓冲之于 RDMA 主题），在本章首次出现时给不超过一句的回指解释。本章新引入的词照旧进导读术语速查并在首次出现处完整解释。
4. **图形内容必须给一遍完整走查**：机制涉及时间线、队列水位、状态迁移、映射链、拓扑时，先用表格、Mermaid 图或 ASCII 图把一个具体输入从进入到出线的每一步走完，再进入机制论述；只用纯文字叙述时间线视同缺失。**形态按知识点自身的难点选择，不为画图而画图**：关系、环路与分支用 Mermaid 流程图；水位、换算与对照用表格；ASCII 布局图只在空间布局本身就是难点时使用——表格已经达意的内容不另画图。Mermaid 以代码内嵌在正文里（根 README 已声明 Obsidian 对 Mermaid 的渲染支持），节点文字必须用机制本名与字段名；flowchart 不声明方向，用默认的垂直布局。图只负责呈现流程与关系，判据仍只写在读法表里；不引入二进制图片附件。数值换算（指数族取值、单位换算、默认值的量级）给出至少两个换算点与一个反推判据。
5. **被划界能力的就地补足**：对 Linux、Kubernetes 主题域只做排除式划界的规定不变；但当本章的判据链直接以被划出的通用能力为对象时（如 MTU、ethtool 计数、队列水位），划界句之外必须给最小自足的解释——「在本章它影响哪一项读数」写到读者不离开本章就能执行判据为止。

同时明确不做什么：不引入 `L1/L2`、`M1–M8` 这类等级编号；导读不写「建议阅读顺序」「适合谁读」；坡度靠上述五条结构性手段实现，不靠降低结论密度、删判据或加科普铺垫。

### 已裁定的分工

跨章主题的分工只写已经裁定过的部分，其余写作时按当章需要自行确定。通用规则一条：**主归属章写机制与判据，其余章只写自己那一段，同一机制不重讲第二遍。**

- 版本四元组的约束方向与安装顺序依赖在第 02 章；RDMA 栈自身的取舍（in-box、DOCA-OFED、MLNX_OFED）在第 04 章；把四元组记进节点交付文档的模板在第 01 章。
- NVLink 与 NVSwitch 的基板形态、P2P 能力与降速在第 03 章；同一块 NVSwitch 上的跨机扩展（MNNVL、IMEX、clique）在第 05 章。
- RoCE 的主机侧配置、PFC/ECN/DCQCN 与 GID 在第 04 章；IB fabric 的集中配置面（子网管理器、分区、SHARP）与 rail 轨道在第 05 章。
- GPUDirect RDMA 的模块前置（`nvidia_peermem`）在第 02 章；它带来的性能差异如何测量在第 06 章；它在容器里的注入在第 07 章。

## 三、写作形态

- **行文用学术报告语体**：写完整句，主语与谓语齐全，句间用「因此 / 由于 / 若 / 反之 / 同时」这类显式逻辑连接；不把结论压缩成电报式的名词短语堆叠。
- **不用比喻与黑话代替机制本名**：把机制、占用与关系按本名写出来；任何结论都要落回字段名、单位、数值或错误文本。本目录的典型违规写法有三类：把「NCCL 卡住了」当结论（应写清卡在哪个阶段、哪个 rank、哪条路径），把「网络抖」当结论（应写出是 PFC pause、ECN 标记还是重传在涨），把「卡坏了」当结论（应给出 XID 码与 Resolution Bucket）。自检口径：把任意一句单独摘出来，读者不需要再问「这是什么意思」。
- **不使用跨章引用**：正文与导航篇都不写「见第 N 章」「第 N 章」这类指路，也不写跨章的篇名。只允许**排除式划界**：用一句「这不是本篇负责的内容」划清范围，**不给方向**。唯一的例外是章导读的「前置依赖」块：它按第二节「前置依赖与坡度」第 1 条写前面章的章名，不写篇名，正文不受此例外影响。正文同样不写「前面几节」「上一节」「后面会讲」这类承接式指路：要承接上文就把结论重述一遍，要划界就用排除式表述。跨篇承接时，重述是义务而不只是许可：用到前面篇的结论必须按第二节「前置依赖与坡度」第 2 条最小重述。篇内的锚点式编号（`2.3`、`第 6 步`）不受此限，但不得指向本篇之外的篇。
- **不使用 wikilink**（`[[...]]`），本章导读的篇目索引除外。引用块只用于呈现逐层演进中被剖析的回答。
- **不讨论文档自身结构**：不写「这篇讲什么」「本文将分三部分」「30 秒速览」「怎么用这篇笔记」，也不出现 `L1/L2`、`M1–M8` 这类等级与技能编号。「必须先读什么」只以第二节「前置依赖与坡度」规定的前置依赖声明形式出现在章导读，正文一律不写。
- **开篇形态不固定**：同一章同一层的多篇不得使用同一个开头标签，也不得逐篇套用同一种句式。开篇仍要先交代「这件事解决了什么问题、代价落在哪里」，再进入机制展开。
- **给出数值就要给出读法**：凡让读者看某个字段，必须同时写清五件事——是什么、单位、判据、与谁同看、看到它转向哪一步。**本条在本目录尤其重要**，因为这里同时有瞬时量与累计量（带宽与计数器）、有上限与实际生效值（`max_mtu` 与 `active_mtu`、`LnkCap` 与 `LnkSta`）、有单机与跨机两种口径，混着读就会得出错误结论。贴命令输出必须声明「数值仅示意、不代表你的环境」。
- 术语首次出现给中文解释 + 英文原词，缩写展开；**「首次」以章为界**，本章导读的术语速查负责本章新引入的词。前面章已展开过的词原则上不再重复解释；唯一的例外是第二节「前置依赖与坡度」第 3 条的负载术语，给不超过一句的回指解释。
- 破坏性操作标「只在实验节点」；只读观测标「生产节点上也可以做」。**本目录的破坏性操作清单比 Linux 短，但后果更重**：`nvidia-smi --gpu-reset`、MIG 的重切分与回收、`rmmod nvidia*`、驱动升级与降级、网卡与 GPU 固件刷新都会中断同一台机器上的**全部**作业，因此每一处都必须写明影响范围与回滚路径，而不只是「先隔离节点」。

## 四、事实纪律

**版本口径**

- **全库对照 NVIDIA 各组件官方文档的当前稳定版**；默认值、字段口径与版本门都以它们为准。本口径写在这里一次，各章正文不重复声明版本基线。
- **版本号只出现在判断点上**。判断点指三种情形：某个版本门决定这个能力能不能用（例如 NCCL 从哪个次版本起动态选择 GID）；某个默认值会改变现场读数（例如 `NCCL_CROSS_NIC` 的默认值随 fabric 形态而变）；某次升级会改变行为或让旧写法失效。**不改变判断的演进史一律不写**。
- **四元组纪律**：凡涉及版本兼容的结论，必须同时给出**驱动 / CUDA / NCCL / RDMA 栈（OFED 或 in-box）**四项，并写清它们之间的约束方向；只给一个版本号不算通过。四元组是同一件事的四个侧面，缺一项就无法判断这套组合能不能跑。
- **默认值现场取，不凭记忆**：`nvidia-smi -q`、`nvidia-smi topo -m`、`/proc/driver/nvidia/version`、`ibv_devinfo -v`、`mlnx_qos -i <if>`、`rdma statistic`、`ethtool -S`、`dkms status`、`modinfo -F filename nvidia` 是常用的几个取法。取不到就写「未确认」，并说明还缺什么才能确认。
- **复核触发**：每当驱动分支或 NCCL 次版本进入稳定发布，在下一次写作之前核对下表的判断性版本行，以及各章默认值的现场取值方式。先改本文件的表，再改正文；两处不一致时以本表为准。

## 五、高发错误清单

本节是第二至第四节规则的反例索引；规则修订时同步核对本节。

1. **机制归因错位**：把观察值安到错误的开关上（把 `nvidia-smi` 可用当成 CUDA 可用；把 `NCCL_P2P_DISABLE` 的效果当成拓扑结论；把 XID 13 当成硬件故障；把 `max_mtu` 当成链路实际生效的 MTU）。
2. **版本号越界**：在不改变判断的地方给版本号；只给一个版本号而不给四元组；用博客、社区整理稿或发行版文档证默认值；引用了会漂移的 `latest` 路径而不标访问时的版本。
3. **给出数值不给读法**：带宽与延迟没写单位与测量条件；计数器没写是累计值还是瞬时值、要不要取差分；`LnkCap` 与 `LnkSta`、`max_mtu` 与 `active_mtu`、`algbw` 与 `busbw` 这几对混用；把自己的实测值当通用结论。
4. **口径与形态**：同一件事两处写且数值或字段名不一致；用单机或 soft-RoCE 的读数支撑跨机与硬件结论；文档自身结构声明（目标、关联复习、30 秒速览、怎么用这篇笔记、回到路线图）与应试口径；跨章 wikilink 与篇末缺边界句；同一章同一层同构开头，使各篇的问题意识被句式掩盖。
5. **坡度失控**：把前置知识默认成读者自带——开篇即以满密度堆叠多个新对象、负载术语不回指、涉及时间线与映射链的机制只有纯文字叙述、对被划界的通用能力只划界不留最小补足、用到前面篇的结论不重述。这类违规的特征是单句都能读懂、连起来跟不上，自检时按第二节「前置依赖与坡度」五条逐项核。
