# 从驱动到 CUDA 应用的软件依赖

一台服务器能在 PCIe 上枚举出 GPU，`nvidia-smi` 也能列出设备，某个 CUDA 应用却仍然启动失败。另一个节点没有 `nvcc`，反而能正常运行同一应用。要解释这两种现象，需要将“装了 CUDA”拆成几件具体的事：谁管理设备，谁提供计算接口，应用带了哪些库，以及 GPU 能否执行应用中的设备代码。

本章的学习任务是：**画出驱动与应用的依赖关系，跟踪一个 CUDA 进程从装载到完成计算的过程，读懂不同版本字段，并根据完整材料判断失败停在哪一层。** 学完后，应能评审一份简单的软件清单，说明哪些依赖由节点提供、哪些随应用交付，以及还需要什么证据。

## 必要前置与章间边界

Linux 进程、内核模块、设备文件和动态库沿用读者已有基础；正文会简短唤起它们在本场景中的作用。从[第 01 章](../01_从一台GPU服务器认识基础设施/00_导读.md)带来 PCIe 枚举与设备身份，从[第 02 章](../02_GPU如何计算与显存/00_导读.md)带来 Kernel、Stream、显存分配和异步完成的认识。

Driver API、CUDA Runtime、Toolkit、NVML、CUDA Context、设备代码架构与兼容性规则在本章建立。本章解释 Linux 宿主机中应用如何获得计算能力；[第 04 章](../04_单机多卡与GPU数据路径/00_导读.md)接着讨论数据在单机多卡间的实际路径。容器设备和库的注入、第 10 章的 Container Toolkit，以及第 12 章的 Operator 管理不在这里展开；内核与库问题只讲本章所需的定位过程，集群升级和回滚由第 19 章负责。

## 贯穿材料的约定

本章另建一台 **`cuda-node-a`**，不与前两章的设备编号、容量或虚构 GPU-T 对应。它是 Linux x86_64 裸机教学场景，只有一张独占、未切分的 NVIDIA A100，设备计算能力为 **8.0**。图文中的 GPU-A 是本章代号；PCI 地址固定为 `0000:41:00.0`，`GPU-<A>` 是 UUID 占位符，不能直接用作命令参数。多设备可见性例题会另行声明条件。

| 项目 | 健康基线 |
| --- | --- |
| 操作系统与内核 | Ubuntu 22.04 x86_64；运行内核 `5.15.0-107-generic`，仅用于解释模块归属 |
| GPU 驱动 | Linux `570.124.06`，用户态与已加载内核态组件配套；所需固件、设备节点与访问权限正常 |
| 应用构建 | `vector-check`，以 CUDA Toolkit 12.8.1 官方分发清单中的 NVCC `12.8.93`、Runtime `12.8.90` 构建 |
| 应用交付 | 主机可执行文件与必需运行库；本例动态链接 `libcudart.so.12`，库随应用放在 `/opt/apps/vector/lib/` |
| 设备代码 | 本例 Kernel 含 `sm_80` cubin 与 `compute_80` PTX；无其他 GPU 插件、无额外计算库依赖 |
| 正常启动环境 | 动态库搜索路径已配置；没有隐藏设备的环境设置；空间足够，无其他作业争用 |

这些是**自拟的教学条件**，不是已部署或已验收的节点。正文中的输出、日志、构建清单和探针记录均为教学材料，就近说明删节和人工汇总方式；无需运行命令即可完成所有练习。命令中的 Linux 路径属于教学节点。

机制以 CUDA **12.8.1 归档文档**为主要基线；驱动数字来自该版 [Release Notes 的两张驱动表](https://docs.nvidia.com/cuda/archive/12.8.1/cuda-toolkit-release-notes/index.html)。应用组件明确采用 [12.8.1 官方分发清单](https://developer.download.nvidia.com/compute/cuda/redist/redistrib_12.8.1.json)中的 Linux x86_64 包；它与 Release Notes 组件表中的 NVCC 补丁号存在差异，具体说明在第三篇。驱动分层、GSP、模块安装的解释补充采用同一 R570 分支的 Linux README 570.124.04，不能将其路径中的补丁号抄入本章 `.06` 节点。兼容性指南、NVML 与管理工具网页采用核对日可访问版本；本章不把它们当前的全部产品支持范围推广到 12.8.1。资料核对日期：**2026-11-08**。
