# 读懂一份应用交付与故障材料

## 先评审一个正常交付

发布者想把 `vector-check` 从构建机交给一台没有完整 Toolkit 的节点。以下是**自拟交付清单与验证记录**，使用导读基线；它覆盖本次所有 GPU 代码和依赖，没有延迟下载的插件。运行节点上没有 `nvcc`，应用所需的普通主机依赖均已满足。

| 类别 | 交付材料 |
| --- | --- |
| 设备与节点 | GPU-A：A100、计算能力 8.0、PCI `0000:41:00.0`；当前内核 `.107` |
| 节点驱动 | 已加载 `nvidia` 为 `570.124.06`；NVML 与 `libcuda` 同版本配套，相关模块、固件和权限正常 |
| 主程序 | Linux x86_64 可执行文件；Toolkit 12.8.1 构建 |
| 应用运行库 | `/opt/apps/vector/lib/libcudart.so.12.8.90`，由 `libcudart.so.12` 指向；无其他 GPU 库依赖 |
| 设备代码 | 全部所需 Kernel 含 `sm_80` cubin 和 `compute_80` PTX |
| 启动环境 | 无覆盖应用库的环境路径；`RUNPATH=$ORIGIN/../lib`；设备未被隐藏 |
| 管理查询 | `nvidia-smi` 可初始化并返回 GPU-A |
| 应用探针 | 实际装载库路径与清单一致；设备发现、初始化、分配、复制、启动、同步和结果检查均通过 |

可以按两条关系审查它。

第一条是依赖归属：GPU、内核驱动、固件与驱动用户态库由节点提供；程序、Runtime 与设备代码随应用交付；编译器只在构建时需要。运行机缺少 `nvcc` 没有破坏这份已编译应用的依赖。

第二条是证据范围：清单先说明组合有依据，探针再证明该次输入实际完成。因为 GPU-A 有对应 `sm_80` 机器码，这次 Kernel 可以走本机代码路径；无需以“节点有完整 Toolkit”作为前置，也无需仅为运行此应用添加兼容包。通过探针说明的是单卡功能链已验证，不能从这份材料推出多卡互联或长期性能已经达标。

这两条关系应同时保留。只看清单会漏掉实际选错库；只看一次成功又难以重建交付条件。

## 独立练习

下面各题彼此独立。沿用 GPU-A 与本章普通 Linux 离散 GPU 目标；若改变环境，会在题内写明。不要求补做实机实验，先给结论、再写使用的证据。

### 1. 分配依赖与工具职责

构建机有 `nvcc`、CUDA 头文件和受支持的主机编译器。运行机只有配套 NVIDIA 驱动、GPU、`vector-check` 和动态链接所需 Runtime，普通主机依赖也齐全。

画出应用到硬件的计算调用链，以及 `nvidia-smi` 的管理调用链；指出 `nvcc` 和 GSP 固件各在什么位置。运行机没有 `nvcc` 是否阻止运行？如果只知道 `nvcc --version` 成功，能否认定这台机器能够完成 GPU 计算？另有一个明确静态链接 Runtime 的应用，`ldd` 没列出 `libcudart.so`，是否说明它缺少 Runtime？

### 2. 读版本与进程设备编号

一台主机有 A、B 两张 GPU，两张卡的 Compute Capability 都是 8.0。题设已经用 UUID 确认：**CUDA 原始枚举顺序**为 A=0、B=1。当前 shell 中 `nvcc` 报 `release 12.6`，`nvidia-smi` 页眉报驱动 `570.124.06`、`CUDA Version: 12.8`；发布清单说明应用用 Toolkit 12.8.1 构建，并携带 Runtime 12.8.90。

用 `CUDA_VISIBLE_DEVICES=1` 启动应用后，应用发现一个设备并选择 ordinal 0。这个 0 对应哪张卡？上述材料能否证明应用正在使用当前 shell 的 12.6 Toolkit？页眉 12.8 是否证明本机安装了 Toolkit 12.8？

### 3. 判断初始化与完成阶段

在本章 CUDA 12.8 基线中，某次运行有以下**自拟阶段记录**：

```text
cudaGetDeviceCount: cudaSuccess, count=1
cudaSetDevice(0): cudaSuccess
cudaMalloc: cudaSuccess
input copy: cudaSuccess
kernel launch check: cudaSuccess
cudaDeviceSynchronize: execution error
output copy: not attempted
```

应用已经完成初始化吗？最后一次成功是否证明 Kernel 完成？可以把错误确定归因于 `cudaDeviceSynchronize` 的实现吗？下一步应查看哪段材料？另将条件改为启动时装载器就报告 `libcudart.so.12` 缺失，此时应先追哪个阶段？

### 4. 比较兼容性组合

共同条件：GPU-A、主机依赖完整、驱动内部配套，无兼容包，无额外 GPU 动态库或插件。表内代码覆盖所有实际要用的 Kernel。

| 组合 | 驱动与应用 |
| --- | --- |
| X | `525.60.13`；CUDA 12.8.1 Runtime；全部有 `sm_80` cubin，不用新驱动特性，也不需要 JIT |
| Y | 与 X 相同，但只携带 `compute_80` PTX；题设旧驱动不能理解其 PTX ISA 版本 |
| Z | `570.124.06`；CUDA 12.8.1 Runtime；只有 `sm_90` cubin，无 PTX |
| W | `520.61.05`；其他条件与 X 相同 |

逐个判断驱动与设备代码条件，说明 X 与 Y 为什么不能只按“都是 CUDA 12.x”得出相同结论。Z 是否可以通过安装更高版本 Toolkit 自动修好？

### 5. 评审兼容包方案与代码覆盖

一份提案写道：“给任意 GPU 安装 `cuda-compat-*`，即可运行任何新 CUDA 应用，还能解决所有 `Driver/library version mismatch`。”另一份代码清单说明：主程序有 `sm_80`，但其必需插件只含 `sm_90`，无 PTX；准备部署到 GPU-A。

分别指出提案缺少哪些支持条件、兼容包实际改变哪一层，以及插件方案是否具备本次 Kernel 的完整代码覆盖。

### 6. 将三份故障快照分层

下表是三次不同故障的**自拟摘要**，每行内部来自同一次启动和同一节点。

| 快照 | 已有证据 |
| --- | --- |
| K | 运行内核 `.108`；`modinfo -k ...108... nvidia` 找不到模块；DKMS 只列 `.107: installed`；当前无已加载 `nvidia` |
| S | `.108` 模块文件存在、接口匹配；强制签名验证；日志明确记录密钥不受信任并拒绝加载 |
| D | 已加载核心模块 `.124.06`；本次 `nvidia-smi` 装载 NVML `.133.07` 并报告 driver/library mismatch；不使用兼容包 |

给每行选择优先检查对象与修复后的验证。K 能否直接认定是缺少头文件？S 能否通过重新打包应用 Runtime 解决？D 仅查磁盘 `modinfo` 是否足够？

### 7. 从路径推导实际装载

应用请求 `libcudart.so.12`；无 `DT_RPATH`，有 `DT_RUNPATH=$ORIGIN/../lib`，不在安全执行模式。其主程序在 `/opt/apps/vector/bin/`，启动环境为 `LD_LIBRARY_PATH=/opt/old-cuda/lib64`。两个目录均有相应库：环境目录为 12.0.146，应用目录为 12.8.90。

应先选哪一份？把 shell 的 `PATH` 改成 `/usr/local/cuda-12.8/bin` 能否直接改变本题的库选择？若没有其他错误材料，能否断言旧库已使本次应用失败？需要什么材料确认改动后的结果？

### 8. 确定成功记录的覆盖范围

运行节点没有 `nvcc`，但管理查询、实际库路径、设备初始化、一次分配复制、Kernel 同步与结果检查均通过。能确定完成了什么？若要评审部署可重复性，至少还应保留哪些身份与构建信息？这份记录能否证明第 04 章要讨论的 GPU 间传输正常？

## 参考答案与推导

### 1. 先分计算、管理与构建

计算路径可画为 `应用 → Runtime → libcuda / Driver API → 内核驱动 → GPU`；直接用 Driver API 的程序可省去 Runtime。管理路径是 `nvidia-smi → NVML → 内核驱动 → GPU 管理状态`，不经过 Runtime 才能查询。

`nvcc` 在构建路径，把主机与设备代码编译、链接成应用；GSP 固件随适用驱动分发，在设备侧承担部分初始化与管理工作。两者都不能放成“每个 Kernel 先经过的主机服务”。给定运行依赖完整，运行机缺 `nvcc` 不阻止已编译应用运行；编译器能输出版本也不证明驱动与 GPU 可用。静态链接 Runtime 的应用已经包含相应代码，不需要装载同名共享库；`ldd` 没列出 `libcudart.so` 与题设一致，仍需 GPU 驱动。

### 2. 每个版本对应一个对象

应用 ordinal 0 对应 B：原始 CUDA 设备 1 被筛选为唯一可见设备，再从 0 编号。推理使用了题设已确认的 CUDA 枚举顺序，没有借用管理工具编号。

12.6 是当前 shell 选中的编译器发行信息；应用构建时用了 12.8.1，运行时库还需按实际装载记录核对。页眉 12.8 表示驱动支持信息，不能证明安装了同版本 Toolkit。没有矛盾需要先“统一所有版本号”；应先明确各对象和依赖关系。

### 3. 初始化成功与执行完成分开

本章 CUDA 12.8 中，`cudaSetDevice(0)` 成功已表明该调用的 Runtime 与 Primary Context 初始化通过；随后分配和输入复制也成功。启动检查成功只说明当时没有报告相应启动问题，不能证明异步 Kernel 完成。

同步时观察到执行错误，应追踪前面提交的 Kernel、输入、设备状态和第一条错误；现有材料不能将同步函数本身定为根因。若装载器在启动阶段已找不到必需 Runtime，应先追库交付与解析，尚未到上述 CUDA 初始化过程。

### 4. 同时核对接口与代码

X 达到 Linux x86_64 的 CUDA 12.x 小版本兼容门槛，已有 GPU-A 的 `sm_80`，且题目排除了新特性与 JIT 限制，故给定驱动/代码条件成立。它仍不是实测成功记录。

Y 的目标能力适合 8.0，但只能走题设已失败的 PTX JIT，不能运行该 Kernel；门槛不会让旧 JIT 理解新 ISA。Z 的驱动达到本章基线，代码却不适合 8.0，需要重建或取得包含适用代码的程序；换 Toolkit 目录不改变现有文件。W 低于 525.60.13，本题未提供其他兼容路径，所以不在给定的 12.x 小版本兼容支持范围内。

### 5. 特殊路径不替代其他条件

兼容包方案需要核对具体 GPU 类别、驱动、包与 Toolkit 的官方组合及使用特性，不能写成任意设备通用。它提供特定 CUDA 用户态驱动/JIT 等库，需要配置实际库选择，不替换内核模块，也不提供任意新硬件能力，更不等同于更新 NVML。

插件是本次必需代码的一部分；主程序有 `sm_80` 无法替插件补上。插件只含 `sm_90` 且无 PTX，所以 GPU-A 的这条执行路径缺少代码覆盖，部署方案不成立。

### 6. 检查哪个状态没有接上

K 首先处理当前 `.108` 的模块交付或构建，查模块包与 DKMS 日志。缺头文件只是待验证原因之一；修复后先确认 `.108` 模块可查，再确认实际加载、设备管理查询与应用探针。

S 已经走到加载信任检查，需按系统策略提供受信任的签名或模块包；重新打包 Runtime 不会改变内核信任集合。修复后确认加载未再被拒绝、模块实际存在于运行内核中，再继续查询与探针。

D 是已加载模块与实际 NVML 版本未配套。需恢复受支持的配套状态并有计划地切换加载版本，然后重新核对已加载模块和新进程库路径；磁盘 `modinfo` 不能替代运行版本证据。三例都不支持在有活动作业时直接执行卸载或重启。

### 7. 按本题给定的解析条件判断

先选 `/opt/old-cuda/lib64/` 的 12.0.146，因为普通进程的 `LD_LIBRARY_PATH` 优先于此处的 `DT_RUNPATH`。修改 `PATH` 影响 shell 查找命令，不改变本题给定的共享库解析。

当前已经证明偏离交付清单，没有给出符号或调用失败，不能仅凭版本不同断定失败。应修订应用启动环境，再以实际装载记录证明选到 12.8.90，并按同样输入运行完整探针、对比首次错误或成功结果。

### 8. 单卡应用功能链与可重复条件

可以确定这次运行中单卡计算链完成了给定输入的工作，并通过结果检查，缺少编译器没有妨碍该已编译应用。复现所需信息至少包括：GPU UUID/PCI 与计算能力、实际内核和已加载驱动版本、用户态驱动路径、应用版本或校验标识、构建 Toolkit 与组件记录、设备代码目标、依赖库清单及实际路径、启动环境和输入条件。

记录没有覆盖 GPU 间传输、多卡拓扑、长时间负载或性能。不存在第二张参与测试的 GPU，就无法从单卡结果推导卡间链路的功能与带宽。

## 带着软件依赖进入下一章

到这里，可以用组件关系解释谁承担工作，用启动阶段确定已经完成什么，再分别核对版本与设备代码。在同一台主机上，“设备存在”“管理可见”“上下文可用”“Kernel 完成”和“结果正确”有各自证据。

第 04 章会继续追问：当复制对象从主机内存变成另一张 GPU 的显存时，请求实际经过哪些器件和链路，为什么同样的驱动与应用也会表现出不同带宽。这里建立的软件可用性是理解那些路径的前置。
