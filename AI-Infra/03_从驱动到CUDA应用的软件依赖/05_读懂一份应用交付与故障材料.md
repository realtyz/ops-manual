# 从交付清单和三份故障记录做判断

接手一个预编译 CUDA 应用时，先把三类材料对齐。交付清单要对应正在运行的产物，主机证据要来自同一次启动，应用错误要对应实际进程和所选 GPU。记录第一个失败的检查点，再选一项能区分剩余解释的证据。只拿到一句「GPU 不可用」时，这三类信息往往还缺至少一项。

## 先建立能重复的健康基线

下表是 **教学基线**，假设 Ubuntu 24.04 LTS、x86_64 Linux 裸机、单张未切分的 H100，正在运行的驱动是 `595.45.04`。用 `probe-sm90` 作为交付件。它启动一个线程把整数 7 写到显存，等待计算完成并拷回校验。构建版本及 GPU 架构取自 NVIDIA 文档，表内输出、启动标识和设备编号均用于推演。 [CUDA 13.2 GA Release Notes · CUDA Driver](https://docs.nvidia.com/cuda/archive/13.2.0/cuda-toolkit-release-notes/index.html#cuda-driver) · [NVIDIA GPU Compute Capability](https://developer.nvidia.com/cuda/gpus) · [Hopper Compatibility Guide](https://docs.nvidia.com/cuda/archive/12.6.0/hopper-compatibility-guide/index.html)

| 记录 | 教学基线 | 取证位置 |
| --- | --- | --- |
| 交付产物 | `probe-sm90`，Toolkit 13.2 GA，`--cudart=shared`，`-gencode=arch=compute_90,code=sm_90` | 构建清单，`cuobjdump --list-elf` 和 `--list-ptx` |
| 当前启动 | 启动记录 `boot-A0`，`6.8.0-51-generic`，内核模块 `595.45.04` | `uname -r`、`journalctl -k -b`、`/proc/driver/nvidia/version` |
| 目标设备 | H100（9.0），UUID 记作 `GPU-H100-A`，BDF `0000:65:00.0`，绑定 `nvidia` | `nvidia-smi --query-gpu=name,uuid,pci.bus_id --format=csv,noheader`、`lspci -nnk` |
| 进程依赖 | 应用装入 `/opt/probe/lib/libcudart.so.13` 和系统驱动提供的 `libcuda.so.1` | `readelf -d` 看声明，`LD_DEBUG=libs,files` 看实际路径 |
| 进程环境与结果 | `CUDA_VISIBLE_DEVICES` 未设。枚举到 1 张卡，应用设备 0 的 BDF 与管理侧相符。启动检查和同步均为 `cudaSuccess`，拷回 7 | 启动参数、环境与应用逐阶段输出 |

同步结果和拷回值表明这份产物在这组条件下完成了计算。复查时固定同一产物和启动环境。用 UUID 确认比较的是同一张卡，用本次启动日志对齐内核状态，用 BDF 将应用的设备 0 对上管理工具的记录。不同工具打印的 PCI 域可能补不同数量的前导零，比较时按字段值对齐。 [NVIDIA SMI · Selective Queries](https://docs.nvidia.com/deploy/nvidia-smi/index.html) · [CUDA 13.2.1 Runtime API · Device Management](https://docs.nvidia.com/cuda/archive/13.2.1/cuda-runtime-api/group__CUDART__DEVICE.html)

## 阅读三份独立的故障材料

案例 A 和 C 沿用教学基线的设备及未变更的条件，各自独立比较。案例 B 来自 Canonical 的公开故障示例，使用其实际公开的版本字段。先根据材料判断首个失败点，再和下文对照。

| 案例 | 已有材料 |
| --- | --- |
| A　新内核启动后查不到卡 | **教学记录。** 新启动记作 `boot-A1`，`uname -r` 为 `6.8.0-52-generic`。PCI 仍列出原 BDF，但该条目的 `Kernel driver in use` 未显示 `nvidia`。`lsmod` 无 `nvidia`，`/proc/driver/nvidia/version` 不存在。`modinfo -k "$(uname -r)" nvidia` 找不到模块。 |
| B　管理查询报驱动库版本失配 | **官方故障示例。** Canonical 文档里的 `nvidia-smi` 在 NVML 初始化时报告驱动与库版本失配。`NVRM: API mismatch` 给出客户端 `570.172.08`、内核模块 `570.158.01`。公开示例未注明 GPU 型号、当前内核或采集日期。 |
| C　能选卡，首个 Kernel 失败 | **教学记录。** H100 与 `595.45.04` 驱动，NVML 查询、CUDA 枚举和选卡均成功。程序首次检查 Kernel 启动结果时得到 `cudaErrorNoKernelImageForDevice`（209）。对实际提交这次 Kernel 的产物检查，只发现 `sm_80` cubin，PTX 列表为空。 |

案例 A 的观测方式参照 Ubuntu 的模块安装路径和 kmod 手册。案例 B 取自 Ubuntu Server 的公开说明。案例 C 的设备匹配与错误含义以 NVIDIA 文档为依据，报错时点设在首次使用该 Kernel。 [Ubuntu Server · NVIDIA drivers installation](https://ubuntu.com/server/docs/how-to/graphics/install-nvidia-drivers/) · [kmod · modinfo(8)](https://man7.org/linux/man-pages/man8/modinfo.8.html) · [Hopper Compatibility Guide](https://docs.nvidia.com/cuda/archive/12.6.0/hopper-compatibility-guide/index.html) · [CUDA Driver API · Error Codes](https://docs.nvidia.com/cuda/archive/13.2.1/cuda-driver-api/group__CUDA__TYPES.html)

### A　定位当前内核的模块

PCI 枚举已通过，最早失败的环节在 NVIDIA 模块与设备绑定一侧。对运行内核执行的 `modinfo` 也找不到模块，支持该内核的模块搜索树缺少可用的 NVIDIA 模块。先看部署方式。预编译模块查当前 ABI 对应的包，DKMS 查目标内核的构建与安装记录。若进一步找到模块文件，改查本次启动的内核日志，区分模块未被发现、因签名或 ABI 问题被拒，以及模块已装入但未绑定这张卡。复核时对齐内核、模块版本和 BDF，确认 `nvidia` 成功绑定，再重跑管理查询和 CUDA 最小程序。 [Ubuntu Server · NVIDIA drivers installation](https://ubuntu.com/server/docs/how-to/graphics/install-nvidia-drivers/) · [Linux Kernel · Module Signing](https://docs.kernel.org/admin-guide/module-signing.html)

### B　找到参与失配的两个版本

最早失败点是 NVML 与内核驱动交互。客户端与模块的完整版本不同，即使两者同属 R570 也存在失配。现场若只有 NVML 报错，先同时取 `/proc/driver/nvidia/version` 与该进程加载的 `libnvidia-ml.so.1` 实际路径。有了这一对，再用 `modinfo` 查磁盘模块版本，判断是用户态包先更新、旧模块仍在运行，还是启动环境选了另一套库。复核时用原启动环境重跑 `nvidia-smi`，确认它解析到预期的 NVML，能与正在运行的模块配合。 [Ubuntu Server · Driver/library version mismatch](https://ubuntu.com/server/docs/how-to/graphics/install-nvidia-drivers/#driver-library-version-mismatch-error) · [Linux man-pages · ld.so(8)](https://man7.org/linux/man-pages/man8/ld-linux.8.html)

### C　检查实际失败的 Kernel 来自哪里

已有成功的选卡记录，上下文已建立。首个失败点是使用该 Kernel 时未找到适用镜像。H100 的计算能力为 9.0，单独的 `sm_80` cubin 无法跨主计算能力装入，也没有 PTX 供 JIT。先确认镜像清单取自实际出错的可执行文件或共享库，尤其是程序按需装入扩展时。再保持主机、Runtime 和输入相同，只换同源且带 `sm_90` 的产物。若启动、同步和拷回校验均成功，就为设备代码目标的判断增加了单变量证据。 [Hopper Compatibility Guide](https://docs.nvidia.com/cuda/archive/12.6.0/hopper-compatibility-guide/index.html) · [CUDA Binary Utilities · cuobjdump](https://docs.nvidia.com/cuda/archive/13.2.1/cuda-binary-utilities/index.html)
