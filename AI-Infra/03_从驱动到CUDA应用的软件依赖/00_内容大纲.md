- **必要前置**　认识 Linux 进程、内核模块、PCIe 设备及设备文件，知道主机程序会提交 Kernel 给 GPU。就地补充共享库名称与实际文件路径、模块文件与已加载模块、计算能力与构建目标这三组概念。

## 01 驱动、Runtime 与 Toolkit 各在哪里

**问题与预期结论**　拿到一台能运行 `nvidia-smi`、找不到 `nvcc` 的机器，能判断它具备哪些能力吗？读完能按来源区分 Linux 驱动组件、应用携带的 Runtime 和构建工具，分别说明两条命令成功或缺失所能证明的范围。

**解释顺序**

1. 从 PCIe 枚举到设备绑定。主机侧 `nvidia.ko` 提供底层访问，`nvidia-uvm.ko` 承担 CUDA 相关的内核侧内存管理。以 H100 为例，把随驱动提供的 GSP 固件放在 GPU 侧，由 GSP 分担初始化和管理工作。对照区分系统能看到 PCI 设备、NVIDIA 模块已经装入、目标设备已绑定三种状态。
2. 在用户态分出两条路径。计算路径由应用经 Runtime API（`libcudart`，可静态或动态链接）进入 CUDA Driver API（Linux 由驱动的 `libcuda.so.1` 提供），应用也可直接调用 Driver API。管理路径由 `nvidia-smi` 调用 NVML（`libnvidia-ml.so.1`）。两条路径共用底层驱动与设备，各自要加载对应的用户态库。CUDA 库的实际解析和失配留给第 04 节。
3. 把 Toolkit 放回构建侧。它提供 `nvcc`、头文件和开发库等，预编译应用的运行条件由实际依赖决定。解释 PATH 中的 `nvcc --version`、`nvidia-smi` 上的驱动版本和 `CUDA Version` 各自的口径。后者是驱动支持的 CUDA 版本，新版工具文档使用 `KMD Version` 和 `CUDA UMD Version` 表明来源，字段以采集版本为准。具体安装包与旧 GPU 的驱动支持分别在第 04、03 节交代。

**支撑材料**

- 拟用一张 Mermaid 依赖图分出构建机、应用进程、主机内核与 GPU。图中画出 Runtime 和直接 Driver API 两种入口，另画 NVML 支路。用驱动 README 的组件清单与 GSP 固件示例核对文件归属及所在边界。 [NVIDIA R580.65.06 · Installed Components](https://download.nvidia.com/XFree86/Linux-x86_64/580.65.06/README/installedcomponents.html) · [NVIDIA R580.65.06 · GSP Firmware](https://download.nvidia.com/XFree86/Linux-x86_64/580.65.06/README/gsp.html)
- 拟列观测对照表，取 `nvidia-smi -q` 的驱动、CUDA 和 GSP 版本字段，`nvcc --version` 的编译器 release，以及 `lspci -nnk` 对应 BDF 的 `Kernel driver in use`。让读者分别判断管理通路、构建工具、设备绑定，并用“管理查询成功、编译器命令缺失”这个教学对照推导预编译应用还需验证什么。 [NVIDIA SMI · Query Attributes](https://docs.nvidia.com/deploy/nvidia-smi/index.html) · [NVML API Reference](https://docs.nvidia.com/deploy/nvml-api/nvml-api-reference.html) · [CUDA 13.2.1 · NVCC](https://docs.nvidia.com/cuda/archive/13.2.1/cuda-compiler-driver-nvcc/index.html)

## 02 一个 CUDA 进程怎样到达第一次计算

**问题与预期结论**　程序已启动，甚至能列出 GPU，为什么第一次选卡或提交 Kernel 仍会失败？读完能按主机库装载、设备枚举、上下文初始化、设备代码装载和提交完成逐项解释成功与失败的含义。

**解释顺序**

1. 从 ELF 进程启动讲起。已声明的共享库依赖由动态链接器解析，按需加载的库可在框架导入或调用时才出现，静态 Runtime 编入程序或库。区分主机侧加载 `.so` 与 CUDA 加载包含设备代码的 module。搜索路径留给第 04 节。
2. Runtime 示范沿 `cudaGetDeviceCount` → `cudaSetDevice(0)` → 最小计算走一遍。先读取枚举结果和进程内编号，用 `CUDA_VISIBLE_DEVICES=` 的空值说明管理查询仍可看到卡、应用却看不到设备。枚举失败或返回无可用设备时就记录结果，健康分支才继续选卡。再用选卡调用讲当前线程的设备选择、进程内每设备按需建立的 primary context，以及上下文与分配、Stream 等资源的关系。CUDA 12.0 起，`cudaSetDevice` 会初始化 Runtime 和所选设备的 primary context，旧版会把初始化推迟到后续需要的调用。旁列 Driver API 的 `cuInit` → `cuDeviceGetCount` → `cuDevicePrimaryCtxRetain` 并将上下文设为当前，说明两种入口对上下文管理的分工。
3. 继续到选取可用 cubin 或对 PTX 做 JIT、装入设备代码、提交和检查完成。把 CUDA module 的延迟加载作为改变报错位置的条件。CUDA 12.2 起 Linux 默认启用 lazy loading，要求 Runtime 至少 11.7、驱动分支至少 R515，并受 `CUDA_MODULE_LOADING` 和适用对象限制。区分同步点观察到的错误与实际出错阶段，Stream 调度细节归第 02 章，设备代码匹配规则放到下一节。

**支撑材料**

- 拟用 Mermaid 时序图分出应用、主机装载器、Runtime、Driver API 与 GPU，在“库解析”“枚举”“选卡”“第一次使用设备代码”“完成”处标注可观察结果。Driver API 的对照用调用序列呈现，初始化与延迟加载的分界按归档文档校对。 [CUDA 13.2.1 · Runtime Initialization](https://docs.nvidia.com/cuda/archive/13.2.1/cuda-programming-guide/02-basics/intro-to-cuda-cpp.html) · [Driver vs Runtime APIs](https://docs.nvidia.com/cuda/archive/13.2.1/cuda-driver-api/driver-vs-runtime-api.html) · [Driver API Initialization](https://docs.nvidia.com/cuda/archive/13.2.1/cuda-driver-api/group__CUDA__INITIALIZE.html) · [Lazy Loading](https://docs.nvidia.com/cuda/archive/13.2.1/cuda-programming-guide/04-special-topics/lazy-loading.html)

## 03 先查驱动兼容性，再查设备代码

**问题与预期结论**　应用用 13.2 构建，`nvidia-smi` 却显示驱动支持 CUDA 13.0，这个应用能在 H100 上运行吗？读完能分别判断应用的 CUDA API 和库需求、驱动提供的兼容路径、实际 GPU 能否运行交付件中的设备代码。

**解释顺序**

1. 先收集输入。固定 GPU 型号及计算能力、运行中的驱动分支和完整版本、应用构建 Toolkit 和 Runtime／额外库版本，以及可执行文件和实际失败的 `.so` 中的设备代码目标。构建信息优先取交付清单，动态库版本取实际装载记录，设备代码取产物。若机器有 `nvcc`，将它的版本单独登记。
2. 查 NVIDIA CUDA Compatibility 与对应 Toolkit 的 Release Notes。先说明新驱动运行旧应用的驱动向后兼容及其平台、应用依赖前提，再查同主版本的 minor version compatibility。比较 CUDA 13.2 GA 对应的 Linux 驱动版本 `595.45.04` 与 13.x 的 minor compatibility 下限 R580，说明 R580 上仍须确认应用所需功能和 PTX JIT。跨主版本的 forward compatibility 单列为受限路径，核对 GPU、操作系统、基础驱动分支、兼容包矩阵及进程实际加载路径。兼容包提供指定 CUDA 用户态驱动库，仍使用原内核模块，部分能力受基础驱动限制。
3. 再查 GPU 代码。用 `sm_80`、`sm_90` 和 `compute_80` 说明普通 cubin 和 PTX 的不同约束。H100（9.0）可执行 `sm_90` cubin。只有 `sm_80` cubin 时跨主计算能力无法加载。通用 `compute_80` PTX 在支持该 PTX 版本的驱动 JIT 下可面向 H100 生成代码。点出同一计算能力主版本内的普通 cubin 兼容规则，以及 `sm_90a`／`compute_90a` 这类特化目标的限制。用 CUDA 13.0 移除 Maxwell、Pascal、Volta 的离线编译和库支持补充 Toolkit 目标范围，旧产物能否运行仍要核对具体 GPU 与驱动支持。编译流程和特殊目标详表留作专题。

**支撑材料**

- 拟做三行驱动查表练习，固定 H100、Linux x86_64 与 CUDA 13.2 GA 构建。① `595.45.04` 对照该 Toolkit 随附驱动。② `580.65.06` 满足 13.x minor compatibility 的分支范围，带 `sm_90` 且无新驱动功能依赖时，可走该路径。将构建切成依赖 13.2 生成的 PTX 后，不能再凭分支范围得出可运行的结论。③ `570.124.06` 低于 R580，需查 `cuda-compat-13-2` 与 570+ 列的组合，并核对平台、SKU、库解析和功能限制。矩阵当前给出兼容条目，正文按版本和分支重新核对。三行均为依据官方表格的推演。 [CUDA 13.2 GA Release Notes · CUDA Driver](https://docs.nvidia.com/cuda/archive/13.2.0/cuda-toolkit-release-notes/index.html) · [Minor Version Compatibility](https://docs.nvidia.com/deploy/cuda-compatibility/minor-version-compatibility.html) · [Forward Compatibility · Support Matrix](https://docs.nvidia.com/deploy/cuda-compatibility/latest/forward-compatibility.html)
- 拟固定同一段最小计算，用 `-gencode=arch=compute_90,code=sm_90`、`-gencode=arch=compute_80,code=sm_80` 和 `-gencode=arch=compute_80,code=compute_80` 形成三份互相独立的目标配置。在驱动与 JIT 均满足 13.2 GA 产物需求的前提下，读 `cuobjdump --list-elf`、`--list-ptx` 与必要时的 `--dump-ptx`，把 cubin 架构与 PTX 的 `.target`、`.version` 分开。用 `CUDA_ERROR_NO_BINARY_FOR_GPU`（209）和 `CUDA_ERROR_UNSUPPORTED_PTX_VERSION`（222）对照“无适用镜像”与“有 PTX 但 JIT 不支持”。 [CUDA 13.2.1 · NVCC](https://docs.nvidia.com/cuda/archive/13.2.1/cuda-compiler-driver-nvcc/index.html) · [CUDA Binary Utilities](https://docs.nvidia.com/cuda/archive/13.2.1/cuda-binary-utilities/index.html) · [Hopper Compatibility Guide](https://docs.nvidia.com/cuda/archive/12.6.0/hopper-compatibility-guide/index.html) · [Driver API · Error Codes](https://docs.nvidia.com/cuda/archive/13.2.1/cuda-driver-api/group__CUDA__TYPES.html) · [CUDA 13.0 Release Notes · Deprecated Architectures](https://docs.nvidia.com/cuda/archive/13.0.0/cuda-toolkit-release-notes/index.html)

## 04 内核更新和库装载怎样让同一程序失效

**问题与预期结论**　重启或更新软件包后，为什么可能整机的管理查询失败，也可能只有一个程序失败？读完能用当前内核、已加载模块、磁盘模块和进程选中的库，定位断在构建、签名、版本一致性还是用户态库解析。

**解释顺序**

1. 从“已安装新内核”与“已启动新内核”拆开。把 `uname -r` 与对应内核 ABI 的预编译模块包或 DKMS 构建记录对齐。缺匹配内核头文件会影响 DKMS 构建，预编译模块路径检查对应内核 ABI 的包。模块存在仍可能因 ABI、符号版本或签名信任策略被拒。将模块签名字段与实际装载结果和内核日志交叉验证，区别签名告警、签名校验拒绝和构建失败。
2. 对照磁盘上的新模块和运行中的旧模块。用户态包已更新时，NVML 可能先装入新版库并遇到旧模块。用 Canonical 的 `NVRM: API mismatch` 示例分辨日志中的客户端版本和已加载模块版本。随后用实际库路径判断是一次升级留下的版本差，还是进程环境选到了其他目录的旧库。
3. 用 glibc 下单一 `DT_RUNPATH` 的例子解释搜索。对于无斜杠的库名、普通进程且没有旧式 `DT_RPATH` 时，`LD_LIBRARY_PATH` 可先于直接依赖的 `DT_RUNPATH`，之后才查缓存和默认目录。把“找不到库”“找到了错误文件或符号不匹配”“加载后驱动库与内核模块握手失败”分列。旧式 `DT_RPATH`、传递依赖和安全执行模式只交代会改变规则，完整部署与恢复流程放到第 18—19 章。

**支撑材料**

- 模块侧用 Ubuntu 官方示例的 `linux-modules-nvidia-${DRIVER_BRANCH}${SERVER}-$(uname -r)` 和匹配内核头文件的 DKMS 路径。拟并读 `uname -r`、`dkms status`（仅 DKMS 安装）、`modinfo -k "$(uname -r)" nvidia` 的 `filename`／`version`／`vermagic`／`signer`，以及 `lspci -nnk` 的绑定和 `journalctl -k -b` 的本次启动记录。用这些字段区分磁盘文件、构建结果、实际绑定及内核拒绝原因。 [Ubuntu Server · NVIDIA drivers installation](https://ubuntu.com/server/docs/how-to/graphics/install-nvidia-drivers/) · [Linux kbuild · External Modules](https://docs.kernel.org/kbuild/modules.html) · [Linux Kernel · Module Signing](https://docs.kernel.org/admin-guide/module-signing.html) · [kmod · modinfo(8)](https://man7.org/linux/man-pages/man8/modinfo.8.html)
- 版本失配拟引用 Canonical 的客户端 `570.172.08` 与内核模块 `570.158.01` 示例，并用 `/proc/driver/nvidia/version` 指认正在运行的模块。动态链接另用教学配置 `DT_NEEDED=libcudart.so.13`、`DT_RUNPATH=$ORIGIN/lib` 与 `LD_LIBRARY_PATH=/opt/old-app/lib`。假设两个目录均有同名库且进程未进入安全执行模式，先预测解析位置，再用 `readelf -d` 检查静态声明、`LD_DEBUG=libs,files` 检查实际选中路径及后续 `dlopen`。用同一 ELF 的两次启动验证环境如何改变选中的库。CUDA 13.2 动态 Runtime 的库名可对照 NVIDIA 官方镜像的链接记录。 [NVIDIA HPC SDK · CUDA 13.2 Runtime Image Layers](https://catalog.ngc.nvidia.com/orgs/nvidia/-/containers/nvhpc/26.5-runtime-cuda13.2-ubuntu22.04/layers) · [Ubuntu Server · Driver/library version mismatch](https://ubuntu.com/server/docs/how-to/graphics/install-nvidia-drivers/) · [Linux man-pages · ld.so(8)](https://man7.org/linux/man-pages/man8/ld-linux.8.html) · [Linux man-pages · dlopen(3)](https://man7.org/linux/man-pages/man3/dlopen.3.html)

## 05 从交付清单和三份故障记录做判断

**问题与预期结论**　接手一份预编译应用和几行报错，如何决定下一步该查宿主机、进程依赖还是构建产物？读完能把同一 GPU、同一启动批次和同一进程的证据对齐，写出“首个失败点、支持的判断、还需要验证的条件”。

**解释顺序**

1. 先读一份健康基线。交付侧登记 Toolkit 13.2 GA、`--cudart=shared`、动态依赖和设备代码目标。宿主机侧登记当前内核、驱动、H100 的 UUID／BDF、进程环境和已加载库。由一次最小计算的同步返回值验证这一份产物能在这一组条件下运行。
2. 对照下表三份独立材料，先找最早失败的检查，再用相邻层的证据排除其他解释。保留一次“日志不足时先取哪项证据”的追问，例如 NVML 失败但没有内核日志时，先对齐运行中的模块和进程实际加载的库。
3. 以复核条件收尾。模块问题复查当前内核对应的构建、签名和绑定，库版本问题复查实际路径与运行中模块，设备代码问题复查实际失败二进制的目标与 GPU，再重复受影响的最小调用。节点恢复编排、回滚窗口和 Xid 归因留给后续运维章节。
