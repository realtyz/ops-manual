# 链路显示 200G，为什么有效吞吐达不到 200G

一个端口显示 200 Gb/s，只给出了协商链路速率。要解释作业为什么慢，需要知道载荷完成了多少、选中了哪条路径、沿途哪些端口或队列有异常。下面用同一拓扑上的两组教学记录分别追踪拥塞与物理链路证据。 [NVIDIA NCCL Networking Troubleshooting](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/troubleshooting/networking_troubleshooting.html)

## 先把链路、端口和有效载荷的口径对齐

假设一条链路标称单向 200 Gb/s，十进制换算为 `25 GB/s`。同一方向、同一条路径、同一个 10 秒窗口，应用完成 `175 GB` 的有效载荷，对应 `175 × 8 ÷ 10 = 140 Gb/s`。路径上某个交换机出口的 TX 字节差值是 `200 GB`，按该端口计数口径折算为 `200 × 8 ÷ 10 = 160 Gb/s`。两个数分别是标称值的 70% 和 80%。端口统计范围可能包含头部、重复发送和其他流量。应用只记完成的有效载荷，所以不能直接用两者差值计算丢包量。端口字节计数也未必覆盖全部线上开销。 [Linux v6.12 mlx5 Ethtool counters，Groups](https://docs.kernel.org/6.12/networking/device_drivers/ethernet/mellanox/mlx5/counters.html) · [NVIDIA Cumulus Linux 5.11，RoCE 端口计数](https://docs.nvidia.com/networking-ethernet-software/cumulus-linux-511/Layer-1-and-Switch-Ports/Quality-of-Service/RDMA-over-Converged-Ethernet-RoCE/)

比较吞吐前固定消息大小、并发、方向、端点和采样时长，再核对实际路径。先看协商速率、链路宽度及链路起落，尤其留意是否降速或降宽。接着从路径上最窄的链路或割面算上界。即使两个 200 Gb/s 等价上联都可用，传统按流 ECMP 也可能把两条流送到同一上联。此时该上联的 200 Gb/s 才是这两条流共同面对的结构上限。 [NVIDIA Cumulus Linux 5.11，ECMP](https://docs.nvidia.com/networking-ethernet-software/cumulus-linux-511/Layer-3/Routing/Equal-Cost-Multipath-Load-Sharing/) · [NVIDIA NCCL Networking Troubleshooting，Physical link health](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/troubleshooting/networking_troubleshooting.html)

## 同一个网络上的两种慢例

以下两组记录均为自拟。设裸机 A0、A1 各用一个 RC QP 和本机 Rail 0 端口，分别向 B0、B1 的 Rail 0 写主机内存。每次写入 1 MiB，每 QP 最多 16 个在途请求。使用 A 侧 `A-L0`、B 侧 `B-L0` 和两个共享 spine `S0`、`S1`。所有链路都保持 200 Gb/s 全双工。两个测试窗口各为 10 秒，只统计 A→B 的载荷，配置参照 Cumulus Linux 5.11 的有 PFC 模式。两次建连得到的实际 ECMP 路径另行记录。表中以整数 GB 表示有效载荷，队列峰值取该窗口内的采样峰值，累计计数均取窗口增量。

| 同窗口观测 | 慢例 A | 慢例 B |
| --- | --- | --- |
| 两条流的上联 | 都走 `A-L0 → S0` | 去 B0 的流走 `S0`，去 B1 的流走 `S1` |
| `A-L0` 两个上联平均 TX 速率，按端口字节计数折算 | `196 / 0 Gb/s` | `105 / 105 Gb/s` |
| 两条流合计有效载荷 | `225 GB`，即 `180 Gb/s` | `220 GB`，即 `176 Gb/s` |
| `A-L0` 到 `S0` 的 RoCE 流量类队列采样峰值 | `2.0 MB`，反复积压 | `40 kB`，接近空闲期 |
| A 侧发送端收到的 CNP 增量，`A-L0` 向主机方向发出的 PFC 增量 | `6,800 / 300` | `0 / 0` |
| B0 NIC 物理端口 `rx_crc_errors_phy` 与 `rx_pcs_symbol_err_phy` 增量 | `0 / 0` | `42,000 / 310,000`，连续几个子窗口都在增长 |
| 其他观测 | 两条流均出现吞吐回落，路径上的物理错误计数稳定 | B0 对应流出现传输重试，B1 对应流稳定。B0 所在 `B-L0 swp1` 的出口队列也接近空闲期 |

**慢例 A。** 两条流在同一上联汇合，`S0` 方向逼近容量，另一条上联空闲。热点队列、CNP 和主机接入链路上的 PFC 增量支持拥塞及反馈已经发生的判断。要验证散列是这处热点的成因，可保持端点、消息大小和并发不变，在对照测试中验证两条流实际走了不同上联，再比较队列、暂停和有效吞吐。若只看到某个端口收到 PFC，还要向下游追对应的发送暂停端口和最先积压的队列。 [NVIDIA Cumulus Linux 5.11，ECMP 与按流散列](https://docs.nvidia.com/networking-ethernet-software/cumulus-linux-511/Layer-3/Routing/Equal-Cost-Multipath-Load-Sharing/) · [NVIDIA Cumulus Linux 5.11，RoCE 状态与计数器](https://docs.nvidia.com/networking-ethernet-software/cumulus-linux-511/Layer-1-and-Switch-Ports/Quality-of-Service/RDMA-over-Converged-Ethernet-RoCE/)

**慢例 B。** 上联较均衡，队列和反馈计数没有呈现慢例 A 的特征。B0 收包方向的 CRC 丢弃和未由 FEC 纠正的 PCS 符号错误在同窗持续增加，支持先调查 `B-L0 swp1 → B0 NIC` 的物理链路。CRC 计数按帧，PCS 符号错误按其字段定义，两个数字不能相加或直接换算成有效吞吐损失。用两端链路状态、FEC 模式、模块的接收光功率和温度等继续缩小范围。在光模块提供 DOM 数据时，可在交换机侧用 `nv show platform transceiver <接口>` 或 `ethtool -m <接口>` 读取，结合模块规格和对端的发送方向判断。若要区分光模块、光纤与端口，可在受控对照中只更换其中一项，再比较相同流量与采样窗口的错误率。 [Linux v6.12 mlx5 Ethtool counters，Physical Port](https://docs.kernel.org/6.12/networking/device_drivers/ethernet/mellanox/mlx5/counters.html) · [NVIDIA Cumulus Linux 5.11，Troubleshoot Layer 1](https://docs.nvidia.com/networking-ethernet-software/cumulus-linux-511/Monitoring-and-Troubleshooting/Troubleshooting-Network-Interfaces/Troubleshoot-Layer-1/)

## 读计数器时保留它能证明的范围

PFC 的收和发各代表一个方向。出口的流量类占用可结合丢弃增量判断是否出现缓存压力，历史峰值要先确认覆盖的区间。`rx_corrected_bits_phy` 记录被纠正的比特，可对照 `rx_bits_phy` 在同窗计算纠正比率、观察变化趋势。判断是否有受损帧被丢弃，再看 `rx_crc_errors_phy` 等字段和对端记录。队列积压与物理错误可能同时存在，某一次采样也可能错过突发。 [NVIDIA Cumulus Linux 5.11，RoCE 端口计数器](https://docs.nvidia.com/networking-ethernet-software/cumulus-linux-511/Layer-1-and-Switch-Ports/Quality-of-Service/RDMA-over-Converged-Ethernet-RoCE/) · [Linux v6.12 mlx5 Ethtool counters](https://docs.kernel.org/6.12/networking/device_drivers/ethernet/mellanox/mlx5/counters.html)

在原生 IB 上，换用对应端口的 `symbol_error` 和 `link_error_recovery` 查看物理符号错误与链路恢复，`port_xmit_discards` 增长时另查丢弃原因。`port_xmit_wait` 记录有数据待发却未发送的计数时段，原因可能是下游信用不足，也可能是没获得仲裁。比较任何设备的计数前，核对设备、物理端口、方向、单位、采样时长和是否回绕或重置。字段未提供时应标作缺测。 [Linux v6.6 InfiniBand sysfs ABI](https://docs.kernel.org/6.6/admin-guide/abi-stable.html) · [NVIDIA Base Command Manager，InfiniBand Metrics](https://docs.nvidia.com/base-command-manager/product-manuals/11/admin/metricshealthchecksactions)
