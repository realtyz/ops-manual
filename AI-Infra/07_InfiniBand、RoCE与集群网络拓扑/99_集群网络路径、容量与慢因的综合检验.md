# 集群网络路径、容量与慢因的综合检验

学完协议封装、拓扑容量、机柜级 NVLink 域与拥塞取证后，现在把整章知识放到五个贴近真实生产现场的排障与架构推演场景中做一次闭卷检验。建议先不展开底部的参考推理，自己拿笔把每一题的路径、算式和证据边界独立推出来。

## 一、基础环境设定（第 1–3 题共用）

两座标准机架（源机架与目的机架）各部署 4 台 GPU 服务器，采用两层 Spine-Leaf 双 Rail 共享脊交换机 RoCEv2 网络，具体拓扑与通信参数汇总如下：

| 维度 | 具体配置与角色映射 |
| --- | --- |
| **物理链路规格** | 全部主机下联与交换机上联均为 `200 Gb/s` 全双工（单向理论线速 `25 GB/s`），开启无损 ECN + PFC 模式 |
| **接入层与核心层** | 每机架 2 台接入交换机（Rail 0 Leaf 与 Rail 1 Leaf）；四台 Leaf 各自上联 2 台共享脊交换机（`Spine-1`、`Spine-2`） |
| **并发通信流** | 源机架的 `node-1`、`node-2` 各自通过 Rail 0 网卡建立 1 条 RC 连接，分别向目的机架的 `node-3`、`node-4` 持续写入主机内存，每条流尝试速率均为 `160 Gb/s` |
| **代表端口映射** | `node-1` 计算口为 `ens3f0`（IP `192.0.2.11/24`，对应 `mlx5_0/1`）；`node-3` 计算口为 `198.51.100.22/24`，经目的 Rail 0 Leaf 的 `swp1` 口接入；`node-4` 使用独立接入口 |

## 二、五道实战检验题

### 题 1：跨子网 RoCEv2 选址与验证边界

在 `node-1` 上以源地址 `192.0.2.11` 查询前往 `198.51.100.22` 的路由，返回出口 `ens3f0`、首跳网关 `192.0.2.1`，且 ARP 邻居可达。

继续核查对应 RDMA 端口 `mlx5_0/1` 的 GID 表发现：索引 `2` 和 `3` 的值均为 `::ffff:192.0.2.11` 且均关联 `ens3f0`，但索引 `2` 类型为 `IB/RoCE v1`，索引 `3` 类型为 `RoCE v2`。

1. `node-1` 的 QP 应选用哪一条 GID 索引？
2. 画出经 `Spine-1` 抵达 `node-3` 的候选路径，指出**首跳帧的目的 MAC**、**末跳帧的目的 MAC**以及**全程的目的 IP 与 UDP 目的端口**。
3. 在 `node-1` 指定源地址 `192.0.2.11` 执行 `ping 198.51.100.22` 成功，它能确认什么，还缺哪些验证才能确认应用级 RC 写入畅通？

### 题 2：脊交换机故障后的割面折算与队列积压

健康状态下，两条 `160 Gb/s` 长流经 ECMP 恰好分散在 `Spine-1` 与 `Spine-2` 上。随后 `Spine-1` 突然宕机，路由快速收敛且其余设备保持健康，两条流继续维持原速率发送。

1. 计算 `Spine-1` 故障前后的**跨机架单向整机架割面上界**。
2. 故障后，这两条同属 Rail 0 的流实际能共享的最大上联带宽上界是多少？为什么用不上 Rail 1 的空闲带宽？
3. 暂不计封装开销与拥塞反馈，若故障后队列初始为空、两条流维持原速持续 `20 µs`，受压出口会形成多少字节的队列积压？

### 题 3：同一窗口内的“拥塞 + 物理误码”混合慢因拆解

在 `Spine-1` 故障后的一个 `10 s` 采样窗口中，记录到如下一组混合证据：
- 两条流合计完成有效载荷 `195 GB`；
- 源 Rail 0 Leaf 通往 `Spine-2` 的上联 TX 字节折算为 `190 Gb/s`，其 RoCE 队列反复积压；
- `node-1` 与 `node-2` 的网卡均收到 CNP，且源 Rail 0 Leaf 在主机下联口发出了 PFC 暂停；
- 与此同时，`node-3` 物理网卡的接收口持续录得不断增长的 `rx_crc_errors_phy` 计数。

1. 复算这两条流的合计**应用有效吞吐（Goodput，单位 `Gb/s`）**。
2. 指出上述两类异常分别发生在哪一段物理路径、哪个方向，为什么不能把总吞吐损失简单归咎于其中单一因素？
3. 设计一套受控对照实验，用来验证“恢复双脊交换机后若依然偏慢，真凶到底卡在哪一个硬件部件”。

### 题 4：跨互联迁移——原生 IB 分区与机柜级 NVLink 域

1. **原生 IB 变体**：两台节点接入单子网原生 InfiniBand，两端 `ibstat` 均显示 `LinkUp` 与 `Active`，`ibtracert` 显示目的 LID 路径完整。应用在 `Train` 分区为两端 QP 选中的 P_Key 均为 `0x0021`，而另外配在 `0x8022` 上的 IPoIB 子接口可以互相 `ping` 通。为什么应用依然通信失败？只需改动哪一项条件即可放通？
2. **机柜级 Scale-up 变体**：在 **DGX GB200 NVL72** 平台上，两张 B200 GPU 位于同一个机架内、属于不同的计算托盘（两个独立的 Linux 操作系统实例），但同属该机柜的 72 卡 NVLink 域。能否仅凭“分属两台独立主机”断定它们必须经 ConnectX-7 网卡和外部 NDR InfiniBand 通信？

### 题 5：在线推理 PD 分离场景的微突发与 PFC 连坐效应

切换到 **PD 分离大模型推理集群**（链路为 `200 Gb/s` 全双工无损 RoCEv2，TC 3 承载 RoCE 数据），某时刻在目的机架 Leaf 下行出口出现如下并发状态：

| 并发流量 | 流量特征与队列归属 |
| --- | --- |
| **KV Cache 迁移流** | 3 个 Prefill 实例同时向同一台 Decode 节点推送 KV Cache，每路注入速率 `100 Gb/s`，形成持续 `30 µs` 的三对一 Incast 突发（归属 TC 3） |
| **在线推理同步小消息** | 另一组低带宽、对微秒级延迟极度敏感的推理通信，与 KV 迁移共用同一出口与同一无损队列（TC 3） |

1. 忽略协议头与早期反馈，计算 `30 µs` 后该汇聚出口的净积压字节数，以及紧跟在队尾的一条在线推理小消息仅排队就需要多等多少微秒？
2. 如果突发继续拉长并触发目的 Leaf 向上游发送 TC 3 的 PFC 暂停帧，为何会直接打穿其他无辜推理请求的 TPOT SLO？从队列调度与架构隔离角度，可以采取哪两项改进措施？

## 三、分步参考推理

> [!example]- 点击展开五道检验题的完整参考推理与推导过程
>
> ### 题 1 参考推理：先锁出口与 GID 类型，再划清验证边界
> 1. **选定 GID 索引 `3`**：跨 IP 子网通信必须使用封装在 IP/UDP 内的 `RoCE v2`；索引 `2` 虽然 IP 数值相同，但属于仅限二层广播域的 `IB/RoCE v1`，出了网关即被丢弃。
> 2. **候选路径与报文头部变化**：
>    - 路径：`node-1 (ens3f0 / mlx5_0/1) → 源 Rail 0 Leaf → Spine-1 → 目的 Rail 0 Leaf (swp1) → node-3`。
>    - 首跳以太网目的 MAC：`192.0.2.1` 对应的首跳网关 MAC；末跳以太网目的 MAC：`node-3` 计算网卡的 MAC；全程外层目的 IP 保持 `198.51.100.22`、UDP 目的端口固定为 `4791`。
> 3. **`ping` 的验证边界**：带源地址的 `ping` 成功仅确认了两端 IP 路由可达、首末跳 ARP 正常且 ICMP 往返畅通。要真正验通 RC 写入，还需核对对端 RoCEv2 GID、两端 QP 状态、网络放行 UDP `4791`、沿途路径 MTU 满足 QP 要求，并实际执行一次满尺寸 RDMA Write 校验结果。
>
> ### 题 2 参考推理：分清“整机架割面”与“单 Rail 实际可用上联”
> 1. **跨机架单向割面上界**：
>    - 健康时，源、目的机架各有 4 条 `200 Gb/s` 上联，割面上界为 $\min(4 \times 200,\; 4 \times 200) = 800\text{ Gb/s}$。
>    - `Spine-1` 故障后，两端各剩 2 条通往 `Spine-2` 的上联，整机架单向割面腰斩至 $\min(2 \times 200,\; 2 \times 200) = 400\text{ Gb/s}$。
> 2. **双流实际共享上联上界**：这两条流绑定在 Rail 0 网卡上，均从源 Rail 0 Leaf 发出。`Spine-1` 宕机后，该 Leaf 仅剩通往 `Spine-2` 的 **1 条 `200 Gb/s` 上联**，因此双流合计上限只有 `200 Gb/s`。Rail 1 的 `200 Gb/s` 幸存上联挂在另一台 Leaf 下，除非应用显式改用 Rail 1 网卡或跨平面重路由，否则无法分摊 Rail 0 的流量。
> 3. **`20 µs` 队列积压推导**：
> $$
> R_{\text{净积压}} = 2 \times 160 - 200 = 120\text{ Gb/s}
> $$
> $$
> Q = \frac{120 \times 10^{9}\text{ bit/s} \times 20 \times 10^{-6}\text{ s}}{8} = 300{,}000\text{ B} = 300\text{ kB}
> $$
>
> ### 题 3 参考推理：按物理位置与方向拆开双故障，用单变量对照定责
> 1. **有效吞吐复算**：
> $$
> \text{Goodput} = \frac{195\text{ GB} \times 8}{10\text{ s}} = 156\text{ Gb/s}
> $$
> 2. **两类现象的位置与方向拆分**：
>    - **共享上联拥塞**：发生在**源 Rail 0 Leaf → `Spine-2`** 的上行出口（`190 Gb/s` 逼近线速、队列反复积压），随后经端到端 CNP 反馈到 `node-1`/`node-2`，并在源 Leaf 主机下联口触发了 PFC 暂停请求。
>    - **物理接收链路误码**：发生在**目的 Rail 0 Leaf `swp1` → `node-3` 网卡**的接收方向（`rx_crc_errors_phy` 持续攀升），引发流向 `node-3` 的报文损坏与重试。
>    - 现有同窗汇总数据能证明两处故障同时存在，但无法把丢失的吞吐直接按比例分摊给二者，必须分别取证。
> 3. **单变量对照排查方案**：先恢复 `Spine-1` 并确认两条流经 ECMP 分散到两条不同上联，同条件下复测 `10 s` 窗口；若上联队列、CNP 与 PFC 归零，但 `node-3` 方向仍有 `rx_crc_errors_phy` 增长和重试掉速，即锁定 `swp1 → node-3` 物理段。
>    - 随后读取两端光模块 DOM 诊断与 FEC 模式，**每次只更换单个部件**（跳线、交换机光模块、网卡光模块或端口）并复测，直至误码清零。
>
> ### 题 4 参考推理：把原理迁移到 IB 分区与超节点 NVLink 域
> 1. **IB 分区放通**：`0x0021` 最高位为 `0`，说明两端均为**受限成员（Limited Member）**；IB 规则禁止 Limited ↔ Limited 互通。
>    - 只需保持低 15 位分区号 `0x0021` 不变，在 OpenSM 中把至少一端改为完整成员（生效键值 `0x8021`），确认 QP 选用该表项即可；`0x8022` 的 IPoIB `ping` 无法替 `Train` 分区背书。
> 2. **NVL72 同域判断**：**不能。** 在机柜级 Scale-up 架构（如 DGX GB200 NVL72）中，NVLink 域已跨越“单个操作系统计算托盘”的物理边界。
>    - 只要两张 GPU 同处一个健康的 72 卡 NVLink 域且通信栈就绪，数据便直接走机柜内 NVLink Switch（单卡单向 `900 GB/s`），不经过 ConnectX-7 与外部 IB 网；仅跨出机柜域时才步入 Scale-out 网。
>
> ### 题 5 参考推理：定量看透推理微突发与 PFC 队头阻塞
> 1. **微突发积压与队尾串行排队延迟**：
> $$
> R_{\text{净积压}} = 3 \times 100 - 200 = 100\text{ Gb/s}
> $$
> $$
> Q = \frac{100 \times 10^{9}\text{ bit/s} \times 30 \times 10^{-6}\text{ s}}{8} = 375{,}000\text{ B} = 375\text{ kB}
> $$
> $$
> T_{\text{排队等待}} = \frac{375{,}000 \times 8\text{ bit}}{200 \times 10^{9}\text{ bit/s}} = 15\text{ }\mu\text{s}
> $$
> 2. **PFC 连坐效应与治理思路**：
>    - **为何打穿 TPOT SLO**：PFC 是按整个优先级队列（TC 3）一刀切暂停的。一旦三路 KV 突发打穿目的 Leaf 入口阈值并触发 PFC 暂停（甚至背压传回上游 Spine），同一链路、同一队列里原本极轻量的在线推理小消息会被整队“冻住”，导致所有无辜请求的每层同步延迟剧烈抖动，瞬间击穿 P99 TPOT SLO。
>    - **两项核心改进**：
>      - **流量分级隔离（QoS 分队列）**：用不同 DSCP 把大块异步 KV 迁移与低延迟同步推理小消息拆进不同流量类，或将高吞吐 KV 迁移独立到专用网络平面/Rail；
>      - **端侧发送限速与流控选型**：对 Prefill 侧 KV 推送做发包节奏整形（Pacing）抑制瞬时 Incast 峰值，并审慎调优低水线 ECN（或评估无 PFC 的 Lossy + 选择性重传）与 PFC 看门狗，杜绝队头阻塞。

## 四、全章收束：把路径、容量与证据串成一张网

回顾第 07 章走过的完整链条，排查或设计任何大规模 GPU 集群网络，都可以按下面四道关卡自顶向下推进：

1. **先判域界（Scale-up vs Scale-out）**：先确认通信双方是否同处一个高速 NVLink 域（单机 8 卡或机柜级 72 卡）；只有跨出域界的流量才进入外部计算网卡与交换机。
2. **再通控制面（封装与寻址）**：原生 IB 看 Subnet Manager、LID 与 P_Key 成员角色；RoCEv2 看 Linux 路由出口、ARP 邻居、RDMA 端口、v2 类型 GID 与全路径 MTU。
3. **三算硬容量（拓扑与故障域）**：画 Spine-Leaf 拓扑算收敛比和单向割面，按多 Rail 映射核对物理布线，识别独立与共享故障域，并防备大象流的 ECMP 静态哈希碰撞。
4. **四对齐证据（吞吐、队列与物理层）**：在同时间窗和同一方向上，把应用 Goodput、交换机队列峰值/ECN/PFC 与网卡物理层 CRC/PCS/FEC 计数器拼在一起，兼顾训练吞吐退化与推理微突发尾延迟抖动。
