# 有效吞吐、拥塞与物理链路证据

集群里最让运维抓狂的现场长这样：**所有光口协商速率都是 `200 Gb/s`、端口状态全是 `ACTIVE`，可两台机器跑同样的数据传输，吞吐却双双掉下了一大截——甚至有时候平均速率看起来平平无奇，在线推理的 P99 尾延迟却突然飙升十倍。**

端口协商速率只是物理层签下的“纸面合同”，绝不等于应用真正拿到手的有效载荷。想把“ECMP 路由拥塞”和“光纤物理层误码”彻底拆开，必须把**应用载荷、交换机端口计数和网卡底层计数器**锚定在同一个方向、同一条实际路径和同一个时间窗里交叉比对。

## 一、对齐同一时间窗内的三种速率口径

在一条单向标称 `200 Gb/s`（十进制换算 `25 GB/s`）的链路上，设我们在同一个 `10 s` 观测窗口内录得两条数据：上层应用确认完成了 `175 GB` 有效载荷，而沿途某交换机出口的 TX 字节计数在同一窗口增长了 `200 GB`。先把三者统一换算到 `Gb/s`：

$$
\text{应用有效吞吐（Goodput）} = \frac{175\text{ GB} \times 8}{10\text{ s}} = 140\text{ Gb/s}\quad（\text{标称线速的 } 70\%）
$$

$$
\text{交换机端口发送速率} = \frac{200\text{ GB} \times 8}{10\text{ s}} = 160\text{ Gb/s}\quad（\text{标称线速的 } 80\%）
$$

这 `20 Gb/s` 的差值包含以太网/IP/UDP/RDMA 各层协议头开销、潜在的协议重传，以及同端口可能混杂的其他流量；在不拆解具体组成前，绝不能拿差值直接倒推丢包率。

做任何两次性能对照时，必须先锁定变量：**固定收发节点、缓冲区类型、消息大小、并发度、统计方向和计时起点**，并确认流量实际经过的交换机端口，再去读该路径上的队列与误码计数。

## 二、实战同窗对比：ECMP 热点拥塞 vs 物理接收误码

下面把两类最常被混淆的慢故障放进完全相同的测试条件里：双机架双 Rail RoCEv2 网络（Cumulus Linux 5.11 无损模式，链路全 `200 Gb/s`），源机架两台节点各开 1 条 RC 连接，经 Rail 0 向目的机架两台独立接收节点持续写入 `1 MiB` 数据块（每 QP 最多 16 个在途请求），统计两个 `10 s` 窗口的跨架单向数据。

| 同时间窗观测维度 | 慢例 A（ECMP 热点拥塞） | 慢例 B（物理接收链路受损） |
| --- | --- | --- |
| **两条流实际经过的 Spine** | 两条流全撞在同一台 Spine 上 | 两条流均匀分散到两台 Spine |
| **源 Leaf 两条上联 TX 平均速率** | `196 Gb/s` / `0 Gb/s`（严重偏斜） | `105 Gb/s` / `105 Gb/s`（均衡余量充足） |
| **双流合计有效载荷（Goodput）** | `225 GB`（`180 Gb/s`） | `220 GB`（`176 Gb/s`） |
| **热点上联的 RoCE 队列峰值** | `2.0 MB`（反复剧烈积压） | `40 kB`（接近空闲基线） |
| **发送端收到 CNP / 接入侧发出 PFC** | `6800` / `300`（拥塞闭环频繁触发） | `0` / `0`（全程无拥塞反馈） |
| **接收节点 1 的 `rx_crc_errors_phy` / `rx_pcs_symbol_err_phy`** | `0` / `0` | **`+42,000` / `+310,000`**（连续子窗口攀升） |
| **两条流各自表现** | 两条流**同步掉速** | 仅流向受损端口的那条流**频发重试掉速**，另一条流稳如磐石 |

看数字最直观：**两个慢例的总有效吞吐几乎一模一样（`180 Gb/s` vs `176 Gb/s`），光看应用层监控根本分不出谁是谁！** 但只要把交换机与网卡的同窗计数器并排拉出来，真凶瞬间原形毕露：

```bash
# ===== 1. 交换机侧（Cumulus Linux 5.11）：查热点上联队列与 PFC =====
cumulus@leaf-src:~$ nv show interface swp49 qos roce counters
Traffic Class 3 (RoCE):
  tc-usage                   : 1.2 MB
  tc-max-usage               : 2.0 MB    # 慢例 A：队列反复冲高至 2 MB，证实严重排队
  unicast-no-buffer-discard  : 0
  tx-pfc-stats.pause-packets : 300       # 接入下行口向发送节点发出了 300 帧 PFC 暂停

# ===== 2. 网卡侧（发送与接收节点）：查 RoCE 拥塞硬件计数与物理误码 =====
# 在发送节点查 DCQCN 降速动作（Reaction Point）
$ grep . /sys/class/infiniband/mlx5_0/ports/1/hw_counters/{rp_cnp_handled,np_cnp_sent}
.../rp_cnp_handled:6800                  # 慢例 A：发送网卡已处理 6800 个 CNP 并主动降速

# 在接收节点查以太网物理层误码、FEC 纠错与优先级暂停计数
$ ethtool -S ens3f0 | grep -E 'rx_crc_errors_phy|rx_pcs_symbol_err_phy|rx_corrected_bits_phy|rx_bits_phy|prio3_pause'
     rx_prio3_pause: 0
     tx_prio3_pause: 0
     rx_crc_errors_phy: 42000            # 慢例 B：物理口收到 4.2 万个校验损坏帧（按帧计）
     rx_pcs_symbol_err_phy: 310000       # 慢例 B：FEC 无法纠正的编码符号错误（按符号计）
     rx_corrected_bits_phy: 89402110     # FEC 勉强救回的比特数，与 rx_bits_phy 做比值可跟踪误码率恶化
     rx_bits_phy: 10500000000000

# ===== 3. 光模块数字诊断（DOM）：排查光衰、脏污与温升 =====
cumulus@leaf-dst:~$ nv show platform transceiver swp1   # 宿主机侧可用 ethtool -m ens3f0
```

### 拆解慢例 A：锁定 ECMP 哈希偏斜

热点上联的 TX 速率高达 `196 Gb/s`（已贴死 `200 Gb/s` 天花板），而另一条等价上联纹丝不动；叠加 `2.0 MB` 队列峰值、发送端 `rp_cnp_handled` 暴涨以及接入侧发出 PFC，四组证据严丝合缝指向**双流撞在同一条上联出口**。

验证手段非常干净：保持端点、消息尺寸与并发完全不变，调整多 QP 或散列因子让两条流分开走两台 Spine 后复测。只要热点、队列和 CNP 同步消失、吞吐立刻恢复，就能盖棺定论。

### 拆解慢例 B：把范围缩死到单向物理链路

两条 Spine 上联均只跑了一半速率、零排队、零 CNP/PFC，彻底排除了网络拥塞。而故障节点的 `rx_crc_errors_phy`（受损以太网帧）与 `rx_pcs_symbol_err_phy`（前向纠错 FEC 救不回来的物理编码符号错误）在连续子窗口里持续飙升，且只有飞往该网卡的那条流在重传。

这把嫌疑范围精准框死在**目的 Leaf 发送端 → 光模块/光纤 → 接收节点网卡接收端**这一条单向物理段上。接下来先用 `nv show platform transceiver` 或 `ethtool -m` 检查收发光功率（DOM）与两端 FEC 模式，再采用**受控单变量替换法**（每次只换光模块、跳线或交换机端口中的一个并同条件复测），就能精准揪出坏件。

## 三、训推排障盲区：为什么平均吞吐正常，推理延迟却炸了？

在排查慢故障时，**分布式训练**与**在线推理**最容易让人看走眼的指标维度截然不同：

| 负载类型 | 典型症状 | 常见观测盲区 | 优先紧盯的网络计数器 |
| --- | --- | --- | --- |
| **分布式训练** | Step 耗时拉长、MFU 下降 | 仅看单卡协商速率，忽略跨机架 ECMP 上联偏斜 | 多秒窗 TX 均值、热点上联 `tc-usage`、发送端 `rp_cnp_handled`、接收端 `rx_crc_errors_phy` |
| **在线推理（TP/EP 与 PD 分离）** | 平均吞吐看似平稳，但 **TTFT / TPOT P99 尾延迟骤然拉高** | **10 秒平均端口速率极低（如 `30 Gb/s`）完全掩盖了亚毫秒级微突发！** | 交换机峰值字段 **`tc-max-usage`**、短窗 **`tx/rx-pfc-stats`** 暂停时长（`pause-duration`）、FEC 纠错率突变与小包重传 |

> [!warning] 常见误区：绝对不要拿 10 秒平均速率否定推理微突发
> 在 PD 分离推理集群里，一次 40 µs 的多对一 KV 突发就能打出 40 µs 以上的额外排队或触发短暂 PFC 暂停，足以让在线请求的 P99 尾延迟剧烈抖动；但摊平到 10 秒平均带宽曲线上，这几十微秒几乎连个毛刺都看不出来。排查推理尾延迟时，必须读取交换机的**队列峰值（`tc-max-usage`）**与 **PFC 累计时长**，不能只看平均带宽。

## 四、读懂计数器的方向、单位与原生 IB 对照

跨工具比对网络证据时，务必守住三条“防误读铁律”：

1. **分清方向**：在 Cumulus Linux 5.11 里，`rx-pfc-stats` 是本口收到对端喊停的暂停帧，`tx-pfc-stats` 是本口向上游喊停发出的暂停帧，各自细分为 `pause-packets`（帧数）与 `pause-duration`（累计暂停时长）；网卡侧 `rx_prio3_pause` 与 `tx_prio3_pause` 同理。发了 PFC 必须去对端看是否真正收到并减速。
2. **严禁跨单位硬算**：`rx_crc_errors_phy` 按**帧**计，`rx_pcs_symbol_err_phy` 按**编码符号**计，`rx_corrected_bits_phy` 按**比特**计——三者绝不能相加或直接折算成字节吞吐损失；但可以用 `rx_corrected_bits_phy` 与同窗 `rx_bits_phy` 之比持续追踪光纤劣化趋势（在彻底出现 CRC 丢包前提前预警）。
3. **对齐原生 InfiniBand 对应口径**：原生 IB 没有以太网 PFC，而是用**虚拟通道（Virtual Lane，VL）信用流控**控制发送节奏。在 IB 网络里排查“拥塞等待 vs 物理受损”，对应观察以下四组核心计数器：
   - **拥塞与信用等待**：`port_xmit_wait` 持续飙升，代表端口队列里有数据待发，但整段时隙因缺少对端接收信用或仲裁受阻而干等；
   - **物理层受损**：`symbol_error`（物理符号错）与 `link_error_recovery`（链路恢复重试）同步增长，直接指向线缆或光模块劣化；
   - **发送侧丢弃**：`port_xmit_discards` 增长时，需结合设备定义排查目的不可达、P_Key 拦截或超时丢弃。

> [!summary] 核心结论
> 无论以太网 RoCEv2 还是原生 InfiniBand，排障都遵循同一条铁律：**先固定同时间窗与单向路径，再把“有效载荷、队列峰值/拥塞反馈、物理误码”三组证据摆在同一张桌子上**。拥塞与物理误码完全可能同时并存，唯有逐项拆解才能开对药方。
