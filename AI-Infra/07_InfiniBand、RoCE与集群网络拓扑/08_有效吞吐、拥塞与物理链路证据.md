
两个端口都显示 200 Gb/s，作业完成的有效载荷仍可能相差很大。协商速率描述链路能力，网络端口计数描述实际流量在设备上的一处观测，应用还要等待自己的传输完成。把三个量放到同一方向、端口和时间窗，才能顺着路径解释吞吐为何下降。 [NVIDIA NCCL Networking Troubleshooting，Physical Link Health 与低层测试](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/troubleshooting/networking_troubleshooting.html)

## 用同一个窗口换算三种速率

设一条单向标称 200 Gb/s 的路径，十进制换算为 25 GB/s。一次 10 秒教学记录中，应用确认完成 175 GB 的有效载荷，沿同方向的一个交换机出口 TX 字节增量是 200 GB。应用有效吞吐是 `175 × 8 ÷ 10 = 140 Gb/s`，该端口按其字节口径算得 `200 × 8 ÷ 10 = 160 Gb/s`。按标称速率归一时，两者分别为 70% 和 80%。端口计数可能还包含头部、重复传输或其他流量，也可能省略部分线上开销。两者的 20 Gb/s 差值没有逐项拆分，不能据此反算丢包。 [Linux v6.12，mlx5 Ethtool Counters](https://docs.kernel.org/6.12/networking/device_drivers/ethernet/mellanox/mlx5/counters.html) · [NVIDIA Cumulus Linux 5.11，RoCE 端口计数](https://docs.nvidia.com/networking-ethernet-software/cumulus-linux-511/Layer-1-and-Switch-Ports/Quality-of-Service/RDMA-over-Converged-Ethernet-RoCE/)

对照两次传输时，固定端点、缓冲区类型、消息大小、并发、方向和计时方法，再确认实际走的端口与路径。由路径先算最窄链路，或为多条流算有向割面。如果只看协商速率，有可能漏掉降宽或偶发链路起落，也可能漏掉多条流共同挤进一个健康出口。队列与物理计数需要沿实际路径逐处对齐。 [NVIDIA Cumulus Linux 5.11，ECMP](https://docs.nvidia.com/networking-ethernet-software/cumulus-linux-511/Layer-3/Routing/Equal-Cost-Multipath-Load-Sharing/) · [NVIDIA NCCL Networking Troubleshooting，Physical Link Health](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/troubleshooting/networking_troubleshooting.html)

## 同一拓扑中的上联热点与物理错误

下表为自拟教学记录。两台裸机 A0、A1 各用一个可靠连接（RC）的队列对（QP），分别向 B0、B1 写主机内存。两条流都用 Rail 0，经过 `A-L0`、共享 spine 和 `B-L0`，分别走各自的 B 侧接入链路。每次写入 1 MiB，每 QP 最多 16 个在途请求。所有链路在记录中保持 200 Gb/s 全双工，交换机采用 Cumulus Linux 5.11 的有 PFC 模式作为示例。两个窗口各为 10 秒，均统计 A→B 载荷。队列取窗口内采样峰值，端口字节和其他累计计数取窗口首尾差，载荷按十进制 GB 取整。B0 通过 `B-L0 swp1` 接入。

| 同窗证据 | 慢例 A | 慢例 B |
| --- | --- | --- |
| 两条流实际经过的 spine | 都走 `S0` | 去 B0 走 `S0`，去 B1 走 `S1` |
| `A-L0 → S0` 与 `A-L0 → S1` 的端口 TX 平均速率 | `196 / 0 Gb/s` | `105 / 105 Gb/s` |
| 两条流合计完成的有效载荷 | `225 GB`，即 `180 Gb/s` | `220 GB`，即 `176 Gb/s` |
| `A-L0 → S0` 的 RoCE 队列 | 采样峰值 2.0 MB，反复积压 | 采样峰值 40 kB，接近空闲期 |
| A0、A1 收到的 CNP 合计／`A-L0` 向这两台主机发送的 PFC 合计 | `6800 / 300` | `0 / 0` |
| B0 网卡物理端口的 `rx_crc_errors_phy` 与 `rx_pcs_symbol_err_phy` 增量 | `0 / 0` | `42000 / 310000`，连续几个子窗口增长 |
| 补充观测 | 两条流都出现吞吐回落，路径物理错误计数稳定 | 仅 B0 对应流出现重试，B1 对应流稳定，`B-L0 swp1` 出口队列接近空闲期 |

**慢例 A 的共享出口。** `A-L0 → S0` 发出约 196 Gb/s，接近单向 200 Gb/s 上界，`S1` 方向空闲。排队反复发生，端点收到 CNP，接入链路还报告了 PFC。合起来支持两条流共享一个拥塞出口。做对照时保持端点、消息大小和并发一致，使两条流实际走不同上联，复查端口利用率、队列、反馈与载荷吞吐。若热点随路径分开而消失，对散列偏斜的解释更有支持。PFC 发送计数只能确认交换机发出了暂停请求。对端是否收到和怎样响应，要看对端计数和发送行为，再沿下游找最先积压的队列。 [NVIDIA Cumulus Linux 5.11，ECMP 与按流散列](https://docs.nvidia.com/networking-ethernet-software/cumulus-linux-511/Layer-3/Routing/Equal-Cost-Multipath-Load-Sharing/) · [NVIDIA Cumulus Linux 5.11，RoCE 状态与计数](https://docs.nvidia.com/networking-ethernet-software/cumulus-linux-511/Layer-1-and-Switch-Ports/Quality-of-Service/RDMA-over-Converged-Ethernet-RoCE/)

**慢例 B 的接收链路。** 两条上联各有余量，观测窗口里没有出现 A 例的队列和反馈特征。B0 的接收物理端口持续录到 CRC 错误帧和 PCS 符号错误。这个 PCS 计数记录前向纠错未能修正的符号错误，也会在未启用纠错时计入符号错误。发生重试的也是去 B0 的流，因此优先调查 `B-L0 swp1 → B0 NIC` 这一方向。CRC（循环冗余校验）错误按帧计，PCS（Physical Coding Sublayer，物理编码子层）错误按符号计，不能相加或直接折算为载荷差。对准交换机的发送端和网卡的接收端，继续查两端链路状态、前向纠错（Forward Error Correction，FEC）模式和错误的时间分布。 [Linux v6.12，mlx5 Physical Port Counters](https://docs.kernel.org/6.12/networking/device_drivers/ethernet/mellanox/mlx5/counters.html)

对于支持数字诊断监测（Digital Optical Monitoring，DOM）的光模块，可用 Cumulus 的 `nv show platform transceiver swp1` 或适用接口上的 `ethtool -m <接口>` 检查收发光功率、温度与告警，结合模块规格和方向看。若要区分两端模块、光纤与端口，可在受控环境一次只更换一个可疑部件，再复测同一方向、负载和窗口。慢例 B 的错误支持把调查缩小到该段链路及两端，具体部件还需要这种对照。 [NVIDIA Cumulus Linux 5.11，Troubleshoot Layer 1](https://docs.nvidia.com/networking-ethernet-software/cumulus-linux-511/Monitoring-and-Troubleshooting/Troubleshooting-Network-Interfaces/Troubleshoot-Layer-1/)

## 计数的方向、单位与边界

以 Cumulus Linux 5.11 的接口计数为例，`rx-pfc-stats` 与 `tx-pfc-stats` 分别记录接收和发出的暂停，各自可看 `pause-packets` 和 `pause-duration`。`tc-usage` 是读取时的流量类缓存占用，`tc-max-usage` 是峰值，使用前应确认覆盖的时间段。`unicast-no-buffer-discard` 的同窗增量可补充说明是否发生缓存不足导致的单播丢弃。mlx5 的 `rx_corrected_bits_phy` 是经 FEC 纠正的比特数。若设备同时提供同一物理端口的 `rx_bits_phy`，可用同窗差值估算纠正比率，跟踪该链路接收质量的变化，再从 CRC 或不可纠正错误看有无受损帧及其他物理异常。设备缺字段时应记为缺测。 [NVIDIA Cumulus Linux 5.11，RoCE 端口计数](https://docs.nvidia.com/networking-ethernet-software/cumulus-linux-511/Layer-1-and-Switch-Ports/Quality-of-Service/RDMA-over-Converged-Ethernet-RoCE/) · [Linux v6.12，mlx5 Ethtool Counters](https://docs.kernel.org/6.12/networking/device_drivers/ethernet/mellanox/mlx5/counters.html)

原生 InfiniBand 也会出现等待。数据使用的虚拟通道（Virtual Lane，VL）可基于接收侧给出的链路信用流控，表示对端还有多少接收余量。`port_xmit_wait` 的增量表示该端口有数据排着却整段计数时隙未发，可能在等信用或仲裁。判断物理问题可同时看 `symbol_error`、`link_error_recovery`，`port_xmit_discards` 增长时需结合设备定义追查丢弃原因。无论哪种网络，累计计数先核对计数范围、方向和单位，再考虑采样期间是否发生复位或回绕。队列积压和物理错误可能并存，粗粒度采样也可能错过突发。 [Linux v6.6，InfiniBand sysfs ABI](https://docs.kernel.org/6.6/admin-guide/abi-stable.html) · [NVIDIA UFM Enterprise，InfiniBand Port Counters](https://docs.nvidia.com/networking/display/nvidia-ufm-enterprise-user-manual-v6-19-4-lts-2024-lts-u3.4%20LTS%20%282024%20LTS%20U3%29.pdf)
