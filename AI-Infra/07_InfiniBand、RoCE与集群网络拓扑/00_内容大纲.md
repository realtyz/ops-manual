# 第 07 章 InfiniBand、RoCE 与集群网络拓扑｜写作大纲

**审查状态**　已批准。正文按下列七节拆篇。RoCE 采用 Cumulus Linux 5.11 的有无 PFC 对照，排障采用自拟教学记录和官方字段释义。

## 范围、必要前置与学习结果

- **范围**　从两台裸机 Linux 服务器的 RC RDMA 连接出发，对照原生 InfiniBand（IB）与运行在三层以太网中的 RoCEv2。先解释报文如何到达对端，再把连接放进交换网络，分析拥塞、路径容量和故障域。RoCEv1 只用于辨认封装和路由边界。第 04、06 章承接节点内拓扑、Verbs 与 GPUDirect RDMA，第 08 章接手 NCCL 选路、集合算法和基准读法，第 13 章接手 Pod 的设备与网络接入，第 17—19 章接手长期基线、处置与验收。
- **必要前置**　能读懂 IP 地址、子网、下一跳和 Linux 接口，知道 GPU 与 NIC 通过节点内互联搬运数据，以及 QP 需要选择本地 RDMA 端口并获取对端路径。首次出现时补充 MAC、VLAN 优先级、全双工、交换机入口与出口队列的最小知识。读者可以用所给材料推导，无需 GPU 实验环境。
- **学完应能画路径**　给定端口状态、IB 分区或 RoCE GID 表及路由信息，画出一条跨机 RDMA 路径，指出交换设备依据什么转发，以及物理链路、管理面、IP 连通和指定 QP 通信各需要什么证据。
- **学完应能算容量和定位故障域**　给定 GPU、NIC、交换机端口与布线表，判断流量在同一 leaf、跨 leaf 或跨 NVLink 域时经过哪里，计算指定割面的单向容量与故障后余量，并说明单流或偏斜流量可能先受哪条链路限制。
- **学完应能区分慢的原因**　给定同一时段的有效吞吐、每跳端口、队列、ECN/PFC 和物理错误数据，区分容量不足、散列热点、拥塞反馈、物理链路异常与证据不足，指出下一项能区分候选原因的观测。

**贯穿案例**　前两节用同一对端点分别走 IB 和 RoCEv2。第 03—05、07 节使用一套自拟的 RoCEv2 拓扑。机架 A、B 各有四台节点，每台选两组 GPU—NIC 近邻关系，两个独立的单端口 NIC 分别接本机架的 Rail 0、Rail 1 leaf。四台 leaf 各以一条 200 Gb/s 链路接两台共享 spine，节点接入同为每口 200 Gb/s 全双工。物理拓扑、队列和吞吐记录均注明教学假设。第 06 节另用 NVIDIA DGX GB200 NVL72 官方参考架构说明实际机架级 NVLink 域。

## 01 同一条 RC 连接，IB 和 RoCEv2 怎样把包送到对端

**问题与预期结论**　应用通过相似的 Verbs API 发数据，为什么换一类网络后，检查路径的命令和地址就变了？读完能从链路类型、封装和地址字段辨认三种路径，判断在原生 IB 子网、RoCEv1 二层域或 RoCEv2 三层网络中，报文分别能走到哪里。

**解释顺序**

1. 从第 06 章的 RC QP 出发，把载荷、RDMA 传输、网络寻址和物理链路拆开。画相同端点的线缆、端口模式和交换节点。IB 主例限定单子网，交换机用目标 LID 转发。GID 是全局标识，涉及全局路由时与 GRH 有关。跨 IB 子网需相应的 IB 路由能力，本章只画边界。
2. 对照 RoCEv1 的二层 EtherType `0x8915` 与 RoCEv2 的 `Ethernet → IPv4/IPv6 → UDP（目的端口 4791）→ RDMA 传输`。RoCEv2 的跨子网转发看 IP 下一跳，每一跳仍需对应的二层交付。以 RC 为例交代可靠性由 RDMA 传输层提供。RoCEv2 的以太网、IP 路由和邻居解析承担网络可达职责，随后再检查选定的 RDMA 端口与 QP。
3. 用一个双网口主机说明 RoCEv2 源地址如何落到本地 RDMA 端口的 GID 表。依次核对路由选出的源 IP 和出口、GID 值、类型和关联 netdev。IPv4 的 GID 用 IPv4 映射的 IPv6 表示。同值条目可以对应不同 RoCE 版本，索引是端口本地信息。修改 VLAN 接口、IP 或路由后重查映射和路径 MTU。应用选设备及自动选路的实现留给第 08 章。

**支撑材料**

- 拟用三行封装与转发字段对照表，以及一个跨 IP 子网的路径图。以 MLNX_OFED v24.10-0.7.0.0 手册的 RoCEv1/v2 报文说明核对 EtherType、UDP 端口和 UDP 源端口提供的流散列输入。用 IB 架构资料核对 LID、GID、GRH 的作用范围。 [NVIDIA · MLNX_OFED v24.10-0.7.0.0，RoCE 章](https://networking-docs.nvidia.com/mlnxofedswum/24100700/rdma-over-converged-ethernet-roce) · [IETF RFC 4392，§2](https://www.rfc-editor.org/rfc/rfc4392)
- 拟用 `rdma link show`、`ip route get <对端 IP> from <源 IP>`，以及同一 `<设备>/ports/<端口>` 下的 `gids/<索引>`、`gid_attrs/types/<索引>`、`gid_attrs/ndevs/<索引>`。教学输入中给出同一个 GID 值的 v1/v2 两行，再加入管理口路由，要求读者给出匹配的端口、GID 类型和出口。IP 路由记录支持出口判断，指定端口的 RDMA 测试结果才支持该连接可用。 [Linux v6.6 · InfiniBand sysfs ABI](https://docs.kernel.org/6.6/admin-guide/abi-stable.html) · [iproute2 v6.12.0 · rdma-link](https://github.com/iproute2/iproute2/blob/v6.12.0/man/man8/rdma-link.8)

## 02 IB 物理链路起来后，子网怎样进入可通信状态

**问题与预期结论**　IB 端口报告物理 `LinkUp`，为什么仍可能无法发起跨机通信？读完能区分链路训练、子网初始化、分区成员资格和上层测试四种证据，并说明 IPoIB 的 `ping` 能验证哪条路径。

**解释顺序**

1. 按物理链路建立、SM 扫描拓扑、给端口分配 LID、计算并下发交换机转发表、配置分区和激活端口的顺序讲解。用 OpenSM 举例，说明 SM 可部署在宿主机或受支持的交换机，转发由交换机执行。SA 提供路径等查询信息。以 `Physical state: LinkUp` 但逻辑 `State: Initializing` 为例，下一步检查当前主 SM 和其可见拓扑。若逻辑状态已 `Active`，继续查指定路径及分区。
2. 用显式 `P_Key` 讲端口成员资格和路径约束。低 15 位标识分区，高位体现完整或受限成员资格。同一分区内两个受限成员不能互通，完整成员与受限成员可满足这项检查。把 P_Key 表索引与键值分开。仅改变对端成员资格就重判一次，避免依赖 OpenSM 缺省分区行为。
3. 把原生 Verbs 载荷路径与 `IP → ib_ipoib → IB` 路径画在同一个 fabric 上。IPoIB 是 IP 接口，可承载 `ping`、Socket 或部分工具的控制通信。对指定原生 RC QP、缓冲区和路径的结论要用对应测试取得。IPoIB 模式、跨子网 IB 路由与 SM 高可用配置只点到边界。

**支撑材料**

- 拟截取 `ibstat` 的 `State`、`Physical state`、`Base lid`、`SM lid`、`Link layer` 字段，配 `sminfo` 的主 SM 状态和一条 `ibtracert` 路径作为不同层的证据。教学记录分为物理已起但 SM 未完成配置、逻辑已起但指定分区的端点组合不满足条件两个案例。状态值按工具版本核对。 [rdma-core v57.0 · ibstat 源码](https://github.com/linux-rdma/rdma-core/blob/v57.0/infiniband-diags/ibstat.c) · [NVIDIA · InfiniBand Cluster Bring-up Procedure](https://docs.nvidia.com/infiniband-cluster-bring-up-procedure.pdf)
- 拟给 OpenSM 的 `Train=0x0021 : <A 的端口 GUID>=full, <B 的端口 GUID>=limited ;` 教学配置，分别对应端口表中的 `0x8021` 与 `0x0021`，再把 A 改为 `limited` 推演结果。IPoIB 对照使用另一个显式启用 `ipoib` 的分区，核对接口 `pkey`，说明一条 IPoIB 测试记录对应哪组成员。 [OpenSM · 分区配置格式](https://raw.githubusercontent.com/linux-rdma/opensm/master/doc/partition-config.txt) · [IETF RFC 4392，§2.2](https://www.rfc-editor.org/rfc/rfc4392) · [Linux · IP over InfiniBand](https://docs.kernel.org/6.2/infiniband/ipoib.html)

## 03 RoCEv2 遇到拥塞时，谁暂停、谁标记、谁降速

**问题与预期结论**　多台主机向同一端口发数据时，为什么链路没有明显物理错误，通信仍会变慢，其他流量甚至也会受影响？读完能把流量分类、排队、ECN/CNP、PFC 和丢包放在同一因果链上，按部署条件解释有 PFC 与无 PFC 两种模式。

**解释顺序**

1. 从主机设置 DSCP 或带 VLAN 标签时的 PCP 开始，沿每跳检查信任字段、内部优先级、流量类和队列映射。画两个 200 Gb/s 输入同时向一个 200 Gb/s 出口发送的时序，解释突发引起的排队与缓存耗尽后的丢弃。把优先级、带宽调度和拥塞阈值分别放在配置表上。
2. 先画端到端反馈。对可标记的包，交换机在拥塞条件下写 IP ECN 的 CE，接收 RNIC 回送 CNP，支持并启用相应拥塞控制的发送 RNIC 调整发送速率。DCQCN 只作这一反馈环的实现例。再画逐跳反馈。当接收侧相应优先级的缓存达到暂停条件，向直接上游发 PFC，预留 headroom 吸收上游停发前仍在途的数据。同一优先级的其他流可能一起被暂停，背压也可能传向更上游。
3. 对照启用 PFC+ECN 与启用 ECN、不启用 PFC。分别追踪优先级错配、突发超过 headroom、端点未响应 CNP 的后果。无 PFC 情形要看端点的丢包恢复能力和实际工作负载，RC 能重试仍可能因丢包付出吞吐与尾延迟代价。阈值、缓存分配、线长、链路速率与设备能力作为联动条件。正文保留机制及核验方法，厂商整网调参留给实际部署和验收章节。

**支撑材料**

- 拟用 Cumulus Linux 5.11 官方示例并排读 `nv set qos roce mode lossless`、`nv set qos roce mode lossy`，配 `nv show qos roce` 和 `nv show interface <接口> qos roce status` 中的信任模式、优先级到流量类映射、ECN 阈值与 PFC 位图。默认 RoCE/CNP 的优先级 3/6 仅用于解释该版本的预设。已核对该版提供上述两种模式，`lossless-single-ipool` 从 5.12 才引入，ASIC 之间需分别核对配置。 [NVIDIA · Cumulus Linux 5.11 RoCE](https://docs.nvidia.com/networking-ethernet-software/cumulus-linux-511/Layer-1-and-Switch-Ports/Quality-of-Service/RDMA-over-Converged-Ethernet-RoCE/) · [NVIDIA · NVUE 5.x QoS 版本记录](https://docs.nvidia.com/networking-ethernet-software/nvue-reference/Set-and-Unset-Commands/QoS/)
- 拟用一张 Mermaid 时序图区分 CE 随数据向前、CNP 从接收端返回、PFC 只发送给相邻上游。以忽略报文开销和反馈的 40 µs 双源突发算队列净增长，`(2 × 200 − 200) Gb/s × 40 µs ÷ 8 = 1 MB`（十进制），仅说明为何短突发也能积压。对照交换机 `rx-pfc-stats`、`tx-pfc-stats` 中的 `pause-packets` 和 `pause-duration`，以及 `tc-max-usage`、`unicast-no-buffer-discard`。CE/CNP 以同一时间窗的两端计数或公开记录补证，不用暂停次数代替拥塞源定位。 [IETF RFC 3168，§5](https://www.rfc-editor.org/rfc/rfc3168) · [Zhu 等 · DCQCN 原始论文](https://conferences.sigcomm.org/sigcomm/2015/pdf/papers/p523.pdf) · [NVIDIA · Cumulus Linux 5.11 RoCE 观测字段](https://docs.nvidia.com/networking-ethernet-software/cumulus-linux-511/Layer-1-and-Switch-Ports/Quality-of-Service/RDMA-over-Converged-Ethernet-RoCE/)

## 04 Spine-Leaf 的容量怎样算，ECMP 怎样影响实际路径

**问题与预期结论**　每口都是 200 Gb/s，为什么跨 leaf 的总吞吐仍可能先见顶？读完能识别两层折叠 Clos 的路径，计算收敛比、指定割面容量和故障后的余量，并区分物理容量与流量散列造成的热点。

**解释顺序**

1. 从 leaf 接节点、每个 leaf 接每个 spine 开始，依次走同 leaf 和跨 leaf 路径。引入折叠 Clos 的层次关系，规模扩大时可以增加交换层。按单向速率分别数节点接入与上行，画指定割面。用对称教学拓扑解释二分带宽的常见读法，并把“等分端点所取的最小割面容量”与“某一给定机架割面的容量”分开。双向值只有明确为两个方向之和时才相加。
2. 用三层 RoCEv2 的 ECMP 走一次路由选择。多个等价下一跳提供可选路径，传统按流散列把同一流放在一个下一跳。UDP 源端口可给散列增加区分度，实际仍取决于交换机散列字段和流量分布。两条重流落到同一条 200 Gb/s 上联时可出现排队，另一条上联仍可能空闲。IB 的 LID 转发表及适用设备上的自适应路由用作对照，具体算法和平台配置留给厂商手册。
3. 拿掉一条上联和拿掉一台共享 spine 各算一次，区分故障收敛后的结构容量和收敛过程中的流量影响。再换成主要发生在同 leaf 的流量，解释为何同一收敛比的可见影响会改变。通信库对 Rail 的利用及集合通信映射留给第 08 章。

**支撑材料**

- 拟给精确拓扑图与容量表。每 leaf 下联 `4 × 200 = 800 Gb/s`，上联 `2 × 200 = 400 Gb/s`，下联与上联之比 `2:1`。假设 spine 内部不构成瓶颈、对端容量充足且流量可以均匀分布，A→B 的指定割面上限是 `800 Gb/s`，同时按双向合计为 `1.6 Tb/s`。A 侧一条上联失效后，A→B 的上限降至 `600 Gb/s`。一台共享 spine 失效后降至 `400 Gb/s`。每个值在表中注明割面、方向、可用链路和假设。 [NVIDIA · HGX AI Factory，Spine-Leaf Networking](https://docs.nvidia.com/enterprise-reference-architectures/hgx-ai-factory-h100-h200-b200/latest/network-logical-architecture.html)
- 拟给同一对等价下一跳的两张端口负载表，两条重流分别散列到不同上联或碰到同一上联。用路由下一跳列表支持“有两条可选路径”，用两条上联在同一时间窗内的发送速率和队列占用判断流量是否均衡。 [NVIDIA · Cumulus Linux 5.11 ECMP](https://docs.nvidia.com/networking-ethernet-software/cumulus-linux-511/Layer-3/Routing/Equal-Cost-Multipath-Load-Sharing/) · [NVIDIA · InfiniBand Cluster Bring-up Procedure，LFT 与自适应路由](https://docs.nvidia.com/infiniband-cluster-bring-up-procedure.pdf)

## 05 从 GPU 编号追到交换机端口，再判断 Rail 的故障域

**问题与预期结论**　节点装了两张网卡，为什么链路可能只用到一部分，甚至两条 Rail 同时受一处故障影响？读完能从节点设备追到交换机端口，核对物理与逻辑映射，判断端口、leaf、spine、机架供电各能影响哪些路径。

**解释顺序**

1. 先由 GPU UUID 和 PCI BDF 找到 GPU，再读 GPU—NIC 拓扑距离，将 NIC 的 PCI BDF、RDMA 设备与端口号、netdev 或 IB 端口 GUID 对齐。随后用交换机邻居或 IB 拓扑工具对线缆标签和端口。GPU—NIC 亲和只说明本机路径特征，实际选择要靠第 08 章的应用证据。
2. 在教学图上对照三种关系。同机架同 Rail 的节点共享对应 leaf，跨机架同 Rail 经过两端 leaf 和共享 spine；教学网络在路由允许时也能经共享 spine 到另一 Rail 的 leaf。说明 Rail 是端点及网络接入的组织方式。再对照物理独立双平面，看交换机、电源、模块和布线路径有无共享，区分端口冗余、容量冗余及作业能否继续。
3. 依次拿掉一根 A0 节点线缆、A 侧 Rail 0 leaf 和一台共享 spine，要求读者按布线表列受影响的 NIC 与路径。A 侧 Rail 0 leaf 失效会切断 A 机架该 Rail 的接入，一台共享 spine 失效会同时降低两条 Rail 的跨 leaf 容量。另一 Rail 能否接管需看端点和应用配置。光模块选型清单及运维变更流程留给第 19 章。

**支撑材料**

- 拟给一张可反查的端口表，列 `机架/节点/槽位 → GPU UUID 与 BDF → NIC BDF → RDMA 设备/端口 → netdev 或端口 GUID → 线缆编号 → leaf/物理端口 → Rail`。以 `nvidia-smi topo -m` 读节点内距离，结合设备 sysfs、`rdma link show` 和交换机侧邻居记录。以太网用启用 LLDP 时的邻居表，IB 用 fabric 拓扑和端口 GUID。拟给一处线缆误接，让读者根据实际端口与台账差异找出偏离。 [NVIDIA · nvidia-smi 手册，Topology](https://docs.nvidia.com/deploy/nvidia-smi/index.html) · [iproute2 v6.12.0 · rdma-link](https://github.com/iproute2/iproute2/blob/v6.12.0/man/man8/rdma-link.8) · [NVIDIA · InfiniBand Cluster Bring-up Procedure](https://docs.nvidia.com/infiniband-cluster-bring-up-procedure.pdf)
- 拟用一张节点、机架和共享 spine 的布线图，标出两个端口的真实终点和三种故障的影响范围。用 DGX H100 SuperPOD 的 rail-aligned IB fabric 说明真实方案里同 Rail 可共享 leaf，跨 Rail 流量可经过 spine。架构图用于支持布线关系，容量仍用本章算例口径。 [NVIDIA · DGX H100 SuperPOD，Compute InfiniBand Fabric](https://docs.nvidia.com/dgx-superpod/reference-architecture-scalable-infrastructure-h100/latest/network-fabrics.html)

## 06 NVLink 域跨了计算托盘，Scale-up 的边界在哪里

**问题与预期结论**　如果两块 GPU 处在不同计算托盘，是否就需要经 NIC 通信？读完能按实际互联域画出机架内和跨域两条候选路径，区分计算节点、机架和 NVLink 域的边界。

**解释顺序**

1. 承接单机 NVLink/NVSwitch，先按 GPU 高速互联域定义本节的 Scale-up，再按由 NIC 和外部交换网络扩展的计算 fabric 说明 Scale-out。节点是主机边界，域是互联边界。用同域不同托盘的 GPU 对与跨域 GPU 对做对照。
2. 以 DGX GB200 NVL72 为实物例子，标出 `18 × 4 = 72` 张 GPU、NVLink 交换托盘和计算托盘的 ConnectX-7 计算网络端口。同一 NVLink 域内具备 NVLink 互联路径。跨两个该架构的 NVLink 域时，经本端计算 NIC、外部 IB fabric 和对端计算 NIC。路径成立仍取决于域配置、端口状态及软件是否选择它，应用日志的解释留给第 08 章。
3. 更换平台或 NVLink 域划分时，从实际的域成员和网络布线重新判断。带内管理、存储和带外管理仅在图上给出位置。型号比较、跨域作业放置和域管理流程留给第 15、19 章。

**支撑材料**

- 拟画双机架对照图。每个机架标明 `18 个计算托盘，共 72 张 GPU`，取两处托盘示意，画域内 GPU 经 NVLink Switch 的路径及跨域 GPU 经 ConnectX-7 和外部 IB 的路径。图按该参考设计核对端点、方向和边界。此处避免把规格表的 NVLink 双向值和单 NIC 单向值混为同一口径。 [NVIDIA · DGX GB Rack Scale Systems，Hardware](https://docs.nvidia.com/dgx/dgxgb200-user-guide/hardware.html) · [NVIDIA · DGX GB200 SuperPOD，NVLink Fabric 与 Compute Fabric](https://docs.nvidia.com/dgx-superpod/reference-architecture-scalable-infrastructure-gb200/latest/network-fabrics.html)

## 07 链路显示 200G，为什么有效吞吐达不到 200G

**问题与预期结论**　两组主机都报告链路正常，哪组数据支持队列或路径瓶颈，哪组指向物理层？读完能从协商速率、端口流量和应用载荷建立可比口径，再用同窗计数差分排查，并说明何时还需要对端或对照证据。

**解释顺序**

1. 确认比较对象和方向。协商速率是链路容量口径，端口字节反映该计数口径下的实际流量，应用有效吞吐以完成传输的载荷除以计时。固定发送方向、消息大小、并发、端点、路径及时间窗，用第 04 节的最窄链路或割面建立上界，再核对流量是否走了预期路径。协议开销、等待、重试和其他流量需按各自证据解释差值。
2. 先看链路速率、宽度和是否反复起落，再按出口利用率、队列峰值、CE/CNP、PFC 收发与丢弃顺序检查拥塞。若速率不变但 CRC、FEC 无法纠正的错误或 IB 链路错误有持续增量，核对对应的物理端口与链路另一端。FEC 已纠正的计数用于观察信号质量趋势，需结合错误率、规格和是否有不可纠正错误解释。光模块可读时核对两端收发光功率、温度及告警，结合 FEC 模式、模块/线缆和端口做进一步区分。
3. 对照同一拓扑的两组慢例。一组上联偏斜，热点出口队列与标记上升，物理错误稳定。另一组队列证据平稳、受影响链路两端的方向能对上，接收侧 CRC 或不可纠正错误连续增长。让读者说明各自的下一项检查，并保留两类问题同时发生的可能。完整的压测矩阵和事件处置留给第 17、18 章。

**支撑材料**

- 拟给十进制单位算例。在单向、10 秒且应用与端口样本对应同一路径的假设下，200 Gb/s 折算为 `25 GB/s`；应用完成 `175 GB` 为 `140 Gb/s`，指定出口端口 TX 字节差值 `200 GB` 为 `160 Gb/s`。两者分别是标称单向速率的 70% 与 80%。须写明端口计数口径，差值不能直接换成丢包量。
- 拟用相同采样窗的端口证据表。以太网侧取 Cumulus 的流量类缓存占用、发送丢弃和 PFC，以及 mlx5 的 `rx_crc_errors_phy`、`rx_corrected_bits_phy`、`rx_pcs_symbol_err_phy`。按端口与方向对齐收发两端，使用 `ethtool -m` 或交换机 transceiver 输出的 DOM 字段解释光链路证据。IB 侧对照 `symbol_error`、`link_error_recovery` 与 `port_xmit_discards`。补一条 `port_xmit_wait` 的例子，说明有数据待发时，链路信用不足和未获仲裁都可能造成发送等待。先核对计数单位、采样范围、回绕或重置与字段可用性。 [Linux v6.12 · mlx5 Ethtool counters](https://docs.kernel.org/6.12/networking/device_drivers/ethernet/mellanox/mlx5/counters.html) · [NVIDIA · Cumulus Linux 5.11 Troubleshoot Layer 1](https://docs.nvidia.com/networking-ethernet-software/cumulus-linux-511/Monitoring-and-Troubleshooting/Troubleshooting-Network-Interfaces/Troubleshoot-Layer-1/) · [Linux v6.6 · InfiniBand 计数 ABI](https://docs.kernel.org/6.6/admin-guide/abi-stable.html) · [NVIDIA · InfiniBand 指标释义](https://docs.nvidia.com/base-command-manager/product-manuals/11/admin/metricshealthchecksactions)

## 已核对的版本边界与待确认项

- **已核对**　MLNX_OFED v24.10-0.7.0.0 手册用于 RoCE 封装和 GID 表。Cumulus Linux 5.11 用于交换机示例，`lossy` 与 `lossless` 都有 ECN，PFC 是两者的主要差异，配置需按 ASIC 核对。Linux v6.6/v6.12 和 rdma-core v57.0 用于字段释义。以上分别是资料出处，具体主机与交换机的互操作组合要另行核对。DGX GB200 NVL72 的域和 NIC 关系限定于该参考架构。各出处随对应小节列明。
- **待确认**　如正文采用实采材料，需取得同一次测试的主机与交换机记录并锁定 NIC 型号与固件、内核和驱动、交换机 ASIC 与 NOS 小版本、端口及模块、测试参数和采样窗口。当前教学材料没有实测来源。CE 与 CNP 的端侧计数器名称、光模块 DOM 字段和告警阈值须随选定环境核对。若仍用自拟记录，用已核实的字段与中性列名展示观测，不给未经核实的真实设备输出。
