## 范围、前置与学习结果

- **范围**　以 Linux 上的双路 x86 服务器和 NVIDIA 独立 GPU 为主，依次建立设备分工、节点物理拓扑、平台形态、运行条件和集群流量五张认知图。用简化双路节点做推演，用 DGX H100 官方配置、拓扑和 BasePOD 参考部署做对照。示意编号与厂商型号材料分别标注。
- **前置**　认识 Linux 进程、主机内存、块设备、网口与 IP/路由的基本概念。正文在首次使用处补足 PCIe 端点、设备地址、NUMA、VLAN 和 BMC 的最小定义。推演使用给定材料，读者无需 GPU 实验环境或 CUDA 编程经验。

- **跨章深度**　02 展开 GPU 执行和显存性能，03 展开驱动与软件可用性，04 展开多卡实际传输、带宽与拓扑工具。05—09 分别承接作业协调、RDMA、网络拓扑、NCCL、存储，13 承接 Pod 多网络，17—19 承接观测、故障和交付。

**叙述顺序**　先用一次读数据并交给 GPU 的动作给设备赋予角色，再把这些角色放回主板连线。读懂连接后，用配置表区分卡、底板和整机，再判断这台整机能否在机架上运行和被管理。最后把节点端口接到集群，按流量职责与故障域读网络。

## 01 一份配置表里的设备各做什么

**问题与预期结论**　读者看到「双路 CPU、2 TB 系统内存、8 张 GPU、NVMe、两类网口」，需要判断作业读入的数据由谁读取、在哪里暂存、最终在哪里计算。读完能区分存储、主机内存和每卡显存，能解释 CPU、GPU、NIC、NVMe 和 PCIe Switch 在这条路径上的位置。

**解释顺序**

1. 从一次常规缓冲式读取开始。数据从本地 NVMe 进入主机内存，CPU 上的应用发起 I/O、准备数据并提交 GPU 工作，准备好的输入传入目标 GPU 的显存供 GPU 计算。解释 PCIe Switch 转发设备间或设备与主机间的 PCIe 事务，按平台连线决定它是否在这条路径上。CPU 发起操作和 CPU 逐字节搬运分别说明。
2. 把输入源换成远端存储，标出 NIC 到主机缓冲区的入口。本节以常规主机缓冲路径为前提，页缓存、预取、Direct I/O 和 GPUDirect Storage 交给 09，NIC 直接访问 GPU 内存交给 06。
3. 回到配置表，将每卡容量与整机合计分栏。普通设备内存分配按目标设备考虑。若某次分配需要单卡上有超过 80 GB 的可用设备显存，合计 640 GB 无法证明它能成功；若应用能分片，还要检查每卡容量、预留与额外开销。GPU 内部访存与执行交给 02，多卡之间如何互访交给 04。

**支撑材料**

- 摘录官方组件表中的 `System memory (DIMM)`、`GPU`、`Storage (OS)`、`Storage (Data Cache)`、两类网络卡，按「部件、容量或端口的统计单位、用途」重排。用 DGX H100 的 `8 × 80 GB = 640 GB` 说明整机合计与每卡限制；规格容量与运行时可用量分开标注。 [DGX H100/H200 User Guide · Component Description](https://docs.nvidia.com/dgx/dgxh100-user-guide/introduction-to-dgxh100.html#dgx-h100-h200-component-descriptions) · [HGX H100 组件规格](https://docs.nvidia.com/enterprise-reference-architectures/hgx-ai-factory-h100-h200-b200/latest/components.html)

## 02 从设备清单画出 PCIe 和 NUMA 拓扑

**问题与预期结论**　同样数量的 GPU 和 NIC，可能在不同根端口下，也可能争用同一上行链路。读者拿到配置表和 Linux 枚举信息后，应能画出设备归属、找出可能跨 Socket 或共享链路的路径，并知道怎样验证实际的内存落点。

**解释顺序**

1. 先画两个 Socket、各自的主机内存和处理器互联，再从 CPU 一侧画 PCIe Root Complex 与 Root Port，经可选 Switch 接 GPU、NIC 和 NVMe。区分上行端口与下行端口。用设备的 PCI 地址 `域:总线:设备.功能` 沿桥逐层回溯。同一个 PCI 域编号下可以有多个根总线，不能把域编号当作 Socket 编号。
2. 在同图叠加操作系统看到的 NUMA 节点。教学节点先假设每 Socket 一个 NUMA 节点，再用 Intel SNC 的例子说明固件配置可在一个 Socket 暴露多个 NUMA 域。分别标出线程在哪个 CPU 上运行、缓冲区的页在哪个 NUMA 节点、设备由哪个根端口接入。
3. 固定 GPU 接在 Socket 0，假设 GPU 的 DMA 直接从这块页锁定的主机缓冲区读取，比较缓冲区驻留在节点 0 和节点 1 时的路径。后者要经过处理器互联。再将提交线程移回节点 0，保持缓冲区的页在节点 1，传输仍会跨 Socket。用默认策略下新分配匿名页的落点引出首次触页、显式内存策略、可用节点和迁页等条件，传输实现与调优留给第 04、15 章。
4. 固定两个 PCIe 端点各有自己的下行链路，比较各自访问主机与两者同方向并发经过同一 Switch 上行的情况。举例每个端点各需 12 GB/s、公共上行同方向有效容量假设为 16 GB/s，则总需求 24 GB/s 超出 8 GB/s，具体分配要结合负载和测量。这是共享关系的教学算例。PCIe 速率换算、P2P 路由和实际传输验证留给 04，GPU 与 NIC 直达的支持条件留给 06。

**支撑材料**

- 官方 DGX 拓扑图 §1.3 用于核对 CPU、PCIe Switch、GPU、NIC 与 NVMe 的图例，并让读者看见 PCIe 和 NVSwitch 是两组连线。拟另画一个更小的双路示意，突出同一设备在本地和远端缓冲区下的路径，以及公共上行的两条分支。标明教学图的编号及省略项。 [DGX H100/H200 User Guide · §1.3 System Topology](https://docs.nvidia.com/dgx/dgxh100-user-guide/dgxh100-user-guide.pdf) · [Linux PCIe 拓扑和 P2P 路由](https://docs.kernel.org/driver-api/pci/p2pdma.html)

## 03 从 PCIe 插卡、SXM 模组读到 HGX 和整机

**问题与预期结论**　报价里同时出现「H100」「SXM」「HGX」「DGX」，读者需要判断哪些词描述单卡，哪些描述 GPU 子系统或服务器。读完应能在同名 GPU 的配置中找出有意义的差异，并知道实际机箱、网口和供电去哪里查。

**解释顺序**

1. 对照 PCIe 插卡进入主板或转接板插槽、SXM 模组安装到相应 GPU 底板。先讲机械与供电、散热边界，再分开读「卡或模组的外形」「连接主机的总线」「GPU 互联」。SXM 系统同样可以通过 PCIe 接到主机，特定 PCIe 卡型也可支持 NVLink。实际互联按 SKU 和平台拓扑判断。
2. 用 HGX H100 8-GPU 底板说明多块 SXM GPU 与高速互联如何组合成子系统，再把底板放回整机范围，补上 CPU、内存、NIC、NVMe、BMC、电源和散热。并排看 DGX H100 和采用 HGX H100 的 Dell PowerEdge XE9680，设备数量相同的配置可以有不同的机箱规格、盘位和端口选项。

## 04 看清带内、带外与整机运行条件

**问题与预期结论**　SSH 失联时仍可能访问 BMC。配置表写有冗余 PSU 时，失去一路 PDU 也仍可能影响作业。读完应能分别判断主机与 BMC 的可达性、厂商定义的节点降级条件，以及机架端供电与散热能否支撑目标运行状态。

**解释顺序**

1. 并排画管理员经主机 NIC 到 OS 的带内路径，以及经管理网络到 BMC 的带外路径。依次改变主机 OS、带外网络和 BMC 供电三个条件。主机关机时，BMC 在有待机供电且管理路径可达的情况下仍可能报告电源状态和保留的事件。再用远程 KVM 在主机上电后观察启动进度。SSH 超时仅表明该访问路径失败，BMC 可达也只证明带外路径可用。
2. 从单 GPU TDP 转到整机最大输入功率，再到 PSU 数量和 PDU 映射。用 DGX H100/H200 官方的 6 个 PSU、4+2 冗余、200–240 V AC 下最大输入 10.2 kW 作例子。分清单 PSU 故障与整组 PSU 丢电。按该机型文档，运行时若三只 PSU 因供电事件失电会降性能，至少三只 PSU 可用才能启动。假设 3+3 接到 A/B，单路丢失就要按剩三只 PSU 的条件判断。
3. 回到机架约束。先核对 U 位、深度、承重、进风与风向，再按正常和故障两种状态核对可用功率与冷却能力。教学算例设两台节点按每台 10.2 kW 最大输入预算、其他设备预留 1.0 kW，两路 PDU 各有 15 kW 可用预算。正常等分时为 `（2 × 10.2 + 1.0）÷ 2 = 10.7 kW/路`；若要求失一路仍承载原预算，`21.4 kW > 15 kW`。这个算例判断机架预算，实际掉电后的功耗和性能另按节点策略、接线与测量判断。节点交付、功率限制设置和故障处置交给 17—19。

**支撑材料**

- 用 DGX BMC 的 `Sensor`、`Logs and Reports` 和远程 KVM 说明带外能观察什么。计划用 `ComputerSystem.PowerState` 与 `LogEntry` 的 `EntryType`、`Created`、`MessageId`、`Severity` 做字段对照，区分当前状态与历史事件。按 `EntryType` 解读 `MessageId`，`Created` 是记录创建时间，跨日志比对需核对时钟。DMTF schema 支撑字段语义，机型手册支撑具体控制能力。 [DGX H100/H200 · Using the BMC](https://docs.nvidia.com/dgx/dgxh100-user-guide/bmc.html) · [DMTF ComputerSystem v1.20.0](https://redfish.dmtf.org/schemas/v1/ComputerSystem.v1_20_0.json) · [DMTF LogEntry v1.9.0](https://redfish.dmtf.org/schemas/v1/LogEntry.v1_9_0.json)

## 05 把一台服务器的端口接到集群

**问题与预期结论**　集群图上写着「管理、作业协调、GPU 通信、存储」，接口表却可能只有几组物理链路。读完应能按流量的发起方、目标和用途分类，再看这些路径是否共享 NIC、线缆或交换机。能解释成员发现成功为何只验证了其中一段路径。

**解释顺序**

1. 用两台节点从启动到运行的一次作业区分四类职责。管理侧分主机运维与 BMC；作业进程经协调端点完成成员发现；GPU 作业进程之间交换数据；节点从存储端读入输入并写回检查点。先画通信双方和阶段，再映射接口、地址、路由或设备端口。
2. 给出两种部署图。一图让两类 IP 流量经不同 VLAN 共享同一物理 trunk，说明 VLAN 的二层分段与物理容量、共同断点的区别；另一图用独立物理端口和交换路径承载高速通信，继续标出仍共享的上游组件。用 BasePOD 对照其中的实际组合，指出其网络命名按部署角色划分，作业协调端点由作业配置给出。
3. 分别变更「协调地址不可达」「高速链路断开」「存储繁忙」三个条件，提出区分现象所需的证据。协调端点连通只能证明对应 IP 路径，GPU 通信还需自己的接口与传输证据，存储需要服务端或客户端 I/O 证据。成员管理留给第 05 章，RDMA 与交换网络留给第 06—07 章，NCCL 启动与数据路径留给第 08 章，数据供给留给第 09 章，Pod 接口选择留给第 13 章。
