# 读懂一份节点交接材料

这一篇把全章放进一个连续场景。先读交接记录并分析已有证据，再补入必要条件，练习画出路径、识别平台和计算供电预算。各项材料沿用导读说明的教学模型。

## 场景与已经拿到的材料

节点采用本章的双路四卡 PCIe 教学模型：CPU0/CPU1 各有 32 个物理核心与 256 GiB 本地内存，四张 GPU 各有 48 GiB 显存。GPU0/GPU1/NIC0 在 PCIe 分支 A，GPU2/GPU3/NIC1 在分支 B。两个 CPU 通过处理器间互联连接。

下面是人工整理的交接清单，GPU 代号与前文拓扑一致。

| 对象 | 物理位置/PCI 地址 | NUMA 关联 | 外部连接或用途 |
| --- | --- | --- | --- |
| GPU0 | 槽位 A1，`0000:41:00.0` | Node 0 | 48 GiB 显存 |
| GPU1 | 槽位 A2，`0000:42:00.0` | Node 0 | 48 GiB 显存 |
| NIC0 | 槽位 A3，`0000:43:00.0` | Node 0 | 单端口，当前协商为 200 Gbit/s |
| GPU2 | 槽位 B1，`0000:c1:00.0` | Node 1 | 48 GiB 显存 |
| GPU3 | 槽位 B2，`0000:c2:00.0` | Node 1 | 48 GiB 显存 |
| NIC1 | 槽位 B3，`0000:c3:00.0` | Node 1 | 单端口，当前协商为 100 Gbit/s |
| 主机管理网卡 | 独立管理端口 | 本题未提供 | 主机管理和作业协调 |
| BMC | 机箱独立管理口 | 不按本题的主机 NUMA 分类 | 管理网络中的独立地址 |
| NVMe0/1 | 分别连接根侧分支 0/1 | 分别关联 Node 0/1 | 两组可重建的本地缓存 |

补充交接记录：

1. 两张高速 NIC 的预期端口速率均为 200 Gbit/s，目前都报告链路已建立。
2. NIC0 到 `compute-sw-01/port-11`，NIC1 到 `compute-sw-01/port-12`。
3. SSH 可以登录，主机上的工具列出了四张 GPU；没有附计算或通信测试结果。
4. 主机管理网卡上划分了管理 VLAN 与存储 VLAN；两者使用同一物理端口。
5. BMC 当前可访问。电源接线表只写“已接两根线”，没有 PDU 和上游回路编号。
6. 机架已有三台同配置节点，计划增加第四台；未提供设施余量。
7. 某次历史作业在 GPU2 上运行时，加载进程位于 CPU0 的核心集合，输入缓冲分配在 Node 0。

## 先独立完成这五个判断

1. 能否把四张卡理解成一个 192 GiB 的普通单卡显存空间？
2. 第 7 条记录中的数据如何到达 GPU2，哪些资源发生了跨域访问？
3. “链路已建立，四卡可见”是否已经支持两组 GPU 具有相同性能？
4. 两个 VLAN、两个高速端口、两根电源线分别提供了怎样的独立性？
5. 增加第四台服务器之前，哪些材料仍缺失？

## 参考分析：先把结论约束在证据范围内

### 显存加法与单卡容量

四张卡的装机显存总量可以相加得到 192 GiB。但每张卡的本地显存仍是 48 GiB。一个需要在单张卡上放下 60 GiB 数据的阶段，能否执行取决于程序的分片、内存管理与支持条件，现有材料不足以证明它能直接放下。

需要补充的是应用实际分配方式，而不是再重复统计空闲卡数。

### 数据位置与目标设备不在同一侧

历史记录中的输入缓冲位于 Node 0，目标 GPU2 位于 CPU1 所连接的分支 B。按本章简化模型，主机内存向 GPU2 搬运时涉及 CPU 间互联与目标侧 PCIe 路径。

这提供了一个值得调查的远端访问因素，尚不足以证明它就是历史作业变慢的根因。还需确认当时的数据量、复制阶段耗时、资源竞争和作业的其他等待。也不能由此直接决定把所有线程绑到 CPU1：作业可能还使用另一侧的 GPU，CPU 和内存容量也要共同考虑。

### 链路已建立与性能对称

NIC1 的实际速率低于预期，说明当前状态已经偏离配置目标。200 Gbit/s 与 100 Gbit/s 分别对应 25 GB/s 与 12.5 GB/s 的比特到字节换算值，实际有效吞吐还需扣除相关开销和考虑其余路径。

应继续核对网卡、交换机端口模式、模块/线缆支持和链路状态记录。材料没有给出这些信息，因此不能断言是哪一端损坏，也不能把 GPU2/GPU3 的任何性能异常都归结为此。

四卡可见证明了当前工具能够枚举这些设备，没有证明四卡都能完成计算、互联正常，或跨节点传输已达到预期。后续需要计算健康、设备路径和通信测试等不同层次的证据。

### 共享条件与故障范围

管理与存储虽然划分了 VLAN，但共享主机物理端口；端口故障仍可能同时影响两类流量，拥塞与带宽保障需要继续检查。两个高速端口接入同一交换机，因此还有交换机级的共同故障点。

电源记录只证明记录者接过两根线，没有证明它们分别来自独立路径，也没有说明冗余策略和单路剩余容量。BMC 可访问则只描述当前管理入口状态，不能补足这些信息。

这里不要求每一项资源都独立。需要的是让共享成为明确的设计事实，能够据此解释故障与容量边界。

### 扩容需要沿路径逐项补齐材料

| 需要补齐的材料 | 用它解决什么问题 |
| --- | --- |
| 精确整机/GPU 型号、PCIe 与底板图、插槽映射 | 教学模型与真实设备布局能否对应 |
| 设备身份、驱动状态、健康与基线记录 | 可见的设备是否具备预期工作能力 |
| NIC 的支持速率、端口配置、模块/线缆与错误计数 | NIC1 的实际速率为何偏离目标 |
| 交换机剩余端口、接入与上行容量、共享负载 | 第四台加入后路径能否承担并发需求 |
| 存储容量、并发吞吐与客户端路径 | 新增 GPU 是否有足够输入与保存能力 |
| PSU 分配、PDU、上游回路、冗余模式与负载余量 | 扩容及一路故障时是否满足供电条件 |
| 机架位置、承重、维护空间与冷却余量 | 物理安装和持续散热能否支持新增节点 |
| 主机/BMC 地址、整机序列号、接线与访问边界 | 故障发生后能否准确定位与远程观测 |

补齐材料的目的，是把设备、路径和运行条件对应起来。接下来选择其中三组信息，练习在条件明确后得出可以核对的结论。

## 条件补齐之后，把判断继续向前推进

### 把同一份输入分别放在两侧内存

现在只考虑一张 GPU 的主机到设备复制：目标固定为 GPU2，源数据已经完整放入主机缓冲区，传输期间缓冲区位置保持不变。对照前文拓扑，画出以下两种安排中的数据路径：

| 安排 | 加载进程的 CPU 集合 | 输入缓冲位置 | 目标 |
| --- | --- | --- | --- |
| A | Socket 0 上的核心 | Node 0 内存 | GPU2 |
| B | Socket 1 上的核心 | Node 1 内存 | GPU2 |

思考：哪一种安排需要经过 Socket 间互联？如果只把加载线程迁到 Socket 1，却保持输入缓冲仍在 Node 0，主机到 GPU 的跨 Socket 搬运是否已经消除？

**参考推导：**先由 GPU2 找到它所在的分支 B 与 Socket 1，再从输入缓冲的位置沿连接图追到目标：

```text
A：Node 0 内存 → Socket 0 侧主机互联 → Socket 间互联
  → Socket 1 侧 PCIe Root Complex → Switch B → GPU2 显存

B：Node 1 内存 → Socket 1 侧 PCIe Root Complex → Switch B → GPU2 显存
```

这里省略了各侧内存控制器等内部细节，路径中的 Socket 不表示数据必须由 CPU 核逐字节复制。在本模型中，A 的源内存和目标设备位于不同侧，数据需要跨 Socket；B 的这次复制可以保持在 Socket 1 一侧。仅迁移线程没有改变源缓冲的物理位置，因此仍要处理 Node 0 到 GPU2 的跨 Socket 数据传输。

![迁移前后源缓冲均位于 Node 0、目标均为 Node 1 的 GPU2，跨 Socket 数据路径保持不变；只有加载线程便签由 CPU0 移到 CPU1。](fig-01-06-01-thread-placement-vs-buffer.png)

图 01-06-01：这幅对照只迁移加载线程，源缓冲仍保持在 Node 0，目标仍是 GPU2，因此本次主机到设备复制的源数据仍需跨 Socket。CPU 符号代表相关主机互联范围，不表示 CPU 核逐字节中转。若另行迁移或重新分配源缓冲，需要作为改变内存位置的另一组条件重新分析。

由此可以确定两种安排的路径差别。实际耗时还需结合复制量、链路负载与执行重叠观察，路径分析本身不提供一个固定的性能提升百分比。

### 从产品名称还原硬件层次

接着收到三份补充资料：

- A：一张 H100 GPU 的 PCIe 插卡产品说明，列出了该变体的显存、接口和功率条件。
- B：一块 HGX H100 八 GPU 底板的说明，其中采用 SXM 模组，并给出 NVLink/NVSwitch 互联结构。
- C：某厂商基于 B 构建的完整服务器配置，另外列出了 CPU、DIMM、网卡、磁盘、BMC、机箱和电源条件。

思考：H100、PCIe 插卡、SXM、HGX 底板与完整服务器分别描述哪一层？哪份资料能够作为核对整机上架条件的起点？拿到 B 能否直接认定已拿到一台可开机的服务器？

**参考推导：**按“产品 → 形态 → 平台/底板 → 整机”的层次逐项归位。

| 名称 | 归属 | 从这一层继续向下查什么 |
| --- | --- | --- |
| H100 | GPU 产品系列，仍需精确变体 | 显存、形态、接口与运行条件 |
| PCIe 插卡、SXM | GPU 的硬件形态 | 插槽或专用底板、供电与散热配套 |
| HGX H100 底板 | 多 GPU 平台中的底板 | 与主机连接、GPU 互联及整机集成条件 |
| C 中的厂商服务器 | 完整系统 | 整机尺寸重量、设施条件和实际配置 |

C 是核对整机上架条件的起点，之后要与目标机架的配电、散热和安装条件逐项匹配。B 提供 GPU 子系统及其集成要求，CPU、主机内存、启动存储等仍需由完整系统配齐。这个练习与[平台形态篇](03_PCIe卡_SXM_HGX与整机平台.md)使用相同的层次划分。

### 给扩容方案计算一个明确结果

最后补齐一组专用于本题的供电条件：

- 三台现有节点与拟新增节点的整机交流输入功率预算均为 4 kW，已包含 PSU 损耗。
- 交换机等其余设备合计按 1 kW 输入功率计，三台与四台方案都取这个值。
- A、B 两条供电路径独立，每路允许的持续输入负载为 14 kW；正常时平均分担。
- 目标是在任一路故障后，剩余一路承担全部预算负载且维持同一运行目标。设备供电接法支持这一切换，其他设施条件已另行满足。

思考：三台方案满足这个供电目标吗？加入第四台后呢？如果计算三台方案的余量时把两路容量相加，会遗漏什么？

**参考推导：**先求整机输入总量，再分别检查正常分担和单路故障两种状态。

| 方案 | 总输入负载 | 正常时每路 | 单路故障后剩余一路 | 与 14 kW 限额比较 |
| --- | --- | --- | --- | --- |
| 三台节点 | `3 × 4 + 1 = 13 kW` | `13 ÷ 2 = 6.5 kW` | `13 kW` | 满足本题目标，故障状态余量 1 kW |
| 四台节点 | `4 × 4 + 1 = 17 kW` | `17 ÷ 2 = 8.5 kW` | `17 kW` | 超出 3 kW，不能按当前目标扩容 |

第四台加入后，正常分担状态仍低于每路限额，约束出现在失去一路之后。把两路加成 28 kW 会掩盖这一点。若维持四台及既定负载，需提高每条剩余路径可承受的容量；若保持现有供电条件，则需减少预算负载或调整节点数量。为故障时限功率而修改运行目标，需要作为另一套有明确性能条件的方案评估。

这个结果使用的是已经包含 PSU 损耗的整机输入功率，可以直接与本题给定的输入侧持续容量比较。实际设施规划还要采用对应设备和回路的完整条件，供电层次的读法见[管理入口与运行条件](04_管理入口与运行条件.md)。

## 把交接材料改写成自己的节点画像

可以用一页纸整理五组信息：

- **身份与位置**：节点、序列号、机架、主机/BMC 地址、设备标识。
- **容量与连接**：CPU/NUMA、主机内存、逐卡显存、PCIe 分支、GPU/NIC/NVMe 映射。
- **对外路径**：端口、线缆、交换机、网络职责、存储入口。
- **运行条件**：电源路径、冗余假设、机架功率与冷却条件。
- **已经验证与仍然未知**：每项状态的采集时间、来源、能够支持的结论及待补证据。

完成这张画像后，应能同时说明设备数量、连接路径、共享关系和当前状态，并根据条件充分程度选择直接推导或继续补充证据。
