# 故障设备撤回、作业恢复与节点复归

计划升级时，我们可以先保检查点、再摘流排空、最后重启维护；可硬件故障从来不打招呼——它会在训练跑得正欢、推理流量满载的深夜，突然击穿 8 卡节点上的一张 GPU。

故障发生后的前 60 秒里，运维最容易犯三个致命误判：以为 Device Plugin 上报坏卡后 Kubernetes 会自动给旧 Pod “热换一张好卡”；以为机房把新卡插回原槽位、节点重新亮出 `8/8` 就能直接接流量；或者在隔离故障节点时忘了同机还有在线推理副本，一把强杀引发线上报错。

第 18 章讲透了如何把 Xid、ECC 与 PCIe AER 证据锁定到具体硬件。本篇承接已经确认需隔离的故障场景，用同一套容量账本完整走通**故障设备撤回 → 训推双线业务恢复 → 换件更新身份与节点复归**的全闭环。

## 一、健康库存、旧 Pod 分配与应用进度的三条异步链

来看本次突发故障的初始局面：域 B 的 4 台 8 卡节点均运行在基线 v1 上。`train-12-b` 占用了 `node-5 / node-6 / node-7` 的半机训练槽位（每节点 4 卡 + 1 VF），`node-8` 训练槽位空闲待命。

与此同时，这 4 台节点的另 4 张卡正承载着在线推理服务 `infer-svc-1`（每台 1 个主力 TP=2 副本 + 2 卡 MIG 小模型实例）。

此刻，`node-7` 上归属 `train-12-b` worker 的一张 H100 发生不可恢复故障，被 Device Plugin 标记为 `Unhealthy`。这一瞬间的状态变化会沿**三条互不等待的异步路径**各自传播：

1. **库存路径**：Device Plugin 通知 kubelet 更新设备健康清单，Node 的 `Allocatable` 下降，调度器随后同步感知。
2. **应用路径**：运行在故障卡上的 CUDA 进程报错退出或挂起，进而拖垮同通信组的其余 11 个 Rank。
3. **控制器路径**：作业控制器察觉成员异常，依据重试策略尝试停止旧组并重新调度。

### 不健康上报究竟改变了什么？

在 Kubernetes `v1.36` 的 Device Plugin 机制下，必须牢牢记住一条铁律：**单卡变 `Unhealthy` 时，Node 的 `Capacity` 保持不变，只有 `Allocatable` 扣减；并且已经分配给存量 Pod 的设备集合绝不会自动缩容或热迁移！**

也就是说，在 `node-7` 这台 8 卡节点上：
- Node 的 GPU `Capacity / Allocatable` 从 `8 / 8` 变为 **`8 / 7`**；
- 旧训练 worker 的 Pod 分配账本里，依然绑着原来的 4 张卡（包含那张坏卡），直到该 Pod 彻底终止才释放；
- 在 Kubernetes `v1.36` 默认启用的 `ResourceHealthStatus`（Beta）特性下，可以直接在 Pod 的容器状态中读出已分配设备的健康标记，再配合 kubelet PodResources 将坏卡 UUID 与 Pod UID 精准对齐。

下表完整追踪了 `node-7` 从突发坏卡到维修复归五个时点的库存与容量变化：

| 处置时点 | `node-7` GPU Capacity / Allocatable | 旧分配、隔离态与同域训练容量变化 |
| --- | :---: | --- |
| **正常运行** | `8 / 8` | 推理池占 4 卡，`train-12-b` 旧 worker 占 4 卡（含故障目标卡）；域 B 有 4 个训练落点 |
| **插件上报坏卡** | `8 / 7` | 旧 worker 仍抓着原 4 卡不放；扣除推理 4 卡后余量 $7 - 4 = 3 < 4$，`node-7` 丧失训练落点 |
| **节点隔离、旧组终止** | `8 / 7` | 旧训练分配已释放，推理副本已无损漂移，节点挂维修污点；`node-5 / node-6 / node-8` 凑齐 3 落点 |
| **换件重启、上报健康** | `8 / 8` | 新卡以**新 UUID** 进入健康库存，但节点仍锁在维修隔离区，禁止普通生产落入 |
| **复归验收通过并开放** | `8 / 8` | 撤除维修污点，`node-7` 重新成为域 B 的合格替换落点与推理冗余位 |

从容量账本看，`node-7` 哪怕卸下旧训练 worker、仅剩 3 张空闲健康卡，对需要 4 张整卡的训练落点来说贡献值已跌为 **`0`**，域 B 的合格训练落点由 4 降至 3。更重要的是，在查明故障是否波及上游 PCIe Switch、NVSwitch 底板或整机供电之前，不能放任其他单卡任务继续挤在故障节点上——**规范做法是直接按整节点维度实施维修隔离**。

## 二、现场取证、节点隔离与训推双线恢复

发现致命 GPU 错误后，第一动作绝不是立刻重启机器（重启会清空内核日志与部分寄存器计数），而是**先冻结现场证据、挂上维修隔离污点，再把节点上的在线推理与离线训练分别送走**。

```bash
# 1. 核对 node-7 库存跌落（8/7）及旧 Pod 已分配设备健康状态（K8s v1.36 ResourceHealthStatus）
$ kubectl get node node-7 \
  -o jsonpath='{.status.capacity.nvidia\.com/gpu}/{.status.allocatable.nvidia\.com/gpu}{"\n"}'
8/7

$ kubectl get pod -n ai-demo train-12-b-worker-2 \
  -o jsonpath='{.status.containerStatuses[0].allocatedResourcesStatus}{"\n"}'
[{"name":"nvidia.com/gpu","resources":[{"health":"Unhealthy","resourceID":"GPU-9a7f...1c04"},...]}]

# 2. 留存故障瞬间的不可变取证包（boot_id、UUID/BDF、Xid 与 PCIe AER 时间窗）
$ cat /proc/sys/kernel/random/boot_id > /tmp/inc-node7/boot_id.txt
$ nvidia-smi --query-gpu=index,uuid,pci.bus_id,ecc.errors.uncorrected.volatile.total \
  --format=csv > /tmp/inc-node7/gpu_inventory.csv
$ dmesg -T | grep -E "NVRM: Xid|AER:" > /tmp/inc-node7/kernel_errors.log

# 3. 挂上维修隔离污点（彻底阻断新放置，区分于日常计划升级的 acceptance 污点）
$ kubectl taint nodes node-7 node-role.infra/repair=true:NoSchedule

# 4. 对同节点上的在线推理副本执行 PDB 受控的无损摘流，使其平滑漂移至健康节点
$ kubectl drain node-7 --pod-selector='app=infer-svc-1' --ignore-daemonsets --timeout=180s
```

隔离落定后，集群进入**两条互相解耦的并行进度线**，平台必须分头记账、切忌混为一谈：

- **业务恢复线（先保线上与训练进度）**：
  - **在线推理侧**：借助前一篇配置好的 `Readiness Probe + preStop + PDB`，`node-7` 上的 `infer-svc-1` 副本在零报错前提下平滑摘流，并在具备反亲和余量的健康节点重新拉起，第一时间守住高峰 TTFT/TPOT SLO。
  - **分布式训练侧**：停止已损坏的 `train-12-b` 旧尝试，确认旧 Pod 与 VF 账本完全归零；从共享存储核验最近一份完整已提交的检查点，调度器把新尝试落位到 **`node-5 / node-6 / node-8`**，重新登记新的 Pod UID、Rank 与 GPU/VF 映射，直至全组越过故障前步数并提交新检查点。
- **节点维修线（按硬件规程拆修）**：确认 `node-7` 上所有残留 GPU 进程清空后，按厂商规程执行断电换件（或整板更换），全过程持续留档维修动作与新件序列号。

如果这场故障不巧叠加了上一篇的“域 B 正在对 `node-8` 做版本试点”，域 B 就会瞬间只剩 `node-5 / node-6` 两台合格节点，**`train-12-b` 将直接被同域约束卡死在 Pending**——哪怕域 A 的 `node-4` 空着也没用。这就是第 04 篇反复强调“维护余量与故障余量必须共用同一张域内账本”的根本原因。

> [!summary] 核心结论：**业务恢复与硬件修好是两件独立事件**
> 借助备用节点 `node-8`，训练和推理完全可以在 `node-7` 还没修好之前就宣告**业务恢复完成**；反之，哪怕机房工程师 1 小时就把 `node-7` 换好了新卡、监控重新显示 `8/8`，只要检查点不可读或新组还没越过旧进度，业务就依然处于故障态。

## 三、以新设备身份完成节点复归验收

机房把故障的 H100 SXM 模组（或整块 HGX 底板）更换完毕并重新上电启动后，绝不能因为 `kubectl get node` 再次显示 `8/8` 就直接删掉维修污点放行生产。故障节点经维修、身份更新并重新通过全量验收回到生产资源池的闭环，称为**节点复归（Node Reinstatement）**。

复归的第一步是**刷新物理身份映射**：新换上的 GPU 即使插在完全相同的物理槽位、拥有一模一样的 PCI BDF 地址，它的 **GPU UUID 也已经彻底改变**。平台必须为旧 UUID 标上退役终止时间戳，将新 UUID 重新绑定到机架资产台账、NVLink 拓扑图和 DCGM/Prometheus 监控标签上，避免历史故障记录与新硬件混作一团。

```bash
# 1. 换件重启后刷新设备身份，核对新 UUID、全 8 卡 Fabric Manager 与库存恢复
$ nvidia-smi --query-gpu=index,uuid,pci.bus_id,serial --format=csv
# 将新出现的 GPU UUID 写入资产台账并关闭旧 UUID 生命周期

$ systemctl is-active nvidia-fabricmanager && nvidia-smi nvlink -s | grep -c "GB/s"
active
144                                   # 8 卡 × 18 条 NVLink 全量恢复激活

$ kubectl get node node-7 \
  -o jsonpath='{.status.capacity.nvidia\.com/gpu}/{.status.allocatable.nvidia\.com/gpu}{"\n"}'
8/8

# 2. 保持 node-role.infra/repair 污点隔离，按第 03 篇执行全量复归验收：
#    - DCGM Level 3 全 8 卡压测（新 boot_id 下零新增 ECC/Xid/AER）
#    - 8 卡 NVSwitch 同机集合 + 逐卡 UUID 计算回读
#    - 同域 GDR + 12-Rank AllReduce 复测（确认在基线 10% 门槛内）
#    - 推理池 MIG/NVMe 预热与并发 TTFT/TPOT SLO 复测

# 3. 全部复归证据签收归档后，正式撤除维修隔离污点，开放生产调度
$ kubectl taint nodes node-7 node-role.infra/repair:NoSchedule-
node/node-7 untainted
```

在维修复归的最后一关，常会遇到一种极具迷惑性的“半康复”状态：**换件后 `8/8` 库存恢复、DCGM 诊断和单卡 CUDA 回读全绿，但同域 12-Rank AllReduce 中位耗时却超过了原 10% 基线门槛。**

遇到这种情况，唯一正确的运维裁决是：台账记录“硬件库存与单卡计算层已恢复”，**但坚决维持维修隔离，拒绝让它以原规格复归训练池！** 必须继续深挖 NVSwitch 链路、PCIe 协商速率、DMA-BUF 路径或跨机端口计数；如果平台最终决定把降级硬件降配改作其他低要求负载池，也必须走正式的资源池重定义与重新验收流程，绝不允许悄悄放水拉低原生产池的服务标准。

复归达标后，`node-7` 重新成为域 B 的合格备用落点与推理冗余位，而此时正在 `node-5 / node-6 / node-8` 上稳定推进的 `train-12-b` 无须人为折腾迁回——只需在台账里同时保住“当前作业实际落点”与“全池最新可用余量”两份事实即可。

> [!tip] 故障撤回与节点复归核对清单
> - **先证后停**：重启前固化 `boot_id`、故障 UUID/BDF、Pod UID、Rank 与 Xid/AER 日志，不丢根因现场。
> - **双线保业务**：推理副本经 PDB + Readiness 无损漂移保 SLA；训练作业按原子检查点在同域备用落点整组重建。
> - **换件必更 ID**：更新新 GPU UUID 资产与监控映射，在维修隔离区走完硬件、互联、双池基准复测后再删污点复归。

至此，整章的七块工程拼图严丝合缝地咬合在了一起：**配置基线**管住交付输入，**权限隔离**守住租户红线，**双池分层验收**把关生产准入，**机房与域内账本**算清持续容量，**恢复资料与关键路径**备齐重建底牌，**双轨排空与试点回滚**驾驭计划变更，**异步撤回与复归闭环**兜住突发故障。
