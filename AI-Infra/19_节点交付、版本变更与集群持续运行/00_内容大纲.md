# 第 19 章 节点交付、版本变更与集群持续运行｜内容大纲

## 读者起点与本章任务

读者已有 Linux/Kubernetes 基础。第 03、10—13 章解释了驱动、容器、设备分配和网络交付，第 14—16 章解释了隔离与成组放置，第 17 章建立带身份、时间和测试条件的性能基线，第 18 章区分作业恢复和节点复归。本章把这些机制用于一个新的问题：如何持续交付一组**有明确使用条件、可验收、能恢复的作业容量**。

先解释节点生命周期与配置基线，再定义租户可用的权限边界，据此验收一台节点；随后从机房与拓扑约束推导整组容量。在动手变更之前，先建立恢复资料、检查点与时间预算，最后用它们评审计划升级和非计划故障。第 20 章再沿一份作业工单综合运用，不在本章重复全部排障过程。

## 可检验的学习目标

1. 区分配置目标、运行实态、性能基线与生产准入，沿内核、驱动、容器、设备与通信依赖写出交付证据，解释配置漂移及管理归属。
2. 沿 API 权限、Pod 准入、设备交付和两张网络找到隔离执行点，为允许与拒绝分别设计有效对照。
3. 由供电、散热、单向网络割面、存储窗口和同域放置复算承载量，区分总容量、空闲落点、维护余量与故障余量。
4. 判断检查点是否完整可读，组织可独立取得的恢复资料，按依赖图计算恢复时间并检查恢复点预算。
5. 用同一容量账本评审排空、混版本试点、停批、回滚和维修复归，分别说明旧分配、新库存、应用进度与节点开放的完成条件。

## 案例、版本与配图

- 保留原有双机架算例。A 为 h1–h4，B 为 h5–h8；开篇 h8 尚待交付。每节点为四卡 HGX H100 的直连 NVLink 拓扑、一个 200 Gb/s RoCEv2 口及独立存储网。相比第 17—18 章，**作业规格相同，但节点由八卡 NVSwitch 改为四卡直连 NVLink**，每节点只承载一个四卡 worker；旧章的同机数值不直接移用。
- 固定训练为同域三 worker、每 worker 四 Rank，请求 4 GPU、16 CPU、96 GiB 主机内存和一个 RDMA VF。节点在满足其他约束后最多贡献一个落点。各篇变更、故障、恢复是明确分开的教学窗口；两租户小探针是隔离验收的独立场景。
- 主线为 Kubernetes v1.36 Device Plugin、整卡、CDI，主机镜像负责内核及 GPU/NIC 驱动，GPU Operator v26.7.2 负责其余指定组件；关闭 NRI。保留 B0 的 Ubuntu 24.04、6.8.0-52-generic、595.91.07 和 B1 的 6.8.0-53-generic 教学设定。版本矩阵条目不等同于这一整套组合已经实测支持。
- 所有数量、日志式描述、性能和恢复结果均为教学构造。复用 NCCL 2.27.3、nccl-tests v2.17.9、perftest 26.07.8 的机制口径；精确 CUDA 驱动对应值与次版本兼容边界单独核对，避免把 Toolkit 对应驱动表读成所有程序的绝对下限。
- 保留五幅现有插画，按新篇序重命名、逐幅打开复核；流程用 Mermaid，精确预算用表格。原大纲链接的配图说明在修订开始时缺失，本轮补建与现有图稿对应的 [配图说明](_配图/配图说明.md)，包含可复制提示词、图注、替代文本及复核记录，不沿用无法证明的历史验收声明。
