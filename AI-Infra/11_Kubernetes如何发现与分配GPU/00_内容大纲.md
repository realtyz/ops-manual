# 11 Kubernetes 如何发现与分配 GPU

## 范围、前置知识与读者目标

- **范围**　以 Linux 节点上的普通 Pod 申请完整 NVIDIA GPU 为主线，追踪设备发现、资源发布、Pod 放置、设备分配、节点准备和容器注入。先讲 Device Plugin，再用同一负载对照 NVIDIA DRA 的显式 Claim 路径。NFD/GFD 用于解释节点特征如何参与放置，CDI 用于解释已选设备如何交给容器。主例关闭 MIG 与共享，容量单位是一张完整 GPU。
- **必要前置**　能读 Pod、Node 和容器级 `resources`，知道 API Server、scheduler、kubelet 和容器运行时各自的位置。开篇补齐两组关系：Pod 调度绑定到节点与容器得到设备是两个时点，主机驱动枚举的 GPU UUID 与容器内的 CUDA 序号是两种标识。解释注入前先用几句交代 CRI 如何提交容器配置，以及 CDI 全名如何查找节点上的设备描述。读者可依照材料离线推导。
- **跨章分工**　第 03、10 章处理驱动与 CUDA 兼容、OCI 设备节点、库挂载和访问权限，本章追到运行时收到什么以及容器看到哪张卡。GPU Operator 安装与组件协调交给第 12 章，RDMA 设备交给第 13 章，共享、MIG 和隔离交给第 14 章，跨 Pod 调度与 NUMA 策略交给第 15 章，硬件错误诊断和升级交给第 18、19 章。
- **读完应能独立判断**　给定 Pod、Node 和节点上的 Pod 请求，能算出还有多少 GPU 资源可用于调度，并判断不满足的是卡数还是节点约束。给定标签、ResourceSlice 和 Claim，能说明属性描述的是整台节点还是某个设备，以及哪张卡满足条件。给定一次启动失败，能用设备 ID、Pod UID 或 Claim UID 找出最早失败的是上报、调度、分配、准备还是注入，并指出下一项能验证的证据。

## 贯穿案例与版本口径

- **教学场景**　`gpu-h` 有两张同型 H100（UUID 简称 A、B），`gpu-a` 有两张同型 A100（C、D）。为 DRA 算例假定驱动为 A、B 发布的 `memory` 是 `80Gi`，C、D 是 `40Gi`，均为教学输入。两路使用独立环境或两份独立状态快照，负载用同一镜像。Device Plugin 例中，A 已分给一个 Pod，B 健康且未分配。先计算 `gpu-h` 的余量，再从新 Pod 已绑定该节点的时点跟踪 B，随后补上让 Pod 落到 `gpu-h` 的型号标签。DRA 对照保留相同的设备与占用关系，改用显式 Claim 表达“一张报告总显存大于 40 GiB 的卡”。各故障变体从指定快照独立推演。除该变体声明的变化外，CPU、内存、污点和其他放置条件均满足。
- **版本锚点**　Kubernetes 文档用 v1.36 归档，源码固定在 v1.36.0。独立 Device Plugin 与 GFD 例以 NVIDIA `k8s-device-plugin` v0.19.2 为准，运行时对照用 containerd v2.3.0。DRA 例用 NVIDIA DRA Driver v0.5.1，依赖说明采用 GPU Operator v26.7 文档的托管路径。上述版本用于核对接口和机制，实验环境的具体版本组合待选定。 [Kubernetes v1.36 Device Plugins](https://v1-36.docs.kubernetes.io/docs/concepts/extend-kubernetes/compute-storage-net/device-plugins/) · [Kubernetes v1.36 DRA](https://v1-36.docs.kubernetes.io/docs/concepts/scheduling-eviction/dynamic-resource-allocation/) · [NVIDIA Device Plugin v0.19.2](https://github.com/NVIDIA/k8s-device-plugin/tree/v0.19.2) · [containerd v2.3.0 CRI 配置](https://github.com/containerd/containerd/blob/v2.3.0/docs/cri/config.md) · [GPU Operator v26.7 DRA 说明](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/26.7/dra-intro-install.html)
- **材料口径**　用可复算的状态表和按版本核对的 YAML 字段串联案例。实测若可取得，记录发行版、GPU 型号与驱动、插件与运行时版本、实际配置、镜像摘要、采集命令与时间。教学状态和配置推演标明假设，源码中的消息与实机日志分开标注。流程与时序用 Mermaid，计数、设备匹配与排查用表格。

## 01 设备插件怎样让 Node 出现 `nvidia.com/gpu`

- **问题与预期结论**　宿主机能枚举两张 GPU，为什么 Node 仍可能没有这一资源？读者应能指出插件注册、设备列表上报和 kubelet 发布 Node 状态各需要什么证据，并从健康变化推导哪些数值会改变。
- **解释顺序**　从 NVIDIA 插件依赖宿主机驱动发现设备讲起。插件先在 `/var/lib/kubelet/device-plugins/` 启动自己的 gRPC 服务，再向 kubelet 注册端点、设备插件 API 版本和资源名。kubelet 经 `ListAndWatch` 接收初始设备列表和后续变更，由 kubelet 更新 Node 状态。一张已上报的卡被标记为 `Unhealthy` 时，保持在列表中的这张卡仍计入 `Capacity`，`Allocatable` 随健康设备数下降，已分到该设备的 Pod 仍持有原设备。kubelet 重启后看插件是否重新注册并重新上报。硬件错误触发条件和恢复过程交给第 18 章。
- **支撑材料**　拟画“驱动枚举 → 插件 socket → kubelet → Node 状态”时序，标出 `Register` 的 `Version`、`Endpoint`、`ResourceName` 与 `ListAndWatch` 的设备 ID、`Health`。将插件注册日志中的资源名和端点、kubelet V(2) 资源更新日志的 `resourceName`、`totalCount`、`healthyCount`，与同节点两个时点的 `.status.capacity["nvidia.com/gpu"]`、`.status.allocatable["nvidia.com/gpu"]` 对齐。用两卡健康时 `2/2`、一张卡仍在列表但标记不健康时 `2/1` 说明健康状态怎样传递。 [Kubernetes 注册与健康更新](https://v1-36.docs.kubernetes.io/docs/concepts/extend-kubernetes/compute-storage-net/device-plugins/#device-plugin-registration) · [NVIDIA 注册和健康上报源码](https://github.com/NVIDIA/k8s-device-plugin/blob/v0.19.2/internal/plugin/server.go) · [kubelet Device Manager v1.36.0](https://github.com/kubernetes/kubernetes/blob/v1.36.0/pkg/kubelet/cm/devicemanager/manager.go)

## 02 调度器怎样从 GPU 请求判断节点是否放得下

- **问题与预期结论**　为什么 Node 写着 `Allocatable: 2`，申请两张卡的 Pod 仍可能排不上？读者应能用调度器已经计入的 Pod 请求计算余额，理解 `nvidia.com/gpu` 的计数与 Pod 放置条件。
- **解释顺序**　从单容器 `resources.limits["nvidia.com/gpu"]` 读起。只写 limit 时 Kubernetes 将其用作 request，同时写两项时数值须相等，GPU 请求须提供 limit，扩展资源按整数且不可超额承诺。介绍 `Capacity`、`Allocatable` 和调度器已计入的请求三个量。在本章默认调度器、Device Plugin 供给的前提下，`NodeResourcesFit` 用 `Allocatable − 已计入请求` 检查新请求，仍须通过其他节点约束。运行中应用的 GPU 利用率只反映活动程度。调度通过时可确定 Pod 的候选节点，下一节再追具体设备 ID。复杂 Pod 的有效请求计算和调度策略交给第 15 章。
- **支撑材料**　拟并排给出 `limits: 1` 单写、`requests` 与 `limits` 同值、以及只写 `requests` 的三个 GPU 字段片段，用官方规则解释默认和校验结果。对 `gpu-h` 做三行数字表：A、B 都健康且都未分配时 `2−0=2`；A 已占一张时 `2−1=1`；随后 B 不健康且 A 的请求仍计入时 `1−1=0`。分别代入新请求 1 和 2，配 Pod 的 `PodScheduled` 条件与 `FailedScheduling` 事件中的 `Insufficient nvidia.com/gpu`。该事件需与各候选节点的其他过滤原因同读。 [GPU 请求规则](https://v1-36.docs.kubernetes.io/docs/tasks/manage-gpus/scheduling-gpus/#using-device-plugins) · [扩展资源规则](https://v1-36.docs.kubernetes.io/docs/concepts/configuration/manage-resources-containers/#extended-resources) · [NodeResourcesFit v1.36.0 源码](https://github.com/kubernetes/kubernetes/blob/v1.36.0/pkg/scheduler/framework/plugins/noderesources/fit.go)

## 03 Pod 绑定节点后，哪张卡怎样交给容器

- **问题与预期结论**　Pod 已绑定 `gpu-h` 且请求一张卡，谁决定是 B，如何验证运行时实际收到了 B？读者应能从节点内分配追到容器看到的 UUID，并区分分配失败、注入失败和应用启动后的计算失败。
- **解释顺序**　以 Pod 已绑定 `gpu-h` 为起点，固定 A 已分配、B 为唯一健康且未分配的设备。kubelet 在节点接纳 Pod 时由 Device Manager 结合健康与占用状态选设备 ID，条件满足时可采纳 `GetPreferredAllocation` 建议。再传 ID 给插件的 `Allocate`，由返回的 `ContainerAllocateResponse` 提供容器启动所需信息。kubelet 按 Pod 与容器记录分配，创建容器时取出配置交给 CRI，Pod 结束后回收记录。`PreStartContainer` 作为协议可选项简述。主例显式设 `flags.plugin.deviceListStrategy: cdi-cri` 和 `flags.plugin.deviceIDStrategy: uuid`，从响应的 CDI 全名和 CRI `CDIDevices` 追到 containerd 读取插件生成的节点规格。对照 v0.19.2 默认 `envvar`，以 `NVIDIA_VISIBLE_DEVICES` 和实际选用的 NVIDIA Runtime 说明交接条件。`volume-mounts`、`cdi-annotations` 只列交接媒介。权限、库文件、OCI 修改细节交给第 10 章，拓扑放置交给第 15 章。
- **支撑材料**　拟用一张时序图连接 scheduler、kubelet、插件和 containerd。并排读插件配置、按 v1.36.0 源码可见的 kubelet V(4) 分配日志字段 `devices`、`resourceName`、`pod`、`containerName`、`Allocate` 响应、CRI 输入和节点上与全名匹配的 CDI 条目。用本机 PodResources `List` 的命名空间、Pod、容器、`resource_name`、`device_ids` 将分配 ID 连到宿主机及容器的 `nvidia-smi -L`，再用最小 CUDA 调用验证计算。记录 CDI 名时以本路径实际生成的规格为准。 [kubelet Device Manager v1.36.0 源码](https://github.com/kubernetes/kubernetes/blob/v1.36.0/pkg/kubelet/cm/devicemanager/manager.go) · [NVIDIA 分配与交接策略](https://github.com/NVIDIA/k8s-device-plugin/tree/v0.19.2#configuration-option-details) · [NVIDIA CDI 规格生成](https://github.com/NVIDIA/k8s-device-plugin/blob/v0.19.2/internal/cdi/cdi.go) · [PodResources API](https://v1-36.docs.kubernetes.io/docs/concepts/extend-kubernetes/compute-storage-net/device-plugins/#monitoring-device-plugin-resources)
- **已核对的版本边界**　Device Manager 接收 Device Plugin 返回的 CDI 名称这一能力于 Kubernetes v1.31 转为 GA，见 `DevicePluginCDIDevices`。运行时仍需能消费 CDI，containerd v2.3.0 示例核对 `enable_cdi` 和 `cdi_spec_dirs`。`cdi-cri` 与 `envvar` 的默认和支持条件按独立 NVIDIA 插件示例说明。 [Kubernetes Device Plugin 的 CDI 支持](https://v1-36.docs.kubernetes.io/docs/concepts/extend-kubernetes/compute-storage-net/device-plugins/#device-plugin-implementation) · [kubelet 容器配置与设备分配的衔接](https://github.com/kubernetes/kubernetes/blob/v1.36.0/pkg/kubelet/cm/container_manager_linux.go) · [containerd v2.3.0 CRI 配置](https://github.com/containerd/containerd/blob/v2.3.0/docs/cri/config.md)

## 04 型号、显存与卡数怎样参与节点筛选

- **问题与预期结论**　两台节点都写着 `nvidia.com/gpu: 2`，怎样让 Pod 落到 H100 节点？如果节点有 GPU 标签却没有可分配资源，应读哪些字段？读者应能判断 `nodeSelector` 与 GPU 请求各自缩小了什么范围。
- **解释顺序**　先用 NFD 的 PCI 厂商存在性信息解释通用硬件发现，再用 GFD 的型号、显存和卡数标签解释 NVIDIA 专用发现。用 GFD v0.19.2 默认的 `NodeFeature` 发布方式说明 GFD 提供特征、NFD 投影到 Node 标签。随后让单容器 Pod 同时要求 H100 的节点标签和一张 `nvidia.com/gpu`，分别过标签和数量检查。用混装节点的短反例限定保证：节点标签约束 Pod 的节点，设备插件按资源名与本地库存分配；当同一资源名下含不同型号时，单靠节点标签无法逐卡承诺型号。NFD 的 `NodeFeatureRule` 可另行发布扩展资源，示例采用常规标签配置。部署规则交给第 12 章，混合 GPU 池和共享口径交给第 14、15 章。
- **支撑材料**　拟并列 Node `.metadata.labels` 和 `.status.allocatable` 摘录。读一个按实际 NFD 配置生成的 NVIDIA PCI 标签，以及 `nvidia.com/gpu.product`、`nvidia.com/gpu.count`、`nvidia.com/gpu.memory`，显存标签按 MiB 解释。用“型号满足、数量有余额”“型号满足、数量无余额”“型号不符、数量有余额”三行表，逐行判断 `nodeSelector` 与资源检查结果。用 GFD 默认配置源码和 NFD 官方说明证明标签的来源，用现有 Pod 请求与 Node 状态证明调度余量。 [NFD 特征标签](https://nfd.sigs.k8s.io/usage/features.html) · [GFD v0.19.2 发布方式](https://github.com/NVIDIA/k8s-device-plugin/blob/v0.19.2/cmd/gpu-feature-discovery/main.go) · [GFD 标签含义](https://github.com/NVIDIA/k8s-device-plugin/blob/main/docs/gpu-feature-discovery/README.md#generated-labels) · [节点标签与 Pod 放置](https://kubernetes.io/docs/concepts/scheduling-eviction/assign-pod-node/)

## 05 DRA 怎样表达设备条件并选定 GPU

- **问题与预期结论**　当负载需要“任意一张总显存大于 40 GiB 的卡”时，怎样从节点标签和整数计数过渡到按设备匹配？读者应能串起 `DeviceClass`、`ResourceSlice`、`ResourceClaim`、`ResourceClaimTemplate` 和 Pod，手算哪张设备符合条件、哪张已被占用。
- **解释顺序**　从 NVIDIA GPU 节点插件发布的 `ResourceSlice` 开始，说明 `driver`、`pool`、设备名、节点可达范围及设备级 `attributes` 和 `capacity`。再看管理员或驱动提供的 `DeviceClass` 如何定义候选设备类，显式 Claim 如何请求该类、设备数量和 CEL 条件。主例用 `ResourceClaimTemplate` 创建每个 Pod 的 Claim，分别解释 `Pod.spec.resourceClaims` 和容器 `resources.claims` 的引用。与同命名空间内直接引用独立 Claim 对照生命周期和消费关系。调度器读取发布到 API 的切片、已有 Claim 分配和新 Pod 的约束，匹配设备与可访问节点，在 Claim 写下分配结果和保留给哪个消费者，再完成 Pod 绑定。模板只提供声明，切片是库存描述，分配结果和授权消费者查看 Claim 状态。共享、优先备选、设备污点与动态 MIG 留给对应专题。
- **支撑材料**　拟裁剪驱动发布的 `ResourceSlice`，保留 `spec.driver`、`spec.pool`、`spec.nodeName`、设备名和 `memory` 等字段。用 `resource.k8s.io/v1` 的模板与 Pod 字段对照官方例子，在 `exactly` 下写 `deviceClassName: gpu.nvidia.com`、`allocationMode: ExactCount`、`count: 1`，比较 `device.capacity['gpu.nvidia.com'].memory.isGreaterThan(quantity("40Gi"))`。按教学值代入 A、B 为 `80Gi`、C、D 为 `40Gi`，先得 A/B 满足严格大于，再因 A 已分配只剩 B。以 `status.allocation.devices.results[]` 的 `request/driver/pool/device` 和 `status.reservedFor[].uid` 确认分配与消费关系。显存字段用来筛选总容量，运行时空闲显存需要单独采样。 [Kubernetes DRA 对象和分配流程](https://v1-36.docs.kubernetes.io/docs/concepts/scheduling-eviction/dynamic-resource-allocation/#dra-terminology) · [ResourceClaim v1 API](https://v1-36.docs.kubernetes.io/docs/reference/kubernetes-api/resource/resource-claim-v1/) · [NVIDIA 整卡申请和 CEL 示例](https://dra-driver-nvidia-gpu.sigs.k8s.io/docs/guides/gpu-allocation/allocating-gpus/) · [NVIDIA 切片字段](https://dra-driver-nvidia-gpu.sigs.k8s.io/docs/reference/resourceslice-attributes/)

## 06 Claim 分配成功后怎样准备并注入设备

- **问题与预期结论**　Claim 已列出设备，为什么容器仍可能启动失败？读者应能从控制面分配追到 NVIDIA 节点插件准备设备、运行时注入以及设备释放，并指出每一步的失败证据。
- **解释顺序**　kubelet 读取 Claim 的分配与消费关系，按驱动名找节点上的 DRA 插件；`NodePrepareResources` RPC 用命名空间、名称和 UID 标识 Claim，驱动依据 Claim 的分配结果准备设备，生成或维护本例所需的 CDI 规格，返回 CDI 名称。kubelet 将容器引用的设备名放入 CRI，containerd 解析 CDI 规格并启动容器。分别推演节点插件不可用和 CDI 名解析失败两种变体。再用一段结束时序带过 `NodeUnprepareResources` 与 Claim 生命周期，解释同节点仍有 Pod 使用同一 Claim 时为何需保留节点准备状态。具体安装流程交给第 12 章。
- **支撑材料**　拟用时序图标出 `status.allocation` 已写入、`NodePrepareResources` 成功、CRI 创建成功三处拐点。材料配对 Claim UID、驱动名、节点、`driver/pool/device`、准备调用的错误或返回的 CDI 名，以及 `ResourceSlice` 的设备 UUID 到容器 UUID 的核对结果。以 kubelet v1.36.0 的 prepare/unprepare 实现和 NVIDIA v0.5.1 的发布、准备源码核对字段与日志。 [kubelet DRA 管理器 v1.36.0](https://github.com/kubernetes/kubernetes/blob/v1.36.0/pkg/kubelet/cm/dra/manager.go) · [NVIDIA DRA Driver v0.5.1 节点实现](https://github.com/kubernetes-sigs/dra-driver-nvidia-gpu/blob/v0.5.1/cmd/gpu-kubelet-plugin/driver.go) · [NVIDIA 的 GPU 分配与注入流程](https://dra-driver-nvidia-gpu.sigs.k8s.io/docs/concepts/gpu-allocation/#how-scheduling-works)
- **已核对的版本边界**　Kubernetes v1.34 将 DRA 核心和 `resource.k8s.io/v1` 转为稳定版，v1.35 起核心机制始终启用。NVIDIA GPU Operator v26.7 管理 DRA Driver v0.5.1 的路径要求 Kubernetes ≥ v1.34.2、可用的 DeviceClass API、NVIDIA GPU 驱动 ≥ 580、已配置 CDI 的容器运行时，并以 `GPUCluster` 管理该新装路径。托管文档把整卡分配列为 GA。`NVMLDeviceHealthCheck`、`DynamicMIG` 等有各自的成熟度与开关。示例只启用整卡分配，ComputeDomain 的硬件与管理条件留给多节点互联专题。 [Kubernetes v1.34 DRA 发布说明](https://v1-35.docs.kubernetes.io/blog/2025/09/01/kubernetes-v1-34-dra-updates/) · [Kubernetes v1.35 发布说明](https://kubernetes.io/blog/2025/12/17/kubernetes-v1-35-release/#continued-innovation-in-dynamic-resource-allocation-dra) · [NVIDIA DRA Driver 前置条件与成熟度](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/26.7/dra-intro-install.html)

## 07 怎样从请求和现场证据认出实际路径

- **问题与预期结论**　工作负载申请了 GPU，怎样确定该去看 Node、Claim、kubelet 还是运行时？读者应能辨认实际供给路径，并从已有证据推导下一项最能区分原因的检查。
- **解释顺序**　沿“请求形式 → 库存来源 → 选设备者 → 节点准备 → 运行时输入 → 容器验证”回放两条路径。Device Plugin 例按扩展资源在节点间放置，再由 kubelet 在节点内选设备。显式 Claim 例在放置过程中分配设备，由节点插件按 Claim 准备。两例都可把 CDI 名交给同一个 containerd。补充 `DRAExtendedResource` 后，同样的扩展资源请求语法还可能由 DRA 供给。它在 v1.34 为 alpha、默认关闭，在 v1.36 为 beta、默认开启。用 `DeviceClass.spec.extendedResourceName` 解释何时 `nvidia.com/gpu` 可走 DRA，并给出 NVIDIA 托管的 `gpu.nvidia.com` 默认类可用的 `deviceclass.resource.kubernetes.io/gpu.nvidia.com` 名称。说明 Kubernetes 能在同一集群的不同节点为同名资源提供不同后端，而 GPU Operator v26.7 的 `GPUCluster` 与 `ClusterPolicy` 托管路径要求二选一。部署与迁移流程交给第 12、19 章。 [Kubernetes v1.34 DRA 扩展资源说明](https://v1-34.docs.kubernetes.io/docs/concepts/scheduling-eviction/dynamic-resource-allocation/) · [Kubernetes v1.36 DRA 扩展资源说明](https://v1-36.docs.kubernetes.io/docs/concepts/scheduling-eviction/dynamic-resource-allocation/#extended-resource-allocation-by-dra) · [NVIDIA 托管路径和命名限制](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/26.7/dra-intro-install.html)
- **支撑材料**　拟用一张对照表标出两路调度与分配的观察点，再用下列教学记录做判断题。Pod 侧取 `spec.nodeName`、`status.conditions[]` 的 `type/status/reason/message` 以及事件的原因和消息，节点侧按 Pod UID、Claim UID、容器名和时间对齐来源。`Pending` 可覆盖尚未调度和已调度但容器尚未启动的情形，要与绑定状态同读。 [Kubernetes Pod phase 与条件](https://v1-36.docs.kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/#pod-phase) · [Kubernetes PodResources 接口](https://v1-36.docs.kubernetes.io/docs/concepts/extend-kubernetes/compute-storage-net/device-plugins/#monitoring-device-plugin-resources)

## 待核实项

- **实机材料**　目前依据官方文档和源码。GPU 节点上的完整版本组合、实际生效的插件策略和 CDI 规格、CRI 请求、事件措辞、日志级别与 CUDA 探针结果尚待实机确认。若只能离线写作，保留明确标注的推演快照，按所选版本的 API 与源码核对字段。
- **现场字段值**　NFD PCI 标签的具体键取决于部署配置，GFD 标签值取实际卡型与策略。DRA 例的 `device` 名、`memory`、UUID、CDI 全名分别从选定版本的切片、准备输出和规格取证，教学输入不替代实卡枚举。若把兼容入口升级为独立案例，再核对特性开关、目标 DeviceClass 和实际生成的 Claim。

## 供审查的取舍

1. **DRA 的篇幅**　拟用两节走完显式 Claim 的选卡、节点准备与注入。扩展资源兼容入口先放在末节作一段对照。若希望覆盖已有清单如何接入 DRA，可扩成一组两种请求与生成 Claim 的对照材料。
2. **案例深度**　拟以可离线复算的上报、调度和分配记录为主。若希望正文可跟做，可增加一套固定软件版本的验证步骤和完整采集记录，实机材料以可获得的 GPU 环境为准。
