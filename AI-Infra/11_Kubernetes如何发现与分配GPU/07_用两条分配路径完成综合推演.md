# 用两条分配路径完成综合推演

## 两份独立交付材料

以下均为**自拟教学材料**。沿用导读版本与身份表；每道变式题单独改变条件，做完回到原材料。没有 init container、重启式 sidecar、Pod overhead、资源共享、并发竞争、状态传播延迟或额外消费者；CPU、主机内存、污点和其他调度约束均满足。镜像已提供对应 Runtime 和 A100/L4 设备代码。

**材料 P：传统 Device Plugin 的全健康起点。**

```text
resource_name=nvidia.com/gpu
gpu-a: capacity=4, allocatable=4, IDs=[U0,U1,U2,U3]
       product_label=A100-SXM4-40GB, gpu.memory_label=40536
gpu-b: capacity=2, allocatable=2, IDs=[V0,V1]
       product_label=NVIDIA-L4, gpu.memory_label=23034
existing Pod old/worker on gpu-a: effective GPU request=2, IDs=[U0,U1]
gpu-b has no existing GPU requests
new Pod probe-p: one ordinary container worker, limits.nvidia.com/gpu=1
                GPU requests omitted; no nodeSelector

本轮另给定实际结果：
probe-p binds to gpu-a
Device Manager chooses U2; plugin cdi-cri Allocate succeeds
PodResources: lesson-dp/probe-p/worker -> U2
CRI CDI name=nvidia.com/gpu=GPU-33333333-3333-4333-8333-333333333333
runtime creation succeeds, required interfaces and driver files accessible
probe: cuda_count=1, cuda:0 UUID=U2, sync=ok, verify=PASS
```

**材料 D：独立 DRA 起点。**同一批设备只由 DRA 管理；Slice 清单完整且可用，无传统 `nvidia.com/gpu` 数量发布。

```text
driver=gpu.nvidia.com
pool gpu-a: gpu-0=U0, gpu-1=U1, gpu-2=U2, gpu-3=U3
            each capacity.memory=40536Mi; accessible node=gpu-a
pool gpu-b: gpu-0=V0, gpu-1=V1
            each capacity.memory=23034Mi; accessible node=gpu-b
all devices have attributes.type=gpu
existing DRA Claims own U0 and U1; no other allocations
DeviceClass lesson-gpu selects this driver's type=gpu devices
Claim lesson-dra/one-30g:
  request=card, exactly.class=lesson-gpu, mode=ExactCount, count=1
  selector=memory >= quantity('30Gi')   # 此行是第五篇 CEL 的简写
Pod probe-d: pod reference accel -> one-30g; worker consumes accel

本轮另给定实际结果：
allocation=(gpu.nvidia.com,gpu-a,gpu-2), request=card
reservedFor names current probe-d UID; Pod binds gpu-a
NodePrepareResources succeeds; all returned CDI names reach CRI
runtime creation succeeds; probe UUID=U2, sync=ok, verify=PASS
```

## 独立推演题

1. 场景 P 的设备插件先要启动哪个服务、向谁注册、提交哪三项核心信息？`ListAndWatch` 由谁调用、谁返回？Node 的数量最终由谁更新？
2. 材料 P 的新 Pod 有效 GPU request 是多少？若分别改为 `limits=0.5`、只写 `requests=1`、或 `requests=1/limits=2`，哪些可作为本章合法的整卡请求？CPU/主机内存的规则能否直接套在 GPU 整卡上？
3. 在材料 P 的初始快照，若新 Pod 改要 3 张，且不限定型号，能放到某个节点吗？给出每节点预算和无法跨节点拼接的原因。改要 2 张又如何？
4. 回到本轮 probe-p 已在 U2 成功运行。写出 gpu-a 的 Capacity、Allocatable、总 GPU request 与下一份请求的数量预算。如果 old/worker 的 GPU 利用率为 0%，这些量是否随之改变？
5. 将 probe-p 的资源请求、绑定节点、插件 ID、CDI 名、设备节点和 CUDA ordinal 对应起来。哪些由 scheduler、Device Manager、插件、运行时和应用分别决定/执行？为什么 PASS 不能外推 NCCL 成功？
6. 只改变初始材料 P：gpu-a 标签仍在，但插件从未完成注册，Node 无该扩展资源；gpu-b 正常。Pod 同时要求 A100-SXM4-40GB 标签和一张 GPU。能否满足？反过来，gpu-a 资源正常但缺失所要求的型号标签，又会怎样？
7. 初始材料 P 的 U0/U1 已分配。先让空闲 U3 变坏，再独立让已分配 U1 变坏。两种情况各写出 Capacity、Allocatable、数量预算、健康未分配 ID。U1 的应用会被自动换到 U2 吗？
8. 材料 D 的 30 GiB 换算成多少 MiB？哪些设备通过容量筛选，排除既有分配后候选是什么？将同一请求的 count 改为 2 或 3，各能否满足？不要把 Slice 行数当作空闲数。
9. 材料 D 中 `accel`、`one-30g`、`card`、`gpu-2`、U2 各是什么身份？两节点都有 `gpu-0`，怎样区分？若 v1 Claim YAML 把 `deviceClassName` 直接放在 request 根部，应怎样修正？
10. 只改变材料 D 的完成记录：allocation/reservedFor 仍正确，Prepare 返回“写驱动检查点 permission denied”，应用入口没有启动。已完成哪步、应先修什么、如何确认修复后整条链成立？若 Prepare 成功但 CRI 丢失 CDI 名称，位置有何变化？
11. 将材料 D 的同一个 Claim 显式交给同 Pod 两个容器使用，会分到两张卡吗？改为两个 Pod 各从同一模板生成独立 Claim，又是什么语义？最后一个消费 Pod 完成后，手工 Claim 对象仍存在是否表示它会一直占用 U2？又能否只凭一次 Unprepare 成功就确认 API 分配已释放？
12. 两个容器分别通过传统插件与 DRA 请求“同一批物理卡”，各自账本都显示有空闲；CDI 名称还不同。为什么这不证明能同时独占？最后给出 Device Plugin、DRA、CDI 的一句职责说明，并指出 K8s DRA GA 对本章 NVIDIA v25.8.0 GPU 功能支持状态能推出什么。

## 参考分析

### 1. 注册入口与设备上报分开

插件先在自己的 Unix socket 提供 Device Plugin gRPC 服务，再向 kubelet 的 `/var/lib/kubelet/device-plugins/kubelet.sock` 注册，提交插件 socket 名、Device Plugin API 版本 `v1beta1`、资源名 `nvidia.com/gpu`。kubelet 调用插件的 ListAndWatch，插件持续返回设备集合和健康状态；kubelet 将聚合数量更新到 Node。注册成功本身还没有证明清单正确或容器可计算。

### 2. 本章整卡请求为 1

只写 limit 1，缺省 request 取 1。三个变式都不能作为这里合法的整卡 GPU 请求：0.5 不是整数单位；request 1 缺少相应 limit；request 与 limit 不相等。CPU 可用小数和 request/limit 不同的行为不能套到本章扩展资源上；主机 memory 也不表示显存容量。

### 3. 每节点分别计算

gpu-a 为 `4−2=2`，gpu-b 为 `2−0=2`。3 大于两者各自预算，所以一个 Pod 都放不下，集群合计剩余 4 无法让这个 Pod 跨节点拿卡。改为 2 时两节点都满足本题全部条件；这只能证明它们都可行，不能预测调度器必选哪一个。

### 4. 健康上限仍为 4

gpu-a 为 Capacity 4、Allocatable 4、总请求 `2+1=3`、预算 `4−3=1`。利用率 0% 不释放 old/worker 的请求，四项均不变。释放取决于相应生命周期清理，不由当前计算忙闲自动触发。

### 5. 一张卡跨过多个命名边界

`request 1 → gpu-a → U2完整UUID → nvidia.com/gpu=U2完整UUID → /dev/nvidia2 → cuda:0（UUID U2）`。scheduler 绑定节点；Device Manager 决定本轮具体 ID；插件通过 Allocate 返回 CDI 接入信息；kubelet/CRI 传递，运行时消费描述并创建；CUDA 在进程内枚举唯一可见设备为 ordinal 0。minor 2 是当前主机映射，未被 CUDA 改名。探针仅验证给定计算的同步与结果，没有进行多卡/多机 NCCL 测试。

### 6. 两类必要条件必须相交

第一变式：gpu-a 型号匹配但无设备资源，gpu-b 有资源却型号不符，没有节点同时满足两个条件。应先查 gpu-a 的插件初始化、注册和清单。第二变式：gpu-a 数量正常却不满足标签，仍不能通过该筛选；应恢复真实特征的发布或纠正请求中的标签值。两种缺口都不能靠另一类字段冒充。

### 7. 标量相同，设备集合不同

U3 变坏：Capacity 4、Allocatable 3、预算 `3−2=1`，健康未分配 `{U2}`。U1 变坏：前三个标量相同，健康未分配却为 `{U2,U3}`；已分配 U1 仍关联原容器，标量预算没有编码这个交集。Device Plugin 不自动迁移 CUDA 上下文或替换为 U2；需要把受影响 Pod 和失败设备关联，再由恢复流程处理。

### 8. 逐设备筛选，再排除已有分配

`30×1024=30720 MiB`。U0—U3 均通过 40536 ≥ 30720，V0/V1 均未通过 23034 < 30720。再排除已分配 U0/U1，候选是 gpu-a 的 U2/U3；count 1 有两种可选，材料另给定选 U2。count 2 可选二者，count 3 不满足。请求只筛选整卡，未切出 30 GiB；不能把容量相加来让一张小卡达标。

### 9. 名字在各自作用域内解析

`accel` 是 Pod 内 Claim 引用名，`one-30g` 是 namespace 中的 Claim 对象名，`card` 是 Claim 内请求名，`gpu-2` 是 pool 内设备名，U2 是其物理 GPU UUID。区分同名设备使用 `(driver,pool,device)`；再由 Slice 的 uuid 对应物理身份。v1 请求应把 `deviceClassName`、`allocationMode`、`count`、`selectors` 放进 `requests[].exactly`，不能直接套旧版本扁平请求。

### 10. 已分配不等于已准备

已完成调度与 API 分配，当前失败在 DRA 节点准备。先检查本轮插件写入检查点目录的挂载、权限和运行身份；修复后确认同一 Claim UID 的 Prepare 成功及返回设备/CDI 名称，再核对 CRI 输入、运行时实际消费、容器 UUID、同步和结果。若 Prepare 已成功而 CRI 丢名称，缺口后移到选择传递；重做容量筛选不会修复这段路径。

### 11. 引用同一分配与生成独立分配不同

同 Pod 两容器明确使用同一 Claim，使用的是 U2 这一次分配，不会自动新增一张；共享引用本身不提供隔离保证。两个 Pod 各生成独立 Claim，是两份独立需求，分配者要分别找到未被其他独立 Claim 占用的设备。本题 count 1 时可分别用 U2/U3，但模板不会保证特定编号。

手工 Claim 对象仍存在，不表示它会永久保留 U2：本章延迟分配路径的控制器移除最后一个有效消费者后会清空 allocation，未来消费可重新选择设备。一次 Unprepare 成功单独证明节点准备已撤销，不能代替读取 API 中的 allocation/reservedFor 及对应清理状态。模板产生的 Claim 归消费 Pod 所有，Pod 完成或删除会推进其回收；对象寿命、API 分配与节点准备要分别核对。

### 12. 两套名字不能协调两套账本

两个独立分配者如果都发布同一卡，彼此未必知道对方已分配。CDI 别名和不同 kind 不增加物理容量，也不提供所有权锁；应划分互斥设备/节点管理范围或采用明确受支持的协同方案。本章采用互斥场景。

Device Plugin 将厂商设备接入 kubelet 的上报与节点内接入流程；DRA 将逐设备属性、需求和分配纳入 API 与调度，并由节点插件完成准备；CDI 将已选名称展开为容器创建修改。Kubernetes DRA 核心 GA 说明核心 API/机制成熟度，不能替代所选 NVIDIA tag 的功能支持声明；本章 v25.8.0 GPU 路径仍按其 README 的未正式支持状态用于教学。
