# 从状态材料定位未完成的环节

## 先确定 Pod 到了哪个责任边界

`Pending` 是 Pod 的宽泛阶段，既可能尚未选定节点，也可能已经绑定、正在拉镜像或准备设备。排查从 `spec.nodeName`、`PodScheduled` 条件与当前事件开始，再关联节点、容器名、Pod UID 和时间。事件可能保留旧失败，只有把它与同一轮启动记录对齐，才知道哪个环节仍未完成。

下面各组为**独立自拟教学材料**，不累计前组变更。命令用于说明取证目的，输出已给出，无需实机。表中未写 API 路径的字段是人工归纳，不冒充 Kubernetes 固定日志字段。

## A：数量够，节点筛选仍然失败

场景 P，全健康。gpu-a 已请求 2、Allocatable 4；gpu-b 已请求 0、Allocatable 2。新 Pod 要 1 张，但它的 `nodeSelector` 要求 `nvidia.com/gpu.product: A100-80GB`，两节点实际标签分别是导读中的 A100-SXM4-40GB、NVIDIA-L4。

```text
# kubectl get pod want-80g -n lesson-dp -o yaml：相关字段自拟删节
spec.nodeName: unset
status.phase: Pending
status.conditions[PodScheduled]: False

# kubectl describe pod ...：事件含义的教学归纳
FailedScheduling: both nodes fail required node selector
```

可确定失败发生在节点选择：两节点的必要标签条件均不成立。现有 GPU 数量有空间，但它们不属于请求指定的节点集合；此时不会通过修改 CDI 描述来扩大集合。应核对需求到底是 80GB 设备，还是写错了已交付型号；需求确为 80GB 时，需要相应资源池，不能为了让 Pod 启动而把 40GB 节点重标成 80GB。

若同一选择器已经匹配 gpu-a，却出现 `Insufficient nvidia.com/gpu`，下一份证据应是同一调度窗口的 Allocatable、已请求量与其他消费者，不能用标签中的 `gpu.count` 代替剩余预算。

## B：已经分配 U2，运行时找不到名称

场景 P，Pod 已绑定 gpu-a；插件采用 `cdi-cri`，Allocate 和 PodResources 都对应 U2。以下是**自拟配对摘要**：

```text
PodScheduled=True; spec.nodeName=gpu-a
Allocate(request=U2) -> success, cdi_devices=[U2 对应完整 CDI 名称]
CRI CreateContainer carries same CDI name
runtime: cannot resolve that CDI device name
runtime CDI inventory: no matching kind/name
entrypoint_started=no
```

已有材料确认节点选择和节点内分配已发生，缺口在本次运行时消费的 CDI 描述。应检查实际搜索目录、描述是否被加载、名字是否一致及描述生成依据；匹配后还需核对源文件/Hook、重新创建和计算结果。本组明确缺少匹配项，足以给出这一定位；只有一句“cannot resolve”而没有实际 inventory 时，还需补查版本解析错误与搜索路径。

不能把 `nvidia.com/gpu: 1` 改成 UUID，也不能改 CUDA ordinal 修复入口启动前的描述匹配。已存在的资源分配记录仍应按 Pod 生命周期处理；直接删除节点的设备检查点会破坏其他容器的所有权对应。

## C：旧容器能算，新容器无法完成 Allocate

场景 P，old/worker 持续在 U0/U1 计算，插件进程随后退出。新 Pod 在状态传播窗口内已经绑定 gpu-a，现给定它需要新的 Allocate，且该 RPC 连接失败：

```text
# 自拟同一节点时间线
10:00:00 old/worker: U0/U1, sync=ok, verify=PASS
10:00:05 plugin process exits; plugin socket unavailable
10:00:06 new Pod already bound to gpu-a
10:00:07 kubelet Allocate for new container: RPC connection unavailable
10:00:08 old/worker: U0/U1, sync=ok, verify=PASS
```

这里有两项明确结论：旧容器本轮交付仍有效；新容器缺少可完成 Allocate 的服务。二者不矛盾，因为插件不在每次 CUDA Kernel 调用的数据路径上。恢复应先让插件初始化、建立 socket、注册并重新上报，再观察新一轮 Allocate 和创建；旧容器是否继续使用由其健康与生命周期决定。

不能从这五行断言“任意新容器一定都失败”或“Node API 会瞬间归零”。不同缓存状态与更新窗口需要实际证据；本组已明确限定需要新 RPC 的容器，才有确定定位。

## D：健康资源减少，失败成员没有自动换卡

场景 P，U0/U1 已给 old/worker，U2/U3 未分配。现在 U1 被插件标记为 Unhealthy，Node 已更新为 Capacity 4、Allocatable 3；PodResources 仍列 U0/U1，应用报告 U1 上同步失败，Pod API 对象尚未被重建。

这组证据支持：健康上报已影响新调度的数量上限，现有容器仍持有原分配，应用确实在原卡出现失败。它不支持“kubelet 应已把容器无缝切到 U2”，也不支持“删掉 Unhealthy 标签即可恢复”。Device Plugin 健康不是 Node label，重新标注标签不会修复设备或重写分配。

本章需要的下一步是将失败设备与受影响 Pod 对齐，停止把故障设备交给新分配，并按上层控制器/应用恢复策略处理失败成员。Xid 根因、节点维护与恢复验证由第 18—19 章继续展开；不将隔离动作等同于已经修好硬件。

Kubernetes 1.34 的本章基线没有启用可选 `ResourceHealthStatus`；因此使用 PodResources 与插件记录完成关联。不要把较新版本默认可见的容器资源健康字段当成本章每份 Pod status 的必填输出。

## E：DRA 的分配、准备与创建逐级核对

场景 D，给出三个独立快照，均请求一张 `lesson-gpu`。已分配快照中的结果都是 gpu-a/gpu-2：

| 快照 | 完整给定材料 | 可确定的停止位置与下一步 |
| --- | --- | --- |
| E1 | Claim 已创建但 `status.allocation` 空；消费 Pod 尚未提交 | 本章消费时分配尚未触发；提交正确引用它的 Pod，再观察调度。不能记为驱动故障 |
| E2 | 消费 Pod 已绑定；allocation、reservedFor 正确；本轮 Prepare 返回写入驱动检查点时 permission denied；入口未启动 | 分配已有结果，节点准备失败。修复检查点目录/挂载和插件运行身份条件，再看同一 Claim 的 Prepare 及后续创建 |
| E3 | Prepare 成功返回 CDI 名称；CRI 未传递该名称；运行时本轮创建未执行对应修改；探针无 GPU | 准备已完成，缺口在向运行时传递选择及创建。核对 kubelet/CRI 请求与版本路径，再复核设备和计算 |

E2 的错误是**按 Prepare 阶段构造的教学归纳**，不是 NVIDIA 的固定错误原文。该 tag 的 Prepare 会写入节点检查点；整卡默认配置未必生成 Claim 专属 CDI 文件，不能擅自把所有 Prepare 故障都写成“生成 CDI 失败”。相关操作见 [v25.8.0 device_state.go 的 Prepare](https://github.com/NVIDIA/k8s-dra-driver/blob/v25.8.0/cmd/gpu-kubelet-plugin/device_state.go)。给定明确失败操作，才能把“权限”落到节点准备这一环；没有理由从它反推 Claim 的显存门槛写错。

DRA 节点插件通过注册机制接入 kubelet，但它的准备 API 与传统 Device Plugin 的 `Allocate` 不是同一个服务。不要只看到一个“插件 Running”就认为两条路径都可用；也不要把传统 socket 目录的注册记录作为 DRA Prepare 已成功的证据。

## 将检查缩短到最后一个已证实阶段

| 已证实的阶段 | 接下来最有用的材料 | 当前不该替代它的证据 |
| --- | --- | --- |
| 驱动可查询 | 插件初始化、注册、设备上报，或 DRA Slice 发布 | PCI 厂商标签 |
| 传统 Node 数量存在 | Pod 有效请求、节点筛选与已请求量 | GPU 利用率 |
| Pod 已绑定 | Device Manager/Allocate，或 Claim allocation 与 Prepare | `Pending` 这一个单词 |
| 设备分配/准备有结果 | 实际 CRI 输入、CDI inventory、创建记录 | 配置文件存在但未确认生效 |
| 创建与枚举完成 | 同步和结果探针，必要时后续通信测试 | 单独 `nvidia-smi` 成功 |
