# 用精度、带宽和运算量估算性能上界

逐元素更新和矩阵乘法都能让 GPU 连续执行 Kernel，前者却往往忙于搬数据，后者有机会让矩阵计算单元持续工作。要比较两者，先确定这次运算能用哪条计算路径，再算每从显存搬一个字节能做多少运算。

## 先选对规格表里的峰值

一项运算可以有四个精度口径。张量以什么格式存储，输入以什么精度参与乘法，中间和以什么精度累加，结果又以什么格式写回。FP16 与 BF16 每元素都是 2 B。BF16 的指数位更多、有效数位更少，表示范围较宽，单位量级上能表示的数较稀疏。FP16 输入的矩阵乘法可以用 FP32 累加并把输出写为 FP32。反过来，用 cuBLAS 的 `CUBLAS_COMPUTE_32F_FAST_TF32` 时，输入和输出矩阵仍能按 FP32 存储，库可以在 Tensor Core 上采用 TF32 运算。因此，计算模式变化后，先分别核对数值误差、算力路径及读写字节数。 [NVIDIA H100 架构白皮书 V1.04 · Tensor Core 数据格式](https://resources.nvidia.com/en-us-hopper-architecture) · [cuBLAS 13.2 · Compute Types 与 GemmEx](https://docs.nvidia.com/cuda/archive/13.2.1/cublas/index.html)

以下是单张 **H100 SXM 80 GB** 的规格摘录。带宽为 HBM 峰值，计算峰值随指令路径和精度而变。白皮书表 3 将 FP16 Tensor Core 的稠密及稀疏有效吞吐并排给出，并注明参考 Boost 频率。数据表中的带星号数值按稀疏口径。以 2:4 结构化稀疏为例，相关矩阵操作数按规定方向分组，每四个连续值至少两个为零。数据满足约束并且实际执行稀疏 Tensor Core 路径时，才使用这一峰值。 [NVIDIA H100 数据表](https://resources.nvidia.com/en-us-gpu/h100-datasheet-24306) · [NVIDIA H100 架构白皮书 V1.04 · 表 3](https://resources.nvidia.com/en-us-hopper-architecture) · [NVIDIA · Structured Sparsity](https://developer.nvidia.com/blog/structured-sparsity-in-the-nvidia-ampere-architecture-and-applications-in-search-engines/)

| 规格项 | 峰值或容量 | 口径 |
| --- | ---: | --- |
| 显存容量 | 80 GB | 单卡，实际可分配量还要查设备状态 |
| 显存带宽 | 3.35 TB/s | GPU 内部 HBM |
| FP32 | 67 TFLOP/s | 常规 FP32 路径，数据表舍入值 |
| TF32 Tensor Core | 989 TFLOP/s | 结构化稀疏 |

## 同时满足计算和搬运两项约束

对一个 Kernel，设它完成 `F` 次浮点运算，在选定的存储层传输 `D` 字节。一次乘加按乘、加两次运算计 2 FLOP，`1 GB = 10⁹ B`，`1 TB = 10¹² B`。算术强度 `I = F/D`，单位是 FLOP/B。设匹配的计算峰值为 `P` FLOP/s，所选层的带宽上界为 `B` B/s。即使计算和搬运完全重叠，计算也至少耗时 `F/P`，搬运也至少耗时 `D/B`，所以整体用时至少是两者较大值。将 `F` 除以这个时间下界，就得到 Roofline 的吞吐上界。 [Nsight Compute · Roofline Charts](https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html#roofline-charts)

```text
时间下界 = max(F/P, D/B)
吞吐上界 = min(P, B × I)
两条上界相交时 I = P/B
```

算术强度低于分界点时，理想上界由带宽给出。高于分界点时，理想上界由计算峰值给出。这里选 HBM，`D` 就要用实际经过 HBM 的读写量或注明假设的估算。程序按元素数算出的逻辑读写可用于计算有效带宽，物理流量还会受到缓存、访存合并与重复读写影响。若数据由主机拷入 GPU，主机链路的字节和时长要另计。 [CUDA Best Practices Guide 13.2 · Bandwidth / Coalesced Access](https://docs.nvidia.com/cuda/archive/13.2.1/cuda-c-best-practices-guide/index.html#bandwidth)

## 复算两个 Kernel

两个例子都假设输入已经在设备端、结果留在设备上，忽略启动开销。数字是**教学估算**。先按规则数出运算与字节，再分别除以匹配峰值。

| 算例 | 工作与流量假设 | F | D | I | F/P | D/B |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| 逐元素更新 `y[i] ← a × x[i] + y[i]` | 10⁸ 个 FP32 元素，标量已就绪。每元素读 x、读旧 y、写新 y，共 12 B 到或来自 HBM | 0.2 GFLOP | 1.2 GB | 约 0.167 FLOP/B | 约 0.003 ms | 约 0.358 ms |
| 稠密矩阵乘法 `C = AB` | 方阵边长 8,192。FP16 输入、FP32 累加和输出。假设理想复用，A、B 各从 HBM 读一次，C 写一次，旧 C 不参与 | 约 1.100 TFLOP | 约 0.537 GB | 2,048 FLOP/B | 约 1.11 ms | 约 0.160 ms |

逐元素更新用 `2 × 10⁸` 算 FLOP，用 `12 × 10⁸` 算字节。即使把算术做得更快，每个元素仍有三项读写。按这组流量和 3.35 TB/s 带宽，Kernel 的吞吐上界约为 0.56 TFLOP/s，远低于这条 FP32 路径的计算峰值。

令矩阵边长为 `N`。每个输出元素做长度为 `N` 的点积，按 `2N` FLOP 计，合计 `2N³`。A、B 各 `2N²` 字节，C 为 `4N²` 字节，合计 `8N²`。使用 989.4 TFLOP/s 的稠密 FP16 Tensor Core 峰值，计算下界在此例中较高。若实际 HBM 流量因重复读写增加到约 `3.35 TB/s × 1.11 ms ≈ 3.72 GB`，两项时间下界才相当。要把「计算是候选限制」变成诊断，还要观察实际流量、执行路径和吞吐离上界有多远。

当实际点远低于两条上界时，可能是访存延迟导致就绪 Warp 不足，也可能是并行规模、指令路径或频率变化。先核对所用上界和计数口径，再补测最能区分原因的证据。作业如果还花时间等待输入、拷贝或同步，需要用端到端时间线判断 Kernel 加速能影响多少总用时。 [Nsight Compute · Roofline Analysis](https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html#roofline-charts)
