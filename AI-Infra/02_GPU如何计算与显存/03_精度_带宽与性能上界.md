# 精度、带宽与性能上界

## 先把存储格式与计算方式分开

一个数用多少字节存储，会影响容量与搬运量；硬件以什么方式计算它，会影响可使用的执行单元、运算吞吐和数值误差。两者相关，但并不是同一个问题。

浮点格式用符号、指数和有效数字表示数值。指数范围影响能表示多大或多小的数，有效数字位数影响相邻可表示数之间的间隔。位数减少可能节省数据空间，也可能产生更明显的舍入、上溢或下溢，需要由应用确认可接受性。

| 格式或计算模式 | 数据与计算的主要区别 | 资源推导时注意什么 |
| --- | --- | --- |
| FP32 | 每元素通常存 4 B | 比较时说明使用普通 FP32 还是其他允许的矩阵计算模式 |
| FP16 | 每元素存 2 B，范围与有效数字不同于 FP32 | 输入变小不等于累加值、状态和工作区全部变小 |
| BF16 | 每元素存 2 B；指数位数与 FP32 相同，有效数字较少 | 和 FP16 容量相同，数值性质与执行支持需要分别判断 |
| TF32 | 某些 Tensor Core 支持的计算模式，使用较少的有效数字参与矩阵乘法、以 FP32 累加 | 不能把它当成应用把 FP32 数组改存为 19 位、显存随之缩小 |
| INT8、FP8 等 | 整数或更低位浮点格式，支持范围依代际与指令而异 | 还要计入缩放因子、转换、中间状态及数值条件 |

TF32 与 BF16 的具体实例可核对 [CUDA 12.8.1 Ampere Tuning Guide：Improved Tensor Core Operations](https://docs.nvidia.com/cuda/archive/12.8.1/ampere-tuning-guide/index.html#improved-tensor-core-operations)。该段描述 Ampere 的能力，不能作为所有 GPU 的格式支持清单。

**混合精度**意味着一次计算可以使用不同的输入、乘法、累加和状态格式。例如，低精度输入配合 FP32 累加，需要分别说明输入存储的字节数与累加的计算方式。基础设施读者需要据此读资源和性能材料，不必在本章设计数值算法。

## 规格表中的“算力”必须先对齐口径

**FLOP** 是浮点运算次数，**FLOP/s** 是单位时间的运算次数。一次融合乘加 `a × b + c` 通常按一次乘法、一次加法计为 2 FLOP。用一个 `M × K` 矩阵乘一个 `K × N` 矩阵，得到 `M × N` 个输出；每个输出累加 K 个乘积，按上述口径共约 `2MNK` FLOP。具体问题若含额外操作，也要单独计入。

读到一个很大的 TFLOP/s 数字，至少先确认：

| 规格条件 | 为什么会改变比较结果 |
| --- | --- |
| 输入格式、乘法与累加精度 | FP32、FP16、TF32 等对应的执行吞吐不同 |
| CUDA Core 或 Tensor Core 路径 | 任意标量指令不能使用矩阵单元的峰值作分母 |
| 稠密或特定结构化稀疏 | 稀疏峰值依赖指定的数据结构与受支持的指令路径 |
| GPU 精确变体、时钟与功率条件 | 同一产品系列也可能有不同资源与运行条件 |
| 单卡或多卡合计、峰值或实测 | 多卡相加的装机峰值不是一项作业获得的吞吐 |

“结构化稀疏”指满足硬件要求的特定非零分布。它不同于“数组中恰好有很多零”；没有相应的数据格式和实现，就不能直接使用稀疏峰值估计速度。Ampere 的实例见 [NVIDIA Ampere Architecture In-Depth：Third-Generation Tensor Cores](https://developer.nvidia.com/blog/nvidia-ampere-architecture-in-depth/)。

例如，该官方文章 2020 年发布的 A100 规格表 1 按 Boost Clock 列出：普通 FP32 峰值 19.5 TFLOP/s，TF32 Tensor Core 稠密峰值 156 TFLOP/s，启用规定稀疏路径时的等效峰值 312 TFLOP/s。同一张表中出现的三个数描述不同条件；不能把普通 FP32 Kernel 的吞吐除以 312，再据此评价效率。这些是该发布资料的产品实例，不是 GPU-T 的参数，也不代表其他 A100 变体或后续代际。

即使口径相同，Kernel 也会经历数据依赖、访存、边界处理、分支和尾部工作，因此峰值只是特定路径的上界。接下来只分析 GPU-T 已指定的 FP32 路径，不代入其他精度或 Tensor Core 的峰值。

## 把运算量和显存流量换成两个时间

先取一个已经具备足够并行工作、数据位于 GPU 本地显存的 Kernel。定义：

| 符号 | 含义与口径 |
| --- | --- |
| `F` | 本次 Kernel 的浮点运算次数，乘加按 2 FLOP |
| `Q` | 本次 Kernel 在 HBM 边界实际产生的读取与写入字节数之和 |
| `P` | 与本次运算路径一致的计算上界，本章为 `60 × 10^12 FLOP/s` |
| `B` | 与 Q 口径一致的 HBM 读写合计流量上界，本章为 `1.5 × 10^12 B/s` |

Q 不是显存占用量，也不是源代码写出的数组大小之和。缓存命中减少到达 HBM 的流量，重复读取、低效事务或寄存器溢出可能增加流量。如果只是根据算法估计 Q，应说明复用和缓存假设，不能把估计值写成硬件计数器实测值。

两个资源分别给出理想耗时下界：

```text
计算下界 t_compute = F / P
搬运下界 t_memory  = Q / B
Kernel 耗时 t >= max(F / P, Q / B)
```

最后一式只给下界。许多线程之间的运算与搬运可以重叠，所以不能机械把两个下界相加；依赖、延迟、发射限制和启动开销又可能让实际时间比这个最大值大得多。这个模型先回答“哪种资源更早构成上界”，不能代替完整测量。

定义 **算术强度（Arithmetic Intensity）** `I = F / Q`，单位为 FLOP/B。把时间下界改写为性能上界，得到简化的 **Roofline（屋顶线）模型**：

```text
达到的吞吐 F / t <= min(P, B × I)
转折点 I* = P / B = 60 × 10^12 / (1.5 × 10^12) = 40 FLOP/B
```

I 低于 40 时，HBM 带宽先限制这个模型中的上界；I 高于 40 时，指定运算路径的计算上界较低。基本推导可对照 [NVIDIA GPU Performance Background：Understanding Performance](https://docs.nvidia.com/deeplearning/performance/dl-performance-gpu-background/index.html#understand-perf)。这里的 P、B、案例与计算均为本章自拟。

## 同一张卡上的两种 Kernel

给 GPU-T 两项工作，Q 均已按题设确定为 HBM 的实际读写合计流量，均使用同一 FP32 运算路径：

| 项目 | Kernel A | Kernel B |
| --- | --- | --- |
| F | 12 GFLOP | 600 GFLOP |
| Q | 3 GB | 3 GB |
| I | `12 / 3 = 4 FLOP/B` | `600 / 3 = 200 FLOP/B` |
| F/P | 0.2 ms | 10 ms |
| Q/B | 2 ms | 2 ms |
| 理想耗时下界 | 2 ms，带宽一侧先限制 | 10 ms，计算一侧先限制 |
| 模型中的吞吐上界 | 6 TFLOP/s | 60 TFLOP/s |

再给两段**自拟性能记录**：A 用时 2.5 ms，B 用时 12 ms。A 的平均算术吞吐为 `12 GFLOP / 2.5 ms = 4.8 TFLOP/s`，只有计算峰值的 8%；但它的 HBM 平均流量为 `3 GB / 2.5 ms = 1,200 GB/s`，达到本题 B 的 80%，算术吞吐也达到带宽屋顶 6 TFLOP/s 的 80%。

因此，“只达到 8% 的计算峰值”不能单独证明 A 实现很差。按同样的 F、Q 与带宽，计算单元再多也无法突破 6 TFLOP/s 的带宽屋顶。降低 Q 或提高可用带宽，才会抬高这一约束。

B 的平均算术吞吐为 `600 GFLOP / 12 ms = 50 TFLOP/s`，达到本题计算上界的约 83.3%；HBM 平均流量为 250 GB/s。对这项工作，提高 HBM 带宽不会改变 10 ms 的计算下界。两者的“效率”要和各自的上界比较。

这些结果说明 A 的带宽约束较强、B 的计算约束较强，且实际记录靠近各自的模型上界。若 A 实际耗时变成 10 ms，则 2 ms 的下界与实际时间相差很大；仅凭低 I 不能认定它已经把 HBM 带宽用满，还需看访问延迟、并发、事务、调度与其他限制。

## 复用和访问方式怎样改变 Q

矩阵乘法可以将数据块暂存在片上存储，多次用于不同乘加，减少每次运算对应的 HBM 读取。反过来，线程分散地访问很多地址，可能让硬件搬运的字节远多于真正使用的字节。

做一个**限定事务口径的教学对比**：一个 Warp 的 32 个线程各需一个 4 B 元素，有效数据共 128 B。假设读取按 32 B 扇区计数、所有请求都未命中缓存、忽略额外开销：

| 布局 | 假定触及的 32 B 扇区数 | 本次读取流量 | 有效数据比例 |
| --- | --- | --- | --- |
| 连续且对齐的 32 个元素 | 4 | 128 B | 100% |
| 每线程位于不同扇区 | 32 | 1,024 B | 12.5% |

**合并访存（Coalescing）**指硬件将同一 Warp 的访问组织为尽可能少的事务。这里第二种布局即使在事务层搬得很忙，也只利用了其中一小部分数据。32 B 扇区是本例的条件；缓存、指令和架构会影响真实事务与 HBM 流量，不能把表中倍数直接当成整个 Kernel 的减速倍数。相关访问模型见 [CUDA 12.8.1 Best Practices：Coalesced Access to Global Memory](https://docs.nvidia.com/cuda/archive/12.8.1/cuda-c-best-practices-guide/index.html#coalesced-access-to-global-memory)。

复用还会改变算术强度。若 A 的 F 保持 12 GFLOP，Q 从 3 GB 降至 1.5 GB，则 I 变成 8 FLOP/B，搬运下界变成 1 ms，模型吞吐上界变成 12 TFLOP/s；它仍位于 40 FLOP/B 转折点的带宽一侧。能否达到这个新上界，还要看新增的片上存储需求是否降低并发等条件。

## 从单个 Kernel 的上界走向整轮作业

在本章中，先用三个问题组织性能判断：

1. **计算受限**：已经有可执行工作时，指定算术路径的处理能力先限制进度。
2. **访存受限**：已经运行的 Kernel 受数据访问约束；既可能是带宽，也可能是访问延迟、并发不足或事务效率，Roofline 只覆盖其中的带宽上界。
3. **数据或依赖等待**：下一段有用计算还不能启动，例如输入尚未准备好，或仍在等待其他阶段完成。

这不是互斥、完备的硬件分类。一个作业可以先等输入，随后运行带宽受限的 Kernel，再运行计算受限的 Kernel；小 Kernel 还可能受提交与启动延迟影响。通信等待也可能由持续运行的 Kernel 承担，于是“GPU 有 Kernel 活动”仍不能说明有用计算一直推进。
