# 从显存、利用率和作业记录判断瓶颈

两份作业都显示 GPU 利用率接近 100%，一份可能在尽力把数据从 HBM 送到执行单元，另一份可能在持续做矩阵乘法。还有一种作业，Kernel 本身运行正常，却常常等不到下一批输入。判断这三种情况，先把采样值放回同一批次的时间线。

## 每个数描述什么

下面以 Linux 上一张非 MIG 的独立 GPU 为例。先用 `nvidia-smi --help-query-gpu` 核对本机支持的字段，再按设备 UUID 采样。`-l 1` 让命令约每秒查询一次。实际设备的内部利用率采样期由产品决定，NVIDIA 文档给出的范围是约 1/6 秒到 1 秒。查询的时间戳是取得这一行数据的时刻，对齐应用事件时要区分查询时间和指标覆盖的窗口。设备字段如果返回 `N/A`，把它记为缺测。 [NVIDIA System Management Interface · Selective Query Options / Utilization](https://docs.nvidia.com/deploy/nvidia-smi/index.html)

```bash
nvidia-smi --query-gpu=timestamp,uuid,memory.total,memory.used,utilization.gpu,utilization.memory --format=csv -l 1
```

| 观测量 | 能回答的问题 |
| --- | --- |
| `memory.total` 和 `memory.used`（MiB） | 这张设备有多少可报告的显存、当前已用多少。判断某个进程的活跃张量还要看进程或框架记录 |
| `utilization.gpu`（%） | 采样期内有一个或多个 Kernel 执行的时间占比 |
| `utilization.memory`（%） | 采样期内全局设备内存发生读或写的时间占比。要算 HBM 带宽，另取 DRAM 字节数和耗时 |
| Warp 驻留率（%） | 相对于 SM 的最大 Warp 数，当前或统计窗口内驻留了多少 Warp。就绪和发射情况另查调度指标 |
| Kernel 有效计算吞吐相对峰值（%） | 先用完成的 FLOP 除以 Kernel 时长，再除以该精度、指令路径及稀疏口径对应的计算峰值 |

显存用量以字节计，其余百分比的分母分别是采样时间、Warp 上限或计算峰值。一次设备级采样可能包含多个进程的工作。要归因到某个作业，先确认设备 UUID、进程、批次范围与时间窗，结合应用标记确认测量区间。同样是 100% 的设备忙碌时间，Kernel 可以只有部分 SM 在工作，也可以让许多 Warp 等待访存。 [NVIDIA System Management Interface · Utilization](https://docs.nvidia.com/deploy/nvidia-smi/index.html) · [Nsight Compute · Metrics Structure / Occupancy](https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html)

## 先找出关键路径，再选择计数器

用 Nsight Systems 把 CPU CUDA API 调用与 GPU 上的 Stream 活动放到同一条时间轴。记录 CPU 提交与同步调用的开始和结束，记录 H2D 或 D2H 的方向、大小和区间，以及 Kernel 名称、所在 Stream 和执行区间。应用可以按批次加 NVTX 标记或记录 `batch_id`、`input_ready`、`step_end`。`input_ready` 表示主机输入已经可用，`step_end` 采用与作业承诺一致的完成时点，例如结果可被下一阶段读取时。用批次和时钟关联两侧观测。 [Nsight Systems · CUDA Trace / NVTX Trace](https://docs.nvidia.com/nsight-systems/UserGuide/index.html)

沿结果的依赖往回找。若某次 H2D 已和上一批计算重叠，它对完成时间的影响取决于下一批是否还得等它。CPU 线程花很久等同步时，也要查它在等哪项设备操作，避免把同一段时间同时记作 GPU 计算和额外的主机耗时。

| 时间线形态 | 下一步怎么区分 |
| --- | --- |
| 耗时主要落在执行中的 Kernel | 在同一输入、精度和设备条件下，用 Nsight Compute 检查耗时最长的 Kernel。对齐相应的 Roofline、DRAM 读写字节数与实际计算路径 |
| Kernel 之间有空档，拷贝也还未开始 | 找对应批次的输入就绪与 CPU 提交。输入尚未就绪时，检查准备阶段。输入已就绪却未提交时，检查主机调度、提交和同步依赖 |
| Kernel 在等待一段较长的 H2D | 核对 H2D 的字节数、时长和重叠条件。用拷贝字节和时间评估主机到设备传输，GPU 内部的 HBM 带宽用于另一个边界 |

对 Kernel 内部，按所观察的 DRAM 字节数除以 Kernel 耗时得到该区间的 HBM 吞吐。若它接近同条件下可达到的带宽、匹配计算路径仍有明显余量，优先验证带宽受限。若计算吞吐接近匹配峰值、DRAM 仍有余量，计算路径更可能限制性能。两个都远离上界时，查就绪 Warp、调度停顿、访存延迟、并行规模和频率。Nsight Compute 可从 Device Memory 表取 DRAM 流量，对 Tensor Core Kernel 选 Tensor Roofline，并核对 profiler 的重放及缓存设置是否改变了所观察的工作。 [Nsight Compute · Roofline Charts / Memory Tables / Replay](https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html)

## 判读三份作业记录

以下均为**教学数据**。A、B 以 H100 SXM 80 GB 的规格为比较基准，假设各自测量窗口内 Kernel 几乎持续执行，设备没有其他作业。表中的时长、DRAM 流量和计算路径均为假定值。计算和带宽都取单次 Kernel 的口径。H100 的参考值是常规 FP32 67 TFLOP/s、稠密 FP16 Tensor Core 且 FP32 累加 989.4 TFLOP/s、HBM 3.35 TB/s。 [NVIDIA H100 数据表](https://resources.nvidia.com/en-us-gpu/h100-datasheet-24306) · [NVIDIA H100 架构白皮书 V1.04 · 表 3](https://resources.nvidia.com/en-us-hopper-architecture)

| 材料 | 单次 Kernel | 计算与流量 | 按时长折算 |
| --- | --- | --- | --- |
| A | 10⁸ 个 FP32 元素的逐元素更新，0.40 ms | 读两个值、写一个值，合计 1.2 GB。每元素 2 FLOP，合计 0.2 GFLOP | 3.0 TB/s，0.50 TFLOP/s |
| B | 边长 8,192 的稠密方阵乘法，1.25 ms。已确认走 FP16 Tensor Core，FP32 累加 | DRAM 流量约 0.537 GB。按一次乘加计 2 FLOP，合计约 1.100 TFLOP | 约 0.43 TB/s，约 880 TFLOP/s |

- **A 先验证 HBM 带宽。** 3.0 TB/s 约为规格带宽的九成，0.50 TFLOP/s 离常规 FP32 峰值很远。下一步可在相同设备条件下核对可持续带宽，或比较减少 DRAM 字节后 Kernel 耗时是否随之下降。
- **B 先验证计算吞吐。** 约 880 TFLOP/s 接近稠密 FP16 Tensor Core 参考峰值，DRAM 吞吐相对有余量。下一步看实际时钟、Tensor 管线指标和指令路径，确认该窗口里的参考峰值是否适用。

**C 观察数据供给。** 假设单批串行推进，下面各时点是从同一测量起点算起的教学毫秒数。对照只提前备好同样的主机输入，固定批量、dtype、拷贝路径和 Kernel。测量结束定义为 GPU 结果可用。

| 记录 | `batch_id` | 主机 `input_ready` | H2D | Kernel | `step_end` |
| --- | --- | ---: | --- | --- | ---: |
| 基线 | 7 | 12 ms | 12–14 ms | 14–20 ms | 20 ms |
| 提前备好输入 | 7 | 测量开始时已就绪 | 0–2 ms | 2–8 ms | 8 ms |

两条记录里，H2D 和 Kernel 各耗时 2 ms 与 6 ms，测量窗口缩短的 12 ms 来自移到窗口外的输入准备。由此可判定基线的准备阶段在批次关键路径上。若要判断生产作业能否加快，再把预处理成本纳入端到端窗口，检查它能否与上一批重叠并持续供给输入。若基线尚未记录准备过程内部的时间，要补测读取、解码或预取等待，才能进一步区分来源。

实际记录应保留原始采样或 profiler 报告和采集命令，并注明采集时间、GPU 型号与切分状态、驱动、CUDA、框架与工具版本、输入形状和精度、预热、频率或功率条件及统计窗口。每次判读写清三件事。慢在哪段，哪项观测支持判断，哪项新观测能够推翻或细化它。
