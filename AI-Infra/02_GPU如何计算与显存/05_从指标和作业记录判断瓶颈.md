# 从指标和作业记录判断瓶颈

## 三类数字分别回答什么

“显存占用 80%”“GPU 利用率 99%”“达到峰值算力的 8%”可以同时成立。它们的分子、分母和时间范围不同：一个描述空间，一个描述活动时间，一个描述指定运算口径下的吞吐。

| 观察量 | 主要回答的问题 | 需要补充什么才能判断效率 |
| --- | --- | --- |
| 显存 Used/Total | 当前分配等占用了多少设备内存 | 峰值、对象生存期、分配器保留空间、其他进程 |
| `utilization.gpu` | 采样期内，有一个或多个 Kernel 执行的时间比例 | Kernel 做什么、用了多少执行资源、作业是否推进 |
| `utilization.memory` | 采样期内，全局设备内存发生读写的时间比例 | 实际读写字节数、时间、事务效率与带宽上界 |
| 平均算术吞吐 `F/t` | 指定区间完成多少浮点运算 | 运算精度、执行路径、运算计数与合适的性能上界 |
| 平均显存流量 `Q/t` | 指定区间经过 HBM 边界的字节速率 | 流量口径、缓存、有效数据与实际搬运的区别 |
| 作业吞吐或完成时间 | 每秒完成多少有效工作、多久得到结果 | 批量、输入规模、正确性条件和整条关键路径 |

`nvidia-smi` 中 GPU/Memory Utilization 的定义见[官方文档](https://docs.nvidia.com/deploy/nvidia-smi/index.html)的 “Utilization” 小节（该页面没有对应的稳定 HTML 锚点）。GPU 利用率不是“全部 SM 的平均忙碌比例”，Memory Utilization 也不是“已用显存容量比例”或“已经达到多少峰值带宽”。设备、模式和工具还可能不支持某些字段；`N/A` 表示缺少该项读数，不能按 0 处理。

例如，一个很小的 Kernel 持续占着少量 SM，也可能让很多采样窗口都有 Kernel 活动；一个主要轮询或等待通信的 Kernel 也可能保持活动。要评价计算效果，需将活动时间与有用工作、Kernel 级计数和作业进度连接起来。

## 从一段命令材料读出确定的结论

下面命令用于获取同一 GPU 的内存和活动信息。它不修改设备状态，Linux 主机上可以用同类查询取得证据；本章不要求执行。

```bash
nvidia-smi -i 0 --query-gpu=timestamp,index,memory.total,memory.used,memory.free,utilization.gpu,utilization.memory --format=csv
```

下面是**按查询字段自拟的单行 CSV 教学输出**，不是实机采集。它假定本次会话中 index 0 对应 GPU-T，4 GiB 固定占用计入 Used，且没有另列的 Reserved 容量；没有省略其他查询字段。时间只是样例时间，字段标题中的单位沿用工具形式：

```text
timestamp, index, memory.total [MiB], memory.used [MiB], memory.free [MiB], utilization.gpu [%], utilization.memory [%]
2026/11/08 10:00:00.000, 0, 81920, 65536, 16384, 22, 12
```

按字段逐步读：

1. `81,920 MiB ÷ 1,024 = 80 GiB`，与 GPU-T 的容量条件一致。
2. 已用 64 GiB、空闲 16 GiB，设备占用比例为 80%。在本章给定的这个瞬间，4 GiB 固定占用加 50 GiB 长期状态、10 GiB 当前批次，恰好是 64 GiB；12 GiB 工作区尚未申请。
3. 后续加入工作区，设备总占用按题设将到 76 GiB，即应用占用 72 GiB；不能拿当前空闲 16 GiB 全部规划给预取。
4. 22 与 12 是采样时间比例，不能由 12% 推算出 `1,500 × 12% = 180 GB/s` 的 HBM 流量。

内存快照与利用率的时间口径也不完全相同：内存字段描述查询时状态，利用率反映设备自己的近期采样窗口。按 1 秒查询一次不会把所有内部采样窗口自动改成同一个整秒，短暂的峰值和空档仍可能被掩盖。设备 index 的映射也不保证跨重启不变；维护身份映射时应同时保留 UUID 或 PCI 地址，这一点承接第 01 章。

## 再补一条整轮时间线

现在补充同一教学作业的一段**人工汇总的串行稳态记录**，各区间无重叠，完整覆盖从本轮开始到 CPU 能使用本轮结果的 100 ms。它不是上一行利用率输出的精确采样窗口。

| 阶段 | 开始—结束（ms） | 证据含义 |
| --- | --- | --- |
| CPU 等待并完成输入准备 | 0—60 | 本轮 H2D 尚无可用输入；未进一步拆分存储、解码和线程等待 |
| H2D | 60—64 | 输入开始送入设备 |
| GPU Kernel 活动合计 | 64—84 | 本轮有用计算，内部可以包含多个 Kernel |
| D2H | 84—86 | 结果返回主机 |
| CPU 后处理 | 86—100 | 结果达到本题要求的可用状态 |

这条记录支持一个明确结论：GPU Kernel 占本轮 20 ms，输入准备占 60 ms；在这些串行条件下，先把 Kernel 加速一倍，总时间是 `60 + 4 + 10 + 2 + 14 = 90 ms`，端到端只加速 `100/90 ≈ 1.11` 倍。如果把输入准备减到 20 ms，而其余不变，总时间为 60 ms，加速约 1.67 倍。

即使把这 20 ms 的 Kernel 耗时理想地降为零，总时间也还有 80 ms，端到端加速上限为 1.25 倍。这是串行阶段占比限制加速空间的一个具体实例；有重叠时应重画关键路径，不能继续机械相加。

记录还没有说明输入准备内部为什么花了 60 ms，因此不支持直接断言“存储故障”或“CPU 核数不足”。应先把这一段拆成读取、解码/预处理、排队等状态，再看相应证据。当前已经能定位主要时间段，后续取证针对的是这段时间的内部原因。

## 用什么证据连接这些层次

不需要在本章安装工具，但需要知道不同材料的用途。GPU 状态查询适合看到设备层的资源与活动概况；系统级时间线适合把 CPU 调用、设备 Kernel、复制和等待对应起来；Kernel 级分析则进一步观察指令、Warp、缓存与显存事务。

| 当前问题 | 有用材料 | 要形成的判断 |
| --- | --- | --- |
| 下一批为什么迟迟不能开始 | 输入准备区间、CPU 状态、GPU 时间线 | 没有提交工作，还是已经提交但依赖未满足 |
| Kernel 很长，是什么在限制它 | 同一 Kernel 的 F、Q、执行时长与资源分析 | 比较适当的上界，再核对驻留、就绪工作与访存行为 |
| 异步方案为什么没有重叠 | Stream 归属、Event、复制与 Kernel 时间线 | 是依赖、主机缓冲、默认流语义，还是硬件与竞争条件限制 |
| 内存占得多，是否接近失败 | 分配请求、峰值、生存期与内存池记录 | 哪些对象同时存在、分配失败发生在哪一步 |

NVIDIA 的 [Nsight Systems User Guide](https://docs.nvidia.com/nsight-systems/UserGuide/index.html) 说明系统级剖析与时间线能力；[Nsight Compute Profiling Guide](https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html#sections-and-rules) 说明 Kernel 分析中的计算、访存和调度观察项。采集可能产生额外开销或重放，比较时要保留采集范围与条件。本章使用人工汇总材料，未运行这些工具。

## 独立练习：用同一套条件继续推导

以下题目使用 GPU-T，彼此独立的变更均就近说明。可先遮住答案，用纸笔完成；所有必要数值已在题内或前文给出。

### 1. 从 Block 数推导可用并行度

某普通 Kernel 的 Grid 有 160 个 Block，每 Block 256 个线程。仍采用第一篇的每 SM 上限：64 个 Warp、8 个 Block、65,536 个寄存器、96 KiB 共享内存；每线程 128 个寄存器，每 Block 48 KiB 共享内存，忽略分配粒度和其他限制。

计算总线程数、总 Warp 数、每 SM 理论驻留 Block/Warp 数和 Occupancy。Grid 是否提供了足够 Block，让 80 个 SM 都达到这个驻留上限？如果只改为 4 个 Block，最多可同时给多少 SM 分配本次工作的 Block？

### 2. 精度变化怎样影响容量

按第二篇的应用预算 76 GiB，原对象为：长期状态 50 GiB、当前批次 10 GiB、工作区 12 GiB、预取缓冲 8 GiB，同时存活。

现在只把当前批次的数据表示改为原来一半大小，其他对象和生存期完全不变，也不保留额外转换副本。峰值是多少，能否容纳，余量多少？若所有对象保持原大小，只把预取缓冲缩小为 4 GiB，峰值又是多少？

### 3. 由流量和运算量推导性能

某 Kernel 使用本章指定的 FP32 路径，F 为 12 GFLOP，HBM 读写合计 Q 为 3 GB，耗时 2.5 ms；P 为 60 TFLOP/s，B 为 1,500 GB/s。

计算 I、两个耗时下界、吞吐上界、实际算术吞吐、实际 HBM 平均流量。随后只将 Q 减到 1.5 GB，求新的理想下界与吞吐上界；为什么不能直接承诺实测耗时减半？

另作概念判断：仅允许 FP32 输入采用 TF32 矩阵计算模式，是否足以认定输入存储字节数减半？评估本题的 GPU-T FP32 Kernel 时，可否改用第三篇 A100 稀疏规格中的 312 TFLOP/s 作效率分母？

### 4. 从提交返回推导结果何时可用

两批数据各需 H2D 4 ms、Kernel 10 ms、D2H 2 ms。按第四篇条件，复制和计算能够重叠，缓冲独立，主机在 1 ms 前已经提交完所有请求。

分别画出同流串行与双流重叠安排，并给出全部结果最早可用的时间。若 CPU 在 1 ms 就读取输出，是否安全？若两个 Stream 复用同一输入缓冲，而且批次 0 Kernel 仍在读该缓冲，批次 1 H2D 就写入它，缺少什么条件？

### 5. 识别指标口径

只看本篇教学 CSV，能否确定“显存容量占用 80%”“HBM 带宽达到 12%”“所有 SM 有 22% 在工作”这三句话？给出每项判断，并说明需要哪些材料才能计算 HBM 平均流量。

### 6. 找出整轮作业值得先分析的阶段

使用本篇完整的 100 ms 串行时间线，分别计算 Kernel 减半、输入准备减到 20 ms、Kernel 理想归零的端到端结果。现有材料已经足以定位哪个大阶段？还缺哪类信息才能继续判断原因？

### 7. 判断高利用率材料的证据边界

两次运行都报告 `utilization.gpu = 99%`。运行 X 每秒完成 100 批，运行 Y 在 30 秒中没有完成任何一批；除此以外，没有 Kernel 时间线、输入状态或错误记录。

能否认定 Y 是计算受限？下一步应补什么证据，用来区分有用长计算、等待 Kernel 与主机侧没有准备好下一批？

## 参考答案与推导

### 1. 线程、Warp 与驻留

总线程数为 `160 × 256 = 40,960`，每 Block 有 8 个 Warp，总共 1,280 个 Warp。寄存器和共享内存分别都只容纳 2 个 Block，所以每 SM 最多 2 个 Block、16 个 Warp，理论 Occupancy 为 25%。`80 × 2 = 160`，本 Grid 的 Block 数恰好足以在理想放置下填满这一驻留容量。

这给出了资源上限与工作数量的匹配，不保证执行中始终达到该值，也不保证算术单元每周期都繁忙。改为 4 个普通 Block 后，至多给 4 个 SM 分配本次工作；实际也可能有 Block 放在同一 SM，不能断言恰好用了 4 个。

### 2. 容量看变了哪些对象

仅当前批次从 10 GiB 降到 5 GiB，新峰值为 `50 + 5 + 12 + 8 = 75 GiB`，低于 76 GiB 应用预算，余量 1 GiB；加上固定占用，设备总需求 79 GiB。成立条件包括题目给定的无额外副本与无隐藏占用。

另一方案的峰值为 `50 + 10 + 12 + 4 = 76 GiB`，恰好达到应用预算；设备总需求 80 GiB，题设下容纳得下，但没有容量余量。两个结果都不能表述为整项作业显存减半。

### 3. 计算、带宽与上界

I 为 4 FLOP/B；计算下界 0.2 ms，搬运下界 2 ms，理想耗时下界为 2 ms。吞吐上界为 `min(60, 1.5 × 4) = 6 TFLOP/s`。记录中的吞吐为 4.8 TFLOP/s，HBM 平均流量为 1,200 GB/s。

Q 减半后，I 为 8 FLOP/B，搬运下界 1 ms，计算下界仍为 0.2 ms，故新耗时下界为 1 ms、吞吐上界为 12 TFLOP/s。这些是给定资源模型的边界；新增复用是否改变驻留和其他开销尚未给出，无法据此确定实测加速倍数。

TF32 是这里指定的矩阵计算模式，不能据此把 FP32 输入数组的存储大小减半。312 TFLOP/s 则属于另一张真实 GPU 在指定稀疏 Tensor Core 路径下的等效峰值，与本题设备和 FP32 路径都不匹配；本题仍使用给定的 60 TFLOP/s。

### 4. 提交与完成

串行安排依次为 `0—4 H2D0 → 4—14 K0 → 14—16 D2H0 → 16—20 H2D1 → 20—30 K1 → 30—32 D2H1`，全部结果在 32 ms 可用。

双流可行安排为 `H2D0 0—4、H2D1 4—8、K0 4—14、D2H0 14—16、K1 14—24、D2H1 24—26`，全部结果在 26 ms 可用。两组缓冲独立且满足题设的资源条件；这里不能把第二篇容量题中超预算的缓冲方案暗中搬进来。

1 ms 只是主机完成提交的时刻，输出尚未完成，CPU 不能安全读取。需要等待相应 D2H 后的 Event 或 Stream 完成。如果输入缓冲复用，就必须保证 K0 的读取结束后再覆盖；可以通过跨流 Event 建立依赖，或改用独立缓冲。加入依赖后需要重新求时间线。

### 5. 分子和分母

容量占用 80% 可以由 `65,536 / 81,920` 得出。12% 描述近期采样内设备内存读写的活动时间，不能等同于带宽比例；22% 描述有 Kernel 执行的时间比例，不能等同于 SM 数量比例。

计算 HBM 平均流量需要同一观察区间内 HBM 边界的读写字节合计 Q 和对应时长 t，并确认采集、缓存与设备范围的口径。用 `Q/t` 得速率，再和一致的 B 比较。

### 6. 端到端的关键阶段

Kernel 减半得到 90 ms、约 1.11 倍加速；准备减到 20 ms 得到 60 ms、约 1.67 倍加速；Kernel 理想归零得到 80 ms、上限 1.25 倍。输入准备是目前最长的串行阶段，值得先拆分。

缺少的是这 60 ms 内部的读取、预处理、排队与线程状态等材料。它们用于辨认哪一段占据时间；现有表已经支持阶段定位，尚未支持某个存储或 CPU 根因。

### 7. 高活动不等于有用进展

不能认定 Y 是计算受限。99% 只支持近期窗口持续存在 Kernel 活动；30 秒无完成批次可能是有用长计算，也可能是等待、错误或其他状态。

先对齐相同时间段的作业进度、CPU 提交/等待、Kernel 类型与持续时间、复制和错误记录。若主机未准备下一批，应能看到对应提交缺口；若设备持续运行等待 Kernel，应继续跟踪它所等待的事件或通信状态；若是有用长 Kernel，再用运算量、流量与资源分析判断约束。GPU 与作业的时间范围必须对齐，不能拿另一个窗口的高利用率补证。
