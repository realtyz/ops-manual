
## 为三批逐元素更新比较单槽与双槽

以下为离线**教学算例**，设备按整张 H100 SXM 80 GB 的规格参考值比较。程序依次处理三批输入，每批有两个各含 `10⁸` 个 FP32 元素的数组，对每个位置做一次 `y[i] ← a × x[i] + y[i]`。每线程负责一个位置，每 Block 128 个线程。`y` 原地更新，本例在该批更新完成后即可复用槽位，无需为后续阶段留存结果。

- 除输入槽位之外，还有 1.0 GB 的固定设备占用。作业的总显存预算先按 2.4 GB，随后改为 2.8 GB。全题用十进制 GB。
- 计时从第一批 H2D 开始到第三批 Kernel 完成。主机侧三批输入均已在页锁定缓冲区就绪。每批 H2D 按 20 ms，Kernel 按 0.40 ms。独立测量该 Kernel 时，假设跨 HBM 的读写合计为 1.2 GB。
- 只考虑一条 H2D 流和一条计算流。双缓冲时假设设备支持重叠，各项工作及时入队，无额外调度耗时和资源争用。参考峰值取 FP32 67 TFLOP/s、HBM 3.35 TB/s。 [NVIDIA · H100 Specifications](https://www.nvidia.com/en-us/data-center/h100/#specifications)

1. 每批启动多少 Block 和 Warp，最后一组有多少线程有效？如果每线程用 64 个寄存器，忽略分配粒度、共享内存等其他约束，每 SM 最多驻留多少个 Block？
2. 为一批分配一个设备槽位，槽内存放 `x`、`y`。单槽和双槽的预算各是多少？为什么单个 Kernel 的 HBM 流量与这一槽位的大小不同？
3. 计算单个 Kernel 的 Roofline 时间下界和记录中的 HBM 吞吐。按这些数，该先验证哪项设备内部约束？
4. 分别列出单槽串行与双槽重叠的三批时间线。把第 3 批复用槽 0 的条件也写出来。若目标是三批更早完成，应先关注哪段时长？还需要什么实机证据？

## 参考推理

**线程分组与驻留。** `10⁸ ÷ 128 = 781,250` 个 Block，恰好整除。每 Block 有 4 个 Warp，共 3,125,000 个 Warp，最后一组的 32 个线程都参与。按 H100 每 SM 的 65,536 个 32 位寄存器计算，每块用 `128 × 64 = 8,192` 个，最多容纳 8 个 Block，即 32 个 Warp，占每 SM 上限的一半。这是按寄存器推得的驻留上界。整个 Grid 有足够多的 Block 供各 SM 分派，实际就绪和发射还要看运行状态。 [Hopper Tuning Guide 13.2 · Occupancy](https://docs.nvidia.com/cuda/archive/13.2.1/hopper-tuning-guide/index.html#occupancy)

**容量与流量。** 一个槽位占 `2 × 4 B × 10⁸ = 0.8 GB`。固定占用加上槽位，单槽需要 1.8 GB，双槽需要 2.6 GB。2.4 GB 时只有单槽能装下，2.8 GB 时双槽也可装下，按算例尚余 0.2 GB。每批 H2D 传两份输入，共 0.8 GB。Kernel 的 1.2 GB 还包括写回 `y` 的 0.4 GB，读和写共享一块存储但都经过 HBM 边界。

**Kernel 内部。** 一批做 `2 × 10⁸` FLOP，计算时间下界约 0.003 ms，HBM 时间下界约 0.358 ms，取两者较大值。记录中的 DRAM 吞吐为 `1.2 GB ÷ 0.40 ms = 3.0 TB/s`，接近带宽规格。对这次 Kernel 先验证 HBM 带宽约束，例如控制输入和时钟，比较减少 DRAM 字节后用时是否下降。

**整批时间。** 双槽时，计算流要等对应批次的 H2D 完成，拷贝流要等前一项拷贝结束。第 3 批还要等第 1 批 Kernel 写完 `y` 并释放槽 0。到 40 ms 启动第 3 批拷贝时，这一条件已在 20.40 ms 满足。

| 批次 | 单槽 H2D | 单槽 Kernel | 双槽 H2D | 双槽 Kernel |
| --- | --- | --- | --- | --- |
| 1 | 0–20 ms | 20–20.40 ms | 0–20 ms | 20–20.40 ms |
| 2 | 20.40–40.40 ms | 40.40–40.80 ms | 20–40 ms | 40–40.40 ms |
| 3 | 40.80–60.80 ms | 60.80–61.20 ms | 40–60 ms | 60–60.40 ms |

三批总时间从 61.20 ms 降到 60.40 ms。每次只有 0.40 ms 的计算可与下一批 H2D 重叠，三个 20 ms 的 H2D 在同一流上依次进行。因此即使 Kernel 内部先碰到 HBM 约束，完整窗口仍主要受 H2D 限制。实机上先用 CUDA 时间线核对两条流、每批的拷贝字节、持续时间及实际重叠，再沿主机到设备的路径查可持续传输速率。这里的 H2D 按有效载荷折算为 `0.8 GB ÷ 20 ms = 40 GB/s`，要与主机到设备同方向的结果比较。如果实际作业还要求准备输入或读回结果，相应依赖也要放回时间线。

## 从存储位置到作业完成条件

执行由主机提交，GPU 把 Block 派给 SM，再从就绪 Warp 发射指令。数据的存储位置决定一次读取经过的层次，存活的缓冲区决定容量需求，跨存储层的读写量和指令路径共同约束 Kernel 时间。把这些 Kernel 放回批次，Stream 顺序、事件和缓冲区复用又决定哪些工作可同时发生。设备的忙碌百分比只有与这些依赖、流量和时长对齐，才能作为瓶颈的证据。
