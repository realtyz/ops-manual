# 综合检验与本章小结

学完单卡并行执行、显存层次、Roofline 与异步流水线后，最好的检验方式是不依赖实机、仅凭硬件规格和关键观测数据独立推演系统行为。下面准备了两道覆盖**批处理流水线**与**在线大模型推理**的综合实战题，建议先自己动笔列出算式与时间线，再对照参考推理核验每一步结论。

## 一、实战场景一：三批逐元素更新的线程、预算与双缓冲推演

某数据预处理程序在单张 **H100 SXM 80 GB** 上依次处理三批输入，每批包含两个各含 $10^8$ 个 FP32 元素的数组，对每个位置执行一次原地更新 `y[i] ← a × x[i] + y[i]`。结果在当批更新完成后即可释放复用槽位，无需为后续阶段保留。

已知全部硬件与运行参数如下（本题容量与带宽均按十进制 `1 GB = 10⁹ B`、`1 TB = 10¹² B` 计算）：

| 参数维度 | 具体条件 |
| --- | --- |
| 参考设备规格 | H100 SXM 80 GB：每 SM 65,536 个 32 位寄存器、最大 64 Warp；常规 FP32 峰值 67 TFLOP/s；HBM 带宽 3.35 TB/s |
| 启动配置与资源 | 每线程处理 1 个元素；每 Block 128 个线程；每线程用 64 个 32 位寄存器（忽略分配粒度与共享内存限制） |
| 显存预算条件 | 除输入槽位外有 1.0 GB 固定设备占用；作业总预算方案一为 **2.4 GB**，方案二放宽至 **2.8 GB** |
| 流水线与实测耗时 | 主机三批输入均已在页锁定缓冲就绪；仅用 1 条拷贝流与 1 条计算流；每批 H2D 实测 **20 ms**，Kernel 实测 **0.40 ms**，单批 Kernel 跨 HBM 读写合计 **1.2 GB** |

请结合本章知识逐一推导以下四个问题：

1. 每批启动多少个 Block 和 Warp？最后一个 Warp 有多少线程有效？仅按寄存器约束，每个 SM 最多驻留多少个 Block（对应驻留率多少）？
2. 若每批输入（含 `x`、`y`）分配一个设备槽位，单槽与双槽方案各需多少总显存？2.4 GB 与 2.8 GB 预算下分别可行吗？为什么单个 Kernel 的 HBM 流量（1.2 GB）大于单槽体积？
3. 推导单个 Kernel 的 Roofline 时间下界与实测 HBM 吞吐，判断该 Kernel 内部优先受限于哪项约束。
4. 分别排出单槽串行与双槽重叠的三批起止时间线（计时从第 1 批 H2D 开始至第 3 批 Kernel 结束），写明第 3 批复用槽 0 的触发条件。若想让三批整体明显变快，应该先优化哪一段？实机排查还需补采什么证据？

### 场景一参考推理

**1. 线程分组与 SM 寄存器驻留上限**

每批 $10^8$ 个元素恰好被 128 整除，无尾部闲置线程：

$$\text{Block 数} = \frac{10^8}{128} = 781{,}250 \text{ 个}, \qquad \text{Warp 数} = 781{,}250 \times \frac{128}{32} = 3{,}125{,}000 \text{ 个}$$

最后一个 Warp 的 32 个线程全部有效参与更新。按 H100 每 SM 的寄存器配额核算：

$$\text{单 Block 寄存器需求} = 128 \times 64 = 8{,}192 \text{ 个}$$

$$\text{单 SM 最大驻留 Block 数} = \left\lfloor \frac{65{,}536}{8{,}192} \right\rfloor = 8 \text{ 个 Block} = 32 \text{ 个 Warp} \quad (\text{驻留率 } 50\%)$$

整个 Grid 拥有超过 78 万个 Block，足以把 H100 的 132 个 SM 全部喂饱。

**2. 单槽/双槽显存预算与“容量 ≠ 流量”辨析**

单个槽位存放两个各 $10^8$ 个 FP32（4 B）数组：

$$\text{单槽容量} = 2 \times 10^8 \times 4\text{ B} = 0.8\text{ GB}$$

$$\text{单槽总需求} = 1.0 + 0.8 = 1.8\text{ GB}, \qquad \text{双槽总需求} = 1.0 + 2 \times 0.8 = 2.6\text{ GB}$$

因此 **2.4 GB 预算下只能用单槽**（双槽会 OOM）；放宽到 **2.8 GB 后双槽可行**，尚余 0.2 GB 裕量。

单槽容量仅 0.8 GB，而 Kernel 的 HBM 流量却达 1.2 GB，是因为 `y` 原地更新只占 1 份空间（0.4 GB），却既要读旧值又要写新值，加上读 `x`，总流量为 1.2 GB。

**3. Kernel 内部 Roofline 诊断**

单批计算量 $F = 2 \times 10^8\text{ FLOP} = 0.2\text{ GFLOP}$，对照常规 FP32（67 TFLOP/s）与 HBM（3.35 TB/s）：

$$T_{\text{计算下界}} = \frac{0.2\text{ GFLOP}}{67\text{ TFLOP/s}} \approx 0.003\text{ ms}, \qquad T_{\text{HBM下界}} = \frac{1.2\text{ GB}}{3{,}350\text{ GB/s}} \approx 0.358\text{ ms}$$

$$\text{实测 HBM 吞吐} = \frac{1.2\text{ GB}}{0.40\text{ ms}} = 3.00\text{ TB/s} \quad (\text{约为规格峰值的 } 90\%)$$

Kernel 耗时（0.40 ms）紧贴访存时间下界（0.358 ms），属于典型的 **HBM 带宽受限**。若要优化该 Kernel 本身，应优先减少跨 HBM 搬运（如算子融合），而非追求更高浮点算力。

**4. 三批时间线与全局瓶颈反转**

双槽流水线中，第 3 批复用槽 0 必须同时满足两个条件：① 拷贝流已完成第 2 批 H2D（40 ms）；② 第 1 批 Kernel 已通过 `done[1]` 释放槽 0（20.40 ms 早已满足）。两方案时间线如下：

| 批次 | 单槽串行 H2D | 单槽串行 Kernel | 双槽重叠 H2D | 双槽重叠 Kernel |
| :---: | --- | --- | --- | --- |
| 第 1 批 | 0–20 ms | 20–20.40 ms | 0–20 ms | 20–20.40 ms |
| 第 2 批 | 20.40–40.40 ms | 40.40–40.80 ms | 20–40 ms | 40–40.40 ms |
| 第 3 批 | 40.80–60.80 ms | 60.80–61.20 ms | 40–60 ms | 60–60.40 ms |

> [!summary] 场景一关键洞察：局部瓶颈 ≠ 全局关键路径
> 开启双槽后，三批总耗时仅从 **61.20 ms 微降至 60.40 ms**（仅省 0.80 ms），因为每次只有 0.40 ms 的计算能藏进下一批 20 ms 的 H2D 里。尽管单看 Kernel 内部卡在 HBM 带宽，放到整条时间线上，**三段连续的 20 ms H2D 才是绝对关键路径**！
>
> 按载荷折算，实测 H2D 有效速率为 $0.8\text{ GB} \div 20\text{ ms} = 40\text{ GB/s}$。下一步必须用 Nsight Systems 核对拷贝流是否无阻塞重叠，沿第 01/04 章的 PCIe 与 NUMA 路径追查 H2D 速率，或压缩主机侧传输体积。

## 二、实战场景二：在线 LLM 推理的 KV Cache、GPU-Util 迷思与加 Batch 拐点

某在线推理团队在一张 **H100 SXM 80 GB**（可用物理显存按二进制换算约为 $74.5\text{ GiB}$）上部署了一套 **32B 参数、GQA 架构**的对话大模型。其核心架构与硬件参数如下：

| 参数维度 | 具体条件 |
| --- | --- |
| 模型结构 | 总参数量 $W = 3.2 \times 10^{10}$；Transformer 层数 $L = 64$；KV 注意力头数 $n_{\text{kv}} = 8$；单头维度 $d_{\text{head}} = 128$ |
| 显存与精度口径 | 框架运行时与临时工作区固定占 **4.0 GiB**；单卡总可用 HBM 按 **74.5 GiB** 计；HBM 带宽 $B = 3.35\text{ TB/s}$，FP8 稠密 Tensor Core 峰值 $P_{\text{FP8}} = 1{,}978.9\text{ TFLOP/s}$ |
| 线上观测现象 | 模型改用 FP8（权重与 KV 均 1 B/元素）运行 Decode：$B = 1$（极短上下文，暂忽略 KV 读取）时，`nvidia-smi` 报 `GPU-Util = 95%`，单步实测耗时 **11.0 ms** |

请逐一分析并作答：

1. **显存与并发容量对比**：在单请求上下文长度 $S = 8{,}192$（8K）下，计算单 token 与单请求的 KV Cache 大小（分别按 BF16 与 FP8 计算）。将权重与 KV Cache 从 BF16 全面量化到 FP8 后，单卡最多可同时承载的 8K 并发请求数会如何变化？
2. **拆穿 `GPU-Util 95%` 假象**：针对 $B = 1$ 的 FP8 Decode 实测（单步 11.0 ms），核算实际 HBM 吞吐与实际 FP8 计算吞吐占比，解释为何 `GPU-Util` 高达 95% 却远未跑满算力。
3. **Continuous Batching 的收益与拐点**：保持 FP8 精度，通过 Continuous Batching 将并发从 $B = 1$ 提升到 $B = 32$（每请求当前上下文均为 $S = 2{,}048$）。请重新估算单步 HBM 读取总字节、HBM 时间下界与计算时间下界，说明为什么系统总吞吐能暴涨逾 20 倍而单请求延迟仅小幅上升，并指出继续加 Batch 最终会在哪两个边界撞墙。

### 场景二参考推理

**1. KV Cache 核算与 FP8 量化带来的并发跃升**

先按 KV Cache 公式计算 BF16（2 B/元素）与 FP8（1 B/元素）的每 token 及单路 8K 请求占用：

$$\text{单 token KV（BF16）} = 2 \times 64 \times 8 \times 128 \times 2\text{ B} = 262{,}144\text{ B} = 256\text{ KiB} = 0.25\text{ MiB}$$

$$\text{单请求 8K KV（BF16）} = 8{,}192 \times 0.25\text{ MiB} = 2{,}048\text{ MiB} = 2.0\text{ GiB}$$

量化为 FP8 后每元素减半，单 token KV 降至 **128 KiB**，单请求 8K KV 降至 **1.0 GiB**。再对齐权重体积（十进制 GB 换算为二进制 GiB）核算两者的并发天花板：

- **BF16 方案**：权重 $64\text{ GB} \approx 59.6\text{ GiB}$，加上 4.0 GiB 固定开销共占 63.6 GiB，留给 KV Cache 的余量仅 $74.5 - 63.6 = 10.9\text{ GiB}$，最多承载 $\lfloor 10.9 / 2.0 \rfloor = \mathbf{5}$ 路 8K 并发。
- **FP8 方案**：权重减半为 $32\text{ GB} \approx 29.8\text{ GiB}$，加上 4.0 GiB 固定开销共占 33.8 GiB，可用 KV Cache 空间跃升至 $74.5 - 33.8 = 40.7\text{ GiB}$。
  - 由于单路 8K KV 又减半到 1.0 GiB，最大并发可达 $\lfloor 40.7 / 1.0 \rfloor = \mathbf{40}$ 路——**并发承载能力直接翻了 8 倍！**

**2. 拆穿 `GPU-Util 95%` 假象**

32B 模型生成 1 个 token 的线性层计算量 $F \approx 2W = 64\text{ GFLOP}$，FP8 权重读取量 $D \approx 32\text{ GB}$。代入实测耗时 11.0 ms：

$$\text{实测 HBM 吞吐} = \frac{32\text{ GB}}{0.011\text{ s}} \approx 2.91\text{ TB/s} \quad (\text{达 HBM 峰值 } 3.35\text{ TB/s 的 } 87\%)$$

$$\text{实测计算吞吐} = \frac{64\text{ GFLOP}}{0.011\text{ s}} \approx 5.82\text{ TFLOP/s} \quad (\text{仅占 FP8 峰值 } 1{,}978.9\text{ TFLOP/s 的 } 0.29\%)$$

`nvidia-smi` 的 `GPU-Util` 统计的是采样窗口内“存在活跃 Kernel 的时间占比”。由于单步 Decode 连续不断发射各层 Kernel，卡面几乎一直处于有任务挂载状态，因而显示 95%；但硬件真相是 **87% 的 HBM 带宽已经跑满，而 99.7% 的 Tensor Core 算力正在干等数据**。

**3. Continuous Batching 收益推导与双重撞墙边界**

并发扩至 $B = 32$、每请求上下文 $S = 2{,}048$ 时，32 路请求**共享同一份 32 GB 的 FP8 权重读取**，但各自需要独立读取自己的 KV Cache。

每路 2K 上下文的 FP8 KV 体积及 32 路总新增流量为：

$$\text{单路 2K FP8 KV} = 2{,}048 \times 128\text{ KiB} = 0.25\text{ GiB} \approx 0.268\text{ GB}, \qquad 32 \times 0.268\text{ GB} \approx 8.6\text{ GB}$$

$$D_{B=32} \approx 32.0 + 8.6 = 40.6\text{ GB}, \qquad F_{B=32} \approx 32 \times 64\text{ GFLOP} = 2.048\text{ TFLOP}$$

$$T_{\text{HBM下界},\, B=1} = \frac{32.0\text{ GB}}{3{,}350\text{ GB/s}} \approx 9.55\text{ ms} \;\longrightarrow\; T_{\text{HBM下界},\, B=32} = \frac{40.6\text{ GB}}{3{,}350\text{ GB/s}} \approx 12.1\text{ ms}$$

$$T_{\text{计算下界},\, B=32} = \frac{2.048\text{ TFLOP}}{1{,}978.9\text{ TFLOP/s}} \approx 1.03\text{ ms} \ll 12.1\text{ ms}$$

结果极具冲击力：计算时间下界（1.03 ms）仍远远藏在 HBM 搬运时间（12.1 ms）阴影之下；**单步延迟下界仅增加约 27%（9.55 ms → 12.1 ms），而系统总吞吐下界却从约 105 token/s 飙升至约 2,640 token/s（暴涨约 25 倍）！**

继续调大 $B$ 时，这项红利会在两个硬边界处消失、导致单请求 TPOT 开始随 $B$ 线性恶化：
- **越过计算拐点**：FP8 下 H100 拐点约 591 FLOP/B，一旦 $B$ 大到使计算时间 $F/P$ 反超 HBM 搬运时间，Decode 转为计算受限，再加并发便只能靠拉长每步时间来消化算力。
- **KV Cache 反客为主**：各请求 KV Cache 无法共享，若上下文拉长（如 32K），KV 流量会迅速超越 32 GB 的固定权重流量成为 HBM 读写大头，此时总搬运字节直接随 $B$ 线性膨胀，且显存容量也会率先耗尽。

> [!summary] 场景二关键洞察：推理优化的三条硬杠杆
> 1. **量化一箭双雕**：权重与 KV 同步转 FP8，不仅把单卡 8K 并发容量拉高 8 倍，还直接腰斩单路 Decode 延迟下界。
> 2. **批处理摊薄搬运**：在带宽受限区，Continuous Batching 用极小的 TPOT 增量换取数十倍总吞吐。
> 3. **指标穿透分母**：遇到 `GPU-Util 95%` 切勿误判算力打满，必须以 HBM 吞吐与有效 FLOP/s 定性。

## 三、本章小结与下章衔接

回望整章，我们把单张 GPU 从里到外串成了一条严谨的因果链：

1. **执行层（第 01 篇）**：主机提交 Kernel，硬件将 Grid 拆为 Block 分派给 SM，再以 32 线程的 Warp 为单位靠零开销切换隐藏延迟；寄存器与共享内存决定 SM 驻留率，CUDA Core 与 Tensor Core 分工决定实际算力上限。
2. **存储层（第 02 篇）**：数据沿“主机 DRAM → HBM → 共享 L2 → L1/共享内存 → 寄存器”逐级贴近算术单元；显存峰值取决于存活对象的同时叠加——训练盯住优化器与激活，推理盯住随 $B \times S$ 暴涨的动态 KV Cache，实操排障要分清活跃张量、分配器保留与设备已用三层口径。
3. **屋顶线层（第 03 篇）**：算术强度 $I = F/D$ 与硬件拐点 $P/B$ 把算子劈成计算受限（训练大 GEMM、推理 Prefill）与 HBM 带宽受限（逐元素算子、推理 Decode）两类世界；量化同时砍掉容量与搬运字节，Continuous Batching 靠复用权重把 Decode 推向吞吐甜蜜区。
4. **流水与诊断层（第 04–05 篇）**：CUDA Stream、Event、双缓冲与页锁定内存决定了 H2D 与计算能否真正重叠；排查慢作业时必须从完成契约倒推关键路径，用 `nsys` 与 `ncu` 穿透 `GPU-Util` 的时间占比假象。

至此，你已经看清了一张 GPU 内部的算力与显存账本。下一章（第 03 章）将沿“主机启动 Kernel”向下深挖，揭开从 Linux 内核驱动、`libcuda` 到 CUDA Runtime 与编译架构兼容性的软件依赖链。

第 04 章则会回到本篇场景一里卡住关键路径的 H2D 箭头，把视角扩展到单机多卡的 PCIe、NVLink 与 NVSwitch 高速互联。
