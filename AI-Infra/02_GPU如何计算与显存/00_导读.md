# GPU 如何计算，显存为什么重要

同一张 GPU 上，两个作业都显示“显存用了很多、GPU 利用率接近 100%”，完成速度却可以相差很大。理解这个现象，需要把三个问题分开：工作怎样分给 GPU，数据怎样供给执行单元，以及一次计算的时间花在了哪里。

本章的学习任务是：**画出线程到执行硬件的关系，计算显存峰值需求，用运算量和搬运量估计性能上界，并将指标与时间线联系起来解释等待。** 不要求编写 CUDA Kernel，也不要求运行命令。

## 前置与章节边界

读者已有 Linux、容器与 Kubernetes 基础；从[第 01 章](../01_从一台GPU服务器认识基础设施/00_导读.md)带来两个认识：CPU 仍负责组织作业，主机内存与每张 GPU 的本地显存具有各自的位置和容量。进程、线程和虚拟地址的通用含义沿用已有基础；GPU 线程、Warp、SM、Kernel、Stream、算术强度等在本章首次建立。

本章讲清单 GPU 内的执行与存储关系、主机提交与设备完成的差别，以及性能判断的基本方法。[第 03 章](../03_从驱动到CUDA应用的软件依赖/00_导读.md)再展开驱动、CUDA 库与应用依赖；[第 04 章](../04_单机多卡与GPU数据路径/00_导读.md)展开 PCIe、P2P、NVLink 等实际传输路径。数据准备不足在这里表现为时间线上的等待，存储与加载机制在第 09 章继续解释；工具部署和集群监控在第 17 章展开。

## 教学材料的共同约定

本章另建一张虚构的独占、未切分的离散 GPU **GPU-T**，与第 01 章的四张 48 GiB PCIe GPU 没有型号或编号映射。它用于纸面推演，不对应任何 NVIDIA 在售产品：

| 条件 | 本章约定 |
| --- | --- |
| 执行组织 | 80 个 SM；驻留练习只使用普通 Thread Block，不使用跨 Block 协作等高级特性 |
| 本地显存 | 80 GiB，教学模型选用 HBM；容量题另扣 4 GiB 固定占用，给应用 76 GiB 预算 |
| 性能模型 | 指定 FP32 运算路径的计算上界 `P = 60 TFLOP/s`；HBM 读写合计的流量上界 `B = 1,500 GB/s` |
| 边界条件 | 无其他作业争用；各题再给出并发、缓存、时序和临时分配条件 |

容量采用二进制单位：`1 GiB = 2^30 B`、`1 MiB = 2^20 B`。带宽与运算量采用十进制单位：`1 GB = 10^9 B`、`1 TB = 10^12 B`、`1 GFLOP = 10^9` 次浮点运算、`1 TFLOP/s = 10^12` 次浮点运算每秒。性能表中的 GB 不能直接替换为容量表中的 GiB。

图、输出和耗时均为教学材料；命令只说明未来如何取得同类证据。事实核对主要采用 CUDA 12.8.1 的归档编程指南、最佳实践与 Runtime API 文档；精度差异以 Ampere 为具体实例，不将它推广为所有代际的支持矩阵。另用 2020 年 A100 发布规格演示峰值口径，用 PyTorch 2.15 文档说明分配器的容量统计，不要求框架实操。`nvidia-smi` 与 Nsight 文档使用核对日可访问的官方版本。核对日期为 **2026-11-08**。

学完后，尝试用一页纸同时保留三张小图：工作划分图、数据层次图、作业时间线。能够在三张图之间移动，才能解释“显存占得多”“GPU 一直有 Kernel”和“作业推进得快”之间的差别。
