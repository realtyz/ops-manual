## 01 从一次 Kernel 启动到 SM 执行

**问题与预期结论**　应用启动了上千个线程，为什么 GPU 无需给它们各配一个硬件核心？读完能把一次启动拆成 Grid、Block、Warp 和线程，区分 CUDA Core、Tensor Core 与 Warp 调度器的职责，并说明并行规模、同时驻留数量与实际发射之间的关系。

**解释顺序**

1. 用 `y[i] ← a × x[i] + y[i]` 建立「一个线程处理一个元素」的映射，输入先假设已在设备内存。主机指定 Grid 和 Block 的尺寸，普通 Kernel 的 Block 整体分配给一个 SM，多个 Block 可在同一 SM 上驻留。Block 的先后次序和具体 SM 由设备安排。API 提交和等待细节留给第 04 节。
2. SM 将 Block 内线程按 32 个一组划分为 Warp，从已驻留且就绪的 Warp 中选择并发射指令。用尾部越界保护展示部分线程跳过更新，用线程走不同分支解释分歧为何可能降低有效工作比例。寄存器、共享内存、每 SM 最大 Block 和 Warp 数会限制驻留。足够多的就绪 Warp 有助于隐藏等待，驻留 Warp 比例（occupancy）与就绪数量分开说明。
3. 把运算单元画在 SM 内。用标量 FP32 运算说明 CUDA Core 路径，用矩阵乘加说明 Tensor Core 路径。数据类型、所用指令及库选择会改变使用的单元。保留普通 Block 模型，Thread Block Cluster 和 Kernel 编程留作专题。

**支撑材料**

- 用 1,000 个元素、每 Block 128 线程算出 `ceil(1000 / 128) = 8` 个 Block，共 32 个 Warp。尾部 Warp 有 8 个线程处理有效元素，其余 24 个跳过更新。拟画「一次 Grid 启动 → 两个示意 SM → 放大一个 Block 与 Warp」，标明 SM 数是示意，放大的是尾部 Block。用 CUDA 文档核对分组与分派，用 Hopper 架构的 SM 图核对功能单元的位置。 [CUDA 13.2.1 · Programming Model](https://docs.nvidia.com/cuda/archive/13.2.1/cuda-programming-guide/01-introduction/programming-model.html) · [CUDA 13.2.1 · Writing SIMT Kernels](https://docs.nvidia.com/cuda/archive/13.2.1/cuda-programming-guide/02-basics/writing-cuda-kernels.html) · [NVIDIA Hopper Architecture In-Depth](https://developer.nvidia.com/blog/nvidia-hopper-architecture-in-depth/)
- 另用驻留上界算例。假设 Grid 有足够多的 Block，每 Block 128 线程、每线程 64 个 32 位寄存器，先忽略分配粒度和其他资源限制。H100 每 SM 有 65,536 个 32 位寄存器，这一项最多容纳 `65,536 ÷ (128 × 64) = 8` 个 Block，即 32 个 Warp，为每 SM 最多 64 个 Warp 的一半。再说明共享内存或较少的 Block 如何进一步压低驻留。 [Hopper Tuning Guide 13.2 · Occupancy](https://docs.nvidia.com/cuda/archive/13.2.1/hopper-tuning-guide/index.html#occupancy) · [CUDA 13.2.1 · Compute Capabilities](https://docs.nvidia.com/cuda/archive/13.2.1/cuda-programming-guide/05-appendices/compute-capabilities.html)

## 02 数据放在哪里，显存容量怎么算

**问题与预期结论**　同一份权重能装入 GPU，提高批量或并发后却可能 OOM。读完能画出主机内存、HBM、L2 和 SM 内存资源的关系，按同时存活的对象估算峰值，并分清规格容量、设备已用、框架保留与活跃张量的统计范围。

**解释顺序**

1. 区分主机 DRAM 和设备内存。H100 实例中 HBM 是显存的物理介质，常规设备分配得到 GPU 全局内存空间中的缓冲区。沿全局访存路径讲 SM 内 L1、设备共享的 L2 与 HBM，说明访问类型与缓存命中如何改变到达 HBM 的流量。寄存器供线程使用，共享内存由 Block 内线程显式使用。Hopper 的 L1 与共享内存可使用同一片片上存储资源，逻辑用途各自标注。
2. 从张量形状和每元素字节数起算，按阶段记录权重、输入/输出、中间状态与算子工作区的生存期，再加运行时等开销或预算余量。判断峰值时求同一时刻的合计。批量、并发、dtype、算法和缓冲区复用都会改变结果。训练的梯度和优化器状态只列为额外预算项。统一内存只点到受设备与系统条件约束的放置或迁移行为。
3. 区分「某次申请容不下」「活跃对象增加」「分配器持有可复用空间」。把失败分配的大小和时点对照容量、生命周期、分配器记录及其他进程。换到相同单位后再比较。容量回答能装多少字节，带宽回答单位时间能移动多少字节。带宽估算交给第 03 节，主机到设备的实际传输路径交给第 04 章。

**支撑材料**

- 拟画「主机 DRAM → 单张 GPU 的 HBM → L2 与 SM 局部」层次图，用边框表示归属、用箭头区分主机拷贝和 GPU 内部访存。SM 局部标出寄存器、共享内存及 L1 的用途。用 CUDA 的设备内存说明和 Hopper 的 L1/共享内存说明核对图。 [CUDA 13.2.1 · Unified and System Memory](https://docs.nvidia.com/cuda/archive/13.2.1/cuda-programming-guide/02-basics/understanding-memory.html) · [Hopper Tuning Guide 13.2 · Unified Shared Memory/L1/Texture Cache](https://docs.nvidia.com/cuda/archive/13.2.1/hopper-tuning-guide/index.html#unified-shared-memory-l1-texture-cache)
- 用教学容量表。假设单卡给作业的预算为 24 GB（十进制），7×10⁹ 个 FP16 权重占 14 GB。峰值时还同时需要 3 GB 活跃输入/中间状态、2 GB 工作区和 1 GB 预留，预算需求为 20 GB。只把活跃状态改为 8 GB 后，需求变为 25 GB，已超过预算。权重单独换成 FP32 后，权重本身需 28 GB。将各项估算及余量分列，24 GB 标为教学预算。
- 拟用 PyTorch 2.8 原生缓存分配器旁例，配置 `PYTORCH_CUDA_ALLOC_CONF=backend:native`。同一进程、设备和时间点并排读 `memory_allocated()` 与 `memory_reserved()`，再对照 `nvidia-smi` 的 FB Memory Usage · Used。配一条释放张量前后的示意记录，说明活跃量下降时保留量可以维持，设备已用还可能包含其他分配。另读 `max_memory_allocated()` 时交代峰值统计区间。 [PyTorch 2.8 · Memory management](https://docs.pytorch.org/docs/2.8/notes/cuda.html#memory-management) · [NVIDIA System Management Interface](https://docs.nvidia.com/deploy/nvidia-smi/index.html)

## 03 用精度、带宽和运算量估算性能上界

**问题与预期结论**　同一张卡上，矩阵乘法与逐元素更新为何可能各受不同资源限制？读完能从规格表选对数据类型、运算单元和稀疏口径，估出单个 Kernel 更可能碰到哪条上界，并解释作业吞吐还取决于哪些条件。

**解释顺序**

1. 拆开存储格式、运算输入、累加和输出精度。FP16 与 BF16 都是每元素 2 B，表示范围和精度不同。以 FP16 输入、FP32 累加的矩阵乘法说明混合精度。以 cuBLAS 的 TF32 选项说明输入/输出矩阵仍可为 FP32 存储。形状、布局、硬件和库算法共同决定能否走 Tensor Core 路径，低精度还需满足应用的数值误差要求。
2. 读 H100 SXM 规格时，先定位 FP32 的 67 TFLOP/s、单卡 80 GB 与 HBM 带宽 3.35 TB/s，再读带稀疏脚注的 TF32 989 和 FP16/BF16 1,979 TFLOP/s。用白皮书表 3 对照稠密与稀疏两种口径。稠密算例取 FP16 Tensor Core、FP32 累加的 989.4 TFLOP/s。解释 2:4 约束和使用稀疏路径的条件，避免把稀疏峰值套到普通矩阵乘法上。
3. 先数运算量 F 和所选存储层的流量 D，约定一次乘加计 2 FLOP、使用十进制 GB/TB。用算术强度 `I = F/D` 与分界点 `P/B` 比较，其中 P 为计算峰值，B 为该存储层带宽。推导吞吐上界 `min(P, B × I)` 和时间下界 `max(F/P, D/B)`。区分算法逻辑读写、实际 DRAM 流量与主机拷贝。缓存复用、访存合并、并行规模、延迟、指令路径或频率变化时，要更新估算或补测。实际点若远离上界，需补证据再定瓶颈。作业等待交给第 04—05 节。

**支撑材料**

- 用 H100 数据表核对 SKU、峰值和稀疏脚注，用 H100 架构白皮书 V1.04 表 3 核对稠密与稀疏的峰值及对应累加精度，用 NVIDIA 的结构化稀疏说明核对 2:4 约束。用 cuBLAS 的 `cublasComputeType_t` 与 `cublasGemmEx` 类型表核对 TF32 和 FP16/FP32 混合精度。具体 Kernel 走哪条指令路径，留给观测确认。 [NVIDIA H100 数据表](https://resources.nvidia.com/en-us-gpu/h100-datasheet-24306) · [NVIDIA H100 GPU 架构白皮书](https://resources.nvidia.com/en-us-hopper-architecture) · [NVIDIA · Structured Sparsity](https://developer.nvidia.com/blog/structured-sparsity-in-the-nvidia-ampere-architecture-and-applications-in-search-engines/#structured_sparsity_in_the_nvidia_ampere_architecture) · [cuBLAS 13.2 · Compute Types](https://docs.nvidia.com/cuda/archive/13.2.1/cublas/index.html#cublascomputetype-t)
- 逐元素例沿用第 01 节的更新式，改为 10⁸ 个 FP32 元素。假定每元素 2 FLOP，标量 a 已就绪，HBM 读 x 与旧 y、写新 y 各 4 B，无额外流量。则 F = 0.2 GFLOP、D = 1.2 GB、I ≈ 0.167 FLOP/B。计算下界约 0.003 ms，访存下界约 0.358 ms，理想上界由 HBM 带宽给出。
- 矩阵例取 8192×8192 的稠密 C = AB。A/B 为 FP16，FP32 累加并写 FP32 的 C，旧 C 不参与。假定输入初始在 HBM，理想复用下 A、B 各读一次、C 写一次。则 F = 2×8192³ ≈ 1.100 TFLOP，D = 8×8192² ≈ 0.537 GB，I = 2048 FLOP/B。Tensor Core 计算下界约 1.11 ms，按最低流量计算的访存下界约 0.160 ms。若实际 HBM 流量升到约 3.72 GB，两项理想下界才相当。以计算上界为候选，再检查实际流量、指令与峰值差距。两例并排用表呈现。 [CUDA Best Practices Guide 13.2 · Bandwidth](https://docs.nvidia.com/cuda/archive/13.2.1/cuda-c-best-practices-guide/index.html#bandwidth) · [Nsight Compute · Roofline Charts](https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html#roofline-charts)

## 04 在时间线上读懂 Stream、异步与同步

**问题与预期结论**　CPU 侧函数已经返回，为什么 GPU 结果还未完成？为什么两个 Stream 有时仍然串行？读完能标出提交、实际执行和完成，区分主机等待、流内顺序与跨流依赖，并判断两批工作的拷贝与计算是否具备重叠条件。

**解释顺序**

1. 从单 Stream 的「H2D → Kernel → 可选 D2H」开始。主机调用入队，普通操作在同一 Stream 内按序执行。CPU 读取 D2H 结果前等对应操作完成。比较 `cudaEventSynchronize`、`cudaStreamSynchronize` 和 `cudaDeviceSynchronize` 的等待范围。主机时钟围住入队动作，量到的是提交侧耗时。用同流 CUDA Event 对计时，要确保事件完成并交代区间、并发和预热。端到端计时覆盖输入准备至结果可用。
2. 改为一个拷贝流和一个计算流，两个设备缓冲区交替使用。拷贝后记录 ready Event，计算流用 `cudaStreamWaitEvent` 等本批输入。计算结束记录 done Event，拷贝流在覆盖该缓冲区前等 done。主机页锁定缓冲区在拷贝完成前保持有效且内容稳定。第 n+1 批 H2D 才有机会与第 n 批 Kernel 重叠。实际重叠取决于设备拷贝能力、方向、争用和是否及时入队。`asyncEngineCount` 用于判断拷贝相关能力，Kernel 间并发另看 `concurrentKernels` 与 SM 资源。
3. 对照显式流与默认流。Legacy 默认流和同一上下文内的 blocking 流有隐式顺序，`cudaStreamNonBlocking` 创建的流可避开这组隐式同步。Per-thread 默认流按主机线程及上下文区分，与 legacy 混用仍需看同步规则。本例用页锁定缓冲区实现常规显式拷贝的重叠条件。对 pageable 缓冲区，`cudaMemcpyAsync` 可能阻塞主机或因 staging 引入流同步，须区分内存类型和方向。软件栈初始化与物理链路分别留给第 03、04 章。

**支撑材料**

- 用 CUDA 13.2.1 文档核对 `--default-stream per-thread`、`cudaStreamCreateWithFlags(..., cudaStreamNonBlocking)`、`cudaEventRecord`、`cudaStreamWaitEvent` 和 `cudaMemcpyAsync` 的语义。拟用最小调用序列作伪代码，标出 CPU 线程、Stream 与 Event。按 Runtime API 的同步条款界定 pageable 行为。 [CUDA 13.2.1 · Asynchronous Execution](https://docs.nvidia.com/cuda/archive/13.2.1/cuda-programming-guide/02-basics/asynchronous-execution.html) · [Runtime API · Default Stream](https://docs.nvidia.com/cuda/archive/13.2.1/cuda-runtime-api/stream-sync-behavior.html) · [Runtime API · API Synchronization Behavior](https://docs.nvidia.com/cuda/archive/13.2.1/cuda-runtime-api/api-sync-behavior.html) · [Runtime API · cudaDeviceProp](https://docs.nvidia.com/cuda/archive/13.2.1/cuda-runtime-api/structcudaDeviceProp.html) · [Runtime API · Event Management](https://docs.nvidia.com/cuda/archive/13.2.1/cuda-runtime-api/group__CUDART__EVENT.html)

## 05 从显存、利用率和作业记录判断瓶颈

**问题与预期结论**　GPU 利用率接近 100% 时作业仍可能访存受限，利用率偏低时也需要查明哪条依赖让设备闲着。读完能定位作业耗时，再选与假设匹配的指标，给出当前判断、适用区间和下一项验证。

**解释顺序**

1. 按 GPU UUID、进程/作业、设备状态和批次范围对齐采样。区分 `memory.used` 的字节量、`utilization.gpu` 采样期内有 Kernel 运行的时间占比，以及 `utilization.memory` 采样期内全局设备内存读写的时间占比。设备采样期随产品而变，外部轮询间隔另计。本例用非 MIG 单卡。再区分第 01 节的 Warp 驻留比与 Kernel 计算效率，后者拟用「完成的 FLOP / Kernel 时长」相对匹配精度和指令路径的参考峰值来表述。
2. 先看端到端批次时间，再按时间线拆出 CPU 准备、拷贝、执行和同步，确认哪段在关键路径上。若耗时主要落在 Kernel 内，结合算术强度、有效吞吐、DRAM 流量与计算管线判断它接近哪条上界。高 HBM 吞吐与低计算吞吐支持带宽限制，高匹配计算吞吐且访存有余量支持计算限制。两项都低时，补查 Warp 就绪/停顿、访存延迟、工作规模与频率。峰值比较以同一 Kernel、同一口径为前提。
3. 若 Kernel 间有空档，查看输入就绪、H2D、CPU launch 和同步区间。用提前备好同样的主机输入作单变量对照，固定 batch、dtype、拷贝路径和 Kernel。对比空档与测量窗口内耗时的变化，判断数据供给是否在关键路径上。只凭空档还需区分数据准备、提交不足与同步依赖。I/O 和通信的进一步取证分别交给第 09、08 章，采集部署与故障定位留给第 17—18 章。
