## 01 同一段数据，Socket 和 RDMA 各经过哪里

**问题与预期结论**　跨机拷贝时两种方式都用网卡 DMA，为什么 CPU 参与程度仍会不同？读完能沿默认数据路径逐段标出复制、DMA、协议处理和通知，判断哪段工作会被卸载，以及哪些 CPU 成本仍随提交、轮询或通知而变化。

**解释顺序**

1. 先走 Linux 常规 `send` / `recv` 的 TCP 主机内存路径。发送端从用户缓冲区复制到内核网络缓冲区，内核 TCP/IP 栈和网卡驱动准备发送，网卡 DMA 取走载荷。接收端网卡 DMA 落入主机接收缓冲区，经驱动与内核协议栈处理，再复制到接收进程的用户缓冲区。明确网卡 DMA、CPU 复制与协议处理是三类动作。
2. 在同一对主机上替换为硬件 RDMA。应用先经内核准备资源和内存，稳态时用户态 provider 提交工作、通知网卡，RNIC 处理 RDMA 传输并对已注册的用户缓冲区做 DMA，应用读取完成。把 CPU 的建连、注册、发起和回收标在控制线上。轮询仍可占用 CPU，硬件快路径与无 CPU 开销分别判断。
3. 改变条件再重走路径。TCP 校验和、分段卸载改变协议开销，`MSG_ZEROCOPY` 可避免部分发送复制，仍可能退回复制且需要处理缓冲区回收通知。软件 RDMA 保留 Verbs 接口，硬件卸载结论限定在本章的 RNIC 主例。两端的数据移动与下节的资源管理分开，线上的封装留给第 07 章。

## 02 网卡凭什么能访问进程的缓冲区

**问题与预期结论**　应用把一个指针交给网卡，为什么还要注册内存、创建队列并绑定保护域？读完能从一条工作请求找到它所用的缓冲区、访问权限和完成去处，判断一个地址即使落在正确范围内，为什么仍可能被拒绝。

**解释顺序**

1. 从设备上下文展开对象关系。Verbs 是操作接口，保护域（PD）将本地队列对（QP）、内存区域（MR）等资源关联起来。QP 有发送队列和接收队列，分别关联相应的完成队列（CQ），队列可共用 CQ。应用提交工作请求（WR），provider 将其表达为设备可执行的队列项，网卡完成后按相应语义生成完成条目（CQE），应用可通过 `ibv_poll_cq` 取得工作完成记录（WC）。
2. 用普通主机内存注册解释 MR。驱动通常固定页面并建立设备 DMA 映射，注册声明地址范围、生命周期和访问权限。用一个本地 SGE 讲清地址、长度、`lkey`，再用对端提供的地址与 `rkey` 讲清远程授权。把 QP 的远程访问许可、MR 的权限和范围分开核对。举例说明远程 Write 目标 MR 还须允许本地写，地址与密钥匹配也不能弥补缺失的权限。
3. 追踪提交成功、执行完成、回收缓冲区三个时点。主例采用带完成通知的非 inline 请求。简述 inline Send/Write 的源缓冲区可在提交返回后复用，unsignaled 请求需要按后续完成及队列顺序回收。按需分页 ODP 只标为普通固定页模型的例外。用户态与内核的调用关系在第 04 节补全。

**支撑材料**

- 拟用对象关系图和一段字段级伪配置。B 的 QP 开启远程写，目标 MR 长度为 `4096 B`，访问标志为 `IBV_ACCESS_LOCAL_WRITE | IBV_ACCESS_REMOTE_WRITE`，A 用本地 `lkey` 和 B 提供的远程基址、`rkey`。远程基址加 `3072 B` 后写 `1024 B` 刚好落在范围内，改成 `1025 B` 即越界。再各改单项条件，检查错误 `rkey` 或缺少远程写权限会在哪一层被拒绝。 [rdma-core v57.0 · ibv_reg_mr](https://github.com/linux-rdma/rdma-core/blob/v57.0/libibverbs/man/ibv_reg_mr.3) · [ibv_modify_qp](https://github.com/linux-rdma/rdma-core/blob/v57.0/libibverbs/man/ibv_modify_qp.3)
- 拟用 WR 与 WC 对照表，列 `wr_id`、请求 `opcode`、本地 SGE、远端地址及密钥，以及 WC 的 `status`、`qp_num` 和 `vendor_err`。示例字段取自公开 API，数值为教学输入。WC 出错时只解读手册保证有效的 `wr_id`、`status`、`qp_num`、`vendor_err`。 [rdma-core v57.0 · ibv_post_send](https://github.com/linux-rdma/rdma-core/blob/v57.0/libibverbs/man/ibv_post_send.3) · [ibv_poll_cq](https://github.com/linux-rdma/rdma-core/blob/v57.0/libibverbs/man/ibv_poll_cq.3)

## 03 从连接就绪到 Send、Read 和 Write

**问题与预期结论**　两端都已启动，为何 Send 仍可能等不到接收，普通 Write 成功后接收进程也可能没有事件？读完能根据操作判断缓冲区由谁选择、载荷朝哪边走、双方需要提前做什么，以及谁能看到哪种完成通知。

**解释顺序**

1. 用双端时序先隔开控制与数据。以 `librdmacm` 的 RC 流程说明地址和路由解析、建立 QP、连接握手与事件。应用另行交换 Read/Write 所需的远程地址、长度和 `rkey`，在连接和所需缓冲区就绪后提交载荷。旁注可经普通 Socket 交换建连参数并自行驱动 QP 状态，TCP 控制连接成功只说明这段控制路径可用。QP 状态只保留 `RESET → INIT → RTR → RTS` 的阅读深度，寻址及网络条件留给第 07 章。
2. 用同一对 A、B 和同一长度比较三种操作。A `Send` 给 B 时，B 预贴 Receive 并决定落点，B 有接收完成。A 对 B 做 `RDMA Read` 时，载荷从 B 到 A，由 A 的网卡写入 A 的目的缓冲区。A 对 B 做 `RDMA Write` 时，载荷从 A 到 B，由 B 的网卡写入指定缓冲区。后两者由 A 给出远程地址和 `rkey`，B 预先授权，普通操作无需为每次请求贴 Receive，也不产生对应的远端接收完成。
3. 加入两个变量。Send 遇到接收队列缺项时，RC 可出现 RNR，重试耗尽才用相应错误解释。Write with Immediate 消耗对端一个接收项并给出接收完成，载荷仍写到 WR 指定的远程地址。应用层另有“何时可以消费”的通知约定，GPU 端还须满足第 05 节的顺序要求。其他 QP 类型、原子操作和库级协议留在章外。

**支撑材料**

- 拟画一张两端 Mermaid 时序图，标注 `ADDR_RESOLVED`、`ROUTE_RESOLVED`、`ESTABLISHED` 对应的 RDMA CM 事件，并在 CM 流程之后画出应用交换 MR 元数据、提交与完成。用虚线区分控制信息和实际载荷，解释为什么看到 TCP 或 CM 握手记录仍需要后续 WR/WC 证据。 [rdma-core v57.0 · rdma_cm](https://github.com/linux-rdma/rdma-core/blob/v57.0/librdmacm/man/rdma_cm.7) · [ibv_modify_qp](https://github.com/linux-rdma/rdma-core/blob/v57.0/libibverbs/man/ibv_modify_qp.3)
- 拟用四行表比较 Send、Read、Write、Write with Immediate 的发起端、载荷方向、远端缓冲区选择、是否消耗 Receive 和两端完成。配两条教学 WC 变体，`IBV_WC_RNR_RETRY_EXC_ERR` 引向接收队列与重试参数，`IBV_WC_REM_ACCESS_ERR` 引向对端 MR 范围、密钥及权限。具体原因须和对端配置、请求地址及事件记录相互印证。 [NVIDIA · RDMA Aware Networks Programming User Manual v1.7，§3.1](https://docs.nvidia.com/rdma-aware-networks-programming-user-manual-1-7.pdf) · [rdma-core v57.0 · WC 状态定义](https://github.com/linux-rdma/rdma-core/blob/v57.0/libibverbs/verbs.h)

## 04 一条 Verbs 请求由哪些软件和固件接力

**问题与预期结论**　网卡已经有普通网络接口，为什么 RDMA 程序仍可能打不开设备？读完能把应用、用户态 provider、内核 RDMA 驱动和网卡固件的版本证据分别归位，并根据卡在哪一层决定下一项检查。

**解释顺序**

1. 用 ConnectX 画一张职责图。应用经 `libibverbs` 走通用接口和 mlx5 用户态 provider，资源操作通过 `ib_uverbs` 等内核接口进入 RDMA 核心与设备驱动。`mlx5_core` 提供设备核心支持，`mlx5_ib` 承担 RDMA 设备侧的内核支持。用户态典型快路径对映射队列和门铃操作，RNIC 硬件执行工作队列、协议与 DMA，设备固件参与初始化、资源与功能管理。`librdmacm` 单列为可用的建连接口。
2. 区分发行版随内核提供的 inbox 驱动、配套用户态库，以及 MLNX_OFED、DOCA-OFED 厂商发行的组合。普通硬件 RDMA 可用受支持的 inbox 组合。选择依据是目标功能、实际模块和库的来源、内核 ABI 与厂商对 NIC 型号及固件版本的支持。用同名 `mlx5_ib` 在两个软件栈中都可出现，说明模块名只能标识组件，包归属及版本才能说明来源。
3. 按“PCI 枚举和绑定 → RDMA 设备与端口 → 用户态能打开 → 端到端请求完成”分层读证据。内核升级或换包时重新核对已运行的版本。模块安装、固件刷写、Operator 接管与回滚流程分别留给第 13、19 章。

## 05 RDMA 如何从主机缓冲区走到 GPU 显存

**问题与预期结论**　主机内存 RDMA 已经跑通，两端的训练数据却都在 GPU 上。读完能说明换用 GPUDirect RDMA 时省去了哪些拷贝、为什么显存也要注册，以及如何判断本地 GPU 或网卡何时可以使用缓冲区。

**解释顺序**

1. 用 A 发给 B 的同一次 RDMA Write 对照两条完整路径。中转路径先将 A 的显存拷入 A 的页锁定主机缓冲区，NIC 从主机缓冲区取数，B 的 NIC 将数据写入 B 的主机缓冲区，再拷入 B 的显存。直达路径在两端都使用已注册的 GPU 缓冲区，A 的 NIC 经 PCIe peer DMA 读 A 的显存，B 的 NIC 经 PCIe peer DMA 写 B 的显存。发起端与接收端分别判定，允许一侧直达、另一侧中转。
2. 解释地址转换和生命周期。GPU 虚拟地址需由 GPU 驱动和 RDMA 驱动合作建立设备可用的映射，再由 MR 提供访问边界。用 BAR1 作本章 PCIe 路径的映射窗口例，交代映射资源与显存容量是两种口径。DMA-BUF 和 Peer Memory 先标在注册位置，两种路径如何满足支持条件在下一节展开。
3. 用双端时序说明先后关系。A 的 GPU 产生载荷后，应用先以适用的 CUDA 同步确保 NIC 可以读取。B 的应用在获得协议规定的完成信号并建立适用的 CUDA 内存顺序后，才提交依赖该数据的 GPU 工作。点出运行中的 GPU Kernel 并发访问仍在被 NIC 写入的区域可能读到旧值或部分结果。CPU 继续参与资源管理和通知，是否回退中转取决于上层实现。NCCL 的自动选择与日志留给第 08 章。

**支撑材料**

- 拟画一张同布局双栏图，左栏突出两块主机中转缓冲区，右栏突出两端各自的 NIC 与 GPU 显存之间的 PCIe 路径。用教学算例标清数量关系。单向载荷 `8 MiB`，两端各做一次 staging 时，共增加 `16 MiB` 的 GPU↔主机拷贝载荷，直达省去这两段。两种路径的跨网有效载荷都是 `8 MiB`，数值省略协议头、重传和其他内存访问，耗时另受方向、拓扑和重叠程度影响。 [CUDA 13.1.2 · GPUDirect RDMA 概述与 PCI BAR](https://docs.nvidia.com/cuda/archive/13.1.2/gpudirect-rdma/index.html)
- 拟画四事件时序，依次标 GPU 生产完成、NIC 读取、远端写入完成的通知、依赖 Kernel 的提交。用 CUDA 文档里的并发读取例核对“NIC 写事务与 GPU 可见性”的边界，普通 Write 的通知沿用第 03 节的显式协议假设。 [CUDA 13.1.2 · Synchronization and Memory Ordering](https://docs.nvidia.com/cuda/archive/13.1.2/gpudirect-rdma/index.html#synchronization-and-memory-ordering)

## 06 如何判断一对 GPU 与 NIC 支持直达

**问题与预期结论**　`nvidia-smi topo -m` 显示 `PIX`，系统也装好了驱动，为什么仍可能注册失败或只能中转？读完能按“硬件路径、DMA 映射、驱动与 API、实际注册”逐项检查，并为特定平台组合区分必要条件和现场证据。

**解释顺序**

1. 用 BDF 把 GPU、NIC 和上游桥对回 PCIe 树，对照同 Switch、经过 Host Bridge、跨 Socket 三种路径。`PIX`、`PHB`、`SYS` 表示距离类别，同 NUMA 节点仍需核对 Root Complex 和桥路由。对传统 PCIe 路径用 CUDA 的共享上游 Root Complex 要求和平台限制解释为什么跨 Socket 风险更高，读、写方向的能力与性能分别验证。
2. 在同一张树上分辨 IOMMU 与 ACS 的影响。IOMMU 处理设备 DMA 的地址转换与隔离，CUDA 13.1.2 说明其所述传统路径要求设备看到一致的地址，核对实际是否为一一映射或直通。ACS 的 P2P Request/Completion Redirect 可将事务送上游，需对照路径上各桥的 `ACSCtl`，单看 `SrcValid+` 无法确定重定向。把固件与平台支持、内核启动意图、运行态域类型分栏。虚拟化及专用平台按各自支持矩阵判断，本章用只读输出说明检查逻辑。
3. 并排走显存注册的两条链。DMA-BUF 从 CUDA 导出指定分配的 fd，再由 RDMA provider 经 `ibv_reg_dmabuf_mr` 导入并注册。Peer Memory 由 `nvidia-peermem` 向带相应 peer-memory 接口的 RDMA 栈提供 GPU 内存支持，应用走相应注册路径。按 GPU 与分配类型、GPU 内核模块、Linux 内核、NIC 驱动及固件、用户态 provider、测试程序构建六列核对。模块已加载、CUDA 报告可导出、MR 注册成功和传输成功分别记录。

## 07 用两轮测试把判断落到证据上

**问题与预期结论**　管理地址能通、RDMA 端口 `ACTIVE`，还缺哪些证据才可说这一对节点能直接从显存向显存传输？读完能用两轮对照缩小问题范围，核对结果的测量口径，并说出下一项证据。

**解释顺序**

1. 先收齐双端卡片。记录控制面地址、测试 RDMA 设备与端口、GPU 序号和 BDF、链路类型、端口状态、软件及固件版本、NUMA 放置。TCP 建连记录只覆盖相应的控制地址和端口。以同一对端口运行主机缓冲区 `ib_write_bw`，将测试参数和实际输出的连接类型、方向、消息大小与迭代数对上。
2. 保持同样的方向、端口、MTU、消息大小、QP 数与发送深度，第二轮在两端换成显存缓冲区，用同一个 CUDA / DMA-BUF 构建显式选用 `--use_cuda=<本地序号> --use_cuda_dmabuf`。记录显存设备选择、导出和注册路径及传输结果。两轮各自能证明的是所测操作、端点、方向和缓冲区类型。反向性能、数据内容校验、集合通信效率分别需要额外证据。
3. 用三种教学结果收束。主机轮在建连或传输时失败，先区分控制建连、RDMA 路径和本地权限。主机轮成功、显存轮在 MR 注册时失败，沿 GPU 缓冲区类型、导出、NIC 导入和映射条件缩小范围。两轮成功但显存轮较慢，先核对同一测量口径，再用 NIC 读 GPU 与 NIC 写 GPU 的方向对照及设备路径补证。生产基线与拥塞诊断留给第 17、18 章。

## 提请审查的取舍

- **案例是否要求实测**　建议正文先以可复算的双节点教学记录交付，配经上游资料核对的命令骨架。若希望双节点实测成为正文验收条件，需确定可使用的环境或现有记录，再锁定平台和链路配置。
