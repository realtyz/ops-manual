# 一次复制的数据从哪里到哪里

CPU 上的线程提交一条复制指令。假如输入已经在主机内存里，GPU 可以用复制引擎通过 DMA 搬运数据。CPU 核心负责运行应用、准备缓冲区和发起操作，复制引擎按驱动提交的工作访问内存。要画这次复制的路径，先确定**源缓冲区的物理位置、目的缓冲区的物理位置，以及实际负责搬运的组件**。 [CUDA 13.2.1 · Asynchronous Execution](https://docs.nvidia.com/cuda/archive/13.2.1/cuda-programming-guide/02-basics/asynchronous-execution.html)

## 从主机内存到 GPU 显存

本章的四卡教学节点是双路 x86_64 Linux 裸机，每个 Socket 对应一个 NUMA 节点。Socket 0 的根端口通过 Switch A 连接 GPU 0、GPU 1 和 NIC 0，Socket 1 的根端口通过 Switch B 连接 GPU 2、GPU 3 和 NIC 1。两个 Switch 各有自己的上行，GPU 之间没有 NVLink。下文用 M0 和 M1 表示两个 NUMA 节点的主机内存。连接与数值均为教学设定。

先看 GPU 0。假设源缓冲区已经锁页，物理页都位于 M0，驱动让复制引擎直接从该缓冲区 DMA 读取。CPU 线程提交 H2D（host to device）复制后，GPU 发出读取请求。有效数据从 M0 经 Socket 0 的内存子系统和 PCIe 根端口，穿过 Switch A 的上行及 GPU 0 的下行，进入 GPU 0 的显存。D2H（device to host）复制则把有效数据从显存送回指定主机缓冲区。H2D 读取请求朝主机内存走，返回的有效数据朝 GPU 走。本章按**有效数据方向**计算带宽。 [CUDA 13.2.1 · Unified and System Memory](https://docs.nvidia.com/cuda/archive/13.2.1/cuda-programming-guide/02-basics/understanding-memory.html)

若同一张 GPU 的源缓冲区位于 M1，数据须先从 Socket 1 的内存子系统经处理器间互联到 Socket 0，然后进入同一条 PCIe 分支。GPU 的接入位置与缓冲区的实际页落点共同决定这段路径。提交线程在哪颗 CPU 上运行，可能影响最初的分配或数据准备，但分析一次已有缓冲区的 DMA 时，应从这些页当时所在的位置出发。 [Linux · NUMA Memory Policy](https://docs.kernel.org/admin-guide/mm/numa_memory_policy.html)

## 锁页影响搬运和完成时点

普通可分页主机内存可以被操作系统换出。对支持注册的已有缓冲区，应用可以在 `cudaHostRegister` 成功后使用注册范围做 DMA。CUDA 也能分配页锁定主机缓冲区。注册成功、复制调用返回和目的数据可安全使用是三个时点。下面只对照 CUDA 13.2.1 的 H2D 复制。 [CUDA 13.2.1 · Memory Management](https://docs.nvidia.com/cuda/archive/13.2.1/cuda-runtime-api/group__CUDART__MEMORY.html)

| 调用及源缓冲区 | 对调用线程可见的行为 | 如何确认复制完成 |
| --- | --- | --- |
| 同步 `cudaMemcpy`，页锁定 | 对主机同步 | 检查调用成功后再使用结果 |
| 同步 `cudaMemcpy`，可分页 | 复制开始前有 Stream 同步。数据进入页锁定暂存区后，调用可在最终 DMA 完成前返回 | 若从主机判断实际完成，等待复制所属 Stream 完成 |
| `cudaMemcpyAsync`，页锁定 | 可异步提交 | 检查提交结果，再检查该 Stream 的同步结果或复制后记录的事件 |
| `cudaMemcpyAsync`，可分页 | 可能对主机同步。若需要暂存，驱动可能先同步 Stream 并复制到页锁定缓冲区 | 确认相应 Stream 或事件完成。估算重叠时要考虑暂存和同步 |

因此，用 CPU 计时器只包住异步调用，可能量到的只是提交时间。即使接口名带 `Async`，能否与其他工作重叠仍取决于实际内存类型、设备能力和 Stream 依赖。 [CUDA 13.2.1 · API Synchronization Behavior](https://docs.nvidia.com/cuda/archive/13.2.1/cuda-runtime-api/api-sync-behavior.html) · [Asynchronous Execution](https://docs.nvidia.com/cuda/archive/13.2.1/cuda-programming-guide/02-basics/asynchronous-execution.html)

## 源和目的都在显存时

若 GPU 0 和 GPU 1 支持并启用了所需的 PCIe P2P，且事务在 Switch A 内转发，有效数据可在两卡的下行之间搬运，避开上行和主机 DRAM。应用也可以显式安排两段复制，先 D2H 把数据放进主机缓冲区，等该段完成后再从缓冲区 H2D。此时同一份数据在每段各搬一次，两张卡依然各自拥有自己的显存。选哪种传输是运行时和应用实现的问题，后续章节再展开框架与通信库如何选路。 [CUDA 13.2.1 · Multi-Device Peer-to-Peer Transfers and Memory Access](https://docs.nvidia.com/cuda/archive/13.2.1/cuda-programming-guide/03-advanced/multi-gpu-systems.html#multi-device-peer-to-peer-transfers-and-memory-access)

| 教学场景 | 有效数据经过的关键位置 | 主机 DRAM 的角色 | 跨 Socket |
| --- | --- | --- | --- |
| 本地 H2D，M0 → GPU 0 | M0 → Socket 0 根侧 → Switch A → GPU 0 显存 | 源 | 否 |
| 远端 H2D，M1 → GPU 0 | M1 → Socket 1 → 处理器间互联 → Socket 0 根侧 → Switch A → GPU 0 显存 | 源 | 是 |
| 本地 D2H，GPU 0 → M0 | GPU 0 显存 → Switch A → Socket 0 根侧 → M0 | 目的 | 否 |
| 同分支 PCIe P2P，GPU 0 → GPU 1 | GPU 0 显存 → Switch A → GPU 1 显存 | 无有效载荷落点 | 否 |
| 显式主机中转，GPU 0 → GPU 1 | GPU 0 显存 → Switch A → 根侧 → M0，再经根侧 → Switch A → GPU 1 显存 | 两段之间的中转缓冲区 | 否 |

以上从已准备好的缓冲区开始。统一内存的页迁移、存储读取和 NIC 访问显存各有自己的机制与条件。就这张表而言，只要把源和目的画对，下一步便可逐段统计每个方向需要承载的字节数。
