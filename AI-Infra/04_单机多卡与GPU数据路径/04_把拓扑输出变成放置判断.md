# 把拓扑输出变成放置判断

## 先把三个编号空间对齐

`nvidia-smi` 的 index、CUDA 应用的 device ordinal、机箱槽位编号需要分别建立映射。index 是工具当前枚举视图中的序号，ordinal 是应用当前可见设备序列中的序号；过滤、重排或运行环境变化后，两者未必相同。槽位则来自整机标注。UUID 用于维持设备身份，PCI BDF 用于定位当前设备层级。

先获取主机视图。下面是**完整覆盖本章四卡的自拟 CSV**，名称与 UUID 是教学占位；domain 补齐为八位，与导读中的四位写法表达同一个地址。

```text
$ nvidia-smi --query-gpu=index,name,uuid,pci.bus_id --format=csv
index, name, uuid, pci.bus_id
0, 教学 PCIe GPU, GPU-11111111-1111-1111-1111-111111111111, 00000000:41:00.0
1, 教学 PCIe GPU, GPU-22222222-2222-2222-2222-222222222222, 00000000:42:00.0
2, 教学 PCIe GPU, GPU-33333333-3333-3333-3333-333333333333, 00000000:C1:00.0
3, 教学 PCIe GPU, GPU-44444444-4444-4444-4444-444444444444, 00000000:C2:00.0
```

再让应用记录它看到的 ordinal、设备 UUID 与 PCI 地址，通过 CUDA 的设备属性查询建立同一身份记录。本章 P2P 和传输材料已假定完成该核对，ordinal 0—3 恰好对应上述主机 index。这个映射只在本次材料中成立。

例如，另一个进程只按 `GPU-3333…`、`GPU-4444…` 的顺序可见两张卡，其 ordinal 0 可以是物理 GPU2。省略号仅是正文简写，配置时要使用完整 UUID。设备过滤与重排的行为见 [CUDA 12.8.1 编程指南：CUDA Environment Variables](https://docs.nvidia.com/cuda/archive/12.8.1/cuda-c-programming-guide/index.html#cuda-environment-variables)。容器中的具体注入与编号在第 10 章展开。

## 再读拓扑矩阵的每一类关系

以下是**按 `nvidia-smi topo -m` 风格自拟的教学输出**，省略 GPU NUMA ID 等额外列，保留 CPU 和内存 NUMA 亲和；网卡名称的对应由末尾人工整理的 NIC Legend 给出。

```text
        GPU0 GPU1 GPU2 GPU3 NIC0 NIC1 CPU Affinity NUMA Affinity
GPU0     X   PIX  SYS  SYS  PIX  SYS  0-31         0
GPU1    PIX   X   SYS  SYS  PIX  SYS  0-31         0
GPU2    SYS  SYS   X   PIX  SYS  PIX  32-63        1
GPU3    SYS  SYS  PIX   X   SYS  PIX  32-63        1
NIC0    PIX  PIX  SYS  SYS   X   SYS
NIC1    SYS  SYS  PIX  PIX  SYS   X

NIC Legend（教学命名）:
  NIC0: mlx5_0 / 0000:43:00.0
  NIC1: mlx5_1 / 0000:c3:00.0
```

从 GPU2 行读取：与 GPU3 和 NIC1 的关系是 PIX，与 GPU0/GPU1/NIC0 是 SYS；CPU 亲和集合是本例逻辑 CPU 32—63，NUMA 亲和是 Node 1。它支持优先考察同分支的 GPU3/NIC1，以及 Node 1 的主机资源。CPU Affinity 不是“当前进程已经运行在这些 CPU”，NUMA Affinity 也不是“应用页已经分配在这里”。

矩阵关系的含义如下，具体文字与可用列以驱动所附帮助为准，见 [nvidia-smi 官方文档：Topology](https://docs.nvidia.com/deploy/nvidia-smi/index.html)小节。

| 标记 | 连接类别的读法 | 不能直接换算成什么 |
| --- | --- | --- |
| X | 同一设备 | 跨设备传输结果 |
| PIX | 经过单个 PCIe Switch 的近端类别；部分工具图例按 bridge 表述 | P2P 一定成功、某个固定速率 |
| PXB | 经过多个 PCIe 交换/桥接层级，但不经过 PCIe Host Bridge | 精确的实体 Switch 数量与端口预算 |
| PHB | 经过 PCIe Host Bridge | 一定做主机内存中转 |
| NODE | 经过同一 NUMA Node 内 Host Bridge 之间的互联 | 一定与 PHB 等速 |
| SYS | 还经过 NUMA Node 间的处理器互联 | 一定不能 P2P、固定的降速倍数 |
| NV# | 通过一组绑定的 NVLink，# 是该标记报告的链路数量 | # 张 GPU、专属直连、应用有效 GB/s |

NVSwitch 系统上出现 NV#，也不能据此把两 GPU 画成没有交换设备的物理直连。NVLink 矩阵可以配合 `nvidia-smi topo -mp` 查看 PCIe 关系；后者排除 NVLink 视角，不代表把 NVLink 关闭了。本章无 NVLink 的四卡矩阵无需借助这个切换。

## 用 PCIe 树核对它实际指向哪一支

矩阵便于成对阅读，树便于定位共同上游。以下**自拟、删节的 `lspci -D -t` 风格材料**沿用第 01 章地址，末尾用途由人工添加：

```text
-[0000:00]---01.0-[3f-43]----00.0-[40-43]--+-01.0-[41]----00.0  GPU0
                                          +-02.0-[42]----00.0  GPU1
                                          \-03.0-[43]----00.0  NIC0
-[0000:80]---01.0-[bf-c3]----00.0-[c0-c3]--+-01.0-[c1]----00.0  GPU2
                                          +-02.0-[c2]----00.0  GPU3
                                          \-03.0-[c3]----00.0  NIC1
```

GPU2 的地址为 `0000:c1:00.0`，从 `[c1]` 下的叶子往上回溯，与 GPU3/NIC1 汇合到同一交换结构，再进入根总线 `0000:80` 分支。结合整机图，把它命名为 Switch B。这里的 `bf:00.0` 是该交换结构的上行端口，`c0:01.0` 等是下行端口；不应把每个桥 Function 都数成一颗独立的实体 Switch。

再读 `cat /sys/bus/pci/devices/0000:c1:00.0/numa_node`，本例教学返回值为 `1`，与矩阵一致。若返回 `-1`，含义是归属未知，不能当作 Node 0；内核字段语义见 [Linux PCI sysfs ABI：numa_node](https://www.kernel.org/doc/Documentation/ABI/testing/sysfs-bus-pci)。BDF 的十六进制总线号只帮助定位树，不按数值差表示物理距离。

到此得到可操作的定位链：**UUID → 当前 BDF → 交换分支/上行端口 → NUMA Node → 逻辑 CPU 集合**。如果还要让现场找到卡，应继续接上整机槽位表。

## 亲和要对齐线程、主机页和设备

考虑 GPU0 从一个 1 GB 锁页缓冲读取输入。以下是**独立三次运行的自拟条件表**，每次缓冲准备完成后才开始计时，不改变 GPU 或 PCIe 状态：

| 运行 | CPU 工作线程 | 源缓冲物理页 | M→GPU0 的数据路径 |
| --- | --- | --- | --- |
| A | Node 0 | M0 | 本地内存/I/O → 上行 A → GPU0 |
| B | Node 0 | M1 | 仍跨 Socket 取 M1，再走上行 A |
| C | Node 1 | M0 | DMA 的源页仍在 M0；CPU 预处理可能远端访问 M0 |

DMA 路径主要跟源页和设备位置走，CPU 预处理则跟线程与页的位置走。若只关心缓冲已就绪后的 H2D，不能因为 C 的线程远就断言 DMA 必定绕行 Node 1。若关心整轮耗时，则还要把 C 的预处理远端访问纳入时间线。

默认本地分配策略下，匿名页常在首次触碰分配时靠近执行线程；显式内存策略、cpuset 允许集合与后续迁移等会改变结果。`taskset` 只约束 CPU，不约束内存页位置；`numactl --cpunodebind` 与 `--membind` 分别表达 CPU 和内存的节点要求。给进程设置新策略也不会自动迁移已经分配好的所有页。机制见 [Linux NUMA Memory Policy](https://www.kernel.org/doc/html/latest/admin-guide/mm/numa_memory_policy.html)，选项见 [numactl 官方手册源码](https://github.com/numactl/numactl/blob/master/numactl.8)。

未来有环境时，应先建立策略，再分配、触碰和锁定缓冲，并核对实际页位置。`numactl --show` 用于读策略，`numastat -p <PID>` 可观察进程页分布；后者是进程汇总，不能单凭总页数断言某个源缓冲全在指定 Node。需要定位具体缓冲时，还应关联地址范围与 `/proc/<PID>/numa_maps` 等材料。不能用“设置命令成功”代替“缓冲位置已确认”。

## GPU 与 NIC 的近，意味着优先核对哪一对

GPU2 与 NIC1 同在 Switch B 下，GPU0 与 NIC0 同在 Switch A 下。这为设备配对提供候选关系：若未来使用直接访问路径，同分支配对有机会减少经过根侧或 Socket 间的流量；如果使用主机缓冲，还应把 NIC 访问的缓冲与 GPU 输入缓冲一起放回图中。

单凭 PIX 和 RDMA 网卡名称，仍不能推导出网卡可以直接访问 GPU 显存。GPU—GPU P2P 与 GPUDirect RDMA 的设备组合和依赖不同，第 06 章会补齐内存注册、网卡与 GPU 驱动协作、地址映射等条件。这里已经完成的判断是“优先检查 GPU2—NIC1 这一候选配对及其共享上行”，而不是提前承诺网络性能。

放置还要考虑整项作业：同分支两卡有利于卡间交换，却共用一条主机上行；跨分支有利于分散 H2D，却可能让卡间交换变远。下一篇用同一套材料比较这些取舍。
