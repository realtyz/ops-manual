
GPU 0 和 GPU 1 共用 Switch A 的上行，从主机并发接收输入时要共享带宽。GPU 0 和 GPU 2 可以分别使用 A、B 两条上行，但本例跨分支交换需要经主机内存中转。要决定一轮作业该用哪对卡，先确认每阶段何时完成，再比较阶段之间的依赖。

## 单路与并发吞吐的测量口径

同一组对照应记录实际 GPU 的 UUID、BDF 和进程内序号，确认源、目的、有效数据方向、字节数、复制方式、主机缓冲区类型及实际页落点。初始化、分配、锁页和预热放在计时窗口外，同组对照使用相同的测量边界。单路吞吐用有效字节数除以该路实际耗时，并发总吞吐用总交付字节数除以共同起点到最后一路完成的时间。若关心整段并发耗时，可用同一个主机时钟计时，并等待两张卡的相关 Stream 完成。完成后校验目的数据，记录中同时保留单路完成时间与共同完成时间。 [CUDA 13.2.1 · 异步执行与同步范围](https://docs.nvidia.com/cuda/archive/13.2.1/cuda-programming-guide/02-basics/asynchronous-execution.html) · [多设备事件和 Stream 行为](https://docs.nvidia.com/cuda/archive/13.2.1/cuda-programming-guide/03-advanced/multi-gpu-systems.html#multi-device-stream-event-and-memory-copy-behavior)

以下是双路四卡节点的**教学记录**。上行和 GPU 下行按健康的 Gen4 x16 场景，单方向有效预算设为 `25 GB/s`。主机缓冲区均锁页，同向并发共用上行时假设均分预算，独走上行时其余资源充足。每路交付 `1 GB`（`10⁹ B`）。各行均假设完成并通过数据校验。

| 复制记录 | 路径和同时运行的工作 | 共同完成时间 | 有效吞吐 |
| --- | --- | ---: | ---: |
| M0 → GPU 0，或 M0 → GPU 1，或 M1 → GPU 2 | 三次独立的本地 H2D 单测 | 各 40 ms | 各 25 GB/s |
| M0 → GPU 0，M0 → GPU 1 | 并发 H2D，同向共用上行 A | 80 ms | 各 12.5 GB/s，合计 25 GB/s |
| M0 → GPU 0，M1 → GPU 2 | 并发 H2D，分别走上行 A、B | 40 ms | 各 25 GB/s，合计 50 GB/s |
| GPU 0 → GPU 1 | 已确认在 Switch A 内走 PCIe P2P | 40 ms | 25 GB/s |
| GPU 0 → GPU 2 | 两段串行。先 D2H 写 M0，再跨 Socket 从 M0 做 H2D | 90 ms | 约 11.11 GB/s |

同分支并发在上行 A 的同一方向交付 `2 GB`，所以总吞吐为 `2 GB ÷ 0.08 s = 25 GB/s`。使用两条上行后，同样字节数在 `0.04 s` 内到达，得到 `50 GB/s`。同分支的结果符合共享上行的模型。遇到类似实测，仍要核对负载下的上行 `LnkSta`、各缓冲区的页落点与实际并发窗口。链路或内存流量可以进一步区分上行饱和和主机内存一侧的争用。

最后一行的本地 D2H 为 `25 GB/s`，远端 H2D 整条路径设为 `20 GB/s`。完整中转耗时为 `1/25 + 1/20 = 0.09 s`。最终向 GPU 2 交付 `1 GB`，因此得 `1/0.09 ≈ 11.11 GB/s`。模型给定的远端速率适用于这里这条路径，拓扑标签 `SYS` 只描述路径类别。

## 主机输入量与卡间交换量决定放置分界

现在每轮先让两张卡同时接收各 `1 GB` 本地输入，两路都完成后，GPU 0 再向另一张卡交付 `S GB`。忽略两种放置中相同的计算耗时和固定开销，跨分支依旧使用 M0 整块中转，所有路径沿用上表的有效速率。

- **GPU 0 + GPU 1** 的输入耗时为 `80 ms`，交换耗时为 `1000 × S/25 = 40S ms`。一轮比较时间为 `80 + 40S ms`。
- **GPU 0 + GPU 2** 的输入耗时为 `40 ms`，交换耗时为 `1000 × (S/25 + S/20) = 90S ms`。一轮比较时间为 `40 + 90S ms`。

同分支在输入阶段多花 `40 ms`，但每交换 `1 GB` 省 `50 ms`。当 `50S = 40`，两种方案打平，因此分界是 `0.8 GB`。超过该交换量时选同分支更快，低于该交换量时独立上行占优。

| 单轮交换量 | GPU 0 + GPU 1 | GPU 0 + GPU 2 |
| --- | ---: | ---: |
| 1 GB | 120 ms | 130 ms |
| 0.1 GB | 84 ms | 49 ms |

如果每卡输入增加到 `2 GB`，且其他模型条件保持，输入阶段的差距变成 `80 ms`，分界移到 `1.6 GB`。如果输入尚在进行时就能交换，阶段时间就可能重叠。需按数据依赖和共享资源重新排时间线，比较最后一个必需操作何时完成。消息足够小时，也需把提交和同步等固定开销纳入估算。

## P2P 功能测试和带宽矩阵的判读

NVIDIA 的 NCCL 排查文档给出一段 `simpleP2P` 的节录。样例让两张 GPU 分别执行访问对端显存的 Kernel，随后将结果拷回主机校验。输出中的 `Test passed` 对应本次运行所覆盖的访问和数据校验。该节录用于说明怎样看见功能证据，记录中的带宽需结合硬件和构建环境才能复现。 [NCCL 2.31.2 · GPU-to-GPU Communication](https://docs.nvidia.com/deeplearning/nccl/archives/nccl_2312/user-guide/docs/troubleshooting/gpu_troubleshooting.html#gpu-to-gpu-communication)

NVIDIA 的 `nvbandwidth` **v0.10.0** 可用复制引擎（CE，Copy Engine）或运行在流式多处理器（SM，Streaming Multiprocessor）上的 Kernel 搬运数据。以下命令在已构建该版本且具备相应设备能力、驱动和 P2P 权限时选取两个用例。`-b 512` 的单位是 MiB，带宽输出为十进制 `GB/s`。工具默认检查数据，`--skipVerification` 会跳过校验。计带宽用实际复制大小，SM 用例的实际字节数可能因对齐而调整。 [NVIDIA nvbandwidth v0.10.0 · README](https://github.com/NVIDIA/nvbandwidth/blob/v0.10.0/README.md) · [计时与校验实现](https://github.com/NVIDIA/nvbandwidth/blob/v0.10.0/memcpy.cpp#L512-L550)

```bash
./nvbandwidth --version
./nvbandwidth -l
./nvbandwidth -b 512 -v -t device_to_device_memcpy_write_ce device_to_device_memcpy_read_sm
```

这两个单向用例以发起侧为矩阵行、对端为列。`write_ce` 将行设备的数据写到列设备，`read_sm` 将列设备的数据读到行设备。该版本显示标题的箭头在这两个用例中与有效数据方向相反，读方向要跟踪源和目的，也可用 `-v` 的逐项记录交叉检查。矩阵跳过对角线和未能启用 P2P 的设备对，有效单元逐一测量。要回答并发问题，需要对应的并发用例或自行测共同完成时间。留存实测时应同时保存拓扑、版本、命令、消息大小、方向和原始输出。 [NVIDIA nvbandwidth v0.10.0 · 矩阵与用例](https://github.com/NVIDIA/nvbandwidth/blob/v0.10.0/testcases.cpp#L282-L345) · [源与目的缓冲区顺序](https://github.com/NVIDIA/nvbandwidth/blob/v0.10.0/testcase.h#L75-L110)

## 远端输入、放置选择与互联就绪的综合检验

使用本章的四卡教学节点。跨分支试验中，进程记录 `cuda:0` 对应 `0000:c1:00.0`，`cuda:1` 对应 `0000:41:00.0`。两路输入各 `1 GB`，线程 CPU 亲和已经设在各卡本地，但地址匹配的页记录显示两路 DMA 源均在 M0。上行均为健康的 Gen4 x16。假定同时运行时，本地 H2D 仍可达 `25 GB/s`，远端 H2D 可达 `20 GB/s`，其余资源充足。计算后要将 GPU 0 的 `0.7 GB` 结果送往另一张卡。同分支方案的输入仍均为本地。

1. 还原 `cuda:0` 的物理设备、H2D 载荷路径和就近 NIC 候选。说明怎样用桥树和映射页记录验证该路径。
2. 分别画出直达与中转的卡间路径，比较两种放置的完成时间。将 `cuda:0` 的输入页重新放到本地后，结果怎样变化？若在负载下发现上行 B 实为 Gen4 x8，原题设的 `20 GB/s` 是否仍成立？
3. 保留远端输入。若跨分支交换改成七个 0.1 GB 的块，并假定两段能重叠且各自维持给定速率，用两个锁页缓冲槽轮换，交换最少需要多久？
4. 同分支测试报告对端显存读取及校验通过。要进一步确认载荷留在 Switch A 内，还缺什么？对照另一台 HGX H100，若 A 为 `Completed / Success`、B 为 `In Progress / N/A`，且 FM 为 `active`，还需什么证据才能确认 A、B 的 NVLink 通信可用？

**参考推理**

1. 完整 BDF 对到主机 GPU 2，沿桥树回溯到 Switch B 和 Socket 1。直接用于 DMA 的页在 M0，载荷走 M0 → Socket 0 → 处理器间互联 → Socket 1 根侧 → 上行 B → GPU 2。按地址对照 `maps`、`numa_maps` 和锁页缓冲的实际范围，核对采样与传输使用同一批页。NIC 1 与 GPU 2 同在 B 下，是近端候选。
2. 同分支输入共用上行，耗时 `80 ms`。结果从 GPU 0 经 Switch A 直达 GPU 1，耗时 `0.7/25 s = 28 ms`，合计 `108 ms`。跨分支的输入以较慢的远端一路完成为准，`max(40, 50) = 50 ms`。交换先经 A 写入 M0，再从 M0 跨 Socket 经 B 交付 GPU 2，两段分别为 `28 ms` 和 `35 ms`。本轮合计 `113 ms`。GPU 2 的输入页回到 M1 后，两路输入共同耗时降为 `40 ms`，交换的 M0 中转保持原设定，总计 `103 ms`，选择随之反转。若 B 上行只有 Gen4 x8，其编码后单向上界约 `15.75 GB/s`，经过 B 的 `20 GB/s` 假设失效，需重新建立有效预算。
3. 第一块先用 `4 ms` 写入 M0。此后较慢的 H2D 连续耗用 `7 × 5 = 35 ms`。D2H 提前准备下一块并等待上一槽读完再复用，理想交换时间为 `39 ms`，本轮合计 `89 ms`。
4. 直接访问并校验成功验证了访问功能。要归因到 Switch A 内部转发，还要核对路径上各桥的重定向配置，并在平台支持时对照目标下行与公共上行的流量。HGX H100 的观察中，A 已注册，B 尚在注册，服务状态说明 FM 在查询时运行。待 B 的 `State` 和 `Status` 显示注册成功，再核对设备对所需方向的 NVLink P2P 能力，实际执行并校验传输。若应用可回退，还需用测试实现或相关链路观测确认选用了 NVLink。

从缓冲区与设备的位置可以画出候选路径，从能力、配置和测试材料可以确定哪条路径有依据。再把每轮要走这些路径的字节按方向和依赖记账，才能解释为什么同一对 GPU 在不同作业中可能有不同的放置收益。第 05 章将从作业的计算与显存需求推导为什么要交换这些数据，第 08 章再解释通信库如何为实际交换选择传输。
