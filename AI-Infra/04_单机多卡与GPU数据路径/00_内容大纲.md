# 第 04 章 单机多卡与 GPU 数据路径｜写作大纲

**审查状态**　已获批准。正文按以下六节拆为六篇。

## 范围、前置与学习结果

- **范围**　以 x86_64 Linux 裸机、整卡使用的 NVIDIA 独立 GPU 为主。从已准备好的主机输入缓冲区或源卡显存出发，追踪 H2D、D2H、GPU 间直达和经主机内存中转的路径。计算 PCIe 单向链路和共享上行的预算，用拓扑和运行证据判断 GPU、CPU、内存及 NIC 的放置。另用 HGX H100 八卡平台讲 NVLink、NVSwitch 和 Fabric 就绪。
- **必要前置**　认识第 01 章的 PCIe 根端口、Switch、BDF 与 NUMA，第 02 章的独立显存、Stream 和异步完成，第 03 章的 CUDA 应用选卡与驱动分层。首次使用处补足 DMA、页锁定、链路方向和进程内设备序号。读者用给定材料推导，无需 GPU 实验环境或 CUDA 编程经验。
- **读完应能独立解释**　画出一次本地或跨 NUMA 的主机到 GPU 传输，以及同一对 GPU 的两条候选路径。指出谁发起操作、有效数据向哪里流、是否进入主机 DRAM，以及哪些链路被共享。分别说明设备可见、链路已建立、P2P 可用、Fabric 注册成功和指定测试正确完成各需要什么证据。
- **读完应能独立判断**　给定拓扑矩阵、PCIe 树、链路字段、设备身份和传输记录，能还原进程内序号对应的 GPU，算出指定方向的链路上限和并发下界，比较两种设备放置，并指出区分共享上行、远端缓冲区和中转路径还缺哪一项观测。
- **跨章边界**　GPU 内部执行与 Stream 通用语义归第 02 章，驱动加载和 CUDA 兼容性归第 03 章。第 05 章解释作业为何交换数据，第 06 章展开 GPUDirect RDMA，第 07 章展开跨节点互联与机架级 NVLink 域，第 08 章解释 NCCL 选路，第 09 章解释存储供给。容器编号与 Kubernetes 放置分别留到第 10、13、15 章，生产诊断和交付流程归第 17—19 章。

**贯穿材料**　另设一台四卡教学节点。Socket 0 / NUMA 0 下的 Switch A 接 GPU 0、GPU 1、NIC 0，Socket 1 / NUMA 1 下的 Switch B 接 GPU 2、GPU 3、NIC 1。A、B 各有独立上行，GPU 间无 NVLink。每条 GPU 下行与 Switch 上行在健康负载下设为 Gen4 x16。预算题另给每段每方向 `25 GB/s` 有效预算，跨 Socket 段的示例速率单独给定。设备身份、P2P 成对能力和测试结果均为教学设定。HGX H100 材料独立标注平台与出处。CUDA 机制沿用第 03 章的 13.2.1 归档基线，PCIe 预算覆盖 Gen3—Gen5。动态官方文档核对日期为 2026-11-10。

**叙述顺序**　先画数据路径，再算每段能搬多少。接着分清 CUDA 如何获得 GPU 间直达能力，以及 NVSwitch 平台如何达到互联就绪。读者有了这些判据，再用命令输出还原设备位置，最后根据传输记录和负载阶段比较放置方案。

## 01 一次复制的数据从哪里到哪里

**问题与预期结论**　应用在 CPU 上调用复制接口，数据是否就经过 CPU 核心？读完能根据源和目的内存、缓冲类型及设备位置画出数据路径，并指出何时需要主机缓冲区。

**解释顺序**

1. 从页锁定的本地主机缓冲区开始。CPU 线程提交 H2D，GPU 侧复制引擎通过 DMA 访问主机缓冲区，数据经内存控制器、PCIe 根端口、Switch 和下行进入目的显存。对照 D2H 的有效数据方向，单独标记提交、DMA 访问与同步完成。后续算例一律按有效数据方向记账。
2. 将源缓冲区换成可分页内存，交代 CUDA 在适用的复制调用中可能先暂存到页锁定内存，CPU 可见的返回时间也随 API 与参数改变。再固定一块直接用于 DMA 的页锁定缓冲区，把源页放到远端 NUMA 节点，观察多出来的处理器互联。页的实际落点留给第 05 节验证。
3. 将源换成另一张卡的显存，画出设备间直接传输与显存 → 主机 DRAM → 目标显存两条候选路径。显存仍各自归属各卡。中转以显式 D2H 再 H2D 为教学对照，具体框架如何回退留给第 08 章。GPU 内部访存、统一内存迁移和存储入口只交代适用边界。

**支撑材料**

## 02 沿 PCIe 路径算单向与并发带宽

**问题与预期结论**　每张 GPU 都协商到 x16，为什么单路正常、两卡并发却变慢？读完能把链路代际、宽度和流量方向转换成预算，找到可能限制单路或并发的那一段。

**解释顺序**

1. 从 GPU 端点沿下行、Switch 上行追到根端口。逐段对比支持能力与当前协商速率和宽度，说明只看端点会漏掉上游窄链路，空闲时的速率快照也要与负载下读数区分。
2. 对 Gen3—Gen5 用 `每 Lane 的 GT/s × Lane 数 × 128/130 ÷ 8` 计算编码后单向上界。再区分协议开销后的有效载荷、双向合计与应用实测，明确 `GB/s` 用十进制。单路由沿途最小预算约束，多路按每段、每方向分别加总。不同方向各有链路容量，内存和复制引擎仍可能同时受限。
3. 用共同完成时间推导下界。两路同向流过一条上行时用总字节数除以上行预算。两路走独立上行时，仍须给定主机内存等其余资源足够。整块中转用两段时间相加，分块流水只在两段可重叠且资源、缓冲和依赖允许时改变耗时。硬件计数器与系统压测留给第 17 章。

**支撑材料**

- 拟用一组教学 `lspci -D -t` 和 `lspci -D -s <BDF> -vv` 片段，沿树逐段配对 `LnkCap`、`LnkSta` 的 `Speed`、`Width`，另设一个负载下 `16 GT/s x8` 的窄上行变体。用 `nvidia-smi -q` 的 `Current` 与 `Max` 辅助解释空闲和负载读数。PCI-SIG 的速率与编码资料支持复算 Gen4 x16 约 `31.51 GB/s`、Gen4 x8 约 `15.75 GB/s`、Gen5 x16 约 `63.02 GB/s` 的单向上界。 [pciutils · lspci 手册](https://github.com/pciutils/pciutils/blob/master/lspci.man) · [pciutils · PCIe 字段解码源码](https://github.com/pciutils/pciutils/blob/master/ls-caps.c) · [NVIDIA SMI · GPU Link Information](https://docs.nvidia.com/deploy/nvidia-smi/) · [PCI-SIG · 速率与编码表](https://pcisig.com/sites/default/files/files/PCI-SIG-Seamless_Transition_to_PCIe_5.0_in_System_Implementations_FINAL.pdf)
- 拟用共享上行 A 做反例。两路各送 `1 GB`，同向预算 `25 GB/s`，共同完成时间至少 `80 ms`。各走独立上行且其余条件充足时，对照下界为 `40 ms`。反向 D2H 单列预算，公平分配只有在题设给定时才用于推算每路速率。 [PCI-SIG · 每方向速率](https://pcisig.com/sites/default/files/files/PCI-SIG-Seamless_Transition_to_PCIe_5.0_in_System_Implementations_FINAL.pdf)

## 03 GPU 间怎样获得直达访问

**问题与预期结论**　两张卡接在同一个 Switch 下，或者调用了 `cudaMemcpyPeerAsync`，可以断定数据直达吗？读完能按设备对和访问方向，区分候选物理路径、CUDA 能力、启用结果和实际传输证据。

**解释顺序**

1. 先分开复制与远端显存访问。前者把数据放入目标显存，后者让本卡 Kernel 对另一张卡的分配发出访问。以普通 `cudaMalloc` 分配为例，先查 `cudaDeviceCanAccessPeer` 的返回值和能力位，再从访问方选中当前设备并调用 `cudaDeviceEnablePeerAccess`。反向访问需要单独启用。以 GPU 0 读取 GPU 1 为例标清访问者、内存所有者和响应数据方向。特殊分配器、原子操作和虚拟地址管理留作专题。
2. 从同 Switch 的 PCIe 候选路径讲到平台约束。若两卡支持且实际在交换机内转发，可避开根侧上行。某些 ACS 重定向设置会使事务走根侧。CUDA 13.2.1 对启用 IOMMU 的 Linux 裸机 PCIe P2P 有明确限制，适用条件与 VFIO 直通场景分开说明。NVLink 也是可能的物理路径，其链路和交换条件由下一节展开。
3. 用一次显式主机中转与已验证的 P2P 对照。先核对方向、API 返回和同步完成，再验目标数据。要确认实际路由还需结合测试实现、适用链路状态或路径计数。框架会否回退、回退至哪种传输交给第 08 章。

**支撑材料**

- 拟列两对设备的方向表。教学设定 GPU 0/1 具备所需的双向能力并成功启用，GPU 0/2 在本例无所需能力。表中将 `cudaDeviceCanAccessPeer` 的返回码与输出值、启用结果、完成结果及校验结果分列，用于说明 `PIX` 或 `SYS` 只能提供物理线索。 [CUDA 13.2.1 · Peer Device Memory Access](https://docs.nvidia.com/cuda/archive/13.2.1/cuda-runtime-api/group__CUDART__PEER.html) · [Programming Systems with Multiple GPUs](https://docs.nvidia.com/cuda/archive/13.2.1/cuda-programming-guide/03-advanced/multi-gpu-systems.html)
- 拟将 `nvidia-smi topo -p2p p` 与选定桥的 `ACSCtl`、`/proc/cmdline` 和内核日志中的 IOMMU 状态放在同一证据表。用途是分开驱动报告的能力与系统实际限制，说明为何还要用数据校验验证。 [NVIDIA SMI · Topology](https://docs.nvidia.com/deploy/nvidia-smi/) · [NCCL 2.31.2 · GPU Troubleshooting](https://docs.nvidia.com/deeplearning/nccl/archives/nccl_2312/user-guide/docs/troubleshooting/gpu_troubleshooting.html)

## 04 NVLink 与 NVSwitch 平台何时就绪

**问题与预期结论**　管理工具能列出八张 H100，NVLink 链路也已训练，为什么仍要检查 Fabric？读完能分开物理连接、链路训练、GPU 注册和应用验证，并判断在哪类平台查 FM 或 NVLSM。

**解释顺序**

1. 对比有 NVLink 直接连接的一对 GPU，与 HGX H100 八卡通过 NVSwitch 连接的场景。分别标出主机 PCIe 和卡间 NVLink，解释交换结构提供的可达性与每卡显存边界。用每张 H100 SXM 的 `900 GB/s` 双向 NVLink 规格说明方向和聚合口径，实际单向复制与 H2D 各有各的路径和预算。
2. 以 HGX H100 八 GPU 裸机为主例。该平台采用第三代 NVSwitch、第四代 NVLink。先区分 PCIe 枚举，再讲 ALI 可在硬件侧训练链路，GPU 仍须向 Fabric 注册以获得 NVLink P2P。交代 FM 与驱动协作配置、监视 Fabric，服务运行和单卡注册成功各自只证明对应层状态。
3. 一张对照表限定平台与版本。HGX B100/B200/B300 八卡等第四代 NVSwitch 平台由 FM 与 NVLSM 协作，NVLSM 负责交换机转发表，FM 负责 GPU 侧路由与 NVLink 配置等。第四代平台的安装文档区分 R620 以前的驱动分支配套与 R620 起独立版本的 FM，仍须核对平台和驱动库依赖。部署步骤、机架级 Fabric 管理和恢复操作留给后续章节。

## 05 从拓扑输出还原设备和 NUMA 位置

**问题与预期结论**　作业日志写的是 `cuda:0`，运维材料写的是 `GPU2`，旁边还有两个 NIC。读完能用同一采集时刻的标识对应到物理设备，判断哪组 CPU、内存和 NIC 是候选，并用缓冲区页落点验证路径。

**解释顺序**

1. 先连接进程内 ordinal、GPU UUID、主机工具 index 与完整 BDF。用 `CUDA_VISIBLE_DEVICES` 按 UUID 重排作例，应用记录 `cudaDeviceGetPCIBusId` 与主机查询表核对，统一 BDF 域号的显示宽度。NIC 按接口名对应到 PCI 设备，同一 NIC 的端口标识和 GPU 标识分开记。
2. 读 `nvidia-smi topo -m` 的设备矩阵、`CPU Affinity`、`NUMA Affinity`，解释 `PIX`、`PXB`、`PHB`、`NODE`、`SYS` 和 `NV#`。需要看纯 PCI 路径时用 `topo -mp`，再用 `lspci -D -t` 与设备 sysfs 追桥。`NV#` 提示由几条 NVLink 组成的连接，`SYS` 描述跨 NUMA 互联的拓扑路径，实际软件可能走另一条路径。两者都要和能力、测试材料合读。
3. 分开线程允许的 CPU、采样时 CPU、目标缓冲区实际驻留页和设备亲和。说明首次触页、内存策略及迁页能改变实际路径。用 GPU 2 到 NIC 1 为 `PIX`、到 NIC 0 为 `SYS` 举例，解释为何前者是就近候选，GPUDirect RDMA 支持性留给第 06 章。用 `numa_node=-1` 提醒继续查平台材料，Kubernetes 拓扑调度留给第 15 章。

**支撑材料**

- 拟给一组可联查的四卡教学片段，包括 `nvidia-smi --query-gpu=index,uuid,pci.bus_id --format=csv`、`topo -m`、PCIe 树、`/sys/class/net/<ifname>/device` 和应用设备表。设本次主机 index 2 的 BDF 为 `0000:c1:00.0`，通过 UUID 把它排到应用 ordinal 0，让读者还原 Switch B、NUMA 1 与同分支 NIC 1。 [NVIDIA SMI · Topology](https://docs.nvidia.com/deploy/nvidia-smi/) · [CUDA 13.2.1 · Environment Variables](https://docs.nvidia.com/cuda/archive/13.2.1/cuda-programming-guide/05-appendices/environment-variables.html) · [Runtime API · Device Management](https://docs.nvidia.com/cuda/archive/13.2.1/cuda-runtime-api/group__CUDART__DEVICE.html)

## 06 用传输记录比较两种放置

**问题与预期结论**　四张卡单测都正常，同分支的两张卡应优先一起用吗？读完能选对照组、复算吞吐和阶段耗时，解释为什么答案会随主机输入量与卡间交换量改变，并给出可区分剩余原因的下一项检查。

**解释顺序**

1. 先定义可比较记录。固定设备对、方向、内存类型与页落点、实际字节数、复制实现、并发与消息大小。初始化、分配与预热放在计时外，计时到对应复制完成，双路并发用共同起点到最后一路完成。校验目标数据，分别记录单路与总吞吐。
2. 对照同分支和跨分支并发 H2D，并核对主机缓冲落在各卡本地节点。再对照同分支 PCIe P2P 和跨分支显式主机中转。把并发总吞吐是否增加、上行的协商状态、设备对能力和测试采用的实现一起读。仅见吞吐下降时，保留主机内存或复制引擎争用等解释，用独立上行对照、内存页证据或链路计数缩小范围。
3. 用先输入、后交换的两阶段作业做一次推演。以每卡各 `1 GB` 本地 H2D 开始，比较卡间交换量变化后的选择。若计算和传输可重叠、消息很小或更换复制方式，就重新核对时间线和固定开销。集合通信与完整基线测量分别留给第 08、17 章。

**支撑材料**

- 拟用自拟教学表固定以下口径。单路 H2D `25 GB/s`，同分支并发 `80 ms` 完成两路，分到独立上行 `40 ms`。同分支 P2P 按 `25 GB/s`，跨分支显式中转先 D2H `25 GB/s`，再从远端缓冲 H2D `20 GB/s`。两段串行且忽略固定开销。交换 `1 GB` 时，两种放置分别为 `80 + 40 = 120 ms` 和 `40 + 40 + 50 = 130 ms`。若交换 `0.1 GB` 且仍沿用稳定速率，则变为 `84 ms` 和 `49 ms`，选择随之反转。这组数用于复算与解释，独立于任何硬件实测。
