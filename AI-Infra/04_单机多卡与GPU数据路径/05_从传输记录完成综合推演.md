# 从传输记录完成综合推演

## 怎样设计一份能够比较的传输记录

拓扑和能力材料说明了候选关系，还需用完成了多少正确数据、花了多少时间来观察实际效果。开始比较前，应固定 GPU UUID 与 BDF、软件和固件版本、设备模式、主机缓冲类型与位置、消息大小、方向、并发和计时范围，并记录是否有其他负载。

单路测试先得到各路径的基线，再做并发测试观察共享资源。P2P 测试应按实现所需的访问方向检查能力与启用结果；需要双向访问时才要求两个方向都成功。随后检查完成状态和接收数据的正确性。能力查询为 1 后，若实际访问或校验失败，就还没有形成可用路径的证据。

未来可以用 CUDA 示例学习相应测试：`bandwidthTest` 用于主机/设备等复制，`simpleP2P` 包含卡间访问与结果验证；`p2pBandwidthLatencyTest` 提供不同模式的矩阵。但矩阵可能包含“未启用 P2P”的传输和设备内复制，对角线不能当作卡间结果。工具模式与矩阵行列需按对应版本源码读取，不能把本章人工表格的方向套给任意工具。参考 [CUDA Samples v12.8：p2pBandwidthLatencyTest 源码](https://raw.githubusercontent.com/NVIDIA/cuda-samples/v12.8/Samples/5_Domain_Specific/p2pBandwidthLatencyTest/p2pBandwidthLatencyTest.cu)。

当前 NVIDIA 也提供专门的 [nvbandwidth](https://github.com/NVIDIA/nvbandwidth)，区分主机—设备、设备—设备以及复制引擎/SM 等用例。工具所需平台条件和用例支持范围应随版本记录。本章不要求构建这些工具；以下提供完整的教学材料供纸面判断。

## 先读结果，再回到路径

以下是**人工编写的结果汇总，不是任何工具的原始输出**。所有传输为 1 GB 单向有效负载，消息准备、锁页、显存分配、初始化与预热已在计时外完成；计时从首个复制开始到相应复制完成。输入 H2D 使用各行指定的 M0/M1，本表中均与目标 GPU 局部对齐；最后一行的卡间中转则明确使用 M0，对 GPU2 为远端内存。每次重复使用相同条件，无其他负载。采用 P2P 的一对设备已成功启用本节设定的双向权限，所有返回值和数据校验通过。

| 场景 | 并发条件与实现 | 完成时间 | 按最终交付量计算的吞吐 |
| --- | --- | --- | --- |
| M0 → GPU0 | 单独 H2D | 40 ms | 25 GB/s |
| M0 → GPU1 | 单独 H2D | 40 ms | 25 GB/s |
| M0 → GPU0 与 M0 → GPU1 | 同时启动、各 1 GB、题设对等分担上行 A | 两路均 80 ms | 每路 12.5，总计 25 GB/s |
| M0 → GPU0 与 M1 → GPU2 | 同时启动、各 1 GB、上行 A/B 独立，其他资源充足 | 两路均 40 ms | 每路 25，总计 50 GB/s |
| GPU0 → GPU1 | 已确认 Switch A 内部 PCIe P2P，单独复制 | 40 ms | 25 GB/s |
| GPU0 → GPU2 | 明确选择 M0 整块中转，D2H 25 GB/s，随后跨 Socket 的 H2D 20 GB/s | 40 + 50 = 90 ms | 约 11.11 GB/s |

这些数字刻意采用理想化的稳定速率，便于与预算逐项核对。第三行与共享上行的 25 GB/s 预算一致：单路正常、并发总吞吐不增长，是共享约束的证据组合；还不能仅凭“总共 25”排除内存或其他同速瓶颈。本表已经额外给定其他资源充足，才把限制定位到上行 A。

第四行把两个 H2D 分到 A/B，两条上行分别搬 1 GB。第五行虽然和单路 H2D 都是 25 GB/s，却不经过主机上行；同一个速率可以对应不同路径。第六行的跨 Socket H2D 稳定速率由题设另给为 20 GB/s，不从 SYS 标记凭空推出来。

要让真实证据接近这种判断，还需结合链路状态、桥层级、测试实现、并发对照和相应资源计数。单独一个吞吐数字不负责证明物理路径；尤其不能看见“复制很快”就自行宣布 NVLink 已被使用。

## 同分支还是跨分支，由阶段需求决定

用上表比较两张 GPU 的一次**简化串行轮次**：每张卡先从本地主机内存接收 1 GB 输入，两路 H2D 同时开始，全部完成后才进入下一阶段。设计算耗时相同且不参与比较，之后卡间仅需单向交付 1 GB，交付完成后本轮结束。

- 选 GPU0/GPU1：输入共 80 ms，卡间 P2P 40 ms，相关阶段合计 120 ms。
- 选 GPU0/GPU2：输入共 40 ms，卡间整块中转 90 ms，相关阶段合计 130 ms。

在这组条件下，同分支快 10 ms。只把卡间交付量降为 0.1 GB、各段仍处于同样稳定带宽区间，其他不变：同分支是 `80 + 4 = 84 ms`，跨分支是 `40 + 9 = 49 ms`，结论反转。若阶段允许重叠或小消息固定开销不能忽略，要重新画时间线。不能脱离作业的输入量与交换量给出唯一最优位置。

这说明了第 05 章要解决的新问题：多卡作业何时交换什么数据、哪些成员互相等待。当前章节先把可供使用的路径与预算建立起来。

## 独立练习

题目彼此独立；除特别声明外，使用导读中的四卡节点和第二篇的理想化预算。先完成推导，再读答案。

### 1. 画出路径并确认身份

主机输出 index 2 对应导读中的完整 UUID 和 `0000:c1:00.0`。应用已核对自己的 ordinal 0 是这张卡；其输入缓冲全部位于 M0。写出物理 GPU 代号、局部 CPU 集合、同分支 NIC，并画出 M0 到该 GPU 的主要路径。把主机线程移到 Node 1，源页保持不变，H2D 的源位置是否随之改变？

### 2. 从速率与单位排除不可能目标

一张 GPU 在持续负载下端点状态为 Gen4 x8。按 128b/130b 编码计算单向上界；它能否传出 20 GB/s 的单向应用有效负载？另一份资料写 Gen4 x16 双向合计约 63 GB/s，能否据此承诺 H2D 60 GB/s？

### 3. 两个方向分开预算

上行 A 每方向有效预算 25 GB/s。现在 M0 → GPU0 要求 18 GB/s，M0 → GPU1 要求 12 GB/s，GPU1 → M0 要求 20 GB/s。其余资源充足。逐方向判断是否超标。若保持第一和第三项不变，第二项在此约束下最多获得多少？

### 4. 比较整块中转、流水和直达

GPU0 → GPU1 交付 1 GB。两段主机中转各 25 GB/s；求整块串行时间与最终交付吞吐。若分成 10 块且满足第二篇的全部流水条件，求时间；若确认存在单独 25 GB/s 的 PCIe P2P，求其复制时间。为什么这三个结果不同却不自相矛盾？

### 5. 能力、方向、启用与正确性

`cudaDeviceCanAccessPeer(&can, 0, 1)` 成功返回 can=1。应用随后从 GPU0 成功启用到 GPU1 的访问。现在 GPU0 的 Kernel 读取 GPU1 的显存，谁是访问者、谁是所有者、数据朝哪个方向返回？是否已自动启用反向访问？如果只有这两项 API 成功，可否认定应用数据传输一定正确并达到 25 GB/s？

### 6. 改变消息量后的放置选择

使用本篇简化轮次与汇总表。分别计算卡间单向交付 1 GB 和 0.1 GB 时，同分支/跨分支的相关阶段时间，并选较短方案。若改为输入与卡间交换允许重叠，是否仍能直接沿用这些加法？

### 7. 从拓扑近推到哪里

GPU2—NIC1 是 PIX，GPU2—NIC0 是 SYS。可否认定 GPU2—NIC1 的 GPUDirect RDMA 已可用？可否认定 GPU0—GPU2 在所有服务器上都不能 P2P？本章现有能力表对后一对设备在本教学节点上给出了什么明确结论？

### 8. 读懂独立 NVSwitch 平台的状态

另看 HGX H100 八 GPU 平台：FM 服务 Active；GPU A 的 Fabric 从 In Progress/N/A 变为 Completed/Success；尚无其他 GPU 状态与卡间校验结果。可以确认哪些状态？还需哪些材料才能确认整机互联可用？该平台标注的 900 GB/s 能否作一次单向复制的预期吞吐，也能否作 H2D 预算？

## 参考答案与推导

### 1. 编号必须跟身份走

应用 ordinal 0 是物理 GPU2，UUID 为 `GPU-33333333-3333-3333-3333-333333333333`；局部 CPU 是 Node 1 的 32—63，同分支 NIC1 位于 `0000:c3:00.0`。M0 → Socket 0 内存子系统 → Socket 间互联 → Socket 1 I/O/根侧 1 → 上行 B → Switch B → GPU2。主机线程改绑不改变题设中 M0 的源页位置；CPU 预处理与 DMA 应分别分析。

### 2. 上界先对方向

Gen4 x8 为 `16 × 8 × 128/130 ÷ 8 ≈ 15.75 GB/s`，还未扣事务开销，因此 20 GB/s 单向有效负载不成立。Gen4 x16 单向编码后上界约 31.51 GB/s；双向合计约 63.02 GB/s，不能支撑单向 H2D 60 GB/s 的承诺。

### 3. 上行正向是限制

主机→Switch 为 `18 + 12 = 30 GB/s`，超预算 5；Switch→主机为 20 GB/s，未超预算。保持第一项 18，第二项在上行正向最多剩 `25 − 18 = 7 GB/s`。这是假定其他资源充足后的预算上限，未包含具体分配策略。

### 4. 区别在路径与时间安排

整块中转 `40 + 40 = 80 ms`，最终交付吞吐为 12.5 GB/s；10 块流水 `(10 + 1) × 4 = 44 ms`，约 22.73 GB/s；直达复制 `1/25 s = 40 ms`，25 GB/s。流水仍两次搬运同一有效负载，却把不同块的两阶段重叠；直达改变路径，无需落入主机 DRAM。这里排除了固定开销且满足并发条件，不能把结果直接当作未来实测值。

### 5. 访问箭头和数据箭头不同

访问者是 GPU0，内存所有者是 GPU1，读取响应的数据由 GPU1 返回 GPU0。反向权限没有自动启用。能力和启用只给出访问条件；还需检查提交、同步完成、源/目的缓冲与校验，以及实际消息、方式和耗时，才可评价正确性与带宽。若只拿 API 成功直接写“25 GB/s”，遗漏了整个传输证据。

### 6. 放置答案随阶段需求变化

1 GB 交换时，同分支 `80 + 40 = 120 ms`，跨分支 `40 + 40 + 50 = 130 ms`，选同分支。0.1 GB 交换时，同分支 84 ms，跨分支 49 ms，选跨分支。允许重叠后应建立依赖和资源时间线，再求共同完成时间；串行加法不再自动成立。

### 7. 候选与支持性分别回答

PIX 支持优先核对 GPU2—NIC1 这一近端组合；它未提供 GPUDirect RDMA 所需的 GPU/NIC 驱动、内存注册、地址映射等材料。SYS 也不普遍否定 GPU—GPU P2P。本教学节点则已有 API 查询表，GPU0、GPU2 两个访问方向都为 0，因此在这次设备/软件条件下不具备相应直接访问能力；本篇 GPU0→GPU2 明确采用主机中转。

### 8. 单卡注册成功还要接上整机验证

Active 表明 FM 服务处于运行状态；GPU A 在后一个时刻已注册完成且成功。还需其余 GPU 的注册状态、符合整机预期的 NVLink 链路、成对访问与正确性、同口径单路/并发带宽，以及相关错误材料，才能形成整机验收结论。900 GB/s 是该规格的每 GPU NVLink 双向合计，单向合计口径为 450 GB/s，仍不等于实际复制吞吐；H2D 走主机侧路径，应另算 PCIe 和内存等预算。

读完本章，可以给一次传输留下一条完整记录：**身份与源页位置 → 连接路径 → 支持与启用 → 分方向预算 → 完成和正确性 → 实际吞吐**。第 05 章将在这些条件上继续解释多卡作业的成员与通信需求。
