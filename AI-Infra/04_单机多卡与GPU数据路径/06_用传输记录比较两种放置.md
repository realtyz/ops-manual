# 用传输记录比较两种放置

四张卡单独接收输入都很快，两张一起用却可能争用同一条上行。把卡分到两条上行能缩短输入阶段，但卡间交换也可能因此需要主机中转。放置要比较的是**作业各阶段共同完成所需的时间**。

## 先对齐测试口径

记录每项测试的源、目的、方向和消息大小。用 GPU UUID、BDF 和进程序号识别设备，用地址和内存策略记录主机缓冲区类型及实际 NUMA 页落点。注明复制由复制引擎还是由 SM 上的 Kernel 执行、是否显式经主机中转、同时有几路复制。对同一对照组固定重复次数、预热和其他负载条件。

下面的教学比较把初始化、分配、锁页和预热放在计时外，计时到对应复制实际完成。双路吞吐用交付总字节数除以共同起点到最后一路完成的时间。每路速率按各路实际时间计算。校验在传输完成后做，确认目的缓冲区的数据正确。若留存真实测试，还应记录采集时间、GPU 型号与拓扑、操作系统和驱动、CUDA 与测试工具版本、命令参数以及原始结果。 [CUDA 13.2.1 · API Synchronization Behavior](https://docs.nvidia.com/cuda/archive/13.2.1/cuda-runtime-api/api-sync-behavior.html)

## 看单路、同分支并发和独立上行三组记录

以下是**自拟教学表**。环境设定为双路 Linux 裸机、四张整卡、无 NVLink。Switch A 下挂 GPU 0 和 GPU 1，Switch B 下挂 GPU 2 和 GPU 3。M0、M1 是两个 Socket 的本地内存。两条上行和 GPU 下行在健康负载下均为 Gen4 x16，题设另给单向有效预算 `25 GB/s`。每行每路交付 `1 GB`，`1 GB = 10⁹ B`。同分支 H2D 并发时两路均分上行 A。独立上行对照中，题设给定其他资源充足。主机缓冲均已锁页。各行完成与校验均通过。

| 场景 | 路径与并发条件 | 完成时间 | 有效吞吐 |
| --- | --- | ---: | ---: |
| M0 → GPU 0 | 单路 H2D，经上行 A | 40 ms | 25 GB/s |
| M0 → GPU 1 | 单路 H2D，经上行 A | 40 ms | 25 GB/s |
| M1 → GPU 2 | 单路 H2D，经上行 B | 40 ms | 25 GB/s |
| M0 → GPU 0，M0 → GPU 1 | 两路同时启动，共用上行 A 的主机→Switch 方向 | 80 ms | 每路 12.5 GB/s，合计 25 GB/s |
| M0 → GPU 0，M1 → GPU 2 | 两路同时启动，分别走上行 A、B | 40 ms | 每路 25 GB/s，合计 50 GB/s |
| GPU 0 → GPU 1 | 已确认在 Switch A 内走 PCIe P2P | 40 ms | 25 GB/s |
| GPU 0 → GPU 2 | 无所需 P2P 能力，显式整块中转。先到 M0，再跨 Socket 从 M0 到 GPU 2 | 90 ms | 约 11.11 GB/s |

最后一行的 D2H 为本地 `25 GB/s`，随后 H2D 经过处理器间互联，题设给定整条远端 H2D 路径有效速率为 `20 GB/s`。于是完成时间为 `1 ÷ 25 s + 1 ÷ 20 s = 90 ms`。最终交付给 GPU 2 的是 `1 GB`，吞吐用 `1 GB ÷ 0.09 s`。`20 GB/s` 是路径假设，无法从 `SYS` 标签计算出来。

同分支并发的吞吐合计与单路相同，符合上行 A 的预算。分到 A、B 后，合计翻倍且各路达到单测水平。真实机器上，仅有并发降速还可能来自内存控制器或复制引擎。可先查负载下上行的 `LnkSta`，确认两组源缓冲都在目标 GPU 的本地节点，再做独立上行对照。若仍有多个解释，比较相应链路和内存流量能进一步缩小范围。表中的单路 H2D 和同分支 P2P 都是 `25 GB/s`，必须结合实现和路径证据才能区分它们。

## 用同一张表选择 GPU

假设每轮先让两张卡同时接收各 `1 GB` 本地输入，等两路都完成才开始交换。计算耗时在两种放置中相同，比较时略去。交换只有一个方向，从 GPU 0 交付给另一张卡。跨分支使用上表的串行中转，固定开销忽略，各段有效速率保持不变。

| 放置 | 输入阶段 | 交换 `1 GB` 时的总时间 | 交换 `0.1 GB` 时的总时间 |
| --- | ---: | ---: | ---: |
| GPU 0 + GPU 1，同分支 | 80 ms | `80 + 40 = 120 ms` | `80 + 4 = 84 ms` |
| GPU 0 + GPU 2，跨分支 | 40 ms | `40 + 40 + 50 = 130 ms` | `40 + 4 + 5 = 49 ms` |

交换量为 `1 GB` 时，同分支的卡间路径省出的时间足以抵消输入阶段的等待。降到 `0.1 GB` 后，独立上行缩短输入的收益更大，选择反转。若交换可以与输入或计算重叠，就要重画依赖和资源时间线，求最后一个必需操作的完成时刻。消息更小时，也要重新测固定开销在总时间中的占比。

## 从真实工具输出中取证

NVIDIA 在 NCCL 2.31.2 的排查文档中给出 `simpleP2P` 的删节示例。示例运行了两张卡相互读取对端显存的 Kernel，再把结果拷回主机校验，以 `Test passed` 表示样例通过。官方片段未给出完整硬件、驱动和构建环境，适合说明数据校验怎样出现在记录中。 [NCCL 2.31.2 · GPU-to-GPU Communication](https://docs.nvidia.com/deeplearning/nccl/archives/nccl_2312/user-guide/docs/troubleshooting/gpu_troubleshooting.html#gpu-to-gpu-communication)

读带宽时，以 NVIDIA `nvbandwidth` **v0.10.0** 的单节点用例为例。它需要 CUDA 设备与兼容的驱动，目标 GPU 对还须能启用相应 P2P。下面是已构建该版本后选择用例的命令。`-b` 的单位是 MiB，输出带宽是十进制 `GB/s`。默认会校验复制后的数据，`--skipVerification` 会跳过这一步。CE 用例调用复制 API，SM 用例使用复制 Kernel，实际搬运大小可能因对齐而调整。 [NVIDIA nvbandwidth v0.10.0 · README](https://github.com/NVIDIA/nvbandwidth/blob/v0.10.0/README.md) · [计时和校验源码](https://github.com/NVIDIA/nvbandwidth/blob/v0.10.0/memcpy.cpp#L512-L530)

```bash
./nvbandwidth --version
./nvbandwidth -l
./nvbandwidth -b 512 -t device_to_device_memcpy_write_ce device_to_device_memcpy_read_sm
```

在这两个单向用例中，矩阵行对应发起方的设备 ordinal，列对应 peer。按源码追踪有效数据，`write_ce` 把行设备的缓冲写到列设备，`read_sm` 从列设备读取到行设备。该版本标题中的箭头与这两个用例的有效数据方向相反。用用例名和源、目的缓冲区的赋值确认方向，也可用 `-v` 的源到目的记录交叉核对。对角线和未启用 P2P 的设备对会被跳过，矩阵各有效单元是分开测试的，不能相加当作并发总带宽。 [NVIDIA nvbandwidth v0.10.0 · 矩阵与用例实现](https://github.com/NVIDIA/nvbandwidth/blob/v0.10.0/testcases.cpp#L282-L345) · [读写时的缓冲区顺序](https://github.com/NVIDIA/nvbandwidth/blob/v0.10.0/testcase.h#L75-L110)

## 用一个变化复查判断

若应用 ordinal 0 实际是 GPU 2，且源页仍锁在 M0，哪条链路会增加负载？该 H2D 要穿过处理器间互联，再经上行 B 到 GPU 2。先用进程记录的 BDF 对齐 `nvidia-smi` 和桥树，再按缓冲区地址查 `numa_maps`。即使 H2D 变慢，只有吞吐一项也无法区分远端缓冲与链路变窄，需再对照实际页落点和负载下的 PCIe 状态。
