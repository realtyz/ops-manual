# 沿 PCIe 路径计算带宽预算

## 从链路速率换算单向预算

第 01 章已经区分 Lane、代际与宽度。这里继续把它们换成可计算的上界。PCIe Gen3、Gen4、Gen5 的每 Lane 速率分别为 8、16、32 GT/s，采用 128b/130b 编码。在这些代际，可先扣除编码开销，再由 bit 换为 byte：

```text
单向编码后带宽 = 每 Lane 速率 × Lane 数 × 128/130 ÷ 8
Gen4 x16 = 16 × 16 × 128/130 ÷ 8 ≈ 31.51 GB/s
```

这还没有扣除事务包头、流控等开销，不是应用有效数据带宽。128b/130b 的效率与双向合计口径可参阅 [PCI-SIG 的 Gen3 编码 FAQ](https://pcisig.com/how-does-pcie-30-8gts-double-pcie-20-5gts-bit-rate)；各代信号速率见 [PCI-SIG 的 Gen5 FAQ](https://pcisig.com/what-bit-rates-does-pcie-50-specification-support-and-how-does-it-compare-prior-pcie-generations)，Gen5 编码另见 [PCI-SIG 合规测试问答的 Protocol Testing 第 2 问](https://pcisig.com/blog/pcie%C2%AE-50-protocol-and-electrical-compliance-testing-deep-dive-webinar-qa)。本公式不直接套用到采用不同编码与传输机制的 Gen6/Gen7。

| 运行状态 | 扣编码后的单向上界 | 双向同时工作的合计口径 |
| --- | --- | --- |
| Gen3 x16 | 约 15.75 GB/s | 约 31.51 GB/s |
| Gen4 x8 | 约 15.75 GB/s | 约 31.51 GB/s |
| Gen4 x16 | 约 31.51 GB/s | 约 63.02 GB/s |
| Gen5 x16 | 约 63.02 GB/s | 约 126.03 GB/s |

PCIe 是全双工链路，两个方向各有传输能力。宣传中的“双向合计”不能全给一个 H2D 使用。同样，H2D 与 D2H 反向并发时，也不应不分方向地相加后与单向上界比较；端点引擎、内存子系统等仍可能造成其他共享约束。

## 端点状态只描述路径的一段

以下是**按 `lspci -vv` 字段自拟并整理的教学片段**，均为持续传输期间的状态。只保留链路能力和状态；行首设备用途是人工说明。PCIe 桥的端口名称需与整机资料核对。

```text
GPU0，0000:41:00.0：
    LnkCap: Speed 16GT/s, Width x16
    LnkSta: Speed 16GT/s, Width x16
Switch A 上行端口，0000:3f:00.0：
    LnkCap: Speed 16GT/s, Width x16
    LnkSta: Speed 16GT/s, Width x16
```

两条记录分别支持端点下行和 Switch 上行当前为 Gen4 x16。它们没有给 GPU0 独占上行的权利；GPU1 和 NIC0 的相应主机流量也经过这里。真实核对还要保留中间端口、两端能力和整机预期布线。命令及选项见 [pciutils 的 lspci 手册](https://github.com/pciutils/pciutils/blob/master/lspci.man)。

若 GPU0 的持续负载记录变为 `LnkSta: Speed 16GT/s, Width x8`，这段的编码后单向上界就降到约 15.75 GB/s。它足以否定“这段仍可传 25 GB/s 有效负载”，却不能单凭这一行认定是 GPU 卡、插槽、布线还是固件导致。需要对照预期与上下游状态，再查链路错误等证据。

空闲记录应单独标记。功耗管理可能影响工具报告的当前代际或宽度；不能把空闲与持续负载下的状态直接比较为性能退化。相关字段见 [nvidia-smi 文档](https://docs.nvidia.com/deploy/nvidia-smi/index.html)的 “GPU Link information” 小节。

## 共享资源按同一方向分别记账

现在进入**理想化教学预算**：上行 A 和 GPU0/GPU1 下行，每个方向的有效容量都给定为 25 GB/s；内存供给、复制引擎与 Switch 内部结构足以支撑本节安排，无额外争用，忽略启动和同步开销。这个有效值用于计算，不是从 31.51 GB/s 固定乘某个通用效率系数得来。

M0 同时给 GPU0、GPU1 各发 1 GB，要求都在 50 ms 内完成：

```text
每路平均需求 = 1 GB / 0.050 s = 20 GB/s
上行 A 的主机→Switch 方向需求 = 20 + 20 = 40 GB/s
需求 40 > 预算 25，因此 50 ms 目标不可满足
两个请求共同完成的耗时下界 = 2 GB / 25 GB/s = 80 ms
```

只按总容量约束还不能推导每张卡恰好各得 12.5 GB/s；那需要额外的公平分配假设。80 ms 是本节资源模型下的共同完成下界，真实耗时还受调度与其他资源影响。

再比较三个同时持续的请求，表内给出的是**希望维持的有效负载速率**：

| 请求 | 上行 A 主机→Switch | 上行 A Switch→主机 | 其他关键资源 |
| --- | --- | --- | --- |
| M0 → GPU0，20 GB/s | 20 | 0 | GPU0 接收方向 |
| M0 → GPU1，20 GB/s | 20 | 0 | GPU1 接收方向 |
| GPU1 → M0，10 GB/s | 0 | 10 | GPU1 发送方向 |
| 合计 | 40，超出 25 | 10，未超出 25 | 仍需核对端点与内存约束 |

若把第二项改成已经确认走 Switch A 内部直达的 GPU0 → GPU1，20 GB/s，这项有效负载不会再占主机上行；但 GPU0/GPU1 的端口、显存和传输引擎仍要承担它。直达的收益来自改变实际经过的资源，不能把每项流量都加到树的根上。

## 中转有两段，流水有自己的前提

设把 GPU0 上的 1 GB 送给 GPU1。软件明确选择 M0 作为锁页中转缓冲，并规定“整块 D2H 完成后，再启动整块 H2D”；每段稳定有效速率 25 GB/s，忽略其他开销：

```text
GPU0 → M0：1/25 s = 40 ms
M0 → GPU1：1/25 s = 40 ms
整块串行中转：40 + 40 = 80 ms
以最终交付的 1 GB 计，端到端吞吐 = 1/0.080 = 12.5 GB/s
```

中转在主机内存产生至少一次有效负载写入和一次读出；上行 A 两个方向各承载 1 GB。不能把两段合计搬了 2 GB 当成向 GPU1 交付了 2 GB。

若改成 10 块、每块 0.1 GB，允许一块 D2H 与前一块 H2D 并行，两个阶段各需 4 ms。在**反向链路、复制引擎、内存读写均可同时支撑，至少双缓冲且没有额外开销**的条件下：

```text
流水耗时 = 首块 D2H 4 ms + 10 块 H2D × 4 ms = 44 ms
最终交付吞吐 = 1 GB / 0.044 s ≈ 22.73 GB/s
```

这里可达到的模型下界来自分块流水，不能把前面的整块串行安排无条件改写为 `max(40,40)`。每块先写入再读出的依赖、首尾时间与双缓冲容量都必须存在。若两阶段共享某个不能并行的引擎或受同一内存吞吐限制，这个 44 ms 安排就不成立。

## 把预算用于判断

一条持续传输路径的有效带宽受经过的每段资源约束。对单一稳定流，可先用路径中最小的可用预算估计上界；对并发流，要在每段共享资源上分别累计同方向需求。小消息还需要考虑延迟，简单模型可写成 `T ≈ L + Q/B`，其中 L 是该测试条件下的固定开销，Q 是有效负载字节数，B 是稳定传输速率。

预算超过上界时，可以明确排除一个目标；预算没有超标时，只是通过了这一层的必要条件。下一篇继续确定“哪条路可用”，使预算从候选路径落到实际传输方式。
