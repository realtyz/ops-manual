# 用节点交付材料完成综合推演

以下十题都是**自拟教学材料**，各题独立重置。未明确改变的条件沿用导读；只根据给定条件和前文机制判断，无需运行命令。先写出结论和证据，再读参考分析。

## 题目

### 1. 从预装清单修正维护责任

节点平台已在两台节点预装并负责更新驱动、Toolkit 和 NVIDIA 运行时接入，已验证可创建 GPU 容器。集群也已有平台维护的 NFD，配置覆盖本章需要的 PCI 标签。拟安装 Operator，配置却是 `driver.enabled=true`、`toolkit.enabled=true`、`nfd.enabled=true`。同时还有一套平台旧 Device Plugin，发布同一批卡的 `nvidia.com/gpu`。

写出应调整的三项开关，并说明旧插件为什么不能原样并存。交接后的资源分配者是谁？

### 2. 两份 ClusterPolicy 能否隔离版本

有人想在同一集群安装两个本章版本的 release，分别建立 `pool-a-policy` 与 `pool-b-policy`，期待一池使用驱动 X，另一池使用驱动 Y。没有启用 NVIDIADriver CR 功能，也没有可靠的节点级排除或外部责任设计。

说明这份方案哪里缺少机制支持。若只是两池 GPU 型号不同，能否直接推出必须用两个驱动版本？

### 3. ready 与零个目标节点

一个刚部署的集群中，策略 `status.state=ready`，相关 GPU DaemonSet 都是 `desired=0, ready=0`。控制器 condition/日志说明尚未找到 NFD 标签；Node 上也没有 GPU 资源键。

这是否自相矛盾？下一步要补哪类证据，才能区分“没有 GPU 硬件”与“发现链未建立”？

### 4. 选择范围改变了分母

op-a、op-b 都已发现 GPU。平台明确接管 op-b 的驱动，将其 `nvidia.com/gpu.deploy.driver` 设为 `false`；其他 GPU 组件仍纳入管理。驱动 DaemonSet 为 `desired=1, ready=1`，其余节点 DaemonSet 的 desired 都是 2，但本题未提供各自 ready、日志与检查结果。

能否据此说驱动少装了一台？又能否据此说 op-b 的主机驱动已通过验证？列出下一份有用的证据。

### 5. 总空闲量能否放下两卡 Pod

当前材料已确认无 MIG/共享、没有并发分配变化、CPU/内存及其他调度条件满足：

| 节点 | 物理卡数 | Capacity | Allocatable | 尚未结束 Pod 的有效 GPU 请求总和 |
| --- | --- | --- | --- | --- |
| op-a | 2 | 2 | 2 | 1 |
| op-b | 2 | 2 | 1 | 0 |

插件健康记录表明 op-b 一张卡不健康，另一张健康。一个 Pod 请求 2 GPU，能否放入任一节点？如果改为请求 1 GPU，哪些节点在数量上可行？

### 6. 找到共同上游

op-b 的驱动日志报告当前内核构建树缺失；题设确认读取路径与挂载正确，对应头文件确未准备。Toolkit 等待驱动验证，插件与 Exporter 等待尚未产生的 `toolkit-ready`，Node 没有 GPU 数量。op-a 正常。

指出最早失败的必要条件、它解释的后续现象以及恢复后应按什么证据闭合判断。是否需要为每个等待组件分别重装一套软件？

### 7. Validator 到底覆盖了什么

调谐后的配置确认 `validator.plugin.env` 中 `WITH_WORKLOAD=false`；CUDA 检查创建的验证 Pod 成功，插件资源检查成功，Validator 主容器进入运行状态。尚未提供第 03 篇显式请求 1 GPU 的业务式探针记录。

能否断言“插件检查创建了一个请求 GPU 的验证 Pod并成功”？能否断言没有执行任何 CUDA 验证？要闭合本章的请求、分配与计算链，还可增加什么证据？

### 8. 镜像已到，为什么驱动仍失败

完全离线环境中，所有已启用组件及其 init/验证镜像都已镜像到内部仓库。节点无缓存测试拉取成功，驱动主容器也已启动。随后安装日志显示包管理器无法访问当前内核依赖的 OS 软件包仓库；未配置内部包源，也未采用预编译驱动。

故障属于镜像拉取还是驱动安装依赖？预编译方案能减少什么需求，又要新增什么匹配核对？

### 9. 两种异构条件不能混用

方案甲：Ubuntu 22.04 同内核的两个池，分别用 L4 与 A100，候选驱动明确支持二者，MIG 关闭。方案乙：Ubuntu 与 RHEL 两池，使用本章传统 ClusterPolicy 驱动路径，希望只加一个 `pool` 标签就自动满足所有 OS 安装前提。

分别判断。对乙，给出一种责任明确、与本章安装前置一致的处理方向，不必写安装命令。

### 10. 给一份交付报告限定结论

同一时间窗口内，op-b 有 GPU 2/2，驱动与运行时版本符合目标，单卡向量探针输出 `[11,22,33,44]` 且同步和校验成功。Exporter 因自定义采集文件语法错误退出，策略 `notReady`。报告拟写：“整台节点的两张卡和全部管理组件已交付，RDMA 与持续性能正常。”

改写成证据支持的结论，说明仍需补什么。

## 参考分析

### 1. 每项能力只留一条明确维护路径

设置 `driver.enabled=false`、`toolkit.enabled=false`、`nfd.enabled=false`；这些能力继续由节点平台维护，不能因关闭开关停止其更新。旧 Device Plugin 与 Operator 管理的新插件针对同一批卡、同一资源名承担重叠职责，需要设计切换并停止重叠发布；不能把插件副本当成新增物理容量。交接完成后，本题选择 Operator 管理的 Device Plugin 作为传统资源分配接口提供者，kubelet 负责具体节点资源发布与分配过程。切换中既要避免重叠，也要检查接管后的注册、资源和计算；题目不要求直接在运行集群删除旧插件。

### 2. 缺少独立的策略与节点所有权

本章版本的控制器采用单一有效 ClusterPolicy，额外策略可能 `ignored`，传统策略的驱动字段也不是任意逐池版本映射。两个 release 还可能争用集群对象与节点文件。需要选择支持该粒度的配置方式或明确预装/外部维护边界，不能以对象改名代替机制设计。若考虑 NVIDIADriver CR，还须接受该版本技术预览与迁移限制、审查默认资源及选择器重叠。型号不同只触发支持性核对；题设没有给出必须两个版本的理由。

### 3. 汇总范围为空，可以 ready

不矛盾。该版本可在没有 NFD 标签时完成当前管理步骤并写 `ready`；`0/0` 没有覆盖任何 GPU 节点。先核对预期资产中是否有 GPU，再对预期节点检查 PCI 枚举、NFD 部署/来源配置/日志及其标签；随后观察组件是否开始覆盖。若 PCI 已有 NVIDIA GPU 而 NFD 无相关输出，重点在发现链；若资产与 PCI 均无 GPU，不能要求 Operator 创造硬件。

### 4. desired 的分母服从选择条件

驱动 `1/1` 符合只管理 op-a 的配置，没有“应为 2”的依据。op-b 被排除仅证明责任边界被表达，未证明平台已经完成驱动。下一份可用证据是 op-b 主机驱动实际版本、NVML 查询、Validator 对预装路径的检查，以及请求 GPU 的计算探针。其他组件 desired=2 只说明目标覆盖，不能补出尚未提供的运行结果。

### 5. 单 Pod 的两卡请求不能跨节点拼凑

op-a 的数量余额为 `2-1=1`，op-b 为 `1-0=1`。聚合还有两个单位，但两卡 Pod 必须在单台节点满足请求，因此两台都不能放下。改成单卡时，两台在数量上均可行。物理共四张、健康可分配共三张、扣除已有请求后共两个单位，三种口径应分别保留；op-b 的不健康设备没有凭空从物理清单消失。

### 6. 先补驱动的构建前提

最早失败条件是当前内核对应的构建依赖未准备。多个 init 等待与插件尚未发布数量都是该上游未完成的后果，无需把它们推为多套独立坏软件。责任方修复依赖供给后，依次获取驱动成功与设备枚举、依赖等待解除、运行时接入、插件注册与 Node 数量、所选验证及计算结果。这里“依次获取”是解释证据的次序，支路可以在运行中并行完成。

### 7. 两个检查不能互相顶替

不能断言插件检查创建过请求 GPU 的 Pod，因为已明确关闭它的 workload 分支；也不能说完全没有 CUDA 验证，因为独立 CUDA 验证 Pod 已成功。该 CUDA Pod 直接指定节点、使用特权和全卡可见性，未通过普通 GPU request 验证分配。当前证据覆盖了它自己的 CUDA 路径和资源发现，尚不能将不存在的插件 workload 当作已执行。可追加第 03 篇的显式请求探针，关联 Pod spec、分配/创建、设备身份、同步与读回结果；如需双卡覆盖，应逐卡给出记录。Validator 主容器不持续重跑这些检查，旧成功也不自动覆盖后续变更。

### 8. 缺的是另一条供给链

镜像链已经有无缓存成功证据，故障在普通驱动容器所需 OS 包供给。应补内部包源及依赖、认证、证书或改用符合条件的其他路径。预编译驱动减少现场编译和下载构建包需求；仍需完整匹配 OS、架构、内核版本/变体、驱动分支及功能支持，并确认对应镜像存在。不能只把一个开关改成 true 就假定物料齐全。

### 9. 先分清改变的是硬件还是安装环境

甲在题设支持条件下，可以共用一套驱动目标；两池仍用节点属性和资源请求表达工作负载选择。乙的一个 pool 标签没有提供 OS 匹配的驱动管理能力，不满足本章传统路径的安装前置。可选择全局禁用 Operator 驱动部署，各 OS 池由节点平台预装和维护受支持驱动；若 Toolkit 接入也按池维护，则一并交接并关闭其 Operator 部署。后续插件、发现、监控仍要核对各池条件。另选 Driver CR 路径必须独立评审其版本限制，不能悄悄当成本题已启用。

### 10. 分别报告已证实和未闭合的部分

可写：“op-b 当前上报两个可分配 GPU 单位，驱动和运行时版本符合目标；本次分配的一张卡完成向量计算、同步与读回校验。监控采集配置失败，管理组件交付尚未闭合。”还需修复 Exporter 并验证采集、补设备身份和另一张卡的覆盖记录；持续性能需要固定条件的负载测试。RDMA 没有出现在本章基线中，也没有证据支持。`notReady` 在此反映监控支路未完成，不推翻已发生的单次计算成功。

这些答案将“目标、覆盖、当前接口、一次运行结果”分别关联起来。后续第 13 章把同样的方法用于附加网络和 RDMA 设备；设备请求与组件可用之后，还需要证明作业实际使用了正确的网络路径。
