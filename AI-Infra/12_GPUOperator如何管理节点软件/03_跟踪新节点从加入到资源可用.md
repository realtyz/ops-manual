# 跟踪新节点从加入到资源可用

## Node Ready 是过程的起点

`op-a` 已经有两张可分配 L4，`op-b` 新加入。此时 kubelet 能向 API Server 汇报，Node condition 中 `Ready=True`，只说明 Kubernetes 节点达到其就绪判据。GPU 驱动可能尚未准备，插件尚未注册，也可能没有任何 GPU 标签。

本章把“资源可用”拆成三件可分别确认的事：节点已上报符合模型的 GPU 数量，运行时能够交付请求的设备，短计算经过同步和结果校验。发现、监控与管理组件也各有交付条件。把这些条件分开，才能解释它们为何不总在同一时刻完成。

下面是**自拟事件时间线**。T0—T6 是观察顺序，不承诺实际耗时，也不对应 Operator 的内部状态枚举。无业务 Pod 竞争资源，镜像、依赖包和准入条件先设为满足。

| 观察时刻 | op-b 的新证据 | 此时可以确认什么 |
| --- | --- | --- |
| T0 | `Node Ready=True`；没有 GPU Capacity | kubelet 与节点基础服务可用，GPU 交付未完成 |
| T1 | NFD 发布本章 PCI 发现标签；组件部署标签出现 | 节点进入 GPU 组件目标集合 |
| T2 | 驱动侧查询成功，枚举 B0、B1；版本为 570.124.06 | 当前驱动可管理两张设备 |
| T3 | Toolkit 配置生效；nvidia handler 能创建验证容器并查询设备 | 本次容器创建的运行时接入成立 |
| T4 | 插件注册并上报两个健康 ID；Node GPU Capacity / Allocatable 均为 2 | kubelet 的传统 GPU 资源接口已建立 |
| T5 | GFD 属性与硬件相符；Exporter 能采集；Validator 当前配置的检查完成 | 发现与观测支路及所选验证项目完成 |
| T6 | 显式请求 1 GPU 的教学探针完成计算和读回校验 | 此次 Pod 的请求、分配、注入与计算链已走通 |

本章部署模板要求插件先等到 `toolkit-ready`，所以 T4 的插件启动在该信号之后；但它不以“所有业务容器已测试成功”为资源上报前提。GFD、监控与验证工作负载也可能交错推进。应保持这些明确依赖，不能把表格全部行号理解成 Kubernetes 全局串行屏障。

## 候选节点怎样进入组件的目标集合

T1 的发现依赖 NFD 从节点读取特征，而不是先调用 CUDA。控制器看到候选节点后，根据策略与标签生成相应目标，DaemonSet 再让 kubelet 在该节点启动组件 Pod。因而从“PCI 能发现 GPU”到“驱动能够访问 GPU”之间还有一段真正需要完成的主机工作。

驱动 Pod 成功启动还不足以略过内核检查。若当前内核的头文件缺失，驱动安装可能失败；若模块装载被拒绝，后续依赖设备访问的组件只能等待。它们显示 `Init`，不表示每个组件都独立损坏。初始容器的等待是为了避免在基础条件未完成时直接启动依赖组件。

Toolkit 准备好运行时后，Device Plugin 仍需独立完成 kubelet 注册和设备上报。kubelet 才是 Node 资源数量的发布者；Operator 的作用是让插件及其前提得到部署与维护。T4 没有改变第 11 章的分配接口。

## 用同一时刻的字段完成数量推导

以下命令与输出是 **T4 的自拟删节材料**，命令用于说明字段来源：

```bash
kubectl get node op-b -o yaml
```

```yaml
metadata:
  name: op-b
  labels:
    feature.node.kubernetes.io/pci-10de.present: "true"
    nvidia.com/gpu.present: "true"
status:
  capacity:
    nvidia.com/gpu: "2"
  allocatable:
    nvidia.com/gpu: "2"
```

再给定同一时刻平台核算的、尚未结束 Pod 的有效 GPU 请求总和为 **0**，且 CPU、内存、污点与亲和条件满足。新 Pod 请求 1 GPU，则数量可容纳：`2 - 0 = 2 ≥ 1`。这里 Allocatable 是健康可分配总额，不是每次分配后自动减一的空闲余额；以后已有 Pod 请求 2 时，即使该字段仍是 2，也容纳不了另一个整卡请求。

在当前模型中每卡健康、无共享且没有 MIG，两个请求单位才对应两张物理卡。不能把这个对应直接移植到第 14 章的副本共享或切分模型。

Node 数量建立后，普通业务调度未必等待 Operator 所有验证与监控分支完成。若平台要求验收完才接收业务，应另设清楚的节点准入或维护流程，而不是假设 `ClusterPolicy ready` 天然构成调度屏障。相关生产流程在第 19 章展开。

## 用一次完整创建闭合链路

T6 使用下面的 **自拟 Pod 教学配置**。`lesson/gpu-probe:cuda12.8.1` 是虚构的已构建镜像，含 L4 所需设备代码与下述探针，不是公共可拉取镜像；命名空间 `lesson` 已存在，RuntimeClass `nvidia` 已映射到节点有效 handler。

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: op-b-probe
  namespace: lesson
spec:
  restartPolicy: Never
  runtimeClassName: nvidia
  nodeSelector:
    kubernetes.io/hostname: op-b
  containers:
    - name: probe
      image: lesson/gpu-probe:cuda12.8.1
      command: ["gpu-probe", "--vector-add"]
      resources:
        limits:
          nvidia.com/gpu: 1
```

只写 GPU limit 时，Kubernetes 使用同值 request；`nodeSelector` 选择 op-b，仍经调度与 kubelet 分配，没有通过 `nodeName` 绕过调度。Probe 在分到的一张卡上分配少量显存，把 `[1,2,3,4]` 与 `[10,20,30,40]` 相加，等待 GPU 完成，读回结果并比较。**自拟输出**如下：

```text
node=op-b visible_cuda_devices=1
input_a=[1,2,3,4] input_b=[10,20,30,40]
cuda_launch=success synchronize=success
result=[11,22,33,44] check=PASS
```

它证明本次容器的一张被分配设备完成了短计算。它没有单独证明 B0、B1 都被测试，也没有提供持续负载性能、ECC 状态或跨节点通信证据。若要确认每张卡，必须提供明确的设备身份与覆盖记录；不能把一次单卡 PASS 乘以物理卡数。

## 新节点不是一条只向前走的进度条

上述过程也会反向变化。内核更新后驱动可能无法重新装载，节点重启后运行时配置可能被平台镜像覆盖，某张卡变为不健康后插件会改变上报。控制器重试解决不了所有外部条件；状态也会受异步上报和旧记录影响。

因此，交付证据应关联节点、组件版本和采集时刻，重建或变更后重新检查受影响环节。下面一篇不再按“安装步骤”找错，而从可观察证据沿依赖往回追。
