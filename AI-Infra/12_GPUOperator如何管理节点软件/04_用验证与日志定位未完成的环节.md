# 用验证与日志定位未完成的环节

## 先给每份证据标明范围

排查时先确认三件事：正在看哪个节点，材料是否来自同一配置和时间窗口，展示的是目标还是实际结果。下面的证据强度不同，但每份都有用途：

| 材料 | 首先回答什么 | 继续核实什么 |
| --- | --- | --- |
| Helm values / ClusterPolicy spec | 目标是否正确、组件是否启用 | 当前模板和节点配置是否已生效 |
| ClusterPolicy status / 控制器日志 | 哪个管理步骤尚未满足 | 对应工作负载、目标节点和具体原因 |
| DaemonSet desired / ready | 应覆盖多少节点、多少已就绪 | 少的那份在哪台节点、停在哪个容器 |
| Pod 状态、事件、分容器日志 | 镜像、准入、初始化、进程哪步失败 | 依赖是否失败，日志是否为本次或前次容器 |
| Node GPU 字段 / 插件上报 | kubelet 是否发布对应数量 | 健康 ID、已有请求、设备交付与计算 |
| Validator 与短计算结果 | 特定项目或路径是否完成 | 覆盖哪些设备、采用哪些检查配置 |

`DaemonSet desired=0, ready=0` 可以是选择条件没有匹配节点；不应读成“零个失败，所以全部 GPU 已好”。`Running` 也只是 Pod phase，和 `Ready` condition、init 完成情况以及探针执行结果不同。

## Validator 分别在验证什么

本章版本的 `nvidia-operator-validator` 是节点 DaemonSet。其 init containers 按部署后的模板执行驱动、Toolkit、CUDA、插件等检查，最后主容器保持运行。主容器存在说明本轮已配置的初始化过程成功，不等于持续重跑所有 GPU 测试。

| 检查名 | 在本章主线中的工作 | 如何理解通过结果 |
| --- | --- | --- |
| `driver-validation` | 验证可用驱动入口；区分主机预装与驱动容器路径 | 当前驱动管理查询成立 |
| `toolkit-validation` | 在检查容器中调用 `nvidia-smi`，使用注入的设备与文件 | 本次检查容器能够访问 NVML 路径 |
| `cuda-validation` | 创建节点上的 CUDA 验证 Pod，并等待结果 | 这次所选 CUDA 验证工作负载完成 |
| `plugin-validation` | 检查 Node GPU 资源；按配置决定是否再创建请求 GPU 的验证 Pod | 资源发现通过；是否覆盖请求分配路径要看配置 |

这些名称来自 [v25.3.0 Validator DaemonSet 模板](https://github.com/NVIDIA/gpu-operator/blob/v25.3.0/assets/state-operator-validation/0500_daemonset.yaml)；具体检查见 [validator/main.go 的 Driver、Toolkit、CUDA、Plugin 实现](https://github.com/NVIDIA/gpu-operator/blob/v25.3.0/validator/main.go)。本章不启用 GDS，对应 `nvidia-fs` 检查不承担额外工作，不把模板原始 init 数量当作所有配置固定数量。

还有一个容易漏掉的配置覆盖：原始 DaemonSet 模板中插件检查写了 `WITH_WORKLOAD=true`，但发布配置的 `validator.plugin.env` 默认把它设为 **false**。按本章 chart 默认值，插件检查不再额外创建该 GPU 请求工作负载；CUDA 检查仍有自己的工作负载。这是两处不同的检查，不能混为一个开关。应读取调谐后的模板和环境变量，不能只看模板源文件或只看某个 CLI 的默认值。

这份 CUDA 验证 Pod 的模板使用特权和 `NVIDIA_VISIBLE_DEVICES=all`，没有普通业务 Pod 的 GPU resource request；验证程序又直接指定节点。因此它可以证明自己的 CUDA 路径，却不能替代一次正常请求、调度与分配的验证。插件 workload 分支若启用，会为其初始化容器设置一个 GPU 请求；第 03 篇另给出经调度的业务式探针。对照模板见 [cuda-workload-validation.yaml](https://github.com/NVIDIA/gpu-operator/blob/v25.3.0/validator/cuda-workload-validation.yaml)与 [plugin-workload-validation.yaml](https://github.com/NVIDIA/gpu-operator/blob/v25.3.0/validator/plugin-workload-validation.yaml)。

检查过程会在主机共享目录 `/run/nvidia/validations` 写状态文件，供其他组件等待前提。它们是实现中的协调信号，不能代替持续健康与端到端证据，也不能手工创建文件来“修复验证”。最终计算结论仍应关联本轮日志、Pod 和实际结果。插件验证中“是否有 GPU 资源”的查询使用 Node Capacity，不能把它等同于读到了业务当前剩余余额。

## 案例一：多个 Init，只有一个上游阻塞

重置到 op-b 未完成驱动的情况；op-a 正常。下面是 **09:10 的自拟命令与删节输出**，所有相关 DaemonSet 的目标都是这两台节点：

```bash
kubectl get ds -n gpu-operator
```

```text
NAME                              DESIRED CURRENT READY UP-TO-DATE AVAILABLE
nvidia-driver-daemonset            2       2       1     2          1
nvidia-container-toolkit-daemonset 2       2       1     2          1
nvidia-device-plugin-daemonset     2       2       1     2          1
gpu-feature-discovery              2       2       1     2          1
nvidia-dcgm-exporter               2       2       1     2          1
nvidia-operator-validator          2       2       1     2          1
```

先查节点归属：`kubectl get pods -n gpu-operator -o wide`。**自拟整理结果**表明缺少的 ready 都在 op-b：驱动主容器重启，Toolkit 和 Validator 等待驱动检查，插件、GFD 与 Exporter 等待 `toolkit-ready`；op-a 的 GPU Capacity / Allocatable 为 2/2，op-b 没有 GPU 资源键。这里“等待”是日志归纳，不冒充 Kubernetes 原始 reason 字段。

进一步给出本轮 Pod 名与容器名。下面命令及日志仍为**自拟材料**，省略无关行：

```bash
kubectl logs -n gpu-operator nvidia-driver-daemonset-b9k2m -c nvidia-driver-ctr --previous
kubectl logs -n gpu-operator nvidia-container-toolkit-daemonset-k4q7v -c driver-validation
```

```text
# 第一条：前一次退出的驱动主容器
running_kernel=5.15.0-134-generic
kernel_build_tree=/lib/modules/5.15.0-134-generic/build
kernel_build_tree_missing=true; driver installation stopped

# 第二条：当前 Toolkit 的 driver-validation 初始化容器
driver validation has not succeeded; retrying
```

题设再补足关键条件：驱动容器确实可以读取配置要求的内核依赖位置，但当前运行内核对应的头文件/构建树未准备。由此可以明确判断，本例阻塞在驱动构建前提，不是六份互不相关的故障。Toolkit 的等待解释了它尚未进入主流程，插件没上报也与上游驱动不可用一致。

合理修复应由责任方补齐当前内核对应依赖及其供给路径，随后观察驱动成功、等待解除、数量上报与探针结果。反复删除所有 Pod 或关闭 Validator 没有补齐依赖。真实故障若只看到一个路径不存在，仍需核实挂载、包版本及运行内核；本题已明确给定这些条件，才可收敛到上述结论。

普通驱动容器对 OS 包的需求见 [Air-Gapped Installations](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/25.3.0/install-gpu-operator-air-gapped.html)。真实案例还可能涉及 nouveau、模块签名或硬件初始化；这些各自需要证据，不能从本题推成所有 `Init` 的固定根因。

## 案例二：运行时名字存在，节点 handler 未生效

独立重置 op-b：驱动查询成功；此前已正常启动的 Device Plugin 仍在上报，Node GPU 为 2/2。之后节点平台覆盖了运行时配置，已运行插件的上报尚未停止，新容器创建却开始失败。RuntimeClass 对象 `nvidia` 仍存在且其 handler 为 `nvidia`。新验证 Pod 创建 sandbox 时，**自拟事件摘要**显示：

```text
reason=FailedCreatePodSandBox node=op-b requested_handler=nvidia
containerd reports no configured runtime handler named nvidia
```

这把故障定位到节点运行时接入。RuntimeClass 只是把名字交给 CRI，不能自动把 NVIDIA Runtime 装进每台节点。应查 Toolkit 主容器日志、它实际写入的配置路径、containerd 服务的启动配置路径与重载结果。若平台确认 Toolkit 写入 `/etc/containerd/config.toml`，服务却读取另一份文件，便有明确因果：配置没有进入本次运行的 containerd。

此时 `toolkit-validation` 甚至可能还没开始运行。先检查创建事件，不能只等待它输出内部报错。官方 [Troubleshooting 的 Failed to Create Pod Sandbox 小节](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/25.3.0/troubleshooting.html)也展示过 handler 不存在的现象，但其中驱动/nouveau 的背景与本例配置路径不同；相同表面错误可以有不同上游原因。

## 案例三：监控失败，计算路径已通过

再次独立重置：op-b 的驱动、Toolkit、插件和当前计算探针正常，Node GPU 为 2/2；Exporter 在加载自定义采集文件时退出。**自拟日志摘要**为：

```text
component=dcgm-exporter
collector_config=/etc/dcgm-exporter/custom.csv
config_parse=failed; invalid field entry; exporter exiting
```

本题确认文件已挂载、错误来自其内容。可判断监控支路没有达到交付目标，应修正采集配置并验证端点恢复；当前单卡计算路径已有成功证据。若策略因 Exporter 未就绪显示 `notReady`，也不等于两张卡都无法计算。反过来，业务短计算通过不能取消监控修复任务。

## 按最早失败的必要条件决定下一步

三例的共同方法是先找到目标节点，再沿功能依赖定位最早失败的必要条件。发现入口缺失就查 NFD 来源与部署；工作负载创建被拒就查事件；驱动失败就查主机与驱动；资源缺失就查插件注册；sandbox 失败就查运行时；仅观测失效就查采集支路。顺序服务于已有证据，不能把它变成跳过现场条件的固定安装清单。
