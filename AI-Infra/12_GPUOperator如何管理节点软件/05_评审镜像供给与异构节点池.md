# 评审镜像供给与异构节点池

## 软件要先到达执行它的地方

Operator 可以表达组件目标，但不会自动把外部依赖变成集群里的现成文件。离线准备至少包含 Helm/chart 物料、容器镜像、普通驱动容器所需 OS 包三类供给。管理员电脑能下载，只说明准备端可访问；节点能拉镜像、驱动容器能下载依赖，还要分别验证。

| 供给对象 | 谁在使用它 | 失败时首先可能看到什么 |
| --- | --- | --- |
| release chart、依赖 chart、CRD 等安装物料 | Helm 客户端与 API Server | 取 chart、渲染或创建对象阶段失败 |
| Operator、init、各受管理组件及验证镜像 | 节点 kubelet 经 containerd 拉取 | `ErrImagePull` / `ImagePullBackOff` 及事件 |
| 当前内核头文件、构建工具与其他依赖包 | 普通驱动容器内的包管理与安装流程 | 驱动主容器已启动，却安装失败 |

本章普通驱动路径的“两条下载链”是 **节点运行时 → 镜像仓库**，以及 **驱动容器 → OS 包仓库**。前者成功不能推出后者成功。内部仓库 CA 被 containerd 信任，也不代表容器内包管理器信任同一个 CA；镜像拉取 Secret 同样不是软件包仓库的认证配置。

官方 [25.3.0 Air-Gapped Environments 的 About、Local Image Registry、Local Package Repository 小节](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/25.3.0/install-gpu-operator-air-gapped.html)分别描述了这些需求。DNS、路由、代理、证书与凭据应按实际执行端验证；不要拿一台跳板机的成功请求替代节点侧证据。

## 镜像清单从实际配置产生

镜像清单既来自 chart，也来自控制器生成的工作负载。只镜像 `gpu-operator` 和 `driver` 两项，会遗漏 Toolkit、插件、GFD、Exporter、Validator、驱动管理辅助镜像、NFD，以及安装或验证阶段的 init/临时 Pod。某些组件会复用镜像，但“镜像复用”不意味着可以省掉对该使用位置的认证与拉取策略检查。

一个可审阅的物料表应包含：组件与使用位置、源仓库及 tag、目标仓库、实际 digest、适用架构、预期节点池，以及这次启用与否。tag 表示命名选择，digest 用于固定内容；本章不虚构一组 digest 来冒充已下载的物料。

下面是 **自拟 values 片段**，只演示两个组件的重定向。`registry.example.internal` 是占位内部地址，Secret 已在受管理组件所在命名空间创建；其余组件仍需逐项配置与核对：

```yaml
driver:
  repository: registry.example.internal/nvidia
  image: driver
  version: "570.124.06"
  imagePullSecrets: [gpu-registry]
toolkit:
  repository: registry.example.internal/nvidia/k8s
  image: container-toolkit
  version: v1.17.5-ubuntu20.04
  imagePullSecrets: [gpu-registry]
```

这不是一个全局镜像仓库开关。组件字段分别处理镜像与 Secret，NFD 又有其依赖 chart 配置。驱动最终镜像标签还与所选 OS 或预编译内核路径有关，不能只复制 values 中的版本字符串而漏掉实际使用的变体。应结合 release chart、固定 tag 模板及调谐后的 Pod `image` 字段核对，见 [v25.3.0 values.yaml](https://github.com/NVIDIA/gpu-operator/blob/v25.3.0/deployments/gpu-operator/values.yaml)。

离线评审还要覆盖平时不出现的使用位置。例如节点已经缓存了 Validator 镜像，当前验证可以通过；新节点或重建节点无缓存时，漏配的验证仓库才暴露。交付材料需要证明未缓存场景的供给能力，不能只以“现有 Pod 正在 Running”为证据。

## 预编译驱动减少依赖，同时增加匹配要求

普通驱动容器在节点侧准备当前内核所需模块，预编译驱动容器则提前提供对应构建产物，减少现场编译与下载 OS 构建包的需求。它不是一个与任何 Linux 内核都通用的二进制镜像。

判断是否可用要把 GPU 驱动分支、完整内核版本/变体、OS、架构与相关功能支持一起核对。节点内核从 `5.15.0-134-generic` 变成另一个完整版本后，旧内核对应的预编译镜像不能凭“都是 5.15”就继续算匹配。没有现成镜像时，需选择文档支持的构建或其他部署路径。

本章主线未启用此功能。有关标签命名与依赖减少的机制参考 [25.3.0 Precompiled Driver Containers](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/25.3.0/precompiled-drivers.html)。该页与同版本 Platform Support 的后续增补中，对支持 OS 的列表存在口径差异；本章因此不将它们合并成新的支持矩阵，也不据此推荐某个扩展组合。具体部署必须重新核对目标 release 的明确支持说明与镜像存在性。

## 异构要拆开看：硬件、内核、OS 与维护者

GPU 型号不同，不必然要求驱动版本不同；OS 相同，也不代表内核构建依赖相同。先找出真正变化的维度，再决定是否仍可共用一条管理路径。

| 改变的条件 | 必须重新核对的东西 | 本章可以确定的边界 |
| --- | --- | --- |
| 同 OS、同内核，一池 L4，一池 A100 | 驱动支持、应用设备代码、插件/GFD 策略 | 不能因型号不同就推导必须两个 ClusterPolicy；MIG 仍按本章条件关闭 |
| 同 OS、不同内核 | 每个运行内核的构建依赖；若预编译则核对每种镜像 | 同一驱动版本不等于同一内核模块产物 |
| Ubuntu 与 RHEL 等不同 OS | 安装方式、镜像变体、文件布局和运行时接入 | 不把传统 ClusterPolicy 驱动路径外推成任意混合 OS 自动支持 |
| 部分节点平台预装、部分由 Operator 安装 | 每节点责任与部署标签、升级和恢复路径 | 排除某节点的驱动 Pod，不会替它安装主机驱动 |

对于本章传统 ClusterPolicy 驱动方式，官方安装前置要求 GPU 节点使用相同 OS 版本；预装驱动是文档给出的不同 OS 处理路径之一。若要用最清晰的责任设计处理混合 OS，可以全局 `driver.enabled=false`，各池由节点平台维护驱动；若 Toolkit 接入也交给各池，则同时 `toolkit.enabled=false`。其他组件是否适用仍要分别核对，不能因为驱动交接了就假定所有容器布局通用。安装前置见 [25.3.0 Install 的 Prerequisites](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/25.3.0/getting-started.html)。

## 需要按池配置驱动时，先确认使用的是哪种 API

传统 ClusterPolicy 的驱动字段提供一套驱动类型/版本目标。节点标签能排除工作负载，却不能把同一个 `driver.version` 自动变成两个版本。为了给不同池指定版本而安装两个相互覆盖的 release，会把全局对象、节点标签和宿主机文件的所有权变得模糊。

v25.3.0 另有 **NVIDIADriver 自定义资源**，可按 `nodeSelector` 表达不同驱动配置，但该版本文档将其标为 **Technology Preview**，并明确限制从旧安装迁移的路径。它不是本章默认启用的功能，也不能把新版能力倒推给传统 ClusterPolicy。

选择这条路径时，除了启用对应功能，还要检查默认 Driver CR 是否覆盖全部 GPU 节点、自建资源的选择器是否重叠，以及版本和功能是否在支持范围内。本章仅解释为什么需要不同表达能力，不提供未经验证的生产迁移 YAML。依据见 [NVIDIA GPU Driver CRD 的 Overview、Comparison 和 Default CR 小节](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/25.3.0/gpu-driver-configuration.html)。

## 把版本匹配落实到可审阅的材料

Operator chart 版本只是版本清单的一项。交付材料还应连接 OS/内核、模块类型、驱动实际版本、Toolkit 与运行时实际配置、插件与发现版本、Exporter/Validator 镜像，以及应用 CUDA 运行条件。对驱动/Toolkit 的覆盖配置，不能仅写“沿用 Operator 默认值”，应记录最终值与来源。

版本更新的影响沿依赖传播：内核改变可能使驱动需要重建；驱动文件根改变会影响注入与采集；Toolkit 配置入口改变可能使插件仍能上报但容器无法创建；插件策略改变则会影响资源语义。第 19 章再展开排空、试点、回滚和性能复核，这里已经能判断为什么一次 Helm 成功不能替代这些工作。

网络组件也有独立责任。GPU Operator 的驱动侧配置与 Network Operator、主机 NIC 驱动及 Pod 网络应在 GPUDirect RDMA 场景中协同，但“GPU 资源已出现”没有验证任何 RDMA 路径。第 13 章将沿网络设备进入 Pod 的链继续解释。
