# 12 GPU Operator 如何管理节点软件

## 范围、前置知识与读者目标

- **范围**　以 Linux 裸金属集群中一台新 GPU 节点的交付为主线，从节点发现追到驱动加载、运行时接入、资源上报和工作负载验证。主例是 `ClusterPolicy` 管理的 Device Plugin 路径。用 `GPUCluster` 对照 DRA 路径的管理范围、接入条件和验收证据。以节点预装、混合节点池和离线部署说明同一条链在不同环境下的变化。
- **必要前置**　能阅读 Pod、Node 和 DaemonSet 的 YAML，知道 kubelet 和 containerd 的角色。开篇补足三组关系：主机内核驱动与容器里的 CUDA 用户态、设备分配与 CDI 注入、Node 特征标签与可分配资源。读控制器时用本章实际对象解释 CRD、CR、`spec`、`status` 和协调循环。
- **读完应能独立判断**　给定 Helm 值、集群中的 CR、DaemonSet 和节点配置，能指出每项软件由谁交付和维护、哪些节点会部署它。给定同一节点的标签、Pod 状态、验证日志和资源字段，能指出已通过哪一层、下一项取证应查哪里。给定两个节点池的 OS、运行内核、驱动模式和镜像清单，能判断部署条件及缺失的依赖。
- **跨章分工**　第 03、10 章负责驱动/CUDA 兼容与 OCI 注入机制，第 11 章负责 kubelet 的设备分配和 DRA Claim 生命周期。本章以这些机制的配置入口和观测结果为接口。RDMA 联动与 MIG/共享分别交给第 13、14 章，指标解读、硬件诊断和生产升级分别交给第 17、18、19 章。

## 贯穿案例与版本口径

- **教学场景**　集群已有 `gpu-h0` 和 CPU 节点 `cpu-0`，加入同型的 `gpu-h1`。两台 GPU 节点各有两张 H100 PCIe，采用整卡独占和无 NVSwitch 的拓扑。主例假定 NFD 由 chart 安装，驱动和 Toolkit 由 Operator 交付，CDI 开启、NRI 关闭。验证 Pod 在 `gpu-h1` 有空闲整卡时用节点选择器限定目标，申请一张 GPU 并运行 CUDA VectorAdd。异常与预装场景从主例分别改变指定条件。
- **版本锚点**　以 GPU Operator chart、镜像默认配置和源码标签 `v26.7.2` 为准。Kubernetes v1.36、containerd 2.3、x86_64 Ubuntu 24.04 LTS 用于教学取样，分别对照平台矩阵。chart 中默认驱动为 `595.91.07`，Toolkit 为 `1.20.1`，Device Plugin 和 GFD 为 `0.20.1`，DRA 对照用 `0.5.1`。第 11 章的独立插件示例有自己的版本与配置。这里以本章实际生成的 DaemonSet 为准。 [NVIDIA v26.7 平台与组件矩阵](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/26.7/platform-support.html) · [v26.7.2 chart 默认值](https://raw.githubusercontent.com/NVIDIA/gpu-operator/v26.7.2/deployments/gpu-operator/values.yaml)
- **材料口径**　依赖图和时间线采用 Mermaid，配置差异、计数、证据与适用条件用表格。教学快照标明假设。若取得实机记录，注明来源、采集命令与时间、节点名、OS、内核、卡型、驱动与运行时版本、chart 版本和镜像标识。官方示例、源码消息和实机输出各自注明出处。

## 01 哪些组件共同把一张 GPU 交付给 Kubernetes

- **问题与预期结论**　机器插着 GPU，为什么平台仍要装一组组件？读者应能指出缺少驱动、Toolkit、设备插件、发现或监控任一环节时，节点分别失去什么能力。
- **解释顺序**　从新节点的 PCI 枚举起步。NFD 提供 Operator 可识别的硬件标签，驱动使 OS 能访问设备，Toolkit 准备容器运行时接入，Device Plugin 向 kubelet 供给设备，kubelet 更新 Node 上的资源。另画两条分支：GFD 发现型号等 GPU 特征并通过 NFD 更新节点标签，DCGM 提供遥测、DCGM Exporter 暴露指标。把 Validator 放在相应检查点。用监控单独中断的变体说明为何要分别验收计算和遥测。MIG Manager 只交代职责，配置见第 14 章。
- **支撑材料**　拟画一张依赖图，箭头分别标注特征标签、驱动访问、设备上报、容器注入和指标输出。以 `nvidia.com/gpu.product`、`.status.allocatable["nvidia.com/gpu"]` 和 Exporter 端点各举一项输出。用 `dcgm.enabled: false` 与 `dcgmExporter.enabled: true` 说明默认使用 Exporter 内嵌的 host engine，解释为何现场可能只有 Exporter 的 DaemonSet。 [NVIDIA Operator 组件概览](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/26.7/overview.html) · [v26.7.2 chart 默认值](https://raw.githubusercontent.com/NVIDIA/gpu-operator/v26.7.2/deployments/gpu-operator/values.yaml) · [Kubernetes v1.36 Device Plugin](https://v1-36.docs.kubernetes.io/docs/concepts/extend-kubernetes/compute-storage-net/device-plugins/)

## 02 从 Helm 值到节点 Pod，控制器怎样协作

- **问题与预期结论**　Helm 已安装，为什么新节点还会陆续出现组件 Pod？读者应能从安装输入追到生效的 CR、Node 标签和 DaemonSet，判断配置改动由哪个控制环处理。
- **解释顺序**　先展示 chart 安装 Operator Deployment、提供 CRD 并按开关生成 `ClusterPolicy/cluster-policy`，默认还部署 NFD 子 chart。用一个 `toolkit.enabled` 值贯穿 `values → CR spec → Operator 协调 → 节点工作负载`。NFD 更新 PCI 标签后，Operator 更新节点部署标签，并按策略协调管理组件的对象。DaemonSet 控制器依据 Pod 模板和节点条件创建 Pod，kubelet 在节点上执行容器与 init 检查。交代同一 CR 可反复协调，新节点入池无需再次安装 Helm。组件对象的创建和容器通过依赖检查是不同时间点。
- **支撑材料**　并排摘取 `clusterPolicy.deployCR`、`ClusterPolicy.spec.toolkit.enabled` 和 Toolkit DaemonSet 的 `spec.template.spec.nodeSelector`。对照 Node 的 `feature.node.kubernetes.io/pci-10de.present`、`nvidia.com/gpu.present`、`nvidia.com/gpu.deploy.container-toolkit`，再用 Pod 的 `spec.nodeName` 和 `ownerReferences` 验证实际落点与所属 DaemonSet。安装时使用的字段取 Helm 值，当前意图取线上 CR，实际行为取生成对象与节点状态。 [v26.7.2 ClusterPolicy 模板](https://raw.githubusercontent.com/NVIDIA/gpu-operator/v26.7.2/deployments/gpu-operator/templates/clusterpolicy.yaml) · [Operator 节点识别与状态管理](https://raw.githubusercontent.com/NVIDIA/gpu-operator/v26.7.2/controllers/state_manager.go) · [Toolkit DaemonSet 模板](https://raw.githubusercontent.com/NVIDIA/gpu-operator/v26.7.2/assets/state-container-toolkit/0500_daemonset.yaml) · [Kubernetes DaemonSet API](https://v1-36.docs.kubernetes.io/docs/reference/kubernetes-api/apps/daemon-set-v1/)
- **DRA 对照**　用一个配置差异框说明 `clusterPolicy.deployCR=false`、`gpuCluster.deployCR=true` 如何创建集群级单例 `GPUCluster/gpu-cluster`。此 CR 协调 DRA kubelet 插件、DRA Validator 与监控，驱动由宿主机预装或另一个 `NVIDIADriver` CR 交付，平台侧事先配置支持 CDI 的运行时。v26.7.2 托管路径要求 Kubernetes ≥ v1.34.2、有 DeviceClass API、GPU 驱动 ≥ 580，且 `ClusterPolicy` 与 `GPUCluster` 在同一集群互斥。该流程面向新装集群，原地迁移在官方支持范围之外。整卡对照显式关闭默认启用的 ComputeDomain，资源分配过程回到第 11 章。 [v26.7.2 GPUCluster 模板](https://raw.githubusercontent.com/NVIDIA/gpu-operator/v26.7.2/deployments/gpu-operator/templates/gpucluster.yaml) · [NVIDIA 托管 DRA 的组件、前置条件及限制](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/26.7/dra-intro-install.html)

## 03 节点已有驱动或 Toolkit 时，谁负责后续维护

- **问题与预期结论**　两台节点都可运行 `nvidia-smi`，怎样确认当前驱动由节点镜像、`ClusterPolicy` 还是 `NVIDIADriver` 管理？读者应能决定新节点池需保留哪些 Operator 组件，以及谁要更新并验收预装软件。
- **解释顺序**　先列驱动与 Toolkit 都由 Operator 管理、只预装驱动、两者都预装、只预装 Toolkit 四种组合。说明 `driver.enabled=false` 和 `toolkit.enabled=false` 的集群范围，再用 `nvidia.com/gpu.deploy.driver=false` 解释主例中的单节点驱动排除，和 `nvidia.com/gpu.deploy.operands=false` 的整套组件排除范围。保留默认驱动部署时，若 driver Pod 的 init 检出预装驱动，Operator 路径会退出该节点的驱动部署，其他组件继续启动。预装 Toolkit 配容器化驱动时，核对驱动根目录和运行时生效配置。已有 NFD 时，说明 `nfd.enabled=false` 的含义及核对现有 NFD 标签的必要性。
- **支撑材料**　拟用责任表逐行给出 Helm 差异、运行在哪些节点、由谁管理版本、用什么验证。驱动路径以 driver Pod、节点驱动枚举和实际驱动根目录交叉判断；Toolkit 路径读生成的 Toolkit Pod、节点上的 containerd 生效配置与 CDI 规格。用 `/run/nvidia/driver` 说明容器化驱动文件的位置及预装 Toolkit 的依赖。默认 `cdi.enabled=true` 始于 v25.10.0。主例的 v26.7.2 控制器为插件设置 `DEVICE_LIST_STRATEGY=cdi-annotations,cdi-cri`，正文配生成对象核对实际值。普通整卡工作负载沿运行时原生 CDI 路径验证。使用 `NVIDIA_VISIBLE_DEVICES` 的管理容器在 NRI 关闭时另核对 `RuntimeClass` 及实际 handler。 [NVIDIA 预装场景、节点排除及 containerd 配置](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/26.7/getting-started.html#common-deployment-scenarios) · [CDI 与管理容器](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/26.7/cdi.html) · [v26.7.2 配置注入源码](https://raw.githubusercontent.com/NVIDIA/gpu-operator/v26.7.2/controllers/object_controls.go)
- **按池交付驱动**　用 `driver.nvidiaDriverCRD.enabled=true → ClusterPolicy.spec.driver.useNvidiaDriverCRD=true` 引出驱动控制权的委托。并排给出两个 `nvidia.com/v1alpha1` 的 `NVIDIADriver` 摘录，保留 `spec.version`、`spec.nodeSelector`，再加一个 `spec.default: true` 的回退例。让读者根据两组节点标签判断哪个 CR 接管，推演两个非默认选择器重叠时报 `ConflictingNodeSelector`，并保留已有驱动归属。核对 Node 的 `nvidia.com/gpu-operator.driver.owner`、驱动 DaemonSet 选择器和 CR 条件。迁移与驱动升级时序交给第 19 章。 [NVIDIA Driver CRD 的管理模式和匹配规则](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/26.7/gpu-driver-configuration.html) · [v26.7.2 NVIDIADriver API 定义](https://raw.githubusercontent.com/NVIDIA/gpu-operator/v26.7.2/deployments/gpu-operator/crds/nvidia.com_nvidiadrivers.yaml)

## 04 新 GPU 节点从注册到可供 Pod 使用，经历哪些状态

- **问题与预期结论**　`gpu-h1` 已显示 `Ready`，什么时候可以把它计入 GPU 池？读者应能用同一节点的证据识别硬件已发现、组件已覆盖、设备已上报和工作负载可用四个时点。
- **解释顺序**　按 `Node 注册 → NFD 标签 → Operator 部署标签 → 驱动与 Toolkit 就绪 → 插件注册与设备上报 → Node 资源发布 → 测试 Pod 使用 GPU` 推进。画出确实存在的启动依赖，例如 Toolkit DaemonSet 的 `driver-validation` init，以及 Device Plugin 的 `toolkit-validation` 检查 `/run/nvidia/validations/toolkit-ready` 和驱动模块。NFD 发现、GFD 标签、监控启动和不同对象的状态更新可交错。用两卡容量和测试请求连接资源可调度与容器可计算两层验证。
- **支撑材料**　拟在时序图下配同一节点的教学快照。假设旧 GPU 节点始终就绪，CPU 节点始终不匹配 Device Plugin。以 Device Plugin DaemonSet 的 `desiredNumberScheduled/numberReady` 计数和新节点的 GPU `Capacity/Allocatable` 为两列，逐行说明各字段可作何判断。基于 NVIDIA 的 CUDA VectorAdd 示例增加 `gpu-h1` 的节点选择器，保留 `resources.limits["nvidia.com/gpu"]: 1`。用 PodResources 记录分配的设备 ID，用 VectorAdd 的退出状态和测试输出验收计算。假设新节点原无其他 GPU 请求，测试 Pod 的请求计入后，调度余量为 `2 − 1 = 1`，Node 的 GPU `Allocatable` 仍是 2。 [Toolkit 的驱动检查](https://raw.githubusercontent.com/NVIDIA/gpu-operator/v26.7.2/assets/state-container-toolkit/0500_daemonset.yaml) · [Device Plugin 的启动门槛](https://raw.githubusercontent.com/NVIDIA/gpu-operator/v26.7.2/assets/state-device-plugin/0500_daemonset.yaml) · [Kubernetes Device Plugin 与 PodResources](https://v1-36.docs.kubernetes.io/docs/concepts/extend-kubernetes/compute-storage-net/device-plugins/) · [NVIDIA CUDA VectorAdd 示例](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/26.7/getting-started.html#cuda-vectoradd)

## 05 多处状态不一致时，哪一项证据能缩小故障范围

- **问题与预期结论**　`ClusterPolicy` 显示 `ready`、Validator 通过或某个 DaemonSet 全部就绪，分别能证明什么？读者应能从集群状态定位到目标节点、组件和容器，选择一项可区分相邻故障层的检查。
- **解释顺序**　先看 `ClusterPolicy.status.state` 与 `status.conditions[]` 的 `type/status/reason/message`。v26.7.2 控制器在当前协调结束且无 GPU 节点或无 NFD 标签时也会写 `ready`，通过原因区分。随后看组件 DaemonSet 的期望数、当前节点数、就绪数和目标 Node 上的 Pod。最后将 Validator 的检查覆盖范围与业务 Pod 的调度、分配和注入逐项对照。DRA 的对应证据是 `GPUCluster` 条件、节点的 `ResourceSlice`、`DeviceClass` 和 DRA Validator 的 Claim 及 Pod 结果。
- **Validator 的证据**　`driver-validation` 检查预装或容器化驱动，从 `driver-ready` 取 `IS_HOST_DRIVER` 和 `NVIDIA_DRIVER_ROOT` 核对归属。 `toolkit-validation` 在容器内运行 `nvidia-smi`，成功后写 `toolkit-ready`。 `cuda-validation` 在工作负载开关开启时创建指定 `spec.nodeName` 的测试 Pod，用它说明节点上的 CUDA 验证，标准 GPU 请求的调度仍由第 04 节的普通 Pod 验证。 `plugin-validation` 在主例检查 Node 的 `.status.capacity` 是否有数量至少为 1 的 GPU 资源，清单默认设 `WITH_WORKLOAD=false`，显式开启才追加带 GPU 请求的测试。用“两张卡仍上报但均被标为不健康”的快照推导 `Capacity=2`、`Allocatable=0`，说明通过这项容量检查后还需要核对哪些字段。 [Validator init 清单](https://raw.githubusercontent.com/NVIDIA/gpu-operator/v26.7.2/assets/state-operator-validation/0500_daemonset.yaml) · [v26.7.2 Validator 实现](https://raw.githubusercontent.com/NVIDIA/gpu-operator/v26.7.2/cmd/nvidia-validator/main.go) · [Kubernetes 不健康设备的资源计数](https://v1-36.docs.kubernetes.io/docs/concepts/extend-kubernetes/compute-storage-net/device-plugins/#device-plugin-and-unhealthy-devices)
- **支撑材料**　拟给下表各一份同节点、相近时间的对象摘录和观测记录。Pod 用 `spec.nodeName`、`metadata.uid`、`status.initContainerStatuses`、容器名与事件 `reason/message` 对齐日志。Operator 侧用 `ClusterPolicy step completed` 的 `state:` 和 `status` 定位组件，再读节点侧当前或上一轮失败容器。材料取自固定版本清单、控制器代码和官方故障样例。 [v26.7.2 ClusterPolicy 状态分支](https://raw.githubusercontent.com/NVIDIA/gpu-operator/v26.7.2/controllers/clusterpolicy_controller.go) · [Validator init 清单](https://raw.githubusercontent.com/NVIDIA/gpu-operator/v26.7.2/assets/state-operator-validation/0500_daemonset.yaml) · [NVIDIA 故障样例](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/26.7/troubleshooting.html) · [NVIDIA DRA 安装验证](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/26.7/dra-intro-install.html#validate-installation)

| 教学异常 | 拟提供的证据 | 预期判断与下一步 |
| --- | --- | --- |
| 策略显示 `ready`，新节点没有插件 Pod | CR 条件、NFD PCI 标签、插件部署标签、DaemonSet 的期望数与事件 | 从发现、选择器、污点和容忍查起。若新节点已计入期望数，再看 DaemonSet 的 Pod 创建事件。 |
| Toolkit 与插件都卡在 init | 两个 init 的状态、`k8s-driver-manager` 或 `nvidia-driver-ctr` 的日志、驱动枚举 | 确认 Toolkit 是否等驱动，以及插件是否继续等 Toolkit。用内核或包管理日志区分驱动安装阶段的原因。 |
| 插件 Pod 就绪，Node 未出现 GPU 资源 | 插件注册与枚举日志、同节点的 kubelet 日志、Node 状态 | 确定插件有无枚举和上报、kubelet 有无接收，判断是否只缺 Node 状态更新。 |

| 资源已发布，单卡验证仍失败 | Pod 请求和绑定状态、分配或 CDI 注入错误、容器 UUID 与 CUDA 探针结果 | 用绑定和创建状态先区分调度、节点分配及注入，再用探针退出状态判断是否已进入 CUDA 计算阶段。 |

## 06 镜像、软件包和节点池差异怎样改变部署结果

- **问题与预期结论**　同一份配置在试验节点通过，为什么到隔离网络或不同内核的节点池就失败？读者应能根据部署产物找出所需的容器镜像和内核软件包，并判断哪些节点可以共用一套驱动配置。
- **解释顺序**　先从固定 chart 值和节点 OS 推导最后的镜像清单。清单包括启用的控制器、子 chart、组件、init 容器与验证工作负载。离线时把 chart 获取、节点运行时拉容器镜像、传统 driver 容器获取匹配运行内核的系统软件包分开验证。用一个镜像拉取失败及一个镜像已拉到、安装阶段缺内核头文件的变体区分故障。预编译驱动省去启动时的软件包下载，前提是支持矩阵和 registry 同时有对应驱动分支、完整内核版本、变体与 OS 标签的镜像。
- **支撑材料**　拟从 `repository/image/version`、`imagePullSecrets` 和 `driver.repoConfig.configMapName` 追到线上 Pod 的实际 `image` 与 driver 容器的包源配置。配一个 `ErrImagePull`/`ImagePullBackOff` 事件和一个包仓库缺目标 `linux-headers` 的**教学**记录，对照镜像地址、仓库可达性、容器日志与 `uname -r`。预编译行用 `<branch>-<kernel-release>-<os-tag>` 展开期望标签，从目标仓确认具体标签和摘要。 [NVIDIA 离线安装和包源字段](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/26.7/install-gpu-operator-air-gapped.html) · [NVIDIA 预编译驱动的标签与限制](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/26.7/precompiled-drivers.html) · [Kubernetes 镜像拉取状态](https://v1-36.docs.kubernetes.io/docs/concepts/containers/images/)
- **异构池与版本算例**　给出 Ubuntu 22.04 和 24.04 两个 GPU 池，假定二者各有一种内核、共同采用同一个 `NVIDIADriver` CR 的传统驱动设置。按“一条 CR、两种 OS 版本”推得两组 driver DaemonSet，并逐池核对选择器和镜像。对照直接由 `ClusterPolicy` 配置容器化驱动时 GPU worker 池需同 OS 版本的条件，以及各池预装驱动的选择。兼容矩阵保留 GPU 型号、架构、OS、内核、驱动分支、Kubernetes、containerd、Toolkit、插件和 CUDA 验证镜像，区分 NVIDIA 声明的支持与现场验证通过。生产发布顺序、排空和回滚交给第 19 章。 [NVIDIA 安装前置条件](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/26.7/getting-started.html#prerequisites) · [NVIDIADriver 的 DaemonSet 分组规则](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/26.7/gpu-driver-configuration.html) · [NVIDIA v26.7 支持矩阵](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/26.7/platform-support.html)

## 待核实项

- **实机基线**　待确认 GPU 环境是否可取得。若有环境，采集完整 OS/内核版本、节点镜像、镜像摘要、CDI 规格和已加载的运行时配置，以及上报、Validator 与整卡 CUDA 探针的同节点记录。离线写作时用标明假设的快照和固定版本清单说明机制。
- **部署产物**　待以所选部署环境核对转换后的 DaemonSet、实际验证 Pod 的镜像与 GPU 请求、默认与预装配置下生效的 RuntimeClass。离线举例中具体 driver tag、内核包名和摘要待对应目标 kernel release 与仓库确认。若做 DRA 实验，另取实际 `ResourceSlice` 与 Validator Claim 记录。

## 供审查的取舍

1. **DRA 篇幅**　建议保留管理对象、版本条件和验收证据的小对照。若希望准备新装 DRA 集群，可将它扩成独立一篇，并用实际生成的对象走完一次节点交付。
2. **材料深度**　建议以可离线推导的 GPU 节点入池案例为主，包含软件归属表、节点时间线和故障证据。若希望正文可跟做，可增加一套固定版本的小型实验，实测取决于可用 GPU 环境。
