# 第 12 章 GPU Operator 如何管理节点软件｜内容大纲

## 读者起点与学习目标

读者认识 Node、Pod、DaemonSet、kubelet 和容器运行时。第 03 章分清 Linux 内核驱动和应用镜像内的 CUDA 用户态，第 10 章建立容器设备接口 CDI，第 11 章建立节点发现、资源上报、调度选节点和节点分配的过程。本章先用一台新节点交代这些软件从何而来，再解释为什么配置已提交、组件已部署和业务已能使用 GPU 是三个可独立观察的结果。

读完后应能完成四项任务。

1. 从 Helm 值追到线上策略、部署标签、DaemonSet 模板与节点 Pod，解释新节点如何自动进入部署范围。
2. 结合节点状态、组件覆盖、init 检查、资源与 Pod 结果，定位最早缺证据的一步，并选择能验证这一判断的检查。
3. 在已有驱动或 Toolkit、异构 OS、隔离网络等条件下确定维护方、节点覆盖、驱动制品及包源依赖。
4. 对比 GPU Operator 托管 Device Plugin 与 DRA 时的管理对象、驱动和运行时前提，并为两种路径选取相应的验收证据。

## 贯穿案例与版本

- 集群已有 CPU 节点 `cpu-0` 和两卡节点 `gpu-h0`，加入同型的 `gpu-h1`。两台 GPU 节点各有两张 H100 PCIe，采用整卡独占、无 NVSwitch。案例与第 11 章的节点和独立插件版本分别取样，第 13 章继续使用这里的两个 GPU 节点名。
- 主例以 GPU Operator `v26.7.2` 的 chart、源码与资产为准，采用 Kubernetes v1.36、x86_64 Ubuntu 24.04 LTS 和 containerd 2.3。默认驱动为 `595.91.07`，Container Toolkit 为 `1.20.1`，Device Plugin 和 GFD 为 `0.20.1`。启用 chart 附带的 NFD 和 CDI，关闭 NRI。DRA 对照采用托管的 NVIDIA DRA Driver `v0.5.1`。
- 状态、计数、日志摘要、驱动池和离线仓库材料均为教学推演，分别陈述变化的条件。时间顺序表达依赖，跨对象字段可能异步更新。配置区分 Helm 值、CR 与运行时产物，片段标明省略项和占位符。
- 用 Mermaid 表达运行依赖和协作过程，保留三张原插图。部署范围图归第 04 篇，驱动根目录图归第 05 篇，离线两次下载图归第 06 篇。同步检查图号、文件路径、节点标识、方向、替代文本及图注。

## 技术依据与验证范围

用 NVIDIA v26.7 文档核对平台、运行时、预装、驱动 CR、DRA 和离线支持条件，用 `v26.7.2` 的 chart、节点组件模板和控制器源码限定默认值、标签、转换与 Validator 行为。资源计数、调度与 DRA 对象按 Kubernetes v1.36 文档解释。引用随论断放在正文。 [NVIDIA 组件矩阵](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/26.7/platform-support.html) · [GPU Operator v26.7.2 发布说明](https://github.com/NVIDIA/gpu-operator/releases/tag/v26.7.2) · [Kubernetes v1.36 Device Plugins](https://v1-36.docs.kubernetes.io/docs/concepts/extend-kubernetes/compute-storage-net/device-plugins/)

目标环境的内核、镜像标签与摘要、实际生成的 DaemonSet、节点有效运行时配置、CDI 规格、Validator 与工作负载输出，以及 DRA 的实际切片和 Claim，需要按目标集群验证。
