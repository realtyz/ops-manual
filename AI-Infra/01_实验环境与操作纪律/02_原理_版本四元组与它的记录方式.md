# 版本四元组与它的记录方式

一次驱动升级只动了四项里的第一项，升级后报错却指向第三项；又一次回滚把第一项改回原值，问题仍然存在，因为真正被改动的其实是第二项。这类场景反复出现的原因不在升级动作本身，而在记录：如果记录里只有一个版本号，那么升级前后唯一的比对对象就只有那一项，其余三项在变更中是否被动过、动到了什么程度，事后没有任何依据。版本四元组要解决的就是这件事——它把**驱动、CUDA、通信库（NCCL）与 RDMA 栈**四项固定成一组必须同时记录的字段。这四项是同一件事的四个侧面：能跑、能跑多快、走哪条路径这些结论都建立在某一套组合之上，换了其中任何一项，之前的结论就要重新确认。

四项之间的**约束方向**——哪一项抬高会把哪一项变成下限、升级顺序为什么有先后——不在本篇展开，它属于驱动那一条链路的内容；本篇只回答两件事：每一项各自怎么取、怎么把它记成一份可比的组合。

## 每一项都要取，而且各有歧义

四项里的第一项起就有多个「版本」，取值入口不同，读数含义也不同。把每一组取值入口摆出来，是记录不歧义的前提。

| 项 | 取值入口 | 读到的是什么 | 常见歧义 |
| --- | --- | --- | --- |
| 驱动 | `nvidia-smi` 头部显示的驱动版本 | 用户态工具与库所见的驱动版本 | 它与已加载内核模块的版本是两个量，可以不一致 |
| 驱动 | `/proc/driver/nvidia/version` 的版本行 | 已加载内核模块的版本 | 系统里有多个模块来源时，这一行才是当前生效的那个 |
| 驱动 | `modinfo -F version nvidia` | 磁盘上模块文件自称的版本 | 磁盘上的模块与已加载的模块未必是同一份 |
| CUDA | `nvidia-smi` 头部的 CUDA 版本 | 当前驱动**支持的最高** CUDA 运行时版本，是上限不是安装版本 | 把它当成机器上安装的 toolkit 版本是最常见的读错 |
| CUDA | `nvcc --version` | 编译工具链的版本 | 有工具链不等于运行期加载的运行时库是同一个版本 |
| 通信库 | 训练框架启动时报告的版本，或测试工具编译时的版本 | 本次运行实际加载的那一份 | 框架、测试工具与容器镜像可能各带一份，取值要说明来源 |
| RDMA 栈 | `ofed_info -s` | 厂商栈的整份发行版标识 | 它标识的是整套栈，不是某一个模块或库文件的版本 |
| RDMA 栈 | 内核自带栈下的模块与设备来源 | 栈来自内核自带还是来自厂商安装包 | 内核自带栈下没有厂商栈的命令，命令不存在不代表栈缺失 |

把这些入口按「字段 → 是什么与单位 → 判据 → 与谁同看 → 转向哪一步」整理成读法表，是记录模板的核心部分。

| 字段 | 是什么与单位 | 判据 | 与谁同看 | 转向哪一步 |
| --- | --- | --- | --- | --- |
| 头部显示的驱动版本与应用加载的运行时版本 | 两个分别由工具输出与进程实际链接反映的版本 | 两者不一致说明出现了版本不匹配，不是显示问题 | 与已加载内核模块的版本同看 | 若内核模块版本与其它两项都不同，先判断是否为升级后未重启 |
| 头部显示的 CUDA 上限与工具链版本 | 一个是能力上限，一个是编译工具版本 | 两者不相等是正常现象，把两者当成同一个版本才是读错 | 与运行期实际加载的运行时库版本同看 | 两者关系与预期不符时，先确认应用链接的是哪一份运行时 |
| 通信库的版本串 | 形如「主版本.次版本.修订号+构建时使用的 CUDA 版本」 | 后缀标识这份库编译时使用的 CUDA，它要落在驱动的支持范围内 | 与头部的 CUDA 上限、工具链版本同看 | 后缀超出现有驱动上限时，先确认加载的是镜像内哪一份库 |
| RDMA 栈的发行版标识 | 厂商栈的整套发行版标识，形如「发行版名-版本号」 | 它标识整套栈而不是单个模块，与单个模块版本不是同一个口径 | 与网卡驱动来源、设备固件版本同看 | 命令不存在时先判断这台机器本来就该用内核自带栈，还是安装有缺项 |

## 记成一组，而不是记成一行

记录的形态决定它能不能用于比对。四项分开写在四个地方、或者只留下一个笼统的「版本已确认」，都无法支撑一次升级前后的对照。可用的记录满足四条要求：

- **成组**：四项一次记齐，不允许先记一项、其余留待以后补。
- **带来源**：每一组取值要写清是用哪个入口取的，尤其是通信库与 RDMA 栈，来源不同读数就不同。
- **带时刻**：同一次记录要有统一的采集时刻，跨时刻的两组值不能直接相减。
- **带环境**：机型、GPU 型号、网卡型号与固件版本、内核版本要随同一份记录留档，缺其中任一项，这组值就失去了可比的边界。

一份记录能不能用，判据很直接：**只看这份记录，能不能回答「这次变更改了哪几项、从什么改到什么」**。回答不了，说明它还停留在「有一组数字」的层面，达不到「有一份基线」的要求。

## 只报一项会掩盖什么

把四项压成一项的代价，在一次变更里会具体展开。下表按「报了什么 → 掩盖了什么 → 后果」的顺序走一遍。

| 记录里只有 | 掩盖了什么 | 后果 |
| --- | --- | --- |
| 驱动版本 | 同一台机器上可能同时存在多个驱动版本表示，且通信库与栈的版本未被记录 | 变更后行为变化，无法判断是哪一项引起的 |
| CUDA 上限 | 上限与实际安装的工具链、运行期加载的运行时库是三个量 | 升级了工具链却没有升级运行时，读不出来 |
| 通信库版本 | 框架、测试工具与镜像可能各带一份，只记一个数字不说明来源 | 复现时加载了另一份库，结论对不上 |
| RDMA 栈标识 | 栈的发行版标识、网卡模块版本与固件版本是三个量 | 栈被替换而其它项未记录，跨机比对失效 |

四项一起记录的收益也在这里：任何一次行为变化，都能先在四项里定位「哪一项变了」，把范围从「整套环境」缩到「一个字段」。

```bash
# 验证：四项的取值入口各取一次，按下表整理成一组（只读，生产节点上也可以做）
nvidia-smi; cat /proc/driver/nvidia/version; nvcc --version; ofed_info -s
```

上面这条命令只用来说明四项各自的取值入口；版本串、发行版标识与是否有厂商栈命令随机型、版本四元组与安装方式变化，这里不给出示例取值，任何对照使用的数值仅示意、不代表你的环境。

**第一反应不要做什么**：不要只报一个版本号就说四元组已经记录；不要把头部显示的 CUDA 上限当成安装的 toolkit 版本；不要用不同时刻取到的四项拼成一组；不要在记录里省略采集时刻与机型。正确的顺序是四项一次记齐、各写清来源、每项都带上取值时刻，再把它与上一组记录逐项对照。
