# 高频误判

下面十条取自主机侧环境判定、版本记录、证据采集与验收判断四类真实处境，每一条按同一套字段展开：场景、常见误判以及它为什么看起来成立、判据、一句话结论、出处；其中判据一项固定交代读哪个字段、该字段是上限还是实际生效值或累计量与瞬时量、期望的趋势是什么、需要与谁同看，以及哪些条件一旦改变结论就会翻转。

### 「这台机器跑通了集合通信，所以 RoCE 的能力可以下结论」

- **场景**：在一台只有普通以太网卡的机器上用软件模拟设备跑通集合通信，或在双机直连环境里跑通一次，于是把「RoCE 可用」写进交付记录。
- **常见误判**：把流程验证当成能力验证。它看起来成立的原因在于程序确实跑完、退出码正常，而两类验证在命令层面完全一样。
- **判据**：先读设备来源，判断这个 RDMA 设备是真实硬件还是软件模拟；再读机器档位，判断这台机器属于单机、双机还是多机。判据是结论里出现的每一类对象都落在这档环境的覆盖范围内；同看对象是交付记录里声明的档位字段。条件会变：换到真实硬件与双机档位之后，同一条命令的结论才成立。
- **结论**：跑通只证明流程能走通；能不能支撑 RoCE 结论由设备来源与机器档位决定，不由程序是否成功决定。
- **出处**：NVIDIA GPUDirect RDMA 文档（模拟设备不具备显存直连能力）；Linux 内核文档中 RDMA 子系统的说明（设备来源的判断方式）。

### 「显卡查询工具头部的 CUDA 版本就是这台机器装的 CUDA」

- **场景**：整理版本记录时，把查询工具头部的 CUDA 版本直接抄成「本机 CUDA 版本」，与编译工具链的版本混为一项。
- **常见误判**：把驱动支持的上限当成已安装版本。它看起来成立的原因在于这个字段确实叫 CUDA 版本，而且它就显示在最显眼的位置。
- **判据**：读头部的 CUDA 字段，它的含义是当前驱动支持的最高运行时版本；再单独读编译工具链的版本。两者不相等是正常现象，判据是这两个字段同时存在、各自标注来源，而不是比较它们是否相等；同看对象是应用运行期实际加载的运行时库版本。条件会变：只升级工具链而不升级运行时库时，头部字段完全不变。
- **结论**：头部字段是上限，不是安装版本；只有把上限、工具链与运行期实际加载三者的来源都写清，CUDA 这一项才算记录完整。
- **出处**：NVIDIA CUDA 兼容性文档与 CUDA 安装指南（驱动支持上限与已安装工具链的区别）。

### 「驱动版本对上了，四项版本就齐了」

- **场景**：变更记录里只留下驱动一项，事后行为发生变化，无法判断是哪一项引起的。
- **常见误判**：把「版本记录」等同于「记一个版本号」。它看起来成立的原因在于变更的入口确实是驱动包，其余三项没有被直接触碰。
- **判据**：判据不是记了没有，而是这份记录能不能回答「这次变更改了哪几项、从什么改到什么」。检查四项是否成组、每一项是否带取值来源、是否共用同一个采集时刻；同看对象是变更前后的两份记录。条件会变：如果通信库是由镜像带入的，那么升级镜像同样会改动四项中的一项，而这一项不在包管理器的视野里。
- **结论**：只报一项等于没有记录；四项必须成组、各写来源、共用时刻，才能在变更后定位到具体是哪一项变了。
- **出处**：NCCL 用户指南的环境变量一页与排障章节（通信库版本串的构成与查看方式）；NVIDIA 驱动安装指南中关于版本锁定的各节（驱动的多种版本表示）。

### 「变更后能跑起来，就算复测通过」

- **场景**：变更之后复跑一次程序，程序正常结束、数字看起来也正常，于是宣布变更完成。
- **常见误判**：把一次孤立的测量当成复测。它看起来成立的原因在于这次运行确实没有报错。
- **判据**：复测要与基线同环境、同命令与参数、同单位，并且与基线结果逐项对照。判据是差异有明确的对照对象；同看对象是变更前的那一份基线卡与它记录的四项要素。条件会变：若中间换过进程数或测试尺寸，这次数字与基线就不在同一个口径上，不能相减。
- **结论**：没有对照对象、或者口径与基线不同的复测不构成验收；复测的完整形式是同口径的两次测量之差。
- **出处**：集合通信测试工具的仓库说明（两种带宽口径各自的定义）；NCCL 用户指南排障章节中关于性能与调优的一节。

### 「错误计数归零，说明卡好了」

- **场景**：前一天读取到一组非零的错误计数，第二天再看已经归零，于是判断硬件已经恢复正常。
- **常见误判**：忽略计数所在的生命周期。它看起来成立的原因在于同一个字段前一天非零、后一天为零，趋势方向确实在变好。
- **判据**：显存错误计数分两组，一组属于「本次初始化到反初始化」这一段生命周期，另一组长期累计。读第一组的归零只能说明这一段生命周期结束了，不能说明硬件恢复正常；判据是第一组的值与 GPU 是否处于保持初始化状态同看。条件会变：若这台机器启用了保持初始化的机制，第一组就不会因为客户端退出而清零，此时它的趋势才具备长期意义。
- **结论**：归零不等于恢复；只有确认清零的原因是「生命周期结束」还是「问题消失」，这个读数才能支撑结论。
- **出处**：NVIDIA 驱动的持久化文档中关于数据持久性的一节（两组错误计数各自的生命周期）。

### 「先动手，出问题再抓日志」

- **场景**：故障出现后先重启、先卸载模块、先让作业退出，等到想复盘时再去收集材料。
- **常见误判**：认为日志与计数会一直留着。它看起来成立的原因在于这些文件确实一直存在于系统里，读写也一直可用。
- **判据**：重启、模块卸载与作业退出这三类动作各自会清掉一类现场：内核环形缓冲与未持久化日志、模块与设备暴露的运行时状态、以及进程级现场。判据是取证是否排在这三类动作之前；同看对象是当前计划的下一步处置动作。条件会变：日志若已配置为持久化，上一次启动的内核消息可能仍可读，但能否读到要按启动编号确认，且环形缓冲早先的消息仍可能已被覆盖。
- **结论**：取证是事前动作；一旦重启、卸载或作业退出发生，某一类现场就无法再补。
- **出处**：`dmesg(1)` 与 `journalctl(1)` 手册页（环形缓冲的滚动行为、按启动编号查询日志的条件）；NVIDIA 驱动的持久化文档（模块卸载与重启对运行时状态的影响）。

### 「隔离就是把调度器上的作业排掉」

- **场景**：在调度器里把节点标记为不可调度，确认不再有新任务被派上来，随即执行变更。
- **常见误判**：只检查了新分配这一个方向。它看起来成立的原因在于调度器侧确实已经没有待调度的任务。
- **判据**：隔离完成的判据有三条同时成立——调度器侧不再产生新的分配、已有作业确已退出或已在其它节点上继续运行、设备上不再有残留的进程占用。三条要逐条核对；同看对象是设备占用情况与作业退出记录。条件会变：一条已经在运行的作业不会因为节点被标记而自动退出，它会在设备被摘走时异常结束。
- **结论**：隔离的判据落在设备上，不落在调度器上；只挡住新任务不构成隔离完成。
- **出处**：NVIDIA 驱动安装指南中关于卸载与升级的各节（这类动作会中断同一台机器上的全部作业）。

### 「栈查询命令不存在，说明 RDMA 栈没装」

- **场景**：在一台使用内核自带 RDMA 栈的机器上执行厂商栈的查询命令，命令提示不存在，于是判断这台机器没有 RDMA 栈。
- **常见误判**：把「厂商栈命令不存在」等同于「栈缺失」。它看起来成立的原因在于这条命令在装了厂商栈的机器上确实会返回一个版本标识。
- **判据**：厂商栈的查询命令只在厂商安装包存在时可用；内核自带栈下这条命令本来就不存在。判据要换成模块来源与设备清单——读网卡内核模块的来源与设备清单，确认栈是否随内核提供；同看对象是网卡驱动信息与设备清单。条件会变：若这台机器本来计划使用厂商栈，则命令不存在是一条安装缺项，而不是正常状态。
- **结论**：命令不存在只说明栈不是厂商安装包；判断栈是否可用要回到模块来源与设备清单。
- **出处**：Linux 内核文档中 RDMA 子系统的说明；网卡厂商驱动与固件查询工具说明。

### 「软件模拟环境跑出的带宽可以作为基线」

- **场景**：在没有真实网卡的环境里用软件模拟设备测出一组带宽与延迟，把它写进基线卡并用于后续对照。
- **常见误判**：把流程环境的数字当成硬件证据。它看起来成立的原因在于测量过程完整、单位明确、数值可复现。
- **判据**：先确认设备来源，模拟设备的性能由处理器与普通以太网路径决定，与真实网卡的硬件卸载无关。判据是这份记录里是否声明了设备来源；同看对象是基线卡的环境字段。条件会变：在真实硬件上重新测量一次，同样的测试参数会给出不同量级的数字，两组不能放进同一个对照序列。
- **结论**：模拟环境的数字只能用于验证流程与熟悉命令，不能进入任何性能结论或性能基线。
- **出处**：NVIDIA GPUDirect RDMA 文档（显存直连所需的模块前置，以及模拟设备不具备该能力这一条）。

### 「同机型，基线数字可以直接横向比较」

- **场景**：另一台同型号节点的基线数字拿来与本机对照，发现数值低了一截，于是按性能异常处理。
- **常见误判**：只看机型这一个维度。它看起来成立的原因在于两台机器的硬件配置完全相同。
- **判据**：基线的可比性由四项共同定义——环境、命令与参数、结果、采集时间。同机型只覆盖了第一项中的一部分；还要核对命令与参数是否一致、测量所在的卡与网卡的亲和关系是否一致、以及两次取值的时间跨度是否过大。判据是四项逐项对齐；同看对象是两份基线卡的字段。条件会变：两台机器的亲和关系不同，或其中一台在测量时有其它作业占用同一张卡，都会让数字不可比。
- **结论**：同机型不等于可比；四项要素对齐之前，两份数字不能相减。
- **出处**：集合通信测试工具的仓库说明（参数与口径的定义）；`nvidia-smi(1)` 手册页（拓扑字段的口径）。

## 值班口径

这十条可以归成四类共同成因。第一类是把「跑通」当成结论：可用性、正确性与性能是三个互不替代的问题，而程序能跑完只回答第一个，程序还可能跑在一条不打算用的路径上，因此凡是结论止步于「跑通了」的判断，都需要补一次路径确认与一次结果校验。

第二类成因是读数口径：把上限当实际生效值（头部的 CUDA 版本）、把生命周期清零当问题消失（错误计数归零）、把命令不存在当功能缺失（厂商栈查询命令），这三件事的共同修正是先问「这个字段代表的是上限、生命周期还是存在性」，再决定它的趋势能不能支撑结论。

第三类成因是时序：取证必须排在重启、模块卸载与作业退出之前，而这三类动作在处置流程里几乎必然发生；因此取证的判据不是「材料全不全」，而是「顺序对不对」。

第四类成因是记录形态：四项版本必须成组、带来源、共用时刻，基线的可比性也必须四项齐备，这样才能在变更之后回答「改了哪几项」。任何一类的结论依赖某个版本或某个默认值时，都必须同时给出驱动、CUDA、通信库与 RDMA 栈四项，缺任一项时读数不构成结论。

**第一反应不要做什么**：不要用「跑通了」宣布验收通过；不要把头部显示的 CUDA 版本当成安装版本；不要只报一个版本号就说版本已记录；不要把一次孤立测量当成复测；不要因为一组计数归零就判断硬件恢复；不要在重启、卸载或作业退出之后才去取证；不要把调度器排空当作隔离完成；不要把厂商栈命令不存在当作栈缺失；不要把软件模拟设备的数字写进性能结论；不要拿同机型但参数与亲和关系不同的两份数字直接相减。正确的顺序是先确认环境档位与设备来源，再按固定字段成组记录四项版本，在变更前完成取证，最后用同口径的两次测量做对照。

## 参考文档

- NVIDIA CUDA 兼容性文档与 CUDA 安装指南：驱动支持上限与已安装工具链的区别。
- NVIDIA 驱动安装指南中关于安装方式、版本锁定与卸载的各节：驱动的多种版本表示，以及变更对整机作业的影响范围。
- NVIDIA 驱动的持久化文档：两组错误计数各自的生命周期与清零时机。
- NVIDIA GPUDirect RDMA 文档：显存直连所需的模块前置条件，以及模拟设备不具备该能力这一条。
- NCCL 用户指南的环境变量一页与排障章节：通信库版本串的构成、路径判断与性能对照的口径。
- `nvidia-smi(1)`、`dmesg(1)` 与 `journalctl(1)` 手册页：字段口径、环形缓冲的滚动行为与按启动编号查询日志的条件。
