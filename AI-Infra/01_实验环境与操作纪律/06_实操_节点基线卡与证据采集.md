# 节点基线卡与证据采集

这台机器正常的时候是多少，只有在它还正常的时候才会被记下来。等出了问题再去取一份「当前值」，得到的永远是异常值本身，没有任何对照对象；而事后补记的另一条路也走不通，因为时间、负载与当时的四项版本都已经变了。因此基线卡不是一份事后整理的表格，它是节点进入可用状态之前必须交出的产物之一：**在已知正常的状态下，按固定的字段与固定的命令取一次，连同取值时刻一起留档。**

## 一张基线卡由哪些字段构成

基线卡的字段分三组：一组描述环境、一组描述版本、一组描述测量。三组缺一组，这张卡就只能用于本机自查，不能用于跨机对照。

| 组 | 字段 | 取值方式 | 归档要求 |
| --- | --- | --- | --- |
| 环境 | 机型、GPU 型号与显卡固件版本 | 显卡查询工具的名称与固件版本字段 | 逐卡记录，多卡机型不合并成一行 |
| 环境 | 发行版与内核版本 | 系统发行版文件与内核版本命令 | 与网卡驱动来源一起记，用于判断模块构建方式 |
| 环境 | 网卡型号与固件版本 | 网卡驱动信息查询与固件管理工具的查询输出 | 逐口记录，注明端口与所在网络设备 |
| 环境 | 拓扑与亲和关系 | 显卡拓扑矩阵与 NUMA 信息 | 记录本次测量实际使用的卡与网卡的亲和关系，而不是整机全表 |
| 版本 | 驱动、CUDA、通信库、RDMA 栈四项 | 四项各自的取值入口 | 四项成组、各写来源、共用一个采集时刻 |
| 版本 | 模块构建方式与来源 | 模块文件路径与模块构建系统的状态输出 | 记到「这一台机器属于哪一种构建方式」，用于预判内核升级的影响 |
| 测量 | 命令与参数 | 本次测量实际执行的命令行 | 原样抄录，包括进程数、尺寸、次数等参数 |
| 测量 | 结果与单位 | 测量工具的输出值 | 数值必须带单位与口径名称，禁止只写一个数 |
| 测量 | 采集时间与采集人 | 记录时刻与执行者 | 时间精确到分钟，与四项版本共享同一个时间戳 |

一份基线卡的四项构成是：环境、命令与参数、结果、采集时间。四者共同定义一个可比较的参照；少任何一项，这份记录就只能算一次孤立的测量。这条要求不因记录载体是表格、笔记还是工单系统而改变。

## 取证材料各自的落点

基线卡回答「正常时是多少」，取证材料回答「出事时现场是什么」。两类材料的采集命令不同，落点也不同，混在一起采集会导致顺序错误。

| 材料 | 取值入口 | 落在哪里 | 采集时机 | 只读还是破坏性 |
| --- | --- | --- | --- | --- |
| 整机取证快照 | 驱动自带的取证脚本 | 一个压缩包，含驱动、模块、设备节点、内核日志与拓扑 | 变更或处置之前 | 采集过程会打开设备 |
| 内核日志中的驱动记录 | 内核日志查询工具 | 内核日志的驱动相关行 | 变更或处置之前 | 只读 |
| 计数器快照 | 端口计数器目录与网卡查询工具 | 计数文件的两次读数 | 变更之前取两次 | 只读 |
| 设备节点与权限清单 | 设备目录列表 | 字符设备节点的属主与权限位 | 变更之前 | 只读 |
| 正在运行的作业清单 | 调度器查询与进程表 | 作业标识、占用设备、运行时长 | 隔离之前 | 只读 |
| 通信库运行日志 | 集合通信库的日志输出 | 初始化段的路径与版本信息 | 作业运行期间 | 只读 |

## 采集顺序

采集顺序的原则只有一条：**先做只读的，后做会改变状态的。** 把材料按时间摆开，顺序就是一份清单。

| 时刻 | 采集什么 | 为什么排在这个位置 |
| --- | --- | --- |
| 第一步 | 设备节点与权限清单、正在运行的作业清单 | 这两项一旦隔离或变更就消失，且完全只读 |
| 第二步 | 会随生命周期清零的那一组错误计数 | 取证脚本本身会打开设备，可能触发初始化并清零这一组 |
| 第三步 | 计数器首次快照、内核日志中的驱动记录 | 都是只读，且要在变更前取得第一次读数 |
| 第四步 | 整机取证快照 | 采集范围最大、耗时最长，放在只读项全部取完之后 |
| 第五步（变更后） | 计数器第二次快照、复测结果、同一组四项版本 | 此时的对象已经是「变更后」，与前面各步不混放 |

## 采样纪律

采样纪律决定两次记录能不能相减。以下六条是固定动作：

- **累计量取差分**：端口计数器与错误计数是累计量，单次绝对值没有意义，判据是两次读数之差在运行期间的增长。
- **瞬时量单独记**：带宽、利用率、队列水位是瞬时量，只能与同一时刻的负载条件一起记录，不能与累计量放进同一个算式。
- **两次读数之间要有稳定的工况**：一次故障前后取的两次读数，如果中间负载变化很大，差值就不能直接归因。
- **上下限与实际生效值分列**：能力上限与实际生效值是两列，记录时不允许合并。
- **「无变化」也要写下来**：累计量完全不动与平稳增长是两种不同结论，前者可能是路径没有被使用，因此不能留空。
- **原始输出不入库**：临时脚本、原始输出与草稿报告不进入正式记录，正式记录只保留字段化后的取值与可复现的取值入口。

```bash
# 验证：基线卡里最容易被漏掉的是「哪些卡、哪些口、在什么亲和关系下测的」（只读）
nvidia-smi --query-gpu=index,name,vbios_version --format=csv; numactl --hardware
```

上面这条命令只用于固定记录中的逐卡与亲和字段；输出字段名与取值随机型、版本四元组变化，这里不给出示例取值，任何对照使用的数值仅示意、不代表你的环境。

## 故障现场定位表

下表只在已经完成环境档位判定之后使用。表里的每一行对应主链六段中的一段，用法是先按现象定段，再到该行指定的字段上核对；两列都符合判据而现象仍在时，说明要查的对象已经不在主机侧这一列。同一现象在表里可能对应多行，因此进入这张表之后把现象对应的每一行都读一遍，通常只有一到两行的字段不符合判据，那一到两行就是当前该处理的对象。

| 现象 | 属于哪一段 | 先读哪两个字段 | 不符合时转向哪一步 |
| --- | --- | --- | --- |
| 结论要跨机或跨硬件才成立 | 段 1 判定环境档位 | 设备来源（真实硬件还是软件模拟）；机器档位（单机、双机还是多机） | 设备来源与档位有一项不足时，先在正确档位上重做一次，不要解释这次读数 |
| 变更后行为变化，说不清改了哪一项 | 段 2 记录现状 | 变更前与变更后两份版本四元组；每一项是否带取值来源与统一时刻 | 记录不成组时只能补记当前值，并注明变更前的记录缺失，不能用推测补回 |
| 升级后命令与库报出的版本对不上 | 段 2 记录现状 | 已加载内核模块的版本；用户态工具与库所见的驱动版本 | 两者不一致时，先判断是「升级后未重启」还是「模块未为新内核重编」 |
| 复盘的某份材料已经找不到 | 段 3 抓取现场 | 内核日志本次启动与上一次启动的差异；取证快照的落盘时间 | 材料落在重启、卸载或作业退出之后时，这一次已经无法补，只能按现有材料限定结论范围 |
| 变更打断了正在运行的作业 | 段 4 隔离节点 | 设备上的进程占用；调度器侧是否仍有该节点的分配 | 仍有作业占用设备时，先等它退出或迁移，再继续变更 |
| 变更失败，退不回去 | 段 5 执行变更 | 变更前的版本与包清单；事先写下的回滚动作 | 回滚路径未确认时立即停手，先补齐变更前状态；固件类要先确认可降级性 |
| 变更后数字与基线对不上 | 段 6 复测并归档 | 两次测量的命令与参数；两次测量的版本四元组与亲和关系 | 口径不一致时按基线口径重跑，不要用不同口径的两个数字相减 |
| 同一现象在一个节点池里只有一台机器出现 | 段 2 记录现状 | 这台机器与池内基线的版本四元组差异；机型与显卡固件版本差异 | 差异定位到具体一项后，再决定是拉回池内基线还是把池的基线整体上移，不要就地逐项修补 |

这张表在主机侧能收敛到的范围是「现象能否定位到六段中的某一段、该段的字段是否符合判据」。交换机侧的取值、其它节点的配置状态以及集群级的排期决策不在主机侧可自证的范围里，定位到这一段之后应由对应的责任方接续。

## 常见故障与排查方向

下面四个场景把故障现场定位表给出的第一份读数继续走完：每个场景先写现场，再写先读什么，然后写读到什么就转往哪一步，最后写一份合格的回答应当包含什么。场景一走在定位表之前——它是环境档位判定这个入口本身的走查；其余三个场景设定在单机档位，结论只覆盖主机侧的纪律与流程。场景里的机器规格、时间线与数值都是具象设定，用来练判断，不代表你的环境。

### 场景一：引用一份测量记录之前，先判定它能支撑到哪一档

**现场**：复盘会上，有人拿出一份上个季度在测试环境跑出的带宽记录，想用它证明「现在生产环境的数字偏低」。记录里有命令、参数与结果，没有写设备来源与机器档位。

**先看什么**：一份记录能不能支撑某个结论，取决于它产生于哪一档环境。先补读两个字段：设备来源是真实硬件还是软件模拟，机器档位是单机、双机还是多机。读不到时，这份记录不具备被引用的资格。

```bash
# 以下两条在产生记录的那台机器上执行（只读）
ibv_devices                                                # 验证：这台机器的 RDMA 设备清单（软件模拟设备会以其类型名出现）
nvidia-smi --query-gpu=index,name --format=csv             # 验证：GPU 型号，与记录里的环境字段对照
```

**读到什么就转往哪一步**：

- 若设备来源是软件模拟，则这份记录只能证明流程跑通过：模拟设备的性能由处理器与普通以太网路径决定，与真实硬件的卸载路径无关，它的数字不得进入任何性能结论或性能基线。
- 若记录缺设备来源与档位字段，则退回补记；补不回来的，标注「环境未确认」，只能当轶事材料，不进任何对照序列。
- 若档位是单机，则它能支撑驱动、拓扑与单机集合通信的结论，不能支撑无损行为与跨机结论：要下跨机结论，在双机档上重做一次，不要解释这次读数。
- 若档位是双机、而要下的结论关于多机 fabric，同样降一档使用：轨道、子网管理器与多机互联形态超出它的覆盖范围。
- 若环境字段齐备、档位也覆盖结论对象，则进入下一道核对：基线卡四要素——环境、命令与参数、结果、采集时间——逐项对照，任何一项不齐都不能相减。

**一份合格的回答**应当说清：结论是这份记录能支撑到哪一档、不能支撑什么；依据是设备来源与机器档位两个字段，以及四要素的齐备程度；边界是低档环境的读数不得用来支撑高档环境的结论，补不回来的字段不能用推测回填；动作是把记录按档位归档、退回补记，还是在正确档位上重测。

### 场景二：凌晨故障，早上复盘时材料已经消耗

**现场**：一台训练节点凌晨 3 点作业崩溃，值班为尽快恢复，重启了机器并重新拉起作业。早上复盘会的问题是「它为什么崩的」。机器已重启过一次，作业已换了一批进程。

**先看什么**：先确认各类现场还在不在，再决定结论能下到什么范围。重启、模块卸载与作业退出各自清掉一类现场：未持久化的内核日志、模块与设备的运行时状态、进程级现场。

```bash
journalctl --list-boots                 # 验证：还能回溯几次启动（只有一条 = 上一轮的现场已丢）
journalctl -b -1 -k -p warning          # 验证：上一次启动的内核警告与错误（上一条有多行时才有意义）
nvidia-smi -q | grep -E -A3 'ECC'       # 验证：两组错误计数的当前值（随生命周期清零的那组在重启后读不出昨晚的趋势）
```

**读到什么就转往哪一步**：

- 若启动记录只有一条，则上一轮的内存日志已随重启消失，这一类现场无法再补：复盘结论里凡是依赖内核日志的部分都只能写「未确认」；把日志持久化列为整改项，并注意从现在起每一次重启都在继续消耗现场。
- 若启动记录有多行，则上一次启动的内核日志可读：按时间过滤取出崩溃前后的驱动相关记录，把结论范围限定到这些记录支持的部分。
- 若那组会随生命周期清零的错误计数已归零，则它的趋势不可用：改读长期累计的那一组；两组都没有异常时，硬件这一条只能写「未见证据」，不能写「硬件正常」。
- 若有人在处置之前按取证顺序落盘过材料，则以那份材料为准复盘并归档；若没有，把「取证排在处置之前」写进整改项——下一次的顺序决定下一次的结论质量。

**一份合格的回答**应当说清：结论是哪些能下、哪些只能写「未确认」；依据是各类材料的存活状态——启动记录条数、可读的日志范围、两组计数各自的可用性；边界是重启、模块卸载与作业退出之后，对应类别的现场无法再补，不能用现在的正常读数反推故障时刻；动作是按现有材料限定结论范围并列出整改项，还是进入材料支持的分析。

### 场景三：变更窗口前的隔离验收

**现场**：一台训练节点排在今晚的窗口做驱动升级，值班主任要求下午给出「这台机器现在能不能动手」的结论。调度侧已经把节点标记为不可调度。

**先看什么**：隔离完成的判据有三条，要逐条核对而不是只看调度器：不再产生新的分配、已有作业确已退出或已在其它节点上继续运行、设备上不再有残留的进程占用。三条里最后一条最容易漏。

```bash
# 调度器侧先确认节点无新分配（按本集群的调度器查询入口，只读）
nvidia-smi --query-compute-apps=pid,process_name,used_memory --format=csv   # 验证：设备上的计算进程占用
fuser -v /dev/nvidia* 2>/dev/null       # 验证：打开设备节点的全部进程清单
```

**读到什么就转往哪一步**：

- 若调度器侧已无新分配、而设备上仍有进程占用，则隔离未完成：一条正在运行的作业不会因为节点被标记而自动退出，它会在设备被摘走时异常结束；先分清占用者是谁，等它退出或迁移，再继续变更。
- 若占用来自残留的监控或管理进程，则确认它不持有计算上下文之后再按流程处理；不要为了让清单变空去结束不认识的进程。
- 若三条判据都满足，则给出「可动手」的结论，并同时交出变更前的取证与记录：设备节点与权限清单、正在运行的作业清单、版本四元组、会随生命周期清零的那组计数——这些在变更之后都取不到。
- 若窗口临近而占用未清，则结论只能是「不满足动手条件」：改期，或在流程内迁移作业，不要在占用存在时开始变更。

**一份合格的回答**应当说清：结论是三条判据各自的核对结果；依据是调度器状态、设备占用清单与进程归属；边界是隔离的判据落在设备上而不落在调度器上，「无新分配」不构成隔离完成；动作是放行变更并附上变更前取证清单，还是暂缓并写明阻塞项。

### 场景四：变更后复测，数字与基线对不上

**现场**：一次驱动升级完成后按流程复测，同一用例的带宽比基线低了 8%。变更方认为「升级导致性能回归」，业务方认为「测试没跑对」。基线卡与本次复测的命令行都在手边。

**先看什么**：复测不是「再跑一次」，是同口径的两次测量之差。先把两份记录的四要素逐项摆开：环境、命令与参数、结果、采集时间。

```bash
# 先逐项对照两份命令行：进程数、消息尺寸、迭代次数、缓冲类型（以基线卡原样抄录的为准）
nvidia-smi topo -m                      # 验证：本次测量实际使用的卡与网卡的亲和关系，与基线卡记录的那次对照
```

**读到什么就转往哪一步**：

- 若两次的命令与参数有任何一项不同（进程数、尺寸、次数、缓冲类型），则差异来自口径：按基线口径原样重跑，不要拿不同口径的两个数字相减。
- 若命令一致而亲和关系不同（这次换了卡或网卡的组合），则仍属口径问题：拓扑不同的两次测量不可比，回到基线使用的那组设备复跑。
- 若口径全部对齐，则差异成立：按变更内容定位——这次变更动了四元组里的哪几项，就从哪几项查起，查的过程中全程使用同一口径。
- 若基线卡本身缺要素（没有命令、没有亲和关系或没有采集时刻），则它不构成对照对象：这次复测降格为新的基线起点，按四要素补齐记录；本次「回归」只能记为「未确认」，既不成立也不被否证。

**一份合格的回答**应当说清：结论是口径差异还是真实回归；依据是两份记录四要素的逐项对照；边界是不同口径的数字不能相减，基线缺要素时结论只能是「未确认」；动作是按基线口径重跑、按变更项定位，还是把本次降格为新基线起点并补齐记录。

**第一反应不要做什么**：不要在机器已经被改动之后才去补一份基线；不要把一次测量当成基线而省略采集时刻与环境；不要把上下限当成实际生效值记进去；不要只保留测量结果而丢掉命令与参数；不要用不同工况下的两次累计读数直接相减。正确的顺序是先按固定字段在正常状态下取一次，再把命令与参数、结果与时刻一并留档，最后才允许这台机器进入被引用的状态。
