# AI 基础设施学习大纲（GPU / RDMA，生产级）

> **定位**：面向「GPU 集群 / AI 训练平台运维」的学习路径，覆盖**主机与网络数据面**——也就是 Kubernetes 大纲不负责的那一层。
> **前置基础**：Linux 系统管理（内核模块、PCIe/NUMA、网络排障）、TCP/IP、跑过 CUDA 程序。
> **配套笔记**：控制面与编排层见 [[Kubernetes/00_简介|Kubernetes 大纲]]（尤其 [[08_GPU_AI场景]]）；通用主机能力见 [[Linux/00_简介|Linux 大纲]]。
>
> 原则：每个模块都按 **概念 → 生产实践 → 要点自测** 三层推进，并且**每条结论都要能落到一条命令或一个指标上**。这一层的内容最怕「听说过」——面试官追问两句就会露底。

---

## 学习路径总览（Roadmap）

| 阶段 | 主题 | 建议周期 | 产出目标 |
| --- | --- | --- | --- |
| 1 | 驱动与内核模块 | 3~5 天 | 讲清驱动 ↔ CUDA ↔ NCCL ↔ OFED 的兼容关系，能安全升级与回滚 |
| 2 | GPU 拓扑与 PCIe / NUMA | 3~5 天 | 读得懂 `nvidia-smi topo -m`，能判断「卡放错了」 |
| 3 | RDMA 与 RoCE 无损网络 ★ | 1~2 周 | 能查能讲 RoCEv2 与 PFC/ECN，说清丢包为什么对 RDMA 致命 |
| 4 | perftest 与性能基线 | 3~5 天 | 建立带宽/延迟基线，能区分「变慢了」和「一直就慢」 |
| 5 | 容器内 GPU 与 RDMA | 1 周 | 把设备与数据面正确带进容器，容器内跑通 nccl-tests |
| 6 | NCCL 排障 ★ | 1 周 | 判断走的是 RDMA 还是 socket，定位卡住与静默降速 |
| 7 | XID 与硬件故障处理 | 1 周 | 读懂 XID、处理掉卡，判断「换卡」还是「重启」 |
| 8 | 复习与自测 | 持续 | 场景题能脱稿讲 3~5 分钟 |

> 标 ★ 的 **阶段 3（RoCE 无损网络）** 与 **阶段 6（NCCL 排障）** 是这块内容里区分度最高的两块：驱动安装人人会写，能把「训练变慢」定位到某一跳的 PFC 计数或某个 GID 索引的人不多。优先打透。

## 前置：硬件与环境基线（不单独成篇，但必须先解决）

### 环境三档，按能练什么选

| 环境 | 能练什么 | 说明 |
| --- | --- | --- |
| 单机 | 驱动与内核模块、拓扑、MIG、DCGM、容器内 GPU | 一条命令就能开始，覆盖面最窄 |
| 双机（直连或经交换机） | RoCEv2、perftest、双机 nccl-tests、链路故障 | **最小可验证环境**，没有双机就讲不清 RDMA |
| 多机 / 集群 | 拓扑感知调度、队列与配额、故障注入 | 通常只在手上有集群时做，属加分项 |

> [!tip] 手上没有高速网卡怎么办
> `rdma_rxe`（soft-RoCE）能在普通网卡上把 RDMA 内核栈、设备节点、`perftest`、`rdma` 工具链跑通，用来熟悉命令与验证链路。但它**性能不代表真实硬件，也不支持 GPUDirect RDMA**——讲性能结论时不能拿它当证据。

### 版本基线（每次动手前先记录）

| 项 | 查看方式 |
| --- | --- |
| 发行版与内核 | `cat /etc/os-release`、`uname -r` |
| NVIDIA 驱动 | `nvidia-smi`、`cat /proc/driver/nvidia/version` |
| CUDA Toolkit | `nvcc --version` |
| NCCL | `python -c "import torch; print(torch.cuda.nccl.version())"` 或 `nccl-tests` 编译时的版本 |
| RDMA 栈 | `ofed_info -s`（MLNX_OFED）或 `rdma link`、`ibv_devinfo` |
| 网卡固件 | `mlxfwmanager --query`、`ethtool -i` |
| GPU 型号与 VBIOS | `nvidia-smi -q`、`nvidia-smi --query-gpu=name,vbios_version --format=csv` |

> [!important] 讲兼容性时只说一个版本号是没有意义的
> 驱动、CUDA、NCCL、OFED 是**四元组**，升任意一个都可能让原有组合破功。面试里能主动说出「这四个版本要一起记录」，比背某个具体版本号有用得多。

### 操作纪律

- 固件升级、驱动降级、`nvidia-smi --gpu-reset`、MIG 重切分只在实验机做；生产上先隔离节点再动手
- 动驱动或固件之前：记录版本 + 抓一份 `nvidia-bug-report.sh`；改完立即复测基线（perftest + nccl-tests）
- 训练作业的 NCCL 日志要留存——它是事后判断「当时走没走 RDMA」的唯一证据
- GPU 节点尽量单独成池（taint/toleration），不要让普通业务和训练任务混跑（编排层见 [[08_GPU_AI场景]]）

## 阶段 1：驱动与内核模块

> **对应笔记**：[[01_驱动与内核模块]]

### 1.1 驱动与内核模块

- [ ] 三种安装路径的取舍：发行版仓库包、NVIDIA 官方仓库（`cuda-drivers`）、`.run` 安装包——以及为什么生产上基本不用 `.run`
- [ ] DKMS 与预编译模块的区别，**内核升级后 DKMS 重编译失败会导致 `nvidia-smi` 直接失联**
- [ ] 关键内核模块：`nvidia`、`nvidia_uvm`（`/dev/nvidia-uvm`，CUDA 依赖）、`nvidia_modeset`、**`nvidia_peermem`**（GPUDirect RDMA 用，取代旧的 `nv_peer_mem`）
- [ ] 设备节点：`/dev/nvidia0..N`、`/dev/nvidiactl`、`/dev/nvidia-uvm`，以及容器里为什么必须把它们一起带进去
- [ ] 与内核/发行版相关的坑：Secure Boot 下的模块签名（MOK 注册）、`nouveau` 黑名单、`nvidia-persistenced` 与 persistence mode
- [ ] 容器工具链：NVIDIA Container Toolkit（`nvidia-ctk`）、`nvidia-container-runtime`、`NVIDIA_VISIBLE_DEVICES` / `NVIDIA_DRIVER_CAPABILITIES`
- [ ] 版本兼容：驱动 ↔ CUDA Toolkit ↔ NCCL ↔ OFED 的关系，以及 CUDA forward compatibility 的能力边界
- [ ] 卸载与回滚：`nvidia-uninstall` / 包管理降级、驱动与内核不匹配时的恢复顺序
- [ ] 取证：`nvidia-bug-report.sh`、`dmesg` 里的 `NVRM` 日志

**生产实践**

- 驱动版本由**节点池**统一，不要逐台漂移；升级走「先在实验机验证 → 灰度一个节点池 → 全量」
- 内核升级与驱动升级要一起规划：内核动了，DKMS 模块要跟着重编，这一步失败就是整机 GPU 不可用
- 容器工具链版本要与驱动能力匹配，别用 `--gpus all` 一条命令掩盖能力集（`compute`/`utility`/`ipc`）的缺失
- 驱动是**内核态代码**：不要在生产上直接验证新版本，崩溃的是整台机器，不只是某个进程

**要点自测**

- `/dev/nvidia-uvm` 没挂进容器，会看到什么现象？
- `nvidia_peermem` 是干什么的？没加载时 GPUDirect RDMA 会退化成什么路径？
- 内核升级后 `nvidia-smi` 报错，你怎么排查和恢复？
- 为什么讲兼容性要同时说驱动、CUDA、NCCL、OFED 四个版本？

## 阶段 2：GPU 拓扑与 PCIe / NUMA

> **对应笔记**：[[02_GPU拓扑与PCIe_NUMA]]

- [ ] `nvidia-smi topo -m` 的读法：`NV#`（NVLink）、`PIX`（同一 PCIe 交换机）、`PXB`（多次交换）、`PHB`（同一 Host Bridge）、`SYS`（跨 NUMA/socket）
- [ ] P2P 能力与 GPU 间通信：`nvidia-smi topo -m` 与 P2P 开关（`NCCL_P2P_DISABLE` 做对照实验）
- [ ] 链路速率与宽度：`lspci -vv` 的 `LnkCap`/`LnkSta`，**GPU 掉到 x8 或降代（Gen4→Gen3）是真实生产故障**，会静默降速
- [ ] NUMA 视图：`numactl --hardware`、`lscpu`、`/sys/bus/pci/devices/<BDF>/numa_node`，以及 GPU / 网卡 / NVMe 各自挂在哪号 NUMA
- [ ] 绑核与绑内存：`numactl --cpunodebind --membind`，让训练进程、GPU、网卡落在同一 NUMA 域
- [ ] BIOS 侧前提：Above 4G Decoding、Resizable BAR / Large BAR、IOMMU 与 ACS（影响 P2P 能否直通）
- [ ] 节点内互联：NVLink / NVSwitch 的层级差异，以及 8 卡机型的常见拓扑形态
- [ ] 与调度层的衔接：Topology Manager / CPU Manager 如何把 CPU、GPU、网卡对齐（见 [[08_GPU_AI场景]]）

**生产实践**

- **拓扑放错不报错，只会变慢**：把一个 8 卡训练任务分散到跨 NUMA 的位置，现象是「能跑通但慢一半」
- 交付新机型时先出一份拓扑基线：`nvidia-smi topo -m` + `lspci -tv` + NUMA 分布，写进交付文档
- GPU 与高速网卡必须在同一 NUMA 域，这是 GPUDirect RDMA 发挥收益的前提
- 监控里保留「跨 NUMA 训练任务占比」这类指标，否则拓扑错位永远是隐性问题

**要点自测**

- `nvidia-smi topo -m` 输出里 `NV4`、`PIX`、`SYS` 分别意味着什么？
- 怎么判断一张卡有没有「降速」？看哪个文件的哪个字段？
- 为什么 GPU 与网卡的 NUMA 亲和会影响训练吞吐？影响的是带宽还是延迟？
- 拓扑错位的典型现象是什么？为什么监控上很难发现？

## 阶段 3：RDMA 与 RoCE 无损网络 ★（核心区）

> **对应笔记**：[[03_RDMA与RoCE无损网络]]

### 3.1 设备与协议栈

- [ ] 设备工具链：`rdma link show`、`ibv_devinfo`、`ibstat`、`ibdev2netdev`、`/sys/class/infiniband/`
- [ ] RDMA 关键词的语义：QP、CQ、Memory Region、`memlock`（`ulimit -l`）——知道它们解释了「为什么 RDMA 延迟低」就够了
- [ ] InfiniBand 与 RoCE 的区别：IB 是原生网络，**RoCEv2 是把 IB 传输层封装进 UDP/IP**（可路由）
- [ ] GID 索引：`show_gids`、`cma_roce_mode`，以及 `-x <gid_index>` 为什么是 RoCE 排障里最容易出错的一个参数
- [ ] 内核侧模块：`mlx5_core`、`ib_core`、`rdma_cm`、`rdma_ucm`、`nvidia_peermem` 各自的作用

### 3.2 无损网络：PFC / ECN / DCQCN

- [ ] **PFC（优先级流控）**：按优先级逐跳反压，是 RoCE 不丢包的基础；代价是可能引发 PFC 风暴甚至死锁
- [ ] **ECN + DCQCN**：端到端拥塞控制，与 PFC 配合避免「靠反压硬扛」
- [ ] 映射关系：DSCP/PCP 优先级标记 → 交换机队列 → PFC 使能队列，主机侧与交换机侧必须对齐
- [ ] 主机侧配置工具：`mlnx_qos`、`cma_roce_tos`、`cma_roce_mode`、MTU 设置（`ip link` / `show_gids` 确认实际生效值）
- [ ] 丢包观测：`ethtool -S` 的 `rx_pause`/`tx_pause`、`rdma statistic`、以及 `symbol_error`、`link_downed`、`port_rcv_errors`、`local_ack_timeout_err` 等 IB 计数器
- [ ] 驱动与固件：MLNX_OFED 与 in-box 驱动的取舍、`mlxfwmanager`/`mstflint` 查固件、固件与驱动的匹配关系
- [ ] 硬件侧：DAC / AOC / 光模块的适用距离，链路质量与误码
- [ ] 主机调优：IRQ 亲和、软中断分布、多队列与环形缓冲、`tuned` profile（通用部分见 [[05_网络协议栈与排障]]）

**生产实践**

- **PFC 与 ECN 要主机与交换机两侧同时配**：只配一边往往表现为「平时正常、一上压力就抖动」，比彻底不通更难查
- 把 PFC pause 计数、IB 错误计数器纳入监控：它们涨得慢，但涨起来就是训练掉点数的前兆
- GID 索引、MTU、优先级映射这三项纳入节点交付标准；换机型或换固件后必须重新验证
- 网卡固件升级按节点批次做，先隔离节点再升级，升完跑一遍 perftest 基线
- 与网络团队划清责任边界：主机侧到网卡计数器是可查证的，交换机侧配置要找对方对账

**要点自测**

- RoCEv2 和 IB 的本质区别是什么？为什么 RoCE 必须做到无损？
- 为什么「能 ping 通、能用 Service 访问」完全不能证明 RDMA 可用？
- 时延抖动、重传、PFC pause 计数增长，三者之间的因果关系是什么？
- `-x <gid_index>` 选错会出现什么现象？
- PFC 风暴是怎么形成的？为什么它比丢包更危险？

## 阶段 4：perftest 与性能基线

> **对应笔记**：[[04_perftest与性能基线]]

- [ ] perftest 基本用法：`ib_write_bw`、`ib_read_bw`、`ib_write_lat`、`ib_send_bw`，以及 `-d`（设备）、`-i`（端口）、`-x`（GID 索引）、`-s`（消息大小）、`-q`（队列深度）、`-a`（扫全部消息大小）
- [ ] 结果怎么读：小消息看**延迟**，大消息看**带宽**，把实测值与线速（100/200/400 Gb/s）对比而不是与「感觉」对比
- [ ] 变量控制：单向/双向、单流/多流、多 QP、CPU 绑核，以及为什么不同参数下结论会不一样
- [ ] nccl-tests：`all_reduce_perf`、`all_gather_perf`、`reduce_scatter_perf`；**`algbw` 与 `busbw` 的区别**及各自适用场合
- [ ] GPUDirect RDMA 验证：`nvidia_peermem` 已加载、GPU 与网卡同 NUMA、带宽相比非 GDR 路径是否真的更高
- [ ] 基线管理：把「版本四元组 + 拓扑 + 参数 + 结果」一起记录，形成可对比的正常值
- [ ] 常见伪结论：用 soft-RoCE 的成绩代表硬件性能、混用不同消息大小、忽略 NUMA 错位

**生产实践**

- 每个节点池上线时跑一次基线并归档；之后判断「训练变慢」才有参照物
- 变更（固件、驱动、交换机策略、内核参数）后复测基线，这是唯一可靠的回归验证手段
- 交付验收用**数字**说话：带宽达到线速的多少、延迟多少微秒，而不是「跑通了」
- 把基线结果、`nvidia-smi topo -m` 输出和 nccl-tests 命令写进交付文档，故障时可直接复用

**要点自测**

- 怎么判断一条 RDMA 链路是「正常」的？看哪些数字？
- `algbw` 和 `busbw` 有什么区别？汇报给业务方该用哪个？
- 怎么证明 GPUDirect RDMA 真的生效了（而不只是「配了」）？
- 双机 nccl-tests 跑出来明显低于单机，你会按什么顺序定位？

## 阶段 5：容器内 GPU 与 RDMA

> **对应笔记**：[[05_容器内GPU与RDMA]]

- [ ] 容器内 GPU：NVIDIA Container Toolkit 的注入机制，`--gpus` / `NVIDIA_VISIBLE_DEVICES` 的实际效果，以及能力集（`compute`/`utility`/`ipc`）缺失时的报错
- [ ] 容器内 RDMA 需要三样东西：设备节点（`/dev/infiniband/*`）、权限（`capabilities`、`memlock` 不限）、以及正确的 GID/设备索引
- [ ] `IPC_LOCK` / `ulimit -l unlimited` 的必要性（RDMA 要锁内存），以及 `IPC_LOCK` 给多带来的安全代价
- [ ] 共享内存：`--shm-size` 或 `ipc: host`——**NCCL 走 SHM 时共享内存不够会直接失败**
- [ ] 附加网卡：Multus + SR-IOV CNI + RDMA CNI 的分工，以及「默认网卡管控制面、附加网卡管数据面」的两套数据面（编排细节见 [[08_GPU_AI场景]]）
- [ ] SR-IOV VF 直通：VF 的 netdev 与 RDMA 设备如何一起进入容器的网络命名空间，以及 `rdma` cgroup 的资源限制
- [ ] 容器内验证清单：`nvidia-smi`、`ibv_devinfo`、`ib_write_bw`、`nccl-tests` 四件套
- [ ] 常见坑：宿主机装了工具但容器镜像里没有、GID 索引在容器内外不一致、`mlx5` 设备名在容器内变化

**生产实践**

- 容器内 GPU/RDMA 的验证要固化成一个「验收镜像」+ 一份检查清单，而不是每次手工试
- 训练镜像固定 CUDA / NCCL / OFED 版本，并在 CI 里跑一次单机 nccl-tests 冒烟
- 数据面不受 Service 管辖：安全组、NetworkPolicy 只覆盖默认网络，高速网络的隔离要单独设计
- 权限给到够用为止：`IPC_LOCK` 与设备节点按需挂载，不要让训练容器顶到特权模式

**要点自测**

- 容器里 `nvidia-smi` 正常但 CUDA 程序报错，可能缺了什么？
- 一个 Pod 里怎么同时拥有「默认网卡」和「RDMA 网卡」？两套数据面各自负责什么？
- 为什么 RDMA 程序需要 `memlock` 无限？不放开会怎么报错？
- NCCL 在容器里起不来，你会先查哪几项？

## 阶段 6：NCCL 排障 ★（核心区）

> **对应笔记**：[[06_NCCL排障]]

- [ ] NCCL 在做什么：拓扑探测（NVLink/NVSwitch/PCIe/IB/RoCE）→ 选择算法（Ring/Tree）与协议（Simple/LL/LL128）
- [ ] `NCCL_DEBUG=INFO` 的读法：拓扑探测段、通道建立段、以及 **`NET/IB` 与 `NET/Socket` 的关键差异**
- [ ] 关键环境变量：`NCCL_SOCKET_IFNAME`（避免走管理网）、`NCCL_IB_HCA`、`NCCL_IB_GID_INDEX`、`NCCL_IB_TIMEOUT`、`NCCL_TOPO_DUMP_FILE`
- [ ] 对照实验变量：`NCCL_IB_DISABLE=1`、`NCCL_P2P_DISABLE=1`、`NCCL_SHM_DISABLE=1`——用来快速判定问题出在哪条路径上
- [ ] 两类故障的区分：**卡住不动**（多为 bootstrap/网络不通/MTU/GID）与**静默降速**（走了 socket、拓扑错位、PFC 丢包）
- [ ] hang 时的取证：各 rank 的 NCCL 日志对齐、进程栈（`py-spy`/`gdb`）、`ibv_devinfo` 与 IB 计数器快照
- [ ] 多机场景：rank 与节点/网卡的映射关系、机架与拓扑对集合通信效率的影响
- [ ] 与 K8s 的衔接：JobSet / PyTorchJob 下多 Pod 的日志收集与失败重试语义（见 [[08_GPU_AI场景]]）

**生产实践**

- 训练作业默认带 `NCCL_DEBUG=WARN`；排障时临时提到 `INFO`，但**必须同时打开日志落盘**，否则现场一过就没证据
- 把「是否走 RDMA」做成上线前的必查项：只跑得通不算验收
- 训练变慢先分三类：卡在通信、通信正常但慢、通信快但算得慢——分类错了，后面所有命令都白敲
- 多机任务超时/掉卡时，先看是哪几个 rank 掉队，再对号入座查对应节点，不要全量重启

**要点自测**

- 怎么从 NCCL 日志判断走的是 RDMA 还是 socket？
- 训练在第一个 `AllReduce` 就卡住，你的排查顺序是什么？
- 训练能跑完但吞吐只有基线的一半，可能的原因有哪些？
- `NCCL_SOCKET_IFNAME` 设错会有什么后果？为什么它会引发「看起来很随机」的失败？
- 多机任务里只有一个 rank 报错，你会怎么定位到具体节点与网卡？

## 阶段 7：XID 与硬件故障处理

> **对应笔记**：[[07_XID与硬件故障处理]]

- [ ] XID 是什么：NVIDIA 驱动上报的错误码，**硬件/驱动故障的第一现场**；对照官方 XID 表逐码判读，不靠印象
- [ ] 常见码的取向（示例，务必对照官方表使用）：`13`/`31`（图形或计算引擎异常）、`43`（GPU 停止处理任务）、`48`（双比特 ECC）、`63`/`64`（ECC/行重映射相关）、`74`/`92`/`94`/`95`（NVLink 链路）、`79`（GPU 从总线上掉下来）、`119`/`120`（GSP/驱动相关）
- [ ] 掉卡（fallen off the bus）：`nvidia-smi` 失联、`lspci` 里看不到设备、`dmesg` 里的 PCIe AER 报错
- [ ] ECC 与行重映射：volatile / aggregate 计数、可纠正与不可纠正错误的处理差别
- [ ] 温度与功耗：thermal slowdown、功耗墙、风扇与机箱风道
- [ ] 健康检查：`nvidia-smi -q` 全量、`nvidia-smi dmon`、DCGM 诊断（`dcgmi diag`）与 DCGM 指标（见 [[08_GPU_AI场景]]）
- [ ] MIG 实操：`nvidia-smi mig` 的 GI/CI 概念、切分策略与回收，以及 MIG 下监控归因的变化
- [ ] 固件：GPU VBIOS 版本核对、`nvidia-smi --gpu-reset` 的能力与限制
- [ ] 处置流程：先取证（`dmesg` + `nvidia-bug-report.sh` + DCGM）→ 判定软件还是硬件 → 隔离节点 → 重启/换卡 → 复测基线

**生产实践**

- XID 与掉卡都要在监控里告警，并联动到节点隔离：**让调度器别再往这台机器上放任务**
- 「重启后恢复了」不等于修好了：记录 XID 码、复测基线，判定是偶发还是硬件劣化
- 换卡是有流程的：先确认业务侧能重调度，再动硬件；换完必须复跑 perftest 与 nccl-tests
- 把每次硬件故障的 XID 码、处置动作、复测结果记进台账，用来判断某批卡、某个机型的故障率

**要点自测**

- `nvidia-smi` 报错、`lspci` 也看不到卡，你会按什么顺序取证据？
- 可纠正 ECC 与不可纠正 ECC 的处理策略差别是什么？
- XID 79 出现后，这台机器还能继续跑训练吗？依据是什么？
- 怎么判断一次故障是「软件问题重启就好」还是「硬件劣化要换卡」？
- MIG 开启后，为什么按 Pod 归因 GPU 用量会变难？
