# GPU 的数据从哪里来：存储与 I/O

集合通信测试正常，作业仍然隔一会儿停一下。GPU 在等磁盘、CPU 解码，还是另一台机器先拿到下一批数据？本章从存储中的样本一直追到显存，再把保存与恢复状态产生的反向流量放回同一套资源预算。

本章的学习任务是：**画出普通数据加载与 GDS 的路径；把存储字节、样本和显存字节换成同一供给速率；解释并发、缓存、预取和锁页内存分别改变什么；根据访问模式辨认存储瓶颈；计算 Checkpoint 的容量、写入和恢复压力；用时间线区分数据等待、通信等待和计算阶段。**

## 前置与章节边界

读者已有 Linux 的文件、进程、页缓存、内存和网络基础，以及 Kubernetes 的容器和资源概念。[第 02 章](../02_GPU如何计算与显存/00_导读.md)提供显存与异步执行，[第 04 章](../04_单机多卡与GPU数据路径/00_导读.md)提供 PCIe/NUMA 与 H2D 路径，[第 05 章](../05_为什么一个作业需要多张GPU/00_导读.md)提供 Rank 与同步成员，[第 06 章](../06_从普通网络通信走向RDMA/00_导读.md)提供 RDMA 和显存注册。第 07—08 章的网络预算与集合通信用于解释另一类等待；本章会就近重述当前推导需要的含义。

本章完整建立数据供给、访问模式、Checkpoint、GDS 与瓶颈判断。文件系统仅讲客户端路径、元数据和数据布局；不展开服务器安装、RAID、完整存储运维或训练算法。第 10 章负责 GPU 进入容器，第 13 章负责 Pod 的高速网络；CSI、PV/PVC 的通用机制按已有 Kubernetes 基础处理，本章不把“卷已挂载”当作吞吐或 GDS 已获保证。第 17—19 章再负责监控系统、处置和变更流程。

## 贯穿模型与材料约定

新作业 `job-09` 使用 `io-a`、`io-b` 两个同构节点，每节点两张独占 NVIDIA GPU。`io-a` 的 r0、r1 分别使用本机 G0、G1，`io-b` 的 r2、r3 也分别使用本机 G0、G1；每 Rank 一个数据加载器。**本模型独立于前章，不继承设备编号或性能结果。**

| 给定条件 | 本章含义 |
| --- | --- |
| 每节点 32 个可用 CPU 核、256 GiB 主机内存 | Worker、运行库、主进程和 I/O 协助共享预算 |
| 每节点 `/scratch`：2 TiB 本地 NVMe | 可用数据空间；给定顺序读取有效上限 6 GiB/s，节点丢失时不保证数据保留 |
| `/datasets`：共享文件系统 | 本作业两节点读取时每节点上限 4 GiB/s，服务聚合读取上限 8 GiB/s；写入示例另给条件 |
| 每节点独立的存储 NIC 与集合通信 NIC | 基线不共享物理端口；仍可能共享 CPU、DRAM 和 PCIe 资源 |
| 一份压缩样本 256 KiB，CPU 解码后 1 MiB | 每 Rank 每步 64 个不同样本：读 16 MiB，H2D 64 MiB；无额外膨胀与丢弃 |
| GPU 工作段 80 ms/步 | 已有数据时，含 60 ms 计算与 20 ms 不重叠集合通信；四 Rank 同步推进 |
| 单 GPU H2D 有效速率 12.5 GiB/s | 64 MiB 耗时 5 ms；节点两路并发时仍各能达到该速率 |
| 每个解码 Worker 400 样本/s | 仅在后文给定独立 CPU 核、存储足够且无其他竞争时按 Worker 数线性合计 |

图、事件表、命令配套输出及数字均为**自拟教学材料**，使用处标明；没有 GPU、存储集群或训练实测。Linux 命令面向读懂证据，不要求读者运行。单位为 `KiB/MiB/GiB/TiB = 2^10/2^20/2^30/2^40 B`，`GB/s = 10^9 B/s`，`Gb/s = 10^9 bit/s`。全文区分每 Rank、每节点与全作业，给定的有效速率不能当作硬件规格或性能承诺。

数据加载参数按 **PyTorch 2.9** 文档说明；CUDA 复制机制参考 **CUDA 12.8.1**。GDS 按核对日官方 cuFile 文档及 Release Notes 的 **v1.7、v1.13** 历史条目解释版本差异，未指定一套已经验证的部署组合；当前在线文档会更新，不能据本章推断任意新版本的支持性。资料核对日期：**2026-11-08**。
