# 训推数据供给与多级缓存综合检验

本篇把本章的训练供给与恢复、GPUDirect Storage、多 Rank 时间线归因，以及在线推理权重冷启动与 KV Cache 多级缓存放进同一套实战检验里。无需实机环境，建议先独立完成推演与算式，再展开参考推理逐项核对。

## 一、实战场景与已知条件

### 场景 A：双节点四卡分布式训练

| 维度 | 已知参数与观测事实 |
| --- | --- |
| **集群与任务** | `gpu-a` 运行 `Rank 0 / 1`，`gpu-b` 运行 `Rank 2 / 3`（每 Rank 独占 1 张 GPU）。每 Rank 每步 `32` 个编码图像样本，目标步时 `125 ms`。编码样本平均 `256 KiB`，解码后输入张量 `1 MiB`。默认四 Rank 分片互不重叠、每样本冷读一次，暂不计索引、协议头与预读放大。 |
| **存储布局候选** | **布局甲（小文件）**：每样本 1 个文件，每次取样触发 1 次受限远端查找；查找上限 `800 次/s`，数据路径有效载荷上限 `300 MiB/s`。<br>**布局乙（分片）**：每 `32 MiB` 分片连续存放 `128` 个样本，顺序读完期间复用句柄。 |
| **流水与内存** | 单批耗时：存储读 `R = 50 ms`、CPU 处理 `P = 90 ms`、H2D `H = 8 ms`、GPU 计算与通信 `G = 125 ms`（H2D 与计算可独立推进、缓冲充足，理想多 worker 互不争用）。内存核算采用每 Rank `num_workers=4`、`prefetch_factor=2`、每批主机张量 `32 MiB`。 |
| **Checkpoint** | 每份完整有效载荷 `64 GiB`（4 个 Rank 各分片 `16 GiB`）。每 `600 s` 保存一次，要求 `20 s` 内写完载荷。常驻保留 `3` 份完整版本，新版发布后才删最旧版。恢复合计需读 `64 GiB`，有效聚合读速 `2 GiB/s`。 |
| **GDS 对照记录** | 本地 NVMe 存放预处理定长记录。`gdscheck -p` 输出 `NVMe: p2pdma, compat`，`/etc/cufile.json` 已双处开启 `use_pci_p2pdma` 并允许兼容模式。目标请求成功返回，但短诊断 TRACE 日志打印 `cufile IO mode: POSIX`。另一次核实的直达读使单次 I/O 缩短 `6 ms`，而该读取原本完全藏在前一批计算期间且预取队列从未为空。 |
| **多 Rank 慢步记录** | 某步起点为 `0 ms`，`Rank 0` 在 `70 ms` 进入集合，`Rank 2` 在 `110 ms` 进入集合，全组在 `115 ms` 完成。同窗 `Rank 2` 的 `next_batch_wait_ms` 与 `read_ms` 拉长，解码、H2D 与前置 Kernel 不变。训练读与 Checkpoint 后台写共用同一文件服务，NCCL 使用独立物理高速网络。 |

### 场景 B：四卡 H100 在线推理服务

| 维度 | 已知参数与观测事实 |
| --- | --- |
| **模型与部署** | **Llama 3 70B（BF16）**：权重 `140 GB ≈ 130.4 GiB`，总参数 $W = 7 \times 10^{10}$，80 层，GQA 8 个 KV 头，单头维度 128，单 token KV 为 `320 KiB`（`327,680 B`）。部署于 4× H100 SXM（`TP = 4`），四卡聚合 Prefill 有效算力 $C_{\text{eff}} = 2{,}000\text{ TFLOP/s}$。对照大模型为 **405B FP8（`405 GB`）**。 |
| **冷启动与多级缓存** | 扩容方案：容器镜像冷拉解压（有效 `0.8 GB/s`）、S3 并发流式拉取（`10 GB/s`）、本地四盘 NVMe 预热直读（`25 GB/s`）。推理命中一段 `16,384 tokens`（16K）公共前缀；下级介质备选 L2 主机内存（4 卡 PCIe Gen4 聚合 `100 GB/s`）、L3 本地单盘 NVMe（`6 GB/s`）与普通 10 GbE NFS（`1 GB/s`）。 |

## 二、检验题目

1. **输入路径与供给速率**：沿单个 Rank 梳理采样索引到 GPU Kernel 消费的依赖链，说明页缓存、锁页缓冲与跨流 Event 各自的作用。计算全作业每秒样本数、冷读有效载荷、H2D 输入量及每节点后两项。若数据页命中率 `75%`，后端载荷降为多少？解码和 H2D 会同步降 `75%` 吗？
2. **文件布局与四类存储路径**：布局甲的数据通道与查找通道各允许多少样本/s，整体受限于哪项？按每步 128 样本算平均步时下界。布局乙顺序读每秒打开几次文件、冷读载荷多少？若强随机打散造成分片间跳跃，哪些前提失效？简述本地 NVMe、NFS、Lustre 与 S3 的路径与核心观测。
3. **流水线、内存预算与设备重叠**：计算完全串行、单 worker 流水与双 worker 理想流水的稳态间隔，解释单 worker 为何不能套用 $\max(50, 90, 8, 125)$。算出总加载 worker 数、每 Rank 预取张量内存及 `prefetch_factor` 调为 `4` 后的变化，并列举三项隐形内存开销。为什么只开 `pin_memory` 与 `non_blocking` 仍不足以保证真重叠？
4. **Checkpoint 窗口压力与完成语义**：计算长期平均写速、20 s 突发带宽、三作业撞窗带宽、版本切换期最低逻辑容量和恢复读取下界。说明 `staging_completion`、`upload_completion` 与全组恢复就绪各自证明什么。仅见分片文件和写返回，还缺哪些证据？
5. **GDS 路径核实与端到端收益**：给定记录能否证实目标请求走了 P2PDMA？它实际坐实了什么？验证另一条无 POSIX 日志的请求走上游 P2PDMA，须组合哪些证据？为何 `O_DIRECT`、NCCL GDR 日志和 `nvidia-fs` 零增长都不能单独作证？局部快 `6 ms` 为何未必缩短稳态步时？
6. **多 Rank 慢步归因与三轮对照**：`Rank 0` 账面集合区间多长，其中多少在等 `Rank 2`？下一步查 `Rank 2` 与共享存储的哪些同窗证据？说明本地预置、主机预生成、显存预生成三轮对照各移除什么，为何不能只做第三轮就定罪存储？
7. **百 GB 模型权重冷启动 RTO 核算**：分别计算 70B BF16（`140 GB`）在容器镜像冷拉解压（`0.8 GB/s`）、S3 并发流式（`10 GB/s`）与本地四盘 NVMe（`25 GB/s`）下的纯搬运耗时下界，并算 405B FP8（`405 GB`）在后两方案的耗时。
   - 为何严禁把百 GB 权重塞进镜像？说明 `safetensors`、`fastsafetensors` 与 RDMA 如何协同压低 RTO。
8. **Prefix Caching 与 KV Offloading 盈亏平衡**：对 Llama 3 70B（BF16、`TP=4`）计算 `16,384 tokens` 前缀的完整与单卡 KV 体积、线性层 Prefill 重算耗时，并推导 4 卡聚合与单卡的盈亏平衡带宽 $B_{\text{break-even}}$。
   - 据此评判 L2 内存（`100 GB/s`）、单盘 NVMe（`6 GB/s`）与 10 GbE NFS（`1 GB/s`）。若换成单卡 H100 跑 **8B 模型（32 层 GQA，单 token KV `128 KiB`）配 FP8 Prefill（`1,000 TFLOP/s`）与 BF16 KV**，单盘 NVMe 还划算吗？

## 三、分步参考推理

> [!example]- 参考推理 1：输入路径与供给速率
> **依赖链与缓冲职责**：采样索引 → 定位文件或分片偏移 → 读文件（未命中时填充**页缓存**）→ 进应用缓冲，由 CPU 解码、变换并批整理 → 迁入**锁页主机缓冲** → 拷贝引擎 H2D 进显存 → 计算 Stream 启动 Kernel 消费。
> - **页缓存**复用已读文件字节，命中时省去后端 I/O；
> - **页锁定缓冲**固定主机物理页，支持 GPU 异步高速 DMA；
> - **跨流 Event**建立拷贝 Stream 与计算 Stream 的硬件依赖，确保数据落稳再开算。
>
> **速率核算**：
> $$\text{全作业样本速率} = \frac{4 \times 32}{0.125\text{ s}} = 1{,}024\text{ 样本/s}$$
> $$\text{全作业存储冷读载荷} = 1{,}024 \times 256\text{ KiB/s} = 256\text{ MiB/s}\quad(\text{每节点 } 128\text{ MiB/s})$$
> $$\text{全作业 H2D 输入量} = 1{,}024 \times 1\text{ MiB/s} = 1\text{ GiB/s}\quad(\text{每节点 } 512\text{ MiB/s})$$
>
> **75% 页缓存命中**：后端仅补齐未命中的 25%，载荷降至 $256 \times 25\% = 64\text{ MiB/s}$。但 1,024 样本/s 仍须全部解码并按 `1 GiB/s` 拷进显存，解码与 H2D **不减少**。目录属性缓存另算；若 `DistributedSampler` 发生补齐重复索引，原始假设须按实际取样重算。

> [!example]- 参考推理 2：文件布局与四类存储路径
> **布局甲（小文件）**：数据通道允许 $300 \div 0.25 = 1{,}200\text{ 样本/s}$，但查找上限仅 `800 样本/s`。串联受短板锁死在 **800 样本/s**。全局每步 128 样本，最高步频为 $800 \div 128 = 6.25\text{ 步/s}$：
> $$T_{\text{step}} \ge \frac{1}{6.25} = 160\text{ ms} > 125\text{ ms}$$
>
> **布局乙（分片）**：顺序读并复用句柄时，打开速率压至 $1{,}024 \div 128 = 8\text{ 次/s}$。冷读载荷仍是 `256 MiB/s`，低于 `300 MiB/s` 上限。若强随机打散造成分片间跳跃，句柄复用、连续读与预读命中全部失效，且会引发**读放大**，必须按真实打开率与实际读取量重算。
>
> **四类存储路径**：
> - **本地 NVMe**：本机内核处理命名与权限，冷读直下本地盘；看块设备吞吐、请求大小、`aqu-sz` 与 `r_await`。
> - **NFS**：查找、属性和读写转为 RPC 走网络；看 `nfsstat -m`、`nfsiostat`（`op/s`、`avg RTT`、`avg exe`、重传）与 `mountstats`。
> - **Lustre**：冷打开问 MDS/MDT 拿布局，数据按条带并发走 OSS/OST；分开看元数据耗时、`lfs getstripe` 布局与热点 OST。
> - **S3**：按对象键发整对象 `GET` 或连续 `Range GET`；看请求范围、状态码（如 `503`）、重试与有效下载量。

> [!example]- 参考推理 3：流水线、内存预算与设备重叠
> **稳态出批间隔**：
> - 完全串行：$T_{\text{serial}} = 50 + 90 + 8 + 125 = 273\text{ ms}$。
> - 单 worker 流水：读与解码在同一进程串行，主机阶段锁死为 $50 + 90 = 140\text{ ms}$，稳态间隔 $\max(140, 8, 125) = 140\text{ ms}$。套用 $\max(50, 90, 8, 125)$ 错在假设读与解码能并行处理不同批次。
> - 双 worker 理想流水：主机平均间隔降至 $(50 + 90) \div 2 = 70\text{ ms}$，稳态间隔回到 $\max(70, 8, 125) = 125\text{ ms}$。
>
> **内存预算**：全作业共 $4 \times 4 = 16$ 个加载 worker。`prefetch_factor = 2` 时，每 Rank 目标预取 8 批，成品张量占 $8 \times 32 = 256\text{ MiB}$（单节点 `512 MiB`，全作业 `1 GiB`）；调到 `4` 后翻倍至每 Rank 16 批、**512 MiB**。
>
> 隐形内存包括：解码中间态、在消费批次、锁页复制瞬间的双份副本、进程解释器与元数据，以及容器 `/dev/shm` 占用。
>
> **真重叠条件**：`pin_memory=True` 与 `non_blocking=True` 仅解锁异步提交。设备端真重叠还需独立拷贝引擎、拷贝/计算分流加 Event 同步、独立双缓冲显存槽位，以及严守缓冲生命周期。最终须在 Profiler 时间线上看到设备 H2D 与上一批 Kernel 区间实际相交。

> [!example]- 参考推理 4：Checkpoint 窗口压力与完成语义
> **量化结果**：
> $$\text{长期平均写速} = \frac{64\text{ GiB}}{600\text{ s}} \approx 0.107\text{ GiB/s}, \qquad \text{20 s 突发带宽} = \frac{64\text{ GiB}}{20\text{ s}} = 3.2\text{ GiB/s}$$
> $$\text{三作业撞窗带宽} = 3 \times 3.2 = 9.6\text{ GiB/s}, \qquad \text{切换期逻辑容量} = (3 + 1) \times 64 = 256\text{ GiB}$$
> $$\text{恢复读取下界} = \frac{64\text{ GiB}}{2\text{ GiB/s}} = 32\text{ s}$$
> （实际恢复还须叠加元数据解析、反序列化、H2D 与最慢 Rank 等待，且 DCP 扩缩容会重算读取计划。）
>
> **完成语义边界**：
> - `staging_completion` 仅证明本 Rank 隔离副本就绪，后台尚未落盘；
> - 默认协调的 `upload_completion` 表示全组分片写完且 `.metadata` 已发布，但断电持久性仍受 `sync_files`、目录 `fsync` 与存储契约制约；
> - 全组恢复就绪要求全部必需 Rank 找到有效版本、读齐并装入 GPU；
> - 仅见分片与普通写返回，既缺 `.metadata` 版本完整性证据，也缺 `fsync`/NFS `COMMIT` 持久性证据。

> [!example]- 参考推理 5：GDS 路径核实与端到端收益
> **判定结论**：记录**证伪**了目标请求走 P2PDMA。`gdscheck` 与配置仅说明具备候选能力，调用返回只说明拿到了数据。TRACE 中的 `cufile IO mode: POSIX` 直接坐实该请求已静默退回兼容路径。
>
> **完整取证组合**：先用 `findmnt -T` 核对挂载、`lspci -t` 核对拓扑，确认缓冲对齐与双处 `use_pci_p2pdma` 开关。再用 `gdscheck -p` 确认候选能力。最后用 `gds_stats -p <pid> -l 3` 核对每卡请求 `n`、`posix` 降级计数为 0 与 `unalign`，配合同版本 P2PDMA 统计和短时 TRACE 交叉验证。
>
> **三类单据失效原因**：`O_DIRECT` 只管跳过主机页缓存，不指定显存目标。NCCL GDR 日志只覆盖网卡通信，不管文件 I/O。`/proc/driver/nvidia-fs/stats` 只计传统 `nvidia-fs` 模块，上游 P2PDMA 绕开了它，零增长无法区分 P2PDMA 还是兼容回退。
>
> **局部收益与整步**：提前 `6 ms` 未必缩短稳态步时。该读取原本完全藏在前一批计算中且队列未见底，不在关键路径上，步时可毫无变化（但 CPU 与 DRAM 减压可另行实测）。

> [!example]- 参考推理 6：多 Rank 慢步归因与三轮对照
> **时间线拆解**：`Rank 0` 账面集合区间为 $115 - 70 = 45\text{ ms}$。其中 $110 - 70 = 40\text{ ms}$ 全在等 `Rank 2` 抵达，真正集合执行仅 `5 ms`。把它当网络变慢属于典型误诊。
>
> **下一步查什么**：首个晚到锁定在 `Rank 2` 的取批与读取，下一步应查同批 `read_ms`、文件打开/读耗时及共享服务的操作率与 RTT。
>
> 同时对齐同窗 Checkpoint 后台 `write_ms`、`publish_ms` 与实际写流量（本地 staging 不等同服务端写流量）验证读写争用；因 NCCL 走独立物理网，存储端口计数不可当成 NCCL 拥塞证据。
>
> **三轮对照**：本地预置移除远端存储与存储网；主机预生成再移除读盘与 CPU 解码；显存预生成再移除主机交付与 H2D。若跳过前两轮直接做第三轮且慢步消失，只说明整条输入链里至少有一环卡住，无法直接断定根因就是存储。

> [!example]- 参考推理 7：百 GB 模型权重冷启动 RTO 核算
> **纯搬运耗时下界（$T_{\text{load}} \ge V_{\text{weights}} / B_{\text{eff}}$）**：
> - **70B BF16（`140 GB`）**：镜像冷拉解压（`0.8 GB/s`）需 $140 \div 0.8 = \mathbf{175.0\text{ s}}$（约 2.9 分钟，含初始化轻松超 3 分钟）；S3 并发流式（`10 GB/s`）需 $\mathbf{14.0\text{ s}}$；本地四盘 NVMe（`25 GB/s`）仅需 $\mathbf{5.6\text{ s}}$。
> - **405B FP8（`405 GB`）**：S3 并发流式需 $405 \div 10 = \mathbf{40.5\text{ s}}$；本地四盘 NVMe 仅需 $405 \div 25 = \mathbf{16.2\text{ s}}$。
>
> **禁用权重镜像原因**：单核 gzip 解压极慢、OverlayFS 落盘极易打爆系统盘，且代码改动被迫绑死百 GB 镜像重复推拉，彻底拖垮弹性扩容 RTO。
>
> **三项协同加速**：`safetensors` 用 JSON 头实现零拷贝与按 TP 并发切片读，消除 `pickle` 开销。`fastsafetensors` 借助 GDS 让本地 NVMe 权重绕开主机内存直达显存。无本地缓存的新节点还可借跨机 RDMA 从活跃副本内存或显存直拉权重，把百 GB RTO 压入数秒级。

> [!example]- 参考推理 8：Prefix Caching 与 KV Offloading 盈亏平衡
> **1. Llama 3 70B（BF16、`TP=4`）16K 前缀核算**：
> $$V_{\text{KV}} = 16{,}384 \times 320\text{ KiB} = 5.0\text{ GiB} \approx 5.369\text{ GB}\quad(\text{单卡 } 1.25\text{ GiB} \approx 1.342\text{ GB})$$
> $$F_{\text{linear}} = 2 \times 7 \times 10^{10} \times 16{,}384 \approx 2{,}294\text{ TFLOP}, \qquad T_{\text{recompute}} \approx \frac{2{,}294}{2{,}000} \approx \mathbf{1.147\text{ s}}$$
> $$B_{\text{break-even}} = \frac{s_{\text{KV}} \cdot C_{\text{eff}}}{2 W} = \frac{327{,}680 \times 2 \times 10^{15}}{1.4 \times 10^{11}} \approx \mathbf{4.68\text{ GB/s}}\;(\text{4 卡合计；单卡 } \mathbf{1.17\text{ GB/s}})$$
>
> **三类介质判定**：
> - **L2 主机内存（`100 GB/s`）**：换入耗时 `53.7 ms`，比重算快 21 倍，极其划算；
> - **L3 本地单盘 NVMe（`6 GB/s`）**：换入耗时 `895 ms < 1,147 ms`，略快于重算，且能把 Tensor Core 完全让给其他并发请求；
> - **10 GbE NFS（`1 GB/s`）**：换入耗时 `5.37 s`，比重算慢近 4.7 倍，明显不划算，应直接重算。
>
> **2. 8B 模型 + FP8 Prefill（单卡 H100）反转验证**：
> 代入 $W = 8 \times 10^9$（$2W = 1.6 \times 10^{10}$）、$s_{\text{KV}} = 128\text{ KiB} = 131{,}072\text{ B/tok}$、$C_{\text{eff}} = 10^{15}\text{ FLOP/s}$：
> $$B_{\text{break-even, 8B-FP8}} = \frac{131{,}072 \times 10^{15}}{1.6 \times 10^{10}} \approx \mathbf{8.19\text{ GB/s}} > 6\text{ GB/s}$$
> **单盘 NVMe（`6 GB/s`）不再划算。** 模型变小且启用 FP8 算力翻倍而 KV 维持 BF16 时，重算极快。此时唯有主机内存（`25–50 GB/s`）或多盘 NVMe 条带才能跑赢重算。

## 四、全章知识串联与下阶段衔接

回看整章，训练与推理两条存储主线表面形态不同，底层却共用一套严密的工程骨架：

- **训练供给与恢复主线**：文件布局与采样顺序决定操作率与字节率，页缓存改写回源流量。加载 worker 与预取队列用主机资源换稳态吞吐，锁页缓冲配 Stream/Event 实现 H2D 真重叠。Checkpoint 把流向反转成短窗口突发写，引入稳定副本与版本发布语义。多 Rank 时间线与三轮剥离则防止把慢成员数据等待误诊为网络故障。
- **推理加载与缓存主线**：模型冷启动把百 GB 只读权重搬运推上弹性扩容 RTO 的关键路径，催生了 `safetensors`、并发流式、本地预热、GDS 与 RDMA 直拉。长上下文 KV 溢出催生了 Prefix Caching 与三级卸载，而换入是否划算永远受盈亏公式 $B_{\text{break-even}} = \frac{s_{\text{KV}} \cdot C_{\text{eff}}}{2 W}$ 约束。

至此，全书第二阶段（[第 05 章](../05_为什么一个作业需要多张GPU/00_内容大纲.md)至本章）圆满收官。你已经贯通了多卡并行、RDMA、集群网络、NCCL 与训推存储的底层逻辑。

接下来进入第三阶段——[第 10 章 GPU 如何进入容器](../10_GPU如何进入容器/00_内容大纲.md)将推开云原生大门，看看 GPU 设备、驱动库与高速存储路径如何穿过容器与 Kubernetes 边界。后续在[第 15 章](../15_从单个Pod放置到多卡作业调度/00_内容大纲.md)与[第 17 章](../17_把设备、网络与作业状态联系起来/00_内容大纲.md)至[第 19 章](../19_节点交付、版本变更与集群持续运行/00_内容大纲.md)中，权重预热亲和、数据等待指标和存储验收还将汇聚成完整的集群运维闭环。
