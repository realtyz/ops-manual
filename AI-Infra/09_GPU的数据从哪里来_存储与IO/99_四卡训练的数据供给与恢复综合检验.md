
本篇把输入路径、存储请求、加载流水线、Checkpoint、GDS 和多 Rank 时间线放进同一份纸面材料。所有数值与记录均为**教学设定**，没有声称在真实 GPU 或存储集群上执行。请写出关键推导，并区分“材料已经证明的事实”“仍需验证的解释”。

## 练习材料

节点 `gpu-a` 上是 Rank 0、1，节点 `gpu-b` 上是 Rank 2、3，每 Rank 一个训练进程和一张 GPU。每 Rank 每步 32 个样本，目标计算与通信步时为 125 ms。编码样本平均 256 KiB，整理后的输入张量为 1 MiB。除题目明确改变条件外，四个 Rank 的样本互不重叠，每样本只从存储读取一次；忽略索引、协议、预读放大与重试。

存储有两种候选布局：

- **甲：小文件。** 每样本一个文件，每次取样都触发一次受限远端查找。查找上限为 800 次/s，数据路径有效载荷上限为 300 MiB/s。
- **乙：分片。** 每个 32 MiB 分片连续存放 128 个样本。计算打开次数时，先假设各分片被连续消费、句柄保持到读完且索引开销忽略。

加载算例中，每批读取 50 ms、CPU 处理 90 ms、H2D 8 ms、GPU 计算与通信 125 ms。跨批流水假设 H2D 与 GPU 工作可独立推进，缓冲充足；多 worker 的理想模型先假定并发不增加每批读取或处理时间。另一个内存估算使用每 Rank `num_workers=4, prefetch_factor=2`，每批 CPU 张量为 32 MiB。

每份 Checkpoint 的有效载荷为 64 GiB，四个 Rank 等量分片。每 600 s 保存一次，希望 20 s 内写完载荷；保留三份已完成版本，新一份完整后才删除最旧版本。恢复时合计读取 64 GiB，有效聚合读速率为 2 GiB/s。

GDS 对照使用 NVMe 上的预处理定长记录。教学记录为：`gdscheck -p` 报告 `NVMe: p2pdma, compat`，配置同时启用两个 `use_pci_p2pdma` 并允许兼容模式；目标请求成功返回，但对应 TRACE 为 `cufile IO mode: POSIX`。另一次已核实的直达对照使单次 I/O 提前 6 ms，而该 I/O 原本完全隐藏在前一批计算期间，取批队列从未为空。

同一步的集合教学时序为：Rank 0 在 70 ms 进入，Rank 2 在 110 ms 进入，全组在 115 ms 完成。Rank 2 的 `next_batch_wait_ms` 和 `read_ms` 同窗口增加，解码、H2D 与前置 Kernel 时长不变。存储读与 Checkpoint 写在本题中共用同一文件服务；计算通信使用独立的物理网络，不能把存储端口计数直接当成 NCCL 端口证据。

## 题目

1. **输入路径与供给速率。** 先按一个 Rank 画出或排列“采样索引→定位→文件读取与缓存→解码/批整理→主机输入张量→H2D→设备输入→Kernel”的依赖链，标出页缓存、页锁定和跨 Stream Event 各自解决什么。再计算全作业每秒样本数、冷读存储有效载荷与 H2D 输入量，以及每节点的后两项。若另一轮按字节的客户端数据页命中率为 75%，且无额外预读或重复拉取，后端有效载荷变为多少？解码量和 H2D 是否也减少 75%？
2. **文件布局与存储路径。** 甲布局的数据路径与查找路径分别允许多少样本/s，整体受哪一项限制？按每步全局 128 样本估算平均步时下界。乙布局达到目标样本速率需要多少次打开/s和多少有效载荷？如果随机采样使各 Rank 在分片间来回跳，哪些题设必须重新核对？再分别说明本地 NVMe、NFS、Lustre 与 S3 的命名/元数据和数据请求经过哪里，以及应选哪类观测区分路径。
3. **流水线、缓冲与设备交接。** 分别计算完全串行、单 worker 跨批流水、双 worker 理想跨批流水的稳态出批间隔。为什么不能对单 worker 直接使用 `max(50,90,8,125)`？按内存估算的配置，四个 Rank 共多少加载 worker，每 Rank 的预取张量部分占多少主机内存？若把 `prefetch_factor` 增为 4，这部分怎样变化，还有哪些内存项未计入？最后说明 `pin_memory=True` 与 `non_blocking=True` 为什么仍不保证 H2D/Kernel 实际重叠，还需哪些 Stream/Event、槽位和缓冲生命周期条件。
4. **保存与恢复。** 计算 Checkpoint 的长期平均写速率、20 s 窗口带宽、三个作业窗口完全重叠时的合计带宽，以及版本切换期间的最低逻辑容量。恢复读取的时间下界是多少？`staging_completion`、框架 `upload_completion` 与所有 Rank 恢复就绪分别能证明什么？若只看到分片文件和普通写调用返回，还缺哪些完整性与持久性证据？
5. **GDS 路径。** 给定记录能否证明目标请求走了 P2PDMA？它实际支持什么结论？若要进一步核实另一条没有 POSIX 日志的请求是否使用上游 P2PDMA，应组合哪些文件、拓扑、配置和统计证据？为什么 `O_DIRECT`、NCCL 的 GDR 日志或 `/proc/driver/nvidia-fs/stats` 没有增量都不能单独给出答案？6 ms 的局部收益是否必然缩短稳态步时？
6. **多 Rank 归因。** Rank 0 的集合观察区间多长，其中多少发生在 Rank 2 抵达之前？能否把这段全部称为网络传输变慢？下一步应查 Rank 2 的哪些记录与哪一层存储证据？分别说明“预置本地样本”“主机预生成批次”“显存预生成输入”三轮对照各移除什么；若只进行最后一轮，为什么不足以直接认定原根因就是存储？

## 参考推理

### 1. 先走通输入路径，再按数据形态计算

一个 Rank 的依赖链是：采样器给出索引，数据集定位文件或分片内偏移并读取编码字节；所需数据页未命中时由后端填充页缓存，随后字节进入应用缓冲，经 CPU 解码、变换和 `collate_fn` 形成主机输入张量，再经 H2D 成为设备输入，最后由 Kernel 消费。页缓存保存文件字节，页锁定为异步 DMA 提供合适的主机缓冲，二者位置与作用不同；若 H2D 与 Kernel 分属不同 Stream，计算 Stream 必须等待对应拷贝完成 Event。无论 `num_workers=0` 还是多进程加载，这些对象转换都不能被跳过。

全作业样本速率为：

`4 × 32 ÷ 0.125 = 1,024 样本/s`。

冷读存储有效载荷为 `1,024 × 256 KiB/s = 256 MiB/s`，H2D 输入量为 `1,024 × 1 MiB/s = 1 GiB/s`。每节点有两个 Rank，所以分别是 `128 MiB/s` 和 `512 MiB/s`。前者使用编码字节，后者使用解码整理后的张量字节，不能混用。

75% 数据页命中只让后端承担未命中的 25%：`256 × 25% = 64 MiB/s`。全部样本仍要解码，全部输入张量仍要送入 GPU，所以 CPU 解码工作与 H2D 不按 75% 减少。目录项、属性与打开操作的命中率另算；若 DistributedSampler 为凑齐各 Rank 样本数而补充重复索引，“互不重叠、每样本只读一次”的原始假设也需要按实际索引重算。 [PyTorch 2.9 DistributedSampler](https://docs.pytorch.org/docs/2.9/data.html#torch.utils.data.distributed.DistributedSampler)

### 2. 请求率、字节率与存储路径分别核对

甲的数据路径允许 `300 ÷ 0.25 = 1,200 样本/s`，查找路径只允许 800 样本/s，所以整体先受查找限制。全局每步有 `4 × 32 = 128` 样本，按 800 样本/s 只能完成 `800 ÷ 128 = 6.25 步/s`，对应仅由该模型给出的平均步时下界为 160 ms；完整训练还需满足处理、拷贝与计算依赖。

乙在连续消费的前提下需要 `1,024 ÷ 128 = 8 次打开/s`，冷读有效载荷仍是 256 MiB/s，低于题设 300 MiB/s。若随机采样导致分片间跳跃，句柄复用、连续读取、预读命中和读放大假设都可能失效；需要按实际打开次数、Range/读取大小和从后端取回的字节重新计算，而不能继续使用 8 次打开/s。

| 访问路径 | 命名/元数据与数据请求 | 有区分力的观测 |
| --- | --- | --- |
| 本地 NVMe | 本机文件系统处理命名与权限，冷读数据请求到本机块设备 | 目标挂载对应的设备吞吐、请求大小、排队与 `r_await`，再与目标 Rank 请求互证 |
| NFS | 客户端把查找、属性和读写翻译成 RPC，经网络到服务端 | 按挂载区分 `op/s`、RTT、执行时间与重传，不能只合计 MiB/s |
| Lustre | 冷打开经 MDS/MDT 取得命名空间与布局，数据再按条带访问 OSS/OST | 分开看元数据操作、`lfs getstripe` 布局和实际涉及目标，不能把所有 OST 带宽直接相加 |
| S3 | 按对象键发整对象 GET 或连续 Range GET；对象键不是文件系统目录，分片可保存为对象，但按对象请求语义读取 | 记录请求键与范围、响应码、耗时、重试和实际下载字节 |

### 3. 最慢阶段决定长期节奏，队列只保存余量

完全串行为 `50 + 90 + 8 + 125 = 273 ms`。单 worker 把读取与处理串成 140 ms 的生产阶段，跨批流水后稳态间隔为 `max(140,8,125) = 140 ms`。直接使用 `max(50,90,8,125)` 会假设读取与解码能同时处理不同批次，单 worker 不满足这个条件。

双 worker 在每批时长不变、两路真正并行的理想模型下，主机平均生产间隔为 `(50 + 90) ÷ 2 = 70 ms`，全链稳态间隔由 `max(70,8,125) = 125 ms` 决定。若共享 CPU 或存储使每批时长上升，必须代入新的时长；队列深度不能修复长期产能不足。

内存估算中，四个 Rank 共有 `4 × 4 = 16` 个加载 worker。每 Rank 的预取目标为 `4 × 2 = 8` 批，张量部分为 `8 × 32 = 256 MiB`；`prefetch_factor=4` 时为 16 批、512 MiB。此处不含解码中间态、正在交付或消费的批次、锁页期间可能并存的副本、进程地址空间和数据集元数据，也不表示任何时刻都恰好物化这么多批次。 [PyTorch 2.9 prefetch_factor](https://docs.pytorch.org/docs/2.9/data.html#torch.utils.data.DataLoader)

`pin_memory=True` 让标准 CPU 张量批次位于页锁定内存，`non_blocking=True` 则尝试相对主机异步提交，二者都不保证设备区间自动重叠。还需可用拷贝引擎与设备资源，把下一批 H2D 放到拷贝 Stream，并让计算 Stream 等待对应 Event；不同批次使用独立目标槽位，或等旧消费者完成后复用。主机在拷贝完成前不得改写或释放源缓冲，设备目标槽也要等最后消费者完成。最终要看到设备 H2D 区间与上一批 Kernel 区间实际相交，才能确认重叠，而不是只看异步调用已经返回。 [PyTorch 2.9 Tensor.to](https://docs.pytorch.org/docs/2.9/generated/torch.Tensor.to.html) · [CUDA 12.9 拷贝与计算重叠](https://docs.nvidia.com/cuda/archive/12.9.1/cuda-c-programming-guide/index.html#overlap-of-data-transfer-and-kernel-execution)

### 4. 平均速率、窗口压力与完成契约分开算

长期平均写速率为 `64 ÷ 600 ≈ 0.107 GiB/s`；20 s 窗口要求 `64 ÷ 20 = 3.2 GiB/s`；三个作业完全重叠时为 `9.6 GiB/s`。保留三份完整版本且新版完成后才删最旧版，切换期同时存在三份完整版和一份进行中版本，最低逻辑容量为 `(3 + 1) × 64 = 256 GiB`，后端副本与临时开销另计。恢复读取下界为 `64 ÷ 2 = 32 s`，不含不能重叠的元数据、反序列化、装载与最慢 Rank 等待。

`staging_completion` 表示本 Rank 可用于后台保存的本地稳定副本已就绪，不是全组上传完成。在本文默认协调的 DCP 路径中，`upload_completion` 表示后续保存过程（含必要协调与最终元数据发布）完成；不等于仅本 Rank 文件关闭，也不证明新进程已经恢复或任意故障下均已持久化。所有 Rank 恢复就绪还要求找到完整版本、按目标布局读齐并装载状态。只有分片文件和普通写返回，尚缺最终元数据及版本完整性证据，也缺按目标后端契约确认的数据与命名持久性证据。PyTorch 2.9.0 的 `FileSystemWriter(sync_files=True)` 会同步数据文件和临时元数据后再重命名，但不能把这个实现细节泛化成所有后端、所有目录项和任意故障的持久性保证。 [DCP 2.9.0 保存返回值](https://github.com/pytorch/pytorch/blob/v2.9.0/torch/distributed/checkpoint/state_dict_saver.py#L203-L214) · [FileSystemWriter 完成路径](https://github.com/pytorch/pytorch/blob/v2.9.0/torch/distributed/checkpoint/filesystem.py#L754-L786)

### 5. 候选能力、实选路径和端到端收益是三件事

给定记录不能证明目标请求走了 P2PDMA。`gdscheck` 与配置给出候选能力，成功返回只说明读取完成，而 `cufile IO mode: POSIX` 明确说明对应请求走了兼容路径。 [GDS 兼容模式诊断](https://docs.nvidia.com/gpudirect-storage/troubleshooting-guide/advanced-troubleshooting.html#gds-and-compatibility-mode)

对另一条没有 POSIX 日志的请求，先核对目标文件实际挂载、文件系统与偏移/长度、GPU 缓冲及注册，再核对 GPU—NVMe 拓扑、两个 P2PDMA 开关、平台候选能力，最后对齐同一请求的用户态计数、TRACE/后端选择记录和该版本提供的 P2PDMA 统计。`O_DIRECT` 只控制一类主机直接 I/O 行为，NCCL GDR 只覆盖通信路径；`nvidia-fs` 统计又不包含兼容或上游 P2PDMA I/O，所以三者都不能独立回答本次 cuFile 请求的后端。 [GDS NVMe P2PDMA 配置](https://docs.nvidia.com/gpudirect-storage/troubleshooting-guide/nvme-p2pdma-troubleshooting.html#cufile-json-settings) · [GDS 用户态计数](https://docs.nvidia.com/gpudirect-storage/troubleshooting-guide/user-space-counters-in-gpudirect-storage.html#distribution-of-io-usage-in-each-gpu) · [P2PDMA 与 nvidia-fs 统计边界](https://docs.nvidia.com/gpudirect-storage/troubleshooting-guide/nvme-p2pdma-troubleshooting.html#statistics)

6 ms 的局部 I/O 提前不必然缩短稳态步时。题设说明 I/O 已完全隐藏在计算期间且队列从未为空，它不在当前关键路径上，因此端到端步时可以不变；CPU 时间、主机内存路径占用与缓冲余量是否改善，应分别测量，读取的有效载荷字节也不会仅因直达而减少。若换成 CPU 解码图像，还要另算预处理位置与数据形态的变化。

### 6. 先找最早晚到，再逐段移除

Rank 0 的观察区间是 `115 − 70 = 45 ms`，其中 `110 − 70 = 40 ms` 在 Rank 2 抵达之前。它不是 45 ms 的纯网络传输时间。已有记录把首个晚到指向 Rank 2 的取批和读取；下一步应对齐该批的 `read_ms`、应用打开/读取时长、目标挂载的相应操作率与时延，以及服务端或本地设备同窗证据。还要对齐同一 `checkpoint_id` 的后台 `write_ms`、`publish_ms` 和实际写流量，检查它们是否与 Rank 2 的读取变慢、挂载 RTT/排队及服务端负载同窗，以检验共享文件服务争用；本地 staging 时间不能直接当作文件服务写流量。解码、H2D 和前置 Kernel 不变使这些环节的解释优先级下降，但系统级聚合指标仍需与该 Rank 的实际文件和请求对应，不能凭总量直接归因。存储端口计数也不能替代独立 NCCL 网络的证据。

本地预置只替换远端存储与存储网络，保留读取、解码和 H2D；主机预生成同时移除读取与解码；显存预生成进一步移除主机交付和 H2D。只做最后一轮时，即使慢步消失，也只能说明被移除的整条输入链中某个环节有影响，不能区分远端读取、本地读取、CPU 解码、队列或 H2D。应由外到内逐轮对照，并观察最先变化的阶段和端到端步时；若存储与计算网络分用，还要用各自路径的证据验证，不能跨端口替代。

## 本章知识关系

GPU 的输入等待可以沿一条连续关系重建：**样本布局与采样顺序、缓存和并发共同影响存储操作与字节请求，缓存改变其中需要走到后端的部分，CPU 与加载 worker 把字节生产成主机批次，预取队列保存时间余量，H2D 与 Stream/Event 把批次交付给设备，慢 Rank 再把本地延迟传播到集合同步点。**

Checkpoint 复用同一套路径与容量思维，但增加了稳定副本、版本发布、持久性和恢复布局。GDS 只改变受支持请求的文件载荷搬运段，不替代数据组织、CPU 预处理、完成同步或端到端验证。局部速率、局部路径和局部完成信号只有放回关键路径，才能解释整步是否改善。

至此，第二阶段已经覆盖多卡作业为何协同、RDMA 与网络怎样承载交换、NCCL 怎样组织通信，以及存储怎样供给和保存数据。第 10 章开始进入 Kubernetes 交付阶段，先解释主机上的 GPU、驱动库和设备节点怎样提供给容器；本章假定的文件挂载与设备路径也将在容器边界内重新核对。
