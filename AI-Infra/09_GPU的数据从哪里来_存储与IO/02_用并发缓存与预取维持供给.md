# 用并发缓存与预取维持供给

## 增加 Worker 是增加服务并发

加载器把索引或读取任务交给 Worker，由 Worker 访问数据、解码、变换和拼批。PyTorch 的 `num_workers` 是**每个 DataLoader** 的子进程数，`prefetch_factor` 是每 Worker 预先加载的批数；`persistent_workers` 决定一轮数据遍历结束后是否保留 Worker。参数语义见 [PyTorch 2.9 DataLoader](https://docs.pytorch.org/docs/2.9/data.html#torch.utils.data.DataLoader)。

以下是**教学配置片段**，假定 `dataset` 和负责跨 Rank 划分样本的 `sampler` 已由应用提供；不是可独立运行的训练程序。

```python
loader = DataLoader(
    dataset, batch_size=64, sampler=sampler,
    num_workers=4, prefetch_factor=2,
    pin_memory=True, persistent_workers=True,
)
```

一个 Rank 有四个 Worker，每节点两个 Rank 就有八个 Worker，全作业十六个。`prefetch_factor=2` 不是“整机只预取两批”。`persistent_workers` 减少跨 Epoch 的重建成本，Epoch 指一次约定的数据遍历；它不会凭空提高解码速度。样本划分也要独立处理，否则更多 Worker 可以更快地产生重复样本；对 IterableDataset，还要由实现同时按 Rank 和 Worker 划分数据，见 [PyTorch 2.9 IterableDataset](https://docs.pytorch.org/docs/2.9/data.html#torch.utils.data.IterableDataset)。

本模型每 Worker 独占一个可用 CPU 核时为 400 样本/s，四个可达 1,600，超过单 Rank 所需的 800。但每 Worker 内部的解码库还可能启动线程，八个 Worker 各开八线程会争用 32 个核。增加并发也会增加存储请求与内存占用；当共享存储已满、CPU 内存带宽已满或线程过量时，更多进程可能加大排队，不能继续按 Worker 数线性预测。

## 预取用空间交换短期等待

设队列已有 Q 批就绪，GPU 每 80 ms 取一批。若生产者完全停止供给，理想覆盖时间为 `Q × 80 ms`。已有四批时可覆盖 320 ms；这只计算已准备好的队列，不把仍在读取/解码的任务算进去。生产者恢复后还要有高于消费的余量，才能补回库存。

例如生产者稳定每秒 6.25 批，GPU 需要 12.5 批。即使事先攒了八批，净消耗为 6.25 批/s，也会在 `8/6.25 = 1.28 s` 后耗尽。增加队列延缓了第一次空队列，没有改变长期吞吐。

`4 Worker × prefetch_factor 2 = 8 批/Rank` 表达预取任务规模，不保证某时刻八批都已完成，也不保证八批均处于锁页状态。Worker、进程间队列、锁页线程和主进程可以各持有不同阶段的对象。正文采用下面的**显式内存估算**，不把参数乘法当作实际 RSS 测量：

| 每节点对象 | 教学峰值假设 | 内存 |
| --- | --- | --- |
| 预取逻辑数据 | 两 Rank 各八批，每批 64 MiB | 1 GiB |
| 暂时共存的可分页与锁页副本 | 假定上行逻辑数据各有一份副本 | 合计 2 GiB |
| Worker 解码工作区 | 八个 Worker 各 128 MiB，独立于上述副本 | 1 GiB |
| 主进程当前批 | 两份各 64 MiB，另行保留 | 0.125 GiB |
| 上述合计 | 不含其他对象 | 3.125 GiB |

Dataset 索引、进程对象、库、页缓存、共享内存及分配器缓存仍要另算；PyTorch 也说明被 Worker 访问的父进程 Python 对象可能显著放大内存，见 [Multi-process data loading](https://docs.pytorch.org/docs/2.9/data.html#multi-process-data-loading)。不能将 3.125 GiB 当作任意框架的严格峰值。实际核对应按对象生命周期、进程内存和节点整体占用合起来看，避免共享页被 RSS 简单重复求和。

## 页缓存、本地缓存与预取缓存的是不同东西

页缓存用主机 DRAM 留住文件内容；本地缓存把远端数据复制到 NVMe；加载队列保存待消费批次，通常已完成更多处理。它们减少的工作不同：

| 命中位置 | 避免的主要工作 | 仍需完成的工作 |
| --- | --- | --- |
| 客户端页缓存中的编码字节 | 再次访问后端的数据读取 | 解码、拼批及 H2D，元数据是否命中另看 |
| 本地 NVMe 上的编码文件 | 从远端重新传入这份数据 | 本地读取、解码和 H2D |
| 已准备好的主机 Batch | 本轮文件读取及 CPU 准备 | 锁页/复制是否已完成，以及 GPU 消费 |

本章数据集编码容量为 2 TiB 的一个独立缓存例子，单节点内存为 256 GiB，应用等占去 64 GiB后，最多按 192 GiB 留给页缓存。即使没有其他开销，也仅容纳数据集的 `192/2048 = 9.375%`。这只是可缓存比例，**不是命中率**；命中率取决于下一次读哪些数据、复用距离与逐出行为。一次顺序遍历后再从头读，不会自动让整轮成为内存读取。

如果在同一访问区间实测/给定按字节计算的客户端命中率为 75%，节点逻辑读取需求 400 MiB/s，其中后端数据字节需求可估为 `400 × 25% = 100 MiB/s`；CPU 仍需处理全部 1,600 样本/s。这个公式只适用于同一编码字节口径，不能把“75% 文件数命中”直接代入大小不均的文件集。

比较缓存效果要说明客户端缓存、服务端缓存和本地副本的状态。“冷客户端”不等于“所有后端介质都冷”。本章不要求读者清缓存；Linux 文档指出 `drop_caches` 会丢弃可回收缓存并产生重建成本，不应当作日常缓存治理方式，见 [内核 drop_caches 说明](https://www.kernel.org/doc/html/latest/admin-guide/sysctl/vm.html#drop-caches)。

## 锁页和异步复制仍然需要依赖关系

锁页主机内存使 GPU DMA 可以使用稳定的主机页，避免传输阶段再做某些临时搬运。锁页过多也会挤占系统可灵活回收的内存。机制见 [CUDA 12.8.1：Pinned Memory 与 Asynchronous and Overlapping Transfers](https://docs.nvidia.com/cuda/archive/12.8.1/cuda-c-best-practices-guide/index.html#pinned-memory)。

应用提交 `batch.to(device, non_blocking=True)`，主要表达允许复制调用异步返回；不能由调用返回推断数据已到显存。让第 k+1 批复制与第 k 批计算重叠，还需要可用复制引擎、适合异步 DMA 的主机缓冲、不同 Stream 的安排，以及缓冲生命周期和消费等待。相同 Stream 内先复制再计算，会保持先后关系。示例与条件见 [PyTorch pin_memory / non_blocking 教程](https://docs.pytorch.org/tutorials/intermediate/pinmem_nonblock.html)。

可以把正确顺序读成：主机完成写入锁页缓冲→提交 H2D→确认对应复制完成后才消费目标显存→消费完成后才能复用这份目标缓冲。异步提交期间也不能提前改写源数据。双缓冲让不同批次轮换使用两份缓冲，提供重叠的空间，但会增加主机和显存容量需求。本章的 80 ms 理想间隔只有在这些条件满足时才成立。
