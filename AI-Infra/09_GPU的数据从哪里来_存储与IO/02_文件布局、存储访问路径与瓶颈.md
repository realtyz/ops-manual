# 文件布局、存储访问路径与瓶颈

拿测速工具测一块盘或一套共享存储，大文件顺序读轻松飙到 `3 GB/s`。这比上一篇算出的 `256 MiB/s` 富余了十倍。可训练脚本一跑起来，数据加载却照样卡成慢动作。

问题出在哪？存储系统从来不只看“每秒读多少字节”。它还背着另一本同样沉重的账：**每秒完成多少次打开、查找和零散小读**。把操作率、字节率与物理路径摆在一起，卡点才会原形毕露。

## 一、找文件与读数据，是两套不同的开销

程序打开并读取一个文件，底层会拆成两类截然不同的工作。前者盯的是目录与权限，后者盯的才是真正的数据块。

| 维度 | 底层典型动作 | 常见缓存与复用机制 | 排查时应抓的证据 |
| --- | --- | --- | --- |
| **命名与元数据** | 路径查找、目录项解析、权限属性校验、打开/关闭 | 目录项缓存（dentry）、属性缓存、长持文件句柄 | 应用 `open` 耗时、客户端元数据操作率、服务端元数据负载 |
| **文件数据读** | 按偏移读取字节，未命中时向块设备或远端服务回源 | 客户端页缓存、服务端缓存、顺序预读 | 请求大小、IOPS、读放大比例、排队深度与尾延迟 |

一次应用层 `open`、一次远端查找 RPC 和一次块设备读处于不同层次，数量并不天然一一对应。对大小相近的数据请求，吞吐量遵循一条朴素公式：

$$\text{有效数据速率} \approx \text{每秒完成请求数（IOPS）} \times \text{每请求交付的有效字节数}$$

在存储尚未饱和前，适度增加并发能重叠等待、推高吞吐。一旦磁盘队列、服务端线程或链路打满，继续盲目加并发只会让队列越滚越长，尾延迟直线飙升。

> [!tip] 工程直觉：用 `fio` 测存储，绝不能拿顺序大读当随机小读
> 压测本地 NVMe 或共享目录前，务必固定请求大小、访问模式、队列深度与缓存开关。下面两组典型命令跑出的成绩，往往相差几个数量级：
> ```bash
> # 对照 A：大块顺序读（模拟读取打包好的大分片或模型权重，--direct=1 绕开页缓存）
> fio --name=seq_shard --filename=/mnt/data/test.bin --size=8G \
>     --rw=read --bs=1M --ioengine=io_uring --iodepth=32 --direct=1 --runtime=30
>
> # 对照 B：随机小读（模拟高并发零碎小文件或极小切片读取，直面 IOPS 与延迟墙）
> fio --name=rand_small --filename=/mnt/data/test.bin --size=8G \
>     --rw=randread --bs=4k --ioengine=io_uring --iodepth=32 --direct=1 --runtime=30
> ```
> 同样的硬件，`seq_shard` 跑满数 GB/s 很轻松。而 `rand_small` 哪怕跑出几万 IOPS，折算成字节吞吐也可能只有一两百 MB/s。

## 二、小文件 vs 分片：同一批数据，两份账本

沿用上一篇的训练负荷：全作业目标速率为 `1,024 样本/s`，每步全局消费 $4 \times 32 = 128$ 个样本。单样本平均 `256 KiB`（`0.25 MiB`），冷读总载荷为 `256 MiB/s`。

假定共享存储的数据通道能稳定提供 `300 MiB/s`，看似很有余量。但服务端的远端路径查找上限只有 `800 次/s`。下面把这批样本放进两种截然不同的文件布局。

### 布局甲：每样本独立存成一个小文件

每次取样都要打开一个新文件，触发一次远端查找。分别算出数据通道和查找通道允许的样本上限：

$$\text{数据通道上限} = \frac{300\text{ MiB/s}}{0.25\text{ MiB/样本}} = 1{,}200\text{ 样本/s}$$

$$\text{路径查找上限} = 800\text{ 样本/s}$$

两段环节串联服务同一次请求，整体上限被短板锁死在 **800 样本/s**，追不上 `1,024 样本/s` 的目标。换算成全局每步 128 样本的训练节奏：

$$\text{最高步频} = \frac{800\text{ 样本/s}}{128\text{ 样本/步}} = 6.25\text{ 步/s} \implies \text{平均步时下界} = \frac{1}{6.25} = 160\text{ ms}$$

哪怕解码、H2D 与计算全都零耗时，光靠打开小文件就把步时从 `125 ms` 硬生生拖到了 `160 ms` 以上。

### 布局乙：每 128 个样本连续打包成一个 32 MiB 分片

把零散小文件合并为顺序大包（如 WebDataset tar 分片或二进制索引文件）。采样器连续消费一个分片、读完前保持句柄打开，则每个分片只需打开一次：

$$\text{分片打开速率} = \frac{1{,}024\text{ 样本/s}}{128\text{ 样本/分片}} = 8\text{ 次/s}$$

文件打开率骤降 128 倍，彻底绕开了 `800 次/s` 的元数据高墙。冷读有效载荷仍是 `256 MiB/s`，稳稳落在 `300 MiB/s` 的数据通道余量内。

| 文件布局 | 达到目标速率所需操作 | 冷读有效载荷 | 首要卡点 |
| --- | --- | ---: | --- |
| **每样本一个小文件** | 打开 `1,024 个文件/s`（触发 `1,024 次查找/s`） | `256 MiB/s` | `800 次/s` 元数据查找上限 |
| **每分片 128 个样本** | 顺序读完分片时仅打开 `8 个文件/s` | `256 MiB/s` | 数据通道带宽与顺序读取是否成立 |

> [!warning] 常见误区：打包成分片并非一劳永逸
> 分片提速的前提是顺序消费与句柄复用。如果训练代码做全局强随机打散，加载进程在几千个分片之间来回跳跃，句柄一样无法复用。更糟的是，内核顺序预读会拉回大量根本用不上的相邻页，引发严重的**读放大**（后端读回字节远超应用实际消费量）。工程上常用“分片级全局打散 + 分片内局部滑窗打散”兼顾随机性与顺序读。

## 三、页缓存命中究竟省了多少后端流量

引入缓存变量：假设第二轮训练按所需字节计，有 **75%** 命中客户端数据页缓存（无额外预读浪费或失效重读）。后端存储只需补齐未命中的 25%：

$$\text{后端实际载荷} = 256\text{ MiB/s} \times (1 - 75\%) = 64\text{ MiB/s}$$

千万别误以为整条输入链路的开销都打了二五折。拆开三笔细账就能看清边界：
- **目录与属性缓存独立生效**：数据页命中 75%，而 `open` 与属性验证有独立的缓存与失效机制，需单独观测；
- **CPU 解码与 H2D 纹丝不动**：1,024 个样本仍须全部解码，并按 `1 GiB/s` 拷进显存；
- **换节点即清零**：作业重调度到没有热页的新节点时，后端压力立刻弹回 `256 MiB/s` 的冷读基线。

## 四、同一批样本，走过四种典型存储路径

AI 集群常见的存储形态主要有四类。选型和排障的关键，在于看清**接口语义、共享瓶颈以及最有区分力的观测指标**。

| 存储与访问接口 | 请求流经的关键组件 | 典型定位与共享瓶颈 | 有区分力的核心观测 |
| --- | --- | --- | --- |
| **本地 NVMe（本机文件系统）** | 本机内核处理命名与权限，冷读直下本地块设备 | 高速数据预热盘或缓存盘；节点内多卡共享盘、页缓存与 PCIe，换节点需重预热 | 目标块设备的吞吐、请求大小、排队深度与 `r_await` |
| **NFSv4.1 / TCP 共享目录** | 客户端把查找、属性和读写转为 RPC，经网络发往 NFS 服务端 | 多机共享代码、中小数据集或配置；共享网络链路、服务端与后端存储 | `nfsstat -m` 挂载参数、`nfsiostat` 的 `op/s`、`avg RTT`、`avg exe` 与重传 |
| **Lustre 并行文件系统** | 元数据走 MDS/MDT 拿布局，数据直接并发读写多个 OSS/OST | 大规模多机共享高吞吐训练数据与 Checkpoint；元数据与条带目标分头承压 | 元数据操作延迟、`lfs getstripe` 条带分布、热点 OST 负载 |
| **Amazon S3 对象存储** | 应用按对象键发整对象 `GET` 或连续 `Range GET`（HTTP/HTTPS） | 低成本海量数据湖与模型仓库；连接并发、网关出口带宽与限流重试决定供给 | 对象键与 Range 范围、HTTP 状态码（如 `503`）、重试率与有效下载量 |

### 1. 本地 NVMe：零网络开销，但非天然共享

本地 NVMe 省去了存储网络和远端服务，访问延迟最低。不过单机内多张 GPU 仍会共用盘体带宽、主机页缓存与局部 PCIe 链路。同时它不跨机共享，节点替换或弹性扩容后，必须把数据预热耗时算进交付预算。

### 2. NFS：把操作类型与 RTT/执行时间对齐

排查 NFS 时，先用 `nfsstat -m` 核对实际生效的协议版本与挂载选项，再用 `nfsiostat` 按挂载持续采样。注意 `nfsiostat` 首份输出是自挂载以来的累计值，第二份起才是实时速率：

```bash
# 每 1 秒采样一次，连续输出 3 次（跳过第 1 份历史累计，看第 2–3 份实时窗口）
nfsiostat 1 3 /mnt/nfs-dataset
# 典型关注字段解读：
# read:   ops/s    kB/s    kB/op   retrans   avg RTT (ms)   avg exe (ms)
#         620.0  158720   256.0     0 (0%)       1.8            9.4
# 解读：avg RTT (1.8 ms) 代表网络往返+服务端处理；avg exe (9.4 ms) 含客户端本地排队。
# 当 avg exe 远大于 avg RTT 时，重点查客户端并发队列拥堵；两者同升则查网络或服务端。
```

若怀疑小文件打开拖慢速度，单看读写 `kB/s` 远远不够。应结合 `mountstats` 检查 `LOOKUP`、`GETATTR` 与 `OPEN` 等元数据 RPC 的计数和耗时。

### 3. Lustre：元数据服务与数据条带分头看

Lustre 把命名空间与数据存储彻底拆开。**MDS（元数据服务器）** 和 **MDT（元数据目标）** 专门管理目录、权限与文件布局。**OSS（对象存储服务器）** 和 **OST（对象存储目标）** 则存放实际数据块（这里的“对象”是 Lustre 内部存储概念，不同于 S3 HTTP 对象 API）。

客户端冷打开文件时，先问 MDS 拿到条带分布，再直连对应的 OST 读写数据。排查单目标热点倾斜，常用 `lfs getstripe` 查看条带布局：

```bash
# 查看热点分片文件（或大型权重文件）在 Lustre 上的条带布局
lfs getstripe /mnt/lustre/train_shards/shard_0042.tar
# 典型输出关注点：
# lmm_stripe_count:  1       # 仅落在 1 个 OST 上！多机并发读此文件会打爆单目标
# lmm_stripe_size:   1048576 # 单条带大小 1 MiB
#   obdidx  objid   group
#       12  984210  0        # 实际落在编号 12 的 OST 上
```

热点文件若只落在 1 个 OST 上，集群其余几十个 OST 再闲也帮不上忙。若是批量打开小文件变慢，则应紧盯 MDS/MDT 队列，而不是把所有 OST 带宽加起来算账。

### 4. S3 对象存储：对象键取代目录树

S3 没有传统 POSIX 目录锁。客户端直接凭对象键发起整对象 `GET` 或连续字节段的 `Range GET`。把分片打成合适尺寸的对象能摊薄请求开销。若通过第三方挂载工具把对象桶伪装成目录，排查时务必拆清底层翻译逻辑，核对一次 `open/read` 究竟放大成了多少次对象请求。

遇到服务端返回 `503 Slow Down` 时，说明触发了分区限流。此时应结合客户端重试记录、并发连接数与对象键前缀散列一起调优，不能只盯着总带宽发呆。

> [!summary] 核心结论：先画清物理共享点，再下瓶颈判断
> 无论数据放在本地 NVMe、并行存储还是对象库，最后都要回到物理网络平面核对一条铁律。若存储读写与 NCCL 集合通信共用同一张网卡或交换机上行，两者高峰期会正面撞车。若两者物理分网，排查时就必须各看各的端口计数，绝不能混为一谈。

摸清单次存储请求的成本后，下一步自然要问：既然单批读文件加解码避不开耗时，能不能在 GPU 算这一批的同时，让后台进程提前把下一批做好？下一篇我们拆解 DataLoader 并发、预取队列与 H2D 流水线。
