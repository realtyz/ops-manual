# 09 GPU 的数据从哪里来：存储与 I/O

## 范围与读者目标

- **范围**　沿一次分布式训练解释训练数据如何进显存，Checkpoint 如何写出和读回，以及如何定位这两条路径上的等待。存储侧用本地 NVMe、普通 NFS、Lustre 和 Amazon S3 作架构实例。推理的模型冷启动只在恢复一节用一句话对照。存储系统部署与管理、模型训练算法和框架工程留作扩展。
- **必要前置**　读者熟悉 Linux 的文件和挂载，知道主机内存与显存分属不同地址空间，理解 PCIe/DMA、CUDA Stream 的顺序约束，以及 Rank、同步步和集合操作。开篇补齐页缓存、页锁定主机缓冲和每 Rank 一个训练进程三个约定。GDS 一节用一句话回顾 NIC 访问显存所需的 RDMA 条件。算例和教学记录可在没有 GPU 的情况下推导。
- **跨章分工**　单机 PCIe/NUMA 路径与显存容量承接第 02、04 章，RDMA 和 NCCL 承接第 06—08 章。容器挂载与设备注入交给第 10—13 章，作业重试与调度职责交给第 15—16 章，常态指标、跨层故障处置和交付验收交给第 17—19 章。
- **读完应能独立判断**　给定每步样本数和步时，能分别算出样本速率、存储载荷和 H2D 需求。给定数据布局和观测结果，能判断下一步该查元数据、数据吞吐、缓存、CPU 处理还是搬运与同步。给定 Checkpoint 大小、周期、保留策略和完成窗口，能估算容量与读写压力。给定 cuFile 配置和观测，能区分候选路径与实走路径。给定多 Rank 时间线，能判断应优先验证数据供给、通信、计算还是显存容量。

## 贯穿场景与证据口径

- **教学场景**　沿用第 08 章的两节点四 Rank 形状，A 上为 Rank 0、1，B 上为 Rank 2、3，每 Rank 使用一张 GPU。训练采用图像样本、CPU 解码与批处理。每 Rank 每步 32 样本，供给充足时目标步时 125 ms（含该例中的计算和通信），存储中每样本平均 256 KiB，送入 GPU 的张量每样本 1 MiB。假定 Rank 分片互不重叠、每样本读一次、不计索引和协议开销。全作业需 1,024 样本/s，冷读有效载荷 256 MiB/s，合计 H2D 1 GiB/s。每节点分别为 128 MiB/s 和 512 MiB/s。示例分别注明读流量和集合流量共用或分用链路的条件。
- **版本锚点**　框架行为用 PyTorch 2.9 文档及 `v2.9.0` 源码核对。GDS 主例取 CUDA 12.9 系列、GDS 1.14 的 Linux x86_64 单 NVMe 路径，具体 GPU、文件系统、发行版内核和驱动分支按平台条件列出。两个锚点分别约束示例口径。NFS 用普通 NFSv4.1/TCP 作对照。 [PyTorch 2.9 DataLoader](https://docs.pytorch.org/docs/2.9/data.html) · [DGX OS 6 组件版本表](https://docs.nvidia.com/dgx/dgx-os-6-user-guide/dgx-os-6-user-guide.pdf) · [GDS 1.14 发行说明](https://docs.nvidia.com/gpudirect-storage/pdf/release-notes.pdf) · [NFSv4.1 RFC](https://www.rfc-editor.org/rfc/rfc8881.html)
- **记录与配图**　数值均为可复算假设，示例时间线和应用字段标为教学记录。若正文采用实测，随记录提供来源、软硬件、客户端和服务端配置、样本布局、缓存状态、并发和采样窗口。先用 Mermaid 表达流程、用表格表达精确数值。若获批后需要绘制设备边界或物理数据路径，按配图规范提交独立可复制的提示词。

## 01 一批样本怎样到达 GPU

- **问题与预期结论**　数据集能读、GPU 也能算，为什么每步开头仍有空档？读者应能画出一批样本从文件到 GPU Kernel 的依赖链，指出各次等待发生的位置，并按存储载荷、解码后张量和步时分别计算吞吐。
- **解释顺序**　从训练进程请求下一批开始，沿“索引与取样 → 文件打开与读取 → 内核页缓存命中或向下层取数 → worker 的用户态缓冲、解码及整理 → 页锁定主机缓冲 → H2D DMA → 计算 Stream 等待批次可用”跟踪一批。用本地文件的缓冲读取作第一张图，标出缓存未命中时的块设备和远程数据源接入点。对照热读时可省下的后端读，以及 CPU 解码、批整理、H2D 仍要做的工作。说明各 Rank 取不同样本的前提，并用 GPU 消费速率反推各层最低供给需求。CUDA 显存管理和 PCIe 拓扑沿用前置知识。
- **支撑材料**　用一张路径图标出样本字节流、队列和张量形态，再用逐步换算表追踪每 Rank 的 8 MiB 编码数据与 32 MiB H2D 张量如何得到全作业速率。用 Linux 页缓存文档界定普通读的缓存层，用 PyTorch 文档支撑 worker 中执行数据集访问、变换与 `collate_fn`，以及页锁定缓冲出现的位置。 [Linux 页缓存](https://docs.kernel.org/6.18/mm/page_cache.html) · [PyTorch 2.9 数据加载](https://docs.pytorch.org/docs/2.9/data.html)

## 02 数据加载的并发和预取何时能隐藏等待

- **问题与预期结论**　为什么增加 worker 有时能让 GPU 忙起来，有时只让内存占用和尾延迟上涨？读者应能区分文件预读、DataLoader 批次预取和 GPU 拷贝流水线，并判断加 worker、增大队列或调整 H2D 调度各自针对什么约束。
- **解释顺序**　先分开三层预取：内核对文件页的预读、worker 提前生产批次、训练进程提前提交下一批 H2D。比较完全串行与跨批重叠的时间线，区分单批延迟和稳态出批间隔。预取可吸收短抖动，生产长期慢于消费会耗尽队列。接着看 worker 并发何时覆盖读取等待，何时碰到 CPU 核数、解码线程、共享存储、内存和 IPC 限制。最后拆开 `pin_memory=True`、`.to(device, non_blocking=True)` 与真正的拷贝计算重叠。页锁定源缓冲、可并发的拷贝引擎、跨批无依赖及独立 Stream 共同决定能否重叠。以事件保证计算在对应拷贝完成后消费，源缓冲在拷贝完成前保留。NUMA 只在远端缓冲改变搬运路径时带入。
- **支撑材料**　配置对照用 `num_workers=0`（`prefetch_factor=None`）和 `num_workers=4, prefetch_factor=2, pin_memory=True`，每次只改一个变量。后一配置按每 Rank 四个 worker、每 worker 预取两批估算在途规模，四个 Rank 共 16 个 worker，八批 × 32 MiB 约 256 MiB/Rank 的张量预算只覆盖这部分批次，实际驻留另计解码中间态、IPC、页锁定副本和消费中的批次。时序图用假设的读 50 ms、处理 90 ms、H2D 8 ms、计算与通信 125 ms 比较串行的 273 ms 与理想流水线的 125 ms 稳态间隔，注明各阶段可独立重叠、缓冲充足且无共享争用。另以两批已就绪、每 125 ms 消费一批估算 250 ms 的缓冲余量。用 CPU/CUDA 时间线标注 H2D 与 Kernel 实际重叠区间。 [PyTorch 2.9 加载参数](https://docs.pytorch.org/docs/2.9/data.html) · [CUDA 12.9 拷贝与 Kernel 重叠](https://docs.nvidia.com/cuda/archive/12.9.1/cuda-c-programming-guide/index.html#overlap-of-data-transfer-and-kernel-execution) · [PyTorch 页锁定与非阻塞拷贝示例](https://docs.pytorch.org/tutorials/intermediate/pinmem_nonblock.html)

## 03 从文件布局和访问模式判断存储瓶颈

- **问题与预期结论**　顺序读取跑得很快，为什么多个 Rank 读训练集还是慢？读者应能根据请求大小、请求率、并发、缓存和数据位置，区分元数据操作、随机小读、顺序吞吐与共享路径争用，并解释四类存储各适合承担哪段数据供给。
- **解释顺序**　先区分文件名查找、属性和打开，与真正的数据读取。对照每样本一文件、每组样本一个分片的请求形状，说明缓存命中、读放大、随机顺序、文件句柄复用和分片大小如何改变请求率及尾延迟。再用同一负载走四条路径。节点本地 NVMe 经过本机文件系统与块设备，适合预置数据或作缓存，需计入分发、命中和换节点重建。普通 NFSv4.1/TCP 经过客户端挂载与远端服务路径，查询和读请求会随缓存策略改变。Lustre 提供共享文件命名空间，典型冷打开先取元数据和文件布局，客户端按布局向 OSS/OST 读写数据，条带决定一份大文件可动用哪些目标。S3 走键与 HTTP 请求，可整对象读取或 Range GET，需考虑连接并发、请求开销和重试。结尾按访问接口、数据局部性、共享边界与持久角色对照，条带调优、NFS 服务端配置与对象挂载实现留作扩展。
- **支撑材料**　做一张“四种存储路径 × 请求、主要共享点、用途、对应证据”表。Linux NFS 以 `nfsstat -m` 记录挂载，`nfsiostat` 的 `op/s`、`avg RTT`、`avg exe`、`retrans` 分别提供操作率、请求往返、含客户端等待的执行时间和重传线索。Lustre 用 `lfs getstripe <file>` 的条带计数、大小和 OST 布局解释数据分布。S3 客户端记录 `GetObject`/Range、响应码、耗时与重试次数，服务端配额或拥塞需再取相应证据。 [Linux NFS 缓存及挂载选项](https://man7.org/linux/man-pages/man5/nfs.5.html) · [nfsstat 挂载选项](https://man7.org/linux/man-pages/man8/nfsstat.8.html) · [nfsiostat 字段](https://man7.org/linux/man-pages/man8/nfsiostat.8.html) · [Lustre 客户端和服务端架构](https://wiki.lustre.org/Lustre_Architecture_for_Admins) · [Lustre 操作手册 §19.4](https://doc.lustre.org/lustre_manual.pdf) · [S3 GetObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetObject.html) · [S3 性能指引](https://docs.aws.amazon.com/AmazonS3/latest/userguide/optimizing-performance-guidelines.html)
- **可复算对照**　冷读假定每个小文件都需一次受限的远端查找，元数据上限 800 次/s，数据路径上限 300 MiB/s。每个样本 256 KiB 时，数据路径可供 1,200 样本/s，整体先受 800 样本/s 的查找约束，低于目标 1,024。每分片 128 样本即 32 MiB，假定连续消费、每个分片只打开一次、索引开销忽略，目标降为 8 次打开/s，载荷仍需 256 MiB/s。实际 `open`、查找 RPC 和后端 I/O 分开计数。另用 75% 的按字节客户端页缓存命中率说明在无预读放大和重复拉取的简化模型下，后端有效载荷需求约为 64 MiB/s。

## 04 Checkpoint 怎样写出，作业怎样恢复

- **问题与预期结论**　为什么每十分钟写一次的作业仍会在保存时拖慢训练，重启时又使存储拥塞？读者应能从保存窗口、保留代数和并发恢复估算负载，并区分训练可继续、写入完成和恢复可用三个时点。
- **解释顺序**　先列出需要恢复的模型、优化器和训练进度等状态，容量按实际序列化结果计。对照由一个 Rank 汇集后写入与多个 Rank 分片并行写入，指出前者的汇聚和单写端压力，以及后者对慢写入者和共享后端的依赖。用 PyTorch DCP 说明“可一致读取的状态 → 主机 staging（涉及 GPU 状态时含 D2H）→ 序列化与写各分片 → 发布可恢复的元数据”。区分同步保存、异步写和异步 staging，解释旧一轮写入未完成又提交下一轮时，内存、队列和带宽如何累积。说明缓冲写返回、框架保存完成与故障后的持久性分别依赖哪层契约。恢复按“识别完整版本 → 读元数据与所需分片 → 反序列化和装入目标设备 → 所有 Rank 就绪”展开，注明分片布局或恢复并发改变时，实际读取量与慢端可能变化。框架代码只用于对应阶段，重试编排归调度章节。
- **支撑材料**　对照 `FileSystemWriter` 的 `single_file_per_rank`、`sync_files` 与元数据完成阶段，画 GPU、主机缓冲、共享存储三泳道。PyTorch 2.9 的 `async_save` 传统路径和返回异步 staging Future 时的 `AsyncSaveResponse` 分开说明，后者才使用 `staging_completion`、`upload_completion` 两个信号。拟加应用字段 `checkpoint_id`、`rank`、`bytes`、`stage_ms`、`write_ms`、`publish_ms`、`restore_ready_ms`，并将时间线对齐训练步。 [PyTorch 2.9 DCP](https://docs.pytorch.org/docs/2.9/distributed.checkpoint.html) · [2.9.0 保存返回值源码](https://github.com/pytorch/pytorch/blob/v2.9.0/torch/distributed/checkpoint/state_dict_saver.py) · [2.9.0 文件写入与元数据源码](https://github.com/pytorch/pytorch/blob/v2.9.0/torch/distributed/checkpoint/filesystem.py) · [Linux fsync 语义](https://man7.org/linux/man-pages/man2/fsync.2.html)
- **可复算对照**　假定每份有效载荷 64 GiB，四个等量分片各 16 GiB。每 600 s 保存一次，平均约 0.107 GiB/s，但若要求 20 s 写完载荷，合计需至少 3.2 GiB/s，三个作业同窗需 9.6 GiB/s。若始终保留三份已完成版本，新一份完整后才淘汰旧版本，逻辑容量峰值至少 256 GiB，另计文件系统开销与后端副本。恢复假设四个 Rank 合计有效读取 64 GiB，实得 2 GiB/s，则读取下限为 32 s，反序列化、H2D 等阶段的额外用时取决于能否重叠。并列画出后台写与训练读共享存储或链路时的相交窗口。

## 05 GPUDirect Storage 改变哪段数据路径

- **问题与预期结论**　应用调用 cuFile，文件数据是否实际直达显存，省下的时间能否传到训练步？读者应能区分普通缓冲读加 H2D、GDS 直达和 POSIX 兼容路径，并在应用、文件、平台与运行记录中找到判断依据。
- **解释顺序**　以同节点 NVMe 上供 GPU 消费的预处理记录作对照，先复用普通的“存储 → 主机内存 → 显存”，再画“应用在 CPU 提交 cuFile I/O，受支持的 NVMe DMA 把载荷送入 GPU 缓冲”。远程只补充受支持的文件系统客户端、存储网络和 RDMA NIC 参与时的候选路径。区分 GDS 的文件 I/O 与 GPU Rank 间的 GPUDirect RDMA。顺着 `cuFileHandleRegister`、文件偏移与长度、GPU 缓冲地址检查直达条件，说明 GPU/驱动、内核和文件系统/挂载、PCIe 拓扑、缓冲及对齐都可改变路径。CPU 解码主例继续用主机路径，GDS 对照选可直接在 GPU 消费或处理的数据。补充不满足条件时可能经 GPU 内部缓冲、经主机兼容路径或报错，取决于具体条件和配置。
- **版本核对**　CUDA 12.2 / GDS 1.7 起接受未用 `O_DIRECT` 打开的文件描述符，有可用直达路径时仍可直达，其余此类请求可经兼容路径与页缓存。`O_DIRECT` 影响页缓存及 I/O 条件，单独设置该标志无法确定 DMA 目标。CUDA 12.8 起，特定 Linux x86_64 NVMe 配置可走上游 PCI P2PDMA，无需 `nvidia-fs` 和定制 NVMe 驱动补丁。拟以 GDS 1.14、H100、单盘 XFS、OpenRM R570 和 Ubuntu 22.04 的 6.2 或以上内核作为条件示例，另查 PCI P2PDMA 内核能力、驱动开关和 GPU–NVMe PCIe 拓扑。发行说明同时列出 RHEL 9.4 的 5.14 内核分支，借此说明发行版回移植对版本判断的影响。其他文件系统、远程挂载和 RAID 的支持矩阵留作查表项。 [GDS O_DIRECT 条件](https://docs.nvidia.com/gpudirect-storage/o-direct-guide/index.html) · [GDS 架构与 NVMe P2PDMA](https://docs.nvidia.com/gpudirect-storage/overview-guide/index.html) · [GDS 1.14 发行说明](https://docs.nvidia.com/gpudirect-storage/pdf/release-notes.pdf)
- **支撑材料**　拟用三路示意标出 CPU 控制路径、DMA 发起设备和实际缓冲位置。配置片段取 `properties.allow_compat_mode`、`profile.cufile_stats`，以及 NVMe 的 `properties.use_pci_p2pdma` 和 `block.nvme.use_pci_p2pdma`，配 `findmnt -T`、`lspci -t` 与 `gdscheck -p` 核对挂载和能力。记录活动进程 `gds_stats -p <pid> -l 3` 中每 GPU 的 `n`、`posix`、`unalign`、`MiB`，以目标版本实际字段为准。用 `cufile.log` 的 `cufile IO mode: POSIX` 作兼容路径证据（该字段需 TRACE，单独采集）。判定 NVMe P2PDMA 时，将请求统计与后端选择记录及文件条件对应。若统计无法区分两个直接后端，用仅启用 PCI P2PDMA 的隔离环境再对照，`nvidia-fs` 计数只覆盖该驱动路径。在同文件、同偏移、同请求大小和并发下，拟用已启用的 P2PDMA 与 `CUFILE_FORCE_COMPAT_MODE=true` 做对照，记录各自缓存状态、实际路径、I/O 耗时、CPU 成本与批次可用时刻。单独用热页缓存普通读作基线，评估差异能否影响训练步。 [GDS 配置与基准](https://docs.nvidia.com/gpudirect-storage/configuration-guide/index.html) · [NVMe P2PDMA 配置](https://docs.nvidia.com/deploy/gds-support-for-nvme/setting-cufilejson-configuration.html) · [GDS 诊断与统计](https://docs.nvidia.com/gpudirect-storage/troubleshooting-guide/)

## 06 用多 Rank 时间线缩小瓶颈范围

- **问题与预期结论**　GPU 利用率偏低，某些 Rank 的 NCCL 时间变长，应从哪层验证？读者应能定位第一个晚到的阶段，解释慢 Rank 如何把输入等待传给其他 Rank，并为存储、CPU/H2D、通信、计算或显存问题各选一项有区分力的证据。
- **解释顺序**　先用 `host / rank / step / op_seq` 对齐批次就绪、H2D 完成、Kernel、集合提交与完成、Checkpoint 阶段。记录跨机时钟偏差，同步点和集合序号用来交叉验证顺序。做三组教学判读。① 一个 Rank 先在取批处延迟，其他 Rank 先进入同一集合而等得更久。先分出读取、解码、队列和 H2D，再对照挂载请求、块设备统计和 worker CPU 时间。② 各 Rank 的输入和前置计算如期完成，同一集合实际运行时间仍延长。查看对应通信路径、NIC 负载和集合基线，Checkpoint 同窗时额外核对共享链路的实际流量。③ GPU 持续有计算 Kernel 而步时仍偏长，比较相同形状下的 Kernel 耗时。若伴随分配失败、框架重算或显式 offload，另查分配器与 D2H/H2D 时间线，区分显存容量约束、算子执行耗时和输入等待。运维章节再展开常态基线与系统级故障。
- **支撑材料**　用应用自定义标记 `next_batch_wait_ms`、`read_ms`、`decode_ms`、`h2d_done`、`collective_start/end` 和 Checkpoint 时间窗，配合 PyTorch Profiler 的 CPU/CUDA 活动与显存事件。块设备用 `iostat -x -y 1` 的吞吐、`r_await`、`aqu-sz`，看同窗口的排队和时延。对并行 NVMe 的 `%util` 结合时延、队列和实际吞吐解读。共享存储按第 03 节的客户端字段观测，队列与读延迟都平稳时进一步检查 worker CPU、CPU 限额或拷贝依赖。CPU/CUDA 记录与 NCCL 日志各自标明观测的是主机提交还是设备完成。 [PyTorch 2.9 Profiler](https://docs.pytorch.org/docs/2.9/profiler.html) · [Linux 块设备统计](https://docs.kernel.org/6.18/admin-guide/iostats.html) · [iostat 字段](https://man7.org/linux/man-pages/man1/iostat.1.html) · [Linux cgroup v2 CPU 控制](https://docs.kernel.org/6.18/admin-guide/cgroup-v2.html#cpu)
- **对照顺序**　先把同一批数据复制到本地，保留读取接口、解码和 H2D，并记录两侧冷热缓存。再用主机内存预生成同形状同 dtype 的批次保留 H2D，跳过读取与解码。必要时用设备端同形状输入隔离 H2D。配一张双 Rank 时序图，用教学事件展示同一集合中早到的 Rank 在 70 ms 进入、晚到的 Rank 在 110 ms 进入、两者在 115 ms 完成。早到 Rank 观察到的 45 ms 中有 40 ms 发生在后者到达前，再回查后者的取批时间。各轮固定 Rank 布局、批次形状、计算与集合配置、CPU 配额和并发；保持或单独标记 Checkpoint 窗口。结果用首个变化的阶段和全作业步时共同解释。若同时绕过多层，下一轮拆出单一变量再归因。

## 待审取舍与待核实项

- **存储实例的篇幅**　建议以普通 NFS 和 Lustre 讲透远程文件路径的共享点，用 S3 对照访问接口与请求形状。审查时请决定是否需要为“对象存储 → 节点预置 → 本地 NVMe”单独增加一个流转算例。
- **GDS 的深度**　建议只深入单 NVMe 的路径和验证步骤，远程 GDS 留作条件对照。审查时请决定是否要选定一种并行文件系统，补充其具体客户端版本、挂载和 RDMA 支持矩阵。
- **待环境核实**　目前采用官方资料、教学记录和算例。具体文件及对齐组合走哪条 GDS 路径、该版本统计字段和基准工具选项、不同缓存状态与并发下的收益，需在同一目标环境采样后确定。若采用实测，还需核实 Checkpoint 写入端的持久性约定、集群背景流量和跨机时间线误差。
