# 第 14 章 GPU 共享、切分与隔离｜内容大纲

## 本章定位与前置知识

前文第 02 章建立了 GPU 计算、显存层次与 LLM 推理双阶段（Prefill 计算受限、Decode 显存带宽受限）的底层模型，第 10—12 章打通了设备进入容器与 Kubernetes 的完整链路，第 13 章则对比了高速网络的共享 HCA 与独占 VF。

本章聚焦**面向在线推理服务 SLO 的 GPU 资源池设计**。当单卡算力与显存远超单个 7B/14B 推理服务或开发实例的实际需求时，平台如何把一张 GPU 安全地拆给多个工作负载？不同共享与切分机制在显存硬隔离、算力与 HBM 带宽干扰、P99 尾延迟、卡内碎片和运维灵活性上如何取舍？

本章不再重复展开 SM、NVML、NCCL、Device Plugin、GFD、DRA 与 DCGM 等前序章节基础概念，而是首次系统定义 **TTFT / TPOT（ITL） / SLO** 推理评判标尺，以及 **Time-Slicing、CUDA MPS、MIG、HAMi** 四类主流 GPU 共享与切分方案。

## 核心学习目标

1. **建立在线推理隔离标尺**：结合显存长驻与 KV Cache 突发增长特征，说明共享访问为何会引发 OOM 连坐与 TTFT/TPOT 尾延迟抖动，并从五个工程维度系统评估隔离强度。
2. **区分软件共享与硬件切分的机制边界**：对比 Time-Slicing、CUDA MPS、MIG（GI/CI）与 HAMi-core 的底层隔离能力、故障传播域与放置碎片规律，能够手算显存驻留缺口与 MIG 合法放置窗口。
3. **打通 Kubernetes 与 HAMi 的资源账本**：跟踪 `nvidia.com/gpu`、时分共享副本、MIG `single/mixed` 策略、HAMi 逐卡三维配额与 Flexible MIG 按需预留的调度、准入及注入过程。
4. **落地变更归因与资源池选型**：完整推演一次 MIG 布局重配置到 Node 库存收敛的验收路径，按实例生命周期准确归因监控指标，并为在线推理、开发测试与多卡并行负载选定资源池并设计并跑验收方案。

## 本章贯穿场景说明

本章开篇使用一张 `16 GiB` 可用显存的单卡模型建立直觉，直观呈现“设备可访问”与“显存装得下”的本质差异。

进入具体型号与 Kubernetes 集群交付后，全章以一台双卡 A100-SXM4-40GB 节点（`node-1`，挂载 `GPU 0` 与 `GPU 1`）承载混合推理与研发资源池，并配以独立的同型 HAMi 资源池演示逐卡软件限额与按需 MIG 切分。

全书统一的参考软件版本栈（`Kubernetes v1.36`、`GPU Operator v26.7.2`、`Device Plugin v0.20.1`、`HAMi v2.11.0`、`OpenRM R595`、`CUDA 13.2.1`）与单位口径见 [00_全书基线与术语速查.md](../00_全书基线与术语速查.md)。
