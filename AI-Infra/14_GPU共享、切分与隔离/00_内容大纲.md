# 14 GPU 共享、切分与隔离

## 范围、前置知识与读者目标

- **范围**　以 Linux 裸机上的 NVIDIA GPU 为主，从一个设备怎样给多个任务使用讲起。先区分访问、显存、算力和隔离，再按整卡独占、软件共享、硬件切分理解典型机制。随后把 Time-Slicing、MPS、MIG 和 HAMi 映射到 Kubernetes 请求、设备交付和观测，最后按负载需求选资源池。
- **必要前置**　知道 GPU 上有计算单元和显存，知道应用通过 CUDA 执行。本章在用到时解释 SM、CUDA context 和 Kernel。看第三部分时需要能读简单的 Pod 和 Node，正文会在第一个请求案例中补足 scheduler 与 kubelet 的分工。
- **读完应能独立解释**　给定一种方案，能说清多个任务是在轮流执行、并发使用同一设备，还是各自获得一块硬件分区。能指出显存容量和算力限制由谁执行，以及应用内错误、整卡故障和租户安全分别需要看什么边界。
- **读完应能独立判断**　给定 Pod 请求、节点库存和应用需求，能算出资源够不够、问题发生在哪一步。能分辨容量短缺和布局碎片，核对重配置后的设备与监控归因，并为不同负载选择资源池及验收材料。
- **跨章分工**　第 10–13 章展开容器注入、设备分配、Operator 和 RDMA。本章补足案例所需的步骤。跨 Pod 队列与多节点放置交给第 15–16 章，完整观测与故障诊断交给第 17–18 章，生产发布与回滚交给第 19 章。虚拟机接入用直通和 NVIDIA vGPU 标明范围。HAMi 以 NVIDIA 后端为例，其他加速器查支持矩阵，HAMi-DRA、远程 GPU 和完整部署留给专题。

## 第一部分　基本概念与技术分类

### 01 一张 GPU 能怎样给两个任务用

- **问题与预期结论**　任务 A 的 GPU 活动时高时低，任务 B 能否利用同一张卡？读者应能先问两个任务能否访问这张卡、同时驻留需要多少显存、计算怎样执行，以及它们能否承受互相干扰。
- **解释顺序**　从无 Kubernetes 的单卡场景开始。先把物理 GPU、两个任务和访问权画出来。卡内只标负责运算的 SM 与存放数据的显存。用两次短计算中间的等待期说明，程序暂时没有发起 GPU 计算时，数据仍可能占着显存。CUDA context 随第 05 节的并发案例引入。让 A 独占时先看 B 有无访问机会，再让二者共享时检查显存峰值是否重叠、计算是否竞争。最后区分显存容量上限、算力可用范围、性能干扰、故障影响和租户安全五项，给每项一个可核对的问题。租户安全同时涉及主机、设备访问权限和信任关系。具体错误码留给第 07 节及第 18 章。
- **支撑材料**　拟用一张双任务示意图标明物理边界和访问关系，用教学数字复算显存峰值。假定 A 用 12 GiB、B 用 8 GiB，若峰值重叠，驻留需求合计 20 GiB。容量为 16 GiB 的假想设备可分别运行二者，同时驻留需另想办法。图注说明时序和容量为假设。测试材料分别给显存峰值、吞吐或尾延迟、应用错误及设备状态，说明每类观测回答哪个问题。 [NVIDIA CUDA MPS 架构中的 CUDA context 与执行模型](https://docs.nvidia.com/deploy/mps/595/architecture.html) · [NVIDIA MIG 对 SM、显存和隔离的定义](https://docs.nvidia.com/datacenter/tesla/mig-user-guide/620/concepts.html#terminology)

### 02 GPU 虚拟化技术按什么分类

- **问题与预期结论**　Time-Slicing、MPS、MIG、HAMi 都会出现在 GPU 共享方案里，它们各自改变了什么？读者应能按照执行和资源边界理解分类，并知道为什么一个平台可以同时提供不同的实现。
- **解释顺序**　沿上一节同一张 GPU、两个任务，从三个问题展开。第一，是否把整张设备交给一个任务。第二，若同卡共享，工作是在时间上交错、允许部分并发、还是受软件限额约束。第三，是否划出带独立资源的硬件实例。先说明整卡独占是参照，再看软件共享的三种实现和 MIG 硬件切分。MIG 实例上还可配置 Time-Slicing，届时隔离边界需要同时看实例之间和实例内部。HAMi 是中间件，HAMi-core 和 Flexible MIG 落在两个不同分支。末尾用一小段说明虚拟机接入的维度。整卡直通可把物理 GPU 给一个 VM，NVIDIA vGPU 可采用时分和基于 MIG 的模式。虚拟机方案的实际部署留给专题。 [NVIDIA GPU Operator Time-Slicing](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/26.7/gpu-sharing.html) · [NVIDIA MPS 架构](https://docs.nvidia.com/deploy/mps/595/architecture.html) · [NVIDIA 整卡直通](https://docs.nvidia.com/vgpu/latest/grid-vgpu-user-guide/using-gpu-pass-through.html) · [NVIDIA vGPU 模式](https://docs.nvidia.com/ai-enterprise/release-7/latest/infra-software/vgpu/overview.html)

## 第二部分　分类型理解工作机制

### 03 整卡独占时，空闲的卡还能给谁

- **问题与预期结论**　GPU 已交给 A，A 现在没有 Kernel 在跑，B 能否获得这张卡？读者应能说明整卡分配由任务生命周期决定，并区分分给一个容器的设备、容器按需占用的显存，以及宿主机自身的访问权限。
- **解释顺序**　用一卡两任务画出 A 取得整卡、A 等待数据、A 退出后设备可再分配三个时点。先读分配归属，再读利用率和显存占用。访问范围会随设备授权和宿主机特权改变，整机故障也会影响同机作业。Kubernetes 的整数计数和 UUID 证据在第 08 节展开。
- **支撑材料**　拟用三帧教学卡片标明物理卡、当前持有者和 GPU 是否活动。后两帧都可显示很低的利用率，只有 A 退出且设备回收后才有新的整卡分配机会。用 Kubernetes Device Plugin 的独占设备分配规则支撑后面的 Pod 示例。 [Kubernetes v1.36 Device Plugins](https://v1-36.docs.kubernetes.io/docs/concepts/extend-kubernetes/compute-storage-net/device-plugins/)

### 04 Time-Slicing 怎样让任务轮流使用一张卡

- **问题与预期结论**　如果 A、B 都能用同一张卡，为什么两个访问名额无法换算成两份固定性能？读者应能解释执行交错、显存持续占用，以及增加进程数后会发生什么。
- **解释顺序**　先画 A、B 的执行时序和仍驻留的显存，再从一个 Pod 跑一个进程扩展到一个 Pod 跑多个进程。区分进程活动、执行机会和端到端延迟。共享访问限额由平台配置，活跃进程数、负载与同时驻留显存会改变实际结果。区分普通进程退出、应用显存分配失败和影响同一卡的 GPU 级错误。第 08 节给副本、资源名和节点分配事件，第 18 章展开硬件异常归因。
- **支撑材料**　拟用对齐的两条时间轴显示「交错执行」和「各自仍占显存」。假定两个落到同卡的进程分别需要 22 GiB 同时驻留，合计 44 GiB，超过教学 A100 40GB 的容量。设备访问已经授予时，应用仍可能分配失败。时序图只表达先后与重叠状态，时延与吞吐用同一负载在单跑和并跑下验证。 [GPU Operator v26.7 Time-Slicing 的资源单位与隔离边界](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/26.7/gpu-sharing.html)

### 05 MPS 怎样让小任务并发执行

- **问题与预期结论**　单个进程的 Kernel 填不满 GPU 时，两个进程是否能同时推进？读者应能说明 MPS 提供的并发机会，分辨线程或显存上限与专有计算单元、吞吐下限。
- **解释顺序**　从两个小 Kernel 的执行图进入 A100 上的 CUDA MPS。解释 control daemon、server 和客户端 context 如何配合，交代 Volta 及后续架构的客户端地址空间与提交路径。资源充足时，客户端 Kernel 可重叠。再讲主动线程比例、pinned device memory limit，以及不同客户端何时仍会用到同一 SM。最后用 server 的 `FAULT` 状态说明致命 GPU 故障可能影响哪些客户端。Kubernetes 插件支持条件放到本节末的进阶材料，CUDA MPS 的其他分区接口交给专题。
- **支撑材料**　先用两个小 Kernel 的并发示意解释机会，再并排展示上游 `sharing.mps.resources[]` 与 `replicas: 4` 的配置片段、MPS daemon 的默认线程比例与显存限制查询接口，例如 `get_default_active_thread_percentage` 和 `get_default_device_pinned_mem_limit`。设计一张卡的教学算例：对四个预期客户端采取均等上限，线程比例配置取 `100% ÷ 4 = 25%`，显存上限以设备总量的四分之一为计算口径。核对实际 daemon 设置时，另查单位及舍入，GPU 实际可用粒度和应用吞吐分别验证。拟用官方 `FAULT` / `CUDA_ERROR_MPS_SERVER_NOT_READY` 场景说明恢复条件，用同一负载单跑与并跑的吞吐、尾延迟和显存峰值作为性能证据。若无实测，用测试表列清变量与需要记录的结果。 [NVIDIA MPS R595 架构](https://docs.nvidia.com/deploy/mps/595/architecture.html) · [NVIDIA MPS R595 资源上限与故障](https://docs.nvidia.com/deploy/mps/595/when-to-use-mps.html) · [NVIDIA MPS R595 工具接口](https://docs.nvidia.com/deploy/mps/595/appendix-tools-and-interface-reference.html) · [插件 v0.20.1 MPS 配置](https://github.com/NVIDIA/k8s-device-plugin/blob/v0.20.1/README.md#with-cuda-mps)
- **进阶材料与版本边界**　v0.20.1 Device Plugin 的 MPS 共享仍属实验功能，适用于整卡 `nvidia.com/gpu`。CUDA MPS 本身支持在 MIG 上运行，客户端数量限制随 CI 大小缩减。两种支持范围分别引用对应文档。 [插件 v0.20.1 MPS 限制](https://github.com/NVIDIA/k8s-device-plugin/blob/v0.20.1/README.md#with-cuda-mps) · [MIG 620 应用限制](https://docs.nvidia.com/datacenter/tesla/mig-user-guide/620/deployment-considerations.html#application-considerations)

### 06 HAMi-core 怎样约束同卡任务的显存和算力

- **问题与预期结论**　A 和 B 想共享一张卡，同时分别给出所需显存和算力预算，平台如何执行？读者应能说明调度器记录的份额、HAMi-core 的运行时限额和实际性能是三类证据。
- **解释顺序**　先用 A、B 的预算解释 HAMi-core 的位置，再看容器里的 `libvgpu.so` 怎么在支持的 CUDA 调用路径检查显存分配、怎么节流 Kernel 提交。以同一个请求为例，先看没有同卡竞争时的默认行为，再加同级或更高优先级任务，最后对照强制节流和关闭节流的模式。缓存、带宽和 GPU 级故障仍需按同卡边界评估，部署时还要验证库是否生效以及应用调用是否受支持。完整 Kubernetes 交付与指标归因放在第 09 节，其他加速器按各后端支持矩阵查证。
- **支撑材料**　拟让 A 请求 12 GiB 与 30% 算力，B 请求 8 GiB 与 40%。在卡上只运行 A 和 B 时，两者的调度预算合计 20 GiB、70%。再加入一个与 B 相同的任务，显存合计 28 GiB、算力 110%。假定这一张卡是唯一候选、名额足够且显存和算力预算未超配，第三个请求被算力条件挡住。用这组三个请求区分逐卡调度过滤和程序运行后遇到的显存限额。用官方同卡节流说明和一对带或不带邻居的探针计划解释为什么申请 30% 需要结合实际策略阅读。 [HAMi 逐卡资源与共享](https://project-hami.io/docs/key-features/device-sharing) · [HAMi-core 限额机制与策略](https://project-hami.io/docs/key-features/device-resource-isolation) · [HAMi 支持矩阵](https://project-hami.io/docs/userguide/device-supported)

### 07 MIG 怎样把一张卡切成硬件实例

- **问题与预期结论**　两个任务各自获得一个 MIG 实例时，哪些资源彼此独立？读者应能画出物理 GPU、GPU Instance（GI）和 Compute Instance（CI）的关系，说明什么是 Profile，并判断同一 GI 内再切 CI 时有哪些资源继续共用。
- **解释顺序**　先画一个物理卡切两个 GI，每个 GI 有自己的计算资源、显存及相应内存路径。再把一个 GI 分成两个 CI，让读者看见父 GI 内共享的显存和引擎。用一 GI 一 CI 解释常见 Profile 名，跨多个 CI 的命名作为补充。实例间内存路径和故障边界讲清后，再比较同为 20 GB 级却有不同 SM 数的两种 A100 Profile。下一步从 Profile 规格过渡到合法位置和碎片。实例是预先配置还是按需创建可在此先认识，Flexible MIG 如何选位置、创建及回收放在第 09 节，模式变更放在第 10 节。
- **支撑材料**　拟在 GI/CI 解释后用一张同尺度示意对照两个 GI 的独立内存路径和同一 GI 内两个 CI 的共享边界。按项目配图规范在写正文阶段补可独立复制的提示词。用 A100 40GB Profile 表对照 `3g.20gb` 和 `4g.20gb`，两者都占 `4/8` 显存 slice、SM slice 分别为 `3/7` 与 `4/7`。结合 `1c.3g.20gb` 辨认哪一层的计算粒度变了。 [NVIDIA MIG 620 概念与 Profile](https://docs.nvidia.com/datacenter/tesla/mig-user-guide/620/concepts.html) · [A100 Profile 表](https://docs.nvidia.com/datacenter/tesla/mig-user-guide/620/supported-mig-profiles.html#a100-mig-profiles) · [MIG 设备命名](https://docs.nvidia.com/datacenter/tesla/mig-user-guide/610/mig-device-names.html)
- **进阶材料**　用八格位置图解释显存和 SM 之外的几何约束。按 `nvidia-smi mig -lgipp`，`3g.20gb` 的位置为 `{0,4}:4`。当两份 `1g.5gb` 分别占位置 0、4 时，剩余 6 个位置与 5 个 SM slice，但两个合法窗口均被占一格。小实例集中到 0、1 后，窗口 4–7 可用。用 `-lgi` 的 `Profile ID`、`Instance ID`、`Placement Start:Size` 验证布局，并用 A100 的 Xid 94 与 95 对照说明可局限到应用的错误和需要排空同卡其他实例的设备级错误。 [NVIDIA MIG 620 合法位置与创建样例](https://docs.nvidia.com/datacenter/tesla/mig-user-guide/620/getting-started-with-mig.html) · [NVIDIA A100 的 Xid 94/95](https://docs.nvidia.com/deploy/gpu-debug-guidelines/620/gpu-node-triage.html)

## 第三部分　从机制走到 Kubernetes

### 08 同一个 GPU 请求怎样变成具体设备

- **问题与预期结论**　看见 Pod 请求一份 GPU 资源，怎样知道它拿到整卡、一个共享访问名额还是一份 MIG 实例？读者应能用资源名、配置和 Node 快照判断能否放置，再用分配记录和容器输出验证拿到了什么。
- **解释顺序**　先走最简单的整卡链路。`limits` 请求数量，scheduler 找库存够的节点，kubelet 与 Device Plugin 分配具体设备，最后由容器枚举确认。用两张健康卡和一个已分配 Pod 算 `Allocatable=2`、剩余可调度量 `2 − 1 = 1`。再只改变一件事：给整卡配 Time-Slicing，比较访问名额和资源名。最后加入预建 MIG，先读物理 MIG mode 和布局，再读 `migStrategy` 的 `none`、`single`、`mixed`。在 `mixed` 的特定 Profile 上加共享副本时，用第 02 节的实例内外边界判断。GFD 标签用于筛节点，资源名和数量用于判断库存，节点端分配出的 ID 用于确认交付。
- **支撑材料**　用整卡 Pod 的 `limits`、Node 状态、PodResources 的 `resource_name/device_ids` 与 `nvidia-smi -L` 贯穿第一轮。Time-Slicing 再给 `sharing.timeSlicing.resources`、`replicas: 4`、`renameByDefault: true` 和 `failRequestsGreaterThanOne: true`，对照两张卡上报八个名额。比较资源不足产生的 `FailedScheduling` 与有库存、节点端请求数量被拒的 `UnexpectedAdmissionError`，给官方 `Allocate failed` 事件。说明 `spec.devicePlugin.config.name/default` 和 `nvidia.com/device-plugin.config` 如何选中配置，并依据 v26.7 文档核对 ConfigMap 更新后的插件重启与资源重新上报。MIG 用下表与 `spec.mig.strategy` 核对资源名。若两份 `3g.20gb` 已被一个 Pod 占一份，再来的单容器 Pod 请求两份时，余量为 `2 − 1 = 1`，查 `PodScheduled` 和 `Insufficient nvidia.com/mig-3g.20gb`。 [Kubernetes v1.36 GPU 请求](https://v1-36.docs.kubernetes.io/docs/tasks/manage-gpus/scheduling-gpus/#using-device-plugins) · [Kubernetes v1.36 PodResources](https://v1-36.docs.kubernetes.io/docs/concepts/extend-kubernetes/compute-storage-net/device-plugins/#monitoring-device-plugin-resources) · [Device Plugin v0.20.1 共享配置与事件](https://github.com/NVIDIA/k8s-device-plugin/blob/v0.20.1/README.md#with-cuda-time-slicing) · [GPU Operator v26.7 配置生效](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/26.7/gpu-sharing.html#updating-a-time-slicing-config-map) · [GPU Operator v26.7 MIG 策略](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/26.7/gpu-operator-mig.html#enabling-mig-during-installation)

### 09 HAMi 怎样把逐卡预算变成设备分配

- **问题与预期结论**　Pod 写了显存和算力请求，谁替它选卡，谁执行限额？如果设备池改用 Flexible MIG，显存请求又如何对应到硬件实例？读者应能从配置和记录找出这两条路径的对应环节。
- **解释顺序**　把第 06 节的 A、B 改写成 Pod 请求。先看 webhook 在满足条件时设置 `spec.schedulerName`，再看 HAMi 调度路径如何读取逐卡预算、选择 GPU 并写注解。kubelet 调用 HAMi Device Plugin 的 `Allocate`，由插件按记录交付设备。HAMi-core 模式下插件注入预加载配置和软件限额，再用 `devices.nvidia.gpuCorePolicy` 的 `default`、`force` 和 `disable` 对照运行条件。Flexible MIG 模式下，由调度路径预留具体 GPU、Profile 与位置，插件创建并交付 GI/CI，Pod 结束后回收实例。用第 07 节的几何算例解释为什么有时找不到可用位置。 [HAMi v2.11.0 架构](https://project-hami.io/docs/core-concepts/architecture) · [HAMi-core 限额机制与策略](https://project-hami.io/docs/key-features/device-resource-isolation) · [HAMi v2.11.0 Flexible MIG](https://project-hami.io/docs/userguide/nvidia-device/dynamic-mig-support)
- **支撑材料（配置与算例）**　三项完整资源名用 `nvidia.com/gpu`、`nvidia.com/gpumem`、`nvidia.com/gpucores`。在 `memoryFactor` 与两项 scaling 均为 1 时，每单位显存为 1 MiB，分别将 A、B 的预算填为 12288 MiB/30% 和 8192 MiB/40%，复算第三个请求达到 28672 MiB、110%。Flexible MIG 例沿用 A 的 12288 MiB 显存需求，读 `operatingmode: mig`、`nvidia.com/vgpu-mode: "mig"`、`migProfileAllowlist`，用 NVML 的可用容量与合法位置判断 `2g.10gb` 或 `3g.20gb` 哪个可选。算力按候选硬件 Profile 核对。 [HAMi 显存单位](https://project-hami.io/docs/userguide/nvidia-device/specify-device-memory-usage) · [HAMi 算力单位](https://project-hami.io/docs/userguide/nvidia-device/specify-device-core-usage) · [HAMi v2.11.0 Helm values](https://raw.githubusercontent.com/Project-HAMi/HAMi/v2.11.0/charts/hami/values.yaml)

- **进阶材料与部署边界**　以 `hami.io/vgpu-mig-allocations` 中的 `gpuUUID`、`profile`、`placement` 和 `migUUID` 验证预留与实际交付。默认资源名 `nvidia.com/gpu` 由目标节点上的对应插件注册。若 GPU Operator 继续管理驱动和 Toolkit，核对目标节点上插件归属和容器注入路径。Flexible MIG 目标卡同时需要明确 MIG 实例操作的管理者，首次打开 MIG 模式时还要考虑排空与复位。Volcano 集成、跨 Pod 拓扑与队列留给第 15–16 章。 [HAMi Flexible MIG 前置条件](https://project-hami.io/docs/userguide/nvidia-device/dynamic-mig-support#prerequisites) · [HAMi 安装前提与 GPU Operator 配合](https://project-hami.io/docs/installation/prerequisites) · [HAMi 插件共存说明](https://project-hami.io/docs/faq)

### 11 怎样用工作负载需求选择资源池

- **问题与预期结论**　“集群还有空闲显存”为什么不能直接回答 Pod 能否运行或满足时延目标？读者应能据工作负载的峰值、通信、隔离及观测需求，提出池化方案、排除候选项，并给出上生产前要收集的证据。
- **解释顺序**　先读单设备峰值显存（含工作区及余量）、计算并发特征和通信要求，再读延迟/吞吐目标、故障影响范围和租户信任模型。先识别需要整卡容量或既有多卡通信路径的任务。对可信团队的间歇任务评估 Time-Slicing，对小 Kernel 负载用并发实测评估 MPS，对需要细粒度显存预算的可信 CUDA 任务评估 HAMi-core。需要独立显存分区和较可预测性能时评估 MIG。若使用 HAMi 的调度方式又需要硬件分区，则按 Flexible MIG 的硬件 Profile 和位置约束评审。每项只给出由前提支持的选择。对安全要求高的租户同时核对设备访问权限、主机及控制面边界。再看对严格时延，以并发负载下吞吐、P95/P99、OOM 和错误记录验证，Profile、访问名额和算力预算各自只提供相应的资源信息。
- **支撑材料**　拟给四行资源池评审。可信开发任务以峰值错开和可容忍排队为前提，比较 Time-Slicing 和整卡的并发结果。小 Kernel 批任务以同设备并发吞吐与尾延迟为证据，评估实验性的 MPS。单设备需要 12 GiB 的推理任务，假定当前池只供应 `2g.10gb` 和 `3g.20gb` 两种 Profile，用两个空闲 `2g.10gb`（名义合计 20 GB）与零个空闲 `3g.20gb` 解释库存规格短缺，候选大实例再用实际可分配显存与时延验收。另用可信团队的两种推理服务对照第 06、09 节的 HAMi-core 限额、逐卡过滤与 Flexible MIG 的硬件实例，按 OOM、尾延迟和同卡故障影响判断是否满足各自约束。讨论“保留一些大 Profile 还是切满小实例”对可服务请求的影响，并与第 07 节的同卡放置碎片对照。作业排队与自动放置策略交给第 15–16 章。 [NVIDIA A100 Profile 数据](https://docs.nvidia.com/datacenter/tesla/mig-user-guide/620/supported-mig-profiles.html) · [NVIDIA MPS 适用负载](https://docs.nvidia.com/deploy/mps/595/when-to-use-mps.html) · [HAMi v2.11.0 运行时限额](https://project-hami.io/docs/key-features/device-resource-isolation) · [NVIDIA MIG 设备访问能力](https://docs.nvidia.com/datacenter/tesla/mig-user-guide/620/device-nodes-and-capabilities.html)
- **多卡边界**　拟加一个短例，给定每 Rank 的设备 ID、GPU/NIC 拓扑和 NCCL/CUDA driver 版本，说明为什么要独立验证通信路径。NCCL 自 2.31 起实验性支持 MIG，要求每个 Rank 使用不同的 MIG 实例、CUDA driver version ≥ 13.0 并关闭 MNNVL。P2P 与 GPUDirect RDMA 各自有平台与部署条件。通信机制和基准设计交给第 06、08、13、17 章。 [NCCL 使用 MIG 的条件](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/usage/communicators.html#using-mig-instances) · [MIG 620 P2P 与 GPUDirect RDMA 条件](https://docs.nvidia.com/datacenter/tesla/mig-user-guide/620/deployment-considerations.html#application-considerations)
