# GPU 集群与 AI 基础设施学习大纲

## 文档定位

面向已经具备 Linux 与 Kubernetes 基础知识、希望系统理解 NVIDIA GPU 集群与 Kubernetes AI 基础设施的读者。学习从服务器硬件与 CUDA 软件栈开始，逐步扩展到多机通信、GPU 与 RDMA 的容器化、设备管理、作业调度和集群运维。

以 Linux 与 Kubernetes 的通用知识为前置，重点解释 NUMA、设备分配、容器运行时等机制在 GPU 场景中的作用与约束。

硬件与加速软件以 NVIDIA GPU / CUDA 生态为主。上层范围止于 Kubernetes 中与 GPU 集群相关的基础设施生态。训练、推理等负载只用于解释计算、显存、通信与存储需求，算法实现、模型效果、业务服务和完整 MLOps 平台不进入主线。

学习无需 GPU 实验环境，目标是能根据拓扑、配置和观测结果解释系统行为。

## 学习顺序

主线是：**一台 GPU 服务器如何工作 → 多台服务器如何协同 → Kubernetes 如何管理这些能力 → 如何维持集群的健康与性能。**

| 阶段 | 章节 | 学习结束后应能说明的事情 |
| --- | --- | --- |
| 一、理解一台 GPU 服务器 | 01—04 | GPU 如何计算，软件如何驱动硬件，数据在 CPU、GPU 与设备之间如何移动 |
| 二、理解多机协同与数据供给 | 05—09 | 分布式负载为何需要通信，RDMA 与 NCCL 如何配合，网络和存储如何影响整体效率 |
| 三、将 GPU 集群能力接入 Kubernetes | 10—16 | GPU 与网卡如何进入容器，如何被发现、分配、共享，以及多卡作业如何被调度 |
| 四、理解集群运维的完整过程 | 17—20 | 如何建立观测与性能基线，定位故障，完成交付与升级，并串联一次作业的完整生命周期 |

## 第一阶段：理解一台 GPU 服务器

### 01 从一台 GPU 服务器认识整套基础设施

- 服务器中的 CPU、内存、GPU、网卡、NVMe、PCIe Switch 分别承担什么工作。
- PCIe GPU、SXM 模组与 HGX 等整机平台的形态差异；阅读配置表时需要辨认的信息。
- CPU Socket、NUMA、PCIe Root Complex 与设备连接关系，建立物理拓扑的第一张图。
- 带内管理、BMC 带外管理，以及供电、散热、机架条件对 GPU 节点的约束。
- 从单节点扩展到集群：管理流量、作业协调流量、GPU 通信与存储流量的职责划分；逻辑分工与物理分网的区别。

### 02 GPU 如何计算，显存为什么重要

- SM、CUDA Core、Tensor Core、线程与 Warp 的基本关系，理解 GPU 并行执行的粒度。
- HBM、缓存、主机内存与显存之间的层次；显存容量与显存带宽分别限制什么。
- 运算精度、吞吐与资源需求之间的联系，区分规格表中的峰值与作业实际表现。
- 计算受限、访存受限、数据等待三类情况，建立观察 GPU 性能的基本思路。
- Kernel、Stream、异步执行与同步的概念，解释为什么 CPU 状态和 GPU 状态不一定同步。
- 显存占用、GPU 利用率、计算效率分别反映什么，为什么单个百分比不足以判断瓶颈。

深度以能理解运行行为和性能现象为准，CUDA Kernel 编程不作为学习前置。

### 03 从驱动到 CUDA 应用的软件依赖

- GPU 固件、内核模块、用户态驱动库、CUDA Driver API、CUDA Runtime 与 Toolkit 的分工。
- CUDA 应用启动时如何加载库、发现设备并建立运行上下文。
- `nvidia-smi`、NVML、`nvcc` 分别观察或服务于哪一层。
- 驱动版本、Toolkit 版本、应用构建版本与设备架构之间的兼容关系；如何阅读兼容性说明。
- 内核更新、模块构建、模块签名、库路径与动态链接问题如何影响 GPU 可用性。
- 用“驱动未加载”“库版本不匹配”“应用不支持当前设备”等材料区分故障层次。

兼容性部分以 [NVIDIA CUDA Compatibility](https://docs.nvidia.com/deploy/cuda-compatibility/latest/) 为依据，具体版本组合在正文写作时单独核对。

### 04 单机多卡与 GPU 数据路径

- CPU 到 GPU、GPU 到 GPU 的数据传输分别经过哪些组件。
- PCIe 链路代际、宽度、交换层级和共享上行链路对有效带宽的影响。
- P2P、主机内存中转、NVLink 与 NVSwitch 的作用及适用条件。
- GPU、CPU 与 NIC 的拓扑亲和，跨 NUMA 路径与设备放置的代价。
- Fabric Manager 等管理组件在适用平台上的职责；区分硬件可见与互联可用。
- 阅读 `nvidia-smi topo -m`、PCIe 拓扑和设备标识，将逻辑 GPU 编号映射回物理连接。

## 第二阶段：理解多机协同与数据供给

### 05 为什么一个作业需要多张 GPU

- 计算量、显存容量和完成时间如何推动负载从单卡走向多卡、多机。
- 数据并行、张量并行、流水线并行与专家并行的基本通信形态，仅解释基础设施需求。
- 进程、Rank、Local Rank、World Size 与 GPU 的映射。
- 作业发现、Rendezvous、成员初始化和同步等待之间的关系。
- AllReduce、AllGather、ReduceScatter、Broadcast 与 All-to-All 的数据交换含义。
- 慢节点、失联成员、负载不均和重试为什么会放大为整个作业的问题。

这一章提供学习 RDMA、NCCL 和组调度的动机，不展开模型算法。

### 06 从普通网络通信走向 RDMA

- 对照数据路径理解 Socket 通信与 RDMA，分别观察 CPU 参与、内存复制和协议处理。
- RDMA 网卡、Verbs、QP、CQ、MR、PD 等核心对象，以及内存注册与访问权限的作用。
- Send/Receive、RDMA Read/Write 的基本区别，连接建立与数据传输的先后关系。
- 内核驱动、用户态库和网卡固件如何配合；内核自带驱动栈与厂商软件栈的关系。
- GPUDirect RDMA 如何连接 GPU 显存与网卡，直接访问与主机内存中转的区别。
- PCIe 拓扑、IOMMU、ACS、DMA-BUF、Peer Memory 等相关条件如何参与支持性判断。

重点是能顺着数据路径解释机制和限制。驱动选项与支持条件须结合硬件、内核和软件版本阅读。

### 07 InfiniBand、RoCE 与集群网络拓扑

- InfiniBand 与 RoCEv2 的协议基础、寻址方式、链路与路由关系。
- InfiniBand 的 Subnet Manager、LID/GID、分区等管理概念；区分原生 RDMA 与 IPoIB。
- RoCE 网络中的优先级、PFC、ECN 与拥塞控制，理解丢包、暂停、排队和拥塞扩散。
- Spine-Leaf、Clos、收敛比、双向带宽、ECMP 和多 Rail 设计如何影响多机通信。
- GPU—NIC—交换机之间的端口映射、布线关系和故障域。
- Scale-up 与 Scale-out 的区别；机架级 NVLink 域与跨域网络的关系。
- 链路带宽、有效吞吐、拥塞、光模块与物理链路错误如何区分。

RoCE 按机制与部署条件讲解，不把一份 PFC/ECN 配置当作所有网络的通用答案。

### 08 NCCL 如何组织 GPU 间的通信

- NCCL 在应用框架、CUDA 与底层互联之间的位置，以及作业启动器与通信库的职责边界。
- 集合通信如何映射为实际传输，Ring、Tree 等算法为何受规模和消息大小影响。
- 单机与多机路径中的 P2P、共享内存、网络传输，以及设备发现和路径选择。
- 进程协调与通信初始化、数据传输、同步等待几个阶段的区别。
- 如何阅读 NCCL 日志中的 Rank、设备、网络接口、传输路径与错误信息。
- `nccl-tests` 的测试对象、消息大小、GPU 数量与 `algbw` / `busbw` 的读法。
- 从单链路测试到集合通信测试，理解 perftest 与 NCCL 测试各自能证明什么。

通信库的职责与能力以 [NCCL 官方文档](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/overview.html) 为依据；基准结果须连同拓扑、规模和参数一起解释。

### 09 GPU 的数据从哪里来：存储与 I/O

- 数据读取、预处理、主机内存缓冲、传入显存的一条完整路径。
- CPU 解码、数据加载并发、页缓存和预取如何影响 GPU 等待时间。
- 本地 NVMe、共享文件系统、并行文件系统与对象存储的访问特点和部署角色。
- 元数据、小文件、顺序吞吐、并发访问与缓存命中等不同瓶颈。
- Checkpoint 写入与恢复读取带来的容量、带宽和突发压力。
- GPUDirect Storage 的基本路径、依赖条件与适用边界。
- 将存储瓶颈与通信等待、显存不足、计算不足区分开来。

存储保留为数据供给的一环，产品仅作架构实例，不展开完整存储系统管理教程。

## 第三阶段：将 GPU 集群能力接入 Kubernetes

### 10 GPU 如何进入容器

- 宿主机驱动、容器内 CUDA 库与应用之间的依赖关系。
- 容器使用 GPU 所需的设备节点、库文件、权限与运行时配置。
- NVIDIA Container Toolkit 的组成，以及它与 containerd、OCI Runtime 的衔接。
- CDI 如何描述设备注入，区分设备注入与资源分配。
- GPU 可见性、设备编号与 UUID；容器内外观察同一设备时如何对应。
- 从“宿主机能看到 GPU、容器里不可用”的现象追踪缺失环节。

软件分工以 [NVIDIA Container Toolkit 架构说明](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/arch-overview.html) 为基础；正文区分不同注入方式和版本。

### 11 Kubernetes 如何发现与分配 GPU

- Device Plugin 的注册、设备上报、健康状态更新与分配流程。
- 扩展资源、Node Capacity/Allocatable、Pod 资源请求之间的关系。
- 从 Pod 请求 GPU，到 kubelet 分配设备，再到容器获得设备的完整链路。
- NFD 与 GFD 提供的信息、节点标签的用途及其与资源数量的区别。
- DRA 中 DeviceClass、ResourceSlice、ResourceClaim 等对象，理解设备属性与分配表达方式。
- Device Plugin、DRA 与 CDI 分别解决什么问题，以及各路径对运行时和驱动组件的依赖。

以 [Kubernetes Device Plugins](https://kubernetes.io/docs/concepts/extend-kubernetes/compute-storage-net/device-plugins/) 和 [DRA 官方文档](https://kubernetes.io/docs/concepts/resource-management/dynamic-resource-allocation/) 为依据。DRA 的具体功能按所选 Kubernetes 与 NVIDIA 驱动组件版本说明。

### 12 GPU Operator 如何管理节点软件

- 将驱动、Container Toolkit、设备插件、设备发现与监控组件放回同一张依赖图。
- GPU Operator 的控制器、配置对象和节点侧工作负载如何协作。
- 节点预装软件与 Operator 管理软件的责任划分，如何确定每项组件的管理者。
- 一个新 GPU 节点从加入集群到资源可用的状态变化。
- Validator、组件日志、DaemonSet 状态与节点资源之间如何相互印证。
- 镜像分发、离线环境、异构节点池与组件版本匹配对部署的影响。

组件范围以 [NVIDIA GPU Operator 官方说明](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/latest/overview.html) 为依据。

### 13 Multus 与 RDMA：把高速网络交给 Pod

- 默认 Pod 网络、附加网络、作业协调流量与高速数据流量的关系。
- Multus 的委派机制、NetworkAttachmentDefinition 和 Pod 网络选择。
- PF/VF、SR-IOV Device Plugin、SR-IOV CNI 与 IPAM 各自负责的步骤。
- RDMA Shared Device Plugin、RDMA CNI 与 RDMA 设备命名空间模式的作用。
- 共享 RDMA 设备、SR-IOV VF、其他设备接入方式的资源与隔离差异；按方案选择组件组合。
- Network Operator 与 GPU Operator 的配合，以及主机、Pod 两侧的 GPUDirect RDMA 依赖。
- GPU 和 NIC 的分配关系、NUMA 亲和、附加网卡路由、MTU 和地址管理。
- 默认网络与附加网络的可观测性、安全策略覆盖范围和故障定位边界。

[Multus](https://github.com/k8snetworkplumbingwg/multus-cni) 负责组织多网络接入；高速网络的驱动、设备插件、CNI 与地址管理结合 [NVIDIA Network Operator 文档](https://docs.nvidia.com/networking/display/kubernetes2640/overview.html) 分别讲解。

### 14 GPU 共享、切分与隔离

- GPU 独占、Time-Slicing、MPS 与 MIG 分别在什么层面共享或划分资源。
- 显存容量、计算份额、性能干扰、错误传播与安全隔离需要分别评估。
- MIG 的 GPU Instance、Compute Instance、Profile 与实例生命周期。
- 共享策略如何改变 Kubernetes 中的资源表达、调度行为和监控归因。
- 切分粒度与资源碎片，重配置对现有作业和设备标识的影响。
- 结合负载需求与隔离要求选择资源池，辨认“能够申请”与“获得性能保障”的区别。

MIG 的支持硬件、配置与隔离能力以 [NVIDIA MIG User Guide](https://docs.nvidia.com/datacenter/tesla/mig-user-guide/introduction.html) 为依据，并标注具体平台限制。

### 15 从单个 Pod 放置到多卡作业调度

- 作业副本之间的协作关系，以及为什么部分进程获得资源后仍无法推进计算。
- 作业准入、Pod 调度、节点内设备分配三个阶段的职责。
- Gang Scheduling 的资源成组需求，以及弹性作业与固定规模作业的差异。
- GPU 型号、显存、卡数、CPU、内存、NIC 和网络拓扑共同构成的资源约束。
- 机架/网络域放置与节点内 NUMA 对齐的区别；Topology Manager、CPU Manager 等如何参与节点内资源对齐。
- 资源碎片、装箱、队列公平、优先级、抢占与大作业等待时间的关系。
- 根据 Pending、准入状态与分配失败事件，判断问题停在哪个阶段。

先建立调度问题本身，再进入具体实现，避免把某个项目的对象名称直接当成调度原理。

### 16 以 Volcano 串起作业、队列与调度策略

- Volcano 的 Scheduler、Controller、Admission 组件及其与 Kubernetes 的协作方式。
- VolcanoJob、Task、PodGroup、Queue 的关系与状态变化。
- Gang、队列容量、公平分配、抢占、资源回收与装箱策略解决的具体问题。
- 从一个多机多卡作业的配置开始，跟踪提交、排队、调度、启动、失败和资源释放。
- 作业重试、成员失败、应用保存恢复状态与调度器之间的责任边界。
- 用 Kueue 对照理解配额、准入与 Pod 调度的关系；说明组合使用时需要明确的控制边界。
- JobSet、Kubeflow Trainer 等作业组织组件作为扩展阅读，介绍它们与调度系统的接口，不展开完整平台。

实现主线参考 [Volcano 官方文档](https://volcano.sh/docs/home/introduction/)；准入管理的对照参考 [Kueue Overview](https://kueue.sigs.k8s.io/docs/overview/)。

## 第四阶段：理解集群运维的完整过程

### 17 把设备、网络与作业状态联系起来

- NVIDIA 管理工具、NVML、DCGM 与 DCGM Exporter 的用途和观测层次。
- GPU 温度、功耗、频率、显存、计算活动、ECC、PCIe 和 NVLink 指标如何解释。
- NIC、RDMA 端口、交换机与存储指标如何补充 GPU 侧信息。
- GPU UUID、MIG 实例、节点、Pod、Rank 与作业之间如何建立关联。
- 从物理链路、单机多卡、跨节点 RDMA 到集合通信建立分层性能基线。
- 固定消息大小、并发、拓扑、软件版本和测试方向，解释可比较的测试结果。
- 结合排队时间、失败率、作业进展与资源占用评估集群状态。

监控和诊断能力参考 [NVIDIA DCGM 文档](https://docs.nvidia.com/datacenter/dcgm/latest/user-guide/feature-overview.html)。教学中的基准数字明确标注来源和条件。

### 18 从故障现象追到具体层次

- GPU 不可见：硬件枚举、驱动、容器注入、资源上报与分配链路。
- GPU 可见但不可计算：初始化、显存、库兼容、权限与设备状态。
- Xid、ECC、PCIe AER、NVLink 错误和网卡错误如何与时间线相互印证。
- 单机正常而多机异常：成员发现、网络连通、RDMA、GPUDirect 与 NCCL 初始化。
- 作业挂起或性能下降：慢 Rank、通信等待、拥塞、数据供给不足与硬件降频。
- 硬件链路、驱动、应用行为和平台配置之间的交叉影响；错误码作为线索的使用方法。
- 从采集证据、缩小范围，到隔离节点、恢复作业、验证复归的完整处置思路。

错误码的解释与处置条件查阅 [NVIDIA Xid 文档](https://docs.nvidia.com/deploy/xid-errors/latest/index.html)，案例不将一个错误码直接等同于唯一根因。

### 19 节点交付、版本变更与集群持续运行

- 硬件、固件、内核、GPU/NIC 驱动、CUDA、运行时、Operator 和网络配置的基线。
- 节点交付的分层验收：设备健康、互联、容器访问、Kubernetes 资源与多机通信。
- 从单节点到机架、网络域的容量设计，综合 GPU、网络、存储、供电和散热条件。
- 升级前兼容性检查、试点节点、作业排空、影响评估、回滚与性能复核。
- 故障设备隔离、资源撤回、节点维修与重新入池的状态流转。
- GPU 管理组件的主机权限、设备访问、附加网络隔离与租户资源边界。
- Operator 配置、网络配置、节点镜像和基线资料的留存，以及恢复时需要的外部依赖。

生产过程以配置差异、状态变化和决策材料呈现，读者通过评审一份交付或升级方案来理解工作要求。

### 20 用完整场景串联整套知识

以多机 GPU 集群为背景，结合节点拓扑、网络分工、版本、配置、事件和监控证据分析以下场景。

- **一次多机作业的完整生命周期**：提交 → 排队与准入 → Pod 放置 → GPU/NIC 分配 → 容器启动 → 通信初始化 → 运行 → 退出与回收。
- **一次资源不足的分析**：从“还有空闲 GPU”出发，辨认卡型、显存、拓扑、队列、NIC 与资源碎片约束。
- **一次多机性能退化的分析**：对照健康与异常材料，在 GPU、通信路径、网络、CPU 与存储之间逐步定位。
- **一次 GPU 故障的影响分析**：将设备异常、作业失败、节点隔离、资源容量变化与恢复过程串联。
- **一次集群变更的评审**：判断依赖是否匹配、影响范围是否明确、回滚能否恢复可用性与性能。

学习成果是能够画出数据路径和管理关系、解释现象、提出下一步证据需求，并指出材料尚不足以支持的结论。
