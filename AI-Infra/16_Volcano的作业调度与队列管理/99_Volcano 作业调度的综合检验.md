## 材料二　队列份额、装箱和可回收落点

以下三份快照彼此独立。三台节点各有 8 GPU 和 32 CPU，其余未讨论维度满足要求。

1. **空池保留。** `train` 与 `batch` 的 GPU 上限分别为 16 与 24，应得份额分别为 12 与 11。为 `train` 专属保留 2 GPU 时，`batch` 的 GPU 有效上限是多少？
2. **排序与装箱。** 两个同队列、同优先级的作业 A、B 已分别分配 `2 GPU + 24 CPU` 和 `4 GPU + 12 CPU`，其余资源占比都较低，DRF 前的回调均打平。算主导份额并比较顺序。如果先用 `priority`，并提高 A 的作业优先级，顺序如何变化？另有 10 个单卡 Pod 可放成占用 `4 / 3 / 3` 或 `8 / 2 / 0`，两种布局分别留给 `train-12` 几个落点？如果等的是一个八卡 Pod，答案怎样变化？
3. **回收位置。** 专属保留为 0，`batch` 在 `h1/h2/h3` 占用 `4 / 4 / 7 GPU`，应得份额仍为 11。`train` 当前用量为 0，`train-12` 已入队并生成待放置成员。`h2`、`h3` 各有一个属于 `batch` 的合格四卡驱逐候选，只能提交一个。选用哪种 action？分别推算两个候选退出后的用量、节点余量与成组结果。若只把 `batch` 的 `reclaimable` 设为 `false`，哪道条件改变？

## 参考推理

### 1. 从声明到应用会合

Job Controller 生成 PodGroup。最低成员数是 3，`spec.minTaskMember.worker=3`，`spec.minResources` 对应 12 GPU、48 CPU、288 GiB 和 3 VF。`enqueue` 由 Volcano Scheduler 执行，初始账面是 `12 + 3 + 2 = 17 > 16`，组不能入队。组被放行后，仍由 Job Controller 创建三个 worker。

撤回在途需求后为 `12 + 3 = 15 ≤ 16`，可以入队。合计余 16 GPU，但 `h3` 缺 VF，只有 `h1`、`h2` 各能放一只。Gang 无法提交三人成组方案。`h3` 归还一个 VF，且调度器已计入释放后，三台均可放，组能进入绑定流程。应用仍要等 kubelet 交付和三个 Agent 会合。

只改 Job 门槛为 2 时，v1.16.0 发现它小于各角色门槛的和，跳过逐角色检查。本例改为按两只 Pod 算最低资源，两个落点足以提交。要明确表达弹性规格，把 Job 和 Task 的最低值都设为 2，目标副本数仍为 3。应用需确实支持 `--nnodes=2:3` 的成员变化。两个 Agent 完成会合时为 `2 × 4 = 8` 个进程，若仍用固定三节点参数，则继续等待。

### 2. 从共享账本到空间分布

为 `train` 保留 2 GPU 后，`batch` 有效上限为 `min(24, 24 − 2) = 22`。DRF 中 A 的主导份额为 `max(2/24, 24/96) = 1/4`，B 为 `max(4/24, 12/96) = 1/6`，所以先考虑 B。提高 A 的优先级且优先级回调在前时，先考虑 A。

装箱变体的节点余量分别为 `4 / 5 / 5` 和 `0 / 6 / 8`，总数都是 14。前者有三个四卡落点，后者有两个。对于单个八卡 Pod，前者有零个八卡落点，后者有一个。

跨队列应使用 `reclaim`。两种候选各让 `batch` 从 15 降到应得的 11。释放 `h2` 时，余量为 `4 / 8 / 1`，仍只有两个位置。释放 `h3` 时，余量为 `4 / 4 / 5`，有三个位置。`reclaimable=false` 会使回收 action 从候选范围中排除 `batch` 的 Pod。上述余量描述候选已退出并归账的结果，提交前仍需验证可回收性和成组流水线条件。

### 3. 从旧成员身份到恢复步数

- **甲**　Agent 重启了进程组。核对本轮会合标识、组规模及应用加载的检查点。
- **乙**　同一 Pod 中的容器发生重启。结合 kubelet 事件、原退出码和重启策略查容器层原因。
- **丙**　Job 策略推动了整组重建。用控制器事件和新旧 UID 确认重试路径，再看新 Pod 是否绑定、节点侧是否交付、应用是否重新会合。

可恢复到 9,000 步，需重做 `9,420 − 9,000 = 420` 步。队列账面是 `15 − 12 + 4 = 7 GPU`。旧 Pod 请求全部释放和 API 用量只净降 8 可以同时发生。恢复成功还要核对新一轮实际加载的存档与恢复步数，并确认后续训练继续推进。

### 4. 从准入条件找到下一位处理者

甲已保留配额，障碍在准入检查。查检查名称、状态消息与执行该检查的控制器，然后看 Kueue Job 集成是否解除挂起。乙已经完成准入，第三只正在等节点绑定。查默认调度器针对当前 Pod UID 的事件，按节点复算硬反亲和和 VF 余量。另两台已各承接一只，`h3` 仍没有 VF。

使用题设的 Trainer 集成后，先查 TrainJob 的挂起状态及关联 Workload，再看 Runtime 和生成的 JobSet，沿所有权关系追到子 Kubernetes Job 及 Pod。最后以生成 Pod 的 `spec.schedulerName` 确认绑定者。

## 从配额到可恢复的训练进度

作业规格把应用的成员依赖换算成 Pod 角色、最低规模和资源向量。队列先判断能否承接该向量，调度器再把它落实到具体节点，kubelet 交付实际设备，应用完成会合与通信。成员失败沿同一条链回查，依次确认重试对象、资源状态和可恢复进度。第 17 章会把这些对象、设备和应用证据接到观测时间线上，帮助判断作业是在等资源、等启动，还是已开始运行但进展受阻。
