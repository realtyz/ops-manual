# 基线测量与结果判读

一次测量跑完，输出表里的每个数字都带着字段名与单位；判读要做的是把它与「回答哪个问题、属于哪条路径、这一组变量是什么」对上。对不上的数字分两种：一种一眼可疑，例如比线速还快；另一种看上去完全正常，但它测的不是要回答的那条路径，或者是在一组没有固定住的变量下测出来的。后一种是主要的错误来源：这样的数字一旦被当成结论写进记录，后面所有拿它当参照的对照测量都跟着失效，因为参照本身站不住。因此读数的可信度在读数出现之前就决定了一半：路径确认与变量固定是先于读数存在的两个动作，字段判读只是把这两个动作的结果读出来。

## 路径确认的两个固定动作

第一个动作是确认设备与网络设备的对应关系。测试命令里的 `-d <dev>` 指的是 RDMA 设备名，而这次测量要验证的往往是某一张具体的网卡；两者对不上时，读数取自在另一张卡上，并且这种错误不会以任何报错的形式出现。

```bash
ibdev2netdev   # 验证：设备名与网络设备名的对应关系，确认 -d 指向的设备就是被测的那张网卡
```

第二个动作是确认流量真的经过被测网卡。RDMA 的数据面完全由硬件卸载，这部分流量不进标准以太网接口的软件计数，也不走内核网络栈，因此以太网侧的统计与 ping 的结果都不能证明这次测量走了 RDMA 路径；能证明的只有 RDMA 设备自己的端口计数器。计数器是累计量，判据不是读绝对值，而是取测量前后两次读数之差——差值非零，才说明这段流量真的经过了这张网卡。

```bash
cat /sys/class/infiniband/<device>/ports/1/counters/port_xmit_data   # 验证：测量前后各读一次，取差值；差值非零说明流量真的经过了这张网卡
```

发起端读发送方向的 `port_xmit_data`，对端读收方向的 `port_rcv_data`。两个动作都是只读观测，生产节点上也可以做；这一步没有做，后面所有读数都只是在读一台与这次测量无关的设备。

## 变量控制的固定动作

变量固定的目标可以压成一句话：两次测量之间，除了要对照的那一项，其余取值逐项相同。为此有四组取值要先固定下来，下表给出每一组的入口、它为什么能翻转结论，以及怎么算固定住了。

| 变量 | 固定动作（入口） | 它为什么能翻转结论 | 怎么算固定住了 |
| --- | --- | --- | --- |
| 亲和绑定 | 用 `numactl` 包住测试命令：`--cpunodebind` 与 `--membind` 分别指定核与内存的域，域号取拓扑矩阵的亲和列 | 完成事件由处理器轮询取回，绑定关系决定取回路径；亲和变化常表现为均值几乎不变而分位值显著变差 | 两轮测量使用同一个域，且该域是出线网卡所在的域 |
| 消息大小 | 先用 `-a, --all` 跑全尺寸（2 字节到 2^23），再把对照用的尺寸固定在大消息段的一个取值上 | 小消息段由每次操作的固定开销主导，大消息段由管道填充主导；同一条链路在两端指向完全不同的断点 | 对照读数取自大消息段的那一行；小消息段的读数单独记录，不与大消息段混比 |
| 单向还是双向 | 默认单向；要测双向用 `-b, --bidirectional`，并且先把两个方向各自单独测过 | 双向读数不等于单向的两倍：回程方向不匹配时，双向读数只反映较弱的一侧 | 两个方向的单向读数先各自成立，再谈双向 |
| 队列深度 | `-t, --tx-depth`（带宽测试默认 128）与 `-q, --qp`（默认 1） | 在途字节数不足时，带宽由「在途字节数 ÷ 往返时延」决定，而不是由链路速率决定 | 反推在途字节数（实测带宽 × 往返时延），与「队列深度 × 消息大小」同量级 |

贯穿四组取值的纪律是每一轮只改一个变量。每轮开测之前，把这一轮的取值（消息大小、队列深度与队列对数、单双向、亲和、GPU 序号）随本轮读数一起记下——没有这份取值，下一轮就无法证明只改了一项，差值也就无法归因。

## 每个工具读哪个字段

### 点对点工具的带宽读数

带宽测试的输出按行给出：`#bytes`、`#iterations`、`BW peak[MiB/sec]`、`BW average[MiB/sec]`、`MsgRate[Mpps]`；加 `--report_gbits` 之后，两个带宽列的列头换成 `[Gb/sec]`。每一行对应一个消息大小，判读前先确认读的是哪一行。

| 字段 | 是什么与单位 | 判据 | 与谁同看 | 读到它转向哪一步 |
| --- | --- | --- | --- | --- |
| `BW peak` | 这一行的测量里，最好的一段连续窗口折算出的带宽，单位随列头（默认 `MiB/sec`） | 与同行的 `BW average` 对照：两者差距大，说明这一轮的散布大，先排除测量环境的问题再谈链路 | 同行的 `BW average` | 差距大时先核对绑核与同机其它进程的占用，再复测 |
| `BW average` | 这一行整轮测量的总字节数除以总耗时，单位随列头 | 折到同一单位（位与字节、二进制与十进制两处换算）后，与端口协商出的线速（链路单方向的理论最大速率）同量级，并且不超过它；对照用大消息段的那一行 | 同行的 `#bytes` 与 `MsgRate` | 低于预期时按故障现场定位表逐行核对；单位与方向的折法按「结果的两个口径」核对 |
| `MsgRate[Mpps]` | 每秒完成的消息数，单位是百万条（10^6 条/秒） | 与同行的带宽自洽：带宽（字节每秒）÷ 消息大小 ÷ 10^6 应还原出消息速率 | 同行的 `BW average` 与 `#bytes` | 三个数还原不出来时，先检查单位与行是否抄错，再谈性能 |

`MsgRate` 的自洽关系给两个换算点：8 KB 消息、1.2 Mpps 折合 1.2×10^6 × 8192 字节每秒 ≈ 9.8 GB/s（≈ 78.6 Gb/s）；4 KB 消息、2 Mpps 折合 2×10^6 × 4096 字节每秒 ≈ 8.2 GB/s（≈ 65.5 Gb/s）。反推判据是同一行内部的还原：把 `BW average` 折成字节每秒，除以 `#bytes` 与 10^6，得到的数应当与 `MsgRate` 一致；不一致说明三个数不是同一段窗口，或者单位被混用了（例如把 `MiB/sec` 当成了十进制 `GB/s`）。

### 点对点工具的延迟读数

延迟测试的输出按行给出：`#bytes`、`#iterations`、`t_min[usec]`、`t_max[usec]`、`t_typical[usec]`、`t_avg[usec]`、`t_stdev[usec]`、`99% percentile[usec]`、`99.9% percentile[usec]`。这一组统计在去掉最慢的两个样本之后计算，因此 `t_max` 不是绝对最大值，两个分位值也建立在同一个修剪后的样本集上。

| 字段 | 是什么与单位 | 判据 | 与谁同看 | 读到它转向哪一步 |
| --- | --- | --- | --- | --- |
| `t_avg[usec]` | 这一行全部样本的平均延迟，单位是微秒 | 与同机型同配置的历史值比，而不是与绝对值比；写与双边发送的读数是一半往返时延，读与原子报完整间隔，两类不能直接比大小 | 同行的 `t_typical` 与两个分位值 | 平均值正常而分位值高时，先核对绑核与中断亲和，再谈链路 |
| `t_typical[usec]` | 修剪后的样本里排在中间的值（中位数） | 与 `t_avg` 接近说明分布大体对称；它明显低于 `t_avg` 说明有长尾把平均值拉高了 | 同行的 `t_avg` | 长尾明显时转入分位值与亲和核对 |
| `99% percentile[usec]` | 修剪后的样本里 99% 分位处的延迟 | 它给出「多数情况有多差」；与 `t_avg` 的比值是长尾的直接证据 | 同行的 `t_avg` 与 `t_typical` | 比值大时先核对绑核、中断亲和与同机其它进程的占用 |
| `99.9% percentile[usec]` | 修剪后的样本里 99.9% 分位处的延迟 | 它捕捉偶发停顿：平均值与 99% 分位都正常时，这里仍可能异常 | 同行的 `t_avg` 与 `99% percentile` | 只有它异常时，按偶发停顿处理：固定观察窗口、增加迭代次数复测 |

### 集合通信测试的列与页脚

集合通信测试的输出表按行给出：`size`、`count`、`type`、`redop`、`root`、`time`、`algbw`、`busbw`、`#wrong`；同一行有两组这样的列，左边是 out-of-place（输入与输出用不同缓冲），右边是 in-place（原地操作），两组列的字段名相同，抄数时按组取。

| 字段 | 是什么与单位 | 判据 | 与谁同看 | 读到它转向哪一步 |
| --- | --- | --- | --- | --- |
| `size (B)` 与 `count (elements)` | 这一行的数据量：字节数与元素个数 | 对照的两行这几列必须相同，否则比的是两次不同的操作；带宽判读只看大消息段的那几行 | 同行的 `type` | 对照的两行这几列不同时，换行再比 |
| `type` / `redop` / `root` | 数据类型、归约操作与根节点的 rank 号 | 两次对照必须完全相同；业务实际使用的类型与这里不同时，读数不代表业务 | 同行的 `size` | 类型不同时先统一类型再测 |
| `time (us)` | 这一行的迭代平均耗时，单位是微秒 | 默认是各 rank 的平均值（MPI 拉起多进程时）；`-a` 可切换成 rank 0、最小或最大——要判断最慢的参与者，用最大（`-a 3`）的读数与默认读数对照 | 同行的 `busbw` 与 `#wrong` | 两个读数差距大时，先核对 rank 与网卡的映射是否对称 |
| `algbw (GB/s)` | 算法带宽，按这一轮的数据量与耗时算出，单位是十进制 GB/s | 只与同 rank 数的读数比；它随 rank 数上升而下降由修正系数决定，不是退化 | 同行的 `busbw` | 报数与验收不用它；定位瓶颈时两个都看 |
| `busbw (GB/s)` | 总线带宽，把每个参与者实际进出的数据量都计入，单位是十进制 GB/s | 与这次通信里每个 rank 实际使用的链路合计上限同量级；明显偏低说明这一段没有被压满 | 同行的 `algbw`、各条轨道对应网卡端口的计数器增量 | 明显偏低时先确认通信真的走在预期链路上，再谈带宽 |
| `#wrong` | 正确性检查中越界元素的个数 | 必须为 0；非零说明这一行的结果校验失败，带宽读数作废 | 页脚的 `Out of bounds values` 一行 | 非零时先解决正确性问题，不要在这个读数上做性能判断 |
| 页脚 `Avg bus bandwidth` | 这一轮全部尺寸的 `busbw` 平均值，单位同列头 | 与历次同口径测量的页脚对照，适合作为单点的回归值；判断瓶颈仍要回到逐行 | 逐行的 `busbw` | 与基线对照异常时按故障现场定位表逐行核对 |

## 显存路径的对照测量：可执行步骤

对照测量回答的是「显存路径相对主机内存路径的收益是多少」；它成立的条件只有一条：两轮之间只切换内存类型。步骤按顺序如下。

**前置**：这次对照属于双机档；GPU 与出线网卡的位置关系已由拓扑矩阵确定；显存注册的模块前置已满足（注册显存所依赖的模块已加载，模块名与加载方式以本机为准）——不满足时注册直接失败，按加载类错误处理，不要从链路侧找原因。

**第一轮**，主机内存路径：两端各起一个进程，参数完全相同；响应端不带地址先起，发起端在命令末尾附上对端地址。

```bash
ib_write_bw -d <dev> -i 1 -s 1048576 -n 1000 --report_gbits                    # 验证：主机内存路径的读数，作为对照的基准
```

**第二轮**，显存路径：同一组参数只加内存类型这一项，GPU 序号取与出线网卡同域的那块。

```bash
ib_write_bw -d <dev> -i 1 -s 1048576 -n 1000 --report_gbits --use_cuda=<gpu 序号>   # 验证：显存路径的读数，两轮之差才是这条路径的收益
```

**判读**：对照两轮的 `BW average`（折到同一单位），差值才是收益；其余变量——消息大小、队列深度、单双向、亲和、GPU 与网卡的位置关系——在两轮之间必须不动。软件模拟的网卡（soft-RoCE）不支持显存直接路径，不在它上面做这一对照。这两条测量命令不改变任何配置，但会给链路加负载。

## 故障现场定位表

下表只在路径确认的两个固定动作都做完之后使用：设备与网络设备的对应关系没有核对、端口计数器没有出现增量时，任何读数都不构成结论。表的用法是先按现象定段，再读该行指定的两个字段；同一现象对应多行时逐行读，通常只有一到两行的字段不符合判据，那一到两行就是当前该处理的对象。

| 现象 | 属于哪一段 | 先读哪两个字段 | 不符合时转向哪一步 |
| --- | --- | --- | --- |
| 跨机带宽读数明显低于预期 | 跨机端口段 | 端口协商出的速率（生效值）；`BW average` 所在行的 `#bytes` | 先确认这一行属于大消息段；再分开测两个方向、把队列深度加大后复测 |
| 带宽读数超过线速 | 测量口径（不落在任何一段） | 读数所在列的单位（列头）；这一轮的方向设置（单向或双向） | 按四步核对口径：折单位、看方向、看范围、看对照对象 |
| 小消息段读数低 | 消息大小与延迟 | 同一行的 `MsgRate` 与 `BW average` | 先确认三个数能否互相还原；小消息段由消息速率封顶，按该尺寸的延迟分位值读，不要拿大消息段的判据套它 |
| `BW peak` 与 `BW average` 差距大 | 测量本身的散布 | `BW peak`；`BW average` | 先核对绑核与同机其它进程的占用，再复测；差值不收敛之前不写结论 |
| 平均延迟正常而分位值高 | 环境一致性（跨段） | `t_avg`；`99% percentile` | 先核对绑核与中断亲和，确认测量进程没有被抢占，再谈链路 |
| 集合通信读数低而点对点读数正常 | 集合通信整条链 | `busbw` 与 `algbw` 的比值；各条轨道对应网卡端口的计数器增量 | 先核对 rank 与网卡的映射是否对称，再谈带宽 |
| 显存路径相对主机内存没有收益 | 内存访问段 | 两轮的 `BW average`；`--use_cuda` 指向的 GPU 序号 | 确认两轮只改了内存类型；确认 GPU 与出线网卡的位置关系没有变 |
| 两次测量的结论相反 | 控制变量（跨段） | 两轮命令与参数的逐项对照；两次的采集时间 | 逐项对齐变量后重测；对齐之前的差值不构成结论 |
| 重复测量的散布大 | 测量窗口与外部干扰 | 多次重复的 `BW average`；同一行 `BW peak` 与 `BW average` 的差距 | 固定观察窗口与绑核后重测；散布不收敛时先排除干扰 |
| 容器内读数系统性低于同档宿主机 | 容器内 | 容器内与宿主机两轮的 `BW average`；两轮的命令与参数 | 先逐项核对两轮变量是否对齐，再核对设备可见性与亲和绑定 |
| 全部现象的共同前提 | 任意段 | 设备与网络设备的对应关系；测量期间端口计数器的差值 | 计数器没有增量说明测的不是承载业务的设备或路径，此时任何「读数正常」的结论都不成立 |

这张表能收敛的范围到主机侧的这一轮读数为止；fabric 侧的选路与拥塞判读不是本篇负责的内容。

## 伪结论的识别清单

在把任何结论写进记录之前，按这张清单过一遍。清单上的每一条都对应一种「看起来是结论、实际上缺了一步」的写法，缺的这一步都是可以补做的动作。

- 结论里的数字没有路径证据——测量期间端口计数器的差值没有核对过。补上之前，读数不能作为任何判断的依据。
- 结论把 `BW peak` 当成承诺带宽。它是最好的一段窗口，不是持续能力；报给业务或写进验收要用 `BW average`。
- 结论用 `algbw` 报告吞吐。它的上限随 rank 数变化，跨规模不可比；报告用 `busbw`。
- 结论把双向读数的一半当作单向能力。两个方向没有分开测过时，这个折半没有依据。
- 结论里的数字超过了线速，却没有先核对口径。按四步核对：折单位、看方向、看范围、看对照对象。
- 结论基于队列深度不足的读数。在途字节数没有与带宽时延积对照过时，「链路慢」与「参数没给够」不可区分。
- 结论用点对点工具的读数回答集合通信的问题。点对点工具的覆盖范围不含通信库的选路与算法，两类读数不能互相代替。
- 结论来自两次口径不同的测量。环境档、参数或亲和没有逐项对齐时，差值不构成结论。
- 结论拿换过驱动四元组或网卡固件之前的旧读数当参照。四元组一变，旧读数的口径就不在了，必须重测。
- 结论来自软件模拟的网卡，或从单机档、双机档外推。软件模拟网卡的成绩不进入任何性能结论；单机档支撑不了跨机结论，双机档支撑不了多机结论。

**第一反应不要做什么**：不要在没确认流量经过被测网卡之前接受任何带宽读数；不要拿一行的 `BW peak` 当承诺带宽；不要在变量没有逐项对齐时比较两次读数；不要把队列深度不足导致的低带宽当成链路退化；不要把平均值的正常当成延迟的正常——长尾的证据在分位值上；不要在小消息段上套用大消息段的判据；不要用软件模拟网卡的成绩支撑任何性能结论；不要在记录读数时落下这一轮的变量取值。
