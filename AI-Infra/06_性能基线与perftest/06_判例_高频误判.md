# 高频误判

从一条读数到一份结论，中间隔着若干个看起来显然的推理步骤：命令跑通说明测的是这张网卡，读数落在合理量级说明硬件正常，数字变大说明变更有效。每一步都可能跳过了一个必须先回答的问题，而跳过之后的结论不带任何异常特征——它同样由数字支撑，同样经得起复述；代价要等到拿它做决定时才结算：处置动到了不该动的对象，真正的问题留在原地，而这份结论还会作为参照被下一次比较引用。下面十条是这条推理路上高频出现的误判，每一条按同一套字段展开：场景、常见误判以及它为什么看起来成立、判据、一句话结论、出处；其中判据一项固定交代读哪个字段、该字段是累计量还是瞬时量、期望的趋势是什么、需要与谁同看，以及哪些条件一旦改变结论就会翻转。

### 「读数有了，测的就是这张网卡」

- **场景**：验收报告里写「网卡 A 的带宽是 X」，X 取自一次点对点带宽测试。机器上有多张网卡，业务网卡与存储、管理网卡并存，命令里的 `-d` 指向的设备与报告里写的网卡没有逐字核对过。
- **常见误判**：把「命令跑通并输出数字」当作「测的就是报告里那张网卡」。它看起来成立的原因在于命令没有报错、读数落在合理量级；而 RDMA 的数据面完全由硬件卸载，这部分流量不进标准以太网接口的软件计数，也不走内核网络栈，因此以太网侧的统计与 ping 的结果都不能用来确认数据面走了哪张卡。
- **判据**：读被测设备的端口计数器（`port_xmit_data`、`port_rcv_data` 一类，是累计量，判据是测量前后两次读数之差非零），并用设备与网络设备的对应关系入口（`ibdev2netdev` 一类）确认 `-d` 指向的设备就是报告里写的那张网卡；与谁同看：两端的设备名与业务实际出线的网卡。条件会变：设备对应关系正确而计数器没有增量时，说明这段流量没有经过这张网卡，读数与它无关——此时读数可能完全正常，错的是归属。
- **结论**：读数的归属是一个要单独确认的对象；命令跑通与数值合理都不能代替设备对应关系与计数器差值的核对。
- **出处**：NVIDIA DOCA 文档中 RoCE 一章（数据面由硬件完全卸载、设备与网络设备对应关系的查看入口）；Linux 内核 `Documentation/ABI/stable/sysfs-class-infiniband`（端口计数器的读取位置与语义）。

### 「软件模拟的网卡也能代表 RDMA 性能」

- **场景**：现场没有可用的硬件 RDMA 设备，用软件模拟的 RDMA 实现（soft-RoCE，内核模块 `rdma_rxe`）把工具链跑通；随后的性能记录里出现了它的带宽与延迟读数，甚至被拿去和硬件机型对比。
- **常见误判**：把「RDMA 语义跑通」当作「测到了 RDMA 硬件性能」。它看起来成立的原因在于工具、设备节点与输出表完全一致——列名、单位、数值格式都与硬件环境相同，读数也不会以报错或异常的形式暴露身份；差别只在数据面由谁执行：软件模拟实现的全部数据面处理都落在主机处理器上，读数反映的是处理器与内存的速度，不是链路的速度。
- **判据**：读被测设备的实现来源——软件模拟实现的内核模块在模块清单里可见（`rdma_rxe`），它创建的设备与硬件设备并存于设备清单；测试命令的 `-d` 必须指向设备清单中确认过的硬件设备，设备名以本机清单为准。与谁同看：业务实际出线的网卡。条件会变：只要被测设备是软件模拟实现，它的带宽、消息速率与延迟读数都只能用于熟悉命令与验证链路，不得写进任何性能记录；这类实现也不提供显存直接路径，在它上面做显存路径的对照测量没有意义。
- **结论**：软件模拟实现的读数与硬件读数不是同一个对象；它的成绩只用于熟悉命令与验证链路。
- **出处**：Linux 内核 RDMA 子系统的软件实现目录 `drivers/infiniband/sw/rxe` 与 `rdma-link(8)` 手册页（`type rxe` 设备的创建方式）；NVIDIA GPUDirect RDMA 文档（显存直接路径对设备的前置要求）。

```bash
lsmod | grep rdma_rxe; rdma link   # 验证：软件模拟实现的内核模块与设备清单并存，被测设备名以本机清单为准
```

上面这条命令只用于在本机取到模块条目与设备清单；输出项名与清单随机型、驱动四元组与网卡固件变化，这里不给出示例取值，任何对照使用的数值仅示意、不代表你的环境。

### 「峰值能到多少，链路就能承诺多少」

- **场景**：验收报告或容量规划里写「这条链路可以跑 X」，X 取自带宽测试输出里的 `BW peak` 列，或者取自一次单点测试里最好看的一行。
- **常见误判**：把「整轮测量里最好的一段窗口」当作持续能力。它看起来成立的原因在于这一列的名字里就有「峰值」，而且在大消息段它与 `BW average` 常常接近，让人以为两列可以互换使用。
- **判据**：读同一行的 `BW peak` 与 `BW average`（两者都是这一轮测量的速率量，单位随列头，默认 `MiB/sec`，加 `--report_gbits` 之后为 `Gb/sec`）；`BW peak` 是整轮里最好的一段连续窗口折算出的带宽，`BW average` 是总字节数除以总耗时。判据是两者的差距：差距小说明这一轮读数稳定，差距大说明散布大，先排除测量环境的问题再谈链路；报数、写验收、对业务承诺一律用 `BW average`。与谁同看：同行的 `#iterations`。条件会变：迭代次数超过 20000 时，工具会打印一行警告并停用峰值计算（`-N, --noPeak` 同效），此时峰值列给出的是 0——把 0 当作「峰值很低」是又一层误读，峰值与平均值的对照只在峰值列有效时成立。
- **结论**：峰值回答「最好的一段能到多少」，平均值回答「这一轮平均到多少」；承诺与验收用平均值，峰值只用来判断散布。
- **出处**：perftest 源码中带宽报告函数（`print_report_bw`：峰值按滑动窗口在整轮测量中取最好一段）与迭代次数超过 20000 时停用峰值计算的处理；perftest 仓库 README 第 3 节（默认迭代次数与 `-N` 的用途）。

### 「algbw 更大，就报 algbw」

- **场景**：集合通信测试跑完，报告里抄了 `algbw` 一列；或者在集群扩容前后各测一次，用两次 `algbw` 的下降说明「扩容之后变慢了」。
- **常见误判**：把算法带宽当作可以跨规模比较的吞吐。它看起来成立的原因在于它是输出表里的第一列带宽，大消息段的数值也接近线速量级，而且在小 rank 数下两列差距最小——全部归约在 2 个 rank 时修正系数为 1，两列相等——最容易让人以为它们可以互换。
- **判据**：读同一行的 `algbw` 与 `busbw`（都是这一轮的速率量，单位是十进制 GB/s）；`algbw` 按数据量除以耗时直接算出，没有折算每个参与者实际进出的数据量，它的上限随 rank 数上升而下降，由修正系数决定（全部归约的系数是 2(n-1)/n，把系数乘回 `algbw` 才得到可以与硬件上限直接对照的 `busbw`）。因此 rank 数不同的两次读数只比 `busbw`。与谁同看：这一轮的 rank 总数（进程数乘以每进程的 GPU 数）与页脚的 `Avg bus bandwidth`（全部尺寸的 `busbw` 平均值）。条件会变：同一规模下两列同涨同落，用哪一列都不翻转结论；规模一变，`algbw` 的下降是公式决定的，不是退化——把它当退化，会去排查一条并没有变慢的链路。
- **结论**：报数用 `busbw`；`algbw` 只在同一 rank 数下使用，跨规模比较时它回答不了「快慢」。
- **出处**：nccl-tests 仓库 README 的 Performance 一节与源码中各集合操作的带宽计算式；nccl-tests 的 PERFORMANCE 文档（两个带宽的定义与修正系数）。

### 「双向读数除以二，就是单向能力」

- **场景**：为了省一轮测量，直接跑双向（`-b, --bidirectional`），把读数除以 2 当作单向带宽写进基线记录；或者反过来，把单向读数乘以 2 当作双向能力。
- **常见误判**：把双向读数当作两个方向能力的可除之和。它看起来成立的原因在于双向读数确实是两个方向的合成——每端测量自己发起的流量，测量结束后对端把结果报过来合并——在线路对称的直觉下，「合计除以二」近似成立；但两个方向的路径与对端处理可以不对称，合计值只反映两侧之和，弱的一侧被强的一侧掩盖，除以 2 得到的数不落在任何一侧上。
- **判据**：读单向与双向两组读数（都是这一轮的速率量，单位随列头）；双向测试里加 `--report-both` 可以把本端与对端的结果分成两张表分别报出，合并之前的两个方向各自的读数都在。判据是先把两个方向各自单独测过——各自成立之后，双向读数才有解释基础；否则双向读数只能说明合计是多少。与谁同看：两端各自的端口计数器增量（`port_xmit_data` 与 `port_rcv_data`，累计量，取两次读数之差）。条件会变：两个方向单独测出的读数只要不同，「合计除以二」就既不能当能力值、也不能当比较值；而两个方向读数不同的原因可以完全不在链路——对端的绑核与接收缓冲同样会把它拉低。
- **结论**：双向读数是两个方向之和，不是任一方向的能力；先分开测两个方向，再谈双向。
- **出处**：perftest 仓库 README 第 3 节 Notes on Testing Methodology（双向测试每端测量自己发起的流量、测量结束后由发起端合并）；源码 `src/write_bw.c` 与 `src/perftest_parameters.c`（合并时把对端结果相加；`--report-both` 把本端与对端结果分开报出）。

```bash
ib_write_bw -d <dev> -i 1 -b --report-both   # 验证：双向测试中本端与对端结果分开报出的两张表，弱的一侧不再被合计值掩盖
```

这条测量命令不改变任何配置，但会给链路加负载；输出数值随机型、驱动四元组与网卡固件变化，任何对照使用的数值仅示意、不代表你的环境。

### 「超过线速的读数，先怀疑工具或硬件」

- **场景**：记录里出现一个超过端口线速的带宽数字，例如 400 Gb/s 的单端口链路折算出两倍于线速的读数；第一反应是工具算错了，或者硬件出了异常。
- **常见误判**：把超过物理上限的读数当作测量异常。它看起来成立的原因在于测量误差通常表现为「略高或略低」，而工具确实可能被读错；但超过线速的读数几乎总是一个口径问题，来源只有几处：单位（`MiB/sec` 与 `Gb/sec` 之间隔着位与字节的 8 倍，再叠上二进制与十进制的进制差）、方向（双向读数是两个方向之和，天然可达单向线速的两倍）、范围（多链路合计可以超过单端口线速）、对照对象（机内路径的读数上限不是网卡线速）。
- **判据**：把读数与对照对象折到同一单位后相除。`MiB/sec` 与 `Gb/sec` 的换算有工具自己给出的系数：factor = 10^9/(2^20×8) ≈ 119.2，即 1 Gb/s 对应约 119.2 MiB/sec，反向折算时 1 MiB/sec 约合 8.39 Mb/s；集合通信的两列带宽是十进制 GB/s；线速取端口协商出的生效值（`ibv_devinfo -v` 的速率与宽度字段）。比值不超过 1 才可能是同口径的读数。比值明显大于 1 时按四步核对：折单位、看方向、看范围、看对照对象。与谁同看：这一轮的方向设置（默认单向）与读数所在的行。条件会变：把对照对象换成「该路径实际经过的那一段的上限」之后，超过单端口线速的读数可能完全正常——多链路合计就是这种情况，因此「超过线速」这个结论只在四项排除之后才成立。
- **结论**：超过线速的读数先核对口径，而不是先怀疑工具与硬件；四项排除之后仍超过，说明这个数字被记错了口径。
- **出处**：perftest 源码选项表中 `--report_gbits` 的换算说明；nccl-tests 源码中各集合操作的带宽计算式（十进制 GB/s）；verbs 手册页与 `ibv_devinfo` 手册页（端口速率与宽度字段）。

### 「带宽低，就是链路慢」

- **场景**：跨机复测的带宽只有端口线速的一半左右，链路检查（协商速率、计数器）都没有异常，于是结论写成「这条链路性能不达标」。
- **常见误判**：把「参数没有给够」读成「链路能力不足」。它看起来成立的原因在于读数确实低，而且低得稳定、可复现，符合「能力不足」的表现；但在途字节数不足时，实测带宽由「在途字节数 ÷ 往返时延」决定，而不是由链路速率决定，瓶颈是队列深度这个参数。
- **判据**：反推在途字节数——用实测带宽乘以往返时延，得到维持这个带宽所需的在途字节数，再与「队列深度 × 消息大小」对照（队列深度由 `-t, --tx-depth` 设定，带宽测试默认 128；队列对数由 `-q, --qp` 设定，默认 1；往返时延取小消息的实测值，注意写延迟读数报出的是一半往返时延，取值时乘 2）；判据是两者是否同量级。与谁同看：同一轮的消息大小与延迟读数的分位值。条件会变：两者同量级且加大队列深度或加大消息之后带宽上升，说明瓶颈在参数而不在链路；反过来，所需在途字节数远小于队列容量而带宽仍低，就要转向 MTU 生效值、链路协商速率与亲和绑定，而不是继续加队列深度。
- **结论**：低带宽在归因到链路之前，先完成一次在途字节数的反推；「链路慢」与「参数没给够」用这一步分开。
- **出处**：perftest 源码选项表（`-t/--tx-depth` 与 `-q/--qp` 的语义与默认值）；Mellanox《RDMA Aware Networks Programming User Manual》的未完成工作请求定义（在途请求数的语义）。

### 「同样的命令，读数却不同，说明链路不稳」

- **场景**：变更窗口前后各测一次带宽，两次记录里的命令逐字相同，读数却相差一成以上；两次之间唯一没写进记录的差异是测试进程绑在了不同的 NUMA 域（或没绑）。结论写成「链路不稳定」。
- **常见误判**：把测量环境的差异当作链路行为。它看起来成立的原因在于命令文本相同，且两次读数的差异稳定出现；而绑核不在命令里——它写在包住命令的 `numactl` 调用或调度器的默认行为里，两次测量「看起来相同」，实际取值不同。
- **判据**：读两轮的亲和取值（`numactl` 的 `--cpunodebind` 与 `--membind` 指定的域号，域号取拓扑矩阵的亲和列），以及延迟读数的分位值（`99% percentile` 一类，单位微秒）；判据是两轮使用同一个域，且该域是出线网卡所在的域。亲和变化有一个特征组合：均值几乎不变而分位值显著变差。与谁同看：两轮的命令与参数逐项对照、同一轮里 `BW peak` 与 `BW average` 的差距。条件会变：两轮亲和相同而差值仍在时，把其余变量逐项核对——消息大小、队列深度、单双向、GPU 序号——差值在变量对齐之前不构成结论，不要在「链路不稳」上继续加测。
- **结论**：命令文本相同不等于环境相同；绑核这类不在命令里的取值，必须随读数一起记录并逐轮核对。
- **出处**：`numactl(8)` 手册页（`--cpunodebind` 与 `--membind` 的语义）；NVIDIA System Management Interface 文档的拓扑一节（亲和列的取法）。

### 「点对点的读数可以回答集合通信的问题」

- **场景**：业务问「这套集群的集合通信带宽是多少」，回答里给的是点对点带宽测试的单连接读数；或者反过来，用集合通信测试的读数去评价单张网卡的能力。
- **常见误判**：把一段路径的能力当作整条链的表现，或反过来。它看起来成立的原因在于两类读数单位接近、量级接近，都叫「带宽」，且在大消息段两者确实接近，让人以为它们可以互相换算。
- **判据**：把问题与工具的覆盖范围对齐——点对点工具的读数包含一次操作从提交到完成的全部硬件段（两端内存或显存、两端 PCIe、两端端口与线缆），但不含通信库的选路与算法，它不认识 rank、不组成集合通信组；集合通信读数从调用开始计时，把选路、算法与协议一起算进同一个时间数字。判据是问题属于哪一段：网卡这一段的能力用点对点读数回答，一次集合通信的表现用集合通信读数回答。与谁同看：两者对照时，点对点读数是网络段的上限，端到端读数与它的差额落在哪一段，再用机内段的上限逐段定位。条件会变：单机档与双机档的读数不能外推到多机——rank 数一上来，选路与轨道的作用就进来了；多机读数也不能反过来当单张网卡的能力值，多链路合计与单端口线速是两个对象。
- **结论**：读数的覆盖范围与问题的范围必须一致；「网卡能跑多少」与「这次集合通信多快」是两份读数回答的两个问题。
- **出处**：perftest 仓库 README 第 1 节 Overview（直接调用 verbs 接口、不经过通信库）；nccl-tests 仓库 README（集合通信测试的覆盖范围与运行方式）。

### 「旧读数还能当新版本的参照」

- **场景**：半年前归档的读数与这次新采集的读数放在一起比较，得出结论「新机器更慢」；或者刚变更过驱动、固件，就用变更前的读数判断「变慢了」。两次的机型、命令与参数看起来完全一致。
- **常见误判**：把读数当作与版本无关的量。它看起来成立的原因在于硬件型号相同、命令相同、参数相同，数字理应可比；而一批默认值（超时、地址选择、拥塞控制路线）与特性开关由驱动、CUDA、集合通信库、RDMA 栈四项版本与网卡固件共同决定，同一个命令在两套版本下的行为可以不同——四元组或固件一变，旧读数的口径就不在了。
- **判据**：读两份记录的版本四元组（驱动、CUDA、集合通信库、RDMA 栈）与网卡固件版本，以及各自的采集时间；判据是四项与固件全部一致时两份读数才直接可比。与谁同看：变更记录。条件会变：变更恰好动了四元组或固件时，复测的参照必须是变更后重新采集的读数，而不是变更前的那一份；如果变更动的是硬件型号（GPU 或网卡换代），那已经不是「变慢」的问题，而是重新建立基线的问题——旧数字在这两种情况下都不能继续充当参照。
- **结论**：四元组与固件是读数的组成部分；换过其中任何一项之后，旧读数不再构成参照，必须重测。
- **出处**：NVIDIA CUDA Compatibility 文档（驱动与 CUDA 之间的约束方向）；NVIDIA Driver Installation Guide（驱动包内模块与固件的配对）；NCCL User Guide 的环境变量一页（默认值随版本变化的例子）。

## 值班口径

这十条可以归成三类共同成因。

第一类是读数归属未经确认。命令跑通只说明工具在某个设备上工作过，不说明测的是报告里那张网卡；输出表的列名与单位与硬件环境一致，不说明被测设备是硬件实现；集合通信跑通，不说明它的读数能回答网卡这一段的问题。这一类误判的共同修正是把「测的是谁」变成一个可核对的读数：设备与网络设备的对应关系、端口计数器在测量期间的差值、两类工具各自的覆盖范围——三者里缺任何一项，数字就不属于任何对象，之后的一切比较都建在错误的对象上。

第二类是把多列输出里的某一列当作整份结论。同一行里有峰值与平均值，同一张表里有算法带宽与总线带宽，同一轮里有单向与双向，同一个数字有两种单位——每一列回答的是不同的问题，选错列不是精度问题，而是问题被换掉了。这一类误判的兜底检查是与物理上限对照：把读数折到与对照对象同一单位之后与线速相除，比值不超过 1 才可能是同口径的读数；超过 1 时按四步核对——折单位、看方向、看范围、看对照对象。

第三类是决定读数的取值没有随读数一起记录。队列深度与在途字节数、亲和域、四元组与固件，这些取值都不写在命令正文里，却都能把结论翻过来；它们的共同特征是差值稳定、可复现，看起来像链路行为。修正只有一条：每一轮测量把这一轮的取值随读数一起记下，两次对照之前逐项对齐；对齐之前的差值不构成结论。

这十条的判据都落在主机侧的读数上；fabric 侧的拥塞形态与通信库的算法选择不是本篇负责的内容。

**第一反应不要做什么**：不要在没确认流量经过被测设备之前接受任何带宽读数；不要把软件模拟实现的读数写进任何性能记录；不要在峰值列被停用（显示为 0）或迭代次数不一致时比较峰值；不要用 `algbw` 报数或用它跨规模比较；不要把双向读数折半当单向能力；不要把超过线速的读数先交给工具或硬件；不要在队列深度与亲和没有对齐时把差值归因给链路；不要用点对点读数回答集合通信的问题；不要在四元组或固件换过之后沿用旧参照。正确的顺序是先把读数归属到设备与路径上，再把口径折到同一约定，最后才谈数值的多少与变化。
