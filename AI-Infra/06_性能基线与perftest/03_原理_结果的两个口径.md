# 结果的两个口径

同一次集合通信跑完，工具会同时给出两个带宽数字；两个数字都不是错的，但它们回答的是不同的问题——一个回答「这次操作实际花了多久」，另一个回答「硬件用到了多满」。带宽数字只有相对于各自的参照才有意义：参照选错，同一组读数会同时支持「链路没压满」与「硬件已经跑满」两个相反的结论。这类误判不来自测量误差，而来自把两个不同问题的答案放进同一张表里比大小。

## 两个数字各自是怎么算出来的

**算法带宽**（algorithm bandwidth，`algbw`）：这次操作的数据量除以耗时，`algbw = S / t`。S 是这次操作定义的数据量（字节），t 是这一轮迭代的平均耗时。它回答「按这个速度，同样大小的一次操作要花多久」，适合估算业务时间；但它没有折算集合通信里每个参与者实际进出的数据量，所以它的上限随 rank 数变化。

**总线带宽**（bus bandwidth，`busbw`）：算法带宽乘一个修正系数，`busbw = algbw × 系数`。系数只由集合操作的种类与 rank 数决定，与硬件无关；乘上它之后，数字可以与硬件上限直接对照，并且在不同 rank 数之间可比。

| 集合操作 | 修正系数 | 系数从哪来 |
| --- | --- | --- |
| 全部归约（AllReduce） | 2(n-1)/n | 归约散射与全收集两个阶段，每个 rank 各搬一遍 |
| 归约散射（ReduceScatter） | (n-1)/n | 只有归约阶段 |
| 全收集（AllGather） | (n-1)/n | 只有分发阶段 |
| 全交换（AlltoAll） | (n-1)/n | 每个 rank 向其余 n-1 个 rank 各发一份 |
| 广播（Broadcast） | 1 | 数据全部从根节点出去，瓶颈在根节点的出口 |
| 归约（Reduce） | 1 | 数据全部进根节点，瓶颈在根节点的入口 |

走查全部归约的系数是怎么来的：n 个 rank 组成环，每个 rank 手上的数组大小为 S，分块转发时每块大小 S/n。归约散射阶段每个 rank 依次转发 n-1 块，合计发出 (n-1)/n × S；全收集阶段再发出 (n-1)/n × S；两阶段合计 2(n-1)/n × S。设每个 rank 的链路单向带宽为 B，理想耗时 t = S × 2(n-1) / (n × B)，把 S/t 乘回 2(n-1)/n 就还原出 B——这就是总线带宽能与硬件上限对照的来源，也是系数里出现 2 的原因。

还有一处容易忽略的口径差异：各集合操作对 S 的定义并不相同，全收集与全交换把全部 rank 的合计数据量计入 S，全部归约按每个 rank 的数组大小计入。因此不同集合操作之间的 `algbw` 也不能直接比大小。

## algbw 随 rank 数上升而下降是正常的

把全部归约的修正系数反过来用，就是理论峰值算法带宽：它等于硬件峰值乘 n / (2(n-1))——2 个 rank 时等于硬件峰值，8 个 rank 时约为它的 0.57 倍，64 个 rank 时约为 0.51 倍，随 rank 数增大趋近一半。因此「这次比上次慢」不能只看 `algbw` 的下降：先核对两次的 rank 数是否相同；rank 数不同时，`algbw` 的下降是公式决定的，不是退化。

向业务方报数用 `busbw`：它与 rank 数无关，同一套硬件在不同规模下报出的数字可比。排障时两个都看：`algbw` 回答「这次操作花了多久」（由它反推耗时，t = S / algbw），`busbw` 回答「硬件用到了多满」。两个数字要成对记录——只留其中一个，事后无法还原另一个，因为还原需要的 rank 数不在读数里。

## 用 busbw 与这一段的上限对照：链路是否压满

线速（line rate）是链路在单方向上的理论最大速率，由链路协商速率给出。`busbw` 的对照对象不是「线速」这个抽象值，而是这条路径实际经过的那一段的上限：

- 跨机路径：对照网卡端口的单向线速；一块 GPU 挂多条链路参与同一次通信时，上限是这几条链路的合计；
- 机内路径：对照 NVLink 或 PCIe 的速率，而不是网卡线速。

判据是两分的：`busbw` 与该段上限同量级，说明这一段是瓶颈、且已接近压满；`busbw` 明显低于该段上限，要么这一段没有被压满（选路、队列深度、协议开销在限制），要么瓶颈根本在另一段。链路层的协议开销决定了实测低于线速是常态，能到多高由开销与消息大小共同决定，不要求读数贴着线速。

## 读数超过线速时，先核对口径

同一个带宽数字，三件工具用三种单位报：

| 单位 | 谁在用 | 定义 |
| --- | --- | --- |
| `Gb/sec` | perftest 加 `--report_gbits` 之后的带宽读数 | 10^9 比特每秒，折合 1.25 × 10^8 字节每秒 |
| `MiB/sec` | perftest 的默认带宽单位 | 2^20 字节每秒，即 1,048,576 字节每秒 |
| `GB/s` | 集合通信测试的两列带宽 | 10^9 字节每秒（十进制） |

把线速折成这两种字节单位各是多少，两个换算点：

| 线速 | 折合十进制字节速率 | 折合 perftest 默认单位 |
| --- | --- | --- |
| 100 Gb/s | 12.5 GB/s | ≈ 11,921 MiB/sec |
| 400 Gb/s | 50 GB/s | ≈ 47,684 MiB/sec |

两个换算点之外还有两条常用的互折：1 GB/s 等于 8 Gb/s；1 MiB/sec 约等于 8.39 Mb/s。注意同样写作「100」的两个读数——100 Gb/s 与 100 GB/s——相差 8 倍；位与字节的换算没有折进来时，任何比值都不可信。

反推判据：把实测读数与线速折到同一单位后相除，得到「相当于线速的多少倍」。比值不超过 1 才可能是同口径的读数；比值明显大于 1 时，按下面四步核对口径，而不是先怀疑硬件：

1. **折单位**：读数与线速是否折到了同一单位、同一进制、同一「位还是字节」的约定；
2. **看方向**：这一轮是不是双向——双向读数是两个方向之和，天然可以达到单向线速的两倍；
3. **看范围**：读数是单端口的，还是多链路合计的——合计值可以超过单端口线速；
4. **看对照对象**：拿来比的上限是不是这条路径实际经过的那一段——机内路径的读数是显存搬运，上限不是网卡线速。

四项都排除之后读数仍超过线速，说明这个数字被记错了口径，而不是硬件超出了物理上限。

**第一反应不要做什么**：不要把 `algbw` 的下降直接当成退化；不要把 `algbw` 当作 `busbw` 报给业务或写进验收；不要拿不同 rank 数下的 `algbw` 互相比较；不要在折到同一单位之前把读数与线速比大小；不要把双向读数与单向线速直接比；不要把「读数超过线速」先当成硬件异常。
