
集群有足够的 GPU 时间供作业使用，用户仍可能遇到长队、失败重做或训练变慢。前面五篇给的是设备侧和网络侧的局部证据，本篇把作业在各阶段的时间和结果用统一口径记成账本，再把运行阶段的变化对回设备与数据路径，回答“这段时间实际交付了多少有效工作”。

| --- | --- | ---: |
| 09:56:00 | VolcanoJob `J17` 已提交，进入统计范围。 | — |
| 09:59:00 | PodGroup 记录首次进入 `Inqueue`。 | 等待进队列 180 s |

## 集群指标必须指定时间窗与分母

下面三个问题使用不同分母，都要标明资源池、队列或作业类型，否则同一组数据按小作业数聚合和按 GPU 时间聚合，结论可能相差很大。

- **队列等待和失败率。** 按同一提交批次汇报提交至成组绑定或首步的分布，并单列仍在等待的作业及等待到当前的时长。对作业终态，假设日报以当天结束的作业为总体：完成 17 个、最终失败 3 个、用户取消 4 个，另有 6 个运行中。若约定取消和未结束都独立报告，则按已判成功或失败的 20 个计算，失败率为 `3/20 = 15%`。同一作业中曾失败后成功的尝试，计入尝试失败和重做账本，不能再当成一个失败的作业；终态定义需与记录结果的控制器和应用一致。
- **分配占比。** 以可分配整卡的时间积分为分母、已分配给容器的整卡时间为分子。教学池三节点共 24 张卡，在 300 秒内都可参与分配，分母为 `24 × 300 = 7,200 GPU·s`；`train-12` 占 12 卡全窗，另一作业占其余卡中的 4 卡共 150 秒，分子为 `12 × 300 + 4 × 150 = 4,200 GPU·s`，分配占比为 58.33%。待调度请求、共享名额和 MIG Profile 各有自己的库存，应保留对应口径；节点或设备被移出可分配池时，按实际时段调整分母。
- **有效进展。** 用相同运行阶段的全局完成步、样本数或令牌数除以墙钟时间，全局步只计一份。跨尝试时按应用实际保留的进度计算，并单列从最后可恢复检查点重做的步数。GPU 有分配、设备上有活动、用户收到有效结果，是三个可以独立变化的现象，不能用其中一个代替另外两个。

## 用同一作业的两个运行窗口解释变慢

以下为**教学记录**，均属于 `J17/R1`。GPU、Pod、Rank 和 VF 分配稳定，Rank 5 对应 `h2/P21/GPU-H2-A`。同步数据并行的批量、样本规格和预处理配置在两个窗口相同，计数只包含整组完成步，两窗都没有检查点写入和重试。应用记录使用同步后最大跨机误差 2 ms 的时钟；采样窗含起点、截至终点前。GPU 活动均值按等间隔的有效抓取样本统计，健康窗有 19 个有效样本，慢窗有 20 个。

| 同窗观测 | 10:10–10:15 | 10:20–10:25 |
| --- | ---: | ---: |
| 全局完成步数 | 300 | 200 |
| 作业分配 GPU 数 | 12 | 12 |
| `GPU-H2-A` 平均活动率 | 82% | 55% |
| `h2` RoCE 物理口 TX 平均（同一计数定义） | 60 Gb/s | 40 Gb/s |
| 已采集的 RoCE 端口/优先级上 CRC、PFC 和 ECN 增量 | 各为 0 | 各为 0 |
| `h2` 训练 NFS 挂载 READ 执行时间 p95（客户端逐请求记录） | 8 ms | 90 ms |
| NFS 服务端对应导出路径 | 读队列平稳 | 读队列增大 |

两窗都是 300 秒，进展从 `300/300 = 1.00 步/s` 变为 `200/300 ≈ 0.67 步/s`，按同一基准下降三分之一，而训练一直占着 12 卡。两窗的代表步在等长计算段内有相近活动时间时，仅把每步拉长到原来的 1.5 倍，就足以让约 82% 的活动率降到约 55%。端口平均发送速率同方向下降，也与每单位时间完成的步更少相符；要判断各自贡献，还得核对每步字节与其他流量。

## 在一个全局步内区分晚到与集合变慢

同步训练要求参与者合作完成集合操作。第 08、09 章区分过 CPU 提交和 GPU 工作完成，这里从两窗各选一条代表步，起点取上一步全局完成时点。按 `R1`、全局步、通信组和该步同一集合序号，取对应的输入就绪、应用抵达点和 GPU 侧完成点：抵达时间取本地前置已满足且调用到达记录点的时刻，完成时间取对应 GPU Stream 上确认操作完成的时刻。假设该步剩余开销稳定，且所选集合在步完成的关键路径上。 [NCCL 2.27.3 · CUDA Stream 与完成语义](https://docs.nvidia.com/deeplearning/nccl/archives/nccl_2273/user-guide/docs/usage/streams.html)

| 代表步相对起点 | 健康窗 | 慢窗 |
| --- | ---: | ---: |
| Rank 5 的输入准备好供本地计算使用 | 100 ms | 600 ms |
| 该次集合最早被一个进程抵达 | 780 ms | 780 ms |
| 该次集合被最后一个进程抵达（Rank 5） | 800 ms | 1,300 ms |
| 最晚的 GPU 集合完成时点 | 940 ms | 1,440 ms |
| 该步完成 | 1,000 ms | 1,500 ms |

最早到最晚抵达的跨度从 20 ms 增至 520 ms，而最晚抵达至最晚完成两段都约为 140 ms——这段余量允许集合在最晚抵达之前已经开始部分工作。结合 Rank 5 的输入晚了 500 ms、本地从输入就绪到抵达仍为 700 ms，以及同窗客户端读时延和服务端队列的同向变化，现有证据首先指向数据供给；它尚不足以把责任落到某块盘、某个存储网络跳点或某次元数据调用。

如果另一次观察到各 Rank 抵达跨度仍是约 20 ms，而最晚抵达到完成增加 500 ms，接着要检查集合运行期的实际路径、GPU 进度和网络排队。聚合端口计数的零增量只适用于已覆盖的指标、端口和窗口。用第 05 篇同字节、同拓扑的集合基线重测，可以回答空载重测是否正常；验证数据供给假设时，则在受控重跑中固定样本、批量、并行配置和预处理，提前准备相同输入，分别报告输入就绪、集合余量和步进变化。要继续定位到存储服务端，就对齐同一请求在客户端、网络和服务端的计时。

队列账本决定在何处解释启动等待，作业运行后进度账本给出观察目标，第 02 篇的身份映射确定取证对象，第 05 篇的基线提供可比较的条件。这些记录合在一起，才是一份能交给下一位操作者的状态说明，也是第 18 章故障定位的起点。
