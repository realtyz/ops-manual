# 排队、资源占用与作业进展

月底复盘会上，基础设施团队展示了一张漂亮报表：集群 GPU 分配率超过 `80%`，显卡温度和活动率都很高。可业务方却并不买账——训练团队抱怨排队动辄几十分钟、步时莫名掉速三分之一，推理团队则投诉高峰期首字延迟暴涨十倍、有效吞吐直接腰斩。

症结在于**“卡分出去了”不等于“卡在高效产出”**。前五篇建齐了硬件、身份、网络存储与分层基线。本篇把这些局部证据全部收束到业务交付账本上。

我们先拆分排队耗时与宏观指标分母。随后用**训练双窗口**和**在线推理双窗口**对照，演示如何在真实运行中一锤定音锁定主导瓶颈。

## 从提交到首个完成步的时间账本

在 [第 15 章](../15_从单个Pod放置到多卡作业调度/00_内容大纲.md) 和 [第 16 章](../16_Volcano的作业调度与队列管理/00_内容大纲.md) 中，多卡同步训练从提交到真正干活要跨越队列准入、成组绑定、节点交付和应用会合四道关卡。

为避免“排队慢”变成糊涂账，必须把每个交接里程碑记成时间账本。下表记录了 `train-12` 首轮尝试从 API 接收对象到完成第 1 个全局训练步的完整流转：

| 里程碑时刻 | 本阶段采信的控制面或应用证据 | 较上一阶段耗时 |
| --- | --- | ---: |
| `09:56:00` | VolcanoJob 提交成功，纳入统计起点 | — |
| `09:59:00` | PodGroup 首次进入 `Inqueue` 状态 | 等待入队 `180 s` |
| `10:00:00` | 3 个 worker Pod 全部绑定到节点（取最晚绑定时点） | 入队至成组绑定 `60 s` |
| `10:01:20` | 3 个 `trainer` 容器全部进入运行态（取最晚启动时点） | 绑定齐全至容器起齐 `80 s` |
| `10:02:00` | 训练应用上报第 1 个全局完成步 | 容器起齐至首步完成 `40 s` |

按这套里程碑拆账，整段启动耗时与排队拆解非常直观：

$$
T_{\text{排队}} = 180\text{ s（入队前）} + 60\text{ s（入队至成组绑定）} = 240\text{ s}, \qquad
T_{\text{端到端首步}} = 240 + 80 + 40 = 360\text{ s}
$$

把 `240 s` 进一步拆成 `180 s` 和 `60 s` 极具排障价值：前者指向队列配额不足或优先级靠后，后者指向集群资源碎片或拓扑约束导致迟迟放不下去。

还要注意两点统计细节。一是后两段按整组最晚里程碑记账，先绑定的 Pod 可能已经提前拉起容器，局部阶段存在重叠。二是若平台靠定期轮询捕获状态变更，账本里应同步注明轮询间隔误差。

## 集群核算的三把尺子：先定分母再算账

汇报集群运营质量时，队列失败率、资源分配占比与有效进展分别使用不同分母。动笔前必须先锁死**资源池范围、统计时间窗与分母口径**，否则同一份数据能算出截然相反的结论：

- **作业失败率（终态口径）**：假设某资源池当日终结作业中，成功 `17` 个、最终失败 `3` 个、用户主动取消 `4` 个，另有 `6` 个仍在运行。约定将取消与运行中单列汇报后，已决终态共 `20` 个，作业失败率为：

$$
\text{作业失败率} = \frac{3}{17 + 3} = 15\%
$$

  若某作业中途失败一次但重试后最终跑完，应把这次失败记入**尝试失败与重做账本**，不能重复计作失败作业。

- **GPU 分配占比（卡时积分口径）**：分子为已分配给容器的整卡时长，分母为可分配池总卡时。三节点共 `24` 张 H100 在 `300 s` 内全员在线，`train-12` 全窗占 `12` 卡，另一作业占其余 `4` 卡共 `150 s`：

$$
\text{GPU 分配占比} = \frac{12 \times 300 + 4 \times 150}{24 \times 300} = \frac{4,200\text{ GPU}\cdot\text{s}}{7,200\text{ GPU}\cdot\text{s}} \approx 58.33\%
$$

  当故障节点被摘除出可分配池时，分母需按实际离线时长扣减；MIG 实例与共享名额应按对应库存单独核算。

- **有效进展（Goodput）**：训练用相同运行阶段的全局完成步数或有效样本数除以墙钟时间，跨重试时须单列**从最后可恢复检查点重做的步数**；在线推理则用满足 SLO 约束的有效输出吞吐（tokens/s）衡量，剔除抢占重算浪费的算力。

> [!tip] 工程直觉：三件各自独立的事
> **GPU 已经分配出去**、**GPU 硬件上有活动**、**用户拿到了有效结果**，是三个完全可以独立变化的维度。运维报表必须把三者并排摆出来，绝不能拿高分配率或高 `GPU_UTIL` 替业务有效进展背书。

## 训练双窗口对照：区分“输入晚到”与“集合变慢”

现在对比 `train-12` 首轮尝试的两个相邻 5 分钟窗口。两窗内设备与 Rank 归属不变，批量和预处理配置完全一致，均无检查点写入与重试。跨机时钟误差不超过 `2 ms`（两窗分别采得 `19` 与 `20` 个有效活动率样本）：

| 同窗跨层观测项 | 健康窗（`10:10–10:15`） | 慢窗（`10:20–10:25`） |
| --- | ---: | ---: |
| 全局完成步数（`300 s` 窗内） | `300` 步（`1.00 步/s`） | `200` 步（`0.67 步/s`） |
| 作业占用 GPU 数 | `12` 卡 | `12` 卡 |
| `node-2` 目标卡平均 `GPU_UTIL` | `82%` | `55%` |
| `node-2` RoCE 物理口平均 TX | `60 Gb/s` | `40 Gb/s` |
| RoCE 端口 CRC / PFC / ECN 新增计数 | 全为 `0` | 全为 `0` |
| `node-2` NFS `READ` 执行耗时 p95 | `8 ms` | `90 ms` |
| NFS 服务端对应导出读队列 | 平稳 | 明显拉升 |

先做一层量级校验。慢窗步速从 `1.00 步/s` 降到 `0.67 步/s`，单步耗时拉长为原来的 `1.5` 倍。

只要单步真实计算时长未变，仅增加空等时间，就会把原本 `82%` 的平均活动率摊薄到 $82\% \div 1.5 \approx 54.7\%$。同时，网口平均发送速率也会同步降至 $60 \div 1.5 = 40\text{ Gb/s}$，各项读数完全自洽。

为了彻底排除“是不是跨机集合通信变慢”的嫌疑，我们从两窗各抽 1 个代表步，以上一步全局完成为 `0 ms` 起点，记录该步核心集合操作的抵达与 GPU Stream 完成时刻：

| 代表步相对起点（`0 ms`） | 健康窗 | 慢窗 | 差值拆解 |
| --- | ---: | ---: | --- |
| Rank 5 输入数据就绪 | `100 ms` | `600 ms` | 晚到 `+500 ms` |
| 该次集合**最早**抵达时刻 | `780 ms` | `780 ms` | 其他 Rank 未受影响 |
| 该次集合**最晚**抵达时刻（Rank 5） | `800 ms` | `1,300 ms` | 晚到 `+500 ms` |
| 最晚 GPU 集合完成时刻 | `940 ms` | `1,440 ms` | 整体顺延 `+500 ms` |
| 该步全局完成时刻 | `1,000 ms` | `1,500 ms` | 总步时 `+500 ms` |

把代表步切为**“抵达跨度”**和**“最晚抵达后完成余量”**两段，真凶立刻水落石出：

$$
\text{抵达跨度} = t_{\text{最晚抵达}} - t_{\text{最早抵达}}：\; 20\text{ ms} \longrightarrow 520\text{ ms} \quad (\text{增加 } 500\text{ ms})
$$

$$
\text{最晚抵达后余量} = t_{\text{最晚完成}} - t_{\text{最晚抵达}}：\; 140\text{ ms} \longrightarrow 140\text{ ms} \quad (\text{毫无变化})
$$

慢窗里，Rank 5 从输入就绪到本地算完依然只花了 `700 ms`。全员齐备后的集合收尾余量也稳稳保持在 `140 ms`。唯独输入就绪晚了整整 `500 ms`，与同窗 NFS p95 延迟从 `8 ms` 飙到 `90 ms`、服务端队列拉升严丝合缝。

反之，若某次慢窗里各 Rank 抵达跨度仍是 `20 ms`，而最晚抵达后的完成余量暴涨到 `640 ms`，问题就直接指向**集合执行期本身变慢**（如网络拥塞或硬件降频）。此时应立刻联动第 05 篇的空载 `all_reduce_perf` 基线与第 04 篇的交换机计数展开排查。

## 在线推理双窗口对照：分辨“纯排队饱和”与“KV 抢占雪崩”

把同样的双窗口对照法搬到在线大模型推理服务 `infer-svc-1`（单副本 4 卡 H100 TP=4，预分配 `90%` 显存池），能立刻揭开许多单看硬件面板根本看不懂的故障。

下午业务突然涌入一批超长上下文请求，下面是 `infer-svc-1` 在正常高峰窗（对照第 05 篇并发 `32` 甜点基线）与退化异常窗的跨层数据对比：

| 同窗跨层观测项（单副本 `infer-svc-1`） | 健康窗（`14:00–14:05`） | 退化窗（`14:15–14:20`） |
| --- | ---: | ---: |
| `DCGM_FI_DEV_FB_USED`（单卡显存占用） | `72 GiB (90%)` | `72 GiB (90%)` |
| `DCGM_FI_DEV_GPU_UTIL`（活动率） | `92%` | `96%` |
| `DCGM_FI_PROF_PIPE_TENSOR_ACTIVE` | `0.26` | `0.48` |
| `DCGM_FI_PROF_DRAM_ACTIVE` | `0.78` | `0.85` |
| `vllm:kv_cache_usage_perc`（KV 池水位） | `62%` | `99%` |
| `vllm:num_requests_waiting`（平均排队） | `0.5` | `18` |
| 抢占速率（`num_preemptions_total` 增量） | `0 次/min` | `42 次/min` |
| P99 首字延迟（TTFT） | `380 ms` | `4,200 ms` |
| P99 单 token 延迟（TPOT / ITL） | `28 ms` | `75 ms` |
| 有效输出吞吐（tokens/s） | `1,850 tokens/s` | `920 tokens/s` |

看懂这张对比表的关键，在于识破**虚高的底层算力利用率**：

- **只看 GPU 面板会被彻底误导**：显存纹丝不动停在 `90%`，`GPU_UTIL` 还从 `92%` 升到 `96%`，连 `PIPE_TENSOR_ACTIVE` 都从 `0.26` 飙升到了 `0.48`——表面看机器反而比刚才“跑得更饱满”！
- **叠上引擎指标瞬间真相大白**：`kv_cache_usage_perc` 顶死 `99%`，每分钟发生 `42` 次请求抢占，大量生成到一半的请求被踢出显存并过一会儿重算 Prefill。
  - 正是这些**无效重复 Prefill** 把 `PIPE_TENSOR_ACTIVE` 虚高顶到 `0.48`，有效输出却从 `1,850` 砸到 `920 tokens/s`，P99 TTFT 暴涨超 10 倍！

如果换一种退化场景——**单纯短文本高并发排队（无 KV 抢占）**，监控指纹就会截然不同。

此时排队数 `num_requests_waiting` 同样上升、TTFT 变长，但 `kv_cache_usage_perc` 仍处在安全水位（如 `70%` 以下），`num_preemptions_total` 为 `0`。更重要的是，有效输出吞吐会稳稳顶在基线峰值（约 `1,850 tokens/s`），绝不会像抢占雪崩那样断崖腰斩。

在 Prometheus 里，可以直接用一组联动查询区分这两种在线退化态：

```promql
# 1. 有效生成吞吐（tokens/s）：观察是否出现“算力越忙、产出越低”的雪崩倒挂
sum by (pod) (rate(vllm:generation_tokens_total{pod=~"infer-svc-1.*"}[1m]))

# 2. 抢占告警探针：KV 池水位超 92% 且开始出现抢占，立即触发限流或扩容
(vllm:kv_cache_usage_perc{pod=~"infer-svc-1.*"} > 0.92)
  and on (pod) (rate(vllm:num_preemptions_total{pod=~"infer-svc-1.*"}[1m]) > 0)
```

> [!warning] 常见误区：切忌拿抢占重算期的 `Tensor Active` 当“算力优化成果”
> 就像同步训练里重复回滚重做的步数不能算有效进度一样，在线推理里被 KV 抢占反复重算的 Prefill 同样是纯损耗。无论训练还是推理，**最终验收标准永远是单位时间交付给用户的有效进展（Goodput）与 SLO 达标率**。

> [!summary] 核心结论
> - **账本与分母**：队列账本拆分启动前等待，统一分母口径保证集群报表可比。
> - **训练双窗口**：用“抵达跨度 vs 集合余量”一刀切开数据供给晚到与集合通信变慢。
> - **推理双窗口**：用“KV 水位 + 抢占速率 + 有效吞吐”一刀切开正常排队饱和与 KV 抢占雪崩。
