# 第 17 章 把设备、网络与作业状态联系起来｜内容大纲

## 读者起点与学习目标

读者有 Linux 和 Kubernetes 基础。第 02—04 章建立了 Kernel、显存、驱动管理接口和 GPU–NIC 拓扑；第 05、08、09 章建立了 Rank、集合完成与数据等待；第 06—08 章建立了 RDMA、RoCE 与集合吞吐；第 10—14 章建立了 UUID、PodResources、Operator、VF 与 MIG 实例；第 15、16 章建立了队列、成组放置、会合与重试。本章把这些局部证据组织成带时间、带身份、带条件的观测体系。第 18 章用本章的基线和时间线做故障定位，第 19 章用同类材料验收交付与变更。

1. 从一条 GPU 样本说明 NVML、`nvidia-smi`、DCGM、DCGM Exporter 与 Prometheus 各自是什么、位于哪一层、由谁调用，区分瞬时值与累计计数、设备采样时间与抓取时间，并正确判读缺测。
2. 根据带时间戳的设备清单、PodResources 分配、Kubernetes 对象和应用 Rank 记录，把 GPU 或 MIG 观测还原到当时的实体、Pod、尝试与 Rank，指出重建、实例复用和共享策略下的归因边界。
3. 读出 GPU 活动、显存、时钟、功耗、PCIe、NVLink、ECC 与 Xid 字段的单位、分母和计数生命周期，并用同负载对照解释一次降速或错误增量能支持什么结论。
4. 把 VF、物理端口、交换机队列和存储客户端/服务端计数对到同一次运行的时间窗，复算端口速率，说明时钟精度和计数范围怎样约束结论。
5. 从物理链路、单机卡间、跨节点 RDMA 到十二卡集合通信建立分层基线，复算端口名义速率、RDMA 载荷速率、`algbw` 与 `busbw`，判定两条记录能否直接比较。
6. 用统一的时间窗和分母核算排队、失败率、资源分配占比与有效进展，在同一作业的两个窗口中检验 GPU、网络与数据供给的候选解释，并提出下一项能区分它们的观测。

## 案例与适用条件

- 主例沿用第 16 章 Volcano 作业 `ai-demo/train-12`，作业 UID 短写 `J17`，初次尝试 `R1`。三只 worker Pod 分驻 `h1/h2/h3`，每只请求 4 张 H100 80 GB 整卡、16 CPU、96 GiB 主机内存和 1 个支持 RDMA 的 SR-IOV VF；每节点可供请求 8 GPU、32 CPU、192 GiB 内存和 2 VF。节点内 H100 SXM 经 NVSwitch 互通，每节点一条 200 Gb/s RoCEv2 物理口承载作业 RDMA 流量，存储走独立网络。日志确认 `h1/h2/h3` 分别承载 Rank 0–3、4–7、8–11，重点跟踪 `h2/P21/Rank 5/GPU-H2-A`。MIG、背景流量与重试均为明确标记的独立变体。
- 管理与分配以 Kubernetes v1.36、Volcano v1.16.0、GPU Operator v26.7.2 的 ClusterPolicy 与 Device Plugin 路径、DCGM 4.6.1、DCGM Exporter 4.8.4（镜像标签 `4.6.1-4.8.4-distroless`）为阅读口径。训练与基线以 PyTorch 2.9、NCCL 2.27.3、nccl-tests v2.17.9、perftest 26.07.8、nvbandwidth v0.11.0 为资料口径。驱动、CUDA、固件与工具构建随实测记录另注。 [GPU Operator v26.7.2 Helm 值](https://raw.githubusercontent.com/NVIDIA/gpu-operator/v26.7.2/deployments/gpu-operator/values.yaml) · [Exporter 4.8.4 发布记录](https://github.com/NVIDIA/dcgm-exporter/releases/tag/4.8.4)
- 采样、日志、库存、时间和基准数字均为教学构造，未在 GPU 或 Kubernetes 集群实测。流程与身份关系用 Mermaid，精确数值用表格。五幅手绘插画已验收并入库，提示词、图注与替代文本集中在 [配图说明](_配图/配图说明.md)。
