# AI-Infra 分章节写作与审查方法论

这份方法论整理了本项目从范围确认、大纲设计到第 01 章写作、审查、修订和配图的经验，供后续章节写作与维护使用。

质量判断围绕三个问题展开：**知识是否准确，理解过程是否连续，读者学完后能否独立解释和推导。** 文件数量、篇幅、图表数量和命令数量都不能替代这些判断。

[学习大纲](00_学习大纲.md)规定全书的范围、顺序与各章任务；本文件规定怎样组织解释、准备材料、审查和完成修订。用户后续明确调整的目标与约束优先于既有约定。将本方法用于其他领域时，应先重新确定读者、范围和学习条件，再沿用工作方法。

## 一、已经完成的工作与形成的经验

### 从定位到第一章修订

| 已完成的工作 | 形成的结果 | 后续应沿用的经验 |
| --- | --- | --- |
| 确认读者与内容范围 | 以已有 Linux/Kubernetes 基础的 GPU 集群运维读者为对象，聚焦 NVIDIA 与 Kubernetes 基础设施 | 开始写作前确定边界，防止内容随工具和产品名称无限扩张 |
| 设计学习大纲 | 四个阶段：单机工作、多机协同、Kubernetes 管理、集群运维；规划 20 章 | 按知识依赖建立学习顺序，章节共同服务于整体理解 |
| 确定目录形式 | 每章一个目录，导读加按自然问题拆分的正文 | 目录承担组织，篇目随主题产生，不预设统一篇数 |
| 完成第 01 章 | 从整机组成到拓扑、平台形态、管理与设施、集群连接，再进入综合材料分析 | 使用持续发展的场景把知识连接起来 |
| 进行八个方面的审查 | 找到图示语义、概念铺垫、输出解读、内存解释和练习覆盖等问题 | 完成初稿后，需要按读者能否理解和应用重新审视正文 |
| 逐项修订并复核 | 修正图示，补充基础机制与教学输出，增加正向推导练习，精简重复说明 | 修复一个局部问题后，继续检查它对其他篇目、例子和术语的影响 |

第 01 章当前提供导读与六篇正文，包含五幅 Mermaid 图，并已补充十幅生成配图。这个数量记录了本章成果，不规定后续章节的构成。可从[第 01 章导读](01_从一台GPU服务器认识基础设施/00_导读.md)阅读实例。

本轮完成了文字内容审查、相关官方资料核对、设备与数值一致性复核，以及本地链接、代码块和 Mermaid 分组结构检查。这些工作不等同于图示已在所有阅读器中正确渲染，也不等同于 GPU 实机验证。

### 将具体修订转化为通用规则

| 第 01 章暴露的问题 | 修订方式 | 可以迁移的规则 |
| --- | --- | --- |
| SXM 图把底板画成传输路径中的节点 | 用范围框容纳器件，单独画实际连接 | 包含关系、连接关系与数据流要使用清楚的图形语义 |
| 直接介绍 PCIe 交换结构，却缺少 Lane、代际和宽度铺垫 | 补入支撑当前分析的最小概念集 | 当前推导依赖的知识，必须在读者到达该位置时已经具备 |
| 只有观测命令，没有输出到结论的过程 | 加入多份教学输出，演示身份与位置映射 | 工具名称与命令需要和证据解释连接起来 |
| 主机内存只讲容量，缺少通道与带宽关系 | 补充控制器、通道、DIMM 及同容量布局对比 | 解释资源时，同时关注容量、访问路径与供给能力 |
| 练习偏重判断信息不足 | 增加条件充分的路径、辨识和计算题 | 学习应同时训练确定结论与识别结论边界 |
| 重复声明材料非实测，部分引用难以定位 | 共性说明集中到导读，具体假设就近保留，细化引用 | 诚实说明材料性质，同时保持阅读连续性 |

## 二、内容边界：围绕读者需要掌握的基础设施

以下是本库已确认的约定，后续章节从这里起步。

| 维度 | 本库约定 |
| --- | --- |
| 读者前置 | 已有 Linux、容器与 Kubernetes 的相关基础；新出现的 GPU/AI 基础设施概念仍需解释 |
| 内容独立性 | 正文在 AI-Infra 内形成完整学习路径，不引用仓库其他主题目录来承担必要解释 |
| 硬件与加速生态 | NVIDIA GPU / CUDA 为主线，不扩展为其他加速硬件平台教程 |
| 上层范围 | Kubernetes 中与 GPU、网络、设备管理、共享隔离、作业调度和运维有关的生态，例如 Multus、Volcano |
| 负载知识 | 训练、推理和并行方式用于说明资源、通信、数据供给与运行行为；算法实现、模型效果和业务服务不进入主线 |
| 学习条件 | 无 GPU 实操环境，正文应通过图、配置、输出、日志和推演支持学习 |
| 内容组织 | 按知识依赖循序渐进，不采用统一的“原理 → 体系 → 实操 → 判例 → 治理”篇目分类 |

每个主题能否进入某章，先判断它是否帮助读者完成本章的解释或判断任务。例如，存储在这里要解释 GPU 的数据供给与等待原因；内容需要延伸到哪里，由这个任务决定。

通用 Linux/Kubernetes 机制可以用必要的短句唤起前置知识，然后解释它在 GPU 场景中的具体作用。不要因“已有前置基础”而跳过新设备、新字段或新约束的含义。

章间边界遵循“本章讲足当前理解需要的部分，主责章节展开细节”。后文将讲某项机制，不能成为当前解释缺失的理由；但当前读者用不到的源码、全部参数和产品变体，也不必提前展开。

历史总览中的旧定位若与本目录的新大纲冲突，应按当前大纲及用户已经确认的边界工作。调整主题范围或章节顺序时，应同步相关导航与说明。

## 三、写作前先确定本章的学习任务

开始正文前，形成一份简短的写作计划。它可以存在于工作记录中，无需为每章额外创建流程文件，也无需在用户已明确任务时重复请求确认。

| 要确定的内容 | 合格的表达 |
| --- | --- |
| 学习任务 | 用“解释、辨认、画出、关联、推导、判断”等动作描述读者学完能做什么 |
| 前置知识 | 哪些来自用户已有基础，哪些来自前章，哪些必须在本章第一次建立 |
| 内容归属 | 本章需要讲完整的机制、为衔接而简述的机制，以及后文详细展开的部分 |
| 知识顺序 | 后一个问题需要前面哪些概念；是否存在提前使用尚未解释术语的情况 |
| 支撑材料 | 哪些图、配置、输出、日志或计算能够帮助完成这些学习任务 |

“了解某组件”通常太宽泛。可以写成“能说明它接收什么信息、改变什么状态、与哪些组件协作，并从一段状态材料判断当前停在哪一环”。这些是写作目标，不要求直接变成正文标题。

先列读者会依次遇到的问题，再决定章节内的篇目。例如，设备分配主题可以从“应用如何表达需求”走向“平台如何分配”和“设备如何出现在运行环境中”；通信主题则可以从“为什么要交换数据”走向“数据经过哪里”和“等待发生在哪一步”。具体顺序由主题依赖决定。

## 四、知识深度：足以解释机制并推导结论

### 从名称推进到因果关系

核心概念应让读者逐步理解：对象是什么、为什么需要它、它如何工作、与什么协作、会产生什么可观察结果，以及结论在哪些条件下成立。

这组问题用于检查解释是否充分，不要求每个概念都设置六个小标题。讲述顺序可以从现象、结构或需求出发，最终把必要的因果关系接起来。

以共享链路为例，正文不能止于“存在带宽瓶颈”。需要先交代谁共享哪一段，再说明哪些传输经过那里，最后在给定方向、并发与有效容量时推导是否超出预算。具体例子见[PCIe 与 NUMA 篇](01_从一台GPU服务器认识基础设施/02_把设备放回PCIe与NUMA拓扑.md)。

### 深度由学习任务决定

| 内容层次 | 展开要求 |
| --- | --- |
| 支撑当前判断的核心机制 | 讲清对象关系、运行过程、因果与条件，配必要材料 |
| 读者已有的通用基础 | 简要唤起，重点讲本场景增加的约束与变化 |
| 后续章节主责的机制 | 当前给出足以继续阅读的解释，详细行为在主责章节展开 |
| 可选实现细节 | 当它能解释本章的重要差异、故障或设计取舍时再引入 |

没有实操环境不会降低机制深度。它改变的是学习材料与验证方式：让读者阅读完整证据和推导，而不是要求读者自行运行命令补齐缺失内容。

知识深度也体现在区分不同层次的陈述：资源容量、硬件能力、配置目标、当前状态和实际工作效果应分别说明。观察到其中一项，只能在已经解释的条件下推出其他项。

对肯定结论与不确定结论使用同样严格的条件要求。条件足够时应明确给出判断；条件不足时指出缺少哪项信息、它为什么影响结论，以及下一步获取它的用途。

## 五、目录与篇目：按照连续问题自然拆分

每章采用以下组织形式，名称与篇数由实际内容决定：

```text
AI-Infra/
├── 00_学习大纲.md
├── 写作方法论.md
└── NN_章节主题/
    ├── 00_导读.md
    ├── 01_第一个连续问题.md
    ├── 02_接下来需要理解的问题.md
    └── …
```

章负责一个完整主题，篇负责一个可以连续讲清的问题。短章可以只有一篇正文；复杂章节按依赖关系拆分。不要以固定字数或第一章的篇数决定拆分，也不要把一个因果过程硬拆成“原理篇”和“实例篇”，使读者不断跳转才能理解。

导读保持简短，说明本章任务、前置与前后衔接、阅读顺序，以及贯穿材料的基本约定。正文从导读继续推进，避免每篇重新介绍整章背景。

篇内可以同时出现机制解释、图解、配置与故障分析。材料出现的位置由读者此时的疑问决定：需要看清连接时放图，需要识别状态时给输出，需要比较时用表。

篇末可以用简短过渡说明下一个问题如何产生。已创建篇目使用有效链接；尚未写作的章节可以按章号和主题说明，避免创建失效链接。改变命名、拆篇或移篇后，同步导读、前后导航和已有交叉引用。

## 六、写作风格：让读者顺着解释前进

采用连贯的中文叙述，每段推进一个主要意思。优先把对象、动作和结果写清楚，再补充必要条件。列表适合并列信息与步骤，表格适合对照，长篇机制解释仍应通过段落连接。

新术语在第一次真正参与解释时说明含义。缩写、字段和相似名称尤其要分清：物理位置、逻辑编号、对象名称和资源分组可以使用相似数字，却未必指同一对象。后文沿用同一称呼；更换视角时明确映射。

陈述应具体到对象和关系。例如，“该机制能够提升性能”需要继续说明在哪个条件下减少了什么开销，代价是什么。缺少条件的泛化结论，不应靠“通常”“一般”“可能”等词来掩盖。

保持必要的边界说明，但控制它们的重复：

- 全章共同的教学性质、平台背景和未实测状态放在导读。
- 影响当前推导的前提就近写清，例如负载状态、方向、单位、设备支持或变更后的布局。
- 自拟输出和真实引文在使用位置清楚标注，独立阅读该段时也能辨认材料性质。
- 已经说明过的限制不反复另起一段；可以把条件直接写进结论。

第 01 章修订后，将“仅列出命令，提醒尚不能证明什么”改为“展示材料、建立映射、给出结论与适用条件”。后续应沿用这种积极解释的方式。

避免在正文中反复报告作者如何写作、用了哪些工具或准备如何审查。正文服务于读者学习，写作过程和验证结果放在交付说明中。

## 七、材料设计：无实机也能完成理解与推演

### 维护一套一致的示例条件

选择能支撑本章任务的最小场景，逐步增加必要信息。后续章节可以沿用既有场景，也可以建立新场景；第 01 章的双路四卡模型不自动适用于所有平台和功能。

写作过程中应维护设备身份、地址、编号、拓扑、容量、软件版本、单位和环境条件之间的对应。工作记录可以是一张简表，不要求单独建立数据库或配置文件。新增示例改变条件时，先声明变化，再展开推导。

数字计算必须统一口径。例如：总容量与单设备容量、单向与双向带宽、标称值与有效值、设备输出与整机输入、正常分担与故障状态，分别参与不同问题的计算。教学数字可以人为设定，但应合理、自洽且可复算。

### 清楚标明材料来源

| 材料类型 | 应说明的信息 |
| --- | --- |
| 官方资料摘录或整理 | 来源、适用平台/版本、删节与整理方式，保持原字段含义 |
| 教学示例 | 自拟性质、必要假设、占位值、省略行与人工注释 |
| 实测记录 | 实际环境、采集时间、操作条件、命令或测量方法以及观察到的结果 |

当前没有 GPU 实机环境时，依靠前两类材料完成正文。不能把模拟的输出、合理推演或引用的性能数字记成自己的实测结果。官方摘录也应控制篇幅，以自己的解释组织内容，保留支持关键判断的部分。

### 让命令、配置和证据连起来

围绕核心学习任务，提供一段能够从头读到结论的材料：操作或配置的目的、必要输入、相关输出、字段含义、字段之间的关系，以及推导结果。

无需给每条辅助命令配完整输出，也无需复制长配置。若本章要求读者读懂某类输出，就必须提供足够材料演示这种读法。概念章节若无需命令，也可以通过图、事件序列或计算完成同样的解释。

字段应与当前论点有关，人工删节要保留能支持判断的上下文。命令显示的编号与正文代号之间建立明确映射；配置片段说明改变了哪一环，必要时注明它只是片段及其成立前提。

### 单独审查图表的语义

画图前先确定表达的是物理连接、包含范围、数据路径、控制关系还是状态变化。一个图需要多种关系时，用范围框、线型或标签区分，并在图边说明。

范围框表示包含，连线表示连接，箭头表示已经定义的方向或步骤。将多个器件聚合为一个节点时，应说明聚合范围。省略细节可以降低阅读负担，但不能凭空增加中间设备、改变路径或暗示不存在的直连。

核对图与正文中的名称、数量、方向、父子关系和范围是否相同。Mermaid 语法、分组闭合与实际渲染属于不同检查；图能渲染也不证明技术关系正确。修订实例见[平台形态篇](01_从一台GPU服务器认识基础设施/03_PCIe卡_SXM_HGX与整机平台.md)。

### 按理解难点规划配图

**当前配图重设决定：旧生成图片全部作废，旧版配图方案与提示词停止执行。** 范围包括已经嵌入的正式图、待审候选和尚未生成的旧提示词；过去的验收、图数和插入计划均不作为新方案依据。后续每章从当前正文重新设计，不能逐张给旧图换皮或只替换风格前缀。旧文件保留作历史记录，处理对应章节时清理旧引用与占位说明；已有 Mermaid、表格和代码块按教学用途保留或调整。

本次提供的《容器文件视图与主机驱动挂载架构》和《GPU资源分配与Pod请求示意图》仅作为手绘风格与视觉解释参考，参考文件及现行要求见[配图规范](配图规范.md)。它们不自动成为正式配图，不将其中的对象、数量或布局复制到其他选题。

**每篇正文优先规划一张核心总结图。** 先从全文提炼最值得读者记住的一个主问题和一个核心结论，再选择支撑结论的少量关键关系，组织完整场景、整体加局部或并排对照，帮助读者在读完后整理认识、在复习时回忆全文。多个概念可以共同支撑同一结论；配图仍用于理解复杂或重要的知识点，不把整篇内容、全部名词或配置清单罗列到图片上。

核心总结图默认放在正文主要解释之后或篇末，图内保留必要短标签，完整前提和推导放在正文及图注。选图优先考虑容易混淆的边界、复杂路径、共享关系，以及只改变一个条件的前后对照。

一张核心总结图是默认安排，数量根据内容调整。流程类文章可由 Mermaid 承担总结；独立局部难点确需不同视觉解释时可补图，缺少合适视觉内容时可不新增生成图片。先通读整章，再逐篇记录“主问题、核心结论、总结图形式、与现有材料的分工”，偏离默认安排时说明原因。导读保持简短，练习答案图放在参考分析之后。正文内的 Mermaid、表格和代码块继续承担具体流程、精确数据与局部推导，避免与总结图重复。

选图时先区分流程表达与视觉解释。调用顺序、条件分支、对象引用、依赖和控制闭环优先使用 Mermaid 或表格；文生图优先解释空间分布、资源占用、形态差异、共享边界和整体到局部的机制。每份生成图方案都应回答：**改成普通方框箭头图，会丢掉什么关键教学信息？** 如果几乎不丢失，就不为它另生成一张美化流程图。图片中可以有箭头，关键是缓冲区位置、资源数量、层次剖面或对象细节是否真正参与解释。

“一图一问题”的问题可取自全文主线，允许用两三个互补视区共同支撑文章的核心结论；补充局部图则明确其额外解释作用。绘图对象应具有与其含义相符的形态，例如文件页、显存格阵、共享层面与设备占位；为每个流程节点加图标不算视觉解释。不能为了凑图数，把本来清楚的流程换成没有明确对应关系的工厂、水管等类比。

本项目采用“助手规划并提供提示词 → 用户在其他模型生成图片并放入待审目录 → 助手审查图片 → 合格图片入库并引用”的协作方式。写作时先确定候选配图，正文与教学条件稳定后交付完整提示词；正文完成、提示词完成、图片待生成和图片已嵌入应分别说明。

### 交付可单独使用的完整提示词

配图规划阶段可在章节内的 `_配图/配图说明.md` 中按正文篇目集中组织提示词，具体位置沿用项目已有约定；正式图片沿用章节现有图片目录。每幅图至少包含以下信息：

| 交付项 | 要求 |
| --- | --- |
| 图号与教学目的 | 使用稳定图号，注明核心总结图或补充局部图、主问题与核心结论，明确读者看完后能解释什么 |
| 表达方式与视觉价值 | 说明为何选生成图而非 Mermaid/表格，普通方框箭头会丢失什么信息，由哪种形态、空间或局部细节来承载 |
| 所属正文与插入位置 | 定位到小节和具体段落，附可在当前正文唯一定位的原句；说明与现有 Mermaid、表格及其他新图的分工 |
| 构图与图内文字 | 写清主体、视角、范围、分区、阅读顺序和留白，列出短标签及必要图例 |
| 内容与技术约束 | 写清必要对象、数量、编号、容量、单位、连接、方向，以及本图采用的假设、聚合和省略；禁止模型自行补出事实 |
| 完整提示词 | 将主问题与核心结论、统一风格、配色、构图、图内标签和技术约束写进同一代码块，可整块复制到其他模型使用 |
| 图注与替代文本 | 图注解释关系与适用条件，替代文本概括图中表达的内容，不在图内塞入完整正文 |
| 文件名与验收要点 | 给出候选和正式文件名，列出该图容易画错且需要逐项核对的地方 |

提示词的视觉要求统一采用[配图规范](配图规范.md)：暖白纸底、细记号笔手绘轮廓、清晰手写印刷体，以及低饱和彩铅/淡马克笔填色的说明式技术插画；CPU 与主机内存用蓝色，GPU 与显存用绿色，NIC 与网络设备用青色，BMC 与管理访问用紫色，普通结构用灰色，当前路径或约束用琥珀色，超额或阻断用柔和红色。具体色值、画布比例、文字和线条约定在配图规范中统一维护。根据内容选择剖面、局部放大、资源占位或观察窗口等构图，不把所有名词都画成相同的圆角框。每份完整提示词都要明确写入手绘线条、字体、填色、色值与排版要求，并在同一代码块中写全本图标签、技术约束和应避免的误画，不能只写“沿用统一风格”或要求用户手动拼接公共前缀。若提供参考图，说明仅参考笔触、字体、填色和视觉组织，本图对象、数量与关系仍以新提示词为准。

手绘质感不得牺牲技术精确性：中文标签采用端正、不连笔的手写印刷体；英文缩写、库名、路径和版本号采用清楚的等宽手写印刷体，准确保留大小写、数字与标点。边界、连线端点、格数与对照尺度应清晰，状态斜线和普通彩铅填色笔触要能区分，不能因手绘风格增加、遗漏或混淆对象。

构图应有清楚的阅读顺序、对象边界和留白，同类对象跨图保持一致。对照面板采用相同布局和尺度，仅改变当前问题需要改变的条件。图内使用必要的短标签；内容放不下时减少对象或拆图，不靠缩小文字容纳全部解释。

技术约束来自当前文章，不沿用不相干章节的设备编号、能力或性能数字。范围框、物理连线、数据流、控制关系和状态变化分别定义，避免模型自行补出中间设备、直连、合并容量或性能结论。简化硬件外观时说明它是教学示意，不将生成插图作为真实产品照片、实测截图或精确接线图。

### 配图验收只检查图片本身

收到图片后，逐张打开实际图片，先核对核心总结图是否呈现全文主问题与核心结论、补充局部图是否增加不同理解，再对照正文、提示词和验收要点检查：技术关系、对象数量与边界、图中文字、数值与单位、线型与箭头、图文一致性，以及图片自身的配色、布局和文字可读性。还要核对选题承诺的空间、资源或局部机制是否在画面中可见；若结果退化成名词方框和箭头，不能仅因文字正确就判为符合新配图目标。不能只凭文件存在或文件名匹配判断合格。

**无需打开 Obsidian 或其他阅读器检查嵌入后的显示效果；阅读器主题、窗口宽度、缩放和界面显示均不属于默认验收或完成条件。** 图片入库及引用仍维护正确的文件名、相对路径、图注和替代文本，不由此增加阅读器显示检查。

影响理解或技术准确性的问题，应指出图中具体位置、问题及修改方式，提供针对该图的修改提示词，保留已正确的内容。不影响理解的轻微风格偏差可以记录，不因此要求整批重做。验收与定稿期间保留原始候选，合格图片使用稳定正式文件名；制作阶段资料在完成后按项目约定管理。记录实际审查结论，未知的生成模型或版本不代填。正文修改涉及图中事实时，只复核受影响的图片。

### 练习同时训练推导与判断边界

章级练习应覆盖本章的关键学习目标，形式可以是画路径、读字段、比较配置、计算预算、解释状态或分析故障材料。不要为每篇强制配置同一题型和题量。

练习应包含条件充分时可得出明确结论的任务，也可以包含判断现有证据是否充分的任务。答案给出条件、步骤和结论，避免使用题目未提供、前文也未建立的隐藏假设。

完成一个示范后，可以只改变一个条件，让读者自己继续推导，再给出参考答案。综合材料与练习示例见[节点交接材料篇](01_从一台GPU服务器认识基础设施/06_读懂一份节点交接材料.md)。

## 八、技术资料与版本：让论断可以追溯

优先使用厂商文档、标准组织资料、项目官方文档及必要的源码。二手文章可以帮助发现问题，关键机制、支持性、默认值和兼容性应回到一手资料核对。

引用放在它支持的论断附近，直接指向相关页面或小节。核对来源是否确实支持当前句子，以及平台、版本、方向和条件是否相同。一个链接能够打开，只证明可访问，不能证明它支持结论。

对影响本章判断的版本与平台差异，在相关材料或导读中说明基线和核对日期。稳定机制不必重复列版本；版本敏感的行为不得只凭印象。`latest` 页面可能变化，关键结论尽量记录所用版本或章节名称，便于日后复查。

优先定位到 HTML 小节。锚点需要实际存在；没有稳定锚点时，链接到页面并写明小节名。引用 PDF 时给出文档版本及章节或页码，方便读者找到依据。资料相互冲突时先核对适用条件，未解决的分歧不写成确定结论。

## 九、审查与修订：先解决理解和事实，再处理文字

### 按八个方面审查

| 审查方面 | 需要回答的问题 | 发现问题后的主要动作 |
| --- | --- | --- |
| 章节定位与边界 | 是否完成大纲任务，与前后章分工是否合理 | 补齐缺项，调整越界内容，澄清归属 |
| 技术准确性 | 概念、机制、因果与适用条件是否成立 | 核对一手来源，修正错误和过度泛化 |
| 知识依赖与顺序 | 必要概念是否在使用前具备，阅读是否发生跳步 | 补最小前置解释，调整段落或篇目顺序 |
| 解释深度与完整性 | 能否从机制推导结论，是否只剩定义和提醒 | 补运行过程、因果与关键条件 |
| 跨篇连贯性 | 术语、示例与分工是否一致，是否重复或断裂 | 统一模型与称呼，补衔接，删除重复介绍 |
| 图表与示例 | 图形关系、字段、数字、单位和假设是否正确 | 改图、重算、补必要上下文 |
| 无环境学习有效性 | 现有材料是否足以完成学习与练习 | 补输出解读、完整推导与参考答案 |
| 表达、来源与维护性 | 是否清楚自然、可追溯、可导航和持续更新 | 精简语言，细化引用，修复导航与格式 |

审查先通读，判断理解过程是否完整；再核对事实、图示、输出和例子；最后处理语言、重复和文件结构。对已经清楚且有依据的内容，可以得出“未发现实质问题”，不为凑审查数量扩大范围。

### 审查意见写到可以修改

每条意见说明：**具体位置 → 问题 → 影响读者理解的方式 → 修改建议。** 技术性意见还应给出支持判断的依据；教学性意见应指出缺失的解释或材料。

例如，“拓扑图不够清楚”不足以指导修改；“底板被画成传输路径的中间节点，会让读者混淆包含与连接，应改成范围框并分别连接器件”就具备可执行性。

优先处理会导致错误理解、使关键推导无法完成、造成材料自相矛盾的问题；随后处理重复、篇幅和表达偏好。审查者需要区分事实错误、学习材料不足与可选改进，避免把个人排版偏好当作技术缺陷。

### 每条意见完成修订与复核

修订过程保留问题与修改位置的对应，可以用简短工作清单跟踪。某条意见不适用时，说明依据；不必机械接受缺少事实支撑的建议。

修改后重新走完受影响的阅读路径。例如，补了一个基础概念，应检查后文用词与例子；改了教学地址，应检查输出、图、题目与答案；变更功率口径，应重算相关正常和故障场景。

局部修改完成后，再检查整章的连贯性与范围。新增内容如果使某篇承担过多独立问题，可以自然拆分；如果只是同一推导所需的解释，则保持连续阅读。

## 十、后续章节的执行流程与完成标准

### 一次章节任务怎样推进

1. **读取当前依据。** 阅读大纲对应章节、本方法论、相关前章和已有目标文件，确认用户的最新要求。
2. **确定学习任务。** 写清目标、前置、归属与依赖顺序，选择足够简单的贯穿场景。
3. **准备事实与材料。** 核对关键来源与版本，建立示例对应关系，从当前整章正文逐篇提炼主问题与核心结论，优先规划一张核心总结图并选择表达工具，不继承已作废图单；准备需要的图、字段、输出和练习条件。
4. **完成连续正文与配图提示词。** 从读者的第一个问题推进到本章目标，按实际边界拆篇，完成后校准导读；正文与教学条件稳定后，按统一风格交付可单独使用的完整提示词。
5. **开展八方面审查。** 从结构到事实与材料，再到表达，形成具体问题清单。
6. **逐项修订。** 补解释、改图、修正例子或调整顺序，并检查对其他篇目的影响。
7. **完成适度验证。** 复核数值、身份映射、引用、导航与 Markdown 结构；已收到的生成配图只验收图片本身及其与正文的一致性，无需检查 Obsidian 或其他阅读器的显示效果，准确记录检查范围。
8. **同步并交付。** 更新大纲入口和章内导航，说明正文、提示词、图片生成与嵌入各自的状态，以及主要修订、实际验证范围和仍影响结论的未解决事项。

这是工作的推进顺序，不要求正文使用同名章节，也不强制生成八份过程文档。任务范围已明确时，应连续完成已授权的写作与修订；遇到会实质改变范围且现有依据无法判断的问题，再进行针对性确认。

若采用并行协作，先统一边界、术语、示例条件和文件分工；独立来源核对、不同文件的修订可以并行。整章应由一个负责人通读整合，避免各篇单独正确却相互冲突。

### 章节交付前的检查清单

- [ ] 大纲要求的核心任务已在正文中完成，必要前置没有被推给后文。
- [ ] 读者能够沿着解释理解机制，并在给定条件下完成本章要求的判断或推导。
- [ ] 关键事实有适用条件与来源，教学材料和实测材料可以明确区分。
- [ ] 术语、标识、拓扑、单位、计算、图表和答案相互一致。
- [ ] 各篇已按全文主问题与核心结论优先规划一张核心总结图，数量或形式的例外已说明；未沿用作废的图单或提示词，生成图有明确视觉价值及完整提示词，包含统一手绘风格、配色、构图、短标签、内容约束、图注和验收要点。
- [ ] 已收到的配图已检查图片本身；待生成或待修改的图片如实标明，不把 Obsidian 显示检查作为交付条件。
- [ ] 无实机读者拥有完成核心阅读任务所需的材料与反馈。
- [ ] 审查中影响理解和准确性的问题已解决，剩余问题有明确说明。
- [ ] 大纲、导读、前后篇与交叉引用能正确导航，文件和图示结构已检查。
- [ ] 交付说明与实际完成的工作一致，没有把结构检查写成渲染验证或实机验证。

检查通过的依据应来自正文与实际核对。仅有标题、占位段落、资料链接或“以后补充”的关键解释，不能作为完成章节的依据。审查是为了达到学习目标，无需在没有新变化或未解问题时反复进行相同检查。
