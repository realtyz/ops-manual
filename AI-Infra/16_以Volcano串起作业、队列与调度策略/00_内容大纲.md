# 16 以 Volcano 串起作业、队列与调度策略

## 范围、前置知识与读者目标

- **范围**　先认识 Volcano 的 API 对象、组件职责和调度器配置，再沿一个固定规模的多机多卡作业，解释入队与成组放置这两个基本决策。用同一规格的作业加深到资源借用、公平排序、装箱、抢占和回收，接着处理失败后的重试、恢复和资源释放。最后用 Kueue 对照配额、准入和 Pod 放置的分工，并介绍 JobSet 与 Kubeflow Trainer 的作业组织接口。
- **前置知识**　读者能读 Pod 的资源请求和标签，知道调度器决定 Pod 放在哪个节点、kubelet 在节点上启动容器。反亲和在逐节点放置时补齐，Rank、World Size 和 Rendezvous 在训练进程启动时解释。第 15 章的资源放置原理作为背景，案例提供可独立复算的配置与库存。
- **读完能独立解释**　给定 VolcanoJob YAML，能画出 Job、Task、Pod、PodGroup、Queue 的关系，指出谁接收请求、谁创建成员、谁判断入队和成组、谁绑定 Pod，以及应用何时能开始训练。
- **读完能独立判断**　给定队列账面、节点余量与对象状态，能判断作业卡在 API、入队、成组放置、节点启动还是应用组队，给出能区分原因的下一条证据。能算清队列额度和可放副本数，判断配置变更动到队列上限、借用归还、作业顺序还是节点评分。看到成员重启时，能检查资源何时可再次分配，以及应用从哪里恢复。
- **跨章分工**　设备与网络交付留给第 11—14 章，节点内 NUMA 和拓扑放置原理留给第 15 章。第 17、18 章接手指标关联、NCCL 和跨层故障处置。Volcano 分层队列、HyperNode、多集群与平台部署作为延伸入口。训练算法和 checkpoint 的分布式实现保持在案例所需的接口层。

## 版本与贯穿案例

- **版本基线**　以 Volcano v1.16.0、Kubernetes v1.36 为主例，Volcano 发布说明确认支持 v1.36、构建依赖 v1.36.1。以对应版本的 Helm 调度配置为对照，单独注明教学例修改过的 actions、plugins 和权重。PodGroup 指 `scheduling.volcano.sh/v1beta1` 对象，集群的原生 Workload/PodGroup 走另一套 API，主例无需开启原生特性。Kueue 取 v0.17 系列，与第 15 章一致，字段以 v1beta2 参考为准，安装文档要求 Kubernetes v1.29 及以上。 [Volcano v1.16.0 发布说明](https://github.com/volcano-sh/volcano/releases/tag/v1.16.0) · [v1.16.0 Helm 调度配置](https://github.com/volcano-sh/volcano/blob/v1.16.0/installer/helm/chart/volcano/config/volcano-scheduler.conf) · [Kueue v0.17 安装要求](https://kueue.sigs.k8s.io/v0.17/docs/installation/) · [Kueue v0.17 v1beta2 API](https://kueue.sigs.k8s.io/v0.17/docs/reference/kueue.v1beta2/)
- **作业**　延续第 15 章的规格，先看一个 worker 模板，再读三个副本的完整请求。每个 worker Pod 请求 4 张 H100 80 GB 整卡、16 CPU、96 GiB 主机内存、1 个 RDMA VF，完整作业申请 12 GPU、48 CPU、288 GiB 主机内存和 3 个 VF。每个 Pod 启动 4 个训练进程，共 12 个 Rank。假定设备插件已发布 `nvidia.com/gpu` 与教学资源名 `example.com/rdma-vf`。
- **环境**　使用平级队列 `train` 和 `batch`、互通的三台同型节点 `h1/h2/h3`。单节点的 Allocatable 为 8 GPU、32 CPU、192 GiB 主机内存和 2 VF。各节在首次使用时给出队列字段、节点余量和应用启动参数。除非单独说明，两个队列均为 Open，CPU、主机内存和 VF 能容纳相应 Pod。抢占、回收和装箱使用单独列明初始条件的变体。
- **材料口径**　库存、资源变化和训练步数是教学假设。状态摘录采用版本对应的 API 字段，观测表标注对象、组件和采集时点。引用实测时附集群版本、调度配置、设备环境与采集来源。

## 第一篇　Volcano 对象、组件与调度配置

### 01 VolcanoJob、Task、PodGroup 与 Queue

- **问题与预期结论**　配置里只有一个 `worker` Task，为什么会产生三个 Pod？读者应能从 API 组辨认 VolcanoJob，从模板与副本数算出资源请求，并说明 PodGroup 怎样把成员与 Queue 关联起来。
- **解释顺序**　从读者熟悉的 Pod 模板出发，把一份模板放进 `tasks[]`，用 1 个副本说明映射，再把同一模板扩到 3 个副本。引入 VolcanoJob 作为用户提交的作业规格、PodGroup 作为调度器识别成组成员和最低规模的对象、Queue 作为多个作业共享资源的管理对象。主例用命名空间内的 Job 与 PodGroup 和集群级 Queue。组件怎样写入对象和状态在第 02 节讲，队列容量和成组算法分别在第 04、05 节讲。

### 02 Admission、Controller 与 Scheduler 的职责

- **问题与预期结论**　API Server 接受 Job 后，哪些组件继续处理对象？读者应能根据对象缺失或状态未推进的位置，指出需要查看的组件。
- **解释顺序**　沿一次提交跟踪 API Server 调用 Volcano Admission webhook 做默认化与校验、Job Controller 创建 PodGroup 并在调度放行后尝试创建 Pod、Queue Controller 维护队列状态、Scheduler 观察对象并按调度配置推进，最后交给 kubelet 启动容器。对照 API 接受与 Scheduler 入队两个时点。Webhook 证书和部署交给运维背景，放行与绑定的判定留到第二篇。
- **支撑材料**　用 Mermaid 时序图画出 API 请求、对象生成、入队、Pod 创建和绑定的交接点。用生成的 PodGroup 和 Pod 的 `metadata.ownerReferences` 验证归属，用 Job `spec.schedulerName: volcano` 和 Pod `spec.schedulerName` 检查调度器选择。架构文档提供组件分工，标签源码确认默认化和控制器的写入条件。 [Volcano v1.16 架构](https://volcano.sh/docs/v1.16.0/home/architecture/) · [v1.16.0 Job 默认化 webhook](https://github.com/volcano-sh/volcano/blob/v1.16.0/pkg/webhooks/admission/jobs/mutate/mutate_job.go) · [v1.16.0 Job Controller](https://github.com/volcano-sh/volcano/blob/v1.16.0/pkg/controllers/job/job_controller_actions.go)

### 03 Scheduler 调度周期与 actions、tiers、plugins

- **问题与预期结论**　看到 scheduler ConfigMap 时，怎样判断哪些调度步骤会运行、由哪些策略参与？读者应能从 `actions` 找到执行次序，从 `tiers` 找到已注册的插件及其调用顺序依据。
- **解释顺序**　先说明调度器以 session 执行配置的 actions，再用 `enqueue` 与 `allocate` 分别说明入队和放置发生在哪一步。引入插件给 action 提供判定或评分逻辑的关系，选 `capacity`、`predicates`、`gang` 举例，先识别各自参与的决策，具体字段和算例留到第二篇。队列排序、装箱、抢占和回收在第三篇逐项接回这里的配置。

## 第二篇　入队、成组放置与启动

### 04 Queue 容量与 enqueue 入队

- **问题与预期结论**　创建请求成功，节点明明有空卡，为什么还没有 worker？读者应能区分请求未被 API 接受、控制器尚未生成 PodGroup、PodGroup 等待入队以及控制器创建成员失败，并判断该查哪个组件。
- **解释顺序**　先用 `capability` 定义队列使用上限。确认 Job 与 PodGroup 已存在后，跟踪 `enqueue` 调用 `capacity` 检查队列是否开放、PodGroup 的最低资源请求、已分配和在途用量。开始时 `train` 的两个旧 Pod 分别在 `h1`、`h2`，各用 4 GPU，节点余量 `4 / 4 / 8` 足以放三个 worker，队列账面 `8 + 12 = 20 > 16`，PodGroup 留在 Pending。等 `h1` 的旧 Pod 退出并归账后，`4 + 12 = 16`，PodGroup 进入 Inqueue，控制器尝试创建三个 Pod。已入队却没看到 Pod 时查控制器创建错误和 API 事件。应得份额与专属保留留到第 06 节。
- **支撑材料**　用 `kubectl get jobs.batch.volcano.sh`、`kubectl get podgroups.scheduling.volcano.sh` 和 `kubectl get queues.scheduling.volcano.sh` 的 YAML 摘录，对照 Job `.status.state.phase`、PodGroup `.status.phase` 和 `.status.conditions`、Queue `.status.state`、`.status.allocated` 和 `.spec.capability`。队列计算假设无其他在途需求，正文对照源码交代在途用量也可能影响入队。关注 PodGroup 事件的报告组件、`reason` 与 `note`，用源码中队列配额不足的事件路径和插件日志里的作业名、队列名、拒绝条件验证判断。 [Volcano v1.16 Actions](https://volcano.sh/docs/v1.16.0/scheduler/actions/) · [v1.16.0 enqueue 源码](https://github.com/volcano-sh/volcano/blob/v1.16.0/pkg/scheduler/actions/enqueue/enqueue.go) · [v1.16.0 capacity 源码](https://github.com/volcano-sh/volcano/blob/v1.16.0/pkg/scheduler/plugins/capacity/capacity.go) · [v1.16.0 Job Controller 的 Pod 创建条件](https://github.com/volcano-sh/volcano/blob/v1.16.0/pkg/controllers/job/job_controller_actions.go)

### 05 allocate、Gang 成组放置与 Pod 启动

- **问题与预期结论**　队列已放行，三台节点合计还有 14 张空卡，为什么连能单独放下的两个 worker 也要等？读者应能判断 gang 门槛是否满足，并区分成组放置、容器启动与训练进程组队。
- **解释顺序**　承接三个 worker 已创建的状态。先走 `allocate` 的节点筛选与评分，用标签限定同型节点，用匹配本作业标签的硬反亲和限定每节点最多 1 个 worker。再讲 gang 怎样检查暂选方案是否达到 `minMember`。此时 `batch` 在 `h3` 用 6 GPU，余量 `8 / 4 / 2` 只能放 2 个，等 `h3` 释放 2 GPU 后，`8 / 4 / 4` 才够放 3 个。随后跟踪 Pod 绑定、kubelet 启动和 Rendezvous，用 `torchrun --nnodes=3 --nproc-per-node=4` 解释三个 worker 和十二个 Rank 的关系。将成组门槛降为 2 时，调度器可推进两成员方案，固定规模的应用仍等第三个节点。镜像、设备和网络的详细故障留给第 18 章，多角色最低成员数只标明 `minTaskMember` 配置入口。
- **支撑材料**　用三节点逐行余量表和随条件变化的状态摘录。验收路径依次看 PodGroup `.status.conditions` 的类型、原因和消息，Pod `.spec.nodeName`、`PodScheduled` 和 `.status.containerStatuses[].state`，最后看启动器的 Rendezvous 标识、节点数及组队后的 `WORLD_SIZE=12`。用 `svc` 插件生成的 Headless Service 作为可选的端点材料，解释服务发现怎样为应用组队提供地址。 [Volcano v1.16 Gang](https://volcano.sh/docs/v1.16.0/scheduler/plugins/gang/) · [v1.16.0 allocate 源码](https://github.com/volcano-sh/volcano/blob/v1.16.0/pkg/scheduler/actions/allocate/allocate.go) · [Volcano v1.16 PodGroup](https://volcano.sh/docs/v1.16.0/concepts/podgroup/) · [SVC 插件](https://volcano.sh/docs/v1.16.0/userguide/user_guide_how_to_use_svc_plugin/) · [PyTorch 2.14 torchrun](https://docs.pytorch.org/docs/2.14/elastic/run.html)

## 第三篇　资源分配与调度策略

### 06 Queue 应得份额、专属保留与资源借用

- **问题与预期结论**　队列配置了 12 张卡的应得份额，为什么能用到 16 张？读者应能依据队列上限、应得份额、专属保留及实际需求，区分还能用多少和已借用了多少。
- **解释顺序**　从第 04 节的 `capability` 扩到 `deserved` 与 `guarantee.resource`。先在另一队列空闲时算可借空间，再给另一队列加入需求，算出超出应得份额的用量。比较 `capacity` 显式配置份额与 `proportion` 按 `weight` 动态推导份额，两者择一配置。超额部分何时可被收回及如何选 Pod 留到第 09 节，分层队列作为延伸。
- **支撑材料**　列出三台节点的 24 GPU 总量，以及两个平级队列的关键字段。`train` 和 `batch` 的 `deserved` 都是 12 GPU，`capability` 分别为 16 和 24 GPU，主例省略 `guarantee`。当 `batch` 用 16 GPU 时，超出应得份额 4 GPU。当 `train` 用 16 GPU 时，还同时达到自身上限。在空池变体中为 `train` 保留 4 GPU，用源码中的有效上限计算推导 `batch` 最多可用 `min(24, 24 − 4) = 20` GPU，再按节点余量核算能放几个副本。 [Volcano v1.16 Queue](https://volcano.sh/docs/v1.16.0/concepts/queue/) · [队列资源管理](https://volcano.sh/docs/v1.16.0/keyfeatures/queueresourcemanagement/) · [Capacity 配置指南](https://volcano.sh/docs/v1.16.0/userguide/user_guide_how_to_use_capacity_plugin/) · [v1.16.0 capacity 源码](https://github.com/volcano-sh/volcano/blob/v1.16.0/pkg/scheduler/plugins/capacity/capacity.go)

### 07 Priority 优先级与 DRF 公平排序

- **问题与预期结论**　两个作业各占 4 GPU，但 CPU 用量不同，为什么 DRF 可能优先考虑其中一个？读者应能算主导资源占比，并用调度配置判断优先级和公平排序各在何时生效。
- **解释顺序**　先区分按队列选择和队列内作业排序，再从已分配量占集群资源的比例推导 DRF 的主导份额。先固定同队列、同优先级，比较两个作业的份额。再改变其中一个作业的 `PriorityClass`，跟踪配置中的排序回调和 tier 顺序，解释为何实际先后需要同时看插件配置。驱逐已运行 Pod 的条件留到第 09 节。
- **支撑材料**　同一池的总资源取 24 GPU、96 CPU。两项作业分别已分配 `4 GPU + 16 CPU` 与 `4 GPU + 32 CPU`，假定其余资源占比均不超过各自的主导占比，算得 `max(4/24, 16/96) = 1/6` 与 `max(4/24, 32/96) = 1/3`。给出 `priority`、`drf` 的配置项和实际优先级字段，把 DRF 算例和配置中的排序次序对上。 [Priority 插件](https://volcano.sh/docs/v1.16.0/scheduler/plugins/priority/) · [DRF 插件](https://volcano.sh/docs/v1.16.0/scheduler/plugins/drf/) · [调度器配置指南](https://volcano.sh/docs/v1.16.0/userguide/user_guide_how_to_configure_scheduler/)

### 08 Binpack 节点评分与 GPU 碎片

- **问题与预期结论**　GPU 总余量相同，小 Pod 的放置为什么会改变大作业可用的机器数？读者应能定位 binpack 影响的打分环节，说明提高 GPU 权重能改善哪种碎片，并能指出仍需验证的硬约束。
- **解释顺序**　先让 predicates 筛掉放不下单 Pod 的节点，再比较 binpack 对合格节点的评分和其他评分项的权重。用相同的旧 Pod 数和总余量比较分散与集中，再让三个固定 worker 来选。GPU 紧凑配置只有在 CPU、内存、VF 与节点规则仍允许时才有效，已经分散的旧 Pod 需要等退出或经过单独的迁移策略才能改变布局。
- **支撑材料**　单独从空池放置 15 个单卡小 Pod，使用主例的三台 8 卡节点，假定其他资源充足。分散布局占用 `5 / 5 / 5`，余量 `3 / 3 / 3`。另一种紧凑布局占用 `8 / 7 / 0`，余量 `0 / 1 / 8`。这两种布局均无法运行主例的三个 4 卡 worker，但后者为 8 卡 Pod 保留了整节点。另用 9 个单卡 Pod 对照 `3 / 3 / 3` 和 `8 / 1 / 0` 的占用，验证紧凑布局可能只剩 2 个可放 4 卡 worker 的节点，而分散布局留下 3 个。用两例解释评分目标应与后续作业形状匹配。摘录 `binpack.weight`、`binpack.resources`、`binpack.resources.nvidia.com/gpu`，表格采用假设布局，逐列标出卡余量及通过每节点 1 worker 限制后的计数。 [Volcano v1.16 Binpack](https://volcano.sh/docs/v1.16.0/scheduler/plugins/binpack/) · [调度器配置指南](https://volcano.sh/docs/v1.16.0/userguide/user_guide_how_to_configure_scheduler/)

### 09 preempt 同队列抢占与 reclaim 跨队列回收

- **问题与预期结论**　急作业缺一个节点时，占用方可能是同队列的低优先级作业，也可能是借用了空闲份额的其他队列。读者应能根据请求方与占用方的队列关系，判断该检查哪条路径、需要满足哪些条件、释放后能否凑齐整组。
- **解释顺序**　先确认 PodGroup 已过入队门槛，逐节点找出缺口。沿第 07 节的优先级解释同队列的 `preempt`，沿第 06 节的借用与保留解释跨队列的 `reclaim`。检查 action 是否启用、请求方和受害者的准入与资格、队列 `reclaimable`、受害作业的成组约束及驱逐后的整组可放性。分开观察候选驱逐、Pod 退出与可再次分配的时点。对照第 04 节被 `enqueue` 挡住的作业，说明没有待调度成员时，此路径可能无法触发。

### 10 作业重试、Checkpoint 恢复与资源释放
