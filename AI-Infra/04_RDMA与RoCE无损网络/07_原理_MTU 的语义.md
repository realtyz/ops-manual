# MTU 的语义

交换机上已经按巨帧（jumbo frame）配置过端口，主机侧也按同一份规划核对过，验收时大消息仍然异常；追问下去，得到的回答常常是「网卡报告的 MTU 上限是 4096，所以这条链路就是在用巨帧」。这个结论并不成立，因为同一段输出里有两个字段：一个声明的是端口能力上限，另一个才是此刻生效值，而后者还必须与 IP 侧的网络设备 MTU 一起换算才算对得上。若把上限当成生效值，验收就会停在「配置看起来都对」这一步，现场那种「小消息正常、大消息异常」的分尺寸现象仍然无法解释，而下一步的动作也无法确定落在主机侧还是交换机侧。

## 两个字段不是一件事

`max_mtu` 是端口声明的能力上限，它说明这块网卡与它的固件支持到哪一档；`active_mtu` 是端口此刻生效的值，也就是这条链路上实际使用的报文承载上限。两者混读会产生两类方向相反的错误结论：用 `max_mtu` 判断「这条链路已经用上巨帧」，以及用 `active_mtu` 判断「硬件的上限只有这么高」。因此凡是涉及 MTU 的判断，判据一律取 `active_mtu`，而 `max_mtu` 只用来回答「还能不能往上调」。

官方 `ibv_devinfo` 的输出示例里同时出现 `max_mtu: 4096` 与 `active_mtu: 1024`。这两个数值仅示意、不代表你的环境，且随机型、驱动四元组与网卡固件版本而变化。该示例之所以出现这种组合，原因是那台机器的 IP 侧网络设备 MTU 还是默认的 1500，因此 RDMA 侧只能取到 1024。单独看 `max_mtu` 就会得出「已经支持巨帧」这个错误结论，而这个结论一旦写进交付文档，后续所有关于大消息异常的排查都会从错误的前提出发。

巨帧在主机侧不是一个可以单独打开的开关，它在主机侧的落地形态就是网络设备 MTU，以及由它推导出来的 `active_mtu`。因此「交换机已经按巨帧配置」这句话在主机侧能够核对的只有两个数：本机网络设备 MTU 与 `active_mtu`。只有这两个数之间的换算成立、并且两端一致，才能说这条链路的报文承载上限按规划生效；否则「配了巨帧」只是一句关于交换机侧的声明，它不能代替主机侧的读数。

## 生效值怎么算出来

本节这条换算只适用于以太网承载的 RoCE 端口：此时端口的生效值由本机网络设备 MTU 推导，规则是「不超过网络设备 MTU 的最大 2 的幂」。它的机制是端口生效值取「能力上限」与「由网络设备 MTU 推出的档位」两者中较小的一个，因此既受网络设备 MTU 限制，也受端口自身档位上限限制。换成 InfiniBand 承载的端口，这个值来自 fabric 侧为这条路径协商出的结果，不由本机网络设备 MTU 推导，本节这条换算不适用。由于网络设备 MTU 是任意整数，而生效值只能是 2 的幂，因此这一项是一组离散的档位，从 256 到 4096，而不是一个可以任意填写的数字。这句话决定了 MTU 的判据形态：它不是「这个值看起来够不够大」，而是「换算关系成不成立」。

官方给出的两个换算是：网络设备 MTU 为 1500 时，`active_mtu` 为 1024；网络设备 MTU 为 4200 时，`active_mtu` 为 4096。因此 1500 这个常见的默认值对应的并不是 1500，而是它下面最大的 2 的幂 1024；这也是「交换机配了巨帧、主机侧却仍在小报文档位」这类不一致的常见来源。

把常见的网络设备 MTU 取值按这条规则算一遍（1500 与 4200 两行是官方换算点，其余按同一规则推导）：

| 网络设备 MTU（字节） | 不超过它的最大 2 的幂 | `active_mtu` 应为 | 反推判据 |
| --- | --- | --- | --- |
| 1500 | 1024 | 1024 | 读到 `active_mtu` 为 1024 时，先核对网络设备 MTU 是否仍在默认值 |
| 2048 | 2048 | 2048 | 网络设备 MTU 本身是 2 的幂时，两者相等 |
| 4096 | 4096 | 4096 | 同上 |
| 4200 | 4096 | 4096 | 巨帧规划的常见取值，`active_mtu` 已到端口档位上限 |
| 9000 | 4096 | 4096 | 网络设备 MTU 再大，`active_mtu` 也不超过 4096 这一档 |

反推同样成立：`active_mtu` 为 4096 时，网络设备 MTU 至少是 4096；`active_mtu` 为 1024 时，网络设备 MTU 落在 1024 到 2047 之间。

若 `active_mtu` 与网络设备 MTU 之间不满足这条换算关系，处置顺序是先查网络设备 MTU，再查交换机侧。网络设备 MTU 属于本机可以自己确认的一项，交换机侧那一跳的 MTU 属于网络团队负责的范围；主机侧能够提供的是一份自己的读数，用于两侧对账，而不是单方面把本机的值改大。

读取入口在两侧各有一个，必须一起看才有判据：

```bash
# 验证：RDMA 侧端口声明的上限与此刻生效的 MTU；数值以现场输出为准
ibv_devinfo -v
```

```bash
# 验证：该网络设备的 IP 侧 MTU；与同一端的 active_mtu 按「不超过它的最大 2 的幂」互相校验
ip link show <if>
```

这两项都是只读观测，在生产节点上也可以做。读法是：先用 `ip link show` 输出的 `mtu` 算出理论上应当生效的 2 的幂，再与 `ibv_devinfo -v` 输出的 `active_mtu` 对照。若两者一致，说明换算成立，MTU 这一项可以结案；若两者不一致，说明某一侧刚被改动过，或者中间还有一层没有纳入这次核对，此时先不要下结论，也不要用其中一个值去解释另一个值。

## 生效值不能单独指定

`active_mtu` 不是一个可以直接填写的参数，它是从网络设备 MTU 推导出来的结果：网络设备一侧给多少，RDMA 侧就取不超过它的最大 2 的幂。因此当规划要求提高这条链路的报文承载上限时，动作入口在网络设备 MTU 上，不在 RDMA 侧的某个字段上；反之，只改 RDMA 侧而不改网络设备侧在机制上不成立。

这一条推出一个排查上的结论：若两侧读数对不上，不要去纠正 `active_mtu` 本身，而要去找决定它的那个网络设备 MTU，并确认中间还有没有别的层参与。把 `active_mtu` 当成一个可以随意抬高的目标值，会让改动看起来生效而实际换算关系已经失衡。

## 读数成立的两个前提

在把 `active_mtu` 当作判据之前，要先确认它读得到、并且读到的值能被解释，这需要端口侧的两种情况成立：链路类型是 Ethernet，端口状态是活动状态。若链路类型不是 Ethernet，那么这套「不超过网络设备 MTU 的最大 2 的幂」的换算关系不适用；若端口不是活动状态，`active_mtu` 读到什么数值都不足以说明这条链路能用。

这一条决定的是顺序：端口状态不正常时，先把端口状态解决，MTU 的换算就不构成一个可判定的项。反过来说，只有当端口处于活动状态、链路类型是 Ethernet 时，`active_mtu` 与网络设备 MTU 的对照才有判据意义。

## 交换机侧那一段的划界

交换机端口上的 MTU 规划值与它的配置命令行不属于主机侧负责的内容。主机侧能够交付的证据只有三个读数：本机网络设备 MTU、`active_mtu`，以及按尺寸扫描的结果。两侧对账时把这三个读数与交换机侧给出的规划值对照；对照不成立时先确认以哪一侧为权威，再决定改哪一端，而不是在主机侧单方面把值改大。

## 一次验收要同时确认的几条判据

交付验收时只看一个点不足以结案，下面几条要一起确认，缺其中任意一条验收都不成立。

第一条是两端的 `active_mtu` 是否一致。不一致时的现场特征是分尺寸的，也就是小消息完全正常、大消息异常。

第二条是每一端的 `active_mtu` 与同一端网络设备 MTU 的换算是否成立。这一条不成立时，问题在本机配置或中间层，而不在两端配合上，处置方向随之不同。

第三条是按尺寸扫描是否出现分界。出现分界时先回到前两条，而不是先在应用侧调参数；由于扫描结果是测量值，它只能指出异常落在哪个尺寸区间，不能替代配置侧的对照。

第四条是把这一组读数与机型、驱动四元组、网卡固件版本一起记录。由于读数与这些因素强相关，只记下 MTU 数值而不记这些前提，下一次交付就无法判断两个数值是否可比；其中驱动四元组指驱动、CUDA、NCCL 与 RDMA 栈（发行版自带 in-box 或独立栈）四项，网卡固件版本与设备型号另列一行。

## 上限、生效值与瞬时读数的区别

这一组字段分属两种形态，混起来读会得到不存在的结论。`max_mtu` 是能力上限，它在设备与固件不变的前提下是一个稳定值；`active_mtu` 是此刻的生效值，它会随网络设备 MTU 的改动而变；`ip link show` 的 `mtu` 是 IP 侧当前的配置值，同样属于配置状态；而按尺寸扫描得到的带宽与延迟结果是测量结果，不是配置状态。因此判断「为什么大消息异常」时，前两项给出的是约束关系，测量结果给出的是现象落在哪个尺寸区间；把测量结果当成配置值去解释换算关系，或者用能力上限去解释测量结果，都不会得到可执行的下一步。

同时要分清的是对象：MTU 决定的是单个报文能承载多少有效载荷，而内存注册决定的是网卡能够直接访问哪一段内存。两者是两件事，不存在互相推算的关系；把 `max_mtu` 当成注册内存的上限来估算可注册容量，属于把两类对象混读。

## 两端不一致为什么只在大消息上暴露

若两端生效的 MTU 不同，现场特征是分尺寸的：小消息完全正常，大消息（例如一兆字节以上）才异常。原因是小消息不需要把报文填到承载上限，因而不会触碰到不一致的那一档；只有当消息长度超过较小一侧的承载能力时，问题才会出现。

MTU 决定的是单个报文能承载多少有效载荷，因此一条固定长度的消息在较小的 MTU 下会被切成更多的报文。这一点决定了判断方式：不能靠单次试验判定「异常是不是 MTU 引起的」，而要看一组按尺寸排列的读数——只有当异常集中在较大尺寸上、并且较小尺寸全部正常时，两端生效值不一致才是首选的解释。反之，若各个尺寸都同等异常，那么问题不在 MTU 这一项上，应转向其他环节。

因此交付验收必须扫全尺寸，只跑一个缺省尺寸不足以证明链路可用：缺省尺寸恰好落在正常区间时，验收会给出一个「通过」的错误结论。

perftest 的按尺寸扫描（`-a`）就是为这件事准备的入口，它把一系列消息尺寸逐个测一遍，从而把「小消息正常、大消息异常」这种组合直接暴露成一个分界点。判据是有没有分界，而不是某一个尺寸上的具体数值是否达到了某个期待值；分界出现时，回到两端 `active_mtu` 与两侧网络设备 MTU 的对照，而不是先在应用侧调参数。

## 改动生效值的代价与回滚

网络设备 MTU 的改动入口是 `ip link set dev <if> mtu <n>` 这样的形态：

```bash
# 验证：把该设备的 MTU 改到目标值，再按两侧读数与按尺寸扫描各复测一次；改动前先记录原值
ip link set dev <if> mtu <n>
```

这是破坏性动作，会牵动正在使用该网络设备的全部流量，影响范围是同一台机器上的全部作业，因此只在实验节点执行。回滚路径是：改动前记录原值，需要回退时把 MTU 改回原值，然后重新做一遍两侧读数对照与按尺寸扫描；只把配置值改回去而不复测，不能算完成回滚，因为两端是否仍一致只能由复测证明。若 `ip link show` 显示的 MTU 与交换机侧的规划值不一致，应当先与网络团队确认规划值再动手，而不是在主机侧先改一个看起来更大的值。

确认需要改动的场合，动作顺序是：先与网络团队确认规划值，再在实验节点上改本机的网络设备 MTU，改完按两端读数与按尺寸扫描各复测一次，最后把原值、改动值与复测结果连同四元组一起归档。跳过确认规划值会让改动方向失去依据，而跳过复测则无法证明两端仍然一致。

## 字段怎么读

| 字段 | 是什么与单位 | 判据 | 与谁同看 | 看到它转向哪一步 |
| --- | --- | --- | --- | --- |
| `max_mtu` | 端口声明的 MTU 能力上限，与 `active_mtu` 同为 2 的幂档位取值，范围从 256 到 4096 | 它只说明硬件与固件支持到哪一档，不是当前生效值 | 与同一输出里的 `active_mtu` 同看 | 只有它够大而 `active_mtu` 偏小时，转向网络设备 MTU 的检查，不要用它下结论 |
| `active_mtu` | 端口此刻生效的 MTU，2 的幂档位取值，范围从 256 到 4096，属于配置状态 | 它必须等于「不超过网络设备 MTU 的最大 2 的幂」 | 与 `max_mtu`、`ip link show` 输出的 `mtu` 同看 | 换算不成立时先查本机网络设备 MTU，再与网络团队核对交换机侧那一跳 |
| 网络设备 MTU | IP 侧该网络设备一次可承载的报文大小，单位是字节 | 按「不超过它的最大 2 的幂」推出应当生效的 `active_mtu` | 与 `active_mtu` 以及对端同一项同看 | 两端不一致时先对齐规划值，再决定改哪一端；改动只在实验节点做 |
| perftest 按尺寸扫描的结果 | 一组按消息尺寸排列的带宽与延迟读数，属于测量结果而非配置状态 | 是否存在「小尺寸正常、大尺寸异常」的分界 | 与两端 `active_mtu`、两侧网络设备 MTU 同看 | 出现分界时判定为两端生效 MTU 不一致，回到读数的换算对照 |

这张表的前三行是配置状态，读一次即可判断；第四行是测量结果，必须按尺寸整组看，不能只挑一个缺省尺寸。把第一行当成第二行是本项判断里最常见的错误，而把第四行当成配置值则会让后续动作失去落点。

本项判断上有三种错读会反复出现。第一种是把端口声明的能力上限当成此刻的生效值，由此得出「这条链路已经用上巨帧」。第二种是把 `active_mtu` 当成可以直接抬高的目标值，由此做出在机制上不成立的改动。第三种是把按尺寸扫描得到的读数当成配置状态，用它去解释换算关系。三种错读的共同后果是下一步动作失去落点：既不能确定问题在主机侧还是交换机侧，也不能确定要改的是网络设备 MTU 还是别的东西。

**第一反应不要做什么**：不要看到 `max_mtu` 是 4096 就断定这条链路在用巨帧，也不要在收到「大消息异常」的报告之后直接在主机侧把 MTU 改大。先把 `active_mtu` 与网络设备 MTU 的换算算一遍，再用按尺寸扫描确认异常出现在哪一档；只改一端会让两端不一致的表现变得更难判断，而验收本身也无法因此结案。
