# 高频误判

下面十条取自主机侧无损与地址选择两类真实处境，每一条按同一套字段展开：场景、常见误判以及它为什么看起来成立、判据、一句话结论、出处；其中判据一项固定交代读哪个字段、该字段是累计量还是瞬时量、期望的趋势是什么、需要与谁同看，以及哪些条件一旦改变结论就会翻转。

### 「链路 up、能 ping 通，所以 RDMA 可用」

- **场景**：交付验收或值班初判时，`ibv_devinfo` 输出中端口状态为活动、`link_layer` 为 `Ethernet`，同时对端能 ping 通，于是判定 RDMA 通道可用。
- **常见误判**：把链路层可达与三层可达当作 RDMA 数据面可用的证据。它看起来成立的原因在于这两项检查都返回成功，而 RoCE 的数据面完全由硬件卸载，RoCE 流量不经过内核网络栈，也不进入标准以太网接口的软件计数，因此这两项成功只覆盖了带外通道与链路层。
- **判据**：读 `/sys/class/infiniband/<device>/ports/<port>/counters/` 下端口计数器的增量，并把它与用 RDMA 语义的工具（收发测试工具集）实际跑通的结果一起看；这些计数器是累计量，因此判据是两次读数之差在业务运行期间持续增长，而不是某一次读数的绝对值；同看对象是作业侧的有效吞吐，二者不匹配时说明数据面并没有承担这份流量。条件会变：若作业走的是回退后的套接字路径，端口计数器可以长时间不增长，此时结论从「RDMA 正常」变为「作业通但不是走 RDMA 设备」。
- **结论**：链路 up 与 ping 通只证明带外通道与链路层正常，只有 RDMA 语义的工具跑通且端口计数器同步增长，才能证明流量确实经过了 RDMA 设备。
- **出处**：NVIDIA DOCA 文档中 RoCE 一章（数据面由硬件完全卸载、RoCE 流量计数器的取值位置）。

```bash
# 验证：端口计数器目录中的项名随驱动版本变化，先取本机项名，再隔一段时间取第二次做差
ls /sys/class/infiniband/<device>/ports/<port>/counters/
```

上面这条命令只用于确认本机实际存在的计数器项名；命令的输出项名与取值随机型、驱动四元组与网卡固件变化，因此这里不给出示例取值，任何对照使用的数值仅示意、不代表你的环境。

### 「配了 PFC 就是无损了」

- **场景**：主机侧按验收清单在网卡上使能了优先级流控，命令返回成功，于是认定这条链路的无损能力已经建立。
- **常见误判**：把主机侧命令执行成功当作全路径配置完成。它看起来成立的原因在于命令的返回只反映本端网卡接受了这项设置，而优先级流控必须在端点上和路径上的每一台交换机上都使能，本端成功只说明本端这一跳。
- **判据**：读 `mlnx_qos -i <if>` 的服务等级到优先级映射表、信任模式与按优先级逐位给出的使能状态，读 `ethtool -S` 中该优先级的反压计数是否出现（该优先级没有使能优先级流控时，按优先级的反压计数根本不可见，因此查不到本身是一个信息）；这些值是配置量与累计量的组合，判据是三者相互对齐且与路径上每一跳的使能状态一致。条件会变：两端都配对而路径中间某一跳没有使能时，压力不足的场景下读数一切正常，只有出现微突发才暴露，因此结论只在路径每一跳都有压测证据时才成立。
- **结论**：主机侧的使能成功只覆盖本端，无损是端点与路径每一跳共同成立的结论，缺任何一跳都不能称无损。
- **出处**：NVIDIA DOCA 文档中流控一章（优先级流控的使能范围与按优先级反压计数的可见条件）。

### 「pause 计数不为零就是有问题」

- **场景**：值班时看到按优先级的反压计数不为零，随即判定链路存在异常反压。
- **常见误判**：用绝对值代替趋势，并忽略反压与拥塞标记的分工。它看起来成立的原因在于这个计数器确实记录了停帧，但反压本身是无损机制的一部分，真正需要区分的是它以多快的速率增长，以及同一时间拥塞标记在做什么。
- **判据**：读 `ethtool -S` 中按优先级命名的反压计数（命名形如 `prioN_rx_pause`、`prioN_tx_pause`、`prioN_tx_pause_duration`、`prioN_rx_pause_transition`，其中编号随队列变化），以及厂商扩展计数器里的拥塞标记与拥塞通知包计数；它们都是累计量，判据是单位时间增量与「谁在涨、谁不涨」的组合，健康水位是标记在涨而反压几乎不涨。条件会变：反压几乎不涨而标记也不涨，说明当前压力不足以触发任何一档机制；反压持续快速增长而标记不涨，说明在拿反压承担全部拥塞，结论从「反压在工作」变为「反压是唯一的拥塞出口」。
- **结论**：反压计数是累计量，判据是增长率与方向，标记在涨而反压基本不涨才是健康组合。
- **出处**：NVIDIA DOCA 文档中流控一章（按优先级的停帧计数与拥塞标记的配合）。

### 「`tx_pause` 在涨就是本端在压上游」

- **场景**：看到发送方向的反压计数增长，于是判断本端正在对上游施加反压，并据此去找上游设备的配置。
- **常见误判**：把发送方向与接收方向的含义对调。它看起来成立的原因在于两个方向的计数确实都反映停帧行为，只是发起方不同：发送方向表示本端正在向对端发送停帧，接收方向表示本端正在被对端压住。
- **判据**：读带优先级前缀的两个方向计数。方向指暂停帧自身的进出：`tx` 方向上升说明本端发出了暂停帧、要求对端停发，它反映的是本端接收方向进来得多、排空得慢；`rx` 方向上升说明本端的发送被对端叫停，它反映的是对端接收侧在被灌满。两个方向各自指向一端的接收侧，都不是某一端的出口队列，因此不能由 `tx` 增长推出「本端出口拥塞」。两者都是累计量，判据是分别取增量并分别对应到发出暂停帧的一端与收到暂停帧的一端。条件会变：全局流控与按优先级的流控是两类不同对象，读数必须连同优先级前缀与是否使能该优先级一起解释，缺少前缀的读数不能直接用于归因。
- **结论**：方向不能反读，`rx` 表示本端被压住、`tx` 表示本端在发停帧，两个方向必须分开取增量。
- **出处**：NVIDIA DOCA 文档中流控一章（按优先级停帧计数的方向语义）。

### 「把信任模式改成按三层服务等级就够了」

- **场景**：发现标记没有生效，于是把网卡的信任模式改成按三层服务等级，认为这样标记就会落到预期的队列上。
- **常见误判**：把信任模式当成整条映射链的开关。它看起来成立的原因在于信任模式确实决定了网卡按哪一层字段取值，但取值之后还要经过映射到服务等级与优先级这一段，以及优先级流控使能到哪一个队列这一段，三段中任何一段不齐都不会得到预期结果。
- **判据**：读 `mlnx_qos -i <if>` 的信任模式、服务等级到优先级的映射表与使能无损的优先级，并读强制差分服务代码点的取值位置（全局取值写在流量类别文件里，按规则写法只在没有全局取值时才匹配源与目的地址）；判据是信任模式所选的那一层字段、映射表的目标优先级、以及使能无损的优先级三者指向同一个队列。条件会变：若映射表把标记指向了另一个优先级，改动信任模式只是把「标记不生效」变成「生效到别的队列」，此时结论从「已对齐」变为「对齐到了错误的队列」。
- **结论**：信任模式只让映射有机会生效，映射表与使能无损的优先级必须逐项对齐，只改其中一项不构成配置完成。
- **出处**：NVIDIA DOCA 文档中流控一章与 RoCE 一章的服务类型一节（信任模式、服务等级到优先级的映射与强制差分服务代码点的两级用法）。

### 「抄一个固定的 GID 索引」

- **场景**：从别的机器或旧文档抄来一个全局标识符索引，写进应用配置或环境变量，认为地址选择就此固定。
- **常见误判**：把索引当作与机器无关的不变量。它看起来成立的原因在于索引确实是一个整数，而且在那台出处的机器上工作正常；但全局标识符表按「地址乘以版本」展开，索引会随 VLAN 接口与 IP 地址的增减而漂移，而 GID 表又是每个 RDMA 端口各自一张，换端口就要重新读一遍。
- **判据**：读全局标识符表的三项——取值在 `gids/<index>`、类型在 `gid_attrs/types/<index>`、关联的网络设备在 `gid_attrs/ndevs/<index>`——并读连接管理解析本地标识符时使用的模式设置；判据是类型与关联设备两项同时成立（类型为可路由版本且关联设备上配了地址）才具备跨三层使用的前提。条件会变：NCCL 自 2.21 起动态选择 GID 索引，2.32u1 起默认值写作 AUTO（`-1` 是兼容别名），官方明确该变量不应再手工设置，只有动态选择确实选错时才手工指定；因此手工索引只在「本次交付重新取过、且动态选择被证明错误」这两个条件同时成立时才成立。官方给出的报错文本之一是 `Call to ibv_modify_qp failed with error Invalid argument`，但它不是这一项的专属证据，必须与 GID 三项和连接管理模式一起读。这些行为随驱动、NCCL 与 RDMA 栈（OFED 或 in-box）共同确定，因此现场读数必须同时记录这几项。
- **结论**：索引是随环境漂移的现场取值，交付时必须重新取一遍，默认交给自动选择，只有证明自动选择错误时才手工指定。
- **出处**：NVIDIA DOCA 文档中 RoCE 一章（GID 表的结构与取值位置、地址向量与 GID 类型的关系）；NCCL User Guide 的环境变量一页与网络排障一节（GID 索引自 2.21 起动态选择、2.32u1 起默认值写作 AUTO、该变量不应手工设置这一条，以及选错时的报错文本）。

### 「`max_mtu` 是 4096，所以在用巨帧」

- **场景**：在设备查询输出里看到端口的 `max_mtu` 为 4096，于是认为这条链路已经在用巨帧传输。
- **常见误判**：把 `max_mtu` 当作此刻生效值。它看起来成立的原因在于两个字段名字相近且都在同一段输出里，而厂商给出的示例输出正是一个 `max_mtu` 为 4096、`active_mtu` 为 1024 的组合，后者对应的正是网络设备侧 MTU 仍为默认值 1500 的机器。
- **判据**：读 RDMA 侧的 `active_mtu` 与网络设备侧的 `ip link show` 里的 `mtu`，判据是两者之间的换算（即「不超过网络设备 MTU 的最大 2 的幂」）是否成立，换算的正确性比数值看起来是否够大更重要；`max_mtu` 只用于说明端口能力。条件会变：若换算不成立，应先查网络设备侧的 MTU，再向网络团队核对交换机端口对该 MTU 的承载；若换算成立而两端 `active_mtu` 不同，则结论转向对端，而不是本端。
- **结论**：`max_mtu` 不能作为判据，只有 `active_mtu` 与网络设备 MTU 的换算成立，才能说这条链路在用巨帧。
- **出处**：NVIDIA DOCA 文档中 RoCE 一章的设备查询输出示例与输出说明（`max_mtu` 与 `active_mtu` 的对照）。

### 「只改一端的 MTU 没关系」

- **场景**：为了提升大消息吞吐，在链路的一端把 MTU 调大并完成复测，认为另一端沿用旧值不影响使用。
- **常见误判**：把 RDMA 的 MTU 当作可以单侧决定的量。它看起来成立的原因在于小消息测试与连通性检查都完全正常，而两端不一致的后果只在报文尺寸大到需要分片或超过对端承载能力时才出现。
- **判据**：读两端各自的 `active_mtu` 与各自的网络设备 MTU，并按尺寸扫描跑一遍收发测试；判据是「小消息正常、大消息异常」这个组合是否出现，大消息是指报文尺寸达到兆字节量级的用例。条件会变：只跑缺省尺寸的单点测试不会暴露两端不一致，因此结论只在按尺寸扫描覆盖到大消息之后才成立；此外改变网络设备 MTU 会牵动正在使用该设备的全部流量，因此生产节点上只做读取，改动只在实验节点进行，回滚方式是把 MTU 改回原值并按同一套尺寸扫描复测。
- **结论**：MTU 必须两端换算一致，验收必须按尺寸扫描，只测一个缺省尺寸不足以证明链路可用。
- **出处**：NVIDIA DOCA 文档中 RoCE 一章（两端 MTU 与实际传输行为的关系）；收发测试工具手册页（按尺寸扫描的用法）。

### 「把无损优先级开在承载所有业务的队列上最省事」

- **场景**：为了避免逐条筛选流量，把无损能力使能到承载全部业务的队列上，认为覆盖面越大越安全。
- **常见误判**：把反压当作局部机制。它看起来成立的原因在于反压确实只在相邻两跳之间起作用，但停帧会被逐跳传播，使能无损的优先级一旦覆盖无关流量，这些流量也会一起被停住，形成与拥塞源头无关的头阻塞；极端情况下还会触发停滞防护，让发送端放弃发送停帧。停滞防护有两种模式，默认模式的停滞超时是 8 秒，自动模式把停滞超时设为 100 毫秒，其开关在 `/sys/class/net/<if>/settings/pfc_stall_prevention`，取值是 `default` 或 `auto`。
- **判据**：读使能无损的优先级位图（常规做法是收敛到一个，若开了多个则逐个交代归属与隔离证据）与停滞防护的两个计数 `tx_pause_storm_warning_events` 与 `tx_pause_storm_error_events`，并读同期的重传与超时计数；两个风暴计数是累计量，判据是它们是否出现增量，警戒级计数增长说明已接近停滞超时，错误级计数增长说明网卡已经停止发送停帧。条件会变：一旦网卡放弃发送停帧，链路上就只剩丢包一条路，此时重传与超时计数接替增长，结论从「反压在工作」变为「无损已经失效」。
- **结论**：无损优先级要只覆盖真正需要无损的流量，风暴计数出现增量即说明无损正在或已经失效，停滞防护只是逃生机制而不是治疗手段。
- **出处**：NVIDIA DOCA 文档中流控一章（逐跳反压的传播代价、停滞防护的两种模式与两个风暴计数）。

### 「调大重试次数与超时就能扛住丢包」

- **场景**：出现重传与超时计数增长后，把超时与重试参数调大，认为这样就能在丢包存在的链路上继续跑满带宽。
- **常见误判**：把时间参数当作对丢包的补偿。它看起来成立的原因在于调大之后报错确实变少了，但超时时间本身按超时基数乘以 2 的 timeout 次幂增长（官方换算给出的两个点是 timeout 为 17 时约 536.9 毫秒、为 20 时约 4.3 秒，同一基数下后者约为前者的 8 倍），而重试次数与超时时间的乘积才是一次故障的最长等待；调大参数只改变「多久报错」，不改变「已经丢了」这个事实。
- **判据**：读当前生效的本地确认超时与重试次数字段，按上述换算估算单次超时时间并与重试次数相乘，同时读 `local_ack_timeout_err`、`packet_seq_err`、`rnr_nak_retry_err`、`duplicate_request`、`out_of_sequence` 与 `roce_adp_retrans` 这些累计计数的增量（计数器名字随驱动版本变化，现场用 grep 取）；判据是超时类计数与序号类计数是否同步增长，自适应重传只调整重传行为、不解决根因，因此它自己的计数增长不能作为「问题已缓解」的证据。条件会变：超时与重试是队列对属性，在转入可发送状态时写入，之后不经重建改不了，因此运行期读到的值就是本次连接一直使用的值；唯一能在不重建连接的前提下动到重传行为的是固件层的自适应重传档位，但它的作用范围是该物理功能上的全部队列对，因此调大它的影响面比调一条连接宽得多。此外收发测试工具的重传超时默认值来自源码常量 `DEF_QP_TIME`（取值 14，约 65 毫秒），NCCL 自 2.23 起默认超时为 20（约 4.3 秒）并在重试 7 次后（约 30 秒）报错，两个程序用不同的默认值跑在同一条网络上时，一次超时的代价相差很大；这些默认值同样随驱动、NCCL 与 RDMA 栈共同确定，必须同时记录。

```bash
# 验证：一次丢包之后，本地确认超时与序号错误类计数是否同步增长
grep -E 'local_ack_timeout_err|packet_seq_err' /sys/class/infiniband/<device>/ports/<port>/counters/*
```

计数器项名与取值随驱动四元组与网卡固件变化，因此上面这条命令只用于在本机取到实际项名与两次读数，任何对照使用的数值仅示意、不代表你的环境。

- **结论**：调大超时与重试只改变报错时间与单次故障的最长等待，丢包根因不因此消失，自适应重传也不改变丢包这件事本身。
- **出处**：NVIDIA DOCA 文档中自适应重传一章与拥塞控制基础设施一章（重传超时与自适应重传的定位）；队列对配置接口手册页（超时与重试字段、可发送状态之前完成配置）；NCCL User Guide 的环境变量一页与网络排障一节（默认超时、重试次数与报错文本）。

## 值班口径

这十条可以归成四类共同成因。第一类是把上层可达当作下层证据：链路状态与 ping 通只覆盖链路层与带外通道，主机侧命令执行成功只覆盖本端这一跳，而由于 RoCE 数据面完全由硬件卸载、流量不进入标准以太网接口的软件计数，主机侧能够证明数据面在工作的只有两件事同时成立——RDMA 语义的工具跑通，以及 RDMA 设备的端口计数器出现与作业吞吐相匹配的增量。因此凡是结论止步于「通了」的判断，都需要再补一次 RDMA 语义的验证。

第二类成因是读数纪律：把累计量与瞬时量、上限与实际生效值、发送方向与接收方向、以及全局流控与按优先级的流控混在一起比较。这类错误的共同修正是先取两次读数得到增量，再看方向与优先级前缀，最后才与另一侧的同类读数对齐；由于按优先级的反压计数只在使能了该优先级时可见，读不到某个优先级的计数本身就是一条信息，而不是「没有问题」。

第三类成因是默认配置只落在自己负责的一侧：把优先级流控使能在网卡上就认为无损成立，把 MTU 改在一端就认为两端已对齐，把信任模式改完就认为标记已落到预期队列，把别处记录下来的索引当作本机的不变量。这类错误的共同特征是压力不足时完全看不出来，因此判据必须从「配置动作是否执行成功」改成「端点与路径上每一处的取值是否彼此对齐、并且有压测证据」。

第四类成因是用时间参数掩盖丢包：超时按超时基数乘以 2 的次幂增长，重试次数与超时时间的乘积决定一次故障的最长等待，自适应重传只调整重传行为。因此调大参数只是把故障从「报错」改写成「长时间无进展」，对根因没有作用；同时，凡结论依赖某个默认值或某个版本行为时，都必须同时记录驱动、CUDA、NCCL 与 RDMA 栈四项，缺任一项时读数不构成结论。

**第一反应不要做什么**：不要用 ping 或端口状态宣布 RDMA 正常；不要因为某个反压计数不为零就判定反压异常；不要在读出方向与优先级前缀之前解释停帧计数；不要在映射表没有逐项对齐时只改信任模式；不要抄用别处记录的全局标识符索引；不要把 `max_mtu` 当作生效值；不要只改一端的 MTU；不要把承载全部业务的队列设为无损优先级；也不要用调大重试次数与超时来替代对丢包根因的定位。正确的顺序是先取两次读数得到趋势与方向，再确认改动范围覆盖了端点与路径上的每一跳，最后才动配置。
