# GID 索引与地址选择

一张只插了一根线、只配了一个 IP 地址的网卡，在 RoCE 的地址表里却给出八条地址，这是第一次做 RoCE 交付时最容易停下来的地方。它带来的代价并不是看不看得懂，而是选错：交付脚本里写死的那个索引，换一个机型或加了一个 VLAN 接口之后指向了别的地址，于是同一批节点里只有一部分建链失败，还有一部分能建链却把流量从错误的端口发了出去。因此这一组地址必须先弄清三件事——它由什么生成、按什么顺序排列、每条队列对又是怎么在其中选取的。以下按这三个问题展开。

## 两种承载：地址从哪来、能不能跨三层

RoCEv1 把 InfiniBand 的传输层直接封装进以太网帧，使用专用的以太类型 `0x8915`；由于报文不带 IP 头，它的适用范围限于同一个广播域，因此不能跨三层。

RoCEv2 把传输层封装进 UDP 与 IP 之上，目的端口为 `4791`。由于报文带 IP 头，它可以被路由，因此可以跨三层；同时它的源端口字段可以参与哈希，为等价多路径路由提供流标识，也就是为同一条连接的不同数据流分散到不同路径提供熵。

这两种承载反映到地址上，就产生了同一台设备上成对出现的条目：同一个地址会以 v1 与 v2 两个版本各出现一次，因此条目数量随本机配置了 IP 的网络设备的数量与地址数量成倍增长。

## GID 表：一条地址被拆成三项

全局标识符（Global Identifier，GID）表在配置了 IP 地址的以太网设备上自动生成。每一条包含三项内容：GID 值、GID 类型与关联的网络设备。因此判断一条索引能不能用于跨三层通信，必须同时看类型与关联设备两项：类型为 v2、且关联的网络设备上配置了 IP 地址，这条条目才具备可路由的地址。

三处的取值位置按索引对应：GID 值在 `gids/<index>`，类型在 `gid_attrs/types/<index>`，关联的网络设备在 `gid_attrs/ndevs/<index>`。其中 GID 值可以这样确认：

```bash
# 验证：某一索引上的 GID 值；取值以现场输出为准，形态为 IPv4 映射 GID 或 IPv6 地址
cat /sys/class/infiniband/<device>/ports/<port>/gids/<index>
```

类型与关联设备必须与 GID 值一起读，缺其中一项就无法判断这条条目能不能跨三层。这一组取值都是只读观测，在生产节点上也可以做。

官方给出的 GID 表结构是一条顺序固定的清单：清单开头是默认的两条，也就是链路本地地址的 v1 与 v2；随后是某个以太网设备（例如 `eth1`）上 IP 地址对应的 v1 与 v2；再随后是 VLAN 接口（例如 `eth1.100`）上 IP 地址对应的 v1 与 v2，这两条对应的报文会带 VLAN 头；最后是 IPv6 的 GID 对应的 v1 与 v2。四条地址各两个版本，合计八条，这就是「一张网卡上有八条地址」的来源。

由于清单的顺序由「本机有哪些网络设备、它们各自有几个地址」决定，**「索引 3 就是 IPv4 的 v2」这句话只在没有 VLAN、也没有多个 IP 地址的机器上成立**。一旦加了 VLAN 接口或给同一个设备再加一个 IP 地址，索引与地址的对应关系就会整体后移。这里要同另一个容易混淆的对象分开：GID 表是每个 RDMA 端口各自一张，换到同一台机器上的另一个端口，读到的就是另一张表，因此正确做法是重新读该端口自己的表，而不是把端口数量当成索引漂移的原因。索引的这种漂移是「只有一部分节点失败」这类随机故障的常见来源；因此记录索引这件事必须以「每次交付重新取一遍」为条件，而不是把上一次的数字抄进配置。

查看入口是 `show_gids`：

```bash
# 验证：本机 GID 表的索引、地址、类型与关联网络设备；数值仅示意、不代表你的环境
show_gids
```

它的输出是按索引逐行排列的地址清单，读法是「索引与类型、关联设备一起读」，而不是只读地址本身。若某条索引的类型是 v1，或者它关联的网络设备上没有配置 IP 地址，那么这条条目不能用于跨三层；此时正确的动作是换一条索引，而不是去改地址。

### 一次交付按固定顺序取一遍

由于索引会漂移，取值这件事本身要有固定顺序，否则两次交付的结果无法互相比较。可执行的顺序是四步，每一步的产出都要留下记录。

第一步是确认前提：读端口的链路类型与运行状态，要求链路类型为 Ethernet、端口状态为活动状态；若这一项不成立，其余各步的地址核对都没有意义。

第二步是取本机的 GID 清单，得到索引、地址、类型与关联网络设备四列，并从中挑出类型为 v2、且关联网络设备上配置了本次交付所用 IP 地址的那一条。

第三步是确认 RDMA-CM 使用的模式与第二步挑出的条目一致；在动态选择 GID 已经生效的版本上不需要手工指定索引，但要把「动态选择生效」这个事实一起记录下来。

第四步是把这一组取值与驱动、CUDA、NCCL 以及 RDMA 栈四项版本一起归档。下一次交付重新取一遍并与上一次对照：若索引与地址的对应关系发生了变化，说明本机的网络设备或地址发生过变化，此时应当先解释这次变化，再决定能不能沿用旧配置；反之若两次一致，这个索引才可以作为本次交付的取值写入记录。

## 每条队列对自己选版本

队列对选哪一个 GID 由地址向量（Address Vector，AV）决定，而不是由端口上的某个全局开关决定。连接类队列对从 INIT 转到 RTR（准备接收）状态时必须给出地址向量，其中的 GID 索引决定这条队列对用 v1 还是 v2 发包；无连接队列对同样由地址向量里的 GID 索引决定版本。因此**版本不是端口级开关，而是每条队列对各自的选择**，同一张卡上可以同时存在走 v1 的队列对与走 v2 的队列对。

RDMA 连接管理（RDMA Connection Manager，RDMA-CM）类应用是一个例外：它用一个全局模块设置决定解析本地 GID 时使用哪一种类型，入口是 `cma_roce_mode`。它的查询形态是只读的：

```bash
# 验证：RDMA-CM 当前解析本地 GID 所使用的版本；输出取值以现场工具版本为准
cma_roce_mode -d <device> -p <port>
```

设置形态是 `cma_roce_mode -d <device> -p <port> -m <1|2>`。这一动作会改变本机全部 RDMA-CM 应用的地址解析结果，影响同一台机器上的全部作业，因此只在实验节点执行；回滚路径是改动前记录原值，改动后按原值设回并复测建链。

## 选错会怎样：三种形态

选错的表现不是同一种，因此报错文本本身要能指向具体是哪一种。

第一种是跨三层却选了链路本地的条目。这条条目没有可路由的地址，表现是建链失败，或者在需要选路的场景下找不到路由。

第二种是双端口机器上选了另一个端口 IP 所对应的条目。此时连接可能建立成功，报文也确实发出去了，但走的是另一个端口；这类问题不会留下失败文本，只表现为「能通但走错端口」，需要把连接使用的 GID 索引与两个端口的地址逐一对照才能发现。

第三种是版本选错。此时发包用的承载与对端为另一种承载准备的策略不一致，结果是流量绕过了为它准备的策略；由于两端都能通，症状会推迟到压力出现时才暴露出来。

判断版本与端口状态的前提入口是 `ibv_devinfo -v` 的输出：其中 `link_layer: Ethernet` 与端口状态 `PORT_ACTIVE` 是继续看地址的前提；示例输出里同时出现 `max_mtu: 4096` 与 `active_mtu: 1024`，这两个数值仅示意、不代表你的环境，且与机型、驱动四元组、网卡固件版本强相关。若端口状态不是活动状态，那么地址问题无从谈起，应先解决端口状态。

## 索引漂移与自动选择

RoCE 与 InfiniBand 在管理方式上有一处根本差别：RoCE 没有子网管理器，因此没有本地标识符，相关查询里显示为 0；同时它不支持备用路径迁移。由于无法做路径查询，连接建立之前必须自行把路径记录填好，官方强烈建议用 RDMA-CM 来代劳。这一条决定了 RoCE 上很多配置是每台主机自己的事，地址与版本的选取也就落到了主机侧；InfiniBand fabric 侧的集中配置、分区与轨道不属于主机侧负责的内容。

正因为如此，把索引写死是一种脆弱做法。NCCL 自 2.21 起改为动态选择 GID 索引，2.32u1 起默认值正式写作 AUTO（`-1` 保留为兼容别名），官方明确该变量不应再手工设置；只有动态选择确实选错时才手工指定。动态选择失败或选错时，官方给出的报错文本之一是 `Call to ibv_modify_qp failed with error Invalid argument`——它不是这一项的专属证据，任何让队列对属性组合不成立的改动都可能给出同一条文本，因此必须与 GID 表的三项和连接管理的模式设置一起读。

这一条判断涉及版本，因此必须与四项一起记录：驱动、CUDA、NCCL 与 RDMA 栈（发行版自带 in-box 或随 DOCA-OFED 一类独立栈安装）。四者的约束方向是：本机可用的 GID 条目由驱动与 RDMA 栈决定，而使用哪一条条目由 NCCL 的版本决定；缺任一项时，读数不构成结论。

端口的 RoCE 能力可以整体关闭。当前驱动把它作为设备级的参数暴露，入口随驱动版本变化：使用设备参数接口的是下面这一种形态，较早的驱动则在 PCI 设备目录下用 `roce_enable` 属性暴露同一件事。

```bash
# 验证：该设备的 RoCE 能力开关；条目名与承载方式以现场驱动输出为准
devlink dev param show <pci-bus-address> name enable_roce
```

关闭之后，该端口上不再有 GID 表，只剩裸以太网队列对。该参数属于驱动初始化阶段生效的一类，改动要配合驱动重载才生效，因此判断依据不能只看参数值本身，还要看重载之后 GID 表是否确实消失。由于它会一次改变本机该端口的全部 RDMA 作业，这个动作只在实验节点执行，影响范围是同一台机器上的全部作业，回滚路径是把该参数改回改动前的取值并复测。

## 字段怎么读

| 字段 | 是什么与单位 | 判据 | 与谁同看 | 看到它转向哪一步 |
| --- | --- | --- | --- | --- |
| GID 值 | 某个索引上的地址，形态为 IPv4 映射 GID 或 IPv6 地址；本身不带单位 | 它是否与本机该网络设备上配置的 IP 地址一致 | 与类型、关联网络设备两项同看 | 值正确而类型是 v1 时报文不可路由，转向换索引而不是改地址 |
| GID 类型 | 该条目属于 v1 还是 v2，取值为枚举，具体文本以现场输出为准 | 需要跨三层时必须是 v2；只在同一广播域内通信时才用 v1 | 与 GID 值、关联网络设备同看 | 类型不对时不要改地址，先改队列对使用的索引 |
| 关联网络设备 | 该条目绑定在哪一个网络设备上，取值是设备名 | 该设备上是否配置了 IP 地址 | 与 `ip link` 的设备状态、VLAN 接口同看 | 关联设备与实际出流量的设备不一致时，属于「能通但走错端口」，先核对两个端口的地址 |
| `cma_roce_mode` 的输出 | RDMA-CM 解析本地 GID 时使用的版本，取值为 1 或 2 | 它必须与对端为这批流量准备的策略一致 | 与队列对实际使用的地址向量、交换机侧策略同看 | 不一致时改到一致或按原值设回；该动作只在实验节点执行 |
| `NCCL_IB_GID_INDEX` | NCCL 选用 GID 索引的变量，整数；默认值为 AUTO，`-1` 是保留的兼容别名 | 2.21 起由 NCCL 动态选择 GID，2.32u1 起默认值写作 AUTO；官方明确该变量不应再手工设置 | 与驱动、RDMA 栈的版本，以及建链报错文本同看 | 只有动态选择确实选错时才手工指定，且指定值每次交付重新取一遍 |
| 端口的 `roce_enable` | 端口 RoCE 能力的开关，取值为 0 或 1，属于配置状态 | 为 1 时该端口才有 GID 表 | 与 `show_gids` 的输出同看 | 若为 0，则端口上没有 GID 表，地址问题不成立，先确认是否有人关过它 |
| `ibv_devinfo -v` 的 `link_layer` 与端口状态 | 端口当前的链路类型与运行状态，取值为枚举，例如 Ethernet 与 `PORT_ACTIVE` | 链路类型必须是 Ethernet、端口状态必须是活动状态，地址核对才有意义 | 与 GID 表的取值同看 | 若端口不是活动状态，先解决端口状态，不要继续查索引 |

表里的 GID 表内容与 `roce_enable` 都是配置状态，读一次就能判断当下处于哪一种；`show_gids` 的输出是当前状态而不是历史记录，因此它回答不了「上一次交付时用的是哪个索引」，要回答这个问题必须有归档下来的取值。

**第一反应不要做什么**：不要把上一次交付得到的 GID 索引写进脚本或镜像。索引会随 VLAN 接口与 IP 地址的增减漂移，换端口还要重新读该端口自己的表，先在本机取一遍 GID 表并核对类型与关联网络设备；在动态选择已经生效的版本上，也不要为了「稳妥」而手工覆盖它，只有确认动态选择确实选错时才手工指定。
