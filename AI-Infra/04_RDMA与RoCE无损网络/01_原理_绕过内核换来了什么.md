# 绕过内核换来了什么

同一条物理链路，走内核网络栈搬运一次数据时，参与搬运的是处理器的软件路径：数据从应用缓冲区复制到内核的套接字缓冲区，再从内核缓冲区交给网络设备，而每一次需要软件介入的交接都要求处理器在处理上下文之间切换一次；反之，数据面完全由硬件卸载之后，网卡直接对内存做直接内存访问（Direct Memory Access，DMA），处理器的软件路径不再出现在逐包搬运上。因此「一次搬运有几次内存拷贝与几次上下文切换」的答案，在两条路线上并不相同：通用的内核栈路线，拷贝次数与切换次数由协议栈各层的实现决定，随内核版本与套接字类型变化；绕过内核的路线，数据面上的逐包拷贝次数为 0，接收侧报文的写入与发送侧内存的读取都由硬件直接落到已经注册给网卡的内存里。这里被省掉的是逐包搬运，不是处理器本身的参与：提交工作请求、从完成队列取回结果、在接收侧补充接收缓冲，这些动作仍由处理器执行，只是不再逐包进入协议栈。

以一次发送为例，把两条路线各自经过的环节摆开（环节计数为典型情形，随内核版本、套接字类型与协议栈实现变化，仅示意）：

| 环节 | 内核套接字路线（TCP/IP 的走法） | 绕过内核的路线 |
| --- | --- | --- |
| 发送侧：应用缓冲区到网卡 | 一次系统调用进入内核，数据从应用缓冲区复制到套接字缓冲区，协议栈逐层封装后由网卡以 DMA 取走；处理器参与其中的复制与每一次交接 | 网卡按注册时拿到的地址映射，直接对已注册的应用缓冲区做 DMA；处理器不出现在数据面上 |
| 接收侧：网卡到应用缓冲区 | 网卡 DMA 进内核缓冲区，协议栈处理后再复制到应用缓冲区，并唤醒等待的进程；同样伴随一次上下文切换 | 网卡直接把数据写进对端已注册的内存，完成事件由应用主动向网卡取回 |
| 处理器在每次搬运上的投入 | 复制与切换各若干次，随每次搬运重复付出 | 为零；代价提前到注册内存与建链时一次性付清 |

内核套接字路线就是普通 TCP/IP 流量的走法，它的机制细节归 Linux 主题域展开，本篇不深入；这里只需要它的对照作用——它的代价随每一次搬运发生，而绕过内核的路线把代价挪到了搬运开始之前。
代价并没有消失，只是从「每一次搬运都付」变成「在搬运开始之前一次性付清」，并且变成几项有明确上限的资源占用。可被网卡读写的内存是有限的、有上限的注册资源；完成事件的取回方式决定了处理器核的占用；网卡上的队列对数量是有限的，而连接数就是队列对数。这三项资源都不是按需弹性增长的，因此它们必须在部署与容量规划阶段就被算进去。

## 分界线画在控制面与数据面之间

建立连接与注册内存这两件事仍然要经过内核：应用通过设备节点与用户态 verbs 库（verbs 是 RDMA 的动词式应用编程接口，用户态 verbs 库即 `libibverbs` 这类把操作提交给硬件与驱动栈的运行库）提交请求，而内核把设备暴露成 `uverbs` 设备节点（形如 `/dev/infiniband/uverbs0`，是用户态访问 RDMA 设备的入口）。数据传输本身则不经过内核。

这条分界线直接解释了一个常见困惑：用内核网络栈的工具去看 RDMA 流量，看不到逐包的处理过程，这不是配置漏了哪一项，而是机制的结果——数据面的收发由网卡硬件完成，每个报文不进入内核协议栈的收发包路径，因此 `ss`、`netstat` 这类按套接字统计的工具看不到这部分流量。这一条不能顺手推成「以太网侧的计数都看不到 RDMA 流量」：同一个物理端口同时以网络设备与 RDMA 设备两种身份出现，两侧各自暴露一部分事实。RDMA 设备的端口计数器目录 `/sys/class/infiniband/<device>/ports/<port>/counters/` 给的是协议层与链路层事件；网络设备一侧的 `ethtool -S <if>` 给的是按优先级暂停、物理层误码与链路事件。两类读数互补，缺哪一类都会漏掉整段判断。

与之配套的判据是：判断一个进程是否真的在用 RDMA，比较的是 RDMA 设备端口计数器的增量，而不是以太网接口的收发计数。具体的对照做法写成一行只读观测，生产节点上也可以做：

```bash
ibdev2netdev                                  # 验证：RDMA 设备与网络设备的对应关系，先确认看的是哪一对
grep -E 'port_xmit|port_rcv' /sys/class/infiniband/<device>/ports/<port>/counters/*   # 验证：这一对端口的收发计数器里有哪些项
```

这些计数器的单位是字节或包数，属累计值，判据是两次读数之间的增量，具体字段是否为本机所有以现场输出为准。

## 四个对象各自的位置

一次搬运的指令与结果，落在四个对象上。它们的关系是：工作请求（Work Request，WR）由应用提交，网卡把它取成工作请求条目（Work Queue Element，WQE）放在队列上；队列对（Queue Pair，QP）是一对发送队列与接收队列，是通信的基本单位；完成队列（Completion Queue，CQ）承载完成事件，应用从它取回操作结果；内存区域（Memory Region，MR）是注册给网卡直接读写的一段内存。

| 对象 | 它是什么 | 单位与容量口径 | 与谁同看 |
| --- | --- | --- | --- |
| WQE | 工作请求条目，一条搬运指令在队列上的表示 | 以条目计；队列深度是条目数，不是字节数 | 与队列深度上限、与完成队列条目数同看 |
| QP | 一对发送队列与接收队列，一条连接对应一个 | 以个数计；受设备 `max_qp` 这类上限约束 | 与连接数、与进程数同看 |
| CQ | 完成事件的队列，应用从它取回结果 | 以条目计；条目数与单条完成记录的大小相关 | 与队列深度、与轮询方式同看 |
| MR | 注册给网卡直接读写的一段内存 | 以字节计；受进程可锁定内存上限约束 | 与 `memlock`、与显存注册的模块前置条件同看 |

四个对象中，前三个描述「指令怎么排、结果从哪取」，第四个描述「网卡能碰哪段内存」。注册内存的动作在 verbs 手册页里写作 `ibv_reg_mr(3)`，完成队列的建立写作 `ibv_create_cq(3)`；这两个调用都是控制面动作，它们返回之后，数据面就不再需要内核参与。

设备一侧的容量上限可以从只读观测读到：

```bash
ibv_devinfo -v | grep -E 'max_qp|max_cq|max_mr'   # 验证：这张卡的队列对、完成队列与内存区域各自的上限
```

这些上限是设备声明的能力值，单位是个数，判据是它与实际连接数、队列深度的比值而不是它本身的大小；它属声明上限这一类量，与此刻实际用掉多少不是同一个口径。输出数值仅示意、不代表你的环境，且与机型、驱动四元组、网卡固件强相关。

## 注册内存为什么必须锁定物理页

网卡按物理地址访问内存，而不是按虚拟地址。若某个页在搬运过程中被换出、被迁移或被共享合并，网卡按原地址写入就会落到错误的位置，而这个错误不表现为搬运失败，而表现为内存内容被破坏。因此注册内存的动作实质上是把一段虚拟内存所对应的物理页钉住，即锁定物理页并把它对应的物理地址登记给网卡。

由此产生的约束是可注册内存的上限由进程可锁定内存上限决定。这个上限在 `getrlimit(2)` 中对应 `RLIMIT_MEMLOCK`，单位是字节，可以由 `ulimit -l` 读取；`ulimit -l` 的值以 KiB 计，而无限（`unlimited`）并不等于真正无限：按 `getrlimit(2)` 的说明，同一个上限还存在一个由内核控制的限值，本进程只能把软上限提到硬上限为止。锁页不足时注册调用失败，表现为内存分配类错误，具体错误文本以本地运行库与内核为准；这一点决定了「注册失败」在现象上是调用返回错误，而不是吞吐变慢。

这几项量必须在同一次核对里读完，因为它们的口径不同：`ulimit -l` 是上限，注册调用返回是实际生效结果，两者混读会得出相反结论。以下为只读观测，生产节点上也可以做：

```bash
ulimit -l; ulimit -Hl                            # 验证：软上限与硬上限分别是多少，注意它是 KiB 而不是字节
```

读取结果的单位是 KiB，判据是它与训练进程要注册的缓冲区总量之间的关系，与硬上限同看；若软上限明显小于需求，转向调整上限或减少注册量，而不是继续检查网络配置。

注册显存给网卡直接读写，另有一套模块前置条件；该前置条件的清单与加载顺序不在数据面这条线之内。

## 完成事件用轮询取回，代价是一个核

完成事件有两条取回路径：中断与轮询。中断方式下，事件到达时处理器被打断，上下文切换到驱动的中断处理路径；轮询方式下，应用在一个循环里持续检查完成队列，不做系统调用也不等待通知。由于一次中断意味着一次上下文切换与一段不可预测的唤醒延迟，轮询可以把单次操作的延迟压到更低，代价是执行轮询的那个处理器核被这个循环占满。

因此完成事件的取回方式选择，会反过来决定处理器核的分配：轮询需要一个专属的核，占用时间与提交速率、完成队列深度直接相关；同时网卡的中断亲和（中断请求绑定到哪个核）与轮询所在核的绑定关系会直接影响读数，因为两者争用同一批处理器资源时，延迟分布会明显变化。判断「延迟是否真的被压低」，必须同时记录核绑定方式与轮询所在的核，否则两次测量之间没有可比性。

| 取回方式 | 谁在等待 | 单位与代价口径 | 与谁同看 | 转向哪一步 |
| --- | --- | --- | --- | --- |
| 中断 | 处理器被事件唤醒 | 中断次数以次计；代价是每次唤醒的上下文切换与唤醒延迟 | 与中断亲和、与中断合并参数同看 | 若延迟分布出现长尾而吞吐正常，先核对中断亲和与合并设置 |
| 轮询 | 应用循环主动检查完成队列 | 占用的处理器核以核数计，占用时间随提交速率增长 | 与核绑定、与进程的 CPU 配额同看 | 若单核接近饱和而延迟没有改善，先核对轮询核是否与其他工作争用同一个核 |

上表中两个口径不混用：中断次数是累计量，可以取差分算速率；被占满的核数是瞬时占用，只能看它在此刻是否饱和。

## 队列对数量是连接预算

一张网卡能支持的队列对数量是有限的。在最常见的一对一可靠连接场景里，一条连接占用一个队列对，因此这一场景下的连接数就等于队列对数；换成非连接型队列对（数据报语义，一次发送可以面向多个对端）或共享接收队列这类用法，这条换算不成立，那时队列对数与对端数量之间没有一对一关系。本节以下的结论都限定在前者的场景里。这件事的直接后果是，可用连接并不是只由对端数量决定的，而是由本端网卡能建多少队列对、以及这些队列对各自要消耗多少完成队列与内存区域资源共同决定的。因此「多开几个进程」不是把同一条连接多用几次，而是消耗更多份队列对预算：典型实现下每个进程各自建自己的连接、各自注册自己的内存、各自持有完成队列；把内存区域或完成队列做成跨进程共享是允许的实现选择，但那就需要在容量规划里另外算清楚共享对象的争用。

由此得到一条容量判据：连接规划要按「队列对上限」与「每进程需要的队列对数」同时算，并按同一台机器上的全部作业合计，而不是按单个进程算。若余量不足，表现是部分进程建链失败或长时间等待，而不是带宽下降。

## 三项代价的对照

| 换来的能力              | 代价项          | 单位与上限口径                    | 判据                       | 与谁同看                       | 转向哪一步                   |
| ------------------ | ------------ | -------------------------- | ------------------------ | -------------------------- | ----------------------- |
| 数据面零拷贝、处理器不在数据面上介入 | 可注册内存受锁页上限约束 | 字节；上限由 `RLIMIT_MEMLOCK` 决定 | 注册调用是否返回成功，以及已注册总量与上限的比值 | 与 `ulimit -l`、硬上限、注册调用返回同看 | 注册失败先核对上限与已注册总量，不要先怀疑链路 |
| 单次操作延迟被压低          | 轮询占用一个处理器核   | 核数；瞬时占用                    | 轮询核的占用率与完成队列取回速率         | 与中断亲和、核绑定同看                | 延迟长尾且吞吐正常时，先核对中断与核的分配   |
| 一次建链之后硬件自持搬运       | 队列对数量有限      | 个数；受设备上限约束                 | 计划连接数与设备上限的余量            | 与进程数、完成队列与内存区域用量同看         | 建链失败且计数与链路状态正常时，先算队列对余量 |

三项代价的共同点是都不能通过调参数消除，只能通过规划分摊。

## 关于这几个字段常见的两种混读

一是把设备声明的上限当成此刻的实际占用。`max_qp`、`max_cq`、`max_mr` 是设备能力上限，属声明上限这一类量；实际用掉多少只能从建链结果与注册结果看，两者不是同一个口径。

二是把「注册失败」与「注册成功但被换出」混为一谈。注册成功后物理页被锁定，不存在被换出的可能；因此任何关于「注册过的内存还被换出」的怀疑，都应当先核对注册调用本身的返回值。

**第一反应不要做什么**：不要用内核套接字工具的统计判断 RDMA 流量是否存在；不要把「一对一可靠连接」的队列对换算套到非连接型与共享接收队列的用法上；不要看到设备声明的队列对上限很大就认为连接数不会成为瓶颈；不要在注册调用返回失败时先去查交换机配置。
