# 驱动栈观测与取证

面对一台 GPU 用不了的机器，可用的命令有一二十条，但真正能缩小范围的顺序只有一条：**先用一份读数回答「问题在哪一层」，再用第二份读数回答「这一层为什么不成」**。反过来做——先跑一整轮体检脚本、把几十行输出一起看——得到的是一堆都正常或都不正常的数字，判断反而更慢。本篇按这个顺序组织：先给出问题与工具的对应表，再给出故障现场定位表，说明取证材料各自的落点与影响范围，最后用四个场景把第一份读数之后的路径走完。以下所有命令除标注外都是只读观测，生产节点上也可以执行。

## 一个问题一把工具

| 要回答的问题 | 命令 | 读哪个字段 | 判据 |
| --- | --- | --- | --- |
| 内核模块加载了吗 | `lsmod` | `nvidia` 开头的行与它的 `Used by` 列 | 核心行不存在则内核态这一层没起来；UVM 是否挂在核心行下面影响计算程序能否启动 |
| 模块来自哪种构建方式 | `modinfo -F filename nvidia` | 模块文件的路径 | 落在动态更新目录下是现场编译，落在内核自带目录下是预编译 |
| 当前内核的模块编到哪一步 | `dkms status` | 当前内核那一行的状态 | 不是已完成状态就说明这个内核下没有可加载的模块 |
| 已加载模块是哪个版本 | `/proc/driver/nvidia/version` | 内核模块版本行 | 与包管理器里的驱动版本不一致即为版本漂移 |
| 用户态库报告哪个版本 | 管理工具的版本字段 | 驱动版本 | 与内核模块版本同看，两者不一致是版本不匹配 |
| 固件是哪个版本 | 管理工具的固件版本字段 | 固件版本 | 与模块版本同看，配对不上时模块加载失败 |
| 节点齐不齐、权限对不对 | `ls -l /dev/nvidia*` | 节点清单与权限位 | 与内核登记的设备号对照；UVM 节点缺失时计算程序起不来 |
| 节点编号对不对 | `/proc/devices` | 驱动相关的设备号 | 与 `/dev` 下的节点对照，用于判断节点是不是按当前内核创建的 |
| 模块为什么没加载 | 内核日志过滤器 | `NVRM` 前缀的记录 | 日志给出签名、冲突、固件或缺页这几类具体原因 |
| 签名前置有没有生效 | 安全启动状态查询 | 是否启用 | 启用时模块需要被信任的签名 |
| 有没有冲突驱动占用 | `lsmod` | 开源显示驱动的条目 | 有占用则 NVIDIA 模块的安装与加载不成立 |
| 显存注册模块有没有加载 | `lsmod` | 显存注册模块的条目 | 与旧版模块互斥，两者都出现是配置冲突 |

**这张表的用法是逐行命中，不是逐行执行。** 每一行只在它上面那一行给出「需要继续查」时才执行，问题定位到哪一层就在那一层合上，不把整张表跑完。

## 故障现场定位表

这张表把常见现象映射到第一份读数，用来决定第二个动作落在哪个对象上。

| 现象 | 先看什么 | 判据 | 转向哪一步 |
| --- | --- | --- | --- |
| 管理工具报无法与驱动通信 | 模块清单与节点清单 | 模块缺失与节点缺失会给出同一句报错 | 模块缺失查构建与加载；节点缺失查创建与权限 |
| 管理工具报用户态与内核版本不匹配 | 内核模块版本与用户态库版本 | 两者不一致即为不匹配 | 判断是升级后未重启，还是模块未为新内核重建 |
| 管理工具正常、计算程序起不来 | 两边的节点清单 | 计算程序还需要 UVM 节点 | 缺 UVM 节点时查创建与注入，而不是改版本 |
| 内核升级并重启后失联 | 构建系统状态与模块文件 | 新内核下没有编出来的模块 | 查头文件、编译器与签名前置 |
| 模块存在但装不进内核 | 内核日志与安全启动状态 | 报错文本指向签名被拒绝 | 转入签名信任链的核对 |
| 模块加载中途失败 | 内核日志与固件版本字段 | 日志指向固件文件 | 核对模块与固件是否来自同一个包事务 |
| 显存直连性能不达预期 | 显存注册模块的条目 | 模块未加载时退化为经主机内存中转 | 核对模块与 RDMA 栈的编译顺序 |
| 计数自己归零 | 持久化模式字段 | 未保持初始化时易失性计数会清零 | 换用累计计数，或说明这段趋势不可用 |
| 性能对比发现同池节点数字离散 | 四个版本字段与模块来源 | 版本或构建方式漂移会让读数不可比 | 先对齐版本，再解释性能差异 |

## 取证材料各自的落点

取证材料与诊断命令不同：诊断是为了当场定位，取证是为了事后复盘，因此它要求**时机先于完整性**。

| 材料 | 取值入口 | 落在哪里 | 采集时机 | 只读还是影响状态 |
| --- | --- | --- | --- | --- |
| 整机取证快照 | 驱动自带的取证脚本 | 一个压缩包，含驱动、模块、节点、内核日志与拓扑 | 变更或处置之前 | 采集过程会打开设备 |
| 内核日志中的驱动记录 | 内核日志时间戳过滤 | `NVRM` 前缀的加载与运行记录 | 变更或处置之前 | 只读 |
| 模块与节点清单 | 模块清单与节点列表 | 模块条目与设备文件 | 变更之前 | 只读 |
| 版本字段 | 内核模块版本与用户态库版本 | 两个版本读数 | 变更之前与变更之后各一次 | 只读 |
| 固件版本字段 | 管理工具的固件版本 | 固件版本 | 与版本字段同一时刻 | 只读 |
| 作业侧通信日志 | 作业运行期间的日志输出 | 初始化段的路径与版本信息 | 作业运行期间 | 只读 |

有一类材料必须在动作之前取：**属于「GPU 初始化到反初始化」这一段生命周期的计数会被反初始化清零**，而取证脚本本身会打开设备，可能触发这次初始化。因此顺序是先取那些会被清零的计数，再跑范围更大的取证脚本。

## 采样与记录纪律

- **累计量取差分**：错误计数是累计值，单次绝对值没有意义，判据是两次读数之差在运行期间的增长。
- **瞬时量单独记**：利用率与功耗是瞬时值，采集时刻不同就不能相减。
- **两个版本必须成组**：内核模块版本与用户态库版本要一起记，只记一个发现不了漂移。
- **读数的可比性有条件**：同一机型、同一参数、同一亲和关系下取得的两组数字才可比。
- **取证顺序先于取证完整性**：先取会消失的，再取范围大的。

## 影响范围较大的操作

下面这些操作会中断同一台机器上的**全部**作业，影响范围不是单个进程或单张卡。它们只允许在实验节点上验证；在生产节点上执行前必须完成隔离，且回滚路径要先写清。

| 操作 | 影响范围 | 必备前置 | 回滚路径 |
| --- | --- | --- | --- |
| 卸载或重载驱动模块 | 整机全部依赖该驱动的作业中断 | 现场已取证、作业已退出 | 重新加载模块或重启，使两边版本一致 |
| 驱动升级与降级 | 整机全部作业中断 | 变更前版本清单与取证材料齐备 | 重新安装变更前的版本并重启 |
| 显卡固件刷新 | 整机全部作业中断，部分固件不可降级 | 事先确认该固件能否回退 | 按厂商工具支持情况回退；不可回退时按变更前记录重建 |

```bash
# 验证：一次驱动栈体检的最小读数（只读）
lsmod | grep -E '^nvidia'; ls -l /dev/nvidia*; cat /proc/driver/nvidia/version
```

上面一条命令覆盖「模块、节点、内核模块版本」三个判定的取值入口；数值与清单随机型、驱动四元组与内核版本变化，任何对照使用的数值仅示意、不代表你的环境。

## 常见故障与排查方向

下面四个场景把故障现场定位表给出的第一份读数继续走完：每个场景先写现场，再写先读什么，然后写读到什么就转往哪一步，最后写一份合格的回答应当包含什么。前三个场景设定在单机档位，结论只覆盖主机侧对象；场景四设定在双机直连的实验环境，结论同样只落在主机侧的模块层。场景里的机器规格、时间线与报错文本都是具象设定，用来练判断，不代表你的环境。

### 场景一：内核升级重启后，管理工具报无法与驱动通信

**现场**：一台 8 卡训练节点，夜间补丁窗口升级了内核并重启。早班值班发现管理工具只返回一句 `couldn't communicate with the NVIDIA driver`，机器上已经没有作业。变更记录里只有一句「例行内核补丁」，没有驱动相关的任何记录，因此这台机器的模块属于哪一种构建方式也只能现场确认。

**先看什么**：这句报错的含义是用户态找不到可用的内核模块或设备，它可能来自构建、签名、占用或固件中的任何一环。先取一轮只读读数，把范围缩到其中一环再动手。

```bash
uname -r                                    # 验证：当前内核版本，与构建系统状态里的内核行对照
lsmod | grep -E '^nvidia'                   # 验证：内核态这一层起来没有
dkms status                                 # 验证：当前内核这一行的模块构建状态
modinfo -F filename nvidia                  # 验证：当前内核下有没有模块文件、它落在哪个目录
journalctl -b -k | grep -i -E 'NVRM|reject|nouveau|firmware'  # 验证：加载失败的直接原因
```

**读到什么就转往哪一步**：

- 若模块清单里没有任何 `nvidia` 行，则内核态这一层没起来，现象与设备节点无关，不要转去查 `/dev` 与权限。此时看构建系统：若 `dkms status` 在当前内核那一行不是已完成状态，则问题落在模块构建这一段——新内核下根本没有编出可加载的模块；先确认新内核的头文件是否已经装上，补齐后让构建系统重编，而不是直接重装整套驱动。
- 若模块文件存在、内核日志里却是 `Key was rejected by service` 一类记录，则问题落在签名前置：这台机器的模块是现场编译并用本机密钥签名的，而这把密钥没有注册进机器所有者密钥列表；转入签名信任链的核对，重编模块解决不了签名问题。
- 若日志里出现开源显示驱动占用设备的记录，则黑名单没有随这次启动生效，常见原因是只改了黑名单配置而没有重建 initramfs；补全黑名单、重建 initramfs 并重启。
- 若构建系统显示已完成、日志却指向固件文件缺失或与模块版本不配，则问题落在模块加载时的固件读入环节：模块与它要读入的 GSP 固件文件不来自同一个包事务；核对两者是否同属一次安装，必要时按同一事务重装，让模块与固件一起更新。
- 若以上分支的处置都需要时间、而恢复业务优先，则可以看一条退路：`dkms status` 里旧内核那一行若仍是已完成状态，从引导项选旧内核启动即可先恢复业务，新内核的构建问题留到下一个窗口处理。

**一份合格的回答**应当说清：结论落在构建、签名、冲突占用还是固件这四个分支中的哪一个；依据是构建系统状态行与内核日志中签名或占用相关的具体记录；边界是「新内核下没有可加载模块」这条结论只对现场编译的模块来源成立，预编译路径下这是内核升级后的预期状态而不是故障；动作是补头文件重编、处理签名信任链、补黑名单重建 initramfs 还是回退旧内核，并写清各自用哪一条读数验收。动手重编之前先把失败那次的内核日志存下来，因为重编成功的同时失败现场就被覆盖了。

### 场景二：升级驱动后未重启，管理工具报版本不匹配

**现场**：下午变更窗口给一台已隔离的训练节点升级了驱动包，窗口计划里没有安排重启。变更后管理工具报 `Failed to initialize NVML: Driver/library version mismatch`。调度侧确认节点上没有作业，但机器上常驻一个监控代理。业务方希望不重启就把节点修好。

**先看什么**：这句报错的含义是用户态库已经换成新版本、而内核里加载的仍是旧模块，变更停在重新匹配这一段。能不能不重启，取决于设备上还有没有进程占用，因此先读两个版本字段与占用清单。

```bash
cat /proc/driver/nvidia/version        # 验证：内核已加载模块的版本（管理工具起不来时它仍可读）
dpkg -l | grep -i nvidia               # 验证：磁盘上驱动与用户态库的版本（Debian 系；RHEL 系用 rpm -qa）
fuser -v /dev/nvidia* 2>/dev/null      # 验证：设备节点上的进程占用
```

**读到什么就转往哪一步**：

- 若内核模块版本是旧的、包管理器里的是新的，则确认变更停在重新匹配这一段，与包本身无关。此时看占用清单：若设备上没有任何进程，则具备不重启的处置条件，可以重载模块使两边版本一致；重载属于影响范围较大的操作，它会中断同机全部作业、只在节点确无作业时执行，执行前先按变更前记录确认能退回，回滚路径是重新加载原版本模块或重启。
- 若占用清单里还有进程，则要分清它是谁：监控代理只有在真的打开了设备节点时才构成占用，残留的计算进程才是必须等它退出的那一类。不要为了让设备空出来去结束不认识的进程，先确认它属于哪个业务。
- 若占用清不掉，或机器上还有别的约束，则把重启纳入下一个窗口，不要为了省一次重启在带占用的设备上强行重载。
- 若两个版本字段一致、而报错仍在，则现象不由版本解释，按模块清单、节点清单、内核日志的顺序重新取一轮读数，不要在重启与否上继续纠缠。

**一份合格的回答**应当说清：结论是变更停在重新匹配这一段，而不是包损坏；依据是内核模块版本、包管理器版本与设备占用清单这三份读数的组合；边界是「无占用可重载」只在已隔离的单机上成立，占用未清时重载与重启一样会中断作业；动作是重载或排期重启，并附回滚路径。无论选哪一条，先把本次两份版本读数与占用清单补进变更记录，否则下一次变更仍然没有对照对象。

### 场景三：管理工具正常，计算程序全部初始化失败

**现场**：一台新交付的单机节点做基线验收，管理工具能列出全部 8 张卡，驱动、CUDA、通信库与 RDMA 栈四项版本也已按基线卡格式成组记录。随后在宿主机上直接运行一个最小 CUDA 程序，初始化阶段即失败；换几个已知正常的程序，结果相同。

**先看什么**：管理工具走的管理链路只需要控制设备与显存设备，计算程序还要能打开统一内存设备，两组对象必须分开读。

```bash
lsmod | grep -E '^nvidia'              # 验证：核心行的 Used by 列有没有挂上统一内存模块
ls -l /dev/nvidia*                     # 验证：节点清单里有没有统一内存设备节点
grep -i nvidia /proc/devices           # 验证：内核登记的设备号（统一内存设备的主设备号是动态分配的）
```

**读到什么就转往哪一步**：

- 若核心模块在、而 `Used by` 列没有统一内存模块，则计算链路的内核侧没有挂上：手工加载该模块后重跑最小程序；同时必须查清它为什么没有随核心模块一起加载——安装不完整或加载配置缺失都会让下次重启复发。
- 若模块已挂、而 `/dev` 下没有对应节点，则问题落在节点创建这一段：核对 udev 规则与发行版的兜底创建工具是否正常工作。不要用 `mknod` 手工补节点当作修复，因为主设备号是动态分配的，写死的设备号在下一次启动就会对错号。
- 若模块与节点两组清单都齐全，则驱动栈这一层不能解释现象，转向 CUDA 侧核对：应用链接的运行时库是否用到了当前驱动不具备的能力，这类情况的报错文本形如 `cudaErrorCallRequiresNewerDriver`。从这一步开始，问题已经不在驱动与内核模块的范围内。
- 若现象只在容器内出现、宿主机上两组清单齐全，则问题在注入清单：容器内的节点集合由运行时从宿主机注入，管理链路注入完整不代表计算链路完整。注入机制本身不属本篇范围，本篇能给出的结论是「宿主机侧两组清单逐项齐全」这一对照基准。

**一份合格的回答**应当说清：结论落在统一内存模块未挂、节点未创建，还是驱动栈之外；依据是模块清单的 `Used by` 列、`/dev` 节点清单与 `/proc/devices` 三者的逐项对照；边界是宿主机的结论不自动覆盖容器内，容器内要用同一份清单再对一遍；动作是加载模块或修复节点创建机制，验收方式是在宿主机上重跑同一个最小程序，而不是只看管理工具恢复正常。

### 场景四：显存直连测试的带宽退回主机中转的水平

**现场**：双机直连的实验环境，驱动与 RDMA 栈安装完成后做显存直连的对照测试：同一组参数分别在注册显存与注册主机内存两种缓冲类型下运行，两组带宽几乎相同，都落在中转那一档的量级。链路侧已由负责网络的一方确认无损配置与计数器没有异常。

**先看什么**：带宽退回中转量级，主机侧最常见的原因是显存注册模块没有生效——它安装之后不会自动加载，「装了」与「加载了」是两回事。先读模块清单与它的加载记录。

```bash
lsmod | grep -i peermem                # 验证：显存注册模块的条目是否存在、新旧两个模块有没有并存
journalctl -b -k | grep -i peermem     # 验证：它的加载记录与失败原因
```

**读到什么就转往哪一步**：

- 若模块清单里没有任何显存注册模块的条目，则先加载它再复测。若加载失败、且日志指向符号或接口缺失，则说明它编译时没有找到 RDMA 栈提供的接口，这是安装顺序问题：它要求在 RDMA 栈就位之后编译。按正确顺序重装并重编，在这之前不要把带宽问题往链路侧推。
- 若旧版模块 `nv_peer_mem` 与新版 `nvidia_peermem` 同时出现在清单里，则两者互斥、属于配置冲突：卸除旧模块并确认它不会随启动自动复活，然后复测。
- 若新模块正常加载且无互斥，则主机侧这一层已经正常，剩下的问题是应用是否真的走了显存直连路径。路径确认与带宽口径不属于本篇范围，把「模块层已验证」这个结论连同模块清单读数交接给负责测量的一方。

**一份合格的回答**应当说清：结论是模块未加载、编译顺序错、互斥冲突，还是主机侧无异常；依据是模块清单条目与它的内核日志加载记录；边界是主机侧正常之后带宽仍不达预期时，问题已不在本篇范围，不能留在驱动层反复重装；动作是加载模块、按正确顺序重编或卸除旧模块，回滚是卸掉它退回经主机内存中转的路径，这一档回滚随时可行，代价是功能可用而性能退回。

**第一反应不要做什么**：不要一上来就跑完整套体检脚本；不要在同一个报错文本上直接归因；不要在第一次读数还没看之前先取第二次；不要在机器上还有作业时重载模块；不要在取证之前先做会改变状态的动作。正确的顺序是先用一份读数定位层次，再用第二份读数定位原因，取证排在任何会改变状态的动作之前。
