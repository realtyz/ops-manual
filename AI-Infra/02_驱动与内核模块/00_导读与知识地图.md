## 知识地图

### 一次驱动的安装、升级或回滚在主机上改动了哪些对象：六段

本章的主链是**一次驱动安装、升级或回滚**。它从包或安装包被解开开始，经过内核模块构建、加载、设备节点创建、用户态库替换，最后落到内核重启或模块重载后的重新匹配；这条链路上任何一段没走完，表现出来的都只是「GPU 用不了」这一句笼统的话。

| 段 | 这一段在做什么 | 到这里要能说清 |
| --- | --- | --- |
| 1 安装方式与包落地 | 发行版仓库包、NVIDIA 官方仓库包或 `.run` 安装包把文件放到磁盘上；升级时同一事务把旧包移出 | 三种方式为什么互斥，生产上为什么基本不用 `.run`，以及旧对象（含旧固件文件）随哪一步退出 |
| 2 内核模块构建 | DKMS 用本机 kernel headers 现场编译并按本机密钥签名，或由发行版按内核版本提供预编译模块 | 这台机器是哪一种、内核升级后分别会怎样；Secure Boot 下签名从哪来、`nouveau` 有没有让位 |
| 3 模块加载 | 模块被加载进内核并读入 GSP 固件，`lsmod` 里出现 `nvidia`、`nvidia_uvm` 等条目 | 五个模块各管什么；`nvidia_peermem` 为什么不会自动加载；GSP 固件缺失或不匹配时报错长什么样 |
| 4 设备节点创建 | udev 按规则创建设备节点，`nvidia-modprobe` 作为发行版无关的兜底 | 节点的属主与权限从哪来，主设备号哪一个是动态分配的 |
| 5 用户态库就位 | `libcuda.so`、`libnvidia-ml.so` 等被安装并被进程链接 | `nvidia-smi` 与 CUDA 各自依赖哪一条链路 |
| 6 重新匹配 | 内核重启或模块重载之后，内核模块版本与用户态库版本必须对上 | 不匹配时的两类报错文本，以及不重启的处置边界 |

**贯穿本章的三问**：报错落在三个层次中的哪一层；这台机器的模块是怎么来的（DKMS 还是预编译、开源还是专有）；这一项版本与四元组里其它三项的约束方向是什么。

**与第 01 章的分工**：第 01 章的体系篇讲一次驱动变更的时间线——改之前记录什么、怎么取证、改之后怎么复测；本章的六段讲的是那次变更之中，包落地以后主机上哪些对象被改动了。事故复盘沿第 01 章的时间线走，定位到「执行变更」这一段之后，换用本章的对象链往下查。

### 三个跨阶段的核对对象

| 核对对象 | 它贯穿哪几段 | 每一处读什么字段 |
| --- | --- | --- |
| 版本一致性 | 它贯穿段 2 到段 6，因为内核模块版本、GSP 固件版本、用户态库版本与 CUDA toolkit 版本是几个独立的量 | 在段 2 读 `modinfo nvidia` 的 `version` 与 `dkms status`；在段 3 读 `lsmod` 的模块清单，读 `nvidia-smi -q` 的 `GSP Firmware Version` 与 `dmesg` 里 GSP 固件的加载记录；在段 5 读包管理器里 `nvidia` 与 `libnvidia-*` 的版本；在段 6 读 `/proc/driver/nvidia/version` 与 `nvidia-smi` 的版本是否一致 |
| 设备节点的归属 | 它贯穿段 4 到段 6，因为节点的创建者与使用者分属内核、udev 与容器运行时三方 | 在段 4 读 `ls -l /dev/nvidia*` 的属主与权限位；在段 5 读进程能否打开 `/dev/nvidia-uvm`；在段 6 在容器内读同一份清单并与宿主机逐项比对 |
| 状态的持久性 | 它贯穿段 3、段 5 与段 6，因为 GPU 在最后一个客户端退出时会被反初始化，一批状态随之清零 | 在段 3 读 `nvidia-smi -q` 的 Persistence Mode 字段；在段 5 读 `systemctl status nvidia-persistenced`；在段 6 读 ECC 段的 Volatile 与 Aggregate 两组计数是否出现「自己归零」 |

## 术语速查

| 名词 | 一句话解释 | 在哪一篇展开 |
| --- | --- | --- |
| DKMS | 装包或内核升级时用本机 kernel headers 现场编译内核模块的框架，编译失败会让新内核下没有 `nvidia.ko` | 原理：模块家族与两套 flavor |
| 预编译模块 | 由发行版按内核包版本预先编好的模块，内核升级后要等对应版本的新包 | 原理：模块家族与两套 flavor |
| 开源与专有 flavor | 同一批内核模块的两套实现，515 系列起并存，560 系列起开源成为默认安装并要求 Turing 或更新 | 原理：模块家族与两套 flavor |
| GSP 固件 | GPU System Processor 固件，随包装进 `/lib/firmware/nvidia/<版本>/`，模块加载时读入；文件缺失或与模块版本不匹配时模块加载失败 | 原理：模块家族与两套 flavor |
| `nouveau` | 内核自带的开源 NVIDIA 驱动，会占住 GPU 让 NVIDIA 驱动装不上或装不完全；安装前须黑名单并重建 initramfs | 原理：模块家族与两套 flavor |
| `nvidia_uvm` | 提供统一内存与统一地址空间的内核模块，CUDA 上下文依赖它 | 原理：驱动栈的三个层次 |
| `nvidia_peermem` | 把 GPU 显存注册给 RDMA 子系统以支持 GPUDirect RDMA 的模块，取代了旧的 `nv_peer_mem`，且不会自动加载 | 原理：模块家族与两套 flavor |
| `nvidia-modprobe` | NVIDIA 提供的 setuid 工具，用来确保模块已加载、设备节点已存在；发行版通常已由 udev 覆盖这件事 | 原理：设备节点的归属与访问控制 |
| MOK | 固件里保存的机器所有者密钥列表，Secure Boot 下自签名模块的公钥必须注册进去才会被加载 | 原理：模块家族与两套 flavor |
| 内核模块版本与用户态库版本 | 两个分别由 `/proc/driver/nvidia/version` 与 `nvidia-smi` 反映的版本，不一致即版本不匹配 | 原理：驱动栈的三个层次 |
| Persistence Mode 与 Persistence Daemon | 保持 GPU 处于初始化状态的两种手段，前者是内核态的旧机制且不跨重启，后者是用户态后台进程 | 原理：持久化与非持久状态 |
| Volatile 与 Aggregate ECC | 两组生命周期不同的 ECC 计数，前者随 GPU 反初始化清零，后者基本只在手动清除时归零 | 原理：持久化与非持久状态 |
| minor version compatibility | 同一个 CUDA 大版本族内，较新 toolkit 编译的应用可以跑在较老驱动上的机制 | 原理：版本四元组的约束方向 |
| forward compatibility | 跨 CUDA 大版本运行应用的手段，靠 `cuda-compat-<major>-<minor>` 包提供较新的用户态库 | 原理：版本四元组的约束方向 |

## 关键字段的读法

| 字段 | 是什么与单位 | 判据 | 与谁同看 | 转向哪一步 |
| --- | --- | --- | --- | --- |
| `lsmod` 中的 `nvidia` 行 | 核心内核模块是否已加载，以及它的引用计数 | 这一行不存在就说明内核态这一层没起来 | 与 `dkms status` 和 `dmesg` 的 `NVRM` 记录同看 | 转入「模块为什么没加载」的分支：缺 headers、签名被拒或黑名单 |
| `lsmod` 中 `nvidia` 的 `Used by` 列 | 哪些模块引用了核心模块 | `nvidia_uvm` 出现在这一列说明 UVM 已挂到核心模块上 | 与 `ls -l /dev/nvidia-uvm` 同看 | 若 UVM 缺失，CUDA 一定起不来，转入 CUDA 初始化失败的路径 |
| `couldn't communicate with the NVIDIA driver` | `nvidia-smi` 报的错，表示用户态到内核态这条链路断了 | 出现它先查模块是否加载，而不是先查 CUDA | 与 `lsmod` 的输出、`dmesg` 的 `NVRM` 记录同看 | 转入「模块为什么没加载」的分支：缺 headers、签名被拒或 `nouveau` 占用 |
| `Failed to initialize NVML: Driver/library version mismatch` | `nvidia-smi` 报的错，表示用户态库与已加载内核模块的版本不一致 | 出现它说明段 6 的重新匹配没完成，常见诱因是升级后未重启或未重载 | 与 `/proc/driver/nvidia/version` 和 `nvidia-smi` 显示的版本同看 | 先判断是「升级后未重启」还是「模块未为新内核重编」，再定重启或重载 |
| `/dev/nvidia-uvm` 的主设备号 | UVM 字符设备的主设备号，由内核动态分配 | 它**不是**固定值，脚本里写死会对不上；取值方式是读 `/proc/devices` | 与 `/dev/nvidiactl` 的固定号 195 同看 | 容器内清单比对时以实际设备号为准，不以记忆中的号为准 |
| `nvidia-smi -q` 的 `Persistence Mode` | GPU 是否处于保持初始化的状态 | 取 `Enabled` 时客户端退出不会反初始化 GPU | 与 `systemctl status nvidia-persistenced` 同看 | 若为 `Disabled`，则该机的 Volatile ECC 计数不能当长期证据 |
| `cudaErrorCallRequiresNewerDriver` | CUDA 运行时返回的错误文本，表示用到了新版驱动才有的能力 | 出现它说明当前驱动低于应用所需 | 与 `nvcc --version` 和 `/proc/driver/nvidia/version` 同看 | 转入升级驱动或改用不依赖该特性的构建这两条路 |
