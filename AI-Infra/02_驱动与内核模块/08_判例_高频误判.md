# 高频误判

驱动栈这一层的事故，报错文本往往只有一两句，而可以解释它的机制有很多；误判的共同点不是读错了字段，而是**把一句报错直接等同于一个根因**。下面这些判例按「场景、常见误判、判据、结论、出处」逐条给出，判据里的字段名与单位与前面的读法保持一致。

### 「管理工具能跑，说明驱动装好了」

- **场景**：在一台新装的机器上执行管理工具，能正常列出 GPU，于是认为驱动安装完成，随后启动训练任务，任务在初始化阶段失败。
- **常见误判**：把管理工具可用等同于计算能力可用。它看起来成立的原因在于两者确实依赖同一批内核模块与部分节点。
- **判据**：管理工具走的是管理库那条链路，只需要控制设备与显存设备；计算程序还要能打开统一内存设备。判据是两组节点的清单是否都齐全，同看对象是 `/dev` 下的节点列表与模块清单。条件会变：容器环境里差异最容易出现，因为注入清单由运行时决定。
- **结论**：管理工具能跑只证明管理链路通了，不构成计算链路可用的证据。
- **出处**：NVIDIA 驱动安装指南的 Device Node Verification 一节（各类节点的归属与用途）。

### 「报无法与驱动通信，就重装驱动」

- **场景**：管理工具报出「无法与 NVIDIA 驱动通信」，第一反应是驱动包损坏，直接重装整套驱动。
- **常见误判**：把链路不通当成包损坏。它看起来成立的原因在于重装有时确实能修好，因为重装过程顺带重建了模块。
- **判据**：这句话的含义是「用户态找不到可用的内核模块或设备」，模块缺失与节点缺失会给出同一句报错。判据是先看模块清单与构建系统状态，同看对象是内核日志里的加载记录。条件会变：内核升级之后模块没有为当前内核重建时，重装是治标；真正要补的是构建前置。
- **结论**：这句报错定位的是「内核态或设备节点这一侧」，不是包是否损坏。
- **出处**：NVIDIA 驱动安装指南的 Kernel Modules 一节（模块清单与内核升级后的重建要求）。

### 「用户态与内核版本不匹配，是包坏了」

- **场景**：升级驱动后立刻执行管理工具，报出用户态库与内核模块版本不匹配，于是判断新包有问题。
- **常见误判**：把它当成安装失败。它看起来成立的原因在于报错确实出现在升级之后。
- **判据**：这句报错说明用户态库已经换成了新版本、而内核里加载的仍是旧模块，两者不在同一个驱动版本上。判据是比较内核模块版本与用户态库报告版本，同看对象是包管理器里的驱动版本。条件会变：有些机器可以在无占用时重载模块，有些必须重启，这取决于当前是否有进程占用设备。
- **结论**：版本不匹配描述的是变更没有走完，而不是包损坏。
- **出处**：NVIDIA 驱动持久化文档（模块卸载与重启对内核态状态的影响）。

### 「包管理器里的版本一致，两个版本就一致」

- **场景**：用包管理器查询到驱动包版本一致，于是认为内核模块与用户态库版本也一致，不再读取内核模块版本字段。
- **常见误判**：把包版本当成运行版本。它看起来成立的原因在于磁盘上的文件确实由这个包提供。
- **判据**：内核模块版本与用户态库版本是两个分别由不同字段反映的量，前者看内核已加载模块上报的版本，后者看用户态库报告的版本。判据是这两个字段相等，同看对象是包管理器里的版本。条件会变：升级后未重启时，磁盘是新的、内核里还是旧的，三份读数会出现两两不同。
- **结论**：包版本是磁盘状态，两个版本字段是运行状态，二者不能互相替代。
- **出处**：NVIDIA 驱动包自带的 `nvidia-smi(1)` 手册页（版本字段的口径）。

### 「内核升级与驱动升级可以分开做」

- **场景**：为了打安全补丁只升级内核，认为驱动没有动就不需要处理。
- **常见误判**：把内核与驱动视为彼此独立的升级对象。它看起来成立的原因在于两者确实由不同的包管理。
- **判据**：现场编译的模块绑定具体内核版本，内核升级后需要为它重新编译；预编译的模块要等发行版为新内核提供对应包。判据是构建系统对当前内核的状态，同看对象是模块文件在磁盘上的实际路径。条件会变：预编译路径下，内核升级后一段时间内新内核没有可加载模块是预期状态，而不是故障。
- **结论**：内核升级会连带改变驱动模块的可加载性，两者必须一起规划。
- **出处**：NVIDIA DKMS 使用说明与驱动安装指南的 Kernel Modules 一节。

### 「装了显存注册模块，显存直连就生效了」

- **场景**：确认显存注册模块已经安装，于是认为显存直连已经生效，不再检查它的加载状态与版本。
- **常见误判**：把「安装」当成「加载」。它看起来成立的原因在于模块文件确实在磁盘上。
- **判据**：该模块不会随核心模块自动加载，且它要用 RDMA 栈提供的接口来编译，加载失败的原因也可能出在栈一侧而不是驱动一侧。判据是模块清单里它的条目是否存在，同看对象是它与旧版模块是否互斥、驱动的安装顺序是否正确。
- **结论**：显存注册模块是否生效，看的是它有没有被加载，不是它有没有被安装。
- **出处**：NVIDIA GPUDirect RDMA 文档（模块前置、互斥关系与不会自动加载这一条）。

### 「用持久化模式开关可以代替守护进程」

- **场景**：在一台节点上把持久化模式设为保持状态，认为重启之后仍然保持。
- **常见误判**：把两种保持手段当成同一种。它看起来成立的原因在于管理工具里执行的是同一条命令。
- **判据**：内核态的旧机制不跨重启，用户态的守护进程随服务自启而跨重启；管理工具会优先通过守护进程设置，守护进程未运行时才回落到旧机制。判据是模式字段与服务状态一起读，同看对象是重启前后两组读数。
- **结论**：只凭一条设置命令不能断定重启后的行为，必须把守护进程是否在运行一起看。
- **出处**：NVIDIA 驱动持久化文档（两种手段的实现层与官方定位）。

### 「易失性计数归零说明硬件恢复」

- **场景**：监控里一组显存错误计数归零，于是判断硬件问题消失，把节点重新放回池内。
- **常见误判**：把生命周期清零当成状态改善。它看起来成立的原因在于曲线确实变成了一条从零开始的新曲线。
- **判据**：易失性计数挂在「GPU 初始化到反初始化」这一段生命周期上，最后一个客户端退出就会归零；累计计数才跨客户端保留。判据是持久化模式字段的取值，同看对象是两组计数各自的变化。
- **结论**：归零可能只是生命周期结束，不能据此判断硬件恢复。
- **出处**：NVIDIA 驱动持久化文档的 Data Persistence 一节（三类生命周期与清零时机）。

### 「容器里管理工具正常，说明注入完整」

- **场景**：容器里执行管理工具成功，于是认为设备注入没有问题，随后容器内的计算程序初始化失败。
- **常见误判**：把管理链路的注入完整等同于全部注入完整。它看起来成立的原因在于容器内确实能看到 GPU。
- **判据**：容器内的设备由运行时从宿主机已有节点注入，管理工具与计算程序依赖的节点集合不同。判据是容器内与宿主机的节点清单逐项一致，同看对象是统一内存设备是否也在清单里。条件会变：注入方式与容器配置决定进程能否打开节点，这部分由容器运行时负责，不在驱动这一层。
- **结论**：注入是否完整要以两组节点清单逐项对照为准，而不是管理工具能否运行。
- **出处**：NVIDIA 容器工具链文档（设备注入的对象与方式）。

### 「模块文件里的版本就是驱动版本」

- **场景**：用模块信息工具读出模块文件版本，把它当作整机驱动版本填进记录。
- **常见误判**：把模块版本当成驱动版本。它看起来成立的原因在于模块确实属于驱动。
- **判据**：驱动在主机上至少有两个可比的版本量——内核已加载模块的版本与用户态库报告的版本，模块文件版本只是磁盘上的产物。判据是两个运行期字段是否相等，同看对象是包管理器里的版本。
- **结论**：记录驱动版本要同时记运行期的两个字段，只记模块文件版本会发现不了漂移。
- **出处**：NVIDIA 驱动安装指南的 Post-installation Actions 一节。

## 值班口径

这些判例可以归成四类共同成因。第一类是把某一层或某个环节的读数当成整条链路的结论：管理工具可用只覆盖管理链路，包版本一致只覆盖磁盘状态，模块已安装只覆盖磁盘产物。第二类是读数口径：把上限当实际值、把生命周期清零当状态改善、把文件版本当运行版本，共同修正是先问「这个字段代表的是哪一段时间、哪一份对象」。

第三类是升级时序：内核与驱动、驱动与 RDMA 栈、模块与固件，三组对象都有先后依赖，任何一组被拆开都会在延后的时刻暴露。第四类是加载前置：签名与冲突不属于驱动自身，却决定模块能不能进内核；显存注册模块还有互斥关系。任何一类的结论依赖某个版本或某个默认值时，都必须同时给出驱动、CUDA、通信库与 RDMA 栈四项，缺任一项时读数不构成结论。

**第一反应不要做什么**：不要把管理工具能跑当成驱动装好；不要看到链路不通就重装驱动；不要把版本不匹配当成包损坏；不要用包版本代替运行版本；不要把内核升级当成与驱动无关；不要以为显存注册模块会自动加载；不要用一条持久化设置命令代替对重启行为的判断；不要因为计数归零就放行节点；不要用容器内管理工具能否运行代替节点清单比对；不要把模块文件版本当成整机驱动版本。正确的顺序是先判层次、再取该层字段、最后才谈改动。
