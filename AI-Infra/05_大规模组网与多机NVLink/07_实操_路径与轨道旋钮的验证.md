# 路径与轨道旋钮的验证

验证路径的目标是证明「这次通信实际走了哪条路」，不是寻找一个看起来更快的参数。一次有效的验证必须同时拿到三类证据：**通信库日志里的选路结论、主机 / fabric 侧的计数变化、变更前后的对照结果**。只有日志没有计数，无法证明数据真的走了那条路；只有计数没有日志，无法把计数归到具体 rank 与设备。

## 验证前先固定口径

| 项 | 要固定什么 | 原因 |
| --- | --- | --- |
| 测试程序 | 使用同一个最小 NCCL 测试，例如 `all_reduce_perf`，固定消息大小与进程数 | 参数变了，路径和性能结论都不可比 |
| 节点与 rank | 固定参与节点、GPU、进程数与放置 | 作业放置变化会改变 rail 使用 |
| 采样时间 | 记录测试前后计数器时间点 | 计数器是累计值，必须取差分 |
| 配置基线 | 记录 NCCL 版本、驱动、RDMA 栈与固件 | 版本变化可能改变默认选路 |
| 变量数量 | 一次只改一个变量 | 多变量同时改会失去归因能力 |

`NCCL_DEBUG=INFO` 与 `NCCL_DEBUG_SUBSYS=...` 是排障用配置，不应作为生产常驻配置长期保留。日志应落盘，测试结束后恢复原配置。

## 第一步：读生效配置

先确认进程实际会看到什么，而不是只看启动脚本：

```bash
env | grep '^NCCL_'
cat /etc/nccl.conf
cat "$HOME/.nccl.conf"
test -n "$NCCL_CONF_FILE" && cat "$NCCL_CONF_FILE"
```

这几条命令分别读取进程环境、系统级配置、用户级配置与指定配置文件。若它们互相冲突，不能靠猜优先级下结论；应以 NCCL 日志开头打印的生效值为准，再回到对应载体修改。

至少记录这些变量：

| 变量 | 它控制什么 | 读法 |
| --- | --- | --- |
| `NCCL_IB_HCA` | 可用 HCA 清单，以及可选 port / rail / plane 身份 | 条目形式为 `<hca>[:<port>[:<rail>[:<plane>]]]` |
| `NCCL_CROSS_NIC` | 同一 ring / tree 是否允许不同节点使用不同 NIC | rail-optimized fabric 与同交换机 fabric 的合适取值不同 |
| `NCCL_IB_RAIL_POLICY` | 支持的 ConnectX SuperNIC 自动 rail / plane 分配策略 | 自动分配不会覆盖用户在 `NCCL_IB_HCA` 中显式给出的 rail / plane |
| `NCCL_NET_MERGE_POLICY` | 物理 HCA 合并成虚拟 HCA 时按什么约束合并 | rail-optimized 系统上可用 `RAIL` 避免跨 rail 合并 |
| `NCCL_MNNVL_ENABLE` | 是否启用 MNNVL 自动探测或强制启用 | `0` 禁用，`1` 强制，`2` 自动探测 |
| `NCCL_MNNVL_UUID` / `NCCL_MNNVL_CLIQUE_ID` | 人工覆盖 MNNVL 域标识 | 正常由 Fabric Manager 分配，不应作为常规调优项 |

`NCCL_IB_HCA` 中，`=` 表示精确匹配，`^` 表示排除列表。写 `mlx5_1` 而不写 `=mlx5_1` 时，前缀匹配可能把 `mlx5_10` 到 `mlx5_19` 一并选中；这里是「怎么只配了一张卡却出现多张卡」的常见来源之一。

## 第二步：带日志运行最小测试

单节点或小规模验证可用：

```bash
NCCL_DEBUG=INFO \
NCCL_DEBUG_SUBSYS=INIT,NET,GRAPH,ENV \
NCCL_DEBUG_FILE=/tmp/nccl.%h.%p.log \
./build/all_reduce_perf -b 8 -e 8M -f 2 -g 1
```

多机验证应通过调度器或 MPI 固定节点与进程布局；示例形态如下：

```bash
mpirun -np 2 -N 1 \
  -x NCCL_DEBUG=INFO \
  -x NCCL_DEBUG_SUBSYS=INIT,NET,GRAPH,ENV \
  -x NCCL_DEBUG_FILE=/tmp/nccl.%h.%p.log \
  ./build/all_reduce_perf -b 8 -e 8M -f 2 -g 1
```

消息大小与进程数按现场最小可复现规模调整。这里的输出不用于性能结论，只用于路径验证；性能结论必须另建同口径基线。

日志中至少找三类行：

| 日志内容 | 它证明什么 |
| --- | --- |
| 设备探测行 | NCCL 看到了哪些 HCA、端口与能力 |
| 拓扑 / 通道行 | 每个通道或 peer 使用了哪条路径 |
| MNNVL 字段 | fabric UUID、clique、状态、healthMask 与 MNNVL 是否启用 |

典型的 MNNVL 字段包括：

```text
MNNVL busId ... fabric UUID ... cliqueId ... state ... healthMask ... degradedBw ...
MNNVL 1 cliqueId ... cliqueSize ... cliqueRank ... nvlDomainSize ...
```

`MNNVL 1` 才能证明通信库认为 MNNVL 可用；`MNNVL 0` 或没有该字段时，不能因为硬件存在就声称走了 MNNVL。

## 第三步：把日志结论映射回物理对象

从日志拿到设备名后，先建立这条链：

```text
rank → node → process → HCA / port → rail / plane → switch port
```

可用主机侧状态确认设备与端口：

```bash
ibstat
```

再用 fabric 工具核对链路与计数：

```bash
iblinkinfo
ibqueryerrors
perfquery
```

路径验证的判据是：

| 日志结论 | 计数器结论 | 能说明什么 |
| --- | --- | --- |
| 选定 NIC 0 / rail 0 | Rail 0 对应端口流量增长 | 路径与物理对象一致 |
| 选定 NIC 0 / rail 0 | Rail 1 流量增长 | 映射错误、拓扑文件过期或存在未识别流量 |
| 选定多个 HCA | 只有一个 HCA 计数增长 | 过滤、合并策略或通道建立不符合预期 |
| MNNVL 1 | RDMA 网口计数几乎不增长 | 跨机流量可能走 MNNVL，而不是 RDMA |
| MNNVL 0 | RDMA 网口计数增长 | 走了 RDMA 路径，与 MNNVL 硬件存在与否无关 |

计数必须取测试前后差分。`PortXmitData` 一类字段只说明累计传输量，不说明本次测试贡献了多少；`SymbolError`、`PortRcvErrors`、`PortXmitDiscards` 一类错误字段也必须看同一段时间内的增量。

## 第四步：做单变量对照

只在确认基线路径后，才开始改旋钮。每次只改一个变量，并重新运行同一测试。

### 对照一：限制 HCA

假设要把两张网卡分别固定在 rail 0 的两个 plane 上：

```bash
NCCL_IB_HCA='=mlx5_0:1:0:0,mlx5_1:1:0:1' \
NCCL_DEBUG=INFO \
NCCL_DEBUG_SUBSYS=INIT,NET,GRAPH,ENV \
NCCL_DEBUG_FILE=/tmp/nccl.%h.%p.log \
./build/all_reduce_perf -b 8 -e 8M -f 2 -g 1
```

验证点：

1. 日志中只出现 `mlx5_0:1` 与 `mlx5_1:1`；
2. 两者的 rail 均为 0；
3. 两者的 plane 分别为 0 与 1；
4. 对应 plane 的交换机端口计数增长；
5. 未选中的 HCA 计数没有因这次测试显著增长。

若日志符合预期但计数落在其他 rail，优先怀疑拓扑映射或接线记录，而不是继续改通信库变量。

### 对照二：控制是否跨 NIC

```bash
NCCL_CROSS_NIC=0 \
NCCL_DEBUG=INFO \
NCCL_DEBUG_SUBSYS=INIT,NET,GRAPH,ENV \
NCCL_DEBUG_FILE=/tmp/nccl.%h.%p.log \
./build/all_reduce_perf -b 8 -e 8M -f 2 -g 1
```

`NCCL_CROSS_NIC=0` 表示同一个 ring / tree 尽量使用相同 NIC，避免跨 rail；适合每块网卡接不同 rail、跨轨连接较弱的 fabric。`1` 允许不同 NIC，适合所有网卡接同一台交换机、坚持同卡并不能避免冲突的形态；`2` 是默认值，优先同卡但允许性能模型认为更好的不同网卡。

验证点不是「吞吐是否变高」，而是：

- 不同节点之间是否仍使用同一 rail；
- 跨脊流量是否按预期减少；
- 失败或慢的 rank 是否不再集中在某条 rail。

### 对照三：约束 HCA 合并

在所有网卡与 GPU 距离接近的 rail-optimized 系统上，距离逻辑可能把不同 rail 的设备合并成同一个虚拟 HCA。此时可用：

```bash
NCCL_NET_MERGE_POLICY=RAIL
```

它只合并同一 rail 分配下的设备；`railId == -1` 的未分配设备不会被合并。这个开关要与实际 rail / plane 分配一起看，否则会出现「合并被限制了，但 rail 本身没有正确分配」的假阳性。

### 对照四：验证 MNNVL

若硬件支持 MNNVL，先保持默认自动探测，或显式使用：

```bash
NCCL_MNNVL_ENABLE=2
```

验证点：

1. 所有节点的 GPU fabric 状态为 completed；
2. fabric UUID 一致；
3. cliqueId 与预期一致；
4. `healthMask` 不报告降级带宽；
5. IMEX 通道可导出并导入 FABRIC 句柄；
6. 日志出现 `MNNVL 1`；
7. RDMA 网口计数与 MNNVL 路径的预期相符。

不要用 `NCCL_MNNVL_UUID` 或 `NCCL_MNNVL_CLIQUE_ID` 来「调性能」。这两个变量会改变通信库眼中的域分组；一旦它们与 Fabric Manager 分配的真实域不一致，后续所有路径结论都会失真。

## 结果判读表

| 现象 | 更可能的问题 | 下一步 |
| --- | --- | --- |
| 日志中找不到预期 HCA | `NCCL_IB_HCA` 过滤、设备不可见、容器注入或前缀匹配问题 | 核对生效配置与设备可见性 |
| 日志选择多张 HCA，计数只动一张 | 合并策略、通道建立或测试规模不足 | 检查 `NCCL_NET_MERGE_POLICY` 与通道日志 |
| 日志选择 rail 0，计数落在 rail 1 | 拓扑映射或接线记录错误 | 核对 NIC ↔ rail ↔ switch port |
| 所有 rank 都选同一块网卡 | 显式变量、拓扑文件、设备命名或接线问题 | 先查配置，再查接线 |
| `MNNVL 0` | CUMEM、fabric 状态、UUID、clique 或 IMEX 通道不满足 | 按域状态逐项核对 |
| `MNNVL 1` 但性能低 | NVLink 域降速、算法选择或消息形态不适合 | 看 healthMask、算法日志与同口径基线 |
| 改变量后现象不变 | 变量未生效，或现象不归这一层控制 | 回到日志生效值与计数差分 |

## 变更后的收口

一次路径验证完成后应记录：

| 产物 | 内容 |
| --- | --- |
| 环境卡 | NCCL、CUDA、驱动、RDMA 栈、网卡固件、节点与 GPU 清单 |
| 生效配置 | 进程环境、系统配置文件、启动脚本中的相关变量 |
| 日志文件 | 每个 rank 的 NCCL 日志，至少包含初始化与通道建立段 |
| 计数差分 | 测试前后同一条链路的流量与错误计数 |
| 对照结论 | 变更前后路径差异，以及这个差异能解释什么 |
| 回滚状态 | 恢复了哪些临时变量，日志与调试开关是否关闭 |

**第一反应不要做什么**：不要一次修改多个 NCCL 变量；不要用 `mlx5_1` 这类前缀匹配当作精确设备选择；不要把吞吐变化当作路径证明；不要把 `NCCL_MNNVL_UUID` 与 `NCCL_MNNVL_CLIQUE_ID` 当成常规性能旋钮；不要把调试日志配置长期留在生产环境。
