# 高频误判

下面十条取自大规模 fabric 与多机 NVLink 值班中最常见的误判。每条按同一套字段展开：场景、常见误判、判据、结论、出处。判据中的计数器默认是累计值，只有写明取差分时才比较增量；凡是涉及路径的结论，都必须同时有通信库结论与物理侧计数。

### 「所有 rank 都选了同一块网卡，所以 rail 没有排上」

- **场景**：多机 NCCL 日志中，多个节点的 rank 都显示使用 `mlx5_0`，于是直接判断物理接线或 rail-optimized 配置错误。
- **常见误判**：把「选择结果相同」直接等同于「物理轨道没对齐」。它看起来成立的原因是日志确实显示流量集中在一块网卡上，但选择结果可能来自配置层而不是接线层。
- **判据**：读进程实际生效的 `NCCL_IB_HCA`、`NCCL_CROSS_NIC`、`NCCL_NET_MERGE_POLICY` 与系统级 `nccl.conf`；再读 `ibstat` 的设备清单与 topology 文件中的 NIC / GPU 关系。若 `NCCL_IB_HCA` 被写成 `mlx5_0` 而没有 `=` 精确前缀，它还可能匹配 `mlx5_10` 到 `mlx5_19`；若配置显式只允许一张卡，则这不是接线问题。
- **结论**：所有 rank 选同一块网卡只是现象，先区分显式过滤、拓扑文件、设备命名与物理接线四类原因，再决定找谁。
- **出处**：NCCL User Guide 中 `NCCL_IB_HCA` 的前缀匹配与 port / rail / plane 字段说明。

### 「UFM 显示整网健康，所以这次通信路径没问题」

- **场景**：作业部分 rank 建链失败或超时，fabric 管理平台显示链路与 SM 状态正常，于是判定网络无责。
- **常见误判**：把整网健康当作成员关系与具体路径健康的证明。整网体检覆盖链路与拓扑，但不自动证明这次通信双方处于同一 PKey / VLAN / VRF，也不证明 ECMP 选中的那条路径没有拥塞。
- **判据**：把失败 rank 映射到 node / NIC / rail / port，再核对成员关系与该时间窗内的端口、队列、拥塞计数。成员关系要看发端与收端是否都在同一分区或虚拟网络；队列与拥塞要看同一时间窗差分。
- **结论**：整网健康只能排除一部分全局故障，不能替代路径级成员关系与计数对账。
- **出处**：InfiniBand Architecture 与 UFM 文档中 SM、分区与 fabric 诊断的分工。

### 「SM 切换期间超时，所以链路硬件坏了」

- **场景**：多个节点同时出现 RDMA 超时或 NCCL 卡住，随后发现某段时间发生过 SM 主备切换，值班时仍倾向于直接换线缆或重启节点。
- **常见误判**：把控制面收敛窗口内的数据面异常当成永久硬件故障。它看起来成立的原因是超时与重传统计确实增长了，但这些计数是累计值，不区分收敛前与收敛后。
- **判据**：把 SM 事件、拓扑重算、转发表更新、作业异常与计数器采样放在同一条时间线上；只在事件稳定后继续增长的错误才支持链路故障结论。若异常集中在 10:00:00–10:00:20 的收敛窗口内，且 10:00:20 后不再增长，优先按收敛事件复盘。
- **结论**：SM 切换窗口内的超时不能直接判硬件故障，先做时间线对齐。
- **出处**：InfiniBand Architecture 与 UFM 文档中 SM 状态、拓扑发现与收敛事件的口径。

### 「一条 rail 慢，所以整网都慢」

- **场景**：某次 AllReduce 吞吐低于基线，检查发现 Rail 2 有错误或拥塞，于是得出「整网性能差」的结论。
- **常见误判**：把影响面扩大到全部 rail。rail-optimized fabric 的意义正在于故障与拥塞可以按轨道定位；一条 rail 异常只影响映射到这条 rail 的通信。
- **判据**：读 rank → node → NIC → rail 映射，再读各 rail 的流量与错误计数差分。若只有 Rail 2 的端口错误或队列增长，且慢 rank 均映射到 Rail 2，影响面就是这条 rail 及其作业，而不是整网。
- **结论**：先算影响面，再决定处置范围；不要因为一条 rail 异常隔离所有节点。
- **出处**：rail-optimized 参考架构与交换机端口计数文档。

### 「平均链路利用率不高，所以没有拥塞」

- **场景**：RoCE fabric 中脊链路平均利用率只有 30%，但集合通信延迟高，于是排除拥塞。
- **常见误判**：用平均值否定瞬时队列与散列不均。ECMP 可能把若干流集中到某条等价链路，其他链路仍空闲；集合通信的微突发也可能被较长采样窗口平均掉。
- **判据**：读更细时间粒度的队列、丢包、拥塞标记计数，并按 ECMP 等价链路逐条比较；这些字段通常是累计值，必须取差分。若某条等价链路的拥塞标记或丢弃增长，而其他链路不增长，结论是散列或路径不均，不是总带宽不足。
- **结论**：平均利用率不能否定瞬时拥塞，队列与等价路径分布才是判据。
- **出处**：以太网交换机文档中 ECMP、队列与拥塞计数的说明。

### 「机器有 MNNVL，所以跨机通信不走 RDMA」

- **场景**：节点具备多机 NVLink 硬件，值班时看到 RDMA 网卡计数增长，仍认为通信已经走 MNNVL。
- **常见误判**：把硬件能力当作路径结论。MNNVL 需要 CUMEM、fabric handle、GPU fabric 状态、相同 UUID、相同 clique 或允许跨 clique，以及 IMEX 通道可用。
- **判据**：读 NCCL 日志中的 `MNNVL busId ... fabric UUID ... cliqueId ... state ... healthMask ...` 与 `MNNVL 1 cliqueId ... cliqueSize ... nvlDomainSize ...`；同时读 RDMA 网口计数差分。只有 `MNNVL 1` 且 RDMA 计数与预期相符，才能证明路径；`MNNVL 0` 时应查域与 IMEX，而不是网卡参数。
- **结论**：MNNVL 硬件存在不是路径证据，NCCL 的 MNNVL 字段才是第一判据。
- **出处**：NCCL User Guide 中 `NCCL_MNNVL_ENABLE`、CUMEM 依赖与 IMEX domain 要求。

### 「开了 SHARP 或 NVLS，所以集合通信必然更快」

- **场景**：fabric 或 NVSwitch 域启用了集合通信卸载，性能仍低于预期，于是怀疑硬件异常。
- **常见误判**：把机制可用当作性能必然提升。SHARP / NVLS 会改变数据量、参与节点与路径，但收益取决于消息大小、集合通信类型、拓扑、算法与资源状态。
- **判据**：读通信库日志中的算法与通道结论，确认 SHARP / NVLS 是否实际参与；再读对应链路或 NVLink 域的健康状态与同口径基线。若 healthMask 报告降级带宽，或消息形态不适合卸载路径，性能不升反降是可能的。
- **结论**：SHARP / NVLS 是路径与数据量的改变，不是无条件加速开关。
- **出处**：SHARP 部署文档与 NCCL User Guide 中 NVLS、算法与性能调优的说明。

### 「拓扑文件存在，所以选路一定符合当前硬件」

- **场景**：节点曾接入交付时的拓扑文件，后来网卡更换、线缆调整或节点位置变化，NCCL 仍按旧拓扑选路，现象是部分 rail 闲置或流量集中。
- **常见误判**：把「有拓扑文件」当成「拓扑文件是当前事实」。拓扑文件是缓存或输入，不自动随硬件变更更新。
- **判据**：把 `ibstat` / `iblinkinfo` / `ibnetdiscover` 的当前拓扑与 topology 文件、golden topology 三者比较；再读 NCCL 日志中的 HCA / rail / plane 选择。若当前拓扑与文件不一致，先修文件或重新生成，再做性能测试。
- **结论**：拓扑文件必须与当前硬件对账，不能作为免检输入。
- **出处**：NCCL User Guide 中拓扑探测与网络排障说明；IB 拓扑发现工具手册页。

### 「PKey / VLAN 配错了，所以是随机网络故障」

- **场景**：部分 rank 建链失败，失败节点看似没有规律，于是按随机网络抖动处理。
- **常见误判**：忽略失败集合的结构。成员关系错误通常与 node、NIC、地址段或 rail 相关，不是随机分布。
- **判据**：列出失败 rank 的 node / NIC / rail / port 映射，再与 PKey、VLAN、VRF 成员表重叠。若失败集合全部落在缺少同一成员关系的端口或地址段上，结论是配置缺口，不是随机故障。
- **结论**：成员关系问题先看失败集合的结构，再查配置矩阵。
- **出处**：InfiniBand Architecture 中分区成员关系；以太网 VLAN / VRF 与路由文档。

### 「多平面 fabric 一定用上了所有 plane」

- **场景**：交换机上多个 plane 的链路都是 active，但性能没有达到预期，于是认为容量已经全部可用。
- **常见误判**：把链路 active 当成流量使用。若通信库只选择了一个 plane，其他 plane 只是健康资产，不提供容量。
- **判据**：读 NCCL 日志中的 HCA、rail 与 plane 字段，再读各 plane 对应端口的流量计数差分。若只有一个 plane 的 `PortXmitData` / `PortRcvData` 增长，而其他 plane 不增长，需要核对 `NCCL_IB_HCA` 的 plane 字段与合并策略。
- **结论**：多平面的容量只有被通信路径实际使用时才存在；active 不等于 used。
- **出处**：NCCL User Guide 中 `NCCL_IB_HCA` 的 rail / plane 字段与 `NCCL_NET_MERGE_POLICY` 的说明。

## 值班口径

这十条可以归成四类成因。第一类是**把配置当成路径**：`NCCL_IB_HCA`、拓扑文件、MNNVL 硬件、SHARP / NVLS 开关都只是输入或能力，不能替代日志中的实际选路结论。第二类是**把整网健康当成路径健康**：UFM、SM、链路状态只能回答各自层面，成员关系与具体端口的队列、拥塞、错误仍要单独对账。第三类是**忽略时间与差分**：SM 收敛、ECMP 重分布与链路事件都有时间窗，累计计数必须按窗口取差分。第四类是**忽略影响面结构**：失败 rank、慢 rank、使用的 rail / plane / clique 是否重叠，往往比单个绝对计数更能指向根因。

**第一反应不要做什么**：不要看到所有 rank 用同一块网卡就直接改接线；不要用整网健康结论否定路径问题；不要把 SM 收敛期超时当硬件故障；不要用平均利用率否定瞬时拥塞；不要因为 MNNVL 硬件存在就声称不走 RDMA；不要把 SHARP / NVLS 当成无条件加速；不要在拓扑文件未对账前调选路参数；不要把成员关系错误当随机故障；不要把 plane 的 active 状态当成 used 状态；不要清零计数器来「重新观察」。
