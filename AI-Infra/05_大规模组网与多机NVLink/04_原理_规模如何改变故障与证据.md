# 规模如何改变故障与证据

双机 RDMA 排障的主对象是一条链路：本机网卡、对端网卡、地址选择与两台交换机之间的路径。大规模训练 fabric 的对象则是一张会变化的映射网：rank 在节点上，节点有多块网卡，网卡接在不同 rail 上，rail 连到不同交换机，交换机由 SM 或以太网控制面维护，作业又可能同时占用其中一部分。规模带来的不是「更多命令」，而是四类质变：故障半径变大、控制面收敛成为窗口、集合通信拥塞形态改变、证据必须按拓扑聚合。

## 一、故障半径：从一条链路变成一个影响面

一条 rail 的故障并不只影响「使用这条 rail 的那块网卡」。它会沿着映射链向上影响一批 rank 与作业：

```text
switch port / link → rail → NIC → node → rank → job
```

把这个链条走完一遍：

| 层 | 出问题时影响什么 | 需要的证据 |
| --- | --- | --- |
| 交换机端口或链路 | 该物理路径上的速率、错误、队列与连通性 | 端口状态、错误计数、队列与拥塞计数 |
| rail | 使用该轨道的通信 | rail 编号、该 rail 的叶交换机与上行链路状态 |
| NIC | 本节点上使用该网卡的进程 | 网卡设备名、PCIe / NUMA 位置、端口计数器 |
| node | 该节点上的全部 rank | 节点名、进程列表、作业调度记录 |
| rank | 集合通信中的参与进程 | rank 编号、掉队或超时的首个 rank |
| job | 受影响的训练任务 | 作业 ID、时间窗、重试与失败记录 |

如果没有这张映射，现场只能说「网络有问题」；有了这张映射，才能说「Rail 3 的 Leaf 4 端口 12 在 10:05–10:07 误码增长，影响 node-a17 的 NIC 3，进而影响作业 X 的 rank 96 与 rank 224」。

## 二、控制面收敛：瞬时异常不等于硬件故障

SM 重算、主备切换（SM failover，即主 SM 不可用时备用 SM 接管并重算整张 fabric 的过程）、以太网链路状态变化、路由收敛与 ECMP 重分布都有一个时间窗。窗口内的现象可能是：

- 建链超时；
- 传输层确认超时；
- 重传统计增长；
- 集合通信卡住；
- 多个节点同时出现告警。

这些现象发生在**控制面把新事实传播完成之前**，不一定表示数据面硬件已经损坏。假设一次 SM 事件的时间线如下（时间仅示意）：

| 时间 | fabric 侧 | 主机 / 作业侧 | 能得出的结论 |
| --- | --- | --- | --- |
| 10:00:00 | 主 SM 异常，备用 SM 接管 | 作业仍在运行 | 事件开始 |
| 10:00:05 | 拓扑重新发现，部分端口状态变化 | 传输确认超时增长 | 计数增长发生在收敛窗口内 |
| 10:00:20 | 转发表更新完成 | 通信恢复 | 数据面未必有永久故障 |
| 10:01:00 | SM 稳定 | 作业继续或重试成功 | 需要观察是否复发 |
| 10:30:00 | 同一端口错误继续增长 | 多次作业异常 | 不再只是收敛窗口，转向链路定位 |

读这张表的关键是：**计数器是累计值，事件是时间窗**。只拿 10:00:00 与 10:30:00 两个时间点的计数器相减，会把收敛期和后续故障混在一起；必须把 SM 事件、端口状态变化、作业超时和计数器采样点放在同一条时间线上。

## 三、集合通信的拥塞形态

训练里的集合通信不是随机流量。AllReduce、AllGather 与 ReduceScatter 会形成确定方向的数据搬运，常常在某个节点或某条上行链路上形成多打一。超订比在这个时候才暴露。

一个叶交换机的超订比按下式计算：

```text
oversubscription ratio = 下行端口总带宽 / 上行端口总带宽
```

若下行总带宽为 25,600 Gb/s、上行总带宽为 6,400 Gb/s，则超订比为 4:1；若上行带宽提升到 12,800 Gb/s，则超订比为 2:1。反过来，已知下行总带宽 25,600 Gb/s 与目标超订比 2:1，可反推出上行总带宽必须达到 12,800 Gb/s。

集合通信让这个比例的压力具有方向性：

| 集合通信 | 常见压力形态 | 与拓扑的关系 |
| --- | --- | --- |
| AllReduce | 多个 rank 的数据需要归约，可能形成树形或多打一压力 | ring / tree 算法会把压力分布到不同链路上 |
| AllGather | 数据量随 rank 数增长，容易产生持续带宽压力 | rail 与 spine 的可用带宽决定上限 |
| ReduceScatter | 归约与分发结合，压力分布取决于切片与算法 | 跨轨流量是否被压到最小，决定脊层排队 |

因此，大规模 fabric 的性能问题不能只用「链路平均利用率」判断。平均利用率不高时，仍可能出现短时间队列堆积、ECMP 散列集中、某条 rail 降速或单端口微突发。

## 四、证据必须按拓扑与时间聚合

规模越大，越不能依赖单机证据。一个结论至少要同时具备三类信息：

| 证据类型 | 例子 | 缺失时的后果 |
| --- | --- | --- |
| 拓扑身份 | rank、node、NIC、rail、plane、switch port | 无法定位影响面 |
| 时间窗 | 作业异常、SM / 路由事件、计数器采样、变更记录 | 无法判断因果顺序 |
| 计数差分 | 同一链路两侧、同一时间窗内的错误 / 重传 / 拥塞计数增量 | 只看累计值会把历史问题算进当前事件 |

一条可用的证据链应写成：

```text
异常时间窗 → 受影响 rank / node → 本机 NIC → rail / plane
         → 交换机端口 → 两侧计数差分 → fabric 事件或变更
```

这条链上每一段都有归属：主机侧能先证明设备、路径与本地计数；fabric 侧要补充交换机、SM、PKey / VLAN 与队列状态；域管理服务要补充 MNNVL 的 UUID、clique 与节点就绪状态。任何一方只拿自己那一半证据下最终结论，都容易误判。

## 规模化后的第一判断顺序

| 问题 | 先看谁 | 原因 |
| --- | --- | --- |
| 全部 rank 同时卡住或失败 | 先看整网事件、SM 状态、作业调度变更 | 影响面跨越多个节点，单机故障难以同时解释 |
| 固定一组 rank 反复慢 | 先看这组 rank 的 node / NIC / rail 映射 | 现象与物理位置相关 |
| 现象随作业规模或放置变化 | 先看拓扑感知放置与通信库选路 | 同一硬件在不同作业下使用不同路径 |
| 一条 rail 反复异常 | 先看该 rail 的交换机端口、线缆与拓扑基线 | 局部链路问题比随机 GPU 故障更可能 |
| MNNVL 域内部分节点异常 | 先看域状态、UUID、clique 与 IMEX 通道 | 域一致性破坏会让能力存在但不可用 |

**第一反应不要做什么**：不要用单机命令给整网故障下结论；不要把控制面收敛窗口内的超时当成硬件损坏；不要只报链路平均利用率而不看队列与时间窗；不要在没有 rank / node / NIC / rail 映射时让网络团队「整网排查」。
