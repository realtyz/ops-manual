# 拓扑基线与变更治理

没有拓扑基线时，现场只能回答「现在看起来像什么」；有拓扑基线，才能回答「现在与交付时差在哪里，这个差异是否经过批准，它影响哪条 rail、哪个域、哪些作业」。大规模 fabric 的治理对象不是一台设备，而是一组互相约束的映射：网卡编号、rail / plane、交换机端口、分区成员、MNNVL 域标识与配置版本。

## golden topology 要收什么

golden topology 不是一张截图，而是一组可机器比较的数据。

| 基线项 | 内容 | 用于回答 |
| --- | --- | --- |
| 节点与设备清单 | 节点名、GPU、NIC、HCA 设备名、端口、PCIe / NUMA 位置 | rank / node / NIC 应该映射到哪里 |
| rail / plane 映射 | 每块网卡的 port、rail、plane，以及对应叶交换机端口 | 流量应走哪条轨道与平面 |
| 交换机拓扑 | leaf / spine、端口连接、速率、模块与线缆资产 | 当前发现结果与预期拓扑是否一致 |
| 成员关系 | PKey、VLAN、VRF、路由前缀与地址段 | 哪些端口可以互通 |
| MNNVL 域 | fabric UUID、clique、参与节点、IMEX 通道配置 | 哪些节点属于同一个跨节点 NVLink 域 |
| 配置版本 | SM 配置、交换机配置与固件、网卡固件、驱动、RDMA 栈、NCCL、拓扑文件版本 | 当前行为是否来自预期版本 |
| 交付计数基线 | 端口状态、速率、误码与流量水位的历史参照 | 变更后是否出现新的增长 |

这些内容应能组成同一条链：

```text
rank → node → NIC → port → rail / plane → switch port → membership → domain
```

治理的最低要求是：任意一个 rank、网卡或交换机端口，都能沿这条链找到它的上下游对象。

## 变更分类与影响面

| 变更类型 | 直接影响 | 必须先评估什么 | 回滚对象 |
| --- | --- | --- | --- |
| 物理接线 / 换线缆 | rail / plane 映射 | 受影响节点、NIC、rank 与作业 | 恢复原接线或更新基线 |
| 交换机端口配置 | 端口状态、速率、成员关系 | 该端口所在 rail 与所有下游节点 | 交换机配置备份 |
| SM 配置 / 重算 | 转发表与拓扑发现 | 整个 IB 子网或受影响分区 | SM 配置版本 |
| PKey / VLAN / VRF | 可达性与成员关系 | 失败面是否从部分端口扩大到整组作业 | 成员关系矩阵 |
| 网卡或交换机固件 | 设备行为与计数器语义 | 版本四元组、兼容性与计数基线 | 固件版本与配置备份 |
| topology 文件 | 通信库选路 | 所有使用该文件的节点与作业 | 旧拓扑文件 |
| MNNVL 域配置 | UUID、clique、IMEX 通道 | 同域全部节点与训练作业 | Fabric Manager / IMEX 配置 |

变更窗口内必须给出影响面清单：哪些 node、哪些 NIC、哪些 rail / plane、哪些 PKey / VLAN、哪些 MNNVL clique、哪些作业可能受影响。无法给出影响面的变更，不应进入生产窗口。

## 变更前要交出的四份材料

| 材料 | 内容 | 缺失时的风险 |
| --- | --- | --- |
| 当前基线 | golden topology、成员矩阵、域状态、配置版本 | 无法比较变更后的差异 |
| 变更方案 | 改哪些对象、顺序、预计时间、影响面 | 无法判断是否越界 |
| 验证方案 | 用哪些字段与测试证明变更生效 | 只能靠「没报错」结案 |
| 回滚方案 | 回滚条件、回滚动作、回滚后的验证 | 故障时只能继续试错 |

验证方案至少包含：

1. 拓扑差异：当前发现结果与预期 golden topology 的差异为空，或差异均有批准记录；
2. 端口状态：受影响端口 active，速率与成员关系符合预期；
3. 路径验证：小规模 NCCL 测试日志中的 HCA / rail / plane 与预期一致；
4. 计数差分：测试前后对应端口的流量增长符合预期，错误与丢弃没有新增异常；
5. 域状态：MNNVL UUID、clique、节点就绪状态与 IMEX 通道一致；
6. 作业回归：按变更影响面选择代表性作业复测。

## 变更后的验收表

| 验收项 | 通过判据 | 不通过时的动作 |
| --- | --- | --- |
| 拓扑一致性 | `ibnetdiscover` / `iblinkinfo` 与 golden topology 对齐 | 先恢复接线或更新基线，不做性能测试 |
| 端口健康 | 状态 active、速率正确、错误计数无异常增长 | 转入链路或模块定位 |
| 成员关系 | 发端与收端均处于预期 PKey / VLAN / VRF | 修成员矩阵 |
| 路径选择 | NCCL 日志中的 HCA、port、rail、plane 符合预期 | 核对配置与拓扑文件 |
| 计数对齐 | 对应端口流量增长，其他 rail / plane 无异常增长 | 重新核对映射 |
| MNNVL 域 | UUID、clique、状态与 IMEX 通道一致 | 先修域，再谈作业性能 |
| 配置版本 | 四元组与配置版本已登记 | 不把未登记变更当作基线 |

## 常见的治理缺口

| 缺口 | 现场表现 |
| --- | --- |
| 没有 golden topology | 换线后无法判断 rail 是否偏移 |
| 没有 NIC ↔ rail 映射 | 只能说某台机器慢，不能定位轨道 |
| 没有成员矩阵 | 部分 rank 失败时无法判断是否配置缺口 |
| 没有配置版本 | 行为变化后无法区分 bug、配置漂移与硬件劣化 |
| 没有 topology 文件版本 | NCCL 选路异常时无法判断文件是否过期 |
| 没有 MNNVL 域清单 | UUID 或 clique 不一致时无法判断预期值 |
| 没有计数基线 | 非零累计值无法判断是历史存量还是新增异常 |

**第一反应不要做什么**：不要在没有基线的情况下批准 fabric 变更；不要把「交换机配置成功」当成拓扑与成员关系已对齐；不要同时改接线和通信库配置；不要在 MNNVL 域不一致时先跑性能测试；不要让拓扑文件、交换机配置与 golden topology 三者长期分叉。
