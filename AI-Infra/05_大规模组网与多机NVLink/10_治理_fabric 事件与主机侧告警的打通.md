# fabric 事件与主机侧告警的打通

fabric 事件如果只停留在网络平台上，主机侧看到的是无法解释的超时、重传、掉队与作业失败；主机侧告警如果只看 GPU 与进程，网络侧看到的是「没有网络告警，但训练一直异常」。两边打通的关键不是把所有告警都发到一个群，而是让每条事件都能按**同一时间窗、同一拓扑对象、同一影响面**被关联。

## 必须打通的事件类型

| 事件类型 | fabric 侧证据 | 主机 / 作业侧现象 | 关联键 |
| --- | --- | --- | --- |
| SM 状态变化 | SM 主备切换、重算、拓扑差异 | 多节点超时、重传统计增长、集合通信卡住 | 时间窗、子网、受影响节点 |
| 链路状态变化 | port down / up、速率变化、链路 flap | rank 掉队、建链失败、传输中断 | node、NIC、port、rail |
| 链路质量劣化 | symbol error、CRC / local link integrity error、丢弃计数增长 | 吞吐下降、偶发超时 | rail、交换机端口、rank 分布 |
| 拥塞与 ECMP 异常 | 队列水位、拥塞标记、某等价路径丢弃增长 | 作业慢、分位数延迟升高 | rail、plane、等价路径组 |
| 成员关系变更 | PKey / VLAN / VRF 修改 | 部分 rank 建链失败 | 成员矩阵、失败 rank 集合 |
| 拓扑差异 | 当前发现结果与 golden topology 不一致 | 选路异常、流量集中、plane 闲置 | NIC、rail、plane、switch port |
| MNNVL 域事件 | fabric 状态、UUID、clique、IMEX 通道异常 | MNNVL 未启用、初始化失败或性能下降 | UUID、clique、node、GPU |

## 事件到作业的映射链

一条可用的关联记录应能走完这条链：

```text
fabric event → switch port / domain object → rail / plane
             → NIC → node → rank → job → user-facing symptom
```

| 环节 | 需要的数据 | 缺失时的后果 |
| --- | --- | --- |
| fabric event | 事件类型、开始与结束时间、对象 | 无法判断事件范围 |
| switch port / domain object | 端口、PKey、VLAN、UUID、clique | 无法映射到主机侧 |
| rail / plane | 物理轨道与平面编号 | 无法计算影响面 |
| NIC / node | 设备名、节点名、PCIe / NUMA 位置 | 无法定位主机侧证据 |
| rank / job | rank 编号、进程、作业 ID | 无法解释用户可见现象 |
| symptom | 超时、卡住、吞吐下降、失败文本 | 无法验证因果关系 |

如果没有作业调度与 rank 放置数据，至少要能按节点和时间窗关联；如果能拿到 rank 映射，则应把影响面精确到 rank 与通信组。

## 告警设计的三条纪律

### 一、累计值按增长率告警

误码、重传、丢弃、链路断开类字段通常是累计值。对绝对值告警会把历史存量当成当前故障；对增长速率告警才能回答「现在是否仍在恶化」。

| 字段类型 | 告警口径 |
| --- | --- |
| 错误类计数 | 同一端口两次读数差值除以采样间隔 |
| 链路状态切换 | 事件次数与频率，而不是最后一次状态 |
| 拥塞标记 / 丢弃 | 增长率，并与队列水位同看 |
| 流量类计数 | 用于路径验证与影响面，不宜单独作为故障告警 |
| 拓扑差异 | 非空即告警，除非差异绑定已批准变更 |

### 二、告警必须带拓扑身份

一条只写「node-a17 网络错误」的告警，不足以让网络侧行动。应至少带：

```text
node / NIC / port / rail / plane / switch port / event time / counter delta
```

对 MNNVL 事件，还应带：

```text
fabric UUID / clique / GPU fabric state / IMEX channel state / node list
```

### 三、事件与作业时间必须对齐

告警系统应保留事件时间线，而不是只保留当前状态。尤其是 SM 切换、链路 flap 与拓扑重算这类短事件，作业侧的超时可能发生在事件结束后的若干秒内；若只比较告警触发时刻，会错判为无关。

## 建议的最小告警集

| 告警 | 触发条件 | 联动动作 |
| --- | --- | --- |
| SM 状态异常 | SM 非 master、无响应或发生切换 | 冻结网络侧结论，等待收敛后取计数差分 |
| 链路断开 | 非零 link down 事件 | 关联该 port / rail 上的节点与作业 |
| 链路误码增长 | 错误计数增长率超过基线 | 转入端口、线缆与模块检查 |
| 拥塞异常 | 队列、拥塞标记或丢弃增长集中在某 rail / path | 关联 ECMP 与 rank 分布 |
| 成员关系差异 | 当前成员矩阵与基线不一致 | 阻止相关节点承接新作业 |
| 拓扑差异 | 当前拓扑与 golden topology 不一致 | 核对变更工单 |
| MNNVL 域不一致 | UUID、clique、状态或 IMEX 通道异常 | 先修域，再启动 MNNVL 作业 |
| rail 影响面扩大 | 同一 rail 上多节点或多作业异常 | 评估是否隔离该 rail 或相关节点 |

本篇只规定 fabric 事件必须携带的字段与联动对象；告警阈值的标定与看板组织不属于本篇负责的内容。

## 值班处置口径

| 现象 | 先做 | 不要先做 |
| --- | --- | --- |
| 多节点同时超时 | 拉 SM / 路由 / 链路事件时间线 | 不要逐台重启节点 |
| 一条 rail 反复异常 | 关联该 rail 的节点、rank 与作业 | 不要扩大到整网隔离 |
| 部分 rank 建链失败 | 对失败集合做成员关系重叠分析 | 不要先重跑大作业 |
| MNNVL 域告警 | 核对 UUID、clique、状态与 IMEX 通道 | 不要先改 NCCL 算法 |
| 拓扑差异告警 | 核对变更工单与 golden topology | 不要先改通信库变量 |
| 拥塞告警 | 按等价路径与 rail 分组看计数 | 不要直接扩容 |

处置前应保存：事件时间线、受影响作业、rank 放置、拓扑差异、端口状态、计数差分、MNNVL 域状态与当时生效配置。重启、重跑或清零计数器都会破坏证据，应放在取证之后。

## 责任边界

| 对象 | 负责什么 |
| --- | --- |
| 主机侧 | 设备可见性、端口状态、生效配置、NCCL 日志、主机侧计数差分 |
| fabric / 网络侧 | SM、交换机端口、队列、成员关系、拓扑差异、ECMP 与链路质量 |
| 域管理侧 | Fabric Manager、MNNVL UUID、clique、IMEX 通道与 GPU fabric 状态 |
| 平台 / 作业侧 | rank 放置、作业时间窗、隔离与重跑策略 |
| 值班指挥 | 时间线对齐、影响面判断、证据保全与升级决策 |

**第一反应不要做什么**：不要只看单侧告警下结论；不要用当前状态覆盖历史事件；不要对累计值只看绝对值；不要发出没有 node / NIC / rail / port 身份的告警；不要在事件时间线未对齐前重启节点；不要清零计数器；不要在 MNNVL 域不一致时先调通信参数。
