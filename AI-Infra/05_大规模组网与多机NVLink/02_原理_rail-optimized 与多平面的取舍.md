# rail-optimized 与多平面的取舍

多机训练的通信压力不是均匀地落在「网络」这个抽象对象上，而是落在一张具体的映射关系上：某个 rank 在某个节点上，使用某块网卡，接到某个交换机组，再通过若干链路到达对端。rail-optimized 的目标是把这组映射固定下来，让每台机器的第 n 块网卡总是接到第 n 条轨道（rail），从而让同轨流量尽量停留在本轨叶层，减少不必要的跨脊流量。

一个最小的 rail-optimized 拓扑如下（两台机器、两条 rail，仅示意空间关系）：

```text
Node A                         Node B
  GPU/NIC 0 ------------------- Rail 0 Leaf ------------------- NIC 0
  GPU/NIC 1 ------------------- Rail 1 Leaf ------------------- NIC 1

Rail 0 Leaf ===== Spine ===== Rail 1 Leaf
```

这张图上有三类路径：

| 路径 | 走向 | 健康形态 |
| --- | --- | --- |
| 同轨通信 | Node A 的 NIC 0 到 Node B 的 NIC 0 | 主要停留在 Rail 0 叶层，不占用脊层 |
| 跨轨通信 | Node A 的 NIC 0 到 Node B 的 NIC 1 | 需要经过脊层或跨轨路径 |
| 平面间路径 | 若存在多个 plane，则一个 plane 内的链路不自动变成另一个 plane 的备份 | plane 是独立并行网络，不是同一张网内的等价路径 |

## 轨道对齐解决了什么

| 不对齐时的现象 | 轨道对齐后的变化 | 仍不能解决的问题 |
| --- | --- | --- |
| 通信库按网卡编号选路，但物理接线与编号不对应，路径无法按预期分布 | 第 n 块网卡与第 n 条 rail 的对应关系稳定，rank、网卡与端口可以对账 | 网卡命名漂移、拓扑文件过期、作业放置不合理 |
| 同一节点流量被推到别的 rail，造成跨脊流量 | 同轨流量尽量留在本轨叶层，降低脊层压力 | 消息过大、超订比过高或集合通信本身需要跨轨 |
| 一条 rail 故障时难以判断影响哪些 rank | rank → node → NIC → rail → switch port 的映射可追溯 | 需要拓扑基线与巡检体系才能持续发现偏移 |

因此，rail-optimized 不是「把所有网卡接到同一台交换机」。后者会把多条主机链路收进同一个故障与拥塞域；rail-optimized 则保留多条并行轨道，让轨道编号、网卡编号与交换机端口可以一一映射。

## 超订比怎么读

超订比（oversubscription ratio）描述的是**下行接入带宽与上行转发带宽的比例**。如果一个叶交换机有 64 个 400 Gb/s 的主机侧端口，只有 16 个 400 Gb/s 的上行端口：

- 下行总带宽：64 × 400 = 25,600 Gb/s；
- 上行总带宽：16 × 400 = 6,400 Gb/s；
- 超订比：25,600 / 6,400 = 4:1。

如果上行端口增加到 32 个：

- 上行总带宽：32 × 400 = 12,800 Gb/s；
- 超订比：25,600 / 12,800 = 2:1。

反推判据也来自同一公式：若已知目标超订比为 2:1、下行总带宽为 25,600 Gb/s，则需要的上行总带宽为 25,600 / 2 = 12,800 Gb/s，再除以单端口 400 Gb/s，得到 32 个上行端口。

超订比不是错误配置，而是一种容量取舍。它只在进入上游的流量超过上游可转发能力时暴露为排队、延迟上升或丢包。rail-optimized 能减少跨脊流量，但不能消除集合通信固有的跨轨需求，也不能替代带宽容量规划。

## ECMP 的副作用

以太网 RoCE fabric 通常会用 ECMP 把流量分布到多条等价路径上。它的问题不在于「有 ECMP」，而在于**散列结果不一定均匀**。多条逻辑等价链路的物理速率、拥塞状态或队列水位可能不同，而 ECMP 散列只看它配置所依据的头部字段，不感知当前队列长度。

| 现象 | 常见解释 | 应同看的证据 |
| --- | --- | --- |
| 某条脊链路拥塞，其他等价链路空闲 | ECMP 散列把较多流集中到该链路 | 交换机侧各等价链路的队列、丢包与速率 |
| 只有部分 rank 慢 | 这些 rank 的通信散列到劣化或拥塞路径 | rank → node → NIC → rail → port 映射 |
| 更换端口或重排作业后现象变化 | 散列输入或物理位置变化 | 变更前后同一口径的计数器差分 |
| 计数器显示链路利用率不高但延迟高 | 队列瞬时堆积或微突发，平均值掩盖了峰值 | 更细时间粒度的队列与拥塞标记 |

## 多平面的适用条件

平面（plane）是在 rail 之外的另一层并行网络：多个 plane 各自拥有独立的交换链路与故障域。它的价值在规模变大之后才明显。

| 维度 | 单一平面 | 多平面 |
| --- | --- | --- |
| 管理复杂度 | 拓扑与排障对象较少 | 每个平面都要维护编号、健康与成员关系 |
| 故障隔离 | 一处 fabric 故障可能影响整张网 | 一个 plane 的故障可以与其它 plane 隔离 |
| 路径利用率 | 等价路径集中在同一平面内 | 需要 plane 编号、网卡清单与分配策略正确，否则会出现闲置平面 |
| 适用条件 | 中小规模、运维团队希望对象简单 | 大规模、需要降低单点故障半径或支持分域维护 |

多平面不是「更多带宽」的同义词。如果通信库只使用一个 plane，其他 plane 只是资产，不是容量。判断多平面是否被用上，必须读通信库日志里的设备、rail 与 plane 字段，而不是只看交换机上链路是否 active。

## 从拓扑到证据

rail-optimized 的运维价值最终落在一个映射链上：

```text
rank → process → node → NIC → rail / plane → leaf port → spine path
```

这条链上任何一环缺失，都会让故障无法归因：

| 缺失环 | 现场后果 |
| --- | --- |
| rank 到 node 的映射缺失 | 不知道哪些进程受影响 |
| NIC 到 rail 的映射缺失 | 无法把计数器增长归到某条轨道 |
| rail 到交换机端口的映射缺失 | 无法向网络侧提供可查对象 |
| plane 编号缺失 | 无法判断是否只用了部分并行网络 |
| golden topology 缺失 | 无法判断当前接线是否偏离交付状态 |

**第一反应不要做什么**：不要把 rail-optimized 理解为「所有网卡接同一台交换机」；不要用平均链路利用率否定瞬时拥塞；不要在多平面 fabric 上只核对设备名而不核对 plane 编号；不要在没有 rank / node / NIC / rail 映射的情况下要求网络团队「查整张网」。
