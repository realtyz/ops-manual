# 第 05 章 为什么一个作业需要多张 GPU｜写作大纲

**审查状态**　已获批准。正文按以下六节拆为六篇。

## 范围、前置与学习结果

- **范围**　以 NVIDIA GPU 上的同步训练为例，从单卡的计算量、峰值显存和完成时间推到单机多卡、多机多卡。解释作业如何组织进程、建立通信组，以及数据并行、张量并行、流水线并行和专家并行分别把什么数据放在谁手里、在什么时候交给谁。训练一步只需认识取数据、前向产生中间结果、反向产生梯度、更新参数四个阶段。模型和优化器算法、并行策略实现、生产部署命令留在章外。
- **必要前置**　读者已有 Linux 进程、环境变量和 `host:port` 的基础，知道 GPU 有各自的显存，CUDA 操作可以异步提交，并能区分节点内互联与跨节点网络。第一次用到时补足训练步、全局批次与微批次、进程内 CUDA 设备序号。读者可用给定材料做推导，无需 GPU 实验环境。
- **读完应能独立解释**　给定负载的每卡峰值预算和步时，说明加卡解决的是容量、吞吐还是完成期限。给定启动参数和设备表，把进程映射到节点、物理 GPU 和通信组，并解释成员发现、框架进程组、NCCL communicator 和实际数据交换如何衔接。
- **读完应能独立判断**　根据每个 Rank 的输入写出五种集合操作的输出。根据并行切分、通信组和放置表，判断哪些交换跨节点、哪些交换会阻塞下一段计算。根据同一轮尝试的事件和进程退出记录区分成员未到齐、通信初始化卡住、运行中晚到、调用不匹配与成员退出，指出各结论还需要什么证据。
- **跨章边界**　第 04 章的设备拓扑只用来区分节点内与跨节点路径。第 06—08 章再讲 RDMA、网络拓扑、NCCL 算法与选路及基准测试，第 09 章讲数据供给与 Checkpoint I/O，第 15—16 章讲成组调度与控制器重试，第 17—18 章讲观测基线和生产排障。本章交代这些能力分别对应作业的哪项依赖。

**贯穿案例**　从节点 A 的 1 卡和 4 卡扩展到节点 A、B 各 4 卡。两节点均为 Linux，同一角色每节点启动 4 个 Worker，每个 Worker 独占一张可见的整卡。主例用固定规模的 PyTorch DDP 跑一次同步训练。讨论其他切分方式时复用同一份设备与 Rank 表，各方案单独比较。节点、设备映射、步时和事件均为教学设定。

**已核对的文档基线**　启动配置按 PyTorch `v2.9.1` 源码及 2.9 版文档，设备可见性沿用第 04 章的 CUDA 13.2.1 文档。集合操作按 NCCL 2.31.2 归档语义，专家并行用 Megatron Core 0.15.0 的 dispatcher 作例。各版本分别支撑对应机制。联合运行所需的驱动、CUDA、PyTorch 和 NCCL 软件包组合待有实测材料时确认。

## 01 先判断一张卡缺的是容量还是时间

**问题与预期结论**　同样是单卡跑不完，一个作业在起步时就显存不足，另一个作业能稳定跑但赶不上交付时间。读完能指出每种情况该先看哪项预算，以及复制模型或切分模型各能缓解什么。

**解释顺序**

1. 先列每卡峰值时同时存活的参数、梯度、优化器状态、激活与临时缓冲，区别长期保留和阶段性峰值。复制型数据并行让每卡仍持有完整模型副本。固定全局批次、缩小每卡微批次可以降低部分激活占用，复制的状态仍留在每卡。若复制的状态已经超出预算，就需要改动状态的存放方式，再单独核算切分后重组与缓冲的峰值。
2. 对能放入单卡的负载，固定每次更新的工作量和总步数，分开可并行计算和关键路径上的额外等待。以单卡、单机四卡、双机八卡三档比较步时与完工时间。另解释扩大每步数据量时应看样本吞吐，以及为什么要交代全局批次和更新次数。
3. 单台的可用卡数、每卡容量和节点内的放置限制决定何时跨机。跨机增加了可用资源，也改变了一部分交换的路径和故障范围。互联速率与网络设计留给第 06—08 章。

**支撑材料**

- 拟用一张峰值预算表。每卡可用 `48 GiB`，普通 DDP 的复制状态假设在峰值时合计 `52 GiB`，仅压缩激活仍无法装入。另算均匀八路全分片的状态项 `52 ÷ 8 = 6.5 GiB`，加上同一时刻题设中的激活 `16 GiB` 和分片之外新增的重组与临时空间 `8 GiB`，得到 `30.5 GiB`。用这个差异说明哪些项随切分变化，实际能否放入仍须逐阶段核算。状态分片的通信过程放到第 05 节。 [PyTorch 2.9 · DDP](https://docs.pytorch.org/docs/2.9/generated/torch.nn.parallel.DistributedDataParallel.html) · [PyTorch 2.9 · FSDP2 fully_shard](https://docs.pytorch.org/docs/2.9/distributed.fsdp.fully_shard.html)
- 拟用固定工作量的步时表。单卡计算 `400 ms`，理想均分到四卡和八卡后分别为 `100 ms` 和 `50 ms`，再加题设的未被重叠开销 `30 ms` 和 `70 ms`，步时为 `130 ms` 和 `120 ms`。以 `10,000` 步和 `1,250 s` 期限对照，分别需要 `4,000 s`、`1,300 s`、`1,200 s`。计时范围为稳定迭代，启动、保存和重试置于题设之外。这组数用于算账，正文结合 DDP bucket 说明有多少通信落在关键路径上取决于重叠。 [PyTorch 2.9 · DDP 的 bucket_cap_mb](https://docs.pytorch.org/docs/2.9/generated/torch.nn.parallel.DistributedDataParallel.html)

## 02 从进程编号找到实际使用的 GPU

**问题与预期结论**　两台机器都有进程报告 `LOCAL_RANK=0`，日志里还出现了通信组内的 Rank 0。读完能确定每个编号在哪个范围内有效，并核对进程有没有绑到预期的卡。

**解释顺序**

1. 在本次组队中，以两台节点各一个 `torchrun` Agent、每 Agent 启动四个 Worker 为例。按 `WORLD_SIZE=8`、`LOCAL_WORLD_SIZE=4` 和一轮示例分配 A 上 `RANK=0…3`、B 上 `RANK=4…7` 来介绍全局与本地编号。本轮分配只作为教学表，跨轮对齐使用运行 ID、尝试编号和主机等记录。
2. 跟随 Worker 读取 `LOCAL_RANK`，在继承的可见设备列表里选 CUDA ordinal。给 B 节点的列表换个顺序，用 UUID 和 BDF 回查物理 GPU，区分节点工具 index、进程内 ordinal 和全局 Rank。加入两进程误选同卡的反例，用每进程实际选卡记录核实。独占约束限定为 PyTorch NCCL 多进程场景。
3. 用有序子组 `[1,5]` 展示同一 Worker 的全局 Rank 5 可以是组内 Rank 1。后面的集合操作按通信组的成员与序号解释。容器注入、设备分配与拓扑调度留到第 10—15 章。

**支撑材料**

- 拟给一张 8 行对应表，列 `run_id`、`attempt`、`host`、`pid`、`RANK`、`LOCAL_RANK`、CUDA ordinal、主机 index、GPU UUID、PCI BDF。用按 UUID 重排的 `CUDA_VISIBLE_DEVICES` 和 `nvidia-smi --query-gpu=index,uuid,pci.bus_id --format=csv` 的教学片段，说明为何 B 上 `RANK=4` 可以选到本进程的 `cuda:0`、对应本机 index 2。另列子组成员顺序和两端组内编号，供后文判读 Broadcast 的根。 [PyTorch 2.9 · torchrun 环境变量](https://docs.pytorch.org/docs/2.9/elastic/run.html#environment-variables) · [PyTorch 2.9 · Group Rank](https://docs.pytorch.org/docs/2.9/distributed.html#torch.distributed.get_group_rank) · [CUDA 13.2.1 · CUDA_VISIBLE_DEVICES](https://docs.nvidia.com/cuda/archive/13.2.1/cuda-programming-guide/05-appendices/environment-variables.html#cuda-visible-devices)

## 03 从发现作业成员到首次交换数据

**问题与预期结论**　启动命令已执行，协调端口也能访问，为何训练仍可能没有开始？读完能按事件判断是在等节点加入、等 Worker 初始化，还是在等 GPU 通信，并为每一段指出可观察的结束信号。

**解释顺序**

1. 先分开外部资源管理器决定在哪些节点启动，与各节点的 Agent 用相同的 Rendezvous 后端、地址和作业 ID 找到同一组。主例采用固定两节点的 `c10d` Rendezvous。节点到齐后，Agent 获得本轮组队信息并启动本地 Worker，向它们交付 Rank、规模与初始化所用地址。节点只到了一个或作业 ID 不同，可能停在组队。把 `--rdzv-endpoint` 和 Worker 使用的 `MASTER_ADDR` / `MASTER_PORT` 分开跟踪，地址即便重合也要区分用途。
2. Worker 先选卡，再调用 `init_process_group(backend="nccl", init_method="env://")`，使用 Store 交换进程组初始化信息。继续追踪框架为具体设备和成员建立 NCCL communicator 所需的标识交换与初始化。PyTorch 2.9 的常见惰性路径可能在首个 NCCL 操作才建 communicator，传入 `device_id` 可提前触发。DDP 默认构造时会同步参数和缓冲区，首个 NCCL 操作可以在训练循环之前发生。
3. 按 Rendezvous、框架初始化、communicator 初始化、运行中集合操作四处标记等待。若 A 的 Agent 仍在等待组队且缺少 B 加入的记录，核查 B 的 Agent 与参数。若全部 Worker 已启动且进程组调用已返回，但首个 GPU 集合操作仍未完成，核查该组各 Rank 的进入点与初始化证据。通信路径和超时调参留给第 08、18 章。

**支撑材料**

- 拟给两节点共同的配置片段 `torchrun --nnodes=2 --nproc-per-node=4 --rdzv-backend=c10d --rdzv-endpoint=node-a:29400 --rdzv-id=ai05-demo-001 --max-restarts=1 train.py`。用 `--nnodes` 和 `--nproc-per-node` 推出本轮 8 个 Worker，解释同一作业共享 Rendezvous 参数和 PyTorch 2.9 对每角色同构本地 Worker 数的要求。 `train.py` 是正文拟给出关键调用的占位。 [PyTorch v2.9.1 · torchrun 固定规模示例](https://github.com/pytorch/pytorch/blob/v2.9.1/torch/distributed/run.py) · [PyTorch 2.9 · Rendezvous](https://docs.pytorch.org/docs/2.9/elastic/rendezvous.html)
- 拟用 Mermaid 时序图区分 Agent、Rendezvous、Worker、Store 和 NCCL communicator。每轮配套教学记录列 Agent 的 `rdzv_begin` / `rdzv_done`、Worker 的 `worker_start`、`pg_enter` / `pg_return`、`first_collective_enter` / `first_collective_complete`，这些是自定义事件名。对照有无 `device_id` 的 API 约定，确定何处可以观察到提前初始化，何处需要等待 GPU 完成或核查通信库侧证据。 [PyTorch 2.9 · init_process_group](https://docs.pytorch.org/docs/2.9/distributed.html#torch.distributed.init_process_group) · [PyTorch 2.9 · DDP init_sync](https://docs.pytorch.org/docs/2.9/generated/torch.nn.parallel.DistributedDataParallel.html) · [NCCL 2.31.2 · Communicator Creation](https://docs.nvidia.com/deeplearning/nccl/archives/nccl_2312/user-guide/docs/api/comms.html#ncclcomminitrank)

## 04 按 Rank 读懂五种集合操作

**问题与预期结论**　日志只写了 `AllGather` 或 `ReduceScatter`。读完能从各 Rank 的输入推出每个 Rank 的输出，解释哪些是规约、复制或重排，并判断操作完成所需的成员和调用约定。

**解释顺序**

1. 固定第 02 节的两成员子组 `[1,5]`，统一使用组内 Rank 0、1。先按根选择讲 Broadcast，再按来源顺序讲 AllGather。接着用按元素求和讲 AllReduce，用同一份和按 Rank 分块讲 ReduceScatter，最后给每段输入加目的 Rank 标签讲 All-to-All。说明求和是算例选定的规约，平均若由框架实现需另计。
2. 对照两种输出布局，推导同一规约条件下 ReduceScatter 接 AllGather 得到与 AllReduce 相同的逻辑结果。只比较结果和缓冲大小，实际算法、跨链路字节数和物理路径放在第 08 章。用逻辑 payload、每 Rank 的接收缓冲与链路流量三列区分计数口径。
3. 回到一次正常调用的条件。同一通信组成员需要以相容的顺序发出对应操作，遵守选定 API 的数据类型、计数、根或分块约定。原生 NCCL 等长集合接口与 PyTorch 支持显式分段的 `all_to_all_single` 分开讲。再从计算依赖说明 CPU 提交、GPU 完成与下游使用的区别，单独指出显式 Barrier 用于成员会合。

**支撑材料**

- 拟用一张可复算的五行输入输出表。规约输入 `[1,2]` 和 `[10,20]`，AllReduce 输出均为 `[11,22]`，ReduceScatter 各得 `[11]` 与 `[22]`。AllGather 用每 Rank 输入 `[1]`、`[10]`，输出均为 `[1,10]`。Broadcast 以组内 Rank 1 为根，两端得到它的 `[10,20]`。All-to-All 的输入按目的地排列为 `[a00,a01]`、`[a10,a11]`，两端按来源得到 `[a00,a10]`、`[a01,a11]`。若每元素 4 B，AllGather 每 Rank 的逻辑输入和输出分别为 4 B、8 B。 [NCCL 2.31.2 · Collective Operations](https://docs.nvidia.com/deeplearning/nccl/archives/nccl_2312/user-guide/docs/usage/collectives.html)
- 拟用组内两个 Rank 的发起顺序对照表，分别演示匹配，以及一方先发 AllReduce、另一方先发 Broadcast 的不匹配。用同一个广播根对照 PyTorch 的 `src=5` 和 `group_src=1` 两种写法，说明两者择一。另列出 PyTorch 分段 All-to-All 的输入和输出分段大小须按对端匹配。配一条计算 Stream 等待通信结果的示意线，说明为什么用 CPU 调用返回时刻做判断会漏掉 GPU 上仍在进行的操作。 [PyTorch 2.9 · broadcast](https://docs.pytorch.org/docs/2.9/distributed.html#torch.distributed.broadcast) · [PyTorch 2.9 · all_to_all_single](https://docs.pytorch.org/docs/2.9/distributed.html#torch.distributed.all_to_all_single) · [PyTorch 2.9 · 集合操作同步与异步语义](https://docs.pytorch.org/docs/2.9/distributed.html#synchronous-and-asynchronous-collective-operations)

## 05 并行切分决定哪些数据走哪一组

**问题与预期结论**　同样申请八张卡，为什么一种作业主要在反向阶段交换梯度，另一种在层内、阶段边界或专家路由处反复交换？读完能从切分对象推导交换的载荷、频率、依赖和通信组，并判断改变放置后哪类交换会跨机。

**解释顺序**

1. **数据并行**　以普通 DDP 为主例。各副本处理不同数据，梯度 bucket 就绪后按各 Rank 一致的顺序发起 AllReduce，得到可用于本地更新的同步梯度。已发起的规约可以和后续反向计算重叠。数据切分由输入管道承担，默认的前向缓冲区广播单独标记。用 `no_sync()` 的梯度累积说明同步频率随设置改变，再用单维分片的 FSDP2 作短对照。FSDP2 按需 AllGather 参数、以 ReduceScatter 得到梯度分片，前向后是否重新分片会改变反向前重取参数的需要。
2. **张量并行**　用同一层的两个部分结果说明，输出需要合并或切换布局时，TP 组内才需要相应的 AllReduce、AllGather 或 ReduceScatter。用一个部分和的例子讲下一操作何时依赖通信结果。频率随层数、切分和布局而变，数学推导和模型实现留在章外。
3. **流水线并行**　不同阶段持有不同层。沿相邻阶段画出前向激活和反向激活梯度的点对点方向，按微批次跟踪何时可以推进下一段。比较微批次数量、阶段耗时和跨机边界改变后的等待。完整调度算法留在章外。
4. **专家并行**　专家分布到不同设备，令牌按目标专家所在 Rank 分发，计算完成后将输出送回并合并。用显式选取 `alltoall` 的 dispatcher 说明这种交换。改变 token 路由会改变每个目标的流量与计算负载。只把路由视为已给定的目的地，其他 dispatcher 保留一句适用边界。
5. 用同一张八卡 Rank 表叠加 DP 和 TP 组，再改一处组映射，判断哪些操作由机内变成跨机，哪些反过来。判断依据为该交换的频率、载荷和阻塞关系。放置原则的网络验证和调度落地归第 07、08、15 章。

**支撑材料**

- 拟给一张四类切分对照表，列切分对象、发送内容、参与成员、触发时机、后续依赖和不均衡来源。用 `DistributedSampler`、DDP reducer 的 bucket 顺序及 `no_sync()` 说明输入分片和梯度同步分别由谁负责。FSDP2 对照只追一个模块单元，比较 `reshard_after_forward=True` 与 `False` 对参数保留和反向 AllGather 的影响。 [PyTorch 2.9 · DistributedSampler](https://docs.pytorch.org/docs/2.9/data.html#torch.utils.data.distributed.DistributedSampler) · [PyTorch 2.9 · DDP](https://docs.pytorch.org/docs/2.9/generated/torch.nn.parallel.DistributedDataParallel.html) · [PyTorch 2.9 · DDP Reducer](https://docs.pytorch.org/docs/2.9/notes/ddp.html) · [PyTorch 2.9 · FSDP2](https://docs.pytorch.org/docs/2.9/distributed.fsdp.fully_shard.html)
- 拟用 `RowwiseParallel` 的局部输入、默认复制输出作 TP 例，附两个 Rank 的部分和如何产生完整输出。PP 拟给两阶段、四微批次的前后向依赖图，圈出填充期、相邻阶段的发送与接收以及阶段晚到的传播方向。EP 拟用二 Rank 的令牌数量表，两源各发 4 个，其中都按 `[3,1]` 投向两个目的地，两个目标合计处理 6 个和 2 个，矩阵包含本地处理。它说明等量输入仍可能造成目标负载不均，不用于反推网络流量。 [PyTorch 2.9 · Tensor Parallelism](https://docs.pytorch.org/docs/2.9/distributed.tensor.parallel.html#torch.distributed.tensor.parallel.RowwiseParallel) · [PyTorch 2.9 · Pipeline Parallelism](https://docs.pytorch.org/docs/2.9/distributed.pipelining.html) · [Megatron Core 0.15.0 · Token Dispatching](https://docs.nvidia.com/megatron-core/developer-guide/0.15.0/user-guide/features/moe.html#token-dispatching)

## 06 为什么一个慢成员或失败会拖住整组

**问题与预期结论**　七个进程报告等待，第八个进程较晚到达、发错操作或已退出。读完能用同一轮的多 Rank 证据区分这些情形，解释等待如何放大为步时、作业失败或重算，并判断重试是否可能恢复。

**解释顺序**

1. 从同一通信组最后一个到达的 Rank 追到依赖规约结果的下一步。在该操作位于关键路径且无重叠的简化条件下，最晚就绪时刻和此后的完成时间共同限制整步进展。用输入读取偏慢与 EP 热门目标导致负载偏斜作两种来源。若通信能和独立计算重叠，延迟首先占用可重叠窗口。
2. 用 `run_id + attempt + group + step + collective_seq` 对齐各 Rank 的事件。在同序号对照操作类型、元素计数、数据类型、根或分段、进入和完成时刻。区分某 Rank 正在前置工作、各方调用不匹配、成员已经退出、所有匹配调用已提交但迟迟未见完成。缺少日志时查进程状态、退出证据或 GPU 侧时间线。跨主机比较绝对时间需要时钟对齐，持续时长使用各机单调时钟。解释其余 Rank 的超时为何可能晚于引发故障的事件。
3. 回到固定规模、`--max-restarts=1` 的例子。单个 Worker 退出后，`torchrun` 可在预算内停掉并重启 Worker 组，成员需重新组队、初始化并由应用加载已保存的状态。若节点或 Agent 消失，补回资源或终止作业由外部作业管理器决定。用固定规模与范围式 `--nnodes` 作短对照，说明弹性组队可能改变 Rank 和 World Size，应用须据此重建分组并处理批次与恢复进度。组调度、生产容错和恢复流程留给第 15—18 章。

**支撑材料**

- 拟用一组明确标注为自拟的多 Rank 事件表。正常轮各 Rank 的最终同步点在 `35 ms` 就绪，慢轮仅 Rank 5 在 `50 ms` 就绪，约定通信在成员齐备后统一花 `10 ms`，两种步时为 `45 ms` 和 `60 ms`。另给同序号操作不一致、Rank 5 退出、所有匹配调用提交但无完成证据三条变体。字段包括 `host`、`pid`、GPU UUID、应用定义的 `event` 和组内序号、`op`、`count`、`dtype`、退出码及可用的异常栈。完成事件以对应 GPU 工作完成证据为准。用这些记录将症状缩到某个阶段，并标出还不能归因的情形。 [PyTorch 2.9 · 分布式通信语义](https://docs.pytorch.org/docs/2.9/distributed.html) · [NCCL 2.31.2 · Collective Operations](https://docs.nvidia.com/deeplearning/nccl/archives/nccl_2312/user-guide/docs/usage/collectives.html)
- 拟用一段故障前后教学记录，对照 `TORCHELASTIC_RUN_ID`、`TORCHELASTIC_RESTART_COUNT`、新旧 Rank/PID、`exitcode`、`error_file` 和应用记录的 `checkpoint_step`。若已保存完成 400 步后的状态、故障发生在完成 480 步之后，则恢复后需重算已完成的 80 步，另计未完成步、重建和读取时间。异常示例区分 `@record` 可捕获的未处理 Python 异常与只见退出信息的情况，并解释启动器报告的首个错误时间如何作为线索。 [PyTorch 2.9 · torchrun 失败与成员变化](https://docs.pytorch.org/docs/2.9/elastic/run.html#failure-modes) · [PyTorch 2.9 · Error Propagation](https://docs.pytorch.org/docs/2.9/elastic/errors.html)
