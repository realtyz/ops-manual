# 八卡训推作业与并行架构综合检验

下面六道综合实战题统一建立在本章的双节点八卡集群上，无需实机环境，只需用纸面推导就能把**训练显存与步时、设备映射、集合原语、DP×TP 放置、故障恢复**以及**大模型推理 TP 与 PD 分离 KV 迁移**完整串联一遍。

## 公共场景与设备映射

两台节点 `node-1` 与 `node-2` 各配 4 张整卡，启动参数为 `--nnodes=2 --nproc-per-node=4`（共 8 个独占 GPU 的 Worker）。`node-1` 可见顺序正常，`node-2` 按 UUID 重排如下：

| 节点 | 全局 `RANK` | `LOCAL_RANK` | `CUDA_VISIBLE_DEVICES` 映射到的物理 UUID | 宿主机 index |
| --- | --- | --- | --- | --- |
| `node-1` | `0, 1, 2, 3` | `0, 1, 2, 3` | 依次为 `GPU-a001`、`GPU-a002`、`GPU-a003`、`GPU-a004` | `0, 1, 2, 3` |
| `node-2` | `4, 5, 6, 7` | `0, 1, 2, 3` | 依次为 `GPU-b003`、`GPU-b001`、`GPU-b004`、`GPU-b002` | `2, 0, 3, 1` |

## 一、容量约束、步时与启动映射

1. **显存峰值与步时预算**：某训练负载在反向末尾，完整参数、梯度与优化器状态合计 `52 GiB`，而每卡净可用预算降为 `32 GiB`。八路均匀全分片时，该时刻每卡另需 `16 GiB` 激活和 `8 GiB` 临时空间。
   - 普通 DDP 与全分片各能否通过预算？若异步预取还要占 `2 GiB` 且同时存活，结论如何变化？另有一单卡可放下的任务，要求 `1,250 s` 内迭代 `10,000` 步；扩到八卡后纯计算 `50 ms/步`，关键路径通信同步最多能有多久？
2. **成员映射与启动卡顿取证**：沿用上表，全局 `Rank 5` 位于 `node-2`，同时加入了两成员跨机子组 `[1, 5]`。请写出它的 `LOCAL_RANK`、实选 CUDA 序号、物理 UUID 简称、宿主机 index、在子组内的组内 Rank 以及通信伙伴。若两台节点的八个 Worker 都已从 `init_process_group` 返回，但首次 `AllReduce` 迟迟无结果，你会优先核查哪些事件？

### 参考推理（1—2 题）

1. **显存与步时核算**
   - 普通 DDP 每卡完整复制 `52 GiB`，单这一项已超出 `32 GiB` 预算（无法通过）。
   - 八路均匀全分片在该时刻每卡占用 $52 \div 8 + 16 + 8 = \mathbf{30.5\ \text{GiB}}$，尚余 `1.5 GiB`，可以通过该时刻预算。
   - 若同时存活 `2 GiB` 预取缓冲，占用升至 $30.5 + 2 = \mathbf{32.5\ \text{GiB}}$，超预算 `0.5 GiB`（仍须逐阶段查整步真实峰值）。
   - 完工死线对应的单步上限为 $1,250\ \text{s} \div 10,000 = 125\ \text{ms}$，扣除 `50 ms` 计算后，落在关键路径上的额外开销最多只能有 $125 - 50 = \mathbf{75\ \text{ms}}$。
2. **身份还原与惰性初始化排查**
   - `Rank 5` 在 `node-2` 上对应 `LOCAL_RANK=1` → 实选 **`cuda:1`** → 命中重排列表第二项 **`GPU-b001`** → 宿主机 **index `0`**；在子组 `[1, 5]` 中它是**组内 Rank `1`**，与 `node-1` 上的全局 `Rank 1`（组内 Rank `0`）跨机通信。
   - 八个 `init_process_group` 均返回只确认了前序元数据初始化完成；后续应核对本次 `AllReduce` 涉及的全员是否都已进入调用、参数是否完全匹配、GPU 完成点是否推进——若脚本使用 PyTorch 2.9 默认惰性通信器路径，必须重点核查首次通信期间 **NCCL communicator 创建握手**的日志进度。

## 二、集合原语、训练并行切分与跨机放置

3. **五大集合原语推演**：在子组 `[1, 5]` 中，组内 `Rank 0` 和 `Rank 1` 分别提供 `[2, 3]` 与 `[5, 7]`。
   - 请写出求和 `AllReduce`、`ReduceScatter`、以组内 `Rank 1` 为根的 `Broadcast`，以及单元素切块的 `All-to-All` 输出；再将 `ReduceScatter` 输出接一次 `AllGather`，写出新输出。
4. **组合并行放置反转与 PP/EP 观测**：沿用第 06 篇 `DP=2, TP=4` 案例，对比布置甲（TP 留机内 `[0,1,2,3]/[4,5,6,7]`）与布置乙（TP 跨节点 `[0,1,4,5]/[2,3,6,7]`），说明 `Rank 5` 梯度与谁同步及各自跨机边。
   - 沿用 `115 ms` 机内步时与 `12 × 0.6 ms` TP 跨机开销，若布置甲跨机 DP 开销增至 `12 ms`，哪种布置能赶上 `125 ms` 上限？线性层下游只需各自切片时应换何原语？跨机两阶段 PP 或 EP 各紧盯哪项观测？

### 参考推理（3—4 题）

3. **五大集合原语精确输出**
   - **AllReduce（SUM）**：按位置相加得 `[7, 10]`，两端均拿到完整 `[7, 10]`。
   - **ReduceScatter（SUM）**：组内 `Rank 0` 得 `[7]`，组内 `Rank 1` 得 `[10]`；再接 **AllGather** 后两端按序拼回 `[7, 10]`。
   - **Broadcast（根为组内 Rank 1）**：两端均拿到根的 `[5, 7]`。
   - **All-to-All**：来源 0 把 `2` 留给目的 0、把 `3` 发给目的 1；来源 1 把 `5` 发给目的 0、把 `7` 留给目的 1。最终目的 0 按来源顺序得 **`[2, 5]`**，目的 1 得 **`[3, 7]`**。
4. **DP × TP 放卡反转与通信选型**
   - **布置甲**：`Rank 5` 位于 `TP 组 2` 的 1 号分片位置，跨节点与 `node-1` 的 `Rank 1` 同步梯度（4 个 DP 组跨机，2 个 TP 组留机内）。步时为 $115 + 12 = \mathbf{127\ \text{ms}}$，**超出 `125 ms` 上限**。
   - **布置乙**：`Rank 5` 位于跨机 `TP 组 1`（`[0,1,4,5]`）的 3 号分片位置，在 `node-2` 内部与 `Rank 7` 同步梯度（2 个 TP 组跨机，4 个 DP 组留机内）。步时为 $115 + 12 \times 0.6 = \mathbf{122.2\ \text{ms}}$，**仅布置乙达标**。
   - **原语切换与 PP/EP 观测**：下游各 TP 成员只需各自输出片段时，直接用 **`ReduceScatter`** 边归约边切分交付；PP 须沿**同一微批次**追踪边界激活（前向）与激活梯度（反向）的送达时刻；EP 则须按列统计**每个目标专家实际收到的 token 数**及其计算/回传时刻，因为来源行总量均等时，目的地仍可能严重偏斜。

## 三、同步训练故障与在线推理 PD 分离架构

5. **慢成员、进程退出与 Checkpoint 回滚**：在普通八卡 DDP 训练中，其余七卡于 `35 ms` 就绪最后梯度桶，`Rank 5` 拖到 `50 ms` 才就绪；全员齐备后归约耗时 `10 ms` 且无重叠工作。步时增加多少？
   - 若改为 `Rank 5` 在该操作前已经崩溃退出，靠哪些对齐记录将它与“晚到”彻底区分？作业拥有 1 次重启预算，最近完整 Checkpoint 在第 `400` 步，第 `480` 步完成后故障，重启成功至少要重算多少步？
6. **大模型在线推理的 TP 放置与 PD 分离网络核算**：现在改用这两台四卡节点部署一个 80 层、70B GQA（`320 KiB/token`）的大模型在线推理服务。
   - **(a)** 若单副本采用 `TP=4`，应选布置甲（每节点各放 1 个独立 `TP=4` 副本）还是布置乙（`TP=4` 跨两节点）？按每层 2 次阻塞 AllReduce、机内 NVLink 单次 `15 μs` 与跨机单次 `150 μs` 估算单 token 通信延迟差。
   - **(b)** 若进一步改为 **PD 分离**——`node-1` 作 Prefill 实例、`node-2` 作 Decode 实例——一条 `8,192` token（8K）的长上下文请求需跨节点迁移多少 KV Cache？在普通 `10 Gb/s` TCP（有效 `1 GB/s`）与 `200 Gb/s` RDMA（有效 `20 GB/s`）下，整块迁移各需多久？这说明了什么基础设施约束？

### 参考推理（5—6 题）

5. **故障对齐与恢复代价**
   - 最晚就绪时刻从 `35 ms` 推后至 `50 ms`，加上不变的 `10 ms` 归约，步时从 `45 ms` 升至 **`60 ms`（净增 `15 ms`）**。
   - 按运行 ID、尝试号、组成员表与操作序号对齐：晚到场景中能看到 `Rank 5` 随后发出匹配调用并最终留下 GPU 完成记录；退出场景则呈现“目标操作序号缺失调用 + 同 PID 在 Agent 记录中提前退出”，而不能仅凭其他七卡的超时报错草率定性。
   - 重启后加载第 `400` 步 Checkpoint 从第 `401` 步续跑，已完成的第 `401–480` 步共 **`80` 步**必须重算，实际恢复时间还须叠加上重会合初始化与 Checkpoint 读取耗时。
6. **推理 TP 延迟差与 PD 分离 KV 迁移核算**
   - **(a) 推理 TP 放置**：必须选**布置甲**（每节点各放 1 个机内 `TP=4` 副本，跨节点按多副本 DP 水平扩容，既隔离故障又零跨机同步）。
     - 80 层模型每 token 触发 $80 \times 2 = 160$ 次串行阻塞 AllReduce：机内 NVLink 总通信仅 $160 \times 15\ \mu\text{s} = \mathbf{2.4\ \text{ms}}$，跨节点则飙升至 $160 \times 150\ \mu\text{s} = \mathbf{24.0\ \text{ms}}$（多出 `21.6 ms`，击穿 TPOT 体验线）。
   - **(b) PD 分离 KV 迁移**：8K 上下文 KV Cache 体积为：

$$V_{\text{KV}} = 8,192 \times 320\ \text{KiB} = 2,621,440\ \text{KiB} = 2.5\ \text{GiB} \approx 2.68\ \text{GB}$$

$$T_{\text{10G TCP}} \approx \frac{2.68\ \text{GB}}{1\ \text{GB/s}} \approx \mathbf{2.68\ \text{s}}, \qquad T_{\text{200G RDMA}} \approx \frac{2.68\ \text{GB}}{20\ \text{GB/s}} \approx \mathbf{134\ \text{ms}}$$

   - 这笔账直白证明：**PD 分离虽消除了长 Prompt 对 Decode 的算力抢占，却把跨节点点对点带宽推到了 TTFT 关键路径上**——只有配合高速 RDMA / GPUDirect RDMA（及逐层异步流式传输），跨机 PD 分离才能在生产环境真正落地。
