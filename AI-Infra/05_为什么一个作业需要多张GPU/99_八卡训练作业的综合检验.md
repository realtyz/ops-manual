
沿用节点 A、B 各四张 GPU 的教学环境。A 的全局 Rank 为 0—3，B 为 4—7，每卡一个 Worker。以下各题共享节点和设备表，分别替换容量、通信或故障条件。只需纸面复算。

## 从容量约束推到完成期限

1. **显存和时间。** 某负载在反向末尾，完整参数、梯度与优化器状态合计 `52 GiB`。每卡可用预算降为 `32 GiB`。八路均匀全分片时，该时刻每卡另需 `16 GiB` 激活和 `8 GiB` 临时空间。普通 DDP 和分片各能否通过此时刻的预算？若预取还要占 `2 GiB` 且同时存活，结论如何？另一个能放入单卡的负载要在 `1,250 s` 内稳定迭代 `10,000` 步。它加到八卡后每步计算用 `50 ms`，其余落在关键路径上的开销最多能有多少？
2. **成员和设备。** 启动参数是 `--nnodes=2 --nproc-per-node=4`。B 的可见顺序为 `B2,B0,B3,B1`。全局 Rank 5 的 Local Rank 是 1，子组为 `[1,5]`。写出该进程的 CUDA 序号、UUID 简称、主机 index 和组内 Rank，并解释它和谁通信。若 A、B 的八个 Worker 的初始化调用都返回，但首次求和迟迟没有结果，你会检查哪些事件？

**参考推理**

1. 普通 DDP 每卡复制 `52 GiB`，仅这项就超过 `32 GiB`。分片后，该时刻每卡需要 `52 ÷ 8 + 16 + 8 = 30.5 GiB`，余 `1.5 GiB`。若多出的 `2 GiB` 同时存活，`32.5 GiB` 会超过预算 `0.5 GiB`。逐阶段检查实际峰值才能判断整次运行是否能放下。另一个负载每步时间上限为 `125 ms`，减去 `50 ms`，最多剩 `75 ms`。
2. 两节点会合后预期启动八个 Worker。Rank 5 在 B，`LOCAL_RANK=1` 依次映射到 `cuda:1`、可见列表第二项 B0、B 主机 index 0。在给定子组里它是组内 Rank 1，同组伙伴是 A 的全局 Rank 1。进程组初始化都返回后，继续查本次操作涉及的各 Rank 是否进入、是否匹配、GPU 结果是否可读。若通信器使用惰性初始化，还要在首次操作区间查 communicator 创建进度。初始化返回只确认了前一阶段。

## 从数据布局推到跨机交换

3. **集合语义。** 在子组 `[1,5]` 中，组内 Rank 0 和 1 分别提供 `[2,3]` 和 `[5,7]`。写出求和 AllReduce、ReduceScatter、以组内 Rank 1 为根的 Broadcast 以及每 Rank 将输入切成一元素一段做 All-to-All 的输出。随后把 ReduceScatter 的两份结果做 AllGather，写出新输出。
4. **切分与放置。** 在第 06 篇的 `DP=2, TP=4` 案例中，比较布置甲 `[0,1,2,3] / [4,5,6,7]` 和布置乙 `[0,1,4,5] / [2,3,6,7]`。Rank 5 的梯度分别跟谁同步，两种布置各有什么跨机？沿用 `115 ms` 的机内基线和 `12 × 0.6 ms` 的串行 TP 开销，但把甲的整步跨机 DP 开销改为 `12 ms`。哪种布置能赶上 `125 ms` 的步时上限？第 05 篇的线性层若两个成员各持部分和、下游只需各自输出段，应该怎样合并？若改用跨机的两阶段 PP 或 EP，分别应观察哪项数据来解释谁在等待？

**参考推理**

3. AllReduce 按位置加得 `[7,10]`，两端都有整份。ReduceScatter 后，组内 0 得 `[7]`，组内 1 得 `[10]`，再 AllGather 后两端都是 `[7,10]`。Broadcast 后两端都是根的 `[5,7]`。All-to-All 时来源 0 把 `2` 给目的 0、`3` 给目的 1，来源 1 把 `5` 给目的 0、`7` 给目的 1，所以两端按来源分别得到 `[2,5]`、`[3,7]`。
4. 在甲中，Rank 5 的 TP 组内位置是 1，它与 A 上 Rank 1 同步同一分片的梯度。四个 DP 组跨机，TP 组各在机内。在乙中，Rank 5 位于 TP 组 1 的位置 3，对应 TP 组 2 的 Rank 7，DP 同步留在 B，跨机的是两个 TP 组。甲要 `127 ms`，乙要 `122.2 ms`，给定模型中只有乙达标。如果各 TP 成员只需输出中的一段，按相同位置求和再按段交付，可用 ReduceScatter。PP 要沿同一微批次找前向激活和反向激活梯度的送达时刻。EP 要数每个目标专家实际收到的 token 并看其计算完成和结果返回时刻，来源 token 数相等时，目的地仍可能负载偏斜。

## 用同一轮证据解释停顿和恢复

5. **等待和失败。** 在普通八卡 DDP 的另一轮训练中，其他 Rank 在 `35 ms` 提供最后一个 bucket，Rank 5 到 `50 ms` 才提供。规约要等所有输入就绪后花 `10 ms`，没有其他可重叠工作。步时增加多少？若改为 Rank 5 在该次调用前已经退出，哪些记录能将它与晚到区分？作业有一次重启预算，最近的完整 Checkpoint 为第 400 步，故障发生于第 480 步完成之后。若两节点仍可会合并成功恢复，需重算几步？

**参考推理**

5. 同组最晚就绪时刻从 `35 ms` 移到 `50 ms`，通信仍是 `10 ms`，步时从 `45 ms` 增至 `60 ms`。按运行 ID、尝试编号、组成员和操作序号对齐。晚到场景可看到 Rank 5 随后发出匹配操作，最终有 GPU 完成证据。退出场景需要将缺失调用与同一 PID 的 Agent 退出记录对应起来。只有其他 Rank 的超时报错时，证据范围仍停留在等待现象。重启成功后从 401 开始，已完成的第 401—480 步共 `80` 步要重算，另计初始化和加载耗时。

## 作业需求怎样落到基础设施

显存预算回答哪些状态必须留在本卡、哪些可以分给别的成员。数据切分改变所有权，决定某项计算什么时候需要谁的输入。把通信组与当轮设备表叠起来，才能分辨机内与跨机依赖。结果参与关键路径时，慢成员、传输进度或故障就会反映到整个作业的时间预算中。

第 06—08 章从这条跨机依赖出发，沿 GPU 缓冲区、网卡、网络和通信库追踪数据。第 15 章从同一组成员需求出发，解释为什么有时需要为整个作业一起交付资源。
