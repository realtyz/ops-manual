# 读懂一份多机作业记录

## 先建立一份能够串起来的材料

本篇回到 `job-05` 的完整 W 组，采用四成员副本式 DP，每 Worker 一张设备，所有成员样本数相同。它不是第四篇的 DP×TP 变体，也不是第一篇 56 GiB、复制后放不下的容量案例；这里已知每卡峰值 32 GiB、低于应用预算 44 GiB。

以下全部是**人工编写的教学摘要**，不是 PyTorch/NCCL 原始日志。作者定义了字段与事件：`generation` 为本例的启动代次标签，`ready` 表示本地相应计算已完成，`done` 表示结果已经完成并满足后续使用依赖，不能拿 API 返回代替。跨节点相对时刻由题设提供共同参考，真实采集时需另核对时钟、采集误差或使用可对照的跟踪方法。

```text
job=job-05 generation=0 expected_agents=2 workers_per_agent=2
10:00:00.000 agent=train-a rendezvous_enter id=job-05 endpoint=train-a:29400
10:00:00.010 agent=train-b rendezvous_enter id=job-05 endpoint=train-a:29400
10:00:00.100 rendezvous_complete agents=2 world_size_for_workers=4
10:00:00.200 workers_mapped r0=train-a/A1 r1=train-a/A0 r2=train-b/B0 r3=train-b/B1
10:00:00.500 process_group_init_returned ranks=[0,1,2,3]
10:00:00.700 first_allreduce_done validation=pass
```

到 00.100 可以确认节点级成员形成；到 00.200 能结合第二篇的 UUID 表定位四个 Worker；00.500 只给初始化返回；00.700 才有首次操作完成和正确性证据。这个小测试未给字节数与计时范围，不能据此评估满载吞吐。

## 从一次慢步恢复因果关系

现在给出第 12 步的**自拟事件表**。使用第五篇单桶、全部输入 ready 后再执行通信的模型，本轮输入为每成员 256 MB（`256×10^6 B`）的 FP32 梯度；四人做匹配的 SUM AllReduce，再按本例需要取平均。所有成员本步同时开始，本轮归约服务时间给定为 20 ms，不与本地计算重叠。

| 成员 | 相对本步起点的 ready | done | 结果校验 |
| --- | --- | --- | --- |
| r0 | 80 ms | 140 ms | 通过 |
| r1 | 82 ms | 140 ms | 通过 |
| r2 | 81 ms | 140 ms | 通过 |
| r3 | 120 ms | 140 ms | 通过 |

r0 在材料中经历 `140−80=60 ms` 的结果等待，其中 40 ms 在等最晚输入，20 ms 是题设通信服务。不能用 `256 MB/60 ms` 得到“网卡有效吞吐”，也不能把所有成员的等待相加当成本步墙钟时间。共同完成时刻只有一个：140 ms。

补充材料规定 r3 本轮输入加载比其健康轮次多花 36 ms，r3 其余本地路径不变，通信阶段保持 20 ms。于是移除这份延迟后 r3 在 84 ms ready，共同完成 104 ms。按这个材料，可以把新增 36 ms 归因于输入供应迟到；还不能进一步判断是存储、CPU 解码、主机内存争用还是其他数据路径，下一份证据应分解 r3 的输入供应阶段。第 09 章再展开这些路径。

每个成员每步处理 8 个样本、累积次数为 1，本步全局批量为 32。健康吞吐为 `32/0.104≈307.7 样本/s`，慢步为 `32/0.140≈228.6 样本/s`。这同时说明：模型和卡数相同、归约服务也相同，整体吞吐仍能因一个成员迟到而下降。

## 再看两种都像“通信挂了”的事件

下面的 `seq` 是作者给 W 中逻辑通信操作标的序号，不是某个版本日志保证出现的字段。两个场景互相独立。

**场景 A：调用不同。**

```text
# 自拟调用摘要，group=W generation=0
r0 seq=7 op=AllReduce count=1024 dtype=FP32 reduction=SUM
r1 seq=7 op=AllReduce count=1024 dtype=FP32 reduction=SUM
r2 seq=7 op=AllReduce count=1024 dtype=FP32 reduction=SUM
r3 seq=7 op=Broadcast count=1024 dtype=FP32 root=0
later: operation_timeout observed_by=[r0,r1,r2]
```

已知证据直接支持“W 的第 7 项操作不匹配”，应先核对 r3 的程序分支和各成员调用轨迹。r0—r2 报超时，不表示三张 GPU 同时故障。更换底层传输不能使这两个不同操作变成同一次正确通信。

**场景 B：成员退出。**

```text
# 自拟事件摘要，group=W generation=0，四成员原计划执行相同下一项
t=0 ms   r3 allocation_failed requested=6 GiB available_in_app_budget=4 GiB
t=2 ms   r3 worker_exit code=1
t=5 ms   r0,r1,r2 awaiting_next_collective
t=20 ms  launcher_failure_observed failed_rank=3 action=stop_worker_group
generation=1 new_worker_group_started workers=4
generation=1 checkpoint_loaded step=100 all_shards=complete
```

这份材料把最早失败放在 r3 的分配阶段，组等待发生在它之后，支持先调查显存峰值与新申请为什么超出余量。`available_in_app_budget` 是教学预算字段，不是设备工具原始空闲量。本场景给足了申请失败与退出证据，不需要先假定网络断开。

新代次四成员启动并载入完整检查点后，还需重新建立映射与通信并校验恢复进度，不能让 generation=1 与旧组残余调用混用。这里的 `step=100` 表示检查点已完整提交的第 100 步；若失败时正准备第 104 步，101—103 的三个已完成但未保存步骤仍须重算。重启计数与恢复步号是两类不同信息。

## 独立练习

各题独立，除明确引用某篇的条件外，以本题给定条件为准。先写出推导，再对照答案。

### 1. 卡数增加后能否放下

每卡应用预算 44 GiB，长期状态 56 GiB，本卡输入与中间结果 12 GiB，本卡工作区与通信缓冲 6 GiB。四卡全复制与四卡均分长期状态分别需多少显存、是否可容纳？在均分方案中再增加一个与所有对象同时存活的 20 GiB 聚合缓冲，结果怎样？

### 2. 将一个等待成员定位到设备

使用第二篇的本次映射。r0 和 r2 的 Local Rank 都是 0，它们是否使用同一张设备？写出各自节点、PID、主机 index 与 BDF。r3 在有序组 G=`[r1,r3]` 中的组内 Rank 是多少？G 内 root=0 指哪张物理卡？

### 3. 手算归约、分发与重新聚合

二成员组 H 中，组内 Rank 0 输入 `[1,2,3,4]`，Rank 1 输入 `[10,20,30,40]`。分别求 SUM AllReduce 的各成员结果，以及等分 SUM ReduceScatter 的各成员结果；后者再接 AllGather 得到什么？每个输入元素为 FP32 时，ReduceScatter 的每人输入、输出字节数是多少？

### 4. 区分广播、拼接与重分布

W 的 r2 有 `[7,8]`，希望所有成员得到它，应选什么操作？另有四人各贡献 1024 个 FP32 元素的 AllGather，每人收发缓冲分别多大？对于第三篇标签表，r2 的 All-to-All 输出是什么？每个 `xij` 为 1 MiB 时，四成员间需交给其他成员的有效负载合计多少？

### 5. 把分工变成通信与批量

写出下列要求相应的典型交换：完整副本处理不同输入后统一梯度；两个成员分别得到同一标量的贡献 10 和 21，双方都要完整结果；连续两个阶段交接前向和反向；输入按目的专家分发并回送。第四篇 DP=2、TP=2 的布局中，每副本微批量 8、累积 4 次，全局批量多少？列出两个 DP 组。

### 6. 复算时间与等待

沿用本篇第 12 步条件。求共同完成、r1 等其他输入的时间，以及 r1 从 ready 到 done 的时长。若 r3 在 84 ms 就绪，其余不变，共同完成和每步 32 样本的吞吐是多少？这些数据能否独立证明使用了 RDMA？

### 7. 算出流水空泡与专家热点

第四篇的两阶段零通信前向模型，各阶段每微批 10 ms，改为 8 个微批次，求共同完成与有效设备时间比例。再按该篇专家路由表求 r3 收到的总记录数、外部来源记录数；每条 2 KiB 时分别多大？保持原专家计算假设，为什么 r0 快速空闲仍不能把整个专家阶段缩至 1 ms？

### 8. 判断初始化与失败阶段

已知两台 Agent 都可连接 `train-a:29400`，但只有 train-a 加入 `id=job-05`，train-b 加入 `id=job-06`。能否按本章固定二节点配置形成同一组？如果同一 W 的下一项操作出现场景 A，应优先核对什么？如果场景 B 发生，先报告超时的 r0 是不是已经被证明为故障源？

### 9. 计算扩展与恢复成本

第一篇固定工作量模型中，单卡 400 ms，其中可分摊 360 ms、公共 40 ms；四卡新增串行暴露通信 50 ms、不均衡 10 ms。求四卡耗时、加速比、效率。另有固定四卡作业，失败丢失 30 s、恢复用 10 s，无排队和其他成本，求额外墙钟时间及 GPU·s。若失败由确定的同一步 OOM 引起，仅增加重试次数是否解决原因？

## 参考答案与推导

### 1. 容量随放置规则变化

全复制每卡 `56+12+6=74 GiB`，超出 30 GiB，不能容纳；均分每卡 `14+12+6=32 GiB`，余量 12 GiB，可以容纳。再加同时存活的 20 GiB 后为 52 GiB，超出预算 8 GiB。总容量充足并不能消除每卡峰值限制。

### 2. 相同本地序号属于不同节点

r0 是 train-a/PID 4100/A1/主机 index 1/`0000:42:00.0`；r2 是 train-b/PID 5200/B0/主机 index 0/`0000:41:00.0`。它们是不同设备。r3 在 G 的组内 Rank 为 1；G 内 root=0 是全局 r1，即 train-a 的 A0。确认完整 UUID 时回查第二篇身份表。

### 3. 先逐位置求和，再确定结果在哪里

逐位置和为 `[11,22,33,44]`，AllReduce 后两人各得完整数组。等分 ReduceScatter 后组内 Rank 0 得 `[11,22]`，Rank 1 得 `[33,44]`；AllGather 后两人恢复完整 `[11,22,33,44]`。每人输入 4 个 FP32 元素，即 16 B；输出两个元素，即 8 B；这里的 `recvcount=2`，不是 4。

### 4. 相同内容、全部分块和不同目的各有操作

采用 root=r2 的 Broadcast。AllGather 每人发送 `1024×4=4096 B`，接收 `4×1024×4=16384 B`。All-to-All 中 r2 收到 `[x02,x12,x22,x32]`；其他成员交付量为 `4×3×1=12 MiB`，不包含自留四块，不等于物理链路累计字节数。

### 5. 看交换目的再选形态

副本梯度典型采用 AllReduce，再按需要平均；10 与 21 用 SUM AllReduce 可让两人都得 31。PP 的前向激活、反向梯度按相邻阶段交接；EP 具有按目的专家分发再回送的 All-to-All 形态。全局批量为 `8×2×4=64`；DP 组为 `[r0,r2]`、`[r1,r3]`。如果将 TP 的 2 再乘一次，会重复计算同一批输入。

### 6. 完成时间跟最晚依赖走

共同完成为 `120+20=140 ms`。r1 等其他输入 `120−82=38 ms`，从 ready 到 done 共 `140−82=58 ms`，其中含 20 ms 通信服务。r3 改为 84 ms 时共同完成 `84+20=104 ms`，吞吐 `32/0.104≈307.7 样本/s`。上述时间没有提供后端与路径证据，不能独立证明 RDMA。

### 7. 先计算阶段时隙，再按目的列求和

前向需 `（8+2−1）×10=90 ms`，有效工作 `8×2×10=160 ms`，设备时间 180 ms，比例约 88.9%。专家 r3 的入流为 `1+1+1+3=6` 条，12 KiB；其中自身 3 条，外部 3 条、6 KiB。r2/r3 各有六条串行工作，按题设共同专家计算需 6 ms；r0 空闲不自动迁移专家和状态，也不会取消其他输入的依赖。

### 8. 从最早出现的不一致往后解释

两个不同 id 进入不同会合，各自不足本例要求的二节点，不能形成同一四成员组。场景 A 先核对同组调用次序及 r3 的程序分支，已有材料直接显示操作不匹配。场景 B 的最早明确失败在 r3 的分配与退出，r0 的超时是后续影响；还没有证明 r0 设备失效。

### 9. 计算新增成本，再决定恢复范围

四卡 `360/4+40+50+10=190 ms`；加速比 `400/190≈2.11`，效率约 52.6%。恢复额外墙钟 `30+10=40 s`，四卡合计 `4×40=160 GPU·s`。重试不改变峰值和预算，确定性 OOM 若条件不变仍会复现，需要先改变导致失败的条件。

学完本章，应能把一份多卡需求写成：**容量与时间目标 → 成员/设备映射 → 数据分工 → 所属通信组与交换语义 → 初始化及完成条件 → 等待和恢复范围**。第 06 章接着解释这些数据怎样通过 RDMA 路径移动；尚未写作的后续章节以学习大纲为入口。
