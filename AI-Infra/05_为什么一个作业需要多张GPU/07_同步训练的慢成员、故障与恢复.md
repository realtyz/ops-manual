
在两节点八卡的普通 DDP 作业里，每个 Worker 都要为默认组的梯度规约提供输入。七个 Rank 已经发出调用，第八个还没到时，等待会沿着“梯度就绪 → 规约结果 → 参数更新”的依赖传播。第八个 Rank 晚到、发出不同的调用或已经退出，在其他 Rank 上可能都表现为等待。 [PyTorch 2.9 · DDP Reducer](https://docs.pytorch.org/docs/2.9/notes/ddp.html) · [NCCL 2.31.2 · 集合调用的匹配条件](https://docs.nvidia.com/deeplearning/nccl/archives/nccl_2312/user-guide/docs/usage/collectives.html)

## 最晚输入就绪时刻怎样影响步时

假定最后一个梯度 bucket 的规约是这步更新的唯一剩余前置条件。以下是**时间算例**，从同一步的共同起点计，单位为 ms。模型假定规约在所有输入就绪后花 `10 ms`，中间没有可重叠工作，更新本身的耗时忽略。真实集合操作可能在部分成员就绪时就有进展，须从实际时间线判断。

| 场景 | 其余七个 Rank 输入就绪 | Rank 5 输入就绪 | 规约结束与步时 |
| --- | ---: | ---: | ---: |
| 正常 | 35 ms | 35 ms | `max(35, 35) + 10 = 45 ms` |
| Rank 5 晚到 | 35 ms | 50 ms | `max(35, 50) + 10 = 60 ms` |

在该模型里，Rank 5 慢 `15 ms`，其余成员从自身就绪到结果可用的区间也延长 `15 ms`，通信项始终是 `10 ms`。如果下游另有独立工作到 `55 ms` 才完成，两项都齐备后才能更新，正常步要到 `55 ms`，慢步到 `60 ms`，步时就只增加 `5 ms`。这类晚到可以从输入读取、反向计算或前置通信传播过来。换成专家并行，热点专家的计算负担也会推迟其他成员取得对应输出。

## 按同一通信组和调用序号对齐事件

采集时先按运行 ID、尝试编号和通信组的成员表归并，再沿同组操作序号寻找第一处差异，顺带核对训练步号。步号若已经分歧，本身就是一条线索。每条记录保留主机、PID 和实选 GPU UUID。对于对应的调用，比较操作类型、元素数、数据类型、归约算子以及适用的根或分段。CPU 进入调用与 GPU 完成分开记录。跨节点比较绝对时刻需要对齐时钟，单机阶段耗时可用本机单调时钟。

下表四行是**独立的教学记录**，都发生在 `ai05-demo-001` 的尝试 0。跟踪训练步 480、八 Rank 默认组的操作序号 901。预期操作为 `AllReduce(SUM)`，每 Rank 有 `1024` 个 `float32` 元素。Rank 5 在 B，PID 为 3201，GPU 为 B0。事件由应用、运行器或跟踪工具各自采集。

| 观测 | Rank 5 与同组的证据 | 可作的判断 |
| --- | --- | --- |
| 其他成员先进入规约 | Rank 5 先记录输入等待，随后较晚进入匹配的规约，最终全组有 GPU 完成证据 | 对应调用晚到。用输入和反向分段时间定位延迟 |
| 其他成员等待规约 | Rank 5 在同一操作序号发出 Broadcast | 调用不匹配。从这次调用往前追踪各 Rank 的分支条件 |
| 其他成员等待或稍后超时 | Rank 5 缺少对应调用，Agent 已记录该 PID 在操作前退出 | 该成员已退出。结合同一轮退出码、异常栈和系统记录确定原因 |
| 八个成员均已提交，但未观察到 GPU 完成 | 所有成员的调用相容，进程仍存活 | 先查 GPU 操作是否开始和前置 Stream 依赖是否就绪，再查通信进展与链路 |

缺少一条日志本身只能说明缺少证据。定位早期异常通常需要合并多个 Rank 的记录，因为超时可能在最早异常之后才出现在其他成员。第 08 章会用通信库和两端网络记录进一步收窄实际路径。 [PyTorch 2.9 · 集合调用与 Stream 语义](https://docs.pytorch.org/docs/2.9/distributed.html#synchronous-and-asynchronous-collective-operations) · [NCCL 2.31.2 · 集合调用](https://docs.nvidia.com/deeplearning/nccl/archives/nccl_2312/user-guide/docs/usage/collectives.html)

## Worker 组重启与训练状态恢复

固定规模的 `torchrun` 示例设置了 `--max-restarts=1`。一个 Worker 失败时，若仍有重启预算且两台 Agent 能继续参与，启动器会停止并重启整组 Worker。新进程重新取得编号、选卡并建立通信。若节点或 Agent 消失，替换资源或结束作业由外部作业管理器决定。若允许 `--nnodes=1:2`，重组时 `WORLD_SIZE` 也可能改变，应用需重新建立分组和数据划分，并处理全局批次与训练进度。 [PyTorch 2.9 · torchrun 的失败与成员变化](https://docs.pytorch.org/docs/2.9/elastic/run.html#failure-modes) · [PyTorch v2.9.1 · Agent 重启流程](https://github.com/pytorch/pytorch/blob/v2.9.1/torch/distributed/elastic/agent/server/api.py)

**Checkpoint** 是应用保存的可恢复训练状态，通常包括参数、优化器状态及训练进度。恢复同一数据进度还需保存或重建合适的数据读取状态，按应用需求恢复随机数状态等。启动器负责重启进程，训练应用负责保存并加载 Checkpoint。以下是独立的**恢复教学记录**，假设故障发生在完成第 480 步之后，最近的完整保存点在第 400 步。

| 尝试 | 来源 | 记录 |
| --- | --- | --- |
| 0 | 主训练进程 | 保存并确认 `checkpoint_step=400` |
| 0 | Agent 错误汇总 | B 节点的 Rank 5、PID 3201 以 `exitcode=1` 退出，`error_file` 内有未处理的 Python 异常 |
| 1 | 启动器环境与选卡记录 | `TORCHELASTIC_RESTART_COUNT=1`。新进程在 B，本例重新采集到 Rank 5、PID 4201、GPU B0 |
| 1 | 应用 | 加载第 400 步的保存点，从第 401 步继续 |

若恢复成功，已做过的第 401—480 步共 `480 − 400 = 80` 步需要重算。耗时预算还要加上故障时尚未完成的工作、重新会合与初始化、保存点读取。第 04 篇脚本用 `@record` 包住 Python 入口，可以记录未处理的 Python 异常供 Agent 汇总。进程被直接终止时，可能只有退出码或信号。启动器按时间给出的首个失败可作为调查起点，仍需与各成员的进度和外部事件对照。 [PyTorch 2.9 · Error Propagation](https://docs.pytorch.org/docs/2.9/elastic/errors.html) · [PyTorch 2.9 · torchrun 的训练恢复要求](https://docs.pytorch.org/docs/2.9/elastic/run.html#important-notices)
