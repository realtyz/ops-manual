# 同步训练的慢成员、故障与恢复

在双节点八卡的同步训练作业里，经常能看到一种让人焦虑的现象：七张卡早就干完活、功耗掉了下来，全集群却原地僵住不动，甚至几分钟后集体触发 NCCL 超时崩溃。

同步训练像一场八人绑腿跑——每步参数更新都卡在“梯度就绪 → 集合归约 → 参数更新”的强依赖链上。只要有一名成员**晚到、发出不匹配的调用，或者已经悄悄退出**，在其余七位成员的日志里表现出来的，往往统统都是“死等通信”。

## 木桶效应：最晚就绪时刻如何放大成全组步时

用一个简单的步时模型看清慢成员（Straggler）怎样拖垮全组。假设八卡普通 DDP 的最后一个梯度桶归约是本步更新的唯一剩余前置条件：所有成员的输入全部就绪后，集合归约本身需要 `10 ms`（期间无其他可重叠工作，忽略参数更新耗时）。

从本步共同起点计时，比较全员齐步与单卡晚到 `15 ms` 两种情况：

| 场景 | 其余七个成员就绪时刻 | 慢成员就绪时刻 | 归约结束与单步总耗时 |
| --- | ---: | ---: | ---: |
| 正常步 | `35 ms` | `35 ms` | $\max(35,\, 35) + 10 = \mathbf{45\ \text{ms}}$ |
| 单成员晚到 `15 ms` | `35 ms` | `50 ms` | $\max(35,\, 50) + 10 = \mathbf{60\ \text{ms}}$ |

在这个模型里，集合通信本身的执行时间始终是 `10 ms`，但慢成员晚到的 `15 ms` 毫无损耗地放大成了**全部八张卡的步时增量**。

如果本步下游还有一段不依赖该桶的独立工作直到 `55 ms` 才结束，更新须等两者齐备，则步时变化为：

$$T_{\text{正常}} = \max(45,\, 55) = 55\ \text{ms}, \qquad T_{\text{慢步}} = \max(60,\, 55) = 60\ \text{ms}$$

此时慢成员的 `15 ms` 延迟有 `10 ms` 被并行工作吸收，净拖慢步时 `5 ms`。现实中的“晚到”既可能来自磁盘数据加载抖动、反向计算降频，也可能源自更早一步的通信排队；换成 MoE 专家并行，上一篇看到的热门专家负载偏斜同样会推迟整组拿到最终结果。

## 按运行 ID、尝试号与操作序号对齐多 Rank 故障证据

面对七张卡同时报超时，单翻某一张卡的报错几乎永远找不出真凶——**超时日志通常是受害者留下的下游症状，而不是根因本身**。

高效排障必须先把多节点事件拉到同一张坐标系里对齐：
1. **锁定范围**：按 `TORCHELASTIC_RUN_ID`、`TORCHELASTIC_RESTART_COUNT`（尝试编号）与通信组成员表归并日志，每条记录保留主机名、PID 与物理 GPU UUID；
2. **定位首分歧点**：沿同一通信组的**操作序号**与**训练步号**寻找第一处差异（步号若已错位，本身就是关键线索）；
3. **拆开计时边界**：将操作类型、元素计数、数据类型、归约算子与分段参数逐项比对，并严格区分 **CPU 进入调用** 与 **GPU 实际完成** 两个时点（跨机比绝对时间需对齐时钟，单机阶段耗时优先用本地单调时钟）。

对照双节点八卡作业（`run_id=train-demo-001`、尝试 `0`、第 `480` 步、八卡默认组操作序号 `901`，预期为 `1024` 个 `float32` 元素的 `AllReduce(SUM)`，关注位于 `node-2`、PID `3201`、绑定 `GPU-b001` 的全局 `Rank 5`），四类典型症状的判读逻辑如下：

| 其余七个成员的表现 | 目标成员（`Rank 5`）与同组对齐证据 | 故障定性与下一步排查方向 |
| --- | --- | --- |
| 较早进入归约并开始等待 | 先记录输入等待，随后较晚进入完全匹配的 `AllReduce`，最终全组均有 GPU 完成记录 | **调用晚到（慢成员）**：拆分输入加载、前反向计算与前置通信的分段耗时锁定瓶颈 |
| 长期卡在 `AllReduce` 等待 | 在同一操作序号 `901` 发出了 `Broadcast` 而非 `AllReduce` | **调用不匹配（代码分歧）**：从该序号回溯各 Rank 的条件分支逻辑（如空数据早退或条件日志分支） |
| 持续等待并最终触发超时 | 缺少序号 `901` 的调用记录；Agent 日志显示 PID `3201` 在该操作前已异常退出 | **成员提前退出**：结合同轮退出码、Python 异常栈与宿主机内核/驱动日志查死亡原因 |
| 全部八个成员均已提交 | 各方调用参数完全相容且进程均存活，但迟迟未观测到 GPU 完成证据 | **设备执行或通信数据面卡顿**：先查本卡前置 Stream 依赖是否阻塞，再沿 NCCL 与网络链路追查 |

> [!tip] 工程直觉：缺失日志本身只代表“缺证据”
> 切忌只凭其他成员的 `Watchdog timed out` 就一口咬定是网络故障。把最早异常成员的 Agent 退出记录、操作序号与 GPU 完成点拼成统一时间线，往往五分钟就能把“网络问题”“代码分支 Bug”和“单卡 OOM 崩溃”彻底分开（[第 08 章](../08_NCCL如何组织GPU间的通信/00_内容大纲.md) 与 [第 18 章](../18_从故障现象追到具体层次/00_内容大纲.md) 将深入通信库与硬件报错联合排查）。

## Worker 组重启与 Checkpoint 状态恢复

当某个 Worker 崩溃退出后，集群怎样把它拉回来继续算？

在固定规模启动参数 `--max-restarts=1` 下，只要还有重启预算且两台节点的 Agent 仍然健康在线，`torchrun` 会**主动停止其余七个存活 Worker，并拉起一整批全新的八个 Worker** 重新会合、选卡与建立通信器。如果整台节点失联或 Agent 消失，补充新节点还是终止作业则交给外部作业管理器（如 Kubernetes / Volcano）决定。

> [!note] 弹性扩缩容边界（`--nnodes=1:2`）
> 如果作业启用了可变节点数配置（如 `--nnodes=1:2`），故障重组后的 `WORLD_SIZE` 可能发生变化。此时框架不再只是简单原地复活，应用代码必须重新构建通信分组、重切数据读取分片，并相应调整全局批次与学习率策略。

启动器只负责把进程重新拉活，**真正让训练进度不归零的是应用侧的 Checkpoint（检查点）**。一份可完整复现的 Checkpoint 通常包含模型参数、优化器状态与当前训练步号；若要求精准续读同一数据流，还需保存数据加载器进度及随机数种子状态。

追踪一次发生在第 `480` 步之后的故障恢复记录（最近完整保存点为第 `400` 步）：

| 尝试编号 | 证据来源 | 关键事件记录 |
| ---: | --- | --- |
| `0` | 主训练进程 | 完成并确认落盘 `checkpoint_step=400` |
| `0` | `torchrun` Agent 汇总 | `node-2` 的 `Rank 5`（PID `3201`）以 `exitcode=1` 退出，`error_file` 捕获到未处理 Python 异常 |
| `1` | 启动器与选卡自检 | `TORCHELASTIC_RESTART_COUNT=1`；`node-2` 重新拉起新进程 `Rank 5`（PID `4201`，仍绑 `GPU-b001`） |
| `1` | 训练应用 | 加载第 `400` 步 Checkpoint，从第 `401` 步继续迭代 |

这次恢复直接丢掉了故障前已经算完的第 `401` 到 `480` 步，白白重算的步数为：

$$N_{\text{recompute}} = 480 - 400 = 80\ \text{步}$$

真实恢复总耗时除了重算这 `80` 步，还要叠加上**故障步作废的半截计算、整组重启与重新会合初始化、以及读取百 GB Checkpoint 的存储耗时**。

第 04 篇脚本里给 `main()` 加上 `@record` 装饰器，就是为了把未捕获的 Python 异常栈自动汇总给 Agent（若进程被内核 OOM Killer 强杀，则需结合退出码与 `dmesg` 追查）。

## 对比视角：在线推理中的故障域隔离与尾延迟冲击

把上面的同步训练故障机制放到**大模型在线推理**集群里对照，两类负载的弹性哲学形成鲜明反差：

- **跨副本（DP 之间）具备天然故障隔离**：在线推理通常部署多个独立的模型服务副本。当某个副本所在节点宕机或进程崩溃时，**绝不需要拉停其他副本，更没有 Checkpoint 回滚重算**——前端网关摘除故障副本，新请求立即路由到健康副本，受损面严格收敛在单个故障实例正在处理的少数请求上。
- **副本内部（TP / EP 组内）依然存在严酷的木桶效应**：如果一个 70B 或 MoE 推理实例跨 4 张或 8 张卡运行 TP / EP，这几张卡在每生成一个 token 时都要紧密同步。一旦组内某一张卡因散热降频、PCIe 瞬时重传或热门专家偏斜慢了哪怕 `10 ms`，该实例上所有并发用户的 **P99 TPOT 尾延迟**都会瞬间飙升；而任何一张卡掉卡都会导致整个推理实例立即不可用。

> [!summary] 核心结论
> 同步训练把所有卡绑在同一条关键路径上——一慢全慢、一挂全重启，因此**多 Rank 对齐取证**和**合理控制 Checkpoint 间隔**是保住有效算力的命门；在线推理则通过多副本隔离了跨实例故障，却把延迟敏感度压到了单个 TP/EP 实例内部的微秒级同步上。下一篇，我们就专门展开大模型在线推理的多卡并行形态与 **Prefill / Decode 分离架构**。
