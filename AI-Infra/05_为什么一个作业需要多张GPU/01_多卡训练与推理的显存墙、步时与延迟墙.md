# 多卡训练与推理的显存墙、步时与延迟墙

业务团队找基础设施工程师加卡时，嘴上说的往往都是同一句话：“单卡跑不动了。”但细问下去，背后其实是三种截然不同的硬约束：
- 训练任务刚走到反向传播就报显存不足（OOM）；
- 训练单卡能跑通，但完整收敛要算上好几周，远远赶不上发版窗口；
- 大模型在线推理光是把权重和上下文 KV Cache 塞进一张卡就爆了，或者即便勉强塞下，首字等待和吐字速度也慢到用户根本没法用。

加 GPU 并不是万能加速器。多出来的显卡究竟能不能解围，取决于新卡分摊的是**静态显存、总计算量，还是单次生成的访存带宽**。

## 训练为何冲破单卡：显存峰值与复制 vs 分片

先看训练一步内部究竟诞生了哪些吃显存的对象。模型用参数把输入样本映射成输出，**前向计算**同时产生供后续求导用的中间结果，称为**激活（Activation）**；对比预测输出与目标得到损失后，**反向计算**利用激活算出损失对各参数的**梯度（Gradient）**；最后由优化器按梯度更新参数，并常为每个参数长期保存动量、方差等历史状态。完成一次参数更新，记作一个**训练步（Step）**。

单步更新消耗的全部样本称为**全局批次（Global Batch）**。单个计算副本可以把分配到的样本拆成多次较小的**微批次（Micro-batch）** 依次前向、反向，把梯度累加起来再统一更新。例如 4 个副本各连续执行 2 个微批次、每个微批次含 8 个样本，则单步全局批次为：

$$\text{Global Batch} = 4 \times 2 \times 8 = 64\ \text{样本}$$

这四类训练状态在单步内的存活窗口各不相同，核算峰值显存时必须盯住**同一时刻共存的各项之和**：

| 显存项目 | 存活阶段 | 核算关注点 |
| --- | --- | --- |
| 参数与优化器状态 | 参数贯穿前向与反向；优化器状态建立后通常跨步常驻 | 参数总量、存储精度、优化器类型及是否跨卡分片 |
| 梯度 | 反向传播时逐步生成并保留至参数更新；累积时跨微批次留存 | 同时驻留的梯度大小、有无分片、是否复用通信缓冲 |
| 激活 | 从前向生成持续到反向最后一次求导消费完毕 | 微批次大小、序列长度、是否启用激活重算 |
| 工作区与临时缓冲 | 算子计算、参数重组、集合通信与更新期间动态出现 | 瞬时并发缓冲区大小，以及预取下一模块造成的内存重叠 |

> [!tip] 工程直觉：不要简单把各项“历史峰值”直接相加
> 不同对象往往在不同时间点冲上峰值，逐项取峰值相加只能算作粗略上界。真实排查 OOM 时，还需区分 PyTorch 张量实际分配量、CUDA 缓存分配器（Caching Allocator）保留量与设备侧总占用，并为 CUDA 上下文和其他运行库预留安全余量。

用一笔容量账就能立刻看出“加卡不改状态归属”为什么救不了 OOM。设集群共有 8 张整卡，每卡可用于训练状态和缓冲的净预算为 `48 GiB`（$1\ \text{GiB} = 2^{30}\ \text{B}$）；当反向末尾仍保留梯度时，完整模型参数、梯度与优化器状态合计占 **`52 GiB`**。

对比两种 8 卡策略在该时刻的每卡显存占用：

$$M_{\text{复制}} = 52\ \text{GiB} + M_{\text{激活}} + M_{\text{临时}} > 48\ \text{GiB}$$

$$M_{\text{全分片}} = \frac{52}{8} + 16\ (\text{激活}) + 8\ (\text{重组与临时缓冲}) = 30.5\ \text{GiB} < 48\ \text{GiB}$$

| 八卡放置策略 | 该时刻每卡显存占用 | 能否通过 `48 GiB` 预算 |
| --- | --- | --- |
| **状态完整复制**（如普通 DDP，8 副本分摊样本） | `52 GiB` + 激活与临时缓冲 | **超预算**：哪怕把微批次降到 1 压缩激活，仅复制状态就超出 `4 GiB` |
| **状态八路均匀全分片**（如 FSDP2） | `6.5 + 16 + 8 = 30.5 GiB` | **通过**：尚余 `17.5 GiB`，但仍需继续核查参数重组与预取时的瞬时峰值 |

PyTorch 的普通 **DDP**（DistributedDataParallel）属于第一类，它只切分样本、不切分模型状态；而全分片数据并行（FSDP2）改变了参数、梯度和优化器状态的所有权，把 `52 GiB` 拆到 8 张卡上，同时引入前向/反向按需重组的额外通信与临时空间（第 05 篇展开追踪）。

## 训练的算力墙：步时、关键路径与完工周期

再看第二类约束：模型单卡放得下，但跑完一轮训练太慢。固定全局批次、总计算量与 `10,000` 次更新步数，设单卡每步纯计算耗时 `400 ms`，多卡理想均分计算，稳定迭代期仅统计均分计算时间与**未被计算覆盖的额外开销**（主要是同步与通信等待）：

| 资源配置 | 每卡计算时间 | 未覆盖额外开销 | 每步耗时 | `10,000` 步总完工时间 |
| --- | ---: | ---: | ---: | ---: |
| 单机 1 卡 | `400 ms` | `0 ms` | `400 ms` | `4,000 s` |
| 单机 4 卡 | `100 ms` | `30 ms` | `130 ms` | `1,300 s` |
| 双机 8 卡 | `50 ms` | `70 ms` | `120 ms` | `1,200 s` |

从 4 卡扩到 8 卡，计算时间砍半省出 `50 ms`，但跨机通信把未覆盖开销从 `30 ms` 推高到 `70 ms`，净收益仅 `10 ms`。如果业务死线是 `1,250 s` 内跑完 `10,000` 步，则单步上限与八卡能容忍的最大额外开销为：

$$T_{\text{step,max}} = \frac{1,250\ \text{s}}{10,000} = 125\ \text{ms}, \qquad T_{\text{overhead,max}} = 125 - 50 = 75\ \text{ms}$$

这里要抓住**关键路径（Critical Path）** 的概念：决定一步最早何时完成的依赖链才是关键路径。像 DDP 会在反向传播过程中把已算出的梯度异步归约，与剩余层的反向计算重叠；真正把步时拉长的，只是没被算力藏住、最终暴露在步末的那一段等待。

> [!warning] 常见误区：不要把“吞吐提升”直接等同于“训练更快结束”
> 如果扩卡时保持每卡样本数不变、让全局批次同步翻倍，单步吞吐（$\text{全局批次} \div \text{步时}$）往往非常好看：例如 4 卡 `64` 样本 / `130 ms` 约 `492 样本/s`，8 卡 `128` 样本 / `180 ms` 升至 `711 样本/s`。
>
> 但若算法收敛仍需更新 `10,000` 步，后者总耗时反而拉长到 `1,800 s`（虽然处理的总样本数翻了倍）。推算完工周期前，务必先问清约束是“总样本量固定”还是“更新步数固定”。

## 推理为何同样冲破单卡：百 GB 显存墙与单用户延迟墙

如果把视角切到**大模型在线推理**，驱动多卡部署的底层物理压力与训练既有共性、又有本质分叉：

1. **百 GB 权重与动态 KV Cache 的显存墙**：训练可以减小微批次、重算激活甚至切分优化器来省显存；而在线推理虽然没有梯度和优化器，但一个 70B 参数模型仅 BF16 静态权重就占约 **`140 GB`**，早已超过单张 80 GB H100 的整卡显存上限。再加上 [第 02 章](../02_GPU如何计算与显存/00_内容大纲.md) 算过的 **KV Cache** 随上下文长度和高并发请求数持续膨胀，单卡根本装不下。
2. **首字与吐字的严格延迟墙（TTFT 与 TPOT）**：训练只看几周后的总完工时间，单步多等几毫秒无关痛痒；在线推理直接面对人类用户和实时业务接口，必须同时守住两条延迟红线——
   - **首字延迟（TTFT）**：用户发完长 Prompt 后看到第一个字的等待时间，由计算密集的 **Prefill** 阶段主导；
   - **单 token 生成间隔（TPOT / ITL）**：流式吐字时相邻两个 token 的间隔，由显存带宽受限的 **Decode** 阶段主导。

哪怕把 70B 模型量化到 FP8（约 `70 GB`）勉强塞进一张 80 GB H100，在 Decode 阶段每生成一个 token 都要把全部 `70 GB` 权重和 KV Cache 从 HBM 完整读一遍。

按 H100 约 `3.35 TB/s` 标称显存带宽，仅读权重一项理论下界就超过 `21 ms`，一旦加上长上下文 KV Cache 和并发请求，TPOT 很快就会跌破流畅体验线。把模型切到 4 张或 8 张卡上并行执行，等于同时叠加了多卡的算力与 HBM 聚合带宽，才能把单用户的 TTFT 和 TPOT 压下来。

把训练与推理冲破单卡的驱动力并排对照，后续整章的并行设计选择就全部有了根基：

| 对比维度 | 分布式训练 | 大模型在线推理 |
| --- | --- | --- |
| **显存墙来源** | 参数 + 梯度 + 优化器状态 + 大批量激活 | 百 GB 级静态权重 + 随上下文与并发动态膨胀的 KV Cache |
| **核心性能指标** | 总完工周期、算力利用率与训练吞吐 | 首字延迟（TTFT）、吐字间隔（TPOT）与达标有效吞吐 |
| **扩卡的主要手段** | 数据并行提吞吐，状态/模型切分解 OOM | 张量/专家并行降单请求延迟与扩容，多副本水平扩总吞吐 |
| **对跨机互联的容忍度** | 梯度同步可与反向重叠，有一定跨机缓冲空间 | 层内同步按微秒计，几乎不可容忍高延迟跨机通信 |

> [!summary] 核心结论
> 单卡算力、显存容量和 HBM 带宽的三重天花板，把训练和推理共同推向了多卡与多机协作。一旦作业横跨两台节点、动用八张 GPU，通信就不再只发生在机内总线；要把任何一次跨卡或跨机交换讲清楚，第一步必须先把每个分布式进程精确锚定回物理主机和物理显卡——这正是下一篇的主题。
