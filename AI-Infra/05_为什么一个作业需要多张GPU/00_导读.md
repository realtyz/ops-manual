# 为什么一个作业需要多张 GPU

单卡放不下的工作，增加三张卡后就能放下吗？四个进程已经启动，为什么仍没有一步计算完成？回答这些问题，需要在第 04 章的数据路径之上再建立一层关系：谁持有哪些数据，哪些成员必须交换结果，以及下一步依赖谁完成。

本章学习任务是：**从容量和时间约束解释扩展动机，把进程与 GPU 对应起来，手算五类集合通信的输入输出，从四种并行方式推导通信需求，并沿作业时间线判断初始化、慢成员与成员失败的影响。**

## 必要前置与前后边界

读者已有 Linux 进程、环境变量、地址与端口，以及 Kubernetes Pod 生命周期的基础。[第 02 章](../02_GPU如何计算与显存/00_导读.md)提供显存峰值、Kernel、Stream 与异步完成；[第 03 章](../03_从驱动到CUDA应用的软件依赖/00_导读.md)提供应用访问设备的软件依赖；[第 04 章](../04_单机多卡与GPU数据路径/00_导读.md)提供设备身份、物理路径、有效带宽与共享预算。本章第一次建立 Rank、通信组、会合、集合通信和并行分工，不要求读者会训练模型。

本章解释作业对基础设施提出什么要求。第 06 章展开 RDMA 与 GPU—NIC 数据路径，第 07 章展开集群网络，第 08 章展开 NCCL 的算法、路径选择与原始日志；第 15—16 章展开资源成组与调度实现。本文会说明相应动机，保留当前推导所需机制，不提前提供网络调优参数或作业控制器配置。训练和推理只作为负载例子，模型算法与效果不在范围内。

## 教学模型与材料约定

本章使用新的虚构作业 `job-05`，运行于 `train-a`、`train-b` 两台服务器；**它们不是第 04 章的 `gpu-node-a`**。每机两张独占、未切分的 GPU，每卡物理显存 48 GiB，容量题统一给定应用预算 44 GiB。每个 Worker 进程负责一张 GPU，四个 Worker 组成默认通信组 W。完整映射在第二篇给出；集合通信中的 r0—r3 都指 W 中的成员编号。

这个模型未指定 GPU 型号、NVLink、NIC 速率或 RDMA 支持性，不能由卡数推断这些能力。带宽和时间题在使用处另给有效预算及串行、重叠条件，不从产品规格推算。混合并行、专家路由和流水示例是单独注明条件的分工变体，不同时套用为同一次执行。

图、环境片段、事件、张量和数值均为**自拟教学材料**，不是实测或工具原始日志。`GiB = 2^30 B`、`MiB = 2^20 B` 用于容量；`GB = 10^9 B`、`GB/s` 用于十进制传输预算。Rank 在一次成员组形成期间标识角色，重启后的身份需要重新核对；图中的通信关系不代表物理直连。

机制引用采用 **PyTorch 2.9**、**NCCL 2.31.2** 归档文档；专家通信对照采用 **Megatron Core 0.15.0** 文档，设备可见性沿用 **CUDA 12.8.1** 文档。它们分别用于解释职责和语义，不构成一套已经验证的可安装版本组合。资料核对日期：**2026-11-08**。本章不要求运行启动命令或编写训练代码。
