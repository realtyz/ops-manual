# 用具体数据推演集合通信

## 先把通信看成一份共同约定

一次点对点发送把一份数据从一个成员交给另一个成员；接收方必须知道怎样接收。**集合通信（Collective）**则让一个通信组的成员共同完成某种数据变换，例如求和、拼接或重新分发。这里先确定输入输出的逻辑含义，不指定底层走 Ring、Tree、NVLink 还是网络。

对于本篇的等长操作，成员需要匹配通信组、操作次序、元素数量、数据类型，归约还需匹配操作，广播还需匹配 root。组内成员提交先后可以不同，但必须能组成相同的逻辑操作；应用若让 r0 的第一个操作是求和、r1 的第一个操作是广播，就不能期待通信库自动猜出意图。NCCL 对不匹配调用的风险说明见 [2.31.2 Collective Operations](https://docs.nvidia.com/deeplearning/nccl/archives/nccl_2312/user-guide/docs/usage/collectives.html)。

## AllReduce：相同位置先合并，每个成员得到完整结果

以下是**自拟整数张量**，每个成员输入四个元素，对应位置做 SUM（求和）：

| W 中的 Rank | 输入 |
| --- | --- |
| r0 | `[1, 2, 3, 4]` |
| r1 | `[10, 20, 30, 40]` |
| r2 | `[100, 200, 300, 400]` |
| r3 | `[1000, 2000, 3000, 4000]` |

AllReduce 后每个成员都得到 `[1111, 2222, 3333, 4444]`。其中第一个结果来自 `1+10+100+1000`，不是把四份数组首尾相接。

SUM 只求和，若应用需要平均值，还要执行相应的除法或选择支持的平均归约语义。整数示例用于精确手算；真实浮点数的加法次序会影响舍入，因此数学等价的归约安排不保证逐位一致。

## ReduceScatter：归约相同，但每人只留下指定分块

对上表做 SUM ReduceScatter，并把四元素结果均分为四块、每块一个元素：

| 成员 | 自己最终保留的分块 |
| --- | --- |
| r0 | `[1111]` |
| r1 | `[2222]` |
| r2 | `[3333]` |
| r3 | `[4444]` |

它仍对所有输入的相同位置归约，只是输出分散保存。r2 获得第三块，不是“只把 r2 原输入留在本地”。直接使用等分块 NCCL API 时，`recvcount` 是**每个成员接收的元素数**，每个成员发送缓冲包含 `组大小×recvcount` 个元素。

## AllGather：按成员次序拼起来，不做算术归约

现在把上一步每人保留的一块作为新输入。AllGather 后四个成员各有 `[1111, 2222, 3333, 4444]`。r0 的分块排第一，依次到 r3；若每人持有两个元素，输出就有八个元素。NCCL 的 `sendcount` 指**每个成员贡献的元素数**，每个接收缓冲需要容纳 `组大小×sendcount` 个元素。

这说明 SUM ReduceScatter 接 AllGather，在同组、同序分块和相容数据语义下，能够得到与 SUM AllReduce 相同的逻辑结果。它没有证明每个 AllReduce 实现都必须显式分成这两个 API，也没有算出实际网络字节数。缓冲口径与偏移定义参见 [NCCL 2.31.2 API：AllGather 与 ReduceScatter](https://docs.nvidia.com/deeplearning/nccl/archives/nccl_2312/user-guide/docs/api/colls.html#ncclallgather)。

## Broadcast：由一个 root 提供内容，其余成员接收

W 中 root 为 r2，输入是 `[7, 8]`。Broadcast 后 r0、r1、r2、r3 的输出都是 `[7, 8]`。其他成员原先的接收缓冲内容不参与求和。对照第二篇的映射，这次源设备是 train-b 的 B0，而不是某台机器上的“GPU2”。

广播适合把一份初始配置或状态交给所有成员；它不收集其他成员各自计算出的贡献。若只需要 root 得到归约结果，则是 Reduce，而非本章要求每人取得完整归约结果的 AllReduce。

## All-to-All：每人向每个目的成员交出不同分块

以下**教学标签** `xij` 的第一个下标是来源 Rank i，第二个下标是目的 Rank j。每块等长，各输入缓冲按目的顺序摆放：

| 来源 | 发出前按目的 0、1、2、3 排列的输入 |
| --- | --- |
| r0 | `[x00, x01, x02, x03]` |
| r1 | `[x10, x11, x12, x13]` |
| r2 | `[x20, x21, x22, x23]` |
| r3 | `[x30, x31, x32, x33]` |

输出按来源顺序摆放：r0 得到 `[x00,x10,x20,x30]`，r1 得到 `[x01,x11,x21,x31]`，r2 得到 `[x02,x12,x22,x32]`，r3 得到 `[x03,x13,x23,x33]`。这是一次重分布，既不求和，也不让所有人拿到相同的全部输入。自发给自己的分块逻辑上存在，物理上不必经过外部链路。

若每块 1 MiB，则每人输入 4 MiB、输出 4 MiB；所有成员输入合计 16 MiB。扣除四份自留块，需要交付给其他成员的有效负载为 12 MiB。它仍不是交换机每条端口流量的总和；多跳、算法中转和协议开销要另算。

专家路由还可能让不同源—目的组合的大小不相同，需要交换分块计数并匹配相应接收布局。PyTorch 的 `all_to_all_single` 可用输入/输出 split sizes 表达不等长分块；本篇等长表并未规定所有 All-to-All 都等长。参见 [PyTorch 2.9：all_to_all_single](https://docs.pytorch.org/docs/2.9/distributed.html#torch.distributed.all_to_all_single)。

## 同样的输出大小，不代表同样的通信需求

| 操作（组大小 p） | 每个成员的逻辑输入 | 每个成员的逻辑输出 | 输入如何变化 |
| --- | --- | --- | --- |
| AllReduce | N 个元素 | N 个元素 | 同位置归约，完整结果复制给所有人 |
| ReduceScatter（等分） | p×n 个元素 | n 个元素 | 同位置归约，按 Rank 分块 |
| AllGather（等分） | n 个元素 | p×n 个元素 | 按 Rank 拼接 |
| Broadcast | root 提供 N 个元素 | N 个元素 | 复制 root 的内容 |
| All-to-All（等分） | p×n 个元素 | p×n 个元素 | 按目的发送，按来源接收 |

表中的元素数乘以每元素字节数，才是相应缓冲的字节数。例如四成员、每人贡献 1024 个 FP32 元素的 AllGather，发送缓冲为 4096 B，接收缓冲为 16384 B。这个小消息的运行时间可能主要由启动和协调开销决定；大消息更容易受到可用带宽限制。

为理解消息次数的代价，另设一个**单段、串行传输教学模型**：每次固定启动成本 α=10 μs，有效带宽 B=25 GB/s，无争用，时间 `T=α+S/B`。传 1 MB 用 `0.01+0.04=0.05 ms`，连续传 100 次共 5 ms；合并成一次 100 MB 则用 `0.01+4=4.01 ms`。两者负载同为 100 MB，消息次数改变了固定成本。实际合并还可能推迟提交、失去计算重叠，不能只看这份节省。

这个模型只解释启动与字节量两类成本，未包含集合算法的轮数、成员到达和物理路径。不能把集合输入字节数直接代入单段公式，宣称得到了整组完成时间。下一篇比较不同并行方式时，还要同时关注消息规模、频率和它落在依赖链的什么位置。

集合调用进入 API 不等于所有设备上的结果已经完成；CUDA 的异步工作仍要按相关 Stream、事件或框架完成语义处理。本章时间表中的 `ready` 与 `done` 是作者定义的事件，`done` 明确指结果已经满足后续依赖，不是函数刚返回。具体异步语义参见 [PyTorch 2.9：Synchronous and asynchronous collective operations](https://docs.pytorch.org/docs/2.9/distributed.html#synchronous-and-asynchronous-collective-operations)。
