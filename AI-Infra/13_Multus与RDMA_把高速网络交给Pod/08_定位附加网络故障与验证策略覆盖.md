# 怎样用证据定位附加网络故障并验证策略覆盖

两个 Pod 都能访问集群 DNS，其中发往附加网的通信却失败。先固定一对分布在两个节点上的 Pod，记录命名空间、Pod UID、实际节点、采集时间与附加网络名。把事件、设备分配、CNI 与应用结果串在同一次 Pod 启动和测试上，避免把重建前后的设备或地址当成同一次分配。

## 找到第一处缺失的证据

先读 Pod 的 `spec.nodeName`、`status.conditions` 中的 `PodScheduled`，以及相关事件 `reason` 和 `message`。设备资源不足的判断来自调度信息和目标节点资源。节点已选定时，查 kubelet 的准入与分配结果，再查运行时的 sandbox 事件。对已经运行的 Pod，将 `k8s.v1.cni.cncf.io/network-status` 中的网络名、接口和地址与 `ip -br addr` 对齐，再用 VF BDF、PodResources、`rdma link show` 和 `ibv_devinfo` 对到设备和端口。 [Kubernetes v1.36 PodResources](https://v1-36.docs.kubernetes.io/docs/concepts/extend-kubernetes/compute-storage-net/device-plugins/) · [Kubernetes sandbox 创建事件](https://github.com/kubernetes/kubernetes/blob/v1.36.0/pkg/kubelet/kuberuntime/kuberuntime_manager.go) · [Multus NAD 与 `deviceID` 日志来源](https://github.com/k8snetworkplumbingwg/multus-cni/blob/master/pkg/k8sclient/k8sclient.go)

下表是互相独立的教学快照。事件原因是 Kubernetes 或上游组件中的字段，实际消息和采集位置取决于部署版本、日志级别和 thin/thick 模式。 [Multus 配置与日志选项](https://github.com/k8snetworkplumbingwg/multus-cni/blob/master/docs/configuration.md) · [NVIDIA SR-IOV RDMA 验证流程](https://docs.nvidia.com/networking/display/kubernetes2671/quick-start/sriov-network-rdma.html)

| 观测 | 当前证据支持的判断 | 下一项取证 |
| --- | --- | --- |
| `PodScheduled=False`，事件 `FailedScheduling` 指向 VF 资源不足 | 失败在节点筛选阶段。 | 对照 Pod 的完整资源名、目标节点 `.status.allocatable` 与已绑定请求。还无 `spec.nodeName` 时暂无需沿该 Pod 查 CNI。 |
| Pod 已绑定，kubelet 拒绝节点内准入 | 调度器通过了数量等筛选，节点本地条件仍可能不满足。 | 查 kubelet 准入原因和 GPU/VF 的 NUMA 提示。CNI 阶段的证据需要待 sandbox 调用后采集。 |
| Pod 已绑定且有 VF 分配记录，事件为 `FailedCreatePodSandBox` | 设备分配已走到 kubelet，sandbox 网络接入尚未完成。 | 先从错误中找 NAD、delegate 和 `deviceID`。它们一致时，接着看 CNI 的 IPAM 错误和节点地址块。 |
| `net1` 有地址，指定接口的 Ping 成功，但主机缓冲区 Verbs 试验失败 | 附加网 IP 测试有结果，RDMA 传输这一步失败。 | 核对两端实际 RDMA 设备、端口和 RoCE GID 与 `net1` 的关系。设备枚举正常时，再用两端端口状态、注册或建连错误和 fabric 证据缩小范围。 |
| 同一设备对的主机缓冲区 RDMA 成功，改用 GPU 缓冲区注册失败 | 两端普通 RDMA 的测试路径已打通，故障发生在新增的 GPU 内存步骤。 | 核对出错一端的 GPU ID、测试构建、CUDA 和注册方式，再对照驱动与 PCIe 拓扑。 |

## 用双端试验确认数据经过指定设备

在 `gpu-h0` 的 `rank-0` 上以 `net1` 地址 `192.168.50.11` 为测试端，`gpu-h1` 的 `rank-1` 为客户端。先在两个 Pod 里用 `rdma link show` 查与 `net1` 关联的设备和端口，并让客户端查询到 `.11` 的路由。以下是采用 NVIDIA SR-IOV 验证方法的命令示意。用探测到的本地 RDMA 设备和端口给各端的 `RDMA_DEV`、`RDMA_PORT` 赋值。两端使用相同 perftest 构建与相同消息大小、迭代数和方向。`-R` 用 RDMA CM 连接 QP，客户端最后的地址取服务端附加 IP。 [NVIDIA v26.7.1 SR-IOV 双端测试](https://docs.nvidia.com/networking/display/kubernetes2671/quick-start/sriov-network-rdma.html) · [perftest 参数和两端配置要求](https://github.com/linux-rdma/perftest)

```sh
# 在 rank-0 中启动服务端。用本地设备名和端口给两个变量赋值。
ib_write_bw -d "$RDMA_DEV" -i "$RDMA_PORT" -R -s 65536 -n 1000 --report_gbits

# 在 rank-1 中启动客户端。使用 rank-1 的本地设备名和端口。
ib_write_bw -d "$RDMA_DEV" -i "$RDMA_PORT" -R -s 65536 -n 1000 --report_gbits 192.168.50.11
```

这里是 65536 B 消息和 1000 次迭代的教学设置。读结果时记录程序退出状态、实际设备、缓冲区类型和测试方向。若用端口计数器补证，记录计数属于 PF 还是 VF、采样开始和结束时间、驱动和计数语义。PF 上的总计数可能包含其他 VF 或其他任务流量。单独的计数增量只能支持计数器对应范围内发生了活动。需要引用现场输出时，应保留采集命令、时间、两端设备和系统版本，以及测量条件。

## 按数据路径验收策略

Multus 的 `namespaceIsolation` 与 `globalNamespaces` 约束 Pod 可以引用哪些 NAD。它们解决的是网络附加阶段的引用边界。配置后要观察准入与 Multus 实际处理结果。数据面的访问控制要继续查每条路径由哪个组件执行。 [Multus 命名空间范围配置](https://github.com/k8snetworkplumbingwg/multus-cni/blob/master/docs/configuration.md#namespace-isolation)

默认网络上的 Kubernetes `NetworkPolicy` 由支持它的网络插件执行。对于 `net1`，逐项查附加 CNI、NIC 工作模式和实际执行点，确认策略是否覆盖该流量。举例来说，`multi-networkpolicy-tc` 面向有对应 VF representor 的 switchdev 路径，控制器观察 `MultiNetworkPolicy`，在相应 representor 上编程 TC 规则。要用这个实现判断覆盖范围，应看到规则安装在该 VF 的 representor，并确认要约束的流量确实经过该执行点。若硬件转发或卸载改变了实际路径，按照对应实现与硬件能力重新验收。 [Kubernetes NetworkPolicy](https://v1-36.docs.kubernetes.io/docs/concepts/services-networking/network-policies/) · [MultiNetworkPolicy 的 TC 与 VF representor 实现](https://github.com/k8snetworkplumbingwg/multi-networkpolicy-tc)

用同一对测试 Pod 分别向默认 Pod IP 和附加 IP 发起受控测试，在每个网络上各验证一条预期允许与一条预期拒绝的连接。记录目的地址、实际接口、协议、策略对象和执行点。测试前先用允许路径核实服务确实监听。若要求隔离 RoCE，再用核对过设备和端口的 RDMA 试验及该实现的规则或计数证据验收。一个 TCP 连接被拒绝，只能证明该次 TCP 测试符合预期。
