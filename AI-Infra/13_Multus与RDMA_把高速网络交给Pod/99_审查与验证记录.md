### 通过项的具体检查

#### fig-13-02-02：共享 HCA

确认两个 Pod 各有 net1/macvlan 和 RDMA 访问视图；账本恰四格，A/B 两格已占、两格空闲；下方连续 HCA 底座与唯一端口表达同一个 PF 接入，端口标识为 100 Gb/s。没有把两份余额写成 Allocatable 从 4 变成 2，也没有给每份固定带宽。图能把“独立接入、逻辑记账、共用物理能力”连成一个总结。

图内 Pod 小接口/入口图标是软件接入的观察符号，不代表 Pod 内新增可拔网卡或 HCA；正文图注明确这一点。HCA/网络部分有绿色填色、软件入口偏紫，未完全遵守统一青/灰语义；此图没有 GPU 对照，名称、数量和共用底座仍明确，因此作为**非阻断配色偏差**记录，不要求重做整图。以后若修改此图，网络部分统一青色、软件部分统一灰色。

#### fig-13-03-03：VF 身份对齐

确认真实整体仅一个 NIC/PF、两个 VF、一个物理端口；A 对应 VF0/mlx5_2，B 对应 VF1/mlx5_3。VF0 放大窗中的 `0000:41:00.2`、`net1`、`mlx5_2`、`/dev/infiniband/uverbs2` 与教学映射一致；没有凭 mlx5_3 推填另一个字符设备名。放大窗明确是同一对象的不同视角，未增加硬件。物理 function 留在 NIC 范围，软件对象位于不同 Pod namespace，能回忆“同一身份、多处交付、仍共用端口”。

VF/PF 与部分对象使用蓝绿区分而非统一网络青色，核心结论条略密；按实际图片仍可辨认，图中也没有 CPU/GPU 混淆，记为非阻断风格偏差。正式图注补明连线表示身份关联、非物理数据路径，芯片内分区仅为逻辑 function 示意。

#### fig-13-05-02：Operator 与 GPU MR

确认一个 Pod/容器、共享主机内核和硬件域分层清楚；GPU Operator 与 Network Operator 分别贴在对应维护侧，用户态 CUDA 与 Verbs/provider 在工作负载容器内。G0 显存与右侧同一 GPU MR 放大对应，DMA 箭头从 GPU MR 指向 NIC/function，图中已标“逻辑 DMA，非接线图”；主机内存仍在。nvidia-peermem 位于注册条件层面，没有被画成有效载荷中转。校验纸为空且写“需数据校验”，没有用 ready 或勾选伪造 GDR 测试结果。

个别软件域/驱动采用蓝色或青色、而非全部使用普通结构灰色；维护者标签仍为灰色，软件与硬件的边界明确，记为非阻断配色偏差。右侧 NIC 为局部放大中的同一 function 视角，图注不将其算成第二个硬件。

### 未通过项：位置、影响与修改要求

#### fig-13-01-01：接入关系与数据方向没有分清

**位置**：右下 RoCE fabric 左侧，绿色箭头直接从 `net1 / 附加网络` 引出；下方 `mlx5_2/1` 只通过虚线与 net1 关联。

**影响**：这条未标注语义的箭头可以被理解为附加网络接入，也可以被理解为 RDMA 有效载荷经过 netdev；图片自身无法消除歧义。对照[第 01 篇](01_从一个Pod的两张网开始.md)“netdev、RDMA 设备与设备文件是三种对象”，以及文末明确的 Socket 栈边界，本篇的核心区别应在图上直接可见。

**必要修改**：保留 eth0 的默认网络关系；将 RoCE 的逻辑传输箭头从 RDMA 端口标片 `mlx5_2/1` 引出，并短标“RDMA 逻辑传输”。net1 与 RDMA 端口仅以细灰无箭头线标“接口对应”。字符设备页与 Multus/NAD 均不在有效载荷箭头上。修改时将相关网络对象统一青色、软件文件统一灰色。无需改变整幅布局。

#### fig-13-04-02：同一 NIC 的 function 包含范围缺失

**位置**：左侧 NUMA 0 区，`NIC / PF`、`VF0 空闲`、`VF1 已占` 画成三个独立 PCIe 板卡形态上下并列。

**影响**：空闲数量和 NUMA 归属本身正确，但板卡外形加上缺失的共同范围，容易被误读为三张实际 NIC。正文[第 04 篇](04_让设备位置与网络参数相互匹配.md)明确两个 VF 来自同一个 NUMA 0 PF；不能靠“VF”文字迫使读者忽略形态暗示。PF/VF 是同一设备的 function 视角，职责可对照 [SR-IOV CNI v2.8.1](https://github.com/k8snetworkplumbingwg/sriov-cni/blob/v2.8.1/README.md)。

**必要修改**：把三处整理进“同一 NIC”的一个范围内，只保留一块实体网卡外形；内部用 PF、VF0、VF1 逻辑占位表达，保留 VF0 空闲、VF1 已占。G0 已占、G1 空闲及 NUMA 归属保持不变。左右补“独立反例 A/B”，明确右侧是另给定设备已分配/对齐的网络反例。网络 function 改青色，GPU 保持绿色。右侧 .101/.102、9000/1500 B 的关系无须重做。

#### fig-13-06-01：应用 transport 的证据来源接错

**位置**：底部双栏观察窗，“端口计数”和“应用 transport”的两条引线均终止于 NIC/VF0。

**影响**：读者会将 NIC 计数与应用 transport 日志混为同一个采集来源，恰好违背“证据覆盖范围决定结论范围”的全文主线。[第 06 篇](06_用分层证据判断网络交付到了哪里.md)末段分别规定设备计数器与应用日志的用途；[NCCL 2.25.1 Troubleshooting](https://docs.nvidia.com/deeplearning/nccl/archives/nccl_2251/user-guide/docs/troubleshooting.html)也将 NCCL 诊断消息作为应用库自身证据。

**必要修改**：端口计数引线仍落到 NIC/VF 端口；在 Pod 内明确一处“应用日志”文件视图，使应用 transport 引线只指向该处。保留主机 MR 已校验、GPU MR 待验证、同一 VF0/时间窗和 eth0 策略范围。绿色虚线另明确为接口/网络关联，不与琥珀色已测数据路径混用。无需改写结论或重画全部对象。

三张图的独立可复制修改提示词见[本轮修改提示词](_配图/本轮修改提示词.md)。新候选使用 v02，保留 v01；收到后只复核本次改动及受影响关系。
