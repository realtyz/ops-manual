# 用分层证据判断网络交付到了哪里

## 先闭合一次成功的设备身份

沿用场景 V，两台 worker 各请求一张 GPU 和一个 VF，GPU/NIC 功能条件均按第 05 篇准备。下面是**自拟的三组教学输出**；节点侧客户端输出是整理摘要，不要求读者部署客户端。

第一组，kubelet 设备分配查询与宿主机映射：

```text
node=net-a pod=lesson-net/worker-a container=worker
  nvidia.com/gpu -> G0（已按 UUID 对应回本章节点内代号）
  example.com/roce_vf -> 0000:41:00.2
sysfs: 0000:41:00.0/virtfn0 -> 0000:41:00.2
VF0: NUMA=0, RDMA=mlx5_2, port=1, uverbs=/dev/infiniband/uverbs2
```

第二组，读取 Pod 的 `k8s.v1.cni.cncf.io/network-status` 注解后得到的 JSON 删节；`cluster-cni` 是本例默认 CNI 配置名：

```json
[
  {"name":"cluster-cni","interface":"eth0","ips":["10.244.1.20"],"default":true},
  {"name":"lesson-net/roce-vf","interface":"net1","ips":["192.0.2.101"]}
]
```

第三组，在 `worker-a/worker` 内观察：

```text
$ rdma link show
link mlx5_2/1 state ACTIVE physical_state LINK_UP netdev net1
$ ip route get 192.0.2.102
192.0.2.102 dev net1 src 192.0.2.101
$ test -r /dev/infiniband/uverbs2 && echo uverbs-readable
uverbs-readable
```

这些输出将资源池、具体 VF、RDMA 端口、netdev 和地址接在一起。`test -r` 只检查文件的读访问判断，不执行 Verbs 打开、MR 注册或传输。`ACTIVE` 表示本地端口状态，不能代替对端和 fabric 检查。场景 S 的对应对象会变成 PF HCA `mlx5_0` 和 macvlan 接入，不能把本组 `mlx5_2` 套过去。

## 每一层测试回答一个具体问题

下面是**自拟成功测试记录**，不是实测基准；两端为 `net-a/worker-a` 与 `net-b/worker-b`，只测单 VF 单端口，单向单流、每条消息 64 MiB（67,108,864 B）、稳定窗口 10 s。地址为 `.101/.102`，GPU 为两端 G0；RDMA 路径 MTU 本轮给定为 4096，端到端允许对应报文：

| 层次与输入 | 给定观察结果 | 本次能证明的范围 |
| --- | --- | --- |
| 默认网络 DNS 与会合 | 名称解析、控制 TCP 连接成功 | 当前协调路径成立 |
| net1 IP 连通 | 指定源接口的小报文与预期大小报文通过 | 当前 IP 路径及所测长度可通，不证明 RDMA |
| 主机内存 RDMA | 工具打开 `mlx5_2/1`，主机缓冲区 MR 注册成功，完成与数据校验通过；9.2 GB/s | 本 VF 的主机内存 RDMA 路径在此条件可用 |
| GPU 内存 RDMA | 两端 cudaMalloc 缓冲区；已确认 peer-memory 注册而非主机暂存；同步后读回校验通过；8.8 GB/s | 本 GPU/VF 对的 GPUDirect RDMA 路径在此条件可用 |
| NCCL 作业 | 记录正确 Rank/GPU/HCA 映射、`NET/IB` 和 GDR 路径证据，集合通信结果验证通过 | 本次成员与消息条件下的集合通信可用 |

真实测试可以使用支持相应缓冲区注册方式的 perftest、CUDA/RDMA 测试或通信库探针，但必须记录工具版本、构建能力、启动参数和校验方式；不是所有 `ib_write_bw` 二进制都支持相同 CUDA/DMA-BUF 选项。本表通过给定输入和结果让读者判断覆盖，无需自行运行命令补齐材料。

主机内存测试通过、GPU 内存注册失败时，优先检查 GPU/NIC 配对、注册支持、GPU 驱动与 peer-memory、容器内 CUDA/provider、权限与限制；先前通过的结果缩小了范围。GPU 路径吞吐低于主机路径也不自动否定 GDR：路径成立与吞吐高低是两个问题，性能还取决于设备与访问条件。

## 三类故障材料，分别落回责任环节

### 案例一：调度时就没有可分配的 VF

**独立教学快照**：`net-a` 有 GPU 余额 1，`example.com/roce_vf` Allocatable=2，已请求=2；另一节点 net-b 未上报此资源；其他调度条件均满足。Pod 请求 GPU=1、VF=1。自拟事件删节为：

```text
Warning FailedScheduling  0/2 nodes are available:
  2 Insufficient example.com/roce_vf
```

这是调度前的数量约束：`2-2=0`，没有 VF 余额。NAD 即使正确、地址池即使充足，尚未进入 CNI ADD。核对其他节点的完整筛选原因后，应选择释放/增加适用 VF 容量或调整请求；重写 net1 路由解决不了当前阻塞。

### 案例二：资源已分配，RDMA CNI 拒绝模式

**独立教学快照**：Pod 已绑定，VF0 已分配，NAD 包含 `sriov` 后接 `rdma`。sandbox 创建失败，整理日志为：

```text
FailedCreatePodSandBox: delegate roce-vf ADD failed
rdma: subsystem namespace mode=shared, expected=exclusive
host rdma system show: netns shared
```

这不是 VF 数量不足，也不是“给 Pod 再挂一次 `/dev/infiniband`”就能修复。方案要求 exclusive，实际节点仍是 shared。应回到节点初始化和模式管理，完成受控修正及残留网络清理后重新验证。第 03 篇已解释切换限制；此处不在活跃业务节点上直接执行模式切换。整理日志不是项目保证的完整错误字符串，检查逻辑对应 [RDMA CNI v1.3.0 ensureRdmaSystemMode](https://github.com/k8snetworkplumbingwg/rdma-cni/blob/v1.3.0/cmd/rdma/main.go)。

### 案例三：net1 和 RDMA 都可用，NCCL 仍用 Socket

**独立教学快照**：默认 DNS、net1 路由、VF 主机内存 RDMA 已通过；本轮配置明确设置 `NCCL_IB_DISABLE=1`，NCCL 日志显示 `NET/Socket`，没有使用 IB/RoCE transport。现在已给出直接原因：通信库被显式禁用了该 transport，不能据此判定 Multus 或 VF 接入失败。

在受控复测中去掉此限制，还应观察实际 HCA、端口、GPU 注册和结果，不能把“恢复自动选择”当作测试已通过。若使用 `NCCL_SOCKET_IFNAME`，选择的是 Socket/IP 接口；`NCCL_IB_HCA` 选择 IB/RoCE 的 HCA/端口，两者属于不同视角。例如本轮可比较 Socket 接口 `=eth0` 与 HCA `=mlx5_2:1` 的语义，但不将它们作为所有集群必填配置。选项依据 [NCCL 2.25.1 Environment Variables](https://docs.nvidia.com/deeplearning/nccl/archives/nccl_2251/user-guide/docs/env.html)，本章案例按该版本解释。

## 默认网络的策略与监控不自动覆盖附加路径

NetworkPolicy 由网络实现执行；仅有 Kubernetes 对象不产生过滤规则。[Kubernetes NetworkPolicy 文档](https://kubernetes.io/docs/concepts/services-networking/network-policies/)说明了这一执行前提。Multus 是接入组织者，没有替所有附加 CNI 实现统一的策略数据面。

若主 CNI 在 eth0 的 veth/overlay 上执行策略，macvlan、直接 VF 或 RDMA 数据可能不经过该执行点。必须单独确认附加网络的策略实现与覆盖范围，必要时结合 VLAN/VRF、交换机 ACL、VF 的 MAC/VLAN/anti-spoof 等硬件策略、受控的网络选择与设备访问权限。本章场景为无标签二层域，不因存在不同 NAD 或不同 IP 就推导出安全隔离。

平台需要限制谁能创建/修改 NAD、谁能在 Pod 中选择某网络、谁能请求相应资源，并核对多容器 Pod 共享网络的影响。`namespaceIsolation` 限制 NAD 引用范围，不等于阻断数据通信；ResourceQuota 限定数量，也不提供流量隔离。具体多租户威胁模型与生产治理在第 19 章展开。

观测也应分开：CNI/Multus 日志和 network-status 反映接入；Pod 的接口、地址和路由反映当前 namespace；NIC/VF/RDMA 端口与交换机计数器反映实际路径；应用日志反映 Rank 和 transport。默认网络的字节计数或普通 `tcpdump -i net1` 未见负载，不能直接推出 NIC 没有 RDMA 流量：硬件路径和卸载未必经过这个抓包点。应按节点、PCI/function、RDMA 端口、Pod、Rank 与时间窗口关联，不能把同一 PF 的总计数都算给某一个 VF。

交付记录至少保存网络方案、节点设备映射、组件/驱动版本、资源请求、NAD、地址池与策略范围，以及分层测试输入和结果。这样下一次故障才能区分“从未覆盖”与“曾经通过后退化”。
