# 第 13 章 Multus 与 RDMA：把高速网络交给 Pod｜内容大纲

## 读者起点与学习目标

从一对能通过默认网络完成作业协调的 Pod 入手，为其中的跨节点数据交换交付一条附加路径。读者已具备 Linux 和 Kubernetes 基础，可以读 Pod、Node 和资源请求。正文在首次使用处用最小篇幅回顾网络命名空间、路由及必要的硬件概念。第 06、07 章解释 RDMA、RoCE 和交换网络，第 08 章解释通信库选路，第 10—12 章建立设备访问、分配与 Operator 协调。本章把这些机制合到一次 Pod 接入中。

1. 给定对端地址、路由和应用选择，推断流量使用的网络和传输方式。能从路由、设备和实测结果解释结论成立的条件。
2. 给定 Pod、NAD、节点库存和分配记录，追踪一次 VF 从创建、发布、分配到接入的过程。能复算单节点 VF 与 IP 余量，定位接入中断的位置。
3. 按设备交付粒度、命名空间和共用容量比较共享 HCA、独占 VF 与整接口交付。能用拓扑提示判断节点内准入，再追到实际 GPU/NIC 设备对。
4. 根据两侧 Operator、接入状态和双端测试证据，区分组件就绪、主机内存 RDMA、显存注册与策略执行。能为当前结论选出下一项检查。

## 主例与技术口径

- 沿用第 12 章的 `gpu-h0`、`gpu-h1` 和两张 H100 PCIe 整卡。为本章新增的教学拓扑中，每台有两个 NUMA 节点，每侧各一张 GPU 和一张 ConnectX-7 NIC，另有一个普通网口承载默认网络。每节点的 `ens2f0`、`ens3f0` 各对应本例的一个 PF，各启用四个 VF。高速端口在交换侧均使用同一以太网 VLAN 的无标签接入。本章主线假定网卡、固件、驱动和 RoCEv2 fabric 已具备相应能力。
- `default/rank-0` 位于 `gpu-h0`，`default/rank-1` 位于 `gpu-h1`，各用一张整卡与一个 VF。默认接口 `eth0` 的地址依次为 `10.244.0.10`、`10.244.1.10`，附加接口 `net1` 为 `192.168.50.11/24`、`192.168.50.21/24`。默认路由和 DNS 使用 `eth0`，数据试验显式使用 `net1` 对应的 RDMA 设备。设备名和 BDF 只在本节点有意义。共享、隔离、地址耗尽和局部拓扑用独立快照说明改变的条件。
- 接口与配置以 Kubernetes v1.36、Network Operator v26.7.1 和第 12 章的 GPU Operator v26.7.2 为阅读口径，沿用 Ubuntu 24.04 LTS x86_64、containerd 2.3 作为教学平台。上游 CNI 源码用于解释机制，厂商镜像按 Network Operator 发行矩阵辨认。正文中的地址、状态、分配、命令参数和配置均标明材料性质。 [Network Operator v26.7.1 平台与组件矩阵](https://docs.nvidia.com/networking/display/kubernetes2671/platform-support.html) · [GPU Operator v26.7 平台矩阵](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/26.7/platform-support.html)
- 第 14 章继续分析 GPU 共享粒度和隔离，第 15 章把本章的节点内准入与集群侧多 Pod 放置结合。交换网络设计、通信算法、长期基线和生产变更分别由第 07、08、17—19 章展开。
