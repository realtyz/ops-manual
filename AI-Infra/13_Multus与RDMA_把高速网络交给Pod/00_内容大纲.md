# 13 Multus 与 RDMA：把高速网络交给 Pod

## 范围、前置知识与读者目标

- **范围**　以两个分别落在不同 GPU 节点上的 Pod 为主例，沿着资源申报、VF 分配、附加网络接入、地址可达、RDMA 传输和 GPU 显存注册展开。完整走一遍以太网 RoCE 下的 SR-IOV VF 路径，用 Macvlan + RDMA Shared Device Plugin 对照资源配额和隔离，并用 Host Device 和 InfiniBand 说明更换接入方式时需要替换什么。
- **必要前置**　能读 Pod、Node、资源请求和注解，知道 kubelet、容器运行时、Linux 网络命名空间以及 IP 路由的作用。开篇补足默认 CNI 与附加接口的关系，第一次用到时解释 PCI BDF、PF/VF、HCA、RDMA 设备与端口。设备计数和分配沿用第 11 章的机制，Operator 协调沿用第 12 章的机制。只需理解主机内存和 GPU 显存是不同缓冲区，就能跟完两种 RDMA 验证。
- **读完应能独立解释**　给定 Pod、NAD 和 Node 配置，能指出哪个组件创建 VF、哪个组件分配具体设备、Multus 怎样找到相应设备、谁把地址交给容器。给定平台的独占和共享要求，能选出组件组合，并解释一个 VF 或一个共享资源单位各自代表什么。
- **读完应能独立判断**　给定设备 ID、NUMA 拓扑和路由，能判断资源计数是否足够、哪种 kubelet 策略可能拒绝 Pod、应用点选的设备和地址是否属于同一附加网络。给定事件、接口、RDMA 测试和策略记录，能判断走到了哪一层，说明哪一项证据还需要采集。
- **跨章分工**　第 06、07、08 章负责 Verbs 和 GPUDirect 原理、IB/RoCE 网络设计和 NCCL 选路细节。本章使用这些机制定位 Kubernetes 接入点。多 Pod 放置、机架亲和和组调度交给第 15、16 章。持续监控、完整故障处置与生产变更交给第 17–19 章。

## 贯穿案例与版本口径

- **教学场景**　沿用第 12 章的 `gpu-h0`、`gpu-h1`。每台双 NUMA 节点有两张 H100 PCIe 和两张 ConnectX-7 NIC，每张 NIC 启用一个以太网端口。教学拓扑设为每个 NUMA 节点各一张 GPU 和一张高速 NIC。节点另有用于 Kubernetes 默认网络的普通网口。主例在每节点的两个 PF 上各启用 4 个 VF，共 8 个，两个高速端口均接入同一个 RoCE VLAN。两个测试 Pod 各用一张整卡和一张 VF，以普通 RDMA 验证数据面。默认接口 `eth0` 保留默认路由和集群 DNS，附加接口 `net1` 使用 `192.168.50.0/24` 教学地址段。假定两端 fabric 已配置且无额外地址占用。MTU 和默认路由变体每次仅改一项。
- **主例拟定版本**　Kubernetes v1.36、Ubuntu 24.04 LTS x86_64、containerd 2.3、GPU Operator v26.7.2 与 Network Operator v26.7.1。总纲援引的 Network Operator v26.4.0 平台矩阵为 Kubernetes 1.31–1.35，v26.7.1 平台矩阵为 1.32–1.36。采用 v26.7.1 可延续上一章的 Kubernetes 小版本。两侧矩阵对 NFD 和 GPUDirect 组合仍有需要核实的差异，见文末。配置以 v26.7.1 发行文档和其组件镜像为准，上游源码用于说明接口语义。 [Network Operator v26.4.0 平台矩阵](https://docs.nvidia.com/networking/display/kubernetes2640/platform-support.html) · [Network Operator v26.7.1 平台与组件矩阵](https://docs.nvidia.com/networking/display/kubernetes2671/platform-support.html) · [GPU Operator v26.7 平台与运行时矩阵](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/26.7/platform-support.html)
- **材料用法**　主例的配置做最小字段摘录，逐项对应生成对象、节点资源和 Pod 内观测。教学数值标为假设，官方示例输出注明出处。只有取得可追溯记录才引用实测或现场日志，并注明采集时间、命令、两端节点、硬件/固件、OS/内核、运行时、驱动、Operator 和测试镜像或工具版本。缺少实机材料时，用字段表、官方输出和可复算的假设快照完成正文。

## 01 同一个 Pod 为什么需要两张网卡

- **问题与预期结论**　集群 DNS 和成员发现已经成功，为什么两台机器之间的训练数据还可能走默认网络？读者应能按目的地址、应用选择与实际设备区分两条路径，解释添加网卡后哪些流量会改变。
- **解释顺序**　先用「SR-IOV 基础」小节解释网卡怎样提供可独立分配的 PCI 功能，区分 PF、VF、物理端口和 Pod 接口，并用两个 PF 各启用 4 个 VF 的例子核对设备数量和归属。再画两个 Pod 的 `eth0`/`net1` 分别到普通网络和 RoCE fabric 的路径。以 DNS 查询、Rendezvous 控制连接、跨节点数据交换为例，分别指出目的地址由谁提供，内核按什么选出接口，应用在什么条件下选用 RDMA 设备和端口。用两个例子检验判断，一是应用只用默认 Pod IP 建立连接，二是已给出附加 IP 但进程采用 Socket 数据传输。集群 DNS 和协调流量保留在默认网络是本案例的部署约定，实际应用可配置自己的协调路径。NCCL 的具体变量和选路算法交给第 08 章。
- **支撑材料**　用 Linux 内核文档核对 PCI 功能的枚举方式，并给出 `sriov_totalvfs`、`sriov_numvfs`、`virtfn0` 和 `physfn` 的只读查询。从双节点示意图读出 Pod、宿主机和 fabric 的边界，控制流接 `eth0`，示例中的 RDMA 数据流接 `net1` 所关联的 RDMA 端口。图注说明流向由应用与路由共同决定。另用 `.status.podIP`、附加网络状态中的 `ips`、应用连接的对端地址对照，说明从哪里查到两组地址。 [Linux PCIe SR-IOV](https://docs.kernel.org/PCI/pci-iov-howto.html) · [Linux PCI sysfs](https://www.kernel.org/doc/Documentation/ABI/testing/sysfs-bus-pci) · [Kubernetes 网络模型](https://v1-36.docs.kubernetes.io/docs/concepts/services-networking/) · [Multus 多接口使用说明](https://github.com/k8snetworkplumbingwg/multus-cni/blob/master/docs/how-to-use.md)

## 02 Pod 中的网络注解怎样变成一张附加网卡

- **问题与预期结论**　Pod 引用了 `roce-vf`，集群里也有一个同名 NAD，为什么还可能没有 `net1`？读者应能沿着 Pod、NAD、Multus 和委派的 CNI 插件找到实际接入动作，分清配置意图与接入结果。
- **解释顺序**　从运行时建立 Pod sandbox 的网络命名空间、按节点配置调用 Multus 开始。Multus 将默认网络交给默认 delegate，再按 `k8s.v1.cni.cncf.io/networks` 解析附加网络，查找命名空间内的 NAD，将 `.spec.config` 交给对应插件。用 JSON 选择项显式请求接口名 `net1`，另举 `namespace/name` 的写法。解释 `ADD`、插件结果、`network-status` 回写与 Pod 删除时的 `DEL`。改错命名空间或插件二进制缺失时，分别追到查找和委派失败。CNI 版本、thin/thick 部署形式只在影响配置来源或日志位置时提及。
- **支撑材料**　并排摘 Pod 注解 `[{"name":"roce-vf","interface":"net1"}]`、`NetworkAttachmentDefinition` 的 `apiVersion`、`metadata.namespace`、`metadata.name`、`.spec.config`，以及 `k8s.v1.cni.cncf.io/network-status` 的 `name`、`interface`、`ips`、`default`。用 Mermaid 时序图标出 CRI、Multus、默认 CNI、NAD 和附加 CNI。上游 Multus 源码中的 `NoNetworkFound` 与 kubelet 通用的 `FailedCreatePodSandBox` 作为字段示例，正文按实际部署核对事件报告方和消息。 [Multus 配置参考](https://github.com/k8snetworkplumbingwg/multus-cni/blob/master/docs/configuration.md) · [Multus NAD 查找源码](https://github.com/k8snetworkplumbingwg/multus-cni/blob/master/pkg/k8sclient/k8sclient.go) · [CNI 规范](https://www.cni.dev/docs/spec/)

## 03 一张 SR-IOV VF 如何从 PF 进入 Pod

- **问题与预期结论**　节点上能看到 VF，为什么 Pod 会因资源不足而 Pending，或者已经绑定节点却在网络初始化时失败？读者应能凭资源名与 PCI BDF 定位是 VF 创建、资源发现、调度、节点内分配，还是 CNI 接入出了问题。
- **解释顺序**　先用 PF、VF 和 PCI BDF 解释一个端口如何产生多个可单独分配的 PCI 功能。由节点配置创建 VF，SR-IOV Device Plugin 用选择条件发现 VF，kubelet 上报扩展资源。调度器按资源数量筛选节点，kubelet 在目标节点分配具体 VF。Multus 通过 NAD 的 `k8s.v1.cni.cncf.io/resourceName` 在节点上的资源映射中找出已分配的 `deviceID`，交给 SR-IOV CNI。以 kernel `netdevice` 为例，追踪 VF 进入 Pod 网络命名空间、IPAM 给出地址与路由、CNI 将结果应用到接口、删除时释放地址与还原 VF。对照三种失败条件，分别是空闲 VF 不足、NAD 的完整资源名与已分配资源不匹配、VF 已分配但 IPAM 无地址。主例显式写 Pod 扩展资源请求，自动注入只用于解释线上配置为何有差别。
- **支撑材料**　跟踪 `SriovNetworkNodePolicy.spec.numVfs: 4`、同时选中两个 PF 的 `nicSelector.pfNames`、`deviceType: netdevice`、`isRdma: true` 和 `resourceName: sriov_resource`，接 `SriovNetwork/roce-vf` 的 `spec.resourceName`、`spec.networkNamespace`、`spec.ipam`，再对照生成的 NAD 和 Pod 请求 `nvidia.com/sriov_resource: 1`。抽取 Node `.status.allocatable`、已绑定 Pod 的资源请求、kubelet PodResources API 的 `resource_name`/`device_ids`，把一个 VF BDF 连到 CNI 的 `deviceID`。用各 PF 内的 VF 索引对照三种分组，一个池覆盖两个 PF、两个池各覆盖两个 PF、两个池分别限定一个 PF，说明何时能明确从两个 PF 各分配一个 VF。教学算例假定每节点 8 个 VF 都健康且发布在同名资源池，每节点已有一个 Pod 请求 1 个，各剩 7 个调度单位。再提交请求 8 个 VF 的单 Pod 时，两节点共剩 14 个也无法满足该请求。地址池与物理带宽另有约束。 [NVIDIA SR-IOV RDMA 快速示例](https://docs.nvidia.com/networking/display/kubernetes2671/quick-start/sriov-network-rdma.html) · [SR-IOV 策略与 VF 分组](https://github.com/k8snetworkplumbingwg/sriov-network-operator/blob/master/doc/api/node-policies-api.md#multiple-policies-and-priority) · [SR-IOV Device Plugin](https://github.com/k8snetworkplumbingwg/sriov-network-device-plugin) · [SR-IOV CNI](https://github.com/k8snetworkplumbingwg/sriov-cni) · [Kubernetes v1.36 Device Plugin 与 PodResources](https://v1-36.docs.kubernetes.io/docs/concepts/extend-kubernetes/compute-storage-net/device-plugins/)

## 04 共享 HCA、独占 VF 与 RDMA 命名空间怎样组合

- **问题与预期结论**　给 Pod 配了 `rdma/...: 1` 或单独一张 VF，可以分别承诺什么？读者应能比较每种方案交付的资源、Pod 能看到哪些设备、哪些容量仍共用，以及有没有独立的流量策略执行点。
- **解释顺序**　先以 `macvlan` 的 `master` 说明虚拟接口怎样建立，再接 RDMA Shared Device Plugin 的设备选择和逻辑容量。两个 Pod 可各有地址和接口，同时访问同一个 HCA。然后回到 VF，分清 `isRdma` 对 RDMA 资源交付的作用、VF netdev 的移动、HCA 的命名空间可见性。Linux 的 `shared` 模式允许 RDMA 设备跨网络命名空间可见，应用实际访问还取决于设备节点和权限。独立对照场景使用 `exclusive`，由链式 RDMA CNI 在 SR-IOV CNI 之后将对应 RDMA 设备置入目标网络命名空间，切换前检查节点现有命名空间和 RDMA 活动。主例沿官方快速示例理解 VF 接入，`exclusive` 使用独立配置演示，Macvlan 共享路径用另一组案例快照。末尾比较 Host Device 直接交出一张主机接口，以及 IB 版的 SR-IOV CNI/IPoIB 选择、fabric 地址与分区条件，点到第 07 章为止。
- **支撑材料**　用对照表列出三行（Macvlan + Shared Plugin、SR-IOV VF、Host Device）和五列（申请单位、Pod 接口、RDMA 可见性、共同硬件资源、典型取舍）。共享场景摘 `selectors.ifNames`、`rdmaHcaMax: 63`、`rdma/rdma_shared_device_a: 1` 与 `MacvlanNetwork.spec.master`，假定一张 HCA 可申报 63 个逻辑单位，链路仍只有一个。隔离场景摘 `SriovNetworkPoolConfig.spec.rdmaMode: exclusive` 与 `SriovNetwork.spec.metaPlugins` 中的 `type: rdma`，核对生成 NAD 的 `plugins` 顺序。在主机和对应 Pod 分别观察 `rdma system show`（模式）和 `rdma link show`（设备/端口可见性），再结合 `/dev/infiniband` 区分可见性与打开设备的条件。 [NVIDIA Macvlan 共享示例](https://docs.nvidia.com/networking/display/kubernetes2671/quick-start/macvlan-rdma-shared.html) · [NVIDIA v26.7.1 独占模式、Host Device 与 IB 部署示例](https://docs.nvidia.com/networking/display/kubernetes2671/deployment-guide-kubernetes.html) · [RDMA CNI 上游文档](https://github.com/k8snetworkplumbingwg/rdma-cni) · [iproute2 的 RDMA 命名空间模式](https://github.com/iproute2/iproute2/blob/main/man/man8/rdma-system.8)

## 05 两个 Operator 怎样交付 GPUDirect RDMA 的依赖

- **问题与预期结论**　为什么 Node 上有 GPU 和 RDMA 资源，普通 RDMA 测试也通过了，进程却可能注册不了 GPU 显存？读者应能在主机驱动、Pod 设备与用户态库、应用注册方式之间划定问题范围，并说出每项依赖由谁交付。
- **解释顺序**　先把两侧管理范围放到一张图中。GPU Operator 负责 GPU 侧驱动、Toolkit 和设备交付。Network Operator 可管理 NIC 驱动、Multus、NV-IPAM 等组件，通过启用的 SR-IOV Network Operator 交付 VF 配置、设备插件和网络对象。既有主机驱动和已有 CNI 时，以实际启用的组件与生效配置判断责任。全局组件用 `NicClusterPolicy`，按节点组管理 DOCA-OFED 和两类设备插件时使用 `NicNodePolicy`。两个 Operator 共用一套兼容的 NFD。再由 CPU 内存 RDMA 过渡到 GPU 显存注册，分主机和 Pod 列出所需驱动、拓扑、设备、CUDA/Verbs 用户态与支持该注册方式的应用。依据 GPU Operator v26.7 文档，DMA-BUF 路径要求 Linux ≥ 5.12、开放 GPU 内核模块和工作负载内 CUDA ≥ 11.7，符合条件时可用发行版 NIC 驱动和 RDMA 用户态包。旧的 `nvidia-peermem` 路径需要 MLNX_OFED 或 DOCA-OFED；另核对该 GPU/NIC、内核、驱动和 Operator 组合的厂商支持口径。驱动维护、卸载和升级交给第 19 章。
- **支撑材料**　拟用责任表把 `NicClusterPolicy.spec.secondaryNetwork.multus`、`nvIpam`、`NicNodePolicy.spec.ofedDriver`、SR-IOV 子 Operator 的 Helm 开关与实际 DaemonSet 布置对应起来，用 `status.conditions[]` 的 `type/status/reason/observedGeneration` 和节点本地核验区分协调状态与当前驱动状态。测试材料首选官方双节点 perftest 方法。普通主机缓冲区试验先确认 RDMA 连通，再在明确的两端 RDMA 设备和端口上比较 GPU 缓冲区试验，DMA-BUF 用 `--use_cuda` 和 `--use_cuda_dmabuf`，legacy 对照保留 `--use_cuda`。记录两端使用的缓冲区、参数和注册结果。官方 GPU 测试原例采用 Macvlan + Shared Plugin，正文单独注明；同一 VF 案例的 GPU 测试仅在版本和环境证据齐备时作为实测呈现。 [Network Operator v26.7.1 部署指南](https://docs.nvidia.com/networking/display/kubernetes2671/deployment-guide-kubernetes.html) · [NicClusterPolicy 与 NicNodePolicy 分工](https://docs.nvidia.com/networking/display/kubernetes2671/customizations/nic-node-policy.html) · [Operator 状态字段](https://docs.nvidia.com/networking/display/kubernetes2671/life-cycle-management.html) · [GPU Operator v26.7 的 GDR 前置条件与测试](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/26.7/gpu-operator-rdma.html) · [perftest 上游参数说明](https://github.com/linux-rdma/perftest)

## 06 同一个 Pod 拿到的 GPU 和 NIC 会在同一个 NUMA 节点吗

- **问题与预期结论**　节点上同时有空闲 GPU 和 VF，为什么 Pod 能绑定却可能被 kubelet 拒绝，或能启动但选到跨 Socket 的设备对？读者应能区分节点级数量筛选、kubelet 的 NUMA 对齐条件及实际 PCIe 连接。
- **解释顺序**　先放两张资源池的节点汇总，再把可选 GPU、VF 和 CPU 拆到两个 NUMA 节点。用一只单容器 Pod 同时申请 `nvidia.com/gpu` 和 VF，讲设备插件的 `TopologyInfo`、Device Manager/CPU Manager 的 hints，以及 Topology Manager 在节点内合并提示的时点。对照 `none`、`best-effort` 与 `single-numa-node`。如果插件缺少拓扑提示，或申请分散在多个容器且使用 `container` scope，对齐范围随之改变。需要独占 CPU 时补充 CPU Manager `static` 下 Guaranteed Pod 和整数 CPU 请求的条件。之后看同 NUMA 内两个不同的 PCIe 路径，说明仍需查 PCIe Root Complex 与实际 GPU/NIC 配对。调度器的跨节点拓扑和组放置留给第 15 章。
- **支撑材料**　教学变体给出 NUMA 0 有 0 张可用 GPU、1 个可用 VF，NUMA 1 有 1 张可用 GPU、0 个可用 VF。一个 Pod 请求两项各 1，节点汇总通过；若两项均有准确的单 NUMA 提示且没有共同候选，`single-numa-node` 拒绝，`best-effort` 可接纳。用 PodResources 的设备 ID 和 `topology.nodes[].ID`、GPU UUID 与 PCI BDF 对照、VF 的 `physfn`、PCI sysfs `numa_node` 和 `nvidia-smi topo -m` 核对实际落点。拟用一张双 Socket 教学拓扑图配余量表。图上明确 VF 属于哪个 PF，保持 NUMA 与 PCIe 边界可辨。 [Kubernetes v1.36 Topology Manager](https://v1-36.docs.kubernetes.io/docs/tasks/administer-cluster/topology-manager/) · [Kubernetes Device Plugin 的拓扑字段](https://v1-36.docs.kubernetes.io/docs/concepts/extend-kubernetes/compute-storage-net/device-plugins/) · [SR-IOV Device Plugin 的 `excludeTopology`](https://github.com/k8snetworkplumbingwg/sriov-network-device-plugin) · [NVIDIA GDR 拓扑要求](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/26.7/gpu-operator-rdma.html)

## 07 附加网络的地址、路由和 MTU 怎样验收

- **问题与预期结论**　Pod 已出现 `net1` 和一个 IP，为什么仍可能用错源地址、无法跨节点通信，或小包可达而大包失败？读者应能从地址池、实际路由和两端链路约束预测结果，并选出下一项检查。
- **解释顺序**　先用 `nv-ipam` 的 `poolName` 追到 `IPPool`，解释同一二层子网上控制器按节点分配地址块、节点侧再为 Pod 分配地址。对照 Whereabouts 的跨节点地址分配和 `host-local` 的节点本地状态；多个节点在同一二层使用同一 `host-local` 地址范围时，需要另外保证各节点范围互斥。再按目的地址和源地址解释 `ip route get`。主例用附加子网直连路由保留 `eth0` 默认出口；跨子网需要对应路由与回程。加入 Multus 注解的 `default-route` 变体，观察原来通过默认网访问的目标如何变化，结合接口绑定或 RDMA 设备/端口选择验证应用使用的路径。最后区分 VF/PF netdev MTU、交换路径 MTU 与 RDMA 端口/QP 的 MTU 证据，链路上的最小可用值约束大小，但 IP 探测通过仍需复核 RDMA。
- **支撑材料**　计划摘 `IPPool.spec.subnet`、`perNodeBlockSize` 和每节点分配状态。用一个独立快照说明地址耗尽的条件：节点有 8 个 VF，一个分配块中只有 4 个可用 IP，4 个只申请 VF 的测试 Pod 各使用一个 IP 和 VF，第 5 个 Pod 可以拿到 VF，但无法拿到地址。路由快照取 `net1` 为 `192.168.50.11/24`，对端为 `.21`，以 `ip -br addr`、`ip -4 route get 192.168.50.21`、`ip -4 route get <需经默认路由的地址>` 对照接口和源地址。MTU 算例假定 IPv4 无选项、ICMP Echo、路径 IP MTU 1500 B，载荷上限为 `1500 − 20 − 8 = 1472 B`。用 `ip -d link`、不分片 IP 探测和 `ibv_devinfo` 的 `active_mtu` 说明三类观测分别约束什么。VLAN 配置、RoCE 拥塞和 IB fabric 管理交给第 07 章。 [NV-IPAM 的地址块、路由与状态定义](https://github.com/Mellanox/nvidia-k8s-ipam) · [Whereabouts 地址分配](https://github.com/k8snetworkplumbingwg/whereabouts) · [CNI host-local](https://www.cni.dev/plugins/current/ipam/host-local/) · [Multus 默认路由配置](https://github.com/k8snetworkplumbingwg/multus-cni/blob/master/docs/how-to-use.md#specifying-a-default-route-for-a-specific-attachment) · [IPv4 首部](https://www.rfc-editor.org/rfc/rfc791.html) · [ICMP Echo 格式](https://www.rfc-editor.org/rfc/rfc792.html)

## 08 怎样用证据判断故障层次和策略覆盖范围

- **问题与预期结论**　默认网络可达、Pod 为 `Running`，附加网络上的通信仍然异常，从哪一层查起？读者应能判断每条证据支持到哪一层，并确认安全策略究竟在哪个数据路径执行。
- **解释顺序**　用一对跨节点 Pod 按顺序取证：调度与 kubelet 准入，sandbox 的 CNI/地址交付，netdev 与 RDMA 设备的映射，目标地址与端口选择，主机内存 RDMA，再到 GPU 显存注册。对比三个单变量场景：资源不足引起 `FailedScheduling`；资源已分配但 NAD 或地址池错误导致 `FailedCreatePodSandBox`；`net1` 有地址且 IP 探测成功，但 Verbs 试验失败或 GPU 内存注册失败。每个场景写清相同现象可能对应的原因、下一项取证和如何用双端测试缩小范围。安全部分分别检查 NAD 引用权限与 Multus 命名空间约束、默认网络的 NetworkPolicy 执行插件、附加网的策略实施和硬件数据路径。若选用带 VF representor 的 switchdev 示例，说明 `MultiNetworkPolicy` 须有相应控制器，以及如何从执行点与允许/拒绝测试确认覆盖。具体生产租户策略和故障恢复交给第 18、19 章。
- **支撑材料**　拟做一张从症状到证据的表。用同一 Pod UID、节点名、时间、附加网络名和 VF BDF 对齐 Pod 的 `PodScheduled`/事件 `reason` 与消息、Multus 记录的 NAD/委派插件/`deviceID`、`network-status` 与 Pod 内的 `ip`、`rdma link`、`ibv_devinfo`。用固定两端、设备、端口、消息大小与测试方向的 perftest 结果验证指定路径的 RDMA 传输；端口计数只选已查明驱动语义的项目，注明计数归属和采样区间。安全验收用同一对 Pod 在两个网络分别向目标地址发起允许/拒绝测试，记录实际接口和策略执行点，单独核对 RDMA 流量是否在该实现的覆盖范围内。 [NVIDIA SR-IOV RDMA 双端验证流程](https://docs.nvidia.com/networking/display/kubernetes2671/quick-start/sriov-network-rdma.html) · [Multus 日志和 NAD 命名空间配置](https://github.com/k8snetworkplumbingwg/multus-cni/blob/master/docs/configuration.md) · [Kubernetes NetworkPolicy 对实施插件的要求](https://v1-36.docs.kubernetes.io/docs/concepts/services-networking/network-policies/) · [MultiNetworkPolicy 的 TC 实现与 VF representor 条件](https://github.com/k8snetworkplumbingwg/multi-networkpolicy-tc)

## 提请审查的取舍

1. **版本连续性**　建议采用 Network Operator v26.7.1，承接第 12 章的 Kubernetes v1.36，同时在版本口径交代总纲原引用。若希望正文严格沿用 v26.4.0，则把本章设为独立的 Kubernetes v1.35 案例，并核对 GPU Operator、NFD 和相关字段的配套版本。
