# 第 13 章 Multus 与 RDMA：把高速网络交给 Pod｜内容大纲

## 本章定位与前置知识

阅读本章需具备 Linux 网络命名空间、IP 路由与 Kubernetes 基础，并默认已掌握前文三块能力：[第 06—07 章](../06_从普通网络通信走向RDMA/00_内容大纲.md)建立的 RDMA、RoCEv2 与集群计算网模型，[第 08 章](../08_NCCL如何组织GPU间的通信/00_内容大纲.md)的通信库选路机制，以及[第 10—12 章](../12_GPUOperator如何管理节点软件/00_内容大纲.md)的容器设备注入、资源分配与 Operator 节点自动化管理。

本章是 **Multus、NAD、CNI、SR-IOV 与 PF/VF** 的主定义章，核心回答一个关键工程问题：**如何既保留 Kubernetes 默认网络（`eth0`）的 DNS 与服务发现能力，又把 200 Gb/s / 400 Gb/s 高速 RDMA 硬件通道直通给训练与推理 Pod（`net1`）**。

学完本章后，[第 14 章](../14_GPU共享、切分与隔离/00_内容大纲.md)将展开 GPU 共享与切分策略，[第 15 章](../15_从单个Pod放置到多卡作业调度/00_内容大纲.md)将节点内拓扑约束接入多节点集群调度。

## 核心学习目标

1. **判读双网络流量去向**：给定对端地址、Pod 路由与应用传输协议，能准确推断流量走默认网 `eth0` 还是高速附加网 `net1`，并区分走高速以太网的 TCP 与真正的硬件 RDMA。
2. **追踪 SR-IOV VF 端到端交付**：能沿 `SriovNetworkNodePolicy`、Device Plugin、kubelet 分配、Multus 委派、SR-IOV CNI 与 NV-IPAM 追到同一个 VF BDF，独立复算单节点 VF 与 IP 容量余量。
3. **权衡接入模式与节点内拓扑**：能从隔离性、设备上限与运维复杂度对比共享 HCA、独占 VF（`shared` / `exclusive`）与整接口交付，并用 Topology Manager 推导 GPU 与 VF 的 NUMA 对齐及 PCIe 路径。
4. **验证 GPUDirect RDMA 与多租户策略边界**：能分工核对 GPU Operator 与 Network Operator 状态，设计主机内存与 GPU 显存两轮 RDMA 对比验证，并厘清 `NetworkPolicy`、Multus 命名空间隔离与 `MultiNetworkPolicy` 的生效范围。

## 本章贯穿场景

全章延续第 12 章的双节点集群 `gpu-h0` 与 `gpu-h1`。每台节点配备双路 CPU（对应两个 NUMA 节点），两侧各挂 1 张 H100 PCIe 与 1 张 ConnectX-7 高速网卡，另设 1 个普通网口承载默认网络；高速口 `ens2f0`（NUMA 0）与 `ens3f0`（NUMA 1）作为 PF，各开 4 个无标签 VF 接入同一 RoCE VLAN。

软件参考基线统一为 **Kubernetes `v1.36`**、**Multus `v4.2.4`**、**NVIDIA Network Operator `v26.7.1`**、**NVIDIA GPU Operator `v26.7.2`**、**containerd `2.3.0`** 与 **Ubuntu 24.04 LTS（x86_64）**。

代表性双端 Pod 为运行在 `gpu-h0` 上的 `default/rank-0`（`eth0: 10.244.0.10`，`net1: 192.168.50.11/24`）与 `gpu-h1` 上的 `default/rank-1`（`eth0: 10.244.1.10`，`net1: 192.168.50.21/24`）。
