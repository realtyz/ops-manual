## fig-13-01-01 同一 Pod 的两种接入与三种对象

### 教学目的与全文主线

- **类型**：核心总结图。
- **主问题**：为什么 Pod 增加了 net1，仍不能据此断言应用已经用上 RDMA？
- **核心结论**：Multus 组织创建多网络接入；接口、RDMA 对象、字符设备入口与应用选路要分别成立，net1 的 IP 不能替代其余条件。
- **教学目的**：读者能用一个 Pod 的整体剖面回忆默认网络与附加网络的分工，并区分创建时组织者、运行时接入对象和应用选择。

只用以下关键关系组织画面：

- 同一 Pod namespace 中的 eth0 与 net1 并存，各承担本章选定的协调与高速接入职责。
- net1、mlx5_2/1 与 uverbs2 是相关的三种对象，文件视图不能冒充网络接口。
- 创建时的 Multus/NAD 配置位于数据路径外，应用还需选择可用 HCA。

### 构图与视觉价值

主体采用一个 worker-a 的软件边界剖面，占画面左侧约六成；右侧上下为默认集群网络与 RoCE fabric 两个环境截面。Pod 网络命名空间画成清楚的灰色范围，内置一个应用容器；容器局部用翻开的文件页表现字符设备入口，另外用接口边缘接点表现 eth0/net1，用青色带端口编号的设备对象标片表现 mlx5_2/1。三种对象分开而相邻，用细灰无箭头引线标注关联。eth0 接到右上默认网络，附加 RDMA 接入对应右下 RoCE 环境；net1 与 RDMA 端口只作对应，不能成为串行包处理链。顶端留一小段翻折的配置页，标明创建时的 Multus/NAD；不把它接在运行时通信线上。视线依次看整体 Pod、三个不同形态的局部对象、两种网络环境。

**若改成普通方框箭头，会丢失什么？** 普通方框箭头会弱化同一 namespace 内的共存关系，也会把字符设备文件、netdev 和 RDMA 对象误画成相同节点或连续管线；本图用范围剖面、文件页、接口接点和端口标片保留这些差异。

**必要短标签**：`worker-a`、`同一 Pod 网络命名空间`、`应用容器`、`eth0 / 默认网络`、`net1 / 附加网络`、`mlx5_2/1`、`/dev/infiniband/uverbs2`、`DNS / 协调`、`RoCE fabric`、`创建时：Multus / NAD`、`应用另选 HCA`、`接口可见 ≠ 已使用 RDMA`。标签按视区就近放置，不排成一列目录；文字过密时先减少装饰与非必要细节，不压缩字号。

## fig-13-05-02 两侧软件维护，要在同一 Pod 的 GPU MR 上闭合

### 教学目的与全文主线

- **类型**：核心总结图。
- **主问题**：两个 Operator 都维护了各自组件，为什么还必须在所选 GPU/NIC 与 Pod 中验证 GPUDirect RDMA？
- **核心结论**：GPU 与网络软件各有管理责任，GDR 则要求它们在同一容器的设备访问和 GPU 内存注册处共同成立；组件 ready 不能代替具体路径的数据校验。
- **教学目的**：用主机/Pod 边界及 GPU MR 放大解释两侧责任怎样在实际负载中交会，同时保留软件管理与数据路径的区别。

只用以下关键关系组织画面：

- 同一个主机内核服务于 GPU 与 NIC 两侧驱动，每项组件只指定一个管理者。
- 同一工作负载容器同时具有 GPU/RDMA 访问及 CUDA/provider 等用户态条件。
- 只有所选 GPU 缓冲区的注册与实际访问成立，才能把 RDMA 传输结论推进到 GDR。
