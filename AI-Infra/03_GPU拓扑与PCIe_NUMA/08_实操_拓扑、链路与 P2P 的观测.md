# 拓扑、链路与 P2P 的观测

面对「这台机器比同类节点慢」的问题，可以读的读数有一二十个，但真正能缩小范围的顺序只有一条：**先用一份读数回答「路径长什么样」，再用第二份读数回答「这一段的实际值是多少」**。反过来做——先把所有拓扑与链路命令都跑一遍，把几十行输出一起看——得到的是一堆看起来都正常的数字，判断反而更慢。本篇按这个顺序组织：先给出问题与工具的对应表，再给出故障现场定位表，接着是对照实验的设计，然后是采样纪律与影响范围较大的操作，最后用四个场景把定位表给出的第一份读数之后的路径走完。以下命令除标注外都是只读观测，生产节点上也可以执行。

## 一个问题一把工具

| 要回答的问题 | 命令 | 读哪个字段 | 判据 |
| --- | --- | --- | --- |
| 两件设备隔了几跳 | `nvidia-smi topo -m` | 矩阵里两设备交汇的一格 | 代号写出路径结构；只有 `SYS` 跨 socket，`NODE` 仍在同一 NUMA 节点内 |
| 设备建议绑到哪些核、落在哪个内存域 | 同上 | `CPU Affinity`、`NUMA Affinity` 两列 | 两列一致才构成本地关系；显示 `N/A` 表示当前核集合与设备亲和无交集 |
| 这一对能不能直通 | `nvidia-smi topo -p2p r` 等 | 对应能力矩阵里的一格 | `OK` 表示可用；`CNS`、`TNS`、`GNS`、`NS` 分别指向芯片组、拓扑、设备与未细分 |
| 链路声明能跑多快 | `lspci -vv -s <BDF>` | `LnkCap` | 声明上限，用来判断能不能达到某速率 |
| 链路此刻跑多快 | 同上 | `LnkSta` | 低于 `LnkCap` 即为降档，需排除空闲状态 |
| 设备有没有累积链路错误 | 同上 | `DevSta` | 伴随链路问题的错误位，用来判断是否已累积错误 |
| 链路世代与宽度、上限与此刻 | `nvidia-smi -q` | 链路信息里对应项的 `Max` 与 `Current` | `Max` 对声明、`Current` 对此刻；空闲时 `Current` 可能被降低 |
| NUMA 有几个域、距离多大 | `numactl --hardware` | 节点清单与距离矩阵 | 远端节点距离明显大于本域即跨域有代价 |
| 某件设备挂在哪号域 | `cat /sys/bus/pci/devices/<BDF>/numa_node` | 节点号，无归属时为 -1 | -1 表示固件未上报，不是可配置的参数 |
| 每条 NVLink 通不通、带宽多少 | `nvidia-smi nvlink -s` | 每条链路的状态与带宽 | `Active` 并给出带宽为正常；`Inactive`、`Sleep` 为异常或休眠 |
| NVLink 有没有累积错误 | `nvidia-smi nvlink -e` | 链路错误计数 | 累计量，看两次读数之差是否增长 |
| fabric 注册到哪一步 | `nvidia-smi -q` | fabric 段的状态与结果 | 注册中为「进行中 / 不适用」，成功后为「已完成 / 成功」，两者要同时满足 |
| 管理服务在不在、版本对不对 | 服务状态命令与服务包版本 | 运行态与服务版本 | 运行态且与驱动包同版本 |

**这张表的用法是逐行命中，不是逐行执行。** 每一行只在上一行给出「需要继续查」时才执行，问题定位到哪一段就在那一段合上，不把整张表跑完。

## 故障现场定位表

这张表把常见现象映射到第一份读数，用来决定第二个动作落在哪个对象上。

| 现象 | 先看什么 | 判据 | 转向哪一步 |
| --- | --- | --- | --- |
| 无报错但吞吐只有同类节点的一半 | 链路声明与协商结果 | `LnkSta` 低于 `LnkCap` 即为降档 | 带负载复读，排除空闲降档后再查插槽与固件 |
| 卡间带宽远低于 NVLink 规格 | 链路状态与 fabric 注册状态 | 链路未激活或结构未注册 | 先确认 fabric 是否就绪，再看链路 |
| 跨卡路径退回 PCIe | 结构状态与结果字段 | 任一字段不满足即未注册 | 先修 fabric，再谈卡间能力 |
| `nvidia-smi -q` 里链路宽度只有一半 | 读这份读数的时刻 | 空闲时宽度可能被降低 | 带负载复读一次再判 |
| 派到别的域的任务变慢 | 设备节点与节点距离矩阵 | 设备与内存不在同一域 | 用同口径对照区分本域与跨域 |
| 设备节点读到 -1 | 整机节点清单 | 固件未上报设备归属 | 转向固件侧核对，不在进程绑定上找 |
| 直通能力矩阵出现不支持 | 同一对设备的距离代号 | 代号与能力判定要一起看 | 按不支持码指向的对象分层核对 |
| 计算运行时在初始化阶段报系统未就绪 | fabric 段与服务状态 | 结构状态或结果字段不满足 | 先修管理服务与注册，再谈链路 |
| 部分实例之间直通异常 | 这张卡当前的实例划分 | 模式改变会改变可用能力 | 先确认是否处于切分模式 |

## 用对照实验区分「是不是这一段」

读数是静态的，很多结论要靠**成对的对照**才能落地。设计的原则是：同一对设备、同一段代码、同一口径，只改变一个变量。

- **本域对跨域**：让同一段主机内存搬运分别落在与设备同域和远端域各做一次，比较吞吐；差异显著说明这一趟跨越了内存域。变量只有一个：内存落在哪个域。
- **直通对回退**：在同一对设备上，一次让它走设备间直通、一次让它退化为经主机内存中转，比较吞吐；差异显著说明直通这条路径确实在起作用。变量只有一个：这一对是否直通。
- **同型不同位**：把同一张卡换到同一机型的不同插槽上，比较链路协商结果（正确做法；插槽优先于猜测）。

**卡到网卡这一组不能省。** 判断显存直接远程访问这条路径是否走了预期的位置关系，要在卡与网卡这一对设备上单独做一次对照，而不是拿两张卡之间的结果去推论——两条路径的上限分别由 NVLink 与 PCIe 决定，不能互相替代。

强制回退与吞吐观测的具体手段不在本篇展开：直通的开关落在通信库与运行时一层（例如 NCCL 的 P2P 开关），显存到网卡路径的吞吐观测工具属 perftest 主题，均不属本篇负责的内容。本篇只负责对照实验的设计口径——变量唯一、口径一致、成对执行。

## 采样与记录纪律

- **瞬时量与累计量分开记**：链路协商结果是瞬时值，采集时刻不同就不能相减；链路错误计数是累计量，判据是两次读数之差在运行期的增长。
- **声明与此刻成组记**：`LnkCap` 与 `LnkSta`、`Max` 与 `Current` 要一起取，只取一个发现不了降档。
- **带负载再判降档**：先在设备工作时复读链路读数，空闲时刻的低档位属正常现象。
- **区位三项一起记**：设备位置、内存域、链路协商结果要与机型、代际、实例划分状态一起记，缺任一项都影响可比性。
- **对照只改一个变量**：每次对照只改变一个条件，两个变量一起变则无法归因。

## 影响范围较大的操作

下面这些操作会中断同一台机器上的**全部**作业，影响范围不是单个进程或单张卡。它们只允许在实验节点上验证；在生产节点上执行前必须先完成隔离，且回滚路径要先写清。

| 操作 | 影响范围 | 必备前置 | 回滚路径 |
| --- | --- | --- | --- |
| 复位单张 GPU | 整机全部依赖该卡的作业中断 | 取证材料齐备、作业已退出 | 复位失败时按故障处置流程隔离该卡 |
| 重新切分或回收实例划分 | 该卡上全部作业中断，划分状态改变 | 划分前的实例清单与作业已退出 | 按原划分重建，回到变更前状态 |
| 停止或重启管理服务与子网管理进程 | 整机全部跨卡作业中断 | 现场已取证、作业已退出 | 恢复服务并确认结构状态与结果字段回到成功 |

```bash
# 验证：一次拓扑巡检的最小读数（只读，生产节点上也可以做）
nvidia-smi topo -m; nvidia-smi nvlink -s; lspci -vv -s <BDF> | grep -E 'LnkCap|LnkSta'
```

上面一条命令覆盖「路径结构、链路状态、链路协商」三个判定的取值入口；数值与清单随机型、代际与插槽位置变化，任何对照使用的数值仅示意、不代表你的环境。

## 常见故障与排查方向

下面四个场景把故障现场定位表给出的第一份读数继续走完：每个场景先写现场，再写先读什么，然后写读到什么就转往哪一步，最后写一份合格的回答应当包含什么。四个场景都设定在单机档位的裸金属上：距离、直通与 NUMA 的判定只在裸金属口径下成立，虚拟化或云主机上的同类读数不能外推。场景里的机型、代际、插槽位置与数值都是具象设定，用来练判断，不代表你的环境。

### 场景一：同池同机型，有一台慢一半，没有任何报错

**现场**：同一节点池里的一批同机型 8 卡节点跑同一作业，其中一台的吞吐稳定只有其他节点的一半，日志没有报错、事件计数没有异常。变更记录显示这台机器上周换过一块转接卡。

**先看什么**：慢一半而无报错，先读路径结构再读数值。这种落差最常见的成因是链路协商低于声明能力，而协商只影响速率、不产生任何报错。声明与此刻两份读数要成组取，只取一个发现不了问题。

```bash
lspci -vv -s <BDF> | grep -E 'LnkCap|LnkSta|DevSta'   # 验证：声明能力、实际协商结果与累积错误位（三者成组取）
nvidia-smi -q | grep -E -A2 'GPU Link Info'           # 验证：管理工具侧链路信息的上限与此刻（与上一行互证）
```

**读到什么就转往哪一步**：

- 若此刻的协商结果低于声明能力，先别下结论，确认这份读数取自什么时刻：链路在设备空闲时可能被主动降低。让设备带上负载复读一次；带负载后回到声明值，则这是空闲降档，不是故障。
- 若带负载后仍然低一档（宽度减半或世代降一），则降档成立：接下来查物理与配置侧——插槽、转接卡、固件设置里与链路宽度相关的项；有「换过转接卡」这条变更记录时优先怀疑装配。用「同型不同位」那组对照落实：把卡换到同机型的另一个插槽上比较协商结果，变量只有插槽位置。
- 若 `DevSta` 的错误位已经置起，则这条链路已经累积过错误，按链路退化处理，而不只是「慢」；把错误位与协商结果一起写进取证记录。
- 若声明与此刻在负载下一致，则慢不在链路这一段：转向直通与内存域两段，分别用「直通对回退」与「本域对跨域」两组对照继续定位，不要在链路这一段反复重读。

**一份合格的回答**应当说清：结论落在降档成立、空闲降档，还是不在链路这段；依据是声明与此刻两份读数在带负载前后的对照，以及错误位的状态；边界是降档结论只在带负载的读数上成立，空闲读数不能作为任何一方的证据；动作是查插槽与固件设置、做同型不同位对照，还是转向另外两段，并写清复测时的负载条件。

### 场景二：两卡直通退回中转，能力矩阵给出不支持码

**现场**：裸金属 8 卡机上选两张卡做直通对照实验：同一段搬运代码，一次走设备间直通、一次经主机内存中转，两组吞吐几乎没有差别。查直通能力矩阵，这一对给出 `CNS`。这台机器按记录没有开启实例划分。

**先看什么**：直通与中转无差异，说明直通这条路没有起作用；能力矩阵的不支持码指出最先关上的那一道门。同一对设备要读三个对象：不支持码、距离代号、实例划分状态。

```bash
nvidia-smi topo -p2p r      # 验证：直通能力矩阵里这一对的判定码（按访问类型还有 w/n/a/p 几张矩阵）
nvidia-smi topo -m          # 验证：同一对设备的距离代号，以及亲和两列
```

**读到什么就转往哪一步**：

- 若判定码是 `CNS`，则门在芯片组与固件一侧：核对地址翻译部件是否处于翻译模式、交换桥上的访问控制是否把直通流量压回了根复合体；这两项的开关在内核启动参数与固件设置里，改动要重启，列入变更窗口。
- 若判定码是 `TNS`，则门在拓扑：看同一对设备的距离代号——跨 socket（`SYS`）时不少机型本来就不支持直通，退回中转是预期行为而不是故障；此时的动作是调整任务位置，不是修机器。
- 若判定码是 `GNS`，则先在实例划分状态上核实记录是否属实，再判定该型号本身是否具备此项能力；处于切分模式的卡，跨实例的直通能力与整卡不同。
- 若判定码是 `NS`，则未细分：按芯片组、拓扑、设备的顺序逐层核对，每一步都与距离代号一起读。
- 若这一对是 GPU 与网卡，则判定对象换成显存直接远程访问的拓扑前提：卡与网卡的相对位置决定这条路径能否成立，而模块一侧的加载前置不属本篇范围；也不要拿两张卡之间的对照结果去推论卡到网卡，两条路径的上限分别由不同段落决定。

**一份合格的回答**应当说清：结论落在哪一道门——芯片组与固件、拓扑结构、设备能力，还是跨 socket 下的预期行为；依据是不支持码与同一对设备的距离代号、实例划分状态三者的组合；边界是能力矩阵只回答「能不能走」，路径成立而吞吐异常时要回到声明与实际协商的对照上继续定位；动作是改固件与内核参数、调整任务位置，还是接受中转并评估其代价，改动类动作列入窗口并写清回滚。

### 场景三：NVSwitch 机型上管理工具正常，跨卡任务初始化报系统未就绪

**现场**：一台第三代 NVSwitch 机型（H100 一代），驱动升级之后，跨卡集合通信在初始化阶段报 `cudaErrorSystemNotReady`，单卡任务正常，管理工具能列出全部 8 张卡。升级记录里只有驱动包，没有管理服务。

**先看什么**：管理工具正常只证明管理链路通了，跨卡能力还要求 fabric 注册完成。读结构状态与结果两个字段，以及管理服务的状态与版本。

```bash
nvidia-smi -q | grep -E -A3 'Fabric'        # 验证：结构状态与结果字段（两个字段要同时满足）
systemctl status nvidia-fabricmanager       # 验证：管理服务是否在运行
# 另查服务包版本与驱动包版本是否逐位一致（包管理器查询）
```

**读到什么就转往哪一步**：

- 若结构状态或结果字段不满足，则 fabric 未注册：先核对管理服务版本与驱动包版本是否逐位一致——驱动升级而服务没跟着升级时，注册会在初始化阶段失败。对齐版本并重启服务后复读两个字段；重启管理服务会中断整机全部跨卡作业，执行前确认作业已退出，回滚是恢复原版本组合。
- 若两个字段满足、而链路状态里出现 `Inactive` 或 `Sleep`，则 fabric 正常而个别链路没有工作：转入硬件与基板侧核对；同时看链路错误计数，若它先于报错增长，按劣化处理。
- 若机型是第四代（B100/B200 一代），则管理通路形态不同：交换芯片不再作为 PCIe 设备出现，`lspci` 里找不到它不是故障；判据仍然是结构状态与结果字段，不是设备清单。
- 若全部满足而报错仍在，则问题不在 fabric 这一段：回到驱动栈的落层判读——模块、节点、两个版本字段，不要在 fabric 上反复重启服务。

**一份合格的回答**应当说清：结论落在管理服务版本不配、注册未完成、个别链路异常，还是不在 fabric 段；依据是结构状态与结果两个字段、服务状态与两个版本字段；边界是第三代起链路由硬件自行训练，链路训练完成不代表注册完成，两个字段缺一不可；动作是对齐服务版本并重启、转硬件侧，还是转驱动栈落层，并写明重启服务的影响范围与回滚。

### 场景四：同一作业时快时慢，慢的几次恰好落在另一组核上

**现场**：一台双 socket 节点，同一作业多次运行，吞吐时快时慢；对照调度记录，慢的几次恰好被派到另一组核与内存上。作业本身没有变化，机器上没有其他负载。

**先看什么**：「派到别处就慢」指向内存域：设备、核与内存是否在同一域。先读三个对象——设备挂在哪号域、核集合与内存落在哪号域、节点距离矩阵。

```bash
numactl --hardware                          # 验证：节点清单、各域的核集合与节点距离矩阵
cat /sys/bus/pci/devices/<BDF>/numa_node    # 验证：设备挂在哪号域（-1 表示固件未上报）
nvidia-smi topo -m | grep -E 'Affinity'     # 验证：设备建议的核集合与内存域两列
```

**读到什么就转往哪一步**：

- 若设备在一号域、而慢的那几次核与内存落在另一号域，则跨域搬运成立：用「本域对跨域」那组对照确认——同一段主机内存搬运分别落在同域与远端域各一次，变量只有内存落在哪个域；差异显著即归因成立。跨域主要吃带宽、同时抬高延迟，不要把它只算成延迟问题。
- 若设备的归属读到 -1，则固件没有上报：这不是能就地配置的参数，转向整机固件侧核对；在归属未知时不要凭猜调整进程绑定。
- 若拓扑矩阵里相关设备的距离代号是 `NODE` 或 `PHB`，则它们仍在同一个 NUMA 节点内：跨没跨 socket 以代号为准，五个代号里只有 `SYS` 跨出；不要按代号的名字调整绑定。
- 若三项读数一致、对照也做了而快慢差异仍在，则慢不在内存域这一段：回到链路与直通两段继续定位。

**一份合格的回答**应当说清：结论落在跨域搬运成立、固件未上报、代号误读，还是不在内存域这段；依据是三份区位读数与「本域对跨域」对照的结果；边界是对照结论只在变量唯一时成立，两次对照之间若负载或实例划分状态也变过，则归因不成立；动作是把作业绑回同域、转固件侧，还是转其他段，并写清绑定的验收方式——同一作业、同一口径复跑。

**第一反应不要做什么**：不要一上来就把所有读数跑一遍；不要在没确认路径结构之前就下「慢」的结论；不要在空闲时刻断言链路降档；不要拿两张卡的结果推论卡到网卡；不要在没做对照之前把问题归到 NUMA 或直通；不要在机器上还有作业时执行会中断作业的操作。正确的顺序是先读路径结构、再读该段的实际值、用对照确认归因、最后才谈动作。
