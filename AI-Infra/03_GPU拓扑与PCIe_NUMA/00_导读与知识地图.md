# GPU 拓扑与 PCIe / NUMA

## 知识地图

### 一次 GPU 间或 GPU 到网卡的搬运走哪条路径：五段

本章的主链是**一次搬运的路径选择**。同一份数据从一张卡的显存到另一张卡的显存、或从显存到网卡，可以走若干条距离不同的路；路径由设备在 PCIe 树与 NUMA 域上的位置决定，而位置错误不会报错，只会变慢。

| 段 | 这一段在做什么 | 到这里要能说清 |
| --- | --- | --- |
| 1 判定距离 | 按 `nvidia-smi topo -m` 的代号把两件设备之间的距离分成若干档 | 每个代号对应路径上多了什么，以及判据是哪一个代号 |
| 2 判定能否直通 | 检查 P2P 矩阵与它背后的三道门：设备能力、IOMMU 与 ACS、驱动侧开关 | 走不了 P2P 时数据绕到哪里，现象是什么 |
| 3 判定 NUMA 归属 | 把「距离」平移到 CPU 与内存：GPU、网卡、NVMe 各自挂在哪号 NUMA 域 | 跨 NUMA 影响的是带宽还是延迟，以及绑核绑内存如何生效 |
| 4 判定链路是否降档 | 读链路的协商结果，与它声明的能力对照 | 降速为什么是静默的，以及哪几处读数能把它抓出来 |
| 5 判定节点内互联形态 | 区分 NVLink 直连与经 NVSwitch 的全互联，并确认管理通路已就绪 | NVSwitch 机型上哪一项服务必须先起来，第四代机型的管理通路有什么不同 |

**贯穿本章的三问**：这两件设备之间隔了几跳；这条路径上的带宽上限由哪一段决定；这次读取的是**声明能力**还是**实际协商结果**。

### 三个跨阶段的核对对象

| 核对对象 | 它贯穿哪几段 | 每一处读什么字段 |
| --- | --- | --- |
| 距离 | 它贯穿段 1 到段 5，因为 PCIe 树、NUMA 域与 NVLink 域三种「近」并不等价 | 在段 1 读 `nvidia-smi topo -m` 的矩阵与 `CPU Affinity`/`NUMA Affinity` 两列；在段 3 读 `/sys/bus/pci/devices/<BDF>/numa_node`；在段 5 读 `nvidia-smi -q` 的 Fabric 段与 `nvidia-smi nvlink -s` |
| 上限与实际值 | 它贯穿段 2、段 4 与段 5，因为每一处都同时存在「支持什么」与「此刻是什么」两个量 | 在段 2 读 P2P 矩阵与 `lspci -vv` 的 `DevSta`；在段 4 用 `LnkCap` 与 `LnkSta` 对照，并注意空闲时的降档；在段 5 读 NVLink 的 `Speed` 与 `Width` 两列 |
| 管理通路的就绪状态 | 它贯穿段 5 与后续所有跨卡搬运，因为 NVSwitch 机型上 fabric 未注册会让 NVLink 能力静默消失 | 在段 5 读 `nvidia-smi -q` 的 Fabric 段的 `State` 与 `Status` 两个字段，并读 Fabric Manager 服务的状态；出现 `cudaErrorSystemNotReady` 或跨卡路径退回 PCIe 时先回到这一项 |

## 术语速查

| 名词 | 一句话解释 | 在哪一篇展开 |
| --- | --- | --- |
| `PIX` / `PXB` / `PHB` / `NODE` / `SYS` | `nvidia-smi topo -m` 里表示两件设备之间距离的五个代号，分别对应同一 PCIe 交换机、多级交换机、同一 Host Bridge、同一 NUMA 内跨 Host Bridge、跨 NUMA | 原理：距离的分层与它的成因 |
| `NV#` | 表示两件设备之间存在 NVLink，数字是链路条数 | 原理：NVLink 与 NVSwitch 的形态差异 |
| Host Bridge | CPU 内部连接 PCIe 根复合体的部件，跨过它意味着数据要多走一段 | 原理：距离的分层与它的成因 |
| P2P | 两件 PCIe 设备之间直接搬运数据而不过主机内存 | 原理：P2P 的三道门 |
| ACS | PCIe 交换机上的访问控制服务，开启后会阻止设备绕过根复合体互相访问 | 原理：P2P 的三道门 |
| IOMMU | 把设备地址翻译成物理地址的部件，直通模式下会影响 P2P 能否生效 | 原理：P2P 的三道门 |
| `LnkCap` 与 `LnkSta` | `lspci -vv` 里链路的**声明能力**与**实际协商结果**，两者不一致即为降档 | 原理：链路降速的静默特征 |
| NVSwitch | 把多张 GPU 连成全互联的交换芯片，第二至第四代分别以不同的拓扑与管理通路出现 | 原理：NVLink 与 NVSwitch 的形态差异 |
| Fabric Manager | NVSwitch 机型上负责初始化与注册 NVLink fabric 的服务，与驱动版本必须同号 | 体系：一次 NVSwitch 机型的拓扑体检 |
| ALI 与 NVLSM | 第四代 NVSwitch 机型上分配 NVLink 标识与做链路管理的两个组件 | 原理：NVLink 与 NVSwitch 的形态差异 |
| CX7 bridge | 第四代机型上承载 NVSwitch 管理通路的板载网卡功能，使 NVSwitch 不再作为 PCIe 设备出现 | 原理：NVLink 与 NVSwitch 的形态差异 |

## 关键字段的读法

| 字段 | 是什么与单位 | 判据 | 与谁同看 | 转向哪一步 |
| --- | --- | --- | --- | --- |
| `nvidia-smi topo -m` 矩阵里的一格 | 第 i 行第 j 列表示 GPU i 与 GPU j（或网卡）之间的距离代号 | 出现 `SYS` 才算跨了 socket；`NODE` 仍在同一个 NUMA 节点内 | 与同一张表的 `NUMA Affinity` 列、以及 `numactl --hardware` 同看 | 若出现 `SYS`，先确认这个任务的跨卡通信量有多大，再决定是否重排 |
| `lspci -vv` 的 `LnkCap` | 链路**声明支持**的速率与宽度，例如 `Speed 32GT/s, Width x16` | 它是不变的上限，用来判断这台机器**能不能**达到某个速率 | 与同一设备的 `LnkSta` 同看 | 若 `LnkSta` 低于 `LnkCap`，转入降档排查 |
| `lspci -vv` 的 `LnkSta` | 链路**此刻协商出**的速率与宽度 | 低于 `LnkCap` 即为降档；GPU 掉到 x8 或降一代是真实生产故障 | 与 `DevSta` 以及负载状态同看 | 先在有负载时复读一次排除空闲降档，再查插槽、转接卡与 BIOS 设置 |
| `nvidia-smi -q` 的 Fabric 段 `State` 与 `Status` | NVSwitch fabric 的注册状态与结果 | 常态应为 `State: Completed` 与 `Status: Success` | 与 `systemctl status nvidia-fabricmanager` 同看 | 任一字段不符时先修 fabric，再谈 NVLink 带宽 |
| `nvidia-smi nvlink -s` 的 `Speed` 与 `Width` | 每条 NVLink 的速率与宽度 | 与机型规格对照；为零或减半即为异常 | 与 `nvidia-smi -q` 的 Fabric 段同看 | 若 fabric 正常而链路为零，转入硬件与基板侧排查 |
