## 知识地图

### 一次 GPU 间或 GPU 到网卡的搬运走哪条路径：五段

本章的主链是**一次搬运的路径选择**。同一份数据从一张卡的显存到另一张卡的显存、或从显存到网卡，可以走若干条距离不同的路；路径由设备在 PCIe 树与 NUMA 域上的位置决定，而位置错误不会报错，只会变慢。

| 段 | 这一段在做什么 | 到这里要能说清 |
| --- | --- | --- |
| 1 判定距离 | 按 `nvidia-smi topo -m` 的代号把两件设备之间的距离分成若干档 | 每个代号对应路径上多了什么、判据是哪一个代号，以及每一档距离的带宽量级锚点——没有量级，「上限由哪一段决定」就无法兑现成判据 |
| 2 判定能否直通 | 检查直通能力矩阵与它背后的三道门：硬件路径、BIOS 与内核（IOMMU、ACS）、CUDA 层使能与连接数上限；判定对象同时包含 GPU 对 GPU 与 GPU 对网卡两类 | 走不了直通时数据绕到哪里、现象是什么、四个不支持码各指向谁，以及网卡与 GPU 的相对位置如何决定 GPUDirect RDMA 能否成立（`nvidia_peermem` 的模块前置不是本章负责的内容，本章只判拓扑前提） |
| 3 判定 NUMA 归属 | 把「距离」平移到 CPU 与内存：GPU、网卡、NVMe 各自挂在哪号 NUMA 域 | 跨 NUMA 影响的是带宽还是延迟，以及绑核绑内存如何生效 |
| 4 判定链路是否降档 | 读链路的协商结果，与它声明的能力对照 | 降速为什么是静默的，以及哪几处读数能把它抓出来 |
| 5 判定节点内互联形态 | 区分 NVLink 直连与经 NVSwitch 的全互联，并确认管理通路已就绪 | NVSwitch 机型上哪一项服务必须先起来，第三代起链路训练由谁完成，第四代机型的管理通路有什么不同（「第 N 代」一律指 NVSwitch 代际，正文以对应机型标注） |

**贯穿本章的三问**：这两件设备之间隔了几跳；这条路径上的带宽上限由哪一段决定；这次读取的是**声明能力**还是**实际协商结果**。

**本章收在哪里**：段 5 与篇 05、篇 06 的对象是单机 NVSwitch 域——基板形态、管理通路的就绪判定与 fabric 注册都在一台机器内部收口。NVLink 域跨出机箱之后的部分（多机 NVLink、跨机标识与连通性诊断）不是本章负责的内容；本章读到 fabric 注册成功即止步。

### 三个跨阶段的核对对象

| 核对对象 | 它贯穿哪几段 | 每一处读什么字段 |
| --- | --- | --- |
| 距离 | 它贯穿段 1 到段 5，因为 PCIe 树、NUMA 域与 NVLink 域三种「近」并不等价 | 在段 1 读 `nvidia-smi topo -m` 的矩阵与 `CPU Affinity`/`NUMA Affinity` 两列；在段 3 读 `/sys/bus/pci/devices/<BDF>/numa_node`；在段 5 读 `nvidia-smi -q` 的 Fabric 段与 `nvidia-smi nvlink -s` 的链路状态 |
| 上限与实际值 | 它贯穿段 2、段 4 与段 5，因为每一处都同时存在「支持什么」与「此刻是什么」两个量 | 在段 2 读直通能力矩阵与 `lspci -vv` 的 `DevSta`；在段 4 用 `LnkCap` 与 `LnkSta` 对照，并注意空闲时的降档；在段 5 读 NVLink 的链路状态与 `nvidia-smi nvlink -e` 的错误计数 |
| 管理通路的就绪状态 | 它贯穿段 5 以及本章内所有以 NVLink 带宽为对象的判据，因为 NVSwitch 机型上 fabric 未注册会让 NVLink 能力静默消失 | 在段 5 读 `nvidia-smi -q` 的 Fabric 段的 `State` 与 `Status` 两个字段，并读 Fabric Manager 服务的状态；出现 `cudaErrorSystemNotReady` 或跨卡路径退回 PCIe 时先回到这一项 |

## 术语速查

| 名词 | 一句话解释 | 在哪一篇展开 |
| --- | --- | --- |
| `PIX` / `PXB` / `PHB` / `NODE` / `SYS` | `nvidia-smi topo -m` 里表示两件设备之间距离的五个代号，分别对应至多一个 PCIe 桥、多级 PCIe 桥、跨 Host Bridge、同一 NUMA 节点内更深的路径、跨 NUMA；五者中只有 `SYS` 跨出 socket，`PHB` 与 `NODE` 都留在同一 NUMA 节点内，区别只在路径深度 | 原理：距离的分层与它的成因 |
| `NV#` | 表示两件设备之间存在 NVLink，数字是链路条数 | 原理：NVLink 与 NVSwitch 的形态差异 |
| BDF | 设备的 PCI 地址记号（总线:设备.功能），是 `/sys/bus/pci/devices/` 下的目录名，也是把 `lspci`、`topo -m` 与 sysfs 三方读数对到同一件设备上的键 | 原理：距离的分层与它的成因 |
| `C2C` | 集成平台上 CPU 与 GPU 之间的片间直连代号；这类平台的主数据路径不是 PCIe，PCIe 侧的世代与宽度读数不代表主路径带宽 | 原理：距离的分层与它的成因 |
| Host Bridge | CPU 内部连接 PCIe 根复合体的部件，跨过它意味着数据要多走一段 | 原理：距离的分层与它的成因 |
| P2P | 两件 PCIe 设备之间直接搬运数据而不过主机内存；本章的判定对象既包括 GPU 对 GPU，也包括 GPU 对网卡 | 原理：P2P 的三道门 |
| ACS | PCIe 交换机上的访问控制服务，能力位不止重定向一项；重定向开启后设备之间的直通流量会被压回根复合体，与 IOMMU 的翻译模式共同构成内核侧这道门 | 原理：P2P 的三道门 |
| IOMMU | 把设备地址翻译成物理地址的部件；处于翻译模式时会阻断设备之间的直通搬运，裸金属上应关闭或置于直通模式 | 原理：P2P 的三道门 |
| `LnkCap` 与 `LnkSta` | `lspci -vv` 里链路的**声明能力**与**实际协商结果**，两者不一致即为降档 | 原理：链路降速的静默特征 |
| NVSwitch | 把多张 GPU 连成全互联的交换芯片，第一至第四代分别以不同的拓扑与管理通路出现；本章说的「第 N 代」一律指 NVSwitch 代际，并以对应机型标注 | 原理：NVLink 与 NVSwitch 的形态差异 |
| ALI | 第三代 NVSwitch 机型起的自主链路初始化：链路由 GPU 与 NVSwitch 硬件自行训练，不再需要管理服务参与训练 | 原理：NVLink 与 NVSwitch 的形态差异 |
| Fabric Manager | NVSwitch 机型上负责初始化与注册 NVLink fabric 的服务，版本必须与驱动同号 | 原理：Fabric Manager 与管理通路 |
| NVLSM | NVLink 子网管理器（NVLink Subnet Manager），第四代 NVSwitch 机型起引入，负责配置 NVSwitch 侧的路由表，与管理服务通过进程间接口协同 | 原理：Fabric Manager 与管理通路 |
| NVSDM | NVLink 交换设备管理器（NVLink Switch Device Manager），第四代机型上 NVSwitch 的错误与遥测计数改由它对外提供 | 原理：Fabric Manager 与管理通路 |
| CX7 bridge | 第四代机型上承载 NVSwitch 管理通路的板载网卡功能，使 NVSwitch 不再作为 PCIe 设备出现 | 原理：Fabric Manager 与管理通路 |

## 关键字段的读法

| 字段 | 是什么与单位 | 判据 | 与谁同看 | 转向哪一步 |
| --- | --- | --- | --- | --- |
| `nvidia-smi topo -m` 矩阵里的一格 | 第 i 行第 j 列表示 GPU i 与 GPU j（或网卡）之间的距离代号 | 出现 `SYS` 才算跨了 socket；`NODE` 仍在同一个 NUMA 节点内。GPU 与目标网卡落在哪一档，决定 GPUDirect RDMA 走哪条路径。矩阵里的网卡行可能包含并非 RDMA 能力的 bonded 网口，因此「矩阵里有它」不等于「它能当直通目标」；反过来，一个设备能不能当直通目标要另用 RDMA 侧的设备清单确认，两边读数不能互相替代 | 与同一张表的 `NUMA Affinity` 列、以及 `numactl --hardware` 同看 | 若出现 `SYS`，先确认这个任务的跨卡通信量有多大，再决定是否调整任务的位置 |
| `nvidia-smi topo -p2p r/w/n/a/p` 矩阵里的一格 | 第 i 行第 j 列表示两件设备（GPU 对 GPU，或 GPU 对网卡）之间某一类直通访问的能力判定 | `OK` 表示这条路可用；`CNS` 指向芯片组与 BIOS 侧、`TNS` 指向拓扑、`GNS` 指向 GPU 本身的能力、`NS` 未细分 | 与同一对设备的距离代号、以及 GPU 的 MIG 模式同看 | 出现 `CNS` 或 `TNS` 转入 BIOS、IOMMU 与 ACS 的核对；出现 `GNS` 先查 GPU 是否处于 MIG 模式，再判定该型号本身是否具备此项能力 |
| `/sys/bus/pci/devices/<BDF>/numa_node` 的值 | 设备挂在哪个 NUMA 域，无归属时为 -1 | 读到 -1 或与拓扑明显不符，说明固件上报有问题，不是可以就地配置的参数 | 与 `numactl --hardware` 的节点清单同看 | 转入整机固件侧的核对，而不是继续调整进程绑定 |
| `lspci -vv` 的 `LnkCap` | 链路**声明支持**的速率与宽度，例如 `Speed 32GT/s, Width x16` | 它是不变的上限，用来判断这台机器**能不能**达到某个速率 | 与同一设备的 `LnkSta` 同看 | 若 `LnkSta` 低于 `LnkCap`，转入降档排查 |
| `lspci -vv` 的 `LnkSta` | 链路**此刻协商出**的速率与宽度 | 低于 `LnkCap` 即为降档；GPU 掉到 x8 或降一代是真实生产故障 | 与 `DevSta` 以及负载状态同看 | 先在有负载时复读一次排除空闲降档，再查插槽、转接卡与 BIOS 设置 |
| `nvidia-smi nvlink -s` 的链路状态与带宽 | 每条 NVLink 的状态（`Active`、`Inactive` 或 `Sleep`），活跃时显示该链路的带宽 | 出现 `Inactive` 或 `Sleep` 说明这条链路没有在工作；带宽与机型规格对照 | 与 `nvidia-smi nvlink -e` 的错误计数、`nvidia-smi -q` 的 Fabric 段同看 | 若状态异常而 fabric 正常，转入硬件与基板侧核对；错误计数先于报错增长时按劣化处理 |
| `nvidia-smi -q` 的 Fabric 段 `State` 与 `Status` | fabric 的注册状态与结果 | 常态应为 `State: Completed` 与 `Status: Success` | 与 Fabric Manager 服务的状态同看 | 任一字段不符时先修 fabric，再谈 NVLink 带宽 |
