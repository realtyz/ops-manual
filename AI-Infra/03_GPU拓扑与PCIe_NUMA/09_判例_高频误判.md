# 高频误判

拓扑这一层的事故有一个共同特征：**命令都不报错，读数看起来也正常，只有吞吐和预期对不上**。误判通常不是读错了字段，而是把两个不同口径的量当成了同一个。下面这些判例按「场景、常见误判、判据、结论、出处」逐条给出，判据里的字段名与单位与前面的读法保持一致。

### 「卡间慢，说明卡坏了」

- **场景**：两张卡之间的带宽比同类机器低，第一反应是其中一张卡或某条 NVLink 坏了。
- **常见误判**：把带宽偏低直接归到硬件故障。它看起来成立的原因在于链路确实可能退化。
- **判据**：先看这一对设备在距离矩阵里的代号，再看这两张卡各自挂在哪号内存域。判据项是距离代号与内存域，与链路状态同看。条件会变：全互联机型上任意两卡对称，直连机型上不同卡对的带宽本来就不同。
- **结论**：带宽偏低先要落到「这一对走的是哪条路」，而不是先落到「哪张卡坏了」。
- **出处**：NVIDIA System Management Interface 文档的拓扑一节（距离代号与图例）。

### 「矩阵里没有某张网卡，说明它不在位」

- **场景**：拓扑矩阵的网卡行里没有目标网卡，于是判断这张网卡不在位或不能做直通。
- **常见误判**：把矩阵里的出现当作「在位且能直通」的唯一证据。它看起来成立的原因在于矩阵确实列出设备。
- **判据**：矩阵的网卡行可能包含并非 RDMA 能力的 bonded 网口，因此在位与否、能否做直通目标都要另取读数确认。判据是设备清单与能力判定两份读数，不能互相替代。条件会变：容器环境里可见设备由运行时决定，与宿主机不同。
- **结论**：矩阵里有没有某张网卡，不等于它在不在位、能不能做直通目标。
- **出处**：NVIDIA System Management Interface 文档的拓扑一节（网卡行的说明）。

### 「`PHB` 与 `NODE` 听起来像跨了节点」

- **场景**：距离矩阵里出现 `NODE`，按名字理解成跨了 NUMA 节点，于是调整进程绑定。
- **常见误判**：把代号名当成实际路径。它看起来成立的原因在于名字里带「节点」。
- **判据**：五个代号里只有 `SYS` 跨了 socket；`PHB` 与 `NODE` 都留在同一个 NUMA 节点内，区别只在路径深度。判据是代号本身，与设备的内存域同看。
- **结论**：跨没跨 socket 以代号为准，不以名字的字面为准。
- **出处**：NVIDIA System Management Interface 文档的拓扑一节（图例对 `NODE` 与 `PHB` 的定义）。

### 「空闲时链路宽度减半，是降档」

- **场景**：查看链路读数时发现当前宽度只有声明宽度的一半，判定为降档并去查插槽。
- **常见误判**：把设备空闲时刻的读数当成工作时的读数。它看起来成立的原因在于两个时刻读的是同一个字段。
- **判据**：链路世代与宽度在设备不被使用时可能被主动降低；判据是**带负载时**复读的协商结果与声明能力的对照。条件会变：忙碌程度不同，读数不同。
- **结论**：降档判定必须带负载，空档不能作结论。
- **出处**：NVIDIA System Management Interface 文档中关于链路信息的说明（当前值在设备空闲时可能被降低）。

### 「直通能力显示不支持，就是卡坏了」

- **场景**：直通能力矩阵出现不支持码，判断为设备故障。
- **常见误判**：把能力判定结果直接等同于硬件损坏。它看起来成立的原因在于这一对确实不能直通。
- **判据**：不支持码分四类，分别指向芯片组、拓扑、设备与未细分；且这张卡若处于实例划分模式，跨实例的直通能力会与整卡不同。判据是能力码与实例划分状态，与距离代号同看。
- **结论**：不支持先要落到「哪一道门关了」，再排除实例划分模式，不能直接判故障。
- **出处**：NVIDIA Multi-Instance GPU 用户指南（实例划分对直通能力的影响）。

### 「NVSwitch 机型上 `lspci` 里没有交换芯片，是管理通路坏了」

- **场景**：在某代交换芯片机型上查看 PCIe 设备清单，找不到交换芯片，判断管理通路异常。
- **常见误判**：把「交换芯片应当是 PCIe 设备」当成本代也成立的假设。它看起来成立的原因在于较早世代确实如此。
- **判据**：第四代机型的交换芯片不再作为主机 PCIe 设备出现，管理通路改由集成在基板上的网卡功能承载。判据是服务状态与结构注册状态，不是设备清单。条件会变：代际决定这一条读法。
- **结论**：在第四代机型上，交换芯片不在 PCIe 清单里属正常形态。
- **出处**：NVIDIA Fabric Manager User Guide（第四代机型的基板网卡功能承载管理通路）。

### 「链路训练完成，NVLink 就能用了」

- **场景**：看到 NVLink 链路的硬件训练完成，认为卡间能力已就绪，直接开始跑任务。
- **常见误判**：把链路训练与结构注册当成同一件事。它看起来成立的原因在于两者都在初始化阶段完成。
- **判据**：第三代机型起，链路由硬件自行训练，不再需要管理服务参与；但 GPU 仍要向 fabric 注册，注册完成后计算运行时才可初始化。判据是结构状态与结果字段，二者要同时满足。条件会变：第一、二代机型上训练本身还要由管理服务参与。
- **结论**：链路建立与结构注册是两件事，前者成立不代表后者成立。
- **出处**：NVIDIA Fabric Manager User Guide（自主链路初始化与 GPU 注册的关系）。

### 「管理服务版本差不多就行」

- **场景**：驱动升级后，管理服务没跟着升级，认为大版本一致即可。
- **常见误判**：把「同一大版本」当成足够。它看起来成立的原因在于服务确实在运行。
- **判据**：管理服务的包版本要与驱动包版本相同；不一致时注册会在初始化阶段失败。判据是两个版本字段，与服务状态一起读。
- **结论**：服务与驱动的版本要逐位对齐，不能只看能不能跑起来。
- **出处**：NVIDIA Fabric Manager User Guide（服务包版本与驱动版本相同）。

### 「跨 NUMA 只是延迟问题」

- **场景**：一次主机内存中转的吞吐明显偏低，认为跨域只影响延迟、不影响吞吐。
- **常见误判**：把跨域的影响只归到延迟一项。它看起来成立的原因在于路径确实变长了。
- **判据**：跨域主要吃带宽，同时抬高延迟；判定要用同口径的本域与跨域对照，而不是凭直觉。判据是对照结果的比值，与设备内存域同看。
- **结论**：跨域对带宽的影响往往比延迟更显著，必须用对照确认。
- **出处**：Linux 内核文档中关于 NUMA 的说明（节点距离与跨域访问）。

### 「容器里 `nvidia-smi` 正常，说明 fabric 就绪」

- **场景**：在容器里执行管理工具成功，认为卡间能力已就绪，直接启动跨卡任务。
- **常见误判**：把管理链路可见等同于 fabric 注册完成。它看起来成立的原因在于管理工具确实能列出设备。
- **判据**：结构注册状态要从管理工具的查询输出里单独读结构段，服务状态也要一并看；管理工具能跑只证明管理链路通了。判据是结构状态与结果字段，与服务状态同看。
- **结论**：管理工具可用不等于结构注册完成。
- **出处**：NVIDIA Fabric Manager User Guide（结构注册状态的两组对照输出）。

## 值班口径

这些判例可以归成四类共同成因。第一类是把**结构量当成性能量**：距离代号是结构事实，带宽是它的推论，混在一起就会用「快慢」代替判断。第二类是两个**口径混用**：声明能力与实际协商结果、瞬时值与累计值、卡间水平与卡到网卡水平，修正方法是每一对都成组读。第三类是**环节归属错位**：把直通能力当成硬件故障、把链路训练当成结构就绪、把管理工具可用当成注册完成，修正方法是先问「这一段该看哪一份读数」。第四类是**代际与模式的边界**：交换芯片是否为 PCIe 设备、链路训练由谁完成、实例划分是否改变能力，都随代际与模式变化，不能拿一类机型的结论套到另一类。

**第一反应不要做什么**：不要用「慢」当结论；不要把网卡有没有出现在矩阵里当成它在不在位；不要按代号名字猜跨没跨 socket；不要在空闲时刻断言降档；不要把直通不支持当成硬件损坏；不要在第四代机型上按设备清单判断管理通路；不要把链路训练完成当成结构就绪；不要用「同一大版本」代替逐位对齐；不要把跨域只算成延迟；不要用管理工具能跑代替结构注册完成。正确的顺序是先定结构、再定口径、最后才谈动作。
