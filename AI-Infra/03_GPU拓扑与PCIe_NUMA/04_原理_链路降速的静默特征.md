# 链路降速的静默特征

一条 PCIe 链路有两组数：它**声明**能跑多快，以及它**此刻**协商成了多快。这两组数不一致，就是降档。降档最常见的形态是插槽电气规格、转接卡或背板只连通了部分通道，链路于是以更少的通道或更低的一代速率工作——**功能照旧，吞吐打折，不产生任何错误、事件或告警**。现场能发现它，靠的是主动去读并对照这两组数，而不是等一个报错。

## 声明能力与实际协商结果是两个量

链路的两组数分别落在两个寄存器上，读法如下。

| 字段 | 是什么与单位 | 判据 | 与谁同看 |
| --- | --- | --- | --- |
| `LnkCap` | 链路**声明支持**的速率与宽度，例如「速率 16 GT/s、宽度 x16」 | 它是不变的上限，用来判断这台机器**能不能**达到某个速率 | 与同一设备的 `LnkSta` 同看 |
| `LnkSta` | 链路**此刻协商出**的速率与宽度 | 低于 `LnkCap` 即为降档；速率或宽度任一项更低都算 | 与同一设备的 `DevSta` 同看 |
| `DevSta` | 设备状态寄存器的错误位，含可纠正错误标志 | 它本身不是降档判据，用来判断伴随链路问题是否已累积错误 | 与 `LnkSta` 同看 |

管理工具的另一份读数是同一件事的另一个视角：它的查询输出里有一段链路信息，按「世代」与「宽度」两项分别给出 `Max` 与 `Current`。`Max` 对应 `LnkCap`，`Current` 对应 `LnkSta`。两份读数取自不同的层——一份是 PCI 配置空间，一份是设备管理接口——所以当它们不一致时，先怀疑取数时刻不同，而不是立刻下结论。

```bash
# 验证：链路声明能力与实际协商结果的取值入口（只读，生产节点上也可以做）
lspci -vv -s <BDF> | grep -E 'LnkCap|LnkSta|DevSta'
```

输出仅示意、不代表你的环境：出现的速率、宽度与设备编号随机型与插槽位置变化。

## 最常被误读的一种：空闲降档

链路速率与宽度**会在设备空闲时被主动降下来省电**。管理工具的文档对此有明确说明：`Current` 表示的当前世代与宽度，在设备不被使用时可能被降低。这意味着一个看起来像故障的读数，可能只是因为你读它的那一刻没有负载。

由此得到一条判据：**先在有负载时复读一次，再判定是不是降档**。只有当设备正在工作、链路仍然低于 `LnkCap` 时，才构成真实的降档；空闲时刻的 `Current` 低于 `Max` 属于正常现象，不构成问题。这一条把降档从「随时可判」变成了「必须带负载判」，也是为什么它更依赖巡检而不是即时诊断。

一次典型的误读是这样的：先看一份空闲读数，发现宽度只到一半，于是在插槽与转接卡上找原因；复读一次带负载读数，宽度回到满档，之前找的方向全是空的。判据的对象既然是「实际协商结果」，就必须在实际工作时读。

## 降档从哪里来

`LnkSta` 低于 `LnkCap` 的成因按对象分几类，指向不同的核对范围。

| 成因类别 | 对象 | 为什么会让协商结果低于声明 |
| --- | --- | --- |
| 物理通道不足 | 插槽、转接卡、背板 | 声明是 x16 的槽，电气上只连通了部分通道，链路按连通的通道数协商 |
| 上游瓶颈 | PCIe 交换机、根复合体 | 上游链路本身的规格低于设备，协商结果被上游压低 |
| 固件配置 | BIOS 的链路设置 | 固件把某段链路的上限调低，协商结果随之受限 |
| 处理器代际上限 | 处理器支持的 PCIe 代际 | 设备的声明能力高于平台能提供的代际，实际协商停在平台上限 |
| 链路退化 | 接触、信号完整性 | 原本满档的链路在某一时刻退到更低档，速率或宽度都可能变化 |

这几类的区别在于：前四类是**一插上就达不到**，第五类是**运行中退下来**。两者的判据不同——前者看静态对照，后者看两次读数的变化，因此记录要带时刻。

## 为什么只能靠巡检发现

降档不产生设备事件，不触发中断，也不写进错误计数；它只是让一段链路以更低的档位工作。数据仍然搬得动，程序仍然跑得完，只有吞吐比预期低。因此它落在巡检这一类动作里：在节点交付时取一份基线，在运行中周期复读，两次对照即可发现退化；而在一次具体的性能问题里，它是被列入排查清单的一项读数，不会自己冒出来。

两个换算点与一个反推判据：PCIe 4.0 的一条 x16 链路单向约 32 GB/s，宽度降到 x8 就是约 16 GB/s，减半；速率从 16 GT/s 降到 8 GT/s 一代，同样是减半。反推过来，如果一次以 PCIe 为主路径的搬运吞吐恰好落在同型同代设备预期的一半附近，先怀疑宽度掉档或速率降代，再去核对 `LnkSta` 与 `LnkCap`，比先怀疑设备故障更省时间。

```bash
# 验证：两次读数的对照要在同一设备、同一时刻口径下进行（只读）
lspci -vv -s <BDF> | grep LnkSta
```

对照使用的数值仅示意、不代表你的环境，且必须与本节点基线在同一口径下比较。

**第一反应不要做什么**：不要把空闲时的低宽度当成降档；不要用一次读数下结论，先在有负载时复读；不要把声明能力当成实际生效值；不要在宽度与速率都正常时继续在链路上找原因，去查别的段落；不要在平台代际上限不如设备声明时就断定设备故障。正确的顺序是带负载复读、与声明能力对照、与基线对照，三者都指向降档才成立。
