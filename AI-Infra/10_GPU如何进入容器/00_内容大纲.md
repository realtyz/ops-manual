# 第 10 章 GPU 如何进入容器｜内容大纲

## 读者起点与学习目标

本章进入 Kubernetes 资源交付阶段，但先把范围收束到一台 Linux 节点：上层已经选定一张 NVIDIA GPU，容器运行时怎样把这张卡及所需驱动文件交给进程。第 03 章已经解释 CUDA Runtime、`libcuda`、NVML、宿主机内核模块和首次 Kernel 的依赖，第 04 章已经区分 UUID、PCI BDF 与 CUDA 进程序号。本章只在使用处简短回顾，重点增加容器文件系统、OCI 配置、设备访问控制和运行时注入这几层。

读者能区分镜像与容器进程、读懂基本文件权限和 Kubernetes RuntimeClass 即可，无需 GPU 实验环境。读完应能：

1. 从容器内的一次 NVML 查询和一次 CUDA 计算分别画出应用、用户态库、设备节点、宿主机内核驱动与 GPU 的路径，判断镜像、启动时注入和宿主机各应提供什么。
2. 给定 OCI 配置和进程记录，区分设备节点出现、设备访问授权、Unix 权限与安全策略、动态库装载、CUDA 进程枚举及 Kernel 完成，解释“看得见”为何不等于“用得了”。
3. 沿原生 CDI 主例跟踪设备全名如何从 CRI 请求变成 OCI 修改，说明规格生成、名称解析、配置应用与容器启动各由谁完成；再根据 handler、模式和输入辨认 JIT CDI、包装层读取持久 CDI 与 legacy Hook 路径。
4. 用 UUID 和同节点的 PCI BDF 对齐主机管理索引、设备节点与 CUDA 进程序号，推导单卡注入、双卡反序和进程掩码变化后的身份。
5. 给定同一轮容器交付记录，找出最早有证据支持的失败点，选择一项能区分剩余原因的检查，并说明修复后怎样复核到实际计算。

相邻篇目的关系是“应用需要什么 → OCI 怎样表达这些需求 → CDI 怎样生成这些修改 → 其他运行时路径由谁修改 → 怎样确认注入的是同一张卡 → 怎样用证据定位与复核”。第 11 章向前接设备发现、资源计数与选卡，说明 CDI 全名如何由 Device Plugin 或 DRA 路径产生；本章不把规格中存在设备解释为库存可分配。

## 贯穿案例与技术口径

- 主例为 `node-10`：Linux x86_64、rootful containerd、cgroup v2、普通非特权容器、两张未切分 H100。A/B 的教学 UUID 分别为 `GPU-aaaaaaaa…` 与 `GPU-bbbbbbbb…`，PCI BDF 分别为 `0000:41:00.0` 与 `0000:81:00.0`。本次主机管理索引为 0/1，假定对应节点为 `/dev/nvidia0`、`/dev/nvidia1`；编号恰好相同，不把这个对应关系推广到跨启动场景。主例只把 B 交给容器。
- 镜像沿用第 03 章的预编译 `probe-sm90`：共享 CUDA Runtime 随镜像提供，探针让 H100 的一个线程写入整数 7，再同步并拷回校验。完整健康规格还提供与驱动匹配的计算、NVML 用户态库和所需设备节点；正文 YAML 是为解释合并规则而裁剪的教学材料，省略项明确标出。所有标识、配置和记录均为教学推演，不声称已经实测。
- 版本锚点为 NVIDIA Container Toolkit `1.18.2`、containerd `2.3.0`、CDI `1.1.0`、CRI API `v0.36.0` 和 CUDA `13.2.1` 归档文档。OCI 字段与 Hook 生命周期引用 Runtime Spec `1.2.1` 作稳定机制说明，不把实际 bundle 的 `ociVersion` 或目标 runc 版本固定为 `1.2.1`。版本默认值、模式选择和配置路径随论断注明；生成文件的实际 `cdiVersion`、挂载列表与设备名仍以目标环境为准。
- 正常路径与模式对照使用 Mermaid 和表格。沿用 `fig-10-02-01`、`fig-10-05-01`，不新增生成插画；修订后打开原图核对对象、边界、编号与图注。第 02 图只表示在 Unix 权限和其他安全策略已允许时改变 cgroup 设备规则的结果，第 05 图只表示两个进程重排同一组完整 GPU。

## 核心依据与范围边界

- [NVIDIA Container Toolkit 1.18.2 架构](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/1.18.2/arch-overview.html)、[CDI 支持](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/1.18.2/cdi-support.html) 与固定版本源码用于核对组件和模式；[1.18.0 发行说明](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/1.18.0/release-notes.html) 用于限定默认行为变化。
- [containerd 2.3.0 CRI 配置](https://github.com/containerd/containerd/blob/v2.3.0/docs/cri/config.md)、[CRI 创建实现](https://github.com/containerd/containerd/blob/v2.3.0/internal/cri/server/container_create_linux.go) 与 [CRI v0.36.0](https://github.com/kubernetes/cri-api/blob/v0.36.0/pkg/apis/runtime/v1/api.proto) 用于核对请求和启动时序；[CDI 1.1.0 规范](https://github.com/cncf-tags/container-device-interface/blob/v1.1.0/SPEC.md) 与 [OCI 1.2.1 Linux 配置](https://github.com/opencontainers/runtime-spec/blob/v1.2.1/config-linux.md#devices) 用于核对配置展开。
- [Linux cgroup v2 设备控制](https://docs.kernel.org/6.18/admin-guide/cgroup-v2.html#device-controller)、[CUDA 13.2.1 环境变量](https://docs.nvidia.com/cuda/archive/13.2.1/cuda-programming-guide/05-appendices/environment-variables.html) 与 [NVIDIA SMI](https://docs.nvidia.com/deploy/nvidia-smi/index.html) 用于核对权限、枚举与设备标识。
- 本章不展开 Kubernetes 如何选卡、GPU Operator 安装、MIG/共享隔离、RDMA 设备注入或完整驱动兼容矩阵。这些分别由第 11—14 章和第 03 章承担。`RuntimeClass` 只讲到能识别本次 handler；`ctr`、`nerdctl`、Docker 不混入 CRI 主例。
