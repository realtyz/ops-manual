# 10 GPU 如何进入容器

## 范围、前置知识与读者目标

- **范围**　沿单节点上一次 Linux 容器的创建与启动，解释已选定的 NVIDIA GPU 怎样被交给容器，以及应用怎样通过宿主机驱动使用它。主线为 containerd 的 CRI 与 runc，以原生 CDI 为主例，另读 NVIDIA Runtime 的即时 CDI 和 legacy Hook 两条路径。示例限定 Linux x86_64、rootful containerd、cgroup v2、两张完整 GPU、普通非特权容器。
- **必要前置**　读者会区分镜像和容器进程，能读基本的 Linux 文件权限和容器启动配置，知道 CUDA 应用经用户态驱动访问 GPU。开篇补齐容器共享主机内核、设备文件的主次设备号、文件挂载与设备访问规则，以及 CRI 请求、OCI 运行时配置的关系。读者可以用示意配置和教学记录离线推导。
- **跨章分工**　第 03 章提供驱动、CUDA 库与版本兼容的判断方法，本章把它们放到主机和容器两侧。第 11 章解释 Kubernetes 选定哪张卡、怎样传递分配结果，以及 Device Plugin 与 DRA 的差别。第 12 章接手组件安装与协调，第 13 章扩展到 RDMA，第 14 章展开 MIG、共享和隔离，第 18—19 章处理跨层故障与升级。`RuntimeClass` 在本章仅用于解释运行时选择。
- **读完应能独立判断**　给定镜像与宿主机清单，能列出 CUDA 计算和 NVML 查询分别需要的设备、权限与库。给定容器创建请求、运行时配置和 CDI 文件，能追踪由谁在哪一步改写 OCI 配置，并解释为何有 CDI 文件仍可能用不到 GPU。给定主机、容器和应用的枚举输出，能按 UUID 或同节点 PCI BDF 对齐同一张卡。给定一次失败记录，能找出最早失败的层次，并选取一项能区分候选原因的证据。

## 贯穿场景与版本口径

- **场景**　同一台主机两张 H100，按示例 UUID 分别简称 A、B。假设本次宿主机 `nvidia-smi` 将 A、B 列为 `0`、`1`，PCI BDF 分别为 `0000:41:00.0`、`0000:81:00.0`。主例直接给容器创建层“选 B”的结果。使用同一镜像和预编译的最小 CUDA 探针，对照无注入、只注入 B、注入 A 和 B 后用进程环境重排三种情况。探针计划记录设备数或枚举错误、设备序号和身份、选卡及最小计算的同步结果。
- **版本锚点**　Toolkit 用 `1.18.2` 的发行说明和源码，重点标出 `1.18.0` 的默认模式与 CDI 刷新分界。containerd 用 `2.3.0` 的 `version = 3` 配置和 CRI 实现。两个源码标签均引用 CDI `1.1.0` 库，示例仍以实际文件的 `cdiVersion` 和字段为判断对象。CUDA 枚举语义取 `13.2.1` 归档文档。以上是核对源码和配置的锚点，案例运行记录与镜像、驱动的具体组合待环境核实。 [Toolkit 1.18.2 发行说明](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/1.18.2/release-notes.html) · [Toolkit 1.18.2 依赖](https://github.com/NVIDIA/nvidia-container-toolkit/blob/v1.18.2/go.mod) · [containerd 2.3.0 CRI 配置](https://github.com/containerd/containerd/blob/v2.3.0/docs/cri/config.md) · [containerd 2.3.0 依赖](https://github.com/containerd/containerd/blob/v2.3.0/go.mod) · [CUDA 13.2.1 环境变量](https://docs.nvidia.com/cuda/archive/13.2.1/cuda-programming-guide/05-appendices/environment-variables.html)
- **材料口径**　两卡编号、配置摘录和故障对照用于教学推演。正文若采用实测，随记录给出来源、发行版与内核、驱动和 GPU、Toolkit、containerd 与 runc 版本、cgroup 驱动、镜像摘要、请求和执行身份。依赖与启动时序用 Mermaid，编号与故障证据用表格。若正文需要单独强调宿主机、容器和物理 GPU 的空间边界，再按配图规范准备可独立复制的插画提示词。

## 01 CUDA 计算依赖哪些主机与镜像组件

- **问题与预期结论**　镜像有 CUDA，宿主机也能运行 `nvidia-smi`，为什么还要配置 GPU 注入？读者应能画出应用、CUDA Runtime、用户态驱动、宿主机内核驱动和物理 GPU 的依赖链，并分别判断管理查询和实际计算的最低验证范围。
- **解释顺序**　从容器内已编译的应用跟踪一次 CUDA 调用。镜像通常携带应用及所需的 CUDA Runtime（`libcudart` 可静态链接）和其他应用库，用户态驱动通常通过运行时注入进入容器，容器进程通过设备节点与宿主机正在运行的 NVIDIA 内核驱动交互。另画 `nvidia-smi` → NVML 的管理支路，指出两条路径需要的可执行文件和驱动库不同。接着区分“文件在镜像中”“启动时挂入文件”“进程实际加载了文件”。若使用前向兼容包或改变库搜索路径，实际加载来源可能变化。驱动版本矩阵、设备代码和 PTX JIT 规则回到第 03 章。
- **支撑材料**　拟用一张主机内核／容器文件系统依赖图标明 `libcuda.so.1`、`libcudart`、`libnvidia-ml.so.1` 与 GPU。用镜像构建依赖和 `readelf -d` 辨认动态依赖，用容器挂载及 `LD_DEBUG=libs,files` 核对实际驱动库路径，尤其是运行时才加载的库。用同一镜像的 NVML 查询、CUDA 枚举、最小 Kernel 完成三项结果界定每项能证明的能力。 [NVIDIA Linux 驱动组件清单](https://download.nvidia.com/XFree86/Linux-x86_64/580.65.06/README/installedcomponents.html) · [CUDA 前向兼容包](https://docs.nvidia.com/deploy/cuda-compatibility/forward-compatibility.html) · [NVIDIA SMI 与 NVML](https://docs.nvidia.com/deploy/nvidia-smi/index.html)

## 02 设备出现在 `/dev` 后，进程还要通过哪些检查

- **问题与预期结论**　为什么能看到 `/dev/nvidia*`，打开设备却可能失败？读者应能分开设备节点、设备访问规则、Unix 权限与安全策略，知道权限问题需要哪项运行证据才能归因。
- **解释顺序**　先区分每张卡的字符设备（`/dev/nvidiaN`）与可能一同需要的控制、UVM 节点（如 `/dev/nvidiactl`、`/dev/nvidia-uvm`），清单按功能与环境取值。再将 OCI 的 `linux.devices` 与 `linux.resources.devices` 分开，前者描述设备怎样出现，后者描述哪些类型、主次设备号和 `r/w/m` 操作被允许。cgroup v2 的设备控制由 cgroup BPF 实现。即使节点存在，进程身份和文件模式、有效的设备规则、SELinux 或 AppArmor 等策略仍可能改变访问结果。用“节点缺失”和“节点存在但打开被拒”两条分支进入排障。共享与隔离保证由第 14 章展开。
- **支撑材料**　拟给出同一个字符设备的 `linux.devices[]` 与 `linux.resources.devices[]` 对照，联读 `ls -l` 或 `stat` 得到的设备号、属主和权限，实际进程的 UID/GID、`/proc/<pid>/cgroup` 与目标设备的 `openat` 结果。若是 `EPERM` 或 `EACCES`，再取该 cgroup 的有效设备策略与安全审计记录，结合失败的路径和操作归因。图中把挂载/创建设备、授权和应用打开分成三个检查点。 [OCI Linux 设备配置](https://github.com/opencontainers/runtime-spec/blob/v1.2.1/config-linux.md#devices) · [Linux cgroup v2 设备控制](https://docs.kernel.org/6.18/admin-guide/cgroup-v2.html#device-controller) · [NVIDIA Toolkit 故障示例](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/1.18.2/troubleshooting.html)

## 03 containerd 如何接上 NVIDIA Container Toolkit

- **问题与预期结论**　节点装好了 Toolkit，为什么容器仍可能走普通 runc 路径？读者应能从运行时配置判断容器是否经过 NVIDIA 包装层，并区分 containerd、shim、runc、Toolkit CLI、Runtime、Hook 和 `libnvidia-container` 的职责。
- **解释顺序**　从 CRI 创建请求和运行时选择开始。containerd 组装 OCI 配置，按选定的 runtime handler（未指定时用配置的默认运行时）选运行时配置，经 `io.containerd.runc.v2` 对应的 shim 调用低层可执行文件。用 `BinaryName` 对照直接调用 `runc` 与调用 `nvidia-container-runtime` 包装层。用 `RuntimeClass.handler` 解释 Kubernetes 选择入口，资源分配留到第 11 章。再沿明确设置 `nvidia-container-runtime.mode=legacy` 的对照追踪，包装层修改 OCI 配置并交给 runc，runc 在应用启动前执行 `prestart` Hook，Hook 按请求调用 `nvidia-container-cli`，由 `libnvidia-container` 提供发现与配置能力。`nvidia-ctk` 负责配置和生成 CDI 描述。最后把 legacy 中的 `NVIDIA_VISIBLE_DEVICES` 选卡与 `NVIDIA_DRIVER_CAPABILITIES` 选驱动功能分开，以 `compute` 和 `utility` 说明 CUDA 与 NVML/`nvidia-smi` 需要的文件可能不同。进入包装层后实际走哪种模式，在第 04 节对照。
- **支撑材料**　拟摘录 `version = 3` 下 `plugins."io.containerd.cri.v1.runtime".containerd` 的 `default_runtime_name`、`runtimes.nvidia.runtime_type`、`runtimes.nvidia.options.BinaryName`，以及 `/etc/containerd/config.toml` 的 `imports` 和 Toolkit 生成的 `/etc/containerd/conf.d/99-nvidia.toml`。用同一请求的 handler、配置落点和运行时日志判读“已登记”与“本次选中”。再以 Mermaid 时序图画出 legacy 的包装层、Hook 执行点和应用入口。配置按 CRI 解释，单独运行 `ctr` 或 `nerdctl` 的结果只用作各自入口的证据。 [NVIDIA Toolkit 架构](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/arch-overview.html) · [Toolkit 1.18.2 配置 containerd](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/1.18.2/install-guide.html#configuring-containerd-for-kubernetes) · [containerd 2.3.0 CRI 配置](https://github.com/containerd/containerd/blob/v2.3.0/docs/cri/config.md) · [Kubernetes RuntimeClass](https://kubernetes.io/docs/concepts/containers/runtime-class/) · [NVIDIA 驱动功能变量](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/1.18.2/docker-specialized.html#driver-capabilities)

## 04 CDI 怎样把设备名变成 OCI 配置

- **问题与预期结论**　节点已有 `/var/run/cdi/nvidia.yaml`，为什么普通容器没有 GPU，换一个请求又可能在创建时失败？读者应能区分生成、请求、解析和应用四个环节，判断是没有设备请求、名称解析失败、还是选择了另一条注入路径。CDI 负责按已指定的设备准备容器，选卡、记账与避免重复分配由上层负责。
- **解释顺序**　先读 `cdiVersion`、`kind: nvidia.com/gpu`、`devices[].name` 和两层 `containerEdits`。以 `nvidia.com/gpu=<B 的 UUID>` 为请求，说明规格顶层的公共修改和 B 的专用修改怎样合并到 OCI，逐项对应设备节点及访问规则、库挂载、环境变量和可选 Hook。然后跟踪原生 CDI。`nvidia-ctk` 生成节点上的规格，containerd CRI 按目录扫描并解析 `ContainerConfig.CDIDevices` 中的全名，在交给低层 runtime 前完成 OCI 修改，低层仍可直接用 runc。用同名可解析、请求省略、请求拼错三份材料对照。版本不兼容、目录未被扫描、规格过期或路径缺失都要在相应环节验证，规格列出设备仅说明节点有一份描述。
- **已核对的路径与版本**　containerd 2.0 起 CRI 默认启用 CDI，`2.3.0` 仍有 `enable_cdi` 与 `cdi_spec_dirs`，其 CRI 源码会拒绝在显式禁用 CDI 时提交的非空 `CDIDevices`。Toolkit 自 `1.18.0` 起在支持相应 systemd 单元的安装中自动维护 `/var/run/cdi/nvidia.yaml`，触发条件含 Toolkit/驱动安装、升级与开机。卸载驱动、重配 MIG 需要另行处理刷新。Toolkit `1.18.2` 中，NVIDIA Runtime 在本章 NVML 平台、`mode=auto` 且使用普通 GPU 选择器时走 JIT CDI，按请求在内存生成修改，无须先读取节点的持久规格。全限定 CDI 名可让该包装层的 `auto` 转到 `cdi` 模式，由包装层查找规格，这与 containerd 原生消费是不同入口。显式 `legacy` 仍是支持但已弃用的 Hook 路径。CDI 描述也可含辅助 Hook，判断路径时要看调用者及具体 Hook。对照分别采集，避免旧 Hook 与 CDI 同时作用使证据混杂。 [containerd 2.0 默认值变更](https://github.com/containerd/containerd/blob/v2.0.0/docs/containerd-2.0.md#cdi-is-now-enabled-by-default) · [containerd 2.3.0 CRI 实现](https://github.com/containerd/containerd/blob/v2.3.0/internal/cri/server/container_create_linux.go) · [Toolkit 1.18.2 CDI 支持](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/1.18.2/cdi-support.html) · [1.18.0 发行说明](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/1.18.0/release-notes.html) · [1.18.2 模式选择源码](https://github.com/NVIDIA/nvidia-container-toolkit/blob/v1.18.2/internal/info/auto.go) · [NVIDIA JIT CDI 说明](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/cdi-support.html#jit-cdi-mode)
- **支撑材料**　拟并列裁剪后的 CDI YAML、CRI 请求中的 `CDIDevices[].name` 和 OCI 修改前后字段。以 `/etc/cdi`、`/var/run/cdi` 与有效 `enable_cdi` 配置核查 containerd 的消费条件，用 `nvidia-ctk cdi list` 与 `journalctl -u nvidia-cdi-refresh.service` 检查本机规格和生成过程，再读同一容器的 CRI 创建结果确认消费。另做一张“原生 CDI／包装层 JIT CDI／显式 legacy”对照表，逐列写请求输入、修改配置者、修改时机和主要证据。通过包装层读持久规格的 `cdi` 模式在表下注明。Device Plugin、DRA 产生和传递设备选择的具体过程留给第 11 章。 [CDI 1.1.0 规范](https://github.com/cncf-tags/container-device-interface/blob/v1.1.0/SPEC.md) · [CDI 到 OCI 的转换实现](https://github.com/cncf-tags/container-device-interface/blob/v1.1.0/pkg/cdi/container-edits.go) · [containerd 2.3.0 CRI 配置](https://github.com/containerd/containerd/blob/v2.3.0/docs/cri/config.md) · [Toolkit 1.18.2 CDI 排查](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/1.18.2/cdi-support.html)

## 05 主机、容器和 CUDA 进程怎样对齐同一张卡

- **问题与预期结论**　主机上的 1 号 GPU 为什么在程序里是 `cuda:0`？同一个容器的两个进程又为何可能对 `cuda:0` 指向不同设备？读者应能用 UUID 验证身份，并判断差异来自启动时设备注入、管理工具枚举还是 CUDA 进程的筛选和排序。
- **解释顺序**　先建立宿主机清单，区分 NVML/`nvidia-smi` 的索引、设备文件的次设备号、PCI BDF 和 UUID。再对齐启动时选定的 B（CDI 全名或 legacy 的 `NVIDIA_VISIBLE_DEVICES`）。假设相关权限及库齐备且进程未进一步筛选，只注入 B 时 CUDA 的唯一设备序号是 0。注入两张时用完整 UUID 设置 `CUDA_VISIBLE_DEVICES=<B>,<A>`，预期进程序号 0、1 分别指向 B、A。设为空字符串时 CUDA 看不到设备，已有设备访问配置仍在，NVML 管理查询单独观察。补充 `CUDA_DEVICE_ORDER` 会改变默认枚举、重启后工具索引可能变动，UUID 用于稳定关联，同节点同次采集的 BDF 用于校验物理位置。进程变量用于枚举与选择，实际访问边界由设备授权等内核机制执行。MIG 标识与共享场景的特殊情况留到第 14 章。
- **支撑材料**　拟给出同一时点的宿主机与容器 `nvidia-smi --query-gpu=index,uuid,pci.bus_id,driver_version --format=csv`，用 CUDA 探针的 `cudaGetDeviceCount`、`cudaGetDeviceProperties` 和 `cudaDeviceGetPCIBusId` 对齐设备。做三行映射表，从单卡注入、双卡反序、进程掩码为空依次推导 CUDA 可见数量和 UUID 次序。保留管理工具的实际索引列用于对照，预期结果按 UUID 表达。 [NVIDIA SMI 设备标识及查询](https://docs.nvidia.com/deploy/nvidia-smi/index.html) · [CUDA 13.2.1 枚举环境变量](https://docs.nvidia.com/cuda/archive/13.2.1/cuda-programming-guide/05-appendices/environment-variables.html#cuda-visible-devices) · [CUDA 13.2.1 Runtime 设备 API](https://docs.nvidia.com/cuda/archive/13.2.1/cuda-runtime-api/group__CUDART__DEVICE.html)

## 06 从首个失败点追查容器 GPU 不可用

- **问题与预期结论**　宿主机能看到 B，容器里却报错，应先查什么？读者应能先区分创建失败和应用启动后的失败，再沿请求、OCI 修改、节点权限、库加载、CUDA 枚举与计算逐层收窄范围。
- **解释顺序**　先按节点和时间确认 B 的主机基线，并记录容器 ID 或创建请求标识。创建失败先读创建错误、实际 handler 和注入路径，原生 CDI 分支核对名字和规格，legacy 或 JIT CDI 分支核对 NVIDIA Runtime 模式与日志。容器已启动则核对节点存在及打开结果、驱动库实际解析路径、CUDA 进程环境、选卡与同步结果。`nvidia-smi` 命令缺失时区分 PATH、管理工具和 NVML 依赖，再用 CUDA 探针单独检查计算。管理查询成功但首次计算失败时，看具体 API 返回值，并按第 03 章的方法检查驱动、实际库及设备代码。固定镜像、用户、节点与目标 UUID，每次只改变一个已定位的条件，复测失败检查点及其下游。
- **支撑材料**　以一次成功的原生 CDI 启动为基线。拟用下表的独立教学记录练习，每条保留同节点时间、容器标识、请求的 GPU 身份、运行时路径、错误发生阶段和原始错误字段。创建阶段的具体措辞取所选版本源码或实机日志，系统调用保留路径和 errno，CUDA 探针标出调用名及返回值。 [containerd 2.3.0 创建阶段源码](https://github.com/containerd/containerd/blob/v2.3.0/internal/cri/server/container_create_linux.go) · [Toolkit 1.18.2 调试日志](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/1.18.2/troubleshooting.html#generating-debugging-logs) · [Linux cgroup v2 设备控制](https://docs.kernel.org/6.18/admin-guide/cgroup-v2.html#device-controller) · [CUDA 13.2.1 错误处理](https://docs.nvidia.com/cuda/archive/13.2.1/cuda-runtime-api/group__CUDART__ERROR.html)

## 待核实项

- **配置与实测**　机制、默认值和版本分界已按上列资料核对。真实 H100 环境上的镜像摘要、驱动与 runc 完整版本、CDI 实际生成的 `cdiVersion`、设备名、节点和挂载列表，以及最小探针的返回值待采集。对照时分别保留 containerd 组装的配置、NVIDIA 包装层或 Hook 的修改及容器中的生效结果，记录各份材料所处的时点。环境不可用时使用标明假设的配置推演和教学记录。
- **错误与诊断工具**　请求无法解析、库加载失败及权限拒绝的错误原文按目标版本与失败阶段校验。实机如有权限层问题，再记录 cgroup 驱动、进程身份、安全策略和审计证据。`nvidia-ctk cdi list` 的结果与 containerd 自身的规格目录及创建记录分别采集。
