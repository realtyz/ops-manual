# 用交付材料完成综合推演

## 一份可以读到结论的交付材料

以下是**独立的自拟交付材料**。沿用导读的 ct-a、U0/U1、驱动 570.124.06 和 CUDA 12.8.1 镜像，主机同一计算探针已通过。容器 C-F 采用 NVIDIA Runtime **legacy** 模式，普通 rootful 容器，无 privileged、无用户 namespace 重映射，不叠加原生 CDI。本题明确给定其文件权限、设备访问规则与 LSM 均允许所需操作。

```text
[请求]
runtime_handler=nvidia
NVIDIA_VISIBLE_DEVICES=GPU-22222222-2222-4222-8222-222222222222
NVIDIA_DRIVER_CAPABILITIES=compute,utility
CUDA_VISIBLE_DEVICES=unset

[创建记录]
effective_binary=/usr/bin/nvidia-container-runtime
mode=legacy; prestart_hook=completed successfully
entrypoint_started=yes

[交付与装载核对]
selected_gpu_node=/dev/nvidia1, char 195:1
required_common_interfaces=present and allowed
unselected_gpu_node=/dev/nvidia0 absent
loaded_libcudart=/usr/local/cuda/lib64/libcudart.so.12 (12.8.90)
loaded_libcuda=/usr/lib/x86_64-linux-gnu/libcuda.so.570.124.06
loaded_nvml=/usr/lib/x86_64-linux-gnu/libnvidia-ml.so.570.124.06

[管理查询]
uuid=GPU-22222222-2222-4222-8222-222222222222
pci.bus_id=00000000:B1:00.0

[计算探针]
cuda_count=1
selected_cuda_ordinal=0
selected_uuid=GPU-22222222-2222-4222-8222-222222222222
allocate=ok h2d=ok launch_check=ok sync=ok d2h=ok
expected=[11,22,33,44]
actual=[11,22,33,44]
verify=PASS
```

其中 `loaded_*` 是对实际装载记录的教学归纳，不是 `ldd` 的逐字输出；“公共接口完整且允许”是本题给定条件，不要求读者从一个省略清单反推完整性。材料到达同步与结果校验，读者无需再运行命令才能判断本次计算是否成功。

## 独立推演

各题改变条件时，从该题重新开始，不累计上一题的变化。先写结论及其依据，再核对后面的参考分析。

1. 画出 C-F 中应用到 GPU 的调用关系。标明哪些内容来自镜像，哪些由主机交付，哪个内核由容器和主机共享。指出 CUDA Toolkit 与 Container Toolkit 各处在哪个职责范围。
2. 建立四项映射：宿主机管理 index、设备节点、容器 CUDA ordinal、完整 UUID。本轮 `cuda:0` 究竟是哪张卡？为何不能据此去排查 `/dev/nvidia0`？
3. 主机没有 `nvcc`，C-F 仍得到 PASS；这一现象是否自洽？若换成动态链接了另一 Runtime 主版本、镜像却没提供该库的程序，最早需要检查哪个阶段？
4. 只将 handler 改为普通 `runc`，没有原生 CDI 请求，也没有独立注入 Hook，保留 NVIDIA 环境变量。它能否据这些变量重建 C-F 的 GPU 运行环境？缺失发生在哪一环？
5. 只把 legacy 功能集合改为 `utility`，并给定容器内 NVML 可用、Driver API 库未交付、Runtime 库仍在。预测管理查询与 CUDA 初始化的差异，给出修复后要复核的两个观察点。
6. 保持设备路径和库不变，明确给定设备策略拒绝 `char 195:1 rw`，文件 mode 为 0666，UID 为 0。为什么再做一次 `chmod` 无效？现在已有证据支持哪层故障？
7. 改用原生 CDI。`enable_cdi=true`，描述中名称存在，当前主机源文件存在，消费者支持该描述的 `cdiVersion`。但请求没有携带任何 CDI 设备名。能否由“目录中有 G1 的描述”推出 G1 将被交付？还缺哪个输入？
8. 另建交付两卡的 C-G；明确给定未过滤时 CUDA 顺序 `[U0,U1]`。新进程设置 `CUDA_VISIBLE_DEVICES=1,0`。写出 `cuda:0/1` 映射。若只设为 U1 完整 UUID，CUDA 看到几张卡？这是否撤销了容器对 U0 的设备访问授权？
9. 一份 CDI 文件同时包含 `nvidia.com/gpu=1` 与 `nvidia.com/gpu=GPU-22222222-2222-4222-8222-222222222222`，二者设备节点都为 195:1。两个容器分别请求这两个名称。能否因此认定它们各独占一张不同的物理卡？CDI 本身能否阻止这个冲突？
10. CDI 名称匹配 U1，创建却发现挂载源 `libcuda.so.535.104.05` 不存在，主机现在是 570.124.06。应用入口尚未执行。应先改应用的 CUDA ordinal，还是更新描述与创建环境？给出完整修复验证顺序。
11. 只保留 C-F 的管理查询记录，删除计算探针结果。哪些结论仍有依据？能否补写“CUDA 计算通过、NCCL/RDMA 可用”？再给定另一记录只有 `launch_check=ok`，但 `sync=failed`、没有读回结果，能否记为计算成功？
12. 另一运行中 legacy 容器在 daemon-reload 后出现 NVML Unknown Error，主机探针仍通过。给出应核对的机制和一项完成归因所缺的证据。最后说明：RuntimeClass 指向 `nvidia`，与 Kubernetes 已为该容器分配 U1 之间，还隔着哪类职责？

## 参考分析

### 1. 应用依赖跨过容器文件视图

`gpu-probe → libcudart → libcuda → 设备接口 → 宿主机内核驱动 → G1`。应用、设备代码、Runtime 和主机语言运行依赖来自镜像；配套 Driver API 库、设备接口及访问条件由主机和容器接入过程交付。容器进程使用主机内核。CUDA Toolkit 服务构建与 CUDA 库交付；Container Toolkit 服务运行时接入。本例不需要在容器内启动另一套内核驱动。

### 2. 数字不同，UUID 相同

本轮是 `host index 1 → /dev/nvidia1 (195:1) → cuda ordinal 0 → U1`，完整 UUID 为 `GPU-22222222-2222-4222-8222-222222222222`。CUDA 只有一个设备，从 0 开始编号；这不重命名设备文件。映射的依据是 UUID 和当前 Bus ID，而不是数字相等。

### 3. 编译器和运行依赖分工成立

自洽：程序已经构建，镜像提供其动态 Runtime，主机提供兼容驱动。若缺少程序需要的另一 Runtime 动态库，应先检查主机程序的动态装载阶段；程序可能在到达 CUDA 初始化前就退出。把主机装有 `nvcc` 作为修复，未必改变容器文件视图中的依赖。

### 4. 变量必须有消费者

不能。题目排除了原生 CDI 和独立 Hook，普通 runc 不解析这些 NVIDIA 私有变量。缺口在请求所选运行时入口到 GPU 注入之间。应选择已配置的 NVIDIA handler 或建立完整 CDI 路径，再检查设备、规则、实际库装载及应用结果。

### 5. 管理路径与计算路径分开

按题设 NVML 查询仍可成功，CUDA 因 Driver API 交付缺失无法完成初始化。将功能集合补齐并重新创建后，先复核实际装载的 `libcuda` 来自正确主机驱动，再复核枚举到 U1 并完成同步和数值校验。仅重新运行 `nvidia-smi` 没有覆盖改变的计算路径。

### 6. 文件权限不能覆盖设备拒绝

0666 已经允许此 UID 按文件权限读写，失败由明确给定的设备策略引起。`chmod` 改不到那条规则，UID 0 在本题普通容器条件下也不自动豁免。已有材料支持定位运行时设备允许规则的生成、应用或后续变化；无需据此推断驱动硬件已损坏。

### 7. 描述不会主动选择自身

不能推出。还缺本轮请求的 CDI 设备选择，例如 U1 对应的完整 CDI 名称，以及该输入确实到达消费者的证据。文件可读、版本支持、源文件有效，是执行描述的条件；它们没有表达这次容器要使用哪一个设备。

### 8. 进程枚举可以重排

`1,0` 得到 `cuda:0=U1`、`cuda:1=U0`。只设 U1 完整 UUID 时 CUDA count 为 1、`cuda:0=U1`。两种设置均不撤销容器创建时对 U0 的设备授权；不能把 CUDA 进程筛选用作容器的设备访问安全边界。

### 9. 别名不增加容量

两个名称都指向 195:1，即同一 G1。不能据名称不同宣称两张物理卡或各自独占。CDI 将名称解析为运行环境，不提供资源所有权和冲突仲裁；需要上层资源分配者维持一致账本。两个不同名称同时请求同卡，还可能产生重复修改，进一步说明不应按名称条目数计算 GPU 容量。

### 10. 先修复已经确定的创建失败

先按当前驱动状态重生成描述，核对名称映射与所有源文件，确认实际消费者读取的是新文件并能解析；再新建容器，核对设备规则、挂载和实际库版本；最后枚举 U1 并运行同步及结果校验。入口尚未运行，修改应用 ordinal 无法修复缺失的挂载源。

### 11. 每份证据都有确定范围

保留的记录支持本轮管理路径查到了 U1，不支持已执行 CUDA Kernel，更没有覆盖 NCCL/RDMA。另一个记录只说明提交检查成功，同步已失败；没有完成与结果证据，不能标为计算成功。即使本章完整探针 PASS，也只覆盖给定计算，不外推通信与性能。

### 12. 访问变化与资源所有权各有负责者

应核对 legacy Hook 修改未纳入低层运行时跟踪、后续容器更新改变设备访问条件的已知机制。还缺更新前后规则差异或其他能把拒绝与本轮更新对应的证据；错误字符串和时间相邻仅能指导调查。RuntimeClass 只选择运行时 handler，设备发现、健康上报、数量记账和具体 U1 分配属于上层设备管理与分配流程，第 11 章沿此继续。

本章的运行环境链条已经从设备选择走到计算结果。下一章把起点向前移，解释 Kubernetes 怎样知道有卡、怎样表达请求，并把具体设备的选择交给这里已经建立的注入过程。
