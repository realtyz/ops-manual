# NCCL 如何组织 GPU 间的通信

四个 Rank 都提交了 AllReduce，哪一块数据先发给谁？看到日志里的 `Bootstrap` 和 `NET/IB`，分别能确定什么？同一次测试的 `algbw` 与 `busbw` 为什么不同？本章把第 05 章的集合通信语义和第 06—07 章的数据路径连接起来，解释通信库怎样把一次共同操作落实到设备上。

本章的学习任务是：**区分启动器、框架与 NCCL 的职责；沿初始化和 CUDA Stream 解释完成条件；手算 Ring 的数据与流量，解释 Tree 的取舍；将 Rank、设备和传输日志对应起来；复算 nccl-tests 指标，并判断单链路与集合测试各自支持的结论。**

## 必要前置与章节边界

已有 Linux 进程、动态库、网络接口和 Kubernetes 基础即可。[第 02 章](../02_GPU如何计算与显存/00_导读.md)建立 Kernel、Stream 和异步完成；[第 04 章](../04_单机多卡与GPU数据路径/00_导读.md)建立设备身份、PCIe/P2P 与共享预算；[第 05 章](../05_为什么一个作业需要多张GPU/00_导读.md)建立 Rank 和集合操作的输入输出；[第 06 章](../06_从普通网络通信走向RDMA/00_导读.md)建立 RDMA 与显存直达条件。

[第 07 章](../07_InfiniBand_RoCE与集群网络拓扑/00_导读.md)主责 InfiniBand、RoCE 与网络拓扑。本章就近唤起必要含义：RoCEv2 在以太网/IP 上承载 RDMA；IP 接口和 RDMA 设备是不同命名空间；同一端口的单向容量会被多条通信流共享。阅读不依赖先自行完成网络实验。

本章完整解释 NCCL 的通信组织、阶段、路径与测试读法。交换机寻址、拥塞控制和多 Rail 设计归第 07 章；数据供给归第 09 章；容器和 Pod 的设备接入归第 10、13 章；集群观测、故障处置与升级归第 17—19 章。本章保留支持当前判断的证据链，不展开安装教程、参数大全或训练算法。

## 教学模型与材料约定

新作业 `job-08` 使用 `nccl-a`、`nccl-b` 两台宿主机，每机两张独占、未切分 NVIDIA GPU、一个 RDMA 端口。每个进程使用一张 GPU，四个成员属于通信组 W。**这不是前章的节点，编号、速率和能力不继承。** 每机两张 GPU 与 NIC 连接同一 PCIe Switch，基线给定本机 GPU P2P 和双端 GPUDirect RDMA 可用，不设置 NVLink、NVSwitch、网络归约卸载或跨机 NVLink；完整身份表见第一篇。

图、拓扑、日志式片段、测试输出和数值均为**自拟教学材料**，没有 GPU/RDMA 实测。日志字段依照指定版本文档及源码整理，删掉的行不隐含成功。单位统一为 `KiB = 2^10 B`、`MiB = 2^20 B`、`GB/s = 10^9 B/s`、`Gb/s = 10^9 bit/s`；数值题给定有效速率、方向与并发条件。小数组只用于手算，不推断真实性能。

机制与字段基线为 **NCCL 2.31.2**（源码 tag `v2.31.2-1`）；测试参数和换算核对 **nccl-tests v2.19.7**（commit `1a65d7f0514b8da6a61ae235d1c5f38549478e29`）。两个项目的版本号独立；它们是阅读依据，未构成经过实测的部署组合。资料核对日期：**2026-11-08**。本章聚焦主机 API 发起的普通集合通信；其他算法和硬件加速路径在相关处说明边界，不把 Ring 当作所有调用的固定实现。
