
本题沿用 `gpu-a`、`gpu-b` 两台服务器。Rank 0、1 在 A，Rank 2、3 在 B，每个 Rank 使用一张有独立显存的 GPU。机内可用 PCIe P2P。每台仅有一个 200 Gb/s 全双工 RoCEv2 数据端口 `mlx5_0:1`，另有 `eno1` 用于 TCP 引导。下列记录均为教学材料，可直接做纸面推演。

## 练习材料

应用先用四个 `float` 数组 `[1, 2]`、`[3, 4]`、`[5, 6]`、`[7, 8]` 做一次求和探针，四个 Rank 都收到了正确结果。随后换一个输入批次，组和调用参数保持一致，应用按相同顺序记录下一轮进度。

| 参与者 | 同组初始化 | 下一轮应用记录 |
| --- | --- | --- |
| Rank 0、1、2 | 均 `Init COMPLETE` | 调用 AllReduce 后成功返回，通信 Stream 上的完成 Event 尚未就绪 |
| Rank 3 | `Init COMPLETE` | 已确认应用的分支先等待本地输入，尚未进入这轮 AllReduce |

另有两轮独立完成的四卡基准，均用 `float` 求和，取独立收发缓冲区的结果列，并通过结果校验。每轮每 Rank 输入都是 64 MiB。两轮都确认只用一个 Ring 通道、相同协议和相同网卡，跨机边的收发两端均用 GDR。两轮的 NCCL Rank 到 GPU 的绑定相同。

| 轮次 | 核对后的通道顺序 | `size` | `time` | `#wrong` |
| --- | --- | ---: | ---: | ---: |
| 甲 | `0 → 1 → 2 → 3 → 0` | 67,108,864 B | 5,000 µs | 0 |
| 乙 | `0 → 2 → 1 → 3 → 0` | 67,108,864 B | 9,000 µs | 0 |

乙轮另取持续运行 64 MiB 消息的 2 秒窗口，A 端发送计数 `port_xmit_data` 增加 `11,200,000,000`，B 端的对应接收数量级相同，窗口内没有明显背景流量。另一次 perftest 的 GPU 缓冲轮验证了 `gpu-a` GPU 1 向 `gpu-b` GPU 0 的 8 MiB 单向 RC Write，载荷平均为 180 Gb/s。

1. 哪一层决定梯度做什么运算？启动器、NCCL 和 CUDA 各承担哪一步？算出求和探针的每 Rank 结果。若改为每个 Rank 只需完整归约结果的一块等长切片，应选什么集合操作，需要怎样准备输入？
2. 下一轮目前卡在哪个进度点？该先查哪个 Rank 的什么记录？假如该 Rank 随后提交成功，同轮的应用消费者在哪个条件满足后可以继续？
3. 对甲轮，从 Rank 0 的 `C0` 贡献出发，依次写出在哪些 Rank 做累加、哪里得到完整块、怎样交给另外三张卡。再把它放进一棵根为 0、子节点为 1 和 2、Rank 3 挂在 1 下的树，指出哪些传输可在同一轮完成，以及这个并行需要什么假设。
4. 按单通道四等分的 Ring 模型，计算甲、乙两轮 A → B 方向每次操作的字节量和按名义线速得到的耗时下界，并复算两轮的 `algbw`、`busbw` 和乙轮 A 端的端口速率。哪些证据支持共享端口限制？如何进一步验证？perftest 结果覆盖了哪些实际路径？如果乙轮某条跨机连接只有接收侧选中 GDR，画出这条边的载荷路径，并说明端口字节量是否会随之改变。

## 参考推理

1. 应用或框架决定梯度按何种规则合并，并提交对应缓冲区和参数。启动器把工作进程拉起来，NCCL 建立设备间通信关系并组织数据交换，CUDA 在输入依赖满足后执行 Stream 中的工作。四个 Rank 都得到 `[1+3+5+7, 2+4+6+8] = [16, 20]`。如每个 Rank 只需要归约后的一段，选 ReduceScatter。四个 Rank 必须各交出可分成四个等长结果片的完整输入。探针只有两个元素，可以另取长度为 4 的输入，每个 Rank 得到一个位置的归约结果。 [NCCL AllReduce 与 ReduceScatter 语义](https://docs.nvidia.com/deeplearning/nccl/archives/nccl_2273/user-guide/docs/usage/collectives.html)
2. 各 Rank 已完成组初始化，而且已知 Rank 3 还没有提交下一轮，先追它的本地输入生产与 Event 状态。前三个 Rank 的主机调用已返回，记录说明已入队，设备仍在等这轮完成。Rank 3 后续也成功提交时，其余约束仍需满足，包括同组同序、输入依赖和通信成功。消费与通信在同一条 Stream 时，后续工作按队列顺序读取。消费在另一条 Stream 时，先等待本地通信 Stream 上排在 AllReduce 后的 Event。 [NCCL Stream 完成语义](https://docs.nvidia.com/deeplearning/nccl/archives/nccl_2273/user-guide/docs/usage/streams.html)
3. 环上 `C0` 从 `0 → 1 → 2 → 3`，每个接收方加入自己的贡献，Rank 3 得到完整块。从 `3 → 0 → 1 → 2` 传播时只复制，各 Rank 已归约的其它块同步沿环推进。换成树，`3 → 1` 和 `2 → 0` 可同轮进行，再由 `1 → 0` 汇总。随后 `0 → 1` 与 `0 → 2` 可同轮广播，最后 `1 → 3`。树的两轮广播假定根可以同时向两个孩子提供数据。共享网口或带宽不足时，两条边即使逻辑上可并行，完成时间仍受合计字节量约束。
4. 每条有向环边在一次操作中发送 `6 × 16 MiB = 96 MiB`。甲轮只有 `1 → 2` 从 A 到 B，乙轮由 `0 → 2` 与 `1 → 3` 共用 A 的发送端口，分别是 96 MiB 和 192 MiB。以 `25 × 10⁹ B/s` 除得约 4.03 ms 和 8.05 ms 的下界。用每 Rank 的 64 MiB 除以 5 ms 和 9 ms，得到甲、乙的 `algbw` 约 13.42 和 7.46 GB/s，再乘 1.5 得 `busbw` 约 20.13 和 11.18 GB/s。

   乙轮 A 端计数给出 `11,200,000,000 × 4 B / 2 s = 22.4 GB/s` 的发送速率。乙轮按模型要在 9 ms 内向 B 发送 192 MiB，约合 22.37 GB/s 的载荷速率。材料中的端口速率与模型接近。对端接收和采样窗口也能对齐，这些证据共同支持共享端口限制的解释。进一步比较固定消息、算法、协议、通道数和放置的重复轮次，核对两端同方向计数、背景流量及 Rank 的设备进度。

   perftest 的 180 Gb/s 即 22.5 GB/s，只给出 A 的 GPU 1 向 B 的 GPU 0 在指定条件下的单向载荷基线。在甲轮它与一条跨机边的设备配对相同，乙轮 A → B 换成两条不同的 GPU 配对，还引入共同端口上的并发。如果某条边只有接收侧使用 GDR，载荷从 A 的 GPU 经主机缓冲到 A 的 NIC，经交换网络到 B 的 NIC，再写入 B 的 GPU 接收缓冲。端口收到的算法载荷仍按该边的 96 MiB 计，新增的是 A 节点内部的搬运。 [nccl-tests 带宽口径](https://github.com/NVIDIA/nccl-tests/blob/v2.17.9/doc/PERFORMANCE.md#allreduce) · [Linux 6.18 端口计数 ABI](https://docs.kernel.org/6.18/admin-guide/abi-stable.html)

## 一次通信怎样接回作业的时间线

训练代码先确定哪些成员要交换什么，以及结果要落在哪些设备。通信组把这些成员落实为 Rank 和设备，算法将交换变成有依赖的步骤，通道和传输选择再把步骤落到实际互联。日志能把选择对回设备与调用，完成状态确认后才可消费数据，基准和端口计数帮助估计这些步骤花了多少时间。第 09 章沿 GPU 工作的另一条依赖继续，考察输入数据如何从存储到达进程和显存，以及这条路径上的等待如何出现在训练时间线上。
