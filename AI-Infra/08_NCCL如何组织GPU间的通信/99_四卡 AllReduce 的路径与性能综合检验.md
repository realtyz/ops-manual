# 四卡 AllReduce 的路径与性能综合检验

学完 NCCL 职责边界、通信组初始化、Ring/Tree 算法、物理选路、日志排查与基准复算后，下面通过五道无实机实战题把全章主线彻底串起来。建议先不展开底部的参考推理，独立拿笔列出每一步的进度判断、路径与算式，再对照核验。

## 一、基础环境设定（第 1–4 题共用）

两台裸机 Linux 服务器 `gpu-a` 与 `gpu-b` 组成一个四卡通信组，软件栈对齐 `CUDA 13.2.1`、`NCCL 2.27.3`、`Open MPI 5.0.6`、`nccl-tests v2.17.9` 与 `perftest 26.07.8`，硬件与角色映射如下：

| 维度 | 具体配置与角色映射 |
| --- | --- |
| **节点与 Rank 分布** | `gpu-a` 承载 `Rank 0`（GPU 0）与 `Rank 1`（GPU 1）；`gpu-b` 承载 `Rank 2`（GPU 0）与 `Rank 3`（GPU 1）；每进程独占一张独立显存 GPU |
| **机内互联** | 同机两张 GPU 均支持 PCIe P2P 直达 |
| **网络双平面** | `eno1` 负责默认 TCP 引导；每节点仅配一个 `200 Gb/s` 全双工 RoCEv2 高速口 `mlx5_0:1`（对应 `enp129s0f0`，单向名义线速 `25 GB/s`） |

## 二、五道实战检验题

### 题 1：分层职责、求和探针与集合原语切换

应用先用四个 `float32` 向量 `[1, 2]`、`[3, 4]`、`[5, 6]`、`[7, 8]` 在该四卡组上执行一轮求和 AllReduce 探针，全部成员校验通过。

1. 哪一层决定梯度按什么规则合并？启动器、NCCL 与 CUDA 各自承担哪一步工作？
2. 写出本轮求和探针完成后每个 Rank 拿到的输出向量。
3. 如果需求改为“每个 Rank 只需保留全局归约结果中属于自己的那一块等长切片”，应当改选什么集合操作？输入数组长度需要满足什么条件？

### 题 2：卡顿进度的首个缺失点与消费放行条件

紧接着探针之后，同一通信组按相同参数发起下一轮 AllReduce，各进程采集到的运行进度汇总如下：

| 参与者 | NCCL 初始化状态 | 下一轮应用侧进度记录 |
| --- | --- | --- |
| `Rank 0`、`1`、`2` | 均 `Init COMPLETE` | `ncclAllReduce` 主机调用已返回成功；通信 Stream 上的完成 Event 尚未就绪 |
| `Rank 3` | `Init COMPLETE` | 代码分支正在等待本地输入前置任务就绪，尚未进入本轮 `ncclAllReduce` 调用 |

1. 这一轮集合操作当前卡在哪个进度点？应当优先追查哪个 Rank 的哪类记录？
2. 假如 `Rank 3` 随后顺利提交了匹配的本轮操作，各成员的下游消费代码需要满足什么条件才能安全读取结果（分单 Stream 与多 Stream 两种情形说明）？

### 题 3：同一数据块在 Ring 与 Tree 中的推进对照

假设每卡输入切成 `C0` 至 `C3` 四块，先看标准顺排环 `0 → 1 → 2 → 3 → 0`（记为甲轮），再看一棵根为 `0`、子节点为 `1` 与 `2`、`3` 挂在 `1` 下的四卡树：

1. 在甲轮环上，从 `Rank 0` 的 `C0` 贡献出发，依次写出 `C0` 在哪些 Rank 做累加、在哪张卡合成完整块、再沿哪条路径交付给另外三张卡。
2. 换到上述四卡树中追踪 `C0`，指出归约和广播阶段分别有哪些传输可以在同一轮并行完成，以及这一并行性隐含了什么硬件前提？

### 题 4：顺排环 vs 交错环负载、基准复算与端口计数核验

独立完成两轮四卡 `all_reduce_perf`（`float32` 求和、`out-of-place`、每 Rank 输入 `64 MiB`），两轮均确认启用单 Ring 通道、相同协议、相同 Rank-GPU 绑定，且跨机边收发双端均带 `/GDRDMA`：

| 轮次 | 核对后的通道环顺序 | `size` | `time` | `#wrong` |
| --- | --- | ---: | ---: | ---: |
| **甲轮** | `0 → 1 → 2 → 3 → 0` | `67,108,864 B` | `5,000 µs` | `0` |
| **乙轮** | `0 → 2 → 1 → 3 → 0` | `67,108,864 B` | `9,000 µs` | `0` |

同期采集到以下两条补充证据：
- **硬件端口计数**：乙轮在 `64 MiB` 稳态运行的 `2 s` 窗口内（无背景流量），`gpu-a` 的 `port_xmit_data` 净增 `11,200,000,000`，`gpu-b` 接收端增量同量级；
- **单向 GDR 基线**：另有一轮 GPU 缓冲的 `perftest`（`ib_write_bw`）测得 `gpu-a` GPU 1 向 `gpu-b` GPU 0 的 `8 MiB` 单向 RC Write 平均速率为 `180 Gb/s`。

1. 按单通道四等分 Ring 模型，计算甲、乙两轮在 `gpu-a → gpu-b` 方向的单次端口字节量与按 `25 GB/s` 线速推得的耗时下界。
2. 分别复算甲、乙两轮的 `algbw`、`busbw`，以及乙轮 `2 s` 窗口内 `gpu-a` 的实际端口发送速率（`GB/s`）。
3. 哪些证据共同坐实了乙轮受限于共享网口瓶颈？单轮 `perftest` 的 `180 Gb/s` 覆盖了哪些路径、没覆盖哪些差异？
4. 若乙轮某条跨机边仅接收侧启用 GDR、发送侧退回主机中转，画出该边的数据路径，并判断 `gpu-a` 网卡端口发出的算法字节量是否会改变。

### 题 5：在线推理 TP 小消息与 PD 分离 KV 迁移架构选型

切换到一座采用 **PD 分离架构**的大模型在线推理集群，内部出现两类截然不同的跨卡通信需求：

| 通信需求 | 场景与参数特征 |
| --- | --- |
| **Decode 实例内 TP=8 同步** | 单次 Decode 步中，每层需在 8 张卡之间执行一次 `64 KiB`（$65{,}536\text{ B}$）的同步 AllReduce；设简化对称模型中单跳固定开销 $\alpha = 2\,\mu\text{s}$、单向有效带宽 $B = 25\text{ GB/s}$ |
| **跨池 KV Cache 迁移** | Prefill 池与 Decode 池各自独立弹性扩缩容，每个请求在提示词算完后将 PagedAttention 非连续 KV 块跨节点送往动态选中的 Decode 实例 |

1. 代入 8 卡分块 Ring 与无分块二项树耗时模型，分别算出 `64 KiB` 消息的理论耗时，判断哪种算法更有优势；并说明为何推理 TP 小消息优先偏好 `LL` / `LL128` 协议而非 `Simple`？
2. 为什么第二类“跨池 KV Cache 迁移”通常交由 NIXL 等点对点异步 RDMA 传输库承担，而不把整个 Prefill 池与 Decode 池放进同一个大 NCCL Communicator？

## 三、分步参考推理

> [!example]- 点击展开五道检验题的完整参考推理与推导过程
>
> ### 题 1 参考推理：划清五层边界，核对缓冲区切分条件
> 1. **职责分工**：**应用或框架**决定梯度的合并语义（求和、求平均等）并传入缓冲区与算子；**启动器**负责在两台节点上拉起四个工作进程；**NCCL** 建立通信组并编排数据搬运与归约步骤；**CUDA** 负责在输入依赖就绪后调度执行 Stream 里的通信 Kernel 与内存操作。
> 2. **探针输出**：四个 Rank 均按位置累加得到：
> $$[1+3+5+7,\; 2+4+6+8] = [16,\; 20]$$
> 3. **原语切换**：只需保留各自那一段归约分片时，应选用 **ReduceScatter**。四卡通信组要求每张卡提交的完整输入元素数必须是 `4` 的整数倍，才能按 Rank 等分交付；探针长度 `2` 无法被 `4` 整除，需改用例如长度为 `4` 的输入，使每张卡拿到 1 个位置的归约结果。
>
> ### 题 2 参考推理：先找缺席提交的成员，再按 Stream 模型判消费条件
> 1. **进度定位**：四卡全部已完成 `Init COMPLETE`，说明建组环节无异常；`Rank 0/1/2` 的主机 API 返回仅表示任务已排进各自的 CUDA Stream，而 `Rank 3` 尚未进入调用，因此当前卡在**全组同序入队**这一关。应优先追查 `Rank 3` 的应用分支日志、上游输入生产任务及其本地前置 Event 状态。
> 2. **安全消费条件**：待 `Rank 3` 顺利提交匹配操作且全组通信无异步错误完成后：
>    - 若消费 Kernel 与 AllReduce 排在**同一条 CUDA Stream**，队列顺序自动保证前序通信完成后才执行读取；
>    - 若消费位于**独立的计算 Stream**，则必须在本地通信 Stream 的 AllReduce 之后插入 `cudaEventRecord`，并让消费 Stream 执行 `cudaStreamWaitEvent` 等待该 Event 就绪后再读取结果。
>
> ### 题 3 参考推理：沿着单一数据块对比环与树的并行代价
> 1. **顺排环追踪 `C0`**：
>    - **ReduceScatter（3 轮归约）**：`Rank 0` 发出本地 `C0` → `Rank 1` 累加第 2 份 → `Rank 2` 累加第 3 份 → `Rank 3` 累加第 4 份，**在 `Rank 3` 合成完整 `C0`**；
>    - **AllGather（3 轮分发）**：`Rank 3` 将完整 `C0` 依次沿 `3 → 0 → 1 → 2` 复制回原数组位置（不再求和），与此同时 `C1/C2/C3` 也在其他边上同步推进。
> 2. **四卡树追踪 `C0`**：
>    - **归约（2 轮）**：第 1 轮 `3 → 1` 与 `2 → 0` 可并行；第 2 轮 `1 → 0` 汇总到根 `0`；
>    - **广播（2 轮）**：第 1 轮 `0 → 1` 与 `0 → 2` 可并行；第 2 轮 `1 → 3` 完成全员覆盖。
>    - **隐含假设**：同轮多分支并行假定各条逻辑边不争抢同一物理收发瓶颈（尤其要求根 `0` 能同时向两个子节点全速输出）；一旦两条分支复用同一个受限网口，实际耗时仍受该网口的总字节量约束。
>
> ### 题 4 参考推理：用公式、基准与硬件计数完成三方互证
> 1. **单方向端口载荷与耗时下界**：
>    单条有向环边在一次 `64 MiB` AllReduce 中发送：
> $$V_{\text{edge}} = \frac{2 \times (4 - 1)}{4} \times 64\text{ MiB} = 96\text{ MiB} = 100{,}663{,}296\text{ B}$$
>    - **甲轮（`0 → 1 → 2 → 3 → 0`）**：`gpu-a → gpu-b` 仅有 `1 → 2` 一条跨机边，单向载荷 `96 MiB`：
> $$T_{\min,\text{甲}} = \frac{96 \times 2^{20}\text{ B}}{25 \times 10^9\text{ B/s}} \approx 4.03\text{ ms}$$
>    - **乙轮（`0 → 2 → 1 → 3 → 0`）**：`gpu-a → gpu-b` 同时叠加 `0 → 2` 与 `1 → 3` 两条跨机边，单向载荷翻倍至 `192 MiB`：
> $$T_{\min,\text{乙}} = \frac{192 \times 2^{20}\text{ B}}{25 \times 10^9\text{ B/s}} \approx 8.05\text{ ms}$$
> 2. **`algbw`、`busbw` 与端口实测速率复算**（$S = 67{,}108{,}864\text{ B}$，四卡系数 $2(4-1)/4 = 1.5$）：
> $$\text{algbw}_{\text{甲}} = \frac{67{,}108{,}864}{0.005 \times 10^9} \approx 13.42\text{ GB/s}, \qquad \text{busbw}_{\text{甲}} = 13.42 \times 1.5 \approx 20.13\text{ GB/s}$$
> $$\text{algbw}_{\text{乙}} = \frac{67{,}108{,}864}{0.009 \times 10^9} \approx 7.46\text{ GB/s}, \qquad \text{busbw}_{\text{乙}} = 7.4565 \times 1.5 \approx 11.18\text{ GB/s}$$
>    按 Linux ABI，`port_xmit_data` 每计数为 `4 B`，乙轮 `gpu-a` 端口实测发送速率为：
> $$R_{\text{tx,实测}} = \frac{11{,}200{,}000{,}000 \times 4\text{ B}}{2\text{ s}} = 22.40\text{ GB/s}$$
> 3. **共享网口瓶颈互证与 `perftest` 覆盖边界**：
>    乙轮模型要求在 `9 ms` 内向 `gpu-b` 发送 `192 MiB`，折算理论算法载荷速率为：
> $$R_{\text{tx,模型}} = \frac{192 \times 2^{20}\text{ B}}{0.009\text{ s} \times 10^9} \approx 22.37\text{ GB/s}$$
>    这与端口实测 `22.40 GB/s` 几乎严丝合缝，且对端 RX 同量级、无背景流量、单向逼近 `perftest` 单口基线 `180 Gb/s = 22.5 GB/s`，足以坐实共享单网口饱和。
>
>    `perftest` 覆盖了 `gpu-a` GPU 1 → `gpu-b` GPU 0 的单流单向 GDR（对应甲轮 `1 → 2`），但未覆盖乙轮 `0 → 2`、`1 → 3` 新设备配对及双流争抢同一物理网口的并发开销。
> 4. **单侧 GDR 回退分析**：若发送侧退回主机中转、接收侧保留 GDR，该边路径变为：`gpu-a` 源 GPU 显存 → 本地主机内存缓冲 → `gpu-a` 网卡（`mlx5_0:1`）→ RoCEv2 网络 → `gpu-b` 网卡 → `gpu-b` 目标 GPU 显存。跨越网卡端口的算法载荷仍为该边的 `96 MiB` 不会减少，额外增加的是 `gpu-a` 节点内部多出的一段显存到主机内存搬运开销。
>
> ### 题 5 参考推理：定量对比推理小消息与通信库边界
> 1. **8 卡 `64 KiB`（$65{,}536\text{ B}$）模型耗时对比**：
>    - **分块 Ring**（$14$ 轮，关键路径传 $1.75S$）：
> $$T_{\text{ring}} = 14 \times 2\,\mu\text{s} + \frac{1.75 \times 65{,}536\text{ B}}{25 \times 10^9\text{ B/s}} \times 10^6 \approx 28 + 4.59 = 32.59\,\mu\text{s}$$
>    - **无分块二项树**（$6$ 轮，关键路径传 $6S$）：
> $$T_{\text{tree}} = 6 \times 2\,\mu\text{s} + \frac{6 \times 65{,}536\text{ B}}{25 \times 10^9\text{ B/s}} \times 10^6 \approx 12 + 15.73 = 27.73\,\mu\text{s}$$
>    因为 `64 KiB` 小于理论交点（约 `92 KiB`），Tree 凭更少的串行跳数领先 Ring 约 `4.86 µs`。在协议层面，`Simple` 需等待重型系统内存栅栏，微秒级启动开销过高；而 `LL` / `LL128` 把同步标志直接内联在数据块中轮询触发，能把微秒级延迟压到最低——即便 `LL` 牺牲部分带宽利用率，在每生成一个 token 要执行上百次极小 AllReduce 的推理 TP 中依然大幅降低 TPOT。
> 2. **为何跨池 KV 迁移用 NIXL 等 P2P 异步库而非大 NCCL 组**：
>    - **拓扑弹性冲突**：Prefill 与 Decode 池各自按业务流量动态扩缩容、按请求即时路由配对；NCCL Communicator 偏向静态齐步成员组，频发扩缩重建开销过高。
>    - **内存形态与同步语义不合**：PagedAttention 的 KV Cache 分布在大量离散非连续显存块中，且需要请求级异步单边搬运、不阻塞其他计算；专用传输库（如 NIXL 依托 UCX/RDMA）原生支持离散块注册与非阻塞单边读写，还能无缝兼容向主机内存或本地 NVMe 的异构卸载。

## 四、全章收束：把通信库接回训推作业时间线

回头俯瞰第 08 章串联起的完整链条，一次多卡通信在真实系统里按五道工序逐层落地：

1. **划边界**：区分同步集合通信（交由 NCCL 承担的训练同步与推理实例内 TP）与动态异步点对点传输（交由 NIXL/RDMA 承担的 PD 分离 KV 迁移）。
2. **建上下文**：启动器拉起进程并独占绑卡，经带外分发 UniqueId 与独立引导网完成 Bootstrap，进入 CUDA Stream 异步入队与 Event 同步。
3. **定算法与协议**：结合消息尺度与成员数权衡 Ring 与 Tree，匹配训练大梯度的 `Simple` 高吞吐路线或推理 TP 小消息的 `LL`/`LL128` 低延迟路线。
4. **落物理路径**：将逻辑边映射到机内 P2P/SHM 与跨机 GDR/主机中转，避开无谓的跨机交错折返，对齐网卡与动态 RoCEv2 GID。
5. **用日志与基准闭环验真**：通过 `NCCL_DEBUG` 锁定首个缺失进度点并双边确认 `/GDRDMA`，再用 `nccl-tests`（`algbw`/`busbw`）、`perftest` 与同窗硬件端口计数交叉锁定瓶颈。
