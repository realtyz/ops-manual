# 第 08 章 NCCL 如何组织 GPU 间的通信｜写作大纲

**审查状态**　已批准。正文按以下六节拆篇，RoCEv2 贯穿，采用源码核对过的教学日志和可复算数据。

## 范围、前置知识与学习结果

- **范围**　沿着一次裸机多节点 AllReduce，解释应用如何组成通信组，NCCL 如何根据设备拓扑构建通信路径、选择算法，以及怎样用分阶段日志和分层基准检验这些判断。在初始化篇对照六种常见集合操作的数据语义，再用 AllReduce 深入解释算法、路径和基准。网络插件、NVLS、CollNet 和多 Rail 用于说明选择边界，各自的部署与调优留作扩展。
- **必要前置**　知道进程、Rank、Local Rank 与 GPU 的关系，认识 CUDA Stream、PCIe、NVLink、NUMA、RDMA 端口和 GPUDirect RDMA。开篇用一张映射表、一条 Stream 时间线和一句显存直达的定义补齐这些知识。读者可以用所给材料完成推导，无需 GPU 实验环境。
- **跨章分工**　前几章已交代单机互联、并行切分、Verbs 和 IB/RoCE 网络，本章只在它们改变 NCCL 行为时回顾。第 09 章接手数据供给，第 10—16 章接手容器、Pod 网络及作业调度，第 17—19 章接手常态监控、跨层故障处置和交付验收。
- **读完应能独立判断**　给定各 Rank 的输入与目标布局，能判断该用哪种集合操作。给定启动参数和日志，能还原 communicator 的成员、各 Rank 绑定的实际 GPU，以及引导接口和载荷路径；给定规模与消息大小，能解释 Ring 与 Tree 可能各占优势的条件；给定基准输出，能复算 `algbw` 与 `busbw`、判断两轮结果能否比较，并为初始化失败、首次通信失败和集合吞吐偏低各指出下一项能区分原因的证据。

## 贯穿场景与证据口径

- **教学拓扑**　节点 A、B 各有两张独立显存的 GPU、一张用于 IP 引导的网卡接口 `eno1`，以及一个接入同一 RoCEv2 以太网 Fabric 的 200 Gb/s 端口 `mlx5_0:1`，对应网络接口 `enp129s0f0`。两端用独立于引导网络的 IPv4 地址和 RoCEv2 GID。假设节点内 GPU 支持 PCIe P2P，GPU 与 RDMA NIC 之间满足 GDR 条件，实际是否选用需查对应方向的记录。每 GPU 一个进程，Rank 0/1 位于 A，Rank 2/3 位于 B。单机和两节点各一张 GPU 的测试取此拓扑的子集。200 Gb/s 仅用作名义线速，端口线速、每 Rank 载荷、集合的归一化带宽分别计量。
- **版本锚点**　NCCL 2.27.3 归档文档与源码标签 `v2.27.3-1` 用于核对环境变量和日志模板，示例 CUDA 取发行说明列出的 12.9。`nccl-tests` 以 `v2.17.9` 核对参数、计时与输出，perftest 沿用第 06 章的 `26.07.8`。这些版本用于固定引用和样例口径，组合的编译及运行尚待实机验证。 [NCCL 2.27.3 发行说明](https://docs.nvidia.com/deeplearning/nccl/archives/nccl_2273/release-notes/rel_2-27-3.html) · [NCCL 源码标签](https://github.com/NVIDIA/nccl/tree/v2.27.3-1) · [nccl-tests v2.17.9](https://github.com/NVIDIA/nccl-tests/tree/v2.17.9) · [perftest 26.07.8](https://github.com/linux-rdma/perftest/tree/a31f9ea9df720ee68f941e55f75fec31349fcd35)

## 01 从作业进程到第一次完成 AllReduce

- **问题与结论**　为什么四个进程都已启动，作业仍可能卡在 NCCL 初始化或第一次 AllReduce？读者应能分别指出进程由谁拉起、通信组怎样建立、一次操作何时进入 Stream，以及结果何时可供下游使用。
- **解释顺序**　先沿 `launcher / 应用框架 → NCCL API → CUDA Stream 与传输层` 分配职责。用 MPI 示例说明进程启动、Rank 与设备绑定，再由一个成员调用 `ncclGetUniqueId`，通过 MPI 等外部途径分发 ID；所有成员选定 CUDA device，以同一个 ID、组大小和各自 Rank 调用 `ncclCommInitRank`。接着区分框架 Rendezvous、NCCL bootstrap 与数据连接；默认 Socket 引导走 IP，2.23 起可用 `NCCL_OOB_NET_ENABLE` 改变初始化中 bootstrap AllGather 所用的实现。2.22 起 `NCCL_RUNTIME_CONNECT` 可把部分连接延迟到运行时，2.27.3 源码还要求 `comm->cuMemSupport`，因此 `Init COMPLETE` 后首轮仍可能在连接阶段失败。插入三 Rank 算例，对照 Broadcast、Reduce、AllReduce、AllGather、ReduceScatter 和 All-to-All 的输入输出，区分根 Rank、分片布局和 count 口径。最后画普通阻塞模式下的提交时间线，区分主机 API 返回、CUDA Stream 完成和跨 Stream 消费，说明同一通信组内的调用顺序与参数如何匹配。前置的训练并行与跨 communicator 调度只交代边界。
- **支撑材料**　四行 `host / rank / local rank / cudaDev / GPU BDF` 映射表用于核对 `CUDA_VISIBLE_DEVICES` 重编号后的设备绑定。同一 communicator 内每个 Rank 对应独立 CUDA device，一个进程可管理多个设备。集合类型对照图沿用三 Rank 算例的缓冲区数据。Mermaid 时序图分开展示 ID 分发、bootstrap、首轮可能出现的数据连接和 Stream 完成点。官方 API 说明支撑成员契约和异步语义，源码支撑延迟建连的额外条件。 [NCCL 概览](https://docs.nvidia.com/deeplearning/nccl/archives/nccl_2273/user-guide/docs/overview.html) · [Communicator 创建](https://docs.nvidia.com/deeplearning/nccl/archives/nccl_2273/user-guide/docs/usage/communicators.html) · [集合操作](https://docs.nvidia.com/deeplearning/nccl/archives/nccl_2273/user-guide/docs/usage/collectives.html) · [CUDA Stream 语义](https://docs.nvidia.com/deeplearning/nccl/archives/nccl_2273/user-guide/docs/usage/streams.html) · [环境变量](https://docs.nvidia.com/deeplearning/nccl/archives/nccl_2273/user-guide/docs/env.html#nccl-runtime-connect) · [初始化源码](https://github.com/NVIDIA/nccl/blob/v2.27.3-1/src/init.cc#L1148)

## 02 从设备拓扑到 P2P、SHM 和 NET

- **问题与结论**　两张 GPU 都可见、两节点 RDMA 端口都已激活，NCCL 实际会走哪里？读者应能为一条逻辑边画出节点内或跨节点的物理路径，区分同机 GPU P2P、主机共享缓冲、TCP Socket、Verbs 与显存直达。
- **解释顺序**　先把 Rank 映射到实际 GPU、PCIe 路径、NUMA、NIC 及端口；再说明 2.27.3 如何从拓扑构建 Ring/Tree 的候选通道、按通道邻居及方向检查传输能力。普通连接的源码候选包含 P2P、SHM 和 NET，具体可用性由各实现检查和拓扑约束决定。对照同机 P2P 的 PCIe/NVLink 路径与 SHM 的主机缓冲；SHM 在适用版本和环境可用 cuMem host allocation，NCCL 2.24 起满足 CUDA 驱动能力 ≥ 12.6、Runtime ≥ 12.2 等条件时默认启用，2.26.5 起会检查并在需要时回退到 `/dev/shm`。跨节点分两层判断：NET 用内置 IB Verbs（可用于 IB 或 RoCE）还是 Socket；Verbs 所选的 GPU/NIC 与方向能否用 GDR，抑或仍经主机内存中转。收尾用一句话交代插件和跨节点 NVLink 会改变候选路径。双 Rail 只解释 `NCCL_CROSS_NIC` 如何约束同一 Ring/Tree 两端选口，交换机实际路径和拥塞归前章。
- **支撑材料**　拟作一张双节点路径示意，以 Rank 0→1 和 Rank 1→2 为例，保留各自 GPU/显存、主机缓冲、PCIe、引导接口、RDMA 端口和交换网络，分别标注候选路径。拓扑输入用 `nvidia-smi topo -m`、GPU BDF 与 `rdma link show` 对照。配置对照用 Linux shell 的 `export NCCL_SOCKET_IFNAME='=eno1'`、`export NCCL_IB_HCA='=mlx5_0:1'`，解释前者筛 IP 接口（默认引导和内置 Socket 网络各自选口），后者筛内置 Verbs 端口；指定 HCA 后仍需用通道日志核对 GDR。用端口、netdev 和本地 GID 表验证 RoCEv2 路径，说明 NCCL 2.21 起默认动态选择 GID，以及 2.27.3 如何筛选地址族、网段和 RoCE 版本。 [传输选择源码](https://github.com/NVIDIA/nccl/blob/v2.27.3-1/src/transport.cc) · [拓扑初始化源码](https://github.com/NVIDIA/nccl/blob/v2.27.3-1/src/init.cc#L814) · [环境变量](https://docs.nvidia.com/deeplearning/nccl/archives/nccl_2273/user-guide/docs/env.html) · [共享内存、GPU Direct 与 RoCE 排障](https://docs.nvidia.com/deeplearning/nccl/archives/nccl_2273/user-guide/docs/troubleshooting.html)

## 03 同一次 AllReduce 为什么会选择 Ring 或 Tree

- **问题与结论**　少量数据为何容易受通信轮数限制，大量数据为何更依赖路径带宽？读者应能沿 Ring 追踪分块结果，区分逻辑邻居、物理传输与协议，并解释固定的消息大小阈值为何难以跨平台套用。
- **解释顺序**　先画四个 Rank 的逻辑环，以每 Rank 4 MiB、四个等分块演示 ReduceScatter 的逐跳累加，再用 AllGather 扩散结果。每阶段三轮，每 Rank 每轮发 1 MiB，共发 6 MiB、收 6 MiB，发送量与接收量分别计。再用同一数据块的四 Rank 教学树展示归约与广播的各轮路径，说明根、叶与关键路径，补充 NCCL 2.4 引入的双二叉树如何让两棵树的内部节点和叶子互补。回到实现时，区分通道内 Rank 顺序、每条边的传输实现与 `Simple`/`LL`/`LL128` 协议；NCCL 的调优模型以集合类型、消息大小、通道和拓扑估计延迟与带宽，并过滤硬件与版本不支持的组合。用 NVLS 说明具备相应 NVSwitch 和 GPU 能力时会出现额外候选。定制协议和硬件卸载的实现留作扩展。
- **支撑材料**　先用分块表标出每轮谁给谁、哪个块达到完整归约。Ring/Tree 对照图沿用相同的四 Rank 和 `C0`，标出每轮方向与归约完成点。再单独做八 Rank 算例，假设每轮固定开销 `α = 2 µs`、每个并行通信对可持续 `B = 25 GB/s`、链路同质、收发可重叠，忽略计算与共享争用。简单分块 Ring 用 `2(P−1)α + 2(P−1)S/(PB)`，无切块的理想二项树归约加广播用 `2 log₂(P)(α + S/B)`。在 `S = 4 KiB` 时 Ring/Tree 约 `28.29/12.98 µs`，在 `S = 4 MiB` 时约 `321.60/1018.63 µs`。树的数值只用于展示轮数和传输量的取舍，NCCL 双树的实现以官方说明和源码为准。比较实验可短时限制 `NCCL_ALGO=Ring` 或 `Tree`，并固定拓扑、操作和消息范围；2.24 起白名单无可用算法时会报错，环形回退取决于白名单是否允许 Ring。 [NVIDIA 的双二叉树说明](https://developer.nvidia.com/blog/massively-scale-deep-learning-training-nccl-2-4/) · [2.27.3 调优模型源码](https://github.com/NVIDIA/nccl/blob/v2.27.3-1/src/graph/tuning.cc) · [算法、协议和 NVLS 约束](https://docs.nvidia.com/deeplearning/nccl/archives/nccl_2273/user-guide/docs/env.html#nccl-algo)

## 04 把多 Rank 日志拼成一条时间线

- **问题与结论**　见到 `Bootstrap: Using`、`NET/IB`、`Init COMPLETE` 或某个 Rank 的 timeout 时，哪些判断已经有证据？读者应能按通信组和时间拼接各 Rank 记录，并为每个疑点指出一项可证伪的检查。
- **解释顺序**　先采集全 Rank 记录，按 `host:pid:tid`、`commId`、`rank/nranks` 归组，把 `cudaDev`、`nvmlDev` 与 `busId` 对回拓扑；结合应用日志标出进程启动、`Init START/COMPLETE`、集合序号与提交/完成。再分别读 `Bootstrap: Using` 的接口、`Using network` 的后端、`NET/IB : Using…` 的设备列表、`Channel` 的邻居与 `via` 路径。`/GDRDMA` 按对应通道和 `[send]`/`[receive]` 解读。最后用三组短记录练习：有成员未到 `Init START` 时先查启动器及其退出状态；各成员进了初始化但 bootstrap 无法建连时查监听、选口和双向可达性；各成员均 `Init COMPLETE` 后挂起时，用通道连接警告、应用提交序号和设备进度区分延迟建连、集合调用失配与执行慢。将首发警告与其他 Rank 后续超时分开。RAS（2.24 起）作为补充证据点，跨层故障手册留给运维章节。
- **支撑材料**　配置用 `NCCL_DEBUG=INFO`、`NCCL_DEBUG_SUBSYS=INIT,BOOTSTRAP,ENV,GRAPH,P2P,SHM,NET` 和 `NCCL_DEBUG_FILE=/tmp/nccl.%h.%p.log`。各进程单独记录。2.27.3 的 INFO 默认无墙钟时间，跨机对齐时另设 `TZ=UTC`、`NCCL_DEBUG_TIMESTAMP_LEVELS=WARN,INFO` 与毫秒格式，并保留时钟偏差和每进程原始顺序。拟用源码模板拼一组成功建连节录，展示 `eno1` 的 bootstrap 和 `mlx5_0:1/RoCE` 的 NET/IB 可同时出现，用 QP 日志的 GID 索引与本地 GID 表核对 RoCE 版本，再用上面三组教学短记录标出证据缺口。集合序号、类型、元素数、数据类型及归约操作由应用记录补齐。 [日志设置](https://docs.nvidia.com/deeplearning/nccl/archives/nccl_2273/user-guide/docs/env.html#nccl-debug) · [Bootstrap 源码](https://github.com/NVIDIA/nccl/blob/v2.27.3-1/src/bootstrap.cc#L123) · [初始化字段源码](https://github.com/NVIDIA/nccl/blob/v2.27.3-1/src/init.cc#L1469) · [NET 通道字段源码](https://github.com/NVIDIA/nccl/blob/v2.27.3-1/src/transport/net.cc#L218) · [NCCL 排障与 RAS](https://docs.nvidia.com/deeplearning/nccl/archives/nccl_2273/user-guide/docs/troubleshooting.html)

## 05 用 nccl-tests 量出集合操作的大小与速度

- **问题与结论**　`all_reduce_perf` 的一行结果在测哪组 Rank、每次交换多大、怎样读带宽？读者应能还原运行形状、检查结果是否正确，并复算一行输出。
- **解释顺序**　从 `MPI=1` 的构建选项入手，说明不拆组时总 Rank 数为 `进程数 × 每进程线程数(-t) × 每线程 GPU 数(-g)`。用两节点各两个 MPI 进程、`-t 1 -g 1` 举例，核对 launcher 实际放置和每进程 CUDA 设备。扫描参数拟用 `-b 8 -e 64M -f 2 -d float -o sum -w 5 -n 20 -a 1 -c 1`，标明预热、迭代、MPI 的计时归并和正确性检查。先看 `size/count/type`、in-place/out-of-place 和 `#wrong`，再看 `time`、`algbw` 与 `busbw`；比较时固定计时方式及两种缓冲布局的列，保留实际加载的库版本。时间列以该版本输出和源码的 `µs` 为准，字节量用 MiB，带宽用十进制 GB/s。消息扫小到大观察固定开销、过渡区和大消息吞吐，过渡点由实测决定。
- **支撑材料**　用四 Rank 教学行 `size=67,108,864 B`、`count=16,777,216 float`、`time=5000 µs`、`#wrong=0`。AllReduce 的 `S` 取每 Rank 输入大小，`algbw=S/t≈13.42 GB/s`，`busbw=algbw×2(P−1)/P≈20.13 GB/s`；AllGather 与 ReduceScatter 只补一行表说明 `S` 取完整数组大小及其 `(P−1)/P` 系数。`busbw` 是按操作和 Rank 数归一化的指标，结合实际拓扑解读；若要知道某个 NIC 的实流量，补取端口计数增量和采样时间。 [nccl-tests 参数](https://github.com/NVIDIA/nccl-tests/blob/v2.17.9/README.md) · [带宽定义](https://github.com/NVIDIA/nccl-tests/blob/v2.17.9/doc/PERFORMANCE.md) · [计时与数据校验源码](https://github.com/NVIDIA/nccl-tests/blob/v2.17.9/src/common.cu) · [AllReduce 带宽换算源码](https://github.com/NVIDIA/nccl-tests/blob/v2.17.9/src/all_reduce.cu#L59)

## 06 从双端点 RDMA 到两节点集合通信

- **问题与结论**　同一对端口的 `ib_write_bw` 正常，四卡 AllReduce 仍然慢，下一轮怎么测？读者应能划定每种测量支持的判断，以及怎样控制变量验证共享端口、设备绑定和 GDR 等候选原因。
- **解释顺序**　先固定 NIC 端口、方向、QP 数和消息大小，在同一对端点以各自的 RoCEv2 GID 索引运行 perftest，比较主机缓冲与 GPU 缓冲；前者建立 Verbs 路径基线，后者在确认实际选用 GPU 显存、注册成功并完成传输时建立该 GPU/NIC 对的 GDR 基线。随后用同一 NCCL 版本依次跑每节点本地双卡、跨节点各一卡、跨节点各两卡 AllReduce；规模改变会同时改变 Rank 数、算法或通道，先比对应消息区间并查日志，再按假设设计固定规模对照。对四 Rank 场景先保持消息、并行形状和端口不变，交换所用 GPU 的可见顺序或绑定，再核对映射和通道，观察耗时是否随 GPU–NIC 配对移动。拟用两例：其一，主机缓冲通过而 GPU 缓冲失败，继续查 GPU/NIC 绑定、注册后端和方向；其二，双端点两轮均通过、跨节点各一卡正常，但四卡增长时耗时跳升，查新增逻辑边、后端/GDR、节点内路径和端口负载。仅在相同规模、同一已核对的 Verbs 后端下，以 `NCCL_NET_GDR_LEVEL=LOC` 做 GDR 开关对照，核对实际路径是否变化。独立做日志采集和计时轮次，避免把日志量混入性能对比。
- **支撑材料**　用一张实验矩阵记录 `工具/Rank 或端点/缓冲区/方向/端口/消息大小/QP 或 NCCL 参数/判断范围`。同一 200 Gb/s 端口的单方向名义上限为 `200 ÷ 8 = 25 GB/s`，假设两条同向流共享它，合计仍受该上限约束；各流能分到多少要看并发与排队。仅在已知实际映射的简化 Ring 中估算哪条边跨节点，端口负载用同一计时窗口的 `/sys/class/infiniband/mlx5_0/ports/1/counters/` 下的 `port_xmit_data`、`port_rcv_data` 验证。按该 ABI 各自将计数差乘以 4 后除以秒数，得到端口收发方向的字节速率，并记录背景流量。perftest 单向载荷吞吐与 AllReduce 归一化带宽分别记录，补齐方向、单位和实际瓶颈后再讨论相互关系；集合测试结果只覆盖当时的参与规模、路径和参数。 [perftest 26.07.8 测试与显存选项](https://github.com/linux-rdma/perftest/blob/a31f9ea9df720ee68f941e55f75fec31349fcd35/README) · [NCCL 对低层 RDMA 测试的说明](https://docs.nvidia.com/deeplearning/nccl/archives/nccl_2273/user-guide/docs/troubleshooting.html) · [GDR 拓扑与发送方向开关](https://docs.nvidia.com/deeplearning/nccl/archives/nccl_2273/user-guide/docs/env.html#nccl-net-gdr-level-formerly-nccl-ib-gdr-level) · [Linux 6.18 InfiniBand 端口计数 ABI](https://docs.kernel.org/6.18/admin-guide/abi-stable.html)
