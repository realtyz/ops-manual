# 手工构造容器与镜像落地

## 1. 手工构造一个容器：四次动作，不是一个开关

本节所述的四个动作只在**可丢的实验机**上执行。这些动作不会改动宿主机上的既有文件（新建的命名空间在最后一个引用它的进程退出之后即被回收），但切换根与挂载这两个步骤仍应在实验机上执行，这样既便于观察，也便于收拾。

把"容器"这个词拆开，得到的是建立命名空间、切换根、写 cgroup 限额与在宿主视角观察进程这四个动作；每一个动作都在内核接口上留下可以分别观察的痕迹。

### 动作一：建立命名空间并进入

```bash
# 验证：先记下宿主上每一类命名空间的标识，稍后逐类对比
for ns in mnt uts ipc pid net cgroup user; do
  printf '%s=%s\n' "$ns" "$(readlink /proc/self/ns/$ns)"
done
```

```bash
# 验证：一次调用带上多个标志，多类命名空间同时建立；再取一次标识并对比
sudo unshare --mount --uts --ipc --pid --net --cgroup --fork --mount-proc /bin/bash
```

标志位是位掩码，因此"一次调用只能创建一个类型"是一种误记：多类命名空间可以在同一次调用中一起建立。真正需要记住的是后半句，即**创建容器在内核侧是一串调用，而不是一个原子动作**。正因如此，"某一类隔离没有生效"是完全可能出现的：它可能从未被创建，而不是被谁关闭了。

`--fork` 这一项不可省略。建立 PID 命名空间的那个进程本身不会被移入其中，只有它的第一个子进程才成为新命名空间里的一号进程。若没有带上 `--fork`，得到的结果就是"命名空间已经建立，而当前会话并不在其中"。

判据：逐类比较调用前后的标识。**同一个类型的标识相同，就说明这一类没有隔离**；此时不要先怀疑权限，而要先确认它是否根本没有被创建。若实验机上不允许建立某一类命名空间（例如 cgroup 命名空间受现场布局限制），则应去掉对应的标志再执行一遍，观察少了这一类时哪些现象随之消失。

### 动作二：准备根文件系统并切换根

```bash
# 验证：切换根之后看到的是准备好的目录树，而不是宿主的根
sudo chroot /tmp/rootfs /bin/sh
```

根目录需要单独准备一份：可以从任意基础镜像的各层解开，得到一份最小的目录树；也可以用静态可执行的文件自行搭建。**不要用宿主机的根目录来做这一步。**

这一步只改变了根，在权限方面没有做任何处理。`chroot` 并不构成权限边界；"容器里能否读写某个文件"由运行身份、能力集、挂载标志与强制访问控制共同决定。

### 动作三：写 cgroup 限额并读回

```bash
# 验证：先看这台机器上 cgroup 的布局（统一层次会显示为 0:: 开头的一行）
cat /proc/self/cgroup
```

建立 cgroup 组有两条路径，应按现场允许的那一条执行。

路径一：经由服务管理器建立一个带内存上限的组。该命令会立即返回，而单元留在后台运行；单元所在切片的路径按现场布局取值。

```bash
# 验证：单元建起来之后，把上限读回来
sudo systemd-run -p MemoryMax=256M --unit exp-unit sleep 600
cat /sys/fs/cgroup/system.slice/exp-unit.service/memory.max
```

路径二：手工建立 cgroup 组。

```bash
# 验证：手工建组并读回上限（能否直接建取决于父节点上开放了哪些控制器）
sudo mkdir /sys/fs/cgroup/exp
cat /sys/fs/cgroup/exp/memory.max
```

在**可丢的实验机**上把上限调小，然后观察进程被终止时的事件计数，这是判断额度是否生效的直接判据。下面的命令使用路径一建立的单元；若走路径二，则替换为自己建立的组。

```bash
# 验证：贴住上限被回收时的计数落在事件接口文件里，而不在容器内的整机视图里
cat /sys/fs/cgroup/system.slice/exp-unit.service/memory.events
```

清理与回滚：停掉那个单元（若走路径二，则删掉自己建立的组），并把上限改回原值。

判据：同一个内存量存在两个口径。容器内读到的内存总量来自内核，报告的是**宿主总量**；而这个容器的额度写在上面那个接口文件里。只有把两个数放在一起看，才能判断究竟是额度已经耗尽，还是整机内存用量过高。

### 动作四：在宿主视角看这些进程

```bash
# 验证：这些进程在宿主上就是普通进程，能看到、能发信号、能读它的状态
ps -eo pid,ppid,comm --forest | head
```

判据：这些进程在宿主机上可见，而容器内"只看得见自己"这一现象，来自另一份挂载实例所提供的视图。**隔离是视图层面的隔离，而不是权限层面的隔离**，因此这两件事需要分别取证。

### 四个动作各留下了什么

| 动作 | 留下了什么 | 判据 |
| --- | --- | --- |
| 建立命名空间 | 一组新的内核对象被创建出来 | 逐类标识与宿主机不同；没有带上的类型，其标识保持相同 |
| 切换根 | 进程的根指向了另一棵树 | 切换之后 `/` 的内容发生了变化，而宿主机上原路径仍然存在 |
| 写 cgroup | 一棵带上限的组被建立起来 | 上限与用量分别写在两个接口文件里；容器内的整机视图不受影响 |
| 运行进程 | 这些进程在宿主机上就是普通进程 | 宿主机的 `ps` 可以看到它们，且 `/proc/<pid>/ns/*` 指向新建的那一组 |

## 2. 用 OCI runtime 走一遍"创建"与"启动"

用 OCI runtime 走一遍，可以把"配置进程"与"启动进程"这两个步骤分开看清。为此需要准备一个捆绑目录（bundle）：在一个目录中放入一份 `config.json` 与一个根文件系统目录，其中 `config.json` 至少要写清进程参数、根目录路径、命名空间列表、cgroup 路径与主机名。

```bash
# 验证：创建之后进程处于已创建但未运行的状态
sudo runc --root /tmp/runc-state create -b /tmp/bundle c1
sudo runc --root /tmp/runc-state state c1
```

```bash
# 验证：启动之后再取一次，状态与进程号都变了
sudo runc --root /tmp/runc-state start c1
sudo runc --root /tmp/runc-state state c1
```

```bash
# 验证：宿主上这个容器进程的父进程是谁、托管进程有几个
ps -eo pid,ppid,comm | grep -E 'runc|sh'
```

判据落在状态里的三个字段上：`status`（已创建 / 运行中 / 已停止）、`pid`，以及宿主机上那个进程的**父进程**。

有一条结论只在这里验证一次，后续不再重复推演：**运行时命令在创建完进程之后就退出，留在那里托管进程的是另一个角色。** 因此，"守护进程重启不会影响运行中的容器"这句话在现场的判据，是容器进程的父进程是谁以及托管进程有多少个，而不是有没有守护进程正在运行。

清理与回滚：删掉这个容器并确认宿主机上不再有对应的进程，然后删掉状态目录与捆绑目录。**这一步只在可丢的实验机上执行。**

## 3. 观察联合挂载：白障（whiteout）与 copy-up 留下了什么

```bash
# 验证：把两层只读目录与一个可写目录拼成一个视图
sudo mkdir -p /tmp/ovl/lower1 /tmp/ovl/lower2 /tmp/ovl/upper /tmp/ovl/work /tmp/ovl/merged
printf 'base\n' | sudo tee /tmp/ovl/lower1/a.txt
printf 'over\n' | sudo tee /tmp/ovl/lower2/b.txt
sudo mount -t overlay overlay -o lowerdir=/tmp/ovl/lower2:/tmp/ovl/lower1,upperdir=/tmp/ovl/upper,workdir=/tmp/ovl/work /tmp/ovl/merged
```

下面四件事各做一次，每次只观察同一个位置，也就是可写层多出了什么：

| 在挂载点里做的事 | 可写层里多了什么 | 判据 |
| --- | --- | --- |
| 读取只读层里的文件 | 可写层中不增加任何内容 | 可写层为空，说明读取不产生代价 |
| 修改它的内容 | 出现整份文件的副本 | 副本的字节数等于整份文件的大小，而不是实际改动量 |
| 只修改它的元数据 | **默认同样产生整份副本** | 副本大小仍等于整份文件；只复制元数据的模式有额外的挂载前提 |
| 删除它 | 出现一个特殊条目，而不是内容消失 | 该条目有两种等价写法，看到哪一种取决于底层文件系统与内核 |

```bash
# 验证：读不会在可写层留下任何东西
ls -la /tmp/ovl/upper/
```

```bash
# 验证：只改元数据也会整份复制到可写层
sudo chmod 600 /tmp/ovl/merged/a.txt
ls -la /tmp/ovl/upper/ /tmp/ovl/lower1/
```

```bash
# 验证：写入前后设备号与 inode 是否变化
stat -c '%d %i %s %n' /tmp/ovl/merged/a.txt /tmp/ovl/lower1/a.txt
```

```bash
# 验证：删除在可写层里留下的是一个条目
sudo rm /tmp/ovl/merged/b.txt
ls -la /tmp/ovl/upper/
```

```bash
# 验证：在容器的位置读到的可用空间来自承载可写层的那个文件系统
df -h /tmp/ovl/merged /tmp/ovl/upper
```

白障在磁盘上有两种等价的写法：**设备号为零的字符设备**，或者**零长度文件加一个扩展属性**。以非特权方式挂载时，扩展属性的前缀会从受信任前缀变为用户前缀，因此**查找扩展属性不能只按受信任前缀进行**，否则会得出"这里没有白障"的错误结论。

清理与回滚：先卸载挂载点，再删掉实验目录。**不要在实验机上对真实目录执行这一步。**

## 4. 三类存储占用：同口径取样

取样纪律：**同口径、带时间戳、至少两次、留原始输出。** 一次读数只给出某一个时刻的值，因此说明不了任何趋势。

节点上的三类存储占用（只读层、可写层、日志与卷）各有不同的量法，因此需要在一次拉取**前后各取一次**下面这四个数：

| 取什么 | 量的是哪一类存储占用 | 漏掉了什么 |
| --- | --- | --- |
| 镜像列表里的体积 | 各层**压缩后**的体积之和 | 它与节点磁盘占用无关 |
| 内容存储的目录数与占用 | 与仓库字节相同的 blob | 解压并落地的那一部分 |
| 运行时的文件系统用量接口 | 快照目录的**未压缩**占用与 inode 数 | 内容存储与元数据库 |
| 运行时根目录的实际磁盘统计 | 上面几块连同元数据在内 | 卷与日志属于另一类存储占用 |

判据：这四个数互不可比，相差数倍是常态而不是异常，真正有用的是**同一口径两次读数的差值**。用 inode 再做一遍同样的两遍取样：若空间足够而创建文件失败，则说明是 inode 先行耗尽，它与空间是两个独立的信号。

## 5. 节点侧工具：CRI 客户端与旁证客户端

**默认选择是走 CRI 的那个客户端**（CRI 命令行客户端 `crictl`，由 cri-tools 提供）：它的接口在上游被作为稳定承诺，看到的对象与节点代理的认知一致。运行时自带的客户端只用于做旁证，**不用它执行写操作**。

| 想知道什么 | 走 CRI 的客户端 | 旁证客户端 | 关键字段 |
| --- | --- | --- | --- |
| 这个节点上有哪些沙箱 | `crictl pods` | 以沙箱镜像运行的那个对象 | 沙箱 ID 与名称 |
| 有哪些容器、状态如何 | `crictl ps -a` | `ctr -n k8s.io containers list` | 容器 ID、名称、状态 |
| 某个容器为什么退出 | `crictl inspect` 与上一次运行的日志 | —— | 退出原因与退出码要一起看 |
| 镜像是哪一份 | `crictl images -v` 与 `crictl inspecti` | `ctr -n k8s.io images list` | 列表里的标识与**清单摘要**不是同一个值 |
| 拉取或创建失败的原始原因 | —— | 运行时服务日志 | 原始错误只在这里出现 |

下面的输出只用于展示列名与字段位置：其中的数值与标识仅作示意，不代表你的环境。

```text
CONTAINER        IMAGE               CREATED         STATE    NAME   ATTEMPT
a1b2c3d4e5f6     registry.example/…  2 minutes ago   Running  web    0
```

有两条差异必须在现场核对：

1. **同一个负载的沙箱不会出现在容器列表里。** `crictl ps -a` 列出的是容器，而沙箱由 `crictl pods` 列出；若使用旁证客户端查看，沙箱会以"以沙箱镜像运行的那个对象"的形态出现。同一个对象在两套工具中的名称与归属并不相同，这是"数量对不上"最常见的来源。
2. **旁证客户端必须显式带上运行时自己的命名空间参数。** 若不带该参数，它查看的是另一套存储，列表里自然不会出现那个镜像，这就是"用另一个客户端看不到镜像"这类假阴性的成因。

子命令与字段名随客户端版本变化，按**现场客户端的版本文档**取值。

## 6. 从构建到节点落盘：一次闭环

```bash
# 验证：一次构建产出多个平台的制品并推送（只在实验环境做，推送会改变仓库状态）
docker buildx build --platform linux/amd64,linux/arm64 -t registry.example/demo:probe --push .
```

```bash
# 验证：节点上拿到的这一份对应哪条平台链、清单摘要是什么
crictl inspecti registry.example/demo:probe
```

判据需要分三处查看：在**仓库侧**看索引里有几条平台条目，以及每条的 `platform` 字段取值；在**节点侧**看镜像的清单摘要与各层摘要；在**本地**看内容存储中已有层所占的比例。

拉取耗时必须拆成三段，否则无法定位瓶颈所在：

| 段 | 边界 | 判据 |
| --- | --- | --- |
| 解析与鉴权 | 从发起请求到第一个字节到达 | 需要查看生效的凭证来源、名字解析与仓库往返 |
| 下载 | 从第一个字节到最后一个字节 | 需要查看同时段的网络吞吐曲线与本地已有层占比 |
| 解压落盘 | 从下载完成到目录树就绪 | 需要查看同时段的磁盘写入曲线与文件系统的已用容量 |

判据：若吞吐没有占满而磁盘写入已经占满，瓶颈在解压落盘；若两者都不高却仍在等待，瓶颈在仓库侧、鉴权往返或节点自身的请求限速。

## 7. 制造四类失败，各取一次原始证据

**仅在可丢的实验集群上制造这些失败**；每一类都要先记录所做的改动，使做完之后能够改回原状。

| 造哪一类失败 | 怎么造 | 取哪条证据 | 判据 |
| --- | --- | --- | --- |
| 沙箱不可用 | 把节点侧的沙箱镜像指向一个无法拉取的引用 | 事件中的原因短语 + 运行时日志 | **一个业务容器都不会出现**，这一条本身就是判据 |
| 根文件系统准备失败 | 使容器要使用的根路径或挂载点在节点侧不可用 | 事件中的原因短语 + 运行时日志 | 容器尚未被创建 |
| 运行时档位不存在 | 给负载指定一个该节点上没有声明的档位 | 事件中的错误消息 | 进入终态且不会自愈，需要修改对象或修改节点配置 |
| 拉取鉴权失败 | 用一个对该仓库没有读权限的拉取密钥引用私有镜像 | 运行时日志中的原始错误 | 原始错误显示为鉴权失败，而不是"没有这个镜像" |

这四类失败的报错文本不同，处置动作也完全不同（改制品、改节点配置还是改凭证来源）。**先确定属于哪一类，再执行处置动作。** 每次只在一个节点上制造一类失败，处置记录中写明改动的字段与改回后的核对方式（该节点恢复 Ready，且新负载能够创建成功）。

## 8. 采样、留证与清理的分界

| 动作类别 | 例子 | 在哪做 |
| --- | --- | --- |
| 只读观测 | 列表、详情、日志、文件系统已用容量与接口文件 | 在生产集群上也可以执行 |
| 改变对象的动作 | 删除容器、触发回收、修改节点配置 | 只在可丢的实验环境中执行 |
| 清理类动作 | 释放镜像层与内容 | 先在非生产环境确认后果；在生产上要先记录当前已用容量与**预计释放量**，事后再取一次同口径读数作为验收 |

一句话判据：**"删了"与"释放了"是两件事**，释放量由引用关系决定；若没有事后的同口径读数，就无法区分"没有清理干净"与"清理之后又重新增长"。

## 常见坑

| 常见做法 | 后果 |
| --- | --- |
| 拿宿主机的根目录当作容器的根来尝试 | 可能破坏宿主机；实验应当单独准备目录 |
| 只执行 `chroot` 就认为做出了容器 | 只改变了根，在权限方面没有做任何处理 |
| 在容器内读取内存总量来判断这个容器的额度 | 读到的是宿主口径，而不是这个容器的额度 |
| 手工进入运行时根目录删除文件以腾出空间 | 那些目录属于内部状态；外部读取或删除会让运行时在清理资源时遇到异常 |
| 用旁证客户端删除对象以求"清干净" | 集群侧状态与节点事实分离 |
| 不带命名空间参数就用旁证客户端查询镜像 | 看到的是另一套存储，从而得出"节点没有拉下来"的假阴性 |
| 只取一次读数就下结论 | 单点值无法区分"本来就大"与"正在增长" |
| 在生产节点上直接执行清理动作 | 释放量不可预期，可能破坏正在运行的容器对镜像的引用 |

## 要点自测

**问：一次 `unshare` 调用能不能同时建立多类命名空间？怎么验证？**

答：可以，因为标志位是位掩码。验证的方式是在调用前后逐类比较命名空间标识：带上了标志的类型，其标识会发生变化；没有带上的类型，标识保持相同。

**问：为什么建立 PID 命名空间时要带上 `--fork`？**

答：建立 PID 命名空间的那个进程本身不会被移入其中，只有它的第一个子进程才成为新命名空间里的一号进程。若不带 `--fork`，结果就是"命名空间已经建立，而当前会话并不在其中"。

**问：怎么在现场确认"容器进程没有被守护进程直接托管"？**

答：应查看容器进程的父进程是谁，以及托管进程的数量与节点上负载数量之间的对应关系。判据落在节点上的进程树里。

**问：可写层里的"删除"是一个条目而不是"没有"，这能解释什么？**

答：它可以解释三件事：删除不会释放只读层所占的空间；文件被删除之后若仍被某个进程打开，它依然占用空间；以可写层为对象做增量备份时，这个条目必须被视为一次真实变更。

**问：为什么四个"占用了多少"的数经常差好几倍？**

答：因为它们量的并不是同一类存储占用：压缩后的体积、内容存储中的 blob、解压并落地的目录树，以及连同元数据在内的合计。判据是同口径两次读数的差值，而不是任何一个绝对数值。

**问：容器一直停在创建阶段，怎么用一次取样把范围缩到三段之一？**

答：应看清"到哪一步为止"：沙箱没有建立起来时，一个业务容器都不会出现；根文件系统没有准备好时，容器尚未被创建；容器进程创建失败时，前两样都已经具备。三者的报错文本不同，各取一次原始证据即可完成归类。

**第一反应不要做什么**：不要拿宿主机的根目录做实验；不要把 `chroot` 当作隔离；不要在容器内判断这个容器自身的额度；不要在尚未取得两次同口径读数之前就下结论说存在泄漏；也不要在生产节点上执行清理动作而不先记录已用容量与预估释放量。
