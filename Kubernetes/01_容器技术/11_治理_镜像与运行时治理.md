# 镜像与运行时治理

## 1. 这些上限分别配在哪一层

容器这一层的困难在于"该配在哪"与"是谁在配"经常对不上：同一个效果可能由节点上的运行时配置、运行时的命令行参数、节点代理的配置，甚至制品本身决定。因此需要把下列上限逐项归位。

| 想控制的 | 配在哪一层 | 影响范围 | 谁负责 | 改了要重新验证什么 |
| --- | --- | --- | --- | --- |
| 根文件系统的组织方式（快照器） | 运行时的 CRI 配置 | 该节点上的全部容器 | 节点基线的维护者 | 磁盘占用、首次写延迟与 inode 稳定性；跨节点比较之前必须先对齐 |
| 沙箱镜像 | 运行时的 CRI 配置 | 该节点上全部负载 | 节点基线的维护者 | 该镜像是否可拉取；若它无法拉取，则所有业务容器都无法启动 |
| 内容与快照的落点 | 运行时的根目录与状态目录配置 | 该节点上全部镜像与容器 | 节点基线的维护者 | 是否与容器可写层、日志位于同一文件系统；只有同盘时才需要放在一起观察已用容量 |
| 与节点代理必须一致的那个开关（典型是 cgroup 驱动） | 运行时的配置与节点代理的配置，**两侧都要对** | 该节点上既有与新创建的容器 | 节点基线的维护者 | 一旦不一致，既有容器重建沙箱就会失败，且**重启节点代理可能解决不了**；这属于敏感操作 |
| 运行时档位（多运行时并存时的命名） | 运行时的 CRI 配置声明档位，负载侧选择档位 | 节点侧行为，不改变对象语义 | 节点基线 + 应用发布的共同约定 | 若档位不存在，则失败发生在节点侧，并且不会自愈 |
| 容器日志的单文件上限与份数 | 节点代理的配置 | 该节点上全部容器 | 节点基线的维护者 | 日志能够保留多久、能够占用多少；采集端是否已经取走 |
| 镜像与内容的回收策略 | 运行时的回收 + 节点代理侧的回收触发 | 该节点上的镜像与层 | 节点基线的维护者 | 回收是否会与发布节奏互相冲突 |
| 内容与层的组织方式（层怎么切） | 制品本身（构建流程） | 所有节点 | 制品与构建流程的负责人 | 每次发布的传输量与落盘量；若层切分不合理，每次发布都会产生大量新层 |
| 引用的形态（标签还是摘要） | 制品引用（发布流程） | 所有节点 | 发布流程的负责人 | "两边是否同一份"能否被证明；标签可以被重新推送 |
| 内容的来源可信（签名） | 制品与签名流程 | 所有节点 | 制品与供应链负责人 | 签名是否随制品一起更新，以避免出现"签名还在但内容已换"的情况 |
| 校验是否强制（准入） | 集群侧的校验环节 | 整个集群 | 平台侧的策略负责人 | 策略生效之前应先观察，以避免使发布阻塞 |
| 运行身份、能力集、系统调用过滤 | 负载的运行时约束声明 | 单个负载 | 应用发布的负责人 | 缺少任何一层都不会报出同一种错误；改动必须一次到位 |

**两条归属原则**：

1. **节点级的东西不要写进制品**。快照器、沙箱镜像、落点、节点代理与运行时的一致性开关，都不是应用能够声明的属性；若把它们当成应用配置，就会出现"同一个制品在不同节点行为不同"却无法归因的情况。
2. **制品级的东西不要依靠节点侧作为保底手段**。层怎么切、引用写标签还是摘要，属于制品与发布流程；以节点侧"多拉几次"或"手工把标签改掉"作为保底手段，等于把可复现性交给运气。

## 2. 交付产物

### 2.1 容器节点基线卡

每个节点池一张。字段集合与取法为运行时版本与端点、快照器与根文件系统组织方式、镜像与容器存储及日志的落点、与节点代理必须一致的那个开关、沙箱镜像、日志轮转配置、回收策略，以及一次典型拉取与启动的三段耗时；交付与评审时要写出的是下列内容：

| 字段 | 取值来源 | 交付时要给出 |
| --- | --- | --- |
| 运行时名称与版本 | 运行时的版本接口 | 具体版本号，而不是"最新版" |
| 运行时端点 | 运行时配置 | socket 路径；后续所有查证都以它为准 |
| 快照器与根文件系统组织方式 | 运行时配置 | 具体实现，以及它与其它节点之间的差异 |
| 镜像存储、容器存储、日志的落点 | 挂载信息 | 是否同盘；若同盘，则已用容量要放在一起看 |
| 与节点代理一致的那个开关 | 两侧生效配置 | 两侧各自的值，必须写清"已核对一致" |
| 沙箱镜像 | 运行时配置 | 完整引用（含摘要） |
| 日志轮转配置 | 节点代理配置 | 单文件上限与份数 |
| 镜像与内容回收策略 | 运行时 + 节点代理 | 触发条件与预期释放量 |
| 一次典型拉取与启动的三段耗时 | 同口径多次测量 | 解析、下载、解压落盘三段各给出一个基线值 |

### 2.2 镜像引用规范

一页纸，写清三件事，供发布流程与评审对照：

- **引用形态**：生产环境写清单摘要；标签只作为人可读的别名，并且必须在发布记录中保留"标签 → 摘要"的对应关系。
- **层组织**：约定基础层与依赖层的顺序，使"只改了应用"的发布能够复用尽量多的层。
- **秘密与制品**：明确"任何密钥不进制品"，并写清例外情况的补偿措施（外部注入、轮换周期）。

### 2.3 运行时变更影响面评估单

在节点池上升级或改配置前填写，字段：

| 字段 | 要回答的问题 |
| --- | --- |
| 变更对象 | 运行时大版本、配置项，还是节点代理侧 |
| 是否跨大版本 | 若跨大版本，则列出现时命中的弃用项清单 |
| 两侧一致性 | 与节点代理必须保持一致的那个开关，在改动前后各是什么值 |
| 运行面影响 | 运行中的容器是否会重启（按 shim 与守护进程寿命解耦的口径回答，并注明服务单元的配置是否已经确认） |
| 操作面影响 | 变更窗口内哪些新操作会失败（创建、删除、执行、拉取） |
| 依赖同一端点的组件 | 监控、日志采集等是否会一并中断 |
| 回滚方式 | 回滚到哪个版本、配置怎么回、需要多久 |
| 验收方式 | 变更之后取哪几个读数，以及与基线卡的哪个字段比较 |

### 2.4 层与内容增长的处理记录

| 字段 | 要回答的问题 |
| --- | --- |
| 现象与时间 | 哪个文件系统出现增长、从什么时候开始、当时的已用容量是多少 |
| 两次同口径读数 | 用两次同口径读数算出增长斜率，而不是采用单点值 |
| 归属结论 | 增长归到镜像层、可写层，还是日志；依据是什么 |
| 处置动作 | 走哪个受控入口、预计释放多少 |
| 事后验收 | 按同口径再取一次读数，实际释放了多少 |
| 防复发 | 是改制品层组织、改发布频率，还是纳入基线卡 |

### 2.5 运行时升级操作单

一页纸，配合 2.3 的评估单使用。每一步都要能回答"取哪个读数"，并给出"不通过就不往下走"的判据。

| 步 | 动作 | 取什么读数 | 通过判据 |
| --- | --- | --- | --- |
| 1 | 定变更对象：运行时大版本、配置项，还是节点代理侧 | 运行时自己报告的版本与生效配置 | 生效值取自运行时的报告，而不是配置文件的文本 |
| 2 | 清掉当前命中的弃用项 | 运行时列出的弃用项清单 | 清单为空才进入下一步；若清单非空，说明配置中存在"看起来正确但不生效"的键 |
| 3 | 记录两侧必须一致的开关的当前值 | 运行时报告的值与节点代理侧的值 | 两侧一致才继续；不一致本身就是既有故障，应先修复它，再讨论升级 |
| 4 | 取样基线 | 2.1 基线卡的全部字段，含一次拉取与启动的三段耗时、当前磁盘已用容量 | 每个字段都要落到纸面上，事后的验收才有对照物 |
| 5 | 定顺序与粒度 | —— | 先运行时、后节点代理；一次只动一个节点，先非生产、再一个生产节点、最后按池推进 |
| 6 | 执行升级并确认运行面 | 升级后原有容器是否还在运行、容器进程的父进程是谁 | 运行中的容器没有重启；若整组被重建，应立即停止并回滚，不要继续处理下一个节点 |
| 7 | 确认操作面窗口 | 窗口内哪些新操作会失败（创建、删除、执行、拉取），是否与发布节奏重叠 | 窗口已经通知到发布方；若与发布节奏重叠，则应改期 |
| 8 | 验收 | 按 2.1 的字段逐一与基线比对；用一次拉取加启动复测三段耗时 | 全部字段都落在预期区间；没有新增的弃用项 |
| 9 | 回滚预案 | 回到哪个版本、配置怎么回、需要多久 | 在改动第一个节点之前就要写好；回滚之后同样取一遍基线读数。回滚之前必须先确认既有容器是否已经按新语义创建过：若已经创建过，回滚会重现"重建沙箱失败"，此时应更换这台节点，而不是把配置改回去 |
| 10 | 收尾归档 | 把实际影响面与 2.3 上写的差异记下来 | 差异有解释，而不是"和预计的差不多" |

**两条纪律**：

- **第 6 步是"不通过就停"的那一步。** 它判的是**既有容器能否重建**，而不只是新容器能否起来。两侧那个开关不一致时，既有容器重建沙箱会失败，而重启节点代理可能无法解决；这类问题只能通过更换节点或重装来解决。
- **操作面与运行面要分开写进通知。** 运行面没有影响，并不等于操作面没有影响：变更窗口里发起的新操作会失败。

## 3. 与其它领域的接口

只写接口，不替对方做决定：

- **发布流程**：本层只要求"引用形态"与"层组织"两条约定，并把"标签 → 摘要"的对应关系纳入发布记录；发布节奏与灰度策略不属于本层的决定。
- **主机侧通用能力**：内核参数、文件系统选型、通用磁盘已用容量的治理属于主机主题域；本层只回答"容器这一侧有哪几类存储占用、分别由谁释放"。
- **GPU 与高速网络数据面**：设备与内核模块、设备直通、无损网络配置属于 AI 基础设施主题域；本层只回答"制品与运行时怎么把这些东西带进容器、以及带进来之后权限由谁给"。
- **集群侧的策略**：签名是否强制校验、准入环节怎么配，属于承载策略的那一层；本层只回答"摘要、签名与强制校验是三件不同的事，缺少其中任何一件，供应链都没有形成闭环"。
- **集群侧的资源与压力**：磁盘已用容量越线之后谁被清理、按什么顺序，属于承载节点压力的那一层；本层只回答"引用关系决定什么能被释放"。

## 4. 一个治理场景

**背景**：某节点池连续三次在发布日之后出现磁盘告警，每次都以清日志临时降低已用容量；第三次之后，要求给出根治方案。

**按层归位、按占用类型定因、按斜率验收，处置过程如下**：

1. **先定层**：三次的处置动作都是"清日志"，但日志是三类存储占用中最小的一类，这说明处置动作配错了层，真正在增长的那一类占用从未被确认过。
2. **再定占用类型**：取两次同口径读数（发布日当天与次日），把增长归到镜像层、可写层、日志三者之一。假定结论是"镜像层贡献了绝大部分增长"。
3. **找制品侧的原因**：镜像层增长与发布频率、镜像体积、层组织有关。核对本次发布新增了几层、每层多大，以及是否存在"每次发布只改动少量内容却导致整层失效"的切分方式。
4. **改成制品侧的动作**：调整层组织，让应用层单独成层、基础层得到复用；把"标签 → 摘要"写进发布记录；把镜像体积纳入发布评审的检查项。
5. **交出产物**：
   - 一张节点池的**基线卡**（新节点的交付标准）；
   - 一份**引用规范**（发布流程的上游约定）；
   - 一份**层与内容增长的处理记录**（含两次读数、归属结论、验收结果）；
   - 若同时调整了回收策略，附一张**变更影响面评估单**。
6. **验收**：下一个发布日之后按同口径再取两次读数，确认斜率下降；若斜率未下降，则回到第 2 步重新确定占用类型，而不是再增加一条清理脚本。

**这个场景的要点**：治理动作要落在**产生增长的那一层**。"清日志"是一个正确的技术动作，但它作用于错误的层；必须先确定哪一类占用在增长，再确定该由哪一层负责，这个顺序不能颠倒。

## 5. 常见坑

| 常见做法 | 后果 |
| --- | --- |
| 把快照器、沙箱镜像这类节点级选择写进应用文档 | 应用无法声明它们；出现"同制品不同行为"时无从归因 |
| 用"最新版"记录运行时版本 | 无法在事后复现当时的判断，也无法判断跨版本配置键位问题 |
| 变更评估只写"会重启容器吗"，不写"窗口内哪些操作会失败" | 会低估影响面：运行面没有影响，并不代表操作面没有影响 |
| 清理动作不做事后验收 | 释放量未知；下次告警时无从判断是没有清理干净，还是又增长回来 |
| 用单点读数判断"已经稳定了" | 增长属于斜率问题；单点值无法区分"本来就大"与"正在增长" |
| 把签名当作"校验已经生效" | 签名、摘要、强制是三件事；没有校验环节时签名只是存在 |
| 把节点级一致性开关当成可以随时在线修改的普通配置 | 既有容器重建沙箱时会失败，并且重启节点代理可能无法解决 |
| 把升级做成一次性全池滚动 | 操作单第 6 步一旦不通过，整池都会处在"既有容器重建会失败"的状态；应一次只改动一个节点，先留出可回滚的样本 |

## 值班口径

被追问"为什么节点级的东西不要写进制品"时，答法是：快照器、沙箱镜像、落点、节点代理与运行时的一致性开关，都是节点基线的组成部分；制品只能在节点给定的能力里运行，并不能声明这些能力。若把它们写成应用文档，就会让"同一个制品在不同节点行为不同"这件事失去归因路径。

被追问"一次磁盘告警的处置动作怎么判断它配错了层"时，答法是看它作用于哪一类占用。三类存储占用中日志通常最小；如果处置动作总是清日志，而增长的归属从未被确认过，那么这个动作就配错了层。正确的顺序是：先确定哪一类占用在增长（依据是两次同口径读数的斜率），再确定这一类占用由谁负责，最后才选择动作。

被追问"运行时变更的影响面要分哪两面写"时，答法是分运行面与操作面。运行面回答运行中的容器会不会重启（按托管进程与守护进程寿命解耦的口径回答，并注明服务单元的配置是否已经确认）；操作面回答变更窗口内哪些新操作会失败（创建、删除、执行、拉取）。只写运行面会低估影响。

被追问"摘要、签名、强制校验在治理上分别对应谁的职责"时，答法是：摘要对应制品与发布流程（引用形态要固定到摘要）；签名对应制品与供应链（随制品一起更新）；强制校验对应平台侧的策略（先观察再强制）。三者是三个责任人的三段工作，不能合成一条"镜像已经安全"的结论。

被追问"为什么清理动作必须留事后验收"时，答法是："删了"与"释放了"是两件事，引用关系决定实际释放量。没有事后的同口径读数，就无法区分"没有清理干净"与"清理之后又增长回来"，下一次告警还会重复同一个判断错误。

**第一反应不要做什么**：不要用"清日志"回答每一次磁盘告警；不要把节点级选择写进应用交付文档；不要在变更评估里只回答"会不会重启容器"；不要把签名当成"已经校验过"；也不要仅凭单点读数宣布问题已经稳定。
