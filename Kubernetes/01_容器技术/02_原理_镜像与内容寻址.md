# 镜像与内容寻址

## 1. 用名字引用制品的四类问题

制品要能够在多台机器上分发，并且要求"两边跑的是同一份"。若标识方式只有"位置 + 名字 + 标签"（`registry.example.com/nginx:1.27`），则下面四类问题会同时出现：

| 问题 | 具体表现 | 后果 |
| --- | --- | --- |
| 同名不同内容 | 同一个标签被重新推送过，两台机器在不同时间取到不同的内容 | 环境不可复现，"我这里是好的"这一说法无法被证伪 |
| 无法校验 | 传输链路或存储被改动过时，接收方无从判断 | 完整性只能依靠信任，不能依靠验证 |
| 无法去重 | 十个镜像共用同一个基础系统，因此各存一份、各传一份 | 仓库与节点磁盘以及跨机房带宽成倍浪费 |
| 无法增量 | 每次都要传输整份制品 | 拉取时间与实际变更量脱钩 |

文件系统与版本控制领域早已有现成答案：**不按名字索引，而按内容索引**。名字与标签因此退化为"一个指向某份内容的、可变的指针"，内容本身则由它自己的哈希值命名。镜像规范选择了同一条路径，于是四类问题被一起解决：重算哈希即可校验；同一份内容只有一个地址，因此天然去重；分发按地址进行，因此只传输缺失的部分；引用一个哈希就是引用一份固定内容。

## 2. 一份镜像是一棵由内容地址串起来的树

镜像并不是一个文件，而是四类对象互相指向的结果：

| 对象 | 作用 | 媒体类型 |
| --- | --- | --- |
| 镜像索引（image index） | 列出同一个逻辑镜像在不同平台上的清单，供拉取方按平台挑选 | `application/vnd.oci.image.index.v1+json` |
| 镜像清单（manifest） | 指向"一份配置 + 若干层" | `application/vnd.oci.image.manifest.v1+json` |
| 镜像配置（config） | 运行参数与层的顺序：`architecture`/`os`、`config`（`Env`/`Cmd`/`Entrypoint`/`User`/`WorkingDir`/`Labels`/`StopSignal` 等）、`rootfs.diff_ids`、`history` | `application/vnd.oci.image.config.v1+json` |
| 层（layer） | 一个差分归档（tar，可压缩） | `application/vnd.oci.image.layer.v1.tar`、`…tar+gzip`、`…tar+zstd` |

清单里指向其他对象的每一项都是一个**描述符（descriptor）**，它固定携带三个字段：`mediaType`、`digest`、`size`；索引里的条目还可以携带 `platform`。

**这棵树里没有一处写"名字"。** 名字只存在于"仓库的某个标签指向哪个 digest"这一处映射之中。因此，"镜像叫什么"属于仓库侧的可变状态，而"镜像是什么"才是内容本身。

老一代的媒体类型（容器引擎早期使用的那几种）与 OCI 这几种在结构上兼容，仓库与运行时会同时识别两套。因此，"用某个构建工具构建、在另一个运行时上运行"不需要转换；这不是兼容性妥协，而是两者本来就描述同一件事。

## 3. 摘要一次解决校验、去重、增量与版本固定

digest 的写法是 `算法:十六进制`，例如 `sha256:0f1e…`，其计算对象是**内容自身的字节**。现场要分清的是它究竟在计算哪一份字节：**"摘要"其实是四个不同的东西，混用是这类排障中最常见的口径错误**：

| 名字 | 算的是哪份字节 | 出现在哪 | 怎么读 |
| --- | --- | --- | --- |
| 层摘要（layer digest） | 层**按存储形态**（通常已压缩）的字节 | 清单的 `layers[]` 描述符 | 仓库里那份 blob 的名字；单位是字节，`size` 字段给的就是它 |
| 差分 ID（DiffID） | **未压缩**的层归档的字节 | 配置的 `rootfs.diff_ids`，按层顺序 | 规范明确警告不要与层摘要混为一谈：同一层有这两种字节形态，两个值必然不同 |
| 镜像 ID（ImageID） | 配置 JSON 的字节 | 节点上运行时的镜像列表 | `crictl images` 的 `IMAGE ID` 显示的就是它，**不是**按摘要固定镜像时写的那个 |
| 链 ID（ChainID） | 由前一层的结果与当前层的 DiffID 拼起来再算 | 运行时内部给快照命名 | 既不是层摘要也不是差分 ID，而是"这一层叠上去之后"的标识；现场一般只在核对快照时用到 |

由此得到三条判据：

- **要排除"标签被重推过"的干扰**，就把引用写成 `仓库@sha256:…`，此时写的是**清单**的 digest；
- **要判断两个镜像是不是同一份内容**，应当比较**清单**的 digest，而不是比较层：只改一个环境变量会生成新的配置，进而生成新的清单，而所有层一个都没有变；
- **镜像的身份在清单这一层，不在层这一层**。两台机器上同一个标签拉到的层全都一样、只有 `Env` 差一个值，它们仍然是两个不同的镜像。

两条格式硬规定。第一条针对**消费摘要的那一侧**，也就是构建工具与节点上的运行时：规范要求它能计算并校验 `sha256` 摘要，这条是强制项；`sha512` 也被注册，但属于可选，当前注册表只有这两个算法。第二条针对**摘要本身的写法**：其余算法（含 `blake3`）**规范未注册**，不应按已注册算法写进选型；编码**必须是小写十六进制**，大写形式不允许。仓库一侧不在第一条的约束范围内：它的职责是按地址存取，校验责任落在取走内容的那一侧。

## 4. 层是差分，不是快照

每一层是一个 tar 归档，按 `diff_ids` 的顺序依次应用到空目录上，从而得到容器的根文件系统。层是**相对于下层的差分**，因此"删除"必须在格式中有对应的表示：

| 归档中的条目 | 含义 |
| --- | --- |
| `.wh.<名字>` | 白障（whiteout）：在这一层删除下层同名条目。它是一个**普通空文件**，名字就是 `.wh.` 加上被删条目的名字 |
| `.wh..wh..opq` | 不透明目录（opaque）：这个目录在更下层的内容全部不可见 |

几条容易记反的语义：

- **白障只作用于更下层**：它遮住的是下层里的同名条目，不会删掉本层自己新加的内容。
- **不透明目录先于本层同级条目生效**，与它在归档里的位置无关。
- **`.wh.` 后面必须跟名字**，没有名字属于非法归档；因此一个真实文件**不可能**以 `.wh.` 开头。
- 实现**应当**生成显式白障，但**必须**能接受两种写法：逐条删除，以及一个不透明目录声明；两者语义等价。

这是**归档格式里的表示**，与运行时在磁盘上采用的表示不是同一套（磁盘上的形态不属于本篇的内容）。然而两者表达同一件事，因此"镜像里删掉一个文件会不会变小"有两层答案：层本身会因为这个条目略微变大，而被删的内容仍留在更下层的 blob 里。也就是说，**镜像的历史只增不减**。真正的体积下降要靠重新构建一条更短的层链，而不是靠删除。

另外两件在格式里就有、却常被当成实现细节的事：

- **元数据变更不产生文件系统差异，但仍在 `history` 里留下一条记录**。只改 `Env`/`Cmd`/`Labels` 时，会出现一条标记为"无层"的历史记录；有的构建工具还会补一个空层条目，使层数与历史对齐。因此，**层数不等于"改过几次文件"**。
- **平台选择发生在索引这一层**。节点按自己的 `os`/`architecture`（必要时还有 `variant`）挑选条目；规范要求索引中**恰好有一条与之匹配**，实现按顺序扫描并取第一个匹配项，因此多个条目同时命中时，结果取决于仓库侧的条目顺序。没有匹配条目时，失败发生在**节点拉取时**，报错形如"清单里没有匹配的平台"并附上摘要。因此，**本机拉取成功不代表集群节点上一定成功**。

## 5. 这几个标识的读法

| 看什么 | 是什么 | 单位 | 判据 | 与谁同看 | 看到它转向哪一步 |
| --- | --- | --- | --- | --- | --- |
| `crictl images` 的 `IMAGE ID` | 配置（config）的 digest | 摘要字符串 | 与你要固定的 manifest digest 相比，**不等**是常态；拿它当作"按摘要固定成功"的证据就是误判 | `crictl inspecti` 输出的 manifest 与各层 | 想确认"拿到的就是那一份"→ 改比 manifest digest |
| `crictl inspecti` 的 manifest 与 layers | 该镜像在本地的清单与其各层摘要 | 摘要字符串，每个带 `size`（字节） | 层摘要逐个相同才说明层被复用；层相同并不等于镜像相同 | 配置的 `diff_ids` | 层相同而镜像 ID 不同 → 差异在配置（元数据），不在层 |
| 清单各层 `size` 之和 | 该镜像**压缩后**的体积 | 字节 | 它只代表仓库侧的大小，与节点磁盘占用无关 | 节点侧快照目录的实际占用 | 两者差数倍是正常的 → 转去看未压缩占用 |
| 引用的写法 | 标签还是 `仓库@sha256:…` | — | 生产引用要固定到摘要；标签只作为人可读的别名 | 拉取策略与准入校验 | 只有标签 → 任何"两边不一致"的排查都失去确定性 |

## 6. 分发：仓库只负责按地址存取

分发协议的职责是"如何按地址存取"，而不是"如何组织镜像"；它的端点集合、按 blob 增量拉取、跨仓库挂载与凭证来源不属于本篇负责的范围。判断后续现象所必需的性质只有一条：**blob 只要还被别的清单引用就仍然存在，因此删除标签不等于删除数据。**

## 7. 凭证、完整性与来源可信是三件不同的事

仓库提出的第一个问题是"你是谁"，第二个问题才是"你要的是哪份内容"。分发机制只解决第二个问题，第一个问题由另外的机制解决：凭证有多个可能来源，各自优先级不同，鉴权失败时的第一问是**这几个来源里现在生效的是哪一个**。这几条的判据不属于本篇负责的范围。

而"摘要固定"所解决的范围要说得更窄一些：

| 问题 | 靠什么 | 判据 |
| --- | --- | --- |
| 我拿到的是不是我要的那份内容 | 摘要（重算哈希） | 摘要一致即可判定，不需要信任链路 |
| 这份内容是谁给的、有没有被替换 | 签名与来源证明（把签名作为独立的制品，通过"指向被签对象"的字段挂上去） | 有没有签名、签名是否属于可信主体。**镜像格式本身对此不做任何强制** |
| 集群有没有真的校验上面两件事 | 准入环节 | 没有准入校验时，签名只是"存在"，不构成防线 |

**这三件事不能互相替代**：摘要固定只保证"和你要的是同一份内容"，并不保证"这一份内容里没有后门"；签名只保证"这份内容确实来自某个主体"，并不保证"这个主体是你允许的"；而这两件事都要有准入环节去强制，才在集群里成立。

## 8. 抽象模型的适用边界

1. **标签是可变状态。** `latest` 本身没有"最新"的语义；它出现得如此频繁，只是因为省略标签时工具会补上这个名字。（该规则及其例外以官方文档的镜像一节为准。）也就是说，它经常是"忘了写标签"的产物，而不是一个版本策略。
2. **"删掉就没了"不成立。** 无论是在仓库里删除标签，还是在构建时于某一层删除文件，内容都可能仍留在更下层的 blob 里。秘密一旦写进某一层，重建镜像不会让它从已经推送的 blob 里消失。因此，**密钥绝不该进镜像**，这是这条性质的直接推论。
3. **"镜像多大"有三个口径。** 清单各层 `size` 之和是压缩后体积；节点上解压落盘后是未压缩体积；多个镜像共享层之后真正新增的占用又是另一个数。**规范里根本没有"镜像总大小"这个字段**，所有大小都是工具按各自口径求和的结果，因此不同工具给出不同的数属于正常。
4. **平台不匹配要到节点才暴露。** 索引里没有对应条目时，构建与推送都能成功，错误直到某个节点真正去拉时才出现。
5. **可复现性依赖引用形态。** 按标签引用时，"各节点跑的是不是同一份"取决于各节点各自拉取的时刻；这一点与节点是否重新拉取、与本地是否已有缓存共同决定。

## 常见误解

| 常见说法 | 事实 |
| --- | --- |
| 「`latest` 就是最新版本」 | 它是一个普通标签；不写标签时默认补 `latest`，这才是它出现得多的原因 |
| 「镜像 ID 就是镜像的唯一身份」 | 运行时列表里的 `IMAGE ID` 是配置的 digest；镜像身份在清单的 digest 上，按摘要固定固定的是后者 |
| 「层一样，镜像就一样」 | 元数据（`Env`/`Cmd`/`Labels`）不同会产生不同的配置与清单，因此是两个不同的镜像 |
| 「在构建文件里删掉文件，镜像就变小了」 | 删除在同一层里是白障条目，被删内容留在更下层；只有重建整条层链才真的变小 |
| 「标签固定了，各节点跑的就是同一份」 | 标签可在仓库端被重推；是否重新拉取还取决于拉取策略与本地缓存，两者要一起看 |
| 「每个节点都要把整个镜像从仓库完整下一遍」 | 分发单位是 blob，节点上已有的层不重传；跨仓库还有挂载机制避免重复复制 |
| 「用了 digest 就安全了」 | digest 只解决完整性；来源可信要靠签名与证明，而且要有准入环节去强制 |
| 「仓库里删掉标签，磁盘就该降下来」 | 只要还有其它清单引用这些 blob，内容就仍然存在 |

## 要点自测

**问：为什么镜像用内容寻址，而不是用名字加版本号？**

答：因为内容寻址把四件事一次解决：重算哈希即可校验完整性；相同内容只有一个地址，因此天然去重；分发按地址进行，因此只传输缺失的部分；引用一个摘要就是引用一份固定内容，不受标签被重推的影响。名字与标签因此退化为"一个可变的指针"，只用来给人看。

**问：一份镜像由哪些对象组成，它们之间怎么指？**

答：镜像索引按平台分支到若干镜像清单；清单指向一份配置和若干层；配置里的差分 ID 列表按顺序与这些层对应。每一处指向都是一个描述符，固定携带媒体类型、摘要、大小三个字段；这棵树里没有一处写"名字"。

**问：`crictl images` 里的 `IMAGE ID` 和"按摘要固定镜像"用的是同一个值吗？**

答：不是。`IMAGE ID` 是配置的 digest；按摘要固定镜像时写的是清单的 digest。要核对"我拿到的到底是不是那一份"，应当取清单的 digest 来比较。

**问：只改了一个环境变量，层一个都没变，为什么这是两个不同的镜像？**

答：环境变量在配置里，配置变了就会生成新的配置对象，进而生成新的清单。镜像的身份在清单这一层；层复用只说明文件系统内容相同，不说明镜像相同。

**问：镜像里删掉一个大文件，镜像会变小吗？**

答：镜像本身不会变小。层是差分归档，删除表现为一个白障条目，被删内容仍留在更下层的 blob 里。层链只增不减，只有重建出更短的层链才会真的减少体积。

**问：仓库凭证、摘要固定、签名，这三者分别解决什么问题？**

答：凭证解决"我能不能取"；摘要固定解决"我拿到的是不是我要的那份内容"；签名与来源证明解决"这份内容是谁给的"。三者互不替代，而且都要有准入环节去强制，才在集群里成立。

**第一反应不要做什么**：不要用标签判断"各节点跑的是不是同一份东西"；不要把"仓库里删掉了"当成"字节没了"；不要看到层完全一致就断定是同一个镜像；不要用某个工具报出的"镜像大小"去做容量规划，应先确认它量的是压缩体积、未压缩占用，还是去重后的增量；也不要把"用了摘要"当成供应链已经安全。

- OCI Image Spec 的 `manifest.md`、`image-index.md`、`config.md`、`layer.md`、`descriptor.md`、`media-types.md`：四类对象的结构、媒体类型字符串、差分 ID 与层的对应关系、白障与不透明目录在归档里的表示、描述符的固定字段、`history` 与空层。本篇引用的注册表与措辞按 **v1.1.1** 取值；媒体类型与摘要算法表会随规范增补，核对时以该版本的 `media-types.md` 与 `descriptor.md` 为准。
- OCI Distribution Spec：`/v2/` 端点族、按摘要存取 blob、分块上传与跨仓库挂载的语义、鉴权与授权的作用范围。
- Kubernetes 官方文档的镜像一节：拉取策略的默认规则、拉取密钥的来源与优先级、按摘要引用镜像的写法。
- 具体仓库实现的文档（分发实现、缓存与代理、跨仓库挂载的支持范围）：**端点与能力随实现与版本变化**，以现场所用仓库的版本文档为准。
- 上述规范以**当前稳定版**为准；仓库与运行时可同时接受两套媒体类型，具体支持范围以现场所用的仓库与运行时版本文档为准。
