# 容器与运行时的节点侧观测

## 1. 问题与工具的对应关系

集群侧的工具只能说明"对象处于什么状态"，而节点侧的工具才能说明"机器上实际有什么"。两边使用的并不是同一套标识，因此第一步始终是建立两者之间的对应关系。

| 想知道什么 | 用什么 | 关键字段 / 关键点 |
| --- | --- | --- |
| 这台节点使用哪个运行时、端点在哪里 | 节点代理的启动参数与配置文件、运行时的服务状态 | 运行时端点决定后续使用哪一套客户端 |
| 某个负载在节点上对应哪些容器 | CRI 客户端的沙箱列表与容器列表 | 沙箱名称通常包含负载名与命名空间，容器名称中包含容器名 |
| 某个容器为什么退出 | 容器的详细信息、该容器上一次运行的日志 | 退出原因与退出码需要一起看；原因是判据，退出码只是线索 |
| 容器里此刻有哪些进程 | 通过 CRI 的执行通道进入容器 | 它与集群侧的执行入口走同一条通道，差别只在于是否经过 API 层 |
| 节点上是否有这个镜像、是哪一份 | 镜像列表与单个镜像的详细信息 | 只有摘要字段才是判据；列表里的镜像标识与清单摘要并不是同一个值 |
| 镜像与容器各自占用了多少磁盘 | 运行时的文件系统用量接口、容器可写层的占用 | 单位与"哪一类存储占用"必须同时说明 |
| 运行时自身的报错信息 | 运行时的服务日志 | 拉取、解压与创建失败的原始原因出现在这里 |
| 沙箱持有的那组命名空间 | 沙箱的详细信息 | 排查"一组容器共享了什么"时应查看它，而不是业务容器 |
| 容器被限流、被内存限制终止的记录 | cgroup 接口文件（属于内核接口，而不是命令） | 接口文件是只读观测入口，比容器内的整机视图可靠 |
| 当前配置命中了哪些弃用项 | 运行时的弃用项清单 | 它是跨大版本迁移排查的首选，能够把"键已经失效"这类静默问题提前暴露 |
| 运行时侧的容器身份与运行配置 | 运行目录下"命名空间 / 容器"两级路径中的状态文件（只读） | 它是与集群侧对象建立对应关系时的最终凭据 |

在执行处置动作之前，需要分清两类东西：**CRI 客户端是命令**，必须在节点上执行，并且要能够访问运行时的端点；**cgroup 接口文件与运行目录下的状态文件是内核或组件写出的接口文件**，直接读取即可，不需要额外工具。两者混用最容易出现的错误是"在容器内读取接口文件"，这样读到的往往是宿主侧的那一类存储占用。

还有一条决定"使用哪一件工具"的硬性依据：**运行时自带客户端与 CRI 客户端的稳定性等级并不相同**。上游把运行时自带客户端明确定义为**不受项目支持，次要版本就可能发生破坏性变更**，而它自身的 gRPC 接口、shim 接口与 CRI 接口都被标记为稳定。因此排障时的默认选择是**走 CRI 的那个客户端**，因为它与节点代理使用同一套接口，看到的对象与节点代理的认知一致；运行时自带客户端只用于旁证，**用它执行写操作会导致集群侧状态与节点事实分离**。

## 2. 怎么读这些数字

运行时的状态字段的含义按机制确定；节点侧观测特有的读数是"机器上实际剩下多少、正在往哪里写"。

| 看什么 | 是什么 | 单位 | 判据 | 与谁同看 | 看到它转向哪一步 |
| --- | --- | --- | --- | --- | --- |
| 镜像文件系统的用量 | 运行时存放镜像层的那个文件系统已用了多少、还剩多少 | 字节 | 越接近耗尽，拉取与解压越可能失败；与"高阈值"比较只决定回收何时开始 | 同一文件系统上的可写层与日志、可用 inode | 将满 → 先分清是镜像层、可写层还是日志在增长 |
| 容器的可写层用量 | 这个容器自身写入的那一部分 | 字节 | 它是独占的，随容器删除而释放；异常增长通常来自应用写文件，而不是写日志 | 该容器的日志大小、挂载进来的卷的用量 | "删了容器而占用没有下降" → 主要占用集中在共享只读层，而不在该容器自身 |
| 可用容量与可用 inode | 承载容器与日志的文件系统还剩多少空间、还剩多少个 inode | 字节 / 个 | 这是两个独立信号：inode 先耗尽时，表现为"有空间却创建不了文件" | 是哪一类存储占用在增长 | 创建文件失败 → 先分辨是空间还是 inode |
| 日志文件的大小与份数 | 标准输出落成的那一类文件 | 字节 / 个数 | 上限在"单文件上限 × 份数"这个量级；达到上限后旧内容被丢弃，而不是被压缩 | 采集端是否已经把内容取走 | 日志"缺了一段" → 区分是轮转丢弃，还是采集没有取走 |
| 退出码与退出原因 | 进程如何结束、由谁使它结束 | 整数 / 枚举 | **原因优先于退出码**：同一个码可能来自进程自己退出、被信号杀死或被内存限制终止 | 该容器上一次运行的日志、cgroup 的事件计数 | 重启次数在增长 → 先确定原因，再讨论修改什么 |
| 镜像摘要（清单摘要） | 这一份制品在节点上的身份 | 摘要字符串 | 只有与引用里写的值比对，才能判定"拿到的是否就是约定的那一份" | 各层摘要 | 摘要一致而行为不同 → 问题不在分发 |
| 沙箱与容器的标识 | 运行时侧的对象 ID 与名称 | 字符串 | ID 是运行时使用的身份，名称是给人看的 | 集群侧的对象状态 | "集群侧说有、节点上没有" → 用名称反查 ID 之后再核对 |
| 当前配置命中的弃用项 | 运行时列出的、当前配置里已经失效或即将失效的键 | 列表 | 列表非空就说明配置文件里存在"看起来正确但已经不生效"的键 | 运行时的大版本、配置文件的键位 | 升级前排查 → 先清掉命中的项，再变更版本 |
| 运行时侧的容器身份与运行配置 | 运行目录下两级路径中的状态文件（只读） | 文件 | 两边对不上时，以这里的记录为准 | 集群侧的容器标识 | 对不上 → 回头查是谁绕过了接口 |
| 节点对仓库的请求速率 | 节点代理向镜像仓库发起请求时的限速 | 每秒请求数 / 突发额度 | 文档默认值是每秒 5 个、突发 10 个（本库版本口径下的默认值，**现场取值**）；一次发布中多个镜像同时拉取会被它限住 | 本次发布的镜像个数、单节点并发拉取配置 | 拉取排队而网络不忙 → 转向"限速"，而不是"带宽" |
| 拉取耗时 | 从解析到落地的总时长 | 秒 | 必须拆成解析、下载、解压落盘三段；只看总时长无法定位 | 同时段的网络吞吐与磁盘写入曲线 | 吞吐没有占满而磁盘写入已经占满 → 瓶颈在解压落盘 |

## 3. 采样纪律与基线卡

一个节点应当留下的容器基线卡，字段固定为以下几项。取样的纪律是同口径、带时间戳、至少两次、留原始输出；这张卡要留下的是下列字段：

| 字段 | 取值来源 | 为什么要有 |
| --- | --- | --- |
| 运行时名称与版本 | 运行时的版本接口 | 它是行为差异的第一来源，跨节点比较之前要先对齐 |
| 运行时端点与存储路径 | 运行时配置 | 它决定镜像与容器落在哪一个文件系统上 |
| 快照器与根文件系统的组织方式 | 运行时配置 | 它决定磁盘占用与首次写延迟的量级 |
| 镜像存储与容器存储所在文件系统 | 挂载信息 | 它决定哪些存储占用会互相挤占 |
| 日志目录与轮转配置 | 节点代理配置 | 它决定日志能够保留多久、能够占用多少 |
| 沙箱镜像与其来源 | 运行时配置 | 沙箱镜像拉不下来时，一个业务容器都不会启动 |
| 一次典型拉取与启动的耗时（三段分开记） | 同口径多次测量 | 没有这个基线，就无法判断"是否变慢了"以及慢在哪一段 |

只读观测（列表、详情、日志、文件系统已用容量、接口文件）**在生产节点上也可以做**。清理类动作（删除容器、删除镜像、触发回收）**必须先在非生产环境确认后果**，并且在生产上要先记录当前已用容量与预计释放量，事后再取一次同口径读数作为验收。

## 4. 常见故障与排查方向

### 4.1 容器一直停在创建阶段

现象：单个负载长时间不进入运行状态，而同一节点上的其他负载运行正常；集群侧看到的容器状态一直未就绪。

按顺序排查：

1. **先看停在哪一步**：沙箱没有建立起来、根文件系统没有准备好，还是容器进程创建失败，这三者的报错文本完全不同。应先读取事件中的原因短语与运行时日志中的原始错误，不要先猜测。
2. **沙箱问题**：检查沙箱镜像是否在节点上、运行时配置里指向哪一个镜像，以及它的拉取是否失败。沙箱失败时不会出现任何业务容器，这一点本身就是判据。
3. **镜像问题**：拉取失败的原始原因需要到运行时日志中查看，可能是鉴权失败、域名解析失败、清单里没有匹配的平台或层校验失败，这四种原因的处置完全不同。
4. **容器创建失败**：常见原因包括运行时找不到指定的运行时档位、根文件系统准备失败，以及运行身份或能力集不满足要求。

一份合格的回答应当具备以下结构：**结论**（停在哪一步）、**依据**（哪一条事件、日志里的哪一行）、**边界**（是个例还是该节点上的全部负载）、**动作**（修改节点配置还是修改制品）。

### 4.2 容器起了又立刻退出

现象：某个容器的重启计数持续上升，且间隔逐渐变长；应用的表现时好时坏。

按顺序排查：

1. **先取退出原因，再看退出码**：退出原因能够区分"进程自己退出""被信号杀死"与"被内存限制终止"，只看数字会把这三类混为一类。
2. **查看上一次运行的日志**，而不是当前这一次的日志，因为当前这一次可能取自刚刚启动、尚未产生输出的进程。
3. **查看资源占用**：被内存限制终止时，判据在节点侧的 cgroup 事件计数与内核日志里，而不在容器内的整机视图里。
4. **查看退避间隔**：间隔逐渐拉长属于正常现象，并不代表问题正在缓解。

一份合格的回答应当具备以下结构：**结论**（谁使这个进程结束，或者它为什么自行退出）、**依据**（退出原因 + 上一次日志 + 事件计数）、**边界**（该节点上的所有副本还是单个副本）、**动作**（修改额度、修改启动参数还是修改制品）。

### 4.3 节点上拉取变慢或直接失败

现象：一次发布在多台节点上同时进行时，拉取耗时明显变长；或者部分节点直接报出拉取失败。

按顺序排查：

1. **分清是哪一类失败**：可能是鉴权、名字解析、平台不匹配或层校验，这四类的报错文本不同，处置方式也不同。
2. **拆开耗时三段**：解析与鉴权、下载、解压落盘。应查看同时段的网络吞吐与磁盘写入曲线：若吞吐没有占满而磁盘写入已经占满，瓶颈在落盘；若两者都不高却仍在等待，瓶颈在仓库侧或限速。
3. **查看本地已有层的占比**：占比高说明复用生效，耗时应当较短；占比低说明这一次的层切分使每次发布都产生大量新层。
4. **查看凭证来源**：当只有部分节点失败时，先确认那些节点上生效的凭证是哪一份。

一份合格的回答应当具备以下结构：**结论**（失败类型或瓶颈所在段落）、**依据**（原始错误 + 三段耗时 + 已有层占比）、**边界**（全部节点还是部分节点）、**动作**（修改制品层切分、修改节点限速还是修改凭证来源）。

### 4.4 节点磁盘被容器相关内容占满

现象：节点上文件系统的可用空间持续下降，拉取与创建开始失败；清理之后，过一段时间又会再次发生。

按顺序排查：

1. **分清是哪一类存储占用**：可能是镜像层、可写层，也可能是日志。三者的量法与释放条件都不同，而且只有落在同一个文件系统上时才会互相挤占。
2. **查看是哪一项在增长**：镜像层的增长与发布频率、镜像体积、回收策略相关；可写层的增长与某个应用写文件相关；日志的增长与输出量相关。判据是两次同口径读数的差值，而不是绝对数值。
3. **查看回收入口**：镜像是按引用回收的，因此要检查还有哪些镜像与容器引用着这些层；数量减少并不等于空间已经释放。
4. **查看 inode**：空间足够而创建文件失败时，说明是 inode 先行耗尽。

一份合格的回答应当具备以下结构：**结论**（哪一类存储占用、哪一项在增长、还能维持多久）、**依据**（两次读数与差值）、**边界**（只影响本节点还是影响所有节点）、**动作**（清理哪一类内容，以及防止复发的配置或制品改动）。

## 5. 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 在容器内读取内存与 CPU 的整机视图，以此判断这个容器是否吃紧 | 读到的是宿主口径；容器的额度写在节点侧的 cgroup 接口文件里 |
| 用运行时自带的客户端删除容器，以此"清理现场" | 这样做绕过了 CRI，集群侧状态与节点实际情况脱节；清理应当走受控入口 |
| 只看镜像数量来判断磁盘占用 | 层是共享的，数量与空间并不同步；应当查看文件系统用量与共享关系 |
| 把"重启计数高"直接等同于"制品有 bug" | 退出原因可能来自节点侧的额度限制或运行环境 |
| 只取一次读数就判断存在泄漏 | 没有斜率，就无法区分"本来就大"与"正在增长" |
| 在生产节点上直接执行清理动作 | 释放量不可预期，而且可能破坏正在运行的容器对镜像的引用；应当先记录、再预估、再执行、再验收 |
| 认为回收未使用镜像时会把沙箱镜像也一并清掉 | 该操作会跳过被运行时引用的镜像，而沙箱镜像正是被引用的那一个；它不在回收范围之内，并不代表回收失败 |
| 手工进入运行时根目录删除文件以"腾出空间" | 那些目录属于实现细节；外部读取或监听会使运行时在清理资源时遇到设备忙与失效句柄 |
| 拿不同节点的读数直接进行比较 | 运行时、快照器、存储路径与阈值不同时，两个读数不可比 |

## 6. 要点自测

**问：为什么节点侧的观测不可省略，集群侧的对象状态不够用？**

答：集群侧看到的是节点代理上报的结论，而节点上还存在已经退出但被保留的容器，以及实际占用的磁盘空间。任何涉及"机器上还剩什么、占用多少、由谁在写"的问题，都必须在节点侧取证。

**问：一个"看起来一样"的镜像，怎么确认两台节点用的是同一份？**

答：应比对清单摘要，而不是比对标签或列表里的镜像标识。标签可以在仓库端被重新推送；列表里的标识是配置的摘要，与按清单摘要固定版本时所使用的值并不是同一个。

**问：节点报告磁盘可用空间还有很多，却创建不了新文件，最可能是什么？**

答：最可能是可用 inode 耗尽。空间与 inode 是两个独立信号，在小文件极多的场景（例如大量层文件、大量日志分片）中会先耗尽 inode。判断依据是同时读取可用字节数与可用 inode 数。

**问：容器反复重启时，为什么先看退出原因而不是退出码？**

答：退出码只是一个数字，同一个数字可能来自进程主动退出、被信号杀死或被内存限制终止；退出原因则直接给出这一区分，它决定下一步是查制品、查节点资源还是查启动参数。

**问：一次读数能说明磁盘在泄漏吗？**

答：不能。它只给出某一个时刻的值。要判断是否存在泄漏，必须有同口径的至少两次读数并算出斜率，因为"本来就大"与"正在增长"在单点读数上是同一个现象。

**问：为什么排障默认用走 CRI 的那个客户端，而不是运行时自带的客户端？**

答：前者的接口在上游被作为稳定承诺，它看到的对象与节点代理的认知一致；后者被明确定义为不受项目支持，次要版本就可能发生破坏性变更，因此只适合做旁证。用后者执行写操作会导致集群侧状态与节点事实分离。

**第一反应不要做什么**：不要在容器内判断这个容器自身的资源额度；不要用运行时自带的客户端删除对象以求"清干净"；不要在尚未取得两次读数之前就下结论说存在泄漏；不要在尚未拆开三段耗时之前就断言"拉取慢是网络问题"；也不要在生产节点上直接执行清理动作而不先记录已用容量与预估释放量。
