# 分发与供应链

## 1. 分发的四项要求：取到字节只是其中一项

前面几节已经说明了制品本身：内容按地址命名，四类对象互相指向。接下来的问题是**它如何从仓库到达节点**。这一步需要同时满足四项要求：

| 要满足的 | 具体要求 |
| --- | --- |
| 完整性 | 当传输链路或存储被改动过时，接收方能够自行判断出来 |
| 去重与增量 | 多个镜像共用的基础层只传输一次，并且只存一份 |
| 版本固定 | "两边运行的是同一份"这件事不能取决于拉取时刻 |
| 归属与授权 | 只让有权限的人取，并且取到的内容能够追溯到是谁提供的 |

这里的关键观察是：**前三条由"按内容寻址"这一性质直接给出**，而第四条与前三条无关，因为它关心的是"谁"，而不是"什么内容"。若把这两类问题混在一起，就会出现"用了摘要所以安全"这种错误结论。

## 2. 仓库只负责按地址存取

分发协议的职责是"如何按地址存取"，而不是"如何组织镜像"。核心端点如下：

| 端点 | 用途 |
| --- | --- |
| `GET /v2/` | 探活与协议版本确认 |
| `GET` / `HEAD /v2/<name>/manifests/<reference>` | 取清单，`reference` 可以是标签也可以是 digest |
| `GET` / `HEAD /v2/<name>/blobs/<digest>` | 取任意 blob（层、配置、清单） |
| `POST /v2/<name>/blobs/uploads/` 与后续提交 | 分块上传，最后按 digest 提交 |
| `POST /v2/<name>/blobs/uploads/?mount=<digest>&from=<仓库>` | 跨仓库挂载：内容已存在时直接建立引用，不重传 |

由此得到三条对生产有直接影响的结论：

1. **拉取的单位是 blob，而不是镜像。** 缺失哪一层就补哪一层；同一个基础系统被多个镜像共用时，节点上只保留一份。这就是"一个节点上运行十个镜像、占用远小于十个镜像体积之和"的原因。`HEAD` 请求使客户端在下载之前就能确认某个 blob 是否已经存在。
2. **拉取由节点发起，而不是由控制面发起。** 每个需要使用该镜像的节点各自去仓库取一次，凭证也按节点解析；节点之间互不知情，因此可以同时拉取同一个镜像。**集群层面没有"镜像缓存"这回事**：镜像预热与跨节点共享缓存属于另外的产品能力，而不是这套系统自带的语义。
3. **"仓库里没有了"与"字节没了"是两件事。** blob 只要仍被别的清单引用，就仍然存在，因此删除标签不等于删除数据。反之，**一个标签的变化也不影响已经按摘要落地的那些节点**，因为它们本来就不需要再询问仓库。

## 3. 凭证：先确定身份来源

仓库提出的第一个问题是"你是谁"，第二个问题才是"你要的是哪份内容"。分发解决第二个问题，第一个问题由另外的机制解决。凭证来源不止一处，并且**它们之间存在优先级**：

| 来源 | 在哪声明 | 现场口径 |
| --- | --- | --- |
| 负载自己声明的拉取密钥 | 编排层的对象字段 | 优先级最高；同一个仓库，以这一份为准 |
| 挂在服务账号上的拉取密钥 | 编排层的对象字段 | 次之 |
| 节点上的凭证插件 / 运行时自身的仓库配置 | 节点侧配置 | 最后；**"节点上配过这个仓库的账号"不必然覆盖负载自己声明的那一份** |

因此，鉴权失败时的第一问是：**这几个来源里现在生效的是哪一个**，而不是只看节点配置。第二问才是"这个凭证有没有这个仓库的读权限"。

## 4. 摘要固定、签名与准入是三件不同的事

这是本篇最需要分清的一处。"供应链安全"经常被当成一件事来讲，它实际上是三层：

| 问题 | 靠什么解决 | 判据 | 解决不了什么 |
| --- | --- | --- | --- |
| 我拿到的是不是我要的那份内容 | 摘要（重算哈希） | 摘要一致即判定，**不需要信任链路** | 不说明这份内容本身是否可信 |
| 这份内容是谁提供的、有没有被替换 | 签名与来源证明（签名作为独立制品，通过"指向被签对象"的字段挂上去） | 有没有签名、签名属于哪个主体、证明里的构建过程是否可信 | 内容格式本身对此**不做任何强制** |
| 集群有没有真的校验上面两件事 | 准入环节 | 没有准入校验时，签名只是"存在"，不构成防线 | 不改变内容与来源本身 |

三条推论：

- **摘要固定属于"防篡改"，而不是"防恶意"。** 它保证"和你要的是同一份"，不保证"这一份里没有后门"。
- **签名属于"防替换"，而不是"防权限"。** 它保证内容确实来自某个主体，不保证这个主体是你允许的，后者属于策略问题。
- **没有准入校验时，前两层都只是记录。** 拿到摘要与签名之后由谁来查、查出不通过如何处理，属于另一个环节的事。

## 5. 分发侧的现场读法

| 看什么 | 是什么 | 单位 | 判据 | 与谁同看 | 看到它转向哪一步 |
| --- | --- | --- | --- | --- | --- |
| 引用里的 `@sha256:…` | 清单的 digest | 摘要字符串 | 写的是清单摘要才算"按摘要固定"；写成标签就不是 | 本地清单的摘要 | 只有标签 → 任何"两边是否同一份"的排查都失去确定性 |
| 清单本身 | 指向一份配置与若干层的对象 | JSON，带各层描述符与 `size` | `size` 是**压缩后**字节数，只代表仓库侧大小 | 节点侧未压缩占用 | 两者差数倍属正常 |
| 某一层的 `HEAD` 结果 | 该 blob 在仓库里是否存在、大小多少 | 字节 | 存在即为 200 且带 `Content-Length`；不存在为 404 | 本地内容存储里是否已有同名摘要 | 本地已有 → 不会重传，这正是"增量分发"的来源 |
| 拉取凭证的来源 | 生效的那一份凭证来自哪一层 | — | 按优先级逐层排除，确认生效来源后再判命中 | 仓库返回的鉴权错误 | 401/403 → 先定来源，再查权限，最后才改节点配置 |
| 签名的存在与主体 | 是否存在指向该清单的签名制品及其签发主体 | — | 存在不等于通过；主体是否可信由策略决定 | 准入环节的校验结果 | 有签名但无校验 → 供应链实际未闭环 |

## 6. 抽象模型的适用边界

1. **"用了摘要就安全了"只覆盖了三分之一。** 摘要解决完整性，来源可信要靠签名与证明，而两者都要有准入环节去强制。缺少任何一层，供应链都没有形成闭环。
2. **秘密一旦进入层就无法撤回。** 层链只增不减，已被推送的 blob 里仍然保留着它；重建镜像只对之后拉取的人生效。这条性质是"密钥不应进入镜像"的直接理由。
3. **凭证不止一处，而且优先级不直观。** 排查鉴权问题时，"节点上配过"不能作为结论。
4. **仓库的能力受分布式现实约束。** 跨仓库挂载、范围请求与关联制品查询这些能力，标准只写成"应当支持"或干脆没有写，因此**更换一个仓库实现就可能整套失效**；依赖它们的能力（尤其是按需拉取）在更换仓库时要重新验证。
5. **拉取的规模化成本在节点而不在仓库。** 每个节点各拉一次，因此"同一镜像铺到一千个节点"是节点侧的带宽与磁盘问题，不是仓库出口带宽问题；反之，节点上已缓存的层也不会被跨节点复用。
6. **"平台不匹配"在拉取时才暴露。** 索引里没有对应条目时，构建与推送都能成功；错误直到某个节点真正去拉时才出现，报错形如"清单里没有匹配的平台"。

## 常见误解

| 常见说法 | 事实 |
| --- | --- |
| 「用了 digest 就安全了」 | digest 只解决完整性；来源可信要靠签名与证明，且要有准入环节去强制 |
| 「签名过了就万事大吉」 | 签名是"防替换"，不是"防权限"；主体是否可信、集群有没有校验，是另外两层 |
| 「仓库里删掉标签，磁盘就该降下来」 | 只要还有其它清单引用这些 blob，内容就仍在 |
| 「节点上配了仓库账号，就按它取镜像」 | 负载与服务账号上声明的拉取密钥优先级更高；要先确认生效来源 |
| 「镜像预热可以省掉节点拉取」 | 这套系统本身没有集群级镜像缓存；预热是额外产品能力，不是自带语义 |
| 「每个节点都要把整个镜像完整下一遍」 | 分发单位是 blob，节点上已有的层不重传；跨仓库还有挂载机制避免重复复制 |
| 「推送成功就等于所有节点都能拉到」 | 平台不匹配、仓库能力差异、凭证来源不同都会让某些节点拉不到，而错误只在节点侧出现 |
| 「构建时把密钥删掉就安全了」 | 被删内容仍留在更下层的 blob 里；已推送的镜像撤不回 |

## 要点自测

**问：分发要满足的四件事里，哪几件是"按内容寻址"直接给出的，哪一件不是？**

答：完整性、去重与增量、版本固定这三件由内容寻址直接给出：算哈希即可校验、同一内容只有一个地址、按地址只搬缺的、引用摘要即固定内容。**归属与授权**不是，它关心"谁"，需要另外的机制；两件事混在一起就会出现"用了摘要所以安全"的错误结论。

**问：为什么说"拉取由节点发起"会改变容量规划的对象？**

答：每个要用该镜像的节点各自去仓库取一次，节点之间互不知情，集群层面没有共享缓存。因此"同一镜像铺到大量节点"是节点侧的带宽与磁盘问题，要按节点数乘以镜像增量计算；仓库出口带宽只是其中一段。

**问：仓库凭证的三个来源是什么顺序？排鉴权失败时的第一问是什么？**

答：负载自己声明的拉取密钥优先，其次是服务账号上挂的，最后才是节点侧配置或运行时自身的仓库配置。第一问是"现在生效的是哪一个来源"，因为"节点上配过"不能作为结论。

**问：摘要固定、签名、准入分别解决什么问题？**

答：摘要固定解决"我拿到的是不是我要的那份内容"，判断时不需要信任链路；签名与来源证明解决"这份内容是谁提供的、有没有被替换"；准入解决"集群有没有真的校验前两件事"。三者互不替代，缺少准入时前两层只是记录。

**问：为什么"构建时删掉密钥"不能作为补救措施？**

答：层是差分归档，删除表现为白障条目，被删内容仍留在更下层的 blob 里，而层链只增不减。已经推送过的镜像无法撤回，因此补救办法是重新构建一条不含密钥的层链并轮换那个密钥，而不是"删掉重建"。

**问：为什么推送成功不等于所有节点都能拉到？**

答：至少三种原因：索引里没有该平台时错误只在节点拉取时出现；仓库对跨仓库挂载、范围请求、关联制品的能力差异会让依赖这些能力的方式失效；凭证来源按节点解析，不同节点生效的那一份可能不同。

**第一反应不要做什么**：不要把"用了摘要"当成供应链已经安全；不要看到"有签名"就认为集群校验过了；不要把"仓库里删掉了"当成"字节没了"；不要用节点上的仓库配置推断负载实际使用的是哪份凭证；也不要把"推送成功"当成"各节点都能拉到"。

## 参考文档

- OCI Distribution Spec：`/v2/` 端点族、按摘要存取 blob、分块上传与跨仓库挂载的语义、鉴权与授权的作用范围、对范围请求与关联制品的措辞强度。
- OCI Image Spec 中关于签名与来源证明如何作为制品挂到被签对象上的说明：`subject` 字段的语义、证明的存放方式。
- Kubernetes 官方文档的镜像一节：拉取密钥的来源与优先级、按摘要引用镜像的写法、拉取失败的退避重试行为。
- 供应链工具与规范（签名工具、证明格式、准入校验器）的官方文档：签名与校验的实际落地形态；**具体能力随工具版本变化**。
- 具体仓库实现的文档（缓存与代理、跨仓库挂载、关联制品支持范围）：**端点和能力随实现与版本变化**，以现场所用仓库的版本文档为准。
