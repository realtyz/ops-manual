# 一份制品到一个运行中的进程

## 1. 一次运行请求背后的八个环节

"用这个镜像跑起来"是运维现场最常执行的一条命令。这一句话在跨过仓库、节点与运行时的过程中，实际会经过八个环节，而每个环节失败的表现、判据与责任人都不相同：

| # | 环节 | 由谁执行 | 留下的产物 | 失败时的表现 |
| --- | --- | --- | --- | --- |
| 1 | 构建 | 构建工具（本地或 CI） | 一串差分归档，加上配置与清单，以及索引中的平台分支 | 构建期的错误只出现在构建日志中，与运行时无关 |
| 2 | 标识 | 构建或推送工具 | 每个对象的摘要（层摘要、配置摘要、清单摘要） | 摘要只在被使用时才被核对，因此构建完成并不等于内容无误 |
| 3 | 推送与保管 | 推送工具 → 仓库 | 按摘要命名的 blob，以及一条从标签到摘要的可变映射 | 推送成功并不代表其他节点能够拉取（权限、平台、仓库能力） |
| 4 | 解析 | 节点上的高层运行时 | 本次运行所要使用的那一份清单摘要 | 解析失败发生在拉取之前：鉴权、网络、清单中没有匹配的平台 |
| 5 | 拉取 | 节点的高层运行时 → 仓库 | 本地内容存储中与仓库字节相同的 blob | 拉取失败有明确的原始原因，记录在运行时的服务日志中 |
| 6 | 落地 | 高层运行时 + 快照器 | 每层解压出的目录树，以及该容器独占的可写层 | 解压与落盘会同时消耗磁盘带宽与容量，这一段是"拉取慢"最常被忽略的原因 |
| 7 | 创建 | 运行时按 CRI 接口 → OCI runtime → 内核 | 持有该组命名空间的进程、容器进程，以及一个 shim | 可能阻塞在沙箱、根文件系统准备或进程创建三处，三者的报错不同 |
| 8 | 回收 | 运行时（按引用）+ 节点代理（按水位） | 被释放的层、blob 与可写层 | 删除与释放之间隔着引用关系，这是判断"泄漏"时的关键区分点 |

```mermaid
flowchart LR
  B["① 构建<br/>差分归档"] --> I["② 标识<br/>各对象摘要"]
  I --> P["③ 推送与保管<br/>blob + 标签映射"]
  P --> R["④ 解析<br/>标签 → 摘要"]
  R --> L["⑤ 拉取<br/>只取缺的 blob"]
  L --> S["⑥ 落地<br/>解压 + 快照"]
  S --> C["⑦ 创建<br/>沙箱 → 容器 → 进程"]
  C --> G["⑧ 回收<br/>引用消失才释放"]
  G -.->|"释放出的层与 blob"| L
```

**读懂这条链的关键在于：每一个环节都有自己的"身份"标识，而这些标识并不通用。** 仓库侧的标签、清单摘要、层摘要、本地内容存储的文件名、快照标识与运行时侧的容器 ID 是六个不同的对象；任何"看起来一样"的判断，都必须先说明所比较的是其中哪一段。

## 2. 八个环节各自的现场口径

**① 构建**：产物是层，而层是差分归档。构建期所做的选择（层的边界划在哪里、哪些内容进入哪一层、顺序如何）会一直传递到其后的每一个环节，尤其是第 5 个环节的传输量与第 6 个环节的解压量；层边界应当按**变更节奏**划分，使高频改动落在尾部少数层中。构建期的秘密若处理不当，第 8 个环节的"不可撤销"就会使它变成长期风险。

**② 标识**：内容一旦确定，摘要便随之确定；反之，任何一处字节的改动都会产生新的摘要。这里最容易混淆的是四个摘要，即层摘要、差分 ID、配置摘要（运行时列表里的镜像 ID）与链 ID。其判据是"所计算的是哪一份字节"，而不是"哪一个工具显示的那个值"。

**③ 推送与保管**：仓库是"按地址存取"的存储，而不是"按镜像组织"的对象库。推送的产物是 blob 与一条标签映射，因此：标签可以随时被重新推送；blob 只要仍被引用就依然存在；"删标签"与"删字节"是两件不同的事。

**④ 解析**：这一环节决定"本次运行究竟使用哪一份内容"。引用写成标签时，解析结果取决于解析发生那一刻仓库的状态；引用写成摘要时，解析结果就是一个固定值。平台选择同样发生在这一环节：若索引中没有对应条目，错误便在此处出现，而不是在构建或推送时出现。

**⑤ 拉取**：其单位是 blob，缺少哪一层就补充哪一层。有三个必须同时考虑的因素：

| 因素 | 现场表现 | 判据 |
| --- | --- | --- |
| 本地已有层的占比 | 首次拉取远慢于后续拉取；滚动发布时各节点的表现不一致 | 拉取期间的网络吞吐与本地已有层的比例 |
| 节点对仓库的并发访问受到自身限制 | 一次发布中多个镜像同时拉取时出现排队，而网络并未占满 | 节点侧的请求速率限速配置与本次镜像的个数 |
| 凭证来源 | 同一个仓库在不同节点上的表现不同（有的成功，有的鉴权失败） | 生效的那一份凭证来自负载、服务账号还是节点配置 |

**⑥ 落地**：拉取下来的 blob 是压缩形态，而落地后的目录树是未压缩形态，两者之比通常为数倍。这一环节同时消耗磁盘带宽与容量，因此"拉取耗时"必须拆成解析、下载与解压落盘三段分别观察。快照器的选择在这一环节生效，而它属于节点级选择：同一份镜像在不同节点上的落地方式可以不同。

**⑦ 创建**：这一环节的顺序是固定的：先启动持有命名空间的进程，再建立容器的根文件系统，最后创建容器进程。该顺序决定了失败表现的分类：沙箱创建失败时，不会出现任何业务容器；根文件系统准备失败时，容器尚未被创建；进程创建失败时，前两项都已存在。三者的报错文本不同，可以从事件或运行时日志中区分。

**⑧ 回收**：释放的前提是引用消失。容器引用、沙箱引用、镜像引用与内容 blob 之间逐层指向，只要其中任何一层仍有引用，字节就仍然存在。而"水位越线时由谁首先行动"属于节点代理的策略，并不是运行时的行为。

## 3. 五条横向关系

八个环节是纵向排列的，而横向关系把它们串联起来。每一条横向关系的结论都是一句判据。

### 存储占用

| 环节 | 存储占用上发生的事 |
| --- | --- |
| ① 构建 | 这一环节产生的是压缩后的层大小（仓库侧口径） |
| ⑤ 拉取 | 本地内容存储增加一份与仓库相同的 blob；已经存在的层不会重复增加 |
| ⑥ 落地 | 快照目录增加未压缩的目录树；同一层的多个镜像各自落地一份 |
| ⑦ 创建 | 可写层开始增长；写入只读层中的文件时会额外产生一份复制 |
| ⑧ 回收 | 可写层随容器消失；层与 blob 则需要等到引用消失 |

**结论**："占了多少"必须先说清是哪一类存储占用，也就是压缩体积、未压缩落地、可写层，还是三者之和。工具报出的数值分别对应其中某一类，彼此之间不可比较。

### 身份标识

| 环节 | 用什么指认这个东西 |
| --- | --- |
| ①–② | 以层摘要（压缩形态）与差分 ID（未压缩形态）指认 |
| ③ | 以标签到清单摘要的可变映射指认 |
| ④ | 以清单摘要指认（固定版本时引用的就是它） |
| ⑤ | 以内容存储中的文件名指认，该文件名等于 blob 摘要 |
| ⑥ | 以快照标识指认（它是"这一层叠加上去之后"的结果，与上面几个标识都不同） |
| ⑦ | 以运行时侧的沙箱与容器标识指认；承载它们的进程在宿主上具有 PID |

**结论**：并不存在"唯一身份"，只存在"这一层的身份是什么"。核对时必须先说明所比较的是哪一段，否则"两边看起来一样"会把两个不同的问题混为一谈。

### 权限

| 环节 | 权限从哪来、缺了会怎样 |
| --- | --- |
| ③–④ | 仓库凭证：来源存在优先级；缺少权限时表现为鉴权失败，而不是"没有这个镜像" |
| ⑥ | 挂载标志与卷属主：可写层可写而只读层不可写，这由挂载方式决定，而不由应用决定 |
| ⑦ | 运行身份、能力集与系统调用过滤：缺少其中一层，报出的错误就不会相同 |

**结论**：权限是逐项叠加的。"容器里做不了某件事"应当拆解为"哪一层权限有所缺失"，而不是笼统地归因于"容器权限不够"。

### 信任

| 环节 | 这一层的信任靠什么 |
| --- | --- |
| ② | 摘要：重新计算哈希即可校验，不需要信任传输链路 |
| ③ | 签名与来源证明：用于确认内容来自哪一个主体 |
| ④ | 强制：由谁校验上面两层，以及不通过时如何处理 |

**结论**：三层之中缺少任何一层，供应链就没有形成闭环。摘要只解决"是不是同一份"，签名只解决"由谁提供"。

### 回收

| 环节 | 什么在引用它 |
| --- | --- |
| ⑦–⑧ | 容器 → 沙箱 → 镜像 → 层 → blob，逐层引用 |
| ⑧ | 可写层只被这个容器引用；只读层被所有用到它的镜像与容器引用 |

**结论**：引用不消失，空间就不会回来。判断"删了为什么没有下降"时，应沿着这条关系向上查找，确认还有谁在引用它。

## 4. 关键字段的完整读法

| 看什么 | 是什么 | 单位 | 判据 | 与谁同看 | 看到它转向哪一步 |
| --- | --- | --- | --- | --- | --- |
| 引用形态 | 标签，还是 `仓库@sha256:…` | — | 只有写清单摘要才算固定版本 | 本地清单的摘要 | 只有标签 → 一切"两边是否同一份"的排查都失去确定性 |
| 清单摘要 | 清单对象的摘要 | 摘要字符串 | 它是镜像的身份；与运行时列表里的镜像 ID **不是**同一个值 | 各层摘要 | 摘要一致而行为不同 → 问题不在分发环节，应核对实际运行的是不是这个工作负载 |
| 层摘要 / 差分 ID | 压缩形态 / 未压缩形态的摘要 | 摘要字符串 | 同一层有这两个必然不同的值；判断"是否复用"时看前者 | 本地内容存储里的文件名（等于层摘要） | 层全同而镜像 ID 不同 → 差异在配置，不在层 |
| 本地内容存储的文件名 | 与仓库字节相同的 blob 的名称 | 摘要字符串 | 文件名本身就是摘要，因此可以离线核对 | 仓库侧同一摘要的存在性 | 本地缺失的那几个 blob → 就是这次要传输的量 |
| 快照标识 | "这一层叠加上去之后"的标识 | 字符串 | 它既不是压缩摘要，也不是差分 ID | 快照目录里的目录树数量 | 目录树比 blob 多 → 去重只发生在 blob 一侧 |
| 运行时的文件系统用量接口 | 快照目录的未压缩占用与 inode 数 | 字节 / 个 | **不含内容存储** | 运行时根目录的实际磁盘统计 | 接口数值小、磁盘很满 → 缺少的那部分在内容存储 |
| 容器内 `df` | 承载可写层的文件系统水位 | 字节 | 它不是这个容器的额度 | 可写层自身占用 | 水位低 → 先确认是哪一类存储占用在增长 |
| 退出原因与退出码 | 进程如何结束 / 进程返回了什么 | 枚举 / 整数 | 原因优先：同一个退出码可能来自进程自身退出、被信号杀死或被内存限制终止 | 该容器上一次运行的日志、cgroup 的事件计数 | 原因是内存限制 → 去查额度；原因不是 → 去查日志与探针 |
| 沙箱与业务容器的标识 | 运行时侧的对象 ID 与名称 | 字符串 | 沙箱不承载业务；它一旦消失就意味着整组容器重建 | 集群侧的对象状态 | 集群侧存在而节点侧没有 → 用名称反查运行时侧的 ID |
| 生效的拉取凭证来源 | 负载 / 服务账号 / 节点配置三选一 | — | 按优先级确定来源，然后核对权限 | 仓库返回的鉴权错误 | 401/403 → 先定来源，再查权限，最后才改节点配置 |

## 5. 任务卡：八个环节在现场的应用

现场的问题通常是"把某一个镜像铺到某一批节点上需要多久、占用多大、会阻塞在哪一步"。把八个环节归纳成一张任务卡：

| 要回答的问题 | 在哪一个环节取数 | 取哪些数据 |
| --- | --- | --- |
| 这个制品究竟是什么 | ②④ | 清单摘要；层数与各层压缩后的大小 |
| 会传输多少 | ⑤ | 节点上已有层的比例，乘以各层压缩后的大小 |
| 会落地多少 | ⑥ | 各层未压缩大小之和，再加上可写层与日志的预算 |
| 会阻塞在哪一步 | ④⑤⑦ | 凭证来源、仓库与网络的往返、沙箱与根文件系统的准备 |
| 会不会被释放 | ⑧ | 引用关系：还有谁在引用这些层 |

这五个问题的答案都落在具体字段上；若其中任何一个问题答不出数值，就说明还没有取到证据。

## 6. 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 用"镜像列表里的标识"当作固定版本的依据 | 该标识是配置的摘要，与清单摘要不是同一个值；固定版本固定的是后者 |
| 把"拉取慢"整体归因于网络 | 拉取耗时是解析、下载与解压落盘三段的合成量；三段必须分别计量 |
| 认为删除容器或镜像会立刻释放空间 | 释放的前提是引用消失；只读层被其他镜像或容器引用时不会被释放 |
| 在容器内部判断该容器的资源额度 | 容器内看到的是整机口径；容器的额度记录在节点侧的 cgroup 上 |
| 通过手工删除运行时根目录中的文件来腾出空间 | 那些目录属于实现细节；外部的读取或监听会使运行时在清理资源时遇到设备忙与失效句柄 |
| 跨节点直接比较同一镜像的启动时间与占用 | 快照器与存储路径属于节点级选择；两者不一致时，两个数值不可比较 |
| 把"运行时守护进程重启"当作必然导致业务中断 | 容器由各自的 shim 托管；这条性质还依赖节点上服务单元的配置，配置不正确时重启会清除整个进程组 |

## 7. 要点自测

**问：这条链中"身份"一共有几个不同的对象？为什么不能只记住其中一个？**

答：至少有六个，即层摘要（压缩形态）、差分 ID（未压缩形态）、配置摘要（运行时列表里的镜像 ID）、清单摘要（固定版本时使用的值）、本地 blob 的文件名（等于层摘要）与快照标识（这一层叠加上去之后的结果）。它们分别属于不同的对象与不同的环节；任何"看起来一样"的判断都必须先说明所比较的是哪一段，否则就会把"内容相同"与"镜像相同"混为同一个问题。

**问：一次发布在多个节点上同时拉取镜像时，为什么会排队而网络却并不繁忙？**

答：因为瓶颈可能出现在另外两处：节点自身对仓库的请求速率受到限制；解压与落盘消耗的是磁盘而不是网络。只有把耗时拆成解析、下载与解压落盘三段并分别计量，才能判断应当处置哪一处。

**问：容器创建环节的固定顺序为什么可以用来分类故障？**

答：顺序是先启动持有命名空间的进程，再准备根文件系统，最后创建容器进程。三者失败时留下的现场不同：沙箱失败时不会出现任何业务容器；根文件系统失败时容器尚未被创建；进程创建失败时前两项都已存在。因此，只要看"进行到哪一步为止"，就可以把问题归类，而不必笼统地说"容器起不来"。

**问：为什么"删除了容器而磁盘占用没有下降"不能直接判定为泄漏？**

答：可写层随容器一起释放，但只读层在节点内共享，它的引用来自用到它的其他镜像与容器。应当先分清三类存储占用（只读层、可写层、日志与卷），再用两次同口径的读数判断是否仍在增长，这样才能够区分"历史堆积"与"正在泄漏"。

**问：为什么"水位越线时谁先被清理"不属于本篇的范围？**

答："水位越线时由谁首先被清理"取决于节点代理的策略，属于编排层的行为，而不是容器技术栈本身的性质。容器技术栈本身只决定"引用关系决定什么能够被释放"；至于"释放的时机由谁确定"，则属于承载节点压力那一层的内容。

**第一反应不要做什么**：不要用标签判断"两边是不是同一份东西"；不要把"删除对象"当作"空间会归还"；不要在容器内部判断容器自身的额度；不要把"拉取慢"直接归因于网络；也不要手工删除运行时目录中的文件。
