# 从层到根文件系统

## 1. 问题背景：每次启动都完整展开一层

镜像是一串只读的差分归档。要让它变成可运行的根文件系统，最直接的做法是"按顺序解开到一块专属目录里"。此时三件事会同时出现：

| 问题 | 具体表现 |
| --- | --- |
| 启动成本与镜像体积成正比 | 一个 2 GiB 的镜像，每次启动容器就要写入 2 GiB；水平扩容时最先达到瓶颈的是磁盘带宽，而不是 CPU |
| 同一镜像的多个实例各存一份 | 一个节点上运行 20 个副本，就会多出 20 份完全相同的系统文件 |
| 改动一个小文件要付出整层的代价 | 分层本来是为了复用，展开之后就完全失去了意义 |

答案是把"共享"留在只读部分，并把"独占"压缩到最小：**镜像的每一层在节点上只解出一份，由所有容器共用；在此之上再为每个容器叠加一层属于它自己的可写层**。这就是联合挂载（union mount）在容器场景里的全部用途。它提供的是一个**可写视图**，而不是一个可写副本。

## 2. 快照器：把"层"和本地文件系统对接起来的那个可替换件

镜像层是远端的 blob，可写层是本地目录，两者之间需要一个组件来完成转换。运行时把这件事交给**快照器（snapshotter）**，其职责只有一句：**把"若干只读层 + 一个可写层"组织成一个目录，交给运行时当作根文件系统挂给容器。**

| 概念 | 含义 |
| --- | --- |
| 快照（snapshot） | 一份可被挂载的层视图，有唯一键，有一个可选的父快照 |
| 已提交快照（committed） | 只读、没有可写层；镜像的每一层对应一个 |
| 活动快照（active） | 有可写层、容器正在用它；同一个父快照下可以有多个 |
| 父子链 | 容器的可写层以"镜像最上面那一层"为父；链的末端才是容器能写的那一层 |

实现是可替换的，常见的有以下几类：联合挂载型（默认选择）、完整复制型（把层真的复制出来，退化为第 1 节的做法）、写时复制型文件系统（btrfs/zfs 一类）、块设备型，以及为"按需拉取"服务的几种。

**"按需拉取"这一类需要单独交代代价**，因为它们的宣传口径通常只讲启动变快。它们**不是镜像格式的标准能力**：镜像规范与分发规范里都没有"懒加载"这个原语，标准层对分发协议只使用"应当支持范围请求"这种非强制措辞。也就是说，这一层完全建立在"节点上安装了对应插件"与"镜像或索引里有该插件的私有约定"这两项之上，因此有四条无法回避的约束：

| 约束 | 后果 |
| --- | --- |
| 需要节点侧装插件并**在节点启动时配置好** | 属于节点基线，不是应用能声明的属性；有的实现还要求它作用于节点上的全部容器，否则连沙箱容器都找不到镜像 |
| 镜像或索引必须按该插件的约定生成 | 构建流程要改；不同插件之间不通用，选型即锁定 |
| 依赖仓库支持范围请求或关联制品查询 | 标准只把它写成"应当支持"，部分仓库根本不支持关联制品；换仓库可能整套失效 |
| 有的实现会**改动镜像本身**（加注解或加关联制品） | 镜像摘要因此变化、需要重新推送，而针对原始镜像做过的签名会**失效** |

还有一条与收益直接相关的：这类实现通常**对较小的层不做处理**，因此在小镜像上使用它没有收益。选型时要把"镜像有多大、仓库是否支持、构建链能否修改、签名如何续期"四件事一起评估，而不是只看启动时间。

两条必须掌握的性质：

- **快照器是节点级的全局选择，不是应用能够声明的属性。** 同一份镜像在不同节点上可以有完全不同的落地方式；在跨节点比较"同一个镜像的启动时间与磁盘占用"之前，应先确认两边的快照器一致。
- **更换快照器不是更换一个开关，而是更换一套代价模型。** 它会同时改变磁盘占用、启动时间与去重效果，因此属于节点基线变更。

## 3. 联合挂载怎么做到"共享只读 + 独占可写"

主流做法基于 overlayfs。它的模型只有四个概念：

| 概念 | 作用 |
| --- | --- |
| `lowerdir` | 一个或多个只读目录（用 `:` 分隔），越靠左越上层 |
| `upperdir` | 一个可写目录，容器里所有写操作最终落在它里面 |
| `workdir` | overlayfs 自己用的中转目录，必须与 `upperdir` 在同一个文件系统上 |
| `merged` | 挂给容器的那棵"合成"目录树 |

读取时从最上层向下查找，找到即使用；目录会做合并（下层与上层的同名目录内容叠加显示），而普通文件会被上层完全遮住。写入时，若目标文件只存在于只读层中，overlayfs 会先把**整份**文件复制到上层再修改，这一步称为 **copy-up（升层复制）**。

| 容器里的动作 | 怎么做 | 代价落在哪 |
| --- | --- | --- |
| 读只读层里的文件 | 直接从下层读 | 无额外代价 |
| 改只读层里的文件 | copy-up 整份到可写层，再改 | 写放大：改一个字节要复制整个文件；首次写入出现延迟尖峰 |
| 只改元数据（权限、时间、属主） | **默认同样触发整份 copy-up**；开启只复制元数据的模式后可只复制元数据 | 默认行为下，改一个 1 GiB 文件的权限要复制 1 GiB |
| 新建文件、写文件 | 直接写可写层 | 消耗可写层空间 |
| 删除只读层里的文件 | 在上层放一个白障条目遮住它 | 下层文件仍在，磁盘不释放 |
| 删除目录、要求目录"看起来是空的" | 上层放一个不透明目录标记 | 同上 |

**"白障"在磁盘上有两种等价写法，看到的形态不同**：一种是**设备号为零的字符设备**，另一种是**零长度普通文件加一个扩展属性**；"不透明"则是给目录加一个值为 `y` 的扩展属性。以第一种为例，在挂载点里列目录时会看到一个字符设备，而它并不是你创建的文件。另外，以非特权方式挂载时，扩展属性的命名空间会从受信任前缀变为用户前缀，因此**判断"这里究竟有没有白障"不能只按受信任前缀去查找属性**。

## 4. copy-up 的连锁代价：不止是变慢

写放大只是第一层代价。由于"文件的位置在写入前后发生了变化"，下列依赖稳定身份或原子语义的行为会一同改变：

1. **设备号与 inode 会变。** 同一路径的文件在 copy-up 前后 `st_dev`/`st_ino` 不同（除非位于同一文件系统内且启用了额外机制）。依赖 inode 做标识的缓存、去重与增量备份会把同一个文件当成两个。
2. **跨层硬链接会断。** 一个文件与它在只读层里的硬链接伙伴在 copy-up 之后不再指向同一个 inode。
3. **重命名目录会失败。** 目录是在层间"合并"而成的，无法用一次原子改名表达，因此直接返回 `EXDEV`；要让它在部分场景下可用需要额外开关，而那个开关本身有前提。
4. **`df` 的读数来自承载可写层的那个文件系统**，而不是"只读层 + 可写层"的总和。容器里 `df` 看到的可用空间，与"这个容器还能写多少"不是同一个问题。
5. **覆盖一个正在被执行的程序，在联合挂载上的结果与普通文件系统不同，而且随内核版本变化。** 在普通文件系统上写一个正在被执行的程序会被拒绝；在联合挂载上，copy-up 与写入计数的判定在多个内核版本里改过，因此这一步的结果要按**现场内核版本**核对，不能当作通用结论；升级二进制时的"先删再写"并不总能得到保护。

这几条背后是同一件事：**容器看到的根文件系统是一个由多层拼出来的视图，其读写代价与身份稳定性与普通目录不在同一个量级。** 挂载选项层面的判据（哪几个开关控制元数据复制、目录重命名与 inode 稳定性，以及各自的默认值与前提）属于文件系统本身的性质，不属于本章的内容；这里只需要知道"同一份镜像换一个挂载选项，上面五条的表现就会变"。

## 5. 节点上的三类存储占用

"这个容器占了多少磁盘"之所以经常算不清，是因为三类存储占用（只读层、可写层、日志与卷）分别记录，却可能落在同一块磁盘上：

| 存储占用 | 内容 | 归属 | 谁释放 |
| --- | --- | --- | --- |
| 只读层 | 镜像的每一层，解压落盘 | 节点级，跨容器共享 | 运行时按引用回收；没有镜像引用它之后才消失 |
| 可写层 | 容器运行期间的所有写，含被白障遮住的下层文件 | 容器级，独占 | 容器被删除时释放；被打开的文件会延后释放 |
| 卷与日志 | 挂进来的存储、标准输出落成的日志文件 | 各自独立 | 卷按存储策略回收，日志按轮转策略回收 |

前两类由运行时管理，日志由节点代理管理。它们**是否共用同一份文件系统水位取决于目录布局**：同盘则互相挤占，分盘则各自独立水位。这是"磁盘满了导致容器被清理"这类现象里最需要先确认的一件事：**先确认是哪一类存储在增长，再谈清理什么。**

落到路径上，运行时会把它管理的内容分成两处：**内容存储**里放的是与仓库里字节相同的 blob（**文件名就是它们的摘要**，因此是压缩形态）；**快照目录**里放的是每层解压出来的目录树。以下两条关系容易混淆：

- 快照的标识**既不是压缩摘要，也不是解压后归档的摘要**，而是"这一层叠加到前一层之后"算出来的结果（链 ID）；
- 同一份内容被多个镜像引用时，blob 只存一份，但**每一层解压出来的目录树通常仍各占一份**，也就是说，去重主要发生在内容存储那一侧。

运行时会在内容存储的条目上记录一个"解压后摘要是多少"的标签，这是核对"这一层解压后究竟是哪一份"的入口。

## 6. 三类存储占用的读法

三类存储占用在用工具查询时**口径不一样**，这正是"怎么算都对不上"的根源：

| 你查的东西 | 它量的是什么 | 漏掉了什么 |
| --- | --- | --- |
| 镜像列表里的体积 | 清单里各层描述符大小之和，即**压缩后**的体积 | 与磁盘占用无关，那是仓库侧的大小 |
| 运行时的文件系统用量接口 | 快照目录的**未压缩**占用与 inode 数 | **不含内容存储那一块** |
| 直接对运行时的根目录做磁盘统计 | 快照 + 内容存储 + 元数据库，三块之和 | 这才是节点上真正被占用的磁盘量 |

| 看什么 | 是什么 | 单位 | 判据 | 与谁同看 | 看到它转向哪一步 |
| --- | --- | --- | --- | --- | --- |
| 镜像列表的体积 | 各层压缩体积之和 | 字节 | 判断"从仓库拉了多少"时用它；判断"节点上占了多少"时不能用它 | 快照目录占用 | 两者差数倍是正常 → 不要当成缺陷 |
| 文件系统用量接口 | 快照目录的未压缩占用与 inode 数 | 字节 / 个 | 它是"层的解压落地"这一类存储占用；**不含内容存储** | 运行时根目录的实际磁盘统计 | 接口数很小而磁盘很满 → 缺失的那一部分在内容存储 |
| 承载可写层的文件系统水位 | 容器里 `df` 报出来的可用空间 | 字节 | 它反映的是**那个文件系统**的水位，而不是"这个容器的额度" | 可写层自身的占用、宿主水位 | 水位低 → 先确认是哪一类存储在增长 |
| 内容存储目录的文件数 | 与仓库字节相同的 blob 份数 | 个 | 跨镜像共享，因此同一份内容只有一份 | 快照目录的目录树数 | blob 一份而快照多份 → 去重只发生在前者 |

**一条官方禁令必须遵守**：运行时的根目录与运行目录**属于实现细节，不要修改里面的文件**：外部程序若读取或监听这些目录，会使运行时在清理资源时遇到"设备忙"与已失效的文件句柄。清理应当走受控入口，不要手工删除目录。

## 7. 抽象模型的适用边界

1. **"容器的磁盘占用"不是一个数。** 只读层共享、可写层独占、卷另有独立的存储占用，三者的释放条件都不同。若问"删了容器能腾出多少"，答案通常远小于"它写了多少"。
2. **删除不等于释放。** 白障遮住的下层内容仍占空间；已被删除但被进程打开的文件仍占空间；镜像层在还有别的标签或容器引用时仍占空间。在观察到"删了文件而磁盘没有下降"时，这三个原因需要分别排查。
3. **可写层随容器消失。** 不落进卷、不写出到远端的写入，在容器重建之后不存在。可写层的占用看起来很小，代价是它不可持久。
4. **身份不稳定。** copy-up 之后 inode 与设备号会变，因此任何"按 inode 记忆"的外部工具在联合挂载上都会得到不稳定的结果。
5. **快照器的选择会改变行为。** 同一份镜像在不同快照器上，磁盘占用、首次写延迟与 inode 稳定性都不同；在跨节点比较之前应先确认两边一致。
6. **层的共享是节点内的，不是集群内的。** 每个节点各存一份自己的层，跨节点没有共享；因此"镜像只在仓库里存一份"与"每个节点各存一份"同时成立。

## 常见误解

| 常见说法 | 事实 |
| --- | --- |
| 「容器删了，磁盘占用就还回来了」 | 可写层会释放，但只读层只要还被别的镜像或容器引用就仍占着；白障遮住的下层内容也不会因此消失 |
| 「`df` 显示的可用空间就是容器还能写多少」 | 那是承载可写层的文件系统水位，与这个容器的写入量、与节点其它存储占用都不等价 |
| 「改一个小文件只消耗一个小文件的空间」 | 默认会 copy-up 整份文件，写放大与文件大小成正比，与改动量无关；改元数据也会触发 |
| 「不同节点的同一镜像行为应当完全一致」 | 快照器是节点级选择；实现不同则磁盘占用、首次写延迟与 inode 稳定性都不同 |
| 「容器里的文件系统就是镜像解压出来的那份」 | 它是"只读层 + 可写层"的合成视图；只读层本身不被修改 |
| 「在容器里删掉大文件能腾空间」 | 只加了一个白障条目，下层内容仍然存在；空间要等容器与只读层的引用都消失才可能释放 |
| 「用量接口报的数就是节点上这个镜像占的空间」 | 那个接口量的是快照目录，不含内容存储；要拿全量得看运行时根目录的实际磁盘统计 |
| 「换快照器只是换了个性能选项」 | 它同时改变去重效果、磁盘占用与身份稳定性，因此属于节点基线变更 |

## 要点自测

**问：为什么要引入联合挂载这一层？不用它会怎样？**

答：不用它就得把镜像层完整展开到每个容器自己的目录里，于是启动成本与镜像体积成正比、同一镜像的多个实例各存一份、改一个小文件也要付出整层的代价。联合挂载把只读部分做成节点内共享，并把可写部分压缩成一层专属目录，因此同时解决这三件事。

**问：copy-up 在什么情况下被触发，代价是什么？**

答：往只读层里的文件写入、修改它的元数据（权限、属主、时间），以及为它建立硬链接，都会触发 copy-up；默认整份复制到可写层，因此代价与**文件大小**成正比，与改动量无关。只复制元数据的模式可以避免元数据修改引起的整份复制，但那需要额外的挂载前提。

**问：容器里删除一个只读层里的文件，磁盘为什么没有释放？**

答：删除在联合挂载上表现为在上层放一个白障条目遮住下层同名文件；下层文件本身仍在只读层里，而只读层是跨容器共享的，只有当引用它的镜像与容器都消失后才可能被回收。

**问：为什么在联合挂载上用 inode 做标识不可靠？**

答：文件在被写入前位于只读层、写入后被复制到可写层，前后处于不同的文件系统或层，因此设备号与 inode 会变。任何按 inode 记忆的缓存、去重或增量备份都会把同一个路径当成两个不同的文件。

**问：节点磁盘告警，先确认哪一件事？**

答：先确认是哪一类存储在增长：只读层（节点共享）、可写层（容器独占），还是日志与卷。三类存储占用的量法与释放条件都不同，而且只有落在同一个文件系统上时才互相挤占。确认之后才谈清理动作。

**问：为什么"用量接口报得很少"与"磁盘几乎满了"可以同时成立？**

答：那个接口量的是快照目录（层解压后的落地），不含内容存储与元数据库。要取得节点上真正的占用量，应当直接对运行时的根目录做磁盘统计；而清理仍必须走受控入口，不要手工删除目录。

**第一反应不要做什么**：不要把"删了容器"当成释放磁盘的手段，先确认占据空间的是可写层还是共享的只读层；不要把容器里 `df` 的读数当作这个容器的额度；不要在排查启动变慢时跳过 copy-up，首次写入大文件的延迟尖峰经常被误认为应用初始化慢；也不要手工删除运行时目录里的文件。
