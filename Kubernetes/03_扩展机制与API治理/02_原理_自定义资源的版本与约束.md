# 自定义资源的版本与约束

## 1. schema 决定形状，版本决定寿命

把一个新的类型注册进集群之后，提供方立刻要回答两个互相拉扯的问题：**这个类型的写入要被约束到什么程度**，以及**它的字段结构以后怎么改**。只注册不约束、或者把约束写错位置，三类问题会同时出现：

| 问题 | 具体表现 |
| --- | --- |
| 字段可以随便写 | 客户端与控制器各自解读同一份对象，错误要到运行期才被发现 |
| 约束只写在控制器里 | 不合法对象已经落库，控制器只能事后纠正或删除，写入方拿不到任何提示 |
| 改字段结构没有退路 | 存量对象散落在存储里，客户端版本不一，改字段等于同时改所有读写方 |

解决的办法有两条，且必须同时成立：**把约束写在类型这一层**，使不合法的写入在入口处就被拒绝；**把对外服务的版本与写入存储的版本分开**，使不同客户端可以各用各的版本，而存储里只保留一份表示。

## 2. 结构化 schema 决定剪枝、默认值与校验

`apiextensions.k8s.io/v1` 的 CRD 要求 schema 是**结构化的（structural schema）**：为所有值都声明类型，只在少数明确允许的位置留出"任意 JSON"。这个要求不是形式主义，剪枝、缺省值、只读字段、OpenAPI 发布与钩子转换都以它为前提；schema 不结构化时，CRD 的 `status.conditions` 里会出现 `NonStructuralSchema`，上述能力一并失效。

**字段剪枝（pruning）** 是结构化 schema 最容易被忽略的后果：写入时，schema 里没有声明的字段会被直接去掉，而不是被带上一条错误。要保留未声明的字段，必须在该处显式声明 `x-kubernetes-preserve-unknown-fields: true`。

| 看什么 | 是什么 | 单位 | 判据 | 与谁同看 | 看到它转向哪一步 |
| --- | --- | --- | --- | --- | --- |
| `spec.versions[].schema.openAPIV3Schema` | 这个版本的字段契约 | OpenAPI v3 结构 | 所有值都要有类型；有 `type: object` 且允许任意字段的位置必须显式声明保留 | CRD 的 `NonStructuralSchema` 条件 | 出现该条件 → 先改 schema，再谈剪枝与校验 |
| `x-kubernetes-preserve-unknown-fields` | 在某个位置保留未声明字段 | 布尔 | 默认不保留；声明之后该位置下的未知字段会被原样保存 | 使用该位置的上游字段 | 字段"莫名其妙消失" → 先确认它所在的层级有没有声明保留 |
| `default` | 字段的缺省值 | 与字段同类型 | 缺省值只作用于写入时缺失的字段，不会回填已经存在的对象 | 该版本的 `served` 状态 | 默认值没有出现 → 先确认请求走的是哪一个版本 |
| `status.conditions[]` 的 `NonStructuralSchema` | schema 是否结构化 | 条件类型与状态 | 为真表示存在不结构化之处 | CRD 的更新事件 | 为真 → 剪枝与转换都不会按预期工作 |

有两条现场含义值得单独记住：

- **剪枝发生在写入时，不发生在读取时。** 旧客户端多写的字段会在提交时被静默去掉；反过来，字段改名或调整层级之后，存储里的旧对象读出来仍然带着旧字段，因此字段迁移要按"先并存、后清理"的顺序做，而不是期待一次改 schema 就完成。
- **结构化是所有能力的前置条件。** 校验、缺省值、字段选择器（field selector）与转换都依赖同一个 schema；先修 schema，再看其它问题，能避免在同一份 CRD 上反复折腾。

## 3. 校验规则：三种位置各自能回答什么问题

约束可以写在三个不同的位置，能回答的问题各不相同。把它们混淆，就会出现"约束写了却不生效"或者"约束写了却拦不住"的结果：

| 位置 | 能回答什么 | 不能回答什么 |
| --- | --- | --- |
| schema 的类型与取值约束 | 单个字段的类型、是否必填、取值范围与格式 | 字段之间的相互关系 |
| schema 里的 CEL 校验规则 | 同一个对象内部多个字段之间的关系，例如下界、上界与当前值是否有序 | 其它对象的状态、集群里已经存在什么 |
| 准入策略与控制器 | 请求级别与稳态级别的判断，包括跨对象的一致性与外部系统的状态 | 它们不改变"类型本身能表达什么"，因此不能替代 schema |

CEL（Common Expression Language）校验规则写在 schema 的 `x-kubernetes-validations` 上，其要点如下：

- **规则的作用域是它在 schema 中的位置**，表达式里的 `self` 绑定到该处的值；所有规则都只作用于当前对象，官方文档明确不支持跨对象或有状态的判断。
- **`oldSelf` 只在过渡规则里有意义**，用来比较本次改动前后的值；不引用 `oldSelf` 的规则在满足条件时可以被"棘轮"豁免。
- **规则在 CRD 创建或更新时编译**，编译失败会直接拒绝这次 CRD 写入。因此规则写错的现场表现是"CRD 本身提交不上去"，而不是"对象提交不上去"。
- **每条规则可以带 `message`、`messageExpression`、`reason` 与 `fieldPath`**：`messageExpression` 优先于静态消息，两者都不适合表达时按默认文本回退；`reason` 决定返回给调用方的 HTTP 状态码，取的是规则列表中第一个失败的那一条。
- **表达式有成本预算（cost budget）**，超出预算的规则不允许上线；对策略与匹配条件的严格成本校验自 v1.32 起为稳定默认行为。

这条规则的版本演进是阶段式的：**v1.23 引入（alpha，默认关闭）→ v1.25 进入 beta（默认开启）→ v1.29 稳定（该特性门控此后被移除）**，出处是 KEP-2876 与官方特性门控页的 `CustomResourceValidationExpressions` 阶段表。升级到 v1.23 之前的版本时，规则存在但不会生效，这一点在盘查存量 CRD 时必须确认。

## 4. 校验棘轮：为什么新增规则不会立刻卡住存量对象

给一个已经在使用的类型加校验规则，会立刻遇到一个问题：存量对象大多不满足新规则，但提供方并没有能力一次改完它们。**校验棘轮（validation ratcheting）** 就是为这件事设计的：

它的判据只有一句：**更新后的对象允许仍然不合法，前提是每一个校验失败的部分在这次更新中都没有被改动；不允许把一个本来就合法的对象更新成不合法的对象。**

这条规则的实际效果是：提供方可以安全地新增校验，旧的存量对象在被改动到相关字段之前不会被卡住；一旦有人动到相关字段，就必须把它改成合法值。因此"加规则"与"改存量"必须安排在同一段窗口里，而不是先加规则、以后再慢慢清理。

棘轮有明确的例外，下列校验失败不会被豁免：量词 `allOf`、`oneOf`、`anyOf`、`not` 及其后代节点上的校验，`x-kubernetes-list-type` 与 `x-kubernetes-list-map-keys` 相关的错误，`required`，以及引用 `oldSelf` 的规则；过渡规则本身永远不参与棘轮。

它的版本演进同样是阶段式的：**v1.28 引入（alpha，默认关闭）→ v1.30 进入 beta（默认开启）→ v1.33 稳定**，出处是 KEP-4008 与官方特性门控页的 `CRDValidationRatcheting` 阶段表。

## 5. 多版本与转换：served、storage 与 storedVersions

一个类型可以同时提供多个版本，这些版本由一个"服务版本"与一个"存储版本"的关系串起来：请求以哪个版本提交、以哪个版本被读取，是**服务**的事；对象最终以哪个版本留在存储里，是**存储**的事。两者不一致时，入口组件要先把对象转换（conversion）一次。

| 看什么 | 是什么 | 单位 | 判据 | 与谁同看 | 看到它转向哪一步 |
| --- | --- | --- | --- | --- | --- |
| `spec.versions[].served` | 这个版本是否对外服务 | 布尔 | 置为 `false` 之后，该版本从发现里消失，仍在使用的客户端会直接报错 | `status.storedVersions` | 关闭服务之前，先确认存量对象已经迁出该版本 |
| `spec.versions[].storage` | 这个版本是否是写入存储的版本 | 布尔 | 有且只有一个版本为 `true` | `status.storedVersions` | 推进存储版本后，旧版本仍会留在 `storedVersions` 里，直到迁移完成 |
| `spec.versions[].deprecated` 与 `deprecationWarning` | 该版本是否已弃用 | 布尔与字符串 | 为真时对该版本的请求会返回告警头；告警文本可以自定义 | 客户端的告警输出 | 客户端开始收到告警 → 迁移窗口已经开始，不能等到升级当天 |
| `status.storedVersions` | 曾经以哪些版本写入过存储 | 版本字符串数组 | 迁移完成的判据是该数组只剩目标版本；改 `storage` 不会让它自动收缩 | 转换钩子的可用性 | 数组里仍有旧版本 → 删版本这一步会被挡住 |
| `spec.conversion.strategy` | 版本之间的转换方式 | 枚举 `None` / `Webhook` | `None` 只改 `apiVersion`，其余字段原样；字段语义发生变化时必须用 `Webhook` | `spec.conversion.webhook.clientConfig` | 服务版本与存储版本不一致时，读写都会走到这条策略上 |
| `conversionReviewVersions` | 转换请求使用的评审对象版本 | 字符串数组 | 入口组件与转换服务都能理解的版本才能协商成功 | 转换服务的实现 | 协商失败 → 转换整体失败，表现为对象读不出来或写不进去 |

转换钩子有三条必须记住的边界：

- **它只能改标签与注解。** 官方文档规定，转换不得修改 `metadata` 中除 `labels` 与 `annotations` 以外的内容；对名字、UID 或命名空间的改动会被拒绝，并使触发这次转换的请求失败。
- **它会在所有需要转换的路径上被调用**，包括以另一个版本读取、以另一个版本写入，以及监听创建时对象版本与服务版本不一致的情况；一次请求可能携带多个对象，转换服务必须按顺序逐一处理。
- **它是可用性的一部分。** 作为服务暴露时端口必须是 `443`；入口组件用它完成转换，因此它不可用会直接影响该类型的读写。

版本迁移按官方给出的顺序推进，顺序颠倒就会留下读不出来的对象：

1. 选好转换策略，若是钩子则先把它部署好；
2. 把新版本加入 `spec.versions` 并置为服务版本；
3. 让客户端逐步迁移到新版本，旧版本可以继续服务；
4. 把存储版本指向新版本；
5. 确认 `status.storedVersions` 里只剩新版本；
6. 确认之后，才把旧版本置为不服务并从 `spec.versions` 里删除，最后再撤销转换服务对旧版本的支持。

## 6. 观测态、子资源与字段选择器

自定义资源同样遵循期望态与观测态分离的约定，但这份约定要靠 schema 与子资源来落实：

| 看什么 | 是什么 | 单位 | 判据 | 与谁同看 | 看到它转向哪一步 |
| --- | --- | --- | --- | --- | --- |
| `spec.versions[].subresources.status` | 是否把观测态拆成独立子资源 | 空结构体，存在即开放 | 开放之后，主资源的写入不再改 `status` | 实际使用的客户端命令 | 写观测态没有生效 → 先确认请求走的是不是子资源 |
| `spec.versions[].subresources.scale` | 是否提供统一的副本数读写入口 | 结构体，含 `specReplicasPath` 等路径 | 路径必须指向 schema 中真实存在的字段 | 自动伸缩组件与该类型的语义 | 伸缩组件报错 → 先核对路径与字段类型是否匹配 |
| `spec.versions[].selectableFields` | 哪些字段可以被字段选择器过滤 | 路径数组，**每个版本最多 8 个** | 未声明的字段不能用于选择器；`metadata.name` 与 `metadata.namespace` 始终可用 | 客户端使用的 `fieldSelector` | 选择器没有过滤效果 → 先确认字段是否声明、请求是否走该版本 |
| `spec.versions[].additionalPrinterColumns` | 客户端默认输出的列 | 列定义数组 | 只影响显示，不影响语义 | 客户端的输出与实际字段 | 显示与字段不一致 → 先看列的取值路径，不要怀疑对象 |

字段选择器的版本演进是阶段式的：**v1.30 引入（alpha，默认关闭）→ v1.31 进入 beta（默认开启）→ v1.32 稳定**，出处是官方特性门控页的 `CustomResourceFieldSelectors` 阶段表。

## 7. 做错这一步要付出的代价

| 代价 | 表现 | 现场判据 |
| --- | --- | --- |
| 数据被剪掉 | 客户端写入的字段在读取时不见了，但没有任何报错 | 该字段所在的层级没有声明保留，剪枝在写入时就已发生 |
| 约束落错层 | 不合法的对象进了存储，清理只能靠控制器事后处理 | 约束写在控制器里，而写入方收到的仍然是成功返回 |
| 版本错位 | 服务版本与存储版本不一致，而转换服务不可用 | 读写失败集中在需要转换的路径上，同一类型的其它版本反而正常 |
| 迁移半途而废 | 存储版本已经推进，`storedVersions` 却一直留着旧版本 | 想删除旧版本时被挡住，只能回头补迁移 |
| 成本失控 | 规则表达式复杂到无法上线，或在大批量写入时成为延迟来源 | 规则的编译报错、以及策略与钩子的检查耗时指标 |

## 8. 抽象模型的适用边界

1. **schema 是约束的根。** 剪枝、缺省值、字段选择器与钩子转换都以结构化 schema 为前提，其余手段都是它的补充。
2. **CEL 校验规则只看当前对象。** 它不能读取其它对象，也不能引入状态；跨对象的判断必须留给控制器。
3. **棘轮只豁免未改动的部分。** 它不是"旧对象永远合法"，而是"旧对象在被改动之前不受新规则影响"。
4. **转换必须保持往返一致。** 同一个对象在两个版本之间来回转换之后应当等价；做不到这一点的转换迟早会在某次读写上暴露。
5. **`storedVersions` 是迁移完成的唯一判据。** 存储版本字段改了，并不代表数据已经迁完。
6. **观测态与期望态的分开是可选的约定。** 只有声明了状态子资源，写观测态才被真正拆成独立请求；没有声明时，两者仍然共用同一条写入路径。

## 常见误解

| 常见说法 | 事实 |
| --- | --- |
| 「字段没写进对象，是控制器删掉的」 | 结构化 schema 的剪枝在写入时就把它去掉了；先确认该层级是否声明保留 |
| 「加了校验规则，存量对象立刻全部合规」 | 棘轮会豁免未改动部分；存量对象要等到被改动时才会失败 |
| 「改了 `storage` 就等于数据已经迁移」 | 迁移完成的判据是 `status.storedVersions`，不是 `storage` 字段 |
| 「转换钩子只在读旧版本时才被调用」 | 写入与监听路径同样会触发转换，只要服务版本与存储版本不同 |
| 「转换钩子里顺手改一下名字没关系」 | 对名字、UID 与命名空间的改动会被拒绝，并使本次请求失败 |
| 「规则里可以顺便查一下别的对象」 | CEL 校验规则只作用于当前对象；需要跨对象判断时必须交给控制器 |

## 要点自测

**问：为什么 `x-kubernetes-validations` 写错时表现是"CRD 提交不上去"？**

答：这些规则在 CRD 创建或更新时编译，编译失败会直接拒绝这次 CRD 写入。所以现场的报错出现在 CRD 对象上，而不是出现在自定义对象上；排查方向应当是规则的语法与类型检查，而不是客户端的权限或对象的字段取值。

**问：剪枝与棘轮为什么容易被当成同一类问题？**

答：两者都表现为"写入时的字段与预期不一致"。剪枝去掉的是 **schema 未声明的字段**，发生在写入路径上，且不报错；棘轮放行的是 **已经存在的校验失败**，只豁免未改动的部分。前者要先看 schema，后者要先看这次更新改了哪些字段。

**问：推进存储版本之后，为什么还要单独确认 `status.storedVersions`？**

答：`storage` 说明"从此以后新写入的对象存成哪个版本"，而 `storedVersions` 说明"历史上存过哪些版本、现在还有没有旧版本留在存储里"。旧对象不会被自动重写，因此迁移完成与否只能看后者；只看前者就删版本，会把旧对象留在无法读取的状态。

**问：转换钩子为什么被视为可用性的一部分？**

答：只要服务版本与存储版本不同，读、写与监听路径都会调用转换。它作为服务暴露时端口必须是 `443`，因此它不可用时，受影响的不只是旧版本客户端，而是所有需要转换的请求。

**问：字段选择器为什么必须提前声明？**

答：字段选择器要靠索引回答请求，未声明的字段没有这份索引，因此无法作为过滤条件；每个版本最多声明 8 个字段。`metadata.name` 与 `metadata.namespace` 始终可用，不需要声明。

**第一反应不要做什么**：不要在 schema 不结构化的情况下继续排查字段消失；不要指望新增校验规则会立刻约束到存量对象；不要在 `storedVersions` 还留着旧版本时删除版本；不要在转换钩子里修改名字或命名空间；也不要把字段选择器当成可以随时打开的开关。
