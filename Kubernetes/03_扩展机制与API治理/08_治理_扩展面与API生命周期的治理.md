# 扩展面与 API 生命周期的治理

## 1. 这些上限分别配在哪一层

扩展面上最常见的管理错位是：**想控制的是一件事，配的却是另一层**。同一个效果可能由清单、集群级对象、入口组件配置、外部服务，甚至一次团队约定决定。因此第一步是把每项控制按层归位。

| 想控制的 | 配在哪一层 | 影响范围 | 谁负责 | 改了要重新验证什么 |
| --- | --- | --- | --- | --- |
| 清单里使用哪个 API 版本 | 发布物（清单与模板） | 使用该清单的所有环境 | 发布流程负责人 | 该版本处于生命周期的哪一段，以及转换之后字段语义是否变化 |
| 类型的字段契约 | 类型定义对象 | 该类型的全部对象 | 类型定义方 | 剪枝、缺省值与校验规则对存量对象的影响 |
| 类型的作用域与命名 | 类型定义对象 | 该类型的全部对象 | 类型定义方 | 角色绑定、选择器与客户端的引用是否同步 |
| 服务版本与存储版本 | 类型定义对象 | 该类型的全部对象 | 类型定义方 | `status.storedVersions` 是否已经收缩，转换是否可靠 |
| 转换服务 | 提供方的部署 | 服务版本与存储版本不一致的全部读写 | 提供方 | 端点、信任根、端口与转换失败率 |
| 判定策略与绑定 | 集群级策略对象 | 策略选中的对象 | 策略负责人 | 命中范围与耗时；观察期数据是否支持切换到拒绝 |
| 参数对象 | 集群级或命名空间级对象 | 使用该参数的全部请求 | 平台方与业务方共同约定 | 参数缺失时的行为与读取权限 |
| 写路径上的外部依赖 | 钩子与聚合服务的部署 | 相关写入与发现请求 | 提供方 | 副本数、超时、失败策略与降级预案 |
| 准入豁免清单 | 入口组件的实现与配置 | 整个集群 | 平台方 | 豁免是否是保留自我修复路径所必需的 |
| 控制器的并行与选举 | 控制器部署与配置 | 该控制器管理的对象 | 提供方 | 队列与调和的耗时分布，而不是只看副本数 |
| 审计与事件的保留 | 入口组件配置与存储 | 整个集群 | 平台方 | 复盘能回溯多久，判定痕迹是否留得住 |
| 升级与移除节奏 | 升级流程与政策 | 整个集群 | 平台方 | 每个版本处于生命周期的哪一段 |

**两条归属原则**：

1. **能用清单表达的，不要依赖集群侧保底。** 使用哪个 API 版本、对象叫什么名字、字段是什么形态，都属于发布物的内容；依赖集群侧代为纠正，会让同一份清单在不同环境中的行为不一致。
2. **能自动校验的约定，不要只写进文档。** 命名与标签这类约定如果只写在文档里，几个月之后必然有人违反；要么用策略自动校验（先观察），要么接受它会被违反。

## 2. 交付产物

### 2.1 扩展面清单卡

每个集群一张，字段固定如下：

| 字段 | 取值来源 | 交付时要给出 |
| --- | --- | --- |
| 类型清单与来源 | 发现结果与类型定义清单 | 有哪些组与类型，分别由谁提供 |
| 每个类型的版本状态 | 类型定义对象的版本数组 | 服务版本、存储版本与已弃用版本 |
| 每个类型的迁移状态 | 类型定义对象的历史版本数组 | 是否还有旧版本留在存储里 |
| 每个类型的契约摘要 | 类型定义对象的 schema | 剪枝范围、校验规则条数、子资源与字段选择器 |
| 写路径上的判定清单 | 策略、绑定与钩子配置 | 命中范围、当前动作、失败策略与超时 |
| 转交关系 | `APIService` 清单与状态条件 | 每个组的后端服务、信任根与可用性 |
| 行为责任方 | 控制器的部署与指标 | 谁在调和、副本数、队列与错误情况 |
| 判定与转换的耗时基线 | 入口组件指标，同口径多次测量 | 分位数耗时与拒绝分布，用于判断是否变慢 |

### 2.2 升级前的 API 与扩展检查单

| 检查项 | 要回答的问题 |
| --- | --- |
| 清单里用到的 API 版本 | 它们分别处于生命周期的哪一段 |
| 存量对象的存储版本 | 是否存在只在旧版本写入、需要迁移的对象 |
| 类型的版本与转换 | 转换链是否完整，存储版本是否需要推进，`storedVersions` 是否已经收缩 |
| 判定策略与绑定 | 观察期的数据是否支持继续，失败策略是否与业务的容错能力匹配 |
| 写路径上的外部依赖 | 钩子与聚合服务的版本、信任根与超时是否仍然适配 |
| 控制器的行为 | 队列与调和指标是否处于正常区间，选举是否稳定 |
| 回滚方式 | 回滚到哪里、需要多久、会丢失什么 |

### 2.3 策略上线记录

| 字段 | 要回答的问题 |
| --- | --- |
| 策略与绑定 | 哪一条策略、由哪一条绑定在哪个范围生效 |
| 判定内容 | 表达式检查什么，依赖哪些参数对象 |
| 当前动作 | 是拒绝、只告警还是只记审计 |
| 观察数据 | 命中次数、耗时分布与命中的对象样本 |
| 切换条件 | 满足什么条件才允许从观察切到拒绝 |
| 回滚方式 | 撤销绑定、改回观察动作还是撤销策略本身 |

### 2.4 不兼容变更与移除记录

| 字段 | 要回答的问题 |
| --- | --- |
| 变更对象 | 哪个类型、哪个版本、哪个字段 |
| 当前阶段 | 引入、稳定、弃用、默认关闭还是移除 |
| 影响面 | 哪些客户端、哪些对象、哪些控制器会受影响 |
| 迁移动作 | 谁负责、按什么顺序、需要多长时间 |
| 判据 | 迁移完成的判据是什么（例如历史版本数组已经收缩） |
| 移除之后 | 出现问题时如何回退，或者为什么无法回退 |

## 3. 与其它领域的接口

- **网络与存储**：指标内容与存储供给属于各自的领域；这里只在需要表达关系（选择器、所有者、卷引用）时使用它们的概念，不替它们决定策略。
- **安全与多租户**：身份、权限模型与工作负载加固的具体配置属于承载策略的那一层；这里只回答"判定写在哪一层、失败时留下什么证据、豁免清单由谁维护"。
- **生产运维**：变更流程、升级顺序与备份恢复演练的编排属于运维那一层；这里提供的是它所需要的检查单、基线字段与阶段判据。
- **制品与运行时**：节点上"声明如何变成进程"属于制品与运行时那一层；这里讲到"对象被写入、被判定、被调和、被观测"为止。
- **扩展的提供方**：类型的版本与转换、控制器的调和逻辑、聚合服务与钩子的可用性，由提供方负责；这里只明确"集群提供了哪些机制，以及代价由谁承担"。

## 4. 一个治理场景

**背景**：一个已经在用的类型需要下线旧版本。团队按计划先把旧版本从服务列表里去除，随后业务报错：部分对象读不出来，控制器也停在一半的调谐状态上。

**按本节的做法走一遍**：

1. **先确认所处阶段，不要先执行动作。** 读该类型定义对象的版本数组与历史版本数组，确认服务版本、存储版本与历史版本三者的现状。
2. **定位失败发生在哪一环。** 历史版本数组里仍有旧版本，说明存量对象没有被迁移；同时转换服务的失败率上升，说明读写路径上的转换也没有成功。两件事同时存在，先修哪一件要看客户端当前的报错落在读取还是写入。
3. **恢复一条可用路径。** 在迁移完成之前，把旧版本重新置为可服务，让仍在使用的客户端与控制器恢复工作；这一步是回退点，不是最终方案。
4. **把迁移做完。** 用存储版本迁移能力推进存储版本，逐一确认对象已经被重写；判据是历史版本数组只剩目标版本。
5. **再按顺序收口。** 确认迁移完成之后，才把旧版本停服并从版本列表里删除，最后撤销转换服务对旧版本的支持；客户端一侧的弃用告警应当在更早的阶段就已经开始出现。
6. **交出产物**：
   - 更新后的**扩展面清单卡**（版本状态与迁移状态）；
   - 一份**不兼容变更与移除记录**，写清阶段、影响面、迁移动作与判据；
   - 在**升级前的检查单**里补一条：下线任何版本之前，必须先确认历史版本数组已经收缩；
   - 如果这次变更涉及判定动作的调整，附一份**策略上线记录**。
7. **验收**：在同一口径下再取一次指标，确认转换失败率已经回落到基线，控制器队列不再堆积；然后检查是否还有别的类型处在"存储版本已推进、历史版本未收缩"的状态，把同类隐患一次性排查掉。

**这个场景的要点**：版本下线是"三段判据"的合并动作——服务版本、存储版本与历史版本必须按顺序推进。任何一段跳过，都会留下读不出来的对象；而回退点的价值在于，它让收口之前始终有一条可用路径。

## 5. 常见坑

| 常见做法 | 后果 |
| --- | --- |
| 把类型与字段契约只写在文档里 | 几个月之后必然被违反，而且字段消失时只能靠猜 |
| 只记录清单里的 API 版本 | 升级时无法判断存量对象需要不需要迁移 |
| 策略一上线就切到拒绝 | 新写入可能被大面积拦下，直接阻塞发布流程 |
| 写路径上挂外部服务却不评估可用性 | 服务不可用时相关写入全部失败，演变为集群级故障 |
| 把副本数当成控制器的吞吐配置 | 同一时刻只有一个执行者在调和，扩容达不到预期 |
| 下线版本时先停服、后迁移 | 存量对象读不出来，控制器与客户端一起停摆 |
| 用重启处置判定或调和异常 | 计数与队列被清空，下一次判断失去基线 |
| 卸载扩展组件不检查存量引用 | 此后会出现无法删除的对象，而且没有人知道原因 |

## 值班口径

被追问"扩展面上的一项控制应该配在哪一层"时，答法是先问"这件事会不会随环境变化"。会随环境变化的内容属于发布物；对全集群成立的内容属于类型定义或策略对象；只影响一次请求的内容属于调用方。把三条分别落到负责人身上，配置错位的问题就会明显减少。

被追问"为什么升级前的检查单里要单列存储版本与历史版本"时，答法是：清单里的版本只说明客户端怎么写，存储版本说明对象以什么形态留在存储里，历史版本说明还有没有旧对象没有迁完。三者中只有最后一项是"能不能删版本"的判据，漏掉它就会在升级当天才发现无法收口。

被追问"判定策略从观察切到拒绝的条件是什么"时，答法是三条同时成立：命中范围与预期一致、耗时在可接受区间内、命中的样本里没有把合法对象判为不合规。三条缺一不可；只凭"观察了一周"不足以支持切换。

被追问"哪些动作属于必须先在实验集群演练的破坏性动作"时，答法是：会删除数据、会跳过清理、会让判定静默失效的动作。它们在生产集群上执行之前，必须先确认备份可恢复、执行步骤已经演练、并且有明确的回退点。

**第一反应不要做什么**：不要把类型与契约只写进文档；不要让策略一上线就拒绝；不要在写路径上挂载没有降级预案的外部组件；不要在下线版本时先停服后迁移；不要用重启处置判定或调和异常；也不要用副本数替代并行度设计。
