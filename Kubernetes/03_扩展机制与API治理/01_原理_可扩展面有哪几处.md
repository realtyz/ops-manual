# 可扩展面有哪几处

## 1. 扩展能力的边界在哪里

需要让这套系统认识一种新的对象时——例如网关路由、存储快照或者训练队列——如果唯一的办法是往核心代码里加入新的类型与逻辑，三类问题会同时出现：

| 问题                | 具体表现                     |
| ----------------- | ------------------------ |
| 每新增一种对象都必须跟随上游的节奏 | 版本升级变成"把自己那份补丁重放一遍"      |
| 生态被核心的发版节奏阻塞      | 一个功能必须等待上游流程走完才能使用       |
| 核心会越来越重           | 存储、权限、校验与控制器逻辑全部堆在同一个仓库里 |

解决的办法是**在链路上留出扩展点**，使外部既能声明新的类型，也能为新类型编写逻辑，还能在对象落库前后介入处理。这些扩展点分布在链路的**不同位置**，能做的事与留下的代价都不相同。

## 2. 三处扩展点分别插在链路的哪一段

| 扩展点 | 位于何处 | 能做什么 | 不能做什么 |
| --- | --- | --- | --- |
| 自定义资源（Custom Resource，CR） | 类型注册这一层 | 让 API 认识一个新的类型，并直接复用存储、授权、准入、选择器、事件与审计等既有能力 | 它不会自动产生任何行为，只是能够被存储、被校验、被发现 |
| 聚合 API（aggregated API） | 请求转交这一层 | 把某一段 API 路径的请求交给一个独立服务处理，这个服务可以使用自己的存储 | 它不参与其它对象的处理；可用性、兼容性与权限都由提供方负责 |
| 准入钩子（admission webhook） | 写路径的中间 | 在对象落库之前改写它或者拒绝它 | 它不改变已经存在对象的状态，也不能替代控制器 |

**"让对象产生行为"不是扩展点的职责，而是控制器的职责**：注册了新类型之后，必须有控制器去观察它并采取行动。把自定义资源与控制器放在一起部署，就是通常所说的 Operator 模式；判定一段扩展是否完整，看的不是 CRD 是否装上，而是**有没有一个进程在为它的声明负责**。

这三处扩展点都位于入口组件（`kube-apiserver`）的链路上：自定义资源由入口组件自己处理，聚合 API 由入口组件转发，准入钩子在入口组件内被调用。因此它们的代价都会体现为入口组件的资源占用、延迟或可用性，而不是均匀分摊到各个节点上。

## 3. 自定义资源：注册的是一份类型，不是一段行为

注册一个新类型，是把它的名字、作用域与字段契约交给入口组件。完成之后，它就获得了与内置对象同等的待遇：能被授权系统管理，能被准入策略管理，能被选择器选中，能出现在事件与审计记录里，也能在 API 发现与 OpenAPI 里出现。然而它不会自动具备行为；按照约定它同样使用期望态与观测态两个字段区，但遵守这一约定的是编写它的人，而不是入口组件。

注册阶段要确定的字段，决定了后面所有环节的名字与路径。其中决定身份的四项——组名、资源名、种类名与作用域——**注册之后不可就地修改**：写错了只能重建类型并把对象迁过去。因此注册时要按"这个名字会被写进多少地方的配置"来衡量。

| 看什么 | 是什么 | 单位 | 判据 | 与谁同看 | 看到它转向哪一步 |
| --- | --- | --- | --- | --- | --- |
| `spec.group` 与 `spec.names.plural` | 这个类型的组名与资源名 | 字符串 | CRD 对象的名字必须是 `<plural>.<group>`；两者共同决定 URL 路径与角色里的 `resource` 字段，且**不可就地修改** | `spec.names.kind` 与 `spec.names.listKind` | 客户端找不到这个类型 → 先核对名字三处是否一致，而不是先怀疑权限 |
| `spec.names.kind` | 写在对象 `kind` 字段里的值 | 字符串（通常为大写开头的单数） | 同样不可就地修改；它同时出现在清单、事件与审计记录里 | 客户的清单与工具 | 清单报"不认识这个种类" → 先看 `kind` 与发现结果是否一致 |
| `spec.scope` | 对象属于命名空间还是整个集群 | 枚举 `Namespaced` / `Cluster` | 作用域决定权限与配额能否覆盖它；**该字段不可就地修改** | 客户端提交时是否带 `metadata.namespace` | 作用域选错 → 只能重建类型并把对象迁过去，不能靠改字段纠正 |
| `spec.versions[].subresources.status` | 是否把观测态拆成独立子资源 | 空结构体，存在即开放 | 开放之后，主资源的写入不再改 `status` | 控制器写观测态的路径 | 拆分之后，写期望态与写观测态可以分别授权 |

三条现场口径：

- **版本演进是自定义资源自身必须解决的问题。** 同一个类型可以同时提供多个版本，其中一个被指定为写入存储的版本，不同版本之间需要转换；提交时写入哪一个版本，决定使用哪一套字段约定进行校验。转换服务、存储版本与历史版本这三条线由提供方维护，入口组件只提供机制。
- **子资源可以单独开放。** 声明了状态子资源之后，写期望态与写观测态被拆成两个请求，因此可以分别授权；这正是"调用方不该修改观测态"这一原则的落地手段。
- **删除清理是提供方的责任。** 需要清理集群之外的资源时，必须依靠清理清单项（finalizer）与控制器相互配合；入口组件只保证"清理项没有清空，对象就不会真正消失"。

## 4. 聚合 API：把一段请求交给独立进程

当需要自己的 API 语义或独立存储时，可以把一段 API 路径的请求转交给一个独立服务。它与自定义资源之间的差别，不在于"能否扩展 API"，而在于**由谁的代码来回答这个请求**：

| 维度 | 自定义资源 | 聚合 API |
| --- | --- | --- |
| 由谁处理请求 | 由入口组件自己处理 | 由一个独立服务处理，入口组件只做代理 |
| 存储 | 与其它对象共用同一份存储 | 可以使用自己的存储 |
| 能力上限 | 受入口组件所支持的对象语义限制 | 可以实现完全不同的语义与字段约定 |
| 代价 | 随集群一起升级 | 需要自行保证可用性、权限、兼容性与升级节奏 |
| 发现与权限 | 自动出现在发现与角色体系里 | 同样出现在发现与角色体系里，但由提供方保证语义一致 |

`APIService` 是"认领"这段路径的对象。它的字段决定了请求被送到哪里、用什么信任关系校验对端、以及这个组的优先级如何排序：

| 看什么 | 是什么 | 单位 | 判据 | 与谁同看 | 看到它转向哪一步 |
| --- | --- | --- | --- | --- | --- |
| `spec.group` 与 `spec.version` | 这个 `APIService` 认领哪一段路径 | 字符串 | 同一组版本只能被一个对象认领；冲突时以 `status.conditions` 为准 | `status.conditions[]` | 认领关系错乱 → 请求会被送到错误的服务或直接失败 |
| `spec.service` | 后端服务的命名空间、名字与端口 | 字符串与整数 | 服务端口必须是 `443`；服务不存在时该组不可用 | `status.conditions[]` 的 `Available` | `Available` 为假 → 先确认服务与端点是否还在 |
| `spec.caBundle` | 校验后端服务证书的信任根 | PEM 编码字节 | 证书轮换后必须同步更新；为空时使用入口组件的系统信任根 | 后端服务证书的签发者 | 请求报证书错误 → 是信任根没有跟上轮换，不是认证失败 |
| `status.conditions[]` 的 `Available` | 这个聚合服务是否可用 | 条件类型与状态 | 为真表示服务存在且可达 | 后端服务的副本与端点 | 为假 → 该组 API 的发现与请求一起失败，而不是只失败某几个类型 |

两条与可用性直接相关的现场口径：

- **发现请求有延迟上限。** 官方文档要求扩展服务的发现请求在五秒内往返；超过这个要求时，入口组件的发现调用会超时，客户端与工具拿到的类型清单会残缺。这类问题在现场表现为"某些类型忽然不见了"，而不是某个接口报错。
- **请求压力会集中到入口组件。** 所有聚合 API 的请求都要先经过入口组件再做代理，因此它的副本数、连接数与超时设置同时决定这段路径的容量与延迟。

## 5. 准入钩子：在写路径中间介入

准入钩子在写路径上介入，并且分成两个阶段：前一阶段提供改写的机会，包括补充缺省值、注入内容与规范化；后一阶段提供拒绝的机会，用于合规判定。它与前两处扩展点的差别在于**它没有引入新的类型**，只是改变了别人写入的对象。

| 维度 | 事实 |
| --- | --- |
| 它能看到的范围 | 只有本次提交的对象（以及删除请求中已经存在的那一份），看不到集群最终会是什么样 |
| 它作用的请求 | 只有写请求；已经存在的对象不会因为策略上线而被重新检查 |
| 它在链路里的位置 | 位于写路径中间，因此它的可用性会成为写路径可用性的一部分 |
| 它的时间尺度 | 超时很短，只适合快速判定，不适合调用响应缓慢的外部系统 |
| 它的触发范围 | 可以按资源、操作、作用域、标签与条件裁剪，避免给全部写入带来额外压力 |
| 它与实现的关系 | 判定逻辑在集群之外的进程里，因此它的版本、证书与部署形态都属于提供方的责任 |

准入钩子把"判定逻辑"放在集群外的进程里，声明式策略把"判定逻辑"写进 API 对象里；两者的判定位置、预演能力与证据形态都不同，选用哪一种取决于判定是否需要访问外部系统。**本篇只写扩展点插在链路的哪一段、各自能做什么；关卡在写请求里的顺序与失败语义不属于本篇的范围。**

## 6. 三处扩展点的代价

扩展能力不是没有代价的，代价可以分成四类，每一类都有对应的现场判据：

| 代价 | 表现 | 现场判据 |
| --- | --- | --- |
| 升级负担 | 自定义资源的版本、转换与存储版本必须跟随集群演进；聚合服务需要自行保证兼容 | 升级之前检查弃用项与转换链；聚合服务要有自己的版本偏斜政策 |
| 控制面负重 | 新类型的对象、事件与监听都与内置对象共享入口组件的资源 | 把对象数量、监听数量与请求速率纳入容量考量 |
| 可用性风险 | 准入钩子与聚合服务都位于关键路径上 | 它们的副本数、超时设置、失败策略与降级预案 |
| 权限风险 | 能够注册新类型、能够修改策略配置，本身就是高权限 | 这类权限按管理员级对待，不看它叫什么名字 |

## 7. 抽象模型的适用边界

1. **注册并不等于具备行为。** 自定义资源只是一份能够被存储与校验的对象；没有控制器时，它会一直停留在提交时的状态。
2. **版本兼容是扩展自身必须承担的责任。** 自定义资源的转换链与聚合服务的 API 语义都由提供方保证，集群只提供机制。
3. **准入钩子的判断是局部的。** 它只能看到本次提交的对象，因此跨对象的全局一致性判断不能依靠它；这类判断必须放在控制器里，按稳态反复校正。
4. **策略上线不会回查存量对象。** 判定只作用于其后的写入；已经存在的对象需要另行处理。
5. **钩子会带来可用性风险。** 当集群之外的进程挂在写路径上时，它的可用性也就成为集群的可用性；降级预案必须在上线之前写清。
6. **注册类型的权限等同于管理员权限。** 能够定义新类型、能够修改策略配置的人，也能间接影响整个集群的校验行为。

## 常见误解

| 常见说法 | 事实 |
| --- | --- |
| 「装上 CRD 就等于装好了功能」 | 还需要控制器；没有控制器时，它只是一份能被存取与校验的类型定义 |
| 「准入钩子能看到整个集群的情况」 | 它只能看到这一次提交的对象；跨对象的判断必须交给控制器 |
| 「聚合 API 更灵活，所以更好」 | 它把可用性、权限与升级兼容的责任一起交给了提供方；只在需要独立语义或独立存储时才值得 |
| 「扩展点不影响集群稳定性」 | 新类型、新监听、转换调用与准入回调都占用入口组件的资源，并且位于关键路径上 |
| 「自定义资源的作用域以后可以改」 | 作用域不可就地修改；选错只能重建类型并把对象迁过去 |
| 「聚合服务挂了只影响那一个功能」 | 该组 API 的发现与请求一起失败，依赖类型清单的工具会同时受影响 |

## 要点自测

**问：三处扩展点分别位于链路的什么位置，各自解决什么问题？**

答：自定义资源位于类型注册这一层，它让 API 认识新的类型并复用既有的存储、授权、准入与发现能力；聚合 API 位于请求转交这一层，它把一段路径的请求交给独立服务处理，适合需要自己的语义或独立存储的场景；准入钩子位于写路径中间，它在对象落库之前改写或拒绝该对象。三者都不能让新类型自行产生行为，那必须依靠控制器。

**问：为什么"装了自定义资源"不等于"功能可用"？**

答：注册只是让对象能够被存储、被校验、被发现。要让对象产生实际效果，必须有控制器去观察它并采取行动；它所需要的清理动作也要依靠清理清单项与控制器配合完成。缺少控制器时，对象会一直停在提交时的状态。

**问：自定义资源的注册字段为什么要按"会被写进多少地方的配置"来衡量？**

答：组名与资源名决定 URL 路径与角色里的 `resource`，名字与种类决定清单、事件与审计记录里的写法，作用域决定权限与配额能否覆盖它。这些名字一旦被客户端与角色绑定引用，改动就要同时改多处配置，而作用域根本无法就地修改。

**问：聚合 API 的可用性问题为什么表现为"类型忽然不见了"？**

答：聚合服务的发现请求有明确的延迟上限，服务不可达或响应过慢时，入口组件的发现调用会失败，客户端拿到的类型清单因此残缺。判据是该 `APIService` 的 `Available` 条件，而不是某个具体接口的返回码。

**问：扩展的四类代价分别对应谁的职责？**

答：升级负担由扩展的提供方承担，因为转换链与聚合服务的兼容性由它维护；控制面负重由平台方评估，因为对象、事件与监听都占用入口组件的资源；可用性风险由策略与聚合服务的负责人承担；权限风险由平台方控制，因为注册类型与修改策略本身就属于管理员级权限。

**第一反应不要做什么**：不要把"注册了新类型"当成功能已经完成；不要用准入钩子去做需要查看全局的判断；不要以为策略上线会修正存量对象；不要在写路径上挂载一个没有降级预案的外部服务；也不要在注册之后才发现作用域选错了。
