# 扩展面与策略的现场观测

## 1. 问题与工具的对应关系

扩展面的观测有一个共同特点：**要看的对象分散在好几类资源里**。类型定义在 CRD 上，判定在策略与绑定上，判定能力在钩子配置上，转交关系在 `APIService` 上，行为在控制器自己的指标上。因此第一步不是打开某个面板，而是把"要回答的问题"与"落在哪一层"对应起来。

只读观测在生产集群上也可以做；下面涉及的查询动作都属于这一类。

| 要回答的问题 | 用哪把命令 | 落在哪一层 |
| --- | --- | --- |
| 这个类型注册上了没有 | `kubectl api-resources --api-group=<组>`；`kubectl get --raw /apis/<组>/<版本>` | 入口组件的发现结果 |
| 这个类型的字段契约是什么 | `kubectl get crd <名字> -o yaml`；`kubectl explain <种类>.<字段> --api-version=<组>/<版本>` | CRD 的 schema |
| 这个类型现在是健康的吗 | `kubectl get crd <名字> -o jsonpath='{range .status.conditions[*]}{.type}={.status} {.reason}{"\n"}{end}'` | CRD 自身的状态 |
| 服务版本、存储版本与历史版本分别是什么 | `kubectl get crd <名字> -o jsonpath='{range .spec.versions[*]}{.name}{" served="}{.served}{" storage="}{.storage}{"\n"}{end}'`；`kubectl get crd <名字> -o jsonpath='{.status.storedVersions}{"\n"}'` | CRD 的版本登记 |
| 转换服务还在不在 | `kubectl get crd <名字> -o jsonpath='{.spec.conversion}{"\n"}'`，再查它引用的服务与端点 | CRD 的转换配置与后端服务 |
| 现在有哪些判定在生效 | `kubectl get validatingadmissionpolicies,validatingadmissionpolicybindings,validatingwebhookconfigurations` | 准入配置对象 |
| 判定最近命中多少、耗时多少 | `kubectl get --raw /metrics \| grep -E 'apiserver_admission_webhook\|apiserver_validating_admission_policy'` | 入口组件的运行指标 |
| 聚合服务是否可用 | `kubectl get apiservice -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.status.conditions[?(@.type=="Available")].status}{"\n"}{end}'` | 聚合层的登记对象 |
| 行为是否在及时收敛 | `kubectl get --raw /metrics \| grep -E 'workqueue_depth\|controller_runtime_reconcile_errors_total'` | 控制器自身的指标端点 |

## 2. 这些字段与指标的读法

| 看什么 | 是什么 | 单位 | 判据 | 与谁同看 | 看到它转向哪一步 |
| --- | --- | --- | --- | --- | --- |
| 发现文档里的资源清单 | 入口组件认为这个组里有哪些资源与子资源 | 结构数组 | 名字、种类与作用域三项必须与清单一致 | CRD 的 `spec.names` 与 `spec.scope` | 发现里缺少某个资源 → 先看 CRD 是否在服务中，而不是先看权限 |
| CRD 的 `status.conditions[]` | CRD 自身的状态 | 结构数组 | 逐条看 `type`、`status`、`reason`、`lastTransitionTime`；`Established` 为真是可用的前提 | 事件与入口组件日志 | 出现 `NonStructuralSchema`、`NamesAccepted` 为假或 `Terminating` → 先处理条件，其余结论都不成立 |
| `spec.versions[].served` 与 `storage` | 服务与存储的分工 | 布尔 | 只有一个版本为存储版本；停服与删版本都必须排在迁移之后 | `status.storedVersions` | 三个版本线不一致 → 先做迁移，再谈删除 |
| `status.storedVersions` | 历史上写入过的版本 | 版本字符串数组 | 迁移完成的判据是该数组只剩目标版本 | 转换服务的可用性 | 数组里仍有旧版本 → 不能把旧版本从 `spec.versions` 里删掉 |
| CRD 的转换配置 | 转换方式与对端服务 | 枚举与结构体 | `Webhook` 需要可用的服务、正确的信任根与 `443` 端口 | 转换服务的端点与错误率 | 转换失败 → 该类型的读写一起失败，不只是旧版本客户端 |
| `spec.versions[].schema` 下的校验规则 | 写入时必须满足的字段关系 | CEL 规则数组 | 规则在 CRD 写入时编译；失败会拒绝这次 CRD 更新 | CRD 的更新事件 | CRD 更新被拒 → 先看规则编译报错 |
| 策略与绑定是否成对 | 判定是否有实际作用 | 两类对象的清单 | 策略与绑定必须同时存在，绑定要指向策略名 | 绑定的校验动作 | 只有策略没有绑定 → 当前没有任何判定在生效 |
| 绑定的 `validationActions` | 判定失败时的动作 | 枚举数组 | `Deny` 与 `Warn` 互斥；观察期用 `Warn` 与 `Audit` | 策略指标与审计注解 | 只有审计痕迹 → 当前是观察期，不是拒绝期 |
| 钩子配置的匹配与副作用声明 | 钩子拦什么、能否处理试运行 | 枚举与规则数组 | 匹配策略默认等价匹配；副作用声明与实现必须一致 | 钩子调用与拒绝指标 | 钩子表现异常 → 先核配置，再看进程 |
| `apiserver_validating_admission_policy_check_total` | 声明式校验的检查次数 | 计数（按策略与绑定分标签） | 数量应当与相关写入量同向变化；为 0 说明没有请求命中 | 绑定的校验动作 | 数量为 0 → 回到匹配范围，而不是回到表达式 |
| `apiserver_admission_webhook_admission_duration_seconds` | 钩子调用耗时 | 秒（分位数） | 与超时设置对照；接近上限说明钩子是延迟来源 | 钩子的超时配置 | 耗时接近超时 → 先评估降级方案，再考虑放宽上限 |
| `apiserver_admission_webhook_rejection_count` | 钩子拒绝次数 | 计数（按钩子名与原因类型分标签） | 标签区分"判定拒绝"与"调用失败" | 响应体里的原因文本 | 调用失败类计数上升 → 先修钩子可用性 |
| `apiserver_admission_webhook_fail_open_count` | 因放行失败而未被拦下的次数 | 计数 | 该计数大于 0 表示有请求本该被判定却没有 | 失败策略的配置 | 该计数上升 → 属于策略静默失效，必须评估安全影响 |
| `apiserver_admission_match_condition_evaluation_errors_total` | 匹配条件求值出错的次数 | 计数 | 出错会影响策略与钩子是否被调用 | 条件表达式与策略失败策略 | 持续上升 → 先修条件表达式 |
| `APIService` 的 `Available` 条件 | 聚合服务是否可用 | 条件类型与状态 | 为假时该组 API 的发现与请求一起失败 | 后端服务与端点 | 为假 → 先查服务与信任根 |
| `workqueue_depth` 与 `controller_runtime_reconcile_errors_total` | 控制器是否跟得上 | 个数与计数 | 队列持续增长说明消费不足；错误计数上升说明调和失败 | `controller_runtime_reconcile_time_seconds` | 两者同升 → 先定位失败的调和动作 |
| `leader_election_master_status` | 当前执行者是谁 | 布尔（按持有者分标签） | 同一时刻应当只有一个为真 | 切换次数与选举慢路径计数 | 出现两个为真 → 处于切换窗口，动作必须可重入 |

**指标端点受授权保护。** 读指标之前先确认自己有没有对应的非资源权限；取到的数值只代表当时的采样窗口。这三类指标各用一条命令取出（**计数类要取两次差值，分位类只看窗口**）：

```bash
# 只读观测：声明式策略的检查次数与耗时（按策略、绑定与校验动作分标签）
kubectl get --raw /metrics | grep -E 'apiserver_validating_admission_policy_check'

# 只读观测：钩子的耗时、拒绝与放行失败（标签区分"判定拒绝"与"调用失败"）
kubectl get --raw /metrics | grep -E 'apiserver_admission_webhook_(webhook_admission_duration|rejection_count|fail_open_count)'

# 只读观测：控制器是否跟得上（队列深度与调和错误）
kubectl get --raw /metrics | grep -E 'workqueue_depth|controller_runtime_reconcile_errors_total'
```

判据的分水岭在标签而不是数值：`apiserver_admission_webhook_rejection_count` 的 `error_type` 标签区分**判定拒绝**（另有 `rejection_code`）与**调用失败**，前者的方向是改对象或改规则，后者的方向是修钩子或扩展服务的可用性；`apiserver_admission_webhook_fail_open_count` **大于 0 表示有请求本该被判定却没有**，属于策略静默失效。名称与标签随版本与采集方式变化，**引用时必须写成"以某版本暴露的指标为例"**，数值仅示意。

## 3. 采样纪律与扩展面基线卡

扩展面的问题大多不是"某一次请求失败"，而是"某一段时间里的分布变了"。因此采样要固定口径：同一组标签、同一段时间窗、同一种聚合方式，先把基线记下来，再谈变化。

| 基线项 | 取值来源 | 交付时要给出 |
| --- | --- | --- |
| 类型清单与来源 | `kubectl api-resources -o name`；`kubectl get crd -o custom-columns=NAME:.metadata.name,GROUP:.spec.group,SCOPE:.spec.scope` | 有哪些组、哪些类型、由谁提供 |
| 每个类型的版本状态 | `kubectl get crd <名字> -o jsonpath='{range .spec.versions[*]}{.name}{" served="}{.served}{" storage="}{.storage}{"\n"}{end}'` | 服务版本、存储版本、已弃用版本分别是什么 |
| 每个类型的迁移状态 | `kubectl get crd <名字> -o jsonpath='{.status.storedVersions}{"\n"}'` | 是否还有旧版本留在存储里 |
| 每个类型的契约摘要 | `kubectl get crd <名字> -o jsonpath='{.spec.versions[?(@.storage==true)].schema.openAPIV3Schema.properties.spec.properties}'` | 哪些字段被剪枝、校验规则有多少条、子资源是否开放 |
| 写路径上的判定清单 | `kubectl get validatingadmissionpolicies,validatingadmissionpolicybindings,validatingwebhookconfigurations,mutatingwebhookconfigurations` | 命中哪些资源、当前动作是拒绝还是只观察 |
| 判定耗时与拒绝分布 | `kubectl get --raw /metrics \| grep apiserver_admission` | 分位数耗时、拒绝次数、放行失败次数 |
| 转交关系 | `kubectl get apiservice -o custom-columns=NAME:.metadata.name,AVAILABLE:.status.conditions[?(@.type=="Available")].status,SERVICE:.spec.service.name` | 每个组的后端服务、信任根与可用性 |
| 行为责任方 | `kubectl get deploy -A -o custom-columns=NS:.metadata.namespace,NAME:.metadata.name,REPLICAS:.spec.replicas`；`kubectl get lease -A` | 谁在调和、副本数、队列与错误情况 |
| 升级前的检查结果 | 上述各项的历史快照（同一口径、带时间戳留档） | 与更早一次基线的差异，以及需要动作的条目 |

## 4. 四类现场与排查方向

### 4.1 类型注册与契约

**现场**：清单提交成功，但客户端报"不认识这个类型"，或者写入的字段读回来不见了。

**先看什么**：先看发现文档里有没有这个类型，再看 CRD 的状态条件，最后看 schema 里对应层级有没有声明保留未知字段。**判据**：发现里没有该类型，说明注册或服务状态有问题；发现里有而字段消失，说明是剪枝；出现 `NonStructuralSchema` 说明契约本身不结构化。**转向哪一步**：注册问题回到 CRD 的名字与作用域；剪枝问题回到 schema；状态条件为假时先别继续往下排查。

```bash
# 只读观测：类型是否已建立（等条件比"等几秒再看发现"可复现）
kubectl wait --for=condition=Established crd/widgets.demo.example.com --timeout=60s
kubectl get crd widgets.demo.example.com -o jsonpath='{range .status.conditions[*]}{.type}={.status} {.reason}{"\n"}{end}'

# 只读观测：发现文档里有没有这个类型与它的子资源
kubectl api-resources --api-group=demo.example.com
kubectl get --raw /apis/demo.example.com/v1

# 只读观测：字段契约（不带 --api-version 时看到的是按版本优先级排序后的首选版本）
kubectl explain widget.spec.size --api-version=demo.example.com/v1
```

判据：`kubectl get --raw` 返回的 `resources[]` 里出现以 `/status` 结尾的条目，才是"子资源真的开放"的直接证据；只出现 `apiVersion`/`kind`/`metadata` 说明 schema 没有被发布。

### 4.2 版本与转换

**现场**：某个版本读不出来，或者写入报转换失败；也可能是明明改了存储版本，旧版本却一直删不掉。

**先看什么**：把服务版本、存储版本与 `storedVersions` 三条线并排放，再看转换服务的端点与信任根。**判据**：三线不一致说明迁移没有走完；转换服务不可达或证书过期说明失败发生在转换这一步；`storedVersions` 里仍有旧版本说明不能删版本。**转向哪一步**：迁移未完成就先补迁移；转换失败先修服务与证书；两者都对而客户端仍报错时，再回到客户端的 API 版本设置。

```bash
# 只读观测：三条线并排（服务版本、存储版本、历史写入版本）
kubectl get crd widgets.demo.example.com -o jsonpath='{range .spec.versions[*]}{.name}{" served="}{.served}{" storage="}{.storage}{"\n"}{end}'
kubectl get crd widgets.demo.example.com -o jsonpath='{.status.storedVersions}{"\n"}'

# 只读观测：旧版本停服后的效果（应当从发现里消失）
kubectl get --raw /apis/demo.example.com/v1beta1

# 只读观测：转换配置与它引用的服务
kubectl get crd widgets.demo.example.com -o jsonpath='{.spec.conversion}{"\n"}'
```

判据：推进存储版本后 `storedVersions` **不会自动收缩**——旧对象不会被自动重写，因此迁移完成的判据是这个数组只剩目标版本。**在这个数组还留着旧版本时删除该版本，会把旧对象留在无法读取的状态。** 需要手工改写该状态时要有 `customresourcedefinitions/status` 的 patch 权限，**缺权限时报的是 403，而不是"版本不能删"**。

### 4.3 判定与钩子

**现场**：写入被拒但原因不明；或者反过来说，本该被拦下的写入通过了。

**先看什么**：先分清是判定结论还是调用事故，再看策略与绑定的匹配范围与当前动作。**判据**：拒绝次数带判定类标签，说明是规则命中；带调用失败类标签，说明是钩子不可用；放行失败计数大于零，说明有请求在失败策略下被放过去了。**转向哪一步**：判定命中的回到表达式与规则；调用失败的回到钩子或扩展服务自身；放行失败的先评估影响范围，再决定是否收紧失败策略。

```bash
# 只读观测：策略与绑定是否成对存在，以及当前动作（观察期应为 Warn/Audit）
kubectl get validatingadmissionpolicy <策略名> -o yaml
kubectl get validatingadmissionpolicybinding <绑定名> -o jsonpath='{.spec.validationActions}{"\n"}'

# 只读观测：类型检查的结果（字段不存在即类型检查通过）
kubectl get validatingadmissionpolicy <策略名> -o jsonpath='{.status.typeChecking.expressionWarnings}{"\n"}'

# 只读观测：判定拒绝与调用失败分开看（error_type 标签是分水岭）
kubectl get --raw /metrics | grep apiserver_admission_webhook_rejection_count
kubectl get --raw /metrics | grep apiserver_admission_webhook_fail_open_count
```

判据：只有策略没有绑定，等于**当前没有任何判定在生效**；只有审计痕迹而没有拒绝，说明当前处于观察期而不是拒绝期。钩子的 `failurePolicy` 与 `timeoutSeconds` 不写时分别得到 `Fail` 与 10 秒，**这两个缺省值是事故定界的关键**——`failurePolicy: Fail` 之下钩子不可达会让写请求直接失败。

### 4.4 聚合与控制器

**现场**：某个组的类型忽然从工具里消失；或者对象创建之后长时间没有变化。

**先看什么**：前者先看 `APIService` 的可用条件与后端服务，再看发现请求是否超时；后者先看 `generation` 与 `status.observedGeneration`，再看队列与调和指标。**判据**：条件为假或服务端点缺失，说明问题在聚合层；两个代数长期不等且队列增长，说明问题在控制器侧。**转向哪一步**：聚合层的问题回到服务与信任根；控制器的问题先分清是调和失败还是消费不足。

```bash
# 只读观测：聚合服务是否可用，后端服务在哪里
kubectl get apiservice -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.status.conditions[?(@.type=="Available")].status}{"\t"}{.spec.service.namespace}/{.spec.service.name}{"\n"}{end}'

# 只读观测：控制器是否看过最新期望
kubectl get <类型> <名字> -o jsonpath='{.metadata.generation}{" "}{.status.observedGeneration}{"\n"}'

# 只读观测：是调和失败还是消费不足
kubectl get --raw /metrics | grep -E 'workqueue_depth|controller_runtime_reconcile_errors_total'

# 只读观测：领导者选举当前由谁持有（同一时刻只应有一个为真）
kubectl get lease -n <命名空间> -o jsonpath='{range .items[*]}{.metadata.name}{" "}{.spec.holderIdentity}{" "}{.spec.renewTime}{" "}{.spec.leaseTransitions}{"\n"}{end}'
```

判据：`Available` 为假时，该组 API 的**发现与请求一起失败**，而不是只失败某几个类型——这解释了"某个组的类型忽然从工具里消失"。队列持续增长说明消费不足，错误计数上升说明调和失败，两者的处置方向不同。

## 5. 破坏性动作的边界

前两项会改变数据、第三项会让判定静默失效，因此这三项只能在可丢的实验集群上执行；在生产集群上动手之前，必须先备份、先在实验集群演练一遍恢复。后两项分别给出"需要窗口的配置变更"与"任何集群都不执行"的边界：

| 动作 | 为什么危险 | 边界与不可回滚说明 |
| --- | --- | --- |
| 删除一个 CRD | 入口组件会卸载它的端点，并删除其中**全部**自定义对象 | 只在可丢的实验集群执行；删除后没有回滚路径，只能从备份恢复对象 |
| 手工移除对象的清理项 | 会跳过外部资源的清理，留下无法自动回收的残留 | 只在可丢的实验集群执行；外部资源是否仍需清理必须在动手前确认 |
| 把钩子的失败策略从拒绝改为放行 | 相关判定会静默失效，安全与合规约束随之消失 | 只在可丢的实验集群验证；改动前先记录当前策略与命中范围 |
| 给已在使用的类型加校验规则 | 存量对象在被改动到相关字段时会开始失败 | 属于需要窗口的配置变更，不是破坏性操作；先在观察动作下运行，并准备好撤销规则的回滚点 |
| 直接编辑存储中的对象 | 绕过全部关卡，导致缓存与权威长期不一致 | 任何集群都不执行；这类动作没有可核对的证据链 |

## 6. 能提交的清单

扩展面的四类对象各给一份清单，用来在实验集群上把注册、版本迁移、声明式判定与钩子四条路各走一遍。**清单里的组名、类型名与镜像都可替换**；schema 与规则只写示范性的字段关系，真实契约按平台自己的设计写。

### 6.1 类型注册：最小 CRD 与写入时校验

```yaml
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: widgets.demo.example.com        # 必须是 <plural>.<group>
spec:
  group: demo.example.com
  scope: Namespaced                     # 不可就地修改，选错只能重建
  names:
    kind: Widget
    listKind: WidgetList
    plural: widgets
    singular: widget
    shortNames: [wd]
  versions:
    - name: v1
      served: true
      storage: true                     # 有且只有一个版本可以为真
      subresources:
        status: {}                      # 开放之后主资源的写入不再改 status
      additionalPrinterColumns:
        - name: Size
          type: integer
          jsonPath: .spec.size
      selectableFields:
        - jsonPath: .spec.size          # 每个版本最多 8 个，且不能指向 metadata
      schema:
        openAPIV3Schema:
          type: object
          required: [spec]
          properties:
            spec:
              type: object
              required: [size]
              properties:
                size:
                  type: integer
                  minimum: 1
                  maximum: 100
              x-kubernetes-validations:
                - rule: "self.size % 2 == 0"
                  message: "size 必须是偶数"
                  reason: Invalid       # CRD 侧取值：FieldValueInvalid / FieldValueForbidden / FieldValueRequired / FieldValueDuplicate
```

```bash
# 只读观测：等 Established 条件比"等几秒再看发现"可复现
kubectl apply -f crd.yaml
kubectl wait --for=condition=Established crd/widgets.demo.example.com --timeout=60s
kubectl get crd widgets.demo.example.com -o jsonpath='{range .status.conditions[*]}{.type}={.status} {.reason}{"\n"}{end}'

# 只读观测：发现文档里的资源与子资源（出现以 /status 结尾的条目才是子资源真的开放）
kubectl api-resources --api-group=demo.example.com
kubectl get --raw /apis/demo.example.com/v1

# 只读观测：不带 --api-version 时看到的是按版本优先级排序后的首选版本
kubectl explain widget.spec.size --api-version=demo.example.com/v1

# 只读观测：剪枝发生在写入时不发生在读取时——提交一个 schema 未声明的字段，再读回来确认它消失
kubectl apply -f - <<'EOF'
apiVersion: demo.example.com/v1
kind: Widget
metadata: {name: w1}
spec: {size: 4, undeclaredField: "会被静默去掉"}
EOF
kubectl get widget w1 -o jsonpath='{.spec}{"\n"}'

# 只读观测：CEL 规则在写入时拒绝（提交 size 为奇数应当报 "size 必须是偶数"）
kubectl apply -f - <<'EOF'
apiVersion: demo.example.com/v1
kind: Widget
metadata: {name: w2}
spec: {size: 3}
EOF
```

判据：`get --raw` 里出现 `/status` 条目说明状态子资源开放；`explain` 能读到 `minimum`/`maximum` 说明 schema 生效；最后一条被拒说明 CEL 规则进了写入路径。**规则写错的现场表现是"CRD 本身提交不上去"**，因为规则在 CRD 创建或更新时编译。

### 6.2 版本迁移：三个版本与存储版本推进

```yaml
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: widgets.demo.example.com
spec:
  group: demo.example.com
  scope: Namespaced
  names: {kind: Widget, listKind: WidgetList, plural: widgets, singular: widget}
  conversion:
    strategy: Webhook               # 字段语义变化时必须用 Webhook；None 只改 apiVersion
    webhook:
      conversionReviewVersions: [v1]
      clientConfig:
        service:
          namespace: demo
          name: widget-converter
          port: 443                 # 作为服务暴露时端口必须是 443
        caBundle: "<PEM 编码的信任根>"
  versions:
    - name: v1alpha1
      served: false                 # 客户端的运行时版本：先停服，再确认 storedVersions 干净，最后才从列表里删
      storage: false
    - name: v1beta1
      served: true
      storage: false
    - name: v1
      served: true
      storage: true                 # 新写入的存成这个版本
```

```bash
# 只读观测：三条线并排（服务版本、存储版本、历史写入版本）
kubectl get crd widgets.demo.example.com -o jsonpath='{range .spec.versions[*]}{.name}{" served="}{.served}{" storage="}{.storage}{"\n"}{end}'
kubectl get crd widgets.demo.example.com -o jsonpath='{.status.storedVersions}{"\n"}'

# 只读观测：迁移完成的判据是这个数组只剩目标版本；推进 storage 不会让它自动收缩
kubectl get crd widgets.demo.example.com -o jsonpath='{.spec.conversion}{"\n"}'
```

迁移按官方顺序推进：先部署转换策略 → 新版本加入并置为服务版本 → 客户端逐步迁移 → 把 `storage` 指向新版本 → **确认 `storedVersions` 里只剩新版本** → 才把旧版本停服并删除，最后撤销转换服务对旧版本的支持。**`storedVersions` 还留着旧版本时删除该版本，会把旧对象留在无法读取的状态**；要手工改写这个状态需要有 `customresourcedefinitions/status` 的 patch 权限，**缺权限时报 403，而不是报"版本不能删"**。

### 6.3 声明式判定：策略、绑定与参数三件套

```yaml
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicy
metadata:
  name: demo-require-team-label
spec:
  failurePolicy: Fail
  paramKind:
    apiVersion: v1
    kind: ConfigMap                 # 参数对象是内置类型
  matchConstraints:
    resourceRules:
      - apiGroups: [apps]
        apiVersions: [v1]
        operations: [CREATE, UPDATE]
        resources: [deployments]
  validations:
    - expression: "object.metadata.labels['team'] == params.data.team"
      messageExpression: "'部署必须带上 team=' + params.data.team + ' 的标签'"
      reason: Invalid               # 策略侧取值：Unauthorized / Forbidden / Invalid / RequestEntityTooLarge
```

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: demo-policy-params
  namespace: demo
data:
  team: platform
---
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicyBinding
metadata:
  name: demo-require-team-label
spec:
  policyName: demo-require-team-label
  validationActions: [Warn, Audit]  # 观察期先只告警与记审计；Deny 与 Warn 不能同时使用
  paramRef:
    name: demo-policy-params
    namespace: demo
    parameterNotFoundAction: Deny   # 必填；不写不会得到默认值，而是得到无效绑定
```

```bash
# 只读观测：策略创建后看类型检查结果（字段不存在即类型检查通过）
kubectl apply -f vap.yaml -f vap-params-binding.yaml
kubectl get validatingadmissionpolicy demo-require-team-label -o jsonpath='{.status.typeChecking.expressionWarnings}{"\n"}'

# 只读观测：当前处于观察期还是拒绝期（只有审计痕迹 = 观察期）
kubectl get validatingadmissionpolicybinding demo-require-team-label -o jsonpath='{.spec.validationActions}{"\n"}'

# 只读观测：判定次数与动作分标签（计数类要取两次差值）
kubectl get --raw /metrics | grep apiserver_validating_admission_policy_check
```

两条容易被忽略的边界：**策略必须与绑定成对存在才会生效**（只有策略等于没有任何判定在生效）；**参数对象需要被读取权限覆盖**，判定方读不到参数对象时表现为"策略看着生效但从不拒绝"。观察期用 `Warn` 与 `Audit` 跑一段时间，确认命中范围与耗时之后再改成 `Deny`。

### 6.4 钩子：字段写全的配置与缺省值陷阱

```yaml
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingWebhookConfiguration
metadata:
  name: demo-validate
webhooks:
  - name: validate.demo.example.com     # 同一条配置里的钩子名必须唯一
    admissionReviewVersions: [v1]       # 必填：不写得到的是 API 报错，不是缺省值
    sideEffects: None                   # 必填：声明有副作用却不处理试运行请求时，试运行会被拒
    failurePolicy: Fail                 # 缺省即 Fail：钩子不可达会让写请求直接失败
    matchPolicy: Equivalent             # 缺省即 Equivalent：等价匹配会把对象转成钩子注册的版本
    timeoutSeconds: 10                  # 缺省 10 秒，合法区间 1–30
    reinvocationPolicy: Never           # 缺省 Never；声明 IfNeeded 时调用次数没有保证，逻辑必须幂等
    clientConfig:
      service:
        namespace: demo
        name: demo-webhook
        port: 443                       # 通过服务引用时端口约定为 443
      caBundle: "<PEM 编码的信任根>"
    rules:
      - apiGroups: [apps]
        apiVersions: [v1]
        operations: [CREATE, UPDATE]
        resources: [deployments]
        scope: Namespaced
    namespaceSelector:
      matchLabels: {admission: enabled}
    objectSelector:
      matchLabels: {admission: enabled}
```

```bash
# 只读观测：先确认有哪些钩子在写路径上，再按失败策略与超时定界
kubectl get validatingwebhookconfigurations,mutatingwebhookconfigurations
kubectl get validatingwebhookconfiguration demo-validate -o jsonpath='{range .webhooks[*]}{.name}{" failurePolicy="}{.failurePolicy}{" timeout="}{.timeoutSeconds}{" matchPolicy="}{.matchPolicy}{"\n"}{end}'

# 只读观测：判定拒绝与调用失败分开看（error_type 是分水岭：no_error 是判定拒绝，另有 rejection_code）
kubectl get --raw /metrics | grep apiserver_admission_webhook_rejection_count

# 只读观测：放行失败计数大于 0 表示有请求本该被判定却没有，属于策略静默失效
kubectl get --raw /metrics | grep apiserver_admission_webhook_fail_open_count
```

`rules` 的 `"*"` 匹配全部资源但**不含子资源**，`"*/*"` 才连子资源一起匹配；`namespaceSelector` 拦不住命名空间级请求本身。变更钩子还要记住阶段顺序：**变更阶段先于校验阶段，策略先于钩子**，因此变更钩子看到的是"变更型策略已经改过一遍"的对象。

## 7. 常见坑

| 常见做法 | 后果 |
| --- | --- |
| 只看清单提交成功 | 提交成功只说明对象进了存储，判定、转换与调和都还没有被验证 |
| 用发现结果判断权限 | 发现回答"有什么"，角色回答"能不能做"，两者不能互相替代 |
| 把 `storedVersions` 当成历史信息忽略 | 它决定了删版本这一步能不能做 |
| 看拒绝次数不看原因类型标签 | 判定拒绝与调用失败会被混为一谈，处置方向随之出错 |
| 只在指标上看到异常就重启控制器 | 重启会清空队列与计数，失去基线；先看清是消费不足还是调和失败 |
| 生产集群上验证失败策略的降级行为 | 会让策略静默失效；这类验证只在可丢的实验集群做 |

## 8. 要点自测

**问：为什么排查扩展面问题要先看发现结果，而不是先看权限？**

答：发现回答"集群里有没有这个类型、它的名字与作用域是什么"，权限回答"这个身份能不能对它做某个动作"。如果类型根本没有被服务，权限配置再正确也不会生效；两者混在一起排查，会在错误的方向上反复核对角色绑定。

**问：`storedVersions` 与 `spec.versions[].storage` 各自回答什么问题？**

答：`storage` 回答"从现在开始，新写入的对象存成哪个版本"，`storedVersions` 回答"历史上存过哪些版本、现在还有没有旧版本留在存储里"。迁移完成的判据是后者，不是前者。

**问：为什么判定类指标与调用失败类指标要分开看？**

答：判定类指标上升说明有写入真的不合规，方向是改对象或改规则；调用失败类指标上升说明判定根本没有执行成功，方向是修钩子或扩展服务的可用性。两者的处置动作完全不同，混在一起看会得出相反的结论。

**问：放行失败计数为什么值得单独盯？**

答：它统计的是"本该被判定却因为失败策略被放过去"的请求。该计数大于零意味着存在一段静默失效的窗口，安全与合规上需要评估影响范围；它也是把失败策略从拒绝改成放行之前必须记录的基线。

**问：为什么生产集群上不做失败策略的降级验证？**

答：验证降级必然要临时让判定失效，而这段窗口里不合规的写入会通过。这类验证只能在可丢的实验集群上做，生产上要验证的是降级预案本身是否可行，而不是把判定真正关掉。

**第一反应不要做什么**：不要在 CRD 状态条件为假时继续往下排查；不要在迁移没走完时删除旧版本；不要只看拒绝次数不看原因类型；不要为了看清问题而重启控制器；也不要在生产集群上验证让判定失效的降级路径。
