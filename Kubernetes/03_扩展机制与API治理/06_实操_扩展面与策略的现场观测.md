# 扩展面与策略的现场观测

## 1. 问题与工具的对应关系

扩展面的观测有一个共同特点：**要看的对象分散在好几类资源里**。类型定义在 CRD 上，判定在策略与绑定上，判定能力在钩子配置上，转交关系在 `APIService` 上，行为在控制器自己的指标上。因此第一步不是打开某个面板，而是把"要回答的问题"与"落在哪一层"对应起来。

只读观测在生产集群上也可以做；下面涉及的查询动作都属于这一类。

| 要回答的问题 | 用哪把工具 | 落在哪一层 |
| --- | --- | --- |
| 这个类型注册上了没有 | `kubectl api-resources --api-group=<组>`，或直接读该组的发现文档 | 入口组件的发现结果 |
| 这个类型的字段契约是什么 | `kubectl get crd <名字> -o yaml`，配合 `kubectl explain` | CRD 的 schema |
| 这个类型现在是健康的吗 | 列出 CRD 的状态条件并逐条看 `type` 与 `status` | CRD 自身的状态 |
| 服务版本、存储版本与历史版本分别是什么 | 读取 `spec.versions` 与 `status.storedVersions` | CRD 的版本登记 |
| 转换服务还在不在 | 读 CRD 的转换配置，再查它引用的服务与端点 | CRD 的转换配置与后端服务 |
| 现在有哪些判定在生效 | 列出策略、绑定与钩子配置 | 准入配置对象 |
| 判定最近命中多少、耗时多少 | 读入口组件的指标端点 | 入口组件的运行指标 |
| 聚合服务是否可用 | 列出 `APIService` 并读它的状态条件 | 聚合层的登记对象 |
| 行为是否在及时收敛 | 读控制器暴露的队列与调和指标 | 控制器自身的指标端点 |

## 2. 这些字段与指标的读法

| 看什么 | 是什么 | 单位 | 判据 | 与谁同看 | 看到它转向哪一步 |
| --- | --- | --- | --- | --- | --- |
| 发现文档里的资源清单 | 入口组件认为这个组里有哪些资源与子资源 | 结构数组 | 名字、种类与作用域三项必须与清单一致 | CRD 的 `spec.names` 与 `spec.scope` | 发现里缺少某个资源 → 先看 CRD 是否在服务中，而不是先看权限 |
| CRD 的 `status.conditions[]` | CRD 自身的状态 | 结构数组 | 逐条看 `type`、`status`、`reason`、`lastTransitionTime`；`Established` 为真是可用的前提 | 事件与入口组件日志 | 出现 `NonStructuralSchema`、`NamesAccepted` 为假或 `Terminating` → 先处理条件，其余结论都不成立 |
| `spec.versions[].served` 与 `storage` | 服务与存储的分工 | 布尔 | 只有一个版本为存储版本；停服与删版本都必须排在迁移之后 | `status.storedVersions` | 三个版本线不一致 → 先做迁移，再谈删除 |
| `status.storedVersions` | 历史上写入过的版本 | 版本字符串数组 | 迁移完成的判据是该数组只剩目标版本 | 转换服务的可用性 | 数组里仍有旧版本 → 不能把旧版本从 `spec.versions` 里删掉 |
| CRD 的转换配置 | 转换方式与对端服务 | 枚举与结构体 | `Webhook` 需要可用的服务、正确的信任根与 `443` 端口 | 转换服务的端点与错误率 | 转换失败 → 该类型的读写一起失败，不只是旧版本客户端 |
| `spec.versions[].schema` 下的校验规则 | 写入时必须满足的字段关系 | CEL 规则数组 | 规则在 CRD 写入时编译；失败会拒绝这次 CRD 更新 | CRD 的更新事件 | CRD 更新被拒 → 先看规则编译报错 |
| 策略与绑定是否成对 | 判定是否有实际作用 | 两类对象的清单 | 策略与绑定必须同时存在，绑定要指向策略名 | 绑定的校验动作 | 只有策略没有绑定 → 当前没有任何判定在生效 |
| 绑定的 `validationActions` | 判定失败时的动作 | 枚举数组 | `Deny` 与 `Warn` 互斥；观察期用 `Warn` 与 `Audit` | 策略指标与审计注解 | 只有审计痕迹 → 当前是观察期，不是拒绝期 |
| 钩子配置的匹配与副作用声明 | 钩子拦什么、能否处理试运行 | 枚举与规则数组 | 匹配策略默认等价匹配；副作用声明与实现必须一致 | 钩子调用与拒绝指标 | 钩子表现异常 → 先核配置，再看进程 |
| `apiserver_validating_admission_policy_check_total` | 声明式校验的检查次数 | 计数（按策略与绑定分标签） | 数量应当与相关写入量同向变化；为 0 说明没有请求命中 | 绑定的校验动作 | 数量为 0 → 回到匹配范围，而不是回到表达式 |
| `apiserver_admission_webhook_admission_duration_seconds` | 钩子调用耗时 | 秒（分位数） | 与超时设置对照；接近上限说明钩子是延迟来源 | 钩子的超时配置 | 耗时接近超时 → 先评估降级方案，再考虑放宽上限 |
| `apiserver_admission_webhook_rejection_count` | 钩子拒绝次数 | 计数（按钩子名与原因类型分标签） | 标签区分"判定拒绝"与"调用失败" | 响应体里的原因文本 | 调用失败类计数上升 → 先修钩子可用性 |
| `apiserver_admission_webhook_fail_open_count` | 因放行失败而未被拦下的次数 | 计数 | 该计数大于 0 表示有请求本该被判定却没有 | 失败策略的配置 | 该计数上升 → 属于策略静默失效，必须评估安全影响 |
| `apiserver_admission_match_condition_evaluation_errors_total` | 匹配条件求值出错的次数 | 计数 | 出错会影响策略与钩子是否被调用 | 条件表达式与策略失败策略 | 持续上升 → 先修条件表达式 |
| `APIService` 的 `Available` 条件 | 聚合服务是否可用 | 条件类型与状态 | 为假时该组 API 的发现与请求一起失败 | 后端服务与端点 | 为假 → 先查服务与信任根 |
| `workqueue_depth` 与 `controller_runtime_reconcile_errors_total` | 控制器是否跟得上 | 个数与计数 | 队列持续增长说明消费不足；错误计数上升说明调和失败 | `controller_runtime_reconcile_time_seconds` | 两者同升 → 先定位失败的调和动作 |
| `leader_election_master_status` | 当前执行者是谁 | 布尔（按持有者分标签） | 同一时刻应当只有一个为真 | 切换次数与选举慢路径计数 | 出现两个为真 → 处于切换窗口，动作必须可重入 |

**指标端点受授权保护。** 读指标之前先确认自己有没有对应的非资源权限；取到的数值只代表当时的采样窗口。

## 3. 采样纪律与扩展面基线卡

扩展面的问题大多不是"某一次请求失败"，而是"某一段时间里的分布变了"。因此采样要固定口径：同一组标签、同一段时间窗、同一种聚合方式，先把基线记下来，再谈变化。

| 基线项 | 取值来源 | 交付时要给出 |
| --- | --- | --- |
| 类型清单与来源 | 发现结果与 CRD 清单 | 有哪些组、哪些类型、由谁提供 |
| 每个类型的版本状态 | CRD 的 `spec.versions` | 服务版本、存储版本、已弃用版本分别是什么 |
| 每个类型的迁移状态 | CRD 的 `status.storedVersions` | 是否还有旧版本留在存储里 |
| 每个类型的契约摘要 | CRD 的 schema | 哪些字段被剪枝、校验规则有多少条、子资源是否开放 |
| 写路径上的判定清单 | 策略、绑定与钩子配置 | 命中哪些资源、当前动作是拒绝还是只观察 |
| 判定耗时与拒绝分布 | 入口组件指标 | 分位数耗时、拒绝次数、放行失败次数 |
| 转交关系 | `APIService` 清单与状态条件 | 每个组的后端服务、信任根与可用性 |
| 行为责任方 | 控制器部署与指标 | 谁在调和、副本数、队列与错误情况 |
| 升级前的检查结果 | 基线各项的历史快照 | 与更早一次基线的差异，以及需要动作的条目 |

## 4. 四类现场与排查方向

### 4.1 类型注册与契约

**现场**：清单提交成功，但客户端报"不认识这个类型"，或者写入的字段读回来不见了。

**先看什么**：先看发现文档里有没有这个类型，再看 CRD 的状态条件，最后看 schema 里对应层级有没有声明保留未知字段。**判据**：发现里没有该类型，说明注册或服务状态有问题；发现里有而字段消失，说明是剪枝；出现 `NonStructuralSchema` 说明契约本身不结构化。**转向哪一步**：注册问题回到 CRD 的名字与作用域；剪枝问题回到 schema；状态条件为假时先别继续往下排查。

### 4.2 版本与转换

**现场**：某个版本读不出来，或者写入报转换失败；也可能是明明改了存储版本，旧版本却一直删不掉。

**先看什么**：把服务版本、存储版本与 `storedVersions` 三条线并排放，再看转换服务的端点与信任根。**判据**：三线不一致说明迁移没有走完；转换服务不可达或证书过期说明失败发生在转换这一步；`storedVersions` 里仍有旧版本说明不能删版本。**转向哪一步**：迁移未完成就先补迁移；转换失败先修服务与证书；两者都对而客户端仍报错时，再回到客户端的 API 版本设置。

### 4.3 判定与钩子

**现场**：写入被拒但原因不明；或者反过来说，本该被拦下的写入通过了。

**先看什么**：先分清是判定结论还是调用事故，再看策略与绑定的匹配范围与当前动作。**判据**：拒绝次数带判定类标签，说明是规则命中；带调用失败类标签，说明是钩子不可用；放行失败计数大于零，说明有请求在失败策略下被放过去了。**转向哪一步**：判定命中的回到表达式与规则；调用失败的回到钩子或扩展服务自身；放行失败的先评估影响范围，再决定是否收紧失败策略。

### 4.4 聚合与控制器

**现场**：某个组的类型忽然从工具里消失；或者对象创建之后长时间没有变化。

**先看什么**：前者先看 `APIService` 的可用条件与后端服务，再看发现请求是否超时；后者先看 `generation` 与 `status.observedGeneration`，再看队列与调和指标。**判据**：条件为假或服务端点缺失，说明问题在聚合层；两个代数长期不等且队列增长，说明问题在控制器侧。**转向哪一步**：聚合层的问题回到服务与信任根；控制器的问题先分清是调和失败还是消费不足。

## 5. 破坏性动作的边界

前两项会改变数据、第三项会让判定静默失效，因此这三项只能在可丢的实验集群上执行；在生产集群上动手之前，必须先备份、先在实验集群演练一遍恢复。后两项分别给出"需要窗口的配置变更"与"任何集群都不执行"的边界：

| 动作 | 为什么危险 | 边界与不可回滚说明 |
| --- | --- | --- |
| 删除一个 CRD | 入口组件会卸载它的端点，并删除其中**全部**自定义对象 | 只在可丢的实验集群执行；删除后没有回滚路径，只能从备份恢复对象 |
| 手工移除对象的清理项 | 会跳过外部资源的清理，留下无法自动回收的残留 | 只在可丢的实验集群执行；外部资源是否仍需清理必须在动手前确认 |
| 把钩子的失败策略从拒绝改为放行 | 相关判定会静默失效，安全与合规约束随之消失 | 只在可丢的实验集群验证；改动前先记录当前策略与命中范围 |
| 给已在使用的类型加校验规则 | 存量对象在被改动到相关字段时会开始失败 | 属于需要窗口的配置变更，不是破坏性操作；先在观察动作下运行，并准备好撤销规则的回滚点 |
| 直接编辑存储中的对象 | 绕过全部关卡，导致缓存与权威长期不一致 | 任何集群都不执行；这类动作没有可核对的证据链 |

## 6. 常见坑

| 常见做法 | 后果 |
| --- | --- |
| 只看清单提交成功 | 提交成功只说明对象进了存储，判定、转换与调和都还没有被验证 |
| 用发现结果判断权限 | 发现回答"有什么"，角色回答"能不能做"，两者不能互相替代 |
| 把 `storedVersions` 当成历史信息忽略 | 它决定了删版本这一步能不能做 |
| 看拒绝次数不看原因类型标签 | 判定拒绝与调用失败会被混为一谈，处置方向随之出错 |
| 只在指标上看到异常就重启控制器 | 重启会清空队列与计数，失去基线；先看清是消费不足还是调和失败 |
| 生产集群上验证失败策略的降级行为 | 会让策略静默失效；这类验证只在可丢的实验集群做 |

## 7. 要点自测

**问：为什么排查扩展面问题要先看发现结果，而不是先看权限？**

答：发现回答"集群里有没有这个类型、它的名字与作用域是什么"，权限回答"这个身份能不能对它做某个动作"。如果类型根本没有被服务，权限配置再正确也不会生效；两者混在一起排查，会在错误的方向上反复核对角色绑定。

**问：`storedVersions` 与 `spec.versions[].storage` 各自回答什么问题？**

答：`storage` 回答"从现在开始，新写入的对象存成哪个版本"，`storedVersions` 回答"历史上存过哪些版本、现在还有没有旧版本留在存储里"。迁移完成的判据是后者，不是前者。

**问：为什么判定类指标与调用失败类指标要分开看？**

答：判定类指标上升说明有写入真的不合规，方向是改对象或改规则；调用失败类指标上升说明判定根本没有执行成功，方向是修钩子或扩展服务的可用性。两者的处置动作完全不同，混在一起看会得出相反的结论。

**问：放行失败计数为什么值得单独盯？**

答：它统计的是"本该被判定却因为失败策略被放过去"的请求。该计数大于零意味着存在一段静默失效的窗口，安全与合规上需要评估影响范围；它也是把失败策略从拒绝改成放行之前必须记录的基线。

**问：为什么生产集群上不做失败策略的降级验证？**

答：验证降级必然要临时让判定失效，而这段窗口里不合规的写入会通过。这类验证只能在可丢的实验集群上做，生产上要验证的是降级预案本身是否可行，而不是把判定真正关掉。

**第一反应不要做什么**：不要在 CRD 状态条件为假时继续往下排查；不要在迁移没走完时删除旧版本；不要只看拒绝次数不看原因类型；不要为了看清问题而重启控制器；也不要在生产集群上验证让判定失效的降级路径。
