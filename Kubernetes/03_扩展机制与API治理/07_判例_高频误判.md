# 高频误判

十条判例都取自扩展面与策略上线时的真实处境，每一条都按同一套字段展开：**场景 → 常见误判（以及它为什么看起来成立）→ 判据（读哪个字段、什么数值或趋势、什么条件下结论会变）→ 一句话结论 → 出处**。

## 1. 「CRD 建好了，对象也能创建，所以功能已经就绪」

**场景**：一份 CRD 与几条示例对象提交成功，交付清单上的"扩展已上线"被勾掉；两周之后业务反馈"这个功能一直没动静"。

**常见误判**：把"类型注册完成"当成"行为已经实现"。这一判断之所以看起来成立，是因为对象确实能被创建与读取；但注册只让入口组件认识这个类型，行为必须由一个在运行的控制器去执行。

**判据**：先确认是否存在为这个类型负责的控制器：它是否在运行、是否在调和这个类型的对象、对象上的期望代数与已处理代数是否相等。**条件会变**：如果控制器在运行而代数长期不等，问题在调和逻辑；如果根本没有控制器，那么与集群、权限或 schema 都无关，缺的是一段行为。

**一句话结论**：注册解决"能不能存"，控制器解决"会不会动"；两者是两件事。

**出处**：Kubernetes 官方文档中关于自定义资源与 Operator 概念的章节。

## 2. 「策略上线了，存量对象也应该被拦住」

**场景**：一条新策略切到拒绝动作，随即收到反馈：集群里大量老对象完全不满足新规则，但重新提交一份完全相同的对象却会被拒绝。

**常见误判**：把策略理解成"对集群现状的断言"。这一判断之所以看起来成立，是因为策略描述的确实是"对象应该满足什么"；但判定只发生在写入请求上，已经存在的对象不会被回查。

**判据**：确认策略的判定范围只覆盖写请求，再统计存量对象里有多少不满足规则。**条件会变**：如果对象被人改动到相关字段就会开始失败，说明这不是"策略没生效"，而是"存量对象还没有被处理"；处理存量对象需要另有一条清理或迁移路径。

**一句话结论**：策略管的是之后的写入，存量对象需要单独安排处理动作。

**出处**：Kubernetes 官方文档中关于准入控制与校验型声明式策略的章节。

## 3. 「拒绝就是权限问题，先给这个身份加权限」

**场景**：一个写入请求返回 403，值班第一反应是去给调用方补一条角色绑定；补完之后仍然被拒绝。

**常见误判**：把"被拒"等同于"权限不足"。这一判断之所以看起来成立，是因为授权失败确实返回同一个类别的状态码；但同一个返回码也可能来自准入判定，两者的原因文本完全不同。

**判据**：读响应体里的原因文本，再对照策略与钩子的命中记录。**条件会变**：如果原因文本里出现具体策略名与表达式，那么方向是修改对象或修改策略；如果出现的是权限相关文本，方向才是核对角色与绑定。

**一句话结论**：同一个状态码可能来自不同的关卡，先读原因文本再决定动作。

**出处**：Kubernetes 官方文档中关于授权、准入控制与响应状态码的章节。

## 4. 「钩子挂了只影响新对象」

**场景**：一个校验钩子所在的服务被误删，值班认为"至少已经跑着的业务不受影响"；随后一批自动伸缩触发的写入全部失败。

**常见误判**：把钩子的作用范围理解成"创建时机"。这一判断之所以看起来成立，是因为钩子确实只在写入时被调用；但写入不只是创建，更新、删除与它们背后的控制器动作同样是写入。

**判据**：看钩子的调用失败计数与放行失败计数，并确认失败策略的取值。**条件会变**：失败策略为拒绝时，相关写入会大面积失败，属于可用性事故；策略为放行时，写入会通过但判定静默失效，属于合规问题。两种情况下都不能只盯着"新对象"。

**一句话结论**：钩子位于写路径上，而写路径覆盖创建、更新与删除，因此它的可用性就是写路径的可用性。

**出处**：Kubernetes 官方文档中关于动态准入与失败策略的章节。

## 5. 「字段读回来不见了，是控制器改的」

**场景**：客户端提交的对象里带了一个新字段，读取时却看不到它，值班开始排查控制器与准入钩子。

**常见误判**：把字段消失归因于某个会改对象的组件。这一判断之所以看起来成立，是因为控制器与变更钩子确实会改写对象；但更常见的原因是 CRD 的 schema 没有声明这个字段，入口组件在写入时就已经把它剪掉。

**判据**：先看该字段所在的层级有没有声明保留未知字段，再看对象上记录的字段归属信息。**条件会变**：如果字段在提交之前就被剪掉，与控制器无关；如果字段归属显示它由某个组件管理，再去看这个组件的行为。

**一句话结论**：先确认字段有没有被写入过，再讨论是谁改的。

**出处**：Kubernetes 官方文档中关于结构 schema 与字段剪枝的章节。

## 6. 「`storedVersions` 是历史记录，不影响当前操作」

**场景**：团队决定删掉一个已经不再服务的旧版本，但提交后的 CRD 更新被拒绝。

**常见误判**：把 `storedVersions` 当成仅供参考的历史信息。这一判断之所以看起来成立，是因为它确实记录的是"曾经写入过的版本"；但存储在里面的旧对象并没有被自动重写，只要该数组还包含旧版本，删除版本就会留下读不出来的对象。

**判据**：读 `status.storedVersions`，确认它是否只剩目标版本；再看 `spec.versions` 里的存储版本指向。**条件会变**：数组只剩目标版本时，删除版本是安全动作；数组仍包含旧版本时，必须先完成迁移。

**一句话结论**：`storedVersions` 是"能不能删版本"的判据，不是历史炫耀。

**出处**：Kubernetes 官方文档中关于自定义资源版本与存储版本的章节。

## 7. 「转换服务只服务旧客户端，晚点修也行」

**场景**：转换服务所在的工作负载被滚动更新到一半，值班认为影响的只是"还在用旧版本的少数客户端"。

**常见误判**：把转换理解成"客户端侧兼容"。这一判断之所以看起来成立，是因为转换确实让旧客户端能读懂新对象；但转换发生在服务版本与存储版本不一致的所有路径上，包括写入与监听。

**判据**：确认服务版本与存储版本是否一致，再查转换服务的调用失败率与端点状态。**条件会变**：两者一致时不会触发转换；两者不一致时，转换服务不可用会影响该类型的读写与控制器同步。

**一句话结论**：只要服务版本与存储版本不同，转换就在读写路径的中间，而不是可选的外挂。

**出处**：Kubernetes 官方文档中关于自定义资源转换的章节。

## 8. 「加了新校验规则，存量对象会立刻不合规，所以不能加」

**场景**：提供方希望给已投入使用的类型增加一条字段关系校验，被"会拦住存量对象"的担心劝退。

**常见误判**：把新规则理解成"立刻对全体对象生效"。这一判断之所以看起来成立，是因为校验确实在写入时执行；但校验棘轮会豁免"未被改动的部分"，只有被改动的字段才按新规则判断。

**判据**：确认棘轮是否生效，再看存量对象在改动相关字段时会发生什么。**条件会变**：如果新规则落在棘轮不支持的校验类型上（例如必填项或量词下的校验），那么它不会被豁免，必须按普通的新规则来处理。

**一句话结论**：棘轮让"新增规则"和"清理存量"可以分两步走，但要在同一段窗口内完成。

**出处**：Kubernetes 官方文档中关于自定义资源校验棘轮的章节。

## 9. 「多部署一个副本，控制器就能处理得更快」

**场景**：控制器的队列持续堆积，值班把副本数从 1 调到 3；队列深度没有明显下降。

**常见误判**：把控制器的并行度等同于副本数。这一判断之所以看起来成立，是因为副本数确实是常见的扩容手段；但控制器通过租约保证同一时刻只有一个执行者在调和，其余副本处于待命状态。

**判据**：看持有租约的状态指标，确认同一时刻有几个副本在执行；再看队列的排队时长与处理时长谁在增长。**条件会变**：如果处理时长在增长，问题在单次调和太慢（常见原因是直读或调用外部系统），加副本无效；如果是不同对象集合互相竞争，才需要考虑分片而不是加副本。

**一句话结论**：副本数买的是可用性，不是吞吐；要并行必须按对象集合分片。

**出处**：Kubernetes 官方文档中关于控制器与领导者选举的章节，以及客户端库的选举实现说明。

## 10. 「聚合服务的 `Available` 为假，只影响那一个功能」

**场景**：某个聚合服务的状态条件显示不可用，值班判断"我们没用这个功能，先不管"；随后工具开始报类型清单不全、部分客户端无法发现资源。

**常见误判**：把聚合服务当成一个独立的可选功能。这一判断之所以看起来成立，是因为它确实只提供一组特定的类型；但它的发现请求与入口组件绑定，服务不可达或响应过慢时，整个组的发现结果都会残缺，依赖类型清单的工具与控制器会一起受影响。

**判据**：读该 `APIService` 的状态条件与后端服务的端点，再看发现请求是否出现超时。**条件会变**：如果只是该组内的某个类型异常，问题在该服务内部；如果是整个组从发现里消失，问题在转交关系或服务可用性上。

**一句话结论**：聚合服务挂掉影响的是"这一组 API 能不能被发现"，而不只是某个具体接口。

**出处**：Kubernetes 官方文档中关于聚合层与 `APIService` 的章节。

## 值班口径

被追问"扩展面的十条误判有没有共同的成因"时，答法是把它们归为四类。第一类是**把注册当成完成**：CRD、策略、上传都是起点，不是终点。第二类是**把单点判断当成全局判断**：策略只看写请求，钩子只看本次提交，缓存只反映过去某一刻。第三类是**把可选组件当成外挂**：转换服务、聚合服务与钩子都位于关键路径上。第四类是**把配置项当成注释**：`storedVersions`、校验动作、失败策略与副本数都在决定现场行为。

被追问"为什么判据必须写成读哪个字段加什么条件下结论会变"时，答法是：同一个现象在不同条件下指向不同的根因。只说"看状态条件"只是线索；说清"条件为假时先处理它、为真时才继续往下查"才是可以迁移的判断。

被追问"扩展面上的变更怎么安排窗口"时，答法是分三步：先确认当前处于哪一段（注册、契约、版本、判定、行为），再确认动作的可逆性（改配置可以撤销，删类型与删清理项不可以），最后才安排执行顺序。破坏性动作只在可丢的实验集群演练，生产上执行的是演练过的步骤与已验证的备份恢复。

**第一反应不要做什么**：不要把注册完成当成功能就绪；不要以为策略会回查存量对象；不要把 403 一律当成权限问题；不要把转换与聚合服务当成可选外挂；不要用加副本处理队列堆积。
