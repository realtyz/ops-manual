# 准入策略的判定机制

## 1. 判定写在哪里，决定了它以什么方式失败

把判定逻辑写进准入钩子——在集群外接一个进程，收到评审对象（AdmissionReview）后返回允许或拒绝——几乎没有表达能力上的上限，但三类问题会随之出现：

| 问题 | 具体表现 |
| --- | --- |
| 改一条规则要发一次版 | 判定逻辑在镜像里，规则调整要走构建、发布与回滚流程 |
| 策略内容不可审计 | 集群里只留下一份钩子配置，具体拦了什么、为什么拦，只能翻它的日志 |
| 判定进程成为写路径的一部分 | 它的可用性、证书与版本都变成集群的可用性问题 |

因此需要对判定做一次拆分：**能用声明表达的判定，直接写成 API 对象，在入口组件进程内求值；只有必须访问外部系统或需要任意代码的判定，才留在钩子里**。本章的判定面就是把这两条路各自的配置讲清楚。

## 2. 两条实现路径的对照

| 维度 | 准入钩子 | 声明式准入策略 |
| --- | --- | --- |
| 判定在哪 | 集群之外的进程 | 入口组件进程内 |
| 上线需要什么 | 部署、证书、服务与副本；跨版本兼容 | 只需写入策略与绑定对象 |
| 能否改写对象 | 变更钩子可以，校验钩子不可以 | 变更型策略可以，校验型策略不可以 |
| 观察与预演 | 只能由钩子自己实现试运行与日志 | 校验动作可以直接选择只告警或只记入审计 |
| 证据留在哪 | 钩子自身的日志、审计注解与入口组件指标 | 审计事件、策略的检查状态与入口组件指标 |
| 可用性归属 | 提供方；钩子调用失败按失败策略处理 | 入口组件自身；表达式错误按策略自己的失败策略处理 |
| 表达能力的边界 | 可以访问集群内外的任何服务 | 只能看到本次请求、参数对象与授权检查；不支持跨对象的状态判断 |

两条路径不是替代关系：**声明式策略覆盖绝大多数规则型判定，钩子保留给必须访问外部系统或需要自定义代码的判定**。混合使用时要记住一件事：策略与钩子都会被入口组件调用，因此两者的成本都会体现在写请求的延迟上。

## 3. 钩子的配置面：一段配置决定了它拦什么、怎么拦

钩子由 `ValidatingWebhookConfiguration` 与 `MutatingWebhookConfiguration` 两类对象注册，每个对象里可以有多条钩子，同一条配置里的钩子名必须唯一，否则审计与指标无法对应到具体钩子。

| 字段 | 决定什么 | 判据 |
| --- | --- | --- |
| `rules[]` 的 `operations` / `apiGroups` / `apiVersions` / `resources` / `scope` | 哪些请求会被发给钩子 | `"*"` 匹配全部资源但不含子资源；`"*/*"` 连子资源一起匹配；作用域默认不限 |
| `matchPolicy` | 同一个资源的其它版本是否也匹配 | 取值 `Exact` / `Equivalent`，默认 `Equivalent`；等价匹配会把对象转换成钩子注册的版本 |
| `objectSelector` 与 `namespaceSelector` | 按对象标签与命名空间标签裁剪 | 两个选择器都命中才会发送；命名空间级请求不会被命名空间选择器拦住 |
| `matchConditions`（CEL） | 在以上条件之上再做细粒度过滤 | 全部条件为真才调用；任一条件为假直接跳过；最多 64 条 |
| `sideEffects` | 钩子声明自己有没有副作用 | 取值 `None` / `NoneOnDryRun`；声明有副作用却不处理试运行请求时，试运行请求会被拒绝 |
| `reinvocationPolicy` | 变更钩子是否可能被再次调用 | 取值 `Never`（默认）/ `IfNeeded`；调用次数不保证，钩子必须幂等 |
| `admissionReviewVersions` | 评审对象使用哪个版本 | 入口组件与钩子都能理解的版本才能协商成功 |
| `clientConfig` | 请求发到哪 | 可以直接给 URL，也可以通过服务引用；通过服务引用时端口约定为 `443` |

有两条顺序事实决定了钩子看到什么：

- **变更阶段先于校验阶段，策略先于钩子。** 入口组件推荐的插件顺序是：生命周期的变更插件 → 变更型策略 → 变更钩子 → 校验型策略 → 校验钩子。因此变更钩子看到的是"变更型策略已经改过一遍"的对象，而校验环节看到的是全部变更之后的形态。
- **变更钩子不保证只被调用一次。** 当后续插件或策略修改了对象，声明了 `IfNeeded` 的变更钩子可能被重新调用，而调用次数没有保证。因此变更逻辑必须写成幂等；要校验最终形态，应当在校验阶段做，而不是依赖变更阶段的重复调用。

**本篇写的是判定与变更的机制；关卡在写请求里的顺序与失败语义不属于本篇的范围**，这里只交代配置字段决定了什么。

## 4. 声明式校验策略：定义、绑定与参数三者分开

声明式校验由三类对象共同构成，缺一不可：

| 对象 | 作用 |
| --- | --- |
| `ValidatingAdmissionPolicy` | 描述判定的抽象逻辑，包括匹配范围、判定表达式与失败策略 |
| `ValidatingAdmissionPolicyBinding` | 把策略与参数对象连起来，并声明判定失败时做什么 |
| 参数对象 | 让同一条策略在不同范围产生不同结论；可以是内置类型，也可以是自定义资源 |

匹配与判定分别由这些字段决定：

| 字段 | 决定什么 | 判据 |
| --- | --- | --- |
| `spec.matchConstraints` | 这条策略关心哪些请求 | 含 `resourceRules`、`excludeResourceRules`、`namespaceSelector`、`objectSelector` 与匹配策略；排除规则优先于包含规则 |
| `spec.matchConditions` | 在匹配之上再做过滤 | 全部条件为真才求值；任一条件为假直接跳过；条件求值出错时按策略失败策略处理 |
| `spec.validations[].expression` | 判定表达式 | 求值为 `false` 即判定失败；`object` 在删除请求里为 `null`，`oldObject` 在创建请求里为 `null` |
| `spec.validations[].message` 与 `messageExpression` | 失败时给人看的文本 | `messageExpression` 必须求值为字符串；求值失败或多行文本时回退到静态消息 |
| `spec.validations[].reason` | 失败时返回给调用方的机器可读原因 | 取规则列表中第一条失败的规则；取值限定为 `Unauthorized`、`Forbidden`、`Invalid`、`RequestEntityTooLarge` |
| `spec.variables[]` | 把复杂的子表达式抽出来复用 | 按定义顺序求值，只能引用在它之前定义的变量，因此不存在循环引用 |
| `spec.paramKind` | 参数对象是什么类型 | 不写表示这条策略不需要参数，此时表达式里的 `params` 为 `null` |
| 绑定的 `spec.paramRef` | 用哪些参数对象 | `name` 与 `selector` 只能二选一；多个参数命中时逐个求值并把结论按"与"合并 |
| `spec.paramRef.parameterNotFoundAction` | 参数找不到时怎么办 | 必填；`Allow` 视为通过，`Deny` 交给策略的失败策略处理 |
| 绑定的 `spec.validationActions` | 判定失败时做什么 | `Deny`、`Warn`、`Audit` 可多选；`Deny` 与 `Warn` 不能同时使用 |

几个容易被忽略的边界：

- **策略必须与绑定成对存在才会生效。** 只有策略时，它只是一份没有被使用的定义；只有绑定时，它不指向任何判定逻辑。
- **参数对象需要被读取。** 判定方需要能读到 `paramKind` 指定的资源；参数是按命名空间查找还是全集群共用，由绑定上是否指定命名空间决定。
- **表达式能看到的范围是有限的。** 可用变量是 `object`、`oldObject`、`request`、`params`、`namespaceObject` 与 `authorizer`；除 `apiVersion`、`kind`、`metadata.name`、`metadata.generateName` 之外，表达式只能接触 schema 里声明过的字段。因此它做不了"集群里其它对象是什么样"的判断。
- **类型检查的结果写在策略状态里。** 策略创建后可以看它的检查状态：为空表示没有发现问题；检查本身不影响判定的行为，某条规则在运行时仍然可能出错，那时由失败策略决定结果。检查也不覆盖自定义资源类型，并且匹配类型数量有上限。
- **审计注解会带上策略名。** 注解键以策略名加 `/` 为前缀；如果另一个判定组件用了完全相同的键，先写入的值生效，其余被忽略。

这条路径的版本演进是阶段式的：**v1.26 引入（alpha，默认关闭）→ v1.28 进入 beta（该阶段门控仍默认关闭）→ v1.30 稳定（默认开启）→ 该特性门控在 v1.31 之后被移除**，出处是 KEP-3488 与官方特性门控页的 `ValidatingAdmissionPolicy` 阶段表。

## 5. 声明式变更策略：补丁是怎么被合成出来的

变更型策略用同一套"定义 + 绑定 + 参数"的结构，但它的输出是补丁而不是结论。`spec.mutations` 是一组 CEL 表达式，每条表达式必须产出补丁，且不允许为空列表：

| 补丁类型 | 表达方式 | 判据 |
| --- | --- | --- |
| `ApplyConfiguration` | 表达式求值为一个对象，按服务端应用的结构化合并语义并入请求对象 | 不允许修改原子性的结构、映射与数组，因为合并会连带删除未列出的值 |
| `JSONPatch` | 表达式求值为一组补丁操作，路径按 JSON 指针书写 | 键里含 `/` 或 `~` 时必须转义；操作里可以表达"先测试再替换"这类条件步骤 |

变更型策略可访问的变量与校验型一致，但暴露的元数据更少：只有 `apiVersion`、`kind`、`metadata.name`、`metadata.generateName` 与 `metadata.labels` 可以被直接读取。它的版本演进是阶段式的：**v1.32 引入（alpha，默认关闭）→ v1.34 进入 beta（门控仍默认关闭）→ v1.36 稳定（默认开启）**，出处是 KEP-3962（`keps/sig-api-machinery/3962-mutating-admission-policies`）与官方特性门控页的 `MutatingAdmissionPolicy` 阶段表；该 KEP 的 Implementation History 原文即 Alpha `v1.32`、Beta `v1.34`、Stable `v1.36`。**不要按"到达某个版本就一定可用"推断**，判断现场能否使用这个类型，依据是目标集群生效的门控状态。

变更型策略不能替代校验：官方建议的用法是**用变更把对象补成期望形态，同时用校验把结果定住**；只做变更而不做校验时，一旦表达式写错，被改错的对象会直接进入存储。

## 6. 成本与豁免：哪些对象不能被策略拦住

两条与稳定性直接相关的设计：

- **表达式有成本预算。** 无论是策略的判定表达式，还是钩子与策略的匹配条件，计算量都有上限；超出预算的定义在上线时就会被拒绝。官方对策略与匹配条件的严格成本校验自 v1.32 起为稳定默认行为，出处是官方特性门控页的 `StrictCostEnforcementForVAP` 与 `StrictCostEnforcementForWebhooks` 阶段表。
- **准入配置对象本身被豁免。** 通过 API 创建的策略与绑定不会被别的策略拦住，这是为了防止"一条写错的策略把修改策略的入口也堵上"这种无法用 API 恢复的状态。虚拟的鉴权类请求（例如令牌评审与权限自检）从一开始就被所有声明式策略排除；自 v1.37 起，准入钩子默认也排除这些虚拟资源，出处是官方特性门控页的 `ExcludeAdmissionWebhookVirtualResources` 阶段表。

此外还有一条更晚引入的部署方式：**把准入配置以清单文件的形式挂载到入口组件**，使其在启动时就生效、在存储不可用时仍然可用，也能拦住修改准入配置本身的请求。它的版本演进是 **v1.36 引入（alpha，默认关闭）→ v1.37 进入 beta（默认开启）**，出处是官方特性门控页的 `ManifestBasedAdmissionControlConfig` 阶段表。

## 7. 现场读法

| 看什么 | 是什么 | 单位 | 判据 | 与谁同看 | 看到它转向哪一步 |
| --- | --- | --- | --- | --- | --- |
| 钩子的 `rules` 与 `matchPolicy` | 哪些请求会被拦 | 规则数组与枚举 | `Equivalent` 会在版本之间做等价匹配 | 钩子的调用指标 | 钩子没有被调用 → 先核对规则与匹配策略，而不是先怀疑钩子进程 |
| 钩子的 `sideEffects` | 能否安全地处理试运行请求 | 枚举 | `NoneOnDryRun` 表示只在正常请求上有副作用 | 试运行请求的结果 | 试运行被拒 → 是副作用声明与实现不一致 |
| 策略的 `spec.validations[].expression` | 判定内容 | CEL 表达式 | 只看当前对象、参数与授权检查，不看其它对象 | 绑定的校验动作 | 判定没有生效 → 先确认策略与绑定是否成对存在 |
| 绑定的 `validationActions` | 失败时的动作 | 枚举数组 | 观察期用 `Warn` 与 `Audit`；`Deny` 与 `Warn` 互斥 | 判定表达式与入口组件指标 | 只有审计痕迹而没有拒绝 → 说明当前处于观察期 |
| `paramRef` 与 `parameterNotFoundAction` | 参数从哪里来、缺失时怎么办 | 结构体与枚举 | 缺失时按 `Allow` 放行或按 `Deny` 交给失败策略 | 参数对象的命名空间与选择器 | 参数相关拒绝突然增多 → 先确认参数对象是否存在 |
| 策略的状态与入口组件指标 | 判定是否在正常工作 | 结构体与计数器 | 指标按策略、策略绑定与校验动作分标签 | 审计事件里的注解 | 检查耗时或失败数上升 → 先看是哪条策略、哪个绑定 |

## 8. 抽象模型的适用边界

1. **判定不等于全局状态。** 声明式策略只看到本次请求与参数对象，跨对象的一致性判断仍然属于控制器。
2. **策略上线不会回查存量对象。** 判定只作用于其后的请求；要处理已有对象，必须另有一条清理路径。
3. **变更与校验是两件事。** 变更型策略负责补齐，校验型策略负责定住；只做其中一件都会留下缺口。
4. **调用次数不保证。** 声明了重新调用的变更钩子可能被多次调用，因此变更逻辑必须幂等。
5. **豁免清单是安全边界，不是遗漏。** 准入配置对象与虚拟鉴权资源的豁免，是为了避免把集群锁在无法恢复的状态里。
6. **成本预算决定了策略的上限。** 表达式越复杂，上线门槛越高、运行成本越大；把复杂逻辑写进控制器往往比继续堆表达式更稳。

## 常见误解

| 常见说法 | 事实 |
| --- | --- |
| 「写好策略就生效了」 | 还需要一条指向它的绑定；策略与绑定缺一不可 |
| 「策略能拦住所有写路径」 | 准入配置对象与虚拟鉴权请求被豁免，这是防止自锁的设计 |
| 「表达式里可以顺便查一下别的对象」 | 只能看到本次请求、参数对象与授权检查；跨对象判断要交给控制器 |
| 「把变更钩子设成每次都重新调用更安全」 | 调用次数没有保证，真正的兜底是幂等加上校验阶段 |
| 「判定拒绝和钩子调用失败是一回事」 | 前者是判定结论，后者是调用层面的事故，两者的处置方向不同 |
| 「注册了绑定就会把存量对象也检查一遍」 | 判定只作用于其后的请求；存量对象需要另行处理 |

## 要点自测

**问：声明式策略与准入钩子分别适合什么判定？**

答：声明式策略适合规则型判定：条件只依赖本次请求、参数对象与标签匹配，因此可以写成 API 对象并在入口组件进程内求值，还能只告警或只记审计。钩子保留给必须访问外部系统、需要自定义代码，或者需要集群外状态的判定；它的代价是可用性与版本兼容都由提供方承担。

**问：为什么策略与绑定必须分开设计？**

答：定义与配置分离之后，同一条判定逻辑可以在不同范围产生不同结论：策略描述"判定什么"，绑定决定"在哪里生效、用哪个参数对象、失败时做什么"。这也让一条策略可以被多条绑定以不同的强度使用。

**问：变更型策略为什么不允许修改原子性的结构、映射与数组？**

答：`ApplyConfiguration` 采用结构化合并语义，未列出的值会被视为应当删除。若允许它作用于原子性结构，一次不完整的表达式就会把并发写入的其它字段一并抹掉，因此这类字段被明确排除。

**问：为什么准入配置对象本身要被豁免？**

答：如果一条策略可以拦住对策略与绑定的写入，那么一旦这条策略写错，修复它的入口也会被堵上，集群只能从存储侧恢复。把这类对象排除在策略之外，是保留一条自我修复路径。

**问：观察一套新策略该看什么？**

答：先看绑定上的校验动作：观察期应当只告警与只记审计，此时没有拒绝是预期结果。再看审计事件里的注解与入口组件的策略指标，确认命中范围与耗时；确认无误之后才把动作改成拒绝，并按同口径继续观察。

**第一反应不要做什么**：不要只写策略而忘记绑定；不要用声明式策略去做需要查看其它对象的判断；不要指望上线策略会回头修正存量对象；不要把变更型策略当成校验的替代；也不要在没有观察期的前提下把新策略直接切成拒绝。
