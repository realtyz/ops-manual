# 镜像与运行时治理

## 1. 没有制度会同时出四件事

容器的分发与运行是节点侧行为，而节点侧行为的特点恰恰是**「谁都能改，改了没人知道」**。缺制度时，四类问题会各自出现，并且互相掩盖：

| 问题 | 具体表现 | 为什么会被当成别的问题 |
| --- | --- | --- |
| 不可追溯 | 出事时说不清「当时跑的是哪一份内容」 | 被当成应用 bug，反复回滚无果 |
| 不可复现 | 同一个标签在不同节点、不同时间对应不同内容 | 被当成「环境不一致」这类无法定位的说法 |
| 容量失控 | 节点磁盘水位周期性告警，驱逐把问题放大成故障 | 被当成「磁盘小」，于是加盘，然后再次告警 |
| 行为不一致 | 同一份镜像在不同节点表现不同（启动耗时、磁盘占用、挂载行为） | 被当成「偶发」和「玄学」 |

## 2. 行业通行做法

| 面向 | 通行做法 | 依据 |
| --- | --- | --- |
| 内容标识 | 一切生产引用固定到摘要，标签只作为人可读的别名 | OCI 镜像规范与分发规范对摘要的定义；Kubernetes 文档中镜像引用与拉取策略的行为差异 |
| 分发结构 | 分层构建，把「变化频率低」的内容放在下层，避免每次发布都产生大量新层 | 镜像规范中层的差分语义 |
| 来源可信 | 对镜像签名并生成证明，在准入环节校验，不接受未签名的引用 | 供应链实践：把签名作为与镜像关联的制品，格式本身不做强制 |
| 节点基线 | 运行时、快照器、存储路径、日志与回收参数作为节点配置的一部分被版本化 | Kubernetes 文档中关于节点配置与运行时类的章节 |
| 水位治理 | 回收阈值、驱逐阈值与日志上限按「一次发布所需的余量」反推，而不是随手调 | `kubelet` 配置文档中给出的默认值与信号划分 |
| 维护动作 | 运行时升级、节点池变更走变更流程，影响面按「操作面中断」而非「业务中断」评估 | 运行时文档中关于进程托管与守护进程重启的说明 |

## 3. 可交付产物

### 3.1 镜像准入规范卡

| 字段 | 内容 |
| --- | --- |
| 仓库与命名 | 命名规则（来源、用途、环境是否分离），谁能推 |
| 标签策略 | 允许的标签形态；生产环境禁止使用可变标签直接引用 |
| 摘要固定 | 生产工作负载一律以摘要引用；摘要在哪里被记录、由谁校验 |
| 基础镜像 | 允许的来源清单与版本更新节奏 |
| 体积预算 | 单镜像的层数上限与解压后体积上限，超限需要谁批准 |
| 内容检查 | 扫描要求与阻断规则 |
| 来源校验 | 签名与证明的要求、在哪个准入环节校验、失败时的行为 |
| 禁止项 | 密钥、凭据、构建期临时文件进入镜像的判定方式与检查手段 |

### 3.2 节点容器基线卡

| 字段 | 为什么要有 |
| --- | --- |
| 运行时名称与版本 | 跨节点比较与行为差异的第一来源 |
| 运行时端点 | 决定节点上排障用哪个客户端 |
| 快照器 / 根文件系统组织方式 | 决定磁盘占用与首次写延迟的量级 |
| 镜像存储与容器存储的落点及所在文件系统 | 决定哪些账本互相挤占 |
| 日志目录与轮转参数 | 决定节点侧保留窗口 |
| 镜像回收的高低阈值与最小回收年龄 | 决定回收的时机与速度 |
| 驱逐阈值（软 / 硬，各信号） | 决定节点吃紧时的动作与顺序 |
| 沙箱镜像 | 决定 Pod 能否创建成功；它属于节点侧资产 |
| 可用运行时档位清单 | 决定哪些 Pod 能声明强隔离运行时 |

### 3.3 发布与回收的排期表

| 字段 | 内容 |
| --- | --- |
| 发布窗口与单批节点数 | 与拉取带宽、仓库并发上限对齐 |
| 本次新增的镜像体积 | 预估节点磁盘增量，与回收阈值对照 |
| 回收窗口 | 何时允许回收，与发布错开以避免「刚拉就被回收」 |
| 验收读数 | 发布前后各一次同口径的镜像文件系统用量与水位 |

### 3.4 运行时变更单

| 字段 | 内容 |
| --- | --- |
| 影响面 | 运行中容器不受影响，但变更期间新创建、新执行的操作会失败 |
| 分批与窗口 | 每批哪些节点，批间隔多久 |
| 验证项 | 变更后新 Pod 能否创建、镜像能否拉取、执行与日志通道是否可用 |
| 回滚 | 回退到哪个版本、回退动作、回退后的验证项 |
| 验收读数 | 变更前后的镜像文件系统用量、一次典型拉取与启动的耗时 |

## 4. 关键字段的治理用法

| 字段 | 治理用法 | 常见误用 |
| --- | --- | --- |
| 镜像回收高低阈值 | 两个阈值之间的落差要能容纳**一次发布新增的镜像量**；落差太小会让回收与拉取互相追尾。文档默认是 85 / 80，把高阈值设为 100 等于关掉镜像回收 | 只调高阈值不调低阈值，或者为了省空间把两个都调到很低 |
| 镜像最小回收年龄 | 与发布节奏对齐：短于「一个发布周期」会让刚用的镜像处于可回收状态。文档默认 2 分钟 | 设得极短以「尽量多回收」 |
| 镜像最大回收年龄 | 用它做「按年龄兜底清理」时必须接受一个前提：**它不跨 `kubelet` 重启累计**，重启后计时从头开始，清理会被推迟一整个周期。文档默认是 0 秒，也就是**关闭** | 打开它却不重启节点，于是以为「一周前的镜像早该清了」 |
| 容器回收 | 保留的已退出容器是排障材料，也是有上限的：每个 Pod 保留数与全局保留数各有默认（默认每 Pod 一个、全局不限），要按「留多久够查一次故障」来定 | 把保留数调到极大，于是历史容器把磁盘吃满 |
| 日志单文件上限与份数 | 两者相乘是节点侧的保留窗口；它应当由**采集端的保留期**决定，而不是由排障手感决定。文档默认 10Mi × 5 份 | 为了「多留点历史」放大上限，把磁盘压力从采集端转移到节点 |
| 驱逐阈值（软 / 硬） | 软阈值给应用一个准备窗口并成立；硬阈值保节点存活。文档默认的硬阈值是内存 100Mi、节点文件系统可用 10%、镜像文件系统可用 15%、两者 inode 可用 5% | 只设硬阈值，于是节点没有任何缓冲 |
| 驱逐阈值的完整性 | 要么把所有硬阈值完整写出来，要么显式打开「与默认值合并」的开关 | 只改一个阈值——**其余阈值不再继承默认值而变成 0**，节点会在极低水位才开始动作 |
| 运行时档位（`RuntimeClass`） | 把「需要强隔离」的负载显式声明出来，而不是给它特权去做别的事；同时把可用的档位清单写进节点基线卡 | 用特权容器绕过限制，把安全边界交给应用自觉 |
| 运行时 cgroup 驱动 | 把它写进基线卡并纳入巡检：新版本能自动从运行时探测并忽略本地设置，但**旧运行时的兜底将在 v1.38 被移除**，所以升级顺序是**先动运行时、后动 `kubelet`** | 认为「驱动不一致只是告警」——既有 Pod 的沙箱重建会失败，重启 `kubelet` 可能无效，往往只能换节点 |
| 清理动作的归属 | 镜像与容器的回收交给 `kubelet` 与运行时自身的引用关系；人工清理只走受控入口 | 引入外部清理工具——官方明确不建议，会破坏 `kubelet` 的行为并可能删掉本应存在的容器；手工去运行时根目录删文件同样禁止，那些目录是实现细节，外部读取或监听都会让运行时的清理动作出错 |
| 工具的稳定性分级 | 排障脚本与 Runbook 一律以**走 CRI 的那个客户端**为准，运行时自带客户端只作只读旁证 | 把运行时自带的调试客户端写进自动化——上游明确把它标为不受项目支持，次要版本就可能破坏性变更 |
| 节点服务单元的配置 | 把「运行时守护进程重启不影响运行中容器」写进节点基线并验收：服务单元必须下放 cgroup 管理权、且只终止守护进程本身 | 假设这条性质是运行时自带的——少了那两项配置，一次无感升级会拆掉整台节点上的业务 |
| 镜像引用方式 | 准入环节校验引用是否为摘要；流水线里同时记录标签与摘要的对应 | 只在流水线里固定摘要，集群里的部署模板仍用标签 |

### 4.1 校验的执行点，决定「有没有强制力」

签名与证明本身不拦截任何东西——**它们只是可被校验的关联制品**。真正产生拦截力的是「谁来校验」：

| 执行点 | 能做什么 | 必须记住的事实 |
| --- | --- | --- |
| 镜像格式 | 提供摘要，并提供「把这个制品挂到那个镜像上」的关联机制 | 只提供**能力**，不提供**策略**：规范里没有任何「签名无效就不许运行」的规定 |
| 准入环节 | 校验摘要、把标签改写成摘要、按策略拒绝、把决策外包给后端 | 内置里**碰镜像**的只有两个：一个把拉取策略强制改成「每次都去拉」，它的用途是**多租户下私有镜像不被无凭据方复用，不是验签**；另一个把决策外包给一个必须走 TLS 的后端。声明式策略自 v1.30 起稳定，可以在准入里直接读容器镜像字段做校验。**官方文档没有任何一句声明存在内置的签名校验**——要验签就得靠策略控制器或自己的后端 |
| 节点侧运行时 | 在真正创建容器之前拦下镜像 | 运行时可挂载镜像校验插件，判定方式很硬：**退出码为 0 放行，非 0 阻止**；多个校验器是「与」的关系。要特别注意**校验器目录不存在或为空时不会阻止**——配置写错会静默变成不设防 |
| 拉取凭证校验 | 判断「拉这个镜像时用的凭证对不对」 | 与签名是两件事：它只解决凭证，不解决来源可信，别把它当成验签 |
| 关联制品的可发现性 | 让校验方找到签名与证明 | 依赖仓库支持「按摘要列出关联制品」。运行时自述的一致性版本可能**只覆盖分发规范的最早期版本**，因此这条能力**取决于仓库与客户端各自的版本**，不要默认成立 |

一句话：**格式给摘要，准入给策略，运行时校验器给最后一道闸。** 三处都要有，缺任何一处都留一条绕过路径——只有签名而没有强制点，等于把安全性建立在「没有人会绕过」之上。

## 5. 三个具象治理场景

**场景一：某节点磁盘每周告警一次。** 要交出的产物是**节点容器基线卡 + 参数核算表 + 验收读数**。核算方式是按文件系统分开取两次同口径读数、算出每小时增长率，再反推「一次发布新增多少、当前阈值能容纳几次发布、回收窗口在哪里」。验收读数是调整后连续一周内不再越线，且没有出现「刚拉取就被回收」的迹象。

**场景二：运行时有一个安全补丁要打。** 要交出的产物是**运行时变更单**。关键是把影响面写对：运行中的容器不受影响，受影响的窗口里新创建与新执行的操作会失败。因此验证项写的是「变更后新 Pod 能否创建、镜像能否拉取、执行与日志通道是否可用」，而不是「业务是否中断」。回滚要写清回退的版本与回退后的同一组验证项。

**场景三：一次发布之后，部分节点上的实例行为与预期不符。** 要交出的产物是**镜像准入规范卡 + 摘要固定的落地方式 + 一次复盘**。复盘的结论不能停在「标签被覆盖了」，而要落到「哪一步允许了以可变标签引用生产」以及「准入环节为什么没有拦下来」；改进项要能验证——例如下一次发布中随机抽查若干节点，核对运行的摘要与流水线记录是否一致。

## 6. 与其它章节的接口

| 接口 | 边界 |
| --- | --- |
| 供应链安全（签名、扫描、准入校验策略） | 本篇只规定「要固定摘要、要校验来源」这条治理要求；校验用什么组件、策略怎么写，属于安全那一章 |
| 资源上限与服务质量档位 | 上限配在资源字段上；但**驱逐顺序不由服务质量档位决定**，实际看用量与 requests 的关系以及优先级——这套判定属于调度与资源那一章 |
| 节点水位与生产变更流程 | 水位信号的完整处置顺序、变更的分级与复盘模板属于生产运维那一章 |
| 宿主侧机制 | cgroup 计量、命名空间与联合挂载的判据属于 Linux 主题域；本篇只用它的结论，不重复推导 |

## 7. 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 「先把盘加大，回头再治理」 | 加盘会让增长斜率被掩盖一个周期，但回收与发布的追尾关系没变，告警会以更大规模回来 |
| 「镜像回收交给默认值就行」 | 默认值是按通用场景定的，与你的镜像体积、发布频率、单批节点数无关 |
| 「日志调大是为了排障」 | 节点侧日志是保留窗口而不是归档；历史应当由采集端保存 |
| 「运行时升级风险太高，先不动」 | 运行中的容器不受影响；把影响面写成「业务中断」会让评估失真，也会让该做的补丁一直不做 |
| 「签名上了就安全了」 | 签名只是可校验的关联制品，本身不拦截；没有准入或运行时校验器去强制，它不产生任何拦截力 |
| 「接入了懒加载，启动就变快了」 | 它要求节点装插件并在节点启动时配置，还可能改动镜像本身（摘要变化、针对原镜像的签名失效），而且对小镜像没有收益；标准层根本没有这个原语 |
| 「我们的仓库当然支持关联制品查询」 | 支持程度随仓库与客户端版本变化；有实现自述只覆盖分发规范的最早期版本，选型前要实测 |
| 「节点基线都一样」 | 不同节点池的存储、快照器与阈值可以不同；跨节点比较读数前必须确认基线一致 |
| 「自己写脚本定期清镜像和容器」 | 官方明确不建议使用外部回收工具：会破坏 `kubelet` 自身的回收行为，并可能删掉本应存在的容器 |
| 「驱逐阈值的默认值一直都在，改一个无所谓」 | 默认阈值只在**所有参数都未被改动**时生效；动了一个，其余会变成 0，节点会在极低水位才开始动作 |
| 「先升 `kubelet`，再升运行时」 | 顺序反了：`kubelet` 侧对旧运行时的兜底将在后续版本移除，先升 `kubelet` 会让节点起不来。运行时在前 |
| 「cgroup 驱动配错了改回来就行」 | 既有 Pod 的沙箱重建会失败，重启 `kubelet` 可能解决不了；官方给出的出路是换掉这台节点或用自动化重装 |

## 8. 要点自测

**问：为什么镜像回收的两个阈值要一起调？**

答：高阈值决定何时开始回收，低阈值决定回收到哪里停。两者之间的落差必须能容纳一次发布新增的镜像量；落差太小，回收刚结束就又触发，形成与拉取互相追尾的循环。再叠加最小回收年龄，是为了保护「刚拉下来的镜像」。

**问：运行时升级的影响面怎么写才准确？**

答：写「运行中的容器不受影响，变更窗口内新创建、新执行的操作会失败」。这来自容器进程与守护进程寿命解耦的设计。把它写成「业务会中断」会让风险评估失真——偏严会导致补丁长期不做，偏松会漏掉对依赖同一组件的其它节点侧服务的影响。

**问：为什么生产环境必须用摘要引用镜像，而不能只用标签？**

答：标签是仓库侧的可变映射，同一标签在不同时间可以指向不同内容，因此「部署成功」不能推出「各节点运行的是同一份内容」。摘要由内容决定，可以校验、可以复现、可以追溯。只固定标签会让不可复现性问题以「偶发」「环境不一致」这类无法处置的形式出现。

**问：节点侧日志保留窗口应当由什么决定？**

答：由采集端的保留期决定，节点侧只留到「采集端确认取走」为止。节点侧的日志上限与份数直接构成磁盘占用，把它当成归档会让磁盘压力从有保留策略的采集端转移到没有保留策略的计算节点上。

**问：为什么节点侧的升级顺序必须是「先运行时、后 `kubelet`」？**

答：因为新 `kubelet` 会要求运行时支持第一版的 CRI 接口，并且会自己从运行时探测该用哪种 cgroup 驱动、忽略本地配置。旧运行时两件事都可能不满足，而 `kubelet` 侧对旧运行时的兜底会被后续版本移除。先把 `kubelet` 升上去，节点会直接注册不上或起不来；反过来先升运行时，运行时的向后兼容性要宽松得多。

**问：改动一个硬驱逐阈值，为什么要连带检查其余阈值？**

答：这些默认阈值不是一个一个独立生效的——只有当**所有参数都未被改动**时，默认值才会被套用；只要动了任意一个，其余参数不再继承默认值而变成 0。于是节点会在极低水位才开始动作，看起来「配置对了但不生效」。要么把所有阈值完整写出，要么显式打开「与默认值合并」的开关。

**第一反应不要做什么**：不要用「加盘」代替对增长源与回收参数的核算；不要把节点侧日志当成归档；不要在评估运行时升级时把影响面写成业务中断，也不要在没有基线卡的情况下跨节点比较读数。
