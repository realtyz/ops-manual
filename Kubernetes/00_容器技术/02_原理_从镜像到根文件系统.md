# 从镜像到根文件系统

## 1. 每次启动都完整展开一层，会同时出三件事

镜像是一串只读的差分归档。要让它变成一个可运行的根文件系统，最直接的做法是「按顺序解开到一块专属目录里」。这个做法会同时带来三件互相独立的问题：

| 问题 | 具体表现 |
| --- | --- |
| 启动成本与镜像体积成正比 | 一个 2 GiB 的镜像，每次起容器都要写 2 GiB；水平扩容时最先撞上的是磁盘带宽，不是 CPU |
| 同一镜像的多个实例各存一份 | 一个节点上跑 20 个副本，就多出 20 份完全相同的系统文件 |
| 改动一个小文件要付出整层的代价 | 镜像分层本来是为了复用，展开之后就完全失去了意义 |

答案是把「共享」留在只读部分、「独占」压缩到最小：**镜像的每一层在节点上只解出一份，所有容器共用；再给每个容器叠一层属于它自己的可写层。** 这就是联合挂载（union mount）在容器场景里的用途。它带来的是一个可写视图，不是一个可写副本。

## 2. 快照器：把「层」与本地文件系统对接的那一层

镜像层（远端 blob）与可写层（本地目录）是两套东西，中间需要有人翻译。容器运行时把这件事交给一个可替换的组件——**快照器（snapshotter）**，它的职责只有一句：**把「若干只读层 + 一个可写层」组织成一个目录，交给运行时当作根文件系统挂给容器。**

| 概念 | 含义 |
| --- | --- |
| 快照（snapshot） | 一份可被挂载的层视图，有唯一键（key）与一个可选的父快照 |
| 已提交快照（committed） | 只读，没有可写层；镜像的每一层对应一个 |
| 活动快照（active） | 有可写层，容器正在用它；同一个父快照下可以有多个活动快照 |
| 父子链 | 容器的可写层以「镜像最上面那一层」为父；链的末端才是容器能写的那一层 |

这个组件的实现是可选的，常见几种：overlayfs、native（直接把层复制出来，退化成上面第 1 节的做法）、btrfs、zfs、块设备式（device mapper 一类），以及为「按需拉取」服务的 stargz、nydus、SOCI 等。

「按需拉取」这一类值得单独交代代价，因为它们的宣传口径通常只讲启动变快。它们**不是镜像格式的标准能力**——镜像规范与分发规范里都没有「懒加载」这个原语，相关提案至今没有合并，标准层对分发协议只使用「应当支持范围请求」这种非强制的措辞。也就是说：**这一层完全建立在「节点上装了对应的快照器插件」加上「镜像/索引里有该插件的私有约定」之上**，因此有四个绕不开的约束：

| 约束 | 后果 |
| --- | --- |
| 需要节点侧装插件并在**节点启动时**配置好 | 属于节点基线，不是应用能声明的属性；有的实现还要求它作用于节点上的**全部**容器，否则连沙箱容器都找不到镜像 |
| 镜像或索引必须按该插件的约定生成 | 构建流程要改；不同插件之间不通用，选型即锁定 |
| 依赖仓库支持范围请求或「关联制品」查询 | 标准只把它写成「应当支持」，部分仓库根本不支持关联制品；换仓库可能整套失效 |
| 有的实现会**改动镜像本身**（在清单上加注解或加关联制品） | 镜像摘要因此变化，需要重新推送；而任何针对原始镜像做过的签名都会**失效** |

还有一条与收益直接相关的：这类实现通常对**较小的层**不做处理（例如小于某个默认阈值就不生成索引），所以**小镜像上用它是没有收益的**。选型时要把「镜像有多大、仓库支不支持、构建链能不能改、签名怎么续」四件事一起算，而不是只看启动时间。

有两件事必须记牢，因为它们是这个层次最容易搞错的地方：

- **快照器是运行时级别的全局选择，不是 Pod 级别的属性。** Pod 里写不出「这个容器用哪种快照器」，它由节点上的运行时配置决定；因此同一份镜像在不同节点上可以有完全不同的落地方式与行为差异。
- **换快照器不是换开关，是换代价模型。** 从 overlayfs 换成把层完整复制的实现，会同时改变磁盘占用、启动时间与去重效果；它属于节点基线的变更，不属于应用配置。

## 3. overlayfs 怎么做到「共享只读 + 独占可写」

主流做法是基于 overlayfs 的联合挂载——**运行时文档给出的默认值就是它**（完整复制型的 `native` 不是默认值），具体用哪一个仍以现场配置为准。它的模型只有四个概念：

| 概念 | 作用 |
| --- | --- |
| `lowerdir` | 一个或多个只读目录（用 `:` 分隔），越靠左越上层 |
| `upperdir` | 一个可写目录，容器里所有写操作最终落在它里面 |
| `workdir` | overlayfs 自己用的中转目录，必须与 `upperdir` 在同一个文件系统上 |
| `merged` | 挂给容器的那棵「合成」目录树 |

读的时候从最上层往下找，找到就用；目录做合并（下层与上层的同名目录内容叠加显示），普通文件则被上层完全遮住。写的时候，如果目标文件只在只读层里，overlayfs 会先把整份复制到上层再改——这一步叫 **copy-up（升层复制）**。

| 容器里的动作 | overlayfs 怎么做 | 代价落在哪 |
| --- | --- | --- |
| 读只读层里的文件 | 直接从下层读 | 无额外代价 |
| 改只读层里的文件 | copy-up 整份到可写层，再改 | 写放大：改一个字节要复制整个文件；首次写入出现延迟尖峰 |
| 只改元数据（权限、时间、属主） | 默认同样触发整份 copy-up；开启 metacopy 时只复制元数据 | 默认行为下，`chmod` 一个 1 GiB 的文件要复制 1 GiB |
| 新建文件、写文件 | 直接写可写层 | 消耗可写层空间 |
| 删除只读层里的文件 | 在上层放一个白障条目遮住它 | 下层文件仍在，磁盘不释放 |
| 删除目录、要求目录「看起来是空的」 | 上层放一个不透明目录标记 | 同上 |

「白障」在磁盘上有两种等价写法，判据不同、看到的形态也不同：一种是**设备号为零的字符设备**，另一种是**零长度普通文件加一个扩展属性**；「不透明」则是给目录加一个值为 `y` 的扩展属性。以前者为例，在挂载点里 `ls` 会看到一个字符设备，而它并不是你的文件。另外，以非特权方式挂载时扩展属性的命名空间会从受信任前缀变成用户前缀——**判断「这里到底有没有白障」，不能只按受信任前缀去找属性**。

## 4. copy-up 的连锁反应，比「慢一点」严重

写放大只是第一层。因为「文件的位置在写入前后发生了变化」，下面这些依赖稳定身份或原子语义的行为会一起变：

1. **设备号与 inode 会变。** 同一路径的文件在 copy-up 前后 `st_dev`/`st_ino` 不同（除非同一文件系统内且启用了 xino 一类机制）。依赖 inode 做标识的缓存、去重、增量备份会把同一个文件当成两个。
2. **跨层硬链接会断。** 一个文件与它在只读层里的硬链接伙伴在 copy-up 后不再指向同一个 inode；除非打开 index 一类特性。
3. **重命名目录会失败。** 目录在层间「合并」而成，无法用一次原子改名表达，直接返回 `EXDEV`；要让它在部分场景下可用，需要额外的开关，而这个开关本身有前提。
4. **`df` 的读数来自承载可写层的那个文件系统**，不是「只读层 + 可写层」的总和。容器里 `df` 看到的可用空间，与「这个容器还能写多少」不是同一个问题。
5. **执行中的只读层文件不会报 `ETXTBSY`。** 覆盖一个正在被执行的程序，在普通文件系统上会被拒绝，在联合挂载上不一定——升级二进制时的「先删再写」不总能得到保护。

这一节的完整判据（白障的两种磁盘表示、`redirect_dir`/`index`/`metacopy`/`xino` 这些开关的默认值、挂载期间不许改底层的规定）属于文件系统本身的性质，在存储那一章的《容量边界、挂载与可见性》里展开；在这条线上只需要记住一句：**容器看到的根文件系统是一个由多层拼出来的视图，它的读写代价与普通目录不是一个量级。**

## 5. 节点上的三本账

「这个容器占了多少磁盘」之所以经常算不清，是因为三部分分别记账、却可能落在同一块盘上：

| 账本 | 内容 | 归属 | 谁释放 |
| --- | --- | --- | --- |
| 只读层 | 镜像的每一层，解压落盘 | 节点级，跨容器共享 | 运行时按引用回收；没有镜像引用它之后才消失 |
| 可写层 | 容器运行期间的所有写，含被白障遮住的下层文件 | 容器级，独占 | 容器被删除时释放；被打开的文件会延后释放 |
| 卷与日志 | 挂进来的存储、标准输出落成的日志文件 | 各自独立 | 卷按存储策略回收，日志按轮转策略回收 |

前两本由容器运行时管理，日志由 `kubelet` 管理。它们**是否共用同一份文件系统水位，取决于节点上的目录布局**——同盘则互相挤占，分盘则各自独立水位。这是「磁盘满了导致容器被驱逐」这类现象里最需要先确认的一件事：**先确认是哪一本账在涨，再谈清理哪一份文件。**

落到具体路径上，运行时会把它管的内容分成两处：**内容存储**里放的是与仓库里字节相同的 blob，**文件名就是它们的摘要**（因此是压缩形态）；**快照目录**里放的是每层解压出来的目录树。两者之间有两条容易搞混的关系：

- 快照的标识**既不是压缩摘要、也不是解压后归档的摘要**，而是「这一层叠加到前一层之后」算出来的结果；
- 同一份内容被多个镜像引用时，blob 只存一份，但**每一层解压出来的目录树通常仍各占一份**——所以「去重」主要发生在内容存储那一侧。

运行时会在这类 blob 上记一个「解压后摘要是多少」的标签，这是核对「这一层解压后到底是哪一份」的入口。而**清单里没有任何「镜像总大小」字段**，所以每个工具报的镜像体积都是它自己求和的结果。

这三块账**在用工具查的时候口径还不一样**，这正是「节点磁盘占用怎么算都对不上」的根源：

| 你查的东西 | 它量的是什么 | 漏掉了什么 |
| --- | --- | --- |
| 镜像列表里的体积 | 清单里各层描述符的大小之和，即**压缩后**的体积 | 与磁盘占用无关——那是仓库侧的大小 |
| 运行时的文件系统用量接口 | 快照目录的**未压缩**占用与 inode 数 | **不含内容存储那一块**（实现里明确留着「尚未统计内容存储」的待办） |
| 直接对运行时的根目录做磁盘统计 | 快照 + 内容存储 + 元数据库，三块之和 | 这才是真正吃盘的量 |

所以「镜像列表说只有 2 GiB，磁盘却涨了 8 GiB」不是 bug，而是三个口径本来就不同；做容量规划要取的是**最后一行**。

同时有一条官方禁令必须遵守：运行时的根目录与运行目录**属于实现细节，不要去动里面的文件**——外部程序读取或监听这些目录，会让运行时在清理资源时遇到「设备忙」与失效的文件句柄。清理要走受控入口，不要手工删目录。

## 6. 抽象在哪里漏水

1. **「容器的磁盘占用」不是一个数。** 只读层共享、可写层独占、卷另有账本，三者的释放条件都不同。问「删了容器能腾出多少」得到的答案，通常远小于「它写了多少」。
2. **删除不等于释放。** 白障遮住的下层文件仍占空间；被删除但被进程打开的文件仍占空间；镜像层在还有别的标签或容器引用它时仍占空间。看到「删了文件磁盘没降」时，这三个原因要分开查。
3. **可写层会随容器消失。** 这是容器与虚拟机的关键差别之一：不落进卷、不写出到远端的写入，在容器重建后不存在。可写层的磁盘占用看起来很省，代价是它不可持久。
4. **身份不稳定。** copy-up 之后 inode 与设备号会变，所以任何「按 inode 记忆」的外部工具都会在联合挂载上得到不稳定的结果。
5. **快照器的选择会改变行为。** 同一份镜像在 overlayfs 与完整复制型快照器上，磁盘占用、首次写延迟、inode 稳定性都不同；跨节点比较「同一个镜像的启动时间与磁盘占用」时，先确认两边的快照器一致。
6. **层的共享是节点内的，不是集群内的。** 每个节点各存一份自己的层，跨节点没有任何共享；「镜像只在仓库里存一份」与「每个节点各存一份」同时成立。

## 常见误解

| 常见说法 | 事实 |
| --- | --- |
| 「容器删了，磁盘占用就还回来了」 | 可写层会释放，但只读层只要还被别的镜像或容器引用就仍然占着；白障遮住的下层内容也不会因此消失 |
| 「`df` 显示的可用空间就是容器还能写多少」 | 读数是承载可写层的文件系统水位，与容器的写入量、与节点的其它账本都不等价 |
| 「改一个小文件只消耗一个小文件的空间」 | 默认会 copy-up 整份文件到可写层，写放大与文件大小成正比，与改动量无关 |
| 「不同节点的同一镜像行为应当完全一致」 | 快照器是节点级选择；实现不同则磁盘占用、首次写延迟、inode 稳定性都不同 |
| 「容器里的文件系统就是镜像解压出来的那份」 | 是「只读层 + 可写层」的合成视图，写入落在可写层，只读层本身不被修改 |
| 「在容器里 `rm` 掉大文件能腾空间」 | 只加了一个白障条目，下层内容仍在；空间要等容器与只读层的引用都消失才可能释放 |
| 「换快照器只是换了个性能选项」 | 它同时改变去重效果、磁盘占用与身份稳定性，属于节点基线变更 |

## 要点自测

**问：为什么要引入「联合挂载」这一层？不用它会怎样？**

答：不用它就得把镜像层完整展开到每个容器自己的目录里，于是启动成本与镜像体积成正比、同一镜像的多个实例各存一份、改一个小文件也要付出整层的代价。联合挂载把只读部分做成节点内共享、把可写部分压缩成一层专属目录，同时解决了这三件事。

**问：copy-up 在什么情况下被触发，代价是什么？**

答：往只读层里的文件写入、改它的元数据（权限、属主、时间）、以及为它建立硬链接，都会触发；默认整份复制到可写层，因此代价与**文件大小**成正比，而与改动量无关。开启只复制元数据的模式可以避免元数据修改的整份复制，但那是另一个前提下的行为。

**问：容器里删除一个只读层里的文件，磁盘为什么没有释放？**

答：删除在联合挂载上表现为在上层放一个白障条目，用来遮住下层同名文件；下层文件本身仍在只读层里，而只读层是跨容器共享的，只有当引用它的镜像与容器都消失后才可能被回收。

**问：为什么在联合挂载上用 inode 做标识不可靠？**

答：文件在被写入前位于只读层、写入后被复制到可写层，前后处于不同的文件系统（或不同的层），因此设备号与 inode 会改变。任何按 inode 记忆的缓存、去重或增量备份都会把同一个路径当成两个不同的文件。

**问：节点磁盘满了，怎么判断该清哪一本账？**

答：先把三本账分开：只读层（运行时管理、节点内共享）、可写层（容器独占、随容器删除释放）、日志与卷（由 `kubelet` 与存储策略管理）。这三者是否落在同一个文件系统上，决定了它们是否互相挤占——同盘才需要放在一起看水位，分盘则应各自看各自的水位。确认是哪一本在涨，再去谈清理动作。

**第一反应不要做什么**：不要用「删了容器」当作释放磁盘的手段，先确认占着空间的是可写层还是共享的只读层；不要把容器内 `df` 的读数当作这个容器的额度；不要在排查启动变慢时跳过 copy-up——首次写入大文件的延迟尖峰经常被误认成应用初始化慢。
