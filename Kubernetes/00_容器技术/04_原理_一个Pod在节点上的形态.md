# 一个 Pod 在节点上的形态

## 1. 「一组容器」这个说法本身就不够

Pod 的语义是「一组共享某些上下文的容器」。把这句描述直接当成实现去做，会同时撞上三件事：

| 撞上的事 | 具体表现 |
| --- | --- |
| 共享的上下文由谁建立、由谁持有 | 命名空间没有独立的生命周期，必须有一个进程一直拿着它 |
| 文件系统默认各自独立 | 容器各有自己的根文件系统，卷要「同时」出现在几个容器里，靠的不是共享文件系统 |
| 生命周期是两级的 | 容器会重启，Pod 会被重建；两者不是一回事，退出与重启的粒度必须分开定义 |

第 1 件靠沙箱容器解决（前一篇已述），第 2 件靠节点侧的绑定挂载解决，第 3 件靠重启策略与两级对象的划分解决。这一篇把这三件事在**节点侧的真实形态**讲清楚——因为 `kubectl` 看到的是抽象，节点上看到的是进程、挂载与文件。

## 2. 共享的是哪几样，怎么控制

同一个 Pod 里的容器并不是「共享一切」。逐项看：

| 上下文 | 默认 | 控制方式 | 共享的后果 |
| --- | --- | --- | --- |
| 网络命名空间 | **总是共享** | 不可关闭 | 同一 Pod 的容器共用 IP 与端口空间，互相通过 `localhost` 访问；端口冲突发生在 Pod 内部 |
| IPC 命名空间 | **总是共享** | 不可关闭 | 可以用 System V IPC 与 POSIX 消息队列通信 |
| UTS 命名空间 | **总是共享** | 不可关闭 | 主机名是全 Pod 一个 |
| PID 命名空间 | **默认不共享** | Pod 级开关 | 打开后容器之间互相看得见对方的进程，也就能互相发信号 |
| 挂载命名空间 | **默认不共享** | 卷与卷挂载 | 除卷之外，容器之间看不到对方的任何文件 |
| 用户命名空间 | **默认映射到宿主** | Pod 级开关 | 打开后容器里的 root 与宿主上的 root 不再等同 |
| cgroup | **每个容器各自一份** | 资源字段 | 限制配在容器上，Pod 层还有一层父 cgroup 用于汇总与判定 |

有三处结论值得单独记住：

- **共享是「命名空间级」的，不是「文件级」的。** Pod 的内容器共享的是网络、IPC、主机名这些**系统级上下文**，不是彼此的文件系统。看到「同一个 Pod 里的两个容器」时，默认假设应当是「它们只有网络是通的」。
- **PID 可见性默认关闭，是一个安全与兼容上的取舍。** 默认情况下容器看不到 Pod 内别的进程，因此诊断命令、进程管理工具、以及「一个容器负责收尸」的模式都拿不到别的容器；打开它换来的是便利，代价是任何一个容器都能向同 Pod 的其它进程发信号。
- **打开用户命名空间映射会改变「容器内 root」的含义。** 默认情形下容器内的 root 就是宿主机上的 root（只是被若干机制约束住），这是「提权面」的根源；开启映射之后，容器内的 root 在宿主上只是一个普通 ID，代价是文件属主映射、挂载能力与一部分镜像兼容性问题会跟着出现。

## 3. 卷是怎么同时出现在几个容器里的

卷在节点侧的实现不是「让容器共享文件系统」，而是：**由 `kubelet` 先把卷准备好、挂到节点上的某个位置，再让运行时把这个位置以绑定挂载的方式接进每个用到它的容器。** 于是：

| 现象 | 解释 |
| --- | --- |
| 两个容器写同一个卷能看到对方的数据 | 它们各自挂的是节点上同一个目录；共享发生在宿主侧，不在容器之间 |
| 卷的生命周期比容器长 | 卷由 Pod 管理，容器重启不重建卷；Pod 被重建后，只有持久卷才保留数据 |
| 容器里挂载点会「盖住」镜像里的同名目录 | 挂载是覆盖式的：挂上去之后，镜像里原本在该路径的内容不可见 |
| 只读挂载是真的只读 | 由挂载标志实现，容器内的 root 也写不进去——这与文件权限是两套机制 |

一个容易踩的边界是**挂载的粒度**：把卷挂在某个目录上，整个目录被替换；只想替换目录里的一个文件，需要额外的子路径机制，而它的更新语义与整目录挂载不同（卷内容更新时不会跟着变）。这类差异属于「挂载是挂载，不是同步」。

## 4. 两级生命周期：容器重启与 Pod 重建

节点侧真正发生的事情只有两件：**删掉一个容器再建一个**，或者**把整个沙箱连同所有容器拆掉重建**。所有关于重启的说法都要落到这两件上：

| 情况 | 实际发生的事 | 保留了什么 | 失去了什么 |
| --- | --- | --- | --- |
| 容器退出且策略允许重启 | 只重建该容器 | 沙箱、Pod IP、卷、其他容器 | 该容器的可写层、内存状态 |
| 容器退出且策略不允许重启 | 容器留在已退出状态 | 沙箱（直到 Pod 被删） | 同上，且不会自愈 |
| 沙箱被杀 | 整个 Pod 的容器全部重建 | 持久卷 | Pod IP 可能变化、所有可写层 |
| Pod 被删除 | 沙箱与容器全部清理 | 持久卷、日志文件可能仍在 | 全部运行时状态 |

两个由此派生的判据：

- **`restartPolicy` 是节点侧行为，不是 API 语义。** 它决定的是「容器退出后 `kubelet` 要不要再建一个」；因此「Pod 在运行」并不等于「里面的容器从没失败过」，容器失败次数才是有意义的信号。
- **退避是必然的。** 反复失败时会看到重启间隔逐渐拉长，这是节点侧为避免把一个持续失败的应用变成资源风暴而做的限制；「等一会儿它自己就好了」在退避期间是假象。

初始化容器与边车容器在节点侧其实是**同一类对象的两种用法**。初始化容器按声明顺序依次执行，每一个都必须成功退出，之后才会创建业务容器。边车容器在实现上是初始化容器的一个特例——它写在初始化容器列表里，但带**容器级的「总是重启」策略**；因此它可以与业务容器并行长期运行，也能被单独重启（这个能力自 v1.29 起默认启用、v1.33 起稳定）。

终止时的顺序值得单独记住：`kubelet` 会**推迟**终止边车，直到业务容器完全停止，然后按声明顺序的**相反顺序**逐个关闭；如果宽限期用尽，边车会先收到终止信号、再被强杀。所以**边车在 Pod 终止时以非 0 退出码结束是正常的**，外部工具一般应当忽略它——把它当成故障信号是误判。

## 5. 日志与可写层：容器往外写的两条路

容器里产生的数据只有两条出路，节点侧各自有归属：

| 出路 | 落在哪 | 谁管理 | 容器重建后 |
| --- | --- | --- | --- |
| 标准输出与标准错误 | 节点的日志文件 | `kubelet`（按大小与数量轮转） | 仍在，可按上一次的日志查看 |
| 写进容器文件系统 | 该容器的可写层 | 容器运行时 | 消失 |
| 写进卷 | 卷的落点 | 存储策略 | 按卷的回收策略 |

这条表解释了两类高频现象：应用把日志写进容器文件系统，于是日志随容器重建消失、还悄悄吃可写层空间；以及日志写在标准输出上，于是日志文件由 `kubelet` 轮转，轮转策略配小了会丢历史。

日志的落点由 `kubelet` 的配置决定：默认根目录是 `/var/log/pods`，其下按「命名空间、Pod 名、Pod 唯一标识」拼出目录，再按容器名与实例序号拼出文件。这里有一条最常被忽视的限制——**只能取到最新的那一个日志文件**：轮转出来的更早文件仍然躺在节点上，但通过集群侧的日志入口读不到。所以「日志缺了一段」的第一判据，是轮转上限与采集端是否已经把内容取走，而不是采集链路丢数据。

## 6. 抽象在哪里漏水

1. **共享是双向的。** 同 Pod 的容器共享网络与 IPC，因此一个容器改了共享上下文的属性（比如端口占用、共享内存段）会影响整个 Pod；「只是我这个容器改了设置」在共享命名空间里不成立。
2. **不共享也是默认的。** 除卷之外，Pod 内容器互相看不见对方的文件。把「同一个 Pod」当成「同一台机器」是错的，`localhost` 通只代表网络共享。
3. **重启的粒度决定影响面。** 容器级重启保留 Pod IP 与卷；沙箱级重建会让整个 Pod 的容器一起重来。分清是哪一级，才知道「重启一次」的代价。
4. **退出不等于结束。** 退出后是否重来由策略决定，因此「容器退出了」与「Pod 失败了」是两个结论；反过来，「Pod 在运行」也不能证明里面的容器一直健康。
5. **挂载会覆盖，不会合并。** 卷挂到某个路径上，镜像里该路径的内容就被遮住；这与联合挂载在同一路径下的「上下层合并显示」是两套机制，不要混用直觉。
6. **容器内看到的整机视图不属于这个容器。** 共享内核意味着内存、CPU 总数、负载这类读数仍是宿主口径；这个容器能用多少属于 cgroup 的账本。这一点在宿主侧的原理里已经讲透，但在 Pod 里做容量判断时最容易被忘记。

## 常见误解

| 常见说法 | 事实 |
| --- | --- |
| 「同一个 Pod 里的容器共享文件系统」 | 除卷之外不共享；共享的是网络、IPC 与主机名这些系统级上下文 |
| 「Pod 里的容器能看到彼此的进程」 | 默认看不到；要打开 Pod 级的 PID 共享开关，代价是容器之间可以互相发信号 |
| 「容器里 root 就是宿主 root，所以容器不安全」 | 默认映射下确实等同宿主 root，因此需要靠能力收敛、系统调用过滤与强制访问控制约束；开启用户命名空间映射能让这两者分离 |
| 「Pod 重启了，所以 IP 变了」 | IP 属于沙箱；只有沙箱被重建时才会变，容器级重启不影响 Pod IP |
| 「把卷挂在 `/etc/app` 上就只覆盖这一个目录」 | 挂载是覆盖式的，该路径下镜像里的内容会全部不可见；只替换单个文件要用子路径机制，而它不跟随源更新 |
| 「日志写在容器里最方便」 | 写进可写层的日志随容器重建消失并占用可写层空间；写进标准输出才由节点统一轮转与采集 |
| 「容器退出了，Pod 就结束了」 | 是否重建由重启策略决定；退出与失败是两件事 |

## 要点自测

**问：同一个 Pod 里的容器到底共享什么？**

答：**总是**共享网络、IPC 与 UTS 命名空间；PID 命名空间默认不共享，可以打开；挂载命名空间默认不共享，卷是通过节点侧的绑定挂载分别接进各容器的；用户命名空间默认映射到宿主，可以打开；cgroup 是每个容器各自一份，Pod 层另有一级父 cgroup 用于汇总。

**问：为什么「Pod 内共享文件系统」是错的？**

答：共享发生在命名空间层面，而挂载命名空间默认不共享；卷能同时出现在多个容器里，是因为 `kubelet` 把宿主上的同一个位置分别绑定挂载进了各容器，共享点在宿主侧，不在容器之间。除卷之外，容器彼此完全看不到对方的文件。

**问：容器重启和 Pod 重建的区别是什么？**

答：容器重启是删掉一个容器再建一个，沙箱、Pod IP、卷与其他容器都不受影响，失去的是该容器的可写层与内存状态。Pod 重建是沙箱连同所有容器一起拆掉重来，Pod IP 可能变化，所有可写层消失，只有持久卷保留数据。

**问：打开 Pod 级的 PID 共享，会付出什么代价？**

答：同一个 Pod 的容器之间会互相看见对方的所有进程，也就能互相发信号，因此任何一个容器被攻破都会直接威胁同 Pod 的其它容器；同时进程管理类的工具与「一个容器负责收尸」的模式才成为可能。这是一个便利与爆炸半径之间的取舍。

**问：应用把日志写进容器文件系统，会同时出哪两件事？**

答：日志随容器重建而消失（排障时拿不到历史），并且持续占用该容器的可写层空间，进而计入节点磁盘水位。写进标准输出的日志由节点统一落到文件并按策略轮转，才是可被采集与追溯的那一条路。

**问：容器里的 `nproc` 报的是这台机器能给我用的核数吗？**

答：不是。共享内核意味着容器内看到的整机读数仍是宿主口径；这个容器能用多少属于 cgroup 的账本。做容量判断必须读节点侧的 cgroup 接口，不能读容器内的整机视图。

**第一反应不要做什么**：不要把「同一个 Pod」当作「同一台机器」——同 Pod 只保证网络共享；不要用 Pod 的状态代替容器的状态来判断应用是否健康；不要在排查时先假设容器之间能互相看见文件或进程，先把共享的那几项点清楚。
