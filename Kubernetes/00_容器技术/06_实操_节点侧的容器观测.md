# 节点侧的容器观测

## 1. 一个问题一把工具

集群侧的工具只能告诉你「对象是什么状态」；节点侧的工具才告诉你「机器上实际有什么」。两边用的不是同一套标识，所以第一步永远是建立对应关系。

| 想知道什么 | 用什么 | 关键字段 / 关键点 |
| --- | --- | --- |
| 这台节点用哪个运行时、socket 在哪 | `kubelet` 的启动参数与配置、运行时的服务状态 | 运行时端点决定后面用哪套客户端 |
| 集群里的某个 Pod 在节点上对应哪些容器 | CRI 客户端的沙箱与容器列表，按名称与命名空间过滤 | 沙箱名称通常带 Pod 名与命名空间，容器名里带容器名 |
| 某个容器为什么退出 | 容器的详细信息、该容器的日志 | 退出码与退出原因要一起看；退出原因是判据，退出码只是线索 |
| 容器里此刻有什么进程 | 在容器里执行命令（走 CRI 的 exec 通道） | 与 `kubectl exec` 走同一条通道，差别只在绕过 API 层 |
| 节点上有没有这个镜像、是哪一份 | 镜像列表与单个镜像的详细信息 | 摘要字段是判据；`IMAGE ID` 与清单摘要不是同一个值 |
| 镜像与容器各占了多少磁盘 | 运行时的文件系统用量接口、容器的资源统计 | 单位与「哪一本账」必须同时说明 |
| 运行时自己在抱怨什么 | 运行时的服务日志 | 拉取、解压、创建容器失败的原始原因在这里 |
| 沙箱持有的命名空间在哪 | 沙箱的详细信息 | 排查「Pod 内共享了什么」时看它，不看业务容器 |
| 容器被限流、被 OOM 的记录 | cgroup 接口文件（内核接口，不是命令） | 接口文件是只读观测入口，比容器内的整机视图可靠 |

两类对象的区别要在动手前分清：**CRI 客户端是命令**，它需要在节点上执行、要能访问运行时的 socket；**cgroup 与日志目录下的文件是内核或组件写出的接口文件**，直接读即可，不需要额外工具。把两者混着用，最容易出现的错误是「在容器里读接口文件」——读到的往往是宿主的账本。

还有一条决定「用哪把工具」的硬依据：**运行时自带客户端与 CRI 客户端的稳定性等级不同**。上游把运行时自带客户端明确定义为**不受项目支持、次要版本就可能破坏性变更**，而它自己的 gRPC 接口、运行时 shim 接口与 CRI 接口都标为稳定。所以排障时的默认选择是**走 CRI 的那个客户端**（它与 `kubelet` 说的是同一种话，看到的对象与 `kubelet` 认知一致），运行时自带客户端只用来做旁证——用它做写操作会让集群状态与节点事实分家。另外两个能省很多时间的入口：运行时的**弃用项清单**（把当前配置命中的弃用项一次列出来，是跨大版本迁移排查的首选），以及运行时的**容器状态目录**——运行配置与容器标识放在运行目录下的「某命名空间、某容器」两级路径里，是核对「这个对象在运行时侧的身份证」的地方，同样**只读不写**。

## 2. 怎么读这些数字

| 数字 | 是什么 | 单位 | 判据 | 与谁同看 | 转向哪一步 |
| --- | --- | --- | --- | --- | --- |
| 镜像文件系统的用量 | 运行时存放镜像层的那个文件系统被用了多少、还剩多少 | 字节 | 与「高阈值」比，越过就开始回收；越接近满，拉取越可能失败 | 同一文件系统的容器可写层与日志、节点的 inode 使用量 | 磁盘将满：转向回收与驱逐 |
| 容器的可写层用量 | 这个容器自己写出来的那部分 | 字节 | 它是独占的，会随容器删除释放；异常增长通常来自写文件而不是写日志 | 该容器日志文件的大小、挂载进来的卷的用量 | 「删了容器没降」：说明主要占用在共享层，不在它自己身上 |
| 节点文件系统的水位与 inode | 承载容器与日志的那些文件系统 | 百分比 / 计数 | 分「可用字节」与「可用 inode」两个信号：inode 先耗尽时表现为「有空间却创建不了文件」。节点侧有三个文件系统标识——节点主文件系统、镜像文件系统、容器可写层文件系统，后两个是**可选**的，由 `kubelet` 从运行时自动发现，也可能三者指向同一份底层文件系统 | 卷的落点是否在同一文件系统、另外两个标识是否与它同源 | 创建文件失败或水位告警：先分辨是空间还是 inode，再分辨是哪一份文件系统 |
| 日志文件的大小与份数 | 标准输出落成的文件 | 字节 / 个数 | 上限是「单文件上限 × 份数」量级；到顶之后旧内容被丢弃，不是被压缩 | 采集端是否已经把内容取走 | 日志「缺了一段」：区分是轮转丢掉还是采集没上 |
| 容器的退出码与退出原因 | 进程怎么结束的、谁让它结束的 | 整数 / 枚举 | 退出原因优先于退出码：同一退出码可以来自进程自己退出、被信号杀死、被内存限制终止 | 该容器的资源上限、节点的内存水位、上一次的日志 | 重启次数在涨：先定原因，再谈改配置 |
| 沙箱与容器的标识 | 运行时侧的对象 ID 与名称 | 字符串 | ID 是运行时的身份，名称是给人看的；集群侧用后者能找到前者 | 集群侧的 Pod 与容器状态 | 「集群说有、节点上没有」：用名称反查 ID 再核 |
| 当前配置命中了哪些弃用项 | 运行时的弃用项清单命令 | 列表 | 跨大版本迁移排查的首选：能把「键已失效、行为回落到默认值」这类静默问题提前暴露出来 | 运行时的大版本、现有配置文件的键位 | 升级前排查：先清掉命中的弃用项再动版本 |
| 运行时侧的容器身份与运行配置 | 运行目录下「命名空间 / 容器」两级路径里的状态文件（只读） | 文件 | 这是与集群侧对象建立对应关系时的最终凭据 | 集群侧的 Pod 与容器标识 | 两边对不上时：以这里为事实，回头查是谁绕过了接口 |
| 节点对仓库的请求速率 | `kubelet` 向镜像仓库发起请求的限速 | 每秒请求数 / 突发额度 | 文档默认是每秒 5 个、突发 10 个（1.37 口径）；发布时多镜像同时拉取会被它限住 | 本次发布的镜像个数、单节点并发拉取配置 | 拉取排队但网络不忙：转向「限速」而不是「带宽」 |

## 3. 采样纪律与基线卡

节点侧的观测要成立，靠的是**同口径、带时间戳、至少两次、留原始输出**。一次 `df` 不能说明泄漏，两次同口径的读数才能给出斜率。

一个节点该留的容器基线卡，字段固定为：

| 字段 | 取值来源 | 为什么要有 |
| --- | --- | --- |
| 运行时名称与版本 | 运行时的版本接口 | 行为差异的第一来源，跨节点比较前先对齐 |
| 运行时端点与存储路径 | 运行时配置 | 决定镜像与容器落在哪个文件系统上 |
| 快照器 / 根文件系统组织方式 | 运行时配置 | 决定磁盘占用与首次写延迟的量级 |
| 镜像存储与容器存储所在文件系统 | 挂载信息 | 决定哪些账本会互相挤占 |
| 日志目录与轮转配置 | `kubelet` 配置 | 决定日志能留住多久、能占多少 |
| 镜像回收与驱逐阈值 | `kubelet` 配置 | 决定「磁盘开始吃紧」时节点会做什么 |
| 一次典型拉取与启动的耗时 | 同口径多次测量 | 没有这个基线，无法判断「变慢了」 |

只读观测（列表、详情、日志、水位、接口文件）在生产机上也可以做。清理类动作（删容器、删镜像、触发回收）**必须先在非生产环境确认后果**，并且在生产上先记录当前水位与预计释放量，事后再取一次同口径读数作为验收。

## 4. 常见故障与排查方向

### 4.1 Pod 一直停在容器创建阶段

现象：单节点上的某个 Pod 长时间不进入运行状态，节点其他 Pod 正常；集群侧对象的容器状态一直未就绪。

按顺序排查：

1. **先看停在哪一站**：卷没准备好、沙箱没建起来、镜像没拉下来、容器创建失败，报错文本完全不同。先读事件里的原因短语，不要先猜。
2. **沙箱问题**：沙箱镜像是否在节点上、网络插件是否正常、沙箱的日志里有没有分配网络的错误。沙箱失败时不会出现任何业务容器。
3. **镜像问题**：拉取失败的原始原因要到运行时日志里看（鉴权失败、域名解析失败、清单里没有对应平台）。
4. **容器创建失败**：常见原因是卷的挂载、安全上下文里要求的能力或身份、以及运行时找不到指定的运行时档位。

一份合格的回答长这样：**结论**（卡在哪一站）、**依据**（哪条事件、日志里的哪一行）、**边界**（是个例还是该节点全部 Pod）、**动作**（改配置还是修环境）。

### 4.2 节点磁盘告警，Pod 开始被驱逐

现象：节点磁盘水位越过阈值，若干 Pod 被终止并被重新调度；清理后水位下降，但过一段时间再次发生。

按顺序排查：

1. **分清是哪一本账**：镜像文件系统还是承载容器与日志的那个文件系统；两者水位可能一个告警一个健康。
2. **看是哪一类内容在涨**：镜像层总量（与发布频率相关）、可写层（与某个应用写文件相关）、日志（与输出量相关）。
3. **看被驱逐的是哪些 Pod**：`kubelet` **不**按资源保障档位排序，它看的是「用量是否超过该 Pod 自己的 requests」、Pod 优先级、以及用量相对 requests 的比例。所以「先被驱逐的」说明的是用量与 requests 的关系，不是「谁占得多」。
4. **看增长斜率**：两次同口径读数给出每小时增长量，用它反推还能撑多久，这决定了是「先止血」还是「先扩容」。

一份合格的回答长这样：**结论**（哪一本账、谁在涨、还能撑多久）、**依据**（两次读数与差值）、**边界**（只影响本节点还是所有节点）、**动作**（清理哪一类内容、以及防复发的配置改动）。

### 4.3 容器反复重启

现象：某个 Pod 的重启计数持续上升，间隔逐渐变长；应用时好时坏。

按顺序排查：

1. **先取退出原因，再看退出码**：原因能区分「进程自己退出」「被信号杀死」「被内存限制终止」；只看数字会把三类混成一类。
2. **再看最后一次运行的日志**，而不是当前的（当前可能是刚起来的空壳）。
3. **看资源账本**：内存被限制终止时，判据在节点侧的 cgroup 事件计数与内核日志里，不在容器内的整机视图里。
4. **看探针**：如果进程一直活着却被重启，问题在探针的判定条件上；如果进程确实死了，问题在进程本身。
5. **看退避间隔**：间隔在拉长是正常现象，不代表问题在缓解。

一份合格的回答长这样：**结论**（谁杀死了这个进程，或它为什么自己退出）、**依据**（退出原因 + 日志 + 事件计数）、**边界**（该节点所有副本还是单个副本）、**动作**（改限制、改探针还是修应用）。

## 5. 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 在容器里读内存与 CPU 的整机视图来判断这个容器是否吃紧 | 读到的是宿主口径；容器的额度在节点侧的 cgroup 接口里 |
| 用运行时自带的客户端去删除容器来「清理现场」 | 绕过了 CRI，集群侧状态与节点实际脱节；清理应当走受控入口 |
| 只看镜像数量判断磁盘占用 | 层是共享的，数量与空间不同步；要看文件系统用量与共享关系 |
| 把「重启计数高」直接等同于「应用有 bug」 | 退出原因可能来自节点侧的资源终止或探针判定 |
| 只取一次读数就判断泄漏 | 没有斜率就无法区分「本来就大」与「正在涨」 |
| 在生产上直接执行清理动作 | 释放量不可预期，且可能破坏正在运行的容器对镜像的引用；先记录、再预估、再执行、再验收 |
| 用「按标签删镜像」的命令，以为只删这一个标签 | 走 CRI 的客户端按标签删除时，删掉的是这个镜像的**全部标签**（与容器引擎的同名命令行为不同，会先警告再动手） |
| 认为「清理未使用镜像」会把沙箱镜像也清掉 | 该操作会跳过被运行时「钉住」的镜像，沙箱镜像正是被钉住的那一个；反过来，看到它不在清理范围里不代表清理失败 |
| 手工去运行时的根目录里删文件「腾空间」 | 官方明确：这些目录是实现细节，外部读取或监听都会导致运行时在清理资源时遇到设备忙与失效句柄；清理必须走受控入口 |
| 拿不同节点的读数直接比较 | 运行时、快照器、存储路径与阈值不同时，两个数不可比 |

## 6. 要点自测

**问：为什么节点侧的观测不可省略，集群侧的对象状态不够用？**

答：集群侧看到的是 `kubelet` 上报的结论，节点上还有已退出未清理的容器、被删对象留下的沙箱、以及实际占用的磁盘。任何涉及「机器上还剩什么、占用多少、谁在写」的问题，都必须在节点侧取证。

**问：一个「看起来一样」的镜像，怎么确认两台节点用的是同一份？**

答：比清单摘要，而不是比标签或镜像 ID。标签可以在仓库端被重推；运行时列表里的镜像标识是配置的摘要，与按清单摘要固定版本用的是不同的值。

**问：节点报告磁盘可用空间还有很多，却创建不了新文件，最可能是什么？**

答：可用 inode 耗尽。空间与 inode 是两个独立信号，小文件极多的场景（大量日志分片、大量层文件）会先撞 inode。判断依据是同时读可用字节与可用 inode 两个数。

**问：容器反复重启时，为什么先看退出原因而不是退出码？**

答：退出码只是一个数字，同一个数字可以来自进程主动退出、被信号杀死或被内存限制终止；退出原因把这个区分直接给出来，它才决定下一步是查应用、查节点资源还是查探针。

**问：一次 `df` 能说明磁盘在泄漏吗？**

答：不能。它只给出一个时刻的值。要判断泄漏必须有同口径的至少两次读数并算出斜率；「本来就大」与「正在涨」在单点上是同一个现象。

**第一反应不要做什么**：不要在容器内判断这个容器的资源额度；不要用运行时自带客户端去删除对象「清干净」；不要在没取到两次读数之前就下结论说泄漏；也不要在生产机上直接执行清理动作而不先记录水位与预估释放量。

## 参考文档

- Kubernetes 官方文档中关于节点排障的章节：节点上可用的诊断入口、容器运行时相关的排查步骤、容器日志的定位方式。
- CRI 客户端（`crictl`）的官方使用说明与其配置文件：可用子命令、默认端点、以及与 `kubectl` 在视角上的差别。
- 具体运行时的官方文档：命令行客户端的子命令与状态目录、服务日志的位置、文件系统用量接口。
- 内核与 `kubelet` 写出的接口文件：cgroup 的计量与事件计数、日志目录下的文件与轮转命名；字段口径以现场版本为准。
- 各类阈值与路径（回收阈值、驱逐阈值、日志上限、运行时端点）**以现场配置为准**，文档给出的是默认值而不是你的集群的值。
