# 发布与副本的现场观测

## 1. 问题与工具的对应关系

工作负载的观测有一个特点：**同一件事要同时看三个层次的对象**。期望写在发布对象或集合对象上，中转载在修订对象上，事实落在实例上。只看其中一层，得到的结论往往与实际相反——例如只看发布对象的副本数会以为发布正常，而实例其实一个都没就绪。

下面涉及的查询都属于只读观测，在生产集群上也可以做。

| 要回答的问题 | 用哪把命令 | 落在哪一层 |
| --- | --- | --- |
| 期望是什么、由谁写的 | `kubectl get <类型> <名字> -o yaml --show-managed-fields` | 期望态与字段归属 |
| 控制器是否看过最新期望 | `kubectl get <类型> <名字> -o jsonpath='{.metadata.generation}{" "}{.status.observedGeneration}{"\n"}'` | 控制器的处理进度 |
| 这一次模板改动产生了几个修订 | `kubectl get rs -l <选择器> -o custom-columns=NAME:.metadata.name,HASH:.metadata.labels.pod-template-hash,CREATED:.metadata.creationTimestamp` | 修订层 |
| 每个修订现在有多少实例 | `kubectl get pods -l <选择器> -o custom-columns=NAME:.metadata.name,HASH:.metadata.labels.pod-template-hash,NODE:.spec.nodeName,PHASE:.status.phase` | 修订层的实例分布 |
| 实例是否就绪、卡在哪一步 | `kubectl describe pod <实例>`；`kubectl get pod <实例> -o jsonpath='{.status.conditions}{"\n"}{.status.containerStatuses[*].state}{"\n"}'` | 实例层 |
| 数量账目分别是多少 | `kubectl get deploy <名字> -o jsonpath='{.status.replicas}{" "}{.status.readyReplicas}{" "}{.status.availableReplicas}{" "}{.status.updatedReplicas}{" "}{.status.unavailableReplicas}{" "}{.status.terminatingReplicas}{"\n"}'` | 期望态的状态区 |
| 发布是否已经走完 | `kubectl rollout status deploy/<名字> --timeout=30s`；`kubectl get deploy <名字> -o jsonpath='{range .status.conditions[*]}{.type}={.status} {.reason}{"\n"}{end}'` | 修订层与状态区 |
| 之前的修订还在不在、能不能回退 | `kubectl rollout history deploy/<名字>` | 修订层 |
| 值为什么又变回去了 | `kubectl get <类型> <名字> -o jsonpath='{range .metadata.managedFields[*]}{.manager}{"\t"}{.operation}{"\t"}{.time}{"\n"}{end}'`；`kubectl get <类型> <名字> -o jsonpath='{.metadata.annotations.kubectl\.kubernetes\.io/last-applied-configuration}'` | 字段归属 |
| 实例为什么反复重启 | `kubectl get pod <实例> -o jsonpath='{.status.containerStatuses[*].restartCount}{" "}{.status.containerStatuses[*].state}{"\n"}'`；`kubectl logs <实例> --previous` | 实例层 |
| 任务为什么没成功 | `kubectl get job <名字> -o jsonpath='{.status.succeeded}{" "}{.status.failed}{" "}{.status.active}{"\n"}{range .status.conditions[*]}{.type}={.status} {.reason}{"\n"}{end}'` | 任务层 |
| 这条路径为什么写入被拒 | `kubectl auth can-i <动词> <资源> -n <命名空间> --as=<身份>`；`kubectl create --dry-run=server -f x.yaml -v=6` | 写入路径 |
| 一段时间内的趋势 | 采集器导出的时间序列（例如 `kube_deployment_status_replicas_unavailable`），按同一标签与窗口聚合 | 采集侧 |

**指标来源要说清。** 把对象状态导出成时间序列需要一个采集器（例如 kube-state-metrics），指标名称与标签由采集器决定；控制面自身的队列指标由控制面组件暴露，名称与标签随版本变化。因此引用指标时必须写成"以某采集器为例"，并声明**数值仅示意、不代表你的环境**。

## 2. 这些字段与指标的读法

| 看什么 | 是什么 | 单位 | 判据 | 与谁同看 | 看到它转向哪一步 |
| --- | --- | --- | --- | --- | --- |
| `metadata.generation` 与 `status.observedGeneration` | 期望被改动的次数与控制器处理到的次数 | 整数 | 两者相等才说明控制器已经看过最新期望 | 条件与副本账目 | 长期不相等 → 先查控制器是否在运行、队列是否积压 |
| `status.replicas`（认领数） | 控制器认领的实例数量，含未就绪的 | 计数 | 与 `spec.replicas` 相等只说明数量补齐 | `status.readyReplicas` 与 `status.availableReplicas` | 小于期望且没有错误 → 先看被拒绝的写入与实例状态 |
| `status.readyReplicas`（就绪数） | 通过了就绪判定的实例数 | 计数 | 与认领数的差值就是尚未就绪的实例 | 实例的等待原因与探针声明 | 差值长期不变 → 取实例的等待原因，不要先改参数 |
| `status.availableReplicas`（可用数） | 已计入可用下限的实例数 | 计数 | 就绪之后还要经过最小就绪时长 | `spec.minReadySeconds` 与发布耗时 | 可用数长期低于期望而认领数正常 → 看最小就绪时长与终止中的实例 |
| `status.updatedReplicas`（已更新数） | 属于最新模板的实例数 | 计数 | 等于期望副本数才说明实例都已换成新模板 | 模板哈希标签与推进条件 | 小于期望而条件报完成 → 存在两套模板的实例并存 |
| `status.unavailableReplicas`（不可用数） | 低于可用下限的差额 | 计数 | 它把"未就绪"与"未达可用"合并成一个数 | 可用数与期望副本数 | 长期不为零 → 回到就绪判定与最小就绪时长 |
| `status.terminatingReplicas`（终止中副本数） | 正在终止尚未消失的实例 | 计数 | 解释真实实例数为何短暂超过期望 | 宽限期与节点资源 | 长期不降 → 实例收尾时间超过宽限期 |
| `status.conditions[]` 的 `Progressing` | "是否已经切换到新修订"的判定 | 条件，含类型、状态、原因、翻转时间 | 看 `status` 与 `reason`；超时类原因说明目标实例始终没就绪 | `Available` 条件与新修订的实例状态 | 状态为假且原因是超时 → 回到实例层 |
| `status.conditions[]` 的 `Available` | "是否已达到期望副本数"的判定 | 条件 | 与推进条件分别成立，两者都成立才算完成 | 认领数与可用数 | 数量条件为假 → 先看实例是否被拒绝或未就绪 |
| `metadata.labels.pod-template-hash` | 同一份模板的标识 | 字符串标签 | 不同哈希对应不同修订 | 各实例的标签分组与创建时间 | 出现多个哈希 → 存在多份模板的副本，确认是推进中还是停住 |
| `metadata.labels.controller-revision-hash` | 有状态集或守护进程集的修订标识 | 字符串标签 | 用于判断实例属于哪个修订 | `status.currentRevision` 与 `status.updateRevision` | 两个修订并存 → 正在推进或推进被卡住 |
| 修订对象的历史列表 | 还保留着哪些修订 | 对象列表 | 每个保留的历史对象对应一个可回退的修订 | `spec.revisionHistoryLimit` | 目标修订不在列表里 → 无法回退，需要重新发布旧内容 |
| `metadata.managedFields[].manager` | 每个字段当前归谁写 | 结构数组 | 同一字段只应有一个当前管理者 | 上一次提交注解与交付流程 | 管理者不是交付流程 → 先确认这第二个写入者是否仍然需要这条路径 |
| `status.containerStatuses[]` | 单个容器处于等待、运行还是终止 | 结构体，带原因与退出信息 | `waiting` 的 `reason` 决定下一步；**先取原因再取退出码** | 上一次运行的日志与事件 | 反复重启 → 先取退出码与原因，再看探针与时序 |
| 实例条件中的 `Ready` 与 `ContainersReady` | 实例是否可进入端点、容器自身是否就绪 | 条件 | 两者含义不同：终止流程中前者先变假 | 端点集合与终止时间线 | `Ready` 为假而 `ContainersReady` 为真 → 实例正在终止，不是应用故障 |
| `kube_deployment_status_replicas_unavailable`（采集器指标示例） | 不可用实例数的时间序列 | 计数 | 与期望副本数对照；应当在发布中短暂上升后回落 | 同一采集器的已更新实例数与可用实例数 | 长期不回落 → 与状态字段一致地指向实例未就绪；**数值仅示意，取自采集器的口径** |
| `kube_job_status_failed`（采集器指标示例） | 失败实例数的时间序列 | 计数 | 与重试上限对照；持续上升说明重试在消耗 | 任务的成功计数与判定原因 | 上升后任务判定失败 → 按判定原因分类；**数值仅示意** |
| 控制面队列指标（控制面组件指标示例） | 待处理与处理耗时的分布 | 计数与时长分位数 | 队列深度持续增长说明消费跟不上 | 观测代数与控制器日志 | 队列增长且代数落后 → 问题在控制器侧；**指标名称与标签随版本与采集方式变化** |

## 3. 采样纪律与工作负载基线卡

工作负载的问题大多是"某一段时间里的分布变了"，因此采样要固定口径：同一组对象、同一段时间窗、同一种聚合方式，先记基线，再谈变化。发布类问题尤其要固定**发布过程的观测窗口**，否则一次五分钟的发布与一次五十分钟的发布会被混在一起比较。

| 基线项 | 取值来源 | 交付时要给出 |
| --- | --- | --- |
| 对象与契约 | `kubectl get <类型> <名字> -o yaml` | 每个对象维持什么不变量、期望副本数由什么决定 |
| 期望来源与字段归属 | `kubectl get <类型> <名字> -o jsonpath='{range .metadata.managedFields[*]}{.manager}{"\t"}{.operation}{"\n"}{end}'` | 哪些字段由交付流程写、哪些由其它写入者写 |
| 修订与保留上限 | `kubectl rollout history <类型>/<名字>`；`kubectl get <类型> <名字> -o jsonpath='{.spec.revisionHistoryLimit}{"\n"}'` | 能回退多远、历史对象有多少 |
| 就绪判定 | `kubectl get <类型> <名字> -o jsonpath='{.spec.template.spec.containers[*].readinessProbe}{"\n"}'` | 判定来自哪些探针、失败会怎样表现 |
| 推进参数 | `kubectl get <类型> <名字> -o jsonpath='{.spec.strategy}{" "}{.spec.minReadySeconds}{" "}{.spec.progressDeadlineSeconds}{"\n"}'` | 推进的上界与下界、进度截止时间、最小就绪时长 |
| 存储保留与清理规则 | `kubectl get sts <名字> -o jsonpath='{.spec.persistentVolumeClaimRetentionPolicy}{"\n"}'`；`kubectl get job <名字> -o jsonpath='{.spec.ttlSecondsAfterFinished}{"\n"}'` | 缩容、结束与删除之后还剩什么 |
| 任务的重试与时间预算 | `kubectl get job <名字> -o jsonpath='{.spec.backoffLimit}{" "}{.spec.backoffLimitPerIndex}{" "}{.spec.activeDeadlineSeconds}{"\n"}'` | 失败的判定属于哪一类 |
| 定时任务的并发与历史 | `kubectl get cronjob <名字> -o jsonpath='{.spec.concurrencyPolicy}{" "}{.spec.startingDeadlineSeconds}{" "}{.spec.successfulJobsHistoryLimit}{" "}{.spec.failedJobsHistoryLimit}{"\n"}'` | 允许重叠吗、错过会怎样、历史留多少 |
| 发布时长基线 | `kubectl rollout status <类型>/<名字> --timeout=0` 的耗时统计（同一口径多次） | 正常发布需要多久，超过多少算异常 |
| 写入被拒的记录 | `kubectl create --dry-run=server -f x.yaml -v=6` 的响应体原因 | 常见拒绝原因与对应的处理路径 |

## 4. 故障现场定位表

### 4.1 发布没有推进

**现场**：模板改了，也出现了新的修订对象，但新修订的实例一直不就绪，发布进度停在同一个位置。

**先看什么**：先看期望代数与观测代数是否相等，再取新修订的实例，读它们的等待原因、容器状态与最近事件。**判据**：代数相等说明控制器看过最新期望，问题在实例侧；新修订的实例处于等待并且原因短语集中在同一步，说明问题出在那一类失败（拉取、启动、探针、调度）。**转向哪一步**：控制器侧问题去看队列与控制器状态；实例侧问题按等待原因分流；实例根本没有被创建时，去看写入是否被拒绝。

```bash
# 只读观测：控制器是否看过最新期望
kubectl get deploy demo -o jsonpath='{.metadata.generation}{" "}{.status.observedGeneration}{"\n"}'

# 只读观测：推进条件的类型与原因（超时类原因 = 目标实例始终没就绪）
kubectl get deploy demo -o jsonpath='{range .status.conditions[*]}{.type}={.status} {.reason}{"\n"}{end}'

# 只读观测：发布进度与各修订的实例分布
kubectl rollout status deploy/demo --timeout=30s
kubectl get rs -l app=demo -o custom-columns=NAME:.metadata.name,DESIRED:.spec.replicas,READY:.status.readyReplicas

# 只读观测：新修订实例的等待原因（reason 决定下一步往哪分流）
kubectl get pods -l app=demo -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.status.phase}{"\t"}{.status.containerStatuses[*].state.waiting.reason}{"\n"}{end}'
```

`rollout status` 的退出码是判据的一部分：**退出码为 0 表示已走完；非 0 且提示 `exceeded its progress deadline` 表示发布停滞**。停滞时不要再调副本数，先按上面的等待原因分流。

### 4.2 数量不齐

**现场**：业务报"容量不够"，但发布对象显示的数量看起来正常；或者发布对象显示的数量比期望多。

**先看什么**：把四本账并排放——认领数、就绪数、可用数与终止中副本数，再把实例按模板哈希分组。**判据**：认领数正常而可用数偏低，说明实例存在但不满足可用条件；认领数高于期望且终止中副本数偏高，说明多出来的是尚未消失的旧实例，真实资源占用高于账面。**转向哪一步**：可用不足回到就绪判定；多余副本回到终止流程与宽限期；两本账都对而业务仍报容量不足时，再去看容量侧的口径。

```bash
# 只读观测：四本账一次取出（终止中副本数字段只在发布对象与副本集上有）
kubectl get deploy demo -o jsonpath='replicas={.status.replicas}{" ready="}{.status.readyReplicas}{" available="}{.status.availableReplicas}{" updated="}{.status.updatedReplicas}{" unavailable="}{.status.unavailableReplicas}{" terminating="}{.status.terminatingReplicas}{"\n"}'

# 只读观测：实例按模板哈希分组，确认多出来的是旧修订还是新修订
kubectl get pods -l app=demo -o custom-columns=NAME:.metadata.name,HASH:.metadata.labels.pod-template-hash,PHASE:.status.phase,DELETING:.metadata.deletionTimestamp

# 只读观测：终止中的实例是否超过宽限期仍未退出
kubectl get deploy demo -o jsonpath='{.spec.template.spec.terminationGracePeriodSeconds}{"\n"}'
```

### 4.3 改了又变回去

**现场**：手工调整了某个字段以缓解故障，过一段时间它又回到原值；或者清单里改了副本数，集群里仍是旧值。

**先看什么**：读字段归属记录，确认该字段当前归谁；再看上一次提交注解与交付流程的最近一次执行。**判据**：该字段的管理者是交付流程时，手工改动一定会被下一次交付覆盖；管理者是另一个持续写入者（例如自动伸缩机制）时，清单里的值会被它改写。**转向哪一步**：先决定这个字段归谁写，再决定另一方是停止写入、改为只读，还是把值写进清单。

```bash
# 只读观测：这个字段当前归谁写（不加 --show-managed-fields 在人类可读输出里看不到归属）
kubectl get deploy demo -o jsonpath='{range .metadata.managedFields[*]}{.manager}{"\t"}{.operation}{"\t"}{.time}{"\n"}{end}'

# 只读观测：是否存在客户端应用写入者（返回空表示没有）
kubectl get deploy demo -o jsonpath='{.metadata.annotations.kubectl\.kubernetes\.io/last-applied-configuration}{"\n"}'

# 只读观测：清单源与集群现状的逐字段差异
kubectl diff -f deploy.yaml
```

**接管是破坏性的，只在可丢的实验集群演练**：`kubectl apply --server-side --field-manager=<名字> -f deploy.yaml` 会因字段归属冲突而失败，报错原文形如 `Apply failed with 1 conflict: conflict with "kubectl-client-side-apply": .spec.replicas`；加 `--force-conflicts` 可强行接管。**接管只是把责任取了过来，并没有删除原写入者**——原写入者仍留在 `managedFields` 里，下次提交仍会再次冲突。回滚方式是让原写入者按其 `fieldManager` 名重新提交。

### 4.4 有状态与任务不收敛

**现场**：有状态集合停在某个序号，后续实例一直没有创建；或者任务长期处于活跃状态但成功计数不增加；或者定时任务不再产生新对象。

**先看什么**：有状态集合先看停在哪个序号、这个实例的条件与容器状态；任务先看状态里的成功、失败与活跃计数以及判定原因；定时任务先看最近一次计划时间、暂停标志与并发策略。**判据**：有状态集合停在某个序号说明前一个实例未就绪；任务有活跃实例而成功数不增说明实例在失败重试；定时任务长时间没有新对象，要看是被并发策略跳过、被启动截止跳过，还是调度本身已经暂停。**转向哪一步**：序号停止前进回到实例就绪与存储绑定；任务失败按判定原因分类；定时任务按"跳过 / 暂停 / 错过的计划"分别核对。

```bash
# 只读观测：有状态集合停在哪个序号，以及当前修订与目标修订是否一致
kubectl get sts demo-sts -o jsonpath='ready={.status.readyReplicas}{" current="}{.status.currentRevision}{" update="}{.status.updateRevision}{" partition="}{.spec.updateStrategy.rollingUpdate.partition}{"\n"}'
kubectl get pods -l app=demo-sts -o custom-columns=NAME:.metadata.name,READY:.status.containerStatuses[*].ready,REV:.metadata.labels.controller-revision-hash

# 只读观测：任务的成功、失败与活跃计数，以及判定原因（区分重试用尽与时间用完）
kubectl get job <任务名> -o jsonpath='succeeded={.status.succeeded}{" failed={.status.failed}{" active="}{.status.active}{"\n"}{range .status.conditions[*]}{.type}={.status} {.reason}{"\n"}{end}'

# 只读观测：定时任务最近一次计划时间、暂停标志与并发策略
kubectl get cronjob <任务名> -o jsonpath='last={.status.lastScheduleTime}{" suspend="}{.spec.suspend}{" concurrency="}{.spec.concurrencyPolicy}{" deadline="}{.spec.startingDeadlineSeconds}{"\n"}'
```

任务判定原因的两种结局方向不同：`reason` 指向重试用尽时，方向是查失败原因并判断它是否属于确定性失败；指向超时（`DeadlineExceeded`）时，方向是评估任务本身的时间需求与 `spec.activeDeadlineSeconds` 设置。**不要把两者都当成"重试不够"而直接调大重试上限。**

## 5. 破坏性动作的边界

下面前五项会改变数据或让回退能力消失，因此只能在可丢的实验集群上执行；生产集群上动手前必须先确认备份可恢复、步骤已在实验集群演练过。后三项分别给出"需要窗口的配置变更"与"任何集群都不执行"的边界：

| 动作 | 为什么危险 | 边界与不可回滚说明 |
| --- | --- | --- |
| 删除历史修订对象 | 对应的修订信息随之消失，之后再也不能回退到它 | 只在可丢的实验集群执行；生产上这一步等于主动放弃一个回退点 |
| 强制删除实例、跳过宽限期 | 进程没有收尾时间，外部连接与中间数据可能停在不确定状态 | 只在可丢的实验集群执行；生产上仅在实例确认没有收尾价值时按变更流程执行 |
| 删除有状态负载的卷声明 | 数据随之消失，除非另有可用的备份 | 只在可丢的实验集群执行；生产上必须先确认备份可恢复 |
| 把卷声明的回收策略改成删除 | 之后缩容或删除集合都会自动销毁数据 | 只在可丢的实验集群验证；生产上属于需要窗口的变更，并要有回滚点 |
| 用整体替换的方式写入一个已被别人管理的对象 | 会覆盖对方的字段，冲突被隐藏而不是被解决 | 只在可丢的实验集群演练；生产上应改为按字段合并，或先划清字段归属 |
| 把修订保留上限设为 0 | 发布完成之后历史被回收，回退能力消失 | 属于需要窗口的配置变更，不是破坏性动作；改之前先记录当前修订列表 |
| 删除仍在运行的任务对象 | 实例被连级联删除，尚未落盘的成果会丢失 | 属于需要窗口的动作；先确认输出已经写到外部存储再删除 |
| 直接编辑存储里的对象 | 绕过全部关卡，导致缓存与权威数据长期不一致 | 任何集群都不执行；这类动作没有可核对的证据链 |

## 6. 能提交的清单

下面两份清单把前面几节反复引用的字段一次写全，用来在实验集群上把发布、回退与存储回收三个机制走一遍。**清单里的镜像、标签与命名空间都可替换**；尺寸与阈值只是示意，真实值按自己的应用与集群形态定。

### 6.1 无状态发布：探针、推进参数与回退

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: demo
spec:
  replicas: 3
  revisionHistoryLimit: 10
  progressDeadlineSeconds: 600
  minReadySeconds: 0
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  selector:
    matchLabels: {app: demo}
  template:
    metadata:
      labels: {app: demo}
    spec:
      terminationGracePeriodSeconds: 30
      containers:
        - name: app
          image: registry.example.com/demo:1.0.0
          startupProbe:                 # 预算 = periodSeconds × failureThreshold = 5 × 12 = 60 秒
            httpGet: {path: /healthz, port: 8080}
            periodSeconds: 5
            failureThreshold: 12
          readinessProbe:               # 推进的实际闸门：未声明时该判定按成功处理
            httpGet: {path: /readyz, port: 8080}
            periodSeconds: 5
          livenessProbe:                # 与就绪探针分开：它的失败后果是重启容器
            httpGet: {path: /healthz, port: 8080}
            periodSeconds: 10
          lifecycle:
            preStop:
              exec: {command: ["sleep", "5"]}
```

```bash
# 只读观测：推进过程中 maxUnavailable=0 与 maxSurge=1 共同决定并存实例数（会短暂看到 4 个）
kubectl apply -f deploy.yaml
kubectl get pods -l app=demo -o custom-columns=NAME:.metadata.name,HASH:.metadata.labels.pod-template-hash,READY:.status.containerStatuses[*].ready

# 只读观测：四个修订账目与两组条件
kubectl get deploy demo -o jsonpath='gen={.metadata.generation}{" obsGen="}{.status.observedGeneration}{" replicas="}{.status.replicas}{" ready="}{.status.readyReplicas}{" available="}{.status.availableReplicas}{" updated="}{.status.updatedReplicas}{" terminating="}{.status.terminatingReplicas}{"\n"}'
kubectl get deploy demo -o jsonpath='{range .status.conditions[*]}{.type}={.status} {.reason}{"\n"}{end}'

# 只读观测：发布是否走完；退出码 0 即走完，非 0 且提示 exceeded its progress deadline 即停滞
kubectl rollout status deploy/demo --timeout=60s
```

**改一次模板产生一份新修订**，回退就是让控制器重新指向某一份历史修订：

```bash
# 只读观测：先给这次发布留下可读的原因（不写它，HISTORY 的原因列全是 <none>）
kubectl annotate deploy/demo kubernetes.io/change-cause="image 1.0.0 → 2.0.0"
kubectl set image deploy/demo app=registry.example.com/demo:2.0.0

# 只读观测：历史修订与目标修订是否还在
kubectl rollout history deploy/demo

# 回退：只恢复 spec.template，副本数与策略参数不回退（只在可丢的实验集群演练）
kubectl rollout undo deploy/demo --to-revision=1
```

回退的边界必须写清：**它改的是集群里的期望态，清单源仍写着新版本**，因此下一次交付会把新版本重新推上来——完整的处置必须包含把清单源也改回去这一步。**`revisionHistoryLimit` 之外的修订已经被回收，回退不到**。

### 6.2 有状态集合：稳定身份与存储回收

```yaml
apiVersion: v1
kind: Service
metadata:
  name: demo-headless
spec:
  clusterIP: None                 # 无头服务：为实例提供稳定的实例级域名
  selector: {app: demo-sts}
  ports:
    - port: 80
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: demo-sts
spec:
  serviceName: demo-headless      # 必填：稳定域名的来源
  replicas: 3
  podManagementPolicy: OrderedReady
  updateStrategy:
    type: RollingUpdate
    rollingUpdate:
      partition: 0                # 只更新序号不小于该值的实例
  persistentVolumeClaimRetentionPolicy:
    whenScaled: Retain            # 缺省即保留：缩容不等于释放存储
    whenDeleted: Retain
  selector:
    matchLabels: {app: demo-sts}
  template:
    metadata:
      labels: {app: demo-sts}
    spec:
      containers:
        - name: app
          image: registry.example.com/demo:1.0.0
  volumeClaimTemplates:
    - metadata: {name: data}
      spec:
        accessModes: [ReadWriteOnce]
        resources: {requests: {storage: 1Gi}}
```

```bash
# 只读观测：稳定身份来自"实例名 + 服务名 + 命名空间"，不是来自地址
kubectl apply -f sts.yaml
kubectl get pods -l app=demo-sts -o custom-columns=NAME:.metadata.name,REV:.metadata.labels.controller-revision-hash,READY:.status.containerStatuses[*].ready
kubectl exec demo-sts-0 -- getent hosts demo-sts-0.demo-headless

# 只读观测：缩容之后卷声明还在不在（这是缺省行为，不是故障）
kubectl scale statefulset demo-sts --replicas=1
kubectl get pvc | grep 'data-demo-sts-'
```

卷声明的名字由"模板名 - 集合名 - 序号"拼成，因此**用名字前缀核对比用标签选择器可靠**——集合按模板生成的卷声明不自动继承实例的标签。

```bash
# 演练：把回收策略改成删除之后再缩容，观察存储随之消失（只在可丢的实验集群，数据不可回滚）
kubectl patch statefulset demo-sts --type=merge \
  -p '{"spec":{"persistentVolumeClaimRetentionPolicy":{"whenScaled":"Delete","whenDeleted":"Delete"}}}'
kubectl scale statefulset demo-sts --replicas=0
kubectl get pvc | grep 'data-demo-sts-'

# 回滚：重新提交原清单，并把回收策略改回 Retain
kubectl apply -f sts.yaml
```

分批推进可以用分区验证：把 `partition` 设为大于 0 的值，只让一部分实例更新，判据是**分界两侧的实例带着不同的修订哈希**，同时 `status.currentRevision` 与 `status.updateRevision` 不相等。

## 7. 常见坑

| 常见做法 | 后果 |
| --- | --- |
| 只看发布对象，不看实例 | 发布对象的数量可能正常，而实例一个都没就绪 |
| 只看实例，不看修订 | 会误判"实例正常"，而实际有多个修订的实例同时存在 |
| 用事件判断历史 | 事件只保留有限时间，过期之后"没有看到"不等于没有发生过 |
| 用指标判断当前状态而不记口径 | 指标是时间序列，脱离标签与窗口的引用无法复现 |
| 把字段归属与实际值分开看 | 只看到值变了，不知道是谁写的，也无法判断下一次改动会不会被覆盖 |
| 用重启实例处理"数量不齐" | 会丢掉当前现场，并且掩盖真实的失败原因 |
| 在生产集群上验证破坏性动作 | 数据与回退点无法恢复 |

## 8. 要点自测

**问：为什么工作负载的观测必须同时看三个层次？**

答：因为期望、修订与实例分别回答不同问题：期望回答"要什么"，修订回答"按哪个模板在推进"，实例回答"实际变成了什么"。只看期望会误判发布完成，只看实例会漏掉多个修订并存的事实。

**问：判断"发布是否完成"最短的一条路径是什么？**

答：先看期望代数与观测代数是否相等，确认控制器看过最新期望；再看推进条件的类型、状态与原因，确认推进是否走完；最后看数量条件与新修订的可用实例数，确认数量与可用都达标。

**问：手工改了集群里的字段又被改回去，第一件事做什么？**

答：读字段归属记录，确认这个字段当前归谁写。归属在交付流程时，手工改动必然被覆盖；归属在另一个持续写入者时，清单里的值会被它改写。先确定归属，再决定让哪一方退出这条路径。

**问：为什么"容量不够"的反馈不能只用实例总数来回答？**

答：因为认领数、就绪数、可用数与终止中的实例是四本账：认领数包含未就绪实例，可用数不包含终止中的实例。用总数回答容量问题，会把未就绪与正在退出的实例当成有效容量。

**第一反应不要做什么**：不要只看一层对象下结论；不要在实例未就绪时先改副本数或参数；不要用手工修改代替字段归属的划分；不要在事件过期之后断言"没有发生过"；也不要在生产集群上验证破坏性动作。
