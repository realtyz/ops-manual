# 工作负载与清单的治理

## 1. 这些上限分别配在哪一层

工作负载治理上最常见的管理错位是：**想控制的是一件事，配的却是另一层**。同一个效果可能由清单内容、对象字段、集群侧策略、交付流程甚至一次团队约定决定。因此第一步是把每项控制按层归位。

| 想控制的 | 配在哪一层 | 影响范围 | 谁负责 | 改了要重新验证什么 |
| --- | --- | --- | --- | --- |
| 副本数的来源与取值范围 | 清单内容与对象字段 | 该对象 | 发布流程负责人 | 该字段归谁写、被自动伸缩机制改写时以谁为准 |
| 模板的内容与参数化范围 | 模板与渲染流程 | 使用该模板的全部环境 | 模板维护方 | 渲染产物与集群对象的差异是否可解释 |
| 字段归属的划分 | 提交方式与写入者约定 | 该对象 | 平台方与发布流程负责人共同约定 | 变更之后原本由谁写的字段是否有人接管 |
| 就绪判定的存在与内容 | 对象的模板 | 该对象 | 业务方 | 判定失败时的表现、启动耗时与最小就绪时长是否匹配 |
| 推进的上界、下界与截止时间 | 对象的更新策略参数 | 该对象 | 发布流程负责人 | 与业务可承受的容量下限、发布时长是否匹配 |
| 修订保留上限 | 对象的字段 | 该对象 | 发布流程负责人 | 能回退多远、历史对象数量对存储与列表输出的影响 |
| 存储保留与结束清理规则 | 对象的保留策略字段 | 该对象及其卷声明 | 业务方与平台方共同约定 | 缩容、结束与删除之后还剩什么，成本由谁承担 |
| 任务的重试与时间预算 | 任务的字段 | 该任务 | 业务方 | 失败判定属于哪一类、外部副作用是否幂等 |
| 定时任务的并发、延迟与历史 | 定时任务的字段 | 该定时任务 | 业务方 | 错过与补跑时的行为，以及任务是否幂等 |
| 破坏性动作的执行权限 | 权限授予与变更流程 | 整个集群 | 平台方 | 哪些动作只能在实验集群演练、谁是回退点 |
| 备份与恢复的验证 | 变更流程与演练制度 | 该对象依赖的数据 | 平台方 | 回退与恢复的判据，而不是"有备份"这一事实 |

**两条归属原则：**

1. **能在清单里表达的，不要依赖集群侧保底。** 副本数、模板内容、就绪判定、保留上限都属于发布物的内容；依赖集群侧代为纠正，会让同一份清单在不同环境中的行为不一致，也让事故比对失去基准。
2. **能被自动校验的约定，不要只写进文档。** 命名规范、标签约定、必须配置就绪判定、必须给出保留策略这类要求，如果只写在文档里，几个月之后必然有人违反；要么用准入策略先观察后拒绝，要么明确接受它会被违反。

## 2. 交付产物

### 2.1 工作负载清单卡

每个对象一张，字段固定如下：

| 字段 | 取值来源 | 交付时要给出 |
| --- | --- | --- |
| 对象与契约 | 对象清单与它所属的类型 | 维持什么不变量、期望副本数由什么决定 |
| 期望来源与字段归属 | 字段归属记录与交付流程 | 哪些字段由交付流程写、哪些由其它写入者写 |
| 模板与参数化范围 | 模板与渲染产物 | 哪些值按环境取值、产物与集群对象的差异是什么 |
| 就绪判定 | 实例的探针配置 | 判定内容、失败表现与最小就绪时长 |
| 推进参数 | 更新策略参数 | 上界、下界、进度截止时间，以及业务可承受的容量下限 |
| 修订与保留 | 修订保留上限与历史列表 | 能回退多远、历史对象的数量级 |
| 数据与清理 | 存储保留策略与结束保留期 | 缩容、结束与删除之后还剩什么 |
| 责任方 | 交付流程与业务方的分工 | 谁改模板、谁改参数、谁批破坏性动作 |

### 2.2 发布前检查单

| 检查项 | 要回答的问题 |
| --- | --- |
| 变更落在哪一层 | 这次改动是模板变化还是数量调整，会触发几份修订 |
| 就绪判定 | 新版本是否配置了就绪判定，启动耗时是否在判定的容忍范围内 |
| 容量下限 | 推进期间的可用容量下限是否满足业务的接收能力 |
| 时长与截止 | 预计发布时长与进度截止时间的关系，超时之后谁处置 |
| 回退点 | 要回退到哪一个修订，它在历史列表里是否还在 |
| 数据与外部副作用 | 这次变更是否涉及不可逆的外部改动，回退能否覆盖 |
| 清单源 | 回退时清单源要改成什么内容、由谁执行 |
| 观测口径 | 用哪些字段与哪些时间窗判断发布成功，由谁盯 |

### 2.3 发布与回退记录

| 字段 | 要回答的问题 |
| --- | --- |
| 变更内容 | 哪一次改动、落在哪个字段上、产生了哪几份修订 |
| 推进参数 | 上界、下界、最小就绪时长与进度截止时间的取值 |
| 观测结果 | 发布期间容量账目的最低点、错误率与耗时的变化 |
| 判定结论 | 完成、停滞还是回退，判据是什么字段与什么数值 |
| 回退动作 | 回退到哪个修订、清单源是否同步回写、外部副作用如何处理 |
| 未恢复内容 | 数据、外部系统状态与其它不在恢复范围内的内容 |
| 后续动作 | 需要补的清理、需要调整的参数与需要复验的假设 |

### 2.4 数据与清理保留卡

| 字段 | 要回答的问题 |
| --- | --- |
| 保留策略 | 缩容、结束与删除分别会销毁还是保留什么 |
| 成本归属 | 保留下来的存储与历史对象的成本由谁承担 |
| 清理动作 | 谁在什么时候执行清理，判据是什么 |
| 恢复手段 | 数据被销毁时如何恢复，最后验证是什么时候 |

## 3. 与其它领域的接口

- **调度与放置**：一个实例被放到哪台机器上、为什么被拒绝或抢占，属于放置一侧的判定；这里只回答期望副本数从哪里来，以及实例数量与节点集合之间的对应关系。
- **资源、容量与争抢**：资源请求与上限、配额、驱逐顺序与自动伸缩的判定属于容量一侧；这里只回答副本数这个字段由谁写，以及它被改写时如何与清单源共存。
- **网络**：流量方向、入口规则与按比例分配属于网络一侧；这里只回答两组副本如何并存，以及用什么判据确认实例可用。
- **存储**：卷的供给、扩容、快照与数据一致性属于存储一侧；这里只回答保留策略决定缩容之后还剩什么。
- **安全与多租户**：工作负载加固的具体配置、凭据注入与策略内容属于安全一侧；这里只回答对象由谁提交、模板从哪里来。
- **生产运维**：变更流程、升级顺序与备份恢复演练的编排属于运维一侧；这里提供的是它所需要的检查单、保留规则与阶段判据。
- **交付工具的提供方**：模板语言、交付控制器的部署与调优属于工具自身的文档；这里只写与收敛链相关的判据。

## 4. 一个治理场景

**背景**：一次镜像升级上线后错误率上升，值班把对象回退到上一个修订，服务随即恢复。第二天同样的故障重现；同时成本核对发现，一次缩容之后存储容量并没有下降。

**按本节的做法走一遍：**

1. **先确认回退改的是什么。** 回退动作只改了集群里的对象，清单源里仍是新版本。因此第二天重现不是新的故障，而是下一次交付把新版本重新推进上来的必然结果。
2. **把清单源同步回写。** 在清单源里把模板改回旧内容并提交，让集群状态与声明源头重新一致；这一步是收口的关键，缺了它，任何回退都只是临时的。
3. **区分"恢复"与"未恢复"。** 把这次变更的未恢复内容写下来：外部系统已经按新版本处理过的请求、以及可能已经写入的数据。它们不会随模板回退而回退，因此要单独评估影响范围。
4. **解释存储为什么没有下降。** 读集合的卷声明回收策略，确认缺省行为是缩容时保留；缩容不等于释放资源，因此清理要由单独的动作与判据完成。
5. **把两件事写进检查单。** 发布前检查单里补一条：回退时谁负责把清单源改回旧内容；保留卡里补一条：缩容之后由谁核对存量卷声明，判据是什么。
6. **交出产物**：
   - 更新后的**工作负载清单卡**（期望来源、推进参数与保留规则）；
   - 一份**发布与回退记录**，写清变更内容、判定结论、回退动作与未恢复内容；
   - 补充后的**发布前检查单**与**数据与清理保留卡**。
7. **验收**：在下一次交付之后确认集群里的模板与清单源一致，且没有出现"再次被推回新版本"的现象；同时按同一口径复核存量卷声明的数量与容量，确认清理动作确实执行过。

**这个场景的要点**：回退是链条上的一个动作，不是一个状态。它只有配上清单源的回写、未恢复内容的评估与保留规则的核对，才算收口；这三件事分别落在发布物、影响面评估与清理规则三层上。

## 5. 常见坑

| 常见做法 | 后果 |
| --- | --- |
| 把副本数、保留上限这类内容留在集群侧由人工维护 | 同一份清单在不同环境中的行为不一致，事故比对没有基准 |
| 只把命名与标签约定写进文档 | 几个月之后必然被违反，而且违反时没有判据可查 |
| 使用有状态负载却不给保留策略 | 缩容之后存储成本无人认领，或者清理时误删数据 |
| 不配置就绪判定就上线 | 推进速率由应用的真实行为决定，而不是由参数决定 |
| 回退之后不回写清单源 | 故障在下一个交付周期重现，被当成新问题重新排查 |
| 用修订保留上限为 0 换取"清爽" | 发布完成之后历史被回收，回退能力随之消失 |
| 把破坏性动作留给值班临时决定 | 缺少演练过的步骤与验证过的备份，风险不可控 |
| 用重启或删除实例处置一切 | 现场被清掉，真实原因没有被定位 |

## 值班口径

被追问"工作负载的一项控制应该配在哪一层"时，答法是先问"这件事会不会随环境变化"。会随环境变化的内容属于发布物；对整类对象都成立的内容属于对象的字段或集群侧策略；只影响一次执行的内容属于调用方。把三类分别落到负责人身上，配置错位的问题会明显减少。

被追问"为什么发布前的检查单要单列回退点与清单源"时，答法是：回退点的存在决定了故障时的可选动作，而清单源的回写决定了这个动作是否会被下一次交付撤销。两者缺一，回退就只是一次临时缓解。

被追问"缩容与删除的区别为什么要写进保留卡"时，答法是：缺省语义下删除实例、缩容与删除集合都不销毁数据，因此"下线"这个词在存储层面没有统一含义。保留卡要回答的是"哪种动作会销毁什么、成本由谁承担、恢复手段验证过没有"。

被追问"哪些动作属于必须先在实验集群演练的破坏性动作"时，答法是：会销毁数据、会让回退能力消失、会隐藏字段冲突的动作。它们在生产集群上执行之前，必须确认备份可恢复、步骤已经演练、并且有明确的回退点。

**第一反应不要做什么**：不要把清单内容与集群侧设置混着维护；不要在没有就绪判定的情况下依赖推进参数；不要把回退当成收口；不要用保留上限为 0 换取表面的整洁；不要在没有演练的情况下执行破坏性动作。
