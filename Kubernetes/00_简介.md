# Kubernetes 学习大纲（生产级）

> **定位**：一条「能扛住生产事故、也能落到生产实践」的学习路径。
> **前置基础**：Docker/容器、Linux 基础（systemd、cgroup、namespace、进程）、TCP/IP 网络、YAML。
>
> 原则：每个模块都按 **概念 → 生产实践 → 要点自测** 三层推进，而不是「看教程点一遍就算学会」。

---

## 学习路径总览（Roadmap）

| 阶段 | 主题 | 建议周期 | 产出目标 |
| --- | --- | --- | --- |
| 0 | 前置与实验环境 | 1 周 | 本地集群跑起来，`kubectl` 熟练 |
| 1 | 核心架构与对象模型 | 1~2 周 | 能讲清一次请求如何贯穿集群 |
| 2 | 工作负载与控制器 | 1~2 周 | 能选对 workload 并安全发布 |
| 3 | 调度、资源与 QoS ★ | 1~2 周 | 讲清调度、资源约束与 QoS 判定 |
| 4 | 网络 | 2 周 | 讲清 Service 流量路径与 CNI |
| 5 | 存储 | 1~2 周 | 有状态应用的持久化闭环（申请 → 挂载 → 扩容 → 快照 → 回收） |
| 6 | 安全 | 1~2 周 | 最小权限 + 工作负载加固 + 数据加密 |
| 7 | 生产运维与可观测性 | 2 周 | 排障、扩容、升级、备份（含一次恢复演练） |
| 8 | GPU / AI 场景扩展 ★ | 1~2 周 | 结合你的 RDMA/GPU 背景做差异化 |
| 9 | 复习与自测 | 持续 | 核心要点 + 系统设计练习 |

> 标 ★ 的两段是「投入产出比最高、也最贴合你现有背景」的部分，优先打透。

## 阶段 0：前置与实验环境

> **对应笔记**：[[00_前置与实验环境]]

### 0.1 本地集群

- [ ] 三选一搭本地环境：`minikube` / `kind` / `k3d`（推荐 `kind`，多节点演练网络策略最方便）
- [ ] 用 `kind` 起一个「1 控制面 + 2 工作节点」的集群，并能随手 `kind delete cluster` 删掉重建
- [ ] 知道本地集群的默认 StorageClass 是什么（kind 自带 `standard`，`rancher.io/local-path` + `WaitForFirstConsumer`）
- [ ] 知道本地 `LoadBalancer` 类型 Service 默认会一直 `Pending`（kind 需 Cloud Provider KIND、minikube 用 `minikube tunnel`、k3d 靠 ServiceLB）
- [ ] 会把本地构建的镜像导入集群（`kind load docker-image` / `k3d image import` / `minikube image load`）

### 0.2 容器运行时与 CRI

- [ ] 理解容器运行时与 K8s 的关系：Docker ≠ 容器，`containerd` / `cri-o` 才是 CRI 标准
- [ ] 能讲清 `dockershim` 自 v1.24 起被移除，以及「镜像格式没变，Docker 仍可用来构建镜像」
- [ ] 知道节点上的排查命令是 `crictl ps` / `crictl logs`，而不是 `docker ps` / `docker logs`
- [ ] 知道 kubelet 与容器运行时必须使用同一个 cgroup driver

### 0.3 kubectl 基本功

- [ ] 熟练 `kubectl` 常用子命令：`get/describe/logs/exec/apply/delete/scale/rollout`
- [ ] 会用 `kubectl config get-contexts / current-context / use-context / set-context --current --namespace`
- [ ] 熟悉 `kubectl explain` 和 `kubectl api-resources`
- [ ] 会用 `kubectl get -o yaml/json` + `jq` 快速过滤字段
- [ ] 会用 `-o jsonpath` / `-o custom-columns` 取字段与自建表格
- [ ] 能说清 `--dry-run=client` 与 `--dry-run=server` 的区别（只有 server 端会过准入、补默认值）

### 0.4 操作纪律

- [ ] 建立习惯：危险命令前先确认 `kubectl config current-context`，能用 `--dry-run=server` / `kubectl diff` 就先演练
- [ ] context 命名带环境前缀，能把 context 显示在 shell 提示符里
- [ ] 清楚本地集群的管理员证书不能带到生产，生产用 OIDC / 短期凭据（详见 [[06_安全]]）

**生产实践**
- 真实环境优先 `kubeadm` 或托管服务（EKS/GKE/ACK），不要在生产用手搓的脚本集群
- 尽早建立 `kubectx/kubens` 管理多集群、多 namespace 的习惯，防止「在生产集群误操作」
- 本地集群版本尽量对齐目标生产版本（`kubectl` 建议 ±1 个小版本，kubelet 最多比 apiserver 老 3 个小版本）
- 明确「本地验证不了什么」：etcd 高可用与恢复、多可用区调度、真实块存储与快照、云负载均衡、节点故障与驱逐
- 把建集群的命令与实验 manifest 放进仓库，环境要能一键重建，而不是手工修集群

**要点自测**
- 容器运行时为什么从 Docker 迁移到 containerd？（CRI 标准化、调用链更短）
- CRI 规定了什么、没规定什么？为什么 kubelet 能换运行时？
- `kind` / `minikube` / `k3d` 分别适合什么场景？为什么它们都不能当生产环境？
- 一次 `kubectl` 请求包含哪些要素？kubeconfig 里的 `clusters` / `users` / `contexts` 各是什么？
- `kubectl explain` 和 `kubectl api-resources` 解决什么问题？
- `--dry-run=client` 和 `--dry-run=server` 有什么区别？验证 manifest 该用哪个？

> **对应笔记**：[[01_核心架构与对象模型]]

### 1.1 架构与组件

- [ ] Control Plane：`kube-apiserver`、`etcd`、`kube-scheduler`、`kube-controller-manager`、`cloud-controller-manager`
- [ ] Data Plane（Node）：`kubelet`、`kube-proxy`、容器运行时
- [ ] `etcd`：Raft 共识、quorum（N/2+1）、快照与 WAL、备份恢复

- [ ] `kube-apiserver` 请求全链路：认证 → 授权 → 准入控制（Mutating/Validating Admission Webhook）

### 1.2 核心对象模型

- [ ] Pod 与容器：多容器共享网络/存储命名空间、sidecar 模式
- [ ] Namespace、Label/Selector、Annotation、finalizer
- [ ] ConfigMap / Secret（以及 Secret 的加密：`etcd` 静态加密、KMS、SealedSecrets）
- [ ] ConfigMap / Secret 的更新语义（env 不更新、卷有延迟、`subPath` 不更新）与 Secret 内置类型
- [ ] Pod 状态机：phase / 容器状态 / conditions、重启退避与 `CrashLoopBackOff`、原生 sidecar 容器
- [ ] 探针：`liveness` / `readiness` / `startup` 三者的区别与正确用法
- [ ] 生命周期钩子：`postStart` / `preStop`（配合优雅下线）

**生产实践**
- `readiness` 决定「是否接流量」，`liveness` 决定「是否重启」——两者混用是生产事故高频来源
- `preStop` + `terminationGracePeriodSeconds` 做优雅下线，避免请求被切断

- 控制器模式是什么？为什么说 K8s 是「声明式」系统？

## 阶段 3：调度、资源与 QoS ★（核心区）

> **对应笔记**：[[03_调度_资源_QoS]]

### 3.1 调度

- [ ] 调度两大阶段：过滤（Predicates/Filter）→ 打分（Priorities/Score）
- [ ] **NodeAffinity** ★：`requiredDuringScheduling` vs `preferredDuringScheduling`，operator（In/NotIn/Exists/Gt/Lt）
- [ ] PodAffinity / PodAntiAffinity（拓扑域 `topologyKey` 的坑）
- [ ] **Taints & Tolerations** ★：`NoSchedule` / `PreferNoSchedule` / `NoExecute`，`tolerationSeconds`
- [ ] 优先级与抢占（PriorityClass + Preemption）
- [ ] TopologySpreadConstraints（跨 zone/节点打散）

### 3.2 资源与 QoS

- [ ] `requests` vs `limits`：调度依据是 requests，运行时约束是 limits
- [ ] **QoS 三档** ★：Guaranteed / Burstable / BestEffort（判定规则要背熟）
- [ ] OOM 与驱逐（eviction）顺序：BestEffort → Burstable → Guaranteed
- [ ] ResourceQuota / LimitRange（namespace 级多租户隔离）
- [ ] cgroup v1/v2、CPU throttling、内存超额分配的风险

**生产实践**
- 生产容器 **必须** 设 requests，`limits` 视场景（CPU 可留弹性，内存必须设上限防 OOM 拖垮节点）
- Guaranteed 的判定：每个容器都设 request 且 `request == limit`（且对所有资源一致）
- 用 `NodeAffinity` 做「软约束」（preferred），用 Taint/Toleration 做「硬隔离」（专用节点池）

**要点自测**
- **谈谈 QoS**：三档定义 → 判定规则 → 与 eviction/抢占的关系 → 为什么对生产稳定重要
- **谈谈 Taint 和 Toleration**：是「排斥」而非「亲和」，作用于 Node，能处理污点但调度仍要过过滤/打分；`NoExecute` + `tolerationSeconds` 的驱逐语义
- **谈谈 NodeAffinity**：与 `nodeSelector` 的区别、required vs preferred、与 Taint 如何配合
- 延伸：一个 Pod 一直 `Pending` 如何排查？（资源不足 / 节点不匹配 affinity / 污点无容忍 / 卷未就绪）

## 阶段 4：网络

> **对应笔记**：[[04_网络]]

### 4.1 Service 与流量

- [ ] Service 类型：ClusterIP / NodePort / LoadBalancer / ExternalName / Headless
- [ ] Endpoint / EndpointSlice、Selector 与无 Selector Service
- [ ] `kube-proxy` 模式：iptables（1.37 仍为默认）/ nftables（官方推荐的演进方向，也是 ipvs 的替代）/ ipvs（1.35 起弃用、1.40 起默认关闭、1.43 移除），以及 CNI 自带 Service 转发（差异与选型）
- [ ] Service 到 Pod 的完整流量路径（DNS 解析 + DNAT）
- [ ] DNS：CoreDNS、`headless` service 返回 Pod IP 的机制

### 4.2 南北向与东西向

- [ ] Ingress / Ingress Controller（`nginx-ingress` 与 `ingress-nginx` 是两回事；**Ingress API 已冻结，社区版 Ingress NGINX 已于 2026 年 3 月退役**，新集群不要选它）
- [ ] Gateway API（官方推荐的 Ingress 替代方向：Ingress API 已冻结，不再有新特性）
- [ ] CNI 模型：Flannel / Calico / Cilium（数据面与网络策略能力差异）
- [ ] NetworkPolicy（东西向流量管控，默认拒绝还是默认放行）

**生产实践**
- 大规模集群（Service / 端点数量多、变更频繁）优先评估 nftables 模式，或直接换成 Cilium（eBPF）接管 Service 转发；nftables 的收益来自端点变更同步与内核包处理，官方口径是「包处理效率差异要到数万个 Service 才明显」，与「流量大」不是一回事；ipvs 已弃用并将在 1.43 移除，不要作为新集群的选型依据
- 生产多租户默认策略：namespace 级 NetworkPolicy 白名单，而非裸奔

**要点自测**
- 画一条「用户 → Ingress → Service → Pod」的流量图，讲清每一跳的改写
- `kube-proxy` 被移出数据面后（如 Cilium 替代）Service 流量还怎么走？
- ClusterIP 是虚拟 IP 吗？它真的「绑定」在某个接口上吗？

### 4.3 延伸：RDMA / RoCE 在 K8s（结合你的背景 ★）

- [ ] 多网络：Multus CNI（一张 Pod 挂多块网卡）
- [ ] SR-IOV Device Plugin（把 VF 直通给 Pod）
- [ ] RDMA/RoCE 在容器内的可行性：需要配套的 CNI 链（Multus + SR-IOV CNI + RDMA CNI）+ 宿主机驱动与内核支持 + 网络命名空间内的 RDMA 设备与权限配置
- [ ] RDMA 特点 / RoCE 是否跑以太网 / 网络分层

## 阶段 5：存储

> **对应笔记**：[[05_存储]]

### 5.1 Volume 与卷类型

- [ ] 容器文件系统为什么不持久：可写层随容器重建消失，Pod 内多容器默认不共享文件系统
- [ ] Volume 类型：`emptyDir`（含 `medium: Memory` 与 `sizeLimit`）/ `hostPath` / `local` / `configMap` / `secret` / `downwardAPI` / `projected` / `nfs` / CSI
- [ ] 临时卷的两种形态：generic ephemeral volume（在 Pod 里声明 PVC 模板，随 Pod 生灭）与 CSI inline ephemeral volume
- [ ] `hostPath` 为什么不能当持久化用（节点绑定 + 安全风险 + 不计入临时存储统计），以及 `local` PV 与它的区别（`nodeAffinity` + `WaitForFirstConsumer`）
- [ ] `volumeMode`：`Filesystem`（默认）与 `Block`，以及裸块设备的用法与限制

### 5.2 PV / PVC / StorageClass

- [ ] PV / PVC 模型：静态供给 vs 动态供给，以及「解耦提供方与使用方」的意义
- [ ] 作用域与绑定：PV、StorageClass 是集群级，PVC 是 namespace 级；PVC ↔ PV 一对一绑定（`claimRef` / `volumeName`）
- [ ] 绑定匹配条件：class、accessModes、容量（只往大不往小）、`volumeMode`、`selector`
- [ ] PV 阶段（Available / Bound / Released / Failed）与 PVC 阶段（Pending / Bound / Lost）的区别（新建 PV 会有短暂的 Pending，别和「PVC 没绑上」混为一谈）
- [ ] 保护机制：`kubernetes.io/pvc-protection`、`kubernetes.io/pv-protection`，以及 CSI 的 `external-provisioner` finalizer
- [ ] StorageClass：`provisioner`、`parameters`、`reclaimPolicy`（Retain / Delete；`Recycle` 已弃用）、`volumeBindingMode`、`allowVolumeExpansion`、`allowedTopologies`
- [ ] 默认 StorageClass（注解 `storageclass.kubernetes.io/is-default-class`）与 `DefaultStorageClass` 准入插件、retroactive default assignment
- [ ] `volumeBindingMode`：`Immediate` vs `WaitForFirstConsumer`（有拓扑约束的存储必须用后者，且不能配 `nodeName`）

### 5.3 访问模式与 CSI ★

- [ ] 访问模式：RWO / ROX / RWX / `ReadWriteOncePod`，以及「访问模式不强制写保护」「RWO 的粒度是节点」这两个反直觉点
- [ ] CSI 架构：Controller 插件 + Node 插件，以及 sidecar 分工（provisioner / attacher / resizer / snapshotter / registrar）
- [ ] CSI 相关对象：`CSIDriver`、`CSINode`、`VolumeAttachment`、`CSIStorageCapacity`
- [ ] 一次「动态供给 + 挂载」的完整链路：调度 → 供给 → 绑定 → attach → mount
- [ ] in-tree → CSI 迁移（`CSIMigration`）的现状与选型含义

### 5.4 持久化闭环

- [ ] 卷扩容：`allowVolumeExpansion` + 驱动支持、只能扩不能缩、直接改 PV 容量会导致不再自动扩容
- [ ] 快照与恢复：`VolumeSnapshot` / `VolumeSnapshotContent` / `VolumeSnapshotClass`（CSI 专属，组件由发行版安装）
- [ ] 克隆与数据源：PVC 的 `dataSource` / `dataSourceRef`（快照恢复、卷克隆、volume populator）
- [ ] `VolumeAttributesClass`：改 IOPS / 吞吐等可变属性（1.34 GA、1.36 起稳定），需要驱动实现 `ModifyVolume`
- [ ] 卷健康监控（`CSIVolumeHealth`）与「只上报、不自动处置」的边界
- [ ] StatefulSet 的 `volumeClaimTemplates`、PVC 保留策略（`persistentVolumeClaimRetentionPolicy`）与扩容

**生产实践**
- `reclaimPolicy: Retain` + 手动备份，防止误删 PVC 丢数据；普通数据用 `Delete` 的默认类，关键数据用独立 `Retain` 的类
- 多可用区 / 本地盘的 StorageClass 一律 `WaitForFirstConsumer`，并把 `allowedTopologies` 收窄到业务实际部署的 zone
- 有状态服务不要用节点本地存储（`local` / `hostPath`），除非明确接受「节点故障即不可用、甚至丢数据」
- 卷快照 ≠ 备份：跨区域 / 跨集群归档 + 数据库原生备份 + 定期恢复演练，三层都要有
- 用 `ResourceQuota` 限制 `requests.storage` 与 PVC 数量，避免单个 namespace 吃光存储池
- 关注节点可挂载卷数上限：超限的 Pod 会卡在 `ContainerCreating`，与节点资源是否空闲无关

**要点自测**
- PV / PVC / StorageClass 三者的职责与作用域？绑定为什么是一对一？（注意 `Pending` 是 PVC 的状态，不是 PV 的）
- 删 Pod、删 PVC、删 StatefulSet、缩容副本之后，数据分别在不在？（取决于 `reclaimPolicy` 与 PVC 保留策略）
- 讲一次「PVC → 供给 → 绑定 → attach → mount」的完整链路，并指出 CSI 各组件的分工
- RWO / ROX / RWX / RWOP 的差别？为什么说「访问模式不是写保护」？
- 卷扩容的前提与限制？快照为什么不能替代备份？

## 阶段 6：安全

> **对应笔记**：[[06_安全]]

### 6.1 认证（AuthN）：你是谁

- [ ] 两类主体：用户与组**不是 API 对象**，ServiceAccount 是；`system:` 前缀是系统保留
- [ ] 认证方式：X.509 客户端证书（CN = 用户名、O = 组）、OIDC/JWT、Webhook token、Bootstrap token、匿名认证
- [ ] 结构化认证配置（`--authentication-config`，1.34 起稳定）与 `--anonymous-auth=false`
- [ ] ServiceAccount token 的三代演进：TokenRequest（1.22+）、projected volume 自动轮转、1.24 起不再自动创建长期 Secret token（门控 1.27 移除）
- [ ] `automountServiceAccountToken: false`、token 的 audience 与有效期、`kubectl create token --duration`
- [ ] 证书签发（CSR API 与 signer）与轮换（`kubeadm certs renew`）；证书无法吊销意味着什么

### 6.2 授权（AuthZ）：你能做什么

- [ ] 授权模型：多模块「任一允许即通过」、默认拒绝；apiserver 与 kubelet 的 `--authorization-mode` 默认值都是 `AlwaysAllow`
- [ ] RBAC 四件套：Role / ClusterRole / RoleBinding / ClusterRoleBinding，以及各自作用域
- [ ] `RoleBinding` 引用 `ClusterRole` 时权限只在该 namespace 生效；`roleRef` 不可变
- [ ] 规则字段：`apiGroups` / `resources`（含 `pods/log`、`pods/exec`、`serviceaccounts/token` 等子资源）/ `resourceNames` / `verbs` / `nonResourceURLs` / 通配符
- [ ] 内建角色：`cluster-admin` / `admin` / `edit` / `view` 与 ClusterRole 聚合机制
- [ ] **权限提升面 ★**：读或 list Secret、创建 Pod、创建 PV、`get nodes/proxy`、`escalate` / `bind` / `impersonate`、CSR 审批、`serviceaccounts/token`、改 Namespace 标签、改 webhook 配置
- [ ] Node 授权模块与 `NodeRestriction` 准入控制器
- [ ] 自检与排障：`kubectl auth can-i` / `--list` / `auth reconcile`、SubjectAccessReview

### 6.3 准入控制与策略

- [ ] 准入在链路中的位置：只作用于写请求，Mutating 在前、Validating 在后
- [ ] 内建准入控制器重点：NodeRestriction、PodSecurity、ServiceAccount、LimitRanger、ResourceQuota、CertificateSigning…
- [ ] 动态准入 Webhook：`failurePolicy` / `timeoutSeconds` / `sideEffects` / `matchConditions` / 选择器，以及「`Fail` + 后端不可用 = 集群被锁」的风险
- [ ] 声明式策略：`ValidatingAdmissionPolicy`（1.30 起稳定）与 `MutatingAdmissionPolicy`（1.36 起稳定）
- [ ] 策略生态选型：Kyverno / OPA Gatekeeper / Kubewarden，与内建方案的取舍

### 6.4 工作负载加固（PSS / PSA / SecurityContext）★

- [ ] Pod Security Standards 三档：`privileged` / `baseline` / `restricted`（累积关系）
- [ ] `restricted` 的具体要求：卷类型白名单、`allowPrivilegeEscalation: false`、`runAsNonRoot`、`seccompProfile`、`capabilities.drop: ["ALL"]`
- [ ] Pod Security Admission（1.25 起稳定）：`enforce` / `audit` / `warn` 三模式、`-version` 固定、exemptions、**enforce 只作用于 Pod**
- [ ] SecurityContext：Pod 级与容器级字段、`fsGroup` 与卷权限、`readOnlyRootFilesystem`
- [ ] Linux 内核加固：seccomp（`--seccomp-default`，1.27 起稳定）、AppArmor（1.31 起稳定）、SELinux、capabilities、User Namespaces（1.36 起稳定）、`privileged` 的破坏力
- [ ] 运行时隔离与网络隔离：RuntimeClass（gVisor / Kata）、NetworkPolicy 白名单（见阶段 4）

### 6.5 数据、凭据与供应链

- [ ] Secret 的本质：base64 不是加密、默认在 etcd 明文、1 MiB 上限、内置类型、`immutable`、env / 卷 / `subPath` 三种投递语义
- [ ] 静态加密：`EncryptionConfiguration` 与 `--encryption-provider-config`；`identity` 默认不加密；**KMS v2（1.29 起稳定）**，`kms` v1 自 1.28 起弃用
- [ ] 密钥轮换：第一个 provider 用于加密、所有 provider 用于解密；自动重载与「重写历史数据」
- [ ] 谁能读到 Secret：`list` 也等于读；能创建 Pod 就能读到该 namespace 的 Secret
- [ ] 外部密钥与云身份：Secrets Store CSI Driver、External Secrets、SealedSecrets、云 IAM 与 SA 绑定
- [ ] 镜像：digest 固定与 `imagePullPolicy` 默认规则、`imagePullSecrets`、扫描（Trivy）与签名（cosign）+ 准入校验
- [ ] 审计日志：`None` / `Metadata` / `Request` / `RequestResponse` 四级、log 与 webhook 后端、不要把 Secret 请求体写进日志
- [ ] 运行时检测（Falco 等）与「事前加固 + 事中检测」的分工

**生产实践**
- RBAC 最小权限：用 ServiceAccount 粒度，不用集群 admin 跑业务，任何人都不进 `system:masters`
- 关掉匿名访问（apiserver 与 kubelet），授权模式用 `Node,RBAC` / Webhook，不使用默认的 `AlwaysAllow`
- 业务 namespace 默认 `restricted` 档（先 warn/audit 观察再 enforce），并固定 `-version`
- Secret 走 KMS v2 静态加密 + 外部密钥管理，不写进镜像 / ConfigMap；审计日志不记录 Secret 请求体
- 准入策略先 audit/warn，再切 `Fail`；webhook 必须有多副本、短超时与失败预案
- 镜像私有仓库 + 扫描 + 签名 + digest 固定，配合准入校验来源
- 多租户记住边界：namespace 是软隔离，不可信租户要上节点池或独立集群
- 审计日志集中采集并告警：CSR 审批、webhook 配置变更、批量读取 Secret

**要点自测**
- 一次请求的五关是什么？401、403 与「被策略拒绝」分别出在哪一关？
- RBAC 四件套与作用域？`RoleBinding` 引用 `ClusterRole` 会发生什么？`roleRef` 为什么不可变？
- 哪些权限等于管理员？至少说出六条（读 Secret、建 Pod、建 PV、`nodes/proxy`、`escalate`/`bind`/`impersonate`、CSR 审批、SA token、改 Namespace 标签、改 webhook）
- PSS 三档的差别？`restricted` 到底要求哪几件事？PSA 三种模式与版本固定怎么用？
- ServiceAccount token 的三代演进？如何防止拿到 Pod 里 token 后越权？
- Secret 的保护来自哪几层？KMS v2 的静态加密怎么开、怎么轮换？

## 阶段 7：生产运维与可观测性

> **对应笔记**：[[07_生产运维与可观测性]]

### 7.1 可观测性

- [ ] 三条链路的分工：Metrics（趋势与告警）/ Logs（细节）/ Events 与 Audit（状态变化与人的动作）
- [ ] Metrics：Prometheus + Grafana；**metrics-server（Metrics API）与 kube-state-metrics（对象状态）的区别**
- [ ] 数据源全景：cAdvisor（kubelet 内）/ node-exporter / kube-state-metrics / 控制面 `/metrics`（读取需要 RBAC 授权）/ PSI 指标
- [ ] Logging：EFK / Loki，多行日志、结构化日志
- [ ] 容器日志的落点与轮转：stdout/stderr → `/var/log/pods`、CRI 格式、`containerLogMaxSize`（默认 10Mi）/ `containerLogMaxFiles`（默认 5）
- [ ] 采集架构：节点 DaemonSet agent / sidecar 流式转发 / sidecar 读文件三种路线
- [ ] 事件采集（**事件默认只保留 1 小时**）与审计日志（见 [[06_安全]]）
- [ ] Tracing：OpenTelemetry（结合微服务）
- [ ] 关键指标：USE（CPU/内存/磁盘/网络）、RED、Golden Signals；告警按「SLO → 服务 → 基础设施 → 平台对象」分层

### 7.2 高可用与可靠性

- [ ] Control Plane HA：多 master + 负载均衡的 apiserver
- [ ] 节点健康与心跳：Lease、`--node-monitor-grace-period`（默认 50s）、`not-ready`/`unreachable` 污点与 300s 默认容忍、node controller 标记 Unknown 后等 5 分钟才驱逐
- [ ] Node Condition（Ready / MemoryPressure / DiskPressure / PIDPressure / NetworkUnavailable）与 Node Problem Detector
- [ ] PodDisruptionBudget（PDB）：只保护自愿中断；`minAvailable` / `maxUnavailable`；`unhealthyPodEvictionPolicy`（1.31 起稳定，建议 `AlwaysAllow`）
- [ ] 节点维护：`cordon` → `drain`（走 Eviction API，尊重 PDB）→ 维护 → `uncordon`；drain 卡住的四类原因（PDB、裸 Pod、DaemonSet、本地存储）
- [ ] 集群升级：版本偏斜政策（kubelet 最多老 3 个小版本）、不跳小版本、控制面逐台 → 插件 → 工作节点逐台、**没有官方回滚**
- [ ] `etcd` 备份与恢复演练（**必须亲手做一次恢复**）：`etcdctl snapshot save` / `etcdutl snapshot status` / `etcdutl --data-dir ... snapshot restore`、停 apiserver 的顺序、密钥与 KMS 的可用性
- [ ] 备份分层：etcd 快照 + PV 数据 + 密钥材料 + 交付物；RTO / RPO 与业务对齐
- [ ] HPA（算法、容差 0.1、缩容稳定窗口 5 分钟、`behavior`）/ VPA（`Off` / `Initial` / `Recreate` / `InPlaceOrRecreate` / `InPlace`）/ KEDA / 集群层自动伸缩
- [ ] In-place Pod resize（1.35 起稳定）：不重建 Pod 调整 requests / limits

### 7.3 故障排查（生产手感）

- [ ] 排查套路：先定影响面（全部 / 单服务 / 单节点 / 单 Pod）→ 再定层级（控制面 / 节点 / 调度 / 网络 / 存储 / 应用）→ 收集证据（events、logs、metrics、审计）
- [ ] 三件套与纪律：`describe` + `logs --previous` + `get -o yaml`；**先取证据再动手，重启会毁掉现场**；把报障时间与发布/告警时间对齐（注意时区）
- [ ] 高频故障场景清单：Pod 一直 Pending / CrashLoopBackOff / ImagePullBackOff / OOMKilled / 节点 NotReady
- [ ] 熟练读事件时间线定位根因，而非重启了事
- [ ] 工具箱：`kubectl debug`（ephemeral container、`--copy-to`、`--share-processes`、`kubectl debug node/<node>`）、`crictl`、`journalctl -u kubelet`

**生产实践**
- 指标、日志、事件三条链路都要有，事件必须采集；按 SLO 分层告警，避免按 Pod 刷屏
- 控制面与 etcd 指标纳入监控（apiserver 延迟/5xx、etcd fsync、leader 变更），并监控证书到期
- 核心服务普遍配 PDB，并把 `unhealthyPodEvictionPolicy` 设为 `AlwaysAllow`；节点维护一次只动一台
- 升级前必备份 etcd、检查弃用 API、确认容量能扛住逐台 drain；变更过程盯核心 SLO
- etcd 快照加密、异地保存、定期校验；**每季度至少做一次恢复演练**并记录 RTO/RPO
- 用故障注入（Node 宕机、Pod 被杀、依赖超时）验证告警、PDB、自动伸缩与恢复流程真的有效

**要点自测**
- 用户说「服务很慢」你怎么从 K8s 视角排查？（资源 → 探针 → 网络 → 依赖 → 日志/指标）
- PDB 和 HPA 会冲突吗？PDB 保护什么、不保护什么？
- 节点要下线，drain 后还有 Pod 卡住不走，为什么？（PDB 限制、无控制器托管的裸 Pod、DaemonSet、本地存储）
- 节点失联后，Pod 多久才会被驱逐重建？（50s → 300s → 再等 5 分钟）
- metrics-server 和 kube-state-metrics 有什么区别？分别支撑什么场景？
- 集群升级的顺序与版本偏斜约束？为什么说"回滚 = 从 etcd 快照恢复"？
- etcd 恢复演练的完整步骤与常见误区？（忘备份密钥、快照同故障域、从不演练）

## 阶段 8：GPU / AI 场景扩展 ★（差异化亮点）

> **对应笔记**：[[08_GPU_AI场景]]

> **主机与网络数据面**：驱动与内核模块、PCIe/NUMA 拓扑、RoCE 无损网络、perftest 基线与 XID 硬件故障处理见 [[AI-Infra/00_简介|AI-Infra 大纲]]。

### 8.1 设备与资源模型

- [ ] Device Plugin 机制（Device Plugin API）：`Register` → `ListAndWatch` → `Allocate`，socket 在 `/var/lib/kubelet/device-plugins/`，kubelet 重启要重新注册
- [ ] 扩展资源的规则：整数、不可超卖（requests 与 limits 必须相等）、调度只看 requests、`ResourceQuota` 用 `requests.nvidia.com/gpu`
- [ ] NVIDIA GPU Operator 组件：驱动 / Container Toolkit / Device Plugin / DCGM Exporter / MIG Manager / NFD / GFD / Validator
- [ ] 两条部署路线：Operator 全托管驱动 vs 节点预装驱动 + `driver.enabled=false`；CDI 注入正在取代"专用 runtime"（RuntimeClass）
- [ ] 节点标签与亲和：GFD 的 `nvidia.com/gpu.product` / `gpu.count` / `gpu.memory` 等，以及时间切片 / MIG 带来的标签后缀
- [ ] 新方向 **DRA（Dynamic Resource Allocation，1.35 起稳定）**：`ResourceSlice` / `DeviceClass` / `ResourceClaim`，支持 CEL 设备筛选与设备共享；注意调度器暂不支持 DRA 抢占

### 8.2 GPU 复用

- [ ] 三种共享方式的对比：**时间切片**（可超卖、无显存与故障隔离）/ **MIG**（硬件切分、有隔离，需要机型支持）/ **MPS**（多进程共享上下文）
- [ ] 时间切片落地：ConfigMap（`sharing.timeSlicing.replicaCount`）+ ClusterPolicy 引用 + 节点标签；改完**必须重启 device plugin**
- [ ] 时间切片的两大副作用：`nvidia.com/gpu.product` 变成 `-SHARED`；**DCGM 无法把指标关联到容器**
- [ ] MIG：`migStrategy`（`none` / `single` / `mixed`）与资源名 `nvidia.com/mig-3g.20gb`；同一容器只能请求一种设备类型
- [ ] vGPU 与 MPS 的适用场景与代价

### 8.3 拓扑与 gang 调度 ★

- [ ] 多卡训练的三个难点：通信木桶效应、拓扑不匹配静默降速、必须整体启动（gang）
- [ ] 节点内拓扑：`nvidia-smi topo -m` 读 NVLink / PCIe / NUMA；`nvidia-smi nvlink -s`
- [ ] **Topology Manager**：策略 `none` / `best-effort` / `restricted` / `single-numa-node`，作用域 `container` / `pod`；依赖 CPU Manager、Memory Manager 与支持 `TopologyInfo` 的设备插件
- [ ] GPU 与 RDMA 网卡也要对齐到同一 NUMA / PCIe 域（GPUDirect RDMA）
- [ ] 节点间拓扑：以机架 / leaf / rail 打标签，用 Kueue 的 `Topology`+`ResourceFlavor` 或 Volcano 的网络拓扑感知调度
- [ ] **gang 调度**：Volcano（`PodGroup`、批调度器、binpack、DRF、队列借用与抢占）与 Kueue（`Workload` / `ClusterQueue` / `LocalQueue` / `ResourceFlavor`、公平共享、AdmissionCheck、DRA 集成）的定位差异
- [ ] 配套作业层：JobSet、Kubeflow Training Operator（`PyTorchJob` / `MPIJob`）、scheduler-plugins（coscheduling）、Ray on K8s

### 8.4 训练网络

- [ ] 两张网卡两个数据面：默认 CNI 管控制面 / Service / DNS；Multus + SR-IOV + RDMA CNI 管高速通信
- [ ] GPUDirect RDMA 与 `nvidia-peermem`：让网卡直读显存，前提是 GPU-网卡 PCIe / NUMA 亲和
- [ ] NCCL 排障环境变量：`NCCL_DEBUG`、`NCCL_SOCKET_IFNAME`、`NCCL_IB_HCA`、`NCCL_IB_GID_INDEX`、`NCCL_TOPO_DUMP_FILE`
- [ ] RoCEv2 无损网络（PFC / ECN）、MTU 与 GID 索引的网络侧配合
- [ ] 验证清单：`rdma link`、`ibv_devinfo`、nccl-tests（`all_reduce_perf`）、带宽基线

### 8.5 GPU 监控与成本

- [ ] DCGM Exporter（`:9400/metrics`，DaemonSet）与关键指标：`GPU_UTIL`、`FB_USED`、`MEM_COPY_UTIL`、`GPU_TEMP`、`POWER_USAGE`、`SM_CLOCK`、`XID_ERRORS`、`ECC_*`、`NVLINK_*`
- [ ] 告警项：XID 错误、温度、显存水位、利用率长期为 0 或 100%、GPU allocatable 变 0、队列排队时长
- [ ] 归因限制：时间切片下只有卡级指标；MIG 下要区分实例维度标签
- [ ] 成本视角：按命名空间 / 队列统计 GPU 时长、平均利用率与排队时长，驱动扩容与闲置回收

**生产实践**
- GPU 节点单独成池 + taint/toleration；驱动升级必须 drain 节点并准备回滚
- 训练默认独占，需要隔离的共享上 MIG，时间切片只用于容忍干扰的场景
- `ResourceQuota` + 队列（Kueue/Volcano）双层治理 GPU 配额，分布式训练必须 gang 调度
- 拓扑敏感作业约束到同一 NVLink 域 / 机架；`topologyManagerPolicy` 要实测调度成功率
- RDMA 打通纳入节点池交付标准，并定期跑 nccl-tests 基线；用 `NCCL_DEBUG=INFO` 确认走的是 RDMA 而不是 socket
- 需要按 Pod 归因 GPU 用量时不要开启时间切片

**要点自测**
- K8s 如何知道节点有几块 GPU？（Device Plugin：注册 → 上报 → 分配；扩展资源 `nvidia.com/gpu` 整数、不可超卖）
- 共享 GPU 的三种方式怎么选？时间切片为什么会影响监控归因？
- 多卡训练任务在 K8s 上的调度难点？（通信木桶效应、拓扑、gang、碎片、容错）
- Topology Manager 解决什么问题？策略与作用域怎么选？依赖哪些组件？
- RDMA 网络怎么落地？为什么"Service 能通"不能代表 RDMA 可用？
- GPU 监控看哪些指标？为什么"利用率"经常不够用？
- CUDA / RDMA / 调度 / 可观测串起来讲一遍（面试加分项）
