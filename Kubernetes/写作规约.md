# Kubernetes 写作规约

**本文件是本目录内容写作与结构的唯一依据。** `Linux/写作规约.md` 的写法可以借鉴，但不作为本目录的规则——两个领域的知识对象不同（见第三节），规则必须各自成文。

已废弃、不再恢复：`Kubernetes/99_笔记模板.md`、`Kubernetes/AGENTS.md`、`Kubernetes/00_简介.md`（旧学习大纲）。本目录的写作依据、结构表、层归属矩阵、验收清单与同步清单全部收在本文件；仓库总览见根 `README.md`。

## 一、定位与读者

- 定位：面向运维 / SRE 的生产判断力——把"生产现场真正会被追问的点"和"现场真正会遇到的故障"对齐。验收标准是**能不能在事故现场用出来**，不是能不能复述概念，也不是能不能通过面试。
- 读者：会基本 Shell 与 `kubectl`，用过 `systemctl`、`top`、`docker`，但没有系统学过分布式控制面；容器与编排的机制由本目录负责补。
- **不复述读者画像与阅读顺序**：各章、各篇都不写"这一章写给谁""需要什么基础""读完能回答什么"。
- **不出现应试口径**：不写"脱稿讲 3~5 分钟""错题本""正确率""D+1/D+3""面试加分"。需要限定推演时写"限时推演"，需要说追问时写"值班口径"。

## 二、知识体系怎么组织

### 主线：收敛链

Linux 的知识对象是**一台机器上的一个机制**（内核怎么处理它），证据在 `/proc`、`sysctl`、man。Kubernetes 的知识对象是**一条声明在分布式系统里怎么被收敛成事实**，证据在 API 契约、`status` 与 `conditions`、事件、控制器日志、节点侧工具。

因此每章内部统一跟**一条收敛链**走：

> 声明（API 契约：字段与准入把它变成什么）→ 谁在 watch 它 → 收敛动作（控制器 / 调度器 / kubelet 各做什么）→ 可观测事实（`status` / `conditions` / 事件）→ 代价与失败形态

每个领域都有自己的"一条声明"：工作负载是 Pod 声明，网络是 Service / EndpointSlice 声明，存储是 PVC 声明，安全是 Subject 与 Rule 声明。

**由这条主线派生的两条硬规定**：

1. **"体系"层每章至多一篇，且必须是这条链的完整展开**；压缩成多篇短篇会让链条断裂。
2. **一个动作牵动几处，就要在几处分别给判据**。例如改一次 `requests` 会同时牵动调度、QoS 档位、驱逐顺序、配额、HPA/VPA 五处——分布在不同的章，每一处都要有自己的判据，不能只在一处写。

### 层的判定：一句话该落在哪一层

沿收敛链问四句，问到哪句就落在哪层：

| 问句 | 落层 |
| --- | --- |
| 这句话在讲**声明本身**（字段契约、准入把它变成什么、API 语义），或**为什么必须这么设计** | 原理 |
| 在讲**谁 watch 它、按什么顺序收敛、`status` 怎么从一件事变成另一件事** | 体系 |
| 在讲**用哪把工具看哪个字段、怎么读、先看什么** | 实操 |
| 在讲**看起来是这个原因、其实是那个原因** | 判例 |
| 在讲**上限配在哪一层、交什么产物、和别的领域怎么接** | 治理 |

每层的**排除项**（越界即拆篇）：

| 层 | 只负责 | 不负责 |
| --- | --- | --- |
| 原理 | 机制为什么存在、代价与边界、声明层的不变量 | 命令与工具清单、处置动作、现场案例 |
| 体系 | 一条收敛链的完整展开、字段的读法、横向关系的收口 | 工具清单、制度设计、参数怎么配 |
| 实操 | 用哪把工具、读哪个字段、怎么读、故障排查顺序、交付物 | 机制推演、制度设计 |
| 判例 | 现象 → 误判 → 判据 → 出处 | 完整流程（流程归实操） |
| 治理 | 上限配在哪一层、产物模板、行业通行做法、与其他领域的接口 | 机制原理（原理归原理篇） |

### 章内构成与篇数

- 篇目顺序固定：`原理 → 体系 → 实操 → 判例 → 治理`；命名形如 `NN_层_关键词.md`，叙事不写进文件名。
- **不规定每层篇数，也不规定每章篇数**：按内容需要写。一章内原理可以是一篇也可以是六篇；某层若确实没有有出处的素材，**整层不写**，并在该章 `00_导读与知识地图.md` 的篇目索引里留一行说明，免得读者以为是漏写。
- **顺序与层名不得变**。层名只有这五个：`原理` / `体系` / `实操` / `判例` / `治理`。
- 例外：第 12 章收口章不套分层——它的对象是读者脑中的模型而不是集群里的对象，固定用「知识地图 + 总纲 + 接缝矩阵 + 实战链 + 复述链 + 附录 + 自检清单」，具体篇目按内容需要。

### 章的导航篇

每章 `00_导读与知识地图.md` 只有两块：

1. **知识地图**：本章的收敛链（一条主线的时间轴）与横向关系；
2. **篇目索引**：本章各篇 + 每篇一句话。

**术语速查只收本章新引入的术语**，不当全库术语表。**故障现场定位表放在本章最后一篇（判例或实操）里**，不放导读——读者拿到现象时已经在排障语境里，而且这样不会与第 10 章的排障方法重复。

## 三、写作形态

- **行文用学术报告语体**：写完整句，主语与谓语齐全，句间用"因此 / 由于 / 若 / 反之 / 同时"这类显式逻辑连接；不把结论压缩成电报式的名词短语堆叠。
- **不用比喻与黑话代替机制本名**：不写"抽象在哪里漏水""三本账""横切线""吃光""兜底"这类需要额外解释的说法，把机制、占用与关系按本名写出来（例："节点上的三类存储占用：只读层、可写层、日志与卷"）。自检口径：把任意一句单独摘出来，读者不需要再问"这是什么意思"。
- **比喻不承担判据**：任何结论都要落回字段名、单位、数值或错误文本。
- **不使用跨章引用**：正文与导航篇都不写"见第 N 章""与本篇同一机制"，也不写跨章的篇名。正文里只允许**排除式划界**：用一句"这不是本篇负责的内容"划清范围，**不给方向**。需要读者知道"别处还有一块"时，靠章节目录名与他自选阅读解决。
- **不使用 wikilink**（`[[...]]`）。引用块只用于呈现逐层演进中被剖析的回答。
- **不出现等级与技能编号**（`L1/L2`、`M1–M8`、`S1–S8`、`T0–T4`）。
- **不讨论文档自身结构**：不写"这篇讲什么""必须先读什么""本文将分三部分""30 秒速览""怎么用这篇笔记"。
- **章号不进正文**：正文里不出现"阶段 N""第 N 章"这类指路。
- **给出数值就要给出读法**：凡让读者看某个字段，必须同时写清五件事——是什么、单位、判据、与谁同看、看到它转向哪一步。
- **输出样例只展示格式**：贴命令输出必须声明"数值仅示意、不代表你的环境"。
- 术语首次出现给中文解释 + 英文原词，缩写展开（CRI、CNI、CSI、QoS、PDB、PSA、SSA、GVK、CRD、DRA、CEL、MIG、MPS…）。
- 代码块语言标签按实际内容取（`bash` / `yaml` / `text` / `mermaid`）；命令注释写 `# 验证：…`，不写只有 `#` 的注释行。
- 单位一律 MiB/GiB 与秒；默认值必须带版本与现场取值方式。
- 破坏性操作标"只在可丢的实验集群"；只读观测标"生产集群上也可以做"。
- **「第一反应不要做什么」是每篇必备句**。

## 四、事实纪律

### 版本口径

- **全库对照当前稳定版 1.37 与同主版本的官方文档与上游源码**；默认值、字段口径、版本门都以它们为准。本口径写在这里一次，各章正文不重复声明版本基线。
- **版本门必须写成阶段式**，并给出处。例：`ipvs` 的路线是"1.35 弃用并告警 → 1.37 引入 `KubeProxyIPVS` 门控 → 1.40 默认关闭 → 1.43 锁定为不可再启用 → 1.46 删除门控"。只写"1.43 移除"会让人误判动手时机，这是本次全库审计里出现的一类错误。
- **默认值要写清它是不是默认值、作用在什么范围**。例：`readOnlyRootFilesystem` 是**加固建议**，不是 Pod Security Standards `restricted` 档的判定项——策略校验的字段与加固建议的字段常常不是一伙的，写混就是事实错误。
- **不凭记忆写默认值**。取不到就写"未确认"，并说明还缺什么才能确认。

### 实验环境与实测纪律

- **能查文档就不实测；实测必须标环境与版本。** 本目录的实测基线：单机容器用 Docker + containerd 环境；集群用 kind（多节点）跑 1.37；网络插件与 CSI 按需（如 Cilium 或 Calico + local-path 供应器）。集群形态、插件与版本随篇注明。
- 与目标集群同一主版本取文档（当前 1.37）：老版本文档里的默认值已经变过，`latest` 描述的是尚未进入发行版的东西。
- **上机结果不等于普遍结论**：命令输出与集群版本、发行版、CNI/CSI、节点规格强相关。没出现预想结果优先怀疑环境不匹配，而不是先改结论。实机结果写进正文必须写清环境，并说明可能只在该环境成立。
- 客观事实（字段名、路径、命令输出格式、版本门控）可以也应当上机核对。
- 临时脚本、原始输出、草稿报告**不入库**：放在临时工作目录里，用完即删，正文不引用它们。

### 边界：哪些内容不属于本库

| 内容 | 归哪 |
| --- | --- |
| GPU 驱动、内核模块、PCIe/NUMA 拓扑、RoCE/IB 无损网络、perftest、NCCL 排障、DCGM 指标明细、XID 判读、掉卡处置 | AI 基础设施主题域（主机与网络数据面） |

## 五、高发错误清单

本次全库审计（对旧 `01`–`09` 九篇）确认的错误类型，重写时逐条对照：

1. **只写终点版本**：把"1.43 移除"写成结论，漏掉中间四段阶段门（见第四节）。
2. **策略字段与建议字段混为一谈**：把 `readOnlyRootFilesystem` 这类加固建议写成 PSS `restricted` 的判定项。
3. **跨篇口径打架**：同一件事两处写、且数值或字段名不一致（时间切片字段 `replicaCount` vs `resources[].replicas`；"改一个驱逐阈值其余变 0" 与 `mergeDefaultEvictionSettings` 的可覆盖行为）。
4. **篇内自相矛盾**：同一篇的表格与正文给出两套口径。
5. **计数与自述打架**："三道设计题"与四道、"八个阶段"与十行。
6. **归属错位的低配重复**：把更深的专业篇章的内容在本章重讲一遍且讲得更浅。
7. **机制归因错位**：把观察值安到错误的开关上（"恢复时会把错过的任务全部补上"——实际最多补一次）。
8. **文档自身结构声明**：目标、关联复习、30 秒速览、怎么用这篇笔记、回到路线图。
9. **给出数值不给读法**：只写"看某个字段"，没写是什么、单位、判据、与谁同看、转向哪一步。
10. **输出样例未声明仅示意**，或把自己的实测值当通用结论。
11. **破坏性操作缺边界**：没有实验集群限制、没有回滚步骤、没有上限控制。
12. **术语类别混淆**：准入控制器与准入插件、命令与内核接口文件、CRD 与内置对象、扩展资源与原生资源。
13. **缩写未展开**、**跨章 wikilink**、**篇末缺边界句**。
14. **用比喻或黑话代替机制本名**：把"节点上的三类存储占用""贯穿全链的横向关系"写成"三本账""横切线"，或把机制的失效情形写成"抽象在哪里漏水"。判断口径是读者是否需要先解码措辞才能理解结论。

## 六、定稿自检

每篇写完立即逐条走：

1. 只有一个一级标题；除本章 `00_导读` 外没有 wikilink；引用块只出现在逐层演进处；
2. 篇末有「第一反应不要做什么」；
3. 正文无章号、无跨章指路、无"这篇讲什么"式声明、无应试口径；
4. 术语首次出现有中文解释 + 英文原词，缩写已展开；
5. 每个被引用的字段都给了"是什么 / 单位 / 判据 / 与谁同看 / 转向哪一步"；
6. 引用块与代码块里的数值都声明了"仅示意"，或写明了环境；
7. 每个版本门都是阶段式且给出处；默认值带版本与现场取值方式；
