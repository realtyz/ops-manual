# 对象、事件与控制面观测

## 1. 问题与工具的对应关系

集群侧的观测工具分为三类，它们的分工经常被混用：

| 想知道什么 | 用什么 | 关键点 |
| --- | --- | --- |
| 对象现在是什么状态 | 列出 + 详细描述 | 描述里的"状态摘要"是给人看的拼装结果；判据在对象自身的字段里 |
| 对象的完整当前形态 | 导出完整对象 | 这是唯一能看到全部字段、条件、归属、finalizer 的入口 |
| 为什么会这样 | 事件 | 事件带有原因短语与时间戳，**默认约 1 小时就过期** |
| 谁改过它 | 审计记录 | 只有开启了审计才有；它回答"谁在什么时候做了什么" |
| 控制器跟上没有 | 对象的两个代数标记 | 期望代数与"处理到第几代"是否相等 |
| 这个字段归谁 | 对象的字段归属 | 冲突排查的判据 |
| 控制面本身是否承受压力 | 入口组件的指标 | 请求量、排队、限流、错误率；**不是业务对象的问题** |
| 组件自身报告的问题 | 组件日志 | 控制器、调度器、节点代理的健康与错误 |
| 节点上实际发生了什么 | 节点侧工具 | 这一层不在本章范围内，需要换视角取证 |

**一条纪律**：先读对象与事件，再改动控制面。控制面组件的日志量很大，并且重启组件会丢掉一部分现场（指标计数器归零、内存中的队列丢失）。

**另一条纪律**：读操作（列出、描述、查看、读取指标）可以在生产集群上执行；写操作（改对象、删对象、改配置、重启组件）要按变更流程走，并先记录当前状态作为验收基线。

## 2. 这些字段的读法

| 看什么 | 是什么 | 单位 | 判据 | 与谁同看 | 看到它转向哪一步 |
| --- | --- | --- | --- | --- | --- |
| 期望代数 vs 处理代数 | 期望态被改动了几次 / 控制器处理到第几代 | 整数 | 相等才说明控制器看过最新期望 | 条件的时间戳、控制器日志 | 长期不等 → 转去查控制器，不查业务对象 |
| `conditions[]` | 一组带时间戳的布尔判断 | 结构数组 | 四个字段一起看：类型、状态、原因、翻转时间；**翻转时间只在状态变化时更新** | 事件时间线、观测态字段 | 翻转时间很旧 → 状态确实稳定；刚刚翻转 → 找同一时刻的事件与日志 |
| 观测态里的阶段字段 | 高层概括 | 枚举 | 它是概括而非完整状态机；与更细字段冲突时以细的为准 | 容器状态、条件 | 概括与实际不符 → 以容器状态与事件为准 |
| 容器状态与退出信息 | 每个容器的等待/运行/终止原因 | 结构体 | 反复重启时**先取原因再取退出码** | 上一次运行的日志 | 原因指向环境或额度 → 转节点侧；原因不明 → 看应用日志 |
| `metadata.resourceVersion` | 并发控制令牌 | 不透明字符串 | 只能比对相同或不同 | 冲突报错里的当前值 | 出现冲突 → 重读、重算、重提 |
| `metadata.deletionTimestamp` | 删除请求时间 | 时间 | 非空表示已请求删除但未完成 | finalizer 列表 | 长时间不动 → 看还剩哪个 finalizer |
| `metadata.finalizers[]` | 删除前的待办项 | 字符串数组 | 列表非空就删不掉 | 负责它的控制器是否在运行 | 列表不变 → 控制器没有执行动作，不是入口组件的问题 |
| `metadata.ownerReferences[]` | 属主引用 | 结构数组 | 决定级联；**不能跨命名空间** | 级联策略、属主是否还存在 | 属主已删除而从属还在 → 看策略与引用 |
| `managedFields` | 字段归属 | 结构数组 | 冲突时报出"这个字段归谁" | 审计记录、写入者的日志 | 同一字段持续冲突 → 职责边界要重划 |
| 事件的原因短语 | 组件对"为什么这样"的短句 | 字符串 | 它是分流依据：不同短语指向不同环节 | 事件的时间与计数 | 同一条事件反复出现 → 计数增长说明一直在重试 |
| 事件的计数与首末时间 | 同一原因发生了多少次、从何时到何时 | 整数 / 时间 | 计数大而时间跨度长，即为持续性问题；计数小而集中，即为一次性事件 | 该对象的变更历史 | 停止增长 → 问题已不再发生（但根因可能仍在） |
| 入口组件的请求指标 | 请求量、排队时长、限流与错误计数 | 计数 / 秒 / 分位 | 关注"被限流的请求"与"排队时长"两类 | 业务侧的超时现象 | 出现限流 → 先看是谁在大量请求，再谈扩容 |
| 审计记录 | 谁在什么时候对什么做了什么 | 记录 | 有记录才有结论；未开启时不能反推 | 对象的字段归属 | 需要回答"谁改的"却无审计 → 只能看归属与写入者日志 |

## 3. 采样纪律与集群基线卡

集群侧的观测同样要**同口径、带时间戳、至少两次、留原始输出**。一次"对象不正常"的观察不能说明它正在恶化；只有两次同口径的读数才能给出趋势。

一个集群该留的基线卡，字段固定为：

| 字段 | 取值来源 | 为什么要有 |
| --- | --- | --- |
| 版本与版本偏斜 | 各组件的版本接口 | 组件之间允许的版本差有政策约束，是跨版本行为差异的第一来源 |
| 控制面拓扑与存储形态 | 部署方式与配置 | 决定可用性与恢复方式 |
| 存储的体积、压缩与快照状态 | 存储自身的指标与运维记录 | 空间告警会导致写入被拒，属于最高优先级 |
| 入口组件的副本数与前置负载均衡方式 | 部署配置 | 决定客户端指向哪里、单点在哪里 |
| 入口组件的限流与优先级配置 | 生效配置 | 决定压力下哪些请求会先被牺牲 |
| 准入钩子与聚合扩展服务的清单 | 集群配置 | 它们是写路径上的强依赖，需要知道有哪些、是否高可用 |
| 审计与事件的保留配置 | 生效配置 | 决定"能回溯多久"，直接决定故障复盘的边界 |
| 一次典型写请求与一次典型调谐的耗时基线 | 同口径多次测量 | 没有基线就无法判断"变慢了" |

**只读观测在生产集群上也可以执行**；改动控制面配置、重启组件、清理阻塞的对象属于变更，必须先在非生产环境确认后果，并留下前后两次同口径读数作为验收。

## 4. 常见故障与排查方向

### 4.1 对象删除受阻

现象：删除请求发出之后，对象长时间仍然存在，命名空间整体也停在"终止中"。

排查顺序：

1. **确认是"请求删除未完成"还是"根本没有删"**：看删除时间戳是否非空。
2. **看还剩哪些 finalizer**：删除受阻的原因只可能是 finalizer 没有被移除。
3. **找负责它的控制器**：控制器是否在运行、日志里有没有报错、它依赖的外部资源是否可达。
4. **看命名空间层面**：如果命名空间停在终止中，就找出里面剩余的对象；问题在它们身上，不在命名空间本身。

一份合格的回答应当包含以下要素：**结论**（阻塞在哪个 finalizer、谁该移除它）、**依据**（删除时间戳 + finalizer 列表 + 对应控制器的日志行）、**边界**（只有一个对象还是该命名空间全部）、**动作**（恢复控制器 / 解决外部依赖 / 在确认外部资源状态后移除 finalizer）。

### 4.2 声明已提交，但系统似乎没有响应

现象：对象存在且看起来写对了，但没有任何后续动作（从属对象没有建出、没有绑定、观测态不更新）。

排查顺序：

1. **确认对象真的更新了**：看对象版本与期望代数是否递增。
2. **确认控制器同步到了**：比较期望代数与处理代数；长期不等说明问题在控制器这一侧。
3. **看负责这个对象的控制器是否在运行**：它是否崩溃重启、是否被限流、日志里有没有处理失败。
4. **看后续动作是否被策略拦截**：控制器创建从属对象时同样要过准入，配额与策略都可能让它失败。
5. **看入口组件是否在限流**：压力下低优先级的请求会被排队甚至拒绝，表现为"组件都在运行，但没有组件推进后续动作"。

一份合格的回答应当包含以下要素：**结论**（断在哪个环节）、**依据**（版本与代数、控制器状态、限流或策略的痕迹）、**边界**（只影响这类对象还是全局）、**动作**（恢复控制器 / 调整配额与策略 / 处理请求压力）。

### 4.3 某个字段的值发生意外变化

现象：一个字段的值在一段时间里反复变化，或者被人改动之后又被改回去。

排查顺序：

1. **看字段归属**：这个字段归谁写，用以判断是"有别的写入者"还是"有人在手工修改"。
2. **看审计**：谁在什么时候改过它；没有审计时，只能看写入者的日志与对象的历史版本线索。
3. **找同字段的写入者**：自动伸缩、控制器、准入插件、外部运维脚本都可能是。
4. **定职责边界**：确认这个字段本该由谁负责，然后让另一个写入者不要再修改它。

一份合格的回答应当包含以下要素：**结论**（字段归谁、被谁改）、**依据**（字段归属 + 审计或写入者日志）、**边界**（只有一个对象还是同类对象普遍）、**动作**（划清职责 / 显式接管 / 停止某个写入者）。

### 4.4 创建或更新直接被拒

现象：请求返回失败，响应里有原因文本；对象根本没有被创建。

排查顺序：

1. **看状态码**：`401` 认证问题、`403` 权限或被策略拒绝、`409` 版本冲突、`422` 字段不合法。
2. **看响应体的原因**：被策略拒绝时会带策略名与失败条件；字段不合法时会指出字段路径。
3. **区分"权限不够"与"策略不允许"**：用权限自查手段确认这个身份能否做这个动作；若能，则问题在策略。
4. **看是不是集群级对象**：需要集群范围的权限，或者作用在集群级对象上时，命名空间内的授权不够。

一份合格的回答应当包含以下要素：**结论**（在第几关被拒、为什么）、**依据**（状态码 + 原因文本 + 权限自查结果）、**边界**（只影响这个身份还是所有身份）、**动作**（补权限 / 改对象以符合策略 / 调整策略并留出观察期）。

## 5. 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 用客户端的"状态摘要"当作判据 | 那是给人读的拼装结果；判据在对象的字段里 |
| 只看状态码不看原因文本 | `403` 的两种来源，处置方向完全不同 |
| 把事件当作长期证据 | 事件默认只保留约 1 小时，过期之后"没有看到"不等于"没有发生" |
| 出现故障先重启控制面组件 | 会丢掉现场（计数器归零、内存队列丢失），并且掩盖根因 |
| 在集群侧回答"机器上还剩什么" | 那需要节点侧视角 |
| 无法修改就整体覆盖对象 | 会覆盖其他写入者的字段 |
| 为解除阻塞手工删 finalizer | 跳过了清理逻辑，外部资源残留 |
| 不做变更前后两次同口径读数 | 无法区分"恢复了"与"暂时看起来正常" |

## 6. 要点自测

**问：为什么"描述"不能作为写自动化规则的依据？**

答：它把多个来源拼成给人看的摘要，字段名与层级都不保证稳定；同一条信息在别处可能有更精确的字段。因此自动化的判据应当来自对象的字段本身。

**问：判断"控制器跟上没有"，最直接的判据是什么？**

答：比较对象上的期望代数与"控制器处理到第几代"。两者相等，说明控制器至少看过最新期望；长期不等，说明问题在控制器或它的依赖上，而不在对象本身。

**问：事件为什么不能当长期证据？**

答：事件的默认保留期约 1 小时。故障复盘如果在几小时之后开始，"看不到事件"只说明它已经过期，不能推出"当时没有发生"。因此长期判断要用指标与对象自身的字段。

**问：`403` 的两种来源怎么区分？**

答：一种是没有被授权做这个动作，另一种是通过了授权但被准入策略拒绝。判据是响应体里的原因文本（策略拒绝会带策略名与失败条件），以及用权限自查手段确认这个身份能否做该动作；若能，则问题在策略。

**问：容器反复重启时，为什么先取原因再取退出码？**

答：退出码只是一个数字，同一个数字可以来自进程主动退出、被信号杀死或被资源限制终止；退出原因把类别直接给出来，它决定下一步是查应用、查节点额度还是查启动配置。

**第一反应不要做什么**：不要用描述里的摘要写告警；不要只看状态码；不要把过期的事件用来推出"没有发生过"；不要在没取证据前重启控制面组件；不要在集群侧回答节点侧的问题；也不要为了解除对象阻塞而手工删 finalizer。
