# 高频误判

十二条判例都取自值班与复盘中的真实处境，每一条都按同一套字段展开：**场景 → 常见误判（以及它为什么看起来成立）→ 判据（读哪个字段、什么数值或趋势、什么条件下结论会变）→ 一句话结论 → 出处**。这些字段的读法在实操篇第 2 节与体系篇第 4 节。

## 1. 「创建命令返回成功，服务就该起来了」

**场景**：发布脚本提交了一份声明并收到成功返回，因此脚本继续执行下一步；几分钟之后业务报错，而脚本的记录里全部是"成功"。

**常见误判**：把"声明被接受"当成"状态已经收敛"。这一判断之所以看起来成立，是因为返回码确实表示成功；但写入存储成功只是收敛链的第三个环节，其后还有扇出、补全、绑定、执行与回流这五个环节。

**判据**：判断是否生效要依据观测态，而不是依据返回码。最短的核对路径是依次确认：对象是否已经更新（比较版本与期望代数），控制器是否跟上（比较期望代数与处理代数是否相等），它所需要的从属对象是否齐备，绑定字段是否已经写入，节点侧是否确实在运行。**条件会变**：如果对象已经更新而期望代数长期不相等，那么问题在控制器这一侧；如果期望代数相等而节点侧没有对应对象，那么问题出现在绑定之后的环节。

**一句话结论**：返回成功只能说明"声明已经进入存储"；要判断是否生效，必须看观测态。

**出处**：Kubernetes 官方文档中关于控制器与声明式 API 的章节（期望状态与实际状态的分离）。

## 2. 「对象卡在删除中，是入口组件出问题了」

**场景**：删除一个对象之后，该对象一直显示为终止中；值班重启入口组件，问题依旧存在。

**常见误判**：把"删不掉"当成 API 层的故障。这一判断之所以看起来成立，是因为删除请求确实是发给入口组件的；但删除的语义是"先标记、等清理、再移除"，阻塞发生在 finalizer 上，而负责移除 finalizer 的是控制器。

**判据**：先看删除时间戳是否非空，以确认对象处于"已请求删除但尚未完成"；再列出还剩哪些 finalizer；然后检查负责这些 finalizer 的控制器是否在运行，以及它所依赖的外部资源是否可达。**条件会变**：如果整个命名空间都停在终止中，那么问题在命名空间内部的对象上；如果只有一个对象阻塞，那么问题在该对象所引用的外部依赖上。

**一句话结论**：对象删不掉，其原因几乎总是清理责任方尚未完成动作，而不是入口组件发生了故障。

**出处**：Kubernetes 官方文档中关于 finalizer 与命名空间终止的章节。

## 3. 「`kubectl` 显示的状态就是对象的状态」

**场景**：值班写了一条告警规则，用于匹配客户端输出中的某个状态词，该规则时而准确、时而不准确。

**常见误判**：把客户端的显示值当成字段值。这一判断之所以看起来成立，是因为屏幕上显示的确实是那个词；但那个词是由多个字段拼装出来供人阅读的，字段本身可能使用别的名字，也可能并不属于这个对象。

**判据**：自动化的判据必须取自对象自身的字段，即观测态的阶段字段、容器状态与条件列表。**条件会变**：如果同一信息同时出现在两处（例如阶段与条件），应以粒度更细的字段与事件为准；当两者互相矛盾时，应先怀疑终端输出的拼装方式，而不是先怀疑对象。

**一句话结论**：显示值供人阅读，字段供机器读取；因此告警规则必须落在字段上。

**出处**：Kubernetes 官方文档中关于对象状态与条件的章节；客户端输出的字段映射说明。

## 4. 「`Pod` 一直 `Pending`，先看资源够不够」

**场景**：一个 `Pod` 长时间处于 `Pending`，值班随即去核对节点的剩余资源。

**常见误判**：把"没有运行"等同于"资源不足"。这一判断之所以看起来成立，是因为 `Pending` 最常见的解释确实是"尚未被安排到节点上"；但 `Pending` 只是一个高层概括，它的成因至少有三类：调度范围的问题（没有合适的节点），绑定之后的前置问题（所依赖的对象尚未就绪），以及镜像与沙箱层面的准备问题。

**判据**：先看**绑定字段是否为空**。若为空，则属于调度范畴，应当查明它为什么没有被安排（约束、资源、优先级）；若非空，则说明调度已经完成，问题出现在其后的环节，应当转去检查节点侧以及它所依赖的对象。**条件会变**：如果同类对象全都在等待，那么多半是集群范围的问题（容量或节点就绪）；如果只有一个对象在等待，则应先看它自身的约束与依赖。

**一句话结论**：`Pending` 只说明"还没有运行起来"，第一个动作是查看绑定字段，而不是先看资源。

**出处**：Kubernetes 官方文档中关于 Pod 生命周期阶段与调度概念的章节。

## 5. 「事件里没有报错，说明这一步没发生过」

**场景**：一次故障在数小时之后进行复盘，值班查询事件，发现关键时间段内没有任何记录，因此判断"当时没有异常"。

**常见误判**：把"查不到"当成"没有发生"。这一判断之所以看起来成立，是因为事件确实记录了组件对异常的解释；但事件默认只保留约 1 小时，复盘时它早已过期。

**判据**：事件的判据只在**它的保留窗口内**成立。若需要长期回溯，依据应当是对象自身的条件与时间戳、指标计数器（注意它是累计值，需要取差值）以及审计记录（前提是审计已经开启且保留时间足够）。**条件会变**：如果条件的时间戳显示当时确实发生过翻转，而指标在同一时段也出现异常，那么"事件里没有记录"就只是保留期造成的结果。

**一句话结论**：事件能够解释原因，但只在一个有限的窗口内可用；长期结论必须落在指标、条件与审计上。

**出处**：Kubernetes 官方文档中关于事件与保留策略的说明；审计策略配置文档。

## 6. 「这个字段的值变来变去，肯定是有人在捣乱」

**场景**：某个字段的值被改回之后又发生变化，值班因此认为是有人进行了手工干预。

**常见误判**：把"值在变化"归因于"有人在修改"。这一判断之所以看起来成立，是因为在场的人确实修改过一次；但对象上可能同时存在多个自动写入者（控制器、自动伸缩、准入插件、外部同步工具），它们各自只负责一部分字段。

**判据**：先查字段归属，确认这个字段登记为归谁写入；再查审计记录（若已开启）以确认实际动作；若归属指向某个控制器或插件，则到它的日志中查找同一时刻的写入。**条件会变**：如果归属显示为"人"（例如运维工具所使用的写入者标识），那么确实属于人工或脚本干预，此时应当修改的是流程，而不是代码。

**一句话结论**：值反复变化时应先查字段归属；把原因归为人为误操作，是代价最高的一种假设。

**出处**：Kubernetes 官方文档中关于服务端应用与字段管理的章节。

## 7. 「加了权限还是没有权限，说明授权没生效」

**场景**：给某个身份补了一条权限之后，操作仍然失败，因此判断"授权系统存在问题"。

**常见误判**：把所有的拒绝都归因于授权。这一判断之所以看起来成立，是因为失败确实发生在"被拒绝"这一语境中；但拒绝可能来自另外两道关卡：认证（身份根本没有被识别出来）与准入（对象不符合策略）。

**判据**：区分三个来源，即认证失败（身份不成立）、授权失败（允许的动作中没有这一条，包含作用范围不正确的情形）与准入拒绝（对象被策略挡下，原因文本中带有策略信息）。用"这个身份能否执行这个动作"的自查手段确认授权；若自查通过而操作仍然失败，则问题在准入这一侧。**条件会变**：如果自查显示允许，并且原因文本指向策略，那么补充权限永远不会产生作用。

**一句话结论**：拒绝有三种来源，判据是响应体中的原因文本与权限自查，而不是"再补一条权限"。

**出处**：Kubernetes 官方文档的认证、授权与准入控制章节。

## 8. 「改了标签只是改了个注释」

**场景**：为便于统计，批量给一批对象补上标签；随后发现部分服务不再把这些对象纳入流量，或者有对象被别的工作负载"接管"并改变了配置。

**常见误判**：把标签当成注解。这一判断之所以看起来成立，是因为两者都是键值对，都写在元数据中；但标签是**选择器**的依据，而注解不参与选择。

**判据**：在改动标签之前，先确认有哪些选择器会与之匹配，包括服务与端点的关联、工作负载与副本的关联，以及亲和与打散规则。判据是"这批对象是否会被别的选择器纳入或排除"。**条件会变**：如果改动的是注解，那么拓扑不受影响；如果改动的是选择器本身，那么该动作等价于一次拓扑变更，需要按变更流程执行。

**一句话结论**：标签决定关系，注解只是备注；因此改动标签就是改动拓扑。

**出处**：Kubernetes 官方文档中关于标签与选择器、注解的章节。

## 9. 「命名空间是安全边界，隔离租户够了」

**场景**：多租户平台把每个业务方放在一个命名空间里，并认为租户之间已经实现隔离。

**常见误判**：把作用范围当成隔离边界。这一判断之所以看起来成立，是因为命名空间确实把对象、配额与权限范围分开了；但隔离强度取决于权限与网络策略是否真的按这个边界配置。默认情况下，不同命名空间之间的网络往往是连通的，集群级对象也完全不受命名空间限制。

**判据**：要回答"两个租户能否互相影响"，需要分别确认：网络策略是否默认拒绝并逐条放行，权限是否把集群级对象排除在外，配额是否覆盖了计算与存储资源，以及是否存在被跨租户使用的共享集群级资源（节点、存储类、集群角色）。**条件会变**：如果租户需要运行不可信负载，那么仅有这些措施还不够，需要更强的工作负载隔离机制。

**一句话结论**：命名空间是作用范围，隔离需要依靠权限、网络策略与配额共同实现。

**出处**：Kubernetes 官方文档中关于命名空间、网络策略与多租户的章节。

## 10. 「改了对象没生效，把它删掉重建就好了」

**场景**：某个改动没有按预期生效，值班删除对象并重建，问题暂时消失，但过一段时间之后再次出现。

**常见误判**：把"重建"当成修复手段。这一判断之所以看起来成立，是因为重建确实让对象回到了期望形态；但如果问题来自控制器没有跟上、策略拦截了后续动作，或者某个自动写入者反复把值改回，那么重建只是重置了现场。

**判据**：在重建前后各取一次同口径的读数，观察它是否会再次偏离。如果再次偏离，说明存在一个持续的写入者在把状态改回去，此时应当检查期望代数与处理代数、字段归属，以及策略与配额。**条件会变**：如果属于"存量对象没有被新策略覆盖"这一类问题，那么重建恰好是生效手段；这时需要追问的是"为什么没有对存量对象做统一处理"。

**一句话结论**：重建只能重置状态，无法消除持续把状态改偏的原因。

**出处**：Kubernetes 官方文档中关于控制器调谐与声明式 API 的章节。

## 11. 「升级之后行为变了，一定是新版本有 bug」

**场景**：集群升级之后，某个功能的行为与之前不同，值班按缺陷处理，执行回滚或提交工单。

**常见误判**：把版本之间的行为差异当成缺陷。这一判断之所以看起来成立，是因为"升级之前是好的"；但 API 版本有明确的生命周期（弃用、默认关闭、移除），每一阶段的现场表现都不同；此外也可能是配置键位随版本发生变化，导致设置静默失效。

**判据**：先确认这个 API 版本处于生命周期的哪一段，再看自己的清单中使用的是哪个版本，以及组件之间允许的版本差。判据是"弃用与移除的阶段"加上"现场生效配置"，而不是"以前能够运行"。**条件会变**：如果确认该版本处于转正之后的稳定阶段，并且配置没有被静默改写，此时才值得按缺陷进行排查。

**一句话结论**：应先分清"行为按政策发生了变化"与"实现出现了缺陷"，两者的处置方式完全不同。

**出处**：上游 API 版本演进与弃用政策文档；各组件的版本偏斜政策说明。

## 12. 「控制面响应慢，先重启组件试试」

**场景**：集群的操作开始变慢甚至超时，值班重启入口组件，短暂恢复之后再次变慢。

**常见误判**：把"慢"当成组件故障。这一判断之所以看起来成立，是因为重启确实能够带来短暂缓解；但入口组件是请求的必经之路，变慢的常见原因是请求侧的压力（大量低优先级请求、激进的监听客户端、失控的控制器循环）或者存储侧的延迟，而不是组件本身损坏。

**判据**：先看入口组件的请求指标，包括请求速率、排队时长、被限流的请求数，以及存储侧的提交延迟。判据是"请求总量与被限流的比例"和"存储延迟是否上升"。**条件会变**：如果指标显示请求量正常而存储延迟大幅上升，那么方向在存储一侧；如果请求量异常并且出现限流，那么方向在请求来源；重启只会清空计数器，使下一次判断失去基线。

**一句话结论**：入口组件变慢时应先看请求侧与存储侧的压力，因为重启会把现场清除。

**出处**：Kubernetes 官方文档中关于 API 优先级与公平性、请求限流、以及控制面容量规划的章节。

## 要点自测

**问：这十二条误判有没有共同的成因？**

答：可以归为四类。第一类是**把起点当成终点**：把提交成功、把事件中没有记录、把显示值当成结论。第二类是**用错关卡或视角**：把准入拒绝当成权限问题，在集群侧回答节点侧的问题。第三类是**把元数据当成备注**：标签、命名空间、重建这些动作都会改变对象之间的关系或者现场状态。第四类是**用重置代替定位**：重启、重建、手工删除 finalizer。

**问：为什么判据要写成"读哪个字段 + 什么条件下结论会变"？**

答：因为同一个现象在不同条件下指向不同的根因。只说"看绑定字段"只是一个线索；说清"绑定为空属于调度范畴，非空则转到节点侧"才是可以迁移的判断。

**第一反应不要做什么**：不要用返回码与显示值判断状态；不要用已经过期的事件推出"没有发生"；不要为了解除阻塞而手工删除 finalizer；不要用重启与重建代替定位；也不要把命名空间当成安全边界。
