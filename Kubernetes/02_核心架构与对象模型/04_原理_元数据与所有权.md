# 元数据与所有权

## 1. 问题背景：对象之间的关系只能用字段表达

这套系统既不提供外键，也不提供级联约束，同样不对对象之间的引用做完整性检查。因此，对象之间的任何关系都只能用字段来表达，而每一类关系都需要配一套约定：

| 需要表达的关系 | 使用什么字段 | 由谁使用 |
| --- | --- | --- |
| "这几个对象属于同一组"，即一个可以被选中的集合 | 标签与选择器 | 服务与端点之间的关联、工作负载与副本之间的关联，以及亲和与打散规则都依赖它 |
| "这个对象是由那个对象创建的" | 所有者引用 | 垃圾回收与级联删除依赖它 |
| "删除之前必须先完成一件事" | finalizer | 需要清理外部资源的控制器依赖它 |
| "这个字段由谁负责" | 字段归属记录 | 人、控制器与自动伸缩等多个写入者需要共存 |
| "这一条不是给人看的" | 注解 | 工具用它保存状态、来源信息与集成说明 |

"所有权"这个词在本章里指两件不同的事，因此必须分开讨论：**对象的所有权**指谁跟着谁一起被删除，**字段的所有权**指这个字段归谁写入。两者所使用的字段、背后的机制以及故障表现都不相同。

## 2. 标签与选择器：关系靠"当前长什么样"决定

标签是键值对，选择器则是一段表达式，用来选出满足条件的对象。以下三条是现场口径：

- **关系是计算出来的，而不是被记录下来的。** 一个工作负载依靠选择器找到它的副本，因此一旦改动副本的标签，该副本就会脱离原有的关系，成为无人管理的对象。反之，若误给一个对象加上某个工作负载的标签，它就可能被那个工作负载接管，并被"按期望"改写。
- **选择器既可以写成等值匹配，也可以写成集合表达式**，但不同对象对两者的支持范围并不相同。若在不支持集合表达式的对象上书写集合语法，该语法可能被静默忽略，也可能直接被拒绝，具体以该对象的字段约定为准。
- **标签是可变的，而注解不能被用于选择。** 凡是参与选择的字段，都不适合用来存放频繁变化的状态，否则对象之间的关系就会反复变化。

## 3. 删除不是立即抹除，而是一个有步骤的过程

删除一个对象的完整语义包含以下步骤：

1. 客户端发出删除请求时，服务端**设置删除时间戳**，而不是立刻把对象删除；
2. 若对象上存在 finalizer，则**对象不会被移除**，直到每一个 finalizer 都被移除为止；
3. 只有当所有 finalizer 都被清空之后，对象才真正从存储中消失。

由此可以得到以下几条判据：

| 现象 | 判据 | 转向哪一步 |
| --- | --- | --- |
| 对象请求删除后长期仍然存在 | 查看删除时间戳是否非空，并确认 finalizer 列表中还剩哪几项 | 若仍剩 finalizer，应查找负责该项的控制器，而不是怀疑入口组件 |
| finalizer 长期不消失 | 检查负责清理的控制器是否在运行，以及它的日志与事件中是否记录了失败 | 若控制器没有运行，应先恢复控制器；若外部依赖不可达，应先解决依赖 |
| 删除请求发出之后又希望追加 finalizer | 系统不允许这样做：请求删除之后不能再新增 finalizer | 因此只能在执行删除之前，就把需要清理的事项声明完整 |
| 希望强制删除已经阻塞的对象 | 移除 finalizer 会跳过清理逻辑，**外部资源会残留** | 应先确认外部资源的状态，再决定是否移除 |

**级联删除**由所有者引用驱动，共有三种策略，它们的差别在于哪个对象先消失：

| 策略 | 行为 | 适用场景 |
| --- | --- | --- |
| 后台级联（默认） | 属主先被删除，从属对象随后被清理 | 常规场景；删除请求的响应速度快 |
| 前台级联 | 从属对象先被标记删除并处理完毕，属主最后消失 | 要求"全部清理完成才算删除完成"的场景 |
| 孤立 | 从属对象被保留下来，只断开它与属主之间的引用 | 需要保留产物时，例如留下副本以便排查 |

**有一条性质容易被忽略**：级联**跨命名空间不成立**。所有者引用只能存在于同一个命名空间之内，集群级对象之间则遵循另一套约定；因此，跨命名空间的关系需要自行用 field/label 维护，删除操作不会自动扩展到这些关系上。

## 4. 命名空间的终止是同一套语义的集合版

删除一个命名空间并不是"一次把其中的对象全部删掉"，而是一个分阶段的过程：命名空间首先进入**终止中**状态，随后其中的对象被逐个清理，并且同样遵守各自的 finalizer，直到全部清理完成之后，命名空间本身才消失。由此可以推出三条结论：

- **若命名空间阻塞在终止中状态，原因一定出在某个对象上**：应当找出尚未清理的对象以及它们所持有的 finalizer，而不是反复重发删除请求。
- **处于终止中的命名空间通常不再接受新对象**，创建请求会被拒绝；这也解释了维护期间"为什么无法创建对象"。
- **命名空间不是安全边界**。它只是配额、权限与策略的作用范围；不同命名空间之间的隔离强度，取决于权限与网络策略是否配置到位。若把它当作安全边界，就会形成这类集群中最常见的一种过度信任。

## 5. 字段归属：多个写入者共存的代价与解法

同一个对象总是被多方修改：人修改期望态，控制器写入观测态，自动伸缩修改副本数，别的控制器补充注解。这种多方协作依靠**字段归属**来维持秩序。

| 方式 | 依据 | 判据 | 代价 |
| --- | --- | --- | --- |
| 客户端应用 | 客户端把上一次提交的内容记录在注解中，用它完成三方合并 | 注解中的内容就是该客户端所认为的"上一次我提交过什么" | 别的写入者修改过的字段可能被误删，注解本身也可能被写坏 |
| 服务端应用 | 服务端记录每个字段归属于哪一个写入者 | 对象中的字段归属列表 | 若与别的写入者争夺同一个字段就会冲突，需要显式接管 |

以下三条是现场口径：

1. **冲突是一种保护机制，而不是故障。** 冲突说明"你正在修改的字段归属于别人"；正确的处理方式是**让原主修改**，或者**显式接管**，而不是绕过冲突去覆盖整个对象。
2. **接管只是把责任取了过来，并没有删除那个写入者。** 被接管的写入者在下次提交时仍会再次冲突；从长期看，要么调整职责边界，不再让两个组件写同一个字段，要么让该写入者放弃这个字段。
3. **字段归属与"谁最后写入"是两件事。** 归属回答的是"这个字段由谁负责"，而最后写入者只表示时间上最近的一次写入；要判断"这个值是谁改的"，应当查看归属，并配合审计记录。

## 6. 抽象模型的适用边界

1. **对象之间的关系由标签计算得出，因此改动标签就等同于改动拓扑。** 在生产环境中批量修改标签或者批量修改选择器，都等价于一次拓扑变更。
2. **删除是异步的，并且可能被阻塞。** 当看到对象依然存在时，应先分清它属于"已经请求删除但尚未完成"，还是"根本没有删"。
3. **finalizer 既是一种能力，也是一项负担。** 它保证清理动作不会被遗漏，但一个无法正常工作的控制器足以让整个命名空间的删除被阻塞。
4. **所有者引用不能跨越命名空间。** 跨命名空间的生命周期关系需要自行维护。
5. **字段归属使并发写入变得可控，但它要求职责边界清晰。** 若两个组件写同一个字段，最终必然出现该字段的值在两边反复变化的情况。
6. **命名空间是一种作用范围，而不是隔离边界。** 隔离强度来自权限与策略，并不来自这个对象的存在。

## 常见误解

| 常见说法 | 事实 |
| --- | --- |
| 「删掉对象就等于它不存在了」 | 若对象上存在 finalizer，删除请求只会把它标记为待删除；清理完成之后它才真正消失 |
| 「命名空间阻塞是入口组件的问题」 | 一定是因为其中还有对象或对象的 finalizer 尚未清理完成 |
| 「把 finalizer 手工删掉就能解决阻塞」 | 确实可以删掉，但这样会跳过清理逻辑，外部资源会残留 |
| 「副本的标签随便改没事」 | 标签决定关系；改动标签可能让对象脱离控制，或被别的控制器接管 |
| 「字段冲突说明集群有问题」 | 冲突是并发保护的正常表现，它说明这个字段归别人写 |
| 「命名空间之间天然隔离」 | 命名空间只是配额与权限的作用范围；隔离需要依靠权限与网络策略来实现 |
| 「所有者引用能跨命名空间」 | 不能；跨命名空间的生命周期关系需要自行维护 |

## 要点自测

**问：对象的所有权与字段的所有权，分别解决什么问题？**

答：对象的所有权由所有者引用表达，它解决的是"谁跟着谁一起被删除"，并决定级联删除的行为；字段的所有权由字段归属记录表达，它解决的是"谁负责写这个字段"，使多个写入者能够共存而不互相覆盖。这两套机制所使用的字段、判据与故障表现都不相同。

**问：若一个对象阻塞在删除过程中，应当如何定位？**

答：首先确认删除时间戳是否非空，以判断它属于"已经请求删除但尚未完成"；其次查看还剩哪些 finalizer；最后检查负责这些 finalizer 的控制器是否在运行，以及是否报出错误。结论几乎总是"还有某个责任方尚未完成清理"，而不是入口组件的问题。

**问：级联删除的三种策略，差别是什么？**

答：后台级联先删除属主，随后清理从属对象；前台级联先处理从属对象，属主最后才消失；孤立策略只断开引用，并保留从属对象。它们分别对应的现场需求是：需要快速返回、需要确知已经删除干净，以及需要保留产物。

**问：为什么"批量改标签"在生产上算一次拓扑变更？**

答：因为对象之间的各种关系，包括服务与工作负载的关联、端点的关联以及亲和与打散规则，都是依靠选择器计算出来的。改动标签可能使对象脱离原有关系而成为无人管理的对象，也可能把本不该纳入的对象纳入进来。因此它改变的是拓扑，而不是注释。

**问：字段冲突应当如何处理？**

答：首先确认这个字段的职责归属。若它本来就应当由另一个组件写入，就调整自己，不要去写这个字段；若确实需要接管，就应当显式接管，并让原写入者不再写这个字段。绕过冲突去整体覆盖，会静默删除别人的字段，这是最糟糕的处理方式。

**第一反应不要做什么**：不要把"删除请求已经发出"当成"对象已经不存在"；不要把命名空间的阻塞归因于入口组件；不要为了解除阻塞而手工删除 finalizer，却不去确认外部资源的状态；不要随意修改生产对象的标签与选择器；也不要把命名空间当成安全边界。
