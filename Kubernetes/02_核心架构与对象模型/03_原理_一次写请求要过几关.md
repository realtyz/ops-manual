# 一次写请求要过几关

## 1. 只设一道关卡会漏掉什么

入口组件如果只做一件事——把收到的对象写进存储，任何能够连上它的人都按自己的请求执行——三类问题会同时出现：

| 问题 | 具体表现 |
| --- | --- |
| 无法回答"你是谁" | 任何能够连上端口的人都可以修改集群中的任何对象 |
| 无法区分"能读"与"能改" | 需要查看状态的人与需要修改配置的人持有同一份权限 |
| 无法在入口处拦截危险对象 | 对象一旦被写入，就只能依靠事后清理，而清理动作本身也可能被滥用 |

解决办法是**把检查拆成多道关卡，使每道关卡回答一个不同的问题，并具有各自的失败语义**：

| 关卡 | 只回答 | 失败时对外表现 |
| --- | --- | --- |
| 传输与认证 | 这个请求是谁发出的 | `401` |
| 授权 | 这个身份是否被允许执行这个动作 | `403` |
| 变更准入 | 这个对象需要被补上或缺省哪些内容 | 拒绝时 `403` |
| 结构校验 | 这个对象是否符合该类型的字段约定 | `422` |
| 校验准入 | 这个对象在既定策略下是否被允许存在 | `403`（策略判定） |
| 落库 | 提交时携带的版本是否仍然一致 | `409` |

**关键性质：这些关卡是叠加的，而不是相互替代的。** 通过认证并不意味着拥有权限，拥有权限也不意味着对象合法，对象合法也不意味着策略允许。因此对于"为什么被拒绝"这个问题，第一个要回答的永远是**在哪一关被拒绝**。

## 2. 写请求走一遍

```mermaid
flowchart LR
  C["客户端"] -->|"1 建立连接与认证"| AUTH["认证：你是谁<br/>失败 401"]
  AUTH --> AUTHZ["授权：你被允许吗<br/>失败 403"]
  AUTHZ --> MUT["变更准入<br/>补缺省值 / 注入字段"]
  MUT --> SCH["结构校验<br/>失败 422"]
  SCH --> VAL["校验准入<br/>策略判定，失败 403"]
  VAL --> W["写入存储<br/>版本冲突 409"]
  W --> R["返回对象<br/>此刻只在存储里"]
```

以下几处必须区分清楚：

- **准入只作用于写请求。** 读请求会经过认证与授权，但不经过准入；因此"这个对象为什么没有被加上注解"不能在读请求中寻找原因。
- **变更准入在校验准入之前执行。** 系统先让插件补上缺省值并完成注入，再判断结果是否合法与合规。若顺序反过来，就会出现"策略校验的对象是尚未补全的对象"这种情况。
- **准入拿到的可能还不是最终形态。** 多个变更插件按顺序执行，后一个插件看到的是前一个插件修改过的对象；因此"我提交的值被修改了"是常态。
- **校验失败会给出两种不同的文本**：字段不符合类型约定属于结构校验（`422`）；被策略或钩子拒绝属于准入判定（`403`，响应体中有原因）。这两种情况的排查方向完全不同。
- **"被拒绝"与"钩子没有响应"是两种失败。** 显式拒绝返回 `403`，响应体里带策略或钩子给出的原因；钩子调用失败返回 `500`（内部错误），原因文本里带钩子名与调用错误。前者要改对象或改策略，后者先修钩子自身的可用性。

## 3. 各关卡的判据

| 看什么 | 是什么 | 单位 | 判据 | 与谁同看 | 看到它转向哪一步 |
| --- | --- | --- | --- | --- | --- |
| HTTP 状态码 | 请求被拒的类别 | 整数 | `401` 表示认证未通过；`403` 表示认证通过但未被允许（包括被准入拒绝）；`409` 表示版本冲突；`422` 表示对象不合法；`500` 表示准入钩子调用失败（超时、连不上），不是策略判定 | 响应体中的原因文本 | 401 应当查凭证；403 应当查权限与策略；422 应当查字段；409 应当重读对象之后重新修改；500 应当查钩子自身的可用性 |
| 请求身份 | 本次请求以谁的名义发出 | 用户名 + 组 + 附加信息 | 用户不是对象，而服务账号是对象；应当查看审计记录中的身份字段 | 授权判定与准入判定 | 身份不对 → 先查凭证来源，再查是谁在使用这份凭证 |
| 授权判定 | 这个身份对这个动作的结论 | 允许 / 拒绝 | 多个授权模块按配置顺序依次检查，其中任何一个给出允许或拒绝，结论立即生效并停止检查；全部模块都不表态时，默认结论是拒绝 | 判定所使用的角色与绑定，以及生效的授权模块顺序与清单 | 被拒 → 先用"我能不能做这个动作"的自查手段确认，再看绑定的范围 |
| 变更准入的结果 | 对象被哪些插件改成了什么 | 对象差异 | 应当通过差异比对判断"谁修改了我的字段"，而不是靠猜测 | `managedFields` 的字段归属 | 字段被修改 → 去查找管理该字段的组件或插件 |
| 校验准入的判定 | 策略是否放行、原因是什么 | 结构体（放行 / 拒绝 + 原因） | 拒绝的原因中通常包含策略名与失败条件 | 该策略的配置与它的日志 | 拒绝 → 先确认是哪一条策略，再决定是修改对象还是修改策略 |
| 钩子的超时与失败策略 | 钩子不响应时会发生什么 | 秒 / 枚举 | 失败策略决定钩子调用失败（超时、连不上、响应无法解析）时的行为：`Fail` 时写请求失败，`Ignore` 时放行。`timeoutSeconds` 默认 `10` 秒，允许范围 1–30 秒，现场取值以生效配置为准 | 钩子的副本数与可用性 | 返回 `500`（内部错误）且原因文本带"failed calling webhook"与钩子名 → 先修钩子自身的可用性；返回 `403` 才是策略判定，应改对象或改策略 |
| 版本冲突 | 提交时带的版本已经落后 | 整数（状态码 409） | 冲突只说明有人先行修改过，并不说明哪一方的修改是正确的 | 对象当前版本 | 重读、重算、重提 |

## 4. 为什么关卡必须都在入口组件里

一个自然的问题是：为什么不把这些检查分散到各个组件中去？原因是**任何绕过入口的写入都会跳过全部关卡**：

- 存储在整个集群中只由入口组件直接访问，其目的就是使关卡无法被绕过；
- 各组件的缓存、控制器与节点上报都只能通过入口组件改写状态，因此"是谁修改的"总能够被记录下来（审计）；
- 反之，直接修改存储，或者通过绕过入口组件的状态改写入口（例如运行时自带客户端提供的写操作）去修改状态，会使集群进入"对象合法但无人校验"的境地；这也是排障时**不能用绕过接口的手段去修改状态**的原因。

**代价**：入口组件成为所有请求的必经之路，因此它的可用性与延迟直接决定了集群的响应能力；这也是限流与优先级机制必须存在的理由。

## 5. 抽象模型的适用边界

1. **认证通过不等于授权通过，授权通过也不等于对象合法。** 这三件事的失败语义不同，排查方向也不同。
2. **准入可能改写提交的对象。** 提交的值不一定是最终值；若要查明"是谁修改的"，必须依靠差异比对与字段归属。
3. **拒绝的原因文本比状态码包含更多信息。** 若只看 `403`，排查会在"权限不够"与"策略不允许"两种判断之间反复摇摆。
4. **读请求不经过准入。** "为什么读到的对象与策略要求不一致"这个问题本身问错了方向。
5. **关卡本身构成可用性风险。** 外部钩子不可用时，按照失败策略，它可能使所有相关的写请求失败并返回 `500`；因此策略组件的副本数、超时与失败预案属于它自身的可用性设计。
6. **审计记录的是入口处的事实。** 它能够显示"谁在什么时候修改了什么"，但看不到组件内部的因果关系；若要回答"为什么"，还需要查看对象的状态、事件与组件日志。

## 常见误解

| 常见说法 | 事实 |
| --- | --- |
| 「有权限就能创建这个对象」 | 权限只通过一道关卡；还要通过结构校验与策略校验 |
| 「`403` 就是权限不够」 | 该请求也可能被准入策略拒绝；应当查看响应体中的原因 |
| 「提交的字段值就是最终值」 | 变更准入会补缺省值并执行注入；最终值应当以对象的实际返回为准 |
| 「读不到是因为策略拦住了」 | 读请求不经过准入；应当先查看授权与命名空间范围 |
| 「钩子挂了只影响新对象」 | 按照失败策略，它可能使相关写入全部失败，这属于可用性事件 |
| 「绕过接口直接把状态改对更方便」 | 这等于跳过全部关卡，并且会使缓存与存储长期不一致 |

## 要点自测

**问：一次写请求依次经过哪几关？各自失败时看到什么？**

答：传输入口与认证（`401`）、授权（`403`）、变更准入（补缺省值与注入）、结构校验（`422`）、校验准入（被策略拒绝时返回 `403`，并在原因中说明）、写入存储（版本冲突 `409`）。读请求只经过认证与授权，不经过准入。

**问：为什么变更准入必须在校验准入之前？**

答：因为校验的对象应当是"补全之后的形态"。系统先补上缺省值与注入，再判断对象是否合法与合规；若顺序反过来，就会出现"策略校验的是尚不完整的对象"，导致两份判定结论互相矛盾。

**问："我提交的值被改了"该怎么查，而不是怎么猜？**

答：先查看对象实际返回的最终值，再依据对象中记录的字段归属信息确认这个字段归谁管理，以及哪些准入插件会写入这个字段。字段归属是判据，而"我觉得应该是它修改的"不是判据。

**问：为什么外部准入钩子不可用会导致大批请求失败？**

答：因为钩子的失败策略决定了它在不响应时的行为：一种是把相关请求全部拒绝，另一种是放行。前者意味着集群外的一个组件成为写路径上的强依赖。因此它的副本数、超时、失败策略与应急预案都属于集群自身的可用性设计。

**问：为什么"直接去改存储里的状态"是绝对禁止的动作？**

答：因为存储是唯一的权威，而全部关卡都位于入口组件上。绕过入口的写入既不受校验，也不产生审计记录，因此缓存与权威之间会长期不一致；此后任何"看似正常"的对象都可能在下一轮调谐中被覆盖。

**第一反应不要做什么**：不要把 `403` 一律当成权限问题；不要用"我提交了什么"代替"对象最终是什么"；不要指望读请求会被策略拦住；不要在钩子不可用时通过重启业务来"恢复"；也不要采用任何形式的绕过入口去修改状态。
