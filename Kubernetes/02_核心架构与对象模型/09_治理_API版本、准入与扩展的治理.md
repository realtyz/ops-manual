# API 版本、准入与扩展的治理

## 1. 这些上限分别配在哪一层

本节要处理的问题是："某项控制在配置上应当落在哪一层"与"实际由谁在配置"经常对不上。同一个效果可能由清单、集群级对象、入口组件配置、外部策略组件，甚至一个团队的口头约定决定。因此，本节的全部内容就是把各项控制按层归位。

| 想控制的 | 配在哪一层 | 影响范围 | 谁负责 | 改了要重新验证什么 |
| --- | --- | --- | --- | --- |
| 清单里用哪个 API 版本 | 发布物（清单与模板） | 使用该清单的所有环境 | 发布流程负责人 | 该版本处于生命周期的哪一段，以及转换之后字段语义是否发生变化 |
| 对象命名与标签约定 | 设计约定 + 策略（可选自动校验） | 该集群的全部对象 | 平台方与业务方共同约定 | 选择器是否会因此改变拓扑，以及统计口径是否仍然成立 |
| 删除保护（哪些对象必须挂清理项） | 各控制器自身的实现 | 该控制器管理的对象 | 控制器/扩展的提供方 | 清理逻辑所依赖的外部资源是否可达 |
| 级联删除的默认策略 | 调用方或控制器设置 | 单次删除 | 执行删除的人 | 从属对象是跟着一起删除、先删除还是保留 |
| 作用范围（命名空间级还是集群级） | 对象类型本身 | 该类型的全部对象 | 类型定义方 | 权限与配额能否覆盖到它 |
| 谁能注册新类型、改策略配置 | 权限配置 | 整个集群 | 平台方 | 这类权限按管理员级对待 |
| 准入策略的内容与强度 | 策略对象（集群级） | 该策略选中的对象 | 策略负责人 | 存量对象不会被回查，因此应当先观察、后强制 |
| 外部策略组件的可用性 | 该组件的部署 | 写路径上的相关请求 | 策略负责人 | 副本数、超时、失败策略、应急预案 |
| 审计与事件的保留 | 入口组件配置与存储 | 整个集群 | 平台方 | 故障复盘能回溯多久 |
| 请求压力与优先级 | 入口组件的限流配置 | 整个集群 | 平台方 | 压力下哪些请求先被牺牲 |
| 版本偏斜的容忍度 | 升级流程与政策 | 整个集群 | 平台方 | 各组件之间的版本差是否在政策允许范围内 |

**两条归属原则**：

1. **能用清单表达的，不要依赖集群侧保底。** 使用哪一个 API 版本、对象叫什么名字、标签如何设置，都属于发布物的内容；如果依靠入口组件或策略在集群侧代为纠正，同一份清单在不同环境中的行为就会不一致。
2. **能自动校验的约定，不要只写进文档。** 命名与标签这类约定如果只写在文档中，几个月之后必然有人违反；因此要么用策略进行自动校验（先观察），要么接受它会被违反。

## 2. 交付产物

### 2.1 集群基线卡

每个集群各一张，字段固定如下：

| 字段 | 取值来源 | 交付时要给出 |
| --- | --- | --- |
| 各组件版本与版本偏斜 | 组件版本接口 | 具体版本，以及组件之间的差值是否处于政策允许的范围之内 |
| 控制面拓扑与存储形态 | 部署配置 | 存储节点数、快照去向、最近一次恢复演练时间 |
| 入口组件副本数与前置负载均衡 | 部署配置 | 客户端指向哪里，以及单点位于何处 |
| 限流与优先级配置 | 生效配置 | 压力下哪些请求先被牺牲 |
| 写路径上的外部依赖清单 | 集群配置 | 准入钩子与聚合扩展服务，各自的副本数与失败策略 |
| 审计与事件的保留配置 | 生效配置 | 可回溯的时间窗口 |
| 集群级对象的现状 | 实际查询 | 有哪些集群级资源被多租户共用 |
| 典型写请求与典型调谐的耗时基线 | 同口径多次测量 | 两个基线值，用于判断响应是否变慢 |

### 2.2 升级前的 API 与配置检查单

| 检查项 | 要回答的问题 |
| --- | --- |
| 清单里用到的 API 版本 | 它们分别处于生命周期的哪一段，以及是否存在处于弃用或默认关闭阶段的版本 |
| 存量对象的存储版本 | 是否存在只在旧版本写入、需要迁移的对象 |
| 自定义资源的版本与转换 | 转换链是否完整，以及存储版本是否需要推进 |
| 组件之间的版本差 | 版本差是否处于政策允许的范围之内，以及升级顺序是什么 |
| 配置键位 | 是否存在随版本迁移的键，以及生效值是否与另一侧一致 |
| 写路径上的外部依赖 | 其版本与入口组件是否兼容 |
| 回滚方式 | 回滚到哪个版本、需要多久、代价是什么 |

### 2.3 字段职责澄清记录

本记录用于处理"某个字段反复变化"这一类问题，其字段如下：

| 字段 | 要回答的问题 |
| --- | --- |
| 字段路径 | 是哪个对象的哪个字段 |
| 当前归属 | 字段归属显示该字段归谁写入 |
| 实际写入者 | 审计记录或写入者日志中记录的实际动作 |
| 应有的归属 | 按设计，这个字段应当由谁负责 |
| 处置动作 | 停止某个写入者 / 显式接管 / 改设计 |
| 验证方式 | 处置之后如何确认不再反复 |

### 2.4 删除受阻的记录

| 字段 | 要回答的问题 |
| --- | --- |
| 对象与时间 | 哪个对象、什么时候发出删除 |
| 剩余清理项 | 还剩哪些 finalizer，以及它们各自归谁负责 |
| 责任方状态 | 负责的控制器是否仍在运行，以及失败原因是什么 |
| 外部依赖 | 清理逻辑所依赖的外部资源是否可达 |
| 处置动作 | 恢复控制器 / 解决依赖 / 在确认外部资源状态后移除清理项 |
| 影响面 | 只有一个对象，还是该命名空间整体（或其他同类对象） |

## 3. 与其它领域的接口

本节只写接口，不替对方做决定：

- **网络与存储**：本章只讲"对象与请求链路"这一层的机制；网络策略与存储供给属于各自的领域，因此本章只在需要表达关系（标签、选择器、所有者）时使用它们的概念。
- **安全与多租户**：认证方式、权限模型与工作负载加固的具体配置，属于承载策略的那一层；本章只回答"关卡位于链路的哪几段、失败语义是什么"。
- **生产运维**：变更流程、升级顺序以及备份与恢复演练的编排属于运维那一层；本章提供的是它所需要的检查单与基线字段。
- **容器与运行时**：节点上"声明如何变成进程"这一过程属于制品与运行时那一层；本章只讲到"绑定字段被写入"与"节点回报观测态"为止。
- **扩展的提供方**：自定义资源的版本与转换、控制器的调谐逻辑以及聚合服务的可用性，由提供方负责；本章只明确"集群提供了哪些机制，以及代价由谁承担"。

## 4. 一个治理场景

**背景**：在多租户集群中，一个业务命名空间无法删除，该状态已经持续三天；值班尝试过重复发起删除、重启入口组件，均无效果。本次要求给出可复用的结论。

**按本节的做法走一遍**：

1. **先分类，不要先执行处置动作**：先确认命名空间的删除时间戳非空（即属于"已请求未完成"），再列出其中剩余的对象。
2. **定位到具体对象与清理项**：在剩余的对象中，有一个对象带有 finalizer，而负责它的控制器属于某个已经下线的扩展组件。
3. **判断处置方向**：控制器已经不在集群中，因此这个清理项不会被任何组件移除；但清理逻辑涉及集群之外的资源（对象存储中的一个桶），如果直接删除清理项，外部资源就会残留。
4. **确认外部状态之后再执行处置**：先确认外部资源是否仍然存在、是否需要保留，然后在"移除清理项"与"恢复一个只负责清理的控制器"这两条路径中选择一条。
5. **交出产物**：
   - 一份**删除受阻的记录**（对象、清理项、责任方、外部依赖、处置与影响面）；
   - 更新**集群基线卡**里的"写路径上的外部依赖清单"与"集群级对象现状"；
   - 在**升级前的 API 与配置检查单**里补一条：卸载扩展组件时必须确认没有存量的清理项引用它；
   - 如果决定恢复控制器，附一份**字段职责澄清记录**，写清此后谁负责这个类型的清理。
6. **验收**：命名空间删除完成之后，回头检查"是否还有其他对象引用这个已经下线的组件"，把同类隐患一次性排查掉，而不是等到下一次再出现同样的长时间停滞。

**这个场景的要点**：删除受阻的问题包含两层：机制层（仍有清理项存在）与责任层（没有责任方负责这个清理项）。如果只解决机制层，外部资源会残留；如果只解决责任层，问题会重复发生。本章的治理价值就在于把这两层分开处理。

## 5. 常见坑

| 常见做法 | 后果 |
| --- | --- |
| 把命名与标签约定只写进文档 | 几个月之后必然被违反，而且选择器出现问题时只能靠猜测 |
| 策略一上线就强制 | 存量对象不会被回查，而新写入会被大面积拒绝，可能直接阻塞发布流程 |
| 写路径上挂外部策略组件却不评估可用性 | 该组件不可用时，相关写入会全部失败，从而演变为集群级故障 |
| 升级前不扫弃用项 | 直到升级当天才会发现，有对象与工具使用了已经移除的版本 |
| 用重启来处置控制面变慢 | 计数器与队列被清空，下一次判断失去基线 |
| 卸载扩展组件不检查存量引用 | 此后会出现无法删除的对象，而且没有人知道原因 |
| 把集群级资源当成某个租户的 | 当多租户共用集群级对象时，权限与配额都可能失效 |

## 6. 要点自测

**问：为什么"能用清单表达的不要依赖集群侧保底"？**

答：如果依赖集群侧保底，同一份清单在不同环境中的表现就会不同，而且纠正动作发生在他人不可见的位置。使用哪一个 API 版本、对象叫什么名字、标签如何设置，属于发布物的一部分，应当在提交之前确定。

**问：准入策略上线时"先观察再强制"的原因是什么？**

答：因为策略只作用于其后的写入，不会回查存量对象；如果一上线就强制，新写入会被大面积拒绝，可能直接阻塞发布流程。先用只记录、不拦截的模式观察一段时间，可以提前发现将会命中策略的写入方。

**问：卸载扩展组件时，为什么要检查存量的清理项？**

答：因为清理项需要由对应的控制器移除。组件卸载之后，没有任何组件为这些对象执行清理，删除请求会永久停在"已请求未完成"状态；而直接移除清理项又会跳过对外部资源的清理。检查存量引用是唯一能够同时避免这两种困境的动作。

**问：控制面变慢时，为什么"重启"是最不该先做的动作？**

答：因为重启会清空计数器与内存中的队列，使"变慢之前的压力曲线"这一最重要的证据消失；同时，重启带来的短暂缓解会让人误以为问题已经解决。正确的顺序是先看请求侧的速率、限流比例与存储延迟。

**问：本章的治理产物里，哪一份是应对"升级当天才发现问题"的？**

答：是升级前的 API 与配置检查单。它要求在升级之前，把清单中用到的 API 版本、存量对象的存储版本、自定义资源的转换链、组件版本差与配置键位逐一确认，并给出回滚方式。

**第一反应不要做什么**：不要把命名与标签约定只写进文档；不要让策略一上线就强制；不要在写路径上挂载没有降级预案的外部组件；不要用重启来处置控制面变慢；不要在卸载扩展组件时忽略存量引用；也不要为了删除对象而跳过对外部资源的确认。
