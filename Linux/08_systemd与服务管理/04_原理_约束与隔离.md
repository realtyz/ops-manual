# 约束与隔离

## 1. 一个 unit 同时是说明书和笼子

每次启动一个服务，systemd 做两件容易被合并成一件的事：

1. **在 cgroup 树里给它建一个同名节点**，把「这个服务的进程集合」变成一个内核可识别、可计量的对象；
2. **给这个节点写上限、给进程换视野**——前者改变它能消耗多少，后者改变它能看到什么。

分开理解这两件事很重要，因为它们失败的形态完全不同：**上限不够用**表现为变慢、被节流、被杀；**视野被改变**表现为 `EACCES`/`EROFS`/`ENOENT`、端口绑不上，或者在启动阶段就以 systemd 自己的退出码失败。

cgroup 落点是可预测的：系统单元落在 `/system.slice/<unit>`，用户单元落在 `user.slice/user-<uid>.slice/user@<uid>.service/` 下的 `app.slice/<unit>`（用户单元默认 `Slice=app.slice`，不是 `system.slice`）。服务内读 `/proc/self/cgroup` 会看到同一条路径，这是核对「它到底在哪一格」最直接的办法。

**子节点受父节点约束**：unit 与 slice 都能挂上限，只改 unit 不改它所在的 slice 时，服务仍然受父 slice 的约束。所以「上限设了却没起作用」的第一种可能是设错了层，排查要看整棵树（`systemd-cgls`）而不是只看单个单元。

## 2. 三套限制各自的落点

「给服务调大句柄上限」这件事有三套完全不同的机制，改错地方不会报错，只会没有效果：

| 落点 | 载体 | 生效范围 | 对 systemd 服务 |
| --- | --- | --- | --- |
| `/etc/security/limits.conf` | PAM（Pluggable Authentication Modules，可插拔认证模块）的 `pam_limits` | 经过登录会话的进程（`login`、`su`、`sudo`、`cron` 等） | **永远不生效**——服务不经过登录会话 |
| `ulimit` | shell 内置 | 当前 shell 及其子进程，随 shell 结束消失 | 只影响「手工在 shell 里起」的那一段 |
| unit 的 `Limit*=` | systemd 属性 | 该服务的进程 | **这才是正解** |

所以根因判断很简单：**服务报 `Too many open files` 而 `limits.conf` 改了没用，是因为改错了落点**。正确做法是在 drop-in 里写 `LimitNOFILE=`，再 `daemon-reload` + `restart`，最后用 `/proc/<MainPID>/limits` 验收——注意验收要看进程，不是看配置文件。

`LimitNOFILE=` 与 `LimitNOFILESoft=` 是**两个独立属性**，因为 rlimit 本身就有软硬两个值：

- 只看 `LimitNOFILE=`（硬值）会把「最多能抬到多少」当成「实际可用是多少」；
- 服务实际能开多少句柄由**软值**决定，除非程序自己抬到硬值；
- 核对时要三个一起看：`show -p LimitNOFILE -p LimitNOFILESoft` 与 `/proc/<pid>/limits`。

这两个默认值**不跨环境通用**：它们来自各自 manager 的 `DefaultLimitNOFILE=`/`DefaultLimitNOFILESoft=`，系统 manager 与用户 manager 可以不同。默认值现场取，不凭记忆。

## 3. 三类上限：句柄、内存、CPU

### 3.1 任务数：`LimitNPROC=` 挡不住 fork 炸弹

`LimitNPROC=`（`setrlimit` 语义，每个进程各自一份）与 `TasksMax=`（cgroup 的 `pids.max`，**整个控制组共享一份**）不是一回事。防 fork 类问题要的是后者——每进程一份的限制约束不住整组进程的总数。

### 3.2 内存：`MemoryHigh=` 是刹车，`MemoryMax=` 是墙

- **`MemoryMax=`（硬上限）不是「超过就杀」**：它先触发回收，回收之后仍然超出，才在该 cgroup 内触发 OOM，杀掉其中一个进程。这个先后顺序决定了「撞上限」与「被杀」之间有一个回收窗口。
- **`MemoryHigh=`（软上限）只节流**：超限后加大回收压力、限制速度，进程继续跑。给延迟敏感的服务先上 `high` 通常比直接上 `max` 安全，但如果它真的失控，`high` 拦不住。
- **`MemoryLow=`/`MemoryMin=` 是反向的保护**：告诉回收器「这块尽量别动」；前者是尽力，后者是硬保底（只有整机 OOM 才会打破）。
- **`MemorySwapMax=` 限制该组能用多少 swap**，设 0 表示不许换出。

内存撞限的定性与**整机内存不足完全不同**：内核日志里会带 `constraint=CONSTRAINT_MEMCG` 与 `oom_memcg=<cgroup 路径>`，单元的 `Result` 变成 `oom-kill`、`ExecMainStatus` 是 `9`（`code=killed, status=9/KILL`）。拿宿主 `free` 的余量去否定这类 OOM 是常见误判——撞的是它自己那一格。

还有一条容易漏掉的边界：**`OOMPolicy=stop` 是服务单元的默认值**——该单元内有进程被杀时，systemd 会把整个单元停掉，`Result=oom-kill`、单元进入 `failed`。这对取证不利（cgroup 目录与账本随单元结束被回收）。反过来设成 `OOMPolicy=continue` 时，单元会继续 `active (running)`，**「服务没挂但少了几个 worker」这种状态在 `systemctl status` 上看不出来**，只能靠 cgroup 的 `memory.events`（`oom_kill` 非 0）发现。

### 3.3 CPU：`CPUQuota=` 是配额，不是绑核

`CPUQuota=` 表达的是「**每个周期最多用多少算力**」，换算后落到 cgroup 的 `cpu.max`（`quota period` 两段）。它不是「一个核的百分之多少」，也不是把进程绑到某个核上：

- 在多核机器上，百分比是相对**单核**的算力配额，因此 `CPUQuota=20%` 的忙循环在一个周期里最多拿到单核 20% 的时间；
- 判断它是否真在限流，要看 `cpu.stat` 的 `nr_throttled`/`throttled_usec`，而不是看业务变慢；
- **要绑核用 `CPUAffinity=`/`AllowedCPUs=`**，要按权重分配（只在有竞争时起作用）用 `CPUWeight=`。

## 4. 沙箱改变的是「服务看到的世界」

沙箱选项分四类，各自改变一件不同的事：

| 类别 | 代表选项 | 改变了什么 |
| --- | --- | --- |
| 文件系统视图 | `ProtectSystem=`、`ProtectHome=`、`ReadWritePaths=`、`PrivateTmp=` | 服务能读/写哪些路径 |
| 设备与命名空间 | `PrivateDevices=`、`PrivateNetwork=`、`ProtectProc=`、`RestrictNamespaces=` | 能看到哪些设备、网络、`/proc` 条目、能否再建命名空间 |
| 身份与特权 | `User=`/`Group=`、`DynamicUser=`、`NoNewPrivileges=`、`CapabilityBoundingSet=`、`RestrictSUIDSGID=` | 以什么身份跑、最多持有什么特权 |
| 系统调用与协议族 | `SystemCallFilter=`、`SystemCallArchitectures=`、`RestrictAddressFamilies=` | 能调哪些系统调用、能开哪些协议族 |

`ProtectSystem=` 的四档边界必须精确记住，它们的差别正是「防篡改」与「降暴露面」的差别：

| 取值 | 效果 |
| --- | --- |
| `no` | 不限制（缺省） |
| `yes` | `/usr`、`/boot`、`/efi` 只读（**不含 `/etc`**） |
| `full` | `yes` 再加 `/etc` 只读 |
| `strict` | 整个文件系统层级只读，只留 `/dev`、`/proc`、`/sys` 例外，写入必须用 `ReadWritePaths=` 显式开 |

两处反直觉之处：

- **`strict` 不等于「全盘只读」**：`/home`、`/root`、`/run/user` 归 `ProtectHome=` 管，不写它时它们仍然是可写的。把「防篡改」当成「全盘保护」会得出错误结论。
- **`full` 几乎不改变暴露面评分**，它的价值是防篡改（挡住对系统目录与配置的修改），而不是让服务更难被利用。混淆这两个目标，就会选错档位。

`ProtectHome=` 的取值语义也不同：`yes` 把 `/home` 换成空的只读 `tmpfs`（目录内容变得不可访问），`read-only` 则保留内容、只挂只读。要「还能读但不许写」，用的是后者。

**`PrivateTmp=yes` 不是「换个临时目录」**：它给服务一个私有的 `/tmp`（及 `/var/tmp`），宿主的 `/tmp` 在服务里根本不存在，而且它随服务停止而消失。两个直接后果：

- 依赖 `/tmp` 做跨进程共享（锁文件、IPC）的架构会直接坏掉；
- **把可执行脚本放在 `/tmp` 又开 `PrivateTmp=yes`，服务会以 `203/EXEC` 失败**——宿主机上文件明明在，服务的命名空间里它不存在。脚本应当放在 `/usr/local/lib/<name>/` 这类稳定路径。

## 5. `ReadWritePaths=` 与目录的归属

在只读世界里开可写口靠 `ReadWritePaths=`，但它有一个硬约束：**路径必须已经存在，systemd 不会替你创建**。指向不存在的路径时，失败发生在沙箱搭建阶段，表现为 systemd 的退出码 `226/NAMESPACE`，而不是应用的 `ENOENT`。

正确做法是让 systemd 自己先把目录建出来，再列进可写口：

| 属性 | 系统单元落点 | 用途 |
| --- | --- | --- |
| `RuntimeDirectory=` | `/run/<name>` | 运行期数据，重启即失 |
| `StateDirectory=` | `/var/lib/<name>` | 需要跨重启保留的状态 |
| `CacheDirectory=` | `/var/cache/<name>` | 可重建的缓存 |
| `LogsDirectory=` | `/var/log/<name>` | 日志文件 |

用户单元的落点不同（分别在 `$XDG_RUNTIME_DIR`、`$XDG_STATE_HOME` 等之下），不要照抄系统单元的路径。

还有一条常被忽略的边界：**「建目录」与「开可写口」是两件事**。`StateDirectory=` 只负责以正确的属主创建目录；在 `ProtectSystem=strict` 下，不把该路径加进 `ReadWritePaths=` 照样写不进去。反过来，`ReadWritePaths=` 指向的目录属主与 `User=` 不匹配时，同样写不进去。**目录属主与可写口必须同时对上。**

## 6. `User=` 并不收敛特权

这是本章最值得单独记住的一条：**`User=`/`Group=` 只改变 uid/gid，不改变能力集**。这里的「能力」（capability）指 Linux 把 root 特权拆成的一项项独立权限——一个进程可以只持有其中几项，而不是非有即无地持有全部 root 权力。

只写 `User=` 时：

- `CapabilityBoundingSet`（bounding set，即「最多能持有哪些特权」）**仍是满集**；
- `NoNewPrivileges` 仍是关的。

要真正收敛提权面，必须额外写：

- **`CapabilityBoundingSet=`**：限定「最多能持有哪些能力」。设为空即一项都不给（此时 effective 集合也随之清空）。这是「收敛特权」的核心开关。
- **`NoNewPrivileges=yes`**：让服务及其全部子进程**永远不能获得新特权**——SUID/SGID 位失效、文件能力失效。它一处生效、整棵进程树受益，且极少影响正常业务，属于「低代价高收益」的一项。
- **`AmbientCapabilities=`**：让**非 root** 服务在 `execve` 之后仍保留指定能力。它是「以普通用户运行又要做一件特权事」的正解——例如绑低端口只需 `CAP_NET_BIND_SERVICE`，配上 `User=`、`CapabilityBoundingSet=` 与 `NoNewPrivileges=yes` 即可，不需要给整个服务 root。

身份相关的失败都是硬失败，不会「照常以 root 跑」：用户不存在报 `217/USER`，组不存在报 `216/GROUP`，沙箱路径问题报 `226/NAMESPACE`。**用户级 manager 完全不能切换身份**——用户单元里写 `User=` 也会得到 `216/GROUP`，因为它没有那个权限。

`DynamicUser=yes` 让 systemd 在启动时分配一个临时的 uid/gid、停止后回收，适合不需要固定 UID 的无状态服务；代价是任何「按固定 UID 做审计、配额或文件归属」的架构都不能直接套用。

## 7. 为什么沙箱问题报的是 systemd 退出码

systemd 退出码分两类来源，混淆它们会把排查带偏：

- **进程自己的退出码**（0–255）：进程真的跑起来之后自己返回的；
- **systemd 代替进程报告的码（200 段）**：专指「systemd 没能把你写的服务按你写的样子启动起来」。

判断依据是 `systemd-analyze exit-status <code>` 给出的 `CLASS`：`CLASS=systemd` 的是 systemd 自报，`libc` 的才是进程真实退出码。

常见的几项及其指向：

| 退出码 | 含义 | 先查哪里 |
| --- | --- | --- |
| `200/CHDIR` | 无法进入工作目录 | `WorkingDirectory=` 是否存在、`User=` 是否可进入 |
| `203/EXEC` | 无法执行主命令 | 路径、执行位、shebang 解释器；开了 `PrivateTmp` 时脚本是否在 `/tmp` |
| `216/GROUP` | 无法切换组/用户 | `Group=` 是否存在；是否是用户单元里写了 `User=` |
| `217/USER` | 无法确定用户 | `User=` 指定的用户是否存在 |
| `226/NAMESPACE` | 沙箱/挂载命名空间搭建失败 | `ReadWritePaths=` 路径是否存在、`ProtectSystem=` 与写入是否冲突 |

**看到 `226` 先去查沙箱配置，而不是改业务代码；看到 `203` 先查路径，而不是怀疑程序逻辑。** 这些码是 systemd 在替你分类，把它们当普通退出码去翻应用日志，会白白绕一圈。

一个容易误判的边界：`ProtectSystem=strict` 只是把文件系统挂成只读，**这是挂载选项的限制，不是沙箱搭建失败**。此时进程照样跑起来，它自己的写操作会返回 `EROFS`，单元以应用自身的退出码失败（例如 `1/FAILURE` 而不是 `226`）。`226` 出现在沙箱根本搭不起来时（如路径不存在）。两者都指向同一个配置区，但证据形态不同。

## 常见误解

| 常见说法 | 事实 |
| --- | --- |
| 「服务句柄不够，改 `limits.conf`」 | 服务不经过登录会话，`limits.conf` 对 systemd 服务永远不生效；落点是 unit 的 `Limit*=` |
| 「`show -p LimitNOFILE` 就是服务能用的句柄数」 | 那是硬上限；实际可用是软值 `LimitNOFILESoft=`。三者要一起看 |
| 「`LimitNPROC=` 能防 fork 炸弹」 | 它是每进程的 rlimit；整组的总数要 `TasksMax=` |
| 「`MemoryMax=` 超过就杀」 | 先回收，回收后仍超才 OOM；`MemoryHigh=` 只节流 |
| 「`CPUQuota=10%` 是绑 0.1 个核」 | 是每周期的单核算力配额；绑核用 `CPUAffinity=`/`AllowedCPUs=` |
| 「`ProtectSystem=strict` 就是全盘只读」 | `/home`、`/root` 归 `ProtectHome=` 管，不写它仍然可写 |
| 「`ProtectSystem=full` 能大幅降低暴露面」 | 它主要防篡改；评分上几乎不降 |
| 「`PrivateTmp=yes` 只是换个临时目录」 | 是私有 tmpfs，宿主看不到、停止即消失；依赖共享 `/tmp` 的架构会坏 |
| 「`ReadWritePaths=` 会自动创建目录」 | 不会；路径不存在直接 `226/NAMESPACE`。先用 `*Directory=` 建 |
| 「写了 `StateDirectory=` 就能写进去」 | 建目录与开可写口是两件事，还要 `ReadWritePaths=`，且属主要对上 |
| 「写了 `User=` 就收敛了特权」 | uid/gid 变了，能力集仍是满集、`NoNewPrivileges` 仍是关的 |
| 「用户单元里也能写 `User=`」 | 用户级 manager 无权限切换身份，报 `216/GROUP` |
| 「`User=` 写错会照常以 root 跑」 | 硬失败：`217/USER` 或 `216/GROUP` |
| 「`226` 是应用报的错」 | 这是 systemd 的 `NAMESPACE` 类自报码，指向挂载/沙箱配置 |
| 「`ProtectSystem=strict` 挡住了写，所以是 `226`」 | 只读挂载让进程自己收到 `EROFS`；`226` 是沙箱根本没搭起来 |
| 「为降 `systemd-analyze security` 的分多堆选项」 | 分数是暴露面参考，不是验收标准；堆选项会让服务起不来 |
| 「只改 unit 就能摆脱上层限制」 | 子节点仍受父 slice 约束，要看整棵树 |

## 要点自测

**问：服务报 `Too many open files`，为什么改 `limits.conf` 没有效果？**
答：systemd 服务不经过登录会话，PAM 不介入，`limits.conf` 对它永远不生效。落点是 unit 的 `LimitNOFILE=`，改完要 `daemon-reload` + `restart`，并用 `/proc/<MainPID>/limits` 验收。

**问：`LimitNOFILE=` 与 `LimitNOFILESoft=` 为什么要分开看？**
答：rlimit 有软硬两个值。硬值是「最多能抬到多少」，软值是「当前实际可用」。只看硬值会得出「有几万个句柄」的错误结论。

**问：为什么说 `User=` 不等于「收敛了特权」？**
答：它只改 uid/gid。`CapabilityBoundingSet`（最多持有哪些能力）仍是满集，`NoNewPrivileges` 仍是关的。要收敛必须另写 `CapabilityBoundingSet=` 与 `NoNewPrivileges=yes`。

**问：`ReadWritePaths=` 指向一个不存在的目录会发生什么，怎么避免？**
答：沙箱搭建失败，单元以 `226/NAMESPACE` 失败。避免方式是用 `RuntimeDirectory=`/`StateDirectory=` 等让 systemd 先创建目录，再把它列进 `ReadWritePaths=`，并确认目录属主与 `User=` 匹配。

**问：`ProtectSystem=strict` 下服务写文件失败，为什么退出码可能是 `1/FAILURE` 而不是 `226`？**
答：因为只读挂载已经成功建立，进程正常跑起来后自己的写操作返回 `EROFS`，于是以应用自己的退出码失败。`226` 表示的是沙箱根本没搭起来（如 `ReadWritePaths=` 路径不存在）。

**问：非 root 服务要绑 80 端口，正确的配置组合是什么？**
答：`User=` 指定普通用户，`CapabilityBoundingSet=CAP_NET_BIND_SERVICE` 限定「最多只能持有这一项」，`AmbientCapabilities=CAP_NET_BIND_SERVICE` 让它在 `execve` 后仍保留该项，再配 `NoNewPrivileges=yes`。

**第一反应不要做什么**：不要改 `limits.conf` 来解决服务的 rlimit 问题；不要用 `show -p LimitNOFILE` 当可用句柄数；不要把 `CPUQuota=` 当绑核；不要把 `ProtectSystem=strict` 当全盘只读；不要以为 `User=` 收敛了特权；不要在 `ReadWritePaths=` 里写不存在的路径；不要把脚本放在 `/tmp` 又开 `PrivateTmp=`；不要把 `226/CHDIR/EXEC` 当应用错误去翻代码；不要为刷暴露面评分堆沙箱选项。
