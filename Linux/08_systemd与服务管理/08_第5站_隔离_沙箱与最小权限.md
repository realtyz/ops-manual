## 0. 30 秒速览

> [!abstract] 这一篇只要记住七句话
> - **沙箱的目的是「让服务只能看到它需要的」**：文件系统只读、私有 `/tmp`、私有设备、能力收敛、系统调用过滤。
> - **四类选项要分开看**：文件系统视图（`ProtectSystem`/`ProtectHome`/`ReadWritePaths`）、名字空间（`PrivateTmp`/`PrivateDevices`/`PrivateUsers`）、权限收敛（`NoNewPrivileges`/`CapabilityBoundingSet`/`User`）、系统调用与网络（`SystemCallFilter`/`RestrictAddressFamilies`）。
> - **报错往往不是业务错误码，而是 systemd 的退出码**：实测 `ReadWritePaths=` 指向不存在的路径 → `226/NAMESPACE`；目标用户不存在 → `217/USER`；组不存在（含**用户单元里写 `User=`**）→ `216/GROUP`；`WorkingDirectory=` 不存在 → `200/CHDIR`；`ExecStart=` 不可执行 → `203/EXEC`。
> - **`ProtectSystem=` 逐级收紧，而且必须用 `/proc/self/mounts` 验收**：实测 `no` → `/` 是 `rw`；`full` → `/usr`、`/etc`、`/boot` 变 `ro`；`strict` → `/` 变 `ro`（`ro,nosuid`）。**但不设 `ProtectHome=` 时 `/home` 仍是独立 `rw` 挂载**，写进去照样成功——「strict = 全盘只读」是错的。
> - **`ProtectHome=yes` 才管 `/home` 与 `/root`**：实测它把 `/home` 换成 `tmpfs ro,nosuid,nodev,noexec,size=808352k,mode=755`，服务内 `ls /home` → `Permission denied`；`ProtectHome=read-only` 才是「只读的原目录」。
> - **`PrivateDevices=yes` 把 `/dev` 从 207 个节点砍到 18 个，并换成 `tmpfs ro,nosuid,noexec,size=4096k`**：实测 `/dev/sda*`、`/dev/mem`、`/dev/port`、`/dev/loop-control` 全部消失，`/dev/mem` 从「可读」变成「不存在」。
> - **system 单元里 `User=` 真的能换身份，用户单元里不能**：实测 system 单元写 `User=realtyz`，服务内 `uid=1000`、`CapEff=0000000000000000`，**但 `CapBnd=000001ffffffffff`（仍是满集）、`NoNewPrivs=0`**——`User=` 只换 uid/gid，**不会**自动清空 capability bounding set，也不等于 `NoNewPrivileges`；要清空需另加 `CapabilityBoundingSet=`，要置 1 需另加 `NoNewPrivileges=yes`。而用户单元写 `User=root` 直接 `216/GROUP`。`DynamicUser=yes` 实测分配到 **UID/GID 61593** 并在停止后回收。

## 1. 沙箱的四类选项

| 类别 | 代表选项 | 改变什么 |
| --- | --- | --- |
| 文件系统视图 | `ProtectSystem=`、`ProtectHome=`、`ReadWritePaths=`、`PrivateTmp=`、`InaccessiblePaths=` | 服务能读/写哪些路径 |
| 名字空间与设备 | `PrivateDevices=`、`PrivateNetwork=`、`PrivateUsers=`、`ProtectProc=`、`ProcSubset=`、`RestrictNamespaces=` | 服务能看到哪些设备/网络/proc/名字空间 |
| 权限收敛 | `User=`/`Group=`、`NoNewPrivileges=`、`CapabilityBoundingSet=`、`AmbientCapabilities=`、`DynamicUser=`、`RestrictSUIDSGID=` | 服务以什么身份跑、最多持有什么特权 |
| 系统调用与网络 | `SystemCallFilter=`、`SystemCallArchitectures=`、`RestrictAddressFamilies=` | 服务能调用哪些系统调用、能开哪些协议族 |

一组常用的保守沙箱（按业务逐项验证后再打开）：

```ini
[Service]
NoNewPrivileges=yes
ProtectSystem=strict
ProtectHome=yes
PrivateTmp=yes
PrivateDevices=yes
CapabilityBoundingSet=
SystemCallFilter=@system-service
ReadWritePaths=/var/lib/myapp /var/log/myapp
```

注意最后一项：**`ProtectSystem=strict` 之后，所有写入都必须被显式开出来**，否则服务会以各种「说不清的写失败」告终。

## 2. 文件系统视图：服务看到的目录树

`ProtectSystem=` 逐级收紧（下表每一行都有本次实测的挂载表与写测试作证据）：

| 取值 | 效果 | 本次实测 |
| --- | --- | --- |
| `no`（默认） | 不做限制 | `root_mount=… / ext4 rw,relatime`；往 `/usr`、`/etc`、`/boot` 写**全部成功** |
| `yes` | `/usr`、`/boot`、`/efi` 只读（**不含 `/etc`**） | 见 `full` 一行的实测推导（`full` = `yes` + `/etc`） |
| `full` | 在 `yes` 的基础上**再加 `/etc` 只读** | `usr_mount=… /usr ext4 ro,relatime`、`etc_mount=… /etc ext4 ro,relatime`、`boot_mount=/dev/sda2 /boot ext4 ro,relatime`；写 `/usr`、`/etc`、`/boot` **全部 FAIL**，写 `/var/lib`、`/var/log`、`/run`、`/root`、`/home`、`/tmp` 仍 OK |
| `strict` | 整个文件系统层级只读，只有 `/dev`、`/proc`、`/sys` 除外；写入要用 `ReadWritePaths=` 显式开 | `root_mount=… / ext4 ro,relatime`；写 `/usr`、`/etc`、`/boot`、`/var/log`、`/run`、`/tmp` **全部 FAIL** |

> [!important] `ProtectSystem` 只管这几处，而且 `/home` 是另一个选项的地盘
> `ProtectSystem=` 的管辖范围就是上表那几处；`/home`、`/root`（以及 `/run/user`）是 **`ProtectHome=`** 的地盘。**本次系统级实测把这条边界钉死了**：
> - `ProtectSystem=strict` 但**不写** `ProtectHome=` 时，服务命名空间里 `home_mount=… /home ext4 rw,relatime`（**仍是可写的独立挂载**），`WRITE OK /home/realtyz/lab08-w`——**「strict 等于全盘只读」是错的**。
> - 加上 `ProtectHome=yes` 后，`home_mount=tmpfs /home tmpfs ro,nosuid,nodev,noexec,relatime,size=808352k,mode=755`，服务内 `ls /home` → `ls: cannot open directory '/home': Permission denied`；连 `/root` 的 `stat` 也变成 `home_mode=0 root:root`（不可访问）。
> - `ProtectHome=read-only` 又是另一种语义：目录还在、内容可读、只是挂成只读（实测此时 `/home/realtyz` 的写入 FAIL、但可列举）。
>
> 所以三条可复制的验收命令是：
> ```bash
> grep -E " /(home|usr|etc|boot)? " /proc/self/mounts    # 验证：服务命名空间里各挂载点的 ro/rw（在服务内跑）
> systemctl show myapp -p ProtectSystem -p ProtectHome -p ReadWritePaths   # 验证：生效属性
> systemd-analyze security myapp.service | tail -3       # 验证：加固前后暴露面评分
> ```

`ReadWritePaths=` 的作用是**在只读世界里开一个可写口**。实测把路径写成不存在的 `/nonexistent-lab08-path` 时：

```text
$ systemctl show -p Result -p ExecMainStatus -p ActiveState lab08-sec-rwmissing.service
Result=exit-code
ExecMainStatus=226
ActiveState=failed
$ journalctl -u lab08-sec-rwmissing.service -o cat --no-pager | tail -3
lab08-sec-rwmissing.service: Failed to set up mount namespacing: /nonexistent-lab08-path: No such file or directory
lab08-sec-rwmissing.service: Main process exited, code=exited, status=226/NAMESPACE
lab08-sec-rwmissing.service: Failed with result 'exit-code'.
```

> [!warning] `ReadWritePaths=` 的路径必须存在
> systemd 不会替你创建它。**推荐做法**：让 systemd 用 `RuntimeDirectory=`/`StateDirectory=` 先建目录，再把路径写进 `ReadWritePaths=`：
> ```ini
> [Service]
> StateDirectory=myapp            # 自动创建 /var/lib/myapp 并设好属主
> LogsDirectory=myapp             # 自动创建 /var/log/myapp
> RuntimeDirectory=myapp          # 自动创建 /run/myapp（服务停止后可清理）
> ProtectSystem=strict
> ReadWritePaths=/var/lib/myapp /var/log/myapp /run/myapp
> ```
> 这样既不用手写 `mkdir`，也不会因为路径不存在把服务卡在 `226/NAMESPACE`。**本次实测这四个目录在系统级的落点**：`RuntimeDirectory=lab08b` → `/run/lab08b`、`StateDirectory=lab08b` → `/var/lib/lab08b`、`CacheDirectory=lab08b` → `/var/cache/lab08b`、`LogsDirectory=lab08b` → `/var/log/lab08b`，且停止并清理后四者都被移除。
>
> **这几个路径是 system 单元的落点**：在 user 单元里，`StateDirectory=` 落在 `$XDG_STATE_HOME`（`~/.local/state/myapp`）、`LogsDirectory=` 落在 `~/.local/state/log/myapp`、`RuntimeDirectory=` 落在 `$XDG_RUNTIME_DIR/myapp`，**不是** `/var/lib`、`/var/log`、`/run`（对照表见第 13 篇第 4 节）。
>
> **另一个实测到的陷阱**：`StateDirectory=` 只管「建目录」和「把可写口开出来」两件事之一。实测一个 `User=realtyz` 的普通单元里写 `StateDirectory=lab08sec`，服务内的 `$STATE_DIRECTORY` 指向 `/var/lib/lab08sec`，但**没把 `ReadWritePaths=` 指过去时写不进去**；反过来 `ReadWritePaths=` 指向一个 root 拥有的 `/var/lib/lab08-sec-w` 时，`uid=1000` 的服务也写不进去（`WRITE FAIL`）——**目录属主与可写口必须同时对上**。

## 3. 私有名字空间：`PrivateTmp`、`PrivateDevices`、`ProtectProc`

`PrivateTmp=yes` 给服务一个独立的 `/tmp`（以及 `/var/tmp`）。实测 inode 差异与「宿主看不见」：

```text
$ stat -c %i /tmp                                     # 宿主
1179649
$ journalctl -u lab08-p2-hard.service -o cat --no-pager | grep tmp_inode
PROC tmp_inode=1311092                                # 服务内（PrivateTmp=yes）
$ ls /tmp/lab08-private-marker                        # 宿主侧
ls: cannot access '/tmp/lab08-private-marker': No such file or directory
```

`systemctl show -p PrivateTmp` 也可以从另一侧确认挂载来源：

```text
485 430 252:0 /tmp/systemd-private-decad510b934454f9d61aef2aa2893fd-lab08b-privatetmp.service-hOwQIH/tmp /tmp rw,relatime shared:416 master:1 - ext4 /dev/mapper/ubuntu--vg-ubuntu--lv rw
```

实用含义：

- 服务写进 `/tmp` 的文件，**其它服务/宿主用户看不到**；排查时要进命名空间看（`ls -l /proc/<pid>/root/tmp`、`nsenter -t <pid> -m ls /tmp`，需要权限）。
- **私有 `/tmp` 随服务停止就消失**，不适合放跨重启的持久文件；要跨重启用 `StateDirectory=`，要跨进程共享且不持久用 `RuntimeDirectory=`。
- 依赖 `/tmp` 里共享锁文件/IPC 的架构，开了 `PrivateTmp` 会直接坏掉。
- **一个非常容易踩的组合**：把待执行的脚本放在 `/tmp`，同时开 `PrivateTmp=yes`。实测就是这样拿到 `203/EXEC` 的：`lab08-sec-hard.service: Main process exited, code=exited, status=203/EXEC`——在宿主看那个文件明明在，在服务的私有 `/tmp` 里它就是不存在。**脚本放 `/usr/local/lib/<name>/`，可写数据放 `StateDirectory=`。**

| 场景 | 服务看到的 `/tmp` | 宿主/其他服务能看到吗 |
| --- | --- | --- |
| 普通服务 | 宿主 `/tmp` | 能 |
| `PrivateTmp=yes` | 私有 tmpfs | 不能（除非进命名空间） |
| 容器（Docker/K8s） | 容器自己的 `/tmp` | 不能 |

### 3.1 `PrivateDevices=yes`（本次补测）

`PrivateDevices=` 把服务能看到的设备节点收敛到最小集。实测两个只差这一个选项的 system 单元：

| 探测项 | `PrivateDevices=no`（默认） | `PrivateDevices=yes` |
| --- | --- | --- |
| `/dev` 节点数 | `n_nodes=207` | `n_nodes=18` |
| 块设备 | `has_sda=/dev/sda /dev/sda1 /dev/sda2 /dev/sda3` | `has_sda=`（一个都没有） |
| 裸内存设备 | `has_mem=/dev/mem /dev/port` | `has_mem=`（都不存在） |
| 读 `/dev/mem` | `read_mem=S`（真的读出了内容） | `head: cannot open '/dev/mem' for reading: No such file or directory` |
| `/dev/loop-control` | 存在 | `missing` |
| `/dev` 挂载 | `udev /dev devtmpfs rw,nosuid,relatime,size=3999920k,nr_inodes=999980,mode=755,inode64` | `tmpfs /dev tmpfs ro,nosuid,noexec,size=4096k,nr_inodes=65536,mode=755,inode64` |

宿主侧对照：`host_n_nodes=207`。也就是说 **`PrivateDevices=yes` 让服务彻底失去访问磁盘、内存和 loop 设备的能力**——这正是大多数无状态业务服务想要的状态；需要 GPU、串口等特定设备时再按需放开（`DeviceAllow=`）。

`ProtectProc=invisible` + `ProcSubset=pid` 则进一步收窄 `/proc` 的可见范围（本次随加固单元一起设过，实测 `lsmod` 与 `unshare -U` 都失败，见第 4 节）。

## 4. 权限收敛：身份、能力与提权面

### 4.1 身份：`User=` 只在 system 单元真的生效（本次补测）

```ini
[Service]
User=myapp
Group=myapp
SupplementaryGroups=myapp-data
```

`SupplementaryGroups=` 只在服务确实需要附加组时写。**实测两个方向的证据：**

system 单元（有 root，真的换得动）：

```text
$ journalctl -u lab08t-strichome.service -o cat --no-pager | grep -E '^uid=|^Cap'
uid=1000 user=realtyz
NoNewPrivs=NoNewPrivs:	0
CapPrm: 0000000000000000
CapEff: 0000000000000000
CapBnd: 000001ffffffffff
```

用户单元（`User=` 无效，直接失败）：

```text
$ systemctl --user start lab08-u-root.service; systemctl --user show -p Result -p ExecMainStatus -p User lab08-u-root.service
Result=exit-code
ExecMainStatus=216
User=root
$ systemctl --user show -p ControlGroup -p Slice lab08-u-plain.service
Slice=app.slice
ControlGroup=/user.slice/user-1000.slice/user@1000.service/app.slice/lab08-u-plain.service
```

```text
lab08-u-root.service: Changing group credentials failed: Operation not permitted
lab08-u-root.service: Main process exited, code=exited, status=216/GROUP
```

**目标存在性也各有专属退出码**：用户不存在报 `217/USER`、组不存在报 `216/GROUP`：

```text
lab08-sec-nouser.service: Failed to determine user credentials: No such process
lab08-sec-nouser.service: Main process exited, code=exited, status=217/USER

lab08-sec-badgroup.service: Failed to determine group credentials: No such process
lab08-sec-badgroup.service: Main process exited, code=exited, status=216/GROUP
```

`DynamicUser=yes` 可以让 systemd 在启动时分配一个动态 UID/GID，服务停止后回收（**本次补测**）：

```text
$ journalctl -u lab08-sec-dyn2.service -o cat --no-pager | grep -E 'dyn_|^UID|^GID'
dyn_uid=61593 dyn_gid=61593 dyn_user=lab08-sec-dyn2
UID=61593
GID=61593
$ systemctl show lab08-sec-dyn2.service -p DynamicUser -p StateDirectory
DynamicUser=yes
StateDirectory=lab08dyn
$ ls -ld /var/lib/lab08dyn
lrwxrwxrwx 1 0 0 16 Sep 19 08:12 /var/lib/lab08dyn -> private/lab08dyn
```

适合不需要固定 UID 的无状态服务：**身份是每次启动临时分配的（实测 61593），`StateDirectory=` 自动变成 `private/` 下的符号链接**，服务静态文件权限收敛得很干净；代价是「按 UID 做审计/配额」的架构不能直接套用。

`PrivateUsers=yes`（把服务放进一个 user namespace，服务内看到的是映射后的身份）本次也补测了：

```text
$ journalctl -u lab08-sec-userns2.service -o cat --no-pager | grep -E 'uid|uid_map'
uid=1000 uid_map= 0 0 1
 1000 1000 1
```

**注意这条与本机的一个安全策略相互影响**：本机 `kernel.apparmor_restrict_unprivileged_userns = 1`，所以**非 root（`realtyz`）在服务里自己创建 user namespace 会被拒**：

```text
$ journalctl -u lab08t-hard.service -o cat --no-pager | grep -A1 'unprivileged userns'
--- unprivileged userns
unshare: unshare failed: Operation not permitted
unshare -U FAILED
```

而同一个 `unshare -U` 在**不设 `RestrictNamespaces=` 的 root 单元**里是成功的（`unshare -U OK`）。也就是说：**加固 unit 之后，服务连「自己再套一层隔离」的能力都没有了**——这既是想要的效果，也是排查时容易误判成「沙箱坏了」的地方。

### 4.2 提权面收敛

| 选项 | 作用 | 本次实测 |
| --- | --- | --- |
| `NoNewPrivileges=yes` | 服务及其子进程**永远不能获得新特权**：SUID/SGID 失效、file capabilities 失效 | 服务内 `NoNewPrivs:	1`（默认是 `0`） |
| `CapabilityBoundingSet=` | 限定服务**最多**能持有哪些 capability；设为空 = 一项都不给 | 默认满集 `CapBnd: 000001ffffffffff`；设为空后 `CapBnd: 0000000000000000`，`CapEff` 也为 0，`lsmod` 从 OK 变 FAIL |
| `AmbientCapabilities=` | 让**非 root** 服务在 `execve` 后仍保留指定 capability（如绑低端口用 `CAP_NET_BIND_SERVICE`） | 随 `CapabilityBoundingSet=` 一起收敛，服务内 `CapAmb=0000000000000000` |
| `RestrictSUIDSGID=yes` | 禁止创建 SUID/SGID 文件 | `systemd-analyze security` 里从 `✗` 变 `✓` |
| `UMask=0077` | 收紧新建文件权限 | 默认 `UMask=0022`，设置后 `UMask=0077` |
| `RestrictAddressFamilies=AF_INET AF_INET6 AF_UNIX` | 限定可用的协议族 | 实测 `AF_PACKET` 由 OK 变 `FAIL [Errno 1] Operation not permitted`（`AF_NETLINK` 在另一组里报 `FAIL [Errno 97] Address family not supported by protocol`） |

非 root 服务绑 80 端口的正解之一：

```ini
[Service]
User=myapp
CapabilityBoundingSet=CAP_NET_BIND_SERVICE
AmbientCapabilities=CAP_NET_BIND_SERVICE
NoNewPrivileges=yes
```

发行版自带单元给了一个可参考的实现——本机 `systemd-resolved.service` 用了 `User=`、`ProtectSystem=strict`、`PrivateTmp=yes`、`NoNewPrivileges=yes`，以及：

```text
CapabilityBoundingSet=cap_setpcap cap_net_bind_service cap_net_raw
User=systemd-resolve
ProtectHome=yes
RestrictAddressFamilies=AF_INET AF_INET6 AF_NETLINK AF_UNIX
→ Overall exposure level for systemd-resolved.service: 2.2 OK :-)
```

### 4.3 系统调用与网络

```ini
[Service]
SystemCallFilter=@system-service     # 只允许「一般服务需要的」系统调用组
SystemCallArchitectures=native       # 只允许本机架构的系统调用
RestrictAddressFamilies=AF_INET AF_INET6 AF_UNIX
RestrictNamespaces=yes               # 禁止服务再创建任何 namespace
```

`SystemCallFilter` 语义是「**先拒绝，再按规则放行**」；写得太严会让服务以 `SIGSYS` 或各种奇怪错误退出。**开局建议只加 `@system-service`**，再按报错逐步调整。加上 `RestrictNamespaces=yes` 之后，服务里连 `unshare -U` 都会失败（见 4.1）。

## 5. 打分与加固流程

```text
$ systemd-analyze security lab08t-raw.service --no-pager | tail -3
✗ UMask=                                                      Files created by service are world-readable by default                       0.1

→ Overall exposure level for lab08t-raw.service: 9.6 UNSAFE :-{

$ systemd-analyze security lab08t-hard.service --no-pager | tail -3
✓ RestrictSUIDSGID=                                           SUID/SGID file creation by service is restricted
✓ UMask=                                                      Files created by service are accessible only by service's own user by default

→ Overall exposure level for lab08t-hard.service: 1.9 OK :-)
```

同一台机器上「什么都不做」与「一套完整加固」的差距，以及中间档的对照（`ProtectSystem=full`、`strict` 各自的中间分）：

| 单元 | 关键选项 | `systemd-analyze security` |
| --- | --- | --- |
| `lab08t-raw` / `lab08-sec-p0` / 本机 `ssh.service` | 默认（无沙箱） | **9.6 UNSAFE** |
| `lab08-sec-pfull` | `ProtectSystem=full` + `ProtectHome=read-only` | **9.2 UNSAFE** |
| `lab08-sec-pstrict` | `ProtectSystem=strict` + `ProtectHome=yes` + `RestrictAddressFamilies=` | **1.5 OK** |
| `lab08t-hard` / `lab08-sec-hard` | 完整加固（含 `User=`、`CapabilityBoundingSet=`、`SystemCallFilter=`） | **1.9 OK** |
| 本机 `systemd-journald.service` | 发行版自带 | **4.3 OK** |
| 本机 `systemd-resolved.service` | 发行版自带 | **2.2 OK** |

这张表本身就是最好的教材：**`ProtectSystem=full` 几乎不改变评分（9.6 → 9.2），真正把分数拉下来的是 `strict` + `ProtectHome=` + 能力收敛（→ 1.5/1.9）**。但请注意：

> [!warning] 分数只是起点，不是目标
> `systemd-analyze security` 按「暴露面」逐项列出哪些选项没设（`User=`、`CapabilityBoundingSet=`、`SystemCallFilter=`、`UMask=`…），给一个分数。**为了让分数变好看而堆选项，结果是服务起不来**——本次实测就发生过一次：把探针脚本放在 `/tmp` 又开了 `PrivateTmp=yes`，服务直接 `203/EXEC`（分数很漂亮，功能是零）。

**推荐加固流程（每步都要业务验证）**

1. **建基线**：`systemd-analyze security <unit>` 记录当前分数（本机一个默认单元 = 9.6 UNSAFE），`systemctl show` 记录当前沙箱属性。
2. **先加「低风险、几乎不影响功能」的**：`NoNewPrivileges=yes`、`UMask=0077`、`PrivateTmp=yes`（确认服务不依赖共享 `/tmp`）；再考虑 `ProtectSystem=full`——它会把 `/usr`、`/boot`、`/efi`、**`/etc`** 挂成只读，服务若要写 `/etc` 下的文件，必须单独用 `ReadWritePaths=` 开出来。**注意这一步对评分几乎没有帮助（实测 9.6 → 9.2），它的价值是防篡改，不是「降分」。**
3. **再加身份与能力收敛**（分数的主要贡献者）：`User=`（system 单元）、`CapabilityBoundingSet=`、`AmbientCapabilities=`。
4. **最后加文件系统严格化**：`ProtectSystem=strict` + `ProtectHome=yes` + `StateDirectory=`/`RuntimeDirectory=`/`LogsDirectory=` + `ReadWritePaths=`。
5. **逐项验证**：每加一组就 `daemon-reload` + `restart`，看 `status`/`journalctl`/端口/业务指标；出问题就回退到上一组，缩小范围。**验收命令固定这两条**：服务内 `grep -E " /(home|usr|etc) " /proc/self/mounts`（挂载真的变了吗）与 `/proc/<pid>/limits`、`/proc/<pid>/status`（身份与能力真的变了吗）。

### 实验 5：沙箱选项与「服务看到的世界」

> [!example]- 实验 5：把 `226/NAMESPACE`、`217/USER`、`216/GROUP`、设备收敛、inode 差异一次做出来
> **怎么做**：在 `/etc/systemd/system/` 建一组单元，探针脚本放 **`/usr/local/lib/lab08/probe.sh`**（不要放 `/tmp`）。探针打印 `id -u`、`/proc/self/status` 的 `NoNewPrivs`/`Cap*`、`stat -c %i /tmp`、`grep -E " /(home|usr|etc|boot)? " /proc/self/mounts`，并对 `/usr`、`/etc`、`/boot`、`/var/lib/<dir>`、`/var/log`、`/run`、`/root`、`/home/<user>`、`/tmp`、`/dev/shm` 逐个 `touch`。单元分五档：`raw`（无沙箱）、`full`（`ProtectSystem=full`）、`strict`（只加 `ProtectSystem=strict`）、`strichome`（strict + `ProtectHome=yes` + `User=realtyz`）、`hard`（再叠 `PrivateTmp`/`PrivateDevices`/`NoNewPrivileges`/`CapabilityBoundingSet=`/`SystemCallFilter=@system-service`/`ProtectProc=invisible`/`InaccessiblePaths=`）。另建 `rwmissing`（`ReadWritePaths=/nonexistent-lab08-path`）、`nouser`（`User=` 不存在）、`badgroup`（`Group=` 不存在）。全部 `daemon-reload` 后依次启动取证据。
> **预期**：`raw` 全部写成功、`/` 是 `rw`；`full` 只有 `/usr`、`/etc`、`/boot` 写失败；`strict` 连 `/var/log`、`/run`、`/tmp` 都失败，**但 `/home` 仍可写**；`strichome` 之后 `/home` 变 `tmpfs ro`、`ls /home` 被拒；`hard` 的 `/dev` 节点从 207 掉到 18、`/dev/mem` 消失、`unshare -U` 与 `lsmod` 失败；`rwmissing` → `226/NAMESPACE`；`nouser` → `217/USER`；`badgroup` → `216/GROUP`；`systemd-analyze security` 从 9.6 UNSAFE 降到 1.9 OK。
> **风险**：中（会在 `/var/lib`、`/var/log` 下建临时目录并写探针；**不要碰系统服务**，不要 `systemctl restart` 任何发行版单元）；**耗时**：约 20 分钟；**回滚**：`systemctl stop` 各单元、`systemctl clean --what=all`、`rm -f /etc/systemd/system/lab08*.service`、`rm -rf /usr/local/lib/lab08 /var/lib/lab08* /etc/lab08-secret`、`daemon-reload`、`reset-failed`。
> 机器：任意有 root 的**可快照实验机**；`DynamicUser=`、`PrivateUsers=`、`User=` 真换用户都必须在 system 单元上做（本机实测 systemd 255）。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 「沙箱更安全，先全开上」 | 服务会以 `226/NAMESPACE`、`200/CHDIR`、`203/EXEC`、写失败等形式起不来；必须逐项验证 |
| 把 `ProtectSystem=strict` 当成「全盘只读」 | 实测**不写 `ProtectHome=` 时 `/home` 仍是 `rw`**，写 `$HOME` 照样成功；`strict` 只保证 `/`（以及 `/usr`、`/etc`、`/boot`）只读 |
| 用 `ProtectHome=yes` 却期待「还能读 `/home`」 | `yes` 是「不可访问且为空」（实测换成 `tmpfs ro,nosuid,nodev,noexec`，`ls /home` → `Permission denied`）；要读用 `read-only` |
| `PrivateTmp=yes` 只是「换个目录」 | 它是私有 tmpfs，宿主看不到、停止即消失；**脚本放 `/tmp` 再开它 = 必得 `203/EXEC`**（实测踩过） |
| 以为 `PrivateDevices=yes` 只是「少几个设备」 | 实测 `/dev` 从 207 个节点变 18 个、`/dev/sda*` 与 `/dev/mem` 全部消失、`/dev` 从 `devtmpfs rw` 变 `tmpfs ro,nosuid,noexec,size=4096k`；需要裸设备的业务会直接坏 |
| `ReadWritePaths=` 指向不存在的路径 | 服务起不来，报 `226/NAMESPACE`；用 `StateDirectory=`/`RuntimeDirectory=` 让 systemd 建目录 |
| 以为 `StateDirectory=` 建好目录就一定能写 | 实测「目录属主」与「可写口」是两件事：`uid=1000` 的服务写 root 拥有的 `ReadWritePaths=` 目录仍然 FAIL；不把 `StateDirectory=` 加进 `ReadWritePaths=`（`strict` 下）也写不进去 |
| 在用户单元里写 `User=root` | 报 `216/GROUP`；用户级实例不能切身份——要真换用户必须用 system 单元（实测 system 单元 `User=realtyz` 服务内 `uid=1000`） |
| 以为 `User=` 写错会「照常以 root 跑」 | 目标不存在时是**硬失败**：用户不存在 `217/USER`、组不存在 `216/GROUP` |
| 为了刷 `systemd-analyze security` 的分加了一堆选项 | 分数从 9.6 掉到 1.9 很好看，但服务可能已经起不来；分数是暴露面参考，不是验收标准 |
| 以为加固后「服务还能自己再套一层隔离」 | 加上 `RestrictNamespaces=yes`、`CapabilityBoundingSet=` 之后，实测服务内 `unshare -U` 报 `Operation not permitted`、`lsmod` FAIL——这是设计预期，不是沙箱坏了 |
| `SystemCallFilter=` 一上来就写得很严 | 服务可能因 `SIGSYS` 或缺系统调用而崩；先从 `@system-service` 开始 |
| 把 `NoNewPrivileges=yes` 当可选项 | 它是**一处生效、整棵进程树受益**的高性价比选项（实测 `NoNewPrivs` 由 `0` 变 `1`），且极少影响正常业务 |

## 决策练习

> [!question]- 场景：你给一个自研服务加了 `ProtectSystem=strict`，服务启动失败，日志只有 `status=226/NAMESPACE`。同事说「沙箱太麻烦，删掉吧」。
> A. 删掉 `ProtectSystem=strict`，恢复业务
> B. 用 `systemctl show -p ProtectSystem -p ReadWritePaths -p StateDirectory` 看配置，确认服务需要写哪些路径，用 `StateDirectory=`/`RuntimeDirectory=` 建目录并加进 `ReadWritePaths=`
> C. 改成 `ProtectSystem=full` 试试
> **答案：B。**
> A 放弃了整章最有价值的加固项。
> C 是猜测式降级：`full` 只是不再保护 `/var`、`/home` 这些路径（让服务「碰巧能写」），并没有解决 `226/NAMESPACE` 的根因（要写的路径没被显式开出来，或者路径本身不存在），还顺手把 `/etc` 挂成了只读——这是用降低安全性换一次侥幸通过。
> B 是正解：**把「服务需要写什么」变成显式的 `ReadWritePaths=`，让 systemd 负责建目录与权限**（并顺手核对目录属主与 `User=` 是否匹配）。

## 要点自测

> [!question]- `ProtectSystem`、`ProtectHome`、`PrivateTmp`、`PrivateDevices`、`ReadWritePaths` 分别改变什么？
> - `ProtectSystem=`：把系统目录（到 `strict` 时是 `/` 整体）挂成只读；**不管 `/home`**。
> - `ProtectHome=`：管 `/home`、`/root`、`/run/user`；`yes` 是「空且不可访问」（实测 `tmpfs ro,nosuid,nodev,noexec`、`ls /home` 被拒），`read-only` 才是只读原目录。
> - `PrivateTmp=`：给服务一个私有的 `/tmp`（与 `/var/tmp`），宿主看不到、停止即消失（实测服务内 inode `1311092` vs 宿主 `1179649`）。
> - `PrivateDevices=`：把 `/dev` 从 207 个节点收到 18 个并换成 `tmpfs ro,nosuid,noexec`，`/dev/sda*`、`/dev/mem`、`/dev/loop-control` 全部消失。
> - `ReadWritePaths=`：在只读世界里开一个可写口；路径必须存在（否则 `226/NAMESPACE`），且属主要能对上。
> - **第一反应不要是什么**：不要为了排障直接删掉沙箱；先看服务真正需要的写入路径，也不要以为 `strict` 会把 `/home` 一起锁上。

> [!question]- `NoNewPrivileges`、`CapabilityBoundingSet`、`AmbientCapabilities`、`DynamicUser` 各管什么？
> - `NoNewPrivileges=yes`：禁止服务及其子进程通过任何方式获得新特权（SUID、file capabilities 都失效）；实测 `NoNewPrivs` 由 `0` 变 `1`。
> - `CapabilityBoundingSet=`：限定服务**最多**能持有哪几项 capability，设为空就全不给（实测 `CapBnd` 从 `000001ffffffffff` 变 `0000000000000000`，`lsmod` 随之 FAIL）。
> - `AmbientCapabilities=`：让非 root 服务在 `execve` 之后仍**保留**指定 capability（如绑低端口用 `CAP_NET_BIND_SERVICE`）。
> - `DynamicUser=yes`：每次启动临时分配 UID/GID（实测 `61593`），`StateDirectory=` 变成 `private/` 下的符号链接，停止即回收。
> - **第一反应不要是什么**：不要用「让服务跑 root」来替代这几项——那正是它们要消灭的做法。

> [!question]- 看到 `226/NAMESPACE`、`217/USER`、`216/GROUP`、`200/CHDIR`、`203/EXEC` 分别往哪想？
> - `226/NAMESPACE`：沙箱/挂载设置失败，最常见是 `ReadWritePaths=` 路径不存在或 `ProtectSystem` 与写入冲突。
> - `217/USER`：`User=` 指定的用户不存在（`Failed to determine user credentials: No such process`）。
> - `216/GROUP`：切组/用户失败，比如**用户单元里写了 `User=`**、或 `Group=` 指定的组不存在。
> - `200/CHDIR`：`WorkingDirectory=` 不存在或无权限。
> - `203/EXEC`：`ExecStart=` 的二进制不存在/不可执行/解释器缺失——**开了 `PrivateTmp=yes` 而脚本放在 `/tmp` 时就是这个码**。
> - **第一反应不要是什么**：不要把这些 systemd 退出码当作应用退出码去查业务代码；`systemd-analyze exit-status 200 203 216 226` 会直接给出 `CHDIR / EXEC / GROUP / NAMESPACE` 的对照。
