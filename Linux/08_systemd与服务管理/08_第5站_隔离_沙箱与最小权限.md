# 第 5 站：隔离（沙箱与最小权限）

> **这篇讲什么**：systemd 不只给服务一个资源笼子，还能改变服务**看到的世界**——能写哪些目录、能看到哪些设备、能不能换身份、最多持有哪些特权。这一篇讲清沙箱选项的四类、各自的报错形态，以及**给服务加沙箱时怎么不把它弄坏**。

## 0. 30 秒速览

> [!abstract] 这一篇只要记住七句话
> - **沙箱的目的是「让服务只能看到它需要的」**：文件系统只读、私有 `/tmp`、私有设备、能力收敛、系统调用过滤。
> - **四类选项要分开看**：文件系统视图（`ProtectSystem`/`ProtectHome`/`ReadWritePaths`）、名字空间（`PrivateTmp`/`PrivateDevices`）、权限收敛（`NoNewPrivileges`/`CapabilityBoundingSet`/`User`）、系统调用过滤（`SystemCallFilter`）。
> - **改了沙箱后，报错往往不是业务错误码，而是 systemd 的退出码**：实测 `ReadWritePaths=` 指向不存在的路径 → `status=226/NAMESPACE`；用户单元里写 `User=root` → `status=216/GROUP`；`WorkingDirectory=` 不存在 → `200/CHDIR`；`ExecStart=` 不可执行 → `203/EXEC`。
> - **`ProtectSystem=strict` 按文档是整个文件系统层级只读**（除 `/dev`、`/proc`、`/sys` 与显式 `ReadWritePaths=`）；`yes`/`full` 只管 `/usr`、`/boot`、`/efi`（`full` 再加 `/etc`）。写日志、写 pid、写缓存都要显式开口，**而且要用第 2 节的命令确认它真的生效**。
> - **`PrivateTmp=yes` 是私有 tmpfs**：实测服务内 `/tmp` inode 为 12434、宿主为 73729；宿主看不到服务写进去的文件，服务停止后内容消失。
> - **用 `RuntimeDirectory=`/`StateDirectory=` 让 systemd 帮你建可写目录**，比手写 `ReadWritePaths=` 更安全也不容易写错权限。
> - **加固要逐项加、逐项验**：`systemd-analyze security` 的分数只是暴露面参考，**不要为了刷分把服务配到起不来**。

## 1. 沙箱的四类选项

| 类别 | 代表选项 | 改变什么 |
| --- | --- | --- |
| 文件系统视图 | `ProtectSystem=`、`ProtectHome=`、`ReadWritePaths=`、`PrivateTmp=` | 服务能读/写哪些路径 |
| 名字空间与设备 | `PrivateDevices=`、`PrivateNetwork=`、`ProtectProc=`、`RestrictNamespaces=` | 服务能看到哪些设备/网络/proc |
| 权限收敛 | `User=`/`Group=`、`NoNewPrivileges=`、`CapabilityBoundingSet=`、`AmbientCapabilities=`、`DynamicUser=` | 服务以什么身份跑、最多持有什么特权 |
| 系统调用与网络 | `SystemCallFilter=`、`SystemCallArchitectures=`、`RestrictAddressFamilies=` | 服务能调用哪些系统调用、能开哪些协议族 |

一组常用的保守沙箱（按业务逐项验证后再打开）：

```ini
[Service]
NoNewPrivileges=yes
ProtectSystem=strict
ProtectHome=yes
PrivateTmp=yes
PrivateDevices=yes
CapabilityBoundingSet=
SystemCallFilter=@system-service
ReadWritePaths=/var/lib/myapp /var/log/myapp
```

注意最后一项：**`ProtectSystem=strict` 之后，所有写入都必须被显式开出来**，否则服务会以各种「说不清的写失败」告终。

## 2. 文件系统视图：服务看到的目录树

`ProtectSystem=` 逐级收紧：

| 取值 | 效果 |
| --- | --- |
| `no`（默认） | 不做限制 |
| `yes` | `/usr`、`/boot`、`/efi` 只读（**不含 `/etc`**） |
| `full` | 在 `yes` 的基础上**再加 `/etc` 只读** |
| `strict` | 整个文件系统层级只读，只有 `/dev`、`/proc`、`/sys` 除外；写入要用 `ReadWritePaths=` 显式开 |

> [!important] `ProtectSystem` 只管这几处，别把它当成「整个系统都锁上了」
> `ProtectSystem=` 的管辖范围就是上表那几处；`/home`、`/root`（以及 `/run/user`）是 **`ProtectHome=`** 的地盘，而且 `ProtectHome=yes` 是让它们「不可访问且为空」，`ProtectHome=read-only` 才是只读。**本机（WSL2）实测还有一个容易漏掉的边界**：user 单元里 `strict` 确实让 `/` 变成了 `ro`，但服务命名空间里的 `/home` 仍是一份独立的 `rw` 挂载，往 `$HOME` 写依然成功。
>
> 所以「加了 `strict` 就等于全盘只读」这句话必须自己验证。两条可复制的证据命令：
> ```bash
> systemd-run --user --pipe --wait --collect -p ProtectSystem=strict /bin/cat /proc/self/mounts   # 验证：服务命名空间里 / 的挂载选项，预期含 ro
> systemd-run --user --pipe --wait --collect -p ProtectSystem=strict /usr/bin/touch "$HOME/lab-write-test"   # 验证：没开 ReadWritePaths= 的路径是否真的写不进去（本机实测这条会成功，记得事后删文件）
> ```

```ini
ReadWritePaths=/var/lib/myapp /var/log/myapp
```

`ReadWritePaths=` 的作用是**在只读世界里开一个可写口**。实测把路径写成不存在的 `/nonexistent-lab-path` 时：

```text
$ journalctl --user -u lab-rwmissing.service -o cat | tail -2
lab-rwmissing.service: Main process exited, code=exited, status=226/NAMESPACE
lab-rwmissing.service: Failed with result 'exit-code'.
```

> [!warning] `ReadWritePaths=` 的路径必须存在
> systemd 不会替你创建它。**推荐做法**：让 systemd 用 `RuntimeDirectory=`/`StateDirectory=` 先建目录，再把路径写进 `ReadWritePaths=`：
> ```ini
> [Service]
> StateDirectory=myapp            # 自动创建 /var/lib/myapp 并设好属主
> LogsDirectory=myapp             # 自动创建 /var/log/myapp
> RuntimeDirectory=myapp          # 自动创建 /run/myapp（服务停止后可清理）
> ProtectSystem=strict
> ReadWritePaths=/var/lib/myapp /var/log/myapp /run/myapp
> ```
> 这样既不用手写 `mkdir`，也不会因为路径不存在把服务卡在 `226/NAMESPACE`。
>
> **注意这几个路径是 system 单元的落点**：在 user 单元里，`StateDirectory=` 落在 `$XDG_STATE_HOME`（`~/.local/state/myapp`）、`LogsDirectory=` 落在 `~/.local/state/log/myapp`、`RuntimeDirectory=` 落在 `$XDG_RUNTIME_DIR/myapp`，**不是** `/var/lib`、`/var/log`、`/run`。本章实验都在 user 单元里做，照抄 system 路径会找不到目录（对照表见第 13 篇第 4 节）。

## 3. 私有名字空间：`PrivateTmp` 与 `PrivateDevices`

`PrivateTmp=yes` 给服务一个独立的 `/tmp`（以及 `/var/tmp`）。实测 inode 差异：

```text
$ stat -c %i /tmp                                     # 宿主
73729
$ systemd-run --user --wait --collect --property=PrivateTmp=yes \
    /bin/bash -c "stat -c %i /tmp > \$HOME/lab-private-inode.txt" && cat ~/lab-private-inode.txt
12434                                                 # 服务内
```

实用含义：

- 服务写进 `/tmp` 的文件，**其它服务/宿主用户看不到**；排查时要进命名空间看（`ls -l /proc/<pid>/root/tmp`、`nsenter -t <pid> -m ls /tmp`，需要权限）。
- **私有 `/tmp` 随服务停止就消失**，不适合放跨重启的持久文件；要跨重启用 `StateDirectory=`，要跨进程共享且不持久用 `RuntimeDirectory=`。
- 依赖 `/tmp` 里共享锁文件/IPC 的架构，开了 `PrivateTmp` 会直接坏掉。

| 场景 | 服务看到的 `/tmp` | 宿主/其他服务能看到吗 |
| --- | --- | --- |
| 普通服务 | 宿主 `/tmp` | 能 |
| `PrivateTmp=yes` | 私有 tmpfs | 不能（除非进命名空间） |
| 容器（Docker/K8s） | 容器自己的 `/tmp` | 不能 |

`PrivateDevices=yes` 把服务能看到的设备节点收敛到最小集（不能直接碰裸设备、`/dev/mem` 之类），普通业务服务建议打开；需要访问特定设备（如 GPU、串口）时再按需放开。

## 4. 权限收敛：身份、能力与提权面

### 4.1 身份

```ini
[Service]
User=myapp
Group=myapp
SupplementaryGroups=myapp-data
```

`SupplementaryGroups=` 只在服务确实需要附加组时写。

**`User=` 只对 system 单元有效**。用户单元里写 `User=root` 实测报：

```text
$ journalctl --user -u lab-userdir.service -o cat | tail -3
lab-userdir.service: Changing group credentials failed: Operation not permitted
lab-userdir.service: Main process exited, code=exited, status=216/GROUP
```

`DynamicUser=yes` 可以让 systemd 在启动时分配一个动态 UID/GID，服务停止后回收；适合不需要固定 UID 的无状态服务（本机未实测）。

### 4.2 提权面收敛

| 选项 | 作用 |
| --- | --- |
| `NoNewPrivileges=yes` | 服务及其子进程**永远不能获得新特权**：SUID/SGID 失效、file capabilities 失效——一处设好，整棵进程树都受保护 |
| `CapabilityBoundingSet=` | 限定服务**最多**能持有哪些 capability；设为空 = 一项都不给 |
| `AmbientCapabilities=` | 让**非 root** 服务在 `execve` 后仍保留指定 capability（如绑低端口用 `CAP_NET_BIND_SERVICE`） |
| `RestrictSUIDSGID=yes` | 禁止创建 SUID/SGID 文件 |

非 root 服务绑 80 端口的正解之一：

```ini
[Service]
User=myapp
CapabilityBoundingSet=CAP_NET_BIND_SERVICE
AmbientCapabilities=CAP_NET_BIND_SERVICE
NoNewPrivileges=yes
```

发行版自带单元给了一个可参考的实现——本机 `systemd-resolved.service` 用了 `User=`、`ProtectSystem=strict`、`PrivateTmp=yes`，以及 `CapabilityBoundingSet=CAP_SETPCAP CAP_NET_RAW CAP_NET_BIND_SERVICE`。

### 4.3 系统调用与网络

```ini
SystemCallFilter=@system-service     # 只允许「一般服务需要的」系统调用组
SystemCallArchitectures=native       # 只允许本机架构的系统调用
RestrictAddressFamilies=AF_INET AF_INET6 AF_UNIX
```

`SystemCallFilter` 语义是「**先拒绝，再按规则放行**」；写得太严会让服务以 `SIGSYS` 或各种奇怪错误退出。**开局建议只加 `@system-service`**，再按报错逐步调整。

## 5. 打分与加固流程

```text
$ systemd-analyze --user security lab-limit.service | tail -3
→ Overall exposure level for lab-limit.service: 9.0 UNSAFE 😨
```

`systemd-analyze security` 按「暴露面」逐项列出哪些选项没设（`User=`、`CapabilityBoundingSet=`、`SystemCallFilter=`、`UMask=`…），给一个分数。**分数只是起点，不是目标**：

**推荐加固流程（每步都要业务验证）**

1. **建基线**：`systemd-analyze security <unit>` 记录当前分数，`systemctl show` 记录当前沙箱属性。
2. **先加「低风险、几乎不影响功能」的**：`NoNewPrivileges=yes`、`PrivateTmp=yes`（确认服务不依赖共享 `/tmp`）；再考虑 `ProtectSystem=full`——它会把 `/usr`、`/boot`、`/efi`、**`/etc`** 挂成只读，服务若要写 `/etc` 下的文件，必须单独用 `ReadWritePaths=` 开出来。
3. **再加身份与能力收敛**：`User=`（system 单元）、`CapabilityBoundingSet=`、`AmbientCapabilities=`。
4. **最后加文件系统严格化**：`ProtectSystem=strict` + `StateDirectory=`/`RuntimeDirectory=`/`LogsDirectory=` + `ReadWritePaths=`。
5. **逐项验证**：每加一组就 `daemon-reload` + `restart`，看 `status`/`journalctl`/端口/业务指标；出问题就回退到上一组，缩小范围。

### 实验 5：沙箱选项与「服务看到的世界」

> [!example]- 实验 5：制造一次 `226/NAMESPACE`、一次 `216/GROUP`、一次 inode 差异
> **怎么做**：建三个用户单元：`lab-sandbox`（`ProtectSystem=strict` + `PrivateTmp=yes` + `NoNewPrivileges=yes` + `ReadWritePaths=%t/lab-rw`）、`lab-rwmissing`（`ReadWritePaths=/nonexistent-lab-path`）、`lab-userdir`（写 `User=root`）。其中 `%t` 是运行时目录占位符：在 user 单元里是 `$XDG_RUNTIME_DIR`，所以 `%t/lab-rw` 会落到这个用户自己的运行时目录下。分别启动，用 `journalctl --user -u` 与 `systemd-run --property=PrivateTmp=yes` 取证据；再看服务内 `cat /proc/self/mounts`，确认 `strict` 把 `/` 变成了 `ro`。
> **预期**：`lab-sandbox` 正常，且服务内 `cat /proc/self/mounts` 能看到 `/` 是 `ro`（**这一步才是「strict 真的生效了」的证据，只看服务起没起来是不够的**）；`lab-rwmissing` → `226/NAMESPACE`；`lab-userdir` → `216/GROUP`；私有 `/tmp` 的 inode 与宿主不同（本机实测 12434 vs 73729）。顺带验证边界：`strict` 下往 `$HOME` 写仍可能成功（本机 WSL2 实测如此，因为 `/home` 是独立挂载），所以「strict = 全盘只读」要按环境实测。
> **风险**：低（用户单元）；**耗时**：约 10 分钟；**回滚**：停服务、删文件、`daemon-reload`、`reset-failed`。
> 机器：任意能跑 `systemctl --user` 的环境；`User=` 真换用户与 `DynamicUser` 必须在可快照的实验机用 system 单元补做。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 「沙箱更安全，先全开上」 | 服务会以 `226/NAMESPACE`、`200/CHDIR`、写失败等形式起不来；必须逐项验证 |
| `PrivateTmp=yes` 只是「换个目录」 | 它是私有 tmpfs，宿主看不到、停止即消失；依赖共享 `/tmp` 的架构会直接坏 |
| `ReadWritePaths=` 指向不存在的路径 | 服务起不来，报 `226/NAMESPACE`；用 `StateDirectory=`/`RuntimeDirectory=` 让 systemd 建目录 |
| 在用户单元里写 `User=root` | 报 `216/GROUP`；用户级实例不能切身份，要真换用户用 system 单元 |
| 把 `ProtectSystem=strict` 当成「只读 `/usr`」 | `strict` 的目标是**整个文件系统层级只读**，写入需求要靠 `ReadWritePaths=` 逐个开；加完之后务必用 `/proc/self/mounts` 确认范围（子挂载可能不在保护内） |
| 为了刷 `systemd-analyze security` 的分加了一堆选项 | 分数高但服务功能坏了；分数是暴露面参考，不是验收标准 |
| `SystemCallFilter=` 一上来就写得很严 | 服务可能因 `SIGSYS` 或缺系统调用而崩；先从 `@system-service` 开始 |
| 把 `NoNewPrivileges=yes` 当可选项 | 它是**一处生效、整棵进程树受益**的高性价比选项，且极少影响正常业务 |

## 决策练习

> [!question]- 场景：你给一个自研服务加了 `ProtectSystem=strict`，服务启动失败，日志只有 `status=226/NAMESPACE`。同事说「沙箱太麻烦，删掉吧」。
> A. 删掉 `ProtectSystem=strict`，恢复业务
> B. 用 `systemctl show -p ProtectSystem -p ReadWritePaths -p StateDirectory` 看配置，确认服务需要写哪些路径，用 `StateDirectory=`/`RuntimeDirectory=` 建目录并加进 `ReadWritePaths=`
> C. 改成 `ProtectSystem=full` 试试
> **答案：B。**
> A 放弃了整章最有价值的加固项。
> C 是猜测式降级：`full` 只是不再保护 `/var`、`/home` 这些路径（让服务「碰巧能写」），并没有解决 `226/NAMESPACE` 的根因（要写的路径没被显式开出来，或者路径本身不存在），还顺手把 `/etc` 挂成了只读——这是用降低安全性换一次侥幸通过。
> B 是正解：**把「服务需要写什么」变成显式的 `ReadWritePaths=`，让 systemd 负责建目录与权限**。

## 要点自测

> [!question]- `ProtectSystem`、`PrivateTmp`、`ReadWritePaths` 分别改变什么？
> - `ProtectSystem=`：把系统目录（到 `strict` 时是整个文件系统）挂成只读。
> - `PrivateTmp=`：给服务一个私有的 `/tmp`（与 `/var/tmp`），宿主看不到、停止即消失。
> - `ReadWritePaths=`：在只读世界里开一个可写口；路径必须存在。
> - **第一反应不要是什么**：不要为了排障直接删掉沙箱；先看服务真正需要的写入路径。

> [!question]- `NoNewPrivileges`、`CapabilityBoundingSet`、`AmbientCapabilities` 各管什么？
> - `NoNewPrivileges=yes`：禁止服务及其子进程通过任何方式获得新特权（SUID、file capabilities 都失效）。
> - `CapabilityBoundingSet=`：限定服务**最多**能持有哪几项 capability，设为空就全不给。
> - `AmbientCapabilities=`：让非 root 服务在 `execve` 之后仍**保留**指定 capability（如绑低端口用 `CAP_NET_BIND_SERVICE`）。
> - **第一反应不要是什么**：不要用「让服务跑 root」来替代这三项——那正是它们要消灭的做法。

> [!question]- 看到 `226/NAMESPACE`、`216/GROUP`、`200/CHDIR`、`203/EXEC` 分别往哪想？
> - `226/NAMESPACE`：沙箱/挂载设置失败，最常见是 `ReadWritePaths=` 路径不存在或 `ProtectSystem` 与写入冲突。
> - `216/GROUP`：切换组/用户失败，比如用户单元里写了 `User=`、目标用户不存在。
> - `200/CHDIR`：`WorkingDirectory=` 不存在或无权限。
> - `203/EXEC`：`ExecStart=` 的二进制不存在/不可执行/解释器缺失。
> - **第一反应不要是什么**：不要把这些 systemd 退出码当作应用退出码去查业务代码。
