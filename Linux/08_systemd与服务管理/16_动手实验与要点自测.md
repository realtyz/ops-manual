## 2. 实验步骤索引

> [!example]- 实验 1：`daemon-reload` 的完整生效链（子笔记 04）
> **怎么做**：在 `/etc/systemd/system/` 建 `lab08-simple.service`（`Environment=PHASE=1`、`ExecStart=/bin/bash -c "exec sleep 300"`），启动并记下 `MainPID`；把文件改成 `PHASE=2`，分「不 reload / `daemon-reload` / `restart`」三步，每步对照 `systemctl show -p Environment --value` 与 `tr "\0" "\n" < /proc/<MainPID>/environ | grep PHASE=`；再加一个 drop-in（`Environment=EXTRA=from-dropin`、`LimitNOFILE=256`）验证叠加。
> **预期**：① 两处都还是 `PHASE=1`，`status` 给 `changed on disk` 警告；② `show` 是 `PHASE=2`、进程仍是 `PHASE=1`、`MainPID` 不变（实测 `10813`）；③ `restart` 后 `MainPID` 换成 `10881`、进程才是 `PHASE=2`；drop-in 后 `show -p DropInPaths` 给出 `/etc/systemd/system/lab08-simple.service.d/10-extra.conf`，`/proc/<MainPID>/limits` 的 `Max open files` 是 `256 256`。
> **风险**：低（自建 system 单元 + `sleep`）；**耗时**：约 10 分钟；**回滚**：`systemctl stop lab08-simple.service`、`rm -f /etc/systemd/system/lab08-simple.service` 与 `.d/`、`daemon-reload`。

> [!example]- 实验 2：`Type=` 与「假启动失败」（子笔记 06）
> **怎么做**：`Type=simple` 与 `Type=forking` 跑同一条 `ExecStart=/bin/bash -c "sleep 120 &"`；再做一个 `Type=notify` 的脚本，让**子进程**用 python 直接往 `$NOTIFY_SOCKET` 写 `READY=1`，观察被拒与超时，再加 `NotifyAccess=all` 复测（同时把 `TimeoutStartSec` 设成 8 秒，别等 90 秒）。
> **预期**：`simple` → `MainPID=0`、`SubState=dead`；`forking` → `MainPID=12510`、`active (running)`；`notify` 子进程直写 → `Got notification message from PID …, but reception only permitted for main PID …`，默认等满 **90.237 秒**，设 `TimeoutStartSec=8s` 则 8 秒出头失败；改 `NotifyAccess=all` 后 0.04 秒级成功。
> **风险**：低；**耗时**：约 10 分钟（含一次超时观察）；**回滚**：停服务、删单元、`daemon-reload`、`reset-failed`。

> [!example]- 实验 3：依赖与顺序（子笔记 05）
> **怎么做**：`lab08-b` 声明 `Wants=lab08-a.service` + `After=lab08-a.service`，`lab08-a` 是耗时 3 秒的 `oneshot`；用 `journalctl -u lab08-a -u lab08-b -o short-precise --no-pager | tail -5` 对时间戳；再去掉 `After=` 重跑。
> **预期**：有 `After` 时 `lab08-a` 的 `Finished`（`08:05:09.561157`）早于 `lab08-b` 的 `Starting`（`08:05:09.574918`），差 13.8 毫秒；去掉后两者在 `10.780860` / `10.781683` 同拍启动（差 0.8 毫秒），`lab08-b` 先跑完。
> **风险**：低；**耗时**：约 5 分钟；**回滚**：`rm -f /etc/systemd/system/lab08-a.service /etc/systemd/system/lab08-b.service`、`daemon-reload`、`reset-failed`。

> [!example]- 实验 4：资源上限的生效与验证（子笔记 07）
> **怎么做**：单元里写 `LimitNOFILE=64`、`MemoryMax=32M`、`CPUQuota=10%`、`TasksMax=16`，用 `systemctl show`、服务内 `ulimit -n`、`/proc/<MainPID>/limits`、以及 `/sys/fs/cgroup/system.slice/<unit>/{memory.max,cpu.max,pids.max}` 四方对照；再起一个 `CPUQuota=20%` 的忙循环跑 10 秒，与无配额对照比 `cpu.stat`。
> **预期**：`LimitNOFILE=64`、`MemoryMax=33554432`、`CPUQuotaPerSecUSec=100ms`、`TasksMax=16`、`ControlGroup=/system.slice/lab08-limit.service`；cgroup 文件分别是 `33554432`、`10000 100000`、`16`；20% 配额组 10 秒只拿到 `usage_usec 2022027`（2.02 秒），对照 `10010754`（10.01 秒），且 `nr_throttled=100`。
> **风险**：低（配额已限死 CPU）；**耗时**：约 15 分钟；**回滚**：停服务、删单元、`daemon-reload`。

> [!example]- 实验 5：沙箱选项与「服务看到的世界」（子笔记 08）
> **怎么做**：探针脚本放 `/usr/local/lib/lab08/probe.sh`（**不要放 `/tmp`**）；建 `raw`/`full`/`strict`/`strichome`/`hard` 五档单元，外加 `rwmissing`（`ReadWritePaths=` 指向不存在路径）、`nouser`（`User=` 不存在）、`badgroup`（`Group=` 不存在）；另建一对只差 `PrivateDevices=` 的单元。用服务内 `grep -E " /(home|usr|etc|boot)? " /proc/self/mounts`、`stat -c %i /tmp`、`ls /dev | wc -l`、`/proc/self/status` 取证据。
> **预期**：`raw` 全部可写、`/` 是 `rw`；`full` 只有 `/usr`、`/etc`、`/boot` 写失败；`strict` 连 `/var/log`、`/run`、`/tmp` 都失败但 **`/home` 仍可写**；`strichome` 后 `/home` 变 `tmpfs ro,nosuid,nodev,noexec`、`ls /home` 被拒；`PrivateDevices=yes` 让 `/dev` 从 **207** 个节点变 **18** 个、`/dev/sda*` 与 `/dev/mem` 消失；`rwmissing` → `226/NAMESPACE`、`nouser` → `217/USER`、`badgroup` → `216/GROUP`；`systemd-analyze security` 从 **9.6 UNSAFE** 降到 **1.9 OK**。
> **风险**：中（会建 `/var/lib`、`/var/log` 下的临时目录与 `/etc/lab08-secret`，并写探针文件）；**耗时**：约 20 分钟；**回滚**：`systemctl stop` + `systemctl clean --what=all`、删单元与 `/usr/local/lib/lab08`、`rm -rf /var/lib/lab08* /etc/lab08-secret`、`daemon-reload`、`reset-failed`。

> [!example]- 实验 6：journald 字段、容量与限流（子笔记 09）
> **怎么做**：`systemd-cat` 造一条消息看 `-o json` 字段；`journalctl --disk-usage` 看占用；`systemd-analyze cat-config systemd/journald.conf` 看配置来源；用两个 `oneshot` 单元（`LogRateLimitIntervalSec=1s` + `LogRateLimitBurst=5`，另一次用 `30s` + `5`）做 200 条 stdout / 200 条 `logger` 的限流对照，统计写入条数、读到的条数与 journald 自己发的 `Suppressed` 告警；容量部分**先确认保留要求**，再做 `journalctl --disk-usage` → `--vacuum-size=50M` → `--vacuum-time=1h`（**不可回滚**），每步记录占用与文件数。
> **预期**：字段完整（system 单元用 `_SYSTEMD_UNIT` + `_SYSTEMD_SLICE`，`_TRANSPORT` 分别能看出 `journal`/`stdout`/`syslog`）；`--disk-usage` 是**会变的数**（本机同一小时内读到 `16.0M`/`20.6M`/`26.2M`/`26.3M`/`48.9M`/`53.9M`）；限流对照本机实测 200 条 stdout 只落 **18 条**、`logger` 落 97 条，且 `grep -i suppress` **没有** journald 自己的告警——**正确结论是「不能依赖单元级限流兜底」，不是「文档不成立」**；容量部分实测 `--vacuum-size=50M` 释放 **4.9M**（53.9M → 48.9M），`--vacuum-time=1h` 再释放 **28.2M**（→ 20.6M、文件数 11 → 3），随后 `journalctl -b -1` 变成 `No journal boot entry found from the specified boot offset (-1).`。**只有活动文件时 `--vacuum-*` 会 `freed 0B`——那是正常现象，不是命令失效。**
> **风险**：中（`--vacuum-time=` 会**真删历史启动的 journal**，不可回滚）；**耗时**：约 15 分钟；**回滚**：删单元、`daemon-reload`、`reset-failed`；日志裁剪不可回滚。

> [!example]- 实验 7：`start-limit-hit` 与 `reset-failed`（子笔记 10）
> **怎么做**：`ExecStart=/bin/false` + `Restart=always` + `RestartSec=1` + `[Unit]` 里 `StartLimitIntervalSec=10`、`StartLimitBurst=3`；启动后等 8 秒看 `NRestarts` 与 `Start request repeated too quickly.`，再 `reset-failed`，然后再观察「`stop` 不触发 `Restart=`」与「`on-failure` 遇退出码 0 不重启」两个边界。
> **预期**：`NRestarts=3`、`ExecMainStatus=1`、`Result=exit-code`、`Active: failed`；`reset-failed` 后 `Result=success`、`NRestarts=0`（可再次启动，但根因未改会再次失败）；`systemctl stop` 后 `NRestarts=0`、`SubState=dead`，**不会**被 `Restart=always` 拉起来。
> **风险**：中（会真的制造重启风暴）——**只在实验机、只对 `lab08-*` 单元做**；**耗时**：约 10 分钟；**回滚**：`reset-failed` + 删单元 + `daemon-reload`。

> [!example]- 实验 8：timer 与日历表达式（子笔记 12）
> **怎么做**：建 `oneshot` service + timer（`OnActiveSec=1s`、`OnUnitActiveSec=5s`、`AccuracySec=1s`），`list-timers` 与 `journalctl -o short-precise` 观察触发；跑 `systemd-analyze calendar`/`timespan` 的四个例子；再做一个 `Persistent=true` 的 timer，把 `/var/lib/systemd/timers/stamp-*.timer` 回拨 3 天后重启 timer 观察补跑。
> **预期**：首跑约 1 秒、之后约 5 秒一次（实测 `08:06:49.58 → 08:06:54.82 → 08:06:56.97`，**会有抖动**）；日历表达式给出归一化形式与 UTC 对照（`*:0/15` → `*-*-* *:00/15:00`）；回拨 stamp 后立刻补跑一次（`RUN-AT-…`）。
> **风险**：低；**耗时**：约 10 分钟；**回滚**：停 timer、删两个文件与 stamp 文件、`daemon-reload`。

> [!example]- 实验 9：cron 的环境与 `%` 转义（子笔记 12）
> **怎么做**：**先备份 `crontab -l > ~/crontab.bak`**，再在 `/etc/cron.d/` 放一个片段，装两条任务（`env > …` 与 `echo job-$(date +\%s) …`），等一个整分钟后核对环境与日志（`journalctl -u cron`）。
> **预期**：环境只有 `HOME=/root`、`LOGNAME=root`、`PATH=/usr/local/sbin:…`、`LANG=en_US.UTF-8`、`SHELL=/bin/sh`、`PWD=/root`；`\%` 被正确转义（实测产出 `job-1789805341`）；`journalctl -u cron` 能看到 `CRON[pid]: (root) CMD (…)`。
> **风险**：中（会覆盖/新增 crontab 与 `/etc/cron.d`）；**耗时**：约 5 分钟；**回滚**：删 `/etc/cron.d/<片段>`、从备份恢复 crontab。

> [!example]- 实验 10：tmpfiles 的 age 语义（子笔记 13）
> **怎么做**：在 `/etc/tmpfiles.d/` 放一条规则 `d <目录> 0700 root root 30d`，`touch -d "40 days ago"` 造一个文件，`stat -c "%n mtime=%y ctime=%z"` 看时间戳，`systemd-tmpfiles --clean` 看是否被删；再改成 `m:30d` 重跑。顺带验一验本机**不支持** `--dry-run`。
> **预期**：默认规则下**不**删（`mtime=2026-08-10` 但 `ctime=2026-09-19`，默认 `age-by=abcmABM` 保护它）；`m:30d` 下**删**；`systemd-tmpfiles --dry-run` 报 `unrecognized option '--dry-run'`。
> **风险**：低（专用临时目录）；**耗时**：约 10 分钟；**回滚**：删规则文件与目录、`daemon-reload`。

> [!example]- 实验 11：系统级能力清单（本次已在本机做完）
> **怎么做**：这一条在真机上一次性把「只有 root / 只有系统级才能做」的动作补齐。本机实测的命令与结果如下（全部已跑通并清理）：
> ```bash
> systemctl daemon-reload; systemd-analyze verify /etc/systemd/system/lab08-simple.service   # ① system 单元与语法
> systemctl enable --now lab08-simple.service; systemctl is-enabled lab08-simple.service      # ② 自启：建/删 multi-user.target.wants 软链
> systemctl show lab08-sec-hard.service -p User -p Group -p ProtectSystem -p PrivateTmp -p ReadWritePaths   # ③ 沙箱属性
> journalctl --disk-usage; journalctl --vacuum-size=50M; journalctl --vacuum-time=1h          # ④ 容量裁剪（先确认保留要求）
> systemd-analyze time; systemd-analyze blame | head -12; systemd-analyze critical-chain        # ⑤ 真机开机分析
> ```
> **实测结果**：① `verify_good_rc=0`；② `enable` 在 `/etc/systemd/system/multi-user.target.wants/` 下建软链、`is-enabled` 变 `enabled`，`disable` 删掉软链；③ **`User=realtyz` 真换身份**（服务内 `uid=1000`；**注意 `NoNewPrivs=0`、`CapBnd=000001ffffffffff`（满集）**——`User=` 只换 uid/gid，不清空 bounding set，实测见子笔记 08），`DynamicUser=yes` 分配到 **UID/GID 61593**，`PrivateUsers=yes` 的 `uid_map= 0 0 1 / 1000 1000 1`；④ `--vacuum-size=50M` 释放 **4.9M**、`--vacuum-time=1h` 再释放 **28.2M**（53.9M → 48.9M → 20.6M，文件数 11 → 3），随后 `journalctl -b -1` 报 `No journal boot entry found from the specified boot offset (-1).`；⑤ `Startup finished in 3.922s (kernel) + 2.439s (userspace) = 6.362s`，blame 第一是 `systemd-networkd-wait-online.service` 1.231 秒。
> **仍未实测（本实验环境不做）**：整机重启后的自启落地验证、`systemctl isolate`、`systemctl set-default` 的生效验收（都要重启或切 target）；`systemctl daemon-reexec`；`systemctl restart systemd-journald`。理由统一是：**本机只有 SSH、没有独立控制台，做坏了无法自救**，要留到「可快照且有控制台」的机器上做。
> **风险**：中高（系统单元、真换用户、journal 裁剪、开机分析）；**耗时**：约 1 小时。
> **RHEL 9 差异**（未实测，仅登记）：`chronyc tracking`/`chronyc sources -v`、`authselect`、`/etc/cron.d` 与 `at`/`anacron` 的默认安装状态。

> [!example]- 实验 12：T4 限时模拟（现象 → 定位 → 处置报告）
> **怎么做**：从主笔记第 6 节或 15 号手册挑一个现象，例如「服务 `active` 但行为不对」「定时任务没跑」「改了配置却不生效」或「命令成功但什么都没查到」。准备一台实验机，让同事或你自己从一组单元里制造一个故障；限时 15 分钟，只准按「读 `status` → `show` 关键属性 → `journalctl` → 定位站点 → 写出处置记录」的路径走。结束时必须交一份报告，包含：现象、卡在八站哪一站、三条证据、根因、止血动作、修复动作、回滚命令、下一步。
> **预期**：能独立定位到正确站点并给出证据；报告里能区分「止血」和「修复」，且至少写出一条「第一反应不要做什么」。**建议加一个必答项**：这份证据来自系统级还是用户级 manager？
> **风险**：低（实验机）；**耗时**：约 30 分钟（含复盘）；**回滚**：按报告中记录的回滚命令执行。
> 机器：实验机；计时器从看到现象开始。

## 3. 跨篇要点自测

> [!question]- 服务 `systemctl start` 失败，你的排查顺序是什么？
> - **先读状态四行**：`Loaded`（文件在哪、是否 masked）、`Active` + `Result`、`Main PID`/`Process` 的退出码、`CGroup`/`Tasks` 有没有残留。
> - **再看日志**：`journalctl -u <unit> -b --no-pager | tail -50`，配合 `-p err`。
> - **按退出码分流**：`200/CHDIR` 查 `WorkingDirectory`；`203/EXEC` 查二进制路径与权限（**开了 `PrivateTmp=yes` 而脚本在 `/tmp` 就是这个码**）；`216/GROUP` 查 `User=`/`Group=`（用户单元写 `User=` 也会）；`217/USER` 查用户是否存在；`226/NAMESPACE` 查沙箱与 `ReadWritePaths`；`Result=resources` 查 `EnvironmentFile=`；业务退出码查应用日志。
> - **配置层**：`systemd-analyze verify`（**看输出，退出码可能是 0**）、`systemctl cat`、`show -p FragmentPath -p DropInPaths`，确认改的文件是不是生效文件。
> - **第一反应不要是什么**：不要反复 `restart`、不要先改 `StartLimitBurst`——那会覆盖失败计数并让根因更难定位。

> [!question]- 改完 unit 为什么必须 `daemon-reload`？reload 之后为什么还要 restart？
> - **reload 做什么**：让 PID 1 重新读取全部 unit 文件与 drop-in、重跑 generator、重建依赖树（实测：不 reload 时 manager 里还是旧值，`status` 会有 `changed on disk` 警告）。
> - **reload 不做什么**：不重启正在运行的进程。实测 `daemon-reload` 后 `show -p Environment` 已是 `PHASE=2`，但 `/proc/<MainPID>/environ` 仍是 `PHASE=1`、`MainPID` 也没变（`10813`）；只有 `restart` 后（`MainPID=10881`）新进程才拿到新环境。
> - **正确顺序**：改文件/drop-in → `systemd-analyze verify` → `daemon-reload` → `systemctl show` 核对生效值 → `restart` → 业务验证。
> - **第一反应不要是什么**：不要把 `daemon-reload` 当成「重启服务」的替代品；也不要忘了先确认自己改的是系统级还是用户级的 drop-in 目录。

> [!question]- `Type=` 选错会造成什么「假启动失败」？怎么定位？
> - **`simple` + 会 fork 的进程**：父进程退出后 systemd 认为服务结束（实测 `SubState=dead`、`MainPID=0`，后台子进程被控制组清掉）；改用 `Type=forking`（实测 `MainPID=12510`、`active (running)`）或让程序前台运行。
> - **`forking` + 不 fork 的程序**：systemd 等父进程退出，迟迟不返回 → 启动超时。
> - **`notify` + 通知来源不对**：默认 `NotifyAccess=main`；实测**自己往 socket 写 `READY=1`**（包括主进程 fork 出的直接子进程）会被拒（`Got notification message from PID …`），默认等满 **90.237 秒**；**多包一层再调 `systemd-notify` 也会被拒**（实测 6 秒超时）；改 `NotifyAccess=all` 后 0.04 秒成功。
> - **`dbus` + 名字拿不到**：本机 D-Bus 默认 `deny own="*"`，不放行时报 `AccessDenied: … due to security policies in the configuration file`（实测 0.131 秒即失败）；给策略放行后 0.064 秒启动成功。
> - **定位**：`systemctl show -p Type -p NotifyAccess -p TimeoutStartUSec -p SubState`，再看 `journalctl -u` 的前几行。
> - **第一反应不要是什么**：不要在日志里看到「ready」就断定 systemd 有问题——先对齐 `Type=` 与通知来源；也不要拿一次手工测试成功当作生产写法正确。

> [!question]- `limits.conf`、`ulimit`、systemd `LimitNOFILE` 三者的关系与生效范围？
> - **`limits.conf`**：PAM 的 `pam_limits` 在**登录会话**里设置 rlimit，对 systemd 服务无效。
> - **`ulimit`**：shell 内置，只影响当前 shell 及其子进程。
> - **`LimitNOFILE=`**：unit 里的设置，由 systemd 在创建服务进程时应用（实测 `LimitNOFILE=64` → 服务内 `ulimit -n` 为 64）；默认来自 manager 的 `DefaultLimitNOFILE`——**本机实测系统级硬 `524288` / 软 `1024`，用户级 `1048576`**，两边不一样。
> - **验证**：`systemctl show -p LimitNOFILE -p LimitNOFILESoft <unit>` + `/proc/<MainPID>/limits`（**只看 `LimitNOFILE` 会把硬值当成可用值**）。
> - **第一反应不要是什么**：不要在 `limits.conf` 里反复加行——对 systemd 服务它永远不生效。

> [!question]- `ProtectSystem`/`ProtectHome`/`PrivateTmp`/`PrivateDevices`/`ReadWritePaths` 会改变什么？报错长什么样？
> - `ProtectSystem=`：`full` 管 `/usr`、`/boot`、`/efi`、`/etc`；`strict` 让 `/` 整体变 `ro`（实测 `ro,relatime`）。**它不管 `/home`。**
> - `ProtectHome=`：`yes` 把 `/home`、`/root` 换成不可访问的空 `tmpfs`（实测 `tmpfs ro,nosuid,nodev,noexec,size=808352k`，`ls /home` → `Permission denied`）；`read-only` 才是只读原目录。
> - `PrivateTmp=`：给服务一个私有 `/tmp`（实测服务内 inode `1311092` vs 宿主 `1179649`），宿主看不到、停止即消失；**脚本放 `/tmp` 再开它 = `203/EXEC`**。
> - `PrivateDevices=`：`/dev` 从 **207** 个节点收到 **18** 个并换成 `tmpfs ro,nosuid,noexec,size=4096k`，`/dev/sda*`、`/dev/mem`、`/dev/loop-control` 全部消失。
> - `ReadWritePaths=`：在只读世界里开可写口，**路径必须存在**（否则 `226/NAMESPACE`），且**属主要与 `User=` 对上**（实测 `uid=1000` 写 root 拥有的目录仍 FAIL）。
> - 其它常见退出码：`200/CHDIR`（工作目录）、`203/EXEC`（可执行文件）、`216/GROUP`（切组失败/用户单元写 `User=`）、`217/USER`（用户不存在）。
> - **第一反应不要是什么**：不要为了排障直接删掉沙箱；也不要以为 `strict` 会把 `/home` 一起锁上。

> [!question]- 服务每几秒重启一次，过一会儿就彻底不重启了，怎么解释、怎么恢复？
> - **解释**：`Restart=` 触发重启；在 `StartLimitIntervalSec` 窗口内超过 `StartLimitBurst` 次后，systemd 报 `Start request repeated too quickly.` 并停止重试（实测 `NRestarts=3`、`ExecMainStatus=1`、`Result=exit-code`、`Active: failed`）。
> - **恢复**：`systemctl reset-failed <unit>` 清掉失败状态与计数（实测 `Result=success`、`NRestarts=0`），再 `start`；但真正要做的是修根因。
> - **两个边界**：`systemctl stop` **不会**触发 `Restart=`（实测 `NRestarts=0`、`SubState=dead`）；`Restart=on-failure` 遇到退出码 0 也不重启。
> - **注意**：`StartLimitIntervalSec`/`StartLimitBurst` 在 `[Unit]`；写进 `[Service]` 会被静默忽略（**而且 verify 退出码还是 0**）。
> - **第一反应不要是什么**：不要直接把 `StartLimitBurst` 调到很大——那只是让故障持续输出日志与重启风暴。

> [!question]- 脚本在命令行能跑、放进 `cron` 就跑不通，为什么？
> - **环境不同（实测）**：cron 的环境是 `HOME=/root`、`LOGNAME=root`、`PATH=/usr/local/sbin:…`、`LANG=en_US.UTF-8`、`SHELL=/bin/sh`、`PWD=/root`，**没有 `~/.bashrc`/`~/.profile`、没有别名与函数**。
> - **`PATH` 与工作目录**：用绝对路径或显式 `PATH=`；`PWD` 是 `$HOME`，不是脚本目录。
> - **`%` 未转义**：crontab 里 `%` 表示换行，必须写成 `\%`（实测可用：`date +\%s` → `job-1789805341`）。
> - **shell 差异**：`SHELL=/bin/sh`，bash 专有语法可能失败；脚本首行写 `#!/bin/bash` 并确认可执行位。
> - **第一反应不要是什么**：不要只看 crontab 有没有写对——先让任务把 `env`、`pwd`、退出码写进一个文件，用证据对比。

> [!question]- `systemd timer` 比 `cron` 多了哪些能力？什么场景值得切换？
> - **时间语义**：`OnCalendar` 支持 `Mon..Fri`、`*:0/15`、`minutely` 等，`systemd-analyze calendar` 可离线验证（实测 `*:0/15` → `*-*-* *:00/15:00`）；还有相对式 `OnActiveSec`/`OnUnitActiveSec`。
> - **补跑与精度**：`Persistent=true` 只对 `OnCalendar=` 生效、只补一次（实测回拨 `stamp-*.timer` 3 天后立刻补跑）；`AccuracySec=` 控制抖动（实测 `AccuracySec=1s` 的 5 秒周期出现 `08:06:49.58 → 08:06:54.82 → 08:06:56.97` 这样的不规则间隔）。
> - **环境可复现**：`Environment=`/`EnvironmentFile=` 显式声明，不依赖登录环境。
> - **可观测与约束**：日志与退出码进 journald；可以加 `MemoryMax=`、`ProtectSystem=`、`After=` 依赖（**这些在系统级才有完整语义**）。
> - **切换场景**：生产自研任务、需要资源限制/沙箱/依赖顺序/错过补跑。cron 仍适合简单任务与遗留规范（本机 `anacron`/`at` 都没装，所以「关机期间错过」在 cron 侧本来就没有补跑能力），两者都要幂等 + `flock` + 记录结果 + 监控。

> [!question]- `/tmp` 里的文件是谁在清、什么时候清？为什么 `--clean` 有时不删「很久没改」的文件？
> - **谁在清**：`systemd-tmpfiles-clean.timer`（`OnBootSec=15min` + `OnUnitActiveSec=1d`，本机实测 next 为 23 小时后），按 `D /tmp 1777 root root 30d` 删超龄条目；此外 `PrivateTmp`、应用自清理也会让文件消失。注意**本机 `/tmp` 并不是独立 tmpfs**（它在根文件系统上），所以「重启清空 `/tmp`」在这台机器上不成立。
> - **age 判据**：默认同时看 mtime/atime/ctime，**任一较新就不删**（实测 `touch -d "40 days ago"` 的文件因 ctime 是「现在」而保留，`stat` 显示 `mtime=2026-08-10` 而 `ctime=2026-09-19`；改成 `m:30d` 才被删）。
> - **数据该放哪**：跨重启用 `StateDirectory=`（system 单元 `/var/lib`、用户单元 `~/.local/state`），跨进程不持久用 `RuntimeDirectory=`（system 单元 `/run`、用户单元 `$XDG_RUNTIME_DIR`），纯易失才放 `/tmp`。
> - **第一反应不要是什么**：不要为了「保险」把 `/tmp` 规则删掉——那是把整机治理关掉；也不要指望 `--dry-run`（本机 `systemd-tmpfiles` 没这个选项）。

> [!question]- 服务没开机自启，怎么排查？想彻底停用一个服务怎么做？
> - **三步检查**：`cat | grep -A3 '\[Install\]'`（有没有 `[Install]`，没有就是 `static`）、`list-dependencies <target>`（在不在启动路径）、`is-enabled`/`list-unit-files`（安装态）；再看有没有 `Condition...=` 跳过。
> - **彻底停用**：`systemctl disable --now <svc>` 取消自启并停止（实测会删 `/etc/systemd/system/multi-user.target.wants/<svc>` 软链）；需要「以后也起不来」再 `mask`，并处理触发它的 `.socket`/`.path`/`.timer`。
> - **三个边界**：`disable` 只删软链，别的 unit 仍可 `Wants=` 拉起；`mask` 在 `/etc/systemd/system` 下自己的单元上会失败（`File … already exists`）；被 `.socket` 触发的服务 `mask` 后会提示 `its triggering units are still active`。
> - **第一反应不要是什么**：不要直接删 `/usr/lib` 下的 unit 文件——软件包升级会带回来。

> [!question]- 为什么排障前必须先确认时间基线和「哪棵 manager」？
> - 时钟不同步时跨机日志拼不到一起、证书校验可能失败、定时任务在错误时间触发；**时间不对，整条证据链都失效**。
> - 检查：`timedatectl`（本机 `Time zone: Etc/UTC (UTC, +0000)`、`System clock synchronized: no`、`NTP service: active`）与 `timedatectl timesync-status`（server、poll、stratum）。
> - **本机没有 chrony**（`chronyc`/`chronyd` 都不存在，NTP 客户端是 `systemd-timesyncd`），`hwclock` 也没装（`util-linux-extra` 未安装）——别照抄 `chronyc tracking`。
> - **「哪棵 manager」同理**：系统级与用户级的 unit 集合、cgroup 路径、默认句柄上限、可用 target 都不同；查错一侧的典型症状是「命令成功但什么都没查到」。
> - **第一反应不要是什么**：不要在时钟不同步的情况下比较两台机器的时间戳并据此下结论；也不要在用户级找不到系统单元时怀疑 systemd。
