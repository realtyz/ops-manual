# 观测与基线

## 1. 一个问题，一把工具

| 你想知道 | 用什么 | 关键字段或文件 |
| --- | --- | --- |
| 这个单元现在什么状态、上次怎么失败的 | `systemctl status <unit> --no-pager -l` | `Loaded`、`Active`、`Process`、`Main PID`、`Tasks`、`CGroup`、`TriggeredBy` |
| 生效配置由哪些文件拼成 | `systemctl cat <unit>` | 每个键上方的 `# <路径>` 来源行 |
| 实际生效的那一份文件是哪个 | `systemctl show -p FragmentPath -p DropInPaths` | 两个路径字段 |
| manager 此刻的属性值 | `systemctl show <unit> -p <属性>` | 按属性名取，不要直接 `show` 全量 |
| 配置有没有被静默丢弃 | `systemd-analyze verify <unit 文件>` | **输出文本**，不是退出码 |
| 进程实际拿到的环境 | `tr "\0" "\n" < /proc/<MainPID>/environ` | 变量=值 |
| 进程实际可用的句柄上限 | `/proc/<MainPID>/limits` | `Max open files` 的软/硬两列 |
| 进程实际所属的 cgroup | `/proc/<pid>/cgroup` | `0::<路径>` |
| 内核侧生效的资源上限 | `/sys/fs/cgroup<ControlGroup>/{memory.max,memory.high,cpu.max,cpu.stat,pids.max,pids.current,memory.events}` | 见第 2 节 |
| 谁依赖谁、谁被拉起 | `systemctl list-dependencies [--reverse] <unit>` | 它输出一棵树，而行首符号只表示当前激活状态 |
| 有没有按需激活的监听 | `systemctl list-sockets` | `LISTEN`、`UNIT`、`ACTIVATES` |
| timer 什么时候跑 | `systemctl list-timers --all` | `NEXT`、`LEFT`、`LAST`、`PASSED`、`UNIT`、`ACTIVATES` |
| 有没有卡住的作业 | `systemctl list-jobs` | 在执行的 job（含停止中的） |
| 系统整体健康与失败单元 | `systemctl is-system-running`、`systemctl --failed` | 它给出 `running`/`degraded`/`maintenance` 三种整体状态，以及失败单元的列表 |
| 装了哪些、安装态如何 | `systemctl list-unit-files` | `STATE`（含 `static`/`enabled`/`disabled`/`masked`/`indirect`）与 `PRESET` |
| 开机时间花在哪 | `systemd-analyze time`、`blame`、`critical-chain` | `@` 是变 active 的时刻，`+` 是该单元自身耗时 |
| 时间对不对 | `timedatectl`、`timedatectl timesync-status` | `System clock synchronized`、`NTP service`、`Packet count` |
| 服务的日志与字段 | `journalctl -u <unit> -b`、`-o verbose`、`-o json` | `_SYSTEMD_UNIT`、`_TRANSPORT`、`SYSLOG_IDENTIFIER`、`__MONOTONIC_TIMESTAMP` |
| 日志占了多少、还能查几次启动 | `journalctl --disk-usage`、`--list-boots` | 它给出 journal 当前占用的容量与仍然可查的启动列表 |
| 真正生效的日志配置 | `systemd-analyze cat-config systemd/journald.conf` | 各来源路径与键 |
| `/tmp` 由谁按什么规则清 | `systemd-tmpfiles --cat-config`、`--tldr` | 它给出生效的规则行与这些规则所在的来源路径 |
| 文件到底多老 | `stat -c "%n mtime=%y ctime=%z" <文件>` | `%y`=mtime、`%z`=ctime |
| `/tmp` 是不是内存盘 | `findmnt -T /tmp -o TARGET,SOURCE,FSTYPE` | `FSTYPE` |
| 定时任务的调度与环境 | `crontab -l`、`ls -l /etc/cron.d`、`journalctl -u cron`、`systemd-analyze calendar "<表达式>"` | 触发记录、环境变量、归一化后的触发时间 |
| 单元属于系统级还是用户级 | `systemctl show -p FragmentPath`、`systemctl --user is-system-running` | 它给出单元文件的路径，而用户侧报 `Failed to connect to bus` 就表示当前没有用户会话 |

表里的「用什么」分两类：**命令**（`systemctl`、`journalctl`、`systemd-analyze`、`systemd-tmpfiles`；文档在 `man 1`/`man 8`）与**内核接口文件**（`/proc/...`、`/sys/fs/cgroup/...`；直接读，不需要工具）。判据分不清时看文档节号：`man 5` 是文件格式与配置项，`man 1` 是命令。

**只读与破坏性的边界**：上表全部是只读动作，**生产机上也可以做**——`status`/`cat`/`show`/`list-*`/`is-*`/`journalctl`（读）/`systemd-analyze`（`time`/`blame`/`critical-chain`/`verify`/`exit-status`/`unit-paths`/`cat-config`/`calendar`/`security`）/`timedatectl`/`systemd-tmpfiles --cat-config`/`--tldr`。破坏性的动作包括 `start`/`stop`/`restart`/`reload`/`daemon-reload`/`edit`/`mask`/`set-default`/`isolate`、`journalctl --vacuum-*`、`systemctl clean`、`crontab -r` 与 `crontab -`——**只在可快照的实验机上做**；`--vacuum-*` 还会删掉历史启动的证据，见 2.4。

## 2. 怎么读这些数字

下面每一条都给五件事中的至少四件：**这个数字是什么**、**单位**、**多少算异常**（或说明只能与自身基线比）、**和谁一起看**、**看到它转向哪一步**。文中的命令与输出样例只用来展示**格式**：所有数值仅示意，不代表你的机器；凡标注了环境的值，只在该环境（本机为 Ubuntu 24.04.5 / 内核 6.8.0-139 / systemd 255）成立，换机器要现场重取。

### 2.1 `status` 的四段与退出码

```bash
systemctl status myapp --no-pager -l    # 验证：一次读全 Loaded/Active/Process/Main PID/CGroup
```

```text
● myapp.service - 示例服务
     Loaded: loaded (/etc/systemd/system/myapp.service; enabled; preset: enabled)
     Active: failed (Result: exit-code) since Sun 2026-09-20 14:35:22 UTC; 1s ago
    Process: 135175 ExecStart=/usr/local/bin/myapp (code=exited, status=203/EXEC)
   Main PID: 135175 (code=exited, status=203/EXEC)
        CPU: 455us
```

- **`Loaded:`**：说明文件从哪读、安装态如何、发行版预设给了什么。`not-found` 只说明「按名字没找到」，`masked` 说明被挡住；括号里的 `enabled`/`disabled`/`static` 与 `preset:` 是安装态，与运行态无关。
- **`Active:`**：当前状态加 `Result`。`active (running)`/`active (exited)`/`inactive (dead)`/`failed`。**判据**：`failed` 一定要看 `Result`；`Result` 是 `exit-code`/`timeout`/`signal`/`resources`/`oom-kill` 之一时，对应的排查方向完全不同。`since <时间>` 是进入该状态的墙钟时刻，**只能与自身基线比**，并且要与日志时间戳对齐——时钟未同步时不要下结论。
- **`Process:` 与 `Main PID:` 里的 `status=`**：这是 systemd 的退出码体系。**200 段是 systemd 自报**（它没能按你写的把服务起起来），0–255 是进程自己的退出码。用 `systemd-analyze exit-status <码>` 可以直接把数字翻译成名字。
- **`Tasks:` 与 `CGroup:`**：`Tasks` 是 cgroup 里还剩下的任务数。**判据**：单元已停止而 `Tasks` 不为 0，说明还有子进程没被收走——看 `KillMode=`。
- **`Main PID: 0`**：主进程已不存在。配合 `SubState=dead` 与 `Result=success` 时，先怀疑 `Type=` 与进程模型不匹配（见判例篇）。
- **`TriggeredBy:`**：被哪个 socket/path/timer 触发。它解释了「服务是 inactive 但端口在听」。

`status` 里的退出码对照（`systemd-analyze exit-status` 给出 `NAME`/`STATUS`/`CLASS`，`CLASS=systemd` 即 systemd 自报）：

| 退出码 | 它的含义 | 看到它转向哪一步 |
| --- | --- | --- |
| `200/CHDIR` | systemd 无法进入工作目录 | 先确认 `WorkingDirectory=` 指向的目录是否存在，再确认 `User=` 能否进入它 |
| `203/EXEC` | systemd 无法执行主命令 | 先确认路径与执行位，再确认 shebang 解释器；若开了 `PrivateTmp=`，还要确认脚本是否放在 `/tmp` |
| `216/GROUP` | systemd 无法切换组或用户 | 先确认 `Group=` 是否存在，再确认这是不是用户单元里写了 `User=` |
| `217/USER` | systemd 无法确定用户 | 先确认 `User=` 指定的用户是否存在 |
| `226/NAMESPACE` | 沙箱或挂载命名空间搭建失败 | 先确认 `ReadWritePaths=` 的路径是否存在，再确认 `ProtectSystem=` 是否与这次写入冲突 |
| `1/FAILURE` | 进程自己返回了 1 | 先读应用日志，再确认会不会是 `ExecStartPre=` 失败 |
| `9`（`code=killed`） | 进程被 SIGKILL 结束 | 先看内核日志的 `oom_memcg=` 与 `memory.events` 是否为容器内 OOM，再排除人工 `kill -9` |

### 2.2 生效值、进程值与默认值

```bash
systemctl show myapp -p FragmentPath -p DropInPaths -p Type -p Restart -p KillMode -p LimitNOFILE -p LimitNOFILESoft -p TasksMax -p TimeoutStopUSec   # 验证：manager 里此刻的生效值
```

```text
FragmentPath=/etc/systemd/system/myapp.service
DropInPaths=/etc/systemd/system/myapp.service.d/10-site.conf
Type=simple
Restart=no
KillMode=control-group
LimitNOFILE=524288
LimitNOFILESoft=1024
TasksMax=9374
TimeoutStopUSec=1min 30s
```

上例中的 `Restart`/`KillMode`/`LimitNOFILE`/`LimitNOFILESoft`/`TasksMax`/`TimeoutStopUSec` 是**该环境的缺省值**（Ubuntu 24.04.5 / 内核 6.8.0-139 / systemd 255，临时单元实测）；`FragmentPath`/`DropInPaths` 是与你的单元相关的路径，数值仅示意。换 systemd 版本、发行版或 manager 类型都应当重取。

- **`FragmentPath`/`DropInPaths`**：生效的原文件与叠上去的片段。「我改的文件名不在里面」就是最常见的「改了没生效」。
- **`Type=`**：`show` 里**没有这一项**时不要以为它为空，因为 `Type=` 是 service 单元的属性，只在有 `ExecStart=` 语义的单元上读它才有意义；缺省规则是「有 `ExecStart=` 而无 `Type=` 即 `simple`」。
- **`Restart=`**：缺省是 **`no`**（文档明确），不是 `on-failure`。发行版单元里常见 `Restart=on-failure` 是**单元文件显式写的**，不要当默认值。
- **`KillMode=`**：文档缺省是 **`control-group`**（停止时收掉整个控制组）。发行版里有不少单元显式写 `KillMode=process`（例如 Ubuntu 的 `cron.service`、`ssh.service`），看到 `process` 要先确认它来自 unit 文件还是默认值——`grep '^KillMode' /usr/lib/systemd/system/*.service` 一比就知道。
- **`LimitNOFILE=` 与 `LimitNOFILESoft=`**：硬值与软值是两个属性。**服务实际可用的是软值**（默认 1024），除非程序自己抬到硬值。验收要读 `/proc/<MainPID>/limits` 的 `Max open files` 两列。
- **`TasksMax=`**：cgroup 的 `pids.max`，整个控制组共享一份。它与 `LimitNPROC=`（每进程的 rlimit）不是一回事。
- **`TimeoutStopUSec=`**：SIGTERM 到 SIGKILL 之间的等待窗口。**判据**：一次 `stop` 的实际耗时接近这个值，就说明应用没在窗口内响应 SIGTERM。

**默认值一律现场取**：`systemctl show -p DefaultTimeoutStartUSec -p DefaultTimeoutStopUSec -p DefaultLimitNOFILE -p DefaultLimitNOFILESoft -p DefaultTasksMax -p DefaultOOMPolicy` 给出的是 manager 的缺省，它不是文档上的常量，也会随 systemd 版本与发行版补丁变化。`systemd --version` 与 `UnitFileState` 的 `preset:` 一起记进基线卡。

### 2.3 cgroup 文件：内核侧的事实

```bash
C=$(systemctl show -p ControlGroup --value myapp)   # 验证：先取到该单元的 cgroup 路径，再读内核侧文件
cat "/sys/fs/cgroup$C/memory.max" "/sys/fs/cgroup$C/memory.current" "/sys/fs/cgroup$C/memory.events" "/sys/fs/cgroup$C/cpu.max" "/sys/fs/cgroup$C/pids.max"
```

- **`memory.max`**：硬上限，单位字节（`show -p MemoryMax` 会做同样的换算，例如 `32M` 显示成 `33554432`）。**判据**：`max` 表示不限。`show` 与文件不一致时，说明配置没进内核，或还有上层 slice 在约束。
- **`memory.high`**：软上限，超限只节流不杀；`max` 表示不限。
- **`memory.events`**：事件计数，形如 `low 0 / high 0 / max 38 / oom 1 / oom_kill 1 / oom_group_kill 0`。**`oom_kill` 非 0 才代表确实有进程被杀**；`max` 非 0 只说明撞过上限（可能只被节流）。**这是「服务还是 active 但少了几个 worker」唯一可靠的发现手段**——把 `OOMPolicy` 设成 `continue` 时 `systemctl status` 看不出任何异常。
- **`cpu.max`**：`quota period` 两段（微秒）。`10000 100000` 即每 100 毫秒最多用 10 毫秒单核算力；`max 100000` 表示不限。**判据**：看 `cpu.stat` 的 `nr_throttled`/`throttled_usec` 才能确认它真的在限流。
- **`pids.max`/`pids.current`**：任务数上限与当前值。fork 类问题的落点在这里，不在 `LimitNPROC=`。
- **这些计数都是累积值**：因此「这次事件有没有发生」要用两次读数的**差值**判断。
- **这些计数字段有时效**：cgroup 目录随单元结束被回收，`memory.events` 这类证据只在单元存活期间存在。要复盘就先采下来。

### 2.4 journald：日志为什么查不到

`journalctl` 查不到日志有五种互不相同的原因，按这个顺序排除：

1. **落点**：`systemctl show -p StandardOutput -p StandardError`。缺省是 `journal`；改成 `file:` 之后 `journalctl -u` 就看不到了。**`show -p Environment` 只列 unit 显式声明的值**，`EnvironmentFile=` 里的值不出现在这里——要进程环境就读 `/proc/<MainPID>/environ`。
2. **归属**：`journalctl -u <unit>` 只匹配该单元的消息。手工在 SSH 会话里发的消息属于 `session-N.scope`，用 `-u` 永远查不到，要按 `-t <标识>` 或 `SYSLOG_IDENTIFIER` 查。`-o verbose` 里的 `_TRANSPORT` 说明来源（`stdout`/`syslog`/`kernel`/`audit`）。
3. **保留**：`ls -ld /var/log/journal`。目录存在才是持久化；不存在时日志只在内存里，重启即丢，`-b -1` 也就无从查起。`journalctl --list-boots` 只剩一条，就说明历史启动已经被裁掉或从未持久化。
4. **限流与容量**：`show -p LogRateLimitIntervalUSec -p LogRateLimitBurst` 与 `journalctl --disk-usage`。**这里有一个反直觉的实测结论**：单元级限流确实生效，而且**有效额度会按 journal 可用磁盘空间被放大**（`journald.conf` 的表按可用空间给出倍率），所以「我设了 5 条」不等于「只放 5 条」；更麻烦的是**丢弃时不一定留下任何告警**——`journalctl -b | grep -i suppress` 可能一无所获，而实际少了几百条。**判据要落在「实际落库条数」上**（写 N 条再数落库多少），不能靠有没有告警行。
5. **过滤条件**：`-b`（只看本次启动）、`--since`（按本地时区解释）、`-p <级别>`。时区不一致会把窗口选错——跨机对账统一 `TZ=UTC`。

两个字段的用途要分清：**`_SYSTEMD_UNIT` 决定归属**，**`__MONOTONIC_TIMESTAMP` 决定先后**。墙钟会被 NTP 调整，跨日志源排序要用单调时钟。

**容量治理的边界**：`journalctl --disk-usage` 是一个会变的数（journald 一直在写入与轮转），任何「占用 = X」都要带采样时刻。裁剪只能用 `--vacuum-size=`/`--vacuum-time=`/`--vacuum-files=`，**不要直接 `rm` journal 文件**（可能破坏索引）。另外两条实测边界：`--vacuum-*` **只删已归档文件**，只有活动文件时目标再小也是空操作（输出 `freed 0B`，命令本身没坏）；而 `--vacuum-time=` 删掉的是**历史启动的证据**——跑完之后 `--list-boots` 可能只剩当前一次、`-b -1` 直接报错。**只在可快照的实验机上执行**：它破坏数据且不可回滚，先确认历史启动的证据不再需要，再动手。

**其余破坏性动作的边界**（都不属于只读观测）：`systemctl clean` 会**删掉**单元的状态、缓存与日志目录（`--what=` 可细分），执行前先确认那些目录里没有需要保留的数据；`crontab -r` 与 `crontab -` 会删除或覆盖当前用户的**整份** crontab，动手前先 `crontab -l > ~/crontab.bak`；`systemctl set-default`/`isolate` 影响开机路径，后者会立刻停掉不在目标里的服务（在 SSH 里做可能切断自己），只在有控制台或带外管理时做。

### 2.5 开机与基线

```bash
systemd-analyze time          # 验证：分开看 kernel 与 userspace
systemd-analyze blame | head  # 谁初始化花得久（只是候选）
systemd-analyze critical-chain  # 谁挡住了开机完成时刻
ls /sys/firmware/efi >/dev/null 2>&1 && echo UEFI || echo "Legacy BIOS"
```

- **`time` 的分段**：`kernel` 与 `userspace` 是两个独立量，因此**跨机对比必须注明引导方式与有没有 `firmware`/`loader` 段**——BIOS 引导的机器量不到固件耗时，没有那一段不代表「缺了那个阶段」。
- **`blame` 是候选清单，不是元凶清单**：它按「谁初始化花得久」排序，因此**并行启动的服务会排在前面却不在关键路径上**。
- **`critical-chain` 才是关键路径**：`critical-chain` 输出里标 `+耗时` 的那一环才是真正阻塞开机完成时刻的对象。两者必须同看。
- **读 `systemctl --failed` 是代价最低的一次核对**：健康机器上它的输出为空。若 `is-system-running` 报 `degraded`，就立刻看它；`maintenance` 表示系统进了救援或紧急模式，与 `degraded` 不是一回事。
- **时间基线是排障前提**：`timedatectl` 的两行要分开看——`NTP service: active` 只说明客户端在跑，`System clock synchronized` 才是「时间准了」。更细的证据在 `timedatectl timesync-status` 的 `Packet count`（0 表示一次包都没换到）。**两个 NTP 客户端同时运行会互相打架**（Ubuntu 默认 `systemd-timesyncd`，RHEL 系默认 `chrony`），因此同一个机器上只留一个。

### 2.6 定时任务与临时文件的时间语义

- **`list-timers` 的列**：`NEXT` 给出**墙钟**的下次触发时刻，而相对式 timer 的这个时刻会随开机时刻漂移；`LAST` 与 `PASSED` 给出上次触发以及距今多久；`UNIT` 是 timer 本身，而 **`ACTIVATES` 才是真正干活的 `.service`，因此查日志要去那一个**。若 `LEFT` 与 `NEXT` 都为空，就说明它不会再触发（未激活或已耗尽）。
- **`show -p TimersMonotonic`** 给出的是**距上次触发的单调偏移**，而不是「下次几点」，因此要墙钟时刻就用 `list-timers`。日历式规则可以用 `TimersCalendar` 或 `systemd-analyze calendar` 归一化后核对。
- **`AccuracySec=`** 规定 timer 允许的唤醒抖动窗口，缺省是 `1min`，这样省电但会把触发时间推迟。因此精度敏感的任务必须显式调小它，并且要知道即使调小也仍然存在抖动。
- **`Persistent=`** 的补跑只在 `OnCalendar=` 时有效，且只补一次；它的时间戳落在 `/var/lib/systemd/timers/stamp-<timer>`（用户单元在 `$XDG_STATE_HOME/systemd/timers/`）。**卸载 timer 前先执行 `systemctl clean --what=state <timer>.timer`**，否则下次同名 timer 被启用时可能立刻补跑一次本应错过的任务，看起来像「任务莫名跑了两次」。
- **cron 的环境只有六项**：`HOME`、`LOGNAME`、`PATH`、`LANG`、`SHELL=/bin/sh` 与 `PWD`。它不读 profile，也没有别名与函数；`PWD` 是账号 home 而不是脚本所在目录；命令里的 `%` 必须写成 `\%`。**`journalctl -u cron` 显示的是反转义之后的命令，因此不能拿它当转义写对了的证据**，判据是任务实际写出的结果。
- **`systemd-tmpfiles-clean.timer` 是相对式排程**（缺省开机 15 分钟后第一次、之后每 24 小时），因此不同机器的触发时刻各不相同。
- **tmpfiles 的 `age` 判据是多个时间戳**：缺省下只要有一个戳比阈值新就不清（目录项默认忽略 ctime）。用 `stat -c "%n mtime=%y ctime=%z"` 看差异；要精确控制就在规则里写前缀（如 `m:30d` 只看 mtime）。**`systemd-tmpfiles` 在 systemd 255 上没有 `--dry-run`**，因此只读演练要靠 `--cat-config`/`--tldr` 加限定前缀。

## 3. 采样纪律与基线

一次合格的采集要满足五条：

1. **同口径**：每次采集都要写清读的是 manager 的值还是进程的值、是内核接口文件还是命令输出。同一个「内存上限」在 `show -p MemoryMax` 与 `memory.max` 里都要看，并且两处要一致。
2. **带时间戳**：`journalctl --disk-usage`、`memory.events`、`NRestarts` 都是会变的数；任何读数都要带采样时刻与来源主机。
3. **至少两次**：计数类指标（`memory.events`、`NRestarts`、`cpu.stat`、`__MONOTONIC_TIMESTAMP`）都要取差值，单次读数没有意义。
4. **留原始输出**：`systemctl cat <unit>` 与 `show -p ...` 的原始文本留档——变更前后各一份，这是回滚和复盘的基础。
5. **标注环境**：`systemctl --version`、`systemd-analyze unit-paths`、`systemctl get-default`、`timedatectl`、`ls -ld /var/log/journal`、`grep '^KillMode' /usr/lib/systemd/system/*.service` 这一组事实决定了很多默认值的解释，换机器就必须重采。

**基线卡应当回答的问题**（模板与交付物在治理篇）：这台机器上有哪些单元在运行、哪些会自启、哪些 timer/cron 在跑、`/tmp` 由谁按什么规则清、时间基线是否可信、以及单元级的关键上限与重启策略分别是什么。

## 常见故障与排查方向

### 场景一：新上线的 unit `start` 失败，`status` 只有一行退出码

**场景**：Ubuntu 24.04、systemd 255 的机器上，一个自研服务 `myapp.service` 首次 `start` 失败，`systemctl status myapp` 显示 `Process: ... (code=exited, status=203/EXEC)`。

**排查顺序**：先按退出码分流，不要先看应用日志。

1. 先读 `Loaded:` 一行，判断它是 `not-found` 还是 `loaded`：若是 `not-found`，则说明文件不在搜索路径、名字拼错，或者新建之后没有执行 `daemon-reload`（用 `systemctl list-unit-files | grep myapp` 求证）。
2. 再读 `systemctl show -p FragmentPath -p DropInPaths`，确认生效文件是不是你改的那一份。
3. 读退出码：若是 `203/EXEC`，就查 `ExecStart=` 的路径、执行位与 shebang 解释器，并且**如果开了 `PrivateTmp=yes` 而脚本放在 `/tmp`，则一定是这个码**（宿主机上文件明明在，服务的命名空间里却不存在）；若是 `200/CHDIR`，就查 `WorkingDirectory=`；若是 `216/GROUP` 或 `217/USER`，就查 `User=`/`Group=` 是否存在，以及是不是用户单元里写了 `User=`；若是 `226/NAMESPACE`，就查 `ReadWritePaths=` 的路径是否存在。
4. 若 `Result=resources` 且 `ExecMainStatus=0`，就转去查 `EnvironmentFile=`：该文件缺失且没写前导 `-` 时是硬失败，进程根本没进 `ExecStart`。
5. 若 `Result=timeout`，就转去查 `Type=` 与通知归属，不要先调大超时。

**一份合格的回答应当包含结论、依据、边界与动作这四件事**：结论要指出这次失败卡在装载、判定与约束三层中的哪一层；依据要指出是哪条命令的哪个字段给出了这个退出码；边界要说明这个结论在换发行版或改 `Type=` 之后是否仍然成立；动作要说明改哪一项、怎么复测、怎么回滚。

### 场景二：`active (running)` 但业务不可用

**场景**：`start` 返回 0、`status` 是 `active (running)`，端口却连不上；或端口在听但请求报错。

**排查顺序**：

1. 先读 `ss -lntp | grep <端口>`：若端口没有起，则问题落在应用启动本身，转去看应用日志；若端口已经在听，则问题在应用逻辑或下游。
2. 再读 `systemctl list-sockets | grep <端口>`：若端口由某个 `.socket` 单元持有而服务是 `inactive`，那就是按需激活，不是故障。
3. 再读 `systemctl show -p Type -p SubState -p MainPID -p ExecStartPost`：`Type=simple` 下的「启动完成」发生在 `fork` 之后，因此此时应用可能还没开始监听。
4. 再读 `systemctl list-dependencies` 与日志的 `-o short-precise` 时间线，判断依赖是不是只完成了「启动动作」。**一个具体的坑**：`network-online.target` 等什么由发行版网络配置决定，某些环境把它配成等待特定接口就绪且**不超时**，因此接口迟迟不就绪时，依赖它的服务会安静地卡在 `activating`，日志里没有任何错误。
5. 最后读 `journalctl -u myapp -b -o short-precise | head -20`，看 `Starting` 到 `Started` 之间隔了多久，再与超时值对比。

**一份合格的回答应当包含结论、依据、边界与动作这四件事**：结论要明确区分「没起来」与「没就绪」；依据要指出是端口、依赖、就绪判定这三条证据中的哪一条不成立；边界要说明换 `Type=` 或引入健康检查之后结论会不会变；动作要说明是否需要改 `Type=` 或引入健康检查。

### 场景三：改了配置没生效

**场景**：改了 drop-in、`daemon-reload` 也执行了，`show` 是新值，但服务行为没变。

**排查顺序**：按配置的生效层级逐段核对。

```bash
systemctl cat myapp                                  # 文件层：是不是这个文件、有没有被覆盖
systemd-analyze verify /etc/systemd/system/myapp.service.d/10-site.conf   # 读输出：有没有 ignoring
systemctl show myapp -p FragmentPath -p DropInPaths -p Environment         # manager 层
tr "\0" "\n" < /proc/$(systemctl show -p MainPID --value myapp)/environ     # 进程层
```

**判据**：三层里哪一层没有更新，就补哪一步的动作。若 manager 没有更新，说明 `daemon-reload` 没执行或改错了文件；若进程没有更新，说明只 `reload` 没有 `restart`（此时 `MainPID` 也不会变）。若 `verify` 的输出里出现 `Unknown key name ... ignoring.`，就说明那一项被丢弃了——**因此不能只看它的退出码**。

**一份合格的回答应当包含结论、依据、边界与动作这四件事**：结论要指出配置的生效层级断在哪一段，而不是笼统地说「配置没生效」；依据要指出是哪一层的哪条命令给出了证据；边界要说明这三层中哪一层会在重启后改变；动作要说明该补哪一步。

### 场景四：服务反复重启，之后彻底不重启

**场景**：服务启动后几秒就退出，重启若干次后 `start` 直接报错。

**排查顺序**：

1. 先读 `systemctl show -p Result -p NRestarts -p StartLimitBurst -p StartLimitIntervalUSec`，看 `NRestarts` 是否停在 burst 值。
2. 再读 `journalctl -u myapp -b | grep -E "Scheduled restart|Start request repeated|Failed with result"`，确认节流已经被触发。
3. 再读 `journalctl -u myapp -b | tail -50`，找**第一次**失败的原因（后面的记录都是重试）。
4. 再确认 `Restart=` 与 `RestartSec=`：缺省 `RestartSec=` 是 100 毫秒，因此崩溃循环会变成非常密集的重启。
5. 修掉根因之后再执行 `systemctl reset-failed myapp && systemctl start myapp`。

**一份合格的回答应当包含结论、依据、边界与动作这四件事**：结论要说明节流是被触发的**结果**而不是新故障；依据要指出第一次失败的原因出自哪条日志；边界要说明区分「止血」（临时放宽节流）与「修复」（改掉失败原因）之后结论是否成立；动作要说明临时放宽的期限与回收方式。

### 场景五：日志查不到、被写满，或「占用对不上」

**场景**：`journalctl -u myapp` 什么都查不到；或磁盘告警显示 journal 占用过大，准备清理。

**排查顺序**：

1. 先读 `show -p StandardOutput -p StandardError`，确认日志的落点是不是 journal。
2. 再读 `journalctl --list-boots` 与 `ls -ld /var/log/journal`，确认有没有持久化、历史启动还在不在。
3. 再读 `show -p LogRateLimitIntervalUSec -p LogRateLimitBurst`，并「写 N 条再数落库多少」，确认限流有没有丢消息（**不要依赖 `grep suppress`**）。
4. 再读 `journalctl --disk-usage` 与 `systemd-analyze cat-config systemd/journald.conf`，确认容量上限来自哪个文件、当前占用多少。
5. 要裁剪就用 `--vacuum-size=`/`--vacuum-time=`，但**执行前先确认历史启动的证据还需不需要**（`--list-boots` 会告诉你现在有几次）。

**一份合格的回答应当包含结论、依据、边界与动作这四件事**：结论要分清五类原因中的哪一类；依据要指出是哪条命令的哪个字段支持这个归类；边界要说明容量治理的三层结构（应用按级别输出、journald 容量上限、高频日志分流），并指出不能把单元级限流当保险；动作要说明裁剪命令与执行前提。

### 场景六：定时任务到点没跑

**场景**：`/etc/cron.d/backup` 里的任务昨晚没有执行，产物不存在。

**排查顺序**：分三层查，不要一上来就改表达式。

1. **调度层**：先读 `journalctl -u cron --since "昨天 23:00"` 里有没有 `CRON[pid]: (user) CMD (...)`，再读 `systemctl list-timers` 与 `systemd-analyze calendar` 核对 timer 的 `NEXT` 与归一化结果。
2. **环境层**：让任务把 `env`、`pwd`、`echo $?` 写进文件，再与交互 shell 对比（cron 只有六项环境变量，`SHELL=/bin/sh`，`PWD` 是账号 home）。
3. **业务层**：读退出码与产物；cron 只记录 `CMD` 一行，因此任务必须自己留日志。

**一份合格的回答应当包含结论、依据、边界与动作这四件事**：结论要明确是「没触发」「触发了但环境不同」还是「跑了但结果错」；依据要指出是哪一层的哪条记录支持这个判断；边界要说明如果涉及关机期间错过，cron 侧需要 `anacron`（很多发行版默认不装）而 timer 侧要用 `Persistent=true`；动作要说明该改哪一层。

### 场景七：`/tmp` 里的文件莫名消失

**场景**：服务放在 `/tmp` 的锁文件或数据文件会消失，重启后现象变化。

**排查顺序**：

1. 先读 `findmnt -T /tmp -o TARGET,SOURCE,FSTYPE`：只有它是 tmpfs 才存在「重启清空」，而本机常见是落在根文件系统上，因此重启并不清空。
2. 再读 `systemd-tmpfiles --cat-config | grep -E "^[a-zA-Z].*/tmp"` 与 `systemctl list-timers systemd-tmpfiles-clean.timer`，确认谁在按什么规则清、什么时候跑。
3. 再读 `stat -c "%n mtime=%y ctime=%z" <文件>`，与规则里的 `age-by` 前缀对比。
4. 最后读 `systemctl show <unit> -p PrivateTmp`，确认服务是否有私有 `/tmp`（宿主放进去的文件它看不见，反之亦然）。

**一份合格的回答应当包含结论、依据、边界与动作这四件事**：结论要指出是哪一种机制（清理任务、私有 `/tmp`、应用自清理、tmpfs 重启）；依据要指出是哪条命令的哪个字段支持它；边界要说明数据应该放在哪里，即跨重启保留的数据用 `StateDirectory=`、只在运行期共享的数据用 `RuntimeDirectory=`；动作要说明迁移步骤，并且**不要删掉 `/tmp` 的清理规则来「解决」问题**。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| `systemctl show <unit>` 不带 `-p` | 输出有几百行，因此看不出重点；要按属性名取 |
| 只看 `verify` 的退出码 | 被忽略的键不会改变退出码，因此要读输出 |
| 只看 `show -p LimitNOFILE` | 那是硬值，而实际可用是 `LimitNOFILESoft=`，因此验收要读 `/proc/<pid>/limits` |
| 把 `list-units` 当「装了哪些服务」 | 它列的是运行态，因此安装态要看 `list-unit-files` |
| 把 `blame` 第一名当阻塞源 | 它按初始化耗时排出的只是候选，因此关键路径要看 `critical-chain` |
| 用 `journalctl -u` 查内核消息 | 内核消息属于另一个来源，因此要用 `-k` |
| 用 `grep suppress` 证明日志没丢 | 丢弃时不一定留下告警，因此判据是实际落库条数 |
| 直接 `rm` journal 文件 | 它可能破坏索引，因此要用 `--vacuum-*` 或设容量上限 |
| 把 `--vacuum-*` 当只读操作 | 它是破坏性动作且不可回滚，因为会删掉历史启动的证据 |
| 把 `--disk-usage` 的结果当常量 | journald 一直在写入与轮转，因此这个数必须带采样时刻 |
| 把 `RuntimeMaxUse` 当内存的百分比 | 它是 `/run` 所在 tmpfs 的百分比 |
| 在 `/tmp` 放脚本又开 `PrivateTmp=` | 服务会直接得到 `203/EXEC` |
| 用 `show -p Environment` 当进程环境 | 它只列 unit 显式声明的值，因此 `EnvironmentFile=` 的值不在这里 |
| 把「NTP 服务 active」当「时间已同步」 | 这两行要分开看，必要时还要看 `Packet count` |
| 同时运行两个 NTP 客户端 | 它们会互相打架，因此只留一个 |
| 拿一次采样当基线 | 计数类指标必须取差值，而容量类指标必须带时刻 |
| 跨机对比开机耗时不说引导方式 | BIOS 引导量不到固件耗时，因此数字不可比 |

## 要点自测

**问：`systemctl status` 里的 `status=203/EXEC` 与 `status=1/FAILURE` 有什么本质区别？**
答：前者是 systemd 自报的退出码（`CLASS=systemd`），说明它没能按你写的把服务起起来，指向路径、执行位一类配置问题；后者是进程自己返回的退出码。用 `systemd-analyze exit-status` 可以区分来源。

**问：怎么确认一项资源上限真的写进了内核？**
答：`show -p <属性>` 与 `/sys/fs/cgroup<ControlGroup>/<文件>` 两个都读，值一致才算进了内核；不一致说明配置没生效，或还有上层 slice 在约束。

**问：`journalctl -u myapp` 查不到日志，按什么顺序排除？**
答：第一步确认落点，即读 `StandardOutput=` 与 `StandardError=`；第二步确认归属，即 `_SYSTEMD_UNIT` 与会话消息属于不同来源；第三步确认保留，即读 `/var/log/journal` 是否存在与 `--list-boots`；第四步确认限流与容量，即读实际落库条数与 `--disk-usage`；第五步确认过滤条件，注意 `-b` 与 `--since` 都按本地时区解释。

**问：`systemd-analyze blame` 的第一名一定是开机慢的元凶吗？**
答：不一定。它按初始化耗时排序，并行启动的单元会排在前面却不在关键路径上。谁是阻塞点要看 `critical-chain`。

**问：`systemctl --failed` 为空是否说明系统健康？**
答：它说明没有单元处于失败状态，是必要不充分条件。还要看 `is-system-running`（`degraded`/`maintenance`）、`journalctl -p err -b`、日志容量与时间同步状态。

**第一反应不要做什么**：不要不带 `-p` 就 `show`；不要只看 `verify` 的退出码；不要用 `blame` 的第一名结案；不要把 `--vacuum-*` 当只读操作；不要用有没有告警行判断日志是否被丢；不要把 `-b -1` 当成一定有；不要在生产上执行会 `start`/`stop`/`restart`/`daemon-reload`/`mask`/`clean`/`--vacuum-*` 的动作。
