## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **依赖与顺序是两层，必须分开表达**：`Wants=`/`Requires=` 决定「要不要把对方拉起来」，`After=`/`Before=` 只决定「谁先谁后」，**单独的 `After=` 不会拉起对方**。
> - **systemd 默认并行启动所有 unit**：只要没有 `After`/`Before` 约束，谁先谁后不确定。这是它比脚本式启动快的根本原因。
> - **实测证据（system 单元）**：`lab08-b` 写了 `Wants=lab08-a.service` + `After=lab08-a.service`，`lab08-a`（`oneshot`，耗时 3 秒）在 `08:05:09.561157` 结束，`lab08-b` 才在 `08:05:09.574918` 开始（间隔 **13.8 毫秒**）；把 `After=` 去掉后两者只隔 **0.8 毫秒**先后启动，`lab08-b` 先跑完而 `lab08-a` 的 3 秒还没走完。
> - **`After=` 只保证「对方的启动动作完成」，不保证「对方已经能提供服务」**：连接数据库、等待端口、等配置加载完，要靠 `network-online.target`、`ExecStartPre` 健康检查或应用自身的重试。
> - **每个 service 还有一批默认依赖**：实测一个空 `[Unit]` 的 system 单元拿到 `Requires=system.slice sysinit.target`、`After=systemd-journald.socket system.slice basic.target sysinit.target`；`DefaultDependencies=no` 可以关掉，但要知道自己在干什么。

## 1. 第一层：依赖——要不要把对方拉起来

| 指令 | 语义 | 对方启动失败时 | 会不会拉起对方 |
| --- | --- | --- | --- |
| `Wants=` | 弱依赖：尽力拉起，失败也继续 | 不影响自己 | 会 |
| `Requires=` | 强依赖：对方被停止/重启时自己跟着停/重启；**启动失败只在同时写了 `After=` 时才阻止自己启动** | 写了 `After=` → 自己不会被启动；没写 → 自己照常启动 | 会 |
| `Requisite=` | 对方必须**已经在运行**，否则自己失败 | 自己失败 | 不会 |
| `BindsTo=` | 更强的绑定：对方消失，自己也停 | 自己失败/停止 | 会 |
| `PartOf=` | 停止/重启的单向传播（跟依赖相反的方向） | 不影响启动 | 不会 |
| `Conflicts=` | 互斥：拉起我时停掉它 | 互相影响 | 会（停对方） |

> [!important] `Requires=` 的传播方向，比直觉窄
> `systemd.unit(5)` 的原文是两层：**对方被停止或重启时，自己无条件跟着停/重启**；而**对方启动失败时不启动自己，前提是同时写了 `After=`**。所以 `Requires=redis.service` 而不写 `After=`，既不保证顺序，也不保证 Redis 起不来时你不启动——它只是「把对方拉起来」，外加「对方被停时带你一起停」。想表达「对方起不来就别起我」，正确写法是 `Requires=` + `After=`。

最常见的写法组合是 **`Wants=` + `After=`**：

```ini
[Unit]
Wants=network-online.target
After=network-online.target
```

这句话的完整含义是：「**尝试**把 `network-online.target` 拉起来（失败也没关系），并且**等它的启动动作完成之后**再轮到我」。注意两个限定词——「尝试」和「启动动作完成」，它们分别对应下面两个坑。

## 2. 第二层：顺序——谁先谁后

`After=`/`Before=` 只表达排序，不产生依赖：

正确写法是「依赖 + 顺序」两个都写：

```ini
[Unit]
Wants=redis.service
After=redis.service
```

常见错误是只写依赖、不写顺序，两者会并行启动：

```ini
[Unit]
Requires=redis.service
```

实测（`lab08-a` 为 `oneshot`、耗时 3 秒，`lab08-b` 声明 `Wants=lab08-a.service` + `After=lab08-a.service`）：

```text
$ systemctl start lab08-b.service
$ journalctl -u lab08-a.service -u lab08-b.service -o short-precise --no-pager | tail -5
Sep 19 08:05:09.561157 linux-lab systemd[1]: Finished lab08-a.service - lab08 A (3s).
Sep 19 08:05:09.574918 linux-lab systemd[1]: Starting lab08-b.service - lab08 B (Wants+After A)...
Sep 19 08:05:09.576256 linux-lab bash[11895]: lab08-b-begin
Sep 19 08:05:10.578187 linux-lab bash[11895]: lab08-b-end
Sep 19 08:05:10.579506 linux-lab systemd[1]: Finished lab08-b.service - lab08 B (Wants+After A).
```

去掉 `After=` 之后，两者立刻同拍出发——**注意这一次 `lab08-b` 反而先跑完**，因为 `lab08-a` 还要 `sleep` 3 秒：

```text
Sep 19 08:05:10.780860 linux-lab systemd[1]: Starting lab08-a.service - lab08 A (3s)...
Sep 19 08:05:10.781683 linux-lab systemd[1]: Starting lab08-b.service - lab08 B (Wants only, no After)...
Sep 19 08:05:10.782427 linux-lab bash[11968]: lab08-a-begin
Sep 19 08:05:10.785755 linux-lab bash[11969]: lab08-b-begin
Sep 19 08:05:11.788783 linux-lab systemd[1]: Finished lab08-b.service - lab08 B (Wants only, no After).
```

> [!important] 并行是默认行为，串行要自己声明
> systemd 只要发现两个 unit 之间没有排序约束，就会并行创建它们。这不是缺陷，而是它启动快的设计。**「A 比 B 先就绪」这类需求，永远要靠 `After=` + 就绪判定（而不是靠运气）解决。**

补充一条本节实测到的**触发方式**差异：`systemctl start lab08-b.service` 会因为 `Wants=lab08-a.service` 把 `lab08-a` 一起拉起来（上面的第一条时间线里 `lab08-a` 确实被执行了）。如果只想**排序**、不想拉起对方，就不要写依赖——但那时对方很可能根本不在本次启动的图里。

## 3. 看依赖树：`list-dependencies`

```bash
systemctl list-dependencies lab08-b.service          # 验证：lab08-b 会拉起谁
systemctl list-dependencies --reverse lab08-b.service # 验证：谁依赖 lab08-b（被谁拉起）
systemctl show -p Requires -p Wants -p After -p Before lab08-b.service   # 验证：机器可读的四元组
```

实测输出（system 单元，默认依赖一起展开）：

```text
$ systemctl list-dependencies lab08-b.service
lab08-b.service
○ ├─lab08-a.service
● ├─system.slice
● └─sysinit.target

$ systemctl show -p Requires -p Wants -p After lab08-b.service
Requires=system.slice sysinit.target
Wants=lab08-a.service
After=system.slice sysinit.target basic.target systemd-journald.socket lab08-a.service
```

符号含义：`●` 表示此刻 `active`，`○` 表示未运行或**已运行完退出**。这里的 `○ lab08-a.service` 很容易误判——它是 `oneshot`，已经跑完并退出，所以显示为「未激活」，**但依赖关系确实存在**（`Wants=` 那一行就是证据）。排障时要看「依赖在不在」，而不是「它现在 active 不 active」。

再往下展开 `sysinit.target` 会拉出一长串系统单元（`apparmor`、`lvm2-monitor`、`systemd-journald`、`systemd-resolved`、`systemd-timesyncd`、`systemd-udevd`、`local-fs.target`、`swap.img.swap`…）——**这就是「给业务服务写 `DefaultDependencies=no` 之后你要自己负责多少事」的直观答案**。

> [!important] 用户级 manager 没有这套系统 target
> 上面那棵树的根是 `sysinit.target`/`basic.target`，它们是**系统级**专有的。实测 `/usr/lib/systemd/user/` 下只有 `basic.target`、`default.target`、`paths.target`、`sockets.target`、`timers.target`、`graphical-session*.target` 等一小套，**连 `network-online.target` 都不存在**。所以「靠 `Wants=network-online.target` 等网络就绪」这一招**只在系统级成立**；用户级要等网络，得自己找可观测的判据。这也是「本机有 root，依赖编排就该在系统级做」的一个具体理由。

## 4. 默认依赖：为什么服务会连上 `basic.target`

即使你在 `[Unit]` 里什么都不写，systemd 也会给普通 service 加一批**默认依赖**（`DefaultDependencies=yes` 时的行为，可用 `systemctl show -p DefaultDependencies` 核对）。本机实测一个 `[Unit]` 里只写了 `Description=` 的 system 单元：

```text
$ systemctl show -p DefaultDependencies -p Requires -p Wants -p After lab08-b.service
DefaultDependencies=yes
Requires=system.slice sysinit.target
Wants=
After=systemd-journald.socket system.slice basic.target sysinit.target
```

三条含义：

- 依赖并排在 `sysinit.target`、`basic.target` 之后启动，保证基础系统已经就绪；
- 与 `shutdown.target` 冲突，并在关机时先被停掉；
- 与 `final.target`、`umount.target` 等有对应关系。

`DefaultDependencies=no` 只在写早期启动或特殊单元时用（比如 `sysinit.target` 之前的单元），**普通业务服务不要改**——关掉之后你就要自己负责所有顺序，容易写出「服务比 `/usr` 挂载还早启动」这种问题。

## 5. 顺序 ≠ 就绪：最常见的「明明写了 After 还是连不上」

`After=` 的准确语义是：**等对方的启动动作完成**。对不同 `Type=`，这个「完成」的时刻不同（子笔记 06）：

| 依赖方 `Type=` | `After=` 等到的时刻 | 风险 |
| --- | --- | --- |
| `simple` | `ExecStart` 的进程刚被 fork 出来 | 对方可能还没开始监听端口 |
| `forking` | 父进程退出、pid 文件写出 | 后台进程可能还没就绪 |
| `notify` | 对方发了 `READY=1` | 这是最接近「真的就绪」的 |
| `oneshot` | 对方脚本跑完 | 就绪最明确 |

### 5.1 `network-online.target` 在真虚拟机上到底等什么（本次实测）

这台虚拟机由 `systemd-networkd` 管理网络（`NetworkManager.service` 不存在），`network-online.target` 由 `systemd-networkd-wait-online.service` 提供：

```text
$ systemctl show -p Wants -p After -p ActiveState network-online.target
Wants=systemd-networkd-wait-online.service
After=network.target systemd-networkd-wait-online.service
ActiveState=active

$ systemctl list-dependencies network-online.target
network-online.target
● └─systemd-networkd-wait-online.service
```

真正决定「什么时候算 online」的是 netplan 生成的 drop-in（`/run/systemd/system/systemd-networkd-wait-online.service.d/10-netplan.conf`）——它把上游 vendor 单元的判据改成了**按接口等待**，而且**取消了启动超时**：

```text
[Unit]
ConditionPathIsSymbolicLink=/run/systemd/generator/network-online.target.wants/systemd-networkd-wait-online.service

[Service]
ExecStart=
ExecStart=/lib/systemd/systemd-networkd-wait-online -i ens33:degraded
ExecStart=/lib/systemd/systemd-networkd-wait-online --any -o routable -i ens33
TimeoutStartUSec=infinity
```

含义有三条，都值得记住：

1. **它等的是「接口 `ens33` 达到 routable」，不是「网线插上了」**。实测 `ens33` 状态：`Driver: e1000`、`State: routable (configured)`、`Online state: online`、`192.168.246.128/24`、默认路由 `via 192.168.246.2`。
2. **`TimeoutStartUSec=infinity`**：这个单元**不会超时**。一旦接口一直不到 routable，依赖它的服务就会一直卡在 `activating`。这就是「开机慢且没有任何报错」的一种成因。
3. **它在这次启动里花了 1.231 秒**，是 `systemd-analyze blame` 的**第一名**（`systemd-networkd.service` 自身 336 毫秒）——也就是说，写 `After=network-online.target` 是有真实开机代价的。

反过来，**已经在线时它立刻返回**：实测在我们的单元里 `Wants=network-online.target` + `After=network-online.target` 的启动用了 `0.020490524` 秒，完全不带这个依赖的对照组是 `0.020476160` 秒——**两者相差 0.014 毫秒（< 0.02 毫秒），可以认为没有实际差别**：代价只在你真的需要等网络时才付。

```text
lab08n-noplain start_rc=0 seconds=.020476160
lab08n-net start_rc=0 seconds=.020490524
```

所以「等一个真的表示就绪的目标」是对的，但**要先确认它在你机器上等的是什么、有没有超时**，否则会把一次网络配置问题变成一次无声的开机挂起。

### 5.2 连不上依赖的三层解法

1. **等一个真的表示就绪的目标**：如 `network-online.target`（等网络配置完成），或让依赖方用 `Type=notify`。
2. **在启动前做一次健康检查**：

```ini
[Service]
ExecStartPre=/usr/local/bin/wait-for-port db.internal 5432 30
```

3. **让应用自己带重试**：连接失败就退避重试，配合 `Restart=on-failure` + `RestartSec=`（子笔记 10）。生产服务不能假设「启动顺序对了，依赖就一定在」。

```bash
systemctl show myapp.service -p After -p Wants -p Requires -p ExecStartPre -p Restart
```

### 实验 3：依赖与顺序（`Wants`/`After`）

> [!example]- 实验 3：用时间戳证明「顺序被遵守、去掉 After 就并行」
> **怎么做**：在 `/etc/systemd/system/` 建两个 `oneshot` system 单元。`lab08-a` 打印时间戳后 `sleep 3`；`lab08-b` 声明 `Wants=lab08-a.service` + `After=lab08-a.service`，打印自己的时间戳。`daemon-reload` 后 `systemctl start lab08-b.service`，再用 `journalctl -u lab08-a -u lab08-b -o short-precise --no-pager | tail -5` 看先后。**再把 `After=lab08-a.service` 去掉重跑一遍**。
> **预期**：有 `After` 时 `lab08-a` 的 `Finished` 早于 `lab08-b` 的 `Starting`（本机实测 `09.561157` → `09.574918`，差 13.8 毫秒）；去掉后两者在 `10.780860` / `10.781683` 同拍启动（差 0.8 毫秒），而且 `lab08-b` 会先跑完。
> **风险**：低（自建 system 单元、`oneshot` 秒级任务；**不要碰系统服务**）；**耗时**：约 5 分钟；**回滚**：`rm -f /etc/systemd/system/lab08-a.service /etc/systemd/system/lab08-b.service; systemctl daemon-reload; systemctl reset-failed lab08-a.service lab08-b.service`。
> 机器：任意有 root 的可快照实验机（本机实测 systemd 255）。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 只写 `Requires=` 不写 `After=` | 依赖存在但顺序不保证，两者可能并行 |
| 只写 `After=` 不写 `Wants=`/`Requires=` | 只排序、不拉起；对方没在启动路径里时根本不会被启动 |
| 写 `Requires=` 而不想被拖累 | 对方**被停止/重启**时无条件带你一起停/重启；对方**启动失败**时是否阻止你启动，取决于有没有写 `After=`；只想「尽力而为」要用 `Wants=` |
| 认为 `After=` 就等于「对方准备好了」 | 它只等启动动作完成；就绪要靠 `notify`/健康检查/应用重试 |
| 看到 `list-dependencies` 里依赖是 `○` 就以为依赖丢了 | `oneshot` 跑完会退出，显示为未激活属正常；看 `Wants=`/`Requires=` 那两行才是准 |
| 给业务服务写 `DefaultDependencies=no` | 会失去 `sysinit.target`/`basic.target`/关机顺序的默认保护（实测默认 `After` 里就有一串系统单元），容易出疑难问题 |
| 无脑 `After=network-online.target` | 本机这个单元由 netplan 改成 `-i ens33:degraded` 且 **`TimeoutStartUSec=infinity`**；接口一直不就绪时，依赖它的服务会**无声卡在 `activating`**，而它自己占了开机 blame 第一名 1.231 秒 |
| 用 `sleep 30` 解决依赖未就绪 | 只是把问题推迟到负载高峰；应该等一个可观测的就绪信号 |
| 在用户级 manager 上抄系统级的 target 编排 | 用户级**没有 `network-online.target`**（实测 `/usr/lib/systemd/user/` 下不存在），抄过去会得到一个「写了但永远不会被满足」的顺序约束 |

## 决策练习

> [!question]- 场景：你写的服务 `myapp` 依赖本机的 `redis.service`。你写了 `Requires=redis.service`、`After=redis.service`，但发布到新机器后偶发「启动 30 秒内连接 Redis 失败」。
> A. 在 `ExecStart=` 前面加 `sleep 30`
> B. 检查 `redis.service` 的 `Type=`，把等待改成「可观测的就绪信号」：要么让 redis 用 `Type=notify`，要么给 myapp 加 `ExecStartPre` 端口探测，并让应用带重试
> C. 把 `Requires=` 改成 `Wants=`，避免被 Redis 拖累
> **答案：B。**
> A 是猜测式等待，慢机器还是会失败、快机器白等 30 秒。
> C 只改变了「Redis 失败时 myapp 怎么办」，没有解决「Redis 还没就绪 myapp 就开跑」。
> B 是正解：**顺序 ≠ 就绪，用可观测信号或应用重试把「等」变成有依据的动作**。

## 要点自测

> [!question]- `Wants=`/`Requires=` 与 `After=`/`Before=` 的区别是什么？
> - 前两者是**依赖**：回答「要不要把对方拉起来、对方失败我怎么办」；`Wants` 尽力而为，`Requires` 在对方被停止/重启时带你一起走，对方启动失败时只有配上 `After=` 才阻止你启动。
> - 后两者是**顺序**：只回答「谁先谁后」，不产生依赖；只写 `After=` 而没写依赖，对方可能根本不在本次启动里。
> - 两者必须分开表达：「要拉起对方，并且等它启动动作完成」= `Wants`/`Requires` + `After`。
> - **第一反应不要是什么**：不要以为写了 `Requires=` 就有顺序，也不要以为写了 `After=` 就会拉起对方。

> [!question]- 为什么 `After=` 写了，服务还是连不上依赖？
> - `After=` 只等「对方的启动动作完成」，而不同 `Type=` 对「完成」的定义不同：`simple` 是 fork 出来、`forking` 是父进程退出、`notify` 才是真的 `READY=1`。
> - 所以端口未监听、迁移未完成、配置未加载完都可能发生。
> - 解法：等一个真正的就绪目标（`notify`/`network-online.target`）、`ExecStartPre` 健康检查、应用自带重试，三者选其一或叠加。
> - **第一反应不要是什么**：不要用 `sleep` 掩盖，也不要把 `After=` 当成「已经就绪」。

> [!question]- 为什么说 systemd 默认「并行」？这对写 unit 意味着什么？
> - 没有 `After`/`Before` 约束的 unit 会被并行创建执行（实测去掉 `After=` 后两个单元只隔 0.8 毫秒先后启动），这是 systemd 启动快的原因。
> - 意味着**任何「必须先于/后于」的假设都必须显式声明**，否则偶发性地出问题。
> - 排查顺序问题时用 `journalctl -o short-precise` 对时间戳，或用 `list-dependencies` 看关系图。
> - **第一反应不要是什么**：不要依赖「上次启动碰巧是对的」——并行环境下，顺序不保证，就是不确定。

> [!question]- `network-online.target` 一定代表「网络可用」吗？在系统级和用户级上一样吗？
> - 不一定：本机由 netplan 的 drop-in 改成等 `ens33` 达到 `degraded`/`routable`，并且 **`TimeoutStartUSec=infinity`**——它会一直等、不报错、不超时。
> - 它确实有成本：这次启动里 `systemd-networkd-wait-online.service` 花了 1.231 秒，是 `systemd-analyze blame` 第一；已经在线时立刻返回（实测 0.0205 秒）。
> - **两棵 manager 不一样**：`network-online.target` 只存在于系统级；用户级 `/usr/lib/systemd/user/` 下没有这个目标。
> - **第一反应不要是什么**：不要把它当成「网络 OK 的保证」写进关键依赖链，也不要在用户单元里抄它。
