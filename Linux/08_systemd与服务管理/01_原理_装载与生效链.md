# 装载与生效链

## 1. 生效配置是三份东西拼出来的

改了一个 unit 文件却不生效，根因几乎总在同一件事上：**systemd 手里那份配置，与你编辑的那个文件不是同一份东西**。这里说的「systemd 手里」，指的就是管理进程本身——它是系统启动后内核拉起的第一个用户态进程（PID 1），unit 的装载、依赖与生命周期都由它负责，下文统称 **manager**。从磁盘到进程，一条配置要经过三次转换：

1. **磁盘上的文件**：systemd 先取搜索路径里优先级最高的那一份同名 unit，再把挂在其名下的全部 drop-in 片段按规则叠加进来，因此这一步得到的是一份合成文本；
2. **manager 的认知**：PID 1 把这份文本解析成属性，装进内存里的依赖图。此后所有判断——依赖、顺序、就绪判定、资源上限——用的都是这一份；
3. **进程的实际状态**：`fork`/`execve` 之后，环境变量、句柄上限、cgroup 归属才真正落到进程身上，因此这一步只在启动或重启时发生一次。

三份东西各有各的观测入口，不能互相替代：`systemctl cat` 看**文件**（它会用 `# <路径>` 行摊开每个键来自哪个文件），`systemctl show -p <属性>` 看 **manager**，`/proc/<PID>/environ`、`/proc/<PID>/limits`、`/proc/<PID>/cgroup` 看**进程**。

由此得到这三份配置之间最重要的一条判据：**`daemon-reload` 之后，manager 变了，进程没变。** 让 PID 1 重读文件，它只是把新属性装进内存；已经在跑的进程环境、句柄上限、工作目录都还是老的，`MainPID` 也不会变。要让新配置落到进程上，只有重启（或在应用自己支持的前提下重载）。

## 2. 搜索路径：同名取一份，不合并

`systemd-analyze unit-paths` 会打印当前机器上的完整搜索顺序，它分成三类：管理员的、运行时的、发行版自带的。真正要记住的是三条路径及其顺序，从高到低依次是 `/etc/systemd/system/`、`/run/systemd/system/` 与 `/usr/lib/systemd/system/`。

- **同名 unit 只取优先级最高的那一份，不做内容合并**。想确认实际吃的是哪一份，看 `systemctl show -p FragmentPath`；它指向哪个文件，就是哪一份生效。这与「把片段叠起来」的直觉相反——**叠加只发生在 drop-in 层，不发生在同名文件之间**。
- `/run/systemd/system` 常被误当成最高优先级，其实它在 `/etc` 之后。`/run` 的特殊之处只是「重启即消失」，适合放临时覆盖与生成物，不适合当覆盖 `/etc` 的手段。
- `mask` 正是利用这一层实现的：在 `/etc/systemd/system/` 下建一个指向 `/dev/null` 的同名软链，把发行版那一份彻底挡住。这也是为什么解除屏蔽（`unmask`）之后，单元会退回到它原本的安装态（例如 `static`），而不是变成 `enabled`。
- **改 `/usr/lib/systemd/system/` 下的发行版文件是错的**：软件包升级会把它覆盖回去，而且这类改动在别的机器上不存在。所有本地改动都应当走 `/etc` 下的 drop-in。

## 3. drop-in：只写差异的那一层

`systemctl edit <unit>` 会在 `/etc/systemd/system/<unit>.d/` 下创建一份 `override.conf`。它的语义是**在同一份 unit 上覆盖同名键、追加新键**，而不是替换整份文件：

- **同一份 unit 的多个 drop-in 按文件名字典序生效**，后读到的覆盖先读到的。因此文件名要带序号（`10-base.conf`、`20-site.conf`），不要用 `a.conf`、`b.conf` 这种不表达次序的名字。
- `systemctl show -p DropInPaths` 列出实际参与合成的全部片段。这一项是空的，说明你以为写了的 drop-in 根本没被读到——路径或文件名不对，或者写完没执行 `daemon-reload`。
- drop-in 也是 unit 来源，**改完同样要 `daemon-reload`**。它不会自己生效。
- 回滚就是删掉那个文件再 `daemon-reload`，比在发行版原文件里改回原样可靠得多。

什么时候不该用 drop-in：整份配置要重写时，`systemctl edit --full` 会把整份 unit 复制到 `/etc` 下改。代价是此后与发行版的更新脱节——原文件改进了，你手上这份不会跟着变。

## 4. `daemon-reload`、`reload`、`restart` 是三个不同的动作

| 动作 | 它做了什么 | 它没有做什么 |
| --- | --- | --- |
| `daemon-reload` | 它让 PID 1 重读全部 unit 文件与 drop-in、重跑 generator 并重建依赖图，因此 manager 的认知随之更新 | 它不重启任何进程，也不把新环境注入运行中的进程 |
| `daemon-reexec` | 它让 PID 1 重新执行自身，因此 manager 自身的配置被重读 | 它**不重读 unit 文件**，那是 `daemon-reload` 的职责 |
| `reload` | 它执行该单元的 `ExecReload=` 命令，因此进程本身不换 | 它不重读文件，也不做任何配置注入 |
| `restart` | 它停旧、拉新，因此 `MainPID` 会更换 | 它带来中断窗口，并且会重置 `Result`、`NRestarts` 与上一进程的输出 |

`reload` 有两处容易被当成「不中断的重启」而误用：

- **它不重新读取配置文件，只是执行 `ExecReload=`**。如果应用本身不重读配置，`reload` 返回 0 也不代表新值生效。
- **单元没写 `ExecReload=` 时，`reload` 直接失败**（作业类型不适用），而不是悄悄降级成重启。这时日志与退出码都会明确告诉你「这个单元不支持 reload」。
- 默认的重载信号是 `SIGHUP`。应用若没装 `SIGHUP` 处理函数，默认动作就是终止进程——这时 `reload` 会先把服务打死。判断依据是应用文档，不是「reload 一定更安全」。

对多数服务，判断「这项配置该用哪种方式生效」的标准只有一条：**这项配置是在进程启动时读取的，还是进程运行期间持续读取的**。`ExecStart`、`Environment`、`User`、`Type`、资源上限、沙箱选项都属于前者，必须 `restart`；`ExecReload` 能覆盖的恰恰只有应用明确支持重载的那部分。

## 5. 静默丢弃：配置级的坑

unit 文件的语法错误分两档，代价完全不同：

- **硬错误**：`systemd-analyze verify` 会报错并非零退出（例如给 `Type=simple` 写了多条 `ExecStart=`）。单元根本起不来，问题会立刻暴露。
- **被忽略的键**：键名拼错，或写进了错误的小节——例如把 `StartLimitIntervalSec=`、`StartLimitBurst=` 写进 `[Service]` 而不是 `[Unit]`。这种情况 verify 会打印一行 `Unknown key name ... ignoring`，**但退出码仍是 0**，配置被静静丢掉。单元照常启动，只是那项限制不存在。

所以 `verify` 的用法是**读输出，不是读退出码**。一个干净的单元在 verify 下应当**完全沉默**；它只要说话了，就说明有东西被忽略或被拒绝。

`%` 在 unit 文件里是说明符前缀（`%i`、`%n`、`%t`、`%H`…）。想写一个字面的 `%` 必须写成 `%%`，`$` 要写成 `$$`。写错的后果不是报错而是展开失败或展开成别的值——**模板单元的占位符写错同样不报错，只会得到一个奇怪的结果**，所以 `systemctl cat` 里核对展开后的文本是必要动作，不是多余动作。

## 6. 常见误解

| 常见说法 | 事实 |
| --- | --- |
| 「改完文件 `restart` 一下就好」 | 没执行 `daemon-reload` 时 manager 手里还是旧配置，因此重启出来的仍是旧行为 |
| 「`daemon-reload` 就等于重启服务」 | 它只换 manager 的认知，而进程环境与句柄上限仍是启动时的值，`MainPID` 也不变 |
| 「`systemctl reload` 一定不中断服务」 | 它只执行 `ExecReload=`；若没写该键就直接失败，而默认信号 `SIGHUP` 还可能直接终止进程 |
| 「`daemon-reexec` 能重读 unit」 | 它重执行 PID 1 并重读 manager 自身的配置，而 unit 文件归 `daemon-reload` 管 |
| 「`Loaded: loaded` 说明配置正确生效」 | `Loaded` 只说明装载成功，因此生效值要看 `show -p <属性>`，而全貌要看 `cat` |
| 「同名 unit 会被合并」 | 它只取优先级最高的一份，而叠加只发生在 drop-in 之间 |
| 「`/run/systemd/system` 优先级最高」 | 它的优先级在 `/etc/systemd/system` 之后，而 `/run` 的特点只是重启即消失 |
| 「`verify` 通过就万事大吉」 | 未知键名会被忽略而退出码仍为 0，因此要读它的输出，而干净的单元应当沉默 |
| 「drop-in 不用 `daemon-reload`」 | 它也是 unit 来源，因此同样需要 `daemon-reload` |
| 「改 `/usr/lib/systemd/system/` 里的文件最直接」 | 升级会覆盖它，因此本地改动一律走 `/etc` 下的 drop-in |
| 「`enable` 是现在就启动」 | 它只按 `[Install]` 建自启软链，因此要立刻启动得另加 `--now` 或 `start` |
| 「`disable` 就是彻底停用」 | 它只去掉自启软链，因此服务仍可被手动或依赖拉起；彻底停用要 `mask` |

## 要点自测

**问：`daemon-reload` 之后，为什么 `systemctl show` 的值变了，服务行为却没变？**
答：`show` 读的是 manager 里的属性，`daemon-reload` 换的正是这一份；运行中进程的环境、句柄上限、cgroup 归属在 `execve` 时就定下了，只有重启才会重新应用。

**问：怎么确认一个单元实际吃的是哪个文件？**
答：`systemctl show -p FragmentPath -p DropInPaths`。前者是生效的原文件，后者是叠上去的片段列表；`systemctl cat` 会把每个键的来源文件标出来。

**问：为什么 `/etc/systemd/system` 下的同名文件会盖住 `/usr/lib/systemd/system` 下的？**
答：搜索路径按优先级取第一份命中，不合并内容。`mask` 也靠这个机制：在 `/etc` 下建一个指向 `/dev/null` 的软链就能挡住发行版那份。

**问：`verify` 退出码是 0，能断定配置没问题吗？**
答：不能。键名拼错或写错小节时它只打印 `Unknown key name ... ignoring` 并返回 0，那项配置被丢弃。要读输出；干净单元在 verify 下应当没有任何输出。

**问：什么情况下必须 `restart` 而不能靠 `reload`？**
答：改动属于「进程启动时读取一次」的项时——`ExecStart`、`Environment`、`User`、`Type`、资源上限、沙箱选项。`reload` 只执行 `ExecReload=`，且应用若不重读配置，它连配置都不碰。

**第一反应不要做什么**：不要只 `restart` 而不看生效值；不要把 `daemon-reload` 当重启的替代品；不要在 `reload` 失败时以为它悄悄降级成了重启；不要用 `verify` 的退出码当唯一守门条件；不要改发行版目录下的 unit 文件。

## 参考文档

- `man 5 systemd.unit`：unit 搜索路径、优先级、`[Install]`、模板单元与说明符（`%i`/`%n`/`%t` 等）。
- `man 5 systemd.service`：`ExecStart=`/`ExecReload=`/`ExecStop=` 的语义与失败处理。
- `man 1 systemctl`：`cat`、`show`、`edit`、`daemon-reload`、`daemon-reexec`、`enable`、`mask` 的行为与退出码。
- `man 1 systemd-analyze`：`unit-paths`、`verify`、`cat-config`。
- `man 5 systemd-system.conf`：manager 自身的配置与 `Default*` 系列默认值的来源（重执行 PID 1 时会重新读取它）。
