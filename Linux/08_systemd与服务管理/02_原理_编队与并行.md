# 编队与并行

## 1. 两问两答：拉起与先后

「服务 A 依赖服务 B」在日常说法里是一句话，在 systemd 里必须拆成两个**彼此独立**的问题：

- **要不要把对方拉起来**——由依赖指令回答（`Wants=`/`Requires=`/`Requisite=`/`BindsTo=`）；
- **谁先谁后**——由排序指令回答（`After=`/`Before=`），它们**不产生任何依赖**。

两者都写了才有「先起 B 再起 A」的效果。这个拆分是 systemd 与 `init` 脚本时代最大的观念差别：SysV 的 `Required-Start:` 注释把两件事揉在一起，而 systemd 把「集合关系」与「时间关系」分开表达，代价是**你必须两个都写对**。

由此派生出四条必须记牢的推论：

1. **只写 `After=` 不会拉起对方**。对方不在本次事务的启动集合里，压根不会启动，你的单元也不会等它——因为等待的对象根本没进入队列。
2. **只写 `Wants=`/`Requires=` 不保证顺序**。两者会在同一个事务里被并行创建，谁先就绪取决于各自耗时。这是并行启动的来源，也是「明明写了依赖却偶发连不上」的来源。
3. **写了 `Requires=` 也不保证「对方起不来我就不起」**。要让对方的启动失败阻止自己，还需要同时给出排序关系（`After=`）。想「尽力而为、失败无妨」，用 `Wants=`。
4. **「顺序上对方已完成启动动作」不等于「对方已就绪可服务」**。`After=` 等到的时刻由对方的 `Type=` 决定，详见第 5 节。

## 2. 六条依赖指令：方向与传播

| 指令 | 拉起对方 | 对方消失/停止时 | 典型用途 |
| --- | --- | --- | --- |
| `Wants=` | 会（尽力，失败不影响自己） | 无传播 | 缺省推荐：可选的协作单元 |
| `Requires=` | 会 | 对方被停或重启时，自己无条件跟着停或重启 | 强关联：离开对方无法工作 |
| `Requisite=` | **不会** | —— 对方必须先已在运行，否则自己启动失败 | 只做前置检查，不改变对方的生命周期 |
| `BindsTo=` | 会 | 对方消失（含意外退出）时自己也停 | 与设备、挂载点等「实体」绑定 |
| `PartOf=` | **不会** | 方向相反的传播：**对方**停/重启时，自己跟着停/重启 | 一组单元的统一启停 |
| `Conflicts=` | —— 拉起我时先停对方 | 互斥 | 互斥的服务（保留旧实现做回退） |

这四列话都在表里，但落到机器上要读的是字段：`systemctl show -p Wants -p Requires -p After -p Before` 给出「本单元声明了什么」，`list-dependencies [--reverse]` 给出「这些声明此刻牵动了谁」；两者不一致时，以 `show` 的字段为准——树上的符号只表示当前激活状态。判明传播方向之后，下一步是确认对方到底「到了哪一步」（第 5 节），因为方向对、时刻不对仍然会连不上。

三处容易读错的地方：

- **`Requires=` 的传播方向是「对方 → 我」**：对方停，我也停。这是很多人没预期到的副作用——一次针对 B 的维护性重启会把 A 一起带下去。只想「需要它在，但别牵扯我」的场景，`Wants=` 加自己的重试逻辑更稳妥。
- **`PartOf=` 的传播方向与依赖相反**：写在 A 里的 `PartOf=B` 意思是「B 停/重启时带着我」，而不是「我停时带着 B」。要双向，两边互相写，或用一个 target 统一编排。
- **`Conflicts=` 不是顺序**。它表达互斥，配合 `After=` 才能确定停谁先谁后。

## 3. 默认并行，以及它的边界

**没有排序约束的两个单元会被并行启动**，这不是「实现细节」，是设计目标：并行是把开机时间从「脚本逐条等待」压缩下来的主要原因。因此任何「A 必须在 B 之后」的假设，都必须显式写成排序关系，而不能指望「事务里的先后」。

并行并不是无政府的，缺省还有一层保底：普通 service 单元的 `DefaultDependencies=yes` 会自动补上一组依赖与排序——它被挂到 `sysinit.target`、`basic.target` 之下，与 `shutdown.target` 冲突（关机时先被停），并排在 `systemd-journald.socket`、`system.slice` 之后。这解释了为什么一个只写了 `Description=` 与 `ExecStart=` 的单元也能正常参与开机与关机顺序。

把 `DefaultDependencies=no` 关掉，就等于放弃这层保底，此后所有顺序都要自己负责。它只属于早期启动阶段那些必须在 `sysinit.target` 之前完成的特殊单元；给普通业务服务关掉它，是制造疑难问题的常见方式。

## 4. 读依赖图：看得见的关系与看不见的关系

`systemctl list-dependencies <unit>` 打印一棵树，行首的符号表示**当前时刻**的激活状态，而不是「依赖是否存在」：

- `●` 表示此刻 active；
- `○` 表示此刻未运行——**`Type=oneshot` 的单元跑完就退到 inactive，显示成 `○` 是正常的**，不代表依赖丢了。

真正的关系要以 `systemctl show -p Requires -p Wants -p After -p Before` 为准。反过来问「谁会因为我被拉起来」，用 `list-dependencies --reverse`。

时序核实不能靠 `list-dependencies` 的排列，要看日志时间戳：`journalctl -u A -u B -o short-precise` 把两个单元的消息放在一条时间线上，按微秒级时间戳判断「谁的 `Starting`/`Finished` 在前」。这一条在判断并行与串行时是唯一可靠的证据。

## 5. 排序不等于就绪

这是本章最贵的一个坑：**`After=B` 只保证「B 的启动动作完成了」，而「启动动作完成」的含义完全由 B 的 `Type=` 决定**。

| B 的 `Type=` | `After=B` 实际等到的时刻 |
| --- | --- |
| `simple` | B 的进程被 `fork` 出来（此时它可能还没监听端口） |
| `exec` | B 的二进制真正 `execve` 成功 |
| `forking` | B 的父进程退出、子进程留下 |
| `notify` | B 通过 `sd_notify` 报告 `READY=1`（最接近「真就绪」） |
| `oneshot` | B 的脚本跑完 |

所以「服务 B 是 `Type=simple` 且要花两秒初始化」时，`After=B` 的 A 会在第二秒之前就开始跑，然后抱怨连不上。三类正解，按优先级：

1. **等一个真正代表就绪的目标**：让 B 写成 `Type=notify` 并在就绪时报告，或在 B 之后等 `network-online.target` 这类有实际判据的目标；
2. **自己探测**：在 `ExecStartPre=` 里做健康检查（带重试与超时），探测失败就让启动失败——注意 `ExecStartPre=` 返回非零会让整个服务启动失败，所以探测逻辑必须自带重试，不能把「偶尔还没好」直接报错；
3. **应用层重试**：`Restart=on-failure` 配合 `RestartSec=`，让 A 自己重连。这是最后一道防线，不是第一选择。

**不要用 `sleep` 掩盖依赖未就绪**。它把「确定性等待」换成「赌一个够长的固定时长」：负载高时不够长，负载低时白等，而且失败时没有任何可读的证据。

还要注意 `network-online.target` 也不是「网络已可用」的保证：它本身不做判断，等的是被 `Wants=` 拉起的网络等待服务；那项服务等哪些接口、允许多久超时，由网络配置（如 netplan 生成的 drop-in）决定，某些发行版把它设成不超时——接口迟迟不就绪时，依赖它的服务会安静地卡在 `activating`，日志里没有任何错误。核实方法是 `systemctl show network-online.target` 与查该等待服务的 drop-in，而不是假定。

## 常见误解

| 常见说法 | 事实 |
| --- | --- |
| 「`After=` 会把对方拉起来」 | 排序不产生依赖；对方不在启动集合里就不会启动 |
| 「`Wants=` 保证顺序」 | `Wants=` 只管尽力拉起；顺序要另写 `After=` |
| 「只写 `Requires=` 就有顺序」 | 不保证，两者可能并行 |
| 「写了 `Requires=` 对方失败我就不会起」 | 只有同时给出排序关系时，对方的启动失败才阻止自己 |
| 「`Requires=` 只是单向依赖，不影响我」 | 对方停/重启会无条件带上自己 |
| 「`PartOf=` 是依赖对方」 | 它是方向相反的启停传播，且不拉起对方 |
| 「`Conflicts=` 用来保证顺序」 | 它表达互斥；顺序要 `After=` |
| 「`After=` 就等于对方准备好了」 | 只等到对方的启动动作完成，含义随对方的 `Type=` 而变 |
| 「`list-dependencies` 里的 `○` 说明依赖没生效」 | `oneshot` 跑完就退到 inactive，显示 `○` 属正常 |
| 「关闭 `DefaultDependencies=` 只是去掉几条连线」 | 会一并放弃 `sysinit`/`basic`/关机顺序的保底，普通业务单元不该关 |
| 「用 `sleep 30` 等依赖就绪」 | 只是把问题推迟到负载高峰；应等可观测的就绪信号或让应用重试 |
| 「`network-online.target` 代表网络可用」 | 它本身不做判断，判据在被拉起的等待服务里，且可能被配成不超时 |

## 要点自测

**问：只写 `After=db.service` 的服务，能不能保证数据库先起来？**
答：不能。`After=` 只排序不拉起；数据库不在启动集合里就不会被启动，你的服务也不会等它。要「拉起并等待」得同时写 `Wants=`/`Requires=` 与 `After=`。

**问：`Requires=` 与 `Wants=` 的差别在运维上体现为什么？**
答：`Requires=` 双向强关联——对方停或重启时自己无条件跟着走，且配合 `After=` 时对方启动失败会阻止自己；`Wants=` 只是尽力拉起，对方的问题不牵连自己。

**问：为什么「依赖写了、顺序也写了」还会出现「连不上对方」？**
答：因为 `After=` 等到的是对方的「启动动作完成」，其含义随对方 `Type=` 而变；`simple`/`forking` 都可能在任何监听动作之前就报完成。要真就绪，用 `notify` 或自己探测。

**问：`systemctl list-dependencies` 里出现 `○` 要紧吗？**
答：先看对方的类型。`oneshot` 单元跑完就退到 inactive，显示 `○` 是正常的。依赖是否存在要读 `show -p Requires -p Wants`；时序要读 `journalctl -o short-precise` 的时间戳。

**问：`DefaultDependencies=no` 会在什么时候用到？**
答：只在早期启动阶段那些必须先于 `sysinit.target` 完成的特殊单元上。普通业务服务关掉它，就失去了与 `shutdown.target` 的互斥以及基础排序，容易出难以复现的顺序问题。

**第一反应不要做什么**：不要以为写了依赖就有顺序；不要以为写了 `After=` 就会拉起对方；不要把 `list-dependencies` 的符号当依赖存在性；不要用 `sleep` 掩盖未就绪；不要把 `network-online.target` 当网络可用的保证；不要给业务服务关掉 `DefaultDependencies=`。
