# 临时文件与运行时目录治理

> [!cite] 参考资料

>
> 实测输出来自 Ubuntu 24.04.5 LTS（VMware 虚拟机）/ 内核 6.8.0-139-generic / systemd 255（`255.4-1ubuntu8.17`）/ cgroup v2 / root 的**系统级**实例：`systemd-tmpfiles --create/--clean/--remove/--cat-config`、`/usr/lib/tmpfiles.d/` 与 `/etc/tmpfiles.d/` 的实际内容、`systemd-tmpfiles-clean.timer`、`/tmp` 与 `/run` 的挂载属性、`StateDirectory=`/`RuntimeDirectory=` 的落点与清理本次都已实测。

> **这篇讲什么**：`/tmp`、`/run` 这些路径「谁在清、按什么规则清」，以及**服务的数据到底该放哪**。这一篇回答两个高频问题：`/tmp` 里的文件怎么没了，以及「服务在容器/沙箱里看到的 `/tmp` 是哪一个」。

## 0. 30 秒速览

> [!abstract] 这一篇只要记住六句话
> - **`/tmp`、`/run` 由 `systemd-tmpfiles` 按声明式规则维护**：规则来源是三个目录——`/usr/lib/tmpfiles.d/`（本机 **31** 个文件）、`/etc/tmpfiles.d/`（本机 1 个：`screen-cleanup.conf`）、`/run/tmpfiles.d/`（本机 1 个：`static-nodes.conf`）；`/usr/local/lib/tmpfiles.d/` 在本机**不存在**。**同名时 `/etc` 版本会盖掉 `/usr/lib` 版本**（`screen-cleanup.conf` 正是这种情况），所以磁盘上 33 个文件、`--cat-config` 汇总出的**生效来源只有 32 条**。
> - **本机实测 `/tmp` 的规则是 `D /tmp 1777 root root 30d`，由 `systemd-tmpfiles-clean.timer` 驱动，间隔是 `OnBootSec=15min` + `OnUnitActiveSec=1d`（不是 `OnCalendar=`）**——所以「文件在 `/tmp` 里怎么没了」的三种解释是：这个 timer、`PrivateTmp`、或应用自清理。
> - **本机的 `/tmp` 不是 tmpfs**：`findmnt -T /tmp` 显示它落在根文件系统 `/dev/mapper/ubuntu--vg-ubuntu--lv`（ext4）上，`/var/tmp` 同样；只有 `/run`、`/run/lock` 是 tmpfs。所以在这台机器上「重启会清空 `/tmp`」**不成立**，别把它写进处置手册。
> - **age 默认同时看 mtime/atime/ctime**（`age-by=abcmABM`）：**只要其中任一时间戳比「当前时间 - age」更新，就不会清理**。
> - **实测反直觉现象**：`touch -d "40 days ago"` 造出的「老文件」不会被删，因为它的 **ctime 是「现在」**；把规则改成 `m:30d`（只看 mtime）后立刻被删。
> - **服务的数据按生命周期放对地方**：跨重启持久用 `/var/lib`（`StateDirectory=`），临时但需跨进程共享用 `/run`（`RuntimeDirectory=`），纯易失用 `/tmp`（且知道它会被清/可能私有）。本机系统级实测这四个目录都会被 systemd 自动建出来，`systemctl clean --what=all` 又能全部收走。
> - **这些目录在 unit 文件里有对应的「说明符」**：`%t`=`/run`、`%T`=`/tmp`、`%S`=`/var/lib`、`%C`=`/var/cache`、`%L`=`/var/log`。但它们**会被 systemd 在 `ExecStart=` 里无条件展开**，脚本里的 `date +%T`、`stat -c %d` 到了 unit 里就变成别的东西（见第 6 节）。

## 1. 规则长什么样、放在哪

一条 tmpfiles 规则的格式是 `Type Path Mode User Group Age Argument`，例如：

```text
D /tmp 1777 root root 30d
```

| 类型 | 语义 |
| --- | --- |
| `d` | 创建目录；**其内容按 age 清理** |
| `D` | 创建目录，并在 `--remove` 时清空内容（`--clean` 仍按 age） |
| `e` | 只调整已存在的文件/目录（不创建），并按 age 清理 |
| `x` / `X` | 排除某些路径不参与清理 |
| `r` / `R` | 删除文件 / 递归删除目录（**无年龄判断**） |
| `f` / `F` | 创建文件 / 创建并清空 |
| `L` | 创建软链 |

规则文件的位置与优先级和 unit 类似：`/etc/tmpfiles.d/` 覆盖 `/usr/lib/tmpfiles.d/`；用户规则在 `~/.config/user-tmpfiles.d/`。

```bash
grep -vE "^\s*(#|$)" /usr/lib/tmpfiles.d/tmp.conf          # 验证：本机规则
systemctl list-timers --all --no-pager | grep tmpfiles     # 验证：清理任务的调度时间
systemd-tmpfiles --cat-config | grep -E "^[a-zA-Z].*/tmp"   # 验证：生效规则（合并所有来源）
systemd-tmpfiles --tldr | head                             # 验证：只看规则正文，不看注释
```

本机实测：

```text
$ ls -1 /usr/lib/tmpfiles.d/ | wc -l
31
$ ls -1 /etc/tmpfiles.d/ | wc -l
1
$ ls -1 /run/tmpfiles.d/ | wc -l
1
$ ls -d /usr/local/lib/tmpfiles.d
ls: cannot access '/usr/local/lib/tmpfiles.d': No such file or directory
$ systemd-tmpfiles --cat-config | grep -cE '^# /(usr/lib|etc|run)/tmpfiles\.d/'
32
$ ls -la /etc/tmpfiles.d/
-rw-r--r-- 1 root root 119 Sep  9 06:44 screen-cleanup.conf      # 整机只有这一个
$ ls -la /run/tmpfiles.d/
-rw-r--r-- 1 root root 507 Sep 19 07:08 static-nodes.conf        # 每次开机由 generator 生成
$ grep -vE "^\s*(#|$)" /usr/lib/tmpfiles.d/tmp.conf
D /tmp 1777 root root 30d
$ systemctl list-timers systemd-tmpfiles-clean.timer --no-pager
NEXT                        LEFT LAST                         PASSED  UNIT                         ACTIVATES
Sun 2026-09-20 07:23:36 UTC  23h Sat 2026-09-19 07:23:36 UTC 46min ago systemd-tmpfiles-clean.timer systemd-tmpfiles-clean.service
```

**`screen-cleanup.conf` 是「同名覆盖」的现成例子**：`/usr/lib/tmpfiles.d/screen-cleanup.conf`（29 字节）与 `/etc/tmpfiles.d/screen-cleanup.conf`（119 字节）同时存在，`--cat-config` 只列 `/etc` 那一份，`--tldr` 里生效的也是它的 `d /run/screen 1777 root utmp`。所以数「有多少条规则」时，**数目录里的文件会多算一个**——要数生效来源就数 `--cat-config` 里的路径行。

**注意时间语义**：`systemd-tmpfiles-clean.timer` 用的不是 `OnCalendar=`，而是相对式：

```text
$ systemctl cat systemd-tmpfiles-clean.timer
[Timer]
OnBootSec=15min
OnUnitActiveSec=1d
AccuracyUSec=1min
Persistent=no
```

即「开机 15 分钟后跑第一次，之后每 24 小时跑一次」——所以 `list-timers` 里的 `NEXT` 是**相对上次触发的 24 小时**，不是每天固定时刻。这也解释了为什么不同机器上这个时间各不相同。

`--cat-config` 里还有一批容易忽略的 `/tmp` 相关规则（都是别的软件包装的）：

```text
D! /tmp/snap-private-tmp 0700 root root -
X /tmp/snap-private-tmp
X /tmp/systemd-private-%b-*/tmp
x /var/tmp/systemd-private-%b-*
```

`D!` 的 `!` 表示「只在开机时处理」，`X`/`x` 是**排除**（`X` 排除整棵子树）——这几条正是为了**不让清理任务把 snap 与 `PrivateTmp` 的私有目录清掉**。看到它们就明白：`PrivateTmp` 的目录（`/tmp/systemd-private-<boot-id>-<unit>-XXXXXX/`）是「被显式保护」的。

## 2. age 的判据：为什么老文件没被删

`tmpfiles.d(5)` 的规则是：**年龄由 mtime、atime、ctime 共同决定，默认 `age-by=abcmABM`——只要其中任一时间戳比「当前时间 - age」更新，就不会清理**（目录默认忽略 ctime，避免清理动作自己刷新 ctime）。

实测（**系统级**，用自建规则 `/etc/tmpfiles.d/lab08b.conf`）：

```text
$ printf "%s\n" "d /tmp/08b-tmpfiles 0755 root root 30d" > /etc/tmpfiles.d/lab08b.conf
$ systemd-tmpfiles --create /etc/tmpfiles.d/lab08b.conf
$ ls -ld /tmp/08b-tmpfiles
drwxr-xr-x 2 root root 4096 Sep 19 08:09 /tmp/08b-tmpfiles
$ : > /tmp/08b-tmpfiles/old-default; touch -d "40 days ago" /tmp/08b-tmpfiles/old-default
$ stat -c "%n mtime=%y ctime=%z" /tmp/08b-tmpfiles/old-default
/tmp/08b-tmpfiles/old-default mtime=2026-08-10 08:09:59.643706507 +0000 ctime=2026-09-19 08:09:59.642758010 +0000
$ systemd-tmpfiles --clean /etc/tmpfiles.d/lab08b.conf
$ ls -A /tmp/08b-tmpfiles
old-default                       # mtime 是 40 天前，但 ctime 是「现在」→ 不删
```

改成只看 mtime（`age-by` 前缀 `m:`）后，同一个文件立刻被删：

```text
$ printf "%s\n" "d /tmp/08b-tmpfiles 0755 root root m:30d" > /etc/tmpfiles.d/lab08b.conf
$ : > /tmp/08b-tmpfiles/old-mtime; touch -d "40 days ago" /tmp/08b-tmpfiles/old-mtime
$ stat -c "%n mtime=%y ctime=%z" /tmp/08b-tmpfiles/old-mtime
/tmp/08b-tmpfiles/old-mtime mtime=2026-08-10 08:09:59.650699068 +0000 ctime=2026-09-19 08:09:59.649758010 +0000
$ systemd-tmpfiles --clean /etc/tmpfiles.d/lab08b.conf
$ ls -A /tmp/08b-tmpfiles
（空）                             # 删了
```

**`touch`、复制、改名以及任何写入都会刷新 ctime**——所以「用 `touch -d` 造一个老文件来测试清理」是最容易骗过自己的实验；真实场景里，一个刚被复制过来的旧文件也不会被清理。要精确控制判据用 `age-by` 前缀，如 `m:30d`（只看 mtime）、`c:7d`（只看 ctime）。

收尾用 `--remove` 处理规则里标记可删的条目，再删掉规则文件本身：

```text
$ systemd-tmpfiles --remove /etc/tmpfiles.d/lab08b.conf
$ ls -ld /tmp/08b-tmpfiles
ls: cannot access '/tmp/08b-tmpfiles': No such file or directory
```

> [!important] `systemd-tmpfiles` **在 systemd 255 上没有 `--dry-run`**
> 本机实测 `systemd-tmpfiles --dry-run --clean` 直接报 `systemd-tmpfiles: unrecognized option '--dry-run'`。`--help` 给出的可用选项是 `--cat-config`、`--tldr`、`--create`、`--clean`、`--remove`、`--boot`、`--graceful`、`--prefix=`、`--exclude-prefix=`、`-E`、`--root=`、`--image=`、`--replace=`。
> 所以「先干跑再真删」这一步要用别的方式替代：① 用 `--exclude-prefix=` 把不想动的路径排除；② 先用 `--prefix=` 只对自己关心的前缀生效；③ 把规则限制在自建目录上（本实验的做法）；④ 用 `systemd-tmpfiles --cat-config` 逐条读懂判据。**不要指望 `--dry-run`。**

> [!important] `age-by` 前缀的字母含义
> `a`=atime、`b`=birth time、`c`=ctime、`m`=mtime，大写表示「目录条目」的对应时间。前缀写 `m:30d` 就是「只用 mtime 判断」。**不确定时用 `--clean` 的对照实验验证（或 `--prefix=` 把范围缩到自建目录），再看结果**——systemd 255 没有 `--dry-run`。

## 3. `/tmp` 文件消失的原因

本机（Ubuntu 24.04.5 虚拟机）按可能性排序：

1. **`systemd-tmpfiles-clean.timer`**：本机规则是 `D /tmp 1777 root root 30d`，`OnBootSec=15min` + `OnUnitActiveSec=1d`——超龄即删。**这是本机唯一确定会清空 `/tmp` 的机制。**
2. **`PrivateTmp=yes`**：服务自己的 `/tmp` 是私有的 bind mount（本机实测路径 `/tmp/systemd-private-<boot-id>-<unit>-XXXXXX/tmp`，inode 与宿主不同），服务停止时消失（子笔记 08）。
3. **应用自己清理**：有些软件启动时清理自己的临时目录。
4. **重启清空**：**只在 `/tmp` 是 tmpfs 时成立**。本机 `findmnt -T /tmp` 显示 `/tmp` 落在根文件系统 `/dev/mapper/ubuntu--vg-ubuntu--lv`（ext4）上，`/var/tmp` 同样，**只有 `/run`、`/run/lock` 是 tmpfs**。所以「重启 `/tmp` 就干净了」这条结论**不能从本机迁移出去**，必须先在目标机上跑一次 `findmnt -T /tmp`。

| 场景 | 服务看到的 `/tmp` | 宿主/其他服务能看到吗 |
| --- | --- | --- |
| 普通服务 | 宿主 `/tmp` | 能 |
| `PrivateTmp=yes` | `/tmp/systemd-private-<boot-id>-<unit>-XXXXXX/tmp`（与宿主不同 inode） | 不能（除非进命名空间） |
| 容器（Docker/K8s） | 容器自己的 `/tmp` | 不能 |

本机实测 `PrivateTmp=yes` 的服务看到的挂载：

```text
$ systemctl show lab08b-ptmp.service -p PrivateTmp
PrivateTmp=yes
$ journalctl -u lab08b-ptmp.service -b -o cat | grep " /tmp "
485 430 252:0 /tmp/systemd-private-decad510b934454f9d61aef2aa2893fd-lab08b-ptmp.service-JcKCGz/tmp /tmp rw,relatime shared:343 master:1 - ext4 …
$ stat -c "service /tmp inode=%i dev=%d" → inode=1311047 dev=64512
$ stat -c "host    /tmp inode=%i dev=%d" → inode=1179649 dev=64512
```

两点值得记住：① 目录名里带 **boot-id 与服务名**，所以「哪个服务的私有 `/tmp`」一眼可辨；② inode 不同但 **`dev` 相同**（都在根 ext4 上）——它是一次 `mount --bind` 出来的独立目录，**不是 tmpfs**，所以「服务停了文件就没了」成立，但「私有 `/tmp` 是内存盘」这个说法在本机不成立。

```bash
systemctl show <unit> -p PrivateTmp               # 验证：这个服务是不是私有 /tmp
stat -c "%n mtime=%y ctime=%z" /tmp/somefile      # 验证：这个文件到底「多老」
systemd-tmpfiles --cat-config | grep -E "^[a-zA-Z].*/tmp"   # 验证：本机对 /tmp 的规则
findmnt -T /tmp -o TARGET,SOURCE,FSTYPE           # 验证：/tmp 到底是哪个文件系统
```

## 4. 服务的数据该放哪

这是「临时文件治理」对运维最实际的一条建议：

| 数据性质 | system 单元放哪 | user 单元放哪 | 用哪个选项让 systemd 建 |
| --- | --- | --- | --- |
| 跨重启必须保留（状态、数据库文件、队列） | `/var/lib/<app>` | `~/.local/state/<app>` | `StateDirectory=app` |
| 运行期共享、重启可丢（socket、pid、锁） | `/run/<app>` | `$XDG_RUNTIME_DIR/<app>` | `RuntimeDirectory=app` |
| 日志 | `/var/log/<app>` | `~/.local/state/log/<app>` | `LogsDirectory=app` |
| 可重建的缓存 | `/var/cache/<app>` | `~/.cache/<app>` | `CacheDirectory=app` |
| 纯临时、可随时丢 | `/tmp`（或服务私有 `/tmp`） | 同左 | 无需声明 |

两列都要看：`StateDirectory=`/`LogsDirectory=` 的落点由 **unit 类型**决定（`systemd.exec(5)` 的 Table 2）——system 单元走 `/var/lib`、`/var/log`，user 单元走 `~/.local/state` 那一路，不要照着 system 路径去找用户单元的文件。

```ini
[Service]
RuntimeDirectory=myapp        # system 单元：/run/myapp；user 单元：$XDG_RUNTIME_DIR/myapp（属主设为 User=，停止后可清理）
StateDirectory=myapp          # system 单元：/var/lib/myapp；user 单元：~/.local/state/myapp
LogsDirectory=myapp           # system 单元：/var/log/myapp；user 单元：~/.local/state/log/myapp
CacheDirectory=myapp          # system 单元：/var/cache/myapp；user 单元：~/.cache/myapp
ProtectSystem=strict
ReadWritePaths=/var/lib/myapp /var/log/myapp /run/myapp /var/cache/myapp
```

本机**系统级**实测（`lab08b-dirs.service` 里一次声明四个目录）：

```text
$ systemctl show lab08b-dirs.service -p RuntimeDirectory -p StateDirectory -p LogsDirectory -p CacheDirectory
RuntimeDirectory=lab08b
StateDirectory=lab08b
CacheDirectory=lab08b
LogsDirectory=lab08b
$ systemctl start lab08b-dirs.service
$ ls -ld /run/lab08b /var/lib/lab08b /var/log/lab08b /var/cache/lab08b
drwxr-xr-x 2 root root   40 Sep 19 08:09 /run/lab08b
drwxr-xr-x 2 root root 4096 Sep 19 08:09 /var/cache/lab08b
drwxr-xr-x 2 root root 4096 Sep 19 08:09 /var/lib/lab08b
drwxr-xr-x 2 root root 4096 Sep 19 08:09 /var/log/lab08b
$ systemctl stop lab08b-dirs.service; systemctl clean --what=all lab08b-dirs.service
$ ls -ld /run/lab08b /var/lib/lab08b /var/log/lab08b /var/cache/lab08b
ls: cannot access '/run/lab08b': No such file or directory
ls: cannot access '/var/lib/lab08b': No such file or directory
ls: cannot access '/var/log/lab08b': No such file or directory
ls: cannot access '/var/cache/lab08b': No such file or directory
```

**这套「让 systemd 建、也让 systemd 收」的闭环是它的最大价值**：手工 `mkdir` + `chown` 建出来的目录，停机时没人负责回收；`systemctl clean --what=all` 能一次性把 `RuntimeDirectory`/`StateDirectory`/`LogsDirectory`/`CacheDirectory` 全部清掉（`--what=` 还可细分，如只有 `runtime` 或只有 `state`）。

```bash
systemctl show myapp.service -p RuntimeDirectory -p StateDirectory -p LogsDirectory -p CacheDirectory
ls -ld /run/myapp /var/lib/myapp /var/log/myapp /var/cache/myapp   # system 单元；user 单元改为 $XDG_RUNTIME_DIR/myapp ~/.local/state/myapp
systemctl clean --what=all myapp.service    # 验证：目录被回收（先确认里面没有要留的数据）
```

> [!warning] 不要把跨重启的数据放在 `/tmp` 或 `/run`
> `/tmp` 会被 tmpfiles 清理、可能被 `PrivateTmp` 隔离；`/run` 是 tmpfs，重启即失。**这两处只适合「丢了能重建」的数据**。需要持久化就用 `StateDirectory=`，需要跨进程但不持久就用 `RuntimeDirectory=`。

## 5. 常用命令

| 命令 | 作用 | 风险 |
| --- | --- | --- |
| `systemd-tmpfiles --cat-config` | 列出生效规则（含所有来源） | 只读 |
| `systemd-tmpfiles --tldr` | 只看规则正文，不打印注释（替代干跑的第一步） | 只读 |
| `systemd-tmpfiles --create` | 按规则创建缺失的文件/目录 | 会建目录、设权限 |
| `systemd-tmpfiles --clean` | 按 age 清理 | **会删文件** |
| `systemd-tmpfiles --remove` | 删除规则里标记为可删的条目 | **会删文件** |
| `systemd-tmpfiles --prefix=PATH` / `--exclude-prefix=PATH` | 把动作限制/排除在某前缀内（代替干跑） | 缩小影响面 |
| `systemctl clean --what=all <unit>` | 回收 unit 的 runtime/state/logs/cache 目录 | **会删数据** |
| `systemctl list-timers systemd-tmpfiles-clean.timer` | 清理任务的调度 | 只读 |

**systemd 255 没有 `--dry-run`**（本机实测报 `unrecognized option`），所以「先确认要删什么」要靠读规则与缩小范围：

```bash
systemd-tmpfiles --tldr | grep -E "^[a-zA-Z].*/tmp"     # 验证：只看与 /tmp 有关的规则正文
systemd-tmpfiles --cat-config | grep -n "lab08b"        # 验证：确认你自己的规则确实在生效集合里
systemd-tmpfiles --clean --prefix=/tmp/08b-tmpfiles     # 验证：只用前缀限定自己的目录，影响面可控
```

先干跑，确认要删什么（本机没有 `--dry-run`，改用「读规则 + 限定前缀」）：

systemd-tmpfiles --tldr | grep -n "lab08b"              # 验证：自己的规则已在生效集合里

### 实验 10：tmpfiles 的 age 语义与目录托管

> [!example]- 实验 10：制造一个「40 天前的老文件」，看它为什么没被清
> **怎么做**：在 `/etc/tmpfiles.d/lab08b.conf` 写 `d /tmp/08b-tmpfiles 0755 root root 30d`，用 `systemd-tmpfiles --create /etc/tmpfiles.d/lab08b.conf` 建目录；`touch -d "40 days ago"` 造一个文件，用 `stat -c "%n mtime=%y ctime=%z"` 看两个时间戳；执行 `systemd-tmpfiles --clean /etc/tmpfiles.d/lab08b.conf` 观察是否被删。再把规则改成 `m:30d` 重跑。最后 `systemd-tmpfiles --remove` + 删规则文件回滚。**再补一段目录托管对照**：建一个系统单元声明 `RuntimeDirectory=`/`StateDirectory=`/`LogsDirectory=`/`CacheDirectory=`，启动后 `ls -ld` 看 systemd 建出来的四个目录，`systemctl clean --what=all` 看它们被整体回收。
> **预期**：默认规则下文件**不**被删（ctime 是「现在」）；改成 `m:30d` 后**被删**；四个目录分别落在 `/run`、`/var/lib`、`/var/log`、`/var/cache`，`clean` 后全部消失。
> **风险**：低（规则只覆盖自建路径 `/tmp/08b-tmpfiles` 与自建 unit）；**耗时**：约 15 分钟；**回滚**：`systemd-tmpfiles --remove`、`rm -f /etc/tmpfiles.d/lab08b.conf`、`rm -rf /tmp/08b-tmpfiles`、停单元 + 删 unit 文件 + `systemctl clean --what=all` + `daemon-reload`。
> 机器：可快照实验机（写 `/etc/tmpfiles.d` 需要 root）。**系统级 `--clean` 不要在生产机上试**——不带 `--prefix=` 时它按系统规则删真正的 `/tmp`、`/run`。`--cat-config`、`--tldr`、`list-timers` 是只读，生产机上也可以做。
> 本机证据：`.labvm/evidence/08b_13_tmpfiles.out.txt`、`08b_13_mounts_dryrun.out.txt`。

## 6. 目录说明符：`%t` / `%T` / `%S` / `%C` / `%L`

unit 文件里可以用说明符（specifier）引用上面那张表的目录，**不用把路径写死**：

| 说明符 | 含义 | system 实例解析为 | user 实例解析为 |
| --- | --- | --- | --- |
| `%t` | 运行时目录根 | `/run` | `$XDG_RUNTIME_DIR` |
| `%T` | 临时目录 | `/tmp` | `/tmp` |
| `%S` | 状态目录根 | `/var/lib` | `$XDG_STATE_HOME` |
| `%C` | 缓存目录根 | `/var/cache` | `$XDG_CACHE_HOME` |
| `%L` | 日志目录根 | `/var/log` | `$XDG_STATE_HOME/log` |
| `%E` | 配置目录根 | `/etc` | `$XDG_CONFIG_HOME` |
| `%h` | 用户 home | `/root` | `/home/<user>` |

本机系统级实测：

```text
$ systemctl show lab08b-specdirs.service -p ExecStart   # ExecStart 里写 "t=[%t] T=[%T] S=[%S] C=[%C] L=[%L]"
$ journalctl -u lab08b-specdirs.service -b -o cat | grep "t=\["
t=[/run] T=[/tmp] S=[/var/lib] C=[/var/cache] L=[/var/log]
```

> [!warning] 说明符是**无条件**展开的，脚本里的 `%` 会被吃掉
> 本机踩过两次，都是「命令行能跑、写进 unit 就变成垃圾」：
> ```text
> $ systemctl show lab08b-pct.service -p ExecStart
> ExecStart={ path=/bin/bash ; argv[]=/bin/bash -c echo "BAD=[$(date +/tmp.lab08b-pct)]" ; … }
> $ journalctl -u lab08b-pct.service -b -o cat | grep -E "BAD|GOOD"
> BAD=[/tmp.lab08b-pct]
> GOOD=[08:07:49.202153541]
> ```
> `date +%T.%N` → `date +/tmp.<去掉 .service 的单元名>`（`%T`=临时目录、`%N`=单元名去后缀），而写成 `date +%%T.%%N` 才是对的（`%%` → 字面 `%`）。同类受害者还有 `date +%s`（`%s` = 用户 shell，实测变成 `date +/usr/bin/bash`）和 `stat -c "%i dev=%d"`（`%i`=实例名、`%d`=credentials 目录）。
> **`systemd-analyze verify` 对这两种情况都返回 0**（本机实测），所以它既不会报错也不会警告——**只能靠「输出对不对」验收，不能靠「verify 过没过」验收**。要用 `%` 就写 `%%`；要在 unit 里跑脚本，最稳的做法是把脚本落到一个文件里再 `ExecStart=/bin/bash /path/to/script.sh`（本机第 2 节的三种停止现场就是这么写的）。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 「`/tmp` 里的文件应该是永久的」 | 它按 age 清理（本机 `/usr/lib/tmpfiles.d/tmp.conf` 是 30 天），还可能被 `PrivateTmp` 隔离；跨重启数据不能放这 |
| 「重启就会清空 `/tmp`」 | **本机 `/tmp` 不是 tmpfs**（`findmnt -T /tmp` 落在根 ext4 上），重启不清空；真正清它的是 `systemd-tmpfiles-clean.timer`。`/run` 才是 tmpfs |
| 「`touch -d` 造的老文件会被清理」 | `touch` 刷新了 ctime，默认 `age-by` 看 ctime，所以不删；要测判据得用 `m:` 前缀（本机实测 `m:30d` 立刻删） |
| 「清理没生效」 | 先用 `stat` 看 mtime/ctime/atime，再对照 `--cat-config` 的规则；判据可能不是你想的那个 |
| 用 `systemd-tmpfiles --dry-run` 干跑 | systemd 255 没有这个选项（实测 `unrecognized option '--dry-run'`）；用 `--tldr` 读规则、`--prefix=`/`--exclude-prefix=` 缩小范围 |
| 把 tmpfiles 规则理解成「定时器」 | 规则只是「怎么维护」，真正定时执行的是 `systemd-tmpfiles-clean.timer`（本机是 `OnBootSec=15min` + `OnUnitActiveSec=1d`，**不是每天固定时刻**） |
| 在服务里往 `/run/<app>` 写持久数据 | `/run` 是 tmpfs，重启即失；持久数据用 `StateDirectory=` |
| 手写 `mkdir` + `chown` 建服务目录 | 容易和 `ProtectSystem=strict` 打架，且停机后没人回收；用 `RuntimeDirectory=`/`StateDirectory=` 让 systemd 建、用 `systemctl clean` 收 |
| 直接删 `/tmp` 的清理规则「以防万一」 | 那是把整机的临时文件治理一起关掉，`/tmp` 会越积越多 |
| 在 `/tmp` 放跨进程共享的锁文件且服务开了 `PrivateTmp` | 别的进程看不到那个文件（本机实测服务内 inode 1311047 vs 宿主 1179649），IPC/锁直接失效 |
| 在 `ExecStart=` 里写 `date +%T`、`stat -c %d` | `%` 被 systemd 当说明符展开，命令静默出错，而 `systemd-analyze verify` **退出码仍是 0** |

## 决策练习

> [!question]- 场景：一个自研服务把「待处理的队列文件」写在 `/tmp/myapp/` 里，最近发现队列文件偶尔整批消失，重启后就正常。你要定位。
> A. 认为是应用 bug，让开发加日志
> B. 先看 `systemd-tmpfiles --cat-config | grep -E "^[a-zA-Z].*/tmp"` 与 `systemctl show <unit> -p PrivateTmp`，确认是定时清理还是私有 `/tmp`；再把队列改到 `StateDirectory=` 对应的持久目录
> C. 把 `/usr/lib/tmpfiles.d/tmp.conf` 里的 `D /tmp` 规则删掉
> **答案：B。**
> A 可能拖很久，也可能不是应用逻辑问题。
> C 把整机 `/tmp` 治理关掉，风险外溢到所有服务。
> B 是正解：**先确定「谁在清」，再把数据放到与生命周期匹配的位置**。注意本机 `/tmp` 不是 tmpfs，所以「重启后就正常」这条线索在这台机器上指向的是**清理 timer 或 PrivateTmp**，而不是「重启清空」。

## 要点自测

> [!question]- `/tmp` 里的文件是谁在清、什么时候清？
> - `systemd-tmpfiles-clean.timer` 驱动，本机 `OnBootSec=15min` + `OnUnitActiveSec=1d`（相对式，不是固定时刻），按 `/usr/lib/tmpfiles.d/tmp.conf` 的 `D /tmp 1777 root root 30d` 删除超龄条目。
> - 此外 `PrivateTmp`（服务私有 `/tmp`，停止即消失）与应用自清理也会让文件消失。
> - **本机 `/tmp` 不是 tmpfs**（`findmnt -T /tmp` → 根 ext4），所以「重启清空」在这台机器上不成立；不要照抄成通用结论。
> - 验证：`systemctl list-timers systemd-tmpfiles-clean.timer`、`systemd-tmpfiles --cat-config | grep -E "^[a-zA-Z].*/tmp"`、`findmnt -T /tmp`。
> - **第一反应不要是什么**：不要为了「保险」把 `/tmp` 规则删掉——那是把整机治理关掉。

> [!question]- `systemd-tmpfiles --clean` 为什么有时不删「很久没改」的文件？
> - 默认年龄判据是 mtime/atime/ctime 一起看：**任一时间戳较新就不清理**。
> - `touch`、复制、改名都会刷新 ctime，所以刚被「造旧」或刚被复制过来的文件会被保护（本机实测 40 天前的 mtime 也没删）。
> - 要精确控制就用 `age-by` 前缀，例如 `m:30d` 只看 mtime、`c:7d` 只看 ctime。
> - **第一反应不要是什么**：不要一看到「没删」就说清理没生效——先 `stat -c "%y %z"` 看三个时间戳，也别指望 `--dry-run`（这个版本没有）。

> [!question]- 服务的数据应该放 `/tmp`、`/run` 还是 `/var/lib`？
> - 跨重启必须保留 → system 单元 `/var/lib/<app>`、user 单元 `~/.local/state/<app>`（都是 `StateDirectory=`）。
> - 运行期共享、重启可丢 → system 单元 `/run/<app>`、user 单元 `$XDG_RUNTIME_DIR/<app>`（都是 `RuntimeDirectory=`）。
> - 纯临时、可随时丢 → `/tmp`（注意 age 清理与 `PrivateTmp`）。
> - 让 systemd 建目录比手写 `mkdir` 更可靠，且能和 `ProtectSystem=strict` 配合；本机实测四个目录都会被自动创建，`systemctl clean --what=all` 能一次性全部回收。
> - 在 unit 里引用这些目录用说明符：`%t`/`%T`/`%S`/`%C`/`%L`；但要记住 `%` 会被无条件展开，脚本里的 `date +%T` 之类必须写成 `%%T`。
> - **第一反应不要是什么**：不要把「图省事」写在 `/tmp` 当成能长久的方案；也不要因为「反正重启就没了」而依赖重启来清理——本机 `/tmp` 根本不是 tmpfs。

> [!question]- 为什么在本机上「非 root 也能做隔离类实验」这个前提不成立？
> - 本机 `kernel.apparmor_restrict_unprivileged_userns=1`（Ubuntu 24.04 默认），**非 root（`realtyz`, uid=1000）创建 user namespace 会被拒绝**（`unshare: write failed /proc/self/uid_map: Operation not permitted`），root 执行 `unshare -n` 才正常。
> - 这直接决定了两件事：`PrivateTmp`/`ProtectSystem` 这类沙箱项**要用系统单元测**；用户级 systemd 实验在真虚拟机上依然是「用户级」，不能替代系统级结论。
> - 判据：`sysctl kernel.apparmor_restrict_unprivileged_userns` 与 `unshare -n true` 的退出码，而不是「文档说可以」。
> - **第一反应不要是什么**：不要把 `Operation not permitted` 当成环境故障去重试——先确认自己是哪个 uid、这条 sysctl 是多少。
