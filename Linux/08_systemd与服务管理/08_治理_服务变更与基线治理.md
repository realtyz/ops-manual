# 服务变更与基线治理

## 1. 没有制度时会怎样

systemd 把「资源上限、日志归集、重启策略、优雅停止、开机自启」都变成 unit 文件里的声明式配置。这带来一个副作用：**服务的行为不再散落在启动脚本里，而是集中在几份被间接引用的文件中**。没有制度时，集中反而放大了漂移：

1. **配置漂移**：有人在 `/etc/systemd/system/` 下直接改，有人在 drop-in 里改，`show` 出来的值与手上那份文件对不上，没人说得清「当前生效的是什么」。
2. **静默忽略**：键名拼错、写错小节——`verify` 只打印一行 `ignoring` 且退出码为 0，改了没生效却没人发现。
3. **无界服务**：新服务上线不带任何上限，一个服务把整机拖垮；出事时才发现 `MemoryMax` 是 `infinity`。
4. **无归属的任务**：某个 `/etc/cron.d/` 文件没人认领，失败没人知道；某个 timer 的补跑时间戳没人管，导致任务莫名跑两次。
5. **证据易失**：`restart`/`reset-failed` 覆盖现场，cgroup 目录随单元结束被回收，未持久化的日志随重启消失——不做基线，复盘时没有任何可比对的旧值。

这五条的共同点：**它们都不是知识问题，而是产物缺失**。有基线卡就能回答「之前是什么」，有变更记录就能回答「谁改的、怎么回滚」，有台账就能回答「谁负责」。

## 2. 行业通行做法

不同组织的规范差别很大，但方向一致：

- **配置进版本控制**：unit 与 drop-in 是文件，就应当像代码一样评审、入库、留历史。`/usr/lib/systemd/system/` 下的发行版文件不改，本地差异一律落在 `/etc`。
- **变更分级与影响面评估**：`daemon-reload` 是低影响（不重启进程），`restart` 有中断窗口，`mask`/`isolate`/`set-default` 影响开机路径。级别不同，审批与窗口不同。
- **变更前后各留一次基线**：改之前导出 `systemctl cat` 与 `show -p ...`，改之后用同一条命令复测，差值即变更效果。
- **默认有界**：新服务上线就带资源上限与重启策略，而不是等出事再补。这一点与 cgroup 内存治理的思路一致：**上限首先是可用性手段**。
- **先取证再动手**：`restart` 是动作不是信息；止血与修复分开记录，避免「现象消失」被当成「问题解决」。
- **定时任务必须有归属与幂等**：每个 `cron`/`timer` 写清用途、负责人、加锁方式与失败处理；不检查返回值的定时任务是隐性故障源。

这些方向的原始材料可以在 Google SRE 系列（变更管理与事后复盘）、ITIL/ITSM 的变更与配置管理实践、以及各发行版的 systemd 官方文档里找到，可按自己的环境取舍。

## 3. 治理产物四件套

### 3.1 服务与定时任务基线卡

**用途**：回答「这台机器当前是什么状态」，给变更与复盘提供可比对的旧值。

**字段**（每一项都要写清取值来源命令与采样时刻）：

| 分组 | 字段 |
| --- | --- |
| 环境标识 | 主机名、发行版与版本、`systemctl --version`、内核版本、cgroup 版本、采集时刻 |
| 整体状态 | `systemctl is-system-running`、`systemctl --failed` 输出、运行中的 service 数量 |
| 关键单元 | 每个核心单元的 `ActiveState`/`SubState`/`UnitFileState`、`FragmentPath`、`DropInPaths` |
| 上限与策略 | `MemoryMax`/`MemoryHigh`/`CPUQuotaPerSecUSec`/`TasksMax`/`LimitNOFILE`/`LimitNOFILESoft`/`Restart`/`RestartUSec`/`KillMode`/`TimeoutStopUSec`/`OOMPolicy` |
| 沙箱 | `ProtectSystem`/`ProtectHome`/`PrivateTmp`/`ReadWritePaths`/`User`/`Group`/`NoNewPrivileges`/`CapabilityBoundingSet` |
| 自启 | `is-enabled`、`default.target`、`list-dependencies <target>` 里的关键项 |
| 定时任务 | `list-timers --all` 的关键列（`NEXT`/`LAST`/`UNIT`/`ACTIVATES`）、`crontab -l`、`/etc/cron.d/` 清单 |
| 临时文件 | `systemd-tmpfiles --cat-config` 里与 `/tmp`、`/run` 相关的规则、`systemd-tmpfiles-clean.timer` 的节奏、`findmnt -T /tmp` 的结果 |
| 日志 | `journalctl --disk-usage`、`--list-boots`、`ls -ld /var/log/journal`、`cat-config systemd/journald.conf` 的容量与限流项 |
| 时间 | `timedatectl` 的时区与同步状态、`timesync-status` 的 `Server`/`Offset`；NTP 客户端是哪一个 |
| 开机 | `systemd-analyze time` 的分段、`blame` 前若干名、`critical-chain` 的末梢 |

**判据**：基线卡不是一次性文档，而是**同一口径的重复采样**。任何「变了没有」的判断都来自两次同口径采样的差值；不同口径之间（例如 manager 给出的属性值与内核接口文件里的值、命令输出与配置文件的内容）不能直接比较。

### 3.2 上线变更单

**用途**：把「改配置」变成可评审、可回滚、可复测的动作。

**固定顺序**（每一步都有验收判据，缺一步就不算走完）：

1. 运行 `systemd-analyze verify <文件>`，并**读它的输出**，因为干净的单元应当完全沉默；
2. 执行 `daemon-reload`；
3. 读 `systemctl show -p <属性>` 核对**生效值**，而不是去看文件；
4. 执行 `systemctl start` 或 `restart`，具体用哪一个由「这项配置是不是启动期读取」决定；
5. 做业务验证（端口、日志、健康检查、指标），因为**`start` 返回 0 不是验收**；
6. 最后执行 `enable`；因为 `enable` 不启动服务，所以它不能替代前几步。

**字段**：变更单编号与日期、目标单元与生效文件路径、现值与目标值（逐项写明）、依据（基线卡数据或压测结论）、影响面（是否有中断窗口、涉及几个副本、是否影响启动路径）、验证方式（改完读哪个字段、读到什么算成功）、回滚命令、观察窗口与观察项、执行人与复核人。

### 3.3 故障处置记录

**用途**：把一次排障变成可复用的判断，而不是一段口头结论。

**字段**：现象（含机器规格、时间线、可观测数值）、**这次失败卡在哪个阶段**（装载、编队、判定、约束与隔离、留痕、退场与常驻这七段中的哪一段）、三条证据（每条写清出自哪条命令、哪个字段、来自系统级还是用户级 manager）、根因、**止血动作**与**修复动作**（分开写）、回滚方式、下一步与观察窗口。

**判据**：「止血」是让现象消失，「修复」是让根因不再成立。二者混在一栏，复盘时无法判断问题是否真的解决。

### 3.4 巡检项与台账

**用途**：把「出事后才补」变成「定期发现」。

巡检项（都是只读动作，因此生产机上也可以做）：

- 读 `systemctl --failed`，若它列出了条目，就逐条记录；再读 `is-system-running`，若它返回 `degraded`，就说明已经有单元处于失败状态。
- 逐个读关键单元的 `MemoryMax`，若它仍是 `infinity`，就说明这个服务还没有上限；再用 `memory.current` 与 `memory.max` 的比值判断有没有服务长期贴着上限。
- 读 `memory.events` 并取 `oom_kill` 的差值，因为**这是「服务没挂但少了几个 worker」的唯一线索**。
- 读 `NRestarts` 与 `StartLimitBurst`，若 `NRestarts` 已经停在 `StartLimitBurst` 而 `Result` 不是 `success`，就说明这个单元已经落入启动节流。
- 读 `journalctl --disk-usage` 并与基线对比变化，再读 `--list-boots` 确认历史启动是否还有足够的条数。
- 读 `list-timers --all`，若某个应当定期跑的 timer 的 `NEXT` 为空，就要查它为什么不再触发；同时确认有没有 timer 的补跑时间戳残留。
- 逐个读 `/etc/cron.d/` 与 `/etc/crontab` 里的任务，确认每个任务的用途与负责人都已登记。
- 分别读 `timedatectl` 的两行，确认客户端在运行且时间已经同步；再确认这台机器上是否存在两个 NTP 客户端。
- 读 `is-enabled` 并与 `[Install]` 对照，确认没有出现「以为自启了但其实是 `static`」的单元。
- 列出被 `mask` 的单元，并确认它的触发器（`.socket`/`.path`/`.timer`）是否仍然活跃。

**台账字段**：单元名与类型、用途、负责人、自启方式（`WantedBy=` 或触发器）、关键上限、重启策略、日志落点、变更历史摘要、最近一次复核时间。

## 4. 关键字段的治理用法

字段本身的读写与单位在实操篇与原理篇；这里讲**怎么用它们做决定**。

| 字段 | 治理时怎么用 |
| --- | --- |
| `FragmentPath`/`DropInPaths` | 变更单必须记录这两个值，因为它们是「当前生效配置」的唯一准确描述；若巡检发现它们与上次不一致，就说明有人在本机改过配置 |
| `UnitFileState` 与 `[Install]` | 它们是判断「开机是否拉起」的唯一依据，因此台账要区分 `enabled`、`disabled`、`static`、`masked` 与 `indirect` 这五种安装态 |
| `NRestarts` 与 `StartLimitBurst` | 用它们发现「正在震荡」的服务，早于用户投诉 |
| `Result`/`ExecMainCode`/`ExecMainStatus` | 处置记录里必须写这三个值，否则事后无法把结论复现 |
| `memory.max`/`memory.peak`/`memory.events` | 它们构成上限治理的三项依据：`peak` 用来定上限，而 `events` 用差值判断本次窗口内是否发生过 OOM |
| `OOMPolicy` | 它决定 OOM 之后还能不能取到 cgroup 里的计数字段：缺省 `stop` 会把整个单元停掉并回收 cgroup，因此要复盘就提前把 cgroup 文件采下来，或改用 `continue` |
| `LogRateLimitIntervalUSec`/`LogRateLimitBurst` | 它们**不是**日志安全的保险，因为有效额度会按可用空间放大，而且丢弃时不一定留下告警；因此治理要落在容量上限与分流上 |
| `cat-config systemd/journald.conf` | 它用来判断容量与转发策略真正来自哪个文件，因此在改 `/etc/systemd/journald.conf` 之前要先确认它有没有被 drop-in 覆盖 |
| `systemd-tmpfiles --cat-config` | 它用来判断 `/tmp` 的清理语义到底由哪条规则决定；**数规则时要数生效来源，而不是数文件** |
| `timedatectl` 的两行 | 这两行是变更窗口与复盘时间线可信度的前提，因此未同步时不要用跨机时间对账 |

## 5. 治理场景与产出

### 场景一：新服务上线

**背景**：一个自研服务要上线，运维只在服务器上 `nohup` 起过一次，准备"照原来的样子再起一份"。

**做法**：把它写成 unit，按固定顺序走一遍；四项配置**逐项加、逐项验**：依赖与顺序要把 `Wants=` 与 `After=` 成对写；`Type=` 对长跑服务优先取 `exec` 或 `notify`；资源上限先给初值，上线后按真实峰值复核；重启策略用 `on-failure` 配一个合理的 `RestartSec=`。沙箱先只加低风险的项（`NoNewPrivileges=yes`、`CapabilityBoundingSet=`），把 `ProtectSystem=strict` 这类需要配合 `ReadWritePaths=` 的项留到有验证手段时再加。

**产出**：一个可上线的 unit 与一份上线变更单（含回滚命令与业务验证方式）。

### 场景二：用 drop-in 做一次小改动

**背景**：某个服务需要从 `Restart=no` 改成 `on-failure`，并加一条 `Environment=`。

**做法**：不改发行版原文件，用 `systemctl edit` 写 drop-in；文件名带序号；一次只改一项；改完按固定顺序走一遍：先执行 `verify` 并读它的输出，再执行 `daemon-reload`，然后用 `show` 核对生效值，接着 `restart`，最后做业务验证。改动前先导出 `systemctl cat` 与关键 `show` 值作为对照。

**产出**：变更记录与 drop-in 内容留档（回滚就是删掉文件再执行 `daemon-reload`）。

### 场景三：巡检发现一批服务没有上限

**背景**：巡检 40 个服务，`MemoryMax` 显示 `infinity`；不可能一次全改。

**做法**：按「峰值内存 × 影响面」排序推进，先做核心业务与内存大户；每个服务先补一次只读基线（`memory.current`/`memory.peak`/`memory.events` 与业务峰值时段），再分批改上限；每批改完留观察窗口。**不要一次性批量改**——同时生效等于把一批未知风险同时引入，出了问题无法归因。

**产出**：排期表（服务、当前峰值、目标上限与依据、影响面、批次、验证方式、观察窗口）与每批的变更记录。

### 场景四：把定时任务与临时文件纳入台账

**背景**：发现若干 `/etc/cron.d/` 文件与 timer 没有负责人，且有人把长生命周期数据放在 `/tmp`。

**做法**：逐个任务记录用途、负责人、加锁方式（`flock`）、失败处理与结果落点；对 `/tmp`，先用 `systemd-tmpfiles --cat-config` 与 `findmnt -T /tmp` 确认清理语义与文件系统类型，再把不该放 `/tmp` 的数据迁到 `StateDirectory=`（跨重启）或 `RuntimeDirectory=`（运行期共享）。**不要删掉 `/tmp` 的清理规则来「保住」那些文件**——那是把整机治理一起关掉。

**产出**：定时任务台账与 `/tmp` 治理说明（谁在清、按什么判据、数据应当放哪里）。

### 场景五：改 `/tmp` 清理规则或迁移服务数据目录

**背景**：有服务把需要跨重启保留的数据写在 `/tmp` 下，运维考虑放宽清理规则。

**做法**：先判断数据的生命周期语义，再选目录选项：若数据需要跨重启保留，就选 `StateDirectory=`；若数据只在运行期共享，就选 `RuntimeDirectory=`；日志与缓存各有对应选项。用目录选项让 systemd 建目录并管理归属，同时把它们加进 `ReadWritePaths=`（在 `ProtectSystem=strict` 下）并核对目录属主与 `User=` 是否匹配。做完记录 `systemctl show -p RuntimeDirectory -p StateDirectory` 给出的实际落点，并确认 `systemctl clean` 的语义（它会删数据，属于破坏性动作）。

**产出**：目录迁移记录（旧路径与新路径、落点属性、属主、可写口、清理方式）。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 直接改 `/usr/lib/systemd/system/` 下的文件 | 升级会覆盖它，而其他机器上没有这处改动，因此本地差异一律走 `/etc` 下的 drop-in |
| 变更单只写「改了什么」不写「怎么验、怎么回滚」 | 出问题时只能凭记忆恢复，因此回滚命令必须是可以直接粘贴的 |
| 用文件内容作为「当前配置」的证据 | 生效配置由 `FragmentPath` 与 drop-in 共同决定，因此要记录这两个字段 |
| 上线流程跳过 `verify` 或只看它的退出码 | 被忽略的键不会改变退出码，因此要读输出，而干净的单元应当沉默 |
| 用 `daemon-reload` 当作配置生效的完成 | 进程侧的启动期配置要 `restart` 才会更新 |
| 用 `start` 返回 0 当验收 | 它只说明 `Type=` 判定通过，因此验收要落在业务可观察事实上 |
| 批量修改同类服务 | 这等于同时引入一批未知风险，出了问题无法归因，因此应分批并留观察窗口 |
| 把 `enable` 放在流程最前面 | `enable` 不启动服务，也不影响当前运行状态，因此它应当最后做 |
| 变更前不采基线 | `restart` 与 `reset-failed` 会覆盖 `Result`/`NRestarts` 与上一进程输出，因此事后没有可比对的旧值 |
| 止血与修复写在同一栏 | 复盘时无法判断根因是否已消除 |
| 把 `reset-failed` 或调大 `StartLimitBurst=` 记为「已修复」 | 前者只清掉计数，后者只是让风暴继续 |
| 把单元级日志限流当保险 | 有效额度会按可用空间放大，而且丢弃时不一定留下告警 |
| 直接 `rm` journal 文件清盘 | 这可能破坏索引，因此要用 `--vacuum-*` 或设容量上限，并要知道前者会删掉历史启动的证据 |
| 删掉 `/tmp` 清理规则来保住文件 | 这会把整机临时文件治理一起关掉，正确做法是迁移数据目录 |
| 把 `/tmp` 当作可以「重启即清空」的目录 | 先用 `findmnt -T /tmp` 确认：不是 tmpfs 时重启并不清空，真正清它的是清理任务 |
| 定时任务不写负责人、不加锁、不看返回值 | 失败没人知道，而且重叠执行会造成数据竞争 |
| `mask` 了服务却没处理触发器 | `.socket`/`.path`/`.timer` 仍会活跃，端口还在听，连接被推给一个起不来的服务 |
| 认为 `disable` 之后服务就不会再被启动 | 它仍可被手动启动、被别的单元 `Wants=` 拉起、被触发器拉起 |

## 要点自测

**问：一份服务基线卡至少要能回答哪几个问题？**
答：这台机器上有哪些关键单元在运行、哪些会开机自启、它们的生效文件与关键上限是什么、有哪些定时任务与临时文件规则、日志容量与时间基线是否可信。判据是「同一口径重复采样时能看出变化」。

**问：上线流程为什么把 `enable` 放在最后？**
答：`enable` 只建自启软链，不启动服务、也不影响当前运行状态。先把配置核对好、服务跑起来并通过业务验证，再让它参与开机，才能保证「失败的改动不会带到下一次重启」。

**问：变更单里为什么必须写 `FragmentPath` 与 `DropInPaths`？**
答：它们是「当前生效配置」的唯一准确描述。只写文件名无法排除被更高优先级文件覆盖或被 drop-in 覆盖的情况。

**问：巡检用什么字段发现「服务没挂但少了几个 worker」？**
答：读 cgroup 的 `memory.events` 里 `oom_kill` 的差值，因为 `OOMPolicy=continue` 时单元仍是 `active (running)`，而 `systemctl status` 看不出异常。

**问：为什么止血与修复要分栏记录？**
答：止血是让现象消失（重启、放宽节流、临时开大上限），修复是让根因不再成立。混在一起会让复盘误判「问题已经解决」。

**问：为什么「把数据从 `/tmp` 搬走」比「放宽 `/tmp` 清理规则」更合适？**
答：放宽或删除清理规则会同时影响整机上所有依赖 `/tmp` 易失语义的组件。数据本身的生命周期应当用 `StateDirectory=`（跨重启）或 `RuntimeDirectory=`（运行期共享）表达，由 systemd 建目录、管归属并可回收。

**第一反应不要做什么**：不要改发行版目录下的 unit 文件；不要用文件内容当生效配置的证据；不要跳过 `verify` 或只看它的退出码；不要用 `daemon-reload` 代替 `restart`；不要用 `start` 返回 0 当验收；不要批量改同类服务；不要在没采基线的情况下做变更；不要把止血记成修复；不要把 `reset-failed` 或调大 `StartLimitBurst=` 当修复；不要直接 `rm` journal 文件；不要删掉 `/tmp` 清理规则；不要以为 `disable` 就等于彻底停用。

## 参考文档

- `man 1 systemctl`：`cat`/`show`/`edit`/`daemon-reload`/`enable`/`disable`/`mask`/`reset-failed`/`clean`/`is-enabled`/`list-*` 的语义与返回码。
- `man 5 systemd.unit`：`[Install]` 与 `WantedBy=`、`DefaultDependencies=`、`StartLimitIntervalSec=`/`StartLimitBurst=`。
- `man 5 systemd.exec`、`man 5 systemd.resource-control`：资源上限、沙箱、目录选项与 `NoNewPrivileges=`/`CapabilityBoundingSet=`。
- `man 5 systemd.kill`、`man 5 systemd.service`：停止流程、`Restart=`、`OOMPolicy=`、退出码判定。
- `man 5 journald.conf`、`man 1 journalctl`：容量、持久化、限流与裁剪的边界。
- `man 5 tmpfiles.d`、`man 8 systemd-tmpfiles`：清理语义与 `--cat-config`/`--tldr` 的只读用法。
- `man 1 systemd-analyze`：`verify`、`cat-config`、`exit-status`、`security`、`time`/`blame`/`critical-chain`。
- `man 5 crontab`、`man 8 cron`：定时任务的归属、环境与转义规则。
- 行业材料：Google SRE 系列（变更管理与事后复盘）、ITIL/ITSM 的变更与配置管理实践、各发行版 systemd 官方文档。其中的阈值与流程要按自己的环境重新评估。
