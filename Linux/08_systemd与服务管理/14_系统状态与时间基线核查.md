## 0. 30 秒速览

> [!abstract] 这一篇只要记住六句话
> - **一句结论看系统状态**：`systemctl is-system-running` 输出 `running`/`degraded`/`maintenance`/`starting` 等；**`degraded` 表示有单元失败**，接着用 `systemctl --failed` 列出它们。
> - **开机慢要同时看两个命令**：`blame` 找「谁初始化花得久」，`critical-chain` 找「谁挡住了开机」——**排序第一名往往不是阻塞源**。
> - **实测例子**：本机 `blame` 第一名是 `apt-daily-upgrade.service`（19.497s），但它是 timer 触发的后台任务，`critical-chain` 里根本不在关键路径上。
> - **时间是所有证据的前提**：`System clock synchronized: no` 时，跨机日志对账、证书校验、TLS、Kerberos 都不可信；**先修时间再排障**。
> - **`journalctl` 默认按本地时区显示**，`-o short-iso`/`json` 会带时区偏移；跨时区对账统一换算成 UTC（`TZ=UTC journalctl ...`）。
> - **不要同时开两个 NTP 客户端**：Ubuntu 默认 `systemd-timesyncd`，RHEL 系默认 `chrony`，选一个就好。

## 1. 系统整体状态：一条命令 + 一个列表

```bash
systemctl is-system-running            # 验证：一句话结论
systemctl --failed                     # 验证：失败单元列表（健康机器输出为空）
systemctl list-units --state=running --type=service --no-legend | wc -l   # 验证：运行中的服务数量
```

`is-system-running` 的取值与含义：

| 输出 | 含义 | 要不要处理 |
| --- | --- | --- |
| `running` | 所有单元都正常 | 不用 |
| `degraded` | **有单元失败**（系统仍可用） | 要看 `--failed` |
| `maintenance` | 进入救援/紧急模式 | 需要人工介入 |
| `starting` / `stopping` | 正在启动/停止 | 稍后再看 |
| `offline` / `unknown` | 未运行/无法判断 | 视环境而定 |

失败单元的现场：

```bash
systemctl --failed --no-pager
systemctl status <failed-unit> --no-pager
journalctl -u <failed-unit> -b --no-pager | tail -30
```

> [!tip] 巡检的第一条命令
> 每天登录机器先跑 `systemctl --failed`。它是「有没有东西坏了」最便宜的一问；比逐个服务 `status` 快得多。

## 2. 开机分析：`time` / `blame` / `critical-chain`

```bash
systemd-analyze time
systemd-analyze blame | head -10
systemd-analyze critical-chain | head -20
```

本机实测：

```text
$ systemd-analyze time
Startup finished in 1.036s (userspace)
graphical.target reached after 1.000s in userspace.

$ systemd-analyze critical-chain | head -6
graphical.target @1.000s
└─multi-user.target @999ms
  └─snapd.seeded.service @569ms +213ms
    └─basic.target @558ms
      └─sockets.target @558ms
```

两个命令的分工：

| 命令 | 回答什么 | 怎么用 |
| --- | --- | --- |
| `blame` | 每个 unit **初始化花了多久** | 找「耗时长的候选」，**不代表它们在关键路径上** |
| `critical-chain` | **哪条依赖链决定了开机完成的时刻** | 找真正的阻塞点：链上标 `+耗时` 的那一环 |

实测对照：本机 `blame` 的第一名是 `apt-daily-upgrade.service`（19.497s），但它是 timer 触发的后台任务，`critical-chain` 里根本不在关键路径上。**只看 `blame` 会把后台任务误判成开机慢的元凶。**

看某个 unit 在关键路径上的位置与各自的启动耗时：

```bash
systemd-analyze critical-chain <unit>
systemd-analyze blame | grep <unit>
```

> [!warning] WSL2 / 容器里的开机数字不可比
> 本机的 `systemd-analyze` 输出是在 WSL2 上取的，与物理机、真实虚拟机的数字含义不同（没有固件/GRUB 阶段）。**做开机性能基线必须在真实机器上采。**

## 3. 时间基线：排障前必须先看

```bash
timedatectl
timedatectl timesync-status          # systemd-timesyncd 系统
```

本机实测：

```text
$ timedatectl
               Local time: Thu 2026-09-17 21:30:35 CST
           Universal time: Thu 2026-09-17 13:30:35 UTC
                 Time zone: Asia/Shanghai (CST, +0800)
System clock synchronized: yes
              NTP service: active
          RTC in local TZ: no

$ timedatectl timesync-status
       Server: 185.125.190.57 (ntp.ubuntu.com)
Poll interval: 32s (min: 32s; max 34min 8s)
      Stratum: 2
Root distance: 3.905ms (max: 5s)
```

要点：

- **`System clock synchronized: no` 时一切跨机对齐与证书校验都不可信**；先修时间再排障。
- `RTC in local TZ: no` 是正确设置（硬件时钟用 UTC）；`Local time` 是本机时区换算结果。
- **`journalctl` 默认按本地时区显示**，`-o short-iso`/`json` 里带时区偏移；跨时区对账用 `TZ=UTC journalctl ...` 统一换算。
- Ubuntu 默认 `systemd-timesyncd`（本机实测 `timesync-status` 可用）；RHEL 系默认 `chrony`（`chronyc tracking`/`chronyc sources -v`，**未在本机实测**）。两者都够用，**不要同时开两个 NTP 客户端**。
- 用 `timedatectl set-timezone Asia/Shanghai` 统一时区（需要 root），并把它写进基线；容器/虚拟机迁移后时区经常还是 UTC 或旧区域。

跨时区对账时，把两边都换算成 UTC 再比较：

```bash
TZ=UTC journalctl -u myapp --since "2026-09-17 12:00" --until "2026-09-17 14:00" -o short-iso
```

## 4. 一份可交付的「服务与时间基线卡」（T1）

这一篇的产出物就是它。**全程只读**，生产机可以直接跑：

```bash
systemctl --version | head -1            # ① 系统与版本
systemctl is-system-running
cat /proc/1/comm

systemctl --failed --no-pager            # ② 失败与运行中的服务
systemctl list-units --type=service --state=running --no-legend | wc -l

systemctl list-unit-files --type=service --state=enabled --no-pager   # ③ 自启的服务与安装态

systemctl list-timers --all --no-pager   # ④ 定时任务
crontab -l 2>/dev/null                   # 当前用户；系统任务看 /etc/crontab 与 /etc/cron.d

systemctl list-timers systemd-tmpfiles-clean.timer --no-pager   # ⑤ 临时文件治理
grep -vE "^\s*(#|$)" /usr/lib/tmpfiles.d/tmp.conf

systemd-analyze time                     # ⑥ 开机与日志基线
systemd-analyze blame | head -10
systemd-analyze critical-chain | head -20
journalctl --disk-usage
journalctl -b -p err --no-pager | tail -20

timedatectl                              # ⑦ 时间基线
```

本机实测的样张（**只作格式参照，不要照抄数值**）：

```text
systemd 255 (255.4-1ubuntu8.17)
running
Startup finished in 1.036s (userspace)
Archived and active journals take up 560.7M in the file system.
D /tmp 1777 root root 30d
systemd-tmpfiles-clean.timer  next: 每日一次
用户单元默认 LimitNOFILE=1048576、KillMode=control-group、TimeoutStopUSec=1min 30s、RestartUSec=100ms
```

> [!tip] 基线卡要留档、要能对比
> 服务的价值来自「和上次比」：多出来的自启单元、多出来的 timer、`/tmp` 规则变更、日志占用翻倍——这些只有留档才看得见。把上面的输出按 `日期_主机名` 存一份，就是最朴素的「服务与任务基线」。

## 5. 5 分钟体检：按这个顺序

```bash
systemctl --failed --no-pager            # ① 有没有坏东西
systemctl is-system-running              # ② 整体状态
journalctl -p err -b --no-pager | tail -20   # ③ 本次启动的系统级错误
journalctl --disk-usage                  # ④ 日志占了多少
timedatectl                              # ⑤ 时间对不对
```

顺序不是随便定的：**先看「有没有已知故障」，再看「整体状态」，再看证据，最后确认时间前提**。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 把 `systemctl is-system-running` 的 `degraded` 当正常 | `degraded` = 有单元失败；要看 `--failed` |
| 把 `blame` 第一名当成开机慢的元凶 | `blame` 是耗时排序，`critical-chain` 才是关键路径；实测第一名是后台 timer 任务 |
| 在 WSL2/容器里采开机性能基线 | 没有固件/引导阶段，数字与物理机不可比 |
| 时钟不同步就下结论「日志时间对不上」 | 先 `timedatectl` 确认同步状态，再对齐（UTC）比较 |
| 同时开 `systemd-timesyncd` 和 `chrony` | 两个 NTP 客户端互相打架；只留一个 |
| 用本地时间跨时区对账 | 两边都换算成 UTC 再比，或统一用带时区偏移的输出 |
| 只看本次 boot 的日志下结论 | 问题可能在上一次启动（`-b -1`），前提是日志已持久化 |

## 决策练习

> [!question]- 场景：一台服务器「开机很慢」，你跑 `systemd-analyze blame` 看到第一名是一个 `apt-daily-upgrade.service`，耗时 19s。同事说「把这个服务禁掉就能快 19 秒」。
> A. 禁掉 `apt-daily-upgrade.service`，重启验证
> B. 先看 `systemd-analyze critical-chain`，确认这个服务是否真的在决定开机完成时刻的依赖链上；再决定是否调整（例如改 timer 触发时间），而不是禁掉安全更新
> C. 调大相关服务的 `TimeoutStartSec=`，让它们别超时
> **答案：B。**
> A 可能一点没变快，还顺手关掉了安全更新。
> C 与「开机慢」不是同一个问题，且会掩盖真实原因。
> B 是正解：**先分清「谁慢」与「谁挡住了开机」**，再选对处置对象。

## 要点自测

> [!question]- `systemctl is-system-running` 输出 `degraded` 说明什么？下一步做什么？
> - 说明系统已进入可用状态，但**有单元失败了**（不是完全正常）。
> - 下一步：`systemctl --failed` 列出失败单元，再对每个跑 `status` 与 `journalctl -u`。
> - 注意 `maintenance` 才代表进了救援/紧急模式，与 `degraded` 不同。
> - **第一反应不要是什么**：不要把 `degraded` 当正常，也不要直接重启——先看是哪些单元失败了。

> [!question]- `systemd-analyze blame` 和 `critical-chain` 的区别是什么？
> - `blame`：按**初始化耗时**给 unit 排序，回答「谁慢」。
> - `critical-chain`：打印**决定开机完成时刻的依赖链**，回答「谁挡住了开机」。
> - 实测里 `blame` 第一名可能根本不在关键路径上（本机是 timer 触发的后台任务）。
> - **第一反应不要是什么**：不要只看 `blame` 第一名就动手禁服务。

> [!question]- 为什么排障前必须先确认时间基线？
> - 时钟不同步时，跨机日志时间线拼不到一起、证书校验可能失败、定时任务可能在错误的时间触发。
> - 检查：`timedatectl`（看 `System clock synchronized`、时区、`RTC in local TZ`）与 `timedatectl timesync-status`。
> - 对账：统一换算成 UTC（`TZ=UTC journalctl ...`）或用带时区偏移的输出。
> - **第一反应不要是什么**：不要在时钟不同步的情况下比较两台机器的时间戳并据此下结论。
