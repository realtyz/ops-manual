## 0. 30 秒速览

> [!abstract] 这一篇只要记住六句话
> - **一句结论看系统状态**：`systemctl is-system-running` 输出 `running`/`degraded`/`maintenance`/`starting` 等；**`degraded` 表示有单元失败**，接着用 `systemctl --failed` 列出它们。本机清理掉自建实验单元后实测是 `running`、`--failed` 为 0 条。
> - **开机慢要同时看两个命令**：`blame` 找「谁初始化花得久」，`critical-chain` 找「谁挡住了开机」——**排序第一名往往不是阻塞源**。
> - **实测例子**：本机 `blame` 第一名是 `systemd-networkd-wait-online.service`（1.231s），但 `critical-chain` 的链路是 `graphical.target @2.426s → multi-user.target @2.426s → apport.service @2.270s +154ms → remote-fs.target`，**它不在决定开机完成时刻的那条链上**。
> - **`systemd-analyze time` 在本机只有 kernel + userspace 两段**：实测 `Startup finished in 3.922s (kernel) + 2.439s (userspace) = 6.362s`，**没有 `firmware`/`loader` 行**——因为这台虚拟机是 **Legacy BIOS 引导**（`/sys/firmware/efi` 不存在），而 `systemd-analyze` 的固件/引导耗时来自 EFI 变量。**固件与 GRUB 阶段物理上存在，只是量不到。**
> - **时间是所有证据的前提**：本机 `System clock synchronized: no`（`NTP service: active`，`NTPSynchronized=no`）时，跨机日志对账、证书校验、TLS、Kerberos 都不可信；**先修时间再排障**。
> - **`journalctl` 默认按本地时区显示**，本机时区是 `Etc/UTC (UTC, +0000)`，所以 `-o short` 与 UTC 一致；换到 `Asia/Shanghai` 之类的机器就要注意偏移，跨时区对账统一换算成 UTC（`TZ=UTC journalctl ...`）。
> - **不要同时开两个 NTP 客户端**：Ubuntu 默认 `systemd-timesyncd`（本机实测 `active`+`enabled`，`timesync-status` 可用），RHEL 系默认 `chrony`；本机**没有装 chrony**，所以只有一个客户端，这也是「时间没同步」时要先排除重叠客户端的原因。

## 1. 系统整体状态：一条命令 + 一个列表

```bash
systemctl is-system-running            # 验证：一句话结论
systemctl --failed                     # 验证：失败单元列表（健康机器输出为空）
systemctl list-units --state=running --type=service --no-legend | wc -l   # 验证：运行中的服务数量
```

`is-system-running` 的取值与含义：

| 输出 | 含义 | 要不要处理 |
| --- | --- | --- |
| `running` | 所有单元都正常 | 不用 |
| `degraded` | **有单元失败**（系统仍可用） | 要看 `--failed` |
| `maintenance` | 进入救援/紧急模式 | 需要人工介入 |
| `starting` / `stopping` | 正在启动/停止 | 稍后再看 |
| `offline` / `unknown` | 未运行/无法判断 | 视环境而定 |

失败单元的现场：

```bash
systemctl --failed --no-pager
systemctl status <failed-unit> --no-pager
journalctl -u <failed-unit> -b --no-pager | tail -30
```

> [!tip] 巡检的第一条命令
> 每天登录机器先跑 `systemctl --failed`。它是「有没有东西坏了」最便宜的一问；比逐个服务 `status` 快得多。

本机实测（**清理掉自建实验单元之后**的干净状态）：

```text
$ systemctl is-system-running
running
$ systemctl --failed --no-pager
  UNIT LOAD ACTIVE SUB DESCRIPTION
0 loaded units listed.
$ systemctl list-units --type=service --state=running --no-legend | wc -l
25
```

反例也留下了一次现场：实验期间 `lab08b-stubborn.service`（一个忽略 SIGTERM 的单元，被 `TimeoutStopSec` 超时 SIGKILL）处于 `failed`，那一刻 `is-system-running` 就是 `degraded`：

```text
$ systemctl is-system-running
degraded
$ systemctl --failed --no-pager
  UNIT                    LOAD   ACTIVE SUB    DESCRIPTION
● lab08b-stubborn.service loaded failed failed lab08b ignores SIGTERM
```

## 2. 开机分析：`time` / `blame` / `critical-chain`

```bash
systemd-analyze time
systemd-analyze blame | head -10
systemd-analyze critical-chain | head -20
```

本机实测：

```text
$ systemd-analyze time
Startup finished in 3.922s (kernel) + 2.439s (userspace) = 6.362s
graphical.target reached after 2.426s in userspace.

$ systemd-analyze blame | head -6
1.231s systemd-networkd-wait-online.service
 474ms snapd.seeded.service
 436ms snapd.service
 380ms dev-mapper-ubuntu\x2d\x2dvg\x2dubuntu\x2d\x2dlv.device
 341ms fwupd-refresh.service
 336ms systemd-networkd.service

$ systemd-analyze critical-chain
The time when unit became active or started is printed after the "@" character.
The time the unit took to start is printed after the "+" character.

graphical.target @2.426s
└─multi-user.target @2.426s
  └─apport.service @2.270s +154ms
    └─remote-fs.target @2.269s
      └─remote-fs-pre.target @2.266s
```

两个命令的分工：

| 命令 | 回答什么 | 怎么用 |
| --- | --- | --- |
| `blame` | 每个 unit **初始化花了多久** | 找「耗时长的候选」，**不代表它们在关键路径上** |
| `critical-chain` | **哪条依赖链决定了开机完成的时刻** | 找真正的阻塞点：链上标 `+耗时` 的那一环 |

实测对照：本机 `blame` 的第一名 `systemd-networkd-wait-online.service`（1.231s）**不在** `critical-chain` 上（它有自己的一条链：`systemd-networkd-wait-online.service` → `systemd-networkd.service @650ms +336ms` → `network-pre.target`），真正的关键路径末梢是 `apport.service @2.270s +154ms`。**只看 `blame` 会把并行启动的服务误判成开机慢的元凶。** 另外一个容易误判的事实：本机这一轮启动里 `systemd-analyze blame` 中**根本没有 `apt-daily-upgrade.service`**（`blame | grep -c apt-daily` = 0）——它是 timer 触发的后台任务，跑在开机之后，能不能出现在 `blame` 里取决于当前这次的 timer 触发时间。

看某个 unit 在关键路径上的位置与各自的启动耗时：

```bash
systemd-analyze critical-chain <unit>
systemd-analyze blame | grep <unit>
```

> [!warning] 虚拟机的开机数字也不能直接和物理机比——但缺阶段的是 WSL2/容器，不是虚拟机
> 本机的 `systemd-analyze time` 输出只有 **`kernel` + `userspace`** 两段，没有 `firmware`/`loader`：
> - 这台 VMware 虚拟机是 **Legacy BIOS 引导**（`ls /sys/firmware/efi` → `No such file or directory`），`systemd-analyze` 的固件/引导耗时来自 EFI 变量（`LoaderTimeInitUSec` 等），BIOS 引导下**取不到**；
> - 但固件与引导阶段**物理上确实存在**：`dmesg` 开头有 `BIOS-provided physical RAM map`、`BIOS-e820: …`，`/boot/grub/grub.cfg` 存在（`grub-common 2.12-1ubuntu7.3`），`systemd-analyze blame` 里还有 `grub-common.service`（197ms），内核命令行是 `BOOT_IMAGE=/vmlinuz-6.8.0-139-generic root=/dev/mapper/ubuntu--vg-ubuntu--lv ro`——**这就是一次经 BIOS + GRUB 装载内核的启动**。
> - 所以正确的说法是：**虚拟机（有固件 + 引导阶段，但 BIOS 模式下 `systemd-analyze` 量不到固件耗时）与物理机仍不可比；而 WSL2/容器是真正缺失这些阶段**。要连固件耗时一起量，得上 UEFI 引导 + `systemd-boot`/GRUB 的 EFI 变量，或看带外管理/虚拟化平台的启动耗时。
> - 跨机对比开机性能时，至少要说明：**引导方式（UEFI/BIOS）、`systemd-analyze` 输出里有没有 `firmware`/`loader` 段、内核与 userspace 两段各是多少**。本机基线：`3.922s`(kernel) + `2.439s`(userspace) = `6.362s`。

## 3. 时间基线：排障前必须先看

```bash
timedatectl
timedatectl timesync-status          # systemd-timesyncd 系统
```

本机实测：

```text
$ timedatectl
               Local time: Sat 2026-09-19 08:10:31 UTC
           Universal time: Sat 2026-09-19 08:10:31 UTC
                 RTC time: Sat 2026-09-19 08:10:31
                Time zone: Etc/UTC (UTC, +0000)
System clock synchronized: no
              NTP service: active
          RTC in local TZ: no

$ timedatectl show
Timezone=Etc/UTC
LocalRTC=no
CanNTP=yes
NTP=yes
NTPSynchronized=no
TimeUSec=Sat 2026-09-19 08:10:31 UTC
RTCTimeUSec=Sat 2026-09-19 08:10:31 UTC

$ timedatectl timesync-status
       Server: fdfe:dcba:9876::d (ntp.ubuntu.com)
Poll interval: 34min 8s (min: 32s; max 34min 8s)
 Packet count: 0

$ date -Is
2026-09-19T08:10:31+00:00
```

要点：

- **`System clock synchronized: no` 时一切跨机对齐与证书校验都不可信**；先修时间再排障。本机就是这种状态：`NTP service: active`、`NTPSynchronized=no`、`Packet count: 0`（一次包都没换到）——**「NTP 服务在跑」不等于「时间已同步」**，这两行必须分开看。
- `RTC in local TZ: no` 是正确设置（硬件时钟用 UTC）；`Local time` 是本机时区换算结果。本机时区是 **`Etc/UTC (UTC, +0000)`**，不是常见的 `Asia/Shanghai`——所以本机 `date -Is` 带的是 `+00:00`，`journalctl` 的本地时间与 UTC 一致。**换机器必须重新看这两行，不能照抄。**
- **`journalctl` 默认按本地时区显示**，`-o short-iso`/`json` 里带时区偏移；跨时区对账用 `TZ=UTC journalctl ...` 统一换算。
- Ubuntu 默认 `systemd-timesyncd`（本机实测 `systemctl is-active systemd-timesyncd` = `active`、`is-enabled` = `enabled`，`timesync-status` 可用）。RHEL 系默认 `chrony`（`chronyc tracking`/`chronyc sources -v`）。
  **本机没有安装 chrony**：`command -v chronyc` 与 `chronyd` 都为空，`systemctl is-active chrony` = `inactive`、`is-enabled chrony` = `not-found`。所以 `chronyc` 系列命令**在本机未实测**，本篇只按文档记录其用途。两者都够用，**不要同时开两个 NTP 客户端**——本机只有一个，这也是判「时间为什么不对」时要先排除的一条。
- **`hwclock` 本机也未实测**：`command -v hwclock` 为空（Ubuntu 24.04 把它放在 `util-linux-extra` 包里），`/etc/adjtime` 不存在。RTC 只能通过 `timedatectl` 输出的 `RTC time` 与 `RTC in local TZ` 观察。
- 用 `timedatectl set-timezone Asia/Shanghai` 统一时区（需要 root），并把它写进基线；容器/虚拟机迁移后时区经常还是 UTC 或旧区域——**本机就是 UTC，正好是这一条的现实样本**。

跨时区对账时，把两边都换算成 UTC 再比较：

```bash
TZ=UTC journalctl -u myapp --since "2026-09-19 12:00" --until "2026-09-19 14:00" -o short-iso
```

## 4. 一份可交付的「服务与时间基线卡」（T1）

这一篇的产出物就是它。**全程只读**，生产机可以直接跑：

```bash
systemctl --version | head -1            # ① 系统与版本
systemctl is-system-running
cat /proc/1/comm

systemctl --failed --no-pager            # ② 失败与运行中的服务
systemctl list-units --type=service --state=running --no-legend | wc -l

systemctl list-unit-files --type=service --state=enabled --no-pager   # ③ 自启的服务与安装态
systemctl get-default                                                 # 默认 target

systemctl list-timers --all --no-pager   # ④ 定时任务
crontab -l 2>/dev/null                   # 当前用户；系统任务看 /etc/crontab 与 /etc/cron.d

systemctl list-timers systemd-tmpfiles-clean.timer --no-pager   # ⑤ 临时文件治理
grep -vE "^\s*(#|$)" /usr/lib/tmpfiles.d/tmp.conf
findmnt -T /tmp -o TARGET,SOURCE,FSTYPE  # /tmp 到底是不是 tmpfs

systemd-analyze time                     # ⑥ 开机与日志基线
systemd-analyze blame | head -10
systemd-analyze critical-chain | head -20
journalctl --disk-usage
journalctl --list-boots --no-pager
journalctl -b -p err --no-pager | tail -20

timedatectl                              # ⑦ 时间基线
timedatectl timesync-status
ls /sys/firmware/efi >/dev/null 2>&1 && echo "UEFI boot" || echo "Legacy BIOS boot"   # 开机阶段能不能量
```

本机实测的样张（**只作格式参照，不要照抄数值**）：

```text
systemd 255 (255.4-1ubuntu8.17)
running
25                                  # 运行中的 service 数量
graphical.target                    # 默认 target
Startup finished in 3.922s (kernel) + 2.439s (userspace) = 6.362s
Archived and active journals take up 53.9M in the file system.
D /tmp 1777 root root 30d
systemd-tmpfiles-clean.timer  OnBootSec=15min + OnUnitActiveSec=1d, AccuracyUSec=1min
Legacy BIOS boot                    # /sys/firmware/efi 不存在
Etc/UTC (UTC, +0000) / System clock synchronized: no / NTP service: active / RTC in local TZ: no
系统级默认 KillMode=control-group、KillSignal=15、TimeoutStopUSec=1min 30s、RestartUSec=100ms、Restart=no
```

> [!tip] 基线卡要留档、要能对比
> 服务的价值来自「和上次比」：多出来的自启单元、多出来的 timer、`/tmp` 规则变更、日志占用翻倍——这些只有留档才看得见。把上面的输出按 `日期_主机名` 存一份，就是最朴素的「服务与任务基线」。
> **本机自己做了一次反面示范**：为了测 `journalctl --vacuum-*` 跑了 `--vacuum-time=1h`，日志占用从 53.9 MiB 掉到 16.0 MiB，同时 `journalctl --list-boots` 只剩当前这一次启动。**基线卡的价值就在于让这种变化一眼可见。**

## 5. 5 分钟体检：按这个顺序

```bash
systemctl --failed --no-pager            # ① 有没有坏东西
systemctl is-system-running              # ② 整体状态
journalctl -p err -b --no-pager | tail -20   # ③ 本次启动的系统级错误
journalctl --disk-usage                  # ④ 日志占了多少
timedatectl                              # ⑤ 时间对不对
```

顺序不是随便定的：**先看「有没有已知故障」，再看「整体状态」，再看证据，最后确认时间前提**。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 把 `systemctl is-system-running` 的 `degraded` 当正常 | `degraded` = 有单元失败；要看 `--failed` |
| 把 `blame` 第一名当成开机慢的元凶 | `blame` 是耗时排序，`critical-chain` 才是关键路径；本机实测第一名是 `systemd-networkd-wait-online.service`（1.231s），而它并不在 `critical-chain` 上（链路是 `graphical.target @2.426s → multi-user.target → apport.service @2.270s +154ms`） |
| 在 WSL2/容器里采开机性能基线 | 没有固件/引导阶段，数字与物理机不可比 |
| 时钟不同步就下结论「日志时间对不上」 | 先 `timedatectl` 确认同步状态，再对齐（UTC）比较 |
| 同时开 `systemd-timesyncd` 和 `chrony` | 两个 NTP 客户端互相打架；只留一个 |
| 用本地时间跨时区对账 | 两边都换算成 UTC 再比，或统一用带时区偏移的输出 |
| 只看本次 boot 的日志下结论 | 问题可能在上一次启动（`-b -1`），前提是日志已持久化 |

## 决策练习

> [!question]- 场景：一台服务器「开机很慢」，你跑 `systemd-analyze blame` 看到第一名是一个 `apt-daily-upgrade.service`，耗时 19s。同事说「把这个服务禁掉就能快 19 秒」。
> A. 禁掉 `apt-daily-upgrade.service`，重启验证
> B. 先看 `systemd-analyze critical-chain`，确认这个服务是否真的在决定开机完成时刻的依赖链上；再决定是否调整（例如改 timer 触发时间），而不是禁掉安全更新
> C. 调大相关服务的 `TimeoutStartSec=`，让它们别超时
> **答案：B。**
> A 可能一点没变快，还顺手关掉了安全更新。
> C 与「开机慢」不是同一个问题，且会掩盖真实原因。
> B 是正解：**先分清「谁慢」与「谁挡住了开机」**，再选对处置对象。

## 要点自测

> [!question]- `systemctl is-system-running` 输出 `degraded` 说明什么？下一步做什么？
> - 说明系统已进入可用状态，但**有单元失败了**（不是完全正常）。
> - 下一步：`systemctl --failed` 列出失败单元，再对每个跑 `status` 与 `journalctl -u`。
> - 注意 `maintenance` 才代表进了救援/紧急模式，与 `degraded` 不同。
> - **第一反应不要是什么**：不要把 `degraded` 当正常，也不要直接重启——先看是哪些单元失败了。

> [!question]- `systemd-analyze blame` 和 `critical-chain` 的区别是什么？
> - `blame`：按**初始化耗时**给 unit 排序，回答「谁慢」。
> - `critical-chain`：打印**决定开机完成时刻的依赖链**，回答「谁挡住了开机」。
> - 实测里 `blame` 第一名根本不在关键路径上：本机是 `systemd-networkd-wait-online.service`（1.231s），`critical-chain` 的链路却是 `graphical.target @2.426s → multi-user.target @2.426s → apport.service @2.270s +154ms → remote-fs.target`；`apt-daily` 相关单元在本机 `blame` 里出现 **0** 次。
> - **第一反应不要是什么**：不要只看 `blame` 第一名就动手禁服务。

> [!question]- 为什么排障前必须先确认时间基线？
> - 时钟不同步时，跨机日志时间线拼不到一起、证书校验可能失败、定时任务可能在错误的时间触发。
> - 检查：`timedatectl`（看 `System clock synchronized`、时区、`RTC in local TZ`）与 `timedatectl timesync-status`。
> - 对账：统一换算成 UTC（`TZ=UTC journalctl ...`）或用带时区偏移的输出。
> - **第一反应不要是什么**：不要在时钟不同步的情况下比较两台机器的时间戳并据此下结论。
