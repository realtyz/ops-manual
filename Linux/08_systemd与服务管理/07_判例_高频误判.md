# 高频误判

十四条按值班与复盘里的真实处境写成：**场景**（谁、什么机器、看到什么、别人怎么说）→ **常见误判及它为什么看起来成立** → **判据**（读哪个字段、什么数值或趋势、什么条件下结论会变）→ **一句话结论** → **出处**。字段的读法在实操篇的 2.1–2.3。

## 1. 「改完 unit 了，`restart` 一下就好」

**场景**：同事在 `/etc/systemd/system/myapp.service.d/override.conf` 里把 `Environment=PHASE=2` 加进去，随即 `systemctl restart myapp`，服务行为没变。他说「可能是应用有缓存」。

**常见误判**：认为文件写完就等于生效。它看起来成立，是因为同一条命令在别的系统上（比如直接改配置文件的传统服务）确实立刻生效。

**判据**：分三层问。`systemctl show -p Environment myapp` 看 **manager** 里的值——如果这里还是旧的，说明 `daemon-reload` 没执行（`status` 会有一行 `changed on disk` 警告，但容易漏看）；如果 manager 已是新值而服务行为没变，读 `/proc/<MainPID>/environ` 看**进程**里的值——这里仍是旧的，说明只 reload 没 restart，`MainPID` 也不会变。**条件会变**：属于「运行期持续读取」的配置（应用自己会重读的文件）不需要 restart；判断标准是这项配置在进程启动时读还是运行期读。

**一句话结论**：生效链是三段——文件 → manager → 进程；`daemon-reload` 只走第二段，`restart` 才走到第三段。

**出处**：`man 5 systemd.unit`、`man 1 systemctl`（`show`、`daemon-reload`）；原文作者实测（Ubuntu 24.04.5 / systemd 255）：reload 后 `show` 为 `PHASE=2` 而 `/proc/<pid>/environ` 仍是 `PHASE=1`、`MainPID` 未变。

## 2. 「文件里明明写了，怎么没生效」

**场景**：`StartLimitIntervalSec=30` 写在 `[Service]` 里，`systemd-analyze verify` 退出码为 0，于是认定配置没问题。服务反复重启时完全没有节流。

**常见误判**：把 `verify` 的退出码当合格证明。它看起来成立，是因为「退出码 0 = 通过」是通用直觉。

**判据**：读 `verify` 的**输出文本**——它会打印 `Unknown key name 'StartLimitIntervalSec' in section 'Service', ignoring.`，这一行就是配置被静默丢弃的证据。`StartLimitIntervalSec=`/`StartLimitBurst=` 属于 `[Unit]`。**条件会变**：键名拼错、写错小节都属于这一类；只有结构性错误（例如给 `Type=simple` 写两条 `ExecStart=`）才会让退出码非 0。另一个同类陷阱是 unit 里的 `%`：它会被无条件展开（`%T` 展开成 `/tmp`、`%s` 展开成 shell 路径），写 `date +%T` 会静默出错，退出码同样是 0。

**一句话结论**：干净的单元在 `verify` 下应当**完全沉默**；它只要说话了，就有东西被忽略或拒绝。

**出处**：`man 5 systemd.unit`（键的归属小节）、`man 1 systemd-analyze`（`verify`）；原文作者实测同上。

## 3. 「`limit` 调了没用，把值再调大」

**场景**：Java 服务偶发 `Too many open files`。同事在 `/etc/security/limits.conf` 里把 `nofile` 调到 65535 又执行了 `daemon-reexec`，问题仍在，于是准备继续调大。

**常见误判**：认为 `limits.conf` 是所有进程的上限来源。它看起来成立，是因为登录会话里 `ulimit -n` 确实受它影响。

**判据**：systemd 服务不经过登录会话，PAM 的 `pam_limits` 不介入，`limits.conf` 对它**永远不生效**。正确落点是 unit 的 `LimitNOFILE=`（drop-in 里写），改完 `daemon-reload` + `restart`，最后用 `/proc/<MainPID>/limits` 验收。还要注意 `LimitNOFILE=`（硬）与 `LimitNOFILESoft=`（软）是两个属性：只看硬值会把「最多能抬到多少」当成「实际可用」。**条件会变**：如果服务是被人手工在 shell 里起的，`ulimit` 才有关；生产路径不是。

**一句话结论**：调 rlimit 改的是 unit，不是 `limits.conf`；验收看进程，不看配置文件。

**出处**：`man 5 systemd.exec`（`Limit*=`）、`man 5 systemd-system.conf`（`DefaultLimit*`）、`man 5 limits.conf`。

## 4. 「进程还在跑，服务怎么会是死的」

**场景**：把一条 `ExecStart=/bin/bash -c "sleep 120 &"` 配成 `Type=simple`，`systemctl status` 显示 `inactive (dead)`，但 `ps` 里能看到 `sleep`（或刚启动时能看到）。同事说「systemd 是不是判错了」。

**常见误判**：用「进程是否存在」代替「`Type=` 的判据」。它看起来成立，是因为「服务 = 进程」是日常直觉。

**判据**：读 `show -p Type -p SubState -p Result -p MainPID`。`Type=simple` 把「主进程被 `fork` 出来」当启动完成，主进程（`bash`）一退出就判定服务结束，留在控制组里的后台进程会被一并清掉，所以 `MainPID=0`、`SubState=dead`、`Result=success`。同一条命令配 `Type=forking` 则会得到 `active (running)`、`MainPID` 指向 `sleep`。**条件会变**：如果进程真的脱离了控制组（例如以 `KillMode=process` 加自行 `setsid`），它可能活下来成为孤儿——此时单元状态是 dead 而机器上多一个没人管的进程。

**一句话结论**：状态由 `Type=` 的判据决定；改判定方式，不是让程序去迎合错误的类型。

**出处**：`man 5 systemd.service`（`Type=` 八种取值的判定时机）；原文作者实测同上。

## 5. 「日志里都打印 ready 了，systemd 还等满超时，是 bug 吧」

**场景**：一个 `Type=notify` 的服务，启动时打印了 `ready`，`systemctl start` 却挂了 90 秒才失败。同事准备给 systemd 提 issue。

**常见误判**：把「打印 ready」当成「报告就绪」。它看起来成立，是因为日志里确实有那么一行。

**判据**：只有 `sd_notify` 通知算数，而且**发送者的身份要符合 `NotifyAccess=` 的资格**（缺省 `main`）。日志里会有一行「收到了来自某 PID 的通知，但只允许主 PID」，随后是 `Result=timeout`、`ActiveState=failed`。常见成因是通知由子进程或包了一层 `sh -c`/`env`/`sudo` 的间接调用发出。**特例**：`systemd-notify` 命令行工具会伪造发送者身份，所以「手工测能过、写进服务不行」——手工用的是这个工具。**条件会变**：如果应用根本没调用 `sd_notify`，那不是归属问题，而是没实现协议，只能换 `Type=`。

**一句话结论**：`notify` 的判定依据是「谁发的」，不是「发了什么」；先看拒绝日志，再谈超时值。

**出处**：`man 3 sd_notify`（通知协议与发送方身份判定）、`man 5 systemd.service`（`NotifyAccess=`）、`man 1 systemd-notify`。原文作者实测（Ubuntu 24.04.5 / systemd 255）：主进程自己发约 0.03 秒成功，包一层后 6 秒级超时，默认等到 90.237 秒。

## 6. 「端口在听，服务却是 inactive，肯定有幽灵进程」

**场景**：`ss -lntp` 显示某端口在监听，`systemctl status` 却是 `inactive (dead)`，进程也不属于该服务。

**常见误判**：认为状态与监听必然一致，于是去找「系统外的进程」。它看起来成立，是因为监听确实发生了。

**判据**：看 `status` 里的 `TriggeredBy:` 行与 `systemctl list-sockets`。socket 激活的单元里，持监听套接字的是 `.socket` 单元，服务在第一个连接到达时才被拉起。`inactive` 也可能是 `oneshot` 跑完或 timer 刚触发完。**条件会变**：如果 `list-sockets` 里没有对应条目，那才需要怀疑是别的进程占用端口（用 `ss -lntp` 的 PID 列追）。

**一句话结论**：监听与运行是两个对象；`inactive` 不等于「没有东西在听」。

**出处**：`man 5 systemd.socket`、`man 1 systemctl`（`list-sockets`）。

## 7. 「`active (running)` 了，那就是可用了」

**场景**：上线后 `systemctl start` 返回 0、`status` 显示 `active (running)`，值班据此回复「服务已恢复」；五分钟后业务仍在报错。

**常见误判**：把 systemd 的启动判定当业务验收。它看起来成立，是因为「running」这个词很有说服力。

**判据**：`active (running)` 只说明 `Type=` 的判定通过。业务验收要另取三类证据：端口（`ss -lntp`）、日志（`journalctl -u myapp -b`）、指标或健康检查。常见三种「running 但不可用」：依赖未就绪（`After=` 只等对方的启动动作完成，不等可用）、socket 激活（服务尚未被拉起）、`Type=` 选得太平（`simple` 在进程 `fork` 出来时就判定完成）。**条件会变**：如果端口在听、日志正常但业务仍失败，那要往应用内部与下游查，与 systemd 无关。

**一句话结论**：`start` 返回 0 只代表 systemd 的判定通过；可用性只能用业务证据验收。

**出处**：`man 5 systemd.service`（`Type=`）、`man 1 systemctl`（`start` 的返回语义）。原文作者实测同上：`After=` 等到的时刻随对方 `Type=` 而变。

## 8. 「服务每几秒重启一次，过一会儿彻底不重启了，systemd 卡了」

**场景**：一个启动就崩的服务，头一分钟重启了五次，之后 `start` 直接报错，怎么都不起来。

**常见误判**：把「不再重启」当成新故障。它看起来成立，因为行为确实变了。

**判据**：这是启动节流，不是新故障。`show -p Result -p NRestarts -p StartLimitBurst -p StartLimitIntervalUSec` 会显示 `NRestarts` 停在 burst 值、`ActiveState=failed`；日志里是 `Start request repeated too quickly.`。缺省窗口 10 秒、缺省次数 5 次（systemd 255 实测）。恢复要**先清计数再启动**：`systemctl reset-failed <unit>` 之后 `start`。**条件会变**：`reset-failed` 只是清账，根因不修就会重现；调大 `StartLimitBurst=` 只是让重启风暴继续，属于止血不属于修复。

**一句话结论**：先回答「它为什么反复失败」，再决定要不要 `reset-failed`；不要先调大上限。

**出处**：`man 5 systemd.unit`（`StartLimitIntervalSec=`/`StartLimitBurst=` 属 `[Unit]`）、`man 5 systemd.service`（`Restart=`）、`man 1 systemctl`（`reset-failed`）。

## 9. 「`stop` 之后服务自己又起来了，`Restart=` 配错了吧」

**场景**：为了验证重启策略，同事用 `systemctl stop` 停掉服务，发现它没有自动起来，于是判定「`Restart=` 没生效」。

**常见误判**：用主动停止来验证 `Restart=`。它看起来成立，是因为「停了就该按策略重启」。

**判据**：**systemd 主动发起的停止不会触发 `Restart=`**，这是设计——否则服务永远停不掉。证据是 `stop` 之后 `NRestarts` 保持 0、`SubState=dead`。要验证 `Restart=` 必须让服务**自己**失败退出（例如让主命令返回非 0 或以信号结束）。另外一个反向误判是：`Restart=on-failure` 遇到退出码 0 不会重启，想「正常退出也拉起来」要写 `always`。

**一句话结论**：验证重启策略要靠「自然死亡」，不能靠 `stop`。

**出处**：`man 5 systemd.service`（`Restart=` 一节明确排除 systemd 主动停止与重启的情形）。

## 10. 「`restart` 一下看看」

**场景**：服务行为异常，值班先 `systemctl restart myapp`，然后再去看状态与日志。

**常见误判**：把重启当成无害的观察手段。它看起来成立，因为重启经常真的「好了」。

**判据**：**`restart` 会覆盖现场**。`Result`、`NRestarts`、`ExecMainStatus` 与上一进程的 stdout/stderr 都被重置；如果日志没有持久化，重启前那段可能直接消失；cgroup 目录随单元结束被回收，`memory.events` 之类的账本也没了。正确顺序是先取证：`status --no-pager -l` 读全状态、`show` 取关键属性、`journalctl -u ... -b | tail` 取日志，**之后再决定**是止血还是修复。**条件会变**：如果影响面在扩大、必须立刻恢复业务，先止血（并记录「这一步是止血」）是合理的——但止血不是诊断。

**一句话结论**：重启是动作，不是信息；先取证再动手。

**出处**：`man 1 systemctl`（`restart`、`reset-failed` 的语义）、`Documentation/admin-guide/cgroup-v2.rst`（cgroup 目录的生命周期）。

## 11. 「`disable` 了就等于彻底停用了」

**场景**：要停用一个不想要的发行版服务，执行 `systemctl disable foo` 并确认 `is-enabled` 返回 `disabled`；下次开机它又起来了。

**常见误判**：把「安装态」当成「能不能被启动」。它看起来成立，因为 `disabled` 字面上像「禁用」。

**判据**：`disable` 只删除 `[Install]` 对应的自启软链，服务仍可被手动 `start`、被别的单元 `Wants=` 拉起、被 socket/path/timer 触发。要彻底挡住用 `mask`（在更高优先级目录建指向 `/dev/null` 的软链）。**两处边界**：单元文件本身就在 `/etc/systemd/system/` 时 `mask` 会失败（提示文件已存在），要先移走或改名；如果它由 `.socket`/`.path`/`.timer` 触发，`mask` 服务时 systemd 会提示「触发单元仍然 active」——端口还在监听、连接被推给一个永远起不来的服务，要连触发器一起处理。

**一句话结论**：`disable` 管自启，`mask` 管能不能被启动；触发链要一起看。

**出处**：`man 5 systemd.unit`（`[Install]`）、`man 1 systemctl`（`enable`/`disable`/`mask` 的行为与提示文本）。

## 12. 「关机卡在 `A stop job is running`，把 `KillMode` 改成 `none` 就好了」

**场景**：重启一台机器时卡在「A stop job is running for ...」，等了一分钟才继续。同事建议把该服务的 `KillMode=none` 或超时设成无限大。

**常见误判**：把等待当成机制故障。它看起来成立，因为「卡住」通常意味着「该跳过」。

**判据**：那一分钟来自 `TimeoutStopSec=`（systemd 255 缺省 `1min 30s`）：停止流程是先发 `KillSignal=`（缺省 SIGTERM）、等超时、再补 SIGKILL。日志里会有 `State 'stop-sigterm' timed out. Killing.`，随后 `code=killed, status=9/KILL`、`Failed with result 'timeout'`。`stop` 的实际耗时几乎等于 `TimeoutStopSec=`，用这个规律就能确认是不是它。**条件会变**：如果应用确实需要更长时间收尾，把超时调到略大于真实收尾时间是对的（保留 `SendSIGKILL=yes` 兜底）；改成 `KillMode=none` 会让进程逃出管理器、留下孤儿，只是把问题推到下一次。

**一句话结论**：先确认是应用不响应 SIGTERM 还是超时太短；不要把「跳过信号」当解决。

**出处**：`man 5 systemd.kill`（`KillMode=`、`KillSignal=`、`SendSIGKILL=`、`TimeoutStopSec=`）、`man 1 systemctl`（`list-jobs`）。

## 13. 「定时任务到点没跑，cron 坏了」

**场景**：一个 `/etc/cron.d/backup` 里的任务昨晚没执行，日志里也看不到。同事开始怀疑 cron 服务。

**常见误判**：把「没跑」和「没触发」当成一回事。它看起来成立，因为结果确实缺失。

**判据**：分三层查。**调度层**：`journalctl -u cron --since "..."` 里有没有 `CRON[pid]: (user) CMD (...)` 那一行——没有就是没被调度（cron 服务是否 active、表达式、`/etc/cron.allow` 与 `cron.deny` 的站点策略）。**环境层**：让任务把 `env`、`pwd`、退出码写进文件——cron 的环境只有 `HOME`/`LOGNAME`/`PATH`/`LANG`/`SHELL=/bin/sh`/`PWD` 这几项，没有 profile，`PWD` 是账号 home，命令里的 `%` 必须写成 `\%`。**业务层**：退出码与产物。**条件会变**：如果 `CMD` 行出现了但结果是错的，问题在环境或业务，与调度无关。

**一句话结论**：先分清「没触发」还是「触发了但失败」，再谈改什么。

**出处**：`man 5 crontab`、`man 8 cron`；原文作者实测（Ubuntu 24.04 / cron 3.0pl1）：环境变量仅六项、`%` 需转义、`journalctl -u cron` 显示的是反转义后的命令。

## 14. 「`/tmp` 里四十天没改的老文件没被清，清理没生效」

**场景**：`/tmp` 里堆着旧文件，`/usr/lib/tmpfiles.d/tmp.conf` 里写的是 `D /tmp 1777 root root 30d`，同事用 `touch -d "40 days ago"` 造了个老文件，跑清理却没删掉。

**常见误判**：认为「修改时间超过 30 天」就该被清。它看起来成立，因为 `age` 字面上就是「多老」。

**判据**：`age` 缺省判据是**多个时间戳里只要有一个比阈值新就不清**（目录项默认忽略 ctime，因为清理动作本身会刷新它）。`touch` 会把 ctime 刷新成现在，于是「40 天前的 mtime + 今天的 ctime」不会被清。用 `stat -c "%n mtime=%y ctime=%z"` 就能看到这个差；把规则写成 `m:30d`（只看 mtime）后就按预期清理。**条件会变**：如果文件确实很旧而清理没生效，还要确认清理任务有没有跑（`systemctl list-timers systemd-tmpfiles-clean.timer`）以及规则是否被 `/etc/tmpfiles.d/` 下的同名文件覆盖（用 `systemd-tmpfiles --cat-config` 看生效来源）。**另一处误判**在同一个现象上：本机 `/tmp` 不是 tmpfs 时，「重启就会清空 `/tmp`」不成立——先 `findmnt -T /tmp` 确认。

**一句话结论**：`age` 看的不止 mtime；「清理没生效」常常是判据选了别的戳。

**出处**：`man 5 tmpfiles.d`（`age`/`age-by` 及各前缀）、`man 8 systemd-tmpfiles`；原文作者实测同上。

## 第一反应不要做什么

不要把文件写完当成生效；不要用 `verify` 的退出码当合格证明；不要改 `limits.conf` 解决服务 rlimit；不要用「进程在不在」判断服务状态；不要把「日志打印 ready」当通知；不要把监听当成单元在运行；不要把 `start` 返回 0 当业务可用；不要在没解释清楚前调大 `StartLimitBurst=`；不要用 `stop` 验证 `Restart=`；不要把 `restart` 当观察手段；不要把 `disable` 当 `mask`；不要用 `KillMode=none` 让关机快一点；不要先怪 cron；不要删掉 `/tmp` 清理规则。

## 要点自测

**问：`daemon-reload` 之后 `show` 是新值、服务行为却没变，下一步查什么？**
答：查进程侧：`/proc/<MainPID>/environ`、`/proc/<MainPID>/limits`、`MainPID` 是否变过。manager 与进程是两份状态，重启才会重新应用启动期配置。

**问：`systemd-analyze verify` 退出码 0，能说明 unit 没问题吗？**
答：不能。键名拼错或写错小节只产生 `Unknown key name ... ignoring` 一行提示，退出码仍是 0，那项配置被丢弃。

**问：`Type=notify` 的服务为什么会在打印 ready 之后等满超时？**
答：通知的发送者身份不符合 `NotifyAccess=`（缺省 `main`）的资格，例如由子进程或包装器发出。日志里会有「只允许主 PID」一类记录。`systemd-notify` 命令行工具会伪造身份，所以手工测试可能通过。

**问：服务反复崩溃后 `start` 直接失败，先做什么？**
答：读 `show -p Result -p NRestarts -p StartLimitBurst -p StartLimitIntervalUSec` 与含 `Start request repeated too quickly.` 的日志，确认是节流；先解释反复失败的原因，再 `reset-failed` + `start`。

**问：`active (running)` 之后还要取哪些证据？」
答：端口是否监听（`ss -lntp`）、日志里有没有就绪信号、依赖与下游是否可达。systemd 的判定只覆盖「启动动作完成」。

**第一反应不要做什么**：见上一节汇总——核心是「先取证、后动手；先分清是哪一层的问题，再改配置」。
