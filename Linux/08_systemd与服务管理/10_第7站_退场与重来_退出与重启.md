## 0. 30 秒速览

> [!abstract] 这一篇只要记住七句话
> - **退出码决定两件事**：systemd 报「成功还是失败」，以及 `Restart=on-failure` 这类策略要不要触发。默认只有退出码 0（以及部分信号语义）算成功，可以用 `SuccessExitStatus=` 扩展。
> - **`Restart=` 默认 `no`**：`on-failure` 只在非 0 退出/被信号杀/超时等「失败」时重启，**退出码 0 不重启**；`always` 才会无论怎么退出都重启。
> - **`systemctl stop` 主动停止不触发 `Restart=`**（除非用 `RestartForceExitStatus=` 之类的额外声明）——这是设计，避免你停不掉服务。
> - **停止是「先礼后兵」**：默认先给 `KillMode=control-group` 里所有进程发 SIGTERM，等 `TimeoutStopSec=`（本机系统级实测默认 `TimeoutStopUSec=1min 30s`），到点再 SIGKILL 整个控制组。
> - **`ExecStop=` 跑在信号之前**：本机实测顺序是 `ExecStop=` → 给残留进程发 `KillSignal=` → `ExecStopPost=`；也就是说写了 `ExecStop=` **不会**取消默认的信号行为。
> - **`RestartSec=` 默认 100ms**（实测 `RestartUSec=100ms`），太短会变成重启风暴；生产上至少 1s，并配合启动节流。
> - **启动节流兜底**：`StartLimitIntervalSec=`（窗口，默认 10s）内超过 `StartLimitBurst=`（默认 5 次）就报 `Start request repeated too quickly.`，不再重试并进入 `failed`。**这两个键写在 `[Unit]`，写错段会被静默忽略**（本机实测 `systemd-analyze verify` 只给 `Unknown key name ... in section 'Service', ignoring.`，退出码仍是 0）。
> - **恢复要先解释「为什么反复失败」**：`systemctl reset-failed <unit>` 只是清掉失败计数让下次能试，**不是修复**；调大 `StartLimitBurst` 只是止血。

## 1. 什么算「失败」

systemd 对「成功」的判定比 shell 严格一点，因为它还要考虑信号：

| 退出方式 | 默认算 | 说明 |
| --- | --- | --- |
| `exit 0` | 成功 | `Result=success` |
| `exit 非 0` | 失败 | `Result=exit-code`、`ExecMainStatus=<码>` |
| 被信号杀死 | 失败 | `Result=signal`、`code=killed` |
| 启动/停止超时 | 失败 | `Result=timeout` |
| 被 OOM 杀 | 失败 | `Result=oom-kill` |

可以用 `SuccessExitStatus=` 把某些退出码或信号「改判」为成功（例如某些程序把「正常结束」定义成非 0 退出）。反过来，`RestartPreventExitStatus=` 让指定退出码**不触发**重启，`RestartForceExitStatus=` 让指定退出码**强制**触发重启。

```bash
systemctl show myapp.service -p Result -p ExecMainCode -p ExecMainStatus -p NRestarts \
  -p SuccessExitStatus -p Restart -p RestartUSec
```

## 2. 停止：谁被杀、等多久

| 选项 | 默认（本机系统级实测 systemd 255） | 作用 |
| --- | --- | --- |
| `KillMode=` | `control-group` | 停止时给**整个 cgroup** 里的进程发信号（含子进程），不留孤儿 |
| `KillSignal=` | `15`（SIGTERM） | 先发这个信号，给应用机会优雅退出 |
| `SendSIGKILL=` | `yes` | 超时后补 SIGKILL |
| `TimeoutStopSec=` | `1min 30s`（`TimeoutStopUSec`） | 从 SIGTERM 到 SIGKILL 的等待时间 |
| `ExecStop=` | 无（默认只发信号） | 自定义停止命令；**它跑在信号之前**，不会取消默认信号 |
| `ExecStopPost=` | 无 | 收尾命令，在进程被清掉之后运行（无论成功失败） |

`KillMode=` 的取值：

| 取值 | 杀谁 | 适用 |
| --- | --- | --- |
| `control-group`（默认） | 服务 cgroup 内所有进程 | 绝大多数服务；保证不留子进程 |
| `mixed` | 主进程 SIGTERM，cgroup 内其它进程 SIGKILL | 需要保留/清理伴生进程的特殊场景 |
| `process` | 只杀主进程 | 子进程要交给别人管的场景（如某些守护进程派生的工作进程） |
| `none` | 只执行 `ExecStop=`，不发信号 | 完全自己控制停止流程 |

> [!important] 为什么「服务停了，子进程还在」或「子进程被杀」都可能是 `KillMode` 的锅
> 默认 `control-group` 会**连子进程一起清掉**——这是好事（不留孤儿），但如果你的服务依赖一个外面启动的伴生进程，它也会被带走。反过来，如果你看到「stop 之后还有残留进程」，要先 `systemctl show -p KillMode` 和 `systemctl status` 的 `CGroup`/`Tasks` 行，而不是直接 `kill`。

优雅退出的正确做法：

```ini
[Service]
KillSignal=SIGTERM
TimeoutStopSec=30s
ExecStop=/usr/local/bin/myapp-shutdown-hook   # 可选：需要额外动作时
ExecStopPost=/usr/local/bin/myapp-cleanup     # 可选：无论成败都跑
```

> [!warning] `ExecStart=`/`ExecStop=` 里的 `%` 是 **systemd 的**，不是 shell 的
> unit 文件里的 `%x` 会被 systemd 当成「说明符（specifier）」先展开，**单引号也拦不住**。本机实测：`ExecStart=/bin/bash -c 'echo $(date +%T.%N)'` 实际执行成了 `date +/tmp.lab08b-pct`（`%T` = 临时目录、`%N` = 去掉后缀的单元名）；`date +%s` 会变成 `date +/usr/bin/bash`（`%s` = 用户 shell）。**而且 `systemd-analyze verify` 退出码仍是 0，不会报错**——脚本在命令行能跑、放进 unit 就输出垃圾，往往就是这里。
> 正确写法是把 `%` 写成 `%%`：`ExecStart=/bin/bash -c 'echo $(date +%%T.%%N)'` → 实测输出 `08:07:49.202153541`。同理 `$$` 会被展开成一个字面 `$`（本机实测 `pid=$$` 变成 `pid=$`），要写 `$$$$`。
> 常用说明符：`%t`=`/run`、`%T`=`/tmp`、`%S`=`/var/lib`、`%C`=`/var/cache`、`%L`=`/var/log`、`%n`=完整单元名、`%N`=去掉类型后缀的单元名、`%i`=实例名、`%s`=用户 shell、`%d`=credentials 目录。目录类说明符的用法见子笔记 13。

让应用有机会收尾的前提是：**应用要真的处理 SIGTERM，并尽快退出**。进程收到 SIGTERM 后「多久内退出才算优雅」是应用自己的事；systemd 只负责**等 `TimeoutStopSec=`、然后 SIGKILL**。如果应用要 60 秒才能收尾，就把超时调大到比它长，而不是反过来抱怨 systemd 杀得急。

### 2.1 三种停止现场：实测对照

以下三组都是本机用自建 system 单元跑出来的（`systemctl stop` 后立刻取证）。

**① 应用处理 SIGTERM：优雅退出，`Result=success`。** 单元脚本里 `trap 'echo GOT-TERM >> …; exit 0' TERM`，主循环是 `while true; do sleep 0.2; done`：

```text
$ systemctl start lab08b-trap3.service; sleep 1; systemctl stop lab08b-trap3.service
$ cat /tmp/lab08b-trap3.log
STARTED
GOT-TERM
$ systemctl show lab08b-trap3.service -p KillMode -p KillSignal -p TimeoutStopUSec
KillMode=control-group
KillSignal=15
TimeoutStopUSec=1min 30s
```

**② `KillMode=process`：主进程被杀，子进程留下来变孤儿。** 单元用 `ExecStart=/bin/bash -c 'sleep 300 & echo $! > /tmp/lab08b-child.pid; while true; do sleep 0.5; done'`：

```text
$ systemctl stop lab08b-kmproc.service
$ ps -o pid,ppid,stat,cmd -p 10381
    PID    PPID STAT CMD
  10381       1 S    sleep 300        # 父进程没了，PPID=1，成了孤儿
$ systemctl show lab08b-kmproc.service -p ActiveState -p SubState -p Tasks
ActiveState=inactive
SubState=dead                          # 单元自己「干净地」停了，但机器上多了个 sleep
```

同一份 `sleep 300 &` 换成默认的 `KillMode=control-group`，`systemctl stop` 之后 `ps -p <child>` 只剩表头——**子进程被一起收走了**。

**③ 应用不处理 SIGTERM：超时才 SIGKILL，`Result=timeout`。** 单元设 `TimeoutStopSec=3`，脚本里 `trap "" TERM`：

```text
$ systemctl show lab08b-stubborn.service -p TimeoutStopUSec -p KillSignal -p SendSIGKILL
TimeoutStopUSec=3s
KillSignal=15
SendSIGKILL=yes
$ time systemctl stop lab08b-stubborn.service
stop took: 3.135390399 s
$ journalctl -u lab08b-stubborn.service -b --no-pager -o cat | tail -6
lab08b-stubborn.service: State 'stop-sigterm' timed out. Killing.
lab08b-stubborn.service: Killing process 10543 (bash) with signal SIGKILL.
lab08b-stubborn.service: Killing process 10649 (sleep) with signal SIGKILL.
lab08b-stubborn.service: Main process exited, code=killed, status=9/KILL
lab08b-stubborn.service: Failed with result 'timeout'.
Stopped lab08b-stubborn.service - lab08b ignores SIGTERM.
```

三点读法：① `stop` 的耗时几乎等于 `TimeoutStopSec=`（3.135 秒 vs 3 秒），**这就是「关机卡在 stop job」时屏幕上那一分钟的来源**；② `Result=timeout` 而不是 `success`，单元会进 `failed`（`is-system-running` 因此变 `degraded`）；③ 日志里 `State 'stop-sigterm' timed out. Killing.` 是判定「该调 `TimeoutStopSec=` 还是该修应用」的关键一行。

**`ExecStop=` / `ExecStopPost=` 的顺序也实测了**。单元同时设 `ExecStop=`（写 `EXECSTOP-RAN`）与 `ExecStopPost=`（写 `EXECSTOPPOST-RAN`），主进程在 trap 里写 `MAIN-GOT-TERM`：

```text
$ cat /tmp/lab08b-life.log
MAIN-STARTED
EXECSTOP-RAN
MAIN-GOT-TERM
EXECSTOPPOST-RAN
```

顺序是 **`ExecStop=` → `KillSignal=`（SIGTERM）→ `ExecStopPost=`**。工程含义：`ExecStop=` 适合写「停之前要做的动作」（摘流量、通知上游、让应用开始 drain），**它不是「替代信号」的开关**；`ExecStopPost=` 才是「无论怎么退出都要跑的收尾」（清 pid 文件、回收临时目录），因为它连启动失败/被 SIGKILL 的情况都会跑。

## 3. 重来：`Restart=` 的取值与陷阱

| 取值 | 什么时候重启 | 适用 |
| --- | --- | --- |
| `no`（默认） | 从不 | 一次性任务、由别人决定生命周期的服务 |
| `on-success` | 只在退出码 0 时 | 少见 |
| `on-failure` | 非 0 退出、被信号杀、超时、OOM 等 | **生产常驻服务的常用选择** |
| `on-abnormal` | 被信号杀、超时等「非正常」结束 | 退出码自身有意义时 |
| `on-abort` | 只在收到未被捕获的致命信号时 | 少见 |
| `on-watchdog` | 看门狗超时时 | 配合 `WatchdogSec=` |
| `always` | 无论怎么退出 | 必须常驻、退出即异常的场景 |

```ini
[Service]
Restart=on-failure
RestartSec=2s
```

> [!warning] 三个反直觉的行为
> ① **`systemctl stop` 不触发 `Restart=`**：主动停止是「我要它停」，重启是「它自己死了要拉回来」，两者不应该混。
> ② **`Restart=on-failure` 不会因为退出码 0 重启**：如果服务「正常退出」但其实应该一直跑，要用 `always` 或修应用。
> ③ **`RestartSec=` 默认只有 100ms**：崩溃循环会变成每秒十次的重启风暴，日志和 CPU 都被打满。生产上 `RestartSec>=1s` 并配合节流。

## 4. 启动节流：反复重启之后为什么不重启了

这是排查里最容易被误判成「systemd 卡了」的现象。本机实测现场（**系统单元**）：`ExecStart=/bin/false`、`Restart=always`、`RestartSec=1`、`[Unit]` 里 `StartLimitIntervalSec=10`、`StartLimitBurst=3`。

```text
$ systemctl start lab08b-flap.service; sleep 8
$ systemctl show lab08b-flap.service -p Result -p NRestarts -p StartLimitIntervalUSec -p StartLimitBurst -p ActiveState -p SubState -p ExecMainStatus
Result=exit-code
NRestarts=3
StartLimitIntervalUSec=10s
StartLimitBurst=3
ActiveState=failed
SubState=failed
ExecMainStatus=1
$ journalctl -u lab08b-flap.service -b --no-pager -o cat | tail -5
lab08b-flap.service: Scheduled restart job, restart counter is at 3.
lab08b-flap.service: Start request repeated too quickly.
lab08b-flap.service: Failed with result 'exit-code'.
Failed to start lab08b-flap.service - lab08b flap.
```

恢复要**先清掉失败计数再启动**（这一步必须做，否则 `start` 会被直接拒绝）：

```bash
systemctl reset-failed lab08b-flap.service     # 验证：Result/NRestarts 归零
systemctl show lab08b-flap.service -p Result -p NRestarts -p ActiveState   # 实测 Result=success、NRestarts=0、inactive
```

两个容易搞反的行为也在系统级复核过：

```text
$ systemctl show lab08b-always.service -p Restart -p RestartUSec -p NRestarts   # Restart=always, RestartSec=5
Restart=always
RestartUSec=5s
NRestarts=0
$ systemctl stop lab08b-always.service; sleep 6
$ systemctl show lab08b-always.service -p NRestarts -p ActiveState -p SubState
NRestarts=0
ActiveState=inactive
SubState=dead          # 主动 stop 不会触发 Restart=，重启计数也没涨

$ systemctl show lab08b-ok.service -p Result -p NRestarts   # Restart=on-failure 且脚本 exit 0
Result=success
NRestarts=0
ActiveState=inactive   # 退出码 0 不算失败，不会重启
```

处置顺序（**先解释，再动手**）：

1. **看现场**：`show -p Result -p NRestarts -p StartLimitBurst -p StartLimitIntervalUSec`，`journalctl -u | grep -E "Scheduled restart|Start request repeated|Failed with result"`。
2. **找根因**：为什么它会反复失败？启动脚本、配置、依赖未就绪、端口被占、权限、`Type=` 写错。
3. **修根因**，再 `reset-failed` + `start`。
4. **只有在「已知根因、正在修复、需要临时放宽」时**才用 `systemctl edit` 调大节流参数，并且记一笔「这是止血，不是修复」。

```bash
systemctl show myapp -p Result -p NRestarts -p StartLimitBurst -p StartLimitIntervalUSec
journalctl -u myapp -b --no-pager | grep -E "Scheduled restart|Start request repeated|Failed with result"
systemctl reset-failed myapp        # 清除失败状态与计数后才能再次启动
```

> [!warning] `StartLimitIntervalSec`/`StartLimitBurst` 写在 `[Unit]`
> 写进 `[Service]` 时 `systemd-analyze verify` **只提示** `Unknown key name 'StartLimitIntervalSec' in section 'Service', ignoring.`，**退出码依然是 0**（本机实测）——配置被静默忽略，于是「我明明设了 3 次」而实际还是默认值。这是 unit 排错里最隐蔽的一类问题：**别把 `verify` 的退出码当成判据，要看它的输出文本。**

### 实验 7：`start-limit-hit` 与 `reset-failed`

> [!example]- 实验 7：亲手制造一次「反复重启后彻底不重启」
> **怎么做**：建一个**系统**单元 `lab08b-flap.service`：`Type=simple`、`ExecStart=/bin/false`、`Restart=always`、`RestartSec=1`，并在 `[Unit]` 写 `StartLimitIntervalSec=10`、`StartLimitBurst=3`。`daemon-reload` 后 `start`，等 8 秒，观察 `Result`/`NRestarts` 与日志里的 `Start request repeated too quickly.`；再 `reset-failed` 并 `start`。**顺带对照三件事**：① 把 `StartLimitBurst=` 挪进 `[Service]`，看 `systemd-analyze verify` 的提示与**退出码 0**；② 另建一个 `Restart=always` 的单元，`systemctl stop` 后确认 `NRestarts` 不涨；③ 再建一个 `Restart=on-failure` 且 `exit 0` 的单元，确认 `Result=success` 且不重启。
> **预期**：`NRestarts=3`、`Result=exit-code`、`ActiveState=failed`；`reset-failed` 后 `Result=success`、`NRestarts=0`、可再次启动（然后再次失败，除非修根因）；`[Service]` 里的 `StartLimit*` 只得到一条 `ignoring` 提示。
> **风险**：中（会真的制造重启风暴，但只影响你自己的单元）；**耗时**：约 15 分钟；**回滚**：`reset-failed`、停单元、删 unit 文件、`daemon-reload`。
> 机器：可快照实验机（需要 root 建 system 单元）。**不要在生产机上用真实服务做这个实验**——它会真的制造重启风暴。
> 本机证据：`.labvm/evidence/08b_10_restart.out.txt`、`08b_10_kill.out.txt`。

## 生产动作：给常驻服务配一套退出与重启策略

> [!example]- 配置清单（改一项验一项）
> ```ini
> [Service]
> Restart=on-failure
> RestartSec=2s
> TimeoutStopSec=30s
> KillMode=control-group
> KillSignal=SIGTERM
> ExecStopPost=/usr/local/bin/myapp-cleanup
> SuccessExitStatus=0
> ```
> **验收顺序**：`daemon-reload` → `systemctl show -p Restart -p RestartUSec -p KillMode -p TimeoutStopUSec` 核对生效值 → 做一次 `restart` 观察中断时长 → 做一次 `stop` 确认进程与 cgroup 都被清干净（`systemctl status` 的 `Tasks: 0`，再用 `ps` 确认没有 PPID=1 的孤儿）。
> **回滚**：删掉 drop-in 对应几行，`daemon-reload` + `restart`。
> **注意**：`TimeoutStopSec=` 要比应用优雅退出所需时间更长，否则每次 stop 都会走到 SIGKILL（本机实测 `TimeoutStopSec=3` 时 stop 耗时 3.135 秒并留下 `Result=timeout`）。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 「服务重启几次后不动了，肯定是 systemd 卡了」 | 是启动节流：`StartLimitBurst` 触顶后报 `Start request repeated too quickly.` |
| 直接把 `StartLimitBurst` 调到很大 | 只是让重启风暴继续，日志与 CPU 被打满；根因还在 |
| 以为 `reset-failed` 是修复 | 它只清失败计数让你能再试一次；根因不修，现象会重现 |
| `Restart=on-failure` 却期望「退出码 0 也重启」 | 退出码 0 不算失败；要 `always`（本机实测 `Result=success`、`NRestarts=0`） |
| `RestartSec=` 保持默认 100ms | 崩溃循环会变成每分钟几百次重启 |
| 用 `KillMode=process` 想「保留子进程」 | 子进程会变成孤儿（本机实测 `sleep 300` 的 `PPID` 变成 1，而单元显示 `inactive/dead`）；除非明确知道谁接管，否则用默认 `control-group` |
| `TimeoutStopSec=` 比应用收尾时间短 | 每次停止都会走到 SIGKILL（本机实测 3.135 秒、`Result=timeout`、日志 `State 'stop-sigterm' timed out. Killing.`），应用没机会落盘/关连接 |
| 以为写了 `ExecStop=` 就不会再发 SIGTERM | 实测顺序是 `ExecStop=` → SIGTERM → `ExecStopPost=`；`ExecStop=` 不改变信号行为 |
| 把收尾动作写成 `ExecStop=` | 启动失败/被 SIGKILL 时它**不会**跑；这类动作应放 `ExecStopPost=` |
| 用 `systemctl stop` 想验证 `Restart=` | 主动停止不触发 `Restart=`（实测 `NRestarts` 保持 0），这是设计 |
| `StartLimitBurst=` 写进 `[Service]` | 被静默忽略，且 `systemd-analyze verify` **退出码仍为 0**；判据是输出里的 `Unknown key name ... ignoring.` |
| 在 `ExecStart=`/`ExecStop=` 里写 `date +%T` 或 `date +%s` | `%T`/`%s` 会被 systemd 当说明符展开（`%T`=`/tmp`、`%s`=用户 shell），命令静默出错；要写 `%%T`/`%%s` |

## 决策练习

> [!question]- 场景：一个服务在凌晨反复重启，日志里刷满启动失败信息，最后一次失败后彻底不再重启，需要人工拉起。你到现场时它已经是 `failed`。
> A. 先 `systemctl reset-failed` + `start`，把它拉起来，回头再查
> B. 先看 `Result`/`NRestarts`/`StartLimit*` 与 `journalctl -u` 的失败原因，必要时保留当前现场，再决定是否 `reset-failed`
> C. 直接把 `StartLimitBurst` 调到 100，让它多试几次
> **答案：B。**
> A 可能有效，但会让现场信息（`Result`、最后几轮日志）被覆盖，且根因未明。
> C 是放大重启风暴，只会让日志与资源更乱。
> B 是正解：**先把「为什么反复失败」解释清楚，再决定止损动作**；`reset-failed` 本身不是修复。

## 要点自测

> [!question]- `Restart=` 各取值的区别？为什么 `systemctl stop` 不会触发重启？
> - `no` 从不重启；`on-failure` 只在失败（非 0、信号、超时、OOM）时重启；`on-abnormal`/`on-abort`/`on-watchdog` 对应更窄的条件；`always` 无论怎么退出都重启。
> - `stop` 是「主动停止」，语义是「我要它停」；如果它也触发 `Restart=`，你就永远停不掉服务。
> - 想覆盖这个行为可以用 `RestartForceExitStatus=`/`RestartPreventExitStatus=` 精细指定。
> - **第一反应不要是什么**：不要用 `Restart=always` 兜底一切——退出码 0 也会重启，可能掩盖正常结束。

> [!question]- 服务反复重启然后彻底不重启，怎么解释、怎么恢复？
> - 解释：`Restart=` 触发重启；在 `StartLimitIntervalSec` 窗口内超过 `StartLimitBurst` 次后，systemd 报 `Start request repeated too quickly.` 并停止重试（本机系统级实测 `NRestarts=3`、`Result=exit-code`、`ActiveState=failed`、`StartLimitIntervalUSec=10s`）。
> - 恢复：`systemctl reset-failed <unit>` 清掉失败状态与计数（实测随即变成 `Result=success`、`NRestarts=0`），再 `start`；但真正要做的是修根因。
> - 诊断：`show -p Result -p NRestarts -p StartLimitBurst -p StartLimitIntervalUSec` + `journalctl -u`。
> - **第一反应不要是什么**：不要直接把 `StartLimitBurst` 调到很大——那只是让故障持续输出日志与重启风暴。

> [!question]- 默认停止流程是什么样的？`KillMode=control-group` 意味着什么？`ExecStop=` 在流程里的哪一步？
> - 对 cgroup 内所有进程发 `KillSignal=`（默认 `15`/SIGTERM），等 `TimeoutStopSec=`（默认 `1min 30s`），到点补 SIGKILL。
> - `control-group` 意味着**连子进程一起收干净**，避免孤儿；代价是外部启动的伴生进程也会被带走。换成 `KillMode=process` 后，本机实测那个 `sleep 300` 的 `PPID` 直接变成 1，而 `systemctl status` 显示单元已经干净地 `inactive/dead`——**单元「正常」，机器上却多了个孤儿**。
> - 实测顺序是 `ExecStop=` → SIGTERM → `ExecStopPost=`；`ExecStop=` 不是「取消信号」的开关，`ExecStopPost=` 才是「无论成败都跑」的收尾位。
> - 让服务优雅退出的关键是应用真的处理 SIGTERM，并把 `TimeoutStopSec=` 设得比它收尾时间更长。
> - **第一反应不要是什么**：不要一看到「子进程也被杀了」就把 `KillMode` 改成 `none`，先看这个子进程该由谁管。
