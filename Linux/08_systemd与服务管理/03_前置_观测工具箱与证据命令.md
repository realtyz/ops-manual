## 0. 30 秒速览

> [!abstract] 这一篇只要记住六句话
> - **排障先读 `systemctl status` 的四行**：`Loaded`（文件在哪、是否 masked）、`Active`（当前状态与 `Result`）、`Main PID`/`Process`（退出码）、`CGroup`/`Tasks`（有没有残留）。**重启会覆盖现场**。
> - **看配置要分两层**：`systemctl cat` 看「生效内容 = 原文件 + drop-in」，`systemctl show -p …` 看「manager 里此刻的值」。文件里有、`show` 里没有，就是没生效。
> - **`list-*` 建全景**：`list-units`（运行态）、`list-unit-files`（安装态与自启）、`list-dependencies`（依赖树）、`list-sockets`（按需激活）、`list-timers`（定时）、`list-jobs`（卡在哪一步）。
> - **`journalctl -u <unit> -b` 是服务日志的标准入口**；`-b -1` 看上一次启动，`--since` 按窗口，`-p err` 按级别，`-o json` 暴露字段（如 `_SYSTEMD_UNIT`、`__MONOTONIC_TIMESTAMP`）。
> - **`systemd-analyze` 一个命令解决一类问题**：`verify`（语法）、`unit-paths`（路径优先级）、`exit-status`（退出码含义）、`calendar`/`timespan`（时间表达式）、`blame`/`critical-chain`（开机）、`security`（暴露面）。
> - **systemd 的退出码是「它自己哪一步失败了」**：实测 `200/CHDIR`、`203/EXEC`、`216/GROUP`、`217/USER`、`226/NAMESPACE`，各指向一个具体配置项；完整映射用 `systemd-analyze exit-status <code>` 查（本机输出是一张 `NAME / STATUS / CLASS` 表，`CLASS` 为 `systemd` 的是 systemd 自己报的码，`libc` 的才是进程真实退出码）。

## 1. 命令地图：先分清「看什么」

这一章的命令可以按「回答什么问题」分成四组，别背参数，先记问题：

| 你想知道 | 用什么 | 关键点 |
| --- | --- | --- |
| 这个服务现在什么状态、上次怎么失败的 | `systemctl status <unit>` | 四行信息 + 最近日志 |
| **生效配置**是什么、从哪来 | `systemctl cat`、`systemctl show -p …` | `cat` 看内容，`show` 看值 |
| 机器上有哪些 unit、哪些自启、依赖谁 | `list-units`/`list-unit-files`/`list-dependencies`/`list-sockets`/`list-timers` | 「状态」与「安装态」是两回事 |
| 服务说了什么、系统当时发生了什么 | `journalctl -u <unit> -b` | 按单元、按 boot、按字段 |
| 这个配置文件合法吗、退出码什么意思、时间表达式何时触发 | `systemd-analyze <子命令>` | 瑞士军刀，见第 6 节 |

> [!tip] 本目录的命令示例有一条固定约定
> 正文里不带 `--user` 的 `systemctl` 示例都指 **system 单元**；实验里的 `lab08-*` 也**全部是 system 单元**（本机有 root，实验都做系统级实测），所以照着敲时**不要加** `--user`。加错会得到「命令没报错，但取不到想要的值」——两棵 manager 各有自己的 unit 集合，互相看不见。用户级只在第 1 篇作对照出现。

## 2. `systemctl status`：先读四行

```bash
systemctl status myapp.service --no-pager -l
```

输出里真正要读的是四段。下面是本机 `ssh.service` 的真实输出（只读命令，生产机可做）：

```text
● ssh.service - OpenBSD Secure Shell server
     Loaded: loaded (/usr/lib/systemd/system/ssh.service; disabled; preset: enabled)   ← ① 文件在哪、是否自启、preset
     Active: active (running) since Sat 2026-09-19 07:20:10 UTC; 55min ago           ← ② 当前状态 + Result
TriggeredBy: ● ssh.socket                                                             ← 补充：它是被谁触发的（此处是 socket 激活）
       Docs: man:sshd(8)
             man:sshd_config(5)
```

一次失败的服务长这样（本机实测 `lab08-sec-rwmissing.service`）：

```text
● lab08-sec-rwmissing.service - lab08 ReadWritePaths to a missing path
     Loaded: loaded (/etc/systemd/system/lab08-sec-rwmissing.service; static)
     Active: failed (Result: exit-code) since ...                                     ← ② 当前状态 + Result
    Process: 12345 ExecStart=/bin/sleep 60 (code=exited, status=226/NAMESPACE)        ← ③ 退出码：哪一步、什么码
   Main PID: 12345 (code=exited, status=226/NAMESPACE)
      Tasks: 0 (limit: 9374)                                                          ← ④ cgroup 里还剩几个进程（残留）
     CGroup: /system.slice/lab08-sec-rwmissing.service
```

1. **`Loaded`**：`loaded (...)` 正常；`not-found` 是文件不存在/名字错/没 reload；`masked` 是被屏蔽；括号里还有自启状态（`enabled`/`disabled`/`static`）与 `preset`。
2. **`Active`**：`active (running)`/`active (exited)`/`inactive (dead)`/`failed`，以及括号里的 `Result`（如 `exit-code`、`timeout`、`signal`、`resources`）。
3. **`Process` / `Main PID`**：`code=exited, status=…` 或 `code=killed, signal=…`；**这里的 `status=` 是 systemd 的退出码体系**，见第 7 节。
4. **`Tasks` / `CGroup`**：服务停了但 `Tasks` 不为 0，说明还有子进程没被清掉；`CGroup:` 是它在 cgroup 树里的位置（子笔记 07）。

想只取结构化字段（适合脚本与巡检）时，用同一组属性名：

```bash
systemctl show myapp.service -p LoadState -p ActiveState -p SubState -p Result \
  -p ExecMainCode -p ExecMainStatus -p NRestarts -p FragmentPath -p DropInPaths
```

> [!tip] 第一反应不要是「再 `restart` 一次看看」
> `restart` 会清掉上一轮的失败状态与部分现场（`Result`、`NRestarts`、上一进程的输出）。**先把上面四行和 `journalctl -u` 读完**，再决定是否重启。

## 3. `cat` 与 `show`：看生效配置

```bash
systemctl cat myapp.service                        # 验证：生效内容 = 原文件 + 所有 drop-in，按文件列出
systemctl show myapp.service -p FragmentPath -p DropInPaths
systemctl show myapp.service                       # 验证：manager 里此刻的全部属性（很长，配合 -p 用）
```

区别要记牢：

- **`cat` 看「文件内容」**：能看到 `[Unit]`/`[Service]` 原文与 drop-in，帮你确认「我改的是不是生效文件」。
- **`show` 看「manager 的值」**：unit 文件里的键会换算成具体属性（如 `MemoryMax=32M` → `MemoryMax=33554432`，`CPUQuota=10%` → `CPUQuotaPerSecUSec=100ms`）。**`show` 是验收标准，文件不是。**

一次性核对一个服务的「关键生效属性」：

```bash
systemctl show myapp.service -p Type -p Restart -p RestartUSec -p KillMode -p TimeoutStopUSec \
  -p LimitNOFILE -p MemoryMax -p CPUQuotaPerSecUSec -p ProtectSystem -p PrivateTmp \
  -p User -p Environment -p WorkingDirectory -p ExecMainStatus -p Result -p NRestarts
```

## 4. `list-*` 系列：建全景

| 命令 | 回答什么 | 只读？ |
| --- | --- | --- |
| `systemctl list-units --type=service` | 现在**运行态**有哪些服务 | 是 |
| `systemctl list-unit-files --type=service` | 磁盘上装了哪些 unit、**安装态**（enabled/disabled/masked/static） | 是 |
| `systemctl --failed` | 有没有失败的 unit（服务器日常巡检第一条） | 是 |
| `systemctl list-dependencies <unit>` | 它依赖谁、谁被它拉起（子笔记 05） | 是 |
| `systemctl list-sockets` | 有哪些按需激活的套接字（「inactive 但端口在听」的答案） | 是 |
| `systemctl list-timers --all` | 定时器下次/上次触发时间（子笔记 12） | 是 |
| `systemctl list-jobs` | 有没有卡住的启动/停止任务（开机卡住时看） | 是 |
| `systemctl is-system-running` / `is-active <unit>` / `is-enabled <unit>` | 系统或单个 unit 的一句话结论 | 是 |

```bash
systemctl --failed                                  # 验证：失败列表，健康机器输出为空
systemctl is-system-running                         # 验证：running / degraded / maintenance / starting
systemctl list-sockets --no-pager | head            # 验证：确认某个端口是不是 socket 激活在听
```

## 5. `journalctl`：按单元、按 boot、按字段

```bash
journalctl -u myapp.service -n 50 --no-pager        # 按单元，最近 50 行
journalctl -u myapp.service --since "10 min ago"    # 按时间窗口
journalctl -b -1 -n 20                              # 上一次启动（排「重启后才知道」的问题）
journalctl -p err -b --no-pager | tail -20          # 按级别：emerg/alert/crit/err/warning/notice/info/debug
journalctl -u myapp -o json -n 1 | python3 -m json.tool | head -12   # 看字段
```

`-o json` 的价值是**字段**而不是格式。实测一条 `sshd` 消息（system 单元）的字段：

```text
_HOSTNAME                linux-lab
_PID                     34466
_COMM                    sshd
_UID                     0
_GID                     0
SYSLOG_IDENTIFIER        sshd
_TRANSPORT               syslog
_SYSTEMD_UNIT            ssh.service        ← 系统单元用这个字段
_SYSTEMD_SLICE           system.slice
MESSAGE                  pam_unix(sshd:session): session opened for user root(uid=0) by root(uid=0)
__MONOTONIC_TIMESTAMP    4032173043
_BOOT_ID                 decad510b934454f9d61aef2aa2893fd
```

注意两个环境差异：**系统单元的字段是 `_SYSTEMD_UNIT` + `_SYSTEMD_SLICE`**，用户单元才会出现 `_SYSTEMD_USER_UNIT` + `_SYSTEMD_USER_SLICE`（查用户单元日志要加 `--user`，或用 `journalctl _SYSTEMD_USER_UNIT=...`）。排障常用：`_PID`/`_COMM` 定位是谁写的，`_SYSTEMD_UNIT` 定位是哪个单元，`__MONOTONIC_TIMESTAMP` 做**跨日志源的先后判定**（墙钟会被 NTP 调整，单调时钟不会）。日志的持久化、容量与限流在子笔记 09 展开。

## 6. `systemd-analyze`：一把瑞士军刀

| 子命令 | 回答什么 | 典型用法 |
| --- | --- | --- |
| `verify <unit>` | unit 文件语法/小节错、重复键、缺失依赖 | 改完配置第一步 |
| `unit-paths` | 搜索路径与优先级 | 确认「改哪份才生效」 |
| `cat-config <name>` | 把所有配置来源按顺序列出（含 drop-in） | 「改了配置没效果」时核对 |
| `exit-status [code]` | systemd 退出码含义 | 看到 `226` 不知道啥意思 |
| `calendar "expr"` / `timespan 1h30m` | 时间表达式归一化与下次触发 | 写 timer 前先验证 |
| `blame` / `critical-chain` | 开机各 unit 耗时 / 关键路径 | 开机慢 |
| `time` | 开机总耗时（firmware/loader/kernel/userspace） | 基线 |
| `security <unit>` | 安全暴露面评分 | 沙箱加固前后对比 |

本机实测几条：

```text
$ systemd-analyze exit-status 200 203 216 226
200 CHDIR
203 EXEC
216 GROUP
226 NAMESPACE

$ systemd-analyze calendar "*:0/15"
Normalized form: *-*-* *:00/15:00

$ systemd-analyze verify /etc/systemd/system/lab08-bad.service   # 系统级：把 StartLimitIntervalSec 写进 [Service]
/etc/systemd/system/lab08-bad.service:5: Unknown key name 'StartLimitIntervalSec' in section 'Service', ignoring.
verify_bad_rc=0
```

**`verify` 通过时是静默且退出码 0 的**；只要它说话了，就说明有东西被忽略或被拒绝。但**注意「说话了」也可能退出码 0**：上面那条未知键名就是 `verify_bad_rc=0`——配置被静默丢弃，命令却「成功」。所以脚本拿 `verify` 守门时要解析输出，或对关键属性再补一次 `systemctl show` 断言。

## 7. 退出码速查：systemd 自己失败在哪一步

服务失败时，`systemctl status` 里的 `status=` 有两种来源：**进程自己的退出码**（0–255 里的常规值，如 `1/FAILURE`），以及 **systemd 在启动过程中代替进程报的码**（200 段）。后者专指「systemd 没能把服务按你写的样子启动起来」：

| 退出码 | 名字 | 典型原因 | 先查什么 |
| --- | --- | --- | --- |
| `200` | `CHDIR` | 工作目录不存在或无权限 | `WorkingDirectory=` |
| `203` | `EXEC` | `ExecStart=` 的二进制不存在/不可执行/解释器缺失 | 路径、执行位、shebang |
| `216` | `GROUP` | 切换组/用户失败；用户单元里写了 `User=` 也会这样 | `User=`/`Group=`、用户是否存在 |
| `226` | `NAMESPACE` | 沙箱/挂载设置失败（`ReadWritePaths=` 路径不存在、`ProtectSystem` 与写入冲突） | `ProtectSystem=`、`ReadWritePaths=` |
| `1` | `FAILURE` | 进程自身返回 1；`ExecStartPre` 失败也常表现为它 | 应用日志 |
| `timeout`（`Result=`） | — | `Type=notify/dbus` 没收到就绪通知，或启动真的超时 | `Type=`、`NotifyAccess=`、`TimeoutStartSec=` |

```bash
systemd-analyze exit-status 200 203 216 226   # 验证：本机实测输出 CHDIR / EXEC / GROUP / NAMESPACE
systemd-analyze exit-status <你的码>          # 验证：其它码直接查，不确定就不要猜
```

## 8. 证据清单：哪些东西一 `restart`/重启就没了

排障的黄金法则是**先取证再动手**。这些证据是易失的：

| 证据 | 存放/来源 | 什么时候丢 |
| --- | --- | --- |
| 上一轮的 `Result`、`NRestarts`、退出码 | `systemctl show` | `restart` 或 `reset-failed` 后 |
| 服务上一进程的 stdout/stderr | `journalctl -u`（内存或 `/var/log/journal`） | 未持久化时重启即丢；被容量/限流挤掉时 |
| 进程环境 | `/proc/<pid>/environ` | 进程退出后 |
| cgroup 的实时占用 | `systemd-cgtop`、`/sys/fs/cgroup/...` | 服务停止后 |
| 上一次启动的系统日志 | `journalctl -b -1` | **未持久化时，本机重启即丢** |
| 时间同步状态 | `timedatectl`、`timesync-status` | 时钟随后被校正 |

```bash
ls -ld /var/log/journal     # 验证：存在 = 日志持久化；不存在 = 只存在内存，重启即丢（子笔记 09）
```

> [!warning] `restart` 不是查看问题的手段
> 新人最容易「服务有问题就 restart，反复几次还是不行」。正确的第一轮动作永远是：**读 `status` 四行 → `show` 关键属性 → `journalctl -u` 看退出码与最后几条输出 → 记录下这几项**，然后再决定动手。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 只看 unit 文件就下结论 | 生效配置 = 文件 + drop-in；`systemctl cat` 才是全貌 |
| `systemctl show` 不指定 `-p` | 输出几百行，抓不到重点；巡检时按属性名 `-p` 取 |
| 把 `list-units` 当成「装了哪些服务」 | 那是运行态；安装态要看 `list-unit-files` |
| 看到 `inactive (dead)` 就断定服务没跑 | 可能是 socket 激活或 `oneshot` 跑完，先 `list-sockets`/看 `Type=` |
| 用 `journalctl -u` 看内核报错 | 内核消息用 `-k`；`-u` 只筛某个 unit |
| 重启后才发现「上一次的日志没了」 | 未持久化时 `-b -1` 也不可用；要么开持久化，要么先取证 |
| 看到 `status=226` 就去改业务代码 | 这是 systemd 的 `NAMESPACE`，指向沙箱配置 |

## 决策练习

> [!question]- 场景：凌晨告警「myapp 服务 down」。你登录机器，`systemctl status myapp` 显示 `Active: failed (Result: exit-code)`，`Process: ... status=203/EXEC`。值班同事说「先 `systemctl restart` 一下看看能不能自愈」。
> A. 立刻 restart，观察是否能恢复
> B. 先记录 `status` 四行与 `journalctl -u myapp -b | tail -50`，确认 `203/EXEC` 指向哪个路径，再看该文件是否存在/可执行，然后再决定动作
> C. 直接把二进制路径改成绝对路径猜一个，重启
> **答案：B。**
> A 会覆盖失败现场，而且 `203/EXEC`（路径/执行位问题）不会因为重启而消失。
> C 是猜，可能引入第二个变量。
> B 是正解：**先取证定位到「systemd 没执行成功」这一层，再修那个具体路径**。详见子笔记 15。

## 要点自测

> [!question]- `systemctl cat` 和 `systemctl show` 有什么区别？各自什么场景用？
> - `cat` 打印**生效内容**：原文件 + drop-in 的原文，按文件来源分组，回答「systemd 读到的文本是什么」。
> - `show` 打印 **manager 里的属性值**：unit 键被换算成实际生效值（`32M`→字节、`10%`→周期配额），回答「systemd 此刻按什么值在执行」。
> - 场景：确认「我改的 drop-in 有没有被读到」用 `cat` + `DropInPaths`；验收「改的值真的生效了」用 `show -p`。
> - **第一反应不要是什么**：不要只看编辑器里的文件，也不要只信 `cat` 的输出——`show` 才是验收。

> [!question]- 服务失败时，`status=` 里的 `203/EXEC`、`226/NAMESPACE` 分别往哪想？
> - `203/EXEC`：systemd 没能执行 `ExecStart=`——路径不存在、没有执行位、解释器（shebang）缺失、二进制被删或换架构。
> - `226/NAMESPACE`：沙箱/挂载相关设置失败——最常见是 `ReadWritePaths=` 指向不存在的路径，或 `ProtectSystem=` 与服务的写入需求冲突。
> - 查法：`systemd-analyze exit-status <code>`；再看 `journalctl -u` 的前后几行，它通常直接点名是哪个选项。
> - **第一反应不要是什么**：不要把 systemd 的退出码当成应用退出码去查业务日志。

> [!question]- 为什么说「先取证再重启」？列出至少三类一重启就可能消失的证据。
> - 因为 `restart` 会重置 `Result`/`NRestarts`/上一进程输出，未持久化的日志与 `/proc` 现场也随进程消失。
> - 三类易失证据：① `show` 里的 `Result`/`NRestarts`/`ExecMainStatus`；② 服务上一进程的 stdout/stderr（未持久化时）；③ `/proc/<pid>/environ` 与 cgroup 实时占用。
> - 做法：`status` 四行 + `show -p …` + `journalctl -u` 先留档，最好把关键输出贴进工单/聊天记录。
> - **第一反应不要是什么**：不要用「重启一次试试」当诊断手段——那是在用动作代替信息。
