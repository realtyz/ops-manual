# 什么算启动完成

## 1. 判定权在 `Type=`，不在进程

一个服务是不是「起来了」，不由「进程存不存在」回答，而由 `Type=` 声明的那条判据回答。这是 systemd 里最强制约的一条：**同一条 `ExecStart=`，配上不同的 `Type=`，会得到相反的状态结论**。

一个进程被 `fork` 出来之后，systemd 只能靠 `Type=` 告诉它「等到哪一刻算完成」。于是进程干了什么、systemd 认为发生了什么，这两件事可以完全背离：

- 前台进程自己切到后台（`daemon()` 或 `&`）时，systemd 看到的是「主进程退出了」，于是判定为已结束——**服务被记为 `inactive (dead)`，而进程还在跑，或者已经被控制组一起清掉**；
- 一个根本不会 `fork` 的服务配上 `Type=forking`，systemd 会一直等父进程退出，等到超时——**服务最终 `failed`，而进程其实一直是好的**。

这两类现象在运维里都叫「假启动失败」：日志里没有业务错误，`status` 却给出否定结论。判据是 `systemctl show -p Type -p SubState -p Result -p MainPID`。

## 2. 八种取值各自等到哪一刻

| `Type=` | 判据：等到什么算完成 | 适用对象 |
| --- | --- | --- |
| `simple` | 主进程被 `fork` 出来（在它真正 `execve` 之前） | 前台常驻进程；**`ExecStart=` 已给且未写 `Type=`/`BusName=` 时的缺省值** |
| `exec` | 主进程的二进制真正 `execve` 成功 | 与 `simple` 同类型，但能区分「没执行起来」与「执行后很快退出」 |
| `forking` | 父进程退出、子进程留下 | 传统自后台化守护进程，可配 `PIDFile=` 定位主进程 |
| `oneshot` | 命令跑完且退出码为 0 | 一次性动作（迁移、初始化）；**未写 `Type=` 且未写 `ExecStart=` 时的缺省值** |
| `notify` | 服务通过 `sd_notify` 报告 `READY=1` | 支持通知协议的现代守护进程 |
| `notify-reload` | 同 `notify`，重载由服务用 `RELOADING=1`/`READY=1` 报告 | 需要把「重载完成」也纳入判定的服务（systemd ≥ 253） |
| `dbus` | 该单元在 D-Bus 上取得 `BusName=` 指定的名字 | 总线服务 |
| `idle` | 在其它启动任务跑完之后才执行 | 需要最后跑、且不能在启动阶段抢占控制台的脚本 |

`simple` 与 `exec` 的差别值得单独记住：`simple` 在 `fork` 返回后就认为启动完成，因此**「二进制不存在」「权限位不对」「工作目录不可进入」这类启动前错误不会被它归到启动失败里**；`exec` 会等 `execve` 成功，把这些设置阶段的错误暴露在启动判定中。文档因此建议长跑服务优先用 `Type=exec`——它不改变进程模型，只把判定点往后挪一点，让失败落在正确的地方。

## 3. `oneshot` 与「这件事做过了」

`Type=oneshot` 的单元跑完就结束，默认状态下会落到 `inactive (dead)`——**显示成未运行是正常的，不是失败**。要让它保持 `active`，加 `RemainAfterExit=yes`，此时状态是 `active (exited)`：进程已经退出，但 systemd 记住「这件事做过了」，别的单元可以放心依赖。

`oneshot` 还有三处与其他类型不同：

- **允许写多条 `ExecStart=`**（顺序执行）。其他类型只允许一条，写多条会被 verify 拒绝。
- **`Restart=always` 与 `Restart=on-success` 不被接受**：跑完即结束的单元没有「成功退出后重启」的语义。
- **启动超时默认是 `infinity`**。因为超时逻辑基于「启动后应当保持运行」，而 `oneshot` 本来就该结束。代价是**卡住的迁移脚本会一直停在 `activating`，永不超时**——核对启动耗时的证据只有日志，没有超时兜底。

## 4. `Type=notify` 与通知归属

`notify` 看似是最好的一种判定：服务自己说「我准备好了」，systemd 才认为启动完成。但它有一个容易被忽略的约束——**systemd 只接受「有资格的人」发的通知**，资格由 `NotifyAccess=` 决定：

| `NotifyAccess=` | 谁发的通知被接受 |
| --- | --- |
| `none` | 谁都不接受（缺省值）；但使用 `Type=notify` 或 `WatchdogSec=` 时会被隐式提升为 `main`，所以「用 `none` 关掉通知」是关不掉的 |
| `main` | 只接受主进程发的（`notify` 的缺省行为） |
| `exec` | 接受主进程与 systemd 启动的那些 `Exec*=` 进程发的 |
| `all` | 接受该单元控制组内任何进程发的 |

于是出现本章最典型的一类现象：**应用日志里明明打印了「ready」，systemd 却一直等到超时**。原因通常是通知是子进程（或包了一层 `sh -c`、`env`、`su` 的间接调用）发出的，归属不符合 `main` 的资格，被静默拒绝——日志里会有一行「收到的通知来自某 PID，但只允许主 PID」，随后是启动超时。把 `NotifyAccess=` 放到 `all` 能解决，但代价是放宽了「谁说就绪算数」的边界，等于把判定权让给了进程组里任何一员。

要理解这条约束，得知道通知的判定依据是什么：`sd_notify` 的消息体里**没有「我是谁」的字段**，systemd 完全依赖内核为发送方给出的凭证。所以只要发送者身份对不上，通知就无效——这与「消息内容是否正确」无关。

一个特例：`systemd-notify` 命令行工具在发送时会把自己的身份伪造成父进程，因此在 shell 里直接调用它，反而能被 `NotifyAccess=main` 接受。这也解释了为什么「手工验证时能通过、写进服务就不行」——手工验证时用的是这个工具，服务里用的是应用自己的通知代码。

**超时值的默认与后果**：`notify`/`dbus`/`exec`/`forking`/`simple`/`idle` 的启动超时都取 manager 的 `DefaultTimeoutStartSec=`（本机 systemd 255 为 `1min 30s`）。超时后 `Result=timeout`、`ActiveState=failed`，而**进程可能还在跑**。不要用调大超时来"修复"它——先确认通知有没有到达、归属对不对。

## 5. `Exec*` 各段的失败语义

一次启动里 systemd 会按顺序执行几段命令，每段失败的后果不同：

| 段 | 何时执行 | 返回非 0 的后果 |
| --- | --- | --- |
| `ExecStartPre=` | 主命令之前 | 启动失败，**不进 `ExecStart=`** |
| `ExecStart=` | 主命令 | 按 `Type=` 判定；`oneshot` 需退出码 0 |
| `ExecStartPost=` | 主命令之后 | 判定为启动失败 |
| `ExecReload=` | `systemctl reload` 时 | 重载失败 |
| `ExecStop=` | 停止时 | 记录失败；随后仍按 `KillMode=` 收进程 |

两条实务推论：

- **不要把可选的检查写进 `ExecStartPre=`**。它返回非 0 会让整个服务启动失败，所以检查逻辑必须自带重试与容错，否则「依赖偶尔还没好」会升级成「服务起不来」。
- **没有 `ExecReload=` 时，`reload` 会直接失败**，而不是悄悄改成重启。这一点在变更流程里必须事先确认，不能等到执行时才发现。

## 6. 不启动而「被触发」：socket 与 timer

有一类单元平时根本不在运行，被访问或到点时才被拉起。理解这一点是读懂「端口在听但服务是 `inactive`」的前提：

- **socket 激活**：`.socket` 单元持有监听套接字，第一个连接到达时才拉起对应的 `.service`。此时 `status` 显示 `inactive (dead)`，而端口确实在听——`TriggeredBy:` 行会指出触发它的是哪个 socket 单元。
- **timer 触发**：`.timer` 单元到点拉起对应的 `.service`，跑完就结束，因此 `list-timers` 上看到的 `LAST` 时间与 `.service` 的状态不同步。排查 timer 相关问题时，日志要查 `.service` 而不是触发器本身。
- 这类触发器的 `[Install]` 通常写 `WantedBy=sockets.target` 或 `WantedBy=timers.target`——开机时参与的是**触发器**，服务单元本身往往是 `static`（没有 `[Install]`，无法单独 enable）。

## 常见误解

| 常见说法 | 事实 |
| --- | --- |
| 「进程在跑，服务就是 active」 | 判定权在 `Type=`；`simple` 下后台化的进程会让服务被判 `inactive (dead)` |
| 「`inactive (dead)` 就是挂了」 | 可能是 `oneshot` 跑完、socket 激活、timer 刚跑完；先看 `Type=` 与 `TriggeredBy:` |
| 「不 `fork` 的程序配 `forking` 更稳」 | 会一直等父进程退出直到超时；`Type=` 必须匹配进程模型 |
| 「`Type=simple` 也能发现二进制不存在」 | 它在 `execve` 之前就算完成；要暴露这类错误用 `Type=exec` |
| 「`oneshot` 跑完显示 inactive 是失败」 | 正常；要让它保持 active 用 `RemainAfterExit=yes` |
| 「`oneshot` 也会超时」 | 启动超时默认 `infinity`；卡住时会永远停在 `activating` |
| 「日志打印了 ready，systemd 就该知道」 | 只有 `sd_notify` 通知算数，且发送者身份要符合 `NotifyAccess=` 的资格 |
| 「用 `NotifyAccess=none` 把通知关掉」 | `Type=notify`/`WatchdogSec=` 会把它隐式提升为 `main`，关不掉 |
| 「`systemd-notify` 能通过，服务里用同样的写法也行」 | 该工具会伪造发送者身份；包一层包装器（`sh -c`、`env`、`su`）就会被拒 |
| 「超时就是启动太慢」 | `notify`/`dbus` 的超时更常见是通知没到达或归属不符；先取证再谈超时值 |
| 「单位返回 0 就算启动成功」 | `start` 成功只说明 `Type=` 判定通过；端口、依赖、健康检查都可能没就绪 |
| 「socket 激活的服务是幽灵进程」 | 那是设计行为；`.socket` 持有监听，服务按需拉起 |
| 「`ExecStartPre=` 里可以放可选检查」 | 它返回非 0 会让整个服务启动失败 |
| 「`reload` 失败会退化成重启」 | 没有 `ExecReload=` 时它直接报作业类型不适用 |

## 要点自测

**问：同一条 `ExecStart=/bin/bash -c "sleep 120 &"`，为什么 `Type=simple` 下服务立刻 `inactive`，`Type=forking` 下却 `active (running)`？**
答：因为判据不同。`simple` 把「主进程被 `fork` 出来」当完成，`bash` 立刻退出就判定结束，留在控制组里的后台进程会被一并清掉；`forking` 把「父进程退出、子进程留下」当完成，于是 `sleep` 成为 `MainPID`。

**问：`Type=simple` 与 `Type=exec` 的差别在运维上如何体现？**
答：判定点一个在 `fork` 返回、一个在 `execve` 成功。`exec` 会把「二进制不存在、权限不对、工作目录不可进入」这类设置阶段错误归入启动失败，`simple` 则可能把它们记成「启动成功、随后立刻退出」。

**问：应用日志里已经打印就绪，systemd 仍等满超时，最可能的原因是什么？**
答：通知的发送者不符合 `NotifyAccess=`（缺省 `main`）的资格——例如由子进程或包装器发出。日志里会有「收到的通知来自某 PID，但只允许主 PID」一类记录。也可能是应用只打日志、根本没有调用 `sd_notify`。

**问：`Type=oneshot` 的单元跑完显示 `inactive (dead)`，要不要处理？**
答：不用。那是正常终态；`RemainAfterExit=yes` 会变成 `active (exited)`。需要注意的是它的启动超时缺省为 `infinity`，卡住时不会有超时兜底。

**问：端口在监听，`systemctl status` 却是 `inactive (dead)`，怎么解释？**
答：典型的 socket 激活：`.socket` 单元持有监听套接字，服务按需拉起。看 `TriggeredBy:` 与 `systemctl list-sockets` 即可确认。

**第一反应不要做什么**：不要因为进程还在就断定服务是 active；不要因为 `inactive (dead)` 就重启服务；不要用 `while true` 之类死循环去迎合错误的 `Type=`；不要把「日志有 ready」当 systemd 应当知道的证据；不要用调大超时来掩盖通知未到达；不要给不 `fork` 的程序配 `forking`；不要往 `ExecStartPre=` 里放没有容错的可选检查。
