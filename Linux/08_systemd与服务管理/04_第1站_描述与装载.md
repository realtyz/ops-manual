# 第 1 站：描述与装载

> [!cite] 参考资料
> `man 5 systemd.unit`、`man 5 systemd.service`、`man 5 systemd.exec`、`man 1 systemctl`、`man 1 systemd-analyze`，以及 `systemd.io` 的「Writing Unit Files」。

> 本篇的实测输出来自 Ubuntu 24.04.4（WSL2）/ 内核 `6.6.87.2-microsoft-standard-WSL2` / systemd 255（`255.4-1ubuntu8.17`）/ cgroup v2 / 非 root `uid=1000` 的**用户级** systemd（`systemctl --user`）；system 单元的行为标注为「未实测」。

> **这篇讲什么**：把服务「描述」出来，并让 systemd 真正「装载」这份描述。重点是那条最容易被忽略的链条——**你改的文件、systemd 认识到的配置、正在跑的进程，三者可能同时是三份不同的东西**。这一站是「改了配置没生效」的全部答案。

## 0. 30 秒速览

> [!abstract] 这一篇只要记住六句话
> - **systemd 用的是「manager 里的生效配置」，不是你磁盘上的文件**。两者的刷新动作叫 `daemon-reload`。
> - **`daemon-reload` 只重读文件，不碰进程**：实测完整链条是「改文件 → `status` 出现 changed on disk 警告、`show` 仍是旧值 → `daemon-reload` 后 `show` 变新值、**`/proc/<pid>/environ` 仍是旧值** → `restart` 后才是新值」。
> - **只在启动时使用的项**（`Environment=`、`ExecStart=`、`Restart=`、`User=`…）必须 `restart` 才生效；支持运行期重载的服务用 `ExecReload=` + `systemctl reload`。
> - **改配置的正确顺序**：写 drop-in → `systemd-analyze verify` → `daemon-reload` → `systemctl show` 核对生效值 → `restart` → 业务验证。
> - **先看生效文件再动手**：`systemctl cat`（内容 = 原文件 + drop-in）与 `show -p FragmentPath -p DropInPaths`（来源路径）。
> - **一次 typo 可能把服务停掉**：`verify` 能抓未知键名、放错小节、重复 `ExecStart`；通过时**静默且退出码 0**。

## 1. 三个「配置」：文件、manager、进程

同一个服务，在同一时刻可能有三份互相不一致的「配置」：

```mermaid
flowchart LR
  A["磁盘上的 unit 文件<br/>+ 所有 drop-in"] -- "daemon-reload 读取" --> B["manager（PID 1）<br/>里的生效配置"]
  B -- "start / restart 时应用" --> C["正在运行的进程<br/>环境 / 身份 / 资源 / 沙箱"]
  A -. "文件变了但没 reload" .-> B
  B -. "reload 了但没 restart" .-> C
```

三个位置对应三条命令，分清楚就再也不会被「改了没用」困住：

| 你想确认 | 命令 | 看的是哪一份 |
| --- | --- | --- |
| 我改的文件对不对、drop-in 有没有被读到 | `systemctl cat <unit>`、`show -p FragmentPath -p DropInPaths` | 磁盘文件（含 drop-in） |
| systemd 现在按什么值执行 | `systemctl show -p <属性> <unit>` | manager 的生效配置 |
| 进程此刻实际拿到什么 | `/proc/<pid>/environ`、`/proc/<pid>/cgroup`、`systemctl show -p MainPID` | 运行中的进程 |

## 2. `daemon-reload` 到底改了什么：一次完整实测

这是全章最值得背下来的一段。实验：让服务以 `Environment=PHASE=1` 运行，然后把文件里的值改成 `PHASE=2`，逐级观察。

先看现象对应的三份配置。

第一步，改完文件、还没 reload——`systemctl` 直接告诉你文件变了，但 manager 里仍是旧值：

```text
$ systemctl --user status --no-pager -n 1 lab-simple.service | head -3
Warning: The unit file, source configuration file or drop-ins of lab-simple.service
changed on disk. Run 'systemctl --user daemon-reload' to reload units.
$ systemctl --user show -p Environment --value lab-simple.service
PHASE=1 EXTRA=from-dropin
$ tr "\0" "\n" < /proc/5737/environ | grep PHASE=
PHASE=1                                    # 运行中的进程用的还是启动时的环境
```

第二步，`daemon-reload` 之后——manager 刷新了，运行中的进程没变：

```text
$ systemctl --user daemon-reload
$ systemctl --user show -p Environment --value lab-simple.service
PHASE=2 EXTRA=from-dropin
$ tr "\0" "\n" < /proc/5737/environ | grep PHASE=
PHASE=1                                    # ← 关键：reload 不会重启进程
```

第三步，`restart` 之后——新进程才拿到新环境：

```text
$ systemctl --user restart lab-simple.service
$ tr "\0" "\n" < /proc/<new-pid>/environ | grep PHASE=
PHASE=2
```

结论一句话：**`daemon-reload` 是「让 systemd 重新读文件」，不是「让服务重新读配置」**。

> [!important] 谁需要 reload，谁还需要 restart
> - **改了 unit 文件/drop-in → 一定需要 `daemon-reload`**，否则第 ① 步永远停在旧值。这是对**所有** unit 类型都成立的。
> - **改的是「只在启动瞬间用一次」的项**（`ExecStart=`、`Environment=`、`User=`、`Type=`、资源与沙箱选项、`Restart=`）→ 还要 `restart`，因为运行中的进程不会重新读这些。
> - **改的是「支持运行期重载」的配置**（比如 nginx 的 `nginx.conf`）→ 用服务自己的重载入口：`ExecReload=` + `systemctl reload`。**`systemctl reload` 不是万能热重载**——它只是替你执行 unit 里定义的 `ExecReload=`，有没有真正生效取决于应用。

`reload` 与 `restart` 的取舍：

| 动作 | 做什么 | 影响面 | 什么时候用 |
| --- | --- | --- | --- |
| `systemctl reload <unit>` | 按 `ExecReload=` 发信号/跑命令，**进程不重启** | 小（连接可能不中断） | 应用支持热重载，且你确认它重读了你改的那部分 |
| `systemctl restart <unit>` | 停掉再拉起，**进程换新** | 大（有中断窗口、`MainPID` 变化） | 改了启动期选项，或应用不支持热重载 |
| `systemctl try-restart` | 只在服务正在跑时才重启 | 中 | 滚动维护时避免顺手拉起本来停着的服务 |
| `systemctl reload-or-restart` | 能 reload 就 reload，否则 restart | 取决于分支 | 通用「让配置生效」入口 |

## 3. drop-in：把「我改了什么」写清楚

改配置用 drop-in，不要改 `/usr/lib` 下的原文件（子笔记 02）。实践里建议按用途和顺序命名：

`systemctl edit myapp.service` 会打开 `~` 或 `/etc` 下的 `override.conf` 编辑器。**里面只写要覆盖的那几行**，例如：

```ini
[Service]
LimitNOFILE=65536
```

```bash
systemctl daemon-reload
systemctl show -p LimitNOFILE -p DropInPaths myapp.service   # 验证：值变了、路径里有你的 drop-in
```

```text
/etc/systemd/system/myapp.service.d/10-resource.conf     ← 先应用
/etc/systemd/system/myapp.service.d/20-site.conf         ← 后应用，同名键覆盖前者
```

> [!tip] drop-in 的三个纪律
> ① **只写差异**，不要把整份 unit 复制进来，否则发行版默认值变化你看不到；② **文件名带序号**，让覆盖顺序一目了然；③ **回滚就是删掉对应文件 + `daemon-reload`**，所以 drop-in 天然适合「临时放开、事后收紧」。

## 4. 上线一个 unit 的固定顺序

把「描述」变成「装载」，再变成「真的在跑」，按这个顺序走：

```bash
systemd-analyze verify /etc/systemd/system/myapp.service   # ① 语法与小节；静默 = 通过
systemctl daemon-reload                                    # ② 让 manager 读到新文件
systemctl show -p FragmentPath -p DropInPaths -p ExecStart -p LimitNOFILE myapp.service   # ③ 核对生效值
systemctl start myapp.service                              # ④ 启动
systemctl status myapp.service --no-pager                  # ⑤ 看 Active/Main PID/Result
journalctl -u myapp.service -b --no-pager | tail -30        # ⑥ 看启动日志
ss -lntp | grep <端口>                                      # ⑦ 业务验证：端口真的在听
systemctl enable myapp.service                             # ⑧ 最后才建自启（子笔记 11）
```

> [!warning] 第 ④ 步返回 0 不等于第 ⑦ 步成立
> `start` 成功只说明 `Type=` 判定通过（子笔记 06）。服务可能端口还没起来、依赖数据库没连上、健康检查还没通过。**验收标准永远是业务层面的可观察事实**，不是 `systemctl` 的退出码。

### 生产动作：把一次 unit 变更做成可回滚记录

> [!example]- 变更记录模板（每次改 unit 都填一段）
> ```text
> 变更对象：myapp.service
> 变更时间：2026-09-19 14:30 CST
> 变更前留档：systemctl cat myapp.service > /root/units/myapp.service.2026-09-19
> 变更内容：drop-in 20-resource.conf，LimitNOFILE 65535 → 131072
> 预期影响：句柄上限提高；不动启动参数，不需要重启业务
> 生效步骤：systemd-analyze verify → daemon-reload → show 核对 → restart
> 验收命令：systemctl show -p LimitNOFILE；服务内 cat /proc/<MainPID>/limits
> 回滚命令：删除 20-resource.conf → daemon-reload → restart
> 实际结果：LimitNOFILE=131072 已生效；端口在听；错误日志无新增
> 耗时：约 3 分钟（含重启中断 4 秒）
> ```
> 风险：`restart` 有短暂中断窗口；生产上先确认上层负载均衡能承接，并优先挑非核心业务时段。

### 实验 1：unit 文件、drop-in 与 `daemon-reload`

> [!example]- 实验 1：亲眼看见「文件 / manager / 进程」三份配置的差异
> **怎么做**：在 `~/.config/systemd/user/` 建 `lab-simple.service`（`Environment=PHASE=1`、`ExecStart=/bin/bash -c "exec sleep 300"`），启动后把文件改成 `PHASE=2`，分三步观察：① 不 reload → ② `daemon-reload` → ③ `restart`。每一步都用 `systemctl --user show -p Environment` 和 `tr "\0" "\n" < /proc/<MainPID>/environ | grep PHASE=` 对照；最后加一个 drop-in（`Environment=EXTRA=from-dropin`、`LimitNOFILE=256`），用 `systemctl --user cat` 与 `show -p DropInPaths` 确认。
> **预期**：① `show` 与进程都还是 `PHASE=1`，`status` 给出 changed on disk 警告；② `show` 变 `PHASE=2`、**进程仍是 `PHASE=1`**；③ `restart` 后进程才拿到 `PHASE=2`；drop-in 的键出现在 `cat` 与 `show` 里。
> **风险**：低（用户单元、`sleep`）；**耗时**：约 10 分钟；**回滚**：`systemctl --user stop lab-simple.service`、删单元与 drop-in、`daemon-reload`、`reset-failed`。
> 机器：任意能跑 `systemctl --user` 的环境（本机实测 systemd 255）。

## 5. 常见「装载」失败：先在文件层排掉

| 现象 | 证据 | 结论 |
| --- | --- | --- |
| `Loaded: not-found` | `systemctl list-unit-files \| grep <名字>` | 文件不在搜索路径，或名字拼错，或新建文件后没 `daemon-reload` |
| `Failed to load environment files`、`Result=resources` | `journalctl -u` 前几行 | `EnvironmentFile=` 指向的文件不存在且**没有**加 `-`（子笔记 02） |
| `status=203/EXEC` | `journalctl -u` | `ExecStart=` 的二进制不存在/没有执行位/解释器缺失 |
| `status=200/CHDIR` | `journalctl -u` | `WorkingDirectory=` 不存在或无权限 |
| `Unknown key name ... ignoring` | `systemd-analyze verify` | 键名写错或放错小节，配置被**静默丢弃** |
| `Service has more than one ExecStart= setting ... Refusing.` | `systemd-analyze verify` | `Type=simple` 只能有一条 `ExecStart=`（多条仅 `oneshot` 允许） |

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 「改了 unit，`restart` 一下就好」 | 没 `daemon-reload` 时 systemd 用的还是旧配置；`status` 会提示 changed on disk |
| 「`daemon-reload` 就等于重启服务」 | 实测 reload 后 manager 是新值、**运行中的进程仍是旧值**；必须 `restart` |
| 「用 `systemctl reload` 就一定不停服务」 | `reload` 只是执行 `ExecReload=`；应用不支持或没读到你改的项，等于没生效 |
| 「文件里写了就是生效了」 | 生效配置 = 原文件 + drop-in；`systemctl cat` 才是全貌，`show` 才是值 |
| 「`systemd-analyze verify` 没输出就是没检查」 | 通过时**静默且退出码 0**；说话了才说明有问题 |
| 「改 drop-in 不用 reload」 | drop-in 也是 unit 文件来源，同样要 `daemon-reload` |
| 「`EnvironmentFile=` 读不到就是变量为空」 | 不带 `-` 时是**硬失败**（`Result=resources`），服务根本起不来 |

## 决策练习

> [!question]- 场景：你把 `myapp.service` 的 `Environment=LOG_LEVEL=debug` 改成 `info`，执行了 `systemctl daemon-reload` 和 `systemctl reload myapp`，但应用日志里还是 debug 级。
> A. 认定是应用有 bug，去查代码
> B. 先 `systemctl show -p Environment myapp` 看 manager 的值，再 `tr "\0" "\n" < /proc/<MainPID>/environ` 看进程实际值，确认是「进程没换」还是「应用没重读环境」
> C. 直接 `systemctl restart myapp`，反正重启最省事
> **答案：B。**
> A 跳过了最可能的原因——环境变量只在进程启动时注入一次。
> C 可能有效，但你没有先确认 manager 是否已经更新（如果 drop-in 没写到或者没 reload，重启后仍是旧值，会得出错误结论）。
> B 是正解：**用 `show` 与 `/proc/<pid>/environ` 把「三份配置」分开验证**，再对症下药。详见子笔记 15。

## 要点自测

> [!question]- `daemon-reload` 做了什么、没做什么？为什么它之后还要 `restart`？
> - 做了：让 PID 1 重新读取全部 unit 文件与 drop-in、重新运行 generator、重建依赖图。
> - 没做：不重启正在运行的进程，也不注入新环境；实测 `show -p Environment` 已是新值而 `/proc/<pid>/environ` 仍是旧值。
> - 所以要 `restart`：启动期选项（`Environment=`/`ExecStart=`/`Restart=`…）只在进程创建时应用一次。
> - **第一反应不要是什么**：不要把 `daemon-reload` 当成「重启服务」的替代品，也不要以为它没报错就说明配置生效了。

> [!question]- `systemctl reload` 和 `restart` 怎么选？
> - `reload`：执行 unit 里的 `ExecReload=`，进程不换；适合支持热重载、且你确认它真的重读了配置的服务。
> - `restart`：停旧拉新，`MainPID` 变化；适合改了启动期选项或应用不支持热重载的情况。
> - 冷知识：`try-restart` 只在服务正在跑时重启；`reload-or-restart` 自动二选一。
> - **第一反应不要是什么**：不要默认「`reload` 更温柔所以优先」——如果它根本没读你改的那部分，等于什么都没做。

> [!question]- 怎么在 30 秒内确认「我改的配置生效了」？
> - `systemctl cat <unit>`：确认生效内容里出现了你的改动、drop-in 路径在里面。
> - `systemctl show -p <属性>`：确认 manager 的值是新值（如 `MemoryMax`、`LimitNOFILE`）。
> - 必要时 `restart` 后看 `/proc/<MainPID>/environ` 或 `/proc/<MainPID>/limits`：确认进程真的拿到了新值。
> - **第一反应不要是什么**：不要只看编辑器里的文件就宣布「已生效」。
