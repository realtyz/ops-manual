# 第 3 站：判定（什么算启动完成）

> [!cite] 参考资料
> `man 5 systemd.service`（`Type=`、`NotifyAccess=`、`PIDFile=`、`RemainAfterExit=`、`ExecStartPre/Post`、`TimeoutStartSec=` 的完整语义）、`man 5 systemd.socket`、`man 3 sd_notify`、`man 1 systemd-notify`。
>
> 实测输出来自 Ubuntu 24.04.4（WSL2）/ systemd 255 的用户级 systemd；`Type=dbus`、`Type=notify-reload` 与 `Type=idle` 的行为标注为「未实测」。`TimeoutStartSec` 的默认值随 `Type=` 变化，**`Type=oneshot` 默认关闭启动超时**，具体值以 `systemctl show -p TimeoutStartUSec` 为准。

> **这篇讲什么**：systemd 怎么判断「这个服务算启动成功了」。这一篇的核心是一张表（`Type=` 八种取值）和一个高频事故（**假启动失败**）——**进程明明在跑，systemd 却判定失败；或者服务明明没就绪，systemd 却判定成功**。

## 0. 30 秒速览

> [!abstract] 这一篇只要记住六句话
> - **`Type=` 决定「哪一刻算启动完成」**，也就决定了 systemd 什么时候宣布 `active`、什么时候开始计超时。选错就是「假启动失败」或「假启动成功」。
> - **`simple`（默认）**：`ExecStart` 的进程一 fork 出来就算完成。前台常驻进程用它。
> - **`forking`**：父进程退出、后台子进程留下才算完成，可配 `PIDFile=`。**不 fork 的程序配上它会卡到超时**。
> - **`oneshot`**：进程跑完且退出码为 0 才算完成；不加 `RemainAfterExit=yes` 就是「跑完即 `inactive`」。
> - **`notify`**：进程通过 `sd_notify(READY=1)` 主动报告。**默认 `NotifyAccess=main`，只有主进程能发**；子进程发的通知会被拒（实测日志 `reception only permitted for main PID`），服务一直等到 90 秒 `start operation timed out`。
> - **还有第二种「启动」：socket/path/timer 激活**——服务不在跑时由 `.socket`/`.path`/`.timer` 触发启动。所以「`inactive (dead)` 但端口在听」是正常的，先 `systemctl list-sockets`。

## 1. `Type=` 全表：八种取值与判据

| `Type=` | systemd 认为「启动完成」的时刻 | 适用 | 典型坑 |
| --- | --- | --- | --- |
| `simple`（默认） | `ExecStart` 的进程一 fork 出来就算 | 前台常驻进程 | 进程自己 fork 后父进程退出 → 服务被判 `dead`，子进程被 cgroup 清掉 |
| `exec` | `ExecStart` 的二进制**真正 exec 成功**才算 | 想区分「没执行起来」与「执行了但很快退出」 | 比 `simple` 严格一点，老脚本里少见 |
| `forking` | 父进程退出、子进程留在后台（可配 `PIDFile=`） | 传统 daemon（自己 daemonize） | 不 fork 的程序配上它会一直等到超时 |
| `oneshot` | 进程跑完且退出码为 0 | 初始化、迁移、脚本类任务 | 不加 `RemainAfterExit=yes` 就是「跑完即 `inactive`」 |
| `notify` | 进程通过 `sd_notify(READY=1)` 主动报告 | 支持 notify 的服务（现代守护进程） | `NotifyAccess=` 不匹配 → 一直等到超时 |
| `notify-reload` | 同 `notify`；重载时服务自己用 `RELOADING=1` / `READY=1` 报告完成 | 支持 reload 协议的现代服务（systemd 253 起） | 服务不实现该协议，`reload` 会被判超时（本机未实测） |
| `dbus` | 在 D-Bus 上注册了指定名字 | 总线服务 | 名字写错就等超时（本机未实测） |
| `idle` | 等其它任务跑完再执行 | 需要「最后跑」的脚本 | 与 `simple` 类似（本机未实测） |

```bash
systemctl show myapp.service -p Type -p NotifyAccess -p TimeoutStartUSec -p SubState -p MainPID
```

> [!tip] 怎么给一个服务选 `Type=`
> 看它**前台还是后台**、**会不会自己报告就绪**：
> - 程序默认前台运行、不 fork → `Type=simple`（或者程序支持 notify 时用 `notify`）。
> - 程序默认自己 daemonize、启动后父进程退出 → `Type=forking`（必要时配 `PIDFile=`）。
> - 一次性脚本、跑完就退出 → `Type=oneshot`（需要保持 `active` 就加 `RemainAfterExit=yes`）。
> - 支持 `sd_notify` → 优先 `notify`，这是唯一能准确表达「我真的准备好了」的方式；如果它还实现了 reload 协议（`RELOADING=1`/`READY=1`），用 `notify-reload`（systemd 253 起）。
> - **最忌**：拿 `Type=simple` 套一个会 fork 的程序，或者给不 fork 的程序配 `forking`。

## 2. `simple` 与 `forking`：一次实测的对照

两个单元用**同一条** `ExecStart=/bin/bash -c "sleep 120 &"`，只改 `Type=`：

```text
$ systemctl --user show -p SubState --value lab-fork-simple.service   # Type=simple
dead
$ systemctl --user status --no-pager -n 2 lab-fork-simple.service
○ lab-fork-simple.service - Lab wrong type (simple but forks)
     Active: inactive (dead)          # 后台 sleep 被 systemd 按控制组清掉了

$ systemctl --user status --no-pager -n 3 lab-fork-ok.service         # Type=forking
● lab-fork-ok.service - Lab forking
     Active: active (running) since Thu 2026-09-17 21:27:36 CST; 28ms ago
   Main PID: 5432 (sleep)            # 父进程退出，systemd 把子进程当作主进程
```

解读：`simple` 认定「fork 出来就算启动完成」，随后 `ExecStart` 的 bash 立刻退出（它只是起了个后台进程），systemd 认为服务结束，顺手把 cgroup 里剩下的 `sleep` 一起清掉了——于是 `dead`。`forking` 则相反，它专门等「父进程退出、子进程留下」这个模式。

## 3. `Type=notify` 与 `NotifyAccess=`：最经典的「日志有 ready、systemd 还超时」

`notify` 要求服务主动报告就绪，报告通过 `sd_notify` 发。**默认只有主进程能发**（`NotifyAccess=main`）：

错误示例（脚本里调用 `systemd-notify --ready`，但通知来自子进程）：

```text
$ journalctl --user -u lab-notify.service -o short-precise | tail -4
systemd[504]: Starting lab-notify.service - Lab notify...
systemd[504]: lab-notify.service: Got notification message from PID 5418,
              but reception only permitted for main PID 5417
bash[5417]: lab-notify-ready
systemd[504]: lab-notify.service: start operation timed out. Terminating.
systemd[504]: lab-notify.service: Failed with result 'timeout'.
```

正确做法之一是 `NotifyAccess=all`（允许该服务 cgroup 内任何进程发通知）：

```text
$ systemctl --user start lab-notify2.service && time systemctl --user start lab-notify2.service
real  0m0.039s
$ systemctl --user is-active lab-notify2.service
active
```

排障含义：**服务日志里明明打印了「ready」，systemd 仍等满 90 秒然后 `Failed with result 'timeout'`**——不要怀疑业务逻辑，先看 `NotifyAccess=` 与 `Type=`，再用 `systemctl show -p NotifyAccess -p Type -p TimeoutStartUSec` 核对。

`NotifyAccess=` 的三个取值：

| 取值 | 谁可以发通知 | 适用 |
| --- | --- | --- |
| `none` | 谁都不行 | 显式关闭通知 |
| `main`（默认） | 只有主进程 | 主进程自己 `sd_notify` |
| `exec` | 主进程 + 由 systemd 启动的进程 | 启动脚本代发 |
| `all` | 该服务 cgroup 内任何进程 | 子进程/辅助进程代发 |

> [!warning] `notify` 的三条纪律
> ① **优先让主进程自己报告**，这是最准确的；② 只有不得已才放宽 `NotifyAccess`，放宽意味着「cgroup 里任何进程都能宣布服务就绪」；③ `TimeoutStartSec=` 要按真实启动时间设，默认 90 秒对慢服务可能太短、对快服务又太长（超时前 `systemctl start` 会一直挂着）。

## 4. `oneshot`：跑完就结束的「服务」

`oneshot` 适合「做一件事就退出」的任务型单元：

```ini
[Service]
Type=oneshot
ExecStart=/usr/local/bin/migrate-schema
ExecStart=/usr/local/bin/warm-cache
RemainAfterExit=yes        # 跑完后仍报 active (exited)，而不是 inactive
```

注意多条 `ExecStart=` 只有 `oneshot` 允许。

- **不加 `RemainAfterExit=yes`**：全部 `ExecStart=` 成功退出后，服务变成 `inactive (dead)`。这是正常现象，不是失败。
- **加了 `RemainAfterExit=yes`**：报告 `active (exited)`，便于别的 unit 依赖「这件事已经做过」。
- **多条 `ExecStart=` 只有 `oneshot` 允许**。`Type=simple` 写两条会被 `systemd-analyze verify` 直接拒绝：

```text
$ systemd-analyze --user verify lab-twoexec.service
lab-twoexec.service: Service has more than one ExecStart= setting, which is only allowed
for Type=oneshot services. Refusing.
Unit lab-twoexec.service has a bad unit file setting.
```

> [!tip] `systemd-analyze verify` 应该成为改 unit 的第一步
> 实测把 `StartLimitIntervalSec=`（本应在 `[Unit]`）写进 `[Service]` 时，它报：
> ```text
> lab-broken.service:8: Unknown key name 'StartLimitIntervalSec' in section 'Service', ignoring.
> ```
> **「ignoring」意味着配置被静默丢弃**——这就是「明明写了却没生效」的常见来源。好单元 verify 是**静默且退出码 0** 的。

## 5. 启动的三个阶段：`ExecStartPre` / `ExecStart` / `ExecStartPost`

systemd 把一次启动拆成几段，每段都有明确的失败语义：

| 阶段 | 指令 | 失败时的表现 |
| --- | --- | --- |
| 准备 | `ExecStartPre=`（可多条，按顺序执行） | `Control process exited, status=1/FAILURE`，服务不进入 `ExecStart` |
| 主启动 | `ExecStart=` | 按 `Type=` 判定；失败进 `failed` |
| 收尾 | `ExecStartPost=`（可多条） | 启动被判失败 |
| 停止 | `ExecStop=`（默认发 SIGTERM） | 超时后 SIGKILL（子笔记 10） |
| 重载 | `ExecReload=` | `systemctl reload` 时执行 |

常见用法：`ExecStartPre=` 做等待依赖、检查配置、建目录；`ExecStartPost=` 做注册/预热。**注意 `ExecStartPre=` 里的命令返回非 0 会让整个服务启动失败**，所以别把「可选检查」写成 `ExecStartPre=` 而不做容错。

## 6. 第二种「启动」：socket / path / timer 激活

服务不一定靠 `systemctl start` 或开机拉起。**`.socket`、`.path`、`.timer` 都能触发对应的 `.service`**：

```bash
systemctl list-sockets --no-pager        # 验证：有哪些按需激活的套接字，以及它触发哪个 service
systemctl status <name>.socket --no-pager
```

典型现象：**服务是 `inactive (dead)`，但端口在听**。原因是 `.socket` 代替服务持有监听套接字，第一个连接到来时才拉起 `.service`。排查「服务没起来但端口占用」时，先 `list-sockets` 看有没有对应的 socket unit。

一个最小的 socket 激活（文件名为 `lab.socket`）：

```ini
[Socket]
ListenStream=127.0.0.1:12345
[Install]
WantedBy=sockets.target
```

> [!important] `timer`/`path`/`socket` 与 `service` 是配对的
> `.timer`、`.path`、`.socket` 自己只负责「触发」，真正干活的是它 `Unit=` 指定的 `.service`（默认同名）。**日志要查 `.service`，不是触发器**——这是子笔记 12 反复强调的一点。

## 7. 启动慢与超时：`TimeoutStartSec` 怎么看

```bash
systemctl show myapp.service -p Type -p TimeoutStartUSec -p TimeoutStartSec
journalctl -u myapp.service -b -o short-precise | head -20   # 看启动到就绪之间隔了多久
systemd-analyze blame | head -10                             # 谁在启动阶段花得久
```

- 默认超时随 `Type=` 变化，`notify`/`dbus` 尤其依赖它；**`Type=oneshot` 例外——它默认不设启动超时**，一个卡住的迁移脚本会一直挂在 `activating`，这时要自己写 `TimeoutStartSec=`（子笔记 03 的退出码表里，超时的表现是 `Result=timeout`）。
- 启动慢的常见原因：`ExecStartPre=` 里有阻塞操作、探测依赖用了长 `sleep`、应用自身初始化慢。
- **不要用调大超时来「修复」超时**——先看慢在哪一段；调大只是让告警晚一点来。

### 实验 2：`Type=` 与「假启动失败」

> [!example]- 实验 2：同一条命令，跑出 `dead` 与 `running` 两种结果
> **怎么做**：建 `lab-fork-simple.service`（`Type=simple`）与 `lab-fork-ok.service`（`Type=forking`），`ExecStart` 都用 `/bin/bash -c "sleep 120 &"`；再建 `lab-notify.service`（`Type=notify`，脚本里 `systemd-notify --ready; sleep 120`）。`daemon-reload` 后分别启动，观察 `SubState`、`Main PID` 与 `journalctl -u`。
> **预期**：`lab-fork-simple` → `dead`；`lab-fork-ok` → `running`、`MainPID=sleep`；`lab-notify` → 日志出现 `reception only permitted for main PID`，约 90 秒后 `Failed with result 'timeout'`；给 `lab-notify` 加 `NotifyAccess=all` 后秒级启动（本机实测 0.039s）。
> **风险**：无（用户单元、`sleep` 会在清理时被停掉）；**耗时**：约 10 分钟（含一次 90 秒超时）；**回滚**：停服务、删单元、`daemon-reload`、`reset-failed`。
> 机器：任意能跑 `systemctl --user` 的环境；生产机上做需要隔离的临时单元。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 会 fork 的后台程序用 `Type=simple` | 父进程退出即被判 `dead`，后台子进程被 cgroup 清掉 |
| 不 fork 的程序配 `Type=forking` | systemd 一直等父进程退出，等到超时 |
| 日志里打印 ready 就以为 systemd 应该知道 | 只有 `sd_notify` 通知才算；默认还只接受主进程的通知 |
| 看到 `inactive (dead)` 就断定服务挂了 | 可能是 `oneshot` 跑完、socket 激活、或 timer 触发的服务 |
| `Type=simple` 写多条 `ExecStart=` | verify 直接拒绝；多条仅 `oneshot` 允许 |
| 用调大 `TimeoutStartSec=` 解决超时 | 掩盖真正的慢启动；应先看慢在哪一段 |
| `ExecStartPre=` 里放可选检查 | 返回非 0 会让整个服务启动失败，要自己做容错 |

## 决策练习

> [!question]- 场景：一个自研服务启动时会先做 20 秒的数据预热，预热完成后才监听端口。你写了 `Type=simple`，开机后偶发「systemd 报告 active，但探针检测端口未监听」。
> A. 在探针侧加 30 秒延迟，等它自己好
> B. 让服务在预热完成、开始监听后调用 `sd_notify(READY=1)`，把 unit 改成 `Type=notify`；如果做不到，就用 `ExecStartPost` 做端口探测
> C. 改成 `Type=oneshot` + `RemainAfterExit=yes`，让 systemd 等它跑完
> **答案：B。**
> A 把问题推给下游，且慢机器仍会失败。
> C 的逻辑不对：进程是常驻的，不该用 `oneshot`；`RemainAfterExit` 也解决不了「就绪」判定。
> B 是正解：**让服务自己报告就绪，或用可观测的探测把「就绪」变成 systemd 能等到的信号**。

## 要点自测

> [!question]- `Type=` 八种取值分别在什么时刻判定启动完成？各自适合什么服务？
> - `simple`：进程 fork 出来即完成，适合前台常驻进程；`exec`：二进制 exec 成功才算。
> - `forking`：父进程退出、子进程留下才算，适合会自己 daemonize 的程序（可配 `PIDFile=`）。
> - `oneshot`：跑完且退出码 0 才算，适合脚本/迁移类任务（需要保持 `active` 加 `RemainAfterExit=yes`）。
> - `notify`：进程主动 `sd_notify(READY=1)` 才算，是最准确的「真的就绪」；`notify-reload` 是它的 reload 版本，重载完成也由服务自己报告。
> - `dbus`/`idle`：分别在 D-Bus 注册名、等其它任务跑完时才判定完成。
> - **第一反应不要是什么**：不要用 `simple` 套后台程序，也不要给不 fork 的程序配 `forking`。

> [!question]- 日志打印了 `ready`，systemd 却等到 90 秒超时，怎么解释、怎么处理？
> - 只有通过 `sd_notify` 发出的通知才算数；**普通 `echo ready` 不算**。
> - 即使调用了 `systemd-notify`，默认 `NotifyAccess=main` 只接受主进程的通知；子进程发会被拒（实测日志 `reception only permitted for main PID`）。
> - 处理：优先让主进程自己报告；确实需要子进程代发，再改成 `NotifyAccess=all` 并理解其含义。
> - **第一反应不要是什么**：不要因为日志里有「ready」就断言 systemd 有 bug，也不要直接调大超时。

> [!question]- 「服务是 `inactive (dead)` 但端口在听」可能是什么情况？怎么确认？
> - 可能是 socket 激活：`.socket` 持有监听套接字，服务按需启动，没连接时保持 `inactive`。
> - 也可能是 `timer`/`path` 触发的服务刚跑完（`oneshot`）。
> - 确认：`systemctl list-sockets`、`systemctl status <name>.socket`、看 unit 的 `Type=` 与 `Unit=` 配对。
> - **第一反应不要是什么**：不要因为 `inactive` 就去重启服务——它可能本来就是按需启动的设计。
