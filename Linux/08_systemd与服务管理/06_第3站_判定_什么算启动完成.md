## 0. 30 秒速览

> [!abstract] 这一篇只要记住六句话
> - **`Type=` 决定「哪一刻算启动完成」**，也就决定了 systemd 什么时候宣布 `active`、什么时候开始计超时。选错就是「假启动失败」或「假启动成功」。
> - **`simple`（默认）**：`ExecStart` 的进程一 fork 出来就算完成，`TimeoutStartUSec=1min 30s`。前台常驻进程用它。
> - **`forking`**：父进程退出、后台子进程留下才算完成（实测 `MainPID=12510`、`SubState=running`）。**不 fork 的程序配上它会卡到超时**。
> - **`oneshot`**：进程跑完且退出码为 0 才算完成；**它是唯一默认关闭启动超时的类型**（实测 `TimeoutStartUSec=infinity`），不加 `RemainAfterExit=yes` 就是「跑完即 `inactive (dead)`」，加了就是 `active (exited)`。
> - **`notify`**：进程通过 `sd_notify(READY=1)` 主动报告。**默认 `NotifyAccess=main`，判定按「谁执行了通知」这一层卡**：由单元自己的进程直接执行 `systemd-notify` 都被接受（实测 0.016–0.040 秒），多包一层或自己往 socket 写 `READY=1` 都被拒（实测默认等满 **90.237 秒**）。
> - **还有第二种「启动」：socket/path/timer 激活**——服务不在跑时由 `.socket`/`.path`/`.timer` 触发启动。实测 `lab08b-sock.socket` 在 `127.0.0.1:20511` 上 `LISTEN` 并 `ACTIVATES lab08b-sock.service`，所以「`inactive (dead)` 但端口在听」是正常的，先 `systemctl list-sockets`。

## 1. `Type=` 全表：八种取值与判据

下表右两列已按**本次系统级实测**填齐（原「未实测」项已补测）：

| `Type=` | systemd 认为「启动完成」的时刻 | 适用 | 本次实测 / 典型坑 |
| --- | --- | --- | --- |
| `simple`（默认） | `ExecStart` 的进程一 fork 出来就算 | 前台常驻进程 | 用同一条会 fork 的 `ExecStart` 实测：`MainPID=0`、`ActiveState=inactive`、`SubState=dead`；日志里 `Started` 之后 11.7 毫秒就 `Deactivated successfully` |
| `exec` | `ExecStart` 的二进制**真正 exec 成功**才算 | 想区分「没执行起来」与「执行了但很快退出」 | 实测 `MainPID=12512`、`active (running)`；与 `simple` 的差别只在「fork 出来」还是「exec 成功」这一瞬间 |
| `forking` | 父进程退出、子进程留在后台（可配 `PIDFile=`） | 传统 daemon（自己 daemonize） | 同一命令实测 `MainPID=12510`、`active (running)`——**同一份 `ExecStart`，换个 `Type=` 结论相反** |
| `oneshot` | 进程跑完且退出码为 0 | 初始化、迁移、脚本类任务 | 实测 `TimeoutStartUSec=infinity`（**默认无启动超时**）；不写 `RemainAfterExit=` 时 `inactive (dead)`，写了是 `active (exited)` |
| `notify` | 进程通过 `sd_notify(READY=1)` 主动报告 | 支持 notify 的服务（现代守护进程） | 主进程自己发实测 **0.033 秒**；`NotifyAccess=` 不匹配时一直等到 `TimeoutStartUSec`（默认 **90.237 秒**） |
| `notify-reload` | 同 `notify`；重载时服务自己用 `RELOADING=1` / `READY=1` 报告完成 | 支持 reload 协议的现代服务（systemd 253 起） | **本次补测**：服务实现了协议时 `reload_rc=0`、耗时 **0.206 秒**；不实现协议时 `reload` 在 `TimeoutStartSec` 处超时（实测 6 秒），**单元本身仍是 `active (running)`** |
| `dbus` | 在 D-Bus 上注册了指定名字 | 总线服务 | **本次补测**：名字被拒时 `start_rc=1`、0.131 秒即失败；给策略放行后 `start_rc=0`、**0.064 秒**启动、`MainPID=15156`；名字没人持有则等到 `TimeoutStartSec`（实测 10 秒→`dbus_fail_seconds=10.167`） |
| `idle` | 等其它任务跑完再执行 | 需要「最后跑」的脚本 | **本次补测**：`MainPID=12520`、`active (running)`、`TimeoutStartUSec=1min 30s`，行为与 `simple` 一致 |

```bash
systemctl show myapp.service -p Type -p NotifyAccess -p TimeoutStartUSec -p SubState -p MainPID
```

> [!tip] 怎么给一个服务选 `Type=`
> 看它**前台还是后台**、**会不会自己报告就绪**：
> - 程序默认前台运行、不 fork → `Type=simple`（或者程序支持 notify 时用 `notify`）。
> - 程序默认自己 daemonize、启动后父进程退出 → `Type=forking`（必要时配 `PIDFile=`）。
> - 一次性脚本、跑完就退出 → `Type=oneshot`（需要保持 `active` 就加 `RemainAfterExit=yes`）。
> - 支持 `sd_notify` → 优先 `notify`，这是唯一能准确表达「我真的准备好了」的方式；如果它还实现了 reload 协议（`RELOADING=1`/`READY=1`），用 `notify-reload`（systemd 253 起）。
> - 在系统总线上持有名字 → `Type=dbus` + `BusName=`（注意 D-Bus 策略默认 `deny own="*"`，名字不是想拿就能拿）。
> - **最忌**：拿 `Type=simple` 套一个会 fork 的程序，或者给不 fork 的程序配 `forking`。

## 2. `simple` 与 `forking`：一次实测的对照

两个 **system 单元**用**同一条** `ExecStart=/bin/bash -c "sleep 120 &"`，只改 `Type=`：

```text
$ systemctl show -p SubState --value lab08-t-simple.service
dead
$ systemctl show -p Type -p MainPID -p ActiveState -p SubState lab08-t-simple.service
Type=simple
NotifyAccess=none
TimeoutStartUSec=1min 30s
MainPID=0
ActiveState=inactive
SubState=dead

$ systemctl show -p Type -p MainPID -p ActiveState -p SubState lab08-t-forking.service
Type=forking
NotifyAccess=none
TimeoutStartUSec=1min 30s
MainPID=12510
ActiveState=active
SubState=running
```

日志把时间差也留下了——`simple` 是「宣布启动成功、随即结束」：

```text
Sep 19 08:05:28.138929 linux-lab systemd[1]: Started lab08-t-simple.service - lab08 type simple (forks).
Sep 19 08:05:28.150613 linux-lab systemd[1]: lab08-t-simple.service: Deactivated successfully.
Sep 19 08:05:28.144227 linux-lab systemd[1]: Starting lab08-t-forking.service - lab08 type forking...
Sep 19 08:05:28.148184 linux-lab systemd[1]: Started lab08-t-forking.service - lab08 type forking.
```

解读：`simple` 认定「fork 出来就算启动完成」，随后 `ExecStart` 的 bash 立刻退出（它只是起了个后台进程），systemd 认为服务结束，顺手把 cgroup 里剩下的 `sleep` 一起清掉了——于是 `dead`。`forking` 则相反，它专门等「父进程退出、子进程留下」这个模式，于是后台 `sleep` 被认作主进程。

## 3. `Type=notify` 与 `NotifyAccess=`：最经典的「日志有 ready、systemd 还超时」

`notify` 要求服务主动报告就绪，报告通过 `sd_notify` 发。**默认只有主进程能发**（`NotifyAccess=main`）。把这条边界实测拆开看，结论非常干脆：

| 通知是怎么发的 | 实测结果 |
| --- | --- |
| 由单元自己的进程（主进程，或其直接子进程）**直接执行** `systemd-notify --ready` | **全部被接受**，启动耗时 **0.0159–0.0396 秒**（多个单元、多次重跑：`.017740575` / `.022279901` / `.020563725` / `.020086654` / `.023375582` / `.022134286` / `.015927414` / `.018895847` / `.035621325`） |
| **多包一层**再执行 `systemd-notify`（`sh -c "systemd-notify --ready"`，或 `strace … systemd-notify`） | **被拒**：`start_rc=1`，耗时 `6.010526340` 秒（`TimeoutStartSec=6s`），日志 `Got notification message from PID …, but reception only permitted for main PID …` |
| 自己**往通知 socket 写 `READY=1`**（含「主进程 fork 出的直接子进程」这种看起来最正当的写法） | **被拒**：`Result=timeout`，耗时 `6.211011810` / `6.127640638` / `6.191797678` / `8.208176127` / `8.228218156` / `6.169266303`（`NotifyAccess=exec` 也一样被拒） |
| `NotifyAccess=all` + fork 出来的子进程发 | **被接受**：`.039608574` / `.039256222` / `.021056140` |

一次默认超时的原始现场（子进程发、默认 `NotifyAccess=main`、默认 90 秒）：

```text
$ systemctl start lab08-n-90.service; echo "start_rc=$? seconds=$SECONDS"
start_rc=1 seconds=90.236972527
$ systemctl show -p Type -p NotifyAccess -p TimeoutStartUSec -p Result -p ActiveState lab08-n-90.service
Type=notify
NotifyAccess=main
TimeoutStartUSec=1min 30s
Result=timeout
ActiveState=failed
```

```text
Sep 19 08:06:33.756069 linux-lab python3[16797]: child pid 16797 sent READY=1 (main pid 16796)
Sep 19 08:06:33.756044 linux-lab systemd[1]: lab08-n-90.service: Got notification message from PID 16797, but reception only permitted for main PID 16796
Sep 19 08:08:03.957501 linux-lab systemd[1]: lab08-n-90.service: start operation timed out. Terminating.
Sep 19 08:08:03.957972 linux-lab systemd[1]: lab08-n-90.service: Failed with result 'timeout'.
Sep 19 08:08:03.958200 linux-lab systemd[1]: Failed to start lab08-n-90.service - lab08 notify forked child, default timeout.
```

> [!warning] 为什么「在我机器上能跑」不算证据
> 上表里最关键的一条是：**同一个 `systemd-notify --ready` 调用，因为中间多了一层 `sh -c` 或 `strace`，就从「接受」变成「拒绝」**。也就是说判定发生在「谁执行了通知」这一层，而这层非常容易被一个 wrapper、一个 `env`、一次 `sudo -u`、一层脚本间接调用改掉。
> **第一反应不要是什么**：不要拿一次成功的手工测试去证明生产写法正确。要确认，请直接看拒绝日志（`Got notification message from PID …, but reception only permitted for main PID …`），或按下面的方法自己测一次。
>
> **自己取证的方法**（本次用过的探针）：服务内把 `NOTIFY_SOCKET` 指到一个自己起的 Unix 数据报 socket 上，并打开 `SO_PASSCRED`，就能看到内核给出的**发送方 PID**；把它和 `systemctl show -p MainPID` 对比，就能看出 systemd 会怎么判：
> ```text
> unit main pid=41088 ppid=1 NOTIFY_SOCKET=/tmp/lab08c3/sock
>   [child-runs-systemd-notify] actual sender process pid=41090 rc=0
>   WIRE[child-runs-systemd-notify] payload=b'READY=1\nSTATUS=probe1' SCM_CREDENTIALS.pid=41090  (main pid=41088)
>   [grandchild-via-bash] actual sender process pid=41092 rc=0
>   WIRE[grandchild-via-bash] payload=b'READY=1\nSTATUS=probe2' SCM_CREDENTIALS.pid=41092  (main pid=41088)
>   [child-raw-python-socket] actual sender process pid=41094 rc=0
>   WIRE[child-raw-python-socket] payload=b'READY=1' SCM_CREDENTIALS.pid=41095  (main pid=41088)
> ```
> `systemd-notify` 发出的报文只有 `READY=1`（外加可选的 `STATUS=`），**不带任何「代表哪个 PID」的字段**——所以判定完全依赖内核给出的发送方身份，这也解释了为什么包一层就会翻车。

`NotifyAccess=` 的四个取值：

| 取值 | 谁可以发通知 | 适用 |
| --- | --- | --- |
| `none` | 谁都不行 | 显式关闭通知；**但 `Type=notify` 时它会被强制改成 `main`**（`man systemd.service` 原文），所以别指望用 `none` 把通知关掉 |
| `main`（默认） | 只有主进程 | 主进程自己 `sd_notify` |
| `exec` | 主进程 + 由 systemd 启动的进程 | 启动脚本代发；**实测 `NotifyAccess=exec` 下 fork 出的孙进程仍被拒**（`6.169266303` 秒后超时） |
| `all` | 该服务 cgroup 内任何进程 | 子进程/辅助进程代发 |

> [!important] `notify` 的三条纪律
> ① **优先让主进程自己报告**，这是最准确的；② 只有不得已才放宽 `NotifyAccess`，放宽意味着「cgroup 里任何进程都能宣布服务就绪」；③ `TimeoutStartSec=` 要按真实启动时间设，默认 90 秒对慢服务可能太短、对快服务又太长（超时前 `systemctl start` 会一直挂着，实测就挂了 90.237 秒）。

### 3.1 `Type=notify-reload`：不实现协议会怎样（本次补测）

`notify-reload` 的重载完成同样由服务自己报告。**如果服务不实现这个协议**，`systemctl reload` 会等到超时——但**不会把服务杀掉**：

```text
$ systemctl start lab08-nr2.service; echo "start_rc=$?"
start_rc=0
$ systemctl show -p Type -p NotifyAccess -p TimeoutStartUSec -p Result -p ActiveState -p SubState lab08-nr2.service
Type=notify-reload
NotifyAccess=all
TimeoutStartUSec=6s
Result=success
ActiveState=active
SubState=running

$ systemctl reload lab08-nr2.service; echo "reload_rc=$?"
reload_rc=1
reload_wall=6.10 s
```

```text
got-SIGHUP-ignored
Reloading lab08-nr2.service - lab08 notify-reload but no reload protocol...
lab08-nr2.service: Reload operation timed out. Killing reload process.
Reload failed for lab08-nr2.service - lab08 notify-reload but no reload protocol.
```

三条结论：① 超时长度取 `TimeoutStartSec=`（实测设 6 秒就等 6.10 秒）；② **失败的是 reload，不是服务**——单元仍是 `active (running)`、`NRestarts=0`；③ 实现了协议的服务则 `reload_rc=0`、耗时 **0.206 秒**。反过来说，如果服务**不 trap SIGHUP**，`reload` 会先把进程打死（默认 reload 信号是 SIGHUP），这一点要按服务的信号处理方式一起评估。

## 4. `oneshot`：跑完就结束的「服务」

`oneshot` 适合「做一件事就退出」的任务型单元：

```ini
[Service]
Type=oneshot
ExecStart=/usr/local/bin/migrate-schema
ExecStart=/usr/local/bin/warm-cache
RemainAfterExit=yes        # 跑完后仍报 active (exited)，而不是 inactive
```

注意多条 `ExecStart=` 只有 `oneshot` 允许。

- **不加 `RemainAfterExit=yes`**：全部 `ExecStart=` 成功退出后，服务变成 `inactive (dead)`。这是正常现象，不是失败。
- **加了 `RemainAfterExit=yes`**：报告 `active (exited)`，便于别的 unit 依赖「这件事已经做过」。
- **`oneshot` 默认没有启动超时**（实测 `TimeoutStartUSec=infinity`）：一个卡住的迁移脚本会永远挂在 `activating`，所以要自己写 `TimeoutStartSec=`。
- **多条 `ExecStart=` 只有 `oneshot` 允许**。`Type=simple` 写两条会被 `systemd-analyze verify` 直接拒绝：

```text
$ systemd-analyze verify /etc/systemd/system/lab08-v-twoexec.service; echo "verify_twoexec_rc=$?"
lab08-v-twoexec.service: Service has more than one ExecStart= setting, which is only allowed for Type=oneshot services. Refusing.
Unit lab08-v-twoexec.service has a bad unit file setting.
verify_twoexec_rc=1
```

> [!tip] `systemd-analyze verify` 应该成为改 unit 的第一步——但要看输出
> 实测把 `StartLimitIntervalSec=`（本应在 `[Unit]`）写进 `[Service]` 时，它报：
> ```text
> /etc/systemd/system/lab08-bad.service:5: Unknown key name 'StartLimitIntervalSec' in section 'Service', ignoring.
> verify_unknown_rc=0
> ```
> **「ignoring」意味着配置被静默丢弃，而退出码仍然是 0**——这就是「明明写了却没生效」的常见来源，也是「脚本里用 `verify` 的退出码做守门」会漏掉的那一类。好单元 verify 是**静默且退出码 0** 的。

## 5. 启动的三个阶段：`ExecStartPre` / `ExecStart` / `ExecStartPost`

systemd 把一次启动拆成几段，每段都有明确的失败语义：

| 阶段 | 指令 | 失败时的表现 |
| --- | --- | --- |
| 准备 | `ExecStartPre=`（可多条，按顺序执行） | `Control process exited, status=1/FAILURE`，服务不进入 `ExecStart` |
| 主启动 | `ExecStart=` | 按 `Type=` 判定；失败进 `failed` |
| 收尾 | `ExecStartPost=`（可多条） | 启动被判失败 |
| 停止 | `ExecStop=`（默认发 SIGTERM） | 超时后 SIGKILL（子笔记 10） |
| 重载 | `ExecReload=` | `systemctl reload` 时执行；**没有它时 reload 直接失败（退出码 3）**（子笔记 04） |

常见用法：`ExecStartPre=` 做等待依赖、检查配置、建目录；`ExecStartPost=` 做注册/预热。**注意 `ExecStartPre=` 里的命令返回非 0 会让整个服务启动失败**，所以别把「可选检查」写成 `ExecStartPre=` 而不做容错。

## 6. 第二种「启动」：socket / path / timer 激活

服务不一定靠 `systemctl start` 或开机拉起。**`.socket`、`.path`、`.timer` 都能触发对应的 `.service`**：

```bash
systemctl list-sockets --no-pager        # 验证：有哪些按需激活的套接字，以及它触发哪个 service
systemctl status <name>.socket --no-pager
```

实测（端口取自本阶段预留区间）：

```text
$ systemctl list-sockets --no-pager
LISTEN          UNIT               ACTIVATES
127.0.0.1:20511 lab08b-sock.socket lab08b-sock.service

1 sockets listed.
```

典型现象：**服务是 `inactive (dead)`，但端口在听**。原因是 `.socket` 代替服务持有监听套接字，第一个连接到来时才拉起 `.service`。排查「服务没起来但端口占用」时，先 `list-sockets` 看有没有对应的 socket unit。另外实测一处边界：**把一个有活动 `.socket` 的 `.service` 屏蔽时，`mask` 会明确提示触发单元还在跑**——

```text
Masking 'lab08b-sock.service', but its triggering units are still active:
lab08b-sock.socket
```

一个最小的 socket 激活（文件名为 `lab.socket`）：

```ini
[Socket]
ListenStream=127.0.0.1:20512
[Install]
WantedBy=sockets.target
```

> [!important] `timer`/`path`/`socket` 与 `service` 是配对的
> `.timer`、`.path`、`.socket` 自己只负责「触发」，真正干活的是它 `Unit=` 指定的 `.service`（默认同名）。**日志要查 `.service`，不是触发器**——这是子笔记 12 反复强调的一点。

## 7. 启动慢与超时：`TimeoutStartSec` 怎么看

```bash
systemctl show myapp.service -p Type -p TimeoutStartUSec -p TimeoutStartSec
journalctl -u myapp.service -b -o short-precise | head -20   # 看启动到就绪之间隔了多久
systemd-analyze blame | head -10                             # 谁在启动阶段花得久
systemd-analyze critical-chain myapp.service                 # 谁挡住了它
```

- 默认超时随 `Type=` 变化（本机实测 `simple`/`exec`/`forking`/`notify`/`dbus`/`idle` 都是 `1min 30s`），`notify`/`dbus` 尤其依赖它；**`Type=oneshot` 例外——默认 `infinity`**。
- 启动慢的常见原因：`ExecStartPre=` 里有阻塞操作、探测依赖用了长 `sleep`、应用自身初始化慢、**依赖了一个不会超时的目标**（例如本机的 `systemd-networkd-wait-online.service` 被改成 `TimeoutStartUSec=infinity`，占了开机 blame 第一名 1.231 秒）。
- **不要用调大超时来「修复」超时**——先看慢在哪一段；调大只是让告警晚一点来。

### 实验 2：`Type=` 与「假启动失败」

> [!example]- 实验 2：同一条命令，跑出 `dead` 与 `running` 两种结果
> **怎么做**：在 `/etc/systemd/system/` 建 `lab08-t-simple.service`（`Type=simple`）与 `lab08-t-forking.service`（`Type=forking`），`ExecStart` 都用 `/bin/bash -c "sleep 120 &"`；再建一个 `Type=notify` 的单元，脚本里由**子进程**用 python 往 `$NOTIFY_SOCKET` 直接写 `READY=1`（不要用 `systemd-notify`）。`daemon-reload` 后分别启动，观察 `SubState`、`MainPID`、耗时与 `journalctl -u`。
> **预期**：`simple` → `SubState=dead`、`MainPID=0`；`forking` → `running`、`MainPID=12510`；`notify` 子进程直写 → 日志出现 `reception only permitted for main PID`，等到超时（默认 90 秒；把 `TimeoutStartSec=8s` 就能把实验压到 8 秒出头）；改成 `NotifyAccess=all` 后变成 0.04 秒级启动。
> **风险**：无（自建 system 单元、`sleep` 会在清理时被停掉；**不要碰系统服务**）；**耗时**：约 10 分钟（含一次超时观察）；**回滚**：`systemctl stop` 各单元、`rm -f /etc/systemd/system/lab08-t-*.service`、`daemon-reload`、`reset-failed`。
> 机器：任意有 root 的可快照实验机（本机实测 systemd 255）。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 会 fork 的后台程序用 `Type=simple` | 父进程退出即被判 `dead`（实测 `MainPID=0`、`SubState=dead`），后台子进程被 cgroup 清掉 |
| 不 fork 的程序配 `Type=forking` | systemd 一直等父进程退出，等到超时 |
| 日志里打印 ready 就以为 systemd 应该知道 | 只有 `sd_notify` 通知才算；`echo ready` 完全不算 |
| 「主进程调用 `systemd-notify` 就行，包一层也一样」 | 实测**包一层 `sh -c`/`strace` 就被拒**；判定在「谁执行了通知」这一层，wrapper、`sudo -u`、间接调用都可能翻车 |
| 用 `NotifyAccess=none` 把通知关掉 | `Type=notify` 时它会被 systemd **强制改成 `main`**，关不掉 |
| 以为 `NotifyAccess=exec` 能放行「主进程的孙进程」 | 实测仍被拒（`Got notification message from PID …`，6.169 秒后超时） |
| 看到 `inactive (dead)` 就断定服务挂了 | 可能是 `oneshot` 跑完、socket 激活、或 timer 触发的服务 |
| `Type=simple` 写多条 `ExecStart=` | verify 直接拒绝（退出码 1）；多条仅 `oneshot` 允许 |
| 以为 `oneshot` 也会超时 | 实测 `TimeoutStartUSec=infinity`；卡住的迁移脚本会永远 `activating` |
| `Type=dbus` 只要写对 `BusName=` 就能起 | D-Bus 默认策略是 `<deny own="*"/>`；实测不放行时报 `AccessDenied: Connection ":1.175" is not allowed to own the service "org.example.Lab08" due to security policies in the configuration file` |
| 用调大 `TimeoutStartSec=` 解决超时 | 掩盖真正的慢启动；应先看慢在哪一段 |
| `ExecStartPre=` 里放可选检查 | 返回非 0 会让整个服务启动失败，要自己做容错 |

## 决策练习

> [!question]- 场景：一个自研服务启动时会先做 20 秒的数据预热，预热完成后才监听端口。你写了 `Type=simple`，开机后偶发「systemd 报告 active，但探针检测端口未监听」。
> A. 在探针侧加 30 秒延迟，等它自己好
> B. 让服务在预热完成、开始监听后调用 `sd_notify(READY=1)`，把 unit 改成 `Type=notify`；如果做不到，就用 `ExecStartPost` 做端口探测
> C. 改成 `Type=oneshot` + `RemainAfterExit=yes`，让 systemd 等它跑完
> **答案：B。**
> A 把问题推给下游，且慢机器仍会失败。
> C 的逻辑不对：进程是常驻的，不该用 `oneshot`；`RemainAfterExit` 也解决不了「就绪」判定。
> B 是正解：**让服务自己报告就绪，或用可观测的探测把「就绪」变成 systemd 能等到的信号**。
> 补充一条本次实测的边界：如果走 `notify`，**报告必须由服务自己的主进程发出**——用脚本包一层或交给孙进程都会被拒（默认等满 90 秒），这不是 systemd 的 bug。

## 要点自测

> [!question]- `Type=` 八种取值分别在什么时刻判定启动完成？各自适合什么服务？
> - `simple`：进程 fork 出来即完成；`exec`：二进制 exec 成功才算。都适合前台常驻进程。
> - `forking`：父进程退出、子进程留下才算，适合会自己 daemonize 的程序（可配 `PIDFile=`）。
> - `oneshot`：跑完且退出码 0 才算，适合脚本/迁移类任务（需要保持 `active` 加 `RemainAfterExit=yes`）；**它是唯一默认没有启动超时的类型**。
> - `notify`：进程主动 `sd_notify(READY=1)` 才算，是最准确的「真的就绪」；`notify-reload` 是它的 reload 版本，重载完成也由服务自己报告（实测实现协议时 0.206 秒，不实现时在 `TimeoutStartSec` 处超时且服务不受影响）。
> - `dbus`：在系统总线上持有 `BusName=` 才算（实测成功后 `MainPID=15156`、0.064 秒）；`idle`：等其它任务跑完（实测与 `simple` 行为一致）。
> - **第一反应不要是什么**：不要用 `simple` 套后台程序，也不要给不 fork 的程序配 `forking`。

> [!question]- 日志打印了 `ready`，systemd 却等到 90 秒超时，怎么解释、怎么处理？
> - 只有通过 `sd_notify` 发出的通知才算数；**普通 `echo ready` 不算**。
> - 即使调用了 `systemd-notify`，通知仍然要能正确归属到单元：实测**多包一层**（`sh -c`/`strace`）或**自己往 socket 写**都会被拒（日志 `Got notification message from PID …, but reception only permitted for main PID …`），默认等满 `90.237` 秒。
> - 处理：优先让主进程自己报告；确实需要别的进程代发，再改成 `NotifyAccess=all`（实测 0.04 秒级成功）并理解其含义——放宽等于「cgroup 里任何进程都能宣布服务就绪」。
> - **第一反应不要是什么**：不要因为日志里有「ready」或手工测过一次成功就断言 systemd 有 bug，也不要直接调大超时。

> [!question]- 「服务是 `inactive (dead)` 但端口在听」可能是什么情况？怎么确认？
> - 可能是 socket 激活：`.socket` 持有监听套接字，服务按需启动，没连接时保持 `inactive`。实测 `lab08b-sock.socket` 在 `127.0.0.1:20511` 上 `LISTEN` 并 `ACTIVATES lab08b-sock.service`。
> - 也可能是 `timer`/`path` 触发的服务刚跑完（`oneshot`）。
> - 确认：`systemctl list-sockets`、`systemctl status <name>.socket`、看 unit 的 `Type=` 与 `Unit=` 配对。
> - **第一反应不要是什么**：不要因为 `inactive` 就去重启服务——它可能本来就是按需启动的设计。顺带记住：想「彻底停用」一个 socket 激活的服务，光 `mask` 那个 `.service` 不够，systemd 会提示触发单元还在（实测 `Masking 'lab08b-sock.service', but its triggering units are still active`）。
