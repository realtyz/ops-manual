## 0. 30 秒速览

> [!abstract] 这一篇只要记住六句话
> - **`enable` 不是「现在启动」，而是按 `[Install]` 段建软链**：实测 `systemctl --user enable lab-simple.service` 生成 `~/.config/systemd/user/default.target.wants/lab-simple.service → …`，`disable` 就是把软链删掉。
> - **没有 `[Install]` 段的 unit 无法 `enable`**（会报「no installation config」），只能靠别的 unit `Wants=` 拉它，或被 `.socket`/`.path`/`.timer` 触发。这类单元在 `list-unit-files` 里显示为 `static`。
> - **「服务不自启」三步检查**：unit 有没有 `[Install]` → `WantedBy=` 指向的 target 在不在启动路径上 → `is-enabled` 与 `list-unit-files` 的安装态。
> - **`mask` 比 `disable` 强得多**：它用一个指向 `/dev/null` 的软链让 unit **彻底无法启动**。实测对一个「文件就在自己配置目录」的单元 mask 会失败（`File ... already exists`），必须先移走原文件。
> - **屏蔽 socket/path 触发的单元时，要连触发它的 `.socket`/`.path` 一起处理**：实测 mask 时 systemd 会提醒 `Masking 'gpg-agent.service', but its triggering units are still active`，否则触发链还在。
> - **开机到达哪个 target 由 `default.target` 决定**：`systemctl get-default` 看，`set-default` 改；服务器通常是 `multi-user.target`。

## 1. `[Install]` 与 `enable` 的机制

`[Install]` 段只在 `enable`/`disable` 时被读：

```ini
[Install]
WantedBy=multi-user.target
```

`WantedBy=multi-user.target` 的意思是「当 `multi-user.target` 被拉起时，也**希望**（Wants）拉起我」。`enable` 就是把这个关系落成磁盘上的软链：

```text
$ systemctl --user enable lab-simple.service
Created symlink /home/realtyz/.config/systemd/user/default.target.wants/lab-simple.service
              → /home/realtyz/.config/systemd/user/lab-simple.service.
$ systemctl --user is-enabled lab-simple.service
enabled
$ systemctl --user disable lab-simple.service
Removed "/home/realtyz/.config/systemd/user/default.target.wants/lab-simple.service".
```

user 实例的 target 是 `default.target`（用户级没有 `multi-user.target` 的完整体系），system 实例通常是 `multi-user.target`。

| 指令 | 建/删的软链位置（system 实例） |
| --- | --- |
| `enable foo.service` | `/etc/systemd/system/multi-user.target.wants/foo.service` |
| `enable foo.timer` | `/etc/systemd/system/timers.target.wants/foo.timer` |
| `disable foo.service` | 删除上面那条软链 |

## 2. `enable` / `disable` / `start` / `stop` / `mask` 的关系

这四组动作经常被混为一谈，其实分两个维度：

| 动作 | 管的是 | 立刻影响运行状态吗 |
| --- | --- | --- |
| `start` / `stop` | **现在**的运行状态 | 是 |
| `enable` / `disable` | **开机**要不要拉起 | 否 |
| `mask` / `unmask` | 让 unit **能不能被启动** | 会让后续启动失败 |
| `preset` | 按发行版预设批量 enable/disable | 否（除非 `--now`） |

所以：

- **`enable --now`** = 建自启软链 + 立刻启动。
- **`disable`** 只删软链，**不停止当前进程**；要停用并停止用 `disable --now`。
- **`disable` 不等于「以后都不会被启动」**：别的 unit 仍可以用 `Wants=` 拉它，socket/path/timer 也可能触发它。要彻底不行，才用 `mask`。
- **`mask` 是「双向」的**：既不能手动 `start`，也不能作为依赖被拉起。

### `static` 与 `indirect`

```bash
systemctl list-unit-files --type=service | grep -E "static|disabled|enabled" | head
```

- `enabled`：有自启软链。
- `disabled`：有 `[Install]` 但现在没建软链。
- `static`：**没有 `[Install]` 段**，不能被 `enable`；它要么被别的 unit 拉，要么被触发型 unit 触发。
- `indirect`：`[Install]` 里只有 `Also=`，自身不建软链。

## 3. `mask`：彻底屏蔽与它的边界

`mask` 的实现是「在优先级更高的目录创建一个指向 `/dev/null` 的软链」。实测有两个容易踩的边界：

第一种情况，想 mask 一个「文件就在自己配置目录」的单元——失败：

```text
$ systemctl --user mask lab-oneshot.service
Failed to mask unit: File /home/realtyz/.config/systemd/user/lab-oneshot.service already exists.
```

第二种情况，mask 一个来自下层目录（`/usr/lib/systemd/user`）的单元——成功：

```text
$ systemctl --user mask gpg-agent.service
Created symlink /home/realtyz/.config/systemd/user/gpg-agent.service → /dev/null.
$ systemctl --user is-enabled gpg-agent.service
masked
$ systemctl --user start gpg-agent.service
Failed to start gpg-agent.service: Unit gpg-agent.service is masked.
$ systemctl --user unmask gpg-agent.service
```

原因：mask 要在**更高优先级目录**放同名软链，而你的 unit 文件正好就在那个目录——冲突。**要屏蔽它，得先把文件移走/改名，或者用 `disable` + 一个空的覆盖 unit。**

另外实测 mask 时 systemd 会提醒：

```text
Masking 'gpg-agent.service', but its triggering units are still active
```

含义是：**屏蔽 socket/path 触发的单元时，要连触发它的 `.socket`/`.path` 一起处理**，否则只是不启动服务，触发链还在。

```bash
systemctl list-unit-files --state=masked          # 验证：当前被屏蔽的 unit
systemctl is-enabled <unit>                       # 验证：enabled/disabled/static/masked
```

## 4. `preset`：发行版决定「默认开哪些」

很多发行版用 preset 文件（`/usr/lib/systemd/system-preset/*.preset`）规定「软件包安装后，这个 unit 默认 enable 还是 disable」。`systemctl preset <unit>` 就是按这些规则操作；`systemctl enable` 不受 preset 影响。

```bash
systemctl show myapp.service -p Preset                # 验证：这个 unit 的预设策略
ls /usr/lib/systemd/system-preset/ 2>/dev/null        # 验证：本机有哪些 preset 文件（本机未实测）
```

一般业务不需要动 preset；知道它的存在，是为了理解为什么「装完软件包，有的服务自己就自启了」。

## 5. target：开机到哪一步

`default.target` 是开机默认目标，通常软链到 `graphical.target` 或 `multi-user.target`：

```bash
systemctl get-default                       # 验证：本机默认目标（服务器一般是 multi-user.target）
systemctl list-dependencies multi-user.target | head -20
```

| 命令 | 作用 | 风险 |
| --- | --- | --- |
| `systemctl get-default` | 查看默认目标 | 无（只读） |
| `systemctl set-default multi-user.target` | 改默认目标 | 中（下次开机生效） |
| `systemctl isolate rescue.target` | **立刻切到**另一个目标（会停掉不在该目标里的服务） | **高**，可能在远程把自己关在外面 |
| `systemctl rescue` / `systemctl emergency` | 切换到救援/紧急模式 | 高 |

> [!warning] `isolate` 和救援模式是有「杀伤力」的动作
> `systemctl isolate` 会启动目标需要的、停掉不在目标里的服务；在远程会话里 `isolate rescue.target` 可能直接切断你的 SSH。**这类动作只在能进控制台/带外管理时做**，不要在生产机的 SSH 会话里试。救援入口的完整用法属于启动流程主题，本篇只关心「服务为什么没被拉起」。

## 6. 「服务不自启」的三步检查

第一步看有没有 `[Install]` 段，第二步看 `WantedBy` 指向的 target 在不在启动路径上，第三步看安装态到底是什么：

```bash
systemctl cat myapp.service | grep -A3 "\[Install\]"
systemctl list-dependencies multi-user.target | grep myapp
systemctl is-enabled myapp.service
systemctl list-unit-files | grep myapp
```

| `is-enabled` 输出 | 含义 | 处置 |
| --- | --- | --- |
| `enabled` | 有自启软链 | 若仍不自启，看 `WantedBy` 的 target 是否在启动路径、以及有没有 `Condition...=` 跳过 |
| `disabled` | 有 `[Install]` 但没建软链 | `systemctl enable` |
| `static` | 没有 `[Install]` | 不能 enable；要用别的 unit `Wants=` 或在 target 里加 `Wants=` |
| `masked` | 被屏蔽 | `unmask` 或查是谁屏蔽的 |
| `linked` / `alias` | 通过软链/别名关联 | 看链接指向哪里 |

## 生产动作：上线与下线一个服务的清单

> [!example]- 上线一个服务的固定动作
> ```bash
> systemd-analyze verify /etc/systemd/system/myapp.service
> systemctl daemon-reload
> systemctl start myapp.service
> systemctl status myapp.service --no-pager
> journalctl -u myapp.service -b --no-pager | tail -30
> ss -lntp | grep <端口>
> systemctl enable myapp.service
> systemctl is-enabled myapp.service
> ```
> **验收**：`is-enabled` 为 `enabled`，`list-dependencies multi-user.target` 里能看到它，且**在下一次重启后仍然自动起来**（这一条只能靠演练验证）。

> [!example]- 下线一个服务的固定动作（顺序很重要）
> ```bash
> systemctl disable --now myapp.service     # 先取消自启 + 停止
> systemctl status myapp.service --no-pager # 确认 inactive、Tasks: 0
> rm -f /etc/systemd/system/myapp.service /etc/systemd/system/myapp.service.d/override.conf
> systemctl daemon-reload
> systemctl reset-failed myapp.service      # 清掉失败状态，避免残留
> ```
> **如果只是临时停用**：用 `systemctl mask myapp.service`（记得触发它的 `.socket`/`.path` 也要处理）；**不要**直接删 `/usr/lib` 下的原文件，软件包升级会把它带回来。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 「`enable` 就是现在启动服务」 | `enable` 只建自启软链；要立刻启动得 `--now` 或单独 `start` |
| 「`disable` 之后服务就不会再被启动」 | `disable` 只删软链；别的 unit 的 `Wants=`、socket/path/timer 都可能拉起它 |
| 「`mask` 一定成功」 | 单元文件如果在你自己配置目录里，mask 会失败（实测 `File ... already exists`） |
| 「`mask` 了服务就彻底没了」 | 触发它的 `.socket`/`.path` 仍可能 active（实测 systemd 会提醒） |
| 「删掉 `/usr/lib/systemd/system` 下的文件就能停用服务」 | 软件包升级后文件会回来；应该用 `disable`/`mask` |
| 「`enable` 之后重启一定会自启」 | 还要看 `WantedBy=` 的 target 在不在启动路径、有没有 `Condition...=` 跳过 |
| 在 SSH 里 `systemctl isolate rescue.target` 试手 | 可能立刻切断远程连接；这类动作要在有控制台时做 |

## 决策练习

> [!question]- 场景：一个软件包安装时自带并自启了一个你不需要的服务。你想让它「以后无论如何都不要起来」，同事建议直接 `systemctl disable`。
> A. `systemctl disable <svc>`，收工
> B. `systemctl disable --now <svc>` 停掉并取消自启；再确认没有 `.socket`/`.path` 触发它；仍担心被依赖拉起就 `systemctl mask <svc>` 并核对触发单元
> C. 直接删掉 `/usr/lib/systemd/system/<svc>.service`
> **答案：B。**
> A 只取消自启，服务可能仍被 socket/path 触发或被其它 unit 拉起。
> C 会在软件包升级后复原，且属于对发行版文件的破坏性修改。
> B 是正解：**停用要分「自启」和「能不能被启动」两层，触发链要一起看**。

## 要点自测

> [!question]- `enable` 到底做了什么？为什么有的 unit 不能 `enable`？
> - 它按 `[Install]` 段的 `WantedBy=`/`RequiredBy=` 建软链（`<target>.wants/<unit>`），`disable` 就是删软链。
> - 没有 `[Install]` 段的 unit 不能 `enable`，在 `list-unit-files` 里显示为 `static`；它们靠别的 unit `Wants=` 或被触发型 unit 触发。
> - 验证：`systemctl is-enabled`、`ls -l /etc/systemd/system/multi-user.target.wants/`。
> - **第一反应不要是什么**：不要把 `enable` 当成「启动服务」——它是关于下次开机的。

> [!question]- `disable` 和 `mask` 有什么区别？mask 可能失败吗？
> - `disable` 只删自启软链，unit 仍可被手动启动、被依赖拉起、被触发型 unit 触发。
> - `mask` 建一个指向 `/dev/null` 的软链，让 unit **彻底无法启动**（手动和依赖都不行）。
> - mask 可能失败：当 unit 文件本身就在更高优先级目录（比如你自己的 `/etc/systemd/system` 或 `~/.config/systemd/user`）时，实测报 `File ... already exists`。
> - **第一反应不要是什么**：不要以为 mask 了就万事大吉——触发它的 `.socket`/`.path` 可能还在 active。

> [!question]- 服务没开机自启，怎么排查？
> - 三步：`systemctl cat | grep -A3 '\[Install\]'`（有没有）、`list-dependencies <target>`（在不在启动路径）、`is-enabled`/`list-unit-files`（安装态）。
> - 还要看有没有 `Condition...=` 让它在本次启动被跳过（跳过不算失败，`status` 里会有提示）。
> - 排查完用 `systemctl enable` 修正，并在**下一次重启演练**中确认。
> - **第一反应不要是什么**：不要只跑一次 `enable` 就宣称解决——「下次开机会不会自启」只能靠演练验证。
