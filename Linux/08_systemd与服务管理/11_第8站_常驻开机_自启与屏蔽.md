## 0. 30 秒速览

> [!abstract] 这一篇只要记住六句话
> - **`enable` 不是「现在启动」，而是按 `[Install]` 段建软链**：实测 `systemctl enable lab08b-simple.service`（`[Install] WantedBy=multi-user.target`）生成 `/etc/systemd/system/multi-user.target.wants/lab08b-simple.service → /etc/systemd/system/lab08b-simple.service`，`disable` 就是把软链删掉。
> - **没有 `[Install]` 段的 unit 无法 `enable`**：本机实测报 `The unit files have no installation config (...)`，`is-enabled` 与 `list-unit-files` 都显示 `static`；这类单元只能靠别的 unit `Wants=` 拉它，或被 `.socket`/`.path`/`.timer` 触发。
> - **「服务不自启」三步检查**：unit 有没有 `[Install]` → `WantedBy=` 指向的 target 在不在启动路径上 → `is-enabled` 与 `list-unit-files` 的安装态。本机实测 `enable` 之后 `list-dependencies multi-user.target` 里立刻出现 `lab08b-simple.service`。
> - **`mask` 比 `disable` 强得多，而且有两种结果**：对**软件包装在 `/usr/lib/systemd/system/`** 的单元，`mask` 在 `/etc/systemd/system/` 建一条指向 `/dev/null` 的软链并成功（实测 `is-enabled` = `masked`，`start` 报 `Unit … is masked`）；对**文件就在 `/etc/systemd/system/`** 的单元，`mask` 直接失败（`Failed to mask unit: File /etc/systemd/system/xxx.service already exists.`）。
> - **屏蔽 socket/path 触发的单元时，要连触发它的 `.socket`/`.path` 一起处理**：实测 mask 时 systemd 会提醒 `Masking 'lab08b-sock.service', but its triggering units are still active: lab08b-sock.socket`。
> - **开机到达哪个 target 由 `default.target` 决定**：本机实测 `systemctl get-default` = **`graphical.target`**（这台虚拟机装的是带图形目标的桌面版 Ubuntu，**不是**常说的 `multi-user.target`）；`set-default` 改它，但只在下一次开机生效，本次未实测。

## 1. `[Install]` 与 `enable` 的机制

`[Install]` 段只在 `enable`/`disable` 时被读：

```ini
[Install]
WantedBy=multi-user.target
```

`WantedBy=multi-user.target` 的意思是「当 `multi-user.target` 被拉起时，也**希望**（Wants）拉起我」。`enable` 就是把这个关系落成磁盘上的软链。本机系统级实测（单元放 `/etc/systemd/system/`）：

```text
$ systemctl is-enabled lab08b-simple.service
disabled
$ systemctl enable lab08b-simple.service
Created symlink /etc/systemd/system/multi-user.target.wants/lab08b-simple.service
              → /etc/systemd/system/lab08b-simple.service.
$ systemctl is-enabled lab08b-simple.service
enabled
$ ls -l /etc/systemd/system/multi-user.target.wants/ | grep lab08b
lrwxrwxrwx 1 root root 41 Sep 19 08:06 lab08b-simple.service -> /etc/systemd/system/lab08b-simple.service
$ systemctl list-dependencies multi-user.target --no-pager | grep lab08b
○ ├─lab08b-simple.service
$ systemctl disable lab08b-simple.service
Removed "/etc/systemd/system/multi-user.target.wants/lab08b-simple.service".
```

三点值得记住：① **目录名就是 `WantedBy=` 的值**（`multi-user.target` → `multi-user.target.wants/`）；② 软链**指向单元文件本身**，不是拷贝；③ `enable` 之后**服务并没有被启动**（`list-dependencies` 里那个 `○` 就是未激活）。

| 指令 | 建/删的软链位置（system 实例） |
| --- | --- |
| `enable foo.service` | `/etc/systemd/system/multi-user.target.wants/foo.service` |
| `enable foo.timer` | `/etc/systemd/system/timers.target.wants/foo.timer`（本机实测，见子笔记 12） |
| `enable foo.socket` | `/etc/systemd/system/sockets.target.wants/foo.socket` |
| `disable foo.service` | 删除上面那条软链 |

> [!note] 用户实例的对应物
> 用户实例（`systemctl --user`）把软链建在 `~/.config/systemd/user/<target>.wants/` 下，用户级一般没有 `multi-user.target` 的完整体系，常见的是 `default.target.wants/`。**本机系统级与用户级都存在**（`root` 与 `realtyz` uid=1000 各有一套），所以「这条软链到底在哪」要先确认你在哪一侧操作。

## 2. `enable` / `disable` / `start` / `stop` / `mask` 的关系

这四组动作经常被混为一谈，其实分两个维度：

| 动作 | 管的是 | 立刻影响运行状态吗 |
| --- | --- | --- |
| `start` / `stop` | **现在**的运行状态 | 是 |
| `enable` / `disable` | **开机**要不要拉起 | 否 |
| `mask` / `unmask` | 让 unit **能不能被启动** | 会让后续启动失败 |
| `preset` | 按发行版预设批量 enable/disable | 否（除非 `--now`） |

所以：

- **`enable --now`** = 建自启软链 + 立刻启动。
- **`disable`** 只删软链，**不停止当前进程**；要停用并停止用 `disable --now`。
- **`disable` 不等于「以后都不会被启动」**：别的 unit 仍可以用 `Wants=` 拉它，socket/path/timer 也可能触发它。要彻底不行，才用 `mask`。
- **`mask` 是「双向」的**：既不能手动 `start`，也不能作为依赖被拉起。

### `static` 与 `indirect`

```bash
systemctl list-unit-files --type=service | grep -E "static|disabled|enabled" | head
```

- `enabled`：有自启软链。
- `disabled`：有 `[Install]` 但现在没建软链。
- `static`：**没有 `[Install]` 段**，不能被 `enable`；它要么被别的 unit 拉，要么被触发型 unit 触发。
- `indirect`：`[Install]` 里只有 `Also=`，自身不建软链。

`list-unit-files` 的表头本机实测是 `UNIT FILE / STATE / PRESET` 三列（`PRESET` 那一列就是下一节的发行版预设；没有预设规则的显示 `-`）：

```text
$ systemctl list-unit-files --type=service --state=enabled --no-pager | head -3
UNIT FILE                              STATE   PRESET
apparmor.service                       enabled enabled
apport.service                         enabled enabled
$ systemctl list-unit-files --type=service --state=static --no-pager | head -3
UNIT FILE                                STATE  PRESET
apport-autoreport.service                static -
apt-daily-upgrade.service                static -
```

## 3. `mask`：彻底屏蔽与它的两种结果

`mask` 的实现是「在优先级更高的目录创建一个指向 `/dev/null` 的软链」。本机系统级实测有两种结果。

第一种，**单元文件来自 `/usr/lib/systemd/system/`（软件包安装的）→ 成功**：

```text
$ systemctl mask lab08b-maskme.service
Created symlink /etc/systemd/system/lab08b-maskme.service → /dev/null.
$ systemctl is-enabled lab08b-maskme.service
masked
$ ls -l /etc/systemd/system/lab08b-maskme.service
lrwxrwxrwx 1 root root 9 Sep 19 08:06 /etc/systemd/system/lab08b-maskme.service -> /dev/null
$ systemctl start lab08b-maskme.service
Failed to start lab08b-maskme.service: Unit lab08b-maskme.service is masked.
$ systemctl unmask lab08b-maskme.service
Removed "/etc/systemd/system/lab08b-maskme.service".
```

第二种，**单元文件就在 `/etc/systemd/system/` → 失败**：

```text
$ systemctl mask lab08b-simple.service
Failed to mask unit: File /etc/systemd/system/lab08b-simple.service already exists.
```

原因：mask 要在**更高优先级目录**放同名软链，而你的 unit 文件正好就在那个目录——冲突。**要屏蔽它，得先把文件移走/改名，或者用 `disable` + 一个空的覆盖 unit**（对自己的单元，更直接的做法是直接删掉文件）。

第三种情况本机也复现了——**触发链仍然在**。用一对自建的 socket 激活单元（`.socket` 监听 `127.0.0.1:20511`，`.service` 放在 `/usr/lib/systemd/system/`）：

```text
$ systemctl list-sockets lab08b-sock.socket --no-pager
LISTEN          UNIT               ACTIVATES
127.0.0.1:20511 lab08b-sock.socket lab08b-sock.service
$ systemctl mask lab08b-sock.service
Created symlink /etc/systemd/system/lab08b-sock.service → /dev/null.
Masking 'lab08b-sock.service', but its triggering units are still active:
lab08b-sock.socket
$ systemctl start lab08b-sock.service
Failed to start lab08b-sock.service: Unit lab08b-sock.service is masked.
```

含义是：**屏蔽 socket/path 触发的单元时，要连触发它的 `.socket`/`.path` 一起处理**，否则端口还在监听、只是服务永远起不来（连接会被拒），排障时非常像「服务坏了」。

```bash
systemctl list-unit-files --state=masked          # 验证：当前被屏蔽的 unit
systemctl is-enabled <unit>                       # 验证：enabled/disabled/static/masked
systemctl list-sockets --no-pager | grep <名字>    # 验证：触发它的 socket 还在不在
```

## 4. `preset`：发行版决定「默认开哪些」

很多发行版用 preset 文件（`/usr/lib/systemd/system-preset/*.preset`）规定「软件包安装后，这个 unit 默认 enable 还是 disable」。`systemctl preset <unit>` 就是按这些规则操作；`systemctl enable` 不受 preset 影响。本机实测：

```text
$ ls -l /usr/lib/systemd/system-preset/
-rw-r--r-- 1 root root 1458 Feb 27  2024 90-systemd.preset
$ grep -nE "^(enable|disable)" /usr/lib/systemd/system-preset/90-systemd.preset | head -4
14:enable remote-fs.target
15:enable remote-cryptsetup.target
16:enable machines.target
18:enable getty@.service
$ systemctl preset lab08b-simple.service
Created symlink /etc/systemd/system/multi-user.target.wants/lab08b-simple.service → /etc/systemd/system/lab08b-simple.service.
$ systemctl is-enabled lab08b-simple.service
enabled
```

也就是说：**`preset` 和 `enable` 的结果可以一样，但依据不同**——`enable` 只看单元自己的 `[Install]`，`preset` 还要看发行版预设文件里的 `enable`/`disable` 规则（以及 `systemctl preset-all` 这种批量动作）。`list-unit-files` 的 `PRESET` 列就是这个规则的汇总视图。

一般业务不需要动 preset；知道它的存在，是为了理解为什么「装完软件包，有的服务自己就自启了」。

## 5. target：开机到哪一步

`default.target` 是开机默认目标，通常软链到 `graphical.target` 或 `multi-user.target`：

```bash
systemctl get-default                       # 验证：本机默认目标
systemctl list-dependencies multi-user.target --no-pager | head -12
systemd-analyze unit-paths                  # 验证：单元文件的搜索路径（优先级从高到低）
```

本机实测：

```text
$ systemctl get-default
graphical.target
$ systemd-analyze unit-paths
/etc/systemd/system.control
/run/systemd/system.control
/run/systemd/transient
/run/systemd/generator.early
/etc/systemd/system
/etc/systemd/system.attached
/run/systemd/system
/run/systemd/system.attached
/run/systemd/generator
/usr/local/lib/systemd/system
/usr/lib/systemd/system
/run/systemd/generator.late
```

**注意 `get-default` 是 `graphical.target`**：`multi-user.target` 是 `graphical.target` 的依赖之一，所以即使默认目标是图形，`WantedBy=multi-user.target` 的单元照样会自启（本机实测那个 `lab08b-simple.service` 就出现在 `list-dependencies multi-user.target` 里）。**「服务器通常是 `multi-user.target`」只是常见约定，不要凭它判断某个单元会不会被拉起——要看它挂在哪个 target 上。**

`systemd-analyze unit-paths` 同时解释了「同名 unit 谁赢」：越靠上的目录优先级越高，**`/etc/systemd/system` 覆盖 `/usr/lib/systemd/system`，而且它也高于 `/run/systemd/system`**（`unit-paths` 里 `/etc/systemd/system` 排第 5、`/run/systemd/system` 排第 7，`/usr/lib/systemd/system` 更靠后）——这正是 `mask` 用 `/etc` 下 `/dev/null` 软链生效的原理。**不要以为「运行时生成的 `/run` 一定盖过 `/etc`」**：本机实测把同名 unit 放进 `/run/systemd/system` 后 `daemon-reload`，`FragmentPath` 仍指向 `/etc/systemd/system/…`、`Description` 也没翻盘（子笔记 02 第 2 节有完整现场）。

| 命令 | 作用 | 风险 |
| --- | --- | --- |
| `systemctl get-default` | 查看默认目标（本机实测 `graphical.target`） | 无（只读） |
| `systemctl set-default multi-user.target` | 改默认目标 | 中（**下次开机才生效**；本实验环境不重启整机，未实测） |
| `systemctl isolate rescue.target` | **立刻切到**另一个目标（会停掉不在该目标里的服务） | **高**，可能在远程把自己关在外面 |
| `systemctl rescue` / `systemctl emergency` | 切换到救援/紧急模式 | 高 |

> [!warning] `isolate` 和救援模式是有「杀伤力」的动作
> `systemctl isolate` 会启动目标需要的、停掉不在目标里的服务；在远程会话里 `isolate rescue.target` 可能直接切断你的 SSH。**这类动作只在能进控制台/带外管理时做**，不要在生产机的 SSH 会话里试。救援入口的完整用法属于启动流程主题，本篇只关心「服务为什么没被拉起」。
> 同理，`set-default` 改的是**下一次开机**的目标，本次会话看不到任何效果——**它的验收标准只能是重启后 `get-default` 与 `is-system-running` 的结果**，所以本实验环境（不重启整机、不切 target）保持未实测。

## 6. 「服务不自启」的三步检查

第一步看有没有 `[Install]` 段，第二步看 `WantedBy` 指向的 target 在不在启动路径上，第三步看安装态到底是什么：

```bash
systemctl cat myapp.service | grep -A3 "\[Install\]"
systemctl list-dependencies multi-user.target | grep myapp
systemctl is-enabled myapp.service
systemctl list-unit-files | grep myapp
```

| `is-enabled` 输出 | 含义 | 处置 |
| --- | --- | --- |
| `enabled` | 有自启软链 | 若仍不自启，看 `WantedBy` 的 target 是否在启动路径、以及有没有 `Condition...=` 跳过 |
| `disabled` | 有 `[Install]` 但没建软链 | `systemctl enable` |
| `static` | 没有 `[Install]` | 不能 enable；要用别的 unit `Wants=` 或在 target 里加 `Wants=` |
| `masked` | 被屏蔽 | `unmask` 或查是谁屏蔽的 |
| `linked` / `alias` | 通过软链/别名关联 | 看链接指向哪里 |

## 生产动作：上线与下线一个服务的清单

> [!example]- 上线一个服务的固定动作
> ```bash
> systemd-analyze verify /etc/systemd/system/myapp.service
> systemctl daemon-reload
> systemctl start myapp.service
> systemctl status myapp.service --no-pager
> journalctl -u myapp.service -b --no-pager | tail -30
> ss -lntp | grep <端口>
> systemctl enable myapp.service
> systemctl is-enabled myapp.service
> ```
> **验收**：`is-enabled` 为 `enabled`，`list-dependencies multi-user.target` 里能看到它，且**在下一次重启后仍然自动起来**（这一条只能靠演练验证——本实验环境不重启整机，所以「下一个开机周期」这一段未实测）。

> [!example]- 下线一个服务的固定动作（顺序很重要）
> ```bash
> systemctl disable --now myapp.service     # 先取消自启 + 停止
> systemctl status myapp.service --no-pager # 确认 inactive、Tasks: 0
> systemctl list-sockets --no-pager | grep myapp   # 有 .socket/.path 触发的话一起停
> rm -f /etc/systemd/system/myapp.service /etc/systemd/system/myapp.service.d/override.conf
> systemctl daemon-reload
> systemctl reset-failed myapp.service      # 清掉失败状态，避免残留
> ```
> **如果只是临时停用**：用 `systemctl mask myapp.service`（记得触发它的 `.socket`/`.path` 也要处理）；**不要**直接删 `/usr/lib` 下的原文件，软件包升级会把它带回来。
> **本机实测的清理形态**（和这段清单一致）：停掉单元 → 删 unit 文件 → `daemon-reload` → `reset-failed`，之后 `ls /etc/systemd/system/ | grep lab08b` 为空、`ss -lntup | grep -E ":20[45][0-9][0-9]"` 无输出、`systemctl is-system-running` 回到 `running`。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 「`enable` 就是现在启动服务」 | `enable` 只建自启软链；要立刻启动得 `--now` 或单独 `start`（本机实测 `enable` 后 `list-dependencies` 里仍是未激活的 `○`） |
| 「`disable` 之后服务就不会再被启动」 | `disable` 只删软链；别的 unit 的 `Wants=`、socket/path/timer 都可能拉起它 |
| 「`mask` 一定成功」 | 单元文件如果在你自己配置目录里，mask 会失败（本机实测 `Failed to mask unit: File /etc/systemd/system/lab08b-simple.service already exists.`）；只有来自 `/usr/lib/systemd/system` 的单元才总能屏蔽 |
| 「`mask` 了服务就彻底没了」 | 触发它的 `.socket`/`.path` 仍可能 active，本机实测会打印 `Masking 'lab08b-sock.service', but its triggering units are still active: lab08b-sock.socket`，端口还在监听 |
| 「删掉 `/usr/lib/systemd/system` 下的文件就能停用服务」 | 软件包升级后文件会回来；应该用 `disable`/`mask` |
| 「`enable` 之后重启一定会自启」 | 还要看 `WantedBy=` 的 target 在不在启动路径、有没有 `Condition...=` 跳过 |
| 拿「服务器一般是 `multi-user.target`」当判据 | 本机 `systemctl get-default` 实测是 `graphical.target`；`multi-user.target` 只是它的依赖之一，`WantedBy=multi-user.target` 照样生效 |
| 在 SSH 里 `systemctl isolate rescue.target` 试手 | 可能立刻切断远程连接；这类动作要在有控制台时做 |

## 决策练习

> [!question]- 场景：一个软件包安装时自带并自启了一个你不需要的服务。你想让它「以后无论如何都不要起来」，同事建议直接 `systemctl disable`。
> A. `systemctl disable <svc>`，收工
> B. `systemctl disable --now <svc>` 停掉并取消自启；再确认没有 `.socket`/`.path` 触发它；仍担心被依赖拉起就 `systemctl mask <svc>` 并核对触发单元（本机实测 mask 成功时会同时打印「触发单元仍 active」）
> C. 直接删掉 `/usr/lib/systemd/system/<svc>.service`
> **答案：B。**
> A 只取消自启，服务可能仍被 socket/path 触发或被其它 unit 拉起。
> C 会在软件包升级后复原，且属于对发行版文件的破坏性修改。
> B 是正解：**停用要分「自启」和「能不能被启动」两层，触发链要一起看**。

## 要点自测

> [!question]- `enable` 到底做了什么？为什么有的 unit 不能 `enable`？
> - 它按 `[Install]` 段的 `WantedBy=`/`RequiredBy=` 建软链（`<target>.wants/<unit>`），`disable` 就是删软链；软链指向单元文件本身。
> - 没有 `[Install]` 段的 unit 不能 `enable`（实测提示 `The unit files have no installation config (...)`），在 `list-unit-files` 里显示为 `static`；它们靠别的 unit `Wants=` 或被触发型 unit 触发。
> - 验证：`systemctl is-enabled`、`ls -l /etc/systemd/system/multi-user.target.wants/`、`systemctl list-dependencies multi-user.target`。
> - **第一反应不要是什么**：不要把 `enable` 当成「启动服务」——它是关于下次开机的；也不要只跑一次 `enable` 就宣称解决，「下次开机会不会自启」只能靠重启演练验证。

> [!question]- `disable` 和 `mask` 有什么区别？mask 可能失败吗？
> - `disable` 只删自启软链，unit 仍可被手动启动、被依赖拉起、被触发型 unit 触发。
> - `mask` 建一个指向 `/dev/null` 的软链，让 unit **彻底无法启动**（手动和依赖都不行）；本机实测 `mask` 后 `start` 报 `Unit lab08b-maskme.service is masked.`。
> - mask **可能失败**：当 unit 文件本身就在更高优先级目录（你自己的 `/etc/systemd/system` 或 `~/.config/systemd/user`）时，实测报 `File ... already exists`；只有 `/usr/lib` 下的单元才总能屏蔽。
> - **第一反应不要是什么**：不要以为 mask 了就万事大吉——触发它的 `.socket`/`.path` 可能还在 active。

> [!question]- 服务没开机自启，怎么排查？
> - 三步：`systemctl cat | grep -A3 '\[Install\]'`（有没有）、`list-dependencies <target>`（在不在启动路径）、`is-enabled`/`list-unit-files`（安装态，看 `STATE` 与 `PRESET` 两列）。
> - 还要看有没有 `Condition...=` 让它在本次启动被跳过（跳过不算失败，`status` 里会有提示）。
> - 排查完用 `systemctl enable` 修正，并在**下一次重启演练**中确认——本实验环境不重启整机，所以「下一个开机周期」这一段仍未实测。
> - **第一反应不要是什么**：不要凭「这台机器应该是 `multi-user.target`」下结论——先用 `systemctl get-default` 与 `list-dependencies` 看实际结构。
