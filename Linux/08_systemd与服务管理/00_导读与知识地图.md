# systemd、服务与定时任务

## 知识地图

### 一个 unit 的一生

时间主线跟着**一个 unit**走：它从磁盘上的一份配置文件开始，先被装载成 manager 认知里的「生效配置」，再进入编队、被拉起并被判定算不算就绪，然后被放进 cgroup 并加上沙箱约束与最小权限，运行期间把证据留在 journald，退出之后由 `Restart=` 决定重来还是就此退场，最后到开机时是否还参与。

```mermaid
flowchart LR
  A["① 装载<br/>读文件与 drop-in<br/>合成生效配置"] --> B["② 编队<br/>依赖 · 顺序 · 并行"]
  B --> C["③ 判定<br/>什么算启动完成"]
  C --> D["④ 约束与隔离<br/>cgroup · 沙箱 · 最小权限"]
  D --> E["⑤ 运行与留痕<br/>journald · 时间基线"]
  E --> F["⑥ 退场与重来<br/>退出码 · Restart · 节流"]
  F --> G["⑦ 常驻<br/>enable · mask · target"]
  E -.->|"定时任务与临时文件<br/>由 timer 与 tmpfiles 维护"| G
```

| # | 阶段 | systemd 在这一段做什么 | 到这里要能说清 |
| --- | --- | --- | --- |
| 1 | 装载 | 它按搜索路径读 unit 文件与 drop-in，把两者拼成一份生效配置，再装进 manager 的认知 | 生效配置是由哪几个文件拼出来的；改了文件之后，manager 与进程为什么都还是旧值 |
| 2 | 编队 | 它解析 `Wants=`/`Requires=` 来决定拉起谁，而 `After=`/`Before=` 只决定先后，因此缺省是并行启动 | 依赖与顺序为什么是两层；「对方被拉起」为什么不等于「对方已就绪」 |
| 3 | 判定 | 它按 `Type=` 与 `NotifyAccess=` 判定这次启动算不算完成 | 同一条命令在 `simple` 下为什么立刻变成 `inactive (dead)`、在 `forking` 下常驻、在 `notify` 下等满超时 |
| 4 | 约束与隔离 | 它把服务放进 cgroup 并按 unit 属性限流，同时用沙箱选项改变它看到的世界、用能力集收敛它的特权 | 上限配在哪一层；沙箱报错为什么是 systemd 的退出码而不是应用报的错 |
| 5 | 运行与留痕 | 它把服务的标准输出、syslog 套接字、内核消息（`kmsg`）与审计（audit）四类来源收进 journald，按字段索引、按容量轮转，而时间基线决定这些证据能不能对账 | 日志查不到是因为没写进来、被限流，还是被裁掉了 |
| 6 | 退场与重来 | 它用退出码与 `Result` 定性，用 `Restart=` 决定是否重来，用 `KillMode=` 与超时决定怎么收尾，最后用启动节流决定还让不让重来 | 「反复重启」与「彻底不再重启」为什么是两套机制 |
| 7 | 常驻 | 它按 `[Install]` 与 `enable` 决定开机时是否参与，用 `mask` 决定能不能被拉起 | `disable` 与 `mask` 的边界在哪里 |

### 四个跨阶段的核对对象

有四类量各自贯穿上面多个阶段，排障时按它们切分比从头走一遍时间线更快。下面每一条都写明它贯穿哪几个阶段，以及在这些阶段上分别读什么字段。

| 跨阶段的核对对象 | 它贯穿哪几个阶段 | 每一处读什么字段 |
| --- | --- | --- |
| 配置的生效层级 | 它贯穿阶段 1 到阶段 6，因为同一个属性在磁盘文件、manager 的认知与进程的实际状态三处各有一个取值，而 drop-in、`daemon-reload`、`reload` 与 `restart` 分别只推进其中一段 | 在阶段 1 读 `systemctl cat` 的 `# <路径>` 来源行与 `show -p FragmentPath -p DropInPaths`；在阶段 2 到阶段 6 读 `show -p <属性>` 给出的 manager 当前值；在阶段 3 到阶段 6 再读 `/proc/<MainPID>/environ`、`/proc/<MainPID>/limits` 与 `MainPID`，用来判断进程是否换过 |
| 启动、运行与退出的判据 | 它贯穿阶段 3 到阶段 6，因为启动由 `Type=` 与 `NotifyAccess=` 判定、结束由 `Result` 与退出码判定、此刻由 `ActiveState`/`SubState` 判定，同一个单元在这三套判据上可以给出互相矛盾的印象 | 在阶段 3 读 `show -p Type -p NotifyAccess -p SubState`；在阶段 5 读 `show -p ActiveState -p SubState -p NRestarts` 与 `journalctl -u <unit> -b`；在阶段 6 读 `show -p Result -p ExecMainCode -p ExecMainStatus -p MainPID` |
| 上限与沙箱的作用点 | 它贯穿阶段 1、阶段 4 与阶段 6，因为 `MemoryMax=`/`CPUQuota=`/`TasksMax=` 一类上限落在 cgroup 节点上，`ProtectSystem=`/`User=`/`CapabilityBoundingSet=` 一类沙箱落在进程的命名空间与凭证上，而两者的配置都写在 unit 里、都要靠 `restart` 才落到进程 | 在阶段 1 读 `show -p MemoryMax -p CPUQuotaPerSecUSec -p TasksMax -p ProtectSystem -p User -p CapabilityBoundingSet`；在阶段 4 读 `/sys/fs/cgroup<ControlGroup>/{memory.max,memory.high,cpu.max,pids.max}` 与 `/proc/<pid>/cgroup`；在阶段 6 读 `memory.events` 的 `oom_kill` 与内核日志里的 `oom_memcg=` |
| 证据的落点与时效 | 它贯穿阶段 3 到阶段 7，因为退出码与 `Result` 会被 `restart`、`reset-failed` 覆盖，cgroup 目录随单元结束被回收，未持久化的日志随重启消失，而 `--vacuum-*` 会删掉历史启动的记录 | 在阶段 3 到阶段 6 读 `show -p Result -p NRestarts -p ExecMainStatus` 与 `journalctl -u <unit> -b --no-pager`；在阶段 5 读 `journalctl --disk-usage`、`--list-boots` 与 `ls -ld /var/log/journal`；在阶段 7 读 `show -p UnitFileState`、`is-enabled` 与 `list-unit-files` 的 `STATE`/`PRESET` |

在这四项之外还有一件不是机制的事：**变更纪律**。改 unit、drop-in、`journald.conf`、tmpfiles 规则之前先留基线（把 `systemctl cat` 的输出导出留档），一次只改一项，改完用同一条命令复测；重启服务前确认还有一个已登录的 root 会话或带外通道。

## 术语速查

| 名词 | 一句话解释 | 在哪一篇展开 |
| --- | --- | --- |
| unit | 它是 systemd 管理的最小对象，服务、套接字、目标、定时器、挂载点与 slice 都属于它，并且它有文件形式与运行时形式两种存在方式 | 原理：装载与生效链 |
| target | 它是一组 unit 的集合，用来替代旧的 runlevel，`multi-user.target` 与 `default.target` 都属于这一类 | 原理：装载与生效链 · 体系：一个 unit 的一生 |
| slice / scope | slice 是 cgroup 层级的组织单位，而 scope 是由 systemd 之外的创建者建立、再交给 systemd 管理的进程组，登录会话就属于后者 | 原理：约束与隔离 · 体系 |
| drop-in | 它是挂在某个 unit 名下的一小份配置片段，文件名形如 `*.d/override.conf`，用来在不改原文件的前提下覆盖同名键、追加新键 | 原理：装载与生效链 |
| `FragmentPath` / `DropInPaths` | `FragmentPath` 是 manager 实际读的那个 unit 文件，`DropInPaths` 是叠进这份生效配置的片段清单，两者合起来才是当前生效配置 | 原理：装载与生效链 |
| `daemon-reload` | 它让 PID 1 重读全部 unit 文件与 drop-in 并重建依赖树，但**不重启任何服务**，因此运行中的进程不受影响 | 原理：装载与生效链 |
| `daemon-reexec` | 它让 PID 1 重新执行自身，因此 manager 自身的配置被重读；它不重读 unit 文件，那是 `daemon-reload` 的职责 | 原理：装载与生效链 · 实操 |
| 模板单元 / `%i` | `foo@.service` 这样的模板配上 `systemctl start foo@abc` 就能批量创建同构实例，其中 `%i` 会被替换成实例名 | 原理：装载与生效链 |
| `Wants=` / `Requires=` | 两者都回答「要不要把对方拉起来」：`Wants=` 是弱依赖，对方失败不牵连自己；`Requires=` 是强依赖，对方停止或重启会带上自己 | 原理：编队与并行 |
| `After=` / `Before=` | 两者只表达顺序而不产生依赖，因此不写它们时两个单元会被并行启动 | 原理：编队与并行 |
| `Type=` | 它声明 systemd 用什么方式判定「这次启动算完成」，取值有 simple、exec、forking、oneshot、notify、notify-reload、dbus 与 idle 八种 | 原理：什么算启动完成 |
| `NotifyAccess=` | 它限定谁有资格发 `sd_notify` 通知，取值有 `main`（缺省）、`exec` 与 `all`，因此由子进程或包装器发出的通知可能不被接受 | 原理：什么算启动完成 |
| `RemainAfterExit=` | 它让 `oneshot` 单元跑完之后仍保持 `active (exited)` 而不转到 `inactive`，这样别的单元才能依赖「这件事做过了」 | 原理：什么算启动完成 |
| socket 激活 | 它让 `.socket` 单元在服务不运行时替服务持有监听套接字，直到第一个连接到达才把服务拉起来 | 原理：什么算启动完成 |
| `LimitNOFILE=` | 它是写在 unit 里的句柄上限，与登录会话侧的 `limits.conf`、shell 内置的 `ulimit` 是三套互不替代的机制 | 原理：约束与隔离 |
| `TasksMax=` | 它限定该单元内允许存在的进程与线程总数，落到 cgroup 的 `pids.max`，因此是整组共享的一份上限 | 原理：约束与隔离 |
| `MemoryMax=` / `MemoryHigh=` | `MemoryMax=` 是 cgroup 的内存硬上限，超出后先触发回收、回收无效才在该组内触发 OOM；`MemoryHigh=` 是软上限，超出后只加大回收压力并节流 | 原理：约束与隔离 |
| `CPUQuota=` | 它限定每个周期最多能用多少算力，属于配额而不是绑核；要绑核应当用 `CPUAffinity=` 或 `AllowedCPUs=` | 原理：约束与隔离 |
| `ProtectSystem=` / `PrivateTmp=` | `ProtectSystem=` 把 `/usr`、`/boot` 一类系统目录挂成只读，`PrivateTmp=` 则给服务一个私有的 `/tmp` 与 `/var/tmp` | 原理：约束与隔离 |
| `ReadWritePaths=` | 它在 `ProtectSystem=` 造成的只读世界里列出仍然允许写入的路径，而这些路径必须已经存在 | 原理：约束与隔离 |
| `RuntimeDirectory=` / `StateDirectory=` | 它们让 systemd 以正确的属主创建目录并管理权限：`RuntimeDirectory=` 落在 `/run` 下、重启即失，`StateDirectory=` 落在 `/var/lib` 下、跨重启保留 | 原理：约束与隔离 · 实操 |
| capabilities / `CapabilityBoundingSet=` | capabilities 把 root 的特权拆成一项项独立权限，而 `CapabilityBoundingSet=` 限定该服务最多能持有哪些项 | 原理：约束与隔离 |
| `NoNewPrivileges=` | 它禁止该服务及其子进程通过 `setuid` 位或文件能力再获得新特权，一处生效而整棵进程树受益 | 原理：约束与隔离 |
| journald | 它是 systemd 的日志收集器，把服务的标准输出、syslog 套接字、内核消息与审计四类来源收进来，并按字段建立索引 | 实操：观测与基线 · 体系 |
| `_SYSTEMD_UNIT` / `__MONOTONIC_TIMESTAMP` | `_SYSTEMD_UNIT` 说明这条消息属于哪个单元，`__MONOTONIC_TIMESTAMP` 是单调时钟戳；后者不受 NTP 调整影响，因此跨日志源排序要用它 | 实操：观测与基线 |
| `SystemMaxUse=` / `--vacuum-*` | `SystemMaxUse=` 规定 journal 的总容量上限，`--vacuum-size=`/`--vacuum-time=`/`--vacuum-files=` 则按容量、时间或文件数裁剪已归档文件 | 实操：观测与基线 |
| `Restart=` / `RestartSec=` | 它们决定服务退出后是否自动拉起以及隔多久拉起，其中 `Restart=` 缺省是 `no`，要常驻必须显式写 | 体系：一个 unit 的一生 · 实操 |
| `KillMode=` | 它决定停止服务时杀谁，取值有 `control-group`（缺省，收掉整个控制组）、`mixed`、`process` 与 `none` | 体系：一个 unit 的一生 |
| `StartLimitIntervalSec=` / `StartLimitBurst=` | 它们规定在 `StartLimitIntervalSec=` 这个时间窗内允许启动几次，超过 `StartLimitBurst=` 之后就不再重试；两个键都写在 `[Unit]` 小节 | 体系：一个 unit 的一生 · 判例 |
| `reset-failed` | 它清掉单元的失败状态与重启计数，使单元能够再次启动；它不修根因，因此不是修复动作 | 体系：一个 unit 的一生 · 判例 |
| `enable` / `mask` | `enable` 按 `[Install]` 建自启软链，`mask` 则用一条指向 `/dev/null` 的同名软链把单元彻底屏蔽 | 体系：一个 unit 的一生 · 判例 |
| `preset` | 它是发行版给出的一套规则，决定新安装的单元默认是否 `enable`，因此装完软件包有的服务会自己起来 | 体系：一个 unit 的一生 · 治理 |
| `OnCalendar=` / `Persistent=` | `OnCalendar=` 让 timer 按日历式时刻触发，`Persistent=` 则让关机期间错过的日历式触发在开机后补跑一次 | 实操：观测与基线 |
| `AccuracySec=` | 它规定 timer 允许在目标时刻前后抖动多久，缺省是 `1min`；这样省电，代价是触发时间会推迟 | 实操：观测与基线 |
| tmpfiles / `age-by` | tmpfiles 按声明式规则创建与清理易失路径，`age-by` 则是规则里判断「多老才清」的前缀，例如 `m:30d` 表示只看 mtime | 实操：观测与基线 |
| `timedatectl` / `systemd-timesyncd` | `timedatectl` 用来查看与设置系统时间、时区与 NTP（Network Time Protocol，网络时间协议）同步状态，`systemd-timesyncd` 是 Ubuntu 缺省的时间同步客户端，RHEL 系则缺省用 `chrony` | 实操：观测与基线 |

## 故障现场定位表

排障的第一问不是「怎么修」，而是「**systemd 此刻依据的是哪一份配置、这次失败落在哪个阶段、证据在哪**」。下表把现象先归到阶段，再指出该读哪些字段，然后进对应篇目。

| 你看到的现象 | 它属于哪个阶段 | 现场在哪 | 第一反应不要做 |
| --- | --- | --- | --- |
| 改了 unit 却不生效 | 这属于装载阶段的问题，因为生效配置由磁盘文件、drop-in 与 manager 的认知共同决定 | 先用 `systemctl cat` 看每个键来自哪个文件，再用 `show -p FragmentPath -p DropInPaths` 确认实际吃的是哪一份，最后确认 `daemon-reload` 是否执行过 | 不要只 `restart` 而不看生效值 |
| `Loaded: not-found`、名字拼错、新文件找不到 | 这属于装载阶段的问题，因为 unit 文件没有被搜索路径命中 | 先用 `systemctl cat` 与 `list-unit-files` 确认名字与路径，再确认新文件落地后是否执行过 `daemon-reload` | 不要重装软件包 |
| 服务 `start` 失败，退出码 `203/EXEC` | 这属于装载阶段的问题，因为 systemd 无法执行 `ExecStart=` 指定的主命令 | 先读 `journalctl -u <unit>` 里的退出码与路径，再核对执行位与 shebang 解释器 | 不要先怀疑业务代码 |
| 服务 `start` 失败，退出码 `200/CHDIR` | 这属于装载阶段的问题，因为 systemd 无法进入 `WorkingDirectory=` 指定的目录 | 先读 `show -p WorkingDirectory -p User`，再用 `namei -l` 看该目录对 `User=` 是否可达 | 不要只改文件权限 |
| 明明有进程，服务却立刻 `inactive (dead)` | 这属于判定阶段的问题，因为 `Type=` 的判据与进程模型不匹配 | 先读 `show -p Type -p SubState`，再读 `show -p MainPID -p Result` | 不要写个 `while true` 硬撑 |
| 应用日志已打印就绪，systemd 仍等满超时 | 这属于判定阶段的问题，因为通知的发送者不符合 `NotifyAccess=` 的资格 | 先读 `journalctl -u <unit>` 里「只允许主 PID」一类记录，再读 `show -p Type -p NotifyAccess` | 不要断定 systemd 有 bug |
| 端口在听，服务却是 `inactive` | 这属于判定阶段的 socket 激活，因为持有监听套接字的是 `.socket` 单元而不是服务本身 | 先读 `systemctl list-sockets` 的 `UNIT` 与 `ACTIVATES` 两列，再读 `status` 里的 `TriggeredBy:` 行 | 不要以为服务挂了 |
| 服务 `active (running)` 但业务不可用 | 这属于判定阶段与约束阶段的交界，因为 `start` 成功只说明 `Type=` 判定通过 | 先读 `ss -lntp` 看端口是否在听，再读 `show -p Environment -p WorkingDirectory` 与依赖单元的日志 | 不要把 `start` 返回 0 当验收通过 |
| 服务反复重启，过一会儿彻底不再重启 | 这属于退场与重来阶段的问题，因为启动节流在窗口内拒绝继续启动 | 先读 `show -p Result -p NRestarts -p StartLimitBurst`，再在 `journalctl -u <unit>` 里找 `start-limit-hit` | 不要直接把 `StartLimitBurst` 调大 |
| 关机或重启卡在 `A stop job is running for ...` | 这属于退场与重来阶段的问题，因为应用在 `TimeoutStopSec=` 窗口内没有响应 `KillSignal=` | 先读 `show -p KillMode -p TimeoutStopUSec`，再在 `journalctl -u <unit>` 里找 `stop-sigterm` 超时记录 | 不要改成 `KillMode=none` 或把超时拉到无限大 |
| 服务报错 `226/NAMESPACE`、`217/USER`、`216/GROUP` | 这属于约束与隔离阶段的问题，因为沙箱或身份切换在启动时就没有搭起来 | 先读 `show -p ProtectSystem -p ReadWritePaths -p User -p Group`，再确认路径存在且用户存在 | 不要直接关掉全部沙箱 |
| 服务在跑但读不到数据、写不进去 | 这属于约束与隔离阶段的问题，因为沙箱改变了服务看到的世界 | 先读 `show -p Environment -p WorkingDirectory -p PrivateTmp -p ReadWritePaths`，再确认该路径是否在可写口清单里 | 不要认定是代码问题 |
| 服务把 CPU、内存或句柄用到上限而把邻居拖垮 | 这属于约束阶段的问题，因为该单元的资源上限缺省是 `infinity` | 先读 `show -p MemoryMax -p CPUQuotaPerSecUSec -p TasksMax`，再用 `systemd-cgtop` 看整棵树里谁在消耗 | 不要先扩容主机 |
| 日志查不到、查不全、被写满 | 这属于运行与留痕阶段的问题，因为落点、归属、保留、限流与过滤是五件不同的事 | 先读 `journalctl -u <unit> -b`，再读 `--disk-usage` 与 `journald.conf` 的容量与持久化设置 | 不要先关掉限流 |
| 日志时间对不上、跨机对账失败 | 这属于留痕阶段的时间基线问题，因为墙钟会被 NTP 调整 | 先读 `timedatectl` 的两行，再读 `timedatectl timesync-status` 的 `Packet count` 与 `Offset` | 不要在时钟不同步时下结论 |
| 服务没开机自启、想彻底停用一个服务 | 这属于常驻阶段的问题，因为开机是否参与由 `[Install]` 与 `enable` 决定 | 先读 `is-enabled`，再读 `default.target.wants` 下的软链，最后确认是否需要用 `mask` | 不要以为 `disable` 就等于彻底停了 |
| 开机变慢，说不清谁拖慢 | 这属于跨阶段的状态基线问题，因为并行启动的单元会同时出现在 `blame` 的输出里 | 先读 `systemd-analyze blame` 列出候选，再读 `critical-chain` 看关键路径上真正的阻塞项 | 不要把 blame 第一名当阻塞源 |
| 定时任务到点没跑 | 这属于跨阶段的定时任务问题，因为触发与执行由 timer 和 service 两个对象分别承担 | 先读 `list-timers` 的 `NEXT`/`LAST`/`ACTIVATES` 三列，再读 `crontab -l` 与 `journalctl -u cron` | 不要先怪 cron 坏了 |
| `/tmp` 文件莫名消失、清理没生效 | 这属于跨阶段的临时文件问题，因为清理判据由 tmpfiles 规则与 `PrivateTmp=` 分别决定 | 先用 tmpfiles 规则与 `systemctl list-timers systemd-tmpfiles-clean.timer` 看谁在清，再读 `stat -c %y %z` 与 `findmnt -T /tmp` | 不要删掉 `/tmp` 清理规则 |

两个容易被忽略的边界：

- **`systemctl` 返回 0 不代表服务可用。** `start` 成功只说明 `Type=` 判定通过；端口、依赖、健康检查都可能还没就绪，因此验收必须落在业务层面。
- **「服务没起来」和「服务没就绪」是两件事。** 前者卡在装载、判定或沙箱，后者是 `active (running)` 但依赖未就绪、端口未监听。若把两者混在一起问，就会得出「systemd 说在跑，怎么还用不了」这样的结论。
