> [!info] 读之前：先自检三条前提

## 0. 30 秒速览

> [!abstract] 这一章只要记住七句话
> 首学读不懂很正常：先跳过这一节，读完第 1 节和子笔记 01、03 再回来逐条验证——每一条都是「结论 + 一句可复现的证据」。
> - **一个服务 = 一份 unit 说明书 + 一个 cgroup 笼子 + 一堆留在 journald 的证据**。`systemctl status` 的三段（`Loaded`/`Active`/`CGroup`）恰好对应这三件事，排障第一反应就是把它们读全。
> - **改 unit 文件不等于生效，`daemon-reload` 也不等于重启服务**：实测完整链条是「改文件 → `status` 出现 changed on disk 警告、manager 里仍是旧值 → `daemon-reload` 后 manager 变新值、**运行中的进程环境仍是旧值** → `restart` 后才是新值」。读生效值用 `systemctl show -p ...` 与 `systemctl cat`，不要只看文件。
> - **依赖是两层，别混**：`Wants=`/`Requires=` 决定「要不要拉起对方」，`After=`/`Before=` 只决定「谁先谁后」，不写 `After` 就并行。实测（system 单元）`lab08-a` 在 `08:05:09.561` 结束，`lab08-b` 才在 `08:05:09.575` 开始（相隔 13.8 毫秒）；把 `After=` 去掉后两者在 0.8 毫秒内先后启动，`lab08-b` 先跑完而 `lab08-a` 还在 `sleep`。
> - **`Type=` 决定「什么算启动完成」，选错就是「假启动失败」**：同一条 `ExecStart=/bin/bash -c "sleep 120 &"`，实测 `Type=simple` 立刻 `inactive (dead)`（后台进程被控制组清掉），`Type=forking` 则 `active (running)`、`MainPID=sleep`；`Type=notify` 默认 `NotifyAccess=main`，**fork 出来的子进程直接发 `READY=1` 会被拒**（日志 `reception only permitted for main PID`），实测默认超时 **90.237 秒**；同一个子进程改成 `NotifyAccess=all` 后 **0.039 秒** 启动成功，主进程自己发只要 **0.033 秒**。注意 `systemd-notify` 是特例：它把发送者 PID 伪造成父进程，所以 shell 里调它反而能被 `NotifyAccess=main` 接受。
> - **资源上限的落点是 unit，不是 `limits.conf`**：实测 `LimitNOFILE=64` → 服务内 `ulimit -n` 为 64；`MemoryMax=32M` → cgroup `memory.max=33554432`；`CPUQuota=10%` → `cpu.max=10000 100000`，而 `CPUQuota=20%` 的 `while :; do :; done` 在 10.1 秒墙钟里只拿到 **2.02 秒 CPU**（无配额的对照组是 10.01 秒）。system 单元的默认句柄上限是**硬 524288 / 软 1024**（`LimitNOFILE` / `LimitNOFILESoft` 两个属性，只看 `show -p LimitNOFILE` 会把硬值当成服务实际可用值而误判），另有 `TasksMax=9374`、`KillMode=control-group`、`TimeoutStopUSec=1min 30s`、`RestartUSec=100ms`。
> - **沙箱选项会改变服务看到的世界，报错形态是 systemd 退出码**：`PrivateTmp=yes` 实测服务内 `/tmp` inode 是 1311092、宿主是 1179649；`ProtectSystem=strict` 让服务命名空间里的 `/` 变成 `ro`，`ProtectHome=yes` 把 `/home` 换成只读空 tmpfs；`ReadWritePaths=` 指向不存在的路径 → `226/NAMESPACE`；system 单元里 `User=` 真的能换身份（实测服务内 `uid=1000`），**但 `NoNewPrivs` 与 `CapBnd` 不是 `User=` 的效果**——只写 `User=` 时实测 `CapBnd=000001ffffffffff`（仍是**满集**）、`NoNewPrivs=0`；要清空 bounding set 得另加 `CapabilityBoundingSet=`，要 `NoNewPrivs=1` 得另加 `NoNewPrivileges=yes`，用户不存在报 `217/USER`、组不存在报 `216/GROUP`，**用户单元**里写 `User=root` 也报 `216/GROUP`。`systemd-analyze security` 从 **9.6 UNSAFE** 降到 **1.5 OK**（`ProtectSystem=strict` + `ProtectHome=` + 地址族收敛这一档）/**1.9 OK**（再叠 `User=`、`CapabilityBoundingSet=`、`SystemCallFilter=` 的完整加固单元）；只加 `ProtectSystem=full` 几乎不降分（实测 9.2 UNSAFE），**「防篡改」和「降暴露面」是两件事**。看到 `203/EXEC`、`200/CHDIR` 先查路径与工作目录——把脚本放在 `/tmp` 又开了 `PrivateTmp=yes`，就会直接得到 `203/EXEC`。
> - **定时任务与临时文件的坑集中在「环境」和「时间语义」**：实测 cron 的环境是 `HOME/LOGNAME/PATH/LANG/SHELL=/bin/sh/PWD`（不是你的交互 shell），`%` 必须写成 `\%`；tmpfiles 的 age 默认同时看 **mtime/atime/ctime**——「40 天前 mtime 但今天 ctime」的文件不会被 `--clean` 删除，改成 `m:30d` 才删，这是最容易误判「清理没生效」的一点。

## 1. 知识地图（第一条主线）

### 1.1 一个服务的八站旅程

这一章不按「unit、依赖、日志、timer」四个名词平铺，而是跟着**一个服务的一生**走：从「把要什么写下来」，到「开机时它起不起、起得对不对、跑得稳不稳、出错留没留证据」。

| # | 站点 | systemd 在做什么 | 这一站的证据 | 主要子笔记 |
| --- | --- | --- | --- | --- |
| 1 | 描述与装载 | 按搜索路径读 unit 文件与 drop-in，拼出「生效配置」，放进 manager 的认知 | `systemctl cat`、`show -p FragmentPath -p DropInPaths`、`systemd-analyze unit-paths` | 02、04 |
| 2 | 编队 | 解析 `Wants`/`Requires` 决定拉起谁，`After`/`Before` 决定顺序，默认并行 | `list-dependencies`、`journalctl` 的启动时间戳 | 05 |
| 3 | 判定 | 按 `Type=` 与 `NotifyAccess=` 判定「什么算启动完成」 | `show -p Type -p SubState -p Result`、`result 'timeout'` | 06 |
| 4 | 约束 | 把服务放进 cgroup，按 unit 里的上限限流（CPU/内存/句柄） | `show -p MemoryMax -p CPUQuotaPerSecUSec`、`/sys/fs/cgroup/.../*.max` | 07 |
| 5 | 隔离 | 沙箱选项改变服务看到的文件系统/设备/权限，capabilities 收敛特权 | `show -p ProtectSystem -p PrivateTmp`、退出码 `226`/`216` | 08 |
| 6 | 留痕 | 把 stdout/syslog/kmsg 收进 journald，按字段索引、按容量轮转 | `journalctl -u`、`-o json`、`--disk-usage` | 09 |
| 7 | 退场与重来 | 退出码、`Restart=`、`KillMode=`、`StartLimit*` 决定怎么收尾与是否重来 | `show -p Result -p NRestarts`、`start-limit-hit` | 10 |
| 8 | 常驻开机 | `[Install]`/`WantedBy` 与 `enable`/`mask` 决定开机起不起、能不能起 | `is-enabled`、`default.target.wants` 软链 | 11 |

```mermaid
flowchart LR
  A["① 描述与装载<br/>unit 文件 · drop-in"] --> B["② 编队<br/>Wants/Requires · After"] --> C["③ 判定<br/>Type= · NotifyAccess"] --> D["④ 约束<br/>cgroup · 资源上限"]
  D --> E["⑤ 隔离<br/>沙箱 · capabilities"] --> F["⑥ 留痕<br/>journald"] --> G["⑦ 退场与重来<br/>Restart · StartLimit"] --> H["⑧ 常驻开机<br/>enable · mask · target"]
```

真正要练出来的，是同一个三问：

1. **systemd 现在知道的是什么？** —— 它用的是「manager 里的生效配置」，不是你磁盘上刚改的文件；两者不一致时，一切结论都会错（子笔记 04）。
2. **卡在八站的哪一站？** —— 是文件没读到、依赖没拉起、`Type=` 判定不对、资源上限打满、沙箱挡住了、日志没进来、重启被节流，还是根本没开机自启？每一站都有**能取到的证据**（子笔记 03、15）。
3. **这个动作是止血还是修复？** —— `restart`、`reset-failed`、调大 `StartLimitBurst`、关掉沙箱都可能是「让现象消失」，但根因还在。先分清影响面，再决定动不动手（子笔记 10、15）。

### 1.2 四条横切线

八站是时间线，但有几件事会横穿多个站点。新人最容易「每一站都看过，却串不起来」，就是没抓住这四条线：

| 横切线 | 贯穿内容 | 收口于 | 主要子笔记 |
| --- | --- | --- | --- |
| **生效链** | 文件 → manager 的认知 → 进程实际环境；drop-in、`daemon-reload`、`reload` 与 `restart` 的边界 | 「改了配置没生效」的定位树 | 02、04、06、10、15 |
| **拉起与排序** | 依赖（拉不拉起）与顺序（谁先谁后）是两件事，并行是默认；`[Install]` 决定开机时是否参与 | 「A 比 B 先就绪」「服务没自启」类问题 | 05、11、12 |
| **约束与隔离** | cgroup/slice → 资源上限 → 沙箱与 `User=` → capabilities 最小特权 | 一个 unit 既是「说明书」也是「笼子」 | 07、08、11、13 |
| **可观测** | 退出码、`Result`、unit 字段、journald 字段与容量、时间基线 | 服务故障的取证与复盘 | 03、06、09、10、14、15 |

还有一条不是机制，而是动作：**变更纪律**。改 unit、drop-in、`journald.conf`、`tmpfiles` 规则之前先留基线（`systemctl cat` 导出留档），一次只改一项，改完用同一条命令复测；重启服务前确认控制台/带外可用，避免把自己关在外面。

## 3. 四级训练台阶

技能靠难度递增、风险可控的重复练习获得。**每一级都写明了在哪台机器上做**，这条边界本身就是 S7 的训练内容。

| 台阶 | 做什么 | 在哪台机器 | 交付物 |
| --- | --- | --- | --- |
| **T0 读通** | 画出八站判定链；说清「服务起不来」至少要看哪几站 | 纸面/白板 | 自己画的一张 systemd 判定链图 |
| **T1 观测** | 采集服务、自启、timer/cron、`/tmp` 清理、时间基线；全程只读 | **生产机可以做（只读）** | 服务与定时任务基线卡 |
| **T2 可回滚变更** | 用 drop-in 改一个 unit、加一条 timer、改一条 tmpfiles 规则，改完复测并回滚 | 实验机（root，system 单元） | 变更记录（含验证与回滚） |
| **T3 故障注入与恢复** | 造一次 `Type=` 假失败、一次 `start-limit-hit`、一次沙箱 `226/NAMESPACE`、一次 tmpfiles age 误判 | **可快照实验机** | 演练记录 + 分层判读结论 |
| **T4 限时模拟** | 给一个现象（例如「服务 active 但行为不对」「定时任务没跑」），15 分钟内定位并写出处置记录 | 实验机 + 计时 | 一份排障报告 |

> [!warning] 两条不能破的边界
> **只有 T1 允许在生产机上做，而且全程只读**：`systemctl status/cat/show/list-*`、`journalctl`、`systemd-analyze blame/critical-chain`、`timedatectl`。任何会 `start`/`stop`/`restart`/`daemon-reload`/`edit` 的动作都属于 T2 及以上。
> **T2 到 T4 一律在可快照实验机**：改 unit、`daemon-reload`、`mask`、改 `journald.conf`、`crontab -` 之前先备份原文件与 `crontab -l > ~/crontab.bak`（`crontab -` 与 `crontab -r` 会覆盖/删除当前用户的整份 crontab）；系统单元变更前先确认还有一个已登录的 root 会话。

## 4. 学习路线

**系统学的三遍读法（对应阶段 8 的 3~5 天）：**

- **第一遍（约一天，建立判定链）**：第 1 节 → 前置 01–03 → 04（装载与生效）→ 06（`Type=` 与假失败）→ 15 的「起不来/不生效」两节 → 实验 1、2。这一遍结束应该能处理「改了配置没生效」和「服务 active 但没就绪」。
- **第二遍（约两天，把约束与留痕补齐）**：05（依赖与顺序）→ 07（cgroup 与资源）→ 08（沙箱与最小权限）→ 09（journald）→ 10（退出与重启）→ 11（自启与屏蔽）→ 实验 3、4、5、6。
- **第三遍（治理与收口）**：12（timer 与 cron）→ 13（临时文件治理）→ 14（系统状态与时间基线）→ 15 其余各节 → 16 汇总自测 → T3、T4。

> | capabilities / `CapabilityBoundingSet` | 把 root 特权拆成能力项 / 限定服务最多持有哪几项 | 08 |

## 6. 故障现场定位表

排障的第一问不是「怎么修」，而是「**systemd 现在依据的是什么、这次失败发生在八站的哪一站、证据在哪**」。用这张表把现象定位到站点，再进对应子笔记。

| 你看到的现象 | 卡在哪一站 | 现场在哪 | 第一反应不要做 | 去哪一篇 |
| --- | --- | --- | --- | --- |
| 改了 unit 却不生效 | 1 装载 | `systemctl cat`、`show -p FragmentPath -p DropInPaths`、`/proc/<pid>/environ` | 不要只 `restart` 不看生效值 | 04、15 |
| `Loaded: not-found` / 名字拼错 / 新文件找不到 | 1 装载 | `systemctl cat`、`list-unit-files` | 不要重装软件包 | 04、15 |
| 服务 `start` 失败，`status=203/EXEC` | 1 装载 | `journalctl -u` 的退出码 | 不要先怀疑业务代码 | 03、15 |
| 服务 `start` 失败，`status=200/CHDIR` | 1 装载 | `WorkingDirectory=` | 不要改文件权限了事 | 03、15 |
| 服务立刻 `inactive (dead)`，明明有进程 | 3 判定 | `show -p Type -p SubState` | 不要写个 `while true` 硬撑 | 06、15 |
| 日志打印了 ready，systemd 仍等 90 秒超时 | 3 判定 | `show -p Type -p NotifyAccess` | 不要断定 systemd 有 bug | 06、15 |
| 端口在听但服务 `inactive` | 3 判定（socket 激活） | `systemctl list-sockets` | 不要以为服务挂了 | 06 |
| 服务 `start` 失败，`status=226/NAMESPACE`、`217/USER` 或 `216/GROUP` | 5 隔离 | `show -p ProtectSystem -p ReadWritePaths -p User -p Group` | 不要直接关掉全部沙箱 | 08、15 |
| 服务 `active` 但读不到数据 / 写不进去 | 5 隔离 | `Environment`、`WorkingDirectory`、`PrivateTmp`、`ReadWritePaths` | 不要认定是代码问题 | 08、15 |
| 服务反复重启后彻底不再重启 | 7 退场 | `Result`、`NRestarts`、`StartLimit*` | 不要直接把 `StartLimitBurst` 调大 | 10、15 |
| 关机/重启卡在 `A stop job is running for ...` | 7 退场 | `show -p KillMode -p TimeoutStopUSec`、`journalctl -u <unit>` | 不要直接改成 `KillMode=none` 或把超时拉到无限大 | 10、15 |
| 日志查不到 / 查不全 / 被写满 | 6 留痕 | `journalctl -u -b`、`--disk-usage`、`show -p StandardOutput` | 不要先关掉限流 | 09、15 |
| 定时任务到点没跑 | 横切（定时） | `list-timers`、`crontab -l`、`journalctl -u cron` | 不要先怪 cron 坏了 | 12、15 |
| `/tmp` 文件莫名消失 / 清理没生效 | 横切（临时文件） | tmpfiles 规则、`PrivateTmp`、`stat -c %y %z` | 不要删掉 `/tmp` 清理规则 | 13、15 |
| 服务没开机自启 / 想彻底停用一个服务 | 8 常驻 | `is-enabled`、`default.target.wants`、`mask` | 不要以为 `disable` 就彻底停了 | 11、15 |
| 开机变慢 / 说不清哪个服务拖慢 | 2、8 + 基线 | `systemd-analyze blame` 与 `critical-chain` | 不要把 blame 第一名当成阻塞源 | 14、15 |
| 日志时间对不上 / 跨机对账失败 | 横切（时间基线） | `timedatectl`、`timesync-status` | 不要在时钟不同步时下结论 | 14、15 |

两个容易被忽略的边界：

- **`systemctl` 命令返回 0 不代表服务可用。** `start` 成功只说明 `Type=` 判定通过；服务可能端口没起来、连不上数据库、健康检查没过。**验收永远落在业务层面**（端口、日志、指标），不是命令退出码。
- **「服务没起来」和「服务没就绪」是两件事。** 前者卡在装载/判定/隔离；后者是 `active (running)` 但依赖未就绪、端口未监听。混在一起问，就会得出「systemd 说在跑，怎么还用不了」这种结论。
