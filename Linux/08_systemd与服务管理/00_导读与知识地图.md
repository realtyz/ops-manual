# systemd、服务与定时任务

## 知识地图

### 一个 unit 的一生

时间主线跟着**一个 unit**走：从磁盘上的一份配置文件，到被装载成 manager 认知里的「生效配置」，到编队、拉起、判定就绪，到被放进笼子里约束与隔离，到运行中把证据留在 journald，到退出后决定重来还是就此退场，最后到开机时它是否还参与。

```mermaid
flowchart LR
  A["① 装载<br/>文件 → 生效配置"] --> B["② 编队<br/>依赖 · 顺序 · 并行"]
  B --> C["③ 判定<br/>什么算启动完成"]
  C --> D["④ 约束与隔离<br/>cgroup · 沙箱 · 最小权限"]
  D --> E["⑤ 运行与留痕<br/>journald · 时间基线"]
  E --> F["⑥ 退场与重来<br/>退出码 · Restart · 节流"]
  F --> G["⑦ 常驻<br/>enable · mask · target"]
  E -.->|"定时与临时文件<br/>旁挂的 unit"| G
```

| # | 站点 | systemd 在做什么 | 到这里要能说清 |
| --- | --- | --- | --- |
| 1 | 装载 | 按搜索路径读 unit 文件与 drop-in，拼出生效配置，装进 manager 的认知 | 生效配置是哪几个文件拼出来的；改了文件为什么 manager 与进程都还是旧值 |
| 2 | 编队 | 解析 `Wants=`/`Requires=` 决定拉起谁，`After=`/`Before=` 只决定先后，缺省并行 | 依赖与顺序是两层；「对方被拉起」不等于「对方已就绪」 |
| 3 | 判定 | 按 `Type=` 与 `NotifyAccess=` 判定这次启动算不算完成 | 同一条命令为什么在 `simple` 下立刻 dead、在 `forking` 下常驻、在 `notify` 下等满超时 |
| 4 | 约束与隔离 | 把服务放进 cgroup 并按 unit 属性限流；沙箱选项改变它看到的世界，能力集收敛特权 | 上限配在哪一层；沙箱报错为什么是 systemd 退出码而不是应用的错 |
| 5 | 运行与留痕 | 把服务的标准输出、syslog 套接字、内核消息（`kmsg`）与审计（audit）四类来源收进 journald，按字段索引、按容量轮转；时间基线决定证据能不能对账 | 日志查不到是没写进来、被限流、还是被裁掉了 |
| 6 | 退场与重来 | 退出码与 `Result` 定性，`Restart=` 决定是否重来，`KillMode=` 与超时决定怎么收尾，启动节流决定还让不让重来 | 「反复重启」和「彻底不再重启」是两套机制 |
| 7 | 常驻 | `[Install]` 与 `enable` 决定开机时是否参与，`mask` 决定能不能被拉起 | `disable` 与 `mask` 的边界在哪 |

### 四条横切线

| 横切线 | 贯穿内容 | 收口于 |
| --- | --- | --- |
| 生效链 | 磁盘文件 → manager 的认知 → 进程的实际环境；drop-in、`daemon-reload`、`reload` 与 `restart` 的边界 | 「改了配置没生效」的定位树 |
| 判据链 | `Type=` 与 `NotifyAccess=` 判定启动、`Result` 与退出码判定结束、`ActiveState`/`SubState` 判定当前 | 「启动了但不可用」与「死了但没报错」怎么分开 |
| 边界线 | cgroup/slice → 资源上限 → 沙箱与 `User=` → capabilities 最小特权 | 一个 unit 既是说明书，也是笼子 |
| 留痕线 | 退出码、`Result`、unit 属性、journald 字段与容量、时间基线 | 故障取证与复盘 |

在这四条之外还有一件不是机制的事：**变更纪律**。改 unit、drop-in、`journald.conf`、tmpfiles 规则之前先留基线（`systemctl cat` 导出留档），一次只改一项，改完用同一条命令复测；重启服务前确认还有一个已登录的 root 会话或带外通道。

## 术语速查

| 名词 | 一句话解释 | 在哪一篇展开 |
| --- | --- | --- |
| unit | systemd 管理的最小对象（service/socket/target/timer/mount/slice…），有文件形式与运行时形式 | 原理：装载与生效链 |
| target | 一组 unit 的集合（旧 runlevel 的替代），如 `multi-user.target`、`default.target` | 原理：装载与生效链 · 体系：一个 unit 的一生 |
| slice / scope | cgroup 层级的组织单位 / 由外部创建的进程组（如登录会话） | 原理：约束与隔离 · 体系 |
| drop-in | 不改原文件、只追加覆盖片段的 `*.d/override.conf` | 原理：装载与生效链 |
| `FragmentPath` / `DropInPaths` | manager 实际读的那个文件 / 生效配置里叠进来的片段清单 | 原理：装载与生效链 |
| `daemon-reload` | 让 PID 1 重读全部 unit 文件与 drop-in、重建依赖树；**不重启任何服务** | 原理：装载与生效链 |
| `daemon-reexec` | 让 PID 1 重新执行自身，重读 manager 自身配置；不重读 unit 文件 | 原理：装载与生效链 · 实操 |
| 模板单元 / `%i` | `foo@.service` 配 `systemctl start foo@abc` 批量创建同构实例，`%i` 是实例名 | 原理：装载与生效链 |
| `Wants=` / `Requires=` | 弱依赖 / 强依赖：要不要把对方拉起来 | 原理：编队与并行 |
| `After=` / `Before=` | 只表达顺序；不写就并行启动 | 原理：编队与并行 |
| `Type=` | 判定「服务启动完成」的方式：simple/exec/forking/oneshot/notify/notify-reload/dbus/idle | 原理：什么算启动完成 |
| `NotifyAccess=` | 谁有资格发 `sd_notify`：`main`（默认）/`exec`/`all` | 原理：什么算启动完成 |
| `RemainAfterExit=` | `oneshot` 跑完仍保持 `active` 而不转 `inactive` | 原理：什么算启动完成 |
| socket 激活 | 服务不在跑时由 `.socket` 帮它监听，第一个连接到达才拉起服务 | 原理：什么算启动完成 |
| `LimitNOFILE=` | unit 里的句柄上限；与 `limits.conf`、`ulimit` 是三套东西 | 原理：约束与隔离 |
| `TasksMax=` | 该单元内允许的进程/线程总数（cgroup 的 `pids.max`） | 原理：约束与隔离 |
| `MemoryMax=` / `MemoryHigh=` | cgroup 内存硬上限（撞上会杀）/ 软上限（只节流） | 原理：约束与隔离 |
| `CPUQuota=` | 每个周期最多用多少算力（配额），不是绑核 | 原理：约束与隔离 |
| `ProtectSystem=` / `PrivateTmp=` | 把系统目录挂成只读 / 给服务一个私有 `/tmp` | 原理：约束与隔离 |
| `ReadWritePaths=` | 在只读世界里开出可写的口子 | 原理：约束与隔离 |
| `RuntimeDirectory=` / `StateDirectory=` | 由 systemd 创建并管权限的目录；system 单元落 `/run`、`/var/lib` | 原理：约束与隔离 · 实操 |
| capabilities / `CapabilityBoundingSet=` | 把 root 特权拆成能力项 / 限定服务最多能持有哪些项 | 原理：约束与隔离 |
| `NoNewPrivileges=` | 禁止通过 `setuid`/文件能力再提权 | 原理：约束与隔离 |
| journald | systemd 的日志收集器：收 stdout/syslog/kmsg/audit，按字段索引 | 实操：观测与基线 · 体系 |
| `_SYSTEMD_UNIT` / `__MONOTONIC_TIMESTAMP` | 消息属于哪个单元 / 单调时钟戳（不受 NTP 调整影响） | 实操：观测与基线 |
| `SystemMaxUse=` / `--vacuum-*` | journal 总容量上限 / 按容量、时间或文件数裁剪 | 实操：观测与基线 |
| `Restart=` / `RestartSec=` | 退出后是否自动拉起、隔多久 | 体系：一个 unit 的一生 · 实操 |
| `KillMode=` | 停止服务时杀谁：`control-group`（默认）/`mixed`/`process`/`none` | 体系：一个 unit 的一生 |
| `StartLimitIntervalSec=` / `StartLimitBurst=` | 时间窗内允许启动几次，超了就不再重试（写在 `[Unit]`） | 体系：一个 unit 的一生 · 判例 |
| `reset-failed` | 清掉失败状态与重启计数，让服务能再次启动 | 体系：一个 unit 的一生 · 判例 |
| `enable` / `mask` | 按 `[Install]` 建自启软链 / 用指向 `/dev/null` 的软链彻底屏蔽 | 体系：一个 unit 的一生 · 判例 |
| `preset` | 发行版用 preset 文件决定新装单元默认是否 enable | 体系：一个 unit 的一生 · 治理 |
| `OnCalendar=` / `Persistent=` | timer 的日历式触发 / 关机期间错过的补跑一次 | 实操：观测与基线 |
| `AccuracySec=` | timer 允许的时间抖动窗口（默认 1min，省电但会推迟触发） | 实操：观测与基线 |
| tmpfiles / `age-by` | 按声明式规则创建与清理易失路径 / age 的判据前缀（如 `m:30d` 只看 mtime） | 实操：观测与基线 |
| `timedatectl` / `systemd-timesyncd` | 查看与设置系统时间、时区、NTP（Network Time Protocol，网络时间协议）同步 / 时间同步客户端；Ubuntu 默认 `systemd-timesyncd`，RHEL 系默认 `chrony` | 实操：观测与基线 |

## 故障现场定位表

排障的第一问不是「怎么修」，而是「**systemd 此刻依据的是哪一份配置、这次失败发生在哪一站、证据在哪**」。用这张表把现象定位到站点，再进对应篇目。

| 你看到的现象 | 属于哪一站 | 现场在哪 | 第一反应不要做 |
| --- | --- | --- | --- |
| 改了 unit 却不生效 | 装载 | `systemctl cat`、`show -p FragmentPath -p DropInPaths`、`daemon-reload` 是否执行过 | 不要只 `restart` 而不看生效值 |
| `Loaded: not-found`、名字拼错、新文件找不到 | 装载 | `systemctl cat`、`list-unit-files` | 不要重装软件包 |
| 服务 `start` 失败，退出码 `203/EXEC` | 装载 | `journalctl -u` 里的退出码与路径 | 不要先怀疑业务代码 |
| 服务 `start` 失败，退出码 `200/CHDIR` | 装载 | `WorkingDirectory=` 与 `User=` 的可达性 | 不要只改文件权限 |
| 明明有进程，服务却立刻 `inactive (dead)` | 判定 | `show -p Type -p SubState` | 不要写个 `while true` 硬撑 |
| 应用日志已打印就绪，systemd 仍等满超时 | 判定 | `show -p Type -p NotifyAccess` | 不要断定 systemd 有 bug |
| 端口在听，服务却是 `inactive` | 判定（socket 激活） | `systemctl list-sockets` | 不要以为服务挂了 |
| 服务 `active (running)` 但业务不可用 | 判定 · 边界 | 端口、依赖、健康检查、`Environment=`、`WorkingDirectory=` | 不要把 `start` 返回 0 当验收通过 |
| 服务反复重启，过一会儿彻底不再重启 | 退场与重来 | `show -p Result -p NRestarts -p StartLimitBurst`、`journalctl -u` 的 `start-limit-hit` | 不要直接把 `StartLimitBurst` 调大 |
| 关机或重启卡在 `A stop job is running for ...` | 退场与重来 | `show -p KillMode -p TimeoutStopUSec`、`journalctl -u` | 不要改成 `KillMode=none` 或把超时拉到无限大 |
| 服务报错 `226/NAMESPACE`、`217/USER`、`216/GROUP` | 沙箱与最小权限 | `show -p ProtectSystem -p ReadWritePaths -p User -p Group` | 不要直接关掉全部沙箱 |
| 服务在跑但读不到数据、写不进去 | 沙箱与最小权限 | `Environment=`、`WorkingDirectory=`、`PrivateTmp=`、`ReadWritePaths=` | 不要认定是代码问题 |
| 服务吃满 CPU/内存/句柄把邻居拖垮 | cgroup 约束 | `show -p MemoryMax -p CPUQuotaPerSecUSec -p TasksMax`、`systemd-cgtop` | 不要先扩容主机 |
| 日志查不到、查不全、被写满 | 留痕 | `journalctl -u -b`、`--disk-usage`、`journald.conf` 的容量与持久化 | 不要先关掉限流 |
| 日志时间对不上、跨机对账失败 | 留痕（时间基线） | `timedatectl`、`timedatectl timesync-status` | 不要在时钟不同步时下结论 |
| 服务没开机自启、想彻底停用一个服务 | 常驻 | `is-enabled`、`default.target.wants` 软链、`mask` | 不要以为 `disable` 就等于彻底停了 |
| 开机变慢，说不清谁拖慢 | 横切（状态基线） | `systemd-analyze blame` 与 `critical-chain` | 不要把 blame 第一名当阻塞源 |
| 定时任务到点没跑 | 横切（定时） | `list-timers`、`crontab -l`、`journalctl -u cron` | 不要先怪 cron 坏了 |
| `/tmp` 文件莫名消失、清理没生效 | 横切（临时文件） | tmpfiles 规则、`PrivateTmp=`、`stat -c %y %z` | 不要删掉 `/tmp` 清理规则 |

两个容易被忽略的边界：

- **`systemctl` 返回 0 不代表服务可用。** `start` 成功只说明 `Type=` 判定通过；端口、依赖、健康检查都可能没就绪。验收落在业务层面。
- **「服务没起来」和「服务没就绪」是两件事。** 前者卡在装载、判定或沙箱；后者是 `active (running)` 但依赖未就绪、端口未监听。混在一起问，就会得出「systemd 说在跑，怎么还用不了」。
