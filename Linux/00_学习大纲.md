# Linux 运维学习大纲（生产级）

> **定位**：一条面向运维/SRE 面试的学习路径——不是把命令再过一遍，而是把「生产中真正会遇到的问题」和「面试官真正会追问的点」对齐。
> **前置基础**：会日常 Shell 操作、懂文件权限的基本概念、用过 `top`/`ps`/`systemctl`、能读写简单的 bash 脚本。
>
> 原则：每个模块都按 **概念 → 生产实践 → 要点自测** 三层推进。每一条 checklist 的标准不是「知道这个命令」，而是「能讲清它的语义、边界，以及出问题时怎么用它定位」。

## 学习路径总览（Roadmap）

| 阶段  | 主题              | 建议周期  | 产出目标                                    |
| --- | --------------- | ----- | --------------------------------------- |
| 1   | 实验环境与操作纪律       | 2~3 天 | 有可快照的实验机，能交出基线卡、变更记录与演练记录                |
| 2   | 启动流程、内核与系统初始化   | 3~5 天 | 讲清从加电到登录的全链路，能救回一台起不来的机器                |
| 3   | 进程、信号与资源隔离      | 3~5 天 | 能定位进程卡死、杀不掉、进程数打满；讲清 namespace/cgroup   |
| 4   | 内存管理与 OOM       | 3~5 天 | 讲清可用内存、Page Cache、OOM 判定与 swap 取舍       |
| 5   | 存储、文件系统与 IO     | 4~6 天 | 讲清 inode / 挂载 / LVM / RAID，处理磁盘满与 IO 瓶颈 |
| 6   | 网络协议栈与排障 ★      | 5~7 天 | 按六站分层定位连接/丢包/吞吐问题，用 `ss`/`tcpdump` 取证   |
| 7   | 权限、账号与安全加固      | 3~5 天 | 按十站定位权限拒绝与提权面，能按基线加固一台生产机并做应急取证         |
| 8   | systemd、服务与定时任务 | 3~5 天 | 能排查服务起不来，正确写 unit 与 timer               |
| 9   | 日志、监控与可观测性      | 1 周   | 建立日志轮转与指标采集，告警能落到具体动作                   |
| 10  | 性能分析与故障排查 ★     | 1~2 周 | 用一套方法论把 CPU / 内存 / IO / 网络问题定位到根因       |
| 11  | 生产运维、变更与高可用     | 1 周   | 独立完成一次带回滚的生产变更，交得出变更单、恢复记录与 Runbook    |

> 标 ★ 的 **阶段 6（网络）** 与 **阶段 10（性能排障）** 是运维面试区分度最高的两块：命令谁都会敲，能从现象推到根因的人不多，优先打透。

> **不在本大纲范围内的部分**：GPU 驱动与内核模块、PCIe/NUMA 拓扑、RDMA/RoCE 无损网络、perftest 基线与 XID 硬件故障处理属于 AI 基础设施主题域，见 [[AI-Infra/00_简介|AI-Infra 大纲]]。本大纲只在阶段 6 与阶段 10 保留通用主机侧的调优与观测入口，重复的概念不在这里展开。
>
> 容器运行时（Docker/containerd、镜像与联合文件系统存储驱动）与编排层（Kubernetes 对象、控制器、CNI/CSI）属于容器主题域，见 [[Kubernetes/00_简介|Kubernetes 大纲]]。本大纲只保留容器赖以成立的三个宿主侧机制（namespace / cgroup / 联合文件系统），以及「站在宿主机上看容器」的排障入口。

## 这套大纲怎么用（面试导向）

**面试官真正在考什么**

不是「你记得多少命令」，而是**从现象到根因的推理链**。任何一道运维题，都用同一个骨架作答：

> 现象与影响面 → 分层定位（哪一层）→ 用什么命令取证据 → 结论与根因 → 止损动作 → 长期改进

**三条练习纪律**

- 每个知识点都要能回答三问：**是什么、边界在哪、生产上怎么用**。
- 每个现象都要准备一份「**第一反应不要是什么**」。会讲「不要随手 `kill -9`、不要在生产机上不限流抓包、不要用 `setenforce 0` 掩盖问题」，比多背十个命令更能体现经验。
- 所有结论尽量带**量化**：负载除以核数、`si/so` 是否长期非 0、`await` 与业务延迟的对应关系。只说「感觉慢」在面试里等于没答。

**与 Kubernetes 笔记的关系**

本套笔记是 [[Kubernetes/00_简介|Kubernetes 大纲]] 的前置。阶段 3（cgroup/namespace）、阶段 6（网络）会直接复用到 [[Kubernetes/03_调度_资源_QoS]] 与 [[Kubernetes/04_网络]]，排障方法论也是同一套；两套笔记建议交叉复习。

## 阶段 1：实验环境与操作纪律

> **对应笔记**：[[Linux/01_实验环境与操作纪律/00_导读与知识地图|01 实验环境与操作纪律]]（已按「主笔记 + 子笔记」拆分，共 11 篇）
>
> 知识主线是「**一次手工变更的四站**」：上机（基线卡 + 工具箱）→ 变更前（备份 + 回滚 + 时间窗）→ 现场（同时刻取证）→ 演练（弄坏并救回）；三条横切线是发行版差异、资料与工具来源、风险分级。**技能主线**是 S1–S8 八项可交付能力，配 T0–T4 四级训练台阶。子笔记清单、技能地图与四级台阶都在主笔记里。
>
> 难度分两层：子笔记 08（动态链接库排障）属**核心 + 进阶**，第一遍知道有这条路即可，等真遇到「命令跑不起来」再回来查；其余篇目属于本阶段必须掌握的核心。**读者定位**：会基本 shell、用过 `top`/`ps`/`systemctl`，但没系统整理过「在哪台机器上做、坏了怎么回滚、证据去哪取」。

### 1.1 上机与基线（01–04）

- [ ] 实验机三要件：**能快照、能进控制台、与生产隔离**；知道本地虚拟化 / 云主机 / WSL2 / 容器四种环境的边界，并能用 `systemd-detect-virt` 与 `ls /sys/firmware/efi` 现场确认
- [ ] 三条快照纪律：动手前打快照并记下名字、快照不是备份、演练前用控制台登录一次；并理解「回滚快照 ≠ 回到过去」（时间与外部状态不在快照里）
- [ ] 四项版本基线：发行版（`/etc/os-release`）、内核（`uname -r`）、systemd、cgroup 版本（`stat -fc %T /sys/fs/cgroup`），外加资源、根文件系统、时间、虚拟化类型、工具版本
- [ ] 发行版家族：血统与派生关系（Fedora → RHEL → Rocky/Alma、Debian → Ubuntu）、发布节奏与支持周期（LTS/EOL），以及**内核版本号不能跨发行版直接比较**（RHEL 的 backport 策略）
- [ ] 发行版差异四件套：包管理（`dnf`/`apt` 的源配置）、防火墙（firewalld/ufw/nftables）、网络配置（NetworkManager/netplan）、访问控制（SELinux/AppArmor），并会用 `command -v` 与 `rpm -qf`/`dpkg -S` 现场判断
- [ ] 诊断工具箱按「现象 → 工具」装齐：`sysstat`（`sar`/`iostat`/`pidstat`）、`iotop`、`lsof`、`strace`、`tcpdump`、`perf`、`bpftrace`、`iftop`、`numactl`、`smartmontools`、`iperf3`、`stress-ng`、`openssl`、`nc`；能说出 `sysstat` 的历史数据前提与 `perf`/`bpftrace` 的内核依赖
- [ ] 会用 `man`：`man 1` 命令、`man 2` 系统调用、`man 3` 库函数、`man 5` 配置文件格式、`man 7` 概览、`man 8` 管理命令，并知道 `/usr/share/doc/` 与 `--help` 的分工

### 1.2 变更、取证与演练（05–08）

- [ ] 变更前三件套：带时间戳的备份、写下来的回滚命令、确认过的时间窗；能用六要素（目标 / 范围 / 备份 / 回滚 / 验证 / 窗口）写一份变更记录
- [ ] 取证纪律：现象发生时先取一组**同时刻**证据（时间与身份 / CPU 与负载 / 内存与压力 / IO 与容量 / 连接与协议栈 / 进程与内核日志），并说清哪些证据重启即失
- [ ] 明白「重启能解决 90% 的问题，但会毁掉 100% 的现场」，知道 `journalctl -b -1` 依赖日志持久化，以及历史数据要去 `sar` 或外部监控取
- [ ] 在实验机上主动做破坏性演练（至少三项）：打满一个独立文件系统、写坏 `/etc/fstab`、`down` 掉网卡、改坏 `/etc/passwd`，以及用 `echo c > /proc/sysrq-trigger` 触发内核 panic，并各自走通恢复路径
- [ ] 知道 `kernel.sysrq` 是位掩码：常用安全位是 `176`（sync + remount-ro + reboot），`1` 会连危险位一起打开
- [ ] 记住一个反直觉点：**主机上的 PID 1 不会被 `SIGKILL`/`SIGSTOP` 杀死**——普通用户拿到 `EPERM`，root 下内核不执行这些信号的默认终止动作；容器里的 PID 1 受同样保护，但能从宿主机按宿主 PID 杀掉
- [ ] 动态链接库排障：`ldd`、`readelf -d`、`ldconfig -p`、`LD_DEBUG=libs`、`/etc/ld.so.conf.d/`，以及 `error while loading shared libraries` 的四步处理顺序（确认缺哪个库 → 装没装 → 补搜索路径 → `ldconfig` 后复验）；知道 `LD_LIBRARY_PATH` 只影响当前进程树

### 1.3 收口（09–10）

- [ ] 能按处置手册定位八类现象：SSH 不通但有控制台、进 `emergency mode`、`passwd` 改坏、系统起不来、`command not found`、库找不到、回滚后现象对不上、panic 之后取现场
- [ ] 每类现象都能说出「第一步证据 → 处置动作 → 验收标准 → 回滚方式」，并写成一段 Runbook 片段

**生产实践**

- 实验机和生产机严格分开；生产上的任何手工改动都要有回滚命令，而不是「不行再改回来」
- 把诊断命令整理成「现象 → 工具」速查表，而不是按字母背命令
- 发行版差异要先于命令记忆：RHEL 与 Debian 系在排障入口上差别很大，面试时答错方向很扣分
- 破坏性演练只在实验机做：`sysrq` 的危险位（触发 panic 与强制重启）在生产机上是关掉的，动手前先确认自己在哪台机器的控制台上
- 排障动作按「只读先于写入、应用层先于内核层、单机先于集群、限流先于重启」排序；一个动作只改一个变量
- 每个动作先写下「预期效果 + 验收指标 + 回滚方式」，验收用「命令复验 + 业务探活 + 观察窗口」三件套

**交付物与要点自测**

- 交付物：一份本机基线卡、一份「命令 → 家族 → 是否可用」对照记录、一份工具箱体检结果、一份「问题 → man 章节 → 结论」检索记录、一份带回滚命令的变更记录、一个同时刻取证包、一份演练记录 + 至少一段 Runbook 片段
- 给你一台陌生的机器，5 分钟内你怎么判断它「有没有问题」？（负载、内存水位、磁盘空间与延迟、连接数，看趋势而非瞬时值）
- 为什么说「重启能解决 90% 的问题，但会毁掉 100% 的现场」？
- `man 1/2/3/5` 分别看什么？举三个你会先查 `man 5` 的配置文件。
- RHEL 系和 Debian 系，装包、开端口、配 IP、看安全策略的入口分别差在哪？
- 程序报 `error while loading shared libraries`，你怎么在四步之内定位并持久修好？

## 阶段 2：启动流程、内核与系统初始化

> **对应笔记**：[[Linux/02_启动流程与内核/00_导读与知识地图|02 启动流程与内核]]
>
> 本阶段已改为「主笔记（知识地图 + 生产技能地图）+ 子笔记（逐项深入）」结构：**入口是 [[Linux/02_启动流程与内核/00_导读与知识地图|02 启动流程与内核]]**，本页 checklist 按技能交付物验收；子笔记清单、技能地图（S1–S8）与四级训练台阶（T0–T4）都在主笔记里。
>
> 子笔记按难度分了两层：索引里标 **【进阶】** 的篇目（内核升级/回滚与热补丁、崩溃取证 kdump 与 vmcore）第一遍只需知道有这条路，等真正用到（或到阶段 11）再补；其余篇目属于本阶段必须掌握的核心。知识主线是「**五环接力**」：固件 → GRUB2 → 内核 + initramfs → systemd → 登录；三条横切线是存储、内核、服务。

### 2.1 启动链与救援

- [ ] 完整启动链：固件（BIOS/UEFI）→ GRUB2 → 内核 + `initramfs` → `systemd`（PID 1）→ `default.target`，并知道每一环失败时的典型现象
- [ ] GRUB 交互与应急：编辑启动项进 `rescue.target` / `emergency.target`、`init=/bin/bash`、只读根重新挂载
- [ ] 忘记 root 密码的恢复路径（`rd.break` 等），以及为什么这在生产上属于安全事件
- [ ] `initramfs` 的职责（加载根文件系统所需的存储/文件系统驱动）与重建（`dracut -f` / `update-initramfs -u`）
- [ ] 内核启动参数：临时（GRUB 编辑）、持久（`/etc/default/grub` + `grub2-mkconfig`）、生效后复查（`/proc/cmdline`）——它只在启动时生效，与运行时内核参数是两套东西
- [ ] 运行时内核参数：`sysctl -w` 临时改、`/etc/sysctl.d/*.conf` + `sysctl --system` 持久化、`sysctl -a` 与 `/proc/sys/` 的对应关系
- [ ] 内核模块：`lsmod` / `modprobe` / `modinfo` / blacklist；驱动加载失败怎么看 `dmesg`

### 2.2 启动后排查与内核升级

- [ ] 排查工具：`journalctl -b` / `-b -1`、`systemd-analyze blame` / `critical-chain`、`dmesg -T`
- [ ] 内核升级与回滚：升级前留好退路、通过包管理升级、保留旧内核启动项、重启后验证与回滚
- [ ] 【进阶】`kexec` 快速重启与 Livepatch/热补丁各自解决什么问题、边界在哪
- [ ] 【进阶】内核崩溃取证：`kdump` + `kexec` 抓 `vmcore`，用 `crash` 做初步分析
- [ ] 启动耗时与依赖：哪些服务在拖慢开机、`After`/`Wants` 写错会怎样（详见阶段 8）

**生产实践**

- 生产机永远保留至少一个可用的旧内核启动项；内核升级要排维护窗口，并在重启后验证关键服务与业务指标
- 关键服务器开 `kdump` 并预留 `crashkernel` 内存，否则 panic 之后只剩一句「机器重启了」，没有现场
- 改 `/etc/fstab` 后先 `mount -a` 验证再重启——这是「重启起不来」的头号原因
- 确认带外管理可用（IPMI/iDRAC/云控制台）：根分区损坏、网络配置写错时，这是唯一的救援通道

**要点自测**

- 从按下电源到出现登录提示符，中间发生了什么？云主机上最常出问题的是哪一环？
- `initramfs` 是干什么的？为什么换了存储控制器或做了根分区迁移后系统可能起不来？
- 一台机器卡在 GRUB 或卡在 `emergency.target`，你的处理顺序分别是什么？
- `journalctl -b -1` 在什么场景下是救命命令？
- `sysctl -w` 改过的参数重启后会怎样？想持久化该写到哪里，`/etc/sysctl.conf` 与 `/etc/sysctl.d/` 谁先谁后？

## 阶段 3：进程、信号与资源隔离

> **对应笔记**：[[Linux/03_进程与信号/00_导读与知识地图|03 进程与信号]]
>
> 本阶段已改为「主笔记（知识地图 + 生产技能地图）+ 子笔记（逐项深入）」结构：**入口是 [[Linux/03_进程与信号/00_导读与知识地图|03 进程与信号]]**，本页 checklist 按技能交付物验收；子笔记清单、技能地图（S1–S8）与四级训练台阶（T0–T4）都在主笔记里。
>
> 子笔记按难度分了两层：索引里标 **【进阶】** 的篇目（状态与调度、崩溃取证 core 与 coredumpctl）第一遍只需知道有这条路，用到时再回来查；其余篇目属于本阶段必须掌握的核心。知识主线是「**一个进程的一生**」四站：诞生 → 运行与等待 → 被通知 → 结束与回收；三条横切线是信号、限制、隔离。

- [ ] 进程与线程：`ps -eLf`、`/proc/<pid>/task`、`fork`/`exec`/`clone` 的语义差异
- [ ] 进程状态：`R/S/D/T/Z/I` 的含义，**D 状态为什么 `kill -9` 也杀不掉**，僵尸进程由谁回收
- [ ] 工具分工：`ps`、`top`（含 `top -H` 看线程）、`pidstat`、`pstree`，以及直接读 `/proc/<pid>/{status,wchan,stack,io}`
- [ ] 信号语义：`SIGTERM` vs `SIGKILL`、`SIGHUP` 与配置重载、`SIGUSR1/2`、`SIGSTOP`/`SIGCONT`，以及 `kill -9` 的代价（文件锁、临时文件、数据不一致）
- [ ] 进程退出的三种死法：正常退出码、被信号杀死（退出码 128+N）、被 OOM Killer 选中——`systemctl status` 里的 `signal`/`core-dump` 字段与 `dmesg` 的 OOM 记录分别对应哪一种
- [ ] 用户态崩溃取证：core dump（`ulimit -c`、`/proc/sys/kernel/core_pattern`、systemd-coredump 的 `coredumpctl list`/`info`），以及为什么生产上要限制 core 文件体积
- [ ] 【进阶】优先级与调度：`nice`/`renice`、`chrt` 与实时调度、`taskset` 做 CPU 亲和
- [ ] 资源限制：`ulimit`（`nofile`/`nproc`/`stack`）、`/etc/security/limits.conf` 与 systemd `LimitNOFILE` 的关系——**改 `limits.conf` 对 systemd 服务无效**；`prlimit` 查看与调整运行中进程的限制
- [ ] 资源耗尽：`kernel.pid_max`、`kernel.threads-max`、fork 风暴现象、`fs.file-max` 与句柄上限
- [ ] 孤儿与僵尸：容器里 PID 1 为什么必须处理信号并回收子进程

**生产实践**

- 排查卡死服务先看状态：D 状态查 IO / 网络挂载，Z 状态查父进程，R 状态但不推进查锁与 CPU

**生产实践**

- 可观测性按四件套落地：日志（落点+持久化+轮转）、指标（每机采集+保留）、告警（`up`/水位/证书/错误率，每条有动作）、SLO（至少一个核心服务）；先闭环再扩指标

- 容器与服务问题必须同时取容器内与宿主侧证据：限流看 `cpu.stat`、OOM 看 `memory.events`、IO 限速看 `io.max`；容器内 `top` 不代表容器的真实约束

- [ ] 资产与依赖台账：硬件 / 固件 / 系统三组信息的采集命令（`lscpu`、`free -h`、`lsblk`、`dmidecode`、`lspci`、`ethtool -i`、`systemd-detect-virt`）；一阶依赖怎么用 `ss -lnt` + `ss -tnp` + `systemctl list-dependencies --reverse` 画出来；三类隐式依赖（定时任务、证书、采集代理）；配置漂移的发现方式
- [ ] 可恢复性的语言：RTO / RPO / MTTR / MTTD 各自约束什么；备份、快照、副本、归档四种东西各不能防什么；幂等与可重入的区别；验收三件套（指标 + 业务 + 观察窗口）
- [ ] 变更单六要素：目标、范围、备份、回滚、验证、窗口；写「范围」时要同时写「不改什么」，写「回滚」时要写「触发条件」而不只是命令
- [ ] 评审会必答四问：影响面多大、最坏结果是什么、怎么退回去（多久）、执行时谁有权喊停；紧急变更允许「先做后补」，但必须补单并复盘

### 11.2 准备、执行与收口（05–08）

- [ ] 变更前的三类备份对象（配置文件 / 数据 / 系统状态）与三条合格线（唯一的名字、不在被改动路径内、能 `diff` 与恢复验证）；`cp -a` 到带时间戳目录，并把状态快照（服务、监听、挂载、参数、启停清单）一并采集
- [ ] 回滚的四种形态（配置 / 版本 / 服务 / 数据）与两种假回滚（重启服务、换回文件但不 reload）；回滚命令必须在实验机上跑过并记下耗时，回滚触发条件必须写成「指标 + 阈值 + 持续时间」
- [ ] 灰度分批的四个维度（实例 / 故障域 / 流量 / 租户）与批次大小、观察时间的算法（批次不超过「总容量 − 最小可接受容量」留出的余量；观察时间覆盖一个业务周期与 2~3 个采样间隔）
- [ ] 执行顺序：摘流量（如需要）→ 改 → 单机验证 → 放回流量 → 观察；摘流量的验收是「从外部探失败、从本机探成功」；批次决策点四选一（继续 / 扩批 / 暂停 / 回滚），「解释不了但服务还活着」一律归为暂停
- [ ] 三层验收：单机（运行时值、`systemctl show`、新增报错）、集群（可用实例数、容量水位、冗余）、业务（真实业务路径，而不是只打 `/healthz`）；四种「假成功」（重启后恢复、没有告警、探活全过、跟以前一样）
- [ ] 收口四件事：归档记录（改前 + 改后 + 变更窗口日志）、更新台账与文档、闭环改进项、沉淀 Runbook；复盘六段（时间线 / 影响面 / 证据 / 根因 / 止损动作 / 改进项），并且**「人为失误」不算根因**
- [ ] 改进项写成「有动作、有 owner、有期限、有验收方式」的句子；三种去向：立即修、排期、显式接受风险（含批准人）

### 11.3 横切能力（09–15）

- [ ] 批量运维与自动化纪律（09）：批量 `ssh` 的连接层坑（连接放大、无超时、首连交互）与环境层坑（非交互 shell 不读 `.bashrc`、`PATH` 与别名不同）；Ansible 的 inventory / playbook / 幂等，`--check`、`--limit`、`serial`、`forks` 各自解决什么；脚本四件套（`set -euo pipefail`、`trap ... EXIT`、`timeout`、显式退出码）与 `flock` 防并跑
- [ ] 备份与恢复（10）：决定方案的四个问题（备什么、备到哪、多久一次、怎么验证）；三种粒度（文件级 / 块级 / 应用级）；运行中的数据库不能只靠复制文件——三条一致性路径；3-2-1 与「1 份离线或不可变」；恢复演练八步与实测 RTO
- [ ] 【进阶】灾难恢复（11）：四类灾难（系统起不来、根分区损坏、关键文件误删、整机不可用）各自的最短路径；「修还是重来」的两分钟判断；文件误删的黄金几分钟（停止写入、`lsof +L1`、从备份恢复，**不要先重启**）；带外管理与救援介质的提前准备清单
- [ ] 高可用与故障域（12）：六层故障域（进程 → 主机 → 机架 → 可用区 → 机房 → 共享依赖）与「拔掉一台业务还剩多少」的判定；VIP/VRRP 与脑裂、独立心跳链路与仲裁、fencing；健康检查判得太松与太严的后果；连接排空；N+1/N+2 余量与滚动重启批次的关系
- [ ] 容量、日志与目录治理（13）：`df` 与 `du` 不一致的四类成因；扩容是一条链（云盘：卷 → 分区 → 文件系统；LVM：`pvresize` → `lvextend -r`）与「扩容后必须看 `df`」；journald 的 `SystemMaxUse` 与 `logrotate` 的分工；临时文件治理的四个字段（owner / 保留期 / 上限 / 告警）；容器数据目录的三个增长来源
- [ ] 系统基线与参数治理（14）：`sysctl` 的加载顺序（目录合并按文件名排序、同名文件 `/etc` 优先、最后应用 `/etc/sysctl.conf`，**后加载覆盖先加载**）与「改了不生效」的五步排查；常见调优项的副作用（`somaxconn`、临时端口、`tcp_tw_reuse`、`fs.file-max` 与 `LimitNOFILE`、脏页回写）；参数台账的六个字段；BIOS/UEFI、RAID 卡与 BBU、网卡固件为什么要进台账，以及「虚拟化环境会伪造硬件信息」（GPU/网卡固件的深水区见 [[AI-Infra/00_简介|AI-Infra 大纲]]）
- [ ] 证书、补丁与合规（15）：证书四个时间点与到期检查命令（`openssl s_client -servername`，必须从外部连、必须按剩余天数告警）；证书链不全为什么表现为「部分客户端连不上」；内部 CA 轮换与 ACME 续期失败的常见原因；补丁三分类与「哪些补丁必须重启」；日志留存的三要素（时钟同步、不可篡改、到期才删）

### 11.4 收口（16–17）

- [ ] 能按处置手册定位十二类场景：变更失败要不要回滚、一批里部分成功、事故刚发生、发布后错误率上升、单机挂了流量没切、根分区满、参数不生效、证书告警、恢复备份失败、系统起不来、批量脚本留半成品、只有一个人会做
- [ ] 每类场景都能说出「第一反应不要做什么 → 证据 → 处置 → 验收 → 升级条件」，并写成一段 Runbook 片段
- [ ] 能背出事故通报模板的七行（现象 / 范围 / 开始时间 / 当前状态 / 已知原因 / 下一步 / 下次通报），并把「事实 / 推测 / 待确认」分开写

**生产实践**

- 所有变更遵循「先备份、再验证、后生效、可回滚」，并且把**回滚命令与触发条件**写下来——写在纸上、在实验机上跑过，才算有回滚方案
- 一次只改一个变量、一批只动一部分；灰度同时覆盖两个维度（先按实例验配置，再按故障域验依赖），每个批次都有明确的决策点
- 内核与系统参数按批次推进，先非核心业务；重启前确认上层集群或负载均衡能承接流量，并算清 N+1/N+2 余量
- 备份的唯一验收标准是「能恢复」：定期做恢复演练并记录耗时，对齐 RTO/RPO；**快照与副本都不算备份**
- 能自动化的手工操作尽量自动化，但脚本必须先满足四件套与幂等，再上生产；批量工具先 `--check`、再 `--limit`、最后分批
- 把「止损」和「根因」分开：事故中先恢复业务并保留现场，复盘阶段再追根因；带着「必须当场查清楚」的心态处置，往往会把故障拖长
- 把「有到期日的东西」全部列成一张表（证书、补丁、固件、支持合同、备份保留期），配上责任人和提前量足够（而不是到期当天）的告警
- 任何「只有我会做」的动作都要写成 Runbook 并让另一个人照着做过一次——否则它随时会变成下一次事故的放大器

**交付物与要点自测**

- 交付物：一份六要素齐全的变更单、一份带实测回滚耗时的变更记录、一份批量执行记录（含幂等检查结果）、一份三层验收记录（含回滚触发线）、一份带回滚与验收标准的止损记录、一份带 RTO 计时的恢复演练记录、一份资产与到期台账、一段 Runbook 片段、一篇含 owner 与期限的复盘
- 变更单六要素是什么？最容易漏的是哪两个？为什么「改动很小」不能作为降级的理由？
- 备份、快照、副本分别不能防什么？为什么说「备份的唯一验收标准是能恢复」？
- 3-2-1 原则是什么？为什么还要加「一份离线或不可变」？
- 要在一批 100 台机器上改一个参数，你的方案是什么？（先手工 1 台 → 幂等脚本/playbook → `--limit` 试跑 → `serial` 分批 → 每批验收 → 回滚条件）
- 灰度分批的依据是什么？批次大小与观察时间怎么算？为什么 `serial: 1` 不等于安全？
- 「拔掉一台业务还剩多少」怎么算？为什么「配了 VIP」不等于高可用？脑裂时应该保可用还是保一致？
- `df` 满了但 `du` 很少，四类原因是什么？分别怎么验证？
- 参数改了不生效，怎么在四步内定位？为什么 `/etc/sysctl.conf` 会让你的文件「失效」？
- 一台核心服务器根分区快满了，处置顺序是什么？哪三样东西不该先删？
- 证书为什么总是到线上才发现过期？到期管理要落哪四件事（台账、按剩余天数告警、续期失败告警、从外部验证）？
- 线上故障发生了，你的前三步是什么？什么时候才轮到查根因？通报里最容易犯的错是什么？
- 怎么向面试官证明你的备份有效、你的恢复能力不依赖某一个人？

### 12.1 前置地基与建图（01–04）

- [ ] 复习的科学（01）：重读只带来「熟悉感」，复习要练的是**提取**；主动回忆的四种做法（闭卷写、白板画、讲给人听、闭卷做题）；间隔重复 **D+1 / D+3 / D+7 / D+21**；交错练习让「先分类」成为习惯；错题本**五列**（题目 / 当时的答案 / 正确口径 / 缺的那一层 / 复查日期），其中「缺的那一层」与「复查日期」最常被省掉
- [ ] 证据与口径（02）：一个数字要带**单位、版本、采集条件**三条尾巴；本套笔记统一容量用 MiB、时间用秒；证据 = 命令 + 输出形态 + 环境 + 时间；分位数要报口径（同一组样本的 p95 按四种算法实测为 **20 / 24 / 96 / 100 ms**）；同机不同窗口的 `w_await` 可以是 **6.85 ms** 也可以是 **54.72 ms**；说不清就显式写「未实测 + 原因 + 补做方式」
- [ ] 知识体系怎么搭（03）：一棵树（CPU / 内存 / IO·存储 / 网络四个资源根 + 权限与安全约束 + systemd 与交付组织层）；五条时间线；**九个连接点**（Page Cache、cgroup、时间同步、PID 1、容器三件套、句柄与端口、内核参数、登录与权限、日志落点）；每个知识点过「是什么 / 边界在哪 / 生产上怎么用」三问；画图三纪律（一图一问、箭头有方向、每框有命令）
- [ ] 建图（04）：半天画出三张图——**资源全景图**（机器上有什么）、**时间线图**（过程怎么走、在哪断）、**排障入口图**（出事先看哪一层）；并把十一个阶段各压成「一句话 + 一条最小证据命令 + 一个带条件的数字」；建图只允许翻术语表，卡住处标「？」交给下一站

### 12.2 自测、补缺与输出（05–08）

- [ ] 自测定位（05）：闭卷、限时、写下来，不会的写「空白」不猜；四档评分（**A 能脱稿讲 / B 有结论无证据 / C 认得但讲不出 / D 完全不会**），C 档最危险、按「完全不会」处理；薄弱排序 = 出现频率 × 影响面 × 不熟练度，**本轮只处理前 5 项**；第一次摸底建议只做阶段 2、4、5、6 四组
- [ ] 补缺深挖（06）：五种缺口（结论 / 判据 / 证据 / 边界 / 代价）各有各的补法；补缺的正确形态是「带着问题回原篇，只读 1~2 篇」；产出是**判据卡 + 一句「第一反应不要做什么」**，不是重抄笔记；补缺顺序先地基后横切——「越读越多」通常说明缺的是前置篇；必须记录「我原来错在哪」
- [ ] 输出固化（07）：一屏一页纸（现象 / 判据 / 命令 / 阈值 / 边界 / 不要做）；三分钟口述六段（现象与影响面 → 分层 → 证据 → 结论 → 止损 → 改进）并**结论先行**；脱稿不是背稿，而是能重建因果链；追问两层（「你怎么知道」与「换个条件呢」）必须都能接住；三种变形要避免：抄写型、菜单型、免责型
- [ ] 迁移应用（08）：迁移三个维度（换现象、换条件、换角色）；限时答辩 3 + 20 + 7 分钟，评分五要素（影响面 / 分层 / 证据 / 边界 / 止损与回滚，各 0~2 分）；追问链四步（证据 → 边界 → 反例 → 代价）；值班视角与面试视角的唯一差别是**先止损还是先讲清楚**；答不出时用「缩小范围 + 下一步验证什么」

### 12.3 横切能力（09–13）

- [ ] 跨章大图（09）：五条时间线并排（启动五环 / 进程一生 / 内存旅程 / 盘的一生 / 连接六站，另加日志与告警两条链路）与**九个连接点**的「两个视角 → 如何对齐 → 最容易答错的地方」；三张跨域图分别收口在连接层、内存层、变更层
- [ ] 场景题答题骨架（10）：十五道场景题（负载高但 CPU 不高 / 内存增长直到 OOM / 磁盘满或 inode 满 / 句柄与进程数耗尽 / 服务连不上 / 偶发延迟丢包 / 服务起不来或定时任务没跑 / 疑似入侵 / 内核 panic / 根分区只读 / 单核打满 / 资源空闲但变慢 / SSH 慢 / 时间漂移 / 容器 OOMKilled）各一份六段骨架，每题至少准备**两个成因**和一句「第一反应不要做什么」
- [ ] 高频易错点榜（11）：八十四组「常见说法 vs 事实」，覆盖内存与资源、进程与信号、存储与 IO、网络、systemd、权限与安全、启动与内核、可观测性与生产八组；用法是**遮住右列自测**并统计每组的错误数，把出错的行抄进错题本
- [ ] 端到端演练（12）：十二个实验编成一条链（只读基线 / `fstab` / 打满文件系统 / 耗尽 inode / cgroup OOM / CPU 限流 / 句柄耗尽 / 单核打满 / 日志轮转写错 / 网络丢包 / 服务起不来 / 只读根与 panic）；三条纪律（隔离 / 上限 / 清理复核）；每个实验必须留下**观测指纹**与**恢复耗时**；非 root 可做八项，其余照实标注未实测
- [ ] 向外连接（13）：容器的三个宿主侧机制（namespace / cgroup / 根文件系统与联合挂载）；Linux 概念 ↔ 容器与编排概念 ↔ 宿主侧证据的对照表；三个高频追问的宿主侧答法（OOMKilled / CPU 被限流 / 网络不通）；云上 Linux 的三层变量（虚拟化、云盘与网络、平台配额，含共享型实例的 CPU 积分）

### 12.4 收口（14–15）

- [ ] 能按现象处置复习盲区：串不起来、看完就忘、每次答案不同、有结论无证据、数字口径混乱、被追问就崩、原理会但给不出命令、场景题没头绪、会讲不敢动手、复习断档、只剩三天、值班前热身、容器题答不上——每类都能说出「缺的是什么 → 去哪一篇 → 怎么练 → 怎么验收」
- [ ] 五件交付物齐备并各有一份验收记录：**体系图、错题本、一页纸、限时答辩记录、端到端演练记录**

**生产实践**

- 复习的时间花在「取」上而不是「看」上：每读一节就合上书写 3~5 行，每次复习都要有产物
- 所有结论带单位、版本与采集条件；本套笔记统一容量 MiB、时间秒；说不清的部分显式标「未实测」
- 答题固定六段骨架（现象与影响面 → 分层 → 证据 → 结论 → 止损 → 改进），并保证每题至少两个成因、一句「第一反应不要做什么」
- 复习动作也遵守生产纪律：T1 只读可在生产机做，T2 以上只在实验机；不做未审批的「验证性变更」，不拿唯一的备份做恢复演练
- 错题按 D+1 / D+3 / D+7 / D+21 复查，只碰「上次标错的」与「快忘的」；每条错题都要指到一篇子笔记
- 排期按三周推进（建图与摸底 → 补缺与输出 → 演练与限时答辩），允许砍内容但不允许砍交付物；每天不超过 3 段 × 25 分钟
- 容器与云上的问题一律「宿主侧 + 容器侧」双视角取证，不把问题推给编排层或平台

**交付物与要点自测**

- 交付物：一张自己画的体系图（资源全景 / 时间线 / 排障入口至少两张）、一本五列错题本（每条含复查日期）、一张一屏一页纸、一份限时答辩记录（含四步追问与自评分数）、一份端到端演练记录（含观测指纹、恢复耗时、清理复核与未实测清单）
- 为什么「看了三遍」还是会忘？主动回忆与间隔重复分别在解决什么问题？
- 一个数字要带哪三条尾巴？同一组样本的 p95 为什么可以是 20 ms 也可以是 100 ms？
- 五条时间线是什么？九个连接点里你能说出哪三个？每个连接点的「最容易答错」是什么？
- 四档评分中哪一档最危险？薄弱排序的三个维度是什么？本轮应该处理几项？
- 五种缺口分别怎么补？为什么「补缺越读越多」通常说明缺的是前置篇？
- 一页纸与三分钟口述的骨架分别是什么？为什么口述要「结论先行」？
- 追问链四步是什么？值班视角与面试视角唯一的差别是什么？
- 十五道场景题里，任抽一道，你能不能说清「分层 → 证据 → 结论 → 止损 → 第一反应不要做什么」？
- 演练的三条纪律与三项清理复核是什么？观测指纹和恢复耗时为什么必须记录？
- 容器被 OOMKilled、CPU 被限流、网络不通时，宿主侧分别看什么？云上 Linux 多了哪三层变量？
- 怎么向面试官证明你在复习上是「有体系」的，而不是「背过多」的？（答：交付物 + 证据 + 边界，而不是结论数量）

## 推荐资源

- `man` 页与发行版官方文档：RHEL 文档、Ubuntu Server Guide、Debian Handbook（版本差异以它们为准）
- 《Linux 性能优化实战》（倪朋飞）：排障与性能分析部分最贴合运维面试
- 《Systems Performance》（Brendan Gregg）与其 USE 方法、FlameGraph 项目
- LWN.net（内核机制与新特性）、kernel.org 的 Documentation/
- 《UNIX/Linux 系统管理手册》（Nemeth 等）：体系化的系统管理视角
- 演练环境：本地 KVM/VM 或按量云主机、Killercoda 场景；破坏性实验只在实验机做
- 各发行版的 release notes：讨论版本差异时的依据，避免凭记忆答题
- Prometheus / Alertmanager 与 OpenTelemetry 官方文档：设计指标、告警与链路追踪时的依据
- `man` 之外的子系统文档：`tc`/`netem`、`nft`、`systemd.*` 子手册页与 kernel.org 的网络文档（阶段 6 与阶段 10 用得最多）
