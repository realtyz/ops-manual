# Linux 运维学习大纲

> **定位**：一条面向运维/SRE 面试的学习路径——不是把命令再过一遍，而是把「生产中真正会遇到的问题」和「面试官真正会追问的点」对齐。
> **前置基础**：会日常 Shell 操作、懂文件权限的基本概念、用过 `top`/`ps`/`systemctl`、能读写简单的 bash 脚本。
>
> 原则：每个阶段按**里程碑**过关，章内按「原理 → 体系 → 实操 → 判例 → 治理」展开。每一条的标准不是「知道这个命令」，而是「能讲清它的语义、边界，以及出问题时怎么用它定位」。

## 这套大纲怎么用

**真正在考什么**

不是「你记得多少命令」，而是**从现象到根因的推理链**。任何一道运维题，都用同一个骨架作答：

> 现象与影响面 → 分层定位（哪一层）→ 用什么命令取证据 → 结论与根因 → 止损动作 → 长期改进

**三条练习纪律**

- 每个知识点都要能回答三问：**是什么、边界在哪、生产上怎么用**。
- 每个现象都要准备一份「**第一反应不要是什么**」。会讲「不要随手 `kill -9`、不要在生产机上不限流抓包、不要用 `setenforce 0` 掩盖问题」，比多背十个命令更能体现经验。
- 所有结论尽量带**量化**：负载除以核数、`si/so` 是否长期非 0、`await` 与业务延迟的对应关系。只说「感觉慢」在面试里等于没答。

**与 Kubernetes 笔记的关系**

本套笔记是 [[Kubernetes/00_简介|Kubernetes 大纲]] 的前置。阶段 3（cgroup/namespace）、阶段 6（网络）会直接复用到 [[Kubernetes/03_调度_资源_QoS]] 与 [[Kubernetes/04_网络]]，排障方法论也是同一套；两套笔记建议交叉复习。

## 阶段 6：网络协议栈与排障 ★（核心区）

> **对应笔记**：[[Linux/06_网络协议栈与排障/00_导读与知识地图|06 网络协议栈与排障]]（已按《写作规约》重写，共 9 篇）
>
> 本阶段是原理 4 篇（分层模型与数据包的一生 · 地址、路由与邻居 · 端口、套接字与多路复用 · 连接的生命周期）+ 体系 1 篇（一次请求的生命周期，含五条横切线）+ 实操 1 篇（协议栈观测与网络基线）+ 判例 1 篇 + 治理 1 篇。**入口是 [[Linux/06_网络协议栈与排障/00_导读与知识地图|06 网络协议栈与排障]]**，本页 checklist 按「到这里要能说清」验收。
>
> 知识主线是「**一次请求的生命周期**」六段：名字到地址 → 地址与出口 → 建链与两个队列 → 传输（窗口、拥塞、重传）→ 断开（`TIME_WAIT`/`CLOSE_WAIT`）→ 链路与转发。五条横切线是队列与上限、证据与计数、名字解析、主机内外、变更纪律。

- [ ] 原理 01（分层模型与数据包的一生）：四层各管什么、各自能出什么错、证据在哪；封装与解封装的方向（发是自上而下，排障是自下而上）；抓包里一行怎么逐段读；MTU 与 MSS 的归属与关系；四元组与两种 socket；网络命名空间与 veth 为什么是容器网络的积木
- [ ] 原理 02（地址、路由与邻居）：用前缀截断判断「在不在同一网段」；路由表的字段与最长前缀优先；`ip route get` 的 `via`/`dev`/`src`/`uid`；源地址是选出来的；`ip rule` 先选表后查表；邻居表五种状态的含义；`ip_forward` 与五链的处理顺序
- [ ] 原理 03（端口、套接字与多路复用）：端口三段划分与 **Linux 自己的源端口范围**（`ip_local_port_range`，不是 IANA 的临时端口段）；两种 socket 上 `Recv-Q`/`Send-Q` 的不同语义；状态集合与责任归属；源端口是一种有限资源（`QPS × 60 秒`）；两个队列与「客户端说连上了、服务端说没见过」
- [ ] 原理 04（连接的生命周期）：应用走 `getaddrinfo()` → NSS，`dig` 绕过它；`getent`/`resolvectl`/`dig` 三个视角；`search` × `ndots` 把一次解析放大成多次；三次握手与两个队列的长度由谁决定；`cwnd` 与 `rwnd` 取小者、`app_limited` 的含义；`cubic` 与 `BBR` 的判据差异；四次挥手、`TIME_WAIT` 的意义与不可调性、`CLOSE_WAIT` 只能改应用
- [ ] 体系 05（一次请求的生命周期）：六段主线一条线走完；每个字段的「是什么 / 单位 / 判据 / 与谁同看 / 转向哪一步」；转发路径上的四道关（转发开关、路由与邻居、`FORWARD` 链、conntrack）；五条横切线的收口
- [ ] 实操 06（协议栈观测与网络基线）：一个问题一把工具，分清**命令**与**内核接口文件**；`ss -s`/`ss -tanp`/`ss -lntp`/`ss -ti` 的分工与逐字段读法；`nstat` 的四种观察方式与「必须取差值」；链路层要换一组工具（`ip -s link`/`ethtool -S/-g`/`softnet_stat`/`interrupts`）；采样纪律与可直接复制的基线卡
- [ ] 判例 07（高频误判）：十四条四段式判例，覆盖「`dig` 通所以应用没问题」「`ping` 通所以网络没问题」「服务端没日志所以请求没到」「一次 `ss` 干净所以队列没满」「调 `tcp_fin_timeout` 治 `TIME_WAIT`」「`CLOSE_WAIT` 是内核参数问题」「只调 `somaxconn` 解决队列溢出」「关掉 `tcp_syncookies` 提性能」「吞吐上不去先扩带宽」「大包不通先扩带宽」「`conntrack -C` 是 0 所以健康」「主机侧干净继续调本机」「`ethtool -S` 计数器可跨机型复用」
- [ ] 治理 08（网络基线与变更治理）：上限配在哪一层（`sysctl` / 内核接口文件 / 模块与算法 / unit 属性 / 应用）与各自的影响范围、持久化位置；四类容量怎么算（源端口、conntrack 表、监听队列、名字解析）；网络基线卡、变更记录、处置记录、MTU/链路变更检查单四份产物模板；哪些故障必须靠计数器告警（日志里可能什么都没有）

> RDMA/RoCE 的无损网络配置（PFC/ECN/DCQCN、GID 索引、交换机侧配合）与 perftest 基线属于 AI 基础设施主题域，见 [[AI-Infra/00_简介|AI-Infra 大纲]] 的 [[AI-Infra/03_RDMA与RoCE无损网络]] 与 [[AI-Infra/04_perftest与性能基线]]。

**生产实践**

- 分层排查是基本功：能 `ping` 通不代表 TCP 能连（防火墙、`FORWARD` 链），TCP 能连不代表应用正常（DNS、证书、后端）
- **先分类再动手**：连不上先分「没监听 / 队列溢出 / 被丢 / 被拒」；变慢先分「应用没喂满 / 窗口受限 / 丢包重传 / MTU」
- 计数器一律**取差值**，且任何单一计数器都不能单独定性——伪造源地址的 SYN 实验里，只看一个计数就会得出相反结论
- 参数调整**先量化、一次只改一项、复测一个业务周期**，写清载体与回滚；`net.core.*` 与 `nf_conntrack_max` 是全局参数，只能在整机改
- 生产抓包必须限流限时落盘（`-c`/`-w`/`timeout`），抓完及时清理；偶发问题先在实验链路的隔离命名空间里用 `tc netem` 复现，再决定是否生产取证
- 改动 MTU、环缓冲、bond 模式、防火墙会短暂断流，必须排窗口、有带外入口、预先准备好回滚命令
- 云环境下先分清「主机内」还是「安全组/负载均衡/云网络」；主机侧计数器干净时不要在本机反复折腾

**生产实践**

- 可观测性按四件套落地：日志（落点 + 持久化 + 轮转）、指标（每机采集 + 保留）、告警（可用性 / 水位 / 证书 / 错误率，每条有动作）、目标值（至少一个核心服务）；先闭环再扩指标
- 应用日志与系统日志分目录或分盘存放，避免日志写满根分区造成整机故障

> **实测状态**：单机 CPU / 内存 / IO / 网络 / 耗尽类实验与 cgroup v2 的 CPU 限流、内存 OOM 均在实验机（Ubuntu 24.04.5 LTS / VMware 虚拟机 / 内核 `6.8.0-139-generic` / 4 vCPU / `MemTotal` 7894 MiB / root 可用）上重跑；`sysstat`（12.6.1）、`strace`（6.8）、`perf`（6.8.12）、`fio`（3.36）、`stress-ng`（0.17.06）、`bpftrace`（v0.20.2）等均为系统包、直接可用。**未实测**：PMU 计数器透传（本机 `perf stat -e cycles` 是 `<not supported>`）、真实物理网卡多队列与 offload（`ethtool -l` 报 `Operation not supported`）、火焰图最后画 SVG 的官方脚本（未安装；采样与折叠栈两步已实测）、GPU 与多机摘流量/回滚。**读者定位**：会基本 shell、用过 `top`/`free`/`df`，但没系统想过「为什么整机 CPU 只有 25% 服务还是慢」「`%util` 没到 100% 算不算磁盘瓶颈」。

### 10.1 原理（01–05）

- [ ] 原理 01（性能的语言与「看起来空闲」的那一层）：五个可测量（延迟 / 吞吐 / 利用率 / 饱和度 / 错误）与 USE 三问；利用率—延迟的非线性（`R = S/(1−ρ)`）；Little's law 是**推导式**而非 `iostat` 文档原文（实测六组 `w/s × w_await` 与 `aqu-sz` 对照，如 `324 × 0.00659 = 2.14`）；平均值与中位数都会掩盖尾部（同核竞争实验里 `p50` 全程 8.06～8.13 ms，`max` 从 8.36 涨到 40.87 ms）；分位数的窗口与算法口径；五个视角；「慢」的三种形态决定采样密度
- [ ] 原理 02（观测的代价与降级路径）：三类代价（时间扰动与事件次数成正比、资源占用与采样频率成正比、注入永久改变现象）；`strace` 的代价要记的是**每次拦截的绝对开销**（约 55 µs）而不是倍数（倍数随被测程序的基线浮动）；四个采样盲区（亚窗口脉冲、首行语义、不在 CPU 上的时间、被聚合掉的长尾）；`perf record -e cycles` **录下来的事件名可能是 `task-clock`** 的判据（核对 `perf report`/`perf evlist`，并区分「默认事件列表本来就含软件事件」）；`perf_event_paranoid` 的 3/4 来自发行版补丁而非上游文档；无 root 与无 PMU 时的降级阶梯；取证三条纪律
- [ ] 原理 03（争抢为什么不按比例缩放）：同核竞争的非线性（吞吐 26,473,519 → 12,461,811 → 5,564,871 次/2 s）与 CFS 唤醒抢占导致的「中位数不动而尾部先坏」；`load average` 是 `nr_running + nr_uninterruptible` 的指数平均、**不是使用率**，且 `TASK_IDLE`（`TASK_NOLOAD`）刻意不计入；自愿与非自愿切换的含义相反（实测 40,343.67 次/秒 vs 16.67 次/秒）；并行度超过核数的后果与 Amdahl 定律；cgroup 配额这条另一种缩放失败（`nr_throttled`/`throttled_usec`）
- [ ] 原理 04（资源「有」与任务「完成得了」之间的那道缝）：内存的「空间」与「压力」是两个问题（实测占用 3 GiB 后 `MemAvailable` 少 3079 MiB 而 PSI 的 `avg` 全 0、`total` 涨 9397 µs、`pgscan_direct=0`）；PSI 的 `some`/`full` 定义与「`avg*` 是百分比、`total` 是微秒」、「`cpu.pressure` 的 `full` 自 5.13 起固定为 0」；direct reclaim 与 THP 造成的尖刺；`%util` 不是饱和度（`iostat(1)` 原文只对串行设备成立）；`%iowait` 文档明写不可靠；同步落盘与缓冲写差约两个数量级
- [ ] 原理 05（时间花在「等」上时看哪里）：两类等待（任务在等 / 网络在等）与进程状态分布；`wchan`、`/proc/<pid>/stack`（需 `CAP_SYS_ADMIN`）、自愿切换差分；off-CPU 的三条手段（`perf sched`、off-CPU eBPF、`/proc` 证据链）与各自前提，以及 CPU 采样为什么看不到阻塞时间；网络延迟的四个来源与「`ping` 正常不等于应用不慢」；`ss -ti` 的 `rtt`/`minrtt`/`app_limited` 读法（`app_limited` 只在非 0 时打印）；计数器优先于抓包，以及 `nstat` 默认输出是窗口差值

### 10.2 体系（06–07）

- [ ] 体系 06（一次性能故障的处置）：四站主线一次走完；每站「要回答什么、用什么字段、看到什么转向哪一步」；认领的五个必答问题与三种形态；算力站的字段表（含 `vmstat` 的 `si` 是换入、`%sys` 不含中断、`%iowait` 不可靠）与五个分支；存储与传输站的字段表；下钻站的四级证据与三个必须验证的前提；四条横切线（观测代价、视角缩放、判据与口径、基线与容量）与一张判据卡
- [ ] 体系 07（一次止损的闭环）：三件套验收与四个不算「修好了」的说法；五种手段的影响面排序与各自回滚方式；每个动作的三件套（预期效果 / 验收指标 / 回滚方式与触发条件 / 观察窗口）；用 cgroup 配额做一次完整验收（配置一致 + 内核侧 `cpu.max` 一致 + 行为一致 + 回滚干净）；六段报告与一份填好的示例；四个复盘必答问题与「人为失误不算根因」；四条横切线（证据线、回滚线、留痕线、改进线），含 `OOMPolicy=stop` 会让现场消失

### 10.3 实操、判例与治理（08–10）

- [ ] 实操 08（观测与处置顺序）：一个问题一把工具（整机第一分钟五条 / 单核与线程 / 进程与系统调用 / 服务与 cgroup 宿主侧 / 历史与注入），分清命令、内核接口文件与内核参数；读数字前先固定三样（单位、窗口、来源）与三个「看起来像结论」的数字；采样纪律与基线卡；五个具象场景（单核饱和 / 周期性大块写抢 IO / 容器被限流 / 偶发失败类耗尽 / 事后复盘）各自的排查顺序与「一份合格的回答长什么样」
- [ ] 判例 09（高频误判）：十八条四段式判例（现象 → 误判 → 判据 → 出处），覆盖「整机 25% 所以不是 CPU」「`load` 到 8 才算高」「`%iowait` 高就是磁盘」「`%util` 到 100% 才是瓶颈」「`free` 少就加内存」「PSI 全 0 所以 PSI 没用」「内存涨就是泄漏」「`S` 状态没事」「`perf record -e cycles` 写出文件说明 PMU 可用」「重传 14 次有问题」「`TIME_WAIT` 多就调参」「`ping` 通就网络没问题」「服务端没日志所以请求没到」「`cs` 高就是 CPU 忙」「容器里 `top` 30% 就够用」「重启后好了」「改了文件就生效」
- [ ] 治理 10（性能基线与排障治理）：没有制度时的六类后果；行业做法；四件产物（五组数据的基线卡、容量台账与拐点、排障记录与六段报告、演练与工具边界登记）的字段与判据；关键字段的治理用法（`memory.peak` 定上限、`cpu.stat` 判配额、`aqu-sz` 定 IO 水位、重传率进告警）；六个治理场景与要交出的产物；与阶段 9、11 的接口

**生产实践**

- 先建基线（业务高峰与低谷各一份），没有基线就没有「变慢了」；基线必须带采集条件（同一块盘的 `w_await` 在 0.09 ms 与 6.59 ms 之间摆动，条件不同不可比）
- 排障动作按「只读先于写入、应用层先于内核层、单机先于集群、限流先于重启」排序；一个动作只改一个变量；故障中不做高风险变更
- 每个止损动作先写下「预期效果 + 验收指标 + 回滚方式（含触发条件）」；验收用「指标回到基线 + 业务验收 + 观察窗口」三件套，不用「重启后好了」
- 排障报告固定六段：时间线 / 影响面 / 证据 / 根因 / 止损动作 / 长期改进（含 owner 与期限；尤其要写「为什么之前的防线没拦住」）
- 用故障演练检验排障路径：单核超卖、内存压力、深队列 IO、网络延迟与丢包、句柄/端口耗尽、cgroup 配额；演练必须在隔离环境/命名空间里做、设定明确上限、跑完清理并复核，并记录观测指纹
- 容器与服务问题必须同时取容器内与宿主侧证据：限流看 `cpu.stat`、OOM 看 `memory.events`、IO 限速看 `io.max`；容器内 `top` 不代表容器的真实约束
- 工具方案要准备降级路径：无 PMU、无 tracefs、无 eBPF 时用 `/proc` 证据链 + 采样类工具 + 应用指标与分位数；缺依赖用解包补齐，不依赖安装

**交付物与要点自测**

- 交付物：一份性能基线卡、一份「按核 / 按线程」的定位记录、一张内存与 IO 判据卡、一次「先计数后抓包」的网络判定记录、一份带回滚与验收标准的止损记录、一篇六段排障报告、一份演练记录 + 工具可用性清单
- 负载飙高但 CPU 空闲，可能是什么原因？怎么一步步验证？
- 为什么「整机 CPU 25%」不能排除 CPU 问题？同核超卖对吞吐与延迟的实测影响是多少？
- CPU 高的五个分支怎么判、怎么下钻？`vmstat` 的 `si` 为什么容易看错？
- 内存「有压力」和「用得多」怎么区分？为什么分配 3 GiB 后 PSI 的 `avg` 仍然全 0，而 `total` 涨了 9397 µs？
- `%util`、`await`、`aqu-sz` 为什么可能互不对应？怎么用 Little's law 交叉验证，而这个式子的性质是什么？
- 为什么 CPU 采样看不到进程等锁的时间？off-CPU 有哪几条路，各自需要什么？
- 机器 IO 慢，你怎么把范围从「某块盘」缩小到「某个进程的某个文件」？
- `strace`/`perf`/eBPF 各有什么观测代价与前提？怎么证明某个 perf 事件真的被支持？
- 容器的 CPU 被限流、内存被 OOM，分别在宿主侧看哪个文件？为什么容器内 `top` 不可信？
- 「偶发失败」类问题（连接 / 句柄 / 端口打满）怎么量化，并区分它与网络抖动的差别？
- 请把一次真实的排障讲给面试官听：现象 → 分层 → 证据 → 根因 → 止损 → 长期改进。

## 阶段 11：生产运维、变更与高可用

**入口**：[[Linux/11_生产运维与高可用/00_导读与知识地图|11 生产运维与高可用]]（原理 4 篇 · 体系 2 篇 · 实操 1 篇 · 判例 1 篇 · 治理 1 篇，共 10 篇）

**这条线研究什么**：一次生产变更从「要不要做、谁批准」，到准备退路（备份、回滚、灰度、验收判据）、分批执行、验收守候，最后收口成组织资产的完整过程；以及一次中断从「备份被验证」开始，经过发现与分级、止损、救回数据、救活系统，直到把故障域补齐的完整过程。四条横切线贯穿两条线：可逆性与退路（只读／可回滚／不可逆三档，回滚耗时必须小于 RTO）、幂等与批量（先判断后动作、退出码的语言、并发买时间卖可定位性、分批依据是剩余容量）、台账与到期（资产与依赖、参数落点、容量水位、证书与补丁与固件、备份保留期）、检测与余量（MTTD、探活间隔与失败阈值、N+1/N+2、共享依赖）。要练出的判断是：面对「变更做完出事」「备份恢复不了」「机器起不来」「一台挂了业务全断」这四类处境，先说清自己在两条线的哪一站，再按顺序动手。

参数变更的回滚计时、硬链接快照与恢复、loop 设备上的 LVM 快照与扩容、误删恢复演练、`sysctl` 两套机制的读取集与覆盖顺序（`strace` 实读 + 软链指向 + 两个写入点的对抗实验，均已回滚复核）、证书到期与链复验、容量与 inode 的四口径取证、串行与并发的耗时对照、归档与校验均为实测（实验机：Ubuntu 24.04.5 LTS / VMware 虚拟机 / 内核 `6.8.0-139-generic` / systemd 255 / 4 vCPU / root 可用，另有 `realtyz` uid=1000）。双机 VIP 切换与脑裂、负载均衡摘流量与连接排空、Ansible 批量执行、restic/borg 的 `check` 与 `prune`、云盘在线扩容、补丁窗口与重启批次、写坏 `fstab` 与只读根与内核 panic、带外管理与救援介质标注为「未实测」——本实验机是单台虚拟机、只有 SSH 可用，没有第二台机器也没有控制台，补做方式写在对应篇里。

**过关里程碑**（不按天数）

- [ ] 原理 · 不可逆性与影响面（01）：只读／可回滚／不可逆三档与「可回滚」的三个条件（有退路、退路在实验机跑过、耗时小于 RTO）；影响面的四个维度（用户／服务／数据／时间）与「沿依赖往两头看」；只读计数的时刻性与口径；预发与生产的三处差异（数据规模、流量形态、依赖真实度）；分级只看影响面不看改动量
- [ ] 原理 · 可恢复性的语言（02）：RTO 与 RPO 是约束、MTTR 与 MTTD 是度量且 MTTD 常更值得先优化；备份、快照、副本、归档四者各不能防什么；备份方案的四问与三种粒度；三条一致性路径与「块级快照默认崩溃一致性」；3-2-1 加一份离线或不可变；硬链接快照的容量读法（分开相加是假数字）；恢复演练八步与「唯一验收是能恢复且计时」
- [ ] 原理 · 幂等与可重入的批量执行（03）：批量同时放大数量与静默；连接层四种坑（连接放大、无超时、交互提问、无并发上限）与环境层差异（非交互 shell 不读 dotfiles）；幂等是性质、可重入是设计；脚本四件套与 `set -u` 不拦空值；退出码的语言（124／123／137）；并发买时间卖可定位性，分批依据是剩余容量
- [ ] 原理 · 故障域与检测的赌注（04）：判据是「拔掉一台业务还剩多少」；六层故障域与共享依赖这一层；接入四法（VIP／负载均衡／DNS 多值／服务发现）各自把风险挪到了哪；脑裂与 fencing、CAP 必须先问业务；健康检查判得太松与太严；连接排空；切换时延下限即检测时延；N+1／N+2 与滚动重启批次上限
- [ ] 体系 · 一次生产变更的一生（05）：五站（立项与评审 → 准备与预演 → 执行与分批推进 → 验证与守候 → 收口与沉淀）；六要素与三个隐藏考点；13 项变更前检查清单；回滚四形态与两种假回滚；执行顺序「摘流量 → 改 → 单机验证 → 放回 → 观察」与单机验证内部顺序「状态 → 日志 → 请求」；批次决策点四选一；三层验收与四种假成功；回滚触发线「指标 + 阈值 + 持续时间」；`ExecMainStartTimestamp`、`NRestarts`、`SubState` 的读法；收口四件事与复盘六段；字段的「是什么／单位／判据／与谁同看／转向哪一步」
- [ ] 体系 · 一次中断与恢复的一生（06）：六站（备份与恢复演练 → 发现与分级 → 止损 → 救数据 → 救系统 → 补故障域）；快照的 COW 边界与合并的破坏性；恢复演练八步与频率；`MTTD + MTTR`；四个角色与唯一的决定人；变更失败的四个分支与「回滚也需要验收」；止损优先级「限流 → 摘流量 → 回滚 → 扩容 → 重启」；部分成功三条路径；四类灾难的最短路径与误删黄金几分钟；`findmnt --verify`、`fstab` 的 `by-uuid`、救援准备清单八项；高可用恢复动作与「VIP 在两台」的判据
- [ ] 实操 · 巡检取证与处置顺序（07）：一个问题一把工具的命令地图，分清命令、内核接口文件与内核参数；只读与破坏性的边界；每个字段的五件事读法；采样纪律与基线卡；五类具象现象（根分区满、证书漏登记与链不全、参数不生效、批量脚本留半成品、变更后「服务 active 但业务报错」）的排查顺序与「一份合格的回答长什么样」
- [ ] 判例 · 高频误判（08）：备份任务成功不等于有效、探活与监控正常不等于变更成功、预发通过不等于生产安全、退出码 0 不等于生效、回滚写在纸上不等于有回滚、改一行不等于标准变更、重启不等于回滚、配了 VIP 不等于高可用、快照与副本不是备份、部分成功比全失败更危险、`is-active` 不等于服务健康、没有 root 跳过不等于跑过、`systemctl show` 空输出不等于没设置、`df` 满了不等于只删日志、`df -h` 有空间不等于写得进去（inode）、参数不生效要先分清**哪套机制在读**（开机 `systemd-sysctl` 只读 `.d` 目录 / 手工 `sysctl --system` 末尾再读 `/etc/sysctl.conf`）再看文件名顺序、证书按剩余天数而不是按过期日、日志留存的三前提、归档压一下不等于归档
- [ ] 治理 · 生产运维与变更治理（09）：没有制度时的七类产物缺失；行业通行做法与来源（ITIL、Google SRE 四章、Ansible 幂等与 `serial`、restic/Borg 的 `check` 与 `prune`、RFC 8555）；六件产物（变更单、资产与依赖台账、到期日历、备份与恢复登记、复盘与改进项、Runbook 与交接）的字段与模板；关键字段的治理用法；六个具象治理场景与各自要交出的东西；与阶段 1／5／6／8／9／10 的接口

**生产实践**

- 所有变更遵循「先备份、再验证、后生效、可回滚」，并且把**回滚命令与触发条件**写下来——写在纸上、在实验机上跑过，才算有回滚方案
- 一次只改一个变量、一批只动一部分；灰度同时覆盖两个维度（先按实例验配置，再按故障域验依赖），每个批次都有明确的决策点
- 内核与系统参数按批次推进，先非核心业务；重启前确认上层集群或负载均衡能承接流量，并算清 N+1／N+2 余量
- 备份的唯一验收标准是「能恢复」：定期做恢复演练并记录耗时，对齐 RTO／RPO；**快照与副本都不算备份**
- 能自动化的手工操作尽量自动化，但脚本必须先满足四件套与幂等，再上生产；批量工具先 `--check`、再 `--limit`、最后分批
- 把「止损」和「根因」分开：事故中先恢复业务并保留现场，复盘阶段再追根因；带着「必须当场查清楚」的心态处置，往往会把故障拖长
- 把「有到期日的东西」全部列成一张表（证书、补丁、固件、支持合同、备份保留期），配上责任人和提前量足够（而不是到期当天）的告警
- 任何「只有我会做」的动作都要写成 Runbook 并让另一个人照着做过一次——否则它随时会变成下一次事故的放大器

**交付物与要点自测**

- 交付物：一份资产与依赖台账、一份六要素齐全的变更单、一份带实测回滚耗时的变更记录、一份批量执行记录（含幂等检查结果）、一份三层验收记录（含回滚触发线）、一份带 RTO 计时的恢复演练记录、一份归档包（含校验值）、一段 Runbook 片段与交接记录、一篇含 owner 与期限的复盘
- 变更单六要素是什么？最容易漏的是哪两个？为什么「改动很小」不能作为降级的理由？
- 一个动作要算「可回滚」需要同时满足哪三条？为什么「我知道怎么回滚」不算？
- 备份、快照、副本、归档分别不能防什么？为什么说「备份的唯一验收标准是能恢复」？恢复演练为什么必须从「决定恢复」开始计时？
- 3-2-1 原则是什么？为什么还要加「一份离线或不可变」？快照会满、会失效，判据是什么？
- 要在一批 100 台机器上改一个参数，你的方案是什么？（先手工 1 台 → 幂等脚本或 playbook → `--limit` 试跑 → `serial` 分批 → 每批验收 → 回滚条件）
- 灰度分批的依据是什么？批次大小与观察时间怎么算？为什么 `serial: 1` 不等于安全？
- 「拔掉一台业务还剩多少」怎么算？为什么「配了 VIP」不等于高可用？脑裂时应该保可用还是保一致？
- 变更失败时的四个分支是什么？「解释不了但服务还活着」归为哪一类？为什么「已回滚但现象仍在」要升级？
- 误删之后为什么不能重启？黄金几分钟的四个动作是什么？`lsof +L1` 有输出是不是就有救？
- `df` 满了但 `du` 很少，四类原因是什么？分别怎么验证？`df -h` 还有空间为什么写不进去？
- 参数改了不生效，怎么定位？为什么 `/etc/sysctl.conf` 会让你的文件「失效」？为什么回滚要用 `sysctl -p <单文件>`？

## 阶段 12：复习与自测

> **对应笔记**：[[Linux/12_复习与自测/00_导读与知识地图|12 复习与自测]]（全库收口章，共 10 篇 = 导读 00 + 总纲 01 + 体系 02、03 + 实战 04、05 + 附录 06、07、08 + 收口 09；构成与其它章不同，见下）
>
> 这一章**不引入新机制**，只把阶段 1–11 的十一条线装进同一个模型：**四条线**（算力卖时间、内存卖空间、持久卖提交、连接卖通道）× **一个约束环**（会话 / 服务 / cgroup / 整机四层上限，实际生效的是最紧那一层）× **一层观察面**（指标、日志、追踪、变更记录四类证据，以及"观测有代价、采样有盲区、证据会消失"三条纪律）。十个篇目分三块：**模型与接缝**（总纲、连接点矩阵、压力与排队）、**实战**（端到端处置链、面试追问链）、**附录与自检**（高频误判对照表、闭卷题库、盲区定位表、能力自检清单）。**本章不用原理/体系/实操/判例/治理的五层构成**：那一套的主语是机器上的对象，而这一章的主语是读者脑中的模型。
>
> **题源与判据全部来自阶段 1–11**，每道题都能在对应阶段找到出处；如果本阶段与对应阶段冲突，**以对应阶段为准**并把冲突记进错题清单。**实测状态**：本章不新增实测，引用的数字均转引自前十一章在本实验机（**Ubuntu 24.04.5 LTS / VMware 虚拟机 / 内核 `6.8.0-139-generic` / systemd 255 / 4 vCPU / `MemTotal` 7894 MiB / root 可用**）的记录；需要控制台或快照的演练项（写坏 `/etc/fstab`、真正的根分区 `remount,ro`、内核 panic）标注未实测并给补做方式。

### 12.1 模型与接缝（01–03）

- [ ] 总纲（01）：四条线各卖什么（时间 / 空间 / 提交语义 / 通道）与各自的排队点；约束环五层（前四层技术上限：`ulimit` → unit → cgroup → 内核全局，实际生效的是最紧那一层；第 5 层组织层决定"能不能动手"）；观察面四类证据与三条纪律；十一条线各自的瓶颈、证据与最容易踩的坑
- [ ] 连接点矩阵（02）：**24 处跨章接缝**，每个给出"两侧各看到什么 → 靠什么对齐 → 最容易答错哪一句 → 回哪一章复核"；四种对齐口径（同一对象 / 单位与时钟 / 层次与范围 / 因果与传导）；重点覆盖 Page Cache、cgroup、PID 1、inode 与 fd、句柄与端口与队列、容器与编排的宿主侧机制、时间基线、内核日志与用户态日志、版本与默认值、观测代价、不可逆性
- [ ] 压力与排队（03）：四条线的排队点与判据字段（`r`/`b`、PSI 的 `avg` 与 `total`、`await`/`aqu-sz`、`Recv-Q`/`Send-Q`）；队列容量配在哪一层与生效值取法；**容量怎么算**（从观测反推上限：源端口、`nf_conntrack_max`、全连接队列、句柄、journal 容量、cgroup 内存与 CPU 配额）；三条传导链（配额→堆积→内存放大→OOM、回收→设备排队→延迟尖刺、回写落后→容量假满）

### 12.2 实战（04–05）

- [ ] 端到端处置链（04）：演练顺序（先可回滚后不可回滚）、三条纪律（隔离 / 上限 / 清理复核）、五个观测指纹的完整读法、演练记录模板的三行必填（观测指纹 / 恢复耗时 / 未实测与未解释）；未实测项与补做方式
- [ ] 面试追问链（05）：追问四步（证据 → 边界 → 反例 → 代价）与评分五要素；三道题各自从"只给结论"到"给出边界与代价"的四层演进；四类"配置不生效"的落点与生效值取法（含 `sysctl --system` 与开机路径读的文件集合差异）

### 12.3 附录与自测（06–08）

- [ ] 高频误判对照表（06）：按四条线 + 约束环 + 观察面 + 组织层分组的「常见说法 / 事实 / 出处」；用法是遮住右列自测，把出错的行进错题清单
- [ ] 闭卷题库（07）：六十九道题按线分组（含前提组与启动链路组）、含答案要点；四档评分（A 能脱稿讲 / B 有结论无证据 / C 认得但讲不出 / D 完全不会）与组内定档；第一轮建议先做内存、持久、连接、约束环四组
- [ ] 盲区定位表（08）：按现象索引的补法（现象 → 落在哪条线 → 缺什么 → 补法 → 验收）；六类缺口（结论 / 判据 / 证据 / 边界 / 代价 / 节奏）；五件交付物与验收方式；五张随身卡（值班 / 通报 / 交接 / 面试 / 四句边界）

### 12.4 收口（09）

- [ ] 能力自检清单（09）：26 项可观察行为，分值班就绪（8 项）、面试就绪（6 项）、案例就绪（6 项）、变更就绪（6 项），每项给"需要什么动作 / 做到什么程度算过 / 什么表现是不及格"；分三次勾选（读完本章、跑完演练链、间隔一段时间后）
- [ ] 五件交付物齐备并各有一份验收记录：**体系图、错题清单、一页纸、限时答辩记录、端到端演练记录**
- [ ] 错题清单每条都有"缺的那一层"与下一次复查日期（D+1 / D+3 / D+7 / D+21）
- [ ] 原「核心要点速查」的十一组要点逐条能在高频误判对照表或闭卷题库里找到落点——含 LVM 扩容、RAID 取舍、SSH 加固、`sar` 复盘、USE 方法、trace 与 span、火焰图，不允许在重写中丢点

**生产实践**

- 任何现象先问"这属于哪条线、卡在哪个连接点"，再决定看哪个字段；不要从命令清单里挑一条试
- 所有结论带单位、版本与采集条件；本套笔记统一容量 MiB、时间秒；说不清的部分显式标「未实测」并给补做方式
- 答开放题固定一段骨架（现象与影响面 → 分层 → 证据 → 结论 → 止损 → 改进），每题至少两个成因、一句"第一反应不要做什么"
- 复习动作也遵守生产纪律：只读观测可在生产机做，故障注入只在实验机；不做未审批的"验证性变更"，不拿唯一的备份做恢复演练
- 队列容量与上限的修改，必须先取生效值、确认改的是四层里最紧的那一层，再用同一条命令复验
- 五件交付物是唯一的验收方式；"我觉得我会了"不算交付

**交付物与要点自测**

- 交付物：一张自己的体系图（机器上有什么 / 一个动作怎么穿过各层，至少两张）、一本五列错题清单（每条含"缺的那一层"与复查日期）、一张一屏一页纸、一份限时答辩记录（含两层追问与自评）、一份端到端演练记录（含观测指纹、恢复耗时、清理复核与未实测清单）
- 四条线各卖什么？为什么不能用"资源不足"一个词概括四条线的现象？
- 约束环五层分别是什么？举一个"调大了但没生效"的层间错位例子。
- 为什么"整机 CPU 不高"不能排除 CPU 问题？判据换成什么？
- 页缓存让"写成功"变成一句不完整的话，缺的那半句是什么？
- 为什么退出码 137 不能证明是 OOM？定性证据在哪两处？
- `df` 与 `du` 对不上的四类成因分别怎么验证？空间满与 inode 满的报错为什么一样？
- `ss -lnt` 的 `Recv-Q` 与 `Send-Q` 各是什么？队列溢出时服务端为什么没有日志？
- 追问链四步是什么？评分五要素里哪一项最能区分"做过"与"读过"？
- 演练记录里哪三行不能省？各自防止什么损失？
- 26 项能力自检里，哪几项必须动手才能过？为什么未实测项既不算通过也不算失败？
