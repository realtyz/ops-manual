# 高频误判

十四条按值班与复盘里的真实处境写成：**场景**（谁、什么机器、看到什么、别人怎么说）→ **常见误判及它为什么看起来成立** → **判据**（读哪个字段、什么数值或趋势、什么条件下结论会变）→ **一句话结论** → **出处**。案例按事件的先后排列：日志的落点、轮转与退役在前，指标的判定、降噪与问责在中，统计口径、历史证据与追踪在后。

## 1. 「配置文件里写着 `no`，所以转发没开」

**场景**：同事解释「`/var/log/syslog` 里为什么有 journald 的消息」时说：「`/etc/systemd/journald.conf` 里写着 `#ForwardToSyslog=no`，转发肯定是关的，大概是 rsyslog 自己在读 journal。」这台 Ubuntu 24.04.5 上，`logger -t labtest` 写的消息在 `journalctl` 与 `/var/log/syslog` 两处都出现了——journald 侧是带字段的结构化记录，rsyslog 侧是纯文本一行。

**常见误判**：把某个配置文件里的那一行当成生效值。它看起来成立，是因为「改配置文件 → 重启服务 → 生效」是通用直觉，而这里的那一行确实存在——只是被注释了，而发行版的 drop-in 在更高的优先级上覆盖了它。

**判据**：

- **是什么**：`ForwardToSyslog=` 是 journald 的转发开关（收到消息后再交给 rsyslog）；`Storage=` 是落点（磁盘还是内存）。
- **单位**：布尔值 `yes`/`no`，没有量纲。
- **判据**：读 `systemd-analyze cat-config systemd/journald.conf` 的**合并结果**——输出里以 `# ` 开头的行是**来源标记**（`# /etc/systemd/journald.conf`、`# /usr/lib/systemd/journald.conf.d/syslog.conf`），标记行下面的才是该来源的内容；同一个键出现两次、一次带 `#` 一次不带，就是被 drop-in 覆盖。本机生效值是 `ForwardToSyslog=yes`，来源是 `/usr/lib/systemd/journald.conf.d/syslog.conf`（177 字节），而 `/etc/systemd/journald.conf.d/` 在本机并不存在。
- **与谁同看**：`systemctl show systemd-journald -p ForwardToSyslog -p Storage -p SystemMaxUse` 一起看——它返回空（见下一条），正好说明「unit 属性」与「journald.conf 配置项」是两个命名空间；再与 `/var/log/syslog` 里有没有对应消息对照。
- **转向哪一步**：生效值与预期不符时，逐层 `ls` 各优先级目录找出是谁覆盖的；判断「转发是否发生」只看生效值，不看文件内容。

```bash
systemd-analyze cat-config systemd/journald.conf | grep -nE "^# /(etc|usr/lib)|ForwardToSyslog"
logger -t labtest hello && tail -1 /var/log/syslog     # 验证：两边是否都出现
```

**条件会变**：`ForwardToSyslog=` 在 systemd 上游的默认值是 `no`（这也是 `/etc/systemd/journald.conf` 里那行注释的由来），是否转发完全取决于发行版有没有放 drop-in——换发行版必须重查。

**一句话结论**：生效值只能取自合并结果（`cat-config`）或运行时观察，不能取自某一个文件里的一行。

**出处**：`man 5 journald.conf`（`ForwardToSyslog=`）、`man 1 systemd-analyze`（`cat-config`）；原文作者实测（Ubuntu 24.04.5 / 内核 6.8.0-139 / systemd 255）：`cat-config` 输出 `ForwardToSyslog=yes` 来自 `/usr/lib/systemd/journald.conf.d/syslog.conf`，而 `/etc/` 下同一键是注释掉的 `#ForwardToSyslog=no`。

## 2. 「`systemctl show` 没报错也没输出，说明日志没有容量上限」

**场景**：要给一台根分区只有 47 GiB 的机器定 journal 容量，同事执行 `systemctl show systemd-journald -p Storage -p SystemMaxUse -p SystemKeepFree -p MaxRetentionSec`，屏幕上一片空白、退出码 0，于是回复「没有任何限制，journal 会自己管」。

**常见误判**：把「命令成功但没有输出」读成「这一项没有设置」。它看起来成立，是因为 `systemctl show -p X` 对**存在的属性**一定会打印 `X=值`，空白确实像是「没配」。

**判据**：

- **是什么**：`Storage=`/`SystemMaxUse=`/`SystemKeepFree=`/`MaxRetentionSec=`/`RateLimit*` 都是 **`journald.conf` 的配置项，不是 systemd unit 属性**。
- **单位**：容量项是字节（可带 `K`/`M`/`G` 后缀），`MaxRetentionSec=` 是秒。
- **判据**：`systemctl show` 永远读不到这些键——同一次调用里 `Id`、`MainPID`、`MemoryCurrent` 有值，而上面这些键全空。正确落点分三处：生效配置用 `systemd-analyze cat-config systemd/journald.conf`；实际占用用 `journalctl --disk-usage`；运行时状态用 `journalctl --header`（本机实测能看到 `File path` 与 `State: ARCHIVED`）。**「没有上限」在本机恰恰是错的**：`SystemMaxUse=` 为空时的默认语义是「最多占所在文件系统的 10%、且不超过 4 GiB」，`SystemKeepFree=` 为空时是「至少留 15% 空闲」；本机 `/etc/systemd/journald.conf` 里这些项**全部处于注释状态**，也就是全走默认值。
- **与谁同看**：`df -hT /` 的总量（决定 10% 是多少）、`journalctl --disk-usage` 的当前占用、`journalctl --list-boots` 的最早条目（判断被容量挤掉了多少历史）。
- **转向哪一步**：算完 10% 再决定要不要显式写 `SystemMaxUse=` 与 `MaxRetentionSec=`；只报「当前占用几十 MiB」不够，容量危险的是上限与保留期，不是此刻的大小。

```bash
systemctl show systemd-journald -p Id -p MainPID -p Storage -p SystemMaxUse   # 验证：后两项为空、退出码仍为 0
systemd-analyze cat-config systemd/journald.conf | grep -E "^# /|^Storage|^SystemMax|^MaxRetention"
journalctl --disk-usage                                                        # 验证：当前真的占了多少
```

**条件会变**：`Storage=volatile`/`none` 时 `SystemMaxUse=` 的语义跟着变（内存里的 journal 用 `RuntimeMaxUse=`），别把 `System*` 的默认值套到 `Runtime*` 上。

**一句话结论**：`systemctl show` 的空输出是「这个键不属于 unit」，不是「这个键没设」。

**出处**：`man 1 systemctl`（`show` 只展示单元属性）、`man 5 journald.conf`（`SystemMaxUse=`/`SystemKeepFree=`/`MaxRetentionSec=`/`RuntimeMaxUse=` 的语义与缺省值）、`man 1 journalctl`（`--disk-usage`/`--header`）；原文作者实测（同上环境）：`systemctl show systemd-journald -p Storage -p SystemMaxUse -p ForwardToSyslog` 返回空且退出码 0，`journalctl --disk-usage` 报 20.7 MiB。

## 3. 「容器里日志重启就没了，肯定是应用没打日志」

**场景**：一个精简镜像里的服务，重启后 `journalctl -u mysvc -b -1` 里一条都找不到，同事的结论是「应用没往 stdout 打日志」，准备让开发加日志文件。落点核查显示 `StandardOutput=` 确实指向 journal，也就是说应用**是**打到标准输出的。

**常见误判**：把「重启后查不到」归因到应用侧。它看起来成立，因为日志确实不在，而应用侧是唯一「看起来可以改」的地方。

**判据**：

- **是什么**：`Storage=` 决定 journal 写磁盘还是写内存，而 `auto` 的判据是**目录存在与否**。
- **单位**：枚举值（`volatile`/`persistent`/`auto`/`none`），不是数字。
- **判据**：先读 `Storage=` 的生效值，再读落点存在不存在。`auto`（缺省）的语义是**「`/var/log/journal` 存在就持久化，不存在就写 `/run/log/journal`（内存）」**——所以一条 `ls -ld /var/log/journal` 就能定性：目录在（本机实测存在，下面还有按 machine-id 组织的子目录 `bd821ce75df94970ad5b6d63b6a8f812`）就是持久化，目录不在就是内存存储，**而且不会报错**。
- **与谁同看**：`ls -ld /var/log/journal`（落点是否存在）、`journalctl --disk-usage`（真的写了多少）、`journalctl --list-boots`（还留着几次开机）。三者都指向「有」才叫持久化。
- **转向哪一步**：`/var/log/journal` 缺失时，建目录并让 journald 重开（或直接写 `Storage=persistent`）；已经持久化但历史还是少，那是容量与保留的问题（回到第 2 条与第 7 条）。

```bash
ls -ld /var/log/journal /run/log/journal                 # 验证：落点在哪一侧
systemd-analyze cat-config systemd/journald.conf | grep -E "^# /|^Storage"
journalctl --disk-usage; journalctl --list-boots --no-pager
```

**条件会变**：`Storage=persistent` 会把日志写到磁盘——容器里根文件系统若是只读或 tmpfs，这个选择同样留不住，得改成转发出去；本机 `--list-boots` 只剩当前一次开机，也说明**持久化不等于「历史都留着」**。容器与精简镜像上的这一条是按文档推导，未在本机复现。

**一句话结论**：持久化不是默认必然；`auto` 会在目录缺失时静默退化成内存存储，交付前必须实测一次。

**出处**：`man 5 journald.conf`（`Storage=` 四种取值的落点）、`man 1 journalctl`（`--disk-usage`/`--list-boots`）；原文作者实测（同上环境）：`/var/log/journal` 与 `/run/log/journal` 都存在，`journalctl --header` 的 `File path` 指向 `/var/log/journal/...`、`State: ARCHIVED`。

## 4. 「timer 的 `LAST` 有值、`ConditionResult=no`，所以轮转被电源条件挡了」

**场景**：一台机器的日志归档几天没增长。同事看了 `systemctl list-timers logrotate.timer --no-pager` 就回复「timer 没问题」：`NEXT` 是次日 `00:00:00 UTC`、`LAST` 是本次开机前的 `06:05:24 UTC`。接着他注意到 unit 里有一条 `ConditionACPower=true`、`systemctl show` 的 `ConditionResult` 是 `no`，于是给出完整因果：「虚拟机不接交流电，条件不满足，所以轮转被跳过了。」

**常见误判**：把 timer 层的记录当成服务层的执行记录，再把 `ConditionResult=no` 当成「条件求值失败」。它看起来成立，因为那两个字段都真实存在、名字也贴切，拼起来是一个自洽的故事。

**判据**：

- **是什么**：`LAST` 是 timer 的调度 stamp，不是服务的执行记录；`ConditionTimestampMonotonic` 是这条条件**最近一次被求值**的时刻。
- **单位**：`ConditionTimestampMonotonic` 是自开机起的**微秒数**；`ExecMainStartTimestamp` 是墙上时钟时间戳。
- **判据**：分三层。**① timer 层**：`list-timers` 的 `LAST` 只说明调度器记录过 stamp。**② 服务层**：`systemctl show logrotate.service -p ExecMainStartTimestamp -p Result -p ExecMainStatus`——本机手动执行前 `ExecMainStartTimestamp` **为空**，`journalctl -u logrotate.service` 是 `-- No entries --`，即本次开机内没被拉起来过。**③ 条件层**：`ConditionResult=no` **不区分「求值失败」与「从未求值」**，判据是 **`ConditionTimestampMonotonic=0`**——`0` 表示这条条件一次都没被求值过，此时 `no` 只是默认值。
- **与谁同看**：条件本身用 `systemd-analyze condition 'ConditionACPower=true'` 验证（本机返回 `succeeded`、rc=0，对照的 `ConditionPathExists=/nonexistent-xyz` 返回 `failed`、rc=1）；`ls /sys/class/power_supply/` 下有 `ACAD`，`cat /sys/class/power_supply/ACAD/type /sys/class/power_supply/ACAD/online` 给出 `Mains` 与 `1`——**条件成立**。再与时间对照：timer 是 `OnCalendar=daily` + `AccuracySec=1h` + `Persistent=true`，`NEXT` 指向次日 `00:00`，而本次开机时刻（`uptime -s`）是 `2026-09-19 07:08:29`，**当天的日触发点在本次开机之前就过去了**。
- **转向哪一步**：`ConditionTimestampMonotonic=0` + `ExecMainStartTimestamp` 为空 → 回到「时间还没到」；手动 `systemctl start logrotate.service` 后得到 `ConditionResult=yes`、`ConditionTimestampMonotonic=5527820005`、`Result=success`、`ExecMainStatus=0`，可反向印证条件从未挡过它。再往产物层看：`/var/lib/logrotate/status` 有没有被更新、`/var/log` 下有没有新的 `.1`/`.gz`。

```bash
systemctl list-timers logrotate.timer --no-pager
systemctl show logrotate.service -p ExecMainStartTimestamp -p ConditionResult -p ConditionTimestampMonotonic
systemd-analyze condition 'ConditionACPower=true'        # 验证：条件是否成立（rc=0）
uptime -s; systemctl show logrotate.timer -p NextElapseUSecRealtime
```

**条件会变**：发行版已把 cron 这条路让给 systemd timer（本机 `/etc/cron.daily/logrotate` 第 3 行写着 `# skip in favour of systemd timer`），别的发行版上 cron 仍可能是唯一触发路径；另外 journal 只剩一个 boot 时，「更早的开机里它跑过没有」**无法从现有证据判定**，不要补故事。

**一句话结论**：执行看 `ExecMainStartTimestamp` 与 journal，求值看 `ConditionTimestampMonotonic`，条件是否成立用 `systemd-analyze condition`——`LAST` 和 `ConditionResult` 两个字段都不是判据。

**出处**：`man 5 systemd.timer`（`OnCalendar=`/`AccuracySec=`/`Persistent=`）、`man 5 systemd.unit`（`Condition*=`）、`man 1 systemd-analyze`（`condition`）、`man 1 systemctl`（`show`/`list-timers` 的字段）、`man 8 logrotate`（state 文件）；原文作者实测（同上环境，`logrotate 3.21.0`）：`ConditionTimestampMonotonic=0`、`ExecMainStartTimestamp=` 为空、`ConditionACPower` 为 `succeeded`、`ACAD` 为 `Mains`/`online=1`。

## 5. 「`create` 之后应用会自己跟着写新文件」

**场景**：自研服务的轮转规则写成 `daily` + `rotate 3` + `create 0640`，`postrotate` 里只 echo 了一行日志、没有通知应用（本机的复现实验就是这么写的）。上线三天后，值班发现 `app.log` 一直是 0 字节，而 `app.log.1` 每天都在长，于是判断「日志没丢，只是还在旧文件里」，决定不改配置。

**常见误判**：以为「旧文件被改名、新文件被创建」之后，写日志的进程会自动找到新文件。它看起来成立，因为从文件系统的角度，同名路径下确实已经有一个可写的文件。

**判据**：

- **是什么**：进程持有的是**文件描述符**（fd），fd 指向的是 **inode**，与文件名解耦；`create` 换的是 inode。
- **单位**：inode 号是无量纲整数；行数是计数。
- **判据**：`stat -c "%n inode=%i" logs/app.log logs/app.log.1` 看 inode 是否变过（本机实测 `app2.log inode=1310803`、归档 `app2.log.1 inode=1310798`），再用 `ls -l /proc/<pid>/fd` 看那个 fd 指向哪个文件。本机复现的结果是：`postrotate` 确实执行了（`postrotate-fired` 写进了日志），但随后产生的 **9 行数据全部落进 `app2.log.1`，新的 `app2.log` 是 0 行**。
- **与谁同看**：`/var/lib/logrotate/status`（有没有轮过）、`postrotate` 脚本的内容（有没有真的发信号）、归档文件大小是否还在长（本机「归档每天都在长」就是这一条的直接症状）。
- **转向哪一步**：`postrotate` 里必须真的让应用**重开文件**——发行版自己的做法可以直接抄：`/usr/lib/rsyslog/rsyslog-rotate` 的内容是 `systemctl kill -s HUP rsyslog.service`，配合 `sharedscripts`（6 个文件只发一次信号）与 `delaycompress`（给还没重开的进程留一轮）。

```bash
stat -c "%n inode=%i" logs/app.log logs/app.log.1     # 验证：inode 是否换了
ls -l /proc/$(systemctl show -p MainPID --value myapp)/fd   # 验证：fd 现在指向哪个文件
grep -vE "^[[:space:]]*(#|$)" /etc/logrotate.d/rsyslog      # 对照：发行版的合格写法
```

**条件会变**：应用不支持任何重开方式（不响应 HUP、无管理接口）时，`create` 这条路走不通，只能退到 `copytruncate` 并接受「复制与截断之间有丢日志窗口」这个代价——本机实测 `copytruncate` 的 inode 不变（`1310736 → 1310736`），写入方无感知。**另一处相邻误判**：`/var/lib/logrotate/status` 不存在不是故障，它是**执行之后才产生的产物**；本机在手动执行之前该文件不存在，`logrotate -d` 会明确打印 `state file /var/lib/logrotate/status does not exist`，手动执行之后才生成（954 字节）。它**存在但时间戳不合理**（刚轮过又被轮、时间倒退）才是真故障。

**一句话结论**：`create` 只是换了 inode；不通知持有者重开，新文件就是空的——而「还没轮过」不能靠状态文件缺失去反证。

**出处**：`man 5 logrotate.conf`（`create`/`copytruncate`/`postrotate`/`sharedscripts`/`delaycompress`）、`man 8 logrotate`（`-d`/`-v`/`-s` 与 state 文件的语义）、`man 5 proc_pid_fd`；原文作者实测（同上环境，`logrotate 3.21.0`）：`create` 规则下新文件 0 行、归档 9 行，inode `1310803` vs `1310798`；`copytruncate` 规则下 inode 不变；state 文件手动执行后生成 954 字节。

## 6. 「`rm` 掉大日志就有空间了」

**场景**：凌晨根分区告警，值班第一反应是 `rm -f /var/log/app/old.log`（一个 10 MiB 的当前日志），`df -h` 却一点没降，于是继续删下一个，删了三个都不动。本机的这个实验在临时 loop 文件系统上做，不打满根分区。

**常见误判**：以为「没有文件名 = 空间已归还」。它看起来成立，因为 `ls` 里确实已经没有这个文件了，`du` 也看不到它。

**判据**：

- **是什么**：`rm` 只删掉**目录项**；inode 与数据块要等**最后一个持有该 fd 的进程关闭它**才回收。**单位**：字节（`df -B1`）。
- **判据**：`df` 与 `du` 的**差值**。本机实测 `rm` 之后 `df -B1` 的已用从 `24576` 涨到 `10510336` 字节（多出正好 10 MiB），而同一路径下 `du -sh` 只看到 `20K`——这个差值就是「没有名字但仍然存在」的 inode 大小。
- **与谁同看**：定位持有者用 `lsof +L1` 或遍历 `/proc/*/fd` 找 `(deleted)`——本机实测 `ls -l /proc/$$/fd/4` 给出 `fd4 -> /tmp/09a-fill/mnt/held.bin (deleted)`；关闭 fd（`exec 4>&-`）后 `df` 立刻回落到 `24576`。
- **转向哪一步**：对日志而言，「让持有者重开」就是上一条的 `postrotate`（`systemctl reload` 优于 `restart`）；**不要 `kill -9` 业务进程**。

```bash
df -hT /var; du -xsh /var/log/* | sort -h | tail -3    # 验证：两者的差值
lsof +L1 2>/dev/null | head                            # 验证：有没有 (deleted) 的持有者
find /proc/*/fd -lname '* (deleted)' 2>/dev/null | head
```

**另外三处同现象但不同账的误判必须一起排除**：① `df -h` 还有空间却报 `No space left on device`，先看 `df -i` 的 `IUse%`——本机在 `mkfs.ext4 -N 512` 的 32 MiB 镜像里创建 501 个空文件后，`df -i` 是 `512 512 0 100%`，而 `df -hT` 还是 `28M 32K 26M 1%`，**28 MiB 的盘只用了 32 KiB 却再也建不了文件**；② 「已用 + 可用」小于「总量」的差额是 **ext4 保留块**（`mke2fs` 缺省给 root 留 5%），本机根分区 `Block count 12581888`、`Reserved block count 629094`、`Block size 4096` → 总量 48.0 GiB、保留块 2.4 GiB，正好 5.0%，所以普通用户写数据报 `ENOSPC` 而 root 仍可占用那 5% 继续写；③ `df` 高而 `du` 找不到也可能是**挂载覆盖**（挂载点遮住下层目录），这时用 `findmnt` 而不是 `lsof`。**条件会变**：保留块比例按文件系统而定，XFS 的语义不同，不要把它当成 ext4 之外的通用结论。

**一句话结论**：空间释放的条件是「最后一个 fd 关闭」，不是「文件名消失」；而「写不进去」要先分空间块、inode、保留块三本账。

**出处**：`man 1 df`（`-h`/`-i` 量的是不同的账）、`man 1 du`（只统计目录树里可见的名字）、`man 8 lsof`（`+L1` 列出 link count 小于 1 的打开文件）、`man 5 proc_pid_fd`、`man 8 mke2fs`（`-m`）、`man 8 dumpe2fs`（`Reserved block count`）；原文作者实测（同上环境，64 MiB 临时 loop ext4）：`rm` 前后已用 `24576 → 10510336` 字节、`du -sh` 为 `20K`、关闭 fd 后回落 `24576`；inode 满的镜像 `df -i` 为 `512 512 0 100%`；根分区保留块 `629094 / 12581888` × 4096 B = 2.4 GiB ≈ 5.0%。

## 7. 「`journalctl --vacuum` 只是清理，删了无所谓」

**场景**：journal 占了几十 MiB，同事为了「给盘腾点地方」执行 `journalctl --vacuum-size=15M`，看到 `freed 4.6M` 就继续干活。当天下午要复盘上午的一次故障，发现 `journalctl --since` 查不到那段记录。

**常见误判**：把 `--vacuum-*` 当成可逆的压缩或归档。它看起来成立，因为命令名与输出都像「清理垃圾」，而且命令本身确实成功了。

**判据**：

- **是什么**：`--vacuum-*` 是**删除** journal 归档文件，不是压缩；它只作用于 `ARCHIVED` 状态的文件，当前正在写的 active 文件不参与。**单位**：字节（`--disk-usage` 的 MiB 量级）。
- **判据**：`journalctl --list-boots` 的 `FIRST ENTRY` 在 vacuum 前后是否被推后。本机实测 `--vacuum-size=15M` 之后 `journalctl --disk-usage` 从 `20.7M` 降到 `16.0M`，输出里点名删掉了一个 4.6M 的 `system@…journal`，而 `FIRST ENTRY` 从 `07:08:34` 被推到 **`07:55:24`——那 47 分钟的日志永久消失**。
- **与谁同看**：`journalctl --disk-usage` 前后各一次、`journalctl --list-boots` 前后各一次；再看 `--vacuum-time` 是否报 `freed 0B`——本机紧接着执行 `--vacuum-time=30min` 就是 `freed 0B`，正因为上一步已经把 30 分钟以前的数据删光了，这个 0 本身就是「上一步删干净了」的证据。
- **转向哪一步**：优先用按容量的 `--vacuum-size` 并在执行前记录当前最早条目；要长期解决容量，回到第 2 条显式配 `SystemMaxUse=` 与 `MaxRetentionSec=`。

```bash
journalctl --disk-usage; journalctl --list-boots --no-pager | head -3
journalctl --vacuum-size=15M                            # 验证：不可逆，执行前记录 FIRST ENTRY
journalctl --disk-usage; journalctl --list-boots --no-pager | head -3
```

**条件会变**：`--vacuum-*` 只管 journal，**不影响 `/var/log/*.log`**（那本账由 logrotate 管），所以「日志集中了就不占本机空间」也不成立——发送端与接收端都会落盘；非 root 或未在 `systemd-journal` 组里时这条命令会被拒绝。

**一句话结论**：vacuum 是销毁历史而不是压缩历史；执行前先记录并确认「这段历史不再需要」。

**出处**：`man 1 journalctl`（`--vacuum-size`/`--vacuum-time`/`--disk-usage`/`--list-boots`）、`man 5 journald.conf`（`SystemMaxUse=`/`MaxRetentionSec=`）；原文作者实测（同上环境，journal 持久化在 `/var/log/journal`）：`20.7M → 16.0M`，`FIRST ENTRY` 由 `07:08:34` 退到 `07:55:24`（约 47 分钟）。

## 8. 「`ALERTS` 是空的，说明告警规则没在工作」

**场景**：刚把一组规则上线，值班用 `curl .../api/v1/query?query=ALERTS` 一看是空的，立刻说「规则没生效」，准备去查 Prometheus 的配置加载与通知渠道。同一时刻 `up` 的值是 `1`，CPU 使用率算出来约 3.85%，磁盘剩余约 76.6%。

**常见误判**：把「没有告警」当成「规则没有运行」。它看起来成立，因为 `ALERTS` 是检验告警是否工作的第一站，而它确实是空的。

**判据**：

- **是什么**：`ALERTS` 是告警规则求值结果生成的**特殊时序**（`alertstate` 为 `pending`/`firing`）；`health`/`state`/`lastEvaluation` 是规则自身的求值状态。
- **单位**：`ALERTS` 的值是 0 或 1（触发时为 1）；`lastEvaluation` 是墙上时钟时间戳。
- **判据**：**`ALERTS` 为空是正确结果**——它表示规则在评但条件不成立。本机实测记录规则 `instance:node_cpu_utilisation:rate5m` 的 `health: ok`、告警规则 `NodeCpuHigh` 为 `state: inactive`、`duration: 600`；另加一条恒真规则 `expr: vector(1) > 0` 后，第二轮就出现 `ALERTS{alertname="AlwaysFiringDemo",alertstate="firing",severity="info"} = 1`。**只有 `lastEvaluation` 停住**才说明真的没在评。
- **与谁同看**：`up`（目标抓不抓得到，本机为 `1`）、`/api/v1/targets` 的 `health`/`lastError`（采集链路）。三个视图分别对应「采集正常」「规则在评」「条件成立」。
- **转向哪一步**：`ALERTS` 空且 `state: inactive` → 规则正常、阈值没到；`ALERTS` 空且 `lastEvaluation` 停住或 `health` 非 `ok` → 去看规则加载与语法；`ALERTS` 有 `firing` 但人没收到 → 才转向 Alertmanager 的路由与通知渠道。

```bash
curl -s --get --data-urlencode "query=ALERTS" localhost:9090/api/v1/query
curl -s localhost:9090/api/v1/rules | grep -E '"name"|"health"|"state"|"lastEvaluation"'
promtool check rules rules.yml                          # 验证：只验语法，不验算得对不对
```

**条件会变**：带 `for` 的规则在 `pending` 阶段也不进 `firing`，本机 `NodeCpuHigh` 带 `for: 10m`，验证期间一直停在 `inactive`；另外 `promtool check rules` 只验语法（本机实测合法文件报 `SUCCESS: 4 rules found`，三份坏文件分别报 `unclosed left parenthesis`、`field 'expr' must be set in rule`、`unknown unit " minutes"`），**语法通过不等于算得对**，表达式本身的正确性要靠 `promtool test rules` 的合成序列断言。

**一句话结论**：`ALERTS` 空证明的是「条件不成立」，要用 `/api/v1/rules` 的 `health`/`state`/`lastEvaluation` 才能证明「规则在评」。

**出处**：Prometheus 官方文档的「Alerting rules」（`ALERTS`/`ALERTS_FOR_STATE` 时序）与「HTTP API」（`/api/v1/rules` 的 `state`/`health`/`lastEvaluation`）；原文作者实测（同上环境，解包运行 Prometheus 抓 node_exporter）：阈值未到 `ALERTS` 为空、`NodeCpuHigh` 为 `state: inactive`，恒真规则出现 `alertstate="firing"` 且值为 `1`。

## 9. 「告警太吵了，先把阈值调高、`for` 拉长」

**场景**：一次机架断电导致多台机器同时不可达，一分钟内推了几十条通知。值班被吵醒后把 `NodeCpuHigh` 的阈值从 `0.8` 调到 `0.95`、`for` 从 `10m` 拉到 `30m`，当晚安静了。两周后一台机器的磁盘水位告警被淹没，没人看到。

**常见误判**：把「降噪」等同于「降低触发频率」。它看起来成立，因为通知确实变少了，而且这是配置里最快能改的一个数。

**判据**：

- **是什么**：分组（`group_by`）决定「什么算同一个故障」，抑制（`inhibit_rules`）表达「确定的因果关系」，静默（silence）是**有期限**的临时压制，调阈值是**降低灵敏度**。
- **单位**：`group_by` 是 label 名单；`equal` 是 label 名单；阈值与 `for` 分别是比率和时长。
- **判据**：顺序固定为 **① 分组 → ② 抑制 → ③ 静默 → ④ 调阈值 / 延长 `for`**。判据是「这批告警是不是同一个故障产生的」：本机把两条同 `alertname+service` 的 warning 发进去，webhook 只收到**一个分组**（`groupKey={}/{severity="warning"}:{alertname="NodeCpuHigh", service="web"}`，内含 `linux-lab` 与 `linux-lab2` 两条），`service=db` 那条单独一组。抑制必须用 `equal` 限定对象：本机实测 `inhibit_rules` 带 `equal: ["alertname","service"]` 时，`service=web` 的两条 warning 变成 `state=suppressed`、`inhibitedBy=['0c65b10c93ac87dc']`，而 `service=db` 的 warning 仍是 `state=active`；**不写 `equal` 就退化成「任何 critical 压掉任何 warning」，真故障会被压掉**。
- **与谁同看**：`/api/v2/alerts` 的 `state`/`silencedBy`/`inhibitedBy`（本机 silence 后 `silencedBy=['a23478de-5b79-41f4-aa83-5ee6c70dc0c5']`）、`amtool silence query`（有没有遗留静默）、以及 SLO 的 burn rate（改阈值的真正依据）。
- **转向哪一步**：调阈值前必须回答「漏报的风险谁承担」，并把它当成一次降低灵敏度的变更来评审。

```bash
amtool config routes test --config.file=am.yml severity=warning service=web   # 验证：会送到哪个 receiver
amtool silence query --alertmanager.url=http://127.0.0.1:9093                 # 验证：还挂着哪些静默
curl -s localhost:9093/api/v2/alerts | grep -o '"state":"[a-z]*"'
```

**同一类错误的另一个面**：`up == 1` 是「`/metrics` 抓得到」，不是「服务对用户可用」——用户视角要用 blackbox 的 `probe_success`（本机实测探测在监听的目标得到 `probe_success=1`、`probe_http_status_code=200`、`probe_duration_seconds=0.001531452`，探测无人监听的 `127.0.0.1:20699` 得到 `0`），而且探测结论只是「探测点到目标这条路径」的结论；证书到期同样要按域名分组，同一台机器上 `https://www.example.com` 的 `probe_ssl_earliest_cert_expiry=1.793139441e+09`（剩余 38.6 天）而 `https://mirrors.aliyun.com` 是 `1.803656795e+09`（剩余 160.3 天），一个全局阈值测不出两种现实。

**一句话结论**：降噪是配置层的事前手段；调阈值是最后一步，且必须复盘后做——它和「用 `up` 代替用户视角」是同一类错误的两个面。

**出处**：Alertmanager 官方文档的「Configuration」（`inhibit_rules` 的 `source_matchers`/`target_matchers`/`equal`：`equal` 是必须取值相同的 label 集合）与「Routing tree」「Silences」；blackbox_exporter 官方文档的「Metrics」（`probe_success`/`probe_ssl_earliest_cert_expiry`）；`man 1 amtool`；原文作者实测（同上环境，Alertmanager `0.26.0+ds`）：同组两条 warning 合并为一个分组通知、`service="db"` 的 warning 保持 `active`、silence 后 `silencedBy=['a23478de-5b79-41f4-aa83-5ee6c70dc0c5']`、blackbox 的 `probe_success` 分别取 1 与 0。

## 10. 「用平均响应时间当 SLI，反正是达标的」

**场景**：月底复盘，核心服务的「平均响应时间」是 33.5 ms，低于目标，同事据此把本月判为「稳定性达标」，并批准下周的大版本发布。同月的 p99 记录是 2 s，本月刚过 10 天可用性已经从 99.9% 掉到 99.93%。

**常见误判**：用一个中心趋势的量代表用户体验。它看起来成立，因为平均值确实由真实请求算出来，而且它「达标」了。

**判据**：

- **是什么**：SLI 是**实际测量值**，SLO 是对它的目标，错误预算是 `1 - SLO` 允许的额度；平均值不是 SLI，因为它不携带长尾信息。
- **单位**：毫秒（延迟）、百分比（可用性）、秒或分钟（错误预算）。
- **判据**：四个数一起看——平均值（本机实测 33.5 ms）、最大值（2000 ms）、分位数、以及**错误预算的剩余量与消耗速率**。本机同一份 1000 个样本的数据（950×20ms + 45×100ms + 5×2000ms）里，平均只有 33.5 ms，而占 5% 的长尾样本贡献了 43% 的总耗时——**「平均达标」与「体验达标」在这份数据上就是两件事**。
- **与谁同看**：p95/p99/最大值（第 11 条讲它们的口径）、「快烧」（如 1 小时消耗 2% 预算）与「慢烧」（如 6 小时消耗 5% 预算）两档告警、以及窗口长度（5 分钟的 p95 与 1 小时的 p95 结论可能相反）。
- **转向哪一步**：口径写不出来的（哪条表达式、哪个窗口、哪些请求算）就说明 SLO 还没被定义；先补口径，再谈发布。

```bash
python3 -c "w=30*24*3600; print('99.9%% ->', w*0.001, '秒')"    # 验证：换算表是算术推演
curl -s --get --data-urlencode 'query=sum(rate(http_requests_total{code=~"5.."}[5m]))/sum(rate(http_requests_total[5m]))' localhost:9090/api/v1/query
```

**两个必须同时纠正的口径错误**：① SLO 换算表（99% → 30 天 432.00 分钟、99.9% → 43.20 分钟、99.99% → 4.32 分钟）是 `窗口 × (1 - SLO)` 的**算术推演**，不是任何机器的实测停机时间——真实可用性要用 SLI 时序算；② 「现在仍然达标」是**静态视角**，预算消耗有速率，本机决策场景里 10 天掉到 99.93% 意味着照这个速度本月会超支，发布决策要看速率与剩余额度。**条件会变**：SLO 的组织落地（谁定目标、谁批发布冻结）是流程问题，本机无法实测。

**一句话结论**：平均值不是 SLI；达标与否要同时看分位数、口径定义与错误预算的消耗速率。

**出处**：Google SRE Book 的「Service Level Objectives」「Embracing Risk」、SRE Workbook 的「Alerting on SLOs」（多窗口多消耗速率的 burn-rate 告警）；原文作者实测（同上环境，Python 3.12.3）：换算表 99.9% → 43.20 分钟/30 天（算术推演），同一份样本 `mean=33.5ms`、`max=2000.0ms`。

## 11. 「同一个 p95，怎么会算出一堆不同的数」

**场景**：跨团队对齐延迟目标时，两边的面板都写着「p95 延迟」。A 团队报 20.0 ms、B 团队报 96.0 ms，双方都坚持自己没错，会议停在「到底谁的数据是假的」。

**常见误判**：认为 p95 是一个没有歧义的量，差异只能来自数据造假。它看起来成立，因为「95 分位」在日常语境里有明确含义。

**判据**：

- **是什么**：分位数是**算法 + 窗口 + 聚合层级**三者的函数；它是一个估计量，不是一个恒定的物理量。
- **单位**：毫秒（延迟分位数）。
- **判据**：把同一份原始数据按四类常见定义各算一次。本机实测 1000 个样本（950×20ms + 45×100ms + 5×2000ms，`mean=33.5`、`max=2000.0`）在 `Python 3.12.3` 下得到 **20.0 / 24.0 / 96.0 / 100.0 ms**：最近排名法 `ceil(n×p)` → 20.0；`statistics.quantiles(method="inclusive")`（线性插值）→ 24.0；`method="exclusive"` → 96.0；0 基下标 `int(n×p)` → 100.0——**差 5 倍**。
- **与谁同看**：窗口（5 分钟 / 1 小时 / 30 天）、`method` 或 bucket 边界、以及聚合的 label。**聚合层级同样致命**：全局 p99 不能由各实例 p99 平均得到——各实例请求量差异大时，全局分位数会被大流量实例主导，正确做法是把各实例的**直方图 bucket 相加**再算（Prometheus 的 `histogram_quantile()` 就是这个思路，它自身也是用 bucket 近似）。
- **转向哪一步**：把「算法 + 窗口 + 聚合层级」写进指标口径说明并随面板一起版本化；跨来源比较前先对齐这三项，对齐不了就说明两个数不可比。

```bash
python3 -c "
import statistics, math
v = sorted([20.0]*950 + [100.0]*45 + [2000.0]*5)
print(v[math.ceil(0.95*len(v))-1], v[int(0.95*len(v))], statistics.quantiles(v, n=100, method='inclusive')[94])
"
```

**条件会变**：分位数这一段是纯算法结论，与机器无关；但用它去解释某台机器的延迟时，必须回到那台机器自己的采样窗口，并且知道 Prometheus 的 `histogram_quantile()` 只是 bucket 内的线性近似。

**一句话结论**：报分位数必须同时报算法、窗口与聚合层级，否则两个 p95 不同不代表任何一方错了。

**出处**：Python 标准库 `statistics.quantiles` 的 `method` 定义（`inclusive`/`exclusive`）、Prometheus 官方文档的「Histograms and summaries」（`histogram_quantile()` 与 `le` bucket 的近似）；原文作者实测（同上环境，Python 3.12.3）：四种口径给出 `20.0 / 24.0 / 96.0 / 100.0 ms`。

## 12. 「加个 `path` label 只是多一个维度，采样频率才是成本」

**场景**：为了让错误率能按接口看，有人给 `http_requests_total` 加了 `path` label（约 400 个不同取值），同时把 `scrape_interval` 从 60s 改成 5s。一周后 Prometheus 的磁盘从 20% 涨到 75%，讨论时同事认为「主要怪频率，label 只是多一列」。

**常见误判**：把「维度数量」和「时序数量」当成线性关系，也把两类旋钮分开评估。它看起来成立，因为在 SQL 或日志里多加一列确实便宜，而频率的账（倍数）更容易算出来。

**判据**：

- **是什么**：时序的唯一标识是「指标名 + label 组合」，所以**时序数 ≈ 指标数 × 各 label 取值数之积**；成本是 `时序数 × 采样频率 × 保留期` 的**乘积**。
- **单位**：时序数是条数（`prometheus_tsdb_head_series`），频率是秒，保留期是天。
- **判据**：先读时序数量本身。本机可提供的锚点是单机 `node_exporter` 一次抓取就有 **1574 行**非注释指标（`node_*` 1520 行，其余是 Go 运行时自监控），而这是一台空闲的 4 vCPU 机器。再算乘积：`path`（400 个取值）是 400 倍，`scrape_interval` 从 60s 到 5s 是 12 倍，两个改动叠加约 **4800 倍**的样本增长。**关键的第二半句**：基数一旦写进历史就很难事后清理——即使回滚 label，已写入的时序仍占着存储与索引，且回滚会让同一个指标前后出现两种口径。
- **与谁同看**：`prometheus_tsdb_head_series`、单次抓取耗时（本机 `scrape_duration_seconds ≈ 0.095` 秒）、以及 `up`/抓取失败率（频率提高也会给目标加压）。
- **转向哪一步**：先回滚**影响最大且最容易回滚**的一项（频率），再评估 label 的必要性——确实要按接口看错误率时，用有限的**接口分组**替代完整路径，或把完整路径放进日志与追踪；`user_id`、`request_id`、时间戳这类高基数信息一律不进 label。

```bash
curl -s --get --data-urlencode 'query=prometheus_tsdb_head_series' localhost:9090/api/v1/query
curl -s --get --data-urlencode 'query=count(count by (path) (http_requests_total))' localhost:9090/api/v1/query
```

**条件会变**：不同 exporter 的指标数差异很大，1574 行是本机 node_exporter 的现场值，不是通用常数；「每条时序占多少字节」在本机未实测，4800 倍与存储量属算术推演，容量规划必须按自己环境校准。

**一句话结论**：基数是乘法项而不是加法项，且历史时序难以事后清理；先改设计，后改频率。

**出处**：Prometheus 官方文档的「Data model」「Storage」「Querying basics」（cardinality 与查询成本）、OpenTelemetry 的「Sampling」；原文作者实测（同上环境）：node_exporter 单次抓取 1574 行非注释指标、`scrape_duration_seconds ≈ 0.095`。

## 13. 「这台机器肯定没在采历史指标」

**场景**：业务反馈「昨晚 3 点系统变慢」，同事登录后说「这台机器没装 sysstat，没有历史数据」，于是准备只看现在的 `top` 和 `vmstat` 来推断昨晚的情况。

**常见误判**：把「没有历史」当成前提而不是待验证的假设。它看起来成立，因为很多精简镜像确实不带 sysstat，而 `sar` 的输出又很容易让人以为「没数据」。

**判据**：

- **是什么**：`sadc` 采样、`sar` 读取、`sadf` 导出；数据落在 `SA_DIR`（本机 `/var/log/sysstat/saDD`）。
- **单位**：`saDD` 是文件（字节数表示积累量），采样间隔是秒/分钟，`HISTORY` 是天。
- **判据**：复盘的第一步不是分析，是**确认有数据**，三条判据缺一不可：① `ls -l /var/log/sysstat/` 有没有当天的 `saDD` 且大小是否在长（本机实测 `sa19`，23096 字节，mtime `08:00`）；② `systemctl is-enabled sysstat-collect.timer sysstat-summary.timer`（本机两行都是 `enabled`）；③ `systemctl list-timers sysstat-collect.timer` 的 `LAST` 是不是最近的整十分（本机 `08:00:12 UTC`，timer 的 `OnCalendar=*:00/10`）。**本机就是「正在采」的反例**，所以「没装」这个结论必须先被证伪。
- **与谁同看**：`timedatectl` 的时区（决定 `sadf -d` 与 `sar` 差几小时）、`/etc/sysstat/sysstat` 的 `HISTORY=`（本机实测默认 **7 天**，比复盘窗口短就必须显式改）、`sar -u -s/-e` 窗口内的单点值与 `Average:`（本机窗口平均 `%user=0.80`，而单点最高 `1.51`）。
- **转向哪一步**：真没有当天数据时，别用此刻的 `top` 解释昨晚；改从日志、上游/下游指标、变更记录里找同一时间窗的证据。

```bash
ls -l /var/log/sysstat/                                  # 验证：有没有当天的 saDD
systemctl is-enabled sysstat-collect.timer; systemctl list-timers sysstat-collect.timer --no-pager
LC_ALL=C sar -u -s 07:30:00 -e 08:00:00                  # 验证：窗口参数按本地时区解释
LC_ALL=C sadf -d /var/log/sysstat/sa19 -- -u | head -2    # 验证：导出的时间戳是 UTC
```

**三处容易误读的口径**：① `sadf -d` 导出的是 **UTC**，而 `sar -s/-e` 的时间窗按**本地时区**解释——本机 `TZ=Etc/UTC` 所以差值恰好为 0，**这会让人误以为「永远一致」**，换到 `Asia/Shanghai` 就差 8 小时；② `saDD` 的 `DD` 是**月份里的日**，不是序号（本机当天 19 号 → `sa19`，查 `sa32` 只会得到 `Cannot open /var/log/sysstat/sa32: No such file or directory`，rc=2）；③ `sar -n DEV` **有列名**（`IFACE rxpck/s txpck/s …`），看不到是因为示例常用 `tail -2` 把表头截掉了——**别把命令截断的产物当成工具行为**。另外 `vmstat` 的**第一行是自开机以来的平均**，从第二行起才是按秒的瞬时值。**条件会变**：RHEL 系的配置路径是 `/etc/sysconfig/sysstat`（`HISTORY`/`ENABLED`），**未在本机实测**。

**一句话结论**：历史采集本身也要被验证——`ls -l /var/log/sysstat/` 一条命令的成本，决定事故之后有没有历史可看。

**出处**：`man 1 sar`、`man 1 sadc`、`man 1 sadf`、`man 5 sysstat`（`HISTORY`/`SA_DIR`/`ZIP`）、`man 1 vmstat`（第一行是自开机以来的平均）；原文作者实测（同上环境，`sysstat 12.6.1-2`）：`sa19` 为 23096 字节、两个 timer 均 `enabled`、`sadf -d` 的时间戳带 `UTC`、`sar -n DEV` 有表头、`HISTORY=7`。

## 14. 「`traceparent` 传 `trace_id` 和 `span_id` 两段就够了」

**场景**：自研 SDK 为了「轻量」，跨服务只透传 `trace_id` 与 `span_id` 两个字段，拼出的头是 `00-8b45146f5a334f04-80b3c5c21ba12b0c-01` 这种缺段形式。接入一家合规的追踪后端后，全部 span 变成各自独立的根，链路拼不起来。

**常见误判**：认为上下文透传的格式由自己定，只要「两边都认识」就行。它看起来成立，因为自研的两端确实能对上，本地测试也通过。

**判据**：

- **是什么**：`traceparent` 是 W3C Trace Context 规定的上下文头，**四段定长**：`version`、`trace_id`、`parent_id`、`flags`。
- **单位**：`version` 2 位十六进制、`trace_id` 32 位十六进制（16 字节）、`parent_id` 16 位十六进制（8 字节）、`flags` 2 位十六进制。
- **判据**：把候选头喂给一个按规范校验的解析器。本机实测 7 类反例全部被拒：**只有 3 段**（`必须是 4 段`）、`trace_id` 只有 16 位（`必须是 32 位小写十六进制，得到 16 位`）、`parent_id` 只有 8 位（`得到 8 位`）、`trace_id` 全零、`parent_id` 全零（`规范禁止`）、保留位非 0（`保留位必须为 0，得到 '03'`）、`version` 非 `00`（`得到 'ff'`）。合法头的形状是 `00-<32 位十六进制 trace_id>-<16 位十六进制 parent_id>-<2 位 flags>`，本机实测生成值 `00-b62974f7d235e7af7f15e50ba76b4121-30931907edc3dcf8-01`；`flags` 最低位的 `01` 表示已采样。
- **与谁同看**：同一 trace 下的父子 span（本机实测入口 span `30931907edc3dcf8` 与下游 span `cab3552d09c64724` 共享 `trace_id=b62974f7d235e7af7f15e50ba76b4121`，后者 `parent_span_id` 正好指回入口）、以及 `timedatectl` 的同步状态（跨机 span 的先后依赖各机墙上时钟；本机实测 `System clock synchronized: no` 而 `NTP service: active`）。
- **转向哪一步**：把这 7 类反例做成单测；**采样标志必须随头透传**——每个服务各自决定采样会造成**链路断片**（上游采了、下游没采，中间耗时永远算不出来；本机实测把 last byte 换成 `00` 后解析出 `sampled=False`）。先做「上下文透传 + 把 `trace_id` 写进日志」，它不依赖追踪后端就能让日志按一次请求串起来，再接 SDK 与后端。

```bash
timedatectl; timedatectl timesync-status | head -3        # 验证：跨机追踪前先修对时
python3 -c "import re,sys; p=sys.argv[1].split('-'); print(len(p))" '00-<trace_id>-<parent_id>-01'
```

**条件会变**：本机未部署追踪后端（OpenTelemetry Collector、Jaeger/Tempo），这一段结论只覆盖数据模型与透传这一层；对时状态没修好之前不要下「谁先谁后」的结论。

**一句话结论**：`traceparent` 的四段与全零、保留位约束是规范硬要求，自研 SDK 少传一段或改写保留位就是链路断片。

**出处**：W3C Trace Context 规范（`traceparent` 的字段长度、全零禁止、保留位为 0、版本 `00`）；OpenTelemetry 的「Context propagation」「Sampling」文档；原文作者实测（同上环境，Python 3.12.3）：合法头 `00-3fa03269c9ca9544f21003009cbf188c-82e38b7a157275d3-01`，7 类非法头全部被拒。

## 第一反应不要做什么

不要把某个配置文件里的一行当成生效值；不要把命令「退出码 0 但没有输出」读成「这一项没设置」；不要把「重启后查不到」先归到应用没打日志；不要只看计时器的上次触发时间就认定轮转正常；不要看到条件结果是 `no` 就编出「被条件跳过」的因果；不要以为换新文件之后应用会自动跟着写；不要在状态文件不存在时判定轮转损坏；不要用 `rm` 解决空间问题，也不要 `kill -9` 业务进程；不要在没分清空间、inode、保留块这三本账之前下「写不进去」的结论；不要把按容量回收 journal 当成可逆清理；不要因为告警状态时序为空就认为规则没工作；不要在告警风暴时先调阈值或拉长 `for`；不要用平均值向业务解释体验；不要拿两个来源不同、口径不同的分位数直接比较；不要为了「以后可能按它聚合」给指标加高基数字段；不要凭印象说某台机器「没有历史」；不要把透传头截断成三段或改写保留位。

## 要点自测

**问：一份配置改了却没生效，你的第一层判据是什么？**
答：读合并后的生效值，而不是读你改的那个文件。发行版可以用更高优先级的追加片段覆盖上游默认值，所以同一个键会出现两次、一次被注释；「被注释的那一行」正是最容易骗过人的地方。

**问：`systemctl show <unit> -p <键>` 返回空、退出码 0，说明什么？**
答：说明这个键不属于 systemd 的单元属性，而不是「它没被设置」。收集端与采集端的配置项（容量、保留、转发开关）都在自己的配置文件里，判据是「同一次调用里，哪些键有值、哪些键为空」——有值的那些恰好证明命令本身是正常的。

**问：轮转之后新日志文件是空的、归档却在长，根因是什么？**
答：换新文件的切法改变了文件名指向的 inode，而写入方持有的是指向旧 inode 的文件描述符，它察觉不到变化。判据是归档文件里的内容是否包含轮转之后的条目；修法是让写入方重开文件，做不到就退回复制再截断并接受丢日志窗口。

**问：删掉一个大日志文件，空间没有释放，接下来做什么？**
答：先用只读手段定性——文件系统层面的已用量与目录树可见量的差值、以及文件描述符列表里的已删除标记。判据是「差值等于那个文件的大小」。处置是让持有者关闭 fd（重载优于重启），继续删没有任何用，也不要强杀业务进程。

**问：告警状态时序为空，是故障吗？怎么继续查？**
答：不是。它说明规则在被评估、只是条件不成立。要继续查两件事：规则自身的状态与最近评估时间（区分「没算出来」和「算出来但没触发」），以及阈值与数据源是否本来就该触发。只有这一层都正常，才轮到告警管理组件的路由、分组、抑制与静默。

**问：告警风暴时，为什么不先调阈值？**
答：调阈值降低的是灵敏度，会连带放过将来真正的持续故障；而分组、抑制、静默都不改变判定逻辑，只改变通知形态，所以先做它们。顺序是分组 → 抑制 → 静默 → 最后才是阈值与持续时间，且最后一步必须复盘后再做。

**问：同一个 p95 出现两个不同的数，谁错了？**
答：很可能都没错。分位数不是数据里固有的量，而是由算法定义的：最近排名法、两种线性插值、0 基下标对同一份数据会给出四个不同的值；窗口与聚合层级不同也会改变结果。所以「p99 是多少」这个问题的完整形式必须带上算法、窗口、聚合层级。

**第一反应不要做什么**：见上一节汇总——核心是「先分清是哪一本账、哪一层的问题，再动手；生效值只取自合并结果或运行时观察」。
