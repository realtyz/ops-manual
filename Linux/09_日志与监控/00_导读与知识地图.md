# 日志、监控与可观测性

## 知识地图

### 一条日志的一生

时间主线跟着**一条日志**走：从应用决定「按什么格式写、往哪个通道写」，到它落在 journald 还是 rsyslog，到被谁按什么条件切开，到离开本机、在网线上变成什么样的报文，最后到被删掉、被回收——以及删掉之后空间为什么不释放。

```mermaid
flowchart LR
  A["① 诞生<br/>格式 · 落点选择"] --> B["② 落点<br/>journald / rsyslog"]
  B --> C["③ 轮转<br/>切文件 · 通知重开"]
  C --> D["④ 集中<br/>报文 · 传输 · 接收端"]
  D --> E["⑤ 退役<br/>保留策略 · 磁盘写满"]
```

| # | 站点 | 这一站在解决什么 | 到这里要能说清 |
| --- | --- | --- | --- |
| 1 | 诞生 | 应用按什么格式、往哪个方向写（stdout/stderr、自有文件、syslog 套接字） | 落点决定了后面所有可能性；同一条日志为什么两边都有 |
| 2 | 落点 | journald 与 rsyslog 的分工：谁有字段、谁负责落盘、谁负责转发 | 「日志查不到」是没写进来、没持久化、被限流，还是被裁掉 |
| 3 | 轮转 | 谁在什么时候切文件，切完之后**谁还在写** | inode 换了而应用没重开，新文件就是空的 |
| 4 | 集中 | 报文长什么样、传输怎么选、中心机怎么接住 | 集中只是把容量风险搬到中心机；UDP 丢了没有任何反馈 |
| 5 | 退役 | 容量账怎么算、写满时先分哪四类 | `df` 高而 `du` 找不到，指向的是「已删除但仍被持有」 |

### 一次告警的一生

第二条线跟着**一次告警**走：从暴露一个指标，到规则判定，到通知被合并与压制，到有人拿着依据决定「现在处理还是排期」。

```mermaid
flowchart LR
  A["① 计量<br/>exporter · 指标语义"] --> B["② 判定<br/>表达式 · 规则 · ALERTS"]
  B --> C["③ 路由与降噪<br/>分组 · 抑制 · 静默 · 探测"]
  C --> D["④ 问责<br/>SLI/SLO · 错误预算"]
```

| # | 站点 | 这一站在解决什么 | 到这里要能说清 |
| --- | --- | --- | --- |
| 1 | 计量 | 指标从哪来、类型是什么、语义是什么 | counter 与 gauge 用错，后面所有表达式都是错的 |
| 2 | 判定 | 什么条件算「出事」，表达式怎么验 | 「规则在评」与「条件成立」是两件事 |
| 3 | 路由与降噪 | 一次故障怎么只发一条通知、怎么临时压掉、用户视角是否可用 | 分组的粒度由 `group_by` 决定；抑制必须限定对象 |
| 4 | 问责 | 哪些必须立刻处理、谁负责、怎么复盘 | 错误预算把优先级从「嗓门」变成「数字」 |

四条证据链要能对齐，前提是**时间基线成立**：日志、指标、追踪、变更记录的时间戳必须落在同一条时间轴上，而「NTP 服务在跑」不等于「时钟已同步」。

### 四条横切线

两条主线是时间线，但有几件事横穿多个站点。新人常「每一站都看过，却串不起来」，就是没抓住这四条线。

| 横切线 | 贯穿内容 | 收口于 |
| --- | --- | --- |
| 取用顺序 | 指标定范围 → 日志定细节 → 追踪定段落 → 变更定诱因；四条链各自回答什么问题 | 「服务慢但资源空闲」这类问题的定位树 |
| 统计口径 | 平均掩盖长尾、分位数四种算法、全局分位数要靠合并直方图、瞬时采样漏掉短脉冲 | 一份写清「窗口 + 算法 + 聚合层级」的口径说明 |
| 成本与容量 | 日志保留天数、指标 cardinality、追踪采样率；采集频率是线性成本；/var/log 要分盘 | 三个数字 + 负责人 + 分盘与保留策略 |
| 时间基线 | 时区、对时、墙上时钟与单调时钟、各类时间戳格式 | 把多来源证据对齐到同一条时间轴 |

在这四条之外还有一件不是机制的事：**采集本身要可观测**。`up`、抓取耗时、目标数量、日志采集器的队列与丢弃计数、`sar` 有没有当天数据——缺了这些，故障时你会先怀疑数据本身。

## 故障现场定位表

排障的第一问不是「怎么修」，而是「**这份数据是谁生成的、我该看哪条链路、证据在哪**」。用这张表把现象定位到站点，再进对应篇目。

| 你看到的现象 | 属于哪一站 | 现场在哪 | 第一反应不要做 |
| --- | --- | --- | --- |
| 日志查不到、查不全 | 日志落点 | `systemctl show -p StandardOutput -p StandardError`、`journalctl -u`、`systemd-analyze cat-config systemd/journald.conf` | 不要先怀疑应用没打日志 |
| 日志重启后消失 | 日志落点 | `ls -ld /var/log/journal`、`Storage=` 的生效值 | 不要以为持久化是默认必然 |
| 日志里出现 `Suppressed N messages` | 日志落点 | `RateLimitIntervalSec=`/`RateLimitBurst=` 的生效值 | 不要先关掉限流 |
| 轮转后新日志是空的、旧归档一直在长 | 日志轮转 | `stat -c %i`、`ls -l /proc/<pid>/fd`、`postrotate` 的内容 | 不要以为「切了文件就完事」 |
| 轮转该发生却没发生 | 日志轮转 | `logrotate -d`、`ExecMainStartTimestamp`、`/var/lib/logrotate/status` | 不要用 `-f` 反复强制执行 |
| 磁盘被写满 / 根分区满了 | 日志退役 | `df -hT`、`df -i`、`du -xsh /var/log/*`、`lsof +L1` | 不要 `rm -rf /var/log/*` |
| 删了大文件，空间没释放 | 日志退役 | `/proc/<pid>/fd` 里的 `(deleted)`、`lsof +L1` | 不要继续删，也不要 `kill -9` 业务进程 |
| 建不了文件但 `df -h` 显示还有空间 | 日志退役 | `df -i` | 不要把 inode 用满当成空间用满 |
| 集中到中心机之后日志断了 / 中心机磁盘满 | 日志集中 | 发送端转发配置、接收端落盘与容量、传输方式 | 不要以为集中了就不占空间 |
| 指标缺失、断点或抓取失败 | 指标计量 | `up`、`/api/v1/targets` 的 `health`/`lastError`、目标侧 `curl /metrics` | 不要先改查询与规则 |
| 告警不响 | 规则判定 | `ALERTS`、`/api/v1/rules` 的 `state`/`lastEvaluation` | 不要先查通知渠道 |
| 告警风暴 / 半夜被叫醒 | 路由与降噪 | `group_by`、`inhibit_rules`、`amtool silence query` | 不要直接调高阈值或延长 `for` |
| 证书到期 / 服务从用户视角不可用 | 可用性探测 | `probe_success`、`probe_ssl_earliest_cert_expiry`、`probe_http_status_code` | 不要等用户报障 |
| 服务慢但 CPU/内存/IO 都空闲 | 统计口径与追踪 | 延迟分位数、`/proc/pressure/*`、一次请求的 span 树 | 不要只看平均延迟就下结论 |
| 「昨晚 3 点系统变慢」要复盘 | 历史指标 | `ls -l /var/log/sysstat/`、`sar -u -s 03:00:00 -e 04:00:00` | 不要只看现在的 `top` |
| 各来源的证据时间对不上 | 时间基线 | `timedatectl`、`timedatectl timesync-status`、报文里的 `timeQuality` | 不要在时钟未同步时下「谁先谁后」的结论 |

三个容易被忽略的边界：

- **告警响不响和通知收没收到是两件事。** `ALERTS` 里 `firing` 只说明规则算出来了；还要经过路由、分组、抑制、静默，最后才轮到通知渠道。逐段验证比整体怀疑快得多。
- **「指标正常」不等于「用户正常」。** 指标是聚合视角，用户感受的是单次请求；资源空闲但用户喊慢时，答案通常在分位数、依赖或追踪里，而不是在平均值里。
- **`up=1` 不等于服务可用。** 它只说明 `/metrics` 抓得到；用户视角的可用性要靠黑盒探测，而探测结论又是「这条路径」的结论。
