# 日志、监控与可观测性

## 知识地图

### 一条日志的一生

时间主线跟着**一条日志**走：应用先决定按什么格式写、往哪个通道写，因此后来能收集到它的组件与能带上的字段并不相同；日志随后落在 journald 或 rsyslog，再被轮转工具按时间或大小切开；接着它离开本机，在网线上变成一份有固定字段的报文；最后它被保留策略删掉、被内核回收，而在某些情况下删掉之后空间并不释放。

```mermaid
flowchart LR
  A["① 诞生<br/>格式 · 落点选择"] --> B["② 落点<br/>journald / rsyslog"]
  B --> C["③ 轮转<br/>切文件 · 通知重开"]
  C --> D["④ 集中<br/>报文 · 传输 · 接收端"]
  D --> E["⑤ 退役<br/>保留策略 · 磁盘写满"]
```

| # | 阶段 | 这个阶段在解决什么 | 走到这个阶段要能说清什么 |
| --- | --- | --- | --- |
| 1 | 诞生 | 应用在这个阶段决定按什么格式写、往哪个方向写，可选的方向有 stdout/stderr、自有文件与 syslog 套接字三种 | 因为落点决定了后面所有可能性，所以要能说清同一条日志为什么在 journald 与 rsyslog 两边都有 |
| 2 | 落点 | journald 与 rsyslog 在这个阶段分工，其中 journald 提供结构化字段，rsyslog 负责落到文件并负责远程转发 | 要能说清「日志查不到」究竟是没写进来、没持久化、被限流丢弃，还是被容量策略裁掉 |
| 3 | 轮转 | 轮转工具按时间或大小决定在什么时候切开文件，因此这个阶段还要弄清切完之后**谁还在写** | 因为 inode 已经换了而应用没有重开文件，所以新文件就是空的 |
| 4 | 集中 | 这个阶段要解决三件事：报文长什么样、传输方式怎么选、中心机怎么接住这些报文 | 由于集中只是把容量风险搬到中心机，同时 UDP 丢包在发送端没有任何反馈，所以要能说清两端各自要配哪些容量与传输策略 |
| 5 | 退役 | 这个阶段要算清日志占用的字节数与 inode 数，并在写满时先把现象分成真占空间的文件、已删除但仍被打开的 inode、inode 用满与保留块或挂载覆盖四类 | 若 `df` 的已用字节（`df -B1`）很高而 `du` 的可见文件总量找不到对应的大文件，则指向的是已删除但仍被打开的 inode |

### 一次告警的一生

第二条线跟着**一次告警**走：从暴露一个指标，到规则判定，到通知被合并与压制，到有人拿着依据决定「现在处理还是排期」。

```mermaid
flowchart LR
  A["① 计量<br/>exporter · 指标语义"] --> B["② 判定<br/>表达式 · 规则 · ALERTS"]
  B --> C["③ 路由与降噪<br/>分组 · 抑制 · 静默 · 探测"]
  C --> D["④ 问责<br/>SLI/SLO · 错误预算"]
```

| # | 阶段 | 这个阶段在解决什么 | 走到这个阶段要能说清什么 |
| --- | --- | --- | --- |
| 1 | 计量 | 这个阶段要回答指标从哪里来、属于 counter 还是 gauge，以及每个指标的实际语义是什么 | 因为 counter 与 gauge 一旦用错，后面所有表达式都会算错，所以要能判断一个指标会不会自己减小 |
| 2 | 判定 | 这个阶段要定下什么条件算「出事」，并说明表达式怎么验证 | 由于「规则在评估」与「条件成立」是两件事，所以要能分别读出前者与后者 |
| 3 | 路由与降噪 | 这个阶段要解决一次故障怎么只发一条通知、怎么有期限地临时压掉通知，以及用户视角的服务是否可用 | 因为分组的粒度由 `group_by` 决定，同时抑制必须限定对象，所以要能说清这两处配置各自的作用范围 |
| 4 | 问责 | 这个阶段要按错误预算的消耗速率决定哪些问题必须立刻处理、由谁负责，以及事后怎么复盘 | 因为错误预算把优先级从主观判断变成 `1-SLO` 对应的允许额度，所以要能算出剩余额度还能支撑多久 |

四条证据链要能对齐，前提是**时间基线成立**：日志、指标、追踪、变更记录的时间戳必须落在同一条时间轴上，而「NTP 服务在跑」不等于「时钟已同步」。

### 四个跨阶段的核对对象

两条主线都是时间线，但有几类量各自贯穿多个阶段，因此按它们切分比从头走一遍时间线更快。新手常出现「每个阶段都看过，却串不起来」的情况，原因就是没有抓住下面这四个跨阶段的核对对象。

| 核对对象 | 它贯穿哪几个阶段 | 每一处读什么字段 |
| --- | --- | --- |
| 取用顺序 | 它贯穿全部阶段，因为无论排查走到哪一步，都要按「先用指标确定范围，再用日志确定细节，再用追踪确定慢在哪一段，最后用变更记录确定诱因」这个顺序取用证据 | 在指标计量的阶段读 `up` 与各指标的原始值，在规则判定的阶段读 `ALERTS` 的 `alertstate`，在日志的各个阶段读 journald 的字段与日志正文，在可用性探测的阶段读 `probe_success`，在历史指标的阶段读 `sar` 的输出，在问责的阶段读变更记录与错误预算的剩余额度；判据是遇到「服务慢但资源空闲」这类问题时，能按这条顺序把范围缩小到某一层 |
| 统计口径 | 它贯穿指标计量、规则判定与问责三个阶段，因为指标的类型在计量时就要定下来，表达式的窗口与算法在判定时写定，而 SLO 与错误预算所用的聚合层级在问责时写定 | 在指标计量的阶段读一个指标是 counter 还是 gauge；在规则判定的阶段读表达式所用的窗口长度与它选用的那种分位数算法，并核对全局分位数是否由合并直方图得到；在问责的阶段读 `1-SLO` 对应的允许额度所用的窗口；判据是同一个 p95 在算法或聚合层级不同时结果不同，因此最后要核对一份写清窗口、算法与聚合层级的口径说明 |
| 成本与容量 | 它贯穿日志退役、指标计量与追踪采样三个阶段，因为保留天数决定日志占用、cardinality 决定时序数量、采样率决定追踪数据量，而采集频率对这三者都是线性成本 | 在日志退役的阶段读保留天数与 `/var/log` 所在的文件系统；在指标计量的阶段读由 label 组合数量决定的 cardinality；在追踪的阶段读采样率；判据是这三个数字都要配上负责人，同时 `/var/log` 要与业务数据分盘，因为一项成本在没有上限与负责人时会持续增长 |
| 时间基线 | 它贯穿全部阶段，因为日志、指标、追踪与变更记录这四条证据链都要靠时间戳对齐，而对齐的前提是它们出自同一条时间轴 | 在日志的诞生与集中阶段读报文里的时间戳与 `timeQuality` 的 `isSynced`、`syncAccuracy`；在指标计量与问责的阶段读指标的采样时刻与错误预算窗口的起止时间；同时要分清会被对时调整的墙上时钟与只随开机累加的单调时钟；判据是 `timedatectl timesync-status` 显示时钟已同步，若它显示未同步，则不要下「谁先谁后」的结论 |

除这四个核对对象之外，还有一条与机制无关的纪律：**采集本身要可观测**。若缺少 `up`、抓取耗时、目标数量、日志采集器的队列与丢弃计数以及 `sar` 的当天数据这些字段，则故障时你会先怀疑数据本身。

## 术语速查

| --- | --- | --- |
| 四条证据链 | 四条证据链指日志回答「发生了什么」、指标回答「多严重、何时开始」、追踪回答「慢在哪一段」、变更事件回答「是不是我改的」 | 原理：可观测性的四条链路 |

| cardinality（基数） | cardinality（基数）是 label 组合的数量，它决定了时序数量以及存储与查询的成本 | 原理：可观测性的四条链路 · 体系：一次告警的一生 |
| 墙上时钟 / 单调时钟 | 墙上时钟是会被对时调整的日历时间，单调时钟是只随开机累加、不受对时影响的计时器 | 原理：证据的时间与格式基线 |

## 故障现场定位表

排障的第一问不是「怎么修」，而是「**这份数据是谁生成的、我该看哪条链路、证据在哪**」。因此下表先把现象归到某个阶段，再进入对应的篇目。

| 你看到的现象 | 属于哪个阶段 | 现场在哪 | 第一反应不要做 |
| --- | --- | --- | --- |
| 日志查不到、查不全 | 这属于日志落点阶段的问题 | 先读 `systemctl show -p StandardOutput -p StandardError` 确认落点，再用 `journalctl -u` 查该单元，并用 `systemd-analyze cat-config systemd/journald.conf` 读合并后的生效配置 | 不要先怀疑应用没打日志 |
| 日志重启后消失 | 这属于日志落点阶段的问题 | 先读 `ls -ld /var/log/journal` 确认持久化目录是否存在，再读 `Storage=` 的生效值 | 不要以为持久化是默认必然 |
| 日志里出现 `Suppressed N messages` | 这属于日志落点阶段被限流丢弃的问题 | 先读 `RateLimitIntervalSec=` 与 `RateLimitBurst=` 的生效值 | 不要先关掉限流 |
| 轮转后新日志是空的、旧归档一直在长 | 这属于日志轮转阶段的问题 | 先读 `stat -c %i` 比较新旧 inode，再读 `ls -l /proc/<pid>/fd` 确认写入方持有的 fd，最后读 `postrotate` 的内容 | 不要以为「切了文件就完事」 |
| 轮转该发生却没发生 | 这属于日志轮转阶段的问题 | 先读 `logrotate -d` 打印的计划，再读 `ExecMainStartTimestamp` 确认服务是否真的被执行过，最后读 `/var/lib/logrotate/status` | 不要用 `-f` 反复强制执行 |
| 磁盘被写满 / 根分区满了 | 这属于日志退役阶段的问题 | 先读 `df -hT` 与 `df -i` 区分空间用量与 inode 计数，再用 `du -xsh /var/log/*` 找可见的大文件，最后用 `lsof +L1` 找已删除但仍被打开的 inode | 不要 `rm -rf /var/log/*` |
| 删了大文件，空间没释放 | 这属于日志退役阶段的问题 | 先读 `/proc/<pid>/fd` 里带 `(deleted)` 的条目，再用 `lsof +L1` 找持有者 | 不要继续删，也不要 `kill -9` 业务进程 |
| 建不了文件但 `df -h` 显示还有空间 | 这属于日志退役阶段 inode 用满的问题 | 先读 `df -i` 的 inode 计数 | 不要把 inode 用满当成空间用满 |
| 集中到中心机之后日志断了 / 中心机磁盘满 | 这属于日志集中阶段的问题 | 先读发送端的转发配置，再读接收端的落盘与容量配置，最后确认传输方式 | 不要以为集中了就不占空间 |
| 指标缺失、断点或抓取失败 | 这属于指标计量阶段的问题 | 先读 `up`，再读 `/api/v1/targets` 的 `health` 与 `lastError`，最后在目标侧执行 `curl /metrics` | 不要先改查询与规则 |
| 告警不响 | 这属于规则判定阶段的问题 | 先读 `ALERTS`，再读 `/api/v1/rules` 的 `state` 与 `lastEvaluation` | 不要先查通知渠道 |
| 告警风暴 / 半夜被叫醒 | 这属于路由与降噪阶段的问题 | 先读 `group_by`，再读 `inhibit_rules`，最后用 `amtool silence query` 查遗留的静默 | 不要直接调高阈值或延长 `for` |
| 证书到期 / 服务从用户视角不可用 | 这属于可用性探测阶段的问题 | 先读 `probe_success`，再读 `probe_ssl_earliest_cert_expiry` 与 `probe_http_status_code` | 不要等用户报障 |
| 服务慢但 CPU/内存/IO 都空闲 | 这属于统计口径与追踪两个阶段的问题 | 先读延迟分位数，再读 `/proc/pressure/*`，最后读一次请求的 span 树 | 不要只看平均延迟就下结论 |
| 「昨晚 3 点系统变慢」要复盘 | 这属于历史指标阶段的问题 | 先读 `ls -l /var/log/sysstat/` 确认当天数据存在，再用 `sar -u -s 03:00:00 -e 04:00:00` 查那个时段 | 不要只看现在的 `top` |
| 各来源的证据时间对不上 | 这属于时间基线阶段的问题 | 先读 `timedatectl`，再读 `timedatectl timesync-status`，最后读报文里的 `timeQuality` | 不要在时钟未同步时下「谁先谁后」的结论 |

三个容易被忽略的边界：

- **告警响不响和通知收没收到是两件事。** `ALERTS` 里出现 `firing` 只说明规则算出来了，因为这条时序还要经过路由、分组、抑制与静默，最后才轮到通知渠道，所以逐段验证比整体怀疑快得多。
- **「指标正常」不等于「用户正常」。** 因为指标是聚合视角，而用户感受的是单次请求，所以资源空闲但用户喊慢时，答案通常在分位数、依赖或追踪里，而不是在平均值里。
- **`up=1` 不等于服务可用。** 它只说明 `/metrics` 抓得到，而用户视角的可用性要靠黑盒探测，同时探测结论又只是「从探测点到目标这条路径」的结论。
