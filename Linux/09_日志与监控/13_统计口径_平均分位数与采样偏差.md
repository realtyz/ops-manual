# 统计口径：平均、分位数与采样偏差

> [!cite] 参考资料
> Prometheus 官方文档的「Histograms and summaries」「Querying basics」；`man 5 proc_pid_pressure`（PSI 的 `some`/`full` 与累计值）；Python `statistics.quantiles` 的三种 `method` 定义；`man 1 vmstat`、`man 8 ss`。
>
> **实测环境：Ubuntu 24.04.5 LTS（VMware 虚拟机）/ 内核 `6.8.0-139-generic` / systemd 255（`255.4-1ubuntu8.17`）/ cgroup2fs（v2）/ 4 vCPU / `MemTotal` 7894 MiB / root 可用。**
>
> 本篇输出已在**本实验机**上本次重跑并粘贴，替换了原 WSL2 输出：分位数对比用 **Python 3.12.3** 在 1000 个样本上计算（可完全复现）；PSI、`vmstat`、`ss` 为**同一台机器同一次采集**的只读读取。**分位数那一段的结论与环境无关（纯算法），PSI/`vmstat`/`ss` 的数字则必须按本机的现场值读。**

> **这篇讲什么**：为什么「看指标」这件事本身也有口径问题。同一个 p95，换一种定义就能差 5 倍；同一次采集，瞬时采样会漏掉短脉冲。这一篇不教工具，教**怎么不被数字骗**。
>

>
> **读完能回答**：① 平均值为什么会掩盖问题？② 为什么同一个 p95 会算出不同的数？③ 全局 p99 能不能由各实例 p99 平均得到？④ 瞬时采样会漏掉哪些故障？⑤ 怎么用 PSI 的累计值补上采样盲区？
>

## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **平均值会掩盖长尾。**
>   - 证据：实测 1000 个样本（950×20ms + 45×100ms + 5×2000ms）平均只有 **33.5ms**，但最慢的请求是 **2000ms**；把 950 个 20ms 的贡献（19000.0 ms）与 45×100ms + 5×2000ms 的贡献（14500.0 ms）并排看，长尾 5% 的样本贡献了 43% 的总耗时。
> - **同一个 p95 可以有四种结果，差 5 倍。**
>   - 证据：实测这份数据的 p95 按不同定义分别得到 **20.0 / 24.0 / 96.0 / 100.0 ms**。
> - **全局 p99 ≠ 各实例 p99 的平均。**
>   - 怎么验证：把各实例的直方图 bucket 相加再算（Prometheus 的 `histogram_quantile()` 就是这个思路）；对实例 p99 求平均会抹平大流量实例的权重。
> - **瞬时采样会漏掉两类现象：短脉冲与周期性抖动。**
>   - 怎么验证：短脉冲看 PSI 累计 `total` 与分钟级最大值；周期性抖动看最大值与分位数，而不是 1 小时平均。
> - **PSI 的累计 `total` 是补盲区的关键。**
>   - 证据：实测 `/proc/pressure/cpu:some avg10=0.25 avg60=0.39 avg300=1.26 total=16983404`——`avg10` 会被稀释，而 `total` **只增不减**，能说明「这段时间确实卡过」。

## 1. 平均值的两个陷阱

| 陷阱 | 说明 | 例子（本机实测数据） |
| --- | --- | --- |
| 掩盖长尾 | 少数极慢请求被大量正常请求稀释 | 平均 33.5ms，但最慢 2000ms |
| 掩盖分布形状 | 同样的平均值可以是完全不同的分布 | 「大多数 20ms，少数 2s」与「全部 33ms」平均值相同 |

```text
分布: 950x20ms + 45x100ms + 5x2000ms
  n=1000  mean=33.5ms  max=2000.0ms
  950x20ms 贡献 19000.0 ms，45x100ms+5x2000ms 共贡献 14500.0 ms
```

**排障含义**：如果只看平均延迟，你会得出「服务挺快的」，而真实体验是「每 200 个请求里有 1 个要等 2 秒」。

## 2. 分位数：同一份数据，四种口径

```bash
python3 -VV                             # 验证：本机是 Python 3.12.3
python3 -c "
import statistics, math
vals = sorted([20.0]*950 + [100.0]*45 + [2000.0]*5)
print('n=%d mean=%.1f max=%.1f' % (len(vals), statistics.mean(vals), max(vals)))
print('nearest-rank ceil(n*p): rank=%d -> %.1f' % (math.ceil(0.95*len(vals)), vals[math.ceil(0.95*len(vals))-1]))
print('0-based int(n*p)=%d -> vals[%d]=%.1f' % (int(0.95*len(vals)), int(0.95*len(vals)), vals[int(0.95*len(vals))]))
for m in ['inclusive','exclusive']:
    q = statistics.quantiles(vals, n=100, method=m)
    print('  %-9s p50=%.1f p95=%.1f p99=%.1f' % (m, q[49], q[94], q[98]))
"
```

本机实测：

```text
Python 3.12.3 (main, Aug 31 2026, 10:18:26) [GCC 13.3.0]
n=1000 mean=33.5 max=2000.0
nearest-rank ceil(n*p): rank=950 -> 20.0
0-based int(n*p)=950 -> vals[950]=100.0
  inclusive p50=20.0 p95=24.0 p99=100.0
  exclusive p50=20.0 p95=96.0 p99=100.0
```

同样问「p95 是多少」，四种常见定义给出 **20.0 / 24.0 / 96.0 / 100.0**：

| 口径 | p95 |
| --- | --- |
| 最近排名法（`ceil(n×p)` 名） | 20.0 ms |
| `statistics.quantiles(method="inclusive")`（线性插值） | 24.0 ms |
| `statistics.quantiles(method="exclusive")` | 96.0 ms |
| 0 基下标 `int(n×p)` | 100.0 ms |

这就是为什么：

1. **跨系统对比 p99 前必须统一口径**（算法、窗口、聚合层级）。
2. **Prometheus 用 histogram bucket 近似**，导出到别处再算 percentile 又是另一种近似。
3. **文档里只写「p99 < 500ms」是不够的**，要写清楚用什么算出来的。

> [!important] 全局分位数不能靠「平均」合并
> 10 个实例，每个 p99 = 100ms，**不等于**全局 p99 = 100ms；如果每个实例的请求量差异很大，全局 p99 会被大流量的实例主导。正确做法是把各实例的**直方图 bucket 相加**再算分位数（Prometheus 的 `histogram_quantile()` 就是这个思路）。

## 3. 瞬时采样会漏掉什么

| 现象 | 为什么会被漏掉 | 怎么补 |
| --- | --- | --- |
| 短脉冲（10 秒 CPU 打满） | 每分钟采样一次，采样点落在谷底 | 提高采样频率、用 PSI 的累计 `total`、看分钟级最大值 |
| 周期性抖动（每 5 分钟一次的批处理） | 长时间空闲把平均值稀释 | 看最大值与分位数、看时间序列拐点，而不是看 1 小时平均 |
| 采集本身超时 | 抓取间隔内目标无响应，样本缺失 | 用 `up`、`scrape_duration_seconds` 监控采集链路 |
| 计数器在重启点归零 | 这一条**不属于「会被漏掉」**：`rate()`/`increase()` **内置 counter reset 感知**，归零会被当作回绕自动补偿，**不会产生负值** | 直接正常使用 `rate()`/`increase()` 即可；真正要留意的是：重置会让窗口外推在重置点附近短暂失真，以及只取最后两个样本的 `irate()` 在重置恰落在这两点之间时会出现尖峰/低估 |

本机实测的 PSI 压力信号（**注意 `total` 是累计微秒数**）：

```text
$ grep -H . /proc/pressure/cpu /proc/pressure/io /proc/pressure/memory
/proc/pressure/cpu:some avg10=0.25 avg60=0.39 avg300=1.26 total=16983404
/proc/pressure/cpu:full avg10=0.00 avg60=0.00 avg300=0.00 total=0
/proc/pressure/io:some avg10=0.00 avg60=0.04 avg300=0.39 total=4908689
/proc/pressure/io:full avg10=0.00 avg60=0.04 avg300=0.33 total=4106769
/proc/pressure/memory:some avg10=0.00 avg60=0.00 avg300=0.00 total=285
/proc/pressure/memory:full avg10=0.00 avg60=0.00 avg300=0.00 total=200
```

同一时刻的 `vmstat` 与 `ss`（用来交叉印证「此刻确实不忙」）：

```text
$ LC_ALL=C vmstat 1 3
procs -----------memory---------- ---swap-- -----io---- -system-- -------cpu-------
 r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st gu
 1  0      0 2545636 188596 4930012    0    0   743  1576  731    2  1  1 98  0  0  0
 0  0      0 2556228 188612 4930144    0    0     0    88  975  831  1  2 97  0  0  0
 0  0      0 2444416 188776 4980236    0    0     0     0 4108 6433  3  4 93  0  0  0
$ ss -s
Total: 186
TCP:   82 (estab 5, closed 64, orphaned 0, timewait 64)
```

读法：

- `avg10/60/300` 是滑动平均——**会稀释短脉冲**。
- `some` = 至少一个任务被卡；`full` = 所有任务都被卡。本机 `io:full total=4106769` 与 `io:some total=4908689` 同量级，说明**IO 停顿是「全面停顿」而不只是个别任务被卡**；而 `cpu:full total=0` 说明 CPU 从没出现过全员等待。
- `total` 是自开机以来的累计值——**只要它涨了，就说明那段时间确实卡过**，即使 `avg10` 现在看起来很小。
- 注意 `vmstat 1 3` 的**第一行是自开机以来的平均值**，从第二行起才是按秒的瞬时值；`ss -s` 里的 `timewait 64` 是此刻的连接状态快照，不是历史。

> [!warning] counter 与 gauge 的用法不能混（这里再说一次）
> **counter 只增不减**（进程重启会归零），必须用 `rate()`/`increase()`；**gauge 可升可降**，直接看值。**对 counter 求平均、对 gauge 求 `rate()` 都是错的。** 这条与子笔记 09 的结论一致，但在「统计口径」这一篇里它决定了你的数字有没有意义——PSI 的 `total` 是 counter，`avg10` 是 gauge，两者不能混着比较。

## 4. 一份指标口径说明应该写什么

给每个被用作 SLO 或告警判据的指标写清四件事：

| 项目 | 例子 |
| --- | --- |
| 数据来源 | `node_cpu_seconds_total`（node_exporter，15s 抓取） |
| 计算方式 | `100 - avg(rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100` |
| 窗口与聚合层级 | 5 分钟窗口，按 instance 聚合后再取平均 |
| 分位数口径（若用到） | Prometheus `histogram_quantile(0.95, sum by (le) (rate(http_request_duration_seconds_bucket[5m])))`，bucket 上界见规则文件 |

**这份说明的价值**：半年后有人问「为什么这个数字和 Grafana 上另一张图对不上」，答案就在这四行里。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 「平均延迟达标就行」 | 长尾被掩盖：实测平均 33.5ms、最大 2000ms；占 5% 的长尾样本贡献了 43% 的总耗时 |
| 「p95 就是 p95，算法无所谓」 | 同一份数据四种口径得到 20.0/24.0/96.0/100.0ms，差 5 倍 |
| 把各实例 p99 求平均当全局 p99 | 需要合并直方图；否则大流量实例的权重被抹平 |
| 用 1 小时平均判断「有没有卡过」 | 周期性抖动会被空闲时间稀释；要看最大值、分位数与 PSI 累计值 |
| 把 PSI 的 `avg10` 与 `total` 混着比 | `avg10` 是滑动平均（gauge），`total` 是累计值（counter）；判断「这段时间卡过没有」要看 `total` |
| 窗口取得比抓取间隔还短 | `rate()` 拿不到足够样本，结果抖动或为空 |
| 对 counter 求平均、对 gauge 求 rate | 得到的数字没有物理含义 |
| 面板上改了口径不写文档 | 半年后没人能解释「为什么这两个 p99 不一样」 |

## 决策练习

**场景**：业务反馈「接口偶尔很慢」。你看面板发现过去 1 小时的平均响应时间是 45ms、p95 是 60ms，看起来完全正常。你决定进一步排查，但只有一次机会选择**先看什么**。

**A. 看 p99 与最大值，并把时间窗口切到 5 分钟粒度，寻找尖峰**
**B. 因为指标正常，直接结论「不是服务端问题」**
**C. 把采样间隔从 1 分钟改成 15 秒，然后等明天再看**

**为什么选 A**：四个数字（平均、p95、p99、最大值）里，p95 只是「大多数人的体验」；「偶尔很慢」对应的正是长尾。把窗口切细则是为了看**尖峰是否存在**——1 小时的平均与 p95 会把 5 分钟内的异常彻底稀释（本机实测：950×20ms + 45×100ms + 5×2000ms 这组数据平均只有 33.5ms，而 2000ms 的样本只占 0.5%、对平均值贡献约 10ms；占 5% 的长尾样本却贡献了 43% 的总耗时）。

**为什么不选 B**：p95 正常不代表 p99 和最大值正常；「偶发慢」正是长尾问题的典型描述。

**为什么不选 C**：提高采样频率是对的方向，但「等明天再看」把响应时间拖到了 24 小时之后；先用手上已有的数据切窗口，往往就能找到尖峰。

## 要点自测

> [!question]- 为什么不能只看平均延迟？
> - **掩盖长尾**：实测 950×20ms + 45×100ms + 5×2000ms → 平均 33.5ms，但最大 2000ms；5% 的长尾样本贡献了 43% 的总耗时。
> - **掩盖分布**：相同的平均值可以来自完全不同的分布。
> - **正确做法**：看 p95/p99 + 最大值，并写清窗口与算法口径。
> - **第一反应不要是什么**：不要用平均延迟向用户解释体验。

> [!question]- 为什么同一个 p95 会算出不同的数？
> - **定义不同**：最近排名法、`inclusive`/`exclusive` 插值、0 基下标，实测对同一份数据给出 `20.0 / 24.0 / 96.0 / 100.0`（本机 Python 3.12.3）。
> - **聚合层级不同**：单实例 p95 与全局 p95 不是一回事；全局需要合并直方图。
> - **窗口不同**：5 分钟 p95 与 1 小时 p95 结论可能相反。
> - **落点**：把「算法 + 窗口 + 聚合层级」写进指标口径说明，跨系统对比前先对齐。
> - **第一反应不要是什么**：不要拿两个来源不同、口径不同的 p99 直接比较。

> [!question]- 瞬时采样会漏掉哪些故障？怎么补？
> - **短脉冲**：10 秒 CPU 打满、每分钟采样一次抓不到 → 提高频率、看 PSI 累计 `total`（本机 `cpu:some total=16983404`）、看分钟级最大值。
> - **周期性抖动**：批处理让 `await` 冲高但被平均值稀释 → 看最大值、分位数与时间拐点。
> - **采集失败**：样本直接缺失 → 用 `up`/`scrape_duration_seconds` 监控采集链路本身。
> - **第一反应不要是什么**：不要用「1 小时平均正常」证明「从来没卡过」。
