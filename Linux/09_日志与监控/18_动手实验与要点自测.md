> [!info]- 实验环境与纪律（先读）
> - **实测环境**：Ubuntu 24.04.5 LTS（VMware 虚拟机）/ 内核 `6.8.0-139-generic` / systemd 255 / root 可用（另有 `realtyz` `uid=1000`，属 `adm` 组）。**本机有 root，所有需要系统级权限的动作（系统级 `systemd-run`、`journalctl --vacuum-*`、写 `/usr/share` 补模板、`mkfs`/`mount` loop）都用 root 直接做**；用户级 systemd（`systemctl --user`）在本机也可用（`realtyz` 需要 `XDG_RUNTIME_DIR=/run/user/1000`），但**它不再是唯一选择**。
> - **不需要「非 root 绕行」**：`sysstat`、`logrotate`、`logger`、`nc`、`socat`、`python3` 都是系统里现成的。旧笔记里那种「因为非 root、装不了包，所以只能解包运行」的处境在本机**不成立**。
> - **仍然解包运行的**：Prometheus、Alertmanager、blackbox_exporter、node_exporter。**理由改为「实验环境的一次性做法」**：不把服务装进系统、不留常驻服务与监听端口、做完即删。生产上应当正常安装并由 systemd 托管。
> - **Alertmanager 的特例**：Debian 包把默认模板编译成 `/usr/share/prometheus/alertmanager/*.tmpl` 的绝对路径，直接解包运行会报 `failed to parse templates`。**本机有 root，把包内那两个 `.tmpl` 放到该路径即可（等价于 `apt install` 的效果），做完 `rm -rf /usr/share/prometheus`**。旧笔记用的 `unshare -U -r -m` + tmpfs 绕法在本机已被 AppArmor 禁掉（`kernel.apparmor_restrict_unprivileged_userns=1`，实测报 `Operation not permitted`）。
> - **端口约定**：所有监听都绑在 `127.0.0.1`，且全部落在本章区间 **20600–20799** 内（实测用到 `20600`/`20601`/`20602`/`20603`/`20604`/`20605`/`20610` 与 `20700`–`20705`）；每个实验结束都杀进程、删临时目录，并用 `ss -lntup` 复核。
> - **两条不能破的边界**：只有 T1 允许在生产机上做且全程只读；`logrotate -f`、`rm` 大文件、改采集/告警配置、建静默都属于 T2 及以上，只在实验机或有明确影响面评估时做。
> - **未实测的部分**（见实验 11）：正常安装与 systemd 集成、真正的跨机日志集中（含 TLS 与断网重连）、日志平台（Loki/ES）、追踪后端、K8s DaemonSet、云监控/云日志、RHEL 系默认值、真实通知渠道投递。

## 4. 实验 12：T4 限时模拟

> - **场景 A**：根分区使用率 96%，`du -xsh /var/log/*` 只有 2G。

> ```text

## 5. 要点自测（跨篇）

> [!question]- 「日志写满磁盘」和「告警不响」这两类问题的排查顺序有什么共同点？
> - **都先只读取证**：前者 `df -hT`/`df -i`/`du`/`lsof +L1`；后者 `ALERTS` → 路由 → 抑制/静默 → 渠道。
> - **都先定位环节再动手**：磁盘满要分四类原因；告警不响要分「没算出来 / 没路由 / 被压制 / 渠道失败」。
> - **都禁止跳过定位直接执行「看起来能解决」的动作**（`rm -rf`、改阈值）。
> - **第一反应不要是什么**：不要用「现象消失」当验收标准。

> [!question]- 「服务变慢」和「服务报错」分别该先看哪条链路？为什么不能只靠日志？
> - **报错**：先看**日志**（错误码、堆栈、第一次出现的时间）与错误率指标。
> - **变慢**：先看**指标**（资源水位、延迟分位数），再看**追踪**（哪一段慢），日志用来补细节。
> - **不能只靠日志**：日志是逐条文本、没有聚合能力，「CPU 从 30% 涨到 90%」这种趋势在日志里看不出来。
> - **也不能只靠指标**：指标给不出「哪一次请求、哪个下游、哪条 SQL」。
> - **正确顺序**：指标定范围 → 日志/追踪定根因 → 变更时间线定诱因。

> [!question]- 为什么监控要看分位数而不是只看平均值？为什么「p95 是多少」还取决于算法？
> - **平均值掩盖长尾**：实测 950×20ms + 45×100ms + 5×2000ms → 平均 33.5ms、最大 2000ms；占 5% 的长尾样本贡献了 43% 的总耗时。
> - **分位数是估计值**：同一份数据的 p95 在四种口径下是 20.0 / 24.0 / 96.0 / 100.0 ms（本机 Python 3.12.3 实测），差 5 倍。
> - **跨实例聚合**：全局 p99 ≠ 各实例 p99 的平均，必须合并直方图。
> - **落点**：把「算法 + 窗口 + 聚合层级」写进指标口径说明。
> - **第一反应不要是什么**：不要拿口径不同的 p99 做跨系统对比。

> [!question]- 保留策略要配哪三层？为什么缺一层都不行？
> - **应用层**：按级别输出（生产不开 debug）——控制产生速率。
> - **采集层**：journald 的 `SystemMaxUse=`/`MaxRetentionSec=`——控制系统日志总量。
> - **文件层**：`logrotate` 的 `rotate`/`size`/`compress`——控制自建日志的份数与压缩。
> - **实测参照**：本机 rsyslog 规则是 `rotate 4`/`weekly`/`compress`/`delaycompress`/`sharedscripts`；本次开机内 `logrotate.service` 没有执行记录（当天触发点还没到，`NEXT` 在次日 `00:00`），判据用 `ExecMainStartTimestamp` + `journalctl -u logrotate.service`——**不要用 `ConditionResult`**（本机的 `ConditionACPower=true` 实测是成立的）；journal `26.3M`（以现场为准），且 `/var/log` 与业务数据同在 48.0 GiB 的根文件系统上（未分盘）。
> - **第一反应不要是什么**：不要以为配了其中一层就安全。

> [!question]- 从「指标暴露」到「有人收到一条能干活的通知」，中间要经过多少环节？怎么逐段验证？
> - **环节**：exporter `/metrics` → Prometheus 抓取（`up`）→ 规则评估（`ALERTS`）→ Alertmanager 路由 → 分组 → 抑制 → 静默 → 通知渠道 → 人。
> - **逐段验证**：`curl /metrics` → `query=up` → `query=ALERTS` → `amtool config routes test` → `/api/v2/alerts` 的 `silencedBy`/`inhibitedBy` → 渠道。
> - **实测依据**：`promtool check rules` → `SUCCESS`；`ALERTS` 出现 firing；分组把同 `alertname+service` 的两条合成一条；静默与抑制分别在状态字段里可见（`silencedBy=['a23478de-…']`、`inhibitedBy=['0c65b10c93ac87dc']`）。
> - **第一反应不要是什么**：不要跳过前几段直接查渠道。

> [!question]- `up`、`probe_success`、`node_load1` 这三个指标分别在回答什么问题？
> - **`up`**：Prometheus 能不能抓到目标的 `/metrics`（监控链路的健康度）；本机实测 `up{instance="127.0.0.1:20600"}=1`。
> - **`probe_success`**：blackbox 从探测点能不能按预期访问目标（更接近用户视角的可用性）；本机实测在监听的端口是 `1`、无人监听的 `20699` 是 `0`。
> - **`node_load1`**：过去 1 分钟的平均负载，**与核数比较才有意义**（本机 4 vCPU），且包含 D 状态进程；本机实测 `0.18`。
> - **组合使用**：`up` 挂掉说明采集断了；`up=1` 但 `probe_success=0` 说明「指标在报，但用户访问不了」。
> - **第一反应不要是什么**：不要把 `up=1` 当成服务可用。

> [!question]- 时钟不同步会污染哪些判断？最小验证命令是什么？
> - **污染**：跨机日志先后顺序、日志与指标的对齐、证书有效期、追踪 span 顺序、审计可追溯性。
> - **实测细节**：journald 同一条记录里既有 `__REALTIME_TIMESTAMP` 也有 `__MONOTONIC_TIMESTAMP`（单位微秒，本机一次实测为 `1789805176318725` 与 `3466326305`）；`sadf -d` 导出的是 UTC——**本机 `Time zone: Etc/UTC`，所以与 `sar` 的本地时间相同（差 0），换到 `Asia/Shanghai` 会差 8 小时**。
> - **最小验证**：`timedatectl`（看时区、`System clock synchronized`、NTP）与 `timedatectl timesync-status`（看同步源与 `Poll interval`）。**本机实测 `System clock synchronized: no` 而 `NTP service: active`（`Packet count: 0`）——这是要修的前提。**
> - **第一反应不要是什么**：不要在时钟不同步的机器上做时间线推断。
