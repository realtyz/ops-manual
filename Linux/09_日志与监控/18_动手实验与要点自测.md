> - **端口约定**：所有监听都绑在 `127.0.0.1` 的高位端口（18080/19090/19093/19100/19115），不需要 root；每个实验结束都杀进程、删临时目录。
> - **两条不能破的边界**：只有 T1 允许在生产机上做且全程只读；`logrotate -f`、`rm` 大文件、改采集/告警配置、建静默都属于 T2 及以上，只在实验机或有明确影响面评估时做。
> - **未实测的部分**（见实验 11）：正常安装与 systemd 集成、真正的跨机日志集中（含 TLS 与断网重连）、日志平台（Loki/ES）、追踪后端、K8s DaemonSet、云监控/云日志、RHEL 系默认值、真实通知渠道投递。

## 2. 实验索引（怎么做、预期、风险、回滚）

每个实验的完整步骤写在对应子笔记的 `> [!example]-` 折叠块里。本页只给一句话摘要与验收标准：

| # | 一句话怎么做 | 验收标准（预期） |
| --- | --- | --- |
| 1 | `systemd-run --user` 起一个打印 JSON 的命令，再用 `journalctl -o json` 看字段 | `MESSAGE` 里是原文 JSON，`PRIORITY=6`、`_SYSTEMD_USER_UNIT` 由 journald 加上 |
| 2 | 在 `/tmp` 建两个日志，分别用 `copytruncate` 与 `create`+`postrotate` 轮转一次 | `copytruncate` inode 不变；`create` inode 变化且新数据进新文件（配了 `postrotate`） |
| 3 | `nc` 在本机端口抓 `logger --udp/--tcp` 的报文 | 报文为 `<13>1 <带时区时间戳> <主机> labtest - - [timeQuality …] <消息>`；UDP 无换行、TCP 有 |
| 4 | `exec 4>file` 后写入 200MiB 再 `rm`，观察 `df` 与 `du` | `df` 涨约 200MiB、`du` 看不到；关闭 fd 后回落 |
| 5 | 解包运行 node_exporter，抓一次 `/metrics` | 返回 `200 text/plain; version=0.0.4`；能取到 `node_load1` 等关键指标与采集器耗时 |
| 6 | 解包运行 Prometheus，配一条记录规则 + 一条必然触发的告警规则 | `promtool check rules` 返回 `SUCCESS`；`ALERTS` 出现 `alertstate="firing"` |
| 7 | 解包运行 Alertmanager + webhook，发多条告警 | webhook 收到按 `groupKey` 合并的分组；silence 后 `silencedBy=[id]`；critical 让同实例 warning `inhibitedBy=[fingerprint]` |
| 8 | 用 Python 算 SLO 换算表并写一份 SLO 卡 | 99.9% → 30 天 2592 秒（43.2 分钟）；写清窗口与口径 |
| 9 | 写一份成本基线卡（三个数字 + 分盘 + owner） | 三个数字都有依据与 owner；与账单/磁盘增长核对差异不超过 2 倍 |
| 10 | 解包运行 sysstat：`sadc` 采样后 `sar` 读回、`sadf` 导出 | 能读回 CPU/内存/网卡；CSV 时间戳为 UTC；配置里 `HISTORY=7` |
| 11 | 在真机/多机补做未实测部分 | 见下一节清单 |
| 12 | 限时 20 分钟：给一个现象，定位并写处置报告 | 报告含现象/环节/三条证据/根因/止血/修复/回滚/下一步 |

## 4. 实验 12：T4 限时模拟

> [!example]- 现象 → 定位 → 处置报告（20 分钟）
> 从下面三个场景里任选一个（或由同伴随机指定）：
> - **场景 A**：根分区使用率 96%，`du -xsh /var/log/*` 只有 2G。
> - **场景 B**：一条「磁盘使用率 > 85%」的告警在夜里反复触发，白天正常。
> - **场景 C**：某接口 p99 从 300ms 涨到 2s，但本服务 CPU/内存/IO 都正常。
> 交付一份报告，必须包含八段：
> ```text
> 1. 现象与影响面（谁受影响、从几点开始、多严重）
> 2. 定位到的环节（日志落点 / 轮转 / 容量 / 采集 / 规则 / 降噪 / 统计口径 / 时间基线）
> 3. 三条证据（每条都要有命令与关键输出）
> 4. 根因（区分「诱因」与「放大因素」）
> 5. 止血动作（做了什么、影响面、什么时候回滚）
> 6. 修复动作（治本，含验收标准）
> 7. 回滚方案
> 8. 下一步（要补的指标/告警/Runbook）
> ```
> **判分要点**：有没有先做只读取证；有没有分清止血与治本；证据能不能复现；有没有写「第一反应不要做什么」。
> **风险**：低（只在实验机操作）。
> **耗时**：20 分钟限时 + 10 分钟复盘。

## 5. 要点自测（跨篇）

> [!question]- 「日志写满磁盘」和「告警不响」这两类问题的排查顺序有什么共同点？
> - **都先只读取证**：前者 `df -hT`/`df -i`/`du`/`lsof +L1`；后者 `ALERTS` → 路由 → 抑制/静默 → 渠道。
> - **都先定位环节再动手**：磁盘满要分四类原因；告警不响要分「没算出来 / 没路由 / 被压制 / 渠道失败」。
> - **都禁止跳过定位直接执行「看起来能解决」的动作**（`rm -rf`、改阈值）。
> - **第一反应不要是什么**：不要用「现象消失」当验收标准。

> [!question]- 「服务变慢」和「服务报错」分别该先看哪条链路？为什么不能只靠日志？
> - **报错**：先看**日志**（错误码、堆栈、第一次出现的时间）与错误率指标。
> - **变慢**：先看**指标**（资源水位、延迟分位数），再看**追踪**（哪一段慢），日志用来补细节。
> - **不能只靠日志**：日志是逐条文本、没有聚合能力，「CPU 从 30% 涨到 90%」这种趋势在日志里看不出来。
> - **也不能只靠指标**：指标给不出「哪一次请求、哪个下游、哪条 SQL」。
> - **正确顺序**：指标定范围 → 日志/追踪定根因 → 变更时间线定诱因。

> [!question]- 为什么监控要看分位数而不是只看平均值？为什么「p95 是多少」还取决于算法？
> - **平均值掩盖长尾**：实测 950×20ms + 45×100ms + 5×2000ms → 平均 33.5ms、最大 2000ms。
> - **分位数是估计值**：同一份数据的 p95 在四种口径下是 20.0 / 24.0 / 96.0 / 100.0 ms（本机实测），差 5 倍。
> - **跨实例聚合**：全局 p99 ≠ 各实例 p99 的平均，必须合并直方图。
> - **落点**：把「算法 + 窗口 + 聚合层级」写进指标口径说明。
> - **第一反应不要是什么**：不要拿口径不同的 p99 做跨系统对比。

> [!question]- 保留策略要配哪三层？为什么缺一层都不行？
> - **应用层**：按级别输出（生产不开 debug）——控制产生速率。
> - **采集层**：journald 的 `SystemMaxUse=`/`MaxRetentionSec=`——控制系统日志总量。
> - **文件层**：`logrotate` 的 `rotate`/`size`/`compress`——控制自建日志的份数与压缩。
> - **实测参照**：本机 rsyslog 规则是 `rotate 4`/`weekly`/`compress`/`delaycompress`；journal 约 580MiB。
> - **第一反应不要是什么**：不要以为配了其中一层就安全。

> [!question]- 从「指标暴露」到「有人收到一条能干活的通知」，中间要经过多少环节？怎么逐段验证？
> - **环节**：exporter `/metrics` → Prometheus 抓取（`up`）→ 规则评估（`ALERTS`）→ Alertmanager 路由 → 分组 → 抑制 → 静默 → 通知渠道 → 人。
> - **逐段验证**：`curl /metrics` → `query=up` → `query=ALERTS` → `amtool config routes test` → `/api/v2/alerts` 的 `silencedBy`/`inhibitedBy` → 渠道。
> - **实测依据**：`promtool check rules` → `SUCCESS`；`ALERTS` 出现 firing；分组产生两个 `groupKey`；静默与抑制分别在状态字段里可见。
> - **第一反应不要是什么**：不要跳过前几段直接查渠道。

> [!question]- `up`、`probe_success`、`node_load1` 这三个指标分别在回答什么问题？
> - **`up`**：Prometheus 能不能抓到目标的 `/metrics`（监控链路的健康度）。
> - **`probe_success`**：blackbox 从探测点能不能按预期访问目标（更接近用户视角的可用性）。
> - **`node_load1`**：过去 1 分钟的平均负载，**与核数比较才有意义**，且包含 D 状态进程。
> - **组合使用**：`up` 挂掉说明采集断了；`up=1` 但 `probe_success=0` 说明「指标在报，但用户访问不了」。
> - **第一反应不要是什么**：不要把 `up=1` 当成服务可用。

> [!question]- 时钟不同步会污染哪些判断？最小验证命令是什么？
> - **污染**：跨机日志先后顺序、日志与指标的对齐、证书有效期、追踪 span 顺序、审计可追溯性。
> - **实测细节**：journald 同一条记录里既有 `__REALTIME_TIMESTAMP` 也有 `__MONOTONIC_TIMESTAMP`（单位微秒）；`sadf -d` 导出的是 UTC，实测与本地时间差 8 小时。
> - **最小验证**：`timedatectl`（看时区、`System clock synchronized`、NTP）与 `timedatectl timesync-status`（看同步源与 `Root distance`）。
> - **第一反应不要是什么**：不要在时钟不同步的机器上做时间线推断。

> [!question]- 这一章交付的九项技能分别要交出什么？
> - **S1 可观测性基线盘点** → 一份可观测性基线卡。

> - **S6 规则与告警编写** → 规则文件 + CI 校验记录。
