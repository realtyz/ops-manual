## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **处置的第一步永远是「定位到环节」：日志落点、轮转、容量、采集、规则还是通知。**
>   - 怎么验证：动手前先写下「我认为卡在哪一环」，再按第 1 节的速查表核对；定位错了，后面每一步都是浪费。
> - **只读取证先行。**
>   - 怎么验证：`df`/`du`/`lsof`/`journalctl`/`curl` 都可以在生产机上做；改配置、删文件、重启服务要单独评估影响面。
> - **先止血再治本，止血不等于解决。**
>   - 怎么验证：把处置写成「止血 / 治本 / 防线」三段；只写了一段的报告，说明根因还没处理。
> - **「告警不响」要沿链路逐段验证，不要一上来就怀疑渠道。**
>   - 怎么验证：`ALERTS` → 路由 → `silencedBy`/`inhibitedBy` → 通知渠道，逐段都能给出结论（本机实测静默与抑制都在状态字段里直接可见）。
> - **每一类现象都要留证据：命令、时间、关键输出。**
>   - 怎么验证：把处置记录交给同事，他能否照着复现你看到的每一个数字。

## 2. 磁盘被日志写满

> [!tip] 第一反应不要是 `rm -rf /var/log/*`
> 先定位「哪个文件系统满、谁占的、是活文件还是已删除但仍被持有」。直接删目录可能删掉正在被写的文件（空间不释放）、破坏审计要求、也丢掉复盘证据。

**只读取证（生产机可做）**：

```bash
df -hT; df -i                                   # 验证：空间满还是 inode 满、哪个文件系统
du -xsh /var/log/* 2>/dev/null | sort -h | tail -10
find /var/log -xdev -type f -size +100M -printf "%s %p\n" | sort -n | tail
lsof +L1 2>/dev/null | head                     # 验证：已删除但仍被持有（无 lsof 就遍历 /proc/*/fd）
journalctl --disk-usage                         # 验证：journal 占了多少（会变，以现场为准）
```

本机实测样张（现场时间 2026-09-19T08:14:42+00:00）：

```text
/dev/mapper/ubuntu--vg-ubuntu--lv ext4   47G  8.7G   36G  20% /
/dev/mapper/ubuntu--vg-ubuntu--lv 3145728 159901 2985827    6% /
Archived and active journals take up 26.2M in the file system.
1.4M	/var/log/syslog
1.2M	/var/log/audit
27M	/var/log/journal
```

**处置顺序**：① 确认不是业务数据；② 对活文件先让它轮转（`logrotate -f <conf>`）或临时压缩/截断；③ 对已删除文件让进程重开日志/重启服务；④ 补齐三层保留策略与容量告警。**删之前保留最近一段**——故障复盘还要用。

**判据回看**：本机在 64MiB 的临时 loop 文件系统上实测——`rm` 掉一个仍被持有的 10MiB 文件后，`df` 已用从 `24576` 涨到 `10510336` 字节（恰好 `+10485760`），而 `du -sh` 只看到 20K；关闭 fd 后立刻回落到 `24576`（子笔记 08 实验 4）。

## 3. 日志查不到 / 查不全

按「日志到底写到哪」四条路走：

```bash
systemctl show <unit> -p StandardOutput -p StandardError   # ① 是否写进 journald
journalctl -u <unit> -b --since "10 min ago" --no-pager    # ② 单元/boot/时间窗对不对
journalctl -o json -n 1 | python3 -m json.tool | head -20  # ③ 字段里有没有你要的实例/trace
tail -50 /var/log/syslog /var/log/<app>.log 2>/dev/null    # ④ 是否走了 rsyslog 或自有文件
systemd-analyze cat-config systemd/journald.conf | grep -E "Storage|MaxUse|RateLimit|Forward"
```

本机实测（`logger` 造的消息同时进了两个落点，可直接复现）：

```text
$ journalctl -t labtest -n 1 -o json | python3 -c "import json,sys; d=json.load(sys.stdin); print({k:d[k] for k in ['SYSLOG_IDENTIFIER','_PID','_UID','_TRANSPORT','MESSAGE']})"
{'SYSLOG_IDENTIFIER': 'labtest', '_PID': '15907', '_UID': '0', '_TRANSPORT': 'syslog', 'MESSAGE': 'hello-from-logger'}
$ tail -1 /var/log/syslog
2026-09-19T08:06:27.429240+00:00 linux-lab labtest: hello-from-logger
```

四类常见原因：

1. **落点不对**：应用写自己的文件，journald 只能看到 stdout 与 syslog 套接字。
2. **没持久化**：`/var/log/journal` 不存在，`Storage=auto` 退化成内存存储，重启即丢。**本机 `/var/log/journal` 存在（持久化）**，所以不属于这一种。
3. **被限流丢弃**：`journalctl -u <unit> | grep -i suppres` 可以看到 `Suppressed N messages`。
4. **看错 boot/时区**：`-b -1` 选错开机，或 `--since` 用的是本地时间而你以为在填 UTC。**本机 `TZ=Etc/UTC`，本地时间与 UTC 相同，所以这类错误在本机反而更隐蔽。**

## 4. 轮转没生效 / 新日志文件不增长

| 现象 | 检查 | 结论方向 |
| --- | --- | --- |
| 该轮转没轮转 | `logrotate -d <conf>`；`/var/lib/logrotate/status` 的上次时间；`size`/`daily` 条件 | 条件未到、`notifempty`、或规则没被读进来 |
| 轮转后新日志为空、旧归档在长 | `stat -c %i` 两个文件；`ls -l /proc/<pid>/fd` | 程序还持有旧 fd（`create` 场景），需要 `postrotate` 发信号或重启 |
| 轮转后偶发丢日志 | 是否用了 `copytruncate`；写入速率 | 复制与截断之间的窗口会丢 |
| 状态文件被清理或丢失 | `/var/lib/logrotate/status` 是否存在 | 状态丢失会导致「刚轮过又轮」或按错误时间判断 |

**判据回看**（本机实测）：`create` 之后不通知应用重开文件，随后 **9 行**数据全部写进归档文件（`app2.log.1`）、新文件 `app2.log` 0 行；inode 从 `1310803`（新）与 `1310798`（归档）可见确实换了文件。而 `copytruncate` 那条路 inode 保持 `1310736 → 1310736` 不变（子笔记 06）。

**注意本机的一个现场**：本次开机内 `logrotate.service` 没有执行记录（`ExecMainStartTimestamp` 为空、`journalctl -u logrotate.service` 无条目），原因是 `logrotate.timer` 是 `OnCalendar=daily`、当天的触发点还没到（`NEXT` 是次日 `00:00`）——**不是被条件挡住的**（`ConditionACPower=true` 实测成立）。所以「`rotate 4` 配好了」不等于「真的轮转过」；判据是 `ExecMainStartTimestamp` + `journalctl -u <unit>`，**不要用 `ConditionResult`**（它不区分「求值失败」与「从未求值」，看 `ConditionTimestampMonotonic`；子笔记 06 第 1.1 节）。

## 5. 日志集中后断流 / 中心机磁盘满

```bash
systemctl status rsyslog; grep -vE "^\s*(#|$)" /etc/rsyslog.d/*.conf   # 发送端：转发配置是否还在
journalctl -u rsyslog --since "30 min ago" | tail -20                   # 验证：有没有队列/重试/丢弃的报错
ls -lt /var/log/<集中目录>/ | head                                      # 接收端：最新一条是什么时候
df -hT <集中目录所在文件系统>                                            # 接收端：容量水位
```

**处置顺序**：① 先确认「断的是发送端还是接收端」（看接收端最新文件时间）；② 接收端容量问题先止损（保留策略、压缩、清理最老）；③ 发送端积压要确认队列类型（内存队列会在接收端不可达时丢）；④ 关键日志改 TCP/TLS/RELP 并做接收计数对账。

## 6. 指标缺失、断点或抓取失败

```bash
curl -s "http://<prom>:9090/api/v1/targets" | python3 -m json.tool | grep -E "health|lastError" | head   # Prometheus 侧
curl -s "http://<prom>:9090/api/v1/query?query=up" | head
curl -s "http://<prom>:9090/api/v1/query?query=scrape_duration_seconds" | head
curl -s -o /dev/null -w "%{http_code} %{time_total}\n" http://<target>:9100/metrics                      # 目标侧
ss -lntp | grep 9100; systemctl status <exporter>
```

本机实测的最小闭环（解包运行 node_exporter 在 `127.0.0.1:20600`、Prometheus 在 `127.0.0.1:20601`）：

```text
http=200 content_type=text/plain; version=0.0.4; charset=utf-8; escaping=values
{'__name__': 'up', 'instance': '127.0.0.1:20600', 'job': 'node'} 1
{'__name__': 'scrape_duration_seconds', 'instance': '127.0.0.1:20700', 'job': 'node'} 0.09499738
```

（第一、二行来自本次 `20600`/`20601` 那一轮实测；第三行的 `scrape_duration_seconds` 来自另一轮 `20700` 的抓取——**两次都是本机真跑，端口不同是因为实验批次不同**。抓一次 1500 多条指标耗时约 95 ms。）

**排查顺序**：目标是否监听/可访问 → exporter 是否健康（采集耗时、错误）→ Prometheus 是否抓得到（`up`/`lastError`）→ 规则与查询是否正确（label、时间窗）。

**断点的四个常见来源**：目标重启（counter 归零——`rate()`/`increase()` 会**自动补偿、不会出现负值**，受影响的只是重置点附近的外推精度）、采集超时（`scrape_timeout` 小于采集耗时）、网络/防火墙、**label 变更导致新旧时序断开**。本机还有第五种：**`device` 这类 label 会随环境变**（根分区在 LVM 上时是 `/dev/mapper/ubuntu--vg-ubuntu--lv`，`node_disk_*` 还会同时出现 `dm-0` 与 `sda`），写死了 `device="/dev/sda"` 的表达式换台机器就断。

## 7. 告警不响

```bash
curl -s "http://<prom>:9090/api/v1/query?query=ALERTS" | python3 -m json.tool | head -30        # ① 规则层：有没有触发
curl -s "http://<prom>:9090/api/v1/rules" | python3 -m json.tool | grep -E "name|state|lastEvaluation" | head
amtool config routes test --config.file=/etc/alertmanager/alertmanager.yml severity=critical alertname=X   # ② 路由层
amtool alert query --alertmanager.url=http://<am>:9093                                          # ③ 压制层
amtool silence query --alertmanager.url=http://<am>:9093
```

本机实测的两段关键输出（`ALERTS` 有值 = 规则真的算出来了；状态字段 = 被谁压住了）：

```text
{'__name__': 'ALERTS', 'alertname': 'LabRootAlmostFull', 'alertstate': 'firing', 'severity': 'warning'} 1
 severity=critical service=web instance=linux-lab   state=active     inhibitedBy=[]                     silencedBy=[]
 severity=warning  service=web instance=linux-lab2  state=suppressed inhibitedBy=['0c65b10c93ac87dc'] silencedBy=[]
```

**④ 通知层（渠道是否可用）放在最后一步查**。顺序是：`ALERTS` → 路由 → `silencedBy`/`inhibitedBy` → 通知渠道。**顺序反了就会在渠道上浪费大量时间。**

## 8. 告警风暴

> [!tip] 第一反应不要是「把所有阈值调高」
> 调阈值是**降低灵敏度**，会把真故障一起过滤掉。正确顺序是分组 → 抑制 → 静默 → 复盘后再考虑阈值。

```bash
amtool alert query --alertmanager.url=http://<am>:9093 | head -30   # 验证：当前有多少条、是否同源
amtool silence query --alertmanager.url=http://<am>:9093            # 验证：有没有过期/遗留静默
amtool config routes test --config.file=... severity=critical alertname=X
```

**处置顺序**：① 先按 `alertname`/`service` 归类，找出「一个根因产生了多少条」；② 配置层补分组与抑制（尤其「宕机 ⇒ 其他指标异常」这类确定因果）；③ 对已知问题建**有期限**的静默并记录原因；④ 事后复盘规则本身（阈值、`for`、窗口）。

本机实测的分组效果：同 `alertname+service` 的两条 warning 被合并成一条通知（`groupKey={}/{severity="warning"}:{alertname="NodeCpuHigh", service="web"}`，内含两条），`service="db"` 那条单独一组（子笔记 11）。

## 9. 证书到期 / 用户视角不可用

```bash
curl -s "http://<blackbox>:9115/probe?module=http_2xx&target=https://<域名>" | grep -E "^(probe_success|probe_http_status_code|probe_duration_seconds|probe_ssl_earliest_cert_expiry) "
```

```text
probe_duration_seconds 0.001531452
probe_http_status_code 200
probe_success 1
probe_ssl_earliest_cert_expiry 1.803656795e+09
```

**判据**：`probe_ssl_earliest_cert_expiry - time() < 14 * 86400` 触发证书告警；本机实测上面这个时间戳换算成「剩余 160.3 天」，而同一天另一个域名只有 `1.793139441e+09`（剩余 38.6 天）——**证书告警必须按域名分组，一个全局阈值测不出两种现实**。

**注意**：`probe_success=0` 只说明「从探测点到目标」这条路径不通，不等于目标一定挂了。本机实测探测在监听的 `127.0.0.1:20705` 是 `1`、探测无人监听的 `127.0.0.1:20699` 是 `0`；**上线前用真实探测源与真实路径验证。**

## 10. 服务慢但资源都空闲

```bash
grep -H . /proc/pressure/cpu /proc/pressure/memory /proc/pressure/io    # ① 先确认「确实不忙」（只读）
vmstat 1 3 | tail -2
ss -s | head -3; ss -ti | head -20
```

本机实测的「确实不忙」样张：

```text
/proc/pressure/cpu:some avg10=0.25 avg60=0.39 avg300=1.26 total=16983404
/proc/pressure/cpu:full avg10=0.00 avg60=0.00 avg300=0.00 total=0
/proc/pressure/io:some avg10=0.00 avg60=0.04 avg300=0.39 total=4908689
/proc/pressure/io:full avg10=0.00 avg60=0.04 avg300=0.33 total=4106769
vmstat: r=0 b=0 si=0 so=0 us=1 sy=2 id=97 wa=0
ss: Total: 186 / TCP: 82 (estab 5, timewait 64)
```

**② 再看请求维度**：延迟分位数（哪个接口、哪个实例、从几点开始）、下游依赖的成功率与延迟。**③ 最后看一次请求的 span 树**，并把 `trace_id` 拿去日志系统捞详情。

**常见根因**：锁竞争（应用/数据库）、GC/解释器停世界、DNS 解析慢、下游限流与重试风暴、日志同步落盘、单核打满（整机 CPU 不高）。

## 11. 事后复盘没有历史数据

```bash
ls -l /var/log/sysstat/                    # 验证：有没有当天的 saDD 文件（本机有 sa19，23096 字节）
sar -u -s 03:00:00 -e 04:00:00             # 有数据才谈得上分析（窗口按本地时区解释）
grep -vE "^\s*(#|$)" /etc/sysstat/sysstat  # 验证：HISTORY 是多少（本机 7）
systemctl list-timers 'sysstat*' --no-pager
```

**处置顺序**：① 确认采集是否启用——本机三条判据全部通过（有 `sa19`、两个 timer 都 `enabled`、`sysstat-collect.timer` 的 `LAST` 是最近的整十分）；② 只有在「确实没有历史」时，才改用其它证据源（本机日志、上游监控的历史指标、下游依赖的延迟记录、变更时间线）；③ 把「当日有数据且大小在增长」纳入日常巡检。

> [!important] 别把「有历史」当成理所当然，也别把「没历史」当成既定事实
> 本机就是这个教训的反面：旧版笔记写「本机并未安装 sysstat、`/var/log/sysstat` 不存在」——**在本实验机上这个案例不成立**，`sysstat` 装了、在采、数据就在 `/var/log/sysstat/sa19`。**复盘的第一步永远是 `ls -l` 去看一眼，而不是凭印象下判断**（子笔记 15）。

## 12. 三个系统的证据时间对不上

```bash
timedatectl                                      # 验证：时区、是否同步
timedatectl timesync-status | head -8            # 验证：同步源与 Poll interval
date -Is; date -u +%FT%TZ                        # 验证：本地时间与 UTC 的对应
journalctl -n 1 -o json | python3 -m json.tool | grep -E "REALTIME|MONOTONIC"
```

本机实测：

```text
               Local time: Sat 2026-09-19 08:06:16 UTC
           Universal time: Sat 2026-09-19 08:06:16 UTC
                Time zone: Etc/UTC (UTC, +0000)
System clock synchronized: no
              NTP service: active
```

本机样本里的 journal 字段（**同一条记录同时带墙上时钟与单调时钟，单位都是微秒**）：

```text
{'__MONOTONIC_TIMESTAMP': '3466326305', '__REALTIME_TIMESTAMP': '1789805176318725'}
```

**处置顺序**：① 先统一口径（UTC 还是本地时间，写进报告）；② 确认时钟同步状态并**如实记录**——本机是 `System clock synchronized: no` 且 `NTP service: active`（`Packet count: 0`，尚未完成一次同步），**这是一个要修的前提，不是可以忽略的细节**；③ 需要算「间隔」时用单调时间或序号，不用墙上时钟；④ 记住 `sadf -d` 导出的是 UTC——**本机 `TZ=Etc/UTC` 所以与 `sar` 的本地时间刚好相同（差 0）**，换到 `Asia/Shanghai` 就会差 8 小时（子笔记 02 有 `TZ` 演示：同一时刻分别是 `16:08:53+08:00` 与 `08:08:53+00:00`）。

## 常见坑（跨现象通用）

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 不定位环节就开始动手 | 改了三处还没解决问题，反而引入新变量 |
| 先改配置再取证 | 现场被破坏，后面无法证明根因 |
| 把「现象消失」当「问题解决」 | 重启/静默都能让现象消失，根因仍在 |
| 只留结论不留命令 | 复盘和交接都无法复现 |
| 在生产机上做破坏性验证 | `logrotate -f`、删日志、改采集配置都会产生真实影响 |
| 凭印象说「这台机器没有历史 / 没有监控」 | 本机实测反例：sysstat 在采、`sa19` 有 23096 字节，只是旧笔记的结论没跟着环境更新 |
| 把会变的值写死进笔记或看板 | `journalctl --disk-usage` 本机实测过 `20.7M → 16.0M → 26.2M → 26.3M`；这类量一律写「以现场为准」 |

## 要点自测

> [!question]- 面对「磁盘满」和「告警不响」两类现象，处置的第一条命令分别是什么？
> - **磁盘满**：`df -hT; df -i`——先分清是空间满还是 inode 满、是哪个文件系统。
> - **告警不响**：`curl "http://<prom>:9090/api/v1/query?query=ALERTS"`——先确认规则有没有触发。
> - **共同点**：都先做**只读取证**，再决定动不动手。
> - **第一反应不要是什么**：不要跳过定位直接执行「看起来能解决」的动作。

> [!question]- 哪些动作属于「止血」，哪些属于「治本」？
> - **止血**：清理最老的日志、让进程重开日志（`reload`/`restart`）、建临时静默、扩磁盘。
> - **治本**：补三层保留策略、修 `logrotate` 的 `postrotate`、修 label 基数、把阈值/`for` 改成合理值、加容量与探测告警。
> - **纪律**：止血必须记录「做了什么、影响面是什么、什么时候回滚」；**止血完不回到根因，等于把故障留到下次**。
> - **第一反应不要是什么**：不要把止血动作当成最终方案。

> [!question]- 为什么「告警不响」不要先查通知渠道？
> - **链路上游更可能出问题**：规则没触发（表达式、label、时间窗）、路由没匹配到 receiver、被静默或抑制——这几种都比「渠道坏了」常见。
> - **逐段验证**：`ALERTS` → `amtool config routes test` → `silencedBy`/`inhibitedBy` → 渠道。
> - **实测依据**：本机实测静默与抑制都会让告警变成 `suppressed`，状态字段里能直接看到原因（`silencedBy=['a23478de-…']`、`inhibitedBy=['0c65b10c93ac87dc']`，子笔记 11）。
> - **第一反应不要是什么**：不要因为「没收到邮件」就断定是邮件系统的问题。
