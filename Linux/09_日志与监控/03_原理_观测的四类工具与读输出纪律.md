# 观测的四类工具与读输出纪律

## 1. 四类工具回答四类问题

观测命令看起来杂乱，但若按「它回答什么问题」来归类，它们只有四类；此外还有一类工具不属于观测、却决定观测能不能用：

| 类别 | 回答的问题 | 为什么必须单独一类 |
| --- | --- | --- |
| 日志类 | 它回答日志在不在、写到哪、内容是什么 | 因为它读的是**已经产生的事件**，而不是当前状态 |
| 容量类 | 它回答谁占了空间、还有多少 | 因为它读的是文件系统与内核维护的计数字段（`df` 的已用块、`df -i` 的 inode 计数、`du` 的可见文件总量），而这些计数字段与目录树里看得见的文件并不总是一致 |
| 指标类 | 它回答这台机器或这个服务**现在**是什么状态 | 因为它给出的是**当前值**，一旦过了这一刻就取不到 |
| 历史类 | 它回答**过去某个时刻**发生了什么 | 因为它读的是**提前采样并存下来的数据**，所以它能不能回答取决于有没有采 |
| 时间类 | 它回答上面这些数据的时间戳能不能对齐 | 因为它本身不产生观测结论，只决定其它结论是否成立 |

这个分类的价值在于：**它把「工具用错」和「数据没采」这两种失败区分开了。**

- 若失败属于**工具用错**，它的典型形态是事故已经过去之后才打开 `top` 去看现在的负载，因此这类失败靠换工具解决。
- 若失败属于**数据没采**，它的典型形态是想复盘昨晚三点时，发现历史文件里没有那天的记录，因此这类失败换任何工具都解决不了——**必须在事故发生之前就采**。

第二类失败的代价更高，因为它是不可逆的：此刻没采的数据，事后无法补。所以判断一台机器「观测能力如何」的第一个问题不是「装了哪些工具」，而是「**它有没有在采、采的东西留多久**」。

### 1.1 「现在」与「过去」是两套东西

同一件事在两个时间尺度上有两套完全不同的实现，因此想知道某一项时，要先确定自己问的是此刻还是过去：

| 想知道 | 实时路径 | 历史路径 | 历史的成功条件 |
| --- | --- | --- | --- |
| CPU 忙不忙 | 这一项读 `vmstat`/`mpstat`/`top` 的当前输出 | 这一项读 `sar -u` | 历史路径能回答的前提是采样器正在运行，并且该时刻落在保留期内 |
| 内存使用率（`free` 的 `available`、`/proc/meminfo` 的 `MemAvailable`） | 这一项读 `free` 与 `/proc/meminfo` | 这一项读 `sar -r` | 条件与上一行相同：采样器正在运行，并且该时刻落在保留期内 |
| IO 情况 | 这一项读 `iostat` 与 `/proc/pressure/io` | 这一项读 `sar -b` 与 `sar -d` | 条件与上一行相同：采样器正在运行，并且该时刻落在保留期内 |
| 连接与套接字 | 这一项读 `ss -s` 与 `ss -ti` | 这一项读时序库里的对应指标 | 历史路径能回答的前提是指标已被采集并保留 |

**实时路径的边界在于它永远看不到过去。** 事故后打开实时工具时，你看到的是「事件之后的系统」，因此它最多能回答「问题是否仍在持续」，而不能回答「当时发生了什么」。这正是历史类工具存在的唯一理由，也是「采集本身要可观测」这条纪律的来源：由于历史采集失败时通常不报错，它只表现为 `sa<DD>` 文件静默缺失或不再增长。

## 2. 采样口径的三个陷阱

同一份数据在不同口径下会得到不同的数，因此读任何输出前都要先确认它用的是哪个口径。下面三个陷阱在读任何输出时都要过一遍。

### 2.1 第一行不是当前值

带间隔参数的工具，它的第一行数据常常是**自开机以来的平均值**，因此不能当成此刻的读数：

- `vmstat 1 2` 的第一行数据是开机以来的平均，第二行才是当前这一秒；
- `iostat` 不带参数时给出的是自开机以来的平均值；
- `top`/`uptime` 的 load 是 1/5/15 分钟的平均。

这条纪律的代价可以量化：在一台开机不到一小时的机器上，开机平均值与当前值可能**差两个数量级**（例如上下文切换率的平均是 1、当前一秒是 211）。因此若把第一行当作当前值，得到的结论就会与事实完全相反。

判据很直接：**要看瞬时值，就给「间隔 + 次数」两个参数并取最后一行；`Average:` 那一行是给窗口用的，不是给此刻用的。**

### 2.2 平均值会掩盖长尾

平均是唯一一个必然存在的统计量，也是唯一一个**不能用来描述体验**的统计量。

一组能说明问题的样本：1000 个请求里 950 个 20ms、45 个 100ms、5 个 2000ms。平均值是 33.5ms，最大值是 2000ms。**占 5% 的长尾样本贡献了约 43% 的总耗时**，但它们在平均值里只留下约 10ms 的痕迹。

它的排障含义是：若只看平均延迟，就会得出「服务挺快的」这一结论，而真实体验是「每 200 个请求里有 1 个要等 2 秒」。**长尾是平均值的一部分，却不是平均值能表达的那一部分。**

### 2.3 分位数也看口径

换用分位数能解决长尾问题，但它引入了一个新问题：**同一个 p95，算法不同结果就不同。**

同一份样本在四种常见定义下会给出四个不同的答案，因此口径必须写清：

| 口径 | p95 |
| --- | --- |
| 最近排名法（取第 `ceil(n×p)` 名） | 该口径给出 20.0 ms |
| 线性插值（`inclusive` 型） | 该口径给出 24.0 ms |
| 线性插值（`exclusive` 型） | 该口径给出 96.0 ms |
| 0 基下标 `int(n×p)` | 该口径给出 100.0 ms |

四个答案之间相差 5 倍。原因不难理解：当数据里有大间隔（20ms 跳到 100ms 再跳到 2000ms）时，「落在哪个位置」和「在两点之间插值」会给出完全不同的落点，而 0 基与 1 基的下标约定又会错开一格。

由此推出三条实务要求：

1. **跨系统对比 p99 之前先统一口径**，因为算法、窗口与聚合层级这三样都要一致；
2. **Prometheus 用直方图 bucket 近似分位数**，因此导出到别处再算一次又会得到另一种近似；
3. **写「p99 < 500ms」这种目标时，必须写清楚这个数是用什么算出来的。**

### 2.4 聚合层级不能靠平均来合并

最后一个陷阱关于聚合层级：**全局 p99 不等于各实例 p99 的平均。**

无论用哪个口径，分位数都不是线性可加的。直观的理由是：分位数描述的是「位置」，而「位置」依赖整个分布。10 个实例各有一个 p99，各自丢弃了自己分布 99% 之后的信息；若把这些 p99 再平均一次，就等于对已经丢掉信息的结果做二次加工。因此当各实例流量差异很大时，全局的分位位置会被**大流量实例**主导，而简单平均会给每个实例相同权重。

正确做法是把各实例的**直方图分桶相加**，再在合并后的分布上取分位数——Prometheus 的 `histogram_quantile()` 就是这个思路。它的代价是分桶本身只是近似：桶宽决定精度，分位数落在两个桶之间时只能插值。

## 3. 累积量：补上采样点之间的盲区

周期性采样有一个绕不过去的先天缺陷：**采样点之间的状态看不见。** 若抓取间隔是 60 秒，而 CPU 只在其中 10 秒处于满载，则采样点很可能正好落在 CPU 空闲的那一段。

补这个盲区有两条路径：

1. **提高采样频率**，因为它的成本随频率线性增长，而且抓取本身也会给目标加压；
2. **改用累积量（counter）**，因为它是只增不减的累计值，所以只要它涨了，就说明那段时间确实发生过。

内核的压力指标 PSI（Pressure Stall Information，压力停顿信息）正好两者都有，因此值得把它的字段结构讲清楚，它是理解所有累积量的典型结构：

| 字段 | 类型 | 含义 | 读法 |
| --- | --- | --- | --- |
| `some` | 它按维度逐行给出 | 它表示至少有**一个**任务被卡住 | 它反映的是局部抖动，也就是「有人被影响了」 |
| `full` | 它按维度逐行给出 | 它表示**所有**任务都被卡住 | 它反映的是全面停顿，因此即使平均值不高，延迟也已经受影响 |
| `avg10`/`avg60`/`avg300` | 它们是滑动平均，属于瞬时量 | 它们分别是最近 10/60/300 秒的均值 | 它们**会稀释短脉冲**，因此只能用来判断趋势 |
| `total` | 它是累积量 | 它是自开机以来累计停顿的微秒数 | 它**只增不减，因此两次读数相减就是这段时间的停顿量** |

读它的顺序是：先用 `some` 与 `full` 判断「有没有卡」和「卡得多严重」，再看 `avg300` 判断趋势，需要定量时用两次 `total` 的差。**若只读 `avg10` 就下结论，就等于放弃了 `total` 提供的那部分信息**，而那正是采样盲区里唯一留下的证据。

同类结构在别处也反复出现，例如 `nstat` 的丢包计数、`/proc/net/dev` 的错误计数与 `node_cpu_seconds_total` 的累计秒数。它们的共同点是：**单次读值没有意义，有意义的是两次读值的差（或除以时间得到的速率）。**

## 4. 单位、窗口与来源：读输出时固定要记的三样

一个结论如果不带这三样，事后就无法复核，也无法与别的数据对比，因此下表把它们逐项列出：

| 要素 | 为什么必须写 | 常见错误 |
| --- | --- | --- |
| 单位 | 因为 `MiB` 与 `MB` 相差 4.9%，而 `KiB/s` 与 `KB/s` 同理 | 常见错误是用 `df -h` 的数字去做减法 |
| 时间窗 | 因为 5 分钟的平均与 1 小时的平均可能给出相反结论 | 常见错误是只写「平均负载 3」而不写窗口 |
| 来源与口径 | 因为同一个量在不同工具下的口径不同 | 常见错误是把某台机器的 `%util` 当作整个集群的饱和度 |

窗口的作用可以用一个具体对照说明：一个 30 分钟窗口的平均 CPU 使用率是 0.80%，而窗口内单个 10 分钟采样点是 1.51%——**近两倍**。若只看平均，就会得出「这段时间很闲」的结论；反之若看单点，就会看到其中一个区间明显更忙。**窗口不是给人方便的参数，它本身就是结论的一部分。**

## 5. 只读与破坏性的边界

观测动作本身有代价，其中一些代价不可逆。

- 若属于**只读类**，它包含读 `/proc` 与 `/sys` 的观测文件，`df`/`du`/`lsof`、`ss`、`vmstat`、`sar`、`history` 类的查询，`journalctl` 的读取，以及用 `curl` 抓取指标端点。**这些在生产机上也可以做。**
- 若属于**改变状态类**，它包含清理与裁剪（`journalctl --vacuum-*`、删日志）、强制轮转（`logrotate -f`）、改配置并重启采集、建静默与改告警规则。**这些只在可快照的实验机上做**，并且要写清回滚。
- 若属于**测量类**，它为测量而降低缓存效果，例如 `drop_caches` 这类动作会改变系统行为与性能特征。**它只用于测量，生产上不要执行。**

判据是「结束后系统是否与开始前等价」：只读动作使系统等价，其余动作都不等价。**注意 `--vacuum-*` 属于第二类里最容易被误当成第一类的一个**，因为它看起来像清理，实际却会删掉历史证据且不可恢复。

## 6. 常见误解

| 常见说法 | 事实 |
| --- | --- |
| 「先 `tail -f` 看看」 | 若只看实时输出的尾部，就容易错过故障开始时的第一条错误，因此要用时间窗与单元过滤 |
| 把带间隔工具的第一行当当前值 | 带间隔工具的第一行是自开机以来的平均值，因此当前值要从第二行起算 |
| 「平均延迟达标就行」 | 长尾会被掩盖：平均 33.5ms 的数据里，最慢请求是 2000ms，5% 的长尾占了 43% 的总耗时 |
| 「p95 就是 p95，算法无所谓」 | 同一份数据在四种常见口径下会得到 20.0/24.0/96.0/100.0 ms 四个答案 |
| 把各实例的 p99 求平均当全局 p99 | 分位数不可加，因此要合并直方图分桶再取分位数 |
| 用 1 小时平均判断「有没有卡过」 | 周期性抖动会被空闲时间稀释，因此要看最大值、分位数与累积量 |
| 只读 PSI 的 `avg10` 就下结论 | `avg10` 是滑动平均，因此它会稀释短脉冲；要判断「这段时间卡过没有」，就要看两次 `total` 的差 |
| 「事故之后再打开 `top` 也一样」 | 实时工具看不到过去，因此历史复盘依赖提前采集 |
| 「用 `du` 判断文件系统满没满」 | `du` 走目录树，因此它看不到已删除但仍被打开的文件；两者要一起看 |
| 把命令截断的产物当成工具行为 | 例如若只看 `tail -2`，就会截掉表头，从而以为输出没有列名 |

## 要点自测

**问：为什么「事故之后再打开 `top`」通常没有用？**
答：实时工具只反映此刻。事故已过去时，它最多能回答「问题是否仍在持续」。要回答「当时发生了什么」，必须有提前采样的历史数据——这是历史类工具存在的原因，也是「采集本身要可观测」这条纪律的来源。

**问：`vmstat 1 2` 的两行数据分别是什么？**
答：第一行是自开机以来的平均值，第二行才是当前这一秒。带间隔参数的工具普遍有这个行为（`iostat` 不带参数时同理）。要看瞬时值就给「间隔 + 次数」并取最后一行。

**问：为什么同一个 p95 会算出不同的数？**
答：分位数不是数据里本来就有的东西，而是由算法定义的：最近排名法、两种线性插值、0 基下标对同一份数据给出 20.0/24.0/96.0/100.0 ms。此外窗口与聚合层级也会改变结果。跨系统比较前必须统一这三样。

**问：为什么不把各实例的 p99 平均成全局 p99？**
答：分位数描述「位置」，依赖整个分布，因此不可加。简单平均会给大流量与小流量实例相同权重，而全局分位位置实际由大流量实例主导。正确做法是合并各实例的直方图分桶再取分位数。

**问：PSI 的 `avg10` 和 `total` 分别该怎么用？**
答：`avg10/60/300` 是滑动平均（瞬时量），适合看趋势，但会稀释短脉冲；`total` 是自开机以来的累积停顿微秒数，只增不减，两次读数的差就是这段时间的停顿量。判断「这段时间卡过没有」要看 `total`；`some`/`full` 用来区分「部分任务被卡」和「全部任务被卡」。

**第一反应不要做什么**：不要用实时工具解释过去的现象；不要把第一行数据当当前值；不要用平均值向用户解释体验；不要在本机口径未统一时比较两个来源的分位数；不要在事故发生后才发现历史采集根本没在跑。

## 参考文档

- `man 1 vmstat`、`man 1 iostat`、`man 1 mpstat`、`man 1 pidstat`：各工具的间隔语义、首行平均值与字段含义。
- `man 1 sar`、`man 1 sadc`、`man 1 sadf`、`man 5 sysstat`：历史采样的机制、保留期与导出格式。
- `man 5 proc_pid_pressure`：PSI 的 `some`/`full` 与 `avg*`/`total` 字段定义。
- `man 1 df`、`man 1 du`、`man 1 lsof`：三者统计的对象不同，这正是它们会对不上的原因。
- Python `statistics.quantiles` 的 `method` 参数文档：`inclusive`/`exclusive` 两种插值的定义。
- Prometheus 官方文档的「Histograms and summaries」：直方图分桶近似分位数、以及为什么分位数不能聚合。
