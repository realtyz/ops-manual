# 证据的时间与格式基线

## 1. 排障的本质动作之一是对齐

排障时最常做的一件事是**比较先后**：把「指标拐点」「第一条错误日志」「一次发布」「一次运维操作」放到同一条时间轴上，看谁先动。这个比较只要有一条数据的时间戳不可信，结论就可能把「因」当成「果」。

时间基线要回答三个问题：

1. **这台机器的时间准不准**——有没有同步成功，同步给了谁；
2. **这份数据的时间是哪个时钟、哪个时区**——墙上时钟还是单调时钟，本地时间还是 UTC；
3. **跨机器之间能不能比**——两台机器的偏差有多大。

这三个问题的答案不在同一个地方。「时间准不准」看对时状态，「是哪个时钟」看工具输出用哪个字段，「能不能跨机比」则要同时看前两个。**把它们混成一个问题，就会得到「NTP 服务在跑，所以时间没问题」这种错误结论。**

## 2. 两种时钟

一台机器上至少有两种时间，它们的区别不是精度，而是**会不会被改**：

| 时钟 | 别称 | 会变吗 | 适合用来做什么 |
| --- | --- | --- | --- |
| 墙上时钟（realtime） | `CLOCK_REALTIME` | **会**：对时会做步进或微调，管理员也能改 | 跨机器对账、日志时间戳、证书有效期 |
| 单调时钟（monotonic） | `CLOCK_MONOTONIC` | **不会**：只随开机累加 | 测量耗时与间隔，判断「这事是不是这次开机之后发生的」 |

判断标准可以压成一句：**要跟别人比，用墙上时钟；要算时间差和先后，用单调时钟。**

这个分野在很多地方以「两个字段并排出现」的形式存在，认出来就不会用错：

| 来源 | 墙上时钟字段 | 单调字段 | 单位 |
| --- | --- | --- | --- |
| journald 记录 | `__REALTIME_TIMESTAMP` | `__MONOTONIC_TIMESTAMP` | 微秒 |
| journald 源侧时间 | `_SOURCE_REALTIME_TIMESTAMP` | —— | 微秒 |
| systemd 单元状态 | `ActiveEnterTimestamp` | `ActiveEnterTimestampMonotonic` | 后者是微秒 |
| 内核 | `date`/`/proc/stat` 的 `btime` | `/proc/uptime` 的第一个数 | 秒（可带小数） |

**journald 同时记两份，这是它比纯文本日志强的一个具体原因**：即使中途发生过一次对时步进，同一 boot 内的排序仍然可靠，因为排序可以走单调字段。反过来，如果发现同一 boot 内的日志「后发生的事时间戳更早」，第一个要怀疑的就是对时调整，而不是磁盘坏了。

### 2.1 单调字段的用法：它给的是「开机后多久」

单调字段是**自开机起**的计数，因此它单独出现时信息不完整——要减去当前开机时长才知道「那是多久以前」。这一点最常见的误用是判断「服务是不是刚重启」：

```text
ActiveEnterTimestamp=Sat 2026-09-19 07:08:34 UTC
ActiveEnterTimestampMonotonic=4230531
```

`07:08:34` 看起来像「今天早上」，但它不告诉你「现在离它多远」；`4230531` 微秒（约 4.2 秒）说明这个单元是在**开机后约 4.2 秒**进入 active 的。再与当前开机时长（`/proc/uptime` 的第一个数）相减，才能得出「它已经跑了多久」。

**只看墙上时钟，会把「开机就起、一直没重启」和「刚刚才重启」混为一谈。** 反过来，当两个字段相减接近 0 时，才是「刚才重启过」。

## 3. 同一条时间，四种写法

时间戳格式不统一是常态，因为不同工具来自不同年代、面向不同用途：

| 场景 | 格式示例 | 带时区 | 带年份 | 注意 |
| --- | --- | --- | --- | --- |
| RFC 5424 syslog | `2026-09-19T08:08:01.379099+00:00` | 有 | 有 | 跨时区对账的前提 |
| 旧 BSD 格式（RFC 3164） | `Sep 19 08:06:16` | 无 | **无** | 跨年、跨时区基本没法自动对账 |
| journald 默认显示 | `Sep 19 08:06:16.318693` | 隐含本地时区 | 无 | 用 `-o short-iso` 可得到带时区偏移的写法 |
| `sadf -d` 导出的 CSV | `2026-09-19 08:00:12 UTC` | 有（UTC） | 有 | **恒定输出 UTC，不跟随机器时区** |

第三行与第四行的差别最容易被低估。**`sar -s/-e` 的窗口按进程当前时区解释，而 `sadf -d` 导出的时间戳恒定是 UTC。** 在 UTC 的机器上这两者数值相同，看不出问题；换到 +0800 的机器上，`sar -s 16:00:00` 选的是本地 16 点，而同一采样点在 `sadf -d` 里写成 `08:00 UTC`——把两份数据放进同一张图之前，先统一成 UTC 或统一成同一时区。

同理，按时间窗过滤时也要留意窗口参数用的是哪个时区：`journalctl --since "03:00"` 与 `sar -s 03:00:00` 都按进程当前时区解释。与之相对，`journalctl -b -1` 走的是「上一次开机」，与时钟无关，这一点比时间窗可靠。

## 4. 怎么判断「时间准不准」

对时状态是一个**逐层收窄**的判断，三层各有各的字段：

```mermaid
flowchart LR
  A["① 系统时钟是否已同步<br/>timedatectl / NTPSynchronized"] --> B["② 同步源与轮询状态<br/>timesync-status / chronyc sources"] --> C["③ 估计误差<br/>Root distance / syncAccuracy"]
```

| 层 | 看什么 | 判据 |
| --- | --- | --- |
| ① 是否同步 | `System clock synchronized`、`timedatectl show` 的 `NTPSynchronized` | `no` 就意味着证据随时可能错位 |
| ② 同步服务与来源 | `NTP service`、`timedatectl timesync-status` 的 `Server`/`Poll interval`/`Packet count` | 服务在跑 ≠ 同步成功 |
| ③ 误差量级 | `Root distance`，或 syslog 报文里的 `syncAccuracy` | 毫秒级可做毫秒对账；秒级只能做粗粒度对齐 |

这里有一个必须写清的陷阱：**`NTP service: active` 完全不能推出「时间已经同步」。** 服务处于 active 只说明进程在运行、可能已经选出了服务器，而「有没有收到应答」要看 `Packet count` 之类的字段。当 `Packet count: 0` 时，`Stratum`、`Reference`、`Root distance` 这些行根本不会出现——因为它们只有在同步成功之后才有意义。

发行版差异要现场取：Ubuntu 系默认 `systemd-timesyncd`，RHEL 系默认 `chrony`（命令与查询字段都不同，前者是 `timedatectl timesync-status`，后者是 `chronyc tracking`/`chronyc sources -v`）。

### 4.1 报文自己带着时间可信度

RFC 5424 的结构化数据里可以带 `timeQuality`：

```text
[timeQuality tzKnown="1" isSynced="0"]
```

- `tzKnown` 表示发送方知道自己的时区；
- `isSynced` 表示发送方认为自己的时钟是否已同步；
- `syncAccuracy` 给出精度估计，**只在同步成功时才出现**。

这给了接收端一个很实用的能力：**按 `isSynced` 给日志分流或打标，就能把「时间不可信的来源」筛出来。** 收到一条 `isSynced="0"` 的远程日志时，不要用它做时间线推断——它自己已经声明了不可信。

## 5. 时间错位会污染什么

| 被污染的东西 | 具体表现 | 机制 |
| --- | --- | --- |
| 跨机日志对账 | 「A 的报错比 B 早 3 秒」实际相反 | 两台机器各有自己的偏差，谁快谁慢无从判断 |
| 日志与指标对齐 | 指标拐点在日志里「找不到对应事件」 | 采集时间与业务打点时间用了不同时区或未同步 |
| 证书校验 | `certificate is not yet valid` 或提前报过期 | 证书有效期按墙上时钟判断 |
| 分布式追踪 | span 顺序倒置、父子关系算不出来、耗时出现负数 | 跨机 span 用各自的墙上时钟打点 |
| 审计与合规 | 留存与变更记录的时间线不成立 | 合规要求「可追溯」，时间不可信等于不可追溯 |
| 历史复盘 | 窗口挑错、两份数据差一个时区 | `sar` 按本地时区解释窗口，`sadf -d` 恒定写 UTC |

处置顺序由此确定：**如果 `System clock synchronized` 是 `no`，而你要处理的是一个时间敏感的故障（例如「两个服务谁先挂了」），先修时间，再用单调时间或 boot 内序号从已有数据里排序。** 在漂移的时钟上做时间线分析，等于用一把不准的尺子量长度。

反过来也有边界：如果只是在看「这台机器现在怎么样」，时钟不准不影响 `free`、`df`、`ss` 这类即时观测——它们没有跨机比较的语义。

## 6. 常见误解

| 常见说法 | 事实 |
| --- | --- |
| 「时间差不多就行」 | 差几秒在毫秒级排障里就是「因果颠倒」；先看同步状态字段，而不是服务状态 |
| 「NTP 服务在跑就一定准」 | 服务 active 只说明进程在运行；要看 `NTPSynchronized` 与应答计数 |
| 用墙上时钟算耗时 | 对时调整会让耗时变成负数或虚高；算间隔用单调时间 |
| 「这台机器一直没重启」只看墙上时钟 | 单调字段给的是「开机后多久」，要减去开机时长才是「已经运行多久」 |
| 拿 `sadf -d` 的 CSV 直接和本地日志比时间 | 导出恒定是 UTC，不跟随 `TZ`；在 UTC 机器上看不出来，换时区就整体错开 |
| 「`sar` 和 `sadf` 对同一采样点给出不同时间，是 bug」 | 不是 bug：窗口按本地时区解释、导出按 UTC 写，是两种口径 |
| 在未同步的机器上做跨机时间线分析 | 结论可能是反的；先修时间，或用单调时间与序号排序 |
| 把 `timeQuality` 的结构化数据当噪声丢掉 | `isSynced` 是接收端筛掉「时间不可信来源」的现成判据 |

## 要点自测

**问：墙上时钟和单调时钟分别该在什么时候用？**
答：跨机对账、日志时间戳、证书有效期用墙上时钟；算耗时、算间隔、判断「这次开机之后发生了什么」用单调时钟。识别方式是看工具是否并排给出两个字段（journald 的 `__REALTIME_TIMESTAMP` 与 `__MONOTONIC_TIMESTAMP`、systemd 的 `ActiveEnterTimestamp` 与 `ActiveEnterTimestampMonotonic`）。

**问：`timedatectl` 显示 `NTP service: active`，能说明时间已经同步了吗？**
答：不能。active 只说明同步进程在跑。判据是 `System clock synchronized` / `NTPSynchronized`，以及 `timesync-status` 里的应答计数与 `Root distance`——同步成功之前，`Root distance` 这类字段根本不会出现。

**问：为什么 `sar -s 16:00:00` 和 `sadf -d` 里的 `08:00 UTC` 指的是同一个采样点？**
答：`sar` 的窗口参数按进程当前时区解释，`sadf -d` 导出的时间戳恒定是 UTC。机器在 +0800 时，本地 16 点就是 UTC 8 点。把两份数据放进同一张图之前必须先统一口径。

**问：怎么判断一个服务是「开机就起来一直没动」还是「刚刚重启过」？**
答：读 `ActiveEnterTimestampMonotonic`（开机后多久进入 active），再与 `/proc/uptime` 的第一个数相减。只看墙上时钟无法区分这两种情况。

**问：如果不部署追踪，时间精度还需要那么高吗？**
答：需要。跨机 span 的父子顺序与耗时都建立在各机器的墙上时钟上，时钟漂移会让顺序错乱、耗时出现负数。时间基线是四条链路共同的底座，不是某一条的附属要求。

**第一反应不要做什么**：不要在时钟未同步时写下「A 比 B 早发生」；不要用墙上时钟算耗时；不要把 `sadf -d` 的 UTC 时间戳与本地日志时间直接比较；不要因为同步服务是 active 就跳过同步状态字段。
