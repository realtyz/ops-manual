## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **观测分四类，各有各的工具箱：日志、容量、指标、历史。**
>   - 怎么验证：四类各写出一条你自己最常用的命令（`journalctl` / `df` / `curl /metrics` / `sar`），写不出就说明有一类没练过。
> - **「现在」和「过去」是两套工具，事故后再打开 `top` 看不到过去。**
>   - 怎么验证：`ls /var/log/sysstat/`——本机实测有 `sa19`（23096 字节，当天数据，每 10 分钟一个采样点），`sysstat-collect.timer` 是 `enabled`，所以「昨天 15:20 忙不忙」在本机真的答得出来。
> - **命令输出必须带单位与时间窗。**
>   - 证据：本机实测 `vmstat 1 2` 的第一行数据是**自开机以来的平均值**（`cs=1`），第二行才是当前一秒的值（`cs=211`）；`df -B1` 比 `df -h` 更适合做计算。
> - **`df` 和 `du` 从不同角度回答问题，对不上通常意味着「有已删除但仍被打开的文件」。**
>   - 证据：本机在一个临时 loop 文件系统上实测——`rm` 掉一个仍被持有的 10MiB 文件后，`df` 已用从 `24576` 涨到 `10510336` 字节，而 `du -sh` 只看到 20K。
> - **只读命令可以直接在生产机上用，但要记录下你跑了什么。**
>   - 怎么验证：处置记录里能不能看到「时间 + 命令 + 关键输出」三样；只写结论的记录，事后无法复现。

## 2. 日志类：日志在不在、写到哪

```bash
logger -t labtest "hello-from-logger"                              # 验证：造一条可识别的日志
journalctl -t labtest -n 1 -o short-precise                        # 验证：journald 里有没有
journalctl -t labtest -n 1 -o json | python3 -m json.tool | head -20   # 验证：结构化字段长什么样
tail -2 /var/log/syslog                                            # 验证：rsyslog 侧是否也落了盘
systemctl show <unit> -p StandardOutput -p StandardError           # 验证：某个服务的输出去哪了
journalctl -u <unit> -b --since "10 min ago" --no-pager            # 验证：单元、boot、时间窗是否选对
journalctl --disk-usage                                            # 验证：journal 总共占了多少
```

本机实测（`logger` 造的消息同时进了两个地方）：

```text
$ journalctl -t labtest -n 1 -o short-precise
Sep 19 08:06:27.428985 linux-lab labtest[15907]: hello-from-logger
$ journalctl -t labtest -n 1 -o json | python3 -c "import json,sys; d=json.load(sys.stdin); print({k:d[k] for k in ['SYSLOG_IDENTIFIER','_PID','_UID','_TRANSPORT','MESSAGE']})"
{'SYSLOG_IDENTIFIER': 'labtest', '_PID': '15907', '_UID': '0', '_TRANSPORT': 'syslog', 'MESSAGE': 'hello-from-logger'}
$ tail -1 /var/log/syslog
2026-09-19T08:06:27.429240+00:00 linux-lab labtest: hello-from-logger
$ journalctl --disk-usage
Archived and active journals take up 20.7M in the file system.
```

三个关键点，后面 05、08 会展开：

1. **同一个标识符过滤出的消息可能来自不同通道**（`_TRANSPORT` 字段就是答案）。本机实测 `logger -t labcmp` 的消息是 `_TRANSPORT=syslog`，而 `systemd-cat -t labcmp` 是 `_TRANSPORT=stdout`——同样是 `SYSLOG_IDENTIFIER=labcmp`，来源却不同。
2. **journald 有字段、rsyslog 落盘是纯文本**，两者用途不同。
3. **`journalctl --disk-usage` 是 journal 的容量入口**，但它只覆盖 journal，不覆盖 `/var/log/*.log`。本机写作期间实测在 `20.7M → 16.0M` 之间（做过一次 `--vacuum-size=15M`，见子笔记 08），量级在几十 MiB。

## 3. 容量类：谁占了空间

```bash
df -hT                                        # 验证：哪个文件系统满了、类型是什么
df -i /var                                   # 验证：是空间用尽还是 inode 用尽
du -xsh /var/log/* 2>/dev/null | sort -h | tail -10   # 验证：目录树里谁最大（-x 不跨文件系统）
find /var/log -xdev -type f -size +100M -printf "%s %p\n" | sort -n | tail   # 验证：大文件清单
lsof +L1 2>/dev/null | head                   # 验证：有没有「已删除但仍被打开」的文件
ls -l /proc/<pid>/fd | grep deleted           # 验证：某个进程持有的已删除文件
```

本机实测的「删了不释放」现场（在一个 64MiB 的临时 loop 文件系统里做，完整过程见子笔记 08）：

```text
$ df -B1 /tmp/09a-fill/mnt | tail -1 | awk "{print \$3}"
24576
$ ls -l /proc/$$/fd/4 | sed "s/.*-> /fd4 -> /"
fd4 -> /tmp/09a-fill/mnt/held.bin (deleted)
$ df -B1 /tmp/09a-fill/mnt | tail -1 | awk "{print \$3}"
10510336                   # 已用多了 10485760 字节 = 10 MiB
$ du -sh /tmp/09a-fill/mnt | cut -f1
20K                        # du 看不到已删除文件
$ exec 4>&-; df -B1 /tmp/09a-fill/mnt | tail -1 | awk "{print \$3}"
24576                      # 关闭 fd 后立刻回收
```

**`df` 变大而 `du` 找不到，就是这一类问题的判据。** 在根分区上做这件事的风险是「被别人误当成磁盘真的满了」，所以练习时优先用临时 loop 文件系统——判据完全一样，且不影响整机。

## 4. 指标类：现在忙不忙

```bash
curl -s -o /dev/null -w "%{http_code} %{content_type}\n" http://127.0.0.1:9100/metrics   # 验证：端点是否可达
curl -s http://127.0.0.1:9100/metrics | grep -vc "^#"                                    # 验证：指标行数（成本感受）
ss -s                                                     # 验证：套接字总量与 TCP 状态分布
vmstat 1 2 | tail -1                                      # 验证：r/b（排队）、si/so（换页）、us/sy/wa/id
grep -H . /proc/pressure/cpu /proc/pressure/memory /proc/pressure/io   # 验证：资源压力（some/full）

```


> [!warning] `vmstat` 的第一行不是当前值
> 带间隔参数的 `vmstat 1 2` 输出的**第一行数据是自开机以来的平均值**，第二行才是当前这一秒的值。本机实测的对比很直观：平均值那一行 `cs=1`（开机 57 分钟摊下来的上下文切换率），当前一秒那一行 `cs=211`——**差了 200 倍**。要判断「现在忙不忙」，必须看第二行起（或直接 `vmstat 1 2 | tail -1`）。同理，`top`/`uptime` 的 load 也是 1/5/15 分钟的平均——**「平均」和「此刻」是两回事**，这条纪律在子笔记 13 会展开。

三个字段要会读：

| 字段 | 含义 | 常见误读 |
| --- | --- | --- |
| `r` / `b` | 可运行队列长度 / 不可中断睡眠（D 状态）进程数 | 只看 `r` 会漏掉 IO 阻塞；`b` 高说明在等 IO |
| `si` / `so` | 换入/换出内存（KiB/s） | 长期非 0 说明内存已经不够用 |
| `us/sy/wa/id` | 用户态/内核态/IO 等待/空闲的 CPU 时间占比 | `id` 高不代表没问题（可能卡在 IO 或锁上） |

## 5. 历史类：昨天 15:20 发生了什么

```bash
ls /var/log/sysstat/                       # 验证：历史数据到底有没有在采
sar -u -s 07:50:00 -e 08:10:00             # 验证：指定窗口的 CPU
sar -r -s 07:50:00 -e 08:10:00             # 验证：内存
sar -b                                     # 验证：IO 总体
sar -n DEV                                 # 验证：网卡
sar -q                                     # 验证：负载与队列
sadf -d /var/log/sysstat/sa<DD> -- -u | head    # 验证：导出 CSV 做对比
```

本机实测（`sysstat 12.6.1`，`sysstat-collect.timer` 每 10 分钟采一次，`/etc/sysstat/sysstat` 里 `HISTORY=7`、`COMPRESSAFTER=10`、`SA_DIR=/var/log/sysstat`）：

**这一步的失败模式和别处不同**：不是命令写错，而是**数据根本没采**。所以历史类观测的第一步永远是「确认有数据」，再谈分析（子笔记 15）。本机有数据，所以「怎么用」才是重点：

- `sar` 的默认输入是**当天的** `sa<DD>`（今天是 19 号 → `sa19`）；`sar -f /var/log/sysstat/sa18` 才能看昨天。
- `sar` 的历史文件里会夹着 `LINUX RESTART` 标记行，那是**每次重启**的记录，不是采样点——本机的 `sa19` 里就有 `06:05:24` 与 `06:19:42` 两条，说明这台机器今天被重启过多次，而 `journalctl --list-boots` 只剩当前一次开机（journal 的旧 boot 已被轮转回收，见子笔记 08）。
- 采样间隔可以从 `sadf -d` 输出的第二列读出来（本机是 `600` 秒 = 10 分钟；最后一条是 `596` 秒，说明那次采样比计划早了 4 秒）。

> [!tip] 单次瞬时观测与历史观测的三个命令
> 想「现在多忙」：`iostat`（不跟参数时给的是**自开机以来的平均值**，看设备吞吐够用）、`mpstat 1 1`（每 CPU 的瞬时占比）、`pidstat 1 1`（按进程看谁在吃 CPU）。本机实测这三条都可用：
>
> ```text
> $ mpstat 1 1 | tail -2
> 08:06:26 AM  all    3.51    0.00    3.01    0.00    0.00    0.25    0.00    0.00    0.00   93.23
> Average:     all    3.51    0.00    3.01    0.00    0.00    0.25    0.00    0.00    0.00   93.23
> $ pidstat 1 1 | head -5
> 08:06:26 AM   UID       PID    %usr %system  %guest   %wait    %CPU   CPU  Command
> 08:06:27 AM     0         1   24.75   10.89    0.00    0.99   35.64     2  systemd
> 08:06:27 AM     0        10    0.00    0.99    0.00    0.00    0.99     1  kworker/u256:0-ext4-rsv-conversion
> ```
>
> `mpstat` 与 `pidstat` 都支持「`间隔 次数`」形式，**给了参数才是当前值**；不带参数时它们和 `iostat` 一样会给自开机以来的平均。

## 6. 告警链路类：规则算出来没有、被压掉没有

```bash
curl -s "http://<prom>:9090/api/v1/query?query=up"                     # 验证：抓取是否成功
curl -s "http://<prom>:9090/api/v1/query?query=ALERTS"                 # 验证：规则是否真的进入 firing
curl -s "http://<prom>:9090/api/v1/rules" | python3 -m json.tool | head # 验证：规则名、状态、上次评估时间
amtool alert query --alertmanager.url=http://<am>:9093                 # 验证：Alertmanager 侧当前告警
amtool silence query --alertmanager.url=http://<am>:9093               # 验证：有哪些静默还挂着
```

这条链路是**逐段验证**的典型：目标 → 抓取 → 规则 → 路由 → 静默/抑制 → 通知。**在哪一段停下来，就去查那一段**，不要一上来就怀疑通知渠道（子笔记 10、11）。

## 7. 读输出的四条纪律

1. **记下命令与时间**：`script` 或 `tee` 一份记录，或至少把「几点跑、跑了什么、关键输出」写进处置记录。**没有命令记录的处置，事后无法复现。**
2. **带单位与口径**：`df -B1` 看字节、`df -h` 看人类可读；`MiB` 与 `MB` 不要混用；分位数要写清窗口与算法。
3. **分清「平均」与「此刻」**：`vmstat` 首行、`top` 的 load、`iostat` 的 `Average` 都是平均值；要看瞬时值就用固定次数采样后取最后一行。
4. **分清「聚合」与「单实例」**：一台机器的 `%util` 与整个集群的 p99 不是一回事；**跨实例的 p99 不能靠平均单实例 p99 得到**（子笔记 13）。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 「先 `tail -f` 看看」 | 只看实时输出的最后几行，容易错过故障开始时的第一条错误；用 `--since`/`journalctl -u` 定位时间窗 |
| 用 `du` 判断文件系统满没满 | `du` 看不到已删除但仍被打开的文件；两者要一起看（本机在临时 loop 文件系统上实测差 10 MiB） |
| 把 `vmstat` 第一行当当前值 | 那是自开机以来的平均值（本机实测 `cs=1`），当前一秒是 `cs=211`；用 `vmstat 1 2` 取最后一行 |
| 直接 `cat /proc/pressure/*` 看 `avg10` 就下结论 | 还要看累计 `total`（短脉冲会被平均值稀释）与 `full`（全面停顿） |
| 事故发生后才打开 `top` | 即时工具看不到过去；历史复盘要靠提前采集的 sysstat/时序库。**本机 `sysstat-collect.timer` 是 enabled，数据就在 `/var/log/sysstat/sa<DD>` 里** |
| 以为「用 `sar` 得先想办法装 sysstat」 | 本机 `sysstat` 已正常安装并开机自启，直接用；`apt-get download` + `dpkg-deb -x` 只在**非 root、装不了包**的环境才需要 |
| 「命令跑过了，结论记住了」 | 没记下命令与时间，复盘与交接都无法复现；观测即证据，证据要留痕 |

## 决策练习

**场景**：应用团队说「昨天 15:20 左右我们的服务变慢」。你现在只有一台运行中的机器，没有被监控系统，但这台机器装了 sysstat（本机就是这样）。

**A. 立刻 `top` 看现在的负载，判断这台机器忙不忙**
**B. 先 `ls /var/log/sysstat/` 确认有没有昨天 15:00–16:00 的历史数据，有就用 `sar` 看窗口**
**C. 先翻应用日志，找 15:20 附近的慢请求**

**为什么选 B**：问题的关键词是「昨天」和「变慢」，这是**历史指标**的问题。先确认数据是否存在（本机的答案是「有」：`sa<DD>` 按天存、`HISTORY=7` 保留 7 天），再用 `sar -u -s 15:00:00 -e 16:00:00` 拿 CPU/内存/IO/网络四条线，成本最低且能直接给出「当时机器忙不忙」的结论。注意 `sar -s/-e` 按本地时区解释窗口，而 `sadf -d` 导出的是 UTC，两者混用会在非 UTC 机器上错开一个时区（子笔记 02）。

**为什么不选 A**：现在打开 `top` 看到的是「此刻」，与昨天 15:20 无关。这是最典型的工具用错场景。

**为什么不选 C**：日志能给细节（哪个接口慢、有没有报错），但回答不了「机器当时整体什么状态」；正确顺序是先 B 得到轮廓，再用 C 补细节，最后和变更记录对齐。

## 要点自测

> [!question]- 「磁盘被日志写满」应该按什么顺序用命令？
> - **第一步 `df -hT` / `df -i`**：先分清是空间满还是 inode 满，以及是哪个文件系统。
> - **第二步 `du -xsh /var/log/* | sort -h | tail`**：找真占空间的大文件。
> - **第三步 `lsof +L1` 或遍历 `/proc/*/fd`**：找「已删除但仍被打开」的文件（本机在临时 loop 文件系统上实测：这类文件能让 `df` 多出 10 MiB，而 `du` 只看到 20K）。
> - **最后才动手**：删之前确认不是业务数据、保留最近一段用于复盘。
> - **第一反应不要是什么**：不要直接 `rm -rf /var/log/*`。

> [!question]- 为什么「事故之后再打开 `top`」通常没有用？
> - **因为即时工具只反映此刻**：`top`、`free`、`ss` 都是采样当前状态，看不到历史时间窗。
> - **解法**：提前采集历史数据（sysstat 的 `sadc` 周期采样、或时序库），需要时按窗口回看。
> - **例外**：如果故障仍在持续，即时工具依然有效——但要记住你看到的是「持续中的故障」，不是「当时那一刻」。
> - **第一反应不要是什么**：不要用现在的数据去解释昨天的现象。

> [!question]- `df` 和 `du` 为什么会对不上？
> - **回答的问题不同**：`df` 看文件系统层面的已用块；`du` 看目录树里**可见文件名**的大小。
> - **对不上就意味着有「不可见但仍占空间」的东西**：已删除但被进程持有（本机实测案例）、挂载点覆盖了目录、文件系统保留块。
> - **处置**：`lsof +L1` 找到持有者，让进程重开文件或重启服务，`rm` 不解决问题。
> - **第一反应不要是什么**：不要因为 `du` 找不到大文件就断定「`df` 报错了」。
