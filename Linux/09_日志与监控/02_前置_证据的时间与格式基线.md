## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **一台机器上至少有两种时间：会被 NTP 调整的墙上时钟，和只随开机累加的单调时钟。**
>   - 怎么验证：`date -Is` 给出 `2026-09-19T08:06:16+00:00`（墙上时钟，可被对时改动），`cat /proc/uptime` 给出 `3466.48` 秒（单调时间，只增不减）。
> - **journald 同时记两份时间。**
>   - 证据：实测同一条记录里既有 `__REALTIME_TIMESTAMP=1789805176318725` 也有 `__MONOTONIC_TIMESTAMP=3466326305`（单位都是微秒），所以对时把时间线拽回去也不影响排序。
> - **判断「服务是不是刚重启」要靠单调时间，不能只看墙上时钟。**
>   - 证据：实测 `systemd-journald` 的 `ActiveEnterTimestamp=Sat 2026-09-19 07:08:34 UTC`，而 `ActiveEnterTimestampMonotonic=4230531` 微秒（≈4.2 秒）说明它是**开机后 4.2 秒**进入 active 的；和当前开机时长 `3466.48` 秒一比，服务已跑了约 **3462 秒**，不是「刚重启」。只看墙上时钟会把「开机时就起来、一直没动」误判成别的结论。
> - **时间戳格式不统一是常态，比对前先统一口径。**
>   - 证据：RFC 5424 的 syslog 带时区偏移（实测 `2026-09-19T08:08:01.379099+00:00`），旧的 BSD 格式连年份都没有，而 `sadf -d` **永远导出 UTC**——本机时区恰好就是 UTC，所以两者看起来一致；一旦机器在 +0800，同一采样点就会写成 `16:xx` 与 `08:xx UTC` 两个值（用 `TZ=Asia/Shanghai` 现场可比出来）。
> - **时钟不同步时，任何「对齐时间线」的结论都不成立。**
>   - 怎么验证：本机 `timedatectl` 的 `System clock synchronized` 是 **`no`**、`timedatectl show` 的 `NTPSynchronized=no`、`timedatectl timesync-status` 的 `Packet count: 0`——NTP 服务在跑，但一次都没同步成功。**这时不要写「A 比 B 早几秒」。**

## 1. 为什么时间基线是可观测性的地基

排障的本质动作之一是**对齐**：把「指标拐点」「第一条错误日志」「一次发布」「一次运维操作」放在同一条时间轴上比较先后。只要其中有任何一条数据的时间戳不可信，这个比较就失效——你可能会把「因」当成「果」。

时间基线要回答三个问题：

1. **这台机器的时间准不准**（有没有同步、同步给了谁）。
2. **这份数据的时间是哪个时钟、哪个时区**（墙上时钟还是单调时钟，本地时间还是 UTC）。
3. **跨机器之间能不能比**（不同机器的时间偏差有多大）。

```mermaid
flowchart LR
  A["① 这台机器现在几点<br/>timedatectl"] --> B["② 同步来源与偏差<br/>timesync-status / chronyc"] --> C["③ 数据的时间戳格式<br/>RFC5424 · sadf -d · journal JSON"] --> D["④ 跨机可比性<br/>同一时区、同一同步源"]
```

## 2. 墙上时钟与单调时钟

### 2.1 两种时钟的区别

| 时钟 | 别称 | 会变吗 | 典型用途 |
| --- | --- | --- | --- |
| 墙上时钟（realtime） | `CLOCK_REALTIME` | **会**：NTP 会对它做步进或微调，管理员也能改 | 跨机器对账、日志时间戳、证书有效期 |
| 单调时钟（monotonic） | `CLOCK_MONOTONIC` | **不会**：只随开机累加 | 测量「耗时」「间隔」，以及判断「这事是不是这次开机后发生的」 |

用哪个的判断标准很简单：**要跟别人比，用墙上时钟；要算时间差和先后，用单调时钟。**

### 2.2 journald 同时记两份

本机实测（`journalctl -n 1 -o json`，只挑时间字段）：

```text
$ journalctl -n 1 -o json | python3 -c "import json,sys; d=json.load(sys.stdin); print({k:d[k] for k in d if 'TIME' in k or 'MONOTONIC' in k})"
{'__MONOTONIC_TIMESTAMP': '3466326305', '_SOURCE_REALTIME_TIMESTAMP': '1789805176318693', '_RUNTIME_SCOPE': 'system', '__REALTIME_TIMESTAMP': '1789805176318725'}
```

三个值都是**微秒**：

- `__REALTIME_TIMESTAMP` 是墙上时钟（自 Unix epoch 起，`1789805176318725` µs ≈ `2026-09-19 08:06:16 UTC`），跨机器可比。
- `__MONOTONIC_TIMESTAMP` 是自开机起的单调时间（`3466326305` µs ≈ `3466` 秒，和 `/proc/uptime` 的 `3466.48` 秒对得上），**用来排序和算间隔最可靠**——即使中间做过一次 NTP 步进，这个字段也不会跳。
- `_SOURCE_REALTIME_TIMESTAMP` 是消息在**源头**打的时间戳（比 receiver 侧的接收时间更接近事实）。

排障时如果发现同一个 boot 内的日志时间顺序看起来「怪」（例如后发生的事时间戳更早），先想想是不是发生过对时调整，再用单调时间对照。

### 2.3 systemd 的两种时间戳

同样的思路在 systemd 里也有一份：

```bash
systemctl show -p ActiveEnterTimestamp -p ActiveEnterTimestampMonotonic systemd-journald
```

```text
ActiveEnterTimestamp=Sat 2026-09-19 07:08:34 UTC
ActiveEnterTimestampMonotonic=4230531
```

`ActiveEnterTimestamp=07:08:34` 看起来像「今天早上」，但它没有告诉你任何关于「现在离它多远」的信息；`ActiveEnterTimestampMonotonic=4230531` 微秒（≈4.2 秒）说明它是在**开机后约 4.2 秒**进入 active 的。还要再减去当前开机时长（本机 `/proc/uptime` 第一个数 `3466.48` 秒）才能得出「这个服务已经跑了约 3462 秒」——**只看墙上时钟，你会把「开机就起、一直没重启」和「刚刚才重启」混为一谈。** 反过来，当两者相减接近 0 时，才是「刚才重启过」。

其他两条常用的单调时间来源：

```bash
cat /proc/uptime            # 第一个数是开机秒数（含小数），第二个是空闲秒数
uptime -p                   # 人类可读的开机时长
```

## 3. 时间戳格式：同一条时间，四种写法

| 场景 | 格式示例 | 有没有时区 | 有没有年份 | 注意 |
| --- | --- | --- | --- | --- |
| RFC 5424 syslog | `2026-09-19T08:08:01.379099+00:00` | **有**（`+00:00`） | 有 | 跨时区对账的前提；本文子笔记 07 会看到真实报文 |
| 旧 BSD 格式（RFC 3164） | `Sep 19 08:06:16` | 无 | **无** | 跨年、跨时区的数据基本没法自动对账 |
| journald 默认显示 | `Sep 19 08:06:16.318693` | 隐含本地时区 | 无 | 用 `-o short-iso` 可得到带时区的 `2026-09-19T08:06:16+00:00` |
| `sadf -d` 导出的 CSV | `2026-09-19 08:00:12 UTC` | 有（UTC） | 有 | **`sadf -d` 恒定输出 UTC，不跟随机器的本地时区**；本机时区恰好是 UTC 所以两者看着一样，机器在 +0800 时会写成两个值 |

本机实测的这对差异（同一时刻、两个时区口径）：

```text
$ date -Is
2026-09-19T08:08:53+00:00
$ TZ=Asia/Shanghai date -Is
2026-09-19T16:08:53+08:00
$ sadf -d /var/log/sysstat/sa19 -- -u | tail -1
linux-lab;596;2026-09-19 08:00:12 UTC;-1;0.17;0.00;0.10;0.00;0.00;99.72
$ TZ=Asia/Shanghai sadf -d /var/log/sysstat/sa19 -- -u | tail -1
linux-lab;596;2026-09-19 08:00:12 UTC;-1;0.17;0.00;0.10;0.00;0.00;99.72
```

（上面两行 `sadf -d` 输出完全一致，这就是证据：**`sadf -d` 不理会 `TZ`**，永远写 UTC。第二行 `TZ=Asia/Shanghai` 只改当前进程的时区，不改系统配置，可以安全地在生产机上做。）

**同一个采样点，`sar -s/-e` 里的 `08:00` 与 `sadf -d` 里的 `08:00 UTC` 只有在 UTC 机器上才等价。** 换到 +0800 的机器上，`sar -s 16:00:00` 找的是本地 16 点、`sadf -d` 写的是 `08:00 UTC`——把两份数据放进同一张图之前，先统一成 UTC 或统一成同一时区。

时间窗参数也有隐含语义：

- `journalctl --since "03:00"` / `sar -s 03:00:00 -e 04:00:00` 按**进程当前时区**解释（`journalctl` 与 `sar` 都跟随 `TZ`）。实测 `TZ=Asia/Shanghai sar -u -s 15:50:00 -e 16:10:00` 打印的是 `03:50:16 PM` 那一行，证明它按本地时间挑窗口。
- `journalctl -b -1` 用的是「上一次开机」，与时钟无关，这一点比时间窗可靠。

## 4. 怎么核查一台机器的时间

### 4.1 第一眼：`timedatectl`

```bash
timedatectl
```

```text
               Local time: Sat 2026-09-19 08:06:16 UTC
           Universal time: Sat 2026-09-19 08:06:16 UTC
                 RTC time: Sat 2026-09-19 08:06:16
                Time zone: Etc/UTC (UTC, +0000)
System clock synchronized: no
              NTP service: active
          RTC in local TZ: no
```

三个要看的点：

1. **`Time zone`**：决定本地时间怎么显示，也决定 `--since` 怎么解释。本机是 `Etc/UTC (UTC, +0000)`，所以 `Local time` 与 `Universal time` 完全相同。
2. **`System clock synchronized`**：`no` 就意味着证据随时可能错位。**本机现在是 `no`**，虽然 `NTP service: active`——服务在跑不等于同步成功。
3. **`NTP service`**：同步服务是否在跑。Ubuntu 默认 `systemd-timesyncd`（本机就是它，active + enabled），RHEL 系默认 `chrony`（本机**未安装**：`command -v chronyc` 无输出、`chrony.service` 不存在，对应命令 `chronyc tracking` / `chronyc sources -v` **未实测**）。

与配置的对应关系（只读）：

```bash
cat /etc/timezone                                  # 验证：纯文本时区名
ls -l /etc/localtime                                # 验证：指向哪个 zoneinfo 文件
timedatectl show -p Timezone -p LocalRTC -p NTP -p NTPSynchronized   # 验证：机器可读的形式
```

本机实测：

```text
$ cat /etc/timezone
Etc/UTC
$ ls -l /etc/localtime
lrwxrwxrwx 1 root root 27 Sep  9 06:37 /etc/localtime -> /usr/share/zoneinfo/Etc/UTC
$ timedatectl show -p Timezone -p LocalRTC -p NTP -p NTPSynchronized
Timezone=Etc/UTC
LocalRTC=no
NTP=yes
NTPSynchronized=no
```

### 4.2 第二眼：同步来源与偏差

```bash
timedatectl timesync-status
```

```text
       Server: fdfe:dcba:9876::d (ntp.ubuntu.com)
Poll interval: 34min 8s (min: 32s; max 34min 8s)
 Packet count: 0
```

**这就是「服务在跑但没同步上」的样子**：`systemd-timesyncd` 选出了服务器、给出了轮询区间，但 `Packet count: 0` 说明一次应答都没收到，因此也**没有** `Stratum`、`Reference`、`Root distance` 这些只有在同步成功后才出现的行。对照 `systemctl status systemd-timesyncd`：服务是 `active (running)`、`Status: "Idle."`——所以只看 `is-active` 会得出完全错误的结论。

`Root distance` 是「这台机器与参考时钟之间估计的误差」，可以理解成**这台机器时间的可信区间**：如果它是几毫秒，跨机对账到毫秒级没问题；如果是几秒，就只适合做粗粒度对齐。判据链条是：`System clock synchronized` → `NTPSynchronized` → `Root distance`；本机停在第 1 步就是 `no`，所以后面两步无从谈起。

> [!warning] 本机的现场结论
> `System clock synchronized: no` + `Packet count: 0` 意味着**本机的墙上时钟在本次实测期间没有被 NTP 校正过**。做时间线对齐（「A 比 B 早 3 秒」）时，本机数据只能当相对时间用，跨机结论必须存疑；而依赖单调时间的结论（耗时、间隔、boot 内排序）不受影响。

## 5. 时间错位会污染什么

| 会污染的东西 | 具体表现 | 为什么会这样 |
| --- | --- | --- |
| 跨机日志对账 | 「A 的报错比 B 早 3 秒」其实相反 | 两台机器各有自己的偏差，谁快谁慢无从判断 |
| 日志与指标对齐 | 指标拐点在日志里「找不到对应事件」 | 服务器采集时间与业务打点时间用了不同时区或不同步 |
| 证书校验 | `certificate is not yet valid` / 提前过期告警 | 证书有效期是按墙上时钟判断的 |
| 分布式追踪 | span 顺序看起来倒置，父子关系算不出来 | 跨机用各自的墙上时钟给 span 打点 |
| 审计与合规 | 日志留存、变更记录的时间线不成立 | 合规要求「可追溯」，时间不可信就等于不可追溯 |
| 历史复盘 | `sar -s/-e` 按本地时区挑窗口，`sadf -d` 却恒定写 UTC | 两种口径混用会把窗口错开一个时区；本机是 UTC 所以看不出来，换到 +0800 的机器立刻暴露 |

> [!warning] 时钟不同步时，先修时间再排障
> 如果 `timedatectl` 显示未同步，而你正在处理一个时间敏感的故障（例如「两个服务谁先挂了」），**先把时间同步修好，再从已有数据里对齐**。在漂移的时钟上做时间线分析，等于用一个不准的尺子量长度。
> 反过来，如果只是在看「这台机器现在怎么样」，时钟不准不影响 `free`、`df`、`ss` 这类即时观测。

开机时长 3466.48 秒

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 「时间差不多就行」 | 差几秒在毫秒级排障里就是「因果颠倒」；先看 `System clock synchronized` 与 `NTPSynchronized` |
| 拿 `sadf -d` 的 CSV 直接和本地日志比时间 | `sadf -d` 恒定写 UTC，**不跟随 `TZ`**；机器在 UTC 时看不出来，换到 +0800 就会整体差一个时区（可用 `TZ=Asia/Shanghai date -Is` 现场对照） |
| 「`sar -s 16:00` 和 `sadf -d` 的 `08:00` 不是一回事」当成 bug | 不是 bug：`sar` 的窗口按本地时区解释、`sadf -d` 按 UTC 导出，是两种口径 |
| 用墙上时钟算耗时 | NTP 调整会让耗时变成负数或虚高；算间隔用单调时间或 `__MONOTONIC_TIMESTAMP` |
| 「这台机器一直没重启 / 刚才重启过」只看墙上时钟 | `ActiveEnterTimestampMonotonic=4230531` 微秒说明本机 `systemd-journald` 是开机后 4.2 秒起来的；要减去 `/proc/uptime` 才能得出「已跑 3462 秒」 |
| 「NTP 服务在跑就一定准」 | 本机就是反例：`NTP service: active`、`systemd-timesyncd` running，但 `System clock synchronized: no`、`Packet count: 0` |
| 在未同步的机器上做跨机时间线分析 | 结论可能是反的；先修时间，或用单调时间/序号排序 |

## 决策练习

**场景**：你在复盘一次「服务 A 在 03:10 报超时、服务 B 在 03:10 报内存分配失败」。A 和 B 是两台机器，`sar` 的历史数据导出了 CSV，日志用的是本地时间；两台机器的 `timedatectl` 都显示 `NTP service: active`。

**A. 直接把 CSV 的 03:10 与日志的 03:10 当成同一时刻对齐**
**B. 先确认两台机器的 `System clock synchronized`，把 CSV 的 UTC 时间戳统一换算成同一口径，再对齐**
**C. 因为时间可能不准，干脆放弃时间线，只看两台机器各自的日志内容**

**为什么选 B**：`sadf -d` 的 CSV 恒定是 UTC，而日志是本地时间——这是**确定性的口径差**，必须先统一。更关键的是「`NTP service: active` 不等于已同步」：本机实测就是这个状态（`active` 但 `System clock synchronized: no`、`Packet count: 0`），所以「服务在跑」这句话提供不了任何保证，必须去看同步状态字段。

**为什么不选 A**：口径没统一就是错的。机器不在 UTC 时，`sadf -d` 的 UTC 时间戳会比本地日志小一个时区偏移，你会把「上午的故障」和「下午的事件」拼到一起。

**为什么不选 C**：放弃时间线等于放弃「先后关系」这个最重要的信息。多数故障的根因判断都依赖「谁先动」；正确做法是修正时间口径（必要时用单调时间或 boot 内序号排序），而不是丢掉这条信息。

## 要点自测

> [!question]- 墙上时钟和单调时钟分别该在什么时候用？
> - **墙上时钟**：跨机器对账、日志时间戳、证书有效期、用户看到的「几点几分」。
> - **单调时钟**：算耗时、算间隔、判断「这次开机之后发生了什么」。
> - **实测**：journald 一条记录里同时有 `__REALTIME_TIMESTAMP` 和 `__MONOTONIC_TIMESTAMP`（单位微秒），后者不受对时调整影响。
> - **第一反应不要是什么**：不要用墙上时钟算耗时，也不要用单调时钟做跨机对账。

> [!question]- 为什么 `sar` 的时间窗和 `sadf -d` 导出的时间戳口径不一样？
> - **事实**：`sar -s/-e` 的窗口按**进程当前时区**解释（跟随 `TZ`），`sadf -d` 导出的 CSV 时间戳**恒定是 UTC**、不受 `TZ` 影响。本机实测 `TZ=Asia/Shanghai sadf -d …` 的输出与不加 `TZ` 时逐字节相同。
> - **本机为什么看着一致**：本机时区就是 `Etc/UTC`，两种口径数值相同；换到 +0800 的机器就会出现「窗口挑的是 16:00、导出写的是 08:00」。
> - **怎么办**：统一成 UTC 再比对，或在分析脚本里显式做时区换算，并把「用哪个时区」写进报告。
> - **第一反应不要是什么**：不要怀疑 `sar` 采错了数据——它只是用了另一种时间口径。

> [!question]- 时钟不同步会污染哪些判断？
> - **跨机对账**：先后顺序可能反转。
> - **日志与指标对齐**：拐点找不到对应事件。
> - **证书**：提前报「尚未生效」或「已过期」。
> - **追踪**：跨机 span 顺序错乱。
> - **第一反应不要是什么**：不要在未同步的机器上写下「A 比 B 早发生」这种结论。
