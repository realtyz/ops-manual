# 观测与处置顺序

## 1. 一个问题，一把工具

| 类别 | 你想知道什么 | 用什么 | 关键字段或文件 |
| --- | --- | --- | --- |
| 日志 | 这个服务的输出去哪了？ | 用 `systemctl show <unit> -p StandardOutput -p StandardError` | 读两个属性的值（`journal` / `file:` / `null`） |
| 日志 | 某个单元本次开机留下了哪些记录？ | 用 `journalctl -u <unit> -b --no-pager` | 读 `_SYSTEMD_UNIT` 与 `_BOOT_ID` |
| 日志 | 一条记录上带着哪些字段？ | 用 `journalctl -n 1 -o json` 或 `-o verbose` | 读 `SYSLOG_IDENTIFIER`、`_TRANSPORT`、`PRIORITY`、`__REALTIME_TIMESTAMP`、`__MONOTONIC_TIMESTAMP` |
| 日志 | journald 真正生效的配置是哪一份？ | 用 `systemd-analyze cat-config systemd/journald.conf` | 读 `Storage=`、`SystemMaxUse=`、`SystemKeepFree=`、`MaxRetentionSec=`、`RateLimit*`、`ForwardToSyslog=` 及每项上方的来源路径行 |
| 日志 | 日志有没有落盘、能回溯几次开机？ | 用 `ls -ld /var/log/journal` 与 `journalctl --list-boots` | 读目录是否存在；再读 boot 列表的行数与 `FIRST ENTRY` |
| 日志 | 落盘的文本日志长什么样、谁能读？ | 用 `stat -c "%A %a %U:%G %s %n" /var/log/syslog` | 读 Ubuntu 上的 `640 syslog:adm`（`adm` 组成员可读） |
| 日志 | 轮转有没有真的发生、切完之后谁还在写？ | 用 `logrotate -d <conf>`、`stat -c "%i %n" <文件>` 与 `ls -l /proc/<pid>/fd` | 读演练输出；再读 inode（文件系统对象的编号）与 fd（file descriptor，文件描述符）指向的文件名 |
| 容量 | 哪个文件系统满了、是空间还是 inode 到了上限？ | 用 `df -hT` 与 `df -i` | 读 `Size`/`Used`/`Avail`/`Use%`，以及 `IUsed`/`IFree`/`IUse%` |
| 容量 | 目录树里哪个子项最大？ | 用 `du -xsh /var/log/* 2>/dev/null \| sort -h \| tail -10` | 读每个子项的 MiB/GiB 值（`-x` 不跨文件系统） |
| 容量 | 有没有已删除但仍被打开的 inode？ | 用 `lsof +L1` 与 `ls -l /proc/<pid>/fd` | 读 `(deleted)` 标记与 `SIZE/OFF` |
| 容量 | journal 当前占用多少？ | 用 `journalctl --disk-usage` | 读一行容量值（量级几十 MiB，随系统活动变化） |
| 容量 | 根文件系统保留了多少块？ | 用 `tune2fs -l <设备>` 与 `dumpe2fs -h <设备>` | 读 `Reserved block count` 与 `Block count`、`Free blocks` |
| 指标 | 目标还抓得到吗？ | 用 `curl "/api/v1/query?query=up"` | 读 `up` 的 0/1，配 `instance`、`job` 定位对象 |
| 指标 | 机器此刻忙不忙？ | 用 `vmstat 1 2`（看第二行起） | 读 `r`、`b`、`si`、`so`、`us`、`sy`、`wa`、`id` |
| 指标 | 资源压力与全面停顿有多大？ | 用 `/proc/pressure/{cpu,memory,io}` | 每类两行：读 `some` 与 `full`，各带 `avg10`/`avg60`/`avg300`/`total` |
| 指标 | 句柄够不够？ | 用 `/proc/sys/fs/file-nr` | 读三列：已分配、已分配未使用、上限 |
| 指标 | 套接字总量与状态分布是多少？ | 用 `ss -s` 与 `ss -ti` | 读 `Total`；`estab`/`closed`/`orphaned`/`timewait`；再读每连接的 `rtt`、`retrans` |
| 历史 | 历史采样到底有没有在采？ | 用 `ls -l /var/log/sysstat/` | 读当天 `sa<DD>` 的大小与 mtime（`DD` 是「日」，不是序号） |
| 历史 | 某个时间窗内的资源曲线是什么样？ | 用 `sar -u` / `-r` / `-b` / `-n DEV` / `-q`，配 `-s`/`-e` | 读各列；`Average:` 是整窗平均，不是瞬时峰值 |
| 历史 | 怎么把它导出成可对账的文件？ | 用 `sadf -d /var/log/sysstat/sa<DD> -- -u` | 读分号分隔的 CSV（comma-separated values，纯文本表格）；第二列是采样间隔秒数，时间戳是 UTC |
| 历史 | 谁在采、留几天？ | 用 `grep -E '^(HISTORY\|SA_DIR\|ZIP)=' /etc/sysstat/sysstat` 与 `systemctl list-timers 'sysstat*'` | 读 `HISTORY=`、`SA_DIR=`、`OnCalendar=`、`LAST` |
| 告警链路 | 规则算出来没有？ | 用 `curl "/api/v1/query?query=ALERTS"` | 读 `alertstate` 为 `pending`/`firing`，值为 1 |
| 告警链路 | 规则在不在评、上次求值何时？ | 用 `curl "/api/v1/rules"` | 读每条规则的 `state`、`health`、`lastEvaluation` |
| 告警链路 | 告警被什么压住了？ | 用 `curl "<am>/api/v2/alerts"` | 读 `status.state`、`status.silencedBy`、`status.inhibitedBy` |
| 告警链路 | 它会被送到哪个 receiver？ | 用 `amtool config routes test --config.file=<f> key=value` | 读输出的 receiver 名 |
| 告警链路 | 还挂着哪些静默？ | 用 `amtool silence query --alertmanager.url=<url>` | 读 `Matchers`、`Ends At`、`Created By`、`Comment` |
| 告警链路 | 从用户视角看能不能用？ | 用 `curl "<bb>/probe?module=<m>&target=<t>"` | 读 `probe_success`、`probe_http_status_code`、`probe_duration_seconds`、`probe_ssl_earliest_cert_expiry` |

表里的「用什么」分两类：**命令**（`df`、`du`、`lsof`、`journalctl`、`vmstat`、`ss`、`sar`、`sadf`、`logrotate`、`curl`、`amtool`；文档在 `man 1` 或 `man 8`）与**内核接口文件**（`/proc/pressure/*`、`/proc/sys/fs/file-nr`、`/proc/<pid>/fd`、`/proc/<pid>/limits`；直接读，没有配套命令，也就没有「参数写错」这一类失败）。判据是 man 节号：`man 1`/`man 8` 是命令，`man 5` 是文件格式或配置项，`man 7` 是概览。两个容易混的落点：`/proc/pressure/*` 的口径在内核文档 `Documentation/accounting/psi.rst`（按与目标机器同一主版本取），而 `/proc/sys/fs/file-nr` 是可读的内核参数快照，所以改它要写 `/proc/sys/fs/file-max`。

**只读与破坏性的边界**：上表里 `df`/`du`/`lsof`/`readlink`、`journalctl` 的查询与 `--disk-usage`/`--list-boots`/`--header`、`systemd-analyze cat-config`、`systemctl show`、`vmstat`/`ss`/`ls`/`stat`/`find`、`sar`/`sadf`、`curl` 的各只读 API、`amtool alert query`/`silence query`/`config routes test`、`logrotate -d`（演练，不落盘）——全部是只读动作，**生产机上也可以做**。破坏性的动作包括：`journalctl --vacuum-*`（删掉历史启动的证据，**不可回滚**）、`logrotate -f`（立刻切割正在被写的文件，且不一定解决持有旧 fd 的问题）、`rm`（对已打开的文件既不释放空间又丢掉证据）、改配置（`journald.conf`、`rsyslog`、采集器、告警规则）、建静默（会真的把真告警压下去）、启停服务与 `kill`——这些**只在可快照的实验机上做**。`logrotate -d` 与 `logrotate -f` 只差一个字母，一个是演练一个是动手，敲之前先看清。黑盒探测介于两者之间：对本机是只读的，但它会真的向目标发起请求，对被测服务和计费链路有成本，所以探测频率要进方案。

## 2. 怎么读这些数字

每个字段给五件事：**是什么、单位、多少算异常（或说明只能与自己的基线比）、和谁一起看、看到它转向哪一步**。下面贴的输出只用来展示**格式**：**数值仅示意、不代表你的机器**；凡标注环境的值只在该环境成立。本节的实机数字来自 Ubuntu 24.04.5 LTS（VMware 虚拟机）/ 内核 `6.8.0-139-generic` / systemd 255 / cgroup v2 / root 可用的机器，换机器、换发行版都要现场重取；RHEL 系的路径与默认值**未实测**。

### 2.1 容量：四类计数与它们的差值

```bash
df -hT; df -i                                          # 验证：哪个文件系统的已用块或 inode 计数接近上限
du -xsh /var/log/* 2>/dev/null | sort -h | tail -10     # 验证：目录树里可见文件谁最大
lsof +L1 2>/dev/null | head                            # 验证：已删除但仍被持有的文件
journalctl --disk-usage                                # 验证：journal 的实际占用（不含 /var/log/*.log）
```

```text
/dev/mapper/ubuntu--vg-ubuntu--lv ext4   47G  8.7G   36G  20% /
/dev/mapper/ubuntu--vg-ubuntu--lv 3145728 159901 2985827    6% /
Archived and active journals take up 26.3M in the file system.
```

**数值仅示意、不代表你的机器**（上面三行的量级来自实验机，且 `--disk-usage` 是会变的数）。

- **`df -hT` 的 `Use%` 与 `Avail`**：这一对字段给出文件系统层面已用块与普通用户可用块的占比，由于 `Avail` 的单位是 GiB 而 `Use%` 的单位是百分比，所以两者要一起读。**判据**：`Use%` 达到 90% 以上才算接近上限，但真正的判据不是百分比，而是 `Avail` 按当前增长速率还能撑多久。**与谁同看**：`Size - Used - Avail` 的差额就是 ext4 默认留给 root 的 5%，因为本机实测 `12581888` 块中保留 `629094` 块（约 2.4 GiB），所以它解释了「`df` 说快满了，root 还能写」这个现象。**转向**：若 `Use%` 高且 `du` 也在目录树里找得到大文件，则转场景一的第 3 步；若 `Use%` 高而 `du` 找不到大文件，则转场景一的第 4 步。
- **`df -i` 的 `IUse%`**：这个字段是已用 inode 数与总 inode 数的占比，由于 inode 的计数单位是「个」，所以它与容量百分比是两套不同的计数。**判据**：`IUse%` 接近 100% 时系统就再也建不了文件，而此时 `df -hT` 可能只显示个位数百分比，因为实验机上曾出现 `df -i` 的 `512/512 100%` 而 `df -hT` 显示 `28M 32K 26M 1%`。**与谁同看**：它只与 `df -hT` 一起看，因为两条曲线同时读才分得清「空间满」和「inode 满」。**转向**：若 `IUse%` 高，则要找海量小文件并追问「谁在按秒建文件」，这个方向与日志体积无关。
- **`du -xsh` 的每行大小**：这个值统计目录树里**有文件名**的文件所占用的块数，单位是 MiB/GiB。**判据**：它只能与自己的基线比（也就是同一台机器同一天的 `/var/log` 分布），因为没有一个通用阈值。**与谁同看**：`df`，因为两者的统计口径不同。**转向**：若 `du` 找得到大文件，则说明这些文件真的占用了空间，所以走保留策略与压缩；若 `du` 明显小于 `df -B1` 的已用字节，则转 `lsof +L1`。
- **`lsof +L1` 与 `/proc/<pid>/fd` 里的 `(deleted)`**：这两处列出的就是已删除但仍被打开的 inode，也就是 link count 已为 0、`lsof +L1` 里那行带 `(deleted)` 标记的文件；`SIZE/OFF` 是那个文件仍占用的大小，单位是字节。**判据**：用 `df -B1` 的已用字节减去 `du` 能看到的总量，由于这个差值就是这类 inode 的和，所以它可以直接当作判据。实验机在 64 MiB 的临时 loop 文件系统上实测过它的 10 MiB 版本：`rm` 一个仍被打开的 10 MiB 文件后，`df` 已用从 `24576` 涨到 `10510336`（恰好 `+10485760` 字节），而 `du -sh` 只看到 20K，关掉 fd 后立刻回落到 `24576`。**与谁同看**：同时用 `ss -lntp` 找持有该 fd 的进程是谁、用 `systemctl status` 看它是不是服务主进程，因为要按影响面决定用 `reload` 还是 `restart`。**转向**：若找到了这类 inode，则让持有该 fd 的进程重开文件（`rm` 第二次没有任何用，而对业务进程 `kill -9` 会丢现场）；若找不到而 `df`/`du` 仍对不上，则去查挂载覆盖（`findmnt`）与稀疏文件。

### 2.2 journald：容量、启动与字段

```bash
journalctl --disk-usage                                # 验证：当前占用（会变，以现场为准）
journalctl --list-boots --no-pager                      # 验证：还留着几次开机，最老一条是什么时候
journalctl -n 1 -o json | head -20                      # 验证：一条记录带哪些字段
systemd-analyze cat-config systemd/journald.conf | grep -nE "^# /|^[A-Za-z]"   # 验证：生效值来自哪个文件
```

```text
IDX BOOT ID                          FIRST ENTRY                 LAST ENTRY
  0 decad510b934454f9d61aef2aa2893fd Sat 2026-09-19 07:08:34 UTC Sat 2026-09-19 08:08:26 UTC
```

**数值仅示意、不代表你的机器。**

- **`--disk-usage` 的容量值**：这个值统计 journal 的 active 与 archived 文件合计占用，单位是 MiB/GiB。**判据**：它只能与自身基线比，而且必须带采样时刻，因为实验机在写作期间实测过它从 `20.7M` 降到 `16.0M`（做过一次 `--vacuum-size=15M`）、后来又回到 `26.3M`，可见量级在几十 MiB 并随系统活动与采集器写入变化。**与谁同看**：`systemd-analyze cat-config systemd/journald.conf` 里的上限（也就是下一条）。**转向**：若占用远低于上限，则说明问题不在容量上，所以转落点与限流；若占用贴着上限，则转保留策略与 `--vacuum-*`（这是破坏性动作，先确认历史证据还需不需要）。
- **生效配置里的容量项**：这些项在为空时各自落在默认值上：`SystemMaxUse=` 为空时的实际行为是把上限取作所在文件系统的 10%、且不超过 4 GiB；`SystemKeepFree=` 为空时的实际行为是至少留 15% 空闲；`MaxRetentionSec=` 为空时的实际行为是**不按时间删，只按容量**（所以要「留 30 天」必须显式设置）。**判据**：它只能与自身基线比，因为根分区 48 GiB 时 10% 是数 GiB，而小盘上则可能远不够。**与谁同看**：`df -hT`，因为 journal 与 `/var/log/*.log` 常在同一文件系统上，所以这两类计数要分别算。**转向**：若上限合不上业务要求，则转本章治理篇的保留策略；若上限够而空间仍满，则回到场景一的四类原因。
- **`Storage=` 与 `/var/log/journal` 是否存在**：`Storage=auto`（默认）的语义是「有目录就持久化，没有就写 `/run/log/journal`，因此重启即丢」。**判据**：若 `ls -ld /var/log/journal` 没有输出，则说明日志只存在内存里，而这种情况没有阈值可言。**与谁同看**：`--list-boots`，因为两者一起读才能区分「没持久化」和「被轮转掉了」。**转向**：若目录不存在而业务要求回溯，则建目录（这属于生产变更，不在本机随手做）；若目录存在而 `--list-boots` 只剩一条，则说明是容量把旧 boot 轮转掉了，不是因为没持久化。
- **`--list-boots` 的 `IDX`/`FIRST ENTRY`**：`IDX=0` 是当前这次开机，负数则往回数；`FIRST ENTRY` 是最老一条的时间。**判据**：它只能与自己的保留要求比，因为没有一个通用天数成立。**与谁同看**：`--disk-usage` 与 `sar` 的历史文件，因为 `journalctl --list-boots` 只剩一次开机、而 `sa<DD>` 里还夹着 `LINUX RESTART` 标记行，就说明这台机器重启过多次、journal 的旧 boot 已被回收。**转向**：若要查的开机不在了，则立即缓解已经没有意义，所以改为核对保留期与容量上限。
- **`-o json` 的字段**：`_TRANSPORT` 说明消息从哪个通道进来（`stdout`/`syslog`/`kernel`/`audit`），`SYSLOG_IDENTIFIER` 是来源标识，`PRIORITY` 是 0–7 的级别，`_SYSTEMD_UNIT` 决定归属，而 `__REALTIME_TIMESTAMP`（墙上时钟）与 `__MONOTONIC_TIMESTAMP`（自开机微秒）是两种时间戳，它们的单位都是微秒。**判据**：这里没有「多少算异常」，只有「是不是你要找的那一条」，因为同一个标识符的消息可能来自不同通道（实验机实测 `logger -t labcmp` 是 `_TRANSPORT=syslog`，而 `systemd-cat -t labcmp` 是 `_TRANSPORT=stdout`）。**与谁同看**：`timedatectl`，因为要先确认墙钟可不可信。**转向**：若字段里没有你要的实例 ID 或 `trace_id`，则说明应用没把它写进结构化字段（写在正文里的 JSON 不会自动变成字段），因此转日志规范；若要算间隔或跨源排序，则用单调时间戳，不要用墙钟。
- **`cat-config` 的来源行**：输出里以 `# ` 开头的行是来源路径，它后面跟着该文件的内容，因此同一个键出现两次就说明后一处覆盖了前一处。**判据**：不要看「你在哪个文件里写了什么」，只看合并后的生效值，因为配置项会被覆盖。Ubuntu 24.04 的规范例子是：`/etc/systemd/journald.conf` 里是注释掉的 `#ForwardToSyslog=no`，而 `/usr/lib/systemd/journald.conf.d/syslog.conf` 里是 `ForwardToSyslog=yes`，实际生效的是后者，所以这也解释了「同一条日志为什么 journald 和 `/var/log/syslog` 里都有」。**一个连带的坑**：`systemctl show systemd-journald -p Storage -p SystemMaxUse -p ForwardToSyslog` 会返回空（退出码仍是 0），因为这些是 `journald.conf` 的配置项，不是 unit 属性。**与谁同看**：`journalctl --disk-usage` 与 `journalctl --header`。**转向**：若要判断「限流会不会丢消息」，则读 `RateLimitIntervalSec=30s`/`RateLimitBurst=10000` 的生效值，再落回实际落库条数。

### 2.3 本机此刻：排队、压力、句柄、套接字

```bash
vmstat 1 2 | tail -1                                   # 验证：第二行才是当前一秒，第一行是自开机平均
grep -H . /proc/pressure/cpu /proc/pressure/memory /proc/pressure/io   # 验证：some/full 与 avg10/60/300
cat /proc/sys/fs/file-nr                               # 验证：已分配句柄数与上限（三列）
ss -s | head -3                                        # 验证：套接字总量与 TCP 状态分布
```

```text
  r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st gu
  1  0      0 4718956 177964 2816032    0    0   191   943  511    1  1  1 99  0  0  0
  0  0      0 4718956 177964 2816036    0    0     0  1140  259  211  0  0 100  0  0  0
```

**数值仅示意、不代表你的机器。**上面两行是 `vmstat 1 2` 的两行数据，第一行 `cs=1` 是自开机以来的平均，第二行 `cs=211` 才是当前这一秒——同一个字段差 200 倍，这就是「带间隔参数时第一行不是当前值」的直接证据。

- **`r` 与 `b`**：这两个字段分别是可运行队列长度与不可中断睡眠（D 状态）的进程数，单位是个。**判据**：`r` 要跟 CPU 核数比，因此实验机 4 vCPU 时 `r>4` 才说明在排队；而 `b>0` 就已经说明有进程卡在 IO 或锁上，不需要等它变大。**与谁同看**：`us`/`sy`/`wa`/`id` 四列。**转向**：若 `r` 高且 `us+sy` 高，则去查谁在占用 CPU（看 `us`/`sy` 两列）；若 `r` 不高而 `b` 高，则转 IO 与锁，不要转 CPU。
- **`si`/`so`**：这两个字段是换入与换出速率，单位是 KiB/s。**判据**：它们长期非 0 说明内存已经不够用，而偶发脉冲要结合 `free` 看，因为单次脉冲不足以定性。**与谁同看**：`/proc/pressure/memory` 的 `full`。**转向**：若 `so` 持续为正，则转内存与 OOM（Out Of Memory，内存耗尽）方向，不要在这里继续看 CPU。
- **`us`/`sy`/`wa`/`id`**：这四列分别是用户态、内核态、IO 等待、空闲的 CPU 时间占比，单位是百分比，而它们与 `st`（被虚拟化偷走的时间）、`gu`（跑客户机的时间）不必凑成 100。**判据**：`id` 高不代表没问题，因为锁竞争、GC（garbage collection，垃圾回收）停世界、单核被占满都会让整机 `id` 很高而接口变慢。**与谁同看**：`r`、`wa`、`/proc/pressure/cpu`。**转向**：若 `id` 高而接口慢，则直接转场景九，不要在整机 CPU 上继续找。
- **`/proc/pressure/*` 的 `some`/`full`**：这两个字段是 PSI（Pressure Stall Information，压力停顿信息）给出的时间占比，其中 `some` 是「至少有一个任务因该资源停住」的时间占比，`full` 是「所有非空闲任务同时停住」的时间占比；`avg10`/`avg60`/`avg300` 是三个窗口的百分比，而 `total` 是自开机起的累计微秒，因此它与前三个的读法不同。**判据**：`avg*` 只能与自身基线比；`total` 只用来取差值，因为两次读数相减才是「这段时间里新增了多少停顿」；CPU 的 `full` 在本机实测一直是 0（`total=0`），所以判断 CPU 压力主要看 `some`，而内存与 IO 的 `full` 才是有用的判据。**与谁同看**：`vmstat` 的 `r`/`b`/`si`/`so`。**转向**：若 `io` 的 `full` 非 0，则转 IO 与文件系统；若 `memory` 的 `full` 非 0，则转内存与 OOM；若三类都接近 0 而用户说慢，则转场景九。
- **`/proc/sys/fs/file-nr` 的三列**：这三列依次是「已分配的文件句柄数」「已分配但未使用的句柄数」「系统上限」，单位是个；其中上限默认很大，因为实验机上是一个接近 `2^63` 的数。**判据**：要看第一列相对第三列的增长趋势，因为单次读数只有与自身基线比才有意义；而第二列长期为 0 说明句柄用尽。**与谁同看**：`ss -s` 的 `Total`，以及 `/proc/<pid>/limits` 的 `Max open files` 两列，因为后者是进程自己的软硬上限，所以它与系统上限是两类不同的计数。**转向**：若句柄在长而服务报「too many open files」，则转进程级 rlimit 与 fd 泄漏，因为这不是系统上限的问题。
- **`ss -s` 的 `Total` 与 TCP 状态分布**：`Total` 是套接字总量，而 `estab`（已建立）、`closed`、`orphaned`（无主）、`timewait`（主动关闭后等待）是四类计数，单位都是个。**判据**：`estab` 要有基线；`orphaned` 长期非 0 说明有连接没被应用收走；而 `timewait` 上万说明短连接速率极高或没有连接复用。**与谁同看**：`ss -ti` 的 `retrans`（重传次数）与 `rtt`（往返时延）。**转向**：若 `orphaned` 或 `timewait` 异常，则转应用连接管理与本机端口范围；若 `retrans` 在长，则转网络路径。

### 2.4 历史：`sar` 与 `sadf` 的口径

```bash
ls -l /var/log/sysstat/                                 # 验证：有没有当天的 sa<DD>（第一步永远是这一条）
sar -u -s 03:00:00 -e 04:00:00                          # 验证：指定窗口的 CPU（窗口按本地时区解释）
sar -r -s 03:00:00 -e 04:00:00                          # 验证：同一窗口的内存
sar -b; sar -n DEV; sar -q                              # 验证：IO、网卡、负载三条线
sadf -d /var/log/sysstat/sa<DD> -- -u | head -3         # 验证：导出 CSV，时间戳是 UTC
```

- **`ls -l` 的 `sa<DD>` 大小与 mtime**：这两个值描述 sysstat 的历史采样文件，大小单位是字节；`DD` 是「日」，因为实验机当月 19 号就是 `sa19`，所以查 `sa32` 只会得到 `Cannot open …: No such file or directory`（退出码 2）。**判据**：这里没有通用大小阈值，只能与自身基线比，也就是看「今天有没有这个文件、大小有没有在长、mtime 是不是最近的整十分」。**与谁同看**：`systemctl is-enabled sysstat-collect.timer`（是不是 `enabled`）与 `systemctl list-timers 'sysstat*'` 的 `LAST`。**转向**：若文件缺失或停滞，则转「为什么没采」（权限、磁盘满、timer 被 mask）；若有数据，则才谈得上窗口分析。
- **`sar -u`/`-r`/`-b`/`-n DEV`/`-q` 的列**：`-u` 给出 CPU 各类时间占比（百分比），`-r` 给出内存（其中 `kbmemfree` 单位是 KiB，而 `%commit`/`%memused` 是百分比），`-b` 给出 IO 总体（`tps`/`rtps`/`wtps` 单位是次每秒），`-n DEV` 给出每张网卡（`rxkB/s`/`txkB/s` 单位是 KiB/s），`-q` 给出负载与队列（`ldavg-1/5/15` 与 `runq-sz`、`blocked`）。**判据**：**`Average:` 行是整窗平均，不是瞬时峰值**，因为实验机实测过一个 30 分钟窗口的 `Average %user=0.80`，而窗口内单个 10 分钟采样点是 `1.51`，两者相差近两倍；所以判断尖峰要看采样点行，不要看 `Average:`。**与谁同看**：五条线要交叉对照（例如 CPU 低而 `%iowait` 高、`kbmemfree` 掉且换页起、`txkB/s` 冲高，分别指向不同资源）。**转向**：若窗口内有异常，则拿同一时间窗的日志、变更记录、上游监控去对齐。
- **`sadf -d` 的 CSV**：它是 `;` 分隔的导出格式，第一行是以 `#` 开头的列名，第二列是采样间隔（单位秒，`600` 即 10 分钟），而时间戳列带 `UTC`。**判据**：**`sadf -d` 永远输出 UTC，并且忽略 `TZ`**；`sar -s/-e` 的窗口却按进程本地时区解释，因此两者混用会在非 UTC 机器上错开一个时区偏移——实验机时区是 `Etc/UTC`，差值恰好是 0，**这是最容易误认为「永远一致」的环境**；换到 `Asia/Shanghai` 就差 8 小时。**与谁同看**：`timedatectl` 的时区行、各来源日志的时间戳格式。**转向**：若对不上，则先把所有时间统一到 UTC 再排序，否则「谁先谁后」不可判定。
- **`/etc/sysstat/sysstat` 里的 `HISTORY=` 与采集计划**：`HISTORY=` 是保留天数（实验机 `sysstat 12.6.1` 上是 `7`），而同一文件里还有 `COMPRESSAFTER=10`、`SA_DIR=/var/log/sysstat`、`ZIP="xz"`；采集由 `sysstat-collect.timer`（`OnCalendar=*:00/10`）与 `sysstat-summary.timer`（`00:07:00`）驱动，而 `/etc/cron.d/sysstat` 里还保留了一套 cron 版计划；`sadc` 在 `/usr/lib/sysstat/` 而**不在 `PATH` 里**。**判据**：`HISTORY` 必须 ≥ 你的复盘窗口，因为默认 7 天对「两周内复盘」不够。**与谁同看**：`df -hT`，因为留更久要占更多空间。**转向**：若复盘窗口长于 `HISTORY`，则转容量与保留策略；RHEL 系的对应文件是 `/etc/sysconfig/sysstat`（`HISTORY=`/`ENABLED=`），**未实测**。

### 2.5 指标与规则：`up`、`ALERTS`、`/api/v1/rules`

```bash
curl -s "/api/v1/query?query=up" | head               # 验证：每个 target 的抓取结果
curl -s "/api/v1/query?query=ALERTS" | head           # 验证：规则有没有真的算出来
curl -s "/api/v1/rules" | head -40                    # 验证：每条规则的 state/health/lastEvaluation
```

- **`up`**：这个字段表示 Prometheus 对每个 target 最近一次抓取是否成功，值是 0 或 1，而 `instance`/`job` 是对象标识。**判据**：`up=0` 就是抓取失败；`up=1` 只说明 `/metrics` 抓得到。**与谁同看**：`/api/v1/targets` 的 `health`/`lastError`/`lastScrape`、`scrape_duration_seconds`、目标侧 `curl` 的 HTTP 码。**转向**：若 `up=0`，则转目标与网络；若 `up` 全为 1 而曲线有断点，则转 label 与查询窗口，不要改采集配置。
- **`ALERTS`**：它是由告警规则生成的时序，其中 `alertstate` 取 `pending`（表达式已成立但还没熬过 `for`）或 `firing`，值为 1。**判据**：**`ALERTS` 为空是正确结果，不是故障**，因为它说明规则在评、只是条件不成立；而要验「规则真能 firing」，得另造一条必然为真的表达式或看历史。**与谁同看**：`/api/v1/rules` 的 `state`（`inactive`/`pending`/`firing`）、`health`（`ok`/`err`）、`lastEvaluation`。**转向**：若 `ALERTS` 有值，则去 Alertmanager 看被谁压住；若 `ALERTS` 为空而 `state=inactive`、`health=ok`、`lastEvaluation` 很新，则说明规则正常，所以去查阈值与数据源；若 `health=err` 或 `lastEvaluation` 很旧，则转规则文件与 Prometheus 自身。
- **`/api/v1/rules` 的 `lastEvaluation`**：这个字段是这条规则上次求值的时刻，单位是时间戳。**判据**：要把它与现在比，因为差值应该约等于 `evaluation_interval`，差得远说明评估没在跑。**与谁同看**：`state` 与 `health`，因为三者一起看才分得清「没算」「算了没到」和「算错了」。**转向**：若评估停住，则转 Prometheus 进程与规则文件语法；若 `health=err`，则用 `promtool check rules` 定位到行。

### 2.6 告警状态与路由：`/api/v2/alerts` 与 `amtool`

```bash
curl -s "<am>/api/v2/alerts" | head -40                # 验证：state 与 silencedBy/inhibitedBy
amtool config routes test --config.file=<f> severity=warning service=web   # 验证：会送到哪个 receiver
amtool silence query --alertmanager.url=<am>           # 验证：还挂着哪些静默、什么时候到期
```

- **`status.state`**：这个字段取 `active`（会通知）或 `suppressed`（被静默或抑制，不会通知）两个值之一，因此它没有阈值。**判据**：若 `state=suppressed`，则要紧接着看下面两个字段，否则你不知道是谁压的。**与谁同看**：`silencedBy` 与 `inhibitedBy`。**转向**：若它是 `active` 而人没收到，则转路由与渠道；若它是 `suppressed`，则先确认压制是否仍然应该存在。
- **`status.silencedBy`**：这个字段是压制这条告警的静默 ID 列表，因为实验机实测建一条静默后对应告警变成 `state=suppressed`、`silencedBy=['a23478de-…']`。**判据**：非空即为被静默，因此要配合 `amtool silence query` 的 `Ends At` 看它是维护窗口还是遗留静默。**与谁同看**：`amtool silence query` 的 `Matchers`/`Created By`/`Comment`。**转向**：若它是遗留静默，则去复盘静默的生命周期管理；若它是维护窗口，则属正常。
- **`status.inhibitedBy`**：这个字段是压制这条告警的抑制规则指纹列表，因为实验机实测发一条同 `alertname+service` 的 `critical` 后，两条 warning 变成 `suppressed`、`inhibitedBy=['0c65b10c93ac87dc']`，而 `service="db"` 的 warning 仍是 `active`——原因是抑制规则带了 `equal: ['alertname','service']`。**判据**：非空即为被抑制；被压的范围由 `equal` 决定，因此写宽了会压掉真故障。**与谁同看**：配置里的 `source_matchers`/`target_matchers`/`equal`。**转向**：若真故障被压住，则收窄 `equal`；若噪声没被压住，则检查标签是否真的相等。
- **`amtool config routes test` 的 receiver 名**：这个输出用于离线判断「这条标签组合会被送到哪个 receiver」，它不真的发通知；实验机实测时 `warning service=web` 落到 `team-mail`、`critical service=web` 落到 `pager`，而 `info service=db` 落到 `null-sink`。**判据**：若送到 `null-sink` 一类空接收器，则该路由写错了。**与谁同看**：`group_by`。**转向**：若 receiver 不对，则改路由；若 receiver 对而人没收到，则才轮到渠道。

### 2.7 用户视角探测：blackbox 的四个指标

```bash
curl -s "<bb>/probe?module=http_2xx&target=<url>" | grep -E "^(probe_success|probe_http_status_code|probe_duration_seconds|probe_ssl_earliest_cert_expiry) "   # 验证：一次探测的四条结果
```

- **`probe_success`**：这个字段取 0 或 1，表示本次探测是否按 module 的预期成功。**判据**：`0` 只说明「从**这个探测点**到目标**这条路**」不通，因为实验机实测探测在监听的本地端口是 `1`、而探测无人监听的 `127.0.0.1:20699` 是 `0`，所以上线前必须用真实探测源与真实路径验证。**与谁同看**：`probe_http_status_code`、`up`。**转向**：若 `up=1` 而 `probe_success=0`，则说明指标在报、用户访问不了，所以转目标链路与证书；若 `up=0` 且 `probe_success=0`，则先修采集链。
- **`probe_http_status_code`**：这个字段是 HTTP 响应码。**判据**：`0` 表示连不上（没有响应），`5xx` 表示服务端错，而只有 `200`/`3xx` 才算这条路径通。**与谁同看**：`probe_success`，因为「什么算成功」由 module 定义。**转向**：要用它区分「连不上」与「返回 500」，由于前者转网络与监听、后者转应用日志，所以两种情况的动作不同。
- **`probe_duration_seconds`**：这个字段是探测总耗时，单位是秒。**判据**：它只能与自身基线比，因为同一条探测路径的正常值就是这个指标的历史值。**与谁同看**：`probe_dns_lookup_time_seconds`，因为解析慢会导致偶发慢。**转向**：若耗时在长而成功率还是 1，则转用户视角的延迟，它与场景九用同一套推理。
- **`probe_ssl_earliest_cert_expiry`**：这个字段是证书最早的到期时间，单位是 Unix 秒（从 1970 年起算的秒数）。**判据**：表达式是 `probe_ssl_earliest_cert_expiry - time() < 14 * 86400`，由于 `time()` 也是 Unix 秒，所以两者可以直接相减；**必须按域名分组**，因为实验机同一天两个真实域名的剩余有效期差了约 4 倍（38.6 天与 160.3 天），所以一个全局阈值测不出两种现实。**与谁同看**：`probe_success`（证书问题会让探测直接失败）、`probe_http_status_code`。**转向**：若剩余天数进入窗口，则走续期流程；若 `probe_success=0` 且证书无异常，则转路径与端口。

## 3. 采样纪律与基线卡

一次合格的采集要满足五条：

1. **同口径**：读数时要写清它是命令输出还是内核接口文件，以及它是瞬时值还是窗口平均，因为同一个「磁盘用了多少」在 `df -B1`（文件系统已用块）与 `du -xsh`（可见文件名占用）里是两类不同的计数，所以两个都要读，并且要说清用哪一个下的结论。
2. **带时间戳**：由于 `journalctl --disk-usage`、`/proc/pressure/*` 的 `total`、`--list-boots` 的 `FIRST ENTRY` 都是会变的数，所以任何读数都要带采样时刻与来源主机。
3. **至少两次**：计数类指标（PSI 的 `total`、`/proc/sys/fs/file-nr`、`sa<DD>` 的大小）都必须取差值，因为单点读数说明不了增量；而 `vmstat`、`mpstat`、`pidstat`、`iostat` 不带参数时给的是自开机以来的平均，所以要瞬时值就得给「间隔 次数」并取最后一行。
4. **留原始输出**：要把命令、时间、关键几行一起留档，也就是变更前后各留一份，因为只留结论的记录事后无法复现，也无法交接。
5. **标注环境**：`timedatectl`、`ls -ld /var/log/journal`、`systemd-analyze cat-config systemd/journald.conf`、`df -hT`、`ls -l /var/log/sysstat/`、`systemctl is-enabled sysstat-collect.timer` 这一组事实决定了上面所有默认值该怎么解释，所以换机器就必须重采。

**基线卡要回答的问题**（模板与交付物在本章的治理篇）：日志落到哪几个地方、journal 的容量上限与保留期各是多少、`/var/log` 有没有与业务数据分盘、历史采样留几天、时间基线可不可信，以及告警从规则到通知中间配了哪些降噪手段。这一篇只负责「怎么采」，所以产物形态不在这里定。

## 常见故障与排查方向

### 场景一：磁盘被日志写满

**场景**：这台单机装的是 Ubuntu 24.04，根分区是 ext4 on LVM，约 48 GiB。早上告警显示「`/` 使用率 96%」。登录后 `du -xsh /var/log/*` 加起来只有 2 GiB，而 `find /var/log -size +100M` 没有输出；业务仍在正常响应，同时 `/var/log` 与业务数据没有分盘。

**排查顺序**：由于四类原因的处置互不通用，所以要先把原因分类，然后再动手。

1. 执行 `df -hT` 与 `df -i`，先分清是空间满还是 inode 满、以及是哪个文件系统。若空间接近满而 `df -i` 只有个位数百分比，则走容量方向；若 `df -i` 接近 100% 而 `df -hT` 很空，则走海量小文件方向，而这条与日志体积无关。
2. 算一下 `Size - Used - Avail`：少的那一截是 ext4 默认留给 root 的 5%（实验机实测 `12581888` 块里保留 `629094` 块），由于它既不进 `du` 也不属于已删除但仍被打开的 inode，所以这一条解释了「普通用户写不进去而 root 还能写」。
3. 执行 `du -xsh /var/log/* | sort -h | tail`：若找得到大文件，则说明文件真的占用了空间；若找不到，则进第 4 步。
4. 执行 `lsof +L1`，或者遍历 `/proc/*/fd` 找 `(deleted)` 标记：若找到了，则说明存在已删除但仍被打开的 inode；判据是 `df` 的已用字节远大于 `du` 的可见量（实验机在临时 loop 文件系统上实测过 10 MiB 的版本：`rm` 之后仍被打开的文件让 `df` 已用从 `24576` 涨到 `10510336`，而 `du -sh` 只有 20K）。
5. 执行 `journalctl --disk-usage`：由于 journal 的占用与 `/var/log/*.log` 是两类分别统计的计数，所以要分别核对；它的量级在几十 MiB，因此通常不是根分区被写满的主因，但它与 `/var/log/*.log` 会被同一块盘的容量同时影响。
6. 若以上都排除了，则去查挂载覆盖（`findmnt`）与稀疏文件。

**一份合格的回答**：它应当包含结论、依据、边界与动作四个方面：结论是它属于四类原因中的哪一类；依据来自哪条命令的哪一列、数值是多少；边界要写明这台机器的 `/var/log` 有没有分盘、journal 有没有持久化、保留块占多少；动作分两步，立即缓解是清掉最老的一段或让持有该 fd 的进程重开日志文件，消除产生原因则要落实三层保留策略，也就是应用按级别输出、journald 设 `SystemMaxUse=`/`MaxRetentionSec=`、logrotate 定份数与压缩。

### 场景二：日志查不到、查不全

**场景**：一个 Python 服务重启后，`journalctl -u mysvc -b` 只剩几条启动记录，同事判定「日志丢了」。这台机器 `/var/log/journal` 存在，服务把日志写 stdout，当天有发布变更。

**排查顺序**：由于这五类原因互不相同，所以要依次按落点、归属、保留、限流与容量、过滤条件检查。

1. **落点**：执行 `systemctl show mysvc -p StandardOutput -p StandardError`。只有当这个属性的值取 `journal` 时，日志才会进 journald；若它改成 `file:`，则 `journalctl -u` 就看不到了。
2. **归属**：由于 `-u` 只匹配该单元的消息，而手工在 SSH 会话里发的消息属于 `session-N.scope`，所以用 `-u` 永远查不到，要按 `-t <标识>` 或 `SYSLOG_IDENTIFIER` 查；同时 `-o verbose` 的 `_TRANSPORT` 说明了来源。
3. **保留**：执行 `ls -ld /var/log/journal` 与 `journalctl --list-boots`。若目录不存在，则说明是内存存储、重启即丢；若只剩一条 boot，则说明历史启动已被裁掉或从未持久化。
4. **限流与容量**：执行 `systemctl show mysvc -p LogRateLimitIntervalUSec -p LogRateLimitBurst` 与 `journalctl --disk-usage`。**判据要落在「实际落库条数」上**（写 N 条再数落库多少），**不要用 `grep -i suppress`**，因为丢弃时不一定留下告警行。
5. **过滤条件**：要核对 `-b` 选中了哪次开机、`--since` 是否按本地时区解释、`-p` 级别是否过窄。因为发布变更后的日志被 `-b -1` 选错开机，所以这是最常见的「少了」的原因。
6. `/var/log/syslog` 这一侧要用另一套判据：执行 `tail /var/log/syslog`，并用 `stat` 读属主属组（Ubuntu 上是 `640 syslog:adm`，所以要读得进 `adm` 组）。

**一份合格的回答**：它应当包含结论、依据、边界与动作四个方面：结论是指出它属于这五类里的哪一类，或者哪几类叠加在一起；依据是落点属性的取值、`--list-boots` 的输出，以及落库条数的实测差值；边界要写明换发行版后 rsyslog 的配置路径与默认转发可能不同，并且 RHEL 系未实测；动作要说清该改落点、该建持久化目录，还是该补保留期。

### 场景三：轮转后新日志不增长

**场景**：`/etc/logrotate.d/myapp` 用 `create` + `rotate 4` + `daily`。昨天轮转过之后，`app.log` 一直是 0 行，而 `app.log.1` 还在长；应用是常驻进程，自己 `open()` 文件写日志。

**排查顺序**：因为「没换文件」与「换了但没人往新文件写」的处置不同，所以要先把这两种情况分开。

1. 对两个文件执行 `stat -c "%i %s %n"`：若 inode 不同，则说明确实换了新文件；若新文件是 0 字节而归档文件在长，则说明写入方还握着旧 fd。实验机实测：`create` 之后不通知应用，随后 9 行数据全部写进归档 `app2.log.1`、新文件 `app2.log` 0 行，而 inode 是 `1310803`（新）与 `1310798`（归档）。
2. 执行 `ls -l /proc/<pid>/fd`，找到指向归档文件的那个 fd，并确认持有该 fd 的进程就是主进程。
3. 检查 `postrotate`，看它有没有真的通知应用重开（`systemctl reload` 或约定的信号），以及应用是否实现了重开。**因为轮转脚本跑成功并不代表应用收到了通知，所以这两件事必须分开确认。**
4. 若该轮转却没有轮转，则这是另一条分支：用 `logrotate -d <conf>` 演练（只读）看条件与 `notifempty`/`size`/`daily` 的判定，再用 `journalctl -u logrotate.service` 看它有没有真跑过（判据是 `ExecMainStartTimestamp` 与日志条目，**不要用 `ConditionResult`**）。**不要用 `logrotate -f` 反复强制执行**来「验证」。
5. 另一条可选路径是 `copytruncate`：它的 inode 不变（实验机实测从 `1310736` 变为 `1310736`），因此写入方无感知，代价是「复制到截断」之间的窗口会丢日志。

**一份合格的回答**：它应当包含结论、依据、边界与动作四个方面：结论是指出问题断在「换文件」还是断在「通知重开」；依据是那两个 inode 的取值、fd 指向哪个文件，以及 `postrotate` 的内容；边界要写明 `create` 与 `copytruncate` 各自的丢日志窗口；动作是补上信号或改用另一种切法，并给出一条能证明「轮转后新文件继续增长」的验证。

### 场景四：日志集中后断流，或中心机磁盘满

**场景**：200 台机器把 `/var/log/auth.log` 经 rsyslog 以 `*.* @loghost.example.com:514`（`@` 是 UDP）转发到一台中心机。某天审计要求查昨天下午的登录记录，查不到；同时中心机 `df -hT` 已到 92%。

**排查顺序**：要先定位断在哪一段，然后再谈怎么补。

1. **先分发送端还是接收端**：在接收端执行 `ls -lt <集中目录> | head` 看最新一条的时间，因为它停在几点就说明断点在几点；在发送端执行 `systemctl status rsyslog` 与 `journalctl -u rsyslog --since "30 min ago"`，看队列、重试与丢弃的报错。
2. **传输方式**：`@` 是 UDP，而 `@@` 是 TCP。**UDP 的丢包完全无感知**，因为实验机实测向没有接收端的 UDP 端口发消息时 `logger` 退出码仍是 `0`；同样情况换成 TCP，退出码是 `1` 并报 `failed to connect`。判据是接收端做「发送计数与接收计数」的对账；若做不到对账，则说明这条链路**没有**丢包证据。
3. **队列**：由于 rsyslog 的默认内存队列在接收端不可达时会丢消息，所以要「断网不丢」就得配磁盘队列与重试。**真正的跨机集中、TLS（Transport Layer Security，传输层加密）、RELP（Reliable Event Logging Protocol，带应用层确认的重传协议）以及断网重连，本机均未实测**，因为本机只有一个 loopback，也没有第二台机器。
4. **中心机容量**：集中只是把容量风险从每台机器搬到中心机，因此保留策略、压缩、清理最老的一段与场景一是同一套做法；同时要给接收端目录单独做容量告警。
5. 关键审计日志改 TCP/TLS/RELP 之后，仍要用计数对账来验收，因为「配了就当不丢」不是判据。

**一份合格的回答**：它应当包含结论、依据、边界与动作四个方面：结论是指出断在发送端、网络还是接收端；依据是接收端最新文件的时间、发送端的队列报错，以及退出码或对账数字；边界要写明 UDP 拿不到丢包证据这一事实；动作分两步，立即缓解是在接收端腾空间并限流，消除产生原因则要改传输方式、加磁盘队列，并给中心机做保留与容量告警。

### 场景五：指标缺失、断点或抓取失败

**场景**：Grafana 上某实例的 CPU 曲线从 14:03 起断开，14:20 自己恢复；同一时刻 `up` 在断点后为 0；这台实例昨晚重启过一次。

**排查顺序**：要从「抓取」往「查询」走，不要先改表达式。

1. 执行 `curl "/api/v1/query?query=up"`，找出 `up=0` 的 `instance`/`job`。若全为 1 而曲线仍有洞，则不是抓取失败，所以转第 4 步。
2. 执行 `curl "/api/v1/targets"`，看 `health`（`up`/`down`/`unknown`）与 `lastError`；若它是 `down` 且有 `lastError` 文本，则问题在目标侧或网络；若它是 `unknown`，则说明还没抓过。
3. 在目标侧执行 `curl -s -o /dev/null -w "%{http_code}\n" http://<target>:9100/metrics` 与 `ss -lntp | grep 9100`，确认它到底在不在监听；同时再对一次抓取耗时与 `scrape_timeout` 的大小关系。
4. **断点有五个常见来源**：目标重启（counter 归零，因为 `rate()`/`increase()` 会自动补偿、不会出现负值，所以受影响的只是重置点附近的外推精度）、采集超时、网络与防火墙、**label 变更导致新旧时序断开**，以及环境相关的 label 值变化。实验机上 `device` 就随环境变，因为根分区在 LVM 上时是 `/dev/mapper/ubuntu--vg-ubuntu--lv`，而 `node_disk_*` 还会同时出现 `dm-0` 与 `sda`，所以写死 `device="/dev/sda"` 的表达式换台机器就断。
5. 表达式侧：要确认时间窗 ≥ 2×`scrape_interval`，因为窗口太小时 `rate()` 会得到空值或剧烈抖动。

**一份合格的回答**：它应当包含结论、依据、边界与动作四个方面：结论是要区分「采集断」与「查询断」这两种情况；依据来自 `up`、`health`、`lastError` 与目标侧 HTTP 码这四次证据，并指出其中哪一条不成立；边界要写明目标重启会截断 counter，但 `rate()` 不会因此变成负值；动作是决定该重启 exporter、该放宽超时，还是该修 label 与表达式。

### 场景六：告警不响

**场景**：用户报障说磁盘写满导致写入失败，值班回看监控：「磁盘剩余不足 15%」的规则确实在规则文件里，但没有任何通知记录，也没人记得收到过。

**排查顺序**：要沿链路逐段验证，并把通知渠道放在最后。

1. 执行 `curl "/api/v1/query?query=ALERTS"`：若它为空，则说明规则在评但条件不成立（这是正确结果，不是故障），所以转第 2 步；若有 `alertstate="firing"`，则说明条件成立过，所以转第 3 步。
2. 执行 `curl "/api/v1/rules"`，读这条规则的 `state`（`inactive`/`pending`/`firing`）、`health`（`ok`/`err`）与 `lastEvaluation`。若 `health=err`，则表达式或数据源有问题；若 `lastEvaluation` 很旧，则评估没在跑；若它是 `pending`，则它卡在 `for` 上没熬过去。
3. 执行 `curl "<am>/api/v2/alerts"`，读 `status.state` 与 `silencedBy`/`inhibitedBy`。若它是 `suppressed` 且 `silencedBy=[...]`，则说明被静默，所以用 `amtool silence query` 核对该静默的 `Ends At`/`Created By`（实验机实测这个 ID 与到期时间都直接可见）；若 `inhibitedBy=[...]`，则说明被更高优先级的告警压住。
4. 执行 `amtool config routes test --config.file=<f> severity=... alertname=...`，离线判断它会送到哪个 receiver。若送到 `null-sink` 一类空接收器，则说明路由写错，而不是渠道坏。
5. **通知渠道要放在最后一步查**，因为顺序反了会在渠道上浪费大量时间。

**一份合格的回答**：它应当包含结论、依据、边界与动作四个方面：结论要说出断在五段中的哪一段；依据来自状态字段或路由输出的原文；边界要写明 `ALERTS` 为空说明规则在工作，因此不能当故障处理；动作是说清改表达式、改路由、清遗留静默，还是查渠道。同时要把「规则没算出来」「算出来被压住」「路由到空 receiver」「渠道失败」这四类原因分开写。

### 场景七：告警风暴

**场景**：一次机架断电让 20 台机器同时不可达，1 分钟内推了 300 条通知，值班同事把群消息屏蔽了；两天后另一台机器的磁盘告警没人看到。

**排查顺序**：降噪的顺序是分组、抑制、静默，复盘之后才是阈值，而这个顺序不能反。

1. 执行 `curl "<am>/api/v2/alerts"` 并按 `alertname`/`service` 归类，先数出一个根因产生了多少条告警。
2. **分组**：`group_by` 决定「什么算同一个故障」，因为实验机实测同 `alertname+service` 的两条 warning 被合并成一条通知（`groupKey={}/{severity="warning"}:{alertname="NodeCpuHigh", service="web"}`，内含 `linux-lab` 与 `linux-lab2` 两条），而 `service="db"` 那条单独一组。**判据**：若 `group_by` 里放高基数 label（`pod`、`request_id`），则会让每个实例各自成组，此时分组等于没用。
3. **抑制**：`inhibit_rules` 用来表达确定的因果，也就是「宕机时同一实例的其他指标异常」这种关系，因此**必须用 `equal` 限定对象**。实验机实测同 `alertname+service` 的 critical 让两条 warning 变成 `suppressed`、`inhibitedBy=[...]`，而 `service="db"` 的 warning 仍是 `active`，原因是规则带了 `equal: ['alertname','service']`。若不写 `equal`，则等同于「任何 critical 压掉任何 warning」。
4. **静默**：它只用于已知问题与维护窗口，因此必须带期限、原因与创建人；窗口结束后用 `amtool silence query` 复查有没有遗留。
5. **调阈值或延长 `for` 是最后一步**，因为它降低的是整体灵敏度，会把真故障一起过滤掉，所以必须复盘后再做并评估漏报风险。

**一份合格的回答**：它应当包含结论、依据、边界与动作四个方面：结论要把「同质告警」与「因果连带告警」分开；依据是分组前后的条数与 `inhibitedBy` 的取值；边界要写明临时静默不是解决方案，因为它到期就会恢复；动作分三层，也就是配置层补分组与抑制、操作层给有期限的静默、事后修规则。此外还要说明基础设施类告警要不要单独路由，以免被服务告警刷屏。

### 场景八：证书到期或用户视角不可用

**场景**：一台对外服务的 `up=1` 一直没掉，但一部分用户报「打不开」，浏览器提示证书问题。这台机器上跑了两个域名，分别是主站与镜像站。

**排查顺序**：要先确认「用户视角」，再看证书，最后看路径。

1. 探测四个指标：`probe_success`（0/1，可用性判据）、`probe_http_status_code`（用来区分连不上与返回 5xx）、`probe_duration_seconds`（单位秒，即用户视角耗时）、`probe_ssl_earliest_cert_expiry`（单位是 Unix 秒）。
2. 证书用 `probe_ssl_earliest_cert_expiry - time() < 14 * 86400` 判定，因为 `time()` 也是 Unix 秒，所以两者可以直接相减。**必须按域名分组**，因为实验机同一天两个真实域名的剩余有效期是 38.6 天与 160.3 天、差约 4 倍，所以一个全局阈值测不出两种现实。
3. 路径边界：`probe_success=0` 只说明「从这个探测点到目标这条路」不通，因为实验机实测探测在监听的本地端口是 1、而探测无人监听的端口是 0；所以上线前要用真实探测源与真实路径验证。
4. 与 `up` 对照：由于 `up` 只说明 `/metrics` 抓得到，所以 `up=1` 而 `probe_success=0` 就是「指标在报，用户访问不了」。
5. ICMP 探测需要原始套接字（`CAP_NET_RAW`），而非 root 环境常把它挡住，所以此时要改用 `tcp_connect`；若探测一个不存在的 module，则会直接报 `http=400` 与 `Unknown module`，因此这是配置写错时最容易排查的一种失败。

**一份合格的回答**：它应当包含结论、依据、边界与动作四个方面：结论要把「证书问题」「目标不可达」「返回 5xx」这三类分开；依据是四个探测指标的具体值与换算后的剩余天数；边界要写明结论只覆盖被探测的那条路径，并且按域名分别成立；动作是决定续期、修探测配置，还是查目标本身的监听与上游。

### 场景九：服务慢但资源都空闲

**场景**：某接口 p99 从 300 ms 涨到 2 s，持续两小时。这台 4 vCPU 的机器 `vmstat` 的 `id` 在 95 以上，`si`/`so` 都是 0，磁盘的 `%util` 也不高。

**排查顺序**：要先确认「确实不忙」，再看请求维度，最后看一次请求的内部结构。

1. 确认资源侧：用 `vmstat 1 2` 取第二行起（第一行是自开机以来的平均值，因为实验机那一行 `cs=1`，而当前一秒是 `cs=211`）；再用 `/proc/pressure/*` 读 `some`/`full` 的 `avg10`/`avg60`/`avg300` 与累计 `total`。`full` 为 0 说明没有出现全面停顿；`some` 有值说明至少有一类任务在等。**这一步的产出是「不忙」的证据，不是结论。**
2. 看 `io` 与 `memory` 的 `full` 是否非 0：只有两者都接近 0 才排除资源饱和；若某一类非 0，则回到对应的资源方向。
3. 请求维度要看延迟分位数（哪个接口、哪个实例、从几点开始），以及下游依赖的成功率与延迟。**因为平均值会掩盖长尾，所以不要用平均延迟下结论。**
4. 一次请求的 span 树：看时间花在哪一段，再把 `trace_id` 拿去日志里捞细节。
5. 常见根因有六类：锁竞争（应用或数据库）、GC 或解释器停世界、DNS 解析慢、下游限流与重试风暴、日志同步落盘，以及单核被占满（此时整机 CPU 不高，因为只有一个核被占满）。

**一份合格的回答**：它应当包含结论、依据、边界与动作四个方面：结论是「这台机器此刻在资源上没有饱和」，并给出它的依据，也就是哪条命令的哪个字段、数值是多少；依据还要往下一步给出「慢在哪一段」的证据，也就是分位数或 span；边界要写清分位数口径的窗口、算法与聚合层级，因为跨实例的 p99 不能靠平均单实例 p99 得到；动作是决定该改依赖调用、该加缓存，还是该修采集口径。

### 场景十：事后复盘没有历史数据

**场景**：业务说「昨晚 3 点左右系统变慢」，你现在登录，故障已经恢复。这台机器装了 sysstat，时区是 `Etc/UTC`。

**排查顺序**：因为第一步永远是「确认有数据」，所以要先确认数据，再谈分析。

1. 执行 `ls -l /var/log/sysstat/`，看有没有当天的 `sa<DD>`、大小多少、mtime 是什么时候。这里 `DD` 是「日」而不是序号。
2. 若文件缺失或停滞，则去查「为什么没采」：`systemctl is-enabled sysstat-collect.timer`、`systemctl list-timers 'sysstat*'` 的 `LAST`（是不是最近的整十分），以及 `grep -vE "^\s*(#|$)" /etc/sysstat/sysstat` 里的 `HISTORY=`/`SA_DIR=`。实验机的三条验收判据就是这三个。
3. 若有数据，则用 `sar -u -s 03:00:00 -e 04:00:00` 取窗口，再按 `-r`/`-b`/`-n DEV`/`-q` 四条线对照。窗口按**本地时区**解释，而**`sadf -d` 导出的是 UTC 且忽略 `TZ`**，因此跨时区对账时两者会差一个偏移（实验机是 `Etc/UTC`，差值恰好是 0，而这是最容易误认为「永远一致」的环境）。
4. 要看采样点行，不看 `Average:`，因为整窗平均会稀释尖峰（实验机实测同一个 30 分钟窗口 `Average %user=0.80`，而窗口内单个采样点是 `1.51`）。
5. 若确实没有历史，则改用别的证据源：本机日志、上游监控的历史指标、下游依赖的延迟记录、变更时间线，把这四条对齐到同一条时间轴。默认 `HISTORY=7`（实验机的 `sysstat 12.6.1`），因此复盘窗口更长就要显式改并在磁盘上留出空间；另外 `sadc` 在 `/usr/lib/sysstat/` 而不在 `PATH` 里。

**一份合格的回答**：它应当包含结论、依据、边界与动作四个方面：结论是第一步先给「有没有数据」的判断；依据在有数据时是窗口、工具与对应的列名，在没有数据时是「为什么没采」与替代证据源；边界要写明保留期与时区这两个前提；动作是把「当日有文件且大小在增长」纳入巡检。

### 场景十一：各来源的证据时间对不上

**场景**：日志说 02:58 开始报错，指标说 03:04 才起量，变更记录写的是 03:00。三条对不上，而且这台机器上 `NTP service: active` 与 `System clock synchronized: no` 同时成立。

**排查顺序**：要先判断时钟可不可信，再统一口径，最后才排因果。

1. 执行 `timedatectl`，把三件事分开看：`Time zone`（时区）、`System clock synchronized`（时间准没准）、`NTP service`（同步客户端在不在跑）。**只有第二行说「准了」**，因为 `active` 只说明客户端在跑。
2. 执行 `timedatectl timesync-status`，读同步源与 `Poll interval`，以及 `Packet count`——`0` 表示一次包都没换到，也就是「服务在跑但没有实际同步」。实验机上就是 `active` 配 `synchronized: no`、`Packet count: 0`，所以这是**要修的前提，不是可以忽略的细节**。
3. 统一口径：报告里要写清每个时间戳是 UTC 还是本地时间，跨机对账统一用 `TZ=UTC`。由于三个工具的默认口径不同，所以要分别记住：`journalctl --since` 按本地时区解释，`sar -s/-e` 按本地时区解释，而 `sadf -d` 是 UTC 且忽略 `TZ`。
4. 排序要用单调时钟：journald 的同一条记录同时带 `__REALTIME_TIMESTAMP`（墙上时钟）与 `__MONOTONIC_TIMESTAMP`（自开机起的微秒），因为后者不受对时影响，所以跨日志源排序与算间隔都用它。
5. 若时钟不可信，则把「谁先谁后」标为**不可判定**，只保留「差了几分钟量级」这种结论；要先把对时修好，再回来重放时间线。

**一份合格的回答**：它应当包含结论、依据、边界与动作四个方面：结论是先给「时钟可不可信」的判断；依据是 `timedatectl` 的三行与 `Packet count`；边界要写明时钟未同步时不做顺序推断，并且时区口径要逐来源标注；动作是修对时、统一到 UTC、用单调时钟重建时间线，并说明哪些结论因此变了。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 不定位环节就开始动手 | 结果是改了三处还没解决、反而引入了新变量，所以要先写下「我认为卡在哪一环」，再用第 1 节的表核对 |
| 先改配置再取证 | 现场会被破坏，此后无法证明根因，因此只读取证必须先行 |
| 用 `du` 判断文件系统满没满 | `du` 看不到已删除但仍被打开的 inode（也就是 `lsof +L1` 里带 `(deleted)` 的那些），因此两者要一起看，而 `df` 已用字节与 `du` 可见量的差值就是这类 inode 占用的大小 |
| `rm` 掉大日志就有空间了 | 若进程还持有 fd，则空间不会释放（实验机实测 `df` 多出 10 MiB 而 `du` 只看到 20K），所以必须让持有该 fd 的进程重开文件 |
| 以为 `df -h` 没满就没事 | inode 的计数与空间容量是两类不同的计数，因为实验机上 `df -i` 到 `100%` 时 `df -hT` 还显示 `1%` |
| 把 `df` 的「已用 + 可用 < 总量」当成进程占着已删除文件 | 那个差额其实是 ext4 默认留给 root 的 5% 保留块，因此判据要落到 `tune2fs -l` 的 `Reserved block count` |
| 把 `vmstat` 第一行当当前值 | 第一行是自开机以来的平均（实验机 `cs=1`），而当前一秒在第二行（`cs=211`），所以它不能当当前值用 |
| 只看 `sar -u` 的 `Average:` 判断峰值 | 因为整窗平均会稀释尖峰，所以判据是采样点行，不是 `Average:` |
| 拿 `sadf -d` 的 CSV 直接和本地日志比时间 | 它输出 UTC 且忽略 `TZ`；由于实验机 `Etc/UTC` 的差值恰好是 0，所以这种情况最容易被误认为「永远一致」 |
| 把 `--disk-usage` 的结果当常量 | 因为 journald 一直在写入与轮转，所以这个数会变；实验机写作期间实测过它从 `20.7M` 降到 `16.0M`、后来又回到 `26.3M`，因此任何读数必须带采样时刻 |
| 用 `systemctl show systemd-journald -p Storage` 查 journald 配置 | 它返回空（退出码仍是 0），因为这些是 `journald.conf` 的配置项，而不是 unit 属性 |
| 只看配置文件里的注释值 | `/etc/systemd/journald.conf` 里是注释掉的 `#ForwardToSyslog=no`，而生效值来自 `/usr/lib/systemd/journald.conf.d/syslog.conf` 的 `yes`，因此判据是 `cat-config` 的合并结果 |
| 用 `grep suppress` 证明日志没丢 | 因为丢弃时不一定留下告警行，所以判据是实际落库条数 |
| 用「通知收没收到」判断告警是否工作 | 链路上还有路由、分组、抑制、静默这些环节，所以要先看 `ALERTS` 与 `/api/v2/alerts` 的状态字段 |
| 一遇告警风暴就调高阈值 | 这样会让灵敏度整体下降、真故障一起被过滤，因此顺序是分组、抑制、静默，复盘之后才是阈值 |
| 把 `up=1` 当成服务对用户可用 | 因为 `up` 只说明 `/metrics` 抓得到，所以用户视角要靠黑盒探测，而探测结论只覆盖那条路径 |
| 用「现象消失」当验收标准 | 因为重启与静默都能让现象消失而根因还在，所以立即缓解必须记录影响面与回滚方式 |
| 事后才打开 `top` 想解释昨天 | 即时工具只看此刻，因此历史要靠提前采集的 sysstat 或时序库 |
| 凭印象说「这台机器没有历史 / 没装 rsyslog」 | 实验机上 sysstat 在采、`sa<DD>` 有当天数据，rsyslog 也 `active` 且 `enabled`，所以这些都要先用 `ls`/`is-active` 验证过再说 |
| 在生产机上做破坏性验证 | `logrotate -f`、`rm`、`journalctl --vacuum-*`、改告警规则、建静默都会产生真实影响 |

## 要点自测

**问：「磁盘满」和「告警不响」两类现象，第一条命令分别是什么，共同点是什么？**
答：磁盘满的第一步是执行 `df -hT` 与 `df -i`，因为要先分清空间满还是 inode 满、以及是哪个文件系统；告警不响的第一步是执行 `curl "/api/v1/query?query=ALERTS"`，因为要先确认规则有没有算出来。共同点是**两者都先只读取证**，然后才决定动不动手。

**问：`df` 和 `du` 对不上，说明什么？怎么处置？**
答：两者回答的问题不同，因为 `df` 统计文件系统层面的已用块，而 `du` 只统计目录树里**可见文件名**的占用。对不上就意味着存在「没有名字但仍占空间」的东西，其中最常见的是已删除但仍被打开的 inode（实验机在临时 loop 文件系统上实测差 10 MiB），也可能是挂载覆盖。处置是用 `lsof +L1` 找持有该 fd 的进程，再用 `reload`/`restart` 让它重开文件，因为继续 `rm` 没有任何用。

**问：`vmstat` 的第一行为什么不能用？**
答：因为带间隔参数时第一行是**自开机以来的平均值**，第二行起才是当前区间。实验机上平均值那行 `cs=1`、当前一秒 `cs=211`，两者差 200 倍。同一纪律适用于 `iostat`/`mpstat`/`pidstat` 不带参数时的输出，也适用于 `top` 的 load。

**问：`journalctl --disk-usage` 显示只有几十 MiB，能说明「日志不会写满磁盘」吗？**
答：不能。因为它只覆盖 journal 的占用，不覆盖 `/var/log/*.log`；而且默认 `SystemMaxUse=` 为空时上限是所在文件系统的 10%、且不超过 4 GiB，而 `MaxRetentionSec=` 为空时**不按时间删**。因此该管的是「保留多久、分不分盘」，而不是「现在多大」；同时这个数会变，所以任何读数都要带采样时刻。

**问：怎么判断一条告警为什么没通知到人？**
答：要沿链逐段走：先看 `ALERTS` 有没有算出来，再看 `/api/v1/rules` 的 `state`/`health`/`lastEvaluation` 判断它在不在评、有没有算错，然后看 `/api/v2/alerts` 的 `state`/`silencedBy`/`inhibitedBy` 判断它是被静默还是被抑制，接着用 `amtool config routes test` 看它会被送到哪个 receiver，最后才轮到通知渠道。另外 `ALERTS` 为空是正确结果，因为它说明规则在评、只是条件不成立。

**问：复盘「昨晚 3 点系统变慢」，第一步做什么？**
答：先执行 `ls -l /var/log/sysstat/` 确认有没有当天的 `sa<DD>`、大小有没有在长；再用 `systemctl is-enabled sysstat-collect.timer` 与 `list-timers` 的 `LAST` 交叉验证。因为只有有数据才谈得上用 `sar -u -s 03:00:00 -e 04:00:00` 取窗口，所以没有数据就换证据源。**同时要注意窗口按本地时区解释，而 `sadf -d` 导出的是 UTC。**

**问：证书到期告警为什么不能用一个全局阈值？**
答：因为不同域名的剩余有效期可以差很多，所以实验机同一天两个真实域名是 38.6 天与 160.3 天、差约 4 倍。表达式要用 `probe_ssl_earliest_cert_expiry - time() < 14 * 86400`（两者都是 Unix 秒），并且必须按域名分组。

**第一反应不要做什么**：不要在没定位环节前动手；不要先改配置再取证；不要用 `du` 判断文件系统满没满；不要 `rm -rf /var/log/*`，也不要对持有已删除文件的服务 `kill -9`；不要把 `vmstat` 第一行、`sar` 的 `Average:` 或 `top` 的 load 当瞬时值；不要把 `--disk-usage` 当常量；不要用 `grep suppress` 证明日志没丢；不要用「通知收没收到」判断告警是否工作；不要在告警风暴里先调阈值；不要把 `up=1` 当服务可用；不要用现在的数据解释昨天的现象；不要在时钟未同步时推断先后；不要在生产机上执行 `journalctl --vacuum-*`、`logrotate -f`、改告警规则或建静默。
