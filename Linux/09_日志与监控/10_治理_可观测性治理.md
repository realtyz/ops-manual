# 可观测性治理

下面出现的实测数字取自 Ubuntu 24.04.5 LTS（VMware 虚拟机）/ 内核 `6.8.0-139-generic` / systemd 255 / cgroup v2 / root 可用的机器。默认值与路径都按现场取；换发行版、换内核或换托管方式，同一项都要重新核对。

## 1. 没有制度时会怎样

可观测性的组件都是「配置完就跑」的东西：journald 有默认容量，sysstat 有默认保留期，采集器有默认抓取间隔，告警有一条默认路由。**默认值不是承诺，只是没人做决定时的落点**。没有制度时，出的是这六类事：

1. **保留期吃默认值，天数是没人知道的数**。`SystemMaxUse=`/`SystemKeepFree=`/`MaxRetentionSec=` 全为空时，journal 只按容量管（最多占所在文件系统的 10%、上限 4 GiB，不按时间删）；Ubuntu 上 `sysstat` 的 `HISTORY=7`。没有一张写明天数的卡片，就没人答得出「三个月前那次故障的日志还在不在」，也没人知道合规要求的 180 天到底满足没有。
2. **采集静默停止，复盘时才发现没有历史**。`/var/log/sysstat/` 里没有当天的 `sa<DD>`、`/var/log/journal` 不存在（`Storage=auto` 退化成内存存储，重启即丢）、日志采集器的队列满而丢弃——这三种失败都不报错。发现的时间点通常在事故之后，那时已经补不回来。
3. **基数的增长没有归属，成本自己长**。给指标加一个 `path` label（几百个取值）就是几百倍时序，加 `user_id` 是几十万倍。没有上限、没有 owner、没有评审，账单和查询延迟一起涨；更麻烦的是**历史数据已经写进去了，事后清理不了**。
4. **告警全部汇到一个渠道，最后被静音**。没有分级、没有按服务路由、没有 Runbook，值班的人只有两个选择：一直看，或者把渠道静音。静音之后，真正影响用户的告警也一起消失了。
5. **没有目标，「先修哪个」由嗓门决定**。CPU 打满与用户请求失败率上升，在一条只有机器水位的看板上看起来一样重要。没有 SLO，优先级就只能靠会议上谁声音大，技术债与稳定性投入也排不进计划。
6. **止血时销毁证据**。磁盘满了先 `rm -rf /var/log/*`，空间紧张先 `journalctl --vacuum-time=1s`，故障一出现先重启——动作都很快，但复盘要用的日志、进程状态与连接现场一起没了。「现象消失」被记成了「问题解决」。

这六条的共同点：**它们都不是知识问题，而是产物缺失**。有基线卡就能回答「之前是什么、现在是什么」；有三个成本数字就能回答「谁在管、上限多少、什么时候复核」；有告警规范就能回答「这条告警该发给谁、要做什么」；有 SLO 卡就能回答「这个月还能不能发版」。

## 2. 行业通行做法

不同组织的规范差别很大，但方向是一致的：

- **规则与看板当代码管**：告警规则与记录规则进版本控制、走评审、在流水线里做语法校验与单元测试（`promtool check rules`、`promtool test rules`、`amtool check-config`）。改规则与改代码用同一套流程，才有回滚点与责任人。
- **SLI 从用户视角定义，SLO 当决策工具**：指标选用成功率、延迟分位数这类用户能感知的量，而不是机器水位；目标用来决定「能不能发版、先修哪个」，不用来考核团队。目标值由「用户能接受什么」反推，再由架构投入评估能不能守住。
- **多窗口、多消耗速率的告警**：一个短窗口加一个长窗口同时超阈值才升级为立即处理，长窗口单独超阈值只排期。这样既不在小流量时疯狂误报，也不漏掉「今天已经烧掉一半预算」。
- **每个信号与每个成本数字都有 owner**：日志保留天数、指标基数上限、追踪采样率各有归属，并有复核日期。没有 owner 的数字会在几个月内变成没人敢动也没人知道来历的配置。
- **按紧急度分层，而不是只有一个渠道**：明确区分「现在就要有人起来处理」与「明天上班处理」。只有一个渠道等于没有分级。
- **让采集本身可观测**：抓取成功与否（`up`）、抓取耗时、目标数量、日志采集器的队列与丢弃计数、当天有没有历史文件——这些是「监控的监控」，缺了它们，故障时你会先怀疑数据本身不可信。
- **保留期显式声明**：不接受「默认会留很久」这种假设，容量上限与保留时间写进配置与文档，并核对接收到的时间。
- **采样策略写清楚**：头部采样与尾部采样各自丢什么、错误请求是否补偿采样、采样率依据是什么，都要写下来，否则「按比例采样」会同时丢掉最需要的那批请求。
- **每次观测记录命令与时间**：观测即证据，证据要留痕；结论必须能被另一条命令复现。
- **取证与止血分开**：先只读取证，再做回收与重启；两件事分别记录，避免把「现象消失」当成「根因消除」。
- **基线随变更一起更新**：任何一次影响观测面的变更（换日志落点、改保留期、加采集目标、改路由）都在变更单里带一次新的基线采样，否则基线卡会在几个月内失效而不自知。
- **定期做一次「没有监控也能查」的演练**：至少确认一遍「只有一台机器、只有 journald 与 sysstat，能不能把昨天的事故还原出来」。中心平台不可用时，这种能力是唯一的退路。
- **把观测面的接口写进上线检查表**：新服务上线要求给出日志落点、指标端点、告警负责人、SLI 口径四样东西，而不是等出事后补。这四样与「最小可用的可观测性体系」一一对应。

这些方向的原始材料可以在 Google SRE 系列（服务目标、承担风险、事后复盘）、SRE Workbook 的 SLO 告警实践、Prometheus 与 Alertmanager 官方文档、OpenTelemetry 的采样文档，以及各发行版的日志与性能文档里找到。**它们给的是方向，不是统一标准**：值班模型、合规要求、机器规模不同，阈值与流程都要按自己的环境重新评估。

## 3. 治理产物四件套

### 3.1 可观测性基线卡

**用途**：回答「这套观测当前是什么状态」，给变更、巡检与复盘提供可比对的旧值。

**字段**（每一项都要写清取值来源与采样时刻）：

| 分组 | 字段与取值来源 |
| --- | --- |
| 环境标识 | 主机名、发行版与版本（`/etc/os-release`）、内核（`uname -r`）、systemd 版本（`systemctl --version`）、cgroup 版本、采集时刻（`date -Is`） |
| 日志落点与持久化 | 服务的落点属性（`systemctl show <unit> -p StandardOutput -p StandardError`）、持久化目录是否存在（`ls -ld /var/log/journal`）、生效配置的容量与限流项（`systemd-analyze cat-config systemd/journald.conf` 里的 `Storage=`/`SystemMaxUse=`/`SystemKeepFree=`/`MaxRetentionSec=`/`RateLimitIntervalSec=`/`RateLimitBurst=`）、实际占用（`journalctl --disk-usage`） |
| 轮转与保留 | 在用的轮转规则（`/etc/logrotate.d/` 的清单与 `logrotate -d` 的 dry-run 输出）、保留份数与压缩（`rotate`/`compress`/`delaycompress`）、状态文件（`/var/lib/logrotate/status`）、执行记录（`systemctl show logrotate.service -p ExecMainStartTimestamp`） |
| 历史采集 | 历史目录里有没有当天的文件（`ls -l /var/log/sysstat/`）、保留天数（`/etc/sysstat/sysstat` 的 `HISTORY=`）、采集定时器的下次与上次触发（`systemctl list-timers sysstat-collect.timer` 的 `NEXT`/`LAST`） |
| 指标采集 | 抓取目标与结果（`up`）、目标数量（`/api/v1/targets` 或对 `up` 计数）、单次抓取耗时与样本量（`scrape_duration_seconds`、`scrape_samples_scraped`） |
| 告警链路 | 规则文件的校验状态（`promtool check rules`）、当前处于各状态的数量（`ALERTS` 按 `alertstate` 计数）、路由与静默现状（`amtool config routes show`、`amtool silence query`） |
| 时间基线 | 时区（`timedatectl`）、同步状态（`System clock synchronized` 与 `NTPSynchronized`）、同步源与估计误差（`timedatectl timesync-status` 的 `Server`/`Packet count`/`Root distance`） |

```bash
journalctl --disk-usage                                  # 验证：journal 实际占用（不覆盖 /var/log/*.log）
systemctl list-timers sysstat-collect.timer --no-pager   # 验证：历史采集的下次与上次触发
timedatectl timesync-status                              # 验证：同步源、轮询区间与估计误差
```

**判据**：基线卡的价值在**同口径重复采样**。任何「变了没有」的判断都来自两次同口径采样的差值。两条采样要写清同一条命令、同一台机器、同一时区与同一个时间窗；不同口径之间不能直接比较——`systemctl show` 读不到 journald 的配置项（这些不是 unit 属性，会返回空而退出码仍是 0），配置文件里的值也不等于生效值。采集频率建议是变更前后各一次、日常巡检每周一次。

基线卡落地成巡检项（全部只读，生产机上也可以做）：

- `/var/log/sysstat/` 里有没有当天的 `sa<DD>`，文件大小有没有在长；
- `systemctl is-enabled sysstat-collect.timer` 是不是 `enabled`，`list-timers` 的 `LAST` 是不是最近的整十分；
- `/var/log/journal` 是否仍存在（它消失就意味着退化成内存存储）；
- `journalctl --disk-usage` 相对上一次采样的变化幅度；
- `/etc/logrotate.d/` 里每条规则都有 `compress` 与明确的 `rotate` 份数；
- `df -hT` 里 `/var/log` 是否独立文件系统，使用率落在哪一档水位；
- `up=0` 的目标有几个，`scrape_duration_seconds` 相对基线有没有明显变长；
- `prometheus_tsdb_head_series` 相对基线的增长，以及最近有没有新增 label；
- `ALERTS` 里各 `alertstate` 的数量，有没有长期停在 `pending` 的条目；
- `amtool silence query` 里有没有超过期限仍在生效、或没有创建人的静默；
- `timedatectl` 的两行是否分别正常，`timesync-status` 的 `Packet count` 与 `Root distance` 是否可信。

### 3.2 保留与成本策略

**用途**：把「这套观测要花多少钱、磁盘够不够」变成三个有归属、有依据、有复核日期的数字。

| 数字 | 取值与依据 | owner | 复核 |
| --- | --- | --- | --- |
| 日志保留天数（按层） | 应用日志 7 天、错误日志 30 天、审计日志 180 天（合规）。依据：日均写入量 × 保留天数 × 压缩比 | 日志归属团队 | 每季度，或合规要求变化时 |
| 指标 cardinality 上限 | 活跃时序数上限（从 `prometheus_tsdb_head_series` 读）。参照：单机一台 4 vCPU 空闲机器的 `node_exporter` 就有约 1500 行非注释指标，1000 台就是 150 万条时序的量级（1574 × 1000 ≈ 157 万） | 平台归属团队 | 每季度，或新增高基数 label 时 |
| 追踪采样率 | 核心链路 10%、错误请求 100%（尾部采样）。依据：日均请求数 × 采样率 × 每 trace 平均 span 数 | 应用归属团队 | 每季度，或后端容量变化时 |

保留要配三层，缺一层都不成立：

| 层 | 在哪配 | 控什么 | 缺了会怎样 |
| --- | --- | --- | --- |
| 应用层 | 日志级别与输出目标（生产不开 debug，保留临时调级别的能力） | 产生速率 | 源头量失控，后面两层都在追 |
| 收集层 | journald 的 `SystemMaxUse=`/`SystemKeepFree=`/`MaxRetentionSec=` | 系统日志的总量与时间 | 默认只按容量管（文件系统的 10%、上限 4 GiB，不按时间删），「留 30 天」这类要求做不到 |
| 文件层 | logrotate 的 `rotate`/`size`/`compress`/`delaycompress` | 自建日志的份数与压缩 | 归档无限增长，正在写的文件仍是原大小 |

**分盘与容量**：`/var/log` 应当独立挂载（`findmnt -T /var/log`）；同盘时日志写满会让整机的 journald、sshd 与审计一起写不进去。做容量账要扣掉文件系统的保留块——ext4 默认给 root 留 5%，普通用户可用的空间小于 `df` 显示的总量。本机实测 `/var/log` 与业务数据同在 48.0 GiB 的根文件系统上，未分盘。

**水位告警两档**：使用率高于 80% 是 warning（排期清理），高于 90% 是 critical（立刻处理）；对象既包括文件系统使用率，也包括 journal 相对基线的增长。

**三个数字怎么来的**（写清假设比写清结果更重要）：

- 日志保留天数：日均写入量（MiB/天）× 保留天数 × 压缩比，再按层分别算——错误日志留久、访问日志留短；压缩只降低归档体积，正在写的文件仍是原大小。
- 指标 cardinality 上限：当前活跃时序数乘以一个可接受的增长系数；上限定在「再涨一倍也不会拖垮查询」的位置，而不是定在当前值上。
- 追踪采样率：日均请求数 × 采样率 × 每 trace 平均 span 数，再核对后端能接住的写入量；错误请求单独补偿采样，不跟着整体比例被削掉。

估算的每一项都要标注是实测还是推演：本机的锚点是单机约 1500 行非注释指标、单次抓取约 95 毫秒、`journalctl --disk-usage` 在几十 MiB 量级、根文件系统 48.0 GiB。按这些参数算出来的「每天多少样本、一年多少存储」都是**算术推演，不是实测账单**。

**判据**：三个数字都要同时回答「谁负责」与「下次什么时候复核」；拿它们与实际账单、实际磁盘增长对一次，差异超过 2 倍就说明假设错了。**实测边界**：真正的跨机日志集中、日志平台的保留分层、追踪后端容量、云监控与云日志的计费口径，本机都未实测；RHEL 系的 `sysstat`/`rsyslog`/对时默认值也未实测——这几项要在自己的环境里取现场值。

### 3.3 告警规范

**用途**：让每条告警都对应一个动作与一个责任人，让「现在处理」与「排期处理」的分界不靠感觉。

| 项目 | 要求 | 反例 |
| --- | --- | --- |
| 命名 | `<级别>-<对象>-<现象>`，例如 `critical-node-disk-full` | `Alert_1` |
| `severity` | 统一取值：`critical`/`warning`/`info` | 自定义一堆级别 |
| `summary` | 一句话说清「什么坏了、影响什么」 | 「指标异常」 |
| `description` | 关键数值 + Runbook 链接 | 只有规则表达式 |
| 路由 | 按服务或团队路由到不同 receiver | 全部塞进一个群 |
| 抑制 | 只表达确定的因果关系，必须写 `equal` 限定对象 | 「critical 压掉所有 warning」 |
| 静默 | 带期限、原因、创建人，到期复查 | 永久静默 |
| 复盘 | 误报与漏报都要复盘（阈值、`for`、窗口、采集间隔） | 只在出事故时复盘 |

**分层规则**：

| 层 | 触发方式 | 允许的通知 |
| --- | --- | --- |
| 预算快烧 | 短窗口与长窗口同时超过消耗速率阈值 | 立即处理，可以打扰休息时间 |
| 预算慢烧 | 长窗口的消耗速率超阈值 | 工单或排期，不打扰休息时间 |
| 基础设施水位 | 磁盘、内存、句柄、证书、`up`，按影响面分级 | 有明确处置动作时才升级为立即处理 |
| 单点抖动 | `for` + 分位数 + 持续窗口过滤 | 留在看板上，不发通知 |

**规则**：只有影响用户的告警才允许 page（打扰休息时间）；做不到「第一步跑什么、看哪个面板、找谁」的告警，要么补 Runbook，要么删掉或降级成看板上的指标。分级与路由的顺序不能反：先分组去重，再抑制，再静默，最后才是通知。

每条告警在规范文档里登记这些字段：

| 字段 | 写什么 |
| --- | --- |
| 告警名与规则文件 | 规范里的命名，以及规则所在文件与所在仓库的路径 |
| 判据 | 表达式、`for`、窗口，以及「看到这个值意味着什么」的一句解释 |
| 分层 | 属于预算快烧、预算慢烧、基础设施水位还是抖动过滤 |
| 通知级别 | 立即处理还是排期，路由到哪个 receiver |
| Runbook | 第一步跑什么、看哪个面板、找谁 |
| owner | 服务的责任人，与 SLO 卡上的责任人一致 |
| 抑制关系 | 与哪些告警构成确定的因果关系，`equal` 用哪些 label |
| 最近一次复盘 | 上次误报或漏报的时间与结论、改动了哪一项 |

### 3.4 SLO 定义卡

**用途**：把「服务够不够好」变成可以计算、可以用来做发布决策的东西。

| 字段 | 说明 |
| --- | --- |
| 服务 | 卡片约束的对象，一张卡只对一个服务或一条关键路径 |
| SLI 表达式与口径 | 用哪条表达式算、哪些请求算、哪些不算（健康检查、内部心跳、压测流量通常排除） |
| 统计窗口 | 滚动窗口还是自然月，长度多少；窗口决定预算额度 |
| 目标 | 成功率或分位数的目标值 |
| 错误预算与换算 | `1 - 目标` 对应的允许额度，换算成时间或请求数 |
| 告警 | 快烧与慢烧各自的窗口、阈值、`severity`、路由 |
| 责任人 | 服务 owner，以及复核这张卡的人 |
| Runbook 链接 | 预算被消耗时第一步做什么 |
| 复核周期 | 多久重新评估目标与口径 |

30 天窗口下「几个 9」的换算：

| 目标 | 30 天允许的不达标时间 |
| --- | --- |
| 99% | 约 432 分钟 |
| 99.9% | 约 43.2 分钟 |
| 99.99% | 约 4.32 分钟 |
| 99.999% | 约 25.9 秒 |

这张表是 `窗口长度 × (1 - 目标)` 的**算术推演，不是实测的停机时间**，与任何机器无关；真实的「本月已经不可用了多久」要用 SLI 的时序数据算。多一个 9，允许的不达标时间少一个数量级——所以目标必须和架构投入一起评估。

**判据**：卡片可用的唯一判据是**能不能回答「这个月还能不能发版」**。答不上来，说明它只是文档，不是决策工具。判断依据是消耗速率与剩余额度，而不是当前值——「现在仍然达标」是静态视角，按当前速度下去本月会超支时，该做的是拆小变更或延后。

SLO 卡要配一本可滚动的错误预算台账，让「还剩多少」随时可查：

| 台账列 | 说明 |
| --- | --- |
| 统计窗口与起止 | 滚动窗口的边界，或自然月的起止日期 |
| 已消耗额度 | 按 SLI 时序算出的不达标时间或失败请求数 |
| 剩余额度 | 预算减去已消耗；为负即已耗尽 |
| 消耗速率 | 当前速率相对预算允许水平的倍数，分快、慢两个窗口看 |
| 消耗来源 | 最近几次消耗分别来自什么：发布、依赖抖动、演练、容量不足 |
| 决策记录 | 每次「发布 / 延后 / 拆灰度」的决定、依据与决定人 |
| 复核时间 | 下次重新评估目标与口径的日期 |

## 4. 关键字段的治理用法

字段本身的读写与单位在各原理篇与体系篇；这里讲**怎么用它们做决定**。

| 字段或命令 | 治理时怎么用 |
| --- | --- |
| `systemd-analyze cat-config systemd/journald.conf` | 判断容量与限流真正来自哪个文件；改配置前先确认它有没有被 drop-in 覆盖 |
| `SystemMaxUse=`/`SystemKeepFree=`/`MaxRetentionSec=` | 保留策略里「收集层」的唯一生效来源；默认是空（10%、上限 4 GiB、不按时间删），要写进策略而不是吃默认值 |
| `journalctl --disk-usage` | journal 实际占用的唯一入口，也是基线卡里那个可比较的值；它不覆盖 `/var/log/*.log` |
| `ls -l /var/log/sysstat/` | 「有没有历史」的最便宜判据；`sa<DD>` 的 `DD` 是「日」不是序号，跨月要小心 |
| `ls -ld /var/log/journal` | 持久化是否成立的唯一判据；它不存在时 `Storage=auto` 会写内存，重启即丢，而且不会报错 |
| `findmnt -T /var/log` | 判断日志与业务数据是不是同一个文件系统；分盘是容量风险的第一道隔离 |
| `/var/lib/logrotate/status` | 轮转上次执行的时刻与对象；「该轮转却没轮转」的判据要用它加 `ExecMainStartTimestamp`，不要用 `ConditionResult` |
| `HISTORY=` | 复盘窗口的上限；Ubuntu 默认 7 天，要留两周以上必须显式改，并核对磁盘容量 |
| `list-timers` 的 `NEXT`/`LAST` | 采集定时器是不是真的在跑；`NEXT` 为空或 `LAST` 停在很久以前，就是采集停了 |
| `up` | 采集链路的健康度；`up=0` 与「指标值异常」是两件事，前者说明后面所有结论都没有数据支撑 |
| `scrape_duration_seconds`/`scrape_samples_scraped` | 抓取成本与目标规模；它们随目标数与负载变化，不能当常数用 |
| `prometheus_tsdb_head_series` | 当前活跃时序数，就是那个要写上 owner 与上限的数字 |
| `ALERTS` 与 `amtool silence query` | 分别回答「算出来没有」与「被压掉没有」；两者都为空时不要下「告警链路正常」的结论 |
| `promtool check rules`/`promtool test rules` | 规则上线前的两段验收：语法通过不等于算得对，还要用合成序列做单元测试 |
| `timedatectl` 的两行 | 时间可信度；未同步时不要写下「A 比 B 早发生」这类结论 |
| `df -hT` 与 `Reserved block count` | 容量账要扣掉 ext4 的 5% 预留块；`df` 的总量不等于可写总量 |

## 6. 具象治理场景与要交出的产物

### 场景一：新服务上线，保留期与告警归属都是空的

**背景**：一个自研服务要上线，日志写 stdout 由 journald 收，指标由自己的 `/metrics` 暴露。没有人说过日志留多久、时序上限多少、告警发给谁；上线评审只看了功能。

**做法**：上线前先按同一口径采一次基线卡；把三个成本数字写进评审材料并各自指定 owner；新服务的告警按规范补上命名、`severity`、`summary`、`description` 里的 Runbook 链接与路由；`/var/log` 是否分盘、水位告警两档作为上线前置项核对。**不要用「默认能跑」当验收**——默认值能跑，只是没人知道上限在哪。

**产出**：

- 这份服务的可观测性基线卡（按基线卡的七个分组逐项填，附采样时刻）
- 三个数字：日志保留天数、指标 cardinality 上限、追踪采样率，各带依据、owner 与复核日期
- 告警规范里属于该服务的那几行（命名、统一 `severity`、`summary`、Runbook 链接、路由到哪个 receiver）
- 上线评审记录里的容量与成本结论（含 `/var/log` 是否分盘、水位告警两档、是否设了 `SystemMaxUse=`）

### 场景二：复盘时才发现历史根本没在采

**背景**：业务反馈「昨晚 3 点左右系统变慢」。登录后 `sar -u -s 03:00:00 -e 04:00:00` 是空的，`ls -l /var/log/sysstat/` 里只有今天的 `sa<DD>`；`timedatectl` 显示 `System clock synchronized: no`，NTP 服务却在跑。故障已经恢复。

**做法**：先查清「为什么没采」——采集定时器是否 `enabled`、`SA_DIR` 的权限与磁盘空间、`HISTORY=` 是否够长、有没有被轮转清掉；再把「采集本身可观测」变成一条带判据的巡检项；把保留天数按复盘窗口改长，同时核对磁盘容量；这次复盘只能用日志与其他来源交叉印证，结论里必须写明「历史缺失」这个边界。**不要用现在的 `top` 去解释昨晚的现象**。

**产出**：

- 一条写清判据的采集巡检项：`/var/log/sysstat/` 有当天的 `sa<DD>`、`systemctl is-enabled sysstat-collect.timer` 为 `enabled`、`list-timers` 的 `LAST` 是最近的整十分
- 一份保留期变更记录（`HISTORY=` 的旧值与新值、依据的复盘窗口、磁盘容量核算、验证方式）
- 一份复盘记录（现象与影响面、可用证据与缺失证据、根因、止血动作、修复动作、下一步要补的采集与告警）

### 场景三：计划发布前，错误预算快烧完了

**背景**：核心服务的 SLO 是「30 天滚动成功率 ≥ 99.9%」，也就是 30 天允许约 43.2 分钟不达标（算术值）。本月刚过 10 天已经掉到 99.93%，下周有一个大版本发布。

**做法**：用 SLI 的时序算出已消耗的预算比例与消耗速率，而不是看当前值；对照快烧与慢烧两档告警，确认自己会不会早知道；再决定发布方式——灰度拆分、延后、或按原计划但准备好回滚；不通过修改目标来规避超支，如果目标确实要调整，按用户预期的变化重新评估并记录理由。**不要用「现在仍然达标」当结论**。

**产出**：

- 一份 SLO 定义卡（服务、SLI 表达式与口径、窗口、目标、错误预算换算、责任人、Runbook、复核周期）
- 快烧与慢烧两条告警规则（窗口、阈值、`severity`、路由），并经过语法校验与单元测试
- 一份发布决策记录（剩余预算、消耗速率、发布方案与灰度比例、回滚条件、观察窗口、决定人与依据）

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 保留期吃默认值 | journald 默认只按容量管（所在文件系统的 10%、上限 4 GiB，不按时间删）；Ubuntu 上 sysstat 默认 `HISTORY=7`。要求「留 30 天」时必须在配置里显式写出来 |
| 「采集在跑，不用管」 | 采集失败是静默的：`sa<DD>` 缺失、`/var/log/journal` 不存在导致退化成内存存储、采集器队列丢弃都不报错；必须有巡检项 |
| 「日志集中了本机就不用配保留」 | 发送端与接收端都会落盘；集中只是把容量风险搬到中心机，不是消除风险 |
| 「磁盘还够，先不设上限」 | 基数与日志量的成本是累积的，历史数据写进去之后很难清理 |
| 给业务指标加 `user_id`、`request_id`、完整 URL 做 label | 时序数按 label 取值组合相乘增长；高基数信息应当进日志或追踪，不进指标 label |
| 「加磁盘就能解决」 | 增长率不变的话很快再次撞墙；要先回滚影响最大且最容易回滚的一项（通常是采集频率或高基数 label） |
| 所有告警路由到同一个渠道 | 没有分级就没有优先级，结果是把渠道静音，真正影响用户的告警也一起消失 |
| 告警只有 `summary` 没有 Runbook | 收到的人还得从零排查；做不到「对应一个动作」的告警应当删掉或降级成看板指标 |
| 用永久静默「解决」噪声 | 静默带期限、到期会恢复；真正的噪声要靠修规则并复盘 |
| 抑制写成「critical 压掉所有 warning」 | 会压掉不相关的真故障；抑制只表达确定的因果关系，并且要写 `equal` 限定对象 |
| 只复盘误报，或只在出事故时复盘 | 漏报与误报的原因常常相同（阈值、`for`、窗口、采集间隔）；两者都要复盘 |
| 修改 SLO 目标来规避超支 | 等于取消了这个指标的意义；目标可以调，但必须基于用户预期的重新评估并留记录 |
| 把换算表当成实测可用性 | 表里是「窗口长度 × (1 - 目标)」的算术结果；真实可用性要靠 SLI 的时序数据算 |
| 磁盘满了先 `rm -rf /var/log/*` 或先 vacuum | 删除会带走复盘要用的证据；先取证（`df -hT`/`df -i`/`du`，以及 `lsof` 里「已删除但仍被打开」的那一份清单）再回收 |
| 在时钟未同步的机器上做跨机时间线结论 | 先后顺序可能是反的；先看 `System clock synchronized` 与 `timesync-status` 的 `Packet count` |
| 用 `df` 的总量做容量账 | ext4 默认给 root 留 5% 预留块，普通用户可用空间小于显示值 |

## 要点自测

**问：一张可观测性基线卡至少要能回答哪几个问题？**
答：这套观测的日志落在哪、会不会持久化、容量与保留是多少；轮转规则是哪些、保留几份；历史采集有没有当天数据、保留几天、定时器上次与下次触发是什么时候；抓取哪些目标、成功率与耗时如何；有多少条告警、处于各状态的数量；时间基线可不可信。判据是「同一口径重复采样时能看出变化」。

**问：为什么基线卡强调「同口径」？**
答：因为「变了没有」只能由两次同口径采样的差值回答。不同口径之间不能直接比较：`systemctl show` 读不到 journald 的配置项（不是 unit 属性，返回空而退出码仍是 0），配置里写的值也不等于生效值，`sadf -d` 导出的时间戳恒定是 UTC 而 `sar` 的窗口按本地时区解释。

**问：保留策略要配哪三层？缺一层会怎样？**
答：应用层控产生速率（日志级别、生产不开 debug）；收集层控系统日志的总量与时间（`SystemMaxUse=`/`SystemKeepFree=`/`MaxRetentionSec=`）；文件层控自建日志的份数与压缩（`rotate`/`size`/`compress`）。缺应用层，源头量失控；缺收集层，默认只按容量管且不按时间删；缺文件层，归档无限增长。

**问：三个成本数字是哪三个？每个必须带哪两样东西？**
答：日志保留天数、指标 cardinality 上限、追踪采样率。每个都要有依据（写入量 × 天数 × 压缩比、活跃时序数、请求数 × 采样率）与 owner，并有复核日期；没有 owner 的数字会在几个月内变成没人敢动的配置。

**问：一条告警要满足什么条件才允许打扰休息时间？**
答：它必须对应「用户正在受影响」这件事，并且有明确的处置动作与责任人。机器水位类的告警只在有确定动作时才升级；单点抖动只留在看板上。做不到「第一步跑什么、看哪个面板、找谁」的告警应当删掉或降级。

**问：怎么判断一张 SLO 卡是不是真的在被使用？**
答：看它能不能回答「这个月还能不能发版」，以及判断依据是消耗速率与剩余额度还是当前值。只能回答「现在达标」的卡没有决策能力；把目标当考核指标、或事后改目标来规避超支，都是它没被正确使用的信号。

**问：磁盘满了，为什么不能先删日志？**
答：删除会同时删掉复盘要用的证据，而「空间回来了」只是止血。正确顺序是先用只读命令取证（`df -hT`、`df -i`、`du -xsh /var/log/*`，再用 `lsof` 找已删除但仍被打开的持有者）分清是哪一类原因，保留最近一段日志，再做回收；回收之后仍要补上保留策略、分盘与水位告警。

**问：一条告警在规范文档里至少要登记哪些字段？**
答：告警名与规则文件、判据（表达式与 `for`）、所属分层、通知级别与路由、Runbook、owner、抑制关系（含 `equal` 用哪些 label）、最近一次复盘的时间与结论。登记的用处是让「这条告警该不该存在」可以被追问，而不是只能靠值班的人凭感觉判断。

**问：为什么要求在只有一台机器时可复盘的「退路演练」？**
答：中心平台、日志平台与追踪后端都可能不可用，或者根本没建成（本机的跨机集中、日志平台与追踪后端都未实测）。此时能依靠的只有本机的 journald 与 sysstat；如果这台机器上的保留期是默认值、历史采集没人巡检，退路就是空的。演练的内容很具体：只用一个界面，把昨天某个时刻的日志与资源水位查出来。

**第一反应不要做什么**：不要吃默认保留期；不要以为采集一定在跑；不要在没有 owner 的情况下上采集；不要给指标加高基数 label；不要把告警全塞进一个渠道；不要用永久静默处理噪声；不要用抑制代替分组；不要只复盘误报或只复盘事故；不要用平均值定义目标；不要改目标来规避超支；不要在磁盘满时先删日志；不要在时钟未同步时做跨机时间线结论；不要用 `df` 的总量做容量账。
