# 日志的诞生

## 1. 落点在「写出来」那一刻就决定了

一条日志在应用决定「往哪写」的那一瞬间，它后面所有的可能性就基本定下了：能被谁收集、能带上哪些字段、能保留多久、能不能按字段查询、写满时谁负责。这不是实现细节，而是三种落点各有各的收集链，而收集链决定了字段。

```mermaid
flowchart TD
  A["应用产生日志"] --> B{"往哪写"}
  B -- "stdout / stderr" --> C["systemd 收进 journald<br/>（再有选择地转给 rsyslog）"]
  B -- "自己的日志文件" --> D["由 logrotate 轮转<br/>由采集端搬运"]
  B -- "syslog 套接字" --> E["journald 与 rsyslog 都能收<br/>取决于是否开启转发"]
```

**关键区别不在「方便不方便」，而在「字段由谁产生」**：写 stdout 的日志，字段（单元、优先级、开机标识、单调时间戳）是收集端**自动加上**的；写自有文件的日志，字段只能靠**事后解析文本**得到；写 syslog 套接字的日志，字段取决于协议本身能带什么。

这解释了一个常见困惑：同一个标识符过滤出的消息可能来自不同通道。journald 用 `_TRANSPORT` 字段记录消息是从哪条路进来的（`stdout`/`syslog`/`kernel`/`audit`），所以「这条日志为什么没有某个字段」往往在它被写出来的那一刻就注定了。

| 落点 | 谁负责收集 | 优点 | 代价 |
| --- | --- | --- | --- |
| stdout / stderr | systemd → journald（可选再转 rsyslog） | 不用自己管文件、自动带字段、容器化最推荐 | 依赖收集端的持久化配置；容量由收集端统一管 |
| 自有日志文件 | 自己 + 轮转工具 + 采集端 | 格式自由、直观、可直接查看 | 字段化要靠解析；轮转要自己维护；写满风险自己担 |
| syslog 套接字 | journald 与 rsyslog | 系统级通道，两边都能收 | 要理解 facility/severity 与转发配置；结构化能力弱 |

### 1.1 容器里为什么只能写 stdout

容器的最佳实践是**应用只写 stdout/stderr，其他什么都不管**：容器运行时负责收集，宿主机上的采集端负责搬运，日志的生命周期不依赖容器内的磁盘。

理由不是「方便」，而是**生命周期**：容器内的文件系统随容器销毁一起消失。在容器里写自有文件，等于把日志的存活期绑定到容器的存活期——重启即丢，而且丢失是无声的。stdout 把日志的所有权交给运行时，这是唯一能让日志活得比容器久的写法。

## 2. facility 与 severity：syslog 的两个正交维度

syslog 协议用两个正交的概念描述一条日志，理解它们是理解 `PRI`、过滤规则与转发规则的前提：

- **facility（设施）表示「谁产生的」**：内核、用户态、邮件、认证、定时任务等，各占一个编号；
- **severity（严重程度）表示「多严重」**：从 `emerg`（0）到 `debug`（7），数字越小越严重。

两者被编码进报文的 `<PRI>` 字段：**PRI = facility × 8 + severity**。`<13>` 就是 `1×8 + 5`，即 facility=user、severity=notice。

这个编码方式有两个实务含义：

1. **数值小的 severity 更严重**，与「数字越大越严重」的直觉相反。写阈值过滤时「`-p err` 及以上」指的是 0–3 这一段。
2. **PRI 是唯一一个「谁产生的 + 多严重」压成一个数的字段**，所以它既能做来源过滤也能做级别过滤。远程接收端按 PRI 分流是最省事的做法。

RFC 5424 在旧格式（RFC 3164）基础上补上了两样关键东西：**带时区偏移的时间戳**，以及**结构化数据**（例如 `timeQuality`）。旧格式连年份都没有，跨年、跨时区的数据基本无法自动对账——这也是为什么对账能力强的新格式值得多占几个字节。

## 3. 可检索性：字段而不是句子

排障时最痛的不是「日志太少」，而是**「日志里有信息但没有字段」**。

对比两条日志：

```text
User 12345 failed to login at 10:31
{"ts":"2026-09-19T10:31:02Z","level":"warn","service":"auth","instance":"web-03","event":"login_failed","user_id":12345,"reason":"bad_password"}
```

第一条人读得懂，但要统计「今天登录失败了多少次」，只能写正则去猜——而正则与句子结构强耦合，句子一改就断。第二条的每个字段都可以直接过滤、聚合、告警。

一条可排障的日志最低要带这几项，每一项都对应一种排障动作：

| 字段 | 对应的排障动作 | 缺失的后果 |
| --- | --- | --- |
| 时间（统一 UTC 或带时区） | 与其他证据对齐 | 跨机、跨系统的时间线拼不起来 |
| 级别 | 只看错误、按级别告警 | 无法过滤；生产开 debug 又会淹没一切 |
| 服务 / 应用名 | 按服务切分 | 集中之后无法区分来源 |
| 实例（host / pod / 副本） | 横向对比 | 找不到「只有一台不对」的问题 |
| 请求 ID（最好带追踪 ID） | 把一次请求的日志串起来 | 多副本并发时无法归到同一次请求 |
| 错误码 / 事件名 | 可检索、可统计 | 只能文本搜关键词，口径随措辞变化 |

**JSON 行是最省事的折中**：一行一条记录、字段名固定，人读得懂，采集端也能直接解析。这里要澄清一个常见误解：**收集端不会自动把正文里的 JSON 拆成可查询字段**——正文仍然是正文，字段化要靠收集端或平台的解析能力配合。所以「用 JSON 行」只是把解析从「猜结构」降级成「读键值」，不是免掉解析。

### 3.1 级别是成本开关，不是装饰

日志级别最容易被当成「格式要求」，其实它是**日志成本最主要的旋钮**：

- **应用层是三层保留策略里唯一管「产生速率」的那一层。** 后两层（收集端容量、文件轮转）能做的只是「把已经产生的量裁掉」，裁不赢产生速度。
- **生产开 debug 的代价不是「日志多点」，而是把关键错误淹没**，同时在磁盘与网络两处放大成本。
- **正确的做法是保留「临时打开 debug」的能力**（动态调级别、按请求开启），而不是常开或永远关掉。

对外输出的高频无关信息（例如每个成功请求一行）应当降级或直接去掉；这类日志的量通常比错误日志大几个数量级。

## 4. 一条不该越过的线：别用日志解析做指标

「日志里什么都有，那我解析一下不就有指标了？」这是最自然、也最贵的一个想法。

| 想法 | 现实 |
| --- | --- |
| 「一次解析，什么指标都能算」 | 解析规则与日志文本格式强耦合；应用改一行格式，指标就断了 |
| 「反正日志已经存了，解析不要钱」 | 解析要 CPU 与内存，还要为「可能用到的字段」付出存储与索引成本 |
| 「口径随时能改」 | 恰恰不能：一旦用它做告警与 SLO，历史口径变更会让数据不可比 |

三条代价里，**第一条最危险，因为它静默失败**：解析规则失效时指标不会报错，只会归零或变小——往往等到告警阈值再也不触发、或者报表变成 0 才被发现。

正确的分工是：**日志负责「发生了什么」（细节、堆栈、个案），指标负责「多严重、从什么时候开始」（请求数、错误数、延迟分布、队列深度），而业务指标应该在应用里直接埋点暴露。** 这条线的判断标准很简单：**这个数字将来会不会被用来做告警或 SLO？** 会，就不该从日志里抠。

## 5. 常见误解

| 常见说法 | 事实 |
| --- | --- |
| 「日志里什么都有，不需要指标」 | 日志没有聚合能力，趋势类问题在日志里看不出来 |
| 「生产环境开 debug 方便排障」 | 体积与成本飙升，关键错误被淹没；调试信息应能按开关临时打开 |
| 「日志只写一句话就好」 | 没有级别、实例、请求 ID 的日志无法过滤、无法聚合、无法告警 |
| 「容器里写自己的日志文件」 | 容器销毁日志一起消失；应写 stdout 由运行时收集 |
| 「用日志解析算错误率」 | 口径与文本格式强耦合，格式一改就断，而且是静默断 |
| 「日志格式以后再统一」 | 格式变更会打断历史口径；一开始就用固定字段成本最低 |
| 「收集端会自动把 JSON 正文变成字段」 | 正文仍是正文；字段化要靠收集端或平台的解析能力 |
| 「PRI 里数字越大越严重」 | 相反：severity 0（`emerg`）最严重，7（`debug`）最轻 |

## 要点自测

**问：应用日志的三种落点分别由谁收集？怎么选？**
答：stdout/stderr 由 systemd 收进 journald（容器化首选，字段自动带上）；自有文件由自己加轮转工具与采集端负责；syslog 套接字由 journald 与 rsyslog 两条通道收。选择标准是「这条日志要活多久、要带哪些字段」——能写 stdout 就写 stdout；必须写文件时，同时把轮转与采集配好。

**问：一条可排障的日志最低要带哪些字段？每个字段对应什么动作？**
答：时间（与其他证据对齐）、级别（过滤与告警）、服务（按服务切分）、实例（横向对比）、请求 ID（把一次请求串起来）、错误码或事件名（可检索可统计）。缺任何一项，都会在对应的排障场景里查不出东西。

**问：为什么不应该用日志解析来做业务指标？**
答：三重代价——解析规则与文本格式强耦合且失效时静默；解析与索引本身要成本；一旦承载告警与 SLO，口径就不能随便改。业务指标准确的做法是在应用里埋点暴露，日志只负责细节。

**问：`<13>` 这个 PRI 表示什么？**
答：PRI = facility × 8 + severity，`13 = 1×8 + 5`，即 facility=user、severity=notice。注意 severity 的数字越小越严重。

**问：为什么容器里写自有日志文件是错的？**
答：日志的存活期会被绑定到容器的存活期，容器销毁日志一起消失，而且丢失是无声的。写 stdout 把日志交给运行时收集，才可能活得比容器久。

**第一反应不要做什么**：不要在容器里写自有日志文件；不要因为「日志里已经有这些信息」就去解析它做指标；不要用「以后统一格式」推迟字段规范；不要把日志级别当成可随意调大的调试开关。

## 参考文档

- RFC 5424：syslog 协议报文结构、facility/severity 的 PRI 编码、结构化数据。
- RFC 3164：旧 BSD syslog 格式（无年份、无时区），用于识别老格式来源。
- `man 3 syslog`、`man 1 logger`：facility 与 severity 的取值、以及构造消息的命令行方式。
- `man 5 systemd.exec`：`StandardOutput=`/`StandardError=` 的取值与目的地语义。
