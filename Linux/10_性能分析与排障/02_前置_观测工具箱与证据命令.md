## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **选命令的第一步不是「哪个工具强」，而是「我要看哪个视角」。**
>   - 怎么验证：拿到一个新现象，先写下「整机 / 单核 / 进程 / 线程 / cgroup」里你缺哪个视角，再从地图里挑命令。
> - **第一分钟的五条命令是固定套路：`uptime`、`vmstat 1`、`mpstat -P ALL 1`、`free -m`、`iostat -x 1`（外加 `ss -s`）。**
>   - 证据：本机一次完整扫描的输出只有 **8208 字节**，却覆盖了身份、负载、每核分布、内存、压力、套接字与软中断；脚本见子笔记 04。
> - **开销要分级：`/proc` 与 `free` 是 L0，采样类命令是 L1，`strace` 是 L2，`perf record` 与抓包是 L3，故障注入是 L4。**
>   - 证据：同一份 workload 直接跑 **50～51 ms**、套 `strace -c -f` 后 **2254～2474 ms**（约 **45～48 倍**），这就是 L1 与 L2 之间的量级差。
> - **「工具没装」不再是本机的处境，但「工具用不了」仍然是常态——只是原因换成了权限与硬件。**
>   - 证据：`perf`、`strace`、`fio`、`bpftrace`、`blktrace`、`tcpdump`、`iotop`、`smartctl`、`numactl` 全部在 `/usr/bin` 或 `/usr/sbin` 下；但 `perf stat -e cycles` 仍是 `<not supported>`（VMware 未透传 PMU 计数器）、裸 `perf stat` 直接报错退出、`realtyz` 跑 `perf` 报 `perf_event_paranoid setting is 4` 后 `exit=255`。
> - **每条证据都要带上「版本 + 窗口 + 条件」，否则事后无法复核。**
>   - 怎么验证：回头看自己的记录，能不能回答「这个 `await=7.44 ms` 是 1 秒窗口还是 5 秒平均、是哪个设备、当时在写多大的块」。

## 1. 命令地图（按视角）

先问「我要看谁」，再问「用哪条命令」。

### 1.1 整机视角：确认「这台机器整体状态」

### 1.5 下钻与注入：确认「具体调用」与「制造现象」

| 命令 | 回答什么 | 开销 | 需要 root | 本机状态 |
| --- | --- | --- | --- | --- |
| `strace -c -f <cmd>` | 系统调用画像（谁最多、谁最耗时） | **L2（实测约 45～48 倍减速）** | 否 | **已安装**（strace 6.8） |
| `strace -T -e trace=<syscall>` | 单次调用的耗时 | L2 | 否 | 已安装 |
| `perf stat -e task-clock,context-switches,page-faults` | 事件计数（软件事件可用，硬件事件需 PMU） | L1 | 否（但本机 `paranoid=4` 会拒非 root） | 已安装（perf 6.8.12） |
| `perf record -F 99 -- <cmd>` + `perf report` | 采样热点函数与调用栈 | L3 | 否（同上） | 已安装，热点定位实测可用 |
| `perf sched record` / `perf sched latency` | off-CPU（等锁、等 IO）与调度延迟 | L3 | **是** | **已实测可用**（root 下采到 **35573 个样本**，`perf sched latency` 与 `timehist` 都有输出） |
| `tcpdump -i <dev> -c 200 -w cap.pcap` | 抓到具体报文 | L3 | 是（或 `CAP_NET_RAW`） | **已安装**（tcpdump 4.99.4），实测抓 12 个包、`0 packets dropped by kernel` |
| `tc qdisc add ... netem delay/loss` | 在**独立 netns** 注入延迟与丢包 | L4 | **netns 需 root** | 已实测可用（root + `ip netns`；非 root 的 `unshare -U -r -n` 被 AppArmor 拒绝） |
| `fio` | 建 IO 基线（顺序/随机 × 读/写 × 队列深度） | L4 | 否 | **已安装**（fio-3.36，`libaio` 引擎可用） |
| `stress-ng` | 造 CPU / 内存 / IO 负载 | L4 | 否 | **已安装**（0.17.06） |
| `blktrace` / `blkparse` | 块层归因（哪个进程、哪个扇区、哪一段延迟） | L3 | **是** | **已安装**（blktrace 2.0.0），实测一次 5 秒采集得到 **139 个事件、7 KiB 数据** |
| `bpftrace` | 低开销全量观测（计数、延迟直方图、off-CPU） | L3 | **是** | **已安装**（v0.20.2），实测三类脚本都能跑（子笔记 13） |
| `iotop -b -n 2 -o` | 按进程看磁盘读写 | L1 | **是** | **已安装**，实测输出 `systemd-journald 91.39 K/s` |
| `smartctl -i <dev>` | 介质健康与盘型 | L0 | 是 | **已安装**（7.4），实测识别出 `VMware Virtual S`、`Rotation Rate: Solid State Device` |
| `numactl --hardware` | NUMA 拓扑 | L0 | 否 | **已安装**，实测 `1 nodes`、`node 0 cpus: 0 1 2 3` |

> `ethtool -l ens33` 返回 `netlink error: Operation not supported`、`exit=1`——VMware 模拟的 `e1000` 网卡是**单队列**，驱动不支持通道查询。`ethtool -S ens33` 与 `ethtool -k ens33` 可用（实测 `rx_errors: 0`、`rx-checksumming: off`）。**「网卡多队列 / RPS 分散软中断」这一类手法在本机既做不了也演示不了**，要在物理网卡上做。

## 2. 开销分级：什么时候可以放心敲

| 级别 | 特征 | 代表命令 | 在生产机上 |
| --- | --- | --- | --- |
| **L0 只读瞬时** | 读一次内核计数器，微秒级完成 | `uptime`、`free`、`cat /proc/*`、`ss -s`、`nstat`、`taskset -cp` | 可以随便跑 |
| **L1 采样式** | 每秒读一次，开销 <1% | `vmstat 1`、`mpstat 1`、`pidstat 1`、`iostat -x 1`、`systemd-cgtop`、`iotop -b` | 可以跑，但别开着不理 |
| **L2 逐调用拦截** | 每次系统调用都停下来等你 | `strace` | **只在定位到具体进程后、限时限范围地用** |
| **L3 高频采样 / 抓包 / 内核探针** | 每秒几十到几千次采样、拷贝报文或执行 BPF 程序 | `perf record -F 99`、`tcpdump`、`blktrace`、`bpftrace` | 先评估，短时开、用完就停 |
| **L4 主动注入** | 主动制造负载或故障 | `fio`、`stress-ng`、`tc netem`、`dd` | **只在隔离环境 / 可快照实验机** |

本机对这五个级别的量级实证：

```bash
t0=$(date +%s%N); python3 sys20k.py; t1=$(date +%s%N); echo "$(( (t1-t0)/1000000 ))ms"              # 验证：L1 之外的正常运行
t0=$(date +%s%N); strace -c -f python3 sys20k.py >/dev/null 2>&1; t1=$(date +%s%N); echo "$(( (t1-t0)/1000000 ))ms"   # 验证：L2 的代价
```

```text
baseline 50 ms / 51 ms / 51 ms
strace   2254 ms / 2280 ms / 2474 ms
```

同一份「2 万次 `getpid` + `stat`」的 workload：不加观测 **50～51 ms**，套上 `strace -c -f` 变成 **2254～2474 ms**，约 **45～48 倍**。**这不是说 `strace` 不好用，而是说它必须被当成「有代价的手段」，用在已经缩小到一两个进程之后。**

## 4. 让证据站得住的三条纪律

1. **记版本。** `--version` 或 `-V` 一行：`sysstat 12.6.1-2`、`strace -- version 6.8`、`perf version 6.8.12`、`fio-3.36`、`stress-ng 0.17.06`、`bpftrace v0.20.2`、`blktrace version 2.0.0`、`tcpdump version 4.99.4`、`procps-ng 4.0.4`。不同版本同一列的定义可能不同。
2. **记窗口。** 一条 `iostat -x 1 5` 的「平均值」是 5 秒平均还是 1 秒瞬时？`top` 的首屏窗口只有一两秒（本机实测首屏 `26.2 us`、第二屏 `25.3 us`，两者一致，说明它算的是**很近的差分**而不是「自开机以来平均」）。写结论时把窗口和时间戳一起留下。
3. **记条件。** 同样的 `await=7.44 ms`，在「4 KiB 随机写、`iodepth=64`」和「1 MiB 顺序写」下含义完全不同。采集时顺手记一句「当时在跑什么」。

## 5. 「用不了」的四种典型，以及怎么绕过去

旧环境的四种不可用是「没装、缺共享库」；本机换成了另外四种。

| 不可用 | 本机实测证据 | 降级路径 |
| --- | --- | --- |
| **硬件计数器（PMU）** | `/sys/bus/event_source/devices/` 下有 `cpu_core`/`cpu_atom`/`msr`/`kprobe`/`uprobe` 等设备节点，但 `perf stat -e cycles,instructions` 全部 `<not supported>` | 用软件事件 `task-clock`/`context-switches`/`page-faults` + `perf record -F 99` 采样；**根因是 VMware 未把 PMU 计数器透传给 guest，不是「内核不支持」** |
| **裸 `perf stat` / `perf stat -a`** | `Invalid event (cpu_core/TOPDOWN.SLOTS/) in per-thread mode…`；加 `-a` 变成 `sys_perf_event_open() syscall returned with 22 (Invalid argument)` | **必须显式 `-e <事件列表>`**；默认事件集在本机跑不动 |
| **非 root 用 `perf` / 读 `dmesg` / 建 netns** | `realtyz` 跑 `perf` → `perf_event_paranoid setting is 4` + `exit=255`；`realtyz` 读 `dmesg` → `Operation not permitted`；`realtyz` 跑 `unshare -U -r -n` → `write failed /proc/self/uid_map: Operation not permitted`（`exit=1`） | **用 root**：`perf sched`、`bpftrace`、`blktrace`、`tcpdump`、`ip netns` 全部实测可用；需要非 root 时降级到 `/proc` 证据链 + `pidstat` |
| **FlameGraph / bcc 脚本** | `/usr/share/bcc/tools` 不存在，`/usr/share/doc/flamegraph` 不存在，全盘也找不到 `flamegraph.pl` / `stackcollapse-perf.pl` | 采样仍用 `perf record -g`；「折叠栈」这一步用自写脚本复刻（子笔记 08 给出真实输出），绘图脚本未安装——**按本章并行协作纪律不装包** |

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 「先 `top` 看看」 | `top` 默认整机视角、默认不展开线程、首屏窗口只有一两秒，看不到单核与长尾。应该 `vmstat 1` + `mpstat -P ALL 1` |
| 「工具没装就没法查」 | 本机工具已全装；真正的边界是权限与硬件。没有 root 时用 `/proc` 证据链照样能定位到八成 |
| 「`strace` 是查系统调用的标准动作」 | 实测约 45～48 倍减速。应该先 `-c` 汇总、限时限额，或先用 L1 工具缩小范围 |
| 「开一堆监控工具同时看」 | L1 以上工具叠加会互相干扰，`pidstat -d` 甚至会把别的采样工具自己抓进来当噪声（本机实测输出里出现了 `iostat` 自己 4 kB/s 的记录） |
| 「数字记下来就行」 | 不记版本、窗口、条件，事后无法复核。半年后的自己也算「另一个人」 |
| 「`dmesg` 反正能读」 | 取决于 `dmesg_restrict`：本机为 **1**，`realtyz` 直接 `Operation not permitted`；root 不受限。非 root 场景要退到 `journalctl -k` |
| 「`perf record -e cycles` 没报错就是采到了」 | 本机实测它写出了文件（2 个样本）而 `perf stat -e cycles` 是 `<not supported>`——**命令成功不等于事件被支持**，先看 `perf stat` |
| 「容器里执行 `free` 就是容器的内存」 | 默认看到的是宿主机的整机内存，容器上限在 cgroup 里（子笔记 11） |

## 决策练习

**场景**：下午 3 点，同事说「批处理任务跑到一半变慢了，整台机器好像不太对」。这台机器上是生产环境，**不允许重启、不允许装软件**，你只有普通用户权限。

**选项**：

- **A. 先装 `sysstat` 和 `iotop`，把工具补齐再排查。**
- **B. 用只读命令扫一遍：`uptime`、`vmstat 1 5`、`free -m`、`cat /proc/pressure/*`、`iostat -x 1 3`、`ss -s`、`pidstat -d 1`，同时取一份批处理进程的 `/proc/<pid>/{status,sched,io}`。**
- **C. 直接对批处理进程挂 `strace -f -T`，看它卡在哪个系统调用。**

**为什么选 B**：这是典型的「先用 L0/L1 缩小范围」。`vmstat` 的 `r`/`b` 与 `iostat` 的 `await` 能立刻区分「在算」还是「在等」；`/proc/pressure/*` 用一次读文件就能判断有没有真实压力；`pidstat -d` 与 `/proc/<pid>/io` 能把范围收到具体进程。全程只读、微秒级开销，符合生产纪律。

**为什么不选 A**：环境明确不允许装软件。而且「先把工具补齐」会让排查推迟到安装完——本机经验说明，即使一个工具都不装，只靠 `vmstat` + `/proc` 也能把范围缩小一大半；真需要 `mpstat`/`strace`，再用 `apt-get download` + `dpkg-deb -x` 解包到自己的目录即可（本机不需要，但这是无 root 环境下的兜底）。

**为什么不选 C**：`strace -f -T` 是 L2 手段，实测能把被测程序拖慢约 45～48 倍。在一个已经「变慢」的批处理任务上直接挂 `-f`（跟所有子进程），很可能把 10 分钟的窗口拖成一小时，还会改变现象本身。正确顺序是先用 L1 确认它「卡在 IO 还是 CPU」，再对**单个已定位的进程**限时用 `strace -c`。

## 要点自测

> [!question]- 拿到「服务变慢了」，第一分钟敲哪几条命令？为什么是这几条？
> - `uptime`（负载趋势）、`vmstat 1 5`（`r`/`b`/`si`/`so`/`cs`/CPU 分布）、`mpstat -P ALL 1 3`（每核）、`free -m` + `cat /proc/pressure/*`（内存压力）、`iostat -x 1 3`（IO）、`ss -s`（连接分布）。
> - 选它们的理由是**覆盖面 × 代价**：全部是 L0/L1、全部只读、合起来能在 5 秒内回答「哪一层像、哪一层不像」。
> - **第一反应不要是什么**：不要上来就 `top`（整机视角 + 短窗口 + 不展开线程），也不要直接 `strace`。

> [!question]- 观测手段怎么分级？为什么要分级？
> - L0 只读瞬时（`/proc`、`ss -s`）→ L1 采样（`vmstat`、`iostat`）→ L2 逐调用（`strace`）→ L3 高频采样 / 抓包 / 内核探针（`perf record`、`tcpdump`、`blktrace`、`bpftrace`）→ L4 主动注入（`fio`、`stress-ng`、`tc`）。
> - 分级的理由是**代价差一到两个数量级**：本机实测同一 workload 从 50 ms 变成 2254～2474 ms。
> - 原则是「先用低一级的证据缩小范围，再对已经定位到的少量目标上高一级手段」。

> [!question]- 生产机不允许安装软件、你又是非 root，还能用哪些工具？
> - 系统自带的 `uptime`/`vmstat`/`free`/`ps`/`top`/`ss`/`nstat`/`ip`/`lsof`/`systemd-cgtop`/`taskset`/`pmap`，以及 `/proc`、`/sys/fs/cgroup` 下的所有只读文件。
> - 非 root 用不了的：`perf`（`perf_event_paranoid=4`）、`dmesg`（`dmesg_restrict=1`）、`bpftrace`、`blktrace`、`tcpdump`、`iotop`、建 netns（AppArmor 禁非特权 userns）。
> - 缺的工具可以用 `apt-get download` + `dpkg-deb -x` 解包到自己的目录直接运行，缺共享库时按 `ldd` 的 `not found` 逐个补（本机工具已全装，这条只在别的机器上需要）。
> - **第一反应不要是什么**：不要为了排查去动系统的包管理状态。

> [!question]- 为什么 `top` 的首屏不能直接用来下结论？
> - 本机实测首屏给的是**很近的一段差分**（自旋启动 1 秒后首屏 `%Cpu(s): 26.2 us`，第二屏 `25.3 us`），不是「自开机以来平均」——旧环境「首屏是历史平均」的说法在本机不成立。
> - 但它默认是**整机视角**，4 核机器上一个核打满只显示 25%；而且默认不展开线程。
> - 正确用法：`top` 用来「发现」，用来「证明」要靠 `mpstat -P ALL`、`pidstat -u -t` 这类带明确窗口的采样。

> [!question]- 一条性能结论至少要带上哪三类元信息？
> - **版本**（工具版本与内核版本）、**窗口**（采样间隔与时长、时间戳）、**条件**（当时在跑什么负载、块大小、并发数）。
> - 缺任何一项，这个数字就不可复核——本机的 `w_await` 在「4 KiB 随机写 qd64」窗口是 0.09～0.27 ms，在「`stress-ng --hdd 2`」窗口是 4.18～7.44 ms，条件不同结论不同。
