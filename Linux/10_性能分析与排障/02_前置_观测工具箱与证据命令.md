# 前置：观测工具箱与证据命令

> [!cite] 参考资料
> `man 1 top`、`man 1 ps`、`man 1 free`、`man 8 vmstat`、`man 1 mpstat` / `pidstat` / `iostat` / `sar`（sysstat）、`man 1 strace`、`man 1 perf`、`man 8 ss`、`man 8 nstat`、`man 8 tc`、`man 8 ethtool`、`man 1 fio`、`man 1 stress-ng`、`man 5 proc`、`man 2 getrusage`；《Systems Performance》第 4～6 章的工具清单；内核文档 `Documentation/accounting/psi.rst`。

## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **选命令的第一步不是「哪个工具强」，而是「我要看哪个视角」。**
>   - 怎么验证：拿到一个新现象，先写下「整机 / 单核 / 进程 / 线程 / cgroup」里你缺哪个视角，再从地图里挑命令。
> - **第一分钟的五条命令是固定套路：`uptime`、`vmstat 1`、`mpstat -P ALL 1`、`free -m`、`iostat -x 1`（外加 `ss -s`）。**
>   - 证据：本机一次完整扫描的输出只有 3474 字节，却覆盖了身份、负载、每核分布、内存、压力、套接字与软中断；脚本见子笔记 04。
> - **开销要分级：`/proc` 与 `free` 是 L0，采样类命令是 L1，`strace` 是 L2，`perf record` 与抓包是 L3，故障注入是 L4。**
>   - 证据：同一份 workload 直接跑 28 ms、套 `strace -c -f` 后 2317 ms（约 80 倍），这就是 L1 与 L2 之间的量级差。
> - **工具不可用是常态，不是意外。**
>   - 证据：本机 `mpstat`/`pidstat`/`iostat`/`sar`/`strace`/`perf`/`fio`/`stress-ng` 全部未安装；`perf` 解包后能跑，但没有硬件计数器（`cycles` 显示 `<not supported>`）。
> - **每条证据都要带上「版本 + 窗口 + 条件」，否则事后无法复核。**
>   - 怎么验证：回头看自己的记录，能不能回答「这个 `await=343 ms` 是 1 秒窗口还是 5 秒平均、是哪个设备、当时在写多大的块」。

## 1. 命令地图（按视角）

先问「我要看谁」，再问「用哪条命令」。

### 1.1 整机视角：确认「这台机器整体状态」

| 命令 | 回答什么 | 开销 | 需要 root | 本机状态 |
| --- | --- | --- | --- | --- |
| `uptime` / `cat /proc/loadavg` | 负载趋势（1/5/15 分钟）与运行时长 | L0 | 否 | 自带 |
| `vmstat 1 5` | 可运行队列 `r`、D 状态 `b`、换页 `si/so`、块设备 `bi/bo`、中断 `in`、切换 `cs`、CPU 分布 | L1 | 否 | 自带（procps） |
| `mpstat -P ALL 1 3` | **每个核**的用户态/内核态/软中断/等待/偷取占比 | L1 | 否 | sysstat，未安装，解包运行 |
| `free -m` / `cat /proc/meminfo` | 内存总量、可用量、缓存、swap | L0 | 否 | 自带 |
| `cat /proc/pressure/{cpu,memory,io}` | 压力信号 `some`/`full`（饱和度视角） | L0 | 否 | 自带（内核 5.8+） |
| `iostat -x 1 5` | 每块设备的使用率、队列、平均等待 | L1 | 否 | sysstat，解包运行 |
| `ss -s` | 套接字总览（TIME_WAIT、CLOSED、orphaned 数量） | L0 | 否 | 自带（iproute2） |
| `nstat -az` | 协议栈计数器累计值（重传、超时、队列溢出） | L0 | 否 | 自带 |
| `cat /proc/net/softnet_stat` | 每个 CPU 的收包统计（第 2 列是 dropped） | L0 | 否 | 自带 |
| `dmesg -T` / `journalctl -k` | 内核日志（OOM、块设备错误、掉盘） | L0 | 视 `dmesg_restrict` | 自带，本机 `dmesg_restrict=0` 可读 |
| `systemd-cgtop -m -1` | 按 cgroup 排序的资源占用 | L1 | 否 | 自带 |

### 1.2 单核与线程视角：确认「哪个核、哪个线程」

| 命令 | 回答什么 | 开销 | 需要 root | 本机状态 |
| --- | --- | --- | --- | --- |
| `mpstat -P ALL 1` | 找出 100% 的核 | L1 | 否 | 解包运行 |
| `pidstat -u -t -p <pid> 1` | 进程内部**按线程**拆分的 CPU 时间与运行核 | L1 | 否 | 解包运行 |
| `top -b -n1 -H -p <pid>` | 线程名与状态（`R`/`S`/`D`） | L1 | 否 | 自带 |
| `taskset -cp <pid>` | 进程 / 线程当前的 CPU 亲和性 | L0 | 否 | 自带 |
| `ps -eLo pid,tid,psr,pcpu,stat,comm` | 线程列表与所在核 | L1 | 否 | 自带 |
| `cat /proc/<tid>/sched` | 线程等 CPU 的累计时间（`se.wait_sum`）与切换次数 | L0 | 否 | 自带 |

### 1.3 进程视角：确认「谁在花时间、谁在等」

| 命令 | 回答什么 | 开销 | 需要 root | 本机状态 |
| --- | --- | --- | --- | --- |
| `ps -eo pid,ppid,stat,pcpu,pmem,wchan:20,args --sort=-pcpu` | 进程排序（CPU / 内存 / 状态 / 阻塞点） | L1 | 否 | 自带 |
| `pidstat -d 1` | 进程级读写速率与 `iodelay` | L1 | 否 | 解包运行 |
| `pidstat -w -p <pid> 1` | 自愿 / 非自愿上下文切换速率 | L1 | 否 | 解包运行 |
| `cat /proc/<pid>/{status,sched,io,wchan,limits}` | 状态、切换、真实读写字节、阻塞函数、资源上限 | L0 | 否（`stack` 需权限） | 自带 |
| `cat /proc/<pid>/smaps_rollup` | RSS / PSS / Anonymous / Private_Dirty | L0 | 否 | 自带 |
| `pmap -x <pid>` | 按映射段看内存分布 | L0 | 否 | 自带 |
| `ls -l /proc/<pid>/fd` / `lsof -p <pid>` | 打开了哪些文件、句柄数量、`(deleted)` 文件 | L1 | 否 | 自带 |

### 1.4 cgroup / 服务视角：确认「配额与实际用量」

| 命令 | 回答什么 | 开销 | 需要 root | 本机状态 |
| --- | --- | --- | --- | --- |
| `cat /sys/fs/cgroup/<path>/cpu.max` | CPU 配额（`quota period`） | L0 | 否（读） | 自带（cgroup v2） |
| `cat .../cpu.stat` | `nr_periods`/`nr_throttled`/`throttled_usec`：是否被限流 | L0 | 否 | 自带 |
| `cat .../memory.{current,max,peak,stat,events}` | 当前量、上限、峰值、拆分、OOM 计数 | L0 | 否 | 自带 |
| `systemctl show <unit> -p CPUQuotaPerSecUSec -p MemoryMax -p LimitNOFILE -p OOMPolicy` | unit 的资源与 OOM 策略 | L0 | 否 | 自带 |
| `systemd-run --user --scope -p CPUQuota=20% <cmd>` | **在无 root 的实验机上**造一个带配额的 cgroup | L1 | 否（用户级） | 实测可用 |

### 1.5 下钻与注入：确认「具体调用」与「制造现象」

| 命令 | 回答什么 | 开销 | 需要 root | 本机状态 |
| --- | --- | --- | --- | --- |
| `strace -c -f <cmd>` | 系统调用画像（谁最多、谁最耗时） | **L2（实测约 80 倍减速）** | 否（附加他人进程需权限） | 解包运行 |
| `strace -T -e trace=<syscall>` | 单次调用的耗时 | L2 | 否 | 解包运行 |
| `perf stat -e task-clock,context-switches,page-faults` | 事件计数（软件事件可用，硬件事件需 PMU） | L1 | 否 | 解包运行 |
| `perf record -F 99 -- <cmd>` + `perf report` | 采样热点函数与调用栈 | L3 | 否 | 解包运行，热点定位实测可用 |
| `perf sched record` / `offcputime` | off-CPU（等锁、等 IO） | L3 | **是** | **未实测**：报 `No permissions to read /sys/kernel/tracing//events/sched/sched_switch` |
| `tcpdump -i <dev> -c 200 -w cap.pcap` | 抓到具体报文 | L3 | 是（或 `CAP_NET_RAW`） | **未实测** |
| `tc qdisc add ... netem delay/loss` | 在**独立命名空间**注入延迟与丢包 | L4 | 命名空间内可用 | 实测可用（`unshare -U -r -n`） |
| `fio` | 建 IO 基线（顺序/随机 × 读/写 × 队列深度） | L4 | 否 | 解包运行，需补 12 个共享库 |
| `stress-ng` | 造 CPU / 内存 / IO 负载 | L4 | 否 | 解包运行，需补 5 个共享库 |

## 2. 开销分级：什么时候可以放心敲

| 级别 | 特征 | 代表命令 | 在生产机上 |
| --- | --- | --- | --- |
| **L0 只读瞬时** | 读一次内核计数器，微秒级完成 | `uptime`、`free`、`cat /proc/*`、`ss -s`、`nstat`、`taskset -cp` | 可以随便跑 |
| **L1 采样式** | 每秒读一次，开销 <1% | `vmstat 1`、`mpstat 1`、`pidstat 1`、`iostat -x 1`、`systemd-cgtop` | 可以跑，但别开着不理 |
| **L2 逐调用拦截** | 每次系统调用都停下来等你 | `strace` | **只在定位到具体进程后、限时限范围地用** |
| **L3 高频采样 / 抓包** | 每秒几十到几千次采样或拷贝报文 | `perf record -F 99`、`tcpdump` | 先评估，短时开、用完就停 |
| **L4 主动注入** | 主动制造负载或故障 | `fio`、`stress-ng`、`tc netem`、`dd` | **只在隔离环境 / 可快照实验机** |

本机对这五个级别的量级实证：

```text
$ t0=$(date +%s%N); python3 sys20k.py; t1=$(date +%s%N); echo $(( (t1-t0)/1000000 ))ms   # L1 之外运行
29ms
$ t0=$(date +%s%N); strace -c -f python3 sys20k.py; t1=$(date +%s%N); echo $(( (t1-t0)/1000000 ))ms   # 验证：L2 的代价
2317ms
```

同一份「2 万次 `getpid` + `stat`」的 workload：不加观测 28～29 ms，套上 `strace -c -f` 变成 2317～2342 ms。**这不是说 `strace` 不好用，而是说它必须被当成「有代价的手段」，用在已经缩小到一两个进程之后。**

这张表本身就是排障经验：**真实环境里工具总是缺的**，方案必须包含降级路径。

| 工具 | 来源 | 本机可用性 | 备注 |
| --- | --- | --- | --- |
| `uptime` `free` `ps` `top` `vmstat` `ss` `nstat` `ip` `tc` `lsof` `unshare` `systemd-run` `systemd-cgtop` `journalctl` `dmesg` `taskset` `pmap` | 系统自带 | ✅ 直接可用 | 主力工具 |
| `mpstat` `pidstat` `iostat` `sadc` `sar` | sysstat | ✅ 解包运行 | 未安装、未改系统；`sar` 二进制在这版包里叫 `sar.sysstat` |
| `strace` | strace | ✅ 解包运行 | 约 80 倍减速 |
| `perf` | linux-tools-6.8.0-139 + linux-tools-common | ⚠️ 部分可用 | 软件事件与采样可用；`cycles`/`instructions` 为 `<not supported>`；`perf sched` 被 tracefs 权限拒绝 |
| `fio` | fio | ✅ 解包运行 | 需额外解包 `libaio1t64`、`libibverbs1`、`librdmacm1t64`、`libpmem1`、`libnbd0`、`libgfapi0`、`librados2`、`librbd1`、`libglusterfs0`、`libgfrpc0`、`libgfxdr0`、`libnl-3-200`、`libnl-route-3-200`、`libceph-common`、`libboost-*`、`libndctl6`、`libdaxctl1` 等才启动 |

| `bpftrace` / `bcc` | 需 root + `CAP_BPF` | ❌ 未实测 | 本机 `kernel.unprivileged_bpf_disabled=2` |
| `iotop` | 需 root | ❌ 未安装 | 用 `pidstat -d` 替代 |
| `blktrace` / `biosnoop` | 需 root / eBPF | ❌ 未实测 | 用 `iostat -x` + `pidstat -d` 替代 |
| `smartctl` | smartmontools | ❌ 未安装 | 介质健康检查在阶段 5 |
| `numactl` | numactl | ❌ 未安装 | 多路 NUMA 场景需要它 |

> [!tip] 「未安装」不等于「做不到」
> 用 `apt-get download <pkg>` 拉下 `.deb`，再 `dpkg-deb -x <pkg>.deb <目录>` 解包，然后 `PATH=<目录>/usr/bin:$PATH`、`LD_LIBRARY_PATH=<目录>/usr/lib/x86_64-linux-gnu:$LD_LIBRARY_PATH` 就能直接跑，**不动系统、不装包、不需要 root**。缺共享库时按 `ldd <binary> | grep "not found"` 逐个把库也解包下来即可（`fio` 就是这样从「8 个库缺失」一路补到能跑的）。

## 4. 让证据站得住的三条纪律

1. **记版本。** `--version` 或 `-V` 一行：`sysstat version 12.6.1`、`strace -- version 6.8`、`perf version 6.8.12`、`fio-3.36`、`stress-ng 0.17.06`。不同版本同一列的定义可能不同。
2. **记窗口。** 一条 `iostat -x 1 5` 的「平均值」是 5 秒平均还是 1 秒瞬时？`top` 的首屏是**自开机以来**的平均（本机实测要按 `1` 或等第二屏才看到实时值）。写结论时把窗口和时间戳一起留下。
3. **记条件。** 同样的 `await=343 ms`，在「4 KiB 随机写、`iodepth=64`」和「1 MiB 顺序写」下含义完全不同。采集时顺手记一句「当时在跑什么」。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 「先 `top` 看看」 | `top` 首屏是自开机以来平均；默认整机视角，看不到单核与长尾。应该 `vmstat 1` + `mpstat -P ALL 1` |
| 「工具没装就没法查」 | 本机 8 个主力工具都没装，靠 `apt-get download` + `dpkg-deb -x` 解包一样跑通 |
| 「`strace` 是查系统调用的标准动作」 | 实测约 80 倍减速。应该先 `-c` 汇总、限时限额，或先用 L1 工具缩小范围 |
| 「开一堆监控工具同时看」 | L1 以上工具叠加会互相干扰，`pidstat -d` 甚至会把别的采样工具自己抓进来当噪声 |
| 「数字记下来就行」 | 不记版本、窗口、条件，事后无法复核。半年后的自己也算「另一个人」 |
| 「`dmesg` 一定要 root」 | 取决于 `dmesg_restrict`；本机为 `0`，非 root 可读。为 `1` 时改看 `journalctl -k` |
| 「容器里执行 `free` 就是容器的内存」 | 默认看到的是宿主机的整机内存，容器上限在 cgroup 里（子笔记 11） |

## 决策练习

**场景**：下午 3 点，同事说「批处理任务跑到一半变慢了，整台机器好像不太对」。这台机器上是生产环境，**不允许重启、不允许装软件**，你只有普通用户权限。

**选项**：

- **A. 先装 `sysstat` 和 `iotop`，把工具补齐再排查。**
- **B. 用只读命令扫一遍：`uptime`、`vmstat 1 5`、`free -m`、`cat /proc/pressure/*`、`iostat -x 1 3`、`ss -s`、`pidstat -d 1`，同时取一份批处理进程的 `/proc/<pid>/{status,sched,io}`。**
- **C. 直接对批处理进程挂 `strace -f -T`，看它卡在哪个系统调用。**

**为什么选 B**：这是典型的「先用 L0/L1 缩小范围」。`vmstat` 的 `r`/`b` 与 `iostat` 的 `await` 能立刻区分「在算」还是「在等」；`/proc/pressure/*` 用一次读文件就能判断有没有真实压力；`pidstat -d` 与 `/proc/<pid>/io` 能把范围收到具体进程。全程只读、微秒级开销，符合生产纪律。

**为什么不选 A**：环境明确不允许装软件。而且「先把工具补齐」会让排查推迟到安装完——本机经验说明，即使一个工具都不装，只靠 `vmstat` + `/proc` 也能把范围缩小一大半；真需要 `mpstat`/`strace`，再用 `apt-get download` + `dpkg-deb -x` 解包到自己的目录即可（不动系统）。

**为什么不选 C**：`strace -f -T` 是 L2 手段，实测能把被测程序拖慢约 80 倍。在一个已经「变慢」的批处理任务上直接挂 `-f`（跟所有子进程），很可能把 10 分钟的窗口拖成一小时，还会改变现象本身。正确顺序是先用 L1 确认它「卡在 IO 还是 CPU」，再对**单个已定位的进程**限时用 `strace -c`。

## 要点自测

> [!question]- 拿到「服务变慢了」，第一分钟敲哪几条命令？为什么是这几条？
> - `uptime`（负载趋势）、`vmstat 1 5`（`r`/`b`/`si`/`so`/`cs`/CPU 分布）、`mpstat -P ALL 1 3`（每核）、`free -m` + `cat /proc/pressure/*`（内存压力）、`iostat -x 1 3`（IO）、`ss -s`（连接分布）。
> - 选它们的理由是**覆盖面 × 代价**：全部是 L0/L1、全部只读、合起来能在 5 秒内回答「哪一层像、哪一层不像」。
> - **第一反应不要是什么**：不要上来就 `top`（整机 + 自开机平均），也不要直接 `strace`。

> [!question]- 观测手段怎么分级？为什么要分级？
> - L0 只读瞬时（`/proc`、`ss -s`）→ L1 采样（`vmstat`、`iostat`）→ L2 逐调用（`strace`）→ L3 高频采样 / 抓包（`perf record`、`tcpdump`）→ L4 主动注入（`fio`、`stress-ng`、`tc`）。
> - 分级的理由是**代价差两个数量级**：本机实测同一 workload 从 28 ms 变成 2317 ms。
> - 原则是「先用低一级的证据缩小范围，再对已经定位到的少量目标上高一级手段」。

> [!question]- 生产机不允许安装软件，你还能用哪些工具？
> - 系统自带的 `uptime`/`vmstat`/`free`/`ps`/`top`/`ss`/`nstat`/`ip`/`tc`/`lsof`/`unshare`/`systemd-cgtop`/`taskset`/`pmap`，以及 `/proc`、`/sys/fs/cgroup` 下的所有只读文件。
> - 缺的工具可以用 `apt-get download` + `dpkg-deb -x` 解包到自己的目录直接运行，缺共享库时按 `ldd` 的 `not found` 逐个补。
> - **第一反应不要是什么**：不要为了排查去动系统的包管理状态。

> [!question]- 为什么 `top` 的首屏不能直接用来下结论？
> - 首屏的 CPU 与进程数据是**自开机以来**的平均（本机实测按 `1` 才切到每核实时视图），会严重稀释刚发生的尖刺。
> - 它默认是整机视角，24 核机器上一个核打满只显示 4.2%。
> - 正确用法：`top` 用来「发现」，用来「证明」要靠 `mpstat -P ALL`、`pidstat -u -t` 这类带窗口的采样。

> [!question]- 一条性能结论至少要带上哪三类元信息？
> - **版本**（工具版本与内核版本）、**窗口**（采样间隔与时长、时间戳）、**条件**（当时在跑什么负载、块大小、并发数）。
> - 缺任何一项，这个数字就不可复核——本机的 `await` 在「4 KiB 随机写 qd64」窗口是 54.72 ms，在另一个窗口是 343.08 ms，条件不同结论不同。
