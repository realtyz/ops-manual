## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **网络排障的顺序是：连接状态 → 协议栈计数器 → 收包侧丢弃 → 单连接状态 → 最后才考虑抓包。**
>   - 证据：本机 `ss -s`、`nstat -az`、`/proc/net/softnet_stat`、`ip -s link` 四条只读命令一共花了不到 1 秒，就给出了「重传率 14/654775 ≈ 0.002%、队列溢出 10 次、收包丢弃 0、网卡错误 0」的结论，此时抓包没有额外信息。
> - **`ss -ti` 能把「网络慢」和「应用慢」分开。**
>   - 证据：用 `netem` 在独立 netns 的 `lo` 上注入 50 ms 延迟后，`ss -ti` 显示 `rtt:100.293/0.055`、`minrtt:100.123`、`cwnd:10`、`app_limited`、`unacked:1`、`snd_wnd:65536`——RTT 与注入值吻合，说明链路侧生效。
> - **`netem` 的丢包率会比配置值高，因为 loopback 上两个方向都要过一次。**
>   - 证据：配置 `loss 20%`，200 个包实测 **36.5%** 丢失（收到 127 个）；这与 `1 − 0.8 × 0.8 = 36%` 吻合。10 个包时实测 50%（样本太少）。
> - **`load` 高、CPU 空、进程杀不掉 = 在看 D 状态。**
>   - 怎么验证：`vmstat` 的 `b` > 0、`ps -o stat,wchan` 显示 `D`、`cat /proc/<pid>/wchan` 给出内核阻塞函数。本机实测 `wchan` 直接读出 `hrtimer_nanosleep`，`/proc/<pid>/stack` 在 root 下能拿到完整内核调用链。
> - **`perf` 采样看不到「不在 CPU 上」的时间，但有三种手段能补——本机三种都实测可用。**
>   - 证据：`perf sched record` 以 root 采到 **35573 个样本**（旧环境被 tracefs 权限拒绝），`perf sched latency` 输出按最大延迟排序的表；`bpftrace` 的 `kprobe:schedule`+`kretprobe:schedule` 也能按进程统计 off-CPU 纳秒；最省事的 `cat /proc/<pid>/wchan` 给出 `hrtimer_nanosleep`。

## 1. 网络侧的三层证据

### 1.1 第一层：连接状态分布

```bash
ss -s | head -3          # 验证：全局套接字统计，看 timewait/closed/orphaned 哪个异常
ss -lnt                  # 验证：监听队列（Recv-Q = 已完成握手但未被 accept 的连接数）
```

```text
$ ss -s
Total: 177
TCP:   12 (estab 3, closed 5, orphaned 0, timewait 0)
```

另一份现场来自「3000 条短连接」实验（在**独立 netns** 里做，所以不影响宿主）：

```text
$ ip netns exec lab10port ss -s | head -3
Total: 0
TCP:   3001 (estab 0, closed 3001, orphaned 0, timewait 2988)
```

这条记录要说明的是：**`ss -s` 一眼就能看出「是不是连接堆积型问题」**：

- `timewait` 暴涨 → 短连接过多或服务端主动关闭（子笔记 10 有量化模型）；
- `closed` 很大 → 大量连接处于非活跃状态，可能是泄漏；
- `orphaned` 非 0 → 有连接已无进程持有，通常是应用没有正确关闭。

### 1.2 第二层：协议栈计数器

```bash
nstat -az | grep -E "^(TcpActiveOpens|TcpInSegs|TcpOutSegs|TcpRetransSegs|TcpExtListenOverflows|TcpExtTCPTimeouts)"
```

```text
TcpActiveOpens                  320                0.0
TcpInSegs                       899072             0.0
TcpOutSegs                      654775             0.0
TcpRetransSegs                  14                 0.0
TcpExtListenOverflows           10                 0.0
TcpExtTCPTimeouts               8                  0.0
```

四个判据：

| 计数器 | 含义 | 判据 |
| --- | --- | --- |
| `TcpRetransSegs / TcpOutSegs` | 重传率 | 超过 0.1%～1% 就要查链路（本机 14/654775 ≈ **0.002%**，正常） |
| `TcpExtListenOverflows` | accept 队列溢出次数 | 增长说明应用来不及 `accept()`（不是网络慢，是应用慢） |
| `TcpExtTCPTimeouts` | 超时重传 | 增长通常伴随重传率上升 |
| `TcpExtTCPBacklogDrop` / `TcpExtListenDrops` | SYN 队列丢弃 | 短时间大量新连接时出现（连接风暴、健康检查过密） |

> [!warning] `nstat` 是**累计值**，必须差分
> 本机 `TcpRetransSegs` 读数是 **14**、`TcpExtListenOverflows` 是 **10**——它们都是**开机以来的累计值**，不是「现在正在重传」。判据永远是「在一个窗口内有没有增长」，而不是「是不是 0」。想只看增量可以用 `nstat`（不带 `-a` 时默认输出两次之间的差值）或隔一段时间取两次做差分。

### 1.3 第三层：收包侧丢弃

```bash
awk '{s+=$2} END{print "softnet dropped:", s}' /proc/net/softnet_stat   # 验证：收包来不及处理
ip -s link show lo                                                      # 验证：接口级收发与错误计数
```

```text
softnet dropped: 0

    RX:   bytes packets errors dropped  missed   mcast
    20779197305  587161      0       0       0       0
    TX:   bytes packets errors dropped carrier collsns
    20779197305  587161      0       0       0       0
```

`/proc/net/softnet_stat` 第 2 列是**每个 CPU 的丢包计数**；它非 0 说明「包到了内核但软中断没来得及处理」，方向是收包侧 CPU 不足、软中断没分散、或网卡队列配置问题。配合 `mpstat` 看 `%soft` 集中在哪个核。

本机的 `ens33` 中断全部集中在 **CPU3**（`/proc/interrupts` 里 `19: … IO-APIC 19-fasteoi ens33` 计数 98561，其余核为 0），这与「单队列网卡把收包中断压到一个核上」的形态一致。物理机上还可以加一层 `ethtool -S <dev>`：

```bash
ethtool -S ens33 | head -10     # 验证：网卡级统计
```

```text
NIC statistics:
     rx_packets: 314255
     tx_packets: 69287
     rx_bytes: 429014974
     tx_bytes: 7554296
     rx_errors: 0
```

但**多队列与 offload 类手法在本机做不了**：`ethtool -l ens33` 直接报 `netlink error: Operation not supported`、`exit=1`——VMware 模拟的 `e1000` 是单队列，驱动不支持通道查询。

## 2. `ss -ti`：把「网络慢」和「应用慢」分开

`ss -ti` 给出的是一条连接的内部状态。本机用 `netem` 在**独立 netns** 的 `lo` 上注入 50 ms 单向延迟后（往返约 100 ms）实测：

```bash
ip netns add lab10net
ip netns exec lab10net ip link set lo up
ip netns exec lab10net tc qdisc add dev lo root netem delay 50ms
ip netns exec lab10net python3 tcptest.py &
ip netns exec lab10net ss -ti state established | head -8
```

```text
0      0          127.0.0.1:20800    127.0.0.1:60166
	 cubic wscale:7,7 rto:301 rtt:100.293/0.055 ato:40 mss:32768 pmtu:65535
	 rcvmss:536 advmss:65483 cwnd:10 bytes_sent:2496 bytes_acked:2496
	 bytes_received:2496 segs_out:40 segs_in:80 data_segs_out:39 data_segs_in:39
	 send 26.1Mbps lastsnd:112 lastrcv:112 lastack:12 pacing_rate 52.3Mbps
	 delivery_rate 2.62Mbps delivered:40 app_limited busy:3910ms
	 rcv_space:65483 rcv_ssthresh:65483 minrtt:100.123 snd_wnd:65536
```

| 字段 | 含义 | 怎么用 |
| --- | --- | --- |
| `rtt:x/y` | 平滑 RTT / 偏差（ms） | 与对端/链路预期对比；本机 100.293 与注入的 50×2 吻合 |
| `minrtt` | 观测到的最小 RTT | **最干净的链路时延证据**（不受排队影响）；本机 100.123 ms |
| `retrans` / `unacked` | 重传次数 / 未确认字节数 | 重传持续增长说明丢包；本机 `unacked:1` |
| `cwnd` / `snd_wnd` | 拥塞窗口 / 对端通告窗口 | 小 `cwnd` 说明链路受限；小的 `snd_wnd` 说明**对端**处理不过来。本机 `cwnd:10`、`snd_wnd:65536` |
| `app_limited` | 发送受限是因为应用没提供数据 | **看到它就说明瓶颈不在网络，而在应用** |
| `delivery_rate` / `pacing_rate` | 实测投递速率 / 发送节奏 | 与实际吞吐对照；本机 `delivery_rate 2.62Mbps` |

对照：同一个 netns 在**没有** netem 时的 `lo` 是 `rtt min/avg/max/mdev = 0.008/0.024/0.083/0.007 ms`——比注入后小四个数量级，说明 `ss -ti` 的 `rtt`/`minrtt` 真的在反映链路时延，而不是一个恒定噪声。

**用法要点**：`app_limited` 是这张表里最有价值的一行。它明确告诉你「连接不是被网络卡住，而是没有数据要发」，避免把应用问题当成网络问题查半天。

## 3. 什么时候才需要抓包

抓包是 L3 手段（拷贝每个报文到用户态），应该严格是「兜底」而不是「起手」：

```text
计数器干净（重传率 0.002%、队列溢出 10、softnet 丢弃 0、网卡错误 0）
        │
        ├─ 现象仍然存在 → 先怀疑应用侧（app_limited、慢调用、锁、GC），而不是链路
        └─ 现象指向链路 → 用 ss -ti 的 minrtt/retrans 定位到具体连接
                              │
                              └─ 仍无法解释 → 限时限量抓包（-c 200 -w file，指定 host/port）
```

本机实测的「计数器干净」状态：`TcpRetransSegs=14`（重传率 0.002%）、`TcpExtListenOverflows=10`、`softnet dropped=0`、`lo` 的 `RX/TX errors=0`。在这种状态下抓包，最有价值的产出通常只是确认「没有异常报文」。本机确实跑了一次限时限量的抓包作为对照：

```bash
timeout 15 tcpdump -i lo -c 12 -nn port 20860
```

```text
08:35:46.686904 IP 127.0.0.1.20860 > 127.0.0.1.37420: Flags [S.], seq 3983909647, ack 1989803330, win 65483, options [mss 65495,sackOK,TS val 2969065644 ecr 2969065644,nop,wscale 7], length 0
08:35:46.686942 IP 127.0.0.1.37420 > 127.0.0.1.20860: Flags [P.], seq 1:9, ack 1, win 512, options [nop,nop,TS val 2969065644 ecr 2969065644], length 8
12 packets captured
32 packets received by filter
0 packets dropped by kernel
```

**这就是「兜底」的样子**：抓到的全是正常的握手与 8 字节载荷，唯一的结论是「没有异常报文」。注意 `-c 12` 限了包数、外层 `timeout 15` 限了时间、`port 20860`（本章端口区间内）限了范围——**三个限制缺一不可**。

## 4. 故障注入：用 `netem` 亲手造一次延迟与丢包

本机必须用 **root + `ip netns`**（非 root 的 `unshare -U -r -n` 被 AppArmor 拒绝，见子笔记 03）。注入只影响这个隔离网络，不会碰宿主。

```bash
ip netns add lab10net
ip netns exec lab10net ip link set lo up
ip netns exec lab10net tc qdisc add dev lo root netem delay 50ms
ip netns exec lab10net ping -c 3 -q 127.0.0.1 | tail -2
ip netns exec lab10net tc qdisc del dev lo root
ip netns exec lab10net tc qdisc add dev lo root netem loss 20%
ip netns exec lab10net ping -c 200 -q -i 0.02 127.0.0.1 | tail -2
ip netns del lab10net
```

```text
注入 50 ms 单向延迟：
3 packets transmitted, 3 received, 0% packet loss, time 2003ms
rtt min/avg/max/mdev = 100.131/100.238/100.375/0.101 ms
qdisc netem 8003: root refcnt 2 limit 1000 delay 50ms

注入 20% 丢包、200 个包：
200 packets transmitted, 127 received, 36.5% packet loss, time 4180ms

注入 20% 丢包、10 个包（小样本对照）：
10 packets transmitted, 5 received, 50% packet loss, time 189ms
```

### 4.1 为什么配了 20% 却丢了 36.5%

这不是采样波动，而是**算术**：`netem` 挂在 `lo` 的**出口**上，一次 ping 的请求和应答都要经过 `lo` 的出口，各自有 20% 的概率被丢：

```text
往返成功率 = 0.8 × 0.8 = 0.64
理论丢失率 = 1 − 0.64 = 36%
200 个包实测 = 36.5%
```

**这条结论比「样本量要够」更重要**：注入的方向、位置与观测口径决定了你看到的数字。做丢包演练前，先想清楚「丢的是请求、应答还是两者」。

### 4.2 验证要多少样本

小样本同样会放大误差：10 个包时实测 **50%**（5 个收到），200 个包时 **36.5%**，理论值 **36%**。**结论：验证丢包率要用足够的样本（几百到几千个包），并且先算清楚理论期望值。**

### 4.3 做完必须复核的两件事

```bash
ip netns list            # 验证：自己的 netns 已删除
tc qdisc show dev lo     # 验证：宿主的 lo 没有被注入
```

```text
netns list:
lab6bb (id: 1)
lab6ba (id: 0)
1: lo: <LOOPBACK,UP,LOWER_UP> mtu 65536 qdisc noqueue state UNKNOWN mode DEFAULT group default qlen 1000
qdisc noqueue 0: root refcnt 2
```

注意 `ip netns list` 里剩下的 `lab6bb`/`lab6ba` **不是本章的**（是并行推进的阶段 6 建的），本章自己的 `lab10net` 已删除；宿主 `lo` 上是干净的 `noqueue`。**清理核查时要能分清「谁的残留」，不要误删别人的命名空间。**

## 5. 「在等」：D 状态、`wchan` 与网络存储

网络只是「等待」的一种。更常见的是进程卡在存储或锁上：

```bash
vmstat 1 5                                             # 验证：b 列（D 状态任务数）是否持续 > 0
ps -eo pid,ppid,stat,wchan:24,etime,args | awk '$3 ~ /D/'   # 验证：哪些进程处于 D 状态
cat /proc/<pid>/wchan                                  # 验证：内核里阻塞在哪个函数
cat /proc/<pid>/stack                                  # 验证：完整内核调用链（需 root）
mount | grep -E "nfs|cifs|fuse"                        # 验证：是否挂了网络存储
dmesg -T | tail -30                                    # 验证：块设备/文件系统是否报错
```

```text
$ cat /proc/49112/wchan
hrtimer_nanosleep
$ cat /proc/49112/stack
[<0>] hrtimer_nanosleep+0xa2/0x170
[<0>] common_nsleep+0x43/0x60
[<0>] __x64_sys_clock_nanosleep+0xf1/0x180
[<0>] x64_sys_call+0x1c2c/0x25a0
[<0>] do_syscall_64+0x87/0x180
[<0>] entry_SYSCALL_64_after_hwframe+0x78/0x80
$ runuser -u realtyz -- cat /proc/49112/stack
cat: /proc/49112/stack: Permission denied
```

本机的 `hrtimer_nanosleep` 是一个正常睡眠进程的阻塞点。如果这里出现 `nfs_wait_*`、`*_rpc_wait`、`blk_*` 之类的函数，方向就非常明确了：**它在等一个外部资源**。

| 现象 | 方向 | 证据 |
| --- | --- | --- |
| `b` 持续 > 0，`wchan` 是 `nfs*`/`rpc*` | 网络存储阻塞 | `mount` 里的 `nfs` 挂载、存储服务端状态 |
| `b` 持续 > 0，`wchan` 是 `blk_*` | 块设备层阻塞 | `iostat -x`、`dmesg` 里的 IO 错误 |
| `b` = 0，但进程 `S` 且 CPU 空 | 可能在等锁 / 等对端 | `/proc/<pid>/sched` 的 `se.wait_sum`、`ss -ti` 的 `app_limited`、应用侧的锁指标 |

### 5.1 为什么 `perf` 看不到这段等待——以及本机怎么补

`perf record` 基于采样，只覆盖「线程在 CPU 上」的时间。一个 90% 时间在等 IO 的线程，在火焰图里可能完全看不到。补这个盲区的三条路，**本机三条都实测可用**：

1. `/proc/<pid>/wchan`（当前阻塞点）与 `/proc/<pid>/sched` 的 `se.wait_sum`（累计等待时间）——无需权限，L0。本机实测 `wchan` = `hrtimer_nanosleep`、`nr_switches: 1`。
2. **`perf sched record` + `perf sched latency`——需要 root，本机实测成功**：

```text
$ perf sched record -o sched.data -- sleep 3
[ perf record: Captured and wrote 4.028 MB /tmp/10-lab/sched.data (35573 samples) ]

  Task                  |   Runtime ms  | Switches | Avg delay ms    | Max delay ms    |
  kworker/0:0-cgw:3699  |      0.644 ms |       22 | avg:   0.147 ms | max:   3.010 ms |
  systemd-journal:463   |      0.159 ms |        2 | avg:   0.096 ms | max:   0.181 ms |
  tee:(4)               |      4.288 ms |        7 | avg:   0.092 ms | max:   0.224 ms |
  sleep:48510           |      1.354 ms |        2 | avg:   0.039 ms | max:   0.052 ms |
```

3. **`bpftrace` 的 off-CPU 脚本——需要 root，本机实测成功**：

```text
$ bpftrace -e 'kprobe:schedule { @s[tid] = nsecs; }
    kretprobe:schedule /@s[tid]/ { @offcpu[comm] = sum(nsecs - @s[tid]); delete(@s[tid]); }
    interval:s:5 { exit(); }'
@offcpu[HangDetector]: 4000601427
@offcpu[vmtoolsd]: 4956885942
@offcpu[kworker/3:1]: 4982348769
```

> [!warning] 旧环境「`perf sched` 被拒」不适用于本机
> 旧笔记记录的是 `Error: No permissions to read /sys/kernel/tracing//events/sched/sched_switch`。**本机以 root 跑 `perf sched record` 直接成功**（4.028 MB / 35573 个样本）；因为 `perf_event_paranoid=4` 只限制**非 root**。这条从「未实测」正式升级为实测——off-CPU 分析从「只能靠 `/proc` 猜」变成「有专门的工具」。

> [!warning] D 状态进程的处置纪律
> `kill -9` 对 D 状态进程无效（信号要等它回到用户态才处理）。正确顺序是：先恢复它等待的资源（网络存储服务端、块设备、锁），必要时 `umount -f`/重启整机，而且**先取证**（`dmesg`、`wchan`、`mount` 的输出）。细节见子笔记 14。

## 6. 生产动作：网络侧判定记录（有产出物）

一份可交付的网络侧判定记录包含四段：

1. **连接分布**：`ss -s` 与 `ss -lnt` 的原始输出（TIME_WAIT、监听队列 Recv-Q）。
2. **协议栈计数器**：`nstat` 的重传 / 超时 / 队列溢出，以及**重传率**的计算式与数值（本机 14/654775 ≈ 0.002%）。
3. **收包侧**：`softnet_stat` 的 dropped、`ip -s link` 的收发与错误。
4. **结论与方向**：如果计数器全部干净，明确写出「主机侧网络无明显异常，方向转向应用侧（`app_limited`）或下游依赖」；如果有异常，给出具体计数器与时间点。

这份记录的价值在于：**它把「网络有没有问题」这个争论变成一个可以用四条命令复核的事实。**

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 「网络慢就抓包」 | 先看 `ss -s`/`nstat`/`softnet_stat`/`ip -s link`；本机四条只读命令 1 秒内排除网络 |
| 「`nstat` 里 `TcpRetransSegs` 非 0 就是链路有问题」 | 它是**开机以来的累计值**（本机 14）；要看窗口内的增量与**重传率**（本机 14/654775 ≈ 0.002%） |
| 「`ss -s` 的 timewait 高就是攻击」 | TIME_WAIT 是主动关闭方的正常状态；要先算「端口数 ÷ TIME_WAIT 时长」的上限（子笔记 10） |
| 「有重传就是网络坏了」 | 低频重传是 TCP 的正常行为；要看**重传率**与是否与延迟拐点对齐 |
| 「配 20% 丢包，实测 36.5% 说明工具不准」 | `lo` 上请求与应答各过一次：`1 − 0.8² = 36%`，实测 36.5% 与理论吻合 |
| 「10 个包测出 50% 丢包，说明丢包率是 50%」 | 小样本噪声。10 个包只能给出极粗的区间；验丢包率要用几百到几千个包 |
| 「`ListenOverflows` 增长是网络问题」 | 它是**应用没及时 `accept()`**；方向是应用侧 |
| 「`rtt` 大就是链路差」 | 先看 `minrtt`（最干净的链路时延）与 `app_limited`；大 `app_limited` 说明瓶颈在应用。本机注入前后 `minrtt` 100.123 ms vs 0.008 ms，差四个数量级 |
| 「`perf` 能看出进程在等什么」 | `perf record` 采样只覆盖在 CPU 上的时间；要用 `wchan`/`sched` 或 root 下的 `perf sched`/`bpftrace` off-CPU（本机均已实测） |
| 「D 状态进程 `kill -9` 就行了」 | 信号要等进程回到用户态才处理；要先恢复它等的资源 |
| 「`unshare -U -r -n` 是无 root 做网络注入的标准做法」 | 本机 AppArmor 禁非特权 userns，`realtyz` 直接 `Operation not permitted`；**用 root + `ip netns`** |
| 「容器里的 `ss`/`nstat` 能看到宿主网络」 | 只能看到本 netns 的连接与计数器，宿主视角要另外取（子笔记 11） |

## 决策练习

**场景**：一个跨机房调用的服务报「偶发超时」。`nstat` 显示 `TcpRetransSegs` 在缓慢增长，`ss -s` 的 TIME_WAIT 正常，`softnet_stat` 的 dropped 为 0。同事建议「抓包看是不是中间设备丢包」。

**选项**：

- **A. 直接抓包 1 小时，等下一次超时。**
- **B. 先算重传率（`TcpRetransSegs / TcpOutSegs` 的窗口增量），再用 `ss -ti` 看具体连接上的 `minrtt`/`retrans`/`cwnd`/`app_limited`，把「链路丢包」与「应用写不动」分开，再决定是否抓包。**
- **C. 调整 TCP 参数（`tcp_retries2`、`tcp_rmem`）把超时压下去。**

**为什么选 B**：`TcpRetransSegs` 缓慢增长可能是几十万分之一的重传率，也可能高达百分之几——**不看分母就没有判断依据**（本机是 14/654775 ≈ 0.002%，属于正常范围）。`ss -ti` 的 `minrtt` 是判断链路质量的干净证据，`app_limited` 则直接排除「应用没数据要发」这种伪网络问题；`cwnd` 小说明拥塞，`snd_wnd` 小说明对端处理不过来。这三个字段能把范围收到具体方向。

**为什么不选 A**：抓包是 L3 手段，成本高、数据量大，而且「偶发」意味着大部分抓到的报文都是正常的。正确顺序是先算比率、看单连接状态，再对**已经定位到的那条连接**做限时限量的抓包（本机的示范是 `-c 12` + `timeout 15` + `port 20860` 三重限制）。

**为什么不选 C**：改内核参数在根因未明时是最危险的动作——它会在生产机上引入不可回滚的变量，而且可能只是把「丢包」换成「更长的超时」，让用户感知更差。

## 要点自测

> [!question]- 「网络慢」的排查顺序是什么？为什么通常不需要抓包？
> - 连接状态（`ss -s`/`ss -lnt`）→ 协议栈计数器（`nstat`，看重传率与队列溢出的**增量**）→ 收包侧（`softnet_stat`、`ip -s link`、`ethtool -S`）→ 单连接状态（`ss -ti`）→ 最后才是抓包。
> - 前几层都是 L0，1 秒内可完成；本机实测这几层给出的结论是「重传率 0.002%、队列溢出 10（累计）、收包丢弃 0、网卡错误 0」，此时抓包只能确认「没有异常报文」。
> - **第一反应不要是什么**：不要 `tcpdump -i any` 一开了事。

> [!question]- `ss -ti` 里的 `minrtt`、`cwnd`、`snd_wnd`、`app_limited` 分别说明什么？
> - `minrtt`：观测到的最小 RTT，是链路时延的干净证据（不受排队影响）。本机注入 50 ms 单向延迟后为 100.123 ms，无注入时 `lo` 的 RTT 是 0.008 ms。
> - `cwnd`：本端拥塞窗口；小说明发送受拥塞控制限制。
> - `snd_wnd`：对端通告的接收窗口；小说明**对端**处理不过来。
> - `app_limited`：发送受限是因为应用没提供数据 → **瓶颈在应用，不在网络**。
> - 本机实测（注入 50 ms 单向延迟）：`rtt:100.293/0.055 minrtt:100.123 cwnd:10 app_limited unacked:1 snd_wnd:65536`。

> [!question]- 为什么 `netem` 配 20% 丢包实测却是 36.5%？
> - `netem` 挂在 `lo` 的出口上，请求和应答各经过一次，两次都要成功才算一次成功的 ping：`0.8 × 0.8 = 0.64`，即丢失率约 36%。
> - 实测 10 个包 50%（小样本）、200 个包 36.5%，理论 36%。
> - 教训：做注入演练前先算清楚「丢的是几个方向」，并准备足够的样本量。

> [!question]- 进程处于 D 状态时，为什么 `kill -9` 无效？正确做法是什么？
> - 信号只在进程回到用户态时才被处理；D 状态是不可中断睡眠，内核路径不会去检查待处理信号。
> - 正确顺序：先取证（`dmesg`、`ps -o stat,wchan`、`mount`、必要时 `cat /proc/<pid>/stack`）→ 恢复它等待的资源（网络存储、块设备、锁）→ 必要时 `umount -f` 或重启整机。
> - **第一反应不要是什么**：不要反复 `kill -9`，也不要在没取证前直接重启。

> [!question]- 为什么 `perf` 火焰图里看不到「在等」的时间？本机怎么补？
> - `perf record` 是采样型，只在线程位于 CPU 上时才会采到；等待时间不产生样本。
> - 补法一：`/proc/<pid>/wchan`（当前阻塞点）+ `/proc/<pid>/sched` 的 `se.wait_sum`（累计等待），无需权限；本机实测 `wchan = hrtimer_nanosleep`。
> - 补法二：**`perf sched record` + `perf sched latency`，root 下实测可用**（35573 个样本、有 `Avg delay`/`Max delay` 表）。
> - 补法三：`bpftrace` 的 `kprobe:schedule` + `kretprobe:schedule` 按进程统计 off-CPU 纳秒，root 下实测可用。
> - **第一反应不要是什么**：不要把「火焰图里没有它」当成「它没有卡」。
