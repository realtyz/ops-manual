## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **网络排障的顺序是：连接状态 → 协议栈计数器 → 收包侧丢弃 → 最后才考虑抓包。**
>   - 证据：本机 `ss -s`、`nstat`、`softnet_stat` 三条只读命令一共花了不到 1 秒，就给出了「重传 0、队列溢出 0、收包丢弃 0」的结论，此时抓包没有任何额外信息。
> - **`ss -ti` 能把「网络慢」和「应用慢」分开。**
>   - 证据：用 `netem` 在 `lo` 上注入 50 ms 延迟后，`ss -ti` 显示 `rtt:100.533/0.406`、`minrtt:100.131`、`cwnd:10`、`app_limited`、`unacked:1`——RTT 与注入值吻合，说明链路侧生效。
> - **`netem` 的丢包率会比配置值高，因为 loopback 上两个方向都要过一次。**
>   - 证据：配置 `loss 20%`，200 个包实测 **35.5%** 丢失；这与 `1 − 0.8 × 0.8 = 36%` 吻合——**不是小样本波动，是请求和应答各过一次**。
> - **`load` 高、CPU 空、进程杀不掉 = 在看 D 状态。**
>   - 怎么验证：`vmstat` 的 `b` > 0、`ps -o stat,wchan` 显示 `D`、`cat /proc/<pid>/wchan` 给出内核阻塞函数。
> - **`perf` 采样看不到「不在 CPU 上」的时间，而 `wchan`/`sched` 能。**
>   - 证据：`perf sched record` 在本机被拒（`No permissions to read /sys/kernel/tracing//events/sched/sched_switch`），但 `cat /proc/<pid>/wchan` 直接给出 `hrtimer_nanosleep`。

## 1. 网络侧的三层证据

### 1.1 第一层：连接状态分布

```bash
ss -s | head -3          # 验证：全局套接字统计，看 timewait/closed/orphaned 哪个异常
ss -lnt                  # 验证：监听队列（Recv-Q = 已完成握手但未被 accept 的连接数）
```

```text
$ ss -s
Total: 184
TCP:   3004 (estab 0, closed 3001, orphaned 0, timewait 3001)
```

这条记录是一次「3000 条短连接」实验之后的现场（0.104 秒内建立并关闭 3000 条连接）。它要说明的是：**`ss -s` 一眼就能看出「是不是连接堆积型问题」**：

- `timewait` 暴涨 → 短连接过多或服务端主动关闭（子笔记 10 有量化模型）；
- `closed` 很大 → 大量连接处于非活跃状态，可能是泄漏；
- `orphaned` 非 0 → 有连接已无进程持有，通常是应用没有正确关闭。

### 1.2 第二层：协议栈计数器

```bash
nstat -az | grep -E "^(TcpActiveOpens|TcpInSegs|TcpOutSegs|TcpRetransSegs|TcpExtListenOverflows|TcpExtTCPTimeouts)"
```

```text
TcpActiveOpens                  3014               0.0
TcpInSegs                       53870              0.0
TcpOutSegs                      53788              0.0
TcpRetransSegs                  0                  0.0
TcpExtListenOverflows           0                  0.0
TcpExtTCPTimeouts               0                  0.0
```

四个判据：

| 计数器 | 含义 | 判据 |
| --- | --- | --- |
| `TcpRetransSegs / TcpOutSegs` | 重传率 | 超过 0.1%～1% 就要查链路（本机 0/53788 = 0） |
| `TcpExtListenOverflows` | accept 队列溢出次数 | 增长说明应用来不及 `accept()`（不是网络慢，是应用慢） |
| `TcpExtTCPTimeouts` | 超时重传 | 增长通常伴随重传率上升 |
| `TcpExtTCPBacklogDrop` / `TcpExtListenDrops` | SYN 队列丢弃 | 短时间大量新连接时出现（连接风暴、健康检查过密） |

### 1.3 第三层：收包侧丢弃

```bash
awk '{s+=$2} END{print "softnet dropped:", s}' /proc/net/softnet_stat   # 验证：收包来不及处理
ip -s link                                                              # 验证：网卡级收发与错误计数
```

```text
softnet dropped: 0
```

`/proc/net/softnet_stat` 第 2 列是**每个 CPU 的丢包计数**；它非 0 说明「包到了内核但软中断没来得及处理」，方向是收包侧 CPU 不足、软中断没分散、或网卡队列配置问题。配合 `mpstat` 看 `%soft` 集中在哪个核。

物理机上还可以加一层 `ethtool -S <dev>` 看网卡的 `rx_*_errors`/`rx_dropped`/`pause` 计数（本机是 Hyper-V 虚拟网卡，**未实测**）。

## 2. `ss -ti`：把「网络慢」和「应用慢」分开

`ss -ti` 给出的是一条连接的内部状态。本机用 `netem` 注入 50 ms 单向延迟后（往返约 100 ms）实测：

```bash
unshare -U -r -n bash -c "ip link set lo up; tc qdisc add dev lo root netem delay 50ms; \
  python3 tcptest.py & sleep 3; ss -ti state established | head -4"
```

```text
Recv-Q Send-Q Local Address:Port  Peer Address:Port Process
0      64         127.0.0.1:42025    127.0.0.1:57308
        cubic wscale:7,7 rto:304 rtt:100.533/0.406 ato:40 mss:32768 pmtu:65535
        rcvmss:536 advmss:65483 cwnd:10 bytes_sent:1536 bytes_acked:1472
        bytes_received:1536 segs_out:25 segs_in:27 data_segs_out:24 data_segs_in:24
        send 26.1Mbps lastsnd:24 lastrcv:24 lastack:24 pacing_rate 52.2Mbps
        delivery_rate 2.62Mbps delivered:24 app_limited busy:2328ms unacked:1
        rcv_space:65483 rcv_ssthresh:65483 minrtt:100.131 snd_wnd:65536
```

| 字段 | 含义 | 怎么用 |
| --- | --- | --- |
| `rtt:x/y` | 平滑 RTT / 偏差（ms） | 与对端/链路预期对比；本机 100.533 与注入的 50×2 吻合 |
| `minrtt` | 观测到的最小 RTT | **最干净的链路时延证据**（不受排队影响） |
| `retrans` / `unacked` | 重传次数 / 未确认字节数 | 重传持续增长说明丢包 |
| `cwnd` / `snd_wnd` | 拥塞窗口 / 对端通告窗口 | 小 `cwnd` 说明链路受限；小的 `snd_wnd` 说明**对端**处理不过来 |
| `app_limited` | 发送受限是因为应用没提供数据 | **看到它就说明瓶颈不在网络，而在应用** |
| `delivery_rate` / `pacing_rate` | 实测投递速率 / 发送节奏 | 与实际吞吐对照 |

**用法要点**：`app_limited` 是这张表里最有价值的一行。它明确告诉你「连接不是被网络卡住，而是没有数据要发」，避免把应用问题当成网络问题查半天。

## 3. 什么时候才需要抓包

抓包是 L3 手段（拷贝每个报文到用户态），应该严格是「兜底」而不是「起手」：

```text
计数器干净（重传 0、队列溢出 0、softnet 丢弃 0）
        │
        ├─ 现象仍然存在 → 先怀疑应用侧（app_limited、慢调用、锁、GC），而不是链路
        └─ 现象指向链路 → 用 ss -ti 的 minrtt/retrans 定位到具体连接
                              │
                              └─ 仍无法解释 → 限时限量抓包（-c 200 -w file，指定 host/port）
```

本机实测的「计数器干净」状态：`TcpRetransSegs=0`、`TcpExtListenOverflows=0`、`softnet dropped=0`。在这种状态下抓包，最有价值的产出通常只是确认「没有异常报文」。

## 4. 故障注入：用 `netem` 亲手造一次延迟与丢包

没有 root 也能做：在**用户+网络命名空间**里我们有该命名空间的 `CAP_NET_ADMIN`，注入只影响这个隔离网络，不会碰宿主。

```bash
unshare -U -r -n bash -c "ip link set lo up; tc qdisc add dev lo root netem delay 50ms; ping -c 3 -q 127.0.0.1 | tail -2"
unshare -U -r -n bash -c "ip link set lo up; tc qdisc add dev lo root netem loss 20%; ping -c 200 -q -i 0.02 127.0.0.1 | tail -2"
```

```text
注入 50 ms 单向延迟：
3 packets transmitted, 3 received, 0% packet loss, time 2003ms
rtt min/avg/max/mdev = 100.085/100.164/100.227/0.059 ms
qdisc netem 8001: root refcnt 2 limit 1000 delay 50ms

注入 20% 丢包、200 个包：
200 packets transmitted, 129 received, 35.5% packet loss, time 4779ms
```

### 4.1 为什么配了 20% 却丢了 35.5%

这不是采样波动，而是**算术**：`netem` 挂在 `lo` 的**出口**上，一次 ping 的请求和应答都要经过 `lo` 的出口，各自有 20% 的概率被丢：

```text
往返成功率 = 0.8 × 0.8 = 0.64
实测丢失率 = 1 − 0.64 = 36%      # 40 个样本时 30%、200 个样本时 35.5%
```

**这条结论比「样本量要够」更重要**：注入的方向、位置与观测口径决定了你看到的数字。做丢包演练前，先想清楚「丢的是请求、应答还是两者」。

### 4.2 验证要多少样本

小样本同样会放大误差：10 个包时实测 30%，200 个包时 35.5%，理论值 36%。**结论：验证丢包率要用足够的样本（几百到几千个包），并且先算清楚理论期望值。**

## 5. 「在等」：D 状态、`wchan` 与网络存储

网络只是「等待」的一种。更常见的是进程卡在存储或锁上：

```bash
vmstat 1 5                                             # 验证：b 列（D 状态任务数）是否持续 > 0
ps -eo pid,ppid,stat,wchan:24,etime,args | awk '$3 ~ /D/'   # 验证：哪些进程处于 D 状态
cat /proc/<pid>/wchan                                  # 验证：内核里阻塞在哪个函数
mount | grep -E "nfs|cifs|fuse"                        # 验证：是否挂了网络存储
dmesg -T | tail -30                                    # 验证：块设备/文件系统是否报错
```

```text
$ ps -o pid,stat,wchan:24,comm -p <pid>
  PID STAT WCHAN                    COMMAND
 1788 S    hrtimer_nanosleep        python3
```

本机的 `hrtimer_nanosleep` 是一个正常睡眠进程的阻塞点。如果这里出现 `nfs_wait_*`、`*_rpc_wait`、`blk_*` 之类的函数，方向就非常明确了：**它在等一个外部资源**。

| 现象 | 方向 | 证据 |
| --- | --- | --- |
| `b` 持续 > 0，`wchan` 是 `nfs*`/`rpc*` | 网络存储阻塞 | `mount` 里的 `nfs` 挂载、存储服务端状态 |
| `b` 持续 > 0，`wchan` 是 `blk_*` | 块设备层阻塞 | `iostat -x`、`dmesg` 里的 IO 错误 |
| `b` = 0，但进程 `S` 且 CPU 空 | 可能在等锁 / 等对端 | `/proc/<pid>/sched` 的 `se.wait_sum`、`ss -ti` 的 `app_limited`、应用侧的锁指标 |

### 5.1 为什么 `perf` 看不到这段等待

`perf record` 基于采样，只覆盖「线程在 CPU 上」的时间。一个 90% 时间在等 IO 的线程，在火焰图里可能完全看不到。补这个盲区的三条路：

1. `/proc/<pid>/wchan`（当前阻塞点，无需权限）；
2. `/proc/<pid>/sched` 的 `se.wait_sum`（累计等待时间，无需权限）；
3. `perf sched record` / `offcputime`（**需要 tracefs 或 root**）——本机实测被拒：

```text
$ perf sched record -o s.data -- sleep 2
event syntax error: 'sched:sched_switch'
                     \___ can't access trace events
Error:  No permissions to read /sys/kernel/tracing//events/sched/sched_switch
```

> [!warning] D 状态进程的处置纪律
> `kill -9` 对 D 状态进程无效（信号要等它回到用户态才处理）。正确顺序是：先恢复它等待的资源（网络存储服务端、块设备、锁），必要时 `umount -f`/重启整机，而且**先取证**（`dmesg`、`wchan`、`mount` 的输出）。细节见子笔记 14。

## 6. 生产动作：网络侧判定记录（有产出物）

一份可交付的网络侧判定记录包含四段：

1. **连接分布**：`ss -s` 与 `ss -lnt` 的原始输出（TIME_WAIT、监听队列 Recv-Q）。
2. **协议栈计数器**：`nstat` 的重传 / 超时 / 队列溢出，以及**重传率**的计算式与数值。
3. **收包侧**：`softnet_stat` 的 dropped、`ip -s link` 的收发与错误。
4. **结论与方向**：如果计数器全部干净，明确写出「主机侧网络无明显异常，方向转向应用侧（`app_limited`）或下游依赖」；如果有异常，给出具体计数器与时间点。

这份记录的价值在于：**它把「网络有没有问题」这个争论变成一个可以用三条命令复核的事实。**

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 「网络慢就抓包」 | 先看 `ss -s`/`nstat`/`softnet_stat`；本机三条只读命令 1 秒内排除网络 |
| 「`ss -s` 的 timewait 高就是攻击」 | TIME_WAIT 是主动关闭方的正常状态；要先算「端口数 ÷ TIME_WAIT 时长」的上限（子笔记 10） |
| 「有重传就是网络坏了」 | 低频重传是 TCP 的正常行为；要看**重传率**与是否与延迟拐点对齐 |
| 「配 20% 丢包，实测 35% 说明工具不准」 | `lo` 上请求与应答各过一次：`1 − 0.8² = 36%`，实测 35.5% 与理论吻合 |
| 「`ListenOverflows` 增长是网络问题」 | 它是**应用没及时 `accept()`**；方向是应用侧 |
| 「`rtt` 大就是链路差」 | 先看 `minrtt`（最干净的链路时延）与 `app_limited`；大 `app_limited` 说明瓶颈在应用 |
| 「`perf` 能看出进程在等什么」 | `perf` 采样只覆盖在 CPU 上的时间；用 `wchan`/`sched` 或（有权限时）`perf sched` |
| 「D 状态进程 `kill -9` 就行了」 | 信号要等进程回到用户态才处理；要先恢复它等的资源 |
| 「容器里的 `ss`/`nstat` 能看到宿主网络」 | 只能看到本 netns 的连接与计数器，宿主视角要另外取（子笔记 11） |

## 决策练习

**场景**：一个跨机房调用的服务报「偶发超时」。`nstat` 显示 `TcpRetransSegs` 在缓慢增长，`ss -s` 的 TIME_WAIT 正常，`softnet_stat` 的 dropped 为 0。同事建议「抓包看是不是中间设备丢包」。

**选项**：

- **A. 直接抓包 1 小时，等下一次超时。**
- **B. 先算重传率（`TcpRetransSegs / TcpOutSegs`），再用 `ss -ti` 看具体连接上的 `minrtt`/`retrans`/`cwnd`/`app_limited`，把「链路丢包」与「应用写不动」分开，再决定是否抓包。**
- **C. 调整 TCP 参数（`tcp_retries2`、`tcp_rmem`）把超时压下去。**

**为什么选 B**：`TcpRetransSegs` 缓慢增长可能是几十万分之一的重传率，也可能高达百分之几——**不看分母就没有判断依据**。`ss -ti` 的 `minrtt` 是判断链路质量的干净证据，`app_limited` 则直接排除「应用没数据要发」这种伪网络问题；`cwnd` 小说明拥塞，`snd_wnd` 小说明对端处理不过来。这三个字段能把范围收到具体方向。

**为什么不选 A**：抓包是 L3 手段，成本高、数据量大，而且「偶发」意味着大部分抓到的报文都是正常的。正确顺序是先算比率、看单连接状态，再对**已经定位到的那条连接**做限时限量的抓包。

**为什么不选 C**：改内核参数在根因未明时是最危险的动作——它会在生产机上引入不可回滚的变量，而且可能只是把「丢包」换成「更长的超时」，让用户感知更差。

## 要点自测

> [!question]- 「网络慢」的排查顺序是什么？为什么通常不需要抓包？
> - 连接状态（`ss -s`/`ss -lnt`）→ 协议栈计数器（`nstat`，看重传率与队列溢出）→ 收包侧（`softnet_stat`、`ip -s link`）→ 单连接状态（`ss -ti`）→ 最后才是抓包。
> - 前三层都是 L0，1 秒内可完成；本机实测这三层给出的结论是「重传 0、队列溢出 0、收包丢弃 0」，此时抓包没有额外信息。
> - **第一反应不要是什么**：不要 `tcpdump -i any` 一开了事。

> [!question]- `ss -ti` 里的 `minrtt`、`cwnd`、`snd_wnd`、`app_limited` 分别说明什么？
> - `minrtt`：观测到的最小 RTT，是链路时延的干净证据（不受排队影响）。
> - `cwnd`：本端拥塞窗口；小说明发送受拥塞控制限制。
> - `snd_wnd`：对端通告的接收窗口；小说明**对端**处理不过来。
> - `app_limited`：发送受限是因为应用没提供数据 → **瓶颈在应用，不在网络**。
> - 本机实测（注入 50 ms 单向延迟）：`rtt:100.533/0.406 minrtt:100.131 cwnd:10 app_limited unacked:1`。

> [!question]- 为什么 `netem` 配 20% 丢包实测却是 35.5%？
> - `netem` 挂在 `lo` 的出口上，请求和应答各经过一次，两次都要成功才算一次成功的 ping：`0.8 × 0.8 = 0.64`，即丢失率约 36%。
> - 实测 10 个包 30%、200 个包 35.5%，与理论吻合。
> - 教训：做注入演练前先算清楚「丢的是几个方向」，并准备足够的样本量。

> [!question]- 进程处于 D 状态时，为什么 `kill -9` 无效？正确做法是什么？
> - 信号只在进程回到用户态时才被处理；D 状态是不可中断睡眠，内核路径不会去检查待处理信号。
> - 正确顺序：先取证（`dmesg`、`ps -o stat,wchan`、`mount`）→ 恢复它等待的资源（网络存储、块设备、锁）→ 必要时 `umount -f` 或重启整机。
> - **第一反应不要是什么**：不要反复 `kill -9`，也不要在没取证前直接重启。

> [!question]- 为什么 `perf` 火焰图里看不到「在等」的时间？怎么补？
> - `perf record` 是采样型，只在线程位于 CPU 上时才会采到；等待时间不产生样本。
> - 补法一：`/proc/<pid>/wchan`（当前阻塞点）+ `/proc/<pid>/sched` 的 `se.wait_sum`（累计等待），无需权限。
> - 补法二：`perf sched record` / `offcputime`，需要 tracefs 或 root（本机实测报 `No permissions to read /sys/kernel/tracing//events/sched/sched_switch`）。
> - **第一反应不要是什么**：不要把「火焰图里没有它」当成「它没有卡」。
