## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **没有基线就没有「变慢了」——只有「现在是这个数」。**
>   - 怎么验证：问自己「如果领导问『到底慢了多少』，我能不能给出一个数字和它的比较对象」。
> - **基线必须带采集条件；条件不同的数字不可比。**
>   - 证据：同一块盘的 `w_await` 在「`stress-ng --hdd 2` 并发写」窗口是 6.59 ms、`wareq-sz=3781`，在「4 KiB 随机写 `libaio` `iodepth=64`」窗口是 0.09～0.27 ms、`wareq-sz=4`——差几十倍，但两个都不算异常。
> - **五组数据：身份与规模 / CPU 与负载 / 内存 / IO / 网络。**
>   - 证据：本机一次取证快照（**8208 字节**）就覆盖了身份（`nproc=4`、`load`）、CPU（`vmstat`/`mpstat`）、内存（`/proc/meminfo` + PSI）、网络（`ss -s`、`softnet`），还额外带上了 IO 的 `iostat -x`。
> - **历史指标要「先确认有数据」再依赖它——本机这一条现在是通的。**
>   - 证据：`sysstat 12.6.1-2` 已安装、`sysstat-collect.timer` 为 `active`/`enabled`、`/var/log/sysstat/sa19` 存在（28688 字节），`sar -u` 直接读回 08:00～08:30 的真实采样（`Average: all 1.33 user / 1.01 system / 97.61 idle`）。
> - **容量要按核、按 p99 算，不能按整机平均算。**
>   - 证据：单个自旋进程让整机 `%usr` 只有 **25.04%**，而目标核 **100.00%**；同核 4 个竞争者让固定工作量只剩 **21%**（2647 万 → 556 万次/2 s）。

## 1. 五组数据

| 组 | 采什么 | 频率 / 时机 | 注意 |
| --- | --- | --- | --- |
| **身份与规模** | `nproc`、CPU 型号、`MemTotal`、swap、磁盘型号与数量、网卡速率、虚拟化类型 | 变更时更新 | 没有它，后面的数字无法解释 |
| **CPU 与负载** | 业务高峰的 `load`、`vmstat` 的 `r`/`cs`/`us`/`sy`、`mpstat -P ALL` 的**每核分布** | 每周一次 + 变更后 | 必须留每核数据，否则无法回答单核问题 |
| **内存** | `MemAvailable` 水位、`/proc/pressure/memory`（`avg` 与 `total` 都要）、swap 使用 | 每周一次 | 记 PSI 比记 `MemFree` 有用得多 |
| **IO** | `iostat -x` 的 `w_await`/`aqu-sz`/`%util`/`wareq-sz`；`fio` 四象限基线 | 每周一次 + 换盘后 | 必须记块大小、队列深度与 `ioengine` |
| **网络** | `ss -s` 的连接分布、`nstat` 的重传/超时、带宽峰值 | 每周一次 | 记「重传率」而不是「重传次数」 |

三条采集纪律：

1. **业务高峰与低谷各采一份。** 只采低谷会得到「一切正常」的假象。
2. **写清采集时间与当时在跑什么。** 半年后无法解释的基线等于没有基线。
3. **同一份基线用同一套命令采。** 换了工具或参数，数值就不可比（例如 `iostat` 的采样间隔会影响 `await` 的平均含义）。

## 3. IO 基线：`fio` 四象限

```bash
fio --name=seqwrite    --filename=/data/fio.bin --size=1G --rw=write    --bs=1M --ioengine=psync  --iodepth=1  --direct=1 --runtime=15 --time_based
fio --name=seqread     --filename=/data/fio.bin --size=1G --rw=read     --bs=1M --ioengine=psync  --iodepth=1  --direct=1 --runtime=15 --time_based
fio --name=randwrite4k --filename=/data/fio.bin --size=1G --rw=randwrite --bs=4k --ioengine=libaio --iodepth=32 --direct=1 --runtime=15 --time_based
fio --name=randread4k  --filename=/data/fio.bin --size=1G --rw=randread  --bs=4k --ioengine=libaio --iodepth=32 --direct=1 --runtime=15 --time_based
```

本机样例（VMware 虚拟盘上的 ext4 on LVM，`direct=1`，结论**不可外推到物理盘**，但格式可照抄）：

| 象限 | 吞吐 | `clat` p50 | `clat` p99.9 |
| --- | --- | --- | --- |
| 顺序写 1 MiB，`psync`，`iodepth=1` | 1495 MiB/s | 635 µs | 1876 µs |
| 顺序读 1 MiB，`psync`，`iodepth=1` | 1708 MiB/s | 562 µs | 1434 µs |
| 随机写 4 KiB，`libaio`，`iodepth=32` | 27.3k IOPS（107 MiB/s） | 1090 µs | 3228 µs |
| 随机读 4 KiB，`libaio`，`iodepth=32` | 47.5k IOPS（185 MiB/s） | 619 µs | 1958 µs |

**四象限的意义**：业务负载永远落在某个象限或它的混合里。数据库随机读写偏右下两格，日志/备份偏左上两格。有了这四格，你才能回答「这块盘对我们的业务到底够不够」。

> [!warning] 上生产前的四个注意
> 1. **`fio` 是有写入的破坏性操作**，只能在可丢弃的目录 / 可快照实验机上做，并预先设定 `--size` 与 `--runtime` 上限。
> 2. **`--iodepth` 只在 `libaio`/`io_uring` 下生效。** 本机同一个 `--iodepth=32`，默认的 `psync` 只跑出 **11.7k IOPS**（头部会打印 `ioengine=psync, iodepth=1`），换 `libaio` 才有 **27.3k IOPS**。**基线卡里必须写 `ioengine`。**
> 3. **虚拟化环境的绝对值要打折扣**——本机 `dd iflag=direct` 读 512 MiB 能跑到 8.3～11.1 GB/s，比顺序读基线（1708 MiB/s）还高一个量级，说明宿主层仍在缓存。趋势与相对关系仍然可信。
> 4. **不要在被测业务的高峰期做**——那既污染基线，也污染业务。

## 4. 历史指标：先确认有数据

「昨天下午 3 点开始变慢」这类复盘，靠的是历史指标。三条纪律：

1. **先确认采集开了。** 本机实测：

2. **确认保留天数够用。** sysstat 的 `HISTORY=` 默认往往只有 7 天，复盘「上周的问题」就不够；建议至少两周。
3. **也可以手动生成一份做验证。** 注意 `sadc` 不在 `PATH` 上，它在 `/usr/lib/sysstat/sadc`：

> [!tip] `sadf -d` 的时间戳是 UTC
> 本机时区就是 `Etc/UTC (UTC, +0000)`，所以导出值看起来一致；但**在 +0800 的机器上，`sadf -d` 导出的是 UTC，需要换算出本地时间**再和变更记录对齐。本条实测的导出格式是 `2026-09-19 08:38:43 UTC`，**带明确的时区后缀**——这正是「时间戳口径要写清」的示范。

四项配合：实时（`vmstat`/`iostat`）+ 短期（Prometheus 之类的时序库）+ 历史（`sar`）+ 事后（应用日志与变更记录）。阶段 9 讲了三者的口径与保留策略。

## 5. 容量评估：按核算，不按整机平均算

### 5.1 三个实测事实

1. **整机平均完全看不到单核饱和。** 单核打满时整机 `%usr` 只有 **25.04%**、`load` 只有 **0.34**（4 核机器）。
2. **同核竞争会非线性地吃掉算力。** 独占时 **26,473,519 次/2 s** → 1 个竞争者 **12,461,811 次（−52.9%）** → 4 个竞争者 **5,564,871 次（−79.0%，只剩约 21%）**。
3. **延迟的中位数先受保护、尾部先崩坏。** 竞争者从 0 加到 15 个，`p50` 一直在 8.06～8.13 ms，而 `max` 从 **8.36 ms** 涨到 **40.87 ms（4.9 倍）**。

### 5.2 结论：容量要按「核」和「p99」算

| 错误算法 | 正确算法 |
| --- | --- |
| 整机 CPU 使用率 = 60%，还有 40% 余量 | 每个核的 `%usr` 分布，最热核的余量是多少 |
| 平均延迟 20 ms，达标 | p99 = 300 ms 是否达标；p99 拐点对应的流量是多少 |
| 线程数 = 核数就够 | 关键服务是否需要独占核（cpuset），是否需要留核给中断与软中断 |
| 扩容后必然变快 | 先确认没有单核热点/锁竞争/单线程 acceptor，否则扩容无效 |

### 5.3 从基线到容量结论

```text
基线：4 核机器，业务高峰 QPS 1200，最热核 %usr 72%，p99 = 85 ms
观察：QPS 1500 时最热核 %usr 91%，p99 = 210 ms
结论：该服务的能力上限受「最热核」约束，而不是 4 核的总算力；
      在现有单线程热点未拆之前，扩容副本比提升单机核数更有效。
```

**判据的核心是「拐点」而不是「阈值」**：记录「QPS 是多少时 p99 开始非线性上升」，比记录「CPU 到 80% 告警」有用得多。

## 6. 生产动作：建立一份基线卡（有产出物）

```text
第 1 步：确认采集条件（业务高峰 / 低谷 / 备份窗口各一份）

```

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 「凭印象知道正常水位」 | 半年后无法复核；领导问「慢了多少」也答不出来 |
| 「只采低谷时段」 | 得到「一切正常」的假象，业务高峰的问题完全看不见 |
| 「基线数字不写采集条件」 | 同一块盘的 `w_await` 可以是 0.17 ms 也可以是 6.59 ms，条件不同不可比 |
| 「只记整机 CPU 使用率」 | 单核打满时整机只有 25.04%（4 核）；必须留每核分布 |
| 「`fio --iodepth=32` 就是 32 个请求在飞」 | 只有 `libaio`/`io_uring` 才是；`psync` 忽略 `iodepth`（本机 11.7k vs 27.3k IOPS） |
| 「sysstat 装了就一定有历史」 | 要确认 `sysstat-collect.timer` 是 `active`/`enabled` 且 `/var/log/sysstat/saNN` 存在；本机三项都通过 |
| 「`sar -u` 读不出东西就是没采集」 | 也可能读的是**当天**文件而当天还没产生样本；用 `sar -f <file>` 指定文件、或先 `sadc` 手动造一份 |
| 「`sadf -d` 导出的时间就是本地时间」 | 导出的是 **UTC**（本机实测带 `UTC` 后缀）；不同时区要换算后再和变更记录对齐 |
| 「fio 跑一次峰值带宽就够」 | 业务负载落在不同象限；四象限（顺序/随机 × 读/写）都要有 |
| 「容量按平均值算」 | 平均掩盖单核与长尾；要按最热核与 p99 拐点算 |
| 「扩容一定能解决」 | 单核热点 / 锁竞争 / 单线程 acceptor 场景下无效 |
| 「在生产机的高峰期跑 fio」 | 既污染基线也污染业务；`fio` 必须在隔离环境跑 |

## 决策练习

**场景**：你要为一批新采购的机器建立性能基线，这批机器上会跑数据库和日志服务。你有两天时间，且这些机器还没有承载生产流量。

**选项**：

- **A. 跑一次 `fio` 的顺序读峰值带宽，记录下来当基线。**
- **B. 采集五组数据（身份 / CPU / 内存 / IO / 网络），IO 部分跑 `fio` 四象限并记录块大小、队列深度与 `ioengine`，历史指标确认可用，写成一份带采集条件的基线卡。**
- **C. 先上线，等出问题时再对照「当时的表现」。**

**为什么选 B**：数据库的负载是随机读写（右下象限），日志服务是顺序写（左上象限）——**一个峰值带宽数字无法回答「这批机器够不够」**。而「身份与规模」决定了后面所有数字能解释到什么程度（本机 `nproc=4` 与 `MemTotal 7894 MiB` 就直接决定了「整机一个核打满 = 25%」这个换算），「采集条件」决定了这些数字半年后还能不能复核。

**为什么不选 A**：顺序读峰值是所有象限里最好看的数字，也是最没用的单一数字。只跑它，等于给数据库和日志服务各准备了一份错误的期望。

**为什么不选 C**：等出问题时，你已经失去了「干净基线」这个唯一的比较对象——那时候机器上跑的、装的、配的都已经不是出厂状态了。

## 要点自测

> [!question]- 一份性能基线卡至少要包含哪五组数据？为什么是这五组？
> - 身份与规模（`nproc`、`MemTotal`、swap、磁盘与网卡型号）、CPU 与负载（含**每核**分布）、内存（`MemAvailable` + PSI）、IO（`await`/`aqu-sz`/`%util`/`wareq-sz` + `fio` 四象限）、网络（连接分布 + 重传率）。
> - 这五组对应性能排障的全部资源层；缺哪一组，遇到对应问题时就没有比较对象。
> - **关键**：必须写清采集时间与当时在跑什么，否则数字不可比。

> [!question]- 为什么 `fio` 要跑四象限而不是跑一个峰值带宽？
> - 不同业务落在不同象限：数据库随机读写、日志顺序写、备份顺序读、大文件传输混合。
> - 本机样例：顺序写 1495 MiB/s（`bs=1M, psync, iodepth=1`）、随机写 107 MiB/s（`bs=4k, libaio, iodepth=32`）——同一个盘差 14 倍。
> - 记录时必须带上块大小、队列深度与 `ioengine`，否则两个数字不可比。

> [!question]- 为什么容量要按核、按 p99 算？
> - 整机平均掩盖单核：实测单核 100.00% 时整机 `%usr` 只有 25.04%、`load` 0.34。
> - 竞争非线性：同核 4 个竞争者让固定工作量只剩约 21%。
> - 长尾才是用户感受：`p50` 全程不动时 `max` 涨了 4.9 倍。
> - 结论：记录「最热核余量」与「p99 拐点对应的流量」，而不是「整机 CPU 60%」。

> [!question]- 复盘「昨天下午 3 点变慢」之前，第一步要确认什么？
> - 确认历史指标**真的有数据**：`systemctl is-active sysstat-collect.timer`、`ls /var/log/sysstat/`、`sar -u`（本机三项都通过，`sa19` 存在且能读出 08:00～08:30 的采样）。
> - 确认保留天数够用（`HISTORY=` 默认常常只有 7 天）。
> - 确认时间戳口径（`sadf -d` 导出的是 UTC，本机实测带 `UTC` 后缀，需要和本地时间换算）。
> - **第一反应不要是什么**：不要一上来就 `sar` 然后对着空输出发呆——先确认采集开了没有。
