# 时间花在「等」上时，看哪里

一个进程的墙钟时间里，通常只有一小部分在 CPU 上。剩下那部分可能是等一个锁、等一次磁盘读、等一个下游的响应、等下一个定时周期——**这些时间在基于 CPU 采样的工具里全都不存在**。这不是工具的缺陷，是采样原理决定的：采样的对象是"此刻谁在 CPU 上"，没上 CPU 的时间自然没有样本。

以下读数取自一台 4 vCPU、内核 6.8 的 Ubuntu 24.04 虚拟机：`perf` 6.8.12、iproute2 6.1.0，网卡是虚拟化的单队列 `e1000`。**网络注入在隔离的命名空间里做**，所以下面 `ss -ti` 的字段是在受控延迟下取得的，不是线上值；网卡多队列与 offload 这一类手法在该机上无法演示。

所以"慢"至少要分成两半：**在算**与**在等**。"在等"这一类里，最便宜也最容易被忽略的证据是"它在哪个内核函数上等"，最难量化的是"一共等了多少"；而网络之所以经常成为"等"的主要产地，是因为它的延迟有好几个来源，其中一个来源的改善并不影响另外几个。

## 1. 两种「在等」

先分清两类完全不同的等待，量它们的工具也不同：

| 类型 | 进程状态 | 时间花在哪 | 主要判据 |
| --- | --- | --- | --- |
| **任务在等**（off-CPU） | `S`（可中断睡眠）、`D`（不可中断）、`R` 但没跑上 | 等锁、等 IO 回来、等定时器、排队等 CPU | `wchan`、内核栈、自愿切换计数、运行队列延迟 |
| **网络在等**（on-the-wire） | 进程可能正在跑，也可能睡着 | 数据往返的固有延迟、重传、排队、对端处理 | `ss -ti` 的 RTT/重传、协议栈计数器、软中断队列 |

判断顺序上有个便宜的入口：**看进程的状态分布**。

- 大量 `D` 状态：不可中断地等，通常是存储或内核态路径；
- 大量 `S` 状态且时间很长：可中断地等，锁、下游、定时器都有可能；
- 大量 `R` 但机器不忙：在运行队列里排队——这是 CPU 争抢（见《争抢为什么不按比例缩放》）。

## 2. 三样证据，从「在等」到「等什么」

### 2.1 `wchan`：此刻阻塞在哪个内核函数

`/proc/<pid>/wchan` 给出**当前**阻塞点的内核函数名（符号）。它是"等什么"最短路径的答案，但有两处边界：

- 它只是**一个瞬间**。要多看几次，或者看整体分布，不能凭一次读数下结论；
- 用户态的自旋锁、无锁队列的等待、以及 GC 停顿，都不会体现在 `wchan` 里——它们不在内核里等。

一个 `clock_nanosleep` 的进程，三个字段会给出互相印证的一组读数：

```text
# 说明：数值仅示意、不代表你的机器
/proc/<pid>/wchan     hrtimer_nanosleep
/proc/<pid>/status    State:  S (sleeping)
                      voluntary_ctxt_switches:        1
                      nonvoluntary_ctxt_switches:     0
```

### 2.2 `/proc/<pid>/stack`：内核栈，把一段路径说完整

`wchan` 只给最内层，`/proc/<pid>/stack` 给出完整的内核调用链，能一次看到"在等谁、由谁调起来"：

```text
[<0>] hrtimer_nanosleep+0xa2/0x170
[<0>] common_nsleep+0x43/0x60
[<0>] __x64_sys_clock_nanosleep+0xf1/0x180
[<0>] do_syscall_64+0x87/0x180
[<0>] entry_SYSCALL_64_after_hwframe+0x78/0x80
```

**边界**：读别的进程的 `stack` 需要 `CAP_SYS_ADMIN`（root）。同一个进程 root 读得到、普通用户只得到 `Permission denied`；生产上拿不到 root 时，这条路直接不通，退到 `wchan` 与应用自己的埋点。

### 2.3 自愿切换计数与 off-CPU 的三种手段

`/proc/<pid>/status` 的 `voluntary_ctxt_switches` / `nonvoluntary_ctxt_switches` 是**累计值**，必须差分才有速率含义。自愿切换高说明"经常主动让出"，但不说让给了谁，要配 `wchan` 或栈才有结论。

要真正量化 off-CPU 时间（而不是只看到"在等"），有三条路：

| 手段 | 需要什么 | 给什么 | 代价 |
| --- | --- | --- | --- |
| `/proc/<pid>/wchan` + 自愿切换差分 | 只读权限 | "在等"的证据，没有时长 | 极低，生产机上可以做 |
| `perf sched record` + `perf sched latency` | root、tracefs | 每个任务的运行时间与**调度延迟**（从可运行到真正跑上） | 中；root 下可用（一次 1 秒采集约 0.2 MB、451 个样本；长一点的窗口可到几万个样本） |
| off-CPU eBPF（如 `bpftrace` 挂 `schedule`） | root、`CONFIG_BPF`、BTF | 按进程/栈聚合的阻塞时长 | 中；root 下可用 |
| `perf record`（CPU 采样） | 视事件而定 | **只有"在 CPU 上"的时间** | 低 |

最关键的一行是第四行：**`perf record` 采不到 off-CPU，不是它不好用，而是它回答的是另一个问题**。看到"热点函数很集中、总时间却对不上墙钟"，第一反应应该是"其余时间它在等"，而不是"采样器不准"。

有一条经验判据：**如果某个函数在采样里占了很高比例，但它做的事看起来很少，那多半是在里面等**（比如一个 `read` 或 `futex` 调用在栈里占据高位）。

## 3. 网络：为什么「ping 正常」与「服务慢」经常同时成立

网络这一层最常见的误判是拿一个低延迟的小报文探测去否定整条链路。要分开看三件事：

### 3.1 延迟有四个来源

一次请求的往返时间至少包含：

1. **传播延迟**：由物理距离决定，跨机房、跨地域时是硬下限；
2. **排队与缓冲**：路径上的队列（包括本地 `qdisc`、网卡队列、交换机缓冲）在拥塞时把延迟抬起来；
3. **传输延迟**：由带宽与报文大小决定，大包在低速链路上要更久；
4. **对端处理**：对端应用/协议栈花的时间，网络指标里看不到。

`ping` 量的是小 ICMP 报文的往返，通常体现的是第 1 项（有时加一点第 2 项）。**它不覆盖应用 payload 大小、也不覆盖对端处理**，所以"`ping` 1 ms 但接口 p99 800 ms"是完全可以同时成立的。

### 3.2 单连接的真相在 `ss -ti`

`ss -ti` 打印 TCP 的连接级内部状态，能把"网络慢"和"应用慢"分开：

- `rtt` / `minrtt`：当前与历史最小的往返时间。**`rtt` 远大于 `minrtt`** 说明中间有排队或拥塞；两者都高说明链路本身就有延迟；
- `retrans` / `lost` / `dsack_dups`：重传与丢包线索；
- `cwnd` / `snd_wnd`：发送窗口与实际可用接收窗口。窗口被打满说明受带宽/时延限制；
- `app_limited`：**投递速率被应用层限制**（对应内核 `tcp_info` 的 `tcpi_delivery_rate_app_limited`，即上面的 `delivery_rate` 不是被网络压低的），说明瓶颈不在网络；
- `unacked` / `bytes_acked` / `bytes_received`：配合算有效吞吐与是否在等 ACK。

关于这些字段的出处要说清楚：`man 8 ss` 的 `-i` 字段清单**并不完整**——`app_limited`、`delivery_rate`、`busy`、`rwnd_limited`、`sndbuf_limited` 等实际会打印的字段都不在 man 页里，权威依据是 iproute2 的实现与内核 `struct tcp_info` 的字段名。另外 **`app_limited` 只在标志非 0 时打印**（看不到它不等于这一侧没有被应用限制，只代表采样那一刻标志为 0）。

把一条连接放进隔离的网络命名空间，并注入 50 ms 单向延迟后，`ss -ti` 打印出这样一组字段：

```text
# 说明：数值仅示意、不代表你的机器
cubic wscale:7,7 rto:301 rtt:100.293/0.055 ato:40 mss:32768 pmtu:65535
cwnd:10 bytes_sent:2496 bytes_acked:2496 bytes_received:2496
send 26.1Mbps lastsnd:112 lastrcv:112 lastack:12 pacing_rate 52.3Mbps
delivery_rate 2.62Mbps delivered:40 app_limited busy:3910ms
minrtt:100.123 snd_wnd:65536
```

判读：`rtt` 100.293 ms、`minrtt` 100.123 ms，**两者几乎相等**，说明延迟是链路固有的（注入的 50 ms × 2），不是排队造成的；对照组同一命名空间未注入时的往返是 `0.008/0.024/0.083/0.007 ms`（min/avg/max/mdev），差四个数量级。而 `app_limited` 出现，说明这一侧的投递速率受应用供给限制。

### 3.3 计数器优先，抓包最后

网络排障的顺序应当是**先看连接状态，再看协议栈计数器，然后看收包侧丢弃，接着看单连接状态，最后才考虑抓包**。计数器是"低成本、可长期开着"的证据：

| 计数器 | 含义 | 判据 |
| --- | --- | --- |
| `TcpRetransSegs / TcpOutSegs` | 重传占比 | 长期 > 0.1%～1% 要查链路；本机某窗口 14/654775 ≈ 0.002% |
| `TcpExtTCPTimeouts` | 重传超时次数 | 增长说明有丢包或严重乱序 |
| `TcpExtListenOverflows` / `ListenDrops` | 已完成握手但队列放不下 / 被丢弃 | **增长说明是队列问题，不是网络抖动**——服务端可能一条日志都没有 |
| `/proc/net/softnet_stat` 的 dropped | 收包侧因预算耗尽丢弃 | 非 0 说明软中断来不及处理 |
| `ss -s` 的 `timewait` | 处于 `TIME_WAIT` 的连接数 | 判据是"临时端口数 ÷ 60 秒"的上限，不是绝对数量 |

`nstat` 的默认输出本身就是**两次读数之间的差值**（`-a` 才是显示累计值），这一点必须记清楚，否则会把"开机以来一共 14 次重传"当成"现在正在重传"。本机某窗口 `TcpRetransSegs 14`、`TcpOutSegs 654775`，重传率 0.002%——**只看 14 这个数会以为有问题，算比率才知道正常**。

**抓包的门槛**：计数器干净就不该抓包。真要抓，必须限时限量（`-c`、`timeout`、`port` 过滤），落到文件而不是刷屏，并预先想好"抓到什么算证据"。判断有没有丢包，看 `tcpdump` 收尾那行报的 `packets dropped by kernel`——它是零才说明这次采集本身没丢。

## 4. 耦合现象：会同时抬高「等」的两类东西

有一类故障既不缺 CPU、也不缺内存，却让所有请求都变慢，原因是**共享资源的排队被拖长了**：

- **DNS 解析**。名字解析在请求路径的前端，一次解析放大成多次查询时（`search` 域 + `ndots`），每个请求都要多等一轮往返。指纹是**耗时分布出现固定台阶**（例如每次都恰好多 5 秒——那是解析器的超时重试）。本机 `/etc/resolv.conf` 指向 `systemd-resolved` 存根（`nameserver 127.0.0.53`），实际解析行为由 `resolvectl` 看，不能只看文件；
- **共享的下游或锁**。一个串行的下游（单实例数据库、一把全局锁、一个写热点）会把所有并发请求折成排队。指纹是"本地资源都不忙、吞吐有一个上不去的平台"。

这两类的共同排障动作是相同的：**先量分布（有没有台阶、有没有平台），再量本地资源（确认不忙），然后沿调用链往下游找那个串行点**。

**第一反应不要做什么**：不要把"没在 CPU 上"读成"没问题"；不要用单次 `wchan` 读数下结论；不要用 `ping` 给应用延迟背书；不要在计数器干净时抓包，也不要在抓包时不设上限。

## 常见误解

| 说法 | 事实 |
| --- | --- |
| "`perf` 采出来只有 20% 的时间在 `main`，采样有问题" | CPU 采样只覆盖"在 CPU 上"的时间，其余时间它在等。要另用 off-CPU 手段 |
| "进程在 `S` 状态就是没事" | `S` 是"可中断睡眠"，等锁、等下游、等定时器都在这里，可能正是慢的原因 |
| "`wchan` 显示 `hrtimer_nanosleep` 所以它在睡，跟性能无关" | 单次读数只说明那一刻；要看多次采样与整体分布，并结合业务语义 |
| "普通用户也能看 `/proc/<pid>/stack`" | 需要 `CAP_SYS_ADMIN`；普通用户会被直接拒绝 |
| "`ping` 正常说明网络没问题" | `ping` 是小报文，不含应用 payload 与对端处理时间 |
| "`rtt` 高就是链路差" | 要跟 `minrtt` 对照：`rtt` 远高于 `minrtt` 才是排队/拥塞 |
| "`nstat` 显示 14 次重传，链路有问题" | 默认输出是窗口差值，要看比率；14/654775 是正常的 |
| "服务端没有日志，说明请求没到" | 可能是监听队列溢出（`ListenOverflows` 增长）或丢在收包侧，应用根本没机会处理 |
| "抓包最准，直接抓" | 计数器优先；抓包要限时限量落盘，且要预先定义"什么算证据" |

## 要点自测

**问：为什么 `perf record` 看不到进程"等锁"的时间？**
答：它采样的对象是"此刻在 CPU 上执行的任务"，阻塞在锁上的任务不在 CPU 上，因此没有样本。要看这段要么用调度追踪（`perf sched`）要么用 off-CPU eBPF，两者都需要 root。

**问：`D` 状态和 `S` 状态在排障上的区别是什么？**
答：`D` 是不可中断等待，通常是存储/内核路径，且对它 `kill -9` 不会立刻生效（信号要等它回到可中断状态）；`S` 是可中断等待，锁、下游、定时器都可能。两者都要落到 `wchan`/栈才有个体结论。

**问：`ss -ti` 里 `rtt` 与 `minrtt` 几乎相等，说明什么？如果 `rtt` 远大于 `minrtt` 呢？**
答：几乎相等说明延迟是链路固有的（本机注入 50 ms 单向延迟后 `rtt` 100.293 ms、`minrtt` 100.123 ms）；远大于则说明路径上有排队或拥塞，且当前正处在拥塞状态。

**问：服务端没有收到请求的日志，客户端却出现超时，哪两个计数器最值得先看？**
答：`TcpExtListenOverflows`/`ListenDrops`（监听队列溢出，请求已经握手但没被 `accept`）与 `/proc/net/softnet_stat` 的 dropped（收包侧丢弃）。前者是应用 accept 不及时，后者是内核收包来不及。

**问：什么时候必须抓包，什么时候不该抓？**
答：计数器与连接状态都干净、但现象仍在，且需要看具体报文内容或时序时才抓；计数器已经指出方向（如重传率高、队列溢出）时不抓，直接沿计数器给的方向走。

**问：一个接口"偶发慢"，耗时分布出现固定 5 秒台阶，最可能是什么？**
答：名字解析的超时重试。要区分解析链路（`getent hosts`、`resolvectl query`）与网络链路（`ss -ti`、计数器），因为"解析慢"与"网络慢"的证据完全不同。

**第一反应不要做什么**：不要把"没在 CPU 上"读成"没问题"；不要用单次 `wchan` 读数下结论；不要在计数器没看之前抓包。
