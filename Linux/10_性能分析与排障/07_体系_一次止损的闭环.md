# 一次止损的闭环

找到根因不等于事情结束。从"决定动手"到"组织知道这件事、下次更早发现"，中间还有一段独立的路：**选动作 → 执行 → 验收 → 写报告 → 落改进**。这条线走不完，故障就会以同样的路径再来一次；这条线走歪了，止损动作本身会成为第二次故障。

这条路有五个必须各自答清的问题：什么算修好了、先动哪一个、怎么验证结果、怎么让复盘可复核、以及改进项由谁在什么时候验收。

## 一、决策：什么算「修好了」

止损的起点不是"选哪个命令"，是先把验收标准写下来。**没有验收标准的动作不是止损，是碰运气。**

三件套验收：

| 维度 | 判据 | 例子 |
| --- | --- | --- |
| 指标 | 回到基线或 SLO 之内，并给出具体数值 | p99 从 900 ms 回到 120 ms 以内；错误率回到 0.1% |
| 业务 | 真实业务路径成功（不是探活接口） | 下单链路成功率回到 99.9% |
| 观察窗口 | 覆盖一个业务周期，且周期性故障要覆盖 2～3 个周期 | 变更后连续观察 15～30 分钟 |

**四个不算"修好了"的说法**：

- "重启之后好了"——现场被毁，原因未知，还会复发；
- "指标不报警了"——可能是阈值被调了，或者数据没上来；
- "我改了参数，感觉快多了"——没有数值就没有验收；
- "跟以前一样了"——和哪个"以前"比？恢复到哪个口径？

还有一条容易被忽略的：**恢复之后立刻再取一份基线**。性能故障的过程本身就是一次负载实验，恢复后的读数是你手上最新的一份"正常长什么样"。

## 二、动作：五种手段的排序

止损手段的代价差别很大，排序的原则是"**影响面从小到大**"，而不是"哪个最有效"：

| 手段 | 适用现象 | 代价与影响面 | 回滚方式 |
| --- | --- | --- | --- |
| 限流 | 单服务/单任务争抢资源，其他服务被拖累 | 只影响被限流方，影响面最小 | 去掉配额（cgroup 配额在启动时生效，改完要重启；`--scope` 随命令结束自动释放） |
| 摘流量 | 单实例行为异常，集群还有余量 | 影响该实例的在线请求 | 放回流量（要有"从外部探失败、从本机探成功"的验证） |
| 回滚 | 与近期变更强相关，且回滚路径验证过 | 回到已知状态，但会丢掉新版本能力 | 反向执行；**前提是回滚路径在实验机上跑过** |
| 扩容 | 资源确实不足，且瓶颈不是单线程热点 | 有成本与时间，且对单线程热点无效 | 缩容；注意扩容后要复核瓶颈是否转移 |
| 重启 | 状态泄漏、句柄耗尽、无法在线清理 | **毁掉现场**，且必然复发 | 无（重启不是可回滚动作，是最后手段） |

三条排序原则：

1. **能限流就不摘流量，能摘流量就不重启**。每一档都在扩大影响面；
2. **一个动作只改一个变量**。同时限流又扩容，事后无法判断哪个起了作用；
3. **先取证再动手**。例外只在一处成立：影响面还在扩大、且不需要现场就能确定动作时，可以先止损——但要**同时**记录时间、动作和当时看到的指标。

每个动作在执行前写下三件套：

| 动作 | 预期效果 | 验收指标 | 回滚方式 / 触发条件 | 观察窗口 |
| --- | --- | --- | --- | --- |
| 给批处理加 `CPUQuota=20%` | 批处理吞吐降到约 20%，宿主上延迟敏感服务的 p99 回落 | 宿主服务 p99 < 130 ms；错误率 < 0.5% | 删除 drop-in → `daemon-reload` → `restart`；触发条件：宿主服务 p99 未回落或批处理超时率上升 | 变更后连续 15 分钟 |

**回滚要先写"触发条件"，不能只写命令。** 触发条件必须写成"指标 + 阈值 + 持续时间"，否则执行人会在现场临时判断。

## 三、执行与验收：三件套怎么测

### 3.1 三件套的执行顺序

1. **记录动作前的读数**（同一口径、带时间戳）；
2. **执行动作**，同时记录动作发生的时间点；
3. **等一个观察窗口**再读，不要立刻下结论（很多动作的效果需要几十秒到几分钟才稳定）；
4. **对同一组指标取第二次读数**，与基线比较。

### 3.2 用 cgroup 配额做一次完整演练

本机的限流实验可以直接作为这一站的样板（`systemd-run --scope -p CPUQuota=20%`，系统级 scope，落在 `/system.slice/lab10cpu.scope`）：

```text
# 说明：数值仅示意、不代表你的机器
不限流：        29,823,329 次 / 2.00 s
CPUQuota=20%：  5,757,053 次 / 2.00 s        # 19.30%
cpu.max = 20000 100000
cpu.stat（约 2 秒后）：nr_periods 21、nr_throttled 20、throttled_usec 1597813
```

四条验收结论都能从这一组数里得出：

- **配置生效了吗**：`systemctl show <unit> -p CPUQuotaPerSecUSec` 与 unit 里写的一致；
- **内核侧看到了吗**：`cpu.max` 显示 `20000 100000`（每 100 ms 只有 20 ms CPU 时间）；
- **真的起作用了吗**：吞吐降到 19.30%，`nr_throttled/nr_periods = 20/21`，几乎每个周期都被掐；
- **回滚干净吗**：`--scope` 随命令结束自动释放（`systemctl list-units "lab10*"` 为空、`/sys/fs/cgroup/system.slice/lab10*` 不存在）。

最后一条尤其重要：**验收包含"回滚路径有效"**，而不只是"目标达成了"。

### 3.3 复盘：四个必须回答的问题

1. **现象与根因之间是什么关系**。根因不是现象——"磁盘慢"是现象，"备份任务在业务高峰期以 3.7 MiB 的大块写打满了设备队列"才是可以改的东西；
2. **为什么之前的防线没拦住**。这一问比"谁干的"有价值得多：是没监控、阈值不对、还是压根没有这条防线；
3. **影响面算清了吗**。受影响的用户、服务、数据范围各是什么；
4. **改进项由谁、什么时候、怎么验收**。

**"人为失误"不算根因。** 它是症状：流程允许一个人在不该动的时刻动，或者没有手段在他动之前拦住。

## 四、报告：六段结构

| 段 | 写什么 | 判据 |
| --- | --- | --- |
| 时间线 | 事实发生的顺序：变更、指标拐点、告警、开始处置、每个动作 | 每条带时间戳；事实与推测分开写 |
| 影响面 | 谁受影响、多严重、多久 | 带数值与比较对象 |
| 证据 | 每一层的判定结论与支撑字段 | 引用具体字段与取值，能复现 |
| 根因 | 可以改的那个机制 | 不是"磁盘慢"这类现象，也不是"人为失误" |
| 止损动作 | 做了什么、验收结果、回滚状态 | 三件套齐全 |
| 长期改进 | 方向 + owner + 期限 + 验收方式 | 每条可检查 |

一份填好的例子（用本机的单核超卖现场）：

```text
# 模板，数值仅示意
时间线：14:30 发布 v2.31；14:32 订单服务 p99 开始上升；14:36 告警触发；14:38 开始只读取证；14:41 p99 稳定在 900 ms
影响面：3 个实例中 2 个（同宿主机）受影响；p99 从基线 120 ms 涨到 900 ms（约 7.5 倍）；5xx 从 0.1% 涨到 2.3%
证据：整机 %usr 25.04%、load 0.34，但 CPU 2 达 100.00%；
      pidstat -u -t 显示 PID 45062 的线程独占 100%；taskset -cp 亲和性为 2；
      同核竞争使固定工作量吞吐从 26,473,519 次/2 s 降到 5,564,871 次（−79.0%）；
      延迟探针 max 从 8.36 ms 涨到 40.87 ms（p50 几乎不动）
根因：批处理单线程任务与延迟敏感服务被调度到同一颗核，且没有做 CPU 隔离或配额
止损：给批处理加 CPUQuota=20%（吞吐降到 19.30%），宿主服务 p99 回落至 130 ms 以内，观察 15 分钟无复发
改进：① 批处理与在线服务分核（cpuset）——owner A，两周；② 单核饱和度纳入告警——owner B，一周；
      ③ 扩容评审改用「最热核 + p99 拐点」——owner C，下次评审前
```

**两版报告的差别**：面向管理层的一版保留时间线、影响面、当前状态与下一步；面向复盘的一版保留全部证据与改进项。"重启后好了"在两版里都不合格。

## 五、横切线

### 5.1 证据线：动手之前把现场留住

止损与取证是有冲突的：重启会毁掉现场，`strace` 会拖慢业务。处理顺序是：

- **先取只读、低代价的证据**（一屏命令、计数器、`/proc` 里的文件），再取有代价的（`strace`、抓包），最后才动手；
- **任何动作前记下时刻与当时的指标**，这样即使现场被毁，至少时间线还在；
- 明确哪些证据**重启即失**：`/proc/<pid>/*`、cgroup 里的账本（单元结束后目录被回收）、进程内的堆与连接状态、`dmesg` 的环形缓冲（可能被覆盖）。

### 5.2 回滚线：可回滚是设计出来的

三种"回滚"要分清：

- **配置回滚**：改回配置文件；前提是知道改了什么、有备份、且知道需不需要重启才生效（systemd 资源类属性只在启动时生效）；
- **版本回滚**：回到上一个版本；前提是上一个版本的产物还在、且数据结构兼容；
- **数据回滚**：恢复备份；代价最大，通常只在数据被破坏时用。

**两种假回滚**：重启服务（现场没了但原因还在）、换回文件但没让进程重新加载（配置回滚了，行为没回滚）。判断方法是**验证生效值**，而不是验证文件内容。

### 5.3 留痕线：账本有寿命

cgroup 的 `memory.events`、`cpu.stat`、`memory.peak` 都存在 cgroup 目录里，**单元结束目录就被回收**。想复盘就要在它还活着的时候采集。系统级服务默认 `OOMPolicy=stop`：一次 cgroup OOM 会停掉整个单元，现场随之消失；本机实测用 `-p OOMPolicy=continue` 才能留下 `memory.events` 与内核日志：

```text
# 说明：数值仅示意、不代表你的机器
memory.max 536870912   memory.peak 536870912
memory.events：low 0 / high 0 / max 46 / oom 1 / oom_kill 1 / oom_group_kill 0
dmesg：oom-kill:constraint=CONSTRAINT_MEMCG, ... oom_memcg=/system.slice/lab10mem.service, task=python3,pid=48832,uid=0
       Memory cgroup out of memory: Killed process 48832 (python3) total-vm:1066564kB, anon-rss:522752kB, ...
```

判读要点：`memory.peak` 顶到 `memory.max` 说明曾经贴边；`max 46` 远大于 `oom_kill 1` 说明内核先尝试回收了 46 次；`constraint=CONSTRAINT_MEMCG` 说明是 cgroup 上限而不是整机内存耗尽。这几条合起来才能回答"它撞的是谁的上限"。

一个版本门槛要记住：**`memory.peak` 的"读"与"写重置"是两个门槛**。读它（文件存在、`cat` 有值）早得多；而**把峰值写回 0 以重新计数**的能力要晚得多（内核提交 `c6f53ed8f213` 落在 6.12）。在老内核上会出现"`cat memory.peak` 有值、`echo 0 > memory.peak` 报错"这种组合，写脚本前先确认目标机器在哪个门槛之后。

### 5.4 改进线：从"这次好了"到"下次更早"

四个方向，每个都要有 owner 与验收方式：

| 方向 | 典型改进项 | 验收方式 |
| --- | --- | --- |
| 监控与告警 | 补上这次靠人肉发现的信号（单核饱和、`pgscan_direct`、`nr_throttled` 的速率） | 在演练里能触发告警 |
| 容量与配置 | 按最热核与 p99 拐点重算容量；给服务加上限 | 基线卡更新；上限的生效值与内核侧一致 |
| 架构与隔离 | 拆单线程热点；把批处理与在线服务分核/分机 | 同负载下最热核余量达标 |
| 流程与演练 | 把这次的判据写进运行手册；补一次演练 | 演练记录里能复现这次的观测指纹 |

**第一反应不要做什么**：不要在没有验收标准的情况下动手；不要在同一个窗口里改两个变量；不要把重启当回滚；不要在复盘里把根因写成"人为失误"；不要在 cgroup 被回收之后才想起来要账本。

## 常见误解

| 做法或说法 | 后果或事实 |
| --- | --- |
| "先重启一下试试" | 会毁掉现场，且原因不明、必然复发。它是最后手段，不是第一步 |
| 重启后服务正常了，结案 | "正常了"不是验收；没有指标、业务与观察窗口的结论不可复核 |
| 一次同时限流和扩容 | 一个动作改了多个变量，事后无法归因 |
| 只写回滚命令，不写触发条件 | 执行人会在现场临时判断，"什么时候退"变成靠感觉 |
| 假设改完配置文件就生效 | systemd 资源类属性只在启动时生效；要验证生效值，而不是文件内容 |
| 复盘把根因写成现象 | "磁盘慢"是现象；可以改的是"谁在什么时候以什么方式打了设备" |
| 复盘把根因写成"人为失误" | 那是症状。要问的是哪条防线缺位 |
| 改进项写"加强监控"这类句子 | 没有 owner、期限、验收方式，等于没写 |
| 拿容器内的 `top` 当止损验收依据 | 配额与限流计数在宿主侧 cgroup 里；容器内看不到限流 |
| 认为 `OOMPolicy` 默认会保留现场 | 系统级服务默认 `stop`，整个单元会被停掉，cgroup 目录随之回收 |
| 用"删掉配额"当回滚就完事 | 还要验证内核侧文件已回到原状、业务指标已恢复 |
| 演练完不做清理复核 | 残留 unit / netns / 进程会在下一次实验里制造假现象 |

**第一反应不要做什么**：不要在没有验收标准的情况下动手；不要在同一个窗口里改两个变量；不要把重启当回滚；不要在复盘里写"人为失误"；不要在 cgroup 被回收之后才想起来要账本。

## 要点自测

**问：为什么"重启之后好了"不算修好了？**
答：它同时毁掉现场与原因，且必然复发；它不满足三件套验收（指标回到基线、业务验收、观察窗口），也没有回答"哪条防线缺了"。

**问：止损动作的排序原则是什么？为什么限流排在最前？**
答：按影响面从小到大：限流 → 摘流量 → 回滚 → 扩容 → 重启。限流只影响被限流方，是唯一能"只收窄一个任务"而不动在线流量的手段。

**问：回滚方案里最容易漏的一行是什么？**
答：触发条件。只写命令的回滚方案在现场等于没有方案；触发条件要写成"指标 + 阈值 + 持续时间"。

**问：怎么验证一个 cgroup 配额"真的生效了"？**
答：三层验证：unit 属性与配置一致（`systemctl show <unit> -p CPUQuotaPerSecUSec`）、内核侧文件一致（`cpu.max` 为 `20000 100000`）、行为一致（吞吐降到 19.30%、`nr_throttled/nr_periods = 20/21`）。

**问：为什么 cgroup OOM 的现场常常"不见了"？怎么保留？**
答：账本存在 cgroup 目录里，单元结束目录即被回收；系统级服务默认 `OOMPolicy=stop`，一次 OOM 就停掉整个单元。要在它活着时采集，或把 `OOMPolicy` 设为 `continue`（本机实测这样才读到 `memory.events` 与内核日志）。

**问：复盘里"为什么之前的防线没拦住"为什么比"谁干的"更重要？**
答："谁干的"导向追责，不改变系统；防线缺口才是下次能更早发现的抓手，它对应到监控、容量、隔离、流程四类可执行的改进项。

**问：改进项要写成什么样才算可验收？**
答：有动作、有 owner、有期限、有验收方式，并明确去向（立即修 / 排期 / 显式接受风险并写明批准人）。

**第一反应不要做什么**：不要用重启换取"看起来恢复了"；不要把止损动作和取证顺序颠倒；不要在没写清根因之前写改进项。
