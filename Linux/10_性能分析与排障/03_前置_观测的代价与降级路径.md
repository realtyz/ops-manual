## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **观测一定会改变被测对象，问题只是改变多少。**
>   - 证据：同一份「2 万次系统调用」的 workload，直接跑 28～29 ms，套上 `strace -c -f` 后 2317～2342 ms，**约 80 倍**。
> - **采样有四个固定盲区：亚窗口脉冲、工具首屏的历史平均、不在 CPU 上的时间、被聚合掉的长尾。**
>   - 证据：写 1000 MiB 的 `dd` 全程只花了 1～2 秒，`pidstat -d 1` 采样窗口里**一条记录都没有**，只抓到了 `iostat` 自己 1.33 kB/s 的噪声。
> - **工具不可用是常态：本机 `perf` 没有硬件计数器，`perf sched` 没有 tracefs 权限，eBPF 被内核参数禁用。**
>   - 证据：`perf stat -e cycles` 显示 `<not supported>`；`perf record -e cycles` 能写出文件但 `perf report` 报 `The ... data has no samples!`；`perf sched record` 报 `No permissions to read /sys/kernel/tracing//events/sched/sched_switch`。
> - **降级路径的第一层永远是 `/proc` + 低开销采样 + 应用自己的指标。**
>   - 怎么验证：只用 `vmstat`、`/proc/<pid>/{status,sched,io,wchan}`、`ss -s`、`nstat` 和日志，也能把「在算还是等、哪个进程、等什么」说到八成准确。
> - **取证纪律只有三条：先取证再动手、记录命令与输出、最小影响优先。**
>   - 怎么验证：问自己「如果 5 分钟后现象消失了，我手上的记录能不能支撑一个结论」。

## 1. 观测者效应：三种改变被测对象的方式

### 1.1 时间扰动：每次事件都停下来等你

`strace` 是最典型的例子：它让内核在每次系统调用时停下来，把参数与返回值交给 `strace`，再由 `strace` 恢复进程。

```text
$ t0=$(date +%s%N); python3 sys20k.py; t1=$(date +%s%N); echo "baseline $(( (t1-t0)/1000000 )) ms"
baseline 29 ms
$ t0=$(date +%s%N); strace -c -f python3 sys20k.py; t1=$(date +%s%N); echo "strace $(( (t1-t0)/1000000 )) ms"
strace 2317 ms
$ strace -c -f python3 sys20k.py 2>&1 | tail -1
100.00    0.401201           9     40570        91 total
```

三次重复：基线 29/29/28 ms，`strace` 2317/2322/2342 ms。被记录的调用一共 **40570 次**（2 万个 `getpid` + 2 万个 `stat`，其余是解释器启动开销），每次拦截的代价约 60 µs —— 对 4 万次调用就是 2.4 秒。

**推论**：`strace` 只适合「短时间 + 小范围」。真正有用的用法是先 `-c` 汇总、限定 `-e trace=` 只看几个调用、加 `timeout` 限时，并且优先挂到**已经定位到的一两个进程**上。

### 1.2 资源占用：观测本身消耗 CPU、内存与 IO

- `perf record -F 99` 每秒产生 99 次采样中断，每次要保存调用栈；`-g` 加调用栈时代价更高。
- `tcpdump` 要把报文从内核复制到用户态再写盘；在万兆链路上未加限制的抓包会直接吃掉可观的 CPU 与磁盘带宽（本机**未实测**）。
- 高频 `pidstat`/`iostat` 在几十个进程 / 十几块盘上也会累积；本机实测 `pidstat -d 1` 的输出里就出现了 `iostat` 自己（1.33 kB/s）——**采样工具会把自己写进证据里**。

### 1.3 行为改变：主动注入会永久改变现象

`tc netem`、`fio`、`stress-ng` 不是观测，是**制造现象**：

```text
$ unshare -U -r -n bash -c "ip link set lo up; tc qdisc add dev lo root netem delay 50ms; ping -c 3 -q 127.0.0.1 | tail -1"
rtt min/avg/max/mdev = 100.085/100.164/100.227/0.059 ms
```

注入的 50 ms 单向延迟会一直生效，直到你 `tc qdisc del`。所以这类操作必须满足三个条件：**在隔离环境（命名空间/独立机器）、有明确上限、跑完清理并复核**。绝不能在生产机上「顺手试一下」。

## 2. 采样偏差：四个固定盲区

### 2.1 盲区一：亚窗口脉冲

如果采样间隔是 1 秒，任何短于 1 秒的尖刺都可能整个落在两次采样之间。

本机实证：用 `dd` 写 1000 MiB（无 `direct`，走页缓存，约 1～2 秒完成）时同时跑 `pidstat -d 1`，结果里**没有任何一行属于 `dd`**：

```text
$ pidstat -d 1 2
Average:     1000      2517      0.00      1.33      0.00       0  iostat
```

而同一时段的 `iostat -x 1`（设备层）抓到了完整的写流量。**结论：脉冲型问题要在设备层或更密的采样里看，不要用进程级 1 秒采样去证明「没有 IO」。**

### 2.2 盲区二：工具首屏是「自开机以来」的平均

`top` 第一次输出里的 CPU 与进程百分比是自开机累计的平均值，而不是「现在」。本机实测：`top -b -n1` 的首屏在负载已经开始之后仍显示接近空闲的值，必须按 `1` 切到每核视图、或者取第二屏，才反映当前状态。

同理，`ps` 的 `%CPU` 是**进程生命周期内**的平均，不是瞬时值：

```text
$ ps -o pid,stat,pcpu,comm -p <pid>
   1515 R     100 python3
```

这里的 `100` 之所以看起来像瞬时值，是因为进程才跑了 4 秒、全程满载。一个跑了 10 小时、只在最近 1 分钟变热的进程，`ps` 的 `%CPU` 会被历史稀释。

### 2.3 盲区三：不在 CPU 上的时间

`perf record` 是**基于采样**的：只有当线程在 CPU 上运行时才可能被采到。一个卡在锁上、卡在 IO 上、卡在调度队列里的线程，在 `perf` 的火焰图里可能完全看不到——这就是 off-CPU 分析存在的理由。

补这个盲区的手段（本机**未实测**，需要权限或工具）：

| 手段 | 需要什么 | 看什么 |
| --- | --- | --- |
| `perf sched record` + `perf sched latency` | tracefs 可读（本机被拒） | 每个进程被调度出去的时长与原因 |
| `offcputime`（bcc/bpftrace） | root + `CAP_BPF` | 按调用栈统计 off-CPU 时间 |
| `/proc/<pid>/wchan` + `sched` | 无需权限 | **当前**阻塞在哪个函数、累计等待时间 |

本机实测的权限边界：

```text
$ perf sched record -o s.data -- sleep 2
event syntax error: 'sched:sched_switch'
                     \___ can't access trace events
Error:  No permissions to read /sys/kernel/tracing//events/sched/sched_switch
Hint:   Try 'sudo mount -o remount,mode=755 /sys/kernel/tracing/'
```

但 `/proc` 这条路是通的，而且足够回答「在等什么」：

```text
$ cat /proc/<pid>/wchan
hrtimer_nanosleep
$ grep -E "^(State|voluntary|nonvoluntary)" /proc/<pid>/status
State:  S (sleeping)
voluntary_ctxt_switches:        1
nonvoluntary_ctxt_switches:     0
```

（`/proc/<pid>/stack` 需要 ptrace 权限，本机非 root 实测 `cat: /proc/self/stack: Permission denied`。）

### 2.4 盲区四：被聚合掉的长尾

这一点在子笔记 01 已展开：平均值会把 1% 的极慢请求摊平。补它的方法是**分位数 + 直方图**，而不是「再多取几个平均值」。注意分位数本身也有窗口与算法口径，跨窗口比较前先对齐口径（阶段 9 有专门一节）。

## 3. 工具不可用的四种典型，以及怎么绕过去

### 3.1 没有硬件 PMU

PMU（Performance Monitoring Unit，性能监控单元）是 CPU 上做硬件性能计数的部件。虚拟化环境（WSL、多数云主机）常常不给它：

```text
$ perf stat -e cycles,instructions,cache-misses -- true
   <not supported>      cycles:u
   <not supported>      instructions:u
   <not supported>      cache-misses:u
```

更隐蔽的一种情况：`perf record -e cycles` **不会报错**，它会老老实实写一个数据文件出来：

```text
$ perf record -e cycles -o c.data -- true
[ perf record: Captured and wrote 0.002 MB c.data ]
$ perf report -i c.data --stdio
Error:
The c.data data has no samples!
```

**绕过去**：改用软件事件与采样——`perf stat -e task-clock,context-switches,page-faults`、`perf record -F 99` 仍然可用（本机实测 `perf report` 能定位到热点符号 `_PyEval_EvalFrameDefault`，494 个采样）。想从「热点函数」继续走到「指令级」或「缓存未命中」，就必须换到有 PMU 的物理机。

### 3.2 没有 tracefs 权限

见 2.3 的实测报错。`perf sched`、`perf trace`、`frace`/`ftrace` 都依赖 `/sys/kernel/tracing`。

**绕过去**：用 `/proc/<pid>/sched` 的 `nr_switches`/`se.wait_sum` 看累计等待，用 `pidstat -w` 看切换速率；需要完整调用栈的 off-CPU 分析只能在有 root 的机器上做。

### 3.3 没有 eBPF

eBPF（extended Berkeley Packet Filter，扩展的伯克利包过滤器）把观测程序挂进内核执行，开销比 `strace` 低得多；配套的 BTF（BPF Type Format）描述内核数据结构。

本机内核参数 `kernel.unprivileged_bpf_disabled=2`（2 表示**永久禁止**非特权 BPF），非 root 无法使用 `bpftrace`/`bcc`；即使有 root，还要有匹配的 BTF/头文件与 `libbcc`。

**绕过去**：eBPF 能做的事里，约八成可以用「`/proc` 证据链 + 采样类工具 + 应用埋点」拼出来（子笔记 08 给出对应表）。eBPF 真正的不可替代之处是**低开销的全量观测**（例如「每个进程的每一次 `open`」），这类需求只能等有权限的机器。

### 3.4 缺共享库

解包运行的工具常常「下载成功、一跑就报缺库」：

```text
$ fio --version
fio: error while loading shared libraries: libaio.so.1t64: cannot open shared object file
```

**绕过去**：按 `ldd <binary> | grep "not found"` 的提示逐个把依赖包也解包下来，最后补全 `LD_LIBRARY_PATH`。本机 `fio` 一共补了 12 个以上依赖（`libaio1t64`、`libibverbs1`、`librdmacm1t64`、`libpmem1`、`libnbd0`、`libgfapi0`、`librados2`、`librbd1`、`libglusterfs0`、`libgfrpc0`、`libgfxdr0`、`libnl-3-200`、`libnl-route-3-200`、`libceph-common`、`libboost-*`、`libndctl6`、`libdaxctl1`），`stress-ng` 补了 4 个（`libIPSec_MB`、`libJudy`、`libGLESv2`、`libsctp`）才启动。

> [!warning] 工具目录不要放 `/tmp`
> 本机在写作过程中遇到过**一次 `/tmp` 下解包目录在会话中途消失**（`/usr/lib/tmpfiles.d/tmp.conf` 的规则是 30 天，未定位到具体清理者）。稳妥做法是把解包目录放在 `$HOME` 下（本机后来使用 `$HOME/devtools`），并在脚本里检查目录是否存在、不存在就重建。

## 4. 降级阶梯：目标 → 有工具 → 没工具

排障方案要能「降级执行」。把目标拆开，每一层都准备两个版本：

| 我要回答 | 有工具时 | 没工具时（只靠 `/proc` + 采样 + 日志） |
| --- | --- | --- |
| 是算还是等？ | `perf stat` 看 user/sys 比例 | `vmstat` 的 `us/sy/wa`、`cat /proc/<pid>/stat` 的 utime/stime |
| 哪个函数在烧 CPU？ | `perf record -F 99 -g` + 火焰图 | 语言自带的 profiler、日志里的阶段耗时、二分注释法 |
| 哪个系统调用多/慢？ | `strace -c` / `-T` | `/proc/<pid>/syscall`（当前调用）、`/proc/<pid>/io`（真实读写量） |
| 在等什么？ | `perf sched` / `offcputime` | `/proc/<pid>/wchan`、`State: D`、`/proc/<pid>/sched` 的等待时间 |
| 哪个线程？ | `pidstat -u -t`、`perf top -t` | `top -H -p <pid>`、`ps -L -p <pid>`、`/proc/<pid>/task/*/stat` |
| 谁的 IO？ | `blktrace` / `biosnoop` | `iostat -x`（设备层）+ `pidstat -d`（进程层）+ `/proc/<pid>/io` |
| 丢包在哪一跳？ | `tcpdump` + 抓包分析 | `nstat`、`/proc/net/softnet_stat`、`ss -ti`、`ip -s link` |
| 内存花在哪？ | `heaptrack` / 语言层 profiler | `/proc/<pid>/smaps_rollup`、`pmap -x`、`/proc/<pid>/status` 的趋势 |

这张表的核心意思是：**降级路径不是「查不了」，而是「精度低一档、需要更依赖推理与对照」**。

## 5. 三条取证纪律

1. **先取证，再动手。** 重启、杀进程、改参数都会毁掉现场。救火动作与排查动作要分开记录。
   - 具体做法：准备一个一次性取证脚本（子笔记 04 给出完整脚本与实测输出），故障时先跑它，再考虑任何变更。
2. **记录命令与输出。** 用 `script -f session.log` 全量留档，或 `命令 | tee` 保存关键证据；记录时间与时区（`date -Is`）。
   - 时间对齐是跨系统复盘的前提（阶段 9 讲过时钟与格式基线）。
3. **最小影响优先。** 先用 `-c`/`-s` 汇总再用明细；先对单个进程再对全体；先限时（`timeout 10 strace ...`）再考虑长时间观测；故障中不做高风险变更。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 「先挂 `strace -f -p` 慢慢看」 | 实测约 80 倍减速；2.4 秒的 `strace` 时间还会干扰你正在测的现象 |
| 「`perf` 能看到所有慢的地方」 | `perf` 只采在 CPU 上的时间；等锁、等 IO 的时间要靠 off-CPU 手段 |
| 「`perf record -e cycles` 没报错就是采到了」 | 本机实测它写出了文件但 `perf report` 报 `no samples!`；先看 `perf stat` 的 `<not supported>` |
| 「1 秒采样没看到 IO，就不是 IO 问题」 | 本机实测 1～2 秒的 `dd` 完全落在采样窗口之外 |
| 「`ps` 的 `%CPU` 是实时值」 | 它是进程生命周期内的平均，会被历史稀释 |
| 「观测工具不影响业务」 | 采样有开销、抓包有开销、注入会永久改变现象 |
| 「工具没装就是查不了」 | 本机 8 个主力工具都没装，靠解包与降级路径照样完成了全部实验 |
| 「把解包工具放 `/tmp` 就行」 | 本机遇到过会话中途 `/tmp` 被清空；放 `$HOME` 下更稳 |
| 「先重启恢复业务，回头再分析」 | 现场与证据一起消失，难复现的问题可能再也等不到第二次 |

## 决策练习

**场景**：线上一个 Java 服务报「偶尔卡顿，一次几百毫秒」。你被允许在生产机上做**只读**操作。手头没有 PMU、没有 root、没有 APM，最细的监控粒度是 1 分钟。

**选项**：

- **A. 挂 `strace -f -T -p <服务主进程>` 抓 10 分钟，希望能抓到那几次卡顿。**
- **B. 先取一份一次性快照（`vmstat`、`/proc/pressure/*`、`ss -s`、`iostat -x`、`/proc/<pid>/{status,sched,io,wchan}` 随时间的变化），把「1 分钟粒度的大盘」和「秒级现场」对齐，再决定下一次卡顿出现时抓什么。**
- **C. 直接申请重启服务，看卡顿是否消失。**

**为什么选 B**：1 分钟粒度的监控看不见几百毫秒的尖刺（子笔记 01 的「间歇尖刺」形态），所以要先用**低成本、可持续**的手段记录秒级现场，并且在卡顿发生时能立刻对照。`/proc/<pid>/sched` 的 `se.wait_sum` 与 `/proc/pressure/*` 的 `total` 单调增长，可以把「几百毫秒的卡顿」定位到「等 CPU」还是「等 IO」；这也是原设计里唯一能在生产机上持续跑的方案。

**为什么不选 A**：`strace -f` 是 L2 手段，实测约 80 倍减速，挂 10 分钟会让一个「偶尔卡顿」的 Java 服务变成「一直很慢」，而且 `-f` 会跟着所有线程。即便真抓住了，代价也可能是不可接受的。

**为什么不选 C**：重启会毁掉现场，而且这类问题的复现周期可能是几小时到几天；用重启「验证」相当于把问题推到下一个不确定的时间点。

## 要点自测

> [!question]- `strace` 的代价到底有多大？怎么把它用在生产上？
> - 本机实测：同一份 2 万次系统调用的 workload，直接跑 28～29 ms，`strace -c -f` 后 2317～2342 ms，约 80 倍；被记录的 40570 次调用，均摊约 60 µs/次。
> - 生产用法：限定时间（`timeout`）、限定范围（`-e trace=` 只看关心的调用）、先 `-c` 汇总再 `-T` 明细、只挂已经定位到的那一个进程、优先避开业务高峰。
> - **第一反应不要是什么**：不要 `strace -f -p` 一挂就说「我去看一会儿」。

> [!question]- 采样有哪些固定盲区？各自怎么补？
> - **亚窗口脉冲**：间隔要小于尖刺宽度，或改看设备层聚合（本机 `pidstat -d 1` 漏掉整个 `dd`）。
> - **首屏历史平均**：`top` 首屏、`ps` 的 `%CPU` 都是历史平均，要用带窗口的采样命令。
> - **不在 CPU 上的时间**：`perf record` 采不到；用 `/proc/<pid>/wchan`、`sched`，或（有权限时）`perf sched`/`offcputime`。
> - **被聚合掉的长尾**：用分位数与直方图，并注明窗口与算法口径。

> [!question]- 本机有哪些工具/能力是不可用的？各自的替代方案是什么？
> - 硬件 PMU：`cycles`/`instructions` 为 `<not supported>`，`perf record -e cycles` 采到 0 个样本 → 用 `task-clock`/`context-switches`/`page-faults` 等软件事件与采样。
> - tracefs：`perf sched record` 报 `No permissions to read .../sched/sched_switch` → 用 `/proc/<pid>/wchan`、`sched`、`pidstat -w`。
> - eBPF：`kernel.unprivileged_bpf_disabled=2` → 用 `/proc` 证据链 + 采样 + 应用指标。
> - 缺共享库：`ldd | grep "not found"` 逐个 `apt-get download` + `dpkg-deb -x` 补齐（`fio` 补了 12 个以上，`stress-ng` 补了 4 个）。
> - **第一反应不要是什么**：不要在工具不可用时就宣布「没法查」——降级路径能回答八成问题，只是精度低一档。

> [!question]- 为什么「先取证再动手」比「先恢复业务」更重要？什么情况下例外？
> - 性能故障的现场有时间窗：进程重启、服务重启、参数变更都会让计数器归零，难以复现的问题可能再也等不到第二次。
> - 证据缺失会导致根因判断错误，同样的故障会再发一次，而且下次更贵。
> - **例外**：影响面还在扩大、且不需要现场就能确定止损动作时（例如明确的容量打满），可以先止损再补证据——但要**同时**记录时间、动作和当时的指标。
> - **第一反应不要是什么**：不要把「重启」当默认的第一步。
