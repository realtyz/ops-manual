## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **观测一定会改变被测对象，问题只是改变多少。**
>   - 证据：同一份「2 万次系统调用」的 workload，直接跑 **50～51 ms**，套上 `strace -c -f` 后 **2254～2474 ms**，约 **45～48 倍**；被记录的调用 **40540 次**，均摊约 55 µs/次。
> - **采样有四个固定盲区：亚窗口脉冲、工具首屏的短窗口、不在 CPU 上的时间、被聚合掉的长尾。**
>   - 证据：写 1000 MiB 的 `dd`（`oflag=direct`）只花了 **0.196 秒**，1 秒间隔的 `pidstat -d` **这次恰好抓到了**（`bash` 1013861.39 kB_wr/s、`iodelay` 0）——它落在哪个采样窗口完全取决于时序，所以「没看到」永远不能当作「没有」。
> - **本机的 `perf` 边界和旧环境不一样：设备节点齐全、计数器读不出来、裸命令直接报错。**
>   - 证据：`/sys/bus/event_source/devices/` 下有 `cpu_core`/`cpu_atom`/`msr`/`kprobe`/`uprobe` 等；但 `perf stat -e cycles,instructions` 全部 `<not supported>`（VMware 未透传 PMU 计数器）；**裸 `perf stat` 报 `Invalid event (cpu_core/TOPDOWN.SLOTS/) in per-thread mode, enable system wide with '-a'` 后 `exit=255`，加 `-a` 仍失败**（`sys_perf_event_open() syscall returned with 22`）。
> - **off-CPU 在本机是能做的：`perf sched` 用 root 实测可用。**
>   - 证据：`perf sched record -o sched.data -- sleep 3` 采到 **35573 个样本**、写出 4.028 MB，`perf sched latency` 给出「每个任务被调度出去的时长与最大延迟」表、`perf sched timehist` 给出 `wait time`/`sch delay`/`run time` 三列；`bpftrace` 的 `kprobe:schedule` + `kretprobe:schedule` 也能直接按进程统计 off-CPU 纳秒数（子笔记 13）。
> - **降级路径的第一层永远是 `/proc` + 低开销采样 + 应用自己的指标。**
>   - 怎么验证：只用 `vmstat`、`/proc/<pid>/{status,sched,io,wchan}`、`ss -s`、`nstat` 和日志，也能把「在算还是等、哪个进程、等什么」说到八成准确。

## 1. 观测者效应：三种改变被测对象的方式

### 1.1 时间扰动：每次事件都停下来等你

`strace` 是最典型的例子：它让内核在每次系统调用时停下来，把参数与返回值交给 `strace`，再由 `strace` 恢复进程。

```bash
t0=$(date +%s%N); python3 sys20k.py; t1=$(date +%s%N); echo "baseline $(( (t1-t0)/1000000 )) ms"
t0=$(date +%s%N); strace -c -f python3 sys20k.py; t1=$(date +%s%N); echo "strace $(( (t1-t0)/1000000 )) ms"
strace -c -f python3 sys20k.py 2>&1 | tail -1
```

```text
baseline 50 ms
strace 2254 ms
100.00    0.394055           9     40540        70 total
```

三次重复：基线 50/51/51 ms，`strace` 2254/2280/2474 ms。被记录的调用一共 **40540 次**（2 万个 `getpid` + 2 万个 `newfstatat`，其余是解释器启动开销），每次拦截的代价约 **55 µs** —— 对 4 万次调用就是 2.2 秒。

> [!warning] 减速倍数与基线一起变
> 旧环境（WSL2 上的 24 核实验机）的同一份 workload 是「基线 28～29 ms → `strace` 2317～2342 ms」，比值约 80 倍。本机的基线是 **50～51 ms**（同 workload 的空跑时间接近翻倍）、`strace` 是 **2254～2474 ms**，比值掉到 **45～48 倍**。**结论：`strace` 的绝对代价（每次拦截约 55 µs）是稳定的，但「多少倍」高度依赖被测程序本身的基线——引用倍数时必须把基线和 workload 一起写出来。**

**推论**：`strace` 只适合「短时间 + 小范围」。真正有用的用法是先 `-c` 汇总、限定 `-e trace=` 只看几个调用、加 `timeout` 限时，并且优先挂到**已经定位到的一两个进程**上。

### 1.2 资源占用：观测本身消耗 CPU、内存与 IO

- `perf record -F 99` 每秒产生 99 次采样中断，每次要保存调用栈；`-g` 加调用栈时代价更高（本机 `-g` 采 5 秒写出 0.059 MB、2964 行 `perf script`）。
- `tcpdump` 要把报文从内核复制到用户态再写盘；本机实测限时限量抓 12 个包时 `0 packets dropped by kernel`，但在万兆链路上未加限制的抓包会直接吃掉可观的 CPU 与磁盘带宽。
- 高频 `pidstat`/`iostat` 在几十个进程 / 十几块盘上也会累积；本机实测 `pidstat -d 1` 的输出里就出现了 `iostat` 自己（4.00 kB_wr/s）——**采样工具会把自己写进证据里**。

### 1.3 行为改变：主动注入会永久改变现象

`tc netem`、`fio`、`stress-ng` 不是观测，是**制造现象**。本机用 **root + `ip netns`** 做（非 root 的 `unshare -U -r -n` 在本机被 AppArmor 拒绝）：

```bash
ip netns add lab10net
ip netns exec lab10net ip link set lo up
ip netns exec lab10net tc qdisc add dev lo root netem delay 50ms
ip netns exec lab10net ping -c 3 -q 127.0.0.1 | tail -1
```

```text
rtt min/avg/max/mdev = 100.131/100.238/100.375/0.101 ms
```

注入的 50 ms 单向延迟会一直生效，直到你 `tc qdisc del`。所以这类操作必须满足三个条件：**在隔离环境（命名空间/独立机器）、有明确上限、跑完清理并复核**。绝不能在生产机上「顺手试一下」。

> [!warning] 非 root 的 userns 绕行在本机不成立
> 旧环境用 `unshare -U -r -n` 就能拿到一个「有 `CAP_NET_ADMIN` 的隔离网络」。本机 `kernel.apparmor_restrict_unprivileged_userns=1`，`realtyz` 跑 `unshare -U -r -n` 得 `unshare: write failed /proc/self/uid_map: Operation not permitted`（`exit=1`），`unshare -n` 得 `unshare: unshare failed: Operation not permitted`（`exit=1`）。**正确做法是用 root 直接做**：`ip netns add` / `ip netns exec` 实测完全正常（`root_unshare_exit=0`）。

## 2. 采样偏差：四个固定盲区

### 2.1 盲区一：亚窗口脉冲

如果采样间隔是 1 秒，任何短于 1 秒的尖刺都可能整个落在两次采样之间。

本机实证：用 `dd if=/dev/zero of=pulse.bin bs=1M count=1000 oflag=direct` 写 1000 MiB（`direct`，约 0.2 秒完成）时同时跑 `pidstat -d 1 2`：

```text
1048576000 bytes (1.0 GB, 1000 MiB) copied, 0.195634 s, 5.4 GB/s

Average:      UID       PID   kB_rd/s   kB_wr/s kB_ccwr/s iodelay  Command
Average:        0     46854      0.00 509452.74      0.00       0  bash
```

**这一轮 `pidstat -d` 抓到了**（一个窗口里 `bash` 报 1013861.39 kB_wr/s，`iodelay` 为 0）。它抓到不是因为它够密，而是因为**时序凑巧**：脉冲只有 0.196 秒，而采样窗口是 1 秒。同一份笔记上一轮做相似测试时，1 秒采样就整个漏掉了 `dd`。**结论：看到「进程层没 IO」不等于「没有 IO」**——脉冲型问题要在设备层（`iostat -x` 的 1 秒窗口能覆盖到）或更密的采样、或 `/proc/<pid>/io` 的累计值差分里看。

### 2.2 盲区二：工具首屏是「很短的一段窗口」

`top` 第一次输出里的 CPU 百分比**不是**「自开机以来」的平均。本机实测：自旋进程启动 1 秒后跑 `top -b -n1`，首屏给出 `%Cpu(s): 26.2 us`，第二屏 `25.3 us`——两者一致，而机器已经开了 87 分钟，如果真是开机均值就该接近 0。**这说明它算的是一两秒的差分。**

同理，`ps` 的 `%CPU` 是**进程生命周期内**的平均，不是瞬时值：

```text
$ ps -o pid,stat,pcpu,psr,comm -p 45062
    PID STAT %CPU PSR COMMAND
  45062 R     100   2 python3
```

这里的 `100` 之所以看起来像瞬时值，是因为进程才跑了 10 秒、全程满载。一个跑了 10 小时、只在最近 1 分钟变热的进程，`ps` 的 `%CPU` 会被历史稀释。

### 2.3 盲区三：不在 CPU 上的时间

`perf record` 是**基于采样**的：只有当线程在 CPU 上运行时才可能被采到。一个卡在锁上、卡在 IO 上、卡在调度队列里的线程，在 `perf` 的火焰图里可能完全看不到——这就是 off-CPU 分析存在的理由。

补这个盲区的手段（本机**已实测可用**）：

| 手段 | 需要什么 | 看什么 | 本机实测 |
| --- | --- | --- | --- |
| `perf sched record` + `perf sched latency` | root（或可读 tracefs） | 每个进程被调度出去的时长与最大延迟 | ✅ **采到 35573 个样本**、`perf sched latency` 给出按 `Avg delay`/`Max delay` 排序的表 |
| `perf sched timehist` | 同上 | 逐步的 `wait time`/`sch delay`/`run time` | ✅ 有真实输出（`perf[48499]`、`migration/0[18]` 等行） |
| `bpftrace` off-CPU 脚本 | root + `CAP_BPF` | 按进程统计 off-CPU 纳秒数 | ✅ `kprobe:schedule` + `kretprobe:schedule` 得到 `@offcpu[kworker/3:1H]: 2559457116` 等 |
| `/proc/<pid>/wchan` + `sched` | 无需权限 | **当前**阻塞在哪个函数、累计等待时间 | ✅ `hrtimer_nanosleep`、`nr_switches: 1` |

> [!warning] 旧环境「`perf sched` 被 tracefs 权限拒绝」不适用于本机
> 旧笔记记录的是 `Error: No permissions to read /sys/kernel/tracing//events/sched/sched_switch`。**本机以 root 跑 `perf sched record` 直接成功**（写出 `/tmp/10-lab/sched.data`，4.028 MB、35573 个样本）；因为本机的 `perf_event_paranoid=4` 只限制**非 root**，root 不受限。这条从「未实测」正式升级为实测，降级路径从「唯一选择」变成「没有 root 时的备选」。

数据是一手的，而且足够回答「在等什么」：

```text
$ cat /proc/<pid>/wchan
hrtimer_nanosleep
$ grep -E "^(State|voluntary|nonvoluntary)" /proc/<pid>/status
State:  S (sleeping)
voluntary_ctxt_switches:        1
nonvoluntary_ctxt_switches:     0
```

`/proc/<pid>/stack`（内核栈）需要 ptrace 权限：本机 **root 读普通进程与内核线程都成功**（`hrtimer_nanosleep+0xa2/0x170 …`、`kthreadd+0x194/0x1b0`），**`realtyz` 读同一进程得 `cat: /proc/49112/stack: Permission denied`**。

### 2.4 盲区四：被聚合掉的长尾

这一点在子笔记 01 已展开：平均值会把 1% 的极慢请求摊平，**中位数也会**。补它的方法是**分位数 + 直方图**，而不是「再多取几个平均值」。注意分位数本身也有窗口与算法口径，跨窗口比较前先对齐口径（阶段 9 有专门一节）。

本机的一个干净例子：同核竞争加到 15 个竞争者时，延迟探针的 `p50` 一直是 **8.06 ms**（看不出问题），而 `max` 从 8.36 ms 涨到 **40.87 ms**。**只看中位数会得出「竞争没有影响」的错误结论。**

## 3. 工具不可用的四种典型，以及怎么绕过去

### 3.1 有 PMU 设备节点，但读不出计数器

PMU（Performance Monitoring Unit，性能监控单元）是 CPU 上做硬件性能计数的部件。**本机的边界比「虚拟化环境不给 PMU」更微妙**：

```bash
ls /sys/bus/event_source/devices/          # 验证：设备节点在不在
perf stat -e cycles,instructions,cache-misses,branches -- true   # 验证：能不能读
perf stat -e cpu_core/cycles/,cpu_core/instructions/ -- true     # 验证：显式指定混合架构 PMU
```

```text
breakpoint  cpu_atom  cpu_core  kprobe  msr  power  software  tracepoint  uprobe

   <not supported>      cycles
   <not supported>      instructions
   <not supported>      cache-misses
   <not supported>      branches

   <not supported>      cpu_core/cycles/
   <not supported>      cpu_core/instructions/
```

`/proc/cpuinfo` 里有 `arch_perfmon` 标志、`cpu_core` 的 `type=4 cpus=0-3`、`cpu_atom` 的 `cpus=`（空），但**计数器一律读不出来**——根因是 **VMware 没有把 PMU 计数器透传给 guest**，而不是「内核不支持 perf」或「没有 PMU 硬件」。写结论时要把这条因果说清楚。

更隐蔽的一层：**裸 `perf stat` 在本机根本跑不动**。

```text
$ perf stat -- true
Error:
Invalid event (cpu_core/TOPDOWN.SLOTS/) in per-thread mode, enable system wide with '-a'.
exit=255
$ perf stat -a -- sleep 1
Error:
The sys_perf_event_open() syscall returned with 22 (Invalid argument) for event (cpu_core/TOPDOWN.SLOTS/).
exit=255
```

**必须显式给事件列表**（`-e task-clock,context-switches,page-faults` 这类软件事件正常）。

还有一层「不会报错」的陷阱：`perf record -e cycles` 会老老实实写一个数据文件出来。

```text
$ perf record -e cycles -o c.data -- true
[ perf record: Captured and wrote 0.013 MB /tmp/10-lab/c.data (2 samples) ]
```

**本机写出了 2 个样本**（旧环境是 0 个、`perf report` 报 `no samples!`），但 `perf stat -e cycles` 依然是 `<not supported>`。所以判据不能是「文件写出来了」，也不能是「`perf report` 有没有报错」，而是**先看 `perf stat -e <event>` 有没有 `<not supported>`**。

**绕过去**：改用软件事件与采样——`perf stat -e task-clock,context-switches,page-faults`、`perf record -F 99` 仍然可用（本机实测 `perf report` 能定位到热点符号：`99.80% spin [.] main`、`0.20% [kernel.kallsyms] [k] handle_softirqs`）。想从「热点函数」继续走到「指令级」或「缓存未命中」，就必须换到能透传 PMU 的物理机。

### 3.2 没有权限做内核观测

本机的权限边界（全部实测）：

```text
$ perf sched record -o sched.data -- sleep 3        # root：成功，35573 samples
$ runuser -u realtyz -- perf stat -e cycles -- true  # 非 root：失败
Error:
Access to performance monitoring and observability operations is limited.
perf_event_paranoid setting is 4:
  >= 2: Disallow kernel profiling
$ cat /proc/sys/kernel/dmesg_restrict
1
$ runuser -u realtyz -- dmesg
dmesg: read kernel buffer failed: Operation not permitted
$ runuser -u realtyz -- unshare -U -r -n ip -brief addr
unshare: write failed /proc/self/uid_map: Operation not permitted        # exit=1
```

**绕过去**：用 root。本机 root 下 `perf sched`、`bpftrace`、`blktrace`、`tcpdump`、`iotop`、`ip netns`、`dmesg` 全部实测可用。只有在**必须**用非 root 身份时，才退到 `/proc/<pid>/sched` 的 `nr_switches`/`se.wait_sum`、`pidstat -w`、`pidstat -d`。

### 3.3 eBPF：参数禁用的是「非特权」BPF，不是 BPF

eBPF（extended Berkeley Packet Filter，扩展的伯克利包过滤器）把观测程序挂进内核执行，开销比 `strace` 低得多；配套的 BTF（BPF Type Format）描述内核数据结构。

本机 `kernel.unprivileged_bpf_disabled=2`（2 表示**永久禁止非特权 BPF**），所以非 root 用不了 `bpftrace`/`bcc`；但 **root 完全可用**——本机实测三类脚本都出数：`tracepoint:syscalls:sys_enter_openat` 按进程计数（`@[cat]: 816`、`@[bash]: 210`）、`kprobe:schedule`+`kretprobe:schedule` 统计 off-CPU、`tracepoint:sched:*` 做运行队列延迟直方图。

本机**没有** `bcc` 工具集（`/usr/share/bcc/tools` 不存在），但 `biolatency`/`runqlat`/`offcputime` 这类脚本的语义都可以用 `bpftrace` 现写等价版本（子笔记 13 给出可复制脚本与实测输出）。

**绕过去**：eBPF 能做的事里，约八成可以用「`/proc` 证据链 + 采样类工具 + 应用埋点」拼出来（子笔记 08 给出对应表）。eBPF 真正的不可替代之处是**低开销的全量观测**（例如「每个进程的每一次 `open`」）——本机在 root 下可以直接用它，非 root 才需要降级。

### 3.4 缺的是「分析脚本」，不是「工具本体」

旧环境的典型阻塞是「下载的二进制缺共享库」（`fio: error while loading shared libraries: libaio.so.1t64`）。**本机不存在这个问题**：`fio`、`stress-ng`、`strace`、`perf`、`bpftrace`、`blktrace`、`iotop` 全是 apt 包，依赖齐全。

本机真正缺的是**第三方分析脚本**：

```text
$ ls /usr/share/doc/flamegraph
ls: cannot access '/usr/share/doc/flamegraph': No such file or directory
$ ls /usr/share/bcc/tools
ls: cannot access '/usr/share/bcc/tools': No such file or directory
```

`perl` 在（`/usr/bin/perl`），但 `stackcollapse-perf.pl` / `flamegraph.pl` 找不到。**绕过去**：采样与前两步都能自己做——`perf record -F 99 -g` 出栈、用自写脚本把 `perf script` 的输出折叠成「栈;栈;栈 计数」的格式（本机实测把 3558 行 `perf script` 折成 4 条唯一栈：`_start+0x25;__libc_start_main+0x8b;[unknown];main+0xf` 318 次、`main+0x1a` 187 次、`main+0x13` 87 次、`main+0x8` 1 次）。**只有画 SVG 那一步需要官方脚本**，按本章并行协作纪律不装包，如实标「未实测」。

## 4. 降级阶梯：目标 → 有工具 → 没工具

排障方案要能「降级执行」。把目标拆开，每一层都准备两个版本：

| 我要回答 | 有工具时 | 没工具时（只靠 `/proc` + 采样 + 日志） |
| --- | --- | --- |
| 是算还是等？ | `perf stat` 看 user/sys 比例 | `vmstat` 的 `us/sy/wa`、`cat /proc/<pid>/stat` 的 utime/stime |
| 哪个函数在烧 CPU？ | `perf record -F 99 -g` + 火焰图 | 语言自带的 profiler、日志里的阶段耗时、二分注释法 |
| 哪个系统调用多/慢？ | `strace -c` / `-T` | `/proc/<pid>/syscall`（当前调用）、`/proc/<pid>/io`（真实读写量） |
| 在等什么？ | `perf sched` / `bpftrace` off-CPU（本机 root 可用） | `/proc/<pid>/wchan`、`State: D`、`/proc/<pid>/sched` 的等待时间 |
| 哪个线程？ | `pidstat -u -t`、`perf top -t` | `top -H -p <pid>`、`ps -L -p <pid>`、`/proc/<pid>/task/*/stat` |
| 谁的 IO？ | `blktrace` / `bpftrace`（本机 root 可用） | `iostat -x`（设备层）+ `pidstat -d`（进程层）+ `/proc/<pid>/io` |
| 丢包在哪一跳？ | `tcpdump` + 抓包分析（本机 root 可用） | `nstat`、`/proc/net/softnet_stat`、`ss -ti`、`ip -s link` |
| 内存花在哪？ | `heaptrack` / 语言层 profiler | `/proc/<pid>/smaps_rollup`、`pmap -x`、`/proc/<pid>/status` 的趋势 |

这张表的核心意思是：**降级路径不是「查不了」，而是「精度低一档、需要更依赖推理与对照」**。本机的实际处境更接近左列——降级的需要主要来自「不能用 root」和「硬件不存在」，而不是「工具没装」。

## 5. 三条取证纪律

1. **先取证，再动手。** 重启、杀进程、改参数都会毁掉现场。救火动作与排查动作要分开记录。
   - 具体做法：准备一个一次性取证脚本（子笔记 04 给出完整脚本与实测输出），故障时先跑它，再考虑任何变更。
2. **记录命令与输出。** 用 `script -f session.log` 全量留档，或 `命令 | tee` 保存关键证据；记录时间与时区（`date -Is`）。
   - 本机时区是 `Etc/UTC (UTC, +0000)`，且 `System clock synchronized: no`（`NTP service: active`）——**跨系统对齐时间前先确认这一点**（阶段 9 讲过时钟与格式基线）。
3. **最小影响优先。** 先用 `-c`/`-s` 汇总再用明细；先对单个进程再对全体；先限时（`timeout 10 strace ...`）再考虑长时间观测；故障中不做高风险变更。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 「先挂 `strace -f -p` 慢慢看」 | 实测约 45～48 倍减速；2.2 秒的 `strace` 时间还会干扰你正在测的现象 |
| 「`strace` 大概慢几十倍，记住 80 倍就行」 | 倍数随基线变：本机基线 50 ms、旧环境 28 ms，倍数从 80 掉到 45～48。**要记住的是「每次拦截约 55 µs」，不是倍数** |
| 「`perf` 能看到所有慢的地方」 | `perf` 只采在 CPU 上的时间；等锁、等 IO 的时间要靠 off-CPU 手段（本机 `perf sched`/`bpftrace` 都能做） |
| 「本机没 PMU 所以 `perf` 用不了」 | 设备节点 `cpu_core`/`cpu_atom`/`msr` 都在、`arch_perfmon` 标志也在，只是 **VMware 没透传计数器**；软件事件与采样完全可用 |
| 「`perf stat` 敲下去就能用」 | 裸 `perf stat` 与 `perf stat -a` 在本机都直接报错退出（`exit=255`），**必须显式 `-e <事件>`** |
| 「`perf record -e cycles` 没报错就是采到了」 | 本机写出了 2 个样本，而 `perf stat -e cycles` 仍是 `<not supported>`；先看 `perf stat` |
| 「1 秒采样没看到 IO，就不是 IO 问题」 | 本机 1000 MiB 的 `dd` 只持续 0.196 秒；这次采样抓到了，下次可能整个漏掉——**是时序问题，不是能力问题** |
| 「`ps` 的 `%CPU` 是实时值」 | 它是进程生命周期内的平均，会被历史稀释 |
| 「`unshare -U -r -n` 是通用的无 root 隔离手段」 | 本机 AppArmor 禁非特权 userns，`realtyz` 直接 `Operation not permitted`；**用 root + `ip netns`** |
| 「观测工具不影响业务」 | 采样有开销、抓包有开销、注入会永久改变现象 |
| 「工具没装就是查不了」 | 本机工具全装；真正的边界是权限（非 root 用不了 perf/bpftrace/blktrace/tcpdump）与硬件（无 PMU 透传、无物理多队列网卡） |
| 「先重启恢复业务，回头再分析」 | 现场与证据一起消失，难复现的问题可能再也等不到第二次 |

## 决策练习

**场景**：线上一个 Java 服务报「偶尔卡顿，一次几百毫秒」。你被允许在生产机上做**只读**操作。你**不是** root，最细的监控粒度是 1 分钟。

**选项**：

- **A. 挂 `strace -f -T -p <服务主进程>` 抓 10 分钟，希望能抓到那几次卡顿。**
- **B. 先取一份一次性快照（`vmstat`、`/proc/pressure/*`、`ss -s`、`iostat -x`、`/proc/<pid>/{status,sched,io,wchan}` 随时间的变化），把「1 分钟粒度的大盘」和「秒级现场」对齐，再决定下一次卡顿出现时抓什么。**
- **C. 直接申请重启服务，看卡顿是否消失。**

**为什么选 B**：1 分钟粒度的监控看不见几百毫秒的尖刺（子笔记 01 的「间歇尖刺」形态），所以要先用**低成本、可持续**的手段记录秒级现场，并且在卡顿发生时能立刻对照。`/proc/<pid>/sched` 的 `se.wait_sum` 与 `/proc/pressure/*` 的 `total` 单调增长，可以把「几百毫秒的卡顿」定位到「等 CPU」还是「等 IO」；这也是原设计里唯一能在生产机上持续跑的方案。

**为什么不选 A**：`strace -f` 是 L2 手段，实测约 45～48 倍减速，挂 10 分钟会让一个「偶尔卡顿」的 Java 服务变成「一直很慢」，而且 `-f` 会跟着所有线程。即便真抓住了，代价也可能是不可接受的。

**为什么不选 C**：重启会毁掉现场，而且这类问题的复现周期可能是几小时到几天；用重启「验证」相当于把问题推到下一个不确定的时间点。

## 要点自测

> [!question]- `strace` 的代价到底有多大？怎么把它用在生产上？
> - 本机实测：同一份 2 万次系统调用的 workload，直接跑 50～51 ms，`strace -c -f` 后 2254～2474 ms，约 45～48 倍；被记录的 40540 次调用，均摊约 **55 µs/次**。
> - 「倍数」随 workload 基线变化（旧环境 28 ms 基线 → 80 倍），所以引用时要把基线与 workload 一起写。
> - 生产用法：限定时间（`timeout`）、限定范围（`-e trace=` 只看关心的调用）、先 `-c` 汇总再 `-T` 明细、只挂已经定位到的那一个进程、优先避开业务高峰。
> - **第一反应不要是什么**：不要 `strace -f -p` 一挂就说「我去看一会儿」。

> [!question]- 采样有哪些固定盲区？各自怎么补？
> - **亚窗口脉冲**：间隔要小于尖刺宽度，或改看设备层聚合（本机 `dd` 只跑 0.196 秒，抓到与否取决于时序）。
> - **首屏短窗口**：`top` 首屏是一两秒差分、`ps` 的 `%CPU` 是进程生命周期平均，两者都不能当长窗口证据；要用带明确窗口的采样命令。
> - **不在 CPU 上的时间**：`perf record` 采不到；用 `/proc/<pid>/wchan`、`sched`，或 root 下用 `perf sched`/`bpftrace` off-CPU（本机已实测）。
> - **被聚合掉的长尾**：用分位数与直方图，并注明窗口与算法口径（本机 `p50` 8.06 ms 不变而 `max` 40.87 ms 的例子）。

> [!question]- 本机有哪些工具/能力是不可用的？各自的替代方案是什么？
> - 硬件 PMU 计数器：`cycles`/`instructions`/`cache-misses`/`branches` 全为 `<not supported>`（VMware 未透传）→ 用 `task-clock`/`context-switches`/`page-faults` 等软件事件与 `perf record -F 99` 采样。
> - 裸 `perf stat`：本机直接报错退出 → **必须显式 `-e <事件列表>`**。
> - 非 root 的内核观测：`perf`(`paranoid=4`)、`dmesg`(`dmesg_restrict=1`)、`bpftrace`、`blktrace`、`tcpdump`、非特权 userns 全被拒 → **用 root**。
> - FlameGraph / bcc 脚本：未安装 → 采样与折叠栈自己做，SVG 绘制标「未实测」。
> - **第一反应不要是什么**：不要在工具不可用时就宣布「没法查」——降级路径能回答八成问题，只是精度低一档。

> [!question]- 为什么「先取证再动手」比「先恢复业务」更重要？什么情况下例外？
> - 性能故障的现场有时间窗：进程重启、服务重启、参数变更都会让计数器归零，难以复现的问题可能再也等不到第二次。
> - 证据缺失会导致根因判断错误，同样的故障会再发一次，而且下次更贵。
> - **例外**：影响面还在扩大、且不需要现场就能确定止损动作时（例如明确的容量打满），可以先止损再补证据——但要**同时**记录时间、动作和当时的指标。
> - **第一反应不要是什么**：不要把「重启」当默认的第一步。
