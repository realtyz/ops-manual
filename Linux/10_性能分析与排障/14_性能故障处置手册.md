## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **处置顺序永远是：只读先于写入、应用层先于内核层、单机先于集群、限流先于重启。**
>   - 怎么验证：每一步都写下「预期效果、验收指标、回滚方式」三句；写不全就不执行。
> - **先取证，再动手。**
>   - 证据：一次性取证脚本在本机产出 3474 字节，覆盖身份/负载/每进程 CPU/PSI/内存/套接字/软中断/内核日志。
> - **整机指标正常不等于没有问题。**
>   - 证据：单核打满时整机 `%usr` 4.17%、`load` 0.12；锁竞争时自愿切换 37,962 次/秒而 CPU 空。
> - **「偶发失败」优先怀疑资源上限（端口 / 句柄 / cgroup 配额），而不是网络抖动。**
>   - 证据：3000 条短连接在 0.104 秒后产生 3002 个 TIME_WAIT；第 10236 个 fd 报 `EMFILE`；`CPUQuota=20%` 时 `nr_throttled` 占满全部周期。
> - **验收要「指标 + 业务 + 观察窗口」三件套。**
>   - 怎么验证：指标回到基线、业务侧验收通过、明确长度的观察窗口内不复发。

## 1. 负载高但 CPU 空闲

> [!tip] 第一反应不要是「加 CPU」
> 先确认负载是否真的高、CPU 是否真的闲，再区分「D 状态堆积」「被虚拟化偷走」「大量短任务/频繁唤醒」三类。

```bash
cat /proc/loadavg; nproc; uptime
vmstat 1 5                          # 验证：r（等 CPU）/ b（D 状态）/ si / so / cs
mpstat -P ALL 1 3                   # 验证：%idle / %iowait / %steal 的每核分布
ps -eo stat,pid,etime,wchan:20,args | awk '$1 ~ /D/'   # 验证：哪些进程处于 D
cat /proc/<pid>/wchan               # 验证：在等什么（网络存储 / 块设备 / 锁）
mount | grep -E "nfs|cifs|fuse"     # 验证：是否挂了网络存储
```

**判据与处置**：

| 结果 | 结论 | 处置 |
| --- | --- | --- |
| `b > 0` 且 `wa` 高 | IO / 挂载 / 网络存储阻塞 | 恢复后端存储；必要时 `umount -f`（先取证） |
| `%steal` 高 | 被虚拟化偷走 | 宿主侧问题：提工单 / 换规格 / 迁移 |
| `r` 高但 `id` 也不低、`cs` 极高 | 大量短任务 / 过度唤醒 | 看锁与唤醒源（`pidstat -w`、限时 `strace -c`） |

## 2. 整机 CPU 不高但延迟高

> [!tip] 第一反应不要是「整机才 4%，不是 CPU 问题」
> 24 核上一个核打满就是 4.17%。

```bash
mpstat -P ALL 1 3                        # 验证：找 100% 的单核
pidstat -u -t -p <pid> 1 3               # 验证：落到线程
top -b -n1 -w 200 -H -p <pid>            # 验证：线程名与状态
taskset -cp <pid>                        # 验证：绑核
grep -E "wait_sum|nr_switches" /proc/<pid>/sched   # 验证：等 CPU 的累计时间
```

**实测指纹**：整机 `%usr` 4.17%、`load` 0.12、目标核 100%、线程 `%CPU` 100.50%、亲和性 `2`。

**处置**：把热点与延迟敏感进程分离（`taskset` / cgroup `cpuset`）；给热点加副本；或对热点限流。**不要**直接扩容——单线程热点在副本内部可能依然存在。

## 3. CPU 高：先分五支

```bash
mpstat -P ALL 1 3                  # 验证：先看是 us / sy / soft / wa / st 哪一支
pidstat -u -t 1 3                  # 验证：落到进程/线程
strace -c -f -p <pid>              # 验证：sy 高时看哪个调用最多（限时！）
perf record -F 99 -p <pid> -- sleep 10; perf report   # 验证：us 高时看热点函数
nstat -az; cat /proc/net/softnet_stat                 # 验证：soft 高时看网络侧
iostat -x 1 3                      # 验证：wa 高时看 IO 侧
```

| 分支 | 处置方向 |
| --- | --- |
| `us` | 优化热点函数/算法、扩副本、限流 |
| `sy` | 减少系统调用、批量 IO、定位锁竞争；**先定位再调 `sysctl`** |
| soft（软中断） | 多队列 / RPS / 网卡 offload；`softnet_stat` 的 dropped |
| `wa` | IO 层优化；注意 `wa` 高而 `iostat` 干净时要查网络存储 |
| `st` | 宿主侧超卖，机器内无解 |

## 4. 内存问题

> [!tip] 第一反应不要是「`free` 少了就是内存不够」，也不要用 `drop_caches` 消除现象

```bash
free -m | head -2
grep -E "^(MemTotal|MemAvailable|SwapTotal|SwapFree|Dirty|Writeback)" /proc/meminfo
grep -H . /proc/pressure/memory                        # 验证：真正的压力信号
vmstat 1 5                                             # 验证：si / so
grep -E "pgscan_direct|pgsteal_direct" /proc/vmstat     # 验证：是否在同步回收
dmesg -T | grep -iE "oom|killed process"                # 验证：OOM 现场
ps -eo pid,rss,vsz,pmem,args --sort=-rss | head
grep -E "^(Rss|Pss|Anonymous|Private_Dirty)" /proc/<pid>/smaps_rollup
cat /sys/kernel/mm/transparent_hugepage/enabled
```

**顺序**：确认是不是真的有压力（`MemAvailable` + PSI）→ 是不是被杀过（`dmesg` / cgroup `memory.events`）→ 谁占的（RSS/PSS）→ 是泄漏还是缓存/GC（趋势）。

**实测参照**：分配并触碰 3 GiB 后 `MemAvailable` 15217 → 12138 MiB，PSI 全 0，`VmRSS` 3082 MiB —— **用掉了内存但没有压力**。

## 5. IO 慢：从设备到文件

> [!tip] 第一反应不要是「`%util` 没满就不是磁盘问题」

```bash
iostat -x 1 3                                  # 验证：await / aqu-sz / %util / 请求规模
pidstat -d 1 3                                 # 验证：哪个进程、iodelay
lsof -p <pid> | head                           # 验证：打开的文件
cat /proc/<pid>/io                             # 验证：read_bytes/write_bytes 是否真在读写
mount | grep -E "nfs|cifs"                     # 验证：网络存储
```

**判据**：

| 组合 | 结论 |
| --- | --- |
| `await` 高 + `aqu-sz` 高 | 真的在排队（用 `aqu-sz ≈ 到达率 × await` 交叉验证） |
| `await` 高 + `aqu-sz` 低 | 单请求慢（介质 / 远程存储） |
| `%util` 高但 `await` 低 | 设备忙但速度快，未必是问题 |
| `iodelay` 为 0 而写入量很大 | 写在缓冲里完成，不在这一层阻塞 |

**先决定「是不是 IO 问题」，再决定「谁的 IO」。** 实测参照：深队列窗口 `w/s=2439`、`w_await=54.72 ms`、`aqu-sz=133.47`、`%util=75.20%`；回写突发窗口 `%util=14.40%` 而 `w_await=6.85 ms`。

## 6. 网络慢 / 丢包 / 连接堆积

> [!tip] 第一反应不要是「一上来就抓包」

```bash
ss -s; ss -lnt                                   # 验证：连接分布与监听队列
ss -ti | head -40                                # 验证：rtt / minrtt / retrans / cwnd / app_limited
nstat -az | grep -E "Retrans|Timeouts|Overflow|Drop"
awk '{s+=$2} END{print "softnet dropped:", s}' /proc/net/softnet_stat
ip -s link
```

**判据**：

| 计数器 | 结论 |
| --- | --- |
| `TcpExtListenOverflows` 增长 | accept 队列溢出 → **应用来不及 `accept()`** |
| `TcpRetransSegs / TcpOutSegs` 升高 | 链路或对端丢包 |
| `softnet dropped` 增长 | 收包侧 CPU 不够 / 软中断没分散 |
| `app_limited` 出现 | **瓶颈在应用，不在网络** |

## 7. 进程卡死 / D 状态

```bash
ps -eo pid,ppid,stat,wchan:24,etime,args | awk '$3 ~ /D/'
cat /proc/<pid>/wchan
ls -l /proc/<pid>/task/*/stat
mount | grep -E "nfs|cifs|fuse"
dmesg -T | tail -30                              # 验证：块设备/文件系统报错
```

> [!warning] 处置纪律
> D 状态进程 `kill -9` **无效**（信号要等进程回到用户态才处理）。先恢复它等待的资源（网络存储服务端、块设备、锁），必要时 `umount -f` 或重启整机——**并且先取证**。

## 8. 句柄 / 连接 / 端口耗尽

```bash
ulimit -n; grep -i "open files" /proc/<pid>/limits
ls /proc/<pid>/fd | wc -l
lsof -p <pid> | awk '{print $5}' | sort | uniq -c | sort -rn | head
ss -s; ss -tan state time-wait | wc -l
cat /proc/sys/net/ipv4/ip_local_port_range
```

**实测模型**：

| 项 | 实测 |
| --- | --- |
| 端口范围 | 32768–60999，共 **28232** 个 |
| 短连接上限（同一目标 IP+端口） | 28232 / 60 ≈ **470 条/秒** |
| 实测 | 3000 条短连接 0.104 秒内建完，TIME_WAIT 立即 3002 |
| 句柄 | `ulimit -n=10240` 时第 **10236** 个 fd 报 `[Errno 24]` |

**处置**：长连接/连接池、扩端口范围与缩短 TIME_WAIT 占用、修 fd 泄漏、必要时调 `LimitNOFILE`。两者都表现为**偶发失败**，不是持续失败。

## 9. 容器 / 服务被限流

```bash
cat /proc/<pid>/cgroup
cat /sys/fs/cgroup/<path>/cpu.max                  # 验证：配额
cat /sys/fs/cgroup/<path>/cpu.stat                 # 验证：nr_throttled / throttled_usec
systemd-cgtop -m -1 | head -20
systemctl show <unit> -p CPUQuotaPerSecUSec -p MemoryMax -p OOMPolicy
```

**判据**：`nr_throttled` 持续增长 + 容器内 CPU 不高 + 延迟周期性抖动 = 配额限流。实测：`CPUQuota=20%` 时 `nr_periods` 21→51、`nr_throttled` 21→51、吞吐只剩 18.65%。

**处置**：调整 `CPUQuota`；**不要在容器里加线程**——先在宿主侧确认配额是不是瓶颈。

## 10. 容器 / 服务被 OOM

```bash
cat /sys/fs/cgroup/<path>/memory.max; cat /sys/fs/cgroup/<path>/memory.peak
cat /sys/fs/cgroup/<path>/memory.events            # 验证：oom / oom_kill 计数
dmesg -T | grep -E "oom-kill|Memory cgroup out of memory"
```

**判据**：`memory.events` 的 `oom_kill` 增长、`memory.peak` 顶到 `memory.max`、内核日志 `constraint=CONSTRAINT_MEMCG`。实测：512 MiB 上限下申请 1 GiB，得到 `max 35 / oom 1 / oom_kill 1`、`memory.peak = 536870912`、`oom_score_adj:200`。

**注意**：systemd 默认 `OOMPolicy=stop`，cgroup OOM 之后整个 unit 会被停掉——现场可能直接消失。

## 11. 吞吐低但资源都不忙

```bash
ss -ti | grep -c app_limited        # 验证：连接是否「无数据可发」
mpstat -P ALL 1 3
cat /proc/pressure/*
```

**判据**：资源全正常但吞吐上不去、`app_limited` 出现 → 方向是应用内部串行点（锁、GC、线程池、单线程处理链）或下游依赖延迟。

**处置**：应用层 profiling、依赖延迟排查。**不要**继续加资源。

## 12. 事后复盘：昨晚 3 点发生了什么

```bash
ls /var/log/sysstat/                     # 验证：先确认有数据（本机根本不存在）
sar -u -s 03:00:00 -e 04:00:00           # 验证：CPU 历史
sar -b -s 03:00:00 -e 04:00:00           # 验证：IO 历史
sar -n DEV -s 03:00:00 -e 04:00:00       # 验证：网络历史
journalctl --since "03:00" --until "04:00" -p warning
```

**顺序**：确认历史数据存在 → 确认保留天数够 → 把指标拐点与变更记录、备份窗口、外部事件对齐 → 得出结论并更新基线卡。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 「先重启恢复业务」 | 现场消失、大概率复发（第 7、10、11 节都强调先取证） |
| 「一边限流一边扩容」 | 两个变量同时改，无法归因 |
| 「指标正常就是正常」 | 六类故障发生在整机指标正常时 |
| 「`%util` 没满，磁盘没问题」 | 实测 `%util=75.20%` 时 `aqu-sz=133.47` |
| 「偶发失败是网络抖动」 | 端口与句柄上限都表现为偶发失败 |
| 「D 状态进程 `kill -9` 就好」 | 信号要等进程回到用户态，实际无效 |
| 「容器里 `top` 不高就没事」 | 限流与 OOM 记在宿主侧 cgroup |
| 「扩容了一定快」 | 单核热点/锁竞争/同步落盘场景下无效 |
| 「验收就是重启后业务恢复」 | 需要「指标 + 业务 + 观察窗口」三件套 |

## 决策练习

**场景**：凌晨 2 点被叫醒，告警显示「订单服务错误率 8%」。你登机后看到：整机 CPU 4%，内存 PSI 0，`iostat` 的 `%util` 20%，`ss -s` 显示 `timewait 28000`。同事建议「先重启服务，把 TIME_WAIT 清掉」。

**选项**：

- **A. 重启服务，让 TIME_WAIT 清零。**
- **B. 先记录 `ss -s`、`ss -tan state time-wait | wc -l`、`ip_local_port_range` 与失败报错，判断是不是端口耗尽；如果是，用连接池/长连接或临时扩大端口范围止损，并把「为什么短连接暴涨」作为根因继续查。**
- **C. 直接调大 `net.ipv4.ip_local_port_range` 并打开 `tcp_tw_reuse`。**

**为什么选 B**：`timewait 28000` 已经吃掉本机临时端口范围（28232 个）的**绝大部分（约 99%）**，而 `%util`/PSI/CPU 都很干净——这正是第 8 节的指纹。先取证（数量、范围、错误类型），再选代价最低的止损（连接池/长连接优于调内核参数），同时继续追「为什么短连接暴涨」这个根因。

**为什么不选 A**：重启服务会清掉 TIME_WAIT，但 TIME_WAIT 是**客户端/调用方**的状态，重启服务端往往清不掉它；而且重启毁现场、掩盖根因。

**为什么不选 C**：改 `sysctl` 是不可回滚的高风险动作（`tcp_tw_reuse` 有语义边界，可能影响 NAT 场景），而且在根因未明时改动内核参数属于「用有风险的改动换时间」。正确顺序是先止损（连接池/长连接），再评估是否需要调参。

## 要点自测

> [!question]- 处置顺序的四条原则是什么？
> - 只读先于写入、应用层先于内核层、单机先于集群、限流先于重启。
> - 每个动作都要有「预期效果 + 验收指标 + 回滚方式」。
> - **第一反应不要是什么**：不要先重启、不要先改内核参数、不要一边限流一边扩容。

> [!question]- 哪几类现象「整机指标正常」也会发生？各自的判据是什么？
> - 单核打满（`mpstat -P ALL` 单核 100%）、锁竞争（自愿切换极高、CPU 空）、D 状态（`b > 0`、`wchan`）、同步落盘（`await` 高而 `%util` 低）、端口/句柄耗尽（TIME_WAIT / fd 数）、cgroup 限流（`nr_throttled`）。

> [!question]- 「偶发失败」怎么在 5 分钟内区分端口耗尽与句柄耗尽？
> - `ss -s` 与 `ss -tan state time-wait | wc -l`：timewait 是否接近端口数 ÷ 60 的量级。
> - `ulimit -n`、`/proc/<pid>/limits`、`ls /proc/<pid>/fd | wc -l`：fd 数是否贴近软限。
> - 两者都与并发正相关、都是间歇性失败。

> [!question]- 怎么证明「已经修好了」？
> - 指标回到基线（同一组 p99 / 错误率 / 吞吐）+ 业务验收通过 + 明确长度的观察窗口内不复发。
> - 恢复后立刻再取一份正常态基线。
> - **第一反应不要是什么**：不要把「重启后好了」当结论。
