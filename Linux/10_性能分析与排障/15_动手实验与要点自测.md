## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **十三个实验里，十二个可以在本机直接做（root 可用、工具全装）。**
>   - 证据：`sysstat`（12.6.1-2）、`strace`（6.8）、`perf`（6.8.12）、`fio`（3.36）、`stress-ng`（0.17.06）、`bpftrace`（v0.20.2）、`blktrace`（2.0.0）、`tcpdump`（4.99.4）、`iotop`、`smartctl`（7.4）、`numactl` 全部从系统包直接运行，**不需要 `apt-get download` + `dpkg-deb -x`**；网络注入用 **root + `ip netns`**；cgroup 实验用**系统级** `systemd-run`。
> - **每个实验都要有明确上限与清理复核。**
>   - 怎么验证：每个实验块都写了「上限 / 耗时 / 回滚」，跑完执行 `pgrep`、`ss -lntup`、`systemctl list-units "lab10*"`、`ip netns list`、`losetup -a`、`ls -d /tmp/10-*` 六项复核。
> - **先做只读的实验（1、2 的一部分），再做注入类实验（3～12）。**
>   - 理由：只读实验可以随时在生产机复做，注入类必须在可快照实验机上做。
> - **实验的产出不是「命令跑通了」，而是「观测指纹」与「判读结论」。**
>   - 证据：单核超卖的指纹是「整机 25.04% vs 单核 100.00%、吞吐 −79.0%、`max` 8.36→40.87 ms 而 `p50` 不动」，而不是「我跑了一个自旋进程」。
> - **未实测的部分要照实登记。**
>   - 怎么验证：演练记录的最后一段永远有「未实测 + 原因 + 补做方式」；本机示例见本篇开头的实测状态块——**「能做但没做」与「环境做不了」必须分开写**。

## 3. 实验详解

> [!example]- 实验 1：一次性取证快照（只读，生产机也可以做）
> **怎么做**：把子笔记 04 的脚本存成 `snapshot.sh`，执行 `./snapshot.sh /tmp/10-snap/run1`。
> **预期**：输出一份约 8 KB 的文本，包含身份、`vmstat`、进程排序、PSI、内存、套接字、`nstat`、softnet、`iostat -x`、内核日志。
> **风险**：低（L0/L1 只读；`dmesg` 在本机需 root，非 root 会退到 `journalctl -k`）。
> **耗时**：约 15 秒（`vmstat 1 5` 占 5 秒、`iostat -x 1 3` 占 3 秒）。
> **回滚**：无需回滚；记得把快照文件归档到事故单。

> [!example]- 实验 2：单核打满（整机不忙，延迟照样炸）
> **怎么做**：`taskset -c 2 python3 -c 'while True: pass' &`，同时跑 `mpstat -P ALL 1 3`、`uptime`、`vmstat 1 3`、`pidstat -u -t -p <pid> 1 2`、`top -b -n1 -H -p <pid>`、`taskset -cp <pid>`。
> **预期**：`Average: all 25.04 … 74.96` 与 `Average: 2 100.00 … 0.00`；`load average: 0.34, 0.27, 0.19`；线程 `%CPU` 100.00%、`CPU=2`、亲和性 `2`、状态 `R`。
> **风险**：低（一个核，18 秒）。
> **耗时**：约 1 分钟。
> **回滚**：脚本主动 `kill` 并复核；跑完 `pgrep -af "while True"` 应无输出（本机实测末行 `no residual spin`）。

> [!example]- 实验 3：单核超卖对吞吐与延迟的影响
> **怎么做**：① 测一个「2 秒计数循环」在 CPU 3 上独占时的迭代次数；② 起 1 个、再起 4 个同核自旋，重测；③ 用 300 次 `sleep(8 ms)` 的唤醒延迟探针在 0 / 1 / 5 / 15 个竞争者下各测一次。
> **预期**：26,473,519 → 12,461,811（−52.9%）→ 5,564,871 次（**−79.0%**）；延迟 `p50` 8.13 → 8.06 → 8.06 → 8.06 ms（**中位数几乎不动**），`max` 8.36 → 10.82 → 16.58 → **40.87 ms**；期间整机 `%usr` 始终约 **25%**。
> **风险**：低（全部挤在一个核上，每组 ≤ 6 秒，最多 16 个进程）。
> **耗时**：约 3 分钟。
> **回滚**：全部用脚本内的 `kill`；结束复核无自旋进程。

> [!example]- 实验 4：`us` vs `sy` 与上下文切换
> **怎么做**：① `perf stat -e task-clock,context-switches,page-faults,cycles -- timeout 6 taskset -c 2 python3 -c 'while True: pass'`；② 对「2 万次 `getpid` + `stat`」的脚本重复一次；③ 用线程版 socket ping-pong 跑 9 秒，同时 `pidstat -w -p <pid> 1 3` 并读 `/proc/<pid>/status`。
> **预期**：纯计算 `5.994 s user / 0.007 s sys`（`sys` 占 0.12%）、`33` 次上下文切换、`cycles` 为 `<not supported>`；系统调用负载 `0.0387 s user / 0.0122 s sys`（`sys` 占 **24.0%**）；ping-pong 自愿切换 **40,343.67 次/秒**、非自愿 **16.67 次/秒**。
> **风险**：低。
> **耗时**：约 3 分钟。
> **回滚**：`timeout` 到期自动结束。

> [!example]- 实验 5：内存压力与 PSI
> **怎么做**：先记基线（`free -m`、`grep -H . /proc/pressure/memory`），再在后台分配并逐页触碰 3 GiB，存活期间读 `free`、PSI、`/proc/<pid>/status`、`smaps_rollup`、`/proc/vmstat`。
> **预期**：`MemAvailable` 7224 → **4145 MiB**；PSI `avg10/avg60/avg300` 全程 **0.00**，但 `some` 的 `total` 从 298 涨到 **9695 µs**、`full` 从 208 涨到 **9477 µs**；`VmRSS` **3082 MiB**、`VmSwap` **0**、`pgscan_direct` **0**、`pgscan_kswapd` 127429。
> **风险**：中（3 GiB = 本机总内存的 38%）。必须设上限，不要在有生产负载的机器上做，**也不要再往上加**。
> **耗时**：约 2 分钟。
> **回滚**：进程退出后内存立即释放；复核 `free -m` 回到基线（本机实测回到 available 7216 MiB）。

> [!example]- 实验 6：IO 三指标与 `fsync` 的代价
> **怎么做**：① `iostat -x 1 12 > iostat.out &` 同时 `dd if=/dev/zero of=io.bin bs=1M count=2048 conv=fdatasync`，比对 `iostat.out` 里的 `w/s`/`w_await`/`aqu-sz`/`%util`；② 用 Python 测 200 次 4 KiB 写 + `fsync` 与 200 次纯缓冲写的百分位。
> **预期**：`dd` 约 **2494 MiB/s**（`dd` 自身按 10³ 报 2.6 GB/s）；回写突发窗口 `w/s=477`、`w_await=1.14 ms`、`aqu-sz=0.54`、`%util=42.50%`；`fsync` `p50=0.3614 ms` vs 缓冲写 `p50=0.0019 ms`（约 **190 倍**）。
> **风险**：中（写 2 GiB）。只在可丢弃目录做，跑完删除文件。
> **耗时**：约 3 分钟。
> **回滚**：删除 `io.bin`；确认 `df` 回到基线（本机复核 47G / 8.5G / 37G / 19%）。

> [!example]- 实验 7：`fio` 四象限基线
> **怎么做**：在可丢弃目录依次跑顺序写/读（`bs=1M, psync, iodepth=1, direct=1`）与随机写/读（`bs=4k, libaio, iodepth=32, direct=1`），每次 `--runtime=15 --time_based`，记录 `IOPS`/`BW` 与 `clat` 百分位。
> **预期**：顺序写 **1495 MiB/s**、顺序读 **1708 MiB/s**、随机写 **27.3k IOPS / 107 MiB/s**、随机读 **47.5k IOPS / 185 MiB/s**；`clat` p50 分别 635 / 562 / 1090 / 619 µs。
> **风险**：高（持续写）。必须在实验机、必须带 `--runtime` 与 `--size`。
> **耗时**：约 2 分钟（4 × 15 秒 + 文件准备）。
> **回滚**：删除测试文件；确认磁盘空间回落。
> **注意**：**随机象限必须用 `--ioengine=libaio`**，否则默认的 `psync` 会忽略 `--iodepth`（本机同参数下 `psync` 只有 11.7k IOPS）。

> [!example]- 实验 8：网络延迟/丢包注入与 `ss -ti`
> **怎么做**：`ip netns add lab10net` → `ip netns exec lab10net ip link set lo up` → 加 `tc qdisc add dev lo root netem delay 50ms`，跑 `ping` 与一个 TCP ping-pong 脚本，再用 `ss -ti state established` 看字段；换成 `netem loss 20%` 并跑 200 个包；最后 `ip netns del`。
> **预期**：RTT ≈ **100.238 ms**；`ss -ti` 显示 `rtt:100.293/0.055`、`minrtt:100.123`、`cwnd:10`、`app_limited`、`unacked:1`、`snd_wnd:65536`；丢包实测 **36.5%**（理论 `1 − 0.8² = 36%`）。
> **风险**：低（完全在 netns 内，不影响宿主网络）。
> **耗时**：约 2 分钟。
> **回滚**：`ip netns del`；确认宿主 `tc qdisc show dev lo` 是 `noqueue`。

> [!example]- 实验 9：句柄与端口耗尽
> **怎么做**：① 用 Python 反复 `open("/dev/null")` 直到抛 `OSError`；② 在**独立 netns** 里起一个监听套接字并建立关闭 3000 条连接，然后在 netns 内 `ss -tan state time-wait | wc -l`；③ `ip netns del`。
> **预期**：连续打开 **1021** 个 fd 后报 `[Errno 24] Too many open files`（软限 **1024**）；netns 内 `ss -s` 报 `TCP: 3001 (estab 0, closed 3001, orphaned 0, timewait 2988)`，`wc -l` 得 **2989**；宿主命名空间 `timewait` 全程为 0。
> **风险**：中（消耗句柄与端口）。**必须在 netns 里做**，否则会占用宿主临时端口、影响并行推进的其他实验。
> **耗时**：约 2 分钟。
> **回滚**：进程退出后句柄释放；`ip netns del` 会把 TIME_WAIT 一起带走。

> [!example]- 实验 10：`strace` 的系统调用画像与观察者效应
> **怎么做**：① `strace -c -f python3 <2000 行写日志的脚本>` 看画像；② `strace -T -e trace=openat,write` 看单次耗时；③ 用 `date +%s%N` 对比同一个「2 万次系统调用」脚本在无观测 / 有 `strace` 下的墙钟时间，各跑三次。
> **预期**：画像里 `newfstatat` 占 25.64%、`write` 只占 0.87%（3 次调用）、总调用 517 次；对比脚本里 `newfstatat` 51.97%、`getpid` 47.08%、总调用 **40540** 次；基线 **50～51 ms**、`strace` **2254～2474 ms**（约 **45～48 倍**）。
> **风险**：中（几十倍减速）。只在实验机上做，并限时。
> **耗时**：约 2 分钟。
> **回滚**：无状态；删除产生的数据文件。

> [!example]- 实验 11：`perf` 的可用边界与热点定位
> **怎么做**：① `perf stat -e cycles,instructions,cache-misses,branches -- true` 看硬件事件；② 试裸 `perf stat` 与 `perf stat -a` 看默认事件集；③ `perf stat -e task-clock,context-switches,page-faults,cpu-migrations` 在自旋进程上看软件事件；④ `perf record -F 99` 采样 5 秒后 `perf report --stdio --sort dso,sym`；⑤ `perf record -g` + `perf script` 看调用栈；⑥ `perf sched record` + `perf sched latency`。
> **预期**：硬件事件全部 `<not supported>`；**裸 `perf stat` 与 `perf stat -a` 都报错退出（`exit=255`）**；软件事件正常（`3,000.14 msec task-clock`、`22` 次切换、`211` 次缺页）；`-F 99` 采到 **494** 个样本、热点 `99.80% spin [.] main`；`-g` 给出 `main+0xf → __libc_start_main+0x8b → _start+0x25`；`perf sched record` 采到 **35573** 个样本。
> **风险**：低（采样）。
> **耗时**：约 3 分钟。
> **回滚**：删除 `perf.data`；`perf sched` 的数据文件在 `/tmp` 下，随临时目录一起删。

> [!example]- 实验 12：cgroup 限流与内存 OOM（系统级）
> **怎么做**：① `systemd-run --scope -p CPUQuota=20% --unit=lab10cpu bash quotacpu.sh`，脚本内读自己的 `cpu.max` 与 `cpu.stat`（前后各一次）并跑 2 秒计数循环；② `systemd-run --unit=lab10mem --collect -p MemoryMax=512M -p MemorySwapMax=0 -p OOMPolicy=continue bash memunit.sh`，读 `memory.max`/`memory.peak`/`memory.events` 与 `dmesg`；③ 非 OOM 对照：`MemoryMax=512M` 下只申请 256 MiB 并保持存活。
> **预期**：`cpu.max` = `20000 100000`；`nr_periods` 0→21、`nr_throttled` 0→**20**、`throttled_usec` 0→**1597813 µs**；吞吐 29,823,329 → **5,757,053 次**（**19.30%**）；OOM 侧 `memory.peak` = **536870912**、`memory.events` 出现 `max 46 / oom 1 / oom_kill 1`、内核日志 `constraint=CONSTRAINT_MEMCG`；对照侧 `memory.current=273899520`、`events` 全 0。
> **风险**：中（内存上限与 OOM）。只在实验机做；注意默认 `OOMPolicy=stop` 会让 unit 直接消失（现场读不到）。
> **耗时**：约 3 分钟。
> **回滚**：`--scope` 结束即释放；常驻 unit 用 `systemctl stop` + `reset-failed`；复核 `systemctl list-units "lab10*"` 为 0 行、`/sys/fs/cgroup/system.slice/lab10*` 不存在。

> [!example]- 实验 13：补做清单——哪些已升级、哪些仍缺条件
> **本轮已升级为实测**：`blktrace`（139 个事件 / 7 KiB，`blkparse -s` 给出读写派发与合并统计）、`tcpdump`（12 个包、`0 packets dropped by kernel`）、`bpftrace`（计数 / off-CPU / 延迟直方图三类脚本）、`perf sched` + `off-CPU`（35573 个样本）、`iotop`、`smartctl`（识别 `VMware Virtual S`、`Solid State Device`）、`numactl`（1 个 NUMA 节点）。

## 5. 汇总自测

> [!question]- 用一句话说清这一章的方法论，再说出它的六个站点。
> - 方法论：**先量化影响面，再按资源分层排除，取同时刻证据，最后才动手**；顺序对了，工具差一点也能定位。
> - 六站：① 认领与量化 → ② 算力（CPU 与负载）→ ③ 存储（内存与 IO）→ ④ 传输与等待（网络与阻塞）→ ⑤ 下钻（进程与栈）→ ⑥ 止损与复盘。
> - **第一反应不要是什么**：不要在没量化影响面前就「优化」或重启。

> [!question]- 为什么「整机 CPU 25%」不能排除 CPU 问题？怎么用三步验证？
> - 本机是 **4 核**，一个核打满整机就是 **25.04%**；`load` 也看不到它（本机实测 `load` 0.34）。判断标准是「有没有核贴到 100%」，而不是整机百分比的大小。
> - 三步：`mpstat -P ALL 1 3` 找 100% 的核 → `pidstat -u -t -p <pid> 1 3` 落到线程 → `taskset -cp` 看绑核；补充 `/proc/<tid>/sched` 的 `wait_sum`。
> - 定量影响：同核 4 个竞争者让固定工作量只剩约 21%，`max` 延迟涨 4.9 倍（而 `p50` 不动）。

> [!question]- CPU 高的五个分支怎么判、怎么下钻？
> - `us` → `perf record` 找热点；`sy` → `strace -c` 看调用画像；软中断 → `mpstat %soft` + `/proc/interrupts` + `softnet_stat`；`wa` → `iostat -x`；`st` → 宿主侧超卖。
> - 实测对照：`us` 型 `5.994 s user / 0.007 s sys`（`sys` 占 0.12%），`sy` 型 `0.0387 s user / 0.0122 s sys`（`sys` 占 24.0%）。
> - **不要把 `vmstat` 的 `si` 当软中断**——那是换入，软中断在 `mpstat` 的 `%soft`。

> [!question]- 内存「有压力」和「用得多」怎么区分？
> - 用 `MemAvailable` + `/proc/pressure/memory`，**而且 `avg` 与 `total` 都要读**；`free` 少是 Linux 常态。
> - 实测：分配并触碰 3 GiB 后 `MemAvailable` 少 3079 MiB，而 PSI 的 `avg10` 全程 0.00 —— 只是用掉了；但 `some` 的 `total` 涨了 **9397 µs**，说明不是「零压力」，只是被 10 秒的分母摊平了。
> - 附加：`pgscan_direct` 增长说明在同步回收（direct reclaim），表现为延迟尖刺。本机 `pgscan_direct=0`。

> [!question]- `%util`、`await`、`aqu-sz` 三者为什么可能互不对应？
> - `%util` 回答「忙不忙」，`await` 回答「等多久」，`aqu-sz` 回答「排多长」。
> - 实测两个方向都有：`%util=80.10%` 时 `w_await=6.59 ms`、`aqu-sz=2.14`；而 `%util=98.80%` 时 `w_await=0.09 ms`、`aqu-sz=3.15`。
> - 交叉验证：`324 × 0.00659 = 2.14`，与实测 `aqu-sz` **完全相等**。

> [!question]- 「网络慢」应该按什么顺序排查？`ss -ti` 里哪个字段能洗清网络嫌疑？
> - 顺序：`ss -s`/`ss -lnt` → `nstat`（看**增量**）→ `softnet_stat`/`ip -s link`/`ethtool -S` → `ss -ti` → 最后才抓包。
> - `app_limited`：说明发送受限是因为应用没数据要发 → 瓶颈在应用。
> - 实测：注入 50 ms 单向延迟后 `rtt:100.293/0.055`、`minrtt:100.123`，无注入的 `lo` 是 0.008 ms。

> [!question]- `netem` 配 20% 丢包为什么实测 36.5%？
> - loopback 上请求与应答各经过一次出口：成功率 `0.8 × 0.8 = 0.64`，丢失率 36%。
> - 实测 200 个包丢 36.5%，与理论吻合；10 个包时是 50%（小样本噪声）。
> - 教训：做注入前先算清方向与期望值，并准备足够样本。

> [!question]- 进程处于 D 状态，为什么 `kill -9` 无效？正确顺序是什么？
> - 信号只在进程回到用户态时被处理；D 状态是不可中断睡眠。
> - 顺序：取证（`dmesg`、`ps -o stat,wchan`、`cat /proc/<pid>/stack`、`mount`）→ 恢复它等待的资源 → 必要时 `umount -f`/重启整机。
> - **第一反应不要是什么**：不要反复 `kill -9`，也不要先重启。

> [!question]- `strace`、`perf`、eBPF 各自的代价与前提是什么？
> - `strace`：约 45～48 倍减速（基线 50 ms → 2254～2474 ms，每次拦截约 55 µs），限时限范围使用。
> - `perf`：采样开销小；**裸 `perf stat` 在本机直接报错**，必须显式 `-e`；硬件事件需要 PMU **计数器透传**（本机 `<not supported>`）；`perf sched` 需要 root（**本机实测可用**）。
> - eBPF：`bpftrace` root 下可用（本机 `unprivileged_bpf_disabled=2` 只禁非特权 BPF）；本机没有 bcc 脚本集。
> - 降级路径：`/proc` 证据链 + L1 采样 + 应用日志与指标 + 分位数。

> [!question]- 容器的 CPU 与内存问题为什么必须看宿主侧？各自的证据是什么？
> - 配额、限流计数、内存上限与 OOM 都记在宿主侧 cgroup。
> - CPU：`cpu.stat` 的 `nr_throttled`/`throttled_usec`（实测 `nr_periods` 0→21、`nr_throttled` 0→20、吞吐 19.30%）。
> - 内存：`memory.events` 的 `oom_kill`、`memory.peak` 顶到 `memory.max`（实测 512 MiB 上限、`max 46 / oom 1 / oom_kill 1`、`CONSTRAINT_MEMCG`）。
> - 注意 systemd 默认 `OOMPolicy=stop` 会停掉整个 unit（本机实测现场直接消失），要留现场必须显式 `continue`。

> [!question]- 「偶发失败」类问题怎么量化？
> - 端口：可用端口数 ÷ TIME_WAIT 时长 ≈ 对同一目标端口的短连接上限（28232 / 60 ≈ **470 条/秒**）；实测 3000 条短连接产生 **2988** 个 TIME_WAIT（在 netns 内）。
> - 句柄：`ulimit -n` / `/proc/<pid>/limits` / `ls /proc/<pid>/fd | wc -l`；实测软限 **1024**、连续打开 **1021** 个 fd 后第 1022 次 `open()` 报 `EMFILE`。
> - 判据：间歇性而非持续性、与并发正相关。

> [!question]- 怎么证明「修好了」？六段报告是哪六段？
> - 三件套：指标回到基线 + 业务验收通过 + 观察窗口内无复发。
> - 六段：时间线 / 影响面 / 证据 / 根因 / 止损动作 / 长期改进（含 owner 与期限）。
> - **最容易漏的是「为什么之前的防线没拦住」**——它决定同样的故障会不会再来一次。

> [!question]- 建立一份性能基线卡要包含哪五组数据？为什么容量要按核算？
> - 五组：身份与规模（含 `nproc`、`MemTotal`、swap、磁盘、网卡）/ CPU 与负载（含每核）/ 内存（`MemAvailable` + PSI 的 `avg` 与 `total`）/ IO（`await`、`aqu-sz`、`%util`、`wareq-sz` + `fio` 四象限，**必须记 `ioengine`**）/ 网络（连接分布 + 重传率）。
> - 按核的理由：实测单核 100.00% 时整机 `%usr` 只有 25.04%、`load` 0.34；同核 4 个竞争者只剩约 21% 算力。
> - 容量结论要看「p99 拐点对应的流量」，不是「整机 CPU 到 80% 告警」。

> [!question]- 一次安全的故障演练必须满足哪些条件？你打算怎么复核？
> - 隔离（`ip netns` / 可丢弃目录 / 临时 unit）、明确上限（时长、内存、IO、连接数，且按本机规模定）、跑完清理。
> - 复核六项：无残留进程、无监听端口、无残留 unit、无残留 netns、无残留 loop 设备、无临时目录。
> - 产出：观测指纹 + 判读结论 + 未实测清单（**「能做但没做」与「环境做不了」要分开写**）。

> [!question]- 本机与旧环境相比，最容易被忽略的两处「方向反转」是什么？
> - **`perf sched` / off-CPU**：旧环境被 tracefs 权限拒绝、属「未实测」；**本机 root 下实测可用**（35573 个样本、`perf sched latency` 有输出）。
> - **历史指标**：旧环境 `sysstat` 未安装、`/var/log/sysstat` 不存在；**本机已安装且定时器 active**，`sar -u` 能读出真实历史采样。
> - 另外两处：**网络注入要用 root + `ip netns`**（不能再用 `unshare -U -r -n`）；**cgroup 实验用系统级**（不再是 `systemd-run --user`）。
