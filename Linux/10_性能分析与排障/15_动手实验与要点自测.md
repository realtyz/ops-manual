## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **十三个实验里，九个不需要 root、六个不需要任何安装。**
>   - 证据：本机的 `mpstat`/`pidstat`/`iostat`/`strace`/`perf`/`fio`/`stress-ng` 全部是 `apt-get download` + `dpkg-deb -x` 解包运行；网络注入在 `unshare -U -r -n` 里；cgroup 实验用 `systemd-run --user`。
> - **每个实验都要有明确上限与清理复核。**
>   - 怎么验证：每个实验块都写了「上限 / 耗时 / 回滚」，跑完执行 `pgrep`、`ss -lnt`、`systemctl --user list-units "lab*"` 三项复核。
> - **先做只读的实验（1、2 的一部分），再做注入类实验（3～12）。**
>   - 理由：只读实验可以随时在生产机复做，注入类必须在可快照实验机上做。
> - **实验的产出不是「命令跑通了」，而是「观测指纹」与「判读结论」。**
>   - 证据：单核超卖的指纹是「整机 4.18% vs 单核 100%、吞吐 −76%」，而不是「我跑了一个自旋进程」。
> - **未实测的部分要照实登记。**
>   - 怎么验证：演练记录的最后一段永远有「未实测 + 原因 + 补做方式」。

### 1.2 工具准备（不安装、不需要 root）

```bash
D=$HOME/devtools; mkdir -p $D/pkgs $D/root; cd $D/pkgs
apt-get download sysstat strace stress-ng fio linux-tools-common linux-tools-generic linux-tools-6.8.0-139

```

补依赖的循环（`fio` 与 `stress-ng` 需要）：

```bash
ldd $D/root/usr/bin/fio | grep "not found"          # 验证：逐个列出缺失的库
apt-get download <缺失库对应的包>; dpkg-deb -x <包>.deb $D/root
```

> [!warning] 工具目录不要放 `/tmp`
> 本机在写作过程中遇到过 `/tmp` 下的解包目录消失。稳妥位置是 `$HOME/<name>`（本机用 `$HOME/devtools`）。

### 1.3 三条纪律（每个实验都要遵守）

```bash
timeout 16 taskset -c 2 python3 -c 'while True: pass'      # 上限：写清秒数
pgrep -af "while True: pass|stress-ng|fio"                 # 复核：无残留进程
ss -lnt; systemctl --user list-units "lab*" --all           # 复核：无监听端口 / 无残留 unit
```

## 3. 实验详解

> [!example]- 实验 1：一次性取证快照（只读，生产机也可以做）
> **怎么做**：把子笔记 04 的脚本存成 `snapshot.sh`，执行 `./snapshot.sh /tmp/perf-snap-lab`。
> **预期**：输出一份约 3.4 KB 的文本，包含身份、`vmstat`、进程排序、PSI、内存、套接字、`nstat`、softnet、内核日志。
> **风险**：低（L0/L1 只读）。
> **耗时**：约 15 秒（`vmstat 1 5` 占 5 秒）。
> **回滚**：无需回滚；记得把快照文件归档到事故单。

> [!example]- 实验 2：单核打满（整机不忙，延迟照样炸）
> **怎么做**：`timeout 16 taskset -c 2 python3 -c 'while True: pass' &`，同时跑 `mpstat -P ALL 1 3`、`uptime`、`vmstat 1 2`、`pidstat -u -t -p <pid> 1 2`、`top -b -n1 -H -p <pid>`、`taskset -cp <pid>`。
> **预期**：`Average: all 4.17 … 95.80` 与 `Average: 2 100.00 … 0.00`；`load average` 约 0.12；线程 `%CPU` 约 100.50%、`CPU=2`、亲和性 `2`。
> **风险**：低（一个核，16 秒）。
> **耗时**：约 1 分钟。
> **回滚**：`timeout` 自动结束；跑完 `pgrep -af "while True"` 复核。

> [!example]- 实验 3：单核超卖对吞吐与延迟的影响
> **怎么做**：① 用 `/usr/bin/time` 或 `date +%s%N` 测一个「2 秒计数循环」在 CPU 3 上独占时的迭代次数；② 起 1 个、再起 4 个同核自旋，重测；③ 用 300 次 `sleep(8 ms)` 的唤醒延迟探针在 0 / 1 / 5 个竞争者下各测一次。
> **预期**：2598 万 → 1535 万 → 622 万次（−41% / −76%）；延迟 `p50` 8.13 → 8.05 → 12.00 ms，`max` 8.34 → 8.13 → 25.79 ms；期间整机 `%usr` 始终约 4.18%。
> **风险**：低（最多 5 个核，每组 ≤ 6 秒）。
> **耗时**：约 3 分钟。
> **回滚**：全部用 `timeout`；结束复核无自旋进程。

> [!example]- 实验 4：`us` vs `sy` 与上下文切换
> **怎么做**：① `perf stat -e task-clock,context-switches,page-faults,cycles -- timeout 6 taskset -c 5 python3 -c 'while True: pass'`；② 对「2 万次 `getpid` + `stat`」的脚本重复一次；③ 用线程版 socket ping-pong 跑 6 秒，同时 `pidstat -w -p <pid> 1 2` 并读 `/proc/<pid>/status`。
> **预期**：纯计算 `5.997 s user / 0.004 s sys`、`0` 次上下文切换、`cycles` 为 `<not supported>`；系统调用负载 `0.0151 s user / 0.0113 s sys`（`sys` 占 43%）；ping-pong 自愿切换约 37,962 次/秒、非自愿 0。
> **风险**：低。
> **耗时**：约 3 分钟。
> **回滚**：`timeout` 到期自动结束。

> [!example]- 实验 5：内存压力与 PSI
> **怎么做**：先记基线（`free -m`、`grep -H . /proc/pressure/memory`），再在后台分配并逐页触碰 3 GiB，存活期间读 `free`、PSI、`/proc/<pid>/status`、`smaps_rollup`、`pmap -x`。
> **预期**：`MemAvailable` 15217 → 12138 MiB；PSI `some`/`full` 全程 0；`VmRSS` 3082 MiB、`Rss/Pss/Anonymous` ≈ 3082/3078/3076 MiB。
> **风险**：中（3 GiB 内存）。必须设上限，不要在有生产负载的机器上做。
> **耗时**：约 2 分钟。
> **回滚**：进程退出后内存立即释放；复核 `free -m` 回到基线。

> [!example]- 实验 6：IO 三指标与 `fsync` 的代价
> **怎么做**：① `iostat -x 1 9 > iostat.out &` 同时 `dd if=/dev/zero of=io.bin bs=1M count=2048 conv=fdatasync`，比对 `iostat.out` 里的 `w/s`/`w_await`/`aqu-sz`/`%util`；② 用 Python 测 200 次 4 KiB 写 + `fsync` 与 200 次纯缓冲写的百分位。
> **预期**：`dd` 约 1630 MiB/s（`dd` 自身按 10³ 报 1.7 GB/s）；回写突发窗口 `w/s=555`、`w_await=6.85 ms`、`aqu-sz=3.81`、`%util=14.40%`（`%util` 低但已有等待）；`fsync` `p50≈5.08 ms` vs 缓冲写 `p50≈0.0015 ms`（约 3400 倍）。
> **风险**：中（写 2 GiB）。只在可丢弃目录做，跑完删除文件。
> **耗时**：约 3 分钟。
> **回滚**：删除 `io.bin`；确认 `df` 回到基线。

> [!example]- 实验 7：`fio` 四象限基线
> **怎么做**：在可丢弃目录依次跑顺序写/读（`bs=1M, iodepth=1, direct=1`）与随机写/读（`bs=4k, iodepth=32, direct=1`），每次 `--runtime=15 --time_based`，记录 `IOPS`/`BW` 与 `clat` 百分位。
> **预期**：本机样例 2903 / 2830 MiB/s、17.4k / 12.5k IOPS；`clat` p50 分别 269 / 334 / 51 / 74 µs。
> **风险**：高（持续写）。必须在实验机、必须带 `--runtime` 与 `--size`。
> **耗时**：约 2 分钟（4 × 15 秒 + 文件准备）。
> **回滚**：删除测试文件；确认磁盘空间回落。

> [!example]- 实验 8：网络延迟/丢包注入与 `ss -ti`
> **怎么做**：在 `unshare -U -r -n bash -c "..."` 里 `ip link set lo up`，加 `tc qdisc add dev lo root netem delay 50ms`，跑 `ping` 与一个 TCP ping-pong 脚本，再用 `ss -ti state established` 看字段；换成 `netem loss 20%` 并跑 200 个包。
> **预期**：RTT ≈ 100.16 ms；`ss -ti` 显示 `rtt:100.533/0.406`、`minrtt:100.131`、`cwnd:10`、`app_limited`；丢包实测 35.5%（理论 `1 − 0.8² = 36%`）。
> **风险**：低（完全在命名空间内，不影响宿主网络）。
> **耗时**：约 2 分钟。
> **回滚**：命名空间退出即消失；确认宿主 `ip link show lo` 无 netem qdisc。

> [!example]- 实验 9：句柄与端口耗尽
> **怎么做**：① 用 Python 反复 `open("/dev/null")` 直到抛 `OSError`；② 本地起一个监听套接字并在 0.1 秒内建立并关闭 3000 条连接，然后 `ss -tan state time-wait | wc -l`。
> **预期**：第 10236 个 fd 报 `[Errno 24] Too many open files`；TIME_WAIT 立即涨到 3002。
> **风险**：中（消耗句柄与端口）。跑完等待 TIME_WAIT 自然回收；不要在生产接口上做。
> **耗时**：约 2 分钟。
> **回滚**：进程退出后句柄释放；TIME_WAIT 在 60 秒后自然消失。

> [!example]- 实验 10：`strace` 的系统调用画像与观察者效应
> **怎么做**：① `strace -c -f python3 <2000 行写日志的脚本>` 看画像；② `strace -T -e trace=openat,write` 看单次耗时；③ 用 `date +%s%N` 对比同一个「2 万次系统调用」脚本在无观测/有 `strace` 下的墙钟时间，各跑三次。
> **预期**：画像里 `newfstatat` 占 29.57% 等；基线 28～29 ms，`strace` 2317～2342 ms（约 80 倍），共记录 40570 次调用。
> **风险**：中（约 80 倍减速）。只在实验机上做，并限时。
> **耗时**：约 2 分钟。
> **回滚**：无状态；删除产生的数据文件。

> [!example]- 实验 11：`perf` 的可用边界与热点定位
> **怎么做**：① `perf stat -e cycles,instructions,cache-misses -- true` 看硬件事件；② `perf stat -e task-clock,context-switches,page-faults` 在自旋进程上看软件事件；③ `perf record -F 99` 采样 5 秒后 `perf report --stdio --sort dso,sym`；④ 试 `perf sched record`。
> **预期**：硬件事件显示 `<not supported>`；`perf record -e cycles` 能写出文件但 `perf report` 报 `no samples!`；`-F 99` 采到约 494 个样本，热点 `_PyEval_EvalFrameDefault` 100%；`perf sched record` 报 tracefs 权限错误。
> **风险**：低（采样）。
> **耗时**：约 2 分钟。
> **回滚**：删除 `perf.data`。

> [!example]- 实验 12：cgroup 限流与内存 OOM（无 root 版）
> **怎么做**：① `export XDG_RUNTIME_DIR=/run/user/1000`；② `systemd-run --user --scope -p CPUQuota=20% --unit=labq python3 -c '<2 秒计数循环>'`，同时读该 scope 的 `cpu.max` 与 `cpu.stat`；③ `systemd-run --user --unit=labm6 --collect -p MemoryMax=512M -p MemorySwapMax=0 -p OOMPolicy=continue bash -c "python3 -c '<申请 1 GiB 并触碰>'; sleep 25"`，读 `memory.max`/`memory.peak`/`memory.events` 与 `dmesg`。
> **预期**：`cpu.max` = `20000 100000`；`nr_throttled` 与 `nr_periods` 同步增长（21→51）；吞吐 3179 万 → 593 万次（18.65%）；OOM 侧 `memory.peak` = 536870912、`memory.events` 出现 `max 35 / oom 1 / oom_kill 1`、内核日志 `CONSTRAINT_MEMCG`。
> **风险**：中（内存上限与 OOM）。只在实验机做；注意默认 `OOMPolicy=stop` 会让 unit 直接消失。
> **耗时**：约 3 分钟。
> **回滚**：`systemctl --user stop <unit>`；确认 cgroup 目录已清理。

> [!example]- 实验 13：必须在真机/多机环境补做的部分
> **需要什么条件**：至少一台可快照的物理机或云主机（有 PMU、可 root），以及一个可做配额实验的容器环境和一套可演练的发布系统。
> **补做清单**：硬件 PMU 与 IPC、火焰图、`perf sched`/off-CPU、`bpftrace`/`bcc`、`blktrace`/`biosnoop`、`tcpdump` 抓包分析、真实网卡多队列与 offload、`smartctl` 介质健康、多机摘流量与回滚。
> **产出**：把结果回填到子笔记 06（IO）、07（网络）、08（下钻）、11（cgroup）、13（工具边界），并把本机不适用的结论标注清楚。

## 5. 汇总自测

> [!question]- 用一句话说清这一章的方法论，再说出它的六个站点。
> - 方法论：**先量化影响面，再按资源分层排除，取同时刻证据，最后才动手**；顺序对了，工具差一点也能定位。
> - 六站：① 认领与量化 → ② 算力（CPU 与负载）→ ③ 存储（内存与 IO）→ ④ 传输与等待（网络与阻塞）→ ⑤ 下钻（进程与栈）→ ⑥ 止损与复盘。
> - **第一反应不要是什么**：不要在没量化影响面前就「优化」或重启。

> [!question]- 为什么「整机 CPU 4%」不能排除 CPU 问题？怎么用三步验证？
> - 24 核上一个核打满就是 4.17%；`load` 也看不到它（本机实测 `load` 0.12）。
> - 三步：`mpstat -P ALL 1 3` 找 100% 的核 → `pidstat -u -t -p <pid> 1 3` 落到线程 → `taskset -cp` 看绑核；补充 `/proc/<tid>/sched` 的 `wait_sum`。
> - 定量影响：同核 4 个竞争者让固定工作量只剩 24%，`max` 延迟涨 3.1 倍。

> [!question]- CPU 高的五个分支怎么判、怎么下钻？
> - `us` → `perf record` 找热点；`sy` → `strace -c` 看调用画像；软中断 → `mpstat %soft` + `/proc/interrupts` + `softnet_stat`；`wa` → `iostat -x`；`st` → 宿主侧超卖。
> - 实测对照：`us` 型 `5.997 s user / 0.004 s sys`，`sy` 型 `0.0151 s user / 0.0113 s sys`。
> - **不要把 `vmstat` 的 `si` 当软中断**——那是换入，软中断在 `mpstat` 的 `%soft`。

> [!question]- 内存「有压力」和「用得多」怎么区分？
> - 用 `MemAvailable` + `/proc/pressure/memory`；`free` 少是 Linux 常态。
> - 实测：分配并触碰 3 GiB 后 `MemAvailable` 少 3079 MiB，而 PSI 全 0 —— 只是用掉了。
> - 附加：`pgscan_direct` 增长说明在同步回收（direct reclaim），表现为延迟尖刺。

> [!question]- `%util`、`await`、`aqu-sz` 三者为什么可能互不对应？
> - `%util` 回答「忙不忙」，`await` 回答「等多久」，`aqu-sz` 回答「排多长」。
> - 实测：深队列窗口 `w/s=2439`、`w_await=54.72 ms`、`aqu-sz=133.47`、`%util=75.20%`；回写突发窗口 `%util=14.40%` 却有 `w_await=6.85 ms`。
> - 交叉验证：`2439 × 0.05472 = 133.46` ≈ 实测 `aqu-sz`。

> [!question]- 「网络慢」应该按什么顺序排查？`ss -ti` 里哪一行能洗清网络嫌疑？
> - 顺序：`ss -s`/`ss -lnt` → `nstat` → `softnet_stat`/`ip -s link` → `ss -ti` → 最后才抓包。
> - `app_limited`：说明发送受限是因为应用没数据要发 → 瓶颈在应用。
> - 实测：注入 50 ms 单向延迟后 `rtt:100.533/0.406`、`minrtt:100.131`。

> [!question]- `netem` 配 20% 丢包为什么实测 35.5%？
> - loopback 上请求与应答各经过一次出口：成功率 `0.8 × 0.8 = 0.64`，丢失率 36%。
> - 实测 200 个包丢 35.5%，与理论吻合；10 个包时是 30%（小样本噪声）。
> - 教训：做注入前先算清方向与期望值，并准备足够样本。

> [!question]- 进程处于 D 状态，为什么 `kill -9` 无效？正确顺序是什么？
> - 信号只在进程回到用户态时被处理；D 状态是不可中断睡眠。
> - 顺序：取证（`dmesg`、`ps -o stat,wchan`、`mount`）→ 恢复它等待的资源 → 必要时 `umount -f`/重启整机。
> - **第一反应不要是什么**：不要反复 `kill -9`，也不要先重启。

> [!question]- `strace`、`perf`、eBPF 各自的代价与前提是什么？
> - `strace`：约 80 倍减速，无需特殊权限（附加他人进程需 ptrace），适合短时小范围。
> - `perf`：采样开销小；硬件事件需要 PMU（本机 `<not supported>`）、调用栈需要符号、`perf sched` 需要 tracefs。
> - eBPF：能力最强但需要 root/`CAP_BPF` 与匹配内核（本机 `unprivileged_bpf_disabled=2`）。
> - 降级路径：`/proc` 证据链 + L1 采样 + 应用日志与指标 + 分位数。

> [!question]- 容器的 CPU 与内存问题为什么必须看宿主侧？各自的证据是什么？
> - 配额、限流计数、内存上限与 OOM 都记在宿主侧 cgroup。
> - CPU：`cpu.stat` 的 `nr_throttled`/`throttled_usec`（实测 21→51、吞吐 18.65%）。
> - 内存：`memory.events` 的 `oom_kill`、`memory.peak` 顶到 `memory.max`（实测 512 MiB 上限、`oom_kill 1`、`CONSTRAINT_MEMCG`）。
> - 注意 systemd 默认 `OOMPolicy=stop` 会停掉整个 unit。

> [!question]- 「偶发失败」类问题怎么量化？
> - 端口：可用端口数 ÷ TIME_WAIT 时长 ≈ 对同一目标端口的短连接上限（28232 / 60 ≈ 470 条/秒）；实测 3000 条短连接产生 3002 个 TIME_WAIT。
> - 句柄：`ulimit -n` / `/proc/<pid>/limits` / `ls /proc/<pid>/fd | wc -l`；实测第 10236 个 fd 报 `EMFILE`。
> - 判据：间歇性而非持续性、与并发正相关。

> [!question]- 怎么证明「修好了」？六段报告是哪六段？
> - 三件套：指标回到基线 + 业务验收通过 + 观察窗口内无复发。
> - 六段：时间线 / 影响面 / 证据 / 根因 / 止损动作 / 长期改进（含 owner 与期限）。
> - **最容易漏的是「为什么之前的防线没拦住」**——它决定同样的故障会不会再来一次。

> [!question]- 建立一份性能基线卡要包含哪五组数据？为什么容量要按核算？
> - 五组：身份与规模 / CPU 与负载（含每核）/ 内存（`MemAvailable` + PSI）/ IO（`await`、`aqu-sz`、`%util` + `fio` 四象限）/ 网络（连接分布 + 重传率）。
> - 按核的理由：实测单核 100% 时整机 `%usr` 只有 4.17%、`load` 0.12；同核 4 个竞争者只剩 24% 算力。
> - 容量结论要看「p99 拐点对应的流量」，不是「整机 CPU 到 80% 告警」。

> [!question]- 一次安全的故障演练必须满足哪些条件？你打算怎么复核？
> - 隔离（命名空间 / 可丢弃目录 / 临时 unit）、明确上限（时长、内存、IO、连接数）、跑完清理。
> - 复核三项：无残留进程、无监听端口、无残留 unit / 临时目录。
> - 产出：观测指纹 + 判读结论 + 未实测清单。
