## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **演练的三条纪律：在隔离环境、设明确上限、跑完清理并复核。**
>   - 怎么验证：每份演练记录结尾都有「无残留进程 / 无监听端口 / 无残留 unit 与临时目录 / 无 netns」的复核结果（本机本章的复核输出见第 5 节）。
> - **六类注入都有对应的观测指纹，练过一遍才能在真故障中认出它们。**
>   - 证据：单核超卖（整机 25.04% vs 单核 100.00%、吞吐 −79.0%）、内存 3 GiB（`MemAvailable` −3079 MiB、PSI 平均值为 0 但 `total` 涨了 9397 µs）、深队列 IO（`aqu-sz=3.15`、`w_await=0.09 ms`、`%util=98.80%`）、`netem`（RTT 100.238 ms）、端口耗尽（TIME_WAIT 2988）、句柄耗尽（第 1022 次 `open()` 报 `EMFILE`）。
> - **「工具不可用」在本机换成了权限与硬件，而不是缺包。**
>   - 证据：`blktrace 2.0.0`、`tcpdump 4.99.4`、`bpftrace v0.20.2`、`perf 6.8.12`、`iotop`、`smartctl 7.4`、`numactl`、`ethtool` 全部在 `/usr/bin` 或 `/usr/sbin`；非 root 用不了的只有 `perf`（`paranoid=4`）、`dmesg`（`dmesg_restrict=1`）、`bpftrace`、`blktrace`、`tcpdump`、`iotop`、建 netns。
> - **网络注入在本机必须用 root + `ip netns`。**
>   - 证据：`realtyz` 跑 `unshare -U -r -n` 得 `unshare: write failed /proc/self/uid_map: Operation not permitted`（`exit=1`）；root 跑 `ip netns add` 成功，注入只影响该 netns，宿主的 `lo` 复核为 `qdisc noqueue`。
> - **未实测的部分要如实写下来，并给出补做方式——这本身就是排障经验的一部分。**
>   - 怎么验证：每份记录里「未实测」清单都带「需要什么条件、怎么补做」，而不是一句「没有权限」。

## 1. 演练纪律：三条不能破的边界

| 纪律 | 具体要求 | 违反的后果 |
| --- | --- | --- |
| **隔离** | 网络故障注入放进 **root 建的 `ip netns`**（本机非特权 userns 被禁）；破坏性 IO 写在可丢弃目录；cgroup 类实验用临时 scope/service | 影响真实业务、影响别的同事 |
| **上限** | CPU 负载 ≤ 20 秒；内存 ≤ 4 GiB（**本机总内存只有 7894 MiB，更要克制**）；IO ≤ 2 GiB；连接 ≤ 3000 条；`fio` 必须带 `--runtime`/`--size` | 打满机器、打满磁盘、触发线上告警 |
| **清理与复核** | 结束残留进程、确认无监听端口、清理临时目录与 unit、删除 netns | 污染后续实验、留下常驻资源 |

```bash
pgrep -af "while True: pass|stress-ng|fio"      # 验证：无残留进程
ss -lntup                                        # 验证：无意外监听端口
systemctl list-units "lab10*" --all --no-pager   # 验证：临时 unit 已清理
ip netns list                                    # 验证：自己的 netns 已删除
losetup -a                                       # 验证：没有遗留 loop 设备
ls -d /tmp/10-*                                  # 验证：临时目录已删除
```

## 2. 六类注入：怎么造、看什么、算不算通过

### 2.1 CPU 打满与单核超卖

```bash
taskset -c 2 python3 -c 'while True: pass' &                       # 造：单核热点
mpstat -P ALL 1 3 | grep -E "^Average: +(all|2) "                  # 看：整机 vs 单核
for i in 1 2 3 4; do taskset -c 3 python3 -c 'while True: pass' & done   # 造：同核超卖
```

| 观测指纹 | 实测值 |
| --- | --- |
| 整机 `%usr` | **25.04%**（4 核里的 1 核） |
| 目标核 `%usr` | **100.00%** |
| `load average`（1 分钟） | **0.34**（自旋前 0.28） |
| 吞吐（2 秒计数循环，同核 4 个竞争者） | 26,473,519 → 5,564,871（**−79.0%**） |
| 延迟 `p50`（0 / 1 / 5 / 15 个竞争者） | 8.13 → 8.06 → 8.06 → 8.06 ms（**中位数不动**） |
| 延迟 `max`（同上） | 8.36 → 10.82 → 16.58 → **40.87 ms** |

**验收**：能说出「整机不忙但单核满」的判据链（`mpstat -P ALL` → `pidstat -u -t` → `taskset -cp`），并能解释为什么**只看 `p50` 会漏掉这个竞争**。

### 2.2 内存压力

```bash
free -m | head -2; grep -H . /proc/pressure/memory                 # 基线
python3 -c 'import time
b=bytearray(3*1024*1024*1024)
for i in range(0,len(b),4096): b[i]=1
time.sleep(15)' &                                                  # 造：3 GiB 并逐页触碰
stress-ng --vm 1 --vm-bytes 1G --timeout 8s --metrics-brief        # 造：stress-ng 的内存压力
```

| 观测指纹 | 实测值 |
| --- | --- |
| `MemAvailable` | 7224 MiB → **4145 MiB**（−3079 MiB） |
| PSI memory `avg10`/`avg60`/`avg300` | 0.00 / 0.00 / 0.00（**没有可测出的持续压力**） |
| PSI memory `total` | `some` 298 → **9695 µs**、`full` 208 → **9477 µs**（**有约 9.4 ms 的瞬时压力被摊平**） |
| `VmRSS` / `Rss` / `Pss` / `Anonymous`（kB） | 3156232 / 3156232 / 3151749 / 3149520（约 3082 / 3082 / 3077 / 3076 MiB） |
| `VmSwap` | **0**（没有换页） |
| `pgscan_direct` / `pgscan_kswapd` | 0 / 127429（**没有直接回收**） |

**验收**：能解释「PSI 的 `avg10` 为 0 说明没有持续压力」，同时能说出**只看 `avg` 会漏掉 `total` 的增长**——这两句话缺一不可。

> [!warning] 内存注入的上限要按本机的总内存来定
> 旧环境的总内存约为本机的两倍，做 3 GiB 的触碰很安全。本机只有 **7894 MiB**，3 GiB 已经占了 38%，`MemAvailable` 最低掉到 4145 MiB。**再往上加就有触发整机 OOM 的风险**（会波及并行推进的其他章节）。本机有 swap（4095 MiB），但**不要靠 swap 来兜底**——换页本身就是性能故障。

### 2.3 深队列 IO

```bash
iostat -x 1 15 > iostat.out &                                    # 同时采样
fio --name=deepq --filename=$F --size=1G --rw=randwrite --bs=4k \
    --ioengine=libaio --iodepth=64 --direct=1 --runtime=11 --time_based   # 造：深队列随机写
stress-ng --hdd 2 --hdd-bytes 512M --timeout 9s --metrics-brief           # 造：并发写压力
```

| 观测指纹 | 实测值 |
| --- | --- |
| `w/s` / `wkB/s`（深队列） | 14721 / 58884 → 压力爬升后 35457 / 141828 |
| `w_await` | 0.27 ms → **0.09 ms**（队列变深但单请求更快） |
| `aqu-sz` | 3.92 → **3.15** |
| `%util` | 74.50% → **98.80%** |
| 并发写窗口（`stress-ng --hdd 2`） | `w/s=324`、`w_await=6.59 ms`、`wareq-sz=3781`、`aqu-sz=2.14`、`%util=80.10%` |
| `pidstat -d` | `stress-ng-hdd` 各 524288～786432 kB_wr/s，`iodelay` 为 **0** |

**验收**：能用 `aqu-sz ≈ w/s × w_await` 交叉验证（本机 `324 × 0.00659 = 2.14`，与实测完全相等），并解释为什么 `%util` 不是饱和度——**本机同时给出了两个方向的证据：`%util` 80.10% 时队列 2.14、`%util` 98.80% 时队列 3.15。**

### 2.4 网络延迟与丢包

```bash
ip netns add lab10net                                          # 隔离：root 建 netns
ip netns exec lab10net ip link set lo up
ip netns exec lab10net tc qdisc add dev lo root netem delay 50ms
ip netns exec lab10net ping -c 3 -q 127.0.0.1 | tail -1
ip netns exec lab10net tc qdisc del dev lo root
ip netns exec lab10net tc qdisc add dev lo root netem loss 20%
ip netns exec lab10net ping -c 200 -q -i 0.02 127.0.0.1 | tail -1
ip netns del lab10net
```

| 观测指纹 | 实测值 |
| --- | --- |
| 注入 50 ms 单向延迟后的 RTT | `min/avg/max/mdev = 100.131/100.238/100.375/0.101 ms` |
| `ss -ti` | `rtt:100.293/0.055`、`minrtt:100.123`、`cwnd:10`、`app_limited`、`unacked:1`、`snd_wnd:65536` |
| 无注入的 `lo` 对照 | `rtt min/avg/max/mdev = 0.008/0.024/0.083/0.007 ms`（差四个数量级） |
| 注入 20% 丢包（200 包） | 实测 **36.5%**（`1 − 0.8² = 36%`） |
| 注入 20% 丢包（10 包） | 实测 **50%**（小样本噪声） |
| 宿主侧 | `softnet dropped 0`、`ip -s link lo` 的 errors/dropped 全 0、宿主 `lo` 复核为 `qdisc noqueue` |

**验收**：能解释「为什么配 20% 却丢 36.5%」，也能用 `ss -ti` 的 `app_limited` 把网络问题与应用问题分开。

### 2.5 句柄与端口耗尽

```bash
ulimit -n; cat /proc/sys/net/ipv4/ip_local_port_range
python3 -c 'fds=[]
try:
    for i in range(20000):
        fds.append(open("/dev/null"))
except OSError as e:
    print("opened=%d then failed: [Errno %d] %s"%(len(fds),e.errno,e.strerror))'
ip netns exec lab10port ss -tan state time-wait | wc -l          # 造完短连接后在 netns 内统计
```

| 观测指纹 | 实测值 |
| --- | --- |
| 句柄耗尽 | 连续打开 **1021** 个 fd 后，第 1022 次 `open()` 报 `[Errno 24] Too many open files`（软限 **1024**） |
| 端口范围 | `32768 60999`（28232 个） |
| 3000 条短连接（0.157 秒内，**在独立 netns 里**） | `ss -s` 报 `TCP: 3001 (estab 0, closed 3001, orphaned 0, timewait 2988)`；`ss -tan state time-wait \| wc -l` = **2989** |
| 宿主命名空间 | 全程 `timewait 0`（隔离有效） |
| 短连接 QPS 上限估算 | 28232 / 60 ≈ **470 条/秒**（对同一目标 IP+端口） |

**验收**：能说出「偶发失败」的两种典型原因与各自的量化模型，并能解释**为什么句柄数字必须现场读 `ulimit -n`**（旧环境 10240 → 第 10236 个；本机 1024 → 第 1022 个）。

### 2.6 cgroup 限流与 OOM（系统级）

```bash
systemd-run --scope -p CPUQuota=20% --unit=lab10cpu bash /tmp/10-lab/quotacpu.sh   # 造：CPU 限流
systemd-run --unit=lab10mem --collect -p MemoryMax=512M -p MemorySwapMax=0 \
  -p OOMPolicy=continue bash /tmp/10-lab/memunit.sh                                # 造：内存 OOM
```

| 观测指纹 | 实测值 |
| --- | --- |
| `cpu.max` | `20000 100000`（20%） |
| `cpu.stat` | `nr_periods` 0→21，`nr_throttled` 0→**20**，`throttled_usec` 0→**1597813 µs（1.60 秒）** |
| 吞吐 | 29,823,329 次/2 s → 5,757,053 次/2 s（**19.30%**） |
| `memory.peak` / `memory.max` | 536870912 / 536870912（512 MiB） |
| `memory.events` | `max 46 / oom 1 / oom_kill 1` |
| 内核日志 | `oom-kill:constraint=CONSTRAINT_MEMCG`、`task_memcg=/system.slice/lab10mem.service`、`oom_score_adj:0` |
| 非 OOM 对照（256 MiB / 512 MiB 上限） | `memory.current=273899520`、`memory.peak=274055168`、`memory.events` 全 0 |

**验收**：能在容器内看到「CPU 不高但抖动」时，主动去宿主侧查 `cpu.stat`；知道 `OOMPolicy` 默认 `stop` 会让 unit 直接消失（本机实测默认策略下 6 秒后 unit 已是 `inactive/dead`、cgroup 目录被回收）。

## 4. 未实测清单与补做方式

| 未实测项 | 需要什么条件 | 补做方式 |
| --- | --- | --- |
| 火焰图 SVG 输出 | FlameGraph 项目的 `flamegraph.pl`（`perl` 已具备） | 把本机折叠好的 `栈;栈;栈 计数` 喂给 `flamegraph.pl` 即可；采样与折叠两步已实测 |
| `bcc` 现成脚本（`biosnoop`/`execsnoop`…） | `bpfcc-tools` 包 | 本机用 `bpftrace` 写过等价脚本（第 3.2 节），或装 `bpfcc-tools` 后直接用 |
| 硬件 PMU 与 IPC、缓存未命中 | 一台**透传 PMU 计数器**的物理机或云主机 | `perf stat -e cycles,instructions,cache-misses ./app`；本机 `cpu_core`/`cpu_atom` 节点在但计数器 `<not supported>`（VMware 未透传） |
| 真实网卡多队列 / offload / RPS | 物理网卡 + root | `ethtool -l`/`-L`/`-S`、`mpstat` 看 `%soft` 分布、RPS/RFS 配置；本机 `ethtool -l` 报 `Operation not supported` |
| 生产级摘流量 / 回滚演练 | **至少两台机器** + 负载均衡 + 发布系统 | 在预发环境按灰度流程演练，记录验收指标与回滚耗时；本机只有一台虚拟机 |
| GPU / RDMA / 高速网卡 | 对应硬件 | `nvidia-smi dmon`、`rdma link`、`ibv_devinfo`、`ethtool -S` |
| 真实机械盘的寻道抖动 | 机械盘 | 本机 `smartctl` 报 `Rotation Rate: Solid State Device`（虚拟盘），无论述价值 |
| DNS「超时重试台阶」形状 | 一个可注入延迟或会超时的解析链路 | 本机上游解析器对**任何**名字都立即返回（连 `.invalid` 都被 `search localdomain` 补全并给出合成地址），无法复现固定台阶 |

## 5. 生产动作：演练记录模板（有产出物）

```text
【演练目标】验证「整机不忙但单核打满」的判据链，并记录观测指纹
【环境】Ubuntu 24.04.5 LTS（VMware 虚拟机）/ 内核 6.8.0-139-generic / 4 vCPU / 7894 MiB / root
【隔离方式】CPU 自旋绑核（taskset -c 2）；网络注入放进 root 建的 ip netns；cgroup 实验用系统级 systemd-run
【上限】CPU ≤ 20 s、内存 ≤ 3 GiB（总内存 7894 MiB）、IO ≤ 2 GiB、连接 ≤ 3000
【步骤】1) 记录基线 load 2) 启动单核自旋  3) mpstat -P ALL 1 3  4) pidstat -u -t  5) taskset -cp  6) 结束并复核
【观测指纹】整机 %usr 25.04%；目标核 100.00%；load 0.34；吞吐 −79.0%；p50 8.13→8.06 ms、max 8.36→40.87 ms
【结论】能在 5 分钟内把「整机不忙但慢」定位到单核与线程，并知道「p50 不变」不代表没有问题
【复核】无残留进程 / 无监听端口 / 无临时目录 / 无残留 unit / 无残留 netns（见第 1 节的六条命令）
【未实测】火焰图 SVG、bcc 现成脚本、PMU 微架构、多队列网卡、多机摘流量（原因与补做方式见第 4 节）
```

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 「在测试机上随便跑压力」 | 测试机也在内网、也可能有告警；要隔离、设上限、跑完清理 |
| 「`fio` 不带 `--runtime`」 | 可能跑满整块盘甚至写满分区 |
| 「`fio --iodepth=32` 就够了」 | 默认 `psync` 引擎忽略 `iodepth`；本机同一个 `--iodepth=32`，`psync` 只有 11.7k IOPS、`libaio` 有 27.3k |
| 「内存注入照旧环境做 3 GiB 很安全」 | 旧环境的总内存约为本机的两倍，本机只有 7894 MiB；3 GiB 已占 38%，`MemAvailable` 掉到 4145 MiB，再加就有整机 OOM 风险 |
| 「网络注入用 `unshare -U -r -n`」 | 本机 AppArmor 禁非特权 userns，`realtyz` 直接 `Operation not permitted`；**用 root + `ip netns`** |
| 「端口耗尽实验在宿主机上做也一样」 | 会占用宿主临时端口、影响并行推进的其他实验；本机是在独立 netns 里做的，宿主 `timewait` 全程为 0 |
| 「故障注入不清理」 | 残留进程/端口/netns 会污染后续实验，甚至被误认为真实故障；`ip netns list` 里要能分清哪些是自己的 |
| 「工具没装就不测了」 | 本机工具全装；真正的边界是权限（非 root 用不了 perf/bpftrace/blktrace/tcpdump）与硬件（无 PMU 透传、单队列网卡、只有一台机器） |
| 「没有 PMU / 多队列网卡就不写结论」 | 未实测的部分要如实写，并给出补做方式；不写才是真的缺口 |
| 「预案只在纸面上」 | 没跑过的预案不算预案；演练要把「观测指纹」也记下来 |
| 「演练等于压测」 | 演练的目的是练「判读路径」，不是刷高负载数字 |

## 决策练习

**场景**：你被要求在一个**共享的预发环境**（有真实流量、有告警、有同事在用）上验证一套「服务变慢」的排障流程。你**没有 root**，机器不允许安装任何软件。

**选项**：

- **A. 直接在预发环境跑 `stress-ng --cpu 4 --vm 2 --hdd 2` 造一次综合负载，练全套流程。**
- **B. 先做只读部分（五组基线 + 一次性取证），再用限定上限、限定范围的方式做注入：单核自旋绑到指定核、内存与 IO 上限设为 1 GiB；网络注入因为需要 root 而改用只读计数器（`ss -ti`/`nstat`）代替；每步前后各取一组证据，最后复核清理。**
- **C. 放弃演练，改成讲解一遍流程。**

**为什么选 B**：演练的目标是练判读路径，不是刷负载。复用「隔离 + 上限 + 清理」三条纪律，能在共享环境里做出有效练习：单核自旋只占一个核（整机才 25%），1 GiB 的内存/IO 上限对预发环境影响可控，而且每一步都有证据可对照。**注意本机有 root 时网络注入可以做（`ip netns`），但题目约束了「没有 root」——此时正确的降级是「不做注入，只用只读计数器判定」**，这正是子笔记 03 讲的降级路径。

**为什么不选 A**：4 核满载加 2 路 IO 会直接影响共享预发环境的其它用户与告警，属于「在别人的生产环境里做破坏性实验」；而且本机只有 4 核、7894 MiB，这个组合已经接近打满。

**为什么不选 C**：没有跑过的预案不算预案——演练真正的产出是「观测指纹」和「手速」，不是文档。而且 B 的每一部分都不需要 root，也不需要安装软件。

## 要点自测

> [!question]- 一次安全的故障演练必须满足哪三个条件？
> - 隔离（root 建的 `ip netns` / 可丢弃目录 / 临时 unit）、明确上限（时长、内存、IO、连接数，且按本机规模定）、跑完清理并复核（无残留进程/端口/临时目录/unit/netns）。
> - 还应当**先记录观测指纹再结束**，否则练完什么也没留下。

> [!question]- 六类注入各自的「观测指纹」是什么？
> - CPU：整机 `%usr` 25.04% 对目标核 100.00%；吞吐 −79.0%；`p50` 不动而 `max` 8.36 → 40.87 ms。
> - 内存：`MemAvailable` 少 3079 MiB、PSI `avg10` 全 0 但 `total` 涨了约 9.4 ms。
> - IO：`aqu-sz` 2.14～3.92、`w_await` 0.09～6.59 ms、`%util` 74～99%。
> - 网络：RTT 100.238 ms、`ss -ti` 的 `minrtt:100.123`、丢包 36.5%（理论 36%）。
> - 句柄/端口：连续打开 1021 个 fd 后第 1022 次 `open()` 报 `EMFILE`；3000 条短连接后 `timewait 2988`。
> - cgroup：`nr_throttled/nr_periods = 20/21`、`throttled_usec` 1.60 s、吞吐 19.30%；OOM 时 `memory.events` 出现 `max 46 / oom 1 / oom_kill 1`。

> [!question]- 本机有哪些工具是装好但**用不了**的？为什么？
> - `ethtool -l`：单队列 `e1000`，驱动报 `netlink error: Operation not supported`。
> - `perf` 的硬件事件与裸 `perf stat`：PMU 设备节点在、计数器没透传，且默认事件集跑不动。
> - `perf top -b`：默认事件带 branch stack 修饰，本机不支持。
> - 非 root 下的 `perf`/`dmesg`/`bpftrace`/`blktrace`/`tcpdump`/`iotop`/`ip netns`：权限限制（`paranoid=4`、`dmesg_restrict=1`、`unprivileged_bpf_disabled=2`、AppArmor 禁非特权 userns）。
> - **第一反应不要是什么**：不要把它们当成「工具没装」——原因不同，解法也不同（一个要换硬件，一个要换身份）。

> [!question]- 为什么「未实测」清单本身也是交付物？
> - 它明确划定了结论的边界：哪些能负责、哪些只是方法。
> - 它给出了补做条件与命令，别人（或有权限的你）可以接着做。
> - 假称测过，会在真正的故障现场付出代价。
