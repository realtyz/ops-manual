## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **演练的三条纪律：在隔离环境、设明确上限、跑完清理并复核。**
>   - 怎么验证：每份演练记录结尾都有「无残留进程 / 无监听端口 / 无临时目录」三行复核结果。
> - **六类注入都有对应的观测指纹，练过一遍才能在真故障中认出它们。**
>   - 证据：单核超卖（整机 4.18% vs 单核 100%、吞吐 −76%）、内存 3 GiB（PSI 全 0）、深队列 IO（`aqu-sz=398.02`、`w_await=343.08 ms`）、`netem`（RTT 100.164 ms）、端口耗尽（TIME_WAIT 3002）、句柄耗尽（第 10236 个 fd 报 EMFILE）。
> - **缺依赖不是障碍，是常态；`ldd | grep "not found"` 配合 `dpkg-deb -x` 能解决大部分问题。**
>   - 证据：本机 `fio` 补了 12 个以上依赖、`stress-ng` 补了 4 个才启动，全程不需要 root、不需要安装。
> - **工具目录不要放 `/tmp`。**
>   - 证据：本机在会话中途遇到过 `/tmp` 下的解包目录消失（tmpfiles 规则是 30 天，未定位到清理者），后来改用 `$HOME/devtools`。
> - **未实测的部分要如实写下来，并给出补做方式——这本身就是排障经验的一部分。**
>   - 怎么验证：每份记录里「未实测」清单都带「需要什么条件、怎么补做」，而不是一句「没有权限」。

## 1. 演练纪律：三条不能破的边界

| 纪律 | 具体要求 | 违反的后果 |
| --- | --- | --- |
| **隔离** | 网络故障注入放进 `unshare -U -r -n` 的命名空间；破坏性 IO 写在可丢弃目录；cgroup 类实验用临时 unit | 影响真实业务、影响别的同事 |
| **上限** | CPU 负载 ≤ 20 秒；内存 ≤ 4 GiB；IO ≤ 2 GiB；连接 ≤ 3000 条；`fio` 必须带 `--runtime`/`--size` | 打满机器、打满磁盘、触发线上告警 |
| **清理与复核** | 结束残留进程、确认无监听端口、清理临时目录与 unit | 污染后续实验、留下常驻资源 |

```bash
pgrep -af "while True: pass|stress-ng|fio"      # 验证：无残留进程
ss -lnt                                         # 验证：无意外监听端口
systemctl --user list-units "lab*" --all        # 验证：临时 unit 已清理
```

## 2. 六类注入：怎么造、看什么、算不算通过

### 2.1 CPU 打满与单核超卖

```bash
timeout 16 taskset -c 2 python3 -c 'while True: pass' &            # 造：单核热点
mpstat -P ALL 1 3 | grep -E "^Average: +(all|2) "                  # 看：整机 vs 单核
for i in 1 2 3 4; do timeout 20 taskset -c 3 python3 -c 'while True: pass' & done   # 造：同核超卖
```

| 观测指纹 | 实测值 |
| --- | --- |
| 整机 `%usr` | 4.17%～4.18% |
| 目标核 `%usr` | 100.00% |
| `load average` | 0.12 |
| 吞吐（2 秒计数循环，同核 4 个竞争者） | 2598 万 → 622 万（−76%） |
| 延迟 `p50` / `max`（0 个 vs 5 个竞争者） | 8.13 → 12.00 ms / 8.34 → 25.79 ms |

**验收**：能说出「整机不忙但单核满」的判据链（`mpstat -P ALL` → `pidstat -u -t` → `taskset -cp`）。

### 2.2 内存压力

```bash
free -m | head -2; grep -H . /proc/pressure/memory                 # 基线
python3 -c 'import time
b=bytearray(3*1024*1024*1024)
for i in range(0,len(b),4096): b[i]=1
time.sleep(15)' &                                                  # 造：3 GiB 并逐页触碰
stress-ng --vm 1 --vm-bytes 1G --timeout 8s --metrics-brief        # 造：stress-ng 的内存压力
```

| 观测指纹 | 实测值 |
| --- | --- |
| `MemAvailable` | 15217 MiB → 12138 MiB |
| PSI memory `some`/`full` | 0 / 0（**没有压力，只是用掉了**） |
| `VmRSS` / `Rss` / `Pss` / `Anonymous` | 3082 / 3082 / 3078 / 3076 MiB |
| `stress-ng --vm` 指标 | 1,134,836 bogo ops，135,880 bogo ops/s |

**验收**：能解释「PSI 为 0 说明只是用掉了内存」；能区分「用量」与「压力」。

### 2.3 深队列 IO

```bash
iostat -x 1 14 > iostat.out &                                    # 同时采样
fio --name=deepq --filename=$F --size=1G --rw=randwrite --bs=4k \
    --iodepth=64 --direct=1 --runtime=12 --time_based            # 造：深队列随机写
stress-ng --hdd 2 --timeout 10s                                  # 造：更重的写压力
```

| 观测指纹 | 实测值 |
| --- | --- |
| `w/s` / `wkB/s` | 2439 / 2712912 |
| `w_await` | 54.72 ms（另一窗口 343.08 ms、404.00 ms） |
| `aqu-sz` | 133.47（另一窗口 398.02、256.54） |
| `%util` | 75.20%（另一窗口 74.40%、77.60%） |
| `pidstat -d` | `stress-ng-hdd` 各约 1437 MiB/s（`pidstat` 报 1471836 KiB/s），`iodelay` 为 0 |

**验收**：能用 `aqu-sz ≈ w/s × w_await` 交叉验证，并解释为什么 `%util` 不是饱和度。

### 2.4 网络延迟与丢包

```bash
unshare -U -r -n bash -c "ip link set lo up; tc qdisc add dev lo root netem delay 50ms; ping -c 3 -q 127.0.0.1 | tail -1"
unshare -U -r -n bash -c "ip link set lo up; tc qdisc add dev lo root netem loss 20%; ping -c 200 -q -i 0.02 127.0.0.1 | tail -2"
unshare -U -r -n bash -c "ip link set lo up; tc qdisc add dev lo root netem delay 50ms; python3 tcptest.py & sleep 3; ss -ti state established | head -4"
```

| 观测指纹 | 实测值 |
| --- | --- |
| 注入 50 ms 单向延迟后的 RTT | `min/avg/max = 100.085/100.164/100.227 ms` |
| `ss -ti` | `rtt:100.533/0.406`、`minrtt:100.131`、`cwnd:10`、`app_limited` |
| 注入 20% 丢包（200 包） | 实测 35.5%（`1 − 0.8² = 36%`） |
| 软中断丢弃 | `softnet dropped 0` |

**验收**：能解释「为什么配 20% 却丢 36%」，也能用 `ss -ti` 的 `app_limited` 把网络问题与应用问题分开。

### 2.5 句柄与端口耗尽

```bash
ulimit -n; cat /proc/sys/net/ipv4/ip_local_port_range
python3 -c 'fds=[]
try:
    for i in range(20000):
        fds.append(open("/dev/null"))
except OSError as e:
    print("opened=%d then failed: [Errno %d] %s"%(len(fds),e.errno,e.strerror))'
ss -tan state time-wait | wc -l                                  # 造完短连接后统计
```

| 观测指纹 | 实测值 |
| --- | --- |
| 句柄耗尽 | 打开第 **10236** 个 fd 后报 `[Errno 24] Too many open files`（软限 10240） |
| 端口范围 | `32768 60999`（28232 个） |
| 3000 条短连接（0.104 秒内） | TIME_WAIT 立即涨到 **3002** |
| 短连接 QPS 上限估算 | 28232 / 60 ≈ **470 条/秒**（对同一目标 IP+端口） |

**验收**：能说出「偶发失败」的两种典型原因与各自的量化模型。

### 2.6 cgroup 配额（无 root 版）

```bash
export XDG_RUNTIME_DIR=/run/user/1000
systemd-run --user --scope -p CPUQuota=20% --unit=labq python3 -c 'import time
t=time.perf_counter(); n=0
while time.perf_counter()-t<2.0: n+=1
print("iterations=%d"%n)'                                        # 造：CPU 限流
systemd-run --user --unit=labm6 --collect -p MemoryMax=512M -p MemorySwapMax=0 \
  -p OOMPolicy=continue bash -c "python3 -c 'b=bytearray(1024*1024*1024)
for i in range(0,len(b),4096): b[i]=1'; sleep 25"                # 造：内存 OOM
```

| 观测指纹 | 实测值 |
| --- | --- |
| `cpu.max` | `20000 100000`（20%） |
| `cpu.stat` | `nr_periods` 21→51，`nr_throttled` 21→51，`throttled_usec` 1.62 s→4.02 s |
| 吞吐 | 3179 万次/2 s → 593 万次/2 s（18.65%） |
| `memory.peak` / `memory.max` | 536870912 / 536870912（512 MiB） |
| `memory.events` | `max 35 / oom 1 / oom_kill 1` |
| 内核日志 | `oom-kill:constraint=CONSTRAINT_MEMCG`、`oom_score_adj:200` |

**验收**：能在容器内看到「CPU 不高但抖动」时，主动去宿主侧查 `cpu.stat`；知道 `OOMPolicy` 默认 `stop` 会让 unit 消失。

## 3. 工具可用性矩阵

### 3.1 本机实测结论

| 工具 | 状态 | 说明 / 替代 |
| --- | --- | --- |
| `uptime` `free` `ps` `top` `vmstat` `ss` `nstat` `ip` `tc` `lsof` `unshare` `systemd-run` `systemd-cgtop` `journalctl` `dmesg` `taskset` `pmap` | ✅ 自带可用 | 主力工具，覆盖 L0/L1 |
| `mpstat` `pidstat` `iostat` `sadc` `sar` | ✅ 解包运行 | 本机这版包里 `sar` 叫 `sar.sysstat` |
| `strace` | ✅ 解包运行 | 约 80 倍减速，限时限范围使用 |
| `perf` | ⚠️ 部分可用 | 软件事件与采样可用；无硬件 PMU；`perf sched` 被 tracefs 权限拒绝 |
| `fio` | ✅ 解包运行 | 需补 12 个以上共享库依赖 |
| `stress-ng` | ✅ 解包运行 | 需补 4 个共享库依赖 |
| `bpftrace` / `bcc` | ❌ 未实测 | `kernel.unprivileged_bpf_disabled=2`；需 root + 匹配内核 |
| `tcpdump` | ❌ 未实测 | 需要 `CAP_NET_RAW`；用 `ss -ti`/`nstat`/`softnet_stat` 替代 |
| `iotop` | ❌ 未安装 | 用 `pidstat -d` 替代 |
| `blktrace` / `biosnoop` | ❌ 未实测 | 需要 root/eBPF；用 `iostat -x` + `pidstat -d` 替代 |
| `smartctl` | ❌ 未安装 | 介质健康检查在阶段 5 |
| `numactl` | ❌ 未安装 | 多路 NUMA 场景需要 |

### 3.2 缺依赖的标准处理流程

```bash
ldd <binary> | grep "not found"                    # 验证：先看缺哪个库
apt-get download <package>                         # 验证：只下载不安装
dpkg-deb -x <package>.deb <dir>                    # 验证：解包到自己的目录
export LD_LIBRARY_PATH=<dir>/usr/lib/x86_64-linux-gnu:$LD_LIBRARY_PATH
```

三个实操注意：

1. **有些库在子目录里。** 本机 `libceph-common.so.2` 在 `.../ceph/` 下，`LD_LIBRARY_PATH` 要多加一层。
2. **工具目录不要放 `/tmp`。** 本机遇到过一次会话中途 `/tmp` 下的目录消失（规则是 30 天，未定位清理者）；稳妥位置是 `$HOME/<name>`。
3. **脚本里先检查再重建。** 例如 `[ -x "$D/root/usr/bin/fio" ] || setup_tools`，避免每次重跑都重新下载。

## 4. 未实测清单与补做方式

| 未实测项 | 需要什么条件 | 补做方式 |
| --- | --- | --- |
| 硬件 PMU（`cycles`/`instructions`/`cache-misses`） | 物理机或开启 PMU 的云主机 | `perf stat -e cycles,instructions,cache-misses ./app`；对比 IPC |
| 火焰图 | `perf` 符号 + FlameGraph 脚本 | `perf record -F 99 -g` → `perf script` → `stackcollapse-perf.pl` → `flamegraph.pl` |

| 块层归因 | root | `blktrace -d /dev/sdX` 配 `blkparse -i -`；或 `biosnoop-bpfcc` |
| 真实网卡多队列 / offload | 物理网卡 + root | `ethtool -l`/`-S`、`mpstat` 看 `%soft` 分布、RPS/RFS 配置 |
| 抓包分析 | `CAP_NET_RAW` | `tcpdump -i <dev> -c 200 -w cap.pcap "host X and port Y"`（限时限量） |
| 生产级摘流量 / 回滚演练 | 集群与发布系统 | 在预发环境按灰度流程演练，记录验收指标与回滚耗时 |
| GPU / 高速网卡 | 对应硬件 | `nvidia-smi dmon`、`rdma link`、`ibv_devinfo`、`ethtool -S` |

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 「在测试机上随便跑压力」 | 测试机也在内网、也可能有告警；要隔离、设上限、跑完清理 |
| 「`fio` 不带 `--runtime`」 | 可能跑满整块盘甚至写满分区 |
| 「故障注入不清理」 | 残留进程/端口会污染后续实验，甚至被误认为真实故障 |
| 「工具没装就不测了」 | 本机 8 个主力工具都没装，靠解包 + 降级路径完成了全部实验 |
| 「解包工具放 `/tmp`」 | 本机实测遇到过中途消失；放 `$HOME` 更稳 |
| 「没有 PMU / eBPF 就不写结论」 | 未实测的部分要如实写，并给出补做方式；不写才是真的缺口 |
| 「预案只在纸面上」 | 没跑过的预案不算预案；演练要把「观测指纹」也记下来 |
| 「演练等于压测」 | 演练的目的是练「判读路径」，不是刷高负载数字 |

## 决策练习

**场景**：你被要求在一个**共享的预发环境**（有真实流量、有告警、有同事在用）上验证一套「服务变慢」的排障流程。你没有 root，机器不允许安装任何软件。

**选项**：

- **A. 直接在预发环境跑 `stress-ng --cpu 24 --vm 4 --hdd 4` 造一次综合负载，练全套流程。**
- **B. 先做只读部分（五组基线 + 一次性取证），再用限定上限、限定范围的方式做注入：单核自旋绑到指定核、网络注入放进 `unshare` 命名空间、内存与 IO 上限设为 1 GiB；每步前后各取一组证据，最后复核清理。**
- **C. 放弃演练，改成讲解一遍流程。**

**为什么选 B**：演练的目标是练判读路径，不是刷负载。复用「隔离 + 上限 + 清理」三条纪律，能在共享环境里做出有效练习：单核自旋只占一个核（整机才 4%），命名空间里的网络注入完全不外溢，1 GiB 的内存/IO 上限对预发环境影响可控，而且每一步都有证据可对照。

**为什么不选 A**：24 核满载加 4 路 IO 会直接影响共享预发环境的其它用户与告警，属于「在别人的生产环境里做破坏性实验」。

**为什么不选 C**：没有跑过的预案不算预案——演练真正的产出是「观测指纹」和「手速」，不是文档。而且 B 的每一部分都不需要 root，也不需要安装软件。

## 要点自测

> [!question]- 一次安全的故障演练必须满足哪三个条件？
> - 隔离（命名空间 / 可丢弃目录 / 临时 unit）、明确上限（时长、内存、IO、连接数）、跑完清理并复核（无残留进程/端口/临时目录/unit）。
> - 还应当**先记录观测指纹再结束**，否则练完什么也没留下。

> [!question]- 六类注入各自的「观测指纹」是什么？
> - CPU：整机 `%usr` 4.18% 对目标核 100%；吞吐 −76%；`p50` 8.13→12.00 ms。
> - 内存：`MemAvailable` 少 3 GiB 而 PSI 全 0。
> - IO：`aqu-sz` 133→398、`w_await` 54.72→343.08 ms、`%util` 75% 上下。
> - 网络：RTT 100.164 ms、`ss -ti` 的 `minrtt:100.131`、丢包 35.5%（理论 36%）。
> - 句柄/端口：第 10236 个 fd 报 `EMFILE`；3000 条短连接后 TIME_WAIT 3002。
> - cgroup：`nr_throttled` 51/51、`throttled_usec` 4.02 s、吞吐 18.65%；OOM 时 `memory.events` 出现 `oom_kill 1`。

> [!question]- 工具缺依赖时的标准处理流程是什么？
> - `ldd <binary> | grep "not found"` 找出缺的库 → `apt-get download <pkg>` → `dpkg-deb -x` 解包 → 追加 `LD_LIBRARY_PATH`。
> - 注意子目录（本机 `libceph-common.so.2` 在 `.../ceph/` 下）与工具目录位置（不要放 `/tmp`）。
> - 本机 `fio` 补了 12 个以上依赖、`stress-ng` 补了 4 个。

> [!question]- 为什么「未实测」清单本身也是交付物？
> - 它明确划定了结论的边界：哪些能负责、哪些只是方法。
> - 它给出了补做条件与命令，别人（或有权限的你）可以接着做。
> - 假称测过，会在真正的故障现场付出代价。
