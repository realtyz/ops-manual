# 性能的语言与「看起来空闲」的那一层

一个 4 核的机器，`%usr` 只有 25%、`load average` 0.34、`free` 还有 7 GiB 可用、数据盘 `%util` 15%——每个数字都在说"这台机器很闲"，可服务就是慢了。这不是指标在骗人，而是**这些指标回答的不是同一个问题**。把它们混着读，就一定会得出"机器没问题，去查应用吧"这种既对又没用的结论。

把"慢"翻译成几个可测量的量之后，每个量的边界才看得清：哪些是工具不承诺的、哪些是聚合口径丢掉的、哪些必须与别的量一起读。

下列具体数值取自一台 4 vCPU、`MemTotal` 7894 MiB、内核 6.8 的 Ubuntu 24.04 虚拟机（`systemd-detect-virt` = `vmware`），配合 `sysstat` 12.6.1、`perf` 6.8.12、`strace` 6.8、`fio` 3.36、`stress-ng` 0.17.06。**这些数字只用来说明量级与关系，不是可以照搬到别的机器上的结论**；每一段都注明了单位与比较对象。

## 1. 五个量，五个不同的问题

| 量 | 英文 | 回答的问题 | 常用单位 | 典型来源 |
| --- | --- | --- | --- | --- |
| 延迟 | latency | 一次操作要等多久 | 毫秒、微秒（要连口径一起说） | 业务指标、`ss -ti` 的 `rtt`、`iostat` 的 `await` |
| 吞吐 | throughput | 单位时间完成多少次操作 | 次/秒、IOPS、MiB/s | 业务 QPS、`iostat` 的 `w/s`、`fio` 的报告 |
| 利用率 | utilization | 资源有多长时间是忙的 | 百分比 | `mpstat` 的 `%usr`、`iostat` 的 `%util` |
| 饱和度 | saturation | 有多少工作在排队等它 | 排队长度、队列时间 | `vmstat` 的 `r`/`b`、`iostat` 的 `aqu-sz`、PSI |
| 错误 | errors | 有没有失败的操作 | 次数、比率 | 业务错误率、`nstat` 的计数器、内核日志 |

按资源把后三问排一遍，就是 USE 方法（Utilization / Saturation / Errors，Brendan Gregg 提出）：对 CPU、内存、磁盘、网络每一类都问"多忙、排多长、错多少"。它的价值不在于多问，而在于**逼你不要只问第一个**——前面那个例子的问题，恰恰是三个数字都属于"利用率"，一个"饱和度"都没看。

三个量之间的关系，用一句话记住：

**利用率告诉你资源有没有闲着；饱和度告诉你有没有人在等；只有两者都低，才轮到"资源不是原因"。**

## 2. 为什么"利用率 70%"比"利用率 30%"危险得多

把服务时间记作 `S`，把请求到达率记作 `λ`，那利用率就是 `ρ = λS`。利用率从 30% 涨到 70%，人们直觉上觉得"还有 30% 余量"；但延迟的变化不是线性的。

排队论的经典结果（M/M/1 这类单服务台模型）给出的是响应时间 `R = S / (1 − ρ)`（这里的 `S` 是服务时间，`R` 含排队）：

| 利用率 ρ | `1/(1−ρ)` | 相对服务时间放大多少倍 |
| --- | --- | --- |
| 0.3 | 1.43 | 1.4 倍 |
| 0.5 | 2 | 2 倍 |
| 0.7 | 3.3 | 3.3 倍 |
| 0.9 | 10 | 10 倍 |
| 0.95 | 20 | 20 倍 |
| 0.99 | 100 | 100 倍 |

这张表是这一章最该记住的东西：**资源"还没满"与"还有余量"是两句话**。利用率 70% 时，一次突发就能把延迟推到服务时间的 3 倍以上；利用率 99% 时，多一个请求就多等一个数量级。

现实中的资源还不止一个服务台，所以绝对倍数不会正好这样，但**形状是可靠的：利用率越高，延迟对到达率的敏感度越高**。这也是为什么容量规划要留余量，而不是把利用率优化到 90%。

## 3. Little's law：用三个数互相校验

Little's law（利特尔法则）说：稳定状态下，

**在途数量 `L` = 到达率 `λ` × 平均停留时间 `W`**

它不依赖任何分布假设，所以是排障里最好用的一条"算术校验"。落在 IO 上，`iostat` 的三个列正好对应：

- `w/s` 是到达率（每秒完成多少次写，稳态下等于到达率）；
- `w_await` 是平均停留时间（含排队与服务）；
- `aqu-sz` 的原文定义是 "The average queue length of the requests that were issued to the device."（发往该设备的请求的平均队列长度，旧名 `avgqu-sz`）——它近似于模型里的"在途数"，但**是实测的队列长度，不是模型量**。

于是 `w/s × w_await ≈ aqu-sz` 应当成立——**如果对不上，说明你看的不是稳态**（窗口里有突发、有任务刚启动、或者设备换了行为）。

这里要标清性质：`iostat(1)` 与 sysstat 的官方 FAQ 里**都没有把它写成一个公式**（只把 `aqu-sz` 定义为 "The average queue length of the requests that were issued to the device."），等式本身是**从定义推出的**，不是文档原文。所以它是你的校验手段，不是工具的承诺。在六组不同压力的窗口里，乘积与实测的 `aqu-sz` 三组完全相等、三组只差 0.04～0.08，偏差来自 `w_await` 只保留两位小数：

```text
# 说明：数值仅示意、不代表你的机器
# 同一设备在六种不同压力下的窗口读数（iostat -x 的列）
324.00 × 0.00659 = 2.135    aqu-sz 2.14    %util 80.10%
419.00 × 0.00623 = 2.610    aqu-sz 2.61    %util 83.30%
477.00 × 0.00114 = 0.544    aqu-sz 0.54    %util 42.50%
35457  × 0.00009 = 3.191    aqu-sz 3.15    %util 98.80%
```

（第一列是 `w/s`，第二列是 `w_await` 换算成秒后的值，乘起来就是预计的 `aqu-sz`。）

这条式子最大的用处是**把"看着像"变成"算得出"**：单位时间该排多少队、`await` 这么低为什么还有 3 个请求在飞——都是乘法能回答的问题。

反过来，它也说明**单看一个数会得出相反结论**。`w_await = 0.09 ms` 听上去快得离谱，可配上 35,457 次/秒的到达率，设备上同时有 3 个请求；`w_await = 6.59 ms` 听上去慢，配上 324 次/秒只有 2.14 个。**延迟高不高，要看它是在什么负载下量出来的。**

## 4. 平均值会同时掩盖长尾和拐点

排障时最容易被"平均"骗。同一个 2 秒的固定计算循环，在同一颗核上跑：

```text
# 说明：数值仅示意、不代表你的机器（绑在一颗核上、竞争者逐个加入）
独占：        26,473,519 次 / 2.00 s
1 个竞争者：  12,461,811 次 / 2.00 s      # −52.9%
4 个竞争者：   5,564,871 次 / 2.00 s      # −79.0%
```

同一时刻用 `time.sleep(8 ms)` 的延迟探针测量唤醒延迟（n=300）：

| 场景 | p50 | p95 | p99 | max |
| --- | --- | --- | --- | --- |
| 独占 | 8.13 ms | 8.25 ms | 8.34 ms | 8.36 ms |
| 1 个竞争者 | 8.06 ms | 8.10 ms | 8.11 ms | 10.82 ms |
| 5 个竞争者 | 8.06 ms | 10.99 ms | 11.02 ms | 16.58 ms |
| 15 个竞争者 | 8.06 ms | 10.01 ms | 11.00 ms | **40.87 ms** |

请注意两件事：

- **中位数从头到尾几乎没动**（8.13 → 8.06 ms），而吞吐掉了 79%、`max` 涨了 4.9 倍。只看 p50 会说"没问题"；
- **期间整机 `%usr` 始终是 25%**。机器视角看不到这件事，是因为指标的对象和现象的对象不是同一个。

所以"慢"要固定按 **p99 / max → p95 → p50 → 平均**的顺序看：先确认尾部有没有坏，再判断是普遍慢还是少数请求慢。平均值既掩盖长尾，也掩盖只影响一部分请求的拐点。

三个必须写进结论里的口径，缺一个数就不可比：

- **窗口**：1 秒采样、1 分钟聚合、5 分钟滑动窗，看到的完全是两件事；
- **算法**：同一个"p95"，分位数算法不同结果可以不同；跨机器比较前先确认算法与聚合层级；
- **聚合层级**：不能把各实例的 p95 再平均成"全局 p95"——那不是分位数。要把分位数合并，得从直方图算（这件事在阶段 9 的《体系：一次告警的一生》里展开）。

## 5. 四个视角：同一个现象，四种结论

性能数据是有"焦距"的。四个视角各自能回答、也各自回答不了：

| 视角 | 你在看什么 | 典型来源 | 什么时候必须用 |
| --- | --- | --- | --- |
| 整机 | 这台机器整体像不像有问题 | `uptime`、`vmstat`、`mpstat` 的 `all` 行、`free`、`iostat` | 第一分钟定范围 |
| 单核 | 有没有某一颗核已经贴到 100% | `mpstat -P ALL`、`/proc/interrupts` | 整机看着很闲但延迟高 |
| 进程 | 是谁在花时间、谁在等 | `ps`、`pidstat`、`/proc/<pid>/*` | 已经确定是哪一层 |
| 线程 | 一个进程内部是哪个线程 | `pidstat -u -t`、`top -H`、`/proc/<tid>/sched` | 多线程服务只有一个线程热 |
| cgroup | 这个服务实际被限额多少、用掉多少 | `/sys/fs/cgroup/...`、`systemctl show` | 容器、systemd 服务 |

同一个时刻、同一个负载，四个视角给出四种说法：

```text
# 说明：数值仅示意、不代表你的机器（一个被绑在某一颗核上的单线程任务）
Average:     all   25.04  ...  74.96        # 整机：四分之三的算力空着
Average:       2  100.00  ...   0.00        # 单核：这一颗已经没有任何余量
Average:        0  45062 ...  100.00  python3
pid 45062's current affinity list: 2        # 单线程：只装在这颗核上
load average: 0.34, ...                     # load：几乎没变
```

**判据不是"整机利用率高不高"，而是"最热的那颗核还剩多少"**。容量规划同理：按最热核算，不按整机平均算。

## 6. 「慢」的三种形态，决定采样的密度

在开始看任何数据之前，先问清是哪种形态——它决定你用什么窗口去采，采错了就什么都看不到：

| 形态 | 现象 | 采样要求 | 典型例子 |
| --- | --- | --- | --- |
| 恒定慢 | 每次都慢，一直慢 | 任取一段窗口都行 | 深队列随机写期间 `w_await` 稳定在 0.07～0.27 ms、`%util` 稳定在 74～99% |
| 间歇尖刺 | 大部分请求正常，偶发卡顿 | 高频或累积量；1 分钟聚合会看不见 | 一次 1000 MiB 的 `dd oflag=direct` 只持续 **0.196 秒**，2 GiB 的 `dd conv=fdatasync` 只持续 **0.82 秒** |
| 周期慢 | 每隔固定周期变慢 | 覆盖 2～3 个周期再下结论 | 备份任务、`logrotate`、`updatedb`、证书续期 |

间歇尖刺是最容易漏的一类：一个只持续 0.196 秒的脉冲，如果采样窗口是 1 分钟聚合，它在图上几乎不存在；而用户感受到的正是那一秒里的请求。**看见"没有异常"之前，先确认你的窗口能看见这个形态。**

## 常见误解

| 说法 | 事实 |
| --- | --- |
| "整机 CPU 只有 25%，CPU 不是瓶颈" | 单核可以已经 100%。判据是**最热核**的余量，不是整机平均 |
| "`load` 才 0.3，肯定不忙" | `load` 只数可运行与不可中断任务的平均数，一颗核打满在 4 核机上就是 +1 的量级；它也不是使用率 |
| "`%util` 到 100% 才是磁盘瓶颈" | `%util` 是"至少有一个请求在途的时间占比"，不是饱和度。它 98.80% 时 `aqu-sz` 可能只有 3.15 |
| "`await` 才 0.09 ms，磁盘很快" | 0.09 ms 配上 35,457 次/秒，在途请求是 3 个。延迟要连着负载读 |
| "p50 正常，所以服务正常" | 中位数在 15 个竞争者的场景里从头到尾没动，而 `max` 涨了 4.9 倍 |
| "平均延迟达标就够了" | 平均值同时掩盖长尾和"只影响一部分请求"的拐点 |
| "先把 p95 平均一下得到全局 p95" | 分位数不能跨实例取平均；要合并就得从直方图算 |
| "跑一次 `iostat 1 3` 没事就没事" | 只覆盖 3 秒；间歇与周期形态需要合适的窗口和覆盖周期 |
| "延迟就是应用自己测的那个数" | 应用测的是"它的视角"；网络、排队、调度、GC 都可能加在中间，要连口径一起对齐 |

**第一反应不要做什么**：不要拿一个"整机很闲"的数字去否定整个资源层；不要用平均值或中位数宣布问题不存在；不要在没说清窗口与算法之前比较两个分位数。

## 要点自测

**问：为什么"利用率 70%"和"还有 30% 余量"不是一回事？**
答：延迟对利用率的敏感度是 `1/(1−ρ)` 这种形状：ρ 从 0.3 到 0.7，延迟倍数从 1.4 涨到 3.3；ρ 到 0.95 就是 20 倍。余量指的是"距离饱和还有多远"，不是"延迟还能保持线性多久"。

**问：`w/s × w_await` 和 `aqu-sz` 对不上，最可能说明什么？**
答：说明窗口不是稳态——有突发、任务刚起、或设备行为在窗口内变了。这个式子是用来发现"你看的不是稳态"的，不是用来修正读数的。

**问：整机 `%usr` 25% 但接口 p99 涨了 8 倍，你的第一动作是什么？**
答：换成单核与线程视角：`mpstat -P ALL` 找贴到 100% 的核，再用 `pidstat -u -t` 落到线程、`taskset -cp` 确认亲和性。不要因为整机不忙就把 CPU 层排除掉。

**问：`%util` 98.8% 而 `w_await` 只有 0.09 ms，这两个数矛盾吗？**
答：不矛盾。`%util` 量的是"设备至少有一个请求在途的时间占比"，大块/并发 IO 会让它很高；`await` 是平均停留时间，队列浅、单次服务时间短就会低。两者一起看才说明"设备几乎一直有活在手上，但每个请求等得不久"。

**问：为什么中位数也会骗人？**
答：因为只影响一部分请求的恶化不会进入中位数。同核竞争加到 15 个时 p50 一直是 8.06 ms，而 `max` 从 8.36 ms 涨到 40.87 ms —— 受影响的是尾部请求，而用户投诉的常常就是它们。

**问：一个只持续 0.2 秒的 IO 脉冲，怎么保证不被漏掉？**
答：先判断形态属于"间歇尖刺"，然后用累积量或高频采样（`/proc/vmstat` 的计数器取差分、`pidstat -d 1`、PSI 的 `total`），而不是用 1 分钟聚合的平均值去证明"没有异常"。

**第一反应不要做什么**：不要用一个视角的数字否定另一个视角的结论；不要在没确认形态之前挑采样窗口；不要把 p95 平均成"全局 p95"。
