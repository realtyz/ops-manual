## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **止损动作按「代价从低到高」排序：限流 → 摘流量 → 回滚 → 扩容 → 重启。**
>   - 怎么验证：对每个候选动作先问三句「预期效果是什么、验收指标是哪个、怎么回滚」，答不全就不做。
> - **每个动作都要能回滚，且回滚方式要事先写下来。**
>   - 证据：`systemd-run --user --scope -p CPUQuota=20%` 这种限流是天然的「有期限、可回滚」动作；实测把 2 秒计数循环从 3179 万次压到 593 万次（18.65%），停止 scope 即恢复。
> - **「修好了」的判据是「同一组指标回到基线 + 业务验收通过 + 观察窗口无事」。**
>   - 怎么验证：沿用第 1 站那组量化指标（p99、错误率、吞吐），加上一个明确长度的观察窗口。
> - **报告固定六段：时间线 / 影响面 / 证据 / 根因 / 止损 / 长期改进。**
>   - 怎么验证：让没参与排障的同事照着报告复述一遍，能复述就说明写清楚了。
> - **长期改进必须能落到「谁、什么时候、交付什么」。**
>   - 怎么验证：把改进项写成「补齐每核使用率与 p99 告警（owner：X，期限：两周）」，而不是「加强监控」。

## 1. 止损手段的排序

### 1.1 五种手段的代价与适用面

| 手段 | 适用现象 | 代价 | 回滚方式 | 典型隐患 |
| --- | --- | --- | --- | --- |
| **限流**（网关限速、cgroup 配额、`ionice`、降低线程数） | 资源被单一负载吃满；故障源明确 | 低（有损但可控） | 撤掉配额 / 恢复并发度 | 限得太狠会把正常请求也拒掉 |
| **摘流量**（下线实例、摘除健康检查、切主） | 单实例异常、单机房异常 | 中（容量下降） | 重新挂回 | 剩余实例可能被压垮（要确认容量余量） |
| **回滚**（回滚发布、回滚配置） | 拐点与变更高度对齐 | 中高（丢失新功能/数据兼容风险） | 再次发布（要确认可逆性） | 有数据库迁移时可能不可逆 |
| **扩容**（加副本、加实例、提规格） | 真实容量不足 | 高（成本 + 复杂度） | 缩容 | 对单核热点/锁竞争常常无效 |
| **重启** | 状态泄漏、句柄泄漏、死锁 | 高（现场消失） | 无法回滚 | 毁掉现场，且大概率复发 |

### 1.2 三条排序原则

1. **能限流就不摘流量，能摘流量就不重启。** 代价低的动作先试，因为它同时是「验证假设」的实验。
2. **一个动作只改一个变量。** 同时限流又扩容，事后无法判断哪个起了作用（也无法知道哪个该保留）。
3. **先取证，再动手。** 只有在影响面还在扩大、且动作不需要现场时，才允许「先止损、后补证据」——但必须同时记录时间、动作与当时的指标。

### 1.3 每个动作的三件套

做任何变更前，把这三句话写在纸上（或事故单里）：

```text
动作：给批处理任务所在的 scope 设置 CPUQuota=20%
预期效果：批处理吞吐降到原来的 ~20%，宿主上延迟敏感服务的 p99 回落到 130 ms 以内
验收指标：该 scope 的 cpu.stat 出现 nr_throttled 增长；业务侧 p99 < 130 ms；错误率 < 0.5%
回滚方式：systemctl --user stop <scope>，或把 CPUQuota 恢复为原值
观察窗口：变更后连续观察 15 分钟
```

## 2. 怎么验证「修好了」

### 2.1 三件套验收

| 维度 | 判据 | 例子 |
| --- | --- | --- |
| **指标回落** | 第 1 站那组量化指标回到基线范围 | p99 从 900 ms 回到 120 ms 以内；错误率回到 0.1% |
| **业务验收** | 真实的用户视角正常 | 下单成功率恢复、报表按时产出、下游不再报错 |
| **观察窗口** | 在明确长度的时间窗内没有复发 | 连续观察 15～30 分钟（周期性故障要覆盖 2～3 个周期） |

### 2.2 反例：哪些说法不算「修好了」

- 「重启之后好了」——只证明症状消失，不证明不会复发（子笔记 14 的常见坑）。
- 「指标没报警了」——可能是告警阈值被临时调高，或者流量低谷掩盖了问题。
- 「我改了参数，感觉快多了」——没有量化对照，等于没有验证。

### 2.3 恢复后立刻再取一份基线

故障恢复后的第一件事，是把**正常态**的同一组指标记下来（第 1 站的五项）：这份数据既验证了「确实恢复了」，又成为下次对比的基线。

## 3. 六段排障报告

### 3.1 模板

```text
1. 时间线：几点发现、几点定位、几点止损、几点恢复；关键动作与变更
2. 影响面：受影响的服务/实例/用户；延迟分位数、错误率、吞吐的变化；持续时长
3. 证据：同一时刻的命令与输出（含工具版本、采样窗口、环境）
4. 根因：直接原因 + 触发条件 + 为什么之前的防线没拦住
5. 止损动作：做了什么、为什么是它、有没有副作用
6. 长期改进：代码 / 配置 / 容量 / 监控告警 / 演练，各自有 owner 与期限
```

### 3.2 示例（用本机实测的单核超卖现场填）

> **时间线**：13:23:15 在 CPU 2 上启动一个自旋进程；13:23:18 观测到 CPU 2 达到 100%；13:23:33 结束负载。
>
> **影响面**：与热点同核的延迟敏感任务受影响——定量结果来自同核超卖实验：固定工作量从 **2598 万次/2 s** 掉到 **622 万次/2 s（−76%）**，延迟探针 `p50` 从 **8.13 ms** 升到 **12.00 ms**、`max` 从 **8.34 ms** 升到 **25.79 ms**。**整机 `%usr` 始终只有 4.18%、`load` 只有 0.12，大盘上看不出异常。**
>
> **证据**：`mpstat -P ALL 1 3`（`Average: all 4.17 … 95.80` 与 `Average: 2 100.00 … 0.00`）；`pidstat -u -t -p <pid> 1 2`（单线程 `%CPU 100.50`，`CPU=2`）；`top -b -n1 -H`（线程 `R` `99.9%`）；`taskset -cp`（亲和性 `2`）；`/proc/<pid>/{status,sched}`（`voluntary=1 / nonvoluntary=9`、`nr_switches=10`）。
>
> **根因**：单线程热点占满一个核，与延迟敏感任务共享同一 CPU；**直接原因是绑核/放置策略，触发条件是热点任务与延迟敏感任务被调度到同一个核，防线缺口是监控缺少「每核使用率」与「p99」两个指标。**
>
> **止损**：把热点与延迟敏感任务分离到不同核（`taskset` / `cgroup cpuset`），或对热点做限流（例如 `CPUQuota=20%`，本机实测可把吞吐压到 18.65%）。没有副作用的前提是：分离后两个任务仍各自有足够的核。
>
> **长期改进**：① 监控补「每核 `%usr`」与「p99 延迟」双指标（owner + 期限）；② 容量评估改为按核、按 p99 计算，而不是按整机平均；③ 把「单核超卖」加入故障演练清单；④ 检查部署编排是否默认把关键服务与批处理放到同一批核上。

### 3.3 面向上级 vs 面向复盘

同一份六段报告，两种用途的详略不同：

| 场合 | 重点 | 可以省略 |
| --- | --- | --- |
| **向上级 / 用户同步** | 影响面、当前状态、止损动作、预计恢复时间 | 命令细节 |
| **技术复盘** | 证据、根因、防线缺口、改进项与 owner | 面向业务的话术 |

## 4. 长期改进：四个方向 + owner

一次性能故障的改进项几乎总能归到这四类，每一类都要有人、有期限：

| 方向 | 典型改进项 | 验收 |
| --- | --- | --- |
| **监控告警** | 补每核使用率、补 p99、补 PSI、补 cgroup 限流告警、补句柄/端口水位 | 告警规则上线并在演练中真的响过 |
| **容量** | 按核与 p99 做容量评估、建立 `fio` 四象限基线、更新基线卡 | 一份新的基线卡 |
| **代码 / 配置** | 修同步落盘、减少系统调用、修正绑核与并发度、修句柄泄漏 | 变更记录 + 验证 |
| **演练** | 把这次场景加进演练清单并真的跑一遍 | 一份演练记录 |

## 5. 生产动作：一次止损的完整记录（有产出物）

```text
【现象】批处理任务期间，宿主上服务 p99 从 130 ms 涨到 480 ms
【分层结论】CPU 2 被批处理的单线程热点占满（整机 %usr 4.2%，load 0.12）
【候选动作与代价】
   A 限流（CPUQuota=20%）  代价低、可回滚、可验证     ← 先做
   B 摘流量（下掉一台实例） 代价中、容量下降
   C 改绑核（taskset）     代价低但需要重启进程       ← 与 A 可并用
   D 扩容                  代价高，对单核热点可能无效
【执行】A：systemd-run --user --scope -p CPUQuota=20% 包住批处理
【验收】scope 的 cpu.stat 出现 nr_throttled 增长；服务 p99 回落 < 130 ms；观察 15 分钟无复发
【回滚】systemctl --user stop <scope>（配额定在 unit 上时改为恢复原值 + daemon-reload）
【复盘】六段报告 + 四项长期改进（含 owner 与期限）
```

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 「先重启，恢复业务要紧」 | 现场与证据一起消失；大概率复发，而且下次没有更好的线索 |
| 「一边限流一边扩容，双保险」 | 两个变量同时改，事后无法判断哪个起作用，也无法知道该撤哪个 |
| 「重启之后好了，收工」 | 只证明症状消失。验收要「指标 + 业务 + 观察窗口」三件套 |
| 「告警不响了就是好了」 | 可能是阈值被调高或流量进入低谷；要用同一组指标对比基线 |
| 「改进项写『加强监控』」 | 没有 owner 与期限的改进项等于没有改进 |
| 「报告只写给上级看」 | 面向复盘的那一版才是资产；技术细节（证据、防线缺口）不能省 |
| 「根因就是磁盘慢」 | 「磁盘慢」是现象。根因要写到「谁在什么条件下做了什么，导致哪个资源排队」 |
| 「扩容能解决所有性能问题」 | 对单核热点、锁竞争、同步落盘常常无效，只是把问题推后 |
| 「复盘要追责到人」 | 复盘的目标是补防线。追责会让人下次不敢说真话 |

## 决策练习

**场景**：一个服务的 p99 在 10 分钟内从 80 ms 涨到 1.2 s，错误率从 0.1% 涨到 4%。你已经确认：CPU 每核都不高，内存 PSI 为 0，磁盘 `await` 正常，但 `nstat` 的 `TcpExtListenOverflows` 在快速增长，`ss -lnt` 显示监听套接字的 `Recv-Q` 接近上限。

**选项**：

- **A. 立刻扩容三个副本，先把错误率压下去。**
- **B. 判断为「应用来不及 `accept()`」，先限流/排队保护把错误率压住，同时抓 `/proc/<pid>` 与 `strace -c` 确认 accept 路径；扩容作为备选。**
- **C. 重启服务，让 `Recv-Q` 清零。**

**为什么选 B**：`TcpExtListenOverflows` 增长 + `Recv-Q` 接近上限，是「accept 队列溢出」的明确指纹——**瓶颈在应用侧的接受能力，不在网络也不在资源**。限流（或让上游降低并发）是可回滚、代价最低的动作；同时用 `/proc/<pid>/{status,sched,io}` 与限时的 `strace -c` 确认 accept 路径上是不是有阻塞（例如每次 accept 后同步写日志）。扩容能否有效取决于是否存在单点（例如单线程 acceptor），所以放在备选。

**为什么不选 A**：如果是单线程 acceptor 或全局锁，扩容不会提升接受能力，反而增加系统复杂度与成本；而且它掩盖了「为什么要排队」这个根因。

**为什么不选 C**：重启会瞬间清空队列、错误率下降，看起来「修好了」，但根因（接受能力不足）没有变化，会在下一次流量上升时复发；同时毁掉了现场。

## 要点自测

> [!question]- 五种止损手段怎么排序？为什么？
> - 限流 → 摘流量 → 回滚 → 扩容 → 重启（代价从低到高）。
> - 原则：先做代价低、可回滚、能验证假设的动作；一个动作只改一个变量；先取证再动手。
> - 例外：影响面还在扩大且动作不依赖现场时，可以先止损，但必须同时记录时间、动作与指标。

> [!question]- 怎么证明「修好了」？
> - 三件套：同一组量化指标回到基线（p99/错误率/吞吐）+ 业务侧验收通过 + 观察窗口内无复发。
> - 恢复后立刻再取一份「正常态」基线，用于下次对比。
> - **第一反应不要是什么**：不要把「重启后好了」当结论。

> [!question]- 六段报告是哪六段？哪一段最容易被漏掉？
> - 时间线 / 影响面 / 证据 / 根因 / 止损动作 / 长期改进。
> - 最容易漏的是**根因里的「为什么之前的防线没拦住」**，以及**长期改进里的 owner 与期限**——这两项才决定同样的故障会不会再来一次。

> [!question]- 为什么「一边限流一边扩容」是坏做法？
> - 两个变量同时变，事后无法归因：不知道是限流起效还是扩容起效，也就不知道该保留哪个。
> - 保留错误的措施会带来持续成本（多出来的容量）或被掩盖的隐患（限流把正常流量也挡了）。
> - 正确做法：先做代价最低、可回滚的那一个，观察验收指标，再决定下一步。

> [!question]- 长期改进的四个方向是什么？
> - 监控告警（补每核、p99、PSI、cgroup 限流、句柄/端口水位）。
> - 容量（按核与 p99 评估、`fio` 四象限基线、更新基线卡）。
> - 代码/配置（同步落盘、系统调用、绑核与并发度、句柄泄漏）。
> - 演练（把场景加入演练清单并真的跑一遍）。
> - 每一项都要有 owner 与期限，否则等于没写。
