## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **内存要看压力，不看用量。**
>   - 证据：一个进程分配并逐页触碰 3 GiB 后，`MemAvailable` 从 **7224 MiB** 降到 **4145 MiB**（−3079 MiB），而 `/proc/pressure/memory` 的 `avg10/avg60/avg300` **全程为 0.00**，`pgscan_direct` 也是 **0**；`VmRSS` **3082 MiB**、`VmSwap` **0**。
> - **判断 IO 排队优先看 `await` 与 `aqu-sz`，`%util` 只作参考——而且 `%util` 高不代表队列深。**
>   - 证据：`stress-ng --hdd 2` 窗口实测 `w/s=324`、`w_await=6.59 ms`、`aqu-sz=2.14`、`%util=80.10%`；`fio` 深队列窗口 `w/s=35457`、`w_await=0.09 ms`、`aqu-sz=3.15`、`%util=98.80%`——**前者队列更长、后者利用率更高**。
> - **`fsync` 是最容易被忽视的延迟来源。**
>   - 证据：同一块盘上 200 次 4 KiB 写，`fsync` 版本 `p50=0.3614 ms`，纯缓冲写 `p50=0.0019 ms`，**约 190 倍**；`fsync` 的 `p99` 更是缓冲写的 53 倍（1.5105 ms vs 0.0286 ms）。
> - **基线不能用「感觉」代替；而且队列深度必须用 `libaio` 才吃得到。**
>   - 证据：`fio` 实测顺序写 **1495 MiB/s**、顺序读 **1708 MiB/s**，4 KiB 随机写 **27.3k IOPS / 107 MiB/s**、随机读 **47.5k IOPS / 185 MiB/s**；同一个 `--iodepth=32`，用默认的 `psync` 引擎只跑出 **11.7k IOPS**（引擎忽略 `iodepth`），换 `libaio` 才到 27.3k。
> - **下钻顺序是「设备 → 进程 → 文件 → 调用栈」，而且 1 秒采样可能漏掉短脉冲。**
>   - 证据：本机 1000 MiB 的 `dd oflag=direct` 只持续 **0.196 秒**、2 GiB 的 `dd conv=fdatasync` 只持续 **0.82 秒**；`pidstat -d` 有时抓到、有时抓不到，因此不能用它证明「没有 IO」。

## 1. 内存：为什么「用了多少」不是判据

### 1.1 四个口径

| 口径 | 含义 | 用错会怎样 |
| --- | --- | --- |
| `MemFree` | 完全空闲的内存 | Linux 会把空闲内存拿去做页缓存，所以它通常很少，**不是**「可用内存」 |
| `MemAvailable` | 应用真正还能申请到的量（含可回收的缓存） | 这才是水位告警应该用的口径（阶段 4 有完整推导） |
| `RSS` / `PSS` / `USS` | 常驻内存 / 按共享比例分摊 / 进程独占 | 用 RSS 求和会重复计算共享库；容器内存计价看的是另一种口径 |
| **PSI** `some`/`full` | 「至少一个任务被卡住」/「所有任务都被卡住」的时间比例 | 只有在真正有压力时才动，**比水位更早、也更准** |

### 1.2 实测：分配 3 GiB 时 PSI 的平均值全程为 0

```bash
free -m | head -2; grep -H . /proc/pressure/memory   # 验证：分配前的基线
python3 -c 'import time
b=bytearray(3*1024*1024*1024)
for i in range(0,len(b),4096):
    b[i]=1
print("touched 3GiB")
time.sleep(15)' &                                    # 验证：分配并逐页触碰，保持存活
sleep 8
free -m | head -2; grep -H . /proc/pressure/memory
grep -E "^(VmRSS|VmHWM|VmSwap)" /proc/<pid>/status
grep -E "^(Rss|Pss|Anonymous|Private_Dirty)" /proc/<pid>/smaps_rollup
grep -E "^(pgscan_direct|pgsteal_direct)" /proc/vmstat
```

```text
分配前
               total        used        free      shared  buff/cache   available
Mem:            7894         669        2800           1        4740        7224
/proc/pressure/memory:some avg10=0.00 avg60=0.00 avg300=0.00 total=298
/proc/pressure/memory:full avg10=0.00 avg60=0.00 avg300=0.00 total=208

触碰 3 GiB 之后（进程存活期间）
               total        used        free      shared  buff/cache   available
Mem:            7894        3748         218           1        4235        4145
/proc/pressure/memory:some avg10=0.00 avg60=0.00 avg300=0.00 total=9695
/proc/pressure/memory:full avg10=0.00 avg60=0.00 avg300=0.00 total=9477
VmSize:	 3163716 kB
VmRSS:	 3156232 kB
VmHWM:	 3156232 kB
VmSwap:	       0 kB

Anonymous:       3149520 kB
Private_Dirty:   3149520 kB
pgsteal_direct 0
pgscan_direct 0

```

四条结论：

1. **`MemAvailable` 少了 3079 MiB，PSI 的三个平均值一动不动。** 「内存用掉了」和「内存在被等」是两件事。告警应该看 `MemAvailable` + PSI，而不是 `MemFree`。
2. **但 PSI 的累计计数器动了。** `some` 的 `total` 从 298 µs 涨到 9695 µs（**+9397 µs**）、`full` 从 208 µs 涨到 9477 µs（**+9269 µs**）。`avg10` 之所以还是 0.00，是因为这 9.4 ms 的压力被摊在 10 秒的分母上（< 0.1%）。**「avg 显示 0」不等于「一点压力都没有」——要做窗口内差分，或者直接把 `avg10` 与 `total` 一起读。**
3. **`pgscan_direct=0` 说明没有发生同步回收**，压力来自 `kswapd`（后台回收，`pgscan_kswapd=127429`）。direct reclaim 才会直接变成延迟尖刺；这一轮没有。
4. **没有 swap 使用不代表没有内存压力**——反过来也成立：`VmSwap=0`、`SwapFree` 满值，只说明这次 3 GiB 还在物理内存里；`si/so` 长期非 0 才是真的在换页。

> [!warning] 本机有 swap 但不要打满内存
> 旧环境没有 swap，所以「真回收」类实验只能讲机制。本机有 **4095 MiB 的 `/swap.img`**（`vm.swappiness=60`），意味着换页类实验可以做——但本章并行协作纪律明确要求**不打满内存**（会触发 OOM 影响其他章节）。上面的 3 GiB 触碰是有意控制在「占 3 GiB、留 4 GiB 余量」的范围内的；`MemAvailable` 最低只到 4145 MiB。

### 1.3 `direct reclaim` 与 THP：延迟尖刺的两个经典来源

- **direct reclaim（直接回收）**：内存接近水位时，分配内存的进程必须**同步**去回收页缓存，表现为「分配慢下来」——`%sy` 上升 + 延迟抖动。判据是 PSI memory 非 0、`/proc/vmstat` 的 `pgscan_direct*` 增长。本机基线 `pgscan_direct=0`；要制造它需要把水位压到临界，**本篇不做**（见上一条纪律）。
- **THP（透明大页）**：合并与拆分大页会造成偶发卡顿。本机当前策略是 `madvise`：

```bash
cat /sys/kernel/mm/transparent_hugepage/enabled   # 验证：always [madvise] never
```

正确做法是针对具体 workload 用 `madvise(MADV_HUGEPAGE)`，而不是全局改成 `always`。

### 1.4 运行时的堆与 GC：内存高不等于泄漏

Java / Python / Go 这类运行时有自己的堆与 GC：**RSS 高不等于泄漏；GC 的「停世界」会表现为周期性延迟尖刺**。三个判据：

1. RSS 长期**单调上升**（而不是锯齿形波动）；
2. GC 日志 / 指标与延迟尖刺在时间上对齐；
3. 堆上限设置与业务峰值是否匹配。

单看 `free`/`top` 是看不出这类问题的，要靠应用指标与追踪（阶段 9 讲的三条链路）。

## 2. IO：三个指标不是一回事

### 2.1 `iostat -x` 的读法

```bash
iostat -x 1 5   # 验证：看每块设备的 await / aqu-sz / %util 与请求规模
```

| 指标 | 含义 | 怎么用 |
| --- | --- | --- |
| `w_await` / `r_await` | 一次请求从提交到完成的平均时间（**含排队**） | 最接近「应用感知到的等待」 |
| `aqu-sz` | 平均在途请求数（队列深度） | 与 Little's law 对照：`aqu-sz ≈ 到达率 × await` |
| `%util` | 设备「至少有一个请求在途」的时间比例 | **可并行设备（SSD / 虚拟盘）上不能当饱和度用** |
| `wareq-sz` | 平均每次写请求的字节数 | 判断是「大块顺序」还是「4 KiB 随机」 |

本机同一块盘（`dm-0`，根分区所在的 LVM 逻辑卷）在不同窗口下的实测对比：

| 窗口 | `w/s` | `wkB/s` | `w_await` | `wareq-sz` | `aqu-sz` | `%util` |
| --- | --- | --- | --- | --- | --- | --- |
| `stress-ng --hdd 2` 并发写 | 324.00 | 1225152 | 6.59 ms | 3781.33 | **2.14** | **80.10%** |
| `stress-ng --hdd 2`（另一秒） | 419.00 | 1335848 | 6.23 ms | 3188.18 | **2.61** | **83.30%** |
| `fio` 4 KiB 随机写 `libaio` `iodepth=16` | 30308.00 | 121232 | 0.08 ms | 4.00 | **2.34** | **91.40%** |
| `fio` 4 KiB 随机写 `libaio` `iodepth=64` | 14721.00 | 58884 | 0.27 ms | 4.00 | **3.92** | 74.50% |
| 同上，压力爬升后的一秒 | 35457.00 | 141828 | 0.09 ms | 4.00 | **3.15** | **98.80%** |
| `dd` 2 GiB `conv=fdatasync` 回写突发 | 477.00 | 2097808 | 1.14 ms | 4397.92 | **0.54** | 42.50% |

六组数字互相印证：`324 × 0.00659 = 2.14`、`419 × 0.00623 = 2.61`、`477 × 0.00114 = 0.54` 三组**完全相等**；`fio` 三组因 `w_await` 只保留两位小数而有 0.04～0.08 的舍入偏差。

**关键判读有两层：**

- **`%util` 高不等于排队深。** `%util=98.80%` 的那一秒，`aqu-sz` 只有 3.15、`w_await` 只有 0.09 ms——设备确实几乎一直在忙，但每个请求都很快完成，队列里同时最多三四个请求。
- **`await` 大不等于盘慢。** `stress-ng` 窗口的 `w_await=6.59 ms` 配上 `wareq-sz=3781`（约 **3.7 MiB** 一块的大请求），`aqu-sz` 才 2.14；`fio` 的 `w_await=0.09 ms` 配上 `wareq-sz=4`（4 KiB 小块），`aqu-sz` 反而有 3.15。**`await` 必须和请求规模、到达率一起看。**

### 2.2 四象限基线：为什么必须带块大小与队列深度

```bash
fio --name=seqwrite    --filename=/tmp/lab/fio.bin --size=1G --rw=write    --bs=1M --ioengine=psync  --iodepth=1  --direct=1 --runtime=15 --time_based
fio --name=seqread     --filename=/tmp/lab/fio.bin --size=1G --rw=read     --bs=1M --ioengine=psync  --iodepth=1  --direct=1 --runtime=15 --time_based
fio --name=randwrite4k --filename=/tmp/lab/fio.bin --size=1G --rw=randwrite --bs=4k --ioengine=libaio --iodepth=32 --direct=1 --runtime=15 --time_based
fio --name=randread4k  --filename=/tmp/lab/fio.bin --size=1G --rw=randread  --bs=4k --ioengine=libaio --iodepth=32 --direct=1 --runtime=15 --time_based
```

本机实测（VMware 虚拟盘上的 ext4 on LVM，`direct=1`）：

| 象限 | 吞吐 | `clat` p50 | `clat` p99.9 |
| --- | --- | --- | --- |
| 顺序写 1 MiB，`psync`，`iodepth=1` | 1495 MiB/s | 635 µs | 1876 µs |
| 顺序读 1 MiB，`psync`，`iodepth=1` | 1708 MiB/s | 562 µs | 1434 µs |
| 随机写 4 KiB，`libaio`，`iodepth=32` | **27.3k IOPS（107 MiB/s）** | 1090 µs | 3228 µs |
| 随机读 4 KiB，`libaio`，`iodepth=32` | **47.5k IOPS（185 MiB/s）** | 619 µs | 1958 µs |

> [!warning] `--iodepth` 只有在 `libaio`（或 `io_uring`）下才生效
> 本机第一次跑这四象限时用的是 `fio` 默认的 `psync` 引擎，结果 4 KiB 随机写只有 **11.7k IOPS / 45.5 MiB/s**、随机读 **12.0k IOPS / 47.1 MiB/s**——因为 `psync` 是同步引擎，**它忽略 `--iodepth`**（`fio` 头部会打印 `ioengine=psync, iodepth=1`）。换成 `--ioengine=libaio --iodepth=32` 之后，随机写涨到 **27.3k IOPS**、随机读涨到 **47.5k IOPS**，`clat` p50 也从 ~76 µs 涨到 ~1.1 ms / 0.62 ms（队列变深，单请求等待变长，这是**预期**而不是退步）。**基线必须写清 `ioengine`——只写 `iodepth` 会得到一个骗人的数字。**

**为什么必须记块大小与队列深度**：顺序写 1495 MiB/s 靠的是 1 MiB 大块，单队列（`iodepth=1`）就能吃满带宽；随机写只有 4 KiB 小块，单队列太慢，必须靠 32 个请求同时在飞才拉到 107 MiB/s。**`iodepth` 是随机小块提升 IOPS 的手段，不是代价。** 用「同一个盘另一时段」对比前，先核对块大小、队列深度与引擎，否则两个数字根本不可比。

### 2.3 `fsync`：同步落盘的真实代价

日志类应用最常见的性能陷阱是「每写一行就 `fsync`」。

```bash
python3 -c 'import os,time
f=open("/tmp/lab/fs.bin","wb",buffering=0)
xs=[]
for i in range(200):
    t=time.perf_counter()
    f.write(b"x"*4096); os.fsync(f.fileno())
    xs.append((time.perf_counter()-t)*1000)
f.close(); xs.sort()
print("fsync n=%d p50=%.4fms p95=%.4fms p99=%.4fms max=%.4fms"%(len(xs),xs[100],xs[190],xs[198],xs[-1]))'
```

```text
fsync     n=200 p50=0.3614ms p95=0.4966ms p99=1.5105ms max=1.5820ms
buffered  n=200 p50=0.0019ms p95=0.0026ms p99=0.0286ms max=0.0337ms
```

**`p50` 约 190 倍，`p99` 是 53 倍**（1.5105 ms vs 0.0286 ms）。工程含义：日志用「缓冲 + 定期刷盘」或异步追加；只有确需持久化的关键点（事务提交、审计记录）才 `fsync`；日志盘与数据盘分开（阶段 5 讲了盘位规划）。

> [!warning] 倍数与盘有关，判据是「比值」而不是「毫秒数」
> 旧环境（WSL2 虚拟盘）的 `fsync` 是 `p50=5.084 ms`、缓冲写 `p50=0.0015 ms`（约 3400 倍）；本机是 `p50=0.3614 ms` vs `0.0019 ms`（约 190 倍）。**绝对毫秒数在虚拟化环境里完全不可外推**（本机 VMware 的写入路径明显比旧环境快），可信的是「同步落盘比缓冲写贵两个数量级」这个关系。做这类对照时一定要连同**盘的类型、是否 `direct`、块大小**一起记。

顺带一个 Page Cache 的对照实验（512 MiB 文件，写完后 `sync`，两种读法各三次）：

```bash
dd if=/tmp/lab/seq.bin of=/dev/null bs=1M iflag=direct   # 验证：绕过页缓存
dd if=/tmp/lab/seq.bin of=/dev/null bs=1M                # 验证：走页缓存
```

```text
iflag=direct 读：8.5 GB/s / 8.3 GB/s / 11.1 GB/s      （约 8104 / 7913 / 10583 MiB/s）
走页缓存读：     12.0 GB/s / 12.7 GB/s / 12.2 GB/s     （约 11444 / 12111 / 11634 MiB/s）
```

**读法提示：虚拟化环境里的 `direct` 并不等于「绕过所有缓存」。** 如果 guest 的 `direct` 真的每次都落到介质上，本机不可能读到 8～11 GB/s（比顺序读基线 1708 MiB/s 还高一个量级）——说明**宿主/虚拟盘层仍然在缓存，`direct` 只绕过了 guest 自己的 Page Cache**。这条结论本身很重要：**在虚拟化环境测 IO，绝对数字要打折扣，趋势与相对关系仍然可信。**

## 3. 从「某块盘」下钻到「某个进程的某个文件」

### 3.1 四步顺序

| 步骤 | 命令 | 回答什么 |
| --- | --- | --- |
| 1 设备层 | `iostat -x 1 3` | 哪块盘、读还是写、`await`/`aqu-sz` 多少 |
| 2 进程层 | `pidstat -d 1 3`、`iotop -o`（需 root） | 哪个进程在读写在等 |
| 3 文件层 | `lsof -p <pid>`、`ls -l /proc/<pid>/fd`、`cat /proc/<pid>/io` | 打开/写的是哪些文件，**真实**读写字节（`read_bytes`/`write_bytes` 不含缓存命中） |
| 4 调用栈 / 块层 | `strace -T -e trace=write,fsync`（限时）、`blktrace`/`blkparse`（需 root） | 慢在哪个调用、哪个扇区 |

```bash
pidstat -d 1 3                              # 验证：进程级读写速率与 iodelay
lsof -p <pid> | head                        # 验证：进程打开了哪些文件
cat /proc/<pid>/io                          # 验证：read_bytes/write_bytes 是真实落盘量
```

```text
08:38:15 AM     0     50621      0.00 524288.00      0.00       0  stress-ng-hdd
08:38:15 AM     0     50622      0.00 786432.00      0.00       0  stress-ng-hdd
08:38:18 AM     0       395      0.00    220.00      0.00       0  jbd2/dm-0-8
08:38:20 AM     0      1348      0.00 204980.00 204980.00       0  sshd
```

`iodelay` 为 0 而 `kB_wr/s` 是 524288～786432（约 0.5～0.75 GiB/s），说明**写是在缓冲里完成的**（阻塞不在这个层面）；如果 `iodelay` 明显非 0，说明进程真的被 IO 卡住了。同一段输出里还能看到 `jbd2/dm-0-8`（ext4 日志线程）与 `sshd` 的 `kB_ccwr/s` 等于 `kB_wr/s`（写入被取消，说明它只是短暂缓冲）。

### 3.2 「采样漏掉短脉冲」的实测

```text
$ dd if=/dev/zero of=pulse.bin bs=1M count=1000 oflag=direct &   # 约 0.2 秒完成
$ pidstat -d 1 2
Average:      UID       PID   kB_rd/s   kB_wr/s kB_ccwr/s iodelay  Command
Average:        0     46854      0.00 509452.74      0.00       0  bash
```

`dd` 的 1000 MiB 写**这一次被抓到了**（一个窗口里 `bash` 报 1013861.39 kB_wr/s）——但 `dd` 本身只持续 **0.196 秒**，落在哪个 1 秒窗口里完全是时序问题。**结论：看到「进程层没 IO」不等于「没有 IO」**，必须回到设备层（`iostat -x`）确认，或者用 `/proc/<pid>/io` 的累计值差分。要抓这类短脉冲，可以用更密的采样、更长的持续时间、或直接依赖设备层与累计值。

## 4. 生产动作：IO 问题定位记录（有产出物）

一份可交付的 IO 定位记录固定包含五段：

1. **现象与影响面**：谁的延迟/吞吐变差了、从几点开始（第 1 站的结论）。
2. **设备层证据**：`iostat -x` 的原始行，标注设备、方向、`await`/`aqu-sz`/`%util`/请求规模。
3. **进程层证据**：`pidstat -d` 或 `/proc/<pid>/io` 的差分，说明「谁的 IO」。
4. **文件与调用**：`lsof -p`、`/proc/<pid>/fd`，必要时限时的 `strace -T`。
5. **与基线的对比**：同一设备在正常时段的 `await`/`aqu-sz`（子笔记 12 的 fio 四象限 + 业务基线）。

> [!warning] 别把「同步写」当成「磁盘坏了」
> 本机实测 `fsync` 的 `p50` 是缓冲写的约 190 倍。业务侧「周期性地变慢几十毫秒」很可能就是每次请求一次同步落盘，而不是介质劣化。先做「同步 vs 缓冲」的对照实验，再考虑换盘。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 「`free` 少了就是内存不够」 | 看 `MemAvailable` + PSI。实测分配 3 GiB 后仍有 4145 MiB 可用、PSI 三个平均值全 0 |
| 「PSI 的 `avg10` 是 0，就完全没有内存压力」 | 本机 3 GiB 触碰期间 `some` 的 `total` 涨了 9397 µs、`full` 涨了 9269 µs——**平均值会被分母摊平，要看 `total` 的窗口差分** |
| 「swap 用了就是内存不足」 | 要看 `si/so` 是否长期非 0 与 PSI；本机全程 `VmSwap=0`、`SwapFree` 满值 |
| 「RSS 涨了就是泄漏」 | 运行时有缓存与 GC；要看长期趋势 + PSS + 应用指标 |
| 「`%util` 没到 100%，磁盘没瓶颈」 | 实测 `%util=80.10%` 时 `aqu-sz=2.14`、`w_await=6.59 ms`；而且反例也存在——`%util=98.80%` 时 `aqu-sz` 只有 3.15 |
| 「`%util` 到 99% 就是磁盘极限」 | `%util` 只表示「至少有一个请求在途」的时间比例；本机 `%util=98.80%` 时 `w_await` 只有 0.09 ms |
| 「`await` 大就是盘慢」 | `await` 含排队时间，且与请求规模强相关：本机 6.59 ms 对应 `wareq-sz=3781`，0.09 ms 对应 `wareq-sz=4` |
| 「用同一个盘的另一时段做对比就够了」 | 块大小、队列深度、`ioengine` 不同就不可比（本机 `psync` 11.7k IOPS vs `libaio` 27.3k IOPS，都是 `--iodepth=32`） |
| 「`--iodepth=32` 就是 32 个请求在飞」 | 只有在 `libaio`/`io_uring` 下才成立；`psync` 会忽略 `iodepth` |
| 「`pidstat -d` 没看到写，就不是它」 | 1 秒采样可能漏掉 0.2 秒的脉冲（本机 `dd` 只跑 0.196 秒），抓没抓到取决于时序 |
| 「`direct` 一定绕过所有缓存」 | 虚拟化环境下 guest 的 `direct` 只绕过 guest 的页缓存，宿主层仍有缓存；绝对数字要打折扣 |
| 「内存高就先 `drop_caches`」 | 丢掉的页缓存会让后续读取重新走盘，是典型的「用制造问题的方式掩盖问题」 |
| 「`swappiness` 调小就能减少换页」 | 先找谁在制造压力；在根因未明时调参只会改变现象的形状 |

## 决策练习

**场景**：凌晨 2 点，备份任务启动。监控显示「数据库实例的写入延迟从 2 ms 涨到 300 ms」，同时 `iostat -x` 显示数据盘 `%util=68%`、`w_await=350 ms`、`aqu-sz=310`、`w/s=900`。同事说：「`%util` 才 68%，盘没满，估计是数据库自己的问题。」

**选项**：

- **A. 同意同事，去查数据库的慢查询日志。**
- **B. 指出 `%util` 不是饱和度指标，先记录 `await`/`aqu-sz` 与备份进程的 IO，用 `ionice`/cgroup `io.max` 给备份限速并观察延迟是否回落。**
- **C. 立刻把备份任务杀掉，避免影响数据库。**

**为什么选 B**：`%util=68%` + `w_await=350 ms` + `aqu-sz=310` 的组合，按 Little's law 交叉校验：`900 × 0.350 = 315`，与 `aqu-sz=310` 吻合——**队列是真实存在的**，只是设备还能并行处理，所以 `%util` 没满。时间点（凌晨 2 点 = 备份窗口）与现象高度相关。限速是可回滚、代价低的止损动作，而且效果可以被验证：限速后 `await` 与数据库写入延迟应同步回落。

**为什么不选 A**：慢查询日志值得看，但「同事用 `%util` 排除 IO」这个推理是错的，如果接受它，你会先花时间在数据库内部，而真正的诱因（备份抢 IO）还在继续。

**为什么不选 C**：直接杀备份是不可逆的（备份失败要重跑、可能影响 RPO），而且丢掉了「备份与数据库争 IO」这条结论的证据。正确顺序是「限速 → 观察 → 再决定是否调整备份窗口」。

## 要点自测

> [!question]- 内存还有空余，进程却偶尔卡顿，怎么判断是不是内存压力？
> - 看 `/proc/pressure/memory` 的 `some`/`full`（这才是「被卡住的时间比例」），**同时读 `avg10` 和 `total`**，配合 `MemAvailable` 与 `si/so`。
> - 本机实测：分配 3 GiB 但 `avg10=0.00`、`pgscan_direct=0` → 只是用掉了内存，没有同步回收压力；但 `total` 涨了约 9.3 ms，说明不是「零压力」，只是被摊平了。
> - 还要排除 cgroup 层的内存上限（子笔记 11）与 direct reclaim / THP。
> - **第一反应不要是什么**：不要用 `drop_caches` 或调 `swappiness` 去「消除」现象。

> [!question]- `wa`、`%util`、`await` 分别代表什么？为什么可能互不对应？
> - `wa`：CPU 空闲且至少有一个 IO 未完成的采样比例（CPU 视角）。
> - `%util`：设备至少有一个请求在途的时间比例（忙不忙）。
> - `await`：单个请求的平均完成时间，含排队（应用感知视角）。
> - 实测对照：`%util=80.10%` 时 `aqu-sz=2.14`、`w_await=6.59 ms`；`%util=98.80%` 时 `aqu-sz=3.15`、`w_await=0.09 ms`。**利用率更高的那次反而队列更浅。** 判饱和度优先 `await` + `aqu-sz`。

> [!question]- 同一块盘的两组数字在什么条件下才可比？
> - 块大小、队列深度、`ioengine`、读/写方向、是否 `direct`、文件是否在缓存里、测试时长、`iodepth` 分布都要一致。
> - 本机四象限：顺序写 1495 MiB/s（`bs=1M, psync, iodepth=1`）、随机写 107 MiB/s（`bs=4k, libaio, iodepth=32`）——这两个数不是「同一个盘快慢」，而是两种不同工作负载。
> - 同一个 `--iodepth=32` 下换引擎：`psync` 11.7k IOPS、`libaio` 27.3k IOPS——**引擎不同就直接不可比**。
> - **第一反应不要是什么**：不要拿「峰值带宽」去解释「随机 4 KiB 慢」。

> [!question]- 怎么把「某块盘很慢」下钻到「某个进程的某个文件」？
> - `iostat -x` 定设备与方向 → `pidstat -d` / `iotop` 定进程 → `lsof -p` / `/proc/<pid>/io` 定文件 → `strace -T`（限时）或 `blktrace`（需 root）定调用与扇区。
> - 注意采样盲区：本机 1000 MiB 的 `dd` 只跑 0.196 秒，`pidstat -d 1` 抓到与否取决于时序，必须回设备层确认。
> - **第一反应不要是什么**：不要因为进程层采样没看到 IO 就排除 IO 问题。

> [!question]- 为什么 `fsync` 值得单独拎出来讲？
> - 同一块盘上 4 KiB 写：`fsync` 版 `p50=0.3614 ms`，纯缓冲写 `p50=0.0019 ms`，约 190 倍；`p99` 差 53 倍。
> - 很多「周期性变慢几十毫秒」的现场，根因是「每次请求一次同步落盘」，而不是介质劣化。
> - 处置方向：缓冲 + 定期刷盘、异步追加、日志盘与数据盘分离；只有确需持久化的关键点才 `fsync`。
> - **注意**：绝对毫秒数不可外推（旧环境 `fsync` p50 是 5.084 ms，本机是 0.3614 ms），可信的是两个数量级的比值。
