## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **内存要看压力，不看用量。**
>   - 证据：一个进程分配并逐页触碰 3 GiB 后，`MemAvailable` 从 15217 MiB 降到 12138 MiB，而 `/proc/pressure/memory` 的 `some`/`full` **全程为 0**；`VmRSS` 3082 MiB。
> - **判断 IO 排队优先看 `await` 与 `aqu-sz`，`%util` 只作参考。**
>   - 证据：深队列窗口实测 `w/s=2439`、`w_await=54.72 ms`、`aqu-sz=133.47`、`%util=75.20%`；而 `dd` 回写突发窗口 `%util` 只有 **14.40%**，`w_await` 却有 **6.85 ms**。
> - **`fsync` 是最容易被忽视的延迟来源。**
>   - 证据：同一块盘上 200 次 4 KiB 写，`fsync` 版本 `p50=5.084 ms`，纯缓冲写 `p50=0.0015 ms`，**约 3400 倍**。
> - **基线不能用「感觉」代替：同一块盘的四象限差异可以到两个数量级。**
>   - 证据：`fio` 实测顺序写 2903 MiB/s、顺序读 2830 MiB/s，4 KiB 随机写 17.4k IOPS / 67.8 MiB/s、随机读 12.5k IOPS / 48.8 MiB/s。
> - **下钻顺序是「设备 → 进程 → 文件 → 调用栈」，而且 1 秒采样会漏掉短脉冲。**
>   - 证据：本机写 1000 MiB 的 `dd` 只持续 1～2 秒，`pidstat -d 1` 采样窗口里一条记录都没有。

## 1. 内存：为什么「用了多少」不是判据

### 1.1 四个口径

| 口径 | 含义 | 用错会怎样 |
| --- | --- | --- |
| `MemFree` | 完全空闲的内存 | Linux 会把空闲内存拿去做页缓存，所以它通常很少，**不是**「可用内存」 |
| `MemAvailable` | 应用真正还能申请到的量（含可回收的缓存） | 这才是水位告警应该用的口径（阶段 4 有完整推导） |
| `RSS` / `PSS` / `USS` | 常驻内存 / 按共享比例分摊 / 进程独占 | 用 RSS 求和会重复计算共享库；容器内存计价看的是另一种口径 |
| **PSI** `some`/`full` | 「至少一个任务被卡住」/「所有任务都被卡住」的时间比例 | 只有在真正有压力时才动，**比水位更早、也更准** |

### 1.2 实测：分配 3 GiB 时 PSI 全程为 0

```bash
free -m | head -2; grep -H . /proc/pressure/memory   # 验证：分配前的基线
python3 -c 'import time
b=bytearray(3*1024*1024*1024)
for i in range(0,len(b),4096):
    b[i]=1
print("touched 3GiB")
time.sleep(15)' &                                    # 验证：分配并逐页触碰，保持存活
sleep 6
free -m | head -2; grep -H . /proc/pressure/memory
grep -E "^(VmRSS|VmHWM|VmSwap)" /proc/<pid>/status
grep -E "^(Rss|Pss|Anonymous|Private_Dirty)" /proc/<pid>/smaps_rollup
```

```text
分配前
               total        used        free      shared  buff/cache   available
Mem:           15844         626       14616           3         806       15217
/proc/pressure/memory:some avg10=0.00 avg60=0.00 avg300=0.00 total=0
/proc/pressure/memory:full avg10=0.00 avg60=0.00 avg300=0.00 total=0

触碰 3 GiB 之后（进程存活期间）
Mem:           15844        3705       11537           3         806       12138
/proc/pressure/memory:some avg10=0.00 avg60=0.00 avg300=0.00 total=0
/proc/pressure/memory:full avg10=0.00 avg60=0.00 avg300=0.00 total=0
VmSize:  3087 MiB
VmRSS:   3082 MiB
VmHWM:   3082 MiB
VmSwap:     0 MiB
Rss:             3082 MiB
Pss:             3078 MiB
Pss_Anon:        3076 MiB
Anonymous:       3076 MiB
Private_Dirty:   3076 MiB
```

（`/proc` 的原始输出以 kB 为单位，这里统一换算成 MiB 以便与 `free -m` 对照；换算前的原始值是 `VmRSS/VmHWM 3155712 kB`、`Rss 3155892 kB`、`Pss 3151788 kB`、`Anonymous/Private_Dirty 3149524 kB`。）

三条结论：

1. **`MemAvailable` 少了 3 GiB，PSI 一动不动。** 「内存用掉了」和「内存在被等」是两件事。告警应该看 `MemAvailable` + PSI，而不是 `MemFree`。
2. **RSS / PSS / Anonymous 在本机几乎相等**，因为这是纯私有匿名页。PSS 的价值在共享库多的场景（例如几十个进程共享同一个 `.so`），本机这个例子体现不出来。
3. **没有 swap 使用，不代表没有内存压力**——反过来也成立：`si/so` 非 0 才是真的在换页。

### 1.3 `direct reclaim` 与 THP：延迟尖刺的两个经典来源

- **direct reclaim（直接回收）**：内存接近水位时，分配内存的进程必须**同步**去回收页缓存，表现为「分配慢下来」——`%sy` 上升 + 延迟抖动。判据是 PSI memory 非 0、`/proc/vmstat` 的 `pgscan_direct*` 增长。
- **THP（透明大页）**：合并与拆分大页会造成偶发卡顿。本机当前策略是 `madvise`：

```bash
cat /sys/kernel/mm/transparent_hugepage/enabled   # 验证：always [madvise] never
```

正确做法是针对具体 workload 用 `madvise(MADV_HUGEPAGE)`，而不是全局改成 `always`。

### 1.4 运行时的堆与 GC：内存高不等于泄漏

Java / Python / Go 这类运行时有自己的堆与 GC：**RSS 高不等于泄漏；GC 的「停世界」会表现为周期性延迟尖刺**。三个判据：

1. RSS 长期**单调上升**（而不是锯齿形波动）；
2. GC 日志 / 指标与延迟尖刺在时间上对齐；
3. 堆上限设置与业务峰值是否匹配。

单看 `free`/`top` 是看不出这类问题的，要靠应用指标与追踪（阶段 9 讲的三条链路）。

## 2. IO：三个指标不是一回事

### 2.1 `iostat -x` 的读法

```bash
iostat -x 1 5   # 验证：看每块设备的 await / aqu-sz / %util 与请求规模
```

| 指标 | 含义 | 怎么用 |
| --- | --- | --- |
| `w_await` / `r_await` | 一次请求从提交到完成的平均时间（**含排队**） | 最接近「应用感知到的等待」 |
| `aqu-sz` | 平均在途请求数（队列深度） | 与 Little's law 对照：`aqu-sz ≈ 到达率 × await` |
| `%util` | 设备「至少有一个请求在途」的时间比例 | **可并行设备（SSD / 虚拟盘）上不能当饱和度用** |
| `wareq-sz` | 平均每次写请求的字节数 | 判断是「大块顺序」还是「4 KiB 随机」 |

本机同一块盘（`/dev/sdd`）在不同窗口下的实测对比：

| 窗口 | `w/s` | `wkB/s` | `w_await` | `wareq-sz` | `aqu-sz` | `%util` |
| --- | --- | --- | --- | --- | --- | --- |
| `dd` 2 GiB 脏页回写突发 | 555.00 | 635908 | 6.85 ms | 1145.78 | **3.81** | **14.40%** |
| 4 KiB 随机写 + discard 混流 | 1160.00 | 1353668 | 343.08 ms | 1166.96 | **398.02** | 74.40% |
| 4 KiB 随机写 `iodepth=64` | 2439.00 | 2712912 | 54.72 ms | 1112.31 | **133.47** | 75.20% |
| 4 KiB 随机写（低速窗口） | 635.00 | 743680 | 404.00 ms | 1171.15 | **256.54** | 77.60% |

四个数字互相印证：`555 × 0.00685 = 3.80`、`1160 × 0.34308 = 397.97`、`2439 × 0.05472 = 133.46`、`635 × 0.404 = 256.54`，全部与实测 `aqu-sz` 吻合（第一组差 0.01 是四舍五入）。

**关键判读**：第一行 `%util` 只有 14.40%，但 `w_await` 已有 6.85 ms；后面三行 `%util` 都在 74～78%，`aqu-sz` 却相差三倍（133 → 398）。**`%util` 想回答的问题是「设备忙不忙」，它不回答「排了多长」。**

### 2.2 四象限基线：为什么必须带块大小与队列深度

```bash
fio --name=seqwrite    --filename=/tmp/lab/fio.bin --size=1G --rw=write    --bs=1M --iodepth=1  --direct=1 --runtime=15 --time_based
fio --name=seqread     --filename=/tmp/lab/fio.bin --size=1G --rw=read     --bs=1M --iodepth=1  --direct=1 --runtime=15 --time_based
fio --name=randwrite4k --filename=/tmp/lab/fio.bin --size=1G --rw=randwrite --bs=4k --iodepth=32 --direct=1 --runtime=15 --time_based
fio --name=randread4k  --filename=/tmp/lab/fio.bin --size=1G --rw=randread  --bs=4k --iodepth=32 --direct=1 --runtime=15 --time_based
```

本机实测（WSL2 虚拟盘，`direct=1`）：

| 象限 | 吞吐 | `clat` p50 | `clat` p99.9 |
| --- | --- | --- | --- |
| 顺序写 1 MiB，`iodepth=1` | 2903 MiB/s | 269 µs | 3818 µs |
| 顺序读 1 MiB，`iodepth=1` | 2830 MiB/s | 334 µs | 955 µs |
| 随机写 4 KiB，`iodepth=32` | 17.4k IOPS（67.8 MiB/s） | 51 µs | 241 µs |
| 随机读 4 KiB，`iodepth=32` | 12.5k IOPS（48.8 MiB/s） | 74 µs | 314 µs |

**为什么必须记块大小与队列深度**：顺序写 2903 MiB/s 靠的是 1 MiB 大块，单队列（`iodepth=1`）就能吃满带宽；随机写只有 4 KiB 小块，单队列太慢，必须靠 32 个请求同时在飞才拉到 67.8 MiB/s。**`iodepth` 是随机小块提升 IOPS 的手段，不是代价。** 用「同一个盘另一时段」对比前，先核对块大小与队列深度，否则两个数字根本不可比。

### 2.3 `fsync`：同步落盘的真实代价

日志类应用最常见的性能陷阱是「每写一行就 `fsync`」。

```bash
python3 -c 'import os,time
f=open("/tmp/lab/fs.bin","wb",buffering=0)
xs=[]
for i in range(200):
    t=time.perf_counter()
    f.write(b"x"*4096); os.fsync(f.fileno())
    xs.append((time.perf_counter()-t)*1000)
f.close(); xs.sort()
print("fsync n=%d p50=%.3fms p95=%.3fms p99=%.3fms max=%.3fms"%(len(xs),xs[100],xs[190],xs[198],xs[-1]))'
```

```text
fsync     n=200 p50=5.084ms p95=6.197ms p99=6.425ms max=8.005ms
buffered  n=200 p50=0.0015ms p99=0.0110ms max=0.0120ms
```

**约 3400 倍**。工程含义：日志用「缓冲 + 定期刷盘」或异步追加；只有确需持久化的关键点（事务提交、审计记录）才 `fsync`；日志盘与数据盘分开（阶段 5 讲了盘位规划）。

顺带一个 Page Cache 的对照实验（512 MiB 文件，`dd` 三次）：

```text
$ dd if=seq.bin of=/dev/null bs=1M iflag=direct   # dd 报数：2.4 / 9.1 / 8.4 GB/s
$ dd if=seq.bin of=/dev/null bs=1M                # dd 报数：14.2 / 10.6 / 14.0 GB/s
```

（`dd` 按 10³ 报数，1 GB/s ≈ 954 MiB/s；换算成 MiB/s 后，`direct` 读约 2289 / 8679 / 8011 MiB/s，走 Page Cache 约 13542 / 10109 / 13351 MiB/s。本篇其余吞吐统一用 MiB/s。）

`iflag=direct` 的三次结果波动很大（2289 → 8679 MiB/s），说明**在虚拟化环境里 `direct` 并不等于「绕过所有缓存」**——宿主机/虚拟盘层还有一层缓存。这条结论本身很重要：**在虚拟化环境测 IO，绝对数字要打折扣，趋势与相对关系仍然可信。**

## 3. 从「某块盘」下钻到「某个进程的某个文件」

### 3.1 四步顺序

| 步骤 | 命令 | 回答什么 |
| --- | --- | --- |
| 1 设备层 | `iostat -x 1 3` | 哪块盘、读还是写、`await`/`aqu-sz` 多少 |
| 2 进程层 | `pidstat -d 1 3`、`iotop -o`（需 root） | 哪个进程在读写在等 |
| 3 文件层 | `lsof -p <pid>`、`ls -l /proc/<pid>/fd`、`cat /proc/<pid>/io` | 打开/写的是哪些文件，**真实**读写字节（`read_bytes`/`write_bytes` 不含缓存命中） |
| 4 调用栈 / 块层 | `strace -T -e trace=write,fsync`（限时）、`blktrace`/`biosnoop`（需 root） | 慢在哪个调用、哪个块 |

```bash
pidstat -d 1 3                              # 验证：进程级读写速率与 iodelay
lsof -p <pid> | head                        # 验证：进程打开了哪些文件
cat /proc/<pid>/io                          # 验证：read_bytes/write_bytes 是真实落盘量
```

```text
Average:     1000      2520      0.00 1471836.00      0.00       0  stress-ng-hdd
```

`iodelay` 为 0 而 `kB_wr/s` 是 1471836，说明**写是在缓冲里完成的**（阻塞不在这个层面）；如果 `iodelay` 明显非 0，说明进程真的被 IO 卡住了。

### 3.2 「采样漏掉短脉冲」的实测

```text
$ dd if=/dev/zero of=io2.bin bs=1M count=1000 oflag=direct &   # 约 1～2 秒完成
$ pidstat -d 1 2
Average:     1000      2517      0.00      1.33      0.00       0  iostat      # 只抓到采样工具自己
```

`dd` 的 1000 MiB 写完全没有出现在进程层采样里。**这说明：看到「进程层没 IO」不等于「没有 IO」**，必须回到设备层（`iostat -x`）确认。要抓这类短脉冲，可以用更密的采样、更长的持续时间、或直接依赖设备层与 `/proc/<pid>/io` 的累计值差分。

## 4. 生产动作：IO 问题定位记录（有产出物）

一份可交付的 IO 定位记录固定包含五段：

1. **现象与影响面**：谁的延迟/吞吐变差了、从几点开始（第 1 站的结论）。
2. **设备层证据**：`iostat -x` 的原始行，标注设备、方向、`await`/`aqu-sz`/`%util`/请求规模。
3. **进程层证据**：`pidstat -d` 或 `/proc/<pid>/io` 的差分，说明「谁的 IO」。
4. **文件与调用**：`lsof -p`、`/proc/<pid>/fd`、必要时限时的 `strace -T`。
5. **与基线的对比**：同一设备在正常时段的 `await`/`aqu-sz`（子笔记 12 的 fio 四象限 + 业务基线）。

> [!warning] 别把「同步写」当成「磁盘坏了」
> 本机实测 `fsync` 的 `p50` 是缓冲写的约 3400 倍。业务侧「周期性地变慢几十毫秒」很可能就是每次请求一次同步落盘，而不是介质劣化。先做「同步 vs 缓冲」的对照实验，再考虑换盘。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 「`free` 少了就是内存不够」 | 看 `MemAvailable` + PSI。实测分配 3 GiB 后仍有 12138 MiB 可用、PSI 全 0 |
| 「swap 用了就是内存不足」 | 要看 `si/so` 是否长期非 0 与 PSI；只被换出过几次的页面不构成问题 |
| 「RSS 涨了就是泄漏」 | 运行时有缓存与 GC；要看长期趋势 + PSS + 应用指标 |
| 「`%util` 没到 100%，磁盘没瓶颈」 | 实测 `%util` 75.20% 时 `aqu-sz` 已 133.47；`%util` 14.40% 时 `w_await` 已有 6.85 ms |
| 「`await` 大就是盘慢」 | `await` 含排队时间；要与 `aqu-sz` 和请求规模一起看 |
| 「用同一个盘的另一时段做对比就够了」 | 块大小与队列深度不同就不可比（2903 MiB/s 是 `iodepth=1` 顺序写，67.8 MiB/s 是 `iodepth=32` 随机写） |
| 「`pidstat -d` 没看到写，就不是它」 | 1 秒采样会漏掉 1～2 秒的脉冲（本机实测漏掉整个 `dd`） |
| 「`direct` 一定绕过所有缓存」 | 虚拟化环境下实测波动很大（2289 → 8679 MiB/s），宿主层仍有缓存 |
| 「内存高就先 `drop_caches`」 | 丢掉的页缓存会让后续读取重新走盘，是典型的「用制造问题的方式掩盖问题」 |
| 「`swappiness` 调小就能减少换页」 | 先找谁在制造压力；在根因未明时调参只会改变现象的形状 |

## 决策练习

**场景**：凌晨 2 点，备份任务启动。监控显示「数据库实例的写入延迟从 2 ms 涨到 300 ms」，同时 `iostat -x` 显示数据盘 `%util=68%`、`w_await=350 ms`、`aqu-sz=310`、`w/s=900`。同事说：「`%util` 才 68%，盘没满，估计是数据库自己的问题。」

**选项**：

- **A. 同意同事，去查数据库的慢查询日志。**
- **B. 指出 `%util` 不是饱和度指标，先记录 `await`/`aqu-sz` 与备份进程的 IO，用 `ionice`/cgroup `io.max` 给备份限速并观察延迟是否回落。**
- **C. 立刻把备份任务杀掉，避免影响数据库。**

**为什么选 B**：`%util=68%` + `w_await=350 ms` + `aqu-sz=310` 的组合，按 Little's law 交叉校验：`900 × 0.350 = 315`，与 `aqu-sz=310` 吻合——**队列是真实存在的**，只是设备还能并行处理，所以 `%util` 没满。时间点（凌晨 2 点 = 备份窗口）与现象高度相关。限速是可回滚、代价低的止损动作，而且效果可以被验证：限速后 `await` 与数据库写入延迟应同步回落。

**为什么不选 A**：慢查询日志值得看，但「同事用 `%util` 排除 IO」这个推理是错的，如果接受它，你会先花时间在数据库内部，而真正的诱因（备份抢 IO）还在继续。

**为什么不选 C**：直接杀备份是不可逆的（备份失败要重跑、可能影响 RPO），而且丢掉了「备份与数据库争 IO」这条结论的证据。正确顺序是「限速 → 观察 → 再决定是否调整备份窗口」。

## 要点自测

> [!question]- 内存还有空余，进程却偶尔卡顿，怎么判断是不是内存压力？
> - 看 `/proc/pressure/memory` 的 `some`/`full`（这才是「被卡住的时间比例」），配合 `MemAvailable` 与 `si/so`。
> - 分配 3 GiB 但 PSI 全 0 → 只是用掉了内存，没有压力；反过来 PSI 长期非 0，即使 `free` 看着有余量也已经在伤延迟。
> - 还要排除 cgroup 层的内存上限（子笔记 11）与 direct reclaim / THP。
> - **第一反应不要是什么**：不要用 `drop_caches` 或调 `swappiness` 去「消除」现象。

> [!question]- `wa`、`%util`、`await` 分别代表什么？为什么可能互不对应？
> - `wa`：CPU 空闲且至少有一个 IO 未完成的采样比例（CPU 视角）。
> - `%util`：设备至少有一个请求在途的时间比例（忙不忙）。
> - `await`：单个请求的平均完成时间，含排队（应用感知视角）。
> - 实测反例：`%util=14.40%` 但 `w_await=6.85 ms`；`%util=75.20%` 时 `aqu-sz` 133.47、另一窗口 74.40% 时 398.02。判饱和度优先 `await` + `aqu-sz`。

> [!question]- 同一块盘的两组数字在什么条件下才可比？
> - 块大小、队列深度、读/写方向、是否 `direct`、文件是否在缓存里、测试时长、`iodepth` 分布都要一致。
> - 本机四象限：顺序写 2903 MiB/s（`bs=1M, iodepth=1`）、随机写 67.8 MiB/s（`bs=4k, iodepth=32`）——这两个数不是「同一个盘快慢」，而是两种不同工作负载。
> - **第一反应不要是什么**：不要拿「峰值带宽」去解释「随机 4 KiB 慢」。

> [!question]- 怎么把「某块盘很慢」下钻到「某个进程的某个文件」？
> - `iostat -x` 定设备与方向 → `pidstat -d` / `iotop` 定进程 → `lsof -p` / `/proc/<pid>/io` 定文件 → `strace -T`（限时）或 `blktrace`（需 root）定调用与块。
> - 注意采样盲区：本机写 1000 MiB 的 `dd` 完全没被 `pidstat -d 1` 抓到，必须回设备层确认。
> - **第一反应不要是什么**：不要因为进程层采样没看到 IO 就排除 IO 问题。

> [!question]- 为什么 `fsync` 值得单独拎出来讲？
> - 同一块盘上 4 KiB 写：`fsync` 版 `p50=5.084 ms`，纯缓冲写 `p50=0.0015 ms`，约 3400 倍。
> - 很多「周期性变慢几十毫秒」的现场，根因是「每次请求一次同步落盘」，而不是介质劣化。
> - 处置方向：缓冲 + 定期刷盘、异步追加、日志盘与数据盘分离；只有确需持久化的关键点才 `fsync`。
