# 一次性能故障的处置

一次性能故障的处置可以拆成五个阶段，从接到"变慢了"到说出"是哪一层、哪个进程、为什么"，中间不换话题：**认领与量化、分层排除（算力、存储、传输与等待）、下钻到进程与栈**。每一个阶段的结论既是下一个阶段的输入，也是它的准入门槛；贯穿各阶段的几个核对对象在最后单独收拢。

每一个阶段的准入门槛是上一个阶段的结论。**没有量化就没有比较对象，没有分层结论就没有下钻对象**——所以顺序错了，工具再全也只是在翻截图。

## 一、认领与量化：把「慢」变成有答案的问题

### 1.1 五个必答问题

接到报障的第一个动作不是敲命令，是问问题。这五个问题答不出来，后面所有数据都无法判断：

| # | 问题 | 要具体到什么程度 |
| --- | --- | --- |
| 1 | 谁受影响 | 要问到哪些接口或功能、哪些用户或租户、哪些实例，以及是全部还是只有一部分 |
| 2 | 多严重 | 要给出与基线相比慢了多少（倍数或差值）、错误率变化了多少、有没有超时以及超时率是多少 |
| 3 | 从几点开始 | 要问到具体时刻，并判断它是突变还是渐变 |
| 4 | 还在不在恶化 | 要判断当前是平台期、继续上升，还是已经回落 |
| 5 | 和什么比 | 要说清是与昨天同期比、与变更前比，还是与 SLO 比；**因为没有比较对象就证明不了"异常"** |

### 1.2 量化：三个口径一起说

只说"变慢了"无法验收，也无法判断动作有没有用。因此固定给出三个口径：

- **业务口径**：p99、p95、p50、max、错误率、超时率与吞吐；由于分位数受窗口与算法影响，引用时要把这两项一起说明；
- **资源口径**：最热核利用率、`MemAvailable`、`await`、`aqu-sz` 与 `ss -s` 的状态分布；
- **对比口径**：与基线或同期比，同时给出倍数和绝对差。

一句话结论的模板：

```text
# 模板，数值仅示意
<服务> 的 <指标> 从 <基线> 涨到 <当前>（约 N 倍），影响 <范围>，
自 <时刻> 开始，当前 <趋势>，<已采取/未采取> 动作。
```

### 1.3 对齐时间线：把拐点和变更放在一条线上

性能故障的现场往往**只出现一次**，所以时间线要一次对齐三样东西：

1. **指标拐点**：什么时候开始变，这要用历史数据判断，不要只看现在；
2. **变更事件**：发布、配置、扩缩容、批量任务、证书与上游变更；
3. **外部事件**：流量突增、活动与上游故障。

对齐之前先确认时钟。由于时间没同步时"变更在前还是故障在前"这个判断不成立，所以先读对时状态：

```text
# 验证：本机对时状态（本机实测 System clock synchronized: no，而 NTP service: active）
timedatectl
timedatectl timesync-status
```

注意 `NTP service: active` 不等于"时钟已同步"，因为同步状态写在另一行。时间基线的完整判据见阶段 9 的《原理：证据的时间与格式基线》。

### 1.4 三种形态决定采样密度

这一步在动手之前完成，因为采错了窗口就什么都看不见：

| 形态 | 采样要求 |
| --- | --- |
| 恒定慢 | 这种形态任取一段窗口都能看到，所以没有额外的窗口要求 |
| 间歇尖刺 | 这类形态要用高频采样或累积量的差分，因为 1 分钟聚合的平均值会把脉冲摊平 |
| 周期慢（按小时/按天） | 这类形态必须看历史数据，并覆盖 2～3 个周期才能判断规律 |

**累积量是间歇形态唯一的退路**。因为 `/proc/vmstat`、`nstat`、PSI 的 `total`、cgroup 的 `cpu.stat` 与 `memory.events` 都是只增不减的计数，所以两个时刻的差值不受采样窗口限制。这是唯一能"事后"看见短脉冲的办法。

## 二、算力：CPU 与负载

### 2.1 本阶段要回答的问题

**瓶颈是不是在 CPU？是整机忙，还是只有某一颗核已经满载？CPU 的时间花在哪一类？**

### 2.2 字段读法

| 字段 | 是什么 / 单位 | 判据 | 与谁同看 | 看到它转向哪一步 |
| --- | --- | --- | --- | --- |
| `mpstat -P ALL` 的 `all` 行 | 整机平均利用率，百分比 | **它不能单独用作判据**，因为它把四颗核的忙闲平均掉了 | 逐核行 | 若整机低而某一核到 100%，则转向单核争抢方向 |
| 逐核的 `%usr` | 该核用户态占比，百分比 | 若它贴到 100%，则该核已经没有余量 | `%sys`、`%soft`、`%iowait` | 若有核贴满，则用 `pidstat -u -t` 落到线程 |
| `%sys` | 内核态占比，百分比 | 若它占 CPU 时间的比例很高（经验线为 20%～30%），则说明系统调用或内核路径重 | `strace -c`、`/proc/<pid>/io` | 若确认内核路径重，则转入下钻阶段做系统调用画像 |
| `%soft` | 软中断占比，百分比 | 若单核 `%soft` 高且集中在少数核，则说明中断处理集中 | `/proc/interrupts`、`/proc/net/softnet_stat` | 若集中在少数核，则转入传输与等待阶段查收包侧 |
| `%iowait` | CPU 空闲但**有未完成的 IO** 的时间占比，百分比 | **文档明写它不可靠**（逐核难算、可能下降），因此它不能当作设备饱和的证据 | `await`、`aqu-sz`、`/proc/pressure/io` | 若 `await` 与 `aqu-sz` 同时抬头，则转入存储阶段 |
| `%steal` | 被虚拟化层拿走的占比，百分比 | 若它非 0，则说明宿主在超卖 CPU | 宿主侧指标 | 这一项只有宿主侧能进一步查 |
| `vmstat` 的 `r` | 运行队列长度（可运行任务数），个 | 若它持续大于核数，则说明已经有任务在排队 | `load`、逐核利用率 | 若确认有排队，则去找谁在跑 |
| `vmstat` 的 `b` | 处于不可中断睡眠的任务数，个 | 若它持续大于 0，则说明有任务卡在 IO 或内核路径上 | `ps` 的 `D` 状态、`wchan` | 若确认有 `D` 状态任务，则转入传输与等待阶段 |
| `load average` | 可运行与不可中断任务的平均数，个 | 它要除以核数才有意义，而且**它不是使用率** | `r`、`b`、逐核利用率 | 它只用来提示"有排队"，不能单独下结论 |
| `cs` | 每秒上下文切换次数，次/秒 | 若它极高而 CPU 不忙，则多半是任务在等锁或等 IO | `pidstat -w` 的自愿与非自愿切换 | 若指向等锁，则转入下钻阶段查 `futex` |

**本阶段最容易读错的两处**：

- **`vmstat` 的 `si` 是 swap in（每秒换入页数），不是软中断**。软中断在 `top` 里叫 `si`，在 `vmstat` 里没有单独列，被算进 `sy`。同一个缩写两个含义，是本库高发错误清单里点名的一条；
- **`%iowait` 高不能证明磁盘是瓶颈**。它只说明"CPU 闲着的这段时间里有 IO 没完成"，而原因可能是设备慢，也可能是应用发起的 IO 稀疏但每次都等；判据在设备层的 `await` 与 `aqu-sz`。

### 2.3 五个分支与下一步

| 分支 | 判据 | 第一落点 |
| --- | --- | --- |
| `us` 高 | 若 `%usr` 高而 `%sys` 低，则时间花在用户态计算上 | 用 `perf record` 找热点函数 |
| `sy` 高 | 若 `%sys` 占 CPU 时间的比例高，则时间花在内核路径上 | 用 `strace -c` 看是哪个系统调用 |
| `%soft` 高 | 若软中断时间集中在少数核，则中断处理没有分散开 | 读 `/proc/interrupts` 与 `/proc/net/softnet_stat` |
| `%iowait` 高 | 若空闲时间里有 IO 未完成，则方向可能不在 CPU | 转入存储阶段核对 `await` 与 `aqu-sz` |
| `%steal` 高 | 若该值非 0，则时间被虚拟化层拿走 | 这一项只有宿主侧能查 |

分支判断的依据是一个比值，不是绝对值：`%sys / (%usr + %sys)`。本机实测两个极端——纯计算任务是 `5.994 s user / 0.007 s sys`（`sys` 占 **0.12%**），2 万次 `getpid` 加 `stat` 的任务是 `0.0387 s user / 0.0122 s sys`（`sys` 占 **24.0%**）。由于两者的比值相差两个数量级，前者应当去 `perf`，后者应当去 `strace`。

### 2.4 本阶段的结论长什么样

整机 `%usr` 25.04%、`load` 0.34，但 CPU 2 是 100.00% `us`；`pidstat -u -t` 显示 PID 45062 的线程 45062 独占 100%，`taskset -cp` 亲和性为 2。因此结论是**单核争抢型**，CPU 层"像"；下一步是找出该核上还有谁。

## 三、存储：内存与 IO

### 3.1 本阶段要回答的问题

**瓶颈是不是内存压力？是不是 IO 排队？如果是，那么问题是出在设备上，还是出在应用的写模式上？**

### 3.2 字段读法

| 字段 | 是什么 / 单位 | 判据 | 与谁同看 | 看到它转向哪一步 |
| --- | --- | --- | --- | --- |
| `MemAvailable` | 应用还能申请到的内存，kB/MiB | 它跌破基线余量不等于有事，因此**必须与压力指标同看** | PSI memory、`pgmajfault` | 若有压力则定位工作集；若无压力则转入 IO 方向 |
| `/proc/pressure/memory` 的 `avg10/60/300` | 被内存拖慢的时间占比，**单位是百分比** | 若它持续非 0，则说明有内存压力 | `total` 差值 | 若它抬头，则去查回收与换页 |
| 同上的 `total` | 累计被拖慢的时间，**单位是微秒** | 取两个时刻的差值；由于 `avg` 会被窗口摊平，这是看见短脉冲的唯一途径 | `avg*` | 若差值大而 `avg` 为 0，则说明是偶发停顿 |
| `pgscan_direct`/`pgsteal_direct` | 同步回收扫描与回收的页数，页 | 若它在增长，则说明分配者自己在做回收，这是延迟尖刺的来源 | PSI、`allocstall` | 若增长则扩内存或缩小工作集 |
| `si`/`so` | 每秒换入与换出的页数，页/秒 | 若它长期非 0，则说明工作集被挤出了物理内存 | `pgmajfault`、PSI | 若非 0 则定位工作集与占用大户 |
| `iostat` 的 `r_await`/`w_await` | 一次请求从提交到完成的平均时间，毫秒 | 它要与**基线**比，没有通用阈值 | `aqu-sz`、`wareq-sz` | 若显著高于基线，则定位是谁在发请求 |
| `aqu-sz` | 发往该设备的请求的平均队列长度（旧名 `avgqu-sz`），个 | 若队列长而吞吐不再增长，则设备已经饱和 | `await`、`w/s` | 若饱和则限流或分流 |
| `%util` | 经过时间里"有 I/O 请求被发出到该设备"的时间占比，百分比 | **它不是饱和度**；`iostat(1)` 明说只有串行服务请求的设备才接近 100% 即饱和 | `await`、`aqu-sz` | 它不能单独作为结论 |
| `wareq-sz` | 每次写请求的平均大小，KiB | 它与 `await` 一起决定"为什么慢" | `w/s` | 若请求块大而 `await` 高，则问题在应用写模式 |

### 3.3 用法要点

- **内存看压力不看用量**：本机实测占用 3 GiB 后 `MemAvailable` 少了 3079 MiB，而 PSI 三个 `avg` 全为 0（`total` 差值 9397 µs、`pgscan_direct=0`）。因此"用得多、没有压力"是完全正常的组合。两个口径要一起记：`avg*` 是百分比、`total` 是微秒；另外 `/proc/pressure/cpu` 的 `full` 行系统级无定义，自 5.13 起固定为 0，所以不要拿它下结论；
- **IO 看排队不看忙闲**：本机六组窗口里，`%util` 98.80% 时 `aqu-sz` 3.15、`w_await` 0.09 ms；而 `%util` 80.10% 时 `aqu-sz` 2.14、`w_await` 6.59 ms。这两组数用 Little's law 可以交叉校验：`w/s × w_await ≈ aqu-sz`；
- **先分类再下钻**：内存方向分四类（有压力且同步回收、有压力但只是缓存换出、无压力但 majflt 高、无压力），IO 方向分三类（设备饱和、队列未满但单请求慢、应用写模式问题）。由于分类不同则修法完全不同，所以这一步不能跳。

### 3.4 本阶段的结论长什么样

应用 p99 从 120 ms 涨到 900 ms；`MemAvailable` 4145 MiB、PSI memory 全 0、`pgscan_direct=0`；数据盘 `w_await` 6.59 ms（基线 0.3 ms）、`aqu-sz` 2.14、`%util` 80.10%、`wareq-sz` 3781。因此结论是**内存"不像"，IO"像"，且是大块写请求**；下一步用 `pidstat -d` 定位到进程与文件。

## 四、传输与等待：网络与阻塞

### 4.1 本阶段要回答的问题

**瓶颈是不是在网络？还是进程其实"在等"而不是"在算"？**

### 4.2 顺序：先计数，后抓包

本阶段的顺序是固定的，因为跳步会浪费大量时间：

**先看连接状态分布，再看协议栈计数器，然后看收包侧丢弃，接着看单连接状态，最后才考虑抓包。**

| 字段 | 是什么 / 单位 | 判据 | 与谁同看 | 看到它转向哪一步 |
| --- | --- | --- | --- | --- |
| `ss -s` 的 `estab`/`timewait`/`closed` | 各状态连接数，个 | `TIME_WAIT` 的判据是"端口数 ÷ 60 秒"的上限，而不是绝对条数 | `ip_local_port_range` | 若堆积则进入端口与连接治理 |
| `ss -lnt` 的 `Recv-Q` | **已完成握手、等待 `accept` 的连接数**，个 | 若它持续接近 `Send-Q`（队列上限），则应用 accept 不及时 | `TcpExtListenOverflows` | 若溢出则改应用 accept 或调队列长度 |
| `nstat` 的 `TcpRetransSegs`/`TcpOutSegs` | 重传段数与发送段数，个 | 若比率长期大于 0.1%～1%，则要查链路 | 同窗口的两个计数 | 若比率高则查链路与丢包 |
| `nstat` 的 `TcpExtListenOverflows` | 监听队列溢出次数，次 | 若它在增长，则说明请求到了但没人接 | `ss -lnt` 的 `Recv-Q` | 若增长则转入应用侧排查 |
| `softnet_stat` 的 dropped | 收包侧丢弃的包数，个 | 若它非 0，则说明软中断来不及处理 | `%soft`、`/proc/interrupts` | 若非 0 则查中断与队列分散 |
| `ss -ti` 的 `rtt`/`minrtt` | 当前与历史最小的往返时间，毫秒 | 若 `rtt` 远大于 `minrtt`，则路径上有排队；两者都高则是链路固有延迟 | `cwnd`、`snd_wnd` | 若有排队则查路径与拥塞 |
| `ss -ti` 的 `app_limited` | 投递速率被**应用层**限制（`tcpi_delivery_rate_app_limited`） | 它出现即说明瓶颈不在网络；而且**它只在标志非 0 时打印** | `send`、`delivery_rate` | 若出现则转入应用侧排查 |
| `wchan` / `/proc/<pid>/stack` | 阻塞点的内核函数 | 只有读它才知道进程"在等谁" | `ps` 的 `D` 状态、`vmstat` 的 `b` 列 | 若指向存储或锁，则转回相应阶段 |

**三个必须记住的口径**：

- **`nstat` 默认输出的是两次读数之间的差值**，而 `-a` 才是累计值。把累计值当速率是最常见的误判之一；
- **计数器必须算比率**。本机某窗口 `TcpRetransSegs 14` 与 `TcpOutSegs 654775` 之比约为 0.002%，属于正常；由于只报 14 会得出相反结论，所以要连总量一起报；
- **`Recv-Q`/`Send-Q` 在两种 socket 上含义不同**：监听套接字与已连接套接字不是一回事。

### 4.3 「在等」这一类

进程侧的等待用三样证据定性：`wchan` 说明此刻等什么、`/proc/<pid>/stack` 给出完整内核路径（需要 root）、自愿与非自愿切换计数说明它是在等还是被抢。有三条边界要注意：

- **CPU 采样的结果里没有"等"的时间**。因此 `perf record` 看到的热点可能正是一个阻塞函数；
- **`D` 状态下 `kill -9` 不会立刻生效**，因为信号要等它回到可中断状态。正确的顺序是先取证，再恢复它等待的资源；
- **off-CPU 的量化需要 root**（`perf sched`、off-CPU eBPF）。没有 root 时退到 `wchan`、自愿切换差分与应用埋点。

### 4.4 本阶段的结论长什么样

`ss -s` 状态分布正常、重传率 0.002%、`softnet_stat` dropped 为 0；但 `vmstat` 的 `b` 持续为 2～3，`ps` 显示两个进程处于 `D`，`wchan` 指向 `blk_*`。因此结论是**问题不在网络，而在存储路径的等待**；下一步转回存储阶段做进程级定位。

## 五、下钻：进程、线程与调用

### 5.1 本阶段要回答的问题

**到底是哪个进程、哪个线程、哪一行代码、哪个系统调用或哪个函数？**

### 5.2 四级下钻与各自的证据

| 层级 | 工具 | 证据 | 代价 |
| --- | --- | --- | --- |
| 进程 | `ps`、`pidstat`、`/proc/<pid>/status` | 它给出谁在花 CPU、谁在等、谁在读写 | 只读，生产机上也可以做 |
| 线程 | `pidstat -u -t`、`top -H`、`/proc/<tid>/sched` | 它给出进程内部的热点线程与亲和性 | 只读，生产机上也可以做 |
| 系统调用 | `strace -c` / `-T` / `-e trace=` | 它给出调用次数分布与单次耗时 | 高：每次拦截约 55 µs，本机 4 万次调用实测从 51 ms 变成 2254～2474 ms |
| 函数 / 栈 | `perf record` 加 `perf report` 或 `perf script` | 它给出热点函数与调用栈；off-CPU 另需 `perf sched` 或 eBPF | 中；采样类结果受采样偏差影响 |

### 5.3 三个必须验证的前提

1. **`/proc/<pid>` 里的累计值必须差分**才有速率含义（`io`、`status` 的切换计数、`sched` 的 `se.sum_exec_runtime`）；
2. **`io` 文件里 `rchar` 与 `read_bytes` 是两回事**：前者是经过 `read()`/`write()` 的字节（含缓存命中），后者是真正落到块设备的字节。本机实测一个 `sleep` 进程 `rchar=7088` 而 `read_bytes=0`；
3. **`perf` 的硬件事件可能根本不被支持**。VMware 未透传 PMU 时 `perf stat -e cycles` 显示 `<not supported>`；而 **`perf record -e cycles` 录下来的事件名是 `task-clock`**——本机实测它写出了文件、没有报错，但 `perf report` 的标题写明 `event 'task-clock'`，**不是 cycles**。判据只有一条：先看 `perf stat -e <event>` 有没有 `<not supported>`，并回头核对 `perf report` 或 `perf evlist` 里实际记下的事件名，而不要用"命令成功、文件写出了、样本数不是 0"当证据。

### 5.4 本阶段的结论长什么样

PID 45062（python3）在 CPU 2 上 `us` 100%；它是单线程；`voluntary=0`、`nonvoluntary=16`、`nr_switches=16`，说明它几乎不被切换；`perf record -F 99` 采样 3 秒得 494 个样本，其中 `99.80%` 落在 `spin [.] main`。因此结论是**该进程的单线程自身计算占满了一颗核**，既不是锁也不是 IO。

## 六、跨阶段的核对对象

五个阶段是时间线，但有几件事穿过多阶段。串不起来的原因，通常是没抓住这几条线。

### 6.1 观测代价与降级路径

观测会改变被测对象。`strace` 的代价与调用次数成正比（每次约 55 µs），采样类工具会漏掉不在 CPU 上的时间，也漏掉亚窗口的短脉冲。因此**先取低代价证据，再取高代价证据**；而动手（重启、杀进程、改参数）之前要把证据取完。完整讨论见《观测的代价与降级路径》。

### 6.2 视角缩放

从整机到单核、到进程、到线程、再到 cgroup，同一个现象在不同视角下结论相反。因此判据固定按"最热的那一层"取：容量按最热核，延迟按最慢的实例，内存按 cgroup。完整讨论见《争抢为什么不按比例缩放》。

### 6.3 判据与口径

每个数字都有它回答不了的问题。这条线最后收拢到一张卡上：

| 数字 | 它回答什么 | 它**不能**回答什么 |
| --- | --- | --- |
| `load average` | 它回答有没有任务在排队（含 D 状态） | 它不回答 CPU 使用率，也不回答是哪一层的问题 |
| `%usr`（整机） | 它回答整机平均有多忙 | 它不回答还有没有余量，因为余量要看最热核 |
| `%iowait` | 它回答空闲期有没有未完成的 IO | 它不回答设备是否饱和 |
| `%util` | 它回答设备有没有闲着 | 它不回答是否在排队 |
| `MemFree`/`MemAvailable` | 它们回答还有没有空间 | 它们不回答有没有压力 |
| PSI `avg*` | 它回答压力是否**持续** | 它不回答是否发生过短暂停顿，因为后者要看 `total` 差值 |
| `nstat` 的计数 | 它回答累计发生了什么 | 它不回答此刻的速率，因为速率要差分 |
| 一分钟平均值 | 它回答趋势 | 它看不见亚分钟脉冲 |
| 平均延迟 | 它回答整体水平 | 它看不见长尾与只影响部分请求的拐点 |

### 6.4 基线与容量

没有基线就没有"变慢了"。因此基线必须带采集条件：同一块盘上 `w_await` 在 0.09 ms 与 6.59 ms 之间摆动，条件不同的两组数不可比。容量按最热核与 p99 拐点算，同时用历史数据确认"过去有没有数据"。完整讨论见《一次止损的闭环》。

**第一反应不要做什么**：不要在没量化影响面之前敲命令；不要在没拿到分层结论之前下钻；不要把"某一层的一个数字正常"当成"这一层没问题"；不要用一次采样就宣布结论；不要在证据取完之前动手改配置或重启。

## 常见误解

| 做法或说法 | 后果或事实 |
| --- | --- |
| 用整机 `%usr` 判断 CPU 余量 | 单核可以已经 100%，所以判据在最热核上，不在整机平均上 |
| 用 `load` 当使用率 | 它数的是任务数（含 D 状态），因此要除以核数才有意义 |
| 把 `vmstat` 的 `si` 当成软中断 | 那是 swap in，而软中断在 `top` 里才叫 `si` |
| 用 `%iowait` 认定磁盘瓶颈 | 它只说明"空闲时有 IO 未完成"，而判据在 `await`/`aqu-sz` |
| 用 `%util` 判断饱和 | 它量的是"忙"，因此 NVMe 健康时也能接近 100% |
| 用 `MemFree` 判断内存够不够 | 缓存是资产，所以判据是 `MemAvailable` 加压力指标 |
| 只看 PSI 的 `avg` 就宣布"没有压力" | `avg` 会被窗口摊平，而 `total` 差值才是短脉冲的证据 |
| 把 `nstat` 的累计值当速率 | 默认输出是窗口差值，而 `-a` 才是累计 |
| 用"`perf record` 写出了文件"证明硬件计数器可用 | 录下来的事件名可能是 `task-clock`，所以要回头核对 `perf report` 或 `perf evlist` |
| 用一次 `top` 截图当证据 | 首屏是很短的一段窗口，而且只有整机与进程两个视角 |
| 用 1 分钟聚合证明"没有异常" | 亚分钟脉冲在图上看不见，所以要先判断形态再选窗口 |
| 跨实验、跨条件拼对比表 | 条件不同的两组数不可比，因此同一结论必须来自同一轮统一条件 |

## 要点自测

**问：为什么"五个必答问题"里的第 5 问（和什么比）最重要？**
答：因为没有比较对象只能描述现象，既无法证明异常，也无法验收修复。基线、同期数据或 SLO 是"变慢了"这个判断成立的前提。

**问：同一台机器上，`all` 行 25% 而某一核 100%，哪一个进入结论？**
答：逐核的那个进入结论。因为整机平均会掩盖单核饱和，所以结论要写"CPU 2 已无余量"，而不是"整机还有余量"。

**问：`%iowait` 高，能直接结论"磁盘是瓶颈"吗？为什么？**
答：不能。因为它只说明 CPU 空闲期间有未完成的 IO。判据在设备层的 `await` 与 `aqu-sz`，以及 Little's law 的交叉校验。

**问：为什么内存这一阶段要求 `avg` 与 `total` 一起读？**
答：因为 `avg` 是窗口内被拖慢时间占比的滑动平均，它会把短暂停顿摊平；而 `total` 是累计值，它的差值能看见"发生过 9.4 ms 的停顿"这类事实。两者回答不同问题。

**问：网络这一阶段为什么坚持"先计数、后抓包"？**
答：因为计数器成本低、可长期开着、能让方向收敛，而抓包成本高且需要限时限量。计数器已经指出方向时（重传率高、队列溢出），抓包只是在确认已经知道的事。

**问：`perf record -e cycles` 写出了样本文件，能证明 PMU 可用吗？**
答：不能。本机实测它没有报错、写出了文件，但 `perf report` 的标题写的是 `event 'task-clock'`——录下来的不是 cycles。可靠判据是 `perf stat -e cycles` 是否显示 `<not supported>`，并核对实际事件名。

**问：为什么每个数字都要写"它不能回答什么"？**
答：因为性能排障的失误几乎都是"把数字当成它不代表的含义"。判据卡的作用是让每次引用数字时都附带边界。

**第一反应不要做什么**：不要先重启再找原因；不要在没定位到进程之前改内核参数；不要用单一阶段的证据跳过下一阶段的门槛。
