# 性能基线与排障治理

性能这件事有一个和别的章节不同的地方：**它的结论几乎全部依赖"跟什么比"**。因为没有基线，"变慢了"只是一个感受；因为没有回归门槛，"优化好了"只是一个说法；因为没有复盘产物，同一次故障会以同样的路径再发生一遍。而这三件事都不是靠个人能力补上的，靠的是产物本身——谁在什么时候采、采什么条件、交给谁。

## 1. 没有制度时会怎样

五类产物缺失时的具体后果，都能在本库前面几篇的例子里找到对应：

| 缺什么 | 具体后果 |
| --- | --- |
| 性能基线卡 | 报障时只能说"现在是这个数"，说不出"比正常差多少"。同一块盘的 `w_await` 在两种负载下可以从 0.09 ms 到 6.59 ms，所以没有采集条件就无法判断 |
| 采集条件与工具版本 | 跨时间、跨机器的数字会被放进同一张对比表，得出错误结论 |
| 容量台账与拐点 | 记录里只能留下"CPU 到 80% 告警"这类静态阈值，而写不出"QPS 到多少时 p99 开始非线性上升" |
| 历史指标可用性巡检 | 事后复盘时才发现这台机器昨天没有数据。而"`sysstat` 装了就一定有历史"是最常见的假设 |
| 排障记录与报告规范 | 复盘时只剩下口述；"重启后好了"被当作结论；改进项没有 owner 与期限，下一轮照旧 |
| 演练制度 | 排障路径从未被检验过，所以真出事时才第一次走这条路径 |

一条可以直接用的自检问法：**如果领导问"到底慢了多少"，你能不能给出一个数字和它的比较对象？** 答不出来，说明这一章缺的是产物，不是能力。

## 2. 行业通行的做法

- **USE 方法**（Utilization / Saturation / Errors）作为巡检与基线的组织骨架：它按资源各问三问，而不是按命令罗列。原始表述见 Brendan Gregg 的公开文章；
- **基线必须带采集条件**。这在本库里有一条硬证据：同一块盘的 `w_await`，在"`stress-ng --hdd 2` 并发写（`wareq-sz` 3781）"窗口是 6.59 ms，而在"4 KiB 随机写 `libaio` `iodepth=64`（`wareq-sz` 4）"窗口是 0.09～0.27 ms——两者差几十倍，但两个都不算异常；
- **容量按"最热单元"和"拐点"评估**，不按整机平均。SRE 实践中容量与冗余绑定（N+1 之类），本库阶段 11 展开；
- **排障报告固定分段**（时间线、影响面、证据、根因、止损、改进），并明确"人为失误"不算根因；
- **故障演练**（game day / chaos engineering）用受控实验检验排障路径与监控覆盖，本库阶段 11 与阶段 12 有对应的演练与复盘纪律；
- **错误预算**把"哪些性能问题立刻处理、哪些排期"从嗓门变成数字，口径见阶段 9 的《体系：一次告警的一生》与《治理：可观测性治理》。

## 3. 治理产物四件套

### 3.1 性能基线卡

一份基线卡最少五组数据。**每组都要带采集条件**，因为这是它和"随手抄几个数字"的分界线。

| 组 | 采什么 | 频率 / 时机 | 注意 |
| --- | --- | --- | --- |
| 机器身份 | 主机名与角色、采集时间、采集人、虚拟化类型、内核、CPU、内存、swap、磁盘与 inode、网卡 | 变更时更新 | 这一组决定"哪些结论可以外推" |
| CPU 与负载 | `load(1/5/15)`、`vmstat` 的 `r`/`b`、`mpstat -P ALL` 的整机与**每核峰值**、`cs` | 每周一次，变更后再采一次 | 只记整机就等于没记 |
| 内存 | `MemAvailable`、PSI memory 的 `some`/`full`（`avg10` 与 `total`）、swap 使用、`Dirty`、`Slab` | 每周一次 | 要看压力，不看用量 |
| IO | 正常时段与备份窗口各一份（`w/s`、`w_await`、`aqu-sz`、`%util`、`wareq-sz`），另加 `fio` 四象限 | 每周一次，换盘后再采一次 | 必须写清 `bs`、`ioengine` 与 `iodepth` |
| 网络 | `ss -s` 的 `timewait`/`orphaned`、`nstat` 的 `TcpRetransSegs`/`TcpOutSegs` 与比率、`softnet dropped`、`ip -s link` 的 errors/dropped | 每周一次 | 计数器要带窗口 |

三条采集纪律：**业务高峰与低谷各采一份**；**写清采集时间与当时在跑什么**；**同一份基线用同一套命令采**。

`fio` 四象限的用法是把"这块盘大概能给多少"变成可比的四格。本机（VMware 虚拟盘上的 ext4 on LVM，`direct=1`）实测如下：

| 象限 | 参数 | 吞吐 | `clat` p50 | `clat` p99.9 |
| --- | --- | --- | --- | --- |
| 顺序写 1 MiB | `psync` `iodepth=1` | 1495 MiB/s | 635 µs | 1876 µs |
| 顺序读 1 MiB | `psync` `iodepth=1` | 1708 MiB/s | 562 µs | 1434 µs |
| 随机写 4 KiB | `libaio` `iodepth=32` | 27.3k IOPS（107 MiB/s） | 1090 µs | 3228 µs |
| 随机读 4 KiB | `libaio` `iodepth=32` | 47.5k IOPS（185 MiB/s） | 619 µs | 1958 µs |

三条使用边界：`fio` 是**有写入的破坏性操作**，所以只能在可丢弃目录或可快照实验机上做，并预先定 `--size` 与 `--runtime` 上限；**`--iodepth` 只在 `libaio`/`io_uring` 这类异步引擎下生效**（本机同一个 `--iodepth=32`，默认 `psync` 只跑出 11.7k IOPS，换 `libaio` 才是 27.3k），所以基线卡里必须写 `ioengine`；**虚拟化环境的绝对值要打折扣**（本机 `dd iflag=direct` 读能到 8.3～11.1 GB/s，比顺序读基线还高一个量级，说明宿主层仍在缓存），因此可信的是趋势与相对关系。

### 3.2 容量台账与拐点

台账要记的不是某一个静态数值，而是**"到哪个点开始变坏"**。判据的核心是拐点而不是阈值：记录"QPS 是多少时 p99 开始非线性上升"，比记录"CPU 到 80% 告警"有用得多。

四个常见的错误算法与替代问法：

| 错误算法 | 正确算法 |
| --- | --- |
| 整机 CPU 使用率 60%，所以还有 40% 余量 | 要问最热核的余量是多少，以及单核是否已经饱和 |
| 平均延迟 20 ms 达标，所以服务健康 | 要问 p99 与 max 是多少，以及与基线比变了没有 |
| 线程数 = 核数就够 | 要先分清任务是计算密集还是常等 IO；等待型任务可以超配，而计算型不应超过核数 |
| 扩容后必然变快 | 要先判断瓶颈在单线程热点还是在下游串行点；扩容对这两者都无效 |

本机有三个支撑"按核按 p99"的实测事实：单核打满时整机 `%usr` 只有 25.04%、`load` 只有 0.34；同核竞争把吞吐从 26,473,519 次/2 s 压到 5,564,871 次（−79.0%）；竞争者加到 15 个时 `p50` 一直在 8.06～8.13 ms，而 `max` 从 8.36 ms 涨到 40.87 ms。

从基线到容量结论的一个完整例子：

```text
# 模板，数值仅示意
基线：4 核机器，业务高峰 QPS 1200，最热核 %usr 72%，p99 = 85 ms
观察：QPS 1500 时最热核 %usr 91%，p99 = 210 ms
结论：该服务的能力上限受「最热核」约束，而不是 4 核总算力；
      在单线程热点未拆之前，扩副本比提升单机核数更有效。
```

### 3.3 排障记录与六段报告

一次性能故障至少要留下四份记录，它们的读者不同，所以字段也不同：

- **影响面与时间线记录**：它写现象、范围、开始时刻、当前状态、比较基线与变更时间线；
- **分层判定记录**：它写每一层的结论（像或不像）、支撑字段与取值，以及下一步；
- **止损记录**：它写动作、预期效果、验收指标、回滚方式与触发条件、观察窗口，以及实际结果；
- **六段报告**：时间线、影响面、证据、根因、止损动作与长期改进。其中前五段面向复盘，最后一段面向排期。

### 3.4 演练与工具边界

演练的价值在于**在受控条件下暴露排障路径的断点**。一份演练记录至少要写清五件事：做了什么注入、在什么环境与上限下做、预期观测指纹是什么、实际观测到什么，以及**哪些工具当时不可用、替代路径是什么**。

最后一项经常被省略，却最有用：本机 `kernel.perf_event_paranoid=4`、`kernel.dmesg_restrict=1`、`kernel.unprivileged_bpf_disabled=2`，所以普通用户做不了内核观测；`ethtool -l ens33` 直接报 `Operation not supported`（VMware 模拟的单队列 `e1000`）。**这些"做不了"本身就是需要登记的事实**，因为不登记，下次出事就会有人在这上面浪费半小时。

## 4. 关键字段的治理用法

排障时这些字段用来"看"，治理时它们用来"定"——同名字段，两种用法：

| 字段 | 治理用法 |
| --- | --- |
| `memory.peak` | 它是定 `MemoryMax=` 的依据：把峰值留出余量作为上限，而不是拍脑袋 |
| `memory.events` 的 `oom_kill`/`max` | 它们用来判断"这个上限是不是配错了"：若 `max` 远大于 `oom_kill`，则说明内核尽力回收过；若全是 0，则说明上限还有余量 |
| `cpu.stat` 的 `nr_throttled`/`throttled_usec` | 它们用来判断配额够不够：若持续增长，则说明配额是瓶颈，因此要按业务周期调，而不是按单次峰值调 |
| `%util` 与 `aqu-sz` | 它们用来定 IO 的干预线：若 `%util` 高而 `aqu-sz` 小，则说明设备忙但队列不深，通常不需要干预 |
| 重传率（`TcpRetransSegs`/`TcpOutSegs`） | 它用来定"网络是否要进告警"：要给一个长期基线比率，而不是给绝对次数 |
| `pgscan_direct`/`allocstall` | 它们用来定内存告警线：只要出现增长就意味着有同步回收，因此比"可用内存低于 X"更贴近体感 |

## 5. 六个具象治理场景与要交出的产物

### 场景一：一批新机器上线，没有任何基线

**背景**：出问题的时候无法判断"是不是变慢了"，而容量决策只能凭机器规格。**应当做的事**：按 3.1 的五组数据采集，业务高峰与低谷各一份，并在同一天完成；`fio` 四象限只在实验机或可丢弃目录做。**要交出的产物**：一批带采集条件与工具版本的基线卡；一份"哪些结论不可外推"的说明（虚拟化类型、虚拟盘、单队列网卡）。

### 场景二：复盘时发现历史根本没在采

**背景**："昨晚 3 点变慢"没有任何数据可查。本机 `sysstat` 已安装、`sysstat-collect.timer` 为 `active`/`enabled`、`/var/log/sysstat/saNN` 存在；但**默认保留期往往只有 7 天**（`/etc/sysstat/sysstat` 的 `HISTORY=`），所以跨周复盘就要不到数据。**应当做的事**：把"历史目录里有当天的文件且在增长"纳入巡检；把 `HISTORY=` 调到覆盖一个业务周期以上（本库建议至少两周）。**要交出的产物**：巡检项、保留期配置，以及一份"实时、短期、历史、事后"四层数据源的对应关系表。

### 场景三：容量评审被告知"CPU 还有余量"

**背景**：有人拿整机平均做出了容量结论。**应当做的事**：改成"最热核加 p99 拐点"的双判据；用基线到结论的模板写出上限来自哪里。**要交出的产物**：一页容量评估（当前峰值、拐点位置、约束在哪个单元、扩容方式与代价）。

### 场景四：一次性能故障要收尾

**背景**：手上只有口头结论，而"重启后好了"被当成结论。**应当做的事**：按 3.3 补齐四份记录；改进项写成"有动作、有 owner、有期限、有验收方式"的句子，去向分三种（立即修、排期，或者显式接受风险并写明批准人）。**要交出的产物**：六段报告、止损记录与改进项清单。

### 场景五：给一个批处理服务加上限

**背景**：批任务抢资源，影响了同机上的延迟敏感服务。**应当做的事**：用 drop-in 把 `CPUQuota=`/`IOWeight=`/`MemoryMax=` 配到 unit 上，先验证生效值，再看内核侧文件；验收用"配置一致、内核侧一致、业务高峰延迟回到基线、被限流方吞吐按预期下降"四条。**要交出的产物**：变更记录（含回滚命令与触发条件），以及修正后的基线卡（被限流方的吞吐基线要更新，因为它变了）。

### 场景六：建立一次演练与工具边界登记

**背景**：排障路径从未被检验，而且有人以为本机什么工具都能用。**应当做的事**：在隔离环境（独立 netns、可快照实验机）做注入，设定明确上限，跑完复核"无残留进程、无监听端口、无临时目录、无残留 unit、无残留 netns"。**要交出的产物**：演练记录（含恢复耗时），以及工具可用性清单（哪些可用、哪些被权限或硬件挡住、替代路径是什么）。

## 6. 与其他章节的接口

- **阶段 9（日志、监控与可观测性）**：指标语义、告警规则、SLI/SLO 与错误预算的口径在那里，历史指标的采集与保留也属于那一边；这里只需要"能在事后拿到数据"这一个前提；
- **阶段 11（生产运维与高可用）**：变更单、备份与恢复演练、容量与冗余的落地流程在那里；基线卡与容量结论是它的输入；
- **阶段 4（内存管理与 OOM）与阶段 8（systemd 与服务管理）**：cgroup 上限的语义、systemd 资源控制的生效链在那里；这里只用"给它定上限时的字段与验收"；
- **阶段 6（网络协议栈与排障）**：网络计数器与队列的口径在那里，这里只引用比率判据。

**第一反应不要做什么**：不要在基线里省掉采集条件；不要用整机平均做容量结论；不要把"重启后好了"当验收；不要在没有演练记录的情况下相信自己的排障顺序；不要把改进项写成"加强监控"这类没有 owner 与期限的句子。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 凭印象说"平时就是这个值" | 没有采集条件与时间戳的数字不能用来比较 |
| 只采低谷时段的基线 | 容量评估会系统性偏乐观 |
| 基线卡里只记整机 CPU | 单核饱和会被完全掩盖 |
| 记了 `--iodepth=32` 却没记 `ioengine` | 默认 `psync` 下这个参数不生效，所以基线不可复现 |
| "`sysstat` 装了就有历史" | 要确认采集 timer 是 `active`/`enabled`，历史目录有当天的文件且在增长 |
| 把 `sadf -d` 导出的时间当本地时间 | 它是 UTC（带 `UTC` 后缀），所以时区不是 UTC 的机器上要对齐换算 |
| 在生产机高峰期跑 `fio` | 它会直接影响业务，因此只能在实验机或可丢弃目录做 |
| 容量按平均值算 | 约束通常来自最热单元与长尾，而不是平均 |
| "扩容就能解决" | 单线程热点与下游串行点不会因为加副本而变快 |
| 复盘写"人为失误"当根因 | 那不是根因，而是可改进的流程与防线缺口 |
| 改进项只写"加强监控" | 没有 owner、期限与验收方式的改进项等于没写 |
| 演练不做清理复核 | 残留的 netns、unit 与进程会在后续实验里制造假现象 |

## 要点自测

**问：一份可用的性能基线卡至少要包含哪五组数据？为什么每组都要带采集条件？**
答：机器身份、CPU 与负载、内存、IO、网络。因为条件不同的数字不可比——同一块盘的 `w_await` 在两种负载下可以从 0.09 ms 到 6.59 ms，差了几十倍。

**问：为什么容量评估要看"最热核"和 p99，而不是整机平均与平均延迟？**
答：因为单核打满时整机 `%usr` 只有 25.04%，所以整机平均看不到约束；而 `p50` 在竞争者从 0 加到 15 个时一直是 8.06～8.13 ms，真正变坏的是 `max`（从 8.36 ms 涨到 40.87 ms）。约束体现在最热单元与尾部。

**问：`fio` 基线为什么必须记 `ioengine`？**
答：因为 `--iodepth` 只在异步引擎下生效。本机同一个 `--iodepth=32`，默认 `psync` 只跑 11.7k IOPS，换 `libaio` 才是 27.3k。所以不记引擎的基线不可复现，也不能比。

**问：`memory.peak` 与 `memory.events` 在治理上分别怎么用？**
答：`memory.peak` 用来定 `MemoryMax=` 的依据（峰值留出余量）；`memory.events` 的 `oom_kill` 与 `max` 用来判断上限是不是配错了——若 `max` 远大于 `oom_kill`，则说明内核尽力回收过，而全 0 说明还有余量。

**问："sysstat 装了就一定有历史"错在哪里？**
答：因为采集是靠 timer 驱动的。要确认 `sysstat-collect.timer` 是 `active`/`enabled`、历史目录里有当天的文件且在增长；还要确认 `HISTORY=` 的保留天数够覆盖复盘窗口（默认往往只有 7 天）。

**问：一次故障收尾时，改进项写成什么样才算合格？**
答：要有动作、有 owner、有期限、有验收方式，并明确去向（立即修、排期，或者显式接受风险并写明批准人）。而"加强监控"这类句子不合格。

**问：为什么"工具不可用"也要进演练记录？**
答：因为它决定了降级路径。本机普通用户做不了内核观测（`perf_event_paranoid=4`、`dmesg_restrict=1`、`unprivileged_bpf_disabled=2`），而 `ethtool -l` 在虚拟网卡上直接不支持——不登记就会在真故障时重复踩。

**第一反应不要做什么**：不要在没有条件标注的数字之间做比较；不要把演练当形式；不要在复盘里把根因写成"人为失误"。
