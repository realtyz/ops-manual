# 资源「有」与任务「完成得了」之间的那道缝

有两类现象长得非常像，代价却完全不同：

- 内存还有 4 GiB 可用，进程却开始变慢；
- 磁盘 `%util` 只有 80%，写入延迟却翻了几十倍。

这两件事的共性不是"资源不够"，而是**资源的可用量或忙闲程度，与任务能不能按时完成之间隔着一层机制**。这一层机制在内存上是回收与水位的取舍，在存储上是请求的排队与服务时间。看不清这层缝，就会把"占得多"当成"不够用"、把"设备在忙"当成"设备饱和"。

以下读数取自一台 `MemTotal` 7894 MiB、swap 4095 MiB、根分区 ext4 on LVM（底层是虚拟盘）的内核 6.8 Ubuntu 24.04 虚拟机，`iostat` 来自 sysstat 12.6.1。**块设备是虚拟盘，所以 IO 的绝对毫秒数不可外推到物理盘**；`MemAvailable`、PSI 这类内存口径不受影响。

## 1. 内存：两个完全不同的问题

"内存够不够"这句话里其实混着两个问题：

| 问题 | 看什么 | 判据 |
| --- | --- | --- |
| 有没有空间 | `MemAvailable`（**不是** `MemFree`） | 它代表"应用还能申请到的量"，已经扣掉了不可回收部分、加上了可回收缓存 |
| 有没有压力 | `/proc/pressure/memory`（PSI）、`/proc/vmstat` 的回收与换页计数 | 任务是否因为内存而真的被拖延 |

一个进程分配并逐页触碰 3 GiB 匿名页（堆、栈这类没有文件对应的页），`MemAvailable` 从 7224 MiB 降到 4145 MiB——**但压力指标几乎没动**：

```text
# 说明：数值仅示意、不代表你的机器（PSI 的 total 单位是微秒）
                     total    used    free  shared  buff/cache  available
分配前  Mem:          7894     669    2800       1        4740       7224
触碰后  Mem:          7894    3748     218       1        4235       4145

/proc/pressure/memory:some avg10=0.00 avg60=0.00 avg300=0.00 total=9695   # 之前 298
/proc/pressure/memory:full avg10=0.00 avg60=0.00 avg300=0.00 total=9477   # 之前 208
pgscan_direct 0
pgsteal_direct 0
pgscan_kswapd 127429
```

这一组数字要读出三件事，缺一件就会读错：

1. **用掉了内存 ≠ 有压力**。3 GiB 是真的被占用了（`VmRSS` 3,156,232 kB），但没有任何任务因此停下来等；
2. **`avg` 会摊平事实，`total` 不会**。`some` 的 `total` 涨了 9397 µs、`full` 涨了 9269 µs，这 9.4 ms 的压力被摊在约 10 秒的窗口上（不足 0.1%），所以三个 `avg` 都还是 0.00。**只看 `avg` 会得出"完全没压力"，只看 `total` 差值才知道发生过短暂停顿**；
3. **`pgscan_direct = 0`** 说明回收是后台（`kswapd`，扫描 127429 页）做的，不是在分配者的上下文里同步做的。这是"变慢"与"没变慢"的分水岭。

顺带把 PSI 的三个口径钉死，因为它们很容易被读错：

- `some`：**至少有一部分任务**因为该资源停下来的时间占比；
- `full`：**所有非空闲任务同时**都因该资源停下来的时间占比——文档里说这种状态下 CPU 周期是被浪费掉的，持续出现就叫 thrashing；
- **`/proc/pressure/cpu` 也有 `full` 行，但系统级无定义**，自 5.13 起为了向后兼容固定打印 0。所以"CPU 的 `full` 是 0"不代表"CPU 从不全面停顿"，它根本不是一个有意义的读数；
- `avg10/avg60/avg300` 的单位是**百分比**，`total` 的单位是**微秒**（文档原文 `The total absolute stall time (in us)`）。把 `total` 当纳秒或当比例都会算错。

第 3 点就是那道缝的位置：**内存回收有两条路径**，一条不影响业务，一条直接加在业务的延迟上。

### 1.1 direct reclaim：延迟尖刺的主要来源

内存有空闲页低于水位线时，回收启动。三条水位线（`min`/`low`/`high`）决定什么时候用哪条路径：

- 空闲页跌破 `low`：`kswapd` 在内核线程里后台回收，业务基本无感；
- 空闲页跌破 `min`：**发起分配的那个进程自己被迫同步回收**（direct reclaim）。它要扫描 LRU、可能还要等回写，这些时间全部算在它的延迟里。

判据很直接：`/proc/vmstat` 的 `pgscan_direct`/`pgsteal_direct`（有的内核版本还有 `allocstall`）在增长，配合 `/proc/pressure/memory` 抬头，就是这件事在发生。

**出处要标清**：水位线的三条线在 `Documentation/admin-guide/mm/concepts.rst` 里有明确定义（`low` 触发 `kswapd` 异步回收、`min` 触发同步回收并让分配停顿），但 **`pgscan_direct`/`pgsteal_direct` 这两个字段名并没有出现在内核文档的字段说明里**，它们的语义来自 `mm/vmstat.c` 的计数器定义与回收路径的源码——引用时按"源码证据"标注，不要说成文档定义。

两个常见的伴生现象：

- **刚被回收的页马上又被用到**：`workingset_refault` 增长，说明"回收判断错了"，正确做法是扩内存或缩小工作集，而不是继续调回收参数；
- **换页**：匿名页被换出到 swap，之后访问要读回来。`vmstat` 的 `si`/`so` 长期非 0 说明换了，但注意 **`vmstat` 的 `si` 是 swap in，`top` 的 `si` 是 softirq**——两个同名字段含义完全不同。

有一处边界必须写清楚：**`vm.swappiness` 是权重不是开关**。它调节回收时对匿名页的倾向，取值 0~200，设为 0 时内核"不会主动发起换页，直到空闲页与文件页之和低于 zone 的 `high` 水位"——也就是说**压力足够大时它仍会换页**；要真正禁用只能 `swapoff` 或把该 cgroup 的 `memory.swap.max` 设为 0。而关掉 swap 并不消除风险，只是把"换页变慢"换成"被 OOM 杀掉"。（默认值 60 与 0~200 的范围按内核文档 `Documentation/admin-guide/sysctl/vm.rst`，6.x；6.8 之前的文档里范围写法为 0~100，按目标机器同一主版本取。）

### 1.2 两个会制造尖刺的副作用

内存子系统还有两处会**主动**制造延迟，与"够不够"无关：

- **透明大页（THP）与内存整理**。大页减少地址翻译次数，但按 2 MiB 粒度落地意味着碰到一个字节就占实 2 MiB（内存放大）；后台的 `khugepaged` 合并与碎片整理（compaction）会带来偶发停顿。本机策略是 `always [madvise] never`，即默认只对显式声明 `madvise(MADV_HUGEPAGE)` 的区域启用——这是个合理的折中。要按负载决定，不要全局 `always`；
- **脏页回写与限流**。脏页超过硬阈值后，**发起写的进程会被限速甚至阻塞**（`balance_dirty_pages`）。现象是 `Dirty`/`Writeback` 高、进程进 `D` 状态、写入延迟上涨，而内存并不缺。这一点常被误解成"调低 `dirty_ratio` 能治写入卡顿"——上限只决定"什么时候开始回写"，能不能跟上取决于设备排空速率。

## 2. 存储：`%util` 量的是「忙」，不是「排队」

`iostat -x` 有三列经常被当成同一件事，实际是三件事：

| 列 | 是什么 | 单位 | 回答的问题 |
| --- | --- | --- | --- |
| `w_await`/`r_await` | 一次请求从提交到完成的**平均**时间，含排队与服务 | 毫秒 | 请求等得久不久 |
| `aqu-sz` | 发往该设备的请求的平均队列长度（旧名 `avgqu-sz`） | 个 | 有没有在排队 |
| `%util` | 经过的时间里，"有 I/O 请求被发出到该设备"的时间占比 | 百分比 | 设备有没有闲着 |

`iostat(1)` 对 `%util` 的原文是 "Percentage of elapsed time during which I/O requests were issued to the device (bandwidth utilization for the device)"，紧接着还有一句必须一起读：**"Device saturation occurs when this value is close to 100% for devices serving requests serially. But for devices serving requests in parallel, such as RAID arrays and modern SSDs, this number does not reflect their performance limits."**

也就是说：**`%util` 不是饱和度**。它只回答"这段时间里设备手上有活吗"，不回答"有多少活在等"，而且 man 页自己声明它对可并行服务的设备不反映性能上限。判饱和度优先看 `await` 与 `aqu-sz`——这两个数可以互相矛盾：

```text
# 说明：数值仅示意、不代表你的机器（同一块设备在六种压力下的窗口）
窗口                                  w/s     w_await   wareq-sz      aqu-sz   %util
大块并发写                           324.00    6.59 ms   3781.33       2.14    80.10%
大块并发写（另一秒）                 419.00    6.23 ms   3188.18       2.61    83.30%
4 KiB 随机写，队列深 16            30308.00    0.08 ms      4.00       2.34    91.40%
4 KiB 随机写，队列深 64            14721.00    0.27 ms      4.00       3.92    74.50%
同上，压力爬升后                    35457.00    0.09 ms      4.00       3.15    98.80%
大块回写突发（每次同步落盘）         477.00    1.14 ms   4397.92       0.54    42.50%
```

两张对照要一起看：

- **`%util` 98.80% 的那一秒，`aqu-sz` 只有 3.15、`w_await` 只有 0.09 ms**。设备几乎一直有活在手上，但每个请求等得不久；
- **`w_await` 6.59 ms 的那一秒，`%util` 只有 80.10%、`aqu-sz` 只有 2.14**。设备有 20% 的时间闲着，请求却要等 6 毫秒。

原因在于**请求的大小与设备的并行能力不同**。前者的 `wareq-sz` 是 4 KiB（小块、高并发、设备能并行处理，所以单个请求等得短但设备一直不闲）；后者的 `wareq-sz` 是 3781 KiB（约 3.7 MiB 的大请求，单次服务时间长，设备即使有时闲着，每笔请求本身就很慢）。

由此得到两条判据：

- **`%util` 高不能证明磁盘是瓶颈**。NVMe 这类支持多队列深度并行的设备，在完全健康时 `%util` 也可以长期接近 100%；
- **`%util` 低不能排除磁盘是瓶颈**。单请求服务时间很长的场景（大块写、机械盘寻道、网络存储往返）会在 `%util` 不高时让延迟爆掉。

### 2.1 Little's law 是这里的交叉校验

`w/s × w_await ≈ aqu-sz`（单位要统一：秒 × 次/秒 = 个）。上表六组里，三组完全相等、三组只差 0.04～0.08（来自 `w_await` 只保留两位小数）。它保证：

- 你看到的三个数属于同一个稳态；对不上就说明窗口里有突变；
- `await` 低不等于没问题——0.09 ms × 35,457/秒 = 3.19 个在途请求。

队列长度与延迟的关系还有一个直接的用途：**队列深不是坏事，深而无界才是**。设备能并行的深度有限，队列超过它之后每个请求的等待就会继续变长，而吞吐不再增长。同一个 `iodepth` 从 16 提到 64 的窗口里，`w/s` 从 30,308 掉到 14,721——**深队列下请求等待更久，单位时间能完成的反而更少**。

做这个校验时注意口径：`iostat` 的 `tps` 定义是"**issued** to the device"（发出），而 `r/s`/`w/s` 是"**completed** per second"（完成）。稳态下两者接近，窗口内有突变时不同。用哪个要写明。

### 2.2 两个同族指标的可信度问题

有两处文档自己声明"不可靠"，引用时要带上这个前提：

- **`%iowait`**（`mpstat` 与 `/proc/stat`）的定义是"CPU 空闲、且系统存在未完成的磁盘 I/O 请求的时间占比"。`man 5 proc` 明确写了 **"This value is not reliable"**，并给出三条理由：CPU 不会为了等 I/O 停下来（空闲时会有别的任务被调度上来）；多核上一个在等 I/O 的任务不属于任何特定 CPU，因此**逐核 iowait 难以计算**；以及**该值在某些条件下会下降**——它不是一个可靠的单调累计量。所以 `%iowait` 只能当"当时可能有过 IO"的线索，判据必须落到设备层的 `await`/`aqu-sz`；
- **`%util`** 的记账方式在内核侧也有边界。它的输入是 `/proc/diskstats` 里"花在 I/O 上的毫秒数"那个字段——内核文档的原文是"该字段只要**有请求在途**就增长"，并带一条按版本变化的注记：**"Since 5.0 this field counts jiffies when at least one request was started or completed. If request runs more than 2 jiffies then some I/O time might be not accounted in case of concurrent requests."**（5.0 起按"至少一个请求被启动或完成"的 jiffy 记账，且**并发请求下可能少记**）。所以它既可能对并行设备造成"饱和"的假象，也可能因为记账方式而不精确——**引用它的行为时要连内核版本一起写**（这一段按 6.x 及以后的内核文档取）。

### 2.3 同步落盘：代价差两个数量级

文件写与文件落盘是两件事。缓冲写只是把数据放进页缓存就返回；`fsync`/`fdatasync` 要等数据真的落到设备上。两者在同一文件、同一时段各测 200 次：

```text
# 说明：数值仅示意、不代表你的机器（PSI 之外，单位就是下面写明的毫秒；n=200）
fsync      p50=0.3614 ms  p95=0.4966 ms  p99=1.5105 ms  max=1.5820 ms
缓冲写     p50=0.0019 ms  p95=0.0026 ms  p99=0.0286 ms  max=0.0337 ms
```

`p50` 差约 190 倍、`p99` 差 53 倍。**绝对毫秒数在虚拟化环境里不可外推**（宿主与虚拟盘层的缓存会显著改变它），可信的是这个关系本身：**凡是"每条记录都同步落盘"的设计，延迟就受设备而不是受 CPU 支配**。

这一条解释了相当多"周期性抖动"的现场：日志同步刷盘、审计写入、事务提交、指标落盘，都会在同一周期里制造一段不可压缩的等待。

## 3. 为什么 IO 的"忙"会变成别人的"慢"

单个进程的 IO 会按设备层的排队规则影响其他进程，这中间有几处机制值得记住：

- **回写不是实时的**。写进页缓存之后，数据什么时候落盘由内核决定（脏页阈值 + 回写线程 + 周期性回写）。所以一次 `dd` 的写入可能"瞬间完成"，而延迟在几秒之后才由 `jbd2`/回写线程体现出来；
- **journal 与元数据更新会串行化**。ext4 的 `jbd2/<dev>-<n>` 线程提交日志时，同一文件系统上的其他写入可能被牵连等待——所以并发写窗口里 `pidstat -d` 可能出现 `jbd2/<dev>-<n>` 这个名字，它不是你自己的进程，而是替你的写入提交日志的内核线程；
- **`ionice` 与 cgroup `io.weight` 调节的是份额**，不改变总带宽；在设备已经饱和时，优先级只能重新分配等待，不能让吞吐变大；
- **`direct` IO 不等于绕过所有缓存**。虚拟化层与存储层仍可能有缓存：在虚拟盘上做 `iflag=direct` 读取，读数可以远高于同一块盘的顺序读基线——所以**在虚拟化环境里不要用 `direct` 的绝对数字下结论**。

## 4. 三条判读纪律

把上面所有内容压成三条：

1. **"用得多"与"有压力"要分开问**。内存看 `MemAvailable` + PSI（`avg` 与 `total` 一起），IO 看 `await` + `aqu-sz`；不要用 `MemFree`、不要用 `%util` 当饱和度；
2. **压力的证据是同步回收或同步等待**（`pgscan_direct` 增长、进程在 `D` 状态、`await` 上升），而不是任何量的高低；
3. **任何绝对毫秒数都要带环境**。虚拟盘、网络存储、容器层的缓存都会改变量级，可信的是趋势与相对关系。

**第一反应不要做什么**：不要在内存"占得多"时先清缓存或调 `swappiness`；不要在 IO 变慢时先换盘加盘；不要把 `%util` 或 `%iowait` 当成排队长度；不要拿"还有空闲内存"去否定一次延迟尖刺。

## 常见误解

| 说法 | 事实 |
| --- | --- |
| "`free` 只剩几百 MiB，内存不够了" | 缓存是资产；判据是 `MemAvailable` 与压力指标 |
| "分配了 3 GiB，PSI 还是 0，所以 PSI 没用" | `avg` 被窗口摊平了，`total` 差值涨了 9397 µs。两个都要读 |
| "没有 `pgscan_direct`，就说明内存没问题" | 它只说明没有同步回收；后台回收（`kswapd`）与换页仍可能拖慢任务 |
| "`%util` 到 100% 就是磁盘瓶颈" | `iostat(1)` 自己声明：只有**串行服务请求**的设备才接近 100% 即饱和；RAID 与现代 SSD 这类并行设备上这个数不反映性能上限 |
| "`%iowait` 高所以磁盘是瓶颈" | `man 5 proc` 明写这个值不可靠：逐核难以计算，且可能下降。判据在 `await`/`aqu-sz` |
| "`%util` 没满，所以不是磁盘问题" | 大块请求与网络存储会在 `%util` 不高时让 `await` 爆掉 |
| "`await` 低说明设备很快" | `await` 要与到达率一起读；0.09 ms × 35,457/秒 仍有 3 个在途 |
| "`aqu-sz` 高就是坏" | 队列深是并行能力的体现；坏的是"队列继续变长而吞吐不再增长" |
| "调低 `dirty_ratio` 能治写入卡顿" | 阈值只决定回写何时开始；能不能跟上取决于设备排空速率 |
| "`swappiness=0` 就是不使用 swap" | 它是权重，不是开关；要禁用得 `swapoff` 或 `memory.swap.max=0` |
| "全局开 THP 一定更快" | 大页减少翻译开销，但按 2 MiB 落地会放大内存、`khugepaged`/整理会带来停顿 |
| "`oflag=direct` / `iflag=direct` 一定绕过所有缓存" | 虚拟化与存储层仍可能缓存；direct 读的读数可能高于同一块盘的顺序读基线 |

**第一反应不要做什么**：不要用"还有空闲内存"否定内存压力；不要用 `%util` 决定要不要查磁盘；不要在没确认是设备、回写还是应用写模式之前调 `dirty_*` 或 `swappiness`。

## 要点自测

**问：为什么"用掉了 3 GiB"与"有内存压力"是两件事？**
答：占用是账本，压力是"任务因此停下来等"。占用 3 GiB 时 PSI 的 `avg` 全 0，只有 `total` 差值显示发生过约 9.4 ms 的停顿，且回收是 `kswapd` 后台做的（`pgscan_direct=0`）。

**问：什么证据能证明"同步回收正在拖慢业务"？**
答：`/proc/vmstat` 的 `pgscan_direct`/`pgsteal_direct` 增长，配合 PSI memory 抬头、进程进 `D` 状态、以及业务延迟尖刺对齐。

**问：`%util` 98.8% 而 `w_await` 0.09 ms，怎么解释？**
答：请求是 4 KiB 小块、高并发（35,457 次/秒），设备几乎一直有请求在手上，但每个请求的服务时间很短、排队很浅（`aqu-sz` 3.15）。`%util` 量的是"忙"，不是"等"。

**问：什么时候 `%util` 低也要怀疑磁盘？**
答：单请求服务时间长的时候——大块写（`wareq-sz` 约 3.7 MiB 的窗口里 `w_await` 6.59 ms 而 `%util` 只有 80.10%）、机械盘寻道、NFS 往返、以及虚拟盘/宿主层的排队。

**问：`fsync` 与缓冲写差两个数量级，这说明什么运维事实？**
答：凡是"每条记录同步落盘"的设计（日志、审计、事务提交），延迟由设备而不是 CPU 决定，且会周期性制造不可压缩的等待。绝对毫秒数不可外推，比值关系可信。

**问：`swappiness` 设为 0 能避免换页吗？**
答：不能。它是回收时对匿名页的倾向权重，不是开关。要禁用只能 `swapoff` 或把该 cgroup 的 `memory.swap.max` 设为 0；而且要清楚这会把"变慢"换成"被杀"。

**第一反应不要做什么**：不要在内存"占得多"时先清缓存或调 `swappiness`；不要在 IO 变慢时先换盘加盘；不要把 `%util` 的读数当成队列长度。
