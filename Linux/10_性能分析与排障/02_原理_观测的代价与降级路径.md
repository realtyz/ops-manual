# 观测的代价与降级路径

有一类性能问题特别难查：**你一旦开始仔细看，被测的那个东西就变了。** `strace` 会让程序慢几十倍，`perf record` 会给每次采样加一点开销，抓包会给网络路径加负担，而"先重启试试"看起来什么代价都没有，实际上代价最大——它销毁了唯一的现场。

代价分三处来：插在被观测路径上的开销、采样天生看不见的地方、以及工具在最需要的时候用不了。三者都会让"我没看到异常"这句话变得不成立。

## 1. 观测为什么不是免费的

任何观测都要做至少一件事：**在被观测的路径上插入代码**。插进去的东西决定了代价的形态：

| 代价形态 | 机制 | 典型工具 | 量级直觉 |
| --- | --- | --- | --- |
| 时间扰动 | 每次事件都停下来等你（拦截 + 两次上下文切换） | `strace`、`ltrace` | 与**事件次数**成正比 |
| 资源占用 | 观测进程自己吃 CPU/内存/IO | `perf`、抓包、指标采集器 | 与**采样频率 × 数据量**成正比 |
| 行为改变 | 主动注入，永久改变现象 | `tc netem`、`stress-ng`、`cgroup` 配额 | 与**注入参数**成正比，且不可忽略 |

本章引用的具体数值取自一台 4 vCPU、内核 6.8 的 Ubuntu 24.04 虚拟机（`systemd-detect-virt` = `vmware`，`kernel.perf_event_paranoid=4`、`kernel.dmesg_restrict=1`、`kernel.unprivileged_bpf_disabled=2`），`strace` 6.8、`perf` 6.8.12、iproute2 6.1.0。**权限值与硬件可用性是最容易随环境变化的**，下面凡涉及"能不能用"的结论都按现场取值为准。

三个对照，量级差别很大：

```text
# 说明：数值仅示意、不代表你的机器
# 同一份"2 万次 getpid + 2 万次 stat"的 workload
不加观测：      50 / 51 / 51 ms
套上 strace：   2254 / 2280 / 2474 ms      # 约 45～48 倍
被记录的调用共 40540 次 → 每次拦截约 55 µs
```

值得注意的是：**"每次拦截约 55 µs"是稳定的，"倍数"不是**。同一个 workload 在另一台基线更慢的机器上，拦截次数没变、绝对值没变，但算出来的倍数会明显更大（更慢的基线让同一份绝对开销显得更夸张）。所以工程上要记的是"每次拦截的代价"，而不是某个倍数。

第三条（行为改变）最容易被忽略：`netem` 注入 50 ms 延迟之后，你观测到的所有 TCP 行为都带着这 50 ms。它不是"在看"，是"在改"。注入类实验只能在可快照的实验机、隔离的网络命名空间里做，并预先设定上限。

## 2. 四个采样盲区

采样类工具（`vmstat`、`iostat`、`perf`、`sar`）看的是"某个瞬间"或"某个窗口"，因此有四个固定的看不见的地方：

### 2.1 盲区一：亚窗口的短脉冲

一次只持续 **0.196 秒**的 1000 MiB 写入（`dd oflag=direct`），在 1 秒采样里可能只落在一个窗口；如果窗口更长（比如 1 分钟聚合），它在图上几乎不存在。而用户感受到的正是那一秒里的请求。

绕过去的方法只有两类：**高频采样**（窗口小于脉冲宽度）或**累积量差分**（`/proc/vmstat`、`nstat`、PSI 的 `total`、cgroup 的 `*_usec` 都只增不减，两个时刻相减不受窗口限制）。短命进程还有第三个办法：让工具跟着进程走（`perf record -- <cmd>`、`strace` 直接启动它），而不是按时间采样。

### 2.2 盲区二：第一行不是"现在的值"

这一条有两层：

- **`vmstat` 与 `iostat` 的首份报告是"自上次重启以来的平均"**（`vmstat` 会用一句 `The first report produced gives averages since the last reboot` 明确写出，`iostat` 同）。看它们时必须从第二行起，或者用 `-y` 省略首份报告。另外 `vmstat` 的 `procs` 与 `memory` 两组在任何情况下都是**瞬时值**，首行也一样；
- **`top` 的首屏则不是自开机平均**。让一个自旋进程跑起来 1 秒后执行 `top -b -n1`：首屏与紧接着的第二屏数值一致，而机器已经开了 87 分钟——说明它算的是很近的一段差分（不同版本、不同采集方式的窗口长度可能不同，判据是"首屏与第二屏接近"而不是某个固定值）。**用 `top` 的首屏当"开机以来平均"会得出完全错误的结论。**

### 2.3 盲区三：不在 CPU 上的时间

`perf record` 的采样对象是"此刻正在 CPU 上执行的任务"，所以进程阻塞在锁、磁盘、下游上的时间**没有样本**。这不是缺陷，是采样原理的必然结果。看到"热点函数很集中、总时间却对不上墙钟"，就该想到其余时间它在等。

要覆盖这段只能换手段：`perf sched`（调度延迟）、off-CPU 的 eBPF 程序、或者最朴素的 `/proc/<pid>/wchan` + 自愿切换差分。前两者需要 root；没有 root 时，`kernel.perf_event_paranoid` 的现场值会直接决定 `perf` 能不能用（它会把自己的取值打进错误信息里）。

### 2.4 盲区四：被聚合掉的长尾

这一条与"平均掩盖尾部"是同一件事，但它的观测含义是：**你选的统计口径本身就在丢信息**。1 分钟平均值丢亚分钟脉冲；p95 丢 p99.9；均值丢分布形状。选择口径之前先判断形态（恒定 / 间歇 / 周期），再决定窗口与分位数。

## 3. 工具不可用时的四种典型

生产上更常见的情况不是"工具不够强"，而是"工具用不了"。四种典型与各自的退路：

### 3.1 有 PMU 设备节点，但读不出计数器

本机 `/sys/bus/event_source/devices/` 下有 `cpu_core`/`cpu_atom`/`msr` 等节点，但 `perf stat -e cycles` 输出 `<not supported>`——原因是 **VMware 没有把 PMU 计数器透传给 guest**。硬件计数器不可用时仍然可用的：任务时钟（`task-clock`）、上下文切换、缺页、迁移等**软件事件**。

**这里有一个必须记住的坑**：`perf record -e cycles` **可能不报错、也写出了文件，但录下来的不是 cycles**——本机就是这样：`perf report` 的标题写着 `event 'task-clock'`、`perf evlist` 也只列出 `task-clock`，而同一台机器上 `perf stat -e cycles` 明明报 `<not supported>`。

要准确描述这件事：perf 的源码里**没有**"事件不支持就换一个软件事件"的通用回退（不支持时是跳过该事件并告警，全部打不开才报 `No supported events found.` 并非零退出）。本机这台是**混合拓扑**（`cpu_core` 与 `cpu_atom` 两个 PMU），`-e cycles` 落在 `cpu_core` 上；在 PMU 被虚拟化层挡住的情况下，最终记录下来的事件名变成了 `task-clock`。所以**结论与判据不变，但原因不是"通用回退"**：

- 判据只有一条：先看 `perf stat -e <event>` 有没有 `<not supported>`；
- "命令成功、文件写出、样本数非 0"三者都不能作为"硬件计数器可用"的证据，必须回头看 `perf report` / `perf evlist` 里**实际记下来的事件名**；
- 反过来也要注意：**不写 `-e` 时 perf 的默认事件列表本来就同时包含软件事件**（`task-clock`、`context-switches`、`page-faults`…），看到软件事件是正常的默认行为，不要误读成"回退失败"。

还有一处与权限无关的失败：本机裸 `perf stat` 直接以 `Invalid event (cpu_core/TOPDOWN.SLOTS/) in per-thread mode` 退出（即便把 `perf_event_paranoid` 调到 1 也一样）。这是 perf 在这类混合拓扑上的默认事件选择问题，不是"没有权限"。

### 3.2 没有权限做内核观测

本机默认值（现场取）：`kernel.perf_event_paranoid=4`、`kernel.dmesg_restrict=1`、`kernel.unprivileged_bpf_disabled=2`、`kernel.apparmor_restrict_unprivileged_userns=1`。后果分别是：

- 普通用户用 `perf` 直接失败（错误信息里会打印 `perf_event_paranoid setting is 4`）；
- 普通用户 `dmesg` 被拒（`Operation not permitted`），**退路是 `journalctl -k`**；
- 非特权 BPF 被禁用（`bpftrace` 需要 root）；
- 非特权用户命名空间被 AppArmor 拒绝，所以**网络注入不能用 `unshare -U -r -n`，要用 root + `ip netns`**。

这里的取值有一处容易引错，值得说清：**`perf_event_paranoid` 的上游文档（`Documentation/admin-guide/perf-security.rst` 与 `Documentation/admin-guide/sysctl/kernel.rst`）只写到 `>= 2`**，并没有 `3`；`3` 是 Debian 2016 年加的补丁，`4` 是 Ubuntu 的发行版补丁（本机这两个值在访问控制上落在同一档，因为内核判定用的是 `> 2`）。所以引用"某个值代表什么"时，要么引上游文档（最多到 2），要么写清是哪个发行版补丁引入的——**别把 3 或 4 写成上游语义**。

没有 root 时的可行路径：`/proc` 下的只读文件（`status`、`sched`、`io`、`limits`、`smaps_rollup`）、`vmstat`/`mpstat`/`pidstat`/`iostat`/`ss`/`nstat`、以及应用自己暴露的指标与日志。注意 `/proc/<pid>/stack` 需要 `CAP_SYS_ADMIN`——普通用户读会得到 `Permission denied`。

### 3.3 `dmesg_restrict=1` 与"内核日志取不到"

常见的错误写法是把两个来源串成 `dmesg … || journalctl -k …` 这样的兜底。**这里的 `||` 取的是管道最后一个命令的退出码**，而那个退出码通常是 0（例如 `tail` 或 `head`），所以兜底分支永远不会执行——内核日志被静默丢掉，而你以为已经取到了。

正确的思路是**先判断"这个来源能不能读"，再取**：先确认 `/dev/kmsg` 是否可读、`dmesg` 是否返回 0，据此决定走 `dmesg` 还是退到 `journalctl -k`。按这个思路自己写的判断语句不需要复杂，但**不要用管道后的 `||` 兜底**——那是最容易在故障现场骗过自己的写法。

### 3.4 缺的是"分析脚本"，不是"工具本体"

火焰图的三步是：采样（`perf record -g`）→ 出栈（`perf script`）→ 折叠并画 SVG（`stackcollapse-perf.pl` + `flamegraph.pl`）。前两步只要 `perf` 能用就能做，输出是一堆调用栈文本；**只有最后画 SVG 那一步依赖那两个官方脚本**。这种情况下正确做法是：如实写明"没装脚本"，并给出替代——直接把折叠后的"栈;栈 计数"列表当文本报告用，它已经能回答"热点在哪个调用路径"。

同理，缺一个工具的**某个功能**不等于缺这个工具。`ethtool -l ens33` 在本机报 `Operation not supported`（VMware 模拟的单队列 `e1000`），但 `ethtool -S`、`ethtool -k` 可用——**不要因为一个子命令不支持就宣布整类方法不可用**。

## 4. 降级阶梯

每个观测目标都该有一条退路。按"从低代价到高代价"排，同级里优先选只读的：

| 想知道 | 首选 | 没 root / 没权限时 | 都没有时 |
| --- | --- | --- | --- |
| 谁在花 CPU | `pidstat -u -t` | 同左（只读） | 应用自身的耗时埋点 |
| 在哪一行代码热 | `perf record` + `report` | 无法（`perf_event_paranoid`） | 应用 profiler、日志耗时 |
| 哪个系统调用多 | `strace -c` | 同左，但要限时限进程 | 应用埋点、`/proc/<pid>/io` 差分 |
| 进程在等什么 | `/proc/<pid>/stack`（需 root） | `/proc/<pid>/wchan` + 切换差分 | 应用日志里的等待点 |
| off-CPU 时长 | `perf sched` / off-CPU eBPF（需 root） | 无法量化，只能定性 | 下游服务的耗时指标 |
| 设备排队 | `iostat -x` | 同左 | `sar -d` 的历史数据 |
| 内存压力 | `/proc/pressure/memory` | 同左 | `/proc/vmstat` 的回收/换页计数 |
| 有没有被配额掐 | cgroup `cpu.stat`（宿主侧只读） | 同左 | 容器内看不到——只能间接推断 |
| 报文级证据 | `tcpdump`（限时限量落盘） | 无 | `ss -ti` + 协议栈计数器 |

**这条阶梯的用法是"事先知道"**，不是出事时现找。演练记录里要写清本机哪些工具可用、哪些被权限或硬件挡住、替代路径是什么。

## 5. 三条取证纪律

1. **先取证，再动手**。重启、杀进程、改参数都会毁掉现场，而性能问题的现场往往只出现一次。唯一例外：影响面还在扩大、且不需要现场就能确定动作时可以先止损——但要**同时**记录时间、动作和当时的指标；
2. **记录命令与原始输出**。`script -f session.log`、`| tee`、`date -Is` 打时间戳。只抄一个数字的笔记在复盘时几乎没用，因为它没有窗口与命令；
3. **最小影响优先**。先只读、先整机、先低频率；只有在前面的证据指向明确时，才升级到逐调用拦截或高频采样，并且必须限时（`timeout`）、限范围（`-e trace=`、`-c`、`-p <pid>`）、限量（`-c 12`、`-w file`）。

**第一反应不要做什么**：不要在没记录现状之前重启或改参数；不要在没限时限量的情况下把插桩工具长时间挂在生产进程上；不要把"工具报错、没有输出、只报一个零"当成"没有问题"——那三种情况里至少有一种是"你根本没取到证据"。

## 常见误解

| 说法 | 事实 |
| --- | --- |
| "看一眼不花钱" | 插桩类工具的代价与事件次数成正比（本机每次拦截约 55 µs，4 万次调用把 51 ms 变成 2254 ms） |
| "记倍数就行" | 倍数随被测程序基线浮动（同 workload 在另一台机器上是约 80 倍）；要记的是每次拦截的代价 |
| "`perf stat` 没报错就说明事件可用" | 本机裸 `perf stat` 直接报错退出；`perf record -e cycles` 录下来的事件名却是 `task-clock` |
| "`perf` 采不到的时间说明它不重要" | CPU 采样看不到 off-CPU 的时间；"等"的时间可能才是主要部分 |
| "`top` 首屏是开机以来的平均" | 首屏与第二屏接近、而机器已开机很久，说明它算的是很近的差分 |
| "`vmstat`/`iostat` 每行都是同样的窗口" | 首份报告是自上次重启以来的平均；用 `-y` 省略 |
| "工具没输出就是没问题" | 也可能是取不到（权限、`<not supported>`、被限流、管道后的 `||` 兜底失效） |
| "没有 root 就什么都做不了" | `/proc` 只读文件 + sysstat/ss/nstat + 应用指标仍能覆盖大部分分层判断 |
| "注入实验和观测一样，做完就完" | 注入永久改变了现象；只能在隔离环境做，并预先设定上限与清理复核 |
| "抓包最准，先抓再说" | 抓包有代价、需要限时限量；计数器优先 |

**第一反应不要做什么**：不要在没记录现状之前动手；不要用 `strace -f -p` 长时间挂着生产进程；不要把"工具报错/无输出"当成"没有问题"；不要在宿主机上做没有隔离的注入实验。

## 要点自测

**问：为什么 `strace` 的倍数是浮动的，"每次拦截约 55 µs"才是稳定的？**
答：代价与事件次数成正比，与被测程序自身的基线无关。基线越快，同样的绝对开销显得倍数越大（同一 workload 在一台机器上约 45～48 倍，在另一台上约 80 倍）。

**问：`perf record` 为什么看不到进程等锁的时间？换成什么手段？**
答：它采样的是"此刻在 CPU 上执行的任务"，阻塞的任务没有样本。换 `perf sched` 或 off-CPU eBPF（都需要 root），没有 root 时退到 `wchan` + 自愿切换差分。

**问：`vmstat`、`iostat`、`top` 的首行/首屏语义有什么不同？**
答：`vmstat` 与 `iostat` 的首份报告是"自上次重启以来的平均"（`vmstat` 的 procs/memory 两组例外，任何情况下都是瞬时值）；`top` 的首屏是"很近的一段差分"。用错会得到相反的结论。

**问：怎么可靠地判断 `perf` 的某个硬件事件能不能用？**
答：只看 `perf stat -e <event>` 有没有 `<not supported>`，并回头核对 `perf report` / `perf evlist` 里**实际记下来的事件名**。本机 `perf record -e cycles` 命令成功、文件写出，但录下来的是 `task-clock`——命令成功、文件写出、样本非 0 都不能作为证据。

**问：一个亚秒级的 IO 脉冲，怎么保证不被采样漏掉？**
答：用累积量差分（`/proc/vmstat`、`nstat`、PSI `total`、cgroup `*_usec`）或把采样窗口压到脉冲宽度以下；短命进程还可以让工具跟着它跑（`perf record -- <cmd>`）。

**问：为什么"内核日志取不到"经常是写法问题？**
答：`dmesg ... || journalctl -k ...` 里的 `||` 取的是管道最后一个命令的退出码（通常为 0），兜底分支永远不执行。要先显式判断能不能读，再决定来源。

**第一反应不要做什么**：不要在取证之前重启或改参数；不要在没限时限量的情况下用插桩工具；不要把权限不足当成"没有问题"。
