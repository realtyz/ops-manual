## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **没有量化的「慢」无法验证是否修好。**
>   - 怎么验证：把结论写成「p99 从 60 ms 涨到 900 ms、持续 22 分钟、影响 3 个实例」这样一句可复查的话；写不出来的，说明还没量化。
> - **影响面要问「谁、多严重、从几点开始、还在不在、和什么比」。**
>   - 证据：本机一次完整的只读取证输出只有 3474 字节，却同时给出了 `load average`、每进程 CPU 排序、PSI、内存、套接字与软中断，足以回答前四问。
> - **时间点必须和变更对齐，而且先确认时钟。**
>   - 怎么验证：`date -Is` 记下带时区的采集时刻，把它和发布/配置/数据量增长的时间戳放在同一条时间线上；时钟不同步时不下「谁先谁后」的结论。
> - **「慢」有三种形态，形态决定采样策略。**
>   - 证据：本机写 1000 MiB 的 `dd` 只持续 1～2 秒，1 秒间隔的 `pidstat -d` 完全漏掉；对间歇尖刺必须换更密的采样或改看直方图。
> - **一次性取证：一条命令同时刻抓齐，不要「看一眼再想看第二次」。**
>   - 怎么验证：脚本产出被 `tee` 到文件，事后可以逐行复核；重启或进程退出后这些数字就再也取不到了。

## 1. 五个必答问题

任何性能故障，先答完这五问再碰工具下面更深的东西。答不出来的项要显式记成待办，而不是跳过。

| # | 问题 | 具体到能回答什么程度 | 现场怎么取 |
| --- | --- | --- | --- |
| 1 | **谁受影响？** | 哪些服务/实例/用户/接口；是全部还是一部分（按机房、按版本、按客户） | 应用指标与大屏、报障记录、`ss -s` |
| 2 | **多严重？** | 延迟分位数、错误率、吞吐各变了多少；和 SLO / 基线比差多少 | 延迟与错误率指标、`SLO 剩余错误预算` |
| 3 | **从几点开始？** | 有明确时间点（能对齐到分钟）；是突变还是渐变 | 指标拐点、`date -Is` 与变更记录 |
| 4 | **还在持续吗？** | 持续 / 周期性 / 已恢复；恢复后还复现吗 | 连续采样 2～3 个周期 |
| 5 | **和什么比？** | 与基线（业务高峰/低谷）、与同类实例、与上一小时比 | 基线卡（子笔记 12）、同类实例对照 |

第 5 问最容易被跳过，而它恰恰是「能不能得出结论」的关键——**没有比较对象，你只能描述现象，不能证明异常**。

## 2. 「多严重」怎么量化

### 2.1 三个口径一起看

| 口径 | 变差的含义 | 注意 |
| --- | --- | --- |
| **延迟分位数**（p50/p95/p99） | 用户感受到的变慢程度 | 优先看 p99；平均会掩盖长尾 |
| **错误率**（5xx、超时、重试率） | 已经失败的部分 | 错误率上升往往比延迟上升更值得先止损 |
| **吞吐**（QPS、MiB/s） | 系统实际完成的工作量 | 吞吐不变而延迟上升，通常意味着排队或下游拖慢 |

### 2.2 有 SLO 用 SLO，没有 SLO 用基线

- **有 SLO**：直接换算成「错误预算消耗速度」——是每秒烧掉 1 小时预算、还是 1 天，这决定了你要立刻叫醒谁。
- **没有 SLO**：退回到基线对比。基线至少要包含「同一时段、同一业务量」下的一份正常水位（子笔记 12 给出五组基线的采集模板）。
- **两样都没有**：此时最重要的事情不是继续查，而是**先把当前状态记下来当基线**，并向上要一个「什么算不正常」的定义。

### 2.3 一句话结论模板

写完这五问之后，用一句话总结，方便对上级和同事同步：

```text
【现象】订单服务 p99 从基线 120 ms 涨到 900 ms（约 7.5 倍），5xx 从 0.1% 涨到 2.3%；
【范围】3 个实例中的 2 个（都跑在 host-A），其余正常；
【起点】14:32 开始，14:35 达到平台期，目前仍在持续；
【对比】同为高峰时段的昨天同期 p99 是 130 ms；
【当前动作】只读取证中，未做任何变更。
```

## 3. 对齐时间点：把「拐点」和「变更」放在一条线上

### 3.1 三类要对齐的信息

| 类别 | 例子 | 在哪找 |
| --- | --- | --- |
| **我方变更** | 发布、扩缩容、配置变更、定时任务、备份窗口、证书轮换 | 发布系统、变更记录、`systemctl list-timers` |
| **外部变化** | 流量突增、大客户活动、上游依赖变慢、DNS/TLS 变更 | 业务数据、依赖方公告 |
| **环境变化** | 宿主机同租户压力、网络抖动、磁盘水位、内核参数 | 宿主侧指标、`/proc/pressure/*`、`df` |

### 3.2 先确认时钟

跨系统对比时间前必须确认时钟：`date -Is`、`timedatectl`、`timesync-status`（阶段 8 有完整的时间基线核查，阶段 9 讲了日志与指标的时间戳格式）。**时钟不同步时不要下「谁先谁后」的结论**——先后顺序错一步，因果链就整个反过来。

### 3.3 时间线模板

```text
14:30  发布 v2.31（变更单 #4412）
14:31  宿主机磁盘水位告警（85% → 91%）
14:32  订单服务 p99 开始上升
14:36  监控告警触发
14:38  排障开始，只读取证
14:41  p99 稳定在 900 ms 左右，未继续恶化
```

把这张时间线写下来，你就能第一时间发现「拐点和变更只差 1～2 分钟」这种关键线索；也能避免事后凭记忆编时间线。

## 4. 生产动作：一次性取证快照

### 4.1 为什么是「一次性」

故障现场有时间窗。三个理由让「先跑一次全量快照」比「想到什么敲什么」更好：

1. **同一时刻的数字才对得上。** 分三次采集的 `vmstat`、`iostat`、`ss` 数据可能来自三个不同压力状态，无法互相印证。
2. **现象可能已经过去。** 尖刺、瞬时排队、连接堆积都是短命状态。
3. **统一留档。** 一份带时间戳的文件可以进事故复盘材料，也是六段报告里「证据」那一节的素材。

### 4.2 脚本（只读、低开销，生产机上可以跑）

```bash
#!/usr/bin/env bash
set -u
out=${1:-/tmp/perf-snapshot-$(date +%Y%m%d-%H%M%S)}
mkdir -p "$out"
{
  echo "=== identity ==="; date -Is; uptime; echo "nproc=$(nproc)"; cat /proc/loadavg
  echo "=== vmstat ==="; vmstat 1 5
  echo "=== top cpu ==="; ps -eo pid,ppid,user,stat,etime,pcpu,pmem,args --sort=-pcpu | head -15
  echo "=== pressure ==="; grep -H . /proc/pressure/* 2>/dev/null
  echo "=== meminfo ==="; grep -E "^(MemTotal|MemAvailable|SwapTotal|SwapFree|Dirty|Writeback|Slab)" /proc/meminfo
  echo "=== sockets ==="; ss -s
  echo "=== nstat ==="; nstat -az 2>/dev/null | grep -E "^(TcpRetransSegs|TcpExtListenOverflows|TcpExtTCPTimeouts|TcpActiveOpens|IpInReceives)"
  echo "=== softnet ==="; awk '{s+=$2} END{print "dropped", s}' /proc/net/softnet_stat
  echo "=== io (per device) ==="; command -v iostat >/dev/null && iostat -x 1 3 || echo "iostat 不可用"
  echo "=== kernel log ==="; dmesg -T 2>/dev/null | tail -20 || journalctl -k -n 20 --no-pager
} | tee "$out/snapshot.txt"
echo "已写入 $out/snapshot.txt"
```

七个使用要点：

1. **全程只读**：`date`/`uptime`/`ps`/`cat /proc/*`/`ss`/`nstat`/`dmesg` 都是 L0/L1 手段，不改变系统状态。
2. **`vmstat 1 5` 与 `iostat -x 1 3` 有窗口**：它们会花掉几秒，跑完把「采样窗口」写进结论里。
3. **`ps` 排序取前 15**：再多会淹没信号，也更容易暴露无关进程名。
4. **`dmesg` 是否需要 root 取决于 `dmesg_restrict`**：本机为 `0`，非 root 可读；为 `1` 时退到 `journalctl -k`。
5. **缺工具就降级**：脚本用 `command -v` 判断，`iostat` 不在时打印一行说明，而不是让整个脚本失败。
6. **落盘并保留**：输出被 `tee` 到文件，便于事后逐行复核与随事故单归档。
7. **按需追加**：如果是 IO 类问题追加 `pidstat -d 1 3`，如果是网络类追加 `ss -ti | head -40`，如果是容器类追加对应 cgroup 的 `cpu.stat`/`memory.events`（子笔记 11）。

### 4.3 本机实测输出

```text
$ ./snapshot.sh /tmp/perf-snap-lab
=== identity ===
2026-09-19T13:23:05+08:00
 13:23:05 up 1 min,  1 user,  load average: 0.04, 0.01, 0.00
nproc=24
0.04 0.01 0.00 1/371 1453
=== vmstat ===
 r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st gu
 1  0      0 14973376  55520 766904    0    0  3531  2474 2626    0  0  0 100  0  0  0
...
=== sockets ===
Total: 184
TCP:   10 (estab 0, closed 7, orphaned 0, timewait 7)
...
=== softnet ===
dropped 0
$ wc -c snapshot.txt

```

这份输出本身就能回答不少问题：`nproc=24` 与 `load 0.04` 说明整机不忙；`r=1 / b=0` 说明没有可运行队列也没有 D 状态堆积；PSI 的 memory 全 0 说明没有内存压力；`softnet dropped 0` 说明收包侧没有丢。

> [!warning] 快照只能证明「此刻」
> 一次性快照是**起点**，不是结论。它最大的价值是给出「哪一层像、哪一层不像」的初筛，以及一份可比对的历史锚点。真正的定位要靠后续按形态选择的采样与下钻（子笔记 05～08）。

## 5. 同时就把「基线」记下来

认领阶段顺手做一件收益极高的事：**把当前状态当作基线记录下来**。哪怕这次是排查故障，等它恢复之后，这份「故障态」和后面的「正常态」对比，就是以后最有用的基线之一。

最少记这五项（完整模板见子笔记 12）：

```text
采集时间：2026-09-19T13:23+08:00   采集条件：批处理任务运行中，无其它负载
身份与规模：24 vCPU / MemTotal 15844 MiB / 根分区 /dev/sdd ext4 / 无独立数据盘
CPU 与负载：load 0.12 / 单核峰值 100%（CPU 2）/ %usr 4.17%
内存：MemAvailable 15175 MiB / PSI memory some=0
IO：iostat w/s 555、w_await 6.85 ms、aqu-sz 3.81、%util 14.40%
网络：ss -s timewait 7 / softnet dropped 0 / nstat 无重传
```

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 「先看看 `top`，回头再量化」 | `top` 给的是整机与历史平均；不如先花 10 秒写下五问 |
| 「用户说慢就是慢」 | 没有量化就没有验收标准，修完之后无法证明修好了 |
| 「先重启恢复业务，问题不大」 | 现场与证据一起消失；同一故障再次发生时你仍然一无所知 |
| 「几个指标分开看，想到哪个看哪个」 | 不同时刻的证据无法互相印证；应尽量同一时刻采集 |
| 「没有 SLO 就不需要定严重程度」 | 至少要给出基线对比或同类实例对照，否则「多严重」没有答案 |
| 「时间差不多就行」 | 拐点与变更差 1～2 分钟是强线索；时钟不同步时这条线索直接失效 |
| 「快照跑完就完事了」 | 快照是初筛与锚点，定位要靠按形态选择的后续采样 |
| 「顺手把当前状态也记下来没必要」 | 故障态快照是最有价值的基线之一，恢复后通常再也取不到 |

## 决策练习

**场景**：周一早上 9:05，你收到告警「支付服务 P99 延迟 > 500 ms（持续 3 分钟）」。你登上跳板机，机器上没有任何监控面板的权限，只有命令行。

**选项**：

- **A. 立刻 `top` 看哪个进程 CPU 高，然后把最高的那个重启。**
- **B. 先跑一次性取证快照并留档，同时给出一句话结论（现象/范围/起点/对比/当前动作），再按 05～07 的路径分层排除。**
- **C. 先查昨天的变更记录，如果是发布导致就立刻回滚。**

**为什么选 B**：B 覆盖了认领阶段的两个核心动作：**留下证据**（快照）和**说出影响面**（一句话结论）。有了这两样，后面的分层排除才有依据，回滚这类高代价动作也才有验收标准（回滚之后同一组指标要能回落）。

**为什么不选 A**：重启是最贵的一步，而且会毁掉现场；`top` 只给整机视角，「最高的那个进程」在 24 核机器上可能只是正常波动。

**为什么不选 C**：查变更是对的，但顺序不对。「查变更」是第 3 步（对齐时间点），前置条件是「知道故障从几点开始」。如果一开始就去翻变更记录，很容易被「昨天确实发过版」带偏，把无关变更当成根因。正确做法是先固定现象与时间点，再拿变更去对齐——两个方向的信息合起来才构成证据。

## 要点自测

> [!question]- 接到「服务变慢」，头 5 分钟要问出哪五个问题？
> - 谁受影响（范围）、多严重（分位数/错误率/吞吐 vs SLO 或基线）、从几点开始（能对齐到分钟）、还在不在（持续/周期/已恢复）、和什么比（基线/同类实例/上一时段）。
> - 第 5 问最容易被跳过，但没有比较对象就只能描述现象、不能证明异常。
> - **第一反应不要是什么**：不要还没量化就先去「优化」或重启。

> [!question]- 没有 SLO、也没有历史基线时，怎么判断严重程度？
> - 用「同类实例对照」：同一集群里其它副本是否正常，能快速区分「全局问题」与「单实例问题」。
> - 用「时间对照」：与昨天同时段、上周同日比。
> - **更重要的是把当前状态记下来当基线**，并向上要一个「什么算不正常」的定义。

> [!question]- 为什么一次性取证脚本要「一条命令同时刻抓齐」？
> - 分次采集的数字来自不同压力状态，无法互相印证（例如 `vmstat` 说没队列、`iostat` 却显示深队列，可能只是采集时刻不同）。
> - 短命现象可能已经消失；统一留档还能直接进事故复盘与六段报告。
> - 本机实测这一份输出 3474 字节，覆盖身份、负载、每进程 CPU、PSI、内存、套接字、软中断与内核日志。
> - **第一反应不要是什么**：不要在故障中一边想一边敲，事后只剩零散的截图。

> [!question]- 为什么「对齐时间点」是第 1 站而不是最后一站？
> - 拐点与变更的时间差（1～2 分钟还是 6 小时）直接决定「是不是变更导致的」，这是性价比最高的线索。
> - 时间线是六段报告的第一段，事后再补通常只能凭记忆。
> - 前提是时钟对齐：跨系统比较前用 `date -Is` / `timedatectl` 确认，时钟不同步时不下结论。

> [!question]- 「间歇尖刺」和「恒定慢」在取证策略上有什么不同？
> - 恒定慢：随时采一次就够，1 秒间隔的 `vmstat`/`iostat` 即可。
> - 间歇尖刺：采样间隔必须小于尖刺宽度，或改看设备层聚合与直方图；本机实测 1～2 秒的 `dd` 会被 1 秒采样整个漏掉。
> - 周期性慢：采样窗口要覆盖 2～3 个周期，否则会把周期波动误读成偶发。
