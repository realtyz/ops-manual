# 争抢为什么不按比例缩放

四核的机器上，一颗核已经贴到 100%，整机 `%usr` 却只有 25%；再加一个同样吃满的进程上去，第二个进程的算力不是"减半"，而可能只剩原来的五分之一。这两件事背后是同一条机制：**CPU 的时间是排他资源，多个任务争用同一颗核时，代价不是线性分摊的。**

以下几组读数取自一台 4 vCPU（Intel 混合拓扑：2 socket × 2 core，`cpu_core` 与 `cpu_atom` 两个 PMU）、`MemTotal` 7894 MiB、内核 6.8 的 Ubuntu 24.04 虚拟机；`%steal` 在该机上恒为 0，所以"宿主超卖"这一路没有可用的证据，涉及它的结论不在下面的数据之内。

## 1. 卖出去的是时间，不是核

调度器能分配的只有时间。同一颗核上的两个同等优先级任务，谁也不能同时运行，于是各自的完成速度都乘以一个折扣。这个折扣由**争抢程度**决定：

**争抢程度 = 同一时刻想跑的任务数 / 可用的核数**

Linux 默认的 CFS（Completely Fair Scheduler，完全公平调度器）在这个比值上的行为是"按权重公平地分时间片"。所以：

- 比值 ≤ 1：没人争，任务该跑多久就跑多久；
- 比值 = 2：两个任务各拿一半的时间；
- 比值 = 16：每个任务拿十六分之一的时间，而且**每个任务每次被唤醒都要排在队尾**，延迟不只是变长，是变得不可预测。

这里有个容易搞错的地方：**"核数"指的是"你能用到的核"，不是 `nproc`**。`taskset -cp` 显示亲和性被限制、cgroup 的 `cpu.max` 设了配额、容器只给了 2 个 vCPU——这些都会让"实际可用核数"小于机器上的核数。容量与余量都要按**实际可用**算。

## 2. 争抢的代价：吞吐按份额掉，尾部先坏

把同一段固定计算循环绑在一颗核上（`taskset`），先让它独占，再往同一颗核上逐步加同样的任务，每组取 2 秒：

```text
# 说明：数值仅示意、不代表你的机器（同一颗核上的同一个 2 秒计算循环）
独占：        26,473,519 次 / 2.00 s
1 个竞争者：  12,461,811 次 / 2.00 s      # −52.9%
4 个竞争者：   5,564,871 次 / 2.00 s      # −79.0%，只剩约 1/5
```

一个竞争者就带走约一半——因为时间被对半分了；加到 4 个时只剩约五分之一，比例之外的那部分损失来自调度与相互干扰。同样的条件下，用 8 ms 定时唤醒的延迟探针测同一颗核上的延迟分布（每组 n=300）：

| 同核任务数 | p50 | p95 | p99 | max |
| --- | --- | --- | --- | --- |
| 1（独占） | 8.13 ms | 8.25 ms | 8.34 ms | 8.36 ms |
| 2 | 8.06 ms | 8.10 ms | 8.11 ms | 10.82 ms |
| 5 | 8.06 ms | 10.99 ms | 11.02 ms | 16.58 ms |
| 15 | 8.06 ms | 10.01 ms | 11.00 ms | **40.87 ms** |

三点判读：

- **吞吐按份额下降，延迟按排队的形状上升**。吞吐是"分到多少时间"的直接体现；延迟还多了一层"什么时候轮到我"。
- **中位数对这件事几乎无感**（8.13 → 8.06 ms），尾部才是现场。这也是为什么同核争抢型故障常常被描述成"偶尔卡一下"。
- **CFS 的唤醒抢占让"1 个竞争者延迟就翻倍"这种说法不成立**：刚被唤醒的任务倾向于立刻抢占当前任务，所以 2 个任务时 p50 甚至更低；真正的恶化出现在任务数继续上升之后。

这段实验里还有一个必须记住的对照：**整个过程里整机视角始终是 `%usr ≈ 25%`**。原因很简单——4 颗核里只有 1 颗在忙。所以：

**判断 CPU 余量的判据不是整机利用率，而是"最热的核还剩多少"。**

## 3. load average 在数什么，不在数什么

`/proc/loadavg` 的前三个数是指数滑动平均，窗口分别是 1、5、15 分钟。它们统计的是**可运行与不可中断（D 状态）任务的平均数量**——不只是 CPU 上的任务。

精确一点说，内核按 `nr_running + nr_uninterruptible` 累加（`kernel/sched/loadavg.c` 的文件头注释原文是 `an exponentially decaying average of nr_running + nr_uninterruptible`），所以**被 `kill` 得掉的不可中断睡眠（`TASK_KILLABLE`，它按位包含 `TASK_UNINTERRUPTIBLE`）也计入**。但有一类刻意不计：**`TASK_IDLE`（`TASK_UNINTERRUPTIBLE | TASK_NOLOAD`）**——`TASK_NOLOAD` 的语义就是"不要计入 load"，所以内核里那些用 `TASK_IDLE` 等待的工作线程**不会**推高 `load`。判断一个 D 状态任务算不算在 `load` 里，看它的状态位而不只看那个 `D` 字母。

这带来三个必须记住的性质：

1. **要除以核数才有意义**：4 核机上 `load 4` 意味着"平均有 4 个任务想跑"，大致相当于所有核都排着队；24 核机上 `load 4` 什么都不算。
2. **它包含 D 状态**：所以 `load` 高而 CPU 空，最常见的解释不是"CPU 有问题"，而是"有任务卡在 IO 里"。这是负载与利用率分离的根源。
3. **它只是一个粗信号**：一个持续满载的任务，长期看大约给 `load` 加 1；但因为它是 1 分钟尺度的指数平均，**刚起来几秒的任务几乎推不动它**——所以"`load` 只有零点几"与"已经有一颗核打满"完全可以同时成立。

```text
# 说明：数值仅示意、不代表你的机器（4 核机器，一颗核已被打满）
Average:     all   25.04  ...  74.96        # 整机平均：看着还有四分之三
Average:       2  100.00  ...   0.00        # 逐核：这一颗已经没有余量
load average: 0.34, ...                     # 1 分钟尺度，几乎没动
```

判据：`load / 核数` 长期大于 1 说明有排队；但**"load 低"永远不能作为"CPU 没排队"的证据**——要看逐核利用率和运行队列（`vmstat` 的 `r` 列，字段读法见《体系：一次性能故障的处置》）。

## 4. 上下文切换：两种，含义完全相反

任务被换下 CPU 有两种原因：

| 类型 | 含义 | 高说明什么 |
| --- | --- | --- |
| 自愿切换（voluntary context switch） | 任务主动让出 CPU：等 IO、等锁、`sleep` | 它在等什么东西。等的是什么要往下钻（`wchan`、`futex`） |
| 非自愿切换（involuntary context switch） | 被调度器抢占：时间片用完、有更高优先级任务 | 有争抢，或者优先级设置不合理 |

两个极端的对照（同一台机器上的两类任务）：

```text
# 说明：数值仅示意、不代表你的机器
# 阻塞式 socket ping-pong：自愿切换约 4 万次/秒，非自愿只有十几次/秒
voluntary_ctxt_switches:        199827
nonvoluntary_ctxt_switches:     94

# 对照：纯计算自旋进程
voluntary_ctxt_switches:        0
nonvoluntary_ctxt_switches:     16
```

所以 **"`cs` 高但 CPU 空"是自愿切换高**：任务不是在算，是在等。而"锁竞争"正是这一类里最隐蔽的一种——它不消耗 CPU，所以整机利用率很低，但吞吐上不去、延迟在排队。

读法上要注意：`/proc/<pid>/status` 里的两个切换计数是**自进程启动以来的累计值**，要看速率必须取两次读数做差分；`pidstat -w` 直接给的就是"每秒次数"，但它是窗口平均，会漏掉短脉冲。

这也是同核争抢最容易被忽略的后果：**争抢不只让你算得慢，还会把"等锁"的时间放大**。一个持锁的线程被换下去，等着的那几个线程的等待时间就直接受调度延迟支配。

## 5. 为什么 4 vCPU 的机器上「并行度调到 16」会更慢

把上面的关系合起来看：并行度（同时想跑的任务数）超过可用核数之后，每一个增量任务都在做三件事：

1. **稀释别人的时间份额**（吞吐）；
2. **加长每个任务的排队时间**（延迟尾部）；
3. **增加调度与同步开销**（切换、缓存与 TLB 抖动、锁争用更频繁）。

第三项是"为什么不是线性的"的答案：超过核数的并行度不会增加总吞吐，只会增加切换次数和相互干扰。系统的总吞吐上限由**核数**决定，其余部分换来的是延迟与开销。所以：

- 调大线程池/`worker` 数，只在"任务经常在等 IO"时有收益；
- 对计算密集的任务，"核数 + 1 到 2"就够，再往上通常是负收益；
- 反过来，看到 `cs` 很高、CPU 不忙、吞吐上不去，先怀疑**并行度超过了核数或抢锁**，而不是先怀疑机器慢。

这条关系也有一个更一般的表述（Amdahl 定律，阿姆达尔定律，Amdahl 1967）：如果一个任务里有比例 `p` 的部分必须串行执行，那么可用的加速上限就是 `1/p`，加再多并行度也越不过去。排障时它的用处是提醒你：**先找那个串行的部分**（一把全局锁、一个单线程下游、一个写热点），而不是加线程。

## 6. 另一种缩放失败：被配额掐住

cgroup 的 CPU 配额（`cpu.max`，或 systemd 的 `CPUQuota=`）造成的现象与"核不够"极像，但机制完全不同：**它不是让你排队，而是按周期记账，用超了就强制停下。**

这条路径的机制是**按周期记账**：内核把时间切成固定长度的周期（默认 100 ms），每个周期只允许该 cgroup 用掉配额那么多 CPU 时间，用超了就强制停下等到下一个周期。数值上表现为两件事同时发生：

| 观察项 | 配额 20% 时 | 说明 |
| --- | --- | --- |
| 计算吞吐 | 降到不限流时的 **19.30%** | 配额是**硬上限**，不是建议值 |
| 被掐的周期比例 | 21 个周期里被掐 **20 个** | 说明是持续掐，不是偶尔踩线 |

判读：**配额管的是整个 cgroup，不是一个线程或一颗核**。

两个容易误判的后果：

- **瓶颈被搬到了单线程上**。即使机器还有空闲的核，整个服务也只能用掉配额那么多 CPU；这时候容器里 `top` 显示的"利用率不高"完全不能反映真实约束；
- **一次突发的长尾会明显变差**。被掐住的任务不是在等别人让出 CPU，而是要等下一个周期开始，等待时间与周期长度同量级。

判据：宿主侧看 `cpu.stat` 的 `nr_throttled` 与 `throttled_usec` 是否在增长，而不是看容器内的利用率。这条在《体系：一次止损的闭环》里展开。

两个容易误判的后果：

- **瓶颈被搬到了单线程上**。配额是按整个 cgroup 算的，所以即使机器有 4 颗核空着，整个服务也只能用 20% 的一颗核；这时候容器里 `top` 显示的"利用率不高"完全不能反映真实约束；
- **一次突发的长尾会明显变差**。被掐住的任务不是在等别人让出 CPU，而是要等下一个周期开始，等待时间与周期（默认 100 ms）同量级。

判据：宿主侧看 `cpu.stat` 的 `nr_throttled` 与 `throttled_usec` 是否在增长，而不是看容器内的利用率。这条在《横切：容器与服务视角》里展开。

## 常见误解

| 说法 | 事实 |
| --- | --- |
| "整机 CPU 才 25%，还有 3 个核的空闲" | 空闲的核不能被已经绑核或已经饱和的单线程用上。判据是最热核的余量 |
| "`load` 低，CPU 肯定没排队" | `load` 是 1/5/15 分钟平均，单核打满只加约 1。它也不是使用率 |
| "同核加一个竞争任务，延迟立刻翻倍" | CFS 唤醒时会倾向抢占当前任务，2 个任务时 p50 反而可能更低；恶化出现在更高并行度 |
| "加线程能提高吞吐" | 超过核数之后总吞吐由核数决定，多出来的并行度换成切换与争抢，通常变慢 |
| "`cs` 很高，说明 CPU 很忙" | 可能是自愿切换高，任务在等锁或等 IO。要看是非自愿还是自愿 |
| "`load` 包含了磁盘 IO 在等的任务，所以 `load` 高就是磁盘问题" | D 状态只说明"不可中断地等"，也可能是在等 NFS、等设备、等内核锁；要落到 `wchan` 与设备层证据 |
| "容器里 `top` 显示 30%，容器资源够用" | 配额是整个 cgroup 的硬上限，且会被周期性地掐；判据在宿主侧的 `cpu.stat` |
| "把并行度调到核数的两倍，吞吐会更高" | 计算密集任务的收益在核数附近就到顶，再往上增加的是延迟与开销 |

**第一反应不要做什么**：不要用整机利用率判断 CPU 余量；不要因为 `load` 低就把 CPU 层排除；看到 CPU 不够，不要先加线程或加机器——先确认是**争抢**、是**配额**，还是**根本不该并行**。

## 要点自测

**问：4 核机器上，一颗核打满时整机利用率是多少？为什么这个数字会误导人？**
答：25%。这个数字说明"另外三颗核闲"，不说明"服务不快"——服务可能正被绑在那颗核上，或者受制于一个单线程瓶颈。

**问：为什么加一个同核竞争者，吞吐掉 52.9% 而 p50 几乎不动？**
答：吞吐反映分到的时间份额，直接按份额下降；p50 反映的是典型请求的等待，2 个任务时 CFS 的唤醒抢占让中位数仍然接近独占水平。恶化的部分先在尾部（`max`）出现。

**问：`load average` 里为什么会包含不在 CPU 上运行的任务？这对排障有什么后果？**
答：它统计可运行 + 不可中断（D 状态）任务。后果是 `load` 高与 CPU 忙是两件事：`load` 高而 CPU 空往往指向 IO 或内核态等待，必须落到 `wchan` 与设备证据。

**问：`cs` 高但 CPU 空，`voluntary` 与 `nonvoluntary` 哪个高？各指向什么？**
答：自愿高指向"在等"（锁、IO、下游）；非自愿高指向"被抢"（并行度超过核数或优先级设置不当）。两者的量级差得很远：阻塞式往返的进程自愿切换可以到几万次/秒，而纯计算自旋进程的自愿切换是 0。

**问：为什么并行度超过核数之后总吞吐不再增长？**
答：核数是并行执行的上限；多余的并行度只增加排队、上下文切换与同步开销，还可能加剧缓存与锁争用。若任务里有必须串行的部分，上限由那部分决定（Amdahl 定律）。

**问：容器里 CPU 利用率不高，服务却因为 CPU 变慢，最可能是什么？怎么验证？**
答：cgroup CPU 配额被周期性掐住。宿主侧看该 cgroup 的 `cpu.max` 与 `cpu.stat`（`nr_periods`、`nr_throttled`、`throttled_usec` 是否增长）；配额是硬上限，所以被限流方的吞吐会按配额比例下降，而不是"大致降一点"。

**第一反应不要做什么**：不要把"整机不忙"读成"CPU 有余量"；不要用加线程解决争抢；不要在没看 `cpu.stat` 之前断言容器资源够用。
