## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **`/proc/<pid>` 是一份免费的、几乎无开销的证据源，先把它看全再考虑上重型工具。**
>   - 证据：`wchan` 直接给出 `hrtimer_nanosleep`，`status` 给出 `voluntary=1/nonvoluntary=9`，`sched` 给出 `nr_switches=10`，`io` 区分「实际落盘字节」与「经过页缓存的字节」——全是 L0 读文件。
> - **`strace -c` 给画像，`-T` 给单次耗时，`-f` 跟线程，`-e trace=` 限范围。**
>   - 证据：2000 行写日志的画像里 `newfstatat` 占 29.57%、`write` 只占少数调用；单次调用用 `-T` 能看到 `write(...) = 21 <0.000050>`。
> - **`strace` 的代价是数量级的：约 80 倍。**
>   - 证据：同一 workload 基线 28～29 ms，`strace -c -f` 后 2317～2342 ms；被记录 40570 次调用。
> - **`perf` 在没有硬件 PMU 时退化为「软件事件 + 采样」，仍能定位热点函数。**
>   - 证据：`cycles`/`instructions` 显示 `<not supported>`，但 `perf record -F 99` + `perf report` 给出了 494 个样本、热点 100% 落在 `_PyEval_EvalFrameDefault`。
> - **`perf` 采不到「不在 CPU 上」的时间，必须靠 `wchan`/`sched` 补。**
>   - 怎么验证：`perf sched record` 在本机报权限错误，而 `cat /proc/<pid>/wchan` 立刻给出阻塞点。

## 1. `/proc/<pid>` 证据链

### 1.1 七个关键文件

| 文件 | 回答什么 | 本机实测样例 |
| --- | --- | --- |
| `wchan` | **此刻**阻塞在内核的哪个函数 | `hrtimer_nanosleep` |
| `status` | 状态与累计切换次数 | `State: S (sleeping)`、`voluntary_ctxt_switches: 1`、`nonvoluntary_ctxt_switches: 9` |
| `sched` | 切换次数、累计运行时间、**等 CPU 的累计时间** | `nr_switches: 10`、`se.sum_exec_runtime: 4207.647189`、`se.wait_sum` |
| `io` | **真实**读写字节（不含缓存命中）与系统调用次数 | `rchar/wchar`、`syscr/syscw`、`read_bytes/write_bytes` |
| `smaps_rollup` | 内存拆分（RSS/PSS/Anonymous/Private_Dirty） | `Rss 3082 MiB`、`Pss 3078 MiB`、`Anonymous 3076 MiB` |
| `limits` | 资源上限（句柄、进程数、栈大小） | `Max open files 10240 / 1048576`（软限 / 硬限） |
| `syscall` | 此刻正在执行哪个系统调用及参数 | 对 self 可读；对他人进程需 ptrace 权限 |

```bash
cat /proc/<pid>/wchan
grep -E "^(State|voluntary|nonvoluntary)_ctxt_switches" /proc/<pid>/status
grep -E "^(nr_switches|se.sum_exec_runtime|se.wait_sum)" /proc/<pid>/sched
cat /proc/<pid>/io
grep -E "^(Rss|Pss|Anonymous|Private_Dirty)" /proc/<pid>/smaps_rollup
grep -i "open files" /proc/<pid>/limits
```

```text
$ cat /proc/<pid>/io
rchar: 314687
wchar: 0
syscr: 53
syscw: 0
read_bytes: 0          # 真正从块设备读的字节（不含缓存命中）
write_bytes: 0
cancelled_write_bytes: 0
```

**组合用法**：`wchan` 回答「在等什么」，`sched` 回答「切换了多少次、等了多久」，`io` 回答「真的读写了多少」，`smaps_rollup` 回答「内存花在哪」，`limits` 回答「是不是撞到上限了」。这五句话基本能覆盖一个进程的八成问题，而且**全部是 L0 只读**。

### 1.2 累计值要「差分」才有意义

`/proc/<pid>/io`、`status` 的切换计数、`sched` 的 `sum_exec_runtime` 都是**累计值**。单次读取只能给出「从进程启动到现在」的总量；判断「现在在干什么」要隔几秒取两次做差分：

```bash
a=$(awk '/^read_bytes/{print $2}' /proc/<pid>/io); sleep 5; b=$(awk '/^read_bytes/{print $2}' /proc/<pid>/io)
echo "5 秒内新增落盘读=$((b-a)) 字节"   # 验证：差分才是速率
```

### 1.3 哪些读不了

- `/proc/<pid>/stack`（内核栈）：非 root 且非本人子进程时 `Permission denied`（本机实测 `cat /proc/self/stack` 也被拒）。
- `/proc/<pid>/syscall`、`mem`、`environ`：需要 ptrace 权限；`yama.ptrace_scope` 影响能跟谁。

## 2. `strace`：把「系统调用画像」画出来

### 2.1 四个参数的分工

| 参数 | 作用 | 用在哪一步 |
| --- | --- | --- |
| `-c` | 汇总：每个调用多少次、多少时间、多少错误 | 第一步，判断「谁最多 / 谁最慢」 |
| `-T` | 每次调用的耗时 | 第二步，定位具体的慢调用 |
| `-f` | 跟随线程与子进程 | 多线程/多进程程序 |
| `-e trace=<syscalls>` | 只跟指定的调用 | 缩小输出体积，降低开销 |
| `-p <pid>` | 附加到运行中的进程 | 生产环境（需要 ptrace 权限） |

### 2.2 实测输出

```bash
strace -c -f python3 -c 'f=open("/tmp/lab/w2.txt","w")
for i in range(2000):
    f.write("line %d\n"%i)
f.close()'
```

```text
% time     seconds  usecs/call     calls    errors syscall
------ ----------- ----------- --------- --------- ----------------
 29.57    0.000640           5       122        36 newfstatat
 12.06    0.000261           5        46           read
 10.44    0.000226           3        59           fstat
 10.35    0.000224           4        56        19 openat
  8.64    0.000187           4        42         3 lseek
  7.95    0.000172           4        37           close
  4.67    0.000101           3        26        26 ioctl
  4.62    0.000100           6        16           getdents64
```

```bash
strace -T -e trace=openat,write python3 -c 'f=open("/tmp/lab/w.txt","w")'   # 验证：每次调用的耗时
```

```text
openat(AT_FDCWD, "/tmp/lab/w.txt", O_WRONLY|O_CREAT|O_TRUNC|O_CLOEXEC, 0666) = 3 <0.000068>
write(3, "line 0\nline 1\nline 2\n", 21) = 21 <0.000050>
```

### 2.3 代价：约 80 倍

```bash
t0=$(date +%s%N); python3 sys20k.py; t1=$(date +%s%N); echo "baseline $(( (t1-t0)/1000000 )) ms"
t0=$(date +%s%N); strace -c -f python3 sys20k.py; t1=$(date +%s%N); echo "strace $(( (t1-t0)/1000000 )) ms"
```

```text
baseline 29 ms / 29 ms / 28 ms
strace   2317 ms / 2322 ms / 2342 ms
100.00    0.401201           9     40570        91 total
```

判据：**如果你不能用一句话说清「为什么现在必须用 `strace`」，就先别用。** 常见的正当理由只有两个：已经确定是 `sy` 型问题但不知道是哪个调用；或者要验证某个具体调用的频率与耗时。

## 3. `perf`：三种用法与各自的前提

| 用法 | 命令 | 回答什么 | 前提 | 本机实测 |
| --- | --- | --- | --- | --- |
| 事件计数 | `perf stat -e task-clock,context-switches,page-faults` | 工作量、切换、缺页 | 软件事件即可 | ✅ 可用 |
| 硬件计数 | `perf stat -e cycles,instructions,cache-misses` | IPC、缓存命中 | **需要 PMU** | ❌ `<not supported>` |
| 采样热点 | `perf record -F 99 -- <cmd>` + `perf report` | 热点函数与调用栈 | 符号（`-g` 需要 debuginfo / dynsym） | ✅ 能定位到热点符号 |
| 调度 / off-CPU | `perf sched record` + `perf sched latency` | 「不在 CPU 上时在等什么」 | **tracefs 可读** | ❌ 权限被拒 |

### 3.1 本机实测：没有 PMU 也能定位热点

```bash
perf stat -e task-clock,context-switches,page-faults,cycles -- timeout 6 taskset -c 5 python3 -c 'while True: pass'
perf record -o p.data -F 99 -- timeout 5 taskset -c 5 python3 -c 'while True: pass'
perf report -i p.data --stdio --sort dso,sym | head -20
```

```text
           6000.86 msec task-clock:u                     #    1.000 CPUs utilized
                 0      context-switches:u
   <not supported>      cycles:u

[ perf record: Captured and wrote 0.022 MB p.data (494 samples) ]

  Overhead  Shared Object  Symbol
  ........  .............  ............................
   100.00%  python3.12     [.] _PyEval_EvalFrameDefault
```

### 3.2 两个必须知道的坑

1. **`perf record -e cycles` 不报错，但可能一个样本都没有。**

```text
$ perf record -e cycles -o c.data -- true
[ perf record: Captured and wrote 0.002 MB c.data ]
$ perf report -i c.data --stdio
Error:
The c.data data has no samples!
```

所以「命令成功」不等于「采到数据」——**先看 `perf stat -e <event>` 有没有 `<not supported>`，再看报告里有没有样本。**

2. **`perf` 只覆盖在 CPU 上运行的时间。** 一个 90% 时间在等 IO 的线程，在火焰图里可能完全看不到（子笔记 07 给了三条替代路径）。

### 3.3 火焰图（本机未实测）

标准流程是：

```bash
perf record -F 99 -g -p <pid> -- sleep 30
perf script | stackcollapse-perf.pl | flamegraph.pl > fg.svg
```

三个前提缺一不可：**`-g` 需要调用栈符号**（`debuginfo`，至少要有 `dynsym`）、需要用 `stackcollapse-perf.pl`/`flamegraph.pl` 处理、进程要有足够长的采样窗口。本机没有这些脚本也没有可用符号，**未实测**；给出的替代是「语言自带的 profiler + 日志里的阶段耗时 + 二分注释」。

### 3.4 eBPF 的门槛

`bpftrace`/`bcc` 最吸引人的地方是「一行脚本看延迟分布」（`biolatency`、`execsnoop`、`tcpconnect`、`runqlat`），但门槛是硬的：

- 需要 **root / `CAP_BPF`**：本机 `kernel.unprivileged_bpf_disabled=2`（永久禁止非特权 BPF）；
- 需要内核支持与匹配的 BTF/头文件，4.x 与 5.x/6.x 的可用工具集不同；
- 挂点越多开销越大，生产上要按需、短时开启。

**替代路径**：需要「全量观测每一次调用」时，多数情况下可以用「短时 `strace` + `/proc` 证据链 + 应用埋点」拼出来；eBPF 真正不可替代的是**低开销的全量观测**，这类需求只能等有权限的机器。

## 4. 生产动作：一次完整下钻的记录模板

一份下钻记录应该能让别人复现你的结论，固定五段：

```text
【目标进程】PID 1515（python3，属于 unit lab.service）
【第一组证据】/proc/1515/status：State=R，voluntary=1，nonvoluntary=9
              /proc/1515/sched：nr_switches=10，se.wait_sum 5 秒内 +0 ms
              /proc/1515/io：read_bytes=0，write_bytes=0（5 秒差分）
【第二组证据】mpstat -P ALL 1 3：CPU 2 = 100% us，整机 4.17%
              pidstat -u -t -p 1515 1 2：单线程 100.50%，CPU=2
【下钻】perf record -F 99（5 秒，494 样本）→ 热点 _PyEval_EvalFrameDefault 100%
        没有使用 strace（原因：已确定为 us 型，无系统调用热点）
【结论】单线程 CPU 热点占用 CPU 2；影响面为同核延迟敏感进程
```

注意最后一段：**「为什么没用某个工具」也要写下来**。这既是代价意识的体现，也是复盘时最有价值的经验。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 「先 `strace -f -p` 看看」 | 约 80 倍减速；应先 `/proc` + `mpstat` 缩小范围 |
| 「`read_bytes=0` 说明进程没读文件」 | `read_bytes` 只统计真正落盘的字节；命中页缓存的读记在 `rchar` |
| 「`/proc/<pid>/io` 读一次就知道了」 | 都是累计值，必须差分才是速率 |
| 「`perf record` 成功就说明采到了」 | `-e cycles` 在无 PMU 时会写出一个 0 样本的文件，`perf report` 才报 `no samples!` |
| 「火焰图能看出所有慢」 | 火焰图只覆盖在 CPU 上的时间；等锁、等 IO 是空白区 |
| 「`/proc/<pid>/stack` 随时能看」 | 需要 ptrace 权限；本机非 root 实测 `Permission denied` |
| 「eBPF 是万能工具」 | 需要 root/CAP_BPF + 匹配内核；本机 `unprivileged_bpf_disabled=2` 直接禁用 |
| 「工具能用就用，反正只读」 | `strace`/`perf record`/抓包都不是「只读无代价」；要按级别判断 |

## 决策练习

**场景**：一个 Java 服务 `%sy` 明显偏高（`mpstat` 显示 `%sys` 占 CPU 时间的 45%），`us` 也不低，吞吐比基线低 30%。你有 root，但生产机不允许重启。

**选项**：

- **A. 挂 `strace -f -p <pid>` 并让它跑 30 分钟，希望覆盖完整的业务周期。**
- **B. 先取 `/proc/<pid>/{status,sched,io,limits}` 与 `pidstat -w -p <pid> 1`，判断是「高频小系统调用」还是「锁竞争与过度唤醒」，再用 `strace -c -f -p <pid>`（限时 10～30 秒、`-e trace=` 缩小范围）取调用画像。**
- **C. 直接调大 `net.core.somaxconn`、`vm.swappiness` 等参数试效果。**

**为什么选 B**：`%sy` 高有两个完全不同的方向——**系统调用太多**（话多）与**锁/切换太多**（抢得凶）。`pidstat -w` 的 `cswch/s` 与 `nvcswch/s` 能立刻区分：自愿切换极高 → 阻塞唤醒多；非自愿切换极高 → 抢 CPU。`/proc/<pid>/sched` 的 `wait_sum` 也能给出「等了多久」。确认方向后再用限时的 `strace -c` 取画像，代价可控且结论明确。

**为什么不选 A**：`strace -f` 跑 30 分钟会把服务拖慢一个数量级，等于人为制造一次事故；而且 `-f` 会跟着所有线程，输出体积可能达到几个 GB。

**为什么不选 C**：在根因未明时改内核参数是不可回滚的高风险动作，而且 `%sy` 高的原因与 `somaxconn`/`swappiness` 大多无关。

## 要点自测

> [!question]- `/proc/<pid>` 下哪几个文件最有用？分别回答什么？
> - `wchan`：此刻阻塞在哪个内核函数（在等什么）。
> - `status`：状态与累计的自愿/非自愿切换次数。
> - `sched`：`nr_switches`、`se.sum_exec_runtime`、`se.wait_sum`（等 CPU 的累计时间）。
> - `io`：`rchar`/`wchar` 与 `read_bytes`/`write_bytes`（真实落盘量）。
> - `smaps_rollup`：`Rss`/`Pss`/`Anonymous`/`Private_Dirty`。
> - `limits`：句柄、进程数等上限（本机 `Max open files 10240 / 1048576`）。
> - **共同点**：全部是 L0 只读；累计值要差分才有速率意义。

> [!question]- `strace` 的四个参数分别解决什么问题？代价多大？
> - `-c` 汇总画像、`-T` 单次耗时、`-f` 跟线程与子进程、`-e trace=` 限定调用范围；`-p` 用于附加运行中的进程。
> - 实测代价约 80 倍（28～29 ms → 2317～2342 ms，40570 次调用）。
> - 用法纪律：限时、限量、限范围，只针对已定位的少量进程。
> - **第一反应不要是什么**：不要把 `strace -f -p` 当默认动作。

> [!question]- `perf` 没有硬件计数器时还能做什么？什么情况下必须换机器？
> - 能做：`perf stat` 的软件事件（`task-clock`、`context-switches`、`page-faults`）、`perf record -F 99` 的采样与热点定位（本机 494 个样本，热点 `_PyEval_EvalFrameDefault`）。
> - 不能做：指令级分析、IPC、缓存未命中、以及 off-CPU 分析（`perf sched` 需要 tracefs；本机被拒）。
> - 必须换机器的场景：需要 PMU 的微架构分析、需要 eBPF 的低开销全量观测、需要 `blktrace` 的块层归因。

> [!question]- 为什么 `perf` 火焰图里看不到「在等」的时间？
> - `perf` 是采样工具，只在线程位于 CPU 上时产生样本；等待时间不产生样本。
> - 补法：`/proc/<pid>/wchan`、`/proc/<pid>/sched` 的 `wait_sum`（无需权限）；有权限时用 `perf sched`/`offcputime`。
> - **第一反应不要是什么**：不要把「火焰图里没有」当成「没有等待」。

> [!question]- 一次下钻记录至少要包含什么，别人才能复现？
> - 目标进程的身份（PID、属于哪个 unit/容器）。
> - 原始证据（命令 + 输出片段 + 采样窗口）。
> - 下钻路径与**为什么选择/放弃某个工具**。
> - 结论与它对应的证据行。
