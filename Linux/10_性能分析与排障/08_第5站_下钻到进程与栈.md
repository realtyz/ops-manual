## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **`/proc/<pid>` 是一份免费的、几乎无开销的证据源，先把它看全再考虑上重型工具。**
>   - 证据：`wchan` 直接给出 `hrtimer_nanosleep`，`status` 给出 `voluntary=1/nonvoluntary=0`，`sched` 给出 `nr_switches=1`，`limits` 给出 `Max open files 1024 / 1048576`，`io` 区分「实际落盘字节」（`read_bytes=0`）与「经过页缓存的字节」（`rchar=7088`）——全是 L0 读文件。
> - **`strace -c` 给画像，`-T` 给单次耗时，`-f` 跟线程，`-e trace=` 限范围。**
>   - 证据：2000 行写日志的画像里 `newfstatat` 占 25.64%、`write` 只占 0.87%（3 次调用）；同一份 workload 里 2 万个 `getpid` 是 47.08%。
> - **`strace` 的代价是数量级的：约 45～48 倍；每次拦截约 55 µs。**
>   - 证据：同一 workload 基线 50～51 ms，`strace -c -f` 后 2254～2474 ms；被记录 40540 次调用。
> - **`perf` 在本机退化为「软件事件 + 采样」，仍能定位热点函数与调用栈。**
>   - 证据：`cycles`/`instructions`/`cache-misses`/`branches` 全部 `<not supported>`（VMware 未透传 PMU 计数器），但 `perf record -F 99` + `perf report` 给出 494 个样本、`99.80% spin [.] main`；加 `-g` 后 `perf script` 给出真实调用栈 `main+0xf → __libc_start_main+0x8b → _start+0x25`。
> - **`perf` 采不到「不在 CPU 上」的时间，本机有三种手段能补，而且都实测可用。**
>   - 证据：`perf sched record` root 下采到 **35573 个样本**、`bpftrace` 的 `kprobe:schedule` 给出按进程的 off-CPU 纳秒、`cat /proc/<pid>/wchan` 立刻给出阻塞点。

## 1. `/proc/<pid>` 证据链

### 1.1 七个关键文件

| 文件 | 回答什么 | 本机实测样例 |
| --- | --- | --- |
| `wchan` | **此刻**阻塞在内核的哪个函数 | `hrtimer_nanosleep` |
| `status` | 状态与累计切换次数 | `State: S (sleeping)`、`voluntary_ctxt_switches: 1`、`nonvoluntary_ctxt_switches: 0` |
| `sched` | 切换次数、累计运行时间、**等 CPU 的累计时间** | `nr_switches: 1`、`se.sum_exec_runtime: 1.081539`、`nr_voluntary_switches: 1` |
| `io` | **真实**读写字节（不含缓存命中）与系统调用次数 | `rchar: 7088` vs `read_bytes: 0` |
| `smaps_rollup` | 内存拆分（RSS/PSS/Anonymous/Private_Dirty） | `Rss: 2100 kB`、`Pss: 209 kB`、`Anonymous: 108 kB` |
| `limits` | 资源上限（句柄、进程数、栈大小） | `Max open files 1024 / 1048576`（软限 / 硬限） |
| `stack` | 内核调用链（此刻阻塞的完整路径） | 需 root（见 1.3） |

```bash
cat /proc/<pid>/wchan
grep -E "^(State|voluntary|nonvoluntary)_ctxt_switches" /proc/<pid>/status
grep -E "^(nr_switches|se.sum_exec_runtime|nr_voluntary_switches)" /proc/<pid>/sched
cat /proc/<pid>/io
grep -E "^(Rss|Pss|Anonymous|Private_Dirty)" /proc/<pid>/smaps_rollup
grep -i "open files" /proc/<pid>/limits
cat /proc/<pid>/stack
```

```text
$ cat /proc/49112/io
rchar: 7088          # 经过 read()/write() 的字节（含缓存命中）
wchar: 0
syscr: 10
syscw: 0
read_bytes: 0        # 真正从块设备读的字节（不含缓存命中）
write_bytes: 0
cancelled_write_bytes: 0

$ grep -i "open files" /proc/49112/limits
Max open files            1024                 1048576              files
```

**组合用法**：`wchan` 回答「在等什么」，`sched` 回答「切换了多少次、等了多久」，`io` 回答「真的读写了多少」，`smaps_rollup` 回答「内存花在哪」，`limits` 回答「是不是撞到上限了」。这五句话基本能覆盖一个进程的八成问题，而且**全部是 L0 只读**。

> [!warning] `ulimit -n` 在本机是 1024，不是 10240
> 本机 `ulimit -n`（软限）= **1024**、`ulimit -Hn`（硬限）= **1048576**、`/proc/sys/fs/nr_open` = **1048576**。旧环境的软限是 10240，所以「第 10236 个 fd 报 `EMFILE`」这条结论在本机**完全不适用**——本机实测是**连续打开 1021 个 fd 后，第 1022 次 `open()` 失败**（子笔记 10）。**跨机器引用句柄类数字前必须先读本机的 `ulimit -n`。**

### 1.2 累计值要「差分」才有意义

`/proc/<pid>/io`、`status` 的切换计数、`sched` 的 `sum_exec_runtime` 都是**累计值**。单次读取只能给出「从进程启动到现在」的总量；判断「现在在干什么」要隔几秒取两次做差分：

```bash
a=$(awk '/^read_bytes/{print $2}' /proc/<pid>/io); sleep 5; b=$(awk '/^read_bytes/{print $2}' /proc/<pid>/io)
echo "5 秒内新增落盘读=$((b-a)) 字节"   # 验证：差分才是速率
```

本机对一个只 `sleep` 的进程实测差分结果为 `read_bytes delta=0  write_bytes delta=0`，而它的 `rchar=7088`——**它在「读文件」（经过页缓存），但没有产生任何真实落盘 IO**。这就是「`rchar` 与 `read_bytes` 要分开看」的现场。

### 1.3 哪些读得了、哪些读不了

- `/proc/<pid>/stack`（内核栈）需要 ptrace 权限。本机实测：**root 读普通进程与内核线程都成功**；`realtyz` 读同一进程得 `Permission denied`。

```text
$ cat /proc/49112/stack          # root 读普通进程
[<0>] hrtimer_nanosleep+0xa2/0x170
[<0>] common_nsleep+0x43/0x60
[<0>] __x64_sys_clock_nanosleep+0xf1/0x180
[<0>] do_syscall_64+0x87/0x180
[<0>] entry_SYSCALL_64_after_hwframe+0x78/0x80
$ cat /proc/2/stack              # root 读内核线程
[<0>] kthreadd+0x194/0x1b0
[<0>] ret_from_fork+0x47/0x70
$ runuser -u realtyz -- cat /proc/49112/stack
cat: /proc/49112/stack: Permission denied
```

- `/proc/<pid>/syscall`、`mem`、`environ`：需要 ptrace 权限；`yama.ptrace_scope` 影响能跟谁。

## 2. `strace`：把「系统调用画像」画出来

### 2.1 五个参数的分工

| 参数 | 作用 | 用在哪一步 |
| --- | --- | --- |
| `-c` | 汇总：每个调用多少次、多少时间、多少错误 | 第一步，判断「谁最多 / 谁最慢」 |
| `-T` | 每次调用的耗时 | 第二步，定位具体的慢调用 |
| `-f` | 跟随线程与子进程 | 多线程/多进程程序 |
| `-e trace=<syscalls>` | 只跟指定的调用 | 缩小输出体积，降低开销 |
| `-p <pid>` | 附加到运行中的进程 | 生产环境（需要 ptrace 权限） |

### 2.2 实测输出

```bash
strace -c -f python3 -c 'f=open("/tmp/lab/w2.txt","w")
for i in range(2000):
    f.write("line %d\n"%i)
f.close()'
```


### 2.3 代价：约 45～48 倍

```bash
t0=$(date +%s%N); python3 sys20k.py; t1=$(date +%s%N); echo "baseline $(( (t1-t0)/1000000 )) ms"
t0=$(date +%s%N); strace -c -f python3 sys20k.py; t1=$(date +%s%N); echo "strace $(( (t1-t0)/1000000 )) ms"
```

```text
baseline 50 ms / 51 ms / 51 ms
strace   2254 ms / 2280 ms / 2474 ms
100.00    0.394055           9     40540        70 total
```

判据：**如果你不能用一句话说清「为什么现在必须用 `strace`」，就先别用。** 常见的正当理由只有两个：已经确定是 `sy` 型问题但不知道是哪个调用；或者要验证某个具体调用的频率与耗时。

> [!warning] 「慢多少倍」要连着基线一起报
> 旧环境的同一 workload 基线是 28～29 ms、`strace` 后 2317～2342 ms（约 80 倍）；本机基线是 50～51 ms、`strace` 后 2254～2474 ms（约 45～48 倍）。**绝对代价（每次拦截约 55 µs）是稳定的，倍数却随被测程序基线浮动。** 引用时把基线、workload、被记录调用数一起写出来。

## 3. `perf`：三种用法与各自的前提

| 用法 | 命令 | 回答什么 | 前提 | 本机实测 |
| --- | --- | --- | --- | --- |
| 事件计数 | `perf stat -e task-clock,context-switches,page-faults` | 工作量、切换、缺页 | 软件事件即可，且**必须显式 `-e`** | ✅ 可用 |
| 硬件计数 | `perf stat -e cycles,instructions,cache-misses` | IPC、缓存命中 | **需要 PMU 计数器透传** | ❌ 全部 `<not supported>` |
| 采样热点 | `perf record -F 99 -- <cmd>` + `perf report` | 热点函数与调用栈 | 符号（`-g` 需要 debuginfo / dynsym） | ✅ 能定位到热点符号与调用栈 |
| 调度 / off-CPU | `perf sched record` + `perf sched latency` | 「不在 CPU 上时在等什么」 | **root 或可读 tracefs** | ✅ **root 下可用**（35573 样本） |

### 3.2 三个必须知道的坑

1. **裸 `perf stat` 在本机直接报错退出。**

```text
$ perf stat -- true
Error:
Invalid event (cpu_core/TOPDOWN.SLOTS/) in per-thread mode, enable system wide with '-a'.
exit=255
$ perf stat -a -- sleep 1
Error:
The sys_perf_event_open() syscall returned with 22 (Invalid argument) for event (cpu_core/TOPDOWN.SLOTS/).
exit=255
```

**必须显式 `-e <事件列表>`。** 默认事件集（`cpu_core/TOPDOWN.SLOTS/` 等混合架构 topdown 事件）在本机跑不动——设备节点在、计数器没透传，两者叠加的结果就是「默认用法直接失败」。

2. **`perf record -e cycles` 不报错，但样本数与事件支持度无关。**

```text
$ perf record -e cycles -o c.data -- true
[ perf record: Captured and wrote 0.013 MB /tmp/10-lab/c.data (2 samples) ]
```

本机写出了 **2 个样本**（旧环境是 0 个、`perf report` 报 `no samples!`）。**所以「命令成功」「文件写出来了」「样本数不是 0」都不能证明硬件事件被支持**——先看 `perf stat -e <event>` 有没有 `<not supported>`。

3. **`perf top -b` 在本机不可用。**

```text
$ timeout 4 perf top -b
Error:
cpu-clock:pppH: PMU Hardware or event type doesn't support branch stack sampling.
```

`perf top` 的默认事件带 `H`（branch stack）修饰，本机不支持。要实时看热点可以改用 `perf record` + 短窗口 `perf report`。

### 3.4 eBPF 的门槛

`bpftrace`/`bcc` 最吸引人的地方是「一行脚本看延迟分布」（`biolatency`、`execsnoop`、`tcpconnect`、`runqlat`），门槛有两条：

- 需要 **root / `CAP_BPF`**：本机 `kernel.unprivileged_bpf_disabled=2`（永久禁止非特权 BPF）；**root 下可用**。
- 本机**没有 bcc 工具集**（`/usr/share/bcc/tools` 不存在），但 `bpftrace` 在，可以用它现写等价脚本。

本机实测的三类脚本（子笔记 13 有完整命令与输出）：

```text
$ bpftrace -e 'tracepoint:syscalls:sys_enter_openat { @[comm] = count(); } interval:s:4 { exit(); }'
@[cat]: 816
@[bash]: 210
@[seq]: 3

$ bpftrace -e 'kprobe:schedule { @s[tid] = nsecs; }
    kretprobe:schedule /@s[tid]/ { @offcpu[comm] = sum(nsecs - @s[tid]); delete(@s[tid]); }
    interval:s:5 { exit(); }'
@offcpu[kworker/3:1]: 4982348769
@offcpu[vmtoolsd]: 4956885942
```

## 4. 生产动作：一次完整下钻的记录模板

一份下钻记录应该能让别人复现你的结论，固定五段：

```text
【目标进程】PID 45062（python3，单线程自旋，root 启动）
【第一组证据】/proc/45062/status：State=R，voluntary=0，nonvoluntary=53
              /proc/45062/sched：nr_switches=53，se.sum_exec_runtime=10216.384932
              /proc/45062/limits：Max open files 1024 / 1048576
【第二组证据】mpstat -P ALL 1 3：CPU 2 = 100.00% us，整机 25.04%
              pidstat -u -t -p 45062 1 2：单线程 100.00%，CPU=2
              top -b -n1 -H -p 45062：R 99.9%；taskset -cp 45062：亲和性 2
【下钻】perf record -F 99（5 秒，494 样本）→ 热点 99.80% spin [.] main
        perf record -g → perf script 给出 main+0xf → __libc_start_main+0x8b → _start+0x25
        没有使用 strace（原因：已确定为 us 型，无系统调用热点）
【结论】单线程 CPU 热点占用 CPU 2；影响面为同核延迟敏感进程
```

注意最后一段：**「为什么没用某个工具」也要写下来**。这既是代价意识的体现，也是复盘时最有价值的经验。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 「先 `strace -f -p` 看看」 | 约 45～48 倍减速；应先 `/proc` + `mpstat` 缩小范围 |
| 「`read_bytes=0` 说明进程没读文件」 | `read_bytes` 只统计真正落盘的字节；命中页缓存的读记在 `rchar`（本机实测 `rchar=7088` 而 `read_bytes=0`） |
| 「`/proc/<pid>/io` 读一次就知道了」 | 都是累计值，必须差分才是速率 |
| 「`ulimit -n` 是 10240」 | 本机软限是 **1024**、硬限 1048576；照抄旧环境的句柄数字会差一个数量级 |
| 「`perf stat` 直接敲就行」 | 本机裸 `perf stat` 与 `perf stat -a` 都报错退出；**必须显式 `-e <事件>`** |
| 「`perf record` 成功就说明采到了」 | `-e cycles` 在本机写出 2 个样本，而 `perf stat -e cycles` 是 `<not supported>`；先看 `perf stat` |
| 「`perf top` 是最方便的实时热点视图」 | 本机 `perf top -b` 直接报 `PMU Hardware or event type doesn't support branch stack sampling` |
| 「火焰图能看出所有慢」 | 火焰图只覆盖在 CPU 上的时间；等锁、等 IO 是空白区（本机用 `perf sched`/`bpftrace` off-CPU 补） |
| 「`/proc/<pid>/stack` 随时能看」 | 需要 ptrace 权限；本机 `realtyz` 实测 `Permission denied`，root 可读（含内核线程） |
| 「eBPF 是万能工具」 | 需要 root/`CAP_BPF`（本机 `unprivileged_bpf_disabled=2` 禁的是**非特权** BPF）；root 下可用，但没有 bcc 脚本集 |
| 「工具能用就用，反正只读」 | `strace`/`perf record`/抓包都不是「只读无代价」；要按级别判断 |

## 决策练习

**场景**：一个 Java 服务 `%sy` 明显偏高（`mpstat` 显示 `%sys` 占 CPU 时间的 45%），`us` 也不低，吞吐比基线低 30%。你有 root，但生产机不允许重启。

**选项**：

- **A. 挂 `strace -f -p <pid>` 并让它跑 30 分钟，希望覆盖完整的业务周期。**
- **B. 先取 `/proc/<pid>/{status,sched,io,limits}` 与 `pidstat -w -p <pid> 1`，判断是「高频小系统调用」还是「锁竞争与过度唤醒」，再用 `strace -c -f -p <pid>`（限时 10～30 秒、`-e trace=` 缩小范围）取调用画像。**
- **C. 直接调大 `net.core.somaxconn`、`vm.swappiness` 等参数试效果。**

**为什么选 B**：`%sy` 高有两个完全不同的方向——**系统调用太多**（话多）与**锁/切换太多**（抢得凶）。`pidstat -w` 的 `cswch/s` 与 `nvcswch/s` 能立刻区分：自愿切换极高 → 阻塞唤醒多；非自愿切换极高 → 抢 CPU。`/proc/<pid>/sched` 的 `wait_sum` 也能给出「等了多久」。确认方向后再用限时的 `strace -c` 取画像，代价可控且结论明确。

**为什么不选 A**：`strace -f` 跑 30 分钟会把服务拖慢一个数量级以上（本机实测 45～48 倍），等于人为制造一次事故；而且 `-f` 会跟着所有线程，输出体积可能达到几个 GB。

**为什么不选 C**：在根因未明时改内核参数是不可回滚的高风险动作，而且 `%sy` 高的原因与 `somaxconn`/`swappiness` 大多无关。

## 要点自测

> [!question]- `/proc/<pid>` 下哪几个文件最有用？分别回答什么？
> - `wchan`：此刻阻塞在哪个内核函数（在等什么）。
> - `status`：状态与累计的自愿/非自愿切换次数。
> - `sched`：`nr_switches`、`se.sum_exec_runtime`、`nr_voluntary_switches`（等 CPU 的累计时间看 `se.wait_sum`）。
> - `io`：`rchar`/`wchar`（经过调用层）与 `read_bytes`/`write_bytes`（真实落盘量）。
> - `smaps_rollup`：`Rss`/`Pss`/`Anonymous`/`Private_Dirty`。
> - `limits`：句柄、进程数等上限（本机 `Max open files 1024 / 1048576`）。
> - `stack`：完整内核调用链（需 root）。
> - **共同点**：全部是 L0 只读；累计值要差分才有速率意义。

> [!question]- `strace` 的五个参数分别解决什么问题？代价多大？
> - `-c` 汇总画像、`-T` 单次耗时、`-f` 跟线程与子进程、`-e trace=` 限定调用范围；`-p` 用于附加运行中的进程。
> - 实测代价约 45～48 倍（50～51 ms → 2254～2474 ms，40540 次调用），每次拦截约 55 µs。
> - 用法纪律：限时、限量、限范围，只针对已定位的少量进程。
> - **第一反应不要是什么**：不要把 `strace -f -p` 当默认动作。

> [!question]- `perf` 没有硬件计数器时还能做什么？什么情况下必须换机器？
> - 能做：`perf stat -e task-clock,context-switches,page-faults,cpu-migrations` 的软件事件计数、`perf record -F 99` 的采样与热点定位（本机 494 个样本、`99.80% spin [.] main`）、`perf record -g` + `perf script` 的真实调用栈、以及 **root 下的 `perf sched` off-CPU 分析**。
> - 不能做：指令级分析、IPC、缓存未命中（需要 PMU 计数器透传）、`perf top` 的默认事件。
> - 必须换机器的场景：需要 PMU 的微架构分析。**注意**：本机的 PMU 设备节点是齐的（`cpu_core`/`cpu_atom`/`msr` 都在），缺的是 **VMware 对计数器的透传**——所以「换机器」指的是换一台透传 PMU 的物理机或云主机，而不是「找一台有 PMU 的机器」。

> [!question]- 为什么 `perf` 火焰图里看不到「在等」的时间？本机怎么补？
> - `perf` 是采样工具，只在线程位于 CPU 上时产生样本；等待时间不产生样本。
> - 补法：`/proc/<pid>/wchan`、`/proc/<pid>/sched` 的 `wait_sum`（无需权限）；root 下用 `perf sched`（35573 样本）或 `bpftrace` off-CPU（按进程统计纳秒）。
> - **第一反应不要是什么**：不要把「火焰图里没有」当成「没有等待」。

> [!question]- 一次下钻记录至少要包含什么，别人才能复现？
> - 目标进程的身份（PID、属于哪个 unit/容器）。
> - 原始证据（命令 + 输出片段 + 采样窗口 + 工具版本）。
> - 下钻路径与**为什么选择/放弃某个工具**。
> - 结论与它对应的证据行。
