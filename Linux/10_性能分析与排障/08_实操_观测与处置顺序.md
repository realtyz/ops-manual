# 观测与处置顺序

排障现场只有两个问题：**用哪把工具**、**看到什么转向哪一步**。而这两个问题的答案取决于你手上有没有 root、机器上装了什么、现象属于哪种形态——因为同样一句"内存不够"，在只读权限下的取证路径和在有 root 时的取证路径不是一条。

## 1. 一个问题，一把工具

先分清三类东西，它们的"查文档方式"完全不同：**命令**（`man 1`）、**内核接口文件**（直接读写，`man 5 proc` 一类）、**内核参数**（`sysctl`）。由于把 `memory.max` 当命令查、把 `vm.swappiness` 当文件读已经是最常见的低级错误，所以动手前先分清自己在问哪一类。

### 1.1 整机：第一分钟的五条

| 想知道什么 | 用什么 | 关键字段 |
| --- | --- | --- |
| 排队长不长 | `uptime`、`cat /proc/loadavg` | 三个 1/5/15 分钟平均，以及 `runnable/total` |
| 整机与每核忙不忙 | `vmstat 1 5`、`mpstat -P ALL 1 3` | `r`/`b`、`si`/`so`、`us`/`sy`/`wa`/`st`，以及 `all` 行与逐核行 |
| 内存够不够、有没有压力 | `free -m`、`grep -H . /proc/pressure/*`、`cat /proc/meminfo` | `MemAvailable`，以及 PSI 的 `avg*` 与 `total` |
| IO 忙不忙、排多长 | `iostat -x 1 5` | `r_await`/`w_await`、`aqu-sz`、`%util`、`wareq-sz` |
| 连接与丢包 | `ss -s`、`nstat -az`、`awk '{s+=$2} END{print s}' /proc/net/softnet_stat` | 状态分布、重传比率，以及收包侧 dropped |

`mpstat` 的 `all` 行是**所有处理器的全局平均**，不是"随便挑一核"；`-P ALL` 只影响列出哪些处理器，而**离线 CPU 不显示**，所以行数可能少于 `nproc`，这不是异常。

### 1.2 单核与线程

| 想知道什么 | 用什么 | 关键字段 |
| --- | --- | --- |
| 哪颗核贴满了 | `mpstat -P ALL 1 3` | 逐核的 `%usr`、`%sys`、`%soft`、`%iowait` |
| 中断落在哪颗核 | `/proc/interrupts` | 每个 IRQ 在各核的计数 |
| 进程里哪个线程热 | `pidstat -u -t -p <pid> 1`、`top -b -n1 -H -p <pid>` | `%CPU`、`TID`、`PSR` |
| 它被绑在哪 | `taskset -cp <pid>` | `current affinity list` |
| 它在等还是被抢 | `pidstat -w -p <pid> 1`、`/proc/<pid>/status` | `cswch/s` 与 `nvcswch/s`，以及两个累计切换计数 |

### 1.3 进程与系统调用

| 想知道什么 | 用什么 | 字段：是什么 / 单位 | 判据 | 与谁同看 | 转向哪一步 |
| --- | --- | --- | --- | --- | --- |
| 谁在花 CPU、谁在等 | `ps -eo pid,ppid,stat,pcpu,pmem,wchan:24,args --sort=-pcpu` | `STAT` 是状态字母；`WCHAN` 是阻塞点的内核函数名 | 若 `R` 多，则说明它们在抢 CPU；若 `D` 多，则说明卡在不可中断等待上；若 `S` 多，则说明在等，但这不说明没问题 | 逐核利用率、`vmstat` 的 `r`/`b` | 若有 `D` 状态，则去查 `wchan`；若有 `R` 且核已满，则转线程视角 |
| 谁在读写盘 | `pidstat -d 1 3` | `kB_rd/s` 与 `kB_wr/s` 是每秒读写量（默认按 KiB 计）；`iodelay` 是等待 IO 的时钟节拍 | 若 `iodelay` 为 0 而 `kB_wr/s` 很大，则说明写是在缓存里完成的 | `iostat -x` 的 `w_await` 与 `aqu-sz` | 若 `iodelay` 持续高，则查设备与文件；若只有吞吐高，则查写模式 |
| 单个进程的占用与等待 | `/proc/<pid>/status`、`/proc/<pid>/sched`、`/proc/<pid>/io` | `RssAnon`/`VmSwap` 单位是 kB；`nr_switches` 与 `se.sum_exec_runtime` 是累计值；`rchar` 与 `read_bytes` 是累计字节数 | **累计值必须差分**；`rchar` 含缓存命中，而 `read_bytes` 只算真正落到块设备的 | 同口径的两次读数、`VmHWM` | 差分后得到速率，再与业务量对照；若 `VmSwap` 非 0，则转入内存方向 |
| 句柄与句柄上限 | `ls /proc/<pid>/fd`、`grep -i 'open files' /proc/<pid>/limits` | fd 数量单位是个；软限与硬限单位也是个数 | 数量贴近软限即已是风险，而不是"到硬限才出事" | 错误日志里的 `EMFILE`、`ss -s` | 若贴限，则查持有者与泄漏；若上限本身过低，则转入治理篇 |
| 系统调用画像 | `strace -c -f -p <pid>`（限时） | `calls` 与 `errors` 单位是次；`usecs/call` 单位是微秒 | 要看**分布**，也就是哪几个调用占了主要次数与时间 | `%sys/(%usr+%sys)` 的比值 | 若 `errors` 集中在某个调用上，则查该调用的失败原因；若次数异常，则查应用循环 |
| 热点函数与栈 | `perf record -F 99 -g -- <cmd>` 加 `perf report` | `Overhead` 单位是百分比；`Symbol` 是符号名；另有调用栈 | 先核对**实际记下来的事件名**，不要假设它就是 `cycles` | `perf stat -e <event>` 的输出 | 若热点集中，则查该函数；若热点分散且总时间对不上，则转 off-CPU |

### 1.4 服务与 cgroup（宿主侧）

| 想知道什么 | 用什么 | 字段：是什么 / 单位 | 判据 | 与谁同看 | 转向哪一步 |
| --- | --- | --- | --- | --- | --- |
| 进程属于哪个 cgroup | `cat /proc/<pid>/cgroup` | cgroup v2 路径（形如 `/system.slice/<unit>`） | 这个路径决定后面所有文件的位置 | `systemctl show <unit> -p ControlGroup` | 得到路径之后，去读该目录下的计数文件 |
| 服务的资源上限 | `systemctl show <unit> -p CPUQuotaPerSecUSec -p MemoryMax -p IOWeight -p LimitNOFILE -p OOMPolicy` | 都是生效值，单位依次为微秒、字节、权重、个数与策略名 | 要与配置文件里写的**对照**，不假定两者一致 | 内核侧 cgroup 文件 | 若与配置不符，则去查生效链（阶段 8） |
| 有没有被配额掐 | `<cgroup>/cpu.max`、`<cgroup>/cpu.stat` | `cpu.max` 是 `quota period`，单位微秒；`nr_periods`/`nr_throttled`/`throttled_usec` 都是累计值 | 若 `nr_throttled` 持续增长，则说明配额就是瓶颈 | 抖动的时间点、业务延迟分布 | 若在增长，则按业务周期调配额；若不增长，则转 GC、下游或锁 |
| 内存用掉多少、有没有撞上限 | `<cgroup>/memory.current`、`memory.peak`、`memory.max`、`memory.events` | 前三者单位都是字节；`memory.events` 各项是**累计次数** | 若 `peak` 贴到 `max`，则说明曾经贴边；若 `max` 远大于 `oom_kill`，则说明内核先回收过 | 内核日志的 `constraint=` 与 `oom_memcg=` | 若有 `oom_kill`，则按 cgroup 上限与整机上限分类；若 `peak` 富余，则说明上限可能偏松 |
| 整体谁在吃资源 | `systemd-cgtop -m -1` | 它给出各单元的 CPU、内存与 IO，单位是百分比与字节 | 它用来找"大户"，不用于精确定量 | 逐单元 cgroup 文件 | 锁定单元之后，回到上两行读它的计数文件 |

**容器排障的第一条纪律：同时拿容器内和宿主侧两份证据。** 因为容器里的 `/proc` 通常就是宿主机的，`free` 与 `top` 显示的往往是宿主机总量；而配额与限流计数只记在宿主侧的 cgroup 里。

### 1.5 历史与注入

| 想知道什么 | 用什么 |
| --- | --- |
| 过去发生过什么 | `sar -u -s 03:00:00 -e 04:00:00`、`sa -f <file>`、`sadf -d`（注意时间戳是 UTC） |
| 造一次单核争抢 | `taskset -c 2 python3 -c 'while True: pass' &` |
| 造一次内存压力 | `stress-ng --vm 1 --vm-bytes 1G --timeout 8s --metrics-brief` |
| 造一次 IO 压力 | `stress-ng --hdd 2 --hdd-bytes 512M --timeout 9s --metrics-brief`、`fio`（必带 `--runtime` 与 `--size`） |
| 造一次网络延迟或丢包 | **独立 netns 内**：`ip netns exec <ns> tc qdisc add dev lo root netem delay 50ms`；清理用 `tc qdisc del` 加 `ip netns del` |
| 造一次配额或上限 | `systemd-run --scope -p CPUQuota=20% --unit=<name> <cmd>`；`systemd-run --unit=<name> --collect -p MemoryMax=512M -p MemorySwapMax=0 -p OOMPolicy=continue <cmd>` |

**注入类操作只在可快照的实验机上做，并预先设定上限**：CPU 负载不超过 20 秒、内存不超过 3 GiB（本机总内存 7894 MiB）、IO 不超过 2 GiB、连接不超过 3000 条；跑完复核"无残留进程、无监听端口、无临时目录、无残留 unit、无残留 netns"。

## 2. 怎么读这些数字

字段的完整定义与机制背景在体系篇《一次性能故障的处置》里；这里只列**最容易读错的固定动作**。

### 2.1 先固定三样：单位、窗口、来源

同一列在不同工具里含义不同，甚至同一个缩写含义不同：

| 陷阱 | 事实 |
| --- | --- |
| `si` 在 `vmstat` 与 `top` 里不是一回事 | `vmstat` 的 `si` 是 swap in，而 `top` 的 `si` 是 softirq（软中断） |
| `%sys` 不含中断 | `mpstat` 明确 `%sys` **不包含**硬中断与软中断的时间，后两者在 `%irq` 与 `%soft` |
| `vmstat` 的 `us` 含 nice | 这与 `mpstat` 把 `%usr` 与 `%nice` 分开不同 |
| `vmstat` 首行的 procs 与 memory 是瞬时值 | 首行只有速率类字段是"自上次重启以来的平均"，而 `r`/`b`/`free`/`buff`/`cache` 在任何情况下都是瞬时快照 |
| `iostat`/`vmstat` 首份报告是自启动平均 | 用 `-y` 省略首份报告；只看第 2 行起 |
| `iostat` 的 `kB` 实际是 KiB | 官方 BUGS 与 FAQ 都写明按 1024 计 |
| `nstat` 默认输出是**窗口差值** | `-a` 才是累计值；把累计当速率是最常见的误判 |
| PSI 的 `total` 单位是微秒 | `avg*` 是百分比；`/proc/pressure/cpu` 的 `full` 系统级无定义，自 5.13 起固定为 0 |
| `aqu-sz` 旧名 `avgqu-sz`、`areq-sz` 旧名 `avgrq-sz` | 老资料与新输出对照时容易错位 |

### 2.2 三个"看起来像结论"的数字

```text
# 说明：数值仅示意、不代表你的机器
```

- **`load average`**：它要除以核数才有意义，而且包含 D 状态任务。本机一颗核已被自旋进程打满时，它只有 **0.34**（同一次采集之前空转时是 0.28）——因为它是 1 分钟尺度的平均，所以几乎推不动；
- **`%iowait`**：`man 5 proc` 明写 **"This value is not reliable"**，因为它逐核难以计算、且可能下降。因此它只能当线索；
- **`%util`**：`iostat(1)` 自己声明只对**串行服务请求**的设备"接近 100% 即饱和"，而对 RAID 与现代 SSD 这类并行设备不反映性能上限。

### 2.3 采样纪律与基线卡

- **同口径、带时间戳、至少两次**；判断抖动按秒，判断泄漏按小时或按天；
- **留原始输出**（`script -f`、`tee`、重定向到文件），而不是只抄一个数字；
- **累积量必须差分**才有速率含义；
- 基线卡的五组数据与 `fio` 四象限的写法见治理篇《性能基线与排障治理》。

## 3. 常见故障与排查方向

### 场景一：核心接口 p99 从 80 ms 涨到 1.2 s，整机看着很闲

**机器与服务**：4 vCPU（`MemTotal` 7894 MiB）的 Ubuntu 24.04.5，上面跑一个 4 副本的订单服务；报障时刻为业务高峰期；约束是**不能重启、不能改业务代码**。

**现象数值**：接口 p99 从 80 ms 涨到 1.2 s；错误率从 0.1% 涨到 4%；整机 `%usr` 25%、`load` 0.34。

**排查顺序**：

1. 先确认不是"整机忙"：`mpstat -P ALL 1 3`。此时看到 `all` 25% 而 `CPU 2` 100.00%；
2. 落到进程与线程：`pidstat -u -t -p <pid> 1 2` 显示某个线程 100%、`PSR=2`；`taskset -cp <pid>` 确认亲和性为 2；
3. 判断它在算还是在等：`pidstat -w -p <pid> 1 3` 看自愿与非自愿切换，`cat /proc/<pid>/wchan` 看阻塞点；
4. 按第 3 步的结果分方向：若属于 `us` 型，则用 `perf record -F 99` 找热点函数；若属于 `sy` 型，则用 `strace -c -f` 找系统调用；若切换高，则去查锁与下游；
5. 找同核上的邻居：`ps -eLo pid,tid,psr,pcpu,comm --sort=-pcpu | head`，确认是否有批任务与在线服务挤在同一颗核上。

**一份合格的回答应当包含四个要素。**

**结论**是"单核争抢"：在线服务的热线程与批处理任务被调度到了同一颗核上，所以整机平均看不到这件事。

**依据**是 `mpstat -P ALL` 的 `all 25.04%` 与 `CPU 2 100.00%` 这一对差值、`pidstat -u -t` 显示的单线程 100%，以及 `taskset -cp` 给出的亲和性为 2。

**边界**是这一结论只解释了 CPU 层：若 `wchan` 显示进程阻塞在锁上，那么方向就要改。

**动作**是先给批处理加 `CPUQuota=` 限流，再排期分核。

### 场景二：每 10 分钟写一批数据，接口就抖动几百毫秒

**机器与服务**：同上机器，数据盘是 `/dev/mapper/ubuntu--vg-ubuntu--lv`（ext4 on LVM，在 `iostat` 里是 `dm-0`）；业务是"定时把结果批量落盘"，用户反馈"每个整十分钟左右卡一下"。

**现象数值**：正常情况下 `w/s` 269、`w_await` 0.17 ms、`aqu-sz` 0.07、`%util` 4.21%；到了批处理窗口变成 `w/s` 324、`w_await` 6.59 ms、`aqu-sz` 2.14、`%util` 80.10%、`wareq-sz` 3781.33。

**排查顺序**：

1. 先确认形态：这属于**周期慢**，因此采样必须覆盖至少一个周期（用 `iostat -x 1 12` 连看两个窗口，或者用历史数据）；
2. 看设备层：`await` 与 `aqu-sz` 是否同时上升；本机这一点可以交叉校验：`324 × 0.00659 = 2.14`，与实测 `aqu-sz` 完全相等；
3. 看进程层：`pidstat -d 1 3` 看谁在写、`iodelay` 是多少。注意若 `iodelay` 为 0 而 `kB_wr/s` 很大，则说明写是在缓冲里完成的；
4. 看文件与调用：`ls -l /proc/<pid>/fd`，以及 `cat /proc/<pid>/io` 里 `write_bytes` 的差分；
5. 按前几步的取值分方向：若 `wareq-sz` 很大（本机 3781 KiB），则说明是大块写、单请求服务时间长；若 `%util` 高而 `aqu-sz` 小，则说明设备忙但队列不深，通常不需要动设备。

**一份合格的回答应当包含四个要素。**

**结论**是"大块写抢占了设备，而内存与网络都不是原因"。

**依据**是 `w_await` 6.59 ms 对基线 0.17 ms、`aqu-sz` 2.14、`wareq-sz` 3781，以及通过了的 Little's law 校验。

**边界**有两条：虚拟盘的绝对毫秒数不可外推到物理盘，而 `%util` 不能单独作为理由。

**动作**是给批处理限 IO 权重或把窗口挪开，验收用宿主服务 p99 回到基线。

### 场景三：容器里 CPU 只有 30%，延迟却周期性抖动

**机器与服务**：同一台 4 vCPU 机器，一个 `--cpus=2`（等价 `CPUQuota=200%`）的容器化服务；容器内 `top` 显示 CPU 25%、内存 40%。

**现象数值**：接口每隔几分钟抖动一次；宿主侧 `systemd-cgtop` 显示该单元偶尔冲到 100%。

**排查顺序**：

1. **不要相信容器内的 `top`**：因为容器里的 `/proc` 是宿主机的，它看不到 cgroup 配额；
2. 定位 cgroup：`cat /proc/<pid>/cgroup` 给出形如 `/system.slice/<unit>` 的路径；
3. 读宿主侧计数文件：`cpu.max`（应为 `200000 100000` 这类）与 `cpu.stat` 的 `nr_periods`、`nr_throttled`、`throttled_usec`；
4. 判读：若 `nr_throttled` 持续增长，则配额就是瓶颈；本机实测 `CPUQuota=20%` 时 `nr_throttled/nr_periods = 20/21`、吞吐降到 19.30%；
5. 按第 4 步的结果分方向：若 `nr_throttled` 不增长，则方向转到 GC、下游或锁；若增长，则调配额（按业务周期定，不按单次峰值定）。

**一份合格的回答应当包含四个要素。**

**结论**是"服务被 cgroup CPU 配额周期性掐住"。

**依据**是宿主侧 `cpu.stat` 里 `nr_throttled` 与 `nr_periods` 的差分，并且它与抖动的时间点对齐。

**边界**是容器内 `top` 不能作为依据，因为配额是 cgroup 级硬上限。

**动作**是按分钟记录差分后调配额，验收用抖动消失且宿主侧 `throttled_usec` 不再增长。

### 场景四：服务"偶发失败"，重试有时成功

**机器与服务**：同一台机器上一个短连接密集型服务；`ulimit -n` 软限 1024、硬限 1048576；`ip_local_port_range = 32768 60999`。

**现象数值**：报错里出现 `Too many open files` 或连接超时；本机实测软限 1024 时连续打开 **1021** 个 fd 后下一次 `open()` 失败（因为 1021 加上 3 个标准 fd 正好等于 1024）。

**排查顺序**：

1. 先分类，不要归到"网络抖动"：看 `/proc/<pid>/limits` 的 open files 软限，以及 `ls /proc/<pid>/fd | wc -l`；
2. 看监听队列：`ss -lnt` 的 `Recv-Q` 是否持续接近上限，以及 `nstat` 的 `TcpExtListenOverflows` 与 `ListenDrops` 是否增长；
3. 看端口占用：`ss -s` 的 `timewait`、`ss -tan state time-wait | wc -l`。上限的估算方式是可用端口数除以 60 秒（本机 28232 / 60 约为 470 条/秒，对同一目标）；
4. 按前几步的取值分方向：若 `Recv-Q` 满且 `ListenOverflows` 增长，则说明应用 accept 不及时（改应用或调队列上限）；若 fd 贴到软限，则说明句柄泄漏或上限过低；若 `timewait` 堆积且 QPS 接近上限，则说明源端口不足。

**一份合格的回答应当包含四个要素。**

**结论**是"资源上限耗尽，而不是网络抖动"。

**依据**是 fd 计数贴近软限、`ListenOverflows` 增长，或者 `timewait` 与端口上限的那个算式。

**边界**是改 `ulimit` 只解决"上限过低"这一种情况，而泄漏仍然要查代码。

**动作**是先提高上限或加副本止血，再定位持有者。

### 场景五：事后复盘"昨晚 3 点发生了什么"

**现象**：早上收到"凌晨 3 点系统很慢"的反馈，而现在一切正常。

**排查顺序**：

1. **先确认历史数据在不在**：`ls -l /var/log/sysstat/`、`systemctl is-active sysstat-collect.timer`。本机 `sysstat` 已安装、timer 为 `active`/`enabled`、`/var/log/sysstat/saNN` 存在；但因为保留期默认往往只有 7 天，所以跨周就要不到数据；
2. 用 `sar -u -s 03:00:00 -e 04:00:00` 看 CPU，用 `sar -d`、`sar -r`、`sar -n DEV` 分别看设备、内存与网络；
3. 把拐点与变更记录、定时任务对齐：`systemctl list-timers`、`crontab -l`、发布记录；
4. 按数据形态分方向：若 CPU 有尖峰，则回到场景一与场景二的分支；若 `%iowait` 抬头而没有 `await` 数据，则补 `sar -d` 再判断设备层；若可用内存骤降，则转内存方向并要求补采 PSI；若数据目录里没有当天文件，则记录"这次无法复盘"，并把补采集当成本次的改进项；
5. 注意 `sadf -d` 导出的时间戳是 **UTC**（带 `UTC` 后缀），因此时区不是 UTC 的机器要对齐换算。

**一份合格的回答应当包含四个要素。**

**结论**是要么定位到时间点与资源方向，要么如实说明"数据不在"。

**依据**是 `sar` 的具体行与时间戳。

**边界**是历史采集的粒度与保留期决定了这次能回答到什么程度。

**动作**是把缺的采集项补上，并把"历史目录有当天文件且在增长"纳入巡检。

**第一反应不要做什么**：不要先重启；不要在只读观测就能定性时先改参数；不要用容器内的视图判断容器的资源；不要在没有采集条件的情况下比较两个数字；不要用 1 分钟聚合的数据去否定一个亚分钟脉冲。

## 常见坑

| 做法或说法 | 后果或事实 |
| --- | --- |
| 先 `top` 看一眼就下结论 | 首屏是很短的一段窗口，而且只有整机与进程两个视角 |
| 用 `vmstat` 的 `si` 判断软中断 | 那是 swap in，而软中断在 `top` 里叫 `si`，在 `vmstat` 里算进 `sy` |
| 用 `%sys` 判断中断开销 | 因为 `mpstat` 明确 `%sys` 不含硬中断与软中断 |
| 用整机 `%usr` 判断 CPU 余量 | 单核可以已经 100%，所以要看逐核 |
| 用 `%iowait` 认定磁盘瓶颈 | 文档明写该值不可靠，因此判据在 `await` 与 `aqu-sz` |
| 用 `%util` 认定磁盘饱和 | 它只对串行设备有意义，而在并行设备上不反映上限 |
| 把 `nstat` 的累计值当速率 | 默认输出是窗口差值，而 `-a` 才是累计 |
| 把 PSI 的 `total` 当纳秒或比例 | 它的单位是微秒，而 `avg*` 才是百分比 |
| 在容器里用 `top` 或 `free` 判断容器资源 | 那是宿主机的视图，而配额与限流计数只在宿主侧 cgroup |
| 在生产机上跑 `fio` 或做注入 | 它会直接影响业务，因此注入只在可快照实验机的隔离环境里做 |
| 注入实验后不清理 | 残留的 netns、unit 与进程会在后续实验里制造假现象 |
| 只看 `iostat` 的绝对值不看采集条件 | 同一块盘的 `w_await` 可以从 0.09 ms 到 6.59 ms，条件不同即不可比 |

## 要点自测

**问：第一分钟的五条只读命令是什么？各自回答什么问题？**
答：`uptime` 与 `/proc/loadavg` 回答排队情况；`vmstat 1 5` 给出整机以及内存与 IO 的概览；`mpstat -P ALL 1 3` 给出逐核视角；`free -m` 加 `/proc/pressure/*` 回答内存空间与压力；`iostat -x 1 5` 回答设备与队列。网络类再加 `ss -s` 与 `nstat`。

**问：`mpstat` 的 `all` 行与逐核行是什么关系？为什么有时行数少于 `nproc`？**
答：`all` 是所有处理器的全局平均，它是独立计算的；`-P ALL` 只决定列出哪些处理器，而**离线 CPU 不显示**，所以行数可以少于总核数。

**问：CPU 高的时候，判据是什么比值？两个方向各转向哪把工具？**
答：判据是 `%sys / (%usr + %sys)`。本机实测纯计算任务是 0.12%（去 `perf` 找热点函数），而 2 万次 `getpid` 加 `stat` 是 24.0%（去 `strace -c` 看系统调用）。

**问：为什么"服务偶发失败"要先看句柄与队列，而不是先看网络？**
答：因为它常常是资源上限耗尽：fd 贴到软限（本机 1024 软限下第 1022 次 `open()` 失败），或者监听队列溢出（`TcpExtListenOverflows` 增长）。这两种情况下应用可能一条日志都没有，而网络计数器却完全干净。

**问：`strace` 在生产上怎么用才安全？**
答：四条限制：用 `timeout` 限时；用 `-e trace=` 限范围；先 `-c` 汇总再 `-T` 明细；只挂已定位的一两个进程。它的代价与调用次数成正比（本机实测每次拦截约 55 µs，4 万次调用把 51 ms 变成 2254～2474 ms）。

**问：复盘"昨晚 3 点"时，第一件事是什么？**
答：确认历史数据在不在，也就是 `ls -l /var/log/sysstat/`、`systemctl is-active sysstat-collect.timer`，以及保留天数够不够覆盖那个时间点。因为数据不在就没法复盘，只能补采集。

**第一反应不要做什么**：不要在没确认形态（恒定、间歇、周期）之前挑采样窗口；不要在只读命令能定性时动配置；不要把宿主机视图当容器视图。
