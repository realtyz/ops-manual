# 启动链为什么要分阶段接力

## 1. 如果只有一段程序负责开机

设想一个更简单的设计：主板固件不交棒，自己把操作系统内核读进内存、启动它。这个设计会立刻撞上四件事。

**第一，固件读不懂你的根文件系统。** 今天生产上很少有裸分区做根：根通常在 LVM 逻辑卷上、在 LUKS 加密容器里、在软件 RAID 或 LIO/iSCSI 之上，文件系统可能是 ext4、XFS 或 Btrfs。要读它，就得有卷管理、解密、RAID 组装、以及对应文件系统的解析代码。把这些全塞进固件，等于让固件变成一个操作系统——而固件是焊在主板 flash 里的，改一次要刷机。

**第二，固件不能等太久。** 固件里的一切都发生在操作系统之外，没有进程、没有中断处理框架、没有调度器，只能忙等与轮询。一块硬盘的电机启动是秒级，网络存储的响应是毫秒到秒级，加密卷还要等人输口令。让固件做这些事，就是把开机时间交给最不适合等待的那段代码。

**第三，固件不知道你的策略。** 同一台机器上可能装着两个内核、三个发行版、一个救援系统；用哪个、带什么参数、失败时退到哪个，是人的决定，不是硬件决定的。固件需要一份**可从外部改写的清单**。

**第四，固件不是唯一的启动来源。** 今天一台服务器可能从本地盘启动、从 PXE 网络启动、从 iSCSI 启动、从可移动介质启动。这些路径共享"自检 → 挑一个来源 → 交棒"的结构，却不共享"怎么读根文件系统"。

分阶段不是历史包袱，而是把上面四件事拆给四类角色：**只懂硬件、不必懂文件系统的固件**；**懂一点点文件系统、专门负责搬内核的引导加载器**；**懂硬件与存储、但还没有用户态的内核（配合 initramfs）**；**有完整用户态、能做策略决定的服务管理器**。

## 2. 五段接力，以及每一段交不出去时会怎样

```mermaid
flowchart LR
  A["① 固件<br/>BIOS / UEFI"] --> B["② 引导加载器<br/>GRUB2"]
  B --> C["③ 内核 + initramfs<br/>挂上真根"]
  C --> D["④ 服务管理器<br/>systemd（PID 1）"]
  D --> E["⑤ 登录与服务<br/>getty / sshd / 业务单元"]
```

| 段 | 谁在跑 | 它凭什么交棒 | 交不出去时你看到什么 |
| --- | --- | --- | --- |
| ① 固件 | 主板上的固件程序 | 一个启动项（UEFI 存于 NVRAM）或一个设备顺序（legacy） | 黑屏、蜂鸣、固件报错页、`No bootable device`、直接进固件设置界面 |
| ② 引导加载器 | `shimx64.efi` → `grubx64.efi`（UEFI）或 `boot.img`/`core.img`（legacy） | `grub.cfg`（或其等价物）里那条菜单项指向的 `vmlinuz` 与 initramfs | `grub>` 或 `grub rescue>` 提示符、`error: unknown filesystem` |
| ③ 内核 + initramfs | `vmlinuz` 与 initramfs 里的 `/init` | 命令行里的 `root=`（加密 / LVM / RAID 根还要额外参数） | `VFS: Unable to mount root fs`、`dracut:/#`、`(initramfs)` |
| ④ 服务管理器 | `systemd`（PID 1） | unit 依赖图与 `default.target` | `emergency.target`、`A start job is running for …（1min 30s）` |
| ⑤ 登录与服务 | `getty`、`sshd`、各业务单元 | 单元自身启动成功 | 没有登录提示符、端口没监听、`systemctl --failed` 有内容 |

这张表的用法只有一个方向：**先看输出是谁打的，再决定往哪一段查**。第 ① 段的输出永远不会出现在 `journalctl` 里（那时操作系统还没运行），第 ③ 段的输出不会出现在 systemd 的日志里（那时 PID 1 还没起来）。把段定位错了，后面所有命令都是白做。

## 3. 第 ③ 段的死锁：挂根需要驱动，驱动在根里

五段里唯一一处**逻辑上不可避免的循环依赖**出在第三段。

根文件系统在 LVM 逻辑卷上，那么挂载它需要 device-mapper 与 LVM 的用户态工具（`lvm` 要在内核组装好 dm 设备后做激活）；根在 LUKS 容器里，需要 cryptsetup 与口令输入；根在软件 RAID 上，需要 md 组装；根在 iSCSI 上，需要发起端与网络栈。**而这些驱动、工具与配置都存在根文件系统里**——根还没挂上，去哪读它们？

早期 Linux 用 **initrd**（initial ramdisk）解这个死锁：把一小块块设备镜像当作内存盘先挂上，里面有驱动和工具。现代 Linux 用 **initramfs**（initial RAM filesystem）：一个 **cpio 归档**（可以理解成"给内核用的 tar"，通常经过压缩），内核把它解开到内存里的 `tmpfs`，于是内存中出现一棵完整的目录树，内核执行其中的 `/init`。两者的差别是机制性的，不只是名字换了：

| | 旧 initrd | 现代 initramfs |
| --- | --- | --- |
| 形态 | 压缩的**块设备镜像**，要先当设备挂上 | **cpio 归档**，直接解成 `tmpfs` |
| 需要什么才能用 | 需要 ramdisk 驱动与文件系统支持 | 内核原生支持解包 |
| 修改方式 | 挂载镜像、改内容、再压回 | 解包归档、改内容、再打包 |
| 现在还用吗 | 老文档里常见 | 主流 |

现在 `/boot` 下那个文件名仍叫 `initrd.img-<版本>`（Debian/Ubuntu）或 `initramfs-<版本>.img`（RHEL 系），**内容是 initramfs 归档**。读老文档时按这张表翻译。

由此得到一条可操作的判据：**凡是让"挂根"这件事变复杂的变化，都要重建 initramfs**。换存储控制器、换虚拟化平台、把根迁到 LVM/LUKS/RAID/iSCSI/NFS 上、改 initramfs 自身的配置——这几类变化都会让原有的归档缺东西。反过来，只改命令行参数（`quiet`、`console=`）不需要重建，因为参数不存放在归档里。

## 4. 幂等的前提：每一段都必须能被重复执行

启动这件事全程不可交互（除按 `e` 改菜单那次），所以每一段都必须在**上一次失败后可以重来**。这解释了启动配置里几个看起来古怪的设计：

- **引导加载器的配置是生成物，不是手写物。** GRUB 的 `/boot/grub/grub.cfg` 由 `grub-mkconfig` 从 `/etc/default/grub` 与 `/etc/grub.d/*` 生成；RHEL 8/9 默认走 **BLS**（Boot Loader Specification，把"一个菜单项"变成"一个小配置文件"的约定），菜单项落在 `/boot/loader/entries/*.conf`。生成物的意义是：内核升级时只增删一个小文件，不必重写整份配置，也就不会在重写过程中把引导配置写坏。
- **启动项是"指针 + 实体"两件东西。** UEFI 的启动项（存在主板 NVRAM 里）记的是设备路径加 `.efi` 文件路径；文件在 ESP（EFI System Partition，FAT 格式的小分区）上。指针和实体要分别验证——启动项还在但 ESP 被重新格式化，现象和"启动项丢了"一模一样。
- **固件有一条兜底回退路径。** UEFI 规范规定：启动项为空或全部失败时，固件会尝试 ESP 上的 `\EFI\BOOT\BOOTX64.EFI`。所以"启动项丢了但文件还在、且放在回退路径上"的机器有时仍能起来——这是判断故障范围的一条线索。

## 5. 段与段之间是单向的

整条链上只有一个方向：控制权从固件往下传，**没有任何一段会把控制权交回上一段**。这带来一个在排障里非常实际的后果：

**你无法从系统内部修复它前面那一段。** 一台已经正常运行的机器上，`grub-install`、`efibootmgr`、`mkinitramfs` 这类命令只是**改写了下次启动要读的文件**，它们对当前这次运行没有任何影响，也无法验证"下次真的能起来"——真正的验收只能在一次重启之后。这也是为什么启动相关的变更风险等级普遍偏高：**变更与验证之间隔着重启，而重启本身就是风险**。

同样的单向性解释了为什么救援入口要提前演练：一旦第 ① 段（固件）出问题，操作系统完全没有参与，SSH、`journalctl`、救援模式全都用不上，只剩物理屏与带外管理（IPMI/iDRAC/iLO）。

## 6. 抽象在哪里漏水

**固件不认识 Linux，也不读 `/etc/fstab`。** 它只认启动项和引导器文件。所以"机器起不来"的第一个分支不是"系统坏了"，而是"固件没找到该交给谁"。理解这一点能省掉大量无效排查：在固件阶段去查日志、查挂载、查服务，全都看不到东西，因为那些东西还没开始存在。

**引导加载器懂的文件系统比内核少。** GRUB 只带一组常见文件系统模块，`/boot` 一旦落在它读不了的组合上（某些 LVM 布局、软 RAID、加密卷、较新的文件系统），就会报 `error: unknown filesystem`。这就是为什么 `/boot` 常被单独划成一个普通 ext4 分区——**不是容量规划的需要，是让引导加载器能读懂的需要**。

**`root=` 这个参数名会误导。** 它说的不是"根目录在哪"，而是"根文件系统在哪个设备上"。对 LVM/加密/RAID 根，`root=` 只是答案的一半，还要额外告诉 initramfs 怎么把那个设备组装出来（`rd.luks.uuid=`、`rd.lvm.lv=`、`rd.md.uuid=` 一类）。而且它写的是**根设备的标识，不是 `/boot` 分区的标识**——这两个分区经常被搞混，是手工引导失败最常见的原因。

**段与段之间存在语义断层。** `rd.*` 前缀的参数归 initramfs 用，`systemd.*` 归 PID 1 用；同一个词加不加 `rd.` 前缀，有时是两套完全不同的机制。在 `grub rescue>` 里敲 `rd.break` 没有任何作用——那是内核参数，只有内核已经跑起来才有意义。

## 常见误解

| 说法 | 事实 |
| --- | --- |
| "BIOS/UEFI 会去读 `/boot` 里的内核文件" | 固件只找引导器文件（UEFI 下是 ESP 上的 `.efi`），内核是引导加载器读的 |
| "`initrd` 和 `initramfs` 是同一个东西的两个名字" | 一个是块设备镜像、一个是 cpio 归档，机制与修改方式都不同；现代文件名还叫 `initrd` 但内容是 initramfs |
| "启动项存在就说明能启动" | 启动项是指针，`.efi` 文件是实体；ESP 被重新格式化后指针悬空，现象与"没配启动项"一样 |
| "改完 GRUB 配置就生效了" | 改 `/etc/default/grub` 只是改了输入，`grub.cfg` 要重新生成；改 `grub.cfg` 则下次生成时被覆盖 |
| "根分区换了地方，改 `/etc/fstab` 就行" | `fstab` 要到第 ④ 段才被读；根设备定位发生在第 ③ 段，由 `root=` 与 initramfs 决定 |
| "启动失败时先去看系统日志" | 第 ①②③ 段失败时操作系统还没有日志系统；现场在固件屏、带外日志、GRUB 提示符、initramfs shell 里 |
| "UEFI 启动一定配 GPT" | 两者是独立的选择，legacy 也能配 GPT（需要一个 BIOS boot 分区放 `core.img`），UEFI 也能从 MBR 盘启动 |
| "内核升级只是换个内核文件" | 它同时涉及引导配置、initramfs 重建、模块编译、启动项与回退路径，是一次完整变更 |

## 要点自测

**问：为什么固件不直接把内核读进内存并启动它？**

答：四个理由同时成立。固件读不懂 LVM/LUKS/RAID 与各种文件系统，而这些正是现代根的常见形态；固件运行在无进程、无调度的环境里，只能忙等，等不了秒级的设备与口令交互；用哪个内核、带什么参数、失败退到哪，是人的策略而非硬件决定；启动来源可能不止本地盘（PXE、iSCSI、可移动介质）。分阶段是把这四件事拆给合适的角色。

**第一反应不要做什么**：不要以为"分阶段是历史遗留、现代固件可以吞掉中间层"。UEFI 确实能直接读 ESP 上的内核（不需要 GRUB），但那只是把"引导加载器"这一段的职责压缩了，**第 ③ 段的死锁一点没变**——ESP 是 FAT 分区，读不了 LVM/加密根。

**问：initramfs 解决的是什么问题？为什么它必须存在？**

答：解"挂根需要驱动，而驱动在根里"的循环依赖。它把挂根所需的最小集合——存储与文件系统驱动、卷管理/加密/RAID/网络根所需的用户态工具——打成 cpio 归档放进内存，让内核先跑它，由它去挂真根，再 `switch_root` 切过去。

**第一反应不要做什么**：不要把 initramfs 当成"精简版操作系统"。它里面没有你的服务，也没有完整的 systemd 环境，它的任务只有一个。

**问：哪些变更必须重建 initramfs？哪些不必？**

答：必须的是"让挂根变复杂"的四类——换存储控制器或虚拟化平台、整盘克隆到别的硬件、把根迁到 LVM/LUKS/RAID/iSCSI/NFS 之上、修改 initramfs 自身的配置。不必的是只影响命令行参数（`quiet`、`console=`、`systemd.unit=`）或与启动无关的软件更新。

**第一反应不要做什么**：不要因为"改了一个启动参数"就去重建 initramfs——它解决不了参数问题，却引入一次"重启后再也起不来"的风险。

**问：为什么说"你无法从系统内部验证引导修复是否成功"？**

答：因为控制权在链上单向流动。已经运行的机器上，改写引导器、启动项、initramfs 只是修改了下次启动要读的文件，本次运行不受影响；真正的验收只能来自一次重启。所以启动类变更的验证天然滞后，需要靠"旧内核还在不在""快照能不能回""带外能不能看见画面"这些前置条件来兜底。

- `man 5 fstab`：六个字段与选项。
- `man 5 os-release`、`man 1 systemd-detect-virt`：确认发行版与虚拟化环境。

- 内核 6.x 文档 `Documentation/admin-guide/initrd.rst`（initramfs 的生成与内容约定）。内核文档一律按与目标机器同一主版本取（当前基线 6.x）——同一条路径在不同版本里可能同名而内容不同。
