## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **有两套参数，机制完全不同**：`/proc/cmdline` 里的启动参数只在启动那一瞬间生效；`sysctl` 改的是正在运行的内核，写入即生效。
> - **名字相似不代表是同一个东西**：`pid_max=`（启动参数）与 `kernel.pid_max`（运行时参数）概念相近，但改法和生效时机毫无关系。
> - **「改了没生效」的第一诊断是问它属于哪一套**：`grep <名字> /proc/cmdline` 没有 → 启动参数没带上；`sysctl <名字>` 报错 → 名字写错或模块没加载。
> - **`sysctl` 的覆盖规则是「按文件名字典序，后覆盖前」**，而 `/etc/sysctl.conf` 通常靠 `99-sysctl.conf` 软链排在最后；所以 `50-xxx.conf` 常常被它盖掉。
> - **`lsmod` 里没有 ≠ 内核不支持**：功能可能已经编进内核（builtin）；驱动加载失败的证据只在 `dmesg` 与 `journalctl -k` 里。

## 1. 两套「内核参数」

新人最容易在这里翻车：同一个词，两种机制，改错地方就是「配置写了但没生效」。先建立这张对照表。

| 维度 | 启动参数（内核命令行） | 运行时参数（`sysctl`） |
| --- | --- | --- |
| 存放位置 | 引导器配置 → `/proc/cmdline` | `/proc/sys/**` 下的可读写文件 |
| 谁传递 | GRUB 传给内核 | 内核自己暴露，由用户态写入 |
| 生效时机 | **只在启动那一瞬间**，必须重启（或 kexec） | 写入即生效 |
| 持久化方式 | `/etc/default/grub` + 重新生成，或 `grubby` | `/etc/sysctl.d/*.conf` 等配置文件，开机由 `systemd-sysctl` 写入 |
| 典型例子 | `ro`、`quiet`、`console=`、`crashkernel=`、`systemd.unit=` | `net.ipv4.ip_forward`、`vm.swappiness`、`kernel.pid_max` |
| 唯一验收标准 | `cat /proc/cmdline` | `sysctl <参数名>` 或 `cat /proc/sys/...` |

## 2. 内核命令行参数

### 2.1 先确认本次带了什么

```bash
cat /proc/cmdline                          # 验证：本次启动实际收到的完整命令行
```

这一条是**永久性证据**：它记录的是内核真正收到的东西，不受你「改过哪个配置文件」影响。改启动参数的正确姿势与回滚方式见 [[Linux/02_启动流程与内核/05_第2环_GRUB2引导加载器|05 第 2 环]]。

### 2.2 常见参数按用途分三组

**第一遍只需要记住「日常必知」那三行**，其余两组知道存在、用到再查：

| 分组 | 参数 | 作用 | 坑 |
| --- | --- | --- | --- |
| 日常必知 | `ro` / `rw` | 根文件系统的初始挂载方式 | 用 `init=/bin/bash` 改密码时常需要 `rw`，或进去后 `mount -o remount,rw /` |
| 日常必知 | `quiet`、`rhgb` | 少打内核日志 / 图形化启动画面 | **排障时要先去掉它们**，否则现场信息被吞掉 |
| 日常必知 | `console=ttyS0,115200n8` | 把内核与 systemd 日志输出到串口 | **它只负责「有输出」，不负责「能登录」**；还要 `systemctl enable serial-getty@ttyS0.service`（见子笔记 04）；漏配就只剩一句「机器没起来」 |
| 救援排障 | `systemd.unit=` | 指定本次启动的目标 unit | 名字写错会掉回 `rescue.target` 而不是报错 |
| 救援排障 | `init=` | 指定 PID 1 | `init=/bin/bash` 下没有 systemd，服务与 `systemctl` 全部不可用 |
| 救援排障 | `rd.break` | 停在 initramfs 阶段 | 真根在 `/sysroot` 且只读，改文件要先 `mount -o remount,rw` |
| 救援排障 | `systemd.log_level=debug`、`rd.debug` | 打印 initramfs / systemd 详细日志 | 只在排障时临时加，日志量极大 |
| 救援排障 | `crashkernel=` | 为 kdump 预留捕获内核的内存 | 预留过小抓不全 `vmcore`，过大常年占用业务内存（见子笔记 10） |
| 谨慎使用 | `selinux=0`、`enforcing=0` | 关闭或降级 SELinux | **掩盖问题并让系统进入无标签状态**，重新开启时往往起不来 |
| 谨慎使用 | `net.ifnames=0` | 回到 `eth0` 式网卡命名 | 会让既有网络配置与脚本失配，「改回去」往往比重装还麻烦 |

## 3. 运行时参数与 `sysctl`

### 3.1 三种改法，作用域完全不同

| 改法 | 生效范围 | 重启后 |
| --- | --- | --- |
| `echo 1 > /proc/sys/net/ipv4/ip_forward` | 当前运行内核 | 丢失 |
| `sysctl -w net.ipv4.ip_forward=1` | 当前运行内核（本质就是往 `/proc/sys` 写） | 丢失 |
| 写 `/etc/sysctl.d/99-xxx.conf` + `sysctl --system` | 当前运行内核 + 今后每次开机 | 保留 |

```bash
sysctl -a                                  # 验证：全部运行时参数及其当前值（数量随内核与已加载模块变化）
sysctl net.ipv4.ip_forward                 # 验证：单个参数，等价于 cat /proc/sys/net/ipv4/ip_forward
sysctl --system                            # 验证：按加载顺序重新应用所有配置文件（失败项会打印出来）
```

### 3.2 持久化写哪里、谁覆盖谁

先把结论说了：**想覆盖别人的配置，就把自己的文件名取到 `100` 之后。** 下面是这条结论的由来。

`systemd-sysctl` 会读四个目录，优先级从高到低是 `/etc/sysctl.d/` > `/run/sysctl.d/` > `/usr/local/lib/sysctl.d/` > `/usr/lib/sysctl.d/`。执行规则三条：

1. **不分目录**：所有 `.conf` 文件统一按**文件名字典序**执行，名字靠后的覆盖靠前的；
2. **同名文件**：以高优先级目录里的那一份为准；
3. **发行版默认值**放在 `/usr/lib/sysctl.d/`，你在 `/etc/sysctl.d/` 放同名文件就能盖掉它。

关键在那条软链：systemd 从 v198 起**不再直接读 `/etc/sysctl.conf`**，而多数发行版提供 `/etc/sysctl.d/99-sysctl.conf -> ../sysctl.conf` 来兼容老习惯。于是它以 `99-` 开头，天然排在最后、优先级最高：

```bash
ls -l /etc/sysctl.d/99-sysctl.conf         # 验证：本机到底有没有这个软链，再决定自己的编号策略
```

- 要覆盖它，配置文件名必须排在 `99` 之后，例如 `100-local.conf`；**只写 `50-xxx.conf` 会被它盖掉**。
- 这是「我明明写了配置却不生效」最常见的成因之一。

### 3.3 「参数不存在」的两种情况

```bash
sysctl vm.swappiness                       # 验证：正常应返回值；报 cannot stat 说明参数名写错或对应模块没加载
```

一种是**名字写错**：`/proc/sys` 里的层级用点号表示，写成路径反而找不到。另一种更重要：**参数要等对应模块加载后才存在**。

`systemd-sysctl` 在启动早期就跑完了，而某些 `net.*` 参数要等网卡驱动加载后才出现——这时写进去会失败。这类参数要么改用 udev 规则，要么先用 `modules-load.d/` 让模块提前加载。

## 4. 内核模块

### 4.1 两种存在形态

| 形态 | 表现 | 怎么确认 |
| --- | --- | --- |
| **builtin**（编进内核） | 内核镜像的一部分，开机就在 | `lsmod` 里**看不到**；查内核配置，或直接看设备是否工作 |
| **模块**（`.ko`） | 放在 `/lib/modules/$(uname -r)/` 下，按需加载 | `lsmod` 里有，`modinfo` 能查到路径 |

> [!important] 最容易把人带偏的一句话
> 「`lsmod` 里没有这个驱动」**不能**推断「内核不支持它」——它可能已经编进内核了。

### 4.2 常用命令

```bash
lsmod                                     # 验证：当前已加载的模块及依赖计数、被引用次数
modinfo <module>                          # 验证：模块路径、参数、依赖、别名
modinfo -n <module>                       # 验证：模块文件在 /lib/modules/$(uname -r) 下的真实路径
modprobe <module>                         # 验证：按依赖顺序加载（比 insmod 安全，会处理依赖）
modprobe -r <module>                      # 验证：卸载模块（被占用时会失败，lsmod 第三列非 0 即为占用）
modprobe --show-depends <module>          # 验证：加载它会连带拉起哪些模块
```

### 4.3 `/etc/modprobe.d/*.conf` 里的三条指令

| 指令 | 语义 | 常见误用 |
| --- | --- | --- |
| `options <mod> <k>=<v>` | 加载时附带的模块参数 | 参数名写错不会报错，只会被忽略；用 `modinfo -p <mod>` 核对 |
| `blacklist <mod>` | `modprobe` 与 udev 自动加载时不主动选它 | **挡不住被其他模块依赖而被动加载**；要彻底禁用还要加下面那条 |
| `install <mod> <cmd>` | 用自定义命令替代真正的加载动作 | 写 `/bin/false` 是最常见的「硬禁用」写法 |

### 4.4 另外两张表和一条命令

- **`/etc/modules-load.d/*.conf`**：开机由 `systemd-modules-load.service` 静态加载，用来让模块早于 `sysctl` 生效。
- **`/etc/modprobe.d/`**：管的是「怎么加载」；`modules-load.d/` 管的是「开机加载谁」，两者不要混。
- **`depmod -a`**：手工往 `/lib/modules/$(uname -r)/` 放模块后必须重建依赖表，否则 `modprobe` 找不到它。

### 4.5 驱动加载失败时，证据在哪

只有两处：**内核日志**和**固件文件是否存在**。

```bash
journalctl -k -b                           # 验证：本次启动的内核日志（比 dmesg 更完整、带启动 ID，推荐）
journalctl -k -b -1                        # 验证：上一次启动的内核日志（需要 journal 持久化）
dmesg | grep -i -E 'error|fail|firmware'   # 验证：驱动加载、固件加载、符号缺失的错误
```

| 日志片段 | 含义 | 处理方向 |
| --- | --- | --- |
| `Unknown symbol in module` | 模块与当前内核不匹配（常见于手工编译的老驱动） | 用匹配当前内核的版本重编（DKMS），或回滚内核 |
| `module verification failed` / `Key was rejected by service` | Secure Boot 下模块没签名或被拒 | 用发行版签名模块，或按流程注册 MOK；**不要直接关 Secure Boot** |
| `Direct firmware load for xxx failed` | 模块在，但设备需要的固件文件缺失 | 装对应的固件包（通用固件在 `linux-firmware`，另有厂商专用包），并确认固件路径与版本 |
| `modprobe: ERROR: could not insert` 但内核日志无记录 | 多半是参数/别名问题，或模块根本没打进 initramfs | 核对 `modinfo` 与 `/etc/modprobe.d/`，必要时重建 initramfs（见子笔记 06） |
| 新插入的硬件没被识别 | 模块未随设备自动加载 | 看 `dmesg` 尾部的设备枚举记录，再手工 `modprobe` 验证 |

## 5. 生产动作：持久化一个 `sysctl` 参数（S2）

> [!example]+ 生产动作：改一个运行时内核参数并让它活过重启
> **什么时候用**：需要长期生效的内核调优或功能开关（转发、句柄上限、内存回收策略等）。
>
> **动手前确认**：
> 1. 先用 `sysctl -w` 验证语义与影响——**运行时参数改错可以立刻改回去，写进文件就会在每次开机时复现**。
> 2. 确认文件名编号排在本机 `99-sysctl.conf` 之后。
> 3. 记录原值，回滚时要用。
>
> **怎么做**：
> ```bash
> sysctl net.ipv4.ip_forward                # 验证：记录初始值
> sysctl -w net.ipv4.ip_forward=1           # 验证：当前内核立即生效，先观察影响
> printf 'net.ipv4.ip_forward = 1\n' > /etc/sysctl.d/100-local.conf   # 验证：落盘持久化（编号必须 > 99）
> sysctl --system                           # 验证：重新应用全部配置，观察有无报错或被覆盖
> sysctl net.ipv4.ip_forward                # 验证：当前值为 1
> reboot
> sysctl net.ipv4.ip_forward                # 验证：重启后仍为 1（持久化成功）
> ```
>
> **怎么验证**：`sysctl --system` 不报错；当前值正确；**重启后仍为设定值**。最后这一条才是持久化的验收标准。
>
> **怎么退回去**：删除 `/etc/sysctl.d/100-local.conf`，再执行 `sysctl --system`。
> **注意：删文件不会把参数改回默认值**——文件只影响「开机写入什么」，当前内核里的值仍然是你设的那个。所以回滚要显式做一次 `sysctl -w <参数>=<原值>`，或重启。
>
> **要沉淀什么**：参数名、原值、新值、取值依据、验证输出、回滚命令。调优类参数还要写清「为什么是这个值」，否则半年后没人敢动它。

## 6. 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 用 `sysctl -w` 就当成配置完成 | 重启即丢，也没有审计痕迹；持久化要写 `/etc/sysctl.d/` |
| 写了 `50-xxx.conf` 却以为一定生效 | 常被 `99-sysctl.conf` 覆盖；文件名要排到 `99` 之后 |
| 回滚只删配置文件 | 当前内核里的值不会自己变回去，要显式 `sysctl -w` 或重启 |
| 改启动参数后只重启 | 不核对 `/proc/cmdline`，等于没验证；它是唯一验收标准 |
| 认为 `lsmod` 是内核支持能力的清单 | 它只列可加载模块，builtin 功能看不到 |
| 用 `blacklist` 就以为禁掉了模块 | 被其他模块依赖时照样加载；要配 `install <mod> /bin/false` |
| 手工放模块后不跑 `depmod` | 依赖表没更新，`modprobe` 找不到该模块 |
| 驱动加载失败只反复 `modprobe` | 证据在 `dmesg`/`journalctl -k` 里；不看日志只是重复同一个失败 |

## 7. 决策练习

> [!question]- 场景：你按文档在 `/etc/sysctl.d/50-tuning.conf` 里设了 `vm.swappiness = 10`，`sysctl --system` 也执行了，但 `sysctl vm.swappiness` 仍然显示 60
> 最可能的原因是什么？
> A. 内核不支持这个参数
> B. 有编号更大的配置文件把它覆盖了——先看 `/etc/sysctl.d/99-sysctl.conf` 在不在，以及里面有没有这一项
> C. 必须重启才能生效
>
> **答案：B。**
> 参数能被 `sysctl` 读到，说明它存在且可写（A 不成立）；运行时参数写入即生效（C 不成立）。
> 唯一解释是**顺序覆盖**：所有 `.conf` 按文件名字典序执行，后面覆盖前面。`99-` 开头的文件天然排在 `50-` 后面，而它通常就是 `/etc/sysctl.conf` 的软链。

> [!question]- 场景：一台机器上某个设备不工作，`lsmod | grep <驱动>` 没有任何输出。同事说「内核不支持这个硬件」，准备换机器
> 你先做什么？
> A. 同意换机器
> B. 先确认这个驱动是不是被编进了内核（builtin），再看内核日志里有没有固件加载失败之类的记录
> C. 直接 `modprobe` 一遍再看
>
> **答案：B。**
> `lsmod` 看不到有两种可能：编进内核了，或者根本没加载。两者的处理方向完全相反，**不先区分就动手等于赌**。
> 证据在 `dmesg` / `journalctl -k` 里：`Direct firmware load ... failed` 说明模块在、但缺固件；`Unknown symbol` 说明版本不匹配。C 在没有区分情况前只是重复一次已有结果。

## 8. 要点自测

> [!question]- 启动参数与运行时参数怎么区分？各自的唯一验收标准是什么？
> - 启动参数由引导器传给内核，只在启动瞬间生效，改完必须重启；唯一验收标准是 `cat /proc/cmdline`。
> - 运行时参数通过 `/proc/sys` 读写正在运行的内核，写入即生效；验收标准是 `sysctl <参数名>`。

> [!question]- `sysctl` 配置的加载顺序是什么？为什么 `50-xxx.conf` 常常不生效？
> - 目录优先级 `/etc/` > `/run/` > `/usr/local/lib/` > `/usr/lib/`；所有文件统一按文件名字典序执行，后者覆盖前者。
> - 多数发行版有 `/etc/sysctl.d/99-sysctl.conf` 软链指向 `/etc/sysctl.conf`，它以 `99-` 开头排在最后；编号小于它的文件会被它覆盖。

> [!question]- 驱动加载失败时看什么？四种典型日志分别指向什么？
> - 看 `dmesg` 与 `journalctl -k -b`（必要时 `-b -1`）。
> - `Unknown symbol` 是版本不匹配；`module verification failed` 是 Secure Boot 签名问题；`Direct firmware load failed` 是缺固件文件；`modprobe` 报错但内核日志无记录，则要怀疑模块参数、别名或没打进 initramfs。
