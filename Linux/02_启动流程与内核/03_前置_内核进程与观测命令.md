## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **内核是唯一直接管硬件的程序**。普通程序想读文件、收发包、申请内存，都要通过系统调用「请求内核代做」。
> - **`vmlinuz` 是内核镜像，`.ko` 是可加载模块**。功能可能编进内核（builtin），所以「`lsmod` 里没有」不等于「内核不支持」。
> - **`/proc` 和 `/sys` 是内核的窗口**，不是磁盘上的文件。读 `/proc/cmdline` 就是在问内核「你这次启动收到了什么参数」。
> - **PID 1 是内核拉起的第一个用户态进程**。在主机上它收不到未处理的信号，`kill -9 1` 是静默失败——这是设计，不是权限问题。
> - **journal 不持久化的话，重启后上一次的现场就没了**。`journalctl -b -1` 是排「莫名重启」的第一条命令，前提是 `/var/log/journal` 存在。

## 1. 内核是什么

### 1.1 内核负责的四件事

内核（kernel）是操作系统里唯一直接操作硬件的程序。日常运维碰到的问题，几乎都能归到它的四个职责上：

| 职责 | 它管什么 | 出问题时你看到的 |
| --- | --- | --- |
| 进程调度 | 决定谁在 CPU 上跑、跑多久 | 负载高、延迟抖动、进程卡在 `R`/`D` |
| 内存管理 | 分配/回收内存、虚拟地址到物理地址的映射 | OOM、`free` 读数、Page Cache |
| 文件系统与存储 | 读写块设备、维护文件系统 | IO 慢、`dmesg` 里的介质错误 |
| 网络与设备驱动 | 协议栈、网卡、其他外设 | 网卡不识别、驱动加载失败 |

这四个职责分别对应阶段 3、4、5、6 的专题。这一篇只需要知道：**启动过程，就是内核把这四件事逐个准备好，然后把系统交给用户态。**

### 1.2 用户态与内核态

一个够用的直觉：

> 普通程序跑在**用户态**，能碰的只有自己的内存；要读文件、发网络包、申请内存，必须**发起系统调用**请内核代做。

所以进程「卡住」时，第一件事往往是问：它在等内核做什么？这也是 `/proc/<pid>/wchan`、`/proc/<pid>/stack` 这类文件的用途（深水区在阶段 3 与阶段 10）。

## 2. 内核镜像与模块

### 2.1 `vmlinuz` 是什么

`/boot/vmlinuz-<版本>` 是**压缩过的内核镜像**，由引导器（第 2 环）载入内存。启动要凑齐的不止它一个：`/boot` 下与内核直接相关的文件有三个，第一个是内核本体，后两个是它的搭档。

| 文件                                                                              | 作用                                  |
| ------------------------------------------------------------------------------- | ----------------------------------- |
| `/boot/vmlinuz-$(uname -r)`                                                     | 内核本体                                |
| `/boot/initramfs-$(uname -r).img`（RHEL）/ `/boot/initrd.img-$(uname -r)`（Debian） | 挂根用的临时根文件系统，见子笔记 06                 |
| `/boot/System.map-$(uname -r)`                                                  | 内核符号表，分析 `vmcore`/崩溃时配合 debuginfo 用 |

```bash
uname -r                                  # 验证：当前运行的内核版本（所有 /lib/modules 路径都以它为准）
uname -a                                  # 验证：内核版本 + 架构 + 编译信息
ls -l /boot/                              # 验证：机器上装了哪些内核与 initramfs（有几套就有几条退路）
```

### 2.2 builtin 与可加载模块

内核功能有两种存在形态，这个区分在排障时非常重要：

| 形态 | 表现 | 怎么确认 |
| --- | --- | --- |
| **builtin**（编进内核） | 内核镜像的一部分，开机就在 | `lsmod` 里**看不到**；查内核配置或直接看设备是否工作 |
| **模块**（`.ko`） | 放在 `/lib/modules/$(uname -r)/` 下，按需加载 | `lsmod` 里有；`modinfo` 能查到路径 |

```bash
lsmod                                     # 验证：当前已加载的模块（读的是 /proc/modules）
modinfo <模块名>                           # 验证：模块路径、参数、依赖、别名
```

> [!important] 最容易把人带偏的一句话
> 「`lsmod` 里没有这个驱动」**不能**推断「内核不支持它」——它可能已经编进内核了。正确做法是查 `modinfo`、内核配置，或者直接看设备能不能用。详见子笔记 08。

## 3. `/proc` 与 `/sys`：内核的窗口

这两个目录不在磁盘上，是内核暴露出来的虚拟文件系统。**读它们等于向内核提问**，写它们等于直接改内核状态（有风险，见子笔记 08 的 `sysctl`）。

| 路径 | 内容 | 启动排障时用来干什么 |
| --- | --- | --- |
| `/proc/cmdline` | 本次启动的内核命令行 | 确认启动参数是否真的生效——**唯一验收标准** |
| `/proc/sys/**` | 运行时内核参数 | `sysctl` 的底层；改这里是立即生效、重启即失 |
| `/proc/<pid>/` | 某个进程的实时状态 | `status`、`wchan`、`limits`、`io` 等 |
| `/proc/meminfo` | 内存概况 | 与 `free` 对照 |
| `/sys/firmware/efi` | 固件相关对象 | 判断是不是 UEFI 启动 |
| `/sys/kernel/kexec_crash_size` | kdump 实际预留的内存 | 崩溃取证场景（子笔记 10） |

## 4. PID 1 与 init 的演化

### 4.1 内核的最后一步

内核把硬件都准备好之后，会拉起**第一个用户态进程**，它的 PID 固定是 1。这个进程再按配置把其余服务逐个拉起来——所以它是整棵进程树的根：

```bash
ps -p 1 -o pid,comm,args                    # 验证：PID 1 是谁；现代发行版上应看到 systemd
```

现代发行版上 PID 1 是 `systemd`；更早的发行版用过 SysV init 和 Upstart。这个演化过程带来一个重要的变化：

| 时代 | PID 1 | 启动单位 | 服务管理方式 |
| --- | --- | --- | --- |
| SysV init | `init` | 脚本 + 运行级别（0–6） | `/etc/init.d/` 脚本 |
| Upstart | `init` | 事件 | 已淘汰 |
| systemd | `systemd` | unit + target | `systemctl` |

「运行级别」这个词现在基本被 **target** 取代了，但面试和旧文档里还会出现，所以两者要能对上（子笔记 07 有对照表）。

### 4.2 PID 1 为什么特殊

两条必须记住的语义：

1. **它只接受自己装了处理函数的信号。** 内核在投递之前会对 1 号进程做一次特判：如果这个信号在它这里是默认处置（也就是它没有安装处理函数），内核就**直接把信号丢掉**——既不投递，也不报错。而 `SIGKILL`、`SIGSTOP` 天生不允许安装处理函数，所以它们永远到不了主机 PID 1。

   这正是 `kill -9 1` 「没反应」的原因，也是最容易被误解的地方：以 root 执行时，命令**返回成功**（信号确实发出去了），进程却什么也不做。不是权限不够，也不是内核有 bug，而是内核故意不给「误操作一条命令掀掉整个系统」留路径。想知道 PID 1 究竟装了哪些处理函数，可以读 `/proc/1/status` 里的 `SigCgt` 字段（`SIGKILL`、`SIGSTOP` 永远不会出现在里面）。
2. **它负责回收孤儿进程。** 子进程的父进程先退出时，孤儿被 PID 1 收养，退出后由 PID 1 回收，否则会留下僵尸进程。

> [!info] 和容器的关系
> 容器里的「PID 1」只是**那个命名空间内的 1 号进程**。上面这条特判只保护「从同一个 PID 命名空间内发出的信号」：从宿主机（祖先命名空间）发来的信号不受它保护，`SIGKILL` 会真的把它杀掉。反过来，`SIGTERM` 若没被它处理，仍会被丢掉——`docker stop` 先发 `SIGTERM`，要等超时后才升级到 `SIGKILL`，超时就是这么来的。深水区在阶段 3。

## 5. 观测三件套：`dmesg`、`journalctl`、`systemctl`

### 5.1 分工

| 工具                 | 数据来源          | 看到什么                | 局限                     |
| ------------------ | ------------- | ------------------- | ---------------------- |
| `dmesg`            | 内核环缓冲（内存）     | 内核与驱动的输出            | 缓冲区有限，**旧消息会被覆盖**；重启即失 |
| `journalctl`       | journald 的日志库 | 内核日志 + 服务日志 + 启动元数据 | 未持久化时只有本次启动            |
| `systemctl status` | systemd 的单元状态 | 某个服务/挂载点的状态与最近日志    | 只看单个单元                 |

日常分工是：**查服务看 `systemctl status`，查内核看 `dmesg`/`journalctl -k`，查「上次启动发生了什么」看 `journalctl -b -1`。**

### 5.2 `journalctl` 的常用姿势

```bash
journalctl --list-boots                    # 验证：本机记录了几次启动，以及各自的 boot ID
journalctl -b                             # 验证：本次启动的全部日志
journalctl -b -1 -k                       # 验证：上一次启动的内核日志（救命命令，前提是日志持久化）
journalctl -b -1 -p warning               # 验证：只看 warning 及以上级别，降低噪音
journalctl -u <unit> -b                   # 验证：某个服务本次启动的日志
journalctl -k --since "10 min ago"        # 验证：最近十分钟的内核日志
```

### 5.3 日志会不会留下来

这是 S3（取证）的第一个前提，必须在故障之前确认：

| 情况 | `--list-boots` 的结果 | 重启后能否回溯 |
| --- | --- | --- |
| `/var/log/journal/` 存在（持久化） | 多次启动 | 能 |
| 只有 `/run/log/journal/`（易失） | 通常只有一次 | **不能，现场随重启消失** |

```bash
ls -d /var/log/journal                      # 验证：有输出 = 日志持久化已启用
journalctl --disk-usage                     # 验证：日志当前占用多少磁盘
journalctl --list-boots | tail -5           # 验证：最多能回溯几次启动
```

> [!important] `dmesg -T` 的时间戳不能当证据
> `-T` 是用**当前系统时间**去换算内核内部的单调时间戳。开机早期系统时钟还没和 NTP 同步，换算出来的时间可能是错的。跨机器对齐日志要用 `journalctl -b` 加统一时区。

### 5.4 接手一台机器时先跑的检查

这一篇的动作是**巡检**，零风险、纯读，不必包成「生产动作」，给检查表和判据就够：

```bash
ls -d /var/log/journal                     # 验证：journal 是否持久化
journalctl --disk-usage                    # 验证：日志占用空间是否被限制得过小
journalctl --list-boots | tail -5          # 验证：能回溯几次启动
journalctl -b -1 -k --no-pager | tail -20  # 验证：上一次启动的内核日志是否真实可读
ls -d /var/crash 2>/dev/null               # 验证：是否配置了崩溃转储目录（进阶，见子笔记 10）
```

判据只有一条：`--list-boots` 是否多于一条。只有一条，说明这台机器**重启一次就丢一次现场**，需要先把日志持久化补上（属于阶段 9 的范围）。把结果写进巡检表，未持久化的机器提出整改项。

## 6. 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 「`lsmod` 里没有就是内核不支持」 | 功能可能已经编译进内核（builtin）；要查 `modinfo` 或看设备是否工作 |
| 出事先 `dmesg` | `dmesg` 只反映本次启动的环缓冲，且可能已被覆盖；先 `journalctl -b -1` 更稳 |
| `kill -9 1` 想重启 systemd | 静默失败，什么都不会发生；PID 1 不被投递未处理的信号 |
| 拿 `dmesg -T` 的时间戳做跨机对账 | 开机早期时钟未同步，时间戳可能是错的 |
| 以为「日志肯定都在」 | 未持久化的机器重启后只剩本次启动，`--list-boots` 只有一条 |
| 把容器里的 PID 1 当成主机的 PID 1 | 从宿主机看它只是普通进程，`kill -9` 有效；两种语义完全不同 |

## 7. 决策练习

> [!question]- 场景：凌晨 3 点，一台生产机突然重启，业务已经自动恢复。你想知道上次为什么重启
> 你第一步做什么？
> A. 先重启一次，确认是不是偶发
> B. 先 `journalctl --list-boots` 看有几次启动记录，再 `journalctl -b -1 -k -p warning` 看上一次启动的内核日志
> C. `dmesg | tail` 看看有没有报错
>
> **答案：B。**
> A 是最糟的选择：重启会继续覆盖现场，把「偶发」变成「再也查不到」。C 看到的是**本次启动**的环缓冲，与故障那一次无关。
> B 先确认「现场还在不在」（有没有多次 boot 记录），再看内容——这正是 S3 取证技能的标准顺序：**先确认证据存在，再读证据。**

## 8. 要点自测

> [!question]- 内核和普通进程是什么关系？
> - 内核是唯一直接管硬件的程序，负责调度、内存、文件系统、网络与驱动。
> - 普通进程跑在用户态，通过系统调用请内核代做特权操作；进程「卡住」往往是在等内核完成某个操作。

> [!question]- 为什么主机上的 `kill -9 1` 没有任何效果？
> - 内核只向 PID 1 投递它自己安装了处理函数的信号；未处理的信号（含 `SIGKILL`）不投递。
> - 这是防止「一条命令掀掉整个系统」的设计。容器里的 1 号进程是另一回事，从宿主机看它是普通进程。

> [!question]- `journalctl -b -1` 什么时候会失效？怎么提前避免？
> - 当 journal 没有持久化（只有 `/run/log/journal`）时，重启后只剩当前一次启动，`-b -1` 没有内容。
> - 提前做：确认 `/var/log/journal` 存在、`journald.conf` 的 `Storage` 允许持久化、磁盘与保留策略够用，并把它纳入巡检。
