# 一次启动的完整交接

这条时间主线的**对象是控制权**：从按下电源、固件拿到第一行指令，到最后一个业务单元进入 active、登录提示符出现，中间每一段的交棒条件、能观察到的证据、交不出去时的落点。主线走完，再收拢三条横切线（存储标识线、参数与模块线、证据线）。

下面这条时间线用一台具体的机器做锚点，它不是结论的适用范围，只是把抽象字段落到可核对的位置上：**Ubuntu 24.04.5 LTS（VMware 虚拟机）/ 内核 `6.8.0-139-generic` / systemd 255（`255.4-1ubuntu8.17`）/ 4 vCPU / `MemTotal` 约 7894 MiB / 根分区 ext4 on LVM / legacy BIOS + GPT 分区表**。

## 一、上电到交棒给引导加载器

**这一步在做什么。** 固件（主板上的一段程序）先做加电自检，初始化 CPU、内存控制器、显卡、网卡与存储控制器；然后按一个候选列表挑一个启动来源，把控制权交出去。它**不读你的文件系统，也不认识 Linux**——它只认启动项和引导器文件。

候选列表的形态由固件类型决定，判据是一条只读命令：

| 固件类型 | 判据 | 交棒依据 | 观察工具 |
| --- | --- | --- | --- |
| UEFI | `ls /sys/firmware/efi` **存在** | NVRAM 里的启动项列表，每项指向 ESP 上的一个 `.efi` 文件 | `efibootmgr -v`（需要 root） |
| legacy BIOS | `ls /sys/firmware/efi` **不存在** | 设备顺序；轮到某块盘就读它 LBA0 的引导扇区 | 固件设置界面；`fdisk -l` 看分区表类型 |

锚点机器走的是 legacy 路径，两个证据可以互相对上：

```text
$ ls /sys/firmware/efi          # 无输出且退出码非 0：这台机器不是 UEFI 启动
ls: cannot access '/sys/firmware/efi': No such file or directory

$ lsblk -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINT,UUID
NAME                       SIZE TYPE FSTYPE      MOUNTPOINT UUID
sda                         80G disk
├─sda1                       1M part
├─sda2                       2G part ext4        /boot      5dbd648c-63f3-4460-a25a-8d9b8d07d0ea
└─sda3                      48G part LVM2_member            tNLBbJ-8Y8J-XsVY-JV6B-t7kP-OXwD-zhygtq
  └─ubuntu--vg-ubuntu--lv   48G lvm  ext4        /          30ab1acf-de89-4031-b8fc-302216d92af6
```

`sda1` 只有 1 MiB、没有文件系统，这是 **BIOS boot 分区**——GPT 分区表的盘要在 legacy 模式下引导，就需要这么一块地方放 GRUB 的 `core.img`（MBR 分区表时代它塞在 MBR 与第一个分区之间的空隙里）。它是"legacy 也能配 GPT"这条经常被忽略的事实的实证。（顺便记住另一件事：`FSTYPE` 显示 `LVM2_member` 的 `sda3` 是物理卷，真正的根是它上面的逻辑卷 `ubuntu--vg-ubuntu--lv`；`lsblk` 的缩进关系就是这条父子关系的读法。）

**怎么读这些字段。** `ls /sys/firmware/efi` 是**存在性判据**，不是内容判据：目录在就是 UEFI 启动，不在就是 legacy，没有第三种情况；它在虚拟机与云主机上同样有效。`TYPE=part` 与 `TYPE=lvm` 的区别决定了"设备的标识是什么"：分区的标识是 PARTUUID 与文件系统 UUID，LVM 逻辑卷本身没有分区表、它的标识是卷名（`vg/lv`）与 `dm-uuid`。**与谁同看**：`lsblk` 的 `FSTYPE`/`UUID` 列要和 `/proc/cmdline` 里的 `root=` 对着看，两者对不上就说明这台机器有历史遗留配置或曾被迁移过。

**交不出去时的落点。** 黑屏、蜂鸣、固件报错页说明卡在自检；直接进固件设置界面说明候选列表为空或全部失败；`No bootable device` 说明没找到可引导设备。**这一段的输出不在操作系统日志里**——POST 报错、RAID 卡自检、PXE 尝试只出现在物理屏或带外管理（IPMI/iDRAC/iLO）的日志中。所以第一反应是先确认自己在看哪个屏幕，而不是去查 `journalctl`。

## 二、引导加载器搬内核

**这一步在做什么。** GRUB 从它读得懂的分区上把内核镜像与 initramfs 读进内存，并把一条内核命令行原样递过去。它是整条链上**唯一可交互**的一环：菜单里按 `e` 可以临时改这次启动的命令行，按 `c` 进命令行，`grub rescue>` 下还能手工把系统拉起来。

它读的配置分两层，这一层关系决定了"改哪个文件才对"：

| 层 | Debian / Ubuntu | RHEL 8/9 |
| --- | --- | --- |
| 你手写的配置 | `/etc/default/grub` | `/etc/default/grub` + `grubby` 维护的 BLS 条目 |
| 菜单项的来源 | 由 `/etc/grub.d/*` 扫描 `/boot` 下的内核生成 | 默认 BLS：`/boot/loader/entries/*.conf` |
| 生成的产物 | `/boot/grub/grub.cfg` | BIOS：`/boot/grub2/grub.cfg`；UEFI：ESP 上的 `grub.cfg` |
| 重新生成 | `update-grub` | `grub2-mkconfig -o <对应路径>` |
| 改参数的推荐入口 | 编辑 `/etc/default/grub` | `grubby --update-kernel=ALL --args=...` |

**产物是生成物，不是配置文件。** 手工改 `grub.cfg` 会在下一次内核升级或重新生成时被覆盖。RHEL 8/9 走 BLS 的机器上还有个更实际的分歧：菜单项不在 `grub.cfg` 里，而在 `/boot/loader/entries/*.conf`，所以在那类机器上 `grep grub.cfg` 常常什么都搜不到。

**这一步的可观察证据是启动参数本身。** 锚点机器上：

```text
$ cat /proc/cmdline
BOOT_IMAGE=/vmlinuz-6.8.0-139-generic root=/dev/mapper/ubuntu--vg-ubuntu--lv ro
```

三个字段各有读法。`BOOT_IMAGE=` 是引导加载器留下的痕迹，指出这次载入的是哪个内核文件，**它要和 `uname -r` 一起看**（两者不一致说明启动后有人装过别的内核）；`root=` 是根设备的标识，**要看它是"哪种标识"而不只是"值是什么"**——这台机器写的是 LVM 设备路径而不是 UUID，属于可用但不最优的写法（卷名变了就失效，而 UUID 会在 `mkfs` 时变，所以两者各有失效条件）；`ro` 表示根先以只读方式挂上，第 ④ 段再由 systemd 按 `fstab` 的决定重新挂成可写，**这是设计，不是故障**。

**交不出去时的落点。** `grub>` 说明 GRUB 本体可用、模块已加载，坏的是配置（缺失、被截断、语法错）；`grub rescue>` 说明连 `normal` 模块都没加载起来，通常是找不到 `/boot` 所在分区、或 `/boot` 里的 GRUB 模块目录不在了。这两种落点的修法不同：前者可以手工引导，后者要先用 `ls` 探明分区、`set root`/`set prefix`、`insmod normal` 把菜单找回来。**判断方向只有一条——是"找不到 `/boot`"还是"`/boot` 里的配置坏了"。**

## 三、内核接管并挂上真根

**这一步在做什么。** 内核解压自身、建立内存管理与 CPU 初始化、解析命令行、枚举总线；把 initramfs 解开到内存里的 `tmpfs`，它成为此刻的 `/`；执行其中的 `/init`，由它去找并挂载真正的根文件系统；最后 `switch_root` 把 `/` 换成真根，并在真根上启动 PID 1。

这一段的死锁与 initramfs 的存在理由在原理篇讲透了，这里只关心**它在时间线上的位置**：`/etc/fstab` 此刻**还没被读过**。这不是细节，而是排障里最容易浪费时间的误判来源——停在 initramfs shell 时去改 `fstab`，改动不会产生任何影响，因为读它的程序还没开始运行。

**这一步的可观察证据有两组，必须对着看。** 一组是"内核在找什么"，一组是"现在有什么"：

| 组 | 读什么 | 单位 / 形态 | 判据 |
| --- | --- | --- | --- |
| 它要什么 | `/proc/cmdline` 里的 `root=` | 设备标识字符串 | 是 UUID、PARTUUID、LABEL 还是设备路径 |
| 有什么 | `/dev/disk/by-uuid/`（软链）、`lsblk`（结构）、`blkid`（UUID 与类型） | 设备节点与标识 | 目标设备**在不在**这个列表里 |

分支出结论只有两种：

- 目标设备**在列表里**，但标识与 `root=` 不符 → 设备识别正常，**参数旧了**（分区被重建、系统被克隆、快照回滚过）；
- 目标设备**完全不在列表里** → 内核或 initramfs 根本没识别到那块盘，**驱动缺失或缺固件**。

这两种结论的处理方向完全相反，所以在拿到这两组读数之前不该动手。

**交不出去时的落点与报错。** `VFS: Unable to mount root fs on unknown-block(0,0)` 说明内核完全没找到根设备；`Warning: /dev/disk/by-uuid/<uuid> does not exist` 说明按 UUID 找不到；`dracut-initqueue timeout` 与 Debian 系的 `Gave up waiting for root file system device` 是"等设备超时"的两种写法；最终通常落到 `dracut:/#` 或 `(initramfs)` 的救援 shell。RHEL 系在这一层还留了一份现成的诊断报告（`/run/initramfs/rdsosreport.txt`），里面汇总了设备枚举与模块加载过程——注意它含设备序列号与 UUID，对外提交前要脱敏。

## 四、systemd 接管

**这一步在做什么。** 真根挂上、PID 1 起来之后，systemd 先跑一批生成器把非 unit 格式的配置翻译成 unit（`systemd-fstab-generator` 处理 `fstab`，`systemd-gpt-auto-generator` 处理 GPT 自动挂载，等等），再按依赖图把系统带起来，沿 well-known target 组成的链前进。

锚点机器上这一步的实际耗时分布，是一条很好的"读法示范"（**数值仅示意这一台机器，不代表你的机器**）：

```text
$ systemd-analyze
Startup finished in 4.024s (kernel) + 2.976s (userspace) = 7.001s
graphical.target reached after 2.958s in userspace.

$ systemd-analyze blame | head -5
1.301s systemd-networkd-wait-online.service
1.127s apt-daily-upgrade.service
 768ms docker.service
 603ms fwupd-refresh.service
 490ms snapd.seeded.service

$ systemd-analyze critical-chain
graphical.target @2.958s
└─multi-user.target @2.958s
  └─docker.service @2.189s +768ms
    └─network-online.target @2.187s
      └─systemd-networkd-wait-online.service @885ms +1.301s
        └─systemd-networkd.service @733ms +129ms
```

**怎么读这三个输出**（数值仅示意，不代表你的机器）：

- **`systemd-analyze` 的四段**：`firmware`、`loader`、`kernel`、`userspace`，单位是秒。它把总开机时间按"谁在跑"拆开——**如果 firmware + loader 很大而 kernel 很小，问题在固件与引导器（设备自检、菜单停留），不在 systemd**。这一段是唯一能把"开机慢"分到启动链前半段的工具。注意 `graphical.target reached after ... in userspace` 是 userspace 内部的时间，不含前两段；**而上面这段输出里只出现了 kernel 与 userspace 两段，因为这台机器的固件没有提供 firmware/loader 时间戳——看不到不等于耗时为零，见实操篇 2.1**。
- **`blame` 的每一行**：格式是"单元自身启动耗时"，单位秒（自动换算 ms/s/min）。它**不含等待依赖的时间**，所以排在第一名的常常是一个无辜的小服务。判断"它是否真的拖慢了开机"要和 `critical-chain` 对上，两者相加的量级还要与 `systemd-analyze` 的 `userspace` 段对得上。
- **`critical-chain`**：格式是 `单元 @何时开始 + 自身耗时`，时间单位同样是秒。左边缩进表示依赖层级，**关键路径上的每一项都是"如果它慢、整个开机就慢"**。上面这段输出里，关键路径是 `docker.service → network-online.target → systemd-networkd-wait-online.service`，而耗时最长的一环正是等网络就绪（1.301 s）。**转向哪一步**：这台机器要缩短开机时间，方向是"这个业务单元是否真的需要 `network-online.target`"，而不是去优化 `blame` 里那个排在第二名的定时任务。

**交不出去时的落点。** 挂载失败会把启动落到 `emergency.target`（只有根挂载、只读、要过 root 密码）；一个永远不出现的依赖会让开机卡在 `A start job is running for …（1min 30s）`——那 90 秒是 systemd 的默认单元启动超时（`man 5 systemd-system.conf`：`DefaultTimeoutStartSec`/`DefaultTimeoutStopSec` 在系统与用户管理器里默认都是 90 s），在等一个不会来的东西。

## 五、登录入口与业务服务

**这一步在做什么。** 走到 `default.target` 之后，系统提供三类入口：本地登录（各 tty 上的 `getty`）、远程登录（`sshd`）、业务服务（各自的 unit）。前两类失败属于"入口问题"，第三类才是日常排障的主战场。判断入口统一从状态查起，而不是从"重启试试"起。

**这一段的可观察证据**：`systemctl --failed` 是第一个入口（它回答"有没有东西 failed"），`systemctl status <unit>` 回答"它以什么退出码退出、退出前打了什么"，`systemctl is-enabled`/`is-active` 分别回答"下次开机要不要起"与"现在是不是在跑"。**四者不可互相替代**：一个 `enabled` 的单元可能当前 `failed`，一个 `active` 的单元可能 `disabled`（本次是手工起的）。

## 六、三条横切线

时间主线讲完，把横穿多个环节的三件事收拢起来。

### 6.1 存储标识线：从"一块盘"到"`root=`"

贯穿第 ①③④ 段的一条线是**设备怎么被标识**。同一块盘在不同层有不同的名字，而且每个名字都有自己的失效条件：

| 标识 | 属于谁 | 什么时候变 | 用在哪 |
| --- | --- | --- | --- |
| `/dev/sdX` | 内核枚举顺序 | 插拔、换控制器、换虚拟化平台都可能变 | **禁止用于持久配置** |
| 文件系统 UUID | 文件系统 | 重新 `mkfs` 会变 | `fstab`、`root=UUID=` |
| PARTUUID | 分区 | 重建分区表会变 | GPT 环境下的启动项、`root=PARTUUID=` |
| LABEL | 文件系统 | 手工改名才变，但可重名 | 可读性好，多盘时容易歧义 |
| 卷名（`vg/lv`）/ `dm-uuid` | LVM / dm-crypt 设备 | 改名或重建卷会变 | LVM 设备路径、`rd.lvm.lv=` |

这条线的收口是：**"分区迁移/克隆系统之后起不来"十次里有八次是这条线上某个名字变了而某处配置没跟着变**。而因为它横穿三段（启动项、`root=`、`fstab`），所以修的时候必须三段都核对——只改一处就会以"改了还是起不来"的形式再暴露一次。

### 6.2 参数与模块线：谁在什么时候读它

第二条横切线是**配置在时间轴上被读取的时刻**。同一个值写在不同位置，生效时刻差着几秒到几个阶段：

| 载体 | 何时被读 | 生效范围 | 不改就重启会怎样 |
| --- | --- | --- | --- |
| 内核命令行（`/proc/cmdline`） | 内核解析阶段，第 ③ 段最开头 | 本次启动的整个生命周期 | 永远不生效（值根本没传进去） |
| initramfs 的内容 | 第 ③ 段 | 第 ③ 段 | 永远不生效（归档里没有） |
| 模块参数（`/etc/modprobe.d/`） | 模块加载那一刻 | 该模块 | 取决于模块何时加载 |
| `fstab` | 第 ④ 段开头（生成器） | 本次运行 + 每次开机 | 只有下次开机才生效 |
| `sysctl` 配置（`/etc/sysctl.d/`） | 第 ④ 段早期（`systemd-sysctl`） | 本次运行 + 每次开机 | 只有下次开机才生效 |
| unit 文件 | 第 ④ 段（单元被装载时） | 该单元 | `daemon-reload` 后可当场生效 |

**读法**：看到"配置写了却不生效"，先把那个值定位到这张表的一行，再问"它被读的时刻过了没有"。这一条比记任何具体参数名都有用。

### 6.3 证据线：现场在哪一段，什么时候消失

第三条横切线回答"我该去哪取证、能取多久"。它的依据是**证据存在哪一层介质上**：

| 证据 | 介质 | 消失条件 | 取证命令 |
| --- | --- | --- | --- |
| 固件/POST 输出 | 物理屏、带外 SEL 日志 | 屏幕滚动、日志被覆盖 | 带外控制台、BMC 的 SEL |
| GRUB 提示符与它报的错 | 屏幕 | 重启 | 先看清、拍照 |
| initramfs shell 与 `rdsosreport.txt` | 内存 | **重启即失** | 在 shell 里导出（RHEL 系） |
| 内核环缓冲（`dmesg`） | 内存，有容量上限 | 重启、或被新日志挤掉 | `dmesg`、`journalctl -k -b` |
| journal 的本机日志 | 磁盘（**前提是持久化**） | 轮转、清理、保留期到期 | `journalctl -b -1`、`--list-boots` |
| `vmcore` | 磁盘或远端 | 手工清理 | `ls -lt /var/crash/` |
| 启动耗时数据 | 内存（来自内核与 systemd 的时间戳） | 重启 | `systemd-analyze` |

**读法**：这张表的用法是反着查——先问"这段现场在哪一层介质上"，就知道它会不会在重启时消失，从而决定"先取证还是先止损"。凡是介质一栏写"内存"的，重启就等于删除。

## 七、常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 拿到"起不来"就先重启 | 介质是内存的那几类现场（环缓冲、initramfs shell、启动耗时）重启即失 |
| 在固件阶段查系统日志 | 那时操作系统还没运行，`journalctl` 里不可能有相关内容 |
| 在 initramfs shell 里改 `fstab` | `fstab` 要到第 ④ 段才被读，改动不产生任何影响 |
| 只改一处就以为修好了 `root=` 问题 | 启动项、`root=`、`fstab` 分属三段，必须各自核对 |
| 只看 `blame` 就断定"哪个服务拖慢了开机" | `blame` 不含等待依赖的时间，要和 `critical-chain` 对上 |
| 用 `systemd-analyze` 判断固件慢 | 它确实分出了 `firmware`/`loader` 两段，但固件侧的细节（POST 卡在哪、RAID 卡自检多久）只在带外日志里 |
| 看到 `ro` 就认为根分区坏了 | 根先只读挂载、再由 systemd 重挂可写是设计；`/proc/cmdline` 里的 `ro` 是启动参数，不是结论 |
| 把 `sda1` 这种 1 MiB 分区当成"废弃分区"删掉 | GPT 盘在 legacy 模式下引导，`core.img` 就放在这个 BIOS boot 分区里 |

## 要点自测

**问：为什么 `systemd-analyze blame` 的第一名常常不是真正拖慢开机的单元？**

答：`blame` 排的是**单元自身**的启动耗时，不含它等待依赖的时间。真正决定开机时长的是 `critical-chain` 上的关键路径——那上面每一项的耗时与等待都会累加进总时长。只看 `blame` 会优化一个不在关键路径上的服务，开机时间一点不变。

**第一反应不要做什么**：不要照着 `blame` 的顺序去"优化"服务，先看 `critical-chain` 的关键路径上是谁在等。

**问：一台机器停在 initramfs shell。你要回答哪两个问题，用哪两组命令？**

答："它要什么"——`cat /proc/cmdline` 里的 `root=`；"现在有什么"——`ls /dev/disk/by-uuid/`、`lsblk`、`blkid`。目标设备在列表里但标识不符，是参数旧了；完全不在列表里，是驱动或固件缺失。这两类结论的处理方向相反，所以两组读数都要拿到再动手。

**第一反应不要做什么**：不要先改 `fstab`，也不要反复重启。前者的改动此刻不起作用，后者会把这唯一的现场清掉。

**问：`/proc/cmdline` 里的 `ro` 是什么意思？为什么它不代表根分区有问题？**

答：它表示根文件系统先以只读方式挂载。这是设计的一部分：第 ③ 段挂根、第 ④ 段 systemd 起来后按 `fstab` 的决定重新挂成可写。它也是救援场景里的重要前提——`emergency.target` 与 `rd.break` 下根默认只读，改任何东西之前要先重挂可写。

**第一反应不要做什么**：不要因为看到 `ro` 就去修 `fstab` 或怀疑文件系统损坏。

**问：为什么"分区迁移之后起不来"常常要改不止一处？**

答：因为设备标识横穿三段：第 ① 段的启动项（UEFI 下指向 ESP 上的路径与分区）、第 ② 段菜单项里的 `root=` 与 initrd 路径、第 ④ 段 `fstab` 里的挂载来源。同一块盘在三处的标识可能分别是 PARTUUID、文件系统 UUID 与卷名，迁移或重建后它们各自变化，不会一起更新。只改一处，就会以"改了还是起不来"的形式再暴露一次。

**第一反应不要做什么**：不要在没核对完三段的情况下就重启验证——远端机器上每次错误重启都可能是一次失联。

## 参考文档

- `man 7 bootup`、`man 7 systemd.special`、`man 5 systemd.target`：启动过程与 target 体系的权威描述。
- `man 1 systemd-analyze`：`time`、`blame`、`critical-chain`、`plot` 各子命令的输出格式与限制。
- `man 5 systemd-system.conf`：`DefaultTimeoutStartSec`/`DefaultTimeoutStopSec` 的默认值（系统与用户管理器均为 90 s）。
- `man 8 systemd-fstab-generator`、`man 5 systemd.mount`、`man 5 fstab`：`fstab` 到挂载单元的翻译与 `nofail` 的准确语义。
- `man 8 lsblk`、`man 8 blkid`、`man 8 findmnt`、`man 8 efibootmgr`、`man 8 fdisk`：设备、文件系统、挂载与固件侧的观测入口。
- `man 1 journalctl`、`man 5 journald.conf`：journal 的持久化与回溯能力。
- 内核 6.x 文档 `Documentation/admin-guide/initrd.rst`、`Documentation/admin-guide/kernel-parameters.rst`、`Documentation/admin-guide/sysctl/`。内核文档一律按与目标机器同一主版本取（当前基线 6.x）——同一条路径在不同版本里可能同名而内容不同；另外，`man 7 bootup` 里也明确写了引导过程高度并行、到达各 target 的先后并不确定，本文第四节的顺序描述读作"典型顺序"而非保证。
