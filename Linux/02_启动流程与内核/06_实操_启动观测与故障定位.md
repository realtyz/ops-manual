# 启动观测与故障定位

## 1. 一个问题，一把工具

启动排障的第一个约束是：**能用的工具有一半只在特定阶段存在**。`journalctl` 在第 ③ 段不存在，`efibootmgr` 在 legacy 机器上不存在，`dracut` 在 Debian 系不存在。所以下表把"想知道什么"和"这段现场还在不在"一起给出。

| 你想知道 | 用什么 | 关键字段或文件 |
| --- | --- | --- |
| 这台机器是 UEFI 还是 legacy | `ls /sys/firmware/efi` | 目录**存在与否**本身就是结论 |
| UEFI 的启动项与顺序 | `efibootmgr -v`（root） | `BootOrder`、条目名后的 `*`（启用）、`File(\…\.efi)` 路径 |
| 这台机器装了哪几套内核与 initramfs | `ls -l /boot/` | `vmlinuz-*`、`initrd.img-*`（Debian）/`initramfs-*.img`（RHEL）、`vmlinuz.old` 这类软链 |
| 这次启动实际用的内核与参数 | `uname -r`、`cat /proc/cmdline` | `BOOT_IMAGE=`、`root=`、`ro`/`rw`、`console=` |
| 各段（固件/引导器/内核/用户态）耗时 | `systemd-analyze` | 四段秒数 |
| 谁拖慢了开机 | `systemd-analyze critical-chain`、`… blame` | `critical-chain` 的 `@开始 +自身耗时`；`blame` 只是单元自身耗时 |
| 还有哪些 job 卡着 | `systemctl list-jobs` | 状态为 `running`/`waiting` 的 job 及其依赖 |
| 有没有单元失败 | `systemctl --failed`、`systemctl status <unit>` | `Active:`、退出码、最近日志 |
| 这次启动的内核日志 | `journalctl -k -b`、`dmesg -T` | 驱动与固件加载错误 |
| 上一次启动发生了什么 | `journalctl --list-boots`、`journalctl -b -1 -k -p warning` | boot 列表与上一轮内核日志（**前提是持久化**） |
| 日志会不会留过重启 | `ls -d /var/log/journal`、`journalctl --disk-usage` | 目录存在 = 持久化 |
| 根设备与 `root=` 是否一致 | `lsblk -f`、`blkid`、`findmnt /`、`ls -l /dev/disk/by-uuid/` | UUID/PARTUUID/LABEL 与设备映射 |
| 根是怎么被挂载的 | `findmnt /`、`cat /etc/fstab` | `SOURCE`、`FSTYPE`、`OPTIONS` |
| initramfs 里装了什么 | `lsinitramfs`（Debian）、`lsinitrd`（RHEL） | 模块、`conf/` 下的配置、`scripts/` 下的流程 |
| 谁被判定为失败挂载 | `systemctl status <路径>.mount` | 单元名由路径转义（`/mnt/data` → `mnt-data.mount`） |
| 有没有抓到崩溃转储 | `ls -lt /var/crash/` | 时间戳目录、`vmcore`、`vmcore-dmesg.txt` |
| 内核为崩溃预留了多少内存 | `/proc/cmdline` 里的 `crashkernel=`、`/sys/kernel/kexec_crash_size` | 参数值与实际字节数 |
| SysRq 能做什么 | `sysctl kernel.sysrq`、`/etc/sysctl.d/10-magic-sysrq.conf` | 位含义（见第 2.6 节） |

表里的"用什么"分两类，**分不清类别时看 man 节号**：`man 1`/`man 8` 是命令，`man 2` 是系统调用，`man 5` 是文件格式（`fstab`、`journald.conf`、`systemd.mount` 都在这里）。`/proc`、`/sys` 下的路径是**内核接口文件**，直接 `cat` 就能读，不需要任何工具——它们也不是磁盘上的文件。

按风险给这张表分个层，这一层本身就是纪律：

- **只读、生产机上随时可做**：`ls /sys/firmware/efi`、`cat /proc/cmdline`、`systemd-analyze`、`systemctl --failed`、`journalctl`、`findmnt`、`lsblk`、`lsinitramfs`、`ls -lt /var/crash/`。
- **需要 root、但仍只读**：`efibootmgr -v`、`blkid`、`dmesg`（部分发行版限制）。
- **写操作，只在实验机或有变更窗口时做**：`efibootmgr -o`/`-c`、`grub-install`、`update-grub`/`grub2-mkconfig`、`update-initramfs`/`dracut -f`、`sysctl -w`、改 `/etc/fstab`。
- **破坏性，只在可快照的实验机上做**：`echo c > /proc/sysrq-trigger`、写坏 `fstab`、在 GRUB 里加 `rd.break` 改认证文件。

写操作那一档只有边界，退路要单独设计。这类动作的共同点是**改的是"下次启动要读的文件"**（见体系篇"段与段之间是单向的"），所以退路必须落在三层上：改之前把现状存下来（`efibootmgr -v > /root/efiboot-$(date +%F).txt`、`cp /etc/default/grub /etc/default/grub.bak.$(date +%F)`、`grubby --info=ALL > /root/boot-$(date +%F).txt`）；改的时候**只动输入层、只追加不删除**（启动项只调顺序不删条目）；改完之后按"回滚动作"一层层撤回——`efibootmgr -o <原顺序>`、恢复 `/etc/default/grub` 备份后重新生成、`grubby --update-kernel=ALL --remove-args="<参数>"`。**动启动项与内核参数之前，先确认机器上至少还有一个能起来的旧内核**（判据：`ls -1 /boot/vmlinuz-*` 的条数 ≥ 2）；已经起不来时，唯一还能用的现场手段是在 GRUB 菜单按 `e` 临时改一次参数。

## 2. 怎么读这些数字

下面每一项都给五件事：**是什么、单位、多少算异常（或只能与自己的基线比）、和谁一起看、看到它转向哪一步**。文中的输出样例只用来展示**格式**，数值不代表你的机器。以下样例取自金标准环境（Ubuntu 24.04.5 / 内核 6.8.0-139-generic / systemd 255 / 4 vCPU / 根为 ext4 on LVM / legacy BIOS + GPT）。

### 2.1 `systemd-analyze`：把开机时间分成四段

```bash
systemd-analyze                      # 验证：固件/引导器/内核/用户态四段耗时
systemd-analyze blame | head -20     # 验证：单元自身耗时排行
systemd-analyze critical-chain       # 验证：关键路径上是谁拖住了开机
systemd-analyze plot > /tmp/boot.svg # 验证：时间线可视化（只读，输出到 /tmp）
```

```text
Startup finished in 4.024s (kernel) + 2.976s (userspace) = 7.001s
graphical.target reached after 2.958s in userspace.
```

- **是什么**：`time`/默认子命令把开机时间按"谁在跑"拆成 `firmware`、`loader`、`kernel`、`userspace` 四段。
- **单位与量级**：四段都是秒，精确到毫秒；这一段的量级在几秒到几十秒之间（`firmware` 在带 RAID 卡自检的物理机上可以达到几十秒）。
- **多少算异常**：没有通用阈值，**只能与自己机器的基线比**。两台配置相近的机器上同一段的差距超过一倍才值得深究。
- **与谁同看**：`firmware`+`loader` 大而 `kernel` 小 → 问题在固件与引导器（自检、RAID 卡初始化、菜单停留），不在 systemd；`userspace` 大 → 转 `blame` 与 `critical-chain`。
- **转向哪一步**：`firmware`/`loader` 异常 → 查带外日志与固件设置里的启动顺序；`userspace` 异常 → 第 2.2 节。

上面这段输出里**只出现了 kernel 与 userspace 两段**，这不是被截断：那两段的耗时来自固件在启动时留给内核的时间戳，**固件不提供这些时间戳时（不少虚拟机与部分云主机如此），对应的段就整个不显示**。锚点机器上 `FirmwareTimestampMonotonic` 与 `LoaderTimestampMonotonic` 都是 0（`busctl get-property org.freedesktop.systemd1 /org/freedesktop/systemd1 org.freedesktop.systemd1.Manager FirmwareTimestampMonotonic` 可现场核），所以它的输出没有这两段。**读法上的推论是：看不到 `firmware`/`loader` 不等于它们耗时为 0，而是这段信息没有被记录**——要判断固件侧耗时，只能靠带外日志的时间戳或物理秒表。

锚点机器上这段输出还有一处很实际的读法：`graphical.target reached after 2.958s in userspace` 与 `userspace` 段 2.976 s 几乎相等，说明用户态几乎没有额外等待就到达了默认目标；而 `critical-chain` 显示关键路径的末端是 `systemd-networkd-wait-online.service`（1.301 s）——**这台机器缩短开机的方向是网络依赖，不是 `blame` 排名里的定时任务**。

### 2.2 `blame` 与 `critical-chain`：先看关键路径，再看耗时排行

```text
$ systemd-analyze critical-chain
graphical.target @2.958s
└─multi-user.target @2.958s
  └─docker.service @2.189s +768ms
    └─network-online.target @2.187s
      └─systemd-networkd-wait-online.service @885ms +1.301s
        └─systemd-networkd.service @733ms +129ms
```

- **是什么**：`critical-chain` 的每一项形如 `单元 @开始时刻 +自身耗时`，缩进表示依赖层级；`blame` 是按自身耗时降序排的单元清单。
- **单位与量级**：两个输出里的时间都是秒（自动换算成 `ms`/`s`/`min`），精确到毫秒；用户态单元的自身耗时量级通常是毫秒到几百毫秒，秒级及以上的单元才值得看一眼。
- **判据**：**关键路径上的每一项都是"它慢则开机慢"**；不在关键路径上的单元再慢也不影响总时长（它与其他单元并行）。
- **与谁同看**：`blame` 的排名。两者出现分歧时以 `critical-chain` 为准，因为 `blame` **不含等待依赖的时间**——例如一个单元自身只花了几十毫秒、却卡在 `After=` 指向的某个 90 s 超时上，它在 `blame` 里毫不起眼。两者的总耗时要与 `systemd-analyze` 的 `userspace` 段量级一致。
- **转向哪一步**：看到 `+` 后面特别大 → 查该单元自身（`systemctl status`、它的日志）；看到 `@` 与上一行的 `@` 之间有大空隙 → 那是排序等待，查 `After=`/`Wants=` 的写法。

### 2.3 `systemctl` 的三个状态问题

```bash
systemctl --failed                    # 验证：当前有哪些单元处于 failed（第一入口）
systemctl status <unit>               # 验证：单个单元的状态、退出码与最近日志
systemctl is-enabled <unit>           # 验证：下次开机要不要起（enabled/disabled/static）
systemctl is-active <unit>            # 验证：现在是不是在跑
```

- **是什么**：`--failed` 是筛选视图，`status` 是详情（含 `Active:` 行、`Main PID`、退出码、最近若干行日志），`is-enabled`/`is-active` 是脚本友好的单值判断。
- **单位与量级**：这里要读的"数"是退出码与状态词，不是量。`is-enabled` 的取值是 `enabled`/`disabled`/`static`/`masked` 一类，`is-active` 是 `active`/`inactive`/`failed`/`activating`；`status` 里的退出码写成 `status=<数字>/<大写名>`，量级含义是"进程怎么结束的"（0 正常、1 一般失败、203 可执行文件找不到、128+N 死于信号）。
- **判据**：`is-enabled` 与 `is-active` 是**两个独立的问题**，一个 `enabled` 的单元可能当前 `failed`，一个 `active` 的单元可能 `disabled`（本次是手工起的）。排"服务没起来"必须两个都问。
- **与谁同看**：`status` 里的退出码要和日志一起看——一个以 `status=203/EXEC` 退出的服务是"可执行文件找不到"，方向在路径与权限；以 `status=1/FAILURE` 退出的要看它自己的报错输出。
- **转向哪一步**：`--failed` 有内容 → `status` 看具体单元 → 是 `.mount` 失败则转挂载与 `fstab`；是服务失败则转该服务的日志。

### 2.4 `journalctl`：能回溯多久，取决于介质

```bash
journalctl --list-boots               # 验证：本机记录了几次启动（决定还有没有历史现场）
journalctl -b -1 -k -p warning        # 验证：上一次启动的内核警告与错误（降噪后的救命命令）
journalctl -k -b --no-pager | head -50 # 验证：本次启动的内核日志开头（早期阶段的现场）
ls -d /var/log/journal                # 验证：有输出 = journal 持久化已启用
```

```text
IDX BOOT ID                          FIRST ENTRY                 LAST ENTRY
 -1 decad510b934454f9d61aef2aa2893fd Sat 2026-09-19 07:55:24 UTC Sat 2026-09-19 13:58:54 UTC
  0 7aede980e7204a12a1c8e0081732029e Sun 2026-09-20 12:09:13 UTC Sun 2026-09-20 14:10:45 UTC
```

- **是什么**：`--list-boots` 的 `IDX` 列是相对本次启动的序号（`0` 是本次，`-1` 是上一次），`BOOT ID` 是本次启动的标识。`FIRST/LAST ENTRY` 是该次启动日志的时间范围。
- **单位与量级**：`IDX` 是无单位整数（负数表示更早的启动），`FIRST/LAST ENTRY` 是本地时区的时间戳（可用 `--utc` 换成 UTC）；`--disk-usage` 的输出单位是字节或 MiB/GiB，量级从几 MiB 到几百 MiB 不等。
- **判据**：**只有 `0` 一行 = 这台机器重启一次就丢一次现场**。这是取证能力的前置条件，要在故障之前确认。
- **与谁同看**：`journalctl --disk-usage`（日志占用）与 `journald.conf` 的保留策略（`Storage=`、`SystemMaxUse=`、`MaxRetentionSec=`）。空间被限制得过小时，历史 boot 会因为轮转而消失。还有一道与容量无关的闸门：`RateLimitIntervalSec=`/`RateLimitBurst=` 的限流（systemd 255 的默认是"每 30 秒 10000 条、按服务分别计算"，见 `man 5 journald.conf`），超出的消息会被**直接丢弃**并留一条汇总消息——启动瞬间日志爆发时，一轮启动的早期日志可能就丢在这里，而 `--list-boots` 看起来完全正常。注意本机不一定有 `/etc/systemd/journald.conf`（金标准机器上就没有），不存在时全部按手册默认值读。
- **转向哪一步**：`--list-boots` 只有一行 → 先补持久化（属于日志与监控主题），并注意本次故障之后的所有重启都在继续消耗这唯一的现场；有多行 → 直接进 `-b -1`。

`dmesg -T` 的时间戳**不能当跨机对账的证据**：`-T` 是用当前系统时间换算内核内部的单调时间戳，而开机早期系统时钟还没与时间源同步，换算结果可能是错的。跨机器对齐要用 `journalctl -b` 加统一时区。

### 2.5 `fstab` 与挂载单元：先看它变成了什么

```bash
findmnt /                             # 验证：根文件系统实际挂在哪个设备、什么类型、什么选项
findmnt --verify                      # 验证：fstab 语法与选项是否被支持（会打印警告）
cat /etc/fstab                        # 验证：声明式的挂载清单
systemctl status data.mount           # 验证：该挂载点在 systemd 眼里的状态与失败原因
```

- **是什么**：`findmnt /` 给出**内核视角的事实**（此刻真的挂成了什么样），`/etc/fstab` 给出**声明**（开机时应该挂成什么样）。两者不一致就是问题所在。
- **单位与量级**：这一组输出里没有"数值"可读，读的是**取值本身**——`SOURCE` 是设备标识（UUID、`/dev/mapper/...`、`/dev/sdX` 中的哪一种）、`FSTYPE` 是文件系统类型、`OPTIONS` 是挂载选项串、`systemctl status` 的 `Active:` 是状态词。所以判据只能建立在"声明与事实是否一致"上。
- **多少算异常**：没有数值阈值，**只能与自己的声明比**：`findmnt` 显示的 `SOURCE` 与 `fstab` 里该挂载点的来源写法，指的**是不是同一个设备**；`OPTIONS` 里是否出现了与声明不符的 `ro`。`findmnt --verify` 的警告要当真——`x-systemd.*` 这类选项拼错时 `mount -a` 可能只给警告就过去。
- **与谁同看**：`systemctl --failed` 里的 `.mount` 单元、内核日志里的挂载错误行。
- **转向哪一步**：声明与事实不符 → 分清是"设备不在"（标识问题，改 `fstab` 的来源写法）还是"设备在但挂不上"（文件系统损坏或选项问题）；前者改配置，后者要评估数据风险。

挂载单元的名字由路径转义而来：`/boot` → `boot.mount`、`/data` → `data.mount`、`/mnt/data` → `mnt-data.mount`。改完 `fstab` 后运行中的 systemd 不会自动知道——`systemctl daemon-reload` 让生成器重跑，或者等下次启动。

### 2.6 内核参数：按载体问，不按名字问

```bash
cat /proc/cmdline                                   # 验证：启动参数（唯一验收标准）
sysctl vm.swappiness kernel.pid_max kernel.sysrq    # 验证：运行时参数（写入即生效）
grep -r '<参数名>' /etc/default/grub /etc/sysctl.d/ # 验证：它到底被写在哪一层
sysctl --system                                     # 验证：重新应用全部 sysctl 配置，观察失败与覆盖
```

```text
kernel.pid_max = 4194304
vm.swappiness = 60
kernel.sysrq = 176
```

- **是什么**：`/proc/cmdline` 是启动参数（只在启动瞬间生效，改完必须重启）；`sysctl` 读的是 `/proc/sys/**`（运行时参数，写入即生效）。两者名字可能相似甚至指同一概念，机制完全不同。
- **单位与量级**：启动参数是一串**无单位的字符串**（`key=value` 与开关混排），没有"量级"可读；运行时参数的值**各自带自己的量纲**，必须逐个看文档——`kernel.pid_max` 是进程数上限（锚点机器上是 4194304）、`vm.swappiness` 是无量纲的 0~200 权重（锚点机器上是 60）、`kernel.sysrq` 是位掩码（锚点机器上是 176）。**把这三个数放一起读是没意义的**，它们不是同一类量。
- **`kernel.sysrq` 的读法**：它是**位掩码**，不是开关。`0` 全关、`1` 全开、大于 1 时各位相加：2 = 控制台日志级别、4 = 键盘控制、8 = 进程调试转储、16 = `sync`、32 = 重挂只读、64 = 信号（term/kill/oom-kill）、128 = 重启/关机、256 = RT 任务降级。锚点机器（Ubuntu 24.04.5 / 内核 6.8.0-139-generic）上的 `176 = 128 + 32 + 16`，即允许重启/关机、重挂只读与 `sync`，**不允许**进程转储与信号类操作——这解释了为什么 `echo c > /proc/sysrq-trigger` 之前要先确认这一位（`8`）是否被允许。
- **判据**：`sysctl <名字>` 报 `cannot stat` 有两种原因——名字写错（层级用点号），或对应模块没加载（参数在模块加载后才存在）。启动参数的判据是"在不在 `/proc/cmdline` 里"，只有有/没有两种结果。
- **与谁同看**：配置文件名与编号。所有 `/etc/sysctl.d/*.conf` 按文件名字典序应用、后者覆盖前者，而多数发行版有一条 `99-sysctl.conf` 软链，编号小于它的文件（例如常见的 `50-`、`10-`）会被盖掉（完整规则见原理篇第 3 节，这里只用到"编号"这一条）。
- **转向哪一步**：改了没生效 → 先确认改的是哪一套（`/proc/cmdline` 里有没有？`sysctl` 读到的值是什么？）→ 再看配置文件编号与目录优先级。

### 2.7 崩溃相关：三件事决定"能不能拿到现场"

```bash
cat /proc/cmdline | tr ' ' '\n' | grep crashkernel   # 验证：为捕获内核预留了多少内存
cat /sys/kernel/kexec_crash_size                     # 验证：内核实际保留的字节数（0 = 没预留）
ls -lt /var/crash/                                   # 验证：历史上抓到过哪些崩溃
journalctl --list-boots                              # 验证：还能回溯几次启动
```

- **是什么**：`/sys/kernel/kexec_crash_size` 的单位是字节，直接反映"崩溃时有没有地方让捕获内核落脚"；`/var/crash/<时间戳>/` 每个目录对应一次崩溃，里面通常有 `vmcore` 与 `vmcore-dmesg.txt`。
- **判据**：`kexec_crash_size` 为 0 说明 `crashkernel=` 没生效或环境禁用了 kexec——此时任何"重启后看原因"的期待都会落空。`vmcore-dmesg.txt` 是不需要调试信息就能读的一份文本证据。
- **与谁同看**：转储目标的空间（根分区或远端）、`kdump` 服务的状态、带外/串口日志（无 kexec 环境下的唯一来源）。
- **转向哪一步**：`kexec_crash_size` 非 0 且 `/var/crash/` 有目录 → 进分析；为 0 或目录为空 → 转带外日志，并把"补 kdump 并演练"列为整改项。

## 3. 采样纪律与基线

启动相关的观测绝大多数是**单次、快照式**的（读一次 `/proc/cmdline`、跑一次 `systemd-analyze`），所以纪律的重点不是采样频率，而是**口径与留存**：

1. **同一口径、带时间戳**：把 `uname -r`、`cat /proc/cmdline`、`lsblk -f`、`systemctl get-default`、`systemd-analyze` 的输出一次性存成一份带时间的文件。跨机器比较时，机器规格与启动模式（UEFI/legacy、是否虚拟化）必须一起记，否则数字没有可比性。
2. **至少两次**：`systemd-analyze` 的首次启动会被缓存与一次性任务（设备首次初始化、定时任务抓取）拉长，**连做两三次取稳定值**再下结论。
3. **留原始输出**：不要只抄一个"开机 7 秒"。原始输出里才有 `firmware`/`loader` 的分段、关键路径的层级、以及错误行。
4. **改动前后各取一次**：任何启动相关变更的验收都是"前后对照"，没有前置基线就无法回答"变了吗"。

一份够用的**启动基线卡**长这样（字段就是上表的只读那一层）：

| 栏目 | 来源 |
| --- | --- |
| 发行版、内核、systemd、cgroup 版本 | `cat /etc/os-release`、`uname -r`、`systemctl --version` |
| 启动模式与分区表类型 | `ls /sys/firmware/efi`；`fdisk -l` 的 `Disklabel type` |
| 根设备与 `root=` 的一致性 | `findmnt /`、`cat /proc/cmdline`、`lsblk -f` |
| `/boot` 与 ESP 的角色与剩余空间 | `findmnt /boot`、`df -h /boot`、`findmnt /boot/efi` |
| 已装内核套数与默认启动项 | `ls -1 /boot/vmlinuz-*`、`systemctl get-default` |
| journal 是否持久化、能回溯几次 | `ls -d /var/log/journal`、`journalctl --list-boots`、`journalctl --disk-usage` |
| 崩溃取证能力 | `/proc/cmdline` 里的 `crashkernel=`、`/sys/kernel/kexec_crash_size`、`ls /var/crash/` |
| 救援通道 | 带外管理地址与类型、串口参数、能否在系统未启动时看到画面 |

## 4. 常见故障与排查方向

下面每个场景都写成"现场什么样 → 先看什么 → 看到什么转向哪 → 一份合格的回答长什么样"。场景里的机器规格、时间与数值都是具象设定，用来练判断，不代表你的环境。

### 场景一：虚拟机迁移平台后卡在 initramfs shell

**现场**：一台原本运行正常的业务虚拟机，从 A 虚拟化平台迁到 B（磁盘整体迁移）。重启后带外控制台显示 `VFS: Unable to mount root fs on unknown-block(0,0)`，随后落入 `(initramfs)`。

**先看什么**：在 initramfs shell 里取两组读数。

```bash
cat /proc/cmdline                    # 验证：它在找哪个根设备（对照下一行的实际设备）
ls /dev/disk/by-uuid/                # 验证：现在能识别到哪些设备标识（与 root= 的值对比）
lsblk                                # 验证：磁盘与分区的识别情况（为空说明驱动层就没认到）
```

**看到什么转向哪**：

- `root=` 里的 UUID **出现在** `by-uuid` 列表里 → 参数与设备都在，转去查文件系统类型与 initramfs 里是否有对应模块。
- `root=` 里的 UUID **不出现**，但 `lsblk` 能看到磁盘与分区 → 分区被重建过、UUID 变了，属于**参数旧了**：进系统后更新 `root=`，改完必须复查 `/proc/cmdline`。
- `lsblk` 里**连磁盘都看不到** → 新平台的存储控制器驱动不在 initramfs 里，属于**驱动缺失**：补进 initramfs 配置后重建，跨平台迁移的场景还要用"通用镜像"而不是"只含本机驱动"的模式。

**一份合格的回答**：结论（哪一层的问题）＋依据（`/proc/cmdline` 与 `by-uuid`/`lsblk` 的对比结果）＋边界（这条结论只在"设备识别层"成立，若两者都正常则问题在别处）＋动作（改 `root=` 还是补驱动重建，以及各自的验证与回退）。

### 场景二：内核升级重启后，`uname -r` 是新的，但网卡没了

**现场**：一台装了第三方网卡驱动（经 DKMS 编译）的机器完成内核升级并重启。`uname -r` 显示新内核，`systemctl --failed` 有内容，`ip a` 只有 `lo`，业务不可达。

**先看什么**：先取证，再决定修还是回滚——**现场还在，但会被后续操作覆盖**。

```bash
journalctl -b -k | grep -i -E 'unknown symbol|verification failed|firmware'  # 验证：驱动为什么没起来
lsmod | grep <驱动名>                # 验证：该模块当前是否以模块形式加载着
modinfo <驱动名>                     # 验证：模块文件属于哪个内核版本（modules 目录路径）
dkms status                          # 验证：DKMS 模块在新内核上是否有 built/installed 记录
```

**看到什么转向哪**：

- DKMS 里该模块在新内核上**没有 built/installed 记录** → 编译失败（缺少内核头文件、编译器版本、源码不兼容）。补依赖后重新编译，或回滚到旧内核。
- 模块存在但 `journalctl -k` 里是 `Unknown symbol in module` → 模块与内核不匹配（手工编译的旧驱动），要按当前内核重编。
- 日志里是 `module verification failed` / `Key was rejected by service` → Secure Boot 的签名校验拦下了它，走发行版签名模块或 MOK 注册流程。
- 三种都不是，日志里干脆没提这个设备 → 转去确认设备本身有没有被枚举（`lspci`、`dmesg` 尾部的设备探测记录）。

**一份合格的回答**：结论（驱动层还是设备层）＋依据（DKMS 状态、`journalctl -k` 的具体报错行）＋边界（真机与虚拟机的驱动来源不同，这条结论对虚拟机的虚拟网卡不适用）＋动作（重编模块 / MOK 注册 / 回滚旧内核，附各自的回退）。**回滚前先把失败那次的日志存下来**，否则根因与现场一起丢。

### 场景三：远端机器改完 `fstab` 重启后失联

**现场**：一次运维变更往 `fstab` 里新增了一行数据盘挂载，没有加 `nofail`。重启后 SSH 不通，带外控制台显示 `You are in emergency mode`，并提示输入 root 密码。

**先看什么**：这是在**根已经挂上、可以动手修**的环境里，第一目标是看清"哪个单元 failed"，而不是重演一遍。

```bash
systemctl --failed                          # 验证：当前有哪些单元 failed（这类场景多半是 .mount）
journalctl -xb | grep -i -A5 'failed to mount'   # 验证：挂载失败的具体设备与原因
mount -o remount,rw /                       # 验证：紧急模式下根通常只读，改配置前先确认可写
```

**看到什么转向哪**：

- 失败的是**刚加的那一行** → 先 `mount -a` 确认报错指向哪一行，再改 `fstab` 或把该项补上 `nofail,x-systemd.device-timeout=10s`。
- 失败的是一个**老挂载点**，与本次变更无关 → 说明它一直是隐患，本次重启才暴露；同样先修到能启动。
- 失败的是 `systemd-fsck-root.service` 或某个挂载点因检查失败而挂不上 → **问题在文件系统本身而非配置**：先只读挂载把数据取出来，分清是文件系统损坏还是介质故障，确有把握再修（在已挂载可写的文件系统上跑修复工具会把损坏放大）。
- 修完继续启动按固定顺序：`mount -a` 验证 → `systemctl daemon-reload` 让 systemd 重新生成挂载单元 → `systemctl default` 继续启动。**不必重启**。

**一份合格的回答**：结论（配置问题还是文件系统问题）＋依据（`systemctl --failed` 的单元名与 `journalctl` 的报错行）＋边界（`nofail` 只保证机器能起来，不保证业务能接受这块盘不可用）＋动作（改配置并当场验证，或走数据优先的处置顺序）。

### 场景四：开机卡在「A start job is running for …（1min 30s）」

**现场**：一台机器升级后每次开机多花 90 秒，屏幕上出现一行 `A start job is running for dev-disk-by\x2duuid-….device (1min 30s)`，然后继续启动，系统起来后一切正常。

**先看什么**：那 90 秒是 systemd 的默认单元启动超时（`DefaultTimeoutStartSec`/`DefaultTimeoutStopSec` 默认 90 s），说明它在等一个**永远不会出现**的依赖。

```bash
systemctl list-jobs                  # 验证：还有哪些 job 卡在 running/waiting
systemctl --failed                   # 验证：是不是已经有一个失败的挂载单元
journalctl -b | grep -i 'timed out'  # 验证：超时发生在哪个单元
cat /etc/fstab                       # 验证：那一项写的来源是哪种标识
```

**看到什么转向哪**：

- 等的是 `dev-disk-by\x2duuid-<uuid>.device` → `fstab` 里有一行指向已下线或已改名的设备（转义规则：`-` 写成 `\x2d`）。修来源，并给可选挂载补 `nofail` 与 `x-systemd.device-timeout=`。
- 等的是某服务的网络依赖 → 查它是不是把网络写成了硬依赖（`Requires=`/`Wants=network-online.target`）；用 `systemd-analyze critical-chain` 确认它在关键路径上。
- 等的是 `systemd-udev-settle` → 硬件枚举慢，查驱动或存储设备是否有响应迟缓的迹象（这一项属于性能与 IO 排查的范围）。
- **不要**用调小超时的办法"解决"：超时调小只是让开机变快，那个挂不上/连不上的东西仍然没解决，故障会以更晚、更难查的形式复现。

**一份合格的回答**：结论（在等谁、它为什么不会出现）＋依据（`list-jobs` 的 job 名与 `fstab` 的对应行）＋边界（90 秒是默认值，若本机改过超时则数字会不同，要现场取）＋动作（修来源或补选项，改完用 `systemctl daemon-reload` 与一次重启验证）。

### 场景五：`sysctl` 调优后"看起来生效了"，重启又变回去

**现场**：为降低换页倾向，在 `/etc/sysctl.d/50-tuning.conf` 里写了 `vm.swappiness = 10`，执行过 `sysctl --system`，当时读到的值也是 10。半年后的一次重启后，`sysctl vm.swappiness` 读出来是 60。

**先看什么**：

```bash
sysctl vm.swappiness                          # 验证：现在生效的值是多少
ls -l /etc/sysctl.d/                          # 验证：文件清单与编号，有没有 99-sysctl.conf 软链
grep -rn swappiness /etc/sysctl.d/ /usr/lib/sysctl.d/ 2>/dev/null   # 验证：同一个键被写在哪几个文件里
```

**看到什么转向哪**：

- 存在 `/etc/sysctl.d/99-sysctl.conf` 软链，且它指向的 `/etc/sysctl.conf` 里也有 `vm.swappiness` → **顺序覆盖**：所有文件按文件名字典序应用，`99-` 排在 `50-` 之后、优先级更高。把自己的文件名取到 `99` 之后（例如 `100-tuning.conf`），或把值统一到一个文件里。
- 没有覆盖文件，但值仍是 60 → 确认这个配置文件**开机时真的被应用**了：`systemctl status systemd-sysctl`，以及是否有另一个机制（云初始化工具、编排层、配置管理系统）在更晚的时机又写了一遍。
- 值在某些机器上对、某些机器上不对 → 比"配置文件清单与编号"，而不是比值本身。

同时要记住回滚的边界：**删掉配置文件不会把当前内核里的值改回去**。文件只决定"下次开机写入什么"，当前的值得用 `sysctl -w <参数>=<原值>` 或重启来还原。

**一份合格的回答**：结论（是覆盖、是没被应用，还是被更晚的机制改了）＋依据（文件清单与编号、`sysctl --system` 的输出）＋边界（"改了文件"与"当前生效"是两件事）＋动作（调整编号或统一来源，并用一次重启后的读数验收）。

### 场景六：凌晨重启过，早上一切正常

**现场**：一台机器凌晨 2:14 重启过，早上值班登录时系统运行正常，用户侧只看到"有一段时间不可用"。会议上的问题是：它到底为什么重启？

**先看什么**：先确认**现场还在不在**，再读内容。

```bash
journalctl --list-boots                       # 验证：有几次启动记录
journalctl -b -1 -k -p warning                # 验证：上一次启动的内核警告与错误
ls -lt /var/crash/                            # 验证：有没有落下 vmcore
journalctl -b -1 | tail -50                   # 验证：上一次启动日志的末尾（崩溃前最后发生了什么）
```

**看到什么转向哪**：

- `--list-boots` 只有本次一条 → **现场已随重启消失**，只能从带外/串口日志、BMC 的事件日志与硬件侧记录去找；同时把"日志持久化"列为整改项。
- 有 `-1` 且 `/var/crash/` 里有新的时间戳目录 → 是内核崩溃且抓到了转储，转 `vmcore` 分析（先看 `vmcore-dmesg.txt`，它不需要调试信息）。
- 有 `-1`，内核日志里没有 panic 迹象，且 `last -x`/`who -b` 与带外记录不一致 → 要考虑**掉电、硬件看门狗或人工操作**；操作系统侧看起来一样的事，硬件侧有区别。
- 有 `-1`，日志里是 OOM 记录 → **这不是内核崩溃**，方向在内存账本与限制线（oops/panic/OOM 的分界见原理篇）。
- 有 `-1`，日志末尾是正常的关机序列 → 有人或某个机制执行了重启（补丁工具、编排层、定时任务）。

**一份合格的回答**：结论（哪一类重启，以及证据支持到什么程度）＋依据（`--list-boots` 的结果、`-b -1` 的关键行、`/var/crash/` 的内容）＋边界（没有 vmcore 且日志未持久化时，"是内核崩溃"这个结论**不能给出**，只能写"未确认"）＋动作（补持久化与 kdump 并演练，或在有转储时进分析）。

### 场景七：新机器上架前的取证能力验收

**现场**：一批新机器准备上架，要求"出事时能拿到现场"。你想用十分钟确认这批机器**现在**有没有这个能力。

**先看什么**：只读命令，生产机上也可以做。

```bash
ls -d /var/log/journal                        # 验证：日志持久化是否已启用
journalctl --list-boots | tail -5             # 验证：能回溯几次启动
cat /proc/cmdline | tr ' ' '\n' | grep crashkernel   # 验证：为捕获内核预留了多少内存
cat /sys/kernel/kexec_crash_size              # 验证：内核实际保留的字节数（0 = 没预留）
ls -lt /var/crash/ 2>/dev/null                # 验证：历史上抓到过崩溃没有
df -h /                                       # 验证：转储目标（本机转储时就是它）有多少余量
```

**看到什么转向哪**：

- `--list-boots` 只有一条 → 先补 journal 持久化，否则每一次重启都消耗现场。
- `kexec_crash_size` 为 0 → kdump 未生效；若这台机器在云上或 Lockdown 环境里，kexec 可能被禁，此时确认带外/串口日志通道是否可用（这是唯一替代）。
- 有预留但 `/var/crash/` 从未有过内容 → **不能算"已具备"**：失效条件平时不报错，必须演练一次才能确认。
- 根分区余量小于内存量级 → 本机转储会在崩溃时写不下；改远端转储，或接受"只保留文本形式的崩溃前日志"。

**一份合格的回答**：结论（这批机器现在具备哪几项取证能力）＋依据（每项对应的命令输出）＋边界（只读验收不等于验证过；实际有效性要靠一次演练）＋动作（列出整改项：持久化、`crashkernel=` 取值、转储目标、带外通道，各自附验证方式）。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 只看 `blame` 的排名去优化开机 | `blame` 不含等待依赖的时间；要看 `critical-chain` 的关键路径 |
| 用一次 `systemd-analyze` 的结果下结论 | 首次启动会被缓存与一次性任务拉长；至少取两三次稳定值 |
| 相信 `dmesg -T` 的时间戳并对账 | 开机早期时钟未同步，换算可能错；跨机对账用 `journalctl` 加统一时区 |
| 在没确认持久化的机器上排"上次的重启" | `--list-boots` 只有一条时现场已经没了，任何"看日志找原因"都是空转 |
| 看到 `sysctl` 当前值对就认为持久化好了 | 当前值是运行时状态；持久化的验收是**重启后的读数** |
| 删掉 `sysctl` 配置文件当回滚 | 当前内核里的值不会自己变回去，要显式 `sysctl -w` 或重启 |
| 用 `kernel.sysrq=1` 图方便 | 那会打开信号类与调试类操作（含杀进程、内存转储）；按位选需要的那几项 |
| 把 `echo c > /proc/sysrq-trigger` 在生产机上试 | 这是立即崩溃内核的破坏性操作，只在可快照的实验机上做，且要先确认快照可用 |
| 认为 `crashkernel=` 配了就等于有 `vmcore` | 预留、kexec、转储空间、捕获内核加载四件事都要成立，且只在 panic 时触发 |
| 用 `mount -a` 通过就认为 `fstab` 没问题 | `x-systemd.*` 这类选项拼错可能只给警告；还要 `findmnt --verify` |
| 在紧急模式里对根分区直接跑修复工具 | 根此时是挂着的（只读）；要真正卸载它通常得从救援介质或 initramfs 环境启动，属于另一种风险等级 |

## 要点自测

**问：给一个"开机变慢"的现象，你的第二步（拿到 `systemd-analyze` 之后）是什么？**

答：先看四段分解定位到哪一层——`firmware`+`loader` 大说明问题在固件与引导器，`userspace` 大才轮到 systemd 侧。若在 `userspace`，看 `critical-chain` 的关键路径而不是 `blame` 的排名；关键路径上哪一项的 `+` 耗时或 `@` 之间的空隙最大，就从那里查起。

**第一反应不要做什么**：不要直接去改 `DefaultTimeoutStartSec`。把超时调小只是让症状消失，被等的东西仍然没解决。

**问：为什么"`journalctl -b -1` 查上次重启"这件事必须先验证前提？**

答：因为这条命令依赖 journal 持久化。若只有 `/run/log/journal`（易失），重启后只剩本次启动，`--list-boots` 只有一行，`-b -1` 什么也读不到。前提要在故障之前确认，故障之后确认已经太晚。

**第一反应不要做什么**：不要在只有一条 boot 记录的机器上继续重启排查——每重启一次，你都在消耗本来就不存在的东西，而唯一剩下的证据在带外日志里。

**问：`kernel.sysrq = 176` 意味着哪些操作可用？**

答：它是位掩码，`176 = 128 + 32 + 16`，即允许重启/关机（128）、重挂只读（32）、`sync`（16），而进程调试转储（8）与信号类操作（64）**不允许**。所以在触发 panic 之前要先确认这一位——被禁时 `echo c > /proc/sysrq-trigger` 不会有任何效果，容易误判成"kdump 坏了"。

**第一反应不要做什么**：不要为了演练方便把 `kernel.sysrq` 直接设成 1（全开，包含杀进程与内存转储），按需要的那几位相加来设。

**问：怎么快速判断一台机器"具不具备取证能力"？**

答：四件事：journal 是否持久化（`ls -d /var/log/journal`、`journalctl --list-boots` 有几条）；有没有为崩溃预留内存（`crashkernel=` 与 `/sys/kernel/kexec_crash_size`）；崩溃时转储写到哪、有没有余量（`/var/crash/`、`df -h`）；带外/串口通道能不能在系统未启动时看到画面。四件事里任何一件不成立，对应那一类现场就拿不到。

**第一反应不要做什么**：不要把"命令存在""服务 active"当作"能力具备"。kdump 这类机制的失效条件平时不报错，只有演练过一次才算验证。
