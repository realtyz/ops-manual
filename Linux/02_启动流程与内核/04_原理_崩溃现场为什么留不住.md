# 崩溃现场为什么留不住

## 1. 一次内核崩溃里，什么是"现场"

内核崩溃（panic）发生时，值得后来者回答的问题有一串：崩在哪个子系统、调用栈是什么、崩之前最后打印了什么、当时谁在跑、内存是什么状态。这些信息**全部只存在于内存里**：

| 现场 | 存在哪 | 重启后还在吗 |
| --- | --- | --- |
| panic 时打印到控制台的那段文字 | 控制台缓冲、以及带外/串口日志通道 | 只有被外部（带外日志、串口采集、截屏）带走的才在 |
| 内核环缓冲（`dmesg` 的数据源） | 内存 | **不在** |
| 崩溃瞬间的调用栈、寄存器、进程表 | 内存 | **不在** |
| journal 里的历史日志 | 取决于是否持久化到磁盘 | 持久化过的那部分在 |
| 崩溃内存镜像（`vmcore`） | 需要主动写出来 | 只有在崩溃前配好机制才有 |

这是"机器莫名重启过"这类问题难查的根本原因：**一旦机器自动重启，现场就清空了**。而"会不会自动重启"由 `kernel.panic` 决定（见下）——这一点要先在现场确认，不要假设"崩溃之后机器一定会停在原地等你取证"，也不要假设"它一定会自己起来"。

金标准机器上的三个相关取值可以对照着读（单位与含义见下）：

| 参数 | 锚点机器上的值 | 读法 |
| --- | --- | --- |
| `kernel.panic` | `0` | 单位是秒；`0` 表示 panic 后**不自动重启、停在现场**；非零表示等 N 秒后重启 |
| `kernel.panic_on_oops` | `0` | `1` 会把 oops 升级成 panic，代价是可用性、收益是问题不被静默吞掉 |
| `vm.panic_on_oom` | `0` | `0`/`1`/`2` 三档语义不同（见下），**不能笼统说成"非零就 panic"**；设成会 panic 的档位等于把"内存不足"变成"整机重启"，对"宁可杀一个进程也不许重启"的服务是反效果 |

这三个值的含义以 `man 5 proc` 与内核 6.x 文档 `Documentation/admin-guide/sysctl/` 为准，取值**现场读**（`sysctl <名字>`），不要凭发行版印象推断——"内核默认怎么处置"与"这台机器实际怎么处置"是两件事，后者取决于本机取值或上层框架是否改过它。锚点机器上三个值都还是内核默认值，但**这不构成对别的机器的结论**：是否被改过只能在目标机器上读一次才知道。

## 2. 三级错误严重程度，对应三种完全不同的处置

"内核出问题"不是一件事。按严重程度分三级，它们的证据形态与处置方向都不同：

| 级别 | 含义 | 内核怎么处理 | 留下什么证据 |
| --- | --- | --- | --- |
| **警告 / 错误打印** | 某个驱动或子系统报了错，内核继续运行 | 继续运行 | 内核日志（`journalctl -k -b`） |
| **oops** | 内核代码路径出了无法正常继续的错误（空指针、断言失败、数据结构损坏） | 杀掉当前进程/线程，尽量继续运行 | 内核日志里一段带调用栈的 oops 记录；`kernel.panic_on_oops=1` 时升级为 panic |
| **panic** | 内核判定无法继续安全运行 | 打印诊断信息后停止（按 `kernel.panic` 决定是否重启、等多久重启；配了 kdump 时由捕获内核接管并在转储完成后重启） | 控制台/串口输出；配了 kdump 则有 `vmcore` |

**OOM 不属于这三级的任何一级。** OOM Killer 是内核在内存不足时**杀掉一个进程**，是一个正常的内核机制，默认不产生 panic，也不产生 `vmcore`。`vm.panic_on_oom` 才是那个把 OOM 升级成 panic 的开关，而它的三档取值必须分开说：

| 取值 | 含义 | 后果 |
| --- | --- | --- |
| `0` | 不因 OOM 而 panic | 杀掉进程、业务侧可能少一个实例，整机继续运行（默认态） |
| `1` | **整机**内存耗尽时才 panic | 只有撞到整机水位的那类 OOM 会升级为 panic；受 cgroup 限制而发生的 OOM 不算整机耗尽，仍然只杀进程 |
| `2` | 任何 OOM 都 panic | 连容器/服务撞自己上限被杀也会升级成整机崩溃，可用性代价最大 |

所以"把 `vm.panic_on_oom` 设成非零就会进崩溃取证流程"这句话是错的：**取 `1` 时它只覆盖整机 OOM**，容器被 cgroup 杀掉那类事件依然不会产生 `vmcore`。把"服务被杀"和"内核崩溃"混为一谈，会导致在两个完全不同的方向上找证据（内存侧的账本与限制线，见阶段 4）。

## 3. 让现场活下来的四类载体

既然内存里的东西活不过重启，就必须在崩溃发生前后把信息搬到别处。可用的载体有四类，能力与代价各不相同：

| 载体 | 原理 | 能拿到什么 | 代价与限制 |
| --- | --- | --- | --- |
| **控制台 / 串口 / 带外日志** | 内核日志本来就往控制台输出，由外部设备记录 | panic 的打印、启动全过程日志 | 需要预先配好串口与采集；没配就等于没有 |
| **持久化 journal** | journald 把日志写到磁盘 | 崩溃前的系统与内核日志 | 只能拿到"崩溃前已经写进去的"；内核环缓冲尾部可能丢 |
| **kdump 的 `vmcore`** | 用一个预备好的捕获内核接管，把崩溃内核的内存写成文件 | 完整内存镜像与调用栈 | 需要预留内存、需要 kexec、需要转储空间 |
| **pstore / ramoops** | 把一段日志写到"重启不清空"的存储区域（平台固件保留的内存区或专用区域） | 崩溃尾巴上的一小段 dmesg | 容量很小；依赖平台支持与内核配置 |

**kdump 的原理值得说透，因为它的失效方式很隐蔽。** 它提前做两件事：启动参数 `crashkernel=` 预留一块内存；系统起来后用 `kexec` 把一个**捕获内核**装进那块预留内存。之后正常业务运行；一旦 panic，系统不经过固件与引导加载器，直接用 `kexec` 跳到捕获内核，由它把崩溃内核的内存写成 `vmcore`（通常还要经 `makedumpfile` 过滤掉零页与无关页以缩小体积），存到本地目录或远端，然后重启恢复业务。

由此得到三个必须理解的点：

1. **预留内存是硬成本**。`crashkernel=` 预留的那块内存在正常运行期间不可用于业务，所以它是"兜底能力"与"可用内存"之间的取舍；预留太小会抓不全甚至抓失败，太大则常年占用业务内存。合理值取决于内存容量、内核版本与发行版，**要用发行版自带的估算工具在本机算**，不要照抄别人的数字。
2. **它依赖 kexec 可用**。部分云主机、受管环境、以及 Lockdown（Secure Boot 开启时的受限模式）下 kexec 被禁用，kdump 就无法工作。此时唯一的证据来源是带外/串口日志。
3. **它只在 panic 时触发**。oops 不触发，OOM 不触发，掉电重启不触发。所以"配了 kdump"不等于"任何异常重启都有 `vmcore`"。

## 4. 为什么"没演练过的 kdump 等于没配"

kdump 的失效条件全部**在平时不报错**：预留内存偏小、转储目标空间不够、kexec 被环境禁用、捕获内核未成功加载、转储路径不可写。这些条件只会在崩溃那一刻暴露，而那一刻是你最没有余裕排查的时刻。

这与前面两类载体的失效方式完全不同——journal 是否持久化，一条 `journalctl --list-boots` 就能当场确认；串口是否配好，接一次串口就能验证。kdump 的验证**必须主动制造一次崩溃**（在可快照的实验机上触发 panic），确认 `vmcore` 真的落盘、体积与耗时符合预期、并且能被分析工具打开。这是本章唯一一个"验证手段本身具有破坏性"的机制，所以它天然只在实验机上做。

## 5. `vmcore` 拿到之后从哪看起

分析需要一个与崩溃内核**版本匹配**的调试符号文件（`vmlinux`，来自发行版的 debuginfo 包），否则符号解析不出来，只能看到地址。在此基础上有一份不需要任何调试信息的替代品：**`vmcore-dmesg.txt`**，它是从 `vmcore` 里抽出来的纯文本崩溃前内核日志，是性价比最高的一份证据——它能回答"崩之前发生了什么"，常常直接指向根因。

分析工具（`crash`）里的起手顺序是固定的：先看调用栈（`bt`）定位子系统，再看日志（`log`）找触发点，然后用进程表（`ps`）与内存状态（`vm`）区分"资源耗尽"还是"代码路径问题"。**先定位到子系统，再谈根因**——这一步没做完，后面看什么都是散的。

## 6. 抽象在哪里漏水

**"内核崩溃"和"掉电重启"在操作系统侧看起来一样。** 一台机器重启过，你可能看到的是 panic、可能是掉电、可能是硬件看门狗动作、也可能是有人按了电源。这几种在软件侧的证据形态可能完全相同（都是"上次启动的日志在这里断掉了"），区分它们要靠 BMC/带外的事件日志（SEL）与硬件侧的记录。同一份"莫名重启"现场，先确认它属于哪一类，再决定查什么。

**`dmesg -T` 的时间戳在早期不可靠。** `-T` 是用当前系统时间换算内核内部的单调时间戳；开机早期系统时钟还没与任何时间源同步，换算出来的时间可能是错的。跨机器对齐日志要用 `journalctl -b` 加统一时区，或者以带外日志的时间为准。

**内核环缓冲会被覆盖。** 它是有容量上限的内存缓冲，日志量大时旧消息会被挤掉。所以"崩溃前那段输出"可能已经被挤没了——这也是持久化 journal 的价值所在，它把日志搬到了磁盘上。

**`core_pattern` 决定的是"应用 core 去哪"，不是内核崩溃**。管理 core 文件的机制（用户的 coredumpctl、发行版的 crash 收集器、`kernel.core_pattern`）与内核崩溃取证是两条不同的链；把 `core_pattern` 设成某个收集器，不会让 panic 产生 `vmcore`。

**kdump 不是备份，也不是高可用。** 它只在崩溃现场与重启之间争取一次"把内存拷出来"的机会；它不让业务不中断，也不保证 `vmcore` 一定能被分析（缺 debuginfo、文件截断、版本对不上都会让它变成一堆地址）。

## 常见误解

| 说法 | 事实 |
| --- | --- |
| "机器重启过，肯定是内核崩溃" | panic、掉电、硬件看门狗、人工操作在系统侧可能表现一致；要看 BMC/带外事件日志与硬件记录 |
| "配了 kdump 就有 `vmcore`" | 预留内存、转储空间、kexec 可用、捕获内核加载成功，任一不成立都抓不到，而且平时不报错 |
| "OOM 会有 `vmcore`" | 默认不会。OOM 是内核杀进程的正常机制；`vm.panic_on_oom` 取 `1` 时只覆盖**整机** OOM，取 `2` 时任何 OOM 都 panic |
| "oops 也算崩溃，应该也能抓到 vmcore" | oops 默认只杀当前路径并继续运行，不触发 kdump；除非 `kernel.panic_on_oops=1` |
| "`crash` 直接打开 `vmcore` 就能看调用栈" | 需要与崩溃内核版本匹配的 `vmlinux`/debuginfo；没有它只能看到地址，此时先看 `vmcore-dmesg.txt` |
| "`dmesg -T` 的时间戳可以用来对账" | 开机早期系统时钟未同步，换算结果可能错；跨机对账用 `journalctl` 加统一时区 |
| "只要日志持久化了，panic 现场就完整了" | 持久化只能留下"已经写进 journal 的那部分"；内核环缓冲尾部与崩溃瞬间的内存内容仍然会丢 |
| "kdump 是高可用手段" | 它是取证手段：崩溃照样发生、业务照样中断，它只是把内存拷出来 |

## 要点自测

**问：为什么 panic 的现场留不下来？有哪四类载体能把它留下来？**

答：因为崩溃瞬间需要的信息（调用栈、进程表、内存状态、环缓冲）全在内存里，而 panic 一旦走到重启（是否重启、等多久由 `kernel.panic` 决定，现场取值），这些内容就被清空。四类载体分别是：控制台/串口/带外日志（外部记录打印）、持久化 journal（写到磁盘的系统与内核日志）、kdump 的 `vmcore`（用捕获内核把内存写成文件）、pstore/ramoops（写到重启不清空的存储区域，容量很小）。

**第一反应不要做什么**：不要在没确认"现场还在不在"之前就重启。先看 `journalctl --list-boots` 有几次启动记录、`/var/crash/` 有没有目录——先确认证据存在，再读证据。

**问：kdump 靠什么机制工作？它为什么可能静默失效？**

答：启动时用 `crashkernel=` 预留内存，系统起来后用 `kexec` 把捕获内核装入预留内存；panic 时不经固件与引导加载器直接跳到捕获内核，由它把崩溃内核的内存写成 `vmcore` 后重启。它会静默失效，是因为失效条件（预留偏小、转储空间不足、kexec 被禁用、捕获内核未加载）平时都不报错，只在崩溃那一刻暴露——所以必须主动演练验证。

**第一反应不要做什么**：不要在没演练过的机器上把 kdump 当成"有兜底"。没验证过的配置和没有配置，在崩溃那一刻是等价的。

**问：拿到 `vmcore` 之后第一步看什么？没有 debuginfo 时怎么办？**

答：先在分析工具里看调用栈与崩溃前的日志，定位到子系统；再用进程表与内存状态区分"资源耗尽"和"代码路径问题"。没有匹配版本 debuginfo 时符号解析不出来，退而看 `vmcore-dmesg.txt`——它是不需要调试信息的纯文本崩溃前内核日志。

**第一反应不要做什么**：不要随便找一份 `vmlinux` 去打开 `vmcore`。版本不匹配时得到的地址没有意义，还会让人误以为"栈是坏的"。

**问：`kernel.panic`、`kernel.panic_on_oops`、`vm.panic_on_oom` 三个值分别改变了什么权衡？**

答：`kernel.panic` 是"崩溃后等几秒重启"与"停在现场等人处理"之间的权衡，`0` 表示永不自动重启；`kernel.panic_on_oops` 决定"内核还能继续跑的错误"要不要升级成整机崩溃，开启牺牲可用性换取问题不被静默吞掉；`vm.panic_on_oom` 决定内存不足时是只杀进程（`0`）、只在整机耗尽时崩溃（`1`），还是任何 OOM 都崩溃（`2`）——对延迟敏感或状态难以重建的服务来说，后两档通常是反效果。

**第一反应不要做什么**：不要把三个值当调优旋钮随手改。要改就写清"为哪个场景、牺牲了什么、怎么回滚"，并记进变更记录（见治理篇）。

## 参考文档

- `man 1 kexec`、`man 8 makedumpfile`、`man 1 crash`：捕获内核的换入、转储过滤与体积、`vmcore` 的分析入口。
- `man 8 kdumpctl`、`man 5 kdump.conf`（RHEL 系）、`man 8 kdump-config`、`man 5 kdump-tools.conf`（Debian/Ubuntu 系）：预留值的估算、转储目标、服务状态。
- `man 5 proc` 的 `/proc/sys/kernel/panic`、`panic_on_oops`、`/proc/sys/vm/panic_on_oom` 条目，以及 `/proc/sys/kernel/core_pattern`、`kernel.sysrq` 的位含义。
- `man 1 journalctl` 的 `--list-boots`、`-b`、`-k`、`--disk-usage`；`man 5 journald.conf` 的 `Storage=`。
- 内核 6.x 文档 `Documentation/admin-guide/kdump/`（kdump 的配置与转储流程）、`Documentation/admin-guide/ramoops.rst` 与 `Documentation/admin-guide/pstore-blk.rst`（pstore 的两类后端）、`Documentation/admin-guide/sysctl/kernel.rst` 与 `.../vm.rst`（各参数的官方定义与取值范围）。内核文档一律按与目标机器同一主版本取（当前基线 6.x）——同一条路径在不同版本里可能同名而内容不同。
