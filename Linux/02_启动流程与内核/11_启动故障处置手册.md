# 启动故障处置手册

> [!cite] 参考资料
> 本篇是各篇结论的**收口**，不引入新机制：`man 7 bootup`、`man 5 systemd.unit`、`man 8 dracut`、`man 5 fstab`、`man 8 grubby`、`man 8 sulogin`，以及子笔记 04–10 的对应小节。
>
> 本篇结论来自上述资料，**处置步骤尚未在实验机上逐条演练**；演练后请把实测现象、耗时与踩到的坑回填到对应小节。

> **这篇讲什么**：机器起不来时，按什么顺序看、按什么顺序做，以及每一步的证据在哪里。
>
> **必须先读什么**：至少读完 [[Linux/02_启动流程与内核/00_导读与知识地图|00 导读]] 的第 1、6 节；具体环节的机制见子笔记 04–07。
>
> **读完能做什么**：给一个「起不来」的现象，10 分钟内判定卡在哪一环，并说出下一步该取什么证据。
>
> 所属：[[Linux/02_启动流程与内核/00_导读与知识地图|02 启动流程与内核]] 的收口篇 · 主要练 **S3 取证**、**S4 分层定位**、**S7 风险判断**、**S8 沉淀**

## 0. 统一原则

> [!abstract] 处置前三句话
> - **先定位卡在第几环，再动手。** 判断依据永远是「**现在是谁在输出**」。
> - **没找到现场之前，不做不可逆操作。** 重装、重建引导器、`fsck` 写盘都属于不可逆。
> - **先取证还是先止损，是个明确决策。** 业务中断时优先止损；只要还能取到证据，就先取证据——**重启会毁掉大部分现场**。

三条通用取证动作，任何一环都适用：

```bash
ls /sys/firmware/efi          # 验证：启动模式（UEFI / legacy），决定后面查哪套引导路径
cat /proc/cmdline             # 验证：内核这次收到了什么（root= 是否指向真实设备）
systemctl --failed            # 验证：能进系统时，哪些单元失败了
```

## 1. 卡在 GRUB（第 2 环）

> [!tip] 第一反应不要是「重装系统」
> GRUB 提示符本身就是一个可用的引导器，内核文件通常还在盘上。绝大多数情况能在几分钟内手工拉起来。详见子笔记 05。

**先分辨是哪种提示符**：

| 提示符 | 含义 | 处置方向 |
| --- | --- | --- |
| `grub>` | GRUB 本体可用，但读不到配置 | 手工引导最快 |
| `grub rescue>` | 连正常模块都没加载 | 先 `set root` + `set prefix` + `insmod normal` 找回菜单 |

```bash
ls                                        # 验证：GRUB 能看到哪些磁盘与分区
ls (hd0,gpt2)/                            # 验证：逐个分区试探，找出含 grub2/ 与 vmlinuz 的那个
set root=(hd0,gpt2)                       # 验证：把根设为 /boot 所在分区
set prefix=(hd0,gpt2)/grub2               # 验证：RHEL 常见 /grub2；Debian 常见 /grub
insmod normal                             # 验证：加载 normal 模块
normal                                    # 验证：回到菜单
```

进系统后**立即修根因**：重新生成配置、必要时重装引导器、检查 `/boot` 与 ESP 是否写满。

> **最低成本复现**：把 `grub.cfg` 改个名字再重启，会落到 `grub>`；把启动顺序改掉，会落到 `grub rescue>`。改动前先打快照。

## 2. 卡在 initramfs shell（第 3 环）

> [!tip] 第一反应不要是「重建 initramfs 就完事」
> 先分清是「**设备真的不在了**（盘/RAID/云盘问题）」还是「**名字对不上**（UUID、LVM 名变了）」——这两类的处理方向完全相反。详见子笔记 06。

```bash
cat /proc/cmdline                   # 验证：内核在找哪个根设备
ls /dev/disk/by-uuid/               # 验证：initramfs 现在能看到哪些设备
lsblk                               # 验证：磁盘与分区结构是否被识别（为空 = 驱动问题）
lvm vgscan --mknodes                # 验证：LVM 元数据是否可见（LVM 根分区专用）
cat /run/initramfs/rdsosreport.txt  # 验证：dracut 诊断报告（RHEL 系），含设备与模块加载全过程
```

分支出结论：

- 目标设备**在列表里**但 UUID 不符 → 参数旧了，更新 `root=`。
- 目标设备**完全不在列表里** → 驱动缺失，进系统后补驱动并重建 initramfs。

> **最低成本复现**：在 GRUB 里加 `rd.break` 就能停进同一个 initramfs shell（真根此时在 `/sysroot`）。

## 3. 落到 `emergency.target`（第 4 环）

> [!tip] 第一反应不要是「一路回车直接重启」
> 紧急模式是 systemd 明确告诉你「有东西挂不上」，重启只会再演一遍；而这是一个**根已经挂上、可以动手修**的环境。详见子笔记 07。

```bash
systemctl --failed                  # 验证：哪些 unit 处于 failed（一半以上是 fstab 里的挂载点）
journalctl -xb | grep -A5 -i 'failed to mount'   # 验证：挂载失败的具体设备与原因
mount -o remount,rw /               # 验证：紧急模式下根通常只读，改配置前先确认可写
```

确认可写之后**修改出错的那一行 `fstab`**，再继续：

```bash
mount -a                            # 验证：fstab 全部条目能否手工挂上（报错会直接指到那一行）
systemctl daemon-reload             # 验证：让 systemd 重新生成 .mount 单元
systemctl default                   # 验证：继续启动到默认 target
```

**另一类成因：文件系统检查失败。** 如果 `systemctl --failed` 里出现的是 `systemd-fsck-root.service`，或者某个挂载点因为检查失败而挂不上，那问题不在配置，而在文件系统本身：

```bash
systemctl status systemd-fsck-root.service    # 验证：根文件系统的检查是不是真的失败了
dmesg -T | grep -i -E 'ext4|xfs|I/O error'    # 验证：有没有介质错误或 I/O 错误的迹象
```

处置按风险从低到高：

1. **先只读挂载把数据取出来**——数据优先于修复。
2. **分清是文件系统损坏还是磁盘故障**：日志里出现 `I/O error`、介质错误，多半是盘本身的问题，修复工具救不回来。
3. **确实要修再修**：ext4 用 `e2fsck`，XFS 用 `xfs_repair`，而且**必须在文件系统未挂载或只读挂载的状态下执行**——在已挂载可写的文件系统上跑修复工具，会把损坏放大。
4. **有快照或备份时优先恢复**，不要为了「修好它」冒更大的数据风险。

> [!warning] 别在紧急模式里直接对根分区跑修复工具
> 紧急模式下根是挂着的（只读）。要真正卸载它，通常得从救援介质或 initramfs 环境启动。这一步已经属于「上带外或进机房」的操作，动手前先确认有退路。

> **最低成本复现**：往 `/etc/fstab` 加一行假 UUID 的挂载项，先 `mount -a` 确认报错，再重启。这是最接近真实故障、也最容易把机器搞失联的复现方式，务必先打快照。

## 4. 卡在「A start job is running for ...（1min 30s）」

> [!tip] 第一反应不要是「等它超时」
> 那 90 秒是 systemd 的默认超时在等一个永远不会出现的依赖；等下去只是把一个几秒的开机拖成 90 秒。详见子笔记 07。

| 等的是谁 | 含义 | 处理方向 |
| --- | --- | --- |
| `dev-disk-by\x2duuid-<uuid>.device` | 设备不存在 | 修 `fstab`；可选挂载加 `nofail` 与 `x-systemd.device-timeout=` |
| `NetworkManager-wait-online.service` | 在等网络就绪 | 检查服务是否把网络写成了硬依赖 |
| `systemd-udev-settle` | 硬件枚举慢 | 查驱动或存储设备是否响应迟缓 |

```bash
systemctl list-jobs                 # 验证：还有哪些 job 卡着
systemd-analyze blame | head -20    # 验证：单元自身耗时排行
systemd-analyze critical-chain      # 验证：关键路径上是谁拖住了开机
```

> **最低成本复现**：与第 3 节同源——同一个坏挂载项，这次把启动过程完整看完，观察那 90 秒超时。

## 5. panic 之后取现场

> [!tip] 第一反应不要是「先重启再看」
> 重启一次，`vmcore` 与上一次启动的日志就都没了。详见子笔记 10。

```bash
ls -lt /var/crash/                  # 验证：有没有落下 vmcore（有则先拷到远端保住）
journalctl --list-boots             # 验证：本机保留了几次启动的日志
journalctl -b -1 -k -p warning      # 验证：上一次启动的内核警告与错误（最后一份软件侧证据）
journalctl --disk-usage             # 验证：日志占用空间
```

云主机与控制台通常还导出串口日志，那是 panic 调用栈的另一个来源。

> **最低成本复现**：没有实验机时先做两件只读的事——`ls /var/crash/` 看历史上有没有抓到过 `vmcore`，`journalctl --list-boots` 看日志是否持久化。

## 6. 改了参数却不生效

> [!tip] 第一反应不要是「再改一遍重启试试」
> 先判断你改的是不是**另一套参数**：启动参数与运行时参数是两套机制。详见子笔记 08。

```bash
cat /proc/cmdline                                    # 验证：启动参数是否真的带上（唯一真相）
grep -r '<参数名>' /etc/default/grub /etc/sysctl.d/   # 验证：配置到底写在了哪一层
grep -r '<参数名>' /boot/loader/entries/ 2>/dev/null  # 验证：RHEL/BLS 机器上参数落在哪里（见子笔记 05）
sysctl --system                                      # 验证：重新应用全部 sysctl 配置，观察是否被覆盖
```

三种典型成因：**没重新生成配置**（启动参数）、**被更高优先级的 `sysctl` 文件覆盖**（运行时参数）、**参数归属搞混**（把运行时参数写进了启动参数）。

> **最低成本复现**：把同一个 `sysctl` 参数分别写进 `50-a.conf` 与 `99-b.conf`，给不同值，`sysctl --system` 之后看谁生效。

## 7. 忘记 root 密码（以及它为什么是安全事件）

> [!tip] 第一反应不要是「重装系统」或「找厂商」
> 只要有控制台，重置 root 密码是标准操作。反过来讲，**任何能碰到控制台的人都能做这件事**——这才是它在生产上属于安全事件的原因。

在 GRUB 菜单按 `e`，在内核行末尾加 `rd.break`，按 `Ctrl-X` 引导，进入 dracut 提示符后：

```bash
mount -o remount,rw /sysroot        # 验证：真根以只读方式挂在 /sysroot，先改成可写
chroot /sysroot                     # 验证：把 /sysroot 当根使用
passwd root                         # 验证：重置密码（写的是 /etc/shadow）
touch /.autorelabel                 # 验证：让 SELinux 下次启动重打标签（否则可能登录被拒）
exit                                # 退出 chroot
exit                                # 退出 initramfs，继续启动
```

Debian/Ubuntu 的等价做法：GRUB 里选 recovery mode 进 root shell（根只读，需 `mount -o remount,rw /`），或用 `init=/bin/bash` 后同样先重挂可写再 `passwd`。

三句话必须一起记住：

- **控制台即 root**：未加密磁盘 + 可物理接触或可访问带外控制台 = 可重置任何本地密码。真正的防护是磁盘加密（LUKS）、GRUB/固件密码、带外账号的独立鉴权与审计——而不是指望恢复路径被堵死。
- **恢复动作要留痕**：谁在什么时候进过控制台，应进变更记录；恢复后复查 `/etc/shadow` 的改动时间与登录记录。
- **这类操作本身就是攻击手法**：发现有人进过控制台，按入侵处置的优先级处理。

> **最低成本复现**：只在有快照的实验机上练——这条路径会改到认证文件与 SELinux 标签，在生产上属于安全事件。

## 8. 处置记录模板（S8）

一次处置的价值，一半在于「系统回来了」，另一半在于「下次别人也能照着做」。收尾时把下面这张表填完，存进 Runbook：

| 栏目 | 写什么 |
| --- | --- |
| 时间线 | 现象首次出现的时间、发现时间、处置起止时间（统一时区） |
| 影响面 | 哪些业务/实例受影响，是否触发告警 |
| 现象 | 屏幕/日志上的原文，卡在哪一环（用第 0 节的三问定位） |
| 证据 | `journalctl -b -1`、`dmesg`、`/var/crash/`、带外日志的存放位置 |
| 处置动作 | 每一步做了什么、每条命令的验证结果 |
| 根因 | 是配置、变更、硬件，还是驱动/参数 |
| 回滚验证 | 是否用到了旧内核/备份，回滚后如何确认系统正常 |
| 长期改进 | 要补的巡检项、监控项、变更前检查项 |

> [!important] 「改了配置、能起来了」不是记录
> 记录里必须有**证据位置**和**回滚验证**。否则下一次同类故障发生时，这份记录只能告诉后来者「上次也是这么糊过去的」。

## 9. 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 一上来就重启 | 重启会覆盖 journal 环缓冲与失败启动记录；先取证 |
| 没定位环节就动手 | 在 GRUB 阶段修 systemd、在紧急模式里修引导器，都是无效操作 |
| 只改一处就以为修好 | `root=`、`initramfs`、`fstab` 分属不同环节，改错层等于没改 |
| 直接在生产机上做不可逆操作 | 重装、重建引导器、`fsck` 写盘都要先确认数据和现场都能保住 |
| 忘记检查 `/boot` 与 ESP 空间 | 空间写满会让后续所有引导相关变更静默失败 |
| 处置完不写记录 | 同类故障下次仍要从零开始；Runbook 的价值就在这里 |

## 10. 决策练习

> [!question]- 场景：凌晨 2 点，一台远端机器失联。带外控制台显示画面停在 `dracut:/#`，业务已经完全中断，SLA 还剩 30 分钟
> 你要先止损还是先取证？
> A. 先取证：把 `/run/initramfs/rdsosreport.txt` 和屏幕内容导出，再动手
> B. 先止损：立刻重启，看能不能自己起来
> C. 什么都别做，等天亮再说
>
> **答案：A，但要在很短时间内完成。**
> `dracut:/#` 这个现场**重启一次就没了**，而导出报告只要一两条命令、几十秒。取证完成后，正好用同一批证据判断该改 `root=` 还是直接重启。
> B 把唯一的证据清零，而且大概率重演同一个故障——因为根设备找不到通常是持续性的配置/硬件问题，不是偶发抖动。C 牺牲 SLA。
> **这条题的通用规则是：取证成本低就先取证，取证成本高（需要停机、需要特殊工具）才优先止损。**

> [!question]- 场景：一台机器进了 `emergency.target`，`systemctl --failed` 只显示一个失败的 `.mount` 单元。你修完 `fstab` 后想继续启动
> 正确的顺序是什么？
> A. 直接 `reboot`，反正配置已经改好了
> B. `mount -a` 验证 → `systemctl daemon-reload` → `systemctl default`
> C. `systemctl restart` 那个失败的单元
>
> **答案：B。**
> `mount -a` 是**在重启之前**验证修复是否有效的最低成本手段；`daemon-reload` 让 systemd 重新读取 `fstab` 生成的挂载单元；最后 `systemctl default` 继续启动——整个过程不需要重启。
> 每次都靠重启验证，等于把「验证」变成了「赌一把」：真的还有问题时，机器会再进一次紧急模式，而远端机器可能就此失联。

## 11. 要点自测

> [!question]- 面对「机器起不来」，你的前三步是什么？
> - 第一步：确认**现在是谁在输出**（固件屏 / GRUB 提示符 / initramfs shell / systemd 日志），据此定位环节。
> - 第二步：取该环节的证据（`cat /proc/cmdline`、`ls /dev/disk/by-uuid/`、`systemctl --failed`、`journalctl -b -1`）。
> - 第三步：判断该环节的依赖是否满足（启动项、`root=` 设备、`fstab` 挂载），再动手。

> [!question]- 哪些操作属于「不可逆」，需要先取证再动手？
> - 重装系统、重建/覆盖引导器、`mkfs` 与分区操作、`fsck` 写盘修复、删除或清空 `/var/crash`、`journalctl --vacuum-*` 清理日志。
> - 共同点：**会把现场或数据一起清掉**。既然恢复现场往往不可能，取证就必须排在前面。

> [!question]- 一次处置结束后，Runbook 里必须写下的两样东西是什么？
> - **证据位置**：日志、`vmcore`、带外日志存在哪，谁能在下次复盘时找回来。
> - **回滚验证**：这次靠什么回退、回退后如何确认系统真的正常了。
