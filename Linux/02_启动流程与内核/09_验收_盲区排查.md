# 盲区排查：启动流程与内核

## 1. 本篇解决什么问题

读完整章之后，"不会"这件事通常无法被自己察觉。它不表现为"这个提示符没见过"，而表现为**回答停在某一层却以为已经说完了**——能顺着控制权把五段交接讲一遍，因果都对，但据此说不出下一步该读哪一份文件、读到的值说明什么。

本篇把本章负责的八类现象逐层拆开：每一类给出它在追问下的典型回答、这一层实际检验的是什么、站在这一层的人缺的是哪一类东西。

全部层级中最常见的一种失效，是机制讲得流畅而判据落不到字段上。它在启动链上比别处更隐蔽，因为这条链的每一段都有干净的因果可以叙述——固件为什么不读文件系统、initramfs 为什么必须存在、那 90 秒是谁在等——这些都能讲对，而到了现场依然只剩"重启一下看看"。用途只有一个：**回答者自己对照，找到自己的回答停在哪一层，据此定位缺的是本章哪一篇的哪一节。**

## 2. 分层的方法

每一类现象都沿同一方向逐层展开，共四层，顺序固定：

| 层     | 回答里出现什么            | 检验的是          | 停在这一层的典型说法                     |
| ----- | ------------------ | ------------- | ------------------------------ |
| 第 0 层 | 只给出结论或动作           | 有没有进入机制       | "重启一下""重装系统""先看日志"             |
| 第 1 层 | 说出机制与因果            | 机制是否成立        | "固件不认识 Linux，它只认启动项"           |
| 第 2 层 | 说出字段名与判据           | 判据是否落到可观测处    | "读 `/proc/cmdline` 里的 `root=`" |
| 第 3 层 | 说出该判据何时失效、处置的代价与顺序 | 是否具备条件意识与代价意识 | "跨平台迁移后设备名和控制器型号都会变"           |

第 0 层与第 1 层之间是这条链上最陡的一段：从"知道这一段会交棒失败"到"知道它凭什么交棒"。第 1 层与第 2 层之间的失效最常见，因为二者的语言外观几乎一样，区别只在有没有一个可读的字段。第 3 层决定的是判断能否迁移到另一台机器、另一个固件类型、另一个发行版。

定位自己的位置有一条简单办法：**检查自己的每一句话能不能指到一个字段**。指不到的句子，通常是从别处听来的。

## 3. 现象一：上电后屏幕没有操作系统的输出（黑屏、蜂鸣、固件报错页，或 `No bootable device`）

### 3.1 逐层演进

**第 0 层（多数人的回答）**

> 机器起不来了，进系统里翻翻日志，或者干脆重装一遍。

这一层跳过了"现在是谁在输出"这个唯一的判断对象。固件阶段操作系统还没有运行，日志系统也还不存在，翻不到任何东西；重装则是一次把数据、配置与现场一起交出去的动作。

**第 1 层（说出机制）**

> 固件先做加电自检，再按一个候选列表挑启动来源：UEFI（统一可扩展固件接口）读 NVRAM 里的启动项，legacy 读设备顺序；找不到可引导设备就停下来报错。它不读你的文件系统，也不认识 Linux。

到这里因果链已经完整。但它在机器上不能执行：不知道读哪个字段来区分"顺序被别的设备顶掉了"和"引导器文件实体不在了"。

**第 2 层（给出判据）**

> 这一段没有 shell：系统内的命令一个都敲不了，判据只能从系统之外取。当场可读的三处是带外控制台或物理屏上的固件输出（自检停在哪个设备、报错页写了什么、有没有 PXE 尝试）、带外管理的事件日志（SEL），以及固件设置界面本身——启动顺序里哪一项排在前面、启动项列表是不是空的、系统盘有没有出现在固件的设备列表里。系统内那一组字段（`ls /sys/firmware/efi`、`efibootmgr -v`、`fdisk -l`、`lsblk`）要等这台机器能起来之后、或用救援介质起了另一个系统才有，它们的作用是**事先记进基线、事后与屏幕上的现象对照**：目录在不在定固件类型（在就是 UEFI、不在就是 legacy），`BootOrder`、条目名后的 `*` 与 `File(\…\.efi)` 路径定启动项与它指向的实体，`Disklabel type` 与 `lsblk -o NAME,SIZE,TYPE,FSTYPE` 定分区表类型与设备是否被枚举（GPT（GUID Partition Table，GUID 分区表）盘在 legacy 下要有一块约 1 MiB 的 BIOS boot 分区放 `core.img`）。判据是"指针与实体分别验证"：**启动项是指针、ESP（EFI System Partition，EFI 系统分区）上的 `.efi` 文件是实体**，指针还在而实体不在了，现象与"没配启动项"完全一样。

**第 3 层（给出边界与代价）**

> 边界有三条。一是这一段的判据有取数前提：能在系统里读的字段都要等系统起来，故障当下只有屏幕、带外控制台与固件设置界面可读，所以那些命令的用法是事先采集、事后对照，而不是在故障现场敲；把这一步留到故障当天做，等于没有判据。二是判据随环境换：走 UEFI 时看启动项与 ESP 路径，走 legacy 时看设备顺序与引导扇区，两个判据互不通用；容器里这一整段根本不存在，屏幕上不会有任何固件输出。三是"启动项还在"推不出"能启动"：ESP 被重新格式化后指针悬空，现象与"没配启动项"一样；反过来，UEFI 规范规定启动项为空或全部失败时会尝试 ESP 上的回退路径 `\EFI\BOOT\BOOTX64.EFI`，所以"启动项丢了"与"起不来"也不等价。
>
> 代价与顺序：这一段的当场现场只存在于屏幕与带外日志，它们会被后续输出滚掉，所以第一步是只读取证（看清屏幕、导出事件日志、把固件设置界面的启动顺序拍下来）。之后分两种情况：机器还能从别的启动项起来、或用救援介质起了另一个系统时，才轮到系统内的读数与动手——先存一份现状（`efibootmgr -v` 的输出），再只调顺序、不删条目；机器完全起不来时，可用的动作只剩固件设置界面里的启动顺序与启动项开关。重装是唯一会把数据与配置一起毁掉的动作，排在最后；顺手关掉 Secure Boot 属于降低安全边界的决定，不是排障动作。

### 3.2 站在哪一层，说明什么

| 停留层 | 回答里缺的东西 | 缺口类型 | 回到哪一节 |
| --- | --- | --- | --- |
| 第 0 层 | 没有"现在是谁在输出"这个判断对象 | 结论型 | 原理《启动链为什么要分阶段接力》第 2 节 |
| 第 1 层 | 机制正确，但落不到字段上，也说不出固件侧的现场在哪 | 判据型 | 体系 一（上电到交棒给引导加载器）；实操 1 |
| 第 2 层 | 不知道哪些判据在故障当下根本读不到，也不知道启动项与实体要分开验 | 边界型 | 原理《启动链为什么要分阶段接力》第 4 节；治理 3.1 |
| 第 3 层 | 知道不能重装，但没排出取证与动手的先后 | 代价型 | 治理 3.2 |

### 3.3 第一反应不要做什么

不要在固件阶段去 `journalctl` 里找原因（那时还没有日志系统）；不要在没看清屏幕的情况下重启（那是唯一一份现场）；不要把 Secure Boot 关掉当成修好了签名问题。

## 4. 现象二：卡在 Secure Boot 签名错误，或停在等待按键的界面

### 4.1 逐层演进

**第 0 层（多数人的回答）**

> 签名报错，把 Secure Boot 关掉就过去了，先去 BIOS 里改一下。

关掉的是一条安全约束，不是故障本身；改动之后现象确实消失，所以这个动作看起来成立。换一台仍开着 Secure Boot 的机器，同一个原因会以同样的外观再来一次。

**第 1 层（说出机制）**

> Secure Boot 下固件只执行有可信签名的引导器，发行版因此要在中间放一个双方都认的 `shimx64.efi`；这条约束还会通过 Lockdown（内核切到受限模式的安全特性）往内核里延伸，未签名的模块被拒、`kexec` 受限。自编译或 DKMS（Dynamic Kernel Module Support，内核升级后自动重编第三方模块的框架）编出来的模块要走 MOK（Machine Owner Key，机器所有者密钥）流程把公钥注册进信任库。

因果链完整，但在机器上不能执行：不知道读哪一处来判断卡住的是引导器签名还是模块签名，也不知道这一步为什么不能远程做完。

**第 2 层（给出判据）**

> 当场可读的只有屏幕：停在 MokManager 界面等按键，说明固件已经执行了一个受信任的引导器，等待的是人。系统里那一组要等它起来（或者读上一次启动的日志）：`journalctl -k -b` 里的 `module verification failed` 或 `Key was rejected by service` 是签名被拒，与 `Unknown symbol in module`（模块与当前内核不匹配）、`Direct firmware load for xxx failed`（模块在、缺固件文件）是三件不同的事；`mokutil --sb-state` 与 `mokutil --list-enrolled` 读当前状态与已注册的密钥。与谁同看：`uname -r` 与 `modinfo <模块名>` 给出的 modules 目录路径，确认那个模块属于哪一个内核；DKMS 编译的模块还要看 `dkms status` 有没有 built/installed 记录。

**第 3 层（给出边界与代价）**

> 边界有两条。一是这条判据随环境与版本变：Lockdown 的触发与范围由内核版本、发行版补丁与固件设置共同决定，另一发行版或另一内核版本上，同一个模块可能被拒也可能被放过；云主机与受管环境常常不给固件界面，MOK 注册的"等按键"就表现为机器停在某处不动，屏幕上看不到任何提示。二是三种内核日志报错不能互换：签名被拒要走信任库，版本不匹配要按当前内核重编，缺固件要装固件包——用"签名"一条判据去套后两种，会得出相反的方向。
>
> 代价与顺序：MOK 注册要在重启后由人在固件界面按键确认，这一步无法用一条远程命令完成，所以代价是把一次远程变更变成一次需要有人到场或至少带外可控的操作；`kexec` 在 Lockdown 下受限，还会连带影响崩溃取证的落地空间。顺序是先只读取证（读日志与状态、存下失败那次的输出）→ 再选方向（发行版签名模块 / MOK 注册 / 回滚旧内核）→ 关掉 Secure Boot 只在确认这台机器的安全策略允许时作为临时手段，并且要写明它同时关掉了这一类证据。

### 4.2 站在哪一层，说明什么

| 停留层 | 回答里缺的东西 | 缺口类型 | 回到哪一节 |
| --- | --- | --- | --- |
| 第 0 层 | 把一条安全约束当成故障开关 | 结论型 | 原理《内核参数与模块的两套机制》第 7 节 |
| 第 1 层 | 说不出引导器侧与内核侧各自读什么 | 判据型 | 实操 4.2 |
| 第 2 层 | 不知道 Lockdown 随版本与环境变，也不知道注册必须有人按键 | 边界型 | 原理《内核参数与模块的两套机制》第 7 节 |
| 第 3 层 | 讲得出三条路，但一次也没在固件界面上做过 | 操作型 | 治理 3.5 |

### 4.3 第一反应不要做什么

不要随手关 Secure Boot；不要把 `module verification failed` 与 `Unknown symbol in module`、`Direct firmware load … failed` 当成同一件事；不要在只发了导入命令就重启的机器上反复重试（它在等人按键）。

## 5. 现象三：停在 `grub>`、`error: unknown filesystem`，或 `grub rescue>`

### 5.1 逐层演进

**第 0 层（多数人的回答）**

> 提示符出来了就是引导器坏了：`grub.cfg` 里那行不对，现场改一下、回去再 `update-grub` 存住；要是进了精简模式，重装引导器或系统吧。

两个动作各自错在不同的地方。`grub>` 说明 GRUB 本体与模块都已加载、坏的是配置那份产物，而 `update-grub` 的行为是读输入、重新生成产物，手工改的那一行会在下一次生成时被覆盖。`grub rescue>` 说明连 `normal` 模块都没加载起来，通常是 GRUB 找错了地方，重装是把"找不到"当成了"损坏"。

**第 1 层（说出机制）**

> `grub.cfg` 是生成物，输入是 `/etc/default/grub` 与 `/etc/grub.d/*`；RHEL 8/9 默认走 BLS（Boot Loader Specification，一个内核一个菜单项小文件的约定），菜单项落在 `/boot/loader/entries/*.conf`。掉进精简模式说明 GRUB 找不到 `/boot` 所在分区、或那里的 GRUB 模块目录不在了；`error: unknown filesystem` 是另一件事——GRUB 只带一组常见文件系统模块，`/boot` 落在它读不了的组合上就会报这句。

因果链完整，但没有可读的探针：分不开"GRUB 找错了地方"和"配置产物坏了"，也说不清该读哪两份文件来判断输入层有没有写进去。

**第 2 层（给出判据）**

> 先用两条探针分开两类落点：`ls` 列出 GRUB 眼里的设备与分区编号，看它与装系统时是否一致；`ls (hdX,gptY)/` 看该分区里有没有 `vmlinuz-*` 与 GRUB 模块目录（Debian 系常见 `/grub`、RHEL 系常见 `/grub2`）。判据只有两种结果：目录找不到是"找错了地方"，目录在而配置读不成是"配置坏了"。配置坏了这一侧要等系统拉起来之后再把输入层与产物层并排读（GRUB 提示符下这两个文件都读不到）：`grep -E '^GRUB_CMDLINE' /etc/default/grub` 对 `grep -E 'menuentry|linux' /boot/grub/grub.cfg`（Debian 系）或 `grubby --info=ALL`（RHEL 系）；默认走 BLS 的机器上菜单项不在 `grub.cfg` 里，`grep grub.cfg` 搜不到东西是正常的，要去看 `/boot/loader/entries/*.conf`。`unknown filesystem` 一侧读 `/boot` 的角色与类型：`findmnt /boot` 看它是不是独立分区、`lsblk -f` 看它的 `FSTYPE`。与谁同看：`lsblk -o NAME,SIZE,TYPE,FSTYPE` 看磁盘与分区的实际结构，`ls -l /boot/` 里 `vmlinuz-*` 与 `initrd.img-*` 的条数同时是"还有没有退路"的判据。恢复动作的语义是 `set root`、`set prefix`、`insmod normal`、`normal`，它们只影响本次启动。

**第 3 层（给出边界与代价）**

> 边界有三条。一是"被读的是哪一份产物"随固件类型与发行版变：换成 UEFI 机器后，实际生效的 `grub.cfg` 在 ESP 里，改 BIOS 路径下的那一份不起作用；换到默认走 BLS 的另一发行版后，输入层还包括每个内核的小配置文件——"改输入层再重新生成"这条判据在两种环境里指向的是一组不同的文件。二是设备名与分区编号本身就会变：换成另一块盘以后，`(hd0,gpt1)`、`/dev/sda`、`/dev/vda` 这些名字与编号都可能不同，虚拟机换平台时连控制器型号都变；容器里不存在这一段，没有 GRUB 提示符可落。三是探针"看不到内容"不等于"分区里没有内核"：GRUB 读得懂的文件系统比内核少，`/boot` 落在它读不了的布局上时，`ls` 同样读不出东西。
>
> 代价与顺序：现场动作按可逆性排——`set root`、`set prefix`、`insmod normal` 与菜单里按 `e` 临时改参数都只影响这一次启动，先做；`grub-install` 与重新生成配置改写的是下次启动要读的文件，本次运行不受影响也无法当场验证，排在取证与手动引导之后；重装系统会把数据与配置一起毁掉，只在探针确认 `/boot` 里确实没有内核与模块时才考虑。所有动作之前先看清并记下 `ls` 的输出，那是这一段的唯一现场；改生成物本身不作为动作。

### 5.2 站在哪一层，说明什么

| 停留层 | 回答里缺的东西 | 缺口类型 | 回到哪一节 |
| --- | --- | --- | --- |
| 第 0 层 | 把生成物当成配置文件，或把"找不到"当成"损坏了" | 结论型 | 判例 9；判例 1 |
| 第 1 层 | 说不出两条探针，也分不开输入层与产物层 | 判据型 | 体系 二；实操 1 |
| 第 2 层 | 不知道换个固件类型或另一发行版之后，被读的产物就换了地方 | 边界型 | 原理《启动链为什么要分阶段接力》第 4、6 节；判例 3 |
| 第 3 层 | 说不出重装、重新生成与现场手法之间的可逆性差别 | 代价型 | 治理 3.2 |

### 5.3 第一反应不要做什么

不要在现场直接改 `grub.cfg`；不要在没跑 `ls` 之前 `set root`；不要把"探针读不到内容"当成"分区空了"；不要重装引导器或系统。

## 6. 现象四：`VFS: Unable to mount root fs`、`dracut-initqueue timeout`，落到 `(initramfs)`

### 6.1 逐层演进

**第 0 层（多数人的回答）**

> 根挂不上了，先改 `/etc/fstab` 再重启一次。

`fstab` 要到第 ④ 段才被读，此刻还没有任何程序读过它，改动不产生任何影响；重启则会把这一份只存在于内存里的现场清掉。

**第 1 层（说出机制）**

> 内核把 initramfs 解开到内存里的临时根，执行其中的 `/init` 去找并挂真根；挂根需要驱动与用户态工具，而它们在根里，这个循环依赖由 initramfs 解开。挂不上就落到救援 shell。

因果链完整，但在机器上不能执行：不知道读哪两组读数，也不清楚两组读数各自能推出什么。

**第 2 层（给出判据）**

> 两组读数必须对着看。第一组是"它在找什么"：`cat /proc/cmdline` 里的 `root=`，判据不是值是什么而是**它是哪种标识**（文件系统 UUID（Universally Unique Identifier，通用唯一标识符）、PARTUUID（分区表项标识）、LABEL（卷标）、设备路径），加密或 LVM（Logical Volume Manager，逻辑卷管理）、软 RAID（Redundant Array of Independent Disks，独立磁盘冗余阵列）根还要看 `rd.luks.uuid=`、`rd.lvm.lv=`、`rd.md.uuid=`。第二组是"现在有什么"：`ls /dev/disk/by-uuid/`、`lsblk`、`blkid`。分支只有两种——目标设备在列表里但标识与 `root=` 不符是参数旧了；完全不在列表里是内核或 initramfs 没识别到那块盘，驱动缺失或缺固件。与谁同看：`lsinitramfs`（Debian 系）或 `lsinitrd`（RHEL 系）看归档里有哪些模块与 `conf/` 配置，它们要进系统后才能跑；救援 shell 里唯一能就地留下的成文证据是 RHEL 系的 `/run/initramfs/rdsosreport.txt`，它汇总了设备枚举与模块加载过程，含序列号与 UUID，对外提交前要脱敏。

**第 3 层（给出边界与代价）**

> 边界有两条。一是这一段随环境整体消失或改名：容器里根由运行时提供，不存在 initramfs 救援 shell；换到另一发行版，落点与工具集都不同（`dracut:/#` 与 `(initramfs)`、`dracut` 与 `initramfs-tools` 不通用）。二是"落到 initramfs"这一条判据分不开口令输错与设备没识别到：加密根会先要求输入口令，两种情形最终落到同一个 shell，但前者是输入问题、后者是驱动或参数问题，处置方向相反。
>
> 代价与顺序：initramfs 的现场在内存里，重启即失，`rdsosreport.txt` 一类的报告要先导出；在 shell 里改的文件改的是内存里的临时根，除非先 `mount -o remount,rw /sysroot` 并 `chroot /sysroot`，否则重启后什么都不会留下。顺序是先只读取两组读数 → 在 shell 里把系统拉起来或导出报告 → 进系统后改输入层并重建 initramfs → 最后才谈一次重启验证，而重建 initramfs 属于"让下次开机变复杂"的变更，动手前要确认退路。

### 6.2 站在哪一层，说明什么

| 停留层 | 回答里缺的东西 | 缺口类型 | 回到哪一节 |
| --- | --- | --- | --- |
| 第 0 层 | 不知道读 `fstab` 的程序此刻还没开始运行 | 结论型 | 原理《启动链为什么要分阶段接力》第 3 节 |
| 第 1 层 | 说不出"它要什么"与"现在有什么"两组读数 | 判据型 | 体系 三；实操 4.1 |
| 第 2 层 | 不知道换平台后设备名与控制器型号都会变、容器里没有这一段 | 边界型 | 判例 11 |
| 第 3 层 | 说不出这个 shell 是内存里的现场、也说不清改动为什么留不下 | 代价型 | 实操 4.1 |

### 6.3 第一反应不要做什么

不要在 initramfs shell 里改 `fstab`；不要反复重启；不要在没确认 `rw` 与 `chroot` 之前就在临时根里改文件。

## 7. 现象五：`You are in emergency mode`，或 `Failed to mount …`

### 7.1 逐层演进

**第 0 层（多数人的回答）**

> 启动失败了，重启一遍看看，不行就把新加的那行挂载删掉。

这个环境里根已经挂上、可以动手修，重启只是把同一个场景重演一遍并覆盖日志；而"把新加的那行删掉"在没确认失败的是哪一行之前，只是一次猜测。

**第 1 层（说出机制）**

> `systemd-fstab-generator` 在单元启动前把 `fstab` 与内核命令行翻译成挂载单元，被 `local-fs.target` required 的挂载失败会阻塞启动、把系统落到紧急模式；带 `nofail` 的条目只被 wanted、且不再被等待。

因果链完整，但说不出读哪个单元名、哪一行日志来判定失败的是本次改的那一行还是老隐患。

**第 2 层（给出判据）**

> `systemctl --failed` 是第一个入口，挂载单元的名字由路径转义而来（`/boot` 是 `boot.mount`、`/mnt/data` 是 `mnt-data.mount`、`-` 写作 `\x2d`）；`journalctl -xb` 里 `failed to mount` 附近那几行给出具体设备与原因。判据是"声明与事实"对照：`cat /etc/fstab` 该行写的来源，与 `findmnt <挂载点>` 给出的 `SOURCE`、`FSTYPE`、`OPTIONS` 指的是不是同一个设备。紧急模式下根通常是只读的，改配置前先 `mount -o remount,rw /` 确认可写。与谁同看：`findmnt --verify` 的警告要当真，`x-systemd.*` 这类选项拼错时 `mount -a` 可能只给警告就过去。

**第 3 层（给出边界与代价）**

> 边界有两条。一是"能用的工具与可改的文件"随落在哪个救援环境而变：紧急模式只有根挂载且默认只读、要过 root 密码；另一个救援 target（systemd 里表示"到达某个阶段"的单元）下本地文件系统已挂载、基础服务已起；而绕过认证直接起 shell 的环境里，`systemctl`、`journalctl` 所在的路径可能根本没挂——换成容器环境后，这套救援入口与 target 整体不存在，这条判据无从使用。二是失败的是文件系统本身而不是配置时（检查失败、介质故障），"改配置"这个方向是错的；`nofail` 只保证机器能起来，不保证这块盘能用，它是降级策略不是修复。
>
> 代价与顺序：动作的破坏性递增——`mount -a` 与 `findmnt --verify` 是只读或低风险，先做；改 `fstab` 前先把现状存下来，改完用 `mount -a` 验证、`systemctl daemon-reload` 让生成器重跑、`systemctl default` 继续启动，不必重启；在已挂载可写的文件系统上跑修复工具会把损坏放大，要真正卸载它通常得从救援介质启动，属于另一种风险等级，排在最后且要评估数据风险。

### 7.2 站在哪一层，说明什么

| 停留层 | 回答里缺的东西 | 缺口类型 | 回到哪一节 |
| --- | --- | --- | --- |
| 第 0 层 | 把"根已挂上、可以动手修"当成了"再启动一次" | 结论型 | 原理《从内核到 PID 1 与用户态》第 5.2 节 |
| 第 1 层 | 说不出读哪个单元名与哪一行日志 | 判据型 | 实操 4.3 |
| 第 2 层 | 不知道换一个救援环境后能用的工具与可改的文件就变了 | 边界型 | 原理《从内核到 PID 1 与用户态》第 6 节 |
| 第 3 层 | 说不出哪些动作会把数据风险放大 | 代价型 | 实操 4.3 |

### 7.3 第一反应不要做什么

不要盲目重启；不要在没确认哪一行失败前删 `fstab` 的条目；不要在根还挂着的状态下对文件系统跑修复工具。

## 8. 现象六：`A start job is running for …（1min 30s）`，或开机变慢而说不清哪里慢

### 8.1 逐层演进

**第 0 层（多数人的回答）**

> 开机慢就是有服务拖后腿，把 `blame` 排第一的那个关掉，或者把 90 秒的超时调短一点。

两个动作都作用在症状上：调小超时只是让数字变小，被等的东西仍然没解决；`blame` 排的是单元**自身**耗时、不含等待依赖的时间，所以第一名常常是个无辜的小服务。

**第 1 层（说出机制）**

> 那 90 秒是 systemd 的默认单元启动超时，说明它在等一个永远不会出现的依赖；开机时间可以按"谁在跑"分成固件、引导器、内核、用户态四段，`critical-chain` 给的是关键路径，路径上每一项慢则整体慢。

因果链完整，但还是落不到字段上：不知道"在等谁"读哪几项，也说不出"看不到那两段"意味着什么。

**第 2 层（给出判据）**

> 先分段落：`systemd-analyze` 的四段是秒，`firmware` 加 `loader` 大而 `kernel` 小说明问题在固件与引导器，`userspace` 大才轮到 systemd 侧。再定位在等谁：`systemctl list-jobs` 里状态为 `running`/`waiting` 的 job 名、`systemctl --failed` 里有没有失败的 `.mount` 单元、`fstab` 里那一行写的是哪种来源。关键路径读 `critical-chain` 的 `单元 @开始 +自身耗时`，`blame` 只作对照，两者的量级还要与 `userspace` 段对得上。与谁同看：超时值现场取（本机改过就不是 90 秒）；固件不提供时间戳时 `firmware`/`loader` 两段会整个不显示，可用 `FirmwareTimestampMonotonic`、`LoaderTimestampMonotonic` 是否为 0 现场核。

**第 3 层（给出边界与代价）**

> 边界有两条。一是四段分解这条判据不是到处都成立：虚拟机与部分云主机拿不到固件与引导器的时间戳，那两段不显示，此时"看不到"不等于"耗时为 0"，只能靠带外日志的时间戳；换到另一台机器，段的条数与超时的数字都可能不同。二是等的东西不同方向就不同：等的是某个设备标识，方向在 `fstab` 的来源与 `nofail`、`x-systemd.device-timeout=`；等的是网络，方向在依赖写法；等的是硬件枚举那类服务，方向在驱动与存储，不在配置。
>
> 代价与顺序：`systemd-analyze` 的首次启动会被缓存与一次性任务拉长，单次读数不能当结论，先取两三次稳定值，代价是时间与一次完整启动周期；照 `blame` 排名去优化，代价是改了一个不在关键路径上的服务、开机时间不变，还额外引入一次变更风险。顺序是先取稳定读数 → 定位到段与关键路径 → 再决定改依赖写法（可当场验证、可回滚）还是动硬件侧（需要窗口）。

### 8.2 站在哪一层，说明什么

| 停留层 | 回答里缺的东西 | 缺口类型 | 回到哪一节 |
| --- | --- | --- | --- |
| 第 0 层 | 把超时当成因，把 `blame` 排名当关键路径 | 结论型 | 判例 10 |
| 第 1 层 | 说不出"在等谁"与"慢在哪一段"各读哪几项 | 判据型 | 实操 4.4 |
| 第 2 层 | 不知道固件时间戳可能不提供、超时默认值要现场取 | 边界型 | 实操 2.1 |
| 第 3 层 | 说不清下钻的代价与改依赖写法的方向 | 代价型 | 体系 四 |

### 8.3 第一反应不要做什么

不要调小 `DefaultTimeoutStartSec` 了事；不要照 `blame` 的排名去优化服务；不要用一次 `systemd-analyze` 的结果下结论。

## 9. 现象七：能登录，但服务没起来

### 9.1 逐层演进

**第 0 层（多数人的回答）**

> 服务没起来，先 `systemctl restart` 一下，不行就看看端口通不通。

`restart` 会把上一次失败的现场（退出码、退出前打了什么）覆盖掉，而"端口不通"只是同一个事实的另一种说法，两者都不回答"它以什么方式结束的"。

**第 1 层（说出机制）**

> `is-enabled` 回答下次开机要不要起，`is-active` 回答现在是不是在跑，两者是独立的问题；`default.target` 是指向多用户或图形目标的软链，被指向一个不存在的单元时，开机会落到几乎没有服务的状态，而外观与"正常启动了但没有服务"非常像。

因果链完整，但说不出这三个问题各自的取值、以及退出码该怎么读。

**第 2 层（给出判据）**

> `systemctl --failed` 是第一入口；`systemctl status <unit>` 给出 `Active:` 行与 `status=<数字>/<大写名>`（0 正常、1 一般失败、203 可执行文件找不到、128 加信号号表示死于信号）；`is-enabled` 的取值是 `enabled`/`disabled`/`static`/`masked` 一类，`is-active` 是 `active`/`inactive`/`failed`/`activating`；`systemctl get-default` 给出这次开机的终点。与谁同看：`status=203/EXEC` 要和可执行文件路径与权限一起看，`.mount` 单元失败要转到 `fstab` 与挂载单元，服务自身的失败要看它退出前的日志。

**第 3 层（给出边界与代价）**

> 边界有两条。一是"启动成功"的标准是策略而不是机制，随单元类型变：一种是 `fork` 之后就算成功、此时可能还没监听端口，一种会明确报到，一种靠进程号文件——同一句 `start` 成功在三种类型下的含义不同，所以"起来了"与"可用了"是两件事；换到容器环境里，单元与服务管理器这套概念可能整体不成立。二是依赖写错会以两种相反的外观出现：把网络写成硬依赖会让服务在网络没就绪时直接失败或让开机干等，只写排序不写依赖则是"顺序对了但对方根本没被启动"；用"程序有缺陷"一条判据去套，会漏掉依赖层。
>
> 代价与顺序：先只读取证（`--failed`、`status`、日志）→ 再判断是"没被启动"、"起来了又退出"还是"起来了但没就绪"→ 最后才 `restart`，且只在现场已经留存之后；改单元文件属写操作，重载后可当场生效，但同样要留回滚路径与验收命令。顺序颠倒的代价是：先重启一次，等于把这次失败的证据删掉，之后只能靠复现。

### 9.2 站在哪一层，说明什么

| 停留层 | 回答里缺的东西 | 缺口类型 | 回到哪一节 |
| --- | --- | --- | --- |
| 第 0 层 | 没有"它是以什么方式结束的"这个判断对象 | 结论型 | 体系 五 |
| 第 1 层 | 说不出三个状态问题的取值与退出码的读法 | 判据型 | 实操 2.3 |
| 第 2 层 | 不知道"启动成功"的含义随单元类型变 | 判据型（口径） | 原理《从内核到 PID 1 与用户态》第 7 节 |
| 第 3 层 | 说不出先取证后重启的代价差异 | 代价型 | 治理 3.2 |

### 9.3 第一反应不要做什么

不要先 `restart`；不要把 `enabled` 与 `active` 当成同一个问题；不要把"`start` 成功"当成"已经在提供服务"。

## 10. 现象八：需要进救援环境，而 root 密码不在手上

### 10.1 逐层演进

**第 0 层（多数人的回答）**

> 密码忘了，重装系统最省事；或者想办法把 root 密码重置掉就行。

重装会把数据、配置与现场一起交出去；而"重置掉就行"漏掉了这一步的性质——它改的是认证状态，同时是一起安全事件，动作本身需要授权与留痕。

**第 1 层（说出机制）**

> 救援入口的区别在于控制权停在哪一段、要不要过认证：紧急模式与救援模式由 `systemd-sulogin-shell`（其中调用 `sulogin`）先验 root 密码；`rd.break` 与 `init=/bin/bash` 停在更早的段，不过认证。

因果链完整，但说不出屏幕上那行字说明什么，也不知道"要不要认证"这件事本身有例外。

**第 2 层（给出判据）**

> 先看落点：`(initramfs)` 或 `dracut:/#` 说明还在第 ③ 段，真根挂在 `/sysroot` 且只读，要改文件得先 `mount -o remount,rw /sysroot` 再 `chroot /sysroot`；`You are in emergency mode` 说明根已挂上、PID 1 是 systemd、要先过 root 密码。root 被锁定时屏幕上打印的是 `Cannot open access to console, the root account is locked.`，它是设计而不是故障。与谁同看：这条路径的前提是能碰到控制台，所以带外管理或物理屏能否在系统未启动时看到画面要先确认；例外条件写在 `man 8 sulogin` 里。

**第 3 层（给出边界与代价）**

> 边界有两条。一是"要不要认证"随环境与配置变：root 账号被锁定时，带强制选项的进程会不问密码直接给 root shell，所以"现代发行版一定不给 root shell"不成立——这条判据取决于该系统服务启动时带不带那个选项，也取决于发行版怎么配置，换一个内核版本或发行版要重新看一次。二是换成容器环境后没有引导链与控制台可碰，这套入口整体不成立，入口在宿主一侧；而"能不能碰到控制台"这件事只在实测过一次之后才算数。
>
> 代价与顺序：绕过认证的路径在物理接触与带外控制台面前等于零防护，所以处置顺序与排障相反——先确认这是一次授权操作、留下谁在何时为什么改的记录（它同时是一起安全事件），再动手；改认证文件必须重挂可写并 `chroot`，改动落在真根上、不可逆程度高，只在快照可用时做；重装系统排在最后，且只在数据与配置另有来源时才是可选项。

### 10.2 站在哪一层，说明什么

| 停留层 | 回答里缺的东西 | 缺口类型 | 回到哪一节 |
| --- | --- | --- | --- |
| 第 0 层 | 把认证入口当成系统故障，也漏掉它的安全性质 | 结论型 | 判例 8 |
| 第 1 层 | 说不出四类入口各自停在哪一段、要不要认证 | 判据型 | 原理《从内核到 PID 1 与用户态》第 6 节 |
| 第 2 层 | 不知道 root 被锁定的报错是设计、也不知道强制选项的例外 | 边界型 | 原理《从内核到 PID 1 与用户态》第 6 节 |
| 第 3 层 | 讲得出重置办法，但没在带外或控制台上演练过，也没按安全事件留痕 | 操作型 | 治理 3.5 |

### 10.3 第一反应不要做什么

不要为了拿到 shell 就重装系统；不要把绕过认证的路径当成常规手段（它同时是一起安全事件）；不要在没确认授权、没留记录的情况下改动认证文件。

## 11. 三条横切线

主线之外的三个量横穿全部站点。它们不产生新的现象，但每一个判断都要用到，所以单独列出来定位。

**存储标识线——同一块盘在不同层有好几个名字。**

> 停在第 0 层的说法是"盘还在、数据没丢，改一处配置就行"，第 1 层能说出标识有文件系统 UUID、PARTUUID、LABEL 与设备路径几种、各有自己的失效条件，第 2 层会先读 `ls /dev/disk/by-uuid/` 与 `lsblk` 判断目标设备在不在、再比 `cat /proc/cmdline` 里的 `root=` 是哪种标识，第 3 层知道这些标识分属启动项、`root=`、`fstab` 三处、不会一起更新，克隆或重建分区表之后必须三处各核一次。判据缺失时的表现是：改了一处就重启验证，然后以"改了还是起不来"的形式再暴露一次。

**参数与模块线——同一个值写在不同位置，被读取的时刻差着几个阶段。**

> 停在第 0 层的说法是"哪个文件里改一下、重启就好"，第 1 层能说出启动参数只在启动那一瞬间生效、运行时参数写入即生效但重启即失、模块参数在模块加载那一刻只被读一次，第 2 层会用 `/proc/cmdline`（启动参数的唯一验收标准）与 `sysctl <名字>` 分别验收，并按文件编号与目录优先级判断谁盖了谁，第 3 层知道"配置写了"不等于"生效了"（改了输入没生成产物、产物不是被读的那一份、参数写到了另一个变量上、根本没重启），也知道 `lsmod` 只列可加载模块、`blacklist` 只挡主动加载。判据缺失时的表现是：反复重改同一个文件，或者拿"服务是 active"这类旁证代替验收。

**证据线——现场存在哪一层介质上，决定它会不会在重启时消失。**

> 停在第 0 层的说法是"再看一眼日志就知道了"，第 1 层能说出介质是内存的那几类现场（内核环缓冲、initramfs shell、启动耗时数据）重启即失，第 2 层会先读 `journalctl --list-boots` 有几条、`ls -d /var/log/journal` 是否存在、`/sys/kernel/kexec_crash_size` 是否非 0，再决定能不能读，第 3 层知道持久化只是前提（限流会丢消息、容量与保留期决定能回溯多久）、崩溃转储只在 panic 时触发且四条失效条件平时不报错、重启原因的确定性结论在带外事件日志里。判据缺失时的表现是：先止损再取证，而介质是内存的那部分已经不存在了。

三条线共有的定位信号是"这条线我知道，但每次都要从盘符推回参数、再推回它被谁读"——判据没有落成一张可以查的表。补法是回到体系 6.1、6.2、6.3，把三条线各自的列（标识 / 属于谁 / 什么时候变 / 用在哪；载体 / 何时被读 / 生效范围 / 不改就重启会怎样；证据 / 介质 / 消失条件 / 取证命令）抄成一张自己的对照表。

## 12. 交付物是排查的凭证

定位缺口不能只靠回想，凭物是把"我做过"与"我读过"分开的唯一办法，缺少它们时前面这些自评会整体偏高。

| 物件 | 要留下什么 | 用来验证哪一层 |
| --- | --- | --- |
| 只读启动基线卡 | 在系统能正常启动的状态下采集（固件段的判据只有这时候才读得到）：发行版、内核、systemd 与 cgroup 版本；启动模式与分区表类型；根设备、`root=` 的写法与两者是否一致；`/boot` 与 ESP 的角色与剩余空间；已装内核套数与默认启动项；journal 是否持久化与可回溯几次；`crashkernel=`、`/sys/kernel/kexec_crash_size` 与 `/var/crash/`；救援通道能否在系统未启动时看到画面；采集时刻 | 第 2 层（有没有真取到值） |
| 可回滚变更记录 | 改的是哪一层载体（哪个文件的哪一行、哪个启动项、哪个 `sysctl` 文件与编号）、每条改动对应的可执行验收命令与期望输出、回滚命令与触发回滚的可观察状态、重启后的实际读数 | 第 2、3 层（是否知道验收依据与退路） |
| 启动耗时前后对照 | 改动前后各一次 `systemd-analyze`、`critical-chain`、`blame` 的原始输出，同口径、带时刻、至少两三次，机器规格与启动模式一起记 | 第 2 层（口径是否一致） |
| 换环境对照记录 | 选三项现象，各给出另一环境下的取数位置与判据是否仍成立：另一台走 UEFI 的机器、另一发行版、容器内 | 第 3 层（换环境是否还成立） |
| 救援与取证演练记录 | 演练类型、机器与是否可快照、实际动作与恢复耗时、屏幕上看到什么、用哪个字段判定了分支、踩到的坑、整改项 | 第 3 层 |
| 未实测项清单 | 本环境做不到的项与补做方式：带外通道是否见过画面、主动触发一次崩溃、跨平台迁移、另一发行版的引导与 initramfs 工具路径 | 全部四层（防止把转引当实测） |
| 错题清单 | 现象、当时的答案、正确判据、缺的那一层、下次复查日期 | 定位本身（第四列必须落在缺口类型上） |

上表七件同时也是本章治理篇第 3 节五件产物的自用形态：产物是交出去的，这七件留给自己对照。

## 13. 记录格式

一行记一个现象，五栏：现象、当时读到的字段、判据、边界、缺口层。表头写环境三件事——内核版本、发行版、是否在容器内。每行另加一栏状态，只取三个固定的词：实测、转引、未实测；"转引"必须写出处（man 节号、内核文档路径或发行版文档的章节）。

把读过的当做过是这份记录唯一无法挽救的失效方式：环境更换后结论被推翻，而记录里看不出哪些结论本来就没有实测支撑——启动类的结论尤其如此，它的判据多半依附于固件类型、发行版与内核版本。

复查日期只写 D+1、D+3、D+7、D+21 四个。启动类判据的验收大多要等一次重启，日期就是把那次验证固定下来；没有日期的错题等于没有复查。

## 14. 定位到缺口之后补什么

六个类型的补法不同，用错补法会补到不需要补的地方。

| 缺口类型 | 表现 | 补法 | 不要做什么 |
| --- | --- | --- | --- |
| 结论型 | 停在现象命名或一个动作上，连这一段凭什么交棒都不熟 | 回到对应原理篇，用自己的话写出机制并配一个反例 | 不要从背结论开始 |
| 判据型 | 机制清楚，落不到字段 | 重新执行一次只读命令，记录输出形态与关键字段的值，而不是只记命令名 | 不要只记命令不记输出 |
| 判据型（口径） | 分不清同一个量的多个口径，或把默认值当常数 | 把该字段的口径、单位、判据、与谁同看写成一行；凡默认值一律现场取并记下版本 | 不要把 `blame` 与 `critical-chain` 这类不同口径的输出放进同一张对比表 |
| 边界型 | 结论正确，换个固件类型、发行版或环境就失效 | 列三条反例：换固件类型、换发行版、换容器环境各验证一次 | 不要以"应该大致相同"作结 |
| 代价型 | 知道怎么做，不知道风险与顺序 | 补三行：代价、回滚动作、触发回滚的可观察状态 | 不要把风险留给别人发现 |
| 操作型 | 讲得出，没做过 | 在可快照实验机上做一次只读采集与一次可回滚变更，留下带时刻的原始输出 | 不要用纸面推演代替动手 |

带着一个具体缺口回到一到两篇，比重读整章有效。如果发现"每篇都要重读"，通常说明缺的不是细节，而是前置概念——回到导读确认主线各站与三条横切线各自提供什么。

## 15. 边界

本篇覆盖的范围与本章一致，落在别处的追问照实划出去：挂载选项的取舍与文件系统的修复、日志的落点与保留期、内存压力与进程被杀的分界、开机耗时里与设备响应有关的部分、单元文件的编写与依赖设计、容器运行时的镜像与根文件系统、带外通道与硬件的资产台账，都不在本篇的判据之内。遇到这类追问，正确回答是指出它属于哪个领域，而不是在本章内部勉强作答。

本篇的判据只引用本章出现过的字段。引用章外指标时，测的是别的东西，缺口也会被错误归因。

核查动作用只读方式：`ls /sys/firmware/efi`、`cat /proc/cmdline`、`systemd-analyze`、`systemctl --failed`、`journalctl`、`findmnt`、`lsblk`、`ls -lt /var/crash/` 在生产机上也可以做。需要变更才能验证的项——调整启动项、重新生成引导配置、重建 initramfs、写 `sysctl`、改 `fstab`、主动触发一次崩溃——在可快照的实验机上做，并留下回滚命令与观察窗口。

## 16. 核对方式

从导读的故障现场定位表抽四行（固件无输出、提示符、initramfs、紧急模式、变慢各至少覆盖一类），逐行遮住右侧自测；每项说出站点、首查字段、判据、一条边界、一句"第一反应不要做什么"。说完之后自己回答一个问题：**刚才哪一句指不到字段**。指不出的那一句就是当前所处的位置，据此翻回第 3 至第 10 节的对应表格。

再抽一项承接两层追问：第一层问"依据是什么"，第二层问"换个环境还成立吗"。第二层答不出的，缺口在边界型，补法见第 14 节。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 把这篇当成一张评分表 | 它的用途是定位停在哪一层，不是给出通过与否 |
| 用"读了几遍"判断自己会不会 | 阅读次数与能不能当场给出判据无关 |
| 用术语熟练度代替判断力 | 名字记得住、机器上没取过值，缺的是操作层 |
| 机制讲得流畅就以为说得完整 | 判据落不到字段上，是启动链上最常见的一种失效 |
| 未实测项不标注 | 固件类型、发行版或内核版本一换，无法分辨哪些结论本来就没有实测支撑 |
| 缺口用"没记住"概括 | 缺的类型不同补法不同，概括之后一定补错方向 |
| 一次把所有层级都读完 | 逐现象一次读一层、对照一次，比通读一遍有效 |
| 在没确认现场是否还在的情况下先重启 | 介质是内存的那几类证据（环缓冲、initramfs shell、启动耗时）重启即失 |
| 把系统内的命令用到固件段或救援环境 | 故障当下没有 shell；`efibootmgr`、`lsblk`、`lsinitramfs` 这类读数只能在系统能起来时取，或事先采进基线，当场可读的只有屏幕、带外控制台与固件设置界面 |

## 要点自测

**问：本篇与本章的判例篇、治理篇分工有什么不同？**
答：判例篇回答"这个现象最容易被误判成什么、判据是什么"，治理篇回答"要交出哪些产物、字段怎么填"，本篇回答"我的回答停在哪一层、因此缺的是哪一篇的哪一节"。

**问：现象一的判据为什么不能在故障当天再取？**
答：固件段故障当下没有 shell，系统内那一组字段（`ls /sys/firmware/efi`、`efibootmgr -v`、`lsblk`）都要等系统能起来才读得到，当场可读的只有屏幕、带外控制台与固件设置界面。所以这一组判据必须在机器正常时采进基线，故障当天做的是"屏幕上的现象 ↔ 基线里的记录"的对照。同一个前提在引导加载器提示符与 initramfs shell 里也成立：那两个环境里读不到 `/etc/default/grub` 与 `/boot` 下的文件，能就地在提示符里敲的只有 GRUB 自己的那条探针。

**问：第 1 层与第 2 层在语言外观上几乎一样，区分它们的那一个动作是什么？**
答：能不能指到一个字段。指不到字段的机制叙述停在第一层——例如讲清了 initramfs 要解的死锁，却说不出在救援 shell 里该读哪两组读数。

**问：为什么"那 90 秒"这一处的第 0 层误判值得单独列出来？**
答：它把超时当成了成因。调小超时能让开机数字变小，但被等的东西仍然没出现，故障会以更晚、更难查的形式复现；而同一处的第二个动作——照 `blame` 排名优化服务——优化的是不在关键路径上的单元。

**问：现象一与现象三都把"重装"排在最后，两处的理由有什么不同？**
答：现象一的现场在屏幕与带外日志上，重装是最先把这份现场抹掉的动作，且它同时毁掉数据与配置；现象三的现场在 GRUB 提示符里，`ls` 的两条探针一旦跑过就能判断"找错地方"还是"配置坏了"，而这两种情形的修法都比重装轻，重装只在探针确认 `/boot` 里确实没有内核与模块时才有理由。

**问：三条横切线共有的定位信号是什么？**
答："这条线我知道，但每次都要重新推一遍"——说明判据没有落成一张可查的表，缺的是把三条线各自的列抄在一起的对照表。

**问：错题清单里最关键的是哪一列？**
答：缺的那一层。只抄正确判据，第二次会错在同一处。
