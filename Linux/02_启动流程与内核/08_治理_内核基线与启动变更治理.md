# 内核基线与启动变更治理

## 1. 没有制度的启动变更会怎样

启动链有一个别处没有的性质：**它的验证滞后于它的执行**。控制权在链上单向流动，已经运行的机器上改写引导配置、启动项、initramfs，只是修改了"下次启动要读的文件"——本次运行完全不受影响，真正的验收只能来自一次重启。于是变更与验证之间隔着一个**重启**，而重启本身是风险：起不来就是机器不可用，远端机器还可能失联。

没有制度时，这个问题会以四种可预期的形态出现：

**形态一：没有可回退的内核。** "升级内核"在大多数团队被当成一条命令（`dnf install kernel` 或 `apt install linux-image-*`）。但发行版的自动清理机制（RHEL 系 `installonly_limit` 限制保留数量；Debian 系 `autoremove` 可被带 `--purge` 执行）会静默删掉旧内核。等到新内核起不来时，退路在几个月前就被清掉了。

**形态二：参数改动没有台账。** 内核侧的值有两类载体——启动参数（内核命令行）与运行时参数（`sysctl`），机制与生效时机完全不同（分界见原理篇"同一个词，两条完全不同的通路"，本文不再展开），但它们在实际工作里被混着改、混着记。没有台账时，团队会积累一批"某人某次改过"的值：没人知道它的取值依据、改在哪个文件、怎么撤回。半年后要求放宽或收紧时，只能靠试。

**形态三：启动相关的变更被当成普通配置变更。** 一次 `fstab` 编辑、一次 `initramfs` 重建、一次启动项调整，在变更分级里常常和"改一个业务配置"同级。它们的实际风险差着一个数量级：前者做错是**重启后彻底失联**，后者做错通常只是某个功能不工作。

**形态四：取证能力从未被验证。** 崩溃转储、带外通道、日志持久化这三件事的失效条件都不在平时报错，只在最需要它们的那一刻暴露。没有制度时，它们会一直是"配置上写着有"的状态。

## 2. 行业通行做法

下面五条是这个领域的通行做法，出处都是公开资料。它们不是"最佳实践清单"，而是**已经有人付过学费的结论**。

**第一条：永远保证机器上至少有一个能起来的旧内核。** 这是发行版自己就在做的设计——RHEL 系用 `installonly_limit` 限制同时安装的内核数量而不是替换，Debian 系把每个内核做成独立的 `linux-image-*` 包。设计意图就是"升级是新增，不是替换"。运维侧要做的是**在升级前确认这个不变量还成立**，而不是在升级后祈祷。

**第二条：内核升级是"一次变更"，不是"一次命令"。** 上游与发行版的文档都把它写成一段流程（升级前准备 → 只装不删 → 重启后逐项验证 → 准备好回滚），原因是升级会连带触发三件独立的事：新内核与配套 initramfs 的生成、第三方模块（DKMS）的重新编译、引导配置的更新。任何一件失败都不会让包安装失败，但都会让"重启"变成"起不来"。

**第三条：减少重启的手段要与它不能做的事一起记录。** `kexec` 与热补丁（RHEL 的 `kpatch`、Ubuntu 的 livepatch）常被放在一起说，但它们解决的问题完全不同：`kexec` 跳过固件与引导加载器直接把新内核换进内存，省的是 POST 时间，**它不是冷重启、不复位硬件，因此不能用来排除硬件问题**；热补丁用函数级补丁修厂商明确覆盖的 CVE，用来**推迟**重启窗口，不替代版本升级、不覆盖驱动与模块。行业做法是把"这个季度哪些 CVE 在覆盖清单里"作为决策依据，而不是把热补丁当成"不用升级"。

**第四条：救援通道按"故障时还能不能看见画面"来验收，而不是按"配过没有"。** 服务器厂商与带外管理（IPMI/iDRAC/iLO）的文档都把"能在操作系统未启动时看到画面并操作"作为可用性标准。这条通道会随固件升级、密码轮换、网络策略变更而失效，所以要写成巡检项，并且**验收动作是实测一次**，不是查看配置。

**第五条：崩溃取证能力必须演练。** 内核文档把 kdump 的配置与转储流程写得很清楚，同时它的失效条件（预留内存不足、转储空间不够、kexec 被禁用、捕获内核未加载）**在平时完全不报错**。所以业界的做法是把它纳入上架验收与年度演练：在可快照的实验机上主动触发一次 panic，确认 `vmcore` 真的落盘、体积与耗时符合预期、并且能被分析工具打开。

## 3. 可交付产物

下面五件是这套治理的最小产物集。每一件都给出**字段**，因为"有产出"的判据是字段填满了，不是文件存在。

### 3.1 启动基线卡

**用途**：任何启动相关变更的前置条件与后置对照。**采集一次约十分钟，全部只读，生产机上可以做。**

| 字段 | 取值来源 | 为什么需要它 |
| --- | --- | --- |
| 发行版、内核、systemd、cgroup 版本 | `cat /etc/os-release`、`uname -r`、`systemctl --version` | 默认值与路径随版本变化，没有版本就没有可比性 |
| 启动模式与分区表类型 | `ls /sys/firmware/efi`；`fdisk -l` 的 `Disklabel type` | 决定后面查哪一套引导路径 |
| 根设备、`root=` 的写法、两者是否一致 | `findmnt /`、`cat /proc/cmdline`、`lsblk -f` | "分区迁移后起不来"的根因就在这一栏 |
| `/boot` 与 ESP 的角色与剩余空间 | `findmnt /boot`、`findmnt /boot/efi`、`df -h` | 空间写满会让所有引导相关变更静默失败 |
| 已装内核套数与默认启动项 | `ls -1 /boot/vmlinuz-*`、`systemctl get-default` | "至少留一个能起来的旧内核"这条不变量的现场证据 |
| 日志持久化与可回溯次数 | `ls -d /var/log/journal`、`journalctl --list-boots`、`journalctl --disk-usage` | 取证能力的前提；容量与限流会决定"真出事时还剩多少"（判定见判例篇第 12 条） |
| 崩溃取证能力 | `/proc/cmdline` 里的 `crashkernel=`、`/sys/kernel/kexec_crash_size`、`ls /var/crash/` | 决定"崩溃后还能不能看原因" |
| 救援通道 | 带外地址与类型、串口参数、能否在系统未启动时看到画面 | 唯一一条独立于操作系统的通道 |
| 采集时间 | 现场时间（统一时区） | 跨机器比较的前提 |

### 3.2 启动类变更记录

**用途**：每一次涉及引导器、内核、initramfs、启动参数、`fstab`、启动项的变更都要有一份。字段是固定的六要素，缺一项这份记录就不能用于事故复盘。

| 字段 | 填什么 |
| --- | --- |
| 目标与影响面 | 为什么改、影响哪些机器与业务、是否需要停机窗口 |
| 变更前的状态 | 基线卡里相关字段的实际值（不是"应该是多少"） |
| 改动的载体 | 具体到文件与行（`/etc/default/grub` 的哪个变量、哪个 BLS 条目、`fstab` 的哪一行、哪个 `sysctl` 文件与编号） |
| 验证命令与期望输出 | 每条改动对应一条**可执行**的验收命令及其期望结果 |
| 回滚动作 | 回滚命令、触发回滚的条件（什么可观察状态下必须回滚） |
| 时间线与执行人 | 起止时间、分批范围、每一批的观察窗口 |

### 3.3 内核升级检查单

**用途**：把"升级四步"固化成一张可以打勾的单子。它是 3.2 的一个特化实例，因为内核升级是启动类变更里频率最高、连带最多的一种。

| 阶段 | 检查项 | 现场判据 |
| --- | --- | --- |
| 升级前 | 基线已记录 | `uname -r`、`/proc/cmdline`、启动项快照已存档 |
| 升级前 | 旧内核与旧 initramfs 都在 | `ls -1 /boot/vmlinuz-*`、`ls -1 /boot/initrd.img-*`（或 RHEL 的命名）条数 ≥ 2 |
| 升级前 | `/boot` 与 ESP 空间足够 | `df -h /boot`（一个内核加它的 initramfs 通常占几十至上百 MiB，两套内核并存就要留两倍；空间不足会让新 initramfs 被截断，**保证起不来**） |
| 升级前 | 退路可用 | 快照可用，或带外通道能在系统未启动时看到画面 |
| 升级前 | 已知第三方模块清单 | DKMS 状态、以及新内核上要验证哪些设备 |
| 升级中 | 只装不删 | 新旧内核并存；不手工改默认启动项 |
| 升级中 | 确认 initramfs 重建成功 | 产物文件时间戳更新、大小非零、能列出关键驱动 |
| 重启后 | 内核版本正确 | `uname -r` 是新版本 |
| 重启后 | 系统无新增失败单元 | `systemctl --failed` 为空 |
| 重启后 | 设备齐全 | `ip a`、`lsblk`、`lspci`，以及业务侧探活（DKMS 类问题常在"起来了但设备悄悄不对"时暴露） |
| 回滚前 | 先存现场 | `journalctl -b -1 > /root/failed-boot.log`（否则回滚成功的同时，根因也一起丢了） |

### 3.4 内核参数台账

**用途**：两类内核参数需要分开记账，否则"这个值是谁改的、为什么是这个值"会永久失传。

| 参数名 | 类别 | 载体（文件与行/编号） | 取值 | 取值依据 | 生效验证 | 回滚动作 |
| --- | --- | --- | --- | --- | --- | --- |
| 例如 `console=` | 启动参数 | `/etc/default/grub` 的 `GRUB_CMDLINE_LINUX`（或 BLS 条目） | 现场取 | 为什么需要串口输出 | 重启后 `cat /proc/cmdline` 里有它 | 从同一变量移除后重新生成 |
| 例如 `vm.swappiness` | 运行时参数 | `/etc/sysctl.d/100-tuning.conf` | 现场取 | 与同组机器的统一口径 | `sysctl vm.swappiness`，**重启后复核** | 改回原值并 `sysctl -w`（删文件不会改回当前值） |

两个容易漏的字段：**取值依据**（为什么是这个值）与**回滚动作**（怎么改回去）。少了前者，半年后没人敢动它；少了后者，出事时只能猜。

### 3.5 救援与取证演练记录

**用途**：证明"能力真的具备"，而不是"配置上写着有"。

| 字段 | 填什么 |
| --- | --- |
| 演练类型 | 带外通道可达性 / `fstab` 写坏恢复 / 忘记 root 密码 / panic 取证 |
| 机器与环境 | 哪台机、是否可快照、发行版与内核版本 |
| 前置条件 | 快照已打、业务已停、下游依赖已通知 |
| 实际动作与耗时 | 从发现问题到恢复服务的分钟数（这个数字才是 SLA 的依据） |
| 现象与判据 | 屏幕上看到什么、用哪个字段判定了分支 |
| 踩到的坑 | 与文档不符之处（例如本机 `mokutil` 未安装、`dracut` 不存在而用 `initramfs-tools`） |
| 整改项 | 要补的巡检项、监控项、变更前检查项 |

## 4. 治理场景与产出

### 场景一：给一批新上架机器建立启动基线

**背景**：一批 40 台同型号服务器即将交付，运维要确认"出事时能拿到现场"，并且以后做内核相关变更时有对照。

**做法**：把 3.1 的基线卡做成一次只读采集（生产机上可做，单台约十分钟），逐台填；对"不满足"的机器按 3.5 的方式整改后复采。**基线不是一次性动作**：任何启动相关变更后都要回填，否则半年后它描述的是半年前的机器。

**产出**：40 份启动基线卡 + 一份汇总（按"日志持久化 / 崩溃取证 / 救援通道"三项分列满足与不满足的机器清单）+ 整改排期表。**汇总比单机卡更有价值**——它直接回答"这批机器的取证能力短板在哪一项"。

### 场景二：一次内核安全升级的完整变更

**背景**：安全扫描要求把内核升到某个带补丁的版本，涉及 3 个业务集群、共 60 台机器，业务方只给了每周日凌晨两小时窗口。

**做法**：按 3.3 的检查单把升级拆成"准备 / 执行 / 验证 / 回滚预案"四段，并按集群分三批推进：先非核心集群选 1 台做试点（观察一个完整业务周期），再扩到该集群其余机器，最后才动核心集群。**关键设计是"至少留一台机器保留旧内核启动项"这条不变量在每个批次里都成立**——检查单的第 2 项就是它的现场判据。

**产出**：一份带批次的变更单（含每批的机器清单、观察窗口、回滚触发条件）+ 试点的完整验证记录 + 升级后的启动基线卡回填。**回滚触发条件必须写成可观察的状态**（例如"试点机重启后 `systemctl --failed` 非空且 5 分钟内未自愈"），不能写"如果出问题就回滚"。

### 场景三：把散落的 `sysctl` 调优收敛成台账

**背景**：一批机器上积累了三年的调优参数，散落在 `/etc/sysctl.conf`、`/etc/sysctl.d/` 的十几个文件、以及某些服务 unit 的启动脚本里；同一个键在多个文件里被赋了不同的值，实际生效值只能靠 `sysctl` 现场读。

**做法**：A 步先把"实际生效值"采下来（`sysctl -a` 或按需的子集），B 步把"每个键被写在哪些文件里"找出来（`grep -rn <键名> /etc/sysctl.d/ /usr/lib/sysctl.d/ /etc/sysctl.conf`），C 步处理三类冲突：**编号冲突**（应用顺序决定的覆盖）、**跨机制冲突**（`/etc/sysctl.conf` 与 `/etc/sysctl.d/*.conf` 同名键）、**更晚的写入者**（云初始化工具、配置管理系统、容器编排层的启动脚本会在 systemd-sysctl 之后重写同一个键）。收敛的目标不是"只留一个文件"，而是**每个键只有一个权威来源，且这个来源在台账里可查**。

**产出**：一份内核参数台账（3.4 的字段）+ 一份冲突清单（键名、涉及文件、实际生效值、收敛后的归属）+ 一次重启后的复核记录（证明"开机写入的就是台账里的值"）。

### 场景四：一次"机器莫名重启"的复盘，落脚到制度

**背景**：一台机器在夜间自己重启过一次，日志未持久化，没有崩溃转储，带外通道当时也不可用。复盘时只能得出"未确认"的结论。

**做法**：复盘不能停在"没查到原因"，要落到可执行的整改项，并且每一项都要有验收方式。这类复盘的典型产出是四条：把 journal 持久化补上（验收：`journalctl --list-boots` 有多条记录）；把崩溃取证配上并演练（验收：实验机上主动 panic 一次，`vmcore` 落盘且能打开）；确认带外通道能在系统未启动时看到画面（验收：实际接一次控制台）；把这三项写进上架验收与巡检项（验收：下一批机器的基线卡里这三栏都满足）。

**产出**：一份复盘记录，包含**结论的置信度**（本次只能写"未确认"及其依据）、四条整改项与各自的验收方式、以及整改的排期与责任人。**复盘的价值不在于这一次查出了什么，而在于让下一次的现场不会消失。**

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 把内核升级当一条命令执行 | 升级会连带触发 initramfs 重建、DKMS 编译、引导配置更新三件事，任一件失败都会让重启变成起不来 |
| 让自动清理删掉旧内核 | RHEL 系 `installonly_limit` 设得小、Debian 系跑过带 `--purge` 的 `autoremove`，都会让退路消失；要在升级**前**确认 |
| 回滚后不保留失败日志 | 现场随重启丢失，根因永远查不出来；回滚前先存日志 |
| 用 `kexec` 排除硬件问题 | 它不经过固件、不复位硬件，不是冷重启；用它排硬件故障会得出错误结论 |
| 把热补丁当成"可以不升级内核" | 它只覆盖厂商明确修补的函数级 CVE，不含驱动与模块，补丁通常还是累积的 |
| 参数台账只记"值" | 不记取值依据与回滚动作，半年后没人敢动它；删掉 `sysctl` 配置文件也不会把当前值改回 |
| 把带外通道的可用性当成"配过一次就永久有效" | 固件升级、密码轮换、网络策略变更都会让它失效；要写成巡检项并实测 |
| 用"服务 active"验收 kdump | 失效条件平时不报错；验收方式是在实验机上主动触发一次 panic |
| 一次性给全部机器升级 | 出问题时全站同时失去退路；先试点、再分批 |
| 变更单写"如果出问题就回滚" | 回滚触发条件必须是可观察的状态，否则执行时只能靠临场判断 |

## 要点自测

**问：为什么启动类变更需要专门的治理，而不能沿用普通配置变更的流程？**

答：因为它的**验证滞后于执行**。启动链单向流动，运行中的机器上改写引导配置、启动项、initramfs 只影响下次启动，验收只能来自一次重启；而重启本身有失联风险。所以这类变更需要"前置退路"（旧内核、快照、带外通道）与"延后验收"（重启后逐项检查）两套机制同时成立。

**第一反应不要做什么**：不要把"命令没报错"当成变更完成。内核升级的验收标准是重启后的 `uname -r` 与设备/业务状态。

**问：内核参数台账里，最容易被漏掉的两个字段是什么？为什么它们重要？**

答：**取值依据**（为什么是这个值）与**回滚动作**（怎么改回去）。少了前者，调优值会在半年后变成没人敢动的神秘数字；少了后者，出事时只能靠猜——而且运行时参数还有一个陷阱：删掉配置文件不会把当前内核里的值改回去，必须显式写回或重启。

**第一反应不要做什么**：不要在台账里只记"某键 = 某值"。那种记录在事故现场等于没有。

**问：怎么验收"这台机器具备崩溃取证能力"？**

答：分两层。第一层是只读核查：`crashkernel=` 预留是否生效（`/sys/kernel/kexec_crash_size` 非 0）、转储目标是否有空间、kexec 是否可用（云主机与 Lockdown 环境可能禁用）。第二层是**演练**：在可快照的实验机上主动触发一次 panic，确认 `vmcore` 真的落盘、体积与耗时符合预期、并且能被分析工具打开。第一层只能排除明显缺失，**只有第二层能证明能力具备**。

**第一反应不要做什么**：不要把第一层的读数当结论写进验收记录，也不要为了演练方便在生产机上做。

**问：一次"未确认原因"的重启复盘，怎样才算有价值？**

答：价值不在"这次查出了什么"，而在产出可执行、可验收的整改项：补日志持久化（验收：`--list-boots` 有多条）、配崩溃取证并演练（验收：实验机上 `vmcore` 落盘且能打开）、确认带外通道能在系统未启动时看到画面（验收：实际接一次控制台），并把这三项写进上架验收与巡检。同时复盘记录里必须写明**结论的置信度与依据**，把"未确认"写清楚，而不是用一个像样的猜测把它填满。

**第一反应不要做什么**：不要为了交出一份"有结论"的复盘而把猜测写成根因。错误的前提会让后续所有排查都走偏。

- `man 5 sysctl.d`、`man 8 sysctl`、`man 5 systemd-system.conf`：运行时参数的持久化规则与系统级默认值。
