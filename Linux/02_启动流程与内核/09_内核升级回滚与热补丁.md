## 0. 30 秒速览

> [!abstract] 这一篇只要记住六句话
> - **原则只有一句：永远保证机器上至少有一个能起来的旧内核。** 其余都是流程细节。
> - **内核升级是「一次变更」，不是「一次命令」。** 四步缺一步都算没做完：升级前准备 → 升级中保留旧内核 → 重启后逐项验证 → 准备好回滚。
> - **验收标准是 `uname -r`，不是「命令没报错」。** 重启后必须确认运行的是新内核，且关键服务与设备都在。
> - **三个高发翻车点**：`/boot` 空间不足导致 initramfs 被截断、DKMS 第三方模块没编出来、`fstab` 有坏挂载项——它们都会让「重启」变成「起不来」。
> - **`kexec` 不是冷重启**：它跳过固件、不复位硬件，不能用来排除硬件问题。
> - **Livepatch 只修厂商覆盖到的 CVE**：不覆盖驱动与模块，也不替代版本升级。

## 1. 升级前：先固定版本基线

升级前后要有可比对的基线，否则「变慢了」「有问题」都是主观印象：

```bash
cat /etc/os-release                        # 验证：发行版与版本（决定用哪套包管理与内核命名）
uname -r                                   # 验证：当前运行的内核版本（升级前的基准值）
systemctl --version | head -1              # 验证：systemd 版本（决定 unit 语法与 sysctl 行为）
cat /proc/cmdline                          # 验证：当前内核命令行（升级后要对比它有没有变）
ls -1 /boot/vmlinuz-* /boot/initramfs-*.img 2>/dev/null   # 验证：机器上现存的几套内核与 initramfs
df -h /boot                                # 验证：/boot 剩余空间（升级最容易在这里翻车）
systemctl --failed                         # 验证：升级前系统是否已经带病运行
```

把输出存成一份基线文件。**升级后所有验证都拿它做对照**，这才是「变了吗」的判据。

## 2. 升级四步

### 2.1 升级前准备

| 检查项 | 为什么 |
| --- | --- |
| 记录 `uname -r`、`/proc/cmdline`、现有启动项 | 回滚与验证的依据 |
| `/boot` 剩余空间 | 内核与 initramfs 各占几十 MiB；空间不足会让新 initramfs 被截断 |
| 带外管理通道可用 | 新内核起不来时，这是唯一的重启与选择入口 |
| 快照（虚拟机）或维护窗口（物理机） | 回滚成本最低的手段 |
| DKMS 模块清单（NVIDIA、部分存储驱动） | 新内核没有对应模块 → 网卡、存储、GPU 可能全失联 |
| 业务侧确认 | 内核升级必然重启，需要业务窗口 |

### 2.2 升级中：只装不删

```bash
dnf install kernel-<版本>                      # RHEL 8/9：新内核与配套 initramfs 出现在 /boot
grep -r installonly_limit /etc/dnf/dnf.conf     # 验证：本机保留几个内核（默认值以输出为准）
ls -1 /boot/loader/entries/                     # 验证：BLS 启动项是否新增（见子笔记 05）
```

```bash
apt install linux-image-<版本>                  # Debian/Ubuntu：/boot 下新增 vmlinuz 与 initrd，grub.cfg 自动刷新
dpkg -l 'linux-image-*' | grep ^ii              # 验证：本机装了哪些内核（确认旧内核还在）
```

这一步的核心是**不要动默认启动项**：让新旧内核并存，先确认新内核能起来再说。如果安装了 DKMS 模块，还要确认新内核的模块编译成功——编译失败通常不会让包安装失败，但会让机器在下次启动时丢设备。

### 2.3 重启后验证

```bash
uname -r                                   # 验证：运行的确实是新内核（第一验收标准）
systemctl --failed                         # 验证：没有新增失败单元
dmesg -T | tail -50                        # 验证：新内核启动时没有设备/驱动报错
ip a                                       # 验证：网卡与地址齐全（DKMS 类问题往往在这里暴露）
cat /proc/cmdline                          # 验证：启动参数与基线一致
```

还要把**业务健康检查**跑一遍。内核升级的风险不在「系统起不起来」，而在「起来了但某个设备/驱动悄悄不对」，这类问题只有业务指标能发现。

### 2.4 回滚

```bash
grubby --default-kernel                    # 验证：下次默认启动哪个内核（RHEL 系）
grubby --info=ALL                          # 验证：所有启动项及其 args
grubby --set-default /boot/vmlinuz-<旧版本>  # 验证：把默认启动项指回旧内核
```

回滚的两条路径：

- **重启时在 GRUB 菜单选旧内核**——最快，适合现场处置。
- **系统内改默认启动项再重启**——适合已知旧内核可用、需要稳定恢复的场景。

> [!important] 回滚后要保住现场
> 回滚前先执行 `journalctl -b -1 > /root/failed-boot.log`（把失败那次的日志存下来）。否则「回滚成功」的同时，**新内核为什么起不来的证据也一起丢了**，等于白失败一次。

## 3. 保留退路：旧内核怎么留住

| 系统 | 机制 | 要确认什么 |
| --- | --- | --- |
| RHEL 8/9 | `installonly_limit` 限制内核保留数量（`dnf` 的配置） | 值不能太小；升级后 `ls /boot/vmlinuz-*` 里仍有旧版本 |
| Debian / Ubuntu | 由包管理保留 `linux-image-*`，但可被 `autoremove` 清掉 | `dpkg -l 'linux-image-*'` 里旧内核还在，没有被自动清理 |

> [!warning] 「自动清理」是退路的头号杀手
> RHEL 上 `installonly_limit` 设得小、或手动执行过内核清理；Debian 上跑过一次带 `--purge` 的 `autoremove`——都可能把旧内核删干净。**这类操作要在升级前检查，而不是在起不来之后才发现。**

## 4. 两种「少重启」手段（进阶）

内核升级必然要重启，但有些场景希望减少重启次数或推迟重启窗口。两种手段常被放在一起说，解决的问题其实完全不同。

| 手段 | 能做什么 | **不能做什么** |
| --- | --- | --- |
| `kexec`（`systemctl kexec` 等） | 跳过固件与 GRUB，直接把新内核换进内存重启，省掉 POST 时间 | **不是冷重启**：固件未重新初始化、硬件状态未复位，不能用来排除硬件问题；Secure Boot 下对未签名内核会失败 |
| Livepatch（RHEL 的 `kpatch`、Ubuntu 的 livepatch 客户端） | 用函数级热补丁修厂商明确覆盖的 **CVE**，推迟重启窗口 | 不能替代内核**版本升级**；不覆盖驱动与模块；补丁通常是累积的，难以只挑一个；不同发行版/内核版本覆盖范围差异很大，装机前要查清单 |

判断口诀：**要「更快地换内核」用 kexec，要「暂时不换内核但修漏洞」用 Livepatch。** 两者都不是「不升级内核」的借口。

## 5. 生产动作：一次完整的内核升级与回滚演练（S2、S7）

> [!example]+ 生产动作：内核升级（含回滚路径）
> **什么时候用**：安全补丁要求内核版本更新、或需要新内核特性时。
>
> **动手前确认**（缺一项就不要开始）：
> 1. 有维护窗口与业务侧确认；
> 2. 有快照，或带外通道确认可用；
> 3. `/boot` 空间充足，且基线已记录；
> 4. 已确认机器上**会保留旧内核启动项**；
> 5. 已知 DKMS 模块清单，并知道新内核上要验证哪些设备。
>
> **怎么做**：
> ```bash
> uname -r > /root/kernel-before.txt            # 验证：记录升级前内核
> grubby --info=ALL > /root/grub-before.txt     # 验证：记录升级前所有启动项（RHEL 系）
> dnf install kernel-<版本>                     # 验证：RHEL 系安装新内核；Debian 系用 apt install linux-image-<版本>
> ls -1 /boot/vmlinuz-*                         # 验证：新旧内核都在
> reboot                                        # 验证：重启进入新内核
> uname -r                                      # 验证：运行的是新内核
> systemctl --failed                            # 验证：无失败单元
> dmesg -T | tail -50                           # 验证：无设备/驱动报错
> ```
>
> 别忘了**业务健康检查**——内核升级的风险常在「起来了但某个设备悄悄不对」。
>
> **怎么验证**：`uname -r` 显示新版本；`systemctl --failed` 为空；设备齐全（网卡、存储、GPU）；业务健康检查通过。**「命令没报错」不算验证通过。**
>
> **怎么退回去**：
> ```bash
> journalctl -b -1 > /root/failed-boot.log       # 先存现场
> grubby --set-default /boot/vmlinuz-<旧版本>    # 把默认启动项指回旧内核
> reboot
> uname -r                                      # 验证：已回到旧内核
> ```
> 现场处置时也可以在 GRUB 菜单里直接选旧内核。
>
> **要沉淀什么**：升级前后的 `uname -r`、启动项快照、`/boot` 空间、DKMS 模块编译结果、验证输出、耗时与踩到的坑。**这次升级的检查项就是下次升级的检查单。**

## 6. 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 升级后「装完就重启」 | DKMS 模块没编好、`/boot` 写满、`fstab` 有坏项，任何一个都会让重启变成起不来 |
| 只看命令退出码 | 安装成功不等于新内核可用；验收标准是重启后的 `uname -r` 与设备/业务状态 |
| 升级前不检查 `/boot` | 空间不足时新 initramfs 被截断，**保证起不来**；且备份可能一起损坏 |
| 让自动清理删掉旧内核 | 新内核起不来时没有退路；升级前必须确认旧内核启动项还在 |
| 回滚后不保留失败日志 | 现场随重启丢失，根因永远查不出来 |
| 用 `kexec` 排除硬件问题 | 它不做冷重启、不复位硬件，用来排硬件故障会得出错误结论 |
| 以为 Livepatch 可以替代升级 | 它只覆盖厂商明确修补的函数级 CVE，不含驱动/模块，也不覆盖所有漏洞 |
| 多台机器一次性全升级 | 出问题时全站同时失去退路；应先非核心、分批推进 |

## 7. 决策练习

> [!question]- 场景：一台机器升级内核并重启后，`uname -r` 显示新内核，但网卡全不见了。你现在最该做什么？
> A. 立刻回到旧内核，把机器恢复
> B. 先把现场固定下来（`journalctl -b -1`、`dmesg`、`ip a`、`lspci` 输出存盘或截图），再决定是修还是回滚
> C. 在新内核上重装网卡驱动
>
> **答案：B。**
> 「起来了但设备没了」是 DKMS/驱动类问题的典型特征。现场虽然还在（系统是活的），但它会随着后续操作被覆盖，而**回滚是随时能做的、把现场留下来却只有这一次机会**。
> A 不算错，但要排在取证之后；C 在没有确认根因（是模块没编出来、还是驱动版本不兼容）之前属于盲改。

> [!question]- 场景：安全扫描要求修一个内核 CVE，但业务方要求「这个季度不能重启」。你的方案应该是什么？
> A. 用 Livepatch 顶上，同时把这个季度的重启窗口排期
> B. 直接拒绝，说必须重启
> C. 关掉相关功能规避
>
> **答案：A。**
> Livepatch 的设计目标正是这个场景：用函数级热补丁覆盖厂商已修补的 CVE，把重启推迟到窗口期。**但它只覆盖被明确修补的部分**，所以必须同时确认该 CVE 在覆盖清单里。
> B 忽略了可行手段；C 属于用降低功能可用性换时间，需要单独评估，不能作为默认答案。

## 8. 要点自测

> [!question]- 内核升级的四步是什么？每一步的核心动作和验收标准各是什么？
> - 升级前：记录基线（`uname -r`、`/proc/cmdline`、启动项）、确认 `/boot` 空间与带外通道、明确 DKMS 清单。
> - 升级中：只安装、不动默认启动项，让新旧内核并存；确认 initramfs 重建与 DKMS 编译成功。
> - 重启后：`uname -r` 确认新内核，`systemctl --failed`、`dmesg -T`、`ip a` 与业务健康检查逐项过。
> - 回滚：GRUB 菜单选旧内核或 `grubby --set-default`；回滚前先把失败日志存下来。

> [!question]- 怎么保证「至少有一个能起来的旧内核」？
> - RHEL：确认 `installonly_limit` 的值合理，升级后 `ls /boot/vmlinuz-*` 里仍有旧版本。
> - Debian/Ubuntu：确认 `dpkg -l 'linux-image-*'` 里旧内核仍在，没有被 `autoremove` 清理。
> - 两者都要在**升级前**检查，而不是出事之后。

> [!question]- `kexec` 与 Livepatch 分别不能做什么？
> - `kexec` 不是冷重启：固件未重新初始化、硬件状态未复位，不能用来排除硬件问题；Secure Boot 下对未签名内核会失败。
> - Livepatch 不能替代版本升级：它只覆盖厂商明确修补的函数级 CVE，不覆盖驱动与模块，补丁通常还是累积的。
