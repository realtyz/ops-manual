# 高频误判

十二条按值班与复盘里的真实处境写成：**场景**（谁的机器、看到什么、别人怎么说）→ **常见误判及它为什么看起来成立** → **判据**（读哪个字段、什么数值或趋势、什么条件下结论会变）→ **一句话结论** → **出处**。字段的读法在实操篇第 2 节，各机制的由来在原理篇。

## 1. 「进 `grub rescue>` 了，引导器坏了，重装系统吧」

**场景**：一台 2U 机架服务器（Ubuntu 24.04 / 内核 6.8，系统盘在原 SATA 口 0 上），凌晨维护窗口里加了一块数据盘、把系统盘挪到了 SATA 口 3，重启后停在 `grub rescue>`。值班同事说引导器坏了，建议用装机 U 盘重装，天亮前恢复。

**常见误判**：把"GRUB 没找到自己的模块"当成"引导器文件损坏"。它看起来成立，是因为 `grub rescue>` 这个提示符本身很像"系统被破坏了"。

**判据**：`grub rescue>` 与 `grub>` 是两种不同的失败表现，区分它们就分开了两类原因。掉进 `grub rescue>` 说明连 `normal` 模块都没加载起来——GRUB 找不到 `/boot` 所在分区、或 `/boot` 里的 GRUB 模块目录不在了。判据是两条探针：`ls` 看分区编号是否与装系统时一致（增删磁盘、换接口、改固件启动顺序后，`(hd0,gpt1)` 很可能不再是原来那块盘），`ls (hdX,gptY)/` 看该分区里有没有 `vmlinuz-*` 与 GRUB 模块目录（RHEL 系常见 `/grub2`，Debian 系常见 `/grub`）。**条件会变**：如果这两条探针都正常、只是配置读不成（缺失、被截断、语法错），那是 `grub>` 一类的问题，处置是进系统后重新生成配置——**两类都不该在现场直接改 `grub.cfg`**，它是生成物。

**一句话结论**：`grub rescue>` 十次里有八次是"GRUB 找错了地方"，先 `ls` 探明分区再谈修法，别动重装。

**出处**：GNU GRUB Manual 的 "GRUB command line" 一章（`ls`/`set root`/`set prefix`/`insmod normal`/`normal` 的语义）；`man 8 grub-mkconfig`（`grub.cfg` 是生成物）。

## 2. 「fstab 里写 `/dev/sda1` 更直观，反正就一块盘」

**场景**：一台单盘虚拟机（Ubuntu 22.04，40 GiB 系统盘，`sda1` 是 `/`），新增数据盘时在 `/etc/fstab` 里写了 `/dev/sda1  /data  ext4  defaults  0 2`。当时挂载正常（那台机器上数据盘是 `sdb`），半年后扩容加了第二块盘并重启，机器进了 `emergency.target`，`/data` 挂到了别的地方。

**常见误判**：认为"只有一块盘时设备名就是稳定的"。它看起来成立，是因为在那台机器上它确实一直没变过。

**判据**：`/dev/sdX` 里的字母是**内核枚举顺序**，不是插槽位置：插拔磁盘、换控制器、换虚拟化平台、云盘挂载顺序变化都可能改变它。判据是把"声明"和"事实"对照着读——`cat /etc/fstab` 写的是什么来源，`findmnt /data` 与 `lsblk -f` 显示的又是什么设备。**条件会变**：文件系统 UUID 也不是永久标识（重新 `mkfs` 会变），但它只在"你自己重建文件系统"时变，而设备名会在你什么都没做的情况下变——两者的失效条件完全不同，这才是选 UUID 的理由。分区级标识用 PARTUUID，它在重建分区表时变。

**一句话结论**：持久配置里禁止出现 `/dev/sdX`；用 UUID（文件系统）或 PARTUUID（分区），并在变更后核对声明与事实是否一致。

**出处**：`man 5 fstab`（设备字段的写法与推荐）；`man 8 lsblk`、`man 8 findmnt`、`man 8 blkid`（如何读出现有标识）。

## 3. 「改了内核参数，重启了，怎么还是没生效」

**场景**：一台物理服务器（RHEL 9，内核 5.14）需要把内核日志持久送到串口，机房已接好串口采集。运维在 `/etc/default/grub` 的 `GRUB_CMDLINE_LINUX` 里加了 `console=ttyS0,115200n8`，重启后 `cat /proc/cmdline` 里没有这个参数。另一位同事说"参数写错地方了"。

**常见误判**：把问题定性在"参数名或变量名写错"，于是反复改 `/etc/default/grub` 并重启。它看起来成立，因为"写了没生效"最直觉的原因就是写错了。

**判据**：改参数这件事有三层，`/etc/default/grub` 只是输入层，中间还有一层"生成"，最后是"被读的是哪一份产物"。判据是逐层核对：`grep -E '^GRUB_CMDLINE' /etc/default/grub` 看输入；`grep -E 'menuentry|linux' /boot/grub/grub.cfg`（Debian 系）或 `grubby --info=ALL`（RHEL 系）看产物里每个启动项是否都带上了新参数；`cat /proc/cmdline` 看内核这次真正收到了什么。**条件会变**：默认走 BLS 的系统（RHEL 8/9，`GRUB_ENABLE_BLSCFG=true`）菜单项在 `/boot/loader/entries/*.conf` 而不在 `grub.cfg` 里；UEFI 机器上实际生效的 `grub.cfg` 在 ESP 里，写到 BIOS 的 `/boot/grub2/grub.cfg` 不起作用。验收标准见体系篇"二、引导加载器搬内核"——`cat /proc/cmdline` 是唯一一处。

**一句话结论**：不要问"参数名对不对"，先问"进入 / 产物 / 被读的那一份"这三层里哪一层没通。

**出处**：`man 8 grub-mkconfig`、`man 8 grubby`、内核 6.x 文档 `Documentation/admin-guide/kernel-parameters.rst`。

## 4. 「这台机器也调了 `vm.swappiness`，怎么重启后又变回 60」

**场景**：一批 20 台机器统一调优，工程师把 `vm.swappiness = 10` 写进了 `/etc/sysctl.d/50-tuning.conf`，执行 `sysctl --system` 后读到 10，认为完成。当晚其中一台因补丁重启，值班在它上面读到的是 60。

**常见误判**：认为"`sysctl --system` 不报错就是配置生效了"。它看起来成立，因为命令确实执行成功、当时的值也确实变了。

**判据**：`sysctl --system` 只是"**现在**把配置文件应用一遍"，它既不保证这次没被覆盖，也不保证下次开机会应用同一份结果。判据是查覆盖链：`ls -l /etc/sysctl.d/` 看有哪些文件与编号、有没有 `99-sysctl.conf` 软链；`grep -rn <参数名> /etc/sysctl.d/ /usr/lib/sysctl.d/ 2>/dev/null` 看同一个键被写在了几个地方。字典序覆盖的完整规则见原理篇"为什么运行时参数有作用顺序这件事"，本判例只用其中一条：**编号小于 `99-sysctl.conf` 的文件会被它盖掉**。**条件会变**：如果配置文件清单里没有冲突、值却依然回退，那要找的是"更晚写入这个键的机制"——云初始化工具、配置管理系统、编排层的 entrypoint 都可能在某次启动或某个时刻重写同一个键，此时要比的是"谁在什么时刻写"，而不是文件编号。

**一句话结论**：`sysctl --system` 成功不等于持久化成立；持久化的验收是**重启之后**的读数，判据是配置文件的编号与来源数量。

**出处**：`man 8 sysctl`、`man 5 sysctl.d`（目录优先级与字典序规则）。

## 5. 「`lsmod` 里没有这个驱动，内核不支持这个硬件」

**场景**：一台新上架的 2U 服务器（Ubuntu 24.04，10/25 GbE 双口网卡，装机时 `lspci` 能看到两块卡），业务侧发现其中一个口不通，`lsmod | grep <驱动名>` 没有任何输出。同事据此判断"内核不支持这款网卡"，准备换机型或换发行版。

**常见误判**：把 `lsmod` 当成内核支持能力的清单。它看起来成立，因为 `lsmod` 确实是查模块最常用的命令。

**判据**：功能有两种存在形态——编进内核（builtin，`lsmod` 看不到）与可加载模块（`.ko`）。区分手段是 `modinfo <模块名>`（能查到路径就是模块）、以及看设备是否真的工作。真正的证据在内核日志里：`journalctl -k -b` 与 `dmesg` 里的 `Direct firmware load for xxx failed`（模块在、缺固件文件）、`Unknown symbol in module`（模块与内核不匹配）、`module verification failed`（Secure Boot 签名被拒）。**条件会变**：如果这些日志一条都没有、设备也确实没被枚举，方向才转到"确实没有对应驱动/固件包"，此时该做的是装固件包或换受支持的硬件，而不是继续找日志。

**一句话结论**：`lsmod` 里没有只能说明"它不是以模块形式加载着"，不能推出"内核不支持"；先看内核日志再下结论。

**出处**：`man 8 lsmod`、`man 8 modinfo`、`man 8 modprobe`；内核 6.x 文档 `Documentation/admin-guide/module-signing.rst`。

## 6. 「机器自己重启了，肯定是有 panic，找 `vmcore` 就行」

**场景**：一台 64 GiB 的数据库从库在 02:14 重启过，业务在 02:16 自动切走又切回。早上值班登录后翻日志，没看到任何崩溃迹象，`/var/crash/` 是空的。有人判断"那就是崩溃了但没产生 vmcore"，也有人判断"可能是掉电"。

**常见误判**：把"重启过"直接等同于"内核崩溃"。它看起来成立，因为 panic 之后确实会重启，而且"莫名重启"最常见的解释就是崩溃。

**判据**：至少要分开四种可能——内核 panic、oops 之后重启、掉电/断电、硬件看门狗或人工操作。操作系统侧的证据是 `journalctl --list-boots`（能回溯几次）、`journalctl -b -1 -k -p warning`（上一轮内核日志）、`ls -lt /var/crash/`（有没有转储）、日志末尾是不是一段正常的关机序列。**硬件侧的证据才是决定性的**：带外管理（IPMI/iDRAC/iLO）的事件日志（SEL）、机箱/电源事件记录、以及"日志是断在某一行还是以关机序列收尾"。**条件会变**：`kernel.panic` 的默认值本身是 0（不自动重启），而发行版通常会改成非零，所以"崩溃后它会不会自己起来"取决于本机取值——现场用 `sysctl kernel.panic` 取，不要凭发行版印象推断。同样地，kdump 只在 **panic** 时触发：oops 默认不触发、OOM 默认不触发，所以"没有 vmcore"完全不能反推"没有崩溃"。

**一句话结论**：重启原因要分四类，操作系统侧只能给出"是/不是内核崩溃"的弱证据，确定性结论要靠硬件侧的事件日志；没有 vmcore 时结论应当写"未确认"。

**出处**：`man 5 proc`（`/proc/sys/kernel/panic`、`panic_on_oops`）、`man 1 journalctl`（`--list-boots`、`-b`）、`man 8 kdumpctl` 与内核 6.x 文档 `Documentation/admin-guide/kdump/`（kdump 的触发条件）。

## 7. 「kdump 配好了、`systemctl status` 是 active，就以为这台机器已经具备崩溃转储能力」

**场景**：一批 30 台新机器（Ubuntu 24.04，256 GiB 内存）统一配了崩溃转储，`kdump` 服务 `active`、转储目录写的是本机根分区。上架半年后其中一台（承载内存型服务，根分区已用到 82%）真崩过一次，`/var/crash/` 里什么都没有。

**常见误判**：把"服务在跑"当成"能力可用"。它看起来成立，因为服务状态是运维最熟悉的判据。

**判据**：kdump 要同时成立四件事——`crashkernel=` 预留成功（`/sys/kernel/kexec_crash_size` 非 0）、kexec 可用（读取该文件为 0 就是"没预留成功或被禁用"，它是这两件事的合并判据；要分开就得先确认参数在不在 `/proc/cmdline` 里）、捕获内核已加载、转储目标在崩溃那一刻**可写且空间够**。判据是逐条查：`cat /proc/cmdline | tr ' ' '\n' | grep crashkernel`、`cat /sys/kernel/kexec_crash_size`、转储目标的空间（本机转储时就是根分区，`df -h /`）、以及用发行版自带的估算工具算预留值是否合理。**条件会变**：转储目标是本机磁盘时，根分区写满会让崩溃抓不下来；生产上更常见的是 NFS/SSH 远端转储。而且这四条失效**平时都不报错**——所以验收方式不是"看状态"，而是**在可快照的实验机上主动触发一次 panic，确认 `vmcore` 真的落盘并能被打开**。

**一句话结论**：没演练过的 kdump 等于没配；"服务 active"只说明进程在跑，也不说明崩溃时真的能拿到 `vmcore`。

**出处**：`man 8 kdumpctl`、`man 5 kdump.conf`、`man 1 kexec`、`man 8 makedumpfile`；内核 6.x 文档 `Documentation/admin-guide/kdump/`。

## 8. 「卡住了就有 root shell，直接 `rd.break` 进就行」

**场景**：一台生产机（RHEL 9，带内 SSH 不通）重启后停在 `You are in emergency mode`，要求输入 root 密码；带外控制台能看到画面。值班手里没有密码（在密码管理器里，需要审批），在群里问"是不是可以加 `rd.break` 绕过"。有人回复"可以，反正是同一回事"。

**常见误判**：把四种救援入口当成同一件事的不同叫法。它看起来成立，因为它们都能"不登录系统就拿到 shell"。

**判据**：区别在**控制权停在哪一段、以及要不要过认证**。`systemd.unit=emergency.target` 与 `systemd.unit=rescue.target` 下 PID 1 是 systemd，会由 `emergency.service`/`rescue.service` 执行 `systemd-sulogin-shell`（其中调用 `sulogin`）先验 root 密码，root 被锁定时会直接拒绝并打印 `Cannot open access to console, the root account is locked.`；`rd.break` 停在 initramfs 里、`init=/bin/bash` 直接起 shell，这两条都**不过认证**。判据是看当前提示符与文件系统状态：`(initramfs)`/`dracut:/#` 说明还在第 ③ 段（真根挂在 `/sysroot`、只读）；`emergency mode` 说明根已挂上、systemd 在跑。**条件会变**：`man 8 sulogin` 写明了例外——root 账号被 `!` 或 `*` 锁定时，`sulogin --force` 会不问密码直接给 root shell，所以"现代发行版一定不给 root shell"也不成立，取决于该服务启动时带不带 `--force`。

**一句话结论**：先分清失败表现再选手段；而"绕过认证的路径存在"这件事本身就是安全事实——在物理接触与带外控制台面前，本地认证不构成防护。

**出处**：`man 8 sulogin`（`--force` 的条件与提醒）、`man 8 systemd-sulogin-shell`、`man 5 systemd.unit` 与 `man 7 systemd.special`（`emergency.target`/`rescue.target` 的依赖与 `AllowIsolate`）。

## 9. 「改完 `/boot/grub/grub.cfg` 再 `update-grub` 一下，让它认我的改动」

**场景**：需要给一台实验机（Ubuntu 24.04，`/boot` 是独立分区）的内核加一个参数。工程师嫌改 `/etc/default/grub` 麻烦，直接编辑了 `/boot/grub/grub.cfg` 里那一行 `linux`，重启确认生效后，为了"让改动固化"，又执行了一次 `update-grub`。再次重启后参数消失。

**常见误判**：以为 `update-grub` 是"把当前状态固化"。它看起来成立，因为这个名字听起来像"更新并保存"。

**判据**：`grub.cfg` 是**生成物**，输入是 `/etc/default/grub` 与 `/etc/grub.d/*`；`update-grub` 的行为是"读取输入、重新生成产物"，所以它会**覆盖**手工改动。判据是看改动落在哪一层：`grep -E '^GRUB_CMDLINE' /etc/default/grub`（输入层）与 `grep -E 'menuentry|linux' /boot/grub/grub.cfg`（产物层）里有没有这个参数。**条件会变**：临时改一次启动（菜单里按 `e` 编辑后 `Ctrl-X`）完全不经过这两个文件，它只影响这一次启动，不需要也不应该固化；RHEL 8/9 走 BLS 时输入层还包括 `/boot/loader/entries/*.conf`，用 `grubby` 直接改条目比改 `/etc/default/grub` 更贴近实际生效位置。

**一句话结论**：改生成物等于在下次生成时被重新生成的内容覆盖；所有这类改动都要落在输入层（`/etc/default/grub` 或 BLS 条目），改完再生成、再核对。

**出处**：`man 8 grub-mkconfig`、`man 5 grub.d`、`man 8 grubby`；GNU GRUB Manual 的 "Simple configuration" 一章。

## 10. 「95 秒才开机，把 `DefaultTimeoutStartSec` 调小就好了」

**场景**：一台机器每次开机多花约 90 秒，`systemd-analyze blame` 显示一个不相关的小服务耗时最长。有人建议把 `DefaultTimeoutStartSec` 从 90 s 调到 10 s，还有人建议优化 `blame` 里的第一名。

**常见误判**：把超时当症状的成因。它看起来成立，因为屏幕上确实在等一个 90 秒的超时，而调小之后开机数字确实变小了。

**判据**：那 90 秒是 systemd 的默认单元启动超时（`man 5 systemd-system.conf`：`DefaultTimeoutStartSec`/`DefaultTimeoutStopSec` 在系统与用户管理器里默认都是 90 s），它说明某个依赖永远不会出现。要回答"在等谁"，看 `systemctl list-jobs`（还有哪些 job 卡着）与 `systemctl --failed`（是不是已经有一个失败的挂载单元），再看 `fstab` 里那一行写的来源。**要回答"为什么慢"，看 `systemd-analyze critical-chain` 而不是 `blame`**——`blame` 排的是单元**自身**耗时、不含等待依赖的时间，所以第一名常常是个无辜的小服务。**条件会变**：如果本机改过超时值，屏幕上的数字会不同（不一定正好 90 s），要现场取；如果等的是 `systemd-udev-settle` 这类硬件枚举，方向在驱动与存储，不在配置。

**一句话结论**：90 秒是"某个依赖永远不来"的信号，不是可调的参数问题；先找出它在等谁，再决定修哪一层。把超时调小只是把症状藏起来。

**出处**：`man 5 systemd-system.conf`（默认超时 90 s）、`man 1 systemd-analyze`（`blame` 与 `critical-chain` 的口径差异）、`man 5 systemd.mount`（`nofail`、`x-systemd.device-timeout=` 的语义）。

## 11. 「这块盘是整盘克隆过来的，`root=` 还指得对，能直接起」

**场景**：一台虚拟机（Ubuntu 22.04 on LVM，系统盘 60 GiB）从 A 虚拟化平台整盘复制到 B 平台，作为新机器启动。`/etc/fstab` 用的是 UUID，`root=UUID=` 也没改，工程师认为"UUID 是复制过来的、肯定还是对的"，直接开机。开机停在 initramfs shell，报 `Warning: /dev/disk/by-uuid/<uuid> does not exist`。

**常见误判**：把"整盘克隆"等同于"标识也被克隆"。它看起来成立，因为整盘拷贝确实连分区表与文件系统一起拷了过去。

**判据**：分三种情况，处置方向不同，判据是"目标设备在不在当前能看到的设备列表里"。在 initramfs shell 里读两组数：`cat /proc/cmdline`（它在找什么）与 `ls /dev/disk/by-uuid/`、`lsblk`（现在有什么）。**目标设备在列表里、标识也对，但挂载仍失败** → 方向在文件系统类型或 initramfs 缺少对应模块；**目标设备在列表里但标识不同** → 参数旧了，更新 `root=` 后必须复查 `/proc/cmdline`；**目标设备完全不在** → 新平台的存储控制器驱动不在 initramfs 里（克隆场景常见于 host-only 模式的镜像），要补驱动并用通用镜像重建。**条件会变**：虚拟化平台换了之后，磁盘在客户机里的设备名（`/dev/sda` 与 `/dev/vda`）与控制器型号都会变，所以"拷贝成功"与"能启动"是两个独立的问题。

**一句话结论**：克隆保留的是数据，不保证"谁来认这块盘"的那一层也跟着成立；启动失败先分清是标识变了还是驱动缺了。

**出处**：`man 7 bootup`（内核与 initramfs 的交接）、`man 8 lsblk`、`man 8 blkid`、`man 8 initramfs-tools`（Debian 系）与 `man 8 dracut`（RHEL 系的通用镜像模式）。

## 12. 「日志都持久化了，`journalctl -b -1` 一定能看到上次重启的原因」

**场景**：一台机器上 `/var/log/journal` 存在、`journalctl --list-boots` 能列出十几次启动，工程师据此认为取证能力完备。某次它在 40 分钟内连续重启两次，事后他用 `-b -1` 去看第一轮发生了什么，读到的只有重启前最后几秒的内容，之前的过程不见了。

**常见误判**：把"持久化已开启"当成"每一轮的现场都留住了"。它看起来成立，因为持久化本身确实是取证的前提。

**判据**：journal 不是完整的记录，它有两道限制。第一道是**限流**：`journald.conf` 的 `RateLimitIntervalSec=`/`RateLimitBurst=` 默认是"每 30 秒 10000 条、按服务分别计算"（systemd 255 的 `man 5 journald.conf`），超出后该服务在这个区间内的后续消息**被直接丢弃**，并生成一条"丢弃了多少条"的汇总消息——启动瞬间日志量激增时最容易触发它。第二道是**容量与保留**：`journalctl --disk-usage` 的占用、`Storage=`/`SystemMaxUse=`/`MaxRetentionSec=` 共同决定能回溯多久，短时间内的连续重启会让更早的内容因 journald 清理旧归档而消失。判据是 `journalctl --list-boots` 的条数与各次的时间范围、`journalctl --disk-usage`，以及在日志里搜那条限流汇总（`journalctl -b -1 | grep -i suppress`，实际文本随版本变化，先确认本机输出的字样）。另外内核环缓冲（`dmesg` 的数据源）本身就在内存里、有容量上限，崩溃前最后几行可能已经被新日志覆盖。**条件会变**：如果关心的是"崩溃瞬间"的内容，靠 journal 本来就不够——那属于 kdump（`vmcore`）与 pstore 的范围；journal 能回答的是"崩溃之前的系统与内核日志"。另外，本机不一定有 `/etc/systemd/journald.conf` 文件（金标准机器上就没有，全部取编译默认值），判断保留策略要先确认配置文件是否存在，不存在时按 `man 5 journald.conf` 的默认值读。

**一句话结论**：持久化只保证"已经写进磁盘的那部分能跨重启"，不保证容量够、不保证崩溃瞬间的内容还在。

**出处**：`man 1 journalctl`（`--list-boots`、`--disk-usage`、`--vacuum-*`）、`man 5 journald.conf`（`Storage=`、容量与保留期）、`man 8 makedumpfile`（`vmcore` 的过滤与体积）。

## 第一反应不要做什么

这张清单里的每一条，都可以压缩成一句"第一反应不要做"：

- 不要因为停在 `grub rescue>` 就重装引导器或系统——先 `ls` 探明分区编号与 `/boot` 内容。
- 不要在持久配置里写 `/dev/sdX`，也不要在变更后只核对一处标识。
- 不要问"参数名写对了吗"，先问"输入层、产物层、被读的那一份"通了没有。
- 不要把 `sysctl --system` 成功当持久化成功；持久化的验收是重启后的读数。
- 不要用 `lsmod` 反推"内核不支持"，证据在内核日志里。
- 不要把"重启过"直接写成"内核崩溃"；没有 vmcore 与硬件侧记录时写"未确认"。
- 不要把"服务 active"当"能力可用"，kdump 这类机制必须演练过一次。
- 不要在没看清当前停在哪一段（initramfs 还是 systemd）之前就选救援手段。
- 不要直接编辑生成物；改动要落在输入层，然后重新生成。
- 不要把超时调小来"解决"开机慢；先找出它在等谁。
- 不要假设"克隆过来的机器标识也对"；先确认设备认不认得出来。
- 不要在排查现场之前执行 `journalctl --vacuum-*` 或清理 `/var/crash/`——那是自己删证据。

## 要点自测

**问：判断"`grub rescue>` 是找错地方还是文件坏了"，用哪两条命令？**

答：`ls` 看分区编号是否与装系统时一致；`ls (hdX,gptY)/` 看该分区里有没有内核文件与 GRUB 模块目录。目录找不到是"找错了地方"，目录在而配置读不成是"配置坏了"。

**第一反应不要做什么**：不要在现场直接改 `grub.cfg`——它是生成物，进系统后重新生成才是正解。

**问：怎么判断一次"莫名重启"是不是内核崩溃？**

答：操作系统侧只能给出弱证据——`journalctl --list-boots`（还有没有历史）、`journalctl -b -1 -k`（上一轮内核日志）、`ls -lt /var/crash/`（有没有转储）、日志末尾是不是正常关机序列。决定性证据在硬件侧：带外管理的事件日志与电源/机箱事件。没有 vmcore 且日志未持久化时，结论只能写"未确认"。

**第一反应不要做什么**：不要在深夜的重启事件里急着宣布"是内核崩溃"——一旦写进复盘记录，后续所有排查都会被这个错误前提带偏。

**问：为什么"加了 `nofail`"不等于"这块盘的问题解决了"？**

答：`man 5 systemd.mount` 说得很明确：带 `nofail` 的挂载只被 `local-fs.target` **wanted**、不被 required，而且不再排在它之前——也就是开机既不要求它成功、也不等它完成。所以它保证的是"机器能起来"，不是"这块盘能用"。设备真的丢了照样挂不上，业务侧照样缺数据；这是降级策略，不是修复。

**第一反应不要做什么**：不要因为加了 `nofail` 就把这个挂载点从监控里去掉。它更需要监控——因为失败不再表现为"开不了机"，而是表现为"业务悄悄少了数据"。
