## 1. 实验 0：只读观测（零风险，先做这个）

```bash
systemd-analyze time                  # 验证：firmware / loader / kernel / userspace 各段耗时
systemd-analyze blame | head -20      # 验证：单元自身的启动耗时排行（不含等待依赖的时间）
systemd-analyze critical-chain        # 验证：关键路径上是谁拖住了开机
systemd-analyze plot > /tmp/boot.svg  # 验证：可视化时间线，可直接在浏览器打开
cat /proc/cmdline                     # 验证：本次启动实际使用的内核命令行
journalctl -b -k | head -50           # 验证：本次启动的内核日志长什么样
lsblk -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINTS,UUID,PARTUUID   # 验证：根分区与它现在的 UUID
lsinitrd | head -30                   # 验证：initramfs 里装了什么（RHEL 系；Debian 系用 lsinitramfs）
```

**预期**：`systemd-analyze time` 的四段加起来接近总耗时；`blame` 里的高耗时单元与 `critical-chain` 里 `@` 后面的时间要对得上，对不上的部分通常是「并行等待」——这正是只看 `blame` 会误判的原因。

**环境**：任意 systemd 发行版；建议连做三次取稳定值，避免首次启动的缓存干扰。

**风险**：无，全部只读。

**耗时**：约 15 分钟。

**回滚**：无需回滚。把输出存成一份基线文件——后面几个实验都拿它做对照。

**要沉淀什么**：这份输出就是 T1 要求的「本机启动基线卡」，包含发行版与内核版本、`/proc/cmdline`、根设备、initramfs 类型。

## 3. 总自测

题目前带 **【进阶】** 的，对应笔记里的进阶小节；答不上来不影响阶段 2 过关。其余题目要求能**盖住答案脱稿讲 3~5 分钟**。

> [!question]- 从按下电源到出现登录提示符，中间发生了什么？云主机上最常出问题的是哪一环？
> - **五环链条**：固件（BIOS/UEFI）→ GRUB2 → 内核 + `initramfs` → `systemd`（PID 1）→ `default.target`。
> - **每环的产出**：固件交出控制权；GRUB 载入 `vmlinuz` 与 initramfs 并传递命令行；内核与 initramfs 挂上真根并 `switch_root`；systemd 按 unit 与 `fstab` 拉起服务；最后给出登录入口。
> - **云主机最常出问题的位置**：第 3、4 环——根设备 UUID/设备名变化、initramfs 缺存储驱动、`fstab` 写错、网络就绪把启动拖住；真正的固件故障相对罕见。
> - **落点**：判断故障先问「现在是谁在输出」——固件的事 `journalctl` 看不到，systemd 的事不会出现在 dracut shell 里。
> - **第一反应不要是什么**：不要一上来就重启，`journalctl -b -1` 与带外串口日志是重启一次就没了的证据。

> [!question]- `initramfs` 是干什么的？为什么换了存储控制器或做了根分区迁移后系统可能起不来？
> - 它解决「挂根需要驱动，而驱动在根里」的死锁：把存储、文件系统、LVM/RAID/LUKS、网络根所需的模块打进一个内存中的临时根，先跑它去挂真根，再 `switch_root`。
> - 换控制器/迁移根分区后起不来，是因为**新的根设备依赖新的驱动或新的标识**（驱动不在 initramfs 里，或 `root=UUID=` 还是旧值），这两件事都不会自动跟着变。
> - 处置：在 dracut shell 里对比 `cat /proc/cmdline` 与 `ls /dev/disk/by-uuid/`，进系统后重建 initramfs（迁移场景用 `--no-hostonly`）或更新 `root=`。
> - **第一反应不要是什么**：不要只改 `fstab`——根设备的定位发生在 initramfs 阶段，改 `fstab` 影响不到它。

> [!question]- 一台机器卡在 GRUB，另一台卡在 `emergency.target`，处理顺序分别是什么？
> - **卡在 GRUB**：先分辨 `grub>` 还是 `grub rescue>`；后者用 `ls`/`set root`/`set prefix`/`insmod normal`/`normal` 找回菜单，或用 `linux` + `initrd` + `boot` 手工引导；进系统后重生成配置、必要时重装引导器、检查 `/boot` 与 ESP 空间。
> - **卡在 `emergency.target`**：`systemctl --failed` 与 `journalctl -xb` 找失败单元（多为 `fstab`），先 `mount -o remount,rw /`，改完 `mount -a` 验证，再 `systemctl default` 继续启动。
> - **共性**：目标都是「先让系统起来并保住数据」，根因分析放到恢复之后。
> - **第一反应不要是什么**：不要在 GRUB 阶段就重装引导器，也不要在紧急模式里盲目重启。

> [!question]- `journalctl -b -1` 在什么场景下是救命命令？
> - 机器刚刚异常重启或 panic，第二次启动一切正常，现场只剩「上一次启动」——这是唯一能回答「上一次到底发生了什么」的命令（配合 `-k` 看内核、`-p warning` 降噪）。
> - 前提是 **journal 持久化**：`/var/log/journal` 存在且 `Storage=` 允许持久，否则 `--list-boots` 里只有一条。
> - 相关限制：内核环缓冲会被覆盖，日志也可能被限流丢弃，所以关键机器要先把持久化与保留策略配好。
> - **第一反应不要是什么**：不要在排查现场前执行 `journalctl --vacuum-*`，那等于自己删证据。

> [!question]- `sysctl -w` 改过的参数重启后会怎样？想持久化该写到哪里？`/etc/sysctl.conf` 与 `/etc/sysctl.d/` 谁先谁后？
> - `sysctl -w` 只写当前内核，**重启即失效**，也不留审计痕迹；生产上只用于临时验证或应急。
> - 持久化写到 `/etc/sysctl.d/*.conf`，文件名建议排在 `99` 之后，然后 `sysctl --system` 应用，用 `sysctl <key>` 复查。
> - 加载规则：目录优先级 `/etc/sysctl.d/` > `/run/sysctl.d/` > `/usr/local/lib/sysctl.d/` > `/usr/lib/sysctl.d/`；所有文件统一按文件名字典序执行，**名字靠后的覆盖靠前的**。
> - `/etc/sysctl.conf` 在 systemd v198 之后不再被直接读取，通常靠软链 `/etc/sysctl.d/99-sysctl.conf` 生效，于是它排在最后、优先级最高。
> - **第一反应不要是什么**：不要以为「写了 `50-xxx.conf` 就一定生效」，先用 `ls -l /etc/sysctl.d/99-sysctl.conf` 看清本机布局。

> [!question]- 内核升级后新内核起不来，你会怎么做？（其中 `kexec` 与 Livepatch 属进阶）
> - **回滚**：重启时在 GRUB 菜单选旧内核，或 `grubby --set-default <旧内核>` 后重启；回滚前先 `journalctl -b -1 > /root/failed-boot.log` 保住现场。
> - **前提**：升级前确认旧内核启动项还在（RHEL 由 `installonly_limit` 控制，Debian 要确认旧 `linux-image-*` 没被 `autoremove` 清掉）。
> - **`kexec`**：跳过固件与 GRUB 快速换内核，省 POST 时间；但它不是冷重启，硬件状态未复位，不能用来排除硬件问题。
> - **Livepatch**：厂商覆盖的函数级 CVE 热补丁，用来推迟重启窗口；不能替代版本升级，不覆盖驱动/模块。
> - **第一反应不要是什么**：不要把「装上就重启」当流程——DKMS 模块没编好、`/boot` 写满、`fstab` 有问题，这三件事会让重启变成一台起不来的机器。

> [!question]-【进阶】内核 panic 之后，你怎么拿到「现场」？
> - **配置阶段**：`crashkernel=` 预留内存 + kdump 服务加载捕获内核；转储目标在 `/etc/kdump.conf`（RHEL 系）。
> - **取证阶段**：`/var/crash/<时间戳>/` 里的 `vmcore` 与 `vmcore-dmesg.txt`；云主机或无 kexec 环境则靠带外串口日志。
> - **分析阶段**：`crash <vmlinux> <vmcore>`，先 `bt` 看崩溃路径，再 `log`、`ps`、`vm`；需要与内核版本匹配的 debuginfo。
> - **验证阶段**：在实验机上用 `echo c > /proc/sysrq-trigger` 主动 panic 演练一次，确认能抓到、能分析、磁盘空间够用。
> - **第一反应不要是什么**：不要在没有 kdump 的机器上指望「重启后还能看到原因」——重启之后现场只剩一句「机器重启过」。

> [!question]- 忘记 root 密码怎么恢复？为什么说这在生产上属于安全事件？
> - **恢复路径**：能用 GRUB 时走 `rd.break`（RHEL）或 recovery / `init=/bin/bash`（Debian），把 `/sysroot` 或 `/` 重新挂成可写、`chroot` 后 `passwd`，最后按需 `touch /.autorelabel`。
> - **为什么是安全事件**：这条路径不需要任何凭据，**谁能碰到控制台谁就能拿到 root**；所以「有人进过控制台并改过本地认证文件」必须按入侵处置的口径查证。
> - **真正的防护**：磁盘加密（LUKS）+ 固件/GRUB 密码 + 带外管理独立鉴权与审计 + 变更留痕，而不是「把恢复路径堵死」（堵不住）。
> - **第一反应不要是什么**：不要在排障机上重装系统——数据、审计线索和根因会一起丢掉。
