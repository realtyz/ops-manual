# 内核参数与模块的两套机制

## 1. 同一个词，两条完全不同的通路

"改内核参数"这句话在 Linux 上指两件毫不相干的事。它们的名字经常长得像，甚至指同一个概念——`pid_max`（命令行参数）与 `kernel.pid_max`（运行时参数）说的是同一个上限——但改法、生效时机、持久化位置、验收方式全都不同。

| 维度 | 启动参数（内核命令行） | 运行时参数（`sysctl`） |
| --- | --- | --- |
| 值放在哪 | 引导加载器的配置里（`/etc/default/grub`、BLS 条目），启动时传给内核 | `/proc/sys/**` 下的一批可读写文件 |
| 谁写进去 | 引导加载器在交接前传给内核 | 用户态程序（`systemd-sysctl`、`sysctl`、任何进程）直接写 |
| 什么时候生效 | **只在启动那一瞬间**；启动后无法追加 | 写入即生效 |
| 怎么持久化 | 改引导配置后重新生成，重启才生效 | 写进 `/etc/sysctl.d/*.conf`，开机由 `systemd-sysctl` 应用 |
| 唯一验收标准 | `cat /proc/cmdline` | `sysctl <参数名>` 或 `cat /proc/sys/...` |
| 典型例子 | `ro`、`quiet`、`console=`、`crashkernel=`、`systemd.unit=`、`rd.break` | `net.ipv4.ip_forward`、`vm.swappiness`、`kernel.pid_max` |

区分的方法不靠记忆，靠**问题归位**：如果这个值必须在内核初始化之前就知道（根文件系统的挂载方式、initramfs 的行为、控制台往哪输出、为崩溃转储预留多少内存），它只能是启动参数；如果是内核跑起来之后才可能被调整的策略（转发开关、回收倾向、连接数上限），它是运行时参数。

## 2. 为什么启动参数不能"事后补"

启动参数在时间轴上的位置**早于内核的大部分子系统初始化**。内核命令行是在解压之后马上解析的，那时还没有 `/proc`、没有模块加载、没有驱动探测；很多参数的效果正是"改变这些子系统怎么初始化"。事后补一个参数在原理上就说不通：

- `root=` 决定去哪里找根文件系统——根挂上之后再改它没有意义；
- `crashkernel=` 决定**预留**一块内存给捕获内核——内存已经被业务用掉了，这时说"预留 256 MiB"做不到；
- `systemd.unit=` 决定 PID 1 走到哪个 target——那时 PID 1 已经跑完了；
- `console=` 决定早期日志往哪输出——早期已经过去了。

所以在启动参数上"改了却不生效"，几乎总是四种原因之一：改了输入但没重新生成产物（改 `/etc/default/grub` 没跑 `update-grub`）；产物路径不是实际被读的那一份（UEFI 机器上改了 BIOS 的 `/boot/grub2/grub.cfg`，或在默认走 BLS 的系统上只改 `grub.cfg`）；参数被写到了另一个变量上（`GRUB_CMDLINE_LINUX` 作用于所有菜单项，`GRUB_CMDLINE_LINUX_DEFAULT` 只作用于默认项）；以及**根本没重启**。

## 3. 为什么运行时参数有"作用顺序"这件事

`sysctl` 的配置散落在多个目录的多个文件里，还可能有同名文件互相覆盖，所以内核需要一个明确的合并规则。这里有个容易被误传的点，值得按文档说清。

`systemd-sysctl` 读取的目录按优先级从高到低是 `/etc/sysctl.d/`、`/run/sysctl.d/`、`/usr/local/lib/sysctl.d/`、`/usr/lib/sysctl.d/`。执行规则是**所有 `.conf` 文件统一按文件名字典序应用，名字靠后的覆盖靠前的**；同名文件则以高优先级目录里的那一份为准。发行版的默认值放在 `/usr/lib/sysctl.d/`，因此你在 `/etc/sysctl.d/` 放一个同名文件就能盖掉它。

关键在那条软链：systemd 从 v198 起不再直接读 `/etc/sysctl.conf`，而多数发行版提供 `/etc/sysctl.d/99-sysctl.conf -> ../sysctl.conf` 来兼容老习惯。于是它以 `99-` 开头，天然排在最后、优先级最高——**只写 `50-xxx.conf` 会被它盖掉**。这是"我明明写了配置却不生效"最常见的成因。

金标准机器上的实际布局印证了这条规则，也说明"编号普遍很小"是正常的：`/etc/sysctl.d/` 下是 `10-bufferbloat.conf`、`10-console-messages.conf`、`10-ipv6-privacy.conf`、`10-kernel-hardening.conf`、`10-magic-sysrq.conf`、`10-map-count.conf`、`10-network-security.conf`、`10-ptrace.conf`、`10-zeropage.conf` 与软链 `99-sysctl.conf -> ../sysctl.conf`；`/usr/lib/sysctl.d/` 下是 `10-apparmor.conf`、`50-pid-max.conf`、`99-protect-links.conf`。**读法**：先看编号定顺序，再看同名文件落在哪个目录定胜者（`/etc/` 优先于 `/usr/lib/`），然后才看值。

顺带一个实用推论：**参数在两台机器上不一致时，先比"哪个文件设的"，而不是比"值是多少"**。取 `sysctl --system` 的输出、加上配置文件的名称与编号，才是可复现的口径。

## 4. 参数的可见性取决于模块是否已加载

`/proc/sys` 下的参数不是一张固定清单，它随**已加载的模块**变化。`systemd-sysctl` 在启动早期就跑完了，而某些 `net.*` 参数要等网卡驱动加载后才存在——这时写进去会失败，而且失败方式很容易被忽略（`sysctl --system` 会打印失败项，但只在这次输出里）。

这解释了"参数不存在"的两种完全不同的原因：

| 现象 | 原因 | 处置方向 |
| --- | --- | --- |
| `sysctl <名字>` 报 `cannot stat`／找不到文件 | 名字写错（层级用点号，不是路径） | 对照 `/proc/sys` 的实际目录结构改名 |
| 同一个参数在 A 机器上存在、B 机器上不存在 | B 机器上对应的模块没加载（可能是 builtin、也可能根本没装） | 先确认模块状态，再谈参数 |

**先加载模块、再写参数**的顺序是有机制的，不是习惯问题：`systemd-sysctl` 与 `systemd-modules-load` 是两个不同的服务，要让参数在开机时能被写进去，就得让模块先就位。金标准机器上可以看到这两个服务的分工痕迹——`sysctl` 与 `kmod-static-nodes` 都在 `sysinit.target` 的依赖里，而模块静态加载由 `/etc/modules-load.d/*.conf` 与 `/usr/lib/modules-load.d/*.conf` 提供配置。

## 5. 模块的两种存在形态，以及为什么 `lsmod` 会骗人

内核功能有两种形态，`lsmod` 只能看到其中一种：

| 形态 | 表现 | 怎么确认 |
| --- | --- | --- |
| **builtin**（编进内核镜像） | 内核的一部分，开机就在 | `lsmod` 里**看不到**；查内核配置，或直接看设备是否工作 |
| **模块**（`.ko` 文件） | 放在 `/lib/modules/$(uname -r)/` 下，按需加载 | `lsmod` 里有；`modinfo` 能查到路径 |

所以"`lsmod` 里没有这个驱动"**不能**推出"内核不支持这个硬件"。这是排障里最贵的一句话：它会让人去换机器、换发行版、装别的驱动，而真正的证据（固件加载失败、符号不匹配、签名被拒）就在内核日志里躺着。

## 6. 模块加载要经过四道关

一个模块从"文件在盘上"到"设备能用"，中间有四道可能失败的关卡，每一道失败的现象与证据都不同：

| 关卡 | 谁在做 | 失败的现象 | 证据在哪 |
| --- | --- | --- | --- |
| 依赖与别名解析 | `modprobe`、`depmod` 生成的依赖表 | `modprobe` 找不到模块，或没加载依赖就跑 | `modprobe --show-depends`、`depmod -a` 重建依赖表 |
| 参数与策略 | `/etc/modprobe.d/*.conf` 的 `options`、`blacklist`、`install` 指令 | 参数被静默忽略；`blacklist` 挡住了主动加载、但没挡住被别人依赖而被动加载 | `modinfo -p <模块>`、`/etc/modprobe.d/` 的实际内容 |
| 内核接受它 | 版本匹配、符号解析、Lockdown/Secure Boot 的签名校验 | `Unknown symbol in module`、`module verification failed`、`Key was rejected by service` | `journalctl -k -b`、`dmesg` |
| 设备真的起来 | 模块需要设备固件（firmware）才能初始化 | `Direct firmware load for xxx failed` | `journalctl -k -b`；固件文件在 `/lib/firmware` 下 |

四道关的顺序是固定的：**先解析依赖，再套用策略，再由内核校验与插入，最后才是设备初始化**。所以"`modprobe` 报错但内核日志里什么都没有"通常意味着失败发生在第一或第二道关（参数、别名、依赖表），此时去看内核日志当然看不到东西。

## 7. Lockdown 与 Secure Boot：一条贯穿启动链的约束

固件阶段的一个开关会一路影响到内核阶段：**Secure Boot 开启时，固件只肯执行有可信签名的引导器**；这条约束会通过 **Lockdown**（一种把内核切到受限模式的安全特性）向内延伸，限制内核接受未签名代码——包括未签名的模块、以及某些直接操作内存的接口。

这解释了启动链上三个看起来不相关的现象其实是同一件事：

1. 发行版的 `grubx64.efi` 通常不是固件内置密钥签的，所以中间要有一个由微软 UEFI CA 签约的 `shimx64.efi`：固件放行 shim，shim 再验证发行版签名的 `grubx64.efi`。
2. 自编译或 DKMS 编出来的模块（某些第三方存储驱动、GPU 驱动）会因为没有可信签名而被拒，需要走 **MOK**（Machine Owner Key，机器所有者密钥）流程把公钥注册进信任库。
3. `kexec`（kdump 依赖它）在 Lockdown 下受限，因此必须使用发行版提供的**已签名**捕获内核。

要理解这条约束的一个实践后果：**MOK 注册、自签名模块、直接换自编译内核，都不是"远程一条命令"能做完的事**。MOK 注册要在重启后由人在固件界面（MokManager）里按键确认——只发了导入命令就重启的机器会停在那里等输入，现象与"机器起不来"一模一样。这也是为什么"这台机器开没开 Secure Boot"应当在接手时就记进基线，而不是等变更当天才发现（阶段 1 讲基线卡的做法）。

## 8. 抽象在哪里漏水

**参数的"默认值"不是一个常数。** 它取决于内核版本、发行版补丁、以及"哪个配置文件先跑"。所以默认值要现场取（`sysctl <名字>`、`/proc/cmdline`），并且把发行版与内核版本一起记下来；凭记忆或凭别的机器上的值设定，是变更事故的常见起点。

**"生效"和"持久"是两件事。** 运行时参数写入即生效但重启即失；配置文件保证下次开机写入什么，但**删掉配置文件不会把当前内核里的值改回去**。回滚必须显式做一次 `sysctl -w <参数>=<原值>`，或重启。这一条与启动参数正好相反：启动参数改错了不重启反而没事，运行时参数改错了当场就生效。

**模块禁用有软硬之分。** `blacklist` 只是让自动加载不主动选它，被其他模块依赖时照样会被拉起来；要真正挡住，还得配一条 `install <模块> /bin/false`。把"加了黑名单"当成"禁用了"，会在某次重启后以"它怎么又回来了"的形式暴露。

**同名的东西不一定同类。** 判断一个"参数"是哪一类，看它的载体：`/proc/cmdline` 里的是启动参数，`sysctl` 与 `/proc/sys/**` 是运行时参数，`/etc/modprobe.d/` 里的是模块参数（只在模块加载时被读取一次），cgroup 下的文件是内核接口文件（直接读写、按 cgroup 生效）。四类的生效时机互不相同。

## 常见误解

| 说法 | 事实 |
| --- | --- |
| "内核参数都一样，改哪个文件都行" | 启动参数与运行时参数是两套机制，载体、时机、验收全不同 |
| "`sysctl -w` 之后再加个配置文件就持久了" | 配置文件只决定下次开机写入什么；本次的值要靠 `-w` 或重启 |
| "删掉配置文件，参数就回默认值了" | 当前内核里的值不会自己变回去；要显式改回或重启 |
| "`50-xxx.conf` 一定生效" | 所有文件按文件名字典序应用，`99-sysctl.conf`（通常是 `/etc/sysctl.conf` 的软链）会盖掉编号更小的 |
| "参数存在与否是内核固定的" | 参数随已加载模块变化；`systemd-sysctl` 跑得比某些网卡驱动更早，这类参数在开机写入时会失败 |
| "`lsmod` 是内核支持能力的清单" | 它只列可加载模块；编进内核的功能看不到 |
| "`blacklist` 就等于禁用模块" | 它只挡主动加载；被依赖时仍会加载，硬禁用要配 `install <模块> /bin/false` |
| "`modprobe` 报错就去内核日志找原因" | 若失败在参数/别名/依赖表这一层，内核日志里什么都没有 |
| "Secure Boot 只是固件阶段的事" | 它通过 Lockdown 延伸到内核：未签名模块被拒、kexec 受限、需要 MOK 流程 |

## 要点自测

**问：怎么判断一个"内核参数"属于启动参数还是运行时参数？**

答：看它的值必须什么时候被知道。如果它改变的是内核初始化本身的行为（找根、预留内存、指定 target、把日志送到串口），只能是启动参数，改完必须重启，验收看 `/proc/cmdline`；如果是内核跑起来之后的策略（转发、回收、上限），它是运行时参数，写入即生效，验收看 `sysctl <名字>`。

**第一反应不要做什么**：不要因为"改了文件却没生效"就反复重改同一个文件。先问它属于哪一套，再用那套的验收标准去查——启动参数看 `/proc/cmdline`，运行时参数看 `sysctl`。

**问：为什么 `sysctl --system` 有时会打印失败项？**

答：因为一部分参数要等对应模块加载后才存在，而 `systemd-sysctl` 在启动早期就执行完了。这时候的失败是"时机问题"而不是"名字写错"——区分方法是看该参数现在是否存在（`sysctl <名字>`），若现在存在，那开机时就是时序问题，需要让模块提前加载。

**第一反应不要做什么**：不要把这类失败当成"配置文件写错了"去反复校对语法。

**问：`blacklist` 与 `install <模块> /bin/false` 分别挡什么？**

答：`blacklist` 只让 `modprobe` 与 udev 的自动加载不主动选它，被别的模块依赖时仍会被加载；`install <模块> /bin/false` 用一条自定义命令替代真正的加载动作，能把这条路彻底堵死。要"禁用"，两条都要有。

**第一反应不要做什么**：不要在加了 `blacklist` 之后就用 `lsmod` 验证"确实没加载"——它可能正在被依赖而加载着。

**问：内核日志里 `Unknown symbol in module`、`module verification failed`、`Direct firmware load for xxx failed` 分别指向什么？**

答：`Unknown symbol` 说明模块与当前内核不匹配（常见于手工编译的老驱动），要用匹配当前内核的版本重编（DKMS）或回滚内核；`module verification failed`（或 `Key was rejected by service`）说明签名没通过，走发行版签名模块或按流程注册 MOK，**不要直接关 Secure Boot**；`Direct firmware load ... failed` 说明模块在、但设备需要的固件文件缺失，要装对应的固件包并确认路径与版本。

**第一反应不要做什么**：不要反复 `modprobe` 同一个模块。不看日志就重试，只是在重复同一个失败。
