# Linux 运维学习大纲（生产级）

> **定位**：一条面向运维/SRE 面试的学习路径——不是把命令再过一遍，而是把「生产中真正会遇到的问题」和「面试官真正会追问的点」对齐。
> **前置基础**：会日常 Shell 操作、懂文件权限的基本概念、用过 `top`/`ps`/`systemctl`、能读写简单的 bash 脚本。
>
> 原则：每个模块都按 **概念 → 生产实践 → 要点自测** 三层推进。每一条 checklist 的标准不是「知道这个命令」，而是「能讲清它的语义、边界，以及出问题时怎么用它定位」。

## 学习路径总览（Roadmap）

| 阶段  | 主题              | 建议周期  | 产出目标                                    |

| 3   | 内存管理与 OOM       | 1 周   | 讲清可用内存、Page Cache、OOM 判定与 swap 取舍       |
| 4   | 存储、文件系统与 IO     | 1 周   | 讲清 inode / 挂载 / LVM / RAID，处理磁盘满与 IO 瓶颈 |
| 5   | 网络协议栈与排障 ★      | 1~2 周 | 画出 TCP 状态机，用 `ss`/`tcpdump` 定位丢包与连接堆积   |
| 6   | 权限、账号与安全加固      | 1 周   | 讲清权限模型与提权面，能按基线加固一台生产机                  |
| 7   | systemd、服务与定时任务 | 3~5 天 | 能排查服务起不来，正确写 unit 与 timer               |
| 8   | 日志、监控与可观测性      | 1 周   | 建立日志轮转与指标采集，告警能落到具体动作                   |
| 9   | 性能分析与故障排查 ★     | 1~2 周 | 用一套方法论把 CPU / 内存 / IO / 网络问题定位到根因       |
| 10  | 生产运维、变更与高可用     | 1 周   | 内核升级、备份、批量运维都有流程与回滚路径                   |

> 标 ★ 的 **阶段 5（网络）** 与 **阶段 9（性能排障）** 是运维面试区分度最高的两块：命令谁都会敲，能从现象推到根因的人不多，优先打透。

> **不在本大纲范围内的部分**：GPU 驱动与内核模块、PCIe/NUMA 拓扑、RDMA/RoCE 无损网络、perftest 基线与 XID 硬件故障处理属于 AI 基础设施主题域，见 [[AI-Infra/00_简介|AI-Infra 大纲]]。本大纲只在阶段 5 与阶段 9 保留通用主机侧的调优与观测入口，重复的概念不在这里展开。

## 这套大纲怎么用（面试导向）

**面试官真正在考什么**

不是「你记得多少命令」，而是**从现象到根因的推理链**。任何一道运维题，都用同一个骨架作答：

> 现象与影响面 → 分层定位（哪一层）→ 用什么命令取证据 → 结论与根因 → 止损动作 → 长期改进

**三条练习纪律**

- 每个知识点都要能回答三问：**是什么、边界在哪、生产上怎么用**。
- 每个现象都要准备一份「**第一反应不要是什么**」。会讲「不要随手 `kill -9`、不要在生产机上不限流抓包、不要用 `setenforce 0` 掩盖问题」，比多背十个命令更能体现经验。
- 所有结论尽量带**量化**：负载除以核数、`si/so` 是否长期非 0、`await` 与业务延迟的对应关系。只说「感觉慢」在面试里等于没答。

**与 Kubernetes 笔记的关系**

本套笔记是 [[Kubernetes/00_简介|Kubernetes 大纲]] 的前置。阶段 2（cgroup/namespace）、阶段 5（网络）会直接复用到 [[03_调度_资源_QoS]] 与 [[04_网络]]，排障方法论也是同一套；两套笔记建议交叉复习。

## 阶段 0：实验环境与操作纪律

> **对应笔记**：[[00_实验环境与操作纪律]]

- [ ] 准备一台能随时快照/重建的实验机，发行版与目标岗位对齐（RHEL 系 / Ubuntu LTS / Debian）
- [ ] 固化版本基线并写在笔记首页：发行版版本、内核版本（`uname -r`）、systemd 版本、cgroup 版本（v1/v2）
- [ ] 诊断工具箱装齐：`sysstat`（`sar`/`iostat`）、`iotop`、`htop`、`lsof`、`strace`、`tcpdump`、`perf`、`bpftrace`/bcc、`iftop`、`numactl`
- [ ] 会用 `man`：`man 1` 命令、`man 5` 配置文件格式、`man 2/3` 系统调用，比搜索引擎快也准
- [ ] 养成变更前三件事：备份原文件（带时间戳）、确认回滚方式、确认可以在哪个窗口做
- [ ] 建立取证纪律：现象发生时先用 `top`/`vmstat`/`iostat`/`ss` 取一组同时刻快照，**重启会毁掉现场**
- [ ] 在实验机上主动做破坏性演练：打满根分区、`kill -9` 掉 PID 1、`down` 掉网卡、写坏 `/etc/fstab`，观察现象与恢复方式
- [ ] 按目标岗位补齐发行版差异：包管理、防火墙（firewalld/ufw/nftables）、网络配置（NetworkManager/netplan）、访问控制（SELinux/AppArmor）

**生产实践**

- 实验机和生产机严格分开；生产上的任何手工改动都要有回滚命令，而不是「不行再改回来」
- 把诊断命令整理成「现象 → 工具」速查表，而不是按字母背命令
- 发行版差异要先于命令记忆：RHEL 与 Debian 系在排障入口上差别很大，面试时答错方向很扣分

**要点自测**

- 给你一台陌生的机器，5 分钟内你怎么判断它「有没有问题」？（负载、内存水位、磁盘空间与延迟、连接数，看趋势而非瞬时值）
- 为什么说「重启能解决 90% 的问题，但会毁掉 100% 的现场」？
- `man 1/2/5` 分别看什么？举三个你会先查 `man 5` 的配置文件。

## 阶段 1：启动流程、内核与系统初始化

> **对应笔记**：[[01_启动流程与内核]]

### 1.1 启动链与救援

- [ ] 完整启动链：固件（BIOS/UEFI）→ GRUB2 → 内核 + `initramfs` → `systemd`（PID 1）→ `default.target`，并知道每一环失败时的典型现象
- [ ] GRUB 交互与应急：编辑启动项进 `rescue.target` / `emergency.target`、`init=/bin/bash`、只读根重新挂载
- [ ] 忘记 root 密码的恢复路径（`rd.break` 等），以及为什么这在生产上属于安全事件
- [ ] `initramfs` 的职责（加载根文件系统所需的存储/文件系统驱动）与重建（`dracut -f` / `update-initramfs -u`）
- [ ] 内核参数的三个入口：临时（GRUB 编辑）、持久（`/etc/default/grub` + `grub2-mkconfig`）、运行时（`sysctl`）
- [ ] 内核模块：`lsmod` / `modprobe` / `modinfo` / blacklist；驱动加载失败怎么看 `dmesg`

### 1.2 启动后排查与内核升级

- [ ] 排查工具：`journalctl -b` / `-b -1`、`systemd-analyze blame` / `critical-chain`、`dmesg -T`
- [ ] 内核升级与回滚：通过包管理升级、保留旧内核启动项、`kexec` 快速重启、Livepatch/热补丁的能力边界
- [ ] 内核崩溃取证：`kdump` + `kexec` 抓 `vmcore`，用 `crash` 做初步分析
- [ ] 启动耗时与依赖：哪些服务在拖慢开机、`After`/`Wants` 写错会怎样（详见 [[07_systemd与服务管理]]）

**生产实践**

- 生产机永远保留至少一个可用的旧内核启动项；内核升级要排维护窗口，并在重启后验证关键服务与业务指标
- 关键服务器开 `kdump` 并预留 `crashkernel` 内存，否则 panic 之后只剩一句「机器重启了」，没有现场
- 改 `/etc/fstab` 后先 `mount -a` 验证再重启——这是「重启起不来」的头号原因
- 确认带外管理可用（IPMI/iDRAC/云控制台）：根分区损坏、网络配置写错时，这是唯一的救援通道

**要点自测**

- 从按下电源到出现登录提示符，中间发生了什么？云主机上最常出问题的是哪一环？
- `initramfs` 是干什么的？为什么换了存储控制器或做了根分区迁移后系统可能起不来？
- 一台机器卡在 GRUB 或卡在 `emergency.target`，你的处理顺序分别是什么？
- `journalctl -b -1` 在什么场景下是救命命令？

## 阶段 2：进程、信号与资源隔离

> **对应笔记**：[[02_进程与信号]]

- [ ] 进程与线程：`ps -eLf`、`/proc/<pid>/task`、`fork`/`exec`/`clone` 的语义差异
- [ ] 进程状态：`R/S/D/T/Z/I` 的含义，**D 状态为什么 `kill -9` 也杀不掉**，僵尸进程由谁回收
- [ ] 工具分工：`ps`、`top`（含 `top -H` 看线程）、`pidstat`、`pstree`，以及直接读 `/proc/<pid>/{status,wchan,stack,io}`
- [ ] 信号语义：`SIGTERM` vs `SIGKILL`、`SIGHUP` 与配置重载、`SIGUSR1/2`，以及 `kill -9` 的代价（文件锁、临时文件、数据不一致）
- [ ] 优先级与调度：`nice`/`renice`、`chrt` 与实时调度、`taskset` 做 CPU 亲和
- [ ] 资源限制：`ulimit`（`nofile`/`nproc`/`stack`）、`/etc/security/limits.conf` 与 systemd `LimitNOFILE` 的关系——**改 `limits.conf` 对 systemd 服务无效**
- [ ] 资源耗尽：`kernel.pid_max`、`kernel.threads-max`、fork 风暴现象、`fs.file-max` 与句柄上限
- [ ] 孤儿与僵尸：容器里 PID 1 为什么必须处理信号并回收子进程
- [ ] namespace 与 cgroup：隔离「看到什么」vs 限制「用多少」，以及它们如何构成容器（衔接 [[03_调度_资源_QoS]]）

**生产实践**

- 排查卡死服务先看状态：D 状态查 IO / 网络挂载，Z 状态查父进程，R 状态但不推进查锁与 CPU
- 重启服务优先 `systemctl restart`（先 `SIGTERM`，超时后才 `SIGKILL`），而不是直接 `kill -9`
- 用 `nohup`/`&` 起的进程必须补日志、存活检查与自启，否则它随时会「悄悄消失」
- 被锁住的进程要先确认数据一致性风险，再谈杀不杀——数据库、消息队列尤其如此

**要点自测**

- 机器进程数到上限会发生什么？怎么快速定位是谁在创建进程？
- D 状态的进程为什么杀不掉？接下来你会查什么？
- 僵尸进程的成因与解法？为什么「杀父进程」有时能解决？
- namespace 和 cgroup 分别解决什么问题？容器的「隔离」到底是哪一层做的？

## 阶段 3：内存管理与 OOM

> **对应笔记**：[[03_内存管理与OOM]]

- [ ] 虚拟内存基础：映射与页表、缺页异常、大页（HugePages）与透明大页（THP）
- [ ] `free` 的正确读法：`free` 与 `available` 的区别、buff/cache 的可回收部分、**「剩余内存很少」在 Linux 上通常是正常的**
- [ ] Page Cache：读缓存与写缓冲、脏页回写（`vm.dirty_ratio` / `vm.dirty_background_ratio`）、`drop_caches` 只该用于测量而非日常运维
- [ ] Swap：`vm.swappiness` 的语义、换页对延迟的影响、什么时候必须开或必须关（数据库、K8s 节点）
- [ ] 内存超额与 OOM：`vm.overcommit_memory` 三种模式、OOM Killer 的评分（`/proc/<pid>/oom_score`、`oom_score_adj`）、cgroup v2 级的 OOM（`memory.oom.group`）与用户态 OOM 处理（如 `systemd-oomd`）
- [ ] 泄漏 vs 增长：RSS/VSZ/PSS 的差别（`/proc/<pid>/smaps_rollup`、`pmap`），如何确认「真的在泄漏」
- [ ] NUMA：`numactl --hardware`、跨 NUMA 访问的代价、绑核与绑内存
- [ ] 内存压力信号：`/proc/pressure/memory`（PSI）、`vmstat` 的 `si/so`、major/minor page fault
- [ ] OOM 后取证：`dmesg` / `journalctl -k` 里的 OOM 记录，被选中进程、当时的 cgroup 水位与整机状态

**生产实践**

- 服务必须有内存上限（cgroup），否则单个进程能拖垮整机；`oom_score_adj` 要谨慎使用，别把 OOM 引到 SSH、systemd 这类关键进程上
- 内存告警看 `available` 与 PSI，不看 `free`；`si/so` 长期非 0 说明已经在换页，延迟必然抖动
- 数据库/缓存类服务按厂商建议配置 swappiness 与大页；容器节点按平台规范处理 swap
- 排查「内存缓慢增长」要按天/周取样，区分内存泄漏、缓存增长与业务自然增长，别用一个瞬时快照下结论

**要点自测**

- `free` 显示可用内存很少，要紧吗？怎么判断内存真的不够？
- OOM Killer 是怎么选中某个进程的？为什么容器里被杀掉的常常不是最占内存的那个？
- VSZ 很大但 RSS 很小，说明什么？排查时该看 PSS 吗？
- 什么时候必须关闭 swap？关掉之后风险是什么？

## 阶段 4：存储、文件系统与 IO

> **对应笔记**：[[04_存储与文件系统]]

### 4.1 设备、文件系统与挂载

- [ ] 块设备与分区：`lsblk`、`blkid`、`parted`/`fdisk`、GPT vs MBR、用 UUID 挂载
- [ ] ext4 与 XFS 的差别：inode 数量、在线扩容能力、**XFS 只能扩不能缩**、ext4 为 root 保留的 5% 空间
- [ ] 挂载参数与语义：`noatime`、`errors=`、`_netdev`，以及 `df` 的容量从哪来
- [ ] `/etc/fstab` 的字段、`systemd` 挂载单元与 `x-systemd.*` 选项、写错后如何进 rescue 修复
- [ ] inode 与「明明有空间却写不进去」：`df -h` vs `df -i`、小文件场景
- [ ] `df` 与 `du` 不一致的四类原因：已删除但被进程持有（`lsof +L1`）、被挂载覆盖的目录、保留块、稀疏/延迟分配

### 4.2 LVM、RAID 与 IO 性能

- [ ] LVM：PV/VG/LV 概念、在线扩容链路（`vgextend` → `lvextend` → `resize2fs`/`xfs_growfs`）、快照的用途与代价
- [ ] RAID 取舍：RAID0/1/5/6/10 的容量、性能与重建风险；硬件 RAID 与 `mdadm` 的差异
- [ ] IO 栈：机械盘 vs SSD/NVMe、多队列与 IO 调度器（`none`/`mq-deadline`/`kyber`）、`fio` 建立性能基线
- [ ] IO 观测：`iostat -x` 的 `await`/`aqu-sz`/`%util`、`iotop`、`pidstat -d`、`blktrace` 定位到具体进程与文件
- [ ] 句柄与事件：`lsof` 按进程/端口/目录统计、`fs.file-max`、`inotify` 上限（大量文件监控的服务经常踩到）
- [ ] 网络存储：NFS 的 `hard`/`soft`、`_netdev`，以及挂载点卡死导致 D 状态堆积时的处置

**生产实践**

- 挂载一律用 UUID 或 LVM 标签，不用 `/dev/sdX`；变更 `fstab` 后先 `mount -a` 验证
- 系统盘、数据盘、日志分区分开，避免日志写满根分区造成整机故障
- 扩容优先走 LVM 在线扩容；ext4 缩容必须卸载且风险高，生产上一般不缩
- 上线前用 `fio` 跑一次基线，之后判断「磁盘变慢」才有参照物
- 看 IO 要同时看 `%util`、`await`、队列深度与业务延迟——NVMe 上 `%util` 经常 100% 却毫无瓶颈

**要点自测**

- `df` 显示还有空间、`du` 也找不到大文件，却写不进去，可能是哪几种原因？
- ext4 与 XFS 在扩缩容上的差别？为什么生产上常见 XFS + LVM 的组合？
- 磁盘 IO 慢怎么查？为什么不能只看 `%util`？
- RAID5 在大容量盘上的风险是什么？重建期间系统会经历什么？

## 阶段 5：网络协议栈与排障 ★（核心区）

> **对应笔记**：[[05_网络协议栈与排障]]

### 5.1 协议与连接状态

- [ ] TCP 三次握手/四次挥手，半连接与全连接队列、`SYN` 队列溢出（`nstat` / `netstat -s`）的现象
- [ ] 状态机在排障中的用法：`LISTEN`/`SYN_SENT`/`ESTABLISHED`/`TIME_WAIT`/`CLOSE_WAIT`/`FIN_WAIT2` 分别说明什么
- [ ] **`TIME_WAIT` 与 `CLOSE_WAIT` 的区别**：前者是主动关闭方的正常状态（2MSL），后者是应用没关连接，**只能改应用，不能靠调内核参数**
- [ ] 关键内核参数讲清语义与副作用：`somaxconn`、`tcp_max_syn_backlog`、`tcp_tw_reuse`、`tcp_fin_timeout`、`tcp_syncookies`、`ip_local_port_range`
- [ ] UDP 无重传带来的「丢包无感知」，以及在 DNS、监控、QUIC 场景下的表现

### 5.2 地址、路由与转发

- [ ] `ip` 命令族：`ip addr/route/neigh/link`、`ip route get`、策略路由
- [ ] 转发与 NAT：`net.ipv4.ip_forward`、nftables/iptables 的 `filter`/`nat` 表、**连接跟踪表满导致丢包**（`conntrack`）
- [ ] 链路层：bond/team 模式、VLAN、网桥、MTU 与分片，以及 MTU 不一致的典型现象
- [ ] DNS 排障：`/etc/resolv.conf`、`/etc/nsswitch.conf`、`systemd-resolved`，以及 `getent hosts` 与 `dig` 结果不一致的含义

### 5.3 抓包与分层定位

- [ ] `ss -s` / `ss -tanp` / `ss -lntp`，以及相对 `netstat` 的替代关系
- [ ] `tcpdump` 基本功：`-i any -nn`、按 host/port/flag 过滤、落盘后用 Wireshark 分析、抓包本身的性能开销
- [ ] 工具链：`ping`/`mtr`/`traceroute`、`nc`/`curl -v`、`iftop`/`nload`
- [ ] 定位顺序（自下而上）：link/driver（`ip -s link`、`ethtool -S`）→ IP 与路由 → 端口与防火墙 → DNS → 应用层
- [ ] 与容器/K8s 的衔接：Pod 网络、Service 转发、NetworkPolicy 的排障入口（见 [[04_网络]]）

### 5.4 延伸：主机侧网络调优（通用）

- [ ] IRQ 亲和与软中断分布：`/proc/interrupts`、多队列网卡、中断绑定工具与 `tuned` profile 的取舍
- [ ] 环形缓冲与队列数：`ethtool -G`（ring buffer）、`ethtool -L`（队列数）、offload 开关 `ethtool -K` 的适用场景
- [ ] 巨帧与 MTU 一致性：`ip link` 设置、`ping -M do` 验证、路径 MTU 发现失效时的现象
- [ ] 网卡固件与驱动版本纳入基线：`ethtool -i` 查驱动与固件版本，升级前记录版本与当前配置
- [ ] 高吞吐场景的通用取舍：缓冲调大换延迟、offload 打开换 CPU，**每一项都要有量化依据**

> RDMA/RoCE 的无损网络配置（PFC/ECN/DCQCN、GID 索引、交换机侧配合）与 perftest 基线属于 AI 基础设施主题域，见 [[AI-Infra/00_简介|AI-Infra 大纲]] 的 [[03_RDMA与RoCE无损网络]] 与 [[04_perftest与性能基线]]。

**生产实践**

- 分层排查是基本功：能 ping 通不代表 TCP 能连（防火墙），TCP 能连不代表应用正常（DNS、证书、后端）
- 生产抓包必须限流限时（`-c` 包数、`-w` 落到独立目录、抓完及时清理），别把机器抓挂

- 云环境下先分清「主机内」还是「云网络/负载均衡/安全组」的问题，看 `nstat` 的重传与丢包统计再下结论

- 用户说「服务连不上」，你的排查顺序是什么？每一步用什么命令、期待看到什么？

- MTU 不一致的典型现象是什么？怎么验证？

## 阶段 7：systemd、服务与定时任务

> **对应笔记**：[[07_systemd与服务管理]]

- [ ] 核心概念：unit 类型（service/target/timer/socket/mount）、依赖（`Wants`/`Requires`/`After`/`Before`）与并行启动
- [ ] unit 的三处位置与优先级（`/etc/systemd/system` > `/run/systemd/system` > `/usr/lib/systemd/system`）、为什么改完必须 `daemon-reload`、用 `systemctl edit` 写 drop-in
- [ ] 服务排障：`systemctl status`、`journalctl -u`、`systemd-analyze`，以及 `Type=` 选错（`simple`/`forking`/`notify`）导致的「假启动失败」
- [ ] 资源与生命周期约束：`LimitNOFILE`、`MemoryMax`/`CPUQuota`、`Restart=`/`RestartSec=`、`KillMode`、`TimeoutStopSec`
- [ ] 沙箱选项：`ProtectSystem`、`PrivateTmp`、`ReadWritePaths` 的用途与踩坑
- [ ] 日志接口：`journalctl` 的 `-u`/`-b`/`--since`/`-p`/`-o json`，journald 持久化（`/var/log/journal`）与 `SystemMaxUse`
- [ ] 定时任务：`cron` 与 `systemd timer` 的取舍、`cron` 的环境变量与 PATH 坑、`/etc/cron.d` 与 `crontab -u`
- [ ] `systemd timer` 的 `OnCalendar`/`Persistent`/`AccuracySec`，以及错过的任务如何补跑
- [ ] 自启与屏蔽：`systemctl enable/disable` 与 `WantedBy` 的关系、`mask` 的用途
- [ ] 时间基线：`chrony`/`timedatectl` 与统一时区——排障时时间不对齐，整条证据链都失效

**生产实践**

- 自研服务一律写成 unit，不靠 `nohup`；重启策略、日志归集、资源上限都交给 systemd 管理
- 定时任务必须**幂等 + 加锁**（`flock`）并监控执行结果；不检查返回值的 `cron` 是隐性故障源
- 变更 unit 后必须 `daemon-reload`；`restart` 之后一定要验证端口、日志与业务指标，而不是看命令没报错就走
- 排障前先确认时间与时区是否正确，跨系统对日志时这一步优先级最高

**要点自测**

- 服务 `systemctl start` 失败，你的排查顺序是什么？
- `limits.conf`、`ulimit`、systemd `LimitNOFILE` 三者的关系与生效范围？
- 脚本在命令行能跑、放进 `cron` 就跑不通，为什么？
- `systemd timer` 比 `cron` 多了哪些能力？什么场景值得切换？

## 阶段 8：日志、监控与可观测性

> **对应笔记**：[[08_日志与监控]]

- [ ] 日志体系：journald 与 rsyslog 的分工、应用日志的落点与格式、集中采集方案（远程 syslog / Filebeat / Promtail / Vector）的取舍
- [ ] 日志轮转：`logrotate` 的 `daily`/`size`/`rotate`/`compress`，`copytruncate` 与「发信号让应用重开文件」的差别
- [ ] 磁盘满的日志侧治理：日志量与保留策略、`du` 找增长源、已删除文件的处理
- [ ] 指标采集：`node_exporter` 的关键指标（CPU/内存/磁盘/网络/文件系统/连接数），以及自建采集的边界
- [ ] `sysstat` 的历史价值：`sar -u/-r/-b/-n DEV`、`sa1`/`sa2` 与数据保留期，用它做「事后复盘」

**生产实践**

- 每台机器都要有可回溯的历史指标（`sar` 至少留两周），否则「昨天下午开始变慢」只能靠猜

- 排障时把变更时间线（发布、配置、内核、网络）与指标拐点对齐，多数问题能靠这一步缩小到很小的范围

## 阶段 9：性能分析与故障排查 ★（核心区）

> **对应笔记**：[[09_性能分析与排障]]

### 9.1 方法论与 CPU

- [ ] 方法论先行：先量化影响面与时间点，再按资源分层（CPU / 内存 / IO / 网络 / 锁）逐一排除，最后给根因与改进
- [ ] 负载与 CPU：`uptime` 的 load **包含 D 状态进程**、`vmstat` 的 `r/b/si/so/cs/us/sy/wa`、`mpstat -P ALL`、`pidstat`
- [ ] CPU 高的五种分支：`us`（应用计算）、`sy`（系统调用/锁/切换）、`si`（软中断/网络）、`st`（虚拟化被偷）、`wa`（IO 等待）
- [ ] 上下文切换与中断：自愿 vs 非自愿切换、`/proc/interrupts`、多队列网卡与软中断分布、RSS/RPS 的基本概念

### 9.2 内存、IO 与网络

- [ ] 内存分析：`free`/`vmstat`/PSI、RSS/VSZ/PSS、`pmap`，以及泄漏的确认方法
- [ ] IO 分析：`iostat -x` 各列的含义与组合解读、`iotop`、`fio` 基线对比、`blktrace` 下钻到进程与文件
- [ ] 网络分析：`ss -s`、`nstat` 的重传与错误计数、`sar -n`、`tcpdump` 定位丢包在哪一跳
- [ ] 进程级深挖：`strace -p -f -T`、`/proc/<pid>/{stack,wchan,io}`、`perf top` / `perf record -g` + 火焰图
- [ ] eBPF 工具：`bpftrace` 一行脚本、bcc 的 `execsnoop`/`biolatency`/`tcpconnect`，以及对内核版本的要求
- [ ] 加速器与高速网卡的观测入口：`nvidia-smi dmon`、`rdma link`/`ibv_devinfo`、`ethtool -S` 的 pause 与错误计数（下钻方法见 [[AI-Infra/00_简介|AI-Infra 大纲]]）

### 9.3 高频杀手场景

- [ ] 内存回收导致的抖动（direct reclaim）、THP 引起的偶发卡顿
- [ ] 锁竞争：应用锁、数据库锁，表现为 CPU 不高但吞吐上不去
- [ ] DNS 解析慢、日志同步落盘阻塞、备份任务抢占 IO
- [ ] 连接数/句柄/端口打满，表现为「偶发失败」而非「持续失败」
- [ ] GPU 场景：XID 错误、掉卡、训练通信静默降速（见 [[07_XID与硬件故障处理]]、[[06_NCCL排障]]）
- [ ] 排障纪律：先取证再动手，用 `script`/`tee` 记录命令与输出，时间统一时区

**生产实践**

- 先建性能基线（业务高峰的正常水位），有基线才能说「变慢了」
- 排障动作按「影响面最小、代价最低」排序；故障中不做高风险变更（重启、改内核参数）
- 排障报告固定六段：时间线、影响面、证据、根因、止损动作、长期改进（含监控与告警的补齐）
- 用故障演练检验排障路径：人为制造 CPU 打满、内存泄漏、IO 打满、网络丢包，练习 10 分钟内定位

**要点自测**

- 负载飙高但 CPU 空闲，可能是什么原因？怎么一步步验证？
- `wa` 高、`%util` 高、`await` 高分别代表什么？为什么它们可能互不对应？
- 内存看起来还有空余，进程却一直在换页，怎么解释？
- 机器 IO 慢，你怎么把范围从「某块盘」缩小到「某个进程的某个文件」？
- 请把一次真实的排障讲给面试官听：现象 → 分层 → 证据 → 根因 → 改进。

- 《Linux 性能优化实战》（倪朋飞）：排障与性能分析部分最贴合运维面试
- 《Systems Performance》（Brendan Gregg）与其 USE 方法、FlameGraph 项目
- LWN.net（内核机制与新特性）、kernel.org 的 Documentation/
- 《UNIX/Linux 系统管理手册》（Nemeth 等）：体系化的系统管理视角
- 演练环境：本地 KVM/VM 或按量云主机、Killercoda 场景；破坏性实验只在实验机做
- 各发行版的 release notes：讨论版本差异时的依据，避免凭记忆答题
