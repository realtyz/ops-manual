# Linux 运维学习大纲（生产级）

> **定位**：一条面向运维/SRE 面试的学习路径——不是把命令再过一遍，而是把「生产中真正会遇到的问题」和「面试官真正会追问的点」对齐。
> **前置基础**：会日常 Shell 操作、懂文件权限的基本概念、用过 `top`/`ps`/`systemctl`、能读写简单的 bash 脚本。
>
> 原则：每个模块都按 **概念 → 生产实践 → 要点自测** 三层推进。每一条 checklist 的标准不是「知道这个命令」，而是「能讲清它的语义、边界，以及出问题时怎么用它定位」。

---

## 学习路径总览（Roadmap）

| 阶段  | 主题              | 建议周期  | 产出目标                                    |
| --- | --------------- | ----- | --------------------------------------- |
| 1   | 实验环境与操作纪律       | 2~3 天 | 有可快照的实验机，形成「先取证再动手」的习惯                  |
| 2   | 启动流程、内核与系统初始化   | 3~5 天 | 讲清从加电到登录的全链路，能救回一台起不来的机器                |
| 3   | 进程、信号与资源隔离      | 1 周   | 能定位进程卡死、杀不掉、进程数打满；讲清 namespace/cgroup   |
| 4   | 内存管理与 OOM       | 1 周   | 讲清可用内存、Page Cache、OOM 判定与 swap 取舍       |
| 5   | 存储、文件系统与 IO     | 1 周   | 讲清 inode / 挂载 / LVM / RAID，处理磁盘满与 IO 瓶颈 |
| 6   | 网络协议栈与排障 ★      | 1~2 周 | 画出 TCP 状态机，用 `ss`/`tcpdump` 定位丢包与连接堆积   |
| 7   | 权限、账号与安全加固      | 1 周   | 讲清权限模型与提权面，能按基线加固一台生产机                  |
| 8   | systemd、服务与定时任务 | 3~5 天 | 能排查服务起不来，正确写 unit 与 timer               |
| 9   | 日志、监控与可观测性      | 1 周   | 建立日志轮转与指标采集，告警能落到具体动作                   |
| 10  | 性能分析与故障排查 ★     | 1~2 周 | 用一套方法论把 CPU / 内存 / IO / 网络问题定位到根因       |
| 11  | 生产运维、变更与高可用     | 1 周   | 内核升级、备份、批量运维都有流程与回滚路径                   |
| 12  | 复习与自测           | 持续    | 高频题 + 场景题能脱稿讲 3~5 分钟                    |

> 标 ★ 的 **阶段 6（网络）** 与 **阶段 10（性能排障）** 是运维面试区分度最高的两块：命令谁都会敲，能从现象推到根因的人不多，优先打透。

> **不在本大纲范围内的部分**：GPU 驱动与内核模块、PCIe/NUMA 拓扑、RDMA/RoCE 无损网络、perftest 基线与 XID 硬件故障处理属于 AI 基础设施主题域，见 [[AI-Infra/00_简介|AI-Infra 大纲]]。本大纲只在阶段 6 与阶段 10 保留通用主机侧的调优与观测入口，重复的概念不在这里展开。
>
> 容器运行时（Docker/containerd、镜像与联合文件系统存储驱动）与编排层（Kubernetes 对象、控制器、CNI/CSI）属于容器主题域，见 [[Kubernetes/00_简介|Kubernetes 大纲]]。本大纲只保留容器赖以成立的三个宿主侧机制（namespace / cgroup / 联合文件系统），以及「站在宿主机上看容器」的排障入口。

## 这套大纲怎么用（面试导向）

**面试官真正在考什么**

不是「你记得多少命令」，而是**从现象到根因的推理链**。任何一道运维题，都用同一个骨架作答：

> 现象与影响面 → 分层定位（哪一层）→ 用什么命令取证据 → 结论与根因 → 止损动作 → 长期改进

**三条练习纪律**

- 每个知识点都要能回答三问：**是什么、边界在哪、生产上怎么用**。
- 每个现象都要准备一份「**第一反应不要是什么**」。会讲「不要随手 `kill -9`、不要在生产机上不限流抓包、不要用 `setenforce 0` 掩盖问题」，比多背十个命令更能体现经验。
- 所有结论尽量带**量化**：负载除以核数、`si/so` 是否长期非 0、`await` 与业务延迟的对应关系。只说「感觉慢」在面试里等于没答。

**与 Kubernetes 笔记的关系**

本套笔记是 [[Kubernetes/00_简介|Kubernetes 大纲]] 的前置。阶段 3（cgroup/namespace）、阶段 6（网络）会直接复用到 [[Kubernetes/03_调度_资源_QoS]] 与 [[Kubernetes/04_网络]]，排障方法论也是同一套；两套笔记建议交叉复习。

## 阶段 1：实验环境与操作纪律

> **对应笔记**：[[01_实验环境与操作纪律]]
>
> 该笔记按难度分了两层：标 **【进阶】** 的条目（动态链接库排障）第一遍只需知道有这条路，等真遇到「命令跑不起来」再回来查；其余条目属于本阶段必须掌握的核心。

- [ ] 准备一台能随时快照/重建的实验机，发行版与目标岗位对齐（RHEL 系 / Ubuntu LTS / Debian）
- [ ] 固化版本基线并写在笔记首页：发行版版本、内核版本（`uname -r`）、systemd 版本、cgroup 版本（v1/v2）
- [ ] 主流发行版对比：血统与派生关系（Fedora → RHEL → Rocky/Alma、Debian → Ubuntu）、发布节奏与支持周期（LTS/EOL）、包管理与默认栈的差异，以及**内核版本号不能跨发行版直接比较**（RHEL 的 backport 策略）
- [ ] 诊断工具箱装齐：`sysstat`（`sar`/`iostat`）、`iotop`、`htop`、`lsof`、`strace`、`tcpdump`、`perf`、`bpftrace`/bcc、`iftop`、`numactl`、`smartmontools`（`smartctl`）、`iperf3`、`stress-ng`、`openssl`、`nc`
- [ ] 动态链接库排障：`ldd`、`LD_LIBRARY_PATH`、`ldconfig` 与 `/etc/ld.so.conf`，`error while loading shared libraries` 的标准处理顺序（确认缺哪个库 → 装包或补搜索路径 → `ldconfig` 刷新缓存）
- [ ] 会用 `man`：`man 1` 命令、`man 2` 系统调用、`man 3` 库函数、`man 5` 配置文件格式，比搜索引擎快也准
- [ ] 养成变更前三件事：备份原文件（带时间戳）、确认回滚方式、确认可以在哪个窗口做
- [ ] 建立取证纪律：现象发生时先用 `top`/`vmstat`/`iostat`/`ss` 取一组同时刻快照，**重启会毁掉现场**
- [ ] 在实验机上主动做破坏性演练：打满根分区、写坏 `/etc/fstab`、`down` 掉网卡、改坏 `/etc/passwd`，以及用 `echo c > /proc/sysrq-trigger`（配合 `kernel.sysrq=1`）触发内核 panic，观察现象与恢复方式
- [ ] 记住一个反直觉点：**主机上的 PID 1 永远忽略 `SIGKILL`/`SIGSTOP`**，`kill -9 1` 是静默失败；能被杀掉的只有容器里那个「子命名空间的 init」（从宿主机才能杀）
- [ ] 按目标岗位补齐发行版差异：包管理（`dnf`/`apt` 的源配置、依赖冲突处理、本地包安装、源码编译安装的大致流程）、防火墙（firewalld/ufw/nftables）、网络配置（NetworkManager/netplan）、访问控制（SELinux/AppArmor）

**生产实践**

- 实验机和生产机严格分开；生产上的任何手工改动都要有回滚命令，而不是「不行再改回来」
- 把诊断命令整理成「现象 → 工具」速查表，而不是按字母背命令
- 发行版差异要先于命令记忆：RHEL 与 Debian 系在排障入口上差别很大，面试时答错方向很扣分
- 破坏性演练只在实验机做：`sysrq` 的危险位（触发 panic 与强制重启）在生产机上是关掉的，动手前先确认自己在哪台机器的控制台上

**要点自测**

- 给你一台陌生的机器，5 分钟内你怎么判断它「有没有问题」？（负载、内存水位、磁盘空间与延迟、连接数，看趋势而非瞬时值）
- 为什么说「重启能解决 90% 的问题，但会毁掉 100% 的现场」？
- `man 1/2/3/5` 分别看什么？举三个你会先查 `man 5` 的配置文件。

## 阶段 2：启动流程、内核与系统初始化

> **对应笔记**：[[02_启动流程与内核]]
>
> 该笔记按难度分了两层：标 **【进阶】** 的条目第一遍只需知道有这条路，等真正用到（或到阶段 11）再补；其余条目属于本阶段必须掌握的核心。

### 2.1 启动链与救援

- [ ] 完整启动链：固件（BIOS/UEFI）→ GRUB2 → 内核 + `initramfs` → `systemd`（PID 1）→ `default.target`，并知道每一环失败时的典型现象
- [ ] GRUB 交互与应急：编辑启动项进 `rescue.target` / `emergency.target`、`init=/bin/bash`、只读根重新挂载
- [ ] 忘记 root 密码的恢复路径（`rd.break` 等），以及为什么这在生产上属于安全事件
- [ ] `initramfs` 的职责（加载根文件系统所需的存储/文件系统驱动）与重建（`dracut -f` / `update-initramfs -u`）
- [ ] 内核启动参数：临时（GRUB 编辑）、持久（`/etc/default/grub` + `grub2-mkconfig`）、生效后复查（`/proc/cmdline`）——它只在启动时生效，与运行时内核参数是两套东西
- [ ] 运行时内核参数：`sysctl -w` 临时改、`/etc/sysctl.d/*.conf` + `sysctl --system` 持久化、`sysctl -a` 与 `/proc/sys/` 的对应关系
- [ ] 内核模块：`lsmod` / `modprobe` / `modinfo` / blacklist；驱动加载失败怎么看 `dmesg`

### 2.2 启动后排查与内核升级

- [ ] 排查工具：`journalctl -b` / `-b -1`、`systemd-analyze blame` / `critical-chain`、`dmesg -T`
- [ ] 内核升级与回滚：升级前留好退路、通过包管理升级、保留旧内核启动项、重启后验证与回滚
- [ ] 【进阶】`kexec` 快速重启与 Livepatch/热补丁各自解决什么问题、边界在哪
- [ ] 【进阶】内核崩溃取证：`kdump` + `kexec` 抓 `vmcore`，用 `crash` 做初步分析
- [ ] 启动耗时与依赖：哪些服务在拖慢开机、`After`/`Wants` 写错会怎样（详见 [[08_systemd与服务管理]]）

**生产实践**

- 生产机永远保留至少一个可用的旧内核启动项；内核升级要排维护窗口，并在重启后验证关键服务与业务指标
- 关键服务器开 `kdump` 并预留 `crashkernel` 内存，否则 panic 之后只剩一句「机器重启了」，没有现场
- 改 `/etc/fstab` 后先 `mount -a` 验证再重启——这是「重启起不来」的头号原因
- 确认带外管理可用（IPMI/iDRAC/云控制台）：根分区损坏、网络配置写错时，这是唯一的救援通道

**要点自测**

- 从按下电源到出现登录提示符，中间发生了什么？云主机上最常出问题的是哪一环？
- `initramfs` 是干什么的？为什么换了存储控制器或做了根分区迁移后系统可能起不来？
- 一台机器卡在 GRUB 或卡在 `emergency.target`，你的处理顺序分别是什么？
- `journalctl -b -1` 在什么场景下是救命命令？
- `sysctl -w` 改过的参数重启后会怎样？想持久化该写到哪里，`/etc/sysctl.conf` 与 `/etc/sysctl.d/` 谁先谁后？

## 阶段 3：进程、信号与资源隔离

> **对应笔记**：[[03_进程与信号]]
>
> 该笔记按难度分了两层：标 **【进阶】** 的条目第一遍只需知道有这条路，用到时再回来查；其余条目属于本阶段必须掌握的核心。

- [ ] 进程与线程：`ps -eLf`、`/proc/<pid>/task`、`fork`/`exec`/`clone` 的语义差异
- [ ] 进程状态：`R/S/D/T/Z/I` 的含义，**D 状态为什么 `kill -9` 也杀不掉**，僵尸进程由谁回收
- [ ] 工具分工：`ps`、`top`（含 `top -H` 看线程）、`pidstat`、`pstree`，以及直接读 `/proc/<pid>/{status,wchan,stack,io}`
- [ ] 信号语义：`SIGTERM` vs `SIGKILL`、`SIGHUP` 与配置重载、`SIGUSR1/2`、`SIGSTOP`/`SIGCONT`，以及 `kill -9` 的代价（文件锁、临时文件、数据不一致）
- [ ] 进程退出的三种死法：正常退出码、被信号杀死（退出码 128+N）、被 OOM Killer 选中——`systemctl status` 里的 `signal`/`core-dump` 字段与 `dmesg` 的 OOM 记录分别对应哪一种
- [ ] 用户态崩溃取证：core dump（`ulimit -c`、`/proc/sys/kernel/core_pattern`、systemd-coredump 的 `coredumpctl list`/`info`），以及为什么生产上要限制 core 文件体积
- [ ] 【进阶】优先级与调度：`nice`/`renice`、`chrt` 与实时调度、`taskset` 做 CPU 亲和
- [ ] 资源限制：`ulimit`（`nofile`/`nproc`/`stack`）、`/etc/security/limits.conf` 与 systemd `LimitNOFILE` 的关系——**改 `limits.conf` 对 systemd 服务无效**；`prlimit` 查看与调整运行中进程的限制
- [ ] 资源耗尽：`kernel.pid_max`、`kernel.threads-max`、fork 风暴现象、`fs.file-max` 与句柄上限
- [ ] 孤儿与僵尸：容器里 PID 1 为什么必须处理信号并回收子进程
- [ ] namespace 与 cgroup：隔离「看到什么」vs 限制「用多少」，以及它们如何构成容器（衔接 [[Kubernetes/03_调度_资源_QoS]]）；用 `systemd-cgls`/`systemd-cgtop` 看 cgroup 树与各组的实际占用

**生产实践**

- 排查卡死服务先看状态：D 状态查 IO / 网络挂载，Z 状态查父进程，R 状态但不推进查锁与 CPU
- 重启服务优先 `systemctl restart`（先 `SIGTERM`，超时后才 `SIGKILL`），而不是直接 `kill -9`
- 用 `nohup`/`&` 起的进程必须补日志、存活检查与自启，否则它随时会「悄悄消失」
- 被锁住的进程要先确认数据一致性风险，再谈杀不杀——数据库、消息队列尤其如此
- 服务「自己重启了」先取证再重启：看 `journalctl -u` 的退出码与信号、`coredumpctl` 有没有留下 core；重启本身会把现场一起清掉

**要点自测**

- 机器进程数到上限会发生什么？怎么快速定位是谁在创建进程？
- D 状态的进程为什么杀不掉？接下来你会查什么？
- 僵尸进程的成因与解法？为什么「杀父进程」有时能解决？
- namespace 和 cgroup 分别解决什么问题？容器的「隔离」到底是哪一层做的？
- 进程莫名消失，你怎么区分它是自己退出、被信号杀死，还是被 OOM Killer 选中？
- 容器里 PID 1 是 `bash` 时，为什么 `docker stop` 会超时、最后被强杀？

## 阶段 4：内存管理与 OOM

> **对应笔记**：[[04_内存管理与OOM]]

- [ ] 虚拟内存基础：映射与页表、缺页异常、大页（HugePages）与透明大页（THP）
- [ ] `free` 的正确读法：`free` 与 `available` 的区别、buff/cache 的可回收部分、**「剩余内存很少」在 Linux 上通常是正常的**
- [ ] Page Cache：读缓存与写缓冲、脏页回写（`vm.dirty_ratio` / `vm.dirty_background_ratio`）、`drop_caches` 只该用于测量而非日常运维
- [ ] Swap：`vm.swappiness` 的语义、换页对延迟的影响、什么时候必须开或必须关（数据库、K8s 节点）；swap 分区 vs swapfile（`fallocate` + `mkswap` + `swapon`；注意 `swapon` 拒绝带空洞的文件，Btrfs 上 `fallocate` 出来的文件也不能直接用作 swap，需按发行版文档单独处理）、zram/zswap 的适用场景
- [ ] 内存超额与 OOM：`vm.overcommit_memory` 三种模式、OOM Killer 的评分（`/proc/<pid>/oom_score`、`oom_score_adj`）、cgroup v2 级的 OOM（`memory.oom.group`）与用户态 OOM 处理（如 `systemd-oomd`）
- [ ] 超额与水位的内核侧参数：`vm.overcommit_ratio` 与 `CommitLimit`/`Committed_AS` 的对应关系、`vm.min_free_kbytes` 调大后 direct reclaim 与整体延迟的取舍
- [ ] cgroup v2 的内存控制：`memory.max`/`memory.high`/`memory.swap.max`、`memory.current`/`memory.stat`，以及用 `memory.events` 的 `oom`/`oom_kill` 计数确认某个 cgroup 是否真的被杀过
- [ ] 泄漏 vs 增长：RSS/VSZ/PSS 的差别（`/proc/<pid>/smaps_rollup`、`pmap`），如何确认「真的在泄漏」
- [ ] 「内存去哪了」的三类答案：tmpfs 与 `/dev/shm`（占的是内存不是磁盘，用 `df` 或 `du` 都容易漏掉）、内核 slab 与 dentry/inode cache（`slabtop`、`/proc/meminfo` 的 `Slab`/`SReclaimable`）、被 cgroup 计入的页缓存
- [ ] NUMA：`numactl --hardware`、跨 NUMA 访问的代价、绑核与绑内存
- [ ] 内存压力信号：`/proc/pressure/memory`（PSI）、`vmstat` 的 `si/so`、major/minor page fault
- [ ] OOM 后取证：`dmesg` / `journalctl -k` 里的 OOM 记录，被选中进程、当时的 cgroup 水位与整机状态

**生产实践**

- 服务必须有内存上限（cgroup），否则单个进程能拖垮整机；`oom_score_adj` 要谨慎使用，别把 OOM 引到 SSH、systemd 这类关键进程上
- 内存告警看 `available` 与 PSI，不看 `free`；`si/so` 长期非 0 说明已经在换页，延迟必然抖动
- 数据库/缓存类服务按厂商建议配置 swappiness 与大页；容器节点按平台规范处理 swap
- 排查「内存缓慢增长」要按天/周取样，区分内存泄漏、缓存增长与业务自然增长，别用一个瞬时快照下结论
- 内存「不明去向」先按三类拆开：tmpfs 与共享内存、内核 slab、被 cgroup 计入的页缓存——这三项在 `free` 里都不显眼，要靠 `/proc/meminfo` 与 `memory.stat` 才能对上账

**要点自测**

- `free` 显示可用内存很少，要紧吗？怎么判断内存真的不够？

## 阶段 5：存储、文件系统与 IO

> **对应笔记**：[[05_存储与文件系统]]

### 5.1 设备、文件系统与挂载

- [ ] 块设备与分区：`lsblk`、`blkid`、`parted`/`fdisk`、GPT vs MBR、用 UUID 挂载
- [ ] ext4 与 XFS 的差别：inode 数量、在线扩容能力、**XFS 只能扩不能缩**、ext4 为 root 保留的 5% 空间
- [ ] 挂载参数与语义：`noatime`、`errors=`、`_netdev`，以及 `df` 的容量从哪来
- [ ] `/etc/fstab` 的字段、`systemd` 挂载单元与 `x-systemd.*` 选项、写错后如何进 rescue 修复
- [ ] inode 与「明明有空间却写不进去」：`df -h` vs `df -i`、小文件场景

### 5.2 LVM、RAID 与 IO 性能

- [ ] LVM：PV/VG/LV 概念、在线扩容链路（`vgextend` → `lvextend` → `resize2fs`/`xfs_growfs`）、快照的用途与代价
- [ ] RAID 取舍：RAID0/1/5/6/10 的容量、性能与重建风险；硬件 RAID 与 `mdadm` 的差异
- [ ] IO 栈：机械盘 vs SSD/NVMe、多队列与 IO 调度器（`none`/`mq-deadline`/`kyber`）、`fio` 建立性能基线
- [ ] IO 观测：`iostat -x` 的 `await`/`aqu-sz`/`%util`、`iotop`、`pidstat -d`、`blktrace` 定位到具体进程与文件
- [ ] 句柄与事件：`lsof` 按进程/端口/目录统计、`fs.file-max`、`inotify` 上限（大量文件监控的服务经常踩到）；与阶段 3 的资源限制交叉看，句柄耗尽常常表现为「服务端无日志的偶发失败」
- [ ] 网络存储：NFS 的 `hard`/`soft`、`_netdev`，以及挂载点卡死导致 D 状态堆积时的处置
- [ ] 磁盘健康与磨损：`smartctl -a` 的 `Reallocated_Sector_Ct`/`Current_Pending_Sector`（机械盘与 SATA SSD）与 NVMe 的 `Percentage_Used`/`Available Spare`、`dmesg` 里的介质错误与 IO error，以及坏盘下线与替换流程
- [ ] SSD/NVMe 的维护动作：`fstrim`/`discard` 挂载项与 `fstrim.timer`、`blkdiscard`、`nvme smart-log`，以及为什么 NVMe 上 `%util` 的参考价值有限
- [ ] RAID 与企业存储：`/proc/mdstat` 的重建进度与 `sync_speed` 限速、坏盘替换与热备盘；iSCSI/FC 场景的 `multipath -ll` 与路径故障切换
- [ ] 配额治理：`quota`/`xfs_quota` 的用户、组与项目配额，以及为什么共享目录必须有容量上限

**生产实践**

- 挂载一律用 UUID 或 LVM 标签，不用 `/dev/sdX`；变更 `fstab` 后先 `mount -a` 验证
- 系统盘、数据盘、日志分区分开，避免日志写满根分区造成整机故障
- 扩容优先走 LVM 在线扩容；ext4 缩容必须卸载且风险高，生产上一般不缩
- 上线前用 `fio` 跑一次基线，之后判断「磁盘变慢」才有参照物
- 看 IO 要同时看 `%util`、`await`、队列深度与业务延迟——NVMe 上 `%util` 经常 100% 却毫无瓶颈
- 磁盘健康要主动看：`smartctl -a` 配合 `dmesg` 的介质错误，比等到阵列降级、文件系统变只读要早得多
- SSD 把 `fstrim.timer` 纳入基线；别默认依赖挂载项 `discard`，在线 discard 在部分盘上会带来延迟抖动

## 阶段 6：网络协议栈与排障 ★（核心区）

> **对应笔记**：[[06_网络协议栈与排障]]

### 6.1 协议与连接状态

- [ ] TCP 三次握手/四次挥手，半连接与全连接队列、`SYN` 队列溢出（`nstat` / `netstat -s`）的现象
- [ ] 状态机在排障中的用法：`LISTEN`/`SYN_SENT`/`ESTABLISHED`/`TIME_WAIT`/`CLOSE_WAIT`/`FIN_WAIT2` 分别说明什么
- [ ] **`TIME_WAIT` 与 `CLOSE_WAIT` 的区别**：前者是主动关闭方的正常状态（2MSL），后者是应用没关连接，**只能改应用，不能靠调内核参数**
- [ ] 关键内核参数讲清语义与副作用：`somaxconn`、`tcp_max_syn_backlog`、`tcp_tw_reuse`、`tcp_fin_timeout`、`tcp_syncookies`、`ip_local_port_range`——注意 **`tcp_fin_timeout` 影响的是 `FIN_WAIT2` 的超时，不是 `TIME_WAIT`**（2MSL 由协议决定，没有对应的 sysctl），这是最常见的误解
- [ ] 全连接（accept）队列溢出：`ss -lnt` 的 `Recv-Q` 是当前队列深度、`Send-Q` 就是队列上限，`nstat` 里的 `ListenOverflows`/`ListenDrops` 计数，以及 `tcp_abort_on_overflow` 的取舍（静默丢弃 vs 直接回 RST）
- [ ] 拥塞控制：`cubic` 与 `BBR` 的差别、`net.ipv4.tcp_congestion_control` 与 `tcp_available_congestion_control`，以及用 `ss -ti` 直接读 RTT/重传/窗口（不抓包也能判断链路质量）
- [ ] UDP 无重传带来的「丢包无感知」，以及在 DNS、监控、QUIC 场景下的表现

### 6.2 地址、路由与转发

- [ ] `ip` 命令族：`ip addr/route/neigh/link`、`ip route get`、策略路由
- [ ] 转发与 NAT：`net.ipv4.ip_forward`、nftables/iptables 的 `filter`/`nat` 表、**连接跟踪表满导致丢包**（`conntrack`）
- [ ] 链路层：bond/team 模式、VLAN、网桥、MTU 与分片，以及 MTU 不一致的典型现象
- [ ] DNS 排障：`/etc/resolv.conf`、`/etc/nsswitch.conf`、`systemd-resolved`，以及 `getent hosts` 与 `dig` 结果不一致的含义

### 6.3 抓包与分层定位

- [ ] `ss -s` / `ss -tanp` / `ss -lntp`，以及相对 `netstat` 的替代关系
- [ ] `tcpdump` 基本功：`-i any -nn`、按 host/port/flag 过滤、落盘后用 Wireshark 分析、抓包本身的性能开销
- [ ] 流量控制与故障注入：`tc qdisc`（默认 `fq_codel`）与 `tc netem` 模拟延迟、丢包、抖动，用来复现「偶发变慢」并验证限速策略
- [ ] 工具链：`ping`/`mtr`/`traceroute`、`nc`/`curl -v`、`iperf3`（带宽与延迟基线）、`iftop`/`nload`
- [ ] 定位顺序（自下而上）：link/driver（`ip -s link`、`ethtool -S`）→ IP 与路由 → 端口与防火墙 → DNS → 应用层
- [ ] 与容器/K8s 的衔接：Pod 网络、Service 转发、NetworkPolicy 的排障入口（见 [[Kubernetes/04_网络]]）

### 6.4 延伸：主机侧网络调优（通用）

- [ ] IRQ 亲和与软中断分布：`/proc/interrupts`、多队列网卡、中断绑定工具与 `tuned` profile 的取舍
- [ ] 环形缓冲与队列数：`ethtool -G`（ring buffer）、`ethtool -L`（队列数）、offload 开关 `ethtool -K` 的适用场景
- [ ] 巨帧与 MTU 一致性：`ip link` 设置、`ping -M do` 验证、路径 MTU 发现失效时的现象
- [ ] 网卡固件与驱动版本纳入基线：`ethtool -i` 查驱动与固件版本，升级前记录版本与当前配置
- [ ] 高吞吐场景的通用取舍：缓冲调大换延迟、offload 打开换 CPU，**每一项都要有量化依据**

> RDMA/RoCE 的无损网络配置（PFC/ECN/DCQCN、GID 索引、交换机侧配合）与 perftest 基线属于 AI 基础设施主题域，见 [[AI-Infra/00_简介|AI-Infra 大纲]] 的 [[AI-Infra/03_RDMA与RoCE无损网络]] 与 [[AI-Infra/04_perftest与性能基线]]。

**生产实践**

- 分层排查是基本功：能 ping 通不代表 TCP 能连（防火墙），TCP 能连不代表应用正常（DNS、证书、后端）
- 生产抓包必须限流限时（`-c` 包数、`-w` 落到独立目录、抓完及时清理），别把机器抓挂
- 高并发短连接场景最常见的调优项就是 `conntrack` 表大小、`somaxconn`、`ip_local_port_range`、`tcp_tw_reuse`——**调之前先量化当前连接数与错误计数**
- 云环境下先分清「主机内」还是「云网络/负载均衡/安全组」的问题，看 `nstat` 的重传与丢包统计再下结论
- 带宽与延迟先测再调：用 `iperf3` 建基线、`ss -ti` 看 RTT 与重传；要复现「偶发变慢」就在实验链路用 `tc netem` 注入延迟与丢包，而不是等生产上再遇到一次

**要点自测**

- 大量 `TIME_WAIT` 是问题吗？什么情况下需要处理？为什么 `CLOSE_WAIT` 只能改应用？
- 用户说「服务连不上」，你的排查顺序是什么？每一步用什么命令、期待看到什么？
- 抓包怎么抓才能既拿到证据又不影响生产？
- `getent hosts` 和 `dig` 结果不一致，说明什么？
- MTU 不一致的典型现象是什么？怎么验证？
- TCP 能连通但吞吐上不去，你会看哪些指标？（`ss -ti` 的 RTT/重传/窗口、`iperf3` 基线、路径 MTU）
- 客户端偶发连接失败、服务端却没有日志，可能和什么有关？（accept 队列溢出、`conntrack` 表满）

## 阶段 7：权限、账号与安全加固

> **对应笔记**：[[07_权限与安全加固]]
>
> 该笔记按难度分了两层：标 **【核心】** 的条目属于本阶段必须掌握；标 **【进阶】** 的条目（`chattr` 与扩展属性、内核安全参数的取舍、SSH CA 与主机指纹）第一遍只需知道有这条路，用到时再回来查。笔记内的命令都标了「验证什么」与预期输出，实测环境与未实测部分见文末「验证进度」。

### 7.1 权限模型与提权面

- [ ] 权限模型：`rwx` 对文件与目录的不同含义、属主/属组/其他人、`umask` 的影响
- [ ] 目录权限的路径语义：访问 `dir/file` 要求路径上**每一级**都有 `x`（`namei -l` 一次列全）、删文件看的是目录的 `w`、sticky 只保护目录内的条目；`umask` 的三个落点（PAM/`login.defs`、systemd `UMask=`、进程自身）分别管哪类进程
- [ ] 特殊权限：SUID/SGID/Sticky 的作用与提权风险，用 `find -perm` 排查异常 SUID 程序
- [ ] Capabilities：`getcap`/`setcap` 精确授予单个特权（如 `cap_net_bind_service`）、systemd 的 `AmbientCapabilities`/`CapabilityBoundingSet`、容器里的 `--cap-drop all`——这是 SUID 之外的主要提权面，也是现代加固的首选替代
- [ ] 提权面全景（不止 SUID）：file capabilities、`sudo`/`su`、被 root 执行的**可写脚本与配置**（cron / systemd / PATH）、`authorized_keys`、`/etc/ld.so.preload`、无主文件与世界可写目录——每一类都要有核查命令，并与留档基线比对
- [ ] 扩展能力：`setfacl`/`getfacl`、`chattr +i`、SELinux 上下文（`ls -Z`、`restorecon`、`ausearch`）
- [ ] ACL 的深层语义：`mask` 与 `#effective`、默认 ACL 的继承、`chmod` 会重算 mask、备份要带上扩展属性（`tar --acls --xattrs` / `rsync -A -X`）
- [ ] 账号体系：`/etc/passwd`/`shadow`/`group`、`useradd`/`usermod`、密码与有效期策略（`chage`、PAM）、禁止 root 直接登录
- [ ] PAM 与密码策略的落地：`auth`/`account`/`password`/`session` 四类栈与 `pam_unix`/`pam_limits`/`pam_umask`/`pam_faillock`/`pam_pwquality`；RHEL 9（`authselect` 默认带失败锁定）与 Debian 系（需自行启用）的差异——**这是「改 `limits.conf` 为什么对 systemd 服务不生效」的落点，与阶段 3 交叉**
- [ ] `su` 与 `sudo`：`visudo` 与 sudoers 写法、`sudo -l`、免密边界、`Defaults` 关键项
- [ ] SSH 加固：只开密钥、禁用密码与 root 登录、`AllowUsers`、`Match` 段、`authorized_keys` 的 `command=` 限制、失败锁定
- [ ] SSH 进阶：用 `sshd -T` 看生效配置（而不是只看配置文件）、密钥类型与轮换（ed25519）、SSH CA 与证书、`ProxyJump` 跳板、`known_hosts` 里主机指纹变更意味着什么

### 7.2 强制访问控制与审计

- [ ] SELinux 三种模式与常见排坑（`enforcing` 下服务起不来怎么定位），模式持久化（`/etc/selinux/config`、`enforcing=0` 内核参数），以及 AppArmor 的定位差异
- [ ] SELinux 的处置四步：`ausearch` 找拒绝记录 → `audit2allow`/`semanage` 修策略 → `restorecon` 修上下文 → `getsebool`/`setsebool -P` 调布尔值
- [ ] 防火墙：`firewalld`/`ufw` 与底层 `nftables`/`iptables` 的关系，规则持久化与生效顺序
- [ ] 审计与取证：`auditd` 规则（`-w`/`-a`）与持久化（`/etc/audit/rules.d/`）、容量参数（`max_log_file`/`num_logs`/`space_left_action`/`disk_full_action`）、`last`/`lastb`/`who`/`w` 与 `wtmp`/`btmp`/`lastlog` 的权限、`rsyslog` 远程集中、`history` 为什么不可靠
- [ ] 加固与合规：CVE 与补丁管理（含 `apt` 的 phased updates 与重启生效）、文件完整性校验（`dpkg -V`、`rpm -Va`、`debsums`、AIDE 基线库）、CIS/OpenSCAP 基线扫描、最小化安装（关掉不用的服务与端口）
- [ ] 内核与网络安全参数：`rp_filter`、`accept_redirects`、`syncookies`、`perf_event_paranoid`/`kptr_restrict`/`dmesg_restrict`（安全与可观测性的取舍）、`fs.protected_*`/`yama.ptrace_scope`/`unprivileged_bpf_disabled`，以及 `/etc/sysctl.d/` 的加载顺序
- [ ] 挂载层的加固：`nosuid`/`nodev`/`noexec`（尤其 `/tmp`、`/dev/shm`、数据盘）与 `findmnt` 核查，`noexec` 对安装脚本与解释器的兼容性代价

### 7.3 入侵排查与应急处置

- [ ] 处置顺序：隔离（云上先做磁盘快照，再限制网络；**不关机、不重启、不 `kill -9`、不急着重装**）→ 保全现场（内存侧证据优先）→ 取证 → 判定影响面 → 恢复或重建
- [ ] 持久化点清单：`cron`/`systemd timer`/`enabled` 服务、`authorized_keys` 与 shell 启动文件、`/etc/ld.so.preload`、PAM 与服务配置、内核模块
- [ ] 现场取证命令：`ps --forest`、`ss -antup`、`/proc/<pid>/{exe,cwd,environ}`、`lsof`、`last`/`lastb`、`ausearch`、`dpkg -V`/`rpm -Va`
- [ ] 判定与恢复：用包管理器反查文件归属（`dpkg -S`/`rpm -qf`）、按时间线判断横向移动范围；**被 root 完全控制的机器以重建为准**，重建前轮换全部相关凭据

**生产实践**

- 禁止密码登录，统一走密钥 + 堡垒机；`sudo` 按最小权限分配并留审计，不共享 root 密码
- 所有变更留痕：`sudo` 日志、`auditd`、堡垒机录像；安全事件先保留现场再处置（隔离网络，但别急着重装）
- 加固策略先在测试环境验证 SELinux/防火墙，别在生产上第一次打开就直接 `enforcing`
- 定期做基线核查：**多余账号、SUID 文件、监听端口、计划任务、SSH 授权文件**——这五类是最常见的入侵落点
- 不要再靠 SUID 给完整 root 来换一个能力：能 `setcap` 就 `setcap`，能在 systemd 里限定 `CapabilityBoundingSet` 就限定，让进程只拿到它真正需要的那一项特权
- 至少每半年演练一次应急流程：从五类核查发现异常 → 隔离 → 取证 → 写出时间线与影响面，并把演练结论补进 Runbook
- 被 root 完全控制的机器不做「清理后继续用」：确认影响范围后重建，重建前轮换同一批机器共用的全部凭据

- 为什么改 `/etc/security/limits.conf` 对 systemd 服务不生效？（与阶段 3 交叉）
- 怀疑机器被入侵，你的处置顺序是什么？（隔离 → 保留现场 → 取证 → 恢复或重建）

## 阶段 8：systemd、服务与定时任务

> **对应笔记**：[[08_systemd与服务管理]]
>
> 该笔记按难度分了两层：标 **【核心】** 的条目属于本阶段必须掌握；标 **【进阶】** 的条目（沙箱细节、cgroup 与 slice 的层级、模板单元）第一遍只需知道有这条路。笔记内的命令都标了「验证什么」与预期输出，用户级 systemd 的结论为实测，system 单元与 RHEL 差异标注为「未实测」，详见文末「验证进度」。

- [ ] 核心概念：unit 类型（service/target/timer/socket/mount）、依赖（`Wants`/`Requires`/`After`/`Before`）与并行启动
- [ ] unit 与 cgroup 的对应：`systemctl status` 的 `CGroup` 行、`slice` 层级（`system.slice`/`user@1000.service`）、用 `systemd-cgls`/`systemd-cgtop` 看「这个服务占了多少」（与阶段 3 交叉）
- [ ] unit 的三处位置与优先级（`/etc/systemd/system` > `/run/systemd/system` > `/usr/lib/systemd/system`）、为什么改完必须 `daemon-reload`、用 `systemctl edit` 写 drop-in；模板单元与实例化（`foo@.service`、`%i`）的用途与 drop-in 写法
- [ ] 服务排障：`systemctl status` 的 `Loaded/Active/Result/Process` 四段与 systemd 退出码（`200/CHDIR`、`203/EXEC`、`216/GROUP`、`226/NAMESPACE`）、`journalctl -u`、`systemd-analyze`，以及 `Type=` 选错（`simple`/`forking`/`notify`）导致的「假启动失败」
- [ ] 资源与生命周期约束：`LimitNOFILE`、`MemoryMax`/`CPUQuota`、`Restart=`/`RestartSec=`、`KillMode`、`TimeoutStartSec`/`TimeoutStopSec`；`ExecReload=` 与 `systemctl reload` 相比 `restart` 的边界
- [ ] 沙箱选项：`ProtectSystem`、`PrivateTmp`、`ReadWritePaths` 的用途与踩坑
- [ ] 单元内容与调试：`systemctl cat`/`show`（看生效配置而非文件）、`list-dependencies`、`ExecStartPre`/`EnvironmentFile=`/`User=`/`WorkingDirectory=` 的常见坑、`systemd-run` 按需跑一个带资源限制的临时单元
- [ ] `systemd-analyze` 工具箱：`unit-paths`（路径与优先级）、`verify`（语法与小节错误）、`exit-status`（退出码含义）、`calendar`/`timespan`（时间表达式）、`security`（暴露面评分）
- [ ] 反复重启与放弃：`Restart=` 配合 `StartLimitBurst`/`StartLimitIntervalSec`，服务被 systemd 判定为「启动失败过多」后不再重试该怎么恢复（`systemctl reset-failed`）
- [ ] 日志接口：`journalctl` 的 `-u`/`-b`/`-b -1`/`--since`/`-p`/`-o json`（关键字段如 `_SYSTEMD_UNIT`、`_PID`、`__MONOTONIC_TIMESTAMP`）与 `journalctl --user`，journald 持久化（`/var/log/journal` 与 `Storage=auto`）、`SystemMaxUse`、磁盘占用与治理（`--disk-usage`/`--vacuum-size`/`--vacuum-time`）、`journald.conf` 的 `RateLimitBurst`（日志风暴时先保住日志本身；**单元级限流不可盲信，要实测**）
- [ ] 临时文件治理：`systemd-tmpfiles` 与 `/etc/tmpfiles.d/`（`/tmp`、`/run` 的清理策略）和我们自己服务的关系、`PrivateTmp` 打开后看到的 `/tmp` 是哪一个；`d`/`D`/`e`/`x` 规则类型与 `age-by` 语义（默认 mtime/atime/ctime 任一较新就不清理）
- [ ] 定时任务：`cron` 与 `systemd timer` 的取舍、`cron` 的环境变量与 PATH 坑（实测 `SHELL=/bin/sh`、无 profile）、`%` 必须写成 `\%`、`/etc/cron.d` 与 `crontab -u`、`/etc/cron.allow`「两个文件都不存在」时的行为以实测为准、`anacron` 补跑错过的任务、`at`/`batch` 的一次性任务
- [ ] `systemd timer` 的 `OnCalendar`/`Persistent`/`AccuracySec`，以及错过的任务如何补跑
- [ ] 自启与屏蔽：`systemctl enable/disable` 与 `WantedBy` 的关系、`enable --now` 与 preset、`mask` 的用途与边界（自己配置目录里的单元无法直接 mask；触发它的 socket/path 仍可能 active）
- [ ] 时间基线：`chrony`/`timedatectl` 与统一时区——排障时时间不对齐，整条证据链都失效

**生产实践**

- 自研服务一律写成 unit，不靠 `nohup`；重启策略、日志归集、资源上限都交给 systemd 管理
- 上线流程固定为：`systemd-analyze verify` → `daemon-reload` → `start` → 业务验证（端口/日志/指标）→ `enable`；不要跳过 verify，也不要拿 `restart` 当验证
- 定时任务必须**幂等 + 加锁**（`flock`）并监控执行结果；不检查返回值的 `cron` 是隐性故障源
- 变更 unit 后必须 `daemon-reload`；`restart` 之后一定要验证端口、日志与业务指标，而不是看命令没报错就走
- 排障前先确认时间与时区是否正确，跨系统对日志时这一步优先级最高
- 定时任务与临时文件都要有归属：每个 `cron`/`timer` 写清用途和负责人，每个 `/tmp` 清理策略都要先确认没有服务在里面放长生命周期文件
- 日志治理要靠「应用按级别输出 + journald 容量上限 + 高频日志分流」三层，不能指望单元级限流兜底（本文实测限流未按配置生效）

**要点自测**

- 服务 `systemctl start` 失败，你的排查顺序是什么？
- `Type=` 选错（`simple`/`forking`/`notify`）会造成什么「假启动失败」？怎么用日志区分？
- 为什么改完 unit 必须 `daemon-reload`？reload 之后为什么还要 restart 才能真正换配置？
- `limits.conf`、`ulimit`、systemd `LimitNOFILE` 三者的关系与生效范围？
- 脚本在命令行能跑、放进 `cron` 就跑不通，为什么？
- `systemd timer` 比 `cron` 多了哪些能力？什么场景值得切换？
- 服务每几秒重启一次，过一会儿就彻底不重启了，怎么解释、怎么恢复？
- `/tmp` 里的文件是谁在清、什么时候清？如果有服务把长生命周期文件放在 `/tmp`，会发生什么？
- 为什么 `systemd-tmpfiles --clean` 有时不删「很久没改」的文件？`age-by` 是在看哪些时间戳？

## 阶段 9：日志、监控与可观测性

> **对应笔记**：[[09_日志与监控]]
>
> 该笔记按难度分了两层：标 **【核心】** 的条目属于本阶段必须掌握；标 **【进阶】** 的条目（分布式追踪、采集成本与 cardinality、告警分层细节）第一遍只需知道有这条路。日志链路与监控栈机制均为实测（Prometheus/Alertmanager/blackbox/node_exporter/sysstat 用发行版包解包运行），真实部署、集中平台与追踪后端标注为「未实测」，详见文末「验证进度」。

- [ ] 日志体系：journald 与 rsyslog 的分工、结构化字段与纯文本的取舍（`journalctl -o json` 的 `_SYSTEMD_UNIT`/`_PID`/`__MONOTONIC_TIMESTAMP`）、应用日志的落点与格式、集中采集方案（远程 syslog / Filebeat / Promtail / Vector）的取舍；syslog 报文的 PRI/RFC 5424 字段与 UDP/TCP(`@`/`@@`)/TLS 的传输选择
- [ ] 日志轮转：`logrotate` 的 `daily`/`size`/`rotate`/`compress`/`delaycompress`/`missingok`/`notifempty`/`sharedscripts` 与状态文件，`copytruncate` 与「发信号让应用重开文件」的差别（inode 与数据落点的实测证据），以及 `-d`/`-v -f` 的调试方式
- [ ] 磁盘满的日志侧治理：四类原因（真文件 / 已删除但仍被持有 / inode / 保留块）、`df` 与 `du` 不一致、`du` 找增长源、`/proc/<pid>/fd` 与 `lsof +L1`，以及「应用级别 + journald 容量 + logrotate 保留」三层策略
- [ ] 指标采集：`node_exporter` 的关键指标（CPU/内存/磁盘/网络/文件系统/连接数/采集器耗时）、pull 模型与 Prometheus `up`，以及自建采集的边界（cardinality、采集频率、exporter 自监控）
- [ ] `sysstat` 的历史价值：`sar -u/-r/-b/-n DEV`、`sa1`/`sa2`（systemd timer 或 `/etc/cron.d/sysstat`）、`sadf` 导出 CSV，以及数据保留期（默认 `HISTORY=7`，要「至少两周」必须显式配置并验证）；进程级历史用 `atop` 补充
- [ ] 指标语义：USE 方法（Utilization / Saturation / Errors）与 PSI、告警分层、counter 与 gauge 的正确用法、平均值 vs 分位数（含**分位数算法口径**的差异），以及瞬时采样会漏掉什么
- [ ] 三条链路的分工：日志看细节（发生了什么）、指标看趋势（多严重、从什么时候开始）、链路追踪看一次请求的耗时分布（慢在哪一段），再叠加变更事件做时间线对齐；对应到宿主机与容器两个视角（见 [[Kubernetes/07_生产运维与可观测性]]）；采集的最小维度集（环境/服务/实例/版本）
- [ ] 分布式追踪：OpenTelemetry 的数据模型（trace/span）、采样策略（头部采样 vs 尾部采样）与上下文透传（W3C `traceparent` 与采样标志），以及它在「服务慢但资源都空闲」这类问题里的用法；最小落地是把 `trace_id` 写进日志
- [ ] 告警链路：Prometheus 数据模型与 PromQL（`rate`/聚合/比率）、recording rule 与 alerting rule（用 `ALERTS` 与 `promtool check rules` 验证）、Alertmanager 的路由/分组/抑制/静默，用 `blackbox_exporter` 补可用性与证书到期探测（`probe_ssl_earliest_cert_expiry`），以及告警风暴时的降噪顺序（分组 → 抑制 → 静默）
- [ ] 告警工程化：命名与分级（`severity`）、每条告警对应 Runbook 与负责人、`group_by`/`repeat_interval` 的取舍、维护窗口 silence 的期限与复查、告警规则的评审与 CI 校验
- [ ] 可用性目标：SLI/SLO 的定义方式、错误预算与「几个 9」对应的可接受中断时长，以及它如何决定「哪些告警立刻处理、哪些排期」

**生产实践**

- 每台机器都要有可回溯的历史指标（`sar` 至少留两周），否则「昨天下午开始变慢」只能靠猜
- 可观测性按四件套落地：日志（落点+持久化+轮转）、指标（每机采集+保留）、告警（`up`/水位/证书/错误率，每条有动作）、SLO（至少一个核心服务）；先闭环再扩指标
- 应用日志与系统日志分目录或分盘存放，避免日志写满根分区造成整机故障
- 告警要能对应到具体动作，并区分「立刻处理」与「排期处理」；只报不处理的告警等于没有告警
- 排障时把变更时间线（发布、配置、内核、网络）与指标拐点对齐，多数问题能靠这一步缩小到很小的范围
- 三条链路的采集都要能回答「哪个服务、哪个实例、哪一次请求」——没有实例维度的指标，放到集群里等于不可用
- 采集成本要有 owner：日志保留天数、指标 cardinality、追踪采样率三个数字写进方案；高基数信息进日志/追踪，不进 label

**要点自测**

- 磁盘被日志写满，你的处理顺序是什么？「删了文件但空间没释放」怎么办？
- 怎么用 `sar` 复盘「昨晚 3 点系统变慢」？
- `logrotate` 的 `copytruncate` 有什么副作用？什么场景必须用它？
- 为什么监控要看分位数而不是只看平均值？为什么「p95 是多少」还取决于分位数算法？
- 「服务变慢」和「服务报错」分别该先看哪条链路？为什么不能只靠日志？
- journald 与 rsyslog 的分工是什么？远程集中怎么选（`@` 与 `@@`、TLS、Filebeat/Promtail/Vector）？
- Prometheus 的「目标 → 规则 → Alertmanager → 通知」这条链路怎么逐段验证？`ALERTS` 与 `promtool` 各解决什么？
- 告警风暴的降噪顺序是什么？Alertmanager 的「抑制」和「静默」分别解决什么问题？
- SLI/SLO/错误预算怎么定义？它如何决定「哪些告警立刻处理、哪些排期」？

## 阶段 10：性能分析与故障排查 ★（核心区）

> **对应笔记**：[[10_性能分析与排障]]
>
> 该笔记按难度分了两层：标 **【核心】** 的条目属于本阶段必须掌握；标 **【进阶】** 的条目（off-CPU 分析、eBPF、容器与宿主双视角、观测成本）第一遍只需知道有这条路。单机 CPU/内存/IO/网络/耗尽类实验为实测；硬件 PMU、eBPF、`fio`/`stress-ng`、`blktrace`、cgroup 限流标注为「未实测」（需 root/真机），详见文末「验证进度」。

### 10.1 方法论与 CPU

- [ ] 方法论先行：先量化影响面与时间点，再按资源分层（CPU / 内存 / IO / 网络 / 锁）逐一排除，最后给根因与改进；**观测本身有代价与采样偏差**（实测 `strace` 让同一 workload 慢约 79 倍；`top` 第一屏是自开机平均；采样会漏短脉冲），以及工具不可用时的降级路径（无 PMU/eBPF 时用 `/proc` + `strace` + 日志 + 分位数）
- [ ] 负载与 CPU：`uptime` 的 load **包含 D 状态进程**、`vmstat` 的 `r/b/si/so/cs/us/sy/wa`、`mpstat -P ALL`、`pidstat`
- [ ] 「负载高但 CPU 空闲」的判定表：D 状态堆积（IO/网络存储/锁）→ `b`/`%iowait`/`wchan`；被虚拟化偷走 → `%steal`；短任务与过度唤醒 → `cs` 高而 `id` 不低
- [ ] CPU 高的五种分支：`us`（应用计算）、`sy`（系统调用/锁/切换）、`si`（软中断/网络）、`st`（虚拟化被偷）、`wa`（IO 等待）
- [ ] 上下文切换与中断：自愿 vs 非自愿切换、`/proc/interrupts`、多队列网卡与软中断分布、网卡侧多队列（RSS）与软件侧分流（RPS）的基本概念
- [ ] 单核视角：`mpstat -P ALL` 找 100% 的核、`pidstat -u -t` 落到线程、`taskset -cp` 看绑核，并用「同核竞争」实验量化对 p99 的影响（实测 p50 7.31→17.66ms、p99 8.16→22.22ms，而整机仅 4.19%）

### 10.2 内存、IO 与网络

- [ ] 内存分析：`free`/`vmstat`/PSI、RSS/VSZ/PSS、`pmap`，以及泄漏的确认方法
- [ ] IO 分析：`iostat -x` 各列的含义与组合解读、`iotop`、`fio` 基线对比、`blktrace` 下钻到进程与文件
- [ ] 网络分析：`ss -s`、`nstat` 的重传与错误计数、`sar -n`、`tcpdump` 定位丢包在哪一跳
- [ ] 进程级深挖：`strace -p -f -T`、`/proc/<pid>/{stack,wchan,io}`、`perf top` / `perf record -g` + 火焰图
- [ ] `/proc` 证据链：`status`（自愿/非自愿切换）、`sched`（`nr_switches`/`wait_sum`）、`wchan`（在等什么）、`io`（真实读写）、`smaps_rollup`（RSS/PSS/匿名页）
- [ ] `perf` 的三种用法：`perf stat` 看事件计数、`perf record -g` + 火焰图看热点函数、`perf sched` 与 off-CPU 分析看「进程不在 CPU 上时在等什么」（需要 debuginfo 或内核符号）
- [ ] eBPF 工具：`bpftrace` 一行脚本、bcc 的 `execsnoop`/`biolatency`/`tcpconnect`，以及对内核版本的要求
- [ ] 容器与宿主双视角：cgroup v2 的 `cpu.stat`（`nr_throttled`/`throttled_usec`）、`memory.max`/`memory.events`、`io.max`、`systemd-cgtop`；CPU throttling 的指纹是「容器内 CPU 不高 + 延迟周期性尖刺」
- [ ] 加速器与高速网卡的观测入口：`nvidia-smi dmon`、`rdma link`/`ibv_devinfo`、`ethtool -S` 的 pause 与错误计数（下钻方法见 [[AI-Infra/00_简介|AI-Infra 大纲]]）

### 10.3 高频杀手场景

- [ ] 内存回收导致的抖动（direct reclaim）、THP 引起的偶发卡顿
- [ ] 锁竞争：应用锁、数据库锁，表现为 CPU 不高但吞吐上不去；入口是 `pidstat -w` 的高自愿切换、`strace -c` 的 futex、`/proc/<pid>/sched` 的等待时间与 off-CPU 分析
- [ ] 单核打满：整机 CPU 不高但延迟飙升（单线程热点、绑核与 `taskset` 用错、GC 或解释器停世界），比整机 CPU 高更难发现
- [ ] DNS 解析慢、日志同步落盘阻塞、备份任务抢占 IO
- [ ] 连接数/句柄/端口打满，表现为「偶发失败」而非「持续失败」；能用「端口数 ÷ TIME_WAIT 时长」估算短连接 QPS 上限（实测 28232 个端口、3000 条短连接 0.1s 后 3023 个 TIME_WAIT），并用 `ulimit -n`/`EMFILE`/`/proc/<pid>/fd` 定位句柄耗尽
- [ ] GPU 场景：XID 错误、掉卡、训练通信静默降速（见 [[AI-Infra/09_XID与硬件故障处理]]、[[AI-Infra/06_NCCL排障]]）
- [ ] 排障纪律：先取证再动手，用 `script`/`tee` 记录命令与输出，时间统一时区；有一套**一次性取证脚本**（同一次运行抓齐负载/进程/PSI/内存/套接字/`nstat`/softnet/内核日志）

**生产实践**

- 先建性能基线（业务高峰的正常水位），有基线才能说「变慢了」；基线要留下「身份与规模 / CPU 与负载 / 内存 / IO / 网络」五组数据并注明采集时的负载条件
- 排障动作按「影响面最小、代价最低」排序；故障中不做高风险变更（重启、改内核参数）
- 排障报告固定六段：时间线、影响面、证据、根因、止损动作、长期改进（含监控与告警的补齐）
- 用故障演练检验排障路径：人为制造 CPU 打满、内存泄漏、IO 打满、网络丢包（`stress-ng`、`fio`、`tc netem`），练习 10 分钟内定位；演练必须在隔离环境/命名空间里做、设定明确上限、跑完清理并复核

**要点自测**

- 负载飙高但 CPU 空闲，可能是什么原因？怎么一步步验证？
- `wa` 高、`%util` 高、`await` 高分别代表什么？为什么它们可能互不对应？
- 内存看起来还有空余，进程却一直在换页，怎么解释？
- 机器 IO 慢，你怎么把范围从「某块盘」缩小到「某个进程的某个文件」？
- 请把一次真实的排障讲给面试官听：现象 → 分层 → 证据 → 根因 → 改进。
- 整机 CPU 不高但延迟飙升，怎么验证是不是单核打满？
- `strace`/`perf`/eBPF 各有什么观测代价与前提？工具不可用时你的降级路径是什么？
- 容器的 CPU 被限流（throttling）在宿主侧怎么确认？为什么容器内 `top` 不可信？
- 「偶发失败」类问题（连接/句柄/端口打满）怎么量化，并区分它与网络抖动的差别？

## 阶段 11：生产运维、变更与高可用

> **对应笔记**：[[11_生产运维与高可用]]

- [ ] 变更管理：灰度与分批、变更窗口、回滚方案、变更前后的核对清单（配置版本、进程、端口、业务指标）
- [ ] 事故响应流程：故障分级与通报口径、升级路径与 on-call 轮值、**止损优先于根因**、事后复盘（时间线 + 改进项闭环）与 Runbook/SOP 维护
- [ ] 系统参数调优：`/etc/sysctl.d/` 的加载顺序与生效方式、常见调优项（连接数、句柄、网络缓冲、内存回收）的副作用
- [ ] 容量治理：根分区扩容（LVM / 云盘在线扩容）、`/var/log` 与容器数据目录治理、临时文件清理策略
- [ ] 硬件与固件基线：`dmidecode`/`lscpu`/`lspci` 采集资产信息、RAID 卡与 BBU 状态、BIOS 与固件版本纳入台账（GPU/网卡固件的深水区见 [[AI-Infra/00_简介|AI-Infra 大纲]]）
- [ ] 备份与恢复：`rsync` 增量与 `--link-dest` 硬链接快照、数据库一致性备份、快照的一致性问题
- [ ] 备份工具与策略：`rsync` 之外的 restic/borg（去重、加密、可校验）、3-2-1 原则、异地与离线副本、保留策略，以及「备份成功」与「能恢复」的区别
- [ ] 高可用：keepalived + VIP、负载均衡层、脑裂与仲裁、单机故障对业务的影响面
- [ ] 批量运维：Ansible 的 inventory/playbook 与幂等性、批量 `ssh` 的坑（并发放大、超时、非交互环境变量）
- [ ] 脚本规范：`set -euo pipefail`、引号与错误处理、可重入、日志与退出码
- [ ] 安全运维流程：补丁窗口与重启批次、证书到期管理、日志留存与合规要求
- [ ] 证书与密钥生命周期：`openssl s_client`/`x509 -enddate` 查有效期、内部 CA 的签发与轮换、certbot/ACME 自动续期，以及为什么证书过期总是到线上才被发现
- [ ] 灾难恢复：内核起不来、根分区损坏、关键文件误删的最短恢复路径；带外管理与救援介质准备

**生产实践**

- 所有变更遵循「先备份、再验证、后生效、可回滚」，并且把回滚命令写清楚
- 内核与系统参数按批次推进，先非核心业务；重启前确认上层集群或负载均衡能承接流量
- 备份的唯一验收标准是「能恢复」：定期做恢复演练并记录耗时，对齐 RTO/RPO
- 能自动化的手工操作尽量自动化，至少沉淀成脚本与文档，避免只有某个人会做
- 把「止损」和「根因」分开：事故中先恢复业务并保留现场，复盘阶段再追根因；带着「必须当场查清楚」的心态处置，往往会把故障拖长

**要点自测**

- 要给 100 台机器调整内核参数，你的方案是什么？（分批、自动化、验证、回滚）
- 一台核心服务器根分区快满了，处置顺序是什么？
- 怎么设计一个「重启不停服」的运维方案？
- 备份做到什么程度才算合格？你怎么向面试官证明它有效？
- 线上故障发生了，你的前三步是什么？什么时候才轮到查根因？

## 阶段 12：复习与自测

> **对应笔记**：[[12_复习与自测]]

### 核心要点速查（每个都能脱稿讲 3~5 分钟）

- [ ] 启动链与救援：从加电到登录，每一环失败的现象与处理
- [ ] 进程与信号：D/Z 状态、`SIGTERM` vs `SIGKILL`、优雅退出
- [ ] 内存：`free` 的正确读法、OOM 判定、swap 取舍、泄漏排查
- [ ] 存储：inode、`df`/`du` 不一致、LVM 扩容、RAID 取舍、IO 瓶颈判定
- [ ] 网络：TCP 状态机、`TIME_WAIT`/`CLOSE_WAIT`、抓包、分层排查顺序
- [ ] 权限与安全：权限位与 SUID、capabilities、sudo 最小权限、SSH 加固、SELinux 排坑
- [ ] systemd：依赖关系、服务排障、资源限制、timer 与 cron
- [ ] 可观测性：日志轮转、`sar` 复盘、USE 方法、告警分层、trace 与 SLO 基础
- [ ] 性能排障：`us/sy/wa/si` 的分支判断、上下文切换、火焰图
- [ ] 生产运维：变更与回滚、批量运维、备份恢复演练
- [ ] Linux 与容器的关系：namespace / cgroup / overlayfs，串起 [[Kubernetes/03_调度_资源_QoS]] 与 [[Kubernetes/04_网络]]

### 场景题（每题都按「现象 → 分层 → 命令 → 结论 → 改进」写成一份答案）

- [ ] 机器负载很高，但 CPU 使用率不高
- [ ] 服务内存持续增长，最终被 OOM kill
- [ ] 磁盘空间满 / inode 满
- [ ] `too many open files` / 无法创建新进程
- [ ] 服务连不上：链路、路由、防火墙、DNS、应用逐层验证
- [ ] 偶发网络延迟与丢包（MTU、conntrack、网卡队列、对端限速）
- [ ] 服务起不来 / 开机不自启 / 定时任务没执行
- [ ] 机器疑似被入侵的处置与取证
- [ ] 内核 panic 后的现场分析与恢复
- [ ] 根文件系统变成只读（remount ro）的处置
- [ ] 单核 CPU 打满：整机 CPU 不高，但延迟飙升
- [ ] 资源都空闲但服务变慢（锁、GC、下游依赖、DNS）
- [ ] SSH 登录很慢或时通时断（DNS 反解、MTU、防火墙）
- [ ] 服务器时间漂移：时钟不同步如何污染日志比对与证书校验
- [ ] 容器被 OOMKilled：从宿主机与容器两个视角各看一遍（见 [[Kubernetes/03_调度_资源_QoS]]）
