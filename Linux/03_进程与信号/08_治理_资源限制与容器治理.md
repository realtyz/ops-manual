# 资源限制与容器治理

## 1. 为什么每个进程组都要有边界

没有边界的进程组可以吃掉整机的任务数、句柄或内存，把「一个服务变慢」放大成「一台机器不可用」。给它配上边界（再配合副本数与容量规划）能把故障限制在一个服务内——**限制线首先是可用性手段，其次才是资源手段**。

这句话有一个实际推论：**限制的目标不是「省资源」，而是「让失败可控」**。所以「这个上限设得对不对」的判断标准不是「它用得少不少」，而是「撞上它的时候，坏掉的是不是只有它自己」。

边界有五层**来源**，但真正的**执法层只有三类**：进程的 `RLIMIT`／cgroup 控制器／整机 `sysctl`。`limits.conf` 与单元上的 `LimitXXX=` 都只是**写 `RLIMIT` 的途径**——同一个进程的 `RLIMIT` 只有一个值，unit 未显式配置时取 `DefaultLimit*=`，也就是**后者覆盖前者**。各层来源的**载体不同**，查文档与改配置的位置也不同：

| 层 | 载体 | 作用范围 | 撞上之后 |
| --- | --- | --- | --- |
| 进程自身 | 资源限制（软/硬限制） | 单个进程及其后代 | 申请失败（`EAGAIN`/`ENOMEM`），进程可能直接报错退出 |
| 登录会话 | PAM 的登录限制配置 | 由 PAM 建立的登录会话 | 同上，但只影响登录进来的命令 |
| 服务 | 服务单元的限制属性 | 该服务拉起的全部进程 | 同上，或触发组级 OOM |
| 组 | cgroup v2 控制器 | 整组进程 | 计数型失败、速率型被限速、容量型被杀 |
| 整机 | 内核参数 | 全系统 | 整机级 OOM 或全局失败 |

出问题时先确定撞的是哪一层：进程自己报错退出、被组级机制杀掉、还是整机水位被撞穿——三种结论对应三种完全不同的修法。**改错一层等于没改**。

## 2. 两种计数口径：任务数与句柄数

这两类资源是运维最常打交道的，它们各自都有多条独立上限，而且**报错文案相似、判据完全不同**。

### 2.1 任务数：四条上限

| 上限 | 语义 | 撞上之后的特征 |
| --- | --- | --- |
| PID 编号空间 | 分配不出新编号就无法创建 | 创建失败；内核可能提示编号耗尽 |
| 整机 task 总数 | 全系统任务数天花板 | 创建线程或进程失败 |
| 按用户的进程数 | **按 real UID 计**，用户维度 | **只有该用户的创建失败**，其他用户正常 |
| 组内 task 数 | cgroup 的 pids 控制器 | 创建失败，内核日志有控制器拒绝记录 |

**四条上限不要背数字**：PID 编号空间与整机任务数在现代发行版上往往被初始化配置抬高或被内核按内存规模推算，只能用查询命令看本机实际值。按用户的那条同样不是服务管理器给的：内核在 `kernel/fork.c` 的 `fork_init()` 里把 PID 1 的 `RLIMIT_NPROC` 设为 `threads-max/2`（实测 31249），再由子进程一路继承，而 `DefaultLimitNPROC=` 并未设置——它和 unit 上的任务数上限是**两个互不相干的入口**，别把现场读到的大值归给服务管理器。

**判断顺序**：先看报错属于哪一类（资源暂时不可用 vs 内存不足）→ 再看是整机范围还是某一组/某一用户 → 最后才谈改哪一层。

### 2.2 句柄数：两条上限加一个硬顶

| 上限 | 语义 | 说明 |
| --- | --- | --- |
| 进程的打开文件限制 | 单进程可打开的 fd 数（软/硬限制） | 服务侧由单元属性决定，登录会话由 PAM 决定 |
| 整机可打开文件总数 | 全系统 fd 总量 | 常与「整机水位」一起监控 |
| 单进程 fd 数的硬顶 | 内核参数 | 进程限制**不能超过**它；写大了会被截断 |

**句柄耗尽不一定是泄漏。** 每个连接一个 fd、每个日志文件一个 fd，长连接服务本来就可能是设计使然。判断顺序是：先看是整机还是单进程 → 再看构成（套接字还是普通文件）→ 最后看趋势（长期单调上涨才是泄漏）。

还有一个容易忽略的程序侧天花板：**用老式轮询接口的程序有编译期上限**（通常 1024），把系统上限调到多大都没用。判断方法是看它是否「无论上限多大，都在同一个数量附近出问题」。

## 3. cgroup v2 的接口怎么用于治理决策

字段本身的读写与单位在实操篇；这里讲**怎么用它们做决定**。

| 文件 | 治理时怎么用 |
| --- | --- |
| 当前用量 | 长期贴着上限 = 上限定得过紧或应用确实在涨 |
| 历史峰值 | **定上限的主要依据**：上限应高于正常峰值并留出余量 |
| 硬上限 | 撞上它、且回收也降不下来时，内核才调 OOM killer；表示「无上限」时说明这个组没有边界 |
| 软上限 | 超出后只节流（回收 + 限速），不杀进程——适合「先踩刹车」的场景 |
| 保护值 | 回收时尽量不动这里的页；给关键服务用 |
| swap 上限 | 该组可用的换出空间（`memory.swap.max`，字节）；设为 0 是**匿名页不再换出**，不等于禁用换页——文件页回收照旧，也与 `vm.swappiness` 无关 |
| 构成明细 | **决定处置方向**：匿名页高 → 应用真的在用；文件页高 → 页缓存计入；内核对象高 → 内核开销 |
| 事件计数 | 记的是**该 cgroup 创建以来**的累计，组被销毁、服务重启重建后归零；`memory.events` 默认按**层级累计**（含后代），只看本级用 `memory.events.local`。`pids.events` 只有 `max`（撞 `pids.max` 的次数）；`oom_kill` 非 0 只说明本组进程被任何 OOM killer 杀过，**不等于本组撞了 `memory.max`** |

三条使用要点：

1. **所有计数都是累积值**，「这次事件有没有发生」要用两次读数的**差值**判断；
2. **上限不是拍出来的**：用历史峰值与曲线说话，并写清安全系数；
3. **账本有时效**：cgroup 目录会随单元结束被回收，事件计数这类证据只在存活期间存在——**复盘要趁现场还在**。

**软上限与硬上限的分工值得单独记住**：软上限是「刹车」（回收、限速，进程继续跑），硬上限是「墙」（撞上且回收降不下来才杀）。给延迟敏感的服务先上软上限通常比直接上硬上限更安全，但如果它真的失控，软上限拦不住。

## 4. 服务侧的几个默认行为必须知道

服务管理器把 cgroup 包了一层，大部分属性是接口文件的封装。有几条默认行为会直接影响复盘：

**任务数的两层默认值。** 单元上的任务数上限有系统级默认值，它不是「无限」：`DefaultTasksMax=` 取 `MIN(kernel.pid_max, kernel.threads-max, 根 cgroup pids.max)` × 15%（systemd 228 起），所以它随内核参数与本机内存规模变化；一个多线程服务在启动阶段撞上它，表现为「起不来」而不是「跑得慢」。

**内存记账默认开启**，但上限默认是「无」——**没有上限的服务是常态而不是例外**，这正是巡检要查的第一项。

**组级 OOM 之后单元可能被整体停掉**，同时 cgroup 与账本一起消失。是否整体停掉由 `OOMPolicy=` 决定（systemd 243 起）：系统管理器侧默认 `DefaultOOMPolicy=stop`（组内进程被杀就干净地停掉整个单元），而带 `Delegate=` 的单元默认 `continue`（只记日志、单元继续跑）。这意味着：**如果不提前采集，事件计数在事后就读不到了**。要在 OOM 之后复盘现场，要么在存活期间采集，要么把单元配置成不被整体停掉（现场用 `systemctl show -p OOMPolicy` 确认）。

**还存在一个用户态的 OOM 处理组件 `systemd-oomd`**：它由 `ManagedOOM*=` 接管（默认 `auto`，systemd 247 起），基于 cgroup 与压力指标在「压力很大但还没 OOM」时提前动手，判据取自 `oomd.conf` 的 `SwapUsedLimit=90%`、`DefaultMemoryPressureLimit=60%`、`DefaultMemoryPressureDurationSec=30s`，日志形态与内核 OOM 不同。**并非所有发行版都装了它**（本库的实验机上就没有），排查时要先确认动手的是哪一个。

## 5. 治理场景与产出

下面四个场景是运维侧真正会遇到的治理动作。每个都给出**要做出的产出**——限制线治理的验收标准是「交出了东西」，不是「看过文档」。

### 场景一：给一个即将上线的服务定任务数与句柄上限

**背景**：新服务压测显示：稳态线程 180、峰值 260；稳态句柄 900、峰值 1400；计划 3 个副本。

**做法**：以「高于峰值并留安全系数」给初值（例如任务数上限 512、句柄上限 4096），上线后按真实峰值复核。**不要照抄邻居服务**——它们的并发模型不同。同时确认上限链的每一环：进程限制不超过内核硬顶，整机总量还有余量。内核侧的硬顶是 `fs.nr_open`——把 `RLIMIT_NOFILE` 硬限制设到它之上，内核直接返回 **`EPERM`**（特权进程也一样，这项检查在 `CAP_SYS_RESOURCE` 之前）；而服务管理器在应用 unit 限制时走「取最接近可行值」的 `setrlimit_closest()` 回退，`LimitNOFILE=` 写超通常表现为**被压低**而不报错，所以验收只能读进程实际生效的值。

**产出**：一条带依据的记录：服务名、所在组路径、初值与依据（压测峰值 × 系数）、复核时间与复核方法、回滚方式。

### 场景二：上限调小之后服务开始被组级 OOM 杀掉

**背景**：为「节省资源」，某服务内存上限被调小；当晚它被杀数次，每次历史峰值都贴住新上限。

**做法**：先确证撞的是它（内核日志或组级事件计数的差值），再看构成明细与当时的业务量。结论只有三种，必须落到其中一种：

- **配额过紧** → 回滚或调整上限（依据是峰值与业务增长趋势）；
- **应用峰值超出预期** → 优化或扩容，配额只是把问题暴露出来；
- **页缓存计入吃额度** → 看访问模式，可能要给缓存留余量而不是继续加限制。

**产出**：一份复盘记录，回答三个问题——谁被杀（进程、组路径、当时用量）、为什么是它（打分与选择依据）、撞的是谁的上限（组级还是整机）；并附回滚动作与观察窗口。

### 场景三：同一节点上多个服务互相拖累

**背景**：节点上 A 服务突发把资源吃紧，导致 B 服务开始换页、延迟抖动。两者暂时无法拆机。

**做法**：给 A 设硬上限把它关在自己那格；给 B 设保护值让回收时尽量不动它；如果 A 是多进程组，考虑让组级 OOM 终结整个组而不是单个进程。**优先用 cgroup 做隔离，而不是调整内核挑选被杀进程的倾向**——后者是概率，前者是边界。

**产出**：隔离方案与验证方式（各自的硬上限、保护设置、以及「压力下 B 是否还在换页」的复查步骤）。

### 场景四：巡检发现一批服务没有上限

**背景**：巡检 40 个服务，任务数与内存上限都显示为「无限」，不可能一次全改。

**做法**：按「峰值用量 × 影响面」排序推进，先做核心链路与资源大户；每个服务先补一次只读基线（峰值、构成、压力），再分批改上限；每批改完留观察窗口。**不要一次性批量改**——40 个服务的上限同时生效，等于把 40 个未知风险同时引入。

**产出**：一张排期表（服务、当前峰值、目标上限、影响面、批次、验证方式）与每批的变更记录。

## 6. 治理产物四件套

**限制基线卡**：服务名与所在组路径、任务数上限与实测峰值、句柄限制与实测水位、内存上限与历史峰值、内存构成、历史 OOM 次数、换页使用（组侧读 `memory.swap.current`/`memory.swap.max`（字节），进程侧读 `/proc/<pid>/status` 的 `VmSwap`，整机侧看 `vmstat` 的 `si`/`so`——判断「在涨」要两次读数取差值）、停止策略（停止范围与等待上限）。用途：回答「这个上限该不该调」。

**配额变更单**：现值 → 目标值、依据（基线卡数据）、影响面（副本数、峰值时段）、验证方式（改完读哪个文件、读到什么值算成功）、回滚命令。**上限调整属于生产变更**，要有窗口与记录。

**死亡复盘记录**：谁被杀 / 谁退出、退出码与信号、定性依据（内核日志或事件计数的位置）、根因分类（容量不足 / 配额过紧 / 应用行为异常 / 配置错误）、处置与回滚、巡检项。**退出码 137 必须配一份「谁发的信号」的说明**。

**巡检项**：有没有服务仍是无限上限、有没有服务长期贴着上限、组级事件计数有没有新增击杀、换页使用是否在增长、任务数与句柄水位是否超过基线的某个倍数、有没有僵尸堆积。

## 7. 行业常见做法

不同组织的规范差别很大，但方向一致：

- **默认有界**：新服务上线就带上限，而不是等出事再补；
- **按观测定参**：上限由峰值与安全系数决定，并随负载变化定期复核；
- **OOM 与崩溃需要复盘**：它们往往意味着配额与真实需求脱节，或应用存在异常增长；
- **限制与容量互补**：上限收窄故障域，容量提供余量；只做其中一件都会稳定地出问题；
- **停止语义要设计**：把「怎么被停下来」当作服务的一个功能来验收（可捕获的终止信号、可预期的收尾时间、覆盖整组的停止范围）。

这些方向的原始材料在 Google SRE 系列（容量规划与错误预算部分）、Kubernetes 官方文档（资源请求与限制、驱逐与 OOM 行为）以及内核 cgroup v2 文档里都有，可按自己的环境取舍。

## 8. 容器里的六个坑

1. **容器内的整机文件反映的是宿主**。容器的额度与用量在 cgroup 文件里。判断：容器内看到的整机总量与宿主一致，而与它的配额无关。
2. **页缓存计入容器**。容器读写文件产生的缓存算在它的额度里（可回收，但会推高当前用量）。判断：构成明细里文件页占大头；处置是看访问模式，不是简单加额度。
3. **共享内存目录默认很小**。共享内存类应用会在这里失败，报的是空间不足而不是内存不足。判断：查该目录的容量；处置是调大或改用文件/流式处理，并评估内存占用。
4. **页表与内核栈同样计入**。大内存、多线程进程的页表开销会占掉一部分额度。判断：构成明细里的内核对象相关项；处置是减少映射数量或线程数。
5. **「被 OOM 杀」只是一个标签**。要区分撞的是组配额还是整机水位：前者是配额问题，后者是容量或邻居问题。
6. **容器看到的 CPU 可用集合与可分配 NUMA 节点可能与宿主不同**（cgroup 收窄的是 `cpuset.cpus.effective` 与 `cpuset.mems`），但 **NUMA 节点数本身不会被隐藏**——`/sys/devices/system/node` 不在 cgroup 的虚拟化范围内，只有 lxcfs 这类工具会改写 `/sys`。按容器内视角推算容量会失真，容量规划要回到宿主视角。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 服务不设任何上限 | 单个服务即可拖垮整机；这是整机级故障最常见的成因 |
| 只设软上限就以为被保护了 | 软上限只节流；要挡住失控必须设硬上限 |
| 在登录会话的限制配置里改服务的限额 | 服务不经过登录流程，改动对它无效 |
| 只改配置文件就认为改完了 | 验收标准是进程实际生效的值与组接口文件里的值 |
| 用当前用量定上限 | 应该用**历史峰值**加安全系数；当前用量可能正好在低谷 |
| 照抄邻居服务的上限 | 并发模型与增长曲线不同，峰值也不同 |
| 批量给所有服务加上限 | 等于同时引入一批未知风险，出了问题无法归因 |
| 事后才去读组级事件计数 | 组目录随单元结束被回收；默认策略还可能把整个单元停掉 |
| 用调低被杀倾向代替隔离 | 那是在赌内核挑谁，不是划边界 |
| 增加上限后不留缺陷单 | 掩盖了泄漏或设计问题，直到整机天花板也被吃光 |

## 要点自测

**问：为什么说「限制线首先是可用性手段」？**
答：它的作用是把故障域收窄到一个服务内，避免单个服务耗尽整机资源导致全局不可用。判断一个上限定得好不好，看的是撞上它时坏掉的是不是只有它自己。

**问：一个服务报 `fork` 失败，你的判断顺序是什么？**
答：先看报错类型（资源暂时不可用 → 计数型上限；内存不足 → 容量或地址空间）→ 再看范围（整机、某个用户、某个组）→ 最后才决定改哪一层。禁止的第一步是直接调大某个上限。

**问：给一个服务定句柄上限的依据是什么？**
答：同一口径下实测的正常水位与峰值（含连接数与文件数），加安全系数；同时确认不超过内核给单进程设的硬顶、整机总量还有余量。上线后按新峰值复核。不能用「邻居是多少」来定。

**问：什么情况下「句柄数高」不需要处理？**
答：构成固定、长期稳定在高位不涨，且是设计使然（长连接服务）时，属于容量规划问题而不是泄漏；要做的可能是调上限与加水监控，而不是改程序。

**问：为什么复盘时常常读不到组级事件计数？**
答：组目录随单元结束被回收，而服务管理器的 `OOMPolicy=`（默认 `stop`）可能在组级 OOM 后把整个单元停掉。要在存活期间采集，或把单元配置成不被整体停掉。

**问：巡检发现一批服务没有上限，怎么排优先级？**
答：按「峰值用量 × 影响面」排序，先做核心链路与资源大户；每个服务先补一次只读基线，再分批改，每批留观察窗口与变更记录。

**第一反应不要做什么**：不要在登录会话的限制配置里改服务限额；不要用当前用量定上限；不要一次改完一批没有上限的服务；不要把「调低被杀倾向」当成隔离手段；不要在没有回滚命令的情况下改上限。

## 参考文档

- 内核文档 `Documentation/admin-guide/cgroup-v2.rst`：pids 与 memory 控制器的接口文件、事件计数、单一层级树与控制器委派规则。
- `man 5 systemd.resource-control`：任务数上限、内存软硬上限、CPU 配额与权重、组级 OOM 行为与相关属性的版本门控；用户态 OOM 处理组件的判据与默认值见 `man 5 oomd.conf` 与 `man 8 systemd-oomd.service`。
- `man 5 systemd.exec`、`man 5 systemd-system.conf`：进程资源限制属性与服务管理器默认值。
- `man 5 limits.conf`、`man 8 pam_limits`：登录会话限制的应用时机（与服务的区别）。
- `man 5 systemd.kill`、`man 5 systemd.service`：停止范围、等待上限、兜底强杀与重启策略（**默认值现场取**）。
- `man 5 proc_pid_limits`、`man 5 proc_sys_fs`、`man 5 proc_sys_kernel`、`man 5 proc_sys_vm`：`/proc/<pid>/limits`、`/proc/sys/fs/file-nr`、`/proc/sys/kernel/pid_max`、`/proc/sys/vm/max_map_count` 的字段口径（`man 5 proc` 只作 proc 文件系统的总览）。
- 行业材料：Google SRE 系列（容量规划与错误预算）、Kubernetes 官方文档（资源请求/限制、驱逐与 OOM 行为）。其中的阈值与流程要按自己的环境重新评估。
- 本节引用的 man 页与内核文档按**与目标机器同一主版本（当前基线 6.x）**取；路径与语义在版本间会变，所以凡涉及默认值与版本门控，以现场 `man`、`sysctl`、`systemctl show` 的实际输出为准。
