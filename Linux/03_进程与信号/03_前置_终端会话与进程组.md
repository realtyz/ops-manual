## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **归属有三层**：进程 → 进程组（PGID）→ 会话（SID）。`kill` 的负号语法打的是**进程组**，不是单个进程。
> - **控制终端（tty）是可以没有的**。`ps` 的 `tty` 列显示 `?` 表示这个进程没有控制终端——systemd 拉起的服务全是这样，这不是故障。
> - **终端断开时，内核给前台进程组发 `SIGHUP`**。这就是「SSH 一断脚本就死」的机制，也是 `nohup` 存在的全部理由。
> - **`nohup`/`&`/`disown`/`setsid`/`tmux` 只解决「别被终端带走」，不解决自启、重试、日志、资源上限**。真正把这些解决掉的是 systemd（阶段 8）。
> - **服务不需要 `nohup`**：它本来就没有控制终端，也不挂在你的 SSH 会话下——用 `nohup` 起关键服务是把问题从「会不会掉」换成「掉了没人知道」。

## 1. 三层归属：进程、进程组、会话

### 1.1 三个字段

```bash
ps -o pid,ppid,pgid,sid,tty,stat,cmd -p <pid>     # 验证：一条命令看清目标进程的全部归属信息
ps -eo pid,pgid,sid,tty,stat,comm | head -20      # 验证：整机的归属分布（注意很多行的 tty 是 ?）
```

| 层次 | 字段 | 一句话含义 | 由谁决定 |
| --- | --- | --- | --- |
| 进程 | `PID` | 哪个执行流 | `fork`/`clone` 时分配 |
| 进程组 | `PGID` | 一组可以「被一起发信号」的进程；管道 `a \| b` 的两侧通常在同一组 | `setpgid()`；作业控制下每个作业一组 |
| 会话 | `SID` | 一组进程组的集合，最多关联一个**控制终端**；登录一次通常就是一个会话 | `setsid()` |
| 控制终端 | `tty` | 这个进程的输入输出挂在哪个终端上（`?` 表示没有） | 会话首进程打开终端时建立 |

`ps` 的 `STAT` 列还带两个和归属有关的后缀：`s` 表示它是**会话首进程**（session leader），`+` 表示它位于**前台进程组**。所以登录 shell 常见的是 `Ss` 或 `S+`。

### 1.2 为什么要分这两层

因为「一次操作影响一组进程」是刚需：

- 你在终端里敲 `Ctrl+C`，希望的是**停掉整条管道**（`tail -f access.log | grep ERROR`），而不是只停 `tail`；
- 你在 shell 里 `kill %1`，希望的是**清掉这个作业的全部子进程**；
- 终端断开时，希望**这一组前台进程一起收到 `SIGHUP`**，而不是同时残留几十个半死不活的进程。

进程组就是「最小的一次性操作单位」，会话是「一次登录的边界」。

## 2. 作业控制：`Ctrl+Z`、`jobs`、`%1`

交互式 shell 打开作业控制后，每启动一条命令会给它分配一个进程组，并把终端交给它（前台）。于是有了这套操作：

| 操作 | 发生了什么 | 进程状态 |
| --- | --- | --- |
| `Ctrl+C` | 前台进程组收到 `SIGINT` | 通常终止 |
| `Ctrl+Z` | 前台进程组收到 `SIGTSTP` | 进入 `T`（停止），仍占着内存与句柄 |
| `jobs` | 列出当前 shell 的作业与它们的编号 | — |
| `fg %1` / `bg %1` | 把作业切到前台 / 放到后台继续 | `T` → `R`/`S` |
| `kill %1` | 给这个作业的进程组发信号 | 取决于信号 |

```bash
sleep 600                                # 起一个前台任务，然后按 Ctrl+Z
jobs -l                                  # 验证：作业号、PID、进程组 ID 与状态
bg %1                                    # 验证：任务在后台继续（状态从 T 变回 S）
ps -o pid,pgid,sid,tty,stat,cmd -p <pid> # 验证：它仍属于当前会话与终端，只是不再占前台
kill -STOP <pid>; ps -o stat,cmd -p <pid>  # 验证：SIGSTOP 也能造出 T 状态（但不可被捕获，与 Ctrl+Z 的 SIGTSTP 不同）
kill -CONT <pid>                         # 验证：SIGCONT 让它继续跑
kill %1                                  # 验证：按作业号发信号（默认 TERM）
```

> [!important] `kill -9 <pid>` 杀不掉的「子进程」，通常要找进程组
> `kill <pid>` 只对一个进程生效。一个父进程被打死，它的子进程不一定跟着走（真正的连带清理要靠进程组、会话或 cgroup）。所以清一串残留进程时，常用的是负号语法：
> ```bash
> ps -o pid,pgid,stat,cmd -p <pid>            # 验证：先拿到它的 PGID
> kill -TERM -<pgid>                          # 验证：给整个进程组发 TERM（负号即「进程组」）
> ```
> **发之前一定要 `ps -o pgid` 确认这个组里都是你要清掉的进程**——进程组里可能还有别的作业，打错了就是误伤。

## 3. 终端断开时谁被带走

### 3.1 机制

终端（或 SSH 连接）断开时，内核会向这个终端的**前台进程组**发 `SIGHUP`（紧接着还会补一个 `SIGCONT`，让被停住的进程有机会处理它）；`SIGHUP` 的默认动作是**终止进程**。于是「SSH 一断，前台跑的脚本就死了」。

```bash
ps -o pid,ppid,pgid,sid,tty,stat,cmd -p <pid>   # 验证：目标进程的 tty 是不是 pts/N（有终端）
echo $PPID; ps -o sid= -p $$                    # 验证：当前 shell 所在会话；会话首进程通常是 sshd 起的登录 shell
loginctl list-sessions                          # 验证：本机有哪些登录会话（systemd 系统上）
loginctl show-session <ID> -p TTY -p Leader -p State   # 验证：这个会话的终端、首进程与会话状态
```

### 3.2 六种「让它活下来」的手段，以及它们各自的边界

| 手段 | 做了什么 | 解决什么 | **没解决什么** |
| --- | --- | --- | --- |
| `cmd &` | 放到后台 | 不阻塞当前终端 | 仍然会被断开时的 `SIGHUP` 带走 |
| `nohup cmd &` | 让进程**忽略 `SIGHUP`**，并把输出重定向到 `nohup.out`（终端输出时） | 终端断开时它不再被 `SIGHUP` 带走 | 自启、失败重试、日志轮转、资源上限 |
| `disown -h %1` | 标记该作业**不接收 `SIGHUP`**（不加 `-h` 则是把它从作业表里移除） | shell 退出时不再给它发 `SIGHUP` | 同上；进程仍然只是一个「没人管的后台进程」 |
| `setsid cmd` | 新开一个会话，**脱离控制终端** | 彻底与终端解耦 | 同上；而且它的输出不再属于任何终端 |
| `tmux` / `screen` | 在服务器上保留一个**持久的伪终端**，你的 SSH 只是「连上去看」 | 会话可重连、可多人共享 | 服务器重启就没了；资源上限、依赖顺序仍要自己管 |
| `systemd-run` / 写成 unit | 交给 **PID 1** 管理，自带日志、重启策略、资源限制 | 上面所有问题 | 需要按 unit 规范写清楚（阶段 8） |

两个必须说清的边界：

1. **`nohup` 的 stdout 会累积在 `nohup.out`**，长期任务不轮转就会写满磁盘；`setsid` 之后连这个都没有，输出直接丢失；
2. **「不掉」不等于「可靠」**：进程崩了没人重启、机器重启不会自启、跑飞了没有上限。生产上的长任务应当走 systemd（见第 4 节的生产动作）。

## 4. 生产动作：把一个「跑在 SSH 里」的长任务交出去（S2）

> [!example]+ 生产动作：把一条 6 小时的命令从 SSH 会话里搬走
> **什么时候用**：备份、数据导出、批量清理这类跑很久、又不想被终端断线带走的任务。
>
> **动手前确认**：
> 1. 这条命令是否**幂等**、失败了能不能重跑；
> 2. 它的输出要落到哪里（日志文件还是 journal）；
> 3. 它会不会吃满 CPU/内存/磁盘——如果会，先想好上限（`MemoryMax=`、`CPUQuota=`）；
> 4. 生产机上**不要**用 `nohup` 长期养一个业务任务，正式做法是写成 unit（阶段 8）。
>
> **怎么做**（以实验机上的临时单元为例）：
> ```bash
> systemd-run --unit=lab-longjob --property=MemoryMax=256M --property=CPUQuota=50% \
>   /usr/local/bin/backup.sh                                 # 验证：返回「Running as unit: lab-longjob.service」
> systemctl status lab-longjob --no-pager                    # 验证：单元处于 active；Process 段能看到真实 PID
> journalctl -u lab-longjob -f                               # 验证：输出进 journal（不用自己管日志文件）
> ps -o pid,ppid,tty,pgid,sid,stat,cmd -p $(systemctl show -p MainPID --value lab-longjob)
>                                                            # 验证：PPID 是 1、tty 是 ?——它已经不在你的 SSH 会话里
> systemctl stop lab-longjob                                 # 验证：按 unit 停止（默认停整个 cgroup，子进程一起清）
> ```
>
> **怎么验证**：断开 SSH 再连回来，`systemctl status` 仍是 active；`systemctl show -p MainPID` 的进程 `tty` 为 `?`、`PPID` 为 1。
>
> **怎么退回去**：`systemctl stop lab-longjob`；如果单元卡在 failed，`systemctl reset-failed lab-longjob`。
>
> **注意**：`systemd-run` 起的临时单元**重启后就没了**，也不会自启。要长期运行，按阶段 8 写正式 unit 并 `systemctl enable --now`。

## 5. 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 用 `nohup ... &` 养业务服务 | 无自启、无重试、无资源上限，日志堆在 `nohup.out`；崩溃后没人知道 |
| 以为 `&` 之后进程就安全了 | 终端断开时它仍会收到 `SIGHUP`（除非 `nohup`/`disown`/`setsid`） |
| 以为 `disown` 等于「守护进程化」 | 它只是把作业从 shell 的作业表移走，进程仍无自启、无重试、无监控 |
| 「SSH 一断服务就死，说明服务器有问题」 | 那是会话与终端的设计行为；服务应该由 systemd 拉起，与你的 SSH 会话无关 |
| `kill <pid>` 之后发现子进程还在 | 只杀了单个进程；要连带清理用进程组（`kill -TERM -<pgid>`）或 cgroup（`systemctl stop`） |
| 看到 `tty` 是 `?` 就以为是异常 | 没有控制终端是**正常状态**：systemd 服务、内核线程、`setsid` 后的进程都是 `?` |
| 以为 `T` 状态的进程「必须 `SIGCONT` 才能处理信号」 | 普通信号（如 `SIGTERM`）确实会一直挂着，要 `SIGCONT` 之后才处理；但 **`SIGKILL` 能直接终止一个停止的进程**。先 `SIGCONT` 的目的是让它有机会优雅收尾，不是为了「杀得掉」 |
| 在脚本里依赖 `jobs`/`%1` 的作业号 | 作业控制是**交互式 shell** 的功能，非交互脚本里没有作业表，`%1` 不成立 |

## 6. 决策练习

> [!question]- 场景：你在 SSH 会话里发现一个数据导出脚本要跑 6 小时，但你的会话 30 分钟后会被审计系统强制断开
> 你会怎么安排这个任务？
> A. `nohup ./export.sh &` 然后断开，明天来看
> B. `tmux new -s export` 里跑，或者用 `systemd-run --unit=export-job ./export.sh` 交出去；跑之前确认输出落点、失败可见性与资源上限
> C. 用 `Ctrl+Z` 挂起，明天连回来 `fg` 继续跑
>
> **答案：B。**
> A 能活下来，但「跑完没有」「失败没有」「吃了多少资源」全靠第二天回去看，而且一行日志都不在 journal 里；对一个 6 小时的任务来说，这是把可靠性交给运气。
> C 完全不成立：`SIGTSTP` 只暂停进程；SSH 一断，登录 shell 退出时会对作业发 `SIGHUP`（并补一个 `SIGCONT` 让挂起的作业能被处理），它照样会死；而且挂起期间占着的内存与句柄都不释放。
> B 是正解：`tmux` 解决「会话可重连」，`systemd-run` 在此基础上还解决了日志（进 journal）、资源上限与统一停止；生产上则应写成正式 unit，加上 `Restart=` 与监控。

## 7. 要点自测

> [!question]- 进程组（PGID）和会话（SID）分别解决什么问题？
> - 进程组是「一次操作影响一组进程」的最小单位：`kill -<pgid>`、终端的前台作业切换都基于它。
> - 会话是「一次登录的边界」，最多关联一个控制终端；终端断开时的 `SIGHUP` 与会话绑定。
> - **第一反应不要是什么**：不要以为「父子关系」就够用——父子关系决定谁回收退出状态，进程组/会话决定信号的投递范围，两套体系都要看。

> [!question]- 为什么 systemd 拉起的服务不需要 `nohup`？
> - 它没有控制终端（`tty` 列为 `?`），也不属于你的 SSH 会话；终端断开与它无关。
> - 它的日志默认进 journald，停止与重启由 systemd 管理（默认停整个 cgroup，子进程一起清）。
> - **第一反应不要是什么**：不要为了让服务「不掉」而去包一层 `nohup`——那只会让你失去 systemd 的状态可见性与重启策略。

> [!question]- `nohup`、`setsid`、`tmux` 三者的差别是什么？
> - `nohup`：让进程忽略 `SIGHUP`，输出落到 `nohup.out`；进程仍在原会话里（只是不再被信号带走）。
> - `setsid`：新建会话、脱离控制终端，彻底与终端解耦，但输出也不再属于任何终端。
> - `tmux`：在服务器端保留一个持久伪终端，你的 SSH 断开后它仍在运行、还能重连。
> - **第一反应不要是什么**：不要把它们当成「服务托管方案」——三者都不提供自启、重试、资源上限与集中日志。
