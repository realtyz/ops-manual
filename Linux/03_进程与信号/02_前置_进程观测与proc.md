## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **`/proc` 是内核的窗口，不是磁盘上的文件**。读 `/proc/<pid>/status` 等于当场问内核「这个进程现在什么样」，**每次读到的是瞬时值**。
> - **四个文件回答四个不同的问题**：`status`（它是什么状态、占多少内存）、`limits`（它的上限是多少）、`wchan`+`stack`（它卡在内核的哪个位置）、`fd/`（它开着哪些文件与连接）。
> - **`ps` 的 `%CPU` 是「生命周期平均值」，不是「此刻占用」**。要看此刻，用 `top`、`pidstat 1` 这类需要**两次采样**的工具。
> - **`top` 的第一次刷新不可信**。它需要前后两次采样才能算出百分比；脚本里要用 `top -b -n2` 取第二次。
> - **快照必须带上下文**：只抄一个数字（比如「内存 3.2G」）没有意义，要连 PID、时间、口径（RSS 还是 VSZ）一起留档，才能在下一次对比。

## 1. 工具分工：一个问题配一个工具

先把「要问什么」和「用哪个工具」对上。新人最容易犯的错是手上有十个工具，却不知道哪个回答哪个问题。

| 你要回答的问题 | 首选工具 | 为什么 |
| --- | --- | --- |
| 现在谁在吃 CPU / 内存 | `top`、`htop` | 交互式实时视图，需要**两次采样**才准 |
| 某个进程此刻吃多少 CPU | `pidstat -p <pid> 1` | 按秒采样，输出的是**区间值**，最适合脚本与留档 |
| 一批进程的静态清单与父子关系 | `ps --forest`、`pstree -p` | 一次性快照，适合贴进工单 |
| 某进程的内存分布细节 | `/proc/<pid>/status`、`/proc/<pid>/smaps_rollup` | 能看到 RSS、Swap、页表等分项 |
| 某进程的上限是多少 | `/proc/<pid>/limits` | 进程**实际生效**的软/硬限制（唯一权威） |
| 某进程卡在哪 | `/proc/<pid>/wchan`、`/proc/<pid>/stack` | 内核态等待点与调用栈（子笔记 05 的主战场） |
| 某进程开着哪些文件/连接 | `ls -l /proc/<pid>/fd`、`lsof -p <pid>` | 句柄泄漏的定位入口（子笔记 09） |
| 某进程属于哪个 cgroup | `/proc/<pid>/cgroup`、`systemctl status` | 判断它的资源上限来自哪里（子笔记 11） |
| 这个进程是谁拉起来的 | `systemctl status <pid>`、`ps -o ppid=` | 服务进程看 unit，普通进程看父进程 |

## 2. `/proc/<pid>/` 一本通

`/proc/<pid>/` 下的每个文件都是一个小接口。下表只列排障真正会用的，**遇到不认识的先 `cat` 一下再查 `man 5 proc`**：

| 文件 | 内容 | 典型用法 |
| --- | --- | --- |
| `cmdline` | 启动命令（参数之间用 `\0` 分隔） | `cat` 出来会连成一行，用 `tr '\0' ' '` 还原 |
| `comm` | 进程名（最多 15 字符） | `top`/`ps` 的 `COMMAND` 列取的就是它 |
| `status` | 可读性最好的状态汇总（State、Threads、VmRSS、信号掩码…） | 第一眼看状态与内存 |
| `stat` | 机器可读的状态（含 PPID、优先级、CPU 时间） | 脚本解析用 |
| `limits` | 软/硬限制的完整列表 | 判断「上限到底是多少」的**唯一**依据 |
| `cgroup` | 所属 cgroup 路径 | 判断资源限制来自哪一层 |
| `wchan` | 正在哪个内核函数上等待 | `D` 状态的第一手证据；进程在跑时是 `0` |
| `stack` | 内核态调用栈 | 需要 root 且内核开启栈回溯；比 `wchan` 更详细 |
| `io` | 读写字节数（`read_bytes`、`write_bytes` 等） | 判断「谁在写盘」；通常需要属主或 root 才能读 |
| `fd/` | 打开的文件描述符（符号链接指向真实对象） | 数与内容就是句柄泄漏的证据 |
| `fdinfo/` | 每个 fd 的详细信息（偏移、flags） | 需要深挖时用 |
| `environ` | 启动时的环境变量（`\0` 分隔） | 确认服务拿到的是哪套环境（注意可能含密钥） |
| `cwd`、`exe`、`root` | 工作目录 / 可执行文件 / 根目录 | `ls -l` 看真实路径，常用于判断「是不是被替换过的二进制」 |
| `task/<tid>/` | 每个线程的独立目录 | 线程级排查（`status`、`stack` 都能单独读） |
| `oom_score`、`oom_score_adj` | OOM 打分与人工调整值 | 判断「为什么是它被杀」（子笔记 07） |
| `sched`、`schedstat` | 调度相关统计 | 需要深挖上下文切换时用 |

`/proc/self/` 是「当前正在读它的那个进程」，所以下面这条能一行看清自己：

```bash
cat /proc/self/status | head -8          # 验证：Self 就是执行 cat 的这个进程（Tgid 与 Pid 相同）
```

### 2.1 `status` 里值得看的几行

```bash
cat /proc/<pid>/status | grep -E '^(Name|State|Tgid|Pid|PPid|Threads|VmRSS|VmSwap|voluntary)' 
                                         # 验证：名字、状态、线程组、线程数、内存、上下文切换
cat /proc/<pid>/status | grep -A3 'SigQ' # 验证：挂起信号队列（SigQ 是「已用/上限」，SigPnd/ShdPnd 是挂起位图）
```

| 字段 | 读法 |
| --- | --- |
| `State` | `R/S/D/T/t/Z/I` 之一，是内核状态机的原始值（含义见子笔记 05） |
| `Tgid` / `Pid` | 线程组 ID 与线程 ID；主线程两者相同，子线程不同 |
| `Threads` | 这个进程当前有多少个线程 |
| `VmRSS` | 驻留内存（真正占的物理内存），**整组共享** |
| `VmSize` | 虚拟地址空间大小（`VSZ`）；**包含尚未真正分配的内存，不能当作内存占用看**（深水区在阶段 4） |
| `VmSwap` | 被换出的内存；Swap 用得多时，服务延迟会莫名变高 |
| `voluntary_ctxt_switches` | 主动让出 CPU 的次数（在等事件）；**只有和 `nonvoluntary_ctxt_switches` 对比才有意义**（见子笔记 05） |
| `nonvoluntary_ctxt_switches` | 被抢占而让出 CPU 的次数（在等 CPU）；增长快说明它在排队 |

### 2.2 「两次采样」是这条工具链的核心纪律

进程的 CPU、IO、上下文切换都是**速率**，速率必须有两个时间点。所以：

```bash
pidstat -p <pid> 1 5                     # 验证：每秒一行，共 5 行——这是区间值，可直接留档
top -b -n2 -d 1 | tail -n +8             # 验证：脚本里取第二次输出，第一次的 %CPU 是自启动以来的平均值
cat /proc/<pid>/io                       # 验证：累计值；隔 10 秒再读一次，两个数相减才是速率
vmstat 1 5                               # 验证：整机视角的 r/b/si/so/us/sy/wa，与进程视角对照
```

## 3. 一份能对比的「进程快照」

单看一个数字说明不了问题，**能对比的快照**才有价值。下面是接手一台机器时最省事的采集方式（全部只读，**生产机上可以做**）：

```bash
date; hostname; uptime                                    # 验证：时间基线与负载（时间不对，后面所有证据都失效）
uname -r; systemd --version | head -1                     # 验证：内核与 systemd 版本（决定默认值）
stat -fc %T /sys/fs/cgroup                                # 验证：cgroup v2（cgroup2fs）还是 v1
ps -eo pid,ppid,user,stat,pcpu,pmem,etimes,time,comm --sort=-pcpu | head -20
                                                          # 验证：CPU Top 20（etimes=运行时长，time=累计 CPU 时间）
ps -eo pid,user,nlwp,rss,comm --sort=-rss | head -15      # 验证：内存 Top 15 与各自的线程数
free -m; vmstat 1 5                                       # 验证：整机内存与 CPU 的对照视角
df -h / /var; df -i / /var                                # 验证：空间与 inode（进程写不进去时这两个都要看）
systemctl --failed --no-pager                             # 验证：有没有失败的服务单元（服务问题先看这里）
journalctl -p warning -b --no-pager | tail -30            # 验证：本次启动的告警与错误
```

两条使用纪律：

1. **一组快照必须同时取**。CPU、内存、磁盘、日志要落在同一个时间窗口里，否则拼不出因果——「先看 CPU 再看磁盘」得到的是两个时刻的两件事。
2. **留档要写清口径**。`ps` 的 `%CPU` 是生命周期平均值、`top` 是区间值、`pidstat` 也是区间值；三个数不一样**不是工具坏了**，是口径不同。

## 4. 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 「`ps aux` 里 `%CPU` 是 300%，机器要炸了」 | 多线程进程的百分比可超过 100%（每核 100% 累加）；而且它是**生命周期平均值**，不能当瞬时值用 |
| 用 `top` 第一屏的数字做结论 | 第一次刷新没有前一时间点，`%CPU` 由内核启动以来的平均值推算，**必须先等到第二次刷新** |
| 「`/proc/<pid>/status` 里的内存是某个线程的」 | `VmRSS` 是整组共享的；线程级内存要读 `/proc/<pid>/task/<tid>/status` 并注意仍会重复计算共享页 |
| 「`VSZ` 好几个 G，肯定是内存泄漏」 | `VSZ`/`VmSize` 是虚拟地址空间，包含未真正分配的映射（预留、mmap、线程栈）；判断实际占用看 `VmRSS`，判断共享部分可以用 `/proc/<pid>/smaps_rollup` |
| 「读 `/proc/<pid>/io` 报错，是内核不支持」 | 多数情况是权限：该文件通常只允许属主或 root 读；换成 `sudo` 或换用 `pidstat -d -p <pid> 1` |
| 拿 `ps -eo pcpu` 判断「此刻谁在吃 CPU」 | 它同样是生命周期平均值；刚启动的进程会显示很高的百分比（因为分母 `etimes` 很小） |
| 「`lsof` 看不到，说明没有打开」 | `lsof` 非 root 时看不到别人的进程；容器/命名空间里的进程还要在对应命名空间里看 |
| 只看一次数字就写进结论 | 速率类指标必须两次采样；快照要与「正常时的基线」对比才有意义 |
| 记录时只写 PID，不写时间与进程名 | PID 会复用（`pid_max` 很大但仍会回收），只写数字的证据链无法复现 |

## 5. 决策练习

> [!question]- 场景：一个服务「每天下午三点左右变慢」，其他时间正常。你在它变慢时能用 SSH 登录，但只有 5 分钟窗口
> 你打算怎么取证据？
> A. 先 `top` 看一眼，再决定下一步；如果看不出问题就重启
> B. 直接上 `strace -p <pid>`，挂上去看它卡在哪个系统调用
> C. 先跑一组同时刻的快照（`date`/`uptime`/`ps -eo pid,stat,pcpu,pmem,etimes,comm --sort=-pcpu`/`ps -eo pid,rss,comm --sort=-rss`/`vmstat 1 5`/`systemctl --failed`/`journalctl -p warning`），全部存成文件；同时记下服务 PID 与 `etimes`
>
> **答案：C。**
> A 的「先看一眼」在 5 分钟窗口里几乎必然什么都没看到，重启又会把现场清掉。
> B 是第二步：`strace` 会让被跟踪进程明显变慢，在生产机上贸然长时间挂载有业务风险，而且在没有快照对照的情况下，你也说不清「现在这个样子」算不算异常。
> C 是正确顺序：先**建立可比对的基线**（把同一个时间窗口的 CPU、内存、磁盘、日志一起留下），再决定要不要用 `strace`、`perf` 这类会加扰动的工具下钻。变慢是「趋势」，而趋势必须有多个时间点的数据。

## 6. 要点自测

> [!question]- 想知道一个进程「卡在内核的哪里」，你会看哪几个文件？
> - `wchan`（等待点，进程在跑时是 `0`）和 `stack`（内核态调用栈，需要 root）；再配合 `status` 的 `State`。
> - 如果是「为什么没吃到 CPU」，看 `sched`/`schedstat` 与 `voluntary_ctxt_switches` 的变化。
> - **第一反应不要是什么**：不要只看 `D`/`S` 这个字母就下结论——字母只说明「在哪一类等待」，不说明「在等谁」。

> [!question]- `ps`、`top`、`pidstat` 给出的 CPU 百分比为什么不一样？
> - `ps` 的 `%CPU` = 累计 CPU 时间 ÷ 进程已运行时长，是**生命周期平均值**；
> - `top` 是**区间值**（第一次刷新例外），`pidstat 1` 明确给出每秒的区间值；
> - 三者口径不同，结论必须写清用的哪个工具、哪个时间窗口。
> - **第一反应不要是什么**：不要用 `ps` 的百分比去判断「此刻有没有热点」，那会把长期平均值当成瞬时值。

> [!question]- 一份可以拿来对比的进程快照，至少要包含什么？
> - 时间与主机标识（否则跨机跨时可对不上）、内核与 systemd 版本、cgroup 版本；
> - 同时刻的 CPU Top、内存 Top、整机资源（`free`/`vmstat`/`df`）、失败单元与告警日志；
> - 目标进程的 PID、进程名、运行时长（`etimes`）与它的 `limits`。
> - **第一反应不要是什么**：不要只截一张 `top` 图就当成证据——它没有时间上下文，也没有整机视角。
