## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **进程数有四条独立上限**：`kernel.pid_max`（PID 编号）、`kernel.threads-max`（整机 task 数）、`RLIMIT_NPROC`（**按 real UID**）、cgroup 的 `pids.max`（按组）。**报错文案相似，判据完全不同。**
> - **句柄有两条**：单进程的 `RLIMIT_NOFILE`（软/硬限制）与整机的 `fs.file-max`；`fs.nr_open` 是单进程 fd 上限的**硬顶**。
> - **`fork` 失败先看报错类型**：`EAGAIN`（`Resource temporarily unavailable`）指向限制，`ENOMEM`（`Cannot allocate memory`）指向内存。
> - **句柄耗尽未必是泄漏**：每个连接一个 fd、每个日志文件一个 fd，本来就可能是设计使然。先看 `/proc/<pid>/fd` 里到底是套接字还是普通文件。
> - **止血与定位的顺序是可以选的，但取证必须在前**：重启进程能立刻恢复句柄，但会丢掉现场——先留档，再重启。

## 1. 进程数：四条上限，四种判据

| 上限 | 在哪看 | 语义 | 撞上之后 |
| --- | --- | --- | --- |
| `kernel.pid_max` | `sysctl kernel.pid_max` | PID 编号上限（分配不出新 PID 就无法创建进程） | `fork` 返回 `EAGAIN`，内核日志可能提示 PID 耗尽 |
| `kernel.threads-max` | `sysctl kernel.threads-max` | 全系统 task 总数上限 | 创建线程失败，报 `EAGAIN` 或 `Cannot allocate memory` |
| `RLIMIT_NPROC` | `ulimit -u`、`/proc/<pid>/limits` 的 `Max processes` | **同一 real UID** 的进程/线程数 | 该用户的 `fork` 失败（**其他用户不受影响**，这是关键特征） |
| cgroup `pids.max` | `/sys/fs/cgroup/.../pids.max` | 整组的 task 数（容器里通常就是它） | `fork` 失败；内核日志出现 `cgroup: fork rejected by pids controller` |

> [!important] 不要背 `pid_max` 的数字
> 现代发行版的值往往**不是内核默认值**，而是 systemd 通过 `/usr/lib/sysctl.d/50-pid-max.conf` 抬高的（用于降低 PID 复用带来的风险）。**只能用 `sysctl kernel.pid_max` 看本机实际值**；`threads-max` 同理，由内核按内存规模推算。

两条容易误判的规则：

1. **`RLIMIT_NPROC` 按 real UID 计数**：一台机器上多个服务用同一个用户跑，会互相抢额度；
2. **特权进程通常不受 `RLIMIT_NPROC` 约束**（root、`CAP_SYS_RESOURCE`）：所以容器里以 root 运行的程序撞到的多半是 cgroup 的 `pids.max`，不是 `ulimit -u`。

## 2. fork 风暴：现场与定位

「进程数被打满」最常见的来源是某个程序在**批量创建进程**（错误的重试逻辑、失控的 worker 池、脚本里的循环 `&`）。它的现场很有特征：

```bash
cat /proc/loadavg                    # 验证：最后一列是「最近分配的 PID」，连看两次即可估算消耗速率
ps -e --no-headers | wc -l           # 验证：当前进程总数（默认按进程统计）
ps -eLf --no-headers | wc -l         # 验证：当前 task 总数（含线程，这才是调度实体数量）
ps -eo user,ppid,comm --no-headers | sort | uniq -c | sort -rn | head -20
                                     # 验证：谁在批量创建（按用户 / 父进程 / 命令名聚合）
ps -eo pid,ppid,etime,cmd --sort=start_time | tail -20   # 验证：最新创建的进程长什么样
dmesg -T | grep -i -E 'fork|pids' | tail -20             # 验证：内核是否记录了 cgroup 拒绝 fork
vmstat 1 5                           # 验证：sy（内核态 CPU）与 cs（上下文切换）是否同步飙升
```

**判据**：`/proc/loadavg` 最后一列两次取值相差大、`ps -e | wc -l` 快速上升、`sy` 与 `cs` 高——三者同时出现，基本可以定性为创建风暴。

## 3. 句柄耗尽：先看构成，再谈泄漏

```bash
cat /proc/sys/fs/file-nr             # 验证：已分配 / 未使用 / 系统上限（第一个数接近第三个即整机吃紧；第二个字段在现代内核上恒为 0）
cat /proc/<pid>/limits | grep -i 'open files'
                                     # 验证：进程实际生效的 fd 软/硬限制
ls /proc/<pid>/fd | wc -l            # 验证：当前打开的 fd 数（定位泄漏的第一刀）
ls -l /proc/<pid>/fd | awk '{print $NF}' | sort | uniq -c | sort -rn | head
                                     # 验证：把 fd 按目标归类，一眼看出是套接字还是普通文件
lsof -p <pid> | wc -l                # 验证：同上，但能看到 fd 指向的完整对象（需要权限）
```

三步判断法：

1. **是整机还是单进程**：`file-nr` 到顶是整机问题，`/proc/<pid>/fd` 到顶是单进程问题；
2. **是套接字还是文件**：大量 `socket` 多指向连接未关闭/连接池无上限，大量普通文件多指向日志或临时文件；
3. **是上涨还是平稳**：**长期单调上涨**才是泄漏，稳定在高位只说明容量需要规划。

> [!warning] 老的 `select()` 程序有个历史坑
> 用 `select()` 的旧程序受 `FD_SETSIZE`（通常编译期固定为 1024）限制，**即使把 `ulimit -n` 调到很大也没用**。这类程序需要改成 `poll`/`epoll`，或拆成多个进程。判断方法是看它是不是「无论上限多大，都在 1024 附近出问题」。

## 4. 生产动作：一次耗尽的止血与恢复（S6）

> [!example]+ 生产动作：服务句柄耗尽（或进程数打满）的处置
> **什么时候用**：服务报 `too many open files` / `fork: Resource temporarily unavailable`，业务出现偶发失败。
>
> **动手前确认**：
> 1. **先取证**（这一步不能省）：用量多少、构成如何、从什么时候开始涨；
> 2. 判断影响面：是单实例还是全集群（是代码问题还是容量问题）；
> 3. 想清楚「止血手段」和「定位手段」分别是什么，以及止血会丢掉哪些证据。
>
> **怎么做（取证 → 止血 → 定位 → 长期修复）**：
> ```bash
> date; hostname; ps -o pid,ppid,etime,cmd -p <pid>        # 验证：时间基线与进程信息
> cat /proc/<pid>/limits | grep -i -E 'open files|processes'   # 验证：进程实际生效的上限
> ls -l /proc/<pid>/fd | awk '{print $NF}' | sort | uniq -c | sort -rn | head -20 > /tmp/fd-$(date +%F-%H%M).txt
>                                                          # 验证：fd 构成留档（这是定位泄漏的唯一线索）
> cat /proc/sys/fs/file-nr; cat /proc/loadavg               # 验证：整机句柄与 PID 消耗情况
> ```
> **止血（按侵入性从小到大）**：
> 1. 若确认是容量不足且无泄漏 → 按子笔记 08 在**正确的一层**提高上限并重启服务（有业务影响，需窗口）；
> 2. 若是泄漏 → 重启进程/滚动重启实例可立即回收句柄，但**必须在重启前完成上面那组留档**；
> 3. 若是整机 `file-max` 到顶 → 先确认是哪几个进程在吃，再决定扩容还是限流（重启整机是最后手段）。
> **怎么验证**：句柄数回落到基线、业务报错消失、并且**监控里加上了「句柄数 / 上限」的水位项**。
> **怎么退回去**：上限类改动回滚见子笔记 08；进程重启类操作没有回滚，只能靠前面的留档支撑复盘。
> **收尾（S8）**：写一段 Runbook 片段——现象、证据、根因、止血动作、回滚、巡检项（例如「句柄水位 > 70% 告警」）。

## 5. 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 「起不了进程就加大 `ulimit -u`」 | 要分清是 `pid_max`、`threads-max`、`RLIMIT_NPROC` 还是 `pids.max`；改错一层完全无效 |
| 用 `ps aux \| wc -l` 统计进程数 | 口径不对（按进程而非 task），而且 `aux` 默认**不显示线程**；用 `ps -e`/`ps -eLf` 或 cgroup 的 `pids.current` |
| 「句柄涨了就是泄漏」 | 可能是设计使然（连接数、日志文件数）；要看 fd 构成与**是否单调上涨** |
| 先把上限调到一百万，问题就消失了 | 掩盖泄漏，直到某天连整机 `file-max` 也被吃光；扩容的同时必须留缺陷单 |
| 重启进程前不取证 | 句柄构成、增长曲线、当时的连接状态全部丢失，只剩一句「重启后好了」 |
| 只在单机上扩容做修复 | 集群里同样的代码同样会涨；要么统一扩容，要么修应用 |
| 忽略 `fs.nr_open` 这一层 | `LimitNOFILE=` 写得比它大，实际仍会被截断 |
| 忽略容器内的 `ulimit` | 容器内 `ulimit` 由运行时设定，改容器内文件没有持久意义，重启容器即失效 |

## 6. 决策练习

> [!question]- 场景：某服务每小时报几次「偶发失败」，日志里有 `Resource temporarily unavailable`；`/proc/loadavg` 的最后一列在 5 分钟内从 12000 跳到 45000
> 你的处理顺序是什么？
> A. 先把 `kernel.pid_max` 调大，让 PID 不再耗尽
> B. 先定位是谁在批量创建：按父进程/命令名聚合 `ps`，同时看内核日志有没有 `fork rejected by pids controller`，确认是应用 bug 还是正常业务量；止血优先选择「限制创建源」（限流/停掉异常实例），而不是放宽全局上限
> C. 直接重启那台机器，PID 会全部回收
>
> **答案：B。**
> A 会掩盖问题：PID 消耗速率没有变化，调大上限只是让它晚一点再撞墙，而且整机上限的改动影响所有服务。
> C 是最差的选择：重启会清掉现场（进程树、父进程关系、内核日志上下文），而且几分钟后同样的事情会重演。
> B 是正解：**先分类（哪个上限）→ 再定位创建源 → 判断是 bug 还是容量 → 优先止损在源头**。这类问题的根因几乎总在应用侧（重试逻辑、worker 扩缩容失控、脚本循环 `&`）。

## 7. 要点自测

> [!question]- 机器进程数到上限会发生什么？怎么快速定位是谁在创建进程？
> - 现象：`fork: Resource temporarily unavailable`（`EAGAIN`）；cgroup 场景下内核日志会有 `cgroup: fork rejected by pids controller`；业务表现为「偶发无法接收新连接」。
> - 分层判断：整机看 `kernel.pid_max`、`kernel.threads-max`；按 UID 看 `ulimit -u`；按组看 `pids.current`/`pids.max`。
> - 定位创建者：`/proc/loadavg` 最后一列连看两次算速率；`ps -eo user,ppid,comm | sort | uniq -c` 找聚合源头；`pidstat` / `execsnoop` 追到具体父进程。
> - **第一反应不要是什么**：不要只调大 `ulimit -u`（可能改错层），也不要先杀进程——先留下「谁在批量创建」的证据。

> [!question]- `too many open files` 的定位顺序是什么？
> - 定位进程：`/proc/sys/fs/file-nr`（整机）与 `ls /proc/<pid>/fd | wc -l`（进程）。
> - 看构成：`socket` 还是普通文件，用 `ls -l /proc/<pid>/fd` 归类；判断是否单调上涨。
> - 确认限制链：`/proc/<pid>/limits`、`fs.nr_open`、`fs.file-max`、unit 的 `LimitNOFILE=`。
> - **第一反应不要是什么**：不要直接调到一百万，也不要忽略 `select()`/`FD_SETSIZE` 这类程序侧的天花板。

> [!question]- 打满之后，先止血还是先定位？
> - 先**取证**（这一点没有选择余地）：上限值、用量、构成、时间线。
> - 再按影响面决定：业务已经受损就止血（扩上限或滚动重启），业务尚可就先定位；止血手段本身要能解释给复盘听。
> - **第一反应不要是什么**：不要在没有任何留档的情况下重启——「重启后好了」不是结论，是问题的暂停。
