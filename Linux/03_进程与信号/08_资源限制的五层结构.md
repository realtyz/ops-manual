# 资源限制的五层结构

> [!cite] 参考资料
> `man 2 getrlimit`、`man 2 setrlimit`、`man 5 limits.conf`、`man 8 pam_limits`、`man 5 systemd.exec`（`LimitXXX=`）、`man 5 systemd.resource-control`、`man 5 systemd.system.conf`、`man 1 prlimit`、`man 5 proc`（`/proc/<pid>/limits`）、`man 8 sysctl`；登录认证与 PAM 的完整内容在阶段 7（权限与安全加固）。

> **这篇讲什么**：同一个「上限」（比如「最多能开多少个文件」），可能来自五个完全不同的层次。**改错地方就等于没改**——这是「我明明改了怎么不生效」的唯一正解。
>
> **必须先读什么**：[[Linux/03_进程与信号/02_前置_进程观测与proc|02 前置：进程观测与 /proc]]（`/proc/<pid>/limits` 的读法）。

>
> 所属：[[Linux/03_进程与信号/00_导读与知识地图|03 进程与信号]] 的 1.2 横切线（限制线）· 主要练 **S5 限制治理**、**S7 风险与止损判断**

## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **上限有五层**：当前会话（`ulimit`）→ 登录会话（`limits.conf`/PAM）→ 服务（unit 的 `LimitXXX=`/`TasksMax=`）→ cgroup（整组）→ 内核全局（`fs.file-max`、`kernel.pid_max`）。**层层独立，谁都不会自动覆盖谁。**
> - **`limits.conf` 管不到 systemd 服务**：服务的进程不是通过 PAM 登录会话拉起来的，它走 unit 的 `LimitXXX=` 与 systemd 的 `DefaultLimitXXX=`。
> - **唯一的验收依据是 `/proc/<pid>/limits`**（或对应的 cgroup 文件）。配置文件写了什么不算，进程实际拿到什么才算。
> - **软限制是当前生效值，硬限制是软限制的上限**；无特权时把硬限制调低就再也升不回去——这是「手滑把服务锁死」的经典方式。
> - **五层之外还有一层容易忘**：应用自己的配置（连接池上限、线程池大小）。它不在内核里，但同样会让服务「撞墙」。

## 1. 五层结构总览

| 层次 | 配置位置 | 生效范围 | 重启/重登后 | 谁来改 |
| --- | --- | --- | --- | --- |
| **会话** | `ulimit`（shell 内置命令） | 当前 shell 及其子进程 | 丢失 | 手工，临时验证用 |
| **登录会话** | `/etc/security/limits.conf`、`/etc/security/limits.d/*.conf`（经 PAM） | **经 PAM 建立的登录会话** | 保留（需重新登录） | 系统管理员 |
| **服务** | unit 里的 `LimitNOFILE=`、`LimitNPROC=`、`LimitCORE=`、`TasksMax=` | 该服务拉起的所有进程 | 保留（`daemon-reload` + 重启服务） | 服务负责人 |
| **cgroup** | `memory.max`、`cpu.max`、`pids.max`、`io.max`（v2） | 整组进程 | 由 systemd/容器运行时管理 | 编排层或 `systemctl set-property` |
| **内核全局** | `fs.file-max`、`fs.nr_open`、`kernel.pid_max`、`kernel.threads-max`、`vm.max_map_count` | 全系统 | 由 `/etc/sysctl.d/*.conf` 持久化 | 系统管理员 |

一张判断图：**服务进程 → 看 unit；人登录进来跑命令 → 看 `limits.conf`/`ulimit`；整组容器 → 看 cgroup；全机器 → 看 sysctl。**

## 2. 第一、二层：`ulimit` 与 `limits.conf`

### 2.1 `ulimit` 与 `setrlimit`

`ulimit` 是 `setrlimit(2)` 的 shell 前端，**每个进程各持一份限制**。常用参数只有两个需要现在就记住：

| 限制 | ulimit 参数 | 控制什么 | 典型报错 |
| --- | --- | --- | --- |
| `RLIMIT_NOFILE` | `-n` | 单进程可打开的 fd 数 | `too many open files` |
| `RLIMIT_NPROC` | `-u` | **同一 real UID** 下的进程/线程数 | `fork: Resource temporarily unavailable` |

其余的（`-c` core 大小、`-v`/`-d` 地址空间/数据段、`-s` 线程栈、`-l` 可锁定内存、`-f` 单文件大小）**不用背，遇到报错再回来查**：

```bash
ulimit -Sa                            # 验证：当前会话的软限制全表
ulimit -Ha                            # 验证：当前会话的硬限制全表（软限制不能超过它）
cat /proc/self/limits                 # 验证：当前进程实际生效的限制（与 ulimit 同源）
cat /proc/<pid>/limits                # 验证：任意进程实际生效的限制（排障的最终依据）
prlimit --pid <pid>                   # 验证：同样的信息，工具形式（支持在线调整）
prlimit --pid <pid> --nofile=4096:4096   # 验证：在线调整（soft:hard；只能降低硬限制）
```

两条容易踩的规则：

1. **降低硬限制是不可逆的**（无特权时）：调低之后无法再调高，只能重启进程；
2. **`ulimit` 只影响当前 shell 及其后续子进程**，对已经在跑的进程、对 systemd 服务都无效。

### 2.2 `limits.conf` 与 PAM

`/etc/security/limits.conf` 由 PAM 模块 `pam_limits` 在**建立登录会话时**应用，格式是 `域 类型 项 值`。下面是示例（**不要直接照抄数值**）：

```text
*        soft    nofile   65535
*        hard    nofile   65535
@dba     soft    nproc    8192
```

```bash
ls -l /etc/security/limits.d/          # 验证：发行版自带的额外规则（RHEL 系常见 20-nproc.conf）
ulimit -Sn; ulimit -Hn                 # 验证：本机登录会话实际拿到多少（以实测为准，不要背默认值）
ssh <user>@<host> 'ulimit -Sn'         # 验证：重新登录后是否生效（改完必须重登）
```

> [!important] 为什么 `limits.conf` 对服务无效
> systemd 服务的进程**不是通过 PAM 登录会话拉起来的**：systemd 直接 `fork`+`exec`，并按自己的规则设置限制（unit 的 `LimitXXX=`，未配置时取 `DefaultLimitXXX=`）。所以往 `limits.conf` 里写 `nofile 65535`，然后重启服务——**一点都不会变**。
> 反过来说：`limits.conf` 解决的是「人登录进来跑命令」的限额问题，系统服务与容器里的服务都不归它管。
>
> 顺带一句：`su`/`sudo` 这类切换用户的动作是否经过 PAM、是否应用 `pam_limits`，**各发行版的 PAM 配置不一样**；不要靠记忆下结论，用 `ulimit -n` 实测。PAM 配置本身的细节在阶段 7（权限与安全加固）。

## 3. 第三层：systemd 服务

服务的限制写在 unit（或 drop-in）里，改完必须 `daemon-reload` 再重启服务：

```bash
systemctl edit <svc>                  # 验证：写 drop-in（推荐，不动发行版自带的 unit 文件）
systemctl daemon-reload               # 验证：systemd 重新读取单元（不重启服务则不会生效）
systemctl restart <svc>               # 验证：重启后新限制才生效
systemctl show -p LimitNOFILE -p LimitNPROC -p LimitCORE -p TasksMax <svc>
                                      # 验证：unit 层解析出来的配置值
cat /proc/$(systemctl show -p MainPID --value <svc>)/limits | grep -i -E 'open files|processes'
                                      # 验证：服务进程实际拿到的值（与上一行对比）
systemctl show -p DefaultLimitNOFILE -p DefaultTasksMax
                                      # 验证：没写 LimitXXX= 时的默认值（全系统范围）
```

在上面 `systemctl edit <svc>` 打开的编辑器里，写入的内容是：

```ini
[Service]
LimitNOFILE=65535
LimitNPROC=8192
LimitCORE=0
TasksMax=infinity
```

几个要点：

- **`TasksMax=` 优于 `LimitNPROC=`**：前者走 cgroup 的 `pids` 控制器，按「这个服务能用多少任务」计数；后者是 `RLIMIT_NPROC`，按 **real UID** 计数，同一用户跑多个服务时会互相抢额度。
- **容器里的服务不受宿主机 `limits.conf` 与 unit 影响**：它的限制来自容器运行时（也就是 cgroup），改容器内文件没有持久意义。
- **`LimitCORE=` 决定崩溃时有没有 core**（子笔记 10）。

## 4. 第四、五层：cgroup 与内核全局

```bash
cat /proc/<pid>/cgroup                # 验证：这个进程属于哪个 cgroup（v2 形如 0::/system.slice/foo.service）
systemctl show -p MemoryMax -p CPUQuotaPerSecUSec -p TasksMax <svc>   # 验证：unit 上的资源约束
cat /sys/fs/cgroup/system.slice/<svc>/memory.max                      # 验证：cgroup 实际生效的内存上限
sysctl fs.file-max fs.nr_open kernel.pid_max kernel.threads-max vm.max_map_count
                                      # 验证：内核全局上限基线（写入资产台账）
```

内核全局项统一用 `/etc/sysctl.d/*.conf` 持久化、`sysctl --system` 应用（加载顺序的细节见阶段 2 的子笔记 08）。它们的特点是：**改动影响整机，回滚成本高**——生产上先 `sysctl -w` 验证，再写文件。

还有一层不在内核里，但同样会让服务「撞墙」：**应用自己的配置**。连接池上限、线程池大小、队列长度都可能是真正的天花板——`/proc/<pid>/limits` 显示还有余量、服务却报「资源不足」，就要往这一层找。

## 5. 生产动作：把一个服务的上限改到正确的一层（S5）

> [!example]+ 生产动作：给服务提高文件句柄上限
> **什么时候用**：服务日志里出现 `too many open files`，或监控显示句柄数长期贴着上限。
>
> **动手前确认**：
> 1. **先判断是不是泄漏**：`ls /proc/<pid>/fd | wc -l` 长期单调上涨 → 先按子笔记 09 定位泄漏，扩容只是止血；
> 2. 确认这一层改得动：服务由 systemd 管吗？跑在容器里吗？
> 3. 确认上限链的每一环：`LimitNOFILE=` ≤ `fs.nr_open`，整机还有 `fs.file-max` 的余量；
> 4. 记录当前值，准备好回滚命令。
>
> **怎么做**：
> ```bash
> systemctl show -p LimitNOFILE <svc>                              # 验证：改动前的配置值
> cat /proc/$(systemctl show -p MainPID --value <svc>)/limits | grep -i 'open files'
>                                                                  # 验证：改动前进程实际拿到的值
> sysctl fs.nr_open fs.file-max                                    # 验证：全局天花板还有余量
> systemctl edit <svc>                                             # 写入 [Service] LimitNOFILE=<新值>
> systemctl daemon-reload && systemctl restart <svc>               # 验证：重启后生效（重启会有业务影响，注意窗口）
> systemctl show -p LimitNOFILE <svc>                              # 验证：unit 层已变成新值
> cat /proc/$(systemctl show -p MainPID --value <svc>)/limits | grep -i 'open files'
>                                                                  # 验证：进程实际值同步（这才是验收通过）
> ls /proc/$(systemctl show -p MainPID --value <svc>)/fd | wc -l   # 验证：当前句柄用量，与上限对比看余量
> ```
>
> **怎么验证**：`/proc/<pid>/limits` 显示新值，且业务不再报 `too many open files`；同时把「句柄数 / 上限」做成监控项。
>
> **怎么退回去**：把 drop-in 里的 `LimitNOFILE=` 改回原值（或 `systemctl revert <svc>` 撤销全部 drop-in）→ `daemon-reload` → `restart` → 再次核对 `/proc/<pid>/limits`。
>
> **比扩容更重要的一件事**：把「为什么要这么多句柄」写进缺陷单。**上限是给正常水位留余量的，不是用来掩盖泄漏的。**

## 6. 配套实验：证明「三层各管一段」（S5）

> [!example]- 实验 3：句柄上限的层级验证（顺便证明 `limits.conf` 管不到服务）
> 本实验覆盖五层里的**会话、服务、PAM 登录**三层；另外两层（cgroup、内核全局）在第 1 节的基线与子笔记 11 里。
>
> **环境**：任意 systemd 发行版；第三层要看到效果，需要 `sshd` 的 `UsePAM yes` 与可用的 SSH 登录。
>
> **怎么做**：
> ```bash
> ulimit -Sn; ulimit -Hn; cat /proc/self/limits | grep -i 'open files'
>                                                # 第一层：当前会话；验证：软/硬限制与进程实际值一致
> systemd-run --unit=lab-limits --property=LimitNOFILE=8192 --property=TasksMax=16 /bin/sleep 300
>                                                # 第二层：systemd 服务（用临时单元，不碰业务）
>                                                # 验证：返回「Running as unit: lab-limits.service」
> systemctl show -p LimitNOFILE -p TasksMax lab-limits       # 验证：unit 层解析出的配置值
> cat /proc/$(systemctl show -p MainPID --value lab-limits)/limits | grep -i 'open files'
>                                                # 验证：进程实际拿到 8192，与 unit 配置一致
> echo '* soft nofile 99999' > /etc/security/limits.d/99-lab.conf   # 第三层：PAM 登录会话
> systemctl restart lab-limits
> cat /proc/$(systemctl show -p MainPID --value lab-limits)/limits | grep -i 'open files'
>                                                # 验证：仍是 8192 —— limits.conf 对服务无效
> ssh <user>@localhost 'ulimit -Sn'              # 验证：重新登录的会话才看到 99999
> rm -f /etc/security/limits.d/99-lab.conf; systemctl stop lab-limits
> ```
>
> **预期**：会话层 `ulimit` 只能改当前 shell；unit 层由 `LimitNOFILE=` 决定；`limits.d` 只影响 PAM 登录会话——三条链路各自独立、互不覆盖。
>
> **风险**：中。会临时写入 `/etc/security/limits.d/` 并重启一个**临时单元**——不要拿业务服务做这一步。
>
> **耗时**：约 30 分钟（含一次重新登录）。
>
> **怎么退回去**：删除 `99-lab.conf`、`systemctl stop lab-limits`（脚本最后一行已包含）；确认 `ls /etc/security/limits.d/` 里没有残留。

## 7. 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 「改了 `/etc/security/limits.conf`，重启服务就生效」 | 对 systemd 服务无效（不走 PAM）；要写 unit 的 `LimitXXX=` 或 drop-in |
| 「`ulimit -n 100000` 一定能成功」 | 超过 `fs.nr_open` 会被拒；而且只影响当前 shell 的后续进程 |
| 用 `ulimit -u` 推算「还能起多少进程」 | 容器里的真实上限是 cgroup 的 `pids.max`；`RLIMIT_NPROC` 按 UID 计数、对特权进程常不生效 |
| 只改配置文件就认为改完了 | 验收标准是 `/proc/<pid>/limits` 或 cgroup 文件里的**实际值**，不是文件内容 |
| 改完不 `daemon-reload` 就重启服务 | 部分改动不生效；改 unit 的标准动作是 `daemon-reload` + `restart` |
| 在同一台机器上给多个服务设同一个用户的 `nproc` | `RLIMIT_NPROC` 按 real UID 共享，多个服务会互相抢额度；改用 `TasksMax=` |
| 把硬限制调低做「临时限制」 | 无特权时不可逆：只能重启进程才能恢复；对服务意味着一次中断 |
| 只加内核参数不看内层 | 整机放开了、服务自己的 unit 上限还在，问题照样复现 |

## 8. 决策练习

> [!question]- 场景：一个 systemd 管的 Java 服务报 `too many open files`，你已经在 `/etc/security/limits.conf` 里写了 `* soft nofile 65535`，重启服务后依然报错
> 你的下一步是什么？
> A. `systemctl show -p LimitNOFILE -p TasksMax <svc>` 看 unit 层，再用 `cat /proc/<MainPID>/limits` 看实际生效值；确认是则用 `systemctl edit` 写 drop-in，`daemon-reload` + `restart` 后复查
> B. 再确认 `sshd` 的 `UsePAM yes`，然后重启 sshd
> C. 把 `fs.file-max` 调到 100 万，重启服务试试
>
> **答案：A。**
> B 方向错了：`limits.conf` 影响的是 PAM 登录会话（人登录进来跑命令），systemd 服务根本不经过它，改 sshd 也没用。
> C 是隔靴搔痒：`fs.file-max` 是**整机**上限，服务撞的是自己的 `RLIMIT_NOFILE`（来自 unit）；调大全局上限不会改变服务的软/硬限制。
> A 是正解：**先看 unit 层配置 → 再看进程实际值 → 在正确的一层改 → 用 `/proc/<pid>/limits` 验收**。这也是 S5 的标准动作。

## 9. 要点自测

> [!question]- 软限制与硬限制的区别？为什么 `ulimit -n` 改完只对「当前 shell 及其子进程」有效？
> - 软限制是当前生效值，硬限制是软限制能达到的上限；无特权时硬限制只能降、不能升。
> - `ulimit` 改的是**当前 shell 进程自己的**限制集，子进程继承；已经在跑的进程与服务不受影响。
> - **第一反应不要是什么**：不要把 `ulimit` 当成全局配置——它连「本机所有新进程」都影响不到。

> [!question]- `limits.conf`、`ulimit`、systemd 的 `LimitNOFILE=` 三者的关系是什么？
> - `ulimit`：当前会话及其子进程，重登或重启即失效。
> - `limits.conf`：由 PAM 在**建立登录会话**时应用，只影响登录会话（`sshd` 的 `UsePAM` 与发行版 PAM 配置会影响结果，以实测为准）。
> - unit 的 `LimitNOFILE=`/`TasksMax=`：systemd 服务的正确位置；未配置时取 `DefaultLimitXXX=`。
> - **第一反应不要是什么**：不要改完 `limits.conf` 就重启服务然后疑惑「为什么不生效」——先问「这个进程是 PAM 拉起来的吗」。

> [!question]- 改完限制，用什么验收？
> - `/proc/<pid>/limits` 的**实际值**（或对应的 cgroup 文件），不是配置文件内容。
> - 同时对比上限链的每一环：unit 配置值 ≤ `fs.nr_open`，整机 `fs.file-max` 有余量。
> - **第一反应不要是什么**：不要把「`systemctl show` 显示新值」当成验收通过——那只是配置层，进程可能还没重启。
