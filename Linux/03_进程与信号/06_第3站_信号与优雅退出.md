## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **信号的投递是异步的，而且可以延迟**：进程阻塞在内核态时，信号只会被**挂起**，等它回到用户态才处理。所以「发出去了」不等于「已经生效」，`kill` 命令几乎永远返回成功。
> - **`SIGKILL` 与 `SIGSTOP` 是唯二不可捕获、不可阻塞、不可忽略的信号**。其余信号，进程都可以选择捕获、忽略或用默认动作。
> - **`SIGTERM` 是请求，`SIGKILL` 是命令**。前者给应用「收尾」的机会，后者只保证进程消失——文件锁、临时文件、在途请求、未落盘的数据都不保证。
> - **PID 1 受特殊保护**：内核对它**不执行信号的默认动作**，凡是它没有安装处理函数的信号一律被忽略。这条规则在主机上保护 systemd，在容器里却会造成事故（子笔记 07）。
> - **优雅退出是一项要设计、可验收的能力**：应用处理 `SIGTERM` + 停机时间小于 `TimeoutStopSec=` + 停机后有日志可查，三件事缺一不可。

## 1. 信号是什么

一句话：**信号是内核投递给进程的一张小纸条**——它不携带详细内容（除了少数实时信号），只告诉进程「发生了某件事」，进程只能从三种反应里选一种：**捕获处理、忽略、用默认动作**。

| 信号 | 号 | 默认动作 | 生产上的含义 |
| --- | --- | --- | --- |
| `SIGHUP` | 1 | 终止 | 终端断开；**守护进程约定用它做配置重载**（重开日志也常用它） |
| `SIGINT` | 2 | 终止 | `Ctrl+C`，交互式中断 |
| `SIGQUIT` | 3 | 终止 + core | 部分程序（如 JVM）用它输出线程栈 |
| `SIGABRT` | 6 | 终止 + core | `abort()`，断言失败的标准出口 |
| `SIGKILL` | 9 | 终止 | **不可捕获**；没有任何清理机会 |
| `SIGSEGV` | 11 | 终止 + core | 段错误，用户态崩溃取证的主战场（子笔记 10） |
| `SIGPIPE` | 13 | 终止 | 往已关闭的管道/套接字写；日志管道断开时常见 |
| `SIGTERM` | 15 | 终止 | 优雅退出的标准信号，`systemctl stop` 与 `docker stop` 的第一发 |
| `SIGCHLD` | 17 | 忽略 | 子进程状态变化通知，**父进程回收僵尸的钩子**（子笔记 07） |
| `SIGCONT` | 18 | 继续 | 与 `SIGSTOP` 配对，`fg`/`bg` 背后就是它 |
| `SIGSTOP` | 19 | 停止 | **不可捕获**；调试与「冻住进程」用 |
| `SIGTSTP` | 20 | 停止 | `Ctrl+Z`；与 `SIGSTOP` 不同，它可以被捕获 |
| `SIGUSR1/2` | 10/12 | 终止 | 应用自定义：重开日志、dump 状态（nginx 用 `SIGUSR1` 重开日志文件） |

> [!info] 信号编号的坑
> **1~15 号在常见架构上一致，后面的编号各架构不同**（例如 `SIGUSR1` 在 x86_64 上是 10，在部分架构上是 16）。所以脚本里一律**用名字**（`kill -TERM`），需要查编号就用 `kill -l` 看本机结果，不要背数字。

## 2. 五条必须记住的语义边界

1. **信号是挂起后投递的**：进程正阻塞在内核态（例如 `D` 状态等 IO）时，信号会被记下，等它回到用户态才处理。这解释了「`kill -9` 没反应」与「`kill` 返回 0 但进程还在」。
2. **可以屏蔽**：程序可以用 `sigprocmask` 阻塞除 `SIGKILL`/`SIGSTOP` 之外的任何信号。**这是「为什么这个服务对 `SIGTERM` 没反应」最常见的原因**——不是内核不投递，是它选择不处理。
3. **PID 1 受内核特殊保护**：内核对 PID 1 **不执行信号的默认动作**。在主机上 `kill -9 1` 是静默失败；在容器里，这条保护会把「应用没处理 `SIGTERM`」变成「`docker stop` 必然超时」。
4. **`SIGKILL` 也杀不掉 `D` 状态与僵尸**：前者因为信号投递不进去，后者因为进程已经终止、只剩一个待回收的壳。
5. **信号是发给「进程」而不是某个线程的**：内核会在该线程组里挑一个**没有屏蔽这个信号**的线程去执行处理函数——通常是主线程，也可能是恰好空闲的工作线程。所以「停机逻辑具体跑在哪个线程上」是不确定的；如果所有线程都屏蔽了它，信号会一直挂在 `SigPnd` 里（看 `/proc/<pid>/status`）。

```bash
kill -l                              # 验证：本机的信号名与编号对照表（脚本里仍建议用名字）
cat /proc/<pid>/status | grep -E 'SigQ|SigPnd|ShdPnd|SigBlk|SigIgn|SigCgt'
                                     # 验证：挂起信号队列 / 待处理位图 / 被阻塞、忽略、捕获的信号位图
```

`SigBlk`、`SigIgn`、`SigCgt` 三行是十六进制位图，**只要某个信号在 `SigIgn` 里有位，就说明这个进程选择了忽略它**——排查「为什么它不响应」时非常好用。

## 3. 怎么发信号、发给谁

| 命令 | 用法 | 注意 |
| --- | --- | --- |
| `kill -15 <pid>` | 给单个进程发信号 | 等价 `kill -TERM <pid>`；默认信号就是 `TERM` |
| `kill -TERM -<pgid>` | 给一个**进程组**发信号 | 负号后面是 PGID；发之前先 `ps -o pgid` 确认组内成员 |
| `pkill -f '<模式>'` | 按命令行匹配批量发信号 | **危险**：模式写宽了会误伤，先 `ps -ef | grep` 核对 |
| `timeout -k 5 30 <cmd>` | 30 秒后发 `TERM`，5 秒后仍不退则发 `KILL` | 脚本里最省事的「优雅停机 + 兜底强杀」 |
| `systemctl stop <svc>` | 按 unit 停止服务 | 默认停**整个 cgroup**（`KillMode=control-group`），子进程一起清 |
| `systemctl kill -s HUP <svc>` | 给服务的所有进程发指定信号 | 用于「应用处理 SIGHUP」的重载场景 |
| `docker stop <ctr>` / `kubectl delete` | 先 `SIGTERM`，超时后 `SIGKILL` | 容器内 PID 1 不处理 `TERM` 时必然走满超时（子笔记 07） |

```bash
ps -o pid,pgid,sid,tty,stat,cmd -p <pid>          # 验证：确认目标进程的归属，再决定发给谁
kill -TERM <pid>                                   # 验证：优雅退出的标准动作
kill -0 <pid> && echo 仍在运行                      # 验证：只探测进程是否存在，不发送实际信号
timeout -k 5 30 <cmd>                              # 验证：脚本里的超时 + 兜底强杀
```

## 4. 优雅退出：要设计，也要验收

一个服务能被「温柔地停下来」，需要四件事同时成立：

| 检查项 | 怎么确认 |
| --- | --- |
| **应用处理了 `SIGTERM`** | 日志里应出现「收到终止信号 → 停止接收新请求 → 处理完在途请求 → 释放资源 → 退出」的记录 |
| **停机时间小于服务管理器给的上限** | `systemctl show -p TimeoutStopUSec <svc>`；超时后 systemd 会补一发 `SIGKILL`，等于没优雅 |
| **停止范围覆盖全部子进程** | `KillMode=`（默认 `control-group`，停整个 cgroup）；自定义 `ExecStop=` 写 `kill $MAINPID` 时容易留下孤儿 |
| **重载走专门通道** | 要么应用自己处理 `SIGHUP`，要么 unit 里配 `ExecReload=`，再用 `systemctl reload`（**reload 不重启进程，是「不丢连接」的关键**） |

```bash
systemctl show -p TimeoutStopUSec -p KillMode -p KillSignal -p ExecReload <svc>
                                          # 验证：这个服务的停机超时、停止范围、默认终止信号与重载命令
systemctl reload <svc>; systemctl show -p MainPID <svc>
                                          # 验证：reload 之后 MainPID 不变（说明没有重启进程）
journalctl -u <svc> --since '5 min ago' | tail -30
                                          # 验证：应用自己记录的停机/重载过程
```

> [!important] `KillMode=` 决定「停得干净不干净」
> 默认的 `control-group` 会停止该服务 cgroup 里的**所有**进程，这正是「`systemctl stop` 能连带清掉 worker」的原因；`process` 只停主进程，容易留下孤儿；`none` 只发信号不做别的。老服务改成 systemd 托管时，「停不掉 / 停完还有残留进程」十有八九出在这一项。

## 5. `kill -9` 的代价：要能具体说出来

| 场景 | `kill -9` 之后会发生什么 |
| --- | --- |
| 数据库 | 未落盘的事务丢失，恢复期变长；严重时数据文件损坏、需要从备份重建 |
| 消息队列 / 分布式组件 | 未提交的偏移与状态残留，重启后重复消费或脑裂 |
| 写文件的批处理 | 目标文件只写了一半（临时文件残留），下游读到脏数据 |
| 持有文件锁的进程 | 锁随进程释放，但**中间状态没有回滚**，别的进程可能看到不一致的数据 |
| 有共享内存 / 信号量的进程 | POSIX 共享内存段残留（`/dev/shm` 占内存），需要手工清理 |
| 自己写的守护脚本 | 子进程变孤儿继续占端口，重启时「端口被占用」 |

判断要不要动用它，问三个问题：**这个进程有没有在途数据？有没有持锁？它停下之后有没有别人接力？** 三个都是「没有」，`SIGKILL` 的代价才可接受。

## 6. 生产动作：给一个服务做一次可回滚的 graceful reload / stop（S2）

> [!example]+ 生产动作：安全地重载一个服务
> **什么时候用**：改完配置要生效，又不想丢连接（nginx、HAProxy 这类）。
>
> **动手前确认**：
> 1. `systemctl cat <svc>` 看清生效配置（不要只看你自己改的那份文件）；
> 2. `systemctl show -p ExecReload -p MainPID <svc>`：有 `ExecReload=` 才能 `reload`，没有就只能 `restart`；
> 3. 确认有回滚路径：配置文件先备份（带时间戳），并想好恢复后要不要再 reload 一次；
> 4. 确认有第二个登录通道（别在 reload 卡住时把自己关在门外）。
>
> **怎么做**：
> ```bash
> systemctl cat <svc>                              # 验证：单元的真实内容（含 drop-in 与优先级）
> systemctl show -p ExecReload -p MainPID <svc>    # 验证：重载命令与当前主进程 PID
> cp -a /etc/<svc>/conf /etc/<svc>/conf.bak.$(date +%F-%H%M)   # 验证：备份已生成
> <改配置，然后先做语法检查（如 nginx -t）>          # 验证：配置语法通过，再 reload
> systemctl reload <svc>                           # 验证：reload 成功（失败会给非 0 退出码与提示）
> systemctl show -p MainPID <svc>                  # 验证：MainPID 未变——进程没有重启，连接没断
> journalctl -u <svc> --since '2 min ago' | tail -20   # 验证：应用自己记录了重载过程
> ```
>
> **怎么验证**：`MainPID` 不变、端口仍在监听（`ss -lntp`）、业务探针/首页 200、应用日志无 error。
>
> **怎么退回去**：恢复备份的配置文件 → `systemctl reload <svc>`（若 reload 失败则 `systemctl restart <svc>`）→ 再次核对端口与日志。
>
> **如果连 reload 都失败**：先 `systemctl status <svc>` 看退出码，再决定是 `restart` 还是先回滚配置。**不要用 `kill -9` 代替 stop**——那会跳过应用的清理逻辑。

## 7. 配套实验：`SIGTERM` 能捕获，`SIGKILL` 不能（S2、S7）

> [!example]- 实验 2：用一个 `trap` 看清两种信号的差别
> **环境**：任意发行版。把 `kill` 那两行换成「前台运行 + 在另一个终端发信号」，观察更直观。
>
> **怎么做**：
> ```bash
> cat > /tmp/lab-sig.sh <<'EOF'
> #!/bin/bash
> trap 'echo "收到 TERM，开始清理，然后退出"; exit 0' TERM
> echo "启动，PID=$$"
> while true; do sleep 1; done
> EOF
> chmod +x /tmp/lab-sig.sh && /tmp/lab-sig.sh &      # 起一个会捕获 TERM 的测试进程
> kill -15 %1                                        # 验证：trap 打印清理信息后退出（退出码 0）
> /tmp/lab-sig.sh & p=$!; kill -9 $p; wait $p; echo $?   # 验证：没有任何输出，退出码是 128+9=137（kill 本身返回 0，要 wait 才拿得到真实退出码）
> cat /proc/<pid>/status | grep -E 'SigIgn|SigCgt'   # 验证：可捕获的信号位图里能看到 TERM 对应的位
> ```
>
> **预期**：`SIGTERM` 走 `trap` 分支；`SIGKILL` 连 `trap` 都进不去——这就是「`kill -9` 没有清理机会」的字面含义。
>
> **风险**：低，只影响你自己起的测试进程。**注意不要对着真实业务 PID 试 `kill -9`。**
>
> **耗时**：约 15 分钟。
>
> **怎么退回去**：两个测试进程都会被杀掉，无需清理；`/tmp/lab-sig.sh` 可以留着复用或删掉。

## 8. 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 「`kill` 返回成功，说明进程已经收到并处理了」 | `kill` 只表示信号送达；进程可能屏蔽它、或在 `D` 状态里收不到 |
| 服务卡住就 `kill -9` | 丢掉现场（栈、锁、临时状态），还可能留下孤儿进程与脏数据；先看状态与 `wchan`，再决定用哪个信号 |
| 用 `pkill -f` 清理进程 | 匹配模式写宽会误伤同机其它服务；先 `ps -ef` 核对再发，或者用精确 PID/PGID |
| 「`SIGTERM` 没反应，说明进程死了」 | 更常见的是它阻塞（屏蔽）了 `SIGTERM`；看 `/proc/<pid>/status` 的 `SigBlk`/`SigIgn` |
| 以为 `kill -9 1` 能重启 systemd | 内核对 PID 1 不执行默认动作，这条命令静默失败；要重启系统用 `systemctl reboot` |
| 用 `SIGHUP` 关掉一个不处理它的程序 | 默认动作是终止——对没实现重载的程序，「重载」等于「杀死」 |
| 只把 `TimeoutStopSec` 调大来解决「停不干净」 | 超时只是兜底；根因通常是应用没处理 `TERM` 或 `ExecStop` 写得不对 |
| 在 `ExecStop=` 里写 `kill $MAINPID` | 只杀了主进程，worker 变孤儿继续占端口；交给 `KillMode=control-group`（默认）处理更可靠 |

## 9. 决策练习

> [!question]- 场景：一个自研服务在发布时「停不掉」，`systemctl stop` 每次都要等满 90 秒，然后日志里出现 `SIGKILL`
> 你会怎么处理？
> A. 把 `TimeoutStopSec` 调到 300 秒，给它更多时间
> B. `systemctl show -p KillSignal -p TimeoutStopUSec -p ExecStop <svc>` 看清默认终止信号与停止范围，再在应用侧确认它是否处理 `SIGTERM`（看 `journalctl -u` 有没有停机记录、看进程的 `SigIgn`/`SigBlk`），必要时用 `systemd-run`/测试实例复现一次停止过程
> C. 直接把服务改成 `KillMode=none`，让 systemd 不要管它的子进程
>
> **答案：B。**
> A 只是让发布更慢：如果应用根本不处理 `SIGTERM`，无论给多久，最后还是会走到 `SIGKILL`。
> C 会让情况更糟：`KillMode=none` 会让 systemd 停止时不清理进程，残留更多。
> B 是正解：**先确认「发的是什么信号、给了多长时间、谁该负责收尾」，再去应用侧确认它的处理逻辑**。这类问题的根因几乎总在应用侧（没装 `SIGTERM` 处理函数、正在执行一个不可中断的循环），而不是超时太短。

## 10. 要点自测

> [!question]- `SIGTERM` 与 `SIGKILL` 的差别是什么？为什么后者是最后手段？
> - `SIGTERM` 可捕获、可忽略，应用能借此做优雅退出（停止接收新请求、处理在途、释放锁、刷新缓冲）。
> - `SIGKILL` 不可捕获、不可阻塞、不可忽略，只保证进程消失；锁、临时文件、在途数据都不保证。
> - **第一反应不要是什么**：不要把「进程没了」等同于「服务正常停止了」——很多事故是 `kill -9` 之后的下一次启动才暴露出来。

> [!question]- 为什么有些服务对 `SIGTERM`「没反应」？
> - 可能它屏蔽了该信号（看 `SigBlk`/`SigIgn`），可能它正卡在 `D` 状态（信号被挂起），也可能它的 PID 1 身份让内核不执行默认动作。
> - 容器语境下最常见：PID 1 是 `bash`/`sh`，没有为 `SIGTERM` 安装处理函数，于是 `docker stop` 只能等超时后强杀（子笔记 07）。
> - **第一反应不要是什么**：不要先怀疑内核或 systemd「没发信号」，先确认进程侧的状态与信号处置。

> [!question]- 一次「可验证的优雅停机」需要哪几件事？
> - 应用处理 `SIGTERM` 并有明确日志；停机时间小于 `TimeoutStopSec=`；停止范围覆盖全部子进程（`KillMode=control-group`）。
> - 重载走专门通道（应用处理 `SIGHUP` 或 unit 配 `ExecReload=`），并用 `MainPID` 是否变化来区分「重载」与「重启」。
> - **第一反应不要是什么**：不要只改超时时间——那只是延长了痛苦的时长，没有解决收尾责任。
