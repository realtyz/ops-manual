# 高频误判

十二条都按值班与复盘里的真实处境来写，每条依次给出场景、常见误判（以及它为什么看起来成立）、判据（读哪个字段、什么数值或趋势、什么条件下结论会变）、一句话结论与出处。字段的读法在实操篇第 2 节与体系篇的关键字段表里。

## 1. 「服务 CPU 打满了，赶紧扩容」

**场景**：在一台 8 vCPU 的机器上，某 Java 服务响应变慢，应用监控显示它的「CPU 使用率 100%」。值班看到整机 CPU 只有 13%，于是判断「机器很空，是应用自己的问题」，并准备扩容副本数。

**常见误判**：值班把「整机 CPU 不高」当成了「不是 CPU 问题」。这个判断看起来成立，因为瓶颈确实不在整机层面；但它的方向错了，因为瓶颈落在**一颗核**上。

**判据**：先按每颗 CPU 核逐个去看（`mpstat -P ALL` 一类的输出），找出占用接近满的那一列；再看线程级，把热点定位到 TID。进程级的 `%CPU` 并不是被多核平均掉的数，因为 `ps`/`pidstat` 算的是「CPU 时间÷存活时间」，**不按核数归一**（只有 `pidstat` 加 `-I`、`top` 切到 Solaris 模式时才除以 CPU 总数），所以一个线程跑满时它显示**接近 100%**；被核数平均掉的是**整机**那一层——8 核机器上一个线程跑满，整机只有约 12%。这正是整机值不能用来否定单核热点的原因。**条件会变**：如果每颗核都不高而服务仍然慢，那么它是在等而不是在算，因此要转向自愿上下文切换、系统调用与 IO 这三个方向去查；如果每颗核都高，那才是真实的容量不足。

**一句话结论**：并发度不足（单线程热点、绑核错误、运行时停世界）与容量不足是两回事，因此判据要取**每核**占用，而不是整机占用。

**出处**：`man 1 ps` 给出 `%CPU` 的定义；`man 1 pidstat` 给出线程级 `-t`、按秒采样的语义与 `-I` 这个归一开关；`man 1 top` 说明 Irix 模式与 Solaris 模式对同一列采用的不同口径；每核采样的出处则是 `man 1 mpstat`。

## 2. 「退出码 137，所以是被 OOM 杀了」

**场景**：一个服务在凌晨消失，随后又被自动拉起。值班看到 `Result=signal`、`ExecMainStatus=9`，于是在事故记录里写下「被 OOM 杀」；但他翻遍内核日志，都没有找到 OOM 记录。

**常见误判**：值班把 137 当成了 OOM 的证据。这个判断看起来成立，因为 137 = 128 + 9 确实意味着进程死于 `SIGKILL`，而 OOM 也确实用 `SIGKILL`；但能让进程收到 `SIGKILL` 的至少有四种来源：内核 OOM（整机或组级）、人工或脚本的 `kill -9`、运行时或服务管理器在停止超时后的强杀、编排层或健康检查触发的重启。

**判据**：137 只回答「进程是怎么死的」。若要定性「是谁发的信号」，就要查三处：整机内核日志里的 OOM 记录、cgroup 事件计数里 `oom_kill` 的差值（由于它是**累积值，必须用差值**），以及人工与编排层的操作记录。四种来源与这三处的对应关系是：内核 OOM 会落进前两处，人工或脚本的 `kill -9` 会落进操作记录，服务管理器的停止超时强杀会留在单元日志里，而编排层与健康检查触发的重启只能回到编排层的事件流里去找。整机 OOM 在内核日志里写成 `oom-kill:constraint=CONSTRAINT_NONE,…,global_oom` 与 `Out of memory: Killed process …`，组级 OOM 写成 `oom-kill:constraint=CONSTRAINT_MEMCG,…,oom_memcg=<路径>` 与 `Memory cgroup out of memory`，**两者都在宿主内核日志里**。真正会先消失的是这些计数字段：cgroup 目录与 `memory.events` 会随单元或容器结束一起被回收，因此取证要趁现场还在。**条件会变**：如果容器被暂停（冻结），那么它发生的 OOM 也可能不出现在宿主侧的常规监控里；如果服务是被编排层按健康检查重启的，那么这三处都不会命中，此时要回到编排层的事件里去找。

**一句话结论**：若三处证据都没有命中，则事故记录只能写「死于 `SIGKILL`，来源待查」，而不能写「推断为 OOM」。

**出处**：137 = 128 + 9 这个口径来自两处：`man 1 bash` 的 EXIT STATUS 一节写明「bash uses the value of 128+N as the exit status」，而 `man 2 wait` 给出 `WIFSIGNALED`/`WTERMSIG`，内核口径里并没有 `128+N`。此外，`man 5 proc_pid_oom_score` 给出 `/proc/<pid>/oom_score`，内核文档 `Documentation/admin-guide/cgroup-v2.rst` 的事件计数一节给出 `memory.events` 与 `oom_kill` 的字段口径，`man 5 systemd.resource-control` 给出服务侧的 cgroup 资源控制字段。

## 3. 「`kill -9` 都杀不掉，这进程肯定死了 / 内核坏了」

**场景**：有一个进程的状态是 `D`，值班发了两次 `kill -9` 都没有反应，于是他判断「它已经死了，是 `ps` 显示错了」，并决定重启机器。

**常见误判**：值班把「命令没有反应」理解成了「内核拒绝执行」。这个判断看起来成立，因为 `kill` 确实返回了成功，而进程也确实还在。

**判据**：由于信号只在**从内核态返回用户态**的时刻被处理，因此处于 `D` 状态的 task 等不到这个时刻，信号只留在待处理位图上。所以要看的是等待点（`wchan`）与内核栈，而不是状态字母：`TASK_KILLABLE` 这类等待能被致命信号打断，而它的外观同样是 `D`，因此「`D` 一定杀不掉」只说对了一半。**条件会变**：如果 `wchan` 指向的是本地块设备路径，那么等 IO 恢复后信号会立刻生效；如果它指向网络存储，则要等服务端可达；如果内核已经报了长时间的阻塞超时记录，那么排查重点在存储与驱动路径。

**一句话结论**：所以 `D` 状态的问题不是「怎么杀掉它」，而是「它在等谁」；同时要记住，重启既会清掉现场，也不保证问题不复发。

**出处**：信号的投递时机见 `man 7 signal`；等待点与内核栈见 `man 5 proc_pid_wchan` 与 `man 5 proc_pid_stack`；`hung_task_timeout_secs` 等参数见内核文档 `Documentation/admin-guide/sysctl/kernel.rst`。`TASK_KILLABLE` 没有任何 man 页覆盖，因此它的依据是内核源码 `include/linux/sched.h` 的 `#define TASK_KILLABLE (TASK_WAKEKILL | TASK_UNINTERRUPTIBLE)` 与 `kernel/signal.c` 的 `signal_wake_up_state()`，并且要按目标内核版本取。

## 4. 「僵尸进程占内存，先批量清掉」

**场景**：容器的进程列表里有 300 多个 `<defunct>`，值班担心这些僵尸把内存推向上限，于是写了一条按状态筛出僵尸、再逐个发 `SIGKILL` 的命令。

**常见误判**：值班把僵尸当成了「没死干净的活进程」。这个判断看起来成立，因为它确实出现在进程列表里，也有 PID 和状态字母。

**判据**：僵尸**已经终止**，留下的只是一个等待父进程领取的退出状态。由于它对信号没有反应（发信号既不报错也不生效），所以它占用的是进程表项与 PID，而不是内存。因此要处理的是它的**父进程**：先按 `PPID` 聚合找出制造者，再看父进程的状态——若父进程卡在 `D`，则僵尸会随它恢复而消失；若父进程正常运行却不回收，那就是程序缺陷；反之，若父进程显式忽略 `SIGCHLD`（等价写法是置 `SA_NOCLDWAIT`），则子进程终止后根本不会留下僵尸。**条件会变**：若孤儿进程的父进程被显示为 1，那只说明中间层已经退出（被收养），并不代表它由 init 直接管理。

**一句话结论**：僵尸只是一个还没被父进程领取的退出状态，并不是「没有死透」，因此处置对象永远是父进程。

**出处**：退出状态的领取责任见 `man 2 wait`，它的 NOTES 写明了显式忽略 `SIGCHLD` 带来的差别；`man 2 sigaction` 给出 `SA_NOCLDWAIT` 的语义；`State: Z` 的定义见 `man 5 proc_pid_status`。

## 5. 「`/etc/security/limits.conf` 改完重启服务就生效」

**场景**：服务报告打开文件过多。管理员在登录会话的限制配置里加了一条全局的打开文件上限，但他重启服务之后，问题依旧。

**常见误判**：管理员把这份配置文件当成了「内核的全局设置」。这个判断看起来成立，因为改完之后它确实对**人登录进来跑的命令**有效，于是就被推广成「对所有进程都有效」。

**判据**：由于那份配置只在**建立登录会话时**由 PAM 应用，而服务管理器启动服务走的是直接创建加装载的路径、并不经过登录会话，所以服务管理器按自己的规则设置限制（unit 上的限制属性；若没有配置，则取服务管理器的默认值）。因此验收只能看进程**实际生效**的值，也就是读该进程的限制文件。**条件会变**：切换用户这类动作是否应用该配置，取决于发行版的 PAM 配置，所以不要靠记忆判断。

**一句话结论**：配置文件里写了什么不算数，只有进程实际拿到的限制才算数；同时，服务侧的限制写在服务定义里。

**出处**：`man 5 limits.conf` 与 `man 8 pam_limits` 给出该配置的字段与应用时机，`man 5 systemd.exec` 给出服务侧的限制属性，`man 5 proc_pid_limits` 给出限制文件的字段口径。

## 6. 「改了上限，`ulimit -n` 看到新值就算生效了」

**场景**：服务仍然报告打开文件过多。值班在一个 shell 里执行了提高打开文件上限的命令，看到新值之后，就判断「上限已经改好了」。

**常见误判**：值班把「当前 shell 的限制」当成了「服务的限制」。这个判断看起来成立，因为命令确实生效了；但它生效的对象是另一个进程。

**判据**：由于限制是**每个进程各持一份**的，shell 上的调整只影响这个 shell 及其后续子进程，而已经在运行的进程与服务不受影响。因此验收要读目标进程的限制文件，并把它和所属 cgroup 的限制层级、整机层面的上限一起看：进程的上限不能超过整机给单进程设的硬限制，而整机还另有总量上限。**条件会变**：把硬限制调低是无特权下不可逆的动作，只能通过重启进程恢复，而对服务而言这就是一次中断。

**一句话结论**：`ulimit` 改的是本进程持有的那一份限制，它既不是配置文件，也不是全局设置。

**出处**：软硬限制的语义见 `man 2 getrlimit` 与 `man 2 setrlimit`；对运行中进程查看与调整限制见 `man 1 prlimit`；`limits` 文件的口径见 `man 5 proc_pid_limits`。

## 7. 「进程数快到上限了，从 `ps aux | wc -l` 看还差多少额度」

**场景**：由于 `fork` 开始偶发失败，值班就用进程列表数了一下行数，算出「还剩几万额度，不可能达到上限」，于是转去查内存。

**常见误判**：值班用错了统计口径。这个判断看起来成立，因为「进程数」这个词在日常对话里指的就是进程列表的行数。

**判据**：由于进程列表默认按**线程组**计数，而限额、调度与资源统计按 **task** 计数，所以一个多线程进程在两种口径下的数量可能相差几十倍。组级限额要看 cgroup 的当前用量与上限；用户级限额按 real UID 计数，因此多个服务共用一个用户时会消耗同一份额度；整机层面还有两条独立的全局上限。**条件会变**：用户级的 `RLIMIT_NPROC` 计数对持有 `CAP_SYS_ADMIN`/`CAP_SYS_RESOURCE` 的进程根本不执行，对 **real user ID 为 0** 的进程同样不执行——而容器多以 root 运行，这才是更常见的那一条——所以容器里触到的往往是组级限额。

**一句话结论**：因此判断额度要看 task 计数与对应那一层的上限，而 `ps aux | wc -l` 给出的完全是另一个量。

**出处**：`ps` 默认按线程组计数、线程要加 `-L`，见 `man 1 ps`；`fork` 的 `EAGAIN` 见 `man 2 fork`；`RLIMIT_NPROC` 按 real UID 计数与它的豁免见 `man 2 setrlimit`；pids 控制器的计数口径见内核文档 `Documentation/admin-guide/cgroup-v2.rst` 的 pids 控制器一节。

## 8. 「线程那么少还报资源不足，肯定不是线程数的问题」

**场景**：某服务在 `ps` 里只有 1 行进程、`nlwp` 显示 1，日志里却持续出现资源相关的失败；值班据此把「线程数」这一项排除了。

**常见误判**：值班把一种工具的默认视图当成了完整视图。这个判断看起来成立，因为 `ps` 的输出确实来自内核。

**判据**：由于 `ps` 的默认输出里每个线程组只占一行，所以**它的线程在这个视图里是看不见的**。因此要判断一个进程有多少执行流，就得看它的线程计数（`status` 里的字段）、线程目录列表，或者显式打开线程视图的工具输出。**条件会变**：若进程数只有一行而组级的 task 计数很高，则说明真正的消耗发生在默认视图之外的那一层；反之，线程数正常也不能排除句柄、地址空间等其他维度已经用尽。

**一句话结论**：默认视图并不等于全部视图，因此要先确认统计口径，再去排除任何一项。

**出处**：`ps` 的 `-L`、`-eLf` 与默认输出的差异见 `man 1 ps`；`/proc/<pid>/status` 的线程数见 `man 5 proc_pid_status`；`/proc/<pid>/task/` 见 `man 5 proc_pid_task`；`pids.current` 的计数口径见内核文档 `Documentation/admin-guide/cgroup-v2.rst`。

## 9. 「`nohup`/`setsid` 之后它就是常驻服务了」

**场景**：为了跑一个长期任务，值班用忽略挂断信号的方式把脚本放到后台；第二天他发现进程不见了，也没有任何日志可查。

**常见误判**：值班把「不被终端带走」当成了「被托管」。这个判断看起来成立，因为挂断信号确实是终端断开时用来终止前台进程的机制。

**判据**：忽略挂断信号只解决一件事：终端断开时进程不再被带走。而开机自启、失败重试、日志落点与轮转、资源上限、统一停止范围都不在其中。所以真正的托管要把进程交给 init 系统：让它保持前台运行，把日志交给日志服务，并用单元来描述重启策略与限制。**条件会变**：如果任务本身会自己退出、失败也可以重跑，那么用后台方式是可以接受的权宜之计；即便如此，也要显式指定输出落点，否则输出要么累积在一个文件里，要么直接丢失。

**一句话结论**：后台化不等于服务化，两者的差别在于有没有人负责它的状态。

**出处**：`man 1 nohup` 与 `man 2 setsid` 是这两个命令语义的出处；作业控制与挂断信号见 `man 1 bash`；托管语义见 `man 5 systemd.service`。

## 10. 「容器 `stop` 等满超时是被杀得太急，把超时调长就好」

**场景**：某容器每次发布都要等满停止超时才被强杀，退出码是 137。值班把停止超时从默认值调到 5 分钟，结果发布变慢了，问题却依旧。

**常见误判**：值班把「等得不够久」当成了根因。这个判断看起来成立，因为延长超时确实让某些服务「有机会」自己退出。

**判据**：先看容器里的 1 号进程是什么。由于内核对 PID 1 **不执行信号的默认动作**，同一个 namespace 里发给它、而它没有安装处理函数的信号（含 `SIGKILL`/`SIGSTOP`）一律被丢弃，所以一个没为终止信号安装处理函数的 PID 1（典型是 shell）等于忽略了停止请求；而来自祖先 namespace（宿主相对容器）的 `SIGKILL`/`SIGSTOP` 会被**强制投递并生效**。因此超时是最后一道回退路径：停止超时到点之后，由宿主侧（也就是相对容器的祖先 namespace）补发 `SIGKILL`，正是这一条让强杀最终生效。这里的判据是容器内 PID 1 的命令行与它的信号位图。**条件会变**：如果 PID 1 是应用本身、也装了处理函数，但仍然超时，那要看应用收尾逻辑本身的耗时是否真的大于超时值——只有在这种情形下，调大超时才有意义。

**一句话结论**：先确认「谁该负责收尾、它有没有被通知」，再谈时间够不够。

**出处**：`man 2 kill` 的 NOTES 写明内核只向 init 投递它显式安装了处理函数的信号；容器内 PID 1 的地位与祖先 namespace 的强制投递见 `man 7 pid_namespaces`；停止信号与超时之后补发强杀这条回退路径的语义见 `man 5 systemd.kill`；停止超时的定义页见 `man 5 systemd.service`，它的**默认值要现场取**。

## 11. 「进程的内存就是把各线程加起来，对不上就是工具坏了」

**场景**：值班要把一个进程各线程的内存加起来核对总量，结果得到 12 GiB，而整台机器总共只有 8 GiB；于是他怀疑统计工具出错了。

**常见误判**：值班把共享内存被重复计数当成了「数据不一致」。这个判断看起来成立，因为每个线程确实都有一个内存数字。

**判据**：由于同一线程组内的执行流共享地址空间，所以常驻这个数字本来就是**整组共享的一份**，而不是「某个线程的」。跨进程也一样：由于共享页在每个映射它的进程里各算一份，因此把所有进程的常驻集相加必然大于整机用量。因此要做总量核对，就要用均摊口径（全机相加近似等于整机用量）；要判断「谁真的占着」，就用私有一列；同时还要记得，共享内存文件系统与内核对象不挂在任何用户进程名下。**条件会变**：若差量随时间单调上涨，而共享内存与内核对象都没有变化，则要回到进程侧按构成去找增长源。

**一句话结论**：常驻计数回答的是这个进程碰到过多少页，而不是它独占了多少页；因此凡说「占用」，都必须先指明是哪一种**占用口径**。

**出处**：`VmRSS` 见 `man 5 proc_pid_status`；`smaps_rollup` 的常驻、均摊与私有口径见 `man 5 proc_pid_smaps`；`RSS` 的列定义见 `man 1 ps`。

## 12. 「`vmstat` 里 `b` 有值，说明有进程卡住了」

**场景**：值班看了一次 `vmstat`，看到阻塞队列那一列的值是 1，就判断「有进程卡在内核态」，并开始按卡死流程排查。

**常见误判**：值班用单点采样下了结论。这个判断看起来成立，因为那一列的语义确实是「处于不可中断睡眠的进程数」。

**判据**：由于那一列是**瞬时计数**，所以单行等于 1 可能只是采样噪声或一次短暂的 IO 脉冲；只有连续多行都有值，才算「确实有进程卡在不可中断睡眠（`D`）里」。同时它既不告诉你**是哪些**进程，也不区分本地设备与网络存储，因此真正的定位要回到进程级的等待点，并逐个设备去看。**条件会变**：若它与换页速率、IO 等待一起升高，那确实是压力；若只是孤立的一两行而其他列都平稳，则要先扩大采样窗口再判断。

**一句话结论**：整机层面的这一列只回答「有没有进程在等」，不回答「谁在等什么」；因此单点采样不能当趋势用。

**出处**：`vmstat` 的 `b` 列定义见 `man 8 vmstat`，它的进程列与内存列都是**瞬时值**，只有首行的速率列是自开机以来的平均值；`/proc/<pid>/wchan` 与 `stack` 见 `man 5 proc_pid_wchan` 与 `man 5 proc_pid_stack`；`man 1 pidstat` 给出 `-w` 的区间速率。

## 第一反应不要做什么

- 不要用整机 CPU 占用去否定单核或单线程的热点；
- 不要用退出码 137 直接断言 OOM；
- 不要对 `D` 状态的进程反复补发 `SIGKILL`，也不要把它当成「已经死了」；
- 不要对僵尸进程发信号；
- 不要以为改了登录会话的限制配置就能影响服务；
- 不要用一个 shell 的限制当成服务的限制；
- 不要用默认的进程列表视图去推算 task 额度；
- 不要在没取到证据之前重启或强杀。

## 要点自测

**问：有人说「服务 CPU 打满」，你要问哪两个问题才能判断是并发度问题还是容量问题？**
答：首先要问占用是每核的还是整机的（去找接近满的那一列）；其次要问线程级分布是热度集中在一个 TID 还是均匀铺开。若热度集中在一个 TID，则属于并发度或热点问题；若均匀铺开，则属于容量问题。

**问：一次 OOM 定性的最小证据集是什么？**
答：最小证据集包含三项：宿主内核日志里的 OOM 记录（整机带 `constraint=CONSTRAINT_NONE` 与 `global_oom`，组级带 `constraint=CONSTRAINT_MEMCG` 与 `oom_memcg=`）、cgroup 事件计数里 `oom_kill` 的差值，以及人工与编排层的操作记录。三者至少要命中一个，否则事故记录只能写「死于 `SIGKILL`，来源待查」。

**问：僵尸堆积为什么有时「杀掉父进程」就好了？**
答：因为退出状态由父进程领取。父进程退出后，僵尸连同其它子进程被最近的收养者接管并回收。但这只在父进程本身不回收时才有效；如果它只是卡在等待资源上，那么正确的动作是去解决父进程所等待的那项资源。

**问：`D` 状态一定杀不掉吗？**
答：不一定。由于有一类内核态等待可以被致命信号打断，而它的外观仍然是 `D`，所以不能凭状态字母下结论；判据是等待点（`wchan`）与内核栈。真正杀不掉的典型是等待块设备或网络存储 IO 的那一类。

**问：为什么「单看 `vmstat` 一列」不能定性？**
答：因为它是瞬时计数，而且只是整机层面的聚合，所以既不能区分噪声与趋势，也不告诉你哪个进程在等什么；要判断就必须用连续窗口加上进程级证据。
