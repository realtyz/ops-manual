## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **进程只有三种死法**：正常退出（有退出码）、被信号杀死（`128+N`）、被 OOM Killer 选中（内核发的 `SIGKILL`）。**三者的证据位置完全不同**。
> - **退出码 137 不等于 OOM**：它是 `128+9`，只说明「被 `SIGKILL` 杀死」；要定性必须去内核日志里找到 OOM 记录，或者找到「有人手工 `kill -9`」的证据。
> - **僵尸不是「没死干净」**，而是**父进程没有回收**：它只剩一个 PID 与退出状态，杀它无效，要处理的是父进程的 `wait()`。
> - **孤儿会被 PID 1 收养**，退出时由收养者回收——这就是「杀父进程有时能解决僵尸堆积」的原因，也是容器里 PID 1 必须会 `wait()` 的原因。
> - **取证顺序永远一样**：先留下「上次启动的日志 + 退出码/信号 + core」，再谈重启。**重启会把大部分现场一起清掉。**

## 1. 三种死法，三套证据

| 死法 | 表现 | 证据在哪里 |
| --- | --- | --- |
| 正常退出 | 退出码 `0`，或应用自定义的非 0（`1`、`2`、`255`…） | 应用日志、`systemctl status` 的 `status=<n>`、shell 里的 `$?` |
| 被信号杀死 | shell 里退出码 `128+N`；systemd 显示 `signal=` | `journalctl -u <svc>`、`systemctl show -p ExecMainCode,ExecMainStatus` |
| 被 OOM Killer 选中 | 内核发的 `SIGKILL`，退出码**同样**是 137 | **只有内核日志**：`dmesg` / `journalctl -k` 的 OOM 记录；cgroup v2 的 `memory.events` |

```bash
echo $?                              # 验证：上一条命令的退出码（128+N 表示被信号 N 杀死）
systemctl status <svc>               # 验证：Process 段会写明 code=exited/killed 与 signal=
systemctl show -p ExecMainCode -p ExecMainStatus -p Result -p ExecMainExitTimestamp <svc>
                                     # 验证：脚本抓取时用这几个字段（exited/killed + 退出码或信号号 + 结果）
journalctl -u <svc> --since '30 min ago' | tail -50   # 验证：服务自己的日志（应用层面的死因）
journalctl -k -b | grep -i -E 'out of memory|oom-kill|killed process'
                                     # 验证：OOM Killer 的完整选择过程（含被选中进程的 RSS 与打分）
```

### 1.1 退出码对照表

| 退出码 | 含义 | 注意 |
| --- | --- | --- |
| `0` | 成功 | — |
| `1` | 通用错误 | 应用自定义，必须看日志 |
| `2` | 用法错误 / 参数不对 | 常见于脚本 |
| `126` | 找到了命令但无法执行 | 权限不足、不是可执行文件 |
| `127` | 命令未找到 | 脚本里 PATH 不对、依赖缺失 |
| `137` | `128 + 9`：被 `SIGKILL` 杀死 | **可能来自 OOM，也可能来自人工 `kill -9`**，靠内核日志与操作记录区分 |
| `143` | `128 + 15`：被 `SIGTERM` 终止 | 常见于 `systemctl stop` 到期后系统主动发的 `TERM` |
| `203` | systemd 自有代码：`EXEC` 失败 | 二进制不存在、权限不对、shebang 有问题——**是「压根没起来」，不是「退出」** |

systemd 还有一批自有退出码（`200/CHDIR`、`216/GROUP`、`226/NAMESPACE` 等），含义可以用 `systemd-analyze exit-status <code>` 查，不要硬背；**较老的 systemd（如 RHEL 8 自带的 239）没有这个子命令**，那就查 `systemd-analyze --help` 或 `man systemd.exec` 里的退出码一节。

## 2. 定性 OOM：一条完整的判定链

**只有内核知道 OOM 是不是它干的**，所以要按顺序查三处，任一处命中即可定性：

1. **整机内核日志**：`journalctl -k -b | grep -i oom`，会打印候选进程的打分与被选中者（`Killed process <pid> (<comm>) total-vm:... anon-rss:...`）；
2. **cgroup 级计数**（cgroup v2）：`/sys/fs/cgroup/.../<unit>/memory.events` 里的 `oom`、`oom_kill` 计数递增，是容器/服务级 OOM 的确凿证据；
3. **人工证据**：堡垒机操作记录、`audit` 日志、变更单——用来排除「有人手工 `kill -9`」。

```bash
journalctl -k -b --no-pager | grep -i -E 'oom|killed process' | tail -20
cat /sys/fs/cgroup/system.slice/<svc>/memory.events    # 验证：oom / oom_kill 计数（cgroup v2）
cat /proc/<pid>/oom_score /proc/<pid>/oom_score_adj    # 验证：某进程的 OOM 打分与人工调整值
cat /proc/sys/vm/panic_on_oom                          # 验证：内核在 OOM 时的行为（0=挑一个进程杀；1=只在受限场景 panic；2=总是 panic）
```

> [!important] 137 的来源必须说清
> 「退出码 137」只回答「它是被 `SIGKILL` 杀死的」。**要写进复盘的是「谁发的 `SIGKILL`」**：内核 OOM（有日志）、人工/脚本（有操作记录）、容器运行时超时后强杀（`docker stop` 超时，见第 4 节）。三者处置完全不同——OOM 要调容量或改内存模型，人工的要查流程，运行时超时的是应用没处理 `SIGTERM`。

## 3. 回收：僵尸、孤儿，以及容器里的 PID 1

### 3.1 僵尸（Z）：已经死了，等父进程收尸

子进程退出后，**退出状态要交给父进程**，内核会暂时保留它的 `task_struct` 与 PID，直到父进程调用 `wait()`/`waitpid()`。于是：

- `kill -9` 对僵尸**无效**（它已经终止了），**要处理的是它的父进程**；
- 父进程及时 `wait()` → 立即回收；父进程自己先退出 → 子进程（含僵尸）被 PID 1 收养并由 PID 1 回收，所以**「杀父进程有时能解决僵尸堆积」**；
- 把 `SIGCHLD` 的处置显式设为 `SIG_IGN` 时，内核会自动回收子进程——这是「不需要 `wait()` 也不会变僵尸」的唯一例外；默认处置（`SIG_DFL`）不会自动回收。

```bash
ps -eo pid,ppid,stat,comm | awk '$3 ~ /Z/ {print}'   # 验证：当前所有僵尸与它们的父进程
ps -o pid,stat,wchan:20,cmd -p <ppid>                # 验证：僵尸的父进程是谁、状态如何（父进程卡在 D，僵尸就会堆积）
ps -eo pid,ppid,stat | grep -c Z                     # 验证：僵尸数量（写进基线的观察项）
```

### 3.2 孤儿（orphan）：父进程先走了

父进程先退出、子进程还活着，这些进程会被「重新挂到」PID 1（或最近的 subreaper）名下。它本身不是故障，但会让守护进程的父子关系变得难以追踪——`ps --forest` 里一大片挂在 PID 1 下的进程，多半是这么来的。

### 3.3 容器把这两件事一起放大了

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `docker stop` 等满超时后强杀，退出码 137 | 容器里的 PID 1 是 `bash` 之类的程序，**没有为 `SIGTERM` 注册处理函数**；内核对 PID 1 不执行默认动作 → `SIGTERM` 等于被忽略 → 超时后由宿主侧 `SIGKILL` | 应用自己处理 `SIGTERM`；或用 `tini`/`dumb-init`、`docker run --init` 作为 PID 1 转发信号 |
| 容器里 `ps` 显示一堆 `<defunct>` | PID 1 不回收被收养的孤儿进程 | 换成真正的 init（tini/`--init`），或让应用主进程自己做 `waitpid(-1, ...)` 循环 |
| 宿主机上 `kill -9 1` 毫无反应 | 主机 PID 1 受内核保护，`SIGKILL` 被忽略 | 不要试图杀 PID 1；用 `systemctl` 或 `reboot` |

```bash
docker exec <ctr> ps -p 1 -o pid,ppid,stat,comm,args   # 验证：容器里的 PID 1 到底是谁
docker exec <ctr> ps -eo pid,ppid,stat,comm | grep Z   # 验证：容器内是否有僵尸堆积
systemctl show -p KillMode -p KillSignal -p TimeoutStopUSec <svc>   # 验证：宿主侧停止服务的行为
```

## 4. 生产动作：处理一次僵尸堆积（S3、S7）

> [!example]+ 生产动作：僵尸进程堆积的取证与处置
> **什么时候用**：`ps` 里出现几十上百个 `<defunct>`，或者监控里的进程数异常上涨。
>
> **动手前确认**：
> 1. **先取证**：僵尸数量、父进程是谁、父进程状态、出现的时间点——这些数据一旦重启就没了；
> 2. **判断是「父进程卡住」还是「父进程不会 wait」**：前者随父进程恢复而自动消失，后者只能改程序或重启父进程；
> 3. **确认父进程是什么**：是业务进程？是 systemd 服务？还是容器里的 PID 1？处置方式完全不同。
>
> **怎么做**：
> ```bash
> ps -eo pid,ppid,stat,comm | awk '$3 ~ /Z/ {print}' | tee /tmp/zombie-$(date +%F-%H%M).txt
>                                                    # 验证：僵尸清单已留档（含时间戳）
> ps -eo pid,ppid,stat,comm | awk '$3 ~ /Z/ {print $2}' | sort | uniq -c | sort -rn
>                                                    # 验证：按父进程聚合，找出「谁制造得最多」
> ps -o pid,ppid,stat,wchan:20,etime,cmd -p <ppid>   # 验证：父进程自身的状态（D 状态要先按 05 篇处理）
> pstree -p <ppid> | head -30                        # 验证：父进程名下的进程树规模
> ```
> **怎么处置**（按优先级）：
> 1. 父进程在 `D` 状态 → 先解决它等待的资源（IO/网络存储），僵尸会随它恢复或退出而消失；
> 2. 父进程是「不会 `wait()` 的程序」→ 列入缺陷单改程序；紧急情况下重启该父进程（它退出后僵尸被 PID 1 收养并回收）；
> 3. 父进程是容器里的 PID 1 → 给容器加 init（`--init`/tini），或让应用主进程负责回收。
> **怎么验证**：僵尸数量回到基线（通常是 0）；父进程恢复后 `ps` 里不再出现 `Z`。
> **怎么退回去**：这一步没有「回滚命令」——**重启父进程本身就是不可逆操作**（会中断它当前的业务）。所以动手前必须先确认它是否持有在途数据。

## 5. 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 「退出码 137 就是被 OOM 杀了」 | 137 只说明被 `SIGKILL`；人工 `kill -9`、容器停止超时后强杀都会得到 137，必须去内核日志/操作记录里定性 |
| 「僵尸占内存，要赶紧清掉」 | 僵尸几乎不占内存，占的是 PID 与进程表项；**杀僵尸无效**，要治父进程；堆积过多会耗尽 PID |
| 批量 `kill -9` 所有 `<defunct>` | 僵尸已经是死的，命令不报错也不生效；只会掩盖真正的问题（父进程） |
| 「服务自己退出了，重启就好」 | 退出码 `0` 却被 systemd 判为失败，多半是 `Type=` 配错；重启前先取 `journalctl -u` 与 `ExecMainCode/Status` |
| 看到「服务每隔几分钟重启一次」直接关掉 `Restart=` | 掩盖了崩溃循环（CrashLoop）；先确认是 OOM、崩溃还是启动失败（子笔记 10、12） |
| 在容器里让业务进程直接当 PID 1 | 它默认不处理 `SIGTERM`、也不回收孤儿，于是「停不掉 + 僵尸堆积」同时出现 |
| 用 `kill -9 1` 重启 systemd | 静默失败；PID 1 不接收未处理的信号（这是保护，不是权限问题） |
| 复盘只写「进程被杀了」 | 没有「谁杀的、为什么杀、下次怎么避免」的复盘无法沉淀成 Runbook（S8） |

## 6. 决策练习

> [!question]- 场景：凌晨 3 点告警「服务重启」，你上线看到服务已经自动恢复运行。`systemctl status` 的 `Result=signal`，`ExecMainStatus=9`
> 你的下一步是什么？
> A. 先取证据：`journalctl -k -b | grep -i oom` 查内核有没有 OOM 记录、`journalctl -u <svc> -b` 看服务退出前后的日志、`coredumpctl list` 看有没有 core，并把这次跟历史重启次数对齐
> B. 服务已经恢复，先睡，明天再说
> C. 马上再重启一次服务，观察是否复现
>
> **答案：A。**
> B 的问题在于：证据有保质期——内核环缓冲会被覆盖、journal 若未持久化则重启即失，等到明天可能什么都查不到。
> C 会在最需要证据的时候把现场清掉：重启会重置计数与内存状态，而且如果根因是 OOM，重启只会让它再来一次。
> A 是正解：`Result=signal` + `ExecMainStatus=9` 已经告诉你「被 `SIGKILL` 杀死」，接下来要做的是**定性（谁发的）**，而不是「恢复（它已经恢复了）」。这条链路正是 S3 取证的标准动作。

## 7. 要点自测

> [!question]- 进程莫名消失，你怎么区分「自己退出」「被信号杀死」「被 OOM 选中」？
> - 自己退出：`ExecMainCode=exited`，有退出码，应用日志通常有正常收尾记录。
> - 被信号杀死：`ExecMainCode=killed`，`ExecMainStatus` 是信号号；shell 里是 `128+N`（143=TERM、137=KILL）。
> - 被 OOM 选中：退出状态同样是 137/9，**必须**在内核日志里找到 OOM 记录，或看到 cgroup v2 `memory.events` 的 `oom_kill` 计数增加。
> - **第一反应不要是什么**：不要用退出码 137 直接断言 OOM；也不要先重启——重启会把内核日志里的现场一起冲淡。

> [!question]- 僵尸进程的成因与解法？为什么「杀父进程」有时能解决？
> - 成因：子进程已退出，父进程没有 `wait()` 回收，内核保留其 PID 与退出状态。
> - 解法：修父进程（加 `waitpid` 或处理 `SIGCHLD`）；`SIGCHLD` 被设为 `SIG_IGN` 时内核自动回收（唯一例外）；父进程卡在 `D` 时先治父进程。
> - 杀父进程有效的原因：父进程死后僵尸被 PID 1 收养并由 PID 1 回收；容器里则取决于那个 PID 1 是否真的回收子进程。
> - **第一反应不要是什么**：不要对僵尸本身发信号，它已经终止了——你看到的这个「进程」只剩一个待回收的壳。

> [!question]- 容器里 PID 1 是 `bash` 时，`docker stop` 为什么会超时、最后被强杀？
> - 信号侧：内核对 PID 1 不执行信号默认动作，而 `bash` 默认没有为 `SIGTERM` 注册处理函数 → `SIGTERM` 等于被忽略 → 超时后宿主侧 `SIGKILL`，所以退出码是 137。
> - 回收侧：`bash` 不会主动回收被重新挂到它名下的孤儿/孙进程，容器里于是堆 `<defunct>`。
> - 正确做法：应用自己处理 `SIGTERM` 并等待子进程；或用 tini/dumb-init、`docker run --init` 充当 PID 1；`CMD` 用 exec 形式让应用真正成为 PID 1。
> - **第一反应不要是什么**：不要靠延长停止超时来「修」这个问题——那只会让每次发布更慢，收尾依旧没人做。
