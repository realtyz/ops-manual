## 1. 实验 0：只读观测（零风险，先做这个）

```bash
date; hostname; uptime                     # 验证：时间基线与负载
uname -r; systemd --version | head -1      # 验证：内核与 systemd 版本（决定默认限制）
stat -fc %T /sys/fs/cgroup                 # 验证：cgroup2fs = v2；其它输出要按 v1 处理
ps -e --no-headers | wc -l                 # 验证：进程（线程组）总数
ps -eLf --no-headers | wc -l               # 验证：task 总数（含线程）——两者之差就是线程带来的量
ps -eo pid,ppid,stat,pcpu,pmem,etimes,time,comm --sort=-pcpu | head -20
                                           # 验证：CPU Top 20（etimes 是运行时长，time 是累计 CPU 时间）
ps -eo pid,nlwp,rss,comm --sort=-rss | head -15     # 验证：内存 Top 15 与各自线程数
cat /proc/loadavg                          # 验证：负载与「最近分配的 PID」（连看两次可估算消耗速率）
sysctl kernel.pid_max kernel.threads-max fs.nr_open fs.file-max vm.max_map_count
                                           # 验证：内核级上限基线
cat /proc/sys/fs/file-nr                   # 验证：已分配 / 空闲 / 系统上限的句柄水位
ulimit -Sa; ulimit -Ha                     # 验证：当前会话的软/硬限制基线
systemctl show -p DefaultLimitNOFILE -p DefaultTasksMax   # 验证：systemd 给服务的默认限制
loginctl list-sessions                     # 验证：本机有哪些登录会话（会话与终端的对应关系）
systemd-cgls | head -30                    # 验证：cgroup 树（服务 → 进程的归属）
systemd-cgtop -m                           # 验证：各组的内存/CPU/IO 实时占用（交互式，看一眼后 Ctrl+C）
```

**预期**：`ps -eLf` 的行数明显大于 `ps -e`（线程不少）；`DefaultLimitNOFILE` 与 `DefaultTasksMax` 给出服务层的默认值——很多「服务偶尔报 `too many open files`」的根因就在这里，而它跟 `/etc/security/limits.conf` 一点关系都没有。

**环境**：任意 systemd 发行版。建议隔一段时间再做一次，两次对比才有意义。

**风险**：无，全部只读。

**耗时**：约 20 分钟。

**回滚**：无需回滚。把输出存成一份基线文件。

**要沉淀什么**：这份输出就是 T1 要求的「进程基线卡」，包含版本、进程/task 数量、CPU 与内存 Top、内核上限、句柄水位、systemd 默认限制、cgroup 树。

## 3. 总自测

题目前带 **【进阶】** 的对应笔记里的进阶小节，答不上来不影响阶段 3 过关。其余题目要求能**盖住答案脱稿讲 3~5 分钟**。

> [!question]- 内核眼里的「调度单位」是什么？它和「进程」「线程」是什么关系？
> - 调度单位是 **task**；进程 = 一组共享地址空间的 task + 一个 TGID（就是 `ps` 里的 PID），线程 = 同一 TGID 下的 task。
> - 因此「线程」不是内核里的一种独立实体，差别只在共享了哪些资源（地址空间、fd 表、信号处理）。
> - 观察方式：`ps -eLf`（LWP 列即 TID）、`/proc/<pid>/task/`、`top -H`。
> - **第一反应不要是什么**：不要用 `ps aux` 数进程去推算「task 还剩多少额度」——统计口径不对。

> [!question]- `R/S/D/T/t/Z/I` 各是什么？`D` 状态为什么杀不掉，接下来查什么？
> - `R` 运行/可运行、`S` 可中断睡眠、`D` 内核态不可中断等待、`T` 作业停止、`t` 被调试器挂住、`Z` 僵尸、`I` 空闲内核线程。
> - `D` 杀不掉是因为信号要等进程回到用户态才处理，而它正卡在内核态等待；`TASK_KILLABLE` 属于可被致命信号打断的例外，但仍显示为 `D`。
> - 下一步：`wchan`、`/proc/<pid>/stack`，再看 `iostat`/`dmesg`/`/proc/mounts` 找它等待的链路；出现 `hung task` 报警时重点查存储与驱动。
> - **第一反应不要是什么**：不要连续 `kill -9`，也不要直接重启——重启既清现场也不保证不复发。

> [!question]- `SIGTERM` 与 `SIGKILL` 的差别是什么？`kill -9` 的代价具体有哪些？
> - `SIGTERM` 可捕获、可忽略，用于优雅退出；`SIGKILL` 不可捕获、不可阻塞、不可忽略，只保证进程消失。
> - 代价：数据库未落盘事务丢失、消息队列未提交状态残留、批处理文件写一半、文件锁中间状态未回滚、共享内存段残留、脚本子进程变孤儿占端口。
> - 判断要不要用：进程有没有在途数据、有没有持锁、停下之后有没有别人接力。
> - **第一反应不要是什么**：不要把「进程没了」当成「服务正常停止了」。

> [!question]- 进程莫名消失，你怎么区分「自己退出」「被信号杀死」「被 OOM 选中」？
> - 自己退出：`ExecMainCode=exited` + 退出码，应用日志有收尾记录。
> - 被信号杀死：`ExecMainCode=killed` + 信号号（shell 里是 `128+N`；143=TERM、137=KILL）。
> - 被 OOM 选中：退出状态同样是 137/9，**必须**在内核日志（`journalctl -k`）里找到 OOM 记录，或看到 cgroup v2 `memory.events` 的 `oom_kill` 计数增加。
> - **第一反应不要是什么**：不要用 137 直接断言 OOM，也不要先重启——内核日志与 `-b -1` 的现场会被冲淡。

> [!question]- 崩溃之后留不下 core，按什么顺序排查？
> - 四道闸门：`RLIMIT_CORE`（`ulimit -c` / unit 的 `LimitCORE=`）→ `core_pattern`（写文件还是管道）→ `fs.suid_dumpable` → 落点是否可写且有空间。
> - 落点有三种：`systemd-coredump` 的 `/var/lib/systemd/coredump/`、`apport` 的 `/var/crash/`、以及文件名模板模式的「进程工作目录」。
> - 读取入口：`coredumpctl list/info/debug/dump`；没有 debuginfo 时只能看信号、栈地址、寄存器与映射。
> - **第一反应不要是什么**：不要靠「再崩一次」等它出现——反复崩溃会先把磁盘吃掉。

> [!question]- 资源上限的五层是什么？为什么改 `limits.conf` 对 systemd 服务无效？
> - 五层：`ulimit`（会话）→ `limits.conf`/PAM（登录会话）→ unit 的 `LimitXXX=`/`TasksMax=`（服务）→ cgroup（整组）→ 内核全局（sysctl）。
> - 服务的进程由 systemd 直接 `fork`+`exec`，不经过 PAM 登录会话，所以不读 `limits.conf`；它读 unit 的 `LimitXXX=` 与 `DefaultLimitXXX=`。
> - 验收标准只有一个：`/proc/<pid>/limits`（或对应的 cgroup 文件）里的**实际值**。
> - **第一反应不要是什么**：不要在 `limits.conf` 里改完就重启服务然后疑惑「为什么不生效」。

> [!question]- 机器进程数到上限会发生什么？怎么快速定位是谁在创建进程？
> - 现象：`fork: Resource temporarily unavailable`（`EAGAIN`）；cgroup 场景内核日志有 `cgroup: fork rejected by pids controller`；业务表现为「偶发无法接收新连接」。
> - 四条上限：`kernel.pid_max`、`kernel.threads-max`、`RLIMIT_NPROC`（按 real UID）、cgroup 的 `pids.max`。
> - 定位创建者：`/proc/loadavg` 最后一列连看两次算速率；`ps -eo user,ppid,comm | sort | uniq -c` 聚合源头；`pidstat`/`execsnoop` 追父进程。
> - **第一反应不要是什么**：不要只调大 `ulimit -u`，也不要先杀进程——先留下「谁在批量创建」的证据。

> [!question]- `too many open files` 的定位顺序？句柄耗尽一定是泄漏吗？
> - 顺序：定位进程（`file-nr` 看整机、`/proc/<pid>/fd` 看进程）→ 看构成（套接字还是普通文件）→ 确认限制链（`limits`、`fs.nr_open`、`fs.file-max`、`LimitNOFILE=`）。
> - 不一定是泄漏：长连接多、日志文件多都可能是设计使然；**长期单调上涨**才算泄漏。
> - 老程序用 `select()` 时受 `FD_SETSIZE`（通常 1024）限制，调 `ulimit -n` 也没用。
> - **第一反应不要是什么**：不要直接把上限调到一百万，也不要在没留档的情况下重启。

> [!question]- 僵尸与孤儿的成因与解法？容器里的 PID 1 特殊在哪？
> - 僵尸：子进程已退出但父进程未 `wait()`；解决要靠父进程（加 `waitpid`/处理 `SIGCHLD`），`SIGCHLD` 设为 `SIG_IGN` 时内核自动回收；**杀僵尸无效**。
> - 孤儿：父进程先退出，子进程被 PID 1（或最近的 subreaper）收养；这正是「杀父进程有时能清掉僵尸」的原因。
> - 容器 PID 1 的两个责任：转发/处理信号（内核不对它执行信号默认动作）与回收被收养的孤儿；缺了就用 tini/`--init` 补上。
> - **第一反应不要是什么**：不要试图杀僵尸，也不要靠延长 `docker stop` 超时来「修」停机问题。

> [!question]- namespace 和 cgroup 分别解决什么问题？构成容器的四层是什么？
> - namespace 管**看得见什么**（`pid`/`net`/`mnt`/`user`…），cgroup 管**能用多少**（`cpu`/`memory`/`io`/`pids`），两者互不替代。
> - 容器 = namespace + cgroup + rootfs/联合文件系统 + 权限约束（capabilities/seccomp/SELinux）。
> - 与虚拟机最本质的差别：**共享同一个内核**，隔离靠内核机制而非硬件虚拟化。
> - **第一反应不要是什么**：不要用「容器就是轻量虚拟机」来解释——这句话会带出一连串错误推论。

> [!question]-【进阶】nice、`cpu.weight`、`taskset` 分别解决什么问题？
> - `nice`：同一组内的相对优先级（`-20~19`），只在 CPU 竞争时起作用。
> - `cpu.weight`：cgroup 之间的 CPU 分配权重；`cpu.max` 才是硬上限。
> - `taskset`：单进程的 CPU 亲和，与 cgroup 的 `cpuset` 取交集。
> - `chrt`：改变调度策略（含实时调度），能越过 nice 的所有规则——生产上要极其克制，并知道 RT 节流参数的存在。
> - **第一反应不要是什么**：不要用「调高优先级」掩盖设计问题，先量化瓶颈。
