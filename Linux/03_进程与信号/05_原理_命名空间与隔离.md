# 命名空间与隔离

## 1. 互不看见，要同时解决四类冲突

多个应用共享一个内核时，冲突不是一种，而是四种，各自有各自的机制：

| 冲突 | 具体表现 | 由谁解决 |
| --- | --- | --- |
| 命名 | 两个应用都要求自己是一号进程、都要求绑定 80 端口、都要求自己是 uid 0，而且都要用同一个主机名 | 由命名空间解决 |
| 视图 | 一个应用不该看见另一个应用的进程、挂载点、网卡与 IPC 队列 | 由命名空间解决 |
| 权限 | 在已经划分好的视图里，某个进程是否有权挂载文件系统、修改网络参数、给别的进程发信号 | 由 capability 与强制访问控制解决 |
| 数量 | 它决定一组进程最多能用多少 CPU、多少内存、多少个任务与多少 IO 带宽 | 由 cgroup 解决 |

**命名空间只负责前两类：它改变的是「看得见什么」与「编号是什么」，而不是「能用多少」。** 由于「能用多少」由 cgroup 与 `RLIMIT_*` 这类进程资源限制决定，所以命名空间与它们回答的是两个不同的问题，彼此不能互相替代。把这四类分开是理解容器的第一步——四类里只有前两类由命名空间提供，而日常排障最常撞上的恰恰是第四类。

## 2. 八种切分，各自只隔离一样东西

内核里没有一个叫「容器」的对象。所谓隔离，是把八种互相独立的切分按需组合，每一种只改一个资源的命名与视图（类型表见 `man 7 namespaces`）：

| 类型 | 创建标志 | 隔离的资源 | 引入版本 | 最容易踩的边界 |
| --- | --- | --- | --- | --- |
| Mount | `CLONE_NEWNS` | 挂载点与整棵挂载树 | 2.4.19 | 挂载事件会按传播类型传播到别的命名空间，所以一次挂载未必只影响本命名空间 |
| UTS | `CLONE_NEWUTS` | 主机名与 NIS 域名 | 2.6.19 | 它只改主机名与 NIS 域名这两个名字，不改别的身份标识 |
| IPC | `CLONE_NEWIPC` | System V IPC 与 POSIX 消息队列 | 2.6.19 | 它与网络无关，因此不要与网络命名空间混为一谈 |
| PID | `CLONE_NEWPID` | 进程编号空间 | 2.6.24 | 它的编号是树状嵌套的，只改编号，不改归属与计数 |
| Network | `CLONE_NEWNET` | 网络设备、协议栈、端口、路由、邻居表、连接跟踪表 | 2.6.24 | `net.core.*` 一类全局参数不在它管辖的范围内，因此这些参数不随网络命名空间独立 |
| User | `CLONE_NEWUSER` | 用户与组 ID 的映射、capability 的作用域 | 3.8 | 它是唯一不需要特权就能创建的一类，因此非特权进程也能用它 |
| Cgroup | `CLONE_NEWCGROUP` | cgroup 根目录的可见路径 | 4.6 | 它只改 `/proc/<pid>/cgroup` 里看到什么，不改计量归属 |
| Time | `CLONE_NEWTIME` | `CLOCK_MONOTONIC` 与 `CLOCK_BOOTTIME` | 5.6 | 它不虚拟化 `CLOCK_REALTIME`，因此墙上时间不在其中 |

这八种互不依赖，可以任意组合：只用网络命名空间就是一次网络实验，把八种全用上再加一个根文件系统，才接近日常说的「一个容器」。版本一栏的读法是：**低于该版本的内核上，对应的标志位不存在，`clone`/`unshare` 会直接失败**，而不是静默降级；因此跨发行版迁移时，它是第一个必须核对的版本判据。

Time 命名空间在用法上还有一个不同：它是目前唯一只能由 `unshare(2)` 创建的一类（`clone` 的 `CLONE_NEWTIME` 不能用来建新进程），而且要求调用者持有 `CAP_SYS_TIME`，否则返回 `EPERM`；命名空间内的偏移通过 `timens_offsets` 写入。它与 PID 命名空间配合，才有「容器里看到的开机时长与宿主无关」这类性质。

## 3. 创建、加入与存活：三套接口的分工

| 入口 | 做什么 | 关键约束 |
| --- | --- | --- |
| `clone(2)` 带 `CLONE_NEW*` | 它创建一个新进程，并让这个进程出生在新的命名空间里 | 一次调用可以同时创建多种命名空间 |
| `unshare(2)` 带 `CLONE_NEW*` | 它把调用者本身移入新建的命名空间 | 调用之后调用者本身仍留在原来的 PID 命名空间里，**只有新创建的子进程才进入新的命名空间** |
| `setns(2)` | 它让调用者加入一个已经存在的命名空间 | 目标命名空间由 `/proc/<pid>/ns/*` 的文件描述符指定 |

`ioctl_ns(2)` 提供查询命名空间类型与父子关系的一组操作。这三套接口之外，还有一个不需要新系统调用的判据：**两个进程是否在同一个命名空间，比较 `/proc/<pid>/ns/<类型>` 符号链接的 `st_dev` 与 `st_ino` 是否相同**（Linux 3.8 起这些条目是符号链接，此前是硬链接）。同一对数值就表示同一个命名空间——这是宿主侧判断「这两个进程是不是一个容器里的」最直接的一步。

权限与版本门控是创建与加入命名空间时最容易记错的一段：

| 动作 | 需要的特权 | 版本门控 |
| --- | --- | --- |
| 创建除 user、time 外的命名空间 | 调用者必须在它所属的 user 命名空间里持有 `CAP_SYS_ADMIN` | 它取决于上表列出的引入版本 |
| 创建 user 命名空间 | 这一步不需要任何特权 | 该能力自 3.8 起；在 3.8 之前创建它需要三项 capability |
| 创建 time 命名空间 | 调用者必须持有 `CAP_SYS_TIME`，而且只能用 `unshare(2)` 创建 | 该能力自 5.6 起 |
| 加入一个 user 命名空间 | 调用者必须在目标命名空间里持有 `CAP_SYS_ADMIN` | 调用者加入之后，会在该命名空间内获得完整的 capability 集 |
| 加入非 user 的命名空间 | 调用者必须在自己的 user 命名空间与目标命名空间所属的 user 命名空间里**都**持有 `CAP_SYS_ADMIN` | 若上述条件不满足，则内核返回 `EPERM` |
| 嵌套深度超限 | 这一条不做特权判断，而是直接失败 | PID 命名空间的嵌套上限是 32 层（3.7 起），user 命名空间同样是 32 层（3.11 起）；一旦超限，内核返回 `ENOSPC` |

32 这个数字的读法是：**它是嵌套层数（层），不是容器数量**，判据是把 `clone`/`unshare` 的返回值与 errno 对上——报 `ENOSPC` 就说明撞的是这条上限，而不是内存不足；它与「这台机器能跑多少个容器」无关，同一层里可以并存很多个兄弟命名空间。

命名空间没有名字，也没有独立的生命周期开关，**它的存活条件是仍被引用**：只要还有一个进程在里面，或者有进程持有 `/proc/<pid>/ns/*` 的文件描述符、或把它绑定挂载到了别处，这个命名空间就不会被回收；最后一个引用消失才释放。这解释了宿主侧的一类现象：容器进程已经退出，相关的命名空间与挂载却仍然占着，直到持有文件描述符的那个进程（往往是运行时或你的诊断 shell）退出。`/proc/<pid>/ns/pid_for_children` 与 `time_for_children` 是这条规则的一个特例入口，它们表示「接下来创建的子进程会进入哪个 PID（时间）命名空间」，而不是当前进程自己所属的那一个。

## 4. user 命名空间：没有特权也能造出一个「局部 root」

user 命名空间之所以关键，是因为它把「隔离」与「特权」解耦了：**在一个新建的 user 命名空间里，进程立刻拥有完整的 capability 集，但这些 capability 的作用域只覆盖由这个 user 命名空间及其后代所拥有的资源**；对初始 user 命名空间（系统启动时的那个）来说，它依然是一个普通进程。于是「rootless 容器」成立，同时「userns 是提权面」也成立——同一件事的两面。

ID 映射的机制与限制（依据 `man 7 user_namespaces`）：

| 项 | 事实 | 读法与判据 |
| --- | --- | --- |
| 映射文件 | 映射写在 `/proc/<pid>/uid_map` 与 `/proc/<pid>/gid_map` 这两个文件里 | 读法是每行三个数，它们依次是容器内的起始 ID、父命名空间中的起始 ID 与区间长度 |
| 未映射的 ID | 未映射的 ID 会显示为 `overflowuid` / `overflowgid`，两者的默认值都是 65534 | 看到 65534 并不表示「有一个 uid 叫 65534」，而是表示「这个 ID 没有映射」，所以要去读 `/proc/sys/kernel/overflowuid` 与映射文件 |
| 写入次数 | 每个 user 命名空间的映射文件只能写一次，第二次写入会返回 `EPERM` | 由于映射写不了第二次，所以它必须在容器内进程开始做事之前定好，事后改不了 |
| 行数上限 | 映射文件的行数上限自 Linux 4.15 起是 340 行，在 4.14 及以前是 5 行 | 若想表达一段不连续的 ID 区间，则行数是硬约束，一旦超限，写入就会失败 |
| 可映射的 ID 个数 | 可映射的 ID 个数由每行第三个数的累加值决定，而主机侧可供分配的区间来自 `/etc/subuid`、`/etc/subgid` 与 `newuidmap`/`newgidmap` | 容器内最多能用多少个不同的 uid，取决于这份分配，**默认值现场取**；若把文件 `chown` 到区间外的 ID，则操作会失败或落到 65534 |

量级上的直觉：常见的 subuid 分配是每用户六万多个 ID（现场取 `/etc/subuid` 核对），换算下来容器内可区分的 uid 数就是这个量级。由此产生一个很具体的现象：**rootless 容器里 `chown` 到某个 ID 失败，往往不是权限不够，而是那个 ID 不在映射区间内**；此时要看的字段是 `uid_map` 的行与 `/etc/subuid`，而不是 capability。

正因为 userns 里的 `CAP_SYS_ADMIN` 能挂载 overlayfs（内核 5.11 起允许在 user 命名空间内挂载）、能建网络命名空间、能挂 `proc` 与 `sys` 的一部分，攻击面随之扩大，发行版开始对它设限：Ubuntu 24.04 起默认用 AppArmor 限制非特权 user 命名空间（`kernel.apparmor_restrict_unprivileged_userns`），被拒绝时表现为 `EPERM` 且**不产生** `apparmor="DENIED"` 审计记录；Debian 系另有 `kernel.unprivileged_userns_clone` 开关。`/proc/sys/user/max_user_namespaces` 一类总量上限也在这里起作用。这一层与权限那一章的口径一致：能力足够但被强制访问控制拦住，是两套机制叠加的结果，不要互相替代。

## 5. 隔离不是一件事：命名空间只占其中一层

| 你期望的效果 | 实际由谁提供 | 判据落在哪 |
| --- | --- | --- |
| 容器里的进程看不见别人的进程与网卡 | 命名空间（PID、Network） | 判据是 `/proc/<pid>/ns/pid` 与 `/proc/<pid>/ns/net` 两个符号链接的 `st_ino` |
| 这个容器用不超过两核 CPU、不超过 2 GiB 内存 | cgroup | 判据是宿主侧的 `cpu.max` 与 `memory.max`，而容器内的 `top` 与 `free` 给不出这个答案 |
| 进程改不了别人的文件，也发不了信号 | 文件权限、capability、强制访问控制 | 判据是进程的实际 uid 与有效 capability 集，以及强制访问控制策略留下的拒绝记录 |
| 容器读不到宿主的整机内存 | 没有哪一层提供这个效果 | 容器内的 `/proc/meminfo` 报的仍然是宿主口径，而容器自己的额度写在 cgroup 的 `memory.max` 里 |

所以「容器」这个词在机制上对应四件东西：**命名空间提供可见范围，cgroup 提供可用量，根文件系统与联合挂载提供文件来源，而权限约束由 capability、`seccomp` 与强制访问控制提供**。少任何一层都不成其为容器；而它与虚拟机最本质的差别只有一条——**共享同一个内核**，因此容器能用上哪些内核特性由宿主内核决定，内核级缺陷的影响面也天然更大。

联合挂载这一层的完整判据（首次写触发的 copy-up、删除留下的 whiteout、`df` 与 inode 读数为什么不等于普通文件系统）在存储那一章的《容量边界、挂载与可见性》里展开；在隔离这一层上要记住的只有一句：**它让同一个路径在两个视角下可以是不同的文件**，因此「容器里删了文件」与「容器里看到的文件大小」这两类结论都不能直接搬到宿主侧。

## 6. 机制在本名与字段上的边界

1. **所有容器共享同一个内核。** 命名空间是内核里的数据结构，不是虚拟化边界；由于所有容器都跑在同一个内核里，所以一条内核缺陷可以跨过全部命名空间。隔离强度是「够不够用」的问题，不是「等价于虚拟机」的问题。
2. **有些东西根本没有对应的命名空间。** 除了 UTS 的主机名与 Time 的两个单调时钟，时间基线、平均负载、页缓存与内存计量、`/sys` 与设备节点、以及 `net.core.*`、`kernel.*` 这类全局参数都不在命名空间的管辖范围内（`net.ipv4.*` 才随网络命名空间独立）。因此「每一类资源都能被隔开」是错误的期望。
3. **祖先命名空间能看见并影响后代，反过来不成立。** 宿主能读到容器进程所属 cgroup 的计数字段（`memory.current`、`pids.current`），能对它发 `SIGKILL`，也能进它的命名空间取证；反之，后代看不见也管不了祖先。PID 1 在同一个 PID 命名空间内受信号保护，但来自祖先命名空间的致命信号会被强制投递，这条例外正是宿主能停掉容器一号进程的原因。
4. **命名空间的回收不是即时的。** 只要还有进程在里面，或者还有 `/proc/<pid>/ns/*` 的文件描述符、绑定挂载引用着它，命名空间就继续存在。排查「容器停了但东西还在」时，先找持有引用的人，而不是先怀疑内核。
5. **挂载传播会把一次挂载带到别的命名空间。** 挂载事件按传播类型（`shared`/`slave`/`private`/`unbindable`，共享子树自 2.6.15 起）在命名空间之间传递，而 `/proc/<pid>/mountinfo` 里能看到当前的传播标记。因此说「在容器里挂载不影响宿主」之前，得先确认这个标记——它不是一个恒定成立的前提。
6. **权限是叠加的，不是替代的。** 由于 capability 足够仍可能被强制访问控制拦住（非特权 userns 被 AppArmor 拒绝就是实例），而挂载被标成只读时 root 也写不进去，所以看到 `EPERM` 时，要先把「缺 capability」「被 MAC 拦」「映射里没有这个 ID」三种可能分开。
7. **编号与归属是两套不同的记录。** PID 命名空间改的只是编号：进程在宿主上仍然是一个普通 PID，也仍然计在它所属的 cgroup 里。判据是 `/proc/<pid>/status` 的 `NSpid` 字段，它按层列出这个进程在每一级 PID 命名空间中的编号；而归属要读 cgroup 的 `pids.current`，它统计的是该 cgroup 里的 task 数。`nsenter` 进去看到的进程表与宿主看到的是同一批 task 的两个视角，不是两份。

## 常见误解

| 常见说法 | 事实 |
| --- | --- |
| 「容器就是一台小机器」 | 容器没有第二份内核；四类机制里只有 cgroup 负责计量，而且它的计数都记在宿主侧，容器内的多处接口是只读的或只是独立视图 |
| 「有命名空间就等于安全隔离」 | 命名空间只提供命名与视图，因此权限边界还要靠 capability 收敛、`seccomp` 与强制访问控制 |
| 「namespace 也能限制 CPU 和内存」 | 资源上限属于 cgroup，而命名空间不参与计量，所以两者互不替代 |
| 「容器里的 `free` 就是容器的额度」 | 它读到的是宿主的 `/proc/meminfo`，而容器的额度写在 cgroup 的 `memory.max` 与 `memory.current` 里 |
| 「改了容器里的 `net.ipv4.*` 就改了宿主」 | `net.ipv4.*` 随网络命名空间独立，所以改它不会改到宿主；只有 `net.core.*` 才是全局的 |
| 「进别人的命名空间一定要 root」 | 创建 user 命名空间自 3.8 起不需要特权，而要加入别人已经建好的命名空间，才需要在那个命名空间里持有 `CAP_SYS_ADMIN` |
| 「容器里的一号进程就是宿主的一号进程」 | 由于 PID 命名空间是树状嵌套的，所以两者是两个不同的 task，编号也不相同 |
| 「容器进程一退，命名空间立刻消失」 | 只要还有文件描述符或绑定挂载引用着它，命名空间就继续存活 |
| 「在容器里挂载不会影响宿主」 | 这取决于挂载的传播类型，因为 `shared` 类型的挂载点会把挂载事件传播出去 |
| 「rootless 就等于安全」 | 它靠的是 user 命名空间里作用域受限的 capability，所以发行版反而要为它加上额外的限制开关 |

## 要点自测

**问：命名空间与 cgroup 各管什么？**

答：命名空间管「看得见什么、编号是什么」，cgroup 管「能用多少」。两者互不替代：一个进程可以待在自己的 PID 与挂载命名空间里，却仍然计在某个 cgroup 组内；因此把上限配到命名空间上是配错了地方。

**问：一个东西要成为「容器」，最少需要哪几件？**

答：需要命名空间提供可见范围，cgroup 提供可用量，根文件系统与联合挂载提供文件来源，capability、`seccomp` 与强制访问控制提供权限约束。内核里没有「容器」这个对象，它是这四件东西的组合。

**问：为什么创建 user 命名空间不需要特权，这又为什么是风险？**

答：3.8 起内核允许无特权进程创建它，目的是让普通用户也能用上隔离能力（rootless 的基础）。代价是进程在其中立刻拥有完整的 capability，可以挂载 overlayfs（5.11 起）、建网络命名空间、挂一部分 `proc` 与 `sys`，于是成为提权面的来源；发行版因此加了 AppArmor 限制或 `kernel.unprivileged_userns_clone` 这类开关，判断时要先看这个开关的实际值。

**问：容器里 `top` 显示 CPU 只用了一成，能说明没用满配额吗？**

答：不能。配额是 cgroup 的硬上限，计数与节流都记在宿主侧：要读 `/sys/fs/cgroup/<路径>/cpu.stat` 的 `nr_throttled` 与 `throttled_usec` 的增量，并把 `cpu.max` 的分子分母一起看。容器内的使用率是按宿主 CPU 总数折算出来的，它的口径与 `cpu.max` 的配额口径不同。

**问：宿主能杀掉容器里的一号进程，反过来为什么不行？**

答：内核对同一个 PID 命名空间内的 init 不执行未安装处理函数的信号的默认动作，而来自祖先命名空间的 `SIGKILL`/`SIGSTOP` 是例外，会被强制投递。隔离的可见性是单向的：祖先看得见并影响后代，后代无法反向操作。

**问：什么情况下命名空间不会随进程退出而回收？**

答：还有进程在它里面，或者有进程持有它对应的 `/proc/<pid>/ns/*` 文件描述符，或者有人把它绑定挂载到了别处。这三种引用都消失之后才释放——诊断时用过的 `nsenter`、运行时持有的句柄都会延长它的寿命。

**第一反应不要做什么**：不要用宿主的视图推断容器内的状态（宿主能解析、宿主内存充足、宿主端口在监听，都推不出容器内的结论）；不要把「看不见」当成「被隔开」；不要以为 rootless 就等于收敛了权限，也不要以为 `EPERM` 一定是 capability 不够——映射区间与强制访问控制都会给出同一个错误码。

## 参考文档

- `man 7 namespaces`：八种命名空间的类型表、`/proc/<pid>/ns/` 条目、三套接口与「除 user、time 外创建需要 `CAP_SYS_ADMIN`」的规则。
- `man 2 clone`、`man 2 unshare`、`man 2 setns`、`man 2 ioctl_ns`：各 `CLONE_NEW*` 标志的引入版本、加入命名空间所需的 `CAP_SYS_ADMIN`、`EPERM` 的条件与 `NS_GET_*` 查询操作。
- `man 7 user_namespaces`：`uid_map`/`gid_map` 的映射规则与写入限制、`CAP_SYS_ADMIN` 在新命名空间内的作用域、嵌套层数上限、`overflowuid`/`overflowgid`。
- `man 7 pid_namespaces`、`man 7 mount_namespaces`、`man 7 network_namespaces`、`man 7 cgroup_namespaces`、`man 7 ipc_namespaces`、`man 7 uts_namespaces`、`man 7 time_namespaces`：每一类的隔离对象、嵌套与传播语义、以及 time 命名空间要求 `CAP_SYS_TIME` 这一例外。
- `man 1 unshare`、`man 1 nsenter`、`man 8 lsns`、`man 1 newuidmap`、`man 5 subuid`：命名空间的进入与枚举入口，以及 ID 映射区间的分配来源。
- `man 5 proc`（`/proc/<pid>/ns/`、`/proc/<pid>/uid_map`、`/proc/<pid>/mountinfo`、`/proc/sys/user/`）、内核文档 `Documentation/admin-guide/cgroup-v2.rst`：与命名空间配套的接口位置与 cgroup 侧的计量归属。
- 本节引用的 man 页与内核文档按**与目标机器同一主版本（当前基线 6.x）**取；默认值与版本门控（嵌套层数、映射行数、发行版对非特权 user 命名空间的限制）一律以现场的 `man`、`sysctl` 与实际接口文件为准。
