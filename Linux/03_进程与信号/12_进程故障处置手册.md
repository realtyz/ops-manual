# 进程故障处置手册

> [!cite] 参考资料
> 本篇是各篇结论的**收口**，不引入新机制：`man 7 signal`、`man 5 proc`、`man 5 systemd.kill`、`man 5 systemd.exec`、`man 1 coredumpctl`、`man 7 cgroups`，以及子笔记 04–11 的对应小节。
>
> 本篇结论来自上述资料，**处置步骤尚未在实验机上逐条演练**；演练后请把实测现象、耗时与踩到的坑回填到对应小节。

> **这篇讲什么**：进程出问题时，按什么顺序看、按什么顺序做，以及每一步的证据在哪里。
>
> **必须先读什么**：至少读完 [[Linux/03_进程与信号/00_导读与知识地图|00 导读]] 的第 1、6 节；具体机制见子笔记 04–11。
>
> **读完能做什么**：给一个现象，10 分钟内判定它属于哪一类，并说出下一步该取什么证据。
>
> 所属：[[Linux/03_进程与信号/00_导读与知识地图|03 进程与信号]] 的收口篇 · 主要练 **S3 事后取证**、**S4 分层定位**、**S6 耗尽处置**、**S8 沉淀**

## 0. 统一原则

> [!abstract] 处置前三句话
> - **先分清「它还在不在」**：进程还在（`D`/`Z`/`T`）时现场是活的，能现取 `wchan`、`stack`、`fd`；进程已经没了时，只剩日志与 core。**这两类的处置顺序完全相反。**
> - **没取到证据之前，不做不可逆操作**：重启、`kill -9`、改上限重启服务都属于会毁掉现场的动作。
> - **先止损还是先取证，是个明确决策**：业务中断时优先止损；只要能取到证据，就先取——**重启会毁掉大部分现场**，而 core 与持久化日志是少数重启后仍在的证据。

三条通用取证动作，任何一类都适用：

```bash
date; hostname; uptime                # 验证：时间基线（时间不对，后面所有证据都对不上）
ps -p <pid> -o pid,ppid,pgid,sid,tty,stat,wchan:24,etime,cmd   # 验证：目标进程的归属与状态
systemctl --failed --no-pager         # 验证：有没有失败的服务单元
```

## 1. 卡死、`kill -9` 也杀不掉（`D` 状态）

> [!tip] 第一反应不要是「再杀一次 / 重启整机」
> 它正卡在内核态等待，信号被挂起；重启会把现场一起清掉，而且不保证不复发。

```bash
ps -o pid,ppid,stat,wchan:24,etime,cmd -p <pid>   # 验证：状态与等待点
cat /proc/<pid>/stack                             # 验证：内核态调用栈（需要 root）
iostat -x 1 5                                     # 验证：是否有一块盘的 await/%util 异常
dmesg -T | grep -i -E 'nfs|blocked for more than|hung task'   # 验证：内核是否已报阻塞超时
cat /proc/mounts | grep -i -E 'nfs|ceph|efs'      # 验证：是否存在网络存储挂载（长时间 D 的常见来源）
```

判断分支：

- 等待点在**块设备或文件系统** → 查盘的介质错误、RAID/多路径状态（阶段 5 的范围）；
- 等待点在**网络存储** → 服务端可达性优先，挂载恢复后进程往往自己走出来；
- 等待点在**内核锁/驱动** → 评估升级内核或驱动，先把业务切走；
- 内核已报 `hung task` → **排查重点在存储/驱动路径**，同时评估业务影响面、准备切流。

> **最低成本复现**：子笔记 05 的配套实验（`dmsetup suspend` 挂起一个环设备）。不允许动 device-mapper 时，用 `kill -STOP` 造 `T` 状态做对照——`T` 能被 `SIGCONT` 唤醒，`D` 谁也唤不醒。

## 2. 僵尸进程堆积

> [!tip] 第一反应不要是「批量 `kill -9` 僵尸」
> 僵尸已经终止，杀不掉也不占内存；要做的是处理它的**父进程**。

```bash
ps -eo pid,ppid,stat,comm | awk '$3 ~ /Z/ {print}' | tee /tmp/zombie-$(date +%F-%H%M).txt
                                                  # 验证：僵尸清单留档
ps -eo pid,ppid,stat,comm | awk '$3 ~ /Z/ {print $2}' | sort | uniq -c | sort -rn
                                                  # 验证：按父进程聚合，找出制造者
ps -o pid,stat,wchan:20,cmd -p <ppid>             # 验证：父进程是否卡在 D（它卡住，僵尸就会堆积）
```

分支：

- 父进程卡在 `D` → 先按第 1 节处理父进程，僵尸会随它恢复或退出而消失；
- 父进程是「不会 `wait()` 的程序」→ 列入缺陷单改程序；紧急时重启该父进程（它退出后僵尸被 PID 1 收养并回收）；
- 容器里 → 给容器加 init（`--init`/tini），或让应用主进程负责回收。

> **最低成本复现**：非交互 shell 里跑 `bash -c 'sleep 0.1 & sleep 60'`，在第二个 `sleep` 期间用上面的命令就能看到一条 `Z`；等父进程退出、子进程被 PID 1 回收后它就消失。

## 3. 服务「悄悄消失」（三种死法）

> [!tip] 第一反应不要是「重启服务再看」
> 重启会把上一次的证据一起清掉；先取退出码、信号、内核日志与 core。

```bash
systemctl show -p ExecMainCode -p ExecMainStatus -p Result -p ExecMainExitTimestamp <svc>
                                            # 验证：exited/killed + 退出码或信号号
journalctl -u <svc> --since '30 min ago' | tail -50       # 验证：应用侧的收尾日志
journalctl -k -b | grep -i -E 'oom|killed process'        # 验证：内核是否做过 OOM
cat /sys/fs/cgroup/system.slice/<svc>/memory.events        # 验证：cgroup 级 oom_kill 计数
coredumpctl list | tail -5                                 # 验证：有没有 core（崩溃而非退出）
journalctl -b -1 -u <svc> | tail -50                       # 验证：上一次启动的日志（若已重启过）
```

判据：`ExecMainCode=killed` + `ExecMainStatus=9`（137）**只表示被 `SIGKILL` 杀死**，可能是 OOM、可能是人工、也可能是容器运行时超时后强杀——必须找到对应证据才能定性。

> **最低成本复现**：子笔记 06 的配套实验覆盖「被信号杀」，子笔记 11 的配套实验覆盖「被 cgroup OOM 杀」，两种死法的证据位置正好对照着看。

## 4. 撞上进程数上限 / `fork` 失败

> [!tip] 第一反应不要是「把 `ulimit -u` 调大」
> 先分清是 `pid_max`、`threads-max`、`RLIMIT_NPROC` 还是 cgroup 的 `pids.max`——四者的判据与处理完全不同。

```bash
cat /proc/loadavg                    # 验证：最后一列（最近分配的 PID）连看两次算消耗速率
cat /sys/fs/cgroup/.../pids.current /sys/fs/cgroup/.../pids.max   # 验证：组内用量与上限
sysctl kernel.pid_max kernel.threads-max                          # 验证：整机上限
cat /proc/<pid>/limits | grep -i processes                        # 验证：进程侧的 Max processes
dmesg -T | grep -i 'pids controller' | tail -5                    # 验证：内核是否拒绝过 fork
ps -eo user,ppid,comm --no-headers | sort | uniq -c | sort -rn | head -20
                                                                  # 验证：谁在批量创建
```

处置顺序：**定位创建源 → 判断是 bug 还是容量 → 优先在源头止损（限流/停异常实例）→ 最后才考虑扩上限**。扩上限要按子笔记 08 改在正确的那一层。

## 5. `too many open files`

> [!tip] 第一反应不要是「把 `ulimit -n` 调到一百万」
> 先确认是单进程泄漏、整机 `file-max` 到顶，还是设计上就是长连接多。

```bash
cat /proc/sys/fs/file-nr             # 验证：整机已分配/空闲/上限
ls /proc/<pid>/fd | wc -l            # 验证：进程侧用量
ls -l /proc/<pid>/fd | awk '{print $NF}' | sort | uniq -c | sort -rn | head
                                     # 验证：fd 构成（套接字还是普通文件）
cat /proc/<pid>/limits | grep -i 'open files'   # 验证：进程实际生效的软/硬限制
```

处置：先留档 → 再止血（按子笔记 08 在正确一层扩容，或滚动重启回收句柄）→ 定位泄漏 → 加水位监控。

> **最低成本复现**：实验机上 `bash -c 'ulimit -n 16; exec <一个要开很多文件或连接的命令>'`，再用 `ls -l /proc/<pid>/fd` 看清是套接字还是文件占满的。

## 6. 崩溃了，但没有 core

> [!tip] 第一反应不要是「再崩一次就有了」
> 先按四道闸门排查；CrashLoop 期间反复崩溃只会把磁盘吃掉。

```bash
ulimit -c                                        # 验证：当前会话的 core 上限（是否被设为 0）
cat /proc/sys/kernel/core_pattern                # 验证：落点规则（文件名模板还是管道程序）
cat /proc/sys/fs/suid_dumpable                   # 验证：setuid 程序是否允许 dump
systemctl show -p LimitCORE <svc>                # 验证：服务侧的上限
cat /proc/$(systemctl show -p MainPID --value <svc>)/limits | grep -i core   # 验证：进程实际值
coredumpctl list | tail -5                       # 验证：有没有落在 systemd 的存储里
ls -l /var/crash/ 2>/dev/null; du -sh /var/lib/systemd/coredump/ 2>/dev/null
                                                 # 验证：另一种落点与当前占用
```

分支：`LimitCORE=0` → 按子笔记 10 的生产动作 B 打开或限量；`core_pattern` 是管道 → 去 `coredumpctl` 找；setuid 程序 → 换用非特权路径复现；落点不可写（容器常见）→ 改 `core_pattern` 或在工作目录可写的位置运行。

## 7. 服务 CPU 打满，但整机看着不高

> [!tip] 第一反应不要是「整机 CPU 不高所以不是 CPU 问题」
> 单线程热点、绑核错误、GC 停世界都会造成这个现象。

```bash
top -H -p <pid>                                  # 验证：进程内哪个线程在跑
ps -L -p <pid> -o pid,tid,pcpu,stat,comm --sort=-pcpu | head
mpstat -P ALL 1 5                                # 验证：是不是某一颗核 100%、其余空闲
pidstat -u -w -t -p <pid> 1 5                    # 验证：线程级 CPU 与上下文切换
vmstat 1 5                                       # 验证：us/sy/wa/si 的构成
```

**判据**：`mpstat -P ALL` 里有核 `%idle` 为 0 = 绑核/单线程热点；`sy` 高 = 系统调用与锁竞争（也可能是 fork 风暴）；`si` 高 = 软中断（阶段 6 的范围）。方法论的深水区在阶段 10（性能分析与排障）。

## 8. 容器 `stop` 等满超时、退出码 137

> [!tip] 第一反应不要是「把超时时间改长」
> 根因通常是容器里的 PID 1 没有处理 `SIGTERM`。

```bash
docker exec <ctr> ps -p 1 -o pid,ppid,stat,comm,args   # 验证：PID 1 是谁（bash/sh 就要警惕）
docker exec <ctr> ps -eo pid,ppid,stat,comm | grep Z   # 验证：有没有僵尸堆积
journalctl -u docker --since '10 min ago' | tail -50   # 验证：运行时的停止与强杀记录
```

修法：应用自己处理 `SIGTERM` 并回收子进程（推荐）；用 `docker run --init`/tini/dumb-init 充当 PID 1；`CMD` 用 exec 形式让应用真正成为 PID 1。

## 9. 处置记录模板（S8）

一次处置结束后，按这六项写一段 Runbook 片段，放进团队知识库：

```text
【现象】谁在什么时候报警，业务表现是什么（例如：服务每 5 分钟重启一次，失败率 3%）
【证据】退出码/信号、内核或应用日志的关键行、@时间点、core 或 cgroup 计数的位置
【根因】一句话说清（例如：cgroup MemoryMax 设得低于正常水位，触发 cgroup OOM）
【处置】做了什么（含止血与定位的先后），耗时多久
【回滚】如果处置本身需要撤销，命令是什么
【巡检】加什么监控/检查项避免复发（例如：MemoryMax 水位 > 80% 告警、句柄水位 > 70% 告警）
```

写不出来通常说明证据没取全——这时应该回头补基线，而不是编一个结论。

## 10. 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 出事第一动作是重启 | 重启会清掉大部分现场；先按第 0 节取三样通用证据，再决定 |
| 拿「重启后好了」当结论 | 那只是问题被暂停；没有根因的记录下次还会踩同一个坑 |
| 用 `kill -9` 处理一切「卡住」 | `D` 状态与僵尸都杀不掉；能杀掉的那些往往也丢掉了收尾机会 |
| 只在一台机器上处理 | 集群里同样的镜像/配置同样会出问题；判断是不是共性问题 |
| 处置完不写记录 | 下一次同现象只能从头再来，团队没有积累（S8 的交付物就落在这里） |
| 不区分「症状」与「根因」 | 「进程卡在 D」是症状，「那块盘有介质错误」才是根因；处置要对着根因 |
| 复盘时用「可能」「大概」 | 证据不足就写清证据不足，不要用猜测填空 |

## 11. 决策练习

> [!question]- 场景：凌晨 2 点，业务告警「接口失败率 30%」，你登录后看到某服务的进程在，但全部处在 `D` 状态；同一台机器上其他服务正常
> 你的第一动作是什么？
> A. `kill -9` 这些进程，让 systemd 自动重启服务
> B. 先看它们的 `wchan`/`stack` 与所在挂载点、块设备状态，确认它们在等什么；同时评估是单机问题还是共享存储问题，并准备摘流
> C. 重启机器
>
> **答案：B。**
> A 不会生效（`D` 状态收不到 `SIGKILL`），而且会掩盖现场；即便侥幸生效，它等待的资源仍然没恢复，重启后照样卡住。
> C 是最重的选项：多台机器共用存储时，重启一台不解决共性问题；而现场（栈、挂载状态、内核报错）全部丢失。
> B 是正解：**症状（D 状态）→ 证据（wchan/stack/dmesg/mount）→ 影响面（单机还是共享）→ 决策（摘流、恢复存储、换盘）**。这正是 S4 与 S7 合起来要练的判断力。

## 12. 要点自测

> [!question]- 拿到「进程有问题」这句话，你的前三个动作是什么？
> - ① 确认它在不在（`ps -p <pid> -o pid,stat,...`）：在 → 现场是活的；不在 → 只能看日志与 core。
> - ② 看它的归属（PPID/PGID/SID/tty）与状态（`stat`、`wchan`），确定它属于哪一类问题。
> - ③ 取一组同时刻证据（时间、进程、整机资源、日志）留档，再决定止损还是继续定位。
> - **第一反应不要是什么**：不要在没有任何留档的情况下重启或 `kill -9`。

> [!question]- 哪些证据重启即失？哪些能活过重启？
> - 重启即失：内存里的状态、`wchan`/`stack`、内核环缓冲（`dmesg`）里的早期记录、未持久化的 journal、`/proc` 下的一切。
> - 能活过重启：持久化的 journal（`/var/log/journal`）、磁盘上的 core、`/var/crash/`、systemd 的单元状态记录（部分）、外部的监控与告警数据。
> - **第一反应不要是什么**：不要默认「日志肯定还在」——先确认 `journalctl --list-boots` 有没有多于一条。

> [!question]- 一次完整的处置记录必须包含哪几项？
> - 现象（含时间与业务影响）、证据（含位置）、根因、处置（含先后与耗时）、回滚、巡检项。
> - 缺少「回滚」与「巡检项」的记录无法沉淀成组织资产——它们正是 S8 的交付物。
> - **第一反应不要是什么**：不要把「重启后恢复」写成根因，那只是处置动作。
