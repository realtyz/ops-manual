# 一个进程的一生

一个进程从被创建到被回收，只经过四件事：被造出来、在 CPU 上跑或等某个事件、被通知、结束并被收尾。以下按这个顺序一次讲完，从 `fork` 复制出的那一刻讲到退出状态被领走，中间不打断；四件事讲完之后，再把贯穿多个阶段的占用口径、限制层级与归属关系收拢到一起。

之所以要连着讲一遍，是因为**单看每一个阶段都懂、串起来却讲不出「为什么它现在这样」，这是新人最常见的状态**。因此段与段之间的接口才是判断力的所在，它包括 `fork` 之后继承了谁的什么、信号在什么时刻才能生效、退出状态交给谁。

## 一、诞生：从一个 unit 到运行队列

### 1.1 创建动作做了什么

创建一个进程是两步（细节见《进程的诞生：fork 与 exec》）：

`fork`/`clone` 复制出一个新 task——复制内核控制结构、页表，并**共享**物理页（写时复制），继承资源限制、信号处置与掩码、fd 表、工作目录、`umask`、进程组与会话；`execve` 再把地址空间换成目标程序，**PID 不变**。

`fork` 的返回值是区分「我是谁」的唯一依据：子进程里返回 0，父进程里返回子进程的 PID。shell 的 `&`、命令替换 `$(...)`、管道两侧全部建立在这条规则上。

**这里埋下了后面所有问题的种子**：继承了哪些 fd 决定「新进程意外占着什么」；继承了哪份资源限制决定「它能开多少文件」；继承了哪个进程组决定「一条 `kill` 会不会连坐到它」。

### 1.2 `execve` 是「重启」，不是「换对象」

| 被保留 | 被替换 |
| --- | --- |
| `execve` 之后 PID/TGID、父进程、进程组与会话、控制终端都被保留下来 | `execve` 之后地址空间、代码、堆、栈与所有匿名映射都被替换掉 |
| `execve` 之后资源限制、`umask`、工作目录与信号掩码都被保留下来 | 信号处置被重置为默认，只有被显式忽略的仍忽略 |
| 未标 `FD_CLOEXEC` 的文件描述符及其偏移量被保留下来 | 环境变量由调用方传入，因此整份被替换 |

两条因此产生的现象，是值班里反复出现的：

- **`exec` 之后仍屏蔽着某个信号**。父进程屏蔽 `SIGTERM` 再 `exec`，新程序在**无人处理**的情况下继续屏蔽它——这就是「这服务对 `SIGTERM` 没反应」的机制之一；
- **`exec` 之后仍占着旧句柄**。默认继承的 fd 让旧连接、旧日志文件一直被持有；`df` 与 `du` 对不上、端口仍被占用，都可能是它。

### 1.3 出生之后的两层归属

新 task 立刻落在两套归属体系里，它们回答的是不同问题，不要混：

| 体系 | 字段 | 回答的问题 | 决定什么 |
| --- | --- | --- | --- |
| 父子 | `PPID` | 它回答谁负责回收这个进程的退出状态 | 因此僵尸由谁清理、孤儿被谁收养都由这条关系决定 |
| 进程组与会话 | `PGID`、`SID`、`tty` | 它回答一条 `kill` 能打到谁、终端断开时谁被带走 | 因此信号的投递范围由这条关系决定 |

**进程组是「一次性操作」的最小单位**：`kill -<pgid>` 打的是整组，`Ctrl+C` 发给前台进程组，终端断开时内核给前台进程组发 `SIGHUP`。**会话是「一次登录」的边界**，最多关联一个控制终端。

由此解释了两个高频现象：`kill <pid>` 之后子进程还在（只杀了单个进程，连带清理要靠进程组或 cgroup）；`tty` 列显示 `?` 不是异常（服务、内核线程、`setsid` 之后的进程都没有控制终端）。

`ps` 的 `STAT` 列还用两个后缀表达归属：`s` 表示会话首进程，`+` 表示位于前台进程组。所以登录 shell 常见 `Ss` 或 `S+`。

## 二、运行与等待：它到底在等谁

### 2.1 状态是「归类」，不是「原因」

`ps` 的 `STAT` 列与 `/proc/<pid>/status` 的 `State:` 来自内核同一张状态表：

| 状态 | 内核含义 | 常见来源 | 对它发 `SIGKILL` 的结果 |
| --- | --- | --- | --- |
| `R` | running / runnable | 它在 CPU 上，或在运行队列里排队 | `SIGKILL` 生效 |
| `S` | interruptible sleep | 它在等网络、等锁或执行 `sleep`；绝大多数进程都处于这个常态 | `SIGKILL` 生效 |
| `D` | uninterruptible sleep | 它在等块设备或网络存储 IO、内核态锁或驱动 | 它**等不到投递时刻**，因此要回到用户态才处理 |
| `T` | stopped（作业停止） | `SIGSTOP` 或 `Ctrl+Z`（`SIGTSTP`）让它停下 | 普通信号会挂着，而 `SIGKILL` 可直接终止它 |
| `t` | tracing stop | 它被 `ptrace`（调试器、跟踪工具）挂住 | 结果与 `T` 相同 |
| `Z` | zombie | 它已退出，正等父进程回收 | `SIGKILL` **无效**，因为它已经终止了 |
| `I` | idle | 它是内核线程（自 Linux 4.14 起显示） | 不需要也不应该管它 |
| `X` | dead | 它是转瞬即逝的中间态 | 基本看不到它 |

**状态字母只说明「在哪一类等待」，永远不说明「在等谁」。** 判断原因要读等待点与内核栈。`D` 既可能是本地磁盘，也可能是网络存储、内核锁或驱动；同一个字母背后的处置方向完全不同。

`/proc/<pid>/status` 的 `State:` 字段给出原始值，`/proc/<pid>/wchan` 给出它当前睡在哪个内核函数上（进程正在跑时是 `0`），`/proc/<pid>/stack` 给出内核态调用栈（需要权限，且要求内核开启栈回溯）。这三样合起来才能给出一个可复述的结论。

### 2.2 造一个长期 `D` 状态的代价

`D` 状态的进程并不是「没事可做」，它通常**还占着内存、句柄与连接**，并且如果它在处理请求，请求会一直挂着不超时。所以处置顺序里有一件事排在「杀进程」之前：**摘流量**。

这也解释了 `T` 与 `D` 的关键差别：`T` 是**被人为停下的**，一份 `SIGCONT` 就能唤醒；`D` 是**在等硬件或内核**，没有任何信号能把它踢出来。用一个 `kill -STOP` 造出的 `T` 状态做对照，能很快看清「信号能做什么、不能做什么」。

### 2.3 排队的一半：为什么「没在跑」也可能是 CPU 问题

进程不在跑有两种原因：**在等事件**（上一节）与**在排队等 CPU**（这一节）。后者由调度决定，能调的调度手段有五类，它们管的事完全不同：

| 手段 | 作用对象 | 取值范围 | 边界 |
| --- | --- | --- | --- |
| `nice` | 它作用于同一调度组内的相对 CPU 权重 | `-20`（最高）~ `19`（最低），默认 `0` | 它**只在有竞争时生效**；整机空闲时 `nice 19` 也能跑满一个核 |
| `ionice` | 它作用于块设备 IO 的调度类与优先级 | 类 `1/2/3` + 级别 `0~7` | 它只对使用该调度器的设备有意义 |
| `chrt` | 它作用于调度策略与实时优先级 | 策略 `OTHER/FIFO/RR/BATCH/IDLE/DEADLINE`，RT 优先级 `1~99` | 由于 RT 会抢占所有非 RT 任务，内核用 RT 节流（`sched_rt_runtime_us`）作为回退路径 |
| `taskset` | 它作用于单进程的 CPU 亲和掩码 | CPU 列表或掩码 | 它与 cgroup 的 `cpuset` 取**交集**，因此容器里常出现「绑了但没生效」 |
| `numactl` | 它作用于 NUMA 节点与内存策略 | — | 它的内存侧细节属于内存章节的范围 |

四条反直觉但必须记住的结论：

**nice 只在竞争时有效。** 整机 CPU 空闲时调整 nice 完全看不出差别；跨组的两件事要分开说——**分配**用 cgroup 的 `cpu.weight`，**设硬顶**用 `cpu.max`。

**`taskset` 与 `cpuset` 是交集关系。** 把进程绑到 cgroup 不允许的 CPU 上不会有任何效果——这种「命令成功但没生效」在容器里非常常见。

**实时调度是双刃剑。** 一个优先级为 `99`（RT 优先级范围是 `1~99`）的线程跑满 CPU 时，`%idle` 会落到 0，而 RT 任务总是抢占非 RT 任务，因此包括 `sshd` 在内的普通进程拿不到 CPU 时间，现场看到的就是机器「看起来活着但登不上去」。内核用 RT 节流（`sched_rt_runtime_us`）作为回退路径，**不要在没读文档的情况下动节流参数**。

**nice 会被继承。** `fork` 与 `execve` 都不重置它。一次 `renice` 影响的是这条进程链后续拉起的全部任务——批量降优先级很方便，改错了也要沿着整条链改回来。

### 2.4 单核打满是最常见的假象

8 核机器上一个线程跑满一颗核，被多核摊薄的是**整机**视角——整机 CPU 只有 12% 左右；**进程级视图不会把热点平均掉**：`ps` 的 `%CPU` 是「CPU 时间 ÷ 存活时间」，**不按核数归一**，一个线程跑满时它显示**接近 100%**（`pidstat` 只有加 `-I`、`top` 只有切到 Solaris 模式才除以 CPU 总数）。它仍是**生命周期平均值**，一个跑了 10 分钟的进程里忙了 1 分钟，显示出来就是 10%。

判据是**每核视角**：看每个 CPU 的占用，找 `%idle` 为 0 的那一列；再下钻到**线程级**，找出 `%CPU` 接近 100 的 TID，带着 TID 去应用侧对号（线程名、日志、运行时的线程转储）。「整机 CPU 不高所以不是 CPU 问题」这句话，在单线程热点、绑核错误、GC 停世界三种情形下都是错的。

### 2.5 等 CPU 与等事件怎么区分

上下文切换计数是区分这两种等待的入口。`voluntary_ctxt_switches` 是主动让出（在等事件），`nonvoluntary_ctxt_switches` 是被抢占（在等 CPU）。

**判据必须建立在同一个进程上比较两者的增长速度**：非自愿那侧涨得快，说明它在排队等 CPU，去查容量与争抢；自愿那侧涨得快，说明它在等别人（IO、锁、网络），去查那件事本身。**两者都高只说明它既在抢又没抢到**，不能单独定性——这也是为什么单看一个数字做结论一定出错。

## 三、被通知：信号怎么改变它的走向

### 3.1 投递的完整路径

信号从产生到被处理要走三步：**选目标**（进程级信号挂在线程组共享队列上，线程级信号挂在具体 task 上）、**看是否放行**（`SIGKILL`/`SIGSTOP` 不可阻塞，其余信号在目标阻塞时只留在待处理位图上）、**等一个可投递的时刻**（只有从内核态返回用户态时才会被处理）。

第三步是全部困惑的来源：**`kill` 返回成功只说明信号送达**，不说明进程处理了它，也不说明进程还在。`D` 状态的进程收不到投递时刻，信号只被记录。

进程实际收到了什么，看五张位图：`SigPnd`/`ShdPnd`（待处理，私有与共享）、`SigBlk`（被阻塞）、`SigIgn`（被忽略）、`SigCgt`（装了处理函数）。**排查「为什么不响应」的顺序是先看 `SigIgn`，再看 `SigBlk`，最后看 `SigCgt`**。

标准信号**不排队**：同一个信号在待处理状态下重复到达会被丢弃。实时信号才有排队语义。所以「发三次只处理了一次」不是内核丢包。

### 3.2 三种走向：捕获、终止、停止

收到信号之后，进程只有三种结局：自己处理（handler）、被终止、被停止。默认动作由内核规定：一部分信号的默认动作**包含产生 core**（例如 `SIGSEGV`、`SIGABRT`、`SIGQUIT`），其余只终止、停止、继续或忽略。

「被终止」这一条分岔出后面要讲的内容——**谁杀的、有没有留下现场**，取决于信号是谁发的、以及 core 那条链路是否打开。

## 四、结束：三种死法，三套证据

### 4.1 三种死法各留什么证据

| 死法 | 表现 | 证据在哪里 |
| --- | --- | --- |
| 正常退出 | 它的退出码是 `0`，或应用自定义的非 0 | 证据在应用日志、`systemctl status` 的状态行与 shell 里的上一条命令退出码里 |
| 被信号杀死 | shell 里看到的是 `128+N`；服务管理器把它显示为被信号终止 | 证据在服务管理器的退出状态字段与信号号、以及应用日志里 |
| 被 OOM Killer 选中 | 它同样死于 `SIGKILL`，退出码同样是 137 | 证据在宿主内核日志里的 OOM 记录（整机 OOM 带 `global_oom`，组级 OOM 带 `constraint=CONSTRAINT_MEMCG` 与 `oom_memcg=`），或在 cgroup 的事件计数里 |

退出码表里只需要记住四个：`126`（找到但不能执行）、`127`（命令未找到）、`137`（`128+9`，被 `SIGKILL`）、`143`（`128+15`，被 `SIGTERM`）。服务管理器自己还有一批代码（例如 `203` 表示执行阶段失败），含义可以查它自带的查询子命令，**不要硬背**（老版本可能没有这个子命令）。

### 4.2 137 只回答「怎么死的」，不回答「谁干的」

`137` 是 `128 + 9`，它唯一的信息是「死于 `SIGKILL`」。能让进程收到 `SIGKILL` 的至少有四种来源：内核 OOM（整机或组级）、人工或脚本的 `kill -9`、运行时或服务管理器停止超时后的强杀、以及编排层或健康检查触发的重启。内核这一路还有几条容易被漏掉、又都有出处的路径：PID namespace 的 init 退出时内核对全组补发的 `SIGKILL`、一次性清空整组的 `cgroup.kill`、以及 `RLIMIT_CPU` 硬限到点后内核补发的 `SIGKILL`。

**定性**要按来源分类去对应的三处取证位置查，任一处命中即可——整机与组级 OOM 归内核日志与 cgroup 事件计数，人工或脚本的 `kill -9` 归人工证据，运行时/服务管理器/编排层的强杀归各自的停止记录：

1. **整机内核日志**里有没有 OOM 记录（会打印候选进程的打分与被选中者）；
2. **cgroup 的事件计数**里 `oom`/`oom_kill` 是否增长（组级 OOM 的确凿证据，注意计数是累积值，要用差值判断「这次」）；
3. **人工证据**：操作审计、变更单、编排层事件——用来排除「有人手工杀的」。

三处都没有时，正确的写法是「死于 `SIGKILL`，来源待查」，而不是「推断为 OOM」。**把 137 直接写成 OOM，是复盘里最常见的一处失真。**

### 4.3 收尾责任：僵尸与孤儿

子进程退出后，退出状态要交给父进程，内核会暂时保留它的控制结构与 PID，直到父进程调用 `wait()` 系列函数。于是：

- **僵尸不是「没死干净」，而是「没人收尸」**。它已经终止，只剩一个待回收的状态；对它发任何信号都无效，要处理的是它的**父进程**；
- **父进程先退出**，子进程被最近的 subreaper（默认是 PID 1）收养，回收责任随之转移。这就是「杀父进程有时能清掉僵尸堆积」的原因；
- **唯一的自动回收例外**是把 `SIGCHLD` 的处置设为 `SA_NOCLDWAIT`——内核会直接回收而不产生僵尸。把 `SIGCHLD` 显式设为 `SIG_IGN` 是**等价写法**，与 `SA_NOCLDWAIT` 的差别只在于是否仍产生 `SIGCHLD` 通知。注意默认动作「忽略」与显式 `SIG_IGN` 的效果不同。

僵尸本身几乎不占内存，占的是进程表项与 PID。堆积多了会耗尽 PID，也会让「进程数」类监控失真，所以少量僵尸是噪声，成百上千条就是故障。

### 4.4 容器把这两件事一起放大

容器里的 PID 1 同时受两件事约束：内核对它**不执行信号默认动作**，而且**它要负责回收被收养的孤儿**。如果那个 PID 1 是不做这两件事的程序（典型的 `bash`/`sh`），就会出现一组特征现象：

| 现象 | 机制 |
| --- | --- |
| 停止请求已经送达却被忽略，于是它最终等满超时后被强杀 | 若 PID 1 没有为 `SIGTERM` 安装处理函数，则内核对它不执行默认动作，`SIGTERM` 因此等于被忽略，停止请求只有等满超时后由宿主侧补发 `SIGKILL` 才生效 |
| 容器里堆积 `<defunct>` | 因为 PID 1 不回收被重新挂到它名下的子进程，所以这些进程一直以 `<defunct>` 的形式留着 |
| 在宿主上对 PID 1 发致命信号看不到任何反应 | 同 namespace 内未装 handler 的信号（含 `SIGKILL`/`SIGSTOP`）一律被丢弃，因此它们不生效；**来自祖先 namespace 的 `SIGKILL`/`SIGSTOP` 是例外——它们被强制投递并生效**，这正是宿主能停掉容器 PID 1 的原因 |

修法有三条，按推荐程度排列：应用自己处理 `SIGTERM` 并回收子进程；用一个真正的 init（`--init`、`tini`、`dumb-init`）充当 PID 1；启动命令用 exec 形式，让应用本身成为 PID 1，而不是被 shell 包一层。

## 五、跨阶段的核对对象：占用口径、限制层级、归属关系

四个阶段讲完，剩下三个会贯穿每一个阶段的核对对象：占用口径、限制层级与归属关系。它们不是新机制，而是同一批机制在不同阶段呈现出的侧面。

### 5.1 占用口径：资源算在谁头上

占用口径贯穿诞生、运行与等待、结束三个阶段：诞生阶段读 `VmSize` 与 `VmRSS`，看新进程继承来的与 `execve` 之后留下的是哪一类占用；运行与等待阶段读 `utime`/`stime` 与 cgroup 的 `memory.current`，看它实际消耗了多少；结束阶段读 cgroup 的 `memory.events` 差值，才能判断这次退出是否由组级 OOM 造成。

运维问「这个进程占了多少」时，必须先把口径固定下来：

| 口径 | 典型字段 | 回答什么 | 会不会重复计数 |
| --- | --- | --- | --- |
| 地址空间 | `VmSize`（`ps` 的 `VSZ`） | 它回答这个进程**要**了多少虚拟地址 | 由于它只是地址空间额度，因此它与物理占用无关 |
| 常驻 | `VmRSS`（`ps` 的 `RSS`） | 它回答这个进程碰到过多少物理页 | 它**会**重复计数，因为共享页被每个使用者各算一份 |
| 均摊 | `Pss` | 它回答共享页均摊之后这个进程占了多少 | 它不会重复计数；但它只覆盖**被映射的页**，因此全机相加只约等于被映射页之和，不能与 `free` 的 `used` 比大小（后者还含 slab、页表、内核栈） |
| 私有 | `Uss`（**工具口径**，内核没有这个字段） | 它就是 `ps -o uss`，也就是 `Private_Clean`+`Private_Dirty`，回答只有它在用的页有多少 | 它不会重复计数，代价是忽略共享带来的收益 |
| 组的额度 | cgroup 的 `memory.current`/`peak` | 它回答这一组在配额体系里用了多少 | 同一组内不重复计数，组间则按层级归属 |

**CPU 时间同样有两种口径**：`utime`/`stime`（进程累计的用户态与内核态 CPU 时间，`/proc/<pid>/stat` 的第 14、15 个字段，单位是时钟滴答）与工具算出的百分比。百分比有两个来源——**生命周期平均值**（`ps` 的 `%CPU` = 累计 CPU 时间 ÷ 运行时长）与**区间值**（`top` 第二次刷新起、按秒采样的工具）。三个数不一样**不是工具坏了**，是口径不同。

同一份数字还有一处纪律：**速率类指标必须两次采样**。CPU 占比、IO 速率、上下文切换速率都是从「两个时间点的累计值之差」算出来的，`/proc/<pid>/io` 这类文件给的是累计值，隔一段时间再读一次相减才有意义。**单点采样得到的不是趋势，是一次快照。**

### 5.2 限制层级：五个层次，验收只有一个依据

限制层级同样贯穿诞生、运行与等待、结束三个阶段：诞生阶段由 `fork`/`execve` 继承 `RLIMIT_*`，此时读 `/proc/<pid>/limits` 看到的是最终生效值；运行与等待阶段由 cgroup 控制器与整机内核参数约束，此时要读对应的 cgroup 接口文件；结束阶段读 `memory.events` 与 `pids.events` 的差值，判断这次退出是否撞上了某一层上限。

上限有五层**来源**，但执法层只有三类——进程 `RLIMIT`／cgroup／整机 sysctl；`limits.conf` 与 `LimitXXX=` 都只是**写 `RLIMIT` 的途径**，unit 未显式配置时取 `DefaultLimit*=`，即**后者覆盖前者**（细节见《资源的边界》）：

| 层 | 载体 | 作用范围 |
| --- | --- | --- |
| 进程自身 | `RLIMIT_*`（软/硬限制） | 它约束单个进程及其后代 |
| 登录会话 | PAM 的 `pam_limits` 读 `/etc/security/limits*` | 它约束由 PAM 建立的登录会话 |
| 服务 | unit 的 `LimitXXX=`/`TasksMax=` | 它约束该服务拉起的全部进程 |
| 组 | cgroup v2 控制器 | 它约束整组进程 |
| 整机 | 内核参数 | 它约束全系统 |

**唯一的验收依据是进程实际生效的值**（`/proc/<pid>/limits`，或对应的 cgroup 文件）。配置文件写了什么不算，命令返回成功也不算。

撞墙的表现与限制的性质相关：**计数型失败时报错、速率型失败时变慢、容量型失败时被杀**。看到报错去找计数型与容量型，看到变慢去找速率型。

### 5.3 归属关系：看得见什么、能用多少

归属关系贯穿诞生、运行与等待、结束三个阶段：诞生阶段 `fork` 定下 `PPID`、`PGID`、`SID` 与 `tty`；运行与等待阶段一条 `kill` 能打到谁、哪些 namespace 里的进程互相看得见，都由这些字段决定；结束阶段回收责任顺着 `PPID` 转移给收养者。

进程的最后一层归属由两组机制表达，它们维度不同、互不替代：

**namespace 改可见性**：`pid`（PID 编号空间，树状嵌套）、`net`（网络栈与设备）、`mnt`（挂载点）、`ipc`、`uts`（主机名）、`user`（UID/GID 映射）、`cgroup`、`time`。容器里「只看到自己的进程与网卡」不是命令坏了，而是因为你观察的已经是另一个 namespace；从宿主侧要看容器内的状态，需要进入目标 namespace。每一类隔离了什么、机制在本名与字段上的边界在哪里，见《命名空间与隔离》。

**cgroup 改可用量**：`pids`（任务数）、`memory`（内存）、`cpu`（CPU）、`io`（块设备）、`cpuset`（CPU 与 NUMA 节点）。它同时提供计数——「这一组用了多少」的答案在这里，而不是在宿主机的整机视角里。

**容器 = namespace + cgroup + 根文件系统 + 权限约束**（capabilities / seccomp / 强制访问控制）。少任何一层都不成其为容器。它与虚拟机最本质的差别只有一条：**共享同一个内核**——所以容器能用到哪些内核特性由宿主内核决定，内核级漏洞的影响面也天然更大。

一条操作纪律：**不要绕过服务管理器手工把 PID 写进 cgroup 的接口文件**。cgroup v2 有唯一管理者，手工迁移会让计数与实际不符，表现为服务停止后进程残留、状态查询看不到它、限制与统计失效。

### 5.4 关键字段的读法

排查这三个核对对象时，下面这些字段是真正会被读到的。每一条给五件事：**是什么 / 单位 / 怎么判断 / 和谁同看 / 看到它转向哪一步**。

| 字段 | 是什么、单位 | 判据 | 与谁同看 | 转向哪一步 |
| --- | --- | --- | --- | --- |
| `State`（`/proc/<pid>/status`） | 它是内核状态值，用字母表示 | 它只能判断这个进程在哪一类等待 | 与 `wchan`、`stack` 以及 `stat` 的后缀一起看 | 若它是 `D`/`t`/`T` 就转去读等待点；若它是 `Z` 就转去查父进程 |
| `wchan` | 它是当前等待的内核函数名（字符串）；进程在跑时它的值是 `0` | 它出现 `0` 就说明这个进程不在等 | 与 `stack` 以及当时的 IO/网络报错一起看 | 它指向存储、网络存储、内核锁或驱动 |
| `PPID` | 它是父进程的 PID，整数 | 它为 `1` 只说明「中间层已退出」 | 与 `pstree`、`systemctl status` 一起看 | 若进程已成僵尸就转去查父进程；若它是孤儿就转去查收养者 |
| `PGID`/`SID`/`tty` | 它们分别是进程组、会话与控制终端 | `tty` 为 `?` 是正常状态 | 与 `ps -o` 的归属列一起看 | 它们决定 `kill` 的目标与终端断开的影响面 |
| `Threads`（`status`） | 它是该线程组的 task 数，单位是个 | 要拿它与基线比；只涨不落就要查 | 与 `ps -eLf` 的行数、`pids.current` 一起看 | 数量异常时转去查线程创建源 |
| `SigIgn`/`SigBlk`/`SigCgt` | 它们是信号位图，用十六进制表示 | 位图里有位，就说明该信号被忽略/阻塞/已装 handler | 与 `SigPnd`、应用日志一起看 | 用来定位「为什么不响应信号」 |
| `%CPU`（`ps`） | 它是**生命周期平均**占用，单位 %（可超 100，按核累加） | 它不能当瞬时值用；新进程分母小会虚高 | 与 `pidstat 1`、`top` 第二次刷新一起看 | 需要此刻的热点就换采样类工具 |
| `%CPU`（`pidstat 1`） | 它是**区间**占用，单位 % | 要与自身基线比，注意多核可超 100 | 与线程级视图、每核占用一起看 | 单核打满时转线程级下钻 |
| `voluntary`/`nonvoluntary_ctxt_switches` | 它们是主动/被抢占让出 CPU 的**累计**次数，单位是次 | **必须两者比增长速度**，单看无效 | 与 `pidstat -w` 的区间速率一起看 | 非自愿多就转 CPU 排队；自愿多就转等事件 |
| `VmSize`（`VSZ`） | 它是虚拟地址空间，单位 kB | **看趋势与额度余量**：它只说明「要了」多少，涨落要与映射数一起看；只有撞上 `RLIMIT_AS` 一类的额度才是问题 | 与 `VmRSS`、`VmSwap` 一起看 | 判断占用时要换常驻/均摊口径 |
| `VmRSS`（`RSS`） | 它是常驻集，单位 kB | **跨进程对账不能直接累加**；要与自己的基线比，只涨不落才怀疑泄漏 | 与 `Pss`/`Uss`、`RssAnon`/`RssFile` 一起看 | 跨进程对账要用均摊口径 |
| `Pss`/`Uss` | 它们是均摊/私有占用，单位 kB（`Uss` 是工具口径的 `ps -o uss`，内核没有这个字段） | `Pss` 用于对账；`Uss` 只在**确认独占再清**时才有意义（被两个进程共用时它会把两边都算成私有） | 与 `RssAnon`/`RssFile`/`RssShmem` 一起看 | 用来判断「内存去哪了」与是否泄漏 |
| `Max open files`（`limits`） | 它是 fd 的软/硬限制，单位是个 | **先读软限再怀疑编译期上限**；软限才报 `EMFILE`，硬限只是改不上去的上限 | 与 `/proc/<pid>/fd` 计数、整机已用句柄数一起看 | 撞限制就转限制层级；用量单调上涨就转泄漏 |
| `Max processes`（`limits`） | 它是 `RLIMIT_NPROC`，按 real UID 计，单位是个 | 同一个 real UID 的进程**合计**计数，不是单进程；到顶时 `fork` 报 `EAGAIN` | 与 cgroup `pids.current`/`max`、整机上限一起看 | `fork` 失败时先分清是哪一层 |
| `oom_score`/`oom_score_adj` | 它是内核打分与人工调整值，后者的范围是 `-1000~1000` | **看候选进程之间的相对排名**，不看绝对值；调整值只改排名 | 与内核 OOM 日志、cgroup 事件计数一起看 | 用来解释「为什么是它被杀」，不作为隔离手段 |
| `cgroup.procs` / `pids.current` | `cgroup.procs` 是本组**每线程组一行**（不含子组，僵尸不出现），`pids.current` 是**本组及其全部后代**的 task 数（按 TID 计），单位是个 | 先分清**本组还是含后代**，再判断 `current` 是否贴着 `max` | 与 `pids.events` 差值一起看 | 容器起不了进程时先看这两项 |
| `memory.current`/`peak` | 它们是组的内存用量与历史峰值，单位是字节 | 定上限要高于峰值并留余量 | 与 `memory.max`、`memory.stat` 构成一起看 | 长期贴上限就转配额复盘 |
| `memory.events` | 它是组事件计数（`max`/`oom`/`oom_kill`），单位是次数 | 它是**该 cgroup 创建以来**的累计，用差值判断本次；默认含后代，只看本级要用 `memory.events.local` | 与内核 OOM 日志、退出码一起看 | `oom_kill` 增长即确证组级 OOM |
| `cpu.max`/`cpu.weight` | 它们是 CPU 配额与权重（配额形如「周期 额度」，单位是微秒） | `cpu.max` 是**硬顶**，配额打满表现为延迟而不是报错；`cpu.weight` 只在同层竞争时体现，整机空闲时改它没有效果 | 与每核占用、组内 `nice` 一起看 | 配额撞满表现为延迟，不是报错 |

`VmSwap` 与整机换页速率的读法：前者是「这个进程有多少匿名页被换出」（kB），后者是整机视角的速率。**单看 `VmSwap` 大于 0 不代表有问题**——它说明这些页被换出去了，是否影响延迟要看换入活动与内存压力指标；两者一起抬头才是真的紧张。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 「`ps` 里看到几个进程，系统里就有几个」 | `ps` 默认按线程组统计，而真正被调度、被限制、被杀的是 task |
| 用 `ps` 的 `%CPU` 找此刻的热点 | 由于它是生命周期平均值，刚启动的进程分母小，所以数字虚高 |
| 拿 `top` 第一屏的数字做结论 | 因为第一次刷新没有前一时间点，所以要先等到第二次 |
| 「整机 CPU 不高，肯定不是 CPU 问题」 | 单线程热点、绑核错误与 GC 停世界这三种情形都会造成这个外观 |
| 只看一个上下文切换数字 | 你必须把自愿与非自愿两者比增长速度，因为单看无法定性 |
| 「`kill` 返回成功就说明信号生效了」 | `kill` 返回成功只说明送达；信号可能被忽略、被阻塞，或在 `D` 状态等不到投递时刻 |
| 「137 就是被 OOM 杀了」 | 137 只说明死于 `SIGKILL`，因此要拿内核日志、组事件计数与人工记录来定性 |
| 对僵尸进程发信号 | 它已经终止，所以命令不报错也不生效；要处理的是它的父进程 |
| 看到「父进程是 1」就认定由 init 管理 | 中间层退出后子进程会被收养，因此 `nohup`、`Type=forking` 都会长成这样 |
| 拿宿主视角的整机数字判断容器 | 容器的额度与用量在 cgroup 文件里，而容器内的整机文件反映的仍是宿主 |
| 手工把 PID 写进 cgroup 接口文件 | 这破坏了 cgroup v2 唯一管理者的计数：服务停不掉、状态看不到、限制失效 |
| 没有任何留档就重启 | 重启会清掉大部分现场，因此内核日志的早期记录、未持久化的日志与内存里的状态都随之消失 |

## 要点自测

**问：把「一个进程的一生」压成四句话，每句话里的关键接口是什么？**
答：诞生阶段的关键接口是 `fork` 继承了什么、`execve` 保留了什么；运行与等待阶段的关键接口是状态字母与等待点，以及排队与等待之间的区分；被通知阶段的关键接口是信号先挂起、等从内核态返回用户态才处理；结束与回收阶段的关键接口是三种死法各自留下的证据与 `wait()` 的回收责任。

**问：一个服务「对 `SIGTERM` 没反应」，你会依次排除哪几种可能？**
答：我会先看它是否主动忽略（`SigIgn` 有位），再看它是否被阻塞（`SigBlk`），然后看它有没有装 handler（`SigCgt`），接着看它是不是卡在 `D` 状态等不到投递时刻，最后看它是不是容器里的 PID 1（因为容器里内核对 PID 1 不执行默认动作）。

**问：为什么 137 不能直接写成「被 OOM 杀」？要补哪几类证据？**
答：137 只等价于「死于 `SIGKILL`」。要补的证据有三类：整机内核日志里的 OOM 记录、cgroup 事件计数里 `oom_kill` 的差值，以及人工与编排层的操作记录。三者都没有时，要写成「死于 `SIGKILL`，来源待查」。

**问：为什么「把所有进程的常驻集加起来」对不上整机用量？**
答：因为共享页在每个映射它的进程里各算一份，所以相加必然偏大；同时 `tmpfs` 与共享内存占内存而不占磁盘，内核对象与页表又不挂在任何用户进程名下，被 cgroup 计入的页缓存也可能落在整机统计里。因此要对账就要用均摊口径，或直接看整机分项。

**问：`nice`、`cpu.weight`、`taskset`、`cpuset` 分别在什么层生效？**
答：`nice` 在调度组内部起作用，并且只在有竞争时有效；`cpu.weight` 在 cgroup 之间分配 CPU；`taskset` 改的是单进程的 CPU 亲和掩码；`cpuset` 限定整组可用的 CPU 集合，因此它与 `taskset` 的关系是**交集**。

**问：哪些证据重启之后就没了？哪些能活过重启？**
答：重启之后就失去的证据有 `/proc` 下的一切（`wchan`、`stack`、位图）、内核环缓冲里的早期记录、未持久化的日志与内存中的状态。能活过重启的证据有落在磁盘上的 core、持久化目录里的日志、cgroup 事件计数（在单元存活期间）以及外部监控与告警数据。

**第一反应不要做什么**：不要在没确认「它还在不在」之前动手；不要用状态字母当原因；不要用单点采样当趋势；不要用 `kill` 的返回值当生效证明；不要在没有任何留档的情况下重启或强杀。
