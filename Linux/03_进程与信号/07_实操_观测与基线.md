# 观测与基线

## 1. 一个问题，一把工具

| 你想知道 | 用什么 | 关键字段或文件 |
| --- | --- | --- |
| 现在谁在吃 CPU / 内存 | `top`、`pidstat` | 需要两次采样；`top` 从第二次刷新起可信 |
| 某个进程此刻吃多少 CPU | `pidstat -p <pid> 1` | 按秒的区间值，最适合留档 |
| 一批进程的静态清单与父子关系 | `ps --forest`、`pstree -p` | 一次性快照，适合贴进工单 |
| 有多少个进程、多少个 task | `ps -e`、`ps -eLf`、cgroup 的 `pids.current` | `ps` 默认按线程组统计；限制与调度按 task |
| 某个进程的状态与等待点 | `/proc/<pid>/status`、`wchan`、`stack` | 卡死类问题的第一现场 |
| 某个进程的内存构成 | `/proc/<pid>/status`、`smaps_rollup` | 常驻、均摊、私有三种口径 |
| 某个进程的上限是多少 | `/proc/<pid>/limits`、`prlimit --pid` | 进程**实际生效**的值，唯一权威 |
| 某个进程开着哪些文件与连接 | `ls -l /proc/<pid>/fd`、`lsof -p` | 句柄泄漏的第一刀 |
| 某个进程属于哪个 cgroup | `/proc/<pid>/cgroup`、`systemctl status` | 决定它的上限来自哪一层 |
| 组内任务数与上限 | cgroup 的 `pids.current`/`pids.max` | 容器「起不了进程」先看这两项 |
| 组的内存额度与事件 | `memory.current`/`max`/`peak`/`events` | 容器账本在这里，不在容器内的整机文件里 |
| 这个进程是谁拉起来的 | 服务管理器的状态查询、`/proc/<pid>/status` 的 `PPid` | 服务看单元，普通进程看父进程 |
| 崩溃有没有留现场 | core 的落点规则与系统级收集工具 | 决定「有 core 没 core」的是一组开关 |
| 谁在批量创建进程 | `/proc/loadavg` 最后一列 + 按父进程聚合的 `ps` | 创建风暴的定位入口 |

表里的「用什么」要分清两类：**命令**（`ps`、`top`、`pidstat`、`pstree`、`prlimit`、`lsof`——文档在 `man 1` 或 `man 8`）与**内核接口文件**（`/proc/...`、`/sys/fs/cgroup/...`——直接读就有，不需要任何工具）。分不清时看文档节号：`man 2` 是系统调用、`man 3` 是库函数、`man 5` 是文件格式。

**本页所有数值——命令块里的输出，以及正文场景里的时间戳、进程数、百分比——都只是示意，不代表你的机器**；贴进工单时必须声明它来自哪台机器、哪个时间点。

## 2. 怎么读这些数字

每个字段的完整读法（是什么 / 单位 / 判据 / 与谁同看 / 转向哪一步）集中在体系篇的关键字段表里。这里只补三类最容易读错、且直接决定下一步动作的判据。

### 2.1 采样类数字：第一行必须丢掉

`vmstat`、`iostat` 这类工具的第一行是**自开机以来的平均值**，不是「现在」，脚本里取数必须跳过第一行（`iostat` 用 `-y` 可以直接省掉它）；`top` 没有「自开机平均」这个概念——它的首屏只是启动后的第一个内部区间，同样从第二次刷新起才可信：

```bash
pidstat -p <pid> 1 5                 # 验证：每秒一行共 5 行；这是区间值，可直接留档
top -b -n2 -d 1 | awk '/^ *PID/{n++} n==2'
                                    # 验证：按迭代横幅切分，只留第二轮；表头行数随任务数与终端宽度变化，不要依赖固定行号
cat /proc/<pid>/io                   # 验证：累计值；隔 10 秒再读一次相减才是速率
vmstat 1 5                           # 验证：整机视角，从第二行起看
```

`ps` 的 `%CPU` 与上面几个都不同：它是**生命周期平均值**（累计 CPU 时间 ÷ 进程已运行时长）。三条由此推出的判据：

- 新启动的进程 `%CPU` 会虚高（分母太小），不能拿它判断「刚起来的进程为什么这么吃 CPU」；
- 长时间运行的进程 `%CPU` 会被历史稀释，抓不到此刻的尖峰；
- 多线程进程的百分比可以超过 100%（每核 100% 累加）。

**要判断「此刻」就换采样类工具，要判断「长期」才用 `ps` 的平均值**，并在留档时写清用的是哪一个。

### 2.2 内存类数字：先定口径

同一个进程会有三个「内存占用」：

```bash
cat /proc/<pid>/status | grep -E 'VmSize|VmRSS|VmSwap'      # 验证：地址空间 / 常驻 / 被换出（单位 kB）
cat /proc/<pid>/smaps_rollup | grep -E '^(Rss|Pss|Private_Clean|Private_Dirty)' # 验证：常驻、均摊与私有口径（单位 kB，按全名挑，避免连带 Pss_Anon 一类汇总行）
```

判据与用法：

- **`VmSize` 只用来解释「它要了多少地址」**，不用来判断占用。线程栈预留、按最大堆预留、大文件映射都会把它撑大；
- **`VmRSS` 是整组共享的一个数**，不能按线程相加，也不能跨进程相加（共享页会重复计数）；
- **跨进程对账用 `Pss` 之和**，它把共享页按使用者数量均摊，所以不会重复计数；但它只覆盖**被映射的页**（内核内存、页表不在其中），全机相加只约等于被映射页之和，不等于整机用量，也不能与 `free` 的 `used` 比大小；判断「谁真的占着内存」用 `Private`/`Uss`；
- **`VmSwap` 非 0 不等于有问题**。它说明有匿名页被换出；要判断是否影响延迟，得和换页速率、内存压力指标一起看。

### 2.3 句柄类数字：水位而不是绝对值

句柄这类**计数型**资源，绝对值的意义很有限，要看的是「用量 / 上限」这个比例和它的趋势：

```bash
cat /proc/sys/fs/file-nr                        # 验证：整机已分配 / 未使用 / 上限（第二个字段按内核文档恒为 0，第三列就是 fs.file-max）
ls /proc/<pid>/fd | wc -l                       # 验证：当前打开的 fd 数
ls -l /proc/<pid>/fd | awk '{print $NF}' | sort | uniq -c | sort -rn | head
                                                # 验证：按目标归类，一眼看出是套接字还是普通文件
cat /proc/<pid>/limits | grep -i 'open files'   # 验证：进程实际生效的软/硬限制
```

`file-nr` 的第三列就是 `fs.file-max`，它在 systemd 的机器上常被抬到 `2^63−1`，所以水位判断真正相关的是 `fs.nr_open`；第二个字段恒为 0 的原文见内核 `Documentation/admin-guide/sysctl/fs.rst`（*"always reports 0 as the number of free file handles"*）。

起步判据（**没有通用阈值，要和自己机器的基线比**）：

- 用量持续超过上限的 70% 且仍在上涨 → 值得加监控与排查；
- 用量长期稳定在高位（例如 80% 但不涨） → 是容量规划问题，不是泄漏；
- 用量**长期单调上涨**（跨天、跨周） → 泄漏特征，去 fd 构成里找是哪一类；
- fd 构成里 `socket` 占大头 → 往连接未释放、连接池无上限方向查；普通文件占大头 → 往日志文件、临时文件方向查。

`ls /proc/<pid>/fd | wc -l` 数的是**已打开的文件描述符个数**，与 `/proc/<pid>/limits` 里 `open files` 的上限**是同一口径**。口径真正不同的是 **`lsof -p`**——它把 `cwd`/`rtd`/`txt` 与加载的动态库也算进去，条数明显更多。**要水位就对同一条命令，要构成再上 `lsof`。**

## 3. 采样纪律与基线

采集进程数据有一条容易吃亏的地方：**这类指标绝大多数是累计值或瞬时值，不能单点解读**。

### 3.1 四条纪律

**同口径**：CPU 用哪个工具、内存用哪个口径、句柄数用哪条命令，一次采集里固定下来，跨次对比才成立。

**带时间戳与主机标识**：`date`、`hostname`、`uptime` 三样必须一起留。时间不对，后面所有证据都对不上；跨机对比少了主机标识就等于没有对比。

**至少两次**：速率类指标（CPU 占比、上下文切换、IO、换页）必须两次采样。`/proc` 下的累计值（`io`、事件计数）也必须两次读数相减。

**留原始输出**：不要只留自己算出来的结论数字。原始输出里包含了当时的口径、上下文与「你没想到要看的字段」。

### 3.2 一份只读基线卡

接手一台机器或给一个服务建基线时，下面这组命令全部只读，**生产机上也可以做**：

```bash
date; hostname; uptime                          # 验证：时间基线与负载
uname -r; cat /etc/os-release | head -3         # 验证：内核与发行版（默认值随它们变化）
stat -fc %T /sys/fs/cgroup                      # 验证：cgroup2fs 表示 v2
ps -e --no-headers | wc -l                      # 验证：线程组（进程）总数
ps -eLf --no-headers | wc -l                    # 验证：task 总数——两者之差就是线程
cat /proc/loadavg                               # 验证：负载与最近分配的 PID（连看两次算 PID 消耗速率）
ps -eo pid,ppid,user,stat,pcpu,pmem,etimes,time,comm --sort=-pcpu | head -20
                                                # 验证：CPU Top 20（etimes 运行时长，time 累计 CPU 时间）
ps -eo pid,nlwp,rss,comm --sort=-rss | head -15 # 验证：内存 Top 15 与各自线程数
ps -eo pid,nlwp,comm --sort=-nlwp | head -10    # 验证：线程数 Top 10
ps -e --ppid 2 --no-headers | wc -l             # 验证：内核线程数量的估算（按父进程是 kthreadd 计），基线值不是异常
                                                # 独立核验：抽样读 /proc/<pid>/status 的 PPid，看父进程是否真是 kthreadd
cat /proc/sys/fs/file-nr                        # 验证：整机句柄水位
sysctl kernel.pid_max kernel.threads-max fs.nr_open fs.file-max vm.max_map_count
                                                # 验证：内核级上限基线
ulimit -Sa; ulimit -Ha                          # 验证：当前会话的软/硬限制
systemctl show -p DefaultLimitNOFILE -p DefaultTasksMax   # 验证：服务层的默认限制
systemctl --failed --no-pager                   # 验证：有没有失败的服务单元
journalctl -p warning -b --no-pager | tail -30  # 验证：本次启动以来的告警
systemd-cgls | head -30                         # 验证：cgroup 树（服务 → 进程的归属）
```

对单个服务再补三样，才算「这个服务的基线」：

```bash
systemctl show -p MainPID -p TasksMax -p LimitNOFILE -p KillMode -p TimeoutStopUSec -p Restart <svc>
                                                # 验证：主进程、上限、停止与重启策略
cat /proc/$(systemctl show -p MainPID --value <svc>)/limits | grep -i -E 'open files|processes|core'
                                                # 验证：进程实际生效的限制（唯一验收依据）；MainPID=0 说明单元没在跑，/proc/0 不存在，先确认它活着再取数
CG=$(systemctl show -p ControlGroup --value <svc>)   # 验证：先现取单元的 cgroup 路径，别按 system.slice 硬拼（user 单元在 user.slice）
cat /sys/fs/cgroup$CG/pids.current /sys/fs/cgroup$CG/pids.max
                                                # 验证：组内 task 用量与上限
```

**基线卡要留下的字段**：机器标识与时间；内核、发行版、init 系统版本；cgroup 版本；进程数与 task 数；CPU 与内存 Top、线程数 Top；内核级上限（`pid_max`、`threads-max`、`fs.nr_open`、`fs.file-max`）；整机句柄水位；服务层默认限制；每个关键服务的主进程、限制实际值、所在 cgroup、停止策略。

**为什么要连服务层默认限制一起留**：它是一大批「服务偶尔报打开文件过多」的根因所在，而它与登录会话的限制配置**一点关系都没有**。留档的意义就在于以后再遇到时能立刻对比出「是默认值太小，还是它涨上来了」。

### 3.3 取证要趁现场还在

进程类故障的现场大多是**活的**（进程还在）或**易失的**（重启即失）。分清三类：

| 证据 | 重启后 |
| --- | --- |
| `/proc` 下的一切（`wchan`、`stack`、位图、fd、smaps） | 消失 |
| 内核环缓冲里的早期记录 | 可能被覆盖 |
| 未持久化的日志 | 消失（先确认日志是否持久化） |
| 落在磁盘上的 core | 保留 |
| cgroup 事件计数 | 单元存活期间保留；单元被停掉即回收 |
| 外部监控与告警数据 | 保留 |

**动手之前先确认「它还在不在」**：进程还在时能现取 `wchan`、`stack`、`fd`、内存；进程已经没了时只剩日志与 core。这两类的处置顺序完全相反，判断错方向会白跑一趟。

## 4. 常见故障与排查方向

下面八个场景都按同一个结构写：**具象场景 → 排查顺序（先看什么、看到什么转向哪）→ 一份合格的回答**。场景里只列**该场景特有**的命令；`ps`/`vmstat`/`pidstat` 这类通用取数与基线采集见第 1~3 节，字段判据见体系篇。所有命令都是只读；涉及变更的动作会单独标注。

### 4.1 场景：一个服务卡住，`kill -9` 也杀不掉

**场景**：4 vCPU / 8 GiB 的机器，数据库主机。14:20 起三个数据库进程处于 `D` 状态，业务接口超时率上升。值班同事已经对其中一个 PID 发过两次 `kill -9`，进程还在。

**排查顺序**：

```bash
date; hostname; uptime                                  # 验证：时间基线（先固定现场的时间坐标）
ps -o pid,ppid,pgid,sid,stat,wchan:24,etime,cmd -p <pid># 验证：状态与等待点
cat /proc/<pid>/stack                                   # 验证：内核态调用栈（需要 root）
cat /proc/<pid>/syscall                                 # 验证：正在执行或阻塞在哪个系统调用
iostat -x 1 5                                           # 验证：哪块盘的 await / 队列深度异常
cat /proc/mounts | grep -i -E 'nfs|ceph|efs'            # 验证：有没有网络存储挂载
dmesg -T | grep -i -E 'nfs|blocked for more than|hung task'   # 验证：内核是否已报阻塞超时
```

看到什么转向哪：

- **等待点在块设备或文件系统的函数上** → 去看那块设备的健康与队列（介质错误、RAID/多路径状态）；`await` 高而队列浅说明设备慢，队列深说明堆积在排队；
- **等待点在网络存储相关函数上** → 先看服务端可达性；挂载恢复后进程往往自己走出来，不需要杀；
- **等待点是内核锁或驱动函数** → 评估升级内核或驱动，先把业务切走；
- **内核已报 `hung task`** → 排查重点在存储与驱动路径，不是进程本身。

**一份合格的回答**

- **结论**：三个进程卡在内核态不可中断等待，等待点是块设备 IO。`kill -9` 无效是因为信号没有投递时刻，不是权限或内核拒绝。
- **依据**：`ps` 的 `stat=D`、`wchan` 与 `/proc/<pid>/stack` 指向块设备路径；`iostat -x` 显示该盘 `await` 与队列深度异常；`dmesg` 在 14:19 已有该盘的 IO 报错，14:20 业务才开始超时——报错在前、现象在后。
- **边界**：目前只确认「在等这块盘」，尚未确认是介质错误、线缆还是上层 RAID 降级——这需要看阵列与盘的详细状态。
- **动作**：先把只读副本切走并摘掉该库的写流量，再排查存储链路；进程不主动杀（它携带着锁与在途状态），等 IO 恢复后自行退出。

**第一反应不要做什么**：不要反复补刀，不要重启机器（现场全丢且不保证不复发），不要在没摘流量的情况下等它自己好。

### 4.2 场景：`ps` 里出现大量 `<defunct>`

**场景**：8 GiB 的机器，某自研服务重启后 `ps` 里出现 200 多个僵尸，进程数监控报警。

**排查顺序**：

```bash
ps -eo pid,ppid,stat,comm | awk '$3 ~ /Z/ {print}' | tee /tmp/zombie-$(date +%F-%H%M).txt
                                            # 验证：僵尸清单留档（带时间戳）
ps -eo pid,ppid,stat,comm | awk '$3 ~ /Z/ {print $2}' | sort | uniq -c | sort -rn
                                            # 验证：按父进程聚合，找出制造者
ps -o pid,ppid,stat,wchan:24,etime,cmd -p <ppid>   # 验证：父进程自身状态（是否卡在 D）
pstree -p <ppid> | head -30                 # 验证：父进程名下的进程树规模
```

看到什么转向哪：

- **父进程卡在 `D`** → 按 4.1 处理父进程；僵尸会随它恢复或退出而消失，不需要单独处理；
- **父进程是「不会回收子进程的程序」** → 列入缺陷单改程序；紧急时重启该父进程（它退出后僵尸被收养者回收）；
- **父进程是容器里的 PID 1** → 给容器加 init（`--init`/`tini`），或让应用主进程负责回收。

**一份合格的回答**

- **结论**：僵尸堆积的成因是父进程未回收退出状态。当前父进程是某服务的 worker 管理器，运行正常但不调用等待接口。
- **依据**：僵尸清单按 `PPID` 聚合后全部指向同一个父进程；父进程自身状态为 `S`（不是卡在 `D`），说明它有能力回收而没回收——这是程序缺陷而非资源问题。
- **边界**：僵尸本身几乎不占内存，风险在于 PID 与进程表项的消耗；当前 200 个尚未逼近上限，但增长趋势需要看。
- **动作**：留档后列入缺陷单；若数量继续上涨到影响新建进程，临时重启该父进程止血，并监控僵尸数回到基线。

**第一反应不要做什么**：不要对僵尸发信号（它已经终止），不要把「批量清理僵尸」当成处置动作。

### 4.3 场景：服务「悄悄消失」，只留下一句「重启过」

**场景**：凌晨 2:10 某个服务消失，编排层已自动拉起，当前状态正常。`systemctl status` 显示 `Result=signal`，`ExecMainStatus=9`。

**排查顺序**：

```bash
systemctl show -p ExecMainCode -p ExecMainStatus -p Result -p ExecMainExitTimestamp -p NRestarts <svc>
                                            # 验证：退出状态与本次启动以来的重启次数
journalctl -u <svc> --since '1 hour ago' | tail -50        # 验证：应用侧收尾与报错日志
journalctl -k -b | grep -i -E 'oom|killed process'         # 验证：内核是否做过 OOM
CG=$(systemctl show -p ControlGroup --value <svc>)         # 验证：先现取单元的 cgroup 路径（user 单元在 user.slice）
cat /sys/fs/cgroup$CG/memory.events                        # 验证：组级 oom_kill 计数（该 cgroup 创建以来的累计，用差值判断本次）
systemctl status <svc> | head -20                          # 验证：CGroup 与 Tasks 行（当前进程范围）
```

看到什么转向哪：

- **内核日志有 OOM 记录，或组级 `oom_kill` 增长** → 定性为 OOM，转容量与上限复盘（撞的是整机还是自己的上限，看日志里给出的 cgroup 路径）；
- **`ExecMainCode=killed` 但没有 OOM 证据** → 查人工操作审计、变更记录、编排层事件、健康检查重启；
- **`ExecMainCode=exited` 且退出码非 0** → 看应用日志里的收尾记录，这是应用自己的退出路径；
- **同一服务反复出现** → 先处理「别再无限重启」（限流或临时关掉自动重启），再逐个分析，否则现场会被一次次重启冲淡。

**一份合格的回答**

- **结论**：进程死于 `SIGKILL`，来源已定性为内核级 OOM（不是人工），撞的是这台机器的整机水位。
- **依据**：内核日志 02:09:47 有该进程的 OOM 记录（含打分与 RSS）；该服务所在 cgroup 的 `memory.events` 中 `oom_kill` 无增长，说明不是组级配额；近一周该服务 RSS 增长与流量峰值相关。
- **边界**：内核环缓冲只覆盖到 02:00 之后，更早的记录已被覆盖；未持久化的应用日志无法回溯。
- **动作**：给该服务补上内存上限把故障域收窄，同时按峰值水位评估容量；监控加内存水位与重启次数。

**第一反应不要做什么**：不要因为「已经自动恢复」就跳过取证；不要在没看内核日志前写「推断为 OOM」；不要在没确认原因前反复手工重启——那只是把证据冲掉。

### 4.4 场景：`fork: Resource temporarily unavailable`

**场景**：某服务 QPS 上升后开始报 `Resource temporarily unavailable`，同机其它服务正常，重启服务能暂时恢复。

**排查顺序**：

```bash
CG=$(systemctl show -p ControlGroup --value <svc>)   # 验证：先现取单元的 cgroup 路径，别按 system.slice 硬拼
cat /sys/fs/cgroup$CG/pids.current /sys/fs/cgroup$CG/pids.max
                                        # 验证：组内 task 用量与上限（current 含全部后代）
cat /proc/$(systemctl show -p MainPID --value <svc>)/limits | grep -i processes
                                        # 验证：进程侧的最大进程数（按 real UID 计）；MainPID=0 时先确认单元在跑
sysctl kernel.pid_max kernel.threads-max   # 验证：整机两条上限
dmesg -T | grep -i 'pids controller' | tail -5   # 验证：内核是否拒绝过 fork
ps -eo user,ppid,comm --no-headers | sort | uniq -c | sort -rn | head -20
                                        # 验证：谁在批量创建（按用户 / 父进程 / 命令名聚合）
```

两条配套读数在第 3.2 节与 2.1 节：`/proc/loadavg` 最后一列连看两次算 PID 消耗速率，`vmstat 1 5` 从第二行起看内核态 CPU 与上下文切换是否同步飙升。

看到什么转向哪：

- **`pids.current` 贴着 `pids.max`** → 撞的是组上限，先判断是业务量正常增长还是程序在批量创建；
- **内核日志有控制器拒绝记录** → 同上，这条日志是组级限制的确证；
- **PID 消耗速率快 + 内核态 CPU 高 + 上下文切换高** → 创建风暴，处置方向是在源头减量（限流、改创建模型），不是扩上限；
- **只有该 UID 的进程失败，其它用户正常** → 撞的是按用户计数的限制；
- **`pids.current` 与整机上限都还远** → 往地址空间限制与内存方向看（那类失败报的是另一种错误）。

**一份合格的回答**

- **结论**：`fork` 失败的原因是服务所在 cgroup 的任务数上限被撞满，不是整机 PID 耗尽。
- **依据**：`pids.current` 等于 `pids.max`；内核日志有该 cgroup 的控制器拒绝记录；整机 `pid_max` 与 `threads-max` 余量充足；PID 消耗速率在 5 分钟内跳升两个数量级，说明存在批量创建。
- **边界**：尚未确认批量创建是正常业务量还是缺陷（例如重试逻辑失控）；这决定了「扩上限」与「修程序」哪个是长期方案。
- **动作**：临时提高该服务的任务数上限止血并留档，同时摘出创建源的行为特征；下一步定位是哪个上游触发。

**第一反应不要做什么**：不要直接调 `ulimit -u`（四类上限里只覆盖一类，且按用户计数），不要在内核态 CPU 还被创建风暴烧着的时候只扩上限。

### 4.5 场景：`too many open files`

**场景**：一个已经跑了两周的 Java 服务开始偶发失败，日志里有打开文件过多。

**排查顺序**：`cat /proc/sys/fs/file-nr` 看整机水位；`ls /proc/<pid>/fd | wc -l` 看进程用量；再用 2.3 节那条归类命令把 fd 构成留档——**这是定位泄漏的唯一线索**；最后 `cat /proc/<pid>/limits | grep -i 'open files'` 确认实际生效的软硬限制，`grep -i Threads /proc/<pid>/status` 确认线程数（线程数也占句柄与内核栈）。

看到什么转向哪：

- **整机水位接近上限** → 整机问题：找出是哪几个进程在吃，再决定扩容还是限流；
- **fd 里 `socket` 占大头且持续上涨** → 连接未释放或连接池无上限；先留档再滚动重启回收；
- **普通文件占大头** → 日志文件、临时文件未关闭；检查是否与轮转配合出问题；
- **数量长期稳定在高位不涨** → 是容量规划问题（长连接本来就多），按限制线在正确的一层调上限；
- **上限调得很大但仍在 1024 附近出问题** → 1024 有两个来源：进程的 `RLIMIT_NOFILE` 软限本来就是 1024，以及老程序用了有编译期上限的接口（`select` 的 `FD_SETSIZE`）。判据是**先确认软限、再怀疑编译期上限**：软限还压在 1024，就先把它放开；放开之后仍卡在 1024，才去查 `select` 这一类接口。

**一份合格的回答**

- **结论**：句柄耗尽由连接未释放引起，属于应用侧泄漏，不是上限设小了。
- **依据**：`/proc/<pid>/fd` 的构成里 socket 占 90% 以上，且与本机整机水位无关；对比两周前的同类留档，socket 数从 800 涨到 9600，形态单调上涨；进程限制为 65535，尚未触顶但增长趋势明确。
- **边界**：无法从 fd 构成判断是应用没关还是下游没关；需要连接的目标地址与对端日志进一步定位。
- **动作**：先完成 fd 构成留档，再滚动重启该实例回收句柄；同时把「句柄水位 / 上限」加入监控，并把泄漏列入缺陷单。**不把上限调到很大来掩盖它。**

**第一反应不要做什么**：不要在没有任何留档的情况下重启（构成与增长曲线全丢）；不要把「扩容」当修复。

### 4.6 场景：崩溃了，但机器上找不到 core

**场景**：某服务崩溃后自动重启，`systemctl status` 显示 core 相关状态，但按经验路径找不到 core 文件。

**排查顺序**：

```bash
cat /proc/sys/kernel/core_pattern                 # 验证：是文件名模板还是管道程序（决定去哪找）
cat /proc/sys/fs/suid_dumpable                    # 验证：特权程序是否允许产生 core
systemctl show -p LimitCORE <svc>                 # 验证：服务层的 core 上限
cat /proc/$(systemctl show -p MainPID --value <svc>)/limits | grep -i core   # 验证：进程实际值（MainPID=0 时先确认单元在跑）
coredumpctl list | tail -5                        # 验证：systemd 的集中存储里有没有（属 systemd-coredump 包，最小化安装常常没装）
ls -l /var/crash/ 2>/dev/null; du -sh /var/lib/systemd/coredump/ /var/crash/ 2>/dev/null
                                                 # 验证：两种落点的清单与占用；Debian/Ubuntu 装了 apport 后 core 落在 /var/crash/
```

看到什么转向哪：

- **进程的 core 上限为 0** → 这是「没有 core」最常见的原因；要在服务层放开或限量；
- **落点规则是管道程序** → 去对应的集中收集工具里找，不要在工作目录里找；
- **是特权程序** → 上游 `suid_dumpable` 默认 0（不产生，防的是信息泄露），但 Debian/Ubuntu 装了 apport 之后它是 2（`suidsafe`）——core 会产生且只归 root 读，落点由 `core_pattern` 决定（装了 apport 时是一个管道程序），不能按「默认不产生」下结论；
- **落点在容器工作目录且不可写** → 换一个可写落点或调整规则；
- **同一服务反复出现** → 先限制 core 的产量与重启频率，保住**一份**有代表性的现场，再去做根因分析（产能跟不上生产速度时，磁盘会先满）。

**一份合格的回答**

- **结论**：没有 core 的原因是该服务进程的 core 上限为 0——这条与**内核版本**无关，但与**发行版的崩溃收集工具强相关**：落点规则（`core_pattern`）与 `suid_dumpable` 都是发行版设的；而且管道收集时 `RLIMIT_CORE` 不生效，所以还要对上收集工具自己的配置。
- **依据**：进程实际生效的限制里 core 为 0；落点规则是系统级集中收集；集中存储里没有任何该可执行文件的记录。
- **边界**：放开之后 core 的体积可能接近进程的整个地址空间，需要同时设置产量上限，否则一次崩溃循环就能写满根分区。
- **动作**：在一台实验机上验证放开后的实际体积与落点，再决定生产上的限量值；把 core 目录纳入容量监控。

**第一反应不要做什么**：不要靠「再崩一次」等它出现——反复崩溃会先吃掉磁盘；不要在不设产量上限的情况下直接放开。

### 4.7 场景：服务 CPU 打满，但整机看着不高

**场景**：某服务响应变慢，业务方说「CPU 打满」。值班看整机 CPU 只有 15%。

**排查顺序**：

```bash
mpstat -P ALL 1 5                                   # 验证：每颗核的占用，找 %idle 为 0 的那一列
ps -L -p <pid> -o pid,tid,pcpu,stat,comm --sort=-pcpu | head
                                                    # 验证：线程级视角（TID 是第一列），输出可直接留档
pidstat -u -w -t -p <pid> 1 5                       # 验证：线程级 CPU 与上下文切换速率
taskset -cp <pid>                                   # 验证：它被允许在哪些 CPU 上跑
```

看到什么转向哪：

- **某颗核 `%idle` 为 0，其余空闲** → 单线程热点或绑定错误；带 TID 去应用侧对号（线程名、日志、运行时线程转储）；
- **每颗核都不高但服务慢** → 它在等，不在算；转自愿上下文切换、系统调用与 IO 方向；
- **线程级占用均匀且都高** → 是真实的并行负载，转容量评估；
- **绑核与容器可用 CPU 集合冲突** → 亲和设置没生效（两者是交集关系）。

**一份合格的回答**

- **结论**：不存在「整机 CPU 高」这个前提，但服务确实被一颗核限制住了——热点的形态是单线程。
- **依据**：每核视角显示第 3 颗核 `%idle` 为 0，其余三颗空闲；线程级视图里某个 TID 持续接近 100%，其余线程几乎为零；`ps` 的进程级 `%CPU` 同样接近 100%（它不按核数归一），被摊薄的只有整机视角——单核跑满只占整机的 **1/核数**，所以「整机不高」不能否定单核热点。
- **边界**：单线程热点可能是锁竞争、正则回溯、序列化或运行时的 GC，具体是哪一类要看线程转储与应用指标。
- **动作**：带 TID 取一次线程转储留档，再决定是拆并行度、优化热点路径还是限制输入规模。

**第一反应不要做什么**：不要因为整机 CPU 低就排除 CPU 方向；不要直接重启（线程名、运行时长与转储机会全丢）。

### 4.8 场景：容器停止要等满超时，退出码 137

**场景**：某容器每次发布都要等 10 秒才停掉，退出码 137。宿主上这个服务的停机策略是默认值。

**排查顺序**：

```bash
PID=$(docker inspect -f '{{.State.Pid}}' <ctr>)       # 验证：容器 PID 1 在宿主上的 PID 号（从宿主侧取数，不依赖镜像里有 ps）
cat /proc/$PID/root/proc/1/status | grep -E '^(Name|SigIgn|SigBlk|SigCgt)'
                                                 # 验证：容器内 PID 1 是谁、它的信号处置如何（精简镜像没有 ps 也读得到）
cat /proc/$PID/root/proc/1/cmdline | tr '\0' ' '  # 验证：PID 1 的完整命令行（判断它是不是 shell 包的）
nsenter -t $PID -p -- ps -eo pid,ppid,stat,comm | grep Z   # 验证：容器内有没有僵尸堆积（借宿主机的 ps 进命名空间看）
journalctl -u <运行时> --since '10 min ago' | tail -50 # 验证：运行时的停止与强杀记录
```

看到什么转向哪：

- **PID 1 是 shell（`bash`/`sh`）** → 它默认不处理终止信号；改用 exec 形式启动，或加一个真正的 init；
- **PID 1 是应用但被 shell 包了一层** → 应用没有真正成为 PID 1，收不到直接投递的信号；
- **容器内堆僵尸** → PID 1 不回收孤儿，同样指向 init 的缺失；
- **`SigIgn` 里终止信号有位** → 应用主动忽略了它，属于应用侧问题，改超时无用。

**一份合格的回答**

- **结论**：容器停不掉的原因是容器里的 PID 1 是 shell，它没有为终止信号安装处理函数；内核对 PID 1 不执行信号默认动作，于是信号等于被忽略，只能等超时后由宿主侧强杀。
- **依据**：容器内 PID 1 的命令行显示为 shell；它的信号位图里终止信号既未捕获也未阻塞（即走默认），而这在 PID 1 身份下等于忽略；运行时日志里有超时后强杀的记录。
- **边界**：即使换成 exec 形式启动，还要确认应用自己处理终止信号并回收子进程，否则只是把问题从 shell 转给了应用。
- **动作**：把启动命令改成 exec 形式，或加一个 init 作为 PID 1；验收标准是停止耗时小于超时上限、退出状态为正常退出而非被信号终止、容器内无僵尸。

**第一反应不要做什么**：不要把停止超时调长了事——那只是让每次发布更慢，收尾依旧没人做。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 用 `top` 第一屏的数字做结论 | 第一次刷新没有前一时间点；脚本里要取第二次 |
| 用 `ps` 的 `%CPU` 判断此刻热点 | 它是生命周期平均值；新进程分母小、数字虚高 |
| 用 `ps aux \| wc -l` 统计进程数与额度 | 口径不对（按线程组计数，且默认不含线程），推算出的余量一定错 |
| 把各线程或各进程的常驻集相加 | 共享页重复计数；要跨进程对账用均摊口径 |
| 「`VSZ` 几个 G 肯定是泄漏」 | 那是地址空间账本；判断占用要看常驻/均摊，判断泄漏要看趋势与构成 |
| 读 `/proc/<pid>/io` 报错就认为内核不支持 | 多数是权限问题（该文件通常只允许属主或特权用户读） |
| 只对目标进程留一个数字 | 没有时间、口径与上下文，无法与下次对比；快照要成组取 |
| 记录时只写 PID | PID 会复用；证据必须带时间、主机名与进程名 |
| 只看 cgroup 事件计数的绝对值 | 它们是累积值；判断「这次」必须用差值 |
| 拿宿主视角的数字判断容器 | 容器内的整机文件反映的仍是宿主；容器的账在 cgroup 里 |
| 在没确认进程是否还在的情况下动手 | 「卡住」与「没了」两类问题的取证顺序相反，先确认再行动 |

## 要点自测

**问：`ps`、`top`、`pidstat` 给出的 CPU 百分比为什么不一样？**
答：`ps` 是生命周期平均值（累计 CPU 时间 ÷ 运行时长），`top` 从第二次刷新起是区间值，按秒采样的工具给出的也是区间值。三个数不同是口径差异，留档时必须写明用的哪个工具、哪个时间窗口。

**问：想知道一个进程「卡在内核的哪里」，看哪几个文件？按什么顺序？**
答：先 `/proc/<pid>/status` 的 `State` 确认类别，再 `/proc/<pid>/wchan` 拿到等待点（进程在跑时是 `0`），需要细节时看 `/proc/<pid>/stack`（要权限），配合 `/proc/<pid>/syscall` 与当时的 IO/网络报错。**不要只看状态字母。**

**问：一份可对比的性能/进程快照至少包含什么？**
答：时间与主机标识；内核、发行版、init 系统版本与 cgroup 版本；同时刻的 CPU/内存 Top、线程数、整机资源与句柄水位；失败单元与告警日志；目标进程的 PID、进程名、运行时长与它实际生效的限制。

**问：句柄数到什么程度算异常？**
答：先和自己机器的基线比，而不是套通用阈值。可操作的起步判据：用量持续超过上限 70% 且仍在上涨；跨天跨周单调上涨（泄漏特征）；构成里某一类占比压倒性（决定排查方向）。稳定在高位不涨通常是容量规划问题。

**问：为什么「先取证」这件事没有选择余地？**
答：`/proc` 下的一切、内核环缓冲里的早期记录、未持久化的日志都是易失的；重启或强杀之后无法重建。取证与止血的先后可以按影响面决定，但**在动手之前留下那一组只读证据**是硬要求。

**第一反应不要做什么**：不要在没取证据前重启；不要用单点采样当趋势；不要用工具默认输出的第一行；不要把不同口径的数字放进同一张对比表。

- `man 1 ps`、`man 1 top`、`man 1 pidstat`、`man 1 pstree`、`man 1 prlimit`、`man 8 lsof`、`man 1 nsenter`：工具的列定义、采样语义与权限要求。列口径随工具版本变化，引用前现场核对。
- `man 5 proc_pid_status`、`man 5 proc_pid_stat`、`man 5 proc_pid_limits`、`man 5 proc_pid_wchan`、`man 5 proc_pid_stack`、`man 5 proc_pid_smaps`、`man 5 proc_pid_io`、`man 5 proc_pid_task`、`man 5 proc_sys_fs`、`man 5 proc_sys_kernel`、`man 5 proc_loadavg`：`/proc/<pid>/` 下各文件的字段口径与权限，以及 `/proc/loadavg`、`/proc/sys/fs/file-nr`、`/proc/sys/fs/nr_open`、`/proc/sys/kernel/pid_max`；`man 5 proc` 只作 procfs 的总览。
- `man 5 limits.conf`、`man 8 pam_limits`、`man 5 systemd.exec`、`man 5 systemd.resource-control`、`man 5 systemd.kill`、`man 5 systemd.service`（`TimeoutStopSec=` 的定义页）：服务侧限制、停止策略与默认值的查询位置（**默认值现场取**）。
- 内核文档 `Documentation/admin-guide/cgroup-v2.rst`、`Documentation/filesystems/proc.rst`、`Documentation/admin-guide/sysctl/kernel.rst`、`Documentation/admin-guide/sysctl/fs.rst`：**按与目标机器同一主版本（6.x）取**，字段与默认值随版本变化。
- `man 5 core`、`man 5 proc_sys_kernel`（`core_pattern`）、`man 5 proc_sys_fs`（`suid_dumpable`）：core 的四道开关与查询入口；`coredumpctl`/`coredump.conf` 属 `systemd-coredump` 包，装了才有，没装时看发行版自带的崩溃收集工具（Debian/Ubuntu 是 apport，落点 `/var/crash/`）。
- `man 1 systemctl`、`man 5 systemd.service`、`man 5 systemd.unit`：单元状态字段（退出码、信号、结果）与重启策略的查询方式。
