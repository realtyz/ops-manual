# 实战：追问链

前面几篇建立了模型。模型能否实际使用，取决于一个具体条件：**当对方沿同一问题逐层追问时，作答能否逐层成立。**

本篇选取三道高频题，逐层展开从"仅给出结论"到"给出边界与代价"的演进过程。重点不在标准答案，而在于**每一层所考察的能力**。

## 1. 追问链的四步

现场与值班的追问方向是一样的，只有四步，顺序固定：

| 步 | 追问内容 | 检验目标 | 无法作答时的典型表现 |
| --- | --- | --- | --- |
| 1 | **证据**：依据是什么 | 是实际观察还是仅阅读过 | 回答"一般来说""应该会" |
| 2 | **边界**：该结论在何种条件下不成立 | 是否具备条件意识 | 回答"基本都这样" |
| 3 | **反例**：何种情况下该处置会使结果变差 | 是否具备代价意识 | 回答"那不会发生" |
| 4 | **代价**：该做法牺牲了什么 | 是否能够做出取舍 | 回答"没有代价" |

评分只看五项：影响面、分层、证据、边界、止损与回滚。仅给出结论的答案得分最低，**因为它连第 1 层都未达到**。

三道题分别覆盖排队、计量口径与生效链三个方向，涉及四条线与约束环。

## 2. 题一：负载高而 CPU 使用率不高

| 项 | 内容 |
| --- | --- |
| 涉及的知识线 | 算力（运行队列）、持久（不可中断睡眠）、连接（软中断） |
| 涉及的连接点 | 内核态时间与软中断、回收与 IO 等待 |
| 最易失分的层级 | 第 2 层（边界）——把"CPU 不高"当作"算力无问题"，或把"IO 等待"当作唯一的其它可能 |

### 2.1 四层演进

**第 0 层（多数人的回答）**

> 负载高但 CPU 不高，一般是 IO 问题，看看磁盘是不是慢了。

这句话本身不算错，但它只是把两个名词并列。一旦追问"如何确认是 IO"便无法继续。

**第 1 层（有分层与判据）**

> 先看 `load` 是由什么构成的：`vmstat 1` 里的 `r` 是可运行任务数，`b` 是不可中断睡眠的任务数。`b` 高说明任务卡在 IO 或锁上；`r` 高说明确实在争抢算力，那就要看 `mpstat -P ALL` 的**最热核**——整机 25% 完全可以是"4 核里 1 核打满"。然后看 `ps -eo stat,wchan`，`D` 状态加 `wchan` 能直接指出在等什么。

到这里已经过了第 1 层：有分层、有字段、有判据。

**第 2 层（带上边界）**

> 这个结论有边界。`load` 高还有第三种来源：**短时突发**。它数的是"某一瞬间在排队和等待的任务数"，1 分钟平均值会被一次密集的短任务抬起来，而 `vmstat` 的采样窗口不一定抓得到。所以至少要取两次读数、间隔固定，再和业务侧的延迟分位数对齐看。
>
> 另外，`iowait`（`wa`）不是可靠判据：`proc(5)` 明写这个值不可靠，逐核统计在有些情况下算不出来，甚至可能下降（man-pages 6.7 起这段原文在 `man 5 proc_stat`）。所以"IO 高不高"不能只看 `wa`，要看设备侧的 `await`/`aqu-sz` 和进程侧的 `wchan`。

这一层是分水岭：能说出"我要用的那个字段本身有已知缺陷"，说明不是在背工具输出的列名。

**第 3 层（带上反例与代价）**

> 有一个反例会让我先不动手：如果 `b` 高但 `iostat` 的 `await` 与 `aqu-sz` 都不高，那阻塞不在本地设备上——可能在网络存储、在锁、在别的 cgroup 的配额上。这时去调本机 IO 参数不会有任何效果。
>
> 处置上的取舍也要说清：`D` 状态的进程**杀不掉**（`SIGKILL` 也要等它从不可中断睡眠里出来），所以"先终止那个进程"这条路在 `D` 状态下不成立。可行的顺序是：先取证（`wchan`、`/proc/<pid>/stack`、设备侧计数），再判断能不能摘流量隔离影响，最后才谈重启——重启是唯一能确定毁掉现场的动作，放在最后。
>
> 代价是：摘流量会减少可用容量，取证会多花几分钟。如果影响面还在扩大，就要先摘流量，取舍标准是"影响面扩大的速度"。

### 2.2 该题考察的层级

| 层级 | 被筛掉的典型回答 | 站住的标志 |
| --- | --- | --- |
| 第 1 层 | "IO 问题，看磁盘" | 说出 `r`/`b`、最热核、`wchan` 三件对象 |
| 第 2 层 | "`wa` 高就是 IO 瓶颈" | 主动指出 `iowait` 不可靠、`load` 有短时突发来源 |
| 第 3 层 | "先终止那个 D 状态的进程" | 知道 `D` 状态杀不掉、知道重启会毁现场、给出顺序与代价 |

## 3. 题二：`df` 已满而 `du` 数值很小

| 项 | 内容 |
| --- | --- |
| 涉及的知识线 | 持久（容量与 inode）、内存（Page Cache 与脏页） |
| 涉及的连接点 | inode 与 fd、Page Cache、脏页与提交语义 |
| 最易失分的层级 | 第 2 层（边界）——只考虑到"删除文件后空间未释放"这一种成因 |

### 3.1 四层演进

**第 0 层**

> 有进程还占着被删掉的文件，用 `lsof +L1` 找出来重启就行了。

这是最流行的答案，也是**只覆盖四类成因里的一类**。

**第 1 层（先把成因分类）**

> `df` 与 `du` 对不上，至少有四类成因，先分类再动手：
>
> 1. **已删除但被持有**：`lsof +L1` 能看到 link count 为 0 的已打开文件，`/proc/<pid>/fd` 里显示 `(deleted)`；
> 2. **inode 耗尽**：`df -h` 有余量但 `df -i` 到 100%——建不了文件，报错文本和空间满一样是 `No space left on device`；
> 3. **保留块**：ext4 默认给 root 留 5% 的块，普通用户写不进去时 root 还能写，表现为"服务写失败但 `df` 没满"；
> 4. **挂载与可见性**：`df` 看的是某个文件系统，`du` 走的可能是另一个挂载点（覆盖挂载、绑定挂载），或者 `du` 没有加 `-x` 而跨了文件系统。

**第 2 层（带判据与边界）**

> 判定顺序：先 `df -hT` 与 `df -i` 一起看，确定是空间还是 inode；再 `du -xsh /path/*` 与 `df` 的已用量对比，差值大就往"已删除但被持有"查；`lsof +L1` 的**输出大小要加起来与差值对照**，不是看到有输出就算命中——差 30 GiB 而 `lsof` 只列出几十兆，说明还有别的原因。
>
> 边界有两条：一是 `lsof` 需要权限，非 root 看不到别人的 fd；二是**容器里 `df` 反映的是容器的文件系统视图**，与宿主不是一回事，排查要在正确的命名空间里做。

**第 3 层（反例与代价）**

> 反例：如果文件是被**日志轮转**改成新的 inode、而进程还持有旧的，`lsof +L1` 可能看不到（link count 仍是 1，只是名字换了）。这时要看 `ls -l /proc/<pid>/fd` 指向的实际路径，以及新旧文件的 inode 是否相同。
>
> 处置的代价差别很大：
>
> - **让持有者重开文件或重启**：立刻释放，但重启会丢现场，要先取证；
> - **直接 `rm` 新文件**：没用，空间不还；
> - **`truncate` 被持有的文件**：能立刻还空间，但会破坏该进程正在写的数据，属于不可逆动作，只在前两种都不可行且影响面还在扩大时考虑；
> - **扩容**：买时间不解决问题，而且如果成因是 inode 或持有，扩容也解决不了。
>
> 我的默认顺序是：先取证（`df` 两份 + `du` + `lsof` + inode），再选最小可逆的动作；如果影响面已经不可接受，就先摘流量把业务拉回来，把取证顺序往后放——但要在动手前记下当时读到的数字。

### 3.2 该题考察的层级

| 层级 | 被筛掉的典型回答 | 站住的标志 |
| --- | --- | --- |
| 第 1 层 | "`lsof +L1` 重启一下" | 说出四类成因，并知道 inode 与空间的报错同形 |
| 第 2 层 | "看到 `lsof` 有输出就是它" | 会把 `lsof` 的大小与差值对照，会提权限与命名空间边界 |
| 第 3 层 | "`truncate` 一下最快" | 说得出 `truncate` 是不可逆动作、扩容买时间不解决成因 |

## 4. 题三：修改配置后未生效

| 项 | 内容 |
| --- | --- |
| 涉及的知识线 | 约束环五层（四层技术上限 + 组织层）、观察面（生效值的取法） |
| 涉及的连接点 | 版本与默认值、cgroup、PID 1、监听队列与 socket 激活 |
| 最易失分的层级 | 第 3 层（反例）——未考虑到"同一项配置存在多个写入点"时会相互覆盖 |

### 4.1 四层演进

**第 0 层**

> 重启一下服务就好了。

这句话的问题不在于错误，而在于**它跳过了"配置是否已被读取"这一环节**。重启后虽已生效，但仍无法解释此前为何未生效，同类问题仍会再次出现。

**第 1 层（先按四个落点分类）**

> "不生效"有四个不同的落点，先确认改的是哪一个：
>
> 1. **内核参数的启动参数**（`/proc/cmdline`）：只在启动那一刻生效，改配置文件后要更新引导器配置并重启；
> 2. **内核参数的运行时值**（`sysctl`）：`sysctl -w` 只改运行时，落盘要写进 `.d` 目录；
> 3. **服务的生效配置**（unit 与 drop-in）：改了文件要 `daemon-reload`，已在跑的进程还要 `restart` 才带上新环境；
> 4. **进程自己的配置**（应用读的文件）：`reload` 与 `restart` 的差别由应用决定，systemd 无法代为保证。

**第 2 层（带生效值的取法）**

> 每一类都有取生效值的命令，**"文件里写了"不是判据**：
>
> - 启动参数：`cat /proc/cmdline`；
> - 运行时参数：`sysctl -n <key>`；
> - unit：`systemctl show -p <属性>`、`systemctl cat <unit>`、`systemctl show -p FragmentPath -p DropInPaths`；
> - 系统级配置的合并结果：`systemd-analyze cat-config <文件>`；
> - SSH：`sshd -T`（合并 `Include`/`Match` 与默认值后的生效配置）；
> - 文件系统挂载：`findmnt -o TARGET,SOURCE,FSTYPE,OPTIONS`。
>
> 这里有一个具体的误区：`sysctl --system` 与开机时的 `systemd-sysctl.service` **读的文件集合不完全一样**。开机路径只读 `.d` 目录（`/etc/sysctl.d/`、`/run/sysctl.d/`、`/usr/local/lib/sysctl.d/`、`/usr/lib/sysctl.d/`）而不读 `/etc/sysctl.conf`；而 procps 的 `sysctl --system` 会在 `.d` 之后**再读一次** `/etc/sysctl.conf`。所以在同一个文件里写了两次值，用 `sysctl --system` 和重启得到的可能是两个结果。本库在实验机上用 `strace` 逐条核对过这个读取集合，条件是那把 procps 版本，换发行版要重新核。

**第 3 层（反例与代价）**

> 反例：**生效的覆盖面**。改 unit 的第 2 层上限，只影响此后由 systemd 启动的进程；已经在跑的进程要在 `restart` 后才带上新值。改 cgroup 第 3 层的文件立刻生效，但若目标进程并不在该 cgroup 内（容器场景较为常见），实际修改的是另一个组。改第 4 层的全局值，可能被别的写入点按字典序覆盖回去。
>
> 处置顺序与代价：
>
> - **先取证再改**：`sysctl -n`、`systemctl show`、`sshd -T` 各取一次"现在生效的值"，与"文件里的值"对照，差值就是问题所在；
> - **回滚要用单文件**：回滚时用 `sysctl -p <单个文件>`，不要用 `sysctl --system`——后者会把所有文件按顺序重放一次，可能引入并非有意生效的写入点；
> - **一次只改一个变量**：同时修改 drop-in 与 sysctl 之后问题消失，无法确定是哪一项起作用，同类问题仍会重复。
>
> 最后一句是代价：走完取证会多花几分钟。如果这是一次事故的止损，先做可逆动作（回滚到上一个已知状态）把业务拉回来，把"为什么没生效"留给复盘——但要把回滚前后的生效值各记一份。

### 4.2 该题考察的层级

| 层级 | 被筛掉的典型回答 | 站住的标志 |
| --- | --- | --- |
| 第 1 层 | "重启服务" | 说出四个落点，并知道 `daemon-reload` 与 `restart` 是两件事 |
| 第 2 层 | "文件改了就应该生效" | 说出每一类的生效值取法，能举出"`--system` 与开机路径读的文件集合不同"这类实证 |
| 第 3 层 | "改完不好再说" | 知道覆盖面（已在跑的进程）、知道回滚要用单文件、知道一次只改一个变量 |

## 5. 三题的共同结构

三道题的回答结构完全一样，把它抽出来就是这一章要交付的那个视角：

1. **先分层，再动手**。任何现象先落在四条线与约束环上的某个位置，而不是先找命令。
2. **每句话都要能指到一个字段**。说不出字段名，就说明这句话是从别处听来的。
3. **主动交代边界**。哪些条件成立、哪些不成立、我用的那个字段本身有什么已知缺陷。
4. **给出代价与顺序**。可逆的动作在前，不可逆的在后；重启这类毁现场的动作排在最后。
5. **区分"实际执行过"与"我读过"**。亲手演练过的、转引别人的、未实测的，必须是三个不同的词。

这五条不需要额外背，它们是前 11 章每一章都在演示的同一件事。区不应只在于：**前 11 章是按对象演示，这一章是按追问演示。**

## 常见误解

| 说法 | 事实 |
| --- | --- |
| "现场就是考记住多少命令" | 追问的四步里没有一步是"命令数量"。它考的是证据、边界、反例与代价 |
| "答案是越全越好" | 全而平的回答在第 1 层就停住了：没有分层、没有取舍、没有边界 |
| "说'我不知道'就扣分" | 说"我不确定，我会用哪个命令去确认，如果看到 A 就转向 B"是合格答案；含糊地说"应该"才扣分 |
| "题答对了就行，追问是刁难" | 追问只沿着同一个问题的四步走，方向固定。被问住的不是知识，是结构 |
| "把未实测的说成实测的更有说服力" | 一旦继续追问细节就会露。标注未实测并给出补做方式，反而是"懂行"的证据 |

## 要点自测

- 追问链的四步是什么？哪一步最能区分"看过"与"背过"？
- 评分五要素是什么？只给结论的答案为什么最多两分？
- `load` 高的三种来源分别是什么？各自的判据字段是哪个？
- 为什么 `iowait` 不是可靠判据？`man` 里给出的理由是什么？
- `df` 与 `du` 对不上的四类成因分别怎么验证？
- 说出四类"配置不生效"的落点，以及每一类取生效值的命令。
- `sysctl --system` 与开机路径读的文件集合差在哪里？这个差异会在什么情况下咬人？
- 为什么回滚要用 `sysctl -p <单文件>` 而不是 `sysctl --system`？
- 三道题里出现的不可逆动作各是哪一个？各自的替代动作是什么？
- 用一句话说清"现场看你会觉得不一样"的那个视角是什么。
