# 附录：高频误判对照表

本表把全库最容易答错的说法集中到一处，并按**四条线 + 约束环 + 观察面 + 组织层**分组；之所以不按章节分组，是因为按章节分组等于把此前十一个阶段各自的结论再背一次。

本表的用法只有一个：**遮住右边两列，逐行只看左列，并说出该行的事实与出处**。若某一行说不出来，就在该行上标记圆点，随后把这一行记入错题清单。

## 1. 算力线

| 常见做法或说法 | 事实 | 出处 |
| --- | --- | --- |
| 负载高就是 CPU 忙 | `load` 把不可中断睡眠（`D` 状态）的任务也计入，因此它统计的是任务数而不是百分比，所以必须与核数对照才有意义 | 出自阶段 10 |
| 整机 CPU 不高就排除 CPU 问题 | 这里遇到的常是单核饱和：在 4 vCPU 的机器上单核跑满时，整机 `%usr` 就是 25%（即 1/4），而 `load` 只有 0.34（**转引**阶段 10 实测），因此整机读数不高并不排除 CPU 竞争 | 出自阶段 10 |
| `vmstat` 的 `si` 是软中断 | `si` 与 `so` 分别是换入与换出，因此它们与软中断无关；要读软中断，应当看 `mpstat` 的 `%soft` | 出自阶段 10 |
| 上下文切换多就说明系统有问题 | 切换要分自愿与非自愿两类：自愿切换多说明任务在等 IO 或等锁，因此它不构成 CPU 竞争的证据；只有非自愿切换多才说明存在 CPU 竞争 | 出自阶段 3、10 |
| `%sys` 高就是系统调用多 | `mpstat` 明确 `%sys` **不含**硬中断与软中断的时间，因此 `%sys` 高不等于系统调用多；要知道中断占用了哪些核，必须读 `/proc/interrupts` 与 `/proc/net/softnet_stat` | 出自阶段 6、10 |
| 进程多就说明线程多 | 内核调度的基本单位是 task，而 `ps -eLf` 数的正是 task，因此它与 `ps -e` 给出的进程数不是同一个量 | 出自阶段 3 |
| 火焰图什么都能看 | 火焰图通常只反映采样到的 on-CPU 栈，因此 off-CPU 等待采不到；若缺少符号或权限受限，同样采不到。它的横轴是样本占比，而不是时间轴 | 出自阶段 10 |
| `top` 首屏是自开机以来的平均 | **这个说法说反了**：本机实测首屏是**很短的一段差分**（开机 4 小时后启动自旋进程，3 秒后执行 `top -b -n1`，首屏即报 `%Cpu(s): 26.2 us`；若它真是开机以来的平均值，该值应接近 0）。首屏不能单独下结论的真实理由是：它是整机视角、不展开线程，而且窗口只有一两秒 | 出自阶段 10 |
| `strace` 是排查慢问题的首选 | **转引**阶段 10 实测，它带来约 **45 倍**减速（基线 51 ms 变为 2280 ms），因此不适合作为首选；正确的用法是短时、定向、只对单个进程使用，或者先读 `/proc` 与计数器 | 出自阶段 10 |
| USE 方法就是把监控工具挨个跑一次 | USE 方法是按资源依次过三个问题：利用率（Utilization）、饱和度（Saturation）与错误（Errors）；因此要先确定"哪个资源的哪一项"，再决定用哪个工具 | 出自阶段 10 |
| 上下文切换的累计值可以直接当速率用 | `/proc/<pid>/status` 与 `vmstat` 里的切换数都是累计值，因此必须差分才能得到区间增量；若要与其它速率比较，还要用同一口径的增量除以采样间隔 | 出自阶段 3、10 |

## 2. 内存线

| 常见做法或说法 | 事实 | 出处 |
| --- | --- | --- |
| `free` 显示可用内存很少，说明内存不够 | 判据是 `MemAvailable` 与内存 PSI，因为缓存占用是正常工作状态。**转引**阶段 10 实测：触碰 3 GiB 内存后，`MemAvailable` 从 7224 降到 4145 MiB，而 PSI 的 `avg10/60/300` 全程为 0（累计值 `total` 在涨：some 从 298 涨到 9695、full 从 208 涨到 9477） | 出自阶段 4（数字转引阶段 10） |
| PSI 的 `avg` 与 `total` 可以一起比大小 | 两者的单位不同，因此不能直接比大小：`avg10/60/300` 的单位是**百分比**，而 `total` 的单位是**微秒**，并且它还是累计值，所以要取两次读数的差值 | 出自阶段 9、10 |
| 退出码 137 就是被 OOM Killer 杀了 | 137 只说明进程被 `SIGKILL` 终止（因为 `128+9` 等于 137），而人工执行 `kill -9` 同样得到 137。要对 OOM 定性，证据是内核日志与 cgroup 的 `memory.events` | 出自阶段 3、4 |
| `VSZ` 很大就是内存泄漏 | 申请不等于占用：`malloc` 只登记虚拟地址与承诺额度，因此它不占用物理内存；只有首次写入时，进程才通过缺页拿到物理页 | 出自阶段 4 |
| `malloc` 成功说明内存已经到手 | 真正的物理页分配发生在首次写入时，因此 `malloc` 成功不代表内存已经到手；同时超额承诺（overcommit）允许承诺总量超过物理内存与 swap 之和 | 出自阶段 4 |
| `vm.swappiness=0` 等于关闭 swap | `vm.swappiness` 是内存回收的倾向权重，而不是开关，因此在内存压力下仍可能发生换页；若要真正禁用 swap，只能执行 `swapoff`，或在 cgroup 层设 `memory.swap.max=0` | 出自阶段 4 |
| 关掉 swap 更安全 | 关闭 swap 只是把"换页变慢"这一种代价换成了"被 OOM 终止"，因此它并不更安全 | 出自阶段 4 |
| "内存去哪了"只有一种答案 | "内存去哪了"有三类主要答案：tmpfs 与共享内存（`Shmem`）、内核 slab 与 dentry/inode 缓存（`Slab`），以及被 cgroup 计入的页缓存 | 出自阶段 4 |
| 容器被 OOMKilled 一定是宿主机内存不够 | 多数情况是 cgroup 级 OOM，因此整机可能还有空闲内存；判断时要同时看宿主侧与容器侧。内核日志里的约束来源（例如 `CONSTRAINT_MEMCG`）能直接指出是哪一层触发的 | 出自阶段 3、4、11 |
| 容器里 `top` / `free` 反映容器的真实约束 | 这两个命令在容器里看到的仍是整机口径，因此它们不反映容器的约束；要知道容器受到的限制，必须读 cgroup 文件，例如 `memory.max` 与 `cpu.max` | 出自阶段 10、11 |
| 容器内存用量可以直接拿宿主读数减 | 容器内的进程可能同时属于别的 cgroup，因此拿宿主读数相减得不到该容器的用量；正确做法是在**宿主侧的 cgroup 路径**上读用量，并确认该路径与容器一致 | 出自阶段 4、8 |
| "内存占用"只有一个口径 | 常驻、均摊与私有是三种不同的计量（分别为 `RSS`、`PSS` 与私有页）：因为常驻按使用者重复计数而均摊不重复，所以这两种口径在共享页多的进程上可以差一倍以上 | 出自阶段 4 |
| 内存回收慢是磁盘的问题 | 两者会互相拖慢：内存回收的落点是设备，因此设备忙时回收会变慢。判据是 `pgscan_direct` 增长与 `iostat` 的 `await` 上升**同时**出现 | 出自阶段 4、5、10 |

## 3. 持久线

| 常见做法或说法 | 事实 | 出处 |
| --- | --- | --- |
| `df` 和 `du` 对不上，说明 `du` 不准 | 对不上有四类原因：文件已被删除但仍被进程持有（用 `lsof +L1` 查）、目录被后续挂载覆盖、保留块与元数据占用，以及稀疏文件与延迟分配 | 出自阶段 5 |
| `rm` 后 `df` 没降，说明文件系统有问题 | 文件可能仍被进程持有，因此 `df` 不会下降；**转引**阶段 9 实测：在 64 MiB 的临时 loop 文件系统里删掉一个仍被持有的 **10 MiB** 文件后，`df` 的已用从 24576 字节涨到 10510336 字节，而 `du -sh` 只有 **20K**，`/proc/<pid>/fd/4` 显示 `(deleted)`，直到关掉该 fd 后才回落到 24576 字节 | 出自阶段 5、9 |
| "磁盘满"就是容量满 | "磁盘满"还有另外三种情形：inode 用满、ext4 保留块（默认 5%）与配额超限（报错文本为 `Disk quota exceeded`）；由于空间满与 inode 满的写入报错文本同为 `No space left on device`，所以只看报错文本分不出是哪一种 | 出自阶段 5 |
| XFS 可以缩容 | XFS 只能扩不能缩，因此缩容这条路走不通；ext4 虽然能缩，但必须先卸载，而且风险很高 | 出自阶段 5 |
| 可以在挂载状态下跑 `e2fsck` | `e2fsck` 必须在卸载（最稳妥）或只读挂载的状态下运行；XFS 对应的工具是 `xfs_repair`，而它默认拒绝对已挂载设备操作 | 出自阶段 5 |
| 文件系统变只读，先 `mount -o remount,rw` | 文件系统转为只读常常是内核的保护动作，因此要先查原因，例如 `dmesg` 里的 ATA/SCSI/NVMe 错误与阵列状态。另外，"遇到错误自动转只读"由**超级块里的 `errors=` 设置**决定，可用 `tune2fs -l <设备> \| grep -i 'Errors behavior'` 现场取（本库实验机读到 `Continue`，即不会自动转只读） | 出自阶段 5 |
| `%util` 100% 说明盘已经饱和 | `%util` 是"有请求发往设备"的时间占比，因此它不携带队列深度与延迟信息；要判断饱和，必须把它与 `await`、`aqu-sz` 连起来读 | 出自阶段 5、10 |
| `await` 高就是盘慢 | `await` 含排队时间，而且与请求规模强相关，因此它高不等于盘慢；**转引**阶段 10 实测：`w/s=324 × w_await=6.59 ms = 2.14`，与同窗口的 `aqu-sz=2.14` 吻合（Little's law）；而另一个窗口在 `%util=98.80%` 时 `aqu-sz` 才 3.15、`w_await` 只有 0.09 ms、`wareq-sz` 只有 4 KiB | 出自阶段 10 |
| IO 慢就是盘坏 | 先要看是否存在回写积压、备份抢 IO 或日志同步落盘，因为这三类都会让 IO 变慢；而盘的介质错误这类健康计数（用 `smartctl` 读）通常早于阵列降级出现 | 出自阶段 5、10 |
| RAID 5 能抵御任意两块盘同时故障 | RAID 5 只容忍单盘故障，因为重建期间再坏一块就会丢数据；而大容量盘的重建时间很长，所以重建窗口本身就是风险窗口 | 出自阶段 5 |
| LVM 扩容只要 `lvextend` 就完成了 | `lvextend` 只改逻辑卷，因此还要扩文件系统（可用 `lvextend -r`，或 `xfs_growfs` / `resize2fs`）；验收标准是 `df`，而不是 `lvs` | 出自阶段 5 |
| 配了 RAID 就等于有了备份 | RAID 只防单块盘故障，因此它不防误删、勒索加密、逻辑损坏与整机故障；备份的验收标准仍然是"能恢复并计时" | 出自阶段 5、11 |
| 写调用返回成功就说明数据已经在盘上 | "写成功"有三个层次：数据进了 Page Cache、进了设备缓存，或者已经提交落盘（`fsync()` 返回）；因为掉电时前两个都会丢，所以不能把这两种当作数据已经在盘上 | 出自阶段 5、11 |
| 日志轮转后应用会自动写新文件 | 持有旧 fd 的进程写的仍然是旧 inode，因此它不会自动写到新文件。`copytruncate` 是原地截断（inode 不变，但有丢数据窗口）；而 `create` + `postrotate` 则要求应用真的重新打开文件 | 出自阶段 9 |

## 4. 连接线

| 常见做法或说法 | 事实 | 出处 |
| --- | --- | --- |
| `tcp_fin_timeout` 能改 `TIME_WAIT` 时长 | 这个参数管的是 `FIN_WAIT2` 的超时，因此它改不了 `TIME_WAIT`；`TIME_WAIT` 的时长由内核常量 `TCP_TIMEWAIT_LEN` 固定为 **60 秒**（**转引**阶段 6 实测：0.5 秒采样下，连接在 **62.06 秒时仍在、63.07 秒时消失**），没有任何 sysctl 能改它 | 出自阶段 6 |
| `CLOSE_WAIT` 多要调内核参数 | `CLOSE_WAIT` 多说明应用收到了 FIN 却没有调用 `close()`，因此它只能靠改应用解决，调内核参数没有用 | 出自阶段 6 |
| `TIME_WAIT` 是异常状态 | 它是主动关闭方的正常状态，因此它本身不是故障；数量过多时，先看业务是否以短连接为主，再考虑是否引入连接复用 | 出自阶段 6 |
| 调大应用 backlog 就能解决队列溢出 | 队列的真实上限是 `min(backlog, somaxconn)`，因此只调大应用 backlog 不一定有效；实测 `listen(10000)` 在 `somaxconn=4096` 的机器上被静默截断成 4096 | 出自阶段 6 |
| 半连接队列满一定丢包 | 现代发行版默认 `tcp_syncookies=1`，此时内核对新连接改发 cookie，计数落在 `TcpExtSyncookiesSent`，因此 `ListenDrops` 不增长，也就未必丢包 | 出自阶段 6 |
| `ping` 通就说明网络没问题 | `ping` 通只证明 ICMP 可达；因为 TCP 可能因防火墙、队列溢出或应用未监听而失败，所以它不能证明网络没有问题 | 出自阶段 6 |
| 客户端偶发超时、服务端无日志就是"玄学" | 这类现象的常见现场是全连接队列溢出后内核静默丢弃 SYN；证据在 `nstat` 的 `TcpExtListenOverflows` 与 `ListenDrops`，由于这两项是累计值，所以要看两次读数的差值 | 出自阶段 6 |
| `ss -lnt` 的 `Recv-Q` 是队列上限 | 对 LISTEN 状态的套接字，`Recv-Q` 是当前队列深度，而 `Send-Q` 才是上限，因此读到 `Recv-Q >= Send-Q` 说明队列已满（内核允许比上限多一个）；若要知道是否"溢出过"，证据是 `nstat` 的 `TcpExtListenOverflows` 与 `ListenDrops` 的增量 | 出自阶段 6 |
| 抓包是排查网络的第一步 | 排查的第一步应当先读计数器（`nstat`、`ss -ti`），再决定要不要抓包；因为全量抓包既影响性能，也抓不完 | 出自阶段 6、10 |
| `ss -ti` 的 `rtt` 与 `iostat` 的 `await` 可以直接比 | 两者的单位其实相同：`man 8 ss` 写明 `rtt` 与 `rttvar` 的单位是**毫秒**，而 `await` 也是毫秒；它们不可比的原因是**对象不同**，前者是单条连接的往返时间，后者是设备的平均单次请求耗时（含排队）。真正属于"单位不同"的例子是 PSI 的 `avg*`（百分比）与 `total`（微秒） | 出自阶段 6、10 |
| 重传率高就是链路丢包率高 | 前者是本机 TCP 的累计重传次数（要取差值才能算成速率），后者是链路侧的丢包比例；由于两者不是同一个量，所以注入丢包时它们会同时变化，却不能互相替代 | 出自阶段 6、10 |
| 端口在听就说明服务健康 | 在 socket 激活的情形下，监听 socket 由 systemd 持有，而服务本身可能没有启动，因此"端口在听"不等于服务健康；`systemctl list-sockets` 与 `systemctl status` 要一起看 | 出自阶段 8 |
| 宿主能解析域名，容器里也一定能 | `/etc/resolv.conf`、`/etc/nsswitch.conf` 与 `/etc/hosts` 都位于容器自己的文件系统视图里，因此容器里的解析结果可以与宿主不同；同时 `getaddrinfo()` 与 `dig` 本来就可以给出不同结果 | 出自阶段 6、10 |
| 网络慢就是带宽不够 | 先要看是否在排队，判据是队列深度、`retrans`，以及 `rtt` 与 `minrtt` 的差距；一旦出现 `app_limited`，瓶颈就在应用侧，此时加带宽没有用 | 出自阶段 6、10 |

## 5. 约束环

| 常见做法或说法 | 事实 | 出处 |
| --- | --- | --- |
| 改 `/etc/security/limits.conf` 能改服务限制 | systemd 服务读的是 unit 里的 `LimitXXX=` 与 `TasksMax=`，而 `limits.conf` 只影响经由 PAM 的登录会话，因此改它动不了服务限制 | 出自阶段 3、8 |
| `ulimit -n` 改了当前服务的上限 | `ulimit -n` 只影响当前 shell 及其子进程，因此运行中的服务不受影响 | 出自阶段 3 |
| 改上限就是改一个数 | 实际生效的是前四层里**最紧**的那一层，这四层分别是会话的 `RLIMIT_*`、unit 属性、cgroup 文件与内核全局值；而第 5 层（组织）决定这一层现在能不能改，因此改错一层等于没改 | 出自阶段 3、8 |
| 改完 unit 上限就已经生效 | 改完 unit 上限只影响此后由 systemd 启动的进程，因为已在运行的进程要等到 `restart` 才会带上新值 | 出自阶段 8 |
| 改了 unit 文件就生效 | 从改文件到真正生效要经过三段：第一步改完文件后，`status` 会给出 changed on disk 警告，而 manager 里仍是旧值；第二步执行 `daemon-reload` 后 manager 变为新值，但运行中进程的环境仍是旧值；第三步执行 `restart` 之后，新值才真正进入进程 | 出自阶段 8 |
| `daemon-reload` 等于重启服务 | 它只重读 unit 定义，因此不重启进程 | 出自阶段 8 |
| `Wants=` 就等于 `After=` | `Wants=` 决定"要不要拉起对方"，而 `After=` 只决定顺序，因此两者不能互相代替；若不写 `After`，两个单元就会并行启动 | 出自阶段 8 |
| `Type=simple` 万能 | `Type=simple` 并不万能：若进程自己后台化，它会被控制组清掉（实测立刻变成 `inactive (dead)`），因此后台化的服务要用 `Type=forking`，或者改成前台运行 | 出自阶段 8 |
| `Type=notify` 一定能等到通知 | `Type=notify` 不一定能等到通知，因为默认值是 `NotifyAccess=main`，此时子进程发出的通知会被拒绝，于是要一直等到超时（**转引**阶段 8 实测：改成 `NotifyAccess=all` 后 0.0396 秒启动成功） | 出自阶段 8 |
| 沙箱选项报错是业务问题 | 常见的 `status=226/NAMESPACE`、`216/GROUP` 与 `203/EXEC` 都是 unit 配置导致的，因此它们不是业务问题 | 出自阶段 8 |
| `tmpfiles` 的 age 只看 mtime | `tmpfiles` 的 age 默认同时看 mtime、atime 与 ctime，并取其中最"严"的口径，因此只看 mtime 会判断错；例如"mtime 在 40 天前而 ctime 是今天"的文件不会被 `--clean` 删除，要删它必须用 `m:30d` 明确指定 | 出自阶段 8 |
| cron 的环境与登录 shell 相同 | 实测 cron 的环境只有 `HOME/LOGNAME/PATH/LANG/SHELL=/bin/sh/PWD`，因此它与登录 shell 不同；其中 `PATH` 与别名都不一样，而 `%` 必须写成 `\%` | 出自阶段 8 |
| `kill -9` 是常规手段 | 它是最后手段，而不是常规手段；因为 `SIGTERM` 可以被捕获并用于优雅退出，所以它才是 `systemctl stop` 发出的第一个信号 | 出自阶段 3 |
| `kill -9` 能终止一切进程 | `kill -9` 不能终止一切进程：发给 `D` 状态进程的信号会被挂起，要等它回到用户态才处理；而僵尸进程其实已经终止，它等的是**父进程**回收 | 出自阶段 3 |
| 僵尸进程占 CPU / 内存 | 僵尸进程已经退出，因此它只占一个进程表项，不占 CPU 与内存；真正要处理的是父进程没有回收它这个问题 | 出自阶段 3 |
| 主机上的 PID 1 能被 `kill -9` 终止 | 内核对 PID 1 不执行这些信号的默认终止动作，因此它不能被 `kill -9` 终止，普通用户执行时会拿到 `EPERM`；容器里的 PID 1 受同样的保护，但可以从宿主按宿主侧的 PID 把它终止 | 出自阶段 1、3 |
| 普通用户绑 80 端口要先改 `ip_unprivileged_port_start` | 更小的授权是给该二进制加上 `CAP_NET_BIND_SERVICE` 能力；而把 `ip_unprivileged_port_start` 改成 0 等于放宽整机策略，因此后者的影响面更大 | 出自阶段 7 |
| 系统起不来就重装 | 启动链的各个阶段各有自己的现场（固件屏、GRUB 提示符、initramfs shell、emergency mode），因此要先判断"现在是谁在输出"，而不是直接重装 | 出自阶段 2 |
| 机器莫名重启过，重启一次再看看 | 重启会覆盖现场，因此不能先重启；要先取 `journalctl -b -1`、`/var/crash/` 与带外日志 | 出自阶段 2 |
| "重启能解决 90% 的问题"是好经验 | 它同时毁掉 100% 的现场，因此这不是好经验；生产上应当先取证，再决定是否重启 | 出自阶段 1 |
| 权限拒绝只需要 `chmod` | `Permission denied` 可能来自五层：DAC 位、ACL、capabilities、挂载选项与 SELinux/AppArmor，因此只改 `chmod` 不一定有效；要按层排查，可用 `namei -l`、`getfacl`、`getcap` 与 `ls -Z` | 出自阶段 7 |
| 目录的 `r` 就能删里面的文件 | 能否删除目录里的文件看的是**目录的 `w` 位**，而不是 `r`；目录的 `x` 才是"能穿过"，而 `r` 只是"能列出名字" | 出自阶段 7 |
| `/tmp` 的 `1777` 只是为了方便 | `1777` 里的 sticky 位并不只是为了方便，因为它的作用是只允许文件属主（或 root）删除自己的文件 | 出自阶段 7 |
| 给脚本加 SUID 就能提权 | 内核对脚本上的 SUID 位不予理会，因此给脚本加 SUID 提不了权；SUID 只对二进制文件生效 | 出自阶段 7 |
| 用 `find -perm 4000` 找 SUID 文件 | `-perm 4000` 是精确匹配，因此它只命中权限位恰好为 4000 的文件；若要找"包含 SUID 位"的文件，必须用 `-perm -4000` | 出自阶段 7 |
| 账号默认设置已经够安全 | 默认值是 `PASS_MAX_DAYS=99999` 与 `INACTIVE=-1`（即不过期），因此加固必须主动收紧 | 出自阶段 7 |
| `setenforce 0` 是修复手段 | 它只是把强制拦截关成 permissive，此时审计与 AVC 拒绝记录**仍在产生**，因此它不是修复手段；正确做法是看 AVC 拒绝记录并调整策略或上下文 | 出自阶段 7 |
| 看配置文件就知道 SSH 的最终策略 | `Match` 会改变最终值，因此看配置文件得不出最终策略；应当用 `sshd -T -C user=...,addr=...` 看生效结果 | 出自阶段 7 |
| 加固的验收是"感觉关掉了" | 验收标准是**可核查**：账号、SUID/SGID/capabilities、监听端口、计划任务与自启、SSH 授权这五类基线 | 出自阶段 7 |
| 关掉 SSH 密码登录就算加固完成 | 还要禁 root 直登、只留必要认证方式、限制可登录用户与组、限制尝试次数与并发，并用 `sshd -T` 看 `Match` 之后的最终生效值 | 出自阶段 7 |
| 配了 VIP 就等于高可用 | 判据是"拔掉一台之后业务还剩多少"，它取决于单实例、流量切换、连接排空与余量 | 出自阶段 11 |

## 6. 观察面

| 常见做法或说法 | 事实 | 出处 |
| --- | --- | --- |
| 内核版本号可以直接跨发行版比大小 | RHEL 会把新特性回移到较老的主线版本上，因此版本号不能直接比大小（例如 RHEL 9 的基线是 5.14，Ubuntu 24.04 是 6.8，Debian 12 是 6.1） | 出自阶段 1 |
| 改了 `/etc/default/grub` 就生效 | 改完还必须重新生成配置（用 `update-grub` 或 `grub2-mkconfig`），因此只改文件不会生效；验收标准是 `cat /proc/cmdline` 的输出 | 出自阶段 2 |
| 启动参数和 `sysctl` 是一回事 | `/proc/cmdline` 里的启动参数只在启动那一刻生效，而 `sysctl` 改的是运行时参数，因此两者不是一回事 | 出自阶段 2 |
| 文件里写了就是生效了 | 文件里写了不等于生效，因为生效值有专门的取法：`sysctl -n`、`systemctl show -p`、`systemd-analyze cat-config`、`sshd -T` 与 `findmnt -o OPTIONS` | 出自阶段 2、7、8、11 |
| 参数改了不生效就再改一次 | 此时要先分清是哪套机制在读：开机阶段由 `systemd-sysctl` 读取，它只读 `.d` 目录；手工重放由 `sysctl --system` 执行，它在末尾还会再读一次 `/etc/sysctl.conf`。两者的合并规则相同：所有 `.conf` 按文件名字典序排序，名字靠后的覆盖靠前的，同名文件以 `/etc` 下的优先 | 出自阶段 11（口径已按实验机实测更正） |
| 回滚参数用 `sysctl --system` 最省事 | `sysctl --system` 会把所有文件按顺序重放一次，因此可能引入并非有意生效的写入点；由于单文件改动只涉及一个文件，所以回滚它应当用 `sysctl -p <单文件>` | 出自阶段 11 |
| 平均值正常就说明服务正常 | 平均值会掩盖长尾：1000 个样本（其中 950 个为 20 ms、45 个为 100 ms、5 个为 2000 ms）的平均值是 33.5 ms，而 `max` 是 2000 ms，因此平均值正常不能说明服务正常 | 出自阶段 9、10 |
| p95 只有一个标准算法 | 同一组样本按四种常见口径算出的 p95 分别是 20.0、24.0、96.0 与 100.0 ms，因此报分位数时必须连算法一起报 | 出自阶段 9 |
| 两个数字可以直接比大小 | 没有采集条件的数字不可比：同一个量在不同窗口既可以是 `0.09 ms`，也可以是 `6.59 ms`（**转引**阶段 10 实测，条件以该阶段为准），因此不能脱离条件直接比大小 | 出自阶段 9、10 |
| 时钟漂移只影响日志好不好看 | 跨机日志比对、告警时序、证书校验以及令牌与审计时间线全都依赖时钟，因此时钟漂移的影响不止于日志是否好看；一旦时钟未同步，"谁先谁后"的结论就整体作废 | 出自阶段 9、11 |
| 手动 `date -s` 对时最快 | 手动 `date -s` 会造成时间跳变，并破坏增量日志与监控数据，因此它不是对时的正确做法；正确的做法是修 NTP/chrony | 出自阶段 9 |
| 日志写满就先删大文件 | 此时先要看是谁在写、文件是否仍被进程持有；**转引**阶段 9 实测：`rm` 一个仍被持有的 **10 MiB** 文件后，`df` 的已用反而从 24K 涨到 10 MiB | 出自阶段 9 |
| `copytruncate` 是最安全的轮转方式 | `copytruncate` 的做法是**原地截断、inode 不变**：持有旧 fd 的进程继续写**同一个 inode**，因此不会写进归档，代价是截断与写入之间存在丢数据窗口；而"持有旧 fd 的进程把后续内容写进归档文件"其实是 **`create` 模式**的行为，所以不能说 `copytruncate` 最安全 | 出自阶段 9 |
| 日志里没有就是没发生 | 日志里没有，可能是没写进来、被限流、被轮转掉、没持久化，或者写到了另一个落点；因为这几类原因的排查方向不同，所以要分开排查 | 出自阶段 9 |
| `sar` 随时都能查到历史数据 | 能查到历史数据的前提是装了 sysstat 并且历史采集已启用。本实验机是正面样本（`sysstat-collect.timer` 处于 enabled、`/var/log/sysstat/` 里有当天数据），但很多机器上该目录根本不存在，因此要先确认有数据，再谈复盘 | 出自阶段 9 |
| trace 是日志的替代品 | 三者互补：日志回答"发生了什么"，指标回答"整体趋势"，而 trace 与 span 回答"这一次请求的时间花在哪一段"，因此 trace 不能替代日志 | 出自阶段 9 |

## 7. 组织层

| 常见做法或说法 | 事实 | 出处 |
| --- | --- | --- |
| 备份任务成功就说明备份可用 | 备份的唯一验收标准是"能恢复"并计时（记录实测的恢复耗时），因此任务成功不等于备份可用；同时快照与副本都不算备份 | 出自阶段 11 |
| 3-2-1 原则就够了 | 3-2-1 原则还不够，还要再加"1 份离线或不可变"，因为在线备份可能被勒索软件一并加密 | 出自阶段 11 |
| 「改动很小」可以不做变更评审 | 影响面与可逆性才是分级依据，因此改动大小不是免于评审的理由；而"小改动"造成的故障占比很高 | 出自阶段 11 |
| 证书浏览器能打开就说明配置正确 | 浏览器会自动补全证书链，因此它能打开不代表配置正确；正确做法是用 `openssl s_client -servername` 从外部验证，并看 `notAfter` | 出自阶段 11 |
| 复盘写到"以后小心"就够了 | 合格的改进项要写成"动作 + owner + 期限 + 验收方式"，因此"以后小心"不算改进项 | 出自阶段 11 |
| 有快照的实验机可以随便改 | 快照保的是存储一致性，保不住"进得去"，因此有快照也不能随便改；一旦网络配置或 `fstab` 被写坏，快照本身无法提供恢复手段 | 出自阶段 1、11 |
| 回滚命令写在变更单上就算有回滚方案 | 有回滚方案要三条同时成立：回滚动作明确、在实验机上跑过并记下耗时、耗时小于业务能容忍的中断时间；因此只把回滚命令写在变更单上不算有回滚方案 | 出自阶段 11 |
| 服务 `active` 就说明业务可用 | 本机实测在监听队列溢出计数上升的那段时间里，探活一直返回成功，因此 `active` 不代表业务可用；而 `systemctl start` 返回 0 只说明 `Type=` 的判定通过了 | 出自阶段 8、11 |

## 8. 使用方式

1. **遮住右两列自测**：逐行只看左列，并说出该行的事实与出处；若说不出来，就在该行上标记圆点。
2. **统计分布**：看清圆点集中在哪一组，下一轮就先补那一条线。
3. **每行配一句"不要做"**：知道错在哪只是第一步；只有能把第一反应改掉（不重启、不 `remount rw`、不全量抓包、不 `chmod 777`），才算会。
4. **挑五条在本机只读复验**：优先选能只读验证的项目（`free` 与 PSI、`df` 与 `du` 的关系、`ss -lnt` 的 `Recv-Q` 与 `Send-Q`、`sysctl -n` 的生效值、`tune2fs -l` 的 `errors` 行为）。只要有一项与预期不符，该项就是实际盲区。
5. **只读复验，不改参数**。因为为了"验证"而在生产机上改一个参数再改回来，已经构成一次未审批的变更，所以它不属于复习。

## 关于使用本表的常见误解

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 通读一次就以为会了 | 通读只带来熟悉感，因此不能据此认为已经会了；必须遮住答案做提取 |
| 只记右边的"事实"，不记左边的"说法" | 现场与限时推演中要识别的是**错误说法**，因此只记住右列没有用，要记住左列 |
| 不标出处 | 不标出处时，补缺就无法定位到篇；本表每一行都给出了来源 |
| 把带条件的结论当绝对结论 | 例如"60 秒"与"100 ms"都可能是对的，因为它们取决于哪个状态、哪个版本、哪个采集窗口 |
| 只做纸面自测，不复跑命令 | 数字背后的口径与输出形态才是最容易丢的部分，因此只做纸面自测补不上这一块 |

## 要点自测

- 本表为什么按"四条线 + 约束环 + 观察面 + 组织层"分组，而不是按阶段分组？
- 表里"事实"那一列，大多数可以概括成同一句话，那一句是什么？
- 从中挑出三条属于"同名不同物"的误判，并说出它们在别的线里分别指什么。
