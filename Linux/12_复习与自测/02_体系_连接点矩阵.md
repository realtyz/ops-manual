# 体系：连接点矩阵

十一条线各自的内部机制讲完之后，剩下的是它们之间的衔接处，而跨章出错几乎都发生在衔接处。这类错误的原因通常不是不了解某一侧的机制，而是不清楚两侧如何对应。

因此每一个连接点都要写清四项：两侧分别观察到什么、依据什么对齐、最容易在哪一句表述上出错，以及回到哪一章复核。

## 1. 连接点的使用方式

一个连接点的成立条件是：**去掉任何一侧，另一侧的结论都会出错**。

以 `df` 显示 100% 为例：若只观察存储一侧，则会得出磁盘已满的结论；然而 `du -xsh` 汇总后只有 30 GiB，两者的差距说明实际机制落在内存与存储的衔接处，即 Page Cache 中仍有脏页尚未回写，或者某个已删除的文件仍被进程持有。由于只观察一侧会去删除不应删除的文件，因此两侧对齐之后就应转去查 `lsof +L1` 与 `Dirty`。

因此连接点在排障中的使用分为三步：

1. **先判断这个问题跨越了哪两章**，而不是先判断它属于哪一章；
2. **确定两侧的同一性**（同一个 inode、同一个 cgroup、同一条连接、同一条时间轴）；
3. **用一侧的证据验证另一侧的结论**；若两侧说法不一致，则先核对口径，再核对机制。

对齐口径共有四种，因此遇到衔接处时先把它归入其中一类：

| 对齐口径 | 含义 | 例子 |
| --- | --- | --- |
| **同一对象** | 两侧分别指向同一个内核对象，只是视角不同 | 例如 fd 与它指向的 file 结构描述同一个对象，cgroup 与进程树描述同一批进程的两种归属，inode 与目录项分别给出同一个文件的对象编号与名字 |
| **单位与时钟** | 两侧的数值同源，但单位或时钟不同 | PSI 的 `avg*` 以百分比给出占用比例，而同一文件的 `total` 以微秒给出累计时间；日志对账要用墙上时钟，而单次耗时测量要用单调时钟 |
| **层次与范围** | 两侧是"整体与部分"或"上限与实际"的关系 | 整机是整体，而 cgroup 是它的一部分；`ulimit`、unit 属性与 cgroup 接口文件分别在不同层次上给出上限与实际用量 |
| **因果与传导** | 一侧的变化是另一侧的原因或结果 | 配额受限会使请求堆积，进而使内存占用放大；页缓存变脏后成为脏页，脏页回写又使设备的回写延迟上升 |

## 2. 算力线与其它线的衔接处

### 2.1 内核态时间与软中断

| 项 | 内容 |
| --- | --- |
| 两侧 | 一侧是算力线的时间构成（用户态、内核态、等待与被偷走的时间），另一侧是连接线与持久线的处理路径 |
| 对齐口径 | 同一对象：内核态时间中有一部分是**代其它线执行的工作**，例如收包软中断、块设备完成与缺页处理，因此两侧指向的是同一份时间 |
| 容易出错 | 若看到 `%sys` 高就判定"系统调用过多"，则会出错，因为应当先区分这部分内核时间属于哪一类工作；`mpstat` 明确 `%sys` **不包含**硬中断与软中断的时间，因此中断占用的核必须另看 `/proc/interrupts` 与 `/proc/net/softnet_stat` |
| 冲突时依据 | 先看中断与软中断计数是否在增长，再看系统调用计数是否在增长；若两者同时增长，则按"哪一类工作占用 CPU"分层 |
| 回哪一章复核 | 第 10 章原理篇（争抢为什么不按比例缩放）、第 6 章实操篇（收包软中断的分布） |

### 2.2 配额与排队

| 项 | 内容 |
| --- | --- |
| 两侧 | 一侧是约束环第 3 层的 cgroup 配额，另一侧是算力线中的运行队列 |
| 对齐口径 | 因果与传导：配额受限会使任务被节流，于是请求在应用侧或连接队列中堆积，最终使内存占用放大 |
| 读法（是什么 / 单位 / 判据 / 与谁同看 / 转向哪一步） | `cpu.stat` 是 cgroup 的 CPU 统计；`nr_throttled` 是**被节流的周期数**（单位：次，累计值，因此须取两次读数的差值）、`throttled_usec` 是被节流的时间（单位：微秒）；判据是同一周期内 `nr_throttled` 是否持续增长；它须与容器内应用的线程数、连接队列深度同看；一旦确认节流，则应转向判断"配额过小还是任务过多"，而不是先增加线程 |
| 容易出错 | 若在容器内看到 CPU 不高就增加线程，则会出错，因为配额是硬上限，增加线程只会使单次请求更慢 |
| 回哪一章复核 | 第 3 章治理篇、第 8 章原理篇（约束与隔离）、第 10 章体系篇（一次止损的闭环） |

### 2.3 中断与网卡队列

| 项 | 内容 |
| --- | --- |
| 两侧 | 一侧是连接线的收包路径，另一侧是算力线的核分布 |
| 对齐口径 | 同一对象：网卡多队列（RSS，Receive Side Scaling）将流量分配到不同核，因此队列与核一一对应 |
| 容易出错 | 若看到单核满负荷而整机空闲就归因于应用，则会出错，因为应当先看 `/proc/interrupts` 的每 CPU 计数是否集中于某一核，再看 `/proc/net/softnet_stat` 第 2 列（每 CPU 的丢弃计数） |
| 回哪一章复核 | 第 6 章实操篇、第 10 章原理篇 |

## 3. 内存线与其它线的衔接处

### 3.1 Page Cache：内存与存储共用同一份

| 项 | 内容 |
| --- | --- |
| 两侧 | 一侧是内存线（`Cached`、可回收、`MemAvailable`），另一侧是持久线（文件内容、脏页、回写） |
| 对齐口径 | 同一对象：**文件页同时计入内存与存储两套计量**；同一份页在内存侧计为可回收缓存，而在存储侧视为尚未落盘的数据 |
| 容易出错 | 若把"内存被缓存占满"判定为内存泄漏，或把"写调用返回成功"等同于"数据已在磁盘上"，则会出错，因为写入 Page Cache 只完成一半，另一半由 `fsync()` 或 `O_SYNC` 决定 |
| 冲突时依据 | 若 `df` 显示无空间而 `du` 显示的占用量很小，则应在内存侧查看 `Dirty`/`Writeback`，并在进程侧查看 `lsof +L1` |
| 回哪一章复核 | 第 4 章体系篇（计量线）、第 5 章原理篇（写入路径与完整性） |

### 3.2 cgroup：进程树与资源计量

| 项 | 内容 |
| --- | --- |
| 两侧 | 一侧是进程线（父子关系、进程所属单元），另一侧是资源线（四条线的用量均按组计量） |
| 对齐口径 | 同一对象：cgroup 是一棵**与进程树无关的树**；一个进程在进程树上是某个服务的子进程，而在 cgroup 树上属于某个 slice/service 或某个容器 |
| 读法 | `cpu.stat`/`memory.current`/`pids.current`/`io.stat` 均为**累计值或瞬时值**，其中 `memory.current` 的单位是字节（除以 1048576 得 MiB）；`memory.events` 为累计计数，因此须用差值判断"该时间段内是否发生"；这些值须与宿主侧同名文件对照，因为两者不是同一个数值；`oom_kill` 增长之后才转向"上限由谁设置、设在哪一层" |
| 容易出错 | 若用宿主的 `free` 判断容器内存，或在容器内调用 `sysctl` 并认为修改了宿主，则会出错，因为容器的 `net.ipv4.*`、`vm.*` 多为独立命名空间或只读 |
| 回哪一章复核 | 第 4 章治理篇、第 8 章原理篇（约束与隔离） |

### 3.3 PID 1：内核与用户态的接口

| 项 | 内容 |
| --- | --- |
| 两侧 | 一侧是内核的进程模型（PID 1 的特殊性、孤儿进程被收养、信号语义），另一侧是用户态（systemd 作为 PID 1 承担编队列与监督） |
| 对齐口径 | 同一对象：**systemd 即 PID 1 本身**；因此"内核启动 init"与"systemd 装载 unit"是同一条链上的相邻两步，而不是两件事 |
| 容易出错 | 若把"服务由 systemd 管理"与"进程由内核调度"视为互不相关的两层，则会出错，因为孤儿进程被 PID 1 收养、僵尸进程由 PID 1 回收、`KillMode=` 决定终止哪一组，这些动作都发生在该衔接处 |
| 回哪一章复核 | 第 2 章原理篇（从内核到 PID 1 与用户态）、第 3 章原理篇（进程的一生）、第 8 章体系篇 |

### 3.4 tmpfs 与共享内存：挂载在内存上的文件系统

| 项 | 内容 |
| --- | --- |
| 两侧 | 一侧是持久线（有路径、有目录、可被 `df` 观察到），另一侧是内存线（不落盘、占用物理内存、不可回收） |
| 对齐口径 | 同一对象：`tmpfs` 的页计入**内存计量**（`Shmem`），而不计入磁盘计量；它可回收的前提是未被换出到 swap 且没有进程持有 |
| 容易出错 | 若在 `/dev/shm` 或 `/run` 写入大文件后观察到 `df` 与 `free` 同时上升，于是分别执行"清理磁盘"与"增加内存"，则会出错；正确动作是先确认写入方，因为容量上限与内存上限是同一份 |
| 回哪一章复核 | 第 4 章体系篇、第 8 章实操篇（`RuntimeDirectory=` 与 tmpfiles） |

### 3.5 缺页与大页

| 项 | 内容 |
| --- | --- |
| 两侧 | 一侧是内存线的缺页处理与算力线的时间消耗，另一侧是持久线的文件映射 |
| 对齐口径 | 因果与传导：首次写入会触发缺页，因此缺页处理时间计入**内核态**；透明大页（THP，Transparent Huge Page）按 2 MiB 映射会放大内存占用，而后台整理（`khugepaged`）会带来停顿 |
| 容易出错 | 若用 `VmPTE` 判断大页是否生效，则会出错，因为判据是 `/proc/meminfo` 的 `AnonHugePages` |
| 回哪一章复核 | 第 4 章原理篇（缺页与写时复制、大页与 NUMA）、第 10 章原理篇 |

### 3.6 内存回收与 IO 等待

| 项 | 内容 |
| --- | --- |
| 两侧 | 一侧是内存线的回收路径，另一侧是持久线的设备队列 |
| 对齐口径 | 因果与传导：内存不足时匿名页换出到 swap、文件页回写，两者的落点都是设备；因此设备繁忙则回收变慢，而回收变慢则分配者进入直接回收，表现为延迟尖刺 |
| 读法 | `pgscan_direct`（`/proc/vmstat`，累计页数，取差值）增长表明发生直接回收；`si`/`so`（`vmstat`，KiB/s）长期非 0 表明换页持续；两者须与 `iostat -x` 的 `await`（毫秒）同看；确认后转向"设备排队还是回收策略" |
| 容易出错 | 若将"内存回收引起的变慢"归因于磁盘慢，或反向当作内存不足而增加内存，则会出错，因为该场景的可观测特征是**两侧同时出现信号** |
| 回哪一章复核 | 第 4 章体系篇（压力线）、第 5 章原理篇、第 10 章原理篇（资源有余量与任务可完成之间的差距） |

## 4. 持久线与其它线的衔接处

### 4.1 inode 与文件描述符

| 项 | 内容 |
| --- | --- |
| 两侧 | 一侧是持久线（inode 是文件系统中的对象编号，目录项是名字），另一侧是进程线（fd 表是进程资源） |
| 对齐口径 | 同一对象：**fd 指向已打开的文件，而不是路径**；因此重命名、删除、轮转都不会改变已打开 fd 所指向的对象 |
| 判据 | 若文件被 `rm` 后空间未释放，则说明仍有进程持有其 fd；`lsof +L1` 列出 link count 小于 1 的已打开文件，而 `/proc/<pid>/fd` 中显示 `(deleted)`；确认后转向"使持有者关闭或重启，而不是继续删除文件" |
| 容易出错 | 日志轮转后新文件为空，是因为应用未重开文件，写入仍指向旧 inode（此时旧文件通常已改名）；这是 `copytruncate` 与 `create`+`postrotate` 两种做法的分界 |
| 回哪一章复核 | 第 5 章原理篇（容量边界）、第 9 章体系篇（一条日志的一生） |

### 4.2 脏页与提交语义

| 项 | 内容 |
| --- | --- |
| 两侧 | 一侧是持久线的写入完整性，另一侧是内存线的 `Dirty`/`Writeback` 计数以及第 11 章的可恢复性 |
| 对齐口径 | 因果与传导：应用认为"已保存"，而内核实际只写入缓存，因此提交点由应用显式调用决定；备份与数据库的 RPO（Recovery Point Objective，恢复点目标）即由提交点确定 |
| 容易出错 | 若备份任务退出码为 0 就认为数据可恢复，则会出错，因为备份成功与可以恢复是两个问题，唯一验收方式是**恢复演练并计时** |
| 回哪一章复核 | 第 5 章原理篇（写入路径与完整性）、第 11 章原理篇（可恢复性的语言） |

### 4.3 快照、COW 与容量

| 项 | 内容 |
| --- | --- |
| 两侧 | 一侧是持久线的容量计量，另一侧是第 11 章的备份体系 |
| 对齐口径 | 同一对象：写时复制（COW，Copy-On-Write）使快照在容量上"看似免费"，但**原始块的改动量会占用快照空间**；一旦改动量超过快照容量，快照即失效 |
| 容易出错 | 若将快照当作备份，则会出错，因为快照与源数据位于同一套存储，源损坏时两者同时损坏；块级快照的语义是无法保证崩溃一致性，相当于拔电源瞬间的状态 |
| 回哪一章复核 | 第 11 章体系篇（一次中断与恢复的一生） |

## 5. 连接线与其它线的衔接处

### 5.1 句柄、端口与连接：三种不可恢复的资源

| 项 | 内容 |
| --- | --- |
| 两侧 | 一侧是进程线的 `RLIMIT_NOFILE`（单进程 fd 上限），另一侧是连接线的源端口范围与监听队列 |
| 对齐口径 | 层次与范围：三种资源各自独立耗尽，且报错形态不同，即 fd 耗尽报 `EMFILE`/`ENFILE`，源端口耗尽报 `EADDRNOTAVAIL`，而队列溢出表现为**客户端偶发超时且服务端无日志** |
| 读法 | `ss -lnt` 的 `Recv-Q` 是当前队列深度，而 `Send-Q` 是该 socket 的队列上限（不是发送队列）；内核判断队列已满使用 `Recv-Q > Send-Q`（允许比上限多排一个），因此读到 `Recv-Q >= Send-Q` 即可判定队列已满；"溢出次数"须看 `nstat` 的 `TcpExtListenOverflows`/`ListenDrops`，该值为累计计数，因此默认输出两次读数的差值、而 `-a` 才输出累计值；这些值须与应用侧 `accept` 速率同看；确认溢出后转向"调整 `backlog`/`somaxconn` 还是提升应用接收速度" |
| 容易出错 | 若将偶发连接失败归因于网络抖动，则会出错，因为主机侧计数器早于抓包给出证据；也不应以 `TIME_WAIT` 作为原因，因为它是主动关闭方的正常状态，Linux 下固定 60 秒，而 `tcp_fin_timeout` 与之无关 |
| 回哪一章复核 | 第 3 章原理篇（资源的边界）、第 6 章原理篇（端口、套接字与多路复用） |

### 5.2 监听队列与 systemd 的 socket 激活

| 项 | 内容 |
| --- | --- |
| 两侧 | 一侧是连接线的监听 socket，另一侧是第 8 章的服务管理 |
| 对齐口径 | 同一对象：socket 激活场景下，**监听 socket 由 systemd 持有**，而服务可能尚未启动；因此"端口在监听"与"服务在运行"可以同时不成立 |
| 容易出错 | 若看到端口在监听就认为服务健康，则会出错，因为还须同时查看 `systemctl list-sockets` 与 `systemctl status` |
| 回哪一章复核 | 第 8 章原理篇（什么算启动完成） |

### 5.3 容器与编排：三个宿主侧机制

| 项 | 内容 |
| --- | --- |
| 两侧 | 一侧是宿主侧的四条线与约束环，另一侧是编排层（容器运行时、Kubernetes）观察到的"一个 Pod / 一个容器" |
| 对齐口径 | 层次与范围：容器不是一台小型机器，而是**三个宿主侧机制的组合**，即 namespace（可见范围）、cgroup（可用量）、根文件系统与联合挂载（文件来源），另加权限约束（capabilities、seccomp、MAC）；因此容器内的问题须先确定由哪个机制造成 |
| 判据与取数位置 | 内存方面，宿主侧读 `/sys/fs/cgroup/<路径>/memory.current`/`memory.max`/`memory.events`，而容器内 `free`/`top` 给出的是整机口径；CPU 方面，读同一路径的 `cpu.max` 与 `cpu.stat` 的 `nr_throttled`；文件系统方面，`/proc/<pid>/mountinfo` 与 `df` 给出的是容器命名空间内的视图；网络方面，用 `nsenter -t <pid> -n ss -lntp` 取得容器内视图，再查宿主侧的 veth、转发规则与 `conntrack` |
| 三类高频现象的宿主侧证据 | **被终止**：读 `memory.events` 的 `oom_kill` 增量，并核对内核日志中的约束来源（`CONSTRAINT_MEMCG`）；**被限流**：读 `cpu.stat` 的 `nr_throttled` 增量，并与 `cpu.max` 的配额对照；**连接失败**：先在容器的网络命名空间内查看监听与路由，再查宿主侧的转发与连接跟踪表 |
| 容易出错 | 若用宿主视图推断容器状态，则会出错，因为宿主能解析、宿主内存充足、宿主端口在监听这三条都推不出容器内的结论；也不应把"容器内使用率不高"当作"未触及配额"，因为配额是按 cgroup 计算的硬上限，而计数只在宿主侧 |
| 云主机上另有三层变量 | 在同一套机制之上，云主机额外引入三层变量：**虚拟化层**（`systemd-detect-virt` 指出实际运行环境；某些实例类型下 DMI 信息为空或不可信，因此硬件字段须现场核对而非照抄）、**云盘与网络层**（云盘有独立的 IOPS 与带宽上限及突发额度，而网络有实例规格绑定的带宽上限与收发包速率）、**平台配额层**（共享型实例的 CPU 积分与基线算力、安全组与网络 ACL）；因此在云上遇到"资源均不繁忙而吞吐上不去"时，应**先排查配额，再排查内核参数** |

### 6.3 口径差异：同一个量在两侧不是同一个数值

| 项 | 内容 |
| --- | --- |
| 两侧 | 一侧是采集端的语义，另一侧是使用端的直觉 |
| 对齐口径 | 这个口径差异落在三种维度上，即单位、时钟与对象，三类高频例子如下：**单位不同**，因为 PSI 的 `avg10/avg60/avg300` 是百分比而 `total` 是微秒，`free` 的 `used` 含可回收缓存而 `MemAvailable` 不含；**对象不同**，因为 `ss -ti` 的 `rtt` 与 `iostat` 的 `await` 单位其实都是毫秒，它们不可比是由于前者是单条连接的往返时间、后者是设备的平均单次请求耗时（含排队）；**时钟不同**，因为墙上时钟用于对账，而单调时钟用于计时 |
| 判据 | 报数必须包含三项，即单位、采集条件（窗口 / 并发 / 工具版本），以及对照项；分位数还要报算法，因为同一组样本的 p95 在不同算法下可以是 20 ms 也可以是 100 ms |
| 容易出错 | 若跨工具、跨机器、跨时间直接比较两个数值，则会出错，因为**缺少采集条件的数字不可比** |

## 常见误解

| 说法 | 事实 |
| --- | --- |
| "跨章问题就是两个知识点都要背" | 跨章问题考察的是衔接处，而不是两侧的知识量；衔接处只有四种对齐口径，即同一对象、单位与时钟、层次与范围、因果与传导 |
| "两侧说法不一致，说明有一处是错的" | 应当先核对口径，再核对机制；因为同一对象在两个视角下的数值本来就该不同（整机与 cgroup、`df` 与 `du`、`%sys` 与中断） |
| "`df` 满了就该删文件" | 先区分三种耗尽（数据块、inode、保留块），再确认是否存在"已删除但仍被持有"的空间占用 |
| "容器就是一台小机器" | 四条线的计量都在宿主侧按 cgroup 记录，而容器内多处接口为只读或独立的命名空间视图 |
| "端口在监听说明服务正常" | socket 激活场景下监听 socket 属于 systemd，而 `start` 成功也只说明 `Type=` 判定通过 |
| "日志能证明影响面" | 日志是抽样与定性的，因此影响面要靠指标；反过来根因也不能只靠指标 |
| "时钟不同步只影响显示" | 跨机时间线推理会整体失效，因此时间同步是复盘结论成立的前提 |
| "文档这么写的，机器一定这么做" | 文档给的是上游默认，而生效值要看现场；`sysctl --system` 与开机路径读的文件集合就不完全一样 |

## 要点自测

- 连接点的成立条件是什么？用它判断"`df` 与 `du` 不一致"算不算一个连接点。
- 四种对齐口径各举一个本库里的例子。
- 为什么 `%sys` 高不能直接推出"系统调用过多"？还须查看哪两个接口文件？
- 用一句话说明 Page Cache 为什么同时出现在内存与存储两套计量中。
- 用宿主 `free` 判断容器内存，错在哪一步？正确的对齐方式是什么？
- 内核日志与 journald 中同一次 OOM 各留下什么证据？哪一项用于定性，哪一项是退出码？
- 时钟、日志、证书、集群这四处为什么共享同一个连接点？
- "改动很小所以可以不走流程"为什么不成立？可回滚的三条判据是什么？
- 具备快照的实验机为什么仍可能无法恢复？缺少的是哪一项保障？
- 若"去掉任何一侧，另一侧结论仍成立"，它是否构成真正的连接点？为什么？
