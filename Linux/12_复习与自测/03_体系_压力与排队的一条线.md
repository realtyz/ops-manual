# 体系：压力与排队的一条线

"资源不足"是现场最常见也最缺乏信息量的结论。四条线各自的不足有不同的物理过程，但外在表现一致：**队列变长**。本篇逐一列出四条线的排队点，使它们共用同一套判据。

## 1. 为何用量不能作为判据

先看四个常见场景：

| 场景 | 表面判断 | 实际发生的过程 |
| --- | --- | --- |
| 整机 CPU 25%，接口延迟翻倍 | "CPU 空闲，与算力无关" | 单核已满负荷，任务在该核的运行队列中排队 |
| `free` 只剩 300 MiB，业务正常 | "内存即将不足" | Page Cache 占主要部分，`MemAvailable` 仍有余量，压力指标接近 0 |
| `%util` 只有 30%，写入变慢 | "磁盘未达瓶颈" | 单请求本身变慢（或队列已排队）；`%util` 衡量的是"有请求发往设备的时间占比"，不反映等待 |
| 带宽仅使用 10%，连接偶发失败 | "网络空闲" | 全连接队列溢出：已完成握手的连接未被 `accept()` |

四个场景具有共同结构：**可直接观察的用量指标（使用率、空闲量、带宽）不是判据，队列长度才是**。原因是这些指标描述的是资源本身是否繁忙，而任务变慢发生在资源之外的等待区。

由此得到第一条纪律：**先定位队列，再评估用量。**

## 2. 四条线各自的排队点

### 2.1 算力线：运行队列与配额

| 项 | 内容 |
| --- | --- |
| 队列位置 | 每个 CPU 的可运行队列；被配额节流的任务则等待下一个周期 |
| 是什么 / 单位 | `vmstat` 的 `r`：可运行与等待运行的任务数（个）；`vmstat` 的 `b`：不可中断睡眠的任务数（个，多半在等 IO）；`/proc/loadavg` 的三个值是 1/5/15 分钟的**可运行 + 不可中断**任务平均数 |
| 判据 | `r` 持续大于实际可调度的核数即表明排队；单核场景看 `mpstat -P ALL` 中**最热核**的余量；配额场景看 `cpu.stat` 的 `nr_throttled` 是否持续增长 |
| 对照项 | `mpstat -P ALL`（最热核）、`pidstat -u -t`（运行主体）、`cpu.stat`（是否被节流）、`/proc/pressure/cpu`（时间被哪一类等待占用） |
| 转向哪一步 | `r` 高且最热核满 → 找那个进程（`pidstat`）；`r` 不高但延迟高 → 转向等待，看 `b`、`wchan` 与 off-CPU 时间 |
| 常见误判 | 用整机使用率排除 CPU；把 `load` 当作使用率（它是任务数，不是百分比） |

`load` 在三种情况下都会升高：可运行任务数量多、任务处于不可中断睡眠（`D` 状态）、以及短时突发。**仅有 `load` 高无法确定原因**，必须结合 `r`/`b` 判断：`r` 高表示算力争抢，`b` 高表示 IO 或锁等待。

### 2.2 内存线：回收队列与压力

| 项 | 内容 |
| --- | --- |
| 队列位置 | 页回收路径：空闲页低于水位线后，分配者需等待回收释放页 |
| 是什么 / 单位 | `/proc/pressure/memory` 的 `some`/`full`：被内存拖住的时间占比；`avg10/avg60/avg300` 是**百分比**，`total` 是**微秒**（累计值，取差值）。`/proc/vmstat` 的 `pgscan_direct`：直接回收扫描的页数（页，累计值，取差值） |
| 判据 | `some` 的 `avg` 长期非 0 表明有任务在等待内存；`total` 的差值增长表明该时间段确实发生停顿；`pgscan_direct` 增长表明分配者被迫自行回收，通常对应延迟尖刺 |
| 对照项 | `MemAvailable`（实际可用量）、`Dirty`/`Writeback`（回收是否需等待回写）、`si`/`so`（是否发生换页）、`memory.events`（是否触及 cgroup 上限）、`iostat -x` 的 `await`（回收落点是否为设备繁忙） |
| 转向哪一步 | `MemAvailable` 低 + PSI 高 → 定位占用方（`smem`/`PSS`/cgroup `memory.current`）；`MemAvailable` 低 + PSI 低 → 缓存属正常占用，不必处置；PSI 高 + `si`/`so` 高 → 检查 swap 与设备 |
| 常见误判 | 用 `free` 的 `used` 或剩余量判断；看到缓存占用高即执行 `drop_caches`（该动作属测量手段，不是治理手段） |

内存线有一项其它线没有的特点：**它的队列是隐式的**。没有字段直接给出"等待内存的任务数"，因此 PSI 具有特殊价值——它把"被拖住的时间"转换为可读的百分比。PSI（Pressure Stall Information，压力停顿信息）的用法是：`avg` 判断趋势，`total` 判断是否确实发生。

### 2.3 持久线：设备队列与提交等待

| 项 | 内容 |
| --- | --- |
| 队列位置 | 块层的请求队列，以及"写入缓存后等待回写完成"与"显式提交等待设备确认"两处等待 |
| 是什么 / 单位 | `iostat -x` 的 `await`：平均等待时间（毫秒，**含排队**）；`aqu-sz`：平均队列长度（个请求）；`r_await`/`w_await` 分开看读与写。`%util`：有请求发往设备的时间占比（百分数） |
| 判据 | `await` 明显高于该设备的基线、且 `aqu-sz` 同时上升 → 排队；`await` 高而 `aqu-sz` 接近 0 → 单请求本身慢（设备、远程存储、或元数据操作）；`Dirty`/`Writeback` 高，说明回写没跟上 |
| 与谁同看 | `/proc/meminfo` 的 `Dirty`/`Writeback`、`pidstat -d`（谁在写）、`/proc/<pid>/io`（读写量）、应用侧是否有周期性任务（备份、日志轮转） |
| 转向哪一步 | 队列偏长 → 确认并发的来源（`pidstat -d`）；单请求慢 → 看设备类型与路径（本地盘、网络存储、虚拟化层）；周期性 → 看计划任务与日志轮转 |
| 常见误判 | 用 `%util` 排除 IO 问题；用单次 `iostat` 输出下结论（它是区间平均值，须同一设备、同一采集窗口才可比较） |

持久线另有一项须单独记住：**"写成功"有三种含义**——写入 Page Cache（内存已接收）、写入设备缓存（设备已接收，掉电会丢失）、提交落盘（`fsync()` 返回）。同样是"写入变慢"，卡在哪一种含义上决定了完全不同的处置方式。

### 2.4 连接线：多个排队点

| 项 | 内容 |
| --- | --- |
| 队列位置 | 半连接队列（收到 SYN 待完成）、全连接队列（握手完成等待 `accept()`）、源端口池、发送缓冲区、收包软中断积压、`conntrack` 表、解析查询 |
| 是什么 / 单位 | `ss -lnt` 的 `Recv-Q`：监听 socket 的当前队列深度（个连接）；`Send-Q`（对 LISTEN 而言）：该 socket 的队列上限（个）；`nstat` 的 `ListenOverflows`/`ListenDrops`：累计溢出次数（次，默认输出两次读数的差值、`-a` 是累计）；`/proc/net/softnet_stat` 第 2 列：每 CPU 的收包丢弃计数（个） |
| 判据 | 队列"满"的判据是 `Recv-Q >= Send-Q`（内核判断满用的是 `>`，即允许比上限多排一个）；发生溢出要看 `ListenOverflows` 的增量（客户端表现为偶发超时，服务端**没有日志**）；`TcpExtTCPTimeWaitOverflow` 等计数器增长说明源端口不够用 |
| 对照项 | `ss -s`（总量）、`ss -tanp state close-wait`（应用未关闭的连接）、应用侧 `accept` 速率与连接池配置、`nf_conntrack_count`/`max` |
| 转向哪一步 | 溢出 → 先提升应用接收速度，再考虑调整队列上限；`CLOSE_WAIT` 堆积 → 修改应用；`TIME_WAIT` 多 → 属正常状态，不必调整 `tcp_fin_timeout`（该参数与之无关） |
| 常见误判 | 将偶发失败归因于网络抖动（主机侧计数器更早给出证据）；把 `TIME_WAIT` 视为故障 |

连接线的排队点最多，因此顺序尤为重要：**先确定是哪一个排队点**，再决定是否需要抓包。抓包是最后手段，计数器是首选证据。

## 3. 四条线的统一判据

四张表可以归纳为一句：

> **资源有余量，是因为没有任务在使用它；变慢，是因为有任务在等待它。**

由此得到三条可直接使用的判断规则：

1. **队列较短、用量较高 → 不构成瓶颈**。缓存占满内存、磁盘大量空闲、带宽只用一半，都不属于问题本身。
2. **队列较长、用量较低 → 构成瓶颈，且容易被误判为"资源空闲"**。单核满负荷、队列溢出、回收抖动均属此类，共同特征是整体指标看似正常。
3. **用量与队列同时偏高 → 已进入传导阶段**。此时应定位最初的变化（配额、变更、流量突增），而不是当前最显著的信号。

三条规则对应的取证动作：

| 现象 | 第一步 | 第二步 | 第三步 |
| --- | --- | --- | --- |
| 延迟高、使用率低 | `vmstat 1` 的 `r`/`b` | `mpstat -P ALL` 的最热核 | `ps -eo stat,wchan` 找等待点 |
| 内存紧、业务正常 | `MemAvailable` | `/proc/pressure/memory` | 决定动不动（多半不动） |
| 写入慢、`%util` 低 | `iostat -x` 的 `await`/`aqu-sz` | `Dirty`/`Writeback` | `pidstat -d` 找写入方 |
| 偶发失败、带宽充足 | `ss -lnt` 的 `Recv-Q`/`Send-Q` | `nstat` 的溢出计数 | 应用侧 `accept` 速率 |

## 4. 传导：线间连锁变化

排队的难点在于它会在四条线之间传导。三条常见传导链：

**配额 → 排队 → 内存放大 → 被杀**

`CPUQuota=` 限制处理速度，请求在应用侧堆积；每个在途请求持有缓冲区与连接，占用随堆积线性增长；内存触及 `memory.max`，内核在 cgroup 内选择进程终止。**起因在算力，表现在内存。** 判据链为：`cpu.stat` 的 `nr_throttled` 增长 → 应用侧队列深度上升 → `memory.current` 上升 → `memory.events` 的 `oom_kill` 增长。

**内存回收 → 设备排队 → 延迟尖刺**

内存紧张时匿名页需换出、文件页需回写，两者的落点都是设备；设备队列变长使回收变慢；分配者在直接回收中等待，表现为无对应业务原因的延迟尖刺。**起因在内存，表现在磁盘。** 判据链为：内存 PSI 的 `some` 上升 → `pgscan_direct` 增长 → `iostat` 的 `await` 上升 → 应用侧延迟 `max`/`p99` 抬升而 `p50` 变化不大。

**回写落后 → 内存计量异常 → 容量显示与实际情况不符**

大量写入时脏页堆积，占用内存且不可回收；同时文件已被删除但 fd 未关闭，空间不释放，`df` 显示 100% 而 `du` 汇总值很小。**起因在写入，表现为容量与内存两套计量同时异常。** 判据链为：`Dirty`/`Writeback` 偏高 → `df` 与 `du` 差值大 → `lsof +L1` 定位持有者。

传导链的使用方式是**由表现反查起因**：观察到最显著的信号（进程被终止、延迟尖刺、磁盘写满）之后，向上追溯使其堆积的上游环节。

## 5. 队列容量：上限所属层级

每个排队点都有容量，容量都有上限，上限位于前四层中的某一层（第 5 层为组织层，不设上限，只决定该层当前是否允许修改）。下表列出四条线的常见上限及其层级，出现"调大后未生效"时按层核对。

| 排队点 | 上限字段 | 所在层级 | 生效值取法 |
| --- | --- | --- | --- |
| 算力 | `cpu.max` | 第 3 层（cgroup） | `cat /sys/fs/cgroup/<path>/cpu.max` |
| 算力 | `CPUQuota=` | 第 2 层（unit） | `systemctl show -p CPUQuotaPerSecUSec` |
| 内存 | `memory.max` / `MemoryMax=` | 第 3 / 2 层 | `cat …/memory.max`、`systemctl show -p MemoryMax` |
| 内存 | `RLIMIT_AS` | 第 1 层（会话） | `ulimit -v`、`/proc/<pid>/limits` |
| 进程数 | `pids.max` / `TasksMax=` | 第 3 / 2 层 | `cat …/pids.max`、`systemctl show -p TasksMax` |
| 句柄 | `RLIMIT_NOFILE` / `LimitNOFILE=` | 第 1 / 2 层 | `ulimit -n`、`systemctl show -p LimitNOFILE`，再与 `/proc/<pid>/limits` 对照 |
| 句柄（整机） | `fs.file-max` | 第 4 层（内核全局） | `sysctl -n fs.file-max` |
| 全连接队列 | `somaxconn` 与应用 `listen()` 的 `backlog` 取小者 | 第 4 层 + 应用参数 | `sysctl -n net.core.somaxconn`、`ss -lnt` 的 `Send-Q` |
| 半连接队列 | `tcp_max_syn_backlog` | 第 4 层 | `sysctl -n net.ipv4.tcp_max_syn_backlog` |
| 源端口 | `ip_local_port_range` | 第 4 层 | `sysctl -n net.ipv4.ip_local_port_range` |
| 连接跟踪 | `nf_conntrack_max` | 第 4 层 | `sysctl -n net.netfilter.nf_conntrack_max` |
| IO 带宽与 IOPS | `io.max` | 第 3 层（cgroup） | `cat …/io.max` |
| 收包积压 | `netdev_max_backlog` | 第 4 层 | `sysctl -n net.core.netdev_max_backlog` |
| 日志容量 | `SystemMaxUse=` 与 `SystemKeepFree=` 取更小者 | 第 4 层（服务自身配置，按前述口径归入整机档） | `systemd-analyze cat-config systemd/journald.conf` |

两条读取纪律：

- **读取生效值，而不是文件名**。"配置中已写入"不构成判据；应以 `sysctl -n`、`systemctl show`、`ss -lnt` 的 `Send-Q`、`cat /sys/fs/cgroup/.../` 为准。
- **修改后确认生效范围**。修改第 2 层只影响此后由 systemd 启动的进程；修改第 3 层须确认目标进程确在该 cgroup 内；修改第 4 层须确认没有其它写入点将其覆盖。

## 6. 容量估算：由观测反推上限

上一节回答"上限位于哪一层"，本节回答"应设为多大"。**两者缺一不可**：只知层级只能改对位置，不了解量级则只是把上限换成另一个估计值。

算法可归纳为一句：**先测当前值与第 99 百分位，再按"峰值 × 安全系数 + 余量"确定上限，最后用同一口径验证**。

| 待配置项 | 反推所依据的观测 | 算式与经验值 | 验证方式 |
| --- | --- | --- | --- |
| 源端口（`ip_local_port_range`） | `ss -s` 的 `timewait`、`nstat -az` 的 `TcpExtTCPTimeWaitOverflow`、每秒新建连接数 | 所需端口数 ≈ 新建连接速率 × 连接处于占用状态的时长。短连接的该时长主要由 `TIME_WAIT` 决定（Linux 固定 60 秒），因此每秒 1000 新建连接的服务至少需要 6 万个可用端口；单机端口总量约 6.4 万个，**此时应采取连接复用，而不是调整端口范围** | 修改后确认 `TcpExtTCPTimeWaitOverflow` 的增量是否归零 |
| 连接跟踪表（`nf_conntrack_max`） | `/proc/sys/net/netfilter/nf_conntrack_count` 的峰值与增长趋势 | 需容纳的条目数 ≈ 并发连接数 + NAT 映射数（同一条流在两个方向各占一项）；按峰值的 2 倍起配，同时须配置 `nf_conntrack_buckets`，否则表大而哈希桶少，查找变慢 | 检查 `nf_conntrack_count` 与 `dmesg` 中是否出现 `nf_conntrack: table full` |
| 全连接队列（`somaxconn` 与应用 `backlog`） | `ss -lnt` 的 `Send-Q`（截断后的实际上限）、`nstat` 的 `ListenOverflows` 增量、应用 `accept` 速率 | 上限须大于"应用最慢阶段的 `accept` 速率 × 峰值到达速率"；调大队列只能吸收突发，长期不足表明应用接收速度偏低 | 溢出计数增量归零，同时确认应用侧并发处理能力足够 |
| 文件句柄（`LimitNOFILE`） | `ls /proc/<pid>/fd \| wc -l` 的峰值、`ss -s` 的连接数、`CLOSE_WAIT` 计数 | 所需句柄 ≈ 并发连接数 + 已打开文件与管道数 + 余量；按峰值 ×1.5～2 配置，**先排除泄漏**（趋势是否单调上升） | 与服务重启前的峰值对比，确认未出现单调增长 |
| journal 容量（`SystemMaxUse=`） | `journalctl --disk-usage`、`du -sh /var/log` 的日增量、保留天数要求 | 默认值不是固定字节，而是 `min(文件系统的 10%, 4 GiB)`，**并与 `SystemKeepFree=`（默认保留 15% 空闲）取更小者**；按"日增量 × 保留天数 × 1.5"核算后，再决定是否显式设定 | 写入日常量级日志后查看 `--disk-usage`，并确认根分区保留 `SystemKeepFree` 的空间 |
| 日志文件与 inode | `df -h` 与 `df -i` 的日增量、`find /var/log -type f \| wc -l`、轮转保留份数 | 所需 inode ≈ 日志文件数 × 保留份数；小文件密集的服务须单独核算 inode，不能只看容量 | `df -i` 的余量按最坏情况留足一个轮转周期 |
| cgroup 内存上限（`MemoryMax=`） | `memory.peak`（历史峰值，字节）、`memory.current` 的中位数、单实例内存 | 上限取"稳定值 ×1.5"与"峰值 ×1.2"之间，既留出尖峰余量，也避免 OOM 成为常态；低于稳定值必然周期性被终止 | 配置后观察一个业务周期，确认 `memory.events` 的 `max` 与 `oom_kill` 不再增长 |
| cgroup CPU 配额（`CPUQuota=`） | `cpu.stat` 的 `usage_usec`、`nr_throttled`、应用吞吐与 p99 | 配额按稳态用量的 1.2～1.5 倍配置；**持续性节流（`nr_throttled` 每个周期均增长）表明配额偏小**，偶发节流属正常削峰 | 配置前后各取一次 `nr_throttled` 增量与 p99 对照 |

**三条纪律优先于算式本身**：

1. **先有观测，再设上限**。没有基线的容量估算等同猜测；本库所有容量结论都必须能指向一个观测字段。
2. **算式给出的是量级，不是精确值**。其用途在于判断"相差一个数量级"还是"相差 20%"：前者需要调整架构，后者才是参数调整。
3. **配置后必须复验**。用同一口径（同一字段、同一窗口）在配置前后各取一次；未复验的参数调整不成立。

## 7. 常见误解

| 说法 | 事实 |
| --- | --- |
| "使用率不高，所以不构成瓶颈" | 使用率描述资源是否繁忙；瓶颈发生在资源之外的等待区。判据是队列，不是使用率 |
| "`load` 高就是 CPU 繁忙" | `load` 统计的是可运行与不可中断睡眠的任务数；`b` 偏高表明在等待 IO 或锁，不属于算力争抢 |
| "`free` 少就是内存不足" | 判据是 `MemAvailable` 与内存 PSI；缓存占用属正常状态 |
| "`%util` 未满说明磁盘未达瓶颈" | `%util` 只表示"有请求发往设备的时间占比"；单请求慢或队列已排队时它可能很低 |
| "带宽未用满，网络就没有问题" | 连接失败多发生在队列（全连接 / 半连接 / `conntrack`），与带宽无关 |
| "偶发超时就是网络抖动" | 先查服务端 `Recv-Q` 与 `ListenOverflows`：溢出时客户端超时而服务端无日志 |
| "`TIME_WAIT` 多须调整 `tcp_fin_timeout`" | `TIME_WAIT` 是主动关闭方的正常状态，Linux 下固定 60 秒；`tcp_fin_timeout` 管理的是 `FIN_WAIT2` |
| "扩容即可解决" | 应先在传导链上定位起因。配额受限导致的排队，扩容无效；回收抖动导致的延迟，增加内存也可能无效 |
| "把上限调大即可" | 生效的是前四层中最紧的那一层；改错层级等于未改，且表面上已完成修改 |
| "看一次 `iostat`/`vmstat` 即可定性" | 这些工具输出的是区间平均值；至少需要两次读数、同一口径、带时间戳 |

## 要点自测

- 为什么使用率、空闲量与带宽都不是判据？判据应当换成什么？
- `vmstat` 的 `r` 与 `b` 分别是什么？各指向哪一类问题？
- 内存 PSI 的 `avg*` 与 `total` 单位分别是什么？为什么必须分清？

- 任举一条传导链，并说明其判据链（每一步查看哪个字段）。
- 一个进程的实际句柄上限由哪几层决定？如何确认生效值？
