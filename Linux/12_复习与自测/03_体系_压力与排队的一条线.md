# 体系：压力与排队的一条线

"资源不足"是现场最常见也最缺乏信息量的结论。四条线各自的不足有不同的物理过程，但它们的外在表现一致，都是队列变长。因此四条线的排队点可以放在同一套判据下比较。

## 1. 为何用量不能作为判据

先看四个常见场景：

| 场景 | 表面判断 | 实际发生的过程 |
| --- | --- | --- |
| 整机 CPU 使用率为 25%，接口延迟翻倍 | "CPU 空闲，与算力无关" | 单个核已经满负荷，因此任务在该核的运行队列中排队 |
| `free` 只剩 300 MiB，业务正常 | "内存即将不足" | Page Cache 占了其中主要部分，而 `MemAvailable` 仍有余量，所以压力指标接近 0 |
| `%util` 只有 30%，写入变慢 | "磁盘未达瓶颈" | 单个请求本身变慢，或者请求已在队列中排队；由于 `%util` 衡量的是"有请求发往设备的时间占比"，因此它不反映等待 |
| 带宽仅使用 10%，连接偶发失败 | "网络空闲" | 全连接队列已经溢出，因此已完成握手的连接没有被 `accept()` 取走 |

四个场景具有共同结构：可直接观察的用量指标（使用率、空闲量、带宽）不是判据，队列长度才是判据。原因是这些指标描述的是资源本身是否繁忙，而任务变慢发生在资源之外的等待区。

由此得到第一条纪律：**先定位队列，再评估用量。**

## 2. 四条线各自的排队点

### 2.1 算力线：运行队列与配额

| 项 | 内容 |
| --- | --- |
| 队列位置 | 任务是排在每个 CPU 的可运行队列上；而被配额节流的任务则等待下一个周期 |
| 是什么 / 单位 | `vmstat` 的 `r` 是可运行与等待运行的任务数，单位是个；`vmstat` 的 `b` 是不可中断睡眠的任务数，单位也是个数，这些任务多半在等 IO；`/proc/loadavg` 的三个值分别是 1 分钟、5 分钟与 15 分钟的**可运行 + 不可中断**任务平均数 |
| 判据 | 若 `r` 持续大于实际可调度的核数，则表明发生了排队；单核场景要去看 `mpstat -P ALL` 中**最热核**的余量；配额场景要看 `cpu.stat` 的 `nr_throttled` 是否持续增长 |
| 对照项 | `mpstat -P ALL` 用来看最热核，`pidstat -u -t` 用来看运行主体，`cpu.stat` 用来看是否被节流，`/proc/pressure/cpu` 用来看时间被哪一类等待占用 |
| 转向哪一步 | 若 `r` 高且最热核已满，则去找那个进程，用 `pidstat`；若 `r` 不高但延迟高，则转向等待，去看 `b`、`wchan` 与 off-CPU 时间 |
| 常见误判 | 误判之一是用整机使用率排除 CPU；误判之二是把 `load` 当作使用率，而它是任务数，不是百分比 |

`load` 在三种情况下都会升高：可运行任务数量多、任务处于不可中断睡眠（`D` 状态）、以及短时突发。**仅有 `load` 高无法确定原因**，因此必须结合 `r` 与 `b` 判断：`r` 高表示算力争抢，而 `b` 高表示 IO 或锁等待。

### 2.2 内存线：回收队列与压力

| 项 | 内容 |
| --- | --- |
| 队列位置 | 队列位于页回收路径上：一旦空闲页低于水位线，分配者就需要等待回收释放页 |
| 是什么 / 单位 | `/proc/pressure/memory` 的 `some` 与 `full` 表示被内存拖住的时间占比，其中 `avg10/avg60/avg300` 的单位是**百分比**，而 `total` 的单位是**微秒**，它是累计值，使用时取差值。`/proc/vmstat` 的 `pgscan_direct` 是直接回收扫描的页数，单位是页，它同样是累计值，使用时也取差值 |
| 判据 | 若 `some` 的 `avg` 长期非 0，则表明有任务在等待内存；若 `total` 的差值在增长，则表明该时间段确实发生了停顿；若 `pgscan_direct` 在增长，则表明分配者被迫自行回收，它通常对应延迟尖刺 |
| 对照项 | 用 `MemAvailable` 看实际可用量，用 `Dirty`/`Writeback` 看回收是否需等待回写，用 `si`/`so` 看是否发生换页，用 `memory.events` 看是否触及 cgroup 上限，用 `iostat -x` 的 `await` 看回收落点是否为设备繁忙 |
| 转向哪一步 | 若 `MemAvailable` 低而 PSI 高，则转去定位占用方，用 `smem`/`PSS`/cgroup `memory.current`；若 `MemAvailable` 低而 PSI 低，则说明缓存属正常占用，因此不必处置；若 PSI 高而 `si`/`so` 高，则转去检查 swap 与设备 |
| 常见误判 | 误判之一是用 `free` 的 `used` 或剩余量判断；误判之二是看到缓存占用高就执行 `drop_caches`，而该动作属测量手段，不是治理手段 |

内存线有一项其它线没有的特点：**它的队列是隐式的**。没有字段直接给出"等待内存的任务数"，因此 PSI 具有特殊价值，因为它把"被拖住的时间"转换为可读的百分比。PSI（Pressure Stall Information，压力停顿信息）的用法是：用 `avg` 判断趋势，用 `total` 判断是否确实发生。

### 2.3 持久线：设备队列与提交等待

| 项 | 内容 |
| --- | --- |
| 队列位置 | 队列位于块层的请求队列上，此外还有两处等待：写入缓存之后等待回写完成，以及显式提交之后等待设备确认 |
| 是什么 / 单位 | `iostat -x` 的 `await` 是平均等待时间，单位是毫秒，它**含排队**；`aqu-sz` 是平均队列长度，单位是个请求；`r_await` 与 `w_await` 则把读与写分开看。`%util` 是有请求发往设备的时间占比，单位是百分数 |
| 判据 | 若 `await` 明显高于该设备的基线、且 `aqu-sz` 同时上升，则说明发生了排队；若 `await` 高而 `aqu-sz` 接近 0，则说明单个请求本身慢，原因可能是设备、远程存储或元数据操作；若 `Dirty`/`Writeback` 高，则说明回写没跟上 |
| 与谁同看 | 它要与 `/proc/meminfo` 的 `Dirty`/`Writeback`、`pidstat -d`（谁在写）、`/proc/<pid>/io`（读写量），以及应用侧是否有周期性任务（备份、日志轮转）一起看 |
| 转向哪一步 | 若队列偏长，则去确认并发的来源，用 `pidstat -d`；若单个请求慢，则去看设备类型与路径（本地盘、网络存储、虚拟化层）；若呈周期性，则去看计划任务与日志轮转 |
| 常见误判 | 误判之一是用 `%util` 排除 IO 问题；误判之二是用单次 `iostat` 输出下结论，而它是区间平均值，因此须同一设备、同一采集窗口才可比较 |

持久线另有一项须单独记住：**"写成功"有三种含义**——写入 Page Cache 表示内存已接收；写入设备缓存表示设备已接收，但掉电会丢失；提交落盘则是 `fsync()` 返回。同样是"写入变慢"，卡在哪一种含义上决定了完全不同的处置方式。

### 2.4 连接线：多个排队点

| 项 | 内容 |
| --- | --- |
| 队列位置 | 排队点包括半连接队列（收到 SYN 待完成）、全连接队列（握手完成等待 `accept()`）、源端口池、发送缓冲区、收包软中断积压、`conntrack` 表与解析查询 |
| 是什么 / 单位 | `ss -lnt` 的 `Recv-Q` 是监听 socket 的当前队列深度，单位是个连接；`Send-Q`（对 LISTEN 而言）是该 socket 的队列上限，单位也是个数；`nstat` 的 `ListenOverflows` 与 `ListenDrops` 是累计溢出次数，单位是次，它默认输出两次读数的差值，而 `-a` 输出的是累计值；`/proc/net/softnet_stat` 第 2 列是每 CPU 的收包丢弃计数，单位是个 |
| 判据 | 队列"满"的判据是 `Recv-Q >= Send-Q`，而内核判断满用的是 `>`，即允许比上限多排一个；若要看是否发生溢出，则要看 `ListenOverflows` 的增量，此时客户端表现为偶发超时，而服务端**没有日志**；若 `TcpExtTCPTimeWaitOverflow` 等计数器增长，则说明源端口不够用 |
| 对照项 | `ss -s` 用来看总量，`ss -tanp state close-wait` 用来看应用未关闭的连接，应用侧的 `accept` 速率与连接池配置要一并核对，`nf_conntrack_count`/`max` 用来判断连接跟踪表是否接近上限 |
| 转向哪一步 | 若发生溢出，则先提升应用接收速度，再考虑调整队列上限；若 `CLOSE_WAIT` 堆积，则要修改应用；若 `TIME_WAIT` 多，则属正常状态，不必调整 `tcp_fin_timeout`，因为该参数与之无关 |
| 常见误判 | 误判之一是将偶发失败归因于网络抖动，而主机侧计数器更早给出证据；误判之二是把 `TIME_WAIT` 视为故障 |

连接线的排队点最多，因此顺序尤为重要：**先确定是哪一个排队点**，再决定是否需要抓包。抓包是最后手段，而计数器是首选证据。

## 3. 四条线的统一判据

四张表可以归纳为一句判断：资源有余量，是因为没有任务在使用它；变慢，是因为有任务在等待它。

由此得到三条可直接使用的判断规则：

1. **队列较短而用量较高时，它不构成瓶颈**。缓存占用了大部分内存、磁盘大量空闲、带宽只用一半，都不属于问题本身。
2. **队列较长而用量较低时，它构成瓶颈，且容易被误判为"资源空闲"**。单核满负荷、队列溢出、回收抖动均属此类，它们的共同特征是整体指标看似正常。
3. **用量与队列同时偏高时，已经进入传导阶段**。此时应定位最初的变化（配额、变更、流量突增），而不是当前最显著的信号。

三条规则对应的取证动作：

| 现象 | 第一步 | 第二步 | 第三步 |
| --- | --- | --- | --- |
| 延迟高、使用率低 | 先读 `vmstat 1` 的 `r`/`b` | 再读 `mpstat -P ALL` 的最热核 | 然后用 `ps -eo stat,wchan` 找出进程正在等待的事件（`wchan`） |
| 内存紧、业务正常 | 先读 `MemAvailable` | 再读 `/proc/pressure/memory` | 然后决定是否处置，而多数情况下不需要采取动作 |
| 写入慢、`%util` 低 | 先读 `iostat -x` 的 `await`/`aqu-sz` | 再读 `Dirty`/`Writeback` | 然后用 `pidstat -d` 找出写入方 |
| 偶发失败、带宽充足 | 先读 `ss -lnt` 的 `Recv-Q`/`Send-Q` | 再读 `nstat` 的溢出计数 | 然后去查应用侧的 `accept` 速率 |

## 4. 传导：线间连锁变化

排队的难点在于它会在四条线之间传导。三条常见传导链如下。

**第一条链：配额受限使请求排队，排队放大内存占用，最终进程被终止。**

由于 `CPUQuota=` 限制了处理速度，请求因此在应用侧堆积；由于每个在途请求都持有缓冲区与连接，所以内存占用随堆积线性增长；一旦内存触及 `memory.max`，内核就在 cgroup 内选择进程终止。**起因在算力，表现在内存。** 判据链为：若 `cpu.stat` 的 `nr_throttled` 增长，则应用侧队列深度随之上升；队列深度上升之后，`memory.current` 上升；一旦 `memory.current` 触及 `memory.max`，`memory.events` 的 `oom_kill` 就开始增长。

**第二条链：内存回收引起设备排队，设备排队表现为延迟尖刺。**

由于内存紧张时匿名页需换出、文件页需回写，而两者的落点都是设备，所以设备队列变长并使回收变慢；分配者因此需要在直接回收中等待，表现为无对应业务原因的延迟尖刺。**起因在内存，表现在磁盘。** 判据链为：若内存 PSI 的 `some` 上升，则 `pgscan_direct` 随之增长；`pgscan_direct` 增长使 `iostat` 的 `await` 上升；最终应用侧延迟的 `max`/`p99` 抬升，而 `p50` 变化不大。

**第三条链：回写落后引起内存计量异常，容量显示与实际情况不符。**

由于大量写入时脏页堆积，这些脏页因此占用内存且不可回收；同时，若文件已被删除但 fd 未关闭，则空间不释放，于是 `df` 显示 100% 而 `du` 汇总值很小。**起因在写入，表现为容量与内存两套计量同时异常。** 判据链为：若 `Dirty`/`Writeback` 偏高，则 `df` 与 `du` 的差值变大；差值变大之后，用 `lsof +L1` 定位持有者。

传导链的使用方式是**由表现反查起因**：观察到最显著的信号（进程被终止、延迟尖刺、磁盘写满）之后，向上追溯使其堆积的上游环节。

## 5. 队列容量：上限所属层级

每个排队点都有容量，容量都有上限，上限位于前四层中的某一层（第 5 层为组织层，它不设上限，只决定该层当前是否允许修改）。下表列出四条线的常见上限及其层级，一旦出现"调大后未生效"，就按层核对。

| 排队点 | 上限字段 | 所在层级 | 生效值取法 |
| --- | --- | --- | --- |
| 算力 | `cpu.max` | 它由第 3 层即 cgroup 施加 | 生效值由 `cat /sys/fs/cgroup/<path>/cpu.max` 读出 |
| 算力 | `CPUQuota=` | 它由第 2 层即 unit 施加 | 生效值由 `systemctl show -p CPUQuotaPerSecUSec` 读出 |
| 内存 | `memory.max` / `MemoryMax=` | 它由第 3 层与第 2 层分别施加 | 生效值分别由 `cat …/memory.max` 与 `systemctl show -p MemoryMax` 读出 |
| 内存 | `RLIMIT_AS` | 它由第 1 层即会话施加 | 生效值由 `ulimit -v` 与 `/proc/<pid>/limits` 读出 |
| 进程数 | `pids.max` / `TasksMax=` | 它由第 3 层与第 2 层分别施加 | 生效值分别由 `cat …/pids.max` 与 `systemctl show -p TasksMax` 读出 |
| 句柄 | `RLIMIT_NOFILE` / `LimitNOFILE=` | 它由第 1 层与第 2 层分别施加 | 生效值由 `ulimit -n` 与 `systemctl show -p LimitNOFILE` 读出，再与 `/proc/<pid>/limits` 对照 |
| 句柄（整机） | `fs.file-max` | 它由第 4 层即内核全局施加 | 生效值由 `sysctl -n fs.file-max` 读出 |
| 全连接队列 | `somaxconn` 与应用 `listen()` 的 `backlog` 取小者 | 它由第 4 层与应用侧参数共同决定，二者取较小者 | 生效值由 `sysctl -n net.core.somaxconn` 与 `ss -lnt` 的 `Send-Q` 读出 |
| 半连接队列 | `tcp_max_syn_backlog` | 它由第 4 层施加 | 生效值由 `sysctl -n net.ipv4.tcp_max_syn_backlog` 读出 |
| 源端口 | `ip_local_port_range` | 它由第 4 层施加 | 生效值由 `sysctl -n net.ipv4.ip_local_port_range` 读出 |
| 连接跟踪 | `nf_conntrack_max` | 它由第 4 层施加 | 生效值由 `sysctl -n net.netfilter.nf_conntrack_max` 读出 |
| IO 带宽与 IOPS | `io.max` | 它由第 3 层即 cgroup 施加 | 生效值由 `cat …/io.max` 读出 |
| 收包积压 | `netdev_max_backlog` | 它由第 4 层施加 | 生效值由 `sysctl -n net.core.netdev_max_backlog` 读出 |
| 日志容量 | `SystemMaxUse=` 与 `SystemKeepFree=` 取更小者 | 它位于第 4 层，即服务自身配置，按前述口径归入整机档 | 生效值由 `systemd-analyze cat-config systemd/journald.conf` 读出 |

两条读取纪律：

- **读取生效值，而不是文件名**。"配置中已写入"不构成判据；应以 `sysctl -n`、`systemctl show`、`ss -lnt` 的 `Send-Q`、`cat /sys/fs/cgroup/.../` 为准。
- **修改后确认生效范围**。修改第 2 层只影响此后由 systemd 启动的进程；修改第 3 层须确认目标进程确在该 cgroup 内；修改第 4 层须确认没有其它写入点将其覆盖。

## 6. 容量估算：由观测反推上限

上一节回答"上限位于哪一层"，本节回答"应设为多大"。**两者缺一不可**：只知层级只能改对位置，而不了解量级则只是把上限换成另一个估计值。

算法可归纳为一句：**先测当前值与第 99 百分位，再按"峰值 × 安全系数 + 余量"确定上限，最后用同一口径验证**。

| 待配置项 | 反推所依据的观测 | 算式与经验值 | 验证方式 |
| --- | --- | --- | --- |
| 源端口（`ip_local_port_range`） | 要读 `ss -s` 的 `timewait`、`nstat -az` 的 `TcpExtTCPTimeWaitOverflow` 与每秒新建连接数 | 所需端口数约等于新建连接速率乘以连接处于占用状态的时长。短连接的该时长主要由 `TIME_WAIT` 决定（Linux 下固定 60 秒），因此每秒 1000 新建连接的服务至少需要 6 万个可用端口；单机端口总量约 6.4 万个，**此时应采取连接复用，而不是调整端口范围** | 修改后确认 `TcpExtTCPTimeWaitOverflow` 的增量是否归零 |
| 连接跟踪表（`nf_conntrack_max`） | 要读 `/proc/sys/net/netfilter/nf_conntrack_count` 的峰值与增长趋势 | 需容纳的条目数约等于并发连接数加 NAT 映射数（同一条流在两个方向各占一项）；按峰值的 2 倍起配，同时须配置 `nf_conntrack_buckets`，否则表大而哈希桶少，查找变慢 | 检查 `nf_conntrack_count` 与 `dmesg` 中是否出现 `nf_conntrack: table full` |
| 全连接队列（`somaxconn` 与应用 `backlog`） | 要读 `ss -lnt` 的 `Send-Q`（截断后的实际上限）、`nstat` 的 `ListenOverflows` 增量与应用 `accept` 速率 | 上限须大于"应用最慢阶段的 `accept` 速率 × 峰值到达速率"；调大队列只能吸收突发，而长期不足表明应用接收速度偏低 | 验证时要确认溢出计数的增量归零，同时确认应用侧的并发处理能力足够 |
| 文件句柄（`LimitNOFILE`） | 要读 `ls /proc/<pid>/fd \| wc -l` 的峰值、`ss -s` 的连接数与 `CLOSE_WAIT` 计数 | 所需句柄约等于并发连接数加已打开文件与管道数再加余量；按峰值 ×1.5～2 配置，**先排除泄漏**（看趋势是否单调上升） | 与服务重启前的峰值对比，确认未出现单调增长 |
| journal 容量（`SystemMaxUse=`） | 要读 `journalctl --disk-usage`、`du -sh /var/log` 的日增量与保留天数要求 | 默认值不是固定字节，而是 `min(文件系统的 10%, 4 GiB)`，**并与 `SystemKeepFree=`（默认保留 15% 空闲）取更小者**；按"日增量 × 保留天数 × 1.5"核算后，再决定是否显式设定 | 写入日常量级日志后查看 `--disk-usage`，并确认根分区保留了 `SystemKeepFree` 要求的空间 |
| 日志文件与 inode | 要读 `df -h` 与 `df -i` 的日增量、`find /var/log -type f \| wc -l` 与轮转保留份数 | 所需 inode 约等于日志文件数乘以保留份数；小文件密集的服务须单独核算 inode，不能只看容量 | `df -i` 的余量要按最坏情况留足一个轮转周期 |
| cgroup 内存上限（`MemoryMax=`） | 要读 `memory.peak`（历史峰值，单位是字节）、`memory.current` 的中位数与单实例内存 | 上限取"稳定值 ×1.5"与"峰值 ×1.2"之间，这样既留出尖峰余量，也避免 OOM 成为常态；若低于稳定值，则必然周期性被终止 | 配置后观察一个业务周期，确认 `memory.events` 的 `max` 与 `oom_kill` 不再增长 |
| cgroup CPU 配额（`CPUQuota=`） | 要读 `cpu.stat` 的 `usage_usec`、`nr_throttled` 与应用吞吐和 p99 | 配额按稳态用量的 1.2～1.5 倍配置；**持续性节流（`nr_throttled` 每个周期均增长）表明配额偏小**，而偶发节流属正常削峰 | 配置前后各取一次 `nr_throttled` 增量与 p99 对照 |

**三条纪律优先于算式本身**：

1. **先有观测，再设上限**。没有基线的容量估算等同猜测；本库所有容量结论都必须能指向一个观测字段。
2. **算式给出的是量级，不是精确值**。它的用途在于判断"相差一个数量级"还是"相差 20%"：前者需要调整架构，而后者才是参数调整。
3. **配置后必须复验**。用同一口径（同一字段、同一窗口）在配置前后各取一次；未复验的参数调整不成立。

## 7. 常见误解

| 说法 | 事实 |
| --- | --- |
| "使用率不高，所以不构成瓶颈" | 使用率描述的是资源是否繁忙，而瓶颈发生在资源之外的等待区，因此判据是队列，不是使用率 |
| "`load` 高就是 CPU 繁忙" | `load` 统计的是可运行与不可中断睡眠的任务数，因此若 `b` 偏高，则表明在等待 IO 或锁，不属于算力争抢 |
| "`free` 少就是内存不足" | 判据是 `MemAvailable` 与内存 PSI，而缓存占用属正常状态 |
| "`%util` 未满说明磁盘未达瓶颈" | `%util` 只表示"有请求发往设备的时间占比"，因此当单个请求慢或队列已排队时，它可能很低 |
| "带宽未用满，网络就没有问题" | 连接失败多发生在队列（全连接、半连接或 `conntrack`），因此与带宽无关 |
| "偶发超时就是网络抖动" | 应先查服务端 `Recv-Q` 与 `ListenOverflows`：一旦发生溢出，客户端就超时，而服务端没有日志 |
| "`TIME_WAIT` 多须调整 `tcp_fin_timeout`" | `TIME_WAIT` 是主动关闭方的正常状态，Linux 下固定 60 秒，而 `tcp_fin_timeout` 管理的是 `FIN_WAIT2` |
| "扩容即可解决" | 应先在传导链上定位起因。配额受限导致的排队，扩容无效；回收抖动导致的延迟，增加内存也可能无效 |
| "把上限调大即可" | 生效的是前四层中最紧的那一层，因此改错层级等于未改，且表面上已完成修改 |
| "看一次 `iostat`/`vmstat` 即可定性" | 这些工具输出的是区间平均值，因此至少需要两次读数、同一口径、带时间戳 |

## 要点自测

- 为什么使用率、空闲量与带宽都不是判据？判据应当换成什么？
- `vmstat` 的 `r` 与 `b` 分别是什么？各指向哪一类问题？
- 内存 PSI 的 `avg*` 与 `total` 单位分别是什么？为什么必须分清？
- `iostat -x` 的 `await` 与 `%util` 各回答什么问题？哪一组组合表明队列排队，哪一组表明单请求变慢？
- `ss -lnt` 的 `Recv-Q >= Send-Q` 说明什么？为什么此时服务端日志通常为空？
- "写成功"有哪三种含义？分别由哪一层保证？
- 任举一条传导链，并说明其判据链（每一步查看哪个字段）。
- 一个进程的实际句柄上限由哪几层决定？如何确认生效值？
- 为什么修改第 2 层后须重启服务才生效，而修改第 3 层不需要？
- 源端口上限应设为多大？依据哪两项观测反推？为什么算出需要 6 万个端口时，应采取连接复用而不是调整端口范围？
- journal 容量的默认值是什么？为什么它不是固定字节数？
- "先有观测再设上限"与"算式给出的是量级不是精确值"这两条纪律各防止哪类错误？
