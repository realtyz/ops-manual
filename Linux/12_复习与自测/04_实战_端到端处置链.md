# 实战：端到端处置链

前面三篇给的是模型与连接点。模型要能用，得在真机上被故障撞过一次——不是背过故障的表现，而是**亲手让它坏、亲手读它的指纹、亲手修回去并计时**。

本篇给出这条演练链：顺序、每个实验在验哪条线、观测指纹的读法、恢复怎么复核。全部实验的实测数值集中在附录《高频误判对照表》与各阶段原文，本篇不复述数字。

## 1. 两个前提与三条纪律

演练的第一风险不是做错，是**做坏之后回不来**。

**前提一：机器合格**。最低要求三条同时成立——能快照、能进控制台（或带外）、与生产隔离。缺第三条就不要做，缺第二条则所有"会断掉入口"的实验必须划掉。有没有快照只解决存储一致性，解决不了"进不去"。

**前提二：破坏性操作之前留基线**。没有对比就不叫验证。

**三条纪律**：

| 纪律 | 具体要求 | 违反的后果 |
| --- | --- | --- |
| **隔离** | 只用独立挂载点、独立目录（如 `/var/tmp/` 下的自建目录）、独立 unit、独立网络命名空间；不碰根分区、不碰系统自带关键 unit | 故障波及正常系统，实验变成事故 |
| **上限** | 每个实验写明上限：镜像大小、内存上限、配额、时长、丢包率 | 压力类实验把共享机器拖垮 |
| **清理复核** | 跑完确认：无残留进程、无残留目录、无残留 loop 设备与命名空间、无残留监听、参数与容量回到基线 | 残留污染后续实验，观测指纹互相污染 |

**每次实验前后各采集一次基线**，这是"有对照才构成验证"的最小实现。基线五项：版本、容量、压力、连接、日志用量。

```bash
# 验证：实验前采集五项基线（只读，生产机上也可以执行）
cat /etc/os-release | head -2; uname -r; systemctl --version | head -1; stat -fc %T /sys/fs/cgroup
df -h /; df -i /
free -m | head -2; cat /proc/pressure/memory
ss -lnt; ss -s | head -3
journalctl --disk-usage
```

```bash
# 验证：实验全部结束后的清理复核（无残留进程、目录、loop 设备、命名空间与监听）
pgrep -af 'spin|lab'                 # 无残留实验进程
ls -ld /var/tmp/review-lab           # 临时目录已清理
losetup -a; ip netns list            # 无残留 loop 设备与命名空间
ss -lntup                            # 无残留监听
free -m | head -2; df -h / | tail -1 # 内存与容量回到基线
```

## 2. 演练链：各实验的检验目标

顺序并非任意：**先做只读与可回滚的实验，再做可能损坏机器、只能依赖快照或控制台恢复的实验**。若首轮即损坏机器，后续实验将无法进行。

| 顺序 | 实验 | 涉及的资源线 | 触发的连接点 | 判据字段 | 是否需要 root |
| --- | --- | --- | --- | --- | --- |
| 1 | 只读基线采集（不属于故障注入） | 观察面 | 全部（建立可比较的基准） | 五项基线的全部字段 | 不需要 |
| 2 | 打满一个独立文件系统 | 持久（容量） | inode 与 fd · Page Cache | `df -h` 的 `Use%` 与写入的 errno | 需要（建 loop 镜像） |
| 3 | 耗尽 inode | 持久（容量） | inode 与 fd | `df -i` 的 `IUse%` 对 `df -h` | 需要 |
| 4 | 只读文件系统（loop 等价复现） | 持久（挂载状态） | 快照与实验边界 | `findmnt` 的 `OPTIONS` 列 | 需要 |
| 5 | cgroup 内存 OOM | 内存 + 约束环第 3 层 | cgroup · 内核日志与用户态日志 | `memory.events` 的 `oom_kill`、`memory.peak` | 需要（系统级 scope） |
| 6 | CPU 配额限流 | 算力 + 约束环第 3 层 | 配额与排队 | `cpu.stat` 的 `nr_throttled`、`throttled_usec` | 需要 |
| 7 | 句柄耗尽 | 连接 + 约束环第 1 层 | 句柄 · 端口 · 队列 | `/proc/<pid>/limits` 与 `EMFILE` 报错 | 不需要（只影响子 shell） |
| 8 | 单核打满 | 算力（单核） | 内核态时间与软中断 | `mpstat -P ALL` 的逐核行、`vmstat` 的 `r` | 不需要 |
| 9 | 日志轮转写错 | 持久 + 观察面 | inode 与 fd | 新旧文件的 inode 与行数 | 不需要 |
| 10 | 网络丢包与延迟注入 | 连接 | 中断与网卡队列 · 口径差异 | `ss -ti` 的 `rtt`/`minrtt`/`retrans`、`tc -s qdisc` | 需要（`ip netns`） |
| 11 | 服务起不来（改坏自建 unit） | 约束环第 2 层 | PID 1 · 监听队列与 socket 激活 | `systemctl status` 的退出码、`Result` | 需要 |
| 12 | 写坏 `/etc/fstab` 后重启 | 约束环第 2 层 | 快照与实验边界 | 启动进入 `emergency mode`、`journalctl -xb` | 需要 + **控制台** |
| 13 | 真正的根分区只读 / 内核 panic | 持久 + 引导 | 快照与实验边界 · 版本与默认值 | `findmnt /` 的 `ro`、`journalctl -b -1 -k` | 需要 + **控制台** |

**未实测的登记**：第 12、13 项需要独立控制台或带外入口，在没有第二条通道的实验机上做坏了无法自救，必须显式标为未实测，并写清补做方式（换一台可快照且有控制台的机器，一次只补一条）。同时要写清**为什么**未实测——例如 `kdump` 处于 `inactive`、`kernel.sysrq` 的值不含 panic 位、`/var/crash/` 为空时，panic 类实验连前提都不满足。

## 3. 观测指纹的读取方法

演练里最关键的不是"故障发生了"，而是**这个故障在哪些字段上留下什么形态**。以下五个指纹覆盖四条线，每个都按"是什么 / 单位 / 判据 / 与谁同看 / 转向哪一步"给全。

### 3.1 容量耗尽：`df -h` 满而 `df -i` 不满

- **是什么**：`df -h` 给的是数据块用量（`Use%`），`df -i` 给的是 inode 用量（`IUse%`）。
- **单位**：百分数；`df -h` 的空间是 GiB/MiB，`df -i` 的数量是"个"。
- **判据**：两者可以独立耗尽。空间满时写入报 `ENOSPC`（No space left on device），inode 满时报的也是同一句 `ENOSPC`——**报错文本一样，成因不同**，必须靠两个 `df` 区分。
- **与谁同看**：`du -xsh`（谁占的）、`lsof +L1`（有没有已删除但仍被持有的文件）、ext4 的保留块（默认给 root 留 5%，普通用户写不进去时 root 可能还能写）。
- **转向哪一步**：`df -h` 满而 `du` 加起来很少 → 查持有者与保留块；`df -i` 满 → 查小文件目录；两者都满 → 先按业务重要性清理，不要 `rm -rf` 日志目录。

只读故障还有一处判据要现场取：文件系统在遇到错误后是否自动转为只读，由**超级块中的设置**决定，并非所有 ext4 文件系统一致。`man 5 ext4` 写明 `errors=` 的默认值存放在超级块、可用 `tune2fs` 修改；取法就一句 `tune2fs -l <设备> | grep -i 'Errors behavior'`（本库实验机读到 `Continue`，即不会自动转只读）。因此在其它机器上遇到根分区只读时，须先确认该机器的这一取值，再判断属于内核转入保护还是人为挂载为只读。

### 3.2 内存上限：`memory.events` 的 `oom_kill`

- **是什么**：cgroup v2 的事件计数文件，记录该组内各类"撞上限"事件。
- **单位**：次数（累计值）。要取两次读数的**差值**才知道"这一段时间内有没有发生"。
- **判据**：`oom_kill` 非 0（增量）是该 cgroup 内真的杀过进程的证据；配合 `memory.peak`（该组内存历史峰值，字节）比对 `memory.max`（硬上限，字节）。
- **与谁同看**：内核日志里的 OOM 记录（含约束来源，例如 `CONSTRAINT_MEMCG` 表示是 cgroup 上限而非整机水位）、进程退出码（137 = 128 + 9，只说明收到 `SIGKILL`）、宿主侧 `free`（宿主可能仍较空闲）。
- **转向哪一步**：确认是 cgroup 级 OOM → 查上限配在哪一层、峰值多少、谁在涨；**不要**只看退出码 137 就写 OOM。

### 3.3 算力配额：`cpu.stat` 的 `nr_throttled`

- **是什么**：cgroup v2 的 CPU 统计，记录周期数与被节流的周期数。
- **单位**：`nr_periods`/`nr_throttled` 是**周期数**（次，累计值），`throttled_usec` 是**微秒**（累计值）。
- **判据**：`nr_throttled` 在两次读数之间持续增长，同时 `throttled_usec` 同步增长，说明这一段时间一直被配额受限；单独看 `nr_throttled` 非 0 只说明"历史上发生过"。
- **与谁同看**：`cpu.max`（配额与周期，形如 `20000 100000` 表示每 100 ms 最多用 20 ms）、应用侧吞吐与延迟、`/proc/pressure/cpu`。
- **转向哪一步**：确认被节流 → 先判断是配额太小还是任务太多（看应用侧在途请求数）；**不要**在容器里加线程。

### 3.4 句柄：`/proc/<pid>/limits` 与 `EMFILE`

- **是什么**：`limits` 给出该进程各资源的软上限与硬上限；`Max open files` 就是 `RLIMIT_NOFILE`。
- **单位**：个数。
- **判据**：进程报 `Too many open files`（`EMFILE`）时，看这个文件里的软上限与实际打开的 fd 数（`ls /proc/<pid>/fd | wc -l`）是否接近；注意软上限可以小于硬上限，非 root 只能提到硬上限。
- **与谁同看**：`ss -s` 的 `timewait`、源端口范围（这两者会与"连接数上限"混淆）、`systemctl show -p LimitNOFILE`（如果这个进程由 systemd 启动，实际值可能来自 unit 而不是登录会话）。
- **转向哪一步**：确认是单进程 fd 耗尽 → 查是不是连接泄漏（`CLOSE_WAIT` 堆积常见于此）；**不要**在生产机上为了"验证"改全局 `fs.file-max`。

### 3.5 网络：`ss -ti` 的 `rtt`/`minrtt` 与 `retrans`

- **是什么**：单条 TCP 连接的内部状态。
- **单位**：`rtt`/`minrtt` 是**毫秒**（`man 8 ss` 原文写明），`retrans` 是该连接的累计重传次数（次）。
- **判据**：`rtt` 明显高于 `minrtt` 表明路径上存在排队（注入延迟、链路拥塞、中间设备缓冲）；`retrans` 增长表明丢包。注入延迟后 `rtt` 抬升而 `retrans` 不变；注入丢包后 `retrans` 才增长——**两个信号须分别判断**。
- **与谁同看**：`nstat` 的重传计数（累计值，默认输出两次读数之差）、`/proc/net/softnet_stat` 的每 CPU 丢弃、`tc -s qdisc show` 的 qdisc 计数（注入侧的证据）。
- **转向哪一步**：延迟高而 `retrans` 低 → 找路径上的排队；`retrans` 高 → 找丢包点（本机驱动、路径、对端）；出现 `app_limited` → 瓶颈在应用，不要在网络上找。

## 4. 演练记录模板

```text
演练 N：<故障名>                      日期：____  机器：____
实验前基线：<版本 / 容量 / 压力 / 连接 / 日志用量>
注入动作：<命令与参数>                启动时刻：____
观测指纹：<命令 → 输出要点 + 数值>
判定过程：<分层 → 结论 → 排除的其它可能>
恢复动作：<命令>                      完成时刻：____
恢复耗时：____ 秒（对照业务能容忍的中断时间：____ 秒）
验收：<命令复验 + 业务探活 + 观察窗口>
清理复核：无残留进程 ☐  无残留目录 ☐  无残留 loop 与命名空间 ☐  参数与容量回到基线 ☐
未实测 / 未解释的现象：____  （原因：____  补做方式：____）
```

模板里三行不能省：

- **观测指纹**：省了这次演练就只证明"我操作过"，不产生可迁移的知识；
- **恢复耗时**：不记时长只能证明"能做到"，不能证明"够快"；它是对齐业务容忍中断时间的唯一证据；
- **未实测与未解释**：照实写。用一次观察当结论，比不写更危险。

## 5. 演练结果与岗位要求的对应

演练链的目标不是完成全部十三项（其中第 1 项为只读基线采集，不属于故障），而是证明三件事：

1. **能够识别**。面对一个现场，能够指出它属于哪条线、受阻于哪个排队点，而不是从命令清单中逐条尝试。
2. **能够恢复**。每个实验都记录了恢复动作与耗时，"可以恢复"有量化依据，而不是主观印象。
3. **能够界定范围**。区分实际执行过的、转引自其它阶段的、以及未实测的三类内容，并使用三个不同的表述。

这三件事的验收方式见下一篇：将演练过的内容置于连续追问之下，检验是否仍能成立。

## 常见误解

| 说法 | 事实 |
| --- | --- |
| "演练就是把故障造出来看看" | 造故障只是动作；可迁移的部分是"指纹 + 判定过程 + 恢复耗时"三样 |
| "有快照就什么都能做" | 快照保存储一致性，保不住入口。会断掉网络或挂载配置的实验，没有控制台就不要做 |
| "实验机是虚拟机，处理坏了重建就行" | 重建成本掩盖了"没有第二条通道"这个真实约束；生产上出事时没有重建这个选项 |
| "恢复耗时不用记，反正能恢复" | 不记时长无法对齐业务容忍的中断时间，也无法证明预案现实 |
| "报错一样就是同一个故障" | 空间耗尽与 inode 耗尽的报错文本同为 `ENOSPC`，成因与处置完全不同 |
| "重传率就是丢包率" | 一个是本机 TCP 的累计重传次数，一个是链路侧的丢包比例，注入丢包时两者会同时变化但不是一个量 |
| "未实测的部分不用写" | 省略标注等同于将其视为实测结论；阅读者（包括数月后的自己）将无法分辨 |

## 要点自测

- 演练的三条纪律是什么？跑完复核哪五项？
- 为什么顺序上要先做可回滚的实验？举一个"做坏了就回不来"的例子。
- 空问耗尽与 inode 耗尽的报错文本相同，怎么在两秒内区分？
- `memory.events` 的 `oom_kill` 为什么要取差值？它与进程退出码 137 各证明什么？
- `nr_throttled` 非 0 与"这一段时间一直被节流"是不是一回事？判据怎么下？
- 一个进程的 fd 上限可能来自哪三个地方？怎么确认它现在生效的是哪一个？
- `ss -ti` 中 `rtt` 抬升与 `retrans` 增长分别指向什么？为什么不能混为一谈？
- 演练记录里哪三行不能省？各自防止什么损失？
- 为什么"有快照"仍不足以支撑写坏 `fstab` 这类实验？
- 分别说明"能够识别、能够恢复、能够界定范围"这三项的验收方式。
