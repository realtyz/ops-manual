# 实战：端到端处置链

前面三篇给出的是模型与连接点，而模型只有经过一次真实的端到端处置才能被检验。验证的方式不是记住故障的表现，而是**亲手注入故障、亲手读取观测指纹、亲手恢复并计时**。

这条演练链的顺序、每个实验所检验的资源线、观测指纹的读法以及恢复的复核方式，都在下面逐项给出；全部实验的实测数值集中在附录《高频误判对照表》与各阶段原文，因此本篇不复述数字。

## 1. 两个前提与三条纪律

演练的第一风险不是做错，而是**做坏之后无法回到原状态**。

**前提一：机器合格**。最低要求是三条同时成立：该机器能快照、能进控制台（或带外管理入口）、与生产环境隔离。若缺少第三条，则不要开展演练；若缺少第二条，则所有"会断掉入口"的实验都必须划掉。因为快照只解决存储一致性，所以它解决不了"进不去"的问题。

**前提二：破坏性操作之前先留基线**。因为没有对比就无法构成验证。

**三条纪律**：

| 纪律 | 具体要求 | 违反的后果 |
| --- | --- | --- |
| **隔离** | 演练只使用独立的挂载点、独立目录（例如 `/var/tmp/` 下的自建目录）、独立 unit 与独立网络命名空间；同时不触碰根分区与系统自带的关键 unit | 一旦隔离不成立，故障就会波及正常系统，因此实验也就变成了事故 |
| **上限** | 每个实验都要写明上限，其中包括镜像大小、内存上限、配额、时长与丢包率 | 若上限缺失，压力类实验就会把共享机器拖垮 |
| **清理复核** | 实验跑完之后要确认：没有残留进程、没有残留目录、没有残留 loop 设备与命名空间、没有残留监听，并且参数与容量都回到基线 | 若清理不彻底，残留就会污染后续实验，因此各次实验的观测指纹也会互相污染 |

**每次实验前后各采集一次基线**，因为有了对照才构成验证，而这是该要求的最小实现。基线的五项分别是版本、容量、压力、连接与日志用量。

```bash
# 验证：实验前采集五项基线（只读，生产机上也可以执行）
cat /etc/os-release | head -2; uname -r; systemctl --version | head -1; stat -fc %T /sys/fs/cgroup
df -h /; df -i /
free -m | head -2; cat /proc/pressure/memory
ss -lnt; ss -s | head -3
journalctl --disk-usage
```

```bash
# 验证：实验全部结束后的清理复核（无残留进程、目录、loop 设备、命名空间与监听）
pgrep -af 'spin|lab'                 # 无残留实验进程
ls -ld /var/tmp/review-lab           # 临时目录已清理
losetup -a; ip netns list            # 无残留 loop 设备与命名空间
ss -lntup                            # 无残留监听
free -m | head -2; df -h / | tail -1 # 内存与容量回到基线
```

## 2. 演练链：各实验的检验目标

这个顺序并非任意：**先做只读与可回滚的实验，再做可能损坏机器、只能依靠快照或控制台恢复的实验**，因为若首轮就损坏了机器，后续实验将无法进行。

| 顺序 | 实验 | 涉及的资源线 | 触发的连接点 | 判据字段 | 是否需要 root |
| --- | --- | --- | --- | --- | --- |
| 1 | 只读基线采集（它不属于故障注入） | 它检验观察面 | 它触及全部连接点，目的是建立可比较的基准 | 它读五项基线的全部字段 | 它不需要 root |
| 2 | 使一个独立文件系统的容量达到上限 | 它检验持久层的容量线 | 它触及 inode 与 fd 以及 Page Cache 两个连接点 | 它读 `df -h` 的 `Use%` 与写入操作的 errno | 它需要 root，因为要建 loop 镜像 |
| 3 | 使一个独立文件系统的 inode 耗尽 | 它检验持久层的容量线 | 它触及 inode 与 fd 这个连接点 | 它把 `df -i` 的 `IUse%` 与 `df -h` 的结果相对照 | 它需要 root |
| 4 | 把文件系统置为只读（用 loop 设备等价复现） | 它检验持久层的挂载状态 | 它触及快照与实验边界这个连接点 | 它读 `findmnt` 的 `OPTIONS` 列 | 它需要 root |
| 5 | 触发 cgroup 级的内存 OOM | 它检验内存线与约束环第 3 层 | 它触及 cgroup 以及内核日志与用户态日志两个连接点 | 它读 `memory.events` 的 `oom_kill` 与 `memory.peak` | 它需要 root，因为要建系统级 scope |
| 6 | 触发 CPU 配额限流 | 它检验算力线与约束环第 3 层 | 它触及配额与排队这个连接点 | 它读 `cpu.stat` 的 `nr_throttled` 与 `throttled_usec` | 它需要 root |
| 7 | 使一个进程的句柄耗尽 | 它检验连接线与约束环第 1 层 | 它触及句柄、端口与队列三个连接点 | 它读 `/proc/<pid>/limits` 与 `EMFILE` 报错 | 它不需要 root，因为它只影响子 shell |
| 8 | 使单个 CPU 核达到满负荷 | 它检验算力线的单核部分 | 它触及内核态时间与软中断这个连接点 | 它读 `mpstat -P ALL` 的逐核行与 `vmstat` 的 `r` | 它不需要 root |
| 9 | 把日志轮转的配置写错 | 它检验持久线与观察面 | 它触及 inode 与 fd 这个连接点 | 它读新旧文件的 inode 与行数 | 它不需要 root |
| 10 | 注入网络丢包与延迟 | 它检验连接线 | 它触及中断与网卡队列以及口径差异两个连接点 | 它读 `ss -ti` 的 `rtt`/`minrtt`/`retrans` 与 `tc -s qdisc` | 它需要 root，因为要用 `ip netns` |
| 11 | 使服务启动失败（改坏自建 unit） | 它检验约束环第 2 层 | 它触及 PID 1 以及监听队列与 socket 激活两个连接点 | 它读 `systemctl status` 的退出码与 `Result` | 它需要 root |
| 12 | 写坏 `/etc/fstab` 之后重启 | 它检验约束环第 2 层 | 它触及快照与实验边界这个连接点 | 它读启动是否进入 `emergency mode` 与 `journalctl -xb` 的输出 | 它需要 root，并且需要**控制台** |
| 13 | 把真正的根分区置为只读，或触发内核 panic | 它检验持久线与引导线 | 它触及快照与实验边界以及版本与默认值两个连接点 | 它读 `findmnt /` 的 `ro` 与 `journalctl -b -1 -k` | 它需要 root，并且需要**控制台** |

**未实测的登记**：第 12、13 项需要独立控制台或带外入口，因此在一台没有第二条通道的实验机上做坏之后就再也进不去；这类项目必须显式标为未实测，并写清补做方式（换一台可快照且有控制台的机器，一次只补一条）。同时要写清**为什么**未实测，例如当 `kdump` 处于 `inactive`、`kernel.sysrq` 的值不含 panic 位、或者 `/var/crash/` 为空时，panic 类实验连前提都不满足。

## 3. 观测指纹的读取方法

演练里最关键的不是"故障已经发生"这一事实，而是**这个故障会在哪些字段上留下什么形态**。下面五个观测指纹覆盖四条资源线，每一个都按"是什么 / 单位 / 判据 / 与谁同看 / 转向哪一步"这五件事给全。

### 3.1 容量耗尽：`df -h` 满而 `df -i` 不满

- **是什么**：`df -h` 给出的是数据块用量（`Use%`），而 `df -i` 给出的是 inode 用量（`IUse%`）。
- **单位**：两者都是百分数；其中 `df -h` 的容量以 GiB 或 MiB 计，而 `df -i` 的 inode 数量以"个"计。
- **判据**：这两者可以独立耗尽。若空间已满，则写入报 `ENOSPC`（No space left on device）；若 inode 已满，则报出的也是同一句 `ENOSPC`。**两者的报错文本相同而成因不同**，因此必须靠两个 `df` 来区分。
- **与谁同看**：它要与 `du -xsh` 同看，以确定空间被哪一级目录占用；要与 `lsof +L1` 同看，以确认是否存在已删除但仍被进程持有的文件；还要与 ext4 的保留块同看，因为 ext4 默认为 root 保留 5% 的块，所以普通用户写不进去时 root 可能仍然写得进去。
- **转向哪一步**：若 `df -h` 已满而 `du` 统计出来的总量很小，则转向查持有者与保留块；若 `df -i` 已满，则转向查小文件目录；若两者都已满，则先按业务重要性清理，而不要执行 `rm -rf` 删除日志目录。

只读故障还有一处判据必须在现场取得：文件系统在遇到错误之后是否自动转为只读，由**超级块中的设置**决定，因此并非所有 ext4 文件系统都一致。`man 5 ext4` 写明 `errors=` 的默认值存放在超级块中，并且可以用 `tune2fs` 修改；取该值只需要执行 `tune2fs -l <设备> | grep -i 'Errors behavior'`（本库实验机读到 `Continue`，即不会自动转为只读）。因此在其它机器上遇到根分区只读时，必须先确认该机器的这一取值，然后才能判断它属于内核转入保护还是人为挂载为只读。

### 3.2 内存上限：`memory.events` 的 `oom_kill`

- **是什么**：它是 cgroup v2 的事件计数文件，记录该组内各类达到上限的事件。
- **单位**：它的单位是次数，而且是累计值，因此必须取两次读数的**差值**，才能知道这一段时间内有没有发生。
- **判据**：若 `oom_kill` 的增量非 0，则该 cgroup 内确实杀过进程；同时要把 `memory.peak`（该组内存的历史峰值，单位为字节）与 `memory.max`（硬上限，单位为字节）相比对。
- **与谁同看**：它要与内核日志里的 OOM 记录同看，因为该记录含约束来源，例如 `CONSTRAINT_MEMCG` 表示本次 OOM 来自 cgroup 上限而不是整机水位；要与进程退出码同看，因为 137 等于 128 + 9，只说明进程收到了 `SIGKILL`；还要与宿主侧的 `free` 同看，因为宿主可能仍然比较空闲。
- **转向哪一步**：一旦确认是 cgroup 级 OOM，就转向查上限配在哪一层、峰值是多少、以及哪个进程在涨；**不要**只根据退出码 137 就写成 OOM。

### 3.3 算力配额：`cpu.stat` 的 `nr_throttled`

- **是什么**：它是 cgroup v2 的 CPU 统计，记录周期数与被节流的周期数。
- **单位**：`nr_periods` 与 `nr_throttled` 的单位是**周期数**（次，累计值），而 `throttled_usec` 的单位是**微秒**（累计值）。
- **判据**：若 `nr_throttled` 在两次读数之间持续增长，同时 `throttled_usec` 也同步增长，则说明这一段时间内一直被配额限制；反之，单独看 `nr_throttled` 非 0 只能说明"历史上发生过"。
- **与谁同看**：它要与 `cpu.max` 同看，该文件给出配额与周期，形如 `20000 100000` 表示每 100 ms 最多使用 20 ms；要与应用侧的吞吐与延迟同看；还要与 `/proc/pressure/cpu` 同看。
- **转向哪一步**：一旦确认被节流，就先判断是配额太小还是任务太多（依据是应用侧的在途请求数）；**不要**在容器里增加线程。

### 3.4 句柄：`/proc/<pid>/limits` 与 `EMFILE`

- **是什么**：该文件给出进程各资源的软上限与硬上限，其中 `Max open files` 就是 `RLIMIT_NOFILE`。
- **单位**：它的单位是个数。
- **判据**：当进程报出 `Too many open files`（`EMFILE`）时，要比较这个文件里的软上限与进程实际打开的 fd 数（用 `ls /proc/<pid>/fd | wc -l` 取得）是否接近；同时要注意软上限可以小于硬上限，而非 root 只能把软上限提到硬上限。
- **与谁同看**：它要与 `ss -s` 的 `timewait` 以及源端口范围同看，因为这两者容易与"连接数上限"混淆；若该进程由 systemd 启动，还要与 `systemctl show -p LimitNOFILE` 同看，因为此时实际值可能来自 unit 而不是登录会话。
- **转向哪一步**：一旦确认是单个进程的 fd 耗尽，就转向查它是不是连接泄漏（`CLOSE_WAIT` 堆积常见于此）；**不要**为了"验证"而在生产机上修改全局的 `fs.file-max`。

### 3.5 网络：`ss -ti` 的 `rtt`/`minrtt` 与 `retrans`

- **是什么**：它是单条 TCP 连接的内部状态。
- **单位**：`rtt` 与 `minrtt` 的单位是**毫秒**（`man 8 ss` 原文写明），而 `retrans` 是该连接的累计重传次数，单位为次。
- **判据**：若 `rtt` 明显高于 `minrtt`，则表明路径上存在排队，其原因可能是注入延迟、链路拥塞或中间设备缓冲；若 `retrans` 增长，则表明发生了丢包。注入延迟之后 `rtt` 抬升而 `retrans` 不变，而注入丢包之后 `retrans` 才增长，因此**这两个信号必须分别判断**。
- **与谁同看**：它要与 `nstat` 的重传计数同看（该计数是累计值，默认输出两次读数之差）；要与 `/proc/net/softnet_stat` 中每个 CPU 的丢弃计数同看；还要与 `tc -s qdisc show` 的 qdisc 计数同看，因为后者是注入侧的证据。
- **转向哪一步**：若延迟高而 `retrans` 低，则转向查路径上的排队；若 `retrans` 高，则转向查丢包点（可能是本机驱动、路径或对端）；若出现 `app_limited`，则说明瓶颈在应用侧，因此不要在网络上继续找。

## 4. 演练记录模板

```text
演练 N：<故障名>                      日期：____  机器：____
实验前基线：<版本 / 容量 / 压力 / 连接 / 日志用量>
注入动作：<命令与参数>                启动时刻：____
观测指纹：<命令，以及输出的要点与关键数值>
判定过程：<分层的依据、得出的结论，以及被排除的其它可能>
恢复动作：<命令>                      完成时刻：____
恢复耗时：____ 秒（对照业务能容忍的中断时间：____ 秒）
验收：<命令复验、业务探活与观察窗口>
清理复核：无残留进程 ☐  无残留目录 ☐  无残留 loop 与命名空间 ☐  参数与容量回到基线 ☐
未实测 / 未解释的现象：____  （原因：____  补做方式：____）
```

模板里三行不能省：

- **观测指纹**：若省去这一行，则这次演练只能证明"我操作过"，无法产生可迁移的知识；
- **恢复耗时**：若不记录时长，就只能证明"能做到"，无法证明"够快"；而该时长是与业务容忍的中断时间对齐的唯一证据；
- **未实测与未解释**：这一行要照实写，因为用一次观察当结论比不写更危险。

## 5. 演练结果与岗位要求的对应

演练链的目标不是完成全部十三项（其中第 1 项为只读基线采集，不属于故障），而是要证明三件事：

1. **能够识别**。面对一个现场，作答者要能够指出它属于哪条线、受阻于哪个排队点，而不是从命令清单中逐条尝试。
2. **能够恢复**。每个实验都记录了恢复动作与耗时，因此"可以恢复"有量化依据，而不是主观印象。
3. **能够界定范围**。作答者要区分实际执行过的、转引自其它阶段的以及未实测的三类内容，并对这三类内容使用三个不同的表述。

这三件事的验收方式见下一篇：将演练过的内容置于连续追问之下，检验是否仍能成立。

## 常见误解

| 说法 | 事实 |
| --- | --- |
| "演练就是把故障造出来看看" | 造故障只是一个动作，而可迁移的部分是"观测指纹、判定过程与恢复耗时"这三样 |
| "有快照就什么都能做" | 快照只能保证存储一致性，保不住入口；因此会断掉网络或挂载配置的实验，在没有控制台时就不要做 |
| "实验机是虚拟机，处理坏了重建就行" | 重建的成本掩盖了"没有第二条通道"这个真实约束；而生产上出事时并没有重建这个选项 |
| "恢复耗时不用记，反正能恢复" | 若不记录时长，就无法与业务容忍的中断时间对齐，也无法证明预案是现实的 |
| "报错一样就是同一个故障" | 空间耗尽与 inode 耗尽的报错文本同为 `ENOSPC`，但两者的成因与处置完全不同 |
| "重传率就是丢包率" | 前者是本机 TCP 的累计重传次数，后者是链路侧的丢包比例；注入丢包时两者会同时变化，但它们不是同一个量 |
| "未实测的部分不用写" | 省略标注等同于把该部分视为实测结论，因此阅读者（包括数月之后的自己）将无法分辨 |

## 要点自测

- 演练的三条纪律是什么？跑完复核哪五项？
- 为什么顺序上要先做可回滚的实验？举一个"做坏了就回不来"的例子。
- 空间耗尽与 inode 耗尽的报错文本相同，怎么在两秒内区分？
- `memory.events` 的 `oom_kill` 为什么要取差值？它与进程退出码 137 各证明什么？
- `nr_throttled` 非 0 与"这一段时间一直被节流"是不是一回事？判据怎么下？
- 一个进程的 fd 上限可能来自哪三个地方？怎么确认它现在生效的是哪一个？
- `ss -ti` 中 `rtt` 抬升与 `retrans` 增长分别指向什么？为什么不能混为一谈？
- 演练记录里哪三行不能省？各自防止什么损失？
- 为什么"有快照"仍不足以支撑写坏 `fstab` 这类实验？
- 分别说明"能够识别、能够恢复、能够界定范围"这三项的验收方式。
