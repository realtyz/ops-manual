# 附录：闭卷题库

六十九道闭卷题，按**四条线 + 约束环 + 观察面 + 组织层**分组，不按阶段分组。开头另有两组不属于四条线的前提题：环境与证据、启动链路。

按阶段出题时，作答者可能已预先知道"该题考查内存"；按线出题时，第一步始终是判断"这属于哪条线的问题"——真实告警不会预先给出所属章节。

题源全部来自前 11 章，每道题的答案都能在对应阶段找到出处。若这里的说法与对应阶段冲突，以对应阶段为准，并将冲突记入错题清单。

## 0. 使用纪律

1. **闭卷、限时、书面作答**。每组 5~13 题，按 20~25 分钟一段拆开完成，不要连续完成整组；无法作答的写"空白"，不要猜测。
2. **先写出答案，再对照下方的答案要点**。作答前先为答案定档：A 能脱稿讲 / B 有结论无证据 / C 认得但讲不出 / D 完全不会。
3. **每题答完写一行"缺的那一层"**：结论 / 判据 / 证据 / 边界 / 代价，选一个。
4. **不写"看情况"**。写不出条件，就说明这一条还没学会。

答完之后按这一组的结果定档：

| 结果 | 说明 | 下一步 |
| --- | --- | --- |
| 该组全 A | 这条线已达"能脱稿讲" | 转向不熟的线 |
| 多数 B（有结论无证据） | 缺证据层 | 回到对应阶段执行一次相关命令，将结论补全为"结论 + 命令 + 数值形态" |
| 多数 C（认得但讲不出） | 缺提取训练 | 按"完全不会"处理，重读该线对应的原理篇，再写一页纸 |
| 多数 D | 缺结论层 | 从对应的原理篇重新完整执行一次，不要直接做下一组 |

## 1. 前提组（环境、版本与证据）

**1.1 实验机与生产机的最低要求是什么？为什么"能快照"还不够？**

- 判定：能快照 + 能进控制台（或带外）+ 与生产隔离。
- 为什么不够：快照提供回滚，控制台提供"网络或 `fstab` 被处理坏之后唯一还能进去的路"；只管快照不留控制台，一次演练就可能把机器变成砖。

**1.2 版本基线四件套是什么？命令分别是什么？**

- 判定：发行版（`cat /etc/os-release`）、内核（`uname -r`）、systemd（`systemctl --version | head -1`）、cgroup（`stat -fc %T /sys/fs/cgroup`）。
- 实测参照（转引阶段 1、7）：本库实验机为 `Ubuntu 24.04.5 LTS` / `6.8.0-139-generic` / `systemd 255` / `cgroup2fs`。
- 边界：没有这四项，后面所有"默认值"都失去意义。

**1.3 为什么内核版本号不能跨发行版直接比大小？**

- 判定：发行版会把新特性回移（backport）进较老的主线版本。
- 证据：RHEL 9 基线内核 5.14、Ubuntu 24.04 是 6.8、Debian 12 是 6.1，但 RHEL 的 5.14 含大量回移特性。
- 落点：讨论版本差异时以该发行版的 release notes 为准。

**1.4 `error while loading shared libraries` 的四步处理顺序？**

- 判定：缺哪个库（`ldd`）→ 装没装（`ldconfig -p` 或包管理）→ 搜索路径对不对（`/etc/ld.so.conf.d/`）→ `ldconfig` 后复验。
- 边界：`LD_LIBRARY_PATH` 只影响当前进程树，不是持久修法。
- 不要做：不要直接把库文件拷到 `/lib` 了事。

**1.5「重启能解决 90% 的问题」这句话的问题在哪？变更前三件事是什么？**

- 判定：重启会毁掉现场；历史日志未持久化时尤其致命。
- 变更前三件事：带时间戳的备份、写下来的回滚命令、确认过的时间窗。
- 落点：先取证再决定是否重启；`journalctl -b -1` 依赖日志持久化。

## 2. 启动链路组

这一组不属于四条线中的任何一条：机器起不来时，四条线都不在服务，问题落在"谁在接力、接力到哪一环断了"。

**2.1 启动五环是什么？每一环失败时的现场在哪？**

- 判定：固件 → 引导加载器 → 内核 + initramfs → systemd → 登录与服务。
- 现场：物理屏与带外日志（固件）；`grub>` / `grub rescue>`（引导加载器）；`dracut:/#` 之类的 initramfs shell（内核与 initramfs）；`emergency.target` 与 `journalctl -xb`（systemd）。
- 第一反应不要是什么：不要先问"怎么修"，先问"**现在是谁在输出**"——输出者决定当前所处的环节。

**2.2 initramfs 的职责是什么？内核升级后起不来最常见的原因？**

- 判定：把"挂载真正根文件系统所需的驱动"装进内存，挂上真根后 `switch_root`。
- 常见原因：新内核没有对应的存储或文件系统模块，或 `root=` 指向的设备对不上（UUID 变了、控制器变了）。
- 落点：改动根设备或存储控制器后，必须重建 initramfs 并在实验机上重启验证。

**2.3 两套"内核参数"指什么？改启动参数的验收标准是什么？**

- 判定：启动参数（`/proc/cmdline`，只在启动那一刻生效）与运行时参数（`sysctl`）。
- 验收：`cat /proc/cmdline` 里能看到新参数；只看 `/etc/default/grub` 不算。
- 边界：Debian 系要 `update-grub`，RHEL 系用 `grub2-mkconfig`（或 `grubby`）。

**2.4 内核 panic 后现场在哪？为什么不能先重启？**

- 判定：`journalctl -b -1 -k`、`/var/crash/`、`dmesg` 的上一轮引导段、带外日志；配置了 kdump 才有 `vmcore`。
- 为什么：重启会覆盖内存现场与未持久化的日志；"再重启一次看看"是最常见的毁现场动作。
- 未实测：panic 实验需要可无法作答溃的实验机与控制台——本库实验机只有 SSH 一条通道，`kdump` 为 `inactive`、`kernel.sysrq` 的值不含 panic 位、`/var/crash/` 为空，做坏了无法自救，因此不做。
- 止损：先让其他节点承接业务（高可用视角），再决定是否分析 `vmcore`；结论候选按"驱动或硬件 → 内核问题 → 内存故障 → 前一次变更"的顺序排查，并与变更时间线对齐。
- 不要做：不要读几秒日志就下"内核 bug"的结论，也不要忘记对齐变更记录。

**2.5 `emergency.target` 与 `rescue.target` 的区别是什么？**

- 判定：区别在挂了多少文件系统、要拉起多少单元；`emergency` 更小（通常只挂根，要求 root 密码），`rescue` 会拉起更多基础服务。
- 落点：`fstab` 写坏时通常落在 emergency 或直接进入维护 shell。
- 不要做：不要在紧急模式里盲目重启，先把 `journalctl -xb` 取下来。

## 3. 算力线

**3.1 性能排障的方法论顺序是什么？第一步做什么？**

- 判定：先量化影响面，再分层排除，最后才动手。
- 第一步：回答五个问题——谁受影响、多严重、从几点开始、还在不在恶化、和什么比。
- 实测参照（转引阶段 10）：单个自旋进程让单核 100%，而整机 `%usr` 只有 25.00%（4 vCPU 的 1/4）、`load` 只有 0.34。

**3.2 `load average` 到底是什么？为什么要除以核数？**

- 判定：它是可运行 + 不可中断睡眠（`D`）任务的平均数，包含等 IO / 等锁的进程。
- 判据：与核数之比 > 1 持续存在才值得追；同时看 `vmstat` 的 `b` 与 `wa` 定位来源。
- 不要做：不要用"`load` 高就是 CPU 忙"下结论。

**3.3 CPU 高的五个分支是什么？`vmstat` 的 `si` 为什么容易看错？**

- 判定：`us`（用户态）、`sy`（内核态）、软中断（`%soft`）、`wa`（IO 等待）、`st`（被虚拟化偷走）。
- `si` 的误区：它是**换入**（swap in），不是软中断；软中断看 `mpstat` 的 `%soft`。
- 边界：`mpstat` 文档明确 `%sys` **不含**硬/软中断的时间，中断占用的核要看 `/proc/interrupts`。
- 落点：每个分支对应不同的下钻工具（`perf`、`pidstat`、`/proc/interrupts`）。

**3.4 自愿切换与非自愿切换分别说明什么？**

- 判定：自愿（voluntary）是进程主动让出 CPU（等 IO、等锁、sleep）；非自愿（involuntary）是被抢占（时间片用尽或优先级竞争）。
- 实测参照（转引阶段 10）：socket ping-pong 场景实测自愿切换 **40,343.67** 次/秒、非自愿 **16.67** 次/秒。
- 判据：非自愿多 → 同核竞争或核数不足；自愿多 → 等锁、等 IO，或切换开销本身；看 `vmstat` 的 `cs` 与 `pidstat -w`。

**3.5 火焰图看什么？什么时候看不了？**

- 判定：它是采样堆栈的聚合图：横轴是样本占比（不是时间轴），纵向是调用栈深度，宽条代表该函数在采样中出现得多。
- 用途：找 on-CPU 热点；off-CPU 等待要看 off-CPU 火焰图或 `/proc/<pid>/wchan`。
- 前提：需要符号（debuginfo 或符号表）与采集权限；容器、无 PMU 或 `perf_event_paranoid` 受限时可能采不到样本。
- 不要做：不要把横轴当时间线读，也不要只看一张图就下结论。

**3.6 `D` 状态进程与僵尸进程分别为什么 `kill -9` 杀不掉？判据是什么？**

- 判定：`D` 状态卡在内核态不可中断等待，信号被挂起，等它回到用户态才处理；僵尸已经终止，等的是**父进程**回收。
- 判据：`ps -o stat,wchan`（`D` 的 `wchan`）、父进程状态与 `ps -o stat,ppid`。
- 不要做：不要对 `D` 状态进程反复 `kill -9`，先找它在等什么（IO、网络存储、锁）。

**3.7 `SIGTERM` 与 `SIGKILL` 的区别？退出码 128+N 是什么意思？**

- 判定：`SIGTERM` 可捕获、可优雅退出；`SIGKILL` 不可捕获、不可阻塞、不可忽略。
- 128+N：被信号 N 杀死时的 shell 退出码（143 = TERM、137 = KILL）。
- 边界：137 不能证明是 OOM；OOM 要看内核日志与 `memory.events`。

**3.8 进程数打满 / 句柄耗尽的排查顺序？**

- 判定：先确认是哪一类上限（`pids.max`、`LimitNOFILE`、`fs.file-max`），再定位是谁在消耗。
- 证据：`systemctl show -p TasksMax,LimitNOFILE`、`/proc/<pid>/limits`、`lsof -p <pid>`、cgroup 的 `pids.current`。
- 边界：任务数这一类上限同时存在四个不同的数——unit 的 `TasksMax` 与 cgroup 的 `pids.max`、进程的 `RLIMIT_NPROC`、内核 `threads-max`、内核 `pid_max`；各自由不同机制生效，不要混为一谈。
- 不要做：不要为了恢复而直接调大内核全局上限，那只是掩盖泄漏。

**3.9 进程与线程在计数与调度上有什么区别？**

- 判定：内核调度的基本单位是 task；一个进程可以包含多个 task（线程），它们共享地址空间但各自被调度。
- 证据：`ps -e` 数的是进程，`ps -eLf` 数的才是 task；cgroup 的 `pids.current` 计的是 task。
- 边界：`TasksMax=`/`pids.max` 限制的是 task 总数，调它要按线程规模算，不是按进程数算。

## 4. 内存线

**4.1 `free` 显示可用内存很少，说明内存不够吗？**

- 判定：不等于；判据是 `MemAvailable` 加内存压力（PSI，`/proc/pressure/memory`）。
- 实测参照（转引阶段 10，条件以该阶段为准）：分配并触碰 3 GiB 后 `MemAvailable` 从 7224 MiB 降到 4145 MiB，而 PSI 的 `avg10/60/300` 全程为 0（累计 `total` 在涨）。
- 不要做：不要因为 `free` 少就重启服务、加内存或清缓存。

**4.2「申请」和「占用」有什么区别？`VSZ` 很大而 `RSS` 很小说明什么？**

- 判定：`malloc`/`mmap` 只是虚拟地址承诺，首次写入才通过缺页拿到物理页。
- 说明：说明承诺了地址空间但还没落地（也可能是保留映射），不能据此判断泄漏。
- 边界：判断泄漏只能看趋势（`pidstat -r` 或历史监控），单次快照说明不了任何问题。

**4.2 Page Cache 什么时候会变成问题？观测指纹是什么？**

- 判定：脏页积压、回写跟不上时，写进程被按在脏页限流上等待。
- 指纹：`wa` 高、`w_await` 与 `aqu-sz` 上升、进程进 `D` 状态；`/proc/meminfo` 的 `Dirty`/`Writeback` 偏高。
- 不要做：不要把"缓存占用高"当作内存不足来处置。

**4.3 `vm.swappiness=0` 等于关闭 swap 吗？关掉 swap 的代价是什么？**

- 判定：不等于，它是回收倾向的权重；禁用要 `swapoff` 或 `memory.swap.max=0`。
- 代价：把"换页变慢"换成"被 OOM 终止"。
- 落点：选哪一边取决于业务对延迟与可用的偏好，不是"哪个默认值更好"的问题。

**4.4 OOM 的判定证据是什么？容器 OOM 与整机 OOM 的区别？**

- 判定：内核日志的 OOM 记录 + cgroup v2 的 `memory.events`；**退出码 137 不是证据**。
- 区别：容器级看 `memory.max`/`memory.current`/`memory.events`；整机级看 `MemAvailable`、PSI 与内核日志。
- 落点：容器化环境里很多 OOM 是 cgroup 级，整机可能还有空闲内存。

**4.5 怎么区分内存"用得多"和"有压力"？PSI 是什么？**

- 判定：用得多看 `MemAvailable` 与缓存构成；有压力看 PSI（`/proc/pressure/memory` 的 `some`/`full`）以及 `si`/`so`、回收计数。
- 实测参照（转引阶段 10）：触碰 3 GiB 后 `MemAvailable` 7224 → 4145 MiB（降 3079 MiB），而 PSI 的 `avg10/60/300` 全程为 0。
- 落点：只读观测，生产机上也可以做。

**4.6 PSI 的 `avg*` 与 `total` 各是什么单位？为什么必须分清？**

- 判定：`avg10/avg60/avg300` 是被压力拖慢的时间占比（百分比）；`total` 是累计的停顿时间（微秒）。
- 判据：`avg` 看"现在有多严重"，`total` 取差值看"这一段时间内有没有真的发生"。
- 不要做：不要把两个单位不同的量放在一起比大小或画在同一条曲线上。

**4.7 内存回收与设备 IO 为什么会互相拖慢？判据是什么？**

- 判定：回收的落点是设备——匿名页要换出到 swap、文件页要回写；设备忙则回收变慢，分配者转入直接回收，表现为延迟尖刺。
- 判据：`/proc/vmstat` 的 `pgscan_direct` 取差值在增长，**同时** `iostat -x` 的 `await` 上升；两者同时出现才是"回收造成 IO 压力"的证据。
- 不要做：不要只看到其中一个信号就定性，也不要用加内存去治设备排队。

**4.8 为什么"内存占用"可以有好几个数？各口径什么时候用？**

- 判定：常驻（`RSS`）按使用者重复计数共享页；均摊（`PSS`）把共享页按使用者数量分摊；私有页只算独占部分。
- 用法：横向比"谁占得多"用均摊，判断"释放这个进程能回收多少"用私有页，看整机账本用 `MemAvailable` 与 `free`。
- 不要做：不要用一个口径的数字去回答另一个口径的问题。

**4.9 大页是否生效看哪个字段？为什么它容易看错？**

- 判定：透明大页看 `/proc/meminfo` 的 `AnonHugePages`（匿名大页，单位 KiB）。
- 为什么容易看错：页表项数量（`VmPTE`）受映射数量、小页与大页混用影响，不能反推大页是否生效——要单独看大页自己的计数。
- 边界：大页按 2 MiB 落地会放大内存占用，`khugepaged` 的后台整理会带来停顿。

## 5. 持久线

**5.1 存储的四层是什么？`lsblk`、`df`、`du` 各回答什么问题？**

- 判定：块设备 → 分区 / LVM → 文件系统 → 挂载点。
- 分工：`lsblk` 看设备与挂载关系、`df` 看文件系统账本、`du` 看目录树里的实际占用。
- 不要做：不要把三个工具的输出混着解释，它们答的是三个问题。

**5.2 `df` 和 `du` 对不上的四类原因？**

- 判定：已删除但被进程持有（`lsof +L1`）、被挂载覆盖的目录、文件系统保留块与元数据、稀疏文件与延迟分配。
- 实测参照（转引阶段 9）：删除一个仍被持有的 **10 MiB** 文件后 `df` 已用从 24576 字节涨到 10510336 字节，而 `du -sh` 只有 **20K**。
- 落点：四类的处置完全不同，逐个排除而不是互相否定。

**5.3「有空间却写不进去」的四种原因与各自判据？**

- 判定：容量满（`df -h`）、inode 满（`df -i`）、ext4 保留块（默认 5%）、配额到顶（报 `Disk quota exceeded`）。
- 落点：先看报错文本，再选对应工具——`No space left on device` 与 `Disk quota exceeded` 的含意不同；空间满与 inode 满的报错文本相同，要靠两个 `df` 区分。
- 不要做：不要一看到"空间"就去删文件。

**5.3 ext4 与 XFS 的核心差别？**

- 判定：ext4 的 inode 数量在 `mkfs` 时固定，能缩容但必须卸载且风险高；XFS 用动态分配的 64 位 inode，只能扩不能缩，在线扩容非常方便。
- 落点：生产上常见"XFS + LVM"的组合。
- 边界：修复必须在卸载或只读挂载下做，XFS 默认拒绝对已挂载设备操作。

**5.4 根文件系统变只读时的处置顺序？第一反应不要做什么？**

- 判定：先查原因（`dmesg` 的 ATA/SCSI/NVMe 错误、阵列状态），再把业务切走决定修还是重建。
- 判据：这台机器"遇到错误会不会自己转只读"由超级块里的 `errors=` 设置决定（`tune2fs -l <设备>` 现场取），不能凭印象说"内核一定会保护"。
- 不要做：不要 `mount -o remount,rw`——那会把保护关掉，可能扩大损坏。

**5.5 LVM 与云盘扩容的完整链路是什么？扩容后验收看什么？**

- 云盘与分区链：先在平台侧扩卷 → `growpart /dev/sdX N` 扩分区 → `xfs_growfs /mount`（XFS）或 `resize2fs`（ext4）。
- LVM 链：底层变大后 `pvresize /dev/sdXN` → `lvextend -r -l +100%FREE /dev/vg/lv`（`-r` 顺带扩文件系统）。
- 验收：`df -h` 看到新容量才算完成；`lsblk`、`pvs`、`vgs`、`lvs` 只能证明前几跳。
- 不要做：不要对 XFS 尝试缩容；操作前先确认业务能承受。

**5.6 RAID 0/1/5/6/10 怎么取舍？RAID 5 到底能防什么？**

- 取舍：RAID 0 无冗余（任一块盘坏即全丢）；RAID 1 镜像、容量减半、容单盘故障；RAID 5 单校验、容单盘故障、写惩罚明显；RAID 6 双校验、容两块盘故障；RAID 10 镜像加条带、容量减半、性能与恢复最好、成本最高。
- RAID 5 的边界：只容忍单盘故障；重建期间再坏一块就丢数据，而大容量盘的重建时间很长——**重建窗口就是风险窗口**。
- 巡检：`cat /proc/mdstat`、`mdadm --detail /dev/mdX` 看阵列状态，`smartctl` 看介质错误。
- 不要做：不要把 RAID 当备份——它不防误删、勒索加密与逻辑损坏。

**5.7 `await`、`aqu-sz`、`%util` 各是什么？为什么它们可以互相矛盾？**

- 判定：`await` 是平均等待时间（毫秒，含排队）、`aqu-sz` 是平均队列长度（个请求）、`%util` 是有 IO 在飞行的时间比例。
- 矛盾的原因：三者描述不同维度；Little's law 可以把 `w/s × w_await` 与 `aqu-sz` 对齐（**转引**阶段 10 实测：324 × 0.00659 s = 2.14，同窗口 `aqu-sz` 实测 2.14）。
- 落点：判断是否饱和要连起来读，并对照业务延迟。

**5.8 `copytruncate` 与 `create` 的区别？为什么要在 `postrotate` 里让应用重开文件？**

- 判定：`copytruncate` 保持 inode 不变（有丢日志窗口）；`create` 换新 inode，但持有旧 fd 的进程会继续写归档文件。
- 实测参照（转引阶段 9）：`copytruncate` 后 inode 不变（`1310736 → 1310736`）；`create` 后 inode 换了（新文件 `1310803`、归档 `1310798`），随后 9 行被写进归档、新文件 0 行。
- 落点：`postrotate` 里 `systemctl reload` 或发信号让应用重开文件。

**5.9 日志把磁盘写满时，先做什么？`rm` 掉被持有的文件会怎样？**

- 判定：先看谁在写、文件是否仍被进程持有，再决定清理与限流。
- 证据（转引阶段 9 实测）：`rm` 一个仍被持有的 **10 MiB** 文件后，`df` 已用反而从 24576 字节涨到 10510336 字节；`/proc/<pid>/fd/4` 显示 `(deleted)`，关掉 fd 后才回落到 24576 字节。
- 落点：`logrotate` + `SystemMaxUse` + 容量告警三件套。

**5.10 同一个容量问题，为什么内核与工具会给出两个不同的视角？**

- 判定：块层看的是"提交到设备的字节"，文件系统看的是"文件占用的块"，用户看的是 `df` 的使用率；页缓存、已删除但仍被持有的文件、保留块、稀疏文件都会让三者不一致。
- 证据：`df -h` 与 `du -xsh` 的差值、`lsof +L1` 的持有者、`/proc/meminfo` 的 `Dirty`/`Writeback`、`tune2fs -l` 的保留块设置。
- 落点：先判定"是哪两个视角不一致"，再选工具；"写成功"的三种含义（进缓存 / 进设备缓存 / `fsync` 返回）是同一个道理在写入路径上的版本，完整对照见《高频误判对照表》持久线一节。

## 6. 连接线

**6.1 一次连接的六站是什么？为什么"先分层"是唯一可靠的方法？**

- 判定：名字 → 地址 → 建链 → 传输 → 断开 → 链路（→ 出门之后）。
- 为什么：`ping` 通 ≠ TCP 能连 ≠ 应用正常；每一层的失败形态与证据都不同。
- 落点：按"链路与驱动 → IP 与路由 → 端口与过滤 → 解析 → 应用"自下而上看。

**6.2 服务端的两个队列是什么？队列上限怎么算？"静默丢 SYN"的证据在哪？**

- 判定：半连接队列（`SYN_RECV`）与全连接队列；全连接队列上限是 `min(backlog, somaxconn)`。
- 证据：`ss -lnt` 里 `Recv-Q` 是当前队列深度、`Send-Q` 是上限；溢出计数在 `nstat` 的 `TcpExtListenOverflows`/`ListenDrops`（累计值，要看差值）。
- 边界：内核判断"队列满"用的是 `Recv-Q > Send-Q`，也就是允许比上限多排一个；因此读到 `Recv-Q >= Send-Q` 就说明已经满了，"溢出过多少次"这件事本身仍然只能看 `nstat` 的增量。
- 实测参照（转引阶段 6）：`listen(10000)` 在 `somaxconn=4096` 的机器上被静默截断成 4096。

**6.3 `TIME_WAIT` 与 `CLOSE_WAIT` 的区别与处置？**

- 判定：前者是主动关闭方的正常状态（Linux 固定 60 秒），后者是应用收到 FIN 却没 `close()`。
- 处置：`TIME_WAIT` 只能通过连接复用缓解；`CLOSE_WAIT` 只能改应用。
- 不要做：不要试图用 `tcp_fin_timeout` 改 `TIME_WAIT`（它管的是 `FIN_WAIT2`）。与之相关的 sysctl 有的是"影响数量"而不是"改时长"：`tcp_max_tw_buckets` 限制同时存在的数量、超限会直接关闭并告警，`tcp_tw_reuse` 允许在安全条件下复用——所以准确说法是"改不了时长，但可以影响数量与复用"。

**6.4 `tcp_syncookies` 起什么作用？它会让哪个计数增长？**

- 判定：半连接队列满时改发 cookie，避免直接丢 SYN。
- 计数：`TcpExtSyncookiesSent`、`TcpExtTCPReqQFullDoCookies`；**`ListenDrops` 不一定增长**。
- 边界：关掉 syncookies 才会变成真丢包。

**6.5 不抓包怎么判断链路质量？`ss -ti` 里看哪几个字段？**

- 判定：`rtt` / `minrtt` / `cwnd` / `retrans` / `pacing_rate` / `delivered` / `app_limited`。
- 实测参照（转引阶段 6）：本机连接实测 `rto:201 rtt:0.028/0.012 mss:1448 ... cwnd:10 ... minrtt:0.004`（不同连接 `rtt` 在 0.007~0.089、`minrtt` 在 0.001~0.012 之间，**单位毫秒**）。
- 落点：出现 `app_limited` 说明"慢"不在网络上。

**6.6 `ss -ti` 的 `rtt` 与 `iostat` 的 `await` 能直接比吗？**

- 判定：不能，但不是因为单位不同——`ss` 文档写明 `rtt`/`rttvar` 的单位是**毫秒**，与 `await` 相同；不可比的原因是**对象不同**：一个是单条连接的往返时间，一个是设备的平均单次请求耗时（含排队），而 `%util` 又是设备忙碌占比。
- 用法：`rtt` 与同一条连接的 `minrtt` 比（差距大说明路径上有排队）；`await` 与同一设备的历史基线比。
- 不要做：不要跨对象地比较两个"看起来都是时间"的数字，也不要把 `%util` 当饱和度。

**6.7 域名解析为什么会出现"同一个名字、两个结果"？**

- 判定：应用走 `getaddrinfo()`（经 NSS，名字服务开关），`dig` 直接问 DNS——两条路径本来就不同；`/etc/hosts`、`resolvectl` 的缓存、`search` 与 `ndots` 的放大都会造成差异。
- 证据：`getent hosts <name>` 与 `dig <name>` 对照；`resolvectl statistics` 看缓存命中。
- 边界：容器内有自己的 `/etc/resolv.conf` 与 `nsswitch.conf`，宿主的结果不能代表容器。

## 7. 约束环

**7.1 一个服务的三件套是什么？`systemctl status` 的三段对应什么？**

- 判定：unit 说明书 + cgroup 笼子 + journald 证据。
- 对应：`Loaded`（unit 与配置）、`Active`（判定状态）、`CGroup`（进程与资源）。
- 落点：排障第一反应是把三段读全。

**7.2 改 unit 文件之后，完整生效链条是什么？**

- 判定：改文件 → `status` 出现 changed on disk 警告、manager 仍是旧值 → `daemon-reload` 后 manager 变新值、**运行中进程环境仍是旧值** → `restart` 后才是新值。
- 验收：读生效值用 `systemctl show -p ...`，不要只看文件。
- 不要做：不要把 `daemon-reload` 当成重启。

**7.3 `Wants=` 与 `After=` 有什么区别？`Type=` 为什么重要？**

- 判定：`Wants=`/`Requires=` 决定要不要拉起对方；`After=`/`Before=` 只决定顺序，不写 `After` 就并行。
- `Type=`：决定"什么算启动完成"——选错就是"假启动失败"（`simple` 遇到后台化进程会立刻 `inactive (dead)`）。
- 落点：`Type=notify` 默认 `NotifyAccess=main`，子进程通知会被拒，一直等到超时（**转引**阶段 8 实测：改成 `NotifyAccess=all` 后 0.0396 秒启动成功）。

**7.4 服务资源上限的落点在哪？给出三个实际值例子。**

- 判定：unit 的 `LimitXXX=`、`MemoryMax=`、`CPUQuota=`；不要改 `limits.conf`。
- 例子：`LimitNOFILE=64` → 服务内 `ulimit -n` 为 64；`MemoryMax=32M` → `memory.max=33554432`；`CPUQuota=10%` → `cpu.max=10000 100000`。
- 边界：**unit 文件里写的值与进程实际拿到的值可能不同**——`systemctl show -p LimitNOFILE` 读到的是 unit 配置，进程真实生效的软/硬上限看 `/proc/<pid>/limits`；两者之间还夹着编译期默认值（如 `DefaultLimitNOFILE=`）。本库实验机上这两个数确实不同，所以"上限到底是多少"要两处都看。
- 边界：容器 OOM 时 cgroup 的 `memory.max` 与 systemd 的 `OOMPolicy=` 会决定是整个 unit 停掉还是只杀进程。

**7.5 systemd timer 与 cron 的差别？各自的误区是什么？**

- 判定：timer 有依赖、日志与 `Persistent=`（补跑）语义；cron 环境极简。
- 误区：cron 非交互 shell 不读 `.bashrc`，`PATH` 与别名不同，`%` 要写成 `\%`；tmpfiles 的 age 默认同时看 mtime/atime/ctime。
- 落点：定时任务排障先看"它到底跑没跑"，再看"跑在什么环境里"。

**7.6 资源限制的五层是什么？改错层会有什么后果？**

- 判定：技术上限有四层——会话（`ulimit` 与 `limits.conf`/PAM 两条来路）→ unit 的 `LimitXXX=`/`TasksMax=`（服务）→ cgroup（整组）→ 内核全局；此外还有第 5 层"组织层"（审批、窗口、冻结期），它不配上限，只决定这些上限现在能不能改。
- 后果：实际生效的是前四层里最紧的那一层；改 `/etc/security/limits.conf` 对 systemd 服务无效，这是最高频的出错点。
- 落点：服务类问题先读 `systemctl show -p LimitNOFILE,TasksMax`，再读 `/proc/<pid>/limits` 与 cgroup 对应文件。

**7.7 namespace 与 cgroup 各管什么？**

- 判定：namespace 管"看得见什么"，cgroup 管"能用多少"。
- 容器定义：namespace + cgroup + 根文件系统 + 权限约束（capabilities/seccomp/MAC），少任何一层都不成其为容器。
- 边界：容器与虚拟机共享同一个内核。

**7.8 `Permission denied` 可能来自哪五层？用什么命令分层看？**

- 判定：DAC 位、ACL、capabilities、挂载选项、SELinux/AppArmor。
- 命令：`namei -l <path>`、`getfacl`、`getcap`、`findmnt`、`ls -Z`、`ausearch -m AVC`。
- 不要做：不要上来就 `chmod 777` 或 `setenforce 0`。

**7.9 文件的 `rwx` 与目录的 `rwx` 语义有什么不同？**

- 判定：文件的 `x` 是"可执行"；目录的 `x` 是"能穿过"，目录的 `r` 才是"能列出名字"。
- 关键推论：删文件看**目录的 `w`**，不看文件自己的 `w`。
- 落点：`/tmp` 的 `1777` 靠 sticky 位限制"只能删自己的"。

**7.10 SUID 的边界有哪些？怎么正确查找 SUID 文件？**

- 判定：SUID 只对二进制生效（脚本被内核忽略）；`no_new_privs`、`nosuid` 挂载、被跟踪时也会被忽略。
- 查找：`find / -perm -4000`（包含该位），不是 `-perm 4000`（精确匹配）。
- 实测参照（转引阶段 7）：本库实验机 SUID 文件 13 个、SGID 文件 7 个、带 file capabilities 的文件 4 个。

**7.11 capabilities 相比 SUID 的优势是什么？怎么给服务最小特权？**

- 判定：capabilities 可以只授予一项能力（如 `cap_net_raw`），而不是整个 root。
- 落点：`setcap` 用于二进制；systemd 服务用 `AmbientCapabilities=`/`CapabilityBoundingSet=` 限定。
- 不要做：不要为了省事直接给 `CAP_SYS_ADMIN` 或整个 root。

**7.12 加固的验收标准是什么？为什么 `setenforce 0` 不算修复？**

- 判定：验收标准是"可核查"——账号、SUID/SGID/capabilities、监听端口、计划任务与自启、SSH 授权五类基线。
- 为什么：`setenforce 0` 只是把**强制拦截**关成 permissive，**审计与 AVC 拒绝记录依然在产生**——它掩盖了问题，并没有改变访问控制的设计。
- 落点：加固前后各采一次基线，用差异证明改动有效。

**7.13 SSH 加固要做哪六件事？验收标准是什么？**

- 六件事：关密码登录（只留密钥）、禁 root 直登、关掉不需要的认证方式（如 GSSAPI）、用 `AllowUsers`/`AllowGroups` 限定人、限制尝试与并发（`MaxAuthTries`、`MaxStartups`）、收敛算法（`KexAlgorithms`/`Ciphers`/`MACs`）。
- 验收：`sshd -T -C user=...,addr=...` 看最终生效值（`Match` 会改变结果）；从另一台机器实测"该进的能进、不该进的进不来"。
- 不要做：不要只改完文件就 reload；先 `sshd -t` 校验语法，并保留一条已经打开的会话做回滚。

## 8. 观察面

**8.1 journald 与 rsyslog 是什么关系？**

- 判定：不是二选一；同一条日志通常两边都有。
- 证据：`logger -t labtest` 后，`journalctl -o json` 有 `SYSLOG_IDENTIFIER`/`_PID`/`_UID`/`_TRANSPORT`，`/var/log/syslog` 是纯文本一行。
- 落点：排查"日志去哪了"时要同时看两个落点与 `ForwardToSyslog=`。

**8.2 为什么平均值会骗人？p95 为什么还要报口径？**

- 判定：平均值掩盖长尾——1000 个样本（950×20 ms + 45×100 ms + 5×2000 ms）平均 33.5 ms，`max` 2000 ms。
- 口径：同一组样本按四种常见算法，p95 分别是 20.0 / 24.0 / 96.0 / 100.0 ms。
- 落点：报分位数必须连算法与采样窗口一起报。

**8.3 告警降噪的四种手段是什么？SLI/SLO/错误预算各是什么？**

- 判定：路由、分组、抑制、静默（另有可用性探测补上用户视角）。
- 定义：SLI 是可测量的服务质量指标；SLO 是它的目标；错误预算是"允许失败的量"，用于决定发布节奏与"立刻处理还是排期"。
- 落点：告警必须落到一个具体动作上，否则就是噪音。

**8.4 USE 方法是什么？它比工具清单好在哪？**

- 判定：对每一类资源（CPU / 内存 / IO / 网络 / 存储）依次问三件事——利用率（Utilization）、饱和度（Saturation）、错误（Errors）。
- 好在哪：先给出一份"该查什么"的清单，再决定用哪个工具，避免把命令挨个跑一次。
- 边界：它只覆盖资源视角；应用层的锁、GC（垃圾回收）、下游依赖要靠 trace、应用指标与日志。

**8.5 `sar` 用来做什么？用它复盘的前提是什么？**

- 判定：`sar` 读的是 sysstat 的历史采集，用来回答"那时候机器是什么状态"——实时观测回不到过去。
- 用法：实时 `sar -u 1 3`；历史 `sar -u -f /var/log/sysstat/saDD`，另有 `-r`（内存）、`-b`（IO）、`-n DEV`（网络）。
- 前提：装了 `sysstat` 且历史采集已启用。本库实验机是"已安装且正在采"的正面样本（`sysstat-collect.timer` 为 `enabled`、`/var/log/sysstat/` 有当天数据）——但很多机器上该目录根本不存在，所以这一题的教训是"**先确认有数据，再读数据**"。
- 不要做：不要拿默认日期的 `sar` 结果解释某次故障，先确认文件日期与采样间隔。

**8.6 trace/span 与日志、指标的分工是什么？**

- 判定：日志回答"发生了什么"，指标回答"整体趋势"，trace/span 回答"这一次请求的时间花在哪一段"。
- 证据：一个 trace 由多个 span 组成，每个 span 有开始、结束、父子关系与服务名；采样率决定开销与留存成本。
- 边界：异步与批处理、缺少上下文传递的调用看不到完整链路。
- 落点：先用指标发现异常时段，再用 trace 定位到具体一段，最后用日志确认原因。

**8.7 日志查不到、查不全，有哪几类原因？**

- 判定：四类——没写进来（落点选错）、没持久化（`Storage=` 的生效值）、被限流（`Suppressed N messages`）、被裁掉或轮转掉。
- 证据：`systemctl show -p StandardOutput,StandardError`、`journalctl --disk-usage`、`systemd-analyze cat-config systemd/journald.conf`、`stat -c %i` 与 `ls -l /proc/<pid>/fd`。
- 不要做：不要先关掉限流；先确认是"没进来"还是"被丢掉"。

## 9. 组织层

**9.1 变更单的六要素是什么？最容易漏的是哪两个？**

- 判定：目标、范围、备份、回滚、验证、窗口。
- 最容易漏：回滚的触发条件与验证的量化判据（要求在动手前即将答案写出）。
- 不要做：不要把"改动很小"当作降级理由。

**9.2 备份、快照、副本分别不能防什么？3-2-1 原则是什么？**

- 判定：快照依赖存储系统且与源同域；副本实时同步会一起被删、被加密；只有独立备份能防误删与逻辑损坏。
- 3-2-1：3 份数据、2 种介质、1 份异地（现代补充：1 份离线或不可变）。
- 落点：备份的唯一验收标准是"能恢复"并计时（对齐 RTO，即恢复时间目标）。

**9.3 灰度分批的依据是什么？为什么 `serial: 1` 不等于安全？**

- 判定：批次大小由余量决定（不超过"总容量 − 最小可接受容量"）；观察时间要覆盖一个业务周期与 2~3 个采样间隔。
- 为什么：`serial: 1` 只是串行；如果每台都改动同一个共享依赖（数据库、证书、配置中心），或者第一批就是核心实例，仍然会全断。
- 落点：批次要同时覆盖实例与故障域两个维度。

**9.4「拔掉一台业务还剩多少」怎么算？脑裂时应保可用还是保一致？**

- 判定：查四件事——是不是单实例、流量会不会切、切换时连接会不会断、剩余容量够不够（N+1/N+2）；并看故障域是否重叠。
- 脑裂取舍：默认保一致（判定不确定时停服务），或用 fencing 强制一方下线；写服务尤其如此。
- 不要做：不要把"配了 VIP"当成高可用。

**9.4 事故响应的前三步是什么？复盘六段是什么？**

- 前三步：分级与通报 → 止损（按可逆性排序）→ 取证（可由并行的一条线完成）；根因留给复盘。
- 复盘六段：时间线、影响面、证据、根因、止损动作、改进项（注意它与答题用的"六段骨架"不是同一套）。
- 落点：改进项要写成"动作 + owner + 期限 + 验收方式"；"人为失误"不算根因。

**9.5 机器疑似被入侵时，处置与取证的顺序是什么？**

- 分层：账号与认证层 → 权限与提权面 → 网络与进程层 → 持久化层（计划任务与自启）。
- 证据：`who`、`last`、`journalctl -u ssh`、`ss -tunap`、`ps auxf`、`find / -perm -4000`、`getcap -r /`、`systemctl list-timers`、`crontab -l`、`ls -l /etc/cron*`。
- 结论候选：① 弱口令或密钥泄漏；② 提权面被利用（SUID 或 capabilities）；③ 未发现的持久化点；④ 误报（要用证据排除，不能靠感觉）。
- 止损：**先隔离而不是先清理**——保住现场（快照、镜像、日志导出），再按流程通报。
- 不要做：不要在取证前 `kill` 进程、删文件或重启——那会毁掉全部现场。

## 10. 首轮建议完成的题组

第一轮建议只做**内存线（第 4 组）、持久线（第 5 组）、连接线（第 6 组）、约束环（第 7 组）**——这四组覆盖"内存压力""容量与 IO""网络分层""上限配在哪一层"，是值班与现场出现频率最高的部分；其余五组在第二轮交错进行。

理由不是"其它不重要"，而是**交错的收益来自混排**：第二轮把前提组、启动链路组与观察面组混进上面四组里做，才会真正考出"先分类"的能力。

## 常见误解

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 一边看题一边看答案 | 退化为识别练习；正确口径难以转化为实际能力 |
| 只做眼熟的题 | 薄弱的题被跳过，摸底失效 |
| 不为答案定档 | 无法排序，也无法判断需要补哪一层 |
| 一次完成全部题目 | 后段疲劳会影响数据质量；按线分组进行，每组控制在 20~25 分钟 |
| 答完不写错题清单 | 这一轮的产物为零；下一轮还会犯同样的错 |
| 把未实测的答案当实测 | 换环境后会被推翻；未实测的部分要照实标注 |
| 按线做却仍按章翻答案 | 第一问应当是"这属于哪条线"，翻答案时才回章节 |

## 要点自测

- 这套题库为什么按线分组而不是按阶段分组？
- 四档评分里哪一档最危险？为什么它要按"完全不会"处理？
- B 档（有结论无证据）最有效的补法是什么？C 档呢？
- 第一轮为什么建议先做内存、持久、连接、约束环四组？
- 为什么"缺的那一层"要单独记一列？它决定什么？
- 答完一组之后，如果全是 A，下一步该做什么？
