# 附录：闭卷题库

这本题库共六十九道闭卷题，它们按**四条线、约束环、观察面与组织层**这几组来划分，而不按学习阶段分组。开头的另外两组题不属于四条线中的任何一条，它们分别是环境与证据组、启动链路组。

若按阶段出题，作答者可能已经预先知道"这道题考查的是内存"；因此本题库改为按线出题，此时作答的第一步始终是判断"这个问题属于哪一条线"，因为真实告警不会预先给出它所属的章节。

题源全部来自前 11 章，因此每道题的答案都能在对应的阶段里找到出处。若这里的说法与对应阶段冲突，则以对应阶段为准，并将冲突记入错题清单。

## 0. 使用纪律

1. **闭卷、限时、书面作答**。每一组的题量在 5~13 题之间，因此要按 20~25 分钟一段把它拆开完成，而不要连续完成整组；若某道题无法作答，则写"空白"，不要猜测。
2. **先写出答案，再对照下方的答案要点**。作答之前先为答案定档，四档分别是：A 表示能脱稿讲，B 表示有结论无证据，C 表示认得但讲不出，D 表示完全不会。
3. **每题答完写一行"缺的那一层"**。答完之后，你要从结论、判据、证据、边界与代价这五项里选出缺失的那一项写下来。
4. **不写"看情况"**。若你写不出条件，那就说明这一条你还没有学会。

答完之后按这一组的结果定档：

| 结果 | 说明 | 下一步 |
| --- | --- | --- |
| 该组全部为 A | 这一组题说明这条线已经达到"能脱稿讲" | 因此下一步应当转向你还不熟的那条线 |
| 多数为 B（有结论无证据） | 这一档说明缺的是证据层 | 因此要回到对应阶段执行一次相关命令，把结论补全成同时含结论、命令与数值形态的完整写法 |
| 多数为 C（认得但讲不出） | 这一档说明缺的是提取训练 | 因此要按"完全不会"处理，重读该线对应的原理篇，再写一页纸 |
| 多数为 D | 这一档说明缺的是结论层 | 因此要从对应的原理篇重新完整执行一次，不要直接做下一组 |

## 1. 前提组（环境、版本与证据）

**1.1 实验机与生产机的最低要求是什么？为什么"能快照"还不够？**

- 判定：最低要求有三条，即这台机器要能快照、要能进入控制台（或带外管理），并且要与生产环境隔离。
- 为什么不够：因为快照只提供回滚能力，而控制台提供的是"网络或 `fstab` 被改坏之后唯一还能进去的那条路"，所以若只管快照而不留控制台，一次演练就可能让这台机器失去所有可用的进入通路。

**1.2 版本基线四件套是什么？命令分别是什么？**

- 判定：版本四件套指的是发行版、内核、systemd 与 cgroup，它们对应的命令分别是 `cat /etc/os-release`、`uname -r`、`systemctl --version | head -1` 与 `stat -fc %T /sys/fs/cgroup`。
- 实测参照（转引阶段 1、7）：本库实验机的这四项依次为 `Ubuntu 24.04.5 LTS`、`6.8.0-139-generic`、`systemd 255` 与 `cgroup2fs`。
- 边界：若这四项没有记录，则后面所有关于"默认值"的讨论都失去了意义。

**1.3 为什么内核版本号不能跨发行版直接比大小？**

- 判定：因为发行版会把新特性回移（backport）进较老的主线版本，所以内核版本号只反映主线基线，不反映这台机器实际具备哪些特性。
- 证据：RHEL 9 的基线内核是 5.14、Ubuntu 24.04 是 6.8、Debian 12 是 6.1，但 RHEL 的 5.14 含大量回移特性。
- 落点：因此讨论版本差异时，要以该发行版的 release notes 为准。

**1.4 `error while loading shared libraries` 出现时，应当按哪四步处理？**

- 判定：处理顺序分四步——第一步用 `ldd` 查出缺的是哪个库；第二步用 `ldconfig -p` 或包管理确认这个库装没装；第三步检查 `/etc/ld.so.conf.d/` 里的搜索路径对不对；第四步在 `ldconfig` 之后复验。
- 边界：`LD_LIBRARY_PATH` 只影响当前进程树，所以它不是持久的修法。
- 不要做：不要直接把库文件拷到 `/lib` 就当作修好了。

**1.5「重启能解决 90% 的问题」这句话的问题在哪？变更之前要做哪三件事？**

- 判定：重启会毁掉现场；若历史日志又没有持久化，那么重启的代价尤其致命。
- 变更前三件事：变更之前要做三件事，分别是带时间戳的备份、写下来的回滚命令与确认过的时间窗。
- 落点：因此要先取证再决定是否重启；其中 `journalctl -b -1` 的有效性依赖日志持久化。

## 2. 启动链路组

这一组不属于四条线中的任何一条：机器起不来时，四条线都不在服务，因此问题落在"当前是哪一段启动阶段在运行、控制权移交到了哪一步，以及移交在哪里中断"。

**2.1 启动链的五个阶段是什么？每个阶段失败时的现场在哪？**

- 判定：这五个阶段依次是固件、引导加载器、内核与 initramfs、systemd、登录与服务。
- 现场：固件阶段的现场是物理屏与带外日志；引导加载器阶段的现场是 `grub>` 或 `grub rescue>`；内核与 initramfs 阶段的现场是 `dracut:/#` 之类的 initramfs shell；systemd 阶段的现场是 `emergency.target` 与 `journalctl -xb`。
- 第一反应不要是什么：第一反应不要先问"怎么修"，而要先问"**现在是谁在输出**"，因为输出者决定了当前所处的阶段。

**2.2 initramfs 的职责是什么？内核升级后起不来最常见的原因是什么？**

- 判定：initramfs 的职责是把"挂载真正根文件系统所需的驱动"装进内存，并在挂上真根之后执行 `switch_root`。
- 常见原因：要么新内核没有对应的存储或文件系统模块，要么 `root=` 指向的设备对不上（例如 UUID 变了或控制器变了）。
- 落点：一旦改动了根设备或存储控制器，就必须重建 initramfs，并在实验机上重启验证。

**2.3 两套"内核参数"指什么？改启动参数的验收标准是什么？**

- 判定：两套"内核参数"指的是启动参数与运行时参数——启动参数记录在 `/proc/cmdline` 里，且只在启动那一刻生效；而运行时参数由 `sysctl` 管理。
- 验收：验收标准是 `cat /proc/cmdline` 里能看到新参数；若只看 `/etc/default/grub`，则不算通过验收。
- 边界：Debian 系要执行 `update-grub`，而 RHEL 系要用 `grub2-mkconfig`（或 `grubby`）。

**2.4 内核 panic 后现场在哪？为什么不能先重启？**

- 判定：panic 之后的现场在 `journalctl -b -1 -k`、`/var/crash/`、`dmesg` 的上一轮引导段与带外日志里；只有配置了 kdump 才会有 `vmcore`。
- 为什么：因为重启会覆盖内存现场与未持久化的日志，所以"再重启一次看看"是最常见的毁现场动作。
- 未实测：panic 实验需要一台允许崩溃、并且能在崩溃后自救的实验机与控制台；由于本库实验机只有 SSH 一条通道，`kdump` 为 `inactive`、`kernel.sysrq` 的值不含 panic 位、`/var/crash/` 为空，一旦做坏就无法自救，因此不做这项实验。
- 止损：先让其他节点承接业务（高可用视角），再决定是否分析 `vmcore`；结论候选的排查顺序是：先看驱动或硬件，再看内核问题，然后看内存故障，最后看前一次变更；同时要与变更时间线对齐。
- 不要做：不要读几秒日志就下"内核 bug"的结论，也不要忘记对齐变更记录。

**2.5 `emergency.target` 与 `rescue.target` 的区别是什么？**

- 判定：两者的区别在于挂载了多少文件系统、要拉起多少单元；`emergency` 更小，它通常只挂根，并要求输入 root 密码，而 `rescue` 会拉起更多基础服务。
- 落点：当 `fstab` 被写坏时，机器通常落在 emergency，或者直接进入维护 shell。
- 不要做：不要在紧急模式里盲目重启，而要先把 `journalctl -xb` 的输出取下来。

## 3. 算力线

**3.1 性能排障的方法论顺序是什么？第一步做什么？**

- 判定：方法论顺序是先量化影响面，再分层排除，最后才动手。
- 第一步：这一步要回答五个问题，即谁受影响、多严重、从几点开始、还在不在恶化，以及与什么作比较。
- 实测参照（转引阶段 10）：单个自旋进程让一个核达到 100%，而整机 `%usr` 只有 25.00%（也就是 4 vCPU 的 1/4）、`load` 只有 0.34。

**3.2 `load average` 到底是什么？为什么要除以核数？**

- 判定：它是处于可运行状态与不可中断睡眠状态（`D`）的任务数的平均值，因此它包含正在等 IO 或等锁的进程。
- 判据：只有它与核数之比持续大于 1 时才值得追；同时要一起看 `vmstat` 的 `b` 与 `wa`，用来定位负载的来源。
- 不要做：不要用"`load` 高就是 CPU 忙"这句话下结论。

**3.3 CPU 高的五个分支是什么？`vmstat` 的 `si` 为什么容易看错？**

- 判定：这五个分支是 `us`（用户态）、`sy`（内核态）、软中断（`%soft`）、`wa`（IO 等待）与 `st`（被虚拟化偷走）。
- `si` 的误区：`si` 的含义是**换入**（swap in），它不是软中断；要看软中断应当看 `mpstat` 的 `%soft`。
- 边界：`mpstat` 文档明确指出 `%sys` **不含**硬中断与软中断的时间，因此中断占用的核要看 `/proc/interrupts`。
- 落点：这五个分支各自对应不同的下钻工具，即 `perf`、`pidstat` 与 `/proc/interrupts`。

**3.4 自愿切换与非自愿切换分别说明什么？**

- 判定：自愿切换（voluntary）指进程主动让出 CPU，常见原因是等 IO、等锁或 sleep；非自愿切换（involuntary）指进程被抢占，原因是时间片用尽或优先级竞争。
- 实测参照（转引阶段 10）：socket ping-pong 场景实测自愿切换 **40,343.67** 次/秒、非自愿 **16.67** 次/秒。
- 判据：若非自愿切换偏多，则说明存在同核竞争或核数不足；若自愿切换偏多，则说明进程在等锁、等 IO，或者切换开销本身就已经很高；这两类都要看 `vmstat` 的 `cs` 与 `pidstat -w`。

**3.5 火焰图看什么？什么时候看不了？**

- 判定：它是采样堆栈的聚合图，其中横轴是样本占比（而不是时间轴），纵向是调用栈深度，因此宽条代表该函数在采样中出现得多。
- 用途：它用来找 on-CPU 热点；若要查 off-CPU 等待，则要看 off-CPU 火焰图或 `/proc/<pid>/wchan`。
- 前提：使用它需要符号（debuginfo 或符号表）与采集权限；因此当进程在容器里、机器没有 PMU，或 `perf_event_paranoid` 受限时，可能采不到样本。
- 不要做：不要把横轴当时间线读，也不要只看一张图就下结论。

**3.6 `D` 状态进程与僵尸进程分别为什么 `kill -9` 杀不掉？判据是什么？**

- 判定：`D` 状态进程卡在内核态的不可中断等待里，发送给它的信号会被挂起，要等它回到用户态才会被处理；僵尸进程则已经终止，它等的是**父进程**来回收。
- 判据：要读的是 `ps -o stat,wchan` 给出的 `D` 状态的 `wchan`，再加上父进程状态与 `ps -o stat,ppid` 的输出。
- 不要做：不要对 `D` 状态进程反复执行 `kill -9`，而要先查它在等什么（IO、网络存储或锁）。

**3.7 `SIGTERM` 与 `SIGKILL` 的区别？退出码 128+N 是什么意思？**

- 判定：`SIGTERM` 可以被捕获，因此进程可以借此优雅退出；`SIGKILL` 不可捕获、不可阻塞，也不可忽略。
- 128+N：它表示进程被信号 N 杀死时 shell 给出的退出码，因此 143 对应 TERM、137 对应 KILL。
- 边界：137 并不能证明进程死于 OOM；要判断 OOM，必须看内核日志与 `memory.events`。

**3.8 进程数达到上限或句柄耗尽时，应当按什么顺序排查？**

- 判定：排查顺序是先确认撞到的是哪一类上限（`pids.max`、`LimitNOFILE` 或 `fs.file-max`），然后再定位是谁在消耗它。
- 证据：要读的是 `systemctl show -p TasksMax,LimitNOFILE`、`/proc/<pid>/limits`、`lsof -p <pid>` 与 cgroup 的 `pids.current`。
- 边界：任务数这一类上限同时存在四个不同的数，即 unit 的 `TasksMax` 与 cgroup 的 `pids.max`、进程的 `RLIMIT_NPROC`、内核的 `threads-max` 与内核的 `pid_max`；由于它们各自由不同机制生效，所以不要把这几者混为一谈。
- 不要做：不要为了恢复服务就直接调大内核全局上限，因为那样做只是掩盖了泄漏。

**3.9 进程与线程在计数与调度上有什么区别？**

- 判定：内核调度的基本单位是 task；由于一个进程可以包含多个 task（也就是线程），所以它们共享地址空间，但每一个 task 各自被调度。
- 证据：`ps -e` 数的是进程，而 `ps -eLf` 数的才是 task；因此 cgroup 的 `pids.current` 计的是 task。
- 边界：`TasksMax=` 与 `pids.max` 限制的是 task 总数，因此调整它时要按线程规模来算，而不能按进程数来算。

## 4. 内存线

**4.1 `free` 显示可用内存很少，说明内存不够吗？**

- 判定：`free` 显示的可用内存很少并不等于内存不够；判据是读 `MemAvailable`，它表示在不触发换页的前提下还能申请到多少内存，同时还要看内存压力，也就是 PSI（`/proc/pressure/memory`）。
- 实测参照（转引阶段 10，条件以该阶段为准）：分配并触碰 3 GiB 之后，`MemAvailable` 从 7224 MiB 降到 4145 MiB，而 PSI 的 `avg10/60/300` 全程为 0（累计 `total` 在涨）。
- 不要做：不要因为 `free` 显示的数值少就去重启服务、加内存或清缓存。

**4.2「申请」和「占用」有什么区别？`VSZ` 很大而 `RSS` 很小说明什么？**

- 判定：`malloc` 与 `mmap` 只是对虚拟地址的承诺，因此进程要等到首次写入时，才通过缺页拿到物理页。
- 说明：`VSZ` 很大而 `RSS` 很小，说明进程承诺了地址空间但还没有落地（也可能只是保留映射），因此不能据此判断泄漏。
- 边界：判断泄漏只能看趋势（用 `pidstat -r` 或历史监控），因为单次快照说明不了任何问题。

**4.2 Page Cache 什么时候会变成问题？观测指纹是什么？**

- 判定：当脏页积压、回写跟不上时，写进程就会被按在脏页限流上等待。
- 现场：此时 `wa` 高、`w_await` 与 `aqu-sz` 上升，进程进入 `D` 状态，并且 `/proc/meminfo` 的 `Dirty` 与 `Writeback` 偏高。
- 不要做：不要把"缓存占用高"当作内存不足来处置。

**4.3 `vm.swappiness=0` 等于关闭 swap 吗？关掉 swap 的代价是什么？**

- 判定：`vm.swappiness=0` 不等于关闭 swap，它只是回收倾向的权重；若要真正禁用 swap，只能用 `swapoff`，或者把 cgroup 的 `memory.swap.max=0` 设上。
- 代价：关掉 swap 的代价是把"换页变慢"换成"被 OOM 终止"。
- 落点：因此选哪一边取决于业务对延迟与可用性的偏好，这不是"哪个默认值更好"的问题。

**4.4 OOM 的判定证据是什么？容器 OOM 与整机 OOM 有什么区别？**

- 判定：证据是内核日志里的 OOM 记录加 cgroup v2 的 `memory.events`；**退出码 137 不是证据**。
- 区别：容器级的 OOM 要看 `memory.max`、`memory.current` 与 `memory.events`；整机级的 OOM 则要看 `MemAvailable`、PSI 与内核日志。
- 落点：由于容器化环境里很多 OOM 只发生在 cgroup 级，所以整机在同一个时刻可能还有空闲内存。

**4.5 怎么区分内存"用得多"和"有压力"？PSI 是什么？**

- 判定：判断"用得多"要看 `MemAvailable` 与缓存的构成；判断"有压力"要看 PSI，也就是 `/proc/pressure/memory` 的 `some` 与 `full`，同时还要看 `si`、`so` 与回收计数。
- 实测参照（转引阶段 10）：触碰 3 GiB 之后，`MemAvailable` 从 7224 MiB 降到 4145 MiB（降了 3079 MiB），而 PSI 的 `avg10/60/300` 全程为 0。
- 落点：这一项是只读观测，因此在生产机上也可以做。

**4.6 PSI 的 `avg*` 与 `total` 各是什么单位？为什么必须分清？**

- 判定：`avg10/avg60/avg300` 是被压力拖慢的时间占比，单位是百分比；`total` 是累计的停顿时间，单位是微秒。
- 判据：`avg` 用来看"现在有多严重"，而 `total` 要取差值，用来看"这一段时间内有没有真的发生"。
- 不要做：不要把两个单位不同的量放在一起比大小，也不要把它们画在同一条曲线上。

**4.7 内存回收与设备 IO 为什么会互相拖慢？判据是什么？**

- 判定：内存回收最终要落到设备上，因为匿名页要换出到 swap、文件页要回写；因此一旦设备忙，回收就变慢，分配者转入直接回收，表现为延迟尖刺。
- 判据：`/proc/vmstat` 的 `pgscan_direct` 取差值后在增长，**同时** `iostat -x` 的 `await` 在上升；由于只有两者同时出现才是"回收造成 IO 压力"的证据，所以不能只看其中一个。
- 不要做：不要只看到其中一个信号就定性，也不要用加内存的办法去治设备排队。

**4.8 为什么"内存占用"可以有好几个数？各口径什么时候用？**

- 判定：常驻集（`RSS`）会按使用者重复计数共享页；均摊（`PSS`）则把共享页按使用者数量分摊；而私有页只算进程独占的那部分。
- 用法：横向比较"谁占得多"时用均摊口径，判断"释放这个进程能回收多少"时用私有页口径，而要看整机的可用内存时则用 `MemAvailable` 与 `free`。
- 不要做：不要用一个口径的数字去回答另一个口径的问题。

**4.9 大页是否生效看哪个字段？为什么它容易看错？**

- 判定：判断透明大页是否生效要看 `/proc/meminfo` 的 `AnonHugePages`，它统计的是匿名大页，单位是 KiB。
- 为什么容易看错：因为页表项数量（`VmPTE`）受映射数量以及小页与大页混用的影响，所以它不能反推大页是否生效；要判断大页是否生效，必须单独看大页自己的计数。
- 边界：大页按 2 MiB 落地会放大内存占用，同时 `khugepaged` 的后台整理会带来停顿。

## 5. 持久线

**5.1 存储的四层是什么？`lsblk`、`df`、`du` 各回答什么问题？**

- 判定：存储的四层从下到上依次是块设备、分区或 LVM、文件系统与挂载点。
- 分工：`lsblk` 用来读设备与挂载关系，`df` 用来读文件系统的容量与已用块计数，而 `du` 用来读目录树里的实际占用。
- 不要做：不要把三个工具的输出混着解释，因为它们回答的是三个不同的问题。

**5.2 `df` 和 `du` 对不上，通常有哪四类原因？**

- 判定：这四类原因分别是文件已被删除但仍被进程持有（用 `lsof +L1` 确认）、目录被挂载覆盖、文件系统的保留块与元数据、稀疏文件与延迟分配。
- 实测参照（转引阶段 9）：删除一个仍被持有的 **10 MiB** 文件之后，`df` 的已用从 24576 字节涨到 10510336 字节，而 `du -sh` 只有 **20K**。
- 落点：由于这四类的处置完全不同，所以要逐个排除，而不能互相否定。

**5.3「有空间却写不进去」有哪四种原因，各自的判据是什么？**

- 判定：这四种原因与判据分别是容量满（用 `df -h` 判）、inode 满（用 `df -i` 判）、ext4 保留块（默认占 5%），以及配额到顶（此时报 `Disk quota exceeded`）。
- 落点：因此要先看报错文本，再选对应的工具——`No space left on device` 与 `Disk quota exceeded` 的含意不同；而空间满与 inode 满的报错文本相同，只能靠两个 `df` 来区分。
- 不要做：不要一看到"空间"就去删文件。

**5.3 ext4 与 XFS 的核心差别是什么？**

- 判定：ext4 的 inode 数量在 `mkfs` 时就固定，它能缩容，但必须卸载而且风险高；XFS 使用动态分配的 64 位 inode，因此只能扩不能缩，在线扩容非常方便。
- 落点：生产上常见"XFS + LVM"的组合。
- 边界：两者的修复都必须在卸载或只读挂载下做，因为 XFS 默认拒绝对已挂载的设备操作。

**5.4 根文件系统变成只读时应当按什么顺序处置？第一反应不要做什么？**

- 判定：处置顺序是先查原因（`dmesg` 里的 ATA、SCSI 或 NVMe 错误，以及阵列状态），再把业务切走，然后决定是修还是重建。
- 判据：这台机器"遇到错误会不会自己转只读"由超级块里的 `errors=` 设置决定，因此要用 `tune2fs -l <设备>` 现场取这个值，而不能凭印象说"内核一定会保护"。
- 不要做：不要执行 `mount -o remount,rw`，因为那会把保护关掉，并可能扩大损坏。

**5.5 LVM 与云盘扩容的完整链路是什么？扩容后验收看什么？**

- 云盘与分区链：先在平台侧扩卷，再用 `growpart /dev/sdX N` 扩分区，最后用 `xfs_growfs /mount`（XFS）或 `resize2fs`（ext4）扩文件系统。
- LVM 链：底层变大之后，先用 `pvresize /dev/sdXN` 扩容物理卷，再用 `lvextend -r -l +100%FREE /dev/vg/lv` 扩容逻辑卷，其中 `-r` 会顺带扩文件系统。
- 验收：只有 `df -h` 看到了新容量才算完成；由于 `lsblk`、`pvs`、`vgs` 与 `lvs` 只能证明前面几步，所以不能拿它们当验收。
- 不要做：不要对 XFS 尝试缩容；同时在操作前先确认业务能承受。

**5.6 RAID 0/1/5/6/10 怎么取舍？RAID 5 到底能防什么？**

- 取舍：RAID 0 没有冗余，因此任意一块盘坏掉就会全部丢失；RAID 1 做镜像，因此容量减半，但能容单盘故障；RAID 5 用单校验，也能容单盘故障，但写惩罚明显；RAID 6 用双校验，因此能容两块盘同时故障；RAID 10 是镜像加条带，容量减半，性能与恢复最好，但成本最高。
- RAID 5 的边界：它只容忍单盘故障，因此重建期间再坏一块就会丢数据，而大容量盘的重建时间很长，所以**重建窗口就是风险窗口**。
- 巡检：用 `cat /proc/mdstat` 与 `mdadm --detail /dev/mdX` 看阵列状态，并用 `smartctl` 看介质错误。
- 不要做：不要把 RAID 当备份，因为它不防误删、勒索加密与逻辑损坏。

**5.7 `await`、`aqu-sz`、`%util` 各是什么？为什么它们可以互相矛盾？**

- 判定：`await` 是平均等待时间，单位是毫秒，其中含排队时间；`aqu-sz` 是平均队列长度，单位是个请求；`%util` 是有 IO 在飞行的时间比例。
- 矛盾的原因：因为这三者描述的是不同维度，所以它们可以互相矛盾；Little's law 可以把 `w/s × w_await` 与 `aqu-sz` 对齐（**转引**阶段 10 实测：324 × 0.00659 s = 2.14，同窗口 `aqu-sz` 实测 2.14）。
- 落点：判断设备是否饱和要把这几个量连起来读，并对照业务延迟。

**5.8 `copytruncate` 与 `create` 的区别？为什么要在 `postrotate` 里让应用重开文件？**

- 判定：`copytruncate` 保持 inode 不变，代价是存在一个丢日志的窗口；`create` 会换一个新 inode，但持有旧 fd 的进程会继续往归档文件里写。
- 实测参照（转引阶段 9）：执行 `copytruncate` 之后 inode 没有变，前后都是 `1310736`；执行 `create` 之后 inode 换了，新文件是 `1310803`、归档是 `1310798`，随后有 9 行被写进归档、新文件里是 0 行。
- 落点：因此要在 `postrotate` 里执行 `systemctl reload` 或发信号，让应用重新打开文件。

**5.9 日志把磁盘写满时，先做什么？`rm` 掉被持有的文件会怎样？**

- 判定：先看是谁在写、文件是否仍被进程持有，然后再决定清理与限流。
- 证据（转引阶段 9 实测）：`rm` 一个仍被持有的 **10 MiB** 文件之后，`df` 的已用反而从 24576 字节涨到 10510336 字节；`/proc/<pid>/fd/4` 显示 `(deleted)`，只有关掉这个 fd 之后，已用才回落到 24576 字节。
- 落点：因此处置要同时安排三件事，即 `logrotate`、`SystemMaxUse` 与容量告警。

**5.10 同一个容量问题，为什么内核与工具会给出两个不同的视角？**

- 判定：块层看的是"提交到设备的字节"，文件系统看的是"文件占用的块"，而用户看的是 `df` 给出的使用率；由于页缓存、已删除但仍被持有的文件、保留块与稀疏文件都会让这三者不一致，所以同一个容量问题会出现两个不同的视角。
- 证据：可以对照 `df -h` 与 `du -xsh` 的差值、`lsof +L1` 给出的持有者、`/proc/meminfo` 的 `Dirty` 与 `Writeback`，以及 `tune2fs -l` 给出的保留块设置。
- 落点：因此要先判定"是哪两个视角不一致"，再选工具；"写成功"的三种含义（进缓存、进设备缓存、`fsync` 返回）是同一个道理在写入路径上的版本，完整对照见《高频误判对照表》持久线一节。

## 6. 连接线

**6.1 一次连接经过哪六个阶段？为什么"先分层"是唯一可靠的方法？**

- 判定：这六个阶段依次是解析名字、拿到地址、建立连接、传输数据、断开连接与链路本身（链路还要延伸到出门之后的那一段）。
- 为什么：因为 `ping` 通不等于 TCP 能连，TCP 能连也不等于应用正常，而且每一层的失败形态与证据都不同，所以先分层是唯一可靠的方法。
- 落点：因此要按"链路与驱动、IP 与路由、端口与过滤、解析、应用"的顺序自下而上看。

**6.2 服务端的两个队列是什么？队列上限怎么算？"静默丢 SYN"的证据在哪？**

- 判定：服务端有两个队列，即半连接队列（`SYN_RECV`）与全连接队列；其中全连接队列的上限是 `min(backlog, somaxconn)`。
- 证据：在 `ss -lnt` 的输出里，`Recv-Q` 是当前队列深度，而 `Send-Q` 是队列上限；溢出计数在 `nstat` 的 `TcpExtListenOverflows` 与 `ListenDrops` 里，它们都是累计值，因此要看差值。
- 边界：内核判断"队列满"用的是 `Recv-Q > Send-Q`，也就是说它允许比上限多排一个；因此一旦读到 `Recv-Q >= Send-Q`，就说明队列已经满了，而"溢出过多少次"这件事本身仍然只能看 `nstat` 的增量。
- 实测参照（转引阶段 6）：`listen(10000)` 在 `somaxconn=4096` 的机器上被静默截断成 4096。

**6.3 `TIME_WAIT` 与 `CLOSE_WAIT` 有什么区别，各应如何处置？**

- 判定：`TIME_WAIT` 是主动关闭方的正常状态，Linux 上固定持续 60 秒；而 `CLOSE_WAIT` 表示应用收到了 FIN 却没有调用 `close()`。
- 处置：`TIME_WAIT` 只能通过连接复用来缓解；`CLOSE_WAIT` 只能改应用。
- 不要做：不要试图用 `tcp_fin_timeout` 去改 `TIME_WAIT`，因为它管的是 `FIN_WAIT2`。与之相关的 sysctl 有的是"影响数量"而不是"改时长"：`tcp_max_tw_buckets` 限制同时存在的数量，超限时会直接关闭并告警，而 `tcp_tw_reuse` 允许在安全条件下复用——所以准确的说法是"改不了时长，但可以影响数量与复用"。

**6.4 `tcp_syncookies` 起什么作用？它会让哪个计数增长？**

- 判定：当半连接队列满时，`tcp_syncookies` 让内核改发 cookie，从而避免直接丢掉 SYN。
- 计数：它会带动增长的计数是 `TcpExtSyncookiesSent` 与 `TcpExtTCPReqQFullDoCookies`；**`ListenDrops` 不一定增长**。
- 边界：只有关掉 syncookies，丢 SYN 才会变成真正的丢包。

**6.5 不抓包怎么判断链路质量？`ss -ti` 里看哪几个字段？**

- 判定：要看的字段是 `rtt`、`minrtt`、`cwnd`、`retrans`、`pacing_rate`、`delivered` 与 `app_limited`。
- 实测参照（转引阶段 6）：本机连接实测 `rto:201 rtt:0.028/0.012 mss:1448 ... cwnd:10 ... minrtt:0.004`（不同连接的 `rtt` 在 0.007~0.089 之间、`minrtt` 在 0.001~0.012 之间，**单位毫秒**）。
- 落点：一旦出现 `app_limited`，就说明"慢"不在网络上。

**6.6 `ss -ti` 的 `rtt` 与 `iostat` 的 `await` 能直接比吗？**

- 判定：不能直接比，但原因不是单位不同——`ss` 文档写明 `rtt` 与 `rttvar` 的单位是**毫秒**，与 `await` 相同；不可比的原因是**对象不同**：一个是单条连接的往返时间，一个是设备的平均单次请求耗时（含排队），而 `%util` 又是设备忙碌占比。
- 用法：`rtt` 要与同一条连接的 `minrtt` 比，差距大就说明路径上有排队；而 `await` 要与同一设备的历史基线比。
- 不要做：不要跨对象地比较两个"看起来都是时间"的数字，也不要把 `%util` 当成饱和度。

**6.7 域名解析为什么会出现"同一个名字、两个结果"？**

- 判定：因为应用走的是 `getaddrinfo()`（经 NSS，也就是名字服务开关），而 `dig` 直接问 DNS，所以这两条路径本来就不同；同时 `/etc/hosts`、`resolvectl` 的缓存、`search` 与 `ndots` 的放大都会造成差异。
- 证据：把 `getent hosts <name>` 与 `dig <name>` 的输出对照起来看，并用 `resolvectl statistics` 看缓存命中。
- 边界：容器内有自己的 `/etc/resolv.conf` 与 `nsswitch.conf`，因此宿主的结果不能代表容器。

## 7. 约束环

**7.1 排查一个服务时要读哪三类记录？`systemctl status` 的三段各自对应什么？**

- 判定：要读的三类记录是 unit 文件、cgroup 文件与 journald 日志；其中 unit 文件描述这个服务应该怎样运行，cgroup 文件记录它能用多少资源，而 journald 保存它运行过程中的证据。
- 对应：`systemctl status` 的三段里，`Loaded` 对应 unit 与配置，`Active` 对应判定出的状态，而 `CGroup` 对应进程与资源。
- 落点：因此排障的第一反应是把这三段读全。

**7.2 改 unit 文件之后，完整生效链条是什么？**

- 判定：完整生效链条分三步——改了文件之后，`status` 会出现 changed on disk 警告，此时 manager 仍是旧值；执行 `daemon-reload` 之后 manager 变成新值，但**运行中进程的环境仍是旧值**；只有执行 `restart` 之后才是新值。
- 验收：读生效值要用 `systemctl show -p ...`，因此不要只看文件。
- 不要做：不要把 `daemon-reload` 当成重启。

**7.3 `Wants=` 与 `After=` 有什么区别？`Type=` 为什么重要？**

- 判定：`Wants=` 与 `Requires=` 决定要不要拉起对方；而 `After=` 与 `Before=` 只决定顺序，若不写 `After`，则几个单元会并行启动。
- `Type=`：`Type=` 决定"什么算启动完成"，因此选错就会出现"假启动失败"，例如 `simple` 遇到后台化的进程时会立刻变成 `inactive (dead)`。
- 落点：`Type=notify` 默认用 `NotifyAccess=main`，因此子进程发出的通知会被拒，服务一直等到超时（**转引**阶段 8 实测：改成 `NotifyAccess=all` 后 0.0396 秒启动成功）。

**7.4 服务资源上限的落点在哪？给出三个实际值例子。**

- 判定：服务资源上限的落点是 unit 里的 `LimitXXX=`、`MemoryMax=` 与 `CPUQuota=`；因此不要去改 `limits.conf`。
- 例子：`LimitNOFILE=64` 会让服务内的 `ulimit -n` 为 64；`MemoryMax=32M` 会让 `memory.max=33554432`；`CPUQuota=10%` 会让 `cpu.max=10000 100000`。
- 边界：**unit 文件里写的值与进程实际拿到的值可能不同**——`systemctl show -p LimitNOFILE` 读到的是 unit 配置，而进程真实生效的软/硬上限要看 `/proc/<pid>/limits`；两者之间还夹着编译期默认值（如 `DefaultLimitNOFILE=`）。由于本库实验机上这两个数确实不同，所以"上限到底是多少"要两处都看。
- 边界：容器发生 OOM 时，cgroup 的 `memory.max` 与 systemd 的 `OOMPolicy=` 会决定是整个 unit 停掉，还是只杀进程。

**7.5 systemd timer 与 cron 有什么差别？各自的误区是什么？**

- 判定：timer 具有依赖、日志与 `Persistent=`（补跑）语义，而 cron 的环境极简。
- 误区：因为 cron 的非交互 shell 不读 `.bashrc`，所以它的 `PATH` 与别名都与登录 shell 不同，而且 `%` 要写成 `\%`；此外 tmpfiles 的 age 默认同时看 mtime、atime 与 ctime。
- 落点：定时任务排障要先看"它到底跑没跑"，再看"它跑在什么环境里"。

**7.6 资源限制的五层是什么？改错层会有什么后果？**

- 判定：技术上限有四层，依次是会话层（它有 `ulimit` 与 `limits.conf`/PAM 两条来路）、unit 的 `LimitXXX=`/`TasksMax=`（针对服务）、cgroup（针对整组）与内核全局；此外还有第 5 层"组织层"（审批、窗口、冻结期），它不配置上限，只决定这些上限现在能不能改。
- 后果：由于实际生效的是前四层里最紧的那一层，所以改 `/etc/security/limits.conf` 对 systemd 服务无效，这是最高频的出错点。
- 落点：服务类问题要先读 `systemctl show -p LimitNOFILE,TasksMax`，再读 `/proc/<pid>/limits` 与 cgroup 里对应的文件。

**7.7 namespace 与 cgroup 各管什么？**

- 判定：namespace 管的是"进程看得见什么"，而 cgroup 管的是"进程能用多少"。
- 容器定义：一个容器由 namespace、cgroup、根文件系统与权限约束（capabilities、seccomp 与 MAC）四部分构成，因此少任何一层都不成其为容器。
- 边界：容器与虚拟机共享同一个内核。

**7.8 `Permission denied` 可能来自哪五层？用什么命令分层看？**

- 判定：`Permission denied` 可能来自五层，即 DAC 位、ACL、capabilities、挂载选项与 SELinux/AppArmor。
- 命令：分层看时依次用 `namei -l <path>`、`getfacl`、`getcap`、`findmnt`、`ls -Z` 与 `ausearch -m AVC`。
- 不要做：不要一上来就执行 `chmod 777` 或 `setenforce 0`。

**7.9 文件的 `rwx` 与目录的 `rwx` 语义有什么不同？**

- 判定：文件的 `x` 表示"可执行"；而目录的 `x` 表示"能穿过"，目录的 `r` 才是"能列出名字"。
- 关键推论：因此删除文件要看**目录的 `w`**，而不看文件自己的 `w`。
- 落点：`/tmp` 的 `1777` 靠 sticky 位来限制"只能删自己的文件"。

**7.10 SUID 的边界有哪些？怎么正确查找 SUID 文件？**

- 判定：SUID 只对二进制生效，脚本上的 SUID 会被内核忽略；此外在 `no_new_privs`、`nosuid` 挂载与被跟踪这三种情况下，它也会被忽略。
- 查找：正确的写法是 `find / -perm -4000`（表示包含该位），而不是 `-perm 4000`（表示精确匹配）。
- 实测参照（转引阶段 7）：本库实验机上有 SUID 文件 13 个、SGID 文件 7 个、带 file capabilities 的文件 4 个。

**7.11 capabilities 相比 SUID 的优势是什么？怎么给服务最小特权？**

- 判定：capabilities 的优势在于它可以只授予一项能力（如 `cap_net_raw`），而不是把整个 root 权限都交出去。
- 落点：`setcap` 用于二进制文件；而 systemd 服务要用 `AmbientCapabilities=`/`CapabilityBoundingSet=` 来限定能力。
- 不要做：不要为了省事就直接给 `CAP_SYS_ADMIN` 或整个 root。

**7.12 加固的验收标准是什么？为什么 `setenforce 0` 不算修复？**

- 判定：加固的验收标准是"可核查"，核查对象是五类基线，即账号、SUID/SGID/capabilities、监听端口、计划任务与自启、SSH 授权。
- 为什么：因为 `setenforce 0` 只是把**强制拦截**关成 permissive，而**审计与 AVC 拒绝记录依然在产生**，所以它掩盖了问题，并没有改变访问控制的设计。
- 落点：因此要在加固前后各采一次基线，用两者的差异证明改动有效。

**7.13 SSH 加固要做哪六件事？验收标准是什么？**

- 六件事：SSH 加固要做六件事，分别是关掉密码登录（只留密钥）、禁止 root 直接登录、关掉不需要的认证方式（如 GSSAPI）、用 `AllowUsers`/`AllowGroups` 限定可登录的人、限制尝试次数与并发（`MaxAuthTries`、`MaxStartups`），以及收敛算法（`KexAlgorithms`/`Ciphers`/`MACs`）。
- 验收：验收时要用 `sshd -T -C user=...,addr=...` 看最终生效值，因为 `Match` 会改变结果；同时要从另一台机器实测"该进的能进、不该进的进不来"。
- 不要做：不要只改完文件就 reload；要先执行 `sshd -t` 校验语法，并保留一条已经打开的会话用于回滚。

## 8. 观察面

**8.1 journald 与 rsyslog 是什么关系？**

- 判定：journald 与 rsyslog 不是二选一的关系；同一条日志通常在这两边都能找到。
- 证据：执行 `logger -t labtest` 之后，`journalctl -o json` 里能看到 `SYSLOG_IDENTIFIER`、`_PID`、`_UID` 与 `_TRANSPORT`，而 `/var/log/syslog` 里是纯文本的一行。
- 落点：因此排查"日志去哪了"时要同时看这两个落点与 `ForwardToSyslog=`。

**8.2 为什么平均值会掩盖长尾？p95 为什么还要报口径？**

- 判定：因为平均值会掩盖长尾——1000 个样本由 950 个 20 ms、45 个 100 ms 与 5 个 2000 ms 组成，它们的平均值是 33.5 ms，而 `max` 是 2000 ms，可见平均值离长尾很远。
- 口径：同一组样本按四种常见算法计算，p95 分别是 20.0、24.0、96.0 与 100.0 ms，因此口径不报清楚就没有意义。
- 落点：所以报分位数时必须把算法与采样窗口一起报出来。

**8.3 告警降噪的四种手段是什么？SLI/SLO/错误预算各是什么？**

- 判定：告警降噪的四种手段是路由、分组、抑制与静默，另有可用性探测用来补上用户视角。
- 定义：SLI 是可测量的服务质量指标；SLO 是这个指标的目标；错误预算是"允许失败的量"，它用于决定发布节奏，以及决定一件事"立刻处理还是排期"。
- 落点：因此告警必须落到一个具体动作上，否则它就是噪音。

**8.4 USE 方法是什么？它比工具清单好在哪？**

- 判定：USE 方法对每一类资源（CPU、内存、IO、网络与存储）依次问三件事，即利用率（Utilization）、饱和度（Saturation）与错误（Errors）。
- 好在哪：它的好处是先给出一份"该查什么"的清单，再决定用哪个工具，从而避免把命令挨个跑一次。
- 边界：它只覆盖资源的视角；应用层的锁、GC（垃圾回收）与下游依赖要靠 trace、应用指标与日志。

**8.5 `sar` 用来做什么？用它复盘的前提是什么？**

- 判定：`sar` 读的是 sysstat 的历史采集，因此它用来回答"那时候机器是什么状态"，因为实时观测回不到过去。
- 用法：实时查看用 `sar -u 1 3`；读历史用 `sar -u -f /var/log/sysstat/saDD`，另有 `-r` 看内存、`-b` 看 IO、`-n DEV` 看网络。
- 前提：它要求装上 `sysstat`，并且历史采集已启用。本库实验机是"已安装且正在采"的正面样本（`sysstat-collect.timer` 为 `enabled`、`/var/log/sysstat/` 有当天数据），但很多机器上该目录根本不存在，所以这一题的教训是"**先确认有数据，再读数据**"。
- 不要做：不要拿默认日期的 `sar` 结果去解释某次故障，而要先确认文件日期与采样间隔。

**8.6 trace/span 与日志、指标的分工是什么？**

- 判定：日志回答"发生了什么"，指标回答"整体趋势"，而 trace/span 回答"这一次请求的时间花在哪一段"。
- 证据：一个 trace 由多个 span 组成，每个 span 都有开始时间、结束时间、父子关系与服务名；采样率决定了开销与留存成本。
- 边界：若调用是异步的或批处理的，或者缺少上下文传递，那么就看不到完整链路。
- 落点：因此要先用指标发现异常时段，再用 trace 定位到具体的一段，最后用日志确认原因。

**8.7 日志查不到、查不全，有哪几类原因？**

- 判定：原因有四类，分别是日志没有写进来（落点选错）、没有持久化（要看 `Storage=` 的生效值）、被限流（表现为 `Suppressed N messages`），以及被裁掉或轮转掉。
- 证据：要读的是 `systemctl show -p StandardOutput,StandardError`、`journalctl --disk-usage`、`systemd-analyze cat-config systemd/journald.conf`、`stat -c %i` 与 `ls -l /proc/<pid>/fd`。
- 不要做：不要先去关掉限流，而要先确认日志是"没进来"还是"被丢掉"。

## 9. 组织层

**9.1 变更单的六要素是什么？最容易漏的是哪两个？**

- 判定：变更单的六要素是目标、范围、备份、回滚、验证与窗口。
- 最容易漏：最容易漏的两项是回滚的触发条件与验证的量化判据，因此要求在动手前就把这两个答案写出来。
- 不要做：不要把"改动很小"当作降级理由。

**9.2 备份、快照、副本分别不能防什么？3-2-1 原则是什么？**

- 判定：快照依赖存储系统，并且与源数据处于同一故障域，因此它不能防这类丢失；副本是实时同步的，所以源被删或被加密时副本会一起被删或被加密；只有独立备份能防误删与逻辑损坏。
- 3-2-1：3-2-1 原则要求 3 份数据、2 种介质与 1 份异地，现代还补充了 1 份离线或不可变。
- 落点：备份的唯一验收标准是"能恢复"，而且要给它计时，也就是对齐 RTO（恢复时间目标）。

**9.3 灰度分批的依据是什么？为什么 `serial: 1` 不等于安全？**

- 判定：批次大小由余量决定，它不超过"总容量 − 最小可接受容量"；同时观察时间要覆盖一个业务周期与 2~3 个采样间隔。
- 为什么：因为 `serial: 1` 只表示串行执行，所以如果每台都改动了同一个共享依赖（数据库、证书或配置中心），或者第一批就是核心实例，那么仍然会全部中断。
- 落点：因此批次要同时覆盖实例与故障域这两个维度。

**9.4「拔掉一台业务还剩多少」怎么算？脑裂时应保可用还是保一致？**

- 判定：要查四件事，即它是不是单实例、流量会不会切走、切换时连接会不会断、剩余容量够不够（N+1/N+2）；同时还要看故障域是否重叠。
- 脑裂取舍：默认选择保一致，也就是在判定不确定时停服务，或者用 fencing 强制一方下线；写服务尤其如此。
- 不要做：不要把"配了 VIP"当成高可用。

**9.4 事故响应的前三步是什么？复盘六段是什么？**

- 前三步：事故响应的前三步依次是分级与通报、止损（按可逆性排序）与取证（取证可以由并行的一条线完成）；至于根因，则留给复盘。
- 复盘六段：复盘的六段依次是时间线、影响面、证据、根因、止损动作与改进项（注意它与答题用的"六段骨架"不是同一套）。
- 落点：改进项要逐项写清要做的动作、负责人（owner）、期限与验收方式；"人为失误"不算根因。

**9.5 机器疑似被入侵时，处置与取证的顺序是什么？**

- 分层：处置与取证要按四层推进，依次是账号与认证层、权限与提权面、网络与进程层，以及持久化层（计划任务与自启）。
- 证据：要读的是 `who`、`last`、`journalctl -u ssh`、`ss -tunap`、`ps auxf`、`find / -perm -4000`、`getcap -r /`、`systemctl list-timers`、`crontab -l` 与 `ls -l /etc/cron*`。
- 结论候选：共有四种，第一种是弱口令或密钥泄漏，第二种是提权面被利用（SUID 或 capabilities），第三种是存在未发现的持久化点，第四种是误报（误报要用证据排除，不能靠感觉）。
- 止损：**先隔离而不是先清理**，也就是先保住现场（快照、镜像、日志导出），再按流程通报。
- 不要做：不要在取证前 `kill` 进程、删文件或重启，因为那会毁掉全部现场。

## 10. 首轮建议完成的题组

第一轮建议只做**内存线（第 4 组）、持久线（第 5 组）、连接线（第 6 组）、约束环（第 7 组）**这四组，因为它们覆盖了"内存压力""容量与 IO""网络分层"与"上限配在哪一层"，而这些是值班与现场出现频率最高的部分；其余五组留到第二轮交错进行。

这样安排的理由不是"其它组不重要"，而是**交错的收益来自混排**：第二轮要把前提组、启动链路组与观察面组混进上面四组里做，才会真正考出"先分类"的能力。

## 常见误解

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 一边看题一边看答案 | 这样做会把练习退化为识别练习，因此正确的口径难以转化为实际能力 |
| 只做眼熟的题 | 这样做会跳过薄弱的题，因此这次摸底就失效了 |
| 不为答案定档 | 不定档就无法排序，也无法判断自己需要补哪一层 |
| 一次完成全部题目 | 后段疲劳会影响数据质量，因此要按线分组进行，并把每组控制在 20~25 分钟 |
| 答完不写错题清单 | 不写错题清单意味着这一轮的产物为零，因此下一轮还会犯同样的错 |
| 把未实测的答案当实测 | 这样的答案换一个环境后会被推翻，因此未实测的部分要照实标注 |
| 按线做却仍按章翻答案 | 按线做时的第一问应当是"这属于哪条线"，只有翻答案时才回到章节 |

## 要点自测

- B 档（有结论无证据）最有效的补法是什么？C 档（认得但讲不出）最有效的补法又是什么？

- 答完一组之后，如果全是 A，下一步该做什么？
