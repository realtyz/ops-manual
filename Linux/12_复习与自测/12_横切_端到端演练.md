## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **三条纪律不能破：隔离、上限、清理复核。**
>   - 怎么验证：所有实验只在可丢弃目录或独立实验机里做；每个实验写明上限（时长、数据量、参数范围）；跑完复核「无残留进程、无残留目录、参数回到基线」。
> - **每个实验必须留下「观测指纹」。**
>   - 理由：故障本身不重要，**「这个故障在哪些指标上长什么样」**才是可迁移的知识。
> - **恢复要计时。**
>   - 证据：阶段 11 的做法是把恢复耗时记进演练记录（对齐 RTO）；不记时长的恢复演练只能证明「能做到」，不能证明「够快」。
> - **先做只读与可回滚的（1、5、6、7、8、9、10、11），再做会改坏机器、只能靠快照或控制台兜底的（2、12）。**
>   - 怎么验证：如果第一轮就把机器弄坏，后面的实验都没得做。实验 3、4 属于中间档——用**临时 loop 文件系统**做等价复现，既拿到了判据，又碰不到根分区。
> - **未实测的部分照实写。**
>   - 怎么验证：演练记录最后一段永远有「未实测 + 原因 + 补做方式」。

## 2. 三条纪律与基线

```bash
mkdir -p /var/tmp/review-lab       # 验证：所有实验只在可丢弃目录里做
uname -r; nproc; free -m | head -2; df -h / | tail -1   # 验证：记录实验前基线
systemd-run --scope true           # 验证：系统级 scope 可用（实验 5、6 依赖它，需 root）
ip netns add lab12                 # 验证：网络命名空间可用（实验 10 依赖它，需 root）
ip netns exec lab12 ip -brief addr # 验证：命名空间里的 lo 可见
ss -lntup; losetup -a; ip netns list   # 验证：实验前没有残留监听、loop 与命名空间
```

**这台实验机的身份与命名空间前提（与旧 WSL2 笔记的关键差异）**：root 可用（`uid=0`），所以 `systemd-run` 用**系统级** `--scope`，`systemctl` 用**系统级** manager；旧笔记里靠 `systemctl --user` 与 `systemd-run --user` 绕权限的做法在这里没有必要，只在做「用户级 vs 系统级」对比时才用。另外**非特权 user namespace 在本机被禁用**（`kernel.apparmor_restrict_unprivileged_userns=1`，AppArmor 默认策略）：以 `realtyz` 执行 `unshare -U -r -n` 会直接报 `unshare: write failed /proc/self/uid_map: Operation not permitted`（`exit=1`），而以 root 执行 `unshare -n` 返回 0、`ip netns add` 也正常——所以实验 10 用 **root + `ip netns`**，不再用 `unshare -U -r -n`。

**每个实验前、后各采一次基线**，这是「有对比才叫验证」的最小实现。

跑完全部实验后，三项清理复核：

```bash
pgrep -af 'spin|lab'               # 复核：没有残留实验进程
ls -ld /var/tmp/review-lab         # 复核：临时目录已清理
losetup -a; ip netns list          # 复核：没有残留 loop 设备与命名空间
ss -lntup                           # 复核：没有残留监听
free -m | head -2; df -h / | tail -1   # 复核：内存与容量回到基线
```

## 3. 十二个实验详解（实验 12 拆为 12a/12b 两档）

> [!example]- 实验 1：只读基线采集（生产机也可以做）
> **怎么做**：按阶段 1 的基线卡采五项：版本（`/etc/os-release`、`uname -r`、`systemctl --version`、`stat -fc %T /sys/fs/cgroup`）、容量（`df -h`、`df -i`）、压力（`free -m`、`/proc/pressure/memory`）、连接（`ss -lnt`、`ss -s`）、日志用量（`journalctl --disk-usage`、`du -sh /var/log`）。
> **观测指纹（转引阶段 11 的只读基线）**：`ss -lnt` 有 **4** 个 LISTEN 套接字（`0.0.0.0:22`、`[::]:22` 两个 ssh，以及解析器的 `127.0.0.53%lo:53`、`127.0.0.54:53`）；`journalctl --disk-usage` **以现场读数为准**（迁移后基线约 53.9 MiB，随后重跑读到 20.7 MiB）；根文件系统 inode 用量 **6%**（159617 / 3145728），容量 46.9 G 级别、已用约 19%。
> **上限/风险**：只读，无风险。**耗时**：约 20 分钟。**验收**：一张填满的基线卡。

> [!example]- 实验 2：写坏 `/etc/fstab` 后重启（**未实测：只在可快照且有控制台的实验机做，需 root**）
> **怎么做**：先快照；在 `/etc/fstab` 里加一行指向不存在的设备并设 `nofail` 缺失；重启（或在虚拟机里重启）；观察启动是否进入 `emergency mode`。
> **观测指纹**：`You are in emergency mode`、`journalctl -xb` 出现 `Failed to mount`。
> **恢复**：在紧急模式里注释掉坏行 → `systemctl daemon-reload` → `mount -a` 验证 → 继续启动。
> **上限/风险**：会打断启动；**必须能进控制台**。**耗时**：约 40 分钟。
> **不要做**：不要在没有控制台的情况下用这个方法练。
> **本机状态**：**未实测**。写坏 `/etc/fstab` 到无法启动属于「禁止」清单：本实验机只有 SSH 一条通道、没有独立控制台，做坏了无法自救；要在可快照、有控制台的实验机上做。

> [!example]- 实验 3：打满一个独立文件系统（**已实测：临时 loop 文件系统等价复现，需 root**）
> **怎么做**：用 loop 文件建一个约 64 MiB 的 ext4 并挂到一个**独立挂载点**（例如 `/mnt/labfull`）；用 `dd` 或 `fallocate` 写到满；观察 `df -hT`、`df -i` 与写入报错。**全程不碰根分区、不碰 `/dev/sda` 分区表。**
> **观测指纹（转引阶段 9 实测，条件以该阶段为准）**：`dd if=/dev/zero of=/mnt/labfull/fill bs=1M count=200` 写到 55 MiB 时满，**`dd` 自己就报错**：`dd: error writing '…': No space left on device` + `54+0 records out`，**退出码 1**；`df -hT` 显示 `56M 55M 0 100%`。这里最容易踩的是**取退出码的方式**：脚本写成 `dd … 2>&1 | tail -3` 再 `echo $?`，拿到的是管道末端 `tail` 的状态（0）——**要取上游命令的退出码必须用 `${PIPESTATUS[0]}`**；所以「`dd` 的退出码不可信、要看 `df`」这个说法本身是错的：`dd` 的退出码可信，是脚本取错了它。打满后再写文件同样报 `No space left on device`（以 root `touch` 一个空文件仍可能成功——ext4 给 root 留了保留块）；写满后 `df -i` 的 `IUsed` 只从 11 变 12——这是**空间**耗尽，不是 **inode** 耗尽。
> **恢复**：`rm` 掉大文件即释放（转引阶段 1 实测 `df` 立刻回到 1%）；`umount` → `losetup -d` → 删镜像文件。
> **上限**：64 MiB 镜像，且只作用于独立挂载点。**耗时**：约 5 分钟（不含阅读）。
> **不要做**：不要把 `dd` 的目标写到系统盘或根分区上。**本机状态**：**已实测**（等价复现，见阶段 1 子笔记 10）。

> [!example]- 实验 4：耗尽 inode（**已实测：临时 loop 文件系统等价复现，需 root**）
> **怎么做**：用 `mkfs.ext4 -N <很小的数>` 在 loop 镜像上造一个 inode 极少的小文件系统，批量创建空文件直到 `df -i` 到 100%；再尝试创建新文件观察报错。
> **观测指纹（转引阶段 9 实测）**：`mkfs.ext4 -N 512` 的 32 MiB 镜像里创建 501 个空文件后，`df -i` 变成 `512 512 0 100%`，而 `df -hT` 仍是 `28M 32K 26M 1%`——**空间几乎没用，却再也建不了文件**；报错文本与容量满一样是 `No space left on device`。作为对照，本实验机根文件系统的 inode 只用了 **6%**（159617 / 3145728）。
> **恢复**：删除小文件（`find ... -delete`，注意顺序与效率）；卸载并删除 loop 镜像。**上限**：独立 loop 文件系统 + 明确数量。**耗时**：约 10 分钟。
> **不要做**：不要在系统盘或生产目录里做。**本机状态**：**已实测**（等价复现，见阶段 5 子笔记 09、阶段 9 子笔记 08）。

> [!example]- 实验 5：cgroup 内存 OOM（root 可用）
> **怎么做**：用 `systemd-run --scope -p MemoryMax=256M` 运行一个会持续分配内存的程序；同时观察该 cgroup 的 `memory.events` 与 `memory.peak`。
> **观测指纹（转引阶段 8、10 实测）**：`memory.events` 出现 `oom_kill` 计数（阶段 10 实测 `oom_kill 1`，非 OOM 对照是 0）、`memory.peak` 顶到上限；内核日志出现 `oom-kill:constraint=CONSTRAINT_MEMCG` 记录。
> **恢复**：结束 scope；`systemctl status` 确认无残留。**上限**：256 MiB，几分钟内结束。**耗时**：约 30 分钟。
> **不要做**：不要在共享机器上调大上限做压力测试——**绝对不要打满内存**，会触发 OOM 影响其他章节与宿主机。

> [!example]- 实验 6：CPU 配额限流（root 可用）
> **怎么做**：`systemd-run --scope -p CPUQuota=20%` 运行一个 CPU 密集任务；读 `cpu.stat` 的 `nr_throttled` 与 `throttled_usec`，并测吞吐。
> **观测指纹（转引阶段 10 实测）**：`nr_throttled` 持续增长（实测 `nr_periods 21 / nr_throttled 20`）、吞吐只剩 **19.30%**（同一段代码的迭代数 29823329 → 5757053；`CPUQuota=20%` 对应 `cpu.max=20000 100000`）。
> **恢复**：结束 scope。**上限**：单个 scope、短时运行（≤ 20 秒 × 1~2 worker，跑完确认 load average 回落）。**耗时**：约 30 分钟。
> **不要做**：不要在共享机器上长时间跑满核。

> [!example]- 实验 7：句柄耗尽（任意身份可做）
> **怎么做**：在子 shell 里 `ulimit -n 64`，运行一个不断打开文件（不关闭）的脚本，观察 `Too many open files`；同时用 `/proc/<pid>/limits` 与 `lsof -p` 佐证。
> **观测指纹**：报错来自 `open`；`limits` 的 `Max open files` 被压低到 64；`lsof` 计数接近上限。（注意本实验机 `ulimit -n` 的 soft 值是 **1024**、hard 是 **1048576**，所以不压低就会在第 1020 个 fd 左右才报错——这正是「口径」的现场教学。）
> **恢复**：退出子 shell 即恢复。**上限**：64 个 fd。**耗时**：约 30 分钟。
> **不要做**：不要在生产机上为了「验证」改全局 `fs.file-max`。

> [!example]- 实验 8：单核打满（任意身份可做）
> **怎么做**：用 `taskset -c 2` 把一个自旋进程绑到某个核上；同时用 `mpstat -P ALL 1 3` 看单核与整机，用 `uptime` 看 load；再加 1~4 个竞争者观察吞吐与延迟长尾。
> **观测指纹（转引阶段 10 实测）**：单核 100% 而整机 `%usr` 25.00%（4 vCPU 的 1/4）、`load` 0.34；同核加 4 个竞争者后吞吐只剩 21%（下降约 79%），延迟探针 `max` 8.36 → 16.58 ms、`p95` 8.25 → 10.99 ms（`p50` 8.13 → 8.06 ms）。
> **恢复**：杀掉自旋进程。**上限**：单核、短时。**耗时**：约 30 分钟。
> **不要做**：不要用「整机 CPU 不高」排除 CPU 问题。

> [!example]- 实验 9：日志轮转写错（任意身份可做）
> **怎么做**：在 `/var/tmp/review-lab` 建一个日志文件，写一个持续写入的后台进程；配一份 `copytruncate` 的 logrotate 规则并手动触发；观察 inode 与新老文件的行数。
> **观测指纹（转引阶段 9 实测）**：`copytruncate` 后 inode 不变（`1310736 → 1310736`）；换成 `create` 后 inode 换了（新 `1310803`、归档 `1310798`），持有旧 fd 的进程把随后 9 行写进了归档文件、新文件 0 行。
> **恢复**：恢复原配置、杀掉写入进程、清理目录。**上限**：自建目录与自建进程。**耗时**：约 30 分钟。
> **不要做**：不要拿系统日志与真实 `logrotate` 配置做实验。

> [!example]- 实验 10：网络丢包与延迟注入（root 可用；**非特权 user namespace 在本机被禁用**）
> **怎么做**：用 `ip netns add lab12` 建独立网络命名空间（root），在里面起一个本机服务并注入 `tc qdisc ... netem delay 50ms`（或 `loss 20%`）；用 `ss -ti` 看 `rtt`/`minrtt`/`retrans`，用 `tc -s qdisc show` 看计数。
> **观测指纹（转引阶段 10 实测）**：注入 50 ms 单向延迟后 `ping` 报 `rtt min/avg/max/mdev = 100.131/100.238/100.375/0.101 ms`，`ss -ti` 的 `minrtt:100.123`（另一条连接 `100.131`）；配 `netem loss 20%` 时 `ping` 实测 `200 transmitted, 127 received, 36.5% packet loss`——**这是丢包率，不是重传率，别把两者混着说**。
> **恢复**：`ip netns del lab12` 即全部消失；确认 `ip netns list` 为空。**上限**：命名空间内、单向延迟 ≤ 100 ms、丢包 ≤ 20%。**耗时**：约 40 分钟。
> **不要做**：不要在宿主机默认命名空间里注入 `tc` 规则；也不要用 `unshare -U -r -n` 当「非 root 绕过手段」——本机 `kernel.apparmor_restrict_unprivileged_userns=1`，以 `realtyz` 跑它会得到 `Operation not permitted`（这是 Ubuntu 24.04 的默认安全策略，不是权限配置错误）。

> [!example]- 实验 11：服务起不来（改坏自建 system 单元，root 可用）
> **怎么做**：写一个 `/etc/systemd/system/lab12-broken.service`，把 `ExecStart` 指到不存在的路径；`systemctl daemon-reload && systemctl start lab12-broken`，读 `systemctl status` 与 `journalctl -u lab12-broken`；再改成正确的路径验证能起来。
> **观测指纹（转引阶段 8 实测）**：`status=203/EXEC`、`Active: failed`；`status` 三段里 `CGroup` 段会显示进程被清掉（阶段 8 也实测了 `226/NAMESPACE`、`216/GROUP`、`200/CHDIR` 的变体）。
> **恢复**：修复 unit → `daemon-reload` → `start`；或 `systemctl disable --now lab12-broken` 后删除文件。**耗时**：约 30 分钟。
> **不要做**：不要拿系统自带的关键服务（`sshd`/`systemd-journald`/`dbus`/`systemd-resolved`）做这个实验——只操作自己新建的 unit。

> [!example]- 实验 12a：只读文件系统（**已实测：临时 loop 文件系统等价复现，需 root**）
> **怎么做**：在实验 3 的 loop 挂载点上 `mount -o remount,ro /mnt/labfull`，观察 `findmnt` 与写入报错；再 `mount -o remount,rw /mnt/labfull` 还原。
> **观测指纹（转引阶段 1 实测）**：`remount,ro` 退出码 0；`findmnt -o TARGET,SOURCE,FSTYPE,OPTIONS` 显示 `ro,relatime`；`touch /mnt/labfull/cannot.txt` 报 `Read-only file system`（退出码 1）；`remount,rw` 后回到 `rw,relatime`。**判据就是 `findmnt` 的 `OPTIONS` 列**，不是「感觉写不进去」。
> **上限/风险**：只影响独立镜像文件与挂载点，**不碰真正的根分区**。**耗时**：约 5 分钟。
> **不要做**：**不要第一反应 `mount -o remount,rw /`**——重挂只读是内核检测到错误后的安全动作（**需显式配 `errors=remount-ro` 才成立**，ext4 默认是 `errors=continue`），先取证（`dmesg -T`、`journalctl -k`）再决定路径。**本机状态**：**已实测**（等价复现，见阶段 1 子笔记 10、阶段 5 子笔记 13）。

> [!example]- 实验 12b：真正的根分区只读与内核 panic（**未实测：可快照实验机 + 控制台，需 root**）
> **怎么做（只读根）**：快照后 `mount -o remount,ro /`，观察 `df`/写入报错，走「先查 `dmesg` 原因 → 切业务 → 决定修或重建」的路径，最后按快照回滚。
> **怎么做（panic）**：在实验机上 `echo c > /proc/sysrq-trigger` 触发崩溃，重启后取 `journalctl -b -1 -k`、`/var/crash/`，再尝试用 `crash` 分析 `vmcore`。
> **观测指纹**：只读时 `findmnt /` 显示 `ro`、写入报 `Read-only file system`；panic 后上一轮引导日志与 `vmcore` 是唯一现场。
> **上限/风险**：会中断系统；**必须能进控制台、必须先快照**。**耗时**：约 60 分钟。
> **不要做**：不要在生产机上触发 panic；不要在没有日志持久化的机器上做——重启后什么都不会留下。
> **本机状态**：**未实测**。本实验机只有 SSH 一条通道、没有独立控制台，把根分区或 SysRq 弄坏后无法自救；而且 panic 类实验的前提本来也不满足（`kdump inactive`、`kernel.sysrq = 176` **不含 panic 位**、`/var/crash` 为空）。**只读故障的判据已用实验 12a 的 loop 等价复现拿到。**

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 不做基线就注入故障 | 无法判断「恢复了没有」；对比是验证的前提 |
| 一次注入多个故障 | 观测指纹互相污染，无法归因 |
| 只记录「故障发生了」，不记录指纹 | 学不到可迁移的知识；下次遇到仍认不出来 |
| 恢复不记耗时 | 无法对齐 RTO，也无法向别人证明恢复能力 |
| 在共享机器上做压力类实验 | 影响他人；所有压力类都要有明确上限 |
| 跑完不清理 | 残留进程会污染后续实验；复核三项是硬性要求 |
| 把未实测的结论当实测写 | 会误导自己与同事；必须显式标注 |

## 决策练习

> 你手上只有一台**能 SSH 登录、但没有独立控制台**的实验机（root 可用），想在今天完成演练。怎么安排顺序？
>
> - **A. 先做实验 2 与 12b**（`fstab`、只读根、panic），因为它们是「最有代表性」的故障。
> - **B. 先做实验 1（基线采集），再按依赖顺序做可自恢复的那些（3、4 的 loop 打满 / inode、12a 的只读文件系统、5、6、7、8、9、10、11），把需要控制台或快照的 2 与 12b 标为未实测并写补做方式。**
> - **C. 用 `sudo -i` 试试看能不能拿到 root，不行再说。**

**为什么选 B**：先建基线，再按「可自恢复 / 不可自恢复」的能力边界推进；`fstab` 与 panic 这类做坏了救不回来的，显式登记为未实测并写清补做方式，这是第 3 节「照实写」的纪律。

**为什么 A 不对**：本实验机只有 SSH 一条通道，写坏 `fstab` 或触发 panic 之后就再也进不去了，硬做只会把机器变成砖。

**为什么 C 不对**：本机 root 本来就可用，问题不是权限而是**没有第二入口**——提权解决不了「进不去」；在没有授权与快照的前提下做不可逆实验，属于越界操作。

## 要点自测

> [!question]- 演练的三条纪律是什么？跑完复核哪三项？
> - **判定**：隔离、上限、清理复核；复核无残留进程、无残留目录、参数与容量回基线。
> - **影响什么**：决定演练会不会伤到别人和后续实验。
> - **不影响什么**：不限制实验数量；限制的是每条实验的影响范围。
> - **落点**：每条演练记录的开头写实验前基线，结尾写复核三项。
>
> [!question]- 为什么每个实验都要留下「观测指纹」？
> - **判定**：指纹是故障在指标上的形态，是可迁移的部分。
> - **例子**：`%util` 几乎不变但 `w_await` 与 `aqu-sz` 同时上升 → 排队而不是设备忙；`memory.events` 出现 `oom_kill` → cgroup 级 OOM。
> - **影响什么**：决定下次遇到同类现象时你能否在几分钟内认出来。
> - **第一反应不要是什么**：不要把「命令跑通了」当作实验完成。
>
> [!question]- 为什么恢复要计时？
> - **判定**：恢复耗时是对齐 RTO 的唯一证据；不记时长只能证明「能做」，不能证明「够快」。
> - **影响什么**：决定变更窗口与故障预案是否现实。
> - **不影响什么**：第一次记的时长通常很难看，这是正常的起点。
> - **落点**：每条演练记录写「恢复耗时 ____ 秒（对照 RTO ____ 秒）」。
