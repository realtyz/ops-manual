# 横切：端到端演练——一台机器走完全部故障

> [!cite] 参考资料
> 本套笔记阶段 1 的破坏性演练清单与快照纪律、阶段 3 的资源耗尽实验、阶段 4 的 cgroup 内存与 OOM 实验、阶段 5 的容量与只读故障演练、阶段 6 的 `netem` 故障注入、阶段 8 的 unit 排障实验、阶段 9 的日志轮转实验、阶段 10 的故障演练与工具边界；阶段 11 的恢复演练与 RTO 计时做法。
>
> **实测状态**：本机为 **Ubuntu 24.04.4 LTS（WSL2）/ 内核 `6.6.87.2-microsoft-standard-WSL2` / systemd 255 / 24 vCPU / `MemTotal` 15844 MiB / 根分区 `/dev/sdd`（ext4，1 TB 虚拟盘）/ 非 root `uid=1000`**。**可在本机非 root 完成**：实验 1、5、6、7、8、9、10、11（其中 6、7 用 `systemd-run --user`，11 用 `unshare -U -r -n`）；**需要 root 或真机**：实验 2、3、4、12（`fstab`、独立文件系统、只读根、内核 panic）。需要 root 的实验在本机**未实测**，只给做法、指纹与验收标准。

> **这篇讲什么**：把前十一章里分散的故障注入串成一条链，在一台机器上依次演一遍「坏 → 观测 → 恢复 → 复核」。
>
> **必须先读什么**：[[Linux/12_复习与自测/10_横切_场景题答题骨架|10 横切：场景题答题骨架]]（先知道每类故障的判定路径）。
>
> **读完能交付**：一份端到端演练记录（含观测指纹、恢复耗时、未实测清单）。
>
> **所属**：横切篇；练习技能 **R7 动手复现**

## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **三条纪律不能破：隔离、上限、清理复核。**
>   - 怎么验证：所有实验只在可丢弃目录或独立实验机里做；每个实验写明上限（时长、数据量、参数范围）；跑完复核「无残留进程、无残留目录、参数回到基线」。
> - **每个实验必须留下「观测指纹」。**
>   - 理由：故障本身不重要，**「这个故障在哪些指标上长什么样」**才是可迁移的知识。
> - **恢复要计时。**
>   - 证据：阶段 11 的做法是把恢复耗时记进演练记录（对齐 RTO）；不记时长的恢复演练只能证明「能做到」，不能证明「够快」。
> - **先做只读与可回滚的（1、5、6、7、8、9、10、11），再做需要特权与破坏性的（2、3、4、12）。**
>   - 怎么验证：如果第一轮就把机器弄坏，后面的实验都没得做。
> - **未实测的部分照实写。**
>   - 怎么验证：演练记录最后一段永远有「未实测 + 原因 + 补做方式」。

## 2. 三条纪律与基线

```bash
mkdir -p /var/tmp/review-lab       # 验证：所有实验只在可丢弃目录里做
uname -r; nproc; free -m | head -2; df -h / | tail -1   # 验证：记录实验前基线
systemd-run --user --scope true    # 验证：用户级 scope 可用（实验 5、6 依赖它）
unshare -U -r -n ip -brief addr    # 验证：用户+网络命名空间可用（实验 10 依赖它）
```

**每个实验前、后各采一次基线**，这是「有对比才叫验证」的最小实现。

跑完全部实验后，三项清理复核：

```bash
pgrep -af 'spin|lab'               # 复核：没有残留实验进程
ls -ld /var/tmp/review-lab         # 复核：临时目录已清理
free -m | head -2; df -h / | tail -1   # 复核：内存与容量回到基线
```

## 3. 十二个实验详解

> [!example]- 实验 1：只读基线采集（生产机也可以做）
> **怎么做**：按阶段 1 的基线卡采五项：版本（`/etc/os-release`、`uname -r`、`systemctl --version`、`stat -fc %T /sys/fs/cgroup`）、容量（`df -h`、`df -i`）、压力（`free -m`、`/proc/pressure/memory`）、连接（`ss -lnt`、`ss -s`）、日志用量（`journalctl --disk-usage`、`du -sh /var/log`）。
> **观测指纹**：本机实测 `ss -lnt` 有 3 个 LISTEN（均为解析器）、`journalctl --disk-usage` 693.7 MiB、inode 用量约 1%。
> **上限/风险**：只读，无风险。**耗时**：约 20 分钟。**验收**：一张填满的基线卡。

> [!example]- 实验 2：写坏 `/etc/fstab` 后重启（**只在可快照实验机，需 root**）
> **怎么做**：先快照；在 `/etc/fstab` 里加一行指向不存在的设备并设 `nofail` 缺失；重启（或在虚拟机里重启）；观察启动是否进入 `emergency mode`。
> **观测指纹**：`You are in emergency mode`、`journalctl -xb` 出现 `Failed to mount`。
> **恢复**：在紧急模式里注释掉坏行 → `systemctl daemon-reload` → `mount -a` 验证 → 继续启动。
> **上限/风险**：会打断启动；**必须能进控制台**。**耗时**：约 40 分钟。
> **不要做**：不要在没有控制台的情况下用这个方法练。
> **本机状态**：非 root，**未实测**。

> [!example]- 实验 3：打满一个独立文件系统（**可快照实验机，需 root**）
> **怎么做**：用 loop 文件建一个约 200 MiB 的 ext4 并挂到 `/mnt/lab`；用 `dd` 或 `fallocate` 写到满；观察 `df` 与写入报错。
> **观测指纹**：`df -h /mnt/lab` 100%、`No space left on device`；注意 `du` 与 `df` 的差异（保留块）。
> **恢复**：删除实验文件、卸载、删除 loop 文件。**上限**：200 MiB，且只作用于独立挂载点。**耗时**：约 40 分钟。
> **不要做**：不要把 `dd` 的目标写到系统盘上。**本机状态**：需 root，**未实测**。

> [!example]- 实验 4：耗尽 inode（**可快照实验机，需 root**）
> **怎么做**：在一个小文件系统上创建大量空文件（如 10 万个），直到 `df -i` 到 100%；再尝试创建新文件观察报错。
> **观测指纹**：`df -h` 仍有空间、`df -i` 100%、创建失败提示 `No space left on device`（on inode）。
> **恢复**：删除小文件；注意用 `find ... -delete` 的效率和顺序。**上限**：小文件系统 + 明确数量。**耗时**：约 40 分钟。
> **不要做**：不要在系统盘或生产目录里做。**本机状态**：需 root，**未实测**。

> [!example]- 实验 5：cgroup 内存 OOM（本机非 root 可用）
> **怎么做**：用 `systemd-run --user --scope -p MemoryMax=256M` 运行一个会持续分配内存的程序；同时观察该 cgroup 的 `memory.events` 与 `memory.peak`。
> **观测指纹**：`memory.events` 出现 `oom_kill` 计数、`memory.peak` 顶到上限；内核日志出现 OOM 记录（阶段 10 实测过 `CONSTRAINT_MEMCG`）。
> **恢复**：结束 scope；`systemctl --user status` 确认无残留。**上限**：256 MiB，几分钟内结束。**耗时**：约 30 分钟。
> **不要做**：不要在系统级（非 `--user`）scope 里做，也不要调大上限做压力测试。

> [!example]- 实验 6：CPU 配额限流（本机非 root 可用）
> **怎么做**：`systemd-run --user --scope -p CPUQuota=20%` 运行一个 CPU 密集任务；读 `cpu.stat` 的 `nr_throttled` 与 `throttled_usec`，并测吞吐。
> **观测指纹**：`nr_throttled` 持续增长、吞吐约为原值的 18~20%（阶段 10 实测 `CPUQuota=20%` 时吞吐只剩 18.65%）。
> **恢复**：结束 scope。**上限**：单个 scope、短时运行。**耗时**：约 30 分钟。
> **不要做**：不要在共享机器上长时间跑满核。

> [!example]- 实验 7：句柄耗尽（本机非 root 可用）
> **怎么做**：在子 shell 里 `ulimit -n 64`，运行一个不断打开文件（不关闭）的脚本，观察 `Too many open files`；同时用 `/proc/<pid>/limits` 与 `lsof -p` 佐证。
> **观测指纹**：报错来自 `open`；`limits` 的 `Max open files` 被压低；`lsof` 计数接近上限。
> **恢复**：退出子 shell 即恢复。**上限**：64 个 fd。**耗时**：约 30 分钟。
> **不要做**：不要在生产机上为了「验证」改全局 `fs.file-max`。

> [!example]- 实验 8：单核打满（本机非 root 可用）
> **怎么做**：用 `taskset -c 2` 把一个自旋进程绑到某个核上；同时用 `mpstat -P ALL 1 3` 看单核与整机，用 `uptime` 看 load；再加 1~4 个竞争者观察吞吐与延迟长尾。
> **观测指纹（本机实测）**：单核 100% 而整机 `%usr` 仅 4.17%、`load` 仅 0.12；加 4 个竞争者后吞吐下降 76%，延迟探针 `p50` 8.13 → 12.00 ms、`max` 8.34 → 25.79 ms。
> **恢复**：杀掉自旋进程。**上限**：单核、短时。**耗时**：约 30 分钟。
> **不要做**：不要用「整机 CPU 不高」排除 CPU 问题。

> [!example]- 实验 9：日志轮转写错（本机非 root 可用）
> **怎么做**：在 `/var/tmp/review-lab` 建一个日志文件，写一个持续写入的后台进程；配一份 `copytruncate` 的 logrotate 规则并手动触发；观察 inode 与新老文件的行数。
> **观测指纹（本机实测参照）**：`copytruncate` 后 inode 不变；换成 `create` 后持有旧 fd 的进程把随后 9 行写进了归档文件、新文件 0 行。
> **恢复**：恢复原配置、杀掉写入进程、清理目录。**上限**：自建目录与自建进程。**耗时**：约 30 分钟。
> **不要做**：不要拿系统日志与真实 `logrotate` 配置做实验。

> [!example]- 实验 10：网络丢包与延迟注入（本机非 root 可用，需用户命名空间）
> **怎么做**：`unshare -U -r -n` 进入独立网络命名空间；起一个本机服务并注入 `tc qdisc ... netem delay 50ms`（或 `loss 20%`）；用 `ss -ti` 看 `rtt`/`minrtt`/`retrans`，用 `tc -s qdisc show` 看计数。
> **观测指纹（本机实测参照）**：注入 50 ms 单向延迟后连接 RTT 为 100.164 ms、`minrtt:100.131`；`netem` 配 20% 丢包时实测重传率约 35.5%（因为一个报文与其重传都可能丢，`1 − 0.8² ≈ 36%`）。
> **恢复**：退出命名空间即全部消失。**上限**：命名空间内、单向延迟 ≤ 100 ms、丢包 ≤ 20%。**耗时**：约 40 分钟。
> **不要做**：不要在宿主机默认命名空间里注入 tc 规则。

> [!example]- 实验 11：服务起不来（改坏用户 unit，本机非 root 可用）
> **怎么做**：写一个 `~/.config/systemd/user/lab-broken.service`，把 `ExecStart` 指到不存在的路径；`systemctl --user daemon-reload && systemctl --user start lab-broken`，读 `status` 与 `journalctl --user -u lab-broken`；再改成正确的路径验证能起来。
> **观测指纹**：`status=203/EXEC`、`Active: failed`；`status` 三段里 `CGroup` 段会显示进程被清掉（阶段 8 也有 `226/NAMESPACE`、`216/GROUP` 的变体）。
> **恢复**：修复 unit → `daemon-reload` → `start`；或 `systemctl --user disable --now` 后删除文件。**耗时**：约 30 分钟。
> **不要做**：不要用系统级 unit 做这个实验。

> [!example]- 实验 12：根分区只读与内核 panic（**可快照实验机 + 控制台，需 root**）
> **怎么做（只读根）**：快照后 `mount -o remount,ro /`，观察 `df`/写入报错，走「先查 `dmesg` 原因 → 切业务 → 决定修或重建」的路径，最后按快照回滚。
> **怎么做（panic）**：在实验机上 `echo c > /proc/sysrq-trigger` 触发崩溃，重启后取 `journalctl -b -1 -k`、`/var/crash/`，再尝试用 `crash` 分析 `vmcore`。
> **观测指纹**：只读时 `mount` 显示 `ro`、写入报 `Read-only file system`；panic 后上一轮引导日志与 `vmcore` 是唯一现场。
> **上限/风险**：会中断系统；**必须能进控制台、必须先快照**。**耗时**：约 60 分钟。
> **不要做**：不要在生产机上触发 panic；不要在没有日志持久化的机器上做——重启后什么都不会留下。
> **本机状态**：WSL2 + 非 root，**未实测**。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 不做基线就注入故障 | 无法判断「恢复了没有」；对比是验证的前提 |
| 一次注入多个故障 | 观测指纹互相污染，无法归因 |
| 只记录「故障发生了」，不记录指纹 | 学不到可迁移的知识；下次遇到仍认不出来 |
| 恢复不记耗时 | 无法对齐 RTO，也无法向别人证明恢复能力 |
| 在共享机器上做压力类实验 | 影响他人；所有压力类都要有明确上限 |
| 跑完不清理 | 残留进程会污染后续实验；复核三项是硬性要求 |
| 把未实测的结论当实测写 | 会误导自己与同事；必须显式标注 |

## 决策练习

> 你只有一台非 root 的机器（WSL2），想在今天完成演练。怎么安排顺序？
>
> - **A. 先做实验 2、3、4**（`fstab`、打满盘、耗尽 inode），因为它们是「最有代表性」的故障。
> - **B. 先做实验 1（基线采集），再做 5~11 里能做的（OOM、CPU 配额、句柄、单核、日志轮转、网络注入、unit 报错），把需要 root 的 2、3、4、12 标为未实测并写补做方式。**
> - **C. 用 `sudo -i` 试试看能不能拿到 root，不行再说。**

**为什么选 B**：先建基线，再按「不需要特权」的能力边界推进；需要 root 的部分显式登记为未实测，这是第 3 节「照实写」的纪律。

**为什么 A 不对**：非 root 做不了，硬做只会浪费时间或破坏机器。

**为什么 C 不对**：在没有授权与快照的前提下提权做破坏性实验，属于越界操作。

## 要点自测

> [!question]- 演练的三条纪律是什么？跑完复核哪三项？
> - **判定**：隔离、上限、清理复核；复核无残留进程、无残留目录、参数与容量回基线。
> - **影响什么**：决定演练会不会伤到别人和后续实验。
> - **不影响什么**：不限制实验数量；限制的是每条实验的影响范围。
> - **落点**：每条演练记录的开头写实验前基线，结尾写复核三项。
>
> [!question]- 为什么每个实验都要留下「观测指纹」？
> - **判定**：指纹是故障在指标上的形态，是可迁移的部分。
> - **例子**：`%util` 几乎不变但 `w_await` 与 `aqu-sz` 同时上升 → 排队而不是设备忙；`memory.events` 出现 `oom_kill` → cgroup 级 OOM。
> - **影响什么**：决定下次遇到同类现象时你能否在几分钟内认出来。
> - **第一反应不要是什么**：不要把「命令跑通了」当作实验完成。
>
> [!question]- 为什么恢复要计时？
> - **判定**：恢复耗时是对齐 RTO 的唯一证据；不记时长只能证明「能做」，不能证明「够快」。
> - **影响什么**：决定变更窗口与故障预案是否现实。
> - **不影响什么**：第一次记的时长通常很难看，这是正常的起点。
> - **落点**：每条演练记录写「恢复耗时 ____ 秒（对照 RTO ____ 秒）」。
