# 前置：证据与口径

> [!cite] 参考资料

## 0. 30 秒速览

> [!abstract] 这一篇只要记住六句话
> - **一个数字要带三条尾巴才有意义：单位、版本、采集条件。**
>   - 证据（**转引**阶段 10 的多窗口实测，条件以该阶段为准）：同一块盘在 `%util=98.80%`（fio 4 KiB 随机写 qd64）时 `w_await` 只有 `0.09 ms`；而在 `%util=80.10%`（`stress-ng --hdd 2` 并发写、`wareq-sz=3781` 的大请求）时 `w_await` 高达 `6.59 ms`——**没有条件，任何一个数都不能单独代表这块盘**。
> - **本套笔记的口径统一为：容量用 MiB，时间用秒。**
>   - 怎么验证：出题与答题时只认 MiB / 秒；写「MB」「分钟」会被要求换算，这是为了在跨章对比时不出现 1000 与 1024 的混乱。
> - **「我记得」不是证据；证据 = 命令 + 输出形态 + 环境 + 时间。**
>   - 怎么验证：把你的答案给一个没读过这套笔记的人看，他能否照着命令复现同样的结论。
> - **版本差异先于命令记忆，也先于结论。**
>   - 证据：RHEL 9 的基线内核是 5.14、Ubuntu 24.04 是 6.8、Debian 12 是 6.1，而 RHEL 会把新特性**回移**进 5.14——「你的内核怎么这么老」不是有效判断。
> - **分位数也有口径：同一组样本的 p95 可以是 20 ms，也可以是 100 ms。**
>   - 证据：1000 个样本（950×20 ms + 45×100 ms + 5×2000 ms）实测平均 33.5 ms，p95 按四种常见算法分别是 **20.0 / 24.0 / 96.0 / 100.0 ms**——报 p95 必须连口径一起报。
> - **说不清就显式说「没验证过」。**
>   - 怎么验证：给答案加一行「未实测 + 原因 + 补做方式」；把「应该是」从结论里赶出去，比多背一条命令更能建立信任。

## 1. 证据的三要素

一条能在生产与面试里站得住的证据，必须同时满足三条：

| 要素 | 含义 | 反例 |
| --- | --- | --- |
| **可复现** | 别人照着你的命令与条件，能得到同样的结论 | 「我以前遇到过一次」 |
| **可定位** | 能说清它是哪一层、哪一环的证据 | 「系统有问题」 |
| **可比较** | 自带基线与条件，能和另一次采集对比 | 「`await` 是 54 ms，很高」 |

> [!important] 一句最常被追问的话
> **「这个数字是在什么条件下采集的？」** —— 你要默认面试官与同事都会问这一句，并在答案里先答掉它。

## 2. 口径：单位、版本、条件

### 2.1 单位

本套笔记统一两个单位，越界就要显式换算：

| 量 | 统一口径 | 常见错误 |
| --- | --- | --- |
| 容量 / 内存 / 磁盘 | **MiB**、GiB | 与 MB、GB 混用（差 4.9%） |
| 时间 | **秒**（毫秒写 `ms`） | 「两分钟」「半小时」混入答题 |
| 速率 | 次/秒、MiB/s | 只写数字不写速率 |
| 延迟 | ms 或 µs，注明测量点 | 「延迟很高」 |

### 2.2 版本与发行版

一条只读命令就能把版本基线钉住，答案里应当顺手给出：

```bash
cat /etc/os-release | head -2        # 验证：发行版与版本号
uname -r                             # 验证：内核版本
systemctl --version | head -1        # 验证：systemd 版本
stat -fc %T /sys/fs/cgroup           # 验证：cgroup 版本（cgroup2fs 即 v2）
```

本实验机输出（实测）：`Ubuntu 24.04.5 LTS` / `6.8.0-139-generic` / `systemd 255` / `cgroup2fs`。

为什么这四条要背下来？因为**绝大多数「默认值」和「默认行为」都随它们变化**：`MemoryAccounting` 的开法、`OOMPolicy` 的默认值、`tcp_tw_reuse` 的版本差异、SELinux 还是 AppArmor，全都取决于这四项。

### 2.3 采集条件

同一个指标在不同条件下能差一个数量级，所以条件要和数字一起说。至少记这五项：

| 条件 | 为什么影响结论 | 举例 |
| --- | --- | --- |
| 负载与并发 | 利用率（`%util`）高**不等于**排队深，`await` 与 `aqu-sz` 才回答排队 | 转引阶段 10：`%util=98.80%` 时 `aqu-sz=3.15`、`w_await=0.09 ms`；而 `%util=80.10%` 时 `aqu-sz=2.14`、`w_await=6.59 ms` |
| 采样间隔 | `top` 首屏只有一两秒窗口，反映的是**很短的一段差分**，**不是**「自开机平均」 | 本机实测：开机 4 小时后，自旋进程启动 3 秒，`top -b -n1` 首屏即报 `%Cpu(s): 26.2 us`（若真是开机均值应接近 0） |
| 数据量与工作集 | 内存结论与「触碰了多少页」强相关 | 转引阶段 10：触碰 3 GiB 后 `MemAvailable` 7224 → 4145 MiB（降 3079 MiB） |
| 观测工具的开销 | 观测者效应会改变被测对象 | `strace` 实测约 45 倍减速（基线 51 ms → 2280 ms） |
| 时间与时钟 | 跨机日志比对依赖时钟同步 | 时钟漂移会让时间线错位 |

## 3. 证据卡：把结论变成可交付物

> [!example]- 证据卡模板（一张卡只放一个结论）
> ```text
> 结论：free 少不等于内存不够；判据是 MemAvailable + PSI。
> 命令：free -m; cat /proc/pressure/memory
> 输出形态：MemAvailable 下降但 PSI 的 some/full 全为 0
> 环境：Ubuntu 24.04.5 LTS（VMware 虚拟机）/ 内核 6.8.0-139-generic / 7894 MiB / root 可用
> 条件：分配并逐页触碰 3 GiB；采样为分配完成后立即读取
> 实测（转引阶段 10）：MemAvailable 7224 MiB → 4145 MiB，PSI 的 avg10/60/300 全 0
> 边界：这是「有缓存、无压力」；若 PSI 上升则属于内存压力，处置不同
> 第一反应不要：不要因为 free 少就重启服务或加内存。
> 出处：阶段 4 的内存章；对应子笔记见该阶段索引。
> ```
>
> 「输出形态」这一行很关键：它让你在没有原始终端的情况下，也能判断别人的输出是否印证了结论。

## 4. 版本与结论的三种关系

不是所有结论都对版本敏感，分清楚能省很多解释成本：

| 类型 | 说明 | 举例 |
| --- | --- | --- |
| **强版本相关** | 换版本结论可能反转 | `OOMPolicy` 的默认行为、`tcp_tw_reuse` 的语义、`systemd` 的 `NotifyAccess` 默认值 |
| **弱版本相关** | 机制不变，参数或路径不同 | `sysctl.d` 的目录合并顺序、unit 文件 drop-in 位置 |
| **版本无关** | 属于协议或文件系统语义 | `TIME_WAIT` 由主动关闭方进入、ext4 的 inode 数量在 `mkfs` 时固定 |

答题时的写法：强相关的先报版本，弱相关的一句话带过，无关的直接讲机制。

## 5. 生产动作：把口径写进日常记录

> [!example]- 生产动作 1：给三条已有结论补条件（生产机也可以做，只读）
> **怎么做**：从错题本里挑三条带数字的结论，用第 2 节的五项条件逐一补齐；缺哪一项就去补一次只读采集。
> **预期**：你会发现至少一条「数字没问题，但条件写错了」，这正是把「背答案」升级为「会判断」的分界线。
> **风险**：无。**耗时**：约 20 分钟。**回滚**：不需要。

> [!example]- 生产动作 2：做一次「同机两次采集」的对比
> **怎么做**：在同一个业务窗口的峰、谷各采一次同一组指标（`free -m`、`iostat -x 1 3`、`ss -s`），把两份输出贴进证据卡，写明时间。
> **预期**：峰谷两组数字差异明显，这正是「没有基线就没有『变慢了』」的实物证据。
> **风险**：无（只读；`iostat` 有轻微开销，采样间隔不要低于 1 秒）。**耗时**：约 30 分钟。**回滚**：不需要。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 「内存用了 90%，快满了」 | 缺少 `available` 与 PSI；Linux 用空闲内存做缓存是正常工作状态 |
| 「`await` 高，磁盘要坏了」 | 没有并发与队列深度；同一块盘在不同窗口实测可以从 0.09 ms 到 6.59 ms（阶段 10） |
| 「p95 是 100 ms」 | 没有说口径；同一组样本按四种算法可以是 20 / 24 / 96 / 100 ms |
| 「内核 5.14 太老了」 | 发行版回移会让版本号失去可比性；要看该发行版 release notes |
| 「我在 Ubuntu 上试过，RHEL 也一样」 | 发行版差异四件套（包管理 / 防火墙 / 网络 / 访问控制）完全不同 |
| 「`top` 显示 CPU 80%，所以 CPU 是瓶颈」 | `top` 默认是**整机平均视角**，会掩盖单核打满（本机实测整机 `%usr` 25.04% 时单核已 100.00%）；`wa`/`si` 也要拆开看。注意 `top` 首屏是短窗口差分、**不是**开机均值 |
| 只报结论不报命令 | 别人无法复现，也无法判断你是否混淆了层 |
| 报告里不写「未验证」的部分 | 把不确定包装成确定，是事故与面试里最贵的错误 |

## 决策练习

> 面试官问：「你们线上一个服务响应变慢，你怎么判断是磁盘的问题？」你手上没有那台机器的任何历史数据。第一个回答应该是什么方向？
>
> - **A. 先说「磁盘 IO 高一般看 `%util`」，然后建议他去看 `iostat`。**
> - **B. 先问/先说明三件事：什么现象、从什么时候开始、有没有基线；然后给分层判定路径（先看进程是否在等 IO，再看设备指标，最后对齐业务延迟）。**
> - **C. 直接给一套完整的排查命令清单，从 `iostat` 到 `iotop` 到 `blktrace`。**

**为什么选 B**：题目给的是开放现象，第一步是**口径与影响面**——没有基线和时间线，任何设备指标都无法解释「变慢」。B 展示了判断顺序，也知道证据要从哪一层取。

**为什么 A 不对**：`%util` 在 NVMe 上常常接近 100% 却与延迟无关；直接给指标等于跳过分层。

**为什么 C 不对**：命令清单没有错，但它是**第 3 步**的动作；先给工具、后给判断，会被追问「如果 `%util` 不高呢」而无法接住。

## 要点自测

> [!question]- 一个数字要带哪三条尾巴？各举一个反例。
> - **判定**：单位、版本、采集条件。
> - **反例**：容量写 MB 而存储按 MiB 报；在 Ubuntu 上得出 RHEL 的默认值；报 p95 不说算法。
> - **影响什么**：决定这个数字能不能与别人的数字比较，也决定它能不能被复现。
> - **第一反应不要是什么**：不要用「差不多」「大概」掩护不确定，直接写「未实测」。
>
> [!question]- 为什么说「`strace` 的代价」也属于口径问题？
> - **判定**：观测工具会改变被测系统（观测者效应），`strace` 实测约 45 倍减速（同一段代码基线 51 ms → 加 `strace -c -f` 后 2280 ms）。
> - **影响什么**：在生产机上用它定位性能问题，可能把「慢」变成「更慢」，甚至影响业务。
> - **不影响什么**：不否定它的价值——短时、定向、单进程仍然可用，但要标出代价与上限。
> - **落点**：选择工具时先问「这个工具会不会改变结论」，再问「它给的信息够不够」。
>
> [!question]- 报告里为什么必须写「未实测」的部分？
> - **判定**：把不确定写成确定，会在下次使用时变成错误结论。
> - **影响什么**：决定别人敢不敢按你的结论操作，也决定复盘时能不能信任时间线。
> - **不影响什么**：不是说「没验证就不能写」，而是写清「哪些验证过、哪些没有、怎么补」。
> - **落点**：未实测的部分写成三段——未实测内容 / 原因（缺机器、缺权限、缺依赖）/ 补做方式。
