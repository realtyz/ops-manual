## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **所有开放题都用同一副骨架：现象与影响面 → 分层 → 证据 → 结论 → 止损 → 改进。**
>   - 怎么验证：随便挑一题，把这六段各写一句，答案立刻成形。
> - **评分看五要素：影响面、分层、证据、边界、止损与回滚。**
>   - 证据：本目录子笔记 08 的评分表（每项 0~2 分）；只给结论的答案最多 2 分。
> - **每题都必须有一句「第一反应不要做什么」。**
>   - 理由：这句话直接体现你是否真的处理过或演练过，而不是背过。
> - **证据要落在「哪一层的哪一个量」，不是「跑一下命令看看」。**
>   - 怎么验证：把答案里的每条命令旁注上「它验证什么」；注不出的命令删掉。
> - **同一现象至少准备两个成因。**
>   - 证据：`load` 高可以来自 CPU、D 状态、内存回收、锁等待；只答一种会在追问「还有呢」时卡住。

## 1. 六段骨架与模板句

```text
1 现象与影响面：从 <时间> 起，<谁> 受影响，<多严重>，<范围>。
2 分层判断：先按分层排除，<层 A> 正常，<层 B> 有信号，问题落在 <层 B>。
3 证据：<命令> 显示 <数值/形态>，与 <基线/另一视角> 对齐后成立。
4 结论：判断是 <根因假设>，置信度 <高/中/低>，因为 <支持与排除理由>。
5 止损：先做 <可逆动作>，验收看 <指标 + 业务 + 观察窗口>，回滚方式 <…>。
6 改进：<监控/流程/容量> 上补一项，owner 与期限 <…>；本次未验证的是 <…>。
```

四句必须出现的「经验句」：

- **「第一反应不要做什么」**——越具体越好（「不要 `mount -o remount,rw`」「不要先重启」）。
- **「先做可逆的动作」**——限流 / 摘流量 / 回滚优先。
- **「一次只改一个变量」**——否则事后无法归因。
- **「哪些证据重启即失」**——决定取证与止损的先后。

## 2. 十五道场景题的骨架

### 题 1：机器负载很高，但 CPU 使用率不高

- **分层**：调度与等待层，不是算力层。
- **证据**：`uptime` 看 load 与核数之比；`vmstat 1 3` 看 `b`（不可中断睡眠）与 `wa`；`ps -eo stat,wchan,cmd` 找 `D` 状态进程；`iostat -x 1 3` 看设备队列。
- **结论候选**：① IO 等待；② 内存回收 / swap；③ 锁或非自愿切换异常；④ 文件系统或网络存储阻塞。
- **止损**：先减少产生等待的负载（限流 / 降低并发），不要直接重启。
- **不要做**：不要因为「CPU 不高」就排除了 CPU 相关原因（单核饱和也能造成等待）。
- **归属**：阶段 10 为主，证据落在阶段 3、4、5。

### 题 2：服务内存持续增长，最终被 OOM kill

- **分层**：内存层；先分「用量」与「压力」，再分「进程级」与「cgroup 级」。
- **证据**：趋势用 `pidstat -r 1` 或监控历史（**单次快照说明不了任何问题**）；`grep -E 'MemAvailable|Dirty|Slab|Shmem' /proc/meminfo`；`cat /proc/pressure/memory`；容器侧看 `memory.events` 的 `oom_kill` 与 `memory.max`；内核日志确认 OOM 记录。
- **结论候选**：① 真泄漏（RSS 单调增长）；② 缓存 / slab / tmpfs 占用；③ cgroup 上限过低；④ 突发批量任务。
- **止损**：限制并发或重启单个实例（接受容量下降），保留现场；回滚即恢复原限制。
- **不要做**：**不要用退出码 137 当作 OOM 的证据**（人工 `kill -9` 也是 137）；不要先清 Page Cache。
- **归属**：阶段 4 为主，容器部分落在阶段 3 与阶段 11。

### 题 3：磁盘空间满 / inode 满

- **分层**：存储层；先分容量、inode、保留块、配额、被删除但被持有五种情况。
- **证据**：`df -h`、`df -i`、`lsof +L1`、`du -x -h --max-depth=1`、配额报表；「有空间却写不进去」还要看是不是 `No space left on device` 还是 `Disk quota exceeded`。
- **结论候选**：① 日志 / 数据增长；② inode 被小文件耗尽；③ ext4 保留块（默认 5%）；④ 配额到顶；⑤ 删除文件仍被进程持有。
- **止损**：先扩容或迁移写热点（可逆），再清理；**清理前先确认文件不再被进程持有**。
- **不要做**：不要先删「看起来最大」的文件；不要在未确认持有者时用 `rm` 假装释放空间。
- **归属**：阶段 5 为主，日志部分落在阶段 9。

### 题 4：`too many open files` / 无法创建新进程

- **分层**：资源限制五层——当前会话（`ulimit`）、PAM 会话（`limits.conf`）、服务（unit 的 `LimitXXX=` / `TasksMax=`）、cgroup（`pids.max`）、内核全局（`fs.file-max`、`kernel.pid_max`）。
- **证据**：服务侧 `systemctl show -p LimitNOFILE,TasksMax X`；进程侧 `/proc/<pid>/limits`；系统侧 `sysctl fs.file-max kernel.pid_max kernel.threads-max`；cgroup 侧 `pids.current` / `pids.max`。
- **结论候选**：① 服务级 limit 太小；② 连接或文件描述符泄漏；③ 线程/进程数达到 `pids.max`；④ fork 风暴（短命进程）。
- **止损**：先限流或重启单个实例；改限制属于变更，要按变更流程做。
- **不要做**：**不要只改 `/etc/security/limits.conf` 就以为服务生效**（systemd 服务读 unit 的 `LimitXXX=`）。
- **归属**：阶段 3 为主，服务侧落在阶段 8。

### 题 5：服务连不上——链路、路由、防火墙、DNS、应用逐层验证

- **分层**：按 `link/driver → IP/路由 → 端口与防火墙 → DNS → 应用` 自下而上。
- **证据**：`ip -brief addr`、`ip route get <IP>`、`ss -lnt`（服务是否在听）、`nstat -az | grep -iE 'listen|drop'`（队列溢出）、`ss -ti`（RTT 与重传）、`resolvectl query` / `dig +stats`、应用日志。
- **结论候选**：① 服务没监听；② 防火墙 / 安全组丢包；③ 全连接队列溢出导致静默丢 SYN；④ DNS 解析异常；⑤ 应用层拒绝（证书、鉴权、后端）。
- **止损**：先确认服务本身是否健康，再考虑摘流量或扩容接入层。
- **不要做**：不要用 `ping` 通就断定「网络没问题」（它只证明 ICMP）。
- **归属**：阶段 6 为主，DNS 落在名字解析站，应用层落在阶段 8、9。

### 题 6：偶发网络延迟与丢包

- **分层**：传输层与链路层；先判断是「丢包」还是「排队」。
- **证据**：`ss -ti` 看 `rtt`/`minrtt`/`retrans`/`cwnd`/`app_limited`；`nstat -az` 看重传与丢弃计数；`tc -s qdisc show` 看排队与丢弃；必要时 `tcpdump` 定向抓包（先限时限量）；对端 / 中间设备的计数。
- **结论候选**：① 链路丢包；② 队列排队（尾延迟）；③ MTU / 分片问题；④ 连接跟踪表压力；⑤ 对端限速。
- **止损**：先摘掉异常实例或降低并发；调参属于后续变更。
- **不要做**：不要一上来就全量抓包（既影响性能也抓不完）。
- **归属**：阶段 6 为主，阶段 10 的「先计数后抓包」决策线。

### 题 7：服务起不来 / 开机不自启 / 定时任务没执行

- **分层**：unit 层（描述与依赖）→ 判定层（什么算启动完成）→ 环境层（沙箱、身份、路径）。
- **证据**：`systemctl status X` 的三段（`Loaded`/`Active`/`CGroup`）；`journalctl -u X -b`；`systemctl show -p Type,ExecMainCode,ExecMainStatus,User X`；`systemctl list-timers --all`；cron 的环境（`PATH`、工作目录、非交互 shell）。
- **结论候选**：① 依赖未满足（`Requires=`/`After=` 写错）；② `Type=` 选错导致「假失败」；③ 沙箱与路径问题（`ProtectSystem=`、`ReadWritePaths=`）；④ 权限或身份问题；⑤ timer 未 enable 或时间语义写错。
- **止损**：先让服务以最小改动恢复（必要时临时改回旧 unit），保留 `status` 与日志。
- **不要做**：不要直接 `systemctl restart` 了事；不要只看 unit 文件而不看 `systemctl show` 的生效值。
- **归属**：阶段 8 为主，日志落在阶段 9。

### 题 8：机器疑似被入侵的处置与取证

- **分层**：账号与认证层 → 权限与提权面 → 网络与进程层 → 持久化层（计划任务 / 自启）。
- **证据**：`who`、`last`、`journalctl -u ssh`、`ss -tunap`、`ps auxf`、`find / -perm -4000`、`getcap -r /`、`systemctl list-timers`、`crontab -l`、`ls -l /etc/cron*`。
- **结论候选**：① 弱口令或密钥泄漏；② 提权面被利用（SUID / capabilities）；③ 未被发现的持久化；④ 仅是一次误报（需用证据排除）。
- **止损**：**先隔离而不是先清理**——保住现场（快照、镜像、日志导出），再按流程通报。
- **不要做**：不要在取证前 `kill` 进程、删文件或重启；那会毁掉全部现场。
- **归属**：阶段 7 为主，审计与取证篇；流程落在阶段 11。

### 题 9：内核 panic 后的现场分析与恢复

- **分层**：启动链第 3、4 环；先确认是否有 `vmcore`。
- **证据**：控制台 / 带外日志、`journalctl -b -1 -k`、`/var/crash/`、`dmesg` 的上一轮引导段、kdump 服务状态。
- **结论候选**：① 驱动或硬件故障；② 内核 bug；③ 内存故障；④ 前一次变更引入（先对齐变更时间线）。
- **止损**：先让服务在其它节点承接（高可用视角），再决定是否分析 core。
- **不要做**：不要「再重启一次看看」；重启会覆盖证据（日志未持久化时尤其致命）。
- **归属**：阶段 2 为主；**本机未实测**——需要可崩溃的实验机与独立控制台（本实验机只有 SSH 一条通道，且 `kdump inactive`、`kernel.sysrq = 176` 不含 panic 位）。

### 题 10：根文件系统变成只读（remount ro）

- **分层**：存储层；只读是内核的保护动作，不是原因。
- **证据**：`dmesg | grep -i -E 'ext4|xfs|I/O error'`；`mount | grep ' / '` 看挂载选项；`journalctl -k`；`smartctl` / `nvme smart-log`（若可用）；阵列状态。
- **结论候选**：① 设备或链路故障；② 文件系统错误触发的保护；③ 阵列降级；④ 人为 / 编排动作。
- **止损**：先把业务切走，再按「修还是重来」的两分钟判断决定路径。
- **不要做**：**不要第一反应 `mount -o remount,rw`**——那会把只读保护关掉，可能扩大损坏。
- **归属**：阶段 5 为主，恢复路径落在阶段 11。

### 题 11：单核 CPU 打满，整机 CPU 不高但延迟飙升

- **分层**：调度层；整机平均掩盖单核饱和。
- **证据**：`mpstat -P ALL 1 3` 找跑满的核；`pidstat -t -p <pid> 1` 看线程；业务延迟探针的 `p50/max`；`/proc/<pid>/status` 的 `voluntary_ctxt_switches`。
- **结论候选**：① 单线程热点；② 同核超卖（多个进程抢同一个核）；③ 中断 / 软中断集中在一个核。
- **实测参照（转引阶段 10）**：单核 100%（4 vCPU 的 1/4）时整机 `%usr` 只有 25.00%、`load` 只有 0.34；同核 +4 竞争者后吞吐只剩 21%（下降约 79%），延迟探针 `max` 8.36 → 16.58 ms、`p95` 8.25 → 10.99 ms（`p50` 8.13 → 8.06 ms，基本不变——抬升的是尾延迟）。
- **止损**：先限制并发或调整绑核，再评估扩容。
- **不要做**：不要用整机 CPU 平均值下结论；不要先加核而不定位热点。
- **归属**：阶段 10 为主，线程与调度落在阶段 3。

### 题 12：资源都空闲但服务变慢

- **分层**：从「资源层」转向「等待层与应用层」：锁、GC、下游依赖、DNS、连接池。
- **证据**：进程状态分布（`S`/`D`/`R`）、`/proc/<pid>/wchan`、`strace -c -f -p`（短时、注意约 45 倍代价，见阶段 10 实测）、应用自身的分位数指标、下游探活与 DNS 计时。
- **结论候选**：① 锁竞争或串行化；② 连接池耗尽；③ 下游慢；④ DNS 慢；⑤ GC 停顿。
- **止损**：先降并发或摘流量，避免把下游压垮。
- **不要做**：不要因为资源空闲就断定「不是系统问题」，也不要长时间 `strace` 生产进程。
- **归属**：阶段 10 为主，应用线索落在阶段 9。

### 题 13：SSH 登录很慢或时通时断

- **分层**：名字解析层 → 认证层 → 网络层。
- **证据**：`ssh -vvv` 看每个阶段耗时；服务端 `UseDNS` / 反向解析；`sshd -T` 看最终生效配置；`ss -tn state established` 与 `ss -ti` 看重传；MTU 与分片。
- **结论候选**：① 反向 DNS 超时；② GSSAPI 或认证方式尝试超时；③ 网络丢包 / MTU；④ 认证服务（LDAP / 双因子）慢。
- **止损**：先保证一条可靠通道（带外 / 控制台），再修配置。
- **不要做**：不要在只靠 SSH 的情况下重启网络；先确认控制台可用。
- **归属**：阶段 6 与阶段 7 为主。

### 题 14：服务器时间漂移，污染日志比对与证书校验

- **分层**：时间基线层；影响可观测性与安全两侧。
- **证据**：`timedatectl`、`chronyc tracking`（或 `ntpq -p`）、`dmesg` 时间跳变记录、日志时间线是否自相矛盾。
- **结论候选**：① NTP 不可达；② 虚拟化宿主时间问题；③ 时区配置错误；④ 手动改时间造成跳变。
- **止损**：先恢复同步并记录跳变量，再回看时间线「哪些结论需要重算」。
- **不要做**：不要用 `date -s` 手动对时（会造成跳变并破坏增量日志）。
- **归属**：阶段 9 与阶段 11 为主，证书部分落在阶段 11。

### 题 15：容器被 OOMKilled

- **分层**：cgroup 内存层 + 宿主内存层；两个视角都要看。
- **证据**：容器侧该 cgroup 的 `memory.events`（`oom_kill`）、`memory.max`、`memory.current`、`memory.peak`；宿主侧 `MemAvailable`、PSI；内核日志中的 OOM 记录与 cgroup 名。
- **结论候选**：① 容器上限过低；② 应用泄漏；③ 突发批量；④ 整机压力导致全局 OOM（少见但存在）。
- **止损**：先让容器以受控方式重启 / 降配并发，保留 `memory.events` 与日志。
- **不要做**：不要在容器里用 `free` / `top` 判断容器受限情况；不要把 `OOMKilled` 一律归因于宿主机内存不足。
- **归属**：阶段 3、4 为主，编排层概念只做衔接（本目录子笔记 13）。

## 3. 三种危险答案

| 类型 | 表现 | 为什么会挂 |
| --- | --- | --- |
| **命令流** | 「先 `top`、再 `iostat`、再 `ss`……」 | 没有分层与结论，听众不知道你要去哪 |
| **单因论** | 「肯定是 OOM / 肯定是磁盘」 | 追问「还有呢」立刻卡住 |
| **无闭环** | 讲完原因就停 | 生产题必须有止损、验收与回滚 |

## 4. 生产动作：十五题一轮

> [!example]- 生产动作：把十五题压成一分钟版本（不需要机器）
> **怎么做**：每题只写六段各一句，控制在 120~200 字；写完后掐表朗读，超时 90 秒就删掉非关键证据。全部写完后，把十五题打乱顺序重做一遍（交错练习）。
> **预期**：第一轮会明显超时；第二轮会自然形成「先分层、再证据」的固定套路。
> **风险**：无。**耗时**：约 60 分钟（第一轮）+ 40 分钟（第二轮）。**回滚**：不需要。
> **验收**：任抽一题，能在 3 分钟内讲完六段，并接住「你怎么知道」与「换个条件呢」两层追问。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 按命令排布答案 | 变成菜单；面试官无法判断你的判断力 |
| 只给一个成因 | 追问「还有呢」立刻断掉；每题至少准备两个成因 |
| 用「可能是」代替结论 | 该给的置信度与验证方式都没给 |
| 讲完根因不讲止损 | 生产语境里等于没有闭环 |
| 证据里只有命令没有数值 | 无法判断你看到过真实输出 |
| 忽略「第一反应不要做」 | 这句话才是经验密度最高的部分 |

## 决策练习

> 面试官问：「一台服务器的 `load average` 从 2 涨到 30，你怎么查？」你有 3 分钟。第一句话说什么最合适？
>
> - **A. 「先 `uptime`，再 `top`，然后 `iostat`，如果还不行就 `perf`。」**
> - **B. 「先确认三件事：这台机器有几个核、从什么时候开始涨、业务是否已经受影响；然后按 `load` 的三个来源分层——运行队列、D 状态、内存压力，逐层取证。」**
> - **C. 「load 高就是 CPU 忙，先加核。」**

**为什么选 B**：先量化影响面（核数、时间线、业务是否受影响），再分层；这正是第 1 节六段骨架的前两段。

**为什么 A 不对**：命令清单没有方向，也没有影响面。

**为什么 C 不对**：`load` 包含 `D` 状态进程，且必须除以核数；直接加核跳过了判断。

## 要点自测

> [!question]- 六段骨架是什么？哪一段最容易被省略？
> - **判定**：现象与影响面、分层、证据、结论、止损、改进；最常被省略的是**影响面**与**止损**。
> - **影响什么**：省略影响面会让处置顺序失去依据；省略止损在值班场景里等于没有闭环。
> - **不影响什么**：纯理论题可以只讲前四段，但仍要说明边界。
> - **落点**：写答案时先写第 1 段和第 5 段，再补中间。
>
> [!question]- 为什么每题至少要准备两个成因？
> - **判定**：同一现象常常对应多类根因（`load` 高可以是 CPU、D 状态、内存压力、锁）。
> - **影响什么**：决定你在追问「还有呢」时是否立刻断掉。
> - **不影响什么**：不必穷举；两个成因 + 各自排除证据就够了。
> - **落点**：每条骨架写一行「另一个可能是……，排除它要看……」。
>
> [!question]- 为什么「第一反应不要做什么」比命令清单更能体现经验？
> - **判定**：它体现的是判断与风险意识（不重启、不 remount rw、不全量抓包）。
> - **影响什么**：决定你在真实故障中会不会把小问题变成大事故。
> - **不影响什么**：它不替代命令，两者是「判断 + 动作」的关系。
> - **落点**：十五题每题的不要做都要背到能脱口而出。
