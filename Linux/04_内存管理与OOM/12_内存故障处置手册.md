# 内存故障处置手册

> [!cite] 参考资料
> 本篇是收口篇，不引入新机制：命令与判据的出处见各子笔记开头的「参考资料」。主要依据 `man 5 proc`、`man 5 sysctl`、`man 5 systemd.resource-control`、`man 8 systemd-oomd.service` 与内核文档 `Documentation/admin-guide/sysctl/vm.rst`、`Documentation/admin-guide/cgroup-v2.rst`。
>
> 本篇的处置记录模板与限时演练需要在实验机上跑过一遍才算完成；实测结果请回填到对应子笔记。

> **这篇讲什么**：把前 11 篇的机制收敛成**现场可执行的处置顺序**。每一类现象都按「第一反应不要做什么 → 判断顺序 → 证据在哪 → 处置分支」展开，最后给一份记录模板与限时演练。
>
> **必须先读什么**：[[Linux/04_内存管理与OOM/00_导读与知识地图|00 导读]] 第 6 节的「故障现场定位表」；具体机制见对应子笔记。
>
> **读完能做什么**：接到一个内存类告警，10 分钟内定位到类别，30 分钟内给出有证据支撑的处置方案，并留下可复盘的记录。
>
> 所属：[[Linux/04_内存管理与OOM/00_导读与知识地图|04 内存管理与 OOM]] 的收口 · 主要练 **M2、M4、M5、M8** 与 **T4**

## 0. 统一原则

1. **先确认「账本归属」**：整机、某个服务、某个容器，三者的账不同；先确定看哪本账。
2. **先取证再动手**：进程还在时能取 `memory.current`/`stat`/`events`/`smaps_rollup`；重启后这些都没了。
3. **区分「变慢」与「被杀」**：变慢属于可调优（回收、回写、换页）；被杀只能复盘与加固。
4. **区分「够不够」与「谁在用」**：前者看 `MemAvailable` + PSI，后者看账目（`Shmem`/`Slab`/`memory.stat`）。
5. **改动必须有回滚**：任何参数或限制的调整，都要把原值与恢复命令写在记录里（子笔记 11）。

## 1. 现象：内存去哪了

> [!tip] 第一反应不要是「加内存」或「清缓存」
> 先把账对上。`free` 的 `used` 减掉了缓存，进程 `RSS` 又漏掉内核与共享部分——直接相加永远对不上。

判断顺序：

1. **分大类**：`MemAvailable` 与 `free` 的差距、`Cached` 的构成、`Slab`/`SReclaimable`/`SUnreclaim`、`Shmem`；
2. **查 tmpfs 与共享内存**：`df -h | grep tmpfs`、`df -h /dev/shm`、`ipcs -m`；无 swap 时基本回收不掉；
3. **查内核侧**：`slabtop` 找膨胀的 slab；`PageTables`/`KernelStack`/`VmallocUsed` 是否异常；
4. **查 cgroup 侧**：服务/容器的 `memory.stat` 里 `anon`/`file`/`shmem`/`slab` 各占多少；
5. **最后才谈扩容**：确认是不可回收的真实需求，再加内存。

```bash
free -h; grep -E '^(MemAvailable|Cached|Shmem|Slab|SReclaimable|SUnreclaim|PageTables|KernelStack):' /proc/meminfo
df -h | grep -i tmpfs; df -h /dev/shm; ipcs -m | head
slabtop -o -s c | head -15
cat /sys/fs/cgroup/<路径>/memory.stat | grep -E '^(anon|file|shmem|slab|sock) '
```

详细展开见子笔记 09。

## 2. 现象：`free` 看着还有内存，却发生了 OOM

> [!tip] 第一反应不要是「日志写错了」
> 常见原因有四类：cgroup 上限、tmpfs、内核内存、水位与碎片。前三类属于「内存被谁占走/记在谁账上」，对应子笔记 09 的对账顺序；第四类不是账目问题，而是「有空闲页但拼不出连续块」。

判断顺序：

1. **看 cgroup 上限**（最常见）：日志前缀若是 `Memory cgroup out of memory`，读该组的 `memory.events`/`memory.current`/`memory.max`；
2. **看 tmpfs/共享内存**：`Shmem` 很大且没有 swap → `MemAvailable` 估算偏乐观；
3. **看内核内存**：`SUnreclaim`、`PageTables`、`KernelStack` 涨上来会挤压用户态可用内存；
4. **看水位与碎片**：`free` 有量但不连续（高阶分配失败）→ `/proc/buddyinfo`（各阶连续空闲块分布）、`compact_stall` 与内核分配失败信息。

```bash
cat /sys/fs/cgroup/<路径>/memory.events; cat /sys/fs/cgroup/<路径>/memory.current
grep -E '^(Shmem|SUnreclaim|PageTables|KernelStack|VmallocUsed|MemAvailable):' /proc/meminfo
cat /proc/buddyinfo
cat /proc/vmstat | grep -E '^(compact_stall|compact_fail|allocstall)'
```

详细展开见子笔记 09、10。

## 3. 现象：`si/so` 长期非 0（换页抖动）

> [!tip] 第一反应不要是「把 `swappiness` 调 0 或直接 `swapoff`」
> 先分清是「换出去就不用了」还是「反复换入换出」；后者才是灾难，而关 swap 会把延迟问题升级成可用性问题。

判断顺序：

1. **看方向**：`si`（换入）与 `so`（换出）哪个持续非 0；只有 `so` 且 PSI 平稳，问题通常不大；
2. **看压力**：`/proc/pressure/memory` 的 `some`/`full` 是否同步升高；
3. **看是谁**：`grep VmSwap /proc/*/status` 找被换出最多的进程，再看它所在的 cgroup；
4. **再谈手段**：扩容、给服务加限制、降低常驻集、调 `swappiness`——而不是一刀切关 swap。

```bash
vmstat 1 10
cat /proc/pressure/memory
grep VmSwap /proc/*/status 2>/dev/null | sort -k2 -rn | head
cat /sys/fs/cgroup/<路径>/memory.pressure
```

详细展开见子笔记 07。

## 4. 现象：写入卡顿、进程进 `D` 状态

> [!tip] 第一反应不要是「加内存」
> 这类问题的根因通常是**回写跟不上**，不是内存不够。

判断顺序：

1. **看脏页水位**：`Dirty`/`Writeback` 与 `dirty_ratio`/`dirty_bytes` 的关系；
2. **看底层能力**：`iostat -x` 的 `await`/`aqu-sz`/`%util`；
3. **看是谁在写**：`pidstat -d`、`iotop -o` 定位写入源与写放大；
4. **对策**：错峰批量任务、降低回写阈值让写入更平滑（或反之）、提升底层性能——**不是 `drop_caches`**。

```bash
grep -E '^(Dirty|Writeback):' /proc/meminfo
iostat -x 1 5
pidstat -d 1 5
```

详细展开见子笔记 06。

## 5. 现象：内存缓慢增长，怀疑泄漏

> [!tip] 第一反应不要是「涨了就是泄漏」
> 业务自然增长、页缓存与连接池扩张都会让占用上升；**泄漏的定义是「不再需要的内存没有被释放」**，只能用趋势与稳态判断。

判断顺序：

1. **取趋势**：按小时/天采样同一口径（`VmRSS`、`RssAnon`、`memory.current`），看是否只涨不落、斜率是否恒定；
2. **分口径**：`RssAnon` 持续涨是典型的堆泄漏；`RssFile`/`file` 涨多为缓存；`RssShmem`/`shmem` 涨要查共享内存与 tmpfs；
3. **看私有占用**：用 `smaps_rollup` 的 `Private_Dirty` 与 `Pss`，避免被共享页误导；
4. **对压力**：如果涨的同时 major fault、PSI、GC 时间都在恶化，优先级要提高；
5. **止损**：先给 cgroup 配 `MemoryHigh`/`MemoryMax` 与告警，防止拖垮整机；滚动重启只是止血，必须同时保留趋势数据与（必要时）内存 dump。

```bash
for i in $(seq 1 6); do date '+%F %T'; grep -E 'VmRSS|RssAnon|RssFile|RssShmem|VmSwap' /proc/<pid>/status; sleep 600; done
cat /proc/<pid>/smaps_rollup | grep -E 'Pss|Private_Dirty'
cat /sys/fs/cgroup/<路径>/memory.current; cat /sys/fs/cgroup/<路径>/memory.stat | grep -E '^(anon|file|shmem) '
```

详细展开见子笔记 05、10。

## 6. 现象：容器被 `OOMKilled`

> [!tip] 第一反应不要是「宿主内存还够，排除内存问题」
> 容器的内存账是 cgroup 的账，与宿主 `free` 无关。

判断顺序：

1. **确认是不是 cgroup OOM**：内核日志里的 `Memory cgroup out of memory` 与 `task_memcg=`/`oom_memcg=`；
2. **看上限于用量**：`memory.max`、`memory.current`、`memory.peak`、`memory.events`；
3. **看构成**：`memory.stat` 里是 `anon`、`file` 还是 `shmem` 在涨；
4. **看编排层状态**：容器被杀后编排层会记录 `OOMKilled` 与上次退出状态；结合 requests/limits 判断是超限还是节点压力驱逐（编排层细节不在本章展开）；
5. **对策**：调 limits、限制 `/dev/shm`、给应用加内存上限与 GC 参数；注意容器写日志同样会把 `file` 记账到本容器。

```bash
journalctl -k -b | grep -i 'Memory cgroup out of memory' | tail -5
cat /sys/fs/cgroup/<容器节点>/memory.peak /sys/fs/cgroup/<容器节点>/memory.max
cat /sys/fs/cgroup/<容器节点>/memory.stat | grep -E '^(anon|file|shmem|sock) '
docker stats --no-stream <容器>       # 或编排层命令，看运行时视角
```

详细展开见子笔记 10。

## 7. 现象：确认一次 OOM，以及「谁被杀」

> [!tip] 第一反应不要是「看退出码 137 就下结论」
> 137 只说明被 `SIGKILL` 杀死（人工 `kill -9` 也是 137）；定性证据只有内核日志与 cgroup 事件计数。

固定六步（顺序不要乱）：

1. **定时间点与影响面**：`journalctl --since '<时间>'`、`journalctl -b -1` 与业务告警对齐；
2. **分清整机还是 cgroup**：日志前缀 `Out of memory:` 对 `Memory cgroup out of memory:`；
3. **看被选中进程与权重**：`anon-rss`、`pgtables`、`oom_score_adj`；
4. **看当时水位**：日志前各 zone 的 `free`/`min`/`low`/`high`；
5. **看 cgroup 侧数据**：`memory.events` 的 `oom_kill`、`memory.current`/`peak`、`memory.stat`；
6. **回到限制来源**：`memory.max` 太小、整机水位不足，还是某进程/缓存突然涨上来。

```bash
journalctl -k -b | grep -i -E 'Memory cgroup out of memory|Out of memory: Killed process'
journalctl -k -b | grep -B30 'Killed process' | head -60
cat /sys/fs/cgroup/<路径>/memory.events
cat /sys/fs/cgroup/<路径>/memory.stat | grep -E '^(anon|file|shmem|slab|sock) '
systemctl show -p MemoryCurrent -p MemoryMax -p MemoryPeak <unit>
```

## 8. 处置记录模板（M8）

> [!example]- 内存故障处置记录
> **1. 现象**：什么时候、谁报的、影响面（哪些服务/用户）、是否仍在持续。
>
> **2. 账本归属**：整机 / 服务 / 容器；cgroup 路径。
>
> **3. 现场证据**（按时间顺序粘贴原始输出，不要只写结论）：
> - `free -h`、关键 `meminfo` 字段、PSI；
> - `memory.current`/`max`/`peak`/`stat`/`events`；
> - 内核日志片段（含水位块与 `Killed process` 行）；
> - 进程侧 `RSS`/`PSS`/`VmSwap` 与趋势数据。
>
> **4. 判断与根因**：属于哪一类（够不够 / 谁在用 / 变慢 / 被杀）；根因是容量、泄漏、缓存、回写还是限制配置。
>
> **5. 处置动作**：止血动作（限流、重启、扩上限）与取证动作分别是什么；有没有丢失证据。
>
> **6. 回滚与验证**：改动前原值、恢复命令、恢复后验收指标。
>
> **7. 跟进项**：告警阈值、巡检项、代码/配置修复、责任人。

## 9. 限时演练（T4）

> [!example]- 演练：给一个现象，10 分钟内定位到类别
> **场景 A**：某服务反复被 OOMKilled，宿主 `available` 30 GiB。
> **场景 B**：延迟抖动 + `si/so` 非 0，`available` 8 GiB。
> **场景 C**：`free` 显示 `used` 不高，但进程申请内存失败。
>
> **要求**：选一个场景，10 分钟内完成——
> 1. 说出属于哪一类，账本记在谁头上；
> 2. 给出三条取证命令与预期输出；
> 3. 说出「第一反应不要做什么」；
> 4. 写出处置动作与回滚方式。
>
> **验收**：把结果填进第 8 节的记录模板；能自圆其说、且每一步都有证据，才算通过。
>
> **风险**：只读演练可以在生产机上做；如果要实际注入故障（造压力、触发 OOM），只在可快照实验机上进行。

## 10. 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 不确认账本归属就开始查 | 整机、服务、容器的账不同，很容易得出「还有内存怎么可能 OOM」 |
| 重启后再去找现场 | cgroup 与进程现场消失，只剩日志 |
| 用退出码 137 定性 OOM | 它只说明被 `SIGKILL`；要看日志与 `memory.events` |
| 一看到 `free` 少就扩容 | 可能是缓存在干活，或者是 cgroup 限制 |
| 一看到 `si/so` 非 0 就关 swap | 会把延迟问题升级成可用性问题 |
| 泄漏判断靠一次 `top` | 单点无法区分自然增长与泄漏 |
| 处置记录只写结论 | 复盘时无法验证；要保留原始输出与时间线 |
| 改动不留原值 | 无法回滚，后续问题会反复出现 |

## 11. 决策练习

> [!question]- 场景：凌晨 02:40 告警「订单服务响应变慢」，同时该主机 `available` 从 12 GiB 降到 3 GiB，PSI memory `some` 从 0.02 升到 0.6，`vmstat` 的 `si/so` 非 0，但该服务进程 `RSS` 只有 2 GiB。你先做什么？
> A. 立刻重启订单服务，恢复可用内存
> B. 先定位「谁在吃内存」：看整机 Top（`ps --sort=-rss`）、`Shmem`/`Slab`/`PageTables`、以及该服务与同机其它服务的 cgroup `memory.current`/`stat`；同时保留 PSI 与 `si/so` 证据，再决定是限流、给责任人加上限还是扩容
> C. 直接把 `vm.swappiness` 调到 0，停止换页
>
> **答案：B。**
> A 会清掉现场（进程内存构成、cgroup 数据），而且没有定位到根因，很可能复发。
> C 会停止换出匿名页，压力直接转成 OOM，是最危险的方向之一。
> B 是正解：**先确定「谁在用」与「压力来源」，再动手**；处置动作要能解释给复盘听。

## 12. 要点自测

> [!question]- 处置内存故障时，统一原则有哪几条？
> - 先确认账本归属；先取证再动手；区分变慢与被杀；区分够不够与谁在用；改动必须留原值与回滚命令。
> - **第一反应不要是什么**：不要先重启、先扩容或先改参数。

> [!question]- 「`free` 有余量却 OOM」的四类原因是什么？
> - cgroup 上限、tmpfs/共享内存、内核内存（`SUnreclaim`/`PageTables`/`KernelStack`）、水位与碎片（高阶分配失败）。
> - 判据分别是 `memory.events`、`Shmem` 与 `df`、`meminfo` 的内核字段、`buddyinfo`/`compact_stall`。
> - **第一反应不要是什么**：不要说日志写错了。

> [!question]- OOM 取证的六步是什么？为什么重启是最后选项？
> - 时间点与影响面 → 整机还是 cgroup → 被选中进程与权重 → 当时水位 → cgroup 侧数据 → 限制来源。
> - 重启会清掉进程与 cgroup 现场；证据一旦丢失就无法复盘根因。
> - **第一反应不要是什么**：不要用「重启后好了」当结论。

> [!question]- 判断「泄漏」需要哪些证据？
> - 同一口径的长期趋势（`RssAnon`、`memory.current`），只涨不落且斜率稳定；
> - 口径拆分（`anon`/`file`/`shmem`）与私有占用（`Private_Dirty`）；
> - 交叉指标（major fault、PSI、GC、业务延迟）同步恶化。
> - **第一反应不要是什么**：不要用单次快照下泄漏结论。

> [!question]- 处置记录里必须包含哪些内容，才能支撑复盘？
> - 现象与时间线、账本归属、原始证据输出、判断与根因、处置动作（止血与取证分开）、回滚与验证、跟进项。
> - **第一反应不要是什么**：不要只写「已重启，恢复正常」。
