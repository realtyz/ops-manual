## 1. 实验 0：只读基线（零风险，先做这个）

```bash
date; hostname; uptime               # 验证：时间基线与负载
uname -r; cat /etc/os-release | head -3
                                     # 验证：内核与发行版（决定默认值与行为差异）
free -h                              # 验证：六个口径的即时快照（重点看 available）
cat /proc/meminfo | head -30         # 验证：MemTotal/MemAvailable/Cached/Shmem/Dirty 等
cat /proc/pressure/memory            # 验证：PSI some/full 的基线
vmstat 1 5                           # 验证：si/so、wa、r/b 的组合基线
swapon --show                        # 验证：swap 设备、大小与优先级（无输出即未配 swap）
sysctl vm.swappiness vm.overcommit_memory vm.overcommit_ratio vm.panic_on_oom
                                     # 验证：四个关键策略（tuned 可能覆盖内核默认值）
sysctl vm.min_free_kbytes vm.watermark_scale_factor vm.dirty_ratio vm.dirty_background_ratio
                                     # 验证：水位与回写参数
cat /sys/kernel/mm/transparent_hugepage/enabled
                                     # 验证：THP 策略（延迟敏感服务的常见抖动来源）
stat -fc %T /sys/fs/cgroup           # 验证：cgroup2fs = v2，其它输出按 v1 处理
systemctl show -p MemoryCurrent -p MemoryMax -p MemoryHigh sshd
                                     # 验证：服务层的用量与限制（很多服务默认是 infinity）
ps -eo pid,comm,rss --sort=-rss | head -10
                                     # 验证：内存 Top 10 与它们所属的服务
slabtop -o -s c | head -10           # 验证：slab 占用排行
```

**预期**：`available` 明显大于 `free`（缓存可回收）；`MemAvailable`、PSI 与 swap 三项共同说明这台机器的内存余量；`MemoryMax` 一类限制在 systemd 服务上是「默认无限」的时候居多——这正是「服务没有上限」的常见起点。

**环境**：任意 systemd 发行版。建议隔一段时间再做一次，两次对比才有意义。

**风险**：无，全部只读。

**耗时**：约 20 分钟。

**回滚**：无需回滚。把输出存成一份基线文件。

**要沉淀什么**：这份输出就是 T1 要求的「内存基线卡」：版本、`MemTotal`/`MemAvailable`、PSI `some`、swap 配置、上面列出的内核参数、THP 策略、cgroup 版本、内存 Top 5 及所属服务。

## 3. 总自测

题目前带 **【进阶】** 的对应笔记里的进阶小节，答不上来不影响阶段 4 过关。其余题目要求能**盖住答案脱稿讲 3~5 分钟**。

> [!question]- `free` 显示可用内存很少，要紧吗？怎么判断内存真的不够？
> - **先看口径**：`free` 是「完全空闲」，`available`/`MemAvailable` 才是「能给新程序用多少」；判据是后者。
> - **Linux 不上班才是浪费**：缓存占内存是设计目标；`buff/cache` 大部分可回收，回收本身有代价，所以内核不会主动清空它。
> - **真正不够的信号**：PSI `memory some` 持续升高、`si/so` 长期非 0、`pgmajfault` 上升、`allocstall`（direct reclaim）增多、`workingset_refault` 增多。
> - **边界**：`MemAvailable` 是估算，它把 file LRU（含 tmpfs）当作可回收；无 swap 且 tmpfs 很大的机器上会偏乐观。
> - **第一反应不要是什么**：不要看到 `free` 少就加内存，更不要 `drop_caches`。

> [!question]- `malloc` 成功意味着什么？`overcommit_memory` 的三种模式分别是什么？
> - 成功只代表地址空间记账（`VSZ`/`Committed_AS` 涨），第一次写入才通过缺页拿到物理页（`RSS` 涨）。
> - `0` 启发式（默认）、`1` 总是允许、`2` 严格按 `CommitLimit`（`swap + overcommit_ratio% × 物理内存` 或 `overcommit_kbytes`）卡。
> - 模式 2 下合法大申请也可能被拒，需要预留 `admin_reserve_kbytes`。
> - **第一反应不要是什么**：不要把「申请成功」当容量验收，也不要为了防 OOM 无脑切模式 2。

> [!question]- `RSS`、`PSS`、`USS` 差在哪？跨进程比较该用哪个？
> - `RSS`：常驻页，共享页对每个使用者重复计数；`PSS`：共享页按使用者均摊；`USS`：只算私有页。
> - 跨进程比较用 `PSS`/`USS`；「杀掉它/释放它能省多少」用 `USS`；`RSS` 用来快速排序找嫌疑。
> - **第一反应不要是什么**：不要把「所有进程 `RSS` 相加」与物理内存对账。

> [!question]- Page Cache 为什么是资产？脏页积压时会出现什么现象？
> - 它是读缓存与写缓冲；干净的 file 页随时可丢弃，所以 `buff/cache` 高是正常状态。
> - 脏页超过 `dirty_ratio`/`dirty_bytes` 时，发起写的进程被 `balance_dirty_pages` 限速或阻塞——`Dirty` 卡在阈值附近、`await` 高、`wa` 高、进程进 `D` 状态。
> - **第一反应不要是什么**：不要把它当内存不足；也不要指望 `drop_caches` 能清掉脏页。

> [!question]- 三条水位线分别触发什么？`kswapd` 与 direct reclaim 有什么不同？
> - `low` 唤醒 `kswapd` 异步回收，`high` 让它停止，`min` 以下由分配者 direct reclaim，再不够就 OOM。
> - direct reclaim 的停顿直接算在业务进程头上，是延迟尖刺的直接来源；`allocstall`/`pgscan_direct` 增长说明后台回收跟不上。
> - **第一反应不要是什么**：不要把 `min_free_kbytes` 当「越大越安全」的参数。

> [!question]- `vm.swappiness` 的真实语义是什么？什么时候必须关闭 swap，关掉有什么代价？
> - 它是回收时对匿名页的倾向权重，不是开关；`0` 表示不到 `high` 水位不主动换出匿名页。
> - 必须关或严格限制的典型场景：延迟敏感的数据库、对尾延迟一致性有硬要求的服务；节点类系统按所用平台的官方文档处理。
> - 关掉的代价：匿名页无处可去，压力直接变成 OOM；前提是有 cgroup 上限、告警与容量水位。
> - **第一反应不要是什么**：不要为了「性能」在所有机器上统一 `swapoff`。

> [!question]- OOM Killer 怎么挑进程？为什么容器里被杀的常常不是「最占内存的」？
> - 得分 ≈ 归一化后的（`RSS` + swap 中的页 + 页表）+ `oom_score_adj` 权重；同一轮 OOM 内比较，得分最高者被杀。
> - cgroup OOM 只在该 cgroup 内选人，所以被杀进程可能只有几百 MiB，而整机还有几十 GiB 空闲。
> - **第一反应不要是什么**：不要用退出码 137 定性，也不要在没看 `memory.events` 前断言「杀错人了」。

> [!question]- 整机 OOM 与 cgroup OOM 的日志怎么区分？六步取证是什么？
> - 前缀：`Out of memory: Killed process` 对 `Memory cgroup out of memory: Killed process`；后者还带 `task_memcg=`/`oom_memcg=` 与 `memory: usage ... limit ...`。
> - 六步：时间点与影响面 → 整机还是 cgroup → 被选中进程与权重 → 当时水位 → cgroup 侧数据 → 限制来源。
> - **第一反应不要是什么**：不要先重启或先扩容；证据一旦丢失就再也拿不回来。

> [!question]- 「内存去哪了」的三类主答案是什么？各自怎么验证？
> - tmpfs 与共享内存：`Shmem`、`df -h | grep tmpfs`、`ipcs -m`；无 swap 时回收不掉。
> - 内核 slab 与 dentry/inode：`Slab`/`SReclaimable`/`SUnreclaim`、`slabtop`。
> - 被 cgroup 计入的页缓存：`memory.stat` 的 `file`。
> - 附加：`PageTables`/`KernelStack`/`VmallocUsed`，以及不计入 `MemTotal` 的 `crashkernel=`/HugePages 预留。
> - **第一反应不要是什么**：不要在没分类前就清缓存或加内存。

> [!question]- 怎么确认「真的在泄漏」？怎么止损？
> - 用同一口径的长期趋势（`RssAnon`、`memory.current`），只涨不落且斜率稳定；拆口径（`anon`/`file`/`shmem`）与私有占用（`Private_Dirty`）。
> - 交叉验证：major fault、PSI、GC、业务延迟是否同步恶化。
> - 止损：先给 cgroup 配 `MemoryHigh`/`MemoryMax` 与告警，防止拖垮整机；滚动重启只是止血，必须保留趋势数据与必要时的内存 dump。
> - **第一反应不要是什么**：不要用一次 `top` 下结论，也不要无限滚动重启。

> [!question]-【进阶】`systemd-oomd` 与内核 OOM 的分工是什么？THP 该不该动？
> - oomd 基于 cgroup v2 + PSI 提前动手，杀目标 cgroup 内**所有**进程；内核 OOM 在分配失败时按打分杀单个进程（或 `oom.group` 整组）。两者可并存，要清楚谁先动手。
> - THP：`always` 有吞吐收益但可能带来内存放大与整理停顿；延迟敏感服务常改为 `madvise`，改之前要有性能基线，改完复测同一组指标。
> - **第一反应不要是什么**：不要把 THP 当「万能性能开关」来回切，也不要以为装了 oomd 就没有内核 OOM。
