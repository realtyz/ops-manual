# 一次内存分配的旅程

一块内存从被申请开始，到落到物理页上，到被当成缓存使用，到被回收或换出，最后到回收不动时由内核杀掉占用它的进程——这条线串起了本章所有机制。下面按这条线一次讲完，最后再把贯穿多个阶段的三个核对对象（内存占用的归属、内存上限的载体与内存压力的表现）收拢在一起。

---

## 一、申请与承诺

### 1.1 申请只改额度，不动物理页

应用程序平时调用的是 `malloc`——它是 **C 库函数**（glibc 提供），自己并不直接跟内核打交道；真正向内核申请地址空间的是它底层的两个**系统调用**：`brk`（扩展堆顶）与 `mmap`（建立一段新映射）。这三个东西返回成功时的含义是一样的：内核把一段虚拟地址划到了这个进程名下、写进它的映射表，**不是**已经把物理内存给它。物理页要等第一次写入、触发缺页时才分配。

所以后面凡看到 `malloc`，指的是**库函数**；看到 `brk`/`mmap`，指的是**系统调用**。**文档的节号就是类别**：`man 2` 是系统调用、`man 3` 是库函数、`man 1` 是普通命令、`man 5` 是文件格式、`man 8` 是管理命令——查不到文档时，先看自己在问哪一类东西。

这条性质有两个直接后果。

- **「申请成功」不能当容量验收。** 要判断一个进程占了多少，必须看物理占用（常驻集），而不是地址空间（`VSZ`）。
- **内存不足可能在任意一次写入上爆发**，而不是在申请的那一刻。启动时申请成功、运行两小时后被杀，是这条性质的典型表现。

### 1.2 申请走的三条路径

| 路径 | 它是什么 | 谁在用它 | 它的特点 |
| --- | --- | --- | --- |
| `brk` | 它是系统调用（`sbrk` 是 glibc 对它的包装，属于库函数） | 分配器用它扩展堆顶 | 它只能连续扩展，因此适合小对象；glibc 用它管理主 arena |
| 匿名 `mmap` | 它是系统调用 | 线程栈、大块 `malloc` 与显式 `mmap` 都用它 | 它建立独立映射，释放时直接归还内核，而且不计入任何文件 |
| 文件 `mmap` | 它是系统调用 | 共享库、文件映射与共享内存都用它 | 它的页来自 Page Cache，因此回收行为与匿名页不同 |

栈是第四条路径：函数调用加深时，内核按需补页；一旦超过 `RLIMIT_STACK`，进程得到的是 `SIGSEGV` 而不是 `ENOMEM`。

glibc 的分配器在堆与匿名映射之间切换，切换阈值（`M_MMAP_THRESHOLD`）默认是 128 KiB，并会随释放的大块在 128 KiB 到 32 MiB 之间动态调整；超过 32 MiB 的请求一律走 `mmap`。这解释了为什么一个进程的 `VSZ` 会随线程数与分配模式一起涨。

### 1.3 映射表与地址空间总量

`/proc/<pid>/maps` 里每一行是一个 **VMA（Virtual Memory Area，虚拟内存区域）**：一段连续的、权限相同的虚拟地址范围。`mmap` 一次多一个 VMA，`munmap` 一次少一个。由此得到三点实务含义。

- VMA 的数量有上限（`vm.max_map_count`，**该值随发行版与初始化配置变化，必须现场用 `sysctl` 取**）。程序疯狂 `mmap` 小块时会以 `ENOMEM` 失败，而这个报错文本与"内存不够"一模一样，原因却与物理内存无关。
- VMA 本身占用内核内存（计入 `/proc/meminfo` 的 `Slab`），因此几万个 VMA 的进程会额外占用内核内存。
- 地址空间总量（`VmSize`）是这些 VMA 的长度总和，因此线程栈预留、按最大堆预留（JVM、数据库）与大文件映射最容易把它撑大。

### 1.4 承诺额度与超额分配

内核允许「承诺总量超过物理内存 + swap」，因为多数程序申请后不会马上用满。这条策略由 `vm.overcommit_memory` 决定。

| 取值 | 它的语义 | 它的代价 |
| --- | --- | --- |
| `0`（默认） | 它是默认值，内核用启发式判断：明显过分的申请被拒，整体仍允许超额 | 「申请成功」不保证「用得出」，因此内存压力最终表现为 OOM |
| `1` | 它总是允许超额 | 承诺完全失去约束，因此 OOM 更突然 |
| `2` | 它不允许超额，因此承诺总量不超过 `CommitLimit` | 合法的大申请会被拒；极端情况下连管理进程也会申请失败 |

`CommitLimit` 由 `swap + overcommit_ratio% × 物理内存` 算出（若设置了 `overcommit_kbytes`，则用它替代乘法项）；`/proc/meminfo` 的 `Committed_AS` 是当前已承诺量。**只有模式 2 会把 `CommitLimit` 当硬约束**，因此在模式 0 与模式 1 下拿它做容量告警会得出错误结论。

模式 2 下还有两个保留量：`admin_reserve_kbytes`（特权用户在限额之外可多用的余量）与 `user_reserve_kbytes`（为普通用户留的空闲内存，避免有人把内存耗尽后连登录都起不来）。这些默认值随内核版本变化，一律现场取。另外 `MAP_NORESERVE` 的效果受模式与内核版本影响，**不能当作绕过承诺的确定性手段**。

`fork` 与超额分配有一处关键交互：`fork` 只复制页表并让父子共享物理页（写时复制），**但承诺额度在 `fork` 的瞬间就增加**。备份、快照、`BGSAVE` 这类「`fork` + 大量写」的场景，真实内存需求由 `fork` 之后写入多少决定。

**第一反应不要做**：不要为了"避免 OOM"把策略改成模式 2——那只是把「OOM 杀掉一个进程」换成「新申请直接失败」，而后者往往更难恢复。改之前要算清 `CommitLimit`、峰值 `Committed_AS` 与余量。

**怎么读这几个数**：`CommitLimit` 与 `Committed_AS` 的单位都是 kB，因此可以直接和 `MemTotal`/`SwapTotal` 放在一起比。`CommitLimit` 是算出来的，可以自己验算一遍。

```bash
# 验证：严格模式的承诺上限 = swap + overcommit_ratio% × 物理内存
awk '/^(MemTotal|SwapTotal|CommitLimit|Committed_AS):/{v[$1]=$2}
     END{printf "MemTotal=%d MB SwapTotal=%d MB 预测上限=%d kB 实际=%d kB 已承诺=%d kB 余量=%d kB\n",
     v["MemTotal:"]/1024, v["SwapTotal:"]/1024,
     v["SwapTotal:"]+v["MemTotal:"]*0.5, v["CommitLimit:"], v["Committed_AS:"],
     v["CommitLimit:"]-v["Committed_AS:"]}' /proc/meminfo
```

把 `0.5` 换成你自己 `sysctl -n vm.overcommit_ratio` 的值即可。读法如下。

| 你看到 | 它的含义 | 下一步 |
| --- | --- | --- |
| 模式为 0 或 1，且 `Committed_AS` 大于物理内存 | 这是设计允许的状态，因此不代表马上要出事 | 不要用它做容量告警 |
| 模式为 2，且余量（上限减已承诺）很小 | 新申请会失败，而这与物理内存还剩多少无关 | 先算清峰值承诺量，再决定调 `overcommit_ratio` 还是改策略 |
| 模式为 2，且 `admin_reserve_kbytes` 被用到 | 这属于连特权操作都在挤占额度的情况 | 优先降低业务侧的承诺量，而不是继续放宽上限 |

**注意别把两类量混着读。** `Committed_AS` 属于承诺额度，`MemAvailable` 属于物理占用。前者贴着上限、后者还有几个 GiB，是完全正常的组合，它说明"额度被用光了，但内存还没被真正占用"。
### 1.5 申请失败时先分类

`malloc` 失败时返回 `NULL`（库函数约定），`mmap` 失败时返回 `-1` 并把 `errno` 置成 `ENOMEM`（系统调用约定）——两者都表示申请失败，但不一定是物理内存没了。按下面的顺序排除，前三类都与内存条上还剩多少无关。

1. 严格承诺撞上限（只在模式 2 下出现，特征是 `Committed_AS` 贴着 `CommitLimit`）；
2. 该进程自己的地址空间限制（`/proc/<pid>/limits` 的 `RLIMIT_AS`/`RLIMIT_DATA`）；
3. 映射段数上限（`vm.max_map_count` 与当前映射数）；
4. 真的没有内存（伴随 OOM 记录、压力指标与换页）。

## 二、落地与计量

### 2.1 缺页把承诺变成占用

第一次访问一个已承诺但未落地的页时，硬件发现页表里没有有效映射，于是触发**缺页异常**，内核接手。

1. **它先判断页在哪里。** 若页已经在内存里（匿名页首次写入、写时复制、文件页已在内核缓存），则这是一次 minor fault；若页不在内存里（文件页被回收、匿名页被换出），则这是一次 major fault，需要等 IO。
2. **它再分配或读取物理页。** 匿名页取一块空闲页并填零，或复制共享页的内容；文件页从缓存或磁盘读取。
3. **它最后更新页表。** 此后访问走正常路径。

两类缺页的代价差一个量级：minor fault 是微秒级，major fault 要高出一到两个数量级，且强烈依赖存储介质。因此**判断压力要看 major fault 是否上升**，而 minor fault 高通常只是分配与映射行为活跃。

还有一处容易误解：**读一个从未写过的匿名页几乎不占内存**。内核把一块内容全零的共享页（zero page）映射进来，只有真正写入时才分配物理页。所以"缺页次数很多"与"内存被占了"是两件事。

文件页的缺页还有**一次映射多页**的行为（缺页放大）：内核会顺带把相邻页的映射建好，因此文件映射的缺页次数往往远小于页数；匿名页则通常一页一次。

**怎么读缺页计数**：两个层面的计数要分清，而且**都要取差值**。

| 看哪里 | 它是什么 | 单位与范围 | 怎么读 |
| --- | --- | --- | --- |
| `/proc/<pid>/stat` 的第 10、12 字段（字段号在 `man 5 proc` 里核对） | 它给出该进程自启动以来的 minor 与 major 缺页数 | 单位是个数，属于累计值 | 两次读数相减得到区间内的缺页次数，再与同期的写入或读取量对照 |
| `/proc/vmstat` 的 `pgfault` / `pgmajfault` | 它们给出整机自启动以来的缺页总数 | 单位是个数，属于累计值 | 同样取差值；`pgmajfault` 的增量除以时间就是 major fault 速率 |

判据是：**`pgmajfault` 的增量持续偏高**（配合压力指标与换页速率）说明工作集不再驻留内存，而 `min_flt` 高只说明分配与映射活跃。注意 major fault 也会被"冷启动读文件"这类正常行为制造出来，所以要看的是**持续性与伴随指标**，不是单次峰值。
### 2.2 三种计量口径

「这个进程占多少内存」没有唯一答案，只有「你问的是哪一个口径」。

| 口径 | 它的含义 | 从哪里读 | 它适合回答 |
| --- | --- | --- | --- |
| 常驻集（`RSS`） | 它统计常驻物理页，并且**把共享页对每个使用者重复计数** | `ps -o rss`、`/proc/<pid>/status` 的 `VmRSS` | 它适合快速定位「谁看起来最大」 |
| 均摊（`PSS`） | 它把共享页按使用者数量均摊 | `/proc/<pid>/smaps_rollup` 的 `Pss` | 它适合回答「这台机器上真正被谁用了」 |
| 私有（`USS`） | 它只算私有页 | 同一文件里 `Private_Clean` 与 `Private_Dirty` 两项之和 | 它适合回答「杀掉它能省多少」，也用于泄漏排查 |

由此得到三条实务规则：容量报表要用均摊或私有口径；判断「杀它能省多少」要用私有口径，因为共享库与共享内存杀了也省不下来；**不要把各进程的常驻集相加**，因为和一定大于物理内存。

按构成可以继续下钻：`/proc/<pid>/status` 的 `RssAnon`/`RssFile`/`RssShmem` 说明涨的是哪一类，`VmSwap` 说明有多少被换出。判断泄漏要靠趋势（同口径、带时间戳、按小时或按天取样），因为单次快照说明不了任何问题。

### 2.3 页表与内核侧开销

页表本身就是内存：一条页表项（PTE）占 8 字节、一页是 4 KiB，所以每落地 4 KiB 约需 0.2% 的额外内存。由此得到三点推论。

- 决定页表大小的是**落地的页数**，不是映射的地址范围；只映射不触碰时几乎不占页表。
- 容器里页表开销计入该 cgroup，因此它会占用这个 cgroup 的内存上限。
- 单进程页表看 `/proc/<pid>/status` 的 `VmPTE`/`VmPMD`，整机看 `/proc/meminfo` 的 `PageTables`。

此外还有几项常被忽略的内核侧占用：`KernelStack`（每个任务的内核栈）、`VmallocUsed`（内核虚拟地址空间）、`Slab`（见第四节）。它们都不在任何进程的常驻集里，但都占用真实的物理内存。

**怎么读页表占用**：整机看 `/proc/meminfo` 的 `PageTables`（单位 kB），单进程看 `/proc/<pid>/status` 的 `VmPTE`/`VmPMD`（单位 kB）。判据是"每落地 4 KiB 约 0.2%"这条算术：一个落地 20 GiB 的进程，页表大致在 40 MiB 量级；如果你看到一个只落地几百 MiB 的进程 `VmPTE` 很大，先怀疑它映射数量异常（去数 `/proc/<pid>/maps` 的行数），而不是先认为"页表天生很大"。**不要用 `VmPTE` 判断大页是否生效**，因为该字段口径随内核统计方式变化，判断大页要看 `AnonHugePages`。
### 2.4 大页与 NUMA：落点决定成本

**透明大页（THP）与显式大页**影响的是"以什么粒度落地"。THP 由内核自动合并（策略取 `always`/`madvise`/`never`），显式大页需要提前预留（`vm.nr_hugepages`、hugetlbfs）。大页减少地址翻译次数，但按 2 MiB 粒度落地意味着**碰到大页里任意一个字节，整块 2 MiB 就占实**，因此稀疏访问的负载会出现明显的内存放大；此外还有内存碎片、后台整理（`khugepaged`）引起的偶发停顿，以及碎片严重时的分配失败。是否启用、用哪种策略，必须做前后对比。

判断大页是否生效，要看 `/proc/<pid>/smaps_rollup` 的 `AnonHugePages`（整机看 `/proc/meminfo` 的同名字段），**不要用 `VmPTE` 判断**，因为该字段的统计口径随内核版本变化。

**NUMA（Non-Uniform Memory Access，非统一内存访问）** 是多路服务器的内存分节点结构：CPU 访问本地节点与远端节点的延迟和带宽差别明显。它带来两类典型现象：「内存总量没满，但某个节点先满」与「资源都空闲却性能不达标」。要点有四条。

- `taskset` 只绑 CPU，不绑内存；绑内存要用 `numactl --membind` 或 `--interleave`。
- 若 `numastat` 里 `numa_miss`/`numa_foreign` 高而本地命中比例低，则说明存在明显跨节点访问。
- 自动 NUMA 平衡（`kernel.numa_balancing`）会在检测到跨节点访问时迁移页，多数场景有收益，但延迟敏感的服务上可能引入抖动。
- 容器里的 NUMA 视图受 `cpuset.mems` 约束，因此「容器看到的拓扑与物理机不同」是正常现象。

## 三、Page Cache 与脏页回写

### 3.1 缓存是资产

内核把空闲内存用来缓存文件内容：读命中就不用访问设备，写操作先落到缓存再异步落盘。所以「空闲内存很少」在 Linux 上通常说明这台机器正在用内存缓存文件内容，而不是内存不够。判断够不够要看可用内存（`MemAvailable`）与压力指标，不看完全空闲的那一列。

`/proc/meminfo` 里要分清三组字段。

- `Cached` 包含 `Shmem`，因为 tmpfs 与共享内存的页也算缓存。所以「`Cached` 涨了」可能是读了文件，也可能是有人往 tmpfs 写了东西，而这两者的含义完全不同。
- `Dirty` 与 `Writeback` 分别是还没落盘、正在落盘的页。
- `SReclaimable` 是压力下可回收的 slab，`SUnreclaim` 是回收不掉的，因此只有后者才是长期占用。

回写参数有三个族：阈值（`dirty_ratio`/`dirty_background_ratio`，或等价的字节数版本 `dirty_bytes`/`dirty_background_bytes`，**两族互斥**，现场取）、时间（`dirty_expire_centisecs`、`dirty_writeback_centisecs`）与设备侧（队列深度、调度器）。改之前先有基线。

**怎么读缓存与脏页**：这几个字段都在 `/proc/meminfo`，单位都是 kB。

| 字段 | 它是什么 | 怎么读 |
| --- | --- | --- |
| `Cached` | 它是页缓存总量，并且**包含 `Shmem`** | 它的涨落是正常现象；要区分文件缓存与 tmpfs，就看 `Shmem` |
| `Shmem` | 它统计 tmpfs 与共享内存占用的页 | 这部分不随压力被丢弃，因此它涨上去要查写入方 |
| `Dirty` / `Writeback` | 它们分别是已改未落盘与正在落盘的页 | 把它们与下面的阈值对照 |
| `SReclaimable` / `SUnreclaim` | 它们分别是可回收与不可回收的内核对象 | 只有 `SUnreclaim` 才是长期占用 |

脏页的两个阈值可以直接算出来（它们通常是比例，乘以物理内存就是字节数）。

```bash
# 验证：脏页阈值（后台回写起点与硬上限），单位 MiB
awk '/^MemTotal:/{t=$2}
     END{printf "background=%d MiB  ratio=%d MiB\n", t*0.10/1024, t*0.20/1024}' /proc/meminfo
```

把 `0.10`/`0.20` 换成 `sysctl -n vm.dirty_background_ratio` 与 `vm.dirty_ratio` 的值；如果配置用的是 `dirty_background_bytes`/`dirty_bytes`，它们本身就是字节数。判据是：**一旦 `Dirty` 接近硬阈值，写进程就会被限速**；而 `Writeback` 长期非 0 说明一直有页在往设备写。注意阈值大小只决定"何时开始回写"，不决定设备能否跟上，因为设备侧的问题要去看 `await` 与队列长度。
### 3.2 写变慢的根因通常是回写跟不上

脏页超过后台阈值后，内核启动后台回写；超过硬阈值后，**发起写的进程会被限速甚至阻塞**（`balance_dirty_pages`）。现象是 `wa` 高、设备 `await` 高、进程进入 `D` 状态，而**内存并不缺**。

判断这类问题要分清两件事：脏页产生的速率，与设备排空的速率。**如果设备本身够快，把脏页上限调小并不会让写变快**，因为它只改变后台回写什么时候开始；只有当排空跟不上产生时，才会出现写进程被按住。这一点常被误解成"调低 `dirty_ratio` 能治写入卡顿"。

`drop_caches`（`/proc/sys/vm/drop_caches`）只该用于"需要一把干净读数"的测量场景：它丢掉干净缓存与可回收 slab，此后业务必须为重建缓存付出 IO。**生产上不要执行。**

### 3.3 缓存与容量

缓存增长到把空闲内存全部用掉是设计行为，不需要"清理"。真正需要治理的是两类：**脏页长期积压**（写路径有问题）与**缓存无法回收**（例如 tmpfs 占用了大量 `Shmem`，而它不随压力被丢掉）。后者是"内存去哪了"的第一类答案，见第五节。

## 四、回收与压力

### 4.1 水位与两种回收

空闲页低于三条警戒线时，回收启动。三条线（`min`/`low`/`high`）的绝对值由 `vm.min_free_kbytes` 与 `vm.watermark_scale_factor` 决定，可以在 `/proc/zoneinfo` 里按内存区（zone）看到。

回收有两条路径。

- **后台回收由 `kswapd` 执行。** 它在内核线程里慢慢回收，因此正常负载下感觉不到。
- **直接回收（direct reclaim）由分配者自己执行。** 空闲页跌破 `min` 时，发起分配的进程被迫去回收，这一步在它的上下文里同步发生，表现为延迟抖动；`/proc/vmstat` 的 `allocstall` 计数增加，就是这件事在发生。

**怎么读水位**：三条线在 `/proc/zoneinfo` 里按内存区（zone）列出，**单位是页数而不是 kB**，因此要乘页大小换算；`vm.min_free_kbytes` 是内核参数（用 `sysctl` 看），它决定 `min` 线，而 `vm.watermark_scale_factor` 决定 `low`/`high` 相对 `min` 的间距。

```bash
# 验证：把某个 zone 的水位与当前空闲页对照着读（输出单位 MiB）
awk '/^Node/{node=$2} /^  /{zone=$1} /pages free/{free=$3} /^        min/{min=$2} /^        low/{low=$2} /^        high/{high=$2}
     END{printf "free=%d MiB min=%d MiB low=%d MiB high=%d MiB\n", free*4/1024, min*4/1024, low*4/1024, high*4/1024}' /proc/zoneinfo | tail -3
```

（`*4` 是按 4 KiB 页换算；页大小要用 `getconf PAGE_SIZE` 确认。）判据是：若 `pages free` 高于 `high`，则系统处于正常状态；一旦跌破 `low`，后台回收就开始活跃；若跌破 `min`，则分配者被迫自己回收（`allocstall` 增长、延迟抖动）。读的时候注意一台机器可能有多个 zone，要分别看，别看错行。
### 4.2 回收谁：LRU 与页的类型

内核按「最近有没有被访问」把页排在 LRU（Least Recently Used，最近最少使用）链表上，回收时从冷端挑。

- **文件页有文件对应，可以直接丢掉、下次用到再读回来**，因此它的回收成本低，是首选。
- **匿名页（堆、栈、`malloc` 的页）没有文件对应，只能写入 swap**（或 zram 之类的压缩后端），因此它的回收成本高。
- **不可回收的页**包括内核锁定的页、`SUnreclaim` 的 slab 与 tmpfs 的共享内存等，回收动不了它们。

`vm.swappiness` 调节的是「回收时对匿名页的**倾向权重**」，取值 0~200（内核 ≥5.8），**它不是开关**：即使设为 0，压力大时也可能换页；要彻底不用 swap，只能 `swapoff` 或把 cgroup 的 `memory.swap.max` 设为 0。关掉 swap 并不会消除风险，只是把「换页变慢」换成「被 OOM 杀掉」。

**swap 的形态与边界**：swap 可以是**分区**，也可以是**文件**。文件形式的创建链路是先用 `fallocate` 划出空间，再用 `mkswap` 写入签名，最后用 `swapon` 启用。有三点边界必须记住。

- **带空洞的文件不能被 `swapon` 接受**，因为稀疏文件会让内核无法确定块的实际位置。
- **在 Btrfs 上用 `fallocate` 出来的文件也不能直接用作 swap**，因为写时复制与压缩会改变块布局，需要按该文件系统的官方说明处理。
- 内核还有两种"压缩换空间"的变体：**zram** 把换出的页压缩后放在内存里，相当于用 CPU 换内存；**zswap** 在写往真实 swap 之前先压缩缓存一层。它们不减少"内存压力"这个事实，只是改变代价的分布——用 CPU 换 IO。

**什么时候必须开、什么时候考虑关**：需要"扛过峰值而不被杀"的节点通常要开 swap，因为换来的是变慢而不是中断；延迟极敏感、且已经确认工作集远小于物理内存的服务，才考虑对它禁用换页（`swapoff`，或把该 cgroup 的 `memory.swap.max` 设为 0）。**判断依据是压力指标与换页速率，不是"有没有 swap"这件事本身。**
### 4.3 压力指标

`/proc/pressure/*`（PSI，Pressure Stall Information）用「被拖慢的时间占比」衡量资源压力，内存侧看 `/proc/pressure/memory` 的 `some`/`full` 与 `avg10`/`avg60`/`avg300`。它是"压力已经影响到任务"的直接证据，因此比"空闲内存还剩多少"更接近体感。

配套要看三项：`vmstat` 的 `si`/`so`（换入换出速率，长期非 0 说明压力已落到磁盘路径）、`pgmajfault`（工作集不再驻留内存的证据）、`workingset_refault`（刚回收的页马上又被用到，说明回收判断错了）。

**采样纪律**：单点读数说明不了问题，必须同一口径、带时间戳、至少两次采样；判断抖动按秒，判断泄漏按小时或按天；原始输出要留档，而不是只抄一个数字。

---

**怎么把压力指标和换页指标合起来读**（字段的通用读法在实操篇 2.2、2.1）：

| 组合 | 它说明什么 | 方向 |
| --- | --- | --- |
| PSI 三个尺度都接近 0，且 `si`/`so` 为 0 | 这属于没有内存压力的状态 | 换一个时间窗口，或者去看历史数据 |
| PSI `some` 抬头，且 `si`/`so` 偶发非 0 | 这属于有压力但还没形成持续换页的状态 | 盯趋势，先不动手 |
| PSI 三个尺度同时抬头、`si` 与 `so` 同时持续非 0，且 `pgmajfault` 增长 | 这是典型的内存紧张状态，说明工作集已不再驻留内存 | 定位工作集与占用大户，评估扩容或限流 |
| PSI 高、`wa` 高，但 `si`/`so` 为 0 | 这属于压力来自 IO 而非内存的情况 | 转到设备与写模式方向 |
| `allocstall` 增长，且 `workingset_refault` 增长 | 这属于分配者被迫回收、刚回收的页马上又被用到的情况 | 说明回收判断与实际工作集不匹配，考虑扩容或调整回收倾向 |
## 五、OOM 的判定

### 5.1 回收不动的两种结局

回收与回写制造的是**变慢**（可观测、可调优），而 OOM 制造的是**中断**（只能定性、只能复盘）。参数调优要决定的，正是压力大到什么程度时从"变慢"转为"中断"。

OOM 分两个层级，判据完全不同。

- **整机 OOM** 发生在物理内存与 swap 都用不出来时，内核从全局挑一个进程杀掉。
- **cgroup OOM** 发生在某个 cgroup 撞到自己的上限（`memory.max`）时，**此时整机内存可能还很充裕**。容器化环境里绝大多数 OOM 属于这一类。

### 5.2 谁被杀

内核按 `oom_badness` 打分挑进程：它主要看该进程占用的内存量，再叠加 `oom_score_adj`（取值 -1000~1000，越小越不容易被杀）。由此得到两个实务要点。

- 单个进程的分数可以从 `/proc/<pid>/oom_score` 看到，调整要用 `oom_score_adj`。
- 保护关键进程（SSH、systemd）要靠"给它们更低的 `oom_score_adj`"或"给业务加限制"，**而不是只调别人的分数**。

### 5.3 定性与取证

**退出码 137 只说明进程死于 `SIGKILL`**（人工 `kill -9` 同样是 137），它不是 OOM 的证明。真正的定性证据有三处。

1. **第一处是内核日志**（`dmesg`/`journalctl -k`）：整机 OOM 会打印 `invoked oom-killer` 与 `Out of memory: Killed process ...`，而 cgroup OOM 会额外带 `oom-kill:constraint=CONSTRAINT_MEMCG`、`oom_memcg=<路径>` 与 `Memory cgroup out of memory`。
2. **第二处是该 cgroup 的计数文件**：`memory.events` 的 `oom`/`oom_kill` 计数非 0，以及 `memory.peak` 是否贴着 `memory.max`。
3. **第三处是人工操作记录**：谁在什么时候杀过进程——这一步常被跳过，却排除误判的关键。

还有两处边界容易忽略。

- **这些计数文件是有时效的：** cgroup 目录会随单元结束被回收，`memory.events` 随之消失，因此要复盘就得在它还活着的时候采集；systemd 服务默认 `OOMPolicy=stop`，一次 cgroup OOM 会把整个单元停掉，需要保留现场时应改为 `continue`（该指令要求 systemd ≥243）。
- **`memory.high` 与 `memory.max` 是两种命运：** 前者只节流（回收与限速），后者才杀进程。

**怎么读 OOM 的证据**：内核日志与该 cgroup 的计数文件都要看，而且各自的字段含义不同。

内核日志（`dmesg -T` / `journalctl -k`）里的一行典型记录如下，逐段读。

```text
Memory cgroup out of memory: Killed process 5619 (python3) total-vm:79664kB, anon-rss:65280kB,
file-rss:6784kB, shmem-rss:0kB, UID:0 pgtables:188kB oom_score_adj:0
```

| 片段 | 它的含义 |
| --- | --- |
| `Memory cgroup out of memory` | 它说明这是 **cgroup 级** OOM，而整机级会写 `Out of memory` |
| `Killed process 5619 (python3)` | 它给出被选中的进程与它的名字 |
| `total-vm` / `anon-rss` / `file-rss` / `shmem-rss` | 它们给出该进程当时的地址空间与三类常驻内存（单位 kB），其中 **`anon-rss` 大说明这是应用自己的内存** |
| `pgtables` | 它给出该进程的页表占用（单位 kB） |
| `oom_score_adj` | 它给出当时的权重设置，因此非默认值说明有人手动调过 |

同一事件在别处的前后文还能给出三项信息：`oom-kill:constraint=CONSTRAINT_MEMCG`（撞的是 cgroup 还是整机）、`oom_memcg=/system.slice/xxx.service`（**撞上限的 cgroup 路径**，复盘时按它去找计数文件）、`task_memcg=`（发起分配的任务属于哪个 cgroup）。

该 cgroup 的计数文件（路径来自上面的 `oom_memcg=`，字段读法见实操篇 2.5）里，`memory.max` 是上限、`memory.peak` 是历史峰值、`memory.events` 里的 `oom` 是触发判定的次数、`oom_kill` 是真正杀掉的次数、`max` 是撞上限被回收或节流的次数；**三个计数都是累积值，因此要用差值判断"这次"**。

进程权重方面，`/proc/<pid>/oom_score` 是当前分数（只读），`/proc/<pid>/oom_score_adj` 是可写的调整量，范围 -1000~1000，**越小越不容易被杀**。判据是：给关键进程（SSH、systemd、监控代理）留更低的权重或更明确的保护，而不是把别人的权重调高，因为后者会改变别人的被杀概率，影响面不可控。
### 5.4 复盘要回答的三个问题

1. **谁被杀**：进程名、cgroup 与当时的用量。
2. **为什么是它**：`oom_score_adj` 是多少，它是 cgroup 里最大的那个，还是在整机层面被选中。
3. **撞的是谁的上限**：是整机水位，还是某个 cgroup 的 `memory.max`——这决定修的是容量、是配置，还是应用行为。

## 六、三个跨阶段的核对对象

前面按时间顺序讲的是一块内存的五个阶段；下面三个核对对象各自贯穿其中多个阶段，排障时按它们切分更快。

### 6.1 第一个核对对象：内存占用的归属

`free` 与 `/proc/meminfo` 的缺口，最终要能拆到四处。

1. **进程的常驻集**，按均摊或私有口径核对；
2. **tmpfs 与共享内存**（`Shmem`），它们占的是内存而不是磁盘，因此 `df` 与 `du` 都容易漏；
3. **内核缓存与内核对象**（`Slab`/`SReclaimable`/`SUnreclaim`、`PageTables`、`KernelStack`）；
4. **被 cgroup 计入的页缓存**，因此在容器场景里，宿主的 `free` 不能当容器的判据。

**第一反应不要做**：不要在账对不上时先加内存。

### 6.2 第二个核对对象：内存上限的载体

一个进程的内存上限可以写在四层，但四层的**载体不同**，因此查文档和改配置的地方也不同：进程自身是**资源限制**（`RLIMIT_AS`/`RLIMIT_DATA`，由 `setrlimit(2)` 或 shell 的 `ulimit` 设置）、服务 unit 是 **systemd 属性**（写进 unit 文件的 `MemoryHigh=`/`MemoryMax=`）、cgroup 是**内核接口文件**（`memory.high`/`memory.max`，直接读写）、整机是**内核参数**（`vm.min_free_kbytes` 一类，用 `sysctl` 查看和设置）。四层各自独立生效，因此**"服务被限制杀死"与"整机内存不足"是两回事**。给服务配上限的意义在于把故障限制在一个服务内，而不是让它拖垮整机。

### 6.3 第三个核对对象：内存压力的表现

从轻到重的顺序是：水位下降、后台回收、直接回收（`allocstall` 上升）、换页与回写（`si`/`so`、`wa`、`D` 状态）、压力指标上升（PSI）、major fault 增加，最后才到 OOM。**能看见变慢，就有机会在中断之前动手。**

## 七、常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 用 `VSZ` 判断进程占用 | `VSZ` 属于地址空间这一类量，因此判断占用要看常驻、均摊或私有口径 |
| 「申请成功了，内存一定够」 | 申请只记录额度，物理页要到第一次写入时才给 |
| 拿 `Committed_AS` 与物理内存比大小做告警 | 在模式 0 与模式 1 下，承诺超过物理内存是设计允许的 |
| 看到 `mmap` 报 `ENOMEM` 就加内存 | 先排除承诺上限、`RLIMIT_*` 与 `vm.max_map_count` 三类成因 |
| 「`free` 小就等于内存不够」 | 缓存是资产，因此判据是可用内存与压力指标 |
| 在生产上执行 `drop_caches` | 丢掉的是性能资产，业务随后要为重建缓存付 IO |
| 认为调低 `dirty_ratio` 能治写入卡顿 | 上限只管"何时开始回写"，而卡顿取决于排空速率是否跟不上产生速率 |
| 把 `swappiness` 当开关 | 它是权重，因此要禁用只能 `swapoff` 或把 `memory.swap.max` 设为 0 |
| 看到 `si`/`so` 非 0 就立刻 `swapoff` | 先分清是偶发换出还是持续抖动；关掉 swap 只是把问题换成 OOM |
| 用退出码 137 认定 OOM | 137 只说明死于 `SIGKILL`，因此定性要看内核日志与 `memory.events` |
| 在容器里用宿主的 `free` 判断容器内存 | 容器的额度记在 cgroup 里，因此宿主空闲不代表容器没撞上限 |
| 把各进程常驻集相加与物理内存对账 | 共享页被重复计数，因此和一定大于物理内存 |
| 用 `VmPTE` 判断大页是否生效 | 该字段口径随内核版本变化，因此要看 `AnonHugePages` |
| 认为容器里 NUMA 视图应与物理机一致 | 容器受 `cpuset.mems` 约束，因此它的拓扑可能与物理机不同 |

**第一反应不要做什么**（三条最有用的）：不要用"还有空闲内存"否定 OOM；不要在没有基线时改参数；不要用一次采样下结论。

## 要点自测

**问：为什么"申请"与"落地"是两个时刻？这带来什么运维后果？**
答：申请只改地址空间与承诺额度，物理页要到第一次写入时才分配。后果是"申请成功"不能当容量验收，内存不足可能在任意一次写入上爆发。

**问：整机还有内存，服务却被杀了，最可能撞的是哪一层？**
答：最可能是 cgroup 层的硬上限（`memory.max`，systemd 的 `MemoryMax=`）。判据是内核日志里的 `constraint=CONSTRAINT_MEMCG` 与 `oom_memcg=`，以及该 cgroup `memory.events` 的 `oom_kill`。

**问：写入变慢时，怎么区分是回写问题还是内存不足？**
答：看可用内存与压力指标是否正常、脏页与回写中的页是否很高、进程是否处于 `D` 状态、设备 `await` 是否升高。若内存充足而 `await` 高，方向就是回写与设备，不是加内存。

**问：为什么容器 OOM 时宿主可能还有大量空闲内存？**
答：因为容器的用量与上限记在它自己的 cgroup 文件里，它撞的是 `memory.max`，所以宿主余量与容器额度是两件事。

**问：进程占用与整机用量对不上时，先查哪四处最容易被漏掉的占用？**
答：先查 tmpfs 与共享内存（`Shmem`）、内核对象（不可回收的 `Slab`、`PageTables`、`KernelStack`）、被 cgroup 计入的页缓存，以及共享页被重复计数导致的相加偏大。

**问：OOM 复盘至少要回答哪三个问题？**
答：谁被杀（进程、cgroup 与当时用量）；为什么是它（权重与选择依据）；撞的是谁的上限（cgroup 还是整机）——这三者对应完全不同的修法。

**第一反应不要做什么**：不要用"还有空闲内存"否定 OOM；不要在账对不上时先加内存；不要在没有基线时改参数。
