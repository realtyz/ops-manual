# 内存管理与 OOM

## 知识地图

### 一次内存分配的旅程

时间主线跟着**一块内存**走：从被申请，到落到物理页上，到被当成缓存用，到被回收或换出，最后到回收不动时的 OOM。

```mermaid
flowchart LR
  A["① 申请与承诺<br/>只记账，不动物理页"] --> B["② 落地与计量<br/>缺页 → 物理页 + 页表"]
  B --> C["③ 缓存与回写<br/>Page Cache / 脏页"]
  C --> D["④ 回收与压力<br/>水位 · kswapd · swap"]
  D --> E["⑤ 不够用<br/>OOM：整机或 cgroup"]
```

| # | 站点 | 内核在做什么 | 到这里要能说清 |
| --- | --- | --- | --- |
| 1 | 申请与承诺 | 进程 `malloc`/`mmap`，内核只记账 | 申请为什么不等于占用；承诺额度与物理内存是两本账 |
| 2 | 落地与计量 | 第一次写入触发缺页，分配物理页并建立映射 | 常驻/均摊/私有三种口径各回答什么；页表与大页的落点 |
| 3 | 缓存与回写 | 文件页进 Page Cache，写操作先进缓存再异步落盘 | 缓存为什么是资产；写变慢为什么常常是回写跟不上 |
| 4 | 回收与压力 | 空闲页低于水位，后台或直接回收；匿名页只能换到 swap | 三条水位线、两类回收、压力指标怎么读 |
| 5 | 不够用：OOM | 撞到整机水位或 cgroup 上限，内核挑进程杀掉 | 谁被杀、为什么、撞的是谁的上限 |

### 三条横切线

| 横切线 | 贯穿内容 | 收口于 |
| --- | --- | --- |
| 账目线 | `free` 口径 → 进程占用口径 → tmpfs 与内核对象 → 被 cgroup 计入的页缓存 | 「内存去哪了」怎么对账 |
| 限制线 | 进程地址空间限制 → unit 的内存上限 → cgroup `memory.max`/`memory.high` → 整机水位 | 为什么整机还有内存却被杀 |
| 压力线 | 水位 → 后台回收 → 直接回收 → 换页与回写 → 压力指标 → OOM | 怎么在「被杀」之前先看见「变慢」 |

## 术语速查

| 名词 | 一句话解释 | 在哪一篇展开 |
| --- | --- | --- |
| 页 / 页框 | 内核管理内存的最小单位（x86_64 常见 4 KiB）/ 承载它的物理内存块 | 原理：为什么要虚拟内存 |
| 虚拟地址空间 | 每个进程独立看到的一套地址，由页表映射到物理页框 | 原理：为什么要虚拟内存 |
| 页表 / 页表项 | 虚拟页到物理页框的映射表 / 表里的一行（x86_64 上 8 字节） | 原理：地址空间与地址翻译 |
| TLB | 缓存最近翻译结果的硬件，容量以表项计 | 原理：地址空间与地址翻译 |
| 缺页异常 | 访问的虚拟页还没有有效映射，内核现补 | 原理：缺页与写时复制 |
| minor / major fault | 页已在内存里只缺映射 / 需要从磁盘或 swap 读入 | 原理：缺页与写时复制 · 体系 |
| 零页 | 内容全零的共享页；读从未写过的匿名页时映射它，几乎不占内存 | 原理：缺页与写时复制 |
| 写时复制（COW） | `fork` 后父子共享物理页，谁写谁复制 | 原理：缺页与写时复制 |
| 常驻 / 均摊 / 私有口径 | 常驻页按使用者重复计数 / 共享页均摊 / 只算私有页 | 体系 |
| 大页 / 透明大页 | 需要预留的大页 / 内核自动合并使用的大页 | 原理：大页与 NUMA |
| NUMA | 多路服务器上内存按 CPU 分节点，跨节点访问更慢 | 原理：大页与 NUMA |
| Page Cache / 脏页 | 用空闲内存缓存文件内容 / 改过但还没落盘的页 | 体系 |
| 水位（watermark） | 空闲页的三条警戒线 `min`/`low`/`high` | 体系 |
| kswapd / 直接回收 | 后台回收线程 / 分配者自己被迫回收 | 体系 |
| 匿名页 / 文件页 | 没有文件对应的页 / 有文件对应、可先丢再读的页 | 体系 |
| swap / thrashing | 匿名页的落盘去处 / 页反复换入换出造成的抖动 | 体系 |
| swappiness | 回收时对匿名页的倾向权重，不是开关 | 体系 |
| PSI | `/proc/pressure/*`，用被拖慢的时间占比衡量压力 | 体系 |
| 超额承诺 | 允许承诺总量超过物理内存 + swap 的策略 | 体系 |
| OOM Killer | 内存用不出来时由内核挑进程杀掉的机制 | 体系 |
| oom_score_adj | 单个进程的 OOM 权重，范围 -1000~1000 | 体系 |
| memory.max / memory.high | cgroup v2 的硬上限（会杀）/ 软上限（只节流） | 治理 |
| memory.events | cgroup 事件计数，`oom_kill` 非 0 就是真的杀过 | 体系 · 治理 |
| systemd-oomd | 用户态 OOM 守护进程，基于 cgroup v2 与压力指标提前动手 | 治理 |
| tmpfs / 共享内存 | 挂在内存里的文件系统；它的页算内存不算磁盘 | 体系 |
| slab / dentry・inode 缓存 | 内核对象缓存与目录项缓存，可回收的那部分随压力释放 | 体系 |

## 故障现场定位表

排障的第一问不是「怎么修」，而是「**这块内存现在算在谁账上、内核正为它做什么**」。用这张表把现象定位到类别，再进对应篇目。

| 你看到的现象 | 属于哪一类 | 现场在哪 | 第一反应不要做 |
| --- | --- | --- | --- |
| `free` 只剩几百 MiB，业务却正常 | 缓存在干活 | 可用内存、压力指标、换页速率 | 不要因此加内存，更不要 `drop_caches` |
| 缓存大，想「清一下」 | 缓存是资产 | `Cached` 与可回收 slab、回收代价 | 不要在生产上执行 `drop_caches` |
| 进程申请内存成功但很快被杀 | 承诺与落地分离 | 地址空间与承诺账本、超额分配策略 | 不要只看 `VSZ` 就判断它占了很多 |
| 「内存去哪了」，进程占用加起来对不上 | 账目有漏项 | tmpfs、内核对象、cgroup 页缓存 | 不要先加内存 |
| `free` 有余量却发生了 OOM | 撞的是局部上限 | 内核日志里的 cgroup OOM 记录、`memory.events` | 不要说「日志写错了」 |
| 容器被 OOMKilled，宿主却很空 | cgroup 记账 | `memory.current`/`max`/`stat`、`/dev/shm` | 不要拿宿主 `free` 当判据 |
| 退出码 137，就直接写「OOM」 | 定性证据不足 | 内核日志与 `memory.events`、人工操作记录 | 不要把 137 当 OOM 的证明 |
| `si`/`so` 长期非 0，延迟抖动 | 换页压力 | `vmstat`、压力指标、进程被换出的页 | 不要直接 `swapoff` 或把 `swappiness` 归零 |
| 写入变慢、进程进 `D` 状态 | 回写跟不上 | 脏页与回写中的页、设备 `await`、进程级 IO | 不要把它当内存不足加内存 |
| 内存缓慢增长，被判定为泄漏 | 趋势问题 | 匿名/文件/共享三类构成的曲线 | 不要用单次 `top` 下结论 |
| 服务把整机拖到 OOM | 缺限制 | 服务的 `MemoryMax=` 与内核日志 | 不要只调 `oom_score_adj` 保护别人 |
| 内存总量比标称少一截 | 预留与保留 | 固件、显卡、大页预留、`crashkernel=` | 不要怀疑内存条坏了 |
