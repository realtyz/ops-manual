# 内存管理与 OOM

## 知识地图

### 一次内存分配的旅程：五个阶段

时间主线跟着**一块内存**走：它先被申请，然后落到物理页上，接着被当成缓存使用，再被回收或换出，最后在回收不动时由内核杀掉占用它的进程。

```mermaid
flowchart LR
  A["① 申请与承诺<br/>只记录额度，不分配物理页"] --> B["② 落地与计量<br/>缺页后才分配物理页并填页表"]
  B --> C["③ 缓存与回写<br/>文件内容进 Page Cache，写操作先成脏页"]
  C --> D["④ 回收与压力<br/>空闲页低于水位后回收或换出"]
  D --> E["⑤ 不够用<br/>OOM：cgroup 上限或整机水位"]
```

| 阶段 | 内核在做什么 | 到这里要能说清 |
| --- | --- | --- |
| 1 申请与承诺 | 进程调用 `malloc` 或 `mmap` 时，内核只在它的地址空间与承诺额度上记一笔，并不分配物理页 | 申请为什么不等于占用；地址空间、承诺额度与物理占用为什么是三类不同的量 |
| 2 落地与计量 | 进程第一次写入时才触发缺页，内核在这一次中断里分配物理页并把映射填进页表 | 常驻、均摊与私有三种口径分别回答什么问题；页表与大页的开销落在哪里 |
| 3 缓存与回写 | 内核把文件内容读进 Page Cache 以省下设备访问，写操作先落到缓存，再由内核异步写回设备 | 缓存为什么是资产；写变慢为什么常常是回写跟不上，而不是内存不够 |
| 4 回收与压力 | 空闲页低于水位线后，内核先做后台回收；一旦跌破 `min` 线，发起分配的进程就要自己回收，匿名页只能写入 swap | `min`、`low`、`high` 三条水位线、后台回收与直接回收的区别，以及压力指标怎么读 |
| 5 不够用：OOM | 整机水位或 cgroup 上限再也回收不出内存时，内核按 `oom_score` 挑一个进程杀掉 | 到这里要能说清谁被杀、为什么是它，以及它撞的是哪一层的上限 |

### 三个跨阶段的核对对象

有三类量各自贯穿多个阶段，排障时按它们切分比从头走一遍时间线更快。每条都要点名它贯穿哪几个阶段、每一处读什么字段。

| 核对对象 | 它贯穿哪几个阶段 | 每一处读什么字段 |
| --- | --- | --- |
| 内存占用的归属 | 它贯穿全部五个阶段，因为申请、落地、缓存、回收与 OOM 都会改变某一类占用的数值 | 在阶段 1 读 `/proc/<pid>/status` 的 `VmSize` 与 `/proc/meminfo` 的 `Committed_AS`；在阶段 2 读 `VmRSS` 与 `/proc/<pid>/smaps_rollup` 的 `Pss`；在阶段 3 与阶段 4 读 `/proc/meminfo` 的 `Cached`、`Shmem`、`SReclaimable`、`SUnreclaim` 与 `PageTables`；在阶段 5 读 cgroup 目录下的 `memory.current` 与 `memory.stat` |
| 内存上限的载体 | 它贯穿阶段 1 与阶段 5，因为额度在申请时记上，而撞上限发生在回收不动之后 | 在阶段 1 读 `/proc/<pid>/limits` 的 `RLIMIT_AS`/`RLIMIT_DATA` 与 `sysctl vm.overcommit_memory`；在阶段 5 读 unit 的 `MemoryHigh=`/`MemoryMax=` 与 cgroup 的 `memory.high`/`memory.max`，再用 `/proc/zoneinfo` 的水位核对整机这一层 |
| 内存压力的表现 | 它贯穿阶段 3 到阶段 5，因为压力先表现为回写变慢，再表现为回收与换页，最后才走到 OOM | 在阶段 3 读 `/proc/meminfo` 的 `Dirty`/`Writeback` 与设备 `await`；在阶段 4 读 `/proc/zoneinfo` 的 `pages free` 与三条水位、`/proc/vmstat` 的 `allocstall`、`/proc/pressure/memory`；在阶段 5 读 `memory.events` 的 `oom`/`oom_kill` |

## 术语速查

| 名词 | 一句话解释 | 它在哪一篇展开 |
| --- | --- | --- |
| 页 / 页框 | 页是内核管理内存的最小单位（x86_64 上常见 4 KiB），页框是承载它的物理内存块 | 原理《为什么要虚拟内存》 |
| 虚拟地址空间 | 它是每个进程独立看到的一套地址，由页表映射到物理页框 | 原理《为什么要虚拟内存》 |
| 页表 / 页表项 | 页表记录虚拟页到物理页框的映射，页表项是这张表里的一行（x86_64 上占 8 字节） | 原理《地址空间与地址翻译》 |
| TLB | 它是 MMU 内部缓存最近翻译结果的硬件，容量以表项数计 | 原理《地址空间与地址翻译》 |
| 缺页异常 | 进程访问的虚拟页还没有有效映射时，内核在这一次中断里把页补上 | 原理《缺页与写时复制》 |
| minor / major fault | minor fault 指页已在内存里、只缺映射；major fault 指页不在内存里，必须从磁盘或 swap 读入 | 原理《缺页与写时复制》与体系篇 |
| 零页 | 它是内容全零的共享页，内核在读从未写过的匿名页时映射它，因此这次读几乎不占内存 | 原理《缺页与写时复制》 |
| 写时复制（COW） | `fork` 之后父子进程共享同一批物理页，谁先写谁触发缺页并复制那一页 | 原理《缺页与写时复制》 |
| 常驻 / 均摊 / 私有口径 | 常驻口径把共享页在每个使用者处各算一份，均摊口径把共享页按使用者数量分摊，私有口径只算私有页 | 体系篇 |
| 大页 / 透明大页 | 显式大页需要提前预留，透明大页由内核自动把小页合并而成 | 原理《大页与 NUMA》 |
| NUMA | 多路服务器把内存按 CPU 分成若干节点，跨节点访问的延迟与带宽都差于本地访问 | 原理《大页与 NUMA》 |
| Page Cache / 脏页 | 内核用空闲内存缓存文件内容；脏页是已经改过但还没有落盘的页 | 体系篇 |
| 水位（watermark） | 它是空闲页的三条警戒线，字段名是 `min`、`low` 与 `high` | 体系篇 |
| kswapd / 直接回收 | 后台回收由内核线程 `kswapd` 执行，直接回收由发起分配的进程自己执行 | 体系篇 |
| 匿名页 / 文件页 | 匿名页没有对应文件、只能换到 swap，文件页有对应文件、可以先丢掉再读回来 | 体系篇 |
| swap / thrashing | swap 是匿名页换出后的去处；thrashing 指页反复换入换出造成的抖动 | 体系篇 |
| swappiness | 它是回收时对匿名页的倾向权重，不是开关 | 体系篇 |
| PSI | 它是 `/proc/pressure/*` 下的指标，用任务被拖慢的时间占比衡量资源压力 | 体系篇 |
| 超额承诺 | 它指内核允许承诺总量超过物理内存与 swap 之和 | 体系篇 |
| OOM Killer | 内存再也回收不出来时，内核按 `oom_score` 挑选并杀掉进程 | 体系篇 |
| oom_score_adj | 它是单个进程的 OOM 权重，取值范围是 -1000~1000 | 体系篇 |
| memory.max / memory.high | 它们是 cgroup v2 的硬上限与软上限，前者撞上会杀进程，后者只节流 | 治理篇 |
| memory.events | 它是 cgroup 的事件计数，其中 `oom_kill` 非 0 就说明这个 cgroup 里真的杀过进程 | 体系篇与治理篇 |
| systemd-oomd | 它是用户态的 OOM 守护进程，依据 cgroup v2 与压力指标在 OOM 之前提前动手 | 治理篇 |
| tmpfs / 共享内存 | tmpfs 是挂在内存里的文件系统，它的页占用物理内存而不占用磁盘 | 体系篇 |
| slab / dentry・inode 缓存 | 它们分别是内核对象缓存与目录项缓存，其中可回收的那部分会随内存压力释放 | 体系篇 |

## 故障现场定位表

排障的第一问不是「怎么修」，而是「**这块内存现在属于哪一类占用、内核正为它做什么**」。下表先把现象归到一类，再进对应的篇目。

| 你看到的现象 | 它属于哪一类 | 现场在哪 | 第一反应不要做 |
| --- | --- | --- | --- |
| `free` 只剩几百 MiB，业务却正常 | 这属于页缓存正在被正常使用的情况 | 先读 `MemAvailable`、`/proc/pressure/memory` 与换页速率 | 不要因此加内存，也不要在生产机上写 `drop_caches` |
| 缓存很大，想「清一下」 | 这属于缓存作为性能资产的情况 | 先读 `Cached` 与可回收的 `SReclaimable`，再评估重建缓存的代价 | 不要在生产机上执行 `drop_caches` |
| 进程申请内存成功但很快被杀 | 这属于承诺额度与物理落地分离的情况 | 先读 `VmSize` 与 `Committed_AS`，再核对超额分配策略 | 不要只看 `VSZ` 就判断这个进程占了很多内存 |
| 「内存去哪了」，进程占用加起来对不上 | 这属于占用归类有漏项的情况 | 依次核对 tmpfs、内核对象与被 cgroup 计入的页缓存 | 不要先加内存 |
| `free` 还有余量却发生了 OOM | 这属于撞上局部上限的情况 | 先在内核日志里找 cgroup OOM 记录，再读该 cgroup 的 `memory.events` | 不要说内核日志写错了 |
| 容器被 OOMKilled，宿主却很空 | 这属于容器用量记在 cgroup 文件里的情况 | 先读该 cgroup 的 `memory.current`、`memory.max` 与 `memory.stat`，再读容器内的 `/dev/shm` | 不要拿宿主的 `free` 当判据 |
| 退出码是 137，就直接写成「OOM」 | 这属于定性证据不足的情况 | 先读内核日志与该 cgroup 的 `memory.events`，再核对人工操作记录 | 不要把 137 当作 OOM 的证明 |
| `si`/`so` 长期非 0，延迟抖动 | 这属于换页压力已经落到磁盘路径的情况 | 先读 `vmstat` 的 `si`/`so`、压力指标与各进程的 `VmSwap` | 不要直接 `swapoff`，也不要把 `swappiness` 归零 |
| 写入变慢、进程进入 `D` 状态 | 这属于回写跟不上设备排空的情况 | 先读 `Dirty`/`Writeback` 与设备 `await`，再读进程级 IO | 不要把它当成内存不足去加内存 |
| 内存缓慢增长，被判定为泄漏 | 这属于要用趋势判断的情况 | 按 `RssAnon`、`RssFile`、`RssShmem` 三条曲线分别取样 | 不要用单次 `top` 的读数下结论 |
| 服务把整机拖到 OOM | 这属于服务缺少上限的情况 | 先读该服务的 `MemoryMax=` 与内核日志 | 不要只调 `oom_score_adj` 去保护别的进程 |
| 内存总量比标称少一截 | 这属于固件与内核预留的情况 | 依次核对固件预留、显存、大页预留与 `crashkernel=` | 不要先怀疑内存条坏了 |
