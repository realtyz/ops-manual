## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **每个进程都以为自己独占内存**：它看到的是一整套虚拟地址空间，真正落在哪块物理内存由页表决定，进程自己看不见。
> - **映射是按需建立的**：`malloc` 只是把地址空间划出去一块，**第一次写入**才触发缺页、拿到物理页，所以「申请成功」和「占用内存」是两件事。
> - **缺页有贵贱**：页已经在内存里、只缺映射是 minor fault；需要从磁盘或 swap 读进来是 major fault，代价差一个数量级。
> - **`fork` 不复制内存，复制的是页表**：父子共享物理页，谁写谁复制（写时复制，Copy-On-Write，简称 COW）。这也是「`fork` 之后两个进程的 `RSS` 加起来翻倍、实际内存没翻倍」的原因。
> - **大页（THP/HugePages）是拿内存粒度换 TLB 效率**：少了 TLB 未命中和页表遍历，代价是内存碎片与偶发停顿。

## 1. 为什么要有虚拟内存

如果进程直接操作物理地址，会立刻碰到四个问题：进程之间互相踩内存、程序必须知道自己被加载到哪、内存不够时没法腾挪、共享一份代码要复制多份。虚拟内存一次解决了这四件事：

| 目标 | 怎么实现 | 代价 |
| --- | --- | --- |
| 隔离 | 每个进程一套页表，谁也不能直接碰别人的物理页 | 每次访存都要走页表（由 TLB 加速） |
| 简化编程 | 程序从固定地址开始编，加载位置由内核安排 | 地址翻译带来开销 |
| 腾挪空间 | 不常用的页可以换出到 swap，再换回来 | 换页引起延迟抖动（子笔记 07） |
| 共享 | 同一份代码页被多个进程映射 | 共享页的计量会失真（`RSS` 重复计数，子笔记 05） |

一句话：**虚拟内存让「进程看到的地址」与「数据实际在哪」解耦**。后面所有的排障，本质上都在追问这层映射的两端：「映射了多少」和「真正落地了多少」。

## 2. 页、页框、页表与 TLB

内核不以字节为单位管理内存，而是以**页**为单位。常见页大小 4 KiB；页表记录「虚拟页 → 物理页框」的对应关系。

| 名词 | 一句话 | 在哪里能观察到 |
| --- | --- | --- |
| 页（page） | 虚拟地址空间里的一段（常见 4 KiB） | `getconf PAGE_SIZE` |
| 页框（page frame） | 承载页的物理内存块 | `/proc/buddyinfo`（按阶的空闲块分布） |
| 页表（page table） | 虚拟页到物理页框的映射表，多级结构 | `/proc/meminfo` 的 `PageTables`、`/proc/<pid>/status` 的 `VmPTE` |
| TLB（Translation Lookaside Buffer） | 缓存最近用过的映射，避免每次访存都遍历页表 | 没有直接文件；通过大页与性能计数间接观察 |
| 映射（mapping） | 一段虚拟地址与某个对象（文件、匿名内存）的对应关系 | `/proc/<pid>/maps` |

```bash
getconf PAGE_SIZE                    # 验证：本机页大小（x86_64 常见 4096）
cat /proc/meminfo | grep -E '^(MemTotal|Mapped|PageTables):'
                                     # 验证：整机内存总量、被映射的页、页表占用的内存
cat /proc/<pid>/maps | head -20      # 验证：某个进程的地址空间被切成了哪些段
cat /proc/<pid>/status | grep -E 'VmSize|VmRSS|VmPTE|VmPMD'
                                     # 验证：该进程的地址空间、常驻页与页表开销
```

两个容易忽略的事实：

1. **页表本身要吃内存**。映射越多，页表越大。数据库、JVM 这类映射了大量地址空间的进程，光页表就可能占几百 MiB 到几 GiB（子笔记 05）。
2. **不是所有虚拟页都有物理页**。`VmSize`（虚拟）远大于 `VmRSS`（常驻）是常态，不是异常。

## 3. 缺页异常：映射是「用到才建」的

进程访问一个虚拟地址时，硬件先查 TLB，再查页表。如果发现这个页还没有对应的物理页框，就触发**缺页异常**，交给内核处理。按代价分两种：

| 类型 | 触发场景 | 代价 | 观察 |
| --- | --- | --- | --- |
| minor fault | 物理页已经在内存里（例如文件页已在 Page Cache、匿名页刚被分配、COW 复制），只缺页表项 | 低 | `ps` 的 `min_flt`、`/proc/<pid>/stat` |
| major fault | 物理页不在内存里，需要从磁盘或 swap 读入 | 高，可能是毫秒级 | `ps` 的 `maj_flt`、`/proc/vmstat` 的 `pgmajfault` |

**major fault 陡增是内存压力的早期信号**：它说明进程要的数据已经被挤到磁盘或 swap 上了。反过来，minor fault 高通常只是分配与映射行为活跃，不代表压力。

```bash
ps -eo pid,comm,min_flt,maj_flt --sort=-maj_flt | head -10
                                     # 验证：哪些进程的 major fault 最多
cat /proc/vmstat | grep -E '^(pgfault|pgmajfault)'
                                     # 验证：整机缺页计数（差值才有意义，看的是速率）
```

## 4. 按需分配与写时复制（COW）

两个「看起来反直觉」的现象都来自这一节。

**按需分配**：`malloc`/`mmap` 返回成功，只代表内核把这段虚拟地址记在了进程名下，不代表物理页已经给出。第一次写入才触发缺页、分配物理页。所以：

- `VSZ` 很大不代表占用大（子笔记 04、05）；
- 内存不足时，进程可能在「用的时候」才被杀，而不是申请的时候（子笔记 08）。

**写时复制**：`fork` 之后，父子进程的页表都指向同一批物理页，并且这些页被标成只读；任一方写入时触发缺页，内核复制一份给写的那一方，再改成可写。所以：

- `fork` 本身很快，内存不会立刻翻倍；
- 但父子任何一方大量写内存，都会触发真实的复制（典型的 `fork` 后立刻改数据，比如某些备份场景）；
- **`ps` 里父子进程的 `RSS` 相加会重复计数同一批共享页**，这就是为什么要用 `PSS`（子笔记 05）。

```bash
cat /proc/meminfo | grep -E '^(AnonPages|Mapped|Shmem|Cached):'
                                     # 验证：整机的匿名页、映射页与缓存分布
pmap -x <pid> | head -20             # 验证：单个进程各段的大小与常驻情况（不同版本列名略有差异）
```

## 5. 地址空间长什么样

一个典型进程的地址空间不是一个连续的大块，而是若干段：代码、只读数据、已初始化/未初始化数据、堆、`mmap` 区域（共享库、文件映射、线程栈）、栈。理解这个布局的实用价值有三点：

1. **`VSZ` 是这些段的总和**，其中线程栈和文件映射最容易把它撑大；
2. **`VmSize` 大、`VmRSS` 小**时，先看 `maps` 里是不是有大段「预留但没碰」的映射；
3. **映射数量本身有上限**（`vm.max_map_count`，常见默认 `65530`），程序疯狂 `mmap` 时会以 `ENOMEM` 失败，看起来像「内存不够」。

```bash
sysctl vm.max_map_count              # 验证：本机允许的最大映射段数
cat /proc/<pid>/maps | wc -l         # 验证：该进程当前的映射段数量（JVM、数据库容易偏高）
```

## 6. 大页：拿粒度换效率【进阶】

4 KiB 页意味着同样的内存需要更多页表项、更多 TLB 覆盖不住的范围、更多缺页次数。大页用更大的粒度换更少的地址翻译开销：

| 方案 | 怎么来 | 收益 | 代价 |
| --- | --- | --- | --- |
| 显式 HugePages（hugetlbfs） | 预留：`vm.nr_hugepages`，应用显式申请 | 延迟稳定、TLB 效率高，适合数据库 | 预留后即使不用也不参与常规分配；需要规划数量 |
| 透明大页 THP | 内核自动合并（`always`）或按 `madvise` 提示 | 无需改应用；吞吐型负载常见收益 | 内存放大、碎片、后台整理带来偶发停顿 |

```bash
cat /sys/kernel/mm/transparent_hugepage/enabled      # 验证：THP 策略 always / madvise / never
cat /sys/kernel/mm/transparent_hugepage/defrag       # 验证：THP 整理策略（内核版本不同取值可能不同）
grep -E '^(AnonHugePages|HugePages_Total|Hugepagesize|ShmemHugePages):' /proc/meminfo
                                     # 验证：当前 THP 与显式大页的使用情况
```

取舍与调法留到子笔记 05 与 11；这里只需要建立一个判断：**大页不是「越大越好」，它把随机的小块分配换成了大块的、需要提前规划的分配**。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 「`VSZ` 有 8 GiB，这个进程太吃内存了」 | `VSZ` 是虚拟地址空间，包含未落地的映射与线程栈；判断占用要看 `RSS`/`PSS` |
| 「`malloc` 成功就说明内存够」 | 成功只代表地址空间记账成功，真正分配在第一次写入时；`overcommit` 允许承诺超过物理内存 |
| 把 minor fault 当内存压力 | minor fault 高多为分配/映射活跃，只有 **major fault 上升**才说明要回磁盘或 swap 取页 |
| 用父子进程 `RSS` 相加估算内存 | `fork` 后共享页会被重复计数；跨进程比较要用 `PSS`/`USS` |
| 「页表不占内存」 | 映射越多页表越大，`PageTables` 可以到 GiB 级，大内存进程尤其明显 |
| 认为 `MemTotal` 就是插的内存条容量 | 固件、显卡、`crashkernel=` 预留与 HugePages 预留都不计入（子笔记 09） |
| 为了「省内存」把 THP 一律关掉或一律开成 `always` | 两种情况都会在特定负载上出问题；改之前要有前后性能对比（子笔记 11） |

## 决策练习

> [!question]- 场景：某 Java 服务 `VSZ` 显示 32 GiB、`RSS` 只有 1.2 GiB，监控告警「内存使用率 95%」。值班同事提议先把 `-Xmx` 调小。你怎么判断，先做什么？
> A. 直接调小 `-Xmx`，反正堆预留了 32 GiB
> B. 先确认告警口径与真实压力：这台机器的 `MemAvailable` 与 PSI 如何、这 32 GiB 里哪些是「预留未落地」的地址空间（`maps`、`VmRSS`、`RssAnon`），再决定是堆预留过大、缓存增长还是真有压力
> C. 把 THP 关掉，Java 的内存问题大多和 THP 有关
>
> **答案：B。**
> A 把「地址空间」当成了「物理占用」：JVM 预留堆地址空间不等于立刻占满内存，贸然调 `-Xmx` 可能直接改变应用行为，却不一定解决告警。
> C 是典型的「用一个常见结论替代诊断」：THP 确实可能造成 Java 停顿，但当前问题描述里没有任何 THP 证据。
> B 是正解：**先分清虚拟与常驻，再看这台机器的真实压力（`MemAvailable` + PSI），最后才谈参数**。这也是本章第一站到第五站的顺序。

## 要点自测

> [!question]- 虚拟地址和物理内存是什么关系？为什么每个进程都「以为自己独占内存」？
> - 进程用的是虚拟地址，内核用页表把它映射到物理页框；不同进程的页表互相独立，所以谁也看不见谁的物理页。
> - 代价是每次访存要翻译地址（TLB 加速），以及页表本身占内存。
> - **第一反应不要是什么**：不要用「虚拟内存就是硬盘上的 swap」来理解——swap 只是虚拟内存机制的一个可选去处，不是虚拟内存本身。

> [!question]- 为什么 `malloc` 成功不等于占用内存？这个性质有什么生产意义？
> - `malloc`/`mmap` 只改变虚拟地址空间的记账，第一次写入才通过缺页拿到物理页。
> - 生产意义：① 判断占用不能看 `VSZ`；② 内存压力可能延后到「真正写入」时才爆发；③ `overcommit` 策略决定了「承诺」的松紧（子笔记 04、08）。
> - **第一反应不要是什么**：不要把「申请成功」当作容量验证，也不要把 `VSZ` 写进容量报表。

> [!question]- minor fault 和 major fault 差在哪？哪个才是压力信号？
> - minor：物理页已在内存里，只缺映射，代价低；major：需要从磁盘或 swap 读入，代价高。
> - 压力信号是 **major fault 上升**（配合 PSI 与 `si/so`），说明工作集已经被挤出内存。
> - **第一反应不要是什么**：不要看到 `pgfault` 总数大就判断内存紧张——缺页是正常行为，要看的是 major 部分和它的变化趋势。

> [!question]- `fork` 为什么「又快又危险」？它对内存计量有什么影响？
> - 快：只复制页表并把页标成只读，父子共享物理页（COW），不复制内容。
> - 危险：父子任一方大量写入都会触发真实复制；如果写入量接近整份内存，等于把内存占用翻倍。
> - 计量影响：共享页会让 `RSS` 重复计数，父子 `RSS` 相加会大于物理占用，跨进程比较要用 `PSS`。
> - **第一反应不要是什么**：不要把「`fork` 成功」当作「内存一定够」，`fork` 之后的写入才是压力真正到来的时刻。

> [!question]- 大页解决了什么问题，又带来什么代价？
> - 解决 TLB 覆盖范围与页表开销问题：同样内存用更少的页表项覆盖，减少地址翻译成本。
> - 代价：显式 HugePages 需要预留、不参与常规分配；THP 会带来内存放大与整理停顿，碎片严重时还可能分配失败。
> - **第一反应不要是什么**：不要用「开/关 THP」这类一刀切动作解释或掩盖性能问题，先量化瓶颈（子笔记 11）。
