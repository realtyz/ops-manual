# 内存去哪了：三类答案

> [!cite] 参考资料
> `man 5 proc`（`/proc/meminfo`、`/proc/<pid>/smaps_rollup`）、`man 1 slabtop`、`man 1 df`、`man 1 ipcs`、`man 8 mount`、`man 5 sysctl`（`vm.vfs_cache_pressure`）、`man 5 systemd.resource-control`，以及内核文档 `Documentation/admin-guide/cgroup-v2.rst`（memory 控制器）与 `Documentation/filesystems/tmpfs.rst`。
>
> 本篇结论来自上述资料，**命令输出尚未在实验机上逐条实测**；本机结果与文中不一致时以本机输出为准。

> **这篇讲什么**：`free` 显示内存被占走了，可把进程 `RSS` 加起来又对不上账——这是内存排障里最常见的追问。答案基本落在三类：**tmpfs 与共享内存、内核 slab 与目录项缓存、被 cgroup 计入的页缓存**。它们都不在任何进程的 `RSS` 里，也都不显眼。
>
> **必须先读什么**：[[Linux/04_内存管理与OOM/02_前置_内存观测工具与proc|02 前置：内存观测工具与 /proc]]、[[Linux/04_内存管理与OOM/05_第2站_落地与计量|05 第 2 站：落地与计量]]（口径）。
>
> **读完能回答**：① 「内存去哪了」按什么顺序对账？② tmpfs 为什么既在 `df` 里又在内存里？③ `SUnreclaim` 涨上来意味着什么？
>

## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **「对不上账」是正常的**：`free` 的 `used` 减掉了缓存，进程 `RSS` 又漏掉内核与共享部分，两边都不可能直接相加。
> - **第一类：tmpfs 与共享内存**：占的是内存（`Shmem`），却能在 `df` 里看见；没有 swap 时基本回收不掉。
> - **第二类：内核 slab**：`SReclaimable` 会随压力释放，`SUnreclaim` 才是长期占用；`dentry/inode` 膨胀常与「扫大量小文件」相关。
> - **第三类：被 cgroup 计入的页缓存**：容器写日志、读大文件都会把 `file` 记进自己的账本——**宿主看很宽松，容器自己 OOM**。
> - **还有一层是「根本没算进 `MemTotal`」**：固件/显卡占用、`crashkernel=` 预留、HugePages 预留，都是「机器有 128 GiB 却显示不到」的原因。

## 1. 为什么会「对不上账」

三张账本口径不同，直接相加必然错位：

| 账本 | 包含什么 | 漏掉什么 |
| --- | --- | --- |
| `free`/`meminfo` | 整机物理内存的全景 | 不告诉你「归谁」 |
| 进程 `RSS` 之和 | 进程常驻页（共享页重复计） | 内核内存、tmpfs（在 `RssShmem` 里但常被忽略）、被重复计的部分 |
| cgroup `memory.stat` | 该组的 `anon`/`file`/`slab`/`shmem` | 只覆盖该组，看不到别的组与整机 |

所以正确的问法不是「`free` 少了多少」，而是「**这几类各占多少**」。

## 2. 第一类：tmpfs 与共享内存

tmpfs 是挂在内存里的文件系统：`/dev/shm`、`/run`、`/tmp`（视发行版配置）都可能是 tmpfs。它的页记在 `Shmem` 与 `Cached` 里，**不在任何进程的 `RSS`**（除非进程自己映射了它）。

```bash
df -h | grep -i tmpfs                # 验证：tmpfs 挂载点与用量（占的是内存）
df -h /dev/shm                       # 验证：共享内存目录（默认上限约为内存的 50%）
mount | grep -E 'tmpfs.*(shm|/tmp)'  # 验证：挂载参数与大小上限
grep -E '^(Shmem|Cached|MemAvailable):' /proc/meminfo
ipcs -m                              # 验证：SysV 共享内存段（老应用常用）
```

两个关键结论：

- **没有 swap 时，tmpfs 页基本回收不掉**（没有后备存储可写回），所以它会让 `MemAvailable` 的估算偏乐观；
- **容器里的 `/dev/shm` 默认只有 64 MiB**（Docker `--shm-size` 默认值），与宿主的「内存一半」不是一回事。容器里写共享内存先撞这个小上限。

## 3. 第二类：内核 slab 与 dentry/inode 缓存

内核自己也要用内存：对象缓存（slab）里最典型的就是目录项（dentry）与 inode 缓存。它们不在任何进程的 `RSS` 里：

| 字段 | 含义 | 处理方式 |
| --- | --- | --- |
| `Slab` | slab 总量（= `SReclaimable` + `SUnreclaim`） | 看构成，不看总数 |
| `SReclaimable` | 有压力时可以回收的部分 | 通常不用管，压力来了自己释放 |
| `SUnreclaim` | 回收不掉的部分 | **持续上涨才是问题**，要定位是哪个 slab |

```bash
cat /proc/meminfo | grep -E '^(Slab|SReclaimable|SUnreclaim):'
slabtop -o -s c | head -20           # 验证：slab 占用排行（按字节排序）
sysctl vm.vfs_cache_pressure         # 验证：dentry/inode 的回收倾向（默认 100）
```

`vfs_cache_pressure` 调低会让内核更愿意保留 dentry/inode 缓存（文件访问更快、内存占用更高）；调高则相反。**它不是「省内存」的开关**，改动要有文件访问性能的对比。

## 4. 第三类：被 cgroup 计入的页缓存

cgroup v2 的 `memory.current` 包含该组名下的页缓存。**页缓存记在「写它的那个 cgroup」头上**：容器写日志、读大文件，都会把 `file` 记进容器自己的账本。

```bash
cat /sys/fs/cgroup/<路径>/memory.current
cat /sys/fs/cgroup/<路径>/memory.stat | grep -E '^(anon|file|shmem|slab|sock|file_dirty) '
cat /sys/fs/cgroup/<路径>/memory.events
```

判读顺序：`anon` 涨说明是进程堆栈；`file` 涨说明是缓存/日志；`shmem` 涨说明是共享内存与 tmpfs（子笔记 10 有完整治理动作）。

> [!important] 「宿主很宽松，容器却被杀」就出在这里
> 宿主 `MemAvailable` 是整机口径；容器的上限是 `memory.max`。容器写日志产生的页缓存会把它自己推向上限，而宿主根本感觉不到。**判断容器内存只看宿主 `free` 一定会误判。**

## 5. 附加答案：内核开销与「不在 `MemTotal` 里」的内存

除了三类主答案，还有两类容易算错：

**内核自身开销**（在 `meminfo` 里，但不属于任何进程）：

| 字段 | 含义 |
| --- | --- |
| `PageTables` | 页表占用（大内存/多映射进程显著） |
| `KernelStack` | 每个任务的内核栈 |
| `VmallocUsed` | 内核虚拟地址空间使用量 |
| `Percpu` | 每 CPU 的分配区 |

**根本没算进 `MemTotal` 的预留**：

| 预留 | 说明 |
| --- | --- |
| 固件/硬件占用 | BIOS/UEFI、集显、部分外设会保留物理内存 |
| `crashkernel=` | 给 kdump 预留的内存，**不计入 `MemTotal`**（阶段 2 已讲过这套机制） |
| HugePages 预留 | `HugePages_Total × Hugepagesize`，预留后即使没人用也不参与常规分配 |

```bash
grep -E '^(PageTables|KernelStack|VmallocUsed|Percpu|HardwareCorrupted|CmaTotal|HugePages_Total|MemTotal):' /proc/meminfo
cat /proc/cmdline                    # 验证：是否有 crashkernel= 等启动参数
```

## 6. 对账流程：五步，从大到小

> [!tip] 第一反应不要是「加内存」或「清缓存」
> 先把账对上：`free` 少的到底是哪一类内存。三类答案各有各的去处与解法。

1. **看整机大账**：`MemTotal`、`MemFree`、`MemAvailable`、`Cached`、`Shmem`、`Slab` 各是多少；
2. **拆缓存**：`Cached` 里多少是 `Shmem`？`Slab` 里多少是 `SUnreclaim`？
3. **看 tmpfs/共享内存**：`df -h | grep tmpfs`、`df -h /dev/shm`、`ipcs -m`；
4. **看内核侧**：`slabtop` 找膨胀的 slab；`PageTables`/`KernelStack` 是否异常；
5. **看 cgroup 侧**：如果现象只在某个服务/容器上，读它的 `memory.stat` 与 `memory.events`。

```bash
free -h; cat /proc/meminfo | grep -E '^(MemTotal|MemFree|MemAvailable|Cached|Shmem|Slab|SReclaimable|SUnreclaim|PageTables|KernelStack):'
df -h | grep -i tmpfs; df -h /dev/shm
slabtop -o -s c | head -15
cat /sys/fs/cgroup/<路径>/memory.stat | grep -E '^(anon|file|shmem|slab|sock) '
```

## 7. 生产动作：实验 3（tmpfs 占内存，`used` 却看不见）

> [!example]- 实验 3：往 `/dev/shm` 写 256 MiB，看 `Shmem` 涨而 `used` 几乎不动
> **怎么做**：
> ```bash
> df -h /dev/shm                       # 验证：tmpfs 的容量上限
> grep -E '^(Shmem|Cached|MemAvailable):' /proc/meminfo; free -h      # 记录基线
> dd if=/dev/zero of=/dev/shm/lab-tmpfs bs=1M count=256               # 写入 256MiB
> df -h /dev/shm; free -h; grep -E '^(Shmem|Cached|MemAvailable):' /proc/meminfo
>                                      # 验证：df 显示用了 256MiB；Shmem/Cached 上涨；used 变化不明显
> rm -f /dev/shm/lab-tmpfs             # 删除文件后立即释放
> df -h /dev/shm; grep -E '^(Shmem|Cached|MemAvailable):' /proc/meminfo
> ```
> **预期**：`/dev/shm` 用量与 `Shmem` 同步变化，而 `df` 给出的「容量」让人误以为这是块磁盘。**在无 swap 的机器上，这些页在文件被删除前基本回收不掉。**
> **风险**：低到中。会真实占用 256 MiB 内存（无 swap 时不可回收）；小内存机器请把 256 MiB 调小。
> **耗时**：约 10 分钟。
> **怎么退回去**：`rm /dev/shm/lab-tmpfs`，确认 `df -h /dev/shm` 与 `Shmem` 回落。

## 常见坑

| 常见做法或说法                       | 后果或事实                                           |
| ----------------------------- | ----------------------------------------------- |
| 把所有进程 `RSS` 相加与 `free` 对账     | 口径不同（共享页重复计、内核内存不在进程账上），永远对不上                   |
| 看到 `Cached` 大就认为「全是文件缓存」      | `Cached` 包含 `Shmem`（tmpfs/共享内存），两者的回收行为不同       |
| 认为 tmpfs 是「内存盘，删了才占」          | 它的页在文件存在期间一直占着内存，无 swap 时回收不掉                   |
| 用宿主 `/dev/shm` 的大小推断容器        | 容器内默认 64 MiB（Docker），与宿主「内存一半」不同                |
| 只看 `Slab` 总数                  | `SReclaimable` 会随压力释放；要盯 `SUnreclaim` 与具体 slab  |
| 把 `vfs_cache_pressure` 当省内存开关 | 它只是调整保留倾向；调低反而占用更多内存                            |
| 「`MemTotal` 比我买的少就是内存条坏了」     | 固件、`crashkernel=`、HugePages 预留都会让 `MemTotal` 偏小 |
| 容器里对不上账就查宿主进程                 | 容器的账在 cgroup 里，页缓存记在容器头上；宿主进程 `RSS` 看不到         |

## 决策练习

> [!question]- 场景：一台无 swap 的机器，`free -h` 显示 `available` 6 GiB、`used` 9 GiB；但把所有进程 `RSS` 加起来只有 5 GiB。有人提议「清理内核页缓存，把那 4 GiB 找回来」。你的判断是？
> A. 执行 `drop_caches`，看能不能找回 4 GiB
> B. 先按五步对账：看 `Shmem`（tmpfs/共享内存，无 swap 时不可回收）、`Slab`/`SUnreclaim`、`PageTables` 与 cgroup 的 `memory.stat`，找出这 4 GiB 属于哪一类再决定动作
> C. 直接加 8 GiB 内存，容量翻倍最省事
>
> **答案：B。**
> A 只能清掉干净缓存，不会碰到 tmpfs 与 `SUnreclaim`；无 swap 的 tmpfs 页删文件之前根本回收不掉。
> C 没有定位就扩容，可能是白花钱。
> B 是正解：**先对账，再动手**。三类答案里，只有确认了归属才知道该删文件、该修应用，还是确实要扩容。

## 要点自测

> [!question]- 「内存去哪了」的三类主答案是什么？各自的现场在哪？
> - tmpfs/共享内存（`Shmem`、`df`、`ipcs -m`）、内核 slab（`Slab`/`SUnreclaim`、`slabtop`）、被 cgroup 计入的页缓存（`memory.stat` 的 `file`）。
> - 附加：`PageTables`/`KernelStack`/`VmallocUsed` 与 `crashkernel=`/HugePages 预留。
> - **第一反应不要是什么**：不要在没分类前加内存或清缓存。

> [!question]- tmpfs 与普通文件缓存有什么本质差别？
> - 普通文件缓存有磁盘后备，脏页可以回写、干净页可以直接丢弃。
> - tmpfs 页没有磁盘后备：删除文件才释放，有 swap 时可以换出，没 swap 时基本回收不掉。
> - **第一反应不要是什么**：不要把 `/dev/shm` 当成一块「不会影响内存」的磁盘。

> [!question]- `SReclaimable` 与 `SUnreclaim` 该怎么看？
> - `SReclaimable`：压力来时会自动释放，通常不需要干预。
> - `SUnreclaim`：回收不掉的长期占用；持续上涨要用 `slabtop` 定位具体缓存（常见是 dentry/inode 或驱动相关对象）。
> - **第一反应不要是什么**：不要看到 `Slab` 大就动手，先分清能不能回收。

> [!question]- 为什么容器里「宿主很空」却会 OOM？
> - 容器的账在 cgroup 里（`memory.current` 对 `memory.max`），页缓存（写日志、读文件）也记在容器头上。
> - 宿主 `MemAvailable` 是整机口径，两者没有直接关系。
> - **第一反应不要是什么**：不要用宿主 `free` 排除容器的内存问题。

> [!question]- `MemTotal` 比标称内存小，可能的原因有哪些？
> - 固件/硬件保留、`crashkernel=` 预留、HugePages 预留、部分内核保留页。
> - 先看 `/proc/cmdline` 与 `meminfo` 的预留相关字段，再判断是否真的异常。
> - **第一反应不要是什么**：不要第一反应就报硬件故障。
