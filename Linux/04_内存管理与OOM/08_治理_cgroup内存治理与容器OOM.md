# cgroup 内存治理与容器 OOM

## 1. 为什么每个服务都要有上限

没有上限的服务可以把整机内存用尽，把故障从"一个服务变慢"放大成"整机不可用"；给它配上内存上限（再配合副本数与容量规划），就能把故障限制在一个服务内。**内存上限首先是可用性手段，其次才是资源手段。**

上限可以从四层写入，而四层的**载体不同**，因此查文档和改配置的地方也不同。

| 层 | 载体 | 撞上之后会发生什么 |
| --- | --- | --- |
| 进程自身 | 它是**资源限制**：`RLIMIT_AS`、`RLIMIT_DATA`（由 `setrlimit(2)` 或 shell 的 `ulimit` 设置） | 申请会失败并返回 `ENOMEM`，进程可能直接报错退出 |
| 服务 unit | 它是 **systemd 属性**：unit 文件里的 `MemoryHigh=`/`MemoryMax=` | 软线只做节流，硬线触发该 cgroup 内的 OOM |
| cgroup | 它是**内核接口文件**：`memory.high`/`memory.max` | 与上一行相同，因为 systemd 这两个属性正是它们的封装 |
| 整机 | 它是**内核参数**：物理内存与 swap 的用量加水位（用 `sysctl` 查看与设置） | 触发整机 OOM，内核从全局挑进程杀掉 |

出问题时先确定是哪一层：是进程自己报错退出、被 cgroup 杀，还是整机水位被撞穿——这三种结论对应三种完全不同的修法。

## 2. cgroup v2 的接口怎么用于治理决策

字段本身的读写与单位在实操篇 2.5；这里讲**怎么用它们做决定**。

| 文件 | 治理时怎么用它 |
| --- | --- |
| `memory.current` | 它给出当前用量；若长期贴着上限，则说明上限定得过紧，或者应用确实在增长 |
| `memory.peak` | 它给出历史峰值，因此是**定上限的主要依据**：上限应高于正常峰值并留出余量 |
| `memory.max` | 它是硬上限，撞上就触发 OOM；取值为 `max` 表示没有上限，这也是很多服务的默认状态 |
| `memory.high` | 它是软上限，超出后只做节流（回收与限速）而不杀进程，因此适合"先抑制增长"的场景 |
| `memory.low` | 它是保护设置：回收时内核尽量不动这里的页，因此适合给关键服务用 |
| `memory.swap.max` | 它限制该 cgroup 可用的 swap；设为 0 表示这类服务禁用换页（代价见判例 7） |
| `memory.stat` | 它给出构成明细，**决定处置方向**：若 `anon` 高，则应用真的在用；若 `file` 高，则是页缓存计入；若 `slab` 高，则是内核对象 |
| `memory.events` | 它给出事件计数：`oom_kill` 非 0 说明确有进程被杀，`max` 非 0 说明撞过上限（可能只被节流） |

由此得到三条使用要点。

1. **所有计数都是累积值**，因此"这次事件有没有发生"要用两次读数的**差值**判断。
2. **上限不是拍出来的**：要用 `memory.peak` 与历史曲线说话，并写清安全系数。
3. **这些计数文件有时效**：cgroup 目录会随单元结束被回收，因此 `memory.events` 这类证据只在存活期间存在——复盘要趁现场还在。

`memory.high` 与 `memory.max` 的区别值得单独记住：前者只做节流（回收与限速），进程继续运行；后者是硬上限，撞上就触发 OOM 并杀掉进程。**给延迟敏感的服务先上 `high` 通常比直接上 `max` 更安全**，但如果它真的失控，`high` 拦不住。

## 3. systemd 侧的映射与默认行为

`MemoryHigh=`/`MemoryMax=`/`MemorySwapMax=` 分别对应 `memory.high`/`memory.max`/`memory.swap.max`；`MemoryAccounting=` 打开记账，服务的默认值是开启。

**必须知道的默认行为**：`OOMPolicy=stop` 是服务单元的默认值，因此该单元内有进程被 OOM 杀掉时，systemd 会把**整个单元停掉**，同时 cgroup 与其中的计数文件一起消失。要在 OOM 之后复盘现场，就得显式设成 `OOMPolicy=continue`（该属性要求 systemd ≥243），或者提前把 cgroup 文件采下来。

`systemd-oomd` 是另一套机制：它是用户态的 OOM 守护进程，基于 cgroup v2 与 PSI 在"压力很大但还没 OOM"时提前动手，配置在 `oomd.conf`。它的动作与内核 OOM 在日志里长得不一样，因此排查时要先确认是哪一个动的手。

## 4. 容器里的六个坑

1. **容器里读 `/proc/meminfo` 看到的是宿主。** 容器的额度与用量在 cgroup 文件里（实操篇 2.5）；判断方法是容器内 `free` 的 `MemTotal` 与宿主一致，而 `memory.current` 与它无关。
2. **页缓存计入容器。** 容器读写文件产生的缓存算在它的内存里，这部分可回收，但会推高 `memory.current`；判断方法是看 `memory.stat` 里 `file` 是否占大头，处置方向是看访问模式，而不是简单加额度。
3. **`/dev/shm` 的大小由挂载选项或容器运行时的默认值决定**，很多环境只有 64 MiB，因此必须现场用 `df -h /dev/shm` 确认。共享内存类应用会在这里失败，报错是 `ENOSPC`；处置是调大它的上限，或改用文件与流式处理，并评估内存占用。
4. **页表与内核栈同样计入。** 大内存、多线程进程的页表开销会占掉一部分额度；判断方法是看 `memory.stat` 的 `slab` 与 `kernel_stack` 相关项，处置是减少映射数量或线程数。
5. **`OOMKilled` 只是一个标签**，因此要区分撞的是 `memory.max` 还是整机水位：前者是配额问题，后者是容量或邻居问题。
6. **容器看到的 CPU 数与 NUMA 节点数可能与宿主不同**，因为它们受 `cpuset` 约束。按容器内视角推算容量会失真，因此容量规划要回到宿主视角。

## 5. 治理场景与产出

下面四个场景是运维侧真正会遇到的治理动作。每个都给出**要做出的产出**，因为内存上限治理的验收标准是"交出了东西"，不是"看过文档"。

### 场景一：给一个即将上线的服务定内存上限

**背景**：新服务上线前压测显示稳态 350 MiB、峰值 780 MiB，计划 3 个副本；团队想知道 `MemoryMax=` 该写多少。

**做法**：以"上限高于峰值并留出安全系数"为原则给初值（例如 1 GiB）；上线后用 `memory.peak` 复核，再按真实峰值重新校准。**不要照抄邻居服务**，因为它们的分配模式不同。

**产出**：一条带依据的记录，它要写明服务名、cgroup 路径、初值及其依据（压测峰值乘以系数）、复核时间与复核方法，以及回滚方式。

### 场景二：上限调小之后，服务开始被 OOMKilled

**背景**：为"节省资源"，某服务上限从 2 GiB 调到 512 MiB；当晚它被 OOMKilled 三次，`memory.peak` 每次都贴住 512 MiB。

**做法**：先确证撞的是它（内核日志的 `oom_memcg=`、`memory.events` 的 `oom_kill` 差值），再看 `memory.stat` 的构成与当时的业务量。结论只有三种，必须落到其中一种：

- 若结论是**配额过紧**，则应回滚或调整上限，依据是峰值与业务增长趋势；
- 若结论是**应用峰值超出预期**，则应优化或扩容，因为配额只是暴露了问题；
- 若结论是**页缓存计入额度**（`memory.stat` 的 `file` 占大头），则应看访问模式，可能要给缓存留余量而不是加限制。

**产出**：一份 OOM 复盘记录，它要回答三个问题——谁被杀（进程、cgroup 与当时用量）、为什么是它（权重与选择依据）、撞的是谁的上限（cgroup 还是整机）；并附回滚动作与后续观察窗口。

### 场景三：同一节点上多个服务互相拖累

**背景**：节点上的 A 服务突发把内存用得很紧，导致 B 服务开始换页、延迟抖动。两者都在同一台机器上，暂时无法拆机。

**做法**：给 A 设 `memory.max`，把它限制在自己那一格；给 B 设 `memory.low`，让回收时尽量不动它；如果 A 是多进程组，就考虑 `memory.oom.group`（设为 1 时 OOM 终结整个 cgroup，而不是单个进程）。**优先用 cgroup 做隔离，而不是调 `oom_score_adj` 去改变内核挑中谁的概率**，因为后者只是概率，前者是边界。

**产出**：隔离方案与验证方式，也就是各自的上限、保护设置，以及"压力下 B 是否还在换页"的复查步骤。

### 场景四：巡检发现一批服务没有上限

**背景**：巡检 40 个服务，`MemoryMax` 显示 `infinity`；不可能一次全改。

**做法**：按"峰值内存乘以影响面"排序推进，先做核心链路与内存大户；每个服务先补一次只读基线（峰值、构成、压力），再分批改上限；每批改完留观察窗口。**不要一次性批量改**，因为 40 个服务的上限同时生效，等于把 40 个未知风险同时引入。

**产出**：一张排期表（服务、当前峰值、目标上限、影响面、批次、验证方式）与每批的变更记录。

## 6. 治理产物四件套

**配额基线卡**要记录服务名与 cgroup 路径、`memory.max` 与 `memory.peak`、稳态与峰值用量、压力指标基线、历史 `oom_kill` 次数，以及是否使用 swap，它的用途是回答"这个上限该不该调"。

**配额变更单**要写清现值与目标值、依据（即基线卡的数据）、影响面（副本数、峰值时段）、验证方式（改完读哪个文件、读到什么值算成功）与回滚命令。**上限调整属于生产变更。**

**OOM 复盘记录**要写明谁被杀、为什么是它、撞的是谁的上限，以及结论属于"容量不足 / 配额过紧 / 应用行为异常"中的哪一类。

**巡检项**要覆盖：有没有服务仍是 `infinity`、有没有服务长期贴着上限、`memory.events` 有没有新增 `oom_kill`、swap 使用是否在增长，以及有没有容器的 `/dev/shm` 接近上限。

## 7. 行业常见做法

不同组织的规范差别很大，但方向一致。

- **默认有界。** 新服务上线就带内存上限，而不是等出事再补。
- **按观测调参。** 上限由峰值与安全系数决定，并随负载变化定期复核。
- **OOM 需要复盘。** OOM 往往意味着配额与真实需求脱节，或者应用存在异常增长。
- **区分可回收与不可回收。** 页缓存多不等于内存不足，因此要盯的是不可回收部分与压力指标。

这些方向的原始材料在 Google SRE 系列（容量规划与错误预算部分）、Kubernetes 官方文档（资源请求与限制、驱逐与 OOM 行为）以及内核 cgroup v2 文档里都有，可以按自己的环境取舍。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 服务不设内存上限 | 单个服务即可拖垮整机，因此这是"整机 OOM"最常见的成因 |
| 只设 `memory.high` 就以为会被保护 | `high` 只做节流，因此要挡住失控必须设 `memory.max` |
| 用宿主 `free` 判断容器是否紧张 | 容器的额度与用量记在 cgroup 里 |
| 事后才去读 `memory.events` | cgroup 目录随单元结束被回收，而且默认 `OOMPolicy=stop` 还会把整个单元停掉 |
| 把 `OOMKilled` 一律当成容量不足 | 它可能是配额过紧或应用行为异常，而结论不同则修法不同 |
| 照抄邻居服务的上限 | 各服务的分配模式不同，因此峰值与增长曲线都不同 |
| 批量给所有服务加上限 | 这等于同时引入一批未知风险，出了问题无法归因 |
| 用调 `oom_score_adj` 代替隔离 | 那只是改变内核挑中谁的概率，而不是划定边界 |

**第一反应不要做什么**：不要用宿主 `free` 判断容器是否紧张；不要在事后才去读 `memory.events`；不要为了"节省资源"把上限一次性压到峰值以下。

## 要点自测

**问：`memory.high` 与 `memory.max` 撞上之后，命运有什么不同？**
答：`high` 只做节流（回收与限速），进程继续运行；`max` 是硬上限，撞上会触发该 cgroup 的 OOM，因此会有进程被杀。给延迟敏感服务先上 `high` 更安全，但它拦不住真正失控的服务。

**问：给一个服务定 `MemoryMax=` 的依据是什么？**
答：依据是 `memory.peak` 与历史曲线给出的真实峰值，加上安全系数；上线后再按新峰值复核。不能用"邻居是多少"或"看着差不多"来定。

**问：为什么复盘时常常读不到 `memory.events`？**
答：因为 cgroup 目录随单元结束被回收，而 systemd 服务默认 `OOMPolicy=stop`，一次 OOM 会把整个单元停掉。要在存活期间采集，或把 `OOMPolicy` 设为 `continue`。

**问：容器里"没跑什么"却接近内存上限，常见原因有哪些？**
答：常见原因是页缓存计入容器（`memory.stat` 的 `file`）、页表与内核栈开销、`/dev/shm` 的使用，以及容器内多进程共享的缓存。要按 `memory.stat` 拆分后再判断。

**问：巡检发现 40 个服务没有上限，怎么排优先级？**
答：按"峰值内存乘以影响面"排序，先做核心链路与内存大户；每个服务先补一次只读基线，再分批改，每批留观察窗口与变更记录。

**问：为什么说"内存上限是可用性手段"？**
答：因为它的作用是把故障域限制在一个服务内，避免单个服务耗尽整机内存导致全局不可用，这就是它与"扩容"互补而非互斥的原因。
