# cgroup 内存治理与容器 OOM

## 1. 为什么每个服务都要有上限

没有上限的服务可以吃掉整机内存，把故障从"一个服务变慢"放大成"整机不可用"。给它配上内存上限（再配合副本数与容量规划）能把故障限制在一个服务内——**限制线首先是可用性手段，其次才是资源手段**。

上限可以从四层写入，四层的**载体不同**，查文档和改配置的地方也不同：

| 层 | 载体 | 撞上之后 |
| --- | --- | --- |
| 进程自身 | **资源限制**：`RLIMIT_AS`、`RLIMIT_DATA`（`setrlimit(2)` 或 shell 的 `ulimit`） | 申请失败（`ENOMEM`），进程可能直接报错退出 |
| 服务 unit | **systemd 属性**：unit 文件里的 `MemoryHigh=`/`MemoryMax=` | 软线节流；硬线触发该 cgroup 内 OOM |
| cgroup | **内核接口文件**：`memory.high`/`memory.max` | 同上（systemd 这两个属性就是它们的封装） |
| 整机 | **内核参数**：物理内存 + swap 与水位（`sysctl`） | 整机 OOM，内核从全局挑进程 |

出问题时先确定是哪一层：进程自己报错退出、被 cgroup 杀、还是整机水位被撞穿——三种结论对应三种完全不同的修法。

## 2. cgroup v2 的接口怎么用于治理决策

字段本身的读写与单位在实操篇 2.5；这里讲**怎么用它们做决定**。

| 文件 | 治理时怎么用 |
| --- | --- |
| `memory.current` | 当前用量。长期贴着上限 = 上限定得过紧或应用确实在涨 |
| `memory.peak` | 历史峰值。**定上限的主要依据**：上限应高于正常峰值并留出余量 |
| `memory.max` | 硬上限。撞上就 OOM；`max` 表示无上限（很多服务的默认值） |
| `memory.high` | 软上限。超出后只节流（回收 + 限速），不杀进程——适合"先踩刹车"的场景 |
| `memory.low` | 保护：回收时尽量不动这里的页。给关键服务用 |
| `memory.swap.max` | 该 cgroup 可用 swap；设 0 表示这类服务禁用换页（代价见判例 7） |
| `memory.stat` | 构成明细，**决定处置方向**：`anon` 高 → 应用真的在用；`file` 高 → 页缓存计入；`slab` 高 → 内核对象 |
| `memory.events` | 事件计数。`oom_kill` 非 0 = 确有进程被杀；`max` 非 0 = 撞过上限（可能只被节流） |

三条使用要点：

1. **所有计数都是累积值**，"这次事件有没有发生"要用两次读数的**差值**判断；
2. **上限不是拍出来的**：用 `memory.peak` 与历史曲线说话，并写清安全系数；
3. **账本有时效**：cgroup 目录会随单元结束被回收，`memory.events` 这类证据只在存活期间存在——复盘要趁现场还在。

`memory.high` 与 `memory.max` 的区别值得单独记住：前者是"刹车"（回收、限速，进程继续跑），后者是"墙"（撞上就杀）。**给延迟敏感的服务先上 `high` 通常比直接上 `max` 更安全**，但如果它真的失控，`high` 拦不住。

## 3. systemd 侧的映射与默认行为

`MemoryHigh=`/`MemoryMax=`/`MemorySwapMax=` 分别对应 `memory.high`/`memory.max`/`memory.swap.max`；`MemoryAccounting=` 打开记账（服务默认开启）。

**必须知道的默认行为**：`OOMPolicy=stop` 是服务单元的默认值——该单元内有进程被 OOM 杀掉时，systemd 会把**整个单元停掉**，同时 cgroup 与账本一起消失。要在 OOM 之后复盘现场，就得显式设成 `OOMPolicy=continue`（该属性要求 systemd ≥243），或者提前把 cgroup 文件采下来。

`systemd-oomd` 是另一套机制：用户态的 OOM 守护进程，基于 cgroup v2 与 PSI 在"压力很大但还没 OOM"时提前动手，配置在 `oomd.conf`。它的动作与内核 OOM 在日志里长得不一样，排查时要先确认是哪一个动的手。

## 4. 容器里的六个坑

1. **容器里读 `/proc/meminfo` 看到的是宿主**。容器额度与用量在 cgroup 文件里（实操篇 2.5）。
   判断：容器内 `free` 的 `MemTotal` 与宿主一致，而 `memory.current` 与它无关。
2. **页缓存计入容器**。容器读写文件产生的缓存算在它的内存里（可回收，但会推高 `memory.current`）。
   判断：`memory.stat` 里 `file` 占大头；处置是看访问模式，不是简单加额度。
3. **`/dev/shm` 默认很小**（很多环境是 64 MiB）。共享内存类应用会在这里失败，报错是 `ENOSPC`。
   判断：容器内 `df -h /dev/shm`；处置是调大或改用文件/流式处理，并评估内存占用。
4. **页表与内核栈同样计入**。大内存、多线程进程的页表开销会占掉一部分额度。
   判断：`memory.stat` 的 `slab` 与 `kernel_stack` 相关项；处置是减少映射数量或线程数。
5. **`OOMKilled` 只是一个标签**，要区分撞的是 `memory.max` 还是整机水位：前者是配额问题，后者是容量或邻居问题。
6. **容器看到的 CPU 数、NUMA 节点数可能与宿主不同**（受 `cpuset` 约束）。按容器内视角推算容量会失真，容量规划要回到宿主视角。

## 5. 治理场景与产出

下面四个场景是运维侧真正会遇到的治理动作。每个都给出**要做出的产出**——限制线治理的验收标准是"交出了东西"，不是"看过文档"。

### 场景一：给一个即将上线的服务定内存上限

**背景**：新服务上线前压测显示稳态 350 MiB、峰值 780 MiB，计划 3 个副本；团队想知道 `MemoryMax=` 该写多少。

**做法**：以上限高于峰值并留出安全系数为原则给初值（例如 1 GiB）；上线后用 `memory.peak` 复核，按真实峰值重新校准。**不要照抄邻居服务**——它们的分配模式不同。

**产出**：一条带依据的记录：服务名、cgroup 路径、初值与其依据（压测峰值 × 系数）、复核时间与复核方法、回滚方式。

### 场景二：上限调小之后，服务开始被 OOMKilled

**背景**：为"节省资源"，某服务上限从 2 GiB 调到 512 MiB；当晚它被 OOMKilled 三次，`memory.peak` 每次都贴住 512 MiB。

**做法**：先确证撞的是它（内核日志的 `oom_memcg=`、`memory.events` 的 `oom_kill` 差值），再看 `memory.stat` 的构成与当时的业务量。结论只有三种，必须落到其中一种：

- **配额过紧** → 回滚或调整上限（依据是峰值与业务增长趋势）；
- **应用峰值超出预期** → 优化或扩容，配额只是暴露了问题；
- **页缓存计入吃额度** → 看访问模式，可能要给缓存留余量而不是加限制。

**产出**：一份 OOM 复盘记录，回答三个问题——谁被杀（进程、cgroup、当时用量）、为什么是它（权重与选择依据）、撞的是谁的上限（cgroup 还是整机）；并附回滚动作与后续观察窗口。

### 场景三：同一节点上多个服务互相拖累

**背景**：节点上 A 服务突发把内存吃紧，导致 B 服务开始换页、延迟抖动。两者都在同一台机器上，暂时无法拆机。

**做法**：给 A 设 `memory.max` 把它关在自己那格；给 B 设 `memory.low` 让回收时尽量不动它；如果 A 是多进程组，考虑 `memory.oom.group`（设为 1 时 OOM 终结整个 cgroup 而不是单个进程）。**优先用 cgroup 做隔离，而不是调 `oom_score_adj` 去"赌"内核挑谁**——后者是概率，前者是边界。

**产出**：隔离方案与验证方式（各自的上限、保护设置、以及"压力下 B 是否还在换页"的复查步骤）。

### 场景四：巡检发现一批服务没有上限

**背景**：巡检 40 个服务，`MemoryMax` 显示 `infinity`；不可能一次全改。

**做法**：按"峰值内存 × 影响面"排序推进，先做核心链路与内存大户；每个服务先补一次只读基线（峰值、构成、压力），再分批改上限；每批改完留观察窗口。**不要一次性批量改**——40 个服务的上限同时生效，等于把 40 个未知风险同时引入。

**产出**：一张排期表（服务、当前峰值、目标上限、影响面、批次、验证方式）与每批的变更记录。

## 6. 治理产物四件套

**配额基线卡**：服务名与 cgroup 路径、`memory.max` 与 `memory.peak`、稳态与峰值用量、压力指标基线、历史 `oom_kill` 次数、是否使用 swap。用途：回答"这个上限该不该调"。

**配额变更单**：现值 → 目标值、依据（基线卡数据）、影响面（副本数、峰值时段）、验证方式（改完读哪个文件、读到什么值算成功）、回滚命令。**上限调整属于生产变更。**

**OOM 复盘记录**：谁被杀、为什么是它、撞的是谁的上限，以及结论属于"容量不足 / 配额过紧 / 应用行为异常"中的哪一类。

**巡检项**：有没有服务仍是 `infinity`、有没有服务长期贴着上限、`memory.events` 有没有新增 `oom_kill`、swap 使用是否在增长、有没有容器的 `/dev/shm` 接近上限。

## 7. 行业常见做法

不同组织的规范差别很大，但方向一致：

- **默认有界**：新服务上线就带内存上限，而不是等出事再补；
- **按观测调参**：上限由峰值与安全系数决定，并随负载变化定期复核；
- **OOM 需要复盘**：OOM 往往意味着配额与真实需求脱节，或应用存在异常增长；
- **区分可回收与不可回收**：页缓存多不等于内存不足，要盯的是不可回收部分与压力指标。

这些方向的原始材料在 Google SRE 系列（容量规划与错误预算部分）、Kubernetes 官方文档（资源请求与限制、驱逐与 OOM 行为）以及内核 cgroup v2 文档里都有，可按自己的环境取舍。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 服务不设内存上限 | 单个服务即可拖垮整机；这是"整机 OOM"最常见的成因 |
| 只设 `memory.high` 就以为会被保护 | `high` 只节流；要挡住失控必须设 `memory.max` |
| 用宿主 `free` 判断容器是否紧张 | 容器的账在 cgroup 里 |
| 事后才去读 `memory.events` | cgroup 目录随单元结束被回收；默认 `OOMPolicy=stop` 还会把整个单元停掉 |
| 把 `OOMKilled` 一律当成容量不足 | 可能是配额过紧或应用行为异常，结论不同修法不同 |
| 照抄邻居服务的上限 | 分配模式不同，峰值与增长曲线都不同 |
| 批量给所有服务加上限 | 等于同时引入一批未知风险，出了问题无法归因 |
| 用调 `oom_score_adj` 代替隔离 | 那是在赌内核挑谁，不是划边界 |

## 要点自测

**问：`memory.high` 与 `memory.max` 撞上之后，命运有什么不同？**
答：`high` 只节流（回收与限速），进程继续跑；`max` 是硬上限，撞上触发该 cgroup 的 OOM，会有进程被杀。给延迟敏感服务先上 `high` 更安全，但它拦不住真正失控的服务。

**问：给一个服务定 `MemoryMax=` 的依据是什么？**
答：`memory.peak` 与历史曲线给出的真实峰值，加上安全系数；上线后按新峰值复核。不能用"邻居是多少"或"看着差不多"来定。

**问：为什么复盘时常常读不到 `memory.events`？**
答：cgroup 目录随单元结束被回收，而 systemd 服务默认 `OOMPolicy=stop`——一次 OOM 会把整个单元停掉。要在存活期间采集，或把 `OOMPolicy` 设为 `continue`。

**问：容器里"没跑什么"却接近内存上限，常见原因有哪些？**
答：页缓存计入容器（`memory.stat` 的 `file`）、页表与内核栈开销、`/dev/shm` 的使用、以及容器内多进程共享的缓存。要按 `memory.stat` 拆分后再判断。

**问：巡检发现 40 个服务没有上限，怎么排优先级？**
答：按"峰值内存 × 影响面"排序，先做核心链路与内存大户；每个服务先补一次只读基线，再分批改，每批留观察窗口与变更记录。

**问：为什么说"内存上限是可用性手段"？**
答：它的作用是把故障域限制在一个服务内，避免单个服务耗尽整机内存导致全局不可用；这是它与"扩容"互补而非互斥的原因。
