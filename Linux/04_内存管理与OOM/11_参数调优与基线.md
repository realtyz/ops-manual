## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **内存调参几乎都是交换**：早回收换的是可用内存变少，晚回收换的是停顿尖刺；关 swap 换的是 OOM 风险。**没有免费的改动。**
> - **默认值不是万能值**：`tuned`、`sysctl.d`、发行版内核都会改默认值；**一律以本机 `sysctl` 为准**。
> - **`sysctl -w` 是运行时修改**，重启即失效；要持久化必须写进 `/etc/sysctl.d/`。
> - **没有基线就不能评估改动**：动参数前先采 `available`、PSI、`si/so`、`Dirty`、业务延迟分位数。
> - **回滚命令要写在变更单上**，而不是等到出问题再想。

## 1. 为什么内存调参是「交换」

内存参数基本都在三类目标之间取舍：

| 目标 | 通常做法 | 代价 |
| --- | --- | --- |
| 降低延迟尖刺 | 提前回收（调大 `min_free_kbytes`/`watermark_scale_factor`）、禁 swap | 可用内存变少、OOM 风险上升 |
| 提高吞吐 | 让缓存与脏页多留一会儿（调低 `vfs_cache_pressure`、调大 `dirty_*`） | 内存占用更高、回写更集中 |
| 提高确定性 | 严格承诺（`overcommit_memory=2`）、硬上限（`memory.max`） | 合法申请可能被拒、服务可能被杀 |

所以第一句话永远是：**这次要优化的是哪一个指标**。不做这个选择，改动就没有验收标准。

## 2. 基线卡：一次采集，长期复用（T1）

```bash
date; hostname; uname -r; cat /etc/os-release | head -3
                                     # 验证：时间、主机、内核、发行版（写进基线的第一行）
free -h; grep -E '^(MemTotal|MemAvailable|Cached|Shmem|Slab|SReclaimable|SUnreclaim|Dirty|Writeback):' /proc/meminfo
                                     # 验证：整机内存大账
cat /proc/pressure/memory            # 验证：PSI 基线（some/full 的 avg10/avg60/avg300）
vmstat 1 5                           # 验证：si/so、wa、r/b 基线
swapon --show; sysctl vm.swappiness  # 验证：swap 配置与倾向权重
sysctl vm.min_free_kbytes vm.watermark_scale_factor vm.dirty_ratio vm.dirty_background_ratio
                                     # 验证：水位与回写参数
sysctl vm.overcommit_memory vm.overcommit_ratio vm.panic_on_oom
                                     # 验证：超额承诺与 panic 策略
cat /sys/kernel/mm/transparent_hugepage/enabled
                                     # 验证：THP 策略
stat -fc %T /sys/fs/cgroup           # 验证：cgroup 版本
ps -eo pid,comm,rss --sort=-rss | head -10
                                     # 验证：内存 Top 10（建立「正常时谁在前面」的印象）
slabtop -o -s c | head -10           # 验证：slab 排行
```

**基线卡最少记录**：版本、`MemTotal`、`MemAvailable`、PSI `some`、swap 配置、上面列出的内核参数、THP 策略、cgroup 版本、内存 Top 5。业务侧还要补：关键服务的 `RSS`/`PSS`、延迟分位数、高峰期 `available`。**第 6 节的故障定位表里每一类现象，都要有对应的基线项才能判断「是否异常」。**

## 3. 参数取舍表

> [!warning] 下表是「调大/调小」的普遍方向，不是推荐值
> 具体数值必须在实验机上用业务负载验证；同一台机器上的改动要单变量进行。

| 参数 | 调大的收益 | 调大的代价 | 验收指标 |
| --- | --- | --- | --- |
| `vm.swappiness` | 内存紧张时更早换出匿名页，给缓存腾空间 | 业务延迟抖动增加 | `si/so`、PSI、业务尾延迟 |
| `vm.min_free_kbytes` | 更早唤醒 `kswapd`，减少 direct reclaim 尖刺 | **可用内存变少，极端情况下更快 OOM** | `allocstall`、`pgscan_direct`、业务延迟 |
| `vm.watermark_scale_factor` | 拉大水位间距，回收更积极 | 常驻保留内存变多 | `kswapd_low_wmark_hit_quickly`、`allocstall` |
| `vm.dirty_background_ratio`/`dirty_background_bytes` | 允许更多脏页积压，减少后台回写频率（对批量写更友好） | 脏页更接近硬阈值，回写更集中、写进程更晚被提醒 | `Dirty` 曲线、`await` |
| `vm.dirty_ratio`/`dirty_bytes` | 允许积压更多脏页（吞吐更好） | 撞上限时的停顿更集中、更严重 | `await`、写进程 `D` 状态时长 |
| `vm.vfs_cache_pressure` | 更积极回收 dentry/inode 缓存 | 文件访问变慢 | `SReclaimable`、文件操作延迟 |
| THP `always` → `madvise`/`never` | 减少整理停顿与内存放大 | TLB 效率下降，部分吞吐型负载变慢 | `compact_stall`、业务吞吐与尾延迟 |
| `vm.overcommit_memory=2` | 承诺严格，避免「申请成功但用不了」 | 合法大申请被拒、管理操作可能失败 | `Committed_AS`/`CommitLimit` 余量、启动成功率 |
| `vm.panic_on_oom=2` | OOM 必留现场（配合 kdump） | **整机重启**，从杀一个进程升级为全停 | 演练验证 kdump 可用性 |

两个补充说明：

- **`dirty_ratio` 与 `dirty_bytes` 互斥**：设置绝对值会把对应的比例归零；大内存机器常用绝对值，避免比例换算出的阈值过大。
- **`min_free_kbytes` 有上下限**：内核按内存规模算出默认值并夹在区间内；文档明确警告低于 1024 KiB 会有风险。

## 4. 变更纪律：五步走

1. **打快照**：虚拟机/云主机先做快照，物理机先确认可回滚窗口；
2. **记录原值**：把 `sysctl` 输出原样粘进变更单（不要只记「默认」两个字）；
3. **单变量修改**：一次只改一个参数，避免无法归因；
4. **同一套指标复测**：用基线卡里的同一组命令与同一个业务指标对比，观察窗口至少覆盖一个业务周期；
5. **写好回滚**：把恢复命令与恢复后的验收标准写在同一处。

```bash
sysctl vm.dirty_bytes vm.dirty_background_bytes    # 验证：改动前的原值（示例）
sysctl -w vm.dirty_background_bytes=8388608        # 运行时修改（重启即失效）
sysctl -w vm.dirty_bytes=16777216
```

持久化要写到 `/etc/sysctl.d/` 下的配置文件里，内容形如 `vm.dirty_bytes = 16777216` 这样的键值对；写完用 `sysctl --system` 加载，并检查与 `tuned` 的 profile 是否冲突（RHEL 系用 `tuned-adm active` 查看当前 profile，必要时把参数加进自定义 profile）。

## 6. 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 用「网上抄来的默认值」对比本机 | `tuned` 与发行版内核会改默认值；一律以本机 `sysctl` 为准 |
| 只 `sysctl -w` 不写持久化配置 | 重启后回到原值，问题会「复发」或「自愈」，无法归因 |
| 一次改多个参数 | 无法判断哪个改动起作用，也无法安全回滚 |
| 没有基线就开始调参 | 改完无法评估，只能凭感觉 |
| 把 `min_free_kbytes` 调得很大以求稳 | 可用内存变少，可能更快触发 OOM |
| 在物理机上直接试验破坏性参数 | 没有快照就无法回滚；破坏性演练只在可快照实验机 |
| 忽略 `tuned` 会覆盖 `sysctl` | 重启或 profile 切换后参数被改回去 |
| 拿平均值评估延迟类改动 | 内存改动大多影响尾延迟，必须看分位数 |

## 决策练习

> [!question]- 场景：某服务在高峰期出现偶发秒级卡顿，`allocstall` 与 `pgscan_direct` 有明显增长；同事提议把 `vm.min_free_kbytes` 从默认值直接调到 4 GiB。你怎么处理？
> A. 按建议执行，越大越早回收，卡顿一定减少
> B. 先在实验机上按小步递增验证：记录 `MemAvailable`、`allocstall`/`pgscan_direct`、业务 p99 与 OOM 事件；确认收益大于「可用内存变少」的代价后再上生产，并写明回滚值
> C. 直接关闭 swap，减少换页造成的停顿
>
> **答案：B。**
> A 的问题是把「提前回收」当成无代价：保留内存变多会减少可用内存，极端情况下更快 OOM；4 GiB 对这台机器可能过大。
> C 会把换页抖动换成 OOM，方向相反。
> B 是正解：**内存参数改动必须有对照与回滚**，而且优先小步试。

## 要点自测

> [!question]- 一份内存基线卡至少要包含哪些项？
> - 版本（发行版/内核）、`MemTotal`/`MemAvailable`、PSI `some`、swap 配置、上面列出的内核参数、THP 策略、cgroup 版本、内存 Top 5 与业务侧延迟分位数。
> - 判断「异常」的前提是有「正常」的记录。
> - **第一反应不要是什么**：不要在没有基线的情况下改参数或下结论。

> [!question]- 「内存调参没有免费的改动」怎么理解？举两个例子。
> - 提前回收（调大水位）减少停顿尖刺，但可用内存变少、可能更快 OOM。
> - 关 swap 减少换页抖动，但匿名页无处可去，压力直接变成 OOM。
> - **第一反应不要是什么**：不要只写收益不写代价的变更方案。

> [!question]- `sysctl -w` 与持久化配置有什么区别？
> - `sysctl -w` 只改运行时内存中的值，重启即失效。
> - 持久化要写 `/etc/sysctl.d/*.conf`，并检查 `tuned` 等工具是否会覆盖。
> - **第一反应不要是什么**：不要把「改完生效了」当成「配置已持久化」。

> [!question]- 一次参数变更记录里，哪两项最容易漏？
> - **原值**（没有原值就无法回滚）与**回滚命令**（出事时没有时间现查）。
> - 还有验收标准与观察窗口；缺了它们，改动无法评估。
> - **第一反应不要是什么**：不要在事故现场才去找「刚才改了什么」。
