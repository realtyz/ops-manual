## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **缺页把承诺变成占用**：minor fault 便宜（只需建映射或复制），major fault 贵（要回磁盘或 swap 取页）。
> - **`RSS` 对共享页重复计数**：同一个共享库被 20 个进程用，20 份 `RSS` 都算它；跨进程比较必须用 `PSS`。
> - **`USS` 回答「杀掉它能省多少」**：只看私有页（`Private_Clean + Private_Dirty`），是泄漏排查与容量规划最相关的口径。
> - **页表也是内存**：映射越多页表越大，大内存与多线程进程的 `PageTables` 可以到 GiB 级。
> - **大页与 NUMA（Non-Uniform Memory Access，非统一内存访问）都是「用规划换效率」**：大页换 TLB 效率（代价是碎片与停顿），NUMA 就近访问换延迟（代价是绑错节点更慢）。

## 1. 从缺页到物理页

第一次写一个已承诺但未落地的页时，内核按下面的路径处理：

1. **查页表**：发现没有有效映射，触发缺页；
2. **判断类型**：
   - 页已经在内存里（Page Cache 命中、COW 共享页、零页）→ **minor fault**，只需建立映射或复制；
   - 页不在内存里（文件页被回收、匿名页被换出）→ **major fault**，需要 IO；
3. **分配物理页并填充**：匿名页写零或复制 COW 内容，文件页从缓存或磁盘读取；
4. **更新页表**：此后访问就走正常路径（还有 TLB 缓存）。

```bash
ps -eo pid,comm,min_flt,maj_flt --sort=-maj_flt | head -10
                                     # 验证：哪些进程的 major fault 最多（压力信号）
cat /proc/vmstat | grep -E '^(pgfault|pgmajfault)'
                                     # 验证：整机缺页计数（看差值，不看绝对值）
cat /proc/<pid>/stat | awk '{print "min_flt="$10, "maj_flt="$12}'
                                     # 验证：单进程的两种缺页计数（字段号随内核版本变化，先用 man proc 核对）
```

> [!important] major fault 是「工作集被挤出内存」的直接证据
> 它和 PSI、`si/so` 一起看（子笔记 07）。如果一台机器 `available` 还很多但 `pgmajfault` 持续上涨，说明某个进程的工作集被回收过，性能已经开始受损。

## 2. 页表的成本

每个映射都要占页表项。页表开销在整机看是 `PageTables`，在单进程看是 `VmPTE`/`VmPMD`：

| 观察点 | 含义 |
| --- | --- |
| `/proc/meminfo` 的 `PageTables` | 全系统页表占用（可达 GiB 级） |
| `/proc/<pid>/status` 的 `VmPTE`/`VmPMD` | 该进程页表项占用的内存 |
| `/proc/meminfo` 的 `KernelStack` | 每个任务的内核栈（常见 16 KiB/任务，线程多时总量可观） |
| `/proc/meminfo` 的 `VmallocUsed` | 内核虚拟地址空间使用量（驱动、模块相关） |
| `vm.max_map_count` | 单进程允许的映射段数上限（常见默认 65530） |

```bash
cat /proc/meminfo | grep -E '^(PageTables|KernelStack|VmallocUsed):'
cat /proc/<pid>/status | grep -E 'VmPTE|VmPMD|VmSize'
sysctl vm.max_map_count
```

**为什么这很重要**：一个进程「看起来只用了 2 GiB」，但页表与内核栈可能再加几百 MiB；容器里这些开销同样计入该 cgroup，会直接吃掉 `memory.max` 的额度（子笔记 10）。

## 3. 四个口径：VSZ / RSS / PSS / USS

「这个进程占多少内存」没有唯一答案，只有「你问的是哪个口径」：

| 口径 | 含义 | 共享页怎么算 | 适合回答 |
| --- | --- | --- | --- |
| `VSZ`/`VmSize` | 虚拟地址空间总量 | 全算 | 「承诺了多少」，**不能判断占用** |
| `RSS`/`VmRSS` | 常驻物理页 | 每个使用者各算一份 | 快速定位「谁看起来最大」 |
| `PSS`（Proportional Set Size） | 共享页按使用者数量均摊后的占用 | 按使用者数分摊 | 「这台机器上真正被谁用了」 |
| `USS`（Unique Set Size） | 私有占用（`Private_Clean + Private_Dirty`） | 完全不计共享页 | 「杀掉它能省多少」「泄漏排查」 |

```bash
ps -eo pid,comm,vsz,rss --sort=-rss | head -20
                                     # 验证：按 RSS 排序的进程表
cat /proc/<pid>/status | grep -E 'VmSize|VmRSS|VmSwap|RssAnon|RssFile|RssShmem'
                                     # 验证：单个进程的内存构成（RSS = Anon + File + Shmem）
cat /proc/<pid>/smaps_rollup | grep -E 'Pss|Private_Clean|Private_Dirty|Anonymous|Swap'
                                     # 验证：PSS 与私有占用（USS = 后两者之和）
pmap -X <pid> | tail -5              # 验证：带 Pss 列的映射明细（不同版本列名略有差异）
```

三个实践规则：

1. **容量报表用 `PSS` 或 `USS`**，`RSS` 只用来排序找嫌疑；
2. **判断「杀它能省多少」用 `USS`**：共享库、共享内存杀了也不会省；
3. **不要把所有进程的 `RSS` 相加**，和会大于物理内存。

## 4. 内存构成：涨的是哪一类

`status` 里的 `RssAnon`/`RssFile`/`RssShmem` 是判断「涨在哪」的第一把刀，`VmSwap` 说明有多少被换出去了：

| 字段 | 含义 | 典型原因 |
| --- | --- | --- |
| `RssAnon` | 匿名页（堆、栈、`malloc`） | 业务数据增长、缓存池、泄漏 |
| `RssFile` | 映射文件的页（含共享库、文件映射） | 读了文件、映射了大文件 |
| `RssShmem` | 共享内存与 tmpfs | `/dev/shm`、共享内存段 |
| `VmSwap` | 该进程被换出的匿名页 | 内存压力（子笔记 07） |

```bash
for i in $(seq 1 6); do date '+%F %T'; grep -E 'VmRSS|RssAnon|RssFile|RssShmem|VmSwap' /proc/<pid>/status; sleep 600; done
                                     # 验证：10 分钟粒度取 6 次，看哪个口径在涨（泄漏判断见子笔记 12）
```

## 5. 大页：THP 与显式 HugePages

| 方案 | 怎么开 | 收益 | 代价 | 判断方式 |
| --- | --- | --- | --- | --- |
| 显式 HugePages | `vm.nr_hugepages`、`hugetlbfs` | 延迟稳定、TLB 效率高 | 预留后不参与常规分配；要提前规划 | `HugePages_Total`/`HugePages_Free`、`Hugepagesize` |
| 透明大页 THP | `enabled=always` 或按 `madvise` 提示 | 无需改应用；吞吐型负载有收益 | 内存放大、碎片、整理停顿 | `AnonHugePages`、`compact_stall` |

```bash
cat /sys/kernel/mm/transparent_hugepage/enabled      # 验证：always / madvise / never
cat /sys/kernel/mm/transparent_hugepage/defrag       # 验证：整理策略（取值随内核版本变化）
grep -E '^(AnonHugePages|HugePages_Total|HugePages_Free|Hugepagesize):' /proc/meminfo
cat /proc/vmstat | grep -E '^(compact_stall|compact_fail|thp_fault_alloc|thp_collapse_alloc)'
                                     # 验证：THP 相关计数（停顿与分配情况）
```

**什么时候要动它**：延迟敏感服务在 `enabled=always` + 积极整理下出现周期性停顿（`compact_stall` 上升），或在碎片严重时出现高阶分配失败。改法是切到 `madvise`（由应用决定）或 `never`，并且**必须做前后性能对比**（子笔记 11）。

## 6. NUMA：跨节点访问的代价【进阶】

多路服务器上，CPU 访问本地节点内存与访问另一个 socket 挂的内存，延迟和带宽差别很大（典型 x86 平台远端延迟是本地的一倍以上，具体以本机实测为准）。这带来两类典型问题：「内存总量没满，但某个节点先满」和「资源都空闲却性能不达标」。

```bash
numactl --hardware                   # 验证：节点数、每节点 CPU 与内存、节点间距离矩阵
numastat -m                          # 验证：各节点的内存使用与命中情况
numastat -p <pid>                    # 验证：单个进程的跨节点分布
grep -H . /sys/devices/system/node/node*/distance     # 验证：节点距离（10 为本地）
sysctl kernel.numa_balancing         # 验证：自动 NUMA 平衡是否开启
```

几个实操结论：

- **`taskset` 只绑 CPU，不绑内存**；要绑内存得用 `numactl --membind=<node>` 或 `--interleave=all`。
- `numastat` 里 `numa_miss`/`numa_foreign` 高、`local_node` 占比低，说明有明显跨节点访问。
- **自动 NUMA 平衡会在检测到跨节点访问时迁移页**：多数场景有收益，延迟敏感服务上可能引入抖动，动它之前先有基线。
- **容器里 NUMA 由 `cpuset.mems` 约束**（编排层还有拓扑管理机制）；「容器里看到的 NUMA 与物理机不同」是正常现象。

## 7. 生产动作：一次占用报表（实验 7）

> [!example]- 实验 7：`RSS` 会重复计数，`PSS`/`USS` 才说真话
> **怎么做**：造一个 512 MiB 文件，让两个进程同时映射并读它，对比 `RSS` 与 `PSS`。
> ```bash
> dd if=/dev/zero of=/tmp/lab-map bs=1M count=512     # 造一个 512MiB 文件
> cat > /tmp/lab-mmap.py <<'EOF'
> import mmap, os, time
> f = open('/tmp/lab-map', 'rb')
> m = mmap.mmap(f.fileno(), 0, access=mmap.ACCESS_READ)
> total = 0
> for i in range(0, len(m), 4096):
>     total += m[i]
> print('touched', os.getpid(), flush=True)
> time.sleep(300)
> EOF
> python3 /tmp/lab-mmap.py & P1=$!
> python3 /tmp/lab-mmap.py & P2=$!
> ps -eo pid,comm,rss --sort=-rss | head -5           # 验证：两个进程的 RSS 各自都很大
> for p in "$P1" "$P2"; do grep -E 'Pss|Private_Dirty' /proc/$p/smaps_rollup; done
>                                                      # 验证：PSS 把共享页均摊，明显小于 RSS
> kill "$P1" "$P2"; rm -f /tmp/lab-map /tmp/lab-mmap.py
> ```
> **预期**：两个进程的 `RSS` 相加约等于 1 GiB，但物理内存只被这 512 MiB 占了一份；`PSS` 会把它均摊。**结论：跨进程比较占用要用 `PSS`/`USS`，「`RSS` 之和」会骗人。**
> **风险**：低。会占用约 512 MiB 页缓存，小内存机器请把文件调小。
> **耗时**：约 15 分钟。
> **怎么退回去**：命令末尾已清理进程与文件。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 用 `RSS` 排序后就下「谁最占内存」的结论 | `RSS` 对共享页重复计数；跨进程结论要用 `PSS`/`USS` |
| 把所有进程 `RSS` 相加与物理内存对账 | 和一定大于物理内存，账永远对不上（子笔记 09） |
| 「`VmRSS` 没涨，所以没用内存」 | 可能是映射了文件（`RssFile`）或共享内存（`RssShmem`）；看构成 |
| 忽略页表与内核栈开销 | 大内存、多线程进程的 `PageTables`/`KernelStack` 可以很可观，容器里同样计入 |
| 用 `minor fault` 多判断内存紧张 | minor fault 多为分配/映射行为；压力信号看 major fault |
| 把 THP 的 `always` 当成「一定更好」 | 可能带来内存放大与整理停顿；改之前要有性能对比 |
| 用 `taskset` 来控制内存位置 | 它只绑 CPU；内存位置要用 `numactl`（`--membind`/`--interleave`） |
| 认为容器里 NUMA 视图应与物理机一致 | 容器受 `cpuset.mems` 约束，节点数与分布都可能不同 |

## 决策练习

> [!question]- 场景：一台 32 GiB 的机器上，某进程 `RSS` 12 GiB，但机器 `available` 还有 15 GiB；同事据此说「这个进程会骗统计，不用管」。你怎么判断？
> A. 同意不用管，`available` 还有 15 GiB，说明没有压力
> B. 先看该进程的 `Pss`/`Private_Dirty` 与 `RssAnon`/`RssFile` 构成，再结合 PSI 与 major fault 判断它是不是真的占了 12 GiB、是不是在挤别人
> C. 直接给它加 `MemoryMax=` 限制到 6 GiB，防止出问题
>
> **答案：B。**
> A 漏掉了「共享页」这一层：`RSS` 12 GiB 里可能有大量共享库与文件页，实际私有占用远小于 12 GiB；但也不能因此不看压力指标。
> C 是没证据就动限制：加得太紧会把正常业务按死，`MemoryMax` 应该在报表与基线之后才配。
> B 是正解：**先分清口径（`RSS` → `PSS`/`USS` + 构成），再看压力（PSI / major fault），最后才谈限制**。

## 要点自测

> [!question]- `RSS`、`PSS`、`USS` 各回答什么问题？
> - `RSS`：谁看起来最大（含重复计数）；`PSS`：共享页均摊后谁真正用了多少；`USS`：杀掉它、释放它专属内存能省多少。
> - 命令：`ps -o rss`、`/proc/<pid>/smaps_rollup` 的 `Pss` 与 `Private_*`。
> - **第一反应不要是什么**：不要用 `RSS` 之和与物理内存对账，也不要只凭 `RSS` 决定杀进程。

> [!question]- 为什么页表、内核栈也要算进内存账？
> - 它们是真金白银的物理内存，只是不在任何进程的 `RSS` 里；整机看 `PageTables`/`KernelStack`，单进程看 `VmPTE`。
> - 容器/服务同样为它们付账，会占用 `memory.max` 的额度。
> - **第一反应不要是什么**：不要用「进程 `RSS` 加起来不大」证明内存没被用掉。

> [!question]- 什么情况下该考虑调整 THP？
> - 延迟敏感服务出现周期性停顿且 `compact_stall`/整理计数上升；或内存碎片导致高阶分配失败。
> - 常见动作是从 `always` 改为 `madvise`，但要先有性能基线，改完复测同一组指标。
> - **第一反应不要是什么**：不要在没有证据的情况下把 THP 当通用「性能开关」来回切。

> [!question]- NUMA 场景下，「绑核」和「绑内存」有什么区别？
> - 绑核：`taskset`（或 `numactl --physcpubind`）限制在哪些 CPU 上跑。
> - 绑内存：`numactl --membind=<node>`（严格）或 `--interleave=all`（跨节点交错）决定内存从哪个节点分配。
> - **第一反应不要是什么**：不要以为绑了 CPU 就绑了内存；跨节点访问的延迟问题不会因此消失。
