# 为什么要虚拟内存

## 1. 让进程直接使用物理地址，会同时碰到四个问题

假设 CPU 发出的地址就是内存条上的真实位置：进程把数据放在 `0x1000`，下一个进程也从 `0x1000` 开始放。这套最朴素的设计会立刻带来四件事。

**第一件事是进程之间互相覆盖。** 两个进程都从 `0x1000` 开始放数据，后启动的那个会直接盖掉先启动的那个；要阻止这件事，硬件必须知道「现在是谁在执行」，并在每次访存时检查这个地址是否属于它。

**第二件事是程序必须知道自己住在哪。** 如果程序被加载到 `0x8000` 而不是 `0x1000`，代码里所有写死的地址（跳转目标、全局变量、函数指针）都要改；让链接器每次都重算可行，但「加载到哪里」就不再是程序能决定的事，因此同一个二进制无法在多台机器上直接复用。

**第三件事是内存不够时无法腾挪。** 物理内存用满，而某个进程有一大块很久不用的数据；要把它挪到硬盘上腾出空间，必须先知道它在物理内存的哪个位置，再改写这个进程里所有指向它的地址，而地址散落在寄存器和栈上，所以内核无法安全地找出全部引用。

**第四件事是共享要复制。** 同一份 `libc` 被 100 个进程使用，最省内存的做法是物理内存里只留一份；但物理地址空间只有一套，因此「多进程共用同一份代码」与「每个进程独立编址」互相矛盾。

这四个问题互相牵制，单独修哪一个都不成立。虚拟内存之所以是操作系统的核心机制之一，就是因为它一次性把四个问题都解决了——代价是每次访存多了一次地址翻译。

## 2. 三种解法，以及它们各自留下的问题

**基址-界限寄存器（base and limit）** 是第一种解法：CPU 里放两个寄存器，一个存进程起始的物理地址（基址），一个存长度（界限）；程序里的地址是相对自己的偏移，CPU 每次访存时加上基址并检查是否越界。这种设计解决了隔离和重定位，但进程仍必须占据**一整段连续物理内存**，因此无法只把其中一部分挪走，共享也无从表达。

**分段（segmentation）** 是第二种解法：地址被拆成「段号 + 段内偏移」，每段各有基址与长度，因此段可以独立移动。它的灵活性大幅提高，但段是**变长的**——一段代码可能几 KiB，一段数据可能几百 MiB；由于长度可变，它必然带来外部碎片：总空闲足够，却没有一块够大的连续空间。

**分页（paging）** 是第三种解法：把地址空间和物理内存都切成**同样大的小块**，映射单位从「段」变成「页」。映射单位换成页之后，前面三个问题同时松开。

- 由于所有块一样大，碎片随之消失：任何空闲块都能用，只剩下页内的小块浪费（内部碎片）；
- 由于映射单位是页，腾挪变得可行：只需改这一页的映射，进程里的地址一个都不用动；
- 由于两个进程的页表可以指向同一个物理页框，共享变得自然。

**为什么选 4 KiB 这个粒度。** 粒度越小，页内浪费越少，但页表项越多、翻译次数越多；粒度越大，页表越省，但一个只用了几十字节的页也要占满整块物理内存。因此 4 KiB 是通用场景下的折中：x86_64 上 `getconf PAGE_SIZE` 与 `man 2 mmap` 都以它为基础，其他架构存在 16 KiB、64 KiB 等选择。后面会看到，把粒度加大到 2 MiB 是一次明确的取舍。

## 3. 虚拟地址空间

进程看到的那套地址叫**虚拟地址（virtual address）**；内存条上的真实位置叫**物理地址（physical address）**。把前者换成后者的动作叫**翻译（translation）**，由 CPU 里的 **MMU（Memory Management Unit，内存管理单元）** 在每次访存时执行。

- **页（page）** 是虚拟地址空间被切成的固定大小块；
- **页框（page frame）** 是物理内存被切成的同样大小的块；
- **页表（page table）** 是记录「哪个虚拟页对应哪个物理页框」以及权限位的数据结构，每个进程一份；
- **页表项（PTE，Page Table Entry）** 是页表里的一行：x86_64 上一条 PTE 占 8 字节，其中一部分位存物理页框号，另一些位存存在、可写、用户可访问等标志。

**页表不是平坦数组，而是多级的。** 若为一个 48 位地址空间的每个 4 KiB 页都放一条 PTE，单进程的页表约需 512 GiB，而绝大多数页根本没被使用；多级页表把「未使用的区域」变成「不存在的中间层」，地址被切成若干段，每段索引一级表，因此只有真正用到的分支才会被分配。这是虚拟地址空间能远大于物理内存的直接原因之一。

**一个进程的地址空间是若干段。** 代码段、只读数据、已初始化与未初始化数据、堆、若干 `mmap` 区域（共享库、文件映射、线程栈）、栈——`/proc/<pid>/maps` 里的每一行就是一段。这个事实带来两个直接后果：这些段的长度总和构成虚拟地址空间总量，与物理占用无关；段的数量有上限（`vm.max_map_count`），映射过多时会以 `ENOMEM` 失败。

## 4. 三类占用：地址空间、承诺额度与物理占用

讨论内存时最容易出错的不是机制，而是**把三个不同的量当成同一个**。它们回答三个不同的问题。

| 占用的类别 | 典型字段 | 它回答的问题 | 能不能超过物理内存 |
| ---- | -------------------------------- | ---------------- | ------------------- |
| 地址空间 | `VmSize`（`ps` 里的 `VSZ`） | 它回答这个进程**要**了多少虚拟地址 | 能，进程可以任意申请 |
| 承诺额度 | `/proc/meminfo` 的 `Committed_AS` | 它回答内核按策略**答应**了多少 | 默认就能超过「物理内存 + swap」 |
| 物理占用 | `VmRSS`、`AnonPages`、`PageTables` | 它回答内存条上**真的**被占了多少 | 不能，物理内存只有那么多 |

`VSZ` 很大而常驻集很小，是常态而不是异常：线程栈预留、应用按最大堆预留、大文件映射都会把地址空间这一项撑大，而它们并不落在物理内存上。值得记住的一句话是：**凡说「占了多少内存」，必须指明说的是哪一类占用。**

## 5. 翻译的代价与 TLB

翻译发生在每一次访存上，由硬件完成，内核不参与——内核只负责建立和维护页表。只要映射有效，进程读写内存时内核完全不知情。

**TLB（Translation Lookaside Buffer，翻译后备缓冲）** 是 MMU 内部缓存最近翻译结果的一小块硬件。它是必需的，因为如果每次访存都要从内存里逐级读页表，访存成本会翻几倍。TLB 的容量以「表项数」计，现代 x86_64 处理器的二级 TLB（同时覆盖 4 KiB 与 2 MiB 页）通常在**一两千项**这个量级（处理器厂商优化手册给出的值，具体随型号变化）。这个数字决定了它能覆盖多大的工作集：

- 若页大小是 4 KiB，一两千项只能覆盖**几 MiB**；
- 若页大小是 2 MiB，同样多的表项能覆盖**几 GiB**。

由此得到三条判断。

**第一，工作集小于 TLB 覆盖范围时，翻译基本免费。** 页表项本身通常也在缓存里，所以一次未命中的代价是几次缓存访问，而不是一次内存往返。

**第二，访问模式决定了能不能看见这笔开销。** 顺序、步长固定的访问会被硬件预取器识别，访存提前发起并与翻译重叠；只有随机跨页访问才会把翻译成本暴露出来。因此**任何「翻译很便宜」的结论，都要先问测量方式是不是把它藏起来了**。

**第三，未命中的比例与未命中的代价，是两件事。** 工作集远超 TLB 覆盖范围，说明几乎每次都未命中；但未命中只是叠加在访存上的一小段开销，而且现代处理器可以并行挂起多个未完成访存，把这段开销摊薄。所以大页带来的通常是**百分之几十**的改善，而不是成倍的提速——它省的是翻译次数，不是内存延迟本身。

**大页的收益与代价来自同一个粒度选择。** 显式大页（`vm.nr_hugepages`、hugetlbfs）需要预留、不参与常规分配；透明大页（THP）由内核自动合并，但按 2 MiB 粒度落地意味着**只要碰了大页里任意一个字节，整块 2 MiB 就占实**，因此对一个稀疏访问的大区域，物理占用可以比真正触碰的字节数高出几个数量级。此外大页还会带来内存碎片、后台整理（`khugepaged`）引起的偶发停顿，以及碎片严重时的分配失败。

## 6. 页表本身的开销

页表是数据结构，它也占物理内存，而且只为**已经落地的页**而增长。

一条 PTE 占 8 字节、一页是 4 KiB，所以每落地 4 KiB 就需要 `8 / 4096 ≈ 0.2%` 的额外内存用于页表。这个比例可以自己验算：落地 2 GiB 时，最底层 PTE 约占 4 MiB，再叠加中间层表的开销。由此得到三点推论。

- **决定页表大小的是「落地的页数」，不是「映射的地址范围」。** 只映射不触碰时，内核不为那段建立 PTE 页；因此一个映射了几百 GiB 但只碰了几十 MiB 的进程，页表仍然很小。
- **要得到 GiB 级的页表，需要落地几百 GiB 的内存**，或者用大量稀疏映射把中间层表撑起来。容器里页表开销计入该 cgroup，因此它会占用这个 cgroup 的内存上限。
- **`VmPTE` 不是判断大页是否生效的手段。** 大页生效时页表结构会变薄，但该字段的统计口径随内核版本变化；可靠的做法是看 `/proc/<pid>/smaps_rollup` 的 `AnonHugePages`（整机看 `/proc/meminfo` 的同名字段）。

## 7. 按需分配、零页与写时复制

**申请不等于占用。** 应用调用 `malloc`（C 库函数）成功时，内核在进程名下划出一段虚拟地址、写进映射表，并按策略在承诺额度上记一笔，**不分配物理页**——真正向内核提出申请的是库函数底层的两个系统调用 `brk` 与 `mmap`。物理页要等第一次写入、触发缺页时才给。这就是为什么「申请成功」不能当容量验收，也是为什么内存不足可能在**任何一次写入**上爆发，而不是在申请的那一刻。

**缺页分两类**，代价差一个量级：

- **minor fault（次要缺页）** 指页已经在物理内存里、只是当前进程还没建立映射：匿名页第一次写入、写时复制、文件页已在内核缓存中，都属于这一类；
- **major fault（主要缺页）** 指页不在内存里，必须从磁盘或 swap 读入，这一步要等 IO；它的代价强烈依赖存储介质，通常比 minor fault 高出一到两个数量级。

**读一个从未写过的匿名页，几乎不占内存。** 内核把一块内容全零的共享页（zero page）映射进来，只有真正写入时才分配物理页。这条机制解释了一个常见困惑：缺页次数很多，并不等于内存被占用。

**写时复制（Copy-On-Write，COW）** 是 `fork` 的实现方式：`fork` 不复制内存内容，只复制页表，并把这些页在父子两边都标成只读；谁先写，谁触发一次缺页，内核才为它复制那一页。因此 `fork` 本身很快、物理内存不会立刻翻倍，但**承诺额度 `Committed_AS` 在 `fork` 的瞬间就会增加**，物理内存要等两边真的写入时才翻倍。备份、快照、`BGSAVE` 这类「`fork` + 大量写」的场景，真实内存需求由 **`fork` 之后写入多少**决定。

## 8. 机制在本名与字段上的边界

**常驻口径会对共享页重复计量。** 共享页在每一个映射它的进程的常驻集中各算一份，因此把所有进程的常驻集相加会大于物理内存；要消除重复计数，必须改用均摊口径（`Pss`）或只看私有页（`Uss`），两者都从 `/proc/<pid>/smaps_rollup` 读。

**承诺额度允许超过物理内存。** 内核默认允许「承诺总量 > 物理内存 + swap」，因为多数程序申请后不会马上用满；这条策略由 `vm.overcommit_memory` 决定，取值为启发式（默认）、总是允许与严格三种。不同取值下「申请失败」的含义完全不同：严格模式下物理内存还有很多也可能申请失败，因为卡住申请的是承诺额度，不是物理内存。

**粒度与物理位置是另外两处边界。** 4 KiB 页换来灵活，代价是翻译次数与 TLB 压力；大页把翻译成本压下去，代价是内存放大与分配失败的可能性；多路服务器上还有内存分节点、跨节点访问更慢的问题（NUMA）。后两者都是**用规划换效率**：想让它发挥作用，必须在部署时就把内存布局规划进去，而不是等性能出问题再调。

这三处边界里的每一个量都有自己的字段名与单位。`VmRSS`、`Committed_AS` 与 `VmSize` 描述的是三类彼此独立的占用，任何一个都不描述「这台机器还够不够用」；`AnonHugePages` 描述的是匿名大页的占用，它不描述大页策略是否已对某个区域生效。

## 常见误解

| 常见说法 | 事实 |
| --- | --- |
| 「虚拟内存就是把硬盘当内存用」 | 这句话把两件事混在一起：把硬盘当内存用的是 swap，虚拟内存指的是每个进程各有一套地址、由硬件完成翻译，swap 只是匿名页腾挪的去处之一 |
| 「`VSZ` 很大说明这个进程很吃内存」 | `VSZ` 是地址空间这一类的量，它包含未落地的映射与线程栈，因此判断占用要看物理占用这一类 |
| 「`malloc` 成功就说明内存够」 | 成功只代表地址空间与承诺额度的登记成功，物理页要到第一次写入时才分配 |
| 「两个进程的虚拟地址相同，访问的就是同一块内存」 | 每个进程各有一套页表，因此同一个虚拟地址在不同进程里可以指向不同物理页框 |
| 「页表不占内存」 | 每落地的 4 KiB 需要一条 8 字节 PTE，约占 0.2%；映射多而落地少时页表并不大 |
| 「`VmPTE` 变小了就说明用上大页了」 | 该字段的口径随内核的统计方式变化，判断大页要看 `AnonHugePages` |
| 「把 THP 当性能开关来回切」 | 大页既省翻译次数，也带来内存放大、碎片与整理停顿，因此改之前要有前后对比 |
| 「缺页多说明内存紧张」 | minor fault 多为分配行为活跃，压力信号要看 major fault 与内存压力指标 |
| 「`fork` 之后内存立刻翻倍」 | 物理页由父子共享（写时复制），但承诺额度会立刻增加，物理占用要到写入之后才涨 |

## 要点自测

**问：虚拟内存一次解决了哪四件事？代价落在哪几处？**
答：它解决了进程隔离、程序不必知道自己被加载到哪、内存不足时可以腾挪单页、同一份代码可被多个进程共享这四件事。代价是每次访存要翻译（TLB 只是缓解）、页表本身占内存、建立映射时要付缺页的代价。

**问：地址空间、承诺额度与物理占用这三类量分别回答什么问题？为什么"占了多少内存"必须指明是哪一个？**
答：地址空间回答"要了多少虚拟地址"，承诺额度回答"内核答应了多少"，物理占用回答"内存条上真的占了多少"。三者可以相差几个数量级，因此混用会得出相反结论。

**问：TLB 只能覆盖几 MiB 的工作集，为什么随机访问不会慢好几倍？**
答：未命中的**比例**会很高，但单次未命中的**代价**只是几次缓存访问，而且处理器可以并行挂起多个未完成访存把这段开销摊薄。大页省的是翻译次数，不是内存延迟。

**问：为什么"缺页次数很多"不等于"内存被占了"？**
答：读一个从未写过的匿名页时，内核映射的是内容全零的共享页（零页），只有写入时才真正分配物理页。

**问：`fork` 之后物理内存会立刻翻倍吗？**
答：不会——父子共享同一批页（写时复制），只有一方写入时才复制那一页。但**承诺额度在 `fork` 的瞬间就会增加**，因此"承诺"与"物理占用"在这里又一次分道扬镳。

**第一反应不要做什么**：不要把虚拟内存等同于 swap；不要用地址空间大小判断内存占用；不要因为"申请成功"就认为容量足够。
