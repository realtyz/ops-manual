## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **申请 = 记账，使用 = 落地**：`malloc`/`mmap` 成功后，物理页还没给；`Committed_AS` 会涨，`RSS` 不会。
> - **`VSZ` 是承诺总量**：线程栈预留、JVM 堆预留、文件映射都会把它撑大，所以它不能当占用报表。
> - **`overcommit_memory` 决定承诺的松紧**：`0` 启发式（默认）、`1` 来者不拒、`2` 严格按 `CommitLimit` 卡。
> - **严格模式下会「申请失败」**：合法的大申请也可能被拒（`ENOMEM`），极端情况下 root 登录都会失败——所以要预留 `admin_reserve_kbytes`。
> - **申请失败不一定怪内存**：`vm.max_map_count`、`RLIMIT_AS`/`RLIMIT_DATA`、地址空间碎片都会让 `mmap` 返回 `ENOMEM`。

## 1. 两个时刻：申请与落地

| 时刻 | 发生了什么 | 可观察的证据 |
| --- | --- | --- |
| 申请（`malloc`/`mmap`/`brk`） | 内核在进程的虚拟地址空间里划出一段范围，按策略记账 | `VmSize`/`VSZ` 上涨；`Committed_AS` 上涨（严格模式下会与 `CommitLimit` 比较） |
| 落地（第一次写入） | 触发缺页，内核分配物理页并建立页表映射 | `VmRSS`/`RSS` 上涨；minor fault 增加 |

```bash
cat /proc/<pid>/status | grep -E 'VmSize|VmRSS'         # 验证：承诺与落地的差距
grep -E '^(CommitLimit|Committed_AS):' /proc/meminfo    # 验证：整机的承诺上限与已承诺量
```

> [!important] 这条性质决定了排障顺序
> 因为落地是延后的，「内存不足」可能出现在**任何一次写入**上，而不是申请的那一刻。所以看到某进程莫名其妙被杀，不能只看它启动时申请了多少，要看它运行时实际写了多少（子笔记 05、08）。

## 2. 申请的三条路径

| 路径 | 用途 | 特点 |
| --- | --- | --- |
| `brk`/`sbrk` | 扩展堆的顶部 | 只适合小对象；glibc 用它管理主 arena |
| `mmap`（匿名） | 大块内存、线程栈、`malloc` 的大对象 | 独立映射，释放时直接还给内核；`M_MMAP_THRESHOLD`（glibc 默认约 128 KiB，动态调整）以上走这条路 |
| `mmap`（文件） | 共享库、文件映射、共享内存 | 页来自 Page Cache，卸载时清理方式不同（子笔记 06） |

另外还有栈：每次函数调用加深一点，内核按需给它补页（超过 `RLIMIT_STACK` 会得到 `SIGSEGV`）。

```bash
cat /proc/<pid>/maps                 # 验证：匿名映射、文件映射与栈的分布
cat /proc/<pid>/limits | grep -E 'Max address space|Max data size|Max stack size'
                                     # 验证：RLIMIT_AS / RLIMIT_DATA / RLIMIT_STACK 的当前值
```

## 3. `VSZ` 为什么总是虚高

`VSZ`/`VmSize` 是「承诺总量」，下面这些都会把它撑大，但都不代表真实占用：

| 来源 | 说明 |
| --- | --- |
| 线程栈预留 | 每个线程默认预留一段栈（`RLIMIT_STACK`，常见 8 MiB），几百个线程就是几 GiB 的 `VSZ` |
| JVM/数据库的堆预留 | 应用按最大堆预留地址空间，实际用多少看运行时 |
| 大文件映射 | `mmap` 一个几十 GiB 的文件，`VSZ` 立刻涨，但只有访问到的页才会进内存 |
| 内存分配器的 arena | 每个线程 arena 有自己的地址空间，`VSZ` 会随线程数增长 |

判断真实占用要用 `RSS`（快速看）与 `PSS`/`USS`（跨进程比较），见子笔记 05。

## 4. 超额承诺：`overcommit_memory` 的三种模式

Linux 默认允许「承诺的内存超过物理内存 + swap」，因为大多数程序申请后并不马上用。策略由 `vm.overcommit_memory` 决定：

| 取值 | 语义 | 什么时候选它 | 代价 |
| --- | --- | --- | --- |
| `0`（默认） | 启发式：明显过分的申请（例如一次要得比物理内存 + swap 还多）被拒，整体允许超额 | 绝大多数系统 | 「申请成功」不保证「一定用得出来」，压力最终变成 OOM |
| `1` | 总是允许超额，直到真的用不出来才 OOM | 依赖「申请即成功」的应用，典型是 Redis 的 `BGSAVE`（`fork` + COW 场景） | 承诺完全失去约束，OOM 更可能突然发生 |
| `2` | 不允许超额：承诺总量不超过 `swap + overcommit_ratio% × 物理内存`（或 `overcommit_kbytes`） | 想用严格承诺换确定性 | 合法的大申请被拒；极端情况下管理进程也可能申请失败 |

```bash
sysctl vm.overcommit_memory vm.overcommit_ratio vm.overcommit_kbytes
                                     # 验证：三种模式的当前配置（kbytes 非 0 时优先于 ratio）
grep -E '^(CommitLimit|Committed_AS|MemTotal|SwapTotal):' /proc/meminfo
                                     # 验证：严格模式下与上限对照的两个数
```

严格模式下还有两条必须知道的规则：

1. **`admin_reserve_kbytes` 与 `user_reserve_kbytes` 管的是「保留余量」**：特权用户（`CAP_SYS_ADMIN`）在 `CommitLimit` 之外还能多用 `admin_reserve_kbytes`（默认取「空闲页的 3%」与 8 MiB 中较小者）；普通用户一侧由 `user_reserve_kbytes`（默认取 3% 与 128 MiB 中较小者）预留一部分空闲内存，避免某个用户把内存吃光后连 shell 都起不来。默认值随内核版本变化，一律用 `sysctl` 查本机。
2. **`MAP_NORESERVE` 不能当作免记账的通行证**：它的实际效果受 `overcommit_memory` 模式与内核版本影响，**不要依赖它绕过承诺计数**。

> [!warning] 不要为了「避免 OOM」就一律改成模式 2
> 模式 2 会把「OOM 杀掉一个进程」换成「新申请直接失败」。对很多应用来说，后者更难处理（可能是启动失败、连接建立失败、甚至管理进程无法登录）。改模式 2 前必须评估：本机 `CommitLimit` 是多少、业务峰值 `Committed_AS` 是多少、留了多少余量。

## 5. 申请失败时，先分清是哪一类

`malloc` 返回 `NULL`、`mmap` 返回 `ENOMEM`，不一定是「物理内存没了」。按下面的顺序排除：

| 判据 | 现象 | 检查 |
| --- | --- | --- |
| 严格承诺撞上限 | 只有模式 2 下出现；`Committed_AS` 贴着 `CommitLimit` | `sysctl vm.overcommit_memory`、`meminfo` 的两个字段 |
| 进程地址空间上限 | 该进程单独失败，其他进程正常 | `/proc/<pid>/limits` 的 `RLIMIT_AS`/`RLIMIT_DATA` |
| 映射段数上限 | 程序创建大量映射（线程、mmap 小块）后失败 | `sysctl vm.max_map_count`、`/proc/<pid>/maps \| wc -l` |
| 真的没内存 | 伴随 OOM 日志、PSI 压力与换页 | 子笔记 07、08 |

## 6. 生产动作：承诺与落地的对照观测（实验 1）

> [!example]- 实验 1：`malloc` 成功不等于占用内存
> **怎么做**：只申请 1 GiB 虚拟地址、一页都不碰，观察 `VSZ`/`RSS`/`Committed_AS`；再逐页写入，观察 `RSS` 的变化。
> ```bash
> grep -E '^(CommitLimit|Committed_AS|MemAvailable):' /proc/meminfo   # 记录基线
> python3 - <<'EOF' & P1=$!
> import mmap, os, time
> m = mmap.mmap(-1, 1024 ** 3)
> print('mapped 1GiB, pid =', os.getpid(), flush=True)
> time.sleep(180)
> EOF
> sleep 2; ps -o pid,vsz,rss,cmd -p "$P1"                            # 验证：VSZ 约 +1GiB，RSS 几乎不变
> grep -E '^(Committed_AS|MemAvailable):' /proc/meminfo              # 验证：Committed_AS 已记账
> python3 - <<'EOF' & P2=$!
> import mmap, os, time
> size = 1024 ** 3
> m = mmap.mmap(-1, size)
> for i in range(0, size, 4096):
>     m[i] = 1
> print('touched all pages, pid =', os.getpid(), flush=True)
> time.sleep(180)
> EOF
> sleep 20; ps -o pid,vsz,rss,cmd -p "$P2"                           # 验证：RSS 涨到约 1GiB
> kill "$P1" "$P2"
> ```
> **预期**：第一步 `VSZ` 涨、`RSS` 不动、`Committed_AS` 上涨；第二步 `RSS` 才涨上来。**「申请成功」与「占用内存」是两件事。**
> **风险**：低。不改内核参数；但第二步会真实占用约 1 GiB 内存，请确保实验机空闲内存足够。
> **耗时**：约 15 分钟。
> **怎么退回去**：命令末尾已 `kill` 两个进程；确认进程退出、内存回到基线即可。若申请失败（`ENOMEM`），把 1 GiB 调小后再试。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 用 `VSZ` 判断进程占用 | `VSZ` 是承诺，不包含落地信息；判断占用用 `RSS`/`PSS` |
| 「申请成功了，内存一定够用」 | 承诺与落地分离；压力可能在第一次写入时才出现 |
| 把 `overcommit_memory=1` 当成「提高性能」 | 它只是取消承诺约束，OOM 的风险反而更高；只在明确场景（如 Redis `BGSAVE`）使用 |
| 一律把 `overcommit_memory` 改成 `2` | 新申请可能直接失败，交易类应用与运维工具都会受影响；必须先算 `CommitLimit` 与峰值 `Committed_AS` |
| `Committed_AS` 超过物理内存就以为要出事 | 在模式 0/1 下这是允许的，只有模式 2 才受 `CommitLimit` 约束 |
| `mmap` 报 `ENOMEM` 就加内存 | 先排除 `RLIMIT_AS`/`RLIMIT_DATA`、`vm.max_map_count` 与模式 2 的承诺上限 |
| 用 `MAP_NORESERVE` 绕过承诺 | 效果随模式与内核版本变化，不能作为确定性手段 |
| 忘记 `fork` 的 COW 会放大写入 | 备份、快照类场景里 `fork` 之后的写入量才决定真实内存需求 |

## 决策练习

> [!question]- 场景：某服务在业务高峰期启动失败，日志报 `Cannot allocate memory`；同时 `free -h` 显示 `available` 还有 20 GiB，`Committed_AS` 已经贴着 `CommitLimit`。你怎么判断？
> A. 加内存条，`available` 不够就得扩
> B. 先确认是不是严格承诺模式（`vm.overcommit_memory=2`）导致的新申请被拒，再评估 `CommitLimit`、`overcommit_ratio`/`overcommit_kbytes` 与峰值 `Committed_AS` 的余量
> C. 把 `overcommit_memory` 改成 `1`，让申请永远成功
>
> **答案：B。**
> A 方向错了：`available` 还有 20 GiB，说明物理页并不缺，缺的是「承诺额度」。
> C 能暂时让启动成功，但取消承诺约束后，压力会以更难预测的 OOM 形式出现；改模式必须有评估与回滚方案。
> B 是正解：**先分类（是物理内存不足还是承诺额度不足）→ 再算余量 → 最后才谈改哪一个参数**。

## 要点自测

> [!question]- `malloc` 成功后，内核到底做了什么？怎么验证？
> - 划出一段虚拟地址并记账（`VSZ`/`Committed_AS` 变化），没有分配物理页。
> - 验证方式：申请后看 `VmRSS` 不变；写入后再看 `VmRSS` 上涨（实验 1）。
> - **第一反应不要是什么**：不要把「申请成功」当成容量验收。

> [!question]- `overcommit_memory` 的三种模式分别适合什么场景？
> - `0`：默认，绝大多数系统；`1`：依赖「申请即成功」的应用（如 Redis `BGSAVE`）；`2`：需要严格承诺、能接受申请被拒的场景。
> - 模式 2 下要同时评估 `overcommit_ratio`/`overcommit_kbytes` 与 `admin_reserve_kbytes`，否则可能连管理操作都失败。
> - **第一反应不要是什么**：不要为了「避免 OOM」无脑切到模式 2，那只是把问题换成另一种失败。

> [!question]- `Committed_AS` 与 `CommitLimit` 是什么？什么时候才要紧张？
> - `CommitLimit` 是严格模式下允许的承诺上限（`swap + overcommit_ratio% × 物理内存`，或由 `overcommit_kbytes` 指定）；`Committed_AS` 是当前已承诺的量。
> - 只有在模式 2 下，`Committed_AS` 贴近 `CommitLimit` 才意味着新申请会失败。
> - **第一反应不要是什么**：不要拿这两个数在模式 0/1 下做容量告警。

> [!question]- `VSZ` 很大但 `RSS` 很小，常见的三种来源是什么？
> - 线程栈预留、应用自己的大块地址预留（JVM 堆等）、大文件映射。
> - 确认方式：`/proc/<pid>/maps` 看映射类型与大小，`/proc/<pid>/status` 对照 `VmSize`/`VmRSS`。
> - **第一反应不要是什么**：不要因为 `VSZ` 大就调小应用的关键参数（例如 `-Xmx`），先确认落地了多少。

> [!question]- `mmap` 返回 `ENOMEM`，按什么顺序排查？
> - 先看是不是模式 2 的承诺上限（对照 `Committed_AS`/`CommitLimit`）。
> - 再看进程自己的 `RLIMIT_AS`/`RLIMIT_DATA` 与 `vm.max_map_count`。
> - 最后才怀疑真实物理内存不足（配合 PSI、`si/so` 与内核日志）。
> - **第一反应不要是什么**：不要直接加内存；三条限制类原因都不吃内存条。
