## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **OOM 是最后手段**：先回收，回收不动才杀进程；杀谁由打分决定，不是随机。
> - **打分的第一项就是占用**：`RSS + swap 中的页 + 页表`，再叠加 `oom_score_adj` 的权重；`-1000` 表示「永不被选」。
> - **整机 OOM 与 cgroup OOM 是两件事**：日志前缀分别是 `Out of memory:` 与 `Memory cgroup out of memory:`，后者还带 `task_memcg=`/`oom_memcg=` 与 `memory: usage ... limit ...`。
> - **退出码 137 不能证明 OOM**：它只说明被 `SIGKILL` 杀过；定性证据是内核日志与 `memory.events` 的 `oom_kill`。
> - **OOM 是「杀进程」，不是「内核崩溃」**：默认不会留下 `vmcore`，只能靠日志、cgroup 事件与持久化 journal（`panic_on_oom=2` 是例外，代价是整机重启）。

## 1. 从回收不动到 OOM：两条岔路

内存分配走到最后一步时，内核会先回收，再判断「撞的是谁的上限」：

| 撞到的上限 | 触发 | 结果 |
| --- | --- | --- |
| 某个 cgroup 的 `memory.max` | 该组用量超过硬上限，且组内回收不动 | **cgroup OOM**：只在该 cgroup 内挑进程 |
| 整机 zone 的 `min` 水位 | 整机可回收内存耗尽 | **整机 OOM**：在可杀进程范围内按打分挑 |

```bash
journalctl -k -b | grep -i -E 'Out of memory: Killed process|Memory cgroup out of memory'
                                     # 验证：本机开机以来的 OOM 事件与类型
cat /sys/fs/cgroup/<路径>/memory.events
                                     # 验证：某个 cgroup 是否发生过 oom / oom_kill
```

> [!important] 「容器被杀但宿主很空」是正常现象
> cgroup OOM 只看该组的账本，与宿主 `MemAvailable` 无关。反过来，整机 OOM 时被杀的进程不一定「最占内存」——还要看它所在的候选范围与 `oom_score_adj`。

## 2. 整机 OOM：日志与打分

典型日志分两块：**水位块**（各 zone 的 `free`/`min`/`low`/`high`）+ **被选中进程那一行**：

```text
Out of memory: Killed process 12345 (java) total-vm:33554432kB, anon-rss:8388608kB,
  file-rss:0kB, shmem-rss:0kB, UID:1000 pgtables:20480kB oom_score_adj:0
```

逐个字段读：`total-vm` 虚拟地址空间、`anon-rss` 匿名常驻、`file-rss` 文件页常驻、`shmem-rss` 共享内存常驻、`pgtables` 页表占用、`oom_score_adj` 权重。**`anon-rss` 与 `pgtables` 解释了它为什么被选中**，`oom_score_adj` 解释了「有没有被人为改动过」。

打分逻辑来自内核 `oom_badness()`：

```text
得分 ≈ 归一化后的（RSS + swap 中的页 + 页表页数）
     + oom_score_adj × (总页数 / 1000)
```

要点：

- 得分越高越先被杀；`/proc/<pid>/oom_score` 是归一化到 0~1000 的当前得分；
- **`oom_score_adj = -1000` 表示永不被选**（内核直接跳过），范围 `-1000`~`1000`；
- 内核线程、正在退出/`vfork` 的进程等会被直接排除；
- **cgroup OOM 只在该组内比较得分**，跨组不比较。

```bash
cat /proc/<pid>/oom_score              # 验证：该进程当前的得分绝对值
cat /proc/<pid>/oom_score_adj          # 验证：当前权重（可写）
choom -p <pid> -n -500                 # 验证：把权重调到 -500（util-linux 提供）
systemctl show -p OOMScoreAdjust <unit>  # 验证：systemd 启动时写入的权重
```

> [!warning] 保护一个进程，等于把刀递给另一个
> 把关键进程设成 `-1000` 并不会让 OOM 消失，只会让它去杀别的进程。**保护清单越长，真正被保护的效果越差**；正确做法是给每个服务配内存上限（子笔记 10），让 OOM 在「责任人」范围内发生。

## 3. cgroup OOM：日志与事件计数

```text
Memory cgroup out of memory: Killed process 12345 (java) total-vm:..., anon-rss:..., UID:1000 ...
  oom_memcg=/kubepods.slice/... task_memcg=/kubepods.slice/...
  memory: usage 4194304kB, limit 4194304kB, failcnt 0
```

多出来的两行是定性关键：

- `oom_memcg=` 是**触发 OOM 的那个 cgroup**，`task_memcg=` 是**被杀进程所属的 cgroup**；两者不同时说明是「别人的上限把组内进程卷进来了」；
- `memory: usage ... limit ... failcnt ...` 是当时的用量、上限与分配失败计数。

| 观察点 | 位置 | 说明 |
| --- | --- | --- |
| `memory.events` | cgroup 文件 | `oom`、`oom_kill`、`oom_group_kill` 计数；`oom_kill` 非 0 就是真的杀过 |
| `memory.current` / `memory.peak` | cgroup 文件 | 当前用量与历史峰值（peak 需要较新内核） |
| `memory.stat` | cgroup 文件 | `anon`/`file`/`shmem`/`slab`/`sock` 构成，判断涨的是哪一类 |
| `memory.oom.group` | cgroup 文件 | 设为 `1` 时整组一起被杀 |

## 4. 用户态 OOM：`systemd-oomd`

除了内核 OOM，systemd 还提供了一个**基于 PSI 提前动手**的用户态守护进程。两者分工：

| 维度 | 内核 OOM | `systemd-oomd` |
| --- | --- | --- |
| 触发时机 | 分配真的失败时 | 压力达到阈值（早于内核） |
| 依据 | 打分 + 上限 | cgroup v2 PSI 与 swap 使用率 |
| 杀谁 | 单个进程（或 `oom.group` 的整组） | 目标 cgroup 内的**所有进程** |
| 配置 | `oom_score_adj`、`memory.max` | unit 的 `ManagedOOMSwap=`、`ManagedOOMMemoryPressure=` |

```bash
systemctl status systemd-oomd        # 验证：守护进程是否在跑
oomctl                               # 验证：当前被监控的 cgroup 与压力数据
cat /etc/systemd/oomd.conf           # 验证：全局策略（SwapUsedLimit、DefaultMemoryPressureLimit 等）
systemctl show -p ManagedOOMSwap -p ManagedOOMMemoryPressure <unit>
                                     # 验证：某个 unit 是否启用了 oomd 接管
```

两个边界：**只有在 cgroup v2 + PSI 可用的系统上才有意义**；并且它只处理**被监控 unit 的后代 cgroup**（叶子节点，或设置了 `memory.oom.group=1` 的组）。默认阈值（swap 使用率 90%、内存压力 60% 持续 20 秒）以 `oomd.conf` 与所用版本的官方文档为准。

## 5. `panic_on_oom`：把「杀一个」升级为「留现场」

| 取值 | 行为 | 适用 |
| --- | --- | --- |
| `0`（默认） | 只杀进程 | 绝大多数服务 |
| `1` | 整机 OOM 时 panic（局部约束导致的 OOM 不 panic） | 希望「内存出不来必留现场」的系统 |
| `2` | 连 cgroup OOM 也触发整机 panic | 取证要求极高、能接受重启的场景 |

`2` + kdump 是已知的强取证组合：能拿到完整内存快照（kdump 的细节在阶段 2 启动流程与内核里）。代价也很明确：**从「杀一个进程」变成「整机重启」**，不适合「宁可杀一个进程也不许重启」的服务。改动前先确认 kdump 真的可用，否则只是白白重启。

## 6. OOM 取证六步（本阶段的固定交付物）

> [!important] 顺序不要乱
> 1. **定时间点与影响面**：`journalctl --since '<时间>'`、`journalctl -b -1` 与业务告警对齐（时间与时区基线见阶段 2）。
> 2. **分清整机还是 cgroup**：看日志前缀是 `Out of memory:` 还是 `Memory cgroup out of memory:`。
> 3. **看被选中进程与权重**：`anon-rss`、`pgtables`、`oom_score_adj`，解释「为什么是它」。
> 4. **看当时的水位**：日志前面各 zone 的 `free`/`min`/`low`/`high`，判断是「真空了」还是「卡在某个水位」。
> 5. **看 cgroup 侧数据**：`memory.events` 的 `oom_kill`、`memory.current`/`peak`、`memory.stat` 的构成。
> 6. **回到限制来源**：是 `memory.max` 太小、整机水位不足，还是某个进程/缓存突然涨上来；这一步决定改进动作。

```bash
journalctl -k -b | grep -i -E 'Memory cgroup out of memory|Out of memory: Killed process'
journalctl -k -b | grep -B30 'Killed process' | head -60      # 连水位块一起看
cat /sys/fs/cgroup/<路径>/memory.events                        # oom / oom_kill 计数
cat /sys/fs/cgroup/<路径>/memory.stat | grep -E '^(anon|file|shmem|slab|sock) '
systemctl show -p MemoryCurrent -p MemoryMax -p MemoryPeak <unit>
```

> [!warning] 平时就要保证证据留得下来
> **普通 OOM 不会产生 `vmcore`**（OOM 不是内核崩溃）。所以必须提前做两件事：把 journal 持久化（`/var/log/journal`），以及让容器/服务的 cgroup 事件被采集。否则事后只能靠业务日志猜。

## 7. 生产动作：实验 6（触发一次 cgroup OOM 并取证）

> [!example]- 实验 6：用 `systemd-run` 触发 cgroup OOM（只在可快照的实验机）
> **怎么做**：起一个限 64 MiB、禁用 swap 的临时单元，让它申请 200 MiB，然后按六步取证。
> ```bash
> systemd-run --unit=lab-oom --property=MemoryMax=64M --property=MemorySwapMax=0 \
>   /usr/bin/python3 -c 'x = bytearray(200*1024*1024); print(len(x))'
> systemctl status lab-oom              # 验证：结果是被杀，而不是整机 OOM
> journalctl -k -b | grep -i -A5 'Memory cgroup out of memory' | tail -30
> cat /sys/fs/cgroup/system.slice/lab-oom.service/memory.events
> cat /sys/fs/cgroup/system.slice/lab-oom.service/memory.stat | head -15
> systemctl show -p MemoryMax -p MemoryPeak lab-oom
> systemctl reset-failed lab-oom        # 取证完成后再清理
> ```
> **预期**：日志前缀是 `Memory cgroup out of memory`，带 `task_memcg=` 与 `memory: usage ... limit ...`；`memory.events` 的 `oom_kill` 从 0 变 1；**整机 `free` 全程没有明显变化**。
> **风险**：中。它会真的杀一个进程（是你自己起的临时单元），需要 cgroup v2 与 Python 3；**只在实验机上做**。
> **耗时**：约 20 分钟。
> **怎么退回去**：`systemctl reset-failed lab-oom`；注意**先取证再清理**，否则 cgroup 文件会一起消失。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 看到退出码 137 就写「被 OOM 杀」 | 137 只说明被 `SIGKILL`；定性要看内核日志或 `memory.events` |
| 拿宿主 `free` 判断容器 OOM | cgroup OOM 与宿主可用内存无关 |
| 把「占内存最多」当作唯一判据 | 只有在同一轮 OOM 的候选范围内才比较；`oom_score_adj` 会改变结果 |
| 给关键进程设 `-1000` 就以为安全 | 刀会转向别的进程；应结合 cgroup 上限与真正的责任人范围 |
| 以为 OOM 会留下 `vmcore` | 默认不会；除非显式配置 `panic_on_oom=2` 且 kdump 可用 |
| 事后才发现 journal 没持久化 | 重启后证据消失；`/var/log/journal` 要提前建 |
| 清理 unit 太早 | `reset-failed` 后 cgroup 目录消失，`memory.events`/`memory.stat` 一起没了 |
| 混淆 `oom_memcg` 与 `task_memcg` | 两者不同时，说明触发上限的组与被杀进程的组不是同一个 |

## 决策练习

> [!question]- 场景：告警显示某容器在 03:12 被杀，退出码 137；宿主 `available` 当时还有 25 GiB。值班同事直接写「疑似 OOM，先扩容宿主」。你怎么做？
> A. 按他的结论执行：宿主加内存
> B. 先按六步取证：确认日志前缀是 `Memory cgroup out of memory`，找 `task_memcg=`/`limit=`，读该 cgroup 的 `memory.events` 与 `memory.stat`，再决定是调 `limits`、修泄漏还是限制 `/dev/shm`
> C. 把容器的 `memory.max` 改成 `max`，避免以后再被杀
>
> **答案：B。**
> A 没有证据，而且宿主还有 25 GiB 更像 cgroup OOM；扩容宿主不解决任何问题。
> C 会让容器失去刹车，是最危险的动作之一。
> B 是正解：**先用日志与事件计数定性，再看构成决定改进动作**。这正是六步取证的价值。

## 要点自测

> [!question]- OOM 是怎么挑进程的？`oom_score_adj` 起什么作用？
> - 得分 ≈ 归一化后的（`RSS` + swap 中的页 + 页表）+ `oom_score_adj` 的权重；得分最高者被杀。
> - `oom_score_adj` 范围 `-1000`~`1000`，`-1000` 表示永不被选；它只影响同一轮 OOM 内的相对排序。
> - **第一反应不要是什么**：不要用「谁占内存最多」解释所有 OOM——候选范围、cgroup 边界与权重都会改变结果。

> [!question]- 整机 OOM 与 cgroup OOM 的判据分别是什么？
> - 整机：日志前缀 `Out of memory: Killed process`，通常伴随各 zone 水位耗尽。
> - cgroup：日志前缀 `Memory cgroup out of memory`，带 `task_memcg=`/`oom_memcg=` 与 `memory: usage ... limit ...`；对应 cgroup 的 `memory.events` 里 `oom_kill` 增加。
> - **第一反应不要是什么**：不要拿宿主 `available` 当判据，也不要靠退出码 137。

> [!question]- 六步取证的顺序是什么？为什么顺序不能乱？
> - 时间点与影响面 → 整机还是 cgroup → 被选中进程与权重 → 当时水位 → cgroup 侧数据 → 限制来源。
> - 前一步决定后一步的取数范围（例如第 2 步决定第 5 步读哪个 cgroup）；顺序乱了会得出错误结论。
> - **第一反应不要是什么**：不要先重启、先扩容或先改限制；证据一旦被冲掉或清理掉就再也拿不回来。

> [!question]- `systemd-oomd` 与内核 OOM 的分工是什么？
> - `systemd-oomd` 基于 cgroup v2 + PSI，在压力达到阈值时提前杀**整组**进程；内核 OOM 在分配失败时按打分杀单个（或 `oom.group` 整组）。
> - 两者可以并存，但要清楚谁先动手、杀掉的是哪一组；配置在 unit 的 `ManagedOOM*=` 与 `oomd.conf`。
> - **第一反应不要是什么**：不要以为装了 `systemd-oomd` 就不会有内核 OOM，也不要忽略它「杀整组」的后果。

> [!question]- 为什么说 OOM 之后「重启是最后选项」？
> - 进程还活着时，现场（`memory.current`/`stat`/`events`、进程内存构成）都能现取；一旦重启，cgroup 与进程现场都会消失。
> - 内核日志虽然会保留（如果 journal 持久化），但缺少 cgroup 细节与业务侧上下文。
> - **第一反应不要是什么**：不要用「重启后好了」当结论——那只是把问题暂停。
