# 观测与基线

## 1. 一个问题，一把工具

| 你想知道             | 用什么                                             | 关键字段或文件                                  |
| ---------------- | ----------------------------------------------- | ---------------------------------------- |
| 整机还有多少能给新程序用     | `free`、`/proc/meminfo`                          | `available`、`MemAvailable`               |
| 整机有没有内存压力        | `/proc/pressure/memory`                         | `some`/`full` 的 `avg10`/`avg60`/`avg300` |
| 有没有在换页、有没有 IO 等待 | `vmstat 1`                                      | `si`、`so`、`wa`、`r`、`b`                   |
| 谁占的内存最多          | `ps -eo pid,comm,rss --sort=-rss`、`top`         | 常驻集（注意共享页重复计数）                           |
| 单个进程的占用构成        | `/proc/<pid>/status`、`/proc/<pid>/smaps_rollup` | `VmRSS`、`RssAnon`、`RssFile`、`Pss`        |
| 内核缓存与内核对象占了多少    | `/proc/meminfo`、`slabtop -o -s c`               | `Slab`、`SReclaimable`、`SUnreclaim`       |
| 页表、内核栈等内核开销      | `/proc/meminfo`                                 | `PageTables`、`KernelStack`、`VmallocUsed` |
| 缓存与脏页            | `/proc/meminfo`                                 | `Cached`、`Shmem`、`Dirty`、`Writeback`     |
| swap 用了多少、谁被换出   | `swapon --show`、`/proc/<pid>/status`            | `SwapTotal`、`SwapFree`、`VmSwap`          |
| 容器/服务的账本         | cgroup 文件与 `systemctl show`                     | `memory.current`/`max`/`stat`/`events`   |
| 进程级 IO 与回写压力     | `pidstat -d 1`、`iostat -x 1`                    | `kB_wr/s`、`await`、`aqu-sz`               |

表里的「用什么」分两类：**命令**（`free`、`vmstat`、`ps`、`slabtop`、`numactl`……文档在 `man 1` 或 `man 8`）与**内核接口文件**（`/proc/...`、`/sys/...`、cgroup 下的文件——直接 `cat` 就能读，不需要任何工具）。分不清时看文档节号：`man 2` 是系统调用、`man 3` 是库函数、`man 5` 是文件格式。

**要动 swap 时**（变更动作，只在实验机上先走一遍）：`fallocate -l 2G /swapfile` → `chmod 600 /swapfile` → `mkswap /swapfile` → `swapon /swapfile`，持久化写进 `/etc/fstab` 或做成一个单元；**验收**看 `swapon --show` 与 `/proc/meminfo` 的 `SwapTotal` 是否等于预期；**回滚**是 `swapoff /swapfile` 再删文件。两个会绊住人的点：`swapon` 拒绝带空洞的文件；Btrfs 上 `fallocate` 出来的文件不能直接用作 swap——发行版与文件系统的差异以官方文档为准。
## 2. 怎么读这些数字

下面每一条都给三样东西：**这个数字是什么**、**多少算异常**、**和谁一起看**。文中的输出样例只用来展示**格式**，数值不代表你的机器。

### 2.1 `vmstat`：第一行必须忽略

```bash
vmstat 1 5        # 验证：每秒采样一次共五行；第一行是自开机以来的平均值
```

```text
procs -----------memory---------- ---swap-- -----io---- -system-- ------cpu-----
 r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
 1  0      0 684123  21144 402188    0    0     3    12   45   88  1  1 98  0  0
 2  0      0 401234  21144 402188    0    0     0     4   52   95  2  1 97  0  0
```

- **第一行是自开机以来的平均值**，`vmstat` 的手册明确写了这一点。判断"现在正在发生什么"必须从**第二行**起看。这是最常见的误读。
- `r`：可运行（含正在运行）的进程数。**和 CPU 核数比**：4 核机器上 `r` 长期大于 4 说明 CPU 排队；`r` 偶尔尖峰无害。
- `b`：处于不可中断睡眠的进程数（多在等 IO）。**单行 `b=1` 不算证据；连续多行 `b` 都 ≥1 才是"有进程被 IO 按住"**。
- `si`/`so`：换入/换出速率，单位 KiB/s（`vmstat -S m` 可换成 MiB）。**只有配了 swap 才有意义**；`so` 持续非 0 表示匿名页在往 swap 写，`si` 跟着非 0 表示它们又被读回来——两者同时持续非 0 就是 thrashing。
- `bi`/`bo`：块设备读写速率（块/s，块大小见 `man vmstat`）。**注意它包含所有块设备**，不只是数据盘；写日志、读缓存都会体现。
- `wa`：CPU 空闲但仍在等 IO 的时间占比。**它只有在 CPU 本来有空闲时才显得出来**；同时看 `b`——`wa` 高而 `b` 长期为 0，更可能是采样噪声或短促脉冲。
- `free`/`buff`/`cache`：单位 KiB。这里的 `cache` 是页缓存，**它小不等于内存不够**（见 2.3）。
- 组合判据（比单列可靠得多）：

| 你看到 | 含义 | 下一步 |
| --- | --- | --- |
| `si`/`so` 持续非 0，`b` 也持续 ≥1 | 换页已经把 IO 拖进来了 | 查谁被换出（`VmSwap`）、看压力指标，评估工作集与内存 |
| `so` 非 0 但 `si` 为 0 | 有匿名页被换出，暂时没人读回 | 观察趋势；配合 `pgmajfault` 是否上涨 |
| `wa` 高、`b` 持续 ≥1、`si`/`so` 为 0 | IO 等待不是内存引起的 | 转 `iostat -x`、`pidstat -d`，查设备与写模式 |
| `r` 远大于核数、`id` 很低 | CPU 排队 | 这是 CPU 问题，不是内存 |
| 五行都平稳、`id` 很高 | 这台机器此刻没有资源压力 | 换时间窗口，或看历史数据 |

### 2.2 压力指标：百分比是"被拖慢的时间占比"

```bash
cat /proc/pressure/memory     # 验证：内存压力；同目录下还有 cpu 与 io
```

```text
some avg10=0.00 avg60=0.00 avg300=0.00 total=0
full avg10=0.00 avg60=0.00 avg300=0.00 total=0
```

- **`some` 与 `full`**：`some` 表示"至少有一部分任务因为内存而停等"，`full` 表示"所有可运行任务都被拖住"——后者出现就说明这台机器已经在明显变慢。
- **`avg10`/`avg60`/`avg300`**：过去 10 秒 / 60 秒 / 300 秒内的占比（%）。要看**三个尺度是否一致上升**：只有 `avg10` 高、`avg60` 为 0，说明是刚刚发生的短促事件；三个都高才是持续压力。
- **`total`**：自开机以来的累计停滞时间（微秒）。它的价值在于**取差值**——两次读数相减，得到这段时间里的绝对停滞量。
- **怎么判断严重**：没有通用阈值，要和自己机器的基线比。可操作的起步判据是：`some` 长期非 0 且 `avg60` 抬头 → 值得查；`full` 非 0 → 已经影响全部任务。
- **必须和谁一起看**：压力是"结果"，还要回答"是被谁、因为什么"——用 `vmstat` 看是换页还是回写，用 `ps` 看是谁在吃内存或制造 IO。

### 2.3 `free` 与 `/proc/meminfo`：先确认列的定义再用

```bash
free -m                              # 验证：人类可读的六个口径
grep -E '^(MemTotal|MemFree|MemAvailable|Buffers|Cached|SReclaimable|Shmem):' /proc/meminfo
```

```text
               total        used        free      shared  buff/cache   available
Mem:            7894         530        7304           1         295        7363
```

- **`available` 是判断"够不够"的那一列**。它由内核估算：把可回收的页缓存按低水位打折后算作可用。`free` 那一列（完全空闲）小是正常的。
- **`used` 的口径随 procps 版本变化**：老版本约等于 `total − free − buff/cache`，较新版本更接近 `total − available`。两者在缓存占用大时能差出几百 MiB，并直接影响"tmpfs 是否体现在 `used` 里"这个结论。**稳妥做法是现场用 `/proc/meminfo` 算一遍**：

```bash
awk '/^(MemTotal|MemFree|MemAvailable|Buffers|Cached|SReclaimable):/{v[$1]=$2}   # 验证：used 到底等于哪个公式（输出单位 MiB）
     END{bc=v["Buffers:"]+v["Cached:"]+v["SReclaimable:"];
         printf "total-free-bc = %d MiB\n", (v["MemTotal:"]-v["MemFree:"]-bc)/1024;
         printf "total-avail   = %d MiB\n", (v["MemTotal:"]-v["MemAvailable:"])/1024}' /proc/meminfo
```

- **`Cached` 包含 `Shmem`**：tmpfs 与共享内存的页算在缓存里。所以"`Cached` 涨了"可能是读了文件，也可能是有人往 tmpfs 写了东西——含义完全不同，要看 `Shmem`。
- **`SReclaimable` 与 `SUnreclaim`**：前者在压力下可回收，后者不能。**只有 `SUnreclaim` 才是长期占用**；看到 `Slab` 大先别慌，先看它拆成这两项之后各多少。
- **`MemTotal` 不等于内存条容量**：固件、显卡、内核预留、显式大页预留都不计入。
- 组合判据：

| 你看到 | 含义 | 下一步 |
| --- | --- | --- |
| `available` 充足、PSI 接近 0 | 缓存在干活 | 不用处理 |
| `available` 低、PSI 抬头、`si`/`so` 非 0 | 真的紧张 | 走"内存不够用了"流程 |
| `available` 低但 PSI 与换页都正常 | 可能是估算偏保守或缓存正在被回收 | 再看两次，别急着动手 |
| `Shmem` 很大、`used` 也高 | tmpfs 或共享内存占住了内存 | 查 `/dev/shm`、`df -h` 里的 tmpfs 挂载点 |
| `SUnreclaim` 持续上涨 | 内核对象在泄漏式增长 | 用 `slabtop` 定位缓存类型 |

### 2.4 进程侧：三种口径怎么选、构成怎么读

```bash
cat /proc/<pid>/status | grep -E 'VmSize|VmRSS|RssAnon|RssFile|RssShmem|VmSwap|VmPTE'
cat /proc/<pid>/smaps_rollup | grep -E 'Rss|Pss|Private_Clean|Private_Dirty|Anonymous|Swap'
```

```text
VmSize:  10500944 kB      # 地址空间（要了多少）
VmRSS:      10268 kB      # 常驻（物理账本）
RssAnon:     4096 kB      # 其中：匿名页
RssFile:     5120 kB      # 其中：文件页
RssShmem:    1024 kB      # 其中：共享内存与 tmpfs
VmSwap:         0 kB      # 已被换出的量
VmPTE:         64 kB      # 页表项占用
```

- **三个口径**：常驻（`VmRSS`）回答"谁看起来最大"，但它对共享页重复计数；均摊（`Pss`）把共享页按使用者数量分摊，回答"这台机器上真正被谁用了"；私有（`Private_Clean + Private_Dirty` 之和）回答"杀掉它能省多少"。**要下结论先想清问的是哪一个。**
- **构成分流**：`RssAnon` 涨 → 应用数据、缓冲池或泄漏；`RssFile` 涨 → 读了文件或映射了大文件，通常可回收；`RssShmem` 涨 → 有人在写 tmpfs 或用共享内存。
- **`VmSize` 与 `VmRSS` 相差很大是常态**，不要用它判断占用；但要留意 `VmSize` 增长伴 `VmPTE` 增长（映射变多）这种情况。
- **判断泄漏要取两次差值**：同口径、同时长间隔，看 `RssAnon` 是否单调上升；只有一次读数无法区分"刚处理完一批数据"与"持续增长"。

### 2.5 cgroup 文件：五个问题五个文件

```bash
stat -fc %T /sys/fs/cgroup                       # 验证：cgroup2fs 表示 v2
CG=/sys/fs/cgroup/system.slice/<unit>.service    # 单元对应的 cgroup 路径
cat $CG/memory.current $CG/memory.max $CG/memory.peak
cat $CG/memory.stat | head
cat $CG/memory.events
```

```text
536735744            # memory.current：当前用量
536870912            # memory.max：硬上限（"max" 表示没有上限）
536870912            # memory.peak：历史峰值
anon 535035904       # memory.stat：匿名页
file 12582912        # memory.stat：文件页（页缓存，可回收）
slab 42512           # memory.stat：内核对象
oom 1                # memory.events：触发过几次 OOM 判定
oom_kill 1           # memory.events：真正杀掉过几个进程
max 707              # memory.events：撞上限的次数（回收尝试）
```

- **单位是字节**，不是 kB——与 `/proc/meminfo` 的习惯不同。`536870912` 就是 512 MiB（除以 1024 两次）。这是新人最容易读错的一处。
- **`memory.current` 贴着 `memory.max`** 说明这个 cgroup 一直在顶格运行；`memory.peak` 记录了历史最高，用来判断"峰值离上限还有多少余量"。
- **`memory.stat` 的 `anon`/`file`/`slab` 决定处置方向**：`file` 占比高且压力不大，通常只是页缓存；`anon` 高才是应用真的在用；`slab` 异常高要看内核对象。
- **`memory.events` 是定性判据**：`oom_kill` 非 0 就说明这个 cgroup 里真的有进程被杀过；`max` 非 0 说明撞过上限（可能只被节流、没杀人）。**这三个计数是累积值，要取差值判断"这次事件"是否发生在本时间段内。**
- **账本有时效**：cgroup 目录会随单元结束被回收，`memory.events` 只在存活期间存在——事后去读往往什么也读不到。

## 3. 采样纪律与基线

内存问题几乎没有"看一眼就定性"的：缓存会涨会落、业务有峰谷、页的归属会变。四条纪律：

1. **同一口径**：这次看可用内存，下次还看可用内存，不要中途换成完全空闲；
2. **带时间戳**：`date` 与读数一起存，事后才能与告警时间对齐；
3. **至少两次**：判断抖动按秒，判断泄漏按小时或按天；
4. **留原始输出**：整份 `/proc/meminfo` 与相关 cgroup 文件都存下来，而不是只抄一个数字——复盘时经常需要当时没注意的字段。

**基线卡最少要记录**：发行版与内核版本、`MemTotal`、`MemAvailable`、压力指标三个尺度、swap 配置、水位与回写参数、大页策略、cgroup 版本、内存占用前几名及其口径。**没有基线的机器上，"内存使用异常"这个判断本身就不成立**——因为没有"正常"可对照。

## 常见故障与排查方向

下面是七个按真实值班场景构造的例子（机器规格、时间线与数值都是示意）。每个场景给三样东西：**背景**（你要面对的具体处境）、**排查顺序**（先看什么、看到什么转向哪）、**一份合格的回答长什么样**（结论、依据、边界、动作）。字段怎么读在第 2 节。

### 场景一：服务变慢，可用内存掉到几百 MiB

**背景**：一台 8 核 16 GiB 的虚拟机，跑一个 Java 订单服务（JVM 堆上限 4 GiB）、一个 Nginx 和一个日志采集进程。周五 14:30 起 P99 从 80 ms 涨到 900 ms，监控显示 `MemAvailable` 从 6.2 GiB 掉到 380 MiB，客服报偶发 504。你只有 SSH，业务高峰持续到 20:00，不能重启。

**排查顺序**

1. **定"够不够"**：`grep -E '^(MemAvailable|SwapFree):' /proc/meminfo`，`cat /proc/pressure/memory`（读法见 2.2、2.3）。
   - 可用量 380 MiB、PSI 的 `some`/`full` 都在抬头 → 内存确实紧，继续；
   - 若 PSI 三个尺度都接近 0 → 不是内存问题，转场景四。
2. **看"正在发生什么"**：`vmstat 1 5`（第一行忽略），看 `si`/`so`/`b`/`wa`（组合判据见 2.1）；`grep -E '^(pgmajfault|allocstall)' /proc/vmstat` 隔 60 秒取两次差值。
   - `si`/`so` 持续非 0 且 `b` 持续 ≥1 → 换页已经在制造 IO 延迟；
   - `pgmajfault` 一分钟涨几千以上 → 工作集被持续挤出。
3. **找"谁在用"**：`ps -eo pid,comm,rss --sort=-rss | head`；对最大的那个进程按 2.4 看构成。
   - `RssAnon` 巨大 → 应用数据或堆；`RssFile` 大 → 读了大量文件（通常可回收）。
4. **补漏账**：`Shmem`（有没有人写 tmpfs）、`SUnreclaim`（内核对象）、`PageTables`；确认这台机器上有没有容器，若有按 2.5 看 cgroup 额度。
5. **方向与止损**：如果能定位到某个进程异常增长，先限流或给它设限；若是整机容量不足，扩容或降级；**任何动作之前先把第 1~4 步的读数带时间戳存下来**。

**一份合格的回答**

- 结论一句话：是"真紧张"还是"缓存在干活"，以及紧张的表现形式（换页、回收还是即将 OOM）。
- 依据：可用量、PSI 三个尺度、`si`/`so` 趋势、`pgmajfault` 增量、最大进程的构成。
- 边界：如果可用量低但 PSI 与换页都正常，结论要改成"缓存正在被回收，尚无压力"；如果 `wa` 高而 `si`/`so` 为 0，方向要转到 IO。
- 动作：先取证、再决定限流/扩容/设限；明确说出**不会**先做的两件事（`drop_caches`、无基线改参数）。

### 场景二：Kubernetes 节点还有 5 GiB 可用，Pod 却反复 OOMKilled

**背景**：一个 32 GiB 的 K8s 工作节点上，某个业务 Pod 近两小时重启了 6 次，`kubectl describe` 显示上次终止原因是 `OOMKilled`；节点 `MemAvailable` 还有 5 GiB。Pod 的 `limits.memory` 是 `512Mi`，副本数 3。你怀疑是应用泄漏，但开发说"本地压测没问题"。

**排查顺序**

1. **定性在日志，不在退出码**：在节点上 `dmesg -T | grep -iE 'oom|killed process' | tail`。找 `constraint=CONSTRAINT_MEMCG` 与 `oom_memcg=`——它们会直接告诉你撞上限的 cgroup 路径。
2. **读那个 cgroup**：按路径读 `memory.max`/`memory.current`/`memory.peak`/`memory.events`（读法与单位见 2.5）。`oom_kill` 非 0 即确证；`memory.peak` 与 `memory.max` 相等说明峰值顶到了上限。
3. **看构成**：`memory.stat` 的 `anon`/`file`/`slab`（2.5）。
   - `anon` 为主 → 应用真的用了这么多内存；
   - `file` 为主 → 页缓存计入额度，可能是读写模式问题；
   - `shmem` 相关偏高 → 查 `/dev/shm` 的使用。
4. **确认节点侧**：同时看节点自己的 `MemAvailable` 与 PSI——如果节点也在回收/换页，说明是整机压力传导，而不是 Pod 自己的问题。

**一份合格的回答**

- 结论一句话：撞的是 **cgroup 上限**（配额问题）还是**整机水位**（容量问题）——这一句话决定后面所有动作。
- 依据：`oom_memcg=` 指向的路径、`memory.peak` 与 `memory.max` 的关系、`memory.events` 的 `oom_kill`、`memory.stat` 的构成。
- 边界：宿主可用内存多**不能**用来否定容器 OOM（两个账本）；但如果节点同时有回收与换页，结论要改成整机压力传导。
- 动作：调到多少要有依据（用 `memory.peak` 与历史曲线说话），并说明这是变更、需要验证与回滚；不建议直接把 limits 翻倍了事。

### 场景三：凌晨两点进程消失，退出码 137

**背景**：一个 systemd 管理的 Python 采集进程在 02:10 消失，业务日志最后一行正常。`systemctl status` 显示 `Main process exited, code=killed, status=9/KILL`，没有 core 文件。群里有人说"应该是被 OOM 杀了"。

**排查顺序**

1. **先纠正结论**：`137 = 128 + 9`，只说明死于 `SIGKILL`，**不能证明是 OOM**。
2. **查内核 OOM 记录**：`dmesg -T | grep -iE 'oom|killed process'` 与 `journalctl -k --since "02:00" --until "02:20"`。
   - 有整机或 cgroup OOM 记录 → 按场景二继续定位；
   - 没有 → 走第 3 步。
3. **查"谁发的信号"**：人工操作记录（`history`、变更单）、发布/重启记录、编排层驱逐（Kubernetes 的 `kubectl get events`、supervisor/K8s 探针失败重启）、以及 systemd 自身的 `OOMPolicy` 行为。
4. **查"是不是崩了"**：若退出码是 139（段错误）或 134（`SIGABRT`），去查 coredump（`coredumpctl list`）与内核 `segfault` 记录。

**一份合格的回答**

- 结论一句话：这次死亡属于 OOM、被人工/编排终止、还是自身崩溃——**在拿到对应证据之前不写"被 OOM 杀"**。
- 依据：内核日志（有/无 OOM 记录）、`memory.events` 的 `oom_kill` 差值、变更与重启记录、core 文件状态。
- 边界：容器被 OOM 杀时可能没有整机日志；systemd 服务默认在 OOM 后会停掉整个单元，所以要看单元状态而不只是进程退出码。
- 动作：把证据固化到事故记录里；如果确实是 OOM，转场景二。

### 场景四：数据库写入延迟从 2 ms 涨到 200 ms，进程进 `D` 状态

**背景**：一台 16 GiB 的从库，`iostat -x` 显示 `w_await` 从 0.2 ms 涨到 30 ms、`aqu-sz` 到 8；`vmstat 1 5` 的 `wa` 约 20%、`b` 长期为 3；`MemAvailable` 7 GiB；`Dirty` 800 MiB（该机 `vm.dirty_ratio=20`，换算阈值约 3.2 GiB）。有同事提议"加内存"。

**排查顺序**

1. **先排除内存**：`MemAvailable` 7 GiB、PSI 内存压力接近 0 → 内存不是瓶颈，**加内存方向错误**。
2. **看回写状态**：`Dirty` 800 MiB 离阈值还有距离，`Writeback` 是否长期非 0（2.3）；`vmstat` 的 `bo` 与 `b`（2.1）。
3. **看设备侧**：`iostat -x 1` 的 `await` 与 `aqu-sz`——两者都高说明请求在设备队列里排队；再看 `%util` 与设备类型（云盘、机械盘、本地 NVMe 的合理区间完全不同）。
4. **看是谁在写**：`pidstat -d 1` 找发起写的进程；再看应用的写模式（每次几个字节、是否每笔都 `fsync`、批量提交大小）。

**一份合格的回答**

- 结论一句话：这是**写路径**问题，瓶颈在设备排队或回写/写模式，不是内存不足。
- 依据：`available` 与 PSI 正常、`b` 持续 ≥1、`wa` 高、`await`/`aqu-sz` 高、`Dirty` 与阈值的距离。
- 边界：如果 `Dirty` 已贴住 `dirty_bytes`/`dirty_ratio` 阈值，那么瓶颈是**回写限速**而不是设备本身——此时调低上限并不会更快（见判例篇）；如果 `await` 很低而写仍慢，要看应用是不是在等锁或等 `fsync`。
- 动作：按设备、回写参数、写模式三条线分别给方案；明确说明不会先做的动作（`drop_caches` 让数字好看）。

### 场景五：服务运行两周，常驻集从 800 MiB 涨到 2.4 GiB

**背景**：一个 Go 服务重启后常驻集回落，两周后又涨到 2.4 GiB；业务请求量没有明显变化；`/proc/<pid>/status` 里 `RssAnon` 占大头。服务自己带内存池与本地缓存，开发认为"这是正常的缓存增长"。

**排查顺序**

1. **按口径采样**：固定口径、带时间戳、按小时或按天取 `VmRSS`/`RssAnon`/`RssFile`/`RssShmem`（2.4）；容器里取 `memory.current`（2.5）。
2. **看形状**：阶梯式上涨且重启后重来一遍 → 像泄漏或缓存无上限；平台期或与请求量同比例增长 → 更像正常增长。
3. **看构成**：`RssAnon` 主 → 应用数据/缓存池；`RssFile` 主 → 文件缓存（压力下可回收，不必处理）；`RssShmem` 主 → 查 tmpfs 与共享内存。
4. **对照外部因素**：是否伴随连接数、队列长度、并发请求上涨；有没有新上线的功能或配置变更。

**一份合格的回答**

- 结论一句话：是**泄漏**、**无上限的缓存**，还是**与业务量同步的正常增长**——三者的处置完全不同。
- 依据：同口径多条曲线、构成拆分（`RssAnon`/`RssFile`/`RssShmem`）、重启后的回落幅度、与业务指标的对照。
- 边界：单次快照与单次 `top` 都不能作为依据；如果 `RssFile` 占大头，即使常驻集很大也不一定是问题。
- 动作：先加趋势监控与构成监控，再决定"改配置、灰度重启、还是抓 profile 排查"；运维侧能做的止损是限制上限并留证，而不是替应用改代码。

### 场景六：容器里写 `/dev/shm` 报空间不足，宿主却很空

**背景**：一个做图像处理的容器在写共享内存时失败，应用日志报 `No space left on device`；宿主 `MemAvailable` 充足，磁盘也没满。

**排查顺序**

1. **确认是哪一个"空间"**：容器内 `df -h /dev/shm`；`/dev/shm` 是 tmpfs，它占的是内存、但有自己的大小上限（很多环境默认很小）。
2. **看内核侧**：宿主 `grep Shmem /proc/meminfo` 看整机共享内存用量；容器侧按 2.5 看 `memory.stat` 里共享内存相关项与 `memory.current`。
3. **看配额**：容器/服务的 `memory.max` 是否被共享内存推高而触发限额。

**一份合格的回答**

- 结论一句话：这是**共享内存的容量上限**问题，不是整机内存不足，也不是磁盘满。
- 依据：容器内 `df -h /dev/shm` 的使用率、宿主 `Shmem` 的数值、cgroup 的用量与上限。
- 边界：`ENOSPC`（空间不足）、`EDQUOT`（配额超出）、`EROFS`（只读文件系统）是三个不同的 errno，报错文本相近但原因不同。
- 动作：调整 tmpfs 大小或改用文件/流式处理，并说明这是配置变更、需要评估内存占用。

### 场景七：swap 一周来一直在动，P99 抖动

**背景**：一台 32 GiB 的缓存服务，配了 8 GiB swap；`sar` 显示一周内 `si`/`so` 稳定在几百 KiB/s，业务 P99 从 5 ms 抖到 40 ms；`MemAvailable` 约 5 GiB；`pgmajfault` 每小时稳定增长。团队里有人主张直接 `swapoff`。

**排查顺序**

1. **判断是不是 thrashing**：`vmstat 1` 从第二行起看 `si`/`so` 是否**同时**持续非 0（2.1）；`pgmajfault` 取差值；PSI 三个尺度是否同时抬头（2.2）。
2. **看谁被换出**：`ps -eo pid,comm,rss --sort=-rss | head` 与 `/proc/<pid>/status` 的 `VmSwap`（2.4）——是服务本身，还是某个次要进程。
3. **看策略**：`sysctl vm.swappiness`（权重而非开关）、是否启用 zram/zswap、swap 设备是什么介质（机械盘上的 swap 抖动会非常明显）。
4. **评估动作的代价**：关闭 swap 会把"变慢"换成"被杀"；正确方向是缩小工作集、加内存、或把不该被换出的页保护起来。

**一份合格的回答**

- 结论一句话：是"工作集大于可用内存导致持续换页"，还是"回收倾向不当造成不必要的换出"。
- 依据：`si`/`so` 是否同时非 0、`pgmajfault` 增量、PSI 三个尺度、`VmSwap` 集中在谁身上。
- 边界：`si`/`so` 偶尔非 0 但 PSI 接近 0，说明换出没有影响任务，不必动手；`swappiness=0` 不等于禁用 swap。
- 动作：给出"缩工作集 / 扩容 / 调回收倾向 / 评估关 swap"的优先级，并说明关 swap 之后 OOM 风险会上升。
## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 直接看 `vmstat` 第一行 | 那是自开机以来的平均值，判断当下要从第二行起 |
| 用单行 `b` 或单次 `si`/`so` 下结论 | `b` 要看连续多行；换页要看趋势与 `pgmajfault` 增量 |
| 「`free` 小 = 内存不够」 | 判据是 `available` 与压力指标；完全空闲小通常是缓存在干活 |
| 用 `free` 的 `used` 当"已用内存" | 该列口径随 procps 版本变化；对账要去读 `/proc/meminfo` 原始字段 |
| 把 cgroup 文件的数值当 kB | cgroup 里是**字节**；`536870912` 是 512 MiB |
| 事后才去读 `memory.events` | cgroup 目录随单元结束被回收，账本只在存活期间存在 |
| 在容器里用宿主的 `free` 判断容器内存 | 容器的账在 cgroup 里 |
| 把 `Cached` 全当成文件缓存 | `Cached` 包含 `Shmem`；tmpfs 占用看起来像缓存 |
| 只看 `Slab` 总和不看 `SUnreclaim` | 可回收的部分会随压力释放，只有不可回收的才是长期占用 |
| 一次采样就下结论 | 缓存涨落会让单点读数误导；泄漏判断必须看趋势 |

## 要点自测

**问：`vmstat 1 5` 输出五行，哪一行能反映"现在正在发生什么"？为什么？**
答：从第二行起。第一行是自开机以来的平均值，`vmstat` 的手册写明了这一点；把首行当成现状是最常见的误读。

**问：`vmstat` 里 `b` 列出现 1，能说明有进程被 IO 按住吗？**
答：不能。单行 `b=1` 可能只是瞬时；要看连续多行是否都 ≥1，并配合 `wa` 与 `bi`/`bo`。若 `b` 持续 ≥1 且 `wa` 高，才说明有进程真的在等 IO。

**问：同事说"这台机器内存不够"，你的前三步是什么？**
答：① 定"够不够"——`MemAvailable` 与 PSI；② 看"正在发生什么"——`vmstat` 从第二行起读 `si`/`so`/`b`/`wa`，并取 `pgmajfault` 差值；③ 定位"谁在用"——按常驻集排序并看构成，最后补齐 tmpfs、内核对象与 cgroup 三处漏账。

**问：`memory.current` 显示 536870912，这是多少？为什么容易读错？**
答：512 MiB。cgroup 文件的单位是字节，而 `/proc/meminfo` 用 kB——两套习惯混着读就会把 512 MiB 看成几百 GiB。

**问：`memory.events` 里 `max 707` 而 `oom_kill 0`，说明什么？**
答：这个 cgroup 撞过上限 707 次，但每次都靠回收或节流化解了，没有真的杀进程。`oom_kill` 非 0 才说明杀过人。

**问：为什么"内存缓慢增长"不能靠一次 `top` 判断？**
答：缓存会涨落、业务有峰谷，单点读数无法区分"持续上涨"与"刚处理完一批数据"。要同口径、带时间戳、按小时或按天取样，并看构成（`RssAnon`/`RssFile`/`RssShmem`）。

**问：给一个现场场景——"K8s 节点还有 5 GiB 可用，某个 Pod 却反复 OOMKilled"，你的回答结构是什么？**
答：先说结论方向——撞的是 **cgroup 上限**而不是整机水位（宿主可用内存不能用来否定容器 OOM）。再给依据：内核日志里 `constraint=CONSTRAINT_MEMCG` 与 `oom_memcg=` 指向的 cgroup、该 cgroup 的 `memory.max` 与 `memory.peak`、`memory.events` 的 `oom_kill`、以及 `memory.stat` 里 `anon`/`file`/`slab` 的构成。然后说边界：如果节点自身也在回收与换页，结论要改成整机压力传导；如果 `file` 占大头，说明是页缓存计入额度而非应用真的用了这么多。最后给动作：按峰值与历史曲线定新上限，走变更流程并写清验证与回滚；不会直接翻倍了事。
