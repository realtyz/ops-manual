> [!warning] 前置纪律
> 实验 0 全部只读、零风险，**可以在生产机上执行**；实验 1、2、4、5、6、7、8、9 需要 root，但**全部作用在 loop 文件上**，不碰真盘；实验 3 会改 `/etc/fstab`，**只在可快照的实验机上做**。

## 1. 实验 0：只读基线（零风险，先做这个）

```bash
date; hostname; uname -r; cat /etc/os-release | head -2
                                     # 验证：时间与版本（决定默认值与行为差异）
lsblk -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINT,ROTA,MODEL,SERIAL,UUID
                                     # 验证：设备 → 分区 → 文件系统 → 挂载点 + 身份
df -hT; df -i                        # 验证：容量与 inode 两个视角（ext4 必看 inode）
findmnt -o TARGET,SOURCE,FSTYPE,OPTIONS
                                     # 验证：挂载参数（ro？nofail？_netdev？noatime？）
sudo pvs; sudo vgs; sudo lvs; cat /proc/mdstat
                                     # 验证：有 LVM/RAID 时的池与阵列结构（无输出即表示没有）
cat /sys/block/<dev>/queue/scheduler; cat /sys/block/<dev>/queue/rotational
                                     # 验证：调度器与介质类型（0=SSD/NVMe、1=机械盘）
sudo smartctl -H /dev/<dev>; sudo nvme list
                                     # 验证：健康总判定与 NVMe 设备清单
sysctl fs.file-max fs.nr_open fs.inotify.max_user_watches fs.inotify.max_queued_events
                                     # 验证：句柄与 inotify 的容量边界（子笔记 15）
sudo tune2fs -l /dev/<dev> | grep -E 'Block count|Reserved block count|Inode count|Filesystem state'
                                     # 验证：ext4 的块数、预留块、inode 总数与干净状态
```

**预期**：得到一份能回答「有几块盘、什么介质、怎么分区/组池、挂在哪、还剩多少、健康如何」的基线卡；`df -h` 与 `df -i` 各自给出独立结论；有 LVM/RAID 的机器会多出池与阵列的信息。

**环境**：任意发行版，**以 root 或带 `sudo` 执行**（`pvs`/`smartctl` 需要权限）。虚拟机上 `smartctl` 可能拿不到真实数据，属于正常。

**风险**：无，全部只读。

**耗时**：约 20 分钟。

**回滚**：无需回滚。把输出存成一份基线文件，例如 `/root/storage-baseline-$(date +%F).txt`。

## 2. 统一清理（实验做乱或中断时先跑这一段）

```bash
for d in /mnt/lab /mnt/labinode /mnt/lvmdata /mnt/quota /mnt/rootcheck /mnt/probe; do
    mountpoint -q "$d" && sudo umount "$d"
done                                 # 验证：卸载所有实验挂载点（未挂载的会被跳过）
sudo lvremove -f vglab/snapdata vglab/lvdata 2>/dev/null; sudo vgremove -f vglab 2>/dev/null
sudo lvremove -f vgquota/lvquota 2>/dev/null; sudo vgremove -f vgquota 2>/dev/null
                                     # 验证：清理实验用的 LVM 结构
sudo losetup -a | grep '/tmp/lab-' | cut -d: -f1 | xargs -r -n1 sudo losetup -d
                                     # 验证：只分离本实验的环设备（按文件名过滤）
rm -f /tmp/lab-*.img                 # 验证：删除实验用镜像文件
sudo losetup -a | grep '/tmp/lab-'   # 验收：没有输出即为干净
```

> [!warning] 不要用 `losetup -D`
> `losetup -D` 会分离系统里**所有**环设备——Ubuntu 的 snap 包正是靠 loop 设备挂载的，执行它可能直接弄坏系统。清理必须按文件名过滤。

## 3. 训练台阶对照与交付物

| 台阶 | 做完哪些实验 | 你应该能交出什么 |
| --- | --- | --- |
| **T0 读通** | 不需要动手 | 一张自己画的「裸盘 → 分区/池 → 文件系统 → 挂载点」图 |
| **T1 观测** | 实验 0、1、2 | 存储基线卡（含设备身份、容量与 inode、挂载参数、健康） |
| **T2 可回滚变更** | 实验 1、3、4、7 | 变更记录：每条都含「改前取值 / 改了什么 / 怎么验收 / 怎么回滚」 |
| **T3 故障注入与恢复** | 实验 3、5、6、8、9 | 演练记录：现象 → 证据 → 根因 → 动作 → 验收 |
| **T4 限时模拟** | 演练（子笔记 16） | 一份 10 分钟内写出的排障报告 |

### 技能交付物清单（M1–M8）

- [ ] **M1 存储基线卡**：设备（型号/序列号/ROTA）、分区与池、文件系统（类型/UUID/块大小/inode）、挂载（参数）、健康（SMART）、容量与 inode 水位。
- [ ] **M2 空间对账表**：把一次「写不进去」拆到容量、inode、保留块、配额、只读、挂载覆盖六类，每类附证据命令。
- [ ] **M3 挂载变更记录**：一条 fstab 改动的原文、`findmnt --verify` 与 `mount -a` 输出、回滚方式。
- [ ] **M4 扩容作业记录**：`lsblk` → `growpart`/`vgextend` → `lvextend -r` → `df` 的完整链路与验收。
- [ ] **M5 配额策略**：目录 ↔ 项目 ID ↔ 业务方 ↔ 软硬限 ↔ 监控阈值 ↔ 变更时间。
- [ ] **M6 IO 基线卡 + 判读记录**：`fio` 条件与结果（含延迟分位）、同段 `iostat` 输出、一次「排队 vs 设备退化」的判读。
- [ ] **M7 只读故障处置记录**：取证 → 停止写入 → 卸载 → 干跑 → 备份 → 修复 → 只读核对 → 恢复写。
- [ ] **M8 换盘 Runbook + 巡检台账**：每周 SMART、每日内核日志与阵列状态、换盘六步、台账字段。

## 4. 综合自测

> [!question]- 你有三块「新」数据盘要接入，动手前必须确认哪三件事？各自的命令是什么？
> - 是不是这块盘（`lsblk -o NAME,SIZE,MODEL,SERIAL`、`/dev/disk/by-id/`）。
> - 上面有没有东西（`wipefs -n`、`blkid`、`parted print`）。
> - 有没有人在用（`findmnt`、`fuser -vm`、`lsof +D`、`dmsetup ls --tree`）。
> - **第一反应不要是什么**：不要因为「工单上写的是新盘」就跳过第二问。

> [!question]- ext4 与 XFS 该怎么选？关键差异各是什么？
> - 看三个问题：会不会缩容（要缩只能 ext4，且停机）、文件多不多（海量小文件用 XFS）、容量会不会很大（XFS + LVM 扩容链最顺）。
> - 关键差异：inode 固定还是动态、是否支持缩容、`resize2fs` 接设备而 `xfs_growfs` 接挂载点、修复工具与约束不同。
> - **第一反应不要是什么**：不要规划「XFS 缩容」。

> [!question]- fstab 里哪两个选项是「保命」的？为什么？
> - `nofail`：挂不上也不阻塞启动；`_netdev`：网络就绪后再挂。
> - 缺 `nofail` 会把「一块盘掉线」升级成「整机进 emergency」；缺 `_netdev` 会导致启动时等超时。
> - **第一反应不要是什么**：不要用重启验证 fstab，用 `mount -a` 与 `findmnt --verify`。

> [!question]- 云盘扩容之后，从「盘变大」到「`df` 变大」要经过哪几步？
> - `lsblk` 确认内核看到新容量 → 扩分区（`growpart` + `partprobe`）→ `pvresize` → `lvextend -r` → `df -h` 与写入测试验收。
> - **第一反应不要是什么**：不要跳过 `pvresize` 直接扩 LV，也不要把 `xfs_growfs` 的参数写成设备。

> [!question]- `df -h` 还有 40%、`du` 也查不出大文件，却写不进去，按什么顺序查？
> - 报错原文 → `df -i` → `lsof +L1` → `findmnt -T <路径>` → 保留块 → 配额 → `findmnt` 的 `ro` → `lvs` 水位。
> - **第一反应不要是什么**：不要先删文件或扩容。

> [!question]- 为什么「删了大文件空间没释放」？怎么处理？
> - 进程还持有该文件的句柄；inode 链接数为 0 但数据块没有释放。
> - `lsof +L1` 找持有者，重启或重载该进程释放；极端情况下才考虑截断 `/proc/<pid>/fd/<n>`。
> - **第一反应不要是什么**：不要以为「再删一遍」有用。

> [!question]- 文件系统变只读，处置顺序是什么？为什么不能重挂可写？
> - 取证 → 判断根因（介质还是元数据）→ 停止写入 → 卸载 → 干跑 → 备份 → 修复 → 只读核对 → 恢复写。
> - 只读是内核的保护动作，**但前提是显式配了 `errors=remount-ro`**（ext4 默认是 `errors=continue`，默认不会因出错自动重挂只读，本机实测 `tune2fs -l` 为 `Continue`）；重挂可写会让损坏继续扩大。
> - **第一反应不要是什么**：不要 `mount -o remount,rw`。

> [!question]- `iostat` 里 `await` 高了，怎么判断是「排队」还是「设备退化」？
> - `await` 与 `aqu-sz` 同涨 = 排队；`await` 涨而队列浅 = 设备或链路慢。
> - 单队列设备上 `%util ≈ 100%` 有意义；NVMe 上要看延迟分位与队列深度。
> - **第一反应不要是什么**：不要只看 `%util` 或只看 `await` 就换盘。

> [!question]- RAID5 在大容量盘上的风险是什么？RAID 能替代备份吗？
> - 重建要读全部成员盘，期间遇到不可恢复读错误即失败；按 URE 1 次/10¹⁴ 比特估算，10TB 量级的失败风险在数十个百分点。
> - RAID 只防盘坏，不防误删、勒索加密、逻辑损坏与机房级故障。
> - **第一反应不要是什么**：不要把「有冗余」当成「有备份」，也不要在重建期间上高压力业务。

> [!question]- 配额到顶报什么错误？为什么说「配额必须配监控」？
> - 报 `Disk quota exceeded`（`EDQUOT`），不是 `No space left on device`。
> - 没有监控的配额只是把「写满整盘」换成「写满自己的配额」，业务照样挂。
> - **第一反应不要是什么**：不要在 XFS 上只 `enable` 而不在挂载时加 `prjquota`。
