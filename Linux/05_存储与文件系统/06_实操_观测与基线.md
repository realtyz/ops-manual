# 观测与基线

## 1. 一个问题，一把工具

| 你想知道 | 用什么 | 关键字段或文件 |
| --- | --- | --- |
| 这台机器有几块盘、什么介质、什么型号 | `lsblk -d` | `NAME`、`SIZE`、`ROTA`、`MODEL`、`SERIAL` |
| 设备 → 分区 → 文件系统 → 挂载点的对应关系 | `lsblk` | `TYPE`、`FSTYPE`、`MOUNTPOINT`、`UUID` |
| 这个文件系统还剩多少空间 | `df` | `Size`、`Used`、`Avail`、`Use%` |
| 这个文件系统的 inode 还剩多少 | `df -i` | `Inodes`、`IUsed`、`IFree`、`IUse%` |
| 某个文件「声称」多大、实际占多少块 | `ls -l`、`stat`、`du` | `Size`、`Blocks`、`--apparent-size` |
| 空间被哪些目录吃掉了 | `du -x` | 各层目录的合计 |
| 有没有「已删除但仍被进程持有」的文件 | `lsof +L1` | 进程、PID、大小、路径 |
| 某个路径实际落在哪个挂载点 | `findmnt -T` | `TARGET`、`SOURCE`、`FSTYPE` |
| 当前挂载参数（是否只读、有没有 `nofail`） | `findmnt`、`/proc/mounts` | `OPTIONS` |
| 有没有 LVM、池水位如何 | `pvs`、`vgs`、`lvs` | 卷大小、`data_percent`、`metadata_percent` |
| 有没有软阵列、是否降级、重建进度 | `/proc/mdstat`、`mdadm --detail` | 成员盘标记、重建百分比与速度 |
| 设备类型、调度器、队列深度、预读 | `/sys/block/<dev>/queue/*` | `rotational`、`scheduler`、`nr_requests`、`read_ahead_kb` |
| 设备级 IO 速率与延迟 | `iostat -x` | `await`、`aqu-sz`、`%util`、请求大小 |
| 哪个进程在打 IO | `iotop -oPa`、`pidstat -d` | 进程级读写速率 |
| 某进程真实落盘了多少 | `/proc/<pid>/io` | `read_bytes`、`write_bytes` |
| 配额用量与软硬限 | `xfs_quota -x -c 'report -h'`、`repquota -a` | 用量、软限、硬限、宽限期 |
| 磁盘健康与寿命 | `smartctl -a`、`nvme smart-log` | 重映射、待处理扇区、寿命消耗、备用块 |
| 内核有没有报存储错误 | `dmesg -T`、`journalctl -k` | 介质错误、IO 错误、控制器重置 |
| 句柄与 inotify 上限 | `sysctl fs.*`、`/proc/<pid>/limits` | `file-max`、`nr_open`、`inotify.*` |

表里的「用什么」分两类，**分不清就会问错地方**：**命令**（`lsblk`、`df`、`du`、`iostat`、`smartctl`……文档在 `man 1` 或 `man 8`）与**内核接口文件**（`/proc/*`、`/sys/*`，直接读就有数据，不需要装任何工具）。判断规则是看文档节号：`man 1` 是命令、`man 2` 是系统调用、`man 3` 是库函数、`man 5` 是文件格式、`man 8` 是管理命令。

一条实用推论：**没装工具不等于看不到**。设备清单与 IO 累计计数都在 `/proc` 与 `/sys` 里；`iostat` 只是把 `/proc/diskstats` 的累计值换算成速率与延迟。

## 2. 怎么读这些数字

下面每一条都给全六件事：**这个数字是什么**、**单位是什么**、**多少算异常**、**和谁一起看**、**看到它转向哪一步**、**什么条件下结论会变**。示例输出中的数值仅用于展示格式。
### 2.1 `df`：容量与 inode 是两个视角

```bash
df -hT /data; df -i /data            # 验证：容量视角与 inode 视角必须同时看
df -B1 /data                         # 验证：以字节为单位输出，避免进制歧义
```

```text
Filesystem                        Type  Size  Used Avail Use% Mounted on
/dev/mapper/vg0-lv_data           xfs   500G  310G  191G  62% /data
Filesystem                        Inodes  IUsed  IFree IUse% Mounted on
/dev/mapper/vg0-lv_data          26214400 26214400     0  100% /data
```

- **`Use%` 与 `IUse%` 要一起看**。上面这组数字就是「有空间却写不进去」的典型现场：容量还剩 38%，inode 已经 100%。**只报容量一定会漏掉这一类故障。**
- **`Avail` 不等于 `Size − Used`**。差额来自元数据、区块对齐，以及 ext4 为 root 保留的比例（`tune2fs -l` 的 `Reserved block count`；现场取值）。普通用户看到的是 `Avail`，root 能看到更多——「root 能写而普通用户不能写」就是它的指纹。
- **`df -h` 用 1024 进位（GiB），`df -H` 用 1000 进位（GB）**。与厂商标称、云控制台对齐时用后者；写台账做精确对账时用 `-B1` 的字节数。
- **`df` 只回答「文件系统的账本还剩多少」**，不回答「文件在哪」。`df` 卡住通常说明挂载点的底层不通（网络存储不可达），这是另一个方向的问题。

### 2.2 `du`、`ls -l`、`stat`：三个大小口径

```bash
du -xh --max-depth=1 /data | sort -rh | head    # 验证：按目录看占用（-x 不跨文件系统）
du -h --apparent-size /data/bigfile; du -h /data/bigfile
                                                # 验证：表观大小 vs 实际占用
stat /data/bigfile                              # 验证：Size（表观）与 Blocks（512B 块数）同屏对照
```

- **`du` 统计的是实际分配的块数**，因此稀疏文件与压缩/去重文件系统上它会明显小于表观大小；小于一个块的文件也会占满一块。
- **`du -x` 的 `-x` 不可省**：跨文件系统统计会把别的盘算进来，彻底破坏「这个盘用了多少」的结论。
- **`du` 看不到两类东西**：被挂载覆盖的目录（遍历不到）与已删除但仍被持有的文件（已不在目录树里）。这正是「`df` 与 `du` 对不上」的两大来源。
- **判断泄漏或增长要用趋势**：同一口径、带时间戳、至少两次采样。单次 `du` 只能说明「现在是多少」。

### 2.3 `lsof +L1`：找出「删了但没释放」的持有者

```bash
sudo lsof +L1 2>/dev/null | head    # 验证：链接数为 0（已删除）但仍被打开的文件
```

- **`+L1` 的语义是「链接数小于 1」**，即目录树里已经没有这个名字。输出的每一行是一个仍持有该文件的进程。
- **判据与动作**：确认是自己的业务进程后，重载或重启它即可释放；**紧急截断句柄（写入 `/proc/<pid>/fd/<n>`）会带来数据风险**（写入空洞、日志错位），只在评估过风险、确无其他办法时用。
- **和它一起看**：`df` 的用量在进程结束后是否下降（这是验证），以及 `/proc/<pid>/fd` 里是否还有别的 deleted 句柄。

### 2.4 `findmnt`：先确认「写到哪里」

```bash
findmnt -T /var/log                 # 验证：这个路径实际属于哪个文件系统与挂载点
findmnt -o TARGET,SOURCE,FSTYPE,OPTIONS
                                    # 验证：当前全部挂载关系与生效参数
```

- **`findmnt -T <路径>` 是「这个目录还剩多少空间」这类问题的第一问。** 目录名不携带文件系统信息：`/var/log` 可能就在根分区上。
- **`/etc/fstab` 是期望，`/proc/mounts` 与 `findmnt` 是实际**。两者不一致是正常的（自动挂载、手动挂载、挂载失败），排障时**以实际为准**。
- **`OPTIONS` 里的 `ro`、`nofail`、`_netdev`、`noatime` 要逐个确认**：看到 `ro` 说明系统已经检测到错误（保护动作），方向是取证而不是恢复写入。

### 2.5 池与阵列：水位和成员状态

```bash
sudo lvs -o+lv_size,data_percent,metadata_percent   # 验证：thin pool 的数据与元数据水位
sudo lvs -a -o+seg_monitor                          # 验证：是否有监控进程在盯着池子
cat /proc/mdstat                                    # 验证：阵列状态、成员盘与重建进度
sudo mdadm --detail /dev/md0 | head -30             # 验证：级别、成员、chunk、bitmap、状态
```

- **`data_percent` 与 `metadata_percent` 必须一起看**。元数据写满比数据写满更难处理；两者任一到 100% 都会波及池内所有卷。
- **判据**：池水位应当有告警阈值并留余量（例如 80% 告警）。**「省空间」是把超配比例拉满的唯一收益，代价是全组故障。**
- **`/proc/mdstat` 的成员标记**：`[U]` 表示在线、`[_]` 表示缺失或降级；附带的重建进度与速度给出窗口还有多长。
- **重建期要限速**：软阵列的速度上下限在 `/proc/sys/dev/raid/speed_limit_*`（单位 KB/s，现场取值）。**不限速的重建会打满带宽，让业务延迟明显恶化。**

### 2.6 `iostat -x`：每一列怎么读

```bash
iostat -x 1 5                       # 验证：每秒采样的扩展指标；第一行是自开机以来的平均值
iostat -x -d /dev/sda 1 5           # 验证：只看某一块盘（多盘机器上更清晰）
```

```text
Device   r/s     w/s   rkB/s   wkB/s  r_await w_await aqu-sz  rareq-sz wareq-sz  %util
sda     12.0    48.0   384.0  2048.0     0.80    9.60   0.72     32.0     42.7   4.10
```

- **`await` 是平均完成时间，单位毫秒，并且包含排队时间**。这是它最容易被误读的地方：`await` 高不等于设备坏。**判据必须成对使用，见下面的组合表。**
- **`aqu-sz` 是平均队列深度**（未完成请求数），旧版本叫 `avgqu-sz`。它回答「有多少请求在排队」。
- **`%util` 是设备忙于处理 IO 的时间比例**。它在单队列设备上接近 100% 基本等于饱和；**在多队列设备（NVMe 典型）上经常接近 100% 却远未饱和**，参考价值有限。
- **`r_await` 与 `w_await` 分开看**：读慢与写慢的根因经常不同——写还牵涉回写与阵列缓存策略。
- **`rareq-sz`/`wareq-sz` 是平均请求大小**，用来区分随机小 IO（4 KiB 级）与顺序大 IO（1 MiB 级）。
- **`svctm` 已废弃**：工具文档已标注它不可靠，**不要再用它下结论**。
- **`iostat` 的第一行是自开机以来的平均值**，判断「现在正在发生什么」必须从第二行起看。

组合判读（比任何单列都可靠）：

| 你看到 | 判读 | 下一步 |
| --- | --- | --- |
| `await` 高 + `aqu-sz` 高 + 单队列设备 `%util` 高 | **排队**：请求量超过设备处理能力 | 找源头进程、错峰、限流、加并行设备 |
| `await` 高 + `aqu-sz` 低 | **设备或链路本身慢**：请求不多但要很久 | 查介质健康、阵列缓存与电池、网络存储链路 |
| 写 `await` 高 + 脏页高 | **回写链**：脏页积压 | 看写入速率与回写参数，而不是换盘 |
| `r/s` 高、`rareq-sz` 小 | 随机小读为主 | 看缓存命中与设备随机能力 |
| `wkB/s` 高、`wareq-sz` 大 | 顺序大写为主 | 看带宽与回写 |
| `await` 与 `aqu-sz` 都正常但业务仍慢 | 瓶颈不在设备侧 | 往上查应用、缓存与元数据操作 |

### 2.7 下钻：从设备到进程到文件

| 顺序 | 工具 | 回答的问题 |
| --- | --- | --- |
| 1 | `iostat -x` | 哪块盘、读还是写、随机还是顺序、延迟与队列 |
| 2 | `iotop -oPa`、`pidstat -d` | 哪个进程在打 IO |
| 3 | `lsof -p`、`/proc/<pid>/io` | 这个进程读写的是哪些文件 |
| 4 | 请求级追踪工具 | 请求在每一阶段花了多久、延迟分布如何 |
| 5 | `dmesg -T`、`smartctl` | 底层有没有介质错误或链路告警 |

- **`/proc/<pid>/io` 里要看 `read_bytes`/`write_bytes`**：它们才是**真正走到块设备层**的字节数；`rchar`/`wchar` 统计的是应用请求的字节数，包含命中缓存的部分。判断「谁把盘打满」用前者，判断「谁在频繁读写」用后者。
- **`iotop -a` 是累计值**，实时判断要用默认模式或速率类工具的输出。

### 2.8 健康与内核日志

```bash
sudo smartctl -H /dev/sda                  # 验证：健康总判定（PASSED/FAILED）
sudo smartctl -a /dev/sda | grep -E 'Reallocated|Pending|Offline_Uncorrectable|CRC'
                                           # 验证：机械盘/SATA SSD 的四个关键计数
sudo nvme smart-log /dev/nvme0             # 验证：NVMe 的寿命、备用块与完整性错误
dmesg -T | grep -i -E 'medium error|I/O error|nvme.*(reset|down)'
                                           # 验证：内核侧的介质与控制器告警（换盘决策的直接证据）
```

- **判据是趋势不是单值**：重映射扇区计数**持续增长**才是信号；待处理扇区大于 0 要重点关注；传输校验错误通常指向线缆、背板或接口，而不是盘本身。
- **NVMe 的寿命字段**超过厂商阈值、完整性错误非 0，都要立刻处理。
- **内核日志通常比健康计数更早出现**：介质错误与 IO 错误一旦出现，就应当进入换盘评估，而不是等阵列降级或文件系统只读。

### 2.9 非空间的「满」：句柄与 inotify

```bash
grep -E 'Max open files' /proc/<pid>/limits   # 验证：运行中进程实际生效的软/硬限制
ls /proc/<pid>/fd | wc -l                     # 验证：该进程当前打开了多少 fd
cat /proc/sys/fs/file-nr                      # 验证：已分配 / 空闲 / 全系统上限
sysctl fs.file-max fs.nr_open fs.inotify.max_user_watches fs.inotify.max_user_instances fs.inotify.max_queued_events
                                              # 验证：计数类上限的当前值（一律现场取）
```

- **`/proc/<pid>/limits` 比 `ulimit` 准**：前者是**运行中进程实际生效**的值，后者是当前 shell 的值。服务类进程由单元属性决定，与登录会话是两套。
- **`/proc/sys/fs/file-nr` 的三个数字**是「已分配 / 空闲 / 上限」；第一列接近第三列就要警惕。
- **`max_queued_events` 的溢出是静默的**：它不会让调用失败，只会丢事件。监控类应用出现「漏报但不报错」时优先查它。

### 2.10 采样纪律与基线卡

单点读数说明不了任何问题。四条纪律：

1. **同口径**：同一命令、同一单位、同一进制；`df -h` 与 `df -H` 的数字不能直接比。
2. **带时间戳**：每条读数都记采集时间，否则趋势无法建立。
3. **至少两次**：判断「现在正在发生什么」至少要两行（工具的第一行是累计平均值）；判断趋势按小时或按天取样。
4. **留原始输出**：不要只抄一个数字，抄数字等于丢掉上下文；原始输出才能事后复核。

一份可复用的存储基线卡至少要有五组内容：

```text
【环境】采集时间 · 主机名 · 发行版与版本 · 内核版本
【身份】每块盘：设备名 · 型号 · 序列号 · 槽位 · 容量 · 介质类型
【结构】分区表类型与分区 · LVM/RAID 成员与级别 · 文件系统类型 · UUID · LABEL · 块大小 · inode 总量
【水位】容量使用率 · inode 使用率 · 池的数据与元数据水位 · 配额用量
【挂载】挂载点 · 挂载参数（ro / nofail / _netdev / noatime / errors=）
【健康】各盘健康总判定与关键计数 · 阵列状态
【边界】句柄与 inotify 上限 · 服务侧的限制属性
```

**缺一项，半年后这份数据就不可比。** 尤其是「身份」与「挂载参数」：容量数字随时在动，而型号与参数决定了这些数字在什么条件下才成立。

### 2.11 几个值得亲手造一次的现场

下面五个实验的目的不是「跑通命令」，而是**把机制变成一个自己见过的现场**。它们全部作用在**用普通文件模拟出来的块设备（loop 设备）**上，不碰真盘；容器里缺设备节点与权限，**做不了**，要在虚拟机里做。每个实验只给做法、判据与边界。

| 实验 | 做法 | 判据（要亲眼看到的） | 边界与回滚 |
| --- | --- | --- | --- |
| inode 耗尽 | 在一个小文件系统上把 inode 密度调到很低，然后不停创建空文件 | 容量还剩很多而 inode 到 100%，创建失败报 `ENOSPC` | 只在 loop 文件上；用完卸载、分离环设备、删文件 |
| 空间不释放 | 写一个大文件，让一个进程打开它，再删除它 | 用量不下降、目录里找不到它、只有查进程句柄能看到 | 结束持有进程后用量应立即下降；截断句柄有数据风险，实验中用结束进程的方式 |
| 被挂载覆盖 | 在一个有内容的目录上挂载另一个文件系统 | 原内容看不到，从上层绑定挂载能看到 | 用完立刻卸载；**不要在被遮住的目录里创建同名文件** |
| 在线扩容 | 在池上建卷与文件系统，再给池加空间并在线扩大 | 全程未卸载，业务侧容量变大；快照的用量随原卷写入上升 | 扩容无法回退（容量已经给出去）；快照用完立刻删除 |
| 配额写穿 | 以配额选项挂载，给一个目录设很小的硬限，然后写到被拦下 | 写入在限额处停下，报的是 `EDQUOT` 而不是 `ENOSPC` | 需要配额工具链；只在 loop 文件上做 |

**清理纪律**：实验会留下挂载点、卷池结构与环设备。清理时**不要用「分离全部环设备」的粗暴写法**——发行版的软件包正是靠环设备挂载的，执行它可能直接弄坏系统；要按文件名过滤，只分离自己创建的。

## 3. 常见故障与排查方向

### 3.1 写入报「空间不足」，但容量还剩很多

**场景**：一台 4 vCPU、16 GiB 内存的日志采集节点，数据盘 1 TiB（ext4 on LVM）。16:40 起采集器持续报写入失败，原文是 `No space left on device`。值班看到 `df -h /data` 是 `Use% 61%`，`du -sh /data` 只有 300 GiB。

**排查顺序**：

1. **看报错原文**——是 `No space left on device`、`Disk quota exceeded` 还是 `Read-only file system`。三者方向完全不同。
2. **确认写入路径**：`findmnt -T <采集器的输出目录>`。**如果它落在根分区而不是 `/data`，「给日志盘留了 1 TiB」这个前提从一开始就不成立。**
3. **两个视角一起看**：`df -h /data` 与 `df -i /data`。inode 满是最常见的「有空间写不进去」。
4. **找持有者**：`lsof +L1`。已删除但仍被持有的文件让 `df` 不降、`du` 找不到。
5. **看保留块**：`tune2fs -l /dev/<dev>` 的 `Block count` 与 `Reserved block count`（比例现场算）。**root 能写而普通用户不能写是它的指纹。**
6. **看配额与池水位**：配额报表、`lvs -o+data_percent,metadata_percent`。
7. **看只读**：`findmnt -o OPTIONS` 里有没有 `ro`，以及 `dmesg -T | tail`。

**一份合格的回答长什么样**：

- **结论**：一句定性——「inode 耗尽」/「已删除但被持有」/「写到了别的文件系统」/「配额到顶」/「文件系统只读」。
- **依据**：支撑结论的那几条命令输出（原文，不是转述），并说明每条排除掉了什么。
- **边界**：这个结论在什么条件下会变（例如「若 inode 使用率继续上升，一周内会复发」）。
- **动作**：短期止血（清理/重载进程/调整）、长期治理（换文件系统/重建/补监控）、以及验收方式。

**第一反应不要做什么**：不要因为「还有 61% 空间」就否掉磁盘方向；不要在没看 `df -i` 之前先删文件（删文件对 inode 满最多只有一点点用，对写错挂载点完全无用）；不要在没确认根因前扩容。

### 3.2 IO 变慢，设备侧指标很高

**场景**：同一台节点，17:20 起采集器写入延迟从 2 ms 涨到 45 ms。`iostat -x` 显示数据盘 `await` 45 ms、`aqu-sz` 32、`%util` 98%。

**排查顺序**：

1. **先看组合**：`await` 与 `aqu-sz` 同涨说明**排队**（请求量超过设备能力）；`await` 高而队列浅才是**设备或链路本身慢**。**这一步决定了后面是优化业务还是换硬件。**
2. **找源头**：`iotop -oPa`、`pidstat -d`；再往下用 `lsof -p`、`/proc/<pid>/io` 的 `read_bytes`/`write_bytes` 确认是哪个文件。
3. **区分读写**：`r_await` 与 `w_await` 分开看；写慢还要查脏页与回写链（写 `await` 高 + 脏页高 = 回写积压，方向是写入模式与刷盘节奏）。
4. **排除非磁盘因素**：回写积压、网络存储链路、阵列缓存与电池状态。
5. **回到硬件**：`dmesg -T` 与健康计数，确认有没有介质问题。

**一份合格的回答**：给出「排队 / 设备退化 / 回写限速」三者中的哪一个，附上支撑它的那两三个字段及其数值趋势，说明这个判断在什么情况下会翻转，并给出对应的动作（限流、错峰、调整写入模式、或进入硬件排查）。

**第一反应不要做什么**：不要只看 `%util` 或只看 `await` 就宣布盘坏了；不要在没定位源头前调大队列深度（队列更深会让延迟更高）；不要在多队列设备上把 `%util` 接近 100% 当告警条件。

### 3.3 改完 fstab 后的验收

**场景**：给一台机器新增一块数据盘，需要在 `/etc/fstab` 加一行并确认重启后仍然成立。

**验收顺序**（**不需要重启**）：

1. **备份原文**——回滚最便宜的一步。
2. **语法与可挂载性检查**：`findmnt --verify --verbose`（只检查，不真正挂载）。
3. **让 systemd 重读**：`systemctl daemon-reload`（否则它手里的挂载单元定义还是旧的）。
4. **逐条挂载**：`mount -a`。错误会在这里立刻暴露。
5. **核对实际结果**：`findmnt -o TARGET,SOURCE,FSTYPE,OPTIONS`，确认选项（`nofail`、`_netdev`、`noatime`）真的生效。
6. **看挂载单元**：`systemctl status <挂载点对应的单元>` 与它的日志，作为失败时的第一现场。

**一份合格的回答**：改前与改后的原文、上面五步的输出、回滚方式（备份文件名或注释掉哪一行）、以及这块盘上跑什么业务、谁依赖这个挂载点。

**第一反应不要做什么**：不要用重启当验证手段——写错的 fstab 可能让机器起不来；不要在网络存储挂载上省掉 `_netdev` 与 `nofail`。

### 3.4 文件系统变成只读

**场景**：凌晨告警某挂载点写入失败，报 `Read-only file system`；`findmnt` 的 `OPTIONS` 里有 `ro`。

**排查顺序**：先取证（内核日志的相关片段、硬件健康的关键计数）→ 判断根因是**介质故障**还是**元数据损坏** → 停止写入 → 卸载 → **只读检查**（只报不改）→ 备份 → 正式修复 → 只读挂载核对 → 恢复可写。

**一份合格的回答**：根因判断（介质还是逻辑）、支撑它的证据（日志片段与健康计数）、被否决的方案与原因（例如「没有直接重挂为可写，因为只读是保护动作」）、以及恢复后如何验证数据完整性。

**第一反应不要做什么**：不要 `mount -o remount,rw`；不要在挂载状态下跑修复工具；不要在没备份时用「全部回答是」的参数；不要在介质已经有错的盘上做文件系统修复。

### 3.5 云盘扩容了，容量没有变大

**场景**：云控制台把数据盘从 500 GiB 扩到 1 TiB，机器上业务看到的可用空间没变。

**排查顺序**：从下往上逐层确认，**每一层都要单独长大**——内核是否看到设备变大 → 分区是否变大（云盘场景常见这一步被跳过）→ PV 是否感知新空间 → 池子是否有空闲 → 卷是否变大 → **文件系统是否扩大** → 业务写入是否正常。

**一份合格的回答**：整条链路上每一步的前后值，以及**业务侧的容量确实变大**这一条验收。中间任何一步没做，「扩过容」的说法都不成立。

**第一反应不要做什么**：不要在没确认内核看到新容量之前直接扩文件系统；不要跳过「PV 感知新空间」这一步；不要把扩容工具的参数写错对象（ext4 接设备、XFS 接挂载点）；**不要用重启代替中间步骤**。

### 3.6 网络存储不可达，进程堆积在不可中断睡眠

**场景**：一台应用服务器的共享目录来自网络存储。凌晨对端机房网络抖动，早上发现数百个进程停在不可中断睡眠，而且 `df`、`ls` 命令本身也会卡住；强杀无效，业务已经不可用。

**排查顺序**：

1. **确认是哪个挂载点**：命令卡住的位置、可疑的网络类挂载、停住的进程共同的路径。
2. **确认通路**：内核日志里该存储子系统与链路的相关报错、到对端的网络可达性与端口、多路径的每条路径状态、对端服务自身是否存活。
3. **优先恢复通路**：修网络、恢复对端、切路径。**通路恢复后等待状态会自行消解**，业务随之恢复。
4. **无法恢复时才谈取舍**：强制卸载或延迟卸载都有数据一致性风险，需要业务方确认；最后手段是重启，且重启前尽量保留日志与现场。
5. **长期改进**：写场景坚持硬挂载并配合理的超时与重传、挂载选项补齐「网络就绪后挂」与「挂不上不阻塞启动」、可选盘改为按需挂载、把「存储不可达」纳入演练与监控。

**一份合格的回答**：确认卡住的是哪个挂载点、通路在哪一段断的、**为什么没有选择杀进程或强卸**、恢复通路后如何验证业务回归，以及后续把哪些参数与演练补上。

**第一反应不要做什么**：不要批量强杀进程（收不到信号，还会破坏现场）；不要一卡住就强卸；不要在生产对端上做「拔线演练」；不要重启——**如果存储仍未恢复，重启后机器可能卡在启动过程中**。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 只看 `df -h` 判断能不能写 | inode、保留块、配额、只读、写错挂载点都会给出相反结论 |
| 用 `du` 的结果否定 `df` | 两者量的是不同东西；差异有四类正常原因 |
| 忽略 `du -x` | 不加 `-x` 会把别的文件系统算进来 |
| 用 `iostat` 第一行判断现场 | 第一行是自开机以来的平均值 |
| 只看 `await` 或只看 `%util` | 要看 `await` + `aqu-sz` + 请求大小的组合 |
| 继续用 `svctm` 下结论 | 工具文档已标注它不可靠 |
| 只看平均延迟 | 平均值掩盖长尾；延迟分位才是业务感知的部分 |
| 用 `/proc/<pid>/io` 的 `rchar`/`wchar` 判断落盘量 | 它们包含命中缓存的部分；落盘量看 `read_bytes`/`write_bytes` |
| 只看健康计数的单次值 | 要看趋势：持续增长才是信号 |
| 在容器里做 loop/LVM 实验 | 缺设备节点与权限；这类实验必须在虚拟机上做 |
| 网络存储挂载省掉「网络就绪后挂」与「挂不上不阻塞启动」 | 启动会等设备超时，或对端不可达时本机进不了系统 |
| 用杀进程或重启处理卡住的网络挂载 | 停在不可中断等待的进程收不到信号；重启会清掉现场，且存储未恢复时可能卡在启动过程中 |
| 用 `losetup -D` 清理实验环境 | 会分离系统里所有环设备（发行版的 snap 包正靠它挂载），可能直接弄坏系统；要按文件名过滤 |
| 基线只记容量不记型号与挂载参数 | 迁移、扩容、性能对比时无法复现条件，数据不可比 |

## 要点自测

**问：为什么 `df -h` 与 `df -i` 必须一起看？**
答：它们量的是两本账。ext4 上 inode 往往比容量先满，而两者报错同为 `ENOSPC`；只报容量一定会漏掉这一类故障。

**问：`await` 高的时候，怎么判断是排队还是设备退化？**
答：看它与 `aqu-sz` 的配对关系：两者同涨是排队（请求量问题），`await` 高而队列浅是设备或链路本身慢。再分开看读/写，写慢还要查脏页与回写。

**问：`df` 与 `du` 差了几十 GiB，第一步做什么？**
答：不要互相否定，按四类原因逐项排除：已删除但被持有的文件、被挂载覆盖的目录、保留块与元数据、稀疏文件与延迟分配。每一类都要给出证据命令。

**问：改完 fstab 的验收步骤是什么，为什么不用重启？**
答：备份原文 → 语法与可挂载性检查 → 让 systemd 重读 → 逐条挂载 → 核对实际参数与单元状态。重启会把一个当场能发现的问题推迟成一次可能进不了系统的生产事故。

**问：`/proc/<pid>/io` 里 `wchar` 与 `write_bytes` 的区别是什么？**
答：`wchar` 是应用请求写入的字节数（含命中缓存的部分），`write_bytes` 才是真正走到块设备层的字节数。判断「谁把盘打满」看后者。

**问：一份合格的存储排障回答必须包含哪四项？**
答：结论（一句定性）、依据（支撑结论的命令输出原文）、边界（结论在什么条件下会变）、动作（短期止血、长期治理与验收方式）。

**问：网络存储不可达导致进程堆积时，为什么强杀与重启都不是第一选择？**
答：进程等的是内核里的 IO 完成，信号要等它回到用户态才被处理，所以杀不掉；重启会清掉现场，而且**存储未恢复时机器可能卡在启动过程中**。第一选择是确认挂载点与通路，优先恢复链路——通路恢复后等待状态自行消解。

**第一反应不要做什么**：不要用「还有空间」否定「写不进去」；不要只凭一个指标下结论；不要在没定位源头时调参数；不要在没取证时恢复写入。
