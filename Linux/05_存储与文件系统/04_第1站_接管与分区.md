## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **动手前的三问：是不是这块盘、上面有没有东西、有没有人在用。** 三问都答完才有资格敲 `parted`/`mkfs`。
> - **`wipefs -n` 是「不写盘的 X 光」**：它把盘上残留的分区表与文件系统签名列出来，回收盘与新盘一样要跑。
> - **现代系统一律用 GPT**：MBR 在大于 2TiB 的盘上根本表达不了全部分区，且只有一份分区表、写坏就完了。
> - **分区从 1MiB 开始、留 1MiB 对齐**：为了避开 MBR/GPT 结构与物理扇区对齐，省这点空间换来的是性能与兼容性。
> - **设备名不是身份，UUID 才是**：分区表建好、文件系统建好之后，**立刻记录 UUID/LABEL 与型号序列号**，它们是后面所有配置与换盘动作的依据。

## 1. 第一问：是不是这块盘

```bash
lsblk -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINT,ROTA,MODEL,SERIAL
                                     # 验证：设备树 + 型号 + 序列号（认盘的最终依据）
lsblk -d -o NAME,SIZE,ROTA,MODEL,SERIAL | grep -v loop
                                     # 验证：只看物理盘（ROTA=1 机械、0 为 SSD/NVMe）
ls -l /dev/disk/by-id/ | grep -v part | head -20
                                     # 验证：按盘序列号建的稳定链接（比 /dev/sdX 可靠）
```

现场经验：

- **物理机上认盘**用序列号 + 机箱 LED（厂商工具如 `storcli`/`perccli`/`ssacli` 可以点灯），**光看 `/dev/sdX` 一定会认错**。
- **云主机上认盘**看云控制台的盘 ID 与容量，再用 `lsblk -o NAME,SIZE,SERIAL` 对照（云盘通常有序列号或卷 ID）。
- **`/dev/nvme0n1` 这类名字里的数字有含义**：`0` 是控制器编号，`n1` 是命名空间编号；一台机器上插多块 NVMe 时，控制器编号同样可能变。

## 2. 第二问：上面有没有东西

```bash
sudo wipefs -n /dev/<dev>            # 验证：列出盘上所有可识别的签名（-n 只读，绝不写盘）
sudo blkid /dev/<dev> /dev/<dev>1    # 验证：有没有已存在的文件系统 UUID/TYPE
sudo parted -s /dev/<dev> print      # 验证：有没有分区表、什么类型、分区从哪到哪
lsblk -f /dev/<dev>                  # 验证：设备上是否已有文件系统或正在被挂载
```

| 看到什么 | 含义 | 该怎么处理 |
| --- | --- | --- |
| `wipefs -n` 无输出、`parted print` 报 `unrecognised disk label` | 真正的新盘 | 可以建分区表 |
| 有旧的分区表与分区，但没有文件系统 | 拆过的盘/回收盘 | **先确认没人要它的数据**，再决定复用还是 `wipefs` 清签名 |
| 有文件系统（`blkid` 有 UUID） | 盘上有数据 | **停下来问**：这块盘是谁的、要不要备份；绝不能直接 `mkfs` |
| `lsblk` 里 `MOUNTPOINT` 非空 | 正在使用中 | 先 `findmnt`/`lsof`/`fuser` 找出使用者（子笔记 06） |

> [!warning] 第一反应不要是「新盘直接 `mkfs`」
> 新盘与回收盘的唯一区别，是**别人有没有告诉你它被回收过**。`wipefs -n`、`blkid`、`parted print` 三条命令加起来不到一秒，而 `mkfs` 一旦敲下去，旧数据就没了。**这正是「第一站」最重要的动作：先看清，再动手。**

## 3. 第三问：有没有人在用

```bash
findmnt /dev/<dev>1                  # 验证：这个分区是否被挂载、挂在哪、什么参数
sudo fuser -vm /data                 # 验证：哪些进程在使用这个挂载点
sudo lsof +D /data 2>/dev/null | head -20   # 验证：目录被哪些进程打开（目录大时较慢）
sudo dmsetup ls --tree               # 验证：设备是否被 LVM/加密/多路径占用（在映射树里能看到）
```

如果设备已经被 LVM 或 RAID「吃」了，`lsblk` 会显示成一层套一层的关系（子笔记 01 的四层结构）。此时**不能直接对它分区**，要沿链路先确认上层（PV/LV/阵列）状态。

## 4. 建分区表：工具选择与标准动作

| 工具 | 适合 | 特点 |
| --- | --- | --- |
| `parted` | **脚本化、批量** | 一条命令能建表+建分区；`-s` 静默模式适合脚本 |
| `fdisk` / `gdisk` | 交互式调整 | `fdisk` 现在同时支持 GPT 与 MBR；`gdisk` 是 GPT 专用（可做备份/恢复） |
| `sfdisk` | **备份与还原分区表** | `sfdisk -d /dev/sda > sda.sfdisk` 是可脚本化的标准做法 |
| `sgdisk` | GPT 备份/恢复/改 GUID | `sgdisk --backup`/`--load-backup`，还能只改分区 GUID |

标准动作（GPT + 单分区，适合数据盘）：

```bash
sudo parted -s /dev/<dev> mklabel gpt
                                     # 验证：写 GPT 分区表（会清空原分区表，动手前已完成三问）
sudo parted -s /dev/<dev> mkpart primary xfs 1MiB 100%
                                     # 验证：建一个从 1MiB 到盘尾的分区（1MiB 是标准对齐起点）
sudo partprobe /dev/<dev>            # 验证：让内核重读分区表（有的内核需要，之后 lsblk 才能看到分区）
lsblk /dev/<dev>                     # 验证：分区出现了（如 sdb1）
sudo sfdisk -d /dev/<dev> > /root/<dev>-parttable-$(date +%F).sfdisk
                                     # 验证：把分区表导出留档（换盘/误删时能原样恢复）
```

三条必须知道的细节：

1. **分区类型名不影响使用**：`mkpart primary xfs 1MiB 100%` 里的 `xfs` 只是给分区打个类型提示，**不创建文件系统**；真正的文件系统要靠下一步 `mkfs`。
2. **内核重读分区表有两种情况**：空闲盘一般自动识别；**正在使用的盘上改分区表**（如扩容最后一个分区）需要 `partprobe`/`partx -u`，而且扩容分区后还要扩文件系统才有用（子笔记 07）。
3. **分区表本身也要有备份**：`sfdisk -d`（MBR 与 GPT 都支持）或 `sgdisk --backup`，随基线卡一起存。**盘的头几个扇区坏了时，重建分区表比重装系统快得多。**

## 5. 稳定的身份：UUID 与 LABEL

```bash
sudo blkid /dev/<dev>1               # 验证：分区的 UUID、TYPE、LABEL（文件系统建好之后才有）
lsblk -o NAME,UUID,LABEL,FSTYPE      # 验证：一屏看全设备与身份（写 fstab 时直接抄这里）
sudo e2label /dev/<dev>1 data-disk-a # 验证：给 ext4 打 LABEL（XFS 用 xfs_admin -L）
sudo xfs_admin -L data-disk-a /dev/<dev>1
                                     # 验证：给 XFS 打 LABEL
```

记录规则（写进台账）：

| 层次 | 记什么 | 为什么 |
| --- | --- | --- |
| 物理盘 | 型号、序列号、槽位、容量、介质类型 | 换盘、点灯、盘位核对 |
| 分区 | 分区表类型、起止扇区、大小 | 重建分区表、扩容排查 |
| 文件系统 | UUID、LABEL、类型、块大小 | fstab/自动挂载/备份脚本 |
| 池与阵列 | VG/LV 名、PV 成员、RAID 级别与成员 | 扩容与换盘（子笔记 07、08） |

> [!tip] 台账不是形式主义
> 换盘时最容易出事的三步是：**认错盘、没等重建完成就上压力、换了盘没更新台账导致下次又认错**。台账把「认盘」从现场记忆变成了一次查表动作。

## 6. 生产动作：接入一块新数据盘的清单

按顺序做，每一步都有验收：

1. **认盘**：`lsblk -o NAME,SIZE,MODEL,SERIAL` 与工单核对 → **验收**：序列号一致。
2. **看残留**：`wipefs -n`、`blkid`、`parted print` → **验收**：确认无有用数据（如果有，停下来问）。
3. **建分区表**：`parted -s mklabel gpt` + `mkpart` + `partprobe` → **验收**：`lsblk` 能看到分区。
4. **备份分区表**：`sfdisk -d > file` → **验收**：文件里有分区条目。
5. **交给下一站**：`mkfs`（子笔记 05）→ 挂载与 fstab（子笔记 06）。
6. **记台账**：型号、序列号、UUID、LABEL、挂载点、负责人、日期 → **验收**：下一个人照着台账能独立定位这块盘。

> [!example]- 实验 1：用 loop 设备走完「接管」这一站
> **怎么做**：用一个普通文件模拟一块 1GiB 的盘，走完建分区表、建分区、看身份的全过程。所有动作都发生在 `/tmp` 的普通文件上，不碰真盘。
> ```bash
> dd if=/dev/zero of=/tmp/lab-disk0.img bs=1M count=1024
>                                      # 验证：造一个 1GiB 的"盘"
> LOOP1=$(losetup --find --show /tmp/lab-disk0.img)
>                                      # 验证：记录环设备名（如 /dev/loop9），实验里用 $LOOP1 接力
> sudo wipefs -n "$LOOP1"; sudo parted -s "$LOOP1" print
>                                      # 验证：新"盘"上没有任何签名、也没有分区表
> sudo parted -s "$LOOP1" mklabel gpt; sudo parted -s "$LOOP1" mkpart primary ext4 1MiB 100%
>                                      # 验证：建 GPT 分区表 + 一个从 1MiB 到盘尾的分区
> sudo partprobe "$LOOP1"; lsblk "$LOOP1"
>                                      # 验证：看到环设备与其分区（如 loop9p1）
> sudo sfdisk -d "$LOOP1"              # 验证：分区表可以导出（这就是换盘时的重建依据）
> lsblk -o NAME,SIZE,TYPE,PARTTYPENAME "$LOOP1"
>                                      # 验证：分区类型与大小；此时还没有文件系统（FSTYPE 为空）
> ```
> **预期**：`lsblk` 从「一块裸盘」变成「盘 + 一个分区」，`parted print` 显示 `gpt` 与分区起止扇区；`FSTYPE` 仍为空——**分区与文件系统是两件事**，下一站才建文件系统。
> **风险**：低。全部作用在 `/tmp` 的普通文件上（仍需 root），不会碰任何真实设备。
> **环境**：任意发行版；需要 `util-linux`（`losetup`、`lsblk`、`sfdisk`）与 `parted`。**容器里做不了。**
> **耗时**：约 15 分钟。
> **怎么退回去**：`sudo losetup -d "$LOOP1"; rm -f /tmp/lab-disk0.img`。若中途失败，用子笔记 17 的「统一清理」段。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 拿 `/dev/sdb` 当身份写进配置 | 设备名会漂移；配置里只能用 UUID/LABEL/by-id |
| 新盘不做 `wipefs -n` 直接 `mkfs` | 回收盘上可能还有旧数据签名，`mkfs` 会立刻清掉它们 |
| 用 MBR 给 4TiB 的盘分区 | 超过 2TiB 的部分无法寻址；大容量盘必须 GPT |
| 分区不从 1MiB 开始 | 与分区表结构/物理扇区不对齐，可能带来性能损失与兼容问题 |
| 改完分区表不 `partprobe` | 内核还用旧分区表，`lsblk` 里看不到新分区 |
| 认为 `mkpart` 里的类型名会创建文件系统 | 那只是分区类型提示；文件系统必须 `mkfs` |
| 只记录挂载点不记录 UUID/序列号 | 换盘或迁移时无法确认「换的是哪块盘」 |
| 在容器里尝试 `parted`/`losetup` | 缺少设备节点与权限，会失败；这类实验必须在虚拟机里做 |

## 决策练习

> [!question]- 场景：你收到一块「新」数据盘，`lsblk` 显示 `/dev/sdb` 1.8TiB 无分区无挂载。你准备 `parted mklabel gpt` 时，`wipefs -n /dev/sdb` 输出里有 `ext4` 与 `gpt` 两条签名。怎么办？
> A. 直接继续：反正是空盘，签名是出厂测试留下的
> B. 停下来核实：盘上有 GPT 与 ext4 签名，说明它可能曾是某台机器的数据盘；先向交付方/资产台账确认它是否已被回收，必要时用 `blkid`、`parted print` 看分区结构，再决定是清签名还是原样返回
> C. 先把签名擦掉，反正擦了也不影响别人
>
> **答案：B。**
> A 与 C 都会立刻造成不可逆的数据丢失：`wipefs` 不带 `-n` 就会真擦签名，后续 `mkfs` 会覆盖元数据，**旧数据基本没救**。
> B 是正解：**签名就是「这块盘曾经有主人」的证据**，回收流程没走完时，最便宜的处置是问一句，而不是擦掉它。这也是「三问」里的第二问存在的理由。

## 要点自测

> [!question]- 新接一块盘，动手前的三问是什么？各自用什么命令回答？
> - **是不是这块盘**：`lsblk -o NAME,SIZE,MODEL,SERIAL`、`/dev/disk/by-id/`。
> - **上面有没有东西**：`wipefs -n`、`blkid`、`parted print`。
> - **有没有人在用**：`findmnt`、`fuser -vm`、`lsof +D`、`dmsetup ls --tree`。
> - **第一反应不要是什么**：不要凭「新盘」的说法跳过第二问。

> [!question]- 为什么分区要从 1MiB 开始？
> - GPT 需要盘头/盘尾的空间存分区表与备份，MBR 需要前 512 字节；从 1MiB 起还能保证与常见的物理扇区大小对齐。
> - 对齐带来的收益是性能与兼容性；代价只有 1MiB 空间。
> - **第一反应不要是什么**：不要为了「省那 1MiB」从 2048 扇区之前开始分区。

> [!question]- 分区表怎么备份与恢复？
> - 备份：`sfdisk -d /dev/sda > sda.sfdisk`（MBR/GPT 通用），或 `sgdisk --backup=file /dev/sda`（GPT 专用，含 GUID）。
> - 恢复：`sfdisk /dev/sda < sda.sfdisk` 或 `sgdisk --load-backup=file /dev/sda`；**恢复后要 `partprobe`**。
> - **第一反应不要是什么**：不要等到分区表坏了才想起来没有备份——它应该和基线卡一起存。

> [!question]- `parted`、`fdisk`、`sfdisk` 各用在什么场景？
> - `parted`：脚本化建表建分区（`-s` 静默模式）；`fdisk`：交互式调整，适合现场改一两个分区。
> - `sfdisk`：**备份/还原分区表**，也可脚本化；`gdisk`/`sgdisk`：GPT 专用，能做备份与改 GUID。
> - **第一反应不要是什么**：不要在生产盘上用交互式工具「边想边改」——脚本化的动作可以进变更单与复盘。
