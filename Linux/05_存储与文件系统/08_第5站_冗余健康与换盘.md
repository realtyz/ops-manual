## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **RAID 不是备份**：它只防「盘坏了」，不防误删、勒索加密、逻辑损坏、机房级故障——这些会被阵列忠实地同步到所有盘上。
> - **重建才是一道坎**：RAID5 重建要读**全部**成员盘，期间任何一块盘出现不可恢复读错误即失败；大容量 + RAID5 的组合因此越来越不受欢迎。
> - **健康要看趋势，不是看有没有值**：`Reallocated_Sector_Ct` **持续增长**、`Current_Pending_Sector > 0`、NVMe `Available_Spare` 下降或 `Media_and_Data_Integrity_Errors` 非 0 都要立刻查。
> - **内核日志比 SMART 更早**：`dmesg -T` 里的 `I/O error`、`medium error`、`nvme.*reset` 是换盘决策的直接证据。
> - **换盘最容易出事的三步**：认错盘（把好盘拔了）、没等重建完成就上业务压力、换了盘不更新台账导致下次再认错。

## 1. RAID 级别：容量、性能与风险

| 级别 | 可用容量 | 冗余 | 读/写性能 | 重建时的风险 |
| --- | --- | --- | --- | --- |
| RAID0 | `n ×` | 无 | 最好（顺序与随机都接近线性） | 一块坏，全盘数据丢失 |
| RAID1 | `n/2 ×`（镜像） | 可容忍同一镜像组各留一块 | 读提升、写略降 | 只需复制一份数据，压力最小 |
| RAID5 | `(n−1) ×` | 单盘冗余 | 读较好、**写有惩罚**（每次写涉及读改写与校验更新） | **重建要读全部数据盘**，遇到不可恢复读错误即失败；另有 write hole 问题 |
| RAID6 | `(n−2) ×` | 双盘冗余 | 写惩罚更高 | 重建压力与 RAID5 同量级，但允许再坏一块 |
| RAID10 | `n/2 ×` | 视镜像组而定 | 好（兼顾随机读写） | 只重建对应镜像，速度快、风险低；代价是容量利用率只有一半 |

**重建风险要有量化的说法**（面试加分点，注意单位是比特）：

- 厂商标称的不可恢复读错误率（URE）一般写作 **1 次 / 10¹⁴ 比特（消费级）** 或 **1 次 / 10¹⁵ 比特（企业级）**。
- 重建一块 10TB 盘需要读约 `8 × 10¹³` 比特。按 `P ≈ 1 − e^(−读取量 / URE 分母)` 估算：消费级约 **55%**、企业级约 **8%** 会遇到至少一次不可恢复读错误。
- 这是**数量级估算**，实际还取决于厂商标称口径、盘龄与阵列能否用其他盘纠错（RAID6/RAID10 容错更好）。但它解释了为什么「大容量盘 + RAID5」在生产上越来越不受欢迎。

还有两条判断：

- **重建期间的性能与风险是叠加的**：阵列降级 + 全盘扫描重建 + 业务高峰期 = 双重风险。生产上要**给重建限速**，必要时主动降低业务压力。
- **同批次、同寿命的盘会一起老化**：一批盘同时到期意味着可能连续降级。**批量替换计划**（而不是等它坏）是成熟运维的做法。

## 2. 软 RAID 与硬件 RAID

| | 软件 RAID（`mdadm`） | 硬件 RAID（阵列卡） |
| --- | --- | --- |
| 谁负责 | 内核的 md 层，一切都在 OS 里 | 阵列卡固件，OS 只看到一块逻辑盘 |
| 优点 | 免费、可控、状态可见、便于统一监控 | 不占主机 CPU、有写缓存与电池/电容保护、支持热插拔管理 |
| 缺点 | 占主机 CPU 与内存、重建速度受主机影响 | 必须靠厂商工具（`storcli`/`perccli`/`ssacli`）看物理盘与缓存状态，黑盒 |
| 看状态 | `/proc/mdstat`、`mdadm --detail` | 厂商工具；OS 侧只能看块设备 |
| 监控重点 | 降级、重建进度、成员盘 | 降级、重建进度、**BBU/电容状态与写缓存策略** |

```bash
cat /proc/mdstat                     # 验证：阵列状态、成员盘（[U] 正常、[_] 缺失）与重建进度
sudo mdadm --detail /dev/md0         # 验证：RAID 级别、chunk 大小、bitmap、每块盘的角色
cat /proc/sys/dev/raid/speed_limit_min /proc/sys/dev/raid/speed_limit_max
                                     # 验证：重建速度下限/上限（KB/s，重建期间可调）
sudo mdadm /dev/md0 --fail /dev/sdb1 --remove /dev/sdb1 --add /dev/sdc1
                                     # 验证：坏盘下线 + 新盘加入重建的完整动作（顺序固定）
sudo mdadm --detail --scan >> /etc/mdadm.conf
                                     # 验证：把阵列定义写进配置（重启后仍能自动组阵）
sudo multipath -ll                   # 验证：iSCSI/FC 多路径设备及路径状态（active/ghost/failed）
```

> [!warning] 第一反应不要是「阵列降级了立刻拔盘换新」
> 先确认**哪块盘真的坏了**：`cat /proc/mdstat` 看哪块被踢出、`dmesg -T` 看介质错误指向哪块盘、用序列号在机箱上定位槽位。**误拔好盘会让冗余度瞬间归零**，从「能容忍一块坏」变成「再坏一块就全丢」。

## 3. 健康巡检：SMART 与内核日志

**主动巡检的价值**：介质错误计数与内核日志里的 `I/O error` 通常**早于**阵列降级、文件系统变只读出现，是最便宜的一次预警。

| 类型 | 关键字段 | 含义与判断 |
| --- | --- | --- |
| 机械盘 / SATA SSD | `Reallocated_Sector_Ct`（ID 5） | 已重映射扇区数，**持续增长即为坏信号**（不是「有值就立刻坏」，看趋势） |
| | `Current_Pending_Sector`（197） | 待处理的不可读扇区，**大于 0 就要重点关注** |
| | `Offline_Uncorrectable`（198） | 离线扫描无法纠正的扇区 |
| | `UDMA_CRC_Error_Count`（199） | 通常指向**线缆/背板/接口**问题，而不是盘本身 |
| | `Temperature_Celsius`（194） | 温度持续偏高会加速老化 |
| NVMe | `Percentage_Used` | 寿命消耗百分比（超过厂商阈值应计划替换） |
| | `Available_Spare` | 备用块余量，低于厂商阈值会出现在 `Critical_Warning` |
| | `Media_and_Data_Integrity_Errors` | 数据完整性错误计数（非 0 要立刻查） |
| | `Unsafe_Shutdowns` | 异常掉电次数，指向电源/固件问题 |

```bash
sudo smartctl -H /dev/sda            # 验证：SMART 总健康判定（PASSED/FAILED）
sudo smartctl -a /dev/sda | grep -E 'Reallocated_Sector_Ct|Current_Pending_Sector|Offline_Uncorrectable|UDMA_CRC_Error_Count|Temperature'
                                     # 验证：机械盘/SATA SSD 的关键指标
sudo smartctl -a -d nvme /dev/nvme0  # 验证：NVMe 的 SMART（Percentage_Used/Available_Spare/完整性错误）
sudo nvme smart-log /dev/nvme0       # 验证：NVMe 原生工具视角（与 smartctl 互为印证）
sudo nvme list                       # 验证：本机 NVMe 设备清单与固件版本
dmesg -T | grep -i -E 'medium error|I/O error|critical medium|nvme.*(reset|down)'
                                     # 验证：介质错误与控制器异常（换盘决策的直接证据）
```

巡检节奏（写进监控与值班手册）：

| 动作 | 节奏 | 判据 |
| --- | --- | --- |
| SMART 关键字段采集 | 每周（timer 或监控 agent） | `Current_Pending_Sector > 0`、`Reallocated_Sector_Ct` 明显增长、NVMe `Percentage_Used`/`Available_Spare` 越过阈值 |
| 内核日志扫描 | 每日 | `I/O error`、`medium error`、`nvme.*reset`、`link is down` |
| 阵列与电池状态 | 每日 | 降级、重建进度、BBU/电容状态、写缓存策略 |
| 换盘演练 | 每季度 | 在实验环境完整走一遍「定位 → 下线 → 更换 → 重建 → 校验 → 台账」 |

## 4. SSD/NVMe 的维护动作

```bash
systemctl status fstrim.timer        # 验证：定期 TRIM 是否启用（多数发行版默认开启）
sudo fstrim -av                      # 验证：手工对所有支持的文件系统执行 TRIM（输出每块盘回收的字节数）
sudo blkid /dev/<dev>; sudo blkdiscard -n /dev/<dev>
                                     # 验证：擦除前先确认设备身份（-n 只做演练，不真正擦除）
sudo nvme id-ctrl /dev/nvme0 | grep -E 'fr|mn|sn'
                                     # 验证：固件版本与型号（固件升级前的记录）
```

| 动作 | 说明 |
| --- | --- |
| `fstrim.timer` | 定期批量下发 TRIM，**推荐做法**；比挂载项 `discard` 更可控 |
| 挂载项 `discard` | 删除时立即下发；在部分盘上会造成延迟抖动，一般只在对延迟不敏感的场景用 |
| `blkdiscard` | 整设备/整分区擦除，**破坏性操作**：会立刻清空数据；只用于重装或回收阵列盘前的清理 |
| 寿命评估 | 结合 `Percentage_Used` 与写入总量（NVMe 的 `Data Units Written` × 1000 × 512 字节换算）与厂商 TBW/DWPD 对比，判断是否需要提前替换 |
| `%util` 的局限 | NVMe 依赖多队列并行，`iostat` 的 `%util` 经常接近 100% 却远未饱和；**要看延迟分位与队列深度**（子笔记 12） |

## 5. 换盘流程：必须演练过

一次规范的换盘包含六步：

1. **确认目标盘**：用序列号 + LED 闪烁或厂商工具定位槽位（**不要凭 `/dev/sdX` 认盘**）。
2. **按流程下线**：软 RAID 用 `mdadm --fail` + `--remove`；硬件 RAID 用厂商工具把盘置为 failed/offline。
3. **换入新盘**：核对新盘型号、容量（**不小于原盘**）、固件版本；热插拔时注意机箱说明。
4. **重建并限速**：加入新盘后观察重建进度；用 `/proc/sys/dev/raid/speed_limit_max`（软 RAID）或厂商策略限速，避免重建打满业务 IO。
5. **校验**：重建完成后核对阵列状态（`/proc/mdstat` 无降级、bitmap 干净）、文件系统可写、业务指标正常。
6. **更新台账**：把新旧盘序列号、更换时间、原因写进资产记录。

三个最容易出事的地方：

- **认错盘**：把好盘拔了，冗余度瞬间归零。
- **没等重建完成就上压力**：重建 + 业务高峰叠加，可能把其余盘也拖坏。
- **换了盘不更新台账**：下次故障时又要在现场猜哪块盘是哪块。

> [!example]- 演练：不做破坏性实验，先把「读」练熟（生产机也可以做）
> **怎么做**：RAID 演练至少需要 3 块独立盘，loop 设备做不出真实的重建压力，所以这一篇不给破坏性实验。**改为在实验机（或生产机的只读巡检窗口）把下面这些命令跑通、把输出读熟**：
> ```bash
> cat /proc/mdstat                     # 验证：阵列是否存在、是否降级、是否有重建进度
> sudo mdadm --detail /dev/md0 | head -30
>                                      # 验证：级别、成员盘、chunk、bitmap、状态
> sudo smartctl -H /dev/<dev>; sudo nvme list
>                                      # 验证：健康总判定与设备清单（记进基线台账）
> sudo smartctl -a /dev/<dev> | grep -E 'Reallocated|Pending|Offline_Uncorrectable|CRC'
>                                      # 验证：四个关键计数（记下当前值，之后看趋势）
> cat /proc/sys/dev/raid/speed_limit_min /proc/sys/dev/raid/speed_limit_max
>                                      # 验证：重建限速的上下限（演练时要知道在哪调）
> systemctl status fstrim.timer; sudo fstrim -av
>                                      # 验证：TRIM 是否在定期执行（NVMe/SSD 上才有意义）
> ```
> **预期**：能独立说出「这台机器有没有阵列、什么级别、每块盘健康如何、重建时在哪限速、TRIM 有没有开」。
> **风险**：无（全部只读；`fstrim -av` 会真正下发 TRIM，但它是正规维护动作，不会破坏数据）。
> **环境**：任意发行版；`smartctl` 读真盘需要 root，虚拟机里可能拿不到真实 SMART 数据。
> **耗时**：约 20 分钟。
> **怎么做一次真正的换盘演练**：在专门的实验虚拟机里用 3 块虚拟盘建 `mdadm` 阵列 → `--fail` 一块 → 观察降级 → 加入新盘 → 限速重建 → 校验 —— **这是 T3 台阶的推荐演练内容**。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 认为「有 RAID 就不用备份」 | RAID 只防盘坏；误删、勒索、逻辑损坏会同步到所有盘 |
| 大容量盘上用 RAID5 | 重建要读全部成员盘，遇到 URE 即失败；容量越大越危险 |
| 只看 `Reallocated_Sector_Ct` 有没有值 | 要看**趋势**：持续增长才是坏信号；单次数值本身不代表立刻报废 |
| 看到 `UDMA_CRC_Error_Count` 就换盘 | 它通常指向线缆/背板/接口，先排查连接件 |
| 阵列降级就先拔可疑盘 | 先确认哪块真坏（`/proc/mdstat` + `dmesg` + 序列号定位），误拔好盘会让冗余归零 |
| 重建期间不做限速 | 重建会打满磁盘带宽，业务 `await` 明显恶化，还可能拖坏其他盘 |
| 在 NVMe 上用 `%util` 判断饱和 | 多队列并行让 `%util` 常接近 100% 却远未饱和；看延迟与队列深度 |
| 长期依赖挂载项 `discard` | 部分盘上会造成延迟抖动；通常改用 `fstrim.timer` |
| 换盘不更新台账 | 下次故障又要现场猜盘，重复踩坑 |
| 同批次盘老化不同步替换 | 一批盘同时到期会造成连续降级；应做批量替换计划 |

## 决策练习

> [!question]- 场景：一台 4 盘 16TB 的备份服务器用 RAID5，`mdadm --detail` 显示 `/dev/sdc` 已 dropped。运维同事提议「立刻拔掉 sdc 换新，越快越好」。你怎么定？
> A. 同意：早换早好，重建期间也还有冗余
> B. 先做三件事：确认坏的是哪块盘（`/proc/mdstat`、`dmesg -T` 的介质错误、序列号 + LED 定位槽位）→ 再决定是否需要立刻换，同时把重建限速准备好并避开业务高峰 → 换盘后校验阵列与文件系统，最后更新台账；并借这次机会评估「大容量 + RAID5」的风险是否要改进（如 RAID6 或 RAID10）
> C. 干脆重建整个阵列，换 RAID10 一次到位
>
> **答案：B。**
> A 的问题在于「没确认就动手」：`sdc` 被 dropped 不等于 `sdc` 一定是坏的（也可能是链路/背板/电源问题），而误拔好盘会让冗余度归零；同时「越快越好」忽略了重建期间的风险叠加。
> C 是重大变更：RAID 级别不能在线改，需要备份 + 重建 + 恢复，与「先解决眼前故障」不是一回事；可以**作为后续改进项**讨论。
> B 是正解：**先定位、再动手、限速重建、事后校验与台账**——这套流程的重点不是快，而是「一次做对」。

## 要点自测

> [!question]- RAID0/1/5/6/10 各适合什么场景？
> - RAID0：只要性能与容量、能接受全丢（临时数据、缓存层）。
> - RAID1：小容量高可靠（系统盘、关键小盘）；RAID10：兼顾性能与可靠，容量利用率只有一半。
> - RAID5/6：容量利用率优先，但要接受重建风险；大容量盘上要慎重（RAID5 尤甚）。
> - **第一反应不要是什么**：不要因为「RAID 有冗余」就把它当备份。

> [!question]- 为什么大容量盘上的 RAID5 重建风险高？
> - 重建要读**所有成员盘的全部数据**，期间任何一块盘出现不可恢复读错误即重建失败。
> - 按 URE 1 次/10¹⁴ 比特估算，重建 10TB 遇到的问题概率在数十个百分点量级（消费级），企业级低一个数量级。
> - **第一反应不要是什么**：不要只看「能容忍一块坏」的参数，忽略重建这个窗口。

> [!question]- `smartctl` 哪些字段需要立刻行动？
> - `Current_Pending_Sector > 0`、`Offline_Uncorrectable` 增长、`Reallocated_Sector_Ct` 持续增长。
> - NVMe：`Available_Spare` 低于阈值、`Media_and_Data_Integrity_Errors` 非 0、`Percentage_Used` 超过厂商阈值。
> - **第一反应不要是什么**：不要等阵列降级或文件系统变只读才处理——那时已经损失了冗余度。

> [!question]- 换盘流程里，哪三步最容易出事？
> - **认错盘**（凭 `/dev/sdX` 而不是序列号 + LED）、**重建未完成就上压力**、**不更新台账**。
> - 另外别忘了重建限速与事后校验（阵列状态 + 文件系统可写 + 业务指标）。
> - **第一反应不要是什么**：不要在没定位清楚的情况下拔盘。
