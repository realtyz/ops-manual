# 串讲：五条主线

本章正文按建造顺序排列：先机制，再体系，再动手、判断与治理。值班与复盘里的提问不按这个顺序进入——它从一个现象或一个「为什么」开始，回答者需要一条能立刻走下去的路径，并在对方追问时知道拐向哪里。

本篇把全章收成五条主线。它与知识地图的关系是：地图里的一条时间主线（一块盘的服役一生）整体占一条；三个跨阶段的核对对象（容量口径与归属、容量上限与拒绝写入、写入顺序与完整性证据）各自独立成一条；第五条是「变慢」——它不落在五个阶段中的任何一个，而由原理《写入路径与完整性》与实操《观测与基线》的两个场景构成一条独立的提问链，因为提问密度高而单独成线。每条主线以一组高频提问为入口，给出沿线的节点顺序；每个节点写四件事：**先答**（第一句先给出的结论）、**举证**（这句话落到哪个字段、文件或命令上）、**深入**（对方再追一层时补上的边界、反例与代价）、**衔接**（问题跨出本节点时拐向哪里）。节点只给骨架：字段的完整读法（是什么、单位、判据、与谁同看、转向哪一步）集中在《观测与基线》第 2 节与「常见故障与排查方向」各场景；被剖析到第 0 层的错误答法在《高频误判》；想验收自己的回答停在哪一层，用《盲区排查》。

## 2. 主线一：一块盘的服役一生

这条线按时间顺序走：从盘被机器认出来，到拥有分区与文件系统，到挂进目录树开始服役，到容量长大，最后到坏掉、可控地换走。它对应知识地图里的时间主线，五个阶段各自成节点，「冗余与退役」因为各含一套独立判据而拆成两个节点。

**入口提问**：「这块盘能不能动」「回收盘直接建文件系统有什么风险」「ext4 和 XFS 怎么选」「哪些参数建完就改不了」「fstab 改完怎么验收」「重启进了紧急模式怎么查」「云盘扩容了容量为什么没变」「RAID5 能坏一块，为什么不能等」「健康计数非零要不要换盘」「换盘哪几步最容易出事」。

```mermaid

  A["① 接管<br/>三问与建分区表"] --> B["② 成型<br/>选型与 mkfs"]
  B --> C["③ 上岗<br/>fstab 与验收"]
  C --> D["④ 长大<br/>扩容六层链"]
  D --> E["⑤ 冗余<br/>RAID 与重建窗口"]
  E --> F["⑥ 退役<br/>健康趋势与换盘"]
```

### 2.1 接管：动手前的三问

- **先答**：接入一块盘时最危险的动作不是分区，而是认错盘，因此三问必须都答完才有资格敲下一条命令——是不是这块盘（靠序列号与型号，不靠设备名）、上面有没有东西（靠签名与分区表，不靠「它看起来是新的」）、有没有人在用（靠挂载关系与映射树）。
- **举证**：三问各有命令——`lsblk -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINT,ROTA,MODEL,SERIAL` 与 `/dev/disk/by-id/` 里的稳定别名回答第一问；`wipefs -n` 只读地列出盘上所有可识别的签名，`blkid` 与 `parted -s /dev/<dev> print` 回答第二问；`findmnt`、`fuser -vm` 与 `dmsetup ls --tree` 回答第三问。`lsblk` 的 `MOUNTPOINT` 非空说明正在使用中；若 `lsblk` 里出现一层套一层的关系、或 `dmsetup ls --tree` 的映射树里能看到这块盘，则它已处在 device-mapper 结构的底层，此时不能直接对它分区。
- **深入**：设备名来自内核的识别顺序，换插槽、加盘、云平台重挂都会改变它，所以持久配置里只能用 UUID、LABEL 或 `/dev/disk/by-id/`；一次性操作可以用 `/dev/sdX`，但敲命令之前必须先核对。分区表建好后立刻把身份记进台账，覆盖物理盘、分区、文件系统、池与阵列四层——换盘最容易出事的三步里，第一步就是认错盘，而台账的作用是把认盘从现场记忆变成一次查表动作。
- **衔接**：选型与建文件系统的判据拐节点 2；「这块盘多大」这句话本身不完整，因为设备容量不等于可用空间，拐主线二节点 2 与节点 1。

### 2.2 成型：选型三问与定下就改不了的参数

- **先答**：选型按三个问题依次回答——这台机器会不会缩容（若会且能停机，则文件系统只能选 ext4，因为 XFS 完全不支持缩容）、会不会有几十万以上的海量小文件（若会，则选 XFS，因为它动态分配 inode，可以避开 inode 耗尽）、容量会不会长到几十 TiB（若会，则选 XFS 配合 LVM，因为这条扩容链路最顺）。`mkfs` 会立刻用新文件系统的超级块、inode 表与块位图覆盖盘上原有的元数据，它不给第二次确认的机会。
- **举证**：**建文件系统时定下、以后改不了的参数**是块大小、ext4 的 inode 密度（`-i`，即每多少字节给一个 inode）、XFS 的分配组（AG，Allocation Group）数量与部分特性（如 `reflink` 写时复制、`bigtime` 大时间戳）；想改这些就等于重建文件系统。相反，ext4 的保留比例（`-m`）、自动检查周期、出错行为，以及 XFS 的标签，都可以事后调整。
- **深入**：建完要立刻做四件事——打 LABEL 并取 UUID、记录块大小与 inode 总量这类结构参数（半年后回头看 inode 用量时要用）、手动挂载验证一次（**不要拿 fstab 当第一次尝试**，那时失败就变成开机故障）、确认「干净状态」。XFS 要求显式加 `-f` 才肯覆盖已有签名，这是它「默认假设你可能敲错了设备名」的保护设计，不是习惯性参数。
- **衔接**：inode 会不会耗尽、扩容能不能解决，拐主线三节点 3；「哪些动作不可逆」的完整清单拐主线四节点 4。

### 2.3 上岗：fstab 的六列与不重启的验收

- **先答**：`/etc/fstab` 的六列里，只有两个选项决定出错时的后果——`nofail` 决定设备缺失或挂载失败时是否阻塞启动（数据盘与可选盘必加，缺了它一块盘掉线就能把整机拖进紧急模式），ext4 的 `errors=` 决定出错时的动作（**默认是「继续」，不显式配置就不会自动切只读**）。设备那一列只能写 UUID 或 LABEL，挂载点那个目录必须已经存在。
- **举证**：改完 fstab 的验收在当前机器上就能做完，共五步——备份原文、做语法与可挂载性检查（`findmnt --verify --verbose`）、让 systemd 重读（`systemctl daemon-reload`）、逐条挂载（`mount -a`）、核对实际生效的参数（`findmnt -o TARGET,SOURCE,FSTYPE,OPTIONS`）。systemd 会把 fstab 的每一条翻译成一个挂载单元，单元名把路径里的 `/` 换成 `-`，因此 `/data` 对应 `data.mount`、`/mnt/disk1` 对应 `mnt-disk1.mount`；挂载失败时的第一现场是这个单元的日志，而不是重读一遍 fstab。
- **深入**：用重启验证 fstab 是把一个当场能发现的问题推迟成一次生产事故——写错的 fstab 可能让机器起不来，远程也连不上。网络存储的挂载还要补 `_netdev`，少了它启动会等设备超时。
- **衔接**：「这个目录是不是真的在独立盘上」不能靠目录名推断，拐主线二节点 3；`findmnt` 的 `OPTIONS` 里出现 `ro` 说明内核已经检测到错误，方向拐主线四节点 3。

### 2.4 长大：扩容六层链与唯一的验收标准

- **先答**：容量从硬件到业务要经过设备、分区、PV、VG、LV、文件系统六层，**任何一层没有扩大，最上层可用的空间都不会变**；验收标准只有一条——业务侧的容量确实变大，并且能正常写入。「卷已经扩了」不等于「业务可以用到更多空间」。
- **举证**：每一层各有验收点——设备的 `SIZE`、分区的 `SIZE`（云盘场景常见这一步被跳过）、PV 的容量与卷组的空闲空间、LV 的大小、文件系统的容量，最后是业务侧写入测试。两个工具的记混点是硬判据：**ext4 的扩容工具接受设备，XFS 的扩容工具接受挂载点**；而 XFS 必须处于挂载状态才能在线扩大。
- **深入**：扩容是把容量给出去的动作，无法回退，所以顺序是先备份结构与数据（分区表导出、池的元数据导出），再从下往上一层层长大、一层层验收。缩容是反向的重操作：顺序与扩容相反（必须先缩文件系统再缩卷），XFS 完全不支持缩容，ext4 缩容必须先卸载并完成一次完整检查——因此「会不会缩容」必须在建文件系统那一步就确认清楚。
- **衔接**：「云盘扩容了但业务容量没变」在这条链上逐层定位；若六层都验收通过而业务侧口径仍不符，拐主线二节点 3 核对业务目录实际属于哪个文件系统。

### 2.5 冗余：RAID 的边界与重建窗口

- **先答**：RAID 的核心价值不是更快，而是把单盘故障从「服务中断加数据丢失」变成一次维护动作；它的边界同样清楚——冗余只对抗盘的物理失效，**不对抗数据错误**，误删、勒索加密、错误写入与逻辑损坏都会被阵列同步到所有成员盘，所以 RAID 不替代备份。
- **举证**：重建是所有动作里最危险的窗口，**它要读全部成员盘，期间阵列处于低冗余甚至无冗余状态**。风险随单盘容量增长而上升：按厂商标称的不可恢复读错误率（URE，Unrecoverable Read Error rate）估算，重建一块 10 TB 盘需读约 `8×10¹³` 比特，消费级标称 1 次/10¹⁴ 比特下的失败概率约 55%，企业级低一个数量级。这是数量级估算，实际取决于标称口径、盘龄与阵列能否用其他盘纠错。
- **深入**：降级不等于「还有冗余」——降级之后阵列已经没有冗余，再坏一块就会丢掉整个阵列的数据，而这个窗口的时长由重建时间决定。因此「还有冗余，等下周维护窗口再处理」这句话把「设计上能容忍一块坏」当成了「现在没有风险」。双校验或镜像结构容错更好，大容量单校验阵列（RAID5）在生产上越来越不受欢迎。
- **衔接**：「重建期间业务变慢怎么办」拐主线五节点 2；「健康计数非零要不要立刻换」拐节点 6。

### 2.6 退役：健康看趋势，换盘按六步

- **先答**：换盘决策依据的是趋势而不是单值——重映射扇区数**持续增长**才是信号，待处理扇区数**大于 0 就要重点关注**，而**数据完整性错误计数非 0 必须立刻介入**，因为它意味着数据已经出错，不是盘在变慢。健康巡检的价值在于它比阵列降级和文件系统只读早得多。
- **举证**：盘的健康有两条独立来源，内核日志通常比健康计数更早——介质错误、IO 错误与控制器重置是换盘决策的直接证据；计数侧要看重映射扇区数、待处理扇区数、离线不可纠正扇区、接口传输校验错误（**它单独增长指向线缆、背板或接口，不是盘本身**）、寿命消耗百分比与备用块余量。巡检节奏应当写进值班手册：健康计数按周采集，内核日志与阵列状态按日扫描，换盘流程每季度在实验环境完整演练一次。
- **深入**：一次规范的换盘包含六步——确认目标盘（用序列号核对并配合槽位指示灯）、按流程下线、换入新盘（容量不小于原盘）、重建并限速、校验、更新台账。三个最容易出事的地方是认错盘（把好盘拔了，冗余度瞬间归零）、没等重建完成就上业务压力（重建与高峰叠加，可能把其余盘也拖坏）、换了盘不更新台账（下次故障又要现场猜）。
- **衔接**：「设备完成时间高是退化还是排队」拐主线五节点 2；同批次盘的批量替换计划与巡检记录表、排期表这两件产物拐主线三节点 6。

## 3. 主线二：容量口径与归属

这条线对应知识地图里的第一个跨阶段的核对对象「容量口径与归属」，它贯穿接管、成型、上岗、长大与冗余和退役五个阶段，因为每一处判断都要用到它。它按「这个数字量的是什么」走：同一个量能有好几个合法的数，答错口径比答错数值更常见。

**入口提问**：「这个目录还剩多少空间」「`df` 和 `du` 差了几十 GiB 谁不准」「删了大文件空间为什么不降」「挂载后目录里的文件去哪了」「标称 1 TB 的盘为什么只有 931 GiB」「容器里 `df` 的数字是哪来的」「容器里删了文件宿主为什么没释放」。

```mermaid
flowchart LR
  A["三个大小口径<br/>表观 · 实际占用 · 记账"] --> B["进位与单位<br/>GiB 与 GB · B 与 b"]
  B --> C["归属<br/>目录名不携带文件系统信息"]
  C --> D["遮挡<br/>挂载遮住原内容"]
  D --> E["差额四类<br/>df 与 du 对不上的落点"]
  E --> F["联合挂载<br/>同一路径两个视角"]
```

### 3.1 三个大小口径

- **先答**：同一个文件在三个地方有三个大小，它们**本来就应该不一样**——表观大小是文件声称自己有多少字节（空洞也计入），实际占用是它真正分配到了多少块，而 `df` 报的是超级块记载的已用块与可用块。选择哪个口径取决于要回答的问题：这批数据能不能放进去用表观大小，还能写多少用 `df` 的可用块，哪些文件占用了这些块用实际占用。
- **举证**：三个口径的字段分别是 `ls -l` 与 `stat` 的 `Size`、`du` 与 `stat` 的 `Blocks`（**单位是 512 B，与表观字节不是一个口径**）、`df` 的已用块与可用块。稀疏文件上表观大小远大于实际占用，小于一个块的文件也会占满一块，支持压缩或去重的文件系统同样会出现偏差。
- **深入**：`df` 的 `Avail` 不等于 `Size − Used`，差额来自元数据、区块对齐，以及 ext4 为 root 保留的比例；`du -x` 的 `-x` 不可省，跨文件系统统计会把别的盘算进来，彻底破坏「这个盘用了多少」的结论。三个数可以相差数倍，用错口径得出的结论会系统性地偏一个方向。
- **衔接**：差额的具体归类拐节点 5；「`ls -l` 显示 1 GiB 而 `du` 显示 100 MiB」在本节点答完。

### 3.2 进位与单位：数字对不上的第一来源

- **先答**：`KiB`/`MiB`/`GiB`/`TiB` 是 1024 进位，`KB`/`MB`/`GB`/`TB` 是 1000 进位，Linux 的 `df -h` 一类工具默认用 1024 进位，而硬盘与云盘标称、网络带宽用 1000 进位；两者相差 2.4%（KiB）到 10%（TiB），**在同一份容量报表里混用这两种进制，是「数字对不上」的第一来源**。存储侧的速率字段里 `B` 是字节、`b` 是比特，两者差 8 倍。
- **举证**：`df -h` 用 1024 进位，`df -H` 用 1000 进位；若要把容量与厂商标称、云控制台对齐就用后者，若要写进跨时间的记录做精确对账就用 `df -B1` 输出字节数。厂商标称 1 TB 是 10¹² 字节，按 1024 进制约等于 931 GiB。
- **深入**：标称 1 TB 的盘从厂商标称到业务可用要经过四次扣减，每一次都有明确原因、**都不是故障**——进位换算、分区表占用与 1 MiB 对齐、文件系统元数据（inode 表、日志、位图与超级块备份）、保留块与配额。因此「这块盘多大」这句话本身是不完整的，问容量时必须同时问是哪一层、哪个口径、给谁用。
- **衔接**：「云盘扩容了但 `df` 没变大」的机制原因在这一条上——扩容只改动了前两个台阶，后面的台阶需要各自的动作才会跟上，完整链路拐主线一节点 4。

### 3.3 归属：目录名不携带文件系统信息

- **先答**：任何关于「这个目录还剩多少空间」的问题，第一步都是确认它属于哪个文件系统，而不是直接读 `df` 的第一行或凭目录名推断——**目录名叫 `/var/log` 不代表它在一块独立的盘上**。
- **举证**：`findmnt -T <路径>` 给出该路径实际属于哪个挂载点与文件系统；`/etc/fstab` 是期望，`/proc/mounts` 与 `findmnt` 是实际，两者不一致是正常的（自动挂载、手动挂载、挂载失败都会造成），排障时**永远以实际为准**。一个目录本来有独立挂载、但在某次变更中被注释掉或挂载失败后退化到根分区，这类退化只能靠挂载关系与挂载单元状态发现。
- **深入**：规划文档里写着「日志盘 `/var/log`」与实施后它真的在一块独立盘上，是两件事；规划阶段的假设必须在实施后验证一次。写入报「空间不足」时，如果它落在根分区而不是数据盘，那么「给日志盘留了 1 TiB」这个前提从一开始就不成立。
- **衔接**：归属核对无误而问题仍在时，「还有空间为什么写不进去」拐主线三节点 1 与节点 2。

### 3.4 遮挡：挂载不删除内容

- **先答**：挂载把一个文件系统的根接到目录树的某个目录上，**挂载点上原有的内容被遮住，而不是被删除**；原内容仍在原文件系统里，卸载后重新可见，或者从上层用绑定挂载查看。
- **举证**：`df` 报的是该文件系统超级块记载的已用块与可用块，因此仍然算着被遮住内容的空间；而 `du` 遍历的是当前目录树，遍历不到它——两者表现不同不是工具坏了。**最危险的动作是在被遮住的目录里重新创建同名文件**，那会在新文件系统里留下第二份数据，而原数据仍在下面，两份内容从此再也对不上。
- **深入**：同一位置还有两类条目容易被当成分区——内存文件系统（tmpfs，`/tmp`、`/dev/shm`、容器的临时目录常用它）**占的是内存不是磁盘**，`df` 里的容量条目与物理盘没有关系；联合挂载的条目由容器运行时管理，与任何一块盘都不对应。这一层被遮住的数据长期没人处理时，它占用的空间会一直算在原文件系统头上，表现为「根分区没放什么东西却快满了」。
- **衔接**：容器里的遮挡与口径失效拐节点 6；要真正让被遮住的数据重新可见需要卸载，而卸载是最后手段，代价与顺序拐主线五节点 4。

### 3.5 差额四类：`df` 与 `du` 对不上的落点

- **先答**：`df` 与 `du` 量的是不同的东西，差值本来就应该存在，需要解释的是**差在哪一类**，而不是断定某个工具不准。四类分别是：已删除但仍被进程持有的文件、被挂载覆盖的目录、保留块与元数据、稀疏文件与延迟分配。
- **举证**：每一类有独立的证伪字段——已被持有的删除文件看 `lsof +L1`（**它的语义是「链接数小于 1」**，输出的每一行是一个仍持有该文件的进程），被挂载覆盖的目录看 `findmnt -T`，保留块与元数据看 `tune2fs -l` 的 `Block count` 与 `Reserved block count` 两个字段之比，稀疏文件看 `stat` 的 `Size` 与 `Blocks`。四类之外还有一处执行条件要核：`du` 有没有带 `-x`，以及有没有因为权限不足静默跳过一部分目录。
- **深入**：「删了大文件空间不降」是四类里的第一类，它的机制是删除分两步——从目录项移除名字、inode 的链接数减一；**只有链接数归零并且没有任何进程持有它的打开句柄时，才释放 inode 与数据块**。因此处置方向是让持有者关闭句柄（重载或重启该进程），不是再删一遍；截断句柄（写入 `/proc/<pid>/fd/<n>`）会带来写入空洞与日志错位，属于评估过风险之后的最后手段。`sync` 与丢弃缓存都不改变任何计数字段：前者不会让 `df` 的已用块下降，后者只是把页缓存这份性能资产扔掉。
- **衔接**：保留块同时是主线三的上限之一，拐主线三节点 2；容器里同一个现象会指向另一个层次，拐节点 6。

### 3.6 联合挂载：同一路径两个视角

- **先答**：联合挂载（union mount，Linux 上的实现是 overlayfs）把若干只读下层与一个可写上层叠成一个视图，它不是在块设备层拼容量，而是在查找路径这一层做合并；因此**联合挂载的可用空间是上层所在文件系统的可用空间**，下层的镜像层占的是另一份空间。
- **举证**：三件事必须一起看——`df` 的可用量、下层的只读占用、上层所在文件系统的水位。容器里删除文件在上层留的是**白障**（whiteout：设备号为 0/0 的字符设备，或带 `overlay.whiteout` 扩展属性的零长文件），下层数据仍在，所以宿主占用不降；删除整个下层目录留的是 **opaque 属性**，使下层同名目录整体不再参与合并，普通列举看不到它。首次写一个下层文件会触发 **copy-up**，**写放大**的规模是文件大小本身，而不是你这一次打算写入的字节数。
- **深入**：`stat` 报出的 `st_dev` 与 `st_ino` 可能来自上层、也可能来自下层，而且一个非目录对象的 inode 在 copy-up 之后会改变；只有当所有层位于同一个文件系统、或启用了把底层标识合成统一编号的特性（`xino`）时，对外才表现得像普通文件系统。因此依赖 inode 做判断的工具（硬链接去重、增量同步、审计比对）可能给出与直觉相反的结果，容器里 `stat` 出来的 inode 与宿主看到的对不上不是工具坏了，要改用按路径与内容比对。
- **衔接**：「容器里 `df` 还有空间却写不进去」要回到主线三节点 1 先分 errno，再回本节点核对可用空间的口径；容器里的进程归属、僵尸与 PID 1 一类问题属于进程章的口径，这里只划界。

## 4. 主线三：容量上限与拒绝写入

这条线对应知识地图里的第二个跨阶段的核对对象「容量上限与拒绝写入」，它贯穿成型、上岗、长大与冗余和退役四个阶段。它按「拒绝写入的是哪一个上限」走：上限的载体不同，查文档和改配置的地方就不同，而扩容只对容量本身那一类有效。

**入口提问**：「还有空间为什么写不进去」「`No space left on device` 和 `Disk quota exceeded` 有什么区别」「inode 满了怎么办」「扩容能不能解决 inode 耗尽」「配额配了为什么不生效」「改了 `limits.conf` 服务为什么不生效」「监控漏事件却不报错」「共享目录怎么划边界」。

```mermaid

  B --> C["ENOSPC 内部三支<br/>数据块 · inode · 保留块"]
  C --> D["配额<br/>对象 · 软硬限 · 记账"]
  D --> E["不占字节的上限<br/>句柄与 inotify"]
  E --> F["边界配在哪一层<br/>与治理产物"]
```

### 4.1 先看报错原文：三个 errno

- **先答**：拒绝一次写入的理由至少有七种，它们**共用几句高度相似的报错文本，处置方向却完全不同**；因此第一步永远是看报错原文——`No space left on device` 是 `ENOSPC`，`Disk quota exceeded` 是 `EDQUOT`，`Read-only file system` 是 `EROFS`，三者指向三条互不重叠的路径。
- **举证**：`ENOSPC` 内部还分三支（数据块用尽、inode 用尽、ext4 保留块），判据分别是 `df` 的可用块降到 0、`df -i` 的可用 inode 数降到 0、以及 root 能写而普通用户写不进去这一现象；`EROFS` 的上限不是容量，而是内核把该文件系统置为只读的保护动作，方向与扩容相反。剩下的两类是 thin pool 写满（常见为写失败或整组变只读）与句柄或用 inotify 上限（报 `too many open files`，也可能借用 `No space left on device`）。
- **深入**：**扩容对所有非容量类的「满」都无效**——配额、只读、句柄、inotify 四类里，扩容不仅无效，还会掩盖真正的问题、延长故障时间。「磁盘满」是一个待细分的判断，不是一个结论。
- **衔接**：inode 那一支拐节点 3；保留块与元数据同时参与 `df` 与 `du` 的差额，拐主线二节点 5；配额拐节点 4。

### 4.2 七个上限的载体与查询入口

- **先答**：七类上限的**载体不同**，因此查文档和改配置的地方也不同——数据块与 inode 在文件系统的内部结构里，保留比例是文件系统的可调参数，配额在挂载选项加配额子系统上，句柄在会话限制、服务单元属性与内核参数三处，inotify 在内核参数上，池水位在卷管理器的元数据里，只读是内核的保护动作。
- **举证**：逐类有各自的查询入口——`df -h` 的 `Use%` 与 `df -i` 的 `IUse%`、`tune2fs -l` 的 `Reserved block count`、`repquota` 的报表与 `xfs_quota` 的 `report`、`ulimit -n` 与 `/proc/<pid>/limits` 与服务单元的 `LimitNOFILE`、三个 `fs.inotify.*` 值、`lvs -o data_percent,metadata_percent`、`findmnt` 的 `OPTIONS` 列里的 `ro`。
- **深入**：排查顺序是固定的——先看报错原文，再确认写入路径属于哪个文件系统，然后逐项排除。少了第二步，后面每一步都可能是在回答另一个文件系统的问题。
- **衔接**：写入路径的归属拐主线二节点 3；只读的机制与处置拐主线四节点 3；池水位的治理阈值拐节点 6。

### 4.3 inode 耗尽与「扩容能不能解决」

- **先答**：ext4 的 inode 总量在 `mkfs` 时就确定了，因此会出现**块仍有剩余而 inode 数已经达到上限**这一反直觉现象；典型元凶都是「文件多」而不是「文件大」——会话文件、邮件队列、缓存目录、容器可写层、日志切片、CI 的工作目录。**报错文本与容量耗尽相同**，`ENOSPC` 只说明「文件系统上没有可用资源」，不区分是块还是 inode。
- **举证**：判据是 `df -i` 的 `IUse%` 与 `IFree` 同容量使用率一起读——「文件多」的观测量是 inode 使用率上升而容量使用率不动。只监控容量不监控 inode，这类故障一定会漏，而且在 ext4 上往往**比容量先满**。
- **深入**：「扩容能不能解决」要分开说：`resize2fs` 扩大 ext4 时**会按原有比例新增 inode**，所以扩容到两倍通常确实能让 inode 用量降下来；但它**没有改变这个比例**，同样的海量小文件增长下去迟早再次撞满，而扩容的代价是动存储，比清理过期文件高得多。正确的答案是三件事一起做：短期清理、长期换 XFS 或重建 ext4 并调小每 inode 字节数、监控补上 inode 水位。XFS 的动态 inode 分配几乎不会出现这类故障，但这不等于它的 inode 无限——它通过 `maxpct`/`imaxpct` 限制 inode 可占用的空间比例，只是默认值足够宽松。
- **衔接**：选型一侧的判据拐主线一节点 2；监控与告警一侧拐节点 6。

### 4.4 配额：对象、软硬限与记账

- **先答**：配额不是单一的一刀切，而是三个参数协同——硬限制（`bhard`/`ihard`）超过即拒绝写入并报 `EDQUOT`，软限制（`bsoft`/`isoft`）超过只告警但要在宽限期内降下来，宽限期是超过软限后仍允许继续写入的时长。配额按对象分三种，**选错对象是「配了不生效」的第二大原因**。
- **举证**：用户配额绑在 uid 上、组配额绑在 gid 上、项目配额绑在**一个目录树**上；共享目录里的文件往往由同一个服务账号写入，此时用户配额和组配额把所有人算成一个对象，起不到隔离作用，而项目配额把边界钉在目录树上，与业务目录一一对应，既能解释也能追溯。**头号原因是记账**：记账与强制是两件事，而且**记账只能在挂载时打开**（ext4 的 `usrquota`/`grpquota`，XFS 的 `uquota`/`gquota`/`prjquota`），挂载之后工具只能开关强制，不能补开记账。
- **深入**：判据是配额报表里的用量、软硬限与宽限期状态；若报表显示用量远低于限额却仍报配额错误，要回头查记账是否真的开着。**配额不是告警的替代品**——没有监控的配额只是把「写满整盘」换成了「写满自己的配额」，业务照样不可用，只是影响面从全机缩小到一个租户。三者缺一都不完整：只设硬限会让业务在峰值时被突然打断，只设软限等于没有边界，不留宽限期则软限退化成硬限。
- **衔接**：「多租户共享盘被一个租户写满」的完整处置、配额策略表与空间对账表两件产物在《容量与限制治理》第 4 节；边界为什么是可用性手段拐节点 6。

### 4.5 不占字节的上限：句柄与 inotify

- **先答**：有一类「满」与容量完全无关，只与**计数**有关。句柄（fd，file descriptor）有三级上限——单进程软硬限制（会话的 `ulimit -n`、systemd 服务的 `LimitNOFILE=`、登录会话的 `limits.conf`）、单进程天花板 `fs.nr_open`、全系统 `fs.file-max`；inotify 有三道上限——`fs.inotify.max_user_watches`、`max_user_instances`、`max_queued_events`。
- **举证**：三级里最容易搞错的是第一级，**终端里的 `ulimit -n` 与 systemd 服务的 `LimitNOFILE=` 是两套东西**，所以「改了 `limits.conf` 却对某个服务无效」几乎总是这个原因；判断一个**运行中**的进程实际生效多少，要看它自己的 `/proc/<pid>/limits`，而不是当前 shell 的 `ulimit`。inotify 的三道上限表现各不相同，其中 `max_queued_events` 太小**不会让任何调用失败，只是让事件在队列里被丢弃**，因此监控类应用会少看到一部分文件变化并且不报错。
- **深入**：调大上限之前必须先问一句——**这个应用为什么需要这么多 watch 或句柄**？常见根因是设计问题（递归监控整个代码仓库、给每个文件建一个独立 watch、每次请求新建连接而不复用）；上限是保护机制，它把单个应用占用的 watch 数与句柄数限制在全局计数上限之内，调大上限只是缓解，改设计才是修复。内核默认值不是一串小常数：`max_user_watches` 由内核按可寻址内存的一定比例计算并夹在一个上下限之间，`max_user_instances` 是固定值，实际值在发行版与版本之间差异很大，**必须现场取**。
- **衔接**：这类问题之所以放在存储章，是因为触发条件与文件数量强相关，常与 inode 类问题同时出现，而报错文本又常与磁盘问题混同；判断顺序是先确认是「字节的满」还是「计数的满」，拐节点 1。

### 4.6 边界配在哪一层，以及要交出的产物

- **先答**：上限分散在四类载体上，修改方式、生效时机与故障形态都不同——一个目录树的总量用文件系统的配额，一个池的总量用卷管理器的池水位（数据与元数据各一道），一个进程的资源用会话限制、服务单元属性与内核参数，一类事件监控用内核参数。**目录级的边界应当设在目录树上，而不是设在账号上。**
- **举证**：判断一个上限配得对不对，标准不是「用得少不少」，而是「撞上它的时候，坏掉的是不是只有它自己」——配额把故障域从整机收缩到一个租户，属于可用性手段，它与扩容互补而非互斥：扩容解决总量不够，边界解决分布失控。池水位是容量治理而不是性能治理，把精简置备的超配比例拉满，等于把「业务不会同时写满」这个假设当成必然。
- **深入**：治理要同时回答三个问题——技术边界在哪、怎么被观测（容量、inode、池的数据与元数据使用率都要进监控，且是与增长趋势比较）、怎么被追溯（谁在什么时候改过谁的额度，依据是什么）。只有第一条的方案会在下次事故里重演。四个治理场景各有产物：给共享目录划边界产出**配额策略表**与变更记录，一个租户写满之后产出**空间对账表**，同批次硬件治理产出**巡检记录表**与**排期表**，变更的可回滚性产出**变更单模板**。
- **衔接**：「只报容量的监控一定会漏」——至少五类故障不体现在容量水位上（inode 耗尽、配额达到硬限、池的数据或元数据水位、句柄与事件队列上限、介质健康与阵列状态），回写积压与重建退化则表现为延迟，拐主线五节点 6 的基线项。

## 5. 主线四：写入的保证与完整性

这条线对应知识地图里的第三个跨阶段的核对对象「写入顺序与完整性证据」，它贯穿上岗、长大与冗余和退役三个阶段。它按「写返回了到底算不算数」走：先讲清保证到哪一步，再讲出错时内核在保护什么，最后落到「哪些动作不可逆、顺序为什么必须固定」。

**入口提问**：「`write` 返回成功数据就安全了吗」「怎么保证落盘」「崩溃之后为什么还能挂上」「ext4 出错会自动变只读吗」「文件系统变只读怎么办」「崩溃了直接 `e2fsck -y` 行不行」「修复工具能不能在挂载状态下跑」「哪些动作不可逆」「快照能不能当备份」。

```mermaid
flowchart LR
  A["write 返回<br/>只说明进了缓存"] --> B["日志重放<br/>一致性不是完整性"]
  B --> C["保护动作<br/>只读意味着已经出过错"]
  C --> D["不可逆动作<br/>动手前先有回退副本"]
  D --> E["处置顺序<br/>取证在最前、恢复可写在最末"]
  E --> F["回退路径的时效<br/>快照不是备份"]
```

### 5.1 `write` 返回不等于落盘

- **先答**：一次 `write` 系统调用返回成功，含义是「内核已经收下了这些字节」，不是「设备已经记住了它们」；默认路径上数据先被复制进 Page Cache（页缓存），函数立刻返回，真正的落盘由内核稍后异步回写（writeback）完成。这个设计换来的是吞吐，代价是**「写入成功」与「数据安全」之间出现了一个窗口**。
- **举证**：窗口什么时候关闭由调用方决定——`write` 返回只保证数据在内核缓存里；`fsync`（或 `fdatasync`）保证数据与必要的元数据都在设备上，代价是每次调用触发一次等待设备的 IO，延迟可达毫秒级；`sync` 是系统范围的全局动作，影响所有进程；直接 IO（`O_DIRECT`）绕过页缓存，代价是失去缓存收益。因此「写很快」不能用来评估持久化能力，不带同步的写入测的是内存速度。
- **深入**：**落盘顺序比落盘速度更容易出事**——应用常常有隐含依赖（「先写数据文件，再写它的元数据索引」），如果两次都只是进了缓存，回写顺序不保证与调用顺序一致，崩溃后可能看到「索引指向不存在的数据」。要保证顺序必须在两次写之间显式同步，或者依赖文件系统的顺序保证（ext4 的默认日志模式会先落数据再提交元数据，这是它默认模式的语义，不是所有模式都如此）。追加写与覆盖写在崩溃后的结果也完全不同：顺序追加最坏是「末尾少一段」，就地覆盖可能既不是旧值也不是新值，这正是日志结构、预写日志与写时复制这类设计存在的理由。
- **衔接**：「写入变慢」多数不在这一层而在回写链，拐主线五节点 3。

### 5.2 日志重放：一致性不是完整性

- **先答**：日志（journal）的做法是先把「要改什么」顺序写进一块连续的日志区，再回头改真正的元数据；崩溃后重新挂载时，内核扫描日志并**重放（replay）**，把已提交但没改完的变更补齐、把没提交的变更撤销，结果是文件系统回到一个**一致**的状态——不是「未受损」的状态。
- **举证**：三条边界每一条都会在排障里用到——重放保证一致性、**不保证数据完整性**（日志里可能只有元数据，正在写入的文件内容可能有部分丢失，因此日志不是备份，也救不回误删的文件）；大多数崩溃后重启**不需要人工修复**，挂载时内核会自动重放日志，失败才需要手动介入；修复工具与日志是两条不同的路径，**修复工具必须在文件系统未挂载（或至少只读）的状态下运行**，因为挂载着修时内核的元数据缓存与工具的改写会互相覆盖。
- **深入**：XFS 的 `xfs_repair` 默认就对已挂载设备直接拒绝——这是保护设计，不是缺陷。`xfs_repair -L` 会**丢弃日志**，用在「日志损坏到无法重放」的场景，代价是尚未落盘的元数据变更永久丢失；ext4 侧的对应风险点是 `e2fsck -y`，它的含义是「所有问题都自动回答 yes」，在元数据自相矛盾时，工具的选择可能是删掉「有数据的那一边」。
- **衔接**：这两个参数与其余不可逆动作的完整清单拐节点 4；「崩溃了直接 `-y` 硬修一遍」是《高频误判》第 9 条的形态。

### 5.3 保护动作：只读意味着已经出过错

- **先答**：文件系统在运行中检测到不一致或底层 IO 错误时，有一组自我保护动作，看到这些现象时要知道系统在保护什么：文件系统被重新挂载为只读是阻止损坏继续扩散到更多元数据，报介质错误是报告底层设备问题，日志重放是把已提交的元数据变更补齐，阵列降级是用冗余数据继续服务，进程进入不可中断睡眠是在等 IO 完成。
- **举证**：这里有一个**必须现场确认**的前提，也是最容易搞反的一点——**ext4 的默认出错行为是「标记并继续」（`errors=continue`），而不是「重新挂载为只读」（`errors=remount-ro`）**；也就是说，没有显式配置时内核检测到错误并不会自动把文件系统切成只读，它会继续带着已知的损坏往下写。默认值由创建时的默认值与挂载选项共同决定，发行版还可以通过配置文件改默认值，因此**不能凭发行版猜**。判据是 `findmnt` 的 `OPTIONS` 里有没有 `ro`，加上内核日志里介质错误、IO 错误与控制器重置的片段。
- **深入**：只读是内核在保护数据，**它意味着已经出过错**，所以第一动作是取证而不是恢复写入——重新挂载为可写等于让它带着已知的损坏继续写，而当时的内核日志是唯一能说明根因的证据。根因判断要把**介质故障与元数据损坏分开**：若硬件计数显示待处理坏扇区或介质错误，根因在设备上，此时做文件系统修复等于在坏盘上折腾数据，**先保数据、先换盘**。
- **衔接**：健康计数的读法拐主线一节点 6；只读的另一来源是容器运行时把层挂成了只读，容器环境里按存储故障的路子查会一无所获，划界见主线二节点 6。

### 5.4 不可逆动作清单与共同前置条件

- **先答**：存储故障处置与内存、CPU 类故障最大的区别是**很多动作没有「再试一次」的机会**，因此它们必须在动作之前被识别：建文件系统、`wipefs` 不带 `-n`、整设备擦除、`xfs_repair -L`、缩小文件系统、缩小卷、`e2fsck -y`。
- **举证**：每一条的不可逆点不同——建文件系统立刻用新文件系统的超级块与元数据覆盖原内容；`wipefs` 直接擦掉分区表与文件系统签名；整设备擦除立刻清空全部数据，只用于已下线或回收前的盘；`xfs_repair -L` 丢掉尚未落盘的元数据变更；缩小文件系统在 ext4 上顺序错一步就切掉正在使用的区域，XFS 完全不支持；`e2fsck -y` 在元数据自相矛盾时可能删掉有数据的一边。
- **深入**：有一类前置动作是所有不可逆操作共用的——**动手前先取一份能回退的副本**，可选形态按代价从低到高是文件系统级的元数据副本（体积极小，适合留证与送分析）、卷级快照（快、有性能代价、会随写入增长）、块级快照（云盘或存储阵列提供，最完整）、完整镜像（最贵，但独立于原设备）。前置条件还要包括确认根因，避免在坏硬件上折腾数据。
- **衔接**：副本的时效拐节点 6；「换盘」本身也是不可逆动作，它的顺序拐主线一节点 6。

### 5.5 处置顺序为什么必须固定

- **先答**：把全章的处置动作排成一条时间线，会看到一条清晰的分界——**变慢是可逆的，写坏是不可逆的**；回写积压、重建限速、队列排队都只影响延迟，可以调优、可以等待，而文件系统只读、介质错误、阵列降级涉及数据风险，必须**先取证、先停写、先备份**。
- **举证**：顺序固定为九个动作——取证、判断根因、停止写入、卸载文件系统、做一次只读且不修改的干跑检查、备份、正式修复、修复后先只读挂载核对数据、核对无误才恢复可写。其中三个判断不可省略：介质故障与元数据损坏要分开；干跑检查必须排在正式修复之前，因为它回答的是「问题规模有多大」，而很多场景（尤其是崩溃后）根本不需要修复；修复后先只读挂载核对数据，少了这一步就无从判断问题出在修复还是别处。
- **深入**：这条顺序的代价要具体说出来——取证多花几分钟，换来的是能区分「修复引入的」与「别的原因」；卸载会中断业务，所以它排在取证之后；而在影响面还在扩大时，先摘流量把业务拉回来是对的，但动手之前要记下当时读到的数字。验收要用业务能感知的指标，而不是「命令没报错」。
- **衔接**：这条顺序的前半段（取证与根因判断）用到的字段拐节点 3 与主线一节点 6；「一份合格的回答应当包含结论、依据、边界与动作」的样板在《观测与基线》第 3.4 节。

### 5.6 回退路径的时效

- **先答**：卷级快照的机制是写时复制，它不复制全部数据，原卷后续被写入时旧块才被复制到快照空间；这决定了它的三个性质——**会增长**（原卷写得越多，快照消耗的空间越多，快照空间用尽时直接失效）、有性能代价（原卷的每次写入都可能多一次复制）、**不是备份**。
- **举证**：正确用法是在备份或变更窗口内做一份临时快照，用完即删。真正需要防的场景（盘坏、误删覆盖整盘、加密勒索、机房级故障）只能靠异地或离线备份，因为快照依赖原卷、与原卷同盘，它的生命周期通常只有一次维护窗口那么长。**把快照当长期备份，等于把「今天能回滚」当成「下个月也能回滚」。**
- **深入**：RAID 与备份的验收方式完全不同——冗余对抗硬件失效，备份对抗数据错误与人为失误，「有 RAID 就有备份了」是最常被误解的一条。同一类边界也适用于日志：它保证一致性，不保证数据内容，也救不回误删。快照还是这条处置顺序里唯一的回退路径，快照过期之后整条顺序不再有回退路径。
- **衔接**：快照的用量要进监控与巡检，拐主线三节点 6；「不可逆动作的共同前置条件是一份能回退的副本」回到节点 4。

## 6. 主线五：变慢的定性与分层

这条线不落在五个阶段中的任何一个，而是由原理《写入路径与完整性》与实操《观测与基线》的两个场景（设备侧指标很高、网络存储不可达）构成的一条独立提问链；故障现场定位表里「设备完成时间很高」「写入变慢、进程进不可中断睡眠」「整机容量命令卡住」「网络存储对端抖动」「闪存盘写入变慢」五行都属于它。它按「慢在哪一层」走，因为「变慢」与「写坏」的处置顺序相反，先把这一侧分清，后面的动作才不会互相抵消。

**入口提问**：「IO 慢是不是盘慢」「换个快盘能不能解决」「`await` 高是不是盘要坏了」「`%util` 接近 100% 是不是饱和」「写入变慢、进程进了 `D` 状态」「整机命令都卡住、大量进程不可中断睡眠」「闪存盘写入变慢要不要做 TRIM」「重建期间业务变慢怎么办」「采样要采几次」。

```mermaid
flowchart LR
  A["先分层<br/>设备指标只覆盖最后一层"] --> B["设备侧组合判读<br/>await 与 aqu-sz"]
  B --> C["回写积压<br/>脏页与两条阈值"]
  C --> D["网络存储<br/>处置对象是通路"]
  D --> E["闪存<br/>回收与寿命都是趋势"]
  E --> F["采样纪律与基线<br/>两次读数与原始输出"]
```

### 6.1 先分层：设备指标只覆盖最后一层

- **先答**：一次 IO 从应用出发到落上介质要经过若干层——应用决定写入模式、同步频率与并发度，系统调用经虚拟文件系统转发给具体文件系统，文件系统处理元数据操作与挂载选项后交给 Page Cache 与回写机制，回写把请求下发到块层，块层决定队列深度、预读与调度策略，最后经设备驱动送到介质。**观测工具大多只能看到最底层**，因此「设备看起来很闲」不等于「存储不是瓶颈」，也可能是请求还没走到设备。
- **举证**：读与写在路径上完全不对称——读命中缓存时就结束了，不碰设备；未命中则要走到底层，随机访问最吃介质能力；写默认只进缓存就返回。所以「读慢」与「写慢」的排查起点不同：读要问命中率与介质随机能力，写要问回写链与设备排空速率。
- **深入**：介质能力的量级必须知道，否则读不懂数字——机械盘的随机小 IO 在百级、SATA SSD 在万级、NVMe 在十万到百万级（单位都是每秒请求数），顺序带宽从百 MB/s 到 GB/s 级，延迟从毫秒级到几十微秒级。**这些都是量级，不是验收标准**，具体数值随型号、队列深度、块大小与阵列缓存策略变化极大；它们的用途只有一个：判断一个数字是「正常」「偏高」还是「离谱到不可能是这个原因」。调优项的收益与代价也要成对看——提高预读对顺序读有帮助而对随机读浪费带宽，加深队列能吸收突发但会拉长延迟。
- **衔接**：「换个更快的盘为什么常常无效」在本节点答完；设备侧的具体判据拐节点 2。

### 6.2 设备侧的组合判读：`await` 要配 `aqu-sz` 读

- **先答**：`await` 是平均完成时间（单位毫秒）**并且包含排队时间**，这是它最容易被误读的地方——`await` 高不等于设备坏。判据是把 `await` 与 `aqu-sz`（平均队列深度，旧版本叫 `avgqu-sz`）放在一起读：两者**同涨**说明请求量超过了设备处理能力，属于排队；`await` 高而**队列浅**才是设备或链路本身慢。
- **举证**：组合判读比任何单列都可靠——`await` 与 `aqu-sz` 同高而单队列设备的 `%util` 也高，方向是找源头进程、错峰、限流；`await` 高而 `aqu-sz` 低，方向是查介质健康、阵列缓存与电池、网络存储链路；写 `await` 高且脏页高，方向是回写链。`r_await` 与 `w_await` 要分开看，因为写还牵涉回写与阵列缓存策略；`rareq-sz` 与 `wareq-sz` 是平均请求大小，用来区分随机小 IO（4 KiB 级）与顺序大 IO（1 MiB 级）。`%util` 是设备忙于处理 IO 的时间比例，它在单队列设备上接近 100% 基本等于饱和，**在多队列设备（NVMe 典型）上经常接近 100% 却远未饱和**；`svctm` 已废弃，不要再用它下结论。
- **深入**：两条边界——`iostat` 的**第一行是自开机以来的平均值**，判断「现在正在发生什么」必须从第二行起看；`await` 与 `aqu-sz` 都正常而业务仍慢，说明瓶颈不在设备侧，要往上查应用、缓存与元数据操作。「排队」与「设备退化」的处置动作相反，所以配对读这一步不能省——把排队当退化会付出换硬件的成本而没有改善，此时加深队列只会让延迟更高，属于反向操作；把退化当排队则会让故障继续。
- **衔接**：「设备是不是在退化」拐主线一节点 6 的健康计数与内核日志；下钻到进程与文件用 `iotop -oPa`、`pidstat -d` 与 `/proc/<pid>/io` 的 `read_bytes`/`write_bytes`（**`rchar`/`wchar` 统计的是应用请求的字节数，包含命中缓存的部分，不能用来判断落盘量**），完整顺序在《观测与基线》第 2.7 节与第 3.2 节。

### 6.3 回写积压：脏页与两条阈值

- **先答**：脏页积累到一定量后内核启动后台回写，超过更硬的阈值后**发起写的进程会被限速甚至阻塞**，直到脏页排空到自己该承担的那一份。这是「写入变慢」最常见的机制来源，它的特征是存储设备本身没有报错、健康也没有变化，而应用表现为间歇性卡顿、写延迟出现长尾、进程进入不可中断睡眠。
- **举证**：分清楚方向的办法是看**配对指标**——脏页量是否贴着阈值（`/proc/meminfo` 的 `Dirty` 与 `Writeback`），与设备侧的排队深度和完成时间是否同时升高。两者组合能区分「请求在设备队列里排队」与「写者被回写机制按住」，这两条路的处置完全不同：前者在设备与写入模式，后者在参数与刷盘节奏。
- **深入**：阈值有比例与字节数两种写法，**两族互斥，实际生效值现场取**；它们只决定「何时开始回写」与「何时开始限速」，不决定设备能不能跟上。因此「写入卡顿就把脏页上限调小」只在一种情况下有效——瓶颈确实是回写限速本身；如果设备排空速率本来就低于产生速率，收紧上限只会让限速更早启动，**总吞吐不会变好，反而可能更差**。此外**丢弃缓存是测量动作，不是优化动作**，生产上不要执行它：被丢掉的是纯性能资产，此后业务必须为重建缓存重新付出 IO，而内存并不会因此变得「更够用」。
- **衔接**：「是回写限速还是设备排队」拐节点 2；「回写积压与介质故障是两种结局」拐节点 4 与主线四节点 3。

### 6.4 网络存储：处置对象是通路而不是进程

- **先答**：网络存储把「一次 IO 有多快」拆成了三个独立变量——本地路径、网络、对端存储。对端不可达时，客户端的行为由一个语义选项决定：**硬挂载**（`hard`，常见默认）无限重试，访问该挂载点的进程停在不可中断等待；**软挂载**（`soft`）超时后把错误返回给应用，代价是**可能产生静默的数据不一致**，因为写入可能只完成一部分。
- **举证**：关键机制在于停在不可中断等待里的进程等待的是内核里的 IO 完成，**信号要等它回到用户态才会被处理**，所以「杀进程」既无效也不解决问题。这也是为什么软挂载通常只用于只读或本身能安全重试的场景，而写场景宁可等待。多路径（同一块存储设备通过多条物理路径可达）解决的是链路冗余，但它有一个业务侧必须知道的副作用——**路径切换会造成秒级 IO 停顿**，业务的超时设置如果短于这个停顿，就会看到「存储没问题但请求超时」。
- **深入**：网络存储的排障顺序与本地存储不同——**先确认通路（对端、网络、路径状态），再谈本地动作**；通路恢复后等待状态会自行消解，业务随之恢复。而在本地能做的动作里，卸载是最后手段，因为强卸不会让进程停止写入，只会让它们继续写到一个已不在目录树里的文件系统上。挂载配置还会把局部故障升级成启动故障：网络存储的挂载必须同时声明「网络就绪之后再挂」与「挂不上也不阻塞启动」，少了后者，对端不可达时本机可能进不了系统。重启排在所有动作之后，因为**存储未恢复时机器可能卡在启动过程中**，而重启还会清掉现场。
- **衔接**：「整机容量命令卡住、大量进程不可中断睡眠」在本节点答完；挂载选项一侧的验收拐主线一节点 3；「慢与坏要先分开」拐主线四节点 5。

### 6.5 闪存：回收通知与寿命都是趋势问题

- **先答**：闪存的写入以页为单位，而擦除以更大的块为单位，改写一个页时必须先把它所在的整块擦掉，这个约束带来写放大与回收两件事。**回收通知（TRIM）就是文件系统把「哪些块里的数据已经被删掉了、可以安全擦除」告诉盘的动作**，它的收益是维持长期写入性能与减少无谓的擦写。
- **举证**：它**不是性能开关**——它解决的是盘的长期写入效率，不是「这台机器现在慢」，一次性执行不会带来可见的性能提升。做法有两个决策点：定期批量下发（时机可控、影响可预期，是常规做法）与删除时立即下发（挂载选项，不需要额外调度，但在部分盘上会造成延迟抖动，只适合对延迟不敏感的场景）。寿命评估的判据是**这些字段相对厂商阈值的位置与增长速度**，而不是单次读数。
- **深入**：闪存盘会报告已消耗寿命的比例与备用块余量，还会报告异常掉电次数与数据完整性错误计数；其中「完整性错误非零」属于需要立即介入的一类，因为它意味着数据已经出错，不是盘在变慢。**`%util` 在闪存盘上参考价值有限**，不要把它当闪存盘的饱和判据写进告警。整设备擦除是破坏性动作，它立刻清空全部数据，只应当用在已下线或待回收的盘上，且执行前必须核对设备身份。
- **衔接**：寿命字段的趋势判断与替换排期拐主线一节点 6；同批次盘的批量替换计划拐主线三节点 6。

### 6.6 采样纪律与基线

- **先答**：单点读数说明不了任何问题，因此采样有四条纪律——**同口径**（同一命令、同一单位、同一进制，`df -h` 与 `df -H` 的数字不能直接比）、**带时间戳**（否则趋势无法建立）、**至少两次**（判断「现在正在发生什么」至少要两行，工具的第一行是累计平均值）、**留原始输出**（只抄一个数字等于丢掉上下文）。
- **举证**：一份可复用的存储基线卡至少要有七组内容——环境、身份、结构、水位、挂载、健康、边界。**缺一项，半年后这份数据就不可比**，尤其是「身份」与「挂载参数」：容量数字随时在动，而型号与参数决定了这些数字在什么条件下才成立。判断泄漏看长期单调上涨，判断容量问题看「稳定在高位但不再上涨」；起步判据只能与自己机器的基线比，没有通用阈值。
- **深入**：**在没有基线的机器上，「存储使用异常」这个判断本身就不成立**，因为没有「正常」可对照。取差值而不取绝对值是一条容易做错的细节——累计型计数（事件次数、阵列重建字节、IO 计数）只有两次读数相减才表达「这段时间发生了什么」。判断抖动按秒采样，判断趋势按小时或按天取样。
- **衔接**：监控的最小集合拐主线三节点 6；「只报容量的监控一定会漏」的清单与产物模板在《容量与限制治理》第 3 节与第 5 节。

## 7. 主线之间的接口

被追问得最多的问题，恰好落在两条主线的接缝上。下表给出接缝处的走法——先说清衔接本身，就是回答的一部分。

| 被问到的问题 | 它落在哪两条主线的接口上 | 怎么走 |
| --- | --- | --- |
| 「还有空间为什么写不进去」 | 主线三的「七个上限」与主线二的「归属」 | 先走主线三节点 1 读报错原文定 errno，再用主线二节点 3 确认写入路径实际属于哪个文件系统；两步都不命中时回主线三节点 2 逐项排除 |
| 「`df` 与 `du` 差了几十 GiB」 | 主线二的「差额四类」与主线三的「保留块与配额」 | 先走主线二节点 5 把差值拆到四类并逐类给字段；其中保留块这一类要回主线三节点 2 读 `Block count` 与 `Reserved block count` 之比，配额这一类要回主线三节点 4 读报表 |
| 「文件系统突然变只读」 | 主线四的「保护动作」与主线五的「设备退化」 | 先走主线四节点 3 说明只读是保护动作、第一动作是取证；再用主线一节点 6 的健康计数与内核日志区分介质故障与元数据损坏，前者先保数据先换盘，后者才谈修复 |
| 「云盘扩容了，业务容量没变」 | 主线一的「扩容六层链」与主线二的「容量口径」 | 先走主线一节点 4 从下往上逐层验收，每一层单独长大；若六层都已验收而业务侧仍不符，拐主线二节点 3 核对业务目录实际属于哪个文件系统 |
| 「写入变慢，进程进了 `D` 状态」 | 主线五的「回写积压」与主线四的「落盘语义」 | 先走主线五节点 3 用脏页与阈值的距离加上设备侧的排队深度和完成时间分开「回写限速」与「设备排队」；再回主线四节点 1 说明写返回只保证进缓存，同步策略是应用设计问题 |
| 「容器里 `df` 还有空间却写不进去」 | 主线二的「联合挂载」与主线三的「上限」 | 先走主线二节点 6 说明容器里的可用量来自上层所在文件系统、删除留的是白障；再走主线三节点 1 读报错原文，因为容器里报 `ENOSPC` 时它的来源常常是配额、池水位或句柄，与字节容量无关 |

## 8. 用法与纪律

- **先答后证**。每个节点先把结论说出去，再补字段；颠倒过来会变成「背了一通机制，但还没回答问题」。
- **每句话指到字段**。凡是落不到一个文件、一列或一位的句子，宁可不说——《盲区排查》把这条作为第 1 层与第 2 层的分界：指不到字段的机制叙述，停在第 1 层。
- **先分变慢与写坏**。回写积压、排队、重建制造的是变慢，它可观测也可调优；只读、介质错误、阵列降级制造的是数据风险，必须先取证再动手。回答时先说明现在处在哪一侧，因为两侧的动作顺序相反。
- **先看报错原文，再确认归属**。三个 errno 分得清、七个上限背得出，都还不算会判断；判断的起点是报错原文与 `findmnt -T` 给出的归属。
- **主线是检索路径，不是逐字稿**。要记的是节点顺序与每个节点的字段锚点；忘了具体展开时，回到「先答、举证、深入」三步现场组织，胜过硬背整段。

## 常见坑

| 常见做法 | 后果或事实 |
| --- | --- |
| 把主线当逐字稿背 | 对方一拐出脚本就接不上；要记的是节点顺序与字段锚点，展开在现场按三步重组 |
| 机制讲得流畅但指不到字段 | 这是《盲区排查》定义的第 1 层——叙述能力不是判断能力，每句话都要自检「这句指到哪个字段」 |
| 用「还有空间」回答「写不进去」 | `ENOSPC` 同时覆盖数据块、inode 与保留块，另有 `EDQUOT`、`EROFS` 与两类不占字节的上限；不看报错原文就没有起点 |
| 用目录名推断文件系统归属 | 目录名不携带这个信息，只有 `findmnt -T` 给出实际归属 |
| 在 `df` 与 `du` 之间选一个「对」的 | 两者量的是不同的东西，正确答法是「差在哪一类」并给出该类的证伪字段 |
| 把只读当成可以随手翻转的状态位 | 只读是内核的保护动作，它意味着已经出过错；第一动作是取证，不是重挂为可写 |
| 一个现象只答一条主线 | 高频问题大多落在主线的接口上（还有空间写不进去、`df` 与 `du` 对不上、变只读、扩容后没变），接口处要把两条主线的衔接说出来 |

## 要点自测

**问：被问「还有空间为什么写不进去」，沿哪条主线走，依次经过哪几个节点？**
答：走主线三。先答三个 errno 的分工与「磁盘满是一个待细分的判断」（节点 1）；举证落到报错原文、`df -h` 的 `Use%` 与 `df -i` 的 `IUse%`、`tune2fs -l` 的 `Block count` 与 `Reserved block count` 之比，以及 `findmnt -T` 给出的归属（节点 2，归属那一句拐主线二节点 3）；深入补扩容的边界——它对非容量类的几类无效，而 inode 那一支即使扩容也只能缓解（节点 3）。若对方补一句「在容器里」，则拐主线二节点 6 说明可用空间的口径。

**问：「`df` 与 `du` 对不上」这条线上，第一个分叉问题是什么？**
答：先问差在哪一类，而不是差多少。四类分别是已删除但仍被进程持有的文件（`lsof +L1`）、被挂载覆盖的目录（`findmnt -T`）、保留块与元数据（`tune2fs -l` 的 `Block count` 与 `Reserved block count`）、稀疏文件与延迟分配（`stat` 的 `Size` 与 `Blocks`）。四类之外还要核 `du` 的执行条件——有没有带 `-x`、有没有因权限不足跳过目录。

**问：「文件系统变只读」的正确回答结构是什么？**
答：四步。先答只读是内核的保护动作、它意味着已经出过错；再给判据（`findmnt` 的 `OPTIONS` 里的 `ro`、内核日志里介质错误与 IO 错误的片段、硬件健康的关键计数）；再说明根因要分成介质故障与元数据损坏，前者先保数据先换盘；最后给顺序——取证、判断根因、停止写入、卸载、干跑检查、备份、修复、只读挂载核对、恢复可写。

**问：「这块盘多大」这句话为什么是不完整的？**
答：因为它没有说清是哪一层、哪个口径、给谁用。从厂商标称到业务可用要经过四次扣减——进位换算、分区表占用与 1 MiB 对齐、文件系统元数据、保留块与配额，每一次都有明确原因、都不是故障。因此问容量时要同时说明读的是设备容量、分区容量、文件系统总容量还是普通用户可用容量。

**问：「IO 慢」沿哪几个节点走，为什么不能只报一个数？**
答：主线五节点 1 给分层——设备指标只覆盖路径的最后一层，请求可能在应用、缓存或回写环节就已经在等；主线五节点 2 给判据——`await` 要配 `aqu-sz` 读，两者同涨是排队、队列浅才是设备或链路本身慢。两句合起来才是完整回答，因为「排队」与「设备退化」的处置动作相反。

**第一反应不要做什么**：不要用「还有空间」否定「写不进去」；不要在没确认写入路径属于哪个文件系统之前讨论空间够不够；不要用目录名推断文件系统归属；不要在没查 inode 使用率之前先删文件；不要在根因未明时扩容；不要看到只读就重挂为可写；不要把快照当备份；不要只看 `await` 一个列就宣布盘要坏了。
