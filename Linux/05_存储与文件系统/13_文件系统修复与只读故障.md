## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **修复工具直接改写元数据结构**；如果文件系统还挂着且可写，内核缓存与工具的改写会互相覆盖，**结果是「修完更坏」**。所以前提是：能卸载就卸载。
> - **ext4 的默认策略是 `errors=continue`，不是 `remount-ro`**：不显式配置时，内核检测到错误只**标记并继续写**——**生产数据盘必须显式加 `errors=remount-ro`**。只有显式配了它，内核才会主动把文件系统重挂为只读；此时重新挂可写，等于让内核带着已知的损坏继续写。（本机 Ubuntu 24.04 实测 `tune2fs -l` 报 `Errors behavior: Continue`。）
> - **安全顺序是固定的**：取证 → 切走业务/停止写入 → 卸载 → 干跑检查 → 备份后修复 → 只读挂载核对 → 恢复写。
> - **XFS 默认拒绝对已挂载设备操作**（这正是保护）；`xfs_repair -L` 会**丢弃日志**，可能丢数据，只在日志损坏且已有备份时用。
> - **先分清是介质故障还是元数据损坏**：前者必须先换盘再恢复（子笔记 08），后者才谈修复；`dmesg -T`/`journalctl -k` 是分界线。

## 1. 为什么必须卸载

修复工具（`e2fsck`、`xfs_repair`）的工作方式是**直接读改磁盘上的元数据结构**：块位图、inode 表、目录树、超级块。

如果此时文件系统处于**可写挂载**状态：

- 内核手里有一份元数据缓存（inode、位图、日志状态），它会继续按自己的理解读写；
- 修复工具在盘上改，内核在内存里改，两边互相覆盖；
- 结果是「修完更坏」，甚至直接把可恢复的数据结构破坏掉。

| 文件系统 | 检查/修复工具 | 关键约束 |
| --- | --- | --- |
| ext4 | `e2fsck`（`fsck` 是它的前端） | 可写挂载时拒绝运行；`-n` 只读检查、`-p` 自动修复安全项、`-y` 全部回答 yes、`-f` 强制检查、`-b 32768` 用备用超级块 |
| XFS | `xfs_repair` | **默认不允许对已挂载设备运行**；先 `xfs_repair -n` 干跑检查；`-L` 会丢弃日志（**有数据丢失风险**） |
| 只读挂载状态 | 保守做法仍是卸载 | 发行版对「只读挂载下能否检查」的说明不完全一致；**最稳的是卸载**，XFS 尤其不要抱侥幸 |

## 2. 安全修复顺序（背下来）

1. **先备份再动手**：块级快照（云盘快照 / LVM 快照）或 `dd` 镜像；`xfs_metadump`/`e2image` 可留元数据副本，体积极小，适合留证。
2. **取证**：`dmesg -T | tail -50`、`journalctl -k`，确认是介质错误、日志损坏还是元数据损坏。
3. **切走业务 / 停止写入**：必要时 `mount -o remount,ro` 先让写入停下来。
4. **卸载**：`umount`；被占用就用 `fuser -vm`/`lsof +D` 找占用者（子笔记 06）。
5. **干跑检查**：`e2fsck -n <dev>` 或 `xfs_repair -n <dev>`，把输出记下来——**很多情况下日志重放就能解决，不需要强修复**。
6. **正式修复**：ext4 用 `e2fsck -f`（有问题时再考虑 `-y` 或备用超级块）；XFS 用 `xfs_repair <dev>`。
7. **只读挂载核对**：先 `mount -o ro` 核对数据完整性，确认无误再改回可写。
8. **写进故障记录**：现象、证据、动作、结果，以及「下次怎么提前发现」。

```bash
dmesg -T | tail -50                  # 验证：内核对这个文件系统说了什么（介质错误？日志重放？）
sudo journalctl -k | grep -i -E 'ext4|xfs' | tail -30
                                     # 验证：本次启动的内核文件系统日志
sudo umount /data                    # 验证：卸载（被占用时用 fuser/lsof 找占用者）
sudo e2fsck -n /dev/<dev>            # 验证：ext4 只读检查，先看问题规模（绝不修改）
sudo xfs_repair -n /dev/<dev>        # 验证：XFS 干跑检查（不写盘）
sudo e2fsck -f /dev/<dev>            # 验证：ext4 强制检查（真正修复；必要时加 -y）
sudo xfs_repair /dev/<dev>           # 验证：XFS 正式修复（慎用 -L，仅日志损坏且已备份时）
sudo mount -o ro /dev/<dev> /mnt/check
                                     # 验证：修复后先只读挂载核对数据
findmnt /mnt/check                   # 验证：OPTIONS 里含 ro
```

> [!warning] 第一反应不要是「看到只读就 `mount -o remount,rw`」
> 文件系统被重挂为只读，意味着**内核已经检测到了错误**。注意前提：**ext4 默认是 `errors=continue`，默认并不会自动重挂只读**，所以生产数据盘要显式配 `errors=remount-ro`；一旦看到只读，重挂可写就是让它带着已知损坏继续写。正确顺序是：
> **取证（`dmesg -T`、`journalctl -k`）→ 切走业务 / 停止写入 → 卸载 → 修复 → 只读挂载核对 → 恢复写。**
> 同时要判断根因：**介质故障**（`medium error`、SMART 报警）必须先换盘（子笔记 08）；**元数据损坏**（日志、超级块、目录结构）才谈修复。

## 3. 常用参数与它们的意思

```bash
sudo e2fsck -n /dev/<dev>            # 验证：只读检查，只报不改
sudo e2fsck -fn /dev/<dev>           # 验证：强制完整检查（仍为只读，耗时更长）
sudo e2fsck -p /dev/<dev>            # 验证：自动修复"安全"问题（启动脚本常用）
sudo tune2fs -l /dev/<dev> | grep -E 'Filesystem state|Maximum mount count|Check interval|Errors behavior'
                                     # 验证：ext4 的干净状态、自动检查策略与出错行为
sudo tune2fs -l /dev/<dev> | grep -i 'backup superblock' -A2
                                     # 验证：备用超级块位置（超级块损坏时的救援入口）
sudo dumpe2fs -h /dev/<dev> | grep -E 'Backup superblock' -A3
                                     # 验证：备用超级块列表（dumpe2fs 的输出更完整）
```

| 参数 | 含义 | 什么时候用 |
| --- | --- | --- |
| `-n` | 只读检查，回答全部 no | **永远先跑这个**，用于评估问题规模 |
| `-f` | 强制完整检查（即使标记为干净） | 正式修复、或怀疑有隐藏问题时 |
| `-p` | 自动修复安全项，不需要交互 | 启动时 `fsck` 的默认行为 |
| `-y` | 所有问题都回答 yes | 确实要修、且已有备份时；**不要当默认选项** |
| `-b 32768` | 使用第 32768 块处的备用超级块 | 主超级块损坏、文件系统挂不上时 |
| `-c` | 顺带做坏块扫描（`badblocks`） | 怀疑介质问题；耗时长，硬盘故障场景要谨慎 |

> [!important] `-y` 不是「更彻底的修复」
> `-y` 的含义是「所有问题都自动回答 yes」。在元数据自相矛盾时，工具的判断可能是把「有数据的那一边」删掉。**先 `-n` 看规模、先备份，再决定是否 `-y`。**

## 4. XFS 的特殊之处

| 项目 | 说明 |
| --- | --- |
| 挂载时修复 | **默认拒绝**：`xfs_repair` 会提示设备已挂载并退出（这正是保护机制） |
| `xfs_repair -n` | 干跑检查，不写盘；先看报告 |
| `xfs_repair -L` | **丢弃日志**：当日志损坏到无法重放时使用，**会丢失那些「只写在日志里、还没落盘」的元数据变更**。只有在日志确实损坏、且已有备份时才用 |
| `xfs_metadump` | 导出元数据副本（体积小），适合在动手前留证或送厂商分析 |
| 自动检查 | XFS **没有** ext4 那种「按挂载次数/间隔自动检查」的机制；`pass` 列通常填 `0` |
| 检查工具 | `xfs_check` 已过时，**用 `xfs_repair -n`** |

```bash
sudo xfs_metadump /dev/<dev> /root/<dev>-$(date +%F).mdump
                                     # 验证：动手前留一份元数据副本（体积小、可送分析）
sudo xfs_repair -n /dev/<dev>        # 验证：干跑，先看报告里有多少问题
sudo xfs_repair /dev/<dev>           # 验证：正式修复（默认会先尝试重放日志）
```

## 5. 与挂载选项的配合

```bash
findmnt -o TARGET,SOURCE,FSTYPE,OPTIONS /data
                                     # 验证：当前挂载是否带 errors=remount-ro、是否已变成 ro
sudo mount -o remount,ro /data       # 验证：应急时先切只读，让业务停止写入（不是修复！）
```

- **ext4**：`errors=continue`（**mke2fs/内核默认**，会让损坏继续扩大，不应用于生产数据盘）、`errors=remount-ro`（**推荐显式配置**，出错即重挂只读）、`errors=panic`（配合 kdump 保留现场）。实际生效值一律用 `tune2fs -l <dev> | grep 'Errors behavior'` 现场确认（默认输出 `Continue`；少数发行版会通过 `/etc/mke2fs.conf` 改默认，不能凭发行版猜）。
- **XFS**：没有同名的 `errors=` 选项，出错时的行为由文件系统自身策略决定。
- **切只读不等于修复**：`remount,ro` 只是让写入停下来，给后续取证与卸载创造条件。

## 6. 生产动作：一次只读故障的处置记录

记录里至少要有：

1. **发现方式**：监控告警、业务报错（什么错误码）、还是内核日志扫描。
2. **现场证据**：`dmesg -T` 与 `journalctl -k` 的相关片段、`findmnt` 的挂载状态（是否 `ro`）、SMART 关键字段。
3. **根因判断**：介质故障 / 元数据损坏 / 掉电或异常重启 / 硬件链路（`UDMA_CRC_Error_Count`）。
4. **动作序列**：切只读 → 停业务 → 卸载 → 干跑 → 备份 → 修复 → 只读核对 → 恢复写，每步的时间与命令。
5. **数据核对结果**：文件数量、关键业务文件校验、应用能否正常启动。
6. **后续**：备份的存放位置、是否换盘、监控项是否需要补充。

> [!example]- 实验 9：干跑检查与只读挂载取证
> **怎么做**：在 loop 文件系统上走一遍「卸载 → 只读检查 → 只读挂载核对 → 恢复读写挂载」，并观察 XFS 对已挂载设备的拒绝。
> ```bash
> LOOP1=/dev/loop0                     # 用你在子笔记 04 实验 1 里记下的环设备名；本机实测为 /dev/loop0，**不要硬编码 loop9**
> sudo umount /mnt/lab
> sudo e2fsck -n "${LOOP1}p1"          # 验证：ext4 只读检查（绝不修改），输出会报告文件系统状态
> sudo e2fsck -fn "${LOOP1}p1"         # 验证：强制完整检查（仍为只读，耗时更长）
> sudo mount -o ro "${LOOP1}p1" /mnt/lab
> findmnt /mnt/lab                     # 验证：OPTIONS 里含 ro
> sudo umount /mnt/lab; sudo mount "${LOOP1}p1" /mnt/lab
>                                      # 验证：确认数据无误后再恢复读写挂载
> sudo xfs_repair -n /dev/vglab/lvdata 2>&1 | head -5
>                                      # 验证：XFS 对已挂载设备会直接拒绝（这就是保护机制）
> sudo tune2fs -l "${LOOP1}p1" | grep -E 'Filesystem state|Errors behavior|Maximum mount count'
>                                      # 验证：ext4 的状态与自动检查策略
> ```
> **预期**：`e2fsck -n` 只报不改；`xfs_repair` 对已挂载设备直接拒绝——**这正是「修复必须在卸载状态下做」的实物证据**。
> **风险**：低。全部作用在 loop 文件上（需要 root）；但**实验前务必先 `umount`**，否则工具会拒绝执行。
> **环境**：任意发行版，需要 `e2fsprogs`（XFS 部分需要 `xfsprogs` 与子笔记 04/07 的实验环境）。
> **耗时**：约 15 分钟。
> **怎么退回去**：恢复读写挂载即可；要彻底清理就跑子笔记 17 的统一清理段。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 文件系统变只读就 `mount -o remount,rw` | 内核是故意重挂只读的；重挂可写会让损坏继续扩大 |
| 在挂载状态下跑 `xfs_repair` | 工具会拒绝（这正是保护）；务必先卸载 |
| 直接 `e2fsck -y` 硬修 | 工具可能在自相矛盾时选择删掉有数据的一边；先 `-n`、先备份 |
| 修复前不备份 | 修复工具可能加重损坏，没有快照等于没有退路 |
| 不区分介质故障与元数据损坏 | 介质有错的盘上做修复，等于在坏盘上折腾数据；必须先换盘（子笔记 08） |
| 随手用 `xfs_repair -L` | 会丢弃日志，可能丢失尚未落盘的元数据变更 |
| 认为「日志重放 = 数据恢复」 | 日志只保证一致性，不保证误删的文件能回来 |
| 修复后立刻挂可写跑业务 | 少了「只读挂载核对数据」这一步；确认无误再恢复写 |
| 认为 XFS 也需要定期 `fsck` | XFS 没有同类自动检查机制；`xfs_repair` 只在出问题时用 |
| 用 `-c` 做坏块扫描作为常规操作 | 耗时很长，且在介质已异常的盘上会增加压力 |

## 决策练习

> [!question]- 场景：凌晨告警「/data 只读」，业务开始报写入失败。你登上去，`dmesg -T | tail` 里有 `EXT4-fs error ... remounting filesystem read-only`，同时 `smartctl -a` 显示 `Current_Pending_Sector` 从 0 涨到 12。接下来怎么做？
> A. `mount -o remount,rw /data` 先恢复写入，再研究日志
> B. 先切业务 / 停止写入 → 取证（内核日志 + SMART）→ 判断为**介质故障**，优先安排数据迁移与换盘，备份后按流程卸载、干跑、修复、只读核对
> C. 直接 `e2fsck -y /dev/<dev>` 修好再说
>
> **答案：B。**
> A 是反向操作：内核把文件系统重挂为只读是**保护动作**，重挂可写会让损坏继续扩大到更多元数据。
> C 越过了两个关键判断：一是**介质已经出现待处理坏扇区**（`Current_Pending_Sector > 0`），说明根因在硬件；二是 `-y` 会放弃人工判断。正确做法是**先保数据（迁移/备份），再处理文件系统**。
> B 是正解：**先取证、先判定根因、先保数据，再谈修复**。这也是 M7 与 M8 的交界处。

## 要点自测

> [!question]- 为什么修复必须在卸载状态下做？
> - 修复工具直接改写磁盘上的元数据结构；可写挂载时内核缓存与工具的改写会互相覆盖，结果是「修完更坏」。
> - 最稳的是卸载；只读挂载在部分场景可用，但发行版说明不一致，XFS 尤其不要抱侥幸。
> - **第一反应不要是什么**：不要在文件系统还挂着的时候跑 `e2fsck`/`xfs_repair`。

> [!question]- 文件系统变只读，正确的动作顺序是什么？
> - 取证（`dmesg -T`、`journalctl -k`）→ 切走业务或 `remount,ro` 停止写入 → 判断根因（介质 vs 元数据）→ 卸载 → 干跑检查 → 备份 → 修复 → 只读挂载核对 → 恢复写。
> - **第一反应不要是什么**：不要 `mount -o remount,rw`。

> [!question]- `e2fsck` 的 `-n`、`-p`、`-y`、`-f` 分别是什么？
> - `-n` 只读检查、`-p` 自动修复安全项、`-y` 全部回答 yes、`-f` 强制完整检查。
> - 常规顺序是先 `-n` 评估规模，备份后再 `-f`（必要时才 `-y`）。
> - **第一反应不要是什么**：不要把 `-y` 当成默认选项。

> [!question]- `xfs_repair -L` 为什么危险？
> - 它丢弃（清空）日志，会在日志无法重放时使用；但日志里可能有尚未落盘的元数据变更，**丢弃意味着可能丢数据**。
> - 只有在日志确实损坏、且已有可用备份时才用。
> - **第一反应不要是什么**：不要在没试过普通 `xfs_repair`、没有备份的情况下直接上 `-L`。
