# IO 观测、下钻与基线

> [!cite] 参考资料
> `man 1 iostat`、`man 1 pidstat`、`man 8 iotop`、`man 1 lsof`、`man 5 proc`（`/proc/<pid>/io`、`/proc/diskstats`）、`man 8 blktrace`、`man 1 blkparse`、`man 1 bpftrace`、`man 1 fio`、`man 8 sar`，以及 sysstat 文档中关于 `svctm` 已废弃的说明。
>
> 本篇结论来自上述资料，**命令输出尚未在实验机上逐条实测**；本机结果与文中不一致时以本机输出为准。

> **这篇讲什么**：「磁盘慢」怎么从一句感觉变成一条证据链。讲清 `iostat -x` 每一列怎么读、**`await` 与 `aqu-sz` 的组合怎么区分「排队」与「设备退化」**、怎么从设备下钻到进程与文件，以及怎么用 `fio` 建一份半年后还能用的基线。
>
> **必须先读什么**：[[Linux/05_存储与文件系统/11_IO栈与调度器|11 IO 栈与调度器]]（一次 IO 经过了哪些层、介质量级）。
>
> **读完能回答**：① `await`、`aqu-sz`、`%util` 三者怎么连起来读？② 怎么从「哪块盘慢」下钻到「哪个进程、哪个文件」？③ 一份 IO 基线必须记录哪些条件？④ 为什么 `svctm` 不能用？
>

## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **`await` 含排队时间**：它涨了不代表盘坏了。**`await` 与 `aqu-sz` 同涨 = 排队；`await` 涨而队列浅 = 设备或链路本身慢。** 这一条能解决大部分误判。
> - **`%util` 只在单队列设备上有效**：机械盘、SATA SSD 上接近 100% 基本等于饱和；**NVMe 多队列上经常 100% 却远未饱和**。
> - **`svctm` 已废弃**：sysstat 文档明确说明它不可靠，**不要再用它下结论**。
> - **下钻有三跳**：`iostat -x` 找盘与模式 → `iotop`/`pidstat -d` 找进程 → `lsof`、`/proc/<pid>/io`、`blktrace` 找文件与请求阶段。
> - **没有基线的「慢」只是感觉**：基线要连**硬件型号、RAID 级别、文件系统、挂载参数、块大小、iodepth、numjobs**一起记，否则前后不可比。

## 1. `iostat -x` 每一列怎么读

```bash
iostat -x 1 5                        # 验证：每秒采样的扩展指标（重点看 await / aqu-sz / %util）
iostat -x -m 1                       # 验证：以 MB/s 为单位输出，便于与业务吞吐对齐
iostat -x -d /dev/sda 1 5            # 验证：只看某块盘（多盘机器上更清晰）
```

| 列 | 含义 | 怎么解读 |
| --- | --- | --- |
| `r/s`、`w/s` | 每秒完成的读/写请求数 | 与 IOPS 对照；注意这些是**合并后**的请求 |
| `rkB/s`、`wkB/s` | 每秒读写量 | 与业务吞吐对齐的重要一列 |
| `await` | 平均完成时间（毫秒，**含排队时间**） | 与设备基线对比；显著高于基线说明排队或设备退化 |
| `r_await` / `w_await` | 读、写分别的 await | 读慢与写慢的根因经常不同（写还牵涉回写与阵列缓存） |
| `aqu-sz`（旧名 `avgqu-sz`） | 平均队列深度（未完成请求数） | **必须与 await 一起看**（组合判读见下一节） |
| `%util` | 设备忙于处理 IO 的时间比例 | 单队列设备上接近 100% ≈ 饱和；**NVMe 上参考价值有限** |
| `rareq-sz`/`wareq-sz` | 平均请求大小 | 判断是随机小 IO 还是顺序大 IO |
| `svctm` | 已废弃 | **不要再用它下结论**（sysstat 文档已标注不可靠） |

## 2. 组合判读：排队还是设备退化

这是全篇最值钱的一张表：

| 现象 | 判读 | 下一步 |
| --- | --- | --- |
| `await` 高 + `aqu-sz` 高 + `%util` 高（单队列） | **排队**：请求比设备能处理的多 | 找源头进程（`iotop`/`pidstat -d`）、错峰、限流、加并行设备 |
| `await` 高 + `aqu-sz` 低 | **设备/链路本身慢**：请求不多但要很久 | 查介质健康（SMART）、阵列缓存与电池、网络存储链路 |
| `await` 低 + `aqu-sz` 高 | 并发高但设备扛得住 | 通常正常；看业务延迟是否受影响 |
| 写 `await` 高 + `Dirty` 高 | **回写链**：脏页积压（阶段 4 的领域） | 看写入速率与 `dirty_*` 参数，而不是换盘 |
| `r/s` 高、`rareq-sz` 小（4K 级） | 随机小读为主 | 常见于数据库、索引随机访问；看缓存命中与设备 IOPS |
| `wkB/s` 高、`wareq-sz` 大（1M 级） | 顺序大写为主 | 常见于备份、日志刷盘；看带宽与回写 |

> [!tip] 第一反应不要是「`await` 一高就换盘」
> `await` **包含排队时间**。业务自己把并发打到几百，任何设备都会「await 高」。先把 `aqu-sz` 一起看：**队列深说明是压力问题，队列浅才是设备问题**；再结合 `dmesg` 与 SMART 判断是不是介质退化。

## 3. 下钻：从设备到进程到文件

```bash
iostat -x 1 10                       # 验证：先定位哪块盘、读还是写、随机还是顺序
sudo iotop -oPa -d 2                 # 验证：只有实际产生 IO 的进程（-a 累计、-P 只看进程）
pidstat -d 1 5                       # 验证：进程级读写速率（kB_rd/s、kB_wr/s）
sudo lsof -p <pid> | head -20        # 验证：这个进程打开了哪些文件
cat /proc/<pid>/io                   # 验证：单进程累计读写字节（read_bytes/write_bytes 为真实落盘量）
sudo blktrace -d /dev/sda -o - | blkparse -i -
                                     # 验证：块设备的请求级追踪（Q→G→I→D→C 各阶段耗时）
sudo bpftrace -e 'tracepoint:block:block_rq_issue { @[comm] = count(); }'
                                     # 验证：按进程统计块设备请求数（需要 bpftrace 与相应内核权限）
```

| 顺序 | 工具 | 回答的问题 |
| --- | --- | --- |
| 1 | `iostat -x` | 哪块盘、读还是写、随机还是顺序、延迟与队列 |
| 2 | `iotop -oPa` / `pidstat -d` | 哪个进程在打 IO |
| 3 | `lsof -p` / `/proc/<pid>/io` | 这个进程在读写在哪个文件上 |
| 4 | `blktrace`/`blkparse`、eBPF（`biosnoop`/`biolatency` 一类） | 请求在每一阶段花了多久、延迟分布如何 |
| 5 | `dmesg -T`、`smartctl` | 底层有没有介质错误或链路告警（子笔记 08、13） |

> [!important] `read_bytes`/`write_bytes` 才是真实落盘量
> `/proc/<pid>/io` 里 `rchar`/`wchar` 统计的是「应用请求的字节数」（包含 Page Cache 命中的部分），而 **`read_bytes`/`write_bytes` 才是真正走到块设备层的字节数**。判断「谁把盘打满」，看后者。

## 4. 建立基线：`fio` 与记录条件

```bash
fio --name=randread-4k --filename=/dev/<dev> --ioengine=libaio --direct=1 \
    --rw=randread --bs=4k --iodepth=32 --numjobs=4 --size=4G --runtime=60 --group_reporting
                                     # 验证：随机读 IOPS 与 clat 分位（p99/p99.9 比平均值重要）
fio --name=randwrite-4k --filename=/dev/<dev> --ioengine=libaio --direct=1 \
    --rw=randwrite --bs=4k --iodepth=32 --numjobs=4 --size=4G --runtime=60 --group_reporting
                                     # 验证：随机写 IOPS 与延迟（写还受回写与阵列缓存影响）
fio --name=seqread-1m --filename=/dev/<dev> --ioengine=libaio --direct=1 \
    --rw=read --bs=1M --iodepth=8 --numjobs=1 --size=8G --runtime=60 --group_reporting
                                     # 验证：顺序读带宽
fio --name=seqwrite-1m --filename=/dev/<dev> --ioengine=libaio --direct=1 \
    --rw=write --bs=1M --iodepth=8 --numjobs=1 --size=8G --runtime=60 --group_reporting
                                     # 验证：顺序写带宽（机械盘与 SSD 差异最大的项目）
```

**基线卡必须记录的条件**（缺一项就不可比）：

1. **硬件**：设备型号、介质类型（`ROTA`）、容量、RAID 级别与条带大小、阵列卡缓存策略与电池状态。
2. **软件**：文件系统类型、挂载选项、块大小、调度器、`read_ahead_kb`、`nr_requests`。
3. **测试条件**：`bs`、`iodepth`、`numjobs`、`direct`、`size`、`runtime`，以及是否走到文件系统层（`--filename` 是裸设备还是文件）。
4. **结果**：IOPS、带宽、`clat` 的 p50/p95/p99/p99.9（**看分位，不只看平均**）。
5. **同时段的 `iostat -x` 输出**：把 `await`/`aqu-sz`/`%util` 记下来，日后对照实时数据用。

> [!warning] `fio` 只能在实验机或已下线的盘上跑
> 它会打满设备、影响业务，甚至写坏数据（对裸设备跑写测试会覆盖数据）。生产上判断「磁盘变慢」应使用**历史监控数据**（`sar`、Prometheus 的 `node_disk_*`）与 `iostat` 采样复盘。

> [!example]- 实验 8：在 loop 上跑一组 `fio` 基线，同时用 `iostat` 对照
> **怎么做**：用一个独立的 loop 文件（不要复用挂着文件系统的那个），一边采集 `iostat`，一边跑随机读与顺序写。
> ```bash
> dd if=/dev/zero of=/tmp/lab-fio.img bs=1M count=1024
> LOOP5=$(losetup --find --show /tmp/lab-fio.img)
>                                      # 验证：单独建一个文件，避免与实验 1 的文件系统互相干扰
> iostat -x 1 30 "$LOOP5"              # 终端 A：开始采集（设备名用 $LOOP5 的实际值）
> fio --name=lab-randread --filename="$LOOP5" --ioengine=libaio --direct=1 \
>     --rw=randread --bs=4k --iodepth=32 --numjobs=2 --size=512M --runtime=30 --group_reporting
>                                      # 终端 B：随机读基线
> fio --name=lab-seqwrite --filename="$LOOP5" --ioengine=libaio --direct=1 \
>     --rw=write --bs=1M --iodepth=8 --numjobs=1 --size=512M --runtime=30 --group_reporting
>                                      # 终端 B：顺序写基线
> sudo losetup -d "$LOOP5"; rm -f /tmp/lab-fio.img
>                                      # 验证：清理（不清理会让下次的基线不可比）
> ```
> **预期**：`fio` 输出 IOPS、带宽与 `clat` 分位；同一时间 `iostat` 里能看到 `r/s`、`w/s`、`wkB/s`、`await`、`aqu-sz` 的对应变化。**把两份输出拼在一起，就是一份可复用的 IO 基线模板。**
> **风险**：中（会打满该设备）。**只对 loop 文件或已下线的盘跑**；loop 设备的数字不代表真实磁盘性能，本实验练的是「怎么读指标、怎么记录条件」。
> **环境**：任意发行版（需要 `fio` 与 `sysstat`）。
> **耗时**：约 30 分钟。
> **怎么退回去**：命令里已 `losetup -d` 并删除临时文件；若中途失败，用子笔记 17 的统一清理段。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 只看 `%util` 判断磁盘饱和 | NVMe 多队列下 `%util` 常接近 100% 却远未饱和；要看 `await`/`aqu-sz`/延迟分位 |
| `await` 一高就换盘 | `await` 含排队时间；先看 `aqu-sz`，队列深说明是压力问题 |
| 继续用 `svctm` 下结论 | sysstat 已标注它不可用；`svctm` 与 `await` 的差值不再有明确含义 |
| 只看平均延迟 | 平均值会掩盖 p99 尖刺；**延迟分位才是业务感知的那部分** |
| 用 `iotop` 的累计值直接对比业务量 | `iotop -a` 是累计值；实时判断要用默认模式或 `pidstat -d` 的速率 |
| 用 `/proc/<pid>/io` 的 `wchar` 判断落盘量 | `wchar` 含 Page Cache 命中；真实落盘看 `write_bytes` |
| 在生产盘上跑 `fio` | 会打满设备、可能写坏数据；只在实验机或已下线盘上做 |
| 基线只记 IOPS 不记条件 | 块大小、队列深度、文件系统与阵列配置不同，数据无法对比 |
| 忽略「同一时段的其他系统活动」 | 备份、日志轮转、批量任务都会影响读数；采集时要记录时间窗 |

## 决策练习

> [!question]- 场景：某服务在 10:00 出现响应变慢，`iostat -x` 显示数据盘 `await` 从 1 ms 涨到 45 ms，`aqu-sz` 从 0.5 涨到 32，`%util` 98%，`r/s` 明显上升。同事说「盘要坏了，准备换盘」。你怎么判断？
> A. 同意换盘：`await` 与 `%util` 都这么高，盘肯定有问题
> B. 先判定是排队：`await` 与 `aqu-sz` 同涨、`r/s` 上升，说明请求量超过了设备处理能力；先用 `iotop -oPa`/`pidstat -d` 找到打 IO 的进程，再决定是限流、错峰、加缓存还是扩容；同时看 `dmesg`/SMART 排除真实介质问题
> C. 直接调大 `nr_requests`，让队列吸收更多请求
>
> **答案：B。**
> A 跳过了组合判读：`%util` 98% 在单队列设备上确实接近饱和，但**饱和的原因可能是业务压力，而不是盘退化**；不找源头就换盘，换完还会复现。
> C 可能会放大问题：队列更深会让延迟进一步上升（`await` 更高），业务感知更差。
> B 是正解：**同涨 = 排队**，先找源头进程；再用 `dmesg`/SMART 排除硬件。这个顺序决定了你是「优化业务」还是「换硬件」。

## 要点自测

> [!question]- `await` 和 `aqu-sz` 怎么配合读？
> - 两者同涨 = 排队（压力来自上层请求量）；`await` 涨而 `aqu-sz` 低 = 设备或链路本身慢。
> - 还要区分读/写：`r_await` 与 `w_await` 的根因经常不同（写牵涉回写与阵列缓存）。
> - **第一反应不要是什么**：不要只看 `await` 下结论。

> [!question]- 为什么 NVMe 上 `%util` 不可靠？
> - NVMe 依赖多队列并行，多个硬件队列同时在处理请求，设备几乎总是「忙」，但远未饱和。
> - 判断饱和要看延迟分位、`aqu-sz` 与业务表现。
> - **第一反应不要是什么**：不要把 NVMe 的 `%util ≈ 100%` 当成告警条件写进监控。

> [!question]- 从「哪块盘慢」到「哪个进程、哪个文件」的三跳是什么？
> - `iostat -x` → `iotop -oPa`/`pidstat -d` → `lsof -p`、`/proc/<pid>/io`，需要更细的粒度再用 `blktrace`/eBPF。
> - 别忘了最后回到 `dmesg`/SMART 排除介质问题。
> - **第一反应不要是什么**：不要停在第一跳就写结论。

> [!question]- 一份 `fio` 基线必须记录哪些条件？
> - 硬件（型号、RAID 级别、缓存策略）、软件（文件系统、挂载选项、调度器、队列与预读）、测试参数（`bs`/`iodepth`/`numjobs`/`direct`/`size`/`runtime`）、结果（含延迟分位）与同时段的 `iostat` 输出。
> - 缺条件的数据半年后不可比，等于没做。
> - **第一反应不要是什么**：不要把「在某台机器上跑过一次」当成基线。
