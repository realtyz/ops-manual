# 一块盘的服役一生

一块盘从被机器认出来，到拥有分区与文件系统，到挂进目录树开始服役，到容量长大，最后到坏掉被换走。

---

## 一、接管

### 1.1 三问：是不是这块盘、上面有没有东西、有没有人在用

内核对盘的命名（`sda`、`sdb`、`nvme0n1`）来自**识别顺序**，换插槽、加盘、云平台重挂都会改变它。所以「新接一块盘」这件看起来最简单的事，实际上是全程风险最高的动作——**认错盘等于当场删掉别人的数据**。三问必须都答完才有资格敲下一条命令。

**第一问：是不是这块盘。** 靠序列号，不靠设备名。

```bash
lsblk -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINT,ROTA,MODEL,SERIAL   # 验证：型号与序列号是认盘的最终依据
lsblk -d -o NAME,SIZE,ROTA,MODEL,SERIAL | grep -v loop        # 验证：只看物理盘（ROTA=1 机械、0 为 SSD/NVMe）
ls -l /dev/disk/by-id/ 2>/dev/null | head                     # 验证：内核按盘序列号建的稳定别名
```

`SERIAL` 是盘固件里的序列号，与工单/台账核对一致才能继续。物理机上还应配合机箱 LED 或厂商工具点灯——**光看 `/dev/sdX` 一定会认错**。云主机上没有物理槽位，改用云控制台的盘 ID 与容量对照 `lsblk` 的 `SIZE`。

**第二问：上面有没有东西。** 新盘与回收盘的唯一区别，是**别人有没有告诉你它被回收过**。

```bash
sudo wipefs -n /dev/<dev>            # 验证：列出盘上所有可识别的签名（-n 只读，绝不写盘）
sudo blkid /dev/<dev> /dev/<dev>1    # 验证：有没有已存在的文件系统 UUID/TYPE
sudo parted -s /dev/<dev> print      # 验证：有没有分区表、什么类型、分区从哪到哪
```

| 看到什么 | 含义 | 该怎么处理 |
| --- | --- | --- |
| 没有签名、分区表报「无法识别的磁盘标签」 | 真正的新盘 | 可以建分区表 |
| 有分区表但没有文件系统 | 拆过或回收的盘 | 先确认没人要它的数据，再决定复用还是清签名 |
| 有文件系统（`blkid` 有 UUID） | 盘上有数据 | **停下来问**：这块盘是谁的、要不要备份 |
| `lsblk` 的 `MOUNTPOINT` 非空 | 正在使用中 | 先找占用者 |

`wipefs -n` 是「不写盘的 X 光」，它列出的每一条签名都是「这块盘曾经有主人」的证据。**回收流程没走完时，最便宜的处置是问一句，而不是擦掉它。**

**第三问：有没有人在用。** 设备可能已经被挂载、被 LVM 接管、被阵列或加密映射占用。

```bash
findmnt /dev/<dev>1                  # 验证：这个分区是否被挂载、挂在哪、什么参数
sudo fuser -vm /data                 # 验证：哪些进程在使用这个挂载点
sudo dmsetup ls --tree               # 验证：设备是否被 LVM/加密/多路径占用（映射树里能看到）
```

`dmsetup ls --tree` 是关键一步：如果 `lsblk` 里出现一层套一层的关系，说明这块盘已经被 device-mapper 结构吃掉了，**此时不能直接对它分区**，要沿链路先确认上层（PV/LV/阵列/多路径）的状态。

### 1.2 建分区表

现代系统一律用 GPT：MBR 的分区表只有一份、写坏就完且单盘上限 2 TiB；GPT 在盘头与盘尾各存一份、带 CRC 校验，容量不受限。建表的标准动作是「建表 → 建分区 → 让内核重读 → 导出留档」：

```bash
sudo parted -s /dev/<dev> mklabel gpt                        # 验证：写 GPT 分区表（会清空原分区表）
sudo parted -s /dev/<dev> mkpart primary xfs 1MiB 100%       # 验证：建一个从 1MiB 到盘尾的分区
sudo partprobe /dev/<dev>                                    # 验证：让内核重读分区表
lsblk /dev/<dev>                                             # 验证：分区出现了（如 sdb1）
sudo sfdisk -d /dev/<dev> > /root/<dev>-parttable-$(date +%F).sfdisk
                                                             # 验证：导出分区表留档（换盘/误删时能原样恢复）
```

四条必须在动手前就知道的细节：

- **分区类型名不创建文件系统。** `mkpart ... xfs` 里的 `xfs` 只是给分区打类型提示；文件系统要等下一站。
- **分区起点是 1 MiB。** 这同时避开分区表占用的空间与物理扇区（4 KiB 或更大）的对齐要求。为「省这 1 MiB」而破坏对齐，换来的是每次 IO 的额外读改写。
- **空闲盘改分区表内核一般自动识别；在用盘上改需要显式重读**（扩容最后一个分区就是这种情况），而且扩完分区还要扩文件系统才有意义。
- **分区表本身也要备份。** 它和文件系统一样是元数据；盘头几个扇区坏掉时，有导出文件就等于有重建依据。

### 1.3 身份进台账

分区表建好、文件系统建好之后（下一站），**立刻记录身份**。台账要覆盖四层，缺一层都会在某个后续动作里卡住：

| 层次 | 记什么 | 为什么 |
| --- | --- | --- |
| 物理盘 | 型号、序列号、槽位、容量、介质类型 | 换盘、点灯、盘位核对 |
| 分区 | 分区表类型、起止扇区、大小 | 重建分区表、扩容排查 |
| 文件系统 | UUID、LABEL、类型、块大小 | `/etc/fstab`、备份清单、迁移 |
| 池与阵列 | VG/LV 名、PV 成员、RAID 级别与成员 | 扩容与换盘 |

台账不是形式主义：换盘时最容易出事的三步是**认错盘、没等重建完成就上压力、换了盘没更新台账导致下次又认错**。台账把「认盘」从现场记忆变成一次查表动作。

## 二、成型

### 2.1 选型与创建

选型按三个问题回答（判据见原理篇 2）：会不会缩容（会则只能 ext4，且必须卸载）；会不会有海量小文件（会则用 XFS，避开 inode 耗尽）；容量会不会长到几十 TiB（会则 XFS + LVM）。生产上最常见的是「XFS + LVM」——整条扩容链路没有一步需要缩容。

`mkfs` 会**立刻在新账本下覆盖原有元数据**，没有「再想想」。它前面必须已经完成三问，并且确认数据已有别的副本；XFS 还要求显式加 `-f` 才肯覆盖已有签名，这是它「默认假设你可能敲错了设备名」的保护设计，**不是习惯性参数**。

**建完立刻做四件事**，缺一件都会在以后以「挂不上」「inode 满」「不知道这是哪块盘」的形式还回来：

1. **打 LABEL 并取 UUID**：这是 fstab、备份清单与迁移脚本要用的身份。
2. **记录结构参数**：块大小、inode 总量、以及文件系统特有的结构（XFS 的 AG 数与特性、ext4 的保留比例）。**半年后回头看 inode 用量时要用。**
3. **手动挂载验证一次**。建文件系统成功不等于能挂上（对齐、工具版本、损坏都可能出问题）；**不要拿 fstab 当第一次尝试**——那时失败就变成开机故障。
4. **确认「干净状态」**：ext4 看文件系统的状态标记是否为 clean；XFS 挂载后内核日志不应有报错。

`mkfs` 的参数里，**块大小、ext4 的 inode 密度、XFS 的 AG 数与部分特性是「定了就改不了」的**——改它们等于重建文件系统。相反，ext4 的保留比例、自动检查周期、出错行为，以及 XFS 的标签，都可以事后调整。

### 2.2 规划时就要定下的事：不要让所有东西共用一个文件系统

系统盘、数据盘、日志盘分区分盘，并让日志、容器数据目录这类「会自己长大」的目录有独立挂载点——否则日志写满根分区会直接变成整机故障：**「业务写满」与「系统写不进去」之间没有缓冲**。

判断一个目录是不是真的在独立的文件系统上，只有一个办法：查它实际属于哪个挂载点。**你以为它在一块独立的盘上，和它真的在，是两件事。**

## 三、上岗

### 3.1 挂载的语义

挂载把一个文件系统的根接到目录树的某个目录上。必须记住的两条语义：

- **挂载点上原有内容被遮住，不是被删除**。原内容仍在原文件系统里；卸载后重新可见，或者从上层绑定挂载去看。
- **同一个文件系统可以出现在多个位置**（绑定挂载），一块设备也可以完全没挂载——设备数与挂载点数没有对应关系。

卸载失败只有一个原因：**还有人持有这个挂载点上的东西**。此时的正确动作是找出占用者并停掉/迁移它，**而不是强卸**——强卸不会让进程停止写入，它只会让那些进程继续写到一个已不在目录树里的文件系统上，常见后果是数据丢失或结构不一致。

### 3.2 fstab 与「保命选项」

`/etc/fstab` 的六列依次是：设备、挂载点、类型、选项、`dump`、`pass`。要点只有几条，但每条都有明确后果：

| 字段/选项 | 要点 | 出错后果 |
| --- | --- | --- |
| 设备 | **只能写 UUID 或 LABEL** | 设备名漂移 → 挂错盘或挂不上 |
| 挂载点 | 目录必须**已经存在** | 目录不存在 → 启动时挂载失败 |
| `nofail` | 设备缺失或挂载失败时不阻塞启动 | **数据盘与可选盘必加**；缺了它，一块盘掉线能把整机拖进紧急模式 |
| `_netdev` | 标记为网络文件系统，排到网络就绪之后 | 网络存储必加；少了它启动会等超时 |
| `noatime` | 不更新访问时间，减少元数据写入 | 依赖访问时间的备份工具会受影响 |
| ext4 的 `errors=` | 出错时的动作（继续 / 重挂只读 / panic） | **默认是「继续」**：不显式配置就不会自动切只读 |

两条纪律：

**改完 fstab 的验收不包含重启。** 顺序是「备份原文 → 编辑 → 语法与可挂载性检查 → 让 systemd 重读 → 逐条挂一遍 → 核对实际参数」。这五步在当前机器上就能完成全部验证；**用重启验证 fstab 是把一个可当场发现的问题推迟成一次生产事故**——如果改的是关键挂载，机器可能起不来，远程也连不上。

**systemd 会把 fstab 的每一条翻译成一个挂载单元**，单元名把路径里的 `/` 换成 `-`：`/` 对应 `-.mount`，`/data` 对应 `data.mount`，`/mnt/disk1` 对应 `mnt-disk1.mount`。挂载失败时的第一现场是这个单元的日志，而不是重读一遍 fstab。

### 3.3 怎么读挂载状态

| 看哪里 | 是什么 | 单位与范围 | 怎么读 |
| --- | --- | --- | --- |
| `findmnt` 的 `TARGET/SOURCE/FSTYPE/OPTIONS` | 当前实际生效的挂载与参数 | 文本 | 这是「实际」；fstab 是「期望」。两者不一致时**永远以实际为准**，并去查为什么不一致 |
| `OPTIONS` 里的 `ro` | 该挂载当前只读 | 布尔 | 看到 `ro` 先取证，**不要重挂为可写** |
| 挂载单元的状态与日志 | systemd 视角的挂载结果 | 文本 | 挂载失败先看单元日志，再决定改 fstab 的哪一行 |

判断「这块盘还有多少空间」之前，**第一步是确认路径属于哪个文件系统**（读法见实操篇）。目录名不携带这个信息。

## 四、长大

### 4.1 扩容是一条链，每一层都要单独长大

容量从硬件到业务要经过若干层，**任何一层没长大，最上层的可用空间都不会变**：

```mermaid
flowchart LR
  A["① 设备容量<br/>云盘/阵列长大"] --> B["② 分区容量<br/>扩分区 + 内核重读"]
  B --> C["③ PV 容量<br/>感知新空间"]
  C --> D["④ VG 容量<br/>池子变大"]
  D --> E["⑤ LV 容量<br/>卷变大"]
  E --> F["⑥ 文件系统<br/>在线扩大"]
  F --> G["⑦ 业务可用<br/>写入测试"]
```

| 步骤 | 验收标准 |
| --- | --- |
| ① 内核看到新容量 | 设备的 `SIZE` 变大 |
| ② 分区变大 | 分区的 `SIZE` 变大（云盘场景常见这一步被跳过） |
| ③ PV 感知新空间 | PV 的容量变大、卷组出现空闲空间 |
| ④ VG 变大 | 池子的空闲空间增加 |
| ⑤ LV 变大 | 卷的大小增加 |
| ⑥ 文件系统扩大 | **业务看到的容量变大** |
| ⑦ 业务可用 | 能正常写入、无报错 |

**验收标准只有一个：业务侧的容量确实变大，并且能正常写文件。** 「卷已经扩了」不等于「业务可以用到更多空间」——有些工具能在扩卷之后顺手把文件系统也扩掉（减少一次手工步骤），但分区与 PV 的扩容仍要自己做。这一步不做，几个月后就会以「我明明扩过容」的形式再次冒出来。

**文件系统扩容两个工具的记混点**：ext4 的扩容工具接受**设备**，XFS 的扩容工具接受**挂载点**。搞反了不是报错就是改错了对象。另外 XFS 必须**处于挂载状态**才能在线扩大。

### 4.2 缩容：为什么生产上通常不做

三条硬规则：

1. **顺序与扩容相反**：扩容是先扩卷再扩文件系统；**缩容必须先缩文件系统，再缩卷**。顺序反了会切掉正在使用的区域。
2. **XFS 完全不支持缩容**，只能备份 → 重建 → 恢复。
3. **ext4 缩容必须先卸载**，且缩之前需要一次完整检查，否则工具会拒绝执行。

由此得到规划阶段就应确认的一件事：**如果业务可能缩容，选型时就只能选 ext4 并接受停机**；等到容量已经写进去再想缩，代价是重建。

### 4.3 快照：能用与不能用

卷级快照的机制是写时复制：快照不复制全部数据，原卷后续被写入时，旧块才被复制到快照空间。这决定了它的三个性质：

- **会增长。** 原卷写得越多，快照消耗的空间越多；快照空间用尽时**直接失效**。
- **有性能代价。** 原卷的每次写入都可能多一次复制，属于写放大。
- **不是备份。** 它依赖原卷、与原卷同盘、生命周期通常只有一次维护窗口。

正确用法是**在备份或变更窗口内做一份短命快照，用完即删**。真正需要防的场景（盘坏、误删覆盖整盘、加密勒索、机房级故障）只能靠异地或离线备份。

## 五、冗余、健康与退役

### 5.1 冗余：把「盘坏」从事故降级成事件

RAID 的核心价值不是「更快」，而是**把单盘故障从「服务中断 + 数据丢失」变成「一次维护动作」**。它的边界同样清楚：冗余只对抗盘的物理失效，**不对抗数据错误**——误删、勒索加密、错误写入、逻辑损坏会被阵列忠实地同步到所有成员盘。

重建是所有 RAID 级别里最危险的窗口：**它要读全部成员盘，期间阵列处于低冗余甚至无冗余状态**。风险随单盘容量增长而上升（按不可恢复读错误的标称率估算，10 TB 量级盘的重建失败概率已达数十个百分点，量级估算见原理篇 1），也因此**大容量盘上的单校验级别（RAID5）在生产上越来越不受欢迎**。

### 5.2 健康：提前发现比事后处理便宜一个数量级

盘的健康有两条独立的信息来源，**内核日志通常比健康计数更早**：

| 来源 | 看什么 | 判据 |
| --- | --- | --- |
| 介质健康计数 | 重映射扇区数、待处理扇区数、离线不可纠正扇区 | 计数**持续增长**才是信号；待处理扇区大于 0 要重点关注 |
| 接口错误计数 | 传输校验错误 | 通常指向线缆、背板、接口，而不是盘本身 |
| 寿命指标（SSD/NVMe） | 寿命消耗百分比、备用块余量、完整性错误计数 | 越过厂商阈值、完整性错误非 0 要立刻处理 |
| 内核日志 | 介质错误、IO 错误、控制器重置 | 是换盘决策的**直接证据** |
| 阵列状态 | 是否降级、重建进度、成员盘标记 | 降级即冗余度下降，先确认是哪一块 |

判断的纪律是「**看趋势，不看单值**」：一个不增长的重映射计数不代表盘要坏了，而一个持续上升的小数字是明确的信号。**健康巡检的价值在于它比阵列降级和文件系统只读早得多**——后者出现时，冗余度往往已经损失了。

上表里每一类字段的读法固定为四件事——**是什么、单位、判据、看到它转向哪一步**：

| 字段类别 | 单位与范围 | 判据（与谁一起看、什么条件下结论会变） | 转向哪一步 |
| --- | --- | --- | --- |
| 重映射扇区数 | 个数，累计值，非负整数 | 单值为 0 是常态；**判据是同一台盘上的时间序列**——持续增长说明介质在退化。偶发一次且长期不变，不必立刻更换 | 进入换盘评估，同时加密备份频率 |
| 待处理扇区数 | 个数，累计值，通常应恒为 0 | **大于 0 就要重点关注**；它表示有读不出来的扇区在等待重试。与 IO 错误日志一起看才成立——只有计数没有日志时先复测一次排除误读 | 先保数据（备份或迁移），再安排换盘；**此时做文件系统修复是本末倒置** |
| 离线不可纠正扇区 | 个数，累计值 | 与重映射、待处理扇区一起看；它单独非零时的解释力弱于前两项 | 同上一行 |
| 接口传输校验错误 | 个数，累计值 | **单独增长指向线缆、背板或接口，不是盘本身**；换盘前先排查连接件，否则换完还会复现 | 检查连接件与背板，必要时更换线缆 |
| 温度 | 摄氏度，瞬时值与历史峰值 | 判据是与厂商规格上限和自己的历史基线比；**持续偏高**加速老化，偶发尖峰不构成结论 | 检查风道与机房环境，纳入巡检趋势 |
| 寿命消耗百分比 | 百分比，0～100 | 与厂商给出的保修阈值比较，而不是与 100% 比较；**结合写入量增长速率**判断还有多久到阈值 | 排入替换计划，按批次统一处理 |
| 备用块余量 | 剩余比例或个数，随消耗下降 | 相对厂商阈值的位置；它下降通常伴随寿命消耗上升，两者要一起看 | 同上，且优先于性能类问题 |
| 数据完整性错误计数 | 个数，累计值 | **非 0 就必须立刻介入**——它意味着数据已经出错，不是盘在变慢 | 立刻停止把它当可靠存储、核对数据并更换 |
| 异常掉电次数 | 个数，累计值 | 与机房供电、固件版本一起看；持续增长说明断电保护或固件有问题 | 查供电与固件，而不是只看盘 |
| 阵列降级与重建进度 | 布尔状态；重建进度为百分比，剩余时间以秒/分钟计 | 降级即冗余度下降；**重建期间的判据是进度是否推进**，停滞要查成员盘与限速设置 | 按换盘流程处置，并给重建限速 |

巡检节奏应当写进值班手册：健康计数按周采集，内核日志与阵列状态按日扫描，换盘流程每季度在实验环境完整演练一次。

### 5.3 换盘：六步，三个坑

一次规范的换盘包含六步：

1. **确认目标盘**：用序列号加 LED 或厂商工具定位槽位——**不要凭设备名认盘**。
2. **按流程下线**：软阵列用 `mdadm` 的 fail 加 remove；硬件阵列用厂商工具把盘置为失败/离线。
3. **换入新盘**：核对型号、容量（**不小于原盘**）、固件版本。
4. **重建并限速**：加入新盘后观察重建进度并**对重建限速**，避免重建打满业务 IO。
5. **校验**：阵列状态无降级、文件系统可写、业务指标正常。
6. **更新台账**：新旧盘序列号、更换时间、原因。

三个最容易出事的地方：**认错盘**（把好盘拔了，冗余度瞬间归零）、**没等重建完成就上业务压力**（重建与业务高峰叠加，可能把其余盘也拖坏）、**换了盘不更新台账**（下次故障又要现场猜）。

### 5.4 闪存的例行维护

机械盘服役期间基本没有「维护动作」，插上用到退役即可；闪存不一样，它需要两项例行操作——**回收通知（TRIM）**与**寿命跟踪**。机制见原理篇 7，这里给动作与判据：

| 动作 | 何时做 | 判据与验收 | 边界 |
| --- | --- | --- | --- |
| 定期下发回收通知 | 由定时任务触发，通常是系统自带的周期任务 | 任务处于启用状态；手工执行时能看到每块盘回收的字节数（大于 0 说明确实有可回收的空间） | 无破坏性；可在生产上执行 |
| 改用「删除时立即下发」 | 只在确认该盘对延迟抖动不敏感时才改挂载选项 | 改动后对比业务的写延迟分位是否恶化；**恶化就改回去** | 属于挂载选项变更，要走变更与验收流程 |
| 整设备擦除 | 只在盘已下线、或将回收时 | 执行前核对设备身份（先用只读方式列出签名与容量） | **破坏性且不可逆**；只用于已下线的盘 |
| 固件与型号记录 | 换盘前、固件升级前 | 记下型号、序列号与固件版本，写进台账 | 固件升级本身属于生产变更 |
| 寿命与写入量跟踪 | 按周随健康巡检一起 | 结合厂商给出的寿命标称与已消耗比例，估算剩余可用期，**排入替换计划而不是等它坏** | 同 5.2 的巡检节奏 |

三条容易踩的边界：

- **回收通知不是性能开关**。它解决的是「盘的长期写入效率」，不是「这台机器现在慢」；一次性执行不会带来可见的性能提升。
- **寿命评估是趋势问题**，判据是相对厂商阈值的位置与增长速度，不是某个单次百分比。
- **`%util` 在闪存盘上参考价值有限**（原理篇 5 讲过原因），不要把它当闪存盘的饱和判据写进告警。

## 六、三条横切线

一条时间线走完之后，有三条线横穿其中多个环节，排障时按它们来切更快。

### 6.1 账目线：这块空间算在谁头上

「`df` 与 `du` 对不上」这类问题的答案，最终要能拆到四处：

1. **已删除但被进程持有的文件**——目录树里已经消失，但数据块没释放；
2. **被挂载覆盖的目录**——原内容被新文件系统的根挡住，`du` 遍历不到而 `df` 仍然记账；
3. **保留块与元数据**——为 root 预留的比例、inode 表、日志、位图、超级块备份；
4. **稀疏文件与延迟分配**——表观大小远大于实际占用。

四类的处置完全不同，**逐个排除而不是互相否定**。所以「`df` 与 `du` 差了多少」的正确答法是「差在哪一类、证据是哪一条命令」，而不是「某个工具不准」。

### 6.2 限制线：为什么「还有空间」却写不进去

拒绝一次写入的理由至少有七种，它们的**载体不同**，因此查文档和改配置的地方也不同：

| 上限类型 | 载体 | 典型查询入口 |
| --- | --- | --- |
| 数据块 / inode | 文件系统的内部结构 | 容量与 inode 两个使用率 |
| 保留比例 | 文件系统的可调参数 | 检查工具的保留块字段 |
| 配额 | 挂载选项 + 配额子系统 | 配额报表与记账状态 |
| 句柄 | 会话限制、服务单元属性、内核参数 | 进程自己的限制文件与服务属性 |
| inotify | 内核参数 | 三个 `fs.inotify.*` 值 |
| 池水位 | LVM 的 thin pool 元数据 | 池的数据与元数据百分比 |
| 只读 | 内核的保护动作 | 实际挂载选项里的 `ro` |

**先看报错原文（是 `ENOSPC`、`EDQUOT` 还是 `EROFS`），再确认写入路径属于哪个文件系统，然后按上表逐项排除。** 扩容对所有非容量类的「满」都无效。

### 6.3 完整性线：动作的顺序与不可逆性

把这一章的处置动作排成一条时间线，会看到一条清晰的分界：

**变慢是可逆的，写坏是不可逆的。** 回写积压、重建限速、队列排队都只影响延迟，可以调优、可以等待；而文件系统只读、介质错误、阵列降级涉及数据风险，必须**先取证、先停写、先备份**。

由此产生的顺序纪律贯穿全章：

- **变更前**：先备份配置原文（fstab、LVM 元数据）、先取只读基线、先确认身份；
- **变更中**：逐层验收（分区 → PV → VG → LV → 文件系统 → 业务）；
- **验收**：用业务能感知的指标（容量变大、写入成功），而不是「命令没报错」；
- **故障时**：取证 → 停止写入 → 卸载 → 干跑检查 → 备份 → 修复 → 只读核对 → 恢复可写；
- **收尾**：更新台账与监控、检查是否批量下发过同样的写法。

## 七、常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 用 `/dev/sdX` 认盘或写进配置 | 认错盘等于当场删数据；配置里只能用 UUID、LABEL 或 by-id |
| 新盘不查签名直接建文件系统 | 回收盘上可能还有旧数据签名，一次操作就覆盖了 |
| 扩张分区后不重读分区表 | 内核还用旧分区表，看不到新容量 |
| 扩了卷就以为业务空间变多 | 还要扩文件系统；验收标准是业务侧容量变大 |
| 用重启验证 fstab | 写错可能进不了系统；当场就能验证 |
| 数据盘不加 `nofail` | 一块盘掉线能把整机拖进紧急模式 |
| 把 ext4 的默认出错行为记成「出错即只读」 | 默认是标记并继续；要自动切只读必须显式配置 |
| 缩容时先缩卷再缩文件系统 | 顺序反了会切掉正在使用的区域 |
| 把快照当备份长期保留 | 快照随原卷写入增长、写满即失效，且与源数据同盘 |
| 阵列降级就先拔可疑盘 | 先确认哪一块真坏；误拔好盘会让冗余度归零 |
| 重建期间不限速、不避高峰 | 重建打满带宽，业务延迟恶化，还可能拖坏其余盘 |
| 只看健康计数的单次值 | 要看趋势：持续增长才是信号 |
| 处理完不更新台账与监控 | 同类故障会在同机或同批次机器上重演 |

**第一反应不要做什么**（三条最有用的）：不要凭设备名认盘；不要在没取证的情况下重挂为可写；不要在还有空间时先扩容。

## 要点自测

**问：接入一块「新」盘，动手前必须回答哪三问、各用什么回答？**
答：是不是这块盘（`lsblk` 的型号与序列号、`/dev/disk/by-id/`）；上面有没有东西（`wipefs -n`、`blkid`、`parted print`）；有没有人在用（`findmnt`、`fuser -vm`、`dmsetup ls --tree`）。三问都没问题才有资格建分区表。

**问：从「盘变大」到「业务可用空间变大」，中间经过哪几层？验收标准是什么？**
答：设备容量 → 分区 → PV → VG → LV → 文件系统 → 业务写入。验收标准是业务侧容量确实变大且能正常写入；只看「命令没报错」不算完成。

**问：为什么改完 fstab 不能靠重启验证？**
答：写错的 fstab 可能让机器进不了系统、远程也连不上；而语法检查、逐条挂载、核对实际参数在当前机器上就能完成全部验证。重启只是把一个当场能发现的问题推迟成一次生产事故。

**问：文件系统变只读时，为什么第一步不是恢复写入？**
答：只读是内核检测到错误后的保护动作，目的是阻止损坏扩散。第一步是取证并判断根因（介质故障还是元数据损坏），然后停止写入、卸载、干跑检查、备份、修复、只读核对，最后才恢复可写。

**问：换盘流程里哪三步最容易出事，为什么？**
答：认错盘（冗余度瞬间归零）；重建未完成就上业务压力（重建与高峰叠加，可能拖坏其余盘）；不更新台账（下次故障又要现场猜）。三者都源于「跳过确认直接动手」。

**问：「`df` 与 `du` 对不上」要能拆成哪四类，为什么不能只报一个差值？**
答：已删除但被进程持有、被挂载覆盖的目录、保留块与元数据、稀疏文件与延迟分配。四类的处置完全不同，只报差值等于没有定位。

**第一反应不要做什么**：不要凭设备名认盘；不要在还有空间时先扩容；不要在没取证时重挂为可写；不要在重建期间给业务加压；不要用重启验证配置改动。
