# 盲区排查：存储、文件系统与 IO

## 1. 本篇解决什么问题

读完整章之后，"不会"通常无法被自己察觉。它不表现为"这道题答不上来"，而表现为**回答停在某一层却以为已经说完了**——报错文本念得对、机制因果说得通，但据此在机器上做不出任何判断。

本篇把本章负责的八类现象逐层拆开：每一层给出它在追问下的典型回答、这一层实际检验的是什么、站在这一层的人下一步该往哪里看。用途只有一个：**自己对照，找到自己的回答停在哪一层，据此定位缺的是哪一篇的哪一节。**

全部层级里最常见的一种失效，是机制讲得流畅而判据落不到字段上。它在存储这一章有一个特定的外观：`ENOSPC`、`EDQUOT`、`EROFS` 三个错误码分得清，七个上限的名单背得出，但被问到"那么你读哪一个文件"时给不出一个字段名——拥有的是叙述能力，不是判断能力，而这两种状态读起来几乎没有区别。

## 2. 分层的方法

每一类现象都沿同一方向逐层展开，共四层，顺序固定：

| 层 | 回答里出现什么 | 检验的是 | 停在这一层的典型说法 |
| --- | --- | --- | --- |
| 第 0 层 | 只给出结论或动作 | 有没有进入机制 | "清理一下"、"扩容"、"重挂回可写" |
| 第 1 层 | 说出机制与因果 | 机制是否成立 | "删除要等链接数归零且没有句柄持有" |
| 第 2 层 | 说出字段名与判据 | 判据是否落到可观测处 | "看 `lsof +L1` 输出里的 PID 与路径" |
| 第 3 层 | 说出该判据何时失效、处置的代价与顺序 | 是否具备条件意识与代价意识 | "配额记账只能在挂载时打开，挂载后补不开" |

第 0 层与第 1 层之间是这条链上最陡的一段：从"知道该做点什么"到"知道这件事为什么发生"。第 1 层与第 2 层之间的失效最常见，因为二者的语言外观几乎一样，区别只在有没有一个可读字段。第 3 层决定的是判断能否迁移到另一台机器、另一个环境：存储结论对内核版本、发行版与是否在容器内都敏感，一个只在某台机器上成立的判据，等于没有判据。

定位自己的位置有一条简单办法：**检查自己的每一句话能不能指到一个字段**。指不到的句子，通常是从别处听来的。

## 3. 现象一：容量还有余，写入报 `No space left on device`

### 3.1 逐层演进

**第 0 层**

> 磁盘满了，把日志和历史文件清一批，不够就扩容。

这个动作在真写满的盘上确实有效，所以它看起来成立；但它把"文件系统上没有可用资源"直接翻译成了"字节不够用"，而 `ENOSPC` 覆盖的资源不止字节一项。清理之后故障会以同样的文本再来一次，而当时的现场已经被清掉。

**第 1 层（说出机制）**

> `No space left on device` 只说明文件系统上没有可用资源，它同时覆盖数据块用尽、inode 用尽与 ext4 保留块三种情况。ext4 的 inode 总量在 `mkfs` 时就定了，而文件名不占 inode，海量小文件会先吃完 inode 而不是吃完容量；保留块是给 root 留的比例，所以会出现 root 能写、普通用户写不进去。

到这里因果已经完整。但它在机器上不能执行：不知道读哪个文件，也不知道读到的值说明什么。

**第 2 层（给出判据）**

> 一起读三个量。容量与 inode 两个使用率来自 `df -h` 与 `df -i`，后者是两本账里更容易先满的那本，看 `IUse%`；保留块来自文件系统的检查工具的 `Block count` 与 `Reserved block count` 两个字段，取两者之比，root 能写而普通用户不能写就是这个字段的指纹；还要先确认写入路径实际属于哪个文件系统——`findmnt -T <那个目录>` 给出 `TARGET` 与 `FSTYPE`，"给这个目录留了一块盘"是假设，不是事实。三个量都对不上时再转向配额报表与池水位。

**第 3 层（给出边界与代价）**

> 边界有两条。保留比例不是常数：它在 `mkfs` 时定下、之后可以用工具调整，发行版与工具版本不同现场值就不同，所以"保留块占比 5%"这类说法必须现场从 `Reserved block count` 与 `Block count` 现算，不能照抄；换到容器环境后 `df -i` 与保留块的解释会整体失效，因为容器根目录常常是联合挂载，`df` 里的条目由运行时管理，容量与 inode 的读数都不再对应任何一块盘。
>
> 代价与顺序：清理过期文件是最便宜的一步，可回滚、不动存储；扩容动存储、不可回退，只应当排在清理与选型判断之后；改保留比例会影响所有普通用户，属于全局变更，要先算清总量再改。这段顺序里没有一步需要重启，重启只会丢掉现场。

### 3.2 站在哪一层，说明什么

| 停留层 | 回答里缺的东西 | 缺口类型 | 回到哪一节 |
| --- | --- | --- | --- |
| 第 0 层 | 没有"撞的是哪一本账"这个判断对象 | 结论型 | 原理《文件系统的结构与选型》第 3 节；判例 1 |
| 第 1 层 | 机制正确，但落不到字段上 | 判据型 | 实操 2.1 与体系 6.2；实操 3.1 的排查顺序 |
| 第 2 层 | 不知道保留比例不是常数、容器里该判据整体失效 | 边界型 | 原理《容量边界、挂载与可见性》第 1 节；判例 1 末段 |
| 第 3 层 | 说不出"清理—扩容—改比例"的代价与顺序 | 代价型 | 实操 3.1"一份合格的回答"四要素；治理 3 |

### 3.3 第一反应不要做什么

不要因为"还有空间"就否掉磁盘方向；不要在没看 inode 使用率之前先删文件；不要在根因未明时扩容。

## 4. 现象二：删了大文件，`df` 的用量不降

### 4.1 逐层演进

**第 0 层**

> 是不是要 `sync` 一下，或者清一下缓存？不行就再删一遍。

这三个动作都基于同一个错误前提：把"名字从目录树里消失"当成了"数据块已经释放"。再删一遍尤其无效——对象已经不存在，它什么也没有删。

**第 1 层（说出机制）**

> 删除分两步：从目录项移除名字、inode 链接数减一；只有链接数归零**并且**没有任何进程持有打开句柄时，才释放 inode 与数据块。进程用 `open` 拿到的是文件对象的引用而不是路径，所以路径没了、文件对象还在。

**第 2 层（给出判据）**

> 判据是进程与其打开句柄的清单：`lsof +L1` 的语义是"链接数小于 1"，即目录树里已经没有这个名字，它输出的每一行是一个仍持有该文件的进程，`PID` 与路径就是证据。与它一起看的两个量是 `df` 的用量在持有者结束之后是否下降（这是验证），以及 `/proc/<pid>/fd` 里是否还有别的已删除句柄。持有者存在时的完整指纹是：`df` 不降、`du` 找不到、只有句柄清单看得到。

**第 3 层（给出边界与代价）**

> 边界有两条。查不到持有者时结论必须改成"差值属于另外三类"，而不是继续在这条路上找；换到容器环境后同一个现象会指向另一个层次——容器可写层与联合挂载把一个删除操作拆到多层目录上，宿主侧看到的句柄清单与容器内看到的不是同一份，配额与项目标识的记账对象也不在容器内。
>
> 代价与顺序：让持有者关闭句柄才是处置方向，而重载或重启该进程会带走它正在处理的在途状态，所以先确认它是谁、在做什么，再选窗口；直接截断句柄（写入 `/proc/<pid>/fd/<n>`）会带来写入空洞与日志错位，属于评估过风险之后的最后手段；`sync` 与丢弃缓存都不改变任何账目，前者不解释放，后者只是把性能资产扔掉。

### 4.2 站在哪一层，说明什么

| 停留层 | 回答里缺的东西 | 缺口类型 | 回到哪一节 |
| --- | --- | --- | --- |
| 第 0 层 | 把"名字消失"当成"空间释放" | 结论型 | 原理《文件系统的结构与选型》第 4 节；判例 3 |
| 第 1 层 | 说不出要看哪张句柄清单 | 判据型 | 实操 2.3；体系 6.1 第一类 |
| 第 2 层 | 不知道配额与项目标识的记账对象不在容器内 | 边界型 | 原理《容量边界、挂载与可见性》第 2 节；判例 7 |
| 第 3 层 | 说不出截断句柄的数据风险与取舍顺序 | 代价型 | 实操 2.3 的判据与动作；实操 3.1 |

### 4.3 第一反应不要做什么

不要反复删同一个文件；不要用 `sync` 或丢弃缓存当作处置；不要在没确认持有者身份之前截断句柄。

## 5. 现象三：`df` 与 `du` 差了几十 GiB

### 5.1 逐层演进

**第 0 层**

> 这两个工具肯定有一个不准，看哪个数字大就信哪个。

两个数字都很确定却互不相容，所以"总有一个是错的"读起来很自然。问题在于：这句话给出了一个结论，却没有指出任何要读的字段，按它行动只能是在两本账之间反复横跳。

**第 1 层（说出机制）**

> `df` 报的是超级块记账的已用块，含元数据、保留块以及已删除但仍被持有的块；`du` 遍历的是当前目录树，只看得到此刻在树里的东西。两者量的是不同的东西，差值本来就应该存在。

**第 2 层（给出判据）**

> 差值要落到四类之一，每一类有独立的字段。已被持有的删除文件看进程句柄清单；被挂载覆盖的目录看该路径的实际挂载关系（`findmnt -T`），`du` 遍历不到它而 `df` 仍记账；保留块与元数据看文件系统检查工具的结构计数字段；稀疏文件与延迟分配看 `stat` 的 `Size` 与 `Blocks`（`Blocks` 的单位是 512 B，与表观字节不是一个口径）。四类之外还有一处执行条件要核：`du` 有没有带"不跨文件系统"的限制，缺了它会把别的盘算进来。

**第 3 层（给出边界与代价）**

> 边界有两条。四类都对不上时不要继续在两本账之间找答案，要怀疑 `du` 的执行条件本身——权限不足会让它静默跳过一部分目录，跨文件系统的遍历会让它统计到不属于这一块的字节；换到 ext4 与 XFS 之间结论的形态也会变，XFS 的 inode 是动态分配的，空间占比的判据要从结构参数取，不能拿 ext4 的预分配口径去套。
>
> 代价与顺序：确认归属是只读动作，生产机上也可以做；被挂载覆盖的那一类要解开遮挡才能看全，而卸载是最后手段——强卸不会让进程停止写入，它只会让那些进程继续写到一个已不在目录树里的文件系统上。因此顺序是先在只读侧把四类逐一排除，再谈是否需要维护窗口。

### 5.2 站在哪一层，说明什么

| 停留层 | 回答里缺的东西 | 缺口类型 | 回到哪一节 |
| --- | --- | --- | --- |
| 第 0 层 | 在两个口径之间选一个"对"的 | 结论型 | 原理《文件系统的结构与选型》第 1 节；判例 4 |
| 第 1 层 | 知道两者不同，说不出四类各自的证据字段 | 判据型 | 实操 2.2 与体系 6.1 的四类拆分 |
| 第 2 层 | 不知道 `du` 自身还有执行条件、不知道 ext4 与 XFS 口径不同 | 边界型 | 判例 4 末段；原理《文件系统的结构与选型》第 2 节 |
| 第 3 层 | 说不出解开遮挡的代价与只读优先的顺序 | 代价型 | 原理《容量边界、挂载与可见性》第 4 节；实操 3.1 |

### 5.3 第一反应不要做什么

不要用一个工具否定另一个工具；不要在没确认归属前先删东西；不要忽略 `du` 的"不跨文件系统"选项。

## 6. 现象四：云盘扩容了，业务看到的容量没变

### 6.1 逐层演进

**第 0 层**

> 控制台显示扩容成功，机器上没变就是文件系统的问题，直接扩文件系统。

这个动作跳过的是整条链路的中间层。跳过之后工具可能报错，也可能成功改了一个对象而不是目标，两种结果都让"我明明扩过容"这句话失去依据。

**第 1 层（说出机制）**

> 容量从硬件到业务要经过设备、分区、物理卷、卷组、逻辑卷、文件系统六层，任何一层没长大，最上层看到的可用空间都不会变；扩容不是一次动作，是一条逐层验收的链。

**第 2 层（给出判据）**

> 逐层读 `SIZE`：设备与分区的容量来自块设备清单，物理卷的容量与卷组的空闲空间来自卷管理器的查询命令，逻辑卷的大小与池的水位（数据与元数据两个百分比）来自同一处，文件系统的容量来自 `df`。两个工具的记混点是硬判据：ext4 的扩容工具接受**设备**，XFS 的扩容工具接受**挂载点**；而 XFS 必须处于挂载状态才能在线扩大。验收标准只有一条——业务侧的容量确实变大并且能正常写入，不是"命令没报错"。

**第 3 层（给出边界与代价）**

> 边界有两条。设备容量变大之后内核不一定已经重读分区表，在用盘上改分区尤其如此，"设备变大了"与"分区变大了"是两个量；换到容器环境后这条链整体不成立，容器可写层与卷的容量由运行时与存储驱动分配，宿主侧扩了一块盘并不意味着容器内看到的可用空间跟着变。
>
> 代价与顺序：扩容是把容量给出去的动作，无法回退；顺序是先备份结构与数据（分区表导出、池的元数据导出），再从下往上一层层长大、一层层验收；相比之下缩容是重操作，XFS 只支持重建，ext4 必须先卸载并完成一次完整检查，所以容量规划应当在建文件系统那一步就确认清楚。

### 6.2 站在哪一层，说明什么

| 停留层 | 回答里缺的东西 | 缺口类型 | 回到哪一节 |
| --- | --- | --- | --- |
| 第 0 层 | 把扩容当成一次动作 | 结论型 | 体系 4.1 的七层链路；实操 3.5 |
| 第 1 层 | 说不出每层各自的字段与验收标准 | 判据型 | 实操 3.5 的排查顺序；实操 2.5 |
| 第 2 层 | 不知道设备与分区是两个量、容器里这条链整体不成立 | 边界型 | 体系 1.2；判例 6 末段 |
| 第 3 层 | 说不出扩容不可回退、缩容的顺序与前提 | 代价型 | 原理《写入路径与完整性》第 4 节；体系 4.2 与 4.3 |

### 6.3 第一反应不要做什么

不要在没确认内核看到新容量之前直接扩文件系统；不要跳过中间层；不要把扩容工具的参数写错对象；不要用重启代替中间步骤。

## 7. 现象五：挂载之后目录里原有数据"消失"

### 7.1 逐层演进

**第 0 层**

> 数据被挂载覆盖掉了，赶紧从备份恢复，或者把文件补回去。

"补回去"这个动作正是危险所在：在被遮住的目录里重建同名文件，会在新文件系统里留下第二份数据，而原数据仍然躺在下面，磁盘上的两份内容从此再也对不上。

**第 1 层（说出机制）**

> 挂载的语义是把一个文件系统的根接到目录树的某个目录上，**遮住**该目录原有的内容，而不是删除。原内容仍在原来的文件系统里，卸载即恢复可见。

**第 2 层（给出判据）**

> 两个方向都要读。向后看当前挂载关系：`findmnt` 的 `TARGET`、`SOURCE`、`FSTYPE` 说明这个位置现在挂着谁；向前查归属：`findmnt -T <那个目录>` 说明这个路径属于哪个文件系统。要查看被遮住的内容，用绑定挂载把上层再挂到另一个位置，从那里进去看（查完立刻卸载，否则它会一直作为一个挂载点存在）。同一现象在账目上的指纹是 `du` 看不到它而 `df` 仍然算着它的空间。

**第 3 层（给出边界与代价）**

> 边界有两条。容量条目要分清类型：内存文件系统与联合挂载的条目在 `df` 里同样占一行，但前者占的是内存不是磁盘，后者由容器运行时管理，把它们当成分区就会得出"这块盘哪来的"这类结论；换到另一台机器或另一个容器宿主上，同一个目录的归属可能完全不同，规划文档里写着"日志盘"与实施后它真的在一块独立盘上，是两件事，这条只能靠实际挂载关系发现。
>
> 代价与顺序：查看是只读的；要真正让被遮住的数据重新可见，需要卸载，而卸载是最后手段——有进程持有该挂载点上的东西时强卸不会让它们停止写入，只会让它们写到一个已不在目录树里的文件系统上。如果这层数据长期没人处理，它占用的空间会一直算在原文件系统头上，表现为"根分区没放什么却快满了"，处置动作应当排进维护窗口而不是当场做。

| 停留层 | 回答里缺的东西 | 缺口类型 | 回到哪一节 |
| --- | --- | --- | --- |
| 第 0 层 | 把"看不见"当成"不存在" | 结论型 | 原理《容量边界、挂载与可见性》第 4 节；判例 5 |
| 第 1 层 | 说不出查归属用哪个字段 | 判据型 | 实操 2.4；体系 3.3 |
| 第 2 层 | 不知道目录归属会随环境变、规划假设必须验证 | 边界型 | 判例 6；原理《容量边界、挂载与可见性》第 4 节 |
| 第 3 层 | 说不出卸载的代价与维护窗口的必要性 | 代价型 | 体系 3.1；实操 3.1 |

### 7.3 第一反应不要做什么

不要以为数据被删；不要在被遮住的目录里重建同名文件；不要用目录名推断文件系统归属。

## 8. 现象六：文件系统突然变只读，报 `Read-only file system`

### 8.1 逐层演进

**第 0 层**

> 业务先跑起来，重挂回可写，白天再研究日志。

从现象上看"恢复写入"确实等于"业务恢复"，所以这个动作读起来是止损。实际后果是让一个已经检测到错误的文件系统带着已知的损坏继续写，而当时的内核日志是唯一能说明根因的证据。

**第 1 层（说出机制）**

> 只读是内核检测到错误之后的保护动作，目的是阻止损坏扩散到更多元数据；它意味着已经出过错。

**第 2 层（给出判据）**

> 三个字段决定方向：`findmnt` 的 `OPTIONS` 里有没有 `ro`，这是"当前实际状态"；内核日志里介质错误、IO 错误与控制器重置的片段，这是根因方向（介质还是元数据）的直接证据；硬件健康计数里的重映射、待处理扇区与完整性错误计数，它决定根因是否落在设备上。把这三处读在一起，才能区分"元数据损坏"与"介质故障"——后者要做的是先保数据、先换盘，文件系统修复排在后面。

**第 3 层（给出边界与代价）**

> 边界有两条。看到只读不等于这份文件系统配置了"出错即重挂只读"：这一项由创建时的默认值、挂载选项与发行版配置共同决定，现场必须从实际挂载选项读，不能从发行版推；换到另一环境同一个现象的解释会整体改变——容器环境里只读的来源可能不是内核保护动作，而是运行时把层挂成了只读，此时按存储故障的路子查会一无所获。
>
> 代价与顺序：取证是只读的、随时可以做；写入与修复动作的不可逆性逐个不同——丢弃日志会永久丢掉尚未落盘的元数据变更，"全部问题自动回答是"在元数据自相矛盾时可能删掉有数据的那一边，自动检查只报告不改动所以风险最低。因此顺序固定在：取证、判断根因、停止写入、卸载、只读检查、备份、修复、只读挂载核对、最后才恢复可写。快照只能提供一次维护窗口那么长的退路，把"今天能回滚"当成"下个月也能回滚"会让整个顺序失去兜底。

### 8.2 站在哪一层，说明什么

| 停留层 | 回答里缺的东西 | 缺口类型 | 回到哪一节 |
| --- | --- | --- | --- |
| 第 0 层 | 把只读当成可以随手翻转的状态位 | 结论型 | 原理《写入路径与完整性》第 3 节；判例 8 |
| 第 1 层 | 说不出取证要看哪三处 | 判据型 | 实操 2.8 与 3.4；体系 5.2 的健康字段表 |
| 第 2 层 | 不知道只读这一现象在容器里另有来源 | 边界型 | 原理《容量边界、挂载与可见性》第 4 节；判例 8 末段 |
| 第 3 层 | 说不出各修复动作的不可逆性差异 | 代价型 | 原理《写入路径与完整性》第 4 节；判例 9 |

### 8.3 第一反应不要做什么

不要重挂为可写；不要在挂载状态下跑修复工具；不要在没备份时用"全部回答是"的参数；不要在介质已经有错的盘上做文件系统修复。

## 9. 现象七：`iostat` 的 `await` 很高

### 9.1 逐层演进

**第 0 层**

> `await` 涨了二十多倍，盘要坏了，准备换盘。

`await` 确实涨了，所以"设备在退化"读起来像是被数据支持的。问题在于这个量包含排队时间，它涨了既可能是设备变慢，也可能是请求变多。

**第 1 层（说出机制）**

> `await` 是平均完成时间并且包含排队时间；队列深度是另一个量。两者同涨说明请求量超过了设备处理能力，属于排队；完成时间高而队列浅，才说明请求不多但要很久，方向在设备或链路本身。

**第 2 层（给出判据）**

> 组合读三处。设备侧读完成时间与队列深度这一对，并把读与写分开（读慢与写慢的根因经常不同，写还要牵涉回写与阵列缓存），再看平均请求大小以区分随机小 IO 与顺序大 IO，且判断"现在正在发生什么"必须从第二行起看——第一行是自开机以来的平均值；内核日志与健康计数的四个关键项用于排除真实介质问题；进程级读数与"真正走到块层"的字节数把源头定到具体进程与文件。

**第 3 层（给出边界与代价）**

> 边界有两条。设备忙的时间比例在多队列设备上经常接近 100% 却远未饱和，那个列只在单队列设备上接近"饱和"的含义，所以判据必须成对使用；换到网络存储上配对关系还会被拆开，本地路径、网络、对端是三个独立变量，路径切换本身就会造成秒级停顿，业务的超时设置短于这个停顿就会看到"存储没问题但请求超时"。
>
> 代价与顺序：完成时间高而队列浅时方向在设备与链路，动作是查介质健康、阵列缓存与链路，换盘这类不可逆动作排在排除之后，并且要限速重建、避开业务高峰；完成时间与队列同高时方向在压力，动作是找源头、限流、错峰，此时加深队列只会让延迟更高，属于反向操作。两条路的动作相反，所以配对读这一步不能省。

### 9.2 站在哪一层，说明什么

| 停留层 | 回答里缺的东西 | 缺口类型 | 回到哪一节 |
| --- | --- | --- | --- |
| 第 0 层 | 把完成时间当设备健康指标 | 结论型 | 判例 10；实操 2.6 |
| 第 1 层 | 知道要配对，说不出配对里各自的字段 | 判据型 | 实操 2.6 的组合判读表；实操 3.2 |
| 第 2 层 | 不知道多队列设备与网络存储会让判据变形 | 边界型 | 原理《写入路径与完整性》第 5 节与第 6 节；判例 10 末段 |
| 第 3 层 | 不知道"排队"与"设备退化"的动作相反 | 操作型 | 实操 3.2"看到什么转向哪"；治理 3 |

### 9.3 第一反应不要做什么

不要只看 `await` 或只看设备忙的比例就宣布盘坏了；不要在没定位源头前调大队列深度；不要在多队列设备上把忙的比例接近 100% 当告警条件；不要继续用已废弃的那一列下结论。

## 10. 现象八：写入变慢，进程进入不可中断睡眠

### 10.1 逐层演进

**第 0 层**

> 进程卡住了，杀不掉就重启，重启完一般就好了。

杀不掉这件事在这个场景里恰好说明方向错了：不可中断睡眠的进程等的是内核里的 IO 完成，信号要等它回到用户态才被处理。重启能"好"，是因为它把现场一起清掉了。

**第 1 层（说出机制）**

> 这一层的慢有两类来源。一类是本地回写积压：脏页积累到阈值后内核启动回写，超过更硬的阈值就限速或阻塞发起写的进程；另一类是网络存储不可达：硬挂载会无限重试，进程停在不可中断睡眠。

**第 2 层（给出判据）**

> 先分方向，再读字段。本地回写的判据是脏页量、阈值与设备侧的排队深度和完成时间：设备没有报错、健康计数没有变化而写入延迟出现长尾，指向回写链；网络存储的判据是问题发生在哪个挂载点、进程等待的位置，以及通路三段（对端、网络、路径状态）各自的状态。判定为网络侧之后，处置对象是通路而不是进程。上限类参数的实际生效值一律现场读，两种写法（比例与字节数）互斥，取错一组等于没设。

**第 3 层（给出边界与代价）**

> 边界有两条。回写积压与介质故障是两种结局：前者可恢复、可调优，只是延迟；后者涉及数据风险，必须停止写入并取证，把"慢"当"坏"处理会白做一场，反过来把"坏"当"慢"处理会继续写坏。换到网络存储与容器环境后判据还会再变一次——网络存储把"一次 IO 有多快"拆成三个独立变量，容器可写层与卷的写入还要过运行时与存储驱动，"网络通"不等于"存储通"，还要看对端服务、导出权限与端口。
>
> 代价与顺序：收紧回写上限只在瓶颈确实是限速本身时有效，如果设备排空速率本来就低于产生速率，收紧只会让限速更早启动总吞吐更差；丢弃缓存是测量动作不是优化动作，生产上不要执行。网络侧的处置顺序是确认挂载点、确认通路、优先恢复通路——通路恢复后等待状态自行消解；强卸与重启排在无法恢复之后，且重启前要留日志，因为存储未恢复时机器可能卡在启动过程中。所有参数改动都要有变更单、验收指标与回滚命令。

### 10.2 站在哪一层，说明什么

| 停留层 | 回答里缺的东西 | 缺口类型 | 回到哪一节 |
| --- | --- | --- | --- |
| 第 0 层 | 把"杀不掉"当成权限或资源问题 | 结论型 | 原理《写入路径与完整性》第 6 节；判例 10 |
| 第 1 层 | 说不出脏页与通路的各自判据 | 判据型 | 实操 3.6 的排查顺序；实操 2.6 |
| 第 2 层 | 不知道"慢"与"坏"要先分、容器与网络存储让判据再变 | 边界型 | 原理《写入路径与完整性》第 2 节与第 6 节；治理 1 |
| 第 3 层 | 不知道参数的两种写法互斥、不写回滚与观察窗口 | 判据型（口径） | 原理《写入路径与完整性》第 2 节；治理 3 与治理 4 场景四 |

### 10.3 第一反应不要做什么

不要批量强杀进程；不要一卡住就强卸；不要在没分清"慢"与"坏"之前动硬件；不要用重启代替通路核查。

## 11. 三条横切线

主线之外的三个量横穿全部站点。它们不产生新的现象，但每一个判断都要用到，所以单独列出来定位。

**账目线——这块空间算在谁头上。**

> 停在第 0 层的说法是"`du` 不准"，第 1 层知道已用块、目录树占用与表观大小是三个口径，第 2 层能把差值拆到四类并给每一类一个字段，第 3 层知道 `du` 自身还有执行条件、且 ext4 与 XFS 的结构口径不同。判据缺失时的表现是：数字对不上就怀疑工具。

**限制线——拒绝写入的是哪一类上限。**

> 停在第 0 层的说法是"`No space left on device` 就是磁盘满了"，第 1 层能分出三个错误码与另外几类不占字节的上限，第 2 层指出每一类的查询入口在哪个文件、哪个字段，第 3 层知道记账只能在挂载时打开、装机时定下的结构参数改不了。判据缺失时的表现是：改完配置、重启了服务，然后疑惑为什么没变化。

**完整性线——哪些动作不可逆、顺序是什么。**

> 停在第 0 层的说法是"重挂回可写让业务先跑起来"，第 1 层知道只读是保护动作、日志重放保证的是一致性，第 2 层会读实际挂载选项、内核日志与健康计数，第 3 层知道丢弃日志与"全部回答是"的数据代价，并且能排出取证在先的顺序。判据缺失时的表现是：先动手恢复写入，之后再也说不清根因是哪一类。

三条线共有的定位信号是"我知道有这几种可能，但每次都要重新推一遍"——这属于判据没落到字段上，补法是回到体系篇第 6 节，把每条线的字段、单位、判据与转向写成一张自己的对照表。

## 12. 交付物是排查的凭证

定位缺口不能只靠回想。以下六件物件是把"我做过"与"我读过"分开的唯一办法，缺少它们时，前面第 3 至第 11 节的自评会整体偏高。

| 物件 | 要留下什么 | 用来验证哪一层 |
| --- | --- | --- |
| 只读基线卡 | 环境（发行版与内核、采集时刻）、身份（型号、序列号、槽位、介质）、结构（分区表与分区、卷与阵列成员、文件系统类型与结构参数）、水位（容量、inode、池的数据与元数据）、挂载（实际生效的选项）、健康（关键计数与阵列状态）、边界（非空间类上限） | 第 2 层（有没有真取到值） |
| 可回滚变更记录 | 改前与改后原文、逐步验收命令与预期输出、回滚命令、失败预案，以及这是哪一类变更（挂载配置、容量、参数） | 第 2、3 层（是否知道验收依据与代价） |
| 复盘记录 | 现象原文、影响面、证据（命令输出原文）、根因判断、动作序列与时间、**被否决的方案及原因**、验收结果 | 第 1、3 层（能否排除掉一种成因） |
| 换环境对照记录 | 选三项现象，各给出容器内与宿主侧的取数位置、以及另一发行版或另一内核版本下会变的那一处 | 第 3 层（换环境是否还成立） |
| 未实测标注 | 本环境做不了的部分与补做方式 | 全部（防止把转引当实测） |
| 错题清单 | 现象、当时的答案、正确口径、缺的那一层、下次复查日期 | 定位本身（缺的那一层必须落在六类缺口上） |

其中只读基线卡与可回滚变更记录直接对应本章的两个里程碑；复盘记录是"有没有真处置过一次"的唯一凭证。这六件同时是治理篇四件套的自用形态：治理产物是交出去的，这六件是留给自己的。

## 13. 记录格式

一行记一个现象，五栏：现象、当时读到的字段、判据、边界、缺口层。表头写环境三件事——内核版本、发行版、是否在容器内。

```text
【环境】内核 6.8.0-139-generic · 发行版 Ubuntu 24.04.5 LTS · 未在容器内
【现象】……｜【当时读到的字段】……｜【判据】……｜【边界】……｜【缺口层】……
```

状态用三个固定的词：实测、转引、未实测。"转引"要写出处（man 节号或内核文档路径）。把读过的当做过是这份记录唯一无法挽救的失效方式：环境更换后结论被推翻，而记录里看不出哪些结论本来就没有实测支撑。

复查日期只写 D+1、D+3、D+7、D+21 四个。没有日期的错题等于没有复查。

## 14. 定位到缺口之后补什么

六个类型的补法不同，用错补法会补到不需要补的地方。

| 缺口类型 | 表现 | 补法 | 不要做什么 |
| --- | --- | --- | --- |
| 结论型 | 停在现象命名，连机制都不熟 | 回到对应原理篇，用自己的话写出机制并配一个反例 | 不要从背结论开始 |
| 判据型 | 机制清楚，落不到字段 | 重新执行一次查询，记录输出形态与关键字段，而不是只记命令名 | 不要只记命令不记输出 |
| 判据型（口径） | 分不清同一量的多个口径、累积值与单位 | 把该字段的口径、单位、是否累计写成一行；凡累计值一律标注"取差值"，凡容量一律标明朝一种进位 | 不要把不同口径、不同进位的数放进同一张对比表 |
| 边界型 | 结论正确，换环境即失效 | 列三条反例：换内核版本、换发行版、换容器环境各验证一次 | 不要以"应该大致相同"作结 |
| 代价型 | 知道怎么做，不知道风险 | 补三行：代价、回滚方式、影响面 | 不要把风险留给别人发现 |
| 操作型 | 讲得出、没做过 | 在可快照实验机上做一次只读采集与一次可回滚变更，留下带时刻的原始输出 | 不要用纸面推演代替动手 |

带着一个具体缺口回到一到两篇，比重读整章有效。如果发现"每篇都要重读"，通常说明缺的不是细节，而是前置概念——回到本章地图确认五站与三条横切线各自提供什么。

## 15. 边界

本篇覆盖的范围与本章一致，落在别处的追问照实划出去：页缓存与内存压力的完整口径在内存那一章，网络协议栈与丢包重传在网络的章节，服务单元的启动顺序与挂载单元的依赖在服务管理的章节，容器运行时的镜像与存储驱动不属于本库范围。遇到这类追问，正确回答是指出它属于哪一章，而不是在本章内部勉强作答。

本篇的判据只引用本章出现过的字段。引用章外指标时，测的是别的东西，缺口也会被错误归因。

核查动作用只读方式，生产机上也可以做；凡需要变更才能验证的项，在可快照的实验机上做，并留下回滚命令与观察窗口。涉及擦除与重建的动作只在已下线或待回收的盘上执行，动手前先核对设备身份。

## 16. 核对方式

从本章地图的故障现场定位表抽四行（写不进去、对不上、变慢、写坏各至少一类），逐行遮住右侧自测；每项说出站点、首查字段、判据、一条边界、一句"第一反应不要做什么"。说完之后自己回答一个问题：**刚才哪一句指不到字段**。指不出的那一句就是当前所处的位置，据此翻回第 3 至第 11 节的对应表格。

再抽一项承接两层追问：第一层问"依据是什么"，第二层问"换个环境还成立吗"。第二层答不出的，缺口在边界型，补法见第 14 节。

## 常见坑

| 常见做法 | 后果或事实 |
| --- | --- |
| 把这篇当成一张评分表 | 它的用途是定位停在哪一层，不是给出通过与否 |
| 用"读了几遍"判断自己会不会 | 阅读次数与提取强度无关，只与能否当场给出判据有关 |
| 用术语熟练度代替判断力 | 三个错误码背得出、机器上没查过，缺的是操作层 |
| 机制讲得流畅就以为已经会了 | 判据落不到字段上，是本篇最常见的一种失效 |
| 把"读到的字段"写成命令名 | 命令名不构成证据；要记的是输出里的哪一个值 |
| 未实测项不标注 | 环境更换后无法分辨哪些结论本来就没有实测支撑 |
| 缺口用"没记住"概括 | 缺的类型不同补法不同，概括之后一定补错方向 |
| 一次把所有层级都读完 | 逐现象一次读一层，对照一次，比通读一遍有效 |
| 只在本机核对，不做换环境对照 | 容器、另一发行版、另一内核版本正是判据失效的地方 |

## 要点自测

**问：本篇与题库、与能力清单的分工有什么不同？**
答：题库检验记住多少，能力清单检验做到什么程度，本篇回答"我的回答停在哪一层、因此缺的是哪一篇的哪一节"。

**问：第 1 层与第 2 层在语言外观上几乎一样，区分它们的那一个动作是什么？**
答：能不能指到一个字段。指不到字段的机制叙述停在第一层。

**问：为什么"容量还有余却写不进去"这一处的第 0 层误判最值得单独列出来？**
答：因为它用一本账的读数否掉了另外两本账，而据此得出的动作（清理）在真写满时有效、在另外两类上无效，且会把 inode 与保留块的现场一起清掉。

**问：`df` 与 `du` 对不上时，为什么"差在哪一类"比"差多少"更重要？**
答：四类的处置完全不同，只报差值等于没有定位；每一类都有独立的证伪字段，说不出字段就没法动手。

**问：文件系统变只读时，为什么第一步不是恢复写入？**
答：只读是内核在保护数据，它意味着已经出过错；先取证并判断根因是介质故障还是元数据损坏，才能决定是先保数据、先换盘，还是进入修复流程。恢复写入会让损坏继续扩散，并让根因失去证据。

**问：`await` 高时，为什么"排队"与"设备退化"的处置动作相反？**
答：排队是请求量问题，动作是找源头、限流与错峰；设备退化是介质或链路问题，动作是查健康与链路、必要时换盘。把前者当后者会付出换硬件的成本而没有改善，把后者当后者之外的东西会让故障继续。

**问：三条横切线共有的定位信号是什么？**
答：可说成"知道有这几种可能，但每次都要重新推一遍"——说明判据没有落到字段上，缺的是可复用的对照表。

**问：错题清单里最关键的是哪一列？**
答：缺的那一层。只抄正确答案，第二次会错在同一处。
