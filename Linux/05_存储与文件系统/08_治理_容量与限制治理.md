# 容量与限制治理

## 1. 没有边界时会怎样

存储的故障形态有一个共同点：**它的影响面由「谁和谁共用同一块盘」决定**，而不由出错的那一方决定。一块共享盘上，一个失控的日志目录能写满整个文件系统，让同盘的其他业务、甚至系统自身的写入一起失败。

三种典型放大路径：

| 放大路径 | 机制 | 结果 |
| --- | --- | --- |
| 共用文件系统 | 同一块盘上的任何一方写满，其他方全部写不进去 | 单租户故障 → 整机故障 |
| 共用卷池 | 精简置备的池写满会波及池内**所有**卷，常见表现是整组变只读 | 单卷故障 → 全组故障 |
| 共用设备 | 重建、全盘扫描、批量备份会打满设备带宽 | 单盘维护 → 全线延迟 |

所以「给共享目录设上限」不是节省空间的手段，而是**可用性手段**：它把故障域从「整台机器」收缩到「一个租户」。这也是它与「扩容」互补而非互斥的原因——扩容解决总量不够，边界解决分布失控。

治理要同时回答三个问题，缺一个都不完整：

1. **技术边界在哪**（谁的上限，配在哪一层）；
2. **怎么被观测**（水位进监控，且是与增长趋势比较）；
3. **怎么被追溯**（谁在什么时候改过谁的额度，改的依据是什么）。

只有第一条的方案会在下次事故里重演；只有前两条的方案无法解释「为什么上个月调过又出事了」。

## 2. 上限配在哪一层

存储的上限分散在四类载体上，**它们的修改方式、生效时机与故障形态都不同**。做治理时先明确「要限制的是哪一件事」，再去找对应的载体。

| 要限制的 | 载体 | 生效时机 | 撞上之后 |
| --- | --- | --- | --- |
| 一个目录树的总量 | 文件系统的配额（项目/用户/组） | **记账需挂载时开启**；强制可运行时开关 | `Disk quota exceeded` |
| 一个池的总量 | 卷管理器的池水位（数据与元数据） | 建池时与池扩容时 | 常见为整组只读或写入失败 |
| 一个进程的资源 | 会话限制、服务单元属性、内核参数 | 会话建立或服务启动时 | 打开失败类错误 |
| 一类事件监控 | 内核参数（各监控子系统上限） | 参数写入后立即 | 创建失败，**或静默丢弃事件** |

三条实践推论：

**目录级的边界应当钉在目录树上，而不是钉在账号上。** 共享目录里的文件往往由服务账号写入，按账号分配会把所有租户算成一个对象。把「一个业务目录 = 一个项目」作为组织方式，边界就与业务结构一致，也更容易解释与追溯。

**记账与强制要分开理解。** 启用配额的子系统大多要求**在挂载时就打开记账**，挂载后只能开关强制。这是「配额配了却不生效」的头号原因，也是变更单里必须写明的一项：改的是挂载选项，不只是运行时的开关。

**池水位是容量治理，不是性能治理。** 精简置备省下的空间来自「业务不会同时写满」这个假设；把超配比例拉满等于把假设变成赌注，而输的代价是全组故障。数据水位与元数据水位都要设阈值并留余量。

## 3. 字段的治理用法

监控里最常被误用的不是缺字段，而是**用错了字段的含义**。下表是把观测字段翻译成治理决策的方式。

| 字段 | 观测含义 | 治理用法 |
| --- | --- | --- |
| 容量使用率 | 文件系统已用块的比例 | 定扩容触发线；**必须与 inode 使用率成对配置** |
| inode 使用率 | 已用 inode 的比例 | ext4 上往往先于容量告警；触发时先想清理与选型，不是扩容 |
| 配额用量百分比 | 对象用量与其额度的比 | 定告警线（如 80% 提示、90% 紧急）；比「是否超限」早得多 |
| 宽限期状态 | 已越过软限、正在计时 | 单独列出：说明该对象已越线很久，应当介入 |
| 池数据/元数据水位 | 池内实际占用与元数据占用 | 两道阈值；元数据写满比数据写满更难处理 |
| 健康关键计数 | 重映射、待处理扇区、寿命消耗 | 用**趋势**而不是单值触发巡检；持续增长才升级 |
| 阵列状态 | 是否降级、重建进度 | 降级即告警；重建进度与限速是维护动作的依据 |
| 设备延迟与队列 | 完成时间与排队深度 | **必须成对读**：定「排队」与「设备退化」的分界 |
| 回写积压 | 待落盘与正在落盘的量 | 与设备延迟同看，区分回写限速与设备瓶颈 |
| 非空间类上限 | 句柄、事件监控与队列 | 与字节容量无关的另外几本账，单独配置 |

两条容易做错的细节：

**取差值，不取绝对值。** 累计型计数（事件次数、阵列重建字节、IO 计数）只有两次读数相减才表达「这段时间发生了什么」。

**基线要带条件。** 容量与延迟的数字只有在同口径、同单位、同条件（型号、挂载参数、测试条件）下才能比较。**没有条件的数字半年后不可比，等于没记。**

## 4. 治理场景与产出

下面四个场景是运维侧真正会遇到的治理动作。每个都给出**要交出的产物**——治理的验收标准是「交出了东西」，不是「看过文档」。

### 场景一：给共享目录划边界

**背景**：一块多租户 XFS 数据盘上有 20 个业务目录，其中一个租户的日志失控增长写满整盘，其他 19 个租户全部写入失败。事后要求「不能再来一次」。

**做法**：确认文件系统以配额选项挂载（否则记账没开）→ 给 20 个业务目录各绑定一个项目标识 → 设软限与硬限（硬限按当前用量上浮留出增长空间，软限低于硬限并配宽限期）→ 把用量百分比与宽限期状态接进监控 → 把「目录 ↔ 项目标识 ↔ 业务方 ↔ 额度 ↔ 变更时间」写进台账。

**产出**：一份**配额策略表**（上述字段齐全）加上一封变更记录，里面写清挂载选项的改动、验收命令、以及回滚方式。

**反例**：让每个租户「自己控制日志轮转」——没有强制力的约定不构成边界，这次事故恰恰证明了靠自觉不成立。

### 场景二：一个租户写满之后

**背景**：告警显示某目录配额用量 96%，业务方报写入间歇失败。

**做法**：先区分是**配额到顶**还是**容量到顶**（两者的 errno 不同、方向不同）→ 看配额报表的用量、软硬限与宽限期状态 → 定位增长来源（哪个子目录、什么文件类型、增长速率）→ 给出三种处置之一并说明依据：让业务清理、调额度（依据是增长趋势与预算）、或改应用行为（例如日志轮转策略）。

**产出**：一份**空间对账表**：对象、当前用量、额度、增长速率、证据命令、处置决定与依据、下次复核时间。

**关键纪律**：调额度属于生产变更，要有变更单；「先调大让它跑起来」会把问题推到下一次更严重的故障。

### 场景三：同批次硬件的批量治理

**背景**：巡检发现 40 台机器上部署了同型号、同批次的数据盘，其中 3 台已出现待处理扇区。

**做法**：把健康计数按批次汇总看趋势（**不是看单台单值**）→ 判断是盘老化、线缆/背板、供电还是固件 → 输出批量替换计划并按影响面排序，而不是等每一台各自降级后再逐个处理。

**产出**：一份**巡检台账**（机器、槽位、序列号、关键计数、趋势、处置状态）与一份排期表。**同批次盘会一起老化，连续降级是可以提前规划的。**

### 场景四：变更的可回滚性

**背景**：一次 fstab 改动导致某台机器重启后进入紧急模式，事后发现没有备份原文、也没有人复核过那一行。

**做法**：把存储类变更的固定动作写进流程——改动前导出现有配置与结构（挂载配置、池的元数据）、改动中逐层验收、改动后用业务指标验收；每人写清**回滚命令**而不只是「回滚方式」。

**产出**：一份**变更单模板**，字段见下一节。

## 5. 治理产物四件套

**存储基线卡**：环境（发行版、内核、采集时间）、身份（型号、序列号、槽位、介质）、结构（分区/池/阵列、文件系统类型与结构参数）、水位（容量、inode、池、配额）、挂载（参数）、健康（关键计数与阵列状态）、边界（非空间类上限）。用途：回答「这台机器正常长什么样」。

**配额策略表**：目录 ↔ 项目标识 ↔ 业务方 ↔ 软硬限 ↔ 宽限期 ↔ 监控阈值 ↔ 变更时间。用途：回答「这个目录谁负责、能长到多大」。

**变更单**：改前原文与改后原文、依据（基线卡或趋势数据）、影响面（哪些业务依赖）、逐步验收命令与预期输出、**回滚命令**、失败预案（尤其针对会改挂载配置的变更）。用途：让下一个人能在不理解全部背景的情况下安全地做或撤。

**巡检与处置记录**：现象原文、影响面、证据（关键命令输出）、根因判断、动作序列与时间（含**被否决的方案与原因**）、验收结果、后续改进与同类机器复查。用途：回答「这次到底修好了没有、别处有没有同样的问题」。

其中「被否决的方案与原因」这一栏的价值常被低估：**它记录了当时的判断过程**，是下一个人（或三个月后的自己）不必重走弯路的原因。

## 6. 行业常见做法

不同组织的规范差别很大，但方向一致：

- **默认有界**：共享目录上线时就带配额，而不是出事后再补；
- **身份优先于路径**：持久配置一律用 UUID、LABEL 或按序列号的稳定别名，不用设备名；
- **健康主动看**：介质健康与内核日志纳入例行巡检，比等阵列降级或文件系统只读便宜一个数量级；
- **重建与维护限速**：把重建、全盘扫描、批量备份看作会影响业务的动作，安排窗口并限速；
- **冗余与备份分开**：冗余对抗硬件失效，备份对抗数据错误与人为失误，两者的验收方式完全不同；
- **变更留证据**：改前备份、逐步验收、写清回滚，尤其是会改挂载配置的变更。

这些方向的原始材料在发行版官方文档的存储管理章节、官方的配额与卷管理文档、存储厂商的白皮书与 Google SRE 系列（容量规划与错误预算部分）里都有，可按自己的环境取舍。**其中的具体阈值与流程必须按自己机器的历史基线重新评估**，不能直接照抄。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 共享目录不设配额 | 单个租户失控即整机故障；这是共享盘最常见的放大路径 |
| 只设硬限不留软限与宽限期 | 业务峰值时被硬砍，可能比写满更严重 |
| 在文件系统上只开运行时强制而不配挂载选项 | 记账没开，配额形同虚设 |
| 把配额当告警的替代 | 只是把「写满整盘」换成「写满自己的配额」，业务照样挂 |
| 精简置备的比例拉满 | 省下的空间来自「不会同时写满」的假设，赌输的代价是全组故障 |
| 只监控容量水位 | inode、配额、池水位、非空间类上限全部漏掉 |
| 用单次健康计数决定换盘 | 要看趋势；单值不表达老化速率 |
| 等每一台机器各自降级后再逐个处理 | 同批次盘会一起老化，应做批量替换计划 |
| 项目标识不写进台账 | 半年后没人知道某个标识对应哪个业务 |
| 变更单只写「已回滚」不写回滚命令 | 下一个人无法在故障中执行回滚 |
| 只报结论不留证据 | 无法复盘，也无法判断是否真的修好 |
| 用「我们会盯着」代替技术边界 | 没有强制力的约定不构成边界 |

**第一反应不要做什么**：不要用「我们会盯着」代替技术边界；不要在没确认记账已开启时配额度；不要在没有依据时调大额度；不要只报容量水位就认为监控完整；不要用单次健康计数值决定换盘。

## 要点自测

**问：为什么共享目录必须有容量上限，它与扩容是什么关系？**
答：因为同一块盘上的任何一方写满都会让其他方全部失败，而存储的影响面由「谁和谁共用」决定。配额把故障域从整机收缩到一个租户，属于可用性手段；扩容解决总量不够，边界解决分布失控，两者互补。

**问：为什么目录级边界通常用「项目」而不是「用户」来组织？**
答：共享目录的文件常由同一个服务账号写入，按用户/组分配会把所有租户算成一个对象；按目录树绑定项目标识能与业务结构对应，既可解释也可追溯。

**问：配额的「记账」与「强制」为什么要分开写在变更单里？**
答：记账大多只能在挂载时开启，挂载后只能开关强制。只改运行时开关的变更对「配额不生效」毫无帮助，所以变更单必须写明改的是挂载选项，并给出验收命令。

**问：监控里哪些项是「只报容量」一定会漏掉的？**
答：inode 使用率、配额用量与宽限期、池的数据与元数据水位、句柄与事件监控类上限、介质健康与阵列状态；此外回写积压与重建退化表现为延迟而非容量。

**问：为什么「调大额度」必须走变更流程？**
答：它改变的是边界本身。没有依据的调大只是把问题推到下一次更严重的故障，而且会失去「为什么这个额度这么定」的历史。

**问：一份变更单里最容易被忽略、但最有价值的一栏是什么？**
答：回滚命令与「被否决的方案及原因」。前者让你在故障中能执行、后者记录了当时的判断过程，让下一个人不必重走弯路。
