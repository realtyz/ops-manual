## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **配额把「整机故障」降级成「某个租户的故障」**：一个人写满配额，其他人不受影响。
> - **XFS 的记账必须在挂载时打开**：`prjquota`/`uquota`/`gquota` 写在 fstab 里；挂载后只能用 `xfs_quota -x -c 'enable'` 开关「强制」，**记账本身关不了**。
> - **优先用项目配额**：它把边界钉在「一个目录树」上，和业务目录一一对应，比按用户分配更好管、更好解释。
> - **配额到顶报 `Disk quota exceeded`（`EDQUOT`）**，不是 `No space left on device`；排查「写不进去」时要单独问一句「这个目录有配额吗」。
> - **配额不是告警的替代品**：不监控配额水位，你只是把「写满整盘」换成了「写满自己的配额」——业务照样挂。

## 1. 为什么共享目录必须有上限

没有配额的共享目录，故障链条是固定的：

1. 某个应用/租户的日志或缓存失控增长 → 2. 写满整个文件系统 → 3. **同盘上的所有业务、甚至系统自身（`/var/log`、`/tmp`）都写不进去** → 4. 整机级事故，所有租户受影响。

配额把这个链条在第 2 步截断：**失控的那个租户先撞到自己的边界**，其他人不受影响。

| 场景 | 为什么需要配额 |
| --- | --- |
| 多租户共享的数据盘 | 一个租户的失控写入不能影响其他租户 |
| 文件上传/网盘类业务 | 用户上传量不可控 |
| 容器节点的容器可写层与日志目录 | 单个 Pod 写爆卷会连带影响宿主 |
| 研发/测试共享目录 | 「临时文件」从来不会自己清理 |
| 数据库备份目录 | 备份策略写错（如全量备份堆积）会迅速吃满盘 |

## 2. ext4 与 XFS 两套机制

| 文件系统 | 启用方式 | 常用命令 | 配额对象 |
| --- | --- | --- | --- |
| ext4 | 挂载参数 `usrquota`/`grpquota`（或用 `tune2fs -O quota` 创建配额文件） | `quotaon`、`setquota`、`edquota`、`repquota -a`、`quotacheck` | 用户、组 |
| XFS | 挂载参数 `uquota`/`gquota`/**`prjquota`**；**记账必须在挂载时打开**，挂载后只能用 `xfs_quota -x -c 'enable'`/`'disable'` 开关强制 | `xfs_quota -x -c 'report -h'`、`xfs_quota -x -c 'project -s -p <path> <id>'`、`xfs_quota -x -c 'limit -p ...'` | 用户、组、**项目（目录树）** |

```bash
findmnt -o TARGET,FSTYPE,OPTIONS /data
                                     # 验证：当前挂载是否启用了配额（XFS 看有没有 prjquota）
sudo repquota -a                     # 验证：ext4 上的用户/组配额使用情况
sudo xfs_quota -x -c 'report -h' /data
                                     # 验证：XFS 的用户/组/项目配额报表
sudo xfs_quota -x -c 'state' /data   # 验证：记账与强制的开关状态（记账是否启用）
```

> [!important] XFS 配额的「记账」与「强制」是两件事
> **记账（accounting）只能在挂载时用 `prjquota`/`uquota`/`gquota` 打开**，之后无法在运行时补开——这也是「配额配好了却不生效」的头号原因：fstab 里少了选项，只 `enable` 强制是没用的。
> **强制（enforcement）**可以在挂载后用 `xfs_quota -x -c 'enable'`/`'disable'` 开关，用于临时放开限制（例如让业务先把数据迁出来）。

## 3. 项目配额：把边界钉在目录上

XFS 的项目配额用「项目 ID」把**一个目录树**和一套额度绑定起来，正好对应「一个租户一个目录」的组织方式：

```bash
sudo mkdir -p /data/tenantA
sudo xfs_quota -x -c 'project -s -p /data/tenantA 1001' /data
                                     # 验证：把目录绑定到项目 ID 1001（-s 会把已有文件也纳入统计）
sudo xfs_quota -x -c 'limit -p bhard=500g bsoft=450g 1001' /data
                                     # 验证：硬上限 500GiB、软上限 450GiB
sudo xfs_quota -x -c 'report -h' /data
                                     # 验证：项目 1001 的用量、软硬上限与是否超软限
sudo xfs_quota -x -c 'project -c -p /data/tenantA 1001' /data
                                     # 验证：只清空继承标记/统计（清理时用，慎用）
```

项目配额的三个实践要点：

1. **一个业务目录 = 一个项目 ID**，ID 建议写进台账（否则半年后没人知道 1001 是谁）。
2. **子目录默认继承**：项目 ID 会沿目录树继承，新增子目录自动计入。**但如果有人把别的目录的文件移进来，或者用 `mv` 跨文件系统搬数据，统计行为要实测确认。**
3. **改配额前先看报表**：`report -h` 是唯一能回答「这个租户现在用了多少」的工具。

## 4. 软限制、硬限制与宽限期

配额不是只有「一刀切」：

| 类型 | 行为 | 用途 |
| --- | --- | --- |
| **硬限制（bhard/ihard）** | 超过即拒绝写入（`EDQUOT`） | 真正的安全边界 |
| **软限制（bsoft/isoft）** | 超过只给警告，但在**宽限期**内必须降下来 | 给业务留出自清理的时间窗 |
| **宽限期（grace time）** | 超过软限后允许「暂时越线」的时长（默认通常 7 天，XFS 用 `-t` 查看与设置） | 避免业务在峰值时被硬砍 |

```bash
sudo xfs_quota -x -c 'timer -p' /data
                                     # 验证：项目配额的宽限期设置（XFS 默认值以本机为准）
sudo xfs_quota -x -c 'limit -p bhard=500g bsoft=450g 1001' /data
                                     # 验证：软限 450GiB、硬限 500GiB 的组合
sudo repquota -a | head              # 验证：ext4 上的软/硬限制与宽限期状态一览
```

设计原则：**软限制留缓冲、硬限制防失控、宽限期给业务留时间**。三者配在一起，才能在「业务峰值不被砍」与「整机不被写爆」之间取得平衡。

## 5. 阈值与监控：配额必须配套

配额配好只是第一步。**没有监控的配额，只是把故障从「写满整盘」换成了「写满自己的配额」**——业务照样挂，只是影响面变小了。

必须纳入监控与告警的项：

1. **每个配额对象的用量百分比**（例如 80% 告警、90% 紧急），而不仅是「有没有超限」。
2. **宽限期状态**：处于宽限期的对象要单独列出（说明它已经越线很久了）。
3. **inode 配额**（如果设了 `ihard`/`isoft`）：文件数也会被限制。
4. **配额策略本身的变更记录**：谁在什么时候把哪个租户的额度调大了。

容量水位本身也建议分两级以上：例如**70% 提示、85% 预警、95% 紧急**，并且**容量与 inode 两条水位一起报**——ext4 上 inode 往往比容量先满，只报容量一定会漏（子笔记 09）。

```bash
sudo xfs_quota -x -c 'report -h' /data | head -20
                                     # 验证：把这份输出交给监控采集（或写脚本解析）
sudo xfs_quota -x -c 'report -h -p' /data
                                     # 验证：只看项目配额（-p），告警脚本最常用
```

## 6. 生产动作：给共享目录划边界

1. **确认文件系统支持哪套配额**：`findmnt -o FSTYPE,OPTIONS /data`；XFS 要有 `prjquota`，ext4 要有 `usrquota`/`grpquota`。
2. **补齐挂载选项**（XFS 场景）：改 fstab → `systemctl daemon-reload` → `umount`/`mount`（或重启，见子笔记 06 的验收三步）。
3. **建目录与项目 ID**：`xfs_quota -x -c 'project -s -p <path> <id>'`。
4. **设软硬限制**：`limit -p bhard=... bsoft=...`（留 10% 左右缓冲）。
5. **验收**：`report -h` 显示额度；用 `dd` 写穿硬限，确认报的是 `Disk quota exceeded`。
6. **接监控**：用量百分比与宽限期状态都进告警。
7. **写台账**：目录 ↔ 项目 ID ↔ 业务方 ↔ 额度 ↔ 变更时间。

> [!example]- 实验 7：在 XFS 上给一个目录设 100MiB 项目配额，写到超限为止
> **怎么做**：在 loop 上建 LVM + XFS（**挂载时带 `prjquota`**），给一个目录设 100MiB 硬上限，然后 `dd` 写到被拦下。
> ```bash
> dd if=/dev/zero of=/tmp/lab-quota.img bs=1M count=1024
> LOOP7=$(losetup --find --show /tmp/lab-quota.img)
> sudo pvcreate "$LOOP7" && sudo vgcreate vgquota "$LOOP7" && sudo lvcreate -l 100%FREE -n lvquota vgquota
> sudo mkfs.xfs -f /dev/vgquota/lvquota
> sudo mkdir -p /mnt/quota && sudo mount -o prjquota /dev/vgquota/lvquota /mnt/quota
>                                      # 验证：项目配额要求挂载时就带上 prjquota（否则记账没开）
> sudo xfs_quota -x -c 'state' /mnt/quota
>                                      # 验证：确认记账（accounting）已经启用
> sudo mkdir -p /mnt/quota/tenantA
> sudo xfs_quota -x -c 'project -s -p /mnt/quota/tenantA 1001' /mnt/quota
>                                      # 验证：目录绑定到项目 ID 1001
> sudo xfs_quota -x -c 'limit -p bhard=100m 1001' /mnt/quota
>                                      # 验证：项目 1001 的硬上限是 100MiB
> sudo dd if=/dev/zero of=/mnt/quota/tenantA/f1 bs=1M count=200
>                                      # 验证：写到约 100MiB 就被拦下，报 Disk quota exceeded
> sudo xfs_quota -x -c 'report -h' /mnt/quota
>                                      # 验证：项目 1001 的用量与硬上限
> ```
> **预期**：`dd` 在约 100MiB 处停下并报 **`Disk quota exceeded`**（这是 `EDQUOT`，不是 `ENOSPC`）——**这一屏就是「配额把整机故障降级为单租户故障」的实证**。
> **风险**：低。全部作用在 loop 文件上（需要 root）。
> **环境**：任意发行版，需要 `lvm2` 与 `xfsprogs`。**容器里做不了。**
> **耗时**：约 25 分钟。
> **怎么退回去**：`sudo umount /mnt/quota; sudo lvremove -f vgquota/lvquota; sudo vgremove vgquota; sudo pvremove "$LOOP7"; sudo losetup -d "$LOOP7"; rm -f /tmp/lab-quota.img`。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 在 XFS 上只 `enable` 而不在挂载时加 `prjquota` | 记账没打开，配额形同虚设；「配了不生效」的头号原因 |
| 把配额当成告警的替代 | 只是把「写满整盘」换成「写满配额」，业务照样挂；用量百分比必须进监控 |
| 只设硬限制、不留软限制与宽限期 | 业务峰值时被硬砍，可能造成比「写满」更严重的中断 |
| 用 `EDQUOT` 与 `ENOSPC` 混为一谈 | 两者处置不同：前者调额度或清理，后者查容量/inode/保留块 |
| 项目 ID 不写进台账 | 半年后没人知道 1001 对应哪个业务 |
| 把别的目录的数据 `mv` 进来就以为计入配额 | 跨文件系统搬移与已有文件的统计行为要实测确认（`project -s` 会把已有文件纳入统计） |
| 用用户配额管理共享目录 | 多人共用一个服务账号时用户配额没有意义；目录级边界应该用项目配额 |
| 只在容器里配配额而不看宿主 | 容器可写层仍写在宿主同一文件系统上；宿主侧目录级配额才是有效边界 |

## 决策练习

> [!question]- 场景：一台多租户数据盘（XFS）上有 20 个业务目录，其中一个租户的日志失控增长，把整盘写满了，导致其他 19 个租户全部写入失败。事后要求「不能再来一次」。给出最小可行的治理方案。
> A. 给每个租户的用户账号分别设用户配额
> B. 确认 XFS 以 `prjquota` 挂载 → 给 20 个业务目录各绑定一个项目 ID → 设软硬限制（如按当前用量上浮 30%）→ 用 `xfs_quota report` 把用量百分比接进监控 → 把「目录 ↔ 项目 ID ↔ 业务方」写进台账
> C. 让每个租户自己控制日志轮转，约定不超过配额
>
> **答案：B。**
> A 的问题是很多目录由同一个服务账号写入，用户配额起不到「目录级隔离」的作用。
> C 只是口头约定，没有强制力——**这次事故恰恰说明「靠自觉」不成立**。
> B 是正解：**技术边界（项目配额）+ 可观测（监控水位）+ 可追溯（台账）三件一起做**，才是完整的容量治理。这也是 M5 的交付物标准。

## 要点自测

> [!question]- 为什么共享目录必须有容量上限？
> - 单个租户写满盘会成为整机故障：同盘上的其他业务、甚至 `/var/log`、`/tmp` 都写不进去。
> - 配额把故障影响面限制在「一个租户」，同时保留可观测的边界。
> - **第一反应不要是什么**：不要用「我们会盯着」代替技术边界。

> [!question]- XFS 的配额为什么必须写进挂载选项？
> - **记账（accounting）只能在挂载时打开**（`prjquota`/`uquota`/`gquota`），运行时不支持补开。
> - 挂载后 `xfs_quota -x -c 'enable'` 只能开关**强制**，不能打开记账。
> - **第一反应不要是什么**：不要只看 `xfs_quota state` 显示 enforce 就以为配置生效，要确认 accounting 也是 on。

> [!question]- 项目配额和用户配额有什么不同？
> - 项目配额绑定的是**目录树**（项目 ID 沿目录继承），用户配额绑定的是 uid。
> - 共享目录、多租户目录、容器日志目录用项目配额；个人 Home 目录用用户配额。
> - **第一反应不要是什么**：不要在「多人共用一个服务账号」的场景下硬套用户配额。

> [!question]- 配额到顶报什么错误？和容量满怎么区分？
> - 报 `Disk quota exceeded`（`EDQUOT`）；容量或 inode 耗尽是 `No space left on device`（`ENOSPC`）。
> - 区分方式：看报错文本、查配额报表（`xfs_quota report`/`repquota`）、看 `df -h`/`df -i` 是否有余量。
> - **第一反应不要是什么**：不要看到「写不进去」就往容量方向查而不问一句「有没有配额」。
