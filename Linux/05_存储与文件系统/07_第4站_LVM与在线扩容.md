## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **三层结构**：PV（物理卷，被 LVM 接管的盘或分区）→ VG（卷组，容量池）→ LV（逻辑卷，切出来给文件系统用的「虚拟分区」）。
> - **扩容是一条链，少一步 `df` 都不会变**：加盘/扩云盘 → `pvresize`/`vgextend` → `lvextend` → 扩文件系统（`resize2fs`/`xfs_growfs`）。**`lvextend -r` 会替你做完最后一步。**
> - **一个参数差异记一辈子**：`resize2fs` 接**设备**，`xfs_growfs` 接**挂载点**；搞反了不是报错就是「改错了对象」。
> - **LVM 快照是 COW，会随原卷写入增长**：写满就失效，**它不是备份**（同盘快照救不了盘坏与误删覆盖整盘）。
> - **thin pool 允许超配，但写满会波及池内所有卷**（常见是变只读）；必须监控 `data_percent`/`metadata_percent`。

## 1. 三层结构与命令族

| 概念 | 是什么 | 常见命令 | 现场查看 |
| --- | --- | --- | --- |
| PV（物理卷） | 被 LVM 接管的盘或分区，头上有 LVM 元数据 | `pvcreate`、`pvresize`、`pvremove` | `pvs`、`pvdisplay` |
| VG（卷组） | 由若干 PV 组成的容量池 | `vgcreate`、`vgextend`、`vgreduce` | `vgs`、`vgdisplay` |
| LV（逻辑卷） | 从 VG 里切出来的「虚拟分区」，给文件系统用 | `lvcreate`、`lvextend`、`lvreduce`、`lvremove` | `lvs`、`lvdisplay` |

```bash
sudo pvs; sudo vgs; sudo lvs          # 验证：三层视图（含剩余容量 VFree 与 LV 大小）
sudo lvs -o+lv_size,data_percent,metadata_percent
                                      # 验证：thin pool 与快照的水位（超配场景必看）
sudo pvdisplay /dev/sdb1; sudo vgdisplay vg0
                                      # 验证：单层细节（PV 的 PE 大小、VG 的剩余空间）
sudo dmsetup ls --tree                # 验证：device-mapper 视角的映射关系
```

为什么要多这一层？因为它把「盘」和「给业务的空间」解耦了：

- **在线扩容量**：往 VG 里加盘（`vgextend`），或者把已有 PV 变大（`pvresize`），再扩 LV。
- **跨盘拼容量**：一块 2TiB + 一块 4TiB 可以组成 6TiB 的池，再切成任意大小的卷。
- **快照**：在改数据（升级、迁移、备份）之前做一份短命快照，出了问题能回滚。
- **代价**：多一层映射与元数据（`/etc/lvm/backup`、`/etc/lvm/archive`），排查时要多看一层；thin pool 还有「写满波及全组」的风险。

## 2. 在线扩容的完整链路

扩容有两种起点：**加一块新盘**，或者**云盘原地变大**。共同点是：**最后一定要扩文件系统**，否则 `df` 不会变。

```bash
lsblk                                # 验证：内核是否已经看到新的容量（云盘扩容后先看这里）
```

**起点 A：加入一块新盘**

```bash
sudo pvcreate /dev/sdb1              # 验证：把新分区交给 LVM（先完成子笔记 04 的三问与分区）
sudo vgextend vg0 /dev/sdb1          # 验证：vgs 的 VFree 增加（池子变大了）
sudo lvextend -r -L +50G /dev/vg0/lv_data
                                     # 验证：扩 LV 并由 -r 自动扩文件系统（一步到位）
sudo df -h /data; sudo lvs -o+lv_size
                                     # 验证：df 变大、LV 大小正确（这一步才算验收）
```

**起点 B：云盘原地扩容（同一块盘变大）**

```bash
sudo growpart /dev/sda 3             # 验证：先扩分区（cloud-utils-growpart 或 parted resize）
sudo partprobe /dev/sda              # 验证：让内核重读分区表
sudo pvresize /dev/sda3              # 验证：让 PV 感知新增空间（pvresize 是关键的一步）
sudo lvextend -r -l +100%FREE /dev/vg0/lv_data
                                     # 验证：把 VG 里剩余空间全部给这个 LV，并自动扩文件系统
sudo df -h /data                     # 验证：最终验收——文件系统变大
```

**手动分步（等价写法，用来理解 `-r` 做了什么）**：

```bash
sudo lvextend -L +50G /dev/vg0/lv_data     # 只扩 LV
sudo resize2fs /dev/vg0/lv_data            # ext4：参数是【设备】
sudo xfs_growfs /data                      # XFS：参数是【挂载点】，不是设备（最常见的记混点）
```

| 步骤 | 命令 | 验收标准 |
| --- | --- | --- |
| 1. 内核看到新容量 | `lsblk` | 设备 SIZE 变大 |
| 2. 分区变大（云盘场景） | `growpart` + `partprobe` | 分区 SIZE 变大 |
| 3. PV 变大 | `pvresize` | `pvs` 的 `PSize` 变大、`VFree` 增加 |
| 4. LV 变大 | `lvextend` | `lvs` 的 `LSize` 变大 |
| 5. 文件系统变大 | `resize2fs`/`xfs_growfs`（或 `-r`） | **`df -h` 变大** |
| 6. 业务可用 | 写入测试 | 能正常写入、无报错 |

> [!important] `df` 不变就没做完
> 「LV 已经扩了」不等于「业务可以用到更多空间」。**验收标准只有一个：`df -h <挂载点>` 的容量与可用空间确实变大，并且能正常写文件。** 这一步不做，几个月后就会以「我明明扩过容」的形式再次冒出来。

## 3. 缩容：为什么生产上通常不做

```bash
sudo umount /data                    # ext4 缩容必须先卸载（XFS 完全不支持缩容）
sudo e2fsck -f /dev/vg0/lv_data      # 验证：缩容前必须完整检查（否则 resize2fs 会拒绝）
sudo resize2fs /dev/vg0/lv_data 20G  # 验证：先把文件系统缩到 20G（顺序不能反！）
sudo lvreduce -L 20G /dev/vg0/lv_data
                                     # 验证：再把 LV 缩到 20G（顺序错了就是直接毁数据）
```

三条硬规则：

1. **顺序是「先缩文件系统，再缩 LV」**；扩容则反过来（先扩 LV，再扩文件系统）。顺序错了会切掉正在使用的区域。
2. **XFS 完全不支持缩容**，只能备份 → 重建 → 恢复。
3. **`lvreduce` 默认要求确认**，脚本里用 `-f` 前请三思——**它不会问第二遍**。

## 4. 快照：能做与不能做

```bash
sudo lvcreate -L 20G -s -n snapdata /dev/vg0/lv_data
                                     # 验证：给 LV 做一份 20GiB 的快照（-s 表示 snapshot）
sudo lvs -o+lv_size,data_percent vg0 # 验证：snapdata 的 data_percent 随原卷写入增长
sudo mkdir -p /mnt/snap && sudo mount -o ro /dev/vg0/snapdata /mnt/snap
                                     # 验证：快照通常只读挂载用来取数据
sudo lvremove -f /dev/vg0/snapdata   # 验证：用完立刻删除（否则它会一直涨）
```

| 事实 | 说明 |
| --- | --- |
| 原理是 **COW** | 快照不复制全部数据；原卷后续被写入时，旧块才被复制到快照空间 |
| **会增长** | 原卷写得多，快照空间消耗得快；用完（`data_percent` 到 100%）快照**直接失效** |
| 有性能代价 | 原卷写入时多一次复制（写放大、延迟上升） |
| 正确用法 | **备份窗口内做一份短命快照，备份完成即删除** |
| 不能当备份 | 同一块盘的快照救不了盘坏、误删覆盖整盘、勒索加密；这些场景要靠异地/离线备份 |

## 5. thin pool：省空间，但把风险集中了

thin provisioning 允许「超配」：LV 声明 1TiB，池子里其实只有 200GiB，靠业务不会同时写满来省空间。

```bash
sudo lvs -o+lv_size,data_percent,metadata_percent
                                      # 验证：池子与元数据水位（两个都要看，元数据满了同样致命）
sudo lvs -a -o+seg_monitor            # 验证：是否有 dmeventd 在监控（thin pool 的自动扩展机制）
```

- **池子写满会波及组内所有卷**：常见表现是整组卷变只读或写入失败——**属于整机级故障**。
- **元数据也会满**：`metadata_percent` 同样要监控；元数据写满比数据写满更麻烦。
- **必须配监控与告警**：`data_percent`、`metadata_percent` 都要有水位的告警，并且留出余量（比如 80% 就告警）。
- **不要为了省空间把超配比例拉满**：省下来的空间是「赌业务不会同时用满」，赌输的代价是全组故障。

## 6. 元数据备份：改结构前的标准动作

```bash
sudo vgcfgbackup -f /root/vg0-$(date +%F-%H%M).bak vg0
                                     # 验证：把 VG 元数据导出留档（改结构前必做）
sudo vgcfgrestore -f /root/vg0-2026-09-18-1030.bak vg0
                                     # 验证：元数据恢复（仅在需要时，且要先确认版本与现状）
ls /etc/lvm/archive/ | tail          # 验证：LVM 自己也会在每次结构变更前存档
```

LVM 的元数据（PV/VG/LV 的结构定义）与数据在同一个盘上，**结构改错时数据还在，但 LVM 已经不认它了**。`vgcfgbackup` 与 `/etc/lvm/archive/` 是这种情况下唯一的救命绳——**改结构之前先备份，成本是一条命令**。

## 7. 生产动作：一份扩容作业记录

扩容类变更的验收标准是「业务真的能用」而不是「命令执行成功」。记录里应有：

1. **起点**：扩容前的 `lsblk`、`pvs`/`vgs`/`lvs`、`df -h` 输出。
2. **动作**：每一步命令（含 `pvresize`/`vgextend`/`lvextend -r`）。
3. **终点**：`lsblk`、`lvs`、**`df -h`** 与一次写入测试。
4. **回滚**：LVM 扩容无法「回滚」（容量已经给出去），但要说清一旦出问题（如文件系统扩容报错）的处置路径：扩文件系统失败时文件系统仍可用，只是没变大，可重试或排查。
5. **监控**：新容量对应的水位告警阈值是否需要调整。

> [!example]- 实验 4：LVM 全链路（建池 → XFS → 在线扩容 → 快照)
> **怎么做**：在 loop 设备上建 PV/VG/LV，做 XFS，然后给 VG 加空间并在线扩容，最后做一份快照观察它「会涨」。
> ```bash
> dd if=/dev/zero of=/tmp/lab-lvm.img bs=1M count=2048
> LOOP4=$(losetup --find --show /tmp/lab-lvm.img)
> sudo pvcreate "$LOOP4" && sudo vgcreate vglab "$LOOP4"
> sudo lvcreate -L 1G -n lvdata vglab
>                                      # 验证：从 2GiB 的池里切出 1GiB 的卷（vgs 的 VFree 还剩约 1GiB）
> sudo mkfs.xfs -f /dev/vglab/lvdata
> sudo mkdir -p /mnt/lvmdata && sudo mount /dev/vglab/lvdata /mnt/lvmdata
> df -hT /mnt/lvmdata                  # 验证：初始 1GiB（XFS 与 LV 大小基本一致）
> sudo lvextend -r -l +100%FREE /dev/vglab/lvdata
>                                      # 验证：把 VG 剩余空间全给这个 LV，并用 -r 自动 xfs_growfs
> df -hT /mnt/lvmdata                  # 验证：在线长大（全程未卸载）
> sudo lvs -o+lv_size vglab            # 验证：LV 的新大小
> sudo lvcreate -L 200M -s -n snapdata /dev/vglab/lvdata
>                                      # 验证：做一份 200MiB 的快照
> dd if=/dev/zero of=/mnt/lvmdata/fill bs=1M count=100
> sudo lvs -o+lv_size,data_percent vglab
>                                      # 验证：snapdata 的 data_percent 随原卷写入上升（这就是"快照会涨"）
> ```
> **预期**：`df` 在**不卸载**的情况下从 1GiB 长到接近 2GiB；快照的 `data_percent` 随写入增长——**这正是「快照会涨、会写满、不能当长期备份」的实物证据**。
> **风险**：低到中。全部动作在 loop 文件上，但会创建 VG/LV 并挂载，需要 root；**只在实验机做**。
> **环境**：任意发行版，需要 `lvm2` 与 `xfsprogs`。**容器里做不了（没有 loop 与 device-mapper 权限）。**
> **耗时**：约 25 分钟。
> **怎么退回去**：`sudo umount /mnt/lvmdata; sudo lvremove -f vglab/snapdata vglab/lvdata; sudo vgremove vglab; sudo pvremove "$LOOP4"; sudo losetup -d "$LOOP4"; rm -f /tmp/lab-lvm.img`。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 扩了 LV 就以为业务空间变多了 | 还要扩文件系统；验收标准是 `df` 变大，不是 `lvs` 变大 |
| 把 `xfs_growfs` 的参数写成设备 | XFS 认挂载点；写设备会报错（`-r` 也会替你调对） |
| 云盘扩容后只做 `lvextend` | 少了 `growpart` 与 `pvresize`，VG 根本没变大，`lvextend` 会因空间不足失败 |
| 缩容时先 `lvreduce` 再缩文件系统 | 顺序反了会切掉正在使用的区域，直接毁数据 |
| 认为 LVM 快照可以长期保留 | 快照随原卷写入增长，写满即失效，而且不是备份 |
| 在快照上做业务读写 | 快照通常只读挂载用于取数据；在上面写会消耗快照空间并造成混乱 |
| thin pool 不监控水位 | 池子写满会影响组内**所有**卷（常见是变只读），属于整机级故障 |
| 改 LVM 结构前不备份元数据 | 结构损坏时数据还在但 LVM 认不出来；`vgcfgbackup` 是唯一的救命绳 |
| 把 LVM 用在需要缩容的场景 | LVM 的强项是「长大」，缩容既有顺序风险又常常不支持（XFS） |

## 决策练习

> [!question]- 场景：云上的一台数据库服务器，数据盘挂在 LVM 上、文件系统是 XFS。云控制台把云盘从 500GiB 扩到了 1TiB，你在机器上跑 `df -h /data` 发现没有任何变化。接下来怎么做？
> A. 直接 `xfs_growfs /data`，让文件系统长大
> B. 按链路上行：`lsblk` 确认内核看到新容量 → `growpart` 扩分区 + `partprobe` → `pvresize` 扩 PV → `lvextend -r -l +100%FREE /dev/vg0/lv_data` → 用 `df -h /data` 与写入测试验收
> C. `lvextend -L +500G /dev/vg0/lv_data`，然后重启让内核识别
>
> **答案：B。**
> A 会失败或没有效果：文件系统只能涨到 LV 那么大，而 LV 还没变大。
> C 少了 `pvresize`：云盘变大了，但 PV 的 `PSize` 还是旧的，VG 没有新空间，`lvextend` 会报空间不足；重启也不会让它自动变大。
> B 是正解：**扩容是一条从硬件一直到文件系统的链，每一层都要单独长大**；`-r` 负责把最后两步（扩 LV + 扩文件系统）串起来。

## 要点自测

> [!question]- PV、VG、LV 分别是什么？容量是怎么传递的？
> - PV 是被 LVM 接管的盘/分区，VG 是由 PV 组成的容量池，LV 是从池里切出来给文件系统用的卷。
> - 容量传递方向：盘变大 → PV 变大（`pvresize`）→ VG 变大 → LV 变大（`lvextend`）→ 文件系统变大（`resize2fs`/`xfs_growfs`）。
> - **第一反应不要是什么**：不要跳过中间层直接去扩文件系统。

> [!question]- `lvextend -r` 里的 `-r` 做了什么？
> - 它在扩完 LV 之后**自动调用文件系统扩容工具**：ext4 走 `resize2fs <设备>`，XFS 走 `xfs_growfs <挂载点>`。
> - 前提是文件系统**已挂载**（XFS 必须挂载才能扩）；未挂载时 `-r` 无法扩 XFS。
> - **第一反应不要是什么**：不要以为 `-r` 能处理所有场景——分区与 PV 的扩容仍要自己做。

> [!question]- 为什么 LVM 快照不能当备份？
> - 它依赖原卷：原卷写得多，快照空间涨得快，写满即失效；同盘快照会跟着盘一起丢。
> - 它防不了误删覆盖整盘、勒索加密、盘坏、机房级故障这些场景。
> - **第一反应不要是什么**：不要把「有快照」当成「有备份」，也不要让快照长期存在。

> [!question]- thin pool 有什么特别的风险？
> - 允许超配（LV 声明空间大于池子实际容量），池子写满会影响组内**所有**卷，常见表现是变只读。
> - 元数据水位（`metadata_percent`）同样要监控，不止数据水位。
> - **第一反应不要是什么**：不要把超配当成免费的空间——它是用「不会同时写满」的假设换来的。
