## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **NFS 默认是 `hard`**：服务端不可达时，访问进程会**一直重试并卡在 `D` 状态**，`kill -9` 无效——要恢复的是通路，不是杀掉进程。
> - **改成 `soft` 不是解决方案**：它把「卡死」换成「超时返回错误」，可能产生**静默的数据不一致**，一般只用于只读或可重试场景。
> - **网络存储挂载必须 `_netdev` + `nofail`**：前者保证网络就绪后再挂，后者保证对端不可达时本机还能正常开机。
> - **D 状态堆积的处置顺序**：确认是哪个挂载点 → 查底层链路（网络、服务端、多路径）→ **优先恢复通路**，恢复后 D 状态自行消解 → 无法恢复时才谈 `umount -f`，最后手段是重启。
> - **`automount` 按需挂载是可选盘的常规做法**：代价是首次访问有延迟，网络不通时业务仍会卡，所以要配超时与告警。

## 1. NFS 的关键选项与取舍

```bash
mount | grep nfs                     # 验证：NFS 挂载点与实际生效参数（hard/soft、timeo、retrans）
nfsstat -m /mnt/nfs                  # 验证：每个 NFS 挂载点的版本、传输协议与参数
nfsstat -rc                          # 验证：NFS 客户端重传与错误计数（网络抖动会体现在这里）
showmount -e <server>                # 验证：服务端导出了哪些目录（排障时先确认对端配置）
```

| 选项 | 语义 | 风险与取舍 |
| --- | --- | --- |
| `hard`（默认） | 服务端不可达时**无限重试** | 进程卡 `D` 状态，`kill -9` 无效；好处是**不会产生部分写入的不一致** |
| `soft` | 超时后返回错误给应用 | 换来「不卡死」，代价是**可能产生数据不一致**，一般只用于只读或可重试场景 |
| `timeo=`（十分之一秒） | 重传超时 | 调小会让重试更频繁，调大则单次等待更久 |
| `retrans=` | 重传次数 | 与 `timeo` 一起决定「多久之后给应用报错」（`soft` 场景） |
| `_netdev` | 标记为网络文件系统 | 不加会导致启动时顺序错误、卡 90 秒甚至挂载失败 |
| `nofail` | 挂不上也不阻塞启动 | 远程存储必加，否则对端不可达时本机可能起不来 |
| `x-systemd.automount` | 首次访问才挂载 | 适合冷数据/可选盘；首次访问有延迟，要配超时与监控 |
| `nconnect=` | 单挂载点使用多条 TCP 连接 | 高吞吐场景可提升并行度；需对端与内核支持 |

## 2. 挂载点卡死、进程堆积在 D 状态

**现象**：`df -h`、`mount` 命令本身也会卡住；`ps` 里大量进程处于 `D` 状态，集中在访问同一个路径；`kill` 与 `kill -9` 都无效。

**为什么杀不掉**：`D` 状态是「不可中断睡眠」，进程正在等内核里的 IO 完成，**信号要等它回到用户态才会被处理**。所以杀进程不是手段，恢复 IO 通路才是。

处置顺序（**先恢复，后取舍**）：

1. **确认是哪个挂载点**：`df -h` 卡住的位置、`/proc/mounts` 里可疑的 NFS/iSCSI 挂载、大量 `D` 进程的共同路径。
2. **确认底层**：`journalctl -k` 里的 NFS/iSCSI/multipath 报错、网络可达性（`ping`/`nc` 到服务端与端口）、`multipath -ll` 的路径状态、服务端自身是否存活。
3. **优先恢复链路**：修网络、恢复服务端、切多路径。**通路恢复后，D 状态会自行消解**，业务也随之恢复。
4. **无法恢复时的取舍**：`umount -f`（强卸）或 `umount -l`（lazy）**都有数据一致性风险**，需要业务方确认；最后手段才是重启，并在重启前尽量保留日志与现场。
5. **长期改进**：`hard` + 合理 `timeo`/`retrans`、`_netdev`/`nofail`、可选盘用 `automount`、把「存储不可达」纳入演练、监控重传与延迟。

```bash
cat /proc/mounts | grep -E 'nfs|cifs|iscsi'   # 验证：有哪些网络挂载
ps -eo pid,stat,wchan:24,comm --sort=-stat | grep -E '^ *[0-9]+ D' | head
                                     # 验证：当前处于 D 状态的进程及其内核等待点
sudo journalctl -k | grep -i -E 'nfs|iscsi|multipath|link is down' | tail -20
                                     # 验证：内核侧的网络存储报错（根因线索）
sudo multipath -ll                   # 验证：多路径设备及每条路径的状态
sudo iscsiadm -m session -P 3        # 验证：iSCSI 会话与设备映射详情
```

> [!tip] 第一反应不要是「批量 `kill -9`」
> 卡在不可中断等待上的进程**收不到信号**，杀不掉也不该杀。要做的是：**先确认是哪个挂载点卡住、底层为什么不通，再恢复通路**。杀掉进程既无效，也会破坏现场。

## 3. iSCSI、FC 与多路径

| 方案 | 关键点 | 风险与处置 |
| --- | --- | --- |
| iSCSI | `iscsiadm` 发现与登录、`/etc/iscsi/` 配置、CHAP 认证 | 配合 dm-multipath 做路径冗余；单路径故障时 IO 会停顿，配置不当还会出现 `queue_if_no_path` 导致 IO 永久挂起 |
| FC / 企业存储 | 由 HBA 与 `multipath` 管理 | `multipath -ll` 看路径状态；**路径切换瞬间的 IO 停顿要纳入业务超时设计** |
| 多路径（dm-multipath） | 同一 LUN 的多条路径聚合成一个设备 | 路径切换（failover）会造成秒级停顿；`path_selector`/`path_grouping_policy` 决定选路策略 |

```bash
sudo multipath -ll                   # 验证：聚合设备、每条路径状态（active/ghost/failed）与优先级
cat /etc/multipath.conf | grep -v '^#' | head -30
                                     # 验证：多路径策略配置（是否启用、哪些设备被聚合）
lsblk -o NAME,SIZE,TYPE,MOUNTPOINT,VENDOR,MODEL
                                     # 验证：多路径设备在多层的呈现（mpathX 与其上的 LVM）
```

三个容易忽略的点：

1. **路径切换会造成 IO 停顿**：业务侧的超时时间要大于切换耗时，否则会出现「存储正常但业务报超时」。
2. **`queue_if_no_path`**：配置不当会让 IO 在所有路径都不可用时**永久排队**，表现为进程卡 `D`——它与 `hard` 挂载是同一类问题。
3. **多路径设备上的 LVM**：扩容与换盘时链路更长（多路径 → PV → LV → FS），每一步都要验收（子笔记 07）。

## 4. 生产动作：网络存储挂载的检查清单

1. **挂载选项**：`_netdev`、`nofail`、`x-systemd.device-timeout=`，可选盘再加 `x-systemd.automount`。
2. **一致性取舍**：写场景坚持默认 `hard`（宁可卡住，不要静默不一致）；只读/可重试场景才考虑 `soft` 并配 `timeo`/`retrans`。
3. **验收**：`findmnt -o TARGET,SOURCE,FSTYPE,OPTIONS` 确认选项生效；`nfsstat -m` 确认版本与参数。
4. **监控**：`nfsstat -rc` 的重传计数、挂载点响应时间、`D` 状态进程数；多路径还要监控路径状态。
5. **演练**：在实验环境模拟「服务端不可达」，验证挂载不会让机器起不来、业务能按预案降级。

> [!example]- 演练：在实验机模拟一次「网络存储不可达」（不碰生产）
> **怎么做**：在两台实验机之间建一个 NFS 共享（或在一个实验机上用 `nfsd` 导出本地目录），按 `_netdev,nofail` 挂载，然后断开对端，观察现象与恢复路径。
> ```bash
> sudo mkdir -p /srv/share && sudo chmod 777 /srv/share
> echo '/srv/share *(rw,sync,no_subtree_check)' | sudo tee /etc/exports
> sudo exportfs -ra && sudo systemctl start nfs-server
>                                      # 验证：上面三行在服务端（实验机 A）执行，导出共享目录
> sudo mount -t nfs -o _netdev,hard,timeo=100,retrans=2 A:/srv/share /mnt/share
>                                      # 验证：这一行在客户端（实验机 B）执行，按网络存储参数挂载
> nfsstat -m /mnt/share                # 验证：挂载参数与协议版本
> sudo systemctl stop nfs-server       # 在 A 上停服务，模拟对端不可达
> ```
> **预期**：客户端上访问 `/mnt/share` 的进程会**卡在 `D` 状态**（`df`/`ls` 也卡）；在 A 上恢复 `nfs-server` 后，客户端访问立即恢复，`D` 状态自行消解。
> **风险**：中。涉及两台机器的服务启停；**只在实验环境做**，不要在生产的 NFS 服务端上演练。
> **环境**：两台可快照的实验机（或同机不同容器/网络命名空间，但机制演示不完整）。
> **耗时**：约 30 分钟。
> **怎么退回去**：恢复服务端服务，`sudo umount /mnt/share`，清理 `/etc/exports` 与共享目录。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 为了「不卡死」把关键挂载改成 `soft` | 会把卡顿换成静默的数据不一致；一般只用于只读或可重试场景 |
| NFS 挂载不加 `_netdev`/`nofail` | 对端不可达时启动卡 90 秒甚至进 emergency，把「挂载失败」升级成「整机起不来」 |
| D 状态进程用 `kill -9` 处理 | 不可中断睡眠收不到信号；要恢复的是 IO 通路 |
| 一卡死就 `umount -f` | 强卸有数据一致性风险；要先尝试恢复通路，并让业务方确认取舍 |
| 认为「网络通就没问题」 | NFS 还依赖服务端进程、导出的权限、`rpc` 端口、防火墙与多路径状态 |
| 忽略路径切换的停顿 | 单条路径故障切换时有秒级停顿，业务超时设置不当会误判为故障 |
| 在生产的 NFS 服务端上做「拔线演练」 | 会真的造成所有客户端卡死；演练要在实验环境做 |
| 忘了监控重传计数 | `nfsstat -rc` 的重传与错误上升是「链路已经开始不稳」的早期信号 |

## 决策练习

> [!question]- 场景：一台应用服务器上 `/mnt/share` 是 NFS 挂载，凌晨服务端机房网络抖动，早上值班发现 200 多个进程处于 `D` 状态，`kill -9` 无效，业务已经不可用。怎么处置？
> A. 立刻 `umount -f /mnt/share`，先把挂载点摘掉让业务恢复
> B. 先确认卡住的是这个挂载点，查 `journalctl -k` 与网络可达性，联系机房确认服务端状态；**优先恢复网络/服务端**，恢复后 D 状态会自行消解；如果确定短时间无法恢复，再评估 `umount -f`/`-l` 的数据风险并与业务方确认取舍
> C. 重启应用服务器，让进程全部清掉
>
> **答案：B。**
> A 的风险是数据一致性：强卸时进程可能还在写，卸载后写入会失败或丢失；而且如果服务端马上恢复，本不需要承担这个风险。
> C 是最后手段：重启会清掉现场（内核日志、`D` 进程的 `wchan`），而且**如果存储仍未恢复，重启后机器可能卡在启动过程中**。
> B 是正解：**先恢复通路（成本最低、无损），再考虑取舍**。这条顺序同样适用于多路径与 iSCSI 场景。

## 要点自测

> [!question]- NFS 的 `hard` 与 `soft` 怎么选？
> - 写场景优先 `hard`：宁可等待，也不要静默的部分写入/不一致。
> - `soft` 适合只读挂载或应用本身能安全重试的场景，并要配 `timeo`/`retrans` 控制多久报错。
> - **第一反应不要是什么**：不要为了「界面不卡」把关键业务挂载改成 `soft`。

> [!question]- 挂载点卡死、进程堆 `D`，处置顺序是什么？
> - 确认是哪个挂载点 → 查底层（内核日志、网络可达、服务端、多路径）→ **优先恢复通路** → 无法恢复时评估 `umount -f`/`-l` → 最后才是重启。
> - 全程不做的事情：批量 `kill -9`。
> - **第一反应不要是什么**：不要用杀进程或重启来「清场」。

> [!question]- 网络存储挂载为什么必须同时加 `_netdev` 和 `nofail`？
> - `_netdev` 保证网络就绪后再挂载，避免启动时顺序错误导致的超时失败。
> - `nofail` 保证挂载失败不阻塞启动——对端不可达时本机仍能起来。
> - **第一反应不要是什么**：不要以为 NFS 挂载失败只影响业务，它可能让整台机器起不来。

> [!question]- 多路径的路径切换对业务有什么影响？
> - 切换瞬间有秒级 IO 停顿，业务的超时设置要大于这个窗口。
> - 所有路径都不可用时，`queue_if_no_path` 之类配置会让 IO 长时间排队，表现为进程卡 `D`。
> - **第一反应不要是什么**：不要只看「存储设备还在」就认为 IO 通路没问题——要 `multipath -ll` 看每条路径状态。
