## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **选型只看两个问题：会不会缩容、文件多不多。** 会缩容（且能停机）才选 ext4；文件海量、容量很大、只扩不缩，选 XFS。
> - **`mkfs` 会立刻清空设备上的元数据**：敲下去就没有「再想想」。前面必须做完三问（子笔记 04），并且确认数据已有备份。
> - **定了就改不了的参数**：块大小、inode 密度（ext4 的 `-i`）、XFS 的 AG 数。**改这些 = 重建文件系统**。
> - **XFS 要用 `-f` 才肯覆盖已有文件系统**，这是它的保护设计；ext4 的 `mkfs.ext4` 默认也要求确认，脚本里要注意 `-F`。
> - **建完立刻做四件事**：打 LABEL、记 UUID 与结构参数、**先挂一次试试**、把结果写进基线卡。跳过这一步，「有空间却写不进去」类问题以后要靠猜。

## 1. 选型：ext4 还是 XFS

| 维度 | ext4 | XFS |
| --- | --- | --- |
| inode | 建文件系统时**按固定数量分配**（`df -i` 能看到总量），可能耗尽 | **动态分配**，几乎没有「inode 耗尽」问题 |
| 缩容 | **支持，但必须卸载且风险高** | **完全不支持**（只能备份 → 重建 → 恢复） |
| 扩容 | 支持在线扩容（`resize2fs`，参数是**设备**） | 支持在线扩容（`xfs_growfs`，参数是**挂载点**），可扩到很大 |
| 空间预留 | 默认**为 root 保留 5%**（`mke2fs -m` 可改，`tune2fs -m` 可后调） | 无 5% 预留概念；`df` 与 `du` 的差异另有原因（子笔记 09） |
| 修复工具 | `e2fsck` | `xfs_repair`（**默认不能对已挂载设备运行**） |
| 大文件/并发 | 通用够用；超大目录与极高并发不如 XFS | 大容量、大文件、高并发写入是强项 |
| 典型用途 | 系统盘、通用小盘、需要缩容的场景 | 数据盘、日志盘、容器存储后端、海量 inode 场景 |
| 常用查询 | `tune2fs -l`、`dumpe2fs -h` | `xfs_info`、`xfs_db` |

**生产上最常见的是「XFS + LVM」**：LVM 负责供容量，XFS 负责在线长大，**整条链路没有一步需要缩容**，正好绕开两者的短板。反过来，如果业务真的需要缩容（例如云盘可以调小、或者要挪一部分空间给别的卷），只有 **ext4 + LVM** 能做到，而且必须停机卸载。

一句话决策：

1. **这台机器要不要缩容？** 要 → ext4（并接受停机）；不要 → 继续。
2. **会不会有海量小文件（几十万以上）？** 会 → XFS（避开 inode 耗尽）；不会 → 两者都行，按团队习惯。
3. **容量会不会长到很大（几十 TiB）？** 会 → XFS + LVM，扩容路径最顺。

## 2. `mkfs`：哪些参数定了就改不了

```bash
sudo mkfs.ext4 -L data-disk-a /dev/<dev>1
                                     # 验证：按默认参数建 ext4（块大小与 inode 密度由 mke2fs 按设备大小推断）
sudo mkfs.ext4 -m 1 -i 16384 -L data-disk-a /dev/<dev>1
                                     # 验证：预留 1%、每 16KiB 给一个 inode（小文件密集场景的取舍）
sudo mkfs.xfs -f -L data-disk-a /dev/<dev>1
                                     # 验证：建 XFS（-f 强制覆盖已有文件系统，脚本里必需，**有数据时禁用**）
sudo mkfs.xfs -f -d agcount=8 -L data-disk-a /dev/<dev>1
                                     # 验证：手工指定 AG 数（默认由设备大小推断，一般不需要改）
```

| 参数 | 作用 | 什么时候动它 |
| --- | --- | --- |
| ext4 `-b` | 块大小（默认 4096） | 极少动；要动必须与业务 IO 大小、页大小一起评估 |
| ext4 `-i` | 每个 inode 摊到多少字节（越小 inode 越多） | **海量小文件**盘；代价是 inode 表占更多空间 |
| ext4 `-m` | 预留百分比（默认 5） | 数据盘可以降到 1；**系统盘不要动** |
| ext4 `-O` | 启用的特性（如 `has_journal`、`^has_journal`） | 特殊场景；关特性前要确认工具链兼容性 |
| ext4 `-E stride=`/`stripe_width=` | 条带对齐（RAID 上） | 有硬件 RAID 且条带已知时 |
| XFS `-d agcount=` | 分配组数量 | 一般不动；XFS 会按容量推断 |
| XFS `-i maxpct=`/`imaxpct=` | inode 占用空间上限 | 需要限制 inode 总量的特殊场景 |
| XFS `-m reflink=`、`bigtime=` | 写时复制、超过 2038 年的时间戳 | 需要对应特性时；**建完就不能改**，注意与旧内核/旧工具的兼容 |
| XFS `-l` | 日志大小或外部日志设备 | 高写入场景调大日志、或用 SSD 做外部日志 |

> [!warning] 第一反应不要是「对已有数据的设备直接 `mkfs`」
> `mkfs` 不是「格式化一下更干净」，而是**在新盘上建立一套全新的空账本**——旧 inode 与目录结构会被覆盖，恢复代价极高。敲之前请确认三件事：**这块盘确实没数据、数据已有别的副本、设备名没认错**（子笔记 04 的三问）。

## 3. 建完立刻做的四件事

```bash
sudo blkid /dev/<dev>1                # 验证：拿到 UUID/TYPE/LABEL（写 fstab 与台账的唯一依据）
sudo tune2fs -l /dev/<dev>1 | grep -E 'Block count|Inode count|Block size|Filesystem features'
                                      # 验证：ext4 的结构参数（块大小、inode 总量、特性）
sudo xfs_info /dev/<dev>1             # 验证：XFS 的 AG 数、块大小、日志段、reflink 等特性
sudo mkdir -p /mnt/probe && sudo mount /dev/<dev>1 /mnt/probe && df -hT /mnt/probe
                                      # 验证：先手动挂一次，确认能挂、容量对得上，再写进 fstab
sudo umount /mnt/probe && sudo rmdir /mnt/probe
                                      # 验证：卸载并清理临时挂载点（正式挂载点按业务命名）
```

四件事的验收标准：

1. **有 LABEL**：`lsblk -o NAME,LABEL` 能看到易读的名字（比 UUID 好认，且 LABEL 也可以用于挂载）。
2. **UUID 与结构参数进台账**：块大小、inode 数量、AG 数、预留比例——半年后回头看 `df -i` 时要用。
3. **手动挂载成功过**：`mkfs` 成功不等于能挂（对齐、损坏、工具版本都可能出问题），**不要拿 fstab 当第一次尝试**。
4. **文件系统的「干净状态」已确认**：`tune2fs -l` 的 `Filesystem state` 应为 `clean`；XFS 挂载后 `dmesg` 不应有报错。

## 4. 「除了 ext4/XFS 还有什么」——一句话版本

| 文件系统 | 一句话 | 生产上什么时候会遇到 |
| --- | --- | --- |
| XFS / ext4 | 本章主角，块设备的通用选择 | 系统盘、数据盘 |
| btrfs | 自带快照、子卷、校验与在线压缩 | 发行版默认（部分 SUSE/openSUSE）、需要子卷快照的场景 |
| ZFS（OpenZFS） | 校验、快照、重删、池化，功能强但内存开销与生态约束多 | 存储服务器、自建 NAS |
| tmpfs | 挂在**内存**里的文件系统，重启即失 | `/tmp`、`/dev/shm`、容器临时目录（见阶段 4） |
| overlayfs | 把多个目录层叠成一个可写视图 | 容器镜像与可写层 |
| vfat/exfat | U 盘与跨平台交换格式，无权限模型、易损坏 | U 盘、EFI 分区（`/boot/efi`） |
| NFS/CIFS | 网络文件系统，不是本机文件系统 | 共享存储（子笔记 14） |

排查时的一个常见误会：**看到 `df` 里有个容量很大的 `tmpfs` 或 `overlay` 条目，就以为它有对应大小的磁盘**。它们不是块设备上的文件系统，`tmpfs` 吃的是内存（阶段 4），`overlay` 由容器运行时管理。

## 5. 生产动作：新数据盘初始化的完整链路

1. **三问**（子笔记 04）：是不是这块盘、有没有数据、有没有人在用 → **验收**：序列号一致、`wipefs -n` 输出已确认。
2. **建分区表与分区**（子笔记 04）→ **验收**：`lsblk` 能看到分区。
3. **选型并 `mkfs`**：按第 1 节的决策树选 ext4/XFS，必要时调 `-m`/`-i` → **验收**：命令无报错，`blkid` 有 UUID。
4. **打 LABEL + 记录结构参数** → **验收**：台账里有 UUID、LABEL、块大小、inode/AG 信息。
5. **手动挂载验证** → **验收**：`df -hT` 显示容量正确、能正常读写一个测试文件。
6. **写 fstab 并验收**（子笔记 06）→ **验收**：`mount -a` 与 `findmnt --verify` 均通过。
7. **纳入监控**：容量水位 + **inode 水位** + 健康（子笔记 08）→ **验收**：告警项已创建并触发过一次测试告警。

> [!tip] 规划阶段就要定下的一件事：别让所有东西共用一个文件系统
> 条件允许时，**系统盘、数据盘、日志盘分区分盘**，并让 `/var/log`、容器数据目录这类「会自己长大」的目录有独立挂载点。否则日志写满根分区会直接变成整机故障——`/var/log` 与业务数据同盘时，「业务写满」和「系统写不进去」之间没有缓冲。
> 判断方法只有一条：`findmnt -T <目录>`。**你以为它在一块独立的盘上，和它真的在，是两件事**（子笔记 09）。

> [!example]- 实验 2：同一块盘上分别建 ext4 与 XFS，对比「结构视角」
> **怎么做**：用两个 loop 文件，分别建 ext4 与 XFS，把 `df -i`、`tune2fs -l`、`xfs_info` 的差异摆在一起看。
> ```bash
> dd if=/dev/zero of=/tmp/lab-ext4.img bs=1M count=1024
> LOOP_EXT4=$(losetup --find --show /tmp/lab-ext4.img)
> sudo mkfs.ext4 -L labext4 "$LOOP_EXT4"
>                                      # 验证：默认参数建 ext4（注意输出的 inode 数与块大小）
> sudo mkdir -p /mnt/labext4 && sudo mount "$LOOP_EXT4" /mnt/labext4
> df -hT /mnt/labext4; df -i /mnt/labext4
>                                      # 验证：容量与 inode 的"总量"在建文件系统时就已经确定
> sudo tune2fs -l "$LOOP_EXT4" | grep -E 'Block count|Reserved block count|Inode count|Block size'
>                                      # 验证：总块数、预留块数（5%）、inode 总数、块大小
> dd if=/dev/zero of=/tmp/lab-xfs.img bs=1M count=1024
> LOOP_XFS=$(losetup --find --show /tmp/lab-xfs.img)
> sudo mkfs.xfs -f -L labxfs "$LOOP_XFS"
>                                      # 验证：建 XFS（-f 才会覆盖已有文件系统）
> sudo mkdir -p /mnt/labxfs && sudo mount "$LOOP_XFS" /mnt/labxfs
> df -hT /mnt/labxfs; df -i /mnt/labxfs
>                                      # 验证：XFS 的 inode 总量是动态的（随使用增长）
> sudo xfs_info /mnt/labxfs            # 验证：AG 数、块大小、日志段与特性
> ```
> **预期**：ext4 的 `df -i` 一开始就显示固定的 inode 总量；XFS 的 `df -i` 总量随创建文件增长。ext4 的 `Reserved block count` 约为 `Block count` 的 5%。**这一屏就是「选型决策」的实物证据。**
> **风险**：低。全部作用在 `/tmp` 的普通文件上（需要 root）。
> **环境**：任意发行版；需要 `e2fsprogs` 与 `xfsprogs`。**容器里做不了。**
> **耗时**：约 20 分钟。
> **怎么退回去**：`sudo umount /mnt/labext4 /mnt/labxfs; sudo losetup -d "$LOOP_EXT4" "$LOOP_XFS"; rm -f /tmp/lab-ext4.img /tmp/lab-xfs.img`。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 在 XFS 上规划缩容 | XFS 不支持缩容，只能备份 → 重建 → 恢复；规划阶段就要确认「只扩不缩」 |
| 对已有数据的设备跑 `mkfs` | 元数据被新账本覆盖，恢复代价极高；动手前必须完成三问 |
| 系统盘用 `-m 0` 去掉预留块 | 磁盘写满时 root 与系统守护进程没有自救空间，故障会放大 |
| 认为「容量大就多用 inode」 | inode 数量与容量没有固定关系：ext4 上默认按比例推算，海量小文件场景可能不够 |
| `mkfs` 成功后直接写 fstab 重启 | 少了「手动挂载验证」这一步；挂不上就直接变成开机故障 |
| 只看 `df -hT` 确认文件系统类型 | 类型、UUID、LABEL、结构参数都要记录；`blkid` 才是取 UUID 的工具 |
| 把 `tmpfs`/`overlay` 当成磁盘文件系统 | 它们不在块设备上：`tmpfs` 吃内存，`overlay` 由容器运行时管理 |
| 忘记 `xfs_growfs` 的参数是挂载点 | `xfs_growfs /dev/vg/lv` 会报错；XFS 认**挂载点**，ext4 的 `resize2fs` 认**设备** |

## 决策练习

> [!question]- 场景：业务要在新数据盘上放一个「每天产生几十万个小文件、需要保留 90 天、容量增长到 20TiB」的日志归档目录，且明确说「容量只会增长，不会缩小」。文件系统怎么选，怎么规划扩容？
> A. ext4：通用、稳定，先按默认建，将来 inode 不够再说
> B. XFS + LVM：XFS 动态 inode、适合海量小文件与大容量，LVM 提供在线扩容；建完后把 `df -i` 与 `df -h` 一起纳入监控
> C. btrfs：自带快照与压缩，还能每 90 天做一次快照
>
> **答案：B。**
> A 的风险是**inode 耗尽**：几十万小文件 × 90 天很容易把固定数量的 inode 用完，而 ext4 扩容不会任意增加 inode；真出问题时只能重建。
> C 虽然功能强，但改动方向超出需求（业务要的是容量与在线扩容），还会引入快照与子卷的运维复杂度，属于「用大炮打蚊子」。
> B 正好对上三件事：**只扩不缩**（XFS 短板不暴露）、**海量小文件**（动态 inode）、**容量会到 20TiB**（在线扩容链路成熟）。剩下要补的是监控与告警。

## 要点自测

> [!question]- ext4 和 XFS 该怎么选？
> - 看三个问题：**会不会缩容**（要缩只能 ext4，且停机）、**文件多不多**（海量小文件用 XFS）、**容量会不会很大**（XFS + LVM 扩容链最顺）。
> - 生产最常见组合是「XFS + LVM」：整条扩容链路不需要缩容。
> - **第一反应不要是什么**：不要因为「ext4 更熟悉」就忽略 inode 与缩容这两个硬约束。

> [!question]- `mkfs` 时哪些参数定了就改不了？
> - 块大小（ext4 `-b`、XFS 块大小）、ext4 的 inode 密度（`-i`）、XFS 的 AG 数量与部分特性（如 `reflink`）。
> - 想改这些，等于**重建文件系统**（备份 → 重建 → 恢复）。
> - **第一反应不要是什么**：不要把「改块大小」当成在线调参——它没有对应的 `tune2fs`/`xfs_admin` 开关。

> [!question]- 建完文件系统到交付业务，中间还差哪几步？
> - 打 LABEL、记录 UUID 与结构参数、**手动挂一次验证**、写 fstab 并 `mount -a` 验收、纳入容量与 inode 监控。
> - 缺任何一步，后面都会以「挂不上」「inode 满」「不知道这是哪块盘」的形式还回来。
> - **第一反应不要是什么**：不要用「重启一次看能不能挂上」代替 `mount -a` 与 `findmnt --verify`。

> [!question]- 为什么 XFS 需要 `-f` 才能 `mkfs`，这说明了什么？
> - 因为它会把目标设备上**已有的 XFS 签名**视为「这里已经有文件系统」，拒绝在未明确要求时覆盖。
> - 这是保护设计：它默认假设「你可能敲错了设备名」。
> - **第一反应不要是什么**：不要把 `-f` 当成习惯性参数加进去——它是「我确认这里的数据可以丢」的显式声明。
