# 容量边界、挂载与可见性

## 1. 「写不进去」不是一种故障

应用报写入失败时，最常见的反应是「磁盘满了」。但在 Linux 上，拒绝一次写入的理由至少有七种，它们**共用几句高度相似的报错文本，处置方向却完全不同**：

| 机制 | 报错与 errno | 真正的上限在哪 | 扩容能解决吗 |
| --- | --- | --- | --- |
| 数据块用尽 | `No space left on device`（`ENOSPC`） | 上限是超级块记载的空闲块数，`df` 报出的可用块降到 0 时触发 | 能 |
| inode 用尽 | `No space left on device`（`ENOSPC`） | 上限是该文件系统的 inode 总量，`df -i` 报出的可用 inode 数降到 0 时触发 | 通常能缓解，改不了根因 |
| ext4 保留块 | `No space left on device`（`ENOSPC`） | 上限是超级块为 root 保留的块数所占的比例 | 需要调比例，不是扩容 |
| 配额到顶 | `Disk quota exceeded`（`EDQUOT`） | 上限是 `bhard`/`ihard` 等硬限制给出的额度 | **不能** |
| 文件系统只读 | `Read-only file system`（`EROFS`） | 上限不是容量，而是内核把该文件系统置为只读的保护动作 | **不能**，且方向相反 |
| thin pool 写满 | 常见为写失败或整组变只读 | 上限是 thin pool 的数据用量或元数据用量达到 100% | 要扩池，不是扩卷 |
| 句柄或用 inotify 上限 | `too many open files` 或 `No space left on device` | 上限是 `fs.file-max`、`fs.nr_open` 与 `fs.inotify.max_user_watches` 这类进程级或系统级计数 | 与容量无关 |

先看报错原文，再选排查方向。`EDQUOT` 与 `ENOSPC` 是两个不同的 errno，处置完全不同；而 `ENOSPC` 内部还分三支。**「磁盘满」是一个待细分的判断，不是一个结论。**

有一部分「满」根本不在文件系统里。句柄与 inotify 的计数上限和字节容量没有任何关系，但它们会借用同一句 `No space left on device`，把排查方向直接带偏。

扩容对所有非容量类的「满」都无效。配额、只读、句柄、inotify 四类里，扩容不仅无效，还会掩盖真正的问题、延长故障时间。

## 2. 配额：把「整机故障」降级成「一个租户的故障」

共享目录、上传目录、多租户数据盘、容器节点的可写层，都是同一类风险：**任何一方不受限制的写入都能把该文件系统的空闲块用到 0**。这个过程的每一步都是确定的：某个应用的日志或缓存目录持续增长，所以 `df` 报出的该文件系统已用块不断上升；一旦可用块降到 0，该文件系统上的写入就返回 `ENOSPC`；此后同一文件系统上其他业务甚至系统自身的 ` /var/log`、`/tmp` 都写不进去，整机因此故障。

配额的作用就是在链条的中段把它截断：**失控的那一方先达到自己的硬限制（`bhard`/`ihard`），其他租户因此不受影响**。这是可用性手段，不只是资源手段。

配额不是单一的「一刀切」，而是三个参数协同：

| 参数 | 行为 | 设计意图 |
| --- | --- | --- |
| 硬限制（`bhard`/`ihard`） | 超过即拒绝写入（`EDQUOT`） | 它是真正的安全边界 |
| 软限制（`bsoft`/`isoft`） | 超过只告警，但要在宽限期内降下来 | 给业务留自清理的时间窗 |
| 宽限期（grace time） | 超过软限后仍允许继续写入的时长 | 避免业务峰值时被硬砍下来 |

三者缺一都不完整：只设硬限，业务峰值时会被突然打断（可能比写满更严重）；只设软限，等于没有边界；不留宽限期，软限就退化成硬限。默认值随文件系统与发行版变化，**一律现场取**。

配额按对象分三种，选错对象是「配了不生效」的第二大原因：

- **用户配额**绑在 uid 上。适合「一人一个 home 目录」的组织方式。
- **组配额**绑在 gid 上。适合「一个团队一个组」。
- **项目配额**绑在**一个目录树**上。适合「一个业务目录一个边界」——这正是共享目录与多租户场景的天然结构。

**为什么项目配额通常是最优选择**：共享目录里的文件往往由同一个服务账号写入，此时用户配额和组配额都把所有人算成一个对象，起不到隔离作用；而项目配额把边界钉在目录树上，与业务目录一一对应，既能解释（「这个目录属于租户 A」）也能追溯（配额报表里一个项目 ID 与一个业务方对应）。

配额有一个容易踩的机制性前提：**记账与强制是两件事，而且记账只能在挂载时打开。** 启用配额的文件系统需要在挂载选项里声明（ext4 的 `usrquota`/`grpquota`，XFS 的 `uquota`/`gquota`/`prjquota`）。挂载之后，工具只能开关**强制**，不能补开**记账**。所以「配额配好了却不生效」的头号原因是：挂载选项里没有它，此时再调多少限额都没有记账数据可依。

最后一条纪律：**配额不是告警的替代品。** 没有监控的配额只是把「写满整盘」换成了「写满自己的配额」——业务照样不可用，只是影响面从全机缩小到一个租户。用量百分比、宽限期状态、inode 配额用量三者都要进监控；监控容量时应当**把容量与 inode 两条使用率一起报**。

## 3. 不占字节的上限：句柄与 inotify

有一类「满」与容量完全无关，只与**计数**有关。

**句柄（fd，file descriptor）**是进程打开文件、套接字、管道的编号，它有三级上限：

| 级别 | 载体 | 达到上限后 |
| --- | --- | --- |
| 单进程软/硬限制 | 会话的 `ulimit -n`；systemd 服务的 `LimitNOFILE=`；登录会话的 `limits.conf` | 该进程报 `too many open files` |
| 单进程天花板 | 内核参数 `fs.nr_open` | 单进程限制不能超过它 |
| 全系统 | 内核参数 `fs.file-max` | 全系统的开文件调用会失败 |

三级里最容易搞错的是第一级：**终端里的 `ulimit -n` 与 systemd 服务的 `LimitNOFILE=` 是两套东西**。终端里的改动只影响该 shell 及其子进程；由 systemd 启动的服务读的是 unit 里的值。**改了 `limits.conf` 却对某个服务无效**，几乎总是这个原因。判断一个**运行中**的进程实际生效多少，要看它自己的限制文件，而不是看当前 shell 的 `ulimit`。

**inotify** 是文件事件监控机制（监视文件或目录的变化），它有三道上限，各条上限达到时的表现各不相同：

| 上限 | 限制什么 | 达到上限时的表现 |
| --- | --- | --- |
| `fs.inotify.max_user_watches` | 每个用户能监视的对象（文件/目录）总数 | 报 watch 上限相关错误，**也可能借用 `No space left on device`** |
| `fs.inotify.max_user_instances` | 每个用户能创建的 inotify 实例数 | 无法创建新实例 |
| `fs.inotify.max_queued_events` | 单个实例的事件队列长度 | 队列溢出，**静默丢事件**——应用漏报而不报错 |

第三条的后果最不容易被发现：`max_queued_events` 太小不会让任何调用失败，它只是让事件在队列里被丢弃。因此监控类应用会**少看到一部分文件变化，并且不报错**。

内核默认值不是「一串小常数」：`max_user_watches` 由内核按**可寻址内存的一定比例**计算并夹在一个上下限之间，`max_queued_events` 有固定的源码默认值，而 `max_user_instances` 是一个**固定值**，并不按内存推算。三者的实际值在 RHEL 与 Debian 系、不同版本之间差异很大，**必须现场取**。

这类问题为什么放在存储章？因为触发条件与「文件数量」强相关（日志目录、工作目录、备份扫描），常与 inode 类问题同时出现；而报错文本又常与磁盘问题混同。**判断顺序应当是：先确认是「字节的满」还是「计数的满」，再决定调参还是改设计。**

调大上限之前必须先问一句：**这个应用为什么需要这么多 watch 或句柄？** 常见根因是设计问题——递归监控整个代码仓库、给每个文件建一个独立 watch（应该用目录级 watch 加事件过滤）、每次请求新建连接而不复用。**上限是保护机制，它把单个应用占用的 watch 数与句柄数限制在 `fs.inotify.max_user_watches`、`fs.file-max` 这类全局计数上限之内；调大上限只是缓解，改设计才是修复。**

## 4. 挂载：可见性是拓扑问题

写失败还有一种与上限无关的来源：**你以为在写的那个目录，和你真正写到的地方不是同一个文件系统。**

挂载把一个文件系统的根接到目录树的某个目录上。这条操作有一个容易被忽略的语义：**挂载点上原有的内容被遮住，而不是被删除。**

| 现象 | 真相 |
| --- | --- |
| 挂载新盘到 `/data` 后，`/data` 里原来的文件「不见了」 | 它们还在原文件系统的那个目录里，只是被新的根挡住了 |
| 卸载之后它们又出现了 | 卸载解除了遮挡，所以原内容重新可见 |
| `du` 看不到它们，`df` 却仍然算着它们的空间 | `du` 遍历的是当前目录树；`df` 报的是该文件系统超级块记载的已用块与可用块 |

因此「我明明给日志盘留了 500 GiB」这类前提，必须**验证**而不是假定：一个目录是不是独立挂载点，只有查实际的挂载关系才知道。**目录名叫 `/var/log` 不代表它在一块独立的盘上。**

同一个文件系统可以同时出现在多个位置，这带来几种常见的拓扑形态：

- **绑定挂载（bind mount）**：把一个已挂载的目录再挂到另一个位置，同一份内容有两个入口。容器把宿主目录接进容器、救援时从「上层」查看被遮住的内容，用的都是它。
- **联合挂载（overlay）**：把多个目录层叠成一个可写视图；容器镜像与可写层就是这种结构（机制与代价见第 5 节）。
- **内存文件系统（tmpfs）**：挂在内存里的文件系统，重启即失。`/tmp`、`/dev/shm`、容器的临时目录常用它——**它的容量占用的是内存，不是磁盘**，`df` 里的容量条目与物理盘没有关系。

这三种形态会制造两类典型误判：**把 `tmpfs` 或 `overlay` 条目当成磁盘分区**（于是奇怪「这块盘哪来的」）；**在被遮住的目录里重新创建同名文件**（于是「补回来」的动作在新文件系统里留下了一份空数据，原数据仍在下面）。

一条通用的判断习惯：**任何关于「这个目录还剩多少空间」的问题，第一步都是确认它属于哪个文件系统**，而不是直接读 `df` 的第一行或凭目录名推断。

## 5. 联合挂载：同一个路径，两个视角

联合挂载（union mount，Linux 上的实现是 overlayfs）把若干只读目录叠成一个可写视图。它不是「把几块盘拼成一块」，而是**在查找路径这一层做合并**，所以它制造的每一个现象都与「同一条路径在合并视图与各层看来指向不同的对象」有关。

机制由三部分构成：一个可写的**上层**（upper）、一个或多个只读的**下层**（lower）、以及一个必须与上层同文件系统的工作目录（workdir）；挂载时给出的层叠视图是合并结果。下层的底层文件系统不必可写，也可以本身就是另一个联合挂载；上层则必须支持扩展属性（存放 overlay 自己的标记）并在 `readdir` 里给出有效的 `d_type`，因此网络文件系统不适合做上层。层与层的排列由挂载时给出的顺序决定（多层时从右到左依次变浅），层数越多，一次查找要走的目录越多。同一个下层可以被多个联合挂载共享（容器镜像层被多个容器复用就是这一条），但**同一个上层或 workdir 不能同时被两个联合挂载使用**，重复使用会失败或进入未定义行为。

| 操作 | 联合挂载里的实际动作 | 由此产生的现象 |
| --- | --- | --- |
| 读一个同名文件 | 上层胜出，下层被遮住；两边都是目录时合并 | 「镜像里的文件被容器改了」其实上层多了一个副本，下层原文件还在 |
| 列目录 | 只合并**名字列表**；元数据与扩展属性取上层 | 合并目录的属性与下层无关，`ls` 看到的不是任何单层的内容 |
| 删除下层文件 | 在上层写一个**白障**（whiteout：设备号为 0/0 的字符设备，或带 `overlay.whiteout` 扩展属性的零长文件） | 文件在视图里消失，但下层数据仍在、宿主磁盘占用不下降 |
| 删除整个下层目录 | 在上层给同名目录打 **opaque** 属性，使下层同名目录整体不再参与合并 | 「目录删掉了却还占着空间」；白障本身也是被隐藏的，普通列举看不到 |
| 首次写一个下层文件 | 触发 **copy-up**：先在上层补齐父目录链，再把文件整份复制上去（数据、元数据、扩展属性） | **写放大**：第一次写一个 N 字节的文件，要额外写下 N 字节；批量启动时集中发生 |
| 改元数据（如 `chmod`）、建硬链接 | 同样触发 copy-up（默认整份复制；启用 metadata-only copy-up 时才先只复制元数据，数据推迟到真正写时再复制） | 「只改了个权限，磁盘却涨了」 |
| 改下层或合并目录的名字 | 默认返回 `EXDEV`（跨设备），`mv` 于是退化成「复制 + 删除」 | 大目录改名慢且瞬时占用翻倍；启用重定向后才在上层改 |

**这一节最重要的判据是可用空间的口径。** 联合挂载的可用空间是**上层所在文件系统**的可用空间，下层的镜像层占的是另一份空间；`du` 遍历的是合并视图，`df` 报的是文件系统超级块记载的用量，两者的口径本来就不同。三件事必须一起看：`df` 的可用量、下层的只读占用、上层所在文件系统的水位。当视图本身是只读的时候，还要多问一句：这个文件读自哪一层。

**`stat` 报出的身份字段同样会变。** `stat` 报出的 `st_dev` 与 `st_ino` 可能来自上层、也可能来自下层，而且一个非目录对象的 inode 在 copy-up 之后会改变；只有当所有层位于同一个文件系统、或启用了把底层标识合成统一编号的特性（`xino`）时，对外才表现得像普通文件系统。依赖 inode 做判断的工具（硬链接去重、增量同步、审计比对）因此可能给出与直觉相反的结果。同一条机制还有两个具体后果：位于下层的多链接文件在 copy-up 后会**断链**（除非启用索引特性，在层间按 copy-up 原点建立对应关系）；正在执行的下层文件被写入或截断时**不会**报 `ETXTBSY`。

耐久性与一致性上有一条明确的边界：**挂载期间不允许改动底层**，改了行为未定义（不会崩，但结果不可预期）；离线改下层在下层没有参与过 copy-up 相关特性的前提下才安全。copy-up 本身是有序的——数据复制完成前会对上层文件做一次同步，再用改名或链接让它生效，所以崩溃后不会读到只写了一半的副本；但目录与「只改元数据」的 copy-up 默认不做同步保证。为性能放弃这一保证的挂载方式（标记为 volatile）在崩溃后不保证数据可用，而且下一次挂载会主动拒绝，直到有人确认上次的残留可以丢弃。

字段读法（是什么 / 单位 / 判据 / 与谁同看 / 转向哪一步）：

| 字段 | 是什么、单位 | 判据 | 与谁同看 | 转向哪一步 |
| --- | --- | --- | --- | --- |
| `df` 的可用量与来源 | 合并视图的可用空间（字节），来自上层所在文件系统 | 写入报 `ENOSPC` 时它才是判据 | 上层所在文件系统的水位、下层只读层的占用 | 若 `df` 报出的可用量正常而写入仍然返回 `ENOSPC`，则改查配额、ext4 保留块与 inode 用量 |
| `du` 与 `df` 的差值 | `du` 报出的合并视图实际分配量（字节），与 `df` 报出的同一文件系统用量之差 | 差值本身正常，需要解释的是差在哪一类 | 稀疏与共享块、白障与 opaque 目录 | 若 `du` 与 `df` 的差值突然变大，则去查最近一次 copy-up 批量事件 |
| 层叠顺序 | 挂载时给出的层序列（从右到左由深到浅） | 同名对象由最浅的层决定 | 各层的内容与时间戳 | 若合并结果与预期不符，则先按挂载时给出的层序列确认顺序，再去怀疑缓存 |
| `stat` 的 `st_dev`/`st_ino` | 对象身份；inode 号无单位 | 同目录内出现不一致或 copy-up 后变化即为该机制的表现 | 是否启用统一编号特性、各层是否同文件系统 | 若依赖 inode 的结论不成立，则改用路径与内容比对来复核 |
| 挂载选项与模块参数 | 特性开关及其默认值 | **默认值现场取**（挂载选项与模块参数目录一起看） | 上层文件系统是否支持扩展属性 | 若行为与文档不符，则先核对挂载选项与模块参数的取值，再去怀疑内核版本 |
| 传播类型（见 `/proc/<pid>/mountinfo`） | 该挂载点的传播标记 | 决定这个挂载上的事件会不会传到别的命名空间 | 该挂载点所在的挂载命名空间 | 若容器里的挂载影响了宿主，则去查该挂载点的传播标记，而不是去查权限 |

容器让这套机制每天都在发生：镜像的每一层是只读下层，容器的可写层是上层。于是容器内的 `df` 与 `df -i` 条目由运行时与存储驱动决定，容量与 inode 的读数不再对应任何一块盘；容器里删除文件会让宿主空间**下降得很慢或根本不降**（留下的是白障）；容器里看到的某个文件，可能是下层原文件、也可能是已 copy-up 的副本——**判断「这个文件占了多少、在哪一层、改了会不会翻倍」之前，先确定 `stat` 读到的对象来自上层还是下层**。这也是容量类判据在容器环境里整体失效的原因，与存储章末验收里的边界一致。

## 常见误解

| 常见说法 | 事实 |
| --- | --- |
| 「`No space left on device` 就是磁盘满了」 | 它同时覆盖 inode 耗尽、ext4 保留块；配额与只读报的是另外的 errno；句柄与 inotify 也会借用这句话 |
| 「`Disk quota exceeded` 与 `No space left on device` 是一回事」 | 前者是 `EDQUOT`、后者是 `ENOSPC`；一个查配额，一个查容量与 inode |
| 「配额配好了，`enable` 一下就行」 | 记账必须在挂载时打开；挂载后只能开关强制，补不开记账 |
| 「用户配额能管住共享目录」 | 多人共用一个服务账号时用户配额把所有人算成一个对象；目录级边界要用项目配额 |
| 「配额本身就够了，不用监控」 | 配额只是把「写满整盘」换成「写满自己的配额」，业务照样不可用 |
| 「改了 `limits.conf` 服务就该生效」 | systemd 服务读 unit 里的 `LimitNOFILE=`；登录会话与终端 `ulimit` 是另外两套 |
| 「inotify 满了肯定报错」 | `max_queued_events` 溢出是**静默丢事件**，应用漏报而不报错 |
| 「上限调大就是解决」 | 常见根因是应用设计（逐文件 watch、连接不复用）；调大上限只是推迟故障，并会占掉其他服务共用的全局计数上限 |
| 「挂载后旧数据被删了」 | 它只是被新的挂载遮住了；卸载该挂载、或从上层用绑定挂载查看，就能见到原内容 |
| 「`df` 里那个 60G 的 tmpfs 是块盘」 | tmpfs 挂在内存里，占的是内存不是磁盘 |
| 「目录叫 `/var/log` 就一定在日志盘上」 | 一个目录是不是独立挂载点，只能查实际的挂载关系才知道 |
| 「`df` 显示还有空间，所以写得进去」 | 联合挂载的可用量来自上层所在文件系统；首次写还会先复制出一份完整副本，空间要算两次 |
| 「容器里删了文件，宿主空间就回来了」 | 删除在上层留的是白障，下层数据仍在；宿主占用不降 |
| 「同一个文件在容器内外的 inode 是一致的」 | inode 可能来自上层或下层，copy-up 之后还会变；只有启用统一编号特性时才稳定 |
| 「只改权限不占空间」 | 默认的元数据修改同样触发 copy-up，一样会写下整份文件 |

## 要点自测

**问：`df -h` 还有 40%，写入报 `No space left on device`，按什么顺序排查？**
答：第一步读报错原文，确认它是 `ENOSPC`、`EDQUOT` 还是 `EROFS`；第二步读 `df -i` 报出的已用 inode 数与可用 inode 数；第三步判断是不是 ext4 保留块，判据是 root 能写而普通用户写不进去；第四步确认写入路径实际落在哪个文件系统；第五步再看配额报表与 thin pool 的用量水位。每一步都只读，可以在生产机上做。

**问：为什么「先看报错原文」能省掉大半排查？**
答：因为 `EDQUOT`（配额）、`EROFS`（只读）、`ENOSPC`（容量或 inode 或保留块）指向三条互不重叠的路径；把 `ENOSPC` 内部再分成三支，剩下的就只有句柄与 inotify 这类非空间上限了。

**问：项目配额为什么比用户配额更适合共享目录？**
答：共享目录的文件常由同一个服务账号写入，用户/组配额会把所有人算成一个对象，起不到隔离作用；项目配额绑在目录树上，与业务目录一一对应，既可解释也可追溯。

**问：为什么在 XFS 上「只 `enable`」不能让配额生效？**
答：记账（accounting）只能在挂载时用挂载选项打开，运行时不支持补开；挂载后的开关只控制**强制（enforcement）**。所以「配了不生效」要先查挂载选项。

**问：句柄与 inotify 上限为什么容易被误判成磁盘问题？**
答：它们会借用 `No space left on device` 或「写入失败」这类文本，触发条件又与文件数量强相关（日志目录、扫描程序），所以容易和 inode 类问题混在一起。判断方法：容量与 inode 都正常时，直接去查计数类上限。

**问：为什么「挂载后原目录数据消失」既不是数据丢失，也不是工具 bug？**
答：挂载把一个文件系统的根接到那个目录上，原内容仍在原文件系统里，只是不再位于目录树的该位置。卸载即恢复可见；要查看可以用绑定挂载从上层看。

**问：容器里 `rm` 掉一个来自镜像层的大文件，宿主磁盘为什么没有释放？**

答：删除没有改下层（下层是只读的），而是在上层写了一个白障记录「这个名字被删了」，合并视图于是不再显示它。占空间的数据仍在下层；要真正释放，得重建对应的镜像层或丢弃整个可写层。判据是「合并视图里看不到」与「宿主占用不降」同时成立。

**问：联合挂载的 `df` 说还有空间，第一次写一个大文件却失败了，为什么？**

答：因为第一次写下层文件要先 copy-up：它需要在上层放下一份**完整副本**，需要的空间是文件大小本身，而不是你这一次打算写入的字节数。判据是把「目标文件的大小」与「上层所在文件系统的可用量」放在一起看，而不是只看这次写入的量。

**问：容器内 `stat` 出来的 inode 与宿主看到的对不上，是工具坏了吗？**

答：不是。联合挂载对外报出的身份可能来自上层或下层，非目录对象在 copy-up 之后 inode 还会改变；只有当所有层位于同一个文件系统、或启用了把底层标识合成统一编号的特性时，它才表现得像普通文件系统。依赖 inode 的结论要换成按路径与内容比对。

**第一反应不要做什么**：不要把「磁盘满」当结论；不要在 inode 告警时先扩容；不要在 XFS 上只 `enable` 就以为配额生效；不要只调大 inotify 或句柄上限而不问设计是否合理；不要在没确认写入路径属于哪个文件系统之前讨论空间够不够；不要把容器里的 `df` 当成宿主文件系统的容量读数，也不要用「删了文件」推断宿主空间会立刻回来。

## 参考文档

- `man 1 df`、`man 1 du`、`man 1 stat`、`man 1 ln`：容量与大小口径。

- `man 3 errno`：`ENOSPC`、`EDQUOT`、`EROFS` 的定义。
- `man 2 getrlimit`、`man 5 limits.conf`、`man 5 systemd.exec`（`LimitNOFILE=`）：句柄的三级上限。
- `man 7 inotify`、`man 5 proc` 与内核文档 `Documentation/admin-guide/sysctl/fs.rst`：`fs.file-max`、`fs.nr_open`、`fs.inotify.*`。
- `man 8 mount`、`man 5 systemd.mount`、`man 5 systemd.automount`：挂载语义、绑定挂载与挂载单元；`man 8 mount` 的 overlay 一段给出 `lowerdir`/`upperdir`/`workdir` 与各特性开关。
- 内核文档 `Documentation/filesystems/overlayfs.rst`：联合挂载的可见性规则、白障与不透明目录、copy-up 的触发与耐久性、身份（`st_dev`/`st_ino`）与统一编号特性的取舍。
- `man 5 proc`（`/proc/<pid>/mountinfo`）：挂载来源与传播类型；`/sys/module/overlay/parameters/` 给出模块级特性默认值，**默认值现场取**。
