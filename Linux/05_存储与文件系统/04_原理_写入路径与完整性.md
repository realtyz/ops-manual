# 写入路径与完整性

## 1. 写返回了，数据还没落盘

一次 `write` 系统调用返回成功，含义是「内核已经收下了这些字节」，不是「设备已经记住了它们」。默认路径上，数据先被复制进 **Page Cache（页缓存）**，函数立刻返回；真正的落盘由内核稍后**异步回写（writeback）**完成。

这个设计换来的是吞吐：应用不必等机械寻道或闪存编程，多个小写可以在缓存里合并成一次大的顺序写，重复写入同一区域只产生最后一次 IO。代价是**「写入成功」与「数据安全」之间出现了一个窗口**——在此期间断电、内核崩溃、设备掉线，数据就没了，而应用完全不知道。

窗口什么时候关闭，由调用方决定：

| 手段 | 保证到哪一步 | 代价 |
| --- | --- | --- |
| `write` 返回 | 数据在内核缓存里 | 无 |
| `fsync`（或 `fdatasync`） | 数据与必要的元数据都在设备上 | 每次调用触发一次等待设备的 IO，延迟可达毫秒级 |
| `sync` | 系统范围内所有脏页被推下去 | 全局动作，影响所有进程 |
| 直接 IO（`O_DIRECT`） | 绕过页缓存，直接发到设备 | 失去缓存收益，需要自己对齐与管理 |

由此推出四条实务规则：

**「写很快」不能用来评估持久化能力。** 不带同步的写入测的是内存速度。对顺序与持久性有要求的测试（例如用 `dd` 测真实写入速度），必须显式要求内核把它落盘；不带这个动作的数字与设备能力无关。

**`fsync` 的代价必须算进设计。** 每次同步都要等设备确认，因此「每条记录同步一次」的写放大非常昂贵。日志、数据库的批量提交、消息队列的刷盘策略，本质都是在「丢多少」与「多慢」之间选一个点。这个选择是应用设计问题，不是内核参数问题。

**追加写与覆盖写在崩溃后的结果完全不同。** 同一次崩溃里，已经落盘的部分保留，还在缓存里的部分消失。顺序追加的文件最坏情况是「末尾少一段」，而就地覆盖的数据结构（例如直接在文件中间改一个索引页）崩溃后可能既不是旧值也不是新值。这是日志结构、预写日志、写时复制这类设计存在的理由。

**落盘顺序比落盘速度更容易出事。** 应用常常有隐含的依赖：「先写数据文件，再写它的元数据索引」。如果两次都只是进了缓存，回写顺序不保证与调用顺序一致，崩溃后可能看到「索引指向不存在的数据」。要保证顺序，必须在两次写之间显式同步，或者依赖文件系统的顺序保证（ext4 的默认日志模式会先落数据再提交元数据，这是它默认模式的语义，而不是所有模式都如此）。

## 2. 回写跟不上时，变慢的是谁

脏页积累到一定量后，内核启动后台回写；超过更硬的阈值后，**发起写的进程会被限速甚至阻塞**，直到脏页排空到自己该承担的那一份。这是「写入变慢」最常见的机制来源，它的特征是：

- 存储设备本身没有报错，健康也没有变化；
- 应用表现为间歇性卡顿、写延迟出现长尾、进程进入不可中断睡眠；
- 瓶颈在**脏页产生速率与设备排空速率的对比**上，而不是在某个阈值的大小上。

阈值（比例或字节数两种写法，**两族互斥，实际生效值现场取**）只决定「何时开始回写」与「何时开始限速」，不决定设备能不能跟上。所以那条最流行的调优建议——「写入卡顿就把脏页上限调小」——只在一种情况下有效：瓶颈确实是回写限速本身。如果设备排空速率本来就低于产生速率，收紧上限只会让限速更早启动，**总吞吐不会变好，反而可能更差**。

分清楚方向的办法是看**配对指标**：脏页量是否贴着阈值，与设备侧的排队深度和完成时间是否同时升高。两者组合能区分「请求在设备队列里排队」与「写者被回写机制按住」，这两条路的处置完全不同（前者在设备与写入模式，后者在参数与刷盘节奏）。

**丢弃缓存是测量动作，不是优化动作。** 内核提供一个接口用来丢掉干净缓存与可回收的内核对象，它在做基准测试、需要一把「冷启动读数」时才有意义。**生产上不要执行它**：被丢掉的是纯性能资产，此后业务必须为重建缓存重新付出 IO，而内存并不会因此变得「更够用」。看到「缓存占用高」的正确反应是确认可用内存与压力指标，不是清缓存。

这也解释了为什么本地盘「变慢」与文件系统「变坏」是两种结局：回写积压再严重也只是延迟问题，可恢复、可调优；而介质错误、只读重挂、阵列降级是**数据风险**，必须立刻停止写入并取证。判断顺序因此是固定的——先确认是「变慢」还是「写坏」，再谈动作。

## 3. 出错时内核会做什么：保护动作与它的前提

文件系统在运行中检测到不一致或底层 IO 错误时，有一组**自我保护**动作。理解它们的目的是为了知道：**看到这些现象时，系统在保护什么，以及第一反应该是什么。**

| 现象 | 内核在做什么 | 第一反应 |
| --- | --- | --- |
| 文件系统被重新挂载为只读 | 阻止损坏继续扩散到更多元数据 | 取证，而不是重新挂载为可写 |
| 报介质错误（读失败、写失败） | 报告底层设备问题 | 先判断是介质还是链路，再谈修复 |
| 日志重放 | 把已提交的元数据变更补齐，恢复到一致状态 | 让它完成；不要抢着人工硬修 |
| 阵列降级 | 用冗余数据继续服务 | 先确认坏的是哪一块，不要立刻拔盘 |
| 进程进入不可中断睡眠 | 等待 IO 完成（包括等一个不可达的网络存储） | 恢复 IO 通路，而不是杀进程 |

这里有一个**必须现场确认**的前提，也是最容易搞反的一点：**ext4 的默认出错行为是「标记并继续」（`errors=continue`），而不是「重新挂载为只读」（`errors=remount-ro`）。** 也就是说，**没有显式配置时，内核检测到错误并不会自动把文件系统切成只读**——它会继续带着已知的损坏往下写。生产数据盘应当显式配置为出错即重挂只读，把「继续写坏」变成「停下来等人处理」。

（默认值一律现场取：ext4 的出错行为由创建时的默认值与挂载选项共同决定，发行版还可以通过配置文件改默认值，因此**不能凭发行版猜**。）

这条性质把「只读」这个现象的含义说清楚了：**只读是内核在保护数据，它意味着已经出过错**。所以正确的顺序是：

**取证（内核日志、硬件健康）→ 判断根因（介质故障还是元数据损坏）→ 停止写入 → 卸载 → 干跑检查（只读、不修改）→ 备份 → 正式修复 → 只读挂载核对 → 恢复可写。**

顺序里有三个不可省略的判断：

- **介质故障与元数据损坏要分开。** 如果硬件计数显示待处理坏扇区或介质错误，根因在设备上——此时做文件系统修复等于在坏盘上折腾数据，**先保数据、先换盘**。元数据损坏（日志、超级块、目录结构）才谈修复。
- **干跑检查必须排在正式修复之前。** 只读检查只报告不改动，它回答的是「问题规模有多大」；很多场景（尤其是崩溃后）根本不需要修复，只要挂载一次让内核重放日志。
- **修复后先只读挂载核对数据，再恢复可写。** 少了这一步，等于把「修过的文件系统」直接交给业务写入，出问题时已经无从判断是修复引入的还是别的原因。

## 4. 哪些动作不可逆

存储故障处置与内存、CPU 类故障最大的区别：**很多动作没有「再试一次」的机会**。把它们单独列出来，是因为它们必须在动作之前被识别，而不是事后总结。

| 动作 | 不可逆在哪 | 前置条件 |
| --- | --- | --- |
| 建文件系统 | 立刻在新账本下覆盖原元数据，恢复代价极高 | 确认设备没数据、有副本、设备名没认错 |
| 清空签名（`wipefs` 不带 `-n`） | 直接擦掉分区表与文件系统签名 | 同上 |
| 整设备擦除 | 立刻清空全部数据 | 只用于已下线或回收前的盘 |
| 丢弃日志（`xfs_repair -L`） | 丢掉尚未落盘的元数据变更，可能丢数据 | 日志确实损坏、且已有可用备份 |
| 缩小文件系统 | ext4 顺序错一步就切掉正在使用的区域；XFS 完全不支持 | 必须卸载、先完整检查、先缩文件系统再缩卷 |
| 缩小卷 | 切掉的容量不会自己回来，且可能切到在用区域 | 顺序与上限都要先算清 |
| 自动回答全部 yes（`e2fsck -y`） | 在元数据自相矛盾时，工具可能选择删掉有数据的一边 | 先只读检查看清规模、先备份 |

因此有一类前置动作是所有不可逆操作共用的：**动手前先取一份能回退的副本**。可选形态按代价从低到高排列——文件系统级的元数据副本（体积极小，适合留证与送分析）、卷级快照（快、有性能代价、会随写入增长）、块级快照（云盘或存储阵列提供，最完整）、完整镜像（最贵，但独立于原设备）。

**快照不是备份**这条边界在原理篇 1 已经讲过，这里要补充的是它的**时效**：卷快照随原卷写入而增长，写满即失效；而它的生命周期通常只有一次维护窗口那么长。把快照当长期备份，等于把「今天能回滚」当成「下个月也能回滚」。

## 5. 性能问题的分层：为什么「换个快盘」经常无效

一次 IO 从应用出发到落上介质，要经过若干层，**每一层都可能让它变慢**：

应用（写入模式、同步频率、并发度）→ 系统调用与虚拟文件系统 → 文件系统（元数据操作、块大小、挂载选项）→ Page Cache 与回写机制 → 块层（队列深度、预读、调度策略）→ 设备驱动 → 介质本身（盘、阵列卡缓存、网络存储的对端）。

这个链条决定了三条判断纪律：

**观测工具大多只能看到最底层。** 设备侧的统计反映的是「到达设备之后」的表现；请求在应用里攒批、在缓存里命中、在回写队列里等待，都不会出现在设备侧的指标里。因此「设备看起来很闲」不等于「存储不是瓶颈」，也可能是请求还没走到设备。

**读与写在路径上完全不对称。** 读命中缓存时就结束了，不碰设备；未命中则要走到底层，随机访问最吃介质能力。写默认只进缓存就返回。所以「读慢」与「写慢」的排查起点不同：读要问命中率与介质随机能力，写要问回写链与设备排空速率（第 2 节）。

**介质能力的量级必须知道，否则读不懂数字。** 机械盘的随机小 IO 在百级、SATA SSD 在万级、NVMe 在十万到百万级（单位都是每秒请求数）；顺序带宽从百 MB/s 到 GB/s 级（这里的 B 是字节，而链路标称常用比特，相差 8 倍）；延迟从毫秒级到几十微秒级。**这些都是量级，不是验收标准**——具体数值随型号、队列深度、块大小、是否直写、阵列缓存策略变化极大。它们的用途只有一个：**看到一个数字时，判断它是「正常」「偏高」还是「离谱到不可能是这个原因」**。

调优项的收益与代价也必须成对看：提高预读对顺序读有帮助、对随机读浪费带宽；加深队列能吸收突发但会拉长延迟；关闭访问时间更新能减少元数据写入但会影响依赖它的备份工具；换更快的介质收益最直接、成本也最高。**没有基线的调优都是在赌**——「变快了吗」这个问题，只有前后同一组条件下的对比能回答。

## 6. 存储不在本机时

网络存储（NFS、iSCSI、光纤通道、云文件服务）把「一次 IO 有多快」拆成了三个独立变量：**本地路径、网络、对端存储**。它带来两个本地盘没有的故障形态。

**第一，本地进程会被远端拖住。** 当对端不可达时，客户端的行为由一个语义选项决定，而这个选项的取舍无法两全：

| 语义 | 对端不可达时的行为 | 换来了什么 | 代价 |
| --- | --- | --- | --- |
| 硬挂载（`hard`，常见默认） | 无限重试，访问该挂载点的进程停在不可中断等待 | 不会产生部分写入造成的不一致 | 进程无法被信号终止，业务卡住 |
| 软挂载（`soft`） | 超时后把错误返回给应用 | 不会无限卡住 | **可能产生静默的数据不一致**：写入可能只完成一部分 |

关键机制在于：停在不可中断等待里的进程等待的是内核里的 IO 完成，**信号要等它回到用户态才会被处理**。所以「杀进程」既无效也不解决问题——要恢复的是 IO 通路。这也解释了为什么软挂载通常只用于只读或本身能安全重试的场景，而写入场景宁可等待。超时与重传参数（以十分之一秒为单位的等待时间、重传次数）决定的是「多久之后返回错误」，只对软挂载有意义。

**第二，挂载配置会把局部故障升级成启动故障。** 网络存储的挂载必须同时声明两件事：一个是**网络就绪之后再挂**，一个是**挂不上也不阻塞启动**。少前一个，启动时会等设备超时（表现为启动卡在某个作业上很久）；少后一个，对端不可达时本机可能进不了系统。这两条与「本地盘掉线导致进紧急模式」是同一类问题的两个变体。

**多路径**（同一块存储设备通过多条物理路径可达）解决的是链路冗余，但它有一个业务侧必须知道的副作用：**路径切换会造成秒级 IO 停顿**。业务的超时设置如果短于这个停顿，就会看到「存储没问题但请求超时」。还有一种配置陷阱：当所有路径都不可用时，某些策略会让 IO **永久排队**而不是立即报错——它的现象与硬挂载完全相同（进程停在不可中断等待），处置思路也一样：先恢复通路。

因此网络存储的排障顺序与本地存储不同：**先确认通路（对端、网络、路径状态），再谈本地动作**。而在本地能做的动作里，卸载是最后手段——强卸不会让进程停止写入，只会让它们继续写到一个已不在目录树里的文件系统上。

**第一反应不要做什么**：不要用批量强杀进程来处理卡住的挂载点；不要为了「界面不卡」把写场景改成软挂载；不要以为网络通就是存储通（还要看对端进程、导出权限、端口与路径状态）。

## 7. 闪存的维护：回收通知与寿命

机械盘的写入是「覆盖就地」，闪存不是。闪存的写入以页为单位，而擦除以更大的块为单位：改写一个页时，必须先把它所在的整块擦掉，把仍然有效的数据搬到别处再写回。这个约束有两个直接后果：

- **写放大**：一次逻辑写入可能引发多次物理读写，写入效率随盘的填满程度下降；
- **需要回收**：盘需要知道「哪些块里的数据已经被文件系统删掉了、可以安全擦除」，否则它只能搬着无效数据一起走。

**TRIM 就是文件系统把这个信息告诉盘的动作**。它的收益是维持长期写入性能与减少无谓的擦写；它的代价是执行时会产生额外的设备动作。因此有两个决策点：

| 做法 | 时机 | 取舍 |
| --- | --- | --- |
| 定期批量下发 | 定时任务触发 | 时机可控、影响可预期；是常规做法 |
| 删除时立即下发（挂载选项） | 每次删除 | 不需要额外调度；在部分盘上会造成延迟抖动，只适合对延迟不敏感的场景 |

**寿命评估是趋势问题。** 闪存盘会报告已消耗寿命的比例与备用块余量，还会报告异常掉电次数与数据完整性错误计数。这些字段的用途是判断「是否需要排入替换计划」，判据是**它们相对厂商阈值的位置与增长速度**，而不是单次读数；其中「完整性错误非零」属于需要立即介入的一类，因为它意味着数据已经出错而不是盘在变慢。

**整设备擦除是破坏性动作**：它立刻清空数据，只应当用在已下线或待回收的盘上，且执行前必须核对设备身份。它属于本节的维护动作里唯一不可逆的一个。

## 常见误解

| 常见说法 | 事实 |
| --- | --- |
| 「`write` 返回成功，数据就安全了」 | 默认路径只保证数据进了内核缓存；落盘由异步回写完成 |
| 「写很快说明盘很快」 | 不带同步的写测的是内存速度，与设备持久化能力无关 |
| 「把脏页上限调小能治写入卡顿」 | 上限只决定何时开始回写与限速；卡不卡取决于排空速率能否跟上产生速率 |
| 「文件系统出错会自动变只读」 | ext4 默认是 `errors=continue`（标记并继续）；要自动重挂只读必须显式配置 |
| 「只读是故障本身」 | 只读是内核的保护动作，它意味着已经出过错，先取证 |
| 「日志重放等于数据恢复」 | 重放保证一致性，不保证数据内容完整，也不是备份 |
| 「修复工具越彻底越好」 | `-y` 一类「全部回答 yes」在矛盾状态下可能删掉有数据的一边；先只读检查、先备份 |
| 「有快照就有退路」 | 快照随原卷写入增长、写满即失效，且与源数据同盘时一起消失 |
| 「IO 慢就是盘慢」 | 应用攒批、缓存命中、回写等待都在设备之前；设备侧的指标只覆盖最后一层 |
| 「量级表可以当验收标准」 | 量级只用于判断数字是否离谱；验收必须用自己的基线 |
| 「网络存储卡住就杀进程」 | 停在不可中断等待的进程收不到信号；要恢复的是 IO 通路 |
| 「软挂载比硬挂载安全」 | 软挂载换来的是「不卡住」，代价是可能静默的数据不一致；写场景优先硬挂载 |
| 「网络通就是存储通」 | 还依赖对端进程、导出权限、端口与多路径状态 |
| 「闪存盘的回收通知是个性能开关」 | 它维持的是长期写入效率，不解决「现在慢」；一次性执行看不到提升 |
| 「整设备擦除只是清空文件」 | 它立刻清空全部数据且不可逆，只用于已下线或待回收的盘 |

## 要点自测

**问：`write` 返回成功之后，数据处于什么状态？什么动作才能保证落盘？**
答：数据在内核的页缓存里，尚未写到设备。要保证落盘需要显式要求同步（如 `fsync`/`fdatasync`，或系统范围的 `sync`），或使用绕过页缓存的直接 IO；代价是等待设备确认。

**问：写入变慢时，怎么区分是回写机制还是设备本身？**
答：看配对指标——脏页量与阈值的关系，与设备侧的排队深度和完成时间。脏页贴着上限、写入被限速而设备并不繁忙，方向在回写与刷盘节奏；设备侧排队深、完成时间高，方向在设备与写入模式。

**问：为什么「ext4 出错会自动变只读」这句话通常不成立？**
答：ext4 的默认出错行为是 `errors=continue`——标记并继续写。要变成「出错即重挂只读」必须在挂载选项里显式配置。默认值由创建时的默认值与发行版配置共同决定，必须现场取。

**问：文件系统变只读时，为什么不能重新挂载为可写？**
答：只读是内核检测到错误后的保护动作，目的是阻止损坏扩散。重挂可写等于让它带着已知的损坏继续写。正确顺序是取证 → 判断根因 → 停止写入 → 卸载 → 干跑检查 → 备份 → 修复 → 只读核对 → 恢复可写。

**问：为什么「换个更快的盘」常常解决不了「IO 慢」？**
答：因为请求可能在到达设备之前就已经在应用、缓存或回写环节等待。设备指标只覆盖路径的最后一层；没有分层定位就换硬件，等于在没确认瓶颈的情况下付出最高成本。

**问：不可逆动作的共同前置条件是什么？**
答：动手前先有一份能回退的副本，且形态要与风险匹配（元数据副本用于留证、快照用于窗口内回滚、块级快照或镜像用于修复与重建）；同时确认根因，避免在坏硬件上折腾数据。

**问：网络存储卡住、进程停在不可中断等待时，为什么杀进程无效？正确处理顺序是什么？**
答：进程等的是内核里的 IO 完成，信号要等它回到用户态才被处理，所以杀不掉也不该杀。顺序是确认是哪个挂载点 → 查通路（对端、网络、路径状态）→ **优先恢复通路**（恢复后等待状态自行消解）→ 无法恢复时才评估强卸的数据风险 → 最后才是重启。

**问：闪存盘的回收通知解决的是什么问题，它不是什么？**
答：它把「哪些块已无效」告诉盘，维持的是长期写入效率，减少写放大；它不是性能开关——对「这台机器现在慢」没有直接作用，一次性执行也看不到提升。寿命评估则看健康字段相对厂商阈值的位置与增长速度。

**第一反应不要做什么**：不要把「写入成功」当数据安全；不要用不带同步的写入结果评估持久化能力；不要看到只读就重挂为可写；不要在没有备份时跑修复类命令；不要在没分类之前把「IO 慢」归到盘上。
