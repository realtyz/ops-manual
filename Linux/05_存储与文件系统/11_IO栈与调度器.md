## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **一次 IO 的路径**：应用 → 系统调用 → VFS → 文件系统 → Page Cache → **块层（blk-mq）→ IO 调度器 → 设备驱动 → 硬件**。**任何一层都能成为瓶颈，而 `iostat` 只能看到最底层的表现。**
> - **读可能根本不碰盘**：命中 Page Cache 的读在图中间就返回了；**写通常先在缓存里攒着**（阶段 4 的回写机制），所以「写快」不等于「落盘快」。
> - **blk-mq 是多队列**：每个 CPU 有独立的软件队列，硬件多队列设备各有硬件队列——所以**老一代的 `cfq`/`deadline`/`noop` 已经不在 RHEL 8/9 上提供**。
> - **调度器的选择跟着介质走**：NVMe 与自带调度的阵列卡多用 `none`；SATA/SAS/机械盘常用 `mq-deadline`；`kyber` 面向低延迟设备；`bfq` 面向公平性与交互。
> - **介质量级差三个数量级**：机械盘随机 4K 约百级 IOPS，NVMe 可达十万到百万级——**具体数值必须用 `fio` 实测，型号差异极大**。

## 1. 一次 IO 的路径

```mermaid
flowchart LR
  A["应用<br/>read/write"] --> B["系统调用 → VFS"]
  B --> C["文件系统<br/>ext4/XFS"]
  C --> D["Page Cache<br/>命中即返回"]
  D --> E["块层 blk-mq<br/>软件队列 → 硬件队列"]
  E --> F["IO 调度器<br/>合并 · 排序 · 限时"]
  F --> G["设备驱动"]
  G --> H["硬件<br/>盘 · 阵列卡缓存 · 网络存储"]
```

| 层 | 能在这里做什么 | 典型现场 |
| --- | --- | --- |
| 应用 | 改写入模式（批量、异步、`O_DIRECT`）、错峰 | 大量小写、fsync 频繁（阶段 10 会展开） |
| 文件系统 | 挂载选项（`noatime`、`nodiratime`）、块大小 | 元数据写入过多 |
| Page Cache | 命中就有收益；回写参数影响写延迟 | `Dirty` 高、写进程进 `D`（阶段 4） |
| 块层 | 队列深度、预读、调度器 | `aqu-sz` 高、请求排队 |
| 设备/阵列/网络 | 介质能力、阵列缓存策略、链路 | `await` 上升、`%util` 饱和 |

> [!important] 读与写在这一层上完全不对称
> **读**：命中 Page Cache 就结束了，没命中才走到底层（随机读最吃介质能力）。
> **写**：默认先进 Page Cache 就返回（`writeback` 模式），真正落盘是稍后异步回写；**要确定落盘的写必须 `fsync`**。
> 所以「写入慢」可能出在**回写链**（阶段 4 的领域），也可能是**底层设备慢**（本阶段）。判断方法是把 `Dirty`/`Writeback` 与 `await`/`aqu-sz` 放在一起看（子笔记 12）。

## 2. 块层：多队列与队列深度

blk-mq（multi-queue block layer）是现代内核的块层框架：每个 CPU 有独立的软件队列（`ctx`），再映射到设备的硬件队列。这带来的直接结果是**并行度大幅提高**，也让「设备忙不忙」不能再用单一比例衡量。

```bash
lsblk -o NAME,TYPE,SIZE,ROTA,SCHED   # 验证：设备类型与调度器一览（较新 util-linux 支持 SCHED 列）
cat /sys/block/<dev>/queue/scheduler # 验证：当前调度器与可选值（中括号内为当前值）
cat /sys/block/<dev>/queue/nr_requests
                                     # 验证：单队列的请求上限（块层排队深度）
cat /sys/block/<dev>/queue/nr_requests; ls /sys/block/<dev>/mq 2>/dev/null | head
                                     # 验证：多队列设备上每个硬件队列都有自己的目录
cat /sys/block/<dev>/queue/read_ahead_kb
                                     # 验证：预读窗口（顺序读场景的常见调优点）
cat /sys/block/<dev>/queue/rotational
                                     # 验证：0=SSD/NVMe、1=机械盘（调度策略的重要输入）
```

| 观测点 | 含义 | 什么时候看 |
| --- | --- | --- |
| `scheduler` | 当前调度器（中括号内生效） | 判断设备是否走直通（`none`） |
| `nr_requests` | 队列可容纳的请求数 | 高并发压力下队列被打满（`aqu-sz` 高） |
| `/sys/block/<dev>/mq/*` | 每个硬件队列的目录 | 确认设备是多队列（NVMe 常见几十个队列） |
| `read_ahead_kb` | 预读窗口 | 顺序读吞吐不理想时 |
| `rotational` | 是否是旋转介质 | 决定调度器与调优方向 |

## 3. 四种 IO 调度器

| 调度器 | 适用场景 | 说明 |
| --- | --- | --- |
| `none` | NVMe、低延迟设备、阵列卡自带调度 | 直通，不做合并与排序，交给硬件 |
| `mq-deadline` | 通用（SATA/SAS、机械盘常见默认） | 给请求设置延迟上限，避免饿死 |
| `kyber` | 快速设备 | 以读/写延迟目标为调度依据 |
| `bfq` | 桌面、交互与公平性 | 按 cgroup/进程公平分配带宽，吞吐略低 |

```bash
cat /sys/block/<dev>/queue/scheduler
                                     # 验证：当前调度器（RHEL 9 文档给出的默认是 NVMe 用 none、其它块设备用 mq-deadline，以本机为准）
echo mq-deadline | sudo tee /sys/block/<dev>/queue/scheduler
                                     # 验证：临时切换（重启失效；持久化要靠 udev 规则）
```

老一代的单队列调度器（`cfq`、`deadline`、`noop`）在多队列架构下已不再提供，**RHEL 8/9 上能选的就是上面这四种**。要持久化切换，需要用 udev 规则（例如按设备名或 `rotational` 属性在 `/etc/udev/rules.d/` 里写 `ATTR{queue/scheduler}`）。

> [!tip] 第一反应不要是「上网抄一个调度器名字就改」
> 调度器的效果**强依赖介质与业务模式**：`bfq` 在桌面交互上体验好，但在高吞吐服务上会降低吞吐；`none` 在 NVMe 上通常最优，但用在机械盘上会让随机 IO 失去排序收益。**要改就先测：用 `fio` 在与生产相似的模式下做前后对比（子笔记 12）。**

## 4. 介质量级：建立「什么是正常」的直觉

| 介质 | 随机 4K IOPS | 顺序带宽 | 典型延迟 |
| --- | --- | --- | --- |
| 机械盘（7200 rpm） | 约 100~200 | 约 150~250MB/s | 毫秒级（含寻道） |
| SATA SSD | 约 1 万~10 万 | 约 500MB/s 量级（受 SATA 限制） | 百微秒级 |
| NVMe SSD | 十万~百万级 | GB/s 级 | 几十~几百微秒 |
| 网络存储（NFS/iSCSI） | 取决于网络与对端 | 受链路带宽限制 | 通常高于本地盘，且波动更大 |

**这些数字只用于建立直觉**：具体数值随型号、队列深度、块大小、是否直写、阵列缓存策略变化极大，**必须以 `fio` 实测为准**。用错量级会得出荒唐结论（例如「NVMe 的 800 IOPS 很正常」）。

```bash
fio --name=randread --filename=/dev/<dev> --ioengine=libaio --direct=1 \
    --rw=randread --bs=4k --iodepth=32 --numjobs=4 --size=4G --runtime=60 --group_reporting
                                     # 验证：随机读 IOPS 与延迟分布（基线要记录 iodepth/numjobs/bs 条件）
fio --name=seqwrite --filename=/dev/<dev> --ioengine=libaio --direct=1 \
    --rw=write --bs=1M --iodepth=8 --numjobs=1 --size=8G --runtime=60 --group_reporting
                                     # 验证：顺序写带宽（机械盘与 SSD 差异最大的项目）
```

> [!warning] `fio` 会打满设备
> **只能在实验机或已下线的盘上跑**。生产上优先使用历史监控数据与 `iostat` 采样复盘；确需在生产做压测，必须经过变更评审并选好业务低谷。

## 5. 这一层的调优项与代价

| 调优项 | 收益 | 代价与前提 |
| --- | --- | --- |
| 提高 `read_ahead_kb` | 顺序读吞吐提升 | 随机读场景浪费带宽与缓存 |
| 提高 `nr_requests` | 高并发下减少排队 | 队列过长会放大延迟（`aqu-sz` 上升） |
| 切换调度器 | 按介质/业务匹配 | 需实测；持久化要 udev 规则 |
| 挂载选项 `noatime` | 减少元数据写入 | 依赖访问时间的备份工具会受影响 |
| 应用改批量/异步写 | 减少请求数与 `fsync` 次数 | 要改应用，属于跨团队动作 |
| 换成 NVMe 或加阵列缓存 | 根本性提升 | 成本；阵列缓存要关注 BBU/电容状态（子笔记 08） |

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 「`iostat` 里 `%util` 100% 就是盘饱和」 | NVMe 多队列下常见 100% 却远未饱和；要看 `await`、`aqu-sz` 与延迟分位 |
| 在 NVMe 上把调度器改成 `bfq` | 吞吐下降；NVMe 通常更适合 `none` |
| 在机械盘上用 `none` | 失去请求合并与排序，随机 IO 更差 |
| 认为「写很快 = 落盘很快」 | 默认写先进 Page Cache；`fsync` 才保证落盘，`dd conv=fsync` 与不带它差别巨大 |
| 只看 IOPS 不看块大小与队列深度 | 4K 随机与 1M 顺序是完全不同的测试，条件不齐的数据不可比 |
| 在生产盘上跑 `fio` | 会打满设备影响业务；压测只能在实验机或已下线盘上做 |
| 拿网上抄来的调度器名字直接改生产 | 介质与业务模式不同，效果可能相反；必须实测对比 |
| 忘记持久化调度器改动 | 直接写 `/sys` 只对本次运行有效，重启即恢复 |
| 忽略阵列卡缓存与电池状态 | 写缓存策略会显著影响写延迟与数据安全（掉电丢写） |

## 决策练习

> [!question]- 场景：一台数据库服务器的数据盘是 NVMe，同事说「网上教程讲 `bfq` 能保证公平性，我们把调度器改成 `bfq` 吧」。你怎么回应？
> A. 同意：公平性听起来对数据库有好处
> B. 先说明现状：NVMe 是多队列设备，`none` 通常是最优选择（把调度交给硬件）；`bfq` 的价值在桌面交互与按 cgroup 分配带宽，在高吞吐设备上会降低吞吐。要改就先在实验机上用与业务相似的 `fio` 模式做前后对比，再决定是否持久化
> C. 改成 `mq-deadline`，因为它是「通用默认」
>
> **答案：B。**
> A 与 C 都是「没测就改」：调度器效果强依赖介质与业务模式，**同一台机器上不同设备的最优选择可能不同**。
> B 是正解：**先确认机制（多队列 vs 单队列、介质类型），再测，再改**。这也是 M6 的训练要求——改参数前必须有基线。

## 要点自测

> [!question]- 一次 IO 要经过哪些层？哪些层可以被调优？
> - 应用 → 系统调用/VFS → 文件系统 → Page Cache → 块层（blk-mq）→ 调度器 → 驱动 → 硬件。
> - 可调：应用写入模式、挂载选项、回写参数、队列深度与预读、调度器、阵列缓存策略；介质能力只能靠换硬件。
> - **第一反应不要是什么**：不要以为「磁盘慢」只能在磁盘层解决——上层每一层都可能造成它。

> [!question]- 为什么老一代的 `cfq`/`deadline`/`noop` 在某些发行版上看不到了？
> - 因为块层换成了 **blk-mq 多队列**架构，单队列时代的调度器不再适用。
> - RHEL 8/9 上能选的是 `none`、`mq-deadline`、`kyber`、`bfq`。
> - **第一反应不要是什么**：不要照抄旧文档里的 `cfq` 调优方案。

> [!question]- 读和写在 IO 路径上的最大差别是什么？
> - 读命中 Page Cache 就返回，不碰设备；写在默认模式下先进缓存并立刻返回，落盘由回写异步完成。
> - 所以「写快」不等于「落盘快」；要确认落盘必须 `fsync`。
> - **第一反应不要是什么**：不要用不带 `fsync` 的 `dd` 结果去评估持久化能力。

> [!question]- 介质量级表有什么用？
> - 用来判断一个观测值是「正常」还是「离谱」：机械盘百级 IOPS、NVMe 十万级以上。
> - 但具体数值随型号与测试条件差异极大，**基线必须实测**（子笔记 12）。
> - **第一反应不要是什么**：不要把量级表当验收标准，也不要在生产盘上跑 `fio` 取基线。
