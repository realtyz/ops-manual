# 文件系统的结构与选型

## 1. 文件系统要解决的问题

块设备的能力只有一条：**按块号读写**。把这个能力变成「文件」需要额外四件事，缺一件就用不了：

- **按名字找到内容**。应用说 `/data/a.txt`，内核要能把它换成「哪个设备上的哪些块」。这需要一层「名字 → 元数据 → 数据块」的映射。
- **知道哪些块是空的**。每次写入都要问「哪块地方没人用」，这需要空闲空间的记账结构。
- **让一次改动能被撤销或重放**。改一个文件往往要同时改好几处元数据（分配 inode、改位图、加目录项、更新总账）。中途断电会留下一套自相矛盾的结构，下次挂载就挂不上。
- **在损坏后能被检查**。任何一套复杂结构都需要一个「自检」入口，否则一次坏块就报废整个文件系统。

格式化（`mkfs`）的本质就是**一次性写下这套账本与规则**。它由五个构件组成：

| 构件 | 存什么 | 出问题时的典型现象 |
| --- | --- | --- |
| 块（block） | 文件内容本身，按固定大小切分（常见 4 KiB，与内核页大小一致） | 块太小则顺序读差；块太大则小文件浪费空间 |
| inode（索引节点） | 一个文件的**元数据**：类型与权限、属主属组、三个时间戳、链接数、大小、指向数据块的指针 | inode 用尽 → 「有空间却写不进去」 |
| 目录项（dentry） | 「文件名 → inode 号」的映射 | 目录里文件过多会拖慢查找；软链接断裂 |
| 超级块（superblock） | 文件系统总账：块数、inode 数、状态、特性、日志位置 | 损坏 → 挂不上，需要靠备份超级块救援 |
| 日志（journal） | 元数据变更的流水（部分模式也记数据） | 损坏 → 需要重放或丢弃，而丢弃有数据代价 |

两个必须记住的结构事实：

**inode 里没有文件名。** 名字在目录项里。这解释了三件常被误解的事：为什么硬链接的两个名字指向同一个 inode 号；为什么重命名一个文件不改变它的 inode；为什么「文件名」不占 inode 的空间预算，而它所在的目录会持续长大。

**这三个大小不相等，而且是设计使然。** `ls -l` 报的是 inode 里的表观字节数，`du` 统计的是真正分配的块数，`df` 报的是超级块的记账。稀疏文件（有空洞的文件）、小于一个块的文件、写时复制共享的块，都会让前两个数字分开。「`df` 与 `du` 对不上」在机制层面是正常的，需要解释的是**差在哪一类**，而不是断定某个工具错了。

## 2. ext4 与 XFS 的结构差异

两者都是日志文件系统，但把同样的概念摆在完全不同的结构上。差异集中在四处：

| 方面 | ext4 | XFS |
| --- | --- | --- |
| 空间组织 | 切成**块组（block group）**，每组自带 inode 表与位图，超级块有多份备份 | 切成**分配组（AG，Allocation Group）**，每个 AG 独立管理空闲空间与 inode |
| inode 分配 | `mkfs` 时**按固定数量预分配**，`df -i` 显示总量 | **动态分配**，随需要增长，总量随使用上升 |
| 空闲空间索引 | 位图 + 块组 | B+ 树（按大小与位置索引），大容量下查找更稳定 |
| 大目录与高并发 | 通用够用；超大目录与极高并发不如 XFS | 大容量、大文件、高并发写入是设计强项 |

**分配组的意义**：XFS 把空间切成若干 AG 之后，多个写入者可以**并行**在各自的 AG 里分配，而不必争抢同一张全局位图。这就是 XFS 在高并发写入与大容量下更稳定的结构原因，也是 XFS 不能缩容的结构原因——**缩容意味着跨越所有 AG 重新分配空间，代价与风险都不可接受**。

选型因此可以归结为三个问题，按顺序回答：

1. **这台机器会不会缩容？** 会（且能停机）→ 只能 ext4；不会 → 继续。
2. **会不会有海量小文件（几十万以上）？** 会 → XFS（动态 inode 避开耗尽）；不会 → 两者都行。
3. **容量会不会长到几十 TiB？** 会 → XFS 配合 LVM，扩容链路最顺。

生产上常见的组合是「XFS + LVM」：LVM 负责把容量长大，XFS 负责在线扩大文件系统，**整条链路没有一步需要缩容**，正好绕开两者的短板。反过来说，只有「ext4 + LVM」能提供缩容能力，代价是必须卸载文件系统。

**`mkfs` 时定下、以后改不了的参数**值得单独记：块大小、ext4 的 inode 密度（`-i`，即每多少字节给一个 inode）、XFS 的 AG 数量与部分特性（如 `reflink` 写时复制、`bigtime` 大时间戳）。**想改这些等于重建文件系统**（备份 → 重建 → 恢复），没有对应的在线调参手段。相反，ext4 的保留比例（`-m`）、自动检查周期、出错行为都可以事后调整。

**建文件系统会立刻清空目标设备。** 它会覆盖原有的分区签名与文件系统元数据，恢复代价极高，所以只应当在**已确认无数据、且能回退的实验环境或被回收下线的盘**上执行。判断这块盘能不能动，靠的是事先读到的签名与分区信息，不是「它看起来是新的」。

## 3. inode 会耗尽，块不会

ext4 的 inode 总量在 `mkfs` 时就确定了。这带来一个与直觉相反的现象：**块还剩很多，inode 已经用光**。典型元凶都是「文件多」而不是「文件大」——会话文件、邮件队列、缓存目录、容器可写层、日志切片、CI 的工作目录。

「文件大」和「文件多」是两种故障，消耗两本不同的账：

| | 文件大 | 文件多 |
| --- | --- | --- |
| 消耗 | 数据块 | inode |
| 观测量 | 容量使用率上升 | **inode 使用率上升而容量使用率不动** |
| 报错 | `ENOSPC`（`No space left on device`） | 同一个 `ENOSPC` |
| 短期处置 | 清理或扩容 | 清理过期小文件 |
| 长期处置 | 扩容 | 换 XFS，或重建 ext4 并调小每 inode 字节数 |

**注意报错文本相同**——`ENOSPC` 只说明「文件系统上没有可用资源」，不区分是块还是 inode。只监控容量不监控 inode，这类故障一定会漏，而且在 ext4 上往往**比容量先满**。

扩容能不能解决 inode 耗尽，要分开说清楚，这是最容易混淆的一点：

- `resize2fs` 扩大 ext4 时**会按原有比例新增 inode**（ext4 的 inode 数本质上是「总块数 × 每多少字节一个 inode」推出来的）。所以「扩容到两倍」通常确实能让 inode 用量降下来；
- 但它**没有改变这个比例**。同样的海量小文件增长下去，迟早再次撞满；
- 而且扩容的代价是动存储，比清理过期文件高得多。

因此正确的答案是三件事一起做：**短期清理、长期换文件系统或重建、监控补上 inode 水位**。任何只做其中一件的方案都会复发。

XFS 的动态 inode 分配几乎不会出现这类故障，但这不等于「XFS 的 inode 无限」——它通过 `maxpct`/`imaxpct` 限制 inode 可占用的空间比例，只是默认值足够宽松，正常负载碰不到。

一个常见疑问：既然 inode 是预分配的，为什么 ext4 的 `df -i` 在某些场景下仍显示「总量在变」？答案是不会变——`df -i` 显示的是**总量与已用量**，只是有些发行版在扩容后会重新计算并显示新的总量。判断「这个文件系统会不会 inode 耗尽」看的是总量与已用量的比值，以及是否有大量小文件在持续产生。

## 4. 删除一个文件，与空间什么时候回来

删除操作在磁盘上分两步，顺序固定：

1. **从目录项里移除那个名字，inode 的链接数减一**；
2. **只有当链接数归零，并且没有任何进程持有它的打开句柄时**，才释放 inode 与数据块。

第 2 步的附加条件是一切「删了文件空间不释放」的来源。进程用 `open` 拿到的是**文件对象的引用**，不是路径；路径被移除后，文件对象与它的数据块仍然存在，直到最后一个句柄关闭。期间：

- 超级块记账不变，所以 `df` 的用量不下降；
- 目录树里已经没有它，所以 `du` 找不到；
- **只有查进程的打开句柄才能找到持有者**。

这是「机制正确、现象反直觉」的典型：从文件系统的角度看，没有任何东西需要释放；从空间管理的角度看，那块空间确实回不来。处置方向因此不是「再删一遍」（对象已经不存在），而是**让持有者关闭句柄**——重启或重载该进程，或在评估数据风险后截断对应的句柄。

同一机制还解释了另外两件事：**硬链接不占新空间**（只是增加链接数），**而 `mv` 在同一文件系统内是瞬时的**（只改目录项，不动数据）。

## 5. 日志：为什么崩溃之后还能挂上

写一个文件通常要改多处元数据。如果改到一半断电，磁盘上会留下一套自相矛盾的结构——超级块说这块空间已分配，位图说它是空的，目录项指向一个不存在的 inode。

日志（journal）的做法是**先把「要改什么」顺序写进一块连续的日志区，再回头改真正的元数据**。顺序写很快，而且日志区在物理上连续，写它的代价可控。

崩溃后重新挂载时，内核扫描日志并**重放（replay）**：把已经提交但没改完的变更补齐，或把没提交的变更撤销。结果是文件系统回到一个**一致**的状态——不是「未受损」的状态。

这引出三条边界，每一条都在排障里会用到：

- **重放保证一致性，不保证数据完整性**。日志里可能只有元数据（ext4 的默认 `data=ordered`、XFS 的做法），正在写入的文件内容可能有部分丢失。日志**不是备份**，也救不回误删的文件。
- **大多数崩溃后重启不需要人工修复**。挂载时内核会自动重放日志，失败才需要手动介入。**看到文件系统「脏」就急着硬修，可能把本来能自动恢复的状态改坏。**
- **修复工具与日志是两条不同的路径**。修复工具直接改写磁盘上的元数据结构，所以**必须在文件系统未挂载（或至少只读）的状态下运行**；挂载着修，内核的元数据缓存与工具的改写会互相覆盖。XFS 的 `xfs_repair` 默认就对已挂载设备直接拒绝——这是保护设计，不是缺陷。

XFS 有一条只有它有的选项：`xfs_repair -L` 会**丢弃（清空）日志**。它用在「日志损坏到无法重放」的场景，代价是日志里那些尚未落盘的元数据变更**永久丢失**。只有在日志确实损坏、且已有可用备份时才考虑。ext4 侧的对应风险点是 `e2fsck -y`：它的含义是「所有问题都自动回答 yes」，在元数据自相矛盾时，工具的选择可能是删掉「有数据的那一边」。**先只读检查看清规模，先备份，再决定是否让它自动回答。**

## 常见误解

| 常见说法 | 事实 |
| --- | --- |
| 「文件名存在 inode 里」 | 名字在目录项里；inode 只有名字之外的一切，这也是硬链接能共用一个 inode 的原因 |
| 「inode 满了就是容量满了」 | 两者是两本账；ext4 上 inode 用尽时容量可能还剩很多，报错却同为 `ENOSPC` |
| 「扩容一定能解决 inode 耗尽」 | 扩容会按比例增加 inode，能缓解但改不了比例，也没有改变海量小文件的根因 |
| 「`lvextend` 之后 inode 也会变多」 | inode 是文件系统的结构，与 LVM 层无关；要扩的是文件系统本身 |
| 「删了文件空间立刻回来」 | 只有链接数归零**且**没有进程持有句柄时才释放 |
| 「日志是数据备份」 | 日志只保证一致性；它不保护数据内容，也不救误删 |
| 「文件系统脏了就直接 `-y` 硬修」 | 挂载时通常能自动重放；盲目硬修可能把可恢复状态改坏 |
| 「修复可以在挂载状态下做」 | 修复工具直接改写磁盘元数据，与内核缓存互相覆盖；必须卸载或至少只读 |
| 「XFS 也需要定期 `fsck`」 | XFS 没有 ext4 那种按挂载次数或间隔自动检查的机制；`xfs_repair` 只在出问题时用 |
| 「`du` 比 `df` 小说明 `du` 不准」 | 两者量的是不同的东西；差异有四类，需要说明差在哪一类 |

## 要点自测

**问：inode 里存了什么、不存什么？**
答：存类型与权限、属主属组、三个时间戳、链接数、大小与块指针（ext4 用 extent，XFS 用 B+ 树）。不存**文件名**（在目录项里）与**文件内容**（在数据块里）。

**问：ext4 与 XFS 的结构差异，如何决定「inode 会不会耗尽」和「能不能缩容」？**
答：ext4 按固定数量预分配 inode，因此会耗尽，也因此可以在卸载状态下重建元数据结构实现缩容；XFS 把空间切成多个 AG 独立管理、inode 动态分配，因此不会耗尽，但跨越所有 AG 的重新分配代价不可接受，所以不支持缩容。

**问：删除一个文件时，空间在什么条件下才真正释放？**
答：目录项移除、链接数减一；**链接数归零且没有进程持有打开句柄**时才释放 inode 与数据块。持有者存在时 `df` 不降、`du` 找不到，只有查进程句柄才能定位。

**问：日志重放解决了什么、没解决什么？**
答：解决了「结构自相矛盾」——它把已提交的元数据变更补齐，让文件系统回到一致状态。没解决数据内容完整性（只记元数据的模式下），也救不回误删，**它不是备份**。

**问：为什么修复工具必须在卸载状态下运行？**
答：它直接读改磁盘上的元数据结构；可写挂载时内核手里还有一份元数据缓存会继续读写，两边互相覆盖，结果是「修完更坏」。XFS 默认拒绝对已挂载设备操作，正是把这条纪律做进了工具。

**第一反应不要做什么**：不要把 `ENOSPC` 一律当容量问题；不要在 inode 告警时先去扩容；不要用「再删一遍」解决空间不释放；不要把日志当备份；不要在挂载状态下跑修复工具；不要把 `-y` 当默认选项。
