## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **inode 存元数据，块存内容**：文件名存在**目录项**里，inode 里只有「名字之外的一切」和指向数据块的指针。
> - **ext4 的 inode 是「建文件系统时定好数量」**：块还剩很多但 inode 用光是完全可能的；**XFS 的 inode 是动态分配的**，几乎不会出现这种故障。
> - **删除 = 减链接数 + 释放 inode 与数据块**；**只要还有进程打开着它，数据块就不会被释放**（这就是「删了文件空间不下降」）。
> - **日志（journal）是元数据变更的流水账**：崩溃后靠重放日志恢复一致性；文件系统被弄脏时内核会把它重挂成只读，而不是继续写。
> - **同一个文件有三个「大小」**：`ls -l` 的表观大小、`du` 占用的块数、`df` 记账的用量——它们本来就可能不一样（稀疏文件、延迟分配）。

## 1. 文件系统把盘切成了什么

格式化（`mkfs`）的本质是：**在块设备上写下一套「谁能用哪些块、文件对应哪个 inode」的账本与规则**。它的基本构件只有五样：

| 构件 | 存什么 | 出问题的典型现象 |
| --- | --- | --- |
| 块（block）/ 簇 | 文件内容本身，按固定大小切分（ext4 常见 4KiB） | 块大小选小了顺序读差，选大了小文件浪费空间 |
| inode | 一个文件的元数据：权限、属主、时间戳、大小、链接数、块指针 | inode 耗尽 → 「有空间却写不进去」 |
| 目录项（dentry） | 「文件名 → inode 号」的映射 | 目录里文件太多会拖慢查找；软链接断裂 |
| 超级块（superblock） | 文件系统总账：块数、inode 数、状态、特性、日志位置 | 超级块损坏 → 挂不上，要靠备份超级块救援 |
| 日志（journal） | 元数据变更的流水（有的模式也记数据） | 日志损坏 → 需要重放或丢弃（`xfs_repair -L` 有风险） |

```bash
sudo dumpe2fs -h /dev/<dev> | head -30                      # 验证：ext4 的超级块：块数、inode 数、特性、日志
sudo tune2fs -l /dev/<dev> | grep -E 'Block count|Inode count|Block size|Filesystem state|Journal'
                                     # 验证：ext4 总账（含预留块与文件系统状态）
sudo xfs_info /mountpoint            # 验证：XFS 的 AG（分配组）数量、块大小、inode 分配策略、日志设备
stat <file>                          # 验证：单个文件的 inode 号、权限、时间、块数与表观大小
```

**块大小怎么选**（建文件系统时决定，之后改不了）：

- 常见的 **4KiB 是通用默认**：与内核页大小一致，小文件浪费可接受，顺序 IO 也不差。
- 大量**小文件**（几十万个小文件）可以考虑更小的块；**大文件顺序读写**为主（日志、备份、媒体）可以考虑更大的块，但浪费与对齐要求都上升。
- 现代 XFS 也支持 `reflink`（写时复制）与 `bigtime` 等特性，属于进阶话题，生产上除非业务明确需要，否则用发行版默认参数。

## 2. inode：为什么它会「用完」

inode 的字段里**没有文件名**——名字在目录项里。一个 inode 通常包含：

| 字段 | 含义 | 相关命令与现象 |
| --- | --- | --- |
| 类型与权限 | 普通文件/目录/软链接 + `rwx` | `ls -l`、`stat` |
| 属主与属组 | uid/gid | `chown`、`chmod`（见阶段 7） |
| 大小与块数 | 表观字节数 + 实际占用的 512B 块数 | `stat`、`du` |
| 三个时间戳 | access / modify / change | `ls -lu`、`ls -l`、`ls -lc` |
| 链接数 | 有多少个名字指向它 | `ls -l` 第二列 |
| 块指针 | 指向内容所在的数据块（ext4 用「extent」，XFS 用 B+ 树） | 决定了「大文件也只是一个 inode」 |

关键差异：

| | ext4 | XFS |
| --- | --- | --- |
| inode 从哪来 | `mkfs` 时按「每个多少字节给一个 inode」预先分配，`df -i` 能看到总量 | **动态分配**（分配在 AG 里），`df -i` 的总量随使用增长 |
| 会不会耗尽 | **会**：小文件写爆 inode 是经典故障 | 基本不会；除非 `imaxpct`/`maxpct` 限制 |
| 能调吗 | `tune2fs` 可调部分参数；新增 inode 需要 `resize2fs` 等操作 | 通过 `maxpct`/`imaxpct` 影响分配 |
| 怎么查 | `df -i`、`tune2fs -l` | `df -i`、`xfs_info`、`xfs_db -c 'freesp'` |

```bash
df -h; df -i                         # 验证：容量视角与 inode 视角必须一起看（详见子笔记 09）
du --inodes -s /var/* 2>/dev/null | sort -rn | head -10
                                     # 验证：按 inode 数找出「文件最多的目录」
sudo tune2fs -l /dev/<dev> | grep -E 'Inode count|Free inodes|Inode size'
                                     # 验证：ext4 的 inode 总量、剩余与 inode 大小
                                     # 注意：tune2fs -l 里没有「Bytes per inode」字段（本机实测 grep 计数为 0），
                                     #       要算「每个 inode 摊到多少字节」得用 Inode count 与总块数自行相除
```

> [!important] 「文件多」和「文件大」是两种故障
> **文件大**消耗块，现象是 `df -h` 涨；**文件多**消耗 inode，现象是 `df -i` 涨而 `df -h` 还很空。缓存目录、session、mail spool、容器可写层、日志切片都是「文件多」的重灾区。**监控只报容量不报 inode，这类故障一定会漏。**

## 3. ext4 与 XFS：同样的概念，不同的摆法

| 维度 | ext4 | XFS |
| --- | --- | --- |
| 元数据结构 | 把盘切成**块组**，每组有自己的 inode 表与位图；超级块有多个备份 | 把盘切成**分配组（AG）**，每个 AG 自带空闲空间与 inode 管理，天然并行 |
| inode 分配 | 预先固定数量 | 动态分配 |
| 空闲空间 | 位图 + 块组 | B+ 树（空闲空间按大小与位置索引） |
| 大文件与并发 | 单目录、超大文件、极高并发下不如 XFS | 大容量、大文件、高并发写入是强项 |
| 典型用途 | 系统盘、通用小盘、需要缩容的场景 | 数据盘、日志盘、容器存储后端、海量 inode |
| 修复工具 | `e2fsck` | `xfs_repair`（**默认拒绝操作已挂载设备**） |
| 扩容 | 在线（`resize2fs`，参数是**设备**） | 在线（`xfs_growfs`，参数是**挂载点**） |
| 缩容 | 支持，但**必须卸载**且有风险 | **完全不支持** |

一句话记住选择逻辑：**「会不会缩容」决定选谁，「要不要长大」决定用不用 LVM**。生产上最常见的是「XFS + LVM」——扩容链路里没有一步需要缩容，正好绕开两者的短板。

## 4. 日志：为什么崩溃后还能挂上

写一个文件往往要改好几个元数据（分配 inode、改位图、加目录项、更新超级块记账）。如果改到一半断电，文件系统就会处于**自相矛盾**的状态。

日志的做法是：**先把「要改什么」写进日志区（顺序写，很快），再回头改真正的元数据**。崩溃后重新挂载时，内核会把日志重放（replay）一遍，把没做完的变更补齐或撤销。

| | ext4 | XFS |
| --- | --- | --- |
| 日志位置 | 可以放在同盘的 inode 区（默认），也可以放在独立设备上 | 默认在**数据区内部的日志段**，也可以指定外部日志设备 |
| 日志模式 | `data=ordered`（默认，数据先落盘再提交元数据）、`data=writeback`、`data=journal` | 只记元数据（相当于 `ordered` 思路） |
| 查日志 | `dumpe2fs -h` 的 `Journal inode`、`journalctl -k` 的 `recovery` 记录 | `xfs_info` 第一行的 `log` 段、`dmesg` 的 XFS 日志重放记录 |
| 与修复的关系 | 能重放就别用 `-y` 硬修 | **`xfs_repair -L` 会丢弃日志**，可能丢数据 |

```bash
dmesg -T | grep -i -E 'ext4.*(recovery|error)|XFS.*(log|error)' | tail -20
                                     # 验证：内核是否做过日志重放、有没有报过错
sudo dumpe2fs -h /dev/<dev> | grep -i -E 'state|errors behavior|check interval|mount count'
                                     # 验证：ext4 的干净状态、出错行为与自动检查策略
```

> [!tip] 第一反应不要是「文件系统脏了就直接 `-y` 硬修」
> 大多数崩溃场景**只要挂载一次，内核就会自动重放日志**，根本不需要修复。安全的顺序永远是：先 `dmesg -T`/`journalctl -k` 看内核报了什么 → 能挂就先挂（只读）→ 挂不上再卸载 → **先干跑检查**（`e2fsck -n` / `xfs_repair -n`）→ 备份后正式修（子笔记 13）。

## 5. 写入、删除、落盘：三次「磁盘上发生了什么」

**写一个小文件**：分配 inode → 在目录项里加「名字 → inode 号」→ 写入数据块（可能先在 Page Cache 里攒着，稍后回写）→ 更新位图与记账 → 元数据变更进日志。

**删除一个文件**：目录项里减一个链接、inode 的链接数减一；**链接数归零且没有进程打开时**，才释放 inode 与数据块。

```bash
ls -li <file>                        # 验证：第一个字段是 inode 号，硬链接之间 inode 号相同
ln <file> <hardlink>; ls -li <file> <hardlink>   # 验证：硬链接只增加链接数，不占新数据块
lsof +L1 2>/dev/null | head          # 验证：所有「已删除但仍被打开」的文件（链接数为 0 但没释放）
df -h <挂载点>; du -sh <挂载点>       # 验证：删除后空间是否真的释放（不降 = 有进程还持有）
```

**落盘（持久化）**：数据先进 Page Cache，由内核异步回写（阶段 4 讲过回写的参数与卡顿），应用要「确定落盘」必须自己调 `fsync`/`fdatasync`。这也是为什么 `dd` 加不带 `conv=fsync` 的写法**测不出真实写入速度**。

```bash
dd if=/dev/zero of=/data/t bs=1M count=512 conv=fsync   # 验证：带 fsync 的真实写入
sync                                                     # 验证：把系统里所有脏页推下去（耗时即为回写压力）
```

## 6. 三个「大小」口径

| 口径 | 命令 | 量的东西 |
| --- | --- | --- |
| 表观大小 | `ls -l`、`stat %s`、`du --apparent-size` | 文件「声称」有多少字节，稀疏文件的空洞也算 |
| 实际占用 | `stat %b`（512B 块数）、`du` | 真正分配了多少块（**稀疏文件、压缩、reflink 会小很多**） |
| 文件系统账本 | `df` | 超级块记账的已用/可用块，包含元数据与保留块 |

```bash
du -h --apparent-size <file>; du -h <file>    # 验证：稀疏文件两个口径的差别
stat -f <挂载点>                               # 验证：文件系统级的块数、空闲块、inode 数（与 df 同源）
```

这三个口径的差异是「`df` 与 `du` 对不上」的技术来源之一，完整的四类原因与判定顺序放在子笔记 09。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 「文件名存在 inode 里」 | 文件名在目录项里；inode 里没有名字，这也是硬链接能指向同一个 inode 的原因 |
| 认为「删了文件空间立刻回来」 | 只要有进程还打开着它，数据块就不会释放，要等进程关闭或重启（子笔记 09） |
| 只用 `df -h` 监控容量 | ext4 上 inode 往往比容量先满；`df -i` 必须一起进监控 |
| 把 `ls -l` 的大小当成磁盘占用 | 稀疏文件与压缩/重删场景下两者差别巨大；占用要看 `du`/`stat %b` |
| 崩溃后就急着 `e2fsck -y` | 内核挂载时通常能自动重放日志；盲目硬修可能把可恢复的状态改坏 |
| 在 `mkfs` 之后才纠结块大小 | 块大小（以及 XFS 的 AG 数）是建文件系统时定下的，之后改不了 |
| 认为 XFS 也需要「定期 fsck」 | XFS 没有同类检查策略；`xfs_repair` 只在出问题时用，且必须卸载 |
| 用 `dd conv=fsync` 之外的方式测写入速度 | 不带 `fsync` 时数据还在 Page Cache 里，测出来是内存速度 |

## 决策练习

> [!question]- 场景：某应用目录里有一百多万个小文件，`df -h` 显示用了 30%，但应用报 `No space left on device`。文件系统是 ext4，`df -i` 显示 100%。业务方说「空间还有 70%，能不能把限制放开？」
> A. 扩容量：把文件系统扩到两倍，inode 也会跟着变多
> B. 先说明机制：ext4 的 inode 数与「容量 × bytes-per-inode 比例」绑定，**扩容（`resize2fs`）会按同一比例新增 inode**，但改不了这个比例；短期靠清理过期小文件，长期要么换 XFS（动态分配 inode），要么重建 ext4 并给更小的 `bytes-per-inode`；同时把 `df -i` 纳入监控
> C. 直接删掉一半文件，先让业务跑起来
>
> **答案：B。**
> A 只说到一半：`resize2fs` 扩容**确实会**按原有比例新增 inode（ext4 的 inode 数 = 容量 × 比例，不是「扩容不增加 inode」），所以「扩到两倍」通常真能让 inode 用量降下来；但它代价高（要动存储）、而且**没有改变 bytes-per-inode 这个根因**——同样的海量小文件迟早会再次撞满，所以它不是完整答案。附带纠正一个常见误解：**ext4 扩容（grow）可以在线做、不需要停机卸载**（只有**缩容**才必须卸载）。
> C 只做了「止血」，没有说明「为什么会满」——不加上过期清理策略，一周后必然复发。
> B 是正解：**先把机制讲清，再给短期止血 + 长期治理 + 监控补齐三条**。这也是 M2「空间账核对」的典型考法。

## 要点自测

> [!question]- inode 里存了什么，不存什么？
> - 存：类型与权限、属主属组、三个时间戳、链接数、大小与块指针（ext4 的 extent / XFS 的 B+ 树）。
> - 不存：**文件名**（在目录项里）与**文件内容**（在数据块里）。
> - **第一反应不要是什么**：不要把 inode 当成「文件头」——它不含名字，也不含数据本身。

> [!question]- 删除一个文件在磁盘上发生了什么？为什么空间有时不释放？
> - 目录项移除、inode 链接数减一；**链接数归零且没有进程打开**时才释放 inode 与数据块。
> - 只要有进程还持有 fd，数据块就继续被占用：`df` 不降、`du` 找不到、`lsof +L1` 能找到持有者。
> - **第一反应不要是什么**：不要用「再删一遍」解决，重启/重载持有进程才会释放。

> [!question]- 日志是干什么的？它和「修复必须卸载」有什么关系？
> - 日志是元数据变更的流水，先写日志再改元数据，崩溃后重放即可恢复一致性。
> - 修复工具直接改写元数据结构，如果文件系统还挂着且可写，内核缓存与工具改写会互相覆盖；所以必须卸载（或至少只读）再修。
> - **第一反应不要是什么**：不要把日志当成数据备份——它只保证一致性，不保证你误删的文件能回来。

> [!question]- ext4 与 XFS 在 inode 上的差别，为什么会影响「扩容能不能解决问题」？
> - ext4 的 inode 数量是 `mkfs` 时预分配的（`df -i` 显示总量），扩容量通常只按比例增加，不能任意变多；XFS 动态分配，几乎没有 inode 耗尽问题。
> - 所以「inode 满了」的长期解法是换 XFS 或重建 ext4 并调小 `bytes-per-inode`，而不是单纯扩容。
> - **第一反应不要是什么**：不要把 inode 问题当成容量问题去扩容。
