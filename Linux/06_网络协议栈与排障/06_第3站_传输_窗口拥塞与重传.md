## 0. 30 秒速览

> [!abstract] 这一篇只要记住六句话
> - **可靠传输的三件套：序号 + 确认 + 重传**。TCP 通过重传「补上」丢掉的段，通过窗口决定「一次能发多少」，通过拥塞控制决定「网络允许我发多快」。
> - **两个窗口，取小者生效**：`rwnd`（接收方通告的能收多少，防把对方缓冲打爆）与 `cwnd`（发送方估计的网络容量，防把链路压垮）。**`cwnd` 小 + `minrtt` 大 = 典型的「窗口受限」**。
> - **BDP = 带宽 × RTT**：高延迟链路要「跑满带宽」，就必须有足够的在途数据量；不够时表现为「带宽没用满但单流上不去」——这就是缓冲区（`tcp_rmem`/`tcp_wmem`）与窗口缩放存在的意义。
> - **`ss -ti` 是「不抓包看链路」的主力**：`rtt`/`minrtt`/`cwnd`/`retrans`/`pacing_rate`/`delivered`/`app_limited` 一次拿全，**不需要在生产上抓包**。
> - **看到 `app_limited` 就先去查应用**：它明确表示「应用没把连接喂满」，此时网络侧做什么都没用。这是把「网络慢」与「应用慢」分开的最快手段。
> - **`cubic` 与 `BBR` 的判据不同**：前者以丢包为拥塞信号，后者用带宽与 RTT 的估计建模；**有随机丢包的长肥链路 BBR 常有收益，但需要 `fq` 做 pacing，且不是所有场景都提升**。

## 1. 前置：TCP 为什么能「可靠」

### 1.1 三个机制

| 机制 | 解决什么 | 在 `ss -ti` 里怎么看 |
| --- | --- | --- |
| **序号与确认** | 乱序、丢包、重复都能被识别 | `segs_in`/`segs_out`、`delivered` |
| **重传** | 丢了就再发一次 | `retrans`/`lost`、`rto` |
| **滑动窗口** | 一次能发多少在途数据（流控） | `snd_wnd`(对端通告)/`rcv_space`(本端可收)、`wscale` |
| **拥塞控制** | 网络能承受多快（避免把链路压垮） | `cwnd`、`pacing_rate`、算法名（`cubic`/`bbr`） |

### 1.2 两个窗口：谁更小谁说了算

```text
发送方真正能发多少在途数据 ≈ min(cwnd, rwnd)

cwnd  ← 发送方自己估的「网络能承受多少」（拥塞控制）
rwnd  ← 接收方通告的「我还能收多少」（流控，ss -ti 里是 snd_wnd）
```

- **`rwnd` 变小甚至为 0**：接收方来不及读（应用慢、缓冲区小），发送方被「憋住」。`ss -ti` 里 `snd_wnd` 很小或为 0 就是证据。
- **`cwnd` 变小**：发送方认为链路拥塞（丢包或 RTT 上升），主动降速。高 RTT 链路上 `cwnd` 需要很大才能跑满带宽（BDP 的概念）。
- **`app_limited`**：发送方没有数据可发——**根本还没轮到网络层出力**。

### 1.3 拥塞控制的四个阶段（够用版）

新人先建立这四个动作的直觉即可，不需要背公式：

1. **慢启动**：刚建连时从小窗口开始，每收到一个 ACK 就把 `cwnd` 增大，快速探到链路容量。
2. **拥塞避免**：接近估计容量后改为缓慢增长，避免过冲。
3. **丢包检测与降速**：`cubic` 把丢包当成拥塞信号，`cwnd` 大幅回退；这正是「有随机丢包的链路上 cubic 表现差」的原因。
4. **恢复**：逐步重新增长。**BBR 换了一种判据**：它持续估计「瓶颈带宽」与「最小 RTT」，据此决定发送速率，而不是「丢包即降速」。

## 2. `ss -ti` 逐字段读法

```bash
ss -ti                                  # 验证：所有连接的拥塞控制细节（关键字段见下表）
ss -ti dport = :443                     # 验证：只看某个服务（也可用 sport/state 组合过滤）
ss -tinp                                # 验证：加上进程与定时器信息
```

```text
ESTAB 0 0 10.0.0.1:9998 10.0.0.2:39548
	 cubic wscale:7,7 rto:204 rtt:0.011/0.005 mss:1448 pmtu:1500 rcvmss:536 advmss:1448
	 cwnd:10 segs_in:2 send 10.5Gbps lastsnd:1992 lastrcv:1992 lastack:1992
	 pacing_rate 21.1Gbps delivered:1 app_limited rcv_space:14600 rcv_ssthresh:64076
	 minrtt:0.011 snd_wnd:64256
```

（以上为**实测输出**，环境见本篇开头：隔离 veth 上的空闲连接。）

| 字段 | 怎么读 |
| --- | --- |
| `cubic` / `bbr` | 当前拥塞控制算法 |
| `wscale:7,7` | 窗口缩放因子（发送/接收）；没有它就撑不起高 BDP 链路的窗口 |
| `rto` | 重传超时（毫秒）；丢包时用来判断「等多久才重传」 |
| `rtt:x/y` | 平滑 RTT / 波动（毫秒） |
| `minrtt` | 观测到的最小 RTT，**判断「路径基线」的最有价值字段**：与 `rtt` 差距大 = 有排队 |
| `mss` / `pmtu` / `advmss` | 协商到的 MSS / 当前路径 MTU / 本端通告的 MSS |
| `cwnd` | 拥塞窗口（以 MSS 计）；小 `cwnd` + 高 `minrtt` = 窗口受限 |
| `retrans` / `lost` | 出现即说明丢包重传（**空闲连接不显示这两个字段，说明没有重传**） |
| `pacing_rate` / `send` | 当前 pacing / 估算发送速率 |
| `delivered` | 已被确认的字节数 |
| `app_limited` | **应用没喂饱连接**——此时「变慢」不是网络问题 |
| `snd_wnd` / `rcv_space` | 对端通告窗口与本端接收窗口；窗口为 0 就是「对端不读」 |

> [!tip] 用 `ss -ti` 做「十分钟分层」的判据
> ① 有 `app_limited` → 去查应用（最常见）；② 有 `retrans`/`lost` 或 RTT 远大于 `minrtt` → 查链路丢包与排队；③ `cwnd` 小且 `minrtt` 大 → 查窗口/缓冲（`tcp_rmem`/`tcp_wmem`、`rmem_max`/`wmem_max`）或中间设备限速；④ `snd_wnd` 为 0 → 对端应用不读，问题在对端。
> **这四种情况的处置完全不同，所以第一步不是「调参数」，而是分类。**

## 3. 重传与丢包：用计数器说话

```bash
nstat -az | grep -E 'TcpRetransSegs|TcpExtTCPSynRetrans|TcpExtTCPTimeouts|TcpExtTCPLostRetransmit|TcpOutSegs'
                                        # 验证：全网重传/超时计数（TcpRetransSegs/TcpOutSegs 就是重传率）
nstat -r 2 | grep -E 'TcpRetransSegs|TCPTimeouts'   # 验证：每 2 秒刷新，观察是否在持续增长
```

| 计数器 | 含义 | 什么时候要警惕 |
| --- | --- | --- |
| `TcpRetransSegs` | 重传的段数 | 与 `TcpOutSegs` 的比值持续 > 0.1% 就值得查 |
| `TcpExtTCPSynRetrans` | SYN 的重传 | 增长说明握手阶段就有丢包（配合子笔记 05 的队列判据） |
| `TcpExtTCPTimeouts` | RTO 超时次数 | 大量出现说明链路质量或对端异常 |
| `TcpExtTCPLostRetransmit` | 重传也丢了 | 链路严重劣化 |

> [!warning] 重传率要看趋势，不要看单点
> 计数器从开机累计。**标准动作是留一份快照，过一段时间再比**（子笔记 03 的三分钟快照、子笔记 11 的基线模板）。单次 `nstat` 的数字不能说明「现在有问题」。

## 4. 拥塞控制算法的取舍

| 维度 | `cubic`（默认） | `BBR` |
| --- | --- | --- |
| 判据 | 基于**丢包**（丢包即认为拥塞） | 基于**带宽与 RTT 的估计**（模型驱动） |
| 适用链路 | 低丢包的局域网/数据中心 | 有随机丢包、RTT 较长的链路（跨地域、跨境） |
| 典型收益 | 标准 | 丢包链路上吞吐明显提升，延迟波动更小 |
| 代价与注意 | 高丢包链路上会过早降速 | 需要 `fq` 队列做 pacing；**与传统流的公平性有争议**，可能挤占同链路其他流量；**不是所有场景都有收益** |
| 启用 | 默认可用 | 需加载 `tcp_bbr` 模块（`modprobe tcp_bbr`），再改 `net.ipv4.tcp_congestion_control` |

```bash
sysctl net.ipv4.tcp_congestion_control net.ipv4.tcp_available_congestion_control net.core.default_qdisc
                                         # 验证：当前算法、可用算法与默认队列规则
                                         # 实测本机：cubic / reno cubic（未加载 tcp_bbr）/ fq_codel
modprobe tcp_bbr                         # 验证：加载模块后 available 里会出现 bbr（改前先记录当前值）
sysctl -w net.core.default_qdisc=fq net.ipv4.tcp_congestion_control=bbr
                                         # 验证：BBR 的标准组合（fq 提供 pacing），改完用 ss -ti 看 pacing_rate 是否有变化
```

> [!warning] 换拥塞算法是一次「影响面未知」的变更
> 它影响的是**全机所有 TCP 连接**。变更前必须有基线（吞吐、P99、重传率），变更后必须复测；且要确认 `fq` 已生效。**在共享链路上还要考虑公平性影响**——这是它经常被拒绝上线的原因，而不是「BBR 不好」。

## 5. UDP：另一条路

UDP 要单独说一句：**没有重传、没有拥塞控制（除非应用自己实现）**，所以指标上「没有重传」不等于「没有丢包」。

| 场景 | 表现 | 怎么发现丢包 |
| --- | --- | --- |
| DNS（UDP 53，被截断时回落到 TCP） | 偶发解析超时 | `resolvectl statistics`、抓 53 端口 |
| QUIC（UDP 上自带重传与拥塞控制） | 应用层指标才有意义 | 应用指标、抓包 |
| SNMP / 监控采集 | 数据点缺失 | 采集端与对端计数器 |

**结论**：UDP 服务的「偶发超时」经常查不出原因，就是因为**内核不替你记账**——必须靠应用层计数或抓包（子笔记 10）。

## 6. 生产动作：一次「吞吐上不去」的取证清单

按顺序做，**每一条都要留下输出**：

1. **先确认瓶颈在哪一边**：`ss -ti` 看 `app_limited`、`retrans`/`lost`、`cwnd`、`minrtt`、`snd_wnd`。
2. **重传率**：`nstat` 采两次，算 `TcpRetransSegs/TcpOutSegs` 的增量比。
3. **路径 MTU**：`ping -M do -s 1472 <ip>`（100% 丢包就是 MTU/PMTU 问题，子笔记 08）。
4. **带宽基线**：`iperf3 -c <ip> -P 4 -t 30`（**本文未实测**；与业务侧吞吐对比才有意义）。
5. **逐跳质量**：`tracepath <ip>`、`mtr -n -c 100 <ip>`（**本文未实测**）。
6. **缓冲区上限**：`sysctl net.ipv4.tcp_rmem net.ipv4.tcp_wmem net.core.rmem_max net.core.wmem_max`。
7. **结论**：写出「瓶颈在应用 / 窗口与缓冲 / 丢包与路径 / MTU」中的哪一类 + 证据命令。

```bash
ss -ti dport = :<port>
nstat -az | grep -E 'TcpRetransSegs|TcpOutSegs|TCPTimeouts|TCPLostRetransmit'
ping -M do -s 1472 <ip>
sysctl net.ipv4.tcp_rmem net.ipv4.tcp_wmem net.core.rmem_max net.core.wmem_max
```

## 7. 缓冲区参数：调大换吞吐，代价是内存

| 参数 | 管什么 | Ubuntu 24.04 实测默认 | 什么时候动 |
| --- | --- | --- | --- |
| `net.ipv4.tcp_rmem` | 单个 TCP 连接的接收缓冲（min/default/max，自动调优在区间内） | `4096 131072 6291456` | 高 BDP 链路（跨地域、高延迟）吞吐上不去时 |
| `net.ipv4.tcp_wmem` | 单个 TCP 连接的发送缓冲 | `4096 16384 4194304` | 同上 |
| `net.core.rmem_max` / `wmem_max` | 应用 `setsockopt` 能申请的**上限** | `212992` / `212992` | 应用显式设置缓冲区且被卡住时 |

```bash
sysctl net.ipv4.tcp_rmem net.ipv4.tcp_wmem net.core.rmem_max net.core.wmem_max
                                         # 验证：本机缓冲区间与上限
```

**代价**：每个连接都能占用更多内存，**连接数大时是数量级的放大**。所以这是「有量化依据才能动」的典型参数（子笔记 11 的调优纪律）。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 「TCP 能连但吞吐上不去，先扩带宽」 | 先分类：`app_limited`（应用）、`cwnd`/`minrtt`（窗口）、`retrans`（丢包）、PMTU（MTU）——四类处置完全不同 |
| 忽略 `app_limited` | 它明确说明网络没被用满；在网络上做任何调优都不会有效果 |
| 用「带宽峰值」判断瓶颈 | 窗口受限与丢包重传都不表现为「带宽跑满」 |
| 认为「没有重传就没有丢包」 | 对 TCP 成立，对 **UDP 不成立**（内核不记账） |
| 直接照抄别人的 `tcp_rmem` 调优值 | 高 BDP 链路与局域网的需求差几个数量级；要以基线为准 |
| 在生产机上直接换成 BBR | 影响全机所有连接，且需要 `fq`；必须有基线与复测 |
| 只看 `ss -s` 的数字 | 它给不到单条连接的质量；要看 `ss -ti` |
| 用一次 `nstat` 的绝对值下结论 | 计数器累计值无意义，要看增量 |

## 要点自测

> [!question]- `rwnd` 与 `cwnd` 有什么区别？谁更小谁说了算吗？
> - `rwnd` 是**接收方通告**的「我还能收多少」，属于流控，防止把对方缓冲打爆；`ss -ti` 里表现为 `snd_wnd`。
> - `cwnd` 是**发送方估计**的「网络能承受多少」，属于拥塞控制，防止把链路压垮。
> - 实际在途数据 ≈ `min(cwnd, rwnd)`；**两者都可能成为瓶颈，要分别判断**。
> - **第一反应不要是什么**：不要把「吞吐上不去」一律归因于带宽或对端。

> [!question]- TCP 能连通但吞吐上不去，你会看哪些指标？
> - **`ss -ti`**：`rtt` vs `minrtt`（有排队）、`cwnd`（窗口受限）、`retrans`/`lost`（丢包）、`pacing_rate`/`delivered`（实际速率）、**`app_limited`（应用没喂满，先去查应用）**。
> - **`nstat`**：`TcpRetransSegs/TcpOutSegs` 的重传率、`TcpExtTCPTimeouts`、`TcpExtTCPLostRetransmit`。
> - **路径侧**：`ping -M do` 验证 MTU（实测不一致时大包全丢）、`mtr`/`tracepath` 看逐跳、`iperf3` 建带宽基线（本文未实测）。
> - **缓冲区侧**：`tcp_rmem`/`tcp_wmem` 的 max 与 `rmem_max`/`wmem_max` 是否卡住了高 BDP 链路。
> - **第一反应不要是什么**：不要只看带宽峰值，也不要跳过 `app_limited`。

> [!question]- `cubic` 与 `BBR` 的核心差别是什么？为什么 BBR 需要 `fq`？
> - `cubic` 把**丢包**当作拥塞信号；`BBR` 用**带宽与最小 RTT 的估计**建模，不因随机丢包就大幅降速。
> - 因此 BBR 在「有随机丢包、RTT 较长」的链路上通常更好，但在低丢包局域网里未必有收益，且与其它流的公平性有争议。
> - `fq`（fair queue）提供 **pacing**（按估算速率平滑发包）的能力，是 BBR 发挥效果的前提；没有它 BBR 的速率控制会失真。
> - **第一反应不要是什么**：不要在生产机上不设基线、不排窗口就整机切换拥塞算法。
