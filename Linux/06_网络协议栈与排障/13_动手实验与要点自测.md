# 动手实验与要点自测

> [!cite] 参考资料
> 实验用到的工具手册页：`man 8 ip`、`man 8 ip-netns`、`man 8 ss`、`man 8 nstat`、`man 8 sysctl`、`man 8 tc`、`man 8 tc-netem`、`man 8 ping`、`man 8 ethtool`、`man 1 python3`。
>
> **实测声明**：下面的实验输出全部是在实验机上**实测粘贴**的。实测环境：**Ubuntu 24.04.5 LTS（VMware 虚拟机）/ 内核 `6.8.0-139-generic` / cgroup2fs（v2）/ 4 vCPU / `MemTotal` 7894 MiB / root 可用**；网卡 `ens33`（驱动 `e1000`，VMware 模拟 Intel 82545EM）。
> 破坏性/干扰性实验（半连接队列、`netem` 注入、MTU 不一致、bond 故障切换）全部在**独立 network namespace** 里做，且**一律用 root 直接建 netns**（本机 AppArmor 禁用了非特权 user namespace，非 root 下 `unshare -U -r -n` 会报 `Operation not permitted`，见子笔记 08 与本篇实验 3）；实验结束已删除全部命名空间，宿主网络栈未改动（实测宿主 `net.ipv4.tcp_syncookies` 仍为 `1`、`net.ipv4.ip_forward` 仍为 `0`、`net.netfilter.nf_conntrack_max` 仍为 `262144`）。
> 实验用的端口全部落在本章分配区间 **9000–9399**（netns 内的端口不会与宿主冲突，但仍按同一编号规则写，便于对照）。

> **这篇讲什么**：把本章全部知识点变成**七个可复现的实验**，并给出统一清理方式与总自测。**实验 1 与实验 3 是本章最值钱的两个**——它们对应生产上最高频、最难发现的「队列溢出」与「syncookies 对照」。

## 2. 实验 1：用真实客户端复现「全连接队列溢出」

这个实验不需要 root 之外的特殊权限、不需要抓包、不需要伪造报文——**一段 Python 脚本就能复现生产上最常见的「偶发连不上」**。

```bash
python3 - <<'PY' &   # ① 服务端：只 listen(1)，永不 accept()。放后台，保持 10 分钟
import socket, time
s = socket.socket()
s.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
s.bind(("127.0.0.1", 9301))
s.listen(1)                 # backlog = 1
time.sleep(600)
PY

sleep 1
python3 - <<'PY' &   # ② 客户端：依次建 6 条连接，每条都保持不关（放后台，保持 90 秒）
import socket, time
held = []
for i in range(6):
    s = socket.socket(); s.settimeout(5)
    try:
        s.connect(("127.0.0.1", 9301)); print(i, "ok", flush=True); held.append(s)
    except Exception as e:
        print(i, type(e).__name__, flush=True)
time.sleep(90)
PY

sleep 10   # ③ 取证：等 10 秒，让前几条连接都试过一轮（第 3 条起会卡在 connect 上重传）
ss -lnt | grep 9301
ss -tan | grep 9301
nstat -az | grep -E 'ListenOverflows|ListenDrops'

kill %1 %2 2>/dev/null   # ④ 收尾：结束两个后台任务
```

**实测输出**：

```text
0 ok
1 ok                                   # ← 只有 2 条能进队列（backlog+1）
LISTEN 2      1          127.0.0.1:9301       0.0.0.0:*          
ESTAB     0      0            127.0.0.1:9301      127.0.0.1:44128        
SYN-SENT  0      1            127.0.0.1:44736     127.0.0.1:9301         # ← 第 3 条卡在 SYN-SENT
2 TimeoutError                         # ← 第 3 条客户端超时（内核把 SYN 丢了）
TcpExtListenOverflows           10                 0.0
TcpExtListenDrops               10                 0.0
```

**这一屏就是子笔记 05 与 12 的全部证据**：`Recv-Q(2) > Send-Q(1)`（队列满）+ `ListenOverflows`/`ListenDrops` 各自涨到 10（内核在丢 SYN）+ 客户端 `SYN-SENT` 直到 `TimeoutError`（应用永远不知道这条连接存在过）。

> 说明：本实验跑在**宿主命名空间**的回环地址上（不含 netns），所以 `ss` 与 `nstat` 看到的是宿主自己的计数；这也是「只在回环/本机端口上做、风险低」的实验 1 与「必须进 netns」的实验 3 的分工。收尾后实测 `9301 已释放`、无残留进程。

**风险**：低。只占用本机 `9301` 端口与少量进程。

**耗时**：约 15 分钟。

**回滚**：命令里已 `kill %1 %2`；确认 `ss -lnt | grep 9301` 无输出即可。

## 3. 实验 2：`somaxconn` 是 `listen()` 的硬上限

```bash
sysctl net.core.somaxconn                     # 验证：本机上限（实测 4096）
python3 - <<'PY' &                            # 放后台：listen(10000) 会怎样
import socket, time
s = socket.socket()
s.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
s.bind(("127.0.0.1", 9302))
s.listen(10000)                               # 远超 somaxconn
time.sleep(300)
PY
sleep 1
ss -lnt | grep 9302
kill %1 2>/dev/null                           # 收尾
```

**实测输出**：

```text
LISTEN 0      4096       127.0.0.1:9302       0.0.0.0:*          
```

**结论**：`Send-Q` 被截断成 4096，不是 10000。应用调大 backlog 之后，**一定回到 `ss -lnt` 确认 `Send-Q` 真的变大了**——被 `somaxconn` 静默截断是极常见的「调了但没用」。

**风险**：低。只占用本机 `9302` 端口。

**耗时**：约 5 分钟。

**回滚**：`kill %1`；确认 `ss -lnt | grep 9302` 无输出。

## 4. 实验 3：半连接队列与 syncookies（隔离命名空间 + 伪造源 SYN）

先搭一套**完全隔离**的两命名空间拓扑（后面实验 5、6、7 复用），再往里灌 SYN。**本机必须用 root 建 netns**：AppArmor 禁用了非特权 user namespace（`kernel.apparmor_restrict_unprivileged_userns=1`，实测），非 root 下 `unshare -U -r -n` 会报 `write failed /proc/self/uid_map: Operation not permitted`、`ip netns add` 会报 `mount --make-shared /run/netns failed: Operation not permitted`。

```bash
ip netns add srv; ip netns add cli   # ① 建拓扑：srv(10.0.0.1) —— veth —— cli(10.0.0.2)
ip link add veth0 type veth peer name veth1
ip link set veth0 netns srv; ip link set veth1 netns cli
ip netns exec srv ip link set lo up; ip netns exec cli ip link set lo up
ip netns exec srv ip addr add 10.0.0.1/24 dev veth0
ip netns exec cli ip addr add 10.0.0.2/24 dev veth1   # 先配地址、再起接口
ip netns exec srv ip link set veth0 up
ip netns exec cli ip link set veth1 up
ip netns exec cli ping -c2 10.0.0.1                  # 验证：实测 RTT 0.033/0.045/0.057 ms，通即说明拓扑正确

cat > /tmp/06-srv.py <<'PY'   # ② srv 里起一个 listen(1) 且不 accept 的服务端
import socket, sys, time
addr, port, backlog = sys.argv[1], int(sys.argv[2]), int(sys.argv[3])
s = socket.socket()
s.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
s.bind((addr, port)); s.listen(backlog)
print("listening", addr, port, "backlog", backlog, flush=True)
time.sleep(900)
PY
ip netns exec srv python3 /tmp/06-srv.py 10.0.0.1 9001 1 &

cat > /tmp/06-syn.py <<'PY'   # ③ cli 里用原始套接字发带伪造源地址的 SYN（只在本命名空间内，出不了这台机器）
import socket, struct, sys, random
def csum(data):
    if len(data) % 2: data = data + b"\x00"
    s = 0
    for i in range(0, len(data), 2): s = s + (data[i] << 8) + data[i + 1]
    while s >> 16: s = (s & 0xffff) + (s >> 16)
    return (~s) & 0xffff
def syn(dst, dport, sport, src_ip):
    seq = random.randint(0, 2 ** 32 - 1)
    tcp = struct.pack("!HHIIBBHHH", sport, dport, seq, 0, 5 << 4, 0x02, 65535, 0, 0)
    pseudo = struct.pack("!4s4sBBH", socket.inet_aton(src_ip), socket.inet_aton(dst), 0, 6, len(tcp))
    tcp = struct.pack("!HHIIBBHHH", sport, dport, seq, 0, 5 << 4, 0x02, 65535, csum(pseudo + tcp), 0)
    ip_sum = csum(struct.pack("!BBHHHBBH4s4s", 0x45, 0, 40, random.randint(0, 65535), 0, 64, 6, 0,
                              socket.inet_aton(src_ip), socket.inet_aton(dst)))
    ip = struct.pack("!BBHHHBBH4s4s", 0x45, 0, 40, random.randint(0, 65535), 0, 64, 6, ip_sum,
                     socket.inet_aton(src_ip), socket.inet_aton(dst))
    return ip + tcp
dst, dport, cnt, prefix = sys.argv[1], int(sys.argv[2]), int(sys.argv[3]), sys.argv[4]
s = socket.socket(socket.AF_INET, socket.SOCK_RAW, socket.IPPROTO_RAW)
s.setsockopt(socket.IPPROTO_IP, socket.IP_HDRINCL, 1)
for i in range(cnt):
    s.sendto(syn(dst, dport, random.randint(1024, 65535), prefix + "." + str(random.randint(3, 254))), (dst, 0))
print("sent", cnt, "SYNs to", dst, dport)
PY

ip netns exec srv sysctl -n net.ipv4.tcp_syncookies              # ④ 对照实验：syncookies=1（默认） vs syncookies=0
ip netns exec cli python3 /tmp/06-syn.py 10.0.0.1 9001 20 10.0.0
sleep 1
ip netns exec srv nstat -az | grep -E 'SyncookiesSent|TCPReqQFull|ListenDrops'
ip netns exec srv sysctl -w net.ipv4.tcp_syncookies=0            # 只改这个命名空间，不影响宿主
ip netns exec cli python3 /tmp/06-syn.py 10.0.0.1 9001 20 10.0.0
sleep 1
ip netns exec srv nstat -az | grep -E 'SyncookiesSent|TCPReqQFull|ListenDrops'
```

**实测输出**（`syncookies=1`（默认）时，队列满 → 发 cookie，不丢）：

```text
TcpExtSyncookiesSent         18
TcpExtTCPReqQFullDoCookies   18        # ← 18 个 SYN 走了 cookie 路径
TcpExtTCPReqQFullDrop        0
TcpExtListenDrops            0         # ← 一个都没丢
```

现场还留得下半连接（`ss -tan state syn-recv`，实测 2 条），且回程真的发出去了（交叉验证：`TcpOutSegs 20`、`IpOutNoRoutes 0`）：

```text
Recv-Q Send-Q Local Address:Port Peer Address:Port Process
0      0           10.0.0.1:9001   10.0.0.104:43695       
0      0           10.0.0.1:9001    10.0.0.38:30872       

TcpOutSegs                   20
IpOutNoRoutes                0
```

把该命名空间内 `syncookies=0` 后，队列满 → 真丢 SYN：

```text
TcpExtSyncookiesSent         18        # ← 不再增长（cookie 关掉了）
TcpExtTCPReqQFullDoCookies   18
TcpExtTCPReqQFullDrop        20        # ← 第二次实验又丢 20 个
TcpExtListenDrops            20        # ← 同步涨到 20
TcpOutSegs                   22
```

**结论**：默认配置下半连接队列满**不会导致连接失败**，只是丢了握手选项、计数落在 `SyncookiesSent`/`ReqQFullDoCookies` 上；**关掉 syncookies 才会真的丢 SYN**（本次实测 20 发 20 丢）——所以「为了性能关掉 syncookies」是典型的负优化。

> [!warning] 踩坑记录：**在 loopback 上伪造源地址做 SYN 实验会得出错误结论**
> 最初的做法是在**宿主命名空间的 `127.0.0.1`** 上伪造 `10.x.x.x` 源地址。结果每个 SYN 都让 `TcpExtListenDrops +1`、且**不留任何半连接**，看起来像「内核把 SYN 全丢了」。
> 真相是：**SYN-ACK 需要发往那个伪造的源地址，而回包没有可用路由，内核在 `route_req()` 阶段就失败了**——这时 `IpOutNoRoutes` 会同步增长，而 `TcpOutSegs` 几乎不动（SYN-ACK 一个都没发出去）。
> **教训**：伪造报文的实验必须有「回程可路由」的环境（本实验用 veth 对解决），**并且要用第二个计数器交叉验证**。上面 `syncookies=1` 那一组实测里 `TcpOutSegs=20`、`IpOutNoRoutes=0`，正说明回程路由是通的——**只看 `ListenDrops` 一个计数器就下结论，是排障里最容易犯的错**。
> 顺带一个本机特有的坑：**非 root 下这个实验根本起不来**（AppArmor 禁用非特权 userns，`ip netns add` 直接 `Operation not permitted`）。本机有 root，正确做法是**用 root 直接做**，而不是去找绕过手段。

**风险**：中。会创建 network namespace 与 veth、伪造报文（但只在本机命名空间内）。

**耗时**：约 30 分钟。

**回滚**：**先不要删**——实验 5、6、7 还要复用这套 `srv`/`cli` 拓扑；全部做完后执行第 8 节的统一清理命令（`ip netns del srv; ip netns del cli` 会连同 veth 一起回收，实测无残留）。

## 5. 实验 4：`TIME_WAIT` 到底停多久

```bash
cat > /tmp/06-tw.py <<'PY'

def server():

    rows = [l for l in out.splitlines() if ":" + str(port) in l]
    state = rows[0].split()[0] if rows else "GONE"
```

**实测输出**（节选，采样间隔 0.5 秒）：

```text

0.51 秒: FIN-WAIT-2 
1.01 秒: TIME-WAIT    <-- 进入 TIME-WAIT
1.52 秒: TIME-WAIT
```

**结论**：`TIME_WAIT` 的时长是**内核写死的 60 秒**（实测进入 `TIME-WAIT` 后 **62.06 秒**消失；0.5 秒采样 + 内核定时器抖动，落在 60~63 秒之间都是正常的），与 `tcp_fin_timeout`（实测 60、管 `FIN_WAIT2`）无关，也没有任何 sysctl 可调——**这就是子笔记 07 那条「面试误解」的实测依据**。
同时注意：**主动关闭的一方才有 `TIME_WAIT`**（本例是客户端 `close()`，服务端立刻 `close()` 反而进了 `CLOSE_WAIT`/`LAST_ACK` 那条路），这决定了「该改客户端还是改服务端」。

**风险**：低。只占用本机 `9002` 端口。

**耗时**：约 5 分钟（脚本本身要跑 60 多秒）。

**回滚**：脚本自行结束；确认 `ss -tan | grep 9002` 无输出。

## 6. 实验 5：用 `tc netem` 注入延迟与丢包（复用实验 3 的拓扑）


## 7. 实验 6：MTU 不一致（同一拓扑）

```bash
ip netns exec srv ip link set veth0 mtu 1400      # 一端 1400
ip netns exec cli ip link set veth1 mtu 1500      # 另一端 1500（不对称）
ip netns exec cli ping -M do -s 1472 -c2 -W2 10.0.0.1    # 需要 1500 字节承载
ip netns exec cli ping -M do -s 1372 -c2 -W2 10.0.0.1    # 需要 1400 字节承载
ip netns exec srv ip link set veth0 mtu 1500      # 恢复
```

**实测输出**（1500 字节（`-s 1472`）时）：

```text
PING 10.0.0.1 (10.0.0.1) 1472(1500) bytes of data.
ping: sendmsg: No buffer space available
ping: sendmsg: No buffer space available

--- 10.0.0.1 ping statistics ---
2 packets transmitted, 0 received, 100% packet loss, time 4015ms
```

1400 字节（`-s 1372`）时：

```text
PING 10.0.0.1 (10.0.0.1) 1372(1400) bytes of data.
1380 bytes from 10.0.0.1: icmp_seq=1 ttl=64 time=0.044 ms
1380 bytes from 10.0.0.1: icmp_seq=2 ttl=64 time=0.039 ms

--- 10.0.0.1 ping statistics ---
2 packets transmitted, 2 received, 0% packet loss, time 1004ms
rtt min/avg/max/mdev = 0.039/0.041/0.044/0.002 ms
```

**结论**：MTU 不一致时**小包全通、大包全丢**——这正好解释了「能 SSH、能 `ping`，一传文件就卡死」的现象。`-M do` 必须带，否则内核分片会掩盖问题。**大包那一侧的第一手报错是 `ping: sendmsg: No buffer space available`**，别把它读成内存不足（它是「接口 MTU 1400 放不下 1500 字节 DF 包」的本机报错）。

**风险**：中。会改动 veth 的 MTU（短暂影响该接口流量）；只在命名空间内。

**耗时**：约 10 分钟。

**回滚**：把 MTU 改回 1500（本实验已执行）；确认 `ip netns exec srv ip link show veth0` 的 mtu 为 1500。

### 7.1 补充：同一思路下的 bond 故障切换（`bonding` 模块，仍在 netns 内）

MTU 之外，链路站还有一件必须亲手验的事：**bond 的冗余到底管不管用**。`bonding` 模块本机默认未加载，`modprobe bonding` 后即可在 netns 里建（不影响宿主网络）：

```bash
modprobe bonding                                  # 本机实测：加载前 /sys/class/net/bonding_masters 不存在
ip netns add bs; ip netns add bp                  # bs=bond 侧，bp=对端网桥侧
ip link add bv0 type veth peer name bp0           # 两对 veth 当两个成员口
ip link add bv1 type veth peer name bp1
ip netns exec bs ip link add bond0 type bond mode active-backup miimon 200
ip netns exec bs ip link set bv0 master bond0
ip netns exec bs ip link set bv1 master bond0
ip netns exec bs ip addr add 10.77.0.1/24 dev bond0
ip netns exec bp ip link add br0 type bridge      # 对端把两个口都接进网桥
ip netns exec bp ip addr add 10.77.0.2/24 dev br0
```

**实测输出**（关键三屏）。

正常工作时的成员口状态：

```text
Currently Active Slave: bv0
MII Status: up
Slave Interface: bv0 → MII Status: up
Slave Interface: bv1 → MII Status: up
2 packets transmitted, 2 received, 0% packet loss, time 1034ms
```

down 掉 active 成员口 → 自动切换，业务不掉：

```text
$ ip netns exec bs ip link set bv0 down
Currently Active Slave: bv1
Slave Interface: bv0 → MII Status: down
Slave Interface: bv1 → MII Status: up
3 packets transmitted, 3 received, 0% packet loss, time 2060ms
```

两个成员口都 down → 才真的不通：

```text
2 packets transmitted, 0 received, 100% packet loss, time 1018ms
```

**这就是 N6 要练的判断力**：`bond0` 是 `UP` 不等于冗余可用，**验收动作是「拔掉一条，看业务还在不在」**。另外把模式换成 `802.3ad`（LACP）、对端仍是普通网桥时，实测 `Partner Mac Address: 00:00:00:00:00:00`、`Number of ports: 1`、两个成员口分属不同 `Aggregator ID`——**协商没成功**（子笔记 08 第 2.2 节）。

**风险**：低到中。只加载一个内核模块 + 在 netns 内建设备；`modprobe -r bonding` 可还原（本机实测卸载后 `lsmod` 里不再有 `bonding`，`bonding_masters` 也消失）。

**耗时**：约 10 分钟。

## 10. 要点自测

下面九道题全部来自本章正文，**每题都要能补一句「第一反应不要是什么」**。逐题自问，答不上就回对应子笔记。

> [!question]- 大量 `TIME_WAIT` 是问题吗？为什么 `CLOSE_WAIT` 只能改应用？
> - **判定**：`TIME_WAIT` 是**主动关闭方**的正常状态，Linux 固定 60 秒（实测进入 `TIME-WAIT` 后 **62.06 秒**消失），**没有 sysctl 可调**；`CLOSE_WAIT` 是**被动关闭方**收到 FIN 后应用没 `close()`。
> - **影响什么**：`TIME_WAIT` 只占**源端口**（上限 = 源端口数 ÷ 60s 对应的出向 QPS）；`CLOSE_WAIT` 占**进程句柄**，会一路涨到 `open files` 上限。
> - **不影响什么**：`TIME_WAIT` 不影响服务端接受新连接，也不会「拖慢」系统；`tcp_fin_timeout` 与它无关（只管 `FIN_WAIT2`）。
> - **落点**：`TIME_WAIT` 多 → 连接池/长连接、必要时 `tcp_tw_reuse=1`、扩端口范围；`CLOSE_WAIT` 多 → 定位进程 + 看句柄增长 + 修代码。
> - **第一反应不要是什么**：不要为了「消灭 `TIME_WAIT`」去调 `tcp_fin_timeout`，也不要尝试 `tcp_tw_recycle`（内核 4.12 已移除）。

> [!question]- 用户说「服务连不上」，你的排查顺序是什么？每一步期待看到什么？
> - **① 监听**：`ss -lntp` → 期待 `0.0.0.0:<port>`；只有 `127.0.0.1:<port>` 就是根因。
> - **② 链路**：`ping` → 区分「到不了主机」还是「到不了服务」；**但别把 `ping` 通当成 TCP 通**。
> - **③ 端口**：`nc -vz` + 服务端同时看 `nstat` → `ListenOverflows`/`ListenDrops` 涨就是队列溢出；都不涨且客户端 `SYN-SENT` → SYN 被中间设备/conntrack 丢；`refused` → 没监听或 `tcp_abort_on_overflow=1`。
> - **④ 名称**：`getent hosts`（不是 `dig`）→ 确认应用视角能解析到正确地址。
> - **⑤ 应用**：`curl -v`、`journalctl -u`、进程是否 `D` 状态。
> - **第一反应不要是什么**：不要先重启服务（会毁掉 `ss`/`nstat`/conntrack 里唯一的现场）。

> [!question]- 抓包怎么抓才能既拿到证据又不影响生产？
> - **三重限制**：`-c`（包数）、`-w`（落到独立目录/文件）、`timeout`（时间）；必要时再加 `-s <len>` 截断载荷。
> - **先想清楚抓哪一跳**：客户端抓、服务端抓、中间抓——**「这一跳有没有」比「抓全了」更有价值**（二分定位）。
> - **过滤表达式要精确**：`host`/`port`/`tcp[tcpflags]` 组合，避免把无关流量也写进盘。
> - **落盘分析而不是盯着屏幕**：`-w` 落 pcap → 拉回本地 Wireshark；生产机上不做复杂显示过滤（非常耗 CPU）。
> - **第一反应不要是什么**：不要在业务高峰无参数直接 `tcpdump -i any`——那是最容易把机器抓挂的做法。

> [!question]- `getent hosts` 和 `dig` 结果不一致，说明什么？
> - **两条不同的路径**：`getent` 走 `getaddrinfo()` → `nsswitch.conf`（`files` 优先于 `dns`）；`dig` 直接发 DNS 查询，**完全绕过 NSS**。
> - **四种常见原因**：名字在 `/etc/hosts` 里；`resolv.conf` 指向 `systemd-resolved` 存根（`127.0.0.53`）；`search` 域 + `ndots` 让 `getent` 试了多个后缀；`getent hosts` 只显示一族地址而 `dig` 显示全部记录（实测：`getent` 只给 IPv6，`resolvectl query` 给 A+AAAA）。
> - **所以**：「`dig` 通」不能证明应用能解析；排障要用 `getent` 复现。
> - **落点**：容器里还要额外看 `ndots:5` 与 `search` 域（K8s 默认），单次解析可能触发 4~5 次查询。

> [!question]- MTU 不一致的典型现象是什么？怎么验证？
> - **指纹**：`ping` 通、SSH 能登录、小请求正常，**大响应/大文件卡住或超时**；HTTP 表现为「请求发出去了但一直收不到完整响应」。
> - **验证**：`ping -M do -s 1472 <ip>`（实测 100% 丢包）→ 缩小到 `-s 1372`（实测 0% 丢包）就能定位可用 MTU；**必须带 `-M do`**，否则分片会掩盖问题。
> - **根因方向**：VPN/隧道/overlay 封装开销、两端配置不一致、路径 MTU 发现依赖的 ICMP 被防火墙屏蔽（PMTU 黑洞）。
> - **落点**：统一两端 MTU，或在网关上做 MSS clamping；`tcp_mtu_probing=1` 只作为 ICMP 被禁时的兜底。
> - **第一反应不要是什么**：不要一上来就扩容带宽——大包全丢而小包正常，不是带宽问题。

> [!question]- TCP 能连通但吞吐上不去，你会看哪些指标？
> - **`ss -ti`**：`rtt` vs `minrtt`（有排队）、`cwnd`（窗口受限）、`retrans`/`lost`（丢包）、`pacing_rate`/`delivered`（实际速率）、**`app_limited`（应用没喂满，先去查应用）**。
> - **`nstat`**：`TcpRetransSegs/TcpOutSegs` 的重传率、`TcpExtTCPTimeouts`、`TcpExtTCPLostRetransmit`。
> - **路径侧**：`ping -M do` 验证 MTU（实测不一致时大包全丢）、`mtr -n -r -c 3` 看逐跳（实测公网目标 2 跳都有回应）、`iperf3 -c 127.0.0.1 -t 3` 建本机回环带宽基线（实测 55.3 Gbits/sec）。
> - **缓冲区侧**：`tcp_rmem`/`tcp_wmem` 的 max 与 `rmem_max`/`wmem_max`（实测 212992）是否卡住了高 BDP 链路。
> - **第一反应不要是什么**：不要只看带宽峰值——`app_limited` 与 `cwnd` 受限都不表现为「带宽跑满」。

> [!question]- 客户端偶发连接失败、服务端却没有日志，可能和什么有关？
> - **全连接队列溢出（首选嫌疑）**：实测 `Recv-Q(2) > Send-Q(1)`、`TcpExtListenOverflows` 增长、客户端卡在 `SYN-SENT`；**应用根本不知道连接存在过**，所以没有日志。
> - **半连接队列满 + syncookies=0**：`TcpExtTCPReqQFullDrop`/`ListenDrops` 同步增长（实测 20 个 SYN 全丢，`ReqQFullDrop 20`/`ListenDrops 20`）。
> - **conntrack 表满**：内核静默丢包，只在 `dmesg`/`conntrack -S` 里留痕。
> - **中间设备限速/抖动/安全组**：主机侧计数器干净，要去对端或网络侧看。
> - **第一反应不要是什么**：不要把「服务端没日志」当成「请求没到达」——**握手成功但没 `accept()` 的情况下，两者同时成立**。

> [!question]- 半连接队列与全连接队列，分别由什么决定？溢出的计数在哪里？
> - **半连接（`SYN_RECV`）**：长度由 `listen()` 的 backlog 推导（实测 `listen(1)` 只留存 2 条，**与 `tcp_max_syn_backlog=512` 无关**）；溢出时 `tcp_syncookies=1` 走 cookie（`TcpExtSyncookiesSent`/`ReqQFullDoCookies`），`=0` 才丢（`TcpExtTCPReqQFullDrop`）。
> - **全连接（accept 队列）**：上限 = `min(backlog, somaxconn)`（实测 `listen(10000)` 被 `somaxconn=4096` 截断），实际能放 backlog+1 条；溢出计数是 `TcpExtListenOverflows` + `ListenDrops`。
> - **判据**：`ss -lnt` 看 `Recv-Q`/`Send-Q`，`nstat` 看计数——**两个一起看才算证据齐全**。
> - **落点**：`ListenOverflows` 必须配告警，它是这类故障唯一的早期信号。

> [!question]- `conntrack` 表满是怎样的现场？怎么处置？
> - **现场**：客户端间歇性超时、服务端应用无感，`dmesg` 里 `nf_conntrack: table full, dropping packet`；`nf_conntrack_count` 逼近 `nf_conntrack_max`。**本机要注意**：`nf_conntrack` 模块**默认未加载**（`/proc/sys/net/netfilter/` 下没有 `nf_conntrack_max`），要先 `modprobe nf_conntrack` 才有值（加载后为 `262144`）；本机实测把上限压到 `64` 后灌 120 条长连接，只有 **63 条**成功、**57 条**失败，`dmesg`/`journalctl -k` 出现了 `nf_conntrack: nf_conntrack: table full, dropping packet`，`conntrack -S` 的 `drop` 涨到 `27`。
> - **定性**：它是**丢包**不是拒绝——所以「重试能好」的偶发故障要优先怀疑它。
> - **处置**：调大 `nf_conntrack_max`（同时看内存与 buckets）→ 缩短 `nf_conntrack_tcp_timeout_established`（实测默认 432000s = 5 天，短连接多的机器影响很大）→ **根治是让应用用长连接/连接池**。
> - **第一反应不要是什么**：不要直接关掉 conntrack（NAT/Service 转发都依赖它）。
