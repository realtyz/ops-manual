# 端口、套接字与多路复用

## 1. 一台主机只有几个地址，却要同时承载几万条会话

一台服务器通常只有一两个 IP 地址，一张网卡，但上面同时跑着 SSH、DNS 解析、HTTP、数据库连接。包到达本机时，IP 层只能说明「这是发给这台主机的」，却回答不了两个问题：**这个包属于哪个进程、属于这个进程的哪一次会话**。

传输层用两层标识回答这两个问题：

- **端口（port）** 回答「属于哪个应用」——一个 16 位整数，0~65535；
- **四元组（源地址、源端口、目的地址、目的端口）** 回答「属于哪一次会话」。

**多路复用（multiplexing）** 指的就是这件事：多个应用共享一个 IP 地址，内核靠端口把到达的包分发给正确的 socket；反过来，多个连接共享一个监听端口，内核靠四元组把它们区分开。

## 2. 端口的三段划分，以及 Linux 自己那一段

| 范围 | 名称 | 用途 | 注意 |
| --- | --- | --- | --- |
| `0` ~ `1023` | 知名端口（well-known / system，IANA 口径） | `22`(ssh)、`53`(dns)、`80`(http)、`443`(https) | 非 root 绑定需要 `CAP_NET_BIND_SERVICE` |
| `1024` ~ `49151` | 注册端口（registered / user，IANA 口径） | 应用自定义端口多落在这里 | 与源端口范围可能重叠 |
| `49152` ~ `65535` | 动态端口（dynamic / ephemeral，IANA 建议） | IANA 建议的临时端口段 | **Linux 并不用这一段做源端口** |
| `32768` ~ `60999` | Linux 实际的源端口范围，由 `ip_local_port_range` 决定 | 本机**主动发起**连接时内核自动选 | 内核/发行版取值，不是 IANA 划分 |

**这张表里最容易出错的一行是最后一行。** 很多人把 IANA 的 `49152~65535` 当成 Linux 的临时端口范围，于是算端口容量时算错。真实范围要现场查：

```bash
cat /proc/sys/net/ipv4/ip_local_port_range      # 验证：本机源端口范围
sysctl net.ipv4.ip_local_port_range             # 验证：同一份数据的 sysctl 视角
```

要点：

- **它是内核参数，随内核与发行版变化**，不能凭记忆写进容量规划；规划时必须现场取。
- **范围里还有排除项**：`ip_local_reserved_ports` 可以从范围中挖掉若干端口，留给需要固定源端口的应用。
- **两个方向用的是不同的东西**：作为服务端，你用的是**监听端口**（由你指定、可复用给成千上万条连接）；作为客户端，你用的是**源端口**（内核分配、每条连接一个，关闭后还可能在 `TIME_WAIT` 里占着）。

**「端口耗尽」几乎总是说源端口，而不是监听端口。**

## 3. socket、四元组与两种身份

内核里代表一次通信的对象叫 **socket（套接字）**。它有两种身份，数量与含义完全不同：

| 对象 | 状态 | 数量 | 有没有队列 | `ss` 里的样子 |
| --- | --- | --- | --- | --- |
| 监听 socket | `LISTEN` | 一个「监听地址:端口」一个 | **它有**半连接队列与全连接队列 | `LISTEN 0 4096 0.0.0.0:8080 0.0.0.0:*` |
| 已连接 socket | `ESTABLISHED` 等 | **每条连接一个** | 无队列，有收发缓冲区 | `ESTAB 0 0 10.0.0.1:8080 10.0.0.2:43848` |

```text
State   Recv-Q  Send-Q  Local Address:Port   Peer Address:Port  Process
LISTEN  0       4096    0.0.0.0:8080         0.0.0.0:*          users:(("nginx",pid=1234,fd=6))
ESTAB   0       0       10.0.0.1:8080        10.0.0.2:43848     users:(("nginx",pid=1234,fd=9))
```

（以上格式按 `ss -lntp` / `ss -tanp` 输出书写，数值仅示意。）

**同样的两列 `Recv-Q`/`Send-Q`，在两种 socket 上语义完全不同**，这是本章最高频的误读之一：

| 列 | 监听 socket | 已连接 socket |
| --- | --- | --- |
| `Recv-Q` | 当前已完成握手、还没被 `accept()` 的连接数（**队列深度**） | 接收缓冲区里还没被应用读走的字节数 |
| `Send-Q` | 该队列的**上限**（由 `listen()` 的 backlog 与 `net.core.somaxconn` 共同决定） | 发送缓冲区里还没被确认的字节数 |

由此得到两条判据：

- 监听 socket 上若 `Recv-Q > Send-Q`，则队列已满（判定细节见原理篇「连接的生命周期」一节）；
- 已连接 socket 上若 `Recv-Q` 长期非零，则应用读得比网络到得慢，瓶颈在应用侧。

## 4. 一条连接的完整状态集合

状态不是排障时才需要背的名词，它是**责任归属的判据**：看到哪个状态在涨，就知道该找谁。

| 状态 | 含义 | 异常时通常指向 |
| --- | --- | --- |
| `LISTEN` | 在监听 | 只绑 `127.0.0.1` 是「外部连不上」的常见原因 |
| `SYN-SENT` | 已发 SYN，等 SYN+ACK | 对端不回或 SYN 被中间设备丢弃 |
| `SYN-RECV` | 收到 SYN，已回 SYN+ACK | 半连接队列积压 |
| `ESTAB` | 已建立 | `Recv-Q`/`Send-Q` 持续非零说明应用读写跟不上 |
| `FIN-WAIT1` / `FIN-WAIT2` | 主动关闭中 | `FIN_WAIT2` 堆积说明对端迟迟不发 FIN |
| `TIME-WAIT` | 主动关闭完成，等 2MSL | 短连接多；Linux 固定 60 秒，无 sysctl 可调 |
| `CLOSE-WAIT` | 收到对端 FIN，本端应用还没 `close()` | **应用侧问题**（内核参数改不掉） |
| `LAST-ACK` | 被动关闭方等最后一个 ACK | 秒级，一般不用管 |
| `CLOSING` | 双方同时关闭 | 罕见 |

**先看分布、再看单条连接**，是因为分布能在几秒内把问题分类：一个状态异常放大时，故障类别基本就定了。三条最短的判据：

```bash
ss -s                                                        # 验证：按协议与状态的总览
ss -tan | awk 'NR>1{print $1}' | sort | uniq -c | sort -rn    # 验证：状态分布排行
ss -tan state time-wait | wc -l                               # 验证：单个状态的精确条数
```

状态机的时间尺度也值得记住：`CLOSING`、`LAST-ACK` 是秒级；`TIME-WAIT` 是分钟级（60 秒，见原理篇「连接的生命周期」）；`CLOSE-WAIT` 可以停到进程结束——**它的持续时间由应用代码路径决定，不由内核决定**。这两个状态在值班现场被误判的次数最多（把 `TIME_WAIT` 当故障、把 `CLOSE_WAIT` 当参数问题），逐条判据见判例篇第 5、6 条。

## 5. 源端口是一种有限资源

本机主动发起连接时，每条连接占一个源端口。端口释放不是瞬时的：主动关闭后该端口会进入 `TIME_WAIT`（Linux 固定 60 秒），期间不能被新连接复用（除非启用 `tcp_tw_reuse`，且只对本机主动发起的连接有效、需要时间戳支持）。

于是有一个可以口算的上限：

```text
同一时刻被占用的源端口数 ≈ 出向短连接 QPS × 60 秒
```

把它和 `ip_local_port_range` 的端口数比较，就能判断「源端口够不够」：

| 你看到 | 含义 | 下一步 |
| --- | --- | --- |
| `TIME_WAIT` 数量远小于源端口数 | 这属于完全在安全范围内的状态 | 不要做任何事，因为数量多不等于有问题 |
| `TIME_WAIT` 数量接近源端口数 | 这属于源端口即将耗尽的状态 | 优先改应用（连接池/长连接），再谈扩端口范围 |
| 应用报 `Cannot assign requested address` | 这属于源端口已经耗尽的状态 | 按上面的顺序处置；`tcp_tw_reuse=1` 可以缓解（只对本机出向连接） |
| `nstat` 的 `TcpExtTCPTimeWaitOverflow` 增量非 0 | 它说明撞上了 `tcp_max_tw_buckets` 上限，内核跳过了 `TIME_WAIT` | 这个计数是唯一的信号，日志里可能什么都没有；代价是 2MSL 保护被破坏 |

**判据一定要用差值或趋势**：这些计数器从开机累计，绝对值说明不了任何问题。

## 6. 队列：为什么「客户端说连上了、服务端说没见过」

握手由内核完成，应用只是 `listen()` 之后不断 `accept()`。中间隔着两个队列：

| 队列 | 内核视图 | 上限由谁决定 | 溢出计数 |
| --- | --- | --- | --- |
| 半连接队列 | `SYN_RECV` 状态的请求套接字 | 现代内核中由 `listen()` 的 backlog 推导 | `TcpExtTCPReqQFullDoCookies`（发 cookie）/ `TcpExtTCPReqQFullDrop`（丢） |
| 全连接队列 | 已完成握手、等 `accept()` | `min(listen() 的 backlog, net.core.somaxconn)` | `TcpExtListenOverflows` + `TcpExtListenDrops` |

**全连接队列里的连接在服务端 `ss` 里显示 `ESTAB`，但应用还没拿到它。** 所以两句话可以同时成立：客户端认为「连上了」，而应用认为「从没见过这个请求」——这就是「客户端偶发超时、服务端应用毫无日志」这一类故障的机制来源，也是「服务端没日志说明请求没到达」这条推论出错的地方。

三个必须记住的边界：

1. **上限是 `min(backlog, somaxconn)`，而实际能放进 `backlog + 1` 条**（内核判满比较用的是 `>`），别用「等于多少」的直觉推，用 `ss` 实测。
2. **溢出时默认静默丢弃**（`tcp_abort_on_overflow=0`）：客户端只能等重传超时，服务端应用完全不知道。把它设成 `1` 会让内核回 RST，故障从「慢失败」变成「快速失败」——**更容易被监控发现，但会把原本可能自愈的抖动放大成用户可见错误**。
3. **半连接队列满不一定丢包**：`tcp_syncookies=1`（现代发行版默认）时内核改发 cookie 继续完成握手，只是会丢失部分握手选项。关掉它才变成真丢包——所以「为了性能关掉 syncookies」是典型的负优化。

## 7. 观测端口与连接：从总览到单条

```bash
ss -s                                  # 总览：按协议与状态
ss -lntp                               # 监听：谁在听、队列多深（Recv-Q 深度 / Send-Q 上限）
ss -tanp                               # 已连接：每条连接及进程归属
ss -tan 'dport = :443'                 # 过滤：目的端口
ss -tan state established '( dport = :443 or sport = :443 )'   # 组合过滤
ss -ti                                 # 单条连接的内部细节（RTT/cwnd/重传/app_limited）
ss -tinp 'dport = :443'                # 细节 + 进程
```

三条使用纪律：

- **排障时必须加 `-n`**：不加会触发反向 DNS 解析，输出慢甚至卡住。
- **`-p` 需要权限**：非 root 只能看到自己的进程，「进程列是空的」是权限问题，不是「没有进程」。`ss -lntp` 里出现 `systemd` 也属正常（它在持有服务的监听 fd）。
- **`ss` 看不到链路层**：网卡错包、驱动丢包在 `ip -s link`、`ethtool -S`、`/proc/net/softnet_stat` 里，不在 `ss` 里。

协议栈计数器是另一个维度：`ss` 这类瞬时读数看不到的「偶发」，几乎都留在那里：

```bash
nstat                                            # 只显示自上次基准以来有变化的计数器
nstat -az > /tmp/nstat.before                    # 全部计数器的快照，用于前后对比
nstat -az | grep -E 'ListenOverflows|ListenDrops|TCPReqQFull|SyncookiesSent'
nstat -r 2                                       # 每 2 秒刷新，观察是否在持续增长
```

`nstat` 的计数器来自 `/proc/net/snmp` 与 `/proc/net/netstat`，是内核协议栈的官方口径；`nstat` 只是把它们整理成带名字、可比较的形态。**这类计数器的正确用法是取差值**：单次绝对值等于「自开机以来一共发生过多少次」。

## 常见误解

| 常见说法 | 事实 |
| --- | --- |
| 「一个监听端口只能有一条连接」 | 端口是四元组的一部分；一个监听端口可承载成千上万条连接 |
| 「Linux 的临时端口是 49152~65535」 | 那是 IANA 建议；Linux 的源端口范围由 `ip_local_port_range` 决定，必须现场取 |
| 「端口耗尽说的是监听端口不够」 | 监听端口可以复用；耗尽的是本机出向连接用的源端口 |
| 「监听 socket 的 `Recv-Q` 是没读的数据」 | 它是「已握手未 `accept()` 的连接数」，`Send-Q` 是队列上限 |
| 「服务端没日志说明请求没到」 | 握手完成但没 `accept()` 时，应用不知道连接存在过 |
| 「`ss` 显示不出的丢包就是没有丢包」 | 链路层与驱动层的计数在 `ip -s link`、`ethtool -S` 与 `/proc/net/softnet_stat` 里，它们不出现在 `ss` 的输出里 |
| 「`nstat` 的绝对值大就有问题」 | 计数器从开机累计；判据是差值、趋势与业务表现 |
| 「`-p` 显示空就是没有进程持有这条连接」 | 非 root 看不到别人的 socket；这是权限问题 |

## 要点自测

**问：多路复用到底复用了什么？**
答：复用了「一个 IP 地址」和「一个监听端口」。多个应用共享同一个 IP，内核用端口把包分发给正确的 socket；多条连接共享同一个监听端口，内核用四元组把它们区分开。

**问：为什么「端口耗尽」通常指源端口，而不是监听端口？**
答：监听端口是「一个地址端口一个 socket」，被所有连接共用；而本机主动发起连接时，每条连接要占一个源端口，且主动关闭后会进入 `TIME_WAIT` 约 60 秒。上限大致是「源端口数 ÷ 60 秒」对应的出向 QPS。

**问：判断源端口够不够，要哪几个数？**
答：`ip_local_port_range` 的规模（现场取）、当前 `TIME_WAIT` 条数（`ss -tan state time-wait | wc -l`）、出向短连接 QPS，以及 `nstat` 的 `TcpExtTCPTimeWaitOverflow` 增量。**四者一起看才能判断是「数量多」还是「真的不够」。**

**问：为什么「客户端说连上了」与「服务端说没见过」可以同时成立？**
答：服务端的握手由内核完成，连接先进入全连接队列（`ss` 里是 `ESTAB`），等应用 `accept()` 才算交给应用。队列溢出与否都不影响这个中间态的存在。

**第一反应不要做什么**：不要用 IANA 的临时端口段推算 Linux 的端口容量；不要把监听 socket 的 `Recv-Q` 当成缓冲区读数；不要因为一次 `ss` 干净就排除队列类故障。
