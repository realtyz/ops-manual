# 盲区排查：网络协议栈与排障

## 1. 本篇解决什么问题

读完整章之后，"不会"这件事通常无法被自己察觉。它不表现为"现象答不上来"，而表现为**回答停在某一层却以为已经说完了**——层次分对了、四元组说得准、方向也没错，但据此无法在机器上做出判断。

本篇把本章负责的八类现象逐层拆开：队列溢出与静默丢包、`SYN-SENT` 堆积、连接被立刻拒绝、`ping` 通而端口连不上、`TIME_WAIT` 与 `CLOSE_WAIT` 两个方向的堆积、吞吐上不去、小请求通而大响应卡住。每一层给出它在追问下的典型回答、这一层实际检验的是什么、以及站在这一层的人下一步该往哪里看。用途只有一个：**回答者自己对照，找到自己的回答停在哪一层，据此定位缺的是本章哪一篇的哪一节。**

全部层级中最常见的一种失效，是机制讲得流畅而判据落不到字段上——它意味着拥有的是叙述能力而不是判断能力，而这种状态读起来与"已经说完了"几乎没有区别。

## 2. 分层的方法

每一类现象都沿同一方向逐层展开，共四层，顺序固定：

| 层 | 回答里出现什么 | 检验的是 | 停在这一层的典型说法 |
| --- | --- | --- | --- |
| 第 0 层 | 只给出结论或动作 | 有没有进入机制 | "先扩带宽""重启服务" |
| 第 1 层 | 说出机制与因果 | 机制是否成立 | "握手由内核完成，队列满时静默丢弃" |
| 第 2 层 | 说出字段名与判据 | 判据是否落到可观测处 | "看监听队列的 `Recv-Q` 与 `Send-Q`，再看溢出计数的增量" |
| 第 3 层 | 说出该判据何时失效、处置的代价与顺序 | 是否具备条件意识与代价意识 | "容器里这个计数在本命名空间，宿主机读不到" |

第 0 层与第 1 层之间的跨度最大：从"知道这件事会发生"到"知道它为什么发生"。第 1 层与第 2 层之间的失效最常见，因为二者的语言外观几乎一样，区别只在有没有一个可读的字段。第 3 层决定的是判断能否迁移到另一台机器、另一个环境。

定位自己的位置有一条简单办法：**检查自己的每一句话能不能指到一个字段**。指不到的句子，通常是从别处听来的。

## 3. 现象一：客户端偶发超时、服务端应用无日志，`ss -lnt` 上 `Recv-Q > Send-Q`

### 3.1 逐层演进

**第 0 层**

> 服务端日志里没有对应请求，说明请求根本没到达主机，是网络抖动，先重启服务压一压。

这一层把"应用没有日志"当成了"主机没有收到"，方向从一开始就错了：握手由内核完成，连接可以先进入全连接队列而应用从未见过它。重启之后服务确实会短暂恢复，而唯一的现场——队列深度与溢出计数——已经被清掉。

**第 1 层（说出机制）**

> 三次握手由内核完成，连接先进入全连接队列，等应用 `accept()` 才算交给应用；队列满时内核默认静默丢弃，客户端只能等重传超时，所以服务端没有日志与客户端超时可以同时成立。

到这里因果链已经完整，它对"为什么没有日志"的回答是准确的。但它在机器上不能执行：不知道读哪个文件，也不知道读到的值说明什么。

**第 2 层（给出判据）**

> 判据是两个维度对上。瞬时看监听 socket 的两列：`Recv-Q` 是已完成握手未被 `accept()` 的条数，`Send-Q` 是队列上限，`Recv-Q > Send-Q` 即此刻已满；累计看 `nstat` 的 `TcpExtListenOverflows` 与 `TcpExtListenDrops`，**必须取两次读数的差值**，非 0 就说明这段时间发生过溢出。方向上再分两侧：`Send-Q` 等于 `net.core.somaxconn` 时是全局上限截断，否则是应用 `listen()` 的 backlog 或 `accept()` 的节奏。

**第 3 层（给出边界与代价）**

> 边界有三条。`tcp_syncookies=1` 时半连接队列满不一定丢包，内核改发 cookie 继续完成握手，所以看到溢出计数先要分清是全连接还是半连接队列，`TcpExtTCPReqQFullDoCookies` 增长而 `ListenDrops` 不涨说明内核改用 cookie 完成了握手、客户端仍能连上。不同环境下队列上限的取值来源不同，容器里 `net.core.somaxconn` 是全局参数、不随命名空间隔离，而应用侧 backlog 由镜像与进程决定，换一个容器或换一个内核主版本就要重新采集。`Send-Q` 已经等于应用期望值而计数仍在涨，瓶颈就是应用 `accept()` 太慢，此时改上限无效。
>
> 代价与顺序：把 `somaxconn` 调大能立刻抬高上限，但如果根因是 `accept()` 慢，它只把撞墙时间往后推，同时给这台机器加上一处与其它机器不同的配置。把 `tcp_abort_on_overflow` 置 1 会让内核在队列满时回 RST，故障从慢失败变成快速失败、更容易被监控发现，代价是把原本可能自愈的抖动放大成用户可见错误。因此顺序是先取证、再判断是上限还是节奏、最后才改配置，且一次只改一项并写清载体与回滚。

### 3.2 站在哪一层，说明什么

| 停留层 | 回答里缺的东西 | 缺口类型 | 回到哪一节 |
| --- | --- | --- | --- |
| 第 0 层 | 用"应用没日志"否定整条链 | 结论型 | 原理《连接的生命周期》2.1、2.2（握手与两个队列）；判例 3 |
| 第 1 层 | 机制正确，但落不到字段上 | 判据型 | 体系 3（建链与两个队列的关键字段表）；实操 4.2 的排查顺序 |
| 第 2 层 | 不知道判据在别的环境里会变 | 边界型 | 原理《连接的生命周期》2.2 末段（半连接队列满时改用 cookie）；判例 7、8 |
| 第 3 层 | 说不出三种动作的先后与代价 | 代价型 | 实操 4.3 判据表与"一份合格的回答"；治理 3.3、5 |

### 3.3 第一反应不要做什么

不要先怀疑网络抖动；不要在取证前重启服务；不要把 `tcp_abort_on_overflow` 当成一个可以随手开关的优化项。

## 4. 现象二：客户端 `SYN-SENT` 堆积、服务端队列计数不涨

### 4.1 逐层演进

**第 0 层**

> 服务端说它没收到 SYN，那就是网络断了，先把中间设备和云平台查一遍。

这一层跳过了"服务端在不在、有没有在跟踪连接"这两个前置问题，直接把结论推到主机之外。它在两处表里最像"深入排查"，实际上是最早的一处闭合。

**第 1 层（说出机制）**

> 客户端已经发出 SYN 并在等 `SYN+ACK`，如果服务端完全没有收到，通常意味着 SYN 在中间设备或连接跟踪表上被丢弃了；服务端侧只有一个握手计数器在动，客户端侧也只有这一条状态在堆。

机制说得对，但没有可读的字段：不知道服务端要读哪一个计数、读到 0 说明什么、客户端那一列状态从哪里来。

**第 2 层（给出判据）**

> 先确认服务端侧到底有没有看见握手：监听队列的两列加上半连接队列的两个计数 `TcpExtTCPReqQFullDoCookies` 与 `TcpExtTCPReqQFullDrop`。计数干净、而客户端 `ss -tan` 里 `SYN-SENT` 条数在涨，方向才落到中间设备；转发节点上再读 `nf_conntrack_count` 与 `nf_conntrack_max` 的比值与 `conntrack -S` 的 `drop`，以及 `dmesg` 里的 `table full, dropping packet`。客户端侧取数的字段是 `ss -tan` 的状态列，加 `-n` 避免反向解析把输出拖慢。

**第 3 层（给出边界与代价）**

> 边界有三条。其一，"这台机器没有在做连接跟踪"是正常状态而不是故障：`conntrack -C` 为 0 或统计文件不存在时，先确认有没有 NAT 与状态化规则，本机实测出现过模块已加载、NAT 规则存在而连接跟踪统计文件不存在的情形，此时这一路判据直接不成立。其二，这个计数的口径随内核主版本变化，老资料里"半连接队列由某个参数单独决定"的说法在现代内核上已不成立，判据只能落在计数器上，不能落在参数值上。其三，容器与云主机上要先把"在谁的栈里"确认清楚。 
>
> 代价与顺序：抓包有 CPU 与磁盘代价，必须限流、限时、落到独立目录，抓完及时清理；改 `tcp_syncookies`、动防火墙、放宽过滤规则都会改变故障形态，属于影响连通性的变更，要排窗口、准备回滚。可行顺序是先做两侧的只读采集，确认计数是否干净，再决定是否需要在宿主机侧与容器内对照取证。

### 4.2 站在哪一层，说明什么

| 停留层 | 回答里缺的东西 | 缺口类型 | 回到哪一节 |
| --- | --- | --- | --- |
| 第 0 层 | 跳过服务端就推到主机外 | 结论型 | 体系 6.3（主机内外）；判例 13 |
| 第 1 层 | 说不出两侧各读哪一列 | 判据型 | 实操 1 工具表；实操 4.1 的排查顺序 |
| 第 2 层 | 不知道"没有在跟踪"也是正常状态 | 边界型 | 原理《端口、套接字与多路复用》6；判例 12 |
| 第 3 层 | 说不出抓包与改过滤的代价顺序 | 代价型 | 实操 3.3 复现与清理边界；治理 4.4 |

### 4.3 第一反应不要做什么

不要在服务端反复重启应用；不要在主机侧计数干净时继续在本机调参；不要把"没有连接跟踪"当成故障。

## 5. 现象三：连接被立刻 `Connection refused`

### 5.1 逐层演进

**第 0 层**

> 连接被拒绝了，这台机器网络不通，先看看路由和网卡。

"被拒绝"与"不通"是两种结局：拒绝说明有回应，不通说明没有回应。把它们混在一起，会在链路与路由上白查一轮。

**第 1 层（说出机制）**

> `Connection refused` 是收到了 RST。来源有两类：端口上没有任何 socket 在监听，或者监听队列溢出时内核被配置成直接回 RST 而不是静默丢弃。要区分必须看服务端自己的记录。

因果成立，但没有落到字段：服务端"自己的记录"是哪两处、怎么读，仍然空着。

**第 2 层（给出判据）**

> 先读监听：`ss -lntp` 看这个端口有没有 socket、绑定的是 `0.0.0.0` 还是 `127.0.0.1`。有监听而客户端仍被拒绝时读第二处：`TcpExtListenOverflows` 与 `TcpExtListenDrops` 的差值配上 `net.ipv4.tcp_abort_on_overflow` 的当前值。两处都干净、客户端依然立刻被拒，才轮到过滤设备，字段在 `nft list ruleset` 的规则集里。

**第 3 层（给出边界与代价）**

> 边界有三条。绑定范围会改变结论：只绑环回地址时外部永远连不上，而 `[::]` 这类绑定在不同内核与发行版上对 IPv4 客户端的接受行为不同，判据只能是 `ss -lntp` 的实际绑定，不能凭记忆推断。换了发行版或换了监听进程的启动方式，同一个端口可能落在另一个 socket 上。容器场景下宿主机的 `ss` 看不到容器里的端口，这不是故障。 
>
> 代价与顺序：改 `tcp_abort_on_overflow` 或改绑定范围都是影响连通性的变更，会改变故障形态或让部分来源无法访问。顺序是先只读确认"有没有监听、绑在哪"，再确认溢出计数，最后才动配置。把这一现象直接按"网络不通"处置，实际的代价是把一次可以在三十秒内定位的配置问题拖成一小时。

### 5.2 站在哪一层，说明什么

| 停留层 | 回答里缺的东西 | 缺口类型 | 回到哪一节 |
| --- | --- | --- | --- |
| 第 0 层 | 把"被拒"当成"不通" | 结论型 | 原理《分层模型与数据包的一生》3、4；判例 2 |
| 第 1 层 | 知道有 RST，说不出两处记录在哪 | 判据型 | 实操 4.1 第 1、3 步 |
| 第 2 层 | 不知道绑定范围与 IPv6 行为会变 | 判据型（口径） | 原理《地址、路由与邻居》2 末段 |
| 第 3 层 | 说不出改绑定与改开关的影响面 | 操作型 | 治理 2 三条判据；治理 4.2 |

### 5.3 第一反应不要做什么

不要把它当成"网络不通"；不要先查路由表；不要在没看 `ss -lntp` 的绑定地址前改防火墙。

## 6. 现象四：`ping` 通但端口连不上

### 6.1 逐层演进

**第 0 层**

> `ping` 是通的，说明网络没问题，这是应用自己的事。

`ping` 只覆盖网络层的 ICMP，它通只能排除这一层；把"这一层通"当成"网络没问题"，是本篇最省事也最常被引用的一句结论。

**第 1 层（说出机制）**

> `ping` 走的是 ICMP，端口通不通属于传输层；ICMP 与 TCP 常被防火墙区别对待，所以"`ping` 通而 TCP 不通"和反过来都是常见形态。

因果对了，但"区别对待"体现在哪个规则集、要读哪一列，仍然没有落点。

**第 2 层（给出判据）**

> 按层往下问，每一步都要有字段：端口在不在听（`ss -lntp` 的绑定地址列）；TCP 能不能建连（`nc -vz` 的两种结局——超时说明被丢、`refused` 说明被拒）；名字是否与应用一致（`getent hosts`，**不是** `dig`）；是否被过滤（`nft list ruleset`）；队列是否溢出（`nstat` 的 `TcpExtListenOverflows` 与 `TcpExtListenDrops` 差值）。

**第 3 层（给出边界与代价）**

> 边界有三条。第一，两者的差别不只在协议：判据要求用与应用同一条路径取数，`dig` 绕过名字服务开关，`getent hosts` 才是应用视角，所以"`dig` 通"不能用来否定应用的报错。第二，IPv4 与 IPv6 的监听与过滤是两套，`[::]` 的接受行为随内核与发行版而变，换环境后必须重新看实际绑定。第三，容器里必须先进对应命名空间取证，宿主机的 `ss` 与 `ip route` 都不等于容器内的视图。
>
> 代价与顺序：这一节的每一步都是只读的，可以在生产机上直接做，所以顺序上应当把五步全部走完再谈动作；唯一有代价的是抓包（限流限时）与改过滤规则、改绑定（影响连通性，需要窗口与回滚）。跳过只读的层次直接改规则，代价是把一个"没监听"的问题改成一堆"与别人不同"的规则。

### 6.2 站在哪一层，说明什么

| 停留层 | 回答里缺的东西 | 缺口类型 | 回到哪一节 |
| --- | --- | --- | --- |
| 第 0 层 | 用一层的结果否定其余四层 | 结论型 | 判例 1、2；原理《分层模型与数据包的一生》3 |
| 第 1 层 | 说不出每一层的取数字段 | 判据型 | 实操 4.1 五步；实操 1 工具表 |
| 第 2 层 | 不知道两个视角与两个地址族各是一套 | 判据型（口径） | 原理《连接的生命周期》1.2；原理《地址、路由与邻居》2 |
| 第 3 层 | 不知道哪一步可以在生产机上做 | 操作型 | 实操 3.1 采样纪律；实操 4.10 |

### 6.3 第一反应不要做什么

不要把 `ping` 通当成 TCP 通；不要用 `dig` 的结果否定应用的报错；不要在没确认命名空间前用宿主机视图下结论。

## 7. 现象五：`ss -s` 显示大量 `TIME_WAIT`，或 `CLOSE_WAIT` 缓慢上涨

### 7.1 逐层演进

**第 0 层**

> 这么多 `TIME_WAIT`/`CLOSE_WAIT`，一定是内核参数没调好，把超时改短、或者干脆重启把连接清掉。

这一层把两个归属完全不同的状态并成了一句动作。它们的相同点只有"名字里都有 WAIT"。

**第 1 层（说出机制）**

> `TIME_WAIT` 只出现在主动关闭方，时长由内核常量固定为 2MSL（Linux 上是 60 秒），没有任何可调参数；`CLOSE_WAIT` 是被动关闭方收到了对端 FIN 而应用还没有 `close()`，内核已经做完，剩下的动作在应用代码里。

机制正确，但没有指出"谁是主动关闭方"该怎么判定，也没有给出句柄趋势的取数位置。

**第 2 层（给出判据）**

> 先判方向：`ss -tan state time-wait` 看本地端口是服务端口还是临时端口，服务端口说明本机是主动关闭方。再算容量：`sysctl net.ipv4.ip_local_port_range` 的端口数（现场取）与"出向短连接 QPS × 60 秒"比较，同时读 `TcpExtTCPTimeWaitOverflow` 的差值——它是撞上 `tcp_max_tw_buckets` 的唯一信号，日志里可能什么都没有。`CLOSE_WAIT` 方向读三处：`ss -tanp state close-wait` 找出进程、按进程聚合找出泄漏者、`/proc/<pid>/fd` 的条数有没有单调增长。

**第 3 层（给出边界与代价）**

> 边界有三条。`TIME_WAIT` 计数只在 TCP 上成立，UDP 没有连接状态，这类堆积在那里不存在。`CLOSE_WAIT` 的句柄稳定在高位而不增长时，要查的是连接池上限与并发模型，不是"泄漏"。复用类参数的适用范围也要现场核：本机 `tcp_tw_reuse` 的取值决定了它是否、以及在哪些路径上生效，它不会让条数变少，只影响本机主动发起的连接能否复用四元组。 
>
> 代价与顺序：改应用是根治，代价是开发周期；扩源端口范围能抬高天花板，代价是与保留端口的重叠需要评估；复用参数能救源端口耗尽的报错，代价是需要时间戳支持且不减少条数；跳过等待保护是回退路径，代价是破坏这一状态存在的两条保护。顺序是先改应用、再扩端口、最后才谈参数。

### 7.2 站在哪一层，说明什么

| 停留层 | 回答里缺的东西 | 缺口类型 | 回到哪一节 |
| --- | --- | --- | --- |
| 第 0 层 | 把两个方向相反的状态并成一个动作 | 结论型 | 原理《连接的生命周期》4.2；判例 5、6 |
| 第 1 层 | 说不出方向怎么判、句柄从哪读 | 判据型 | 实操 4.6 两条排查顺序 |
| 第 2 层 | 不知道复用参数的范围与状态口径 | 判据型（口径） | 体系 4.2；原理《连接的生命周期》4.4 |
| 第 3 层 | 说不出四种做法的代价排序 | 代价型 | 治理 3.1；体系 6.1 队列与上限 |

### 7.3 第一反应不要做什么

不要调 `tcp_fin_timeout` 去治 `TIME_WAIT`；不要看到 `CLOSE_WAIT` 就调内核参数；不要在没算容量前先重启或清理。

## 8. 现象六：TCP 连得上但吞吐上不去，`ss -ti` 里出现 `retrans` 或 `app_limited`

### 8.1 逐层演进

**第 0 层**

> 带宽监控显示没用满，那一定是带宽不够，先申请扩容。

扩容只对四类瓶颈里的一类有效，而且是最少被证明的那一类：带宽不足的表现是吞吐贴近链路容量同时排队与丢包一起上升，而不是"带宽闲着、单流慢慢走"。

**第 1 层（说出机制）**

> "慢"有四种来源：应用没喂满连接、接收窗口或拥塞窗口受限、链路丢包重传、路径 MTU 变小。它们的责任方各不相同，所以第一步是分类而不是调优。

机制完整，但"分类"用什么工具、看哪一个字段，没有落点。

**第 2 层（给出判据）**

> 一条命令分四类：`ss -ti` 里出现 `app_limited` 说明应用没有喂满连接，责任方在应用；`retrans` 与 `lost` 明显时结合 `nstat` 的 `TcpRetransSegs` 与 `TcpOutSegs` 算增量比，与自己的基线比较，而不是与外来的阈值比较；`cwnd` 小且 `minrtt` 大说明窗口与带宽延迟积不匹配；`pmtu` 异常小或 `ping -M do` 大包全丢说明瓶颈在 MTU。`snd_wnd` 很小甚至为 0 则说明对端应用不读。

**第 3 层（给出边界与代价）**

> 边界有三条。重传率的合理水平与链路、业务形态强相关，只能与自己的基线比，拿别人的阈值来套会在正常链路上制造告警；换一个网卡型号或驱动，链路层的计数名与可用字段都会变。`app_limited` 与丢包可能同时存在，此时先解决应用再评估链路，顺序反过来会得出"扩容也没用"的结论并从此不再看这一层。拥塞控制算法的判据也不同，换算法影响全机所有连接，不是一次局部调整。 
>
> 代价与顺序：调大缓冲区上限能覆盖更大的带宽延迟积，代价是每条连接占用更多内存，且它只解决窗口受限这一类；扩容是成本最高、见效最慢的一步。顺序是先按字段分类，再排除 MTU，再评估窗口与缓冲，最后才谈带宽。

### 8.2 站在哪一层，说明什么

| 停留层 | 回答里缺的东西 | 缺口类型 | 回到哪一节 |
| --- | --- | --- | --- |
| 第 0 层 | 把"慢"等同于"带宽不够" | 结论型 | 判例 10；原理《连接的生命周期》3.2 |
| 第 1 层 | 知道四类，说不出各自的字段 | 判据型 | 体系 4.1 四类瓶颈判据表；实操 4.4 |
| 第 2 层 | 不知道阈值只能来自自己的基线 | 判据型（口径） | 实操 2.2 两条铁律；治理 5 三条纪律 |
| 第 3 层 | 说不出两种窗口受限的处置代价 | 代价型 | 原理《连接的生命周期》3.3；实操 4.4 第 5 步 |

### 8.3 第一反应不要做什么

不要先扩带宽；不要用外来的重传率阈值判断自己的链路；不要在没分清 `app_limited` 与丢包前改缓冲区。

## 9. 现象七：`ping` 通、小请求通，大响应卡住

### 9.1 逐层演进

**第 0 层**

> 小请求都正常，只有大文件慢，那是带宽不够，扩一下。

这一层的动作与上一节第 0 层相同，但它错得更彻底：带宽不足不会表现为"小包正常、只在大响应时超时"，这个组合本身就是尺寸问题的形态。

**第 1 层（说出机制）**

> 路径上某一跳的 MTU 比两端都小，大包在禁止分片时被静默丢弃；小包因为尺寸没到阈值所以一路通过。要确认必须让内核不要替你分片。

因果对了，但"让内核不要分片"是哪一个选项、比对哪两个值，仍然没写。

**第 2 层（给出判据）**

> `ping -M do -s 1472 <ip>` 一次性定性，必须带 `-M do`，否则内核分片会掩盖问题；失败就逐步缩小 `-s` 找出实际可用尺寸。再用 `ip link show` 比对两端接口的 `mtu`，用 `ss -ti` 的 `pmtu` 与 `mss` 看协商结果，`mtr -n -r` 定位是哪一跳。隧道与 overlay 会额外占掉空间，字段是封装类型与它对应的开销。

**第 3 层（给出边界与代价）**

> 边界有三条。ICMP 被禁时路径 MTU 发现失效，判据会表现为"大包全丢却收不到任何差错报文"，此时才轮到逐级探测或 `tcp_mtu_probing` 这类回退路径。地址族会改变结论：IPv6 的固定头更长，同一个 `-s` 在两种协议下测的不是同一个尺寸；换发行版或换隧道类型，默认 MTU 与封装开销都要重新取。两端 MTU 一致而仍丢大包时，方向是路径与封装，不是本机配置。
>
> 代价与顺序：改 MTU 作用于这块网卡上的全部流量、会短暂断流，远程操作时可能把自己关在门外，所以要先确认影响面、排窗口、准备带外入口与回滚命令，验收标准是同位置的业务探测恢复而不是"命令没报错"。打开这类探测回退参数属于影响全机连接的变更，代价是可能带来额外的重传。顺序是先只读探测定性，再改一处并复测。

### 9.2 站在哪一层，说明什么

| 停留层 | 回答里缺的东西 | 缺口类型 | 回到哪一节 |
| --- | --- | --- | --- |
| 第 0 层 | 把尺寸问题当成容量问题 | 结论型 | 判例 11；原理《分层模型与数据包的一生》7 |
| 第 1 层 | 知道是 MTU，说不出探测方式 | 判据型 | 实操 4.5 排查顺序 |
| 第 2 层 | 不知道地址族与封装会改变判据 | 边界型 | 原理《分层模型与数据包的一生》7 三条边界 |
| 第 3 层 | 不知道改 MTU 的影响面与回滚要求 | 操作型 | 治理 4.4 检查单；实操 4.5 动作方向 |

### 9.3 第一反应不要做什么

不要先扩带宽；不要用不带 `-M do` 的 `ping` 判断大包；不要在没窗口、没带外入口的情况下改 MTU。

## 10. 现象八：`conntrack` 相关的静默丢包与乱序归因（容器与转发节点）

### 10.1 逐层演进

**第 0 层**

> 这台机器是容器节点，转发全靠连接跟踪，所以先确认跟踪表是不是满了、把上限调大。

在真正做转发的节点上这个方向是合理的，但把"调大上限"直接当成结论，跳过了"这张表在这台机器上到底有没有在跟踪连接"这个前置判断。

**第 1 层（说出机制）**

> 连接跟踪表满时内核静默丢包，应用只会超时；表的容量由上限参数决定，条目数与上限的比值是水位。转发与状态化规则都依赖它。

机制正确，但没有指出水位从哪里读、以及"读不到"意味着什么。

**第 2 层（给出判据）**

> 先确认这台机器在不在跟踪：`nft list ruleset` 里有没有 NAT 或状态化规则、`lsmod` 里有没有相关模块、统计入口是否存在。确认在跟踪之后再读水位：条目数与上限的比值、统计里的 `drop`、以及内核日志里的 `table full, dropping packet`。容器场景还要看规则集里服务转发与网络策略的痕迹，以及宿主机侧的接口与路由。

**第 3 层（给出边界与代价）**

> 边界有三条。不在转发的机器上这套判据一条都不成立，给所有机器套同一份容量模板是错的。本机实测出现过模块已加载、NAT 规则存在，而连接跟踪的统计文件不存在的情形，所以"统计文件在不在"不能单独当作判据。容器把这件事放大：容量参数按命名空间不同而不同，宿主机上的比值不代表容器内的比值。 
>
> 代价与顺序：调大上限能立刻止血，代价是每条条目的内存开销与查找性能，而且如果连接来源是应用连接泄漏，它只是把撞墙时间往后推；改超时参数会让长连接被提前回收，代价落在业务上。顺序是先确认在跟踪、再看水位与趋势、先治本（连接复用）再谈扩容。

### 10.2 站在哪一层，说明什么

| 停留层 | 回答里缺的东西 | 缺口类型 | 回到哪一节 |
| --- | --- | --- | --- |
| 第 0 层 | 跳过"有没有在跟踪连接"直接调上限 | 结论型 | 治理 3.2 两个反直觉点；判例 12 |
| 第 1 层 | 说不出水位与"读不到"的含义 | 判据型 | 体系 4.3；实操 4.7 第 3 步 |
| 第 2 层 | 不知道容量只在转发节点上成立 | 边界型 | 治理 3.2；治理 4.1 "不存在的东西" |
| 第 3 层 | 说不出条目的内存与查找代价 | 代价型 | 治理 2 三条判据；治理 4.2 |

### 10.3 第一反应不要做什么

不要给所有机器套同一份容量模板；不要把"统计文件不存在"当采集失败；不要在没确认连接来源前先调大上限。

## 11. 五个跨阶段的核对对象

主线之外的五个量贯穿全部阶段。它们不产生新的现象，但每一个判断都要用到，所以单独列出来定位。

**队列与上限——"够不够"与"谁在排队"是两个问题。**

> 停在第 0 层的说法是"机器很空闲，怎么会连不上"，第 1 层能说出链路上有一串排队点、每一处的溢出后果不同，第 2 层能指出每一处读哪两列或哪个计数、以及比值与差值怎么取，第 3 层知道同一类排队在宿主与容器内的上限来源不同、静默丢弃与拒绝是两种结局。判据缺失时的表现是：改了某一个参数却不知道它治的是哪一个排队点。

**证据与计数——瞬时值、累计值与抓包各自只能回答一部分。**

> 停在第 0 层的说法是"看一眼 `ss` 就清楚了"，第 1 层知道一次瞬时采样看不到偶发事件、累计计数必须取差值、应用日志覆盖不到未 `accept()` 的连接，第 2 层能给出三者的取数字段与两个维度对照的用法，第 3 层知道计数器的可用字段随内核与驱动变化、换机型或换主版本就要重新确认。判据缺失时的表现是：用一次采样或一个计数器给故障定性。

**名字解析——应用解析的结果不是 DNS 直接给的。**

> 停在第 0 层的说法是"DNS 坏了"，第 1 层能说出应用走名字服务开关、`dig` 绕过它，第 2 层指出三条配置的顺序、后缀与点数选项、存根与真实上游分别从哪里读，第 3 层知道容器内是另一条解析链、改记录后要等缓存与 TTL 过期。判据缺失时的表现是：反复换上游，却说不清一次解析被放大成了几次查询。

**主机内外——主机侧干净不等于已经查完。**

> 停在第 0 层的说法是"本机没问题，去找网络组"，第 1 层能说出主机外还有安全组、负载均衡、云网络与对端，第 2 层指出判定需要哪三样证据（本机计数干净、两侧限时限流对照、按出口路径定位），第 3 层知道抓包的代价与位置选择、以及"这边发了、那边没收到"是二分定位而不是结论。判据缺失时的表现是：在本机反复调参，问题不消失而配置越来越特殊。

**变更纪律——任何一次改动都要能回滚。**

> 停在第 0 层的说法是"先改上去试试"，第 1 层能说出不同的参数写在不同的载体上、生效方式与持久化位置不同，第 2 层指出变更记录要写全哪些栏、原始值从哪里取，第 3 层知道一次只改一项、观察一个业务周期、无效则回滚而不"先留着看看"。判据缺失时的表现是：重启之后值没了，或者复现不了自己上一次的动作。

五个核对对象共有的定位信号是"知道有这个机制，但每次都要重新推一遍"——它说明判据没有落到字段上，补法是回到体系第 6 节，把每个核对对象在这台机器上的字段、单位、判据与转向抄成一张自己的对照表。

## 12. 交付物是排查的凭证

定位缺口不能只靠回想。下面几件物件是把"我做过"与"我读过"分开的唯一办法，缺少它们时，本篇第 3 至第 11 节的自评很可能整体偏高。

**环境**：内核 `6.8.0-139-generic`；发行版 Ubuntu 24.04.5 LTS；不在容器内（VMware 虚拟机，非容器，`/run/systemd/system` 存在）。

| 现象 | 当时读到的字段 | 判据 | 边界 | 缺口层 |
| --- | --- | --- | --- | --- |
| 队列溢出（实测） | `ss -lnt` 报 `Recv-Q 2` / `Send-Q 1`；`TcpExtListenOverflows` 从 30 增到 66；`TcpExtListenDrops` 从 30 增到 66；`net.core.somaxconn=4096`、`tcp_abort_on_overflow=0`、`tcp_syncookies=1` | 差值 36 说明这段时间发生了溢出；`Recv-Q > Send-Q` 说明采样时刻正满；上限取两值之小 | 采样在 25 秒的服务窗口内，第二次读时 socket 已释放、瞬间判据消失，只剩计数留下了痕迹 | 第 2 层（判据已落到字段） |

| 连接跟踪水位（实测） | `nf_conntrack_count=10`、`nf_conntrack_max=262144`；`conntrack -S` 各 CPU 的 `drop=0`；`lsmod` 有相关模块；`/proc/net/stat/nf_conntrack` **不存在** | 比值 10/262144、`drop` 增量为 0 | 模块在、NAT 规则在、统计文件却不在，说明"统计文件在不在"不能单独当判据 | 第 3 层（边界型缺口） |
| MTU 黑洞（未实测） | `pmtu:1500`、`mss:1460`；`ip -s link ens33` 的 `errors/dropped/missed` 全为 0 | 需要路径上更小的一跳才会出现 | 未实测：单台虚拟机没有可缩小 MTU 的中间跳，需搭多节点或命名空间链路 | 第 2 层（字段名已知，未取到现场） |
| 解析放大（实测） | `/etc/nsswitch.conf` 为 `hosts: files dns`；`/etc/resolv.conf` 为 `nameserver 127.0.0.53` + `options edns0 trust-ad` + `search localdomain`；`time getent hosts localhost` 为 0.00 秒级 | 存根地址不是上游；后缀数决定放大倍数 | 本机只有一个 `search` 域，放大效应不明显，容器里注入的搜索域数量不同 | 第 2 层（口径已落到字段） |

状态用三个固定的词：实测、转引、未实测。"转引"要写出处（man 节号、内核文档路径或 RFC 编号）。把读过的当做过是这份记录唯一无法挽救的失效方式：环境更换后结论被推翻，而记录里看不出哪些结论本来就没有实测支撑。**字段列在未实测时也要照实写**：写"未取到"或写字段名并标注未实测，不要留空，也不要填一个看起来合理的数字。

表里那两个计数器只增不减，实验中造成的增量会留在实验机的开机周期里；照这张表复核时要先取一次读数作参照，再算差值，不要拿别处的零值当基线。实验用的监听 socket、进程与临时文件都已清理，实验前后参数值未发生改动。

复查日期只写 D+1、D+3、D+7、D+21 四个；没有日期的错题等于没有复查。

## 14. 定位到缺口之后补什么

六个类型的补法不同，用错补法会补到不需要补的地方。

| 缺口类型 | 表现 | 补法 | 不要做什么 |
| --- | --- | --- | --- |
| 结论型 | 停在现象命名与动作，连机制都不熟 | 回到对应的原理篇，用自己的话写出机制，并配一个"这个机制不成立会看到什么"的反例 | 不要从背结论开始 |
| 判据型 | 机制清楚，落不到字段 | 重新执行一次命令，记录输出形态与关键数值，而不是只记命令名 | 不要只记命令不记输出 |
| 判据型（口径） | 分不清同一个量的多个口径、瞬时值与累计值 | 把该字段的口径、单位、窗口、与谁同看写成一行；凡累计值一律标注"取差值" | 不要把不同口径的数放进同一张对比表 |
| 边界型 | 结论正确，换环境即失效 | 列三条反例：换内核主版本、换发行版、换容器环境各核一次 | 不要以"应该大致相同"作结 |
| 代价型 | 知道怎么做，不知道风险 | 补三行：代价、回滚方式、影响面 | 不要把风险留给别人发现 |
| 操作型 | 讲得出、没做过 | 在可快照实验机上做一次只读采集与一次可回滚变更，留下带时刻的原始输出 | 不要用纸面推演代替动手 |

带着一个具体缺口回到一到两篇，比重读整章有效。如果发现"每篇都要重读"，通常说明缺的不是细节，而是前置概念——回到本章地图确认六段主线各阶段与五个跨阶段的核对对象各自提供什么。

## 15. 边界

本篇覆盖的范围与本章一致，落在别处的追问照实划出去：应用协议本身的语义（HTTP 状态码、证书与认证）、进程与文件描述符层面的原因（应用挂起在存储等待上）、服务单元与编排层的停止与重启语义、以及内存与 IO 压力造成的整体变慢，都不在本章范围内。遇到这类追问，正确回答是指出它属于哪一类领域，而不是在本章内部勉强作答。

落在本章之内但需要设备侧配合的部分只做划界，不给具体出处：安全组、负载均衡与云网络的策略细节在主机之外，本章只负责给出"什么时候可以判定问题不在本机"的判据。

本篇的判据只引用本章出现过的字段。引用章外指标时，测的是别的东西，缺口也会被错误归因。

核查动作用只读方式，本篇第 3 至第 10 节的绝大部分步骤都可以在生产机上直接执行；凡需要变更才能验证的项（改 MTU、改队列规则、改过滤规则、动环缓冲），在可快照的实验机上做，并留下回滚命令与观察窗口。

## 16. 核对方式

从本章地图的故障现场定位表抽四行（覆盖队列、连接状态、名字解析、链路尺寸各至少一类），逐行遮住右侧自测；每项说出所处阶段、首查字段、判据、一条边界、一句"第一反应不要做什么"。说完之后自己回答一个问题：**刚才哪一句指不到字段**。指不出的那一句就是当前所处的位置，据此翻回第 3 至第 10 节的对应表格。

再抽一项承接两层追问：第一层问"依据是什么"，第二层问"换个环境还成立吗"。第二层答不出的，缺口在边界型，补法见第 14 节。

## 常见坑

| 常见做法 | 后果或事实 |
| --- | --- |
| 把这篇当成一张评分表 | 它的用途是定位停在哪一层，不是给出通过与否；当成评分表用，定位信息会被一个判定吃掉 |
| 用"读了几遍"判断自己会不会 | 阅读次数与现场提取的强度无关，只与能否当场给出判据有关 |
| 用术语熟练度代替动手 | 名字记得住、机器上没取过，缺的是操作层 |
| 机制讲得流畅就认为已经查完 | 判据落不到字段上，是本篇最常见的一种失效 |
| 缺口用"没记住"概括 | 缺的类型不同补法不同，概括之后一定补错方向 |
| 未实测项不标注 | 环境更换后无法分辨哪些结论本来就没有实测支撑 |
| 一次把八类现象都读完 | 逐现象一次读一层、对照一次，比通读一遍有效 |
| 拿本篇的字段名到别的机器上直接用 | 字段是否可用随内核主版本、发行版与驱动变化，先现场取一次 |

## 要点自测

**问：第 1 层与第 2 层在语言外观上几乎一样，区分它们的那一个动作是什么？**
答：能不能指到一个字段。指不到字段的机制叙述停在第一层。

**问：为什么"服务端应用没有日志"不能推出"请求没有到达主机"？**
答：握手由内核完成，连接可以先进入全连接队列（在 `ss` 里是 `ESTAB`）而应用从未见过它；队列满时内核默认静默丢弃，所以应用没有日志与客户端超时可以同时成立。

**问：`TIME_WAIT` 与 `CLOSE_WAIT` 的处置方向为什么相反，判据是什么？**
答：前者是主动关闭方的正常状态，时长由内核常量决定，处置方向是减少主动关闭与扩源端口；后者是被动关闭方的应用没有 `close()`，只能改应用。判据是看本地端口是服务端口还是临时端口，确定谁是主动关闭方。

**问：`ping` 通、小请求通、大响应卡住，为什么"带宽不够"是最可能的错误结论？**
答：带宽不足不会表现为只在大响应时超时；这个组合是尺寸问题的形态，判据是一次带 `-M do` 的探测与两端 `mtu` 比对。

**问：为什么"`conntrack -C` 是 0"要分两种含义看？**
答：一种是真的没有条目，另一种是这台机器根本没有在做连接跟踪——没有 NAT 或状态化规则时统计入口可能不存在。先确认在不在跟踪，再读水位。

**问：交付物里为什么必须有只读基线卡与可回滚变更记录？**
答：前者决定"有没有真取到值"，后者决定"是否知道验收依据与回滚方式"；缺前者时第 2 层的自评没有依据，缺后者时第 3 层的代价意识无从体现。

**问：五个跨阶段的核对对象共有的定位信号是什么？**
答："知道有这个机制，但每次都要重新推一遍"——说明判据没有落到字段上，缺的是可复用的对照表。
