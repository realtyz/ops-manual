## 0. 30 秒速览

> [!abstract] 这一篇只要记住六句话
> - **`ip route get <目标>` 是最有用的一条命令**
>   - 证据：本机实测 `ip route get 223.5.5.5` → `223.5.5.5 via 192.168.246.2 dev ens33 src 192.168.246.128 uid 0`；加 `from` 后 `ip route get 8.8.8.8 from 192.168.246.128` → `from 192.168.246.128 via 192.168.246.2 dev ens33`。比翻路由表猜快得多。
> - **同网段靠邻居（ARP/NDP），跨网段靠网关**
>   - 怎么验证：`ip neigh` 里网关 `192.168.246.2` 的 lladdr 是 `00:50:56:f3:d9:3c`；同网段的目的 MAC 就是对端的，跨网段的目的 MAC 是**网关**的。
> - **路由匹配是「最长前缀优先」**
>   - 证据：本机 `ip route` 实测两条——`default via 192.168.246.2 dev ens33 proto static` 与 `192.168.246.0/24 dev ens33 proto kernel scope link src 192.168.246.128`；掩码更长（更具体）的规则胜出，只有默认路由时所有不匹配流量都走它。
> - **源地址是「选」出来的**
>   - 证据：`ip route get` 的 `src 192.168.246.128` 就是内核最终选的源地址；**服务绑在 `127.0.0.1` 时外部永远连不上**，这不是路由问题而是绑定问题（子笔记 05）。
> - **`ip neigh` 里 `INCOMPLETE`/`FAILED` = 二层没通**
>   - 证据：本机实测邻居表是 `192.168.246.2 … STALE` 与 `192.168.246.1 … REACHABLE`——`STALE`/`REACHABLE` 都正常，先看有没有 `INCOMPLETE`/`FAILED`。
> - **`ip rule` 是「先选表、再查表」**
>   - 证据：本机 `ip rule show` 实测就是默认三条 —— `0: from all lookup local` / `32766: from all lookup main` / `32767: from all lookup default`；多网卡、多出口、容器与策略路由场景下「为什么走了另一条路」的答案在这里。

## 1. 地址：IP、掩码与网段

### 1.1 IPv4 地址与 CIDR

一个 IPv4 地址是 32 位，写作 `10.0.0.1`。它总是和**前缀长度**一起出现，例如 `10.0.0.1/24`：

| 写法 | 含义 | 这个网段里的可用地址 |
| --- | --- | --- |
| `10.0.0.1/24` | 前 24 位是网络位，后 8 位是主机位 | `10.0.0.1` ~ `10.0.0.254`（`.0` 是网络地址、`.255` 是广播地址，通常不用） |
| `10.0.0.1/32` | 只有这一个地址（常用于回环、VIP、容器地址） | `10.0.0.1` |
| `192.168.240.128/20` | 前 20 位是网络位 | `192.168.240.0` ~ `192.168.255.255` |

判断「两个地址在不在同一个网段」的办法：把两个地址都按前缀长度截断，看结果是否相同。**在同一个网段 → 直接找对方；不在同一个网段 → 交给网关**。

```bash
ip -br addr                        # 验证：所有接口的地址（紧凑视图，比 ifconfig 好读）
ip addr show dev ens33             # 验证：某个接口的地址、掩码、状态、MAC
```

```text
lo               UNKNOWN        127.0.0.1/8 ::1/128
ens33            UP             192.168.246.128/24 fe80::20c:29ff:fe66:2c0f/64
```

（以上是**本实验机**上 `ip -br addr` 的实测输出：只有一个物理接口 `ens33`，IPv4 是 `192.168.246.128/24`，另有链路本地 IPv6 地址。）

### 1.2 IPv6 简记

IPv6 在运维现场越来越常见（云环境、容器、Kubernetes 双栈）。只需要先记住三件事：

1. **地址更长，但结构一样**：也是「前缀 + 接口标识」，用 `/64` 的网段占绝大多数。
2. **没有广播，用多播与邻居发现（NDP）**：功能对应 IPv4 的 ARP。
3. **一个接口通常同时有多个地址**：链路本地地址（`fe80::/10`）、全球地址、临时地址。`ss -lnt` 里的 `[::]:8080` 表示同时接受 IPv6 与 IPv4（取决于 `net.ipv6.bindv6only`）。

> [!warning] 「服务只监听了 IPv6」是常见的低级故障
> `ss -lnt` 显示 `[::]:8080` 时，多数系统同时接受 IPv4；但如果应用显式绑定了某个 IPv6 地址，IPv4 客户端就连不上。**判断方法永远是 `ss -lntp` 看实际绑定**，不要凭 `netstat` 的老记忆。

## 2. 路由：内核怎么决定「从哪出去」

### 2.1 路由表里有什么

```bash
ip route                           # 验证：主路由表（多条默认路由时尤其要看）
ip route show table all | head -40 # 验证：所有路由表（含 local、策略路由用的自定义表）
```

```text
default via 192.168.246.2 dev ens33 proto static
192.168.246.0/24 dev ens33 proto kernel scope link src 192.168.246.128
```

| 字段 | 含义 |
| --- | --- |
| `default via 192.168.246.2` | 默认路由：所有不匹配其他规则的流量都发给这个网关 |
| `dev ens33` | 出口网卡 |
| `proto kernel` / `proto static` | 这条路由是谁装的（内核自动生成 / 静态配置，本机由 `systemd-networkd` 写入） |
| `scope link` | 目标直接在链路上可达（不需要网关） |
| `src 192.168.246.128` | 这条路由倾向使用的源地址 |
| `metric` | 优先级：**数值越小越优先**；多条等价路由时用得上（本机是单出口，所以输出里没有 `metric` 字段） |

### 2.2 一次真实的选择：`ip route get`

排障时**不要靠人脑算路由表**，直接问内核：

```bash
ip route get 223.5.5.5                       # 验证：到公网目标实际怎么走
ip route get 8.8.8.8 from 192.168.246.128    # 验证：指定源地址时的路由结果
```

```text
223.5.5.5 via 192.168.246.2 dev ens33 src 192.168.246.128 uid 0
    cache
8.8.8.8 from 192.168.246.128 via 192.168.246.2 dev ens33 uid 0
    cache
```

这两行给出四个关键信息：**下一跳（`via`）、出口网卡（`dev`）、源地址（`src`）、发起者（`uid`）**。所以「为什么走了另一条路」这类问题的标准问法就是：

```text
ip route get <目标地址>
```

> [!tip] `ip route get` 排障的三个典型用法
> ① **多网卡机器上确认出口**：判断流量到底从内网口还是管理口出去；② **确认源地址**：应用报「源地址不对」时，用 `src` 一眼定位；③ **确认是否走策略路由**：加上 `from <源地址>` 可以看到指定源地址时的选择结果。
> ```bash
> ip route get 8.8.8.8 from 192.168.246.128   # 验证：指定源地址时的路由结果
> ip route get 8.8.8.8 iif ens33              # 验证：从某接口进来的流量怎么走
> ```

### 2.3 同一网段与跨网段：目的地 MAC 是谁

| 场景 | 目的 IP | 目的 MAC | 中间经过 |
| --- | --- | --- | --- |
| 同网段（`10.0.0.2` → `10.0.0.1/24`） | `10.0.0.1` | **对端的 MAC** | 可能只经过交换机 |
| 跨网段（`10.0.0.2` → `8.8.8.8`） | `8.8.8.8` | **网关的 MAC** | 网关 → 后续每一跳重新封装 |

这也是为什么「同网段不通」和「出网不通」要看不同的东西：前者先看邻居表，后者先看默认路由与网关。

## 3. 邻居（ARP/NDP）：把 IP 换成 MAC

```bash
ip neigh                           # 验证：邻居表状态（旧命令是 arp -n）
ip -s neigh                        # 验证：加上统计（used/confirmed 计数）
```

```text
192.168.246.2 dev ens33 lladdr 00:50:56:f3:d9:3c DELAY
192.168.246.1 dev ens33 lladdr 00:50:56:c0:00:08 REACHABLE
```

| 状态 | 含义 | 是否正常 |
| --- | --- | --- |
| `REACHABLE` | 最近确认过，可以直接用 | 正常 |
| `STALE` | 条目还有效，但需要重新确认后才会用 | 正常（很常见） |
| `DELAY` / `PROBE` | 正在确认可达性 | 过渡状态 |
| `INCOMPLETE` | 发了请求，还没收到回应 | **二层可能不通** |
| `FAILED` | 多次重试都没回应 | **二层不通 / 对端不响应** |

邻居表最常见的两类现象：

- **同网段不通，`ip neigh` 显示 `INCOMPLETE`/`FAILED`**：对端没开、网线/VLAN 不对、被隔离，或者地址配错了网段。
- **`REACHABLE` 满满一片但流量还是不通**：邻居层没问题，往上查 IP 之上的层（防火墙、端口、路由）。

```bash
ip neigh show 192.168.246.2        # 验证：单独看某个邻居（本机网关）
ping -c2 192.168.246.2             # 验证：触发邻居解析（会更新邻居表）
```

## 4. 源地址选择、多网卡与策略路由

### 4.1 源地址不是「配了哪个就用哪个」

内核在发一个包时，会选一个**最合适的源地址**：优先选与出口接口在同一网段、且满足策略约束的地址。所以：

- 同一个目标，从不同 `iif`/`uid` 发起可能选到不同源地址；
- 应用如果 `bind()` 了具体地址，内核就按它绑的来；
- **`ip route get` 的 `src` 字段就是最终答案**。

### 4.2 `ip rule`：先选表，再查表

```bash
ip rule show                       # 验证：策略路由规则（默认三条：local / main / default）
```

```text
0:      from all lookup local
32766:  from all lookup main
32767:  from all lookup default
```

读法：**编号越小越优先**。内核先用规则选出「用哪张路由表」，再到那张表里查路由。`local` 表放本机地址，`main` 表就是你平时 `ip route` 看到的内容。

什么时候会出现自定义规则？多网卡多出口（例如「内网流量走内网口、公网走公网口」）、基于源地址分流、容器/CNI 插件、VPN 分流。**排障时如果 `ip route` 看起来没问题但流量走错了，第一反应就是 `ip rule show`**。

```bash
ip rule show                                        # 验证：规则顺序
ip route show table 100                             # 验证：某张自定义表的内容
ip route get 8.8.8.8 from 192.168.246.128           # 验证：指定源地址时的最终选择
```

### 4.3 `rp_filter`：反向路径过滤

```bash
sysctl net.ipv4.conf.all.rp_filter net.ipv4.conf.ens33.rp_filter   # 验证：当前取值（本机实测两者都是 2=loose）
```

`rp_filter` 会检查「这个包的源地址，从我这里回过去是否也走同一个接口」。**在多网卡、非对称路由、部分隧道与容器场景下，它会误杀正常流量**，表现为「对方发来的包我收到了但被丢弃」。

> [!warning] 排障时不要先动 `rp_filter`
> 它是有安全意义的防护（防源地址伪造）。**只有在确认存在非对称路由、且有其他手段兜底时**才考虑调整，并要写进变更记录。判据：`nstat -az | grep -i IpInAddrErrors`、`netstat -s` 时代的类似计数，以及 `dmesg` 中的相关日志。

## 5. 网络命名空间：为什么实验都用它

后面几个实验（子笔记 05、08、10、13）都用 `ip netns` 建隔离拓扑，这里先把这套机制的意义说清：

```bash
ip netns list                      # 验证：本机有哪些命名空间
ip netns add srv                   # 需要 root：新建一个网络命名空间
ip netns exec srv ip -br addr      # 验证：进入该命名空间执行命令（看到的是它自己的网络栈）
ip netns del srv                   # 验证：删除（里面的接口、进程会一起回收）
```

建立一对 veth（虚拟网线），两端分别放进两个命名空间：

```text
ip link add veth0 type veth peer name veth1
ip link set veth0 netns srv
ip link set veth1 netns cli
ip netns exec srv ip addr add 10.0.0.1/24 dev veth0
ip netns exec cli ip addr add 10.0.0.2/24 dev veth1
ip netns exec srv ip link set veth0 up
ip netns exec cli ip link set veth1 up
```

（以上命令来自子笔记 13 的实验 3，**完整可执行版本在那里**；此处只展示结构。）

三个关键认识：

1. **每个命名空间是一套独立的网络栈**：有自己独立的接口、路由表、邻居表、socket 与 conntrack。**容器就是这样实现的**（子笔记 14）。
2. **veth 是一对「虚拟网线」**：一端发、另一端收；一端 down 两端都不通。它是容器网络、网桥、隧道实验的基础积木。
3. **删命名空间即回收**：所以破坏性实验放在里面做，宿主的网络栈完全不受影响——这是 T2/T3 台阶能安全练习的前提。

## 6. 生产动作：一次「地址与路由」的取证清单

按顺序做，**每一条都要留下输出**（写进故障记录）：

1. **接口与地址**：`ip -br addr`（接口是否 UP、地址与掩码对不对）。
2. **路由选择**：`ip route get <目标地址>`（出口、源地址、下一跳）。
3. **路由表与规则**：`ip rule show` + `ip route show table all`（有没有走策略路由）。
4. **邻居状态**：`ip neigh show <下一跳>`（同网段是否 `REACHABLE`）。
5. **接口计数**：`ip -s link show <dev>`（收发包、errors、dropped）。
6. **转发与过滤**：`sysctl net.ipv4.ip_forward`、`nft list ruleset`（如果是网关/容器节点）。
7. **结论**：写出「是地址、是路由、是邻居、还是过滤」+ 证据命令。

```bash
ip -br addr; ip route get <target>; ip rule show
ip neigh show <next_hop>
ip -s link show <dev>
sysctl net.ipv4.ip_forward net.ipv4.conf.all.rp_filter
```

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 用 `ifconfig`/`route` 排障 | 新系统默认不再安装 `net-tools`；用 `ip -br addr`、`ip route`、`ip neigh`（子笔记 03） |
| 「两个地址看起来像同一个网段」 | 必须按前缀长度判断；`10.0.0.1/24` 与 `10.0.1.1/24` 不在同一网段 |
| `ip route` 正常就说明选路正常 | 可能被 `ip rule` 提前分流；要看 `ip rule show` 与 `ip route get` |
| 同网段不通只看路由 | 先看 `ip neigh`：`INCOMPLETE`/`FAILED` 说明二层就没通 |
| 认为默认路由只有一条 | 多网卡/多网关时可能有多条，靠 `metric` 决定优先级 |
| 用 `ARP` 这个老说法找命令 | 现在的命令是 `ip neigh`（`arp` 仍可用但不推荐） |
| 为了「通」把 `rp_filter` 关掉 | 有安全代价；要先确认非对称路由，再评估替代方案 |
| 在生产机上直接 `ip netns add` 做实验 | 命名空间本身隔离，但**接口名与 IP 可能与生产冲突**；实验用 `srv`/`cli` 这类明确名字并统一清理 |

## 决策练习

> [!question]- 场景：一台双网卡机器（`eth0` 内网、`eth1` 外网）。业务从 `eth1` 发起连接，但抓包看到源地址是 `eth0` 的地址，对端因此拒绝。你怎么定位？
> A. 直接把 `eth1` 的地址写进应用配置
> B. 用 `ip route get <目标> from <源地址>` 查内核的实际选择，再确认是否存在策略路由、`rp_filter` 或应用绑定问题
> C. 关掉 `eth0`
>
> **答案：B。**
> 源地址是内核「选」出来的：先看 `ip rule show` 有没有自定义规则，再看 `ip route get` 的 `src`，最后确认应用是否 `bind()` 了具体地址。A 只在应用支持绑定时有效，而且会绕过内核的校验；C 是破坏性动作，会中断内网流量。
> **第一反应不要是什么**：不要先关网卡，也不要直接改 `rp_filter`。

## 要点自测

> [!question]- `ip route get 8.8.8.8` 输出里的四个关键字段分别是什么？
> - `via`：下一跳（网关）；`dev`：出口网卡；`src`：内核选定的源地址；`uid`：发起者。
> - 这一条命令等价于「内核会怎么走」的最终答案，比人脑算路由表快且准。
> - 加 `from <地址>` / `iif <接口>` 可以模拟不同发起条件。
> - **第一反应不要是什么**：不要只看 `ip route` 里的默认路由就下结论。

> [!question]- 同网段不通和跨网段不通，排查的起点有什么不同？
> - **同网段**：先看 `ip neigh`（`INCOMPLETE`/`FAILED` 说明二层不通），再看 VLAN、网桥、交换机与对端状态。
> - **跨网段**：先看 `ip route get` 的网关、默认路由与 `metric`，再看网关是否可达（`ping` 网关）与中间设备。
> - 两类都要看 `ip -s link` 的 errors/dropped。
> - **第一反应不要是什么**：不要一律从应用层开始查。

> [!question]- `ip rule` 和 `ip route` 是什么关系？
> - `ip rule` 决定「用哪张表」，`ip route` 决定「表里怎么查」，**先规则后查表**。
> - 默认三条规则：`local`（本机地址）→ `main`（主表）→ `default`（兜底），编号越小越优先。
> - 多出口、多网卡、容器与 VPN 场景常见自定义规则；`ip route` 看起来正常但流量走错时，第一反应是看 `ip rule show`。
> - **第一反应不要是什么**：不要在没看规则的前提下直接改主路由表。
