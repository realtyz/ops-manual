## 0. 30 秒速览

> [!abstract] 这一篇只要记住六句话
> - **没有基线的调优就是赌博**
>   - 怎么验证：先采集（T1），再对比（增量），最后才动手；改一项、复测、留回滚。第 3 节给了可直接复制的模板。
> - **五个抓手**：中断与队列分布 → 接收软中断 → 多队列与分流（RSS/RPS/RFS）→ 环缓冲 → offload
>   - 证据：本机五个抓手都能采到具体数值——`smp_affinity_list=0-3`、`netdev_max_backlog=1000`/`netdev_budget=300`/`netdev_budget_usecs=2000`、`ethtool -l` 不支持（单队列）+`rps_cpus` 全 0、`ethtool -g` RX/TX 均 `256`（上限 `4096`）、offload 的 `tx-checksumming/scatter-gather/TSO/GSO` 全 `on`。**每一个都有代价，且都能查到具体数值。**
> - **`netdev_max_backlog` 治的是「软中断来不及」，不是「网卡丢包」**
>   - 证据：本机 `/proc/net/softnet_stat` 4 行的第 2 列（dropped）全为 `0`，同时 `ens33` 的 `ethtool -S` 里 `rx_no_buffer_count`/`rx_missed_errors` 也全为 `0`——**两种「丢包」各有各的计数器**，弄清是哪一个再调，否则白改。
> - **环缓冲改大会重置网卡（短暂断流）**
>   - 怎么验证：先 `ethtool -g ens33` 看 `current` 与 `pre-set maximum`（本机 256 vs 4096）并留档，再排窗口；`ethtool -S` 里 `rx_no_buffer_count` 增长才是「环缓冲不够」的证据。
> - **offload 用 CPU 换吞吐**
>   - 证据：本机 `ethtool -k ens33` 实测 `rx-checksumming: off`、`tx-checksumming: on`、`tcp-segmentation-offload: on`、`generic-segmentation-offload: on`——**接收侧校验本来就是关的**，所以「抓包分析时先关 offload」这条建议在这台机器上只对发送侧有意义。
> - **`tuned`/`irqbalance` 会覆盖你的手工配置**
>   - 证据：本机这两个都**没装**（`command -v tuned-adm irqbalance` 均为空、`systemctl is-enabled` 报 `not-found`），所以这条属于「别人机器上的风险」，照抄前先在本机确认它们存不存在。

## 1. 为什么顺序是「基线 → 观测 → 调优」

调参与排障的区别在于：排障要找根因，调优要换性能。**而性能只有相对基线才有意义**——没有基线，你不知道「现在的 4 万 QPS」是变好了还是变坏了，也不知道改完是否有效。

```mermaid
flowchart LR
  A["① 采集基线<br/>参数 · 设备 · 连接 · 计数器"] --> B["② 观测现象<br/>nstat 增量 · ss -ti · softnet_stat"]
  B --> C["③ 形成假设<br/>瓶颈在队列 / 软中断 / 缓冲 / offload"]
  C --> D["④ 改一项并复测<br/>写变更记录 + 回滚方案"]
  D --> E{"有效吗"}
  E -- "是" --> F["固化并纳入监控"]
  E -- "否" --> G["回滚，回到第 ② 步"]
```

## 2. 五个抓手

| 抓手 | 观测入口 | 本机实测 | 取舍 |
| --- | --- | --- | --- |
| **中断与队列分布** | `/proc/interrupts`、`/proc/irq/<N>/smp_affinity_list` | `ens33` 只有 **1 行**中断（`19: 0 0 0 96871 IO-APIC 19-fasteoi ens33`，实测都落在 CPU 3），`smp_affinity_list = 0-3`（任一 CPU 都可处理） | 绑核换确定性，但绑死可能让某个 CPU 成为瓶颈；不绑核则依赖内核分配（本机 `irqbalance` 未安装） |
| **接收软中断** | `/proc/net/softnet_stat`（**15 列，第 2 列是 dropped**）、`net.core.netdev_max_backlog`、`net.core.netdev_budget` | `netdev_max_backlog=1000`、`netdev_budget=300`、**`netdev_budget_usecs=2000`**（4 行对应 4 vCPU，第 2 列全 0） | backlog 调大占用内存，治的是「软中断来不及」，**不是网卡丢包** |
| **多队列与分流** | `ethtool -l`、`/sys/class/net/<dev>/queues/rx-*/rps_cpus`、`rps_flow_cnt`、`rps_sock_flow_entries` | `ethtool -l ens33` → `netlink error: Operation not supported`（**单队列**）；`rps_cpus=00000000,00000000,00000000,00000000`（**RPS 关闭**）、`rps_flow_cnt=0`、`rps_sock_flow_entries=0`；`/sys/class/net/ens33/queues/` 只有 `rx-0`/`tx-0`，且**没有 `xps_cpus`** | 队列多 = 并行处理（需网卡支持）；RPS/RFS 是「队列不够时用软件补」的兜底，会吃 CPU |
| **环缓冲** | `ethtool -g`（current vs pre-set maximum） | 实测 `RX: 256`（上限 `4096`）、`TX: 256`（上限 `4096`）；`/sys/class/net/ens33/queues/tx-0/byte_queue_limits/` 存在（`limit`/`limit_max`/`limit_min`） | 调大换「抗突发」，**修改会重置网卡**（短暂断流），必须排窗口 |
| **offload** | `ethtool -k` | 实测 `rx-checksumming: off`、`tx-checksumming: on`、`scatter-gather: on`、`tcp-segmentation-offload: on`、`generic-segmentation-offload: on`、`large-receive-offload: off [fixed]` | 打开换 CPU（少做分段与校验），代价是抓包看到的是「大包/未分段」；**排障时临时关掉再抓更清楚** |

```bash
grep -E 'ens33|virtio|eth' /proc/interrupts    # 验证：网卡中断在各 CPU 上的分布（多队列会有多行）
cat /proc/irq/19/smp_affinity_list             # 验证：某个中断允许被哪些 CPU 处理（实测 0-3）
head -2 /proc/net/softnet_stat                 # 验证：每个 CPU 的收包统计（第 2 列 dropped，非 0 就要查 backlog/预算）
ethtool -l ens33; ethtool -g ens33             # 验证：队列数与环缓冲的「当前 vs 上限」
cat /sys/class/net/ens33/queues/rx-0/rps_cpus  # 验证：RPS 是否启用（全 0 = 关闭）
sysctl net.core.netdev_max_backlog net.core.netdev_budget net.core.rps_sock_flow_entries
                                               # 验证：软中断预算与 RPS 全局开关
ethtool -i ens33; ethtool -k ens33             # 验证：驱动/固件版本与 offload 开关（纳入基线）
```

> [!warning] `net.core.*` 里只有一部分参数能「只在 netns 里改」
> 本机实测：`net.core.somaxconn` 在 netns 内可见、可改（改成 1234，宿主仍是 4096）；而 **`net.core.netdev_max_backlog`、`net.core.rmem_max`、`net.core.wmem_max`、`net.core.default_qdisc` 在 netns 内直接报 `sysctl: cannot stat …: No such file or directory`**——它们是**全局参数**，只能在 init_net 里改，改完影响整机。
> 所以实验纪律是：`net.ipv4.*` 与 `net.ipv4.conf.*` 可以在 netns 里随便试（本机 `tcp_max_syn_backlog`、`ip_forward`、`tcp_syncookies` 都在 netns 内改过，宿主不受影响），**`net.core.*` 与 `net.netfilter.nf_conntrack_max` 只能全局改，必须先记原值、测完立刻还原**（`nf_conntrack_max` 甚至不允许在 netns 内写，实测被拒：`Operation not permitted`）。

另外两条属于「基线管理」，不属于调优：

- **驱动与固件版本纳入基线**：`ethtool -i`（实测 `driver: e1000`、`bus-info: 0000:02:01.0`、`firmware-version:` 为空）。**升级网卡固件/驱动前先记录版本与当前配置**，否则出问题无法回滚比对。
- **`tuned` profile 是发行版给的成套参数**：RHEL 系默认带 `tuned`（`tuned-adm profile network-throughput` / `network-latency`），Debian/Ubuntu 需自行安装；**用它之前先确认它到底改了哪些 sysctl**（它会覆盖你的手工配置）。**本次实测的 Ubuntu 环境 `tuned-adm` 与 `irqbalance` 都没有安装**，`systemctl is-enabled tuned irqbalance` 返回 `not-found`。

> [!tip] `netstat` 已经不在默认安装里了
> 实测本机 `command -v netstat ifconfig route arp` 全部为空（`net-tools` 未安装）。老资料里的 `netstat -antp` / `netstat -s` 请替换为 **`ss -tanp` / `ss -s`（连接与状态）** 与 **`nstat -az`（协议计数器）**——后者的口径比 `netstat -s` 更细，且能按增量观察。

## 3. 基线采集模板（可直接复制）

```bash
date; hostname; uname -r; cat /etc/os-release | head -3   # 0) 时间与环境

sysctl net.core.somaxconn net.ipv4.tcp_max_syn_backlog net.ipv4.tcp_syncookies \
       net.ipv4.tcp_tw_reuse net.ipv4.tcp_fin_timeout net.ipv4.ip_local_port_range \
       net.ipv4.tcp_congestion_control net.core.default_qdisc net.ipv4.ip_forward   # 1) 网络参数基线

ip -br addr; ip route; ip rule show   # 2) 设备与驱动基线
ethtool -i ens33; ethtool -g ens33; ethtool -l ens33; ethtool -k ens33

ss -s   # 3) 连接与错误基线（留档，后面才有「变差了」的参照）
ss -tan | awk 'NR>1{print $1}' | sort | uniq -c | sort -rn
nstat -az > /tmp/nstat.baseline

sysctl net.ipv4.tcp_max_tw_buckets net.ipv4.tcp_rmem net.ipv4.tcp_wmem \
       net.core.rmem_max net.core.wmem_max net.core.netdev_max_backlog \
       net.core.netdev_budget_usecs net.netfilter.nf_conntrack_max   # 4) 上限类参数

ip -s link   # 5) 链路计数
grep -E 'ens33' /proc/interrupts; head -4 /proc/net/softnet_stat   # 6) 中断与软中断
```

> [!warning] 第 4 步里的 `net.netfilter.nf_conntrack_max` 在本机**会直接报错**
> 实测本机 `nf_conntrack` 模块**默认未加载**，`sysctl net.netfilter.nf_conntrack_max` 返回 `cannot stat /proc/sys/net/netfilter/nf_conntrack_max: No such file or directory`。采基线时把这一行写成容错形式，并**把「不存在」当作一条基线事实记下来**（它说明这台机器没有在跑 NAT/状态化规则）：
> ```bash
> sysctl net.netfilter.nf_conntrack_max 2>/dev/null || echo "nf_conntrack 未加载（本机基线：无 NAT/状态化规则）"
> ```

实测采集到的本机基线（**换环境必须重采**）：

| 参数 | 本机实测值 | 备注 |
| --- | --- | --- |
| `net.core.somaxconn` | 4096 | 内核 5.4+ 的默认值；老内核是 128，**这是最常被差版本坑到的一项** |
| `net.ipv4.tcp_max_syn_backlog` | **512** | 半连接队列的**传统**上限；**注意它比很多人记忆里的 1024 小一半**，而且现代内核里半连接队列主要由 `listen()` 的 backlog 推导（子笔记 05） |
| `net.ipv4.tcp_syncookies` | 1 | 现代发行版默认开启 |
| `net.ipv4.tcp_tw_reuse` | 2 | **只对回环复用**——Linux 4.12+ 起**内核默认值就是 2**（`ip-sysctl.rst` 的 `Default: 2`，本机实测也是 2），**不是「原始默认 0、发行版改过」** |
| `net.ipv4.tcp_fin_timeout` | 60 | 只管 `FIN_WAIT2` |
| `net.ipv4.ip_local_port_range` | 32768 60999 | 28232 个源端口 |
| `net.ipv4.tcp_max_tw_buckets` | **32768** | 各内核/发行版口径差异大（本机是 32768，不是常见的 65536），**用 `sysctl` 查本机** |
| `net.ipv4.tcp_congestion_control` | cubic | 可用：`reno cubic`（`tcp_bbr` 模块未加载；`modprobe tcp_bbr` 后可用） |
| `net.core.default_qdisc` | fq_codel | 现代发行版默认 |
| `net.core.netdev_max_backlog` | 1000 | 收包软中断队列 |
| `net.core.netdev_budget` / `netdev_budget_usecs` | 300 / **2000** | 每次软中断轮询的包数预算与时间预算（单位 µs）；**本机是 2000µs = 2ms，不是 8000** |
| `net.core.rps_sock_flow_entries` | 0 | RFS 未启用（配合 `rps_cpus` 全 0 一起看） |
| `net.ipv4.tcp_rmem` / `tcp_wmem` | `4096 131072 6291456` / `4096 16384 4194304` | 自动调优区间 |
| `net.core.rmem_max` / `wmem_max` | 212992 / 212992 | 会限制应用 `setsockopt` 的上限 |
| `net.ipv4.conf.all.rp_filter` | 2（loose） | **改之前先确认有没有非对称路由** |
| `net.ipv4.tcp_abort_on_overflow` | 0 | 队列溢出时静默丢弃（子笔记 05） |
| `net.ipv4.tcp_mtu_probing` | 0 | PMTU 黑洞的兜底开关（子笔记 08） |
| `nf_conntrack_max` | **模块默认未加载** | 需 `modprobe nf_conntrack` 后才有值（加载后为 `262144`，`buckets` 同值）；加载后 `nf_conntrack_tcp_timeout_established=432000`（5 天） |

## 4. 分层排查的固定姿势

把「现象 → 分层 → 证据 → 结论 → 止损 → 改进」落到网络场景，就是下面这条固定路径。**面试时按它讲，比背命令列表高一个档次**：

1. **先定影响面**：全部还是部分？同一机房/同一网段/同一客户端？什么时候开始（对齐变更时间线）？
2. **自下而上排除**：链路（`ip -s link`、`ethtool -S`）→ IP/路由（`ip route get`、`ip neigh`）→ 端口/防火墙（`ss -lnt`、`nstat`、conntrack）→ DNS（`getent`）→ 应用（`curl -v`、日志）。
3. **用计数器而不是感觉**：`nstat` 的重传/丢包/溢出计数、`ss -ti` 的 RTT/重传/cwnd、`ethtool -S` 的错包。
4. **区分「主机内」与「主机外」**：云上先分清安全组/负载均衡/云网络与主机内的问题——**主机侧计数干净时，别在主机上反复折腾**。
5. **止损与改进分开**：故障中做影响面最小的动作（换路径、限流、扩容），根因留到复盘阶段查。

## 5. 调参的正确姿势

> [!warning] 三条硬性要求
> ① **先量化**：记录改之前的计数器与业务表现（`nstat`、`ss -s`、`ss -ti`、业务 P99）。
> ② **一次只改一项**：写进变更记录，包括改动原因、期望效果、观察指标、回滚命令。
> ③ **观察至少一个业务周期后再固化**；无效则回滚，不要「先留着看看」。

高并发短连接场景最常见的四项是 `nf_conntrack_max`、`somaxconn`、`ip_local_port_range`、`tcp_tw_reuse`——**它们治的是四种不同的病**，别一起改，否则出了事说不清是谁的功劳或锅。

## 6. 生产动作：一次调优变更的记录模板

| 字段 | 内容示例 |
| --- | --- |
| 现象与影响面 | 「网关偶发连接超时，客户端报 timeout，持续 10 分钟」 |
| 基线证据 | `nstat` 快照、`ss -s`、`nf_conntrack_count/max`、`ss -ti` 关键字段 |
| 假设 | 「conntrack 表接近上限导致丢包」 |
| 变更内容 | `net.netfilter.nf_conntrack_max: 262144 → 524288`（附持久化方式与所在文件；**本机要先 `modprobe nf_conntrack` 才有这个键**，且它是**全局参数、不能在 netns 内改**——实测在 netns 内写会报 `Operation not permitted`） |
| 影响与风险 | 内存开销上升；不影响已有连接 |
| 验证方式 | 复采 `nf_conntrack_count/max`、观察 `dmesg`、观察业务 P99 |
| 回滚 | 改回原值并 `sysctl --system`；保留原快照文件路径 |
| 结果 | 有效 / 无效 / 部分有效 + 下一步 |

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 没有基线就调参 | 无法判断是否有效，也无法回滚到「已知良好」的状态 |
| 「`netdev_max_backlog` 调大就能解决丢包」 | 它只治「软中断来不及」；网卡侧丢包要看 `ethtool -S`/`-g` |
| 一次改多项参数 | 出了事无法归因，也无法回滚单项 |
| 在生产机上直接改环缓冲或队列数 | 会重置网卡、短暂断流；必须排窗口 |
| 认为 `ethtool -S` 的计数器通用 | 名字是驱动私有的，换机型即失效 |
| 开着 offload 抓包分析 TCP 细节 | 看到的是「大包/未分段」；排障窗口内可临时关闭 |
| 用 `tuned` 后又手工改 sysctl | 两边会互相覆盖；先确认 `tuned` 改了哪些项 |
| 只调 `net.core.rmem_max` 就以为缓冲变大了 | 应用还要 `setsockopt`，`tcp_rmem` 的 max 也要相应考虑 |
| 把虚拟网卡/模拟网卡的数据当物理机基线 | 中断分布、队列、环缓冲、固件字段都不可比（本机 `ens33` 是 VMware 模拟的 `e1000`：单队列、无 `xps_cpus`、`firmware-version` 为空） |
| 在 netns 里改 `net.core.*` 却报 `cannot stat` | 那不是命令错了：`net.core.netdev_max_backlog`/`rmem_max`/`default_qdisc` 是**全局参数**，只在 init_net 里存在（实测）；能 per-netns 的只有 `net.core.somaxconn` 这类 |
| 采基线时把 `nf_conntrack_max` 的报错当成机器故障 | 本机模块默认未加载，`No such file or directory` 是**正常基线**；需要值就先 `modprobe nf_conntrack` |

## 决策练习

> [!question]- 场景：一台机器单核软中断高，`/proc/net/softnet_stat` 第 2 列在涨。同事说「把 `netdev_max_backlog` 调到最大」。
> A. 直接调大 `netdev_max_backlog`
> B. 先量化：`ethtool -l/-g`、`/proc/interrupts`、`ip -s link`，确认是队列/环缓冲/中断分布还是单核打满，再选改项并复测
> C. 关掉所有 offload
>
> **答案：B。**
> `netdev_max_backlog` 治的是「软中断来不及消费」的缓冲深度，不解决「流量全压在一个队列/一个核」的分布问题；关 offload 会显著增加 CPU 开销。
> **第一反应不要是什么**：不要在没量化前就改参数，也不要一次改多项。

## 要点自测

> [!question]- 一份合格的网络基线卡至少包含哪几类字段？
> - **环境**：发行版、内核、驱动与固件版本（`ethtool -i`）。
> - **参数**：队列（`somaxconn`）、源端口范围、`tcp_*` 关键项、拥塞算法与 `qdisc`、转发与 conntrack 上限。
> - **设备**：接口与地址、路由与策略路由、MTU、队列数、环缓冲、offload。
> - **连接与计数**：`ss -s`、状态分布、`nstat -az` 快照、`ip -s link`。
> - **第一反应不要是什么**：不要只记「调优后的值」——**原始值才是能回滚的那个值**。

> [!question]- `netdev_max_backlog` 与 `ethtool -g` 分别解决什么问题？
> - `netdev_max_backlog` 是**内核收包软中断的排队上限**：处理不过来时丢包，`/proc/net/softnet_stat` 第 2 列会增长。
> - `ethtool -g` 是**网卡硬件环缓冲**：太小在突发流量时丢包，`ethtool -S` 里会看到相关计数。
> - 前者是软件队列（吃内存），后者是硬件队列（改时会重置网卡）。
> - **第一反应不要是什么**：不要把两个「backlog」当成同一件事来调。

> [!question]- 为什么「先量化再改」在调优里格外重要？
> - 性能是**相对量**：没有改前的数据，就无法证明改动的效果，也无法判断是否引入新问题。
> - 参数之间有交互（例如窗口、缓冲、拥塞算法、`qdisc` 相互影响），一次改多项就失去归因能力。
> - 有了基线，回滚才有明确的「回到哪」。
> - **第一反应不要是什么**：不要在只有一个「大家说这样调比较好」的理由下就动手。
