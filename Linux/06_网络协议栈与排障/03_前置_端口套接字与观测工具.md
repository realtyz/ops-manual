## 0. 30 秒速览

> [!abstract] 这一篇只要记住六句话
> - **`ss` 是主力，`netstat` 已经不是默认安装**：实测 Ubuntu 24.04 上 `command -v netstat` 为空（`net-tools` 不再随系统安装）；`netstat -antp` → `ss -tanp`，`netstat -s` → `nstat -az`。
> - **`ss` 的四个姿势分工明确**：`ss -s`（总览）、`ss -tanp`（谁在连）、`ss -lntp`（谁在听、队列多深）、`ss -ti`（这条连接的质量）。
> - **`ss -ti` 是「不抓包看链路」的主力**：`rtt`/`minrtt`/`cwnd`/`retrans`/`pacing_rate`/`app_limited` 都在这里（子笔记 06）。
> - **`nstat` 是协议栈计数器**：默认只显示**增量**，用来回答「现在有没有在发生」；相比 `netstat -s` 口径更细，且能按需清空基准。
> - **`ss`/`nstat` 看不到链路层的事**：网卡错包、驱动丢包、环缓冲溢出要看 `ip -s link`、`ethtool -S/-g` 和 `/proc/net/softnet_stat`（子笔记 08、11）。
> - **第一组命令永远是「总览 + 状态分布 + 计数器」**：`ss -s`、`ss -tan | awk '{print $1}' | sort | uniq -c | sort -rn`、`nstat -az`。三者一起看，故障类别基本就定了。

## 1. 端口与套接字

### 1.1 端口的三段划分

| 范围 | 名称 | 用途 | 注意 |
| --- | --- | --- | --- |
| `0` ~ `1023` | 知名端口（well-known） | `22`(ssh)、`53`(dns)、`80`(http)、`443`(https) | 非 root 绑定需要 `CAP_NET_BIND_SERVICE` |
| `1024` ~ `32767` | 注册端口（registered） | 应用自定义端口多落在这里 | 与**源端口**范围可能重叠 |
| `32768` ~ `60999` | 临时端口 / 源端口（ephemeral） | 本机**主动发起**连接时内核自动选 | 实测本机 `ip_local_port_range = 32768 60999`，共 28232 个 |

```bash
cat /proc/sys/net/ipv4/ip_local_port_range   # 验证：本机源端口范围（也可用 sysctl 查）
ss -lnt                                      # 验证：本机监听端口
```

> [!important] 「端口耗尽」通常指**源端口**，不是监听端口
> 一个监听端口可以被成千上万条连接共用（靠四元组区分）。但**本机作为客户端**发起连接时，每条连接要占一个源端口，而且主动关闭后该端口会进入 `TIME_WAIT` 约 60 秒。所以「短连接 QPS × 60 秒」就是同时被占用的源端口上限——这是子笔记 07 的核心判据之一。

### 1.2 socket 的两种身份，再强调一次

```bash
ss -lntp        # 验证：监听 socket —— 谁在听、队列多深（Recv-Q 深度 / Send-Q 上限）
ss -tanp        # 验证：已连接 socket —— 每条连接一个，带进程归属
```

```text
State   Recv-Q  Send-Q  Local Address:Port   Peer Address:Port  Process
LISTEN  0       4096    0.0.0.0:8080         0.0.0.0:*          users:(("nginx",pid=1234,fd=6))
ESTAB   0       0       10.0.0.1:8080        10.0.0.2:43848     users:(("nginx",pid=1234,fd=9))
```

两行分别对应两种 socket：**第一行是监听（带队列），第二行是已连接（带缓冲区）**。同样的 `Recv-Q`/`Send-Q` 列，语义完全不同——这个坑在子笔记 01 与 05 都强调过。

### 1.3 状态分布：一眼看出「哪个状态在涨」

```bash
ss -s                                                    # 验证：按协议与状态的总览
ss -tan | awk 'NR>1{print $1}' | sort | uniq -c | sort -rn   # 验证：状态分布排行
ss -tan state time-wait | wc -l                          # 验证：单个状态的精确条数
ss -tan state close-wait | head -20                      # 验证：看是哪些进程/对端
```

```text
Total: 245
TCP:   187 (estab 63, closed 96, orphaned 0, timewait 91, ...)
```

**为什么先看分布**：一个状态异常放大时，故障类别基本就定了——`TIME_WAIT` 堆在客户端说明短连接太多；`CLOSE_WAIT` 堆积说明应用没关连接；`SYN-SENT` 堆积说明握手没人应答；`ESTAB` 的 `Recv-Q` 持续非零说明应用读得慢。

| 状态 | 含义 | 异常时通常指向 |
| --- | --- | --- |
| `LISTEN` | 在监听 | 只绑 `127.0.0.1` 是外部连不上的常见原因 |
| `SYN-SENT` | 已发 SYN，等 SYN+ACK | 对端不回 / SYN 被丢（子笔记 05、09） |
| `SYN-RECV` | 收到 SYN，已回 SYN+ACK | 半连接队列积压（子笔记 05） |
| `ESTAB` | 已建立 | `Recv-Q`/`Send-Q` 大说明应用读写跟不上 |
| `FIN-WAIT1/2` | 主动关闭中 | `FIN_WAIT2` 堆积说明对端迟迟不发 FIN（子笔记 07） |
| `TIME-WAIT` | 主动关闭完成，等 2MSL | 短连接多；**60 秒，无 sysctl 可调**（子笔记 07） |
| `CLOSE-WAIT` | 收到对端 FIN，本端没关 | **应用侧 bug**（子笔记 07） |
| `LAST-ACK` | 被动关闭方等最后 ACK | 秒级，一般不用管 |
| `CLOSING` | 双方同时关闭 | 罕见 |

## 2. `ss`：连接与队列的主力工具

### 2.1 常用参数

| 参数 | 作用 | 典型用法 |
| --- | --- | --- |
| `-t` / `-u` / `-x` | TCP / UDP / Unix socket | `ss -tan` |
| `-a` | 显示所有（含监听与已连接） | `ss -tan` |
| `-l` | 只看监听 | `ss -lntp` |
| `-n` | 不做名字解析（保留数字） | **排障时必加**，避免 DNS 反向解析拖慢输出 |
| `-p` | 显示进程归属 | 需要 root 才能看全 |
| `-s` | 汇总统计 | `ss -s` |
| `-i` | 连接的内部细节（RTT、cwnd…） | `ss -ti` |
| `-o` | 定时器信息 | `ss -to` |
| `-e` | 扩展的 socket 信息 | `ss -tne` |

### 2.2 过滤：把范围缩到一条连接

```bash
ss -tan 'dport = :443'                    # 验证：目的端口 443 的连接
ss -tan 'sport = :8080'                   # 验证：源端口 8080 的连接
ss -tan 'dst 10.0.0.1'                    # 验证：某个对端
ss -tan state established                 # 验证：只看已建立
ss -tan state established '( dport = :443 or sport = :443 )'
                                          # 验证：组合过滤（引号内是表达式）
ss -tinp 'dport = :443'                   # 验证：细节 + 进程，只看 443
```

### 2.3 `ss -ti`：一条连接的自述

```bash
ss -ti                      # 验证：所有 TCP 连接的细节（字段逐项读法见子笔记 06）
ss -tinp dport = :443       # 验证：加上进程与定时器
```

```text
ESTAB 0 0 10.0.0.1:9998 10.0.0.2:39548
	 cubic wscale:7,7 rto:204 rtt:0.011/0.005 mss:1448 pmtu:1500 rcvmss:536 advmss:1448
	 cwnd:10 segs_in:2 send 10.5Gbps lastsnd:1992 lastrcv:1992 lastack:1992
	 pacing_rate 21.1Gbps delivered:1 app_limited rcv_space:14600 rcv_ssthresh:64076
	 minrtt:0.011 snd_wnd:64256
```

（以上是**实测输出**，环境见子笔记 13 的实验 7：隔离命名空间里的空闲 veth 连接。）

这条短小的文本里包含了：拥塞算法（`cubic`）、窗口缩放（`wscale`）、重传超时（`rto`）、平滑 RTT 与波动（`rtt:x/y`）、MSS 与路径 MTU、拥塞窗口（`cwnd`）、发送速率与 pacing（`pacing_rate`）、已确认字节（`delivered`）、**应用是否喂满（`app_limited`）**、对端通告窗口（`snd_wnd`）。**「TCP 能连但吞吐上不去」这一类问题的第一现场就在这里**（子笔记 06）。

## 3. `nstat`：协议栈计数器

```bash
nstat -az | head -40                                   # 验证：全部计数器的绝对值快照
nstat -az | grep -E 'ListenOverflows|ListenDrops'      # 验证：只看队列溢出（子笔记 05）
nstat -az | grep -E 'TcpRetransSegs|TCPTimeouts'       # 验证：重传与超时（子笔记 06）
nstat -a | head -20                                    # 验证：不带 -z 时只显示「自上次以来有变化」的行
nstat -r 2                                             # 验证：每 2 秒刷新一次（观察增量）
```

几个必须搞清楚的口径：

| 写法 | 含义 |
| --- | --- |
| `nstat`（无参数） | 显示**自历史基准以来有变化**的计数器，适合「现在有没有在发生」 |
| `nstat -z` | 显示全部计数器（含值为 0 的），适合留档与前后对比 |
| `nstat -a` | 显示绝对值（不计算增量） |
| `nstat -r <秒>` | 循环刷新，用来观察「此刻在不在涨」 |

**`nstat` 的计数器来自 `/proc/net/snmp` 与 `/proc/net/netstat`**，所以：

```bash
cat /proc/net/snmp | head -20            # 验证：IP/TCP/UDP 的官方计数器（第一行是列名）
cat /proc/net/netstat | head -20         # 验证：扩展计数（TcpExt* 就在这里）
cat /proc/net/tcp | head -5              # 验证：内核视角的 TCP 表（十六进制，ss 的可读版本更好用）
```

> [!tip] 用「差值」而不是「绝对值」做判断
> 计数器从开机累计，绝对值没有意义。标准做法是：**先 `nstat -az > /tmp/nstat.before`，做完动作或等一段时间后再采一次，用 `diff` 或直接看 `nstat` 的增量输出**。子笔记 06、11 的基线模板都用这个套路。
> ```bash
> nstat -az > /tmp/nstat.before      # 留档
> # …（观察或触发操作）
> nstat -az | grep -E 'ListenOverflows|TCPReqQFull|TcpRetransSegs'
> ```

## 4. 链路层的观测工具

`ss`/`nstat` 看不到网卡与驱动的事，需要另一组工具（详细用法见子笔记 08、11）：

| 工具 | 回答什么问题 | 典型命令 |
| --- | --- | --- |
| `ip -s link` | 每个接口收发了多少包、多少 errors/dropped | `ip -s link show eth0` |
| `ethtool -S` | **驱动私有**计数器（丢包原因、队列停止） | `ethtool -S eth0 \| grep -iE 'drop\|err\|no_buffer'` |
| `ethtool -g` | 环缓冲大小（current vs pre-set maximum） | `ethtool -g eth0` |
| `ethtool -l` | 队列数（RSS） | `ethtool -l eth0` |
| `ethtool -i` | 驱动与固件版本 | `ethtool -i eth0` |
| `ethtool -k` | offload 开关状态 | `ethtool -k eth0` |
| `/proc/net/softnet_stat` | 每个 CPU 的收包统计（第 2 列是 dropped） | `head -2 /proc/net/softnet_stat` |
| `/proc/interrupts` | 网卡中断在各 CPU 上的分布 | `grep -E 'eth0\|virtio\|ens' /proc/interrupts` |

> [!warning] `ethtool -S` 的计数器名字是驱动私有的
> 实测本机（虚拟网卡 `hv_netvsc`）的计数器是 `tx_scattered`/`rx_no_memory`/`stop_queue` 这类名字，**在物理网卡上根本不存在**。做告警模板前，必须先在目标机型上 `ethtool -S` 采一遍名字与语义。

## 6. 生产动作：三分钟状态快照

拿到一台「网络有问题」的机器，先做这组**只读**快照，再决定动手。**每一步都留输出**：

```bash
date; hostname; uname -r                                   # 时间与环境
ip -br addr; ip route                                      # 接口、地址、路由
ss -s                                                      # 连接总览
ss -tan | awk 'NR>1{print $1}' | sort | uniq -c | sort -rn  # 状态分布
ss -lntp                                                   # 监听端口与队列
nstat -az > /tmp/nstat.snapshot                            # 计数器留档
sysctl net.core.somaxconn net.ipv4.ip_local_port_range \
       net.ipv4.tcp_max_tw_buckets net.netfilter.nf_conntrack_max \
       net.netfilter.nf_conntrack_count 2>/dev/null        # 关键上限
ip -s link                                                 # 接口计数
```

> [!tip] 这套动作的价值
> 它把「现场」固化下来了。**故障过去之后再采一次，用 `diff` 对比**，就能回答「到底哪个计数器在涨」——这比事后回忆可靠得多，也是子笔记 11 基线卡的最小版本。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 用 `netstat -antp` 排障 | 新系统默认不装 `net-tools`；用 `ss -tanp`，协议计数用 `nstat -az` |
| `ss` 不加 `-n` | 触发反向 DNS 解析，输出慢甚至卡住（尤其在对端 DNS 不可达时） |
| 把 `nstat` 的绝对值当结论 | 计数器从开机累计；要比较**增量**或前后差值 |
| 只 `ss -s` 不给状态分布 | 总览给不出「谁在涨」；补一条 `awk` 排行 |
| 用 `ss` 找网卡丢包 | 那里看不到链路层；要 `ip -s link`/`ethtool -S`/`softnet_stat` |
| 直接照抄别人的 `ethtool -S` 字段做告警 | 计数器名是驱动私有的，换机型即失效 |
| 生产机上跑 `ss -tp` 全量并解析主机名 | 输出量大且会卡；先加过滤条件，再加 `-n` |
| 认为 `-p` 一定能看到进程 | 没有 root 时看不到别人的进程，显示为空是权限问题而不是「没有进程」 |

## 决策练习

> [!question]- 场景：服务端偶发超时，你怀疑监听队列满。同事说「我刚 `ss -lntp` 看过，`Recv-Q` 是 0，不是队列问题」。你怎么继续？
> A. 接受结论，转去查应用
> B. 采两次 `nstat` 的 `ListenOverflows`/`ListenDrops`，并确认「偶发」意味着瞬时 `ss` 抓不到；再用 `ss -tan state syn-recv` 与 `ss -lnt` 的 `Send-Q` 交叉验证
> C. 直接把 `somaxconn` 调到最大
>
> **答案：B。**
> `ss -lntp` 是瞬时值，队列溢出可能已经过去；`nstat` 的计数器是累计增量，能留下偶发证据。C 在没确认是 backlog 还是 `somaxconn` 截断前是无效调参。
> **第一反应不要是什么**：不要因为一次 `ss` 干净就排除队列溢出，也不要先改参数。

## 要点自测

> [!question]- `ss -s`、`ss -lnt`、`ss -tanp`、`ss -ti` 各回答什么问题？
> - `ss -s`：连接与状态**总览**（含 timewait 数量）；`ss -lnt`：**监听**了什么、队列多深（`Recv-Q` 深度 / `Send-Q` 上限）；
> - `ss -tanp`：**每条连接**及其状态与进程归属；`ss -ti`：**某条连接的内部细节**（RTT、cwnd、重传、`app_limited`）。
> - 顺序：先总览、再状态分布、再看监听、最后下钻到单条连接或进程。
> - **第一反应不要是什么**：不要一上来就 `tcpdump`，也不要用 `netstat`。

> [!question]- `nstat` 与 `/proc/net/snmp` 是什么关系？为什么推荐 `nstat`？
> - `nstat` 读取 `/proc/net/snmp` 与 `/proc/net/netstat`，把它们整理成**带名字的计数器**，默认显示增量。
> - 相比 `netstat -s`，`nstat` 口径更细（含 `TcpExt*`），且支持 `-a`/`-z`/`-r` 三种观察方式。
> - 协议栈的「偶发失败」大多只体现在计数器上：`ListenOverflows`、`TCPReqQFullDrop`、`TcpExtTCPTimeouts`……这些都是 `nstat` 的领地。
> - **第一反应不要是什么**：不要看绝对值就下结论，要做前后对比。

> [!question]- 为什么排障时要先看「状态分布」，而不是直接找一条连接看？
> - 状态分布能在**三秒内**把问题分类：`SYN-SENT` 堆积是「没人应答」，`CLOSE-WAIT` 是「应用没关」，`TIME-WAIT` 是「短连接多」。
> - 单条连接只能回答「这条怎么了」，而分布回答「整体在往哪个方向恶化」。
> - 分布异常后再下钻：`ss -tanp state <状态>` → 找到进程 → 看该进程的句柄数与增长趋势。
> - **第一反应不要是什么**：不要随手抓一个 `ESTAB` 连接就开始分析。
