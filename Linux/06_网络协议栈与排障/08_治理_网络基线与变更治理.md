# 网络基线与变更治理

## 1. 没有制度时会发生什么

网络参数的特点是：**改了立刻生效、重启可能失效、影响面是全机或全链路、出错的现象往往延迟出现**。这四条合在一起，制造出三类反复发生的组织问题：

**第一类：参数漂移。** 同一个服务群的十台机器，因为不同时间由不同人处理过故障，`somaxconn`、`tcp_tw_reuse`、`tcp_rmem` 各不相同。故障复现时无法判断「是不是某台机器被改过」，扩容出来的新机器与老机器行为不一致。

**第二类：无归因的调参。** 一次故障里同时改了 `somaxconn`、`nf_conntrack_max` 与环缓冲，问题缓解了——但没人知道是哪一项起了作用，也没人知道另外两项带来了什么代价。下一次同类故障发生时，这套「经验」无法复用。

**第三类：证据不在。** 故障当时没留 `nstat` 快照，重启之后计数器归零、`TIME_WAIT` 消失、conntrack 条目清空，复盘会只能靠回忆。更隐蔽的一种是：**某些计数器的现场会随进程退出而消失**（例如 `tcp_max_tw_buckets` 溢出的唯一信号是计数器，日志里可能什么都没有），不提前纳入监控就等于永远发现不了。

治理要解决的就是这三件事：**把当前状态固化成基线、把改动固化成记录、把早期信号固化成告警。**

## 2. 上限配在哪一层：五种载体

同一件事（比如「提高连接处理能力」）可以写在五种不同的载体上，它们的生效方式、持久化位置、影响范围都不同。

| 载体 | 例子 | 生效方式 | 影响范围 | 持久化位置 |
| --- | --- | --- | --- | --- |
| 内核参数（`sysctl`） | `net.core.somaxconn`、`net.ipv4.tcp_*` | `sysctl -w` 立即，重启失效 | 视参数：多数是 per-netns，部分（如 `net.core.*`）是全局 | `/etc/sysctl.d/*.conf`，由 `systemd-sysctl` 开机按文件名顺序应用 |
| 内核接口文件 | `/proc/sys/...`、`/sys/...` | 直接写入立即生效 | 视文件 | 需自己保证开机重现 |
| 内核模块与算法 | `tcp_bbr`、`nf_conntrack` | `modprobe` 是**全局内核状态变更** | 全机 | `/etc/modules-load.d/`、`/etc/modprobe.d/` |
| 服务单元属性 | systemd 的 `LimitNOFILE=`、`IPAddressAllow=` 等 | `systemctl daemon-reload` 后生效 | 该单元 | unit 文件或 drop-in |
| 应用自身 | 连接池大小、超时、重试次数、socket 缓冲区 `setsockopt` | 应用重启后生效 | 该应用 | 应用配置与代码 |

三条判据：

1. **先确认「谁能改」**：`net.ipv4.*` 多数可以在网络命名空间内单独设置（便于实验）；`net.core.*`（如 `netdev_max_backlog`、`rmem_max`、`default_qdisc`）与 `net.netfilter.nf_conntrack_max` 是全局参数，只能改整机。**做实验前先确认这一点，否则会改到生产机上。**
2. **再确认「会不会持久」**：只敲 `sysctl -w` 等于「重启即回滚」，这在故障处置里可以接受（临时动作），但绝不能被当成「修好了」。
3. **最后确认「影响谁」**：改 MTU、改环缓冲、改 bond 模式、动防火墙规则会影响**整块网卡或整条链路**；改 `tcp_congestion_control` 影响**全机所有 TCP 连接**。这类改动必须走变更流程。

## 3. 容量规划：四类上限要提前算

不是所有「够不够」都能在现场看出来。下面四类必须提前算、提前配、提前告警。

### 3.1 源端口容量

```text
同一时刻占用的源端口数 ≈ 出向短连接 QPS × 60 秒（TIME_WAIT 停留时间）
可用源端口数 = ip_local_port_range 的规模 − ip_local_reserved_ports 保留的部分
```

治理动作：把 `ip_local_port_range` 与 `ip_local_reserved_ports` 写入基线；对出向短连接密集的服务（反向代理、网关、爬虫）算出预估占用，与端口规模比较；把 `TcpExtTCPTimeWaitOverflow` 纳入监控。**顺序上先改应用（连接池/长连接），再谈扩端口**——扩端口只是把天花板抬高。

### 3.2 连接跟踪表容量

```text
并发会话数 ≈ 活跃连接数 + 处于各种超时状态的历史条目
条目占用 ≈ nf_conntrack_max × 每条约几百字节的内存
```

关键接口是 `nf_conntrack_max`（表容量）、`nf_conntrack_buckets`（哈希桶数，影响查找性能）与 `nf_conntrack_tcp_timeout_established`（已建立连接的空闲超时，默认值在内核文档里给出，必须以本机为准）。**必须一并治理的两个反直觉点**：

- **「没有 conntrack」不等于「没有连接」**：现代内核在没有 NAT/状态化规则时不注册 conntrack 钩子，此时 `conntrack -C` 恒为 0、`nf_conntrack_max` 这个键可能不存在。所以容量规划只在真正做转发/NAT 的节点上才有意义，**不要给所有机器套同一份模板**。
- **表满是静默丢包**：现场是「客户端超时、应用无感」，日志里会出现 `table full, dropping packet`，而 `conntrack -S` 的 `drop` 计数是更早的信号。

### 3.3 监听队列容量

```text
全连接队列上限 = min(应用 listen() 的 backlog, net.core.somaxconn)，实际容量为 backlog + 1
```

治理动作分两侧：**应用侧**确认 `listen()` 的 backlog 是显式配置的、且与预期并发匹配；**系统侧**确认 `somaxconn` 不会成为无意的截断点。判据是同一条命令的两个字段（`ss -lnt` 的 `Recv-Q`/`Send-Q`）与两个计数（`TcpExtListenOverflows`/`ListenDrops`）。**这两项计数必须配告警**——它是「客户端偶发超时、服务端无日志」这类故障唯一的早期信号。

### 3.4 名字解析容量

```text
单次解析的查询次数 ≈ search 域数量 + 1（名字里的点数少于 ndots 时）
最坏耗时 ≈ 查询次数 × 每服务器超时 × 重试次数 × 服务器数量
```

治理动作：把 `/etc/nsswitch.conf` 的顺序、`resolv.conf` 的 `search`/`ndots`/`timeout`/`attempts` 写入基线；容器场景要单独记录（编排系统注入的 `ndots:5` 会让带点的名字先试多个后缀）；把 `resolvectl statistics` 的缓存命中率与上游失败数纳入观测。**顺序上先减少查询次数，再谈换更快的上游。**

## 4. 产物模板

### 4.1 网络基线卡

一份基线卡的字段必须能回答三个问题：**这台机器现在是什么状态**、**哪些值是被改过的**、**出问题时从哪里开始对比**。

| 字段 | 内容示例 | 为什么必须有 |
| --- | --- | --- |
| 环境 | 发行版、内核版本、`ethtool -i` 的驱动与固件、虚拟化/物理 | 默认值与可用开关随版本变化 |
| 接口与地址 | 接口名、MAC、MTU、地址与前缀、链路状态 | 大量「连不上」最后落在地址与绑定上 |
| 路由与策略 | `ip route`、`ip rule show` 摘要、默认网关 | 多出口与容器节点必备 |
| 上限类参数 | `net.core.somaxconn`、`net.ipv4.tcp_max_syn_backlog`、`net.ipv4.ip_local_port_range`、`net.ipv4.tcp_max_tw_buckets`、`net.ipv4.tcp_rmem`/`tcp_wmem`、`net.core.rmem_max`/`wmem_max` | 容量的天花板 |
| 行为类参数 | `net.ipv4.tcp_syncookies`、`tcp_abort_on_overflow`、`tcp_tw_reuse`、`tcp_fin_timeout`、`tcp_congestion_control`、`net.core.default_qdisc`、`rp_filter`、`ip_forward`、`tcp_mtu_probing` | 决定故障形态与处置手段 |
| 链路能力 | 队列数、环缓冲 current/maximum、offload 开关、中断分布 | 高负载场景的瓶颈点 |
| 连接现状 | `ss -s`、状态分布、监听端口与队列 | 事后判断「变差了」的参照 |
| 计数器快照 | `nstat -az` 原始输出、`ip -s link`、`ethtool -S` | 偶发问题唯一的早期信号 |
| **不存在的东西** | 「`nf_conntrack_max` 不存在（未加载，本机无 NAT/状态化规则）」 | 「不存在」也是基线事实，能防止后人误判 |
| 采集元信息 | 采集时间、采集人、采集命令版本 | 没有时间戳的基线无法与故障时刻对齐 |

参数名的完整前缀要写全（`net.core.` / `net.ipv4.` / `net.netfilter.`）——**基线卡里的值必须是目标机器上现场采集到的当前值，不能填某个版本的默认值**：默认值随内核与发行版变化，写错比不写更危险，它会让人误以为「这台机器没被改过」。

采集命令与可直接复制的模板见实操篇第 3 节；这里只规定「要留哪些字段」。字段不存在时（例如未加载 `nf_conntrack`）也要把「不存在」记成一条基线事实。

### 4.2 变更记录

| 字段 | 内容示例 |
| --- | --- |
| 现象与影响面 | 「网关偶发新连接超时，客户端报 timeout，持续 10 分钟，影响单个可用区」 |
| 基线证据 | `nstat` 快照路径、`ss -s`、`ss -lnt`、`nf_conntrack_count/max` |
| 假设 | 「连接跟踪表接近上限导致静默丢包」 |
| 变更内容 | 参数名、旧值 → 新值、**载体**（sysctl 临时 / `/etc/sysctl.d/` 持久 / unit 属性）、影响范围 |
| 影响与风险 | 内存开销、对已有连接的影响、是否需要重启或断流 |
| 验证方式 | 复采哪些字段、观察多久、用什么业务指标判断有效 |
| 回滚 | 改回原值的命令与持久化文件位置；原快照文件路径 |
| 结果 | 有效 / 无效 / 部分有效 + 下一步 |

**「载体」这一栏最容易被省掉，却是最值钱的一栏**：它决定了「下次重启之后这个值还在不在」，也决定了另一个工程师能不能复现你的动作。

### 4.3 处置记录（故障与演练共用）

| 字段 | 内容 |
| --- | --- |
| 现象与影响面 | 谁、什么时候、多大范围、什么表现 |
| 时间线 | 首次出现、发现、处置、恢复的时间点（与变更记录对齐） |
| 分层证据 | 链路 / IP 与路由 / 端口与队列 / 名字解析 / 应用 各一条关键输出 |
| 计数器证据 | `nstat` 增量、`ss -ti` 关键字段、`ethtool -S` 计数（含采集时间戳） |
| 根因判定 | 属于哪一层 + 为什么（**要有反证：哪些可能被排除了，怎么排除的**） |
| 处置动作 | 止血动作与根因修复**分开写** |
| 验证 | 用哪条命令确认恢复、观察了多久 |
| 遗留与改进 | 缺失的监控、参数变更、Runbook 更新点 |

### 4.4 MTU 与链路变更检查单

改 MTU、改 bond 模式、改队列数或环缓冲都会**短暂断流**，远程操作时可能把自己关在门外。

1. **影响面**：这块网卡承载哪些业务与哪些 VIP？改动期间是否需要业务侧暂停？
2. **窗口与在场**：是否有维护窗口？是否有带外管理或本地控制台可用？
3. **前置采集**：`ip link show`、`ip -s link`、`ethtool -g/-k/-S`、`ss -ti` 的 `pmtu`/`mss` 留档。
4. **回滚命令**：预先写好并复制到剪贴板或另一台机器上。
5. **验收**：不是「命令没报错」，而是**同一位置的业务探测恢复**（`ping -M do` 分级验证、业务小请求与大响应都通过）。
6. **记录**：写进变更记录，注明持久化位置（发行版网络配置或 unit）。

## 5. 监控要为「没有日志的故障」留位置

有些故障不会在应用层留下任何痕迹。治理上的动作是把它们变成有痕迹的。

| 现象 | 唯一或最早的信号 | 为什么不能靠日志 |
| --- | --- | --- |
| 全连接队列溢出 | `TcpExtListenOverflows`/`TcpExtListenDrops` 增量 | 内核默认静默丢弃，应用从未见过连接 |
| 半连接队列满且关闭了 syncookies | `TcpExtTCPReqQFullDrop`/`ListenDrops` | 同上 |
| `tcp_max_tw_buckets` 溢出 | `TcpExtTCPTimeWaitOverflow` | 本机内核上 `dmesg`/`journalctl -k` 可能完全为空 |
| conntrack 表满 | `nf_conntrack_count/max` 比值、`conntrack -S` 的 `drop` | 表满是丢包不是拒绝，应用只会超时 |
| 收包软中断丢包 | `/proc/net/softnet_stat` 第 2 列 | 内核不为此写日志 |
| 网卡/驱动丢包 | `ip -s link` 的 `errors`/`dropped`、`ethtool -S` | 同上；且驱动计数器名因机型而异 |
| 解析被放大 | 查询次数与 `resolvectl statistics` | 应用只会「偶发变慢」，不会报错 |

告警设计的三条纪律：

1. **告警基于增量或比值**，不基于计数器绝对值；
2. **阈值来自自己的基线**（`nstat` 的日常增量、自己的重传率水平），不外推别人的经验值；
3. **驱动私有计数器进入模板前，必须在目标机型上现场采集字段名**，并为字段缺失准备兜底。

## 6. 三个治理场景与要交出的产物

**场景一：一批新机器上线。**
问题是「新机器与老机器参数不一致，故障无法复现」。动作是采集基线卡并做一次横向比对：环境、上限类参数、行为类参数、链路能力四组字段必须一致，差异写清原因（机型不同导致的驱动与队列差异属正常）。产物：**基线卡 + 横向差异说明**。

**场景二：一次故障后要复盘。**
问题是「证据在重启后归零」。动作是在处置开始前就把 `nstat -az`、`ss -tanp`、`ss -lnt`、`nf_conntrack_count/max`、`dmesg -T` 采下来落到本地；处置动作与根因修复分开记录。产物：**处置记录 + 计数器前后对照**。

**场景三：一次参数调整要上线。**
问题是「改了但说不清有效没有、也说不出怎么回滚」。动作是按变更记录模板写全八栏，特别写清载体与回滚命令；改完复测同一条命令与同一个业务指标，观察至少一个业务周期；无效则回滚。产物：**变更记录 + 复测结果**。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 用 `sysctl -w` 改完就宣布「修好了」 | 重启即回滚；必须写持久化位置或明确标注为临时动作 |
| 在实验命名空间里改 `net.core.*` | 这些是全局参数（`netdev_max_backlog`、`rmem_max`、`default_qdisc` 等），报 `No such file or directory` 不是命令错 |
| 给所有机器套同一份 conntrack 容量模板 | 不做转发/NAT 的机器根本没有在跟踪连接，值可能不存在 |
| 参数调整一次改多项 | 失去归因能力，也无法单项回滚 |
| 基线只记录调优后的值 | 只有原始值（或明确标注的当前值 + 历史值）才支撑回滚 |
| 告警用计数器绝对值 | 从开机累计，绝对值无意义；要用增量或比值 |
| 把别人的重传率/队列阈值当自己的阈值 | 阈值必须来自自己的基线 |
| 把驱动私有计数器写进通用模板 | 换机型即失效 |
| 变更记录里省略「载体」 | 无法判断下次重启后是否还在 |
| 改 MTU/环缓冲/bond 不排窗口 | 会短暂断流，远程操作可能自锁 |
| 故障中顺手清理日志、顺手重启 | 会毁掉现场；止血与根因修复必须分开 |

## 要点自测

**问：为什么「载体」是变更记录里最不能省的字段？**
答：载体（sysctl 临时值 / `/etc/sysctl.d/` 持久配置 / 内核接口文件 / 模块状态 / unit 属性 / 应用配置）决定了生效范围、是否需要重启或断流、以及**下次重启之后这个值还在不在**。缺了它，别人无法复现你的动作，也无法判断故障是否会复发。

**问：四类需要提前算的容量分别是什么？各自的判据字段是什么？**
答：源端口（`ip_local_port_range` 规模 vs `出向 QPS × 60 秒`）、连接跟踪表（`nf_conntrack_count/max`、`conntrack -S` 的 `drop`）、监听队列（`min(backlog, somaxconn)`，计数看 `TcpExtListenOverflows`/`ListenDrops`）、名字解析（查询次数 = `search` 域数 + 1，观测看 `resolvectl statistics`）。

**问：为什么「`nf_conntrack_max` 这个键不存在」要写进基线卡？**
答：它说明这台机器没有 NAT 或状态化规则在跑，因此「连接跟踪表满」这一类故障在这里不成立。把它当成采集失败会让后人反复排查一个不存在的问题。

**问：哪些计数必须纳入监控？为什么不能靠日志？**
答：`TcpExtListenOverflows`/`ListenDrops`、`TcpExtTCPReqQFull*`、`TcpExtTCPTimeWaitOverflow`、conntrack 的 `drop` 与 `count/max`、`/proc/net/softnet_stat` 第 2 列、`ip -s link` 的 errors/dropped。原因是这些故障在内核里是**静默丢弃或静默跳过**，应用层只会看到超时，日志里可能什么都没有。

**第一反应不要做什么**：不要用 `sysctl -w` 的结果当持久修复；不要一次改多项；不要把别人的阈值当自己的基线。
