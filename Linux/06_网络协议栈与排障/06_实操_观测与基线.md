# 协议栈观测与网络基线

## 1. 一个问题，一把工具

| 你想知道 | 用什么 | 关键字段或文件 |
| --- | --- | --- |
| 应用会解析成什么地址 | `getent hosts <name>` | 结果行（NSS 顺序 + search/ndots） |
| resolved 缓存与上游的状态 | `resolvectl status`、`resolvectl statistics` | `Current DNS Server`、`resolv.conf mode`、缓存命中与失败数 |
| 有没有网卡、地址与路由怎么走 | `ip -br addr`、`ip route`、`ip rule show` | 接口状态、`src`、`metric`、规则编号 |
| 内核实际会怎么走 | `ip route get <目标>` | `via`、`dev`、`src`、`uid` |
| 同网段二层通不通 | `ip neigh` | `REACHABLE`/`STALE`/`INCOMPLETE`/`FAILED` |
| 谁在监听、队列多深 | `ss -lntp` | `Recv-Q`（深度）、`Send-Q`（上限）、`users:` |
| 连接状态分布、谁在连接 | `ss -s`、`ss -tanp` | 状态名与条数、进程归属 |
| 这条连接的质量（RTT/窗口/重传） | `ss -ti` | `rtt`/`minrtt`/`cwnd`/`retrans`/`app_limited` |
| 协议栈计数（溢出、重传、超时） | `nstat` | `TcpExtListenOverflows`、`TcpRetransSegs`、`TcpExtTCPTimeWaitOverflow` |
| 转发、NAT 与连接跟踪 | `sysctl net.ipv4.ip_forward`、`conntrack -C/-S`、`nft list ruleset` | `count/max`、`drop`、`table full` |
| 网卡有没有丢包/错包 | `ip -s link`、`ethtool -S`、`ethtool -g` | `errors`/`dropped`/`missed`、驱动私有计数、环缓冲的 current 与 maximum |
| 收包软中断来不来得及 | `/proc/net/softnet_stat` | 第 2 列 dropped（每 CPU 一行） |
| 中断落在哪些 CPU | `/proc/interrupts`、`/proc/irq/<N>/smp_affinity_list` | 每 CPU 计数、允许的 CPU 列表 |
| 队列规则在不在丢包 | `tc -s qdisc show` | `dropped`、`backlog` |
| 线上到底发了什么 | `tcpdump`（限流限时落盘） | 时间戳、四元组、Flags、`seq`/`ack`/`win` |

表里的「用什么」分两类：**命令**（`ss`、`nstat`、`ip`、`ethtool`、`tc`、`tcpdump`、`conntrack`——文档在 `man 1` 或 `man 8`）与**内核接口文件**（`/proc/...`、`/sys/...`，直接读，不需要工具）。分不清时看文档节号：`man 2` 系统调用、`man 3` 库函数、`man 5` 文件格式。

## 2. 怎么读这些数字

下面每一组都给出五件事：**是什么、单位、多少算异常（或只能与自己的基线比）、和谁一起看、看到它转向哪一步**。文中的输出样例只用来展示**格式**，数值不代表你的机器。

### 2.1 `ss`：先总览、再分布、再下钻

```bash
ss -s                                                       # 总览
ss -tan | awk 'NR>1{print $1}' | sort | uniq -c | sort -rn    # 状态分布
ss -lntp                                                    # 监听与队列
ss -ti                                                      # 单条连接的细节
```

```text
Total: 177
TCP:   10 (estab 3, closed 3, orphaned 0, timewait 3)

Transport Total     IP        IPv6
RAW       1         0         1
UDP       2         2         0
TCP       7         6         1
```

| 字段 | 是什么 | 单位 | 判据 | 和谁一起看 | 转向哪一步 |
| --- | --- | --- | --- | --- | --- |
| `TCP: n (estab x, closed y, timewait z)` | 按状态的连接总览 | 条数 | 绝对值必须结合业务量看；异常的是「某个状态在涨」 | 状态分布、`nstat` | 若某个状态在堆积，则下钻该状态 |
| `LISTEN` 的 `Recv-Q` | 已完成握手、未被 `accept()` 的连接数 | 条数 | 若 `Recv-Q` 大于 `Send-Q`，则队列已满 | `Send-Q`、`nstat` 溢出计数 | 去查 `accept()` 的节奏与队列上限 |
| `LISTEN` 的 `Send-Q` | 队列上限 | 条数 | 看它是否等于 `net.core.somaxconn`，等于就说明被全局参数截断 | `sysctl net.core.somaxconn`、应用 backlog | 先确认是应用还是全局参数卡住 |
| `ESTAB` 的 `Recv-Q` | 接收缓冲区未读字节 | 字节 | 若长期非零，则说明应用读得慢 | 应用指标、`ss -ti` 的 `snd_wnd`（对端视角） | 去查应用 |
| `LISTEN` 的 `0.0.0.0:port` 与 `127.0.0.1:port` | 绑定范围 | — | 若只绑了环回地址，则外部永远连不上 | `users:` 归属 | 改配置重新绑定 |

**必须加 `-n`**：不加会触发反向 DNS 解析，输出慢甚至卡住。`-p` 需要权限，非 root 只能看到自己的进程。

### 2.2 `nstat`：协议栈计数器，必须取差值

```bash
nstat                     # 只显示自上次基准以来有变化的行（判断「现在在不在发生」）
nstat -az > /tmp/nstat.before      # 全部计数器的绝对值快照（留档）
nstat -az | grep -E 'ListenOverflows|ListenDrops|TCPReqQFull|SyncookiesSent'
nstat -r 2                # 每 2 秒刷新，观察是否持续增长
```

| 计数器 | 是什么 | 单位 | 判据 | 和谁一起看 | 转向哪一步 |
| --- | --- | --- | --- | --- | --- |
| `TcpExtListenOverflows` | 全连接队列溢出次数 | 次（累计） | 若两次读数的差值非 0，则说明这段时间发生过溢出 | `ListenDrops`、`ss -lnt` | 去查队列上限与 `accept()` 的节奏 |
| `TcpExtListenDrops` | 因队列问题被丢弃的次数 | 次（累计） | 判据与上一行相同，都是看两次读数的差值 | 上面的三个 `ReqQFull*` | 据此区分是半连接还是全连接队列 |
| `TcpExtTCPReqQFullDoCookies` | 半连接队列满、改用 cookie 的次数 | 次 | 若它在增长而 `ListenDrops` 不涨，则说明内核改用 cookie 完成了握手 | `sysctl net.ipv4.tcp_syncookies` | 客户端仍能连上，无需动手 |
| `TcpExtTCPReqQFullDrop` | 半连接队列满、丢弃 SYN 的次数 | 次 | 增长说明 syncookies 被关 | `sysctl net.ipv4.tcp_syncookies` | 把 `tcp_syncookies` 恢复为 1 |
| `TcpExtSyncookiesSent` | 发出的 cookie 数 | 次 | 配合 `ReqQFullDoCookies` 交叉验证 | `sysctl net.ipv4.tcp_syncookies` | 客户端仍能连上，无需动手 |
| `TcpExtTCPTimeWaitOverflow` | `tcp_max_tw_buckets` 溢出次数 | 次 | 若差值非 0，则说明内核跳过了 `TIME_WAIT` | `sysctl net.ipv4.tcp_max_tw_buckets` | 减少主动关闭；**日志里可能无痕** |
| `TcpRetransSegs` / `TcpOutSegs` | 重传段数 / 发送总段数 | 段 | 比值持续偏离自己的基线就查 | `ss -ti` 的 `retrans`/`lost` | 按丢包方向排查，先排除 MTU |
| `TcpExtTCPTimeouts` | RTO 超时次数 | 次 | 若大量增长，则说明链路或对端异常 | `TcpExtTCPLostRetransmit` | 去查路径质量 |
| `IpInAddrErrors` | 因地址问题被丢弃的入包 | 个 | 若它在增长，则结合 `rp_filter` 的取值一起判断 | `sysctl net.ipv4.conf.*.rp_filter` | 转去查非对称路由 |
| `IpOutNoRoutes` | 没有路由可用的出包 | 个 | 若它在增长，则说明发包方向不通 | `ip route get` | 去查路由；在伪造源地址的实验里用它做交叉验证 |

**两条铁律**：计数器从开机累计，**绝对值的唯一用途是算差值**；**任何单一计数器都不能单独定性**（伪造源地址的 SYN 实验里，只看 `ListenDrops` 会得出「内核全丢了」的错误结论，加上 `IpOutNoRoutes` 与 `TcpOutSegs` 才发现是回程没有路由）。

### 2.3 `ss -ti`：单条连接的自述

```bash
ss -ti dport = :443          # 验证：只看某个服务的连接细节
ss -tinp 'dport = :443'      # 验证：加上进程与定时器
```

```text
ESTAB 0 0 10.0.0.1:9998 10.0.0.2:53658
	 cubic wscale:7,7 rto:201 rtt:0.014/0.007 mss:1448 pmtu:1500 cwnd:10
	 segs_in:2 send 8.27Gbps lastsnd:1992 lastrcv:1992 lastack:1992
	 pacing_rate 16.5Gbps delivered:1 app_limited minrtt:0.014 snd_wnd:64256
```

| 字段 | 是什么 | 单位 | 判据 | 和谁一起看 | 转向哪一步 |
| --- | --- | --- | --- | --- | --- |
| `rtt:x/y` | 平滑 RTT / 波动 | 毫秒 | 若它与 `minrtt` 差距大，则说明路径上有排队 | `minrtt`、`retrans` | 去查路径拥塞 |
| `minrtt` | 观测到的最小 RTT | 毫秒 | 它的稳定值就是这条路径的基线 | `rtt`、`ping` | 与历史值比较，看它是否退化 |
| `cwnd` | 拥塞窗口 | 以 MSS 计 | 若 `cwnd` 小、`minrtt` 大，则说明窗口受限 | `snd_wnd`、BDP | 去查缓冲与路径 |
| `snd_wnd` | 对端通告窗口 | 字节 | 若很小甚至为 0，则说明对端应用不读数据 | 对端 `ss` 的 `Recv-Q` | 转到对端去查 |
| `retrans` / `lost` | 重传 / 判定丢失 | 段 | 出现就说明有丢包 | `nstat` 重传率 | 去查链路与 MTU |
| `app_limited` | 应用没喂满连接 | — | 出现即说明瓶颈在应用 | 应用指标 | **不要在网络上找原因** |
| `pmtu` / `mss` | 路径 MTU / 协商 MSS | 字节 | 若 `pmtu` 明显小于两端的 MTU，则路径上有隧道封装 | `ip link show` | 去查两端 MTU 的一致性 |
| `pacing_rate` | 当前 pacing 速率 | 比特每秒 | 把它与链路带宽对照 | `send`、业务吞吐 | 据此判断是否被限速 |

### 2.4 `ethtool`、链路与中断

```bash
ip -s link show ens33                                # 接口计数
ethtool -i ens33                                     # 驱动与固件版本（基线的一部分）
ethtool -S ens33 | grep -iE 'drop|err|miss|no_buffer' # 驱动私有计数
ethtool -g ens33                                     # 环缓冲的当前值与上限
ethtool -k ens33                                     # offload 开关
grep ens33 /proc/interrupts                          # 中断在各 CPU 的分布
head -4 /proc/net/softnet_stat                       # 每 CPU 的收包统计（第 2 列 dropped）
```

| 字段 | 是什么 | 单位 | 判据 | 和谁一起看 | 转向哪一步 |
| --- | --- | --- | --- | --- | --- |
| `ip -s link` 的 `errors`/`dropped`/`missed` | 链路层收发异常 | 个 | 若它在增长，则说明链路层在丢包 | `ethtool -S` | 去查驱动、环缓冲与对端设备 |
| `ethtool -S` 的 `rx_no_buffer_count`/`rx_missed_errors` | 驱动侧的丢包原因 | 个 | **这些名字是驱动私有的**，换机型就可能不存在 | `ethtool -g` | 若环缓冲不够，则排窗口后再调大 |
| `ethtool -g` 的 current 与 maximum | 环缓冲的当前值与上限 | 描述符个数 | 若 current 远小于 maximum 且上面的计数在增长，则说明还有调整余地 | `ethtool -S` | 调整会重置网卡，因此需要窗口 |
| `/proc/net/softnet_stat` 第 2 列 | 收包软中断队列溢出（每 CPU 一行） | 个 | 若它在增长，则说明软中断来不及 | `net.core.netdev_max_backlog` | 治的是软件队列，**不是网卡丢包** |
| `/proc/interrupts` 的分布 | 网卡中断落在哪些 CPU | 计数 | 若中断全部落在一个 CPU 且该核饱和，则是单核打满 | `ethtool -l` 的队列数 | 改多队列、RPS 或中断亲和 |
| `ethtool -l` 的 `Operation not supported` | 网卡不支持 channels 查询 | — | 单队列的网卡会这样报 | `/sys/class/net/<dev>/queues/` | 这不是工具坏了，而是该网卡不支持这项查询 |

**两种「backlog 丢包」要分清**：`/proc/net/softnet_stat` 是内核收包软中断队列，调大它只多占内核内存；`ethtool -g` 是网卡硬件环缓冲，修改它会重置网卡（短暂断流）。

### 2.5 `tc` 与队列规则

```bash
tc qdisc show dev ens33          # 验证：当前队列规则
tc -s qdisc show dev ens33       # 验证：加上统计（dropped / backlog）
```

| 字段 | 是什么 | 单位 | 判据 | 和谁一起看 | 转向哪一步 |
| --- | --- | --- | --- | --- | --- |
| `qdisc` 名称 | 队列规则类型 | — | 它与 `net.core.default_qdisc` 对应；BBR 需要 `fq` | `sysctl net.ipv4.tcp_congestion_control` | 换拥塞控制算法之前先确认 pacing 队列 |
| `dropped` | 该队列丢掉的包 | 个 | 若持续增长，则说明出口在丢包 | `nstat` 的 `TcpExtTCPBacklogDrop` | 去查限速与队列长度 |
| `backlog` | 当前排队字节数 | 字节 | 若长期非零，则说明出口长期拥塞 | 业务吞吐与 RTT | 去查上联带宽 |

### 2.6 名字解析

```bash
getent hosts <name>; time getent hosts <name>    # 应用视角与其耗时
resolvectl status                                # 上游、协议开关、resolv.conf 模式
resolvectl statistics                            # 缓存命中、上游失败、查询总数
dig @<上游> <name> A +noall +answer              # 纯 DNS 视角（含 TTL）
```

| 字段 | 是什么 | 单位 | 判据 | 和谁一起看 | 转向哪一步 |
| --- | --- | --- | --- | --- | --- |
| `time getent hosts` 的耗时 | 应用视角解析耗时 | 秒 | 与「连接耗时」分开量；它只能与自己的基线比 | `resolvectl statistics` | 若它偏慢，则去查后缀放大与上游 |
| `search` 域数量与 `ndots` | 一次解析可能发起的查询次数 | 次 | 点数少于 `ndots` 时，次数是 `search` 域数加 1 | 容器内 `resolv.conf` | 改用完全限定名或减少 `search` 域 |
| `Cache Hits / Misses` | resolved 缓存表现 | 次数 | 若命中率长期很低，则说明每次都在往上问 | `Total Transactions` | 去查 TTL 与上游 |
| `resolv.conf mode: stub` | 使用的是本地存根 | — | 它说明 `resolv.conf` 里的 `nameserver` 不是上游 | `Current DNS Server` | 要读真实上游得去 `resolvectl status` 里看 |

## 3. 采样纪律与网络基线卡

### 3.1 采样纪律

- **同口径**：两次采样用同一条命令、同一个过滤器；改了口径就不是对比。
- **带时间戳**：`date` 写在输出里，或让命令自己带时间；跨机对照时要先对时间。
- **至少两次**：计数器一律取差值；趋势需要至少两个点，判断抖动按秒、判断泄漏按小时或天。
- **留原始输出**：把 `nstat -az`、`ss -tanp`、`ip -s link`、`ethtool -S` 的原始文本留住，而不是只抄一个数字。
- **区分「只读」与「有代价」**：`ss`/`ip`/`nstat`/`sysctl`/`ethtool` 的查询是只读的，**生产机上可以做**；`tcpdump` 有 CPU 与磁盘代价，必须限流限时落盘；`netem`、改 MTU、改环缓冲会改变业务流量，只在实验机的独立命名空间里做。

### 3.2 一份可复制的基线卡

```bash
date; hostname; uname -r; head -3 /etc/os-release          # 环境

sysctl net.core.somaxconn net.ipv4.tcp_max_syn_backlog net.ipv4.tcp_syncookies \
       net.ipv4.tcp_tw_reuse net.ipv4.tcp_fin_timeout net.ipv4.ip_local_port_range \
       net.ipv4.tcp_max_tw_buckets net.ipv4.tcp_congestion_control \
       net.core.default_qdisc net.ipv4.ip_forward net.ipv4.conf.all.rp_filter

ip -br addr; ip route; ip rule show                        # 地址、路由与策略
ethtool -i ens33; ethtool -g ens33; ethtool -k ens33       # 驱动、环缓冲、offload

ss -s                                                      # 连接总览
ss -tan | awk 'NR>1{print $1}' | sort | uniq -c | sort -rn  # 状态分布
nstat -az > /tmp/nstat.baseline                            # 计数器留档（关键）

ip -s link; grep ens33 /proc/interrupts; head -4 /proc/net/softnet_stat

sysctl net.netfilter.nf_conntrack_max 2>/dev/null || echo "nf_conntrack 未加载（本机无 NAT/状态化规则）"
```

第二处容错写法的意义：**「这个键不存在」本身就是一条基线事实**——它说明这台机器上没有 NAT 或状态化规则在跑。基线卡里应当记录这种「不存在」，而不是把它当采集失败。

### 3.3 实验的复现与清理边界

生产上等不来「同等条件的两次故障」，所以偶发问题的定位往往先在实验链路上把现象造出来。这套动作有固定的边界：

- **拓扑**：`ip netns add` 建两到三个命名空间，用一对 veth（virtual Ethernet，虚拟网线）连起来；需要模拟「出门之后」的场景时，中间多放一个命名空间当路由器（`ip_forward=1` + NAT 规则）。**建在命名空间里的东西删掉命名空间即回收**，宿主网络栈不受影响。
- **只在命名空间里做的动作**：注入延迟/丢包/乱序（`tc qdisc add ... netem`）、改 MTU、伪造源地址的 SYN 实验、改 `net.ipv4.*` 参数。**只在整机改的**：`net.core.*`（`netdev_max_backlog`、`rmem_max`、`default_qdisc` 等）与 `net.netfilter.nf_conntrack_max`。
- **注入前先留基线**：同一位置、同一条命令（例如 `ping`、`ss -ti`、`nstat`）先采一次，注入后再采一次。
- **复现的判据不是「命令没报错」，而是「目标现象出现」**：例如 `netem delay 50ms` 之后对端看到的 RTT 从基线升到接近 50 ms，才算注入成功。
- **清理的判据也不是「按了删除键」**：要复测同一位置的 RTT（或丢包率）回到基线，并确认 `tc qdisc show` 里不再有 `netem` 残留、命名空间已删除。**残留的 qdisc 会持续影响之后的每一次实验，让后续所有对比都失去意义。**

### 3.4 基线卡要覆盖的字段类别

| 类别 | 为什么必须留 | 典型来源 |
| --- | --- | --- |
| 环境 | 内核与驱动版本决定默认值与可用开关 | `uname -r`、`head -3 /etc/os-release`、`ethtool -i` |
| 参数（原始值） | **能回滚的那个值是原始值，不是调优后的值** | `sysctl` 各项 |
| 地址、路由与策略 | 大量「连不上」最后落在这里 | `ip -br addr`、`ip route`、`ip rule show` |
| 链路能力 | MTU、队列数、环缓冲、offload 决定上限 | `ip link`、`ethtool -g/-l/-k` |
| 连接与状态 | 之后才能说「变差了」 | `ss -s`、状态分布 |
| 计数器快照 | 偶发问题唯一的早期信号 | `nstat -az`、`ip -s link`、`ethtool -S` |
| 转发与跟踪 | 容器节点、网关必须留 | `ip_forward`、`nft list ruleset`、conntrack |

## 4. 常见故障与排查方向

每一类都先给出具象场景，再给排查顺序，最后说明**一份合格的回答长什么样**。所有命令默认只读；带破坏性的动作已单独标注。

### 4.1 服务连不上（固定的排查顺序）

**场景**：业务方报「订单接口连不上」，机器是 4 vCPU / 8 GiB 的应用服务器，Ubuntu 24.04，应用监听 8080；报障时间 14:20，此前 14:05 有一次发布。

**排查顺序**：

1. **监听**：读 `ss -lntp`，期待看到 `0.0.0.0:8080`；若只看到 `127.0.0.1:8080`，则它就是根因。
2. **链路**：先用 `ping -c3 <ip>` 区分「到不了主机」与「到不了服务」；**`ping` 通不代表 TCP 通**。
3. **端口**：在客户端 `nc -vz <ip> <port>`，同时在服务端读 `nstat`：
   - 若 `TcpExtListenOverflows`/`ListenDrops` 的增量非 0，则说明队列溢出；
   - 若计数不涨而客户端停在 `SYN-SENT`，则 SYN 被中间设备或 conntrack 丢弃；
   - 若客户端立刻收到 `Connection refused`，则服务端回了 RST（没监听，或 `tcp_abort_on_overflow=1`）。
4. **名字**：`getent hosts <name>` 用应用视角复现（不是 `dig`）。
5. **应用与进程**：`curl -v`、`journalctl -u`、进程是否处于 `D` 状态（存储挂载点卡死也会表现为服务无响应）。

```bash
ss -lntp
nstat -az | grep -E 'ListenOverflows|ListenDrops|TCPReqQFull|SyncookiesSent'
nc -vz <ip> <port>
ss -tan | grep -E 'SYN-SENT|SYN-RECV'
getent hosts <name>
```

**一份合格的回答**应当包含四件事：先说清卡在哪一层、是谁的问题，这是结论；再给出依据，即哪条命令的哪一行支持这个结论；然后划出边界，说明哪些层还没有查、为什么可以先把它们排除；最后给出动作，写清改了哪一项、用什么方式验证、如何回滚。

### 4.2 客户端偶发超时、服务端没有日志

**场景**：一个 32 核 / 64 GiB 的网关机，业务方报「大约每 10 分钟有几次连接超时，服务端日志里完全看不到对应的请求」；服务端进程 CPU 与内存都很低。

**排查顺序**：

1. `ss -lntp` 看监听 socket 的 `Recv-Q` 与 `Send-Q`——`Recv-Q > Send-Q` 就是队列已满。
2. `nstat -az` 采两次（间隔 10~30 秒）比较 `TcpExtListenOverflows`/`ListenDrops` 的**增量**。
3. 判断瓶颈在哪一侧：`Send-Q` 是否等于 `net.core.somaxconn`（被全局参数截断），还是应用 `listen()` 的 backlog 太小。
4. 判断 `accept()` 是否慢：`strace -p <pid> -e trace=accept -T`、`ss -lnt` 的 `Recv-Q` 是否长期非 0；常见原因是把 `accept()` 与业务处理放在同一线程，或 GC/全局锁造成周期性停顿。
5. 排除其他静默丢包：conntrack 表是否满（`count/max`、`dmesg` 的 `table full`）、中间设备是否限速。

**必须避免的结论**：「服务端没有日志，所以请求没到达」——握手完成但未被 `accept()` 时，应用确实不知道这些连接存在过。

### 4.3 连接堆积：区分半连接与全连接

**场景**：压测时客户端报大量超时，服务端 `ss -lnt` 的 `Recv-Q` 忽高忽低。

**排查顺序**：先确认是哪一个队列——半连接看 `ss -tan state syn-recv` 与 `TcpExtTCPReqQFull*`；全连接看 `Recv-Q > Send-Q` 与 `TcpExtListenOverflows`。再确认极限值是否被截断（`somaxconn`）。最后确认是应用 `accept()` 慢还是上限太小。

**判据表**：

| 现象 | 计数表现 | 客户端感受 |
| --- | --- | --- |
| 半连接队列满，`tcp_syncookies=1` | `TcpExtSyncookiesSent`/`TCPReqQFullDoCookies` 增长，`ListenDrops` 不涨 | 仍然能连上 |
| 半连接队列满，`tcp_syncookies=0` | `TCPReqQFullDrop` 与 `ListenDrops` 同步增长 | 连接超时 |
| 全连接队列满，`tcp_abort_on_overflow=0` | `ListenOverflows`/`ListenDrops` 增长 | 超时（重传后放弃） |
| 全连接队列满，`tcp_abort_on_overflow=1` | 计数表现与上一行相同 | 立刻 `connection reset` |

### 4.4 TCP 能连但吞吐上不去

**场景**：跨机房调用，TCP 能建连，但单流下载只有预期带宽的一小部分；监控显示出口带宽没跑满。

**排查顺序**：

1. 读 `ss -ti dport = :<port>`：若出现 `app_limited`，则**去查应用**；若 `retrans`/`lost` 明显，则查链路丢包；若 `cwnd` 小且 `minrtt` 大，则窗口与 BDP 受限；若 `snd_wnd` 很小，则对端应用不读数据。
2. 重传率：`nstat -az` 采两次，算 `TcpRetransSegs/TcpOutSegs` 的增量比，与自己的基线比。
3. 路径 MTU：`ping -M do -s 1472 <ip>`，100% 丢包就是 MTU/PMTU 问题。
4. 逐跳质量：`mtr -n -r -c 3 <ip>`。
5. 缓冲上限：`sysctl net.ipv4.tcp_rmem net.ipv4.tcp_wmem net.core.rmem_max net.core.wmem_max`——高 BDP 链路上窗口撑不起来时才考虑调，代价是每个连接占更多内存。

```bash
ss -ti dport = :<port>
nstat -az | grep -E 'TcpRetransSegs|TcpOutSegs|TCPTimeouts|TCPLostRetransmit'
ping -M do -s 1472 <ip>
sysctl net.ipv4.tcp_rmem net.ipv4.tcp_wmem net.core.rmem_max net.core.wmem_max
```

### 4.5 大包不通（`ping` 通、传文件卡死）

**场景**：用户能 SSH 登录、小请求正常，一传大文件就卡死；链路中间有 VPN。

**排查顺序**：

1. 先做 `ping -M do -s 1472 <ip>`；若失败，则二分缩小 `-s`，找出实际可用的 MTU。
2. `ip link show <dev>` 比对本机 MTU；确认隧道/overlay 的封装开销（VXLAN 约 50 字节、IPIP 约 20 字节）。
3. `ss -ti` 看 `pmtu`/`mss` 是否与预期一致。
4. `mtr -n -r -c 3` 看哪一跳变化（`tracepath` 也会给出 `pmtu`，但本机环境下常报 `no reply`，别据此判断链路断了）。

**动作方向**：统一两端 MTU，或在网关上做 MSS clamping；`net.ipv4.tcp_mtu_probing` 只在 ICMP 被禁时作为回退路径。**改 MTU 属于影响连通性的变更**：它作用于整块网卡上的所有流量，必须排窗口、准备回滚。

### 4.6 大量 `TIME_WAIT` 或 `CLOSE_WAIT`

**场景**：一台反向代理上 `ss -s` 显示 `timewait` 上万；另一台应用服务器上 `CLOSE-WAIT` 缓慢增长。

**排查顺序（`TIME_WAIT`）**：

1. 先确认方向：读 `ss -tan state time-wait | head -20`，看本地端口是服务端口还是临时端口，据此判断谁是主动关闭方。
2. 再算容量：把 `sysctl net.ipv4.ip_local_port_range` 的端口数与「出向 QPS × 60 秒」比较。
3. 然后看是否溢出：读 `nstat -az | grep TCPTimeWaitOverflow` 的增量（**日志里可能什么都没有**）。
4. 只有接近端口上限或出现 `Cannot assign requested address` 才动手，顺序是先改应用（连接池/长连接），再扩源端口，然后才考虑 `tcp_tw_reuse=1`，最后才把 `tcp_max_tw_buckets` 当作回退路径。

**排查顺序（`CLOSE_WAIT`）**：先用 `ss -tanp state close-wait` 找出进程，再按进程聚合找出泄漏者，然后读 `ls -l /proc/<pid>/fd | wc -l` 看是否单调增长，最后结合代码与上游分析。**内核参数里没有任何一项能消除它。**

### 4.7 偶发丢包与延迟

**场景**：业务偶发 50 ms 抖动，只在高峰期出现，没有稳定复现手段。

**排查顺序**：

1. **本机出口队列**：`tc -s qdisc show dev <dev>` 的 `dropped`/`backlog`；协议栈侧看 `nstat` 的 `TcpExtTCPBacklogDrop`。
2. **收包软中断**：`/proc/net/softnet_stat` 第 2 列是否增长；协议栈侧看 `nstat` 的 `TcpExtTCPRcvQDrop`。
3. **连接跟踪**：`nf_conntrack_count/max` 比值与 `dmesg` 的 `table full`。
4. **网卡与驱动**：`ip -s link`、`ethtool -S`、`ethtool -g`。
5. **路径**：`mtr -n -r -c 3`；必要时两侧同时限流限时抓包做二分。

**关于「要不要抓包」**：偶发问题直接在生产上长时间抓包，成本高且命中率低。正确顺序是先在实验链路的独立命名空间里用 `tc netem` 复现（注入延迟/丢包/乱序），拿到判据之后再决定生产取证的过滤条件与抓取位置。

### 4.8 名字解析慢或结果不一致

**场景**：应用偶发「解析超时」，但运维在机器上跑 `dig` 一切正常。

**排查顺序**：

1. `getent hosts <name>` 复现应用视角；`time getent hosts <name>` 量化耗时。
2. `cat /etc/nsswitch.conf` 与 `cat /etc/resolv.conf`；若有 resolved，看 `resolvectl status` 的 `resolv.conf mode` 与 `Current DNS Server`。
3. `resolvectl statistics` 看缓存命中与上游失败。
4. 如果应用在容器里：`nsenter -t <pid> -n cat /etc/resolv.conf`，确认 `search`/`ndots`（Kubernetes 常见 `ndots:5`，一次解析可放大成 4~5 次查询）。
5. 改过记录的场景要等 TTL 并清本地缓存。

### 4.9 SSH 登录很慢或时通时断

**场景**：运维反馈 SSH 登录时要停在 `Connecting...` 很久才出密码提示；同机其他服务正常。或者：交互命令正常，一传大文件就卡住。

**排查顺序**：先按现象分类，不要把它们混成一个问题。

| 现象 | 首要嫌疑 | 验证命令 |
| --- | --- | --- |
| 停在 `Connecting...` 很久才出密码提示 | 服务端对客户端做反向 DNS 解析 / GSSAPI 认证超时 | `sshd -T \| grep -i usedns`、`time getent hosts <client_ip>` |
| 输密码后卡住 | PAM 或 `nsswitch` 里的远程模块（LDAP/NIS）超时 | `time getent passwd <user>` |
| 时通时断、偶发超时 | MTU/PMTU、队列溢出、conntrack 表满 | 按 4.2、4.5 与 4.7 三节的命令组合逐项排除 |
| 连接被立刻拒绝 | `sshd` 未监听、被过滤设备拦、被 `fail2ban` 封禁 | `ss -lntp \| grep :22`、`nft list ruleset` |
| 交互正常，传大文件卡住 | MTU/PMTU | `ping -M do -s 1472 <ip>` |

**两个最常被混起来的根因**：服务端反向解析客户端 IP（`UseDNS` 或 PAM/GSSAPI 去查目录服务）与传输大文件撞上 MTU 黑洞。前者的判据是 `sshd -T` 与 `time getent hosts <client_ip>`，后者是 `ping -M do`——**它们的处置完全无关**。

### 4.10 容器与 Kubernetes 场景的衔接

**场景**：Pod 里的服务连不上，但在宿主机上 `ss -lntp` 看不到那个端口。

**排查顺序**：先进对命名空间取证——`nsenter -t <pid> -n ip -br addr`、`ip route`、`ss -lntp`、`cat /etc/resolv.conf`；再看宿主机的转发与跟踪——`ip route get <pod_ip>`、`ip_forward`、`nf_conntrack_count/max`；然后看集群规则——`nft list ruleset` 里 Service 的 DNAT 与 NetworkPolicy 的痕迹；必要时在宿主机 veth 侧与容器内两侧限流抓包。

**三个判据**：宿主机 `ss` 看不到 Pod 端口是**正常现象**（命名空间不同）；Service 转发与出集群的 SNAT **依赖 conntrack**，集群规模大时必须把容量与超时纳入基线；`ping` 通不代表策略放行（ICMP 与 TCP 分开处理）。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 用 `netstat -antp` 排障 | 新系统默认不装 `net-tools`；用 `ss -tanp`，协议计数用 `nstat -az` |
| `ss` 不加 `-n` | 触发反向 DNS 解析，输出慢甚至卡住 |
| 只看 `ss -s` 不给状态分布 | 总览给不出「谁在涨」；补一条状态分布 |
| 用 `nstat` 的绝对值下结论 | 计数器从开机累计；要算增量 |
| 用 `ss` 找网卡丢包 | 那里看不到链路层；用 `ip -s link`/`ethtool -S`/`softnet_stat` |
| 照抄别人的 `ethtool -S` 字段做告警 | 计数器名是驱动私有的，换机型即失效 |
| 把 `netdev_max_backlog` 与 `ethtool -g` 当成同一件事 | 前者是内核软中断队列，调大它只多占内存；后者是网卡硬件环缓冲，修改它会重置网卡 |
| 采基线时把 `nf_conntrack_max` 的报错当故障 | 模块未加载时该键不存在，这本身就是基线事实 |
| 一次改多项参数 | 出事无法归因，也无法单项回滚 |
| 在生产机上改环缓冲或队列数 | 会重置网卡、短暂断流；必须排窗口 |
| 开着 offload 抓包分析 TCP 细节 | 看到的是「大包/未分段」；排障窗口内可临时关闭（会增加 CPU） |
| 在业务高峰无参数 `tcpdump -i any` | 最容易把机器抓挂的做法；必须限流、限时、落到独立目录 |
| 把抓到的包长期留在服务器上 | 占空间且含业务数据；分析完及时删除或归档 |

**第一反应不要做什么**：不要在没量化前改参数；不要用一次采样下结论；不要把「抓包没看到包」当成「没问题」。

## 要点自测

**问：拿到一台「网络有问题」的机器，前三分钟采什么？**
答：先记下环境与时间（`date`、`uname -r`），再读接口与路由（`ip -br addr`、`ip route`、`ip rule show`），然后取连接总览与状态分布（`ss -s`、状态分布），接着读监听与队列（`ss -lntp`），最后留一份计数器快照（`nstat -az`）与链路计数（`ip -s link`）。这些命令全部只读，生产机上可以做；目的是**把现场固化下来**，便于事后用差值对比。

**问：为什么基线卡里必须记录「原始值」？**
答：只有原始值才是能回滚的那个值。记录调优后的值等于丢失了「已知良好」的参照，出问题时无法判断改动是否有贡献。

**问：`/proc/net/softnet_stat` 与 `ethtool -g` 分别治什么病？**
答：前者是内核收包软中断的排队上限（溢出体现在该文件第 2 列），调大它只多占内核内存；后者是网卡硬件环缓冲（溢出体现在 `ethtool -S` 的驱动私有计数），调大它需要重置网卡、会短暂断流。

**问：一次抓包取证，抓之前的检查表是什么？**
答：明确要验证的假设、明确抓哪一跳、写好过滤表达式、准备 `-c`/`-w`/`timeout` 三重限制、确认落盘目录有空间且不在根分区、记录开始时间（跨机对照要事先对时）。抓完立即停止、拉回本地分析、记录结论与证据行、删除或归档临时文件并把结论写进故障记录。

**问：为什么「偶发问题先在实验链路复现」比「直接上生产抓包」更划算？**
答：偶发问题在生产上命中率低，而抓包本身有 CPU 与磁盘代价；用 `tc netem` 在隔离命名空间里注入延迟/丢包可以在几分钟内造出同等条件，从而确定过滤条件、验证重试与超时参数是否合理，再决定是否需要生产取证。

**第一反应不要做什么**：不要在没有基线时改参数；不要在生产高峰无参数抓包；不要把「宿主机视图」当成「容器视图」。
