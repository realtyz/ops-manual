
本规约规定这套 Linux 笔记**怎么写**，同时也是本目录结构与协作流程的唯一依据；仓库总览见根 `README.md`，两者冲突时以本规约为准。

## 一、定位与读者

- 定位：从新人到专家的成长路径；现场能不能用出来才是验收标准。判断一篇写得好不好，看读者能否靠它长能力。
- 读者：会基本 shell、用过 `top`/`free`/`systemctl`，没有系统学过操作系统原理；操作系统原理是本库负责补的空白。
- **定位只在大纲里说一次。** 各章、各篇都不复述"这一章写给谁""需要什么基础""读完能回答什么"——读者会在阅读中自己评估水平与节奏。

## 二、分层与命名

| 层（文件名前缀） | 回答什么问题 | 形态 |
| --- | --- | --- |
| 原理 | 这个机制**为什么存在**、代价落在哪里 | 多篇，各讲透一个机制 |
| 体系 | 各机制**怎么连起来**：一条时间主线 + 若干跨阶段的核对对象 | **汇总为一篇完整的文章**，内部用二级小节展开，不要拆成零散多篇 |
| 实操 | **怎么动手**：工具、字段读法、故障排查顺序、交付物 | 尽量短，一篇 |
| 判例 | **怎么判断**：现象 → 误判 → 判据 → 出处 | 一篇 |
| 治理 | 制度、产物模板、行业通行做法 | 一篇 |

- 命名形如 `NN_层_关键词.md`；**叙事不写进文件名**（"一次旅程的第 N 站"降为篇内小标题）。
- 导航篇（各章 `00_导读`、`00_引言`、本规约）不受前缀约束。
- 一个阶段的推荐构成：原理 4 篇左右 + 体系 1 篇 + 实操 1 篇 + 判例 1 篇 + 治理 1 篇。**参考实现见 `04_内存管理与OOM/`。**

## 三、篇骨架

**篇与篇的边界**（同一内容只写一次；相邻两篇重复时，后一篇用纯文字指向即可）：

| 层 | 只负责 | 不负责 |
| --- | --- | --- |
| 原理 | 机制为什么存在、代价与边界 | 本机观测命令、处置动作 |
| 体系 | 一条主线与跨阶段核对对象的串联、字段的读法 | 工具清单、制度设计 |
| 实操 | 用哪把工具、怎么读、故障排查顺序 | 机制推演、制度 |
| 判例 | 现象 → 误判 → 判据 → 出处 | 完整流程（指向实操） |
| 治理 | 上限配在哪一层、产物模板、行业做法 | 机制原理（指向原理/体系） |

### 原理篇

1. 从问题直接进入（"如果这样设计，会同时出哪几件事"），不要铺垫写作意图；
2. 机制展开：可以做历史演进、量级估算、公式推演、边界讨论；
3. 收尾一节写**机制在本名与字段上的边界**：把这套机制管不到的情况、容易并入其他机制的情况，用"某某字段描述的是 A，不描述 B"这类完整句写清（禁止用"抽象在哪里漏水"这类比喻作标题）；
4. `常见误解`（表：说法 / 事实）；
5. `要点自测`（课后习题形式：先问后答，附"第一反应不要做什么"）；
6. `参考文档`。

**原理篇不写动手章节、不放脚本、不报告个人实测值。** 需要读者自己验证的地方，在正文里可以少量命令演示，或者用一句话给思路。

### 体系篇（每章一篇）

1. 一条时间主线（一个对象的完整生命周期）从起点讲到终点，中间不打断；
2. 再用一节收拢若干条**跨阶段的核对对象**（例如存储标识、配置的读取时刻、证据所在介质），逐条写明它贯穿哪几个阶段、在每处读什么字段；
3. 关键字段给出"怎么读"：是什么、单位、判据、与谁同看、看到它转向哪一步；
4. `常见坑`；5. `要点自测`；6. `参考文档`。

宁可一篇长而连贯，也不要多篇短而断裂——零散分布会让知识不连贯。

### 实操篇

1. 一个问题一把工具（表：想知道什么 / 用什么 / 关键字段），并分清**命令**与**内核接口文件**；
2. **怎么读这些数字**：每个字段给五件事——是什么、单位、多少算异常（或说明只能与自己的基线比）、和谁一起看、看到它转向哪一步；
3. 采样纪律与基线卡（同口径、带时间戳、至少两次、留原始输出）；
4. **常见故障与排查方向**：按现象给具象场景（机器规格、服务、时间线、现象数值、约束）、排查顺序（先读什么、读到什么转往哪一步），并用完整句写出"一份合格的回答应当包含：结论、依据、边界、动作"——四个要素可以用顿号并列，但**不得压缩成"结论（…）＋依据（…）＋边界（…）＋动作（…）"这类无谓语的电报式骨架**；
5. `常见坑`；6. `要点自测`；7. `参考文档`。

**不给完整脚本**；复杂实验只给思路与判据，留给读者自行验证。

### 判例篇

每条四段式，且必须带具象场景：**场景 → 常见误判（以及它为什么看起来成立）→ 判据（读哪个字段、什么数值或趋势、什么条件下结论会变）→ 一句话结论 → 出处**。

判据必须能迁移；没有出处或真实案例支撑的判例不要写。

### 治理篇

1. 问题（没有制度时会怎样）→ 行业通行做法（注明来源）→ 可交付产物（模板与字段）→ 与其它章节的接口；
2. 关键接口字段的治理用法（例如 cgroup 的 `memory.peak` 用来定上限、`memory.events` 用差值判断本次事件）；
3. **具象治理场景 + 要交出的产物**（变更单、复盘记录、排期表等）；
4. `常见坑`；5. `要点自测`；6. `参考文档`。

## 四、写作形态

- 内容一律用标题、段落、表格、代码块承载；**引用块只用于呈现逐层演进中被剖析的回答**（"多数人会这么答"这类），不用于强调、结论或补充说明。
- **不使用 wikilink**：跨篇用纯文字说明大致位置，同章内可用《篇名》指路。**唯一例外是导航篇。**
- **章内验收与排障类篇目必须自足**：不得引用其他章节的内容，也不得把读者指向其他章——它的用途是就地把缺口定位到本章某一篇某一节，凡推去别章即失效。落在本章范围之外的问题只作划界，不给别章的篇名与位置。
- **不出现等级与技能编号**（`L1/L2`、`M1–M8`、`S1–S8`、`T0–T4`）；硬件术语 `L1/L2/L3 cache` 不在此列。
- **不讨论文档自身结构**：不写"这篇讲什么""必须先读什么""和后面的关系""本文将分三部分"这类声明。
- **给出数值就要给出读法**：凡让读者"看某个字段"，必须同时写清五件事（是什么、单位、判据、与谁同看、转向哪一步）。只写"看 `si`/`so`/`wa`"不算写作，那只是线索。
- **输出样例只展示格式**：贴命令输出时必须声明"数值仅示意、不代表你的机器"；不要把自己的实测值当通用结论。
- 术语首次出现给中文解释 + 英文原词，缩写展开（MMU、TLB、PTE、PSS、PSI、COW…）。
- 代码块语言标签按实际内容取（`bash`/`text`/`ini`/`mermaid`）；命令注释写 `# 验证：…`，不写只有 `#` 的注释行。
- 单位一律 MiB/GiB 与秒；默认值、内核差异、发行版差异必须标注，**默认值现场取，不凭记忆**。
- 破坏性操作标"只在可快照的实验机"；只读观测标"生产机上也可以做"；`drop_caches` 这类测量动作写明"只用于测量，生产上不要执行"。
- **「第一反应不要做什么」是必备句式**，它比命令清单更能体现判断力。
- **表述**：需要说「会被追问什么」时写生产现场或值班口径，需要说「演练验收」时写限时推演；读者看到的应当是现场判断力，而不是应试准备。

## 五、行文风格

### 学术报告语体

- **正文与表格单元格写完整句**：主语与谓语齐全，句间用「因此 / 由于 / 若 / 反之 / 同时 / 所以 / 因为 / 一旦」这类**显式逻辑连接**标出关系。不把结论压缩成名词短语堆叠。
- **下列位置允许名词短语**：篇名与文件名的关键词；二级标题提示下面几节讲哪几件事（如 `2. 五段交接，以及每一段交不出去时会怎样`）；流程与架构图中的节点标签；术语表的"名词"列；`**判据**：`/`**出处**：`/`**与谁同看**：` 这类**规约强制标签**的名字本身。
- **表格"内容"列、故障场景的步骤列、结论句不得写成电报**。禁止两种写法：用 `→` 代替「若……则……」或「因此」（例：禁止 `连磁盘都看不到 → 驱动缺失`，应写"若 `lsblk` 连磁盘都看不到，则新平台的存储控制器驱动不在 initramfs 里"）；把一句判断拆成"结论（…）＋依据（…）＋边界（…）＋动作（…）"这类无谓语片段。
- **比喻与黑话不得代替机制本名**：机制、占用与关系一律按本名写；标题、表头与表格单元格尤其禁止（标题会被检索与引用，危害最大）。判据是**把任意一句单独摘出来，读者不需要再问"这是什么意思"**——若必须先读过前文才知道"横切线"指什么，就是违规。
- 下表左列的说法**不得再用**，右列是应当写出来的本名。下表本身是在列举禁用词，左列出现不算违规；左列若出现在引用规范原文、内核文档或错误文本里，照引也不算违规；`死锁`、`水位`、`战场` 这类词在机制本名已在同一句内出现时可以保留。

| 不要写 | 改写为本名 |
| --- | --- |
| 抽象在哪里漏水 / 抽象会在哪里漏水 | 机制在本名与字段上的边界（把管不到的情况写成"某某字段描述的是 A，不描述 B"） |
| 三本账 / 账本（单独使用） | 地址空间、承诺额度、物理占用三类占用（或该机制的实际计数字段名） |
| 横切线 / 横切：参数 | 跨阶段的核对对象（并点名贯穿哪几个阶段与每处读什么字段） |
| 吃光 / 吃满 / 挤掉 | 该字段达到上限（写出字段名与上限值） |
| 兜底 | 回退路径（写清哪个规范、哪个路径）；或直接写"崩溃转储能力""可用内存" |
| 接力 / 交棒 / 接棒 | 控制权移交（写清移交的判据字段与失败落点） |
| 接力站 / 站点 / 一站 | 启动链的阶段（写清第几段、谁在跑） |
| 主战场 / 战场 | 该现象对应的命令与字段（如 `systemctl --failed` 列出的单元） |
| 关卡 / 关口 | 阶段（写清名称） |
| 收口 / 收口于 | 该节收拢到哪里（写清最后核对的字段或产物） |
| 骗人 / 会骗人 | 只说它实际列什么、不列什么（如 `lsmod` 只列可加载模块） |
| 体检 / 体检卡 | 基线采集与判据 |
| 抓不到 / 抓到转储 | 不产生 `vmcore` / 生成了 `vmcore` |
| 锚点机器 | 金标准机器（规约已定义的环境名） |

### 比喻不承担判据

- 任何结论都要落回**字段名、单位、数值或错误文本**。比喻可以用来引出机制，但**不得只给比喻**。
- 正例：「`vm.panic_on_oom` 取 `1` 时只覆盖整机 OOM；受 cgroup 限制的 OOM 仍只杀进程，因此不产生 `vmcore`。」
- 反例：「这一步是防火墙」「方向在内存账本与限制线」——没有字段、没有取值、没有错误文本。

## 六、以文档为准，实机其次

顺序是固定的：

1. **先查权威文档**：man 页、内核文档（`Documentation/`）、发行版官方文档、处理器厂商手册、教科书——其中 man 是命令用法的第一出处。机制、默认值、字段口径都以它们为准；
2. **内核文档与 man 手册优先取 6.x**：按**与目标机器同一主版本**取（当前基线是 6.x），并在引用时写明依据的版本。理由：老版本（4.x、5.x）的 `Documentation/` 里有些接口已被移除、默认值已经变过，直接引用会得到"文档与实机不符"的假冲突；而 `latest` 描述的是尚未进入发行版内核的东西，它只适合用来判断"这个接口还在不在、改成了什么"，默认值不能拿去对一台 6.x 的机器。man 页里的 "Since Linux x.y" 一类版本注记，正是用来判断某个行为在本机是否成立的判据；
3. **查命令的中文速查站只用它定位，不用它定稿**：`https://cmd.ifdev.cn/c/{cmd}.html`（例：`ls` → `https://cmd.ifdev.cn/c/ls.html`）适合快速摸清一个命令有哪些选项、以及某项能力在中文语境里叫什么；但它是社区翻译整理项目，更新滞后于包版本，示例多取自旧发行版，且不覆盖内核参数、`/proc`、`/sys` 与 `man 2/3/5` 的接口。**写进正文的选项名、默认值、单位与字段口径，一律回 man 或官方文档核过一遍**——两边对不上时以 man 为准；
4. **文档说不清、或与观察冲突时，才上机验证**；
5. **上机结果不等于普遍结论**：命令输出与内核版本、发行版、硬件、容器环境强相关。**没出现预想的结果，优先怀疑环境不匹配，而不是先改结论**；要把实机结果写进正文时，必须写清环境，并说明它可能只在这个环境成立。

由此派生四条纪律：

- 引用某个命令输出的口径（例如某一列怎么算）时，先现场用算术核对一遍，并标注工具版本——资料与实现会随版本变化；
- 凡"某特性是否生效"的判断，要给出独立核验手段（例如判断大页是否生效看 `AnonHugePages`，而不是看 `VmPTE`）；
- 不确定就写"未确认"，不要用一次观察当结论。
- 客观事实（关键路径、字段名、进程状态、命令输出格式、版本门控）可以也应当上机核对——核对是保证准确的手段。

## 七、临时验证不入库

- 写作用到的临时脚本、原始输出、草稿报告，放在自己临时建的工作目录里，**用完即删**；它们不属于这套笔记的一部分，正文、大纲、本规约都不引用，也不入库。
- 正文需要给出可复现路径时，给的是"思路 + 用哪个工具 + 读哪个字段"，而不是脚本文件与输出归档。

## 八、高发错误清单

前 8 条继承自 2026-09 全库审核（该审核报告已不在库里），第 9~16 条来自阶段 4 重写过程：

1. **默认值写反**：一切默认值现场取（`sysctl`、`tune2fs -l`、启动日志），不凭发行版或记忆猜。
2. **报错文本混为一谈**：`ENOSPC`/`EDQUOT`/`EROFS` 是三个不同的 errno。
3. **机制归因错位**：把观察值安到错误的开关上（例：`User=` 只换 uid/gid；`setenforce 0` 不等于关掉审计）。
4. **归因与观察不符**：结论要能解释观察，观察要能支持结论。
5. **命令达不到声称的效果**：写下的命令必须真的产生文中所说的输出。
6. **跨章/跨篇数字与口径打架**：同一个量要么一致，要么写清条件差异。
7. **未标发行版/版本**：RHEL 与 Debian 系不同处必须标注；内核文档一律按与目标机器同一主版本取（当前基线 6.x）并写明依据的版本，不引用未标版本的内核文档路径。
8. **危险命令缺边界**：破坏性操作必须有实验机限制、回滚步骤、上限控制。
9. **测量设计掩盖了要测的开销**：顺序、步长固定的访问会被预取掩盖；单点采样掩盖趋势；平均值掩盖长尾。
10. **用一个关键指标判断了错误的对象**：例如拿 `VmPTE` 判断大页是否生效。
11. **把"映射"当成"占用"**：地址空间、承诺额度、物理占用是三类不同的占用，任何"占了多少内存"都要指明是哪一个。
12. **跨实验拼表**：把不同轮次、不同条件的数字放进同一张对比表；对比必须来自同一轮统一实验，或明确标注条件差异。
13. **单轮计时当结论**：计时类结论要多轮并给波动范围；定稿前对最吃重的实验做一次独立复检。
14. **改旋钮 ≠ 重现机制**：把参数收紧不等于复现了它要防的现象，先让机制成立的条件成立。
15. **把工具口径当常数**：同一个列的含义会随工具版本变化，引用前现场核对并标注版本。
16. **混淆东西的类别**：`malloc` 是 C 库函数（`man 3`），`brk`/`mmap` 是系统调用（`man 2`），`free`/`ps` 是命令（`man 1`），`vm.swappiness` 是内核参数（`sysctl`），`memory.max` 是内核接口文件（直接读写），`RLIMIT_AS` 是进程资源限制（`setrlimit`）。**判据：看 man 节号——1 命令、2 系统调用、3 库函数、5 文件格式、8 管理命令。**

## 九、修订后必须同步
