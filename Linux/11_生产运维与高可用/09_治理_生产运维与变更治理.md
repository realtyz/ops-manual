# 生产运维与变更治理

一次变更做得好不好，取决于动手之前写下了多少东西。写下来的东西不是流程负担，而是把「当时我是怎么想的」变成「别人现在能照着做」的唯一手段。台账、变更单、到期日历、演练记录、复盘、Runbook 这六类产物，共同决定了一件事：**这台机器上的知识是在组织手里，还是在某个人的脑子里**。

## 1. 没有制度时会怎样

下面七行是缺制度时最常见的七种塌陷方式，每行的后果都用本库前面已经出现过的实测现象落地。

| 缺什么 | 具体后果 |
| --- | --- |
| 变更分级与审批 | 所有事都按同一个力度做，结果是最该被拦住的那件事没人拦。本机实测 `systemctl list-timers` 首行是 `sysstat-collect.timer`，`NEXT = Sat 2026-09-19 08:10:00 UTC`、`LEFT = 2min 25s`——如果一次配置变更没有分级、没有窗口审批，它完全可能落在 08:10 这个采集与上报的撞点上，事后无法归因是变更引起的还是定时任务引起的 |
| 变更单六要素 | 回滚只存在于执行人的记忆里，等到需要退回去时现场临时组织方案。本机一次真实变更（编号 `CHG-20260919-001`）留下的证据是：变更前状态快照 `state-before.txt` **109 行**、当时 running 服务 **24** 个。没有六要素，这 109 行就只是文件，不是判据——出事后没人知道「回到哪一行算回滚成功」 |
| 执行与验收分离 | 改的人自己宣布成功。本机 `systemctl show ssh` 给出的是 `ActiveState=active`、`SubState=running`、`NRestarts=0`、`ExecMainStartTimestamp=Sat 2026-09-19 07:20:10 UTC`、`UnitFileState=disabled`——自己验收的人通常只看 `active`，不会去看 `NRestarts` 有没有增长、也不会注意到这个 unit 根本没被 enable，下次重启后它不会自己起来 |
| 资产与依赖台账 | 不知道有哪些机器、谁依赖谁。本机资产采集本身就互相矛盾：`lshw` 把 `sda3` 报成 47GiB 的 EFI 分区、把内存报成 8GiB，而 `lsblk` 给的是 `sda 80G`、`ROTA=1`，`smartctl -i /dev/sda` 又报 `Rotation Rate: Solid State Device`。没有台账时，这些矛盾会以「到底哪份是对的」的形式拖住每一次变更 |
| 到期台账（证书 / 补丁 / 固件 / 备份保留期） | 到期这件事只在业务报错那天才被发现。本机 2026-09-19 08:08 UTC 采集 `www.example.com`，得到 `notAfter = Oct 27 22:17:21 2026 GMT`，**剩余 38 天**，链内 **4 张**证书——这 38 天里没有任何一条告警，下次有人看它大概率就是过期当天。补丁侧同样是「看得到但不处理」：`apt list --upgradable` 列出 4 个 netplan 包，`apt-get -s upgrade` 报 `deferred due to phasing`、`0 upgraded`（这是设计行为，不是故障）——没有补丁台账，这 4 个包会一直挂在待办里，谁也不清楚它们该排在哪个窗口 |
| 恢复演练制度 | 备份任务的成功只说明写入完成。本机实测过一组会骗人的数字：数据集 101 MiB 做硬链接（hard link，同一份数据被多个目录项指向）快照后，`du -sh --total` 报 **101 MiB**，而把 base 与 inc-2 两份分开 `du -sm` 相加得到 **202 MiB**——后者是假数字，因为 `big.bin` 的 `links=2`。没演练过的备份，连自己占多少空间都说不清，更谈不上在 RTO（Recovery Time Objective，恢复时间目标）内恢复 |
| Runbook 与交接 | 关键操作只留在一个人手里。本机可用的采集工具其实很齐全（`lscpu`、`lsblk`、`dmidecode`、`ethtool`、`nstat`），但 `restic`、`borg`、`ansible`、`keepalived`、`certbot`、`tuned`、`irqbalance` 在本机**未安装**（`command -v` 返回空）。「本机做不了什么」这本身就是一条必须登记的事实，否则下一个人在真故障里会重复试一遍 |

一条可以直接用的自检问法：**如果把现在这台机器的全部资料交给一个从没碰过它的人，他能不能在不问你任何问题的情况下完成一次变更、一次回滚、一次恢复？** 答不出来，缺的是产物，不是能力。

这条问法还可以拆成三问，逐台机器、逐项产物地问一遍：**这台机器上有哪些东西会在未来 90 天内到期，分别由谁负责？** **上一次有人真的从备份里恢复出数据是什么时候，耗时多少？** **哪一项操作目前只有一个人会做？** 三问都答得出来，说明产物是活的；只能答出第一问，说明台账刚建好、还没运行过。

最后一条边界要写在最前面：**本篇负责的是「哪一层要配上限、要留下哪份产物、谁来维护它」，不负责推导机制。** 一次变更做不过去，通常不是流程写得不全，而是某一层的机制没吃透——那种情况下正确的动作是回到对应章节去补机制，而不是继续往流程里加格子。

## 2. 行业通行的做法

下面每一条都写清它解决的是哪个具体问题，不按书名罗列：

- **ITIL 的变更分类（标准 / 重大 / 紧急）与冻结期**，解决的是「所有变更都被同一个流程对待」这个具体问题。三类变更的差别不在技术方案，而在**审批人、通知范围、时间窗**：标准变更是有 Runbook、低风险、执行人自决；重大变更要有评审记录与业务方在场；紧急变更允许先做后补单，但事后必须回答「为什么必须紧急」——如果答案是「因为平时没排期」，它就暴露出排期机制坏了，而不是这次真的紧急。冻结期（freeze，例如大促、财报、节假日）解决的是「变更与业务高峰撞车」的问题，冻结期内只留两类例外：**止损**（已经在出事）与**有明确时限的安全修复**；
- **Google SRE 手册的「Embracing Risk」**（错误预算与变更节奏），解决的是「为了不出事而停止变更」这个具体问题。错误预算（error budget）把「能容忍多少不可用」变成一个数字，用来决定这一次变更该不该发、发多快，而不是让风险偏好随嗓门大小浮动；
- **同一手册的「Release Engineering」**（渐进式发布 / 金丝雀 canary），解决的是「一次性推全量，失败就是全量事故」这个具体问题。做法是小流量先上、观察、再扩大；本库对应的实战纪律是分批，而批次的边界必须与容量余量绑定——单台虚拟机没有第二台承接流量，所以本机无法验证灰度，只能纸面推演；
- **同一手册的「Postmortem Culture」**（无指责复盘与行动项闭环），解决的是「复盘写完就结束」这个具体问题。无指责（blameless）不是不追责，而是把注意力从「谁按错了」移到「哪一道防线没拦住」；更硬的一半是行动项必须闭环——没有 owner（责任人）、期限与验收方式的行动项等于没写；
- **同一手册的「Managing Incidents」**（事故指挥与通报节奏），解决的是「十个人同时冲上去，互相覆盖对方的操作」这个具体问题。它把角色分开：指挥者不亲手操作，通报有固定节奏与单一出口，取证与止损由不同的人并行做；
- **《The Practice of System and Network Administration》中关于变更管理与文档维护的章节**，解决的是「文档写完就过期」这个具体问题。它主张文档的更新点与变更流程绑定：**变更收口就是文档更新点**，不是「有空再补」；
- **Ansible 官方文档的幂等（idempotency）与 rolling update / `serial`**，解决的是「脚本跑到第 37 台失败，留下 36 台新、64 台旧」这个具体问题。幂等指同一个操作执行一次与执行多次结果相同；声明式模块（模块描述「期望状态」而不是「执行命令」）让重跑收敛到同一状态而不是叠加副作用；`serial` 把一次 play 拆成若干批，让失败的影响面被限制在一批之内；
- **restic 与 BorgBackup 的 `check` / `prune`**，解决的是「备份看起来一直在成功，但仓库已经坏了或无限膨胀」这个具体问题。`check` 是仓库结构与数据完整性体检，`prune` 按保留策略真正回收空间——只删快照不回收，存储会一直涨；
- **RFC 8555（ACME，Automated Certificate Management Environment，自动证书管理环境）**，解决的是「人工签发与人工部署证书不可持续」这个具体问题。它把签发与续期标准化，才让 90 天有效期的证书成为可运维的常态；反过来，证书周期一旦缩短到 90 天，**没有自动续期就等于必然过期**；
- **发行版的分阶段推送（phased updates）**，解决的是「补丁既能打、又不敢一次推全量」这个具体问题。Ubuntu 会把一次更新按比例分批推送给人群，达到比例之后才轮到这台机器——本机实测 `apt list --upgradable` 列出 4 个 netplan 包，而 `apt-get -s upgrade` 报 `deferred due to phasing`、`0 upgraded`。**这是设计行为，不是故障**：补丁台账里要把它记成「等推送比例」，第一反应不要是加 `--force` 绕过。

## 3. 治理产物六件套

### 3.1 变更单

变更单（change request）是「一次有意识修改」的最小书面集合。分类决定审批路径，而分类的口径只有一条：**看影响面与可逆性，不看改动量**——改一行配置也可能不可逆，重启一百台无状态实例也可能完全可回滚。

| 分类 | 判据 | 审批与通知 | 事后动作 |
| --- | --- | --- | --- |
| 标准变更 | 有 Runbook、低风险、可回滚、影响面限于单台或单实例 | 执行人按 Runbook 自决，事前知会变更群 | 记录归档，更新台账 |
| 重大变更 | 影响面跨服务或跨用户群、含不可逆步骤、涉及数据写入或主从切换 | 评审通过后批准，业务方需在场 | 完整记录 + 必须复盘 |
| 紧急变更 | 已在出事，或有明确时限的安全修复 | 值班口头批准，立即执行 | 必须补单 + 必须复盘，并回答「为什么必须紧急」 |

它的六要素各自回答一个问题，字段如下：

| 要素 | 字段 | 填写要求 |
| --- | --- | --- |
| 目标 | 为什么做 / 成功标准 | 成功标准要可量化，例如「配置生效且 p99 不高于基线 10%」；写不出数字说明还没想清做成什么样算成功 |
| 范围 | 对象 / 第一批 / **不改动** / 生成方式 | 对象写成「服务名 + 主机分组」；第一批写「X/Y 台，约占容量 Z%」；不改动一栏本次必须逐条列出；生成方式写清清单是手写的还是从台账导出的 |
| 备份 | 内容与位置 / 时间点 / 验证方式 | 验证方式不能写「已备份」，要写「在实验机上恢复过一次，耗时 N 秒」；本机有可引用的实测：三个配置文件 314 / 255 / 1124 字节（合计 1693 字节）打成 `tar czf` 后 **22195 字节**，`tar tzf` 列出 6 项，`diff -r` 退出码 0 |
| 回滚 | 触发条件 / 回滚命令 / 回滚耗时 / 回滚后验证 | 触发条件必须是可判定的句子，形如「指标 + 阈值 + 持续时间」；耗时写实测，例如本机 `vm.swappiness` 由 60 改 10 再改回 60，apply **3 ms**、rollback **4 ms** |
| 验证 | 指标 / 业务 / 观察窗口 | 指标写「命令 + 阈值」，业务写一次真实调用或探活，观察窗口写时长（间歇性问题覆盖 2~3 个周期） |
| 窗口 | 开始与结束 / 到点未完成怎么办 / 通知对象 | 结束时间与「到点未完成」的判定人必须写；通知对象写清谁需要提前知道、用什么渠道 |

三个隐藏考点，它们是「填过表」与「能执行」的分界：

1. **范围里要写「不改什么」**。只写要改什么，执行时会顺手多改一点，而多改的那一点常常就是事故来源；
2. **回滚要写可判定的触发条件，不只是命令**。合格写法是「错误率 > 1% 持续 5 分钟即回滚」「`NRestarts` 由 0 变为非 0 即回滚」「连接数低于基线 70% 持续 10 分钟即回滚」。不合格写法是「看着不对就回滚」——它既不能执行，也不能交接；
3. **验证要写「怎么做」**。写「服务正常」等于没写；写「`systemctl show ssh -p NRestarts` 仍为 0，且外部探活 200 连续 10 分钟」才算。

执行时逐批填写下面这张表，它是事后追责与复盘唯一的原始素材：

| 批次 | 开始时间 | 结束时间 | 执行人 | 证据（命令与输出摘要） | 结论 |
| --- | --- | --- | --- | --- | --- |
| 第 1 批 <br> 1/10 台 | 2026-09-19 07:05 UTC | 2026-09-19 07:12 UTC | 张 | `systemctl show ssh -p NRestarts` = 0；`is-active` = active | 通过，进入下一批 |
| 第 2 批 | 2026-09-19 07:15 UTC | 2026-09-19 07:22 UTC | 张 | 同上 + 业务探活 200 | 通过 |

收口栏只填四项，缺任何一项这次变更就没有闭合：**结果**（成功 / 部分成功 / 已回滚）；**归档包**（含内容清单与校验和，本机可引用的实测是目录 `du -sh` **224K**、`tar czf` 后 **22195 字节**、`sha256sum` = `3550eec889ca5d803bf055179e458690a2f4838fb614adf691ba491f1cef0093`）；**台账与文档更新**（更新了哪份台账、哪段 Runbook）；**改进项**（问题 / owner / 期限 / 验收方式）。

### 3.2 资产与依赖台账

机器台账十个字段，每个字段都有明确维护点，能自动采集的一律不手填：

| 字段 | 取值示例（本机实测） | 采集方式 |
| --- | --- | --- |
| 资产编号 | `LABVM-001` | 与 CMDB（配置管理数据库）或工单系统对齐，手填 |
| 环境与角色 | 实验 / 单机应用与跳板 | 人写，但必须与命名规则一致 |
| 机房或可用区 | 本地虚拟化平台 | 平台导出 |
| 规格 | 4 vCPU（2 socket × 2 core × 1 thread）、L3 60 MiB、NUMA 1 节点、`MemTotal` 8083496 kB、`SwapTotal` 4194300 kB | `lscpu`、`free`；**注意 `free` 用 kB，正文口径按 MiB 折算（7894 MiB / 4095 MiB）** |
| 发行版与内核 | Ubuntu 24.04.5 LTS / `6.8.0-139-generic` / systemd `255.4-1ubuntu8.17` | `/etc/os-release`、`uname -r`、`systemctl --version` |
| 固件 | `dmidecode -t system` = `VMware, Inc.` / `VMware Virtual Platform`；`-t bios` = `Phoenix Technologies LTD` / `6.00` / `02/17/2026`；`-t baseboard` = `Intel Corporation` / `440BX Desktop Reference Platform` | `dmidecode -t system\|bios\|baseboard`（需要 root） |
| 数据盘与文件系统 | `sda 80G`（`ROTA=1`）、`sda2 2G ext4 /boot`、`sda3 48G LVM2_member`；根分区 ext4 on LVM 46.9 G | `lsblk`、`blkid`、`findmnt` |
| 备份归属 | 无外部备份目标（单机） | 与备份策略表交叉核对 |
| 到期日 | 证书、补丁窗口、备份保留期各自登记 | 见 3.3 |
| 责任人主备 | 主 / 备各一名，写明不在场时的授权人 | 人写，纳入季度复核 |

服务台账的字段要能回答「这个服务坏了会连带什么」，因此必须包含两头依赖与隐式依赖：

| 字段 | 取值示例 |
| --- | --- |
| 服务名与 unit | `ssh.service`（`FragmentPath=/usr/lib/systemd/system/ssh.service`） |
| 端点 | 监听地址与端口、外部域名 |
| 上游依赖 | 它调用谁（数据库、缓存、上游 API） |
| 下游消费者 | 谁调用它；本机可引用的事实是 `systemctl list-dependencies --reverse ssh` 只输出 `ssh.service` 自己一行——技术上没有别的单元依赖它，但它是唯一登录入口，业务影响面反而最大 |
| 隐式依赖 | 定时任务（`systemctl list-timers`）、证书续期、采集与安全 agent（`sysstat`、监控、审计） |
| 备份归属 | 数据由哪个备份任务覆盖、最近一次可恢复时间点 |
| 责任人 | 主 / 备，含联系方式与授权范围 |

三条字段纪律：**每个字段都要有维护点**（谁在什么时机更新它，没有维护点的字段一定会腐烂）；**能自动采集就不手填**（手填的规格数字与实际不符的概率随时间上升）；**不放「据说」**（采不到就写「采不到」并标待确认，而不是写一个来源不明的数字）。

采集命令清单（全部只读，生产机上也可以做；标 root 的需要提权）：`lscpu`、`free`、`lsblk`、`blkid`、`findmnt`、`dmidecode -t system|bios|baseboard`、`lspci`、`ethtool -i`、`smartctl -i`、`systemd-detect-virt`、`/etc/os-release`、`uname -r`、`systemctl --version`、`machine-id`。本机 `hostnamectl` 给出的主机名是 `linux-lab`、Machine ID 是 `bd821ce75df94970ad5b6d63b6a8f812`，`systemd-detect-virt` 回 `vmware`。

这套清单的边界必须写在台账里，因为**采不到同样是需要登记的事实**：本机 `ethtool -i ens33` 给出 `driver: e1000` 而 `firmware-version` 为空；`smartctl -i /dev/sda` 报 `SMART support is: Unavailable - device lacks SMART capability` 而**退出码是 0**（退出码不能作为「数据读到了」的判据）；`perf` 的硬件事件被虚拟化平台挡住。加上三处自相矛盾（`lshw` 的 47GiB EFI、`lshw` 的 8GiB 内存、`lsblk ROTA=1` 与 `smartctl` 的 `Solid State Device`），台账里这三格只能标「待确认」——**每台机器至少要有一个字段标待确认，否则说明采集粒度太粗，根本没去核对**。

### 3.3 到期日历

到期日历（expiry calendar）把「有到期日的东西」从「记在脑子里」变成「按剩余天数告警」。证书台账七列：

| 域名与用途 | 签发方式 | 到期日 | 责任人 | 续期方式 | 失败告警 | 验证方式 |
| --- | --- | --- | --- | --- | --- | --- |
| `www.example.com` 站点 TLS | 外部 CA 签发 | 2026-10-27（2026-09-19 实测剩余 38 天） | 张 | 提前 30 天人工续期 | 剩余 < 30 天 | 外部 `openssl s_client` + `-showcerts` 数张数（实测 4 张） |
| 内部 API TLS | 内部 CA 人工签发 | 2027-03-01 | 李 / 王（备） | 季度批量签发 | 剩余 < 45 天 | 内网探测 |
| 客户端信任库的根证书 | 内部 CA | 2036-01-01 | 王 | 提前 12 个月启动分发 | 提前 18 个月 | 各客户端抽样 |

告警按**剩余天数**分级，而不是按「是否已过期」：剩余 **30 天**进入排期（够走一次常规变更）；剩余 **14 天**升级为必须排入本周窗口，并通知责任人主备；剩余 **7 天**升级为必须当天处理并向上通报。这套分级的存在理由很直接：38 天的余量只够走一次常规流程，14 天只够走一次紧急变更，7 天之后任何流程都来不及了。

补丁三分类与「哪些必须重启」：

| 类别 | 判据 | 节奏 | 是否必须重启 |
| --- | --- | --- | --- |
| 紧急安全补丁 | 远程可利用、在野利用 | 走紧急变更通道，先做后补单 | 视组件而定，见下一张表 |
| 高危安全补丁 | 本地可利用或需要交互 | 排入最近补丁窗口 | 同上 |
| 功能与低危补丁 | 修 bug、增功能、低危漏洞 | 与版本升级一起排期，避免碎片化变更 | 同上 |

| 组件 | 是否需要重启 | 判据 |
| --- | --- | --- |
| 内核 | 需要 | `uname -r` 与已装内核包版本不一致；本机 `needrestart -b` 报 `KCUR=KEXP=6.8.0-139-generic`、`KSTA: 1`，即运行内核与已装内核一致，不需要为内核重启 |
| glibc / systemd 这类核心库 | 需要（至少重启受影响的服务） | 已在运行的进程仍映射着旧库；用 `needrestart` / `needs-restarting` 判断哪些进程受影响 |
| 纯数据包（man 页、词典、时区数据） | 不需要 | 下次被读取时自然生效 |

本机还有两条必须进台账的风险事实：**只装了一个内核版本**（`dpkg -l 'linux-image-*'` 只有一个），所以内核升级失败时没有旧内核启动项可回退；`System clock synchronized: no` 而 `NTP service: active`——「NTP 服务在跑」与「时钟已同步」是两件事，而时钟不同步会让到期计算、日志时间戳、证书校验同时失真。

固件与 BIOS 的登记项：主板厂商与型号、BIOS 版本与日期、RAID 卡与网卡固件版本、当前引导方式（UEFI 还是传统引导）。本机可写的实测值是 BIOS `6.00` / `02/17/2026`、`ethtool -i` 的 `firmware-version` 为空。**登记项里最容易被漏的是「怎么升级、升级窗口在哪、失败能不能回退」**——固件升级通常不可原地回退，属于必须提前演练窗口的动作。

日志留存期的三源取值：**合规与审计**（例如 ≥ 180 天）、**排障需要**（通常 7~30 天）、**安全事件回溯**（越长越好），三者**取最严**。本机可引用的实测量是 `journalctl --disk-usage` = **20.7 MiB**（更早一次基线是 53.9 MiB）、`du -sh /var/log` = 27M（其中 journal 21M、syslog 1.3M、installer 1.2M、`dpkg.log` 820K、`kern.log` 748K）。留存期一旦定下来，就要落到 `SystemMaxUse=` 与 `MaxRetentionSec=` 这两个约束上，否则「留存 180 天」和「磁盘只有 46.9 G」会互相打架。

容量台账里还有两个经常被漏掉的增长源，各自需要一条登记项：

| 增长源 | 会怎么长 | 要登记的约束与判据 |
| --- | --- | --- |
| 临时文件（`/tmp`、`/var/tmp`、应用自己的暂存目录） | 只增不减：失败任务的残留、被打开的临时文件删不掉 | **四个字段**：owner（谁负责清）、保留期（多久算过期，例如 10 天）、上限（目录或文件系统的水位线）、告警（到期未清或越过水位时谁收到）。策略落在 `systemd-tmpfiles` 的配置里，台账记「哪个目录归哪份配置管、保留期多少」，判据是 `systemd-tmpfiles --cat-config` 的生效策略与 `df` 的实际水位能对上 |
| 容器数据目录（镜像层、容器日志、卷与构建缓存） | 三处一起长：拉取的镜像与旧层、容器 stdout 日志（默认没有大小上限）、卷与构建缓存 | 分别定上限：镜像与缓存给保留份数或定期清理窗口，**容器日志单独配上限**（默认不限，是最常见的写满根分区原因），卷要进备份登记。判据是目录增长趋势与「清理动作有没有 runbook」，不是「容器还在跑」 |

两条边界：**容器日志写满根分区时，容器自身的日志里什么都看不到**（它正是被写满的那一方），所以判据只能在宿主侧读；**清临时目录不能代替治理**，因为「谁产生、谁清理」没有落到 owner 上时，清完还会长回来。

### 3.4 备份与恢复的登记

一份备份方案必须回答四个问题，答不出任何一个，这次备份就不算成立：

| 问题 | 不合格写法 | 合格写法 |
| --- | --- | --- |
| 备什么 | 「备份数据」 | 「`/srv/app/data` 与三份配置，排除缓存目录」 |
| 备到哪 | 「备份到远端」 | 「备份到独立介质 / 异地，且有一份离线或不可变」 |
| 多久一次 | 「每天」 | 「全量每周日 02:00，增量每天 02:00；保留 7 份日、4 份周、12 份月」 |
| 怎么验证 | 「任务成功」 | 「每季度从备份恢复到隔离目录，校验条数与校验和，并计时」 |

**三粒度**：文件级（file-level，按文件复制，恢复单个文件最快）；块级（block-level，按块或卷复制，适合整卷与数据库文件）；应用级（application-level，用数据库自带的导出/物理备份接口，一致性最好但恢复最慢）。三种一致性路径：**停机静默**（最可靠，代价是服务中断）、**快照**（存储层时点视图，代价是快照空间）、**应用级导出**（逻辑一致，代价是导出期间的负载与耗时）。

本机的对照数据可以说明粒度选择的代价差异：数据集 101 MiB，硬链接快照 base 101 MiB / 0.29 秒、inc-2 **16 KiB / 0.048 秒**；`rsync -a --checksum` 恢复耗时 **0.42 秒**、`diff -r` 一致；`tar -czf` 打包 101 MiB 用 **2.85 秒**；LVM（Logical Volume Manager，逻辑卷管理器）快照 200M 用 `lvcreate -s` **0.46 秒**，写满时 `data_percent` 从 0.01 涨到 **75.31**（覆盖 150 MiB 后），内核报 `device-mapper: snapshots: Invalidating snapshot: Unable to allocate exception.`——**快照不是备份**，空间用尽时它会自己失效，而失效是静默的。

**3-2-1 加一份离线或不可变**：三份数据、两种介质、一份异地，再补一份离线或 WORM（Write Once Read Many，写入后不可修改、不可删除）存储。补充项针对的是勒索软件与权限误删：一份能被在线账号删掉的备份，不算最后一道防线。

**保留策略 7 / 4 / 12**：7 份日备、4 份周备、12 份月备。它的作用是让保留期与恢复需求对齐——恢复需求通常落在「刚才」「上周」「去年同月」三个尺度上，而不是每天一份。这条策略必须与容量一起登记，否则它只是一个愿望：日均增量 × 保留份数 = 需要的备份容量，本机的对照数字是数据集 101 MiB 的基线、增量快照 **16 KiB**（0.048 秒），而硬链接快照的 `du -sh --total` 只报 **101 MiB**——**只看 `du` 的总数会把保留成本严重低估**，因为它把多份快照共享的数据块只算了一次，真实成本要按「独立介质上的物理占用」算。

恢复演练记录八步，每一步都要留下时间戳：

1. 选一个**真实但可丢**的对象（不要拿唯一的备份做演练）；
2. 从「决定恢复」这一刻开始计时，而不是从命令执行开始；
3. **只靠文档**找备份位置与提取方式，不使用记忆；
4. 恢复到隔离位置（不同目录、不同机器或独立卷）；
5. 校验条数与校验和，并让业务方读一次（读得出来才算数据可用）；
6. 计时到「业务可用」为止，而不是到「文件拷完」为止；
7. 记录实测 RTO 与 RPO（Recovery Point Objective，恢复点目标，即允许丢多少数据）、意外情况与文档缺口；
8. 清理演练产物并复核无残留。

本机做过的误删恢复演练可作为最小样本：快照 **0.046 秒**、`lsof +L1` 里含 `drill` 的条数 **0**、恢复 **0.046 秒**、`sha256sum -c` 三条全 OK。注意那个 0 的含义——**`lsof +L1` 为空不等于「没有已删除文件」，只等于「此刻没有进程持有它」**，这次之所以抓不到，是因为删除的文件本来就没有进程持有。

演练频率：**关键数据季度、配置半年、全站级一年**。频率的依据是「夹具会腐烂」——备份工具版本、凭据、目标路径、责任人都在变，超过一年不演练的恢复路径基本可以视为失效。

### 3.5 复盘与改进项

复盘（postmortem）固定六段，缺任何一段都会导致下次重复同一条路径：

| 段 | 内容 | 判据 |
| --- | --- | --- |
| 时间线 | 精确到分钟：现象出现、被发现、被认领、止损开始、止损生效、恢复 | 「3 点左右」不合格 |
| 影响面 | 多少用户、多少服务、多少数据、持续多久 | 用数字，不用「比较严重」 |
| 证据 | 命令、输出、日志、指标，带时间戳 | 结论必须能被证据支持 |
| 根因 | 直接原因 + **为什么没被提前发现** | 见下 |
| 止损动作 | 做了什么、预期效果、实际结果、有没有回滚 | 与变更单的触发条件对照 |
| 改进项 | 问题 / owner / 期限 / 验收方式 | 缺 owner 的改进项等于没写 |

无指责（blameless）的三个要点：**描述行为不描述人品**（写「当时按下了确认」，不写「太粗心」）；**追问防线而不是追问人**（为什么这个操作没有二次确认、为什么告警没响、为什么演练没覆盖）；**鼓励交出完整时间线**（隐瞒会让人为失误变成系统性未知）。

**「根因是人为失误」不算根因**。人为失误是每一个系统的常量，把它当根因等于宣布「这个问题无法改进」。合格写法是「直接原因：误删了生产目录；为什么没被提前发现：该目录没有任何保护与告警，且操作前没有确认清单」。

改进项三种去向，必须显式选一种：**立即修**（本次窗口内完成）、**排期**（给出期限与负责人）、**显式接受风险并写明批准人**（例如「为成本考虑不建第二台机器，批准人：某主管，复核时间：下一季度」）。第三种最容易漏——不写就是默认接受，写下来才是决策。

复盘触发三条：**发生了回滚**；**影响了业务**；**出现了「解释不了但过去了」的现象**（重启后好了、过了一会儿自己恢复了、没人说得清为什么）。第三条最容易被放过，而它恰恰是下一次事故的预告。

### 3.6 Runbook 与交接

四个词的区别必须分清，否则「文档写了」会被误当成「别人能做」：

| 词 | 时态 | 内容 | 例子 |
| --- | --- | --- | --- |
| 记录（record） | 过去时 | 当时发生了什么 | 变更执行记录、事故时间线 |
| 文档（document） | 现在时 | 系统现在是什么样 | 资产台账、依赖说明、参数基线 |
| Runbook | 遇到某现象怎么做 | 判据 + 动作 + 验收 | 「`NRestarts` 增长」→ 看日志 → 重启并观察 10 分钟 → `NRestarts` 停止增长 |
| SOP（Standard Operating Procedure，标准作业流程） | 必须怎么做 | 流程 + 角色 + 时限 | 「内核升级：申请窗口 → 备份 → 摘流量 → 分批重启 → 验收 → 归档」 |

Runbook 的验收标准只有一条：**别人照着能做，包括夜里三点**。这里的「别人」必须是**没有参与过这件事的人**，并且必须试做过一次。判定方式是把它交出去、让同事独立执行、记录他卡在哪一步——**卡住的每一处都是 Runbook 的缺口，不是他的能力问题**。

交接清单五项：

- Runbook 齐全，且每条都含判据、动作、验收与**升级条件**（什么情况下找谁）；
- 至少一位同事**独立执行过**一次，并留下记录；
- 成对值班与升级路径写明（谁在什么时段是第一联系人，联系不上谁接手）；
- 敏感材料（密钥、凭据、带外管理账号、加密盘的解锁材料）的存放位置与权限登记在册；
- 最近一次演练的时间与结论。

## 4. 关键字段与接口的治理用法

同一个字段有两种用法：**排障时它用来「看」，治理时它用来「定」**——定阈值、定上限、定告警线、定节奏。

| 字段 | 治理用法 |
| --- | --- |
| `systemctl show <unit> -p NRestarts` | 排障时看「它崩过没有」；治理时用来**定「服务是否稳定」的判据**，写进变更单验收栏。本机 `ssh` 实测 `NRestarts=0`——「`is-active` 是 active」不能替代它，一个正在反复崩溃并由 systemd 拉起的服务同样是 active |
| `systemctl show <unit> -p ExecMainStartTimestamp` | 排障时看「主进程什么时候起来的」；治理时用来**证明「主进程真的重启了」**。本机实测 `Sat 2026-09-19 07:20:10 UTC`，与变更窗口日志的时间戳对照才能说明新配置确实被加载 |
| `sysctl -n <key>` | 排障时看当前值；治理时用来**验收参数生效**——写进 `/etc/sysctl.d/` 不等于生效，读运行时值才算。本机 `vm.swappiness` 现场读是 60（单位无量纲，0~100，现场用 `sysctl -n vm.swappiness` 取，不要凭记忆）；`net.core.somaxconn` 运行时是 4096，而**没有任何文件写它**——「没写文件」与「值是默认」是两件事。另外要分清**哪套机制在读**：开机是 `systemd-sysctl.service`（读取集只有 `.d` 目录），手工重放是 procps 的 `sysctl --system`（末尾再读一次 `/etc/sysctl.conf`）；本机 `/etc/sysctl.conf` 之所以最后生效，是因为它被软链成 `/etc/sysctl.d/99-sysctl.conf`（`readlink -f` 指向 `/etc/sysctl.conf`，这条软链由 systemd 包提供）。台账里的「落点」一栏要写清是哪个文件、排在什么位置 |
| `df -i` 与 `df -h` | 排障时分别看 inode（索引节点）与块；治理时用来**定两条独立的容量告警线**。本机用 `mkfs.ext4 -N 32` 造的小 inode 盘实测 `df -i` 到 **100%** 而 `df -h` 只有 **1%**——只配一条告警线会漏掉整类故障 |
| `journalctl --disk-usage` 配 `SystemMaxUse=` / `MaxRetentionSec=` | 排障时看日志占了多少；治理时用来**定日志预算**：先量当前占用（本机 20.7 MiB，更早基线 53.9 MiB），再按「合规留存期 × 日增量」反推上限，最后把上限写进 drop-in。默认值现场取：`systemctl show systemd-journald -p LogsDirectory` 与 `journalctl --disk-usage` 一起看，不同发行版与版本的默认值不同 |
| `lsof +L1` | 排障时找被删除但仍被进程持有的文件；治理时用来**定「容量缺口是不是被已删除文件占着」**。本机 loop 靶盘 128 MiB 实测：删掉一个被进程持有的 40 MiB 文件后，`df` 已用 41 MiB 而 `du` 只有 20 KiB——`df` 与 `du` 打架时，先怀疑这一项 |
| `nstat` 的 `TcpExtListenOverflows` | 排障时看监听队列是否溢出（计数器，单位「次」，自开机起累计，只能看差值）；治理时用来**定「监听队列是否需要上调」**——在业务高峰窗口取差值，增长即意味着要调 `net.core.somaxconn` 与应用的 backlog，而不是加 CPU |
| `openssl s_client` 的 `notAfter` | 排障时看还剩几天；治理时用来**定告警提前量**。本机实测 `notAfter = Oct 27 22:17:21 2026 GMT`、剩余 38 天，据此才能定出 30/14/7 三级；提前量必须大于「续期流程 + 部署 + 观察」的总耗时 |
| `restic check` / `prune` | 排障时看仓库坏没坏、占了多少；治理时用来**定备份仓库的体检节奏**：`check` 只读，可以排进周巡检；`prune` 会重写索引、IO（输入输出）负载重，必须单独排窗口 |

## 5. 具象治理场景与要交出的产物

### 场景一：一个新团队刚接手一批生产机，没台账

**问题**：不知道有哪些机器、什么规格、跑什么、谁依赖谁；接手第一周就有人问「这台机器能不能重启」。**做法**：按 3.2 的十字段与采集命令清单逐台跑一遍，全部只读；能自动采集的字段不手填；采不到的字段写「采不到」，并在备注里写清被什么挡住（权限、硬件、虚拟化平台）；把互相矛盾的来源并列记下，标「待确认」而不是挑一个看起来对的。**产物**：资产与依赖台账 + 一份「哪些字段采不到、标待确认」的说明。可引用的实测事实是：本机 `smartctl` 读不到 SMART 数据却返回退出码 0、`ethtool -i` 的 `firmware-version` 为空、`lshw` 与 `lsblk`/`smartctl` 在三处互相矛盾——这四条都要进说明，否则下一个人会重跑一遍同样的命令。

### 场景二：季度到了要评审所有变更

**问题**：一个季度的变更记录散在各处，无法回答「哪些是标准变更、哪些本该升级为重大」。**做法**：把本季度变更按分类汇总成台账，逐条核对「当时的定级与影响面是否匹配」；把重复出现的标准变更**Runbook 化**（写成判据 + 动作 + 验收），让它下次可以按流程自决；同时写下**退化成重大变更的判据**（例如影响面从单台扩到整个服务、从可回滚变为不可逆、涉及数据库写入、窗口内没有能做回滚决策的人）。**产物**：变更分级台账 + 标准变更的 Runbook 化清单 + 退化为重大变更的判据。判据要写成一句话能执行的句子，例如「只要有一步不可逆，一律按重大变更走评审」，而不是「视情况而定」。

### 场景三：审计问「哪些系统下个月到期」

**问题**：没有到期日历，只能临时去翻邮件和工单。**做法**：按 3.3 的七列表格建台账，把证书、补丁窗口、固件升级计划、备份保留期全部纳入；告警按 30/14/7 天三级；**自动续期必须有独立的失败告警**（续期是静默的，失败不会自己喊）。**产物**：到期日历 + 按剩余天数的三级告警 + 续期失败告警。可引用的实测是 `www.example.com` 在 2026-09-19 08:08 UTC 采集时 `notAfter` 为 `Oct 27 22:17:21 2026 GMT`、剩余 **38 天**、链内 **4 张**——38 天这条数字同时说明两件事：余量够走一次常规变更，以及**这 38 天里当前没有任何告警**。

### 场景四：领导问「我们的备份能不能恢复」

**问题**：只能回答「备份任务每天成功」，这回答的是写入，不是恢复。**做法**：按 3.4 的八步做一次带计时的恢复演练，选真实但可丢的对象，只靠文档找备份，恢复到隔离位置，校验条数与校验和并让业务读一次，计时到「业务可用」为止。**产物**：恢复演练记录 + 实测 RTO / RPO + 与业务数字的差距分析。可引用的实测样本：快照 0.046 秒、恢复 0.046 秒、`sha256sum -c` 三条全 OK；硬链接快照 base 101 MiB / 0.29 秒、inc-2 16 KiB / 0.048 秒。差距分析要写成「实测 RTO 是 N 秒，业务要求是 M 分钟 / 小时，差在哪里」——本机是单机单卷，实测值只能说明**流程走通了**，不能外推到多机与异地场景。

### 场景五：一次回滚过的变更要收口

**问题**：回滚完成后现场就散了，没人知道为什么回滚、下次怎么避免。**做法**：先把证据打包归档（配置原文、窗口日志、执行记录），再按 3.5 写复盘六段，最后把改进项按三种去向分配。可引用的实测归档样本：三个配置文件 314 / 255 / 1124 字节（合计 1693）、变更窗口日志 **207019 字节 / 2184 行**、目录 `du -sh` 224K、`tar czf` 后 **22195 字节**、`tar tzf` 列出 6 项、`diff -r` 退出码 0、`sha256sum` = `3550eec889ca5d803bf055179e458690a2f4838fb614adf691ba491f1cef0093`。**产物**：归档包（含清单与校验和）+ 复盘六段 + 改进项清单（含 owner、期限、验收方式）。复盘里最不能省的是「为什么没被提前发现」这一段——回滚本身说明流程起作用了，真正要追的是哪一道防线让问题走到了回滚这一步。

### 场景六：只有一个人会做的操作

**问题**：某个操作（换证书、重启某个单元、清某个目录）全组只有一个人做过，他一休假就没人敢动。**做法**：把它写成 Runbook（判据 + 动作 + 验收 + 升级条件），交给另一位同事**独立执行一次**，记录他卡住的位置并据此补文档；不打断他、不提示，只在真出危险时介入。**产物**：Runbook + 这位同事之外的人照着做过一次的记录 + 交接清单五项。判定合格的标志是：他做完之后，你能对着他的记录指出下一步该改哪一句，而不是只能评价「做得挺好」。

## 6. 与其它章节的接口

- **阶段 1（实验环境与操作纪律）**：快照与状态一致性、观测工具边界、观测的代价与证据的易失性在那里。**本篇只负责把「证据要留什么、留在哪、谁能拿到」写成制度条款**，不负责证明某次采集是否可靠——那是那一边的判断；
- **阶段 8（systemd 与服务管理）**：unit 的生效链（文件放哪一层、要不要 `daemon-reload`）与 `systemctl show` 的字段口径在那里。**本篇只负责决定「哪些字段进入验收栏」**，例如用 `NRestarts` 判断稳定性、用 `ExecMainStartTimestamp` 证明主进程重启；字段本身是怎么算出来的以那一边为准；
- **阶段 9（日志与监控）**：日志留存、指标与告警规则、SLI（Service Level Indicator，服务等级指标）/ SLO（Service Level Objective，服务等级目标）与错误预算的口径在那里。**本篇只负责提出要求**（留存多久、按剩余天数分几级、失败告警必须有），规则怎么表达、告警怎么路由属于那一边；
- **阶段 10（性能分析与排障）**：性能基线与容量拐点在那里，它是**本篇变更单「验证」一栏的输入**——没有基线，「p99 不高于基线 10%」这句话无法判定。**本篇只负责把基线的采集条件、采集时机写进变更流程**；
- **阶段 6（网络协议栈与排障）**：网络计数器口径在那里（哪些是累计值、怎么看差值、哪些依赖窗口）。**本篇只引用它来定网络类告警线**，例如 `TcpExtListenOverflows` 只在同一业务窗口内取差值才有意义；
- **阶段 5（存储与文件系统）**：容量与文件系统保留块（ext4 默认留给 root 的那部分）的判据在那里。**本篇只负责把容量告警线、`df` 与 `du` 的口径差异写进巡检项**，不重复推导文件系统的结构。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 「改动很小，口头说一下就做」 | 分级看影响面，不看改动量；口头变更出事后没有可复盘对象 |
| 「备份任务成功就等于有备份」 | 成功只说明写入完成；验收标准是恢复并计时。本机 101 MiB 数据集 `du --total` 报 101 MiB，两份分开 `du -sm` 相加却是 202 MiB（硬链接） |
| 「台账建好一次就完了」 | 没有维护点的字段必然腐烂；更新点唯一 = 变更收口 |
| 「到期告警只在过期时响」 | 过期时已经是事故；要按剩余天数分级（本机证书实测剩余 38 天，当前无任何告警） |
| 「自动续期配好了就不用管」 | 续期是静默的，失败不会喊；必须单独配一条续期失败告警 |
| 「打完补丁不重启也算修好了」 | 内核与 glibc/systemd 这类核心库必须重启（或重启受影响服务）才生效 |
| 「复盘写『人为失误』就是根因」 | 那不是根因；要写直接原因 + 为什么没被提前发现 |
| 「改进项写『加强监控』就行」 | 没有 owner、期限、验收方式的改进项等于没写 |
| 「Runbook 写完就算交接完成」 | 验收标准是**未参与者照着做过一次**；他没试过，就不知道哪一步写不清 |
| 「`lsof +L1` 为空就是没有已删除文件」 | 它只说明此刻没有进程持有。本机误删演练里该条数为 0，因为被删文件本来就没有持有者 |
| 「`df` 和 `du` 对不上就是工具坏了」 | 通常是已删除但被持有的文件。本机 loop 靶盘实测 `df` 已用 41 MiB 而 `du` 20 KiB |
| 「容量只看 `df -h` 百分比」 | inode 会先饱和。本机 `mkfs.ext4 -N 32` 的盘实测 `df -i` 100% 而 `df -h` 只有 1% |
| 「工具没装就跳过这一项」 | 「做不了」必须登记。本机 `restic`/`borg`/`ansible`/`keepalived`/`certbot`/`tuned`/`irqbalance` 均未安装（`command -v` 为空；`systemctl is-active tuned` 返回 inactive 而退出码 4、`is-enabled` 是 not-found），不登记就会在真故障里重复试 |
| 「退出码 0 就说明数据读到了」 | 本机 `smartctl -i /dev/sda` 报 SMART 不可用而**退出码 0**；判据必须是输出内容，不是退出码 |

**第一反应不要做什么**：不要在没写下回滚触发条件之前开始执行；不要把「备份任务成功」当验收；不要在台账里填一个来源不明的数字；不要把复盘停在「人为失误」；不要把只有一个人会做的操作继续留在那一个人手里。

## 要点自测

**问：变更单六要素里，哪三个最容易填成空话？怎么把它们填实？**
答：范围（要写出「不改什么」）、回滚（要写出可判定的触发条件：指标 + 阈值 + 持续时间）、验证（要写出「怎么做」而不只是「做什么」）。填实的方法是把它们交给没参与的人，看他能不能照着执行、照着重放。

**问：到期告警为什么必须按剩余天数分级，而不是按「是否已过期」？**
答：过期时已经是事故，告警失去意义。按 30 / 14 / 7 天分级对应三种不同的处理节奏：30 天够走一次常规变更，14 天只够走紧急变更，7 天就只能当天处理。本机 2026-09-19 实测 `www.example.com` 的 `notAfter = Oct 27 22:17:21 2026 GMT`、剩余 38 天，而当时没有任何告警——这条数字本身就是「缺到期台账」的证据。

**问：「`NRestarts=0`」与「`is-active` 是 active」有什么区别，为什么验收要用前者？**
答：`is-active` 只说明此刻进程在跑；一个反复崩溃又被 systemd 拉起的服务同样是 active。`NRestarts` 是累计重启次数，由 0 变为非 0 说明发生过崩溃。治理时它用来定「服务是否稳定」的判据，写进变更单验收栏；本机 `ssh` 实测 `NRestarts=0`、`ExecMainStartTimestamp=Sat 2026-09-19 07:20:10 UTC`。

**问：为什么 `df -i` 必须和 `df -h` 一起作为容量告警线？**
答：两者会分别独立饱和。`df -i` 看 inode（每个文件或目录占一个），`df -h` 看数据块。本机用 `mkfs.ext4 -N 32` 造的小 inode 盘实测 `df -i` 到 100% 而 `df -h` 只有 1%——只配一条线会漏掉整类「盘没满但写不进文件」的故障。

**问：一次合格的恢复演练，八步里哪一步最容易被省掉，省掉之后会丢什么？**
答：第 6 步「计时到业务可用为止」和第 7 步「记录意外与文档缺口」。省掉计时，拿到的是「命令跑完了」而不是 RTO；省掉文档缺口记录，下次演练或真恢复还会卡在同一处。参考实测样本：快照 0.046 秒、恢复 0.046 秒、`sha256sum -c` 三条全 OK。

**问：交接清单里为什么必须有「至少一位同事独立执行过一次」这一项？**
答：因为 Runbook 的验收标准是「别人照着能做，包括夜里三点」，而这件事只能通过试做来检验。试做中卡住的每一处都是文档缺口。没有这一项时，「文档写了」会被当成「别人能做」，两者之间的差距通常只在真出事时才暴露。

**问：改进项的三种去向分别是什么，第三种为什么最容易出问题？**
答：立即修、排期（有 owner 与期限）、显式接受风险并写明批准人。第三种最容易出问题，因为它不写下来就等于默认接受，没人知道这是一个被决定过的风险；写下来它才是一个有批准人、有复核时间的决策。

**第一反应不要做什么**：不要在字段采不到的时候填一个看起来合理的数；不要用工具退出码判断数据是否读到；不要把「演练做了」等同于「记录留了」。
