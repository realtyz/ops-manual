> `/usr/lib/sysctl.d/10-apparmor.conf` → `/etc/sysctl.d/10-bufferbloat.conf` → `/etc/sysctl.d/10-console-messages.conf` → `/etc/sysctl.d/10-ipv6-privacy.conf` → `/etc/sysctl.d/10-kernel-hardening.conf` → `/etc/sysctl.d/10-magic-sysrq.conf` → `/etc/sysctl.d/10-map-count.conf` → `/etc/sysctl.d/10-network-security.conf` → `/etc/sysctl.d/10-ptrace.conf` → `/etc/sysctl.d/10-zeropage.conf` → `/usr/lib/sysctl.d/50-pid-max.conf` → `/usr/lib/sysctl.d/99-protect-links.conf` → `/etc/sysctl.d/99-sysctl.conf` → `/etc/sysctl.conf`。**结论：目录合并后按文件名排序，同名文件 `/etc` 优先于 `/usr/lib`，最后再应用 `/etc/sysctl.conf`；后加载的覆盖先加载的。**
>
> 本次重跑新增/修正的三条事实：
> - **文件清单**：`/etc/sysctl.d/` 是 **9 个 `10-*.conf` + `99-sysctl.conf`**（目录里还有一个 `README.sysctl`，因为它不以 `.conf` 结尾，**不参与应用**，也不会出现在上面的顺序里）；`/usr/lib/sysctl.d/` 是 **3 个文件**；**`/run/sysctl.d/` 在本机根本不存在**——所以 man 页里说的「三个目录」在这台机器上实际只有两个。
> - **权限提示取决于「以谁的身份跑」**：以 **root**（`uid=0`）跑 `sysctl --system` 时**一条 `permission denied` 都没有**（`grep -c` 得 0），退出码 0，成功应用 **17 个键**；以 **`realtyz`（uid=1000）** 跑同一条命令会出现 **17 条** `sysctl: permission denied on key "…", ignoring`（每个键一条），但**退出码仍然是 0**、命令不会中断。`sysctl -a` 同理：root 可读 **1018** 行，`realtyz` 只读到 **1004** 行外加一串 `permission denied`。
> - **硬件与固件信息现在拿得到**：`dmidecode -t system` 报 `Manufacturer: VMware, Inc.` / `Product Name: VMware Virtual Platform` / 序列号 `VMware-56 4d 84 a6 1c 13 ec db-…`；`dmidecode -t bios` 报 `Vendor: Phoenix Technologies LTD` / `Version: 6.00` / `Release Date: 02/17/2026` / `BIOS Revision: 4.6`；`lspci` 报出 40 余个设备（含 `Intel Corporation 82545EM Gigabit Ethernet Controller` 与 `Broadcom / LSI 53c1030` SCSI 控制器）；`lshw -short` 可用；`ethtool -i ens33` 报 `driver: e1000`；**`/sys/class/dmi/id/` 的 `sys_vendor`/`product_name`/`bios_vendor`/`bios_version`/`bios_date`/`board_name` 全部有值**。`smartctl -i /dev/sda` 能认出盘（`Vendor: VMware` / `Product: VMware Virtual S` / `85,899,345,920 bytes`）但明确回 **`SMART support is: Unavailable - device lacks SMART capability`**、退出码 **0**——**「工具装了」不等于「数据拿得到」**。
> - `systemd-detect-virt` 实测输出 **`vmware`**；`hostnamectl` 显示 `Virtualization: vmware`、`Icon name: computer-vm`。
>
> **未实测**：RAID 卡与 BBU（本机没有阵列卡）、固件升级（能读出 BIOS 版本，但不在实验机上刷写）、`smartctl -a` 的健康与属性数据（虚拟盘不支持 SMART）、`tuned`/`irqbalance` 的调优效果（**本机这两个包未安装**：`command -v tuned`/`irqbalance` 都是 `NOT-FOUND`，`systemctl is-active` 返回 `inactive` 但**退出码 4**、`is-enabled` 返回 `not-found`，`/usr/lib/systemd/system/tuned.service` 与 `irqbalance.service` 都不存在——2026-09-19 08:35 UTC 复核，原始输出见 `.labvm/evidence/11b_14_tuned_irqbalance_real.out.txt`）。

## 0. 30 秒速览

> [!abstract] 这一篇只要记住六句话
> - **参数不生效，八成是加载顺序问题，不是「改了没用」。**
>   - 证据：实验机实测 `sysctl --system` 的顺序是 `/usr/lib/sysctl.d/10-apparmor.conf` → `/etc/sysctl.d/10-*.conf`（9 个）→ `/usr/lib/sysctl.d/50-pid-max.conf` → `/usr/lib/sysctl.d/99-protect-links.conf` → `/etc/sysctl.d/99-sysctl.conf` → `/etc/sysctl.conf`；**后加载的覆盖先加载的**，所以「同一个键写在两个文件里」就会产生你意外的结果（本机 `kernel.pid_max` 只在 `/usr/lib/sysctl.d/50-pid-max.conf` 里出现过一次，最终值 4194304 就是它）。
> - **参数的验收口径永远是 `sysctl -n`（运行时值），不是配置文件内容。**
>   - 怎么验证：`sysctl -n net.core.somaxconn` 与 `grep -r somaxconn /etc/sysctl.d/` 是两件事；只改文件不 `sysctl --system` 时，前者不会变。本机 `net.core.somaxconn` 没有任何文件显式写它，`sysctl -n` 得 4096 —— 这是**内核默认值**，不是配置值。
> - **调优参数是「为了修一个具体问题」，不是「抄一份最佳实践」。**
>   - 证据：`net.ipv4.tcp_tw_reuse` 在 NAT 场景下有语义边界，盲目开启可能引发难以定位的问题；每个参数都要写清「为什么调、什么条件下调、怎么回滚」。
> - **大部分「调优项」的正确来源是应用的真实瓶颈，而不是阈值表。**
>   - 怎么验证：先量化瓶颈（连接队列溢出？句柄不够？重传？），再决定改哪个参数；改完用同一个判据复验。
> - **硬件与固件是台账里唯一「平时不看、出事时救命」的一栏。**
>   - 证据：随机重启、网卡丢包、阵列卡缓存策略异常，根因常常在 BIOS/固件版本上；而这些字段**只有采集过才有对比基线**。实验机现在**真能采到**：`dmidecode -t bios` 给出 `Phoenix Technologies LTD / 6.00 / 02/17/2026`，`lspci` 给出网卡与存储控制器型号，`ethtool -i ens33` 给出驱动 `e1000`。
> - **虚拟化环境会伪造硬件信息，采到的字段要先判断真假。**
>   - 证据：实验机是 VMware 全虚拟化，`dmidecode` 里的整机型号是 `VMware Virtual Platform`、主板是 `440BX Desktop Reference Platform`（一个 1998 年的芯片组代号）；`lsblk -d -o ROTA` 把虚拟盘报成 `ROTA=1`（旋转盘），而 `smartctl` 又说 `SMART support is: Unavailable`。**DMI 里有值 ≠ 这台机器真有那块主板。**

## 1. sysctl：改参数的正确姿势

### 1.1 加载顺序（实验机实测）

```bash
sysctl --system 2>&1 | head -20           # 验证：打印本次应用了哪些文件（顺序就是生效顺序）
sysctl --system --debug 2>&1 | head -20   # 验证：--debug 不改变顺序，输出与不加时一致（实验机实测）
```

一次 `sysctl --system` 共应用 **14 个文件、17 个键**——**大多数键根本不在这些文件里，值来自内核默认**。所以「值不对」的第一步永远是 `sysctl -n`，而不是翻文件。

三条规则（按 man 页与实测推导）：

1. **三个目录合并后按文件名排序**：`/etc/sysctl.d/`、`/run/sysctl.d/`、`/usr/lib/sysctl.d/`。注意**目录不存在就不参与**——实验机上 `/run/sysctl.d/` 不存在，实际只有两个目录合并。
2. **同名文件时 `/etc` 优先于 `/run` 优先于 `/usr/lib`**（管理员配置覆盖发行版默认）。
3. **`/etc/sysctl.conf` 最后应用**（兼容旧配置），所以它能覆盖前面所有文件的同名键——这正是「我明明改了 `/etc/sysctl.d/99-xxx.conf` 却不生效」的经典原因。

> [!warning] 权限提示是「身份问题」，不是「环境问题」
> 实验机上以 **root** 跑 `sysctl --system`：**0 条** `permission denied`、退出码 0。以 **`realtyz`（uid=1000）** 跑同一条命令：**17 条** `sysctl: permission denied on key "…", ignoring`（每个键一条）、**退出码仍然是 0**。
>
> 两件事必须分清：**① 这条提示的有无只取决于「当前用户对 `/proc/sys/…` 有没有写权限」**，与是不是虚拟机、是不是 WSL 无关；**② 看到提示不等于命令失败**——被拒的键会被跳过、其余继续应用，退出码依然是 0，所以「靠退出码判断参数是否生效」是错的，必须回读 `sysctl -n`。

> [!warning] 三个实战结论
> - **自建文件用高编号**（例如 `99-`）能减少被覆盖的可能，但**挡不住 `/etc/sysctl.conf`**。
> - **要判断某键的最终值，先 `grep -r` 找出所有写入点**：`grep -rn '<键名>' /etc/sysctl.d /usr/lib/sysctl.d /run/sysctl.d /etc/sysctl.conf`。
> - **同一台机器上多人写参数是常见现象**，所以参数台账（第 3 节）比参数文件更重要。

### 1.2 改与验

```bash
sysctl -n net.core.somaxconn               # 验证：读运行时值（不带键名=只输出值）
sysctl net.core.somaxconn                  # 验证：带键名输出（便于写进记录）
sudo sysctl -w net.core.somaxconn=4096     # 验证：临时修改（重启即失效，用于快速验证效果）
sudo sysctl --system                       # 验证：重新应用全部配置文件（持久化改动后必须执行）
```

四步流程（与全章的变更纪律一致）：

```text
1. 记录现值：sysctl -n <键>            → 写进变更记录
2. 备份：把要改的文件与状态快照留下
3. 改：写入 /etc/sysctl.d/99-<用途>.conf（不要直接改 /etc/sysctl.conf，除非团队约定如此）
4. 验收：sysctl --system 后 sysctl -n <键> 必须等于目标值；再观察业务指标
```

### 1.3 改了不生效：排查顺序

| 步骤 | 命令 | 说明 |
| --- | --- | --- |
| 1 | `sysctl -n <键>` | 先看运行时值到底是多少 |
| 2 | `grep -rn '<键>' /etc/sysctl.d /usr/lib/sysctl.d /run/sysctl.d /etc/sysctl.conf` | 找出所有写入点（可能有更高优先级的文件覆盖） |
| 3 | `sysctl --system 2>&1 \| grep -i '<键>'` | 看应用过程中有没有被拒（权限/只读键） |
| 4 | 检查是否属于「运行时只读」的键 | 部分键只能在启动参数里设，运行时改不了 |
| 5 | 检查应用是否需要重启才读取 | 例如某些网络参数对**已建立连接**不生效，只影响新连接 |

## 2. 常见调优项与副作用

> [!important] 这一节读法
> 下表**不是调优建议**，而是「别人让你调这个参数时，你要问的问题」。每一项都必须先量化瓶颈，再决定改不改。

| 类别 | 代表项 | 什么时候可能需要 | 副作用 / 边界 |
| --- | --- | --- | --- |
| 接受队列 | `net.core.somaxconn`、`net.ipv4.tcp_max_syn_backlog` | 出现 `TcpExtListenOverflows`（accept 队列溢出） | 队列变大只是缓冲，**根因通常是应用 `accept()` 太慢**；同时要确认应用自己的 backlog 参数 |
| 临时端口 | `net.ipv4.ip_local_port_range` | 短连接密集、TIME_WAIT 堆积导致偶发连接失败 | 扩大端口范围会占用更多内存与 conntrack 条目；不能替代连接池 |
| TIME_WAIT | `net.ipv4.tcp_tw_reuse` | 客户端侧端口耗尽 | **NAT 场景下有语义边界**；开启前要确认时间戳等前置条件 |
| 文件句柄 | `fs.file-max` | 系统级 fd 耗尽 | 真正该先改的是进程级 `LimitNOFILE`（systemd 单元）；只调全局上限对服务没用 |
| 进程数 | `kernel.pid_max` | 进程/线程数撞上限 | 调高会增大内核内存开销；先确认是不是 fork 风暴 |
| 网络缓冲 | `net.core.rmem_max`/`wmem_max`、`tcp_rmem`/`tcp_wmem` | 高带宽高延迟链路吞吐上不去 | 内存占用上升；应用未使用缓冲自动调优时才有必要 |
| 内存回收 | `vm.swappiness` | swap 使用策略调整 | 影响回收倾向；在容器与 cgroup v2 下的生效范围要单独确认 |
| 脏页回写 | `vm.dirty_ratio`/`dirty_background_ratio` | 回写突发导致延迟尖刺 | 调大能提升吞吐但会加剧突发；错误方向的调整会放大延迟 |
| 连接跟踪 | `net.netfilter.nf_conntrack_max` | `nf_conntrack: table full` | 表变大占用内存；要先查是不是连接泄漏 |
| 内核应急通道 | `kernel.sysrq` | 误触变成重启或崩溃 | SysRq 是位掩码，打开危险位会让误触变成重启（阶段 1 的纪律）。（注意：内核同页合并 KSM **没有对应的 sysctl 键**，它经 `/sys/kernel/mm/ksm/` 管理，别把两者混在一个台账格里。） |

```bash
sysctl -a 2>/dev/null | wc -l               # 验证：可读键数量（判断有没有权限限制；实验机 root 1018 行 / realtyz 1004 行）
nstat -az | grep -E 'ListenOverflows|ListenDrops|TCPTimeouts|Retrans'
                                          # 验证：改网络参数前，先确认是哪个计数器在涨
ulimit -n; grep -i 'open files' /proc/<pid>/limits
                                          # 验证：句柄问题要先看进程级限制，而不是全局 fs.file-max
```

## 3. 参数基线与台账

### 3.1 每条参数记录六个字段

```text
键：net.core.somaxconn
当前值：4096                        采集时间：2026-09-19T08:10+00:00（实验机时区 Etc/UTC）
落点：无文件写入（内核默认值）      （同时 grep 确认没有其它文件覆盖）
为什么：压测中出现 TcpExtListenOverflows，应用 accept 速率受限
验收：sysctl -n net.core.somaxconn == 4096；Overflows 不再增长
回滚：删除该文件中的这一行 + sysctl --system；旧值 4096
```

六个字段里的「落点」和「回滚」是多数团队的缺口：**没有落点，你不知道谁写的；没有回滚，你不敢改回去。**

### 3.2 基线要成组采集

```bash
{
  date -Is
  uname -r
  sysctl -n vm.swappiness fs.file-max kernel.pid_max net.core.somaxconn \
             net.ipv4.ip_local_port_range net.ipv4.tcp_tw_reuse \
             vm.dirty_ratio vm.dirty_background_ratio 2>/dev/null
  ulimit -n
} | tee "./param-baseline-$(date +%F).txt"
                                          # 验证：一次采齐一组关键参数（成组采集才好比对）
```

## 4. 硬件与固件基线

### 4.1 采什么、怎么采

| 项 | 命令 | 环境限制 |
| --- | --- | --- |
| CPU 型号与拓扑 | `lscpu` | 虚拟化下通常可用；实验机实测 `4` vCPU（2 socket × 2 core × 1 thread）/ `Intel(R) Core(TM) i7-14650HX` / L3 60 MiB / NUMA 1 节点 |
| 内存容量 | `free -m`、`grep MemTotal /proc/meminfo` | 通用；实验机实测 `MemTotal` 7894 MiB（`8083496 kB`）、swap 4095 MiB |
| 主板/整机型号与序列号 | `dmidecode -t system` | **需要 root**；容器里通常拿不到。实验机（VMware 全虚拟化 + root）**实测可用**：`VMware, Inc.` / `VMware Virtual Platform` / `VMware-56 4d 84 …` |
| BIOS/UEFI 版本与日期 | `dmidecode -t bios` | 同上；实验机实测 `Phoenix Technologies LTD / 6.00 / 02/17/2026` |
| PCI 设备（含网卡/RAID 卡） | `lspci`、`lspci -vv` | 虚拟机上看到的是**模拟设备**（实验机实测 `Intel 82545EM` 网卡、`Broadcom / LSI 53c1030` SCSI、`VMware SVGA II`），字段可取但型号是虚拟化平台编造的 |
| 网卡驱动与固件 | `ethtool -i <iface>` | 需要网卡可见；实验机实测 `driver: e1000`、`bus-info: 0000:02:01.0`，**固件版本为空**（虚拟网卡没有独立固件） |
| 磁盘健康 | `smartctl -a <dev>`、`nvme smart-log <dev>` | 需要 root 与直通设备；实验机**工具可用但数据不可用**：`smartctl -i /dev/sda` 能识别盘，却回 `SMART support is: Unavailable - device lacks SMART capability` |
| 阵列卡与 BBU | 厂商工具（`storcli`/`perccli` 等） | 需要厂商工具与对应硬件；实验机无阵列卡 |
| 虚拟化类型 | `systemd-detect-virt` | 通用；实验机实测输出 **`vmware`**（`hostnamectl` 显示 `Virtualization: vmware`） |

### 4.2 为什么固件必须进台账

三个真实场景：

1. **「随机重启」**：BIOS/UEFI 或阵列卡固件的已知缺陷，表现为没有规律的自动重启，日志里什么都看不到。**没有版本记录，就无法判断「是不是升过固件之后才开始的」。**
2. **写缓存策略异常**：BBU 电量不足或失效时，阵列卡会从「写回」降级为「写穿」，IO 延迟显著上升——**这是静默的性能退化，不看阵列卡状态就发现不了**。
3. **网卡固件与驱动不匹配**：表现为丢包、协商异常、甚至驱动崩溃。**采集 `ethtool -i` 的输出，才有比对基线。**

```bash
systemd-detect-virt                       # 验证：先确认是不是虚拟机（虚拟机上很多硬件字段无意义）
lscpu | grep -E '^(Architecture|CPU\(s\)|Model name)'   # 验证：CPU 层信息
ethtool -i <iface> 2>/dev/null            # 验证：网卡驱动与固件版本（物理机上才准确）
dmidecode -t system; dmidecode -t bios    # 验证：整机与 BIOS/固件版本（需要 root）
lspci | head                              # 验证：PCI 设备清单（虚拟机上看到的是模拟设备）
smartctl -i /dev/sda                      # 验证：磁盘是否支持 SMART（虚拟盘通常不支持）
```

实验机的实测产出（芯片组代号那一行最能说明「虚拟化会伪造硬件信息」）：

```text
$ systemd-detect-virt
vmware

$ dmidecode -t system | grep -E 'Manufacturer|Product Name|Serial Number'
	Manufacturer: VMware, Inc.
	Product Name: VMware Virtual Platform
	Serial Number: VMware-56 4d 84 a6 1c 13 ec db-24 40 49 a6 f2 66 2c 0f

$ dmidecode -t bios | grep -E 'Vendor|Version|Release Date'
	Vendor: Phoenix Technologies LTD
	Version: 6.00
	Release Date: 02/17/2026

$ dmidecode -t baseboard | grep -E 'Manufacturer|Product Name'
	Manufacturer: Intel Corporation
	Product Name: 440BX Desktop Reference Platform

$ lspci | grep -E 'Ethernet|SCSI'
00:10.0 SCSI storage controller: Broadcom / LSI 53c1030 PCI-X Fusion-MPT Dual Ultra320 SCSI (rev 01)
02:01.0 Ethernet controller: Intel Corporation 82545EM Gigabit Ethernet Controller (Copper) (rev 01)

$ ethtool -i ens33

version: 6.8.0-139-generic

$ smartctl -i /dev/sda
```

**三条读法**：① `440BX Desktop Reference Platform` 是 1998 年的 Intel 芯片组代号，**这是虚拟化平台编出来的型号**，不能当成真实主板进台账；② 实验机的 `smartctl` **退出码是 0**（命令成功执行），但结论是「不支持」——**退出码 0 不等于数据有效**；③ `lsblk -d -o ROTA` 把这块虚拟盘报成 `ROTA=1`，而 `smartctl` 说是 SSD —— **同一个事实两个工具给出相反答案时，要在台账里写明「以哪个为准、为什么」**。

### 4.3 固件升级也是一次变更

固件升级通常**要求重启**，属于重大变更：需要窗口、需要带外管理、需要回滚方案（很多固件可以回退版本）、需要升级后验证（`dmesg`、阵列卡状态、业务指标）。**而且必须先确认「有没有必要升」**——不是所有固件都需要保持最新，升级本身也带来风险。

> [!example]- 实验 10：实测 `sysctl --system` 的加载顺序（生产机也可以做，只读）
> **怎么做**：① `sysctl --system 2>&1 | head -20` 看应用顺序；② `ls -1 /etc/sysctl.d/ /usr/lib/sysctl.d/` 对照文件名排序（注意 `README.sysctl` 之类不以 `.conf` 结尾的文件不参与）；③ `grep -rn '<某个键>' /etc/sysctl.d /usr/lib/sysctl.d /etc/sysctl.conf` 找出某个键的所有写入点；④ 找一个被多处设置的键，推演「最终值应该是哪一个」，再用 `sysctl -n` 验证你的推演；⑤ 有条件时用 `realtyz` 再跑一遍 `sysctl --system`，观察 `permission denied` 提示与退出码。
> **预期（实验机实测）**：顺序为 `/usr/lib/sysctl.d/10-apparmor.conf` → `/etc/sysctl.d/10-*.conf`（**9** 个）→ `/usr/lib/sysctl.d/50-pid-max.conf` → `/usr/lib/sysctl.d/99-protect-links.conf` → `/etc/sysctl.d/99-sysctl.conf` → `/etc/sysctl.conf`，共 **14 个文件、17 个键**；**root 下 0 条 `permission denied`、退出码 0；`realtyz` 下 17 条同提示、退出码仍为 0**。
> **第 ④ 步在本机的实测结论值得注意**：`net.core.somaxconn` **没有任何文件写它**（`sysctl -n` 得 4096，是内核默认值），`kernel.pid_max` 也**只在 `/usr/lib/sysctl.d/50-pid-max.conf` 里出现过一次**（得 4194304）。也就是说**「某个键被多处设置」这件事必须先 `grep` 验证、不能假设**——这台机器上就没有现成的冲突可推演。
> **风险**：无（全程只读；第 ⑤ 步用 `realtyz` 跑同样只是只读尝试）。
> **耗时**：约 20 分钟。
> **怎么退回去**：不需要回滚。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 改了 `/etc/sysctl.d/` 里的文件就认为生效了 | 不执行 `sysctl --system`（或重启）不会生效；`/etc/sysctl.conf` 还会覆盖它 |
| 用 `cat` 配置文件当验收 | 验收口径必须是运行时值 `sysctl -n` |
| 直接改 `/etc/sysctl.conf` | 它是最后加载的、能覆盖一切；多人协作时很难追踪，建议用独立文件 |
| 抄一份「最佳实践参数表」批量下发 | 参数是给具体瓶颈用的；没有量化的调优会引入新问题 |
| 只改 `fs.file-max` | 服务受进程级 `LimitNOFILE` 限制；只调全局上限通常无效 |
| 盲目开启 `tcp_tw_reuse` | NAT 场景下有语义边界；要先确认根因是不是端口耗尽 |
| 改完不看业务指标 | 参数生效 ≠ 问题解决；要用同一判据（例如 Overflows 不再增长）复验 |
| 认为虚拟机上的硬件信息都是真的 | 虚拟化平台会编造 DMI：实验机报出 `440BX Desktop Reference Platform`（1998 年的芯片组）与 `VMware Virtual Platform`；`lsblk` 谎报 `ROTA=1`，而 `smartctl` 说 `SMART support is: Unavailable`；要先判断字段真假 |
| 看到 `permission denied on key ...` 就以为命令失败了 | 被拒的键会被跳过、其余继续应用，**退出码仍是 0**（实验机以 `realtyz` 跑出 17 条提示、退出码 0）；判据要回读 `sysctl -n` |
| 固件版本不记台账 | 「随机重启」「静默降级」这类问题会变成无法复盘的悬案 |
| 把固件升级当成小变更 | 通常需要重启与窗口；属于重大变更，要有回滚方案 |

## 决策练习

> [!question]- 场景：压测中出现偶发连接失败，监控显示 `TcpExtListenOverflows` 持续增长。同事建议「把 `net.core.somaxconn` 从 128 调到 4096，再顺手把 `tcp_tw_reuse` 打开」。
> A. 两项一起改，效果更明显
> B. 先只改 `somaxconn` 并记录现值；改后用同一压测复验 `ListenOverflows` 是否停止增长，同时查应用侧 `accept()` 速率（`strace -c -f` 或应用指标）判断瓶颈是否真的在队列长度；`tcp_tw_reuse` 在本场景没有依据，先不动
> C. 不改参数，直接扩容——加机器总能解决
>
> **答案：B。**
> A 犯了「一次改两个变量」的错：出问题时无法归因；而且 `tcp_tw_reuse` 与 `ListenOverflows` 没有因果关系（一个是 TIME_WAIT 复用，一个是接受队列溢出），属于典型的「顺手多开一个开关」。
> C 跳过了根因：`ListenOverflows` 说明连接到达速度超过应用 `accept()` 的速度，扩容可能掩盖问题，但如果瓶颈是单个进程的 `accept` 循环，扩容后每个实例仍然会溢出。
> B 是正解：**一次一个变量 + 用同一个判据复验 + 继续追根因**。如果调大队列之后 Overflows 停止增长但应用延迟上升，那说明「问题被推到队列里了」，仍要回到应用侧。

## 要点自测

> [!question]- `sysctl` 的加载顺序是什么？为什么会有「改了不生效」？
> - 三个目录（`/etc/sysctl.d`、`/run/sysctl.d`、`/usr/lib/sysctl.d`）合并后按文件名排序，同名文件 `/etc` 优先；最后应用 `/etc/sysctl.conf`。
> - 后加载的覆盖先加载的，所以同一个键的最终值取决于谁最后写。
> - **第一反应不要是什么**：不要以为「文件改对了」就等于「值生效了」。

> [!question]- 参数改了不生效，排查顺序是什么？
> - 看运行时值 → `grep -rn` 找所有写入点 → 看 `sysctl --system` 应用时有没有被拒 → 确认是不是运行时只读键 → 确认应用是否需要重启或只对新连接生效。
> - **第一反应不要是什么**：不要在没确认「现值是多少」之前重复改文件。

> [!question]- 为什么「抄最佳实践参数表」是危险的？
> - 参数是给具体瓶颈用的；不同负载、不同内核、不同发行版的默认值与边界都不同。
> - 每个参数改动都要有「为什么、验收判据、回滚方式」。
> - **第一反应不要是什么**：不要把调优当成「顺手多开几个开关」。

> [!question]- 哪几类硬件/固件信息必须进台账？为什么？
> - BIOS/UEFI 版本、RAID 卡与 BBU 状态、网卡固件版本、磁盘型号与健康摘要。
> - 因为它们对应「随机重启」「静默性能退化」「丢包」这类**平时无感、出事难查**的问题。
> - **第一反应不要是什么**：不要把虚拟机里采到的硬件字段当真——实验机采到的整机型号是 `VMware Virtual Platform`、主板是 `440BX Desktop Reference Platform`，都是虚拟化平台编出来的。

> [!question]- 参数台账最少要记哪六个字段？
> - 键、当前值、落点、为什么、验收方式、回滚方式。
> - 缺「落点」就无法追踪谁写的；缺「回滚」就不敢改回去。
> - **第一反应不要是什么**：不要只记「改成了多少」。
