# 巡检取证与处置顺序

巡检与处置的现场只有三个动作：**先取证、再判断、最后动手**。取证靠只读命令，判断靠字段读法，动手靠顺序与边界——顺序错了，现场就没了，剩下的只能靠猜。

## 1. 一个问题，一把工具

现场最常见的低级错误不是"用错命令"，而是**把东西的类别搞混**：把 `net.core.somaxconn` 当文件去 `cat`，把 `/proc/sys/net/core/somaxconn` 当命令去 `man`，把 `RLIMIT_NOFILE` 当内核参数去 `sysctl -w`。判据只有一条：**看 man 节号**。

| 类别 | 例子 | 查文档的方式 | 判据 |
| --- | --- | --- | --- |
| 命令 | `ss`、`systemctl`、`lsof`、`journalctl`、`df` | `man 8 ss`、`man 1 systemctl`、`man 1 journalctl` | man 节号 1（用户命令）或 8（管理命令） |
| 内核接口文件 | `/proc/sys/net/core/somaxconn`、`/proc/meminfo`、`/sys/fs/cgroup/<路径>/memory.max` | `man 5 proc`、`man 5 proc_sys_net`、`man 5 cgroups` | man 节号 5（文件格式）；直接读写，没有命令包装 |
| 内核参数 | `net.core.somaxconn`、`vm.swappiness`、`kernel.pid_max` | `man 5 sysctl.d`、`man 8 sysctl`、`man 8 systemd-sysctl` | 由 `sysctl` 读写，落点是 `*.conf` 文件 |
| 进程资源限制 | `RLIMIT_NOFILE`（打开文件数上限） | `man 2 setrlimit`、`man 5 limits.conf`、`man 1 prlimit` | man 节号 2/5；由 `ulimit`/`prlimit` 操作 |

这四类会互相影响（例如 unit 的 `LimitNOFILE=` 最终会写进进程的 `RLIMIT_NOFILE`），但它们的**改法、生效时机、验证方式**是三套不同的东西。分不清类别，就会得出"改了不生效"这类无法验证的结论。

### 1.1 变更前：对象与影响面

| 想知道什么 | 用什么 | 关键字段 |
| --- | --- | --- |
| 谁在听、听在哪个地址 | `ss -lnt` | `Local Address:Port`、`Recv-Q`、`Send-Q` |
| 现在有谁连着我 | `ss -tnp` | `Peer Address:Port`、`users:(("<进程>",pid=<PID>,fd=<n>))` |
| 已建立的连接有多少条 | `ss -tn state established`（要计数就接 `wc -l`，表格里写成 `\| wc -l`） | 行数 |
| 哪些服务正在跑 | `systemctl list-units --state=running` | `UNIT`、`LOAD`、`ACTIVE`、`SUB` |
| 改了它会连带谁 | `systemctl list-dependencies <unit>`、加 `--reverse` | 正向/反向依赖树的行数与层级 |
| 有哪些定时任务会撞车 | `systemctl list-timers --all` | `NEXT`、`LEFT`、`LAST`、`ACTIVATES` |
| 这台机器有几个地址、对外是哪个 | `ip -brief addr` | `IFNAME`、`OPERSTATE`、`ADDR` |
| 这台机器到底是谁 | `hostnamectl` | `Static hostname`、`Machine ID`、`Operating System`、`Kernel` |
| 谁打开了网络句柄 | `lsof -i -P -n` | `COMMAND`、`PID`、`USER`、`NAME`（不解析端口名与服务名） |

```bash
ss -lnt                                   # 验证：监听套接字清单（谁在听、听在哪、队列多长）
ss -tnp                                   # 验证：已建立连接的进程归属
systemctl list-units --state=running      # 验证：本机正在跑的服务数量与名单
lsof -i -P -n                             # 验证：从"进程持有哪个网络句柄"的方向交叉核对
```

实测输出（环境：**Ubuntu 24.04.5 LTS（VMware 虚拟机）/ 内核 `6.8.0-139-generic` / systemd 255（`255.4-1ubuntu8.17`）/ 4 vCPU / `MemTotal` 7894 MiB / 根分区 ext4 on LVM**；采集时刻 **2026-09-19T08:05 UTC**；**数值仅示意、不代表你的机器**）：

```text
$ ss -lnt
State   Recv-Q  Send-Q  Local Address:Port   Peer Address:Port
LISTEN  0       4096    127.0.0.54:53        0.0.0.0:*
LISTEN  0       128     0.0.0.0:22           0.0.0.0:*
LISTEN  0       4096    127.0.0.53%lo:53     0.0.0.0:*
LISTEN  0       128     [::]:22              [::]:*

$ ss -tn state established          → 4 条，对端全部是 192.168.246.1
$ systemctl list-units --state=running   → 24 个 unit
$ ip -brief addr
lo      UNKNOWN  127.0.0.1/8 ::1/128
ens33   UP       192.168.246.128/24
```

同一台机器在 **08:09 UTC 复采变成 6 条 LISTEN、9 条 established、25 个 running unit**：多出来的 `127.0.0.1:20700`、`127.0.0.1:20701` 是同期另一个实验留下的临时监听。**所以这组数字必须带采集时刻才有意义**——同一台机器四分钟之差就能多出两条监听。

`lsof -i -P -n` 的交叉核对价值在于它给的是"进程持有句柄"这个方向：实测 `*:22` 同时挂在 `systemd`（PID 1，socket 激活持有）与 `sshd`（PID 1348）上；`systemd-resolved`（PID 691）另有一条去 `192.168.246.2:53` 的上游 UDP。**归属要看 `COMMAND` 与 `PID` 两列一起**：只看到 `systemd` 就断言"服务没起来"是错的，它可能只是在 socket 激活模式下持有监听。

变更前把这一组取一遍，拿到的是**对象清单**：谁在听、谁在连、谁在跑、改了会连带谁、下一个定时任务几点触发。它的用法不是"看一眼"，而是当作回退时的对照——变更后同一组命令的差异，就是影响面本身。`systemctl list-timers --all` 的 `NEXT`/`LEFT` 尤其要在动手前看一眼：实测 `sysstat-collect.timer` 是 `NEXT 08:10:00` / `LEFT 2min 25s`，意味着两分半后会有一次采集启动，重启类操作最好避开它，否则你会在"数字为什么变了"上多花半小时。

这一组全部是只读，**生产机上也可以做**。`ss -tnp` 与 `lsof -i -P -n` 在非 root 下只能看到自己拥有的进程（实测：同一条命令 root 能看到 `systemd`/`sshd`/`systemd-resolved`，`realtyz` 只看到自己的进程），所以"我看不到"不等于"没有"。`systemctl` 的视图是本机、本启动周期的，看不到对端与上游。这一组里没有破坏性动作；**不要在这一步就 `systemctl restart`**——那是破坏性操作，只在可快照的实验机上或已批准的回退方案里做。

### 1.2 资产与固件

| 想知道什么 | 用什么 | 关键字段 |
| --- | --- | --- |
| 有几颗核、怎么分组 | `lscpu` | `CPU(s)`、`Socket(s)`、`Core(s) per socket`、`Thread(s) per core`、`L3 cache`、`NUMA node(s)` |
| 内存与 swap 有多少 | `free`、`/proc/meminfo` | `MemTotal`、`MemAvailable`、`SwapTotal` |
| 盘、分区、LVM 的层级 | `lsblk` | `NAME`、`SIZE`、`TYPE`（`disk`/`part`/`lvm`）、`ROTA`、`MOUNTPOINTS` |
| 文件系统类型与 UUID | `blkid` | `TYPE`、`UUID` |
| 谁挂在哪、用了什么选项 | `findmnt` | `TARGET`、`SOURCE`、`FSTYPE`、`OPTIONS` |
| 厂商、型号、BIOS、主板 | `dmidecode -t system \| -t bios \| -t baseboard` | `Manufacturer`、`Product Name`、`Version`、`Release Date` |
| 有哪些控制器与网卡 | `lspci` | 设备描述与 `bus-info` 风格地址 |
| 网卡驱动与固件版本 | `ethtool -i <if>` | `driver`、`firmware-version`、`bus-info` |
| 盘的健康与型号 | `smartctl -i <dev>` | `Device Model`、`User Capacity`、`SMART support is:` |
| 是物理机还是虚拟机 | `systemd-detect-virt` | 输出值（`vmware`、`kvm`、`none`…） |
| 发行版与内核 | `/etc/os-release`、`uname -r` | `PRETTY_NAME`、`VERSION_ID`；内核版本 |
| systemd 版本 | `systemctl --version` | 首行的版本号与发行版后缀 |
| 机器身份（台账主键） | `hostnamectl`、`/etc/machine-id` | `Machine ID` |

```bash
lscpu; free -m; lsblk; blkid; findmnt -o TARGET,SOURCE,FSTYPE,OPTIONS
                                          # 验证：CPU/内存/设备/文件系统四层资产
dmidecode -t system | head -20            # 验证：是谁家的机器（需要 root）
ethtool -i ens33; smartctl -i /dev/sda    # 验证：驱动/固件与盘的健康标识
systemd-detect-virt; uname -r; systemctl --version | head -1
                                          # 验证：虚拟化平台、内核、systemd 三件版本事实
```

实测（同一台实验机，**数值仅示意、不代表你的机器**）：`lscpu` 报 4 vCPU（2 socket × 2 core × 1 thread）、L3 60 MiB、NUMA 1 节点；`/proc/meminfo` 的 `MemTotal: 8083496 kB`（≈ 7894 MiB）；`lsblk` 报 `sda` 80G 且 `ROTA=1`、`sda2` 2G ext4 挂 `/boot`、`sda3` 48G `LVM2_member` → `ubuntu--vg-ubuntu--lv` ext4 挂 `/`；`dmidecode -t system` = `VMware, Inc.` / `VMware Virtual Platform`，`-t bios` = `Phoenix Technologies LTD` / `6.00` / `02/17/2026`，`-t baseboard` = `Intel Corporation` / `440BX Desktop Reference Platform`；`lspci` 里有 `Intel 82545EM`（网卡）与 `Broadcom / LSI 53c1030`（存储控制器）；`ethtool -i ens33` = `driver: e1000`、`firmware-version` 为空、`bus-info: 0000:02:01.0`；`smartctl -i /dev/sda` 认出 `VMware Virtual S` / 85,899,345,920 bytes，但同时写 `SMART support is: Unavailable - device lacks SMART capability` 而**退出码仍是 0**；`systemd-detect-virt` = `vmware`；`hostnamectl` 主机名 `linux-lab`、`Machine ID` `bd821ce75df94970ad5b6d63b6a8f812`。

这台机器上还有三处**资产自相矛盾**，正好说明为什么资产项要交叉核对：`lshw` 把 `sda3` 报成 47GiB 的 EFI 分区（`blkid` 明确是 `LVM2_member`）、`lshw` 报 8GiB 内存（`/proc/meminfo` 是 7894 MiB）、`lsblk` 的 `ROTA=1` 与 `smartctl` 的 `Rotation Rate: Solid State Device` 相反。**判据是"以哪个来源为准"**：分区与文件系统以 `blkid`/`findmnt` 为准（内核实际认出来的），内存以 `/proc/meminfo` 为准，`ROTA` 只当线索——虚拟机里这些值由 hypervisor 给出，本来就不保证自洽。

版本类事实要**现场取，不凭记忆**：`/etc/os-release` 给发行版与版本（实测 `PRETTY_NAME` 是 Ubuntu 24.04.5 LTS），`uname -r` 给运行中的内核（`6.8.0-139-generic`），`systemctl --version` 给 systemd 版本（`255.4-1ubuntu8.17`）。这三条是后面所有默认值的**前提**——同一份内核默认值、同一个 `systemd-tmpfiles` 选项、同一条 `logrotate` 行为，在不同主版本上都可能变；把这三条写在巡检记录的最前面，等于给整份记录标了适用范围。同机复采时如果 `uname -r` 与 `/boot` 下最新的 `vmlinuz` 不一致，说明这台机器重启过并换了内核，之前的基线要按新内核重取，不能直接对比。

这一组也是只读，**生产机上也可以做**：`dmidecode` 需要 root（读 SMBIOS 表）、`smartctl -i` 只读标识、`lspci -vvv` 只读配置空间。真正破坏性的是同一批工具的写模式：`smartctl -t`（启动自检会占 IO）、`smartctl -X`（中止自检）、`ethtool -s`（改链路参数）、`ethtool -E`（写 EEPROM）、`mkfs`、`fsck -y`、`xfs_repair -L`（后两条会改文件系统内容且不可逆）——这些**只在可快照的实验机上**做，不能拿"识别一下盘"当借口运行。

### 1.3 参数与基线

| 想知道什么 | 用什么 | 关键字段 |
| --- | --- | --- |
| 某个键现在的运行时值 | `sysctl -n <key>` | 数值本身（不带键名） |
| 开机时按什么顺序应用了哪些文件 | `sysctl --system` | 每行 `* Applying <文件>` 与 `键 = 值` |
| 只应用一个文件 | `sysctl -p <单文件>` | 该文件里的键 |
| 开机时谁按什么顺序写了这些键 | `systemd-sysctl` 的读取集与文件名顺序；实测顺序可用 `strace -f -e trace=openat -o /tmp/x /usr/lib/systemd/systemd-sysctl` 看 | 打开过的 `.conf` 路径序列（**不含 `/etc/sysctl.conf`**） |
| 这个键被哪些文件写过 | `grep -rn <key> /etc/sysctl.d /run/sysctl.d /usr/local/lib/sysctl.d /usr/lib/sysctl.d /etc/sysctl.conf` | 命中文件与行 |
| 某条软链把谁接进了读取集 | `readlink -f /etc/sysctl.d/99-sysctl.conf` | 指向的真实文件（本机实测为 `/etc/sysctl.conf`） |
| 当前 shell 的句柄上限 | `ulimit -n`（软限）、`ulimit -Hn`（硬限） | 两个数字，软限不能超过硬限 |
| 内存账目 | `cat /proc/meminfo` | `MemTotal`、`MemAvailable`、`SwapTotal` |
| 容量与 inode | `df -hT`、`df -i` | `Size`/`Used`/`Use%`；`IUsed`/`IFree`/`IUse%` |

```bash
sysctl -n vm.swappiness                    # 验证：运行时实际值（不是文件里写了什么）
sysctl --system 2>&1 | grep -E 'Applying|permission denied'
                                          # 验证：加载顺序与权限失败（注意退出码可能仍是 0）
grep -rn 'vm.swappiness' /etc/sysctl.d /run/sysctl.d /usr/lib/sysctl.d 2>/dev/null
                                          # 验证：这个键一共有几个写入点
df -hT /; df -i /                          # 验证：容量与 inode 两个口径
```

实测（同机，root；**数值仅示意、不代表你的机器**）：`sysctl --system` 读入的顺序是 `/usr/lib/sysctl.d/10-apparmor.conf` → `/etc/sysctl.d/10-*.conf`（9 个）→ `/usr/lib/sysctl.d/50-pid-max.conf` → `/usr/lib/sysctl.d/99-protect-links.conf` → `/etc/sysctl.d/99-sysctl.conf` → `/etc/sysctl.conf`（末尾两条是**同一次读取**：先打开软链路径、再落到它指向的文件），共 **14 个文件、17 个键**；`/run/sysctl.d/` 与 `/usr/local/lib/sysctl.d/` 在这台机器上**目录都不存在**（不是"没有配置"，是目录都没有），而 `systemd-sysctl` 的 `strace` 读取集里**没有 `/etc/sysctl.conf` 这一条**——它只读到软链 `99-sysctl.conf`。root 跑出 **0 条** `permission denied`、退出码 0；同一台机器换 `realtyz`（uid=1000）跑同一条命令出现 **17 条** `sysctl: permission denied on key "…", ignoring`，而**退出码仍然是 0**。`sysctl -a` 的行数：root 1018 行、`realtyz` 1004 行。几个具体值：`net.core.somaxconn` 没有任何文件写过它，`sysctl -n` 得 **4096**，与这台机器上 `/usr/include/x86_64-linux-gnu/bits/socket.h` 里 `#define SOMAXCONN 4096` 一致——**"没有写入点"是结论，"4096 是不是你机器的默认值"要现场读**（同为内核默认语义的这个参数，在更早的内核里是 128，所以它随版本变，不能凭印象抄）；`kernel.pid_max` 只在 `/usr/lib/sysctl.d/50-pid-max.conf` 出现一次，值 4194304；`vm.swappiness` = 60；`net.ipv4.ip_local_port_range` = `32768 60999`；`fs.file-max` = 9223372036854775807。**覆盖对抗实验**（在同一台机器上做过并已回滚）：往 `/etc/sysctl.d/99-zz-lab-test.conf` 写 `1111`、往 `/etc/sysctl.conf` 写 `2222`，`sysctl --system` 之后读到的是 **2222**；回滚复核为「值回到 4096、两个测试文件不存在、`/etc/sysctl.conf` 无残留行」。

`sysctl -n`、`sysctl -a`、`cat /proc/meminfo`、`df`、`ulimit -n`（不加参数）都是只读，**生产机上也可以做**。`sysctl -w`、`sysctl -p`、`sysctl --system` 会改运行时或重放全部配置；实测改一次 `vm.swappiness` 60→10→60 的 apply 是 **3 ms**、rollback 是 **4 ms**——**毫秒级的执行时间不代表毫秒级的风险**，参数的影响在业务侧，不在命令耗时上。这类写操作属于**只在可快照的实验机上**做，线上要走变更流程并预置回滚。`ulimit -n <值>` 改的是当前 shell 及其子进程的软限，不是系统级配置，退出 shell 就没了。

### 1.4 容量与日志

| 想知道什么 | 用什么 | 关键字段 |
| --- | --- | --- |
| 文件系统容量 | `df -hT` | `Size`、`Used`、`Avail`、`Use%`、`Type` |
| inode 用量 | `df -i` | `IUsed`、`IFree`、`IUse%` |
| 哪个目录占得多 | `du -xsh <目录>`、`du -sh <目录>/* \| sort -rh \| head` | 排行与差值（`-x` 不跨文件系统） |
| 已删除但仍被进程持有的文件 | `lsof +L1` | `COMMAND`、`PID`、`FD`、`SIZE/OFF`、`NLINK`、`NAME (deleted)` |
| journal 占多少 | `journalctl --disk-usage` | 一行摘要里的 MiB 数 |
| 有哪些启动周期可查 | `journalctl --list-boots` | 序号、启动时间、`-b` 可用的编号 |
| 轮转规则会做什么 | `logrotate -d <配置文件>` | `log needs rotating`、`renaming …` |
| 临时文件清理策略 | `systemd-tmpfiles --cat-config` | 每条规则的目录、清理条件 |
| ext4 的保留块与元数据 | `tune2fs -l <dev>` | `Reserved block count`、`Block count`、`Filesystem features` |

```bash
df -hT; df -i                             # 验证：容量与 inode 必须一起看
du -xsh /var/log; du -sh /var/log/* | sort -rh | head
                                          # 验证：总量与构成（-x 避免跨文件系统）
lsof +L1 2>/dev/null | head               # 验证：有没有"删了不释放"的句柄
journalctl --disk-usage; journalctl --list-boots | tail -5
                                          # 验证：journal 总量与可回溯的启动周期
logrotate -d /etc/logrotate.d/<app>       # 验证：干跑，只打印判断与计划动作
tune2fs -l /dev/mapper/ubuntu--vg-ubuntu--lv | grep -i reserved
                                          # 验证：ext4 保留块（"有空间却写不进去"的一个原因）
```

容量实测（同机，2026-09-19；**数值仅示意、不代表你的机器**）：根分区 `/dev/mapper/ubuntu--vg-ubuntu--lv` 46.9 G、用 20%、inode 3145728 用 6%；`journalctl --disk-usage` = **20.7 MiB**（同日更早的基线是 **53.9 MiB**，差值是同期实验的写入与回收造成的）；`du -sh /var/log` = 27M，其中 journal 21M、syslog 1.3M、installer 1.2M、dpkg.log 820K、kern.log 748K。

"删了不释放"这一类在 **128 MiB 的 loop 靶盘**上复现过（破坏性动作**只在可快照的实验机上**做，用临时 loop 设备当靶子，不碰根分区）：删掉一个被进程持有的 40 MiB 文件后，`df` 显示已用 **41 MiB** 而 `du` 只有 **20 KiB**；`lsof +L1` 抓到 `sleep 17678 … 8u … 41943040 … (deleted)`；从 `/proc/<pid>/fd/8` 拷出 **41943040 字节**（可 `sha256sum` 校验）；杀掉进程后已用从 **102M 回落到 62M**。inode 耗尽同样只用 loop 靶盘复现：`mkfs.ext4 -N 32` 的盘空盘时 `df -i` 是 **11/32 = 35%**，`touch` 40 个文件后变成 **32/32 = 100%**，而 `df -h` 只有 **1%**，此时 `touch` 报 `No space left on device`（2026-09-19T08:35 UTC）。

读日志先固定三件事：**范围**（`-u <unit>` 限定单元，`--since`/`--until` 限定窗口）、**启动周期**（配 `--list-boots` 选第几次启动，跨重启的现场只能这样拿）、**口径**（`-o short-iso` 带时区偏移、`-p err` 只看级别、`--no-pager` 保证在脚本里不卡在分页器上）。实测这台机器上，同一个十分钟窗口里限定 `-u ssh` 的错误计数是 0，不限定则是 93——**"有多少条错误"这个问题，不给范围就没有答案**。

`journalctl --disk-usage`、`--list-boots`、`logrotate -d`、`systemd-tmpfiles --cat-config`、`tune2fs -l`、`du`、`lsof +L1` 都是只读，**生产机上也可以做**。**只在可快照的实验机上**做的是：`journalctl --vacuum-size=`/`--vacuum-time=`（真删日志）、`logrotate -f`（强制轮转）、`systemd-tmpfiles --clean`（真删文件）、`rm`（对"被持有的空间"无效，还会丢掉现场）、`tune2fs` 的写模式（`-O`/`-e` 改文件系统元数据）、`lvconvert --merge`（快照回滚会不可逆地丢掉快照之后的写入）、`mkfs`、`fsck -y`/`xfs_repair -L`（后两条不可逆）。

### 1.5 到期与变更状态

| 想知道什么 | 用什么 | 关键字段 |
| --- | --- | --- |
| 某个域名证书什么时候到期 | `openssl s_client -servername <域名> -connect <主机>:443 </dev/null` 接 `openssl x509 -noout -dates` | `notBefore`、`notAfter`（GMT） |
| 服务端发了完整链没有 | 上面的命令加 `-showcerts` | 证书张数、每张的 `s:`/`i:` |
| 链能不能被本地 CA 库验通 | `openssl verify -CAfile <ca> [-untrusted <中间证书>] <叶证书>` | `OK` 或 `error 20 at 0 depth lookup: …` |
| 本机时间对不对、有没有同步 | `timedatectl` | `Time zone`、`System clock synchronized`、`NTP service` |
| 有哪些包可升级 | `apt list --upgradable` | 包名、目标版本、来源仓库 |
| 有哪些服务需要重启才吃到新库 | `needrestart -b` | 待重启的 unit 与原因 |
| 一个 unit 的真实状态 | `systemctl show <unit> -p ActiveState -p SubState -p NRestarts -p ExecMainStartTimestamp -p UnitFileState` | 五个属性各自的含义 |

```bash
openssl s_client -servername www.example.com -connect <主机>:443 </dev/null 2>/dev/null \
  | openssl x509 -noout -dates          # 验证：证书生效与到期时间（GMT）
openssl verify -CAfile /etc/ssl/certs/ca-certificates.crt cert-01.pem
                                          # 验证：只给叶证书时的验链结果
openssl verify -CAfile /etc/ssl/certs/ca-certificates.crt -untrusted interm.pem cert-01.pem
                                          # 验证：补上中间证书后是否变 OK
timedatectl                               # 验证：时区、时钟同步状态、NTP 服务是否在跑
systemctl show ssh -p ActiveState -p SubState -p MainPID -p NRestarts \
  -p ExecMainStartTimestamp -p UnitFileState
                                          # 验证：服务"现在是不是我改完之后的那一个进程"
```

实测（同机，2026-09-19T08:08 UTC，`www.example.com`；OpenSSL 3.0.13；**数值仅示意、不代表你的机器**）：`notAfter = Oct 27 22:17:21 2026 GMT`，距采集时点剩余 **38 天**；链内 **4 张**；`Verify return code: 0 (ok)`。离线复验 `openssl verify -CAfile /etc/ssl/certs/ca-certificates.crt cert-01.pem` 报 `error 20 at 0 depth lookup: unable to get local issuer certificate`，加上 `-untrusted interm.pem` 之后变成 `cert-01.pem: OK`——**同一张证书、同一个 CA 库，只差中间证书**。本机 CA 库在四个常见落点都是 **121 张**。`timedatectl` 显示 `Time zone: Etc/UTC (UTC, +0000)`、**`System clock synchronized: no`**、`NTP service: active`：**`is-active` 是 active 不等于时钟已同步**，这是两件事。

变更状态实测：`systemctl show ssh` 给出 `ActiveState=active`、`SubState=running`、`MainPID=1348`、`NRestarts=0`、`ExecMainStartTimestamp=Sat 2026-09-19 07:20:10 UTC`、`UnitFileState=disabled`、`FragmentPath=/usr/lib/systemd/system/ssh.service`（由 `ssh.socket` 拉起）；`systemctl list-dependencies ssh` 正向 **63 行**，`--reverse` 只有 `ssh.service` 一行；`systemctl list-timers` 首行 `sysstat-collect.timer` 是 `NEXT 08:10:00` / `LEFT 2min 25s` / `LAST 08:00:12`，`fwupd-refresh.timer` 的 `NEXT` 是 `09:25:48`。

`apt list --upgradable` 与 `needrestart -b` 要连起来读：前者回答"仓库里有哪些包可以升级"，后者回答"按当前已装的库，有哪些服务的**运行中进程还在用旧版本**"。两份清单数量不同很正常——一个是仓库状态，一个是本机进程状态；巡检记录里把这两份清单与到期日（证书 `notAfter`）放在同一张表里，才能回答"这次窗口要动哪些东西、动完之后要重启谁"。

这一组除"重启/升级"之外全是只读，**生产机上也可以做**：`openssl s_client`/`verify` 只做握手与本地校验，`apt list --upgradable` 只列可升级项，`needrestart -b` 只输出清单，`systemctl show` 只读属性。破坏性的是它们的下一步：`apt-get upgrade`、`systemctl restart <unit>`（断连接、丢内存态）、`systemctl daemon-reload`（重载 unit 定义，会影响后续启动行为）——这些**只在可快照的实验机上**或在已批准的变更窗口里做，并且要先确认这些动作的回退路径。

## 2. 怎么读这些数字

字段的完整定义与机制背景在主线篇《一次生产变更的一生》与横切篇《系统基线与参数治理》里；这里只列**最容易读错的固定动作**。

### 2.1 先固定三样：单位、窗口、来源

同一列在不同工具里含义不同，甚至同一个缩写含义不同：

| 陷阱 | 事实 |
| --- | --- |
| `nstat` 的输出当速率 | 默认是**窗口差值**，`-a` 才是累计值；而且这个"窗口"是**自上一次有人运行过 `nstat` 以来**（它记录在文件里，`man 8 nstat` 原文：默认是 calculate increments since the previous use），所以别人跑过一次就会把你的差值切小——要可复现就用 `-a` 取累计值再自己差分 |
| `sar -f` 的一条记录当瞬时值 | 它是**该采集间隔内的平均**；实验机的采集间隔是 10 分钟（`sysstat-collect.timer` 的 `NEXT 08:10:00` 与 `LAST 08:00:12` 相隔十分钟），拿它和 1 秒采样的 `iostat 1 5` 比，等于用两个窗口的平均值互相否定 |
| `sadf -d` 导出的时间戳按本地时区读 | 那是 **UTC**（行尾带 `UTC`），时区不是 UTC 的机器要换算 |
| `lsof` 的输出当全量进程清单 | 非 root 只能看到自己拥有的进程，与 root 跑出来的结果不是同一份数据 |
| `ss -lnt` 的 `Recv-Q` 与 `ss -tn` 的 `Recv-Q` 同义 | 监听套接字上它是"已完成握手、还没被应用 `accept()` 的**连接条数**"；已连接套接字上它是"内核缓冲区里还没被读走的**字节数**"。单位不同，不可比 |
| `systemctl` 的视图当集群视图 | 它只反映本机、本启动周期；上游、对端、另一台机器都不在里面 |
| `df` 的 `Size` 与 `du` 的总和应当相等 | 一个按文件系统算，一个按目录算；挂载覆盖、保留块、已删除句柄都会让两者不等 |
| `openssl s_client` 的 `Verify return code: 0 (ok)` 当"客户端一定能连" | 它只说明**本机 CA 库**验通了这条链；主机名匹配要另加校验，客户端的 CA 库与时钟都不在这台机器上 |
| `systemctl is-active` 的成功当"功能正常" | 它只回答"进程在不在"，不回答"能不能连、业务通不通"；实测 `NTP service: active` 而 `System clock synchronized: no` |

关键字段的读法（**是什么 / 单位 / 判据 / 与谁同看 / 转向哪一步**）：

| 字段 | 是什么 | 单位 | 判据 | 与谁同看 | 转向哪一步 |
| --- | --- | --- | --- | --- | --- |
| `ss -lnt` 的 `Recv-Q` | 监听套接字上待 `accept()` 的连接条数 | 条 | 持续等于 `Send-Q`（该套接字的队列上限）就是应用 accept 不及时 | `nstat` 的 `TcpExtListenOverflows`/`ListenDrops` | 转向应用侧 accept 循环或队列上限 |
| `df -i` 的 `IUse%` | inode 使用比例 | 百分比 | 接近 100% 时写入会报 `No space left on device`，与容量无关 | `df -h` 的 `Use%`、`du` 的小文件计数 | 转向小文件清理与保留期 |
| `lsof +L1` 的 `SIZE/OFF` | 已删除仍被持有的文件大小 | 字节 | 与 `df`−`du` 的缺口**同量级**才值得追 | `du -xsh`、`df -h` | 转向"抢救内容或让持有者重开文件" |
| `journalctl --disk-usage` | journal 占用 | MiB | 只看**增长速率与上限**，不看单次快照 | `/etc/systemd/journald.conf` 的 `SystemMaxUse` | 转向 journald 上限或文件式日志轮转 |
| `System clock synchronized` | 系统时钟是否已与时间源同步 | 是/否 | `no` 时所有"剩余天数/时间窗"的判断都不可靠 | `NTP service`、`timedatectl timesync-status` | 转向时钟同步排查 |
| `UnitFileState` | unit 的开机启用状态 | 枚举 | `disabled` 不代表它没在跑（可能被 socket/timer/依赖拉起） | `ExecMainStartTimestamp`、`FragmentPath` | 转向"实际生效的是哪条路径" |
| `ExecMainStartTimestamp` | 主进程启动时刻 | 时间戳 | 早于你的变更时刻 = 主进程没被换掉 | `MainPID`、`NRestarts` | 转向"重启是否真的生效" |
| `NRestarts` | 该 unit 被自动重启的次数 | 次 | 非 0 说明它反复挂掉；空值不等于 0 | `journalctl -u <unit>`、`SubState` | 转向崩溃原因 |

### 2.2 几个"看起来像结论"的数字

- **`df` 与 `du` 不一致**：这不是"`du` 不准"，而是四类成因——已删除但被进程持有（`lsof +L1`）、挂载覆盖（`findmnt`）、保留块与元数据（`tune2fs -l`）、配额（配额报表）。四类的处置完全不同，要逐一排除，而不是互相否定。实测：删掉被持有的 40 MiB 文件后 `df` 是 41 MiB、`du` 是 20 KiB，差值正好是那个文件。
- **`lsof +L1` 有输出**：不等于"磁盘被偷了"。`systemd-journald` 长期持有刚被轮转掉的 journal 文件是正常现象。判据是量级：`SIZE/OFF` 与你的容量缺口是不是同一量级。对不上就先别顺着这条线查。
- **`systemctl show <unit>` 的空输出**：空属性说明该属性此刻没有值（或对该单元类型不适用），不等于"没发生过"。例如 `NRestarts` 为空与 `NRestarts=0` 不是一回事；unit 名写错时 `systemctl show` 也可能照样打印一整套属性、`LoadState` 显示 `not-found`。判据是 `LoadState` 与 `ActiveState`，并用 `systemctl cat <unit>` 确认 unit 定义真的存在。
- **`openssl s_client` 的 `Verify return code: 0 (ok)`**：它只说明**本机 CA 库**验通了服务端发来的这条链，不说明主机名匹配、更不说明客户端能连。实测同一张证书只给叶证书时 `openssl verify` 报 `error 20 at 0 depth lookup: unable to get local issuer certificate`，补上 `-untrusted` 的中间证书才变成 `OK`——**"验不过"与"验得过"的差别可能只是一张中间证书**，而客户端的失败往往就出在服务端没把链发全。
- **命令退出码 0**：只代表命令本身没失败，不代表任务成功。实测三例：`realtyz` 跑 `sysctl --system` 有 **17 条** `permission denied`，退出码仍是 **0**；`smartctl -i` 在 `SMART support is: Unavailable` 时退出码也是 **0**；`df`、`ss` 退出码 0 只说明"我读到了本机视图"。

### 2.3 采样纪律与基线卡

- **同口径、带时间戳、至少两次**：判断抖动按秒、判断泄漏按小时或按天；实测同一台机器 08:05 与 08:09 两次采集，LISTEN 4→6、established 4→9、running 24→25，多出来的正是同期另一个实验的临时监听——**单次采样会被并行活动污染**，所以每次巡检都要带采集时刻，并优先排除"同期有别的实验/变更"。
- **留原始输出**：`script -f`、`tee` 或重定向到文件，而不是只抄一个数字。取证的价值在原始文本里（例如 `error 20 at 0 depth lookup` 这一句比"验不过"值钱得多）。
- **采集顺序固定为"先只读、后判断、再动手"**：任何写操作之前必须留下一份只读快照。实测"删了不释放"这一类，一旦重启，`lsof +L1` 的现场与失败计数就一起没了——事后无法复盘，只能重新等它发生。
- **一次采集、一个时刻、一份文件**：把同一时刻取到的五组输出（对象、资产、参数、容量、到期）落到同一个带时间戳的文件里，而不是散在好几个终端里。实测两次采集只差四分钟，`ss` 与 `systemctl` 的数字就都变了；把不同时刻的输出拼在一起看，等于制造了一份跨轮次的假对照。
- **日志基线必须先剔除他人噪声**：实测 `journalctl -u ssh --since "10 min ago" | grep -icE 'error|fail'` = **0**，而同一窗口不限定 `-u` 的同类计数 = **93**（93 条几乎全来自同机其它服务）。**同一个窗口、同一个模式，加不加 `-u` 是两个数量级的差别**；没有归属范围的"错误数"不是基线。
- **基线卡的五组数据**（对象清单、资产与固件、参数与文件、容量与日志、到期与变更状态）落在治理篇《系统基线与参数治理》与《容量、日志与目录治理》的产物模板里，本篇只负责"怎么取、怎么读"。

## 3. 常见故障与排查方向

### 场景一：根分区 100%，业务写入报 `No space left on device`，但 `du` 加起来只有几 MiB

**机器与服务**：4 vCPU（`MemTotal` 7894 MiB）/ Ubuntu 24.04.5 LTS（VMware 虚拟机）/ 内核 `6.8.0-139-generic` / 根分区 `/dev/mapper/ubuntu--vg-ubuntu--lv`（ext4 on LVM，46.9 G）；**单台虚拟机，没有第二台机器、没有负载均衡**；约束是**不能重启**（内存态业务在跑）。

**现象数值**：`df -hT /` 的 `Use%` = 100%；`du -xsh /` 加起来只有几 MiB；`df -i` 的 `IUse%` 只有 6%。

**排查顺序**：

1. 先只读取证四条，别动手：`df -hT`、`df -i`、`findmnt`、`lsof +L1`。四个口径一起看，才能把"容量、inode、挂载、句柄"四类分开；
2. 看 `lsof +L1` 的 `SIZE/OFF` 与缺口是否同量级。实测这一类会给出 `sleep … 8u … 41943040 … (deleted)` 这样的行；
3. 缺口对得上就先**抢救内容**：`ls -l /proc/<pid>/fd` 找到号，`cp /proc/<pid>/fd/<n> /var/tmp/rescued.bin`，再 `sha256sum` 与业务侧记录核对；
4. 再决定怎么释放：让进程重开文件（reload/重启该服务）或结束那个进程。**这一步有影响，要先确认它是不是业务进程**；
5. 看到什么转向哪：`lsof +L1` **无输出** → 转 `findmnt` 查挂载覆盖（挂载点遮住了下层目录，`du` 看不到被遮的内容）；再转 `tune2fs -l` 查 ext4 保留块；再转配额报表。`df -i` 到 100% → 转小文件与 inode 方向（与容量无关）；
6. 复现只在**可快照的实验机上**做：用 128 MiB 的 loop 靶盘（`truncate` + `losetup` + `mkfs.ext4`），跑完 `umount` + `losetup -d` 回到原状，并复核 `losetup -a` 为空。生产机上只做第 1 步的只读取证。

**一份合格的回答长什么样**：结论（**空间被"已删除但仍被进程持有的文件"占着**，不是日志、不是小文件）+ 依据（`df` 已用 41 MiB 对 `du` 20 KiB、`lsof +L1` 的 `SIZE/OFF` = 41943040 字节、抢救文件的 `sha256` 与业务侧一致）+ 边界（这条只解释"删了不释放"这一类；`lsof +L1` 无输出时方向要改到挂载覆盖或保留块；`kill` 之前要确认进程角色）+ 动作（先抢救内容，再让持有者释放句柄，验收用 `df` 已用回落且业务写入恢复）。

### 场景二：证书巡检发现"台账上没有的域名"，且部分客户端连不上

**机器与服务**：同一台机器（只有一个对外地址 `ens33 192.168.246.128/24`）；**单机、无负载均衡、无第二台机器**——同一 IP 的 443 上跑多个域名时只能靠 SNI 区分，台账漏一个域名就巡检不到一个；约束是不能中断服务。

**现象数值**：`openssl s_client -servername www.example.com -connect <主机>:443 </dev/null | openssl x509 -noout -dates` 得到 `notAfter = Oct 27 22:17:21 2026 GMT`，剩余 **38 天**；链内 **4 张**；`Verify return code: 0 (ok)`；但部分客户端报"证书不可信"。

**排查顺序**：

1. **先固定采集口径**：时刻（2026-09-19T08:08 UTC）、域名、SNI 参数、OpenSSL 版本（3.0.13）。不写这些，"还有 38 天"没法复算；
2. 数链：`-showcerts` 看服务端实际发了几张、每张的签发者；
3. 离线复验：`openssl verify -CAfile /etc/ssl/certs/ca-certificates.crt cert-01.pem` → 实测报 `error 20 at 0 depth lookup: unable to get local issuer certificate`（缺中间证书）；加 `-untrusted interm.pem` 后 `OK`。**报错文本本身就是结论**；
4. 看 CA 库：本机四个落点均 121 张。客户端报错时，第一件要问的是"它的 CA 库与本机是不是同源、有没有更新"；
5. 看时钟：`timedatectl` 实测 `Time zone: Etc/UTC`、**`System clock synchronized: no`**、`NTP service: active`。时钟未同步时，"剩余天数"的算术和证书有效期校验都不可靠；
6. 看到什么转向哪：`Verify return code` 非 0 → 链或 CA 库方向；为 0 而客户端报错 → 主机名校验、客户端 CA 库、时钟、SNI 未发送（老客户端）四个方向；台账缺域名 → 用 `-servername` 逐域名枚举，把清单补进台账。

**一份合格的回答长什么样**：结论（**服务端没发全链，客户端缺中间证书**，且本机时钟未同步）+ 依据（`error 20 at 0 depth lookup`、加 `-untrusted` 后 `OK`、`notAfter` 与剩余 38 天、`System clock synchronized: no`）+ 边界（`s_client` 的 `0 (ok)` 只针对本机 CA 库，不等于主机名匹配、更不代表客户端能通；客户端 CA 库与时钟不在这台机器上，只能给方法）+ 动作（补齐中间证书、同步时钟、把域名清单与到期日纳入台账并逐域名定期巡检；单机上没有第二份入口可交叉验证，这一点要如实写进结论）。

### 场景三：参数"改了不生效"

**机器与服务**：同一台机器；`sysctl --system` 实测 **14 个文件、17 个键**；`/run/sysctl.d/` 不存在；root 与 `realtyz` 两种身份；约束是改动要能回滚。

**现象数值**：把 `vm.swappiness = 10` 写进 `/etc/sysctl.d/99-app.conf` 后，`sysctl -n vm.swappiness` 仍读回 **60**（这台机器的 `/etc/sysctl.d/99-sysctl.conf` 指向 `/etc/sysctl.conf`，名字排在 `99-app.conf` 之后）；或换个身份执行 `sysctl --system` 时满屏 `permission denied`，脚本却"成功返回"。

**排查顺序**：

1. 先取**运行时实际值**：`sysctl -n <key>`。文件里写了什么不算数，运行时值才是判据；
2. 找**所有写入点**：`grep -rn <key> /etc/sysctl.d /run/sysctl.d /usr/local/lib/sysctl.d /usr/lib/sysctl.d /etc/sysctl.conf`。实测这台机器上 `net.core.somaxconn` **一个文件都没写**（运行时值 4096，与内核头文件里的 `SOMAXCONN` 一致，即内核默认），而 `kernel.pid_max` 只在 `/usr/lib/sysctl.d/50-pid-max.conf` 出现一次（值 4194304）——**"这个键归谁管"必须查出来，不能假定**；
3. **先分清是哪套机制在读**，再谈顺序。开机是 `systemd-sysctl.service`，它的读取集**只有 `.d` 目录**（`/etc/sysctl.d/`、`/run/sysctl.d/`、`/usr/local/lib/sysctl.d/`、`/usr/lib/sysctl.d/`），**不读 `/etc/sysctl.conf`**；手工重放是 procps 的 `sysctl --system`，它在那些 `.d` 之后**再读一次 `/etc/sysctl.conf`**。两套机制的合并规则相同：所有 `.conf` 按**文件名字典序**排序（不按目录），名字靠后的覆盖靠前的；**同名文件**以 `/etc` 优先于 `/run`、`/run` 优先于 `/usr`。所以"写进 `/etc/sysctl.d/99-app.conf`"能不能赢，取决于有没有别的文件排在它后面——本机实测 `strace` 到的读入顺序是 `/usr/lib/sysctl.d/10-apparmor.conf` → `/etc/sysctl.d/10-*.conf`（9 个）→ `/usr/lib/sysctl.d/50-pid-max.conf` → `/usr/lib/sysctl.d/99-protect-links.conf` → `/etc/sysctl.d/99-sysctl.conf`，**`99-sysctl.conf` 是 `../sysctl.conf` 的软链**（本机实测 `readlink -f` 得 `/etc/sysctl.conf`），它靠 "99-" 这个字典序排到最后而不靠路径特例；**如果那条软链不存在（新版 Debian 系已开始移除），`/etc/sysctl.conf` 在两套机制里都不会被读**，它就只是一个睡着的文件；
4. 分清 `sysctl -p <单文件>` 与 `sysctl --system`：前者只应用你指定的那一个文件，后者按顺序重放全部——**只跑 `-p` 就断言"开机后是什么值"，口径是错的**；
5. 看**身份**：实测 root 跑 `sysctl --system` 是 0 条 `permission denied`、退出码 0；同一台机器 `realtyz`（uid=1000）出现 17 条 `permission denied on key "…", ignoring`，**退出码仍然是 0**。所以"命令成功"证明不了"参数都应用了"，要用 `sysctl -n` 逐键验收；
6. 看到什么转向哪：运行时值等于写入值但仍"不生效" → 转向调用方（应用是否在启动时又改了一遍、`systemd` unit 的 `LimitNOFILE=` 之类是否覆盖了它）；运行时值不等于任何文件值 → 说明有人用 `sysctl -w` 改过运行时，重放配置就会丢。

**一份合格的回答长什么样**：结论（**这个键有多个写入点，排在最后的那个文件把你的值覆盖了**——本机是软链 `99-sysctl.conf` 指向的 `/etc/sysctl.conf`；或"执行身份权限不足，17 个键被忽略而退出码仍是 0"）+ 依据（`grep -rn` 的全部命中文件、文件名排序与软链指向、`sysctl -n` 的运行时值、`permission denied` 的行数与退出码）+ 边界（两套机制的读取集不同；`/etc/sysctl.conf` 是否被读取决于那条软链在不在；`sysctl -w` 只改运行时，重启即丢；`ulimit` 只影响当前 shell 树；这台机器的 `/run/sysctl.d/` 与 `/usr/local/lib/sysctl.d/` 不存在，引用时不能假定它们存在）+ 动作（把改动写到顺序上真正生效的那个文件、用 `sysctl --system` 重放、用 `sysctl -n` 逐键验收；回滚用同样的重放路径）。

### 场景四：批量脚本跑一半失败，机器上留下半成品

**机器与服务**：同一台机器上跑批处理脚本；约束是不能重启、要保留现场；**这台机器没有第二台可对照**，所以失败定位只能靠脚本自己的记录。

**现象数值**：`xargs -P 4` 的子任务失败时退出码是 **123**（只知道"有失败"，不知道哪一台）；`timeout 5 sleep 30` = **124**、`timeout 5 true` = **0**；`set -u` 引用未设置变量 = **127**；`${VAR:?}` = **127**；`T=""; [ $T = x ]` 退出码 **0**（`-u` 只拦"未设置"，不拦"空值"）；`flock -n` 第二次获取同一把锁 = **1**（非阻塞，不挂住）；幂等脚本连跑三次，第 2、3 次输出"已是目标状态，跳过写入（幂等）"、目标文件行数恒为 **1**，把中间一步换成不存在的命令则停在那一行且退出码 **127**。

**排查顺序**：

1. **先收现场，别先重跑**：`ps -eo pid,etime,args | grep <脚本名>` 找残留进程；`ls -l /var/lock/` 找锁；`ls -ld /tmp/tmp.*` 之类的临时目录；`ls -l <目标文件>*` 找带时间戳的备份与只改了一半的配置；
2. 用**退出码分类**再决定方向：123 = 批量里有失败（要去看脚本自己落的每台日志）、124 = 超时被杀（看是哪一步慢）、127 = 命令不存在或变量未设置被 `-u` 拦住、1 = 一般错误或锁被别人持有。**没有每台输出，123 就等于没有信息**；
3. 查锁：`flock -n` 返回 1 说明另一个实例还在跑。这时"再跑一次"只会制造第二份半成品；
4. 判断半成品到哪一步了：看幂等锚点（例如 `grep -qxF "$LINE" "$CONF"`）与目标文件行数。实测幂等写法下目标文件行数恒为 1，重复执行不会再追加；
5. 决定"补齐"还是"回退"：补齐要能重复执行（幂等），回退要用脚本自己留下的带时间戳备份（`cp -a <文件> <文件>.<日期>`），**不要用"再改一遍"当回滚**；
6. 复跑前先干跑与限量：`logrotate -d`、Ansible 的 `--check --diff`、`--limit`，以及把并发降到 1；跑完复核"无残留进程、无残留锁、无残留临时目录"。

**一份合格的回答长什么样**：结论（**失败点在写入之前/之后**，现场留下了哪几样东西，是真失败还是超时被杀）+ 依据（退出码 123/124/127 的具体来源、锁的持有者、幂等锚点与文件行数、每台输出日志的那一行）+ 边界（123 不指出是哪台，所以批量脚本必须自己记录每台输出；`-u` 不拦空值，`rm -rf "$T/"` 在被赋成空串时依然危险）+ 动作（先清理残留进程与锁、用带时间戳备份回退半成品、把幂等判断补齐后再限量复跑，验收用"连跑两次结果一致"）。

### 场景五：变更窗口内"改完了、服务 active，但业务报错持续"

**机器与服务**：同一台机器上一个 socket 激活的服务（实测 `ssh` 就是这种形态：`FragmentPath=/usr/lib/systemd/system/ssh.service`，由 `ssh.socket` 拉起）；**单机、没有负载均衡**，探活脚本打的是本机回环；约束是变更窗口只剩 10 分钟。

**现象数值**：`systemctl show ssh` = `ActiveState=active`、`SubState=running`、`MainPID=1348`、`NRestarts=0`、`ExecMainStartTimestamp=Sat 2026-09-19 07:20:10 UTC`、`UnitFileState=disabled`；`systemctl list-dependencies ssh` 正向 **63 行**、`--reverse` 只有 **1 行**；`ss -lnt` 里业务端口只出现在 `0.0.0.0` 与 `[::]` 上，本机回环上没有业务监听。

**排查顺序**：

1. **先确认"你改的是不是正在跑的那个东西"**：`systemctl show <unit> -p ActiveState -p SubState -p MainPID -p ExecMainStartTimestamp -p UnitFileState`。判据是 `ExecMainStartTimestamp` **晚于**你的变更时刻——如果它早于变更时刻，说明主进程根本没被换掉，你看到的 `active` 是"本来就在跑"。`UnitFileState=disabled` 还提示实际生效路径可能是 socket/timer/依赖拉起，不是"开机启用"；
2. 看**重启计数**：`NRestarts=0` 说明它没自动重启过；非 0 则说明它反复挂掉，方向转向崩溃原因（`journalctl -u <unit>`）；
3. 看**依赖面**：正向 `list-dependencies` 实测 63 行，说明"改它会连带多少东西"比想象大；`--reverse` 只有 1 行说明**依赖树看不到"谁在用它"**——业务侧影响要看连接，不看依赖树；
4. 看**真实监听**：`ss -lnt` 的 `Local Address:Port`。本机回环上探活成功，只证明回环路径通；`ip -brief addr` 实测对外只有 `ens33 192.168.246.128/24` 一个地址，**外部路径通不通必须从外部验**，本机自测不能替代；
5. 看**集群与上游**：这是最容易出错的一步。`systemctl show` 只反映本机；这台机器**没有第二台、没有负载均衡**，所以"上游是否还有失败单元""对端是否也改了"这类问题在本机**无法取证**，只能如实写成边界，或者去上游/集群侧取数；
6. 看到什么转向哪：`ExecMainStartTimestamp` 没变 → 重启动作本身没生效（改的是别的 unit、或 socket 激活下主进程由别的路径拉起）；时间戳已更新而业务仍报错 → 转向配置内容、依赖面与外部路径；有失败单元 → 按"哪些依赖未就绪"逐条查 `systemctl --failed`。

**一份合格的回答长什么样**：结论（**主进程没有被换掉**，或"服务确实换了，但探活打的是回环，外部路径未验证"）+ 依据（`ExecMainStartTimestamp` 与变更时刻的先后、`MainPID`、`NRestarts`、`ss -lnt` 的监听地址、`ip -brief addr` 的对外地址）+ 边界（本机看不到上游与集群侧状态；单机无第二入口可交叉验证；`ActiveState=active` 只说明进程在，不说明业务通）+ 动作（先确认实际生效的 unit 与启动路径，再从外部做一次探活，最后按依赖面逐条验收；回退用变更前的配置备份并同样验证"主进程真的换了"）。

## 常见坑

| 做法或说法 | 后果或事实 |
| --- | --- |
| 把内核参数当文件去 `cat` | 判据是 man 节号：命令 1/8、文件格式 5、系统调用 2；`net.core.somaxconn` 要 `sysctl -n`，`/proc/sys/net/core/somaxconn` 才能读 |
| 只采样一次就当基线 | 同一台机器 08:05 与 08:09 相差 4 分钟，LISTEN 4→6、established 4→9，多出来的正是同期别的实验 |
| 不写采集时刻就贴数字 | 没有时刻的 `df`/`ss`/`journalctl --disk-usage` 无法复算，也无法判断是否被并行活动污染 |
| 用 `df` 或 `du` 单方面下结论 | 两者不一致有四类明确成因，要逐一排除，而不是宣布"`du` 不准" |
| 看到 `lsof +L1` 有输出就认定磁盘被偷 | `systemd-journald` 持有轮转掉的 journal 是正常的；判据是 `SIZE/OFF` 与缺口是否同量级 |
| 把命令退出码 0 当成任务成功 | `sysctl --system` 在 uid=1000 下有 17 条 `permission denied` 仍退出 0；`smartctl -i` 在 `SMART support is: Unavailable` 时也退出 0 |
| 把 `System clock synchronized: no` 忽略掉 | 时钟没同步时，证书剩余天数、时间窗、日志时间戳都不可靠；`NTP service: active` 不等于已同步 |
| 以为 `sysctl -p <文件>` 等价于开机生效 | `-p` 只应用你给的那一个文件；开机是另一套读取集（`systemd-sysctl` 只读 `.d` 目录），两者的覆盖面不同 |
| 只在一处写参数，不查其它写入点 | 同一个键可能有多个写入点；`net.core.somaxconn` 这台机器上无人写（值是内核默认 4096），`kernel.pid_max` 只在 `50-pid-max.conf` 出现 |
| 用 `systemctl is-active` 或 `active/running` 宣布变更成功 | 它只说明进程在；要看 `ExecMainStartTimestamp` 是否晚于变更时刻、`MainPID` 是否换过 |
| 用本机回环探活代替外部验证 | 回环通只证明回环通；实测对外只有 `ens33`（`192.168.246.128/24`）一个地址，外部路径必须从外部验 |
| `lshw` 与 `lsblk`/`blkid` 矛盾就当异常 | 实测这台虚拟机上 `lshw` 把 `sda3` 报成 47GiB 的 EFI 分区、把内存报成 8GiB，而 `blkid` 明确是 `LVM2_member`、`/proc/meminfo` 是 7894 MiB。虚拟机里这类值由 hypervisor 给出，要以内核实际认出来的来源为准 |
| 用 `systemctl list-dependencies --reverse` 判断影响面 | 依赖树看不到"谁在用它"（实测反向只有 1 行）；业务影响要看连接与上游 |
| 先重启再取证 | 重启会清掉已删除句柄、内存态与失败计数，现场没了；取证是只读的，生产机上也可以做 |

**第一反应不要做什么**：不要先重启；不要在只读取证就能定性时先改参数或先清日志；不要把"命令退出码 0"当成功证据；不要用一台机器的视图回答集群侧的问题。

## 要点自测

**问：怎么区分命令、内核接口文件与内核参数？**
答：看 man 节号——节号 1/8 是命令（`man 8 ss`），节号 5 是文件格式（`man 5 proc`、`man 5 sysctl.d`），节号 2 是系统调用（`man 2 setrlimit`）。`net.core.somaxconn` 用 `sysctl -n` 读，`/proc/sys/net/core/somaxconn` 直接 `cat`，`RLIMIT_NOFILE` 用 `ulimit`/`prlimit`。

**问：`ss -lnt` 与 `ss -tn` 的 `Recv-Q` 有什么不同？**
答：监听套接字上它是"已完成握手、还没被应用 `accept()` 的连接**条数**"，持续等于队列上限（`Send-Q`）就是应用 accept 不及时；已连接套接字上它是"内核缓冲区里没被读走的**字节数**"。单位不同，不能互相比。

**问：`df` 与 `du` 对不上，怎么排？**
答：四类逐一排除——已删除但被进程持有（`lsof +L1`，看 `SIZE/OFF` 与缺口是否同量级）、挂载覆盖（`findmnt`）、ext4 保留块（`tune2fs -l`）、配额（配额报表）。实测删掉被持有的 40 MiB 文件后 `df` 41 MiB、`du` 20 KiB，差值正是那个文件。

**问：参数"改了不生效"，先查哪三样？**
答：运行时值（`sysctl -n`）、所有写入点（`grep -rn` 四个 `.d` 目录加 `/etc/sysctl.conf`）、以及**是哪套机制在读**——开机是 `systemd-sysctl`（只读 `.d` 目录），手工重放是 `sysctl --system`（末尾再读一次 `/etc/sysctl.conf`）。本机实测 `/etc/sysctl.conf` 之所以最后生效，是因为它被软链成 `/etc/sysctl.d/99-sysctl.conf`（`readlink -f` 指向 `/etc/sysctl.conf`）。再确认执行身份——uid=1000 会有 17 条 `permission denied` 而退出码仍是 0。

**问：证书巡检为什么必须记采集时刻、`-servername` 与 CA 库路径？**
答：剩余天数是拿 `notAfter` 与采集时刻相减算出来的，缺一个就算不出；多域名同 IP 只能靠 SNI 区分，不写 `-servername` 可能取到另一个域名的证书；`Verify return code: 0 (ok)` 只针对本机那一个 CA 库（实测四处均 121 张），客户端的 CA 库与时钟都不在这台机器上。

**问：批量脚本失败后，第一件事做什么？**
答：收现场——残留进程、锁（`flock -n` 返回 1 说明还有实例在跑）、临时目录、带时间戳的备份与只改一半的配置；再用退出码分类（123 有失败但不知哪台、124 超时、127 命令或变量问题、1 一般错误）。**没有每台输出，123 等于没有信息**，所以批量脚本必须自己落每台日志。

**问：服务 `active/running`，怎么判断变更真的生效了？**
答：看 `systemctl show` 的 `ExecMainStartTimestamp` 是否晚于变更时刻、`MainPID` 是否换过、`NRestarts` 是否为 0、实际生效路径是什么（`UnitFileState=disabled` 说明可能是 socket/timer 拉起的）；再从外部做探活，不要用本机回环代替。

**第一反应不要做什么**：不要在只读取证之前动手改配置、清日志或重启；不要把退出码 0、`active` 或 `is-active` 当成功证据；不要在时钟未同步时用"剩余天数"下结论；不要用单机视图回答集群侧的问题。
