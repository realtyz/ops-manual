# 巡检取证与处置顺序

巡检与处置的现场只有三个动作：**先取证、再判断、最后动手**。取证要靠只读命令完成，判断要靠字段读法完成，动手则要靠顺序与边界——因为一旦顺序错了，现场就没了，剩下的只能靠猜。

## 1. 一个问题，一把工具

现场最常见的低级错误不是"用错命令"，而是**把东西的类别搞混**：有人把 `net.core.somaxconn` 当文件去 `cat`，有人把 `/proc/sys/net/core/somaxconn` 当命令去 `man`，还有人把 `RLIMIT_NOFILE` 当内核参数去 `sysctl -w`。区分它们只有一条判据，那就是**看 man 的节号**。

| 类别 | 例子 | 查文档的方式 | 判据 |
| --- | --- | --- | --- |
| 命令 | 这一类是可执行的命令，常见的有 `ss`、`systemctl`、`lsof`、`journalctl` 与 `df` | 查它的用法要读 `man 8 ss`、`man 1 systemctl` 或 `man 1 journalctl` | 判据是 man 的节号为 1（用户命令）或 8（管理命令） |
| 内核接口文件 | 这一类是内核直接暴露出来的文件，例如 `/proc/sys/net/core/somaxconn`、`/proc/meminfo` 与 `/sys/fs/cgroup/<路径>/memory.max` | 查它的格式要读 `man 5 proc`、`man 5 proc_sys_net` 或 `man 5 cgroups` | 判据是 man 的节号为 5（文件格式），而且它由内核直接读写，外面没有命令包装 |
| 内核参数 | 这一类是由 `sysctl` 管理的键，例如 `net.core.somaxconn`、`vm.swappiness` 与 `kernel.pid_max` | 查它要读 `man 5 sysctl.d`、`man 8 sysctl` 或 `man 8 systemd-sysctl` | 判据是它由 `sysctl` 读写，并且落点是 `*.conf` 文件 |
| 进程资源限制 | 这一类是施加在单个进程上的资源上限，`RLIMIT_NOFILE`（打开文件数上限）就是其中一项 | 查它要读 `man 2 setrlimit`、`man 5 limits.conf` 或 `man 1 prlimit` | 判据是 man 的节号为 2 或 5，并且它由 `ulimit` 或 `prlimit` 操作 |

这四类会互相影响（例如 unit 的 `LimitNOFILE=` 最终会写进进程的 `RLIMIT_NOFILE`），但由于它们的**改法、生效时机、验证方式**是三套不同的东西，所以分不清类别就会得出"改了不生效"这类无法验证的结论。

### 1.1 变更前：对象与影响面

| 想知道什么 | 用什么 | 关键字段 |
| --- | --- | --- |
| 这一组要回答的是谁在监听、监听落在哪个地址 | 用 `ss -lnt` 来读 | `Local Address:Port`、`Recv-Q`、`Send-Q` |
| 这一组要回答的是此刻有哪些对端连着本机 | 用 `ss -tnp` 来读 | `Peer Address:Port`、`users:(("<进程>",pid=<PID>,fd=<n>))` |
| 这一组要回答的是已建立的连接一共有多少条 | 用 `ss -tn state established` 来数，要计数就再接 `wc -l`，在表格里写成 `\| wc -l` | 行数 |
| 这一组要回答的是有哪些服务正在跑 | 用 `systemctl list-units --state=running` 来读 | `UNIT`、`LOAD`、`ACTIVE`、`SUB` |
| 这一组要回答的是改了某个 unit 会连带哪些单元 | 用 `systemctl list-dependencies <unit>` 来读，要看反向依赖就加 `--reverse` | 正向与反向依赖树的行数与层级 |
| 这一组要回答的是有哪些定时任务可能撞上你的操作 | 用 `systemctl list-timers --all` 来读 | `NEXT`、`LEFT`、`LAST`、`ACTIVATES` |
| 这一组要回答的是这台机器有几个地址、对外的那个是哪个 | 用 `ip -brief addr` 来读 | `IFNAME`、`OPERSTATE`、`ADDR` |
| 这一组要回答的是这台机器到底是谁 | 用 `hostnamectl` 来读 | `Static hostname`、`Machine ID`、`Operating System`、`Kernel` |
| 这一组要回答的是哪些进程持有网络句柄 | 用 `lsof -i -P -n` 来读，它不解析端口名与服务名 | `COMMAND`、`PID`、`USER`、`NAME` |

```bash
ss -lnt                                   # 验证：这一组列出监听套接字清单，回答谁在听、听在哪个地址、队列有多长
ss -tnp                                   # 验证：这一组列出已建立连接的进程归属
systemctl list-units --state=running      # 验证：这一组列出本机正在跑的服务数量与名单
lsof -i -P -n                             # 验证：这一组从"进程持有哪个网络句柄"的方向做交叉核对
```

实测输出（环境：**Ubuntu 24.04.5 LTS（VMware 虚拟机）/ 内核 `6.8.0-139-generic` / systemd 255（`255.4-1ubuntu8.17`）/ 4 vCPU / `MemTotal` 7894 MiB / 根分区 ext4 on LVM**；采集时刻 **2026-09-19T08:05 UTC**；**数值仅示意、不代表你的机器**）：

```text
$ ss -lnt
State   Recv-Q  Send-Q  Local Address:Port   Peer Address:Port
LISTEN  0       4096    127.0.0.54:53        0.0.0.0:*
LISTEN  0       128     0.0.0.0:22           0.0.0.0:*
LISTEN  0       4096    127.0.0.53%lo:53     0.0.0.0:*
LISTEN  0       128     [::]:22              [::]:*

$ ss -tn state established             # 验证：实测得到 4 条，对端全部是 192.168.246.1
$ systemctl list-units --state=running  # 验证：实测得到 24 个 unit
$ ip -brief addr
lo      UNKNOWN  127.0.0.1/8 ::1/128
ens33   UP       192.168.246.128/24
```

同一台机器在 **08:09 UTC 复采时变成 6 条 LISTEN、9 条 established、25 个 running unit**，而多出来的 `127.0.0.1:20700` 与 `127.0.0.1:20701` 是同期另一个实验留下的临时监听。**因此这组数字必须带采集时刻才有意义**：同一台机器只差四分钟，就能多出两条监听。

`lsof -i -P -n` 的交叉核对价值在于它给出的是"进程持有句柄"这个方向：实测 `*:22` 同时挂在 `systemd`（PID 1，socket 激活持有）与 `sshd`（PID 1348）上；`systemd-resolved`（PID 691）另有一条去 `192.168.246.2:53` 的上游 UDP。**归属要看 `COMMAND` 与 `PID` 两列一起**：若只看到 `systemd` 就断言"服务没起来"，那是错的，因为它可能只是在 socket 激活模式下持有监听。

变更前把这一组取一遍，得到的是**变更前的对象清单**，它回答谁在听、谁在连、谁在跑、改了会连带谁、以及下一个定时任务几点触发。它的用法不是"看一眼"，而是当作回退时的对照，因为变更后同一组命令的差异就是影响面本身。`systemctl list-timers --all` 的 `NEXT` 与 `LEFT` 尤其要在动手前看一眼：实测 `sysstat-collect.timer` 是 `NEXT 08:10:00` / `LEFT 2min 25s`，这意味着两分半后会有一次采集启动，因此重启类操作最好避开它，否则你会在"数字为什么变了"上多花半小时。

这一组全部是只读，**生产机上也可以做**。`ss -tnp` 与 `lsof -i -P -n` 在非 root 下只能看到自己拥有的进程（实测：同一条命令 root 能看到 `systemd`、`sshd` 与 `systemd-resolved`，而 `realtyz` 只看到自己的进程），所以"我看不到"不等于"没有"。`systemctl` 的视图是本机、本启动周期的，因此它看不到对端与上游。这一组里没有破坏性动作；**不要在这一步就 `systemctl restart`**，因为那是破坏性操作，只在可快照的实验机上或已批准的回退方案里做。

### 1.2 资产与固件

| 想知道什么 | 用什么 | 关键字段 |
| --- | --- | --- |
| 这一组要回答的是这台机器有几颗核、它们怎么分组 | 用 `lscpu` 来读 | `CPU(s)`、`Socket(s)`、`Core(s) per socket`、`Thread(s) per core`、`L3 cache`、`NUMA node(s)` |
| 这一组要回答的是整机内存与 swap 各有多少 | 用 `free` 与 `/proc/meminfo` 来读 | `MemTotal`、`MemAvailable`、`SwapTotal` |
| 这一组要回答的是盘、分区与 LVM 之间的层级关系 | 用 `lsblk` 来读 | `NAME`、`SIZE`、`TYPE`（`disk`/`part`/`lvm`）、`ROTA`、`MOUNTPOINTS` |
| 这一组要回答的是每个文件系统的类型与 UUID 是什么 | 用 `blkid` 来读 | `TYPE`、`UUID` |
| 这一组要回答的是哪个设备挂在哪个目录上、用了什么挂载选项 | 用 `findmnt` 来读 | `TARGET`、`SOURCE`、`FSTYPE`、`OPTIONS` |
| 这一组要回答的是整机的厂商、型号、BIOS 与主板各是什么 | 用 `dmidecode -t system \| -t bios \| -t baseboard` 来读 | `Manufacturer`、`Product Name`、`Version`、`Release Date` |
| 这一组要回答的是这台机器上有哪些控制器与网卡 | 用 `lspci` 来读 | 设备描述与 `bus-info` 风格地址 |
| 这一组要回答的是网卡用的是哪个驱动、固件是什么版本 | 用 `ethtool -i <if>` 来读 | `driver`、`firmware-version`、`bus-info` |
| 这一组要回答的是盘的健康标识与型号各是什么 | 用 `smartctl -i <dev>` 来读 | `Device Model`、`User Capacity`、`SMART support is:` |
| 这一组要回答的是这台机器是物理机还是虚拟机、跑在哪个平台上 | 用 `systemd-detect-virt` 来读 | 输出值（`vmware`、`kvm`、`none`…） |
| 这一组要回答的是发行版与内核分别是哪个版本 | 用 `/etc/os-release` 与 `uname -r` 来读 | `PRETTY_NAME`、`VERSION_ID`；内核版本 |
| 这一组要回答的是 systemd 是哪个版本 | 用 `systemctl --version` 来读 | 首行的版本号与发行版后缀 |
| 这一组要回答的是这台机器的唯一身份标识，它是台账的主键 | 用 `hostnamectl` 与 `/etc/machine-id` 来读 | `Machine ID` |

```bash
lscpu; free -m; lsblk; blkid; findmnt -o TARGET,SOURCE,FSTYPE,OPTIONS
                                          # 验证：这一组读 CPU、内存、设备与文件系统四层资产
dmidecode -t system | head -20            # 验证：这一组回答是谁家的机器（需要 root）
ethtool -i ens33; smartctl -i /dev/sda    # 验证：这一组读驱动、固件与盘的健康标识
systemd-detect-virt; uname -r; systemctl --version | head -1
                                          # 验证：这一组读虚拟化平台、内核与 systemd 三件版本事实
```

实测（同一台实验机，**数值仅示意、不代表你的机器**）：`lscpu` 报 4 vCPU（2 socket × 2 core × 1 thread）、L3 60 MiB、NUMA 1 节点；`/proc/meminfo` 的 `MemTotal: 8083496 kB`（≈ 7894 MiB）；`lsblk` 报 `sda` 为 80G 且 `ROTA=1`、`sda2` 为 2G ext4 并挂 `/boot`、`sda3` 为 48G 的 `LVM2_member`，其上承载的 `ubuntu--vg-ubuntu--lv` 是 ext4 并挂 `/`；`dmidecode -t system` 报 `VMware, Inc.` / `VMware Virtual Platform`，`-t bios` 报 `Phoenix Technologies LTD` / `6.00` / `02/17/2026`，`-t baseboard` 报 `Intel Corporation` / `440BX Desktop Reference Platform`；`lspci` 里有 `Intel 82545EM`（网卡）与 `Broadcom / LSI 53c1030`（存储控制器）；`ethtool -i ens33` 报 `driver: e1000`、`firmware-version` 为空、`bus-info: 0000:02:01.0`；`smartctl -i /dev/sda` 认出 `VMware Virtual S` / 85,899,345,920 bytes，但同时写 `SMART support is: Unavailable - device lacks SMART capability`，而**退出码仍是 0**；`systemd-detect-virt` 报 `vmware`；`hostnamectl` 报主机名 `linux-lab`、`Machine ID` `bd821ce75df94970ad5b6d63b6a8f812`。

这台机器上还有三处**资产自相矛盾**，它们正好说明资产项为什么要交叉核对：`lshw` 把 `sda3` 报成 47GiB 的 EFI 分区，而 `blkid` 明确说它是 `LVM2_member`；`lshw` 报 8GiB 内存，而 `/proc/meminfo` 报 7894 MiB；`lsblk` 的 `ROTA=1` 与 `smartctl` 的 `Rotation Rate: Solid State Device` 相反。**这里的判据是"以哪个来源为准"**：分区与文件系统以 `blkid` 与 `findmnt` 为准，因为这两个来源读的是内核实际认出来的结果；内存以 `/proc/meminfo` 为准；而 `ROTA` 只当线索，因为虚拟机里这些值由 hypervisor 给出，本来就不保证自洽。

版本类事实要**现场取，不凭记忆**：`/etc/os-release` 给出发行版与版本（实测 `PRETTY_NAME` 是 Ubuntu 24.04.5 LTS），`uname -r` 给出运行中的内核（`6.8.0-139-generic`），`systemctl --version` 给出 systemd 版本（`255.4-1ubuntu8.17`）。这三条是后面所有默认值的**前提**，因为同一份内核默认值、同一个 `systemd-tmpfiles` 选项、同一条 `logrotate` 行为，在不同主版本上都可能变；所以把这三条写在巡检记录的最前面，等于给整份记录标了适用范围。同机复采时，若 `uname -r` 与 `/boot` 下最新的 `vmlinuz` 不一致，则说明这台机器重启过并换了内核，此时之前的基线要按新内核重取，不能直接对比。

这一组也是只读，**生产机上也可以做**：`dmidecode` 需要 root，因为它要读 SMBIOS 表；`smartctl -i` 只读标识；`lspci -vvv` 只读配置空间。真正破坏性的是同一批工具的写模式：`smartctl -t`（启动自检会占 IO）、`smartctl -X`（中止自检）、`ethtool -s`（改链路参数）、`ethtool -E`（写 EEPROM）、`mkfs`、`fsck -y` 与 `xfs_repair -L`（后两条会改文件系统内容且不可逆）。这些**只在可快照的实验机上**做，不能拿"识别一下盘"当借口运行。

### 1.3 参数与基线

| 想知道什么 | 用什么 | 关键字段 |
| --- | --- | --- |
| 这一组要回答的是某个键此刻的运行时值是多少 | 用 `sysctl -n <key>` 来读 | 数值本身，输出里不带键名 |
| 这一组要回答的是开机时按什么顺序应用了哪些文件 | 用 `sysctl --system` 来读 | 每行 `* Applying <文件>` 与 `键 = 值` |
| 这一组要回答的是只应用某一个文件时会得到什么结果 | 用 `sysctl -p <单文件>` 来读 | 该文件里的键 |
| 这一组要回答的是开机时是谁、按什么顺序写下了这些键 | 要看 `systemd-sysctl` 的读取集与文件名顺序；本机实测顺序可以用 `strace -f -e trace=openat -o /tmp/x /usr/lib/systemd/systemd-sysctl` 看到 | 打开过的 `.conf` 路径序列（**不含 `/etc/sysctl.conf`**） |
| 这一组要回答的是同一个键被哪些文件写过 | 用 `grep -rn <key> /etc/sysctl.d /run/sysctl.d /usr/local/lib/sysctl.d /usr/lib/sysctl.d /etc/sysctl.conf` 来查 | 命中文件与行 |
| 这一组要回答的是某条软链把哪一个真实文件接进了读取集 | 用 `readlink -f /etc/sysctl.d/99-sysctl.conf` 来读 | 它指向的真实文件（本机实测为 `/etc/sysctl.conf`） |
| 这一组要回答的是当前 shell 的文件句柄上限是多少 | 用 `ulimit -n` 读软限，用 `ulimit -Hn` 读硬限 | 两个数字，并且软限不能超过硬限 |
| 这一组要回答的是整机内存的各项计数分别是多少 | 用 `cat /proc/meminfo` 来读 | `MemTotal`、`MemAvailable`、`SwapTotal` |
| 这一组要回答的是文件系统的容量与 inode 各用了多少 | 用 `df -hT` 与 `df -i` 来读 | `Size`/`Used`/`Use%`；`IUsed`/`IFree`/`IUse%` |

```bash
sysctl -n vm.swappiness                    # 验证：这一组读运行时实际值，而不是文件里写了什么
sysctl --system 2>&1 | grep -E 'Applying|permission denied'
                                          # 验证：这一组读加载顺序与权限失败（注意退出码可能仍是 0）
grep -rn 'vm.swappiness' /etc/sysctl.d /run/sysctl.d /usr/lib/sysctl.d 2>/dev/null
                                          # 验证：这一组查这个键一共有几个写入点
df -hT /; df -i /                          # 验证：这一组同时读容量与 inode 两个口径
```

实测（同机，root；**数值仅示意、不代表你的机器**）：`sysctl --system` 读入的顺序是：先读 `/usr/lib/sysctl.d/10-apparmor.conf`，接着读 `/etc/sysctl.d/10-*.conf`（9 个），然后读 `/usr/lib/sysctl.d/50-pid-max.conf`，再读 `/usr/lib/sysctl.d/99-protect-links.conf`，最后读 `/etc/sysctl.d/99-sysctl.conf` 与 `/etc/sysctl.conf`（末尾这两条属于**同一次读取**，因为进程先打开软链路径，再落到它指向的文件），总共 **14 个文件、17 个键**；`/run/sysctl.d/` 与 `/usr/local/lib/sysctl.d/` 在这台机器上**目录都不存在**（这不是"没有配置"，而是目录本身都没有），同时 `systemd-sysctl` 的 `strace` 读取集里**没有 `/etc/sysctl.conf` 这一条**，因为它只读到软链 `99-sysctl.conf`。root 跑出 **0 条** `permission denied`、退出码 0；同一台机器换 `realtyz`（uid=1000）跑同一条命令，出现 **17 条** `sysctl: permission denied on key "…", ignoring`，而**退出码仍然是 0**。`sysctl -a` 的行数：root 1018 行、`realtyz` 1004 行。几个具体值如下：`net.core.somaxconn` 没有任何文件写过它，`sysctl -n` 得 **4096**，这与这台机器上 `/usr/include/x86_64-linux-gnu/bits/socket.h` 里 `#define SOMAXCONN 4096` 一致——因此**"没有写入点"是结论，而"4096 是不是你机器的默认值"要现场读**（同为内核默认语义的这个参数，在更早的内核里是 128，所以它随版本变，不能凭印象抄）；`kernel.pid_max` 只在 `/usr/lib/sysctl.d/50-pid-max.conf` 出现一次，值是 4194304；`vm.swappiness` 等于 60；`net.ipv4.ip_local_port_range` 等于 `32768 60999`；`fs.file-max` 等于 9223372036854775807。**覆盖对抗实验**（在同一台机器上做过并已回滚）的做法是往 `/etc/sysctl.d/99-zz-lab-test.conf` 写 `1111`、往 `/etc/sysctl.conf` 写 `2222`，`sysctl --system` 之后读到的是 **2222**；回滚复核的结果是「值回到 4096、两个测试文件不存在、`/etc/sysctl.conf` 无残留行」。

`sysctl -n`、`sysctl -a`、`cat /proc/meminfo`、`df` 与不加参数的 `ulimit -n` 都是只读，**生产机上也可以做**。`sysctl -w`、`sysctl -p` 与 `sysctl --system` 会改运行时或重放全部配置；实测把 `vm.swappiness` 从 60 改成 10、再改回 60，一次 apply 是 **3 ms**，一次 rollback 是 **4 ms**——**毫秒级的执行时间不代表毫秒级的风险**，因为参数的影响落在业务侧，不在命令耗时上。这类写操作属于**只在可快照的实验机上**做，线上要走变更流程并预置回滚。`ulimit -n <值>` 改的是当前 shell 及其子进程的软限，不是系统级配置，因此退出 shell 之后就没了。

### 1.4 容量与日志

| 想知道什么 | 用什么 | 关键字段 |
| --- | --- | --- |
| 这一组要回答的是文件系统的容量用了多少 | 用 `df -hT` 来读 | `Size`、`Used`、`Avail`、`Use%`、`Type` |
| 这一组要回答的是 inode 用了多少 | 用 `df -i` 来读 | `IUsed`、`IFree`、`IUse%` |
| 这一组要回答的是哪个目录占的空间最多 | 用 `du -xsh <目录>` 与 `du -sh <目录>/* \| sort -rh \| head` 来读 | 排行与差值（`-x` 表示不跨文件系统） |
| 这一组要回答的是有没有已经删除、却仍被进程持有的文件 | 用 `lsof +L1` 来读 | `COMMAND`、`PID`、`FD`、`SIZE/OFF`、`NLINK`、`NAME (deleted)` |
| 这一组要回答的是 journal 一共占了多少空间 | 用 `journalctl --disk-usage` 来读 | 一行摘要里的 MiB 数 |
| 这一组要回答的是本机有哪些启动周期可以回溯 | 用 `journalctl --list-boots` 来读 | 序号、启动时间、`-b` 可用的编号 |
| 这一组要回答的是轮转规则打算做哪些动作 | 用 `logrotate -d <配置文件>` 来读 | `log needs rotating`、`renaming …` |
| 这一组要回答的是临时文件的清理策略是什么 | 用 `systemd-tmpfiles --cat-config` 来读 | 每条规则涉及的目录与清理条件 |
| 这一组要回答的是 ext4 的保留块与元数据是什么状况 | 用 `tune2fs -l <dev>` 来读 | `Reserved block count`、`Block count`、`Filesystem features` |

```bash
df -hT; df -i                             # 验证：这一组把容量与 inode 放在一起看
du -xsh /var/log; du -sh /var/log/* | sort -rh | head
                                          # 验证：这一组读总量与构成（-x 避免跨文件系统）
lsof +L1 2>/dev/null | head               # 验证：这一组查有没有"删了不释放"的句柄
journalctl --disk-usage; journalctl --list-boots | tail -5
                                          # 验证：这一组读 journal 总量与可回溯的启动周期
logrotate -d /etc/logrotate.d/<app>       # 验证：这一组干跑，只打印判断与计划动作
tune2fs -l /dev/mapper/ubuntu--vg-ubuntu--lv | grep -i reserved
                                          # 验证：这一组读 ext4 保留块（它是"有空间却写不进去"的一个原因）
```

容量实测（同机，2026-09-19；**数值仅示意、不代表你的机器**）：根分区 `/dev/mapper/ubuntu--vg-ubuntu--lv` 是 46.9 G、已用 20%、inode 3145728 已用 6%；`journalctl --disk-usage` 报 **20.7 MiB**（同日更早的基线是 **53.9 MiB**，两者的差值是同期实验的写入与回收造成的）；`du -sh /var/log` 报 27M，其中 journal 21M、syslog 1.3M、installer 1.2M、dpkg.log 820K、kern.log 748K。

"删了不释放"这一类在 **128 MiB 的 loop 靶盘**上复现过（**数值仅示意、不代表你的机器**；这个破坏性动作**只在可快照的实验机上**做，用临时 loop 设备当靶子，不碰根分区）：删掉一个被进程持有的 40 MiB 文件后，`df` 显示已用 **41 MiB**，而 `du` 只有 **20 KiB**；`lsof +L1` 抓到 `sleep 17678 … 8u … 41943040 … (deleted)`；从 `/proc/<pid>/fd/8` 拷出 **41943040 字节**（可以再用 `sha256sum` 校验）；杀掉进程后已用从 **102M 回落到 62M**。inode 耗尽同样只用 loop 靶盘复现：`mkfs.ext4 -N 32` 的盘在空盘时 `df -i` 是 **11/32 = 35%**，`touch` 40 个文件后变成 **32/32 = 100%**，而 `df -h` 只有 **1%**，此时 `touch` 报 `No space left on device`（2026-09-19T08:35 UTC）。

读日志要先固定三件事：**范围**（用 `-u <unit>` 限定单元，用 `--since` 与 `--until` 限定窗口）、**启动周期**（配 `--list-boots` 选第几次启动，因为跨重启的现场只能这样拿）与**口径**（用 `-o short-iso` 带时区偏移、用 `-p err` 只看级别、用 `--no-pager` 保证在脚本里不卡在分页器上）。实测这台机器上，同一个十分钟窗口里限定 `-u ssh` 的错误计数是 0，而不限定则是 93，因此**"有多少条错误"这个问题，不给范围就没有答案**。

`journalctl --disk-usage`、`--list-boots`、`logrotate -d`、`systemd-tmpfiles --cat-config`、`tune2fs -l`、`du` 与 `lsof +L1` 都是只读，**生产机上也可以做**。**只在可快照的实验机上**做的是：`journalctl --vacuum-size=` 与 `--vacuum-time=`（真删日志）、`logrotate -f`（强制轮转）、`systemd-tmpfiles --clean`（真删文件）、`rm`（它对"被持有的空间"无效，还会丢掉现场）、`tune2fs` 的写模式（`-O` 与 `-e` 会改文件系统元数据）、`lvconvert --merge`（快照回滚会不可逆地丢掉快照之后的写入）、`mkfs`、以及 `fsck -y` 与 `xfs_repair -L`（后两条不可逆）。

### 1.5 到期与变更状态

| 想知道什么 | 用什么 | 关键字段 |
| --- | --- | --- |
| 这一组要回答的是某个域名的证书什么时候到期 | 先用 `openssl s_client -servername <域名> -connect <主机>:443 </dev/null`，再接 `openssl x509 -noout -dates` | `notBefore`、`notAfter`（GMT） |
| 这一组要回答的是服务端有没有把完整的证书链发出来 | 在上面的命令上加 `-showcerts` | 证书张数、每张的 `s:`/`i:` |
| 这一组要回答的是这条链能不能被本机的 CA 库验通过 | 用 `openssl verify -CAfile <ca> [-untrusted <中间证书>] <叶证书>` 来验 | `OK` 或 `error 20 at 0 depth lookup: …` |
| 这一组要回答的是本机时间对不对、有没有与时间源同步 | 用 `timedatectl` 来读 | `Time zone`、`System clock synchronized`、`NTP service` |
| 这一组要回答的是仓库里有哪些包可以升级 | 用 `apt list --upgradable` 来读 | 包名、目标版本、来源仓库 |
| 这一组要回答的是有哪些服务要重启才能用上新版的库 | 用 `needrestart -b` 来读 | 待重启的 unit 与原因 |
| 这一组要回答的是一个 unit 的真实状态是什么 | 用 `systemctl show <unit> -p ActiveState -p SubState -p NRestarts -p ExecMainStartTimestamp -p UnitFileState` 来读 | 五个属性各自的含义 |

```bash
openssl s_client -servername www.example.com -connect <主机>:443 </dev/null 2>/dev/null \
  | openssl x509 -noout -dates          # 验证：这一组读证书的生效与到期时间（GMT）
openssl verify -CAfile /etc/ssl/certs/ca-certificates.crt cert-01.pem
                                          # 验证：这一组读只给叶证书时的验链结果
openssl verify -CAfile /etc/ssl/certs/ca-certificates.crt -untrusted interm.pem cert-01.pem
                                          # 验证：这一组读补上中间证书之后是否变成 OK
timedatectl                               # 验证：这一组读时区、时钟同步状态与 NTP 服务是否在跑
systemctl show ssh -p ActiveState -p SubState -p MainPID -p NRestarts \
  -p ExecMainStartTimestamp -p UnitFileState
                                          # 验证：这一组回答服务"现在是不是我改完之后的那一个进程"
```

实测（同机，2026-09-19T08:08 UTC，`www.example.com`；OpenSSL 3.0.13；**数值仅示意、不代表你的机器**）：`notAfter = Oct 27 22:17:21 2026 GMT`，距采集时点剩余 **38 天**；链内 **4 张**；`Verify return code: 0 (ok)`。离线复验时执行 `openssl verify -CAfile /etc/ssl/certs/ca-certificates.crt cert-01.pem`，它报 `error 20 at 0 depth lookup: unable to get local issuer certificate`，再加上 `-untrusted interm.pem` 之后就变成 `cert-01.pem: OK`——**同一张证书、同一个 CA 库，只差一张中间证书**。本机 CA 库在四个常见落点都是 **121 张**。`timedatectl` 显示 `Time zone: Etc/UTC (UTC, +0000)`、**`System clock synchronized: no`**、`NTP service: active`，因此**`is-active` 是 active 并不等于时钟已同步**，这是两件事。

变更状态实测（**数值仅示意、不代表你的机器**）：`systemctl show ssh` 给出 `ActiveState=active`、`SubState=running`、`MainPID=1348`、`NRestarts=0`、`ExecMainStartTimestamp=Sat 2026-09-19 07:20:10 UTC`、`UnitFileState=disabled`、`FragmentPath=/usr/lib/systemd/system/ssh.service`（它由 `ssh.socket` 拉起）；`systemctl list-dependencies ssh` 的正向输出是 **63 行**，加 `--reverse` 之后只有 `ssh.service` 一行；`systemctl list-timers` 的首行 `sysstat-collect.timer` 是 `NEXT 08:10:00` / `LEFT 2min 25s` / `LAST 08:00:12`，而 `fwupd-refresh.timer` 的 `NEXT` 是 `09:25:48`。

`apt list --upgradable` 与 `needrestart -b` 要连起来读：前者回答"仓库里有哪些包可以升级"，后者回答"按当前已装的库，有哪些服务的**运行中进程还在用旧版本**"。两份清单数量不同很正常，因为一个是仓库状态，另一个是本机进程状态；巡检记录里把这两份清单与到期日（证书 `notAfter`）放在同一张表里，才能回答"这次窗口要动哪些东西、动完之后要重启谁"。

这一组除"重启/升级"之外全是只读，**生产机上也可以做**：`openssl s_client` 与 `verify` 只做握手与本地校验，`apt list --upgradable` 只列可升级项，`needrestart -b` 只输出清单，`systemctl show` 只读属性。破坏性的是它们的下一步：`apt-get upgrade`、`systemctl restart <unit>`（会断连接、丢内存态）、`systemctl daemon-reload`（会重载 unit 定义，影响后续启动行为）。这些**只在可快照的实验机上**做，或者在已批准的变更窗口里做，并且要先确认这些动作的回退路径。

## 2. 怎么读这些数字

字段的完整定义与机制背景见同章《一次生产变更的一生》《一次中断与恢复的一生》与《生产运维与变更治理》，而下面列出的都是**最容易读错的固定动作**。

### 2.1 先固定三样：单位、窗口、来源

同一列在不同工具里含义可能不同，甚至同一个缩写在两处的含义也不同，因此读之前要先把单位、窗口与来源这三样固定下来：

| 陷阱 | 事实 |
| --- | --- |
| 把 `nstat` 的输出当速率 | 它的默认输出是**窗口差值**，只有 `-a` 才是累计值；而且这个"窗口"是**自上一次有人运行过 `nstat` 以来**，因为那个时间戳记录在文件里（`man 8 nstat` 原文写的是默认输出 calculate increments since the previous use），所以别人跑过一次就会把你的差值切小。要可复现，就用 `-a` 取累计值再自己差分 |
| 把 `sar -f` 的一条记录当瞬时值 | 它是**该采集间隔内的平均**，因为实验机的采集间隔是 10 分钟（`sysstat-collect.timer` 的 `NEXT 08:10:00` 与 `LAST 08:00:12` 相隔十分钟），所以拿它和 1 秒采样的 `iostat 1 5` 比，等于用两个窗口的平均值互相否定 |
| 按本地时区读 `sadf -d` 导出的时间戳 | 那是 **UTC**（行尾带 `UTC`），因此时区不是 UTC 的机器必须换算 |
| 把 `lsof` 的输出当全量进程清单 | 非 root 只能看到自己拥有的进程，因此它列出的内容与 root 跑出来的不是同一份数据 |
| 认为 `ss -lnt` 的 `Recv-Q` 与 `ss -tn` 的 `Recv-Q` 同义 | 在监听套接字上它是"已完成握手、还没被应用 `accept()` 的**连接条数**"，而在已连接套接字上它是"内核缓冲区里还没被读走的**字节数**"，所以两者的单位不同，不可比 |
| 把 `systemctl` 的视图当集群视图 | 它只反映本机、本启动周期，因此上游、对端与另一台机器都不在里面 |
| 认为 `df` 的 `Size` 与 `du` 的总和应当相等 | 一个按文件系统算，一个按目录算，因此挂载覆盖、保留块与已删除句柄都会让两者不等 |
| 把 `openssl s_client` 的 `Verify return code: 0 (ok)` 当"客户端一定能连" | 它只说明**本机 CA 库**验通了这条链，所以主机名匹配要另加校验，而且客户端的 CA 库与时钟都不在这台机器上 |
| 把 `systemctl is-active` 的成功当"功能正常" | 它只回答"进程在不在"，不回答"能不能连、业务通不通"；实测本机 `NTP service: active` 而 `System clock synchronized: no` |

下面把每个关键字段的读法拆成五件事：**它是什么、单位是什么、判据是什么、与谁同看、看到它之后转向哪一步**：

| 字段 | 是什么 | 单位 | 判据 | 与谁同看 | 转向哪一步 |
| --- | --- | --- | --- | --- | --- |
| `ss -lnt` 的 `Recv-Q` | 它是在监听套接字上已经完成握手、但还没有被应用 `accept()` 取走的连接条数 | 它的单位是条 | 若它持续等于 `Send-Q`（也就是该套接字的队列上限），则说明应用 accept 不及时 | 要与 `nstat` 的 `TcpExtListenOverflows` 和 `ListenDrops` 一起看 | 若判据成立，则转向应用侧的 accept 循环或该套接字的队列上限 |
| `df -i` 的 `IUse%` | 它是 inode 的使用比例 | 它的单位是百分比 | 若它接近 100%，则写入会报 `No space left on device`，而这个报错与容量无关 | 要与 `df -h` 的 `Use%` 以及 `du` 的小文件计数一起看 | 若判据成立，则转向小文件清理与保留期 |
| `lsof +L1` 的 `SIZE/OFF` | 它是已删除、但仍被进程持有的文件大小 | 它的单位是字节 | 若它与 `df` 减 `du` 的缺口**同量级**，则这个缺口才值得追 | 要与 `du -xsh` 和 `df -h` 一起看 | 若判据成立，则转向抢救内容，或者让持有者重开文件 |
| `journalctl --disk-usage` | 它是 journal 的占用 | 它的单位是 MiB | 判据只看**增长速率与上限**，而不看单次快照的大小 | 要与 `/etc/systemd/journald.conf` 的 `SystemMaxUse` 一起看 | 若增长速率已经顶到上限，则转向 journald 上限或文件式日志的轮转 |
| `System clock synchronized` | 它表示系统时钟是否已经与时间源同步 | 它的取值是是或否 | 它取 `no` 时，所有"剩余天数"与"时间窗"的判断都不可靠 | 要与 `NTP service` 和 `timedatectl timesync-status` 一起看 | 若它取 `no`，则转向时钟同步排查 |
| `UnitFileState` | 它是 unit 的开机启用状态 | 它的取值是枚举值 | 它取 `disabled` 并不代表这个 unit 没在跑，因为它可能被 socket、timer 或别的依赖拉起 | 要与 `ExecMainStartTimestamp` 和 `FragmentPath` 一起看 | 若它取 `disabled` 而服务却在跑，则转向查实际生效的是哪条路径 |
| `ExecMainStartTimestamp` | 它是主进程的启动时刻 | 它的单位是时间戳 | 若它早于你的变更时刻，则说明主进程没有被换掉 | 要与 `MainPID` 和 `NRestarts` 一起看 | 若判据成立，则转向查重启是否真的生效 |
| `NRestarts` | 它是该 unit 被自动重启的次数 | 它的单位是次 | 它非 0 说明这个 unit 反复挂掉；同时空值不等于 0 | 要与 `journalctl -u <unit>` 和 `SubState` 一起看 | 若它非 0，则转向崩溃原因 |

### 2.2 几个"看起来像结论"的数字

- **`df` 与 `du` 不一致**：出现这种不一致并不是因为"`du` 不准"，而是因为它有四类成因——已删除但被进程持有（读 `lsof +L1`）、挂载覆盖（读 `findmnt`）、保留块与元数据（读 `tune2fs -l`）、配额（读配额报表）。这四类的处置完全不同，因此要逐一排除，而不是互相否定。实测删掉被持有的 40 MiB 文件后，`df` 报 41 MiB 而 `du` 报 20 KiB，两者的差值正好是那个文件。
- **`lsof +L1` 有输出**：这并不等于"磁盘被偷了"，因为 `systemd-journald` 长期持有刚被轮转掉的 journal 文件是正常现象。这里的判据是量级，也就是看 `SIZE/OFF` 与你的容量缺口是不是同一量级；若对不上，就先别顺着这条线查。
- **`systemctl show <unit>` 的空输出**：空属性说明该属性此刻没有值（或者对该单元类型不适用），并不等于"没发生过"，因为 `NRestarts` 为空与 `NRestarts=0` 不是一回事。即使 unit 名写错，`systemctl show` 也可能照样打印一整套属性，只是 `LoadState` 显示 `not-found`。因此判据是 `LoadState` 与 `ActiveState`，并用 `systemctl cat <unit>` 确认 unit 定义真的存在。
- **`openssl s_client` 的 `Verify return code: 0 (ok)`**：它只说明**本机 CA 库**验通了服务端发来的这条链，并不说明主机名匹配，更不说明客户端能连。实测同一张证书在只给叶证书时 `openssl verify` 报 `error 20 at 0 depth lookup: unable to get local issuer certificate`，只有补上 `-untrusted` 的中间证书才变成 `OK`，因此**"验不过"与"验得过"的差别可能只是一张中间证书**，而客户端的失败往往就出在服务端没把链发全。
- **命令退出码 0**：它只代表命令本身没失败，不代表任务成功。实测有三例：`realtyz` 跑 `sysctl --system` 时有 **17 条** `permission denied`，退出码仍是 **0**；`smartctl -i` 在 `SMART support is: Unavailable` 时退出码也是 **0**；`df` 与 `ss` 退出码 0 只说明"我读到了本机视图"。

### 2.3 采样纪律与基线卡

- **同口径、带时间戳、至少两次**：判断抖动要按秒，判断泄漏要按小时或按天；实测同一台机器 08:05 与 08:09 两次采集，LISTEN 由 4 条变成 6 条、established 由 4 条变成 9 条、running unit 由 24 个变成 25 个，而多出来的正是同期另一个实验的临时监听。**因为单次采样会被并行活动污染**，所以每次巡检都要带采集时刻，并优先排除"同期有别的实验/变更"。
- **留原始输出**：要用 `script -f`、`tee` 或重定向到文件，而不是只抄一个数字，因为取证的价值在原始文本里（例如 `error 20 at 0 depth lookup` 这一句就比"验不过"值钱得多）。
- **采集顺序固定为"先只读、后判断、再动手"**：任何写操作之前必须留下一份只读快照。实测"删了不释放"这一类，一旦重启，`lsof +L1` 的现场与失败计数就一起没了，因此事后无法复盘，只能重新等它发生。
- **一次采集、一个时刻、一份文件**：把同一时刻取到的五组输出（对象、资产、参数、容量、到期）落到同一个带时间戳的文件里，而不是散在好几个终端里。实测两次采集只差四分钟，`ss` 与 `systemctl` 的数字就都变了；因此把不同时刻的输出拼在一起看，等于制造了一份跨轮次的假对照。
- **日志基线必须先剔除他人噪声**：实测 `journalctl -u ssh --since "10 min ago" | grep -icE 'error|fail'` = **0**，而同一窗口不限定 `-u` 的同类计数 = **93**（这 93 条几乎全来自同机其它服务）。**同一个窗口、同一个模式，加不加 `-u` 是两个数量级的差别**，因此没有归属范围的"错误数"不是基线。
- **基线卡的五组数据**（对象清单、资产与固件、参数与文件、容量与日志、到期与变更状态）落在同章《生产运维与变更治理》的产物模板里，而上面各小节写下的每一条命令与每一个字段就是它们的取法与读法。

## 3. 常见故障与排查方向

### 场景一：根分区 100%，业务写入报 `No space left on device`，但 `du` 加起来只有几 MiB

**机器与服务**：4 vCPU（`MemTotal` 7894 MiB）/ Ubuntu 24.04.5 LTS（VMware 虚拟机）/ 内核 `6.8.0-139-generic` / 根分区 `/dev/mapper/ubuntu--vg-ubuntu--lv`（ext4 on LVM，46.9 G）；**这是单台虚拟机，没有第二台机器，也没有负载均衡**；约束是**不能重启**，因为内存态业务在跑。

**现象数值**：`df -hT /` 的 `Use%` = 100%；`du -xsh /` 加起来只有几 MiB；`df -i` 的 `IUse%` 只有 6%。

**排查顺序**：

1. 先只读取证四条，不要动手：`df -hT`、`df -i`、`findmnt`、`lsof +L1`。因为这四个口径一起看，才能把"容量、inode、挂载、句柄"四类分开；
2. 再看 `lsof +L1` 的 `SIZE/OFF` 与缺口是不是同量级，因为实测这一类会给出 `sleep … 8u … 41943040 … (deleted)` 这样的行；
3. 若缺口对得上，则先**抢救内容**：先用 `ls -l /proc/<pid>/fd` 找到号，再用 `cp /proc/<pid>/fd/<n> /var/tmp/rescued.bin` 拷出来，最后用 `sha256sum` 与业务侧记录核对；
4. 再决定怎么释放：要么让进程重开文件（reload 或重启该服务），要么结束那个进程。**这一步有影响，因此要先确认它是不是业务进程**；
5. 这一步按读数决定方向：若 `lsof +L1` **无输出**，则转向 `findmnt` 查挂载覆盖，因为挂载点遮住了下层目录，`du` 看不到被遮的内容；若这样还不能解释，则再转向 `tune2fs -l` 查 ext4 保留块，然后再转向配额报表。若 `df -i` 到 100%，则转向小文件与 inode 方向，因为这一类与容量无关；
6. 复现只在**可快照的实验机上**做：用 128 MiB 的 loop 靶盘（`truncate` 加 `losetup` 再加 `mkfs.ext4`）搭出来，跑完用 `umount` 加 `losetup -d` 回到原状，并复核 `losetup -a` 为空。生产机上只做第 1 步的只读取证。

**一份合格的回答应当包含：结论、依据、边界、动作**——其中结论是**空间被"已删除但仍被进程持有的文件"占着**，它既不是日志占的，也不是小文件占的；依据是 `df` 已用 41 MiB 对 `du` 20 KiB、`lsof +L1` 的 `SIZE/OFF` = 41943040 字节、以及抢救文件的 `sha256` 与业务侧一致；边界是这条结论只解释"删了不释放"这一类，若 `lsof +L1` 无输出则方向要改到挂载覆盖或保留块，并且在 `kill` 之前要确认进程角色；动作是先抢救内容，再让持有者释放句柄，验收时用 `df` 已用回落且业务写入恢复。

### 场景二：证书巡检发现"台账上没有的域名"，且部分客户端连不上

**机器与服务**：同一台机器（只有一个对外地址 `ens33 192.168.246.128/24`）；**单机、无负载均衡、无第二台机器**，因此同一个 IP 的 443 上跑多个域名时只能靠 SNI（Server Name Indication，TLS 握手中客户端声明所要访问域名的扩展）区分，台账里漏一个域名就有一个域名巡检不到；约束是不能中断服务。

**现象数值**：`openssl s_client -servername www.example.com -connect <主机>:443 </dev/null | openssl x509 -noout -dates` 得到 `notAfter = Oct 27 22:17:21 2026 GMT`，剩余 **38 天**；链内 **4 张**；`Verify return code: 0 (ok)`；但部分客户端报"证书不可信"。

**排查顺序**：

1. **先固定采集口径**：时刻（2026-09-19T08:08 UTC）、域名、SNI 参数与 OpenSSL 版本（3.0.13）。若不写这些，"还有 38 天"就没法复算；
2. 数链：用 `-showcerts` 看服务端实际发了几张、每张的签发者是谁；
3. 离线复验：执行 `openssl verify -CAfile /etc/ssl/certs/ca-certificates.crt cert-01.pem`，实测报 `error 20 at 0 depth lookup: unable to get local issuer certificate`，这说明缺中间证书；加上 `-untrusted interm.pem` 之后就变成 `OK`。**报错文本本身就是结论**；
4. 看 CA 库：本机四个落点均是 121 张。客户端报错时，第一件要问的是"它的 CA 库与本机是不是同源、有没有更新"；
5. 看时钟：`timedatectl` 实测 `Time zone: Etc/UTC`、**`System clock synchronized: no`**、`NTP service: active`。时钟未同步时，"剩余天数"的算术与证书有效期校验都不可靠；
6. 这一步按读数决定方向：若 `Verify return code` 非 0，则转向链或 CA 库方向；若它为 0 而客户端仍报错，则转向主机名校验、客户端 CA 库、时钟与 SNI 未发送（老客户端）这四个方向；若台账里缺域名，则用 `-servername` 逐域名枚举，把清单补进台账。

**一份合格的回答应当包含：结论、依据、边界、动作**——其中结论是**服务端没发全链，客户端缺中间证书**，同时本机时钟未同步；依据是 `error 20 at 0 depth lookup`、加上 `-untrusted` 之后变成 `OK`、`notAfter` 与剩余 38 天、以及 `System clock synchronized: no`；边界是 `s_client` 的 `0 (ok)` 只针对本机 CA 库，它不等于主机名匹配，更不代表客户端能通，而且客户端的 CA 库与时钟都不在这台机器上，只能给方法；动作是补齐中间证书、同步时钟、把域名清单与到期日纳入台账并逐域名定期巡检，同时因为单机上没有第二份入口可交叉验证，这一点要如实写进结论。

### 场景三：参数"改了不生效"

**机器与服务**：同一台机器；`sysctl --system` 实测读入 **14 个文件、17 个键**；`/run/sysctl.d/` 不存在；分别在 root 与 `realtyz` 两种身份下跑；约束是改动要能回滚。

**现象数值**：把 `vm.swappiness = 10` 写进 `/etc/sysctl.d/99-app.conf` 后，`sysctl -n vm.swappiness` 仍读回 **60**，因为这台机器的 `/etc/sysctl.d/99-sysctl.conf` 指向 `/etc/sysctl.conf`，名字排在 `99-app.conf` 之后；或者换个身份执行 `sysctl --system` 时满屏 `permission denied`，而脚本却"成功返回"。

**排查顺序**：

1. 先取**运行时实际值**，也就是跑 `sysctl -n <key>`。文件里写了什么不算数，因为运行时值才是判据；
2. 找**所有写入点**，也就是跑 `grep -rn <key> /etc/sysctl.d /run/sysctl.d /usr/local/lib/sysctl.d /usr/lib/sysctl.d /etc/sysctl.conf`。实测这台机器上 `net.core.somaxconn` **一个文件都没写**（运行时值是 4096，它与内核头文件里的 `SOMAXCONN` 一致，因此属于内核默认），而 `kernel.pid_max` 只在 `/usr/lib/sysctl.d/50-pid-max.conf` 出现一次（值是 4194304），所以**"这个键归谁管"必须查出来，不能假定**；
3. **先分清是哪套机制在读**，再谈顺序。开机时执行的是 `systemd-sysctl.service`，它的读取集**只有 `.d` 目录**（`/etc/sysctl.d/`、`/run/sysctl.d/`、`/usr/local/lib/sysctl.d/`、`/usr/lib/sysctl.d/`），**不读 `/etc/sysctl.conf`**；手工重放时执行的是 procps 的 `sysctl --system`，它在那些 `.d` 之后**再读一次 `/etc/sysctl.conf`**。两套机制的合并规则相同：所有 `.conf` 按**文件名字典序**排序（不按目录），名字靠后的覆盖靠前的；**同名文件**以 `/etc` 优先于 `/run`，`/run` 优先于 `/usr`。因此"写进 `/etc/sysctl.d/99-app.conf`"能不能赢，取决于有没有别的文件排在它后面；本机实测 `strace` 到的读入顺序是：先读 `/usr/lib/sysctl.d/10-apparmor.conf`，接着读 `/etc/sysctl.d/10-*.conf`（9 个），然后读 `/usr/lib/sysctl.d/50-pid-max.conf`，再读 `/usr/lib/sysctl.d/99-protect-links.conf`，最后读 `/etc/sysctl.d/99-sysctl.conf`。其中**`99-sysctl.conf` 是 `../sysctl.conf` 的软链**（本机实测 `readlink -f` 得 `/etc/sysctl.conf`），它靠 "99-" 这个字典序排到最后，而不靠路径特例；**若那条软链不存在（新版 Debian 系已开始移除），则 `/etc/sysctl.conf` 在两套机制里都不会被读**，它里面的键也就不会生效；
4. 分清 `sysctl -p <单文件>` 与 `sysctl --system`：前者只应用你指定的那一个文件，后者按顺序重放全部。因此**只跑 `-p` 就断言"开机后是什么值"，口径是错的**；
5. 看**身份**：实测 root 跑 `sysctl --system` 是 0 条 `permission denied`、退出码 0；同一台机器换 `realtyz`（uid=1000）则出现 17 条 `permission denied on key "…", ignoring`，而**退出码仍然是 0**。因此"命令成功"证明不了"参数都应用了"，要用 `sysctl -n` 逐键验收；
6. 这一步按读数决定方向：若运行时值等于写入值却仍"不生效"，则转向调用方，查应用是否在启动时又改了一遍、或者 `systemd` unit 的 `LimitNOFILE=` 之类是否覆盖了它；若运行时值不等于任何文件里的值，则说明有人用 `sysctl -w` 改过运行时，此时重放配置就会丢掉这次改动。

**一份合格的回答应当包含：结论、依据、边界、动作**——其中结论是**这个键有多个写入点，排在最后的那个文件把你的值覆盖了**（本机是软链 `99-sysctl.conf` 指向的 `/etc/sysctl.conf`），或者"执行身份权限不足，17 个键被忽略而退出码仍是 0"；依据是 `grep -rn` 的全部命中文件、文件名排序与软链指向、`sysctl -n` 的运行时值、以及 `permission denied` 的行数与退出码；边界是两套机制的读取集不同，`/etc/sysctl.conf` 是否被读取决于那条软链在不在，`sysctl -w` 只改运行时并且重启即丢，`ulimit` 只影响当前 shell 树，而这台机器的 `/run/sysctl.d/` 与 `/usr/local/lib/sysctl.d/` 不存在，引用时不能假定它们存在；动作是把改动写到顺序上真正生效的那个文件、用 `sysctl --system` 重放、再用 `sysctl -n` 逐键验收，回滚时走同样的重放路径。

### 场景四：批量脚本跑一半失败，机器上留下半成品

**机器与服务**：同一台机器上跑批处理脚本；约束是不能重启、要保留现场；**这台机器没有第二台可对照**，因此失败定位只能靠脚本自己的记录。

**现象数值**：`xargs -P 4` 的子任务失败时退出码是 **123**（它只知道"有失败"，不知道是哪一台）；`timeout 5 sleep 30` 得 **124**，而 `timeout 5 true` 得 **0**；`set -u` 引用未设置变量得 **127**；`${VAR:?}` 得 **127**；`T=""; [ $T = x ]` 的退出码是 **0**，因为 `-u` 只拦"未设置"，不拦"空值"；`flock -n` 第二次获取同一把锁得 **1**（非阻塞，不挂住）；幂等脚本连跑三次时，第 2、3 次输出"已是目标状态，跳过写入（幂等）"、目标文件行数恒为 **1**，而把中间一步换成不存在的命令，则脚本停在那一行且退出码是 **127**。

**排查顺序**：

1. **先收现场，不要先重跑**：用 `ps -eo pid,etime,args | grep <脚本名>` 找残留进程；用 `ls -l /var/lock/` 找锁；用 `ls -ld /tmp/tmp.*` 之类的命令找临时目录；用 `ls -l <目标文件>*` 找带时间戳的备份与只改了一半的配置；
2. 用**退出码分类**再决定方向：123 表示批量里有失败（因此要去看脚本自己落的每台日志）、124 表示超时被杀（因此要看是哪一步慢）、127 表示命令不存在或变量未设置被 `-u` 拦住、1 表示一般错误或锁被别人持有。**没有每台输出，123 就等于没有信息**；
3. 查锁：若 `flock -n` 返回 1，则说明另一个实例还在跑，这时"再跑一次"只会制造第二份半成品；
4. 判断半成品到哪一步了：看幂等判据（也就是脚本用来判断目标状态是否已达成的那一条判据，例如 `grep -qxF "$LINE" "$CONF"`）与目标文件的行数。实测在幂等写法下，目标文件的行数恒为 1，重复执行不会再追加；
5. 决定"补齐"还是"回退"：补齐要能重复执行（也就是幂等），回退要用脚本自己留下的带时间戳备份（`cp -a <文件> <文件>.<日期>`），**不要用"再改一遍"当回滚**；
6. 复跑前先干跑与限量：用 `logrotate -d`、Ansible 的 `--check --diff` 与 `--limit`，并把并发降到 1；跑完复核"无残留进程、无残留锁、无残留临时目录"。

**一份合格的回答应当包含：结论、依据、边界、动作**——其中结论是**失败点在写入之前还是之后**、现场留下了哪几样东西、以及它是真失败还是超时被杀；依据是退出码 123/124/127 的具体来源、锁的持有者、幂等判据与文件行数、以及每台输出日志的那一行；边界是 123 不指出是哪一台，所以批量脚本必须自己记录每台输出，同时 `-u` 不拦空值，因此 `rm -rf "$T/"` 在 `$T` 被赋成空串时依然危险；动作是先清理残留进程与锁，再用带时间戳的备份回退半成品，然后把幂等判断补齐并限量复跑，验收时用"连跑两次结果一致"。

### 场景五：变更窗口内"改完了、服务 active，但业务报错持续"

**机器与服务**：同一台机器上一个由 socket 激活的服务（实测 `ssh` 就是这种形态：`FragmentPath=/usr/lib/systemd/system/ssh.service`，由 `ssh.socket` 拉起）；**单机、没有负载均衡**，探活脚本打的是本机回环；约束是变更窗口只剩 10 分钟。

**现象数值**：`systemctl show ssh` 报 `ActiveState=active`、`SubState=running`、`MainPID=1348`、`NRestarts=0`、`ExecMainStartTimestamp=Sat 2026-09-19 07:20:10 UTC`、`UnitFileState=disabled`；`systemctl list-dependencies ssh` 的正向输出是 **63 行**，`--reverse` 只有 **1 行**；`ss -lnt` 里业务端口只出现在 `0.0.0.0` 与 `[::]` 上，本机回环上没有业务监听。

**排查顺序**：

1. **先确认"你改的是不是正在跑的那个东西"**：跑 `systemctl show <unit> -p ActiveState -p SubState -p MainPID -p ExecMainStartTimestamp -p UnitFileState`。判据是 `ExecMainStartTimestamp` **晚于**你的变更时刻；若它早于变更时刻，则说明主进程根本没被换掉，你看到的 `active` 是"本来就在跑"。`UnitFileState=disabled` 还提示实际生效路径可能是 socket、timer 或依赖拉起，而不是"开机启用"；
2. 看**重启计数**：`NRestarts=0` 说明它没自动重启过；它非 0 则说明它反复挂掉，此时方向转向崩溃原因（用 `journalctl -u <unit>` 看）；
3. 看**依赖面**：正向 `list-dependencies` 实测有 63 行，说明"改它会连带多少东西"比想象的大；而 `--reverse` 只有 1 行，说明**依赖树看不到"谁在用它"**，因此业务侧影响要看连接，不看依赖树；
4. 看**真实监听**：读 `ss -lnt` 的 `Local Address:Port`。本机回环上探活成功，只证明回环路径通；`ip -brief addr` 实测对外只有 `ens33 192.168.246.128/24` 一个地址，因此**外部路径通不通必须从外部验**，本机自测不能替代；
5. 看**集群与上游**：这是最容易出错的一步。`systemctl show` 只反映本机；这台机器**没有第二台、没有负载均衡**，所以"上游是否还有失败单元""对端是否也改了"这类问题在本机**无法取证**，只能如实写成边界，或者去上游与集群侧取数；
6. 这一步按读数决定方向：若 `ExecMainStartTimestamp` 没变，则说明重启动作本身没生效（可能改的是别的 unit，也可能在 socket 激活下主进程由别的路径拉起）；若时间戳已更新而业务仍报错，则转向配置内容、依赖面与外部路径；若有失败单元，则按"哪些依赖未就绪"逐条查 `systemctl --failed`。

**一份合格的回答应当包含：结论、依据、边界、动作**——其中结论是**主进程没有被换掉**，或者"服务确实换了，但探活打的是回环，外部路径未验证"；依据是 `ExecMainStartTimestamp` 与变更时刻的先后、`MainPID`、`NRestarts`、`ss -lnt` 的监听地址与 `ip -brief addr` 的对外地址；边界是本机看不到上游与集群侧状态，单机上没有第二入口可交叉验证，而且 `ActiveState=active` 只说明进程在、不说明业务通；动作是先确认实际生效的 unit 与启动路径，再从外部做一次探活，最后按依赖面逐条验收，回退时用变更前的配置备份并同样验证"主进程真的换了"。

## 常见坑

| 做法或说法 | 后果或事实 |
| --- | --- |
| 把内核参数当文件去 `cat` | 判据是 man 的节号，因为命令落在 1 与 8 节、文件格式落在 5 节、系统调用落在 2 节；因此 `net.core.somaxconn` 要用 `sysctl -n` 读，而 `/proc/sys/net/core/somaxconn` 才能直接读 |
| 只采样一次就当基线 | 同一台机器 08:05 与 08:09 相差 4 分钟，LISTEN 由 4 条变成 6 条、established 由 4 条变成 9 条，而多出来的正是同期别的实验 |
| 不写采集时刻就贴数字 | 没有时刻的 `df`、`ss` 与 `journalctl --disk-usage` 输出无法复算，也无法判断它是否被并行活动污染 |
| 用 `df` 或 `du` 单方面下结论 | 两者不一致有四类明确成因，因此要逐一排除，而不是宣布"`du` 不准" |
| 看到 `lsof +L1` 有输出就认定磁盘被偷 | `systemd-journald` 持有轮转掉的 journal 是正常的，因此判据是 `SIZE/OFF` 与缺口是否同量级 |
| 把命令退出码 0 当成任务成功 | `sysctl --system` 在 uid=1000 下有 17 条 `permission denied` 却仍退出 0，而 `smartctl -i` 在 `SMART support is: Unavailable` 时也退出 0 |
| 把 `System clock synchronized: no` 忽略掉 | 时钟没同步时，证书剩余天数、时间窗与日志时间戳都不可靠，因为 `NTP service: active` 不等于已同步 |
| 以为 `sysctl -p <文件>` 等价于开机生效 | `-p` 只应用你给的那一个文件，而开机是另一套读取集（`systemd-sysctl` 只读 `.d` 目录），因此两者的覆盖面不同 |
| 只在一处写参数，不查其它写入点 | 同一个键可能有多个写入点，因为 `net.core.somaxconn` 在这台机器上无人写（值是内核默认 4096），而 `kernel.pid_max` 只在 `50-pid-max.conf` 出现 |
| 用 `systemctl is-active` 或 `active/running` 宣布变更成功 | 它只说明进程在，因此要看 `ExecMainStartTimestamp` 是否晚于变更时刻、以及 `MainPID` 是否换过 |
| 用本机回环探活代替外部验证 | 回环通只证明回环通，因为实测对外只有 `ens33`（`192.168.246.128/24`）一个地址，所以外部路径必须从外部验 |
| `lshw` 与 `lsblk`/`blkid` 矛盾就当异常 | 实测这台虚拟机上 `lshw` 把 `sda3` 报成 47GiB 的 EFI 分区、把内存报成 8GiB，而 `blkid` 明确是 `LVM2_member`、`/proc/meminfo` 是 7894 MiB；因为虚拟机里这类值由 hypervisor 给出，所以要以内核实际认出来的来源为准 |
| 用 `systemctl list-dependencies --reverse` 判断影响面 | 依赖树看不到"谁在用它"（实测反向只有 1 行），因此业务影响要看连接与上游 |
| 先重启再取证 | 重启会清掉已删除句柄、内存态与失败计数，现场就没了；而取证是只读的，**生产机上也可以做** |

**第一反应不要做什么**：不要先重启；不要在只读取证就能定性时先改参数或先清日志；不要把"命令退出码 0"当成功证据；不要用一台机器的视图回答集群侧的问题。

## 要点自测

**问：怎么区分命令、内核接口文件与内核参数？**
答：判据是 man 的节号，因为节号 1 与 8 是命令（例如 `man 8 ss`），节号 5 是文件格式（例如 `man 5 proc` 与 `man 5 sysctl.d`），节号 2 是系统调用（例如 `man 2 setrlimit`）。因此 `net.core.somaxconn` 要用 `sysctl -n` 读，`/proc/sys/net/core/somaxconn` 要直接 `cat`，而 `RLIMIT_NOFILE` 要用 `ulimit` 或 `prlimit` 操作。

**问：`ss -lnt` 与 `ss -tn` 的 `Recv-Q` 有什么不同？**
答：在监听套接字上它是"已完成握手、还没被应用 `accept()` 的连接**条数**"，因此它持续等于队列上限（`Send-Q`）就说明应用 accept 不及时；而在已连接套接字上它是"内核缓冲区里没被读走的**字节数**"。两者的单位不同，所以不能互相比。

**问：`df` 与 `du` 对不上，怎么排？**
答：要四类逐一排除：已删除但被进程持有（读 `lsof +L1`，看 `SIZE/OFF` 与缺口是否同量级）、挂载覆盖（读 `findmnt`）、ext4 保留块（读 `tune2fs -l`）、配额（读配额报表）。实测删掉被持有的 40 MiB 文件后 `df` 报 41 MiB、`du` 报 20 KiB，两者的差值正是那个文件。

**问：参数"改了不生效"，先查哪三样？**
答：先读运行时值（`sysctl -n`），再查所有写入点（对四个 `.d` 目录与 `/etc/sysctl.conf` 跑 `grep -rn`），最后分清是哪套机制在读，因为开机是 `systemd-sysctl`（只读 `.d` 目录），而手工重放是 `sysctl --system`（末尾再读一次 `/etc/sysctl.conf`）。本机实测 `/etc/sysctl.conf` 之所以最后生效，是因为它被软链成 `/etc/sysctl.d/99-sysctl.conf`（`readlink -f` 指向 `/etc/sysctl.conf`）。此外还要确认执行身份，因为 uid=1000 会产生 17 条 `permission denied` 而退出码仍是 0。

**问：证书巡检为什么必须记采集时刻、`-servername` 与 CA 库路径？**
答：剩余天数是拿 `notAfter` 与采集时刻相减算出来的，因此缺一个就算不出；多域名同 IP 只能靠 SNI 区分，所以不写 `-servername` 可能取到另一个域名的证书；`Verify return code: 0 (ok)` 只针对本机那一个 CA 库（实测四处均 121 张），因为客户端的 CA 库与时钟都不在这台机器上。

**问：批量脚本失败后，第一件事做什么？**
答：收现场，也就是找残留进程、锁（`flock -n` 返回 1 说明还有实例在跑）、临时目录、带时间戳的备份与只改一半的配置；再用退出码分类（123 表示有失败但不知哪台、124 表示超时、127 表示命令或变量问题、1 表示一般错误）。**没有每台输出，123 等于没有信息**，所以批量脚本必须自己落每台日志。

**问：服务 `active/running`，怎么判断变更真的生效了？**
答：看 `systemctl show` 的 `ExecMainStartTimestamp` 是否晚于变更时刻、`MainPID` 是否换过、`NRestarts` 是否为 0、以及实际生效路径是什么（`UnitFileState=disabled` 说明可能是 socket 或 timer 拉起的）；再从外部做探活，不要用本机回环代替。

**第一反应不要做什么**：不要在只读取证之前动手改配置、清日志或重启；不要把退出码 0、`active` 或 `is-active` 当成功证据；不要在时钟未同步时用"剩余天数"下结论；不要用单机视图回答集群侧的问题。
