## 0. 30 秒速览

> [!abstract] 这一篇只要记住六句话
> - **证书到期不是「突然过期」，而是「一直没人看」。**
>   - 怎么验证：一条命令就能看到剩余天数——本机实测 `openssl s_client -connect www.example.com:443 -servername www.example.com </dev/null | openssl x509 -noout -dates` 输出 `notAfter=Oct 27 22:17:21 2026 GMT`；`-servername` 不能省，否则可能拿到默认站的证书。
> - **到期告警要「按剩余天数」告警，不是「按事件」告警。**
>   - 证据：剩余 30 天告警给你时间排期，剩余 1 天告警只能给你慌乱；监控口径应当是「距到期日天数」而不是「是否已过期」。
> - **证书链不全会表现为「部分客户端连不上」。**
>   - 怎么验证：用 `openssl s_client -showcerts` 看服务端是否发出了完整链；缺中间证书时，浏览器可能靠 AIA（Authority Information Access，证书里指出「中间证书到哪下载」的字段）自动补链，而某些客户端（Java、部分 SDK）不会。
> - **自动续期失败的最常见原因是「挑战路径不通」，不是证书服务本身。**
>   - 证据：HTTP-01 挑战要求 80 端口对公网可达、webroot 路径正确；一旦反向代理改动或防火墙调整，续期就会静默失败——**所以必须有「续期失败」和「剩余天数」两条告警**。
> - **补丁分三类：必须立刻打（在野利用）、排期打（高危）、评估后再打（功能与低危）。**
>   - 怎么验证：`dnf updateinfo list security` 或 `apt list --upgradable` 看清单，再按「是否可被远程利用」排序，而不是一律最新。
> - **日志留存的三个前提：时钟同步、不可篡改、到期才删。**
>   - 证据：本机 `timedatectl` 显示 `System clock synchronized: yes`；时钟不同步时，日志的时间戳在法律与排障两个场景里都不可用。

## 1. 证书：四个时间点与一条命令

### 1.1 一张证书的生命周期

| 时间点 | 含义 | 要做的动作 |
| --- | --- | --- |
| **签发** | CA 签发证书 | 记录到期日、纳入台账 |
| **部署** | 装到服务上并 reload | 用 `openssl s_client` 从**外部**验证实际生效的是新证书 |
| **到期前** | 通常提前 30 天开始续期 | 自动续期 + 剩余天数告警 |
| **到期 / 吊销** | 客户端开始报错 / 主动失效 | 应急替换；吊销要同步更新 CRL（证书吊销列表）与 OCSP（在线证书状态协议） |

### 1.2 查到期：三条命令

```bash
openssl s_client -connect www.example.com:443 -servername www.example.com </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates
                                          # 验证：外部看到的证书主体、签发者与生效/到期时间

openssl s_client -connect www.example.com:443 -servername www.example.com -showcerts </dev/null 2>/dev/null \
  | grep -c 'BEGIN CERTIFICATE'
                                          # 验证：服务端发出了几张证书（1 张通常意味着缺中间证书）

openssl x509 -in /etc/ssl/certs/<cert>.pem -noout -enddate -subject
                                          # 验证：本地证书文件的到期日（部署前的检查）
```

本机实测输出（2026-09-19 采集）：

```text
subject=CN = example.com
issuer=C = US, O = SSL Corporation, CN = Cloudflare TLS Issuing ECC CA 3
notBefore=Jul 29 22:10:08 2026 GMT
notAfter=Oct 27 22:17:21 2026 GMT
```

### 1.3 算剩余天数

```bash
end=$(openssl s_client -connect www.example.com:443 -servername www.example.com </dev/null 2>/dev/null \
        | openssl x509 -noout -enddate | cut -d= -f2)
days=$(( ( $(date -d "$end" +%s) - $(date +%s) ) / 86400 ))
echo "剩余 $days 天（到期：$end）"        # 验证：把「几号到期」变成「还剩几天」，才适合做告警
```

> [!warning] 两个容易踩的点
> - **别忘 `-servername`**：在一台托管多个域名的服务器上，不加它可能验证到的是默认站点的证书，结论完全错误。
> - **别只看本地文件**：`openssl x509 -in` 检查的是文件，**不等于线上实际生效的证书**。生产验收必须从外部连一次（子笔记 07 的「业务验收」同理）。

### 1.4 证书链与「部分客户端连不上」

```bash
openssl s_client -connect <host>:443 -servername <host> -verify_return_error -showcerts </dev/null
                                          # 验证：完整验证并打印链（返回码与 verify 结果都要看）
```

链不全时，现代浏览器通常会通过证书里的 AIA 字段自动下载中间证书补全，所以「浏览器能开」；而 Java 客户端、部分移动端与 SDK 不做 AIA 抓取，直接报链不完整。**这就是「同一个接口有的调用方能调、有的不能调」的典型原因之一。**

### 1.5 内部 CA 与自动续期

| 项 | 要点 |
| --- | --- |
| 内部 CA | 根证书有效期通常很长，中间证书可轮换；**根证书更新要提前很久**，因为所有客户端都要更新信任库 |
| 密钥保护 | 私钥权限最小化、不进代码库、不随镜像分发；有条件的用 HSM 或密钥管理服务 |
| ACME（Automated Certificate Management Environment，自动证书管理环境）/certbot | HTTP-01（需要 80 端口可达）或 DNS-01（需要 DNS API 凭据）；续期用 hook 触发服务 reload |
| 续期失败原因 | 挑战路径不通（反代改动）、DNS 凭据过期、磁盘满、时钟漂移、reload hook 失败 |

```bash
certbot renew --dry-run                   # 验证：只演练续期流程（不会真的换证书，未安装则跳过）
certbot certificates                      # 验证：列出证书与到期日（排查「为什么告警了」）
```

### 1.6 证书台账（直接抄这张表）

| 域名/用途 | 签发方式 | 到期日 | 责任人 | 续期方式 | 失败告警 | 验证方式 |
| --- | --- | --- | --- | --- | --- | --- |
| `api.example.com` | ACME 自动 | 2026-10-27 | 张 | certbot timer + reload hook | 剩余 < 30 天 | 外部 `openssl s_client` |
| `*.internal` | 内部 CA | 2027-03-01 | 李 | 人工签发（季度） | 剩余 < 45 天 | 内网探测 |
| 客户端信任的根证书 | 内部 CA | 2036-01-01 | 王 | 提前 12 个月启动分发 | 提前 18 个月 | 各客户端抽样 |

**这张表的价值在于：它把「证书会不会过期」变成一个可以逐行检查的问题。**

## 2. 补丁：分批与重启

### 2.1 先分类，再排期

| 类别 | 判据 | 处理节奏 |
| --- | --- | --- |
| **紧急安全补丁** | 远程可利用、在野利用、影响面大 | 尽快，走紧急变更通道 |
| **高危安全补丁** | 本地可利用或需要交互、无在野利用 | 排入最近的补丁窗口 |
| **功能与低危补丁** | 修 bug、增功能、低危漏洞 | 与版本升级一起排期，避免碎片化变更 |

```bash
dnf updateinfo list security              # 验证：RHEL 系查看待打的安全补丁清单
dnf check-update --security               # 验证：只检查安全更新（不执行）
apt list --upgradable 2>/dev/null | head  # 验证：Debian 系查看可升级包
apt-get -s upgrade                        # 验证：-s 是模拟执行，先看会发生什么
```

### 2.2 哪些补丁必须重启

| 组件 | 是否需要重启 | 说明 |
| --- | --- | --- |
| 内核 | **需要** | 换的是运行中的内核；不重启就还在跑旧内核（`uname -r` 验收） |
| glibc / systemd / 核心库 | **通常需要**（至少重启受影响的服务） | 已在运行的进程仍持有旧库映射 |
| 用户态服务 | 重启该服务即可 | 用 `needrestart`/`needs-restarting` 判断哪些进程用了被替换的库 |
| 纯数据/文档包 | 不需要 | 例如 man 页、证书包（部分场景要 `update-ca-certificates`） |

```bash
dnf needs-restarting -r                   # 验证：RHEL 系判断是否需要重启系统
needrestart -b                            # 验证：Debian 系批量检查（未安装则跳过）
uname -r; rpm -q kernel-core 2>/dev/null | tail -3
                                          # 验证：运行中的内核版本 vs 已安装的内核包
```

### 2.3 补丁窗口与重启批次

```text
补丁窗口 = 业务低峰 − 其它变更 − 留给回滚的时间
重启批次 = 由容量余量决定（N+1 / N+2，见子笔记 12）
```

四条纪律：

1. **一次只做一件事**：不要「顺便」升级版本或改配置。
2. **重启前摘流量**（有状态服务）并确认对端能承接。
3. **重启后立刻验证**：`uname -r`（内核）、关键服务状态、业务探活、容量水位。
4. **保留回滚路径**：内核保留旧版本启动项；包升级记录旧版本号；不可回滚的补丁要提前说明。

## 3. 合规与日志留存

### 3.1 留存期由三个来源共同决定

| 来源 | 典型要求 | 影响 |
| --- | --- | --- |
| 合规/审计 | 例如 ≥ 180 天 | 决定保留期与存储成本 |
| 排障需要 | 通常 7~30 天 | 决定在线检索窗口 |
| 安全事件回溯 | 越长越好 | 决定归档与不可篡改要求 |

**三者取最严格要求**，并把它落到具体的存储与保留策略上（子笔记 13 的日志治理）。

### 3.2 三个前提

| 前提 | 怎么保证 | 失效后果 |
| --- | --- | --- |
| **时钟同步** | `timedatectl` 显示 synchronized；所有节点同一时间源 | 日志时间对不上，跨系统比对失去意义 |
| **不可篡改** | 集中收集、只追加、权限最小化、必要时 WORM（Write Once Read Many，写入后不可删改）存储 | 审计场景下无法作为证据 |
| **到期才删** | 保留策略 + 自动清理 + 变更审批 | 要么被当证据质疑，要么磁盘被写满 |

```bash
timedatectl                               # 验证：本地时间、时区、同步状态（本机实测 synchronized: yes）
journalctl --disk-usage                   # 验证：日志占用（本机实测 693.7 MiB，见子笔记 13）
ls -l /var/log/journal/                   # 验证：日志是否持久化（存在 = 重启后仍保留）
```

> [!example]- 实验 11：给一批域名做证书到期巡检（生产机也可以做，只读）
> **怎么做**：写一个循环，把域名清单逐个连一遍并算剩余天数，按天数排序输出；对「剩余 < 30 天」的项高亮。示例命令见本篇 1.3。跑完后把结果与台账比对——**台账里没有的域名就是漏登记的证书**。
> **预期**：得到一张「域名 → 到期日 → 剩余天数」的表。本机实测可用的写法：`openssl s_client -connect <host>:443 -servername <host> </dev/null | openssl x509 -noout -enddate`（2026-09-19 采集 `www.example.com` 得到 `notAfter=Oct 27 22:17:21 2026 GMT`）。
> **风险**：低（只读；对外连接建议限制频率，避免被当作扫描）。
> **耗时**：约 20 分钟。
> **怎么退回去**：不需要回滚；把结果归档进台账。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 只在签发时看一眼到期日 | 没人会记得；要进台账 + 按剩余天数告警 |
| 用「是否已过期」做告警 | 过期时已经是事故；应按剩余天数（如 30/14/7 天）分级告警 |
| 查证书时不加 `-servername` | 多域名服务器上会拿到默认站证书，结论错误 |
| 只查本地证书文件 | 文件对不等于线上生效；必须从外部连一次 |
| 证书链只装叶子证书 | 部分客户端（Java、部分 SDK）会因链不全失败 |
| 自动续期没有失败告警 | 续期是静默的；失败要等到过期才发现 |
| 根证书轮换临时启动 | 客户端信任库更新需要很长时间；要提前数月 |
| 补丁一律打最新 | 引入未经灰度验证的行为变化；要按类别排期 |
| 打完补丁不重启就认为生效 | 内核/glibc/systemd 类更新必须重启（或重启对应服务）才生效 |
| 日志保留期拍脑袋定 | 要么不合规，要么把磁盘写满；要由合规与排障需求共同决定 |
| 时钟不同步 | 日志、证书校验、心跳判定全部受影响 |

## 决策练习

> [!question]- 场景：周五下午 4 点，监控告警「内部 API 证书将在 1 天后过期」。签发方式写着「内部 CA 人工签发」，责任人写的是「李（已离职三个月）」。业务方说这个接口周末有大批量调用。
> A. 立刻在周五下午做：联系李、拿到新证书、部署、观察
> B. 分两条线并行：①**应急线**——先确认是否还有其它可用凭据/是否有备用证书，评估能否临时延长（例如用另一张已有证书临时替换，或把调用方切到备用域名），把「周末不中断」作为第一目标；②**治理线**——补上责任人、把签发改为可自动化的方式、把到期告警从「1 天」前移到 30 天，并把「责任人离职」纳入台账复核项
> C. 先不管，等真的过期再说——周末没有人会盯着证书
>
> **答案：B。**
> A 的风险在于**周五下午是最差的变更窗口**：拿到证书之后还要部署、验证、观察，一旦出问题，救援的人最少、业务量还最大。
> C 是把可控风险变成必然事故：周末大批量调用期间过期，等于主动制造一次全量失败。
> B 是正解：**先用止血手段保住周末（可用性优先），再把流程缺口补上**。注意 B 里两个动作都是有价值的诊断输出：「有没有备用凭据」暴露了单点依赖，「责任人离职」说明台账的复核机制缺失——这两条改进项比这次换证书本身更重要。

## 要点自测

> [!question]- 怎么在不影响业务的前提下查一个域名的证书剩余天数？
> - `openssl s_client -connect <host>:443 -servername <host> </dev/null | openssl x509 -noout -enddate`，再把日期换算成天数。
> - 必须加 `-servername`；必须从外部连，而不是只看本地文件。
> - **第一反应不要是什么**：不要用浏览器打开看一眼就当成验证。

> [!question]- 到期告警应该按什么口径设计？
> - 按**剩余天数**分级（例如 30/14/7 天），而不是「是否已过期」。
> - 自动续期的场景还要有「续期任务失败」这条独立告警，因为续期是静默的。
> - **第一反应不要是什么**：不要把「过期告警」当成证书管理的全部。

> [!question]- 证书链不全会有什么现象？怎么验证？
> - 部分客户端（Java、部分 SDK、移动端）失败，而浏览器正常（浏览器会通过 AIA 自动补链）。
> - 用 `openssl s_client -showcerts` 看服务端发出的证书张数，并用 `-verify_return_error` 看完整验证结果。
> - **第一反应不要是什么**：不要因为「浏览器能打开」就认为证书配置没问题。

> [!question]- 哪些补丁必须重启才生效？
> - 内核（`uname -r` 验收）、glibc/systemd 等核心库（至少重启受影响的服务）。
> - 用 `dnf needs-restarting -r` 或 `needrestart` 判断哪些进程还在用被替换的库。
> - **第一反应不要是什么**：不要打完补丁不重启就宣布「已修复漏洞」。

> [!question]- 日志留存要满足哪三个前提？
> - 时钟同步、不可篡改、到期才删。
> - 留存期由合规、排障、安全回溯三者取最严格要求决定。
> - **第一反应不要是什么**：不要把留存期当成「磁盘够大就多留点」的问题。
