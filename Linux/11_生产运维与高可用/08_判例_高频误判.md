# 高频误判

这十九条误判按**一次变更与事故的时间线**排列，因此它们被分成四段。**动手之前**这一段收集的是承诺与依据类的误判，涉及备份、预发、分级与回滚；**执行之中**这一段收集的是过程信号类的误判，涉及退出码、重启、部分成功与并发；**验证时刻**这一段收集的是读数与口径类的误判，涉及服务状态、权限、配置键、容量与 inode；**事后**这一段收集的是资产与到期类的误判，涉及归档、证书与日志留存。因为越靠后的误判被发现得越晚、可挽回的余地也越小，所以这个顺序本身也接近一份处置优先级。

全篇的实测环境统一为 **Ubuntu 24.04.5 LTS（VMware 虚拟机）/ 内核 `6.8.0-139-generic` / systemd 255（`255.4-1ubuntu8.17`）/ cgroup v2 / 4 vCPU / `MemTotal` 7894 MiB / 根分区 `/dev/mapper/ubuntu--vg-ubuntu--lv`（ext4 on LVM，46.9 G）/ 时区 `Etc/UTC` / root 可用，另有 `realtyz`（uid=1000）**。文中贴出的输出与数字都是在这台机器上跑出来的，因此它们**数值仅示意、不代表你的机器**；结论能否迁移，要看每条判据里给出的字段与趋势，而不是照抄数字，因为一旦换到别的内核、发行版或硬件上，绝对值就会不同。

## 1. 「备份任务每天成功，说明备份有效」

**场景**：机器就是上面那台实验机，备份对象是 `/srv/data` 下 101 MiB 的数据集。定时任务用 `rsync --link-dest` 做硬链接快照，因此 `journalctl -u backup.timer` 里每天都有一行退出码 0，`ls -l /backup/` 里也每天多一个目录；于是值班的人在群里说「备份很健康，不用管」。

**常见误判**：值班的人把「任务退出码 0」当成了「备份有效」。这个判断看起来成立，因为退出码确实是备份链路上唯一的自动信号，而且历史记录连续多天都是 0；由于手边没有别的证据，退出码就被当成了全部证据，于是「写入动作没报错」被读成了「数据能拿回来」。

**判据**：

- **是什么**：备份有效性指「数据能被读回来并交付业务」，而不是指「写动作完成了」。前者只有恢复演练能证明，后者只有退出码能证明，因此两者不能互相替代。
- **单位**：恢复耗时用**秒**，数据量用 **MiB**；由于两者要一起报，所以报告应当写成带计时的恢复演练记录。
- **判据**：应当能列出恢复出来的文件、能证明内容与原数据一致，并且恢复耗时小于业务容忍的中断时长（RTO，Recovery Time Objective，恢复时间目标）；若这三件事有一件做不到，则这次备份的有效性就没有证据。
- **与谁同看**：要与「这次备份占了多少空间」一起看，因为增量快照小到不合理时，就要怀疑它其实什么都没拷。
- **转向哪一步**：若不达标，则转向重建备份链；若达标，则把这次耗时写进记录，作为下一次的基线。

本机实测的完整一轮如下：基线快照 `base` 是 101 MiB、耗时 0.29 秒；第二份增量 `inc-2` 只有 **16 KiB**、耗时 0.048 秒；`du -sh --total` 对 `base` 与 `inc-2` 的合计仍然是 **101 MiB**，因为没改动的文件走的是硬链接，所以它们不占第二份空间。恢复 `inc-2` 用了 **0.42 秒**，而且 `diff -r base inc-2` 无差异。

```bash
du -sh --total /backup/base /backup/inc-2  # 验证：硬链接快照合计仍是一份数据的体积
time rsync -a /backup/inc-2/ /tmp/restore/ # 验证：恢复要计时，这是唯一验收
diff -r /srv/data /tmp/restore             # 验证：恢复结果与源数据逐文件比对
```

结论会变的条件只有一个：若 `diff -r` 的输出不再为空，或者恢复耗时超过 RTO，则「备份成功」这几个字毫无意义。同时要记住**硬链接快照的判定标准与全量副本不同**：由于它的体积小是设计行为（因为未改动的文件共享 inode），所以 `du` 报 101 MiB 而不是 202 MiB 属于正常；因此不能因为「增量只有 16 KiB」就怀疑它没拷数据，因为要怀疑的是「改动了的文件有没有进快照」，而验证方法是改一个已知文件再跑一次，然后 `diff` 到那一处。

**结论**：备份的唯一验收标准是「能恢复，并且计时」，而退出码 0 只说明写入动作没报错。出处：`man 1 rsync`（`--link-dest` 与硬链接复用）。

## 2. 「监控和服务探活都正常，说明变更成功」

**场景**：一次监听队列参数调整上线之后，值班的人贴出三份证据：探活脚本对 `/healthz` 返回 200、监控大盘没有红色、`systemctl status` 显示 `active (running)`；由于这三份证据都指向正常，于是他宣布变更成功。

**常见误判**：值班的人把这四种「假成功」都当成了成功。① **重启后恢复正常**：变更过程掉了几秒，重启后服务又回来了，因此看起来「没影响」；② **没有告警**：由于阈值定得太松、或者根本没采到数据，所以静默被误读成健康；③ **单机探活全通过**：由于探活只证明这一台能应答，所以它不证明流量分布正常；④ **跟以前一样**：由于没有量化、也没有对照，所以只能说「没看到变坏」。这四种说法之所以看起来都成立，是因为它们各自都对应一条真实的观测结果，只是那条结果回答的问题都不是「变更有没有成功」。

**判据**：

- **是什么**：验收要的是「变更好或至少不变坏」的**可量化证据**，以及「没有悄悄出错」的独立信号；由于探活只覆盖其中一小部分，所以两者必须分开取证。
- **单位**：网络栈计数器是**累计包数或累计次数**，因此必须取两次读数之间的**差值**；探活是 HTTP 状态码，它没有单位。
- **判据**：要在同一时间窗内把业务指标（延迟分位、错误率）与内核计数器一起看；若计数器有增长、而探活仍然是 200，则这属于「探活看不见的失败」。
- **与谁同看**：要与变更时间线对齐，也就是要核对计数器增长的时刻是否落在变更执行的分钟里。
- **转向哪一步**：一旦发现计数器增长，就转向查监听队列与 accept 积压，而不是继续扩批。

本机实测的这个组合很典型：`nstat -az TcpExtListenOverflows` 在 08:08:19 是 **0**，到 08:16:32 变成 **10**，因此累计值涨了 10 次，也就是有 10 次连接握手完成却因为队列满被丢掉，而同一时段探活一直是 200。

```bash
nstat -az TcpExtListenOverflows            # 验证：累计值，要取差值而不是看单点
ss -lnt                                    # 验证：Recv-Q 是否长期贴近队列上限
```

结论会变的条件有两条：若探活在同一个窗口里出现非 200，则探活本身就已经报警，因此不必再看计数器；若计数器与基线的差值同量级（也就是本来每天都有几十次这种丢弃），则要查的是队列长度是否长期偏小，而不是这次变更。

**结论**：探活正常只覆盖「应用还能应答」，它覆盖不了「连接在进入应用之前就被丢了」，因此验收要看差值。出处：`man 8 nstat`（默认输出是"自上一次使用以来的增量"、`-a` 才是绝对累计值）、`man 8 ss`（`Recv-Q` 在监听套接字上的含义）。顺带一个口径细节：由于默认差值依赖 nstat 自己记录的"上次读数"，所以**别人跑过一次就会把你的窗口切短**；因此要对齐时间窗口，就要用 `-a` 取累计值、由自己差分。

## 3. 「预发验证过了，生产可以全量」

**场景**：预发环境（staging）跑完了全量回归，而且接口的 99 分位延迟与生产基线接近；由于回归与延迟都过了，所以变更单上批注「预发通过，生产直接全量执行」，同时没有分批计划。

**常见误判**：把预发当成生产的小号副本。这个判断看起来成立，因为预发跑的是同一份代码、同一份配置管理；由于代码与配置这两件事确实一致，所以「预发通过」被顺推成了「生产也行」。

**判据**：

- **是什么**：预发与生产至少在三个维度的分布上不同，这三个维度是数据规模、流量形态与依赖真实度。
- **单位**：数据规模用**条数或 GiB**；流量形态用**每秒请求数（QPS，Queries Per Second，每秒查询数）与峰谷比**；由于依赖真实度没有连续量，所以它只能定性描述（真实第三方、真实证书、真实网络延迟）。
- **判据**：若生产数据量是预发的 50 倍、流量是尖峰型、还依赖真实外部接口，则预发通过只能证明「路径通」，不能证明「量级行」。
- **与谁同看**：要与灰度计划一起看，因为生产的真正安全来自分批、验收判据与回滚方案这三件东西，而不是预发结论。
- **转向哪一步**：预发通过之后，应当转向「写分批计划与回滚触发条件」，而不是转向「全量执行」。
- **补充的量化判据**：预发与生产的**规格倍数**（CPU 核数、内存 GiB、磁盘 IOPS）如果相差 10 倍以上，则预发的延迟数字连参考价值都很低，因为排队行为与队列深度的关系不是线性的；这时预发只能用来验功能，不能用来定容量。容量余量要单独算：生产峰值并发如果是 8000，而单实例在预发上验到的安全并发是 2000，那么至少要 5 个实例才叫够，因此「预发通过」对这个数字没有任何贡献。

**结论**：预发缩小的是「代码是否正确」的风险，它不缩小「规模与流量」的风险，所以生产的保险是分批与可回滚。出处：Google SRE 手册「Release Engineering」章（渐进式发布与灰度）。

## 4. 「程序退出码 0，说明命令生效了」

**场景**：一次巡检脚本报告「全部通过」，因为脚本里的每条命令退出码都是 0。复核时发现两件事：`smartctl -i /dev/sda` 打印了 `SMART support is: Unavailable`，`sysctl --system` 打印了 17 条 `permission denied on key "…", ignoring`，而两者的退出码都还是 0。

**常见误判**：把「进程正常结束」当作「目标状态已达成」。这个判断看起来成立，因为退出码是脚本与 CI 里最标准的成功信号；由于这个信号在别处一直可靠，所以它被当成了目标状态的证明。

**判据**：

- **是什么**：生效与否要看**运行时口径**，也就是内核与 systemd 实际持有的值，而不是命令的退出状态，也不是配置文件里的文本。
- **单位**：`sysctl -n` 给出的整数没有单位，因为它的含义随键而定（例如 `vm.swappiness` 是无量纲权重）；`systemctl show` 的时间戳是带时区的绝对时刻。
- **判据**：要用 `sysctl -n <键>` 回读、用 `systemctl show <unit> -p <属性>` 回读、用 `cat /proc/...` 回读；若三者任一与预期不符，则它就是没生效。
- **与谁同看**：要与命令的 stderr 一起看，因为像 `permission denied … ignoring` 这类提示是**跳过动作**的明确声明，而退出码不会因此变化。
- **转向哪一步**：若回读不符，则转向查加载顺序与覆盖点（见第 16 条），而不是再执行一遍同样的命令。

还有一个容易被忽略的层次：**回读运行时值证明的是「系统层生效」，它不证明「应用层读到」**。由于有些参数的读取发生在进程启动那一刻（例如连接池大小、线程数），所以内核值改了而进程没重启时，业务行为不会有任何变化。因此验收要分清三层——**文件内容**（配置管理对得上）、**运行时值**（内核或 unit 实际持有的值）、**行为证据**（日志时间戳、指标变化、端到端探活），三层都过才算生效；由于只过前两层就是「配置正确但没生效」，所以这是变更验收里最常见的假通过。

```bash
sysctl -n vm.swappiness                     # 验证：运行时值，这是唯一算数的口径
systemctl show ssh -p ActiveState -p SubState -p NRestarts
                                            # 验证：运行时状态，不是 unit 文件内容
smartctl -i /dev/sda                        # 验证：注意 `SMART support is: Unavailable` 这类文本
```

**结论**：退出码只描述「程序怎么结束的」，它不描述「系统变成什么样」，所以验收一律回读运行时值。出处：`man 8 sysctl`（`--system` 对无法写入的键只打印忽略提示）、`man 8 smartctl`。

## 5. 「回滚命令写在变更单上，就有回滚方案了」

**场景**：变更单的回滚段写着 `sysctl -w vm.swappiness=60`，评审也通过了。执行当天，执行人把值从 60 改成 10，十分钟后业务出现抖动，于是他照着回滚段敲了一遍，然后说「已经回滚了」。

**常见误判**：把「有回滚命令」当成「有回滚能力」。这个判断看起来成立，因为评审时最容易被检查的就是「回滚段有没有填」；由于这一栏填了，所以它被当成了方案已经存在。

**判据**：

- **是什么**：可回滚要同时满足三个隐含条件，也就是有退路（原件或旧值还在）、退路可用（在实验机上真的跑过一次）、退路够快（耗时小于 RTO）。
- **单位**：回滚耗时用**毫秒或秒**，而 RTO 用秒或分钟；由于两者单位不同，所以必须换算到同一单位再比。
- **判据**：`time` 出来的实测耗时必须小于 RTO，并且回滚后的运行时值必须等于旧值。
- **与谁同看**：要与「这次变更的观察窗口长度」一起看，因为回滚比变更本身还慢时，等于没有回滚方案。
- **转向哪一步**：若任一条不满足，则转向「先补退路」（做备份、预演回滚），而不是继续上线。
- **补充的量化尺度**：把「够快」翻成可比较的数字之后可以分成几档——回滚耗时**小于 1 秒**的（改一个运行时可调参数）可以现场回滚；**几秒到几分钟**的（reload、重启一个进程）必须在变更窗口里预留这段时间；**分钟级以上**的（数据库版本回退、批量配置回滚）就不该安排在业务高峰做。更极端的是**不可逆操作**（删数据、扩到缩、重建文件系统），因为它们的回滚耗时不是一个数字，而是「从备份恢复」的完整时长，所以对它们只有一条纪律：动手前先有备份与演练过的恢复路径。

本机实测的一轮如下：把 `vm.swappiness` 从 60 改成 10 用了 **3 毫秒**，从 10 改回 60 用了 **4 毫秒**。由于这个量级说明「退路够快」在这条变更上是成立的，所以本条的三个条件都满足；但如果换成一次数据库版本升级，则回滚可能是分钟级甚至小时级，那时的结论完全不同。

**结论**：回滚方案是一个被验证过的动作，而不是一句写在纸上的命令。出处：同章《原理：可恢复性的语言》（回滚与恢复验收的口径）、同章《原理：不可逆性与影响面》（哪些动作用户不可逆），相关取舍见同章《体系：一次生产变更的一生》。

## 6. 「就改一行，不用提单」

**场景**：为了让移动端少登几次，一位同事直接在生产的 DNS 服务上把 `token_ttl` 从 3600 改成 7200，理由是「就改一行，走流程要两天」。

**常见误判**：用**改动量**衡量风险。这个判断看起来成立，因为「一行」听起来确实很小；由于改动的行数少，所以风险被默认成也小。

**判据**：

- **是什么**：变更分级看的是**影响面**（也叫爆炸半径，blast radius），而不是 diff 的行数。因为一行 `token_ttl` 改的是全部调用方的凭证有效期，一行 DNS 记录改的是所有解析到该名字的客户端（而且它受 TTL（Time To Live，缓存有效期）约束，未过期前既不能完全生效也不能干净回滚），一行防火墙规则改的是整段网络的连通性，所以这三者都不能按行数分级。
- **单位**：改动量用行数；影响面用**受影响的用户数、实例数、调用方数量**，以及**回滚窗口的时长（秒或分钟）**。
- **判据**：要看能不能一句话说清「最坏情况下谁受影响、影响多久」；若说不清，则它就不属于可以自己动手的那一类。
- **与谁同看**：要与冻结期一起看，因为大促、财报、节假日期间，即使一行也要走紧急变更通道。
- **转向哪一步**：若影响面判不清，则转向「按重大变更提单」，而不是转向「先改了再说」。
- **补充的对照**：三类变更对应不同的授权与执行方式——**标准变更**是低风险、可重复、有既定流程的（例如按 Runbook 重启一个无状态实例）；**重大变更**要单独审批、单独窗口、有回滚方案；**紧急变更**是为了止损而走的快速通道，因此**事后必须补记录**。由于分级的依据始终是影响面，而不是「我有多急」，所以紧急通道解决的是审批速度，它不改变影响面的大小。

**结论**：分级的分母是影响面，而不是改动量，因为一行凭证有效期可以覆盖全部业务。出处：ITIL 变更分类（标准、重大与紧急三类对应不同的授权层级）、ITIL 冻结期概念。

## 7. 「重启服务就等于回滚了」

**场景**：一次配置变更之后接口开始报错，执行人执行了 `systemctl restart app`，报错随即消失，于是结案。三天后重启整机，同样的报错再次出现。

**常见误判**：把「重启」当成「回到过去」。它有两种典型形态：① **重启服务**——由于配置文件还是新的、数据也已经写下了，所以重启只是让进程重新读了一遍**新的**配置；② **换回文件但不 reload**——文件确实换回旧版了，但进程内存里仍然是变更前加载的那一份**旧运行时值**，因此看起来「文件对了」。这两种形态之所以看起来都成立，是因为重启之后表面上确实恢复了正常。

**判据**：

- **是什么**：真正的回滚要同时撤销两样东西，也就是**持久化文件**与**运行时值**；由于只做一半的话，任何一次重启或进程回收都会让变更「复活」，所以两样必须一起核对。
- **单位**：进程启动时间是**带时区的绝对时刻**；`sysctl -n` 的读数是无量纲数值。
- **判据**：要核对 `systemctl show <unit> -p ExecMainStartTimestamp` 的时间戳是否**新于**你执行回滚的时刻（这证明进程真的被重新加载过），并且核对 `sysctl -n <键>` 是否等于旧值。
- **与谁同看**：要与文件内容的哈希或 `diff` 结果一起看，因为文件对了而运行时值不对时，说明少了一步 reload。
- **转向哪一步**：若两样都核对通过，则转向验收观察；若任一不符，则回到「补齐另一半」。

还有一个更隐蔽的层面：如果这次变更**动过数据**（改过表结构、迁移过目录、重写过文件格式），那么文件回滚与进程重载都换不回数据本身，因为数据层的回滚要回到备份或快照，而且必须在**停止写入之后**做，否则恢复过程中的新写入会把状态再次搅乱。所以回滚的完整定义是三件事：**文件、运行时、数据**；由于只做前两件而变更动过数据，等于没回滚。

```bash
systemctl show app -p ExecMainStartTimestamp # 验证：进程是否在回滚之后重新加载过
sysctl -n vm.swappiness                      # 验证：运行时值是否回到旧值
```

**结论**：回滚是「文件 + 运行时」两件事，而重启只是其中一种施加方式，它本身不构成回滚。出处：`man 1 systemctl`（`show` 的属性集合）、`man 8 sysctl`。

## 8. 「配了 VIP 就是高可用」

**场景**：架构评审上有人说「我们做了高可用，两个节点配了 VIP」，而当被问到「拔掉一台之后业务还剩多少」时，回答是「应该没问题吧」。

**常见误判**：把「配置项存在」当作「故障域已被消除」。这个判断看起来成立，因为 VIP（Virtual IP，虚拟 IP，可以在两台机器之间漂移的地址）确实是高可用的常见组件；由于这个组件在配置里存在，所以结论被提前下了。

**判据**：

- **是什么**：高可用的判据是**故障注入后的剩余服务能力**，也就是「拔掉一台，业务还剩多少」。
- **单位**：剩余能力用**请求成功率（百分比）与吞吐（每秒请求数）**；切换耗时用**秒**，因此要与 RTO 比较。
- **判据**：`ip -brief addr` 里除了回环 `lo` 与物理网卡之外，**还存在一个不属于任何物理网卡的地址**（那才是 VIP）；`ss -lnt` 里同一端口在多个地址上被监听；`systemctl is-active keepalived` 或 `haproxy` 是 `active`；`/proc/mdstat` 有无阵列。
- **与谁同看**：要与容量余量一起看，因为一台挂了、另一台接得住的前提是它平时的余量够。
- **转向哪一步**：缺哪一项就转向补哪一项；同时，若 VIP 存在但没有真实演练过一次切换，则仍然不算达标。
- **补充的量化尺度**：把「还剩多少」翻成可比较的数字之后可以这样判定——**N+1 余量**的意思是任意单台故障后，剩余容量仍能承载峰值，例如平时 4 台各跑 25%，拔掉 1 台后 3 台各跑 33%，这时业务不受影响；反之，如果 4 台平时各跑 40%，那么拔掉 1 台后剩下的 3 台要跑到 53%，抖动与超时会立刻出现。另外高可用还有一个常被忽略的前提：**冗余必须跨故障域**，因为两台机器如果共用同一个机柜电源、同一台接入交换机，或者互为同一存储的客户端，那么它们不是两份保障，而是一份保障加一个假象。健康检查的准确性也要一起看：判得太松会把流量发给坏后端，判得太严会把健康后端踢出去。

本机实测的结果是反面对照，因为这台实验机上什么都没有：`ip -brief addr` 只有 `lo` 与 `ens33`，**没有任何 VIP**；`ss -lnt` 对外只有 `0.0.0.0:22` 与 `[::]:22` 两条监听，而且是**同一个 `sshd` 进程（`ss -lntp` 显示 `pid 1348`）**；`/proc/mdstat` 没有阵列；`systemctl list-units` 里没有 `keepalived` 或 `haproxy` 单元。所以在这台机器上「拔掉一台」就是全部没了，因为它连一台可拔的第二台都没有。

**结论**：VIP 是要验证的中间件，而不是结论，因为结论只能来自一次真实的故障切换演练。出处：`man 5 keepalived.conf`。

## 9. 「备份就是快照，快照就是副本，一回事」

**场景**：容量规划的会上，有人提议「存储上已经开了快照，备份系统可以砍掉了」；另一个人接着说「我们还有实时复制，误删也能顶住」。

**常见误判**：把这三个词当成同义词。这个判断看起来成立，因为三者在「有一份数据在别处」这件事上给人的感觉一样；由于感觉相同，所以它们各自防住的失效模式被混成了一件。

**判据**：三者的边界要用三个问题分开问。

- **是什么**：关键差别在**独立性与方向性**——快照是从属的时点视图，副本是同向的实时镜像，归档是离线的历史留存。
- **单位**：快照的占用用**百分比或 MiB**（`data_percent`），副本的代价用**带宽（MiB/秒）**，归档的代价用**介质容量（GiB）与恢复耗时（秒或小时）**。
- **判据**：判据见下面三个问题各自的字段与命令，因为三问全部有明确答案才算「有保护」。
- **与谁同看**：要与 RTO 和 RPO（Recovery Point Objective，恢复点目标，即能容忍丢多少数据）一起看，因为快照防误操作、副本防单机故障、归档防长期丢失，它们各自对应不同的指标。
- **转向哪一步**：若三问里有任何一问答不上来，则转向补那一种能力，而不是拿现有的一种去替代。

| 要回答的问题 | 用来判断的命令 | 命令读到什么 | 读到之后核对哪一项 |
| --- | --- | --- | --- |
| 存储挂了它还在吗 | `lvs -o name,attr,data_percent` 与 `findmnt -o TARGET,SOURCE,FSTYPE` | 前者给出卷的属性与 `Data%`，后者给出挂载点对应的源设备 | 因为快照依赖同一套存储、同一个卷组，所以源与快照同源时它防不了存储故障，也不跨机房 |
| 误删会同步过去吗 | 副本链路的同步方向配置 | 它给出写入方向是单向还是双向 | 因为副本是**实时**的，所以误删、误改、勒索加密都会原样同步到副本上，它不是历史版本 |
| 能恢复出来吗、要多久 | 归档介质的取回流程与恢复耗时计时 | 它给出介质位置与一次恢复的实测耗时 | 因为归档是离线介质上的长期留存，所以恢复需要先找回介质再解包，恢复速度和恢复粒度通常最差 |

补充一条最容易被忽略的事实：**快照合并是破坏性的**，因为 `lvconvert --merge` 会把源卷改回快照那一刻，所以快照建立之后的正常写入会全部丢掉。本机实测的另一个关键形态是**快照写满就失效**：LVM（Logical Volume Manager，逻辑卷管理器）快照的 `data_percent` 从 0.01 一路涨到 **75.31** 之后写满，内核直接打印 `device-mapper: snapshots: Invalidating snapshot: Unable to allocate exception.`，因此在那一刻回滚能力归零。

```bash
lvs -o name,attr,data_percent               # 验证：Data% 与 Attr 里的失效标记 I
findmnt -o TARGET,SOURCE,FSTYPE             # 验证：快照与源是否同一块盘、同一个存储
```

三个问题的答案也决定了**容量与成本的算法不同**：快照按「变化量 × 保留时长」估容量，所以 `data_percent` 是必须监控的字段，而不是配了就能忘；副本按「实时写入的带宽 × 距离」估网络；归档按「数据总量 ÷ 压缩比 × 保留份数」估介质，而且必须把恢复耗时算进 RTO，因为一份要 6 小时才能取回的归档撑不住 30 分钟的 RTO。

**结论**：备份、快照与副本各自防的是不同的失效模式，因此谁都不能替代谁，而三问答不全就等于没有保护。出处：`man 8 lvcreate`（快照的 `--size` 与写满即失效）、`man 1 rsync`（副本与增量同步的语义）。

## 10. 「一批里部分成功，最坏也就是失败」

**场景**：100 台机器上改同一个参数，脚本跑到第 37 台时网络抖动中断。运维说「也就 36 台改了，最坏的情况就当没做」。

**常见误判**：把「部分成功」当成「折中的成功」。这个判断看起来成立，因为改了的那些确实改成了；由于改动本身没有报错，所以这批操作被当成了接近失败但可以忽略的状态。

**判据**：

- **是什么**：部分成功制造的是**不一致状态**，也就是同一批里新旧混杂；由于这种混杂，故障表现从「这台不行」变成「有时好有时坏」，也就是最难定位的间歇性失败。
- **单位**：并发批量用**完成耗时（毫秒或秒）**与**同时操作的目标数**；状态一致性用「新旧机器各有几台」的计数。
- **判据**：要先数出「完全旧」「改了一半」「改完没 reload」三类各有多少台，然后再决定动作。
- **与谁同看**：要与脚本的幂等性一起看，因为幂等（idempotent，同一操作执行一次和执行多次结果相同）是同一份清单重跑的前提。
- **转向哪一步**：处置有三条路径——若全部处于旧状态，则修好根因后用**同一份清单**重跑（脚本必须幂等）；若处于混合状态，则先把已改的退回旧状态，让整体一致，再整批重来；若无法判断状态，则停手，逐台人工核对。

本机实测的并发代价对照如下：5 次服务 reload 串行执行用了 **5100 毫秒**，而用 `xargs -P 4` 提到 4 路并发后是 **2058 毫秒**（因为每次 reload 固定约 1 秒，所以理论上限就是 1 秒多）。两次运行的输出都是 5 行 `is-active=active`，因此看上去完全一样；但**并发更快，失败时的可定位性更差**，因为并发输出交错、顺序不可复现，所以排查「哪一台没成功」比串行难得多。

```bash
xargs -P 4 -n 1 -a hosts.txt ...            # 验证：并发提高速度，同时牺牲输出顺序
systemctl is-active <unit>                  # 验证：逐台核对状态，不要只看汇总行
```

并发的三个附带代价要一起记住：由于 `xargs -P` 只控制并行度，它**不做重试、不保证输出顺序**，而且它的退出码只反映「有没有命令以非零退出」，很难对应到具体哪一台；所以并发批量必须有**逐台的结果落盘**（每台一行「主机名 + 期望值 + 实际值」），否则事后无法回答「第 37 台现在是什么状态」。这也是为什么「部分成功」的处置要放在事后做，而不是当场猜。

**结论**：部分成功比全失败危险，因为它把「失败」变成了「间歇性失败」，所以处置顺序是先让状态一致，再整批重来。出处：`man 1 xargs`（`-P` 的并发语义）、`man 1 bash`（`set -euo pipefail` 与 `trap` 保证中断时不留半成品）。

## 11. 「`systemctl is-active` 是 active，服务就是好的」

**场景**：线上服务偶发 502，值班的人跑了一条 `systemctl is-active app` 并得到 `active`，于是在群里回复「服务是好的，往上游查」。

**常见误判**：用单一字段回答「服务健不健康」。这个判断看起来成立，因为 `is-active` 的输出确实只有 `active` 与 `inactive` 这两种最常见的取值；由于这次拿到的是 `active`，所以它被当成了健康。

**判据**：

- **是什么**：`ActiveState` 只说明「unit 没有被判定为失败」；由于它不描述进程是否在反复重建，所以要看三个字段一起——`ActiveState`（粗粒度状态）、`SubState`（细粒度子状态）、`NRestarts`（**累计重启次数**，需要差分）。
- **单位**：`NRestarts` 是**累计次数**，因此必须取两次读数之间的差值，而只看单点没有意义。
- **判据**：若 `SubState` 长期停在 `auto-restart`、且 `NRestarts` 在涨，则这就是「崩溃重启循环」的假健康，因为每次探活都恰好撞在服务起来的窗口里，所以探活永远成功。
- **与谁同看**：要与 `ExecMainStartTimestamp` 一起看，因为启动时间不断刷新说明进程一直在被重建。
- **转向哪一步**：一旦出现重启循环，就转向 `journalctl -u <unit>` 看退出原因，而不是继续往上游查。

本机实测的对照是健康态：`systemctl show ssh` 给出 `ActiveState=active`、`SubState=running`、`NRestarts=0`，因此这三个字段一致指向健康。

```bash
systemctl show app -p ActiveState -p SubState -p NRestarts -p ExecMainStartTimestamp
                                            # 验证：三个字段一起读，缺一个就会漏掉重启循环
```

判据的时间维度也要说清：**「健康」是一段时间内的稳定，而不是某一刻的快照**。因此正确做法是隔一段时间读两次，比较 `NRestarts` 与 `ExecMainStartTimestamp` 有没有变化——由于两个都不变才算稳定，所以只看一次 `active` 与看一次 `free` 的可靠性是同一量级的。另外要知道 `Restart=` 策略决定了「循环」的形状：配置 `Restart=always` 时，重启之间的间隔由 `RestartSec` 决定（默认 100 毫秒），而 `StartLimitIntervalSec` 与 `StartLimitBurst` 决定「多久之内重启多少次就放弃」；由于放弃之后也会体现在 `ActiveState` 上（变成 `failed`），所以**在那之前的一长段里它一直显示 `active`**，这正是「假健康」能持续存在的原因。因此判断循环要靠时间序列上的 `NRestarts` 差值，不能靠单点状态。

**结论**：`active` 是必要条件，而判健康的充分证据是「`SubState` 稳定在 `running`，并且 `NRestarts` 不再增长」。出处：`man 1 systemctl`（`is-active`、`show` 的属性与 `SubState` 的取值）、`man 5 systemd.service`（重启策略）。

## 12. 「不是 root，所以读不到这些参数，跳过就行」

**场景**：一位同事用普通账号 `realtyz` 跑 `sysctl --system` 做巡检，输出里刷了 17 条 `sysctl: permission denied on key "…", ignoring`；由于命令退出码是 0，所以脚本把这次巡检汇总成「参数巡检通过」。

**常见误判**：把「权限不足」当成「环境差异」。这个判断看起来成立，因为普通用户确实读不到某些内核参数，而这本来很正常；由于这种差异很常见，所以被跳过的键被当成了不必在意的部分。

**判据**：

- **是什么**：被拒的键是**被跳过的键**，而不是「读到了但值不同」的键；由于跳过意味着这次巡检在那些键上完全没有结论，所以它不能被算进覆盖范围。
- **单位**：提示条数是**计数**；参数条数是**行数**；由于两者口径不同，所以要能对上差值。
- **判据**：要先数提示条数，再用**同一条键**做 `sysctl -n` 单键复验；若单键读得到、而 `--system` 读不到，则说明这是批量路径的权限问题，不是值的问题。
- **与谁同看**：要与运行身份一起看（`id -u`），并把「哪些键被跳过」列成清单，而不是把它藏进汇总的通过里。
- **转向哪一步**：若要完整巡检，则转向提权执行或只读单键读；同时不能把「跳过了 17 条」记成「检查了 17 条」。

本机实测的差值如下：root 下 `sysctl --system` 打出 **0** 条权限提示；`realtyz` 下打出 **17** 条，退出码仍是 0。`sysctl -a` 的行数对照是 root **1018** 行、`realtyz` **1004** 行，因此少的 14 行就是被静默跳过的那部分可见性缺口。

```bash
sysctl --system 2>&1 | grep -c 'permission denied'   # 验证：数一数被跳过了几条
sysctl -n net.core.somaxconn                         # 验证：用同一条键单点复验，确认是权限不是值
```

还要分清一件事：**「读不到」与「读到但值不同」在输出形态上完全不同**，因为前者带 `permission denied … ignoring` 的明确文本，而后者只是数字不一样。巡检报告里必须把这两种分开写，因为它们的处置动作一个是「提权重跑」，另一个是「查覆盖点」。另一个容易忽略的细节是最小权限本身：由于单键只读（`sysctl -n`）与批量应用（`--system`）需要的权限不同，所以把巡检脚本降权运行时，**它丢掉的不是精度而是覆盖面**，也就是那 14 行差量里的键在这次巡检里等于根本不存在。

**结论**：权限拒绝是一种「没有结论」，因此必须计数并单独复验，不能混进通过里。出处：`man 8 sysctl`、`man 5 sysctl.d`、`man 8 systemd-sysctl`。

## 13. 「`systemctl show` 没输出，说明这项没有限制」

**场景**：为了评估日志会不会撑爆磁盘，有人执行 `systemctl show systemd-journald -p SystemMaxUse`，输出为空，于是判定「日志容量没有上限，可以放心写」。

**常见误判**：把空输出读成「该属性为空或无限制」。这个判断看起来成立，因为 `systemctl show` 对不存在的属性确实什么也不打印；由于空白与「未设置」在字符上无法区分，所以它被读成了没有限制。

**判据**：

- **是什么**：空输出表示**这个键不属于 unit 属性集合**，它不代表「没设置」。因为 journal 的容量与转发行为是 `journald.conf` 的配置项，属于**单元配置**而不是 unit 运行时属性，所以问错了对象就会得到空白。
- **单位**：容量上限用 **MiB**；保留期用**秒或天**；当前占用用 **MiB**。
- **判据**：配置类问题要读 `systemd-analyze cat-config` 的**合并结果**（它会把各目录下的同名配置按优先级合并后打印），而不是问 unit 要属性。
- **与谁同看**：要与 `journalctl --disk-usage` 的当前占用一起看，因为上限是策略、占用是事实，所以两个都要有。
- **转向哪一步**：要确认某项有没有被限制，就要转向 `systemd-analyze cat-config <配置名>` 找设置点，再用运行时读数复验。

本机实测的当前占用是 `journalctl --disk-usage` = **20.7 MiB**（同一天更早的基线是 53.9 MiB，因为中间有别的实验在写日志与回收，所以这个数字会变，**以现场为准**）。

```bash
systemd-analyze cat-config systemd/journald.conf   # 验证：合并后的最终配置（含各目录优先级）
journalctl --disk-usage                            # 验证：当前实际占用，与上限一起看
```

要区分「属性不存在」与「属性存在但值为空」时，还有一个便宜的办法：对同一个 unit 查一个一定存在的属性做对照（例如 `-p ActiveState`）；若它有输出、而你要找的键没有，则说明是键名不属于该集合，而不是这条命令坏了。journal 的容量与保留期由 `journald.conf` 的 `SystemMaxUse`（总量上限，单位 MiB）与 `MaxRetentionSec`（保留时长，单位秒）管，因此它们属于 journald 自己的配置域；**它们不会出现在任何 unit 的属性列表里，所以 `systemctl show` 对这两个问题永远无话可说。**

**结论**：`show` 的空白回答的是「有没有这个属性」，而不是「有没有这个限制」，所以限制类问题要去读配置文件与合并结果。出处：`man 1 systemctl`（`show` 的属性来源）、`man 5 journald.conf`。

## 14. 「`df` 满了就删日志」

**场景**：线上告警根分区 100%，值班的人登上去看到 `df -h` 已用 41 MiB、而 `du -sh` 只有 20 KiB，于是准备 `rm -rf` 一批日志腾空间。

**常见误判**：把 `df` 与 `du` 当成同一件事，并把「日志」默认成元凶。这个判断看起来成立，因为日志确实是最常见的增长型目录；由于两者都报同一个文件系统的占用，所以它们的差值被当成了统计误差。

**判据**：`df` 与 `du` 不一致有四类成因，因此要先分类再动手。

- **是什么**：`df` 读的是文件系统的**块分配计数**（含被持有却已删除的块与保留块），而 `du` 走的是**目录树**；由于两者口径不同，所以差异本身就是线索。
- **单位**：容量与缺口用 **MiB**，inode 用**个数**，保留块比例用**百分比**（ext4 默认给 root 留 5%）。
- **判据**：要先算 `df` 与 `du` 的缺口大小，再去找「与缺口同量级」的那一类成因；若量级对不上，则不要顺着这条线查下去。
- **与谁同看**：要与 `lsof +L1` 的 `SIZE/OFF`、`findmnt` 的挂载关系、`df -i`、配额报表四者交叉验证。
- **转向哪一步**：若确认是「被持有」，则转向让进程重新打开文件或先抢救内容；若确认是「挂载覆盖」，则转向从正确的挂载点重新统计。

| 成因 | 用来判断的命令 | 命令读到什么 | 读到之后核对哪一项 |
| --- | --- | --- | --- |
| 已删除但被进程持有 | `lsof +L1` | 它列出链接数为 0 的打开文件与各自的 `SIZE/OFF` | 因为块仍被进程持有，所以 `SIZE/OFF` 应当与容量缺口同量级 |
| 挂载覆盖 | `findmnt` | 它给出挂载点与源设备的对应关系 | 因为上层目录被另一个挂载点遮住，所以 `du` 看不见被遮的内容 |
| inode 或 ext4 保留块 | `df -i` 与 `tune2fs -l` | 前者给出 inode 用量，后者给出保留块比例 | 因为保留块参与 `df` 的计算却不被 `du` 统计，所以两者会出现缺口 |
| 配额 | 配额报表 | 它给出各用户或各项目的额度与已用 | 因为报错文本是 `Disk quota exceeded`，所以它与容量无关 |

本机实测的对照如下（这是在 128 MiB 靶盘上做的一轮）：删掉被进程持有的 40 MiB 文件之后，`df -h` 仍然显示已用 **41 MiB**，而 `du -sh` 只有 **20 KiB**；因此**同一时刻两个工具对同一个文件系统给出两个数量级的答案**，直到持有它的进程退出，那 40 MiB 才回到可用空间。**注意这是 loop 靶盘上的演练，所以绝对数值不代表你的机器，能迁移的是「`lsof +L1` 的 `SIZE/OFF` 与缺口对得上」这条判据。**

关于第一反应，有三样东西不该先删，因为删它们能把盘腾出来，但代价是数据丢失或排查现场消失：备份文件、数据库数据目录、正在写的日志。

```bash
df -h; df -i                               # 验证：容量与 inode 两个口径
lsof +L1                                   # 验证：已删除但仍被持有的文件
findmnt -o TARGET,SOURCE,FSTYPE            # 验证：挂载覆盖
```

关于 `lsof +L1` 有一个必须写清的边界：它的 `+L1` 是「链接数小于 1」，也就是**只列出已经没有任何目录项指向的打开文件**；因此**没有输出不能百分百排除被持有**，因为如果文件还有别的硬链接名存在，它就不在 `+L1` 的输出里，而空间照样被占。若要查这类情况，就要看 `lsof` 的完整输出里 `NLINK` 列与 `SIZE/OFF` 的乘积，或者直接按 `df` 与 `du` 的缺口去比对。另外**保留块**（ext4 默认留 5% 给 root）会参与 `df` 的计算但不被 `du` 统计，而 `tune2fs -l` 能读到比例，因此它也是「`df` 说满了、`du` 说没满」的成因之一。

**结论**：`df` 满的第一反应是分类取证，而不是删日志，因为四类成因各有各的判据。出处：`man 1 lsof`（`+L1` 列出链接数为 0 的打开文件）、`man 8 findmnt`、`man 8 tune2fs`、`man 1 df`。

## 15. 「`df -h` 还有空间，肯定写得进去」

**场景**：应用报 `No space left on device`，运维看到 `df -h` 只用了 1%，于是判定「磁盘明明有空间，是应用的问题」。

**常见误判**：用一个口径的结论去否定另一个资源的耗尽。这个判断看起来成立，因为「有空间」与「写得进去」在直觉上是同一件事；由于 `df -h` 报的是 1%，所以它被用来否定了整个报错。

**判据**：

- **是什么**：`No space left on device` 只说明「某种资源用完了」，因为**容量、inode、保留块、配额**都会报同一句话。
- **单位**：inode 用**个数**（总数、已用、已用百分比）；块容量用 **MiB**；由于两者单位不同，所以不能互相推断。
- **判据**：`df -i` 与 `df -h` **必须一起看**；若 `df -i` 到 100% 而 `df -h` 只有个位数，则问题就是 inode。
- **与谁同看**：要与小文件密度一起看，因为邮件队列、缓存目录、会话文件这类「多而小」的写入最先耗尽 inode。
- **转向哪一步**：确认是 inode 耗尽之后，转向删小文件或重建文件系统（`mkfs` 时用 `-i` 或 `-N` 控制 inode 数量）；由于这类操作属于不可逆范畴，所以只在可快照的实验机上做。

本机实测（这是用 `mkfs.ext4 -N 32` 造出的靶文件系统）：空盘时 `df -i` 是 `32  11  21  35%`；`touch` 40 个文件之后变成 `32  32  0  100%`，而同一时刻 `df -h` 是 `24M  24K  22M  1%`；再 `touch` 一个新文件就直接报 `touch: cannot touch '…/extra': No space left on device`（退出码 1）。

```bash
df -i /path                                # 验证：inode 用量，与 df -h 一起读
df -h /path                                # 验证：块容量用量
```

inode 之所以值得单独建监控项，是因为它的**规划发生在建文件系统那一刻，事后不能扩容**——由于 `mkfs` 时用 `-N` 或 `-i` 定下了总数，所以跑起来之后一个也加不了（只能重建文件系统并迁移数据，而那属于不可逆操作）。所以小文件密集型的场景（邮件队列、会话文件、缓存碎块、日志按条切分）必须在建盘时就按「预计文件数 ÷ 0.8」留出余量；同时容量告警也要**有 inode 告警**，因为只监控百分比容量的话，这类故障永远不会提前报警。

**结论**：`df -h` 有空间不能推出「写得进去」，而 `No space left on device` 要先分四类。出处：`man 1 df`（`-i` 的口径）、`man 8 tune2fs`（保留块与 inode 数量）。

## 16. 「参数改了不生效，是内核的问题，再改一次」

**场景**：为了支持更高的并发连接，同事在 `/etc/sysctl.d/99-tuning.conf` 里写了 `net.core.somaxconn = 8192`；执行 `sysctl -p` 之后，`sysctl -n` 读到的还是旧值，于是他的第二反应是「再执行一遍 `sysctl --system`」。

**常见误判**：把「文件写了、命令跑了」当作「值应该变了」。这个判断看起来成立，因为 `-p` 与 `--system` 的输出看起来一切正常；由于没有报错，所以没生效被归因成了内核不听话。

**判据**：第一步要查加载顺序，而不是再改一次。

- **是什么**：运行时值是「合并后最后一个写入点」的结果，而不是某一个文件的内容；因为同名键的先后由加载顺序决定，所以先要判断谁最后写。
- **单位**：键值本身没有单位，或者随键而定（`net.core.somaxconn` 是**个数**，`vm.swappiness` 是无量纲权重）；文件计数用**个数**。
- **判据**：`sysctl -n <键>` 得到事实值，`grep -rn` 得到全部候选写入点；若两者按加载顺序对齐后能解释事实值，则结论成立，而解释不通就说明还有没找到的写入点（例如内核命令行或模块参数）。
- **与谁同看**：要与 `sysctl --system` 的施加过程一起看，确认没有被拒的键。
- **转向哪一步**：确认了覆盖点之后，就要转向在**最后加载的位置**写入，而不是反复改最早的那个文件。

这里必须分开两套机制，因为它们读取的文件集合不同，而**这是本库原先写错、现已实测更正的一处**。

| 机制 | 谁在读 | 读什么 | 什么时候跑 |
| --- | --- | --- | --- |
| 开机持久化 | `systemd-sysctl.service`（其可执行文件是 `/usr/lib/systemd/systemd-sysctl`） | 它读 `/etc/sysctl.d/`、`/run/sysctl.d/`、`/usr/local/lib/sysctl.d/`、`/usr/lib/sysctl.d/` 下的 `*.conf` | 它在每次开机早期运行 |
| 手工重放 | procps 提供的 `sysctl --system` | 它读上面那些 `.conf`，**再加 `/etc/sysctl.conf`（排在所有 `.d` 之后）** | 它在你敲下这条命令的时候运行 |

由于两套机制的合并规则是同一条，所以它们的差别只在读取集上：**文件按文件名字典序排序**，而排序不按目录，因此数字前缀决定先后（`10-` 早于 `50-` 早于 `99-`）；**不同名的文件按名字定胜负**，因此同名的键由名字更靠后的文件覆盖；**同名文件**则以高优先级目录里的那一份为准，即 `/etc` 优先于 `/run`，而 `/run` 优先于 `/usr`。

本机用 `strace` 实测的**读入顺序**如下（环境是 Ubuntu 24.04.5 / 内核 6.8.0-139 / systemd 255）：先读 `/usr/lib/sysctl.d/10-apparmor.conf`，再读 `/etc/sysctl.d/` 下的 9 个 `10-*.conf`，再读 `/usr/lib/sysctl.d/50-pid-max.conf`，再读 `/usr/lib/sysctl.d/99-protect-links.conf`，最后读 `/etc/sysctl.d/99-sysctl.conf`，共 **14 个文件、17 个键**。同时，`/run/sysctl.d/` 与 `/usr/local/lib/sysctl.d/` 在这台机器上**目录都不存在**。

**`/etc/sysctl.conf` 之所以"最后生效"，靠的是一条软链而不是路径特例**：本机实测 `/etc/sysctl.d/99-sysctl.conf -> ../sysctl.conf`（14 字节的符号链接）。由于 `systemd-sysctl` 的读取集里只有 `.d` 目录，所以它读到的其实是这条软链；而软链的名字是 `99-`，字典序排在最后，因此里面的值盖掉前面所有文件。**一旦删掉这条软链，`/etc/sysctl.conf` 在所有机制里都不再被读**，那时它在新 Debian 系上就是"睡着的配置文件"。

一条实验判据可以直接在本机复现：往 `/etc/sysctl.d/99-zz-lab-test.conf` 写一个值、再往 `/etc/sysctl.conf` 写另一个值，然后跑一次 `sysctl --system`，本机实测读到的是 **`/etc/sysctl.conf` 的那个值**。这正是"文件写了、命令跑了、值却是别人的"的成因。**上表与这条实测都在实验机上做过并已回滚（回滚判据是：`sysctl -n net.core.somaxconn` 回到 4096、两个测试文件都不存在、`/etc/sysctl.conf` 里没有残留行）；因此这些数值仅示意、不代表你的机器，能迁移的是「先分清是哪套机制在读，再数写入点」这个方法。**

顺带钉死一个容易含糊的点：`net.core.somaxconn` 在**任何一个配置文件里都没有写入点**，而运行时值是 **4096**，它与这台机器上 `/usr/include/x86_64-linux-gnu/bits/socket.h` 里的 `SOMAXCONN` 定义一致，也就是没有人改过它、你读到的就是默认值。**但"默认值"必须现场读**，因为同一个参数在更早的内核里是 128，而凭印象抄默认值是本库点名的高发错误。

```bash
sysctl -n net.core.somaxconn               # 验证：运行时值（第一件事）
grep -rn 'net.core.somaxconn' /etc/sysctl.d /run/sysctl.d /usr/lib/sysctl.d /etc/sysctl.conf
                                           # 验证：找出全部写入点，看谁最后写
sysctl --system 2>&1 | grep -i 'somaxconn'  # 验证：应用过程有没有被拒
```

另有一条**临时改动**的纪律：验证单个文件的效果要用 `sysctl -p <单文件>`，不要图省事跑 `--system`，因为 `--system` 会把别人尚未落成文件的临时改动一并覆盖掉，事后无法归因。

排查顺序的落点也要明确：**`sysctl -n` 给出的是「事实」，`grep -rn` 给出的是「候选」，`sysctl --system` 给出的是「施加过程」**——由于三者的作用不同，所以缺一个就会得到片面的结论。只看运行时值会以为「内核不听话」，只看配置文件会以为「已经改好了」，只看应用过程会漏掉「被后加载的文件盖掉」。当同一个键出现在多个文件里时，**前面那些写入点就成了干扰项**，所以要按加载顺序把全部写入点列出来并排序，而不是找到第一个就停手。

**结论**：改不动的原因是覆盖与顺序，而不是内核顽固，因此判据是「先分清哪套机制在读，再看谁最后写」。出处：`man 5 sysctl.d`（目录优先级与字典序规则）、`man 5 sysctl.conf`（procps 的 `--system` 读取顺序，末读 `/etc/sysctl.conf`）、`man 8 systemd-sysctl`；实测见上（含 `strace` 读入顺序、软链指向、两个写入点的对抗实验与回滚复核）。

## 17. 「归档就是把文件压一下就完事」

**场景**：一次编号 `CHG-20260919-001` 的变更在归档时，执行人把备份目录 `tar czf` 成一个包，放进归档盘，然后在变更单上写「已归档」。

**常见误判**：把「生成了压缩包」当作「归档可用」。这个判断看起来成立，因为文件确实存在、体积也变小了；由于这两件事都符合对归档的直觉，所以三道验收被压成了一道。

**判据**：归档要过**三道验收**，因为缺一道就等于没归档。

- **是什么**：归档可用等于**可读（列得出）加完整（对得上）加可追溯（有指纹）**，而这三者分别对应归档生命周期的三个失效点。
- **单位**：文件大小用**字节或 MiB**，日志规模用**行数**，校验和是 **SHA-256 的 64 位十六进制字符串**（它没有单位）。
- **判据**：`tar tzf` 要能列出全部条目、`diff -r` 的退出码要为 0、`sha256sum` 要有值且与登记值一致。
- **与谁同看**：要与归档目录的 `du -sh` 一起看，因为压缩后的体积与源目录体积的比值决定了容量预算。
- **转向哪一步**：若任何一道不过，则转向重做归档；若三道都过，则转向「把指纹与位置登记进记录」。

| 验收项 | 用来判断的命令 | 命令读到什么 | 读到之后核对哪一项 |
| --- | --- | --- | --- |
| 能列出 | `tar tzf` | 它打印出压缩包内的完整条目清单 | 因为索引与压缩流都要可读才能列出，所以清单完整就证明这一层没坏 |
| 内容一致 | `rsync -a` 到临时目录后再执行 `diff -r` | 它给出源目录与解出的目录之间的逐文件差异 | 因为解出来的东西要和源一样，所以差异必须为空 |
| 有指纹 | `sha256sum` | 它给出 64 位十六进制校验和 | 因为这一份可能被悄悄换过，所以校验和必须登记进记录 |

本机实测的这次归档数据如下：三个配置文件分别是 314、255、1124 **字节**（合计 1693），变更窗口日志是 **207019 字节 / 2184 行**，源目录 `du -sh` 是 **224K**，`tar czf` 之后是 **22195 字节**，`diff -r` 退出码是 **0**，而 `sha256sum` 的值是 `3550eec889ca5d803bf055179e458690a2f4838fb614adf691ba491f1cef0093`。

注意体积构成：因为 **22195 字节里几乎全是那 207019 字节的日志压出来的**，而三个配置文件加起来只有 1693 字节，所以归档的**容量预算要按日志量估**，而不是按配置量估；这条在规划归档盘容量时最容易被低估。

```bash
tar tzf archive.tar.gz                     # 验证：能列清单（第一道）
mkdir -p /tmp/verify && tar xzf archive.tar.gz -C /tmp/verify
diff -r /srv/chg-20260919-001 /tmp/verify/chg-20260919-001
                                           # 验证：内容一致（第二道）
sha256sum archive.tar.gz                   # 验证：指纹并登记（第三道）
```

三道验收各自防的失效不同，所以不能互相替代：**第一道防的是「压缩流本身坏了」**，因为归档盘上的静默位翻转会让 `tar czf` 的产物在解包时才报错；**第二道防的是「打包时漏了文件」**，因为只比对文件个数不够，所以要用 `diff -r` 逐内容比；**第三道防的是「事后被替换」**，因为指纹要与归档文件一起登记在变更单里，否则半年后无从校验。还有一件事不在这三道里，但同样重要：**归档本身要能被找到**，因为目录结构、编号规则、索引文件缺一不可，而一份「有指纹但没人知道在哪」的归档在事故当天等于不存在。

**结论**：归档的验收是「列得出、对得上、有指纹」三件事，而体积预算要按日志估。出处：`man 1 tar`、`man 1 rsync`、`man 1 sha256sum`。

## 18. 「证书到期那天处理也来得及」

**场景**：巡检发现线上域名证书还有 38 天到期，负责人在群里说「还有一个月，到期前处理就行」，同时没有建任何提醒。

**常见误判**：把「是否已过期」当成唯一判据。这个判断看起来成立，因为过期确实才是故障；由于离过期还有 38 天，所以这段时间被当成了安全的余量。

**判据**：

- **是什么**：判据是**剩余天数**，并且要**分级告警**（例如 30 天、14 天、7 天三档），而不是「过期了没」。更要紧的是：**自动续期必须有独立的「续期失败」告警**，因为续期成功是静默的、失败也是静默的，所以没有告警就只能等过期那天发现。
- **单位**：剩余时间是**天**（由 `notAfter` 减去当前时间得到）；链内证书数量是**张数**。
- **判据**：要用 `openssl s_client` 取出线上**实际生效**的证书，用 `openssl x509 -dates` 读 `notAfter`，再算剩余天数；同时用 `grep -c 'BEGIN CERTIFICATE'` 数服务端发出的张数。
- **与谁同看**：要与严格客户端校验一起看，因为 `openssl verify` **不带 `-untrusted`** 时报 `error 20 at 0 depth lookup: unable to get local issuer certificate`，而带上中间证书之后是 `OK`。
- **转向哪一步**：若链不完整，则转向补发中间证书，因为**浏览器能打开不等于严格客户端能连**——Java 与部分 SDK 不会靠 AIA（Authority Information Access，证书里指出中间证书下载位置的字段）自动补链。

本机实测（采集当时）的数据如下：线上实际生效证书的 `notAfter` 是 `Oct 27 22:17:21 2026 GMT`，距采集时刻剩 **38 天**；服务端链内共 **4 张**证书；`openssl verify` 的两种结果如上，也就是**不带 `-untrusted` 就是 `error 20`，带上就是 `OK`**。原始命令与判定逻辑就是下面这几条，而域名与日期请以你现场取到的为准。

还有一个连带的陷阱：`timedatectl` 的 `NTP service: active` **不等于时钟已同步**，因为它只说明 NTP（Network Time Protocol，网络时间协议）客户端在跑。本机实测同一份输出里 `System clock synchronized: no`，也就是时钟并没有同步，而证书有效期判断依赖时钟。

```bash
openssl s_client -connect <host>:443 -servername <host> </dev/null 2>/dev/null \
  | openssl x509 -noout -dates             # 验证：线上实际生效证书的 notAfter
timedatectl                                # 验证：System clock synchronized 这一行
```

按剩余天数分级还要配一条纪律：**告警要按「剩余天数」算，不能按「是否已过期」算**，因为如果告警条件是「过期」，那么从过期到被发现这段时间业务已经在报错了。另外还有一个更隐蔽的漏检形态：若证书检查只查了负载均衡器或某一台边缘节点，而实际有多份证书分布在不同的入口上（不同域名、不同区域、灰度中的新证书），则**只查一处等于漏检**；因此正确做法是把「域名 × 入口」列成清单逐个查，并把每次的 `notAfter` 登记进到期记录。

**结论**：证书要按剩余天数分级告警、要给续期失败单独告警，并要顺手确认时钟真的同步了。出处：`man 1 openssl-s_client`、`man 1 openssl-x509`、`man 1 openssl-verify`、`man 1 timedatectl`、RFC 8555（ACME，Automated Certificate Management Environment，自动证书管理环境）。

## 19. 「日志留着就行，反正能查」

**场景**：审计问「日志保留多久」，回答是「一直留着，都在磁盘上」；而当被问到「时钟同步吗、能证明没被改过吗」时，回答的人答不上来。

**常见误判**：把「文件还在」当作「日志可用」。这个判断看起来成立，因为日志确实每天都在写；由于文件在磁盘上存在，所以它被当成了可用的证据。

**判据**：留存要同时满足三个前提，因为缺一个，日志在需要它的那天就不可用。

- **是什么**：日志可用等于**时间可信加内容未变加尚未到期**；由于时间可信、内容未变与尚未到期分别由时钟同步、写入控制与保留策略保证，所以三者要分别取证。
- **单位**：保留期用**天**，容量上限与当前占用用 **MiB**，而时钟偏差的判据是 `System clock synchronized` 的 `yes` 或 `no`。
- **判据**：`timedatectl` 的同步状态要为 `yes`；集中收集链路要可达；`journalctl --disk-usage` 要与配置的上限一起看。
- **与谁同看**：要与合规要求的天数、安全回溯要求的天数一起看，并取**最严**的那个作为保留期。
- **转向哪一步**：若时钟不同步，则转向修时间源；若没有集中，则转向补收集链路；由于两者都好了才谈保留期与上限，所以它们排在前面。

| 前提 | 用来判断的命令或字段 | 命令读到什么 | 读到之后核对哪一项 |
| --- | --- | --- | --- |
| 时钟同步 | `timedatectl` 的 `System clock synchronized` 一行 | 它给出 `yes` 或 `no`，也就是时钟是否已经同步 | 因为服务在跑不等于同步成功，所以判据只能是这一行，而不是 `systemctl is-active systemd-timesyncd`；一旦时钟错乱，时间线在事后就无法与别的事件对齐 |
| 不可篡改 | 集中收集的目标、日志文件的打开方式与运行身份，必要时上 **WORM（Write Once Read Many，写入后不可修改、不可删除的存储特性）** | 它给出发送端配置、文件权限与运行身份 | 因为本地文件可以被同机的高权限进程改写，所以只有集中到另一台机器、日志文件只追加、运行身份最小权限才算有写入控制 |
| 到期才删 | `journalctl --disk-usage` 与配置的 `SystemMaxUse`、`MaxRetentionSec`，以及 `logrotate` 的份数与周期 | 它给出当前占用、总量上限与保留时长 | 因为删早了丢的是证据、删晚了该字段就达到上限，所以删除时机要由显式的上限与保留期决定 |

保留期要取**三个来源里最严的那个**：合规要求（常见不短于 180 天）、排障需求（7 到 30 天）、安全回溯（越长越好）。容量上限与保留期要**显式写进配置**（journald 用 `SystemMaxUse` 与 `MaxRetentionSec`，文件日志用 `logrotate` 的份数与周期），而不能靠「磁盘还没满」这个观察。

本机实测的数据如下：journal 当前占用 **20.7 MiB**（同日的更早基线是 53.9 MiB），`du -sh /var/log` 共 **27M**，其中 `/var/log/journal` 就占 21M；因此**这台机器上「日志占空间」约等于「journal 占空间」**。这些数值仅示意、不代表你的机器，能迁移的是「先量分布，再定上限与保留期」。

```bash
journalctl --disk-usage                    # 验证：journal 的实际占用
systemd-analyze cat-config systemd/journald.conf
                                           # 验证：容量上限与保留期的最终合并配置
timedatectl                                # 验证：时钟是否真的同步（不是服务是否在跑）
```

还要区分**「收集」与「留存」**：留存时间再长，如果日志留在 200 台机器各自的本地磁盘上、保留策略各不相同，那么审计时问「某个请求三个月前发生了什么」是答不出来的，因为**跨机检索需要先集中**。所以判「日志够不够用」不能只看单机的保留天数，而要看「能不能在需要的时候把多个来源的日志汇到一处、并且时间戳能互相对齐」。集中之后还有两个必须显式写下的数字：**容量上限**（超过就回收最老的）与**保留期**（到期就删），而这两个数字要写进配置，而不是写在值班人员的记忆里。

**结论**：日志能查的前提是「时间可信、内容未被改过、并且还没到删除期」，而这三件事都要落到配置与告警上。出处：`man 5 journald.conf`、`man 8 logrotate`、`man 1 journalctl`、`man 1 timedatectl`。

## 要点自测

**问：备份任务退出码连续一个月是 0，能不能说备份有效？判据是什么？**
答：不能，因为退出码只证明写动作完成。唯一验收是带计时的恢复演练：本机 `rsync --link-dest` 快照的增量 `inc-2` 只有 16 KiB、合计 `du` 仍是 101 MiB，而恢复 0.42 秒、`diff -r` 无差异——由于它**有耗时、有对照**，所以这一次才算通过。

**问：探活全绿、监控无告警，为什么还可能变更失败？**
答：因为探活与告警都可能有盲区。本机实测 `nstat -az TcpExtListenOverflows` 从 0 涨到 10（连接因监听队列满被丢），而同一时段探活始终 200，所以**累计计数器的差值**才是探活看不见的那一层。

**问：程序退出码 0，为什么不能当作「命令生效」？**
答：因为退出码描述的是进程怎么结束的。本机 `smartctl -i` 打印 `SMART support is: Unavailable` 仍返回 0；`realtyz` 跑 `sysctl --system` 打印 17 条 `permission denied on key "…", ignoring` 也仍返回 0。所以生效与否要看运行时口径（`sysctl -n`、`systemctl show`、`cat /proc/...`）。

**问：回滚命令写在变更单上，还缺什么？**
答：还缺三个隐含条件，也就是退路还在（原件或旧值）、退路在实验机上跑过一次、耗时小于 RTO。本机把 `vm.swappiness` 从 60 改成 10 用了 3 毫秒、回滚用了 4 毫秒；一旦换成小时级的操作，写在纸上的命令就不构成方案。

**问：`systemctl is-active` 是 `active`，为什么还要看别的字段？**
答：因为 `ActiveState` 只说明 unit 没被判失败。要三个一起看：`ActiveState`、`SubState`、`NRestarts`（累计，需差分）。由于 `SubState` 停在 `auto-restart` 且 `NRestarts` 增长就是崩溃重启循环的假健康，所以要靠时间序列判断；本机 `ssh` 的健康态是 active / running / NRestarts=0。

**问：`df -h` 显示还有 99% 空闲，为什么写入报 `No space left on device`？**
答：因为 `No space left on device` 是四类资源共用的报错——容量、inode、ext4 保留块、配额。本机 `mkfs.ext4 -N 32` 的靶盘上 `df -i` 到 100% 而 `df -h` 只有 1%，所以 `df -i` 必须与 `df -h` 一起读。

**问：参数改了不生效，第一步做什么？**
答：第一步是查加载顺序与写入点，而不是再改一次。先要分清是哪套机制在读：开机时 `systemd-sysctl.service` 只读四个 `.d` 目录，而手工重放是 procps 的 `sysctl --system`（它在此之上**末读 `/etc/sysctl.conf`**）。由于两套机制的合并规则相同，所以规律是：所有 `.conf` 按文件名字典序排序、名字靠后的覆盖靠前的，而同名文件以 `/etc` 优先于 `/run`、`/run` 优先于 `/usr`。`/etc/sysctl.conf` 之所以最后生效，是因为它通常被软链成 `/etc/sysctl.d/99-sysctl.conf`（本机实测指向 `../sysctl.conf`）。本机实测读到 14 个文件 17 个键，而 `net.core.somaxconn` 没有任何写入点，运行时值 4096 与这台机器内核头文件里的 `SOMAXCONN` 一致；因此**没有写入点是可以迁移的结论，而 4096 这个数字要现场取**（更早的内核里它是 128）。

**问：归档做完，凭什么说它可用？**
答：凭三道验收——`tar tzf` 能列清单、`rsync -a` 后 `diff -r` 无差异、`sha256sum` 有值并登记。本机 `CHG-20260919-001` 的归档是 22195 字节、日志占 207019 字节、`diff -r` 退出码 0、指纹已登记；同时**体积预算要按日志估**。

**问：证书还有 38 天，算不算安全？**
答：要按剩余天数分级告警（30、14、7 天三档），并且给自动续期配一条独立的失败告警。本机 `www.example.com` 剩 38 天、链内 4 张；因为 `openssl verify` 不带 `-untrusted` 时报 `error 20 … unable to get local issuer certificate`、带上才是 `OK`，所以**浏览器能打开不等于严格客户端能连**。

**问：第一反应不要做什么？**
答：不要用退出码代替生效验证；不要把「任务成功」当成「备份有效」；不要在没有第二台机器的前提下说「我们做了高可用」；不要在状态不清的批次上继续往下做；不要看到 `df` 满就先删日志；不要重复改同一个参数文件；不要把「快照」「副本」「备份」当同义词；不要用 `is-active` 一个字段结束服务健康检查。
