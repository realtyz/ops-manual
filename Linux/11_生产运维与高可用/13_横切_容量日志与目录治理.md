# 横切：容量、日志与目录治理

> [!cite] 参考资料
> `man 1 df`、`man 1 du`、`man 1 lsof`（`+L1`）、`man 8 findmnt`、`man 8 lsblk`、`man 8 lvextend`（`-r`）、`man 8 pvresize`、`man 8 resize2fs`、`man 8 xfs_growfs`、`man 1 growpart`、`man 1 journalctl`（`--disk-usage`、`--vacuum-*`）、`man 5 journald.conf`（`SystemMaxUse`、`MaxRetentionSec`）、`man 8 logrotate`、`man 5 logrotate.conf`、`man 8 systemd-tmpfiles`、`man 5 tmpfiles.d`、`man 8 systemd-cgtop`，以及发行版文档中关于日志轮转与临时文件策略的章节。
>
> **实测状态**：实测环境 **Ubuntu 24.04.5 LTS（VMware 虚拟机）/ 内核 `6.8.0-139-generic` / systemd 255（`255.4-1ubuntu8.17`）/ root 可用**。实验机实测数字（2026-09-19 采集，原始输出见 `.labvm/evidence/11b_13_*`）：

> - `journalctl --disk-usage` 报 **20.7 MiB**（同日更早的基线约 **53.9 MiB**——这个数字会随其它实验的 journal 写入与回收变化，**以现场为准**）；`/var/log/journal` 存在（**持久化**）。`du -sh /var/log` **27 MiB**，其中 `/var/log/journal` **21 MiB**、`syslog` 1.3 MiB、`installer` 1.2 MiB、`dpkg.log` 820 KiB、`kern.log` 748 KiB、`audit` 448 KiB。
> - **`lsof +L1` 在实验机上有输出**：`systemd-journald` 持有 1 个已删除的 8 MiB journal 文件——不再是「无输出」。
> - `systemd-tmpfiles` 位于 `/usr/bin/systemd-tmpfiles`；`systemd-tmpfiles --clean --dry-run` 仍报 `unrecognized option '--dry-run'`（systemd 255）。**`/tmp` 落在根文件系统上，不是 tmpfs**（`findmnt /tmp` 显示 `/dev/mapper/ubuntu--vg-ubuntu--lv`）。
> - **故障复现全部在临时 loop 文件系统上做**（不动根分区）：128 MiB 的 loop ext4 被写满到 **100%**，写入报 `No space left on device`；`mkfs.ext4 -N 32` 的 loop 文件系统 inode 用满后 `df -h` 仍显示 1% 却写不进去；删除被进程持有的 40 MiB 文件后 `df` 已用 41 MiB 而 `du` 只有 20 KiB，`lsof +L1` 抓到该句柄，从 `/proc/<pid>/fd/8` 抢救出的文件 **41943040 字节**、`sha256sum` 可校验，杀掉进程后已用从 102 MiB 回落到 62 MiB。
> - **LVM 在线扩容已在 loop 设备上实测**：`lvextend -r -L +400M` 把 LV 从 1.00 GiB 扩到 1.39 GiB 并在线 `resize2fs` 成功，耗时 **0.13 秒**（`df` 从 974 M 变 1.4 G）。

## 0. 30 秒速览

> [!abstract] 这一篇只要记住六句话
> - **`df` 满但 `du` 对不上，先查「已删除但被进程持有」的文件。**
>   - 怎么验证：`lsof +L1` 直接列出这类句柄；把 `/proc/<pid>/fd/<n>` 拷出来或重启那个进程，空间立刻释放。**实验机在 128 MiB 的临时 loop ext4 上复现过**：删掉一个被进程持有的 40 MiB 文件后 `df` 显示已用 41 MiB、`du` 只有 20 KiB，`lsof +L1` 抓到 `sleep … 41943040 … (deleted)`，从 `/proc/<pid>/fd/8` 抢救出 41943040 字节，杀掉进程后已用从 102 MiB 回落到 62 MiB。本机 `/` 上 `lsof +L1` 也有 1 条（`systemd-journald` 持有 8 MiB 已删除 journal 文件）。
> - **「有空间却写不进去」不止一种原因：容量、inode、保留块、配额。**
>   - 证据：`df -h` 看容量、`df -i` 看 inode、`tune2fs -l` 看保留块、配额报表看配额；实验机实测根文件系统 inode 只用了 **6%**（159617 / 3145728），但用 `mkfs.ext4 -N 32` 造的 loop 文件系统 inode 一满（`df -i` 100%）就立刻写不进去，而 `df -h` 仍显示 **1%** 已用。
> - **日志通常是「慢慢涨」的最大户，且它自己就有治理工具。**
>   - 证据：实验机 `/var/log` 共 **27 MiB**，其中 `/var/log/journal` 就占 **21 MiB**（约 78%）——**日志总量的问题，多半是 journald 的问题**；但这台机器上还有 `installer` 1.2 MiB、`dpkg.log` 820 KiB 这类一次性大户，要先量分布再决定改谁。
> - **扩容是「一条链」，不是一条命令：卷 → 分区 → 文件系统，每一步都要验收。**
>   - 怎么验证：`lsblk` 看设备大小变了、`df -h` 看文件系统变大了；**跳过分区或文件系统那一步，就会出现「云盘扩容了但 `df` 没变」**。实验机在 loop 设备上实测 `lvextend -r -L +400M`：LV 1.00 GiB → 1.39 GiB、在线 `resize2fs` 成功、耗时 **0.13 秒**、`df` 从 974 M 变 1.4 G——**`-r` 这一步就是「扩容只做了一半」的那一半**。
> - **临时文件的治理要靠策略，不是靠手工 `rm`。**
>   - 证据：`systemd-tmpfiles` 负责按 `tmpfiles.d` 的策略清理 `/tmp`、`/var/tmp` 等目录；实验机的策略在 `/usr/lib/tmpfiles.d/` 与 `/etc/tmpfiles.d/` 下，用 `systemd-tmpfiles --cat-config` 可以逐条看（`--dry-run` 在 systemd 255 上不被支持）。
> - **容器数据目录的增长有三个来源：镜像、容器日志、卷与构建缓存。**
>   - 怎么验证：分别查镜像列表、容器日志文件、卷与缓存目录；`prune` 类命令会真的删数据，必须在确认「没有需要保留的镜像/卷」之后再执行。**实验机没有 Docker/containerd，这条只给方法与判据，未实测。**

## 1. 算账：先把「谁占了」查清

### 1.1 四个口径一起看

```bash
df -h                                     # 验证：文件系统容量（按文件系统，不按目录）
df -i                                     # 验证：inode 用量（小文件密集时会先用完）
findmnt -o TARGET,SOURCE,FSTYPE,OPTIONS   # 验证：哪个目录挂的是哪个设备（挂载覆盖会骗过 du）
du -sh /var/log/* 2>/dev/null | sort -rh | head -10
                                          # 验证：按目录排序找大户
lsof +L1 2>/dev/null | head -20           # 验证：已删除但仍被进程持有的文件
```

实验机上的真实产出（2026-09-19 采集）：

```text
$ df -h /
Filesystem                         Size  Used Avail Use% Mounted on
/dev/mapper/ubuntu--vg-ubuntu--lv   47G  8.6G   36G  20% /

$ df -i /
Filesystem                          Inodes  IUsed   IFree IUse% Mounted on
/dev/mapper/ubuntu--vg-ubuntu--lv  3145728 159617 2986111    6% /

$ lsof +L1
COMMAND    PID USER   FD   TYPE DEVICE SIZE/OFF NLINK    NODE NAME
systemd-j  463 root   36u   REG  252,0  8388608     0 1855714 /var/log/journal/…/user-1000@….journal (deleted)
```

**`lsof +L1` 有输出不等于「磁盘被偷了」**：`systemd-journald` 长期持有刚被轮转掉的 journal 文件是正常现象。判断它是不是元凶，看两件事——`SIZE/OFF`（这里是 8 MiB）与你的容量缺口是不是同量级，以及 `du` 与 `df` 的差值是不是正好这么多。**只有量级对得上，才值得顺着这条线查下去。**

四类不一致的成因与判据：

| 现象 | 成因 | 判据 |
| --- | --- | --- |
| `df` 满、`du` 少 | 已删除但被进程持有 | `lsof +L1` 有输出 |
| `df` 大、`du` 小 | 挂载覆盖（挂载点遮住了下层目录，上层 `du` 看不到被遮的内容） | `findmnt` 看挂载关系；把根 bind 到别处再看。反向的「`df` 小、`du` 大」通常只是 `du` 缺 `-x`、跨了文件系统 |
| 写入报 `No space left on device` 但容量还有 | inode 用完，或 ext4 保留块 | `df -i`、`tune2fs -l` |
| 写入报 `Disk quota exceeded` | 配额到顶 | 配额报表（不是容量问题） |

### 1.2 「删了文件空间不释放」怎么处置

找到持有者之后有两条路：**让进程重新打开文件**（通常需要 reload 或重启该服务），或者**把内容拷出来**（进程还在、且文件重要时的抢救手段）。

```bash
lsof +L1 2>/dev/null                      # 验证：找到持有者（进程号与 fd）
ls -l /proc/<pid>/fd | grep deleted       # 验证：确认哪个 fd 指向已删除文件
cp /proc/<pid>/fd/<n> /var/tmp/rescued.bin
```

**第一反应不要是「再删一遍」**：文件已经不在目录树里了，再删也没用；要么让持有它的进程释放句柄，要么先把内容抢救出来。

### 1.3 怎么安全地复现「打满」与「inode 耗尽」

这两类故障在实验机上是**可以安全复现**的——关键是**不要动根分区**：用一块临时 loop 文件系统当靶子，演练完 `umount` + `losetup -d` 就回到原状（本节做法与子笔记 10 的 LVM 快照演练共用同一套约束）。实验机实测，原始输出见 `.labvm/evidence/11b_13_capacity_loop`：

```bash
truncate -s 128M /tmp/11b-fill.img        # 验证：造一块 128 MiB 的"假盘"
LOOP=$(losetup -f --show /tmp/11b-fill.img)
mkfs.ext4 -q -F "$LOOP"
mount "$LOOP" /tmp/11b-fill-mnt           # 验证：挂到自建挂载点，绝不碰 /
dd if=/dev/zero of=/tmp/11b-fill-mnt/held.bin bs=1M count=40 status=none
sleep 300 8<>/tmp/11b-fill-mnt/held.bin & # 验证：让一个进程持有这个文件
rm -f /tmp/11b-fill-mnt/held.bin          # 验证：删除文件但保留句柄，空间不会释放
df -h /tmp/11b-fill-mnt; du -sh /tmp/11b-fill-mnt
                                          # 验证：df 与 du 对不上，差值就是被持有的 40 MiB
dd if=/dev/zero of=/tmp/11b-fill-mnt/big.bin bs=1M count=200
                                          # 验证：把剩余空间打满（会提前遇到 ENOSPC，这是预期）
bash -c 'echo x > /tmp/11b-fill-mnt/newfile'
                                          # 验证：写入报 No space left on device
lsof +L1 | grep 11b-fill                  # 验证：定位持有已删除文件的进程
cp /proc/<pid>/fd/8 /tmp/11b-rescued.bin  # 验证：先抢救内容，再决定杀不杀进程
kill <pid>                                # 验证：进程退出后空间立刻回来
umount /tmp/11b-fill-mnt; losetup -d "$LOOP"; rm -f /tmp/11b-fill.img
                                          # 验证：清理；losetup -a 应回到空
```

```text
$ df -h /tmp/11b-fill-mnt    （删掉被进程持有的 held.bin 之后）
/dev/loop0      104M   41M   55M  43% /tmp/11b-fill-mnt
$ du -sh /tmp/11b-fill-mnt
20K	/tmp/11b-fill-mnt

$ df -h /tmp/11b-fill-mnt    （把剩余空间打满之后）
/dev/loop0      104M  102M     0 100% /tmp/11b-fill-mnt
$ lsof +L1 | grep 11b-fill
sleep     17678 root    8u   REG    7,0 41943040     0      12 /tmp/11b-fill-mnt/held.bin (deleted)
$ ls -l /tmp/11b-rescued.bin
-rw-r--r-- 1 root root 41943040 Sep  9 08:06 /tmp/11b-rescued.bin

$ df -h /tmp/11b-fill-mnt    （杀掉持有进程之后）
/dev/loop0      104M   62M   34M  65% /tmp/11b-fill-mnt
```

上面这一段来自 **`128 MiB` 靶盘那一轮**（来源 `.labvm/evidence/11b_13_capacity_loop.out.txt`，**2026-09-19 08:06 UTC 采集**）；那一轮往满盘写小文件时只记下了 `写入退出码=1`，**没有留下报错文本**。报错原文来自**另一轮更小的靶盘**（28 MiB，挂载点 `/tmp/11b-small-mnt`，见 `.labvm/evidence/11b_13_logrotate_enospc.out.txt`）——两次运行的目标盘与挂载点不同，不能当作同一次输出读：

```text
$ df -h /tmp/11b-small-mnt
/dev/loop0       23M   22M     0 100% /tmp/11b-small-mnt
$ bash -c 'echo x > /tmp/11b-small-mnt/newfile'
bash: line 1: echo: write error: No space left on device     （exit=1）
```

**inode 耗尽同理**，只要把文件系统造成 inode 很少即可（`-N 32` 表示总共只给 32 个 inode）：

```bash
mkfs.ext4 -q -F -N 32 "$LOOP"             # 验证：造一个 inode 极少的文件系统
mount "$LOOP" /tmp/11b-inode-mnt          # 验证：挂到自建挂载点（这一轮用的是独立挂载点）
df -i /tmp/11b-inode-mnt                  # 验证：inode 总量只有 32
for i in $(seq 1 40); do touch /tmp/11b-inode-mnt/f$i 2>/dev/null; done
df -i /tmp/11b-inode-mnt; df -h /tmp/11b-inode-mnt
                                          # 验证：inode 到 100%，而容量只用了 1%
touch /tmp/11b-inode-mnt/extra            # 验证：报 No space left on device（与容量无关）
```

实测输出（来源 `.labvm/evidence/11b_13_logrotate_enospc_rerun.out.txt` C 节，**2026-09-19 08:35 UTC 单次连续运行**）：

```text
$ df -i /tmp/11b-inode-mnt
/dev/loop0         32    11    21   35% /tmp/11b-inode-mnt      ← 空盘时
$ df -i /tmp/11b-inode-mnt
/dev/loop0         32    32     0  100% /tmp/11b-inode-mnt      ← touch 40 个之后
$ df -h /tmp/11b-inode-mnt
/dev/loop0       24M   24K   22M   1% /tmp/11b-inode-mnt        ← 容量只用 1%
$ touch /tmp/11b-inode-mnt/extra
touch: cannot touch '/tmp/11b-inode-mnt/extra': No space left on device     （exit=1）
```

（历史证据 `.labvm/evidence/11b_13_logrotate_enospc.out.txt` 里这一轮用的是 `/tmp/11b-small-mnt`，同为独立挂载点；本节统一写成 `/tmp/11b-inode-mnt`，是 2026-09-19 复跑时的名字。）

**这两组输出合起来就是本篇最值钱的一句话**：`No space left on device` 只说明「某种资源用完了」——容量、inode、保留块、配额都会报同一句话，所以**先取证分类，再动手清理**。把 loop 演练做完并清理干净的复核是：`losetup -a` 为空、`vgs` 只剩 `ubuntu-vg`、`ls -d /tmp/11b-*` 无匹配。

## 2. 扩容：一条完整的链

### 2.1 三种场景

| 场景 | 链路 | 最容易漏的一步 |
| --- | --- | --- |
| **云盘扩容** | 控制台/API 扩容云盘 → 让操作系统重新识别大小 → 扩分区 → 扩文件系统 | 云上扩完了但系统没重新识别分区表（需要重扫或重启） |
| **LVM 扩容** | `pvresize`（让 PV 认识新增空间）→ `lvextend -r`（扩 LV 并顺带扩文件系统） | 只 `lvextend` 不扩文件系统 → `df` 不变 |
| **加盘挂载** | 分区 → `mkfs` → 写入 `fstab`（用 UUID）→ `mount -a` 验收 | 用了 `/dev/sdX` 而不是 UUID（设备名会漂移） |

```bash
lsblk                                     # 验证：设备与分区的大小（第一站：设备层）
sudo pvresize /dev/<new-dev>              # 验证：让 PV 使用新增的空间
sudo lvextend -r -l +100%FREE /dev/<vg>/<lv>
                                          # 验证：-r 会在扩 LV 后自动扩文件系统（XFS/ext4 都支持）
df -h /<mount>                            # 验证：文件系统容量确实变大了（最终验收）
```

实验机在 **loop 设备**上把这条链完整走了一遍（不动根分区，见第 4 节末尾的约束）：

```text
$ df -h /tmp/11b-lvm-mnt    （扩之前）
/dev/mapper/lab11--vg-lab11--lv  974M   24K  907M   1% /tmp/11b-lvm-mnt

$ lvextend -q -r -L +400M /dev/lab11-vg/lab11-lv
  Size of logical volume lab11-vg/lab11-lv changed from 1.00 GiB (256 extents) to 1.39 GiB (356 extents).
  Logical volume lab11-vg/lab11-lv successfully resized.
Filesystem at /dev/mapper/lab11--vg-lab11--lv is mounted on /tmp/11b-lvm-mnt; on-line resizing required
The filesystem on /dev/mapper/lab11--vg-lab11--lv is now 364544 (4k) blocks long.

$ df -h /tmp/11b-lvm-mnt    （扩之后）
/dev/mapper/lab11--vg-lab11--lv  1.4G  201M  1.1G  16% /tmp/11b-lvm-mnt
```

耗时 **0.13 秒**，且 `resize2fs` 在**挂载状态下**完成（`on-line resizing required`）——这就是「在线扩容」的字面意思。注意 `-r` 不是可选项：**去掉它，上面第二段输出里 `df` 那一行不会变**。

### 2.2 扩容也要走变更流程

扩容看起来「只是变大，没风险」，实际有三个风险点：**扩分区可能写坏分区表**（误操作相邻分区）、**在线扩文件系统有版本限制**、**容量变化会影响依赖它的复制与备份**。所以扩容同样要有：备份（至少分区表 `sfdisk -d`/`sgdisk --backup` 导出）、回滚方案（多数情况无法回滚，属于不可逆 → 按不可逆处理）、验收（`df` + 业务写入）。

## 3. 日志治理

### 3.1 先问「这些日志谁要看、看多久」

日志治理的三个决定，都必须由人给出答案：

| 问题 | 影响 | 常见结论 |
| --- | --- | --- |
| 谁要看？ | 决定日志级别与内容 | 应用日志给开发，系统日志给运维，审计日志给安全 |
| 看多久？ | 决定保留期与磁盘预算 | 排障 7~30 天；合规可能要求 180 天以上 |
| 存哪里？ | 决定本机还是集中采集 | 本机保留短期，长期送集中存储 |

### 3.2 journald 的容量治理

```bash
journalctl --disk-usage                   # 验证：当前日志占用的磁盘空间（实验机实测 20.7 MiB，同日更早基线 53.9 MiB）
journalctl --vacuum-size=200M             # 验证：收缩到 200 MiB（按大小）
journalctl --vacuum-time=7d               # 验证：只保留最近 7 天（按时间）
```

持久化的落点是 `/var/log/journal`（实验机上存在，说明日志会在重启后保留）；容量上限写在 `/etc/systemd/journald.conf` 里（改完需要 `systemctl restart systemd-journald`）：

```ini
[Journal]
Storage=persistent
SystemMaxUse=500M
MaxRetentionSec=14day
```

> [!warning] 先确认日志是「持久化」还是「内存态」
> `Storage=volatile`（或 `/var/log/journal` 不存在）时，日志只在内存与运行态目录里，**重启即丢**。这会影响两件事：一是排障时拿不到上次启动的日志，二是容量治理的对象不同。本机 `/var/log/journal` 存在，属于持久化配置。

### 3.3 文件式日志的轮转

```bash
sudo logrotate -d /etc/logrotate.d/<app>  # 验证：-d 是 dry-run，只打印将要做什么（不实际轮转）
sudo logrotate -f /etc/logrotate.d/<app>  # 验证：强制执行一次（用于验证配置是否正确）
```

实验机上用一份临时配置（`size 1k` + `rotate 3` + `compress` + `copytruncate`）干跑，输出会明确告诉你它**判断**了什么。下面这一整块是 **2026-09-19 08:35 UTC 一次连续运行**的原始输出（来源 `.labvm/evidence/11b_13_logrotate_enospc_rerun.out.txt` A 节）——**先用 300 字节的日志跑一次（判「不需要轮转」），再把日志撑到 4 KiB 跑第二次（判「需要轮转」）**，两次的 `Now:` 相同，所以能直接对照「同一个时刻、同一份配置、只改了日志大小，判断就翻转了」：

```text
$ logrotate -d /tmp/11b-logrotate.conf     （第一次：app.log 只有 300 字节）
considering log /tmp/11b-logs/app.log
  Now: 2026-09-19 08:35
  Last rotated at 2026-09-19 08:00
  log does not need rotating (log size is below the 'size' threshold)

$ logrotate -d /tmp/11b-logrotate.conf     （第二次：app.log 撑到 4096 字节）
considering log /tmp/11b-logs/app.log
Creating new state
  Now: 2026-09-19 08:35
  Last rotated at 2026-09-19 08:00
  log needs rotating
rotating log /tmp/11b-logs/app.log, log->rotateCount is 3
dateext suffix '-20260919'
glob pattern '-[0-9][0-9][0-9][0-9][0-9][0-9][0-9][0-9]'
renaming /tmp/11b-logs/app.log.3.gz to /tmp/11b-logs/app.log.4.gz (rotatecount 3, logstart 1, i 3),
renaming /tmp/11b-logs/app.log.2.gz to /tmp/11b-logs/app.log.3.gz (rotatecount 3, logstart 1, i 2),
renaming /tmp/11b-logs/app.log.1.gz to /tmp/11b-logs/app.log.2.gz (rotatecount 3, logstart 1, i 1),
log /tmp/11b-logs/app.log.4.gz doesn't exist -- won't try to dispose of it
copying /tmp/11b-logs/app.log to /tmp/11b-logs/app.log.1
truncating /tmp/11b-logs/app.log
compressing log with: /bin/gzip
```

**`-d` 的价值在于它把「判断」和「动作」分开打印**：先看 `log needs rotating`（触发条件判对了没有），再看 `renaming …`（保留份数与命名符合预期吗）。写完一条 `logrotate` 配置**应该先 `-d` 再上线**——这是本篇里最便宜的验证动作。注意 `logrotate -d` 本身会警告「debug mode does nothing except printing debug messages」，这句话就是在提醒你「别把干跑当成执行过了」。

| 关键项 | 含义 | 常见坑 |
| --- | --- | --- |
| `rotate N` | 保留多少份 | 份数 × 单份大小 = 磁盘预算；算一下再定 |
| `size` / `daily` | 何时轮转 | 只按时间轮转时，短时间暴涨的日志根本来不及轮转 |
| `compress` | 压缩旧日志 | 压缩需要 CPU，日志量大时要评估 |
| `copytruncate` | 复制后截断原文件 | 有丢日志的窗口；适合不能 reload 的应用 |
| `create` + `postrotate` | 轮转后新建文件并让应用重开 | **忘了让应用重开文件，写入会继续进已轮转的旧文件** |
| `maxsize` | 兜底的硬上限 | 只有 `maxsize` 才能防止「一天涨 20 GiB」 |

### 3.4 实验机实测的日志构成

```text
$ journalctl --disk-usage
Archived and active journals take up 20.7M in the file system.

$ du -sh /var/log
27M	/var/log

$ du -sh /var/log/* | sort -rh | head -8
21M     /var/log/journal
1.3M    /var/log/syslog
1.2M    /var/log/installer
820K    /var/log/dpkg.log
748K    /var/log/kern.log
448K    /var/log/audit
200K    /var/log/apt
172K    /var/log/auth.log
```

**结论**：这台机器上「日志占空间」≈「journal 占空间」（21 MiB / 27 MiB ≈ 78%），但**剩下的 22% 全是「装完就不长」的一次性大户**（`installer` 1.2 MiB、`dpkg.log` 820 KiB）——这两类的处置方式完全不同：journal 改 `journald.conf` 的上限，一次性日志直接定保留期。做日志治理时先量一遍分布，再决定改 `journald.conf` 还是改 `logrotate` —— 改错对象是最常见的浪费。

> [!warning] `--disk-usage` 的数字会变，别把它当常量记
> 同一台实验机在同一天里，`journalctl --disk-usage` 先报过 **53.9 MiB**、后报 **20.7 MiB**：中间有另一个实验在写日志、也有实验在 `--vacuum` 回收。**治理的判据是「增长速度与上限」，不是某一个快照数字**；巡检项里写死「超过 100 MiB 就查」这类阈值，比写死「现在是 20.7 MiB」有用得多。

## 4. 临时文件与容器数据目录

### 4.1 临时文件

```bash
systemd-tmpfiles --cat-config             # 验证：打印生效的清理策略（实验机含 /usr/lib/tmpfiles.d/ 与 /etc/tmpfiles.d/）
systemd-tmpfiles --clean --prefix=/tmp    # 验证：只对 /tmp 相关规则执行清理，缩小影响面
```

> [!warning] 不要照抄「`--dry-run`」这种写法
> 实验机实测（systemd 255）：`systemd-tmpfiles --clean --dry-run` 直接报 `unrecognized option '--dry-run'`。**不同版本支持的选项不同**，所以更稳的做法是「先用 `--cat-config` 看清策略，再用 `--prefix=` 把作用范围限定在你要治理的那个目录」，而不是依赖一个记在脑子里的参数名。

| 目录 | 常见策略 | 注意 |
| --- | --- | --- |
| `/tmp` | 按天数清理（常见 10 天） | **实验机 `/tmp` 在根文件系统上，不是 tmpfs**（`findmnt /tmp` 显示的是 `/dev/mapper/ubuntu--vg-ubuntu--lv`）——它不会被重启清空，会实实在在占磁盘 |
| `/var/tmp` | 保留更久（常见 30 天） | 常被应用用来放「跨重启的临时数据」，清理策略要更保守 |
| 应用自有临时目录 | 由应用自己管理 | 应用崩溃后常留下大量残留文件；要写进巡检项 |

> [!important] 临时文件治理的验收是「策略生效」，不是「手工删过」
> 手工 `rm` 解决的是这一次，策略解决的是下一次。**每个「会增长的目录」都应该有：owner、保留期、上限、以及一条能看见它的告警。**

### 4.2 容器数据目录

| 增长来源 | 位置（以常见配置为例） | 治理动作 |
| --- | --- | --- |
| 镜像与层 | `/var/lib/docker/overlay2`、`/var/lib/containerd` | 定期清理无引用镜像；**不要在有运行容器的宿主机上盲目 prune** |
| 容器日志 | `/var/lib/docker/containers/*/*-json.log` | 配置日志驱动的大小与份数上限（默认可能无上限） |
| 卷与构建缓存 | `/var/lib/docker/volumes`、构建缓存目录 | 清缓存前确认没有在跑的构建；卷要按业务确认 |

```bash
du -sh /var/lib/docker/* 2>/dev/null | sort -rh | head
                                          # 验证：容器数据目录的大户是谁
```

**容器日志默认无上限是最经典的「慢慢写满磁盘」**：一个反复打印错误的应用能在几小时内把 `/var` 写满，而 `df` 的曲线看起来一直很平，直到某个时刻突然断崖。

## 5. 预防：把治理变成常态

```text
每个「会增长的目录」四个字段：
  owner（谁负责）
  retention（保留多久 / 多少份）
  limit（硬上限，达到后会发生什么）
  alert（在什么水位告警、告警给谁）
```

做到这四步之后，容量问题就从「偶发事故」变成了「可预测的常规维护」。具体到动作：

| 频率 | 动作 |
| --- | --- |
| 每日 | 看容量水位告警；确认备份任务退出码 |
| 每周 | 看增长最快的目录（`du` 排行），判断是正常增长还是异常 |
| 每月 | 复核保留策略与磁盘预算；做一次 `df`/`du` 对账 |
| 每季度 | 做一次扩容演练或恢复演练（子笔记 10） |

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 「`du` 不准」就结束排查 | `df` 与 `du` 不一致有明确的四类成因，要逐一排除 |
| 删了文件空间不释放就反复删 | 文件已被进程持有；要释放句柄或先拷出内容 |
| 只看 `df -h` 不看 `df -i` | 小文件密集场景会先耗尽 inode，现象同样是「写不进去」 |
| 云盘扩容后直接看 `df` | 少了「扩分区 + 扩文件系统」两步，`df` 当然不变 |
| 只 `lvextend` 不加 `-r` | LV 变大了但文件系统没扩，`df` 不变（最经典的「扩容只做了一半」） |
| 扩容不做分区表备份 | 扩分区写坏分区表是不可逆的；先导出 `sgdisk --backup`/`sfdisk -d` |
| 把日志保留期定成「越长越安全」 | 磁盘预算会被吃掉；保留期要由「谁看、看多久」决定 |
| 只按 `daily` 轮转、不设 `maxsize` | 日志暴涨时来不及轮转，直接写满磁盘 |
| `copytruncate` 用在能 reload 的应用上 | 有丢日志窗口；能 reload 就用 `create` + `postrotate` |
| 手工 `rm` 临时文件代替策略 | 这次清了，下次还会满；治理的对象是策略与告警 |
| 在跑着容器的宿主机上盲目 prune | 会删掉正在用的镜像/卷；要先确认引用关系 |
| 容器日志不设上限 | 是「慢慢写满磁盘」的最常见原因 |

## 决策练习

> [!question]- 场景：告警显示某台机器的 `/` 使用率 100%，业务开始报 `No space left on device`。你登上去看到 `du -sh /var/log` 只有 2 GiB，而 `df -h /` 显示 100 GiB 已满。
> A. 先把 `/var/log` 清空，释放空间让业务恢复
> B. 先做只读取证（`df -h`、`df -i`、`findmnt`、`lsof +L1`、`du` 排行），判断属于四类里的哪一类；如果是「已删除但被进程持有」，优先抢救内容或让进程释放句柄，而不是删别的东西
> C. 立刻重启那台机器——重启会清理临时文件和句柄
>
> **答案：B。**
> A 错在两处：`du` 只有 2 GiB 说明**日志不是元凶**，删它解决不了问题；而且清空正在写的日志会丢掉排查现场（`/var/log` 日志还会被应用继续写）。
> C 会把现场一起清掉：如果根因是「某个进程持有 90 GiB 的已删除文件」，重启确实能释放，但**你永远不知道是谁干的、为什么干**，下次还会发生。
> B 是正解：**先按四个口径取证分类，再动手**。本题的 `df` 与 `du` 巨大差异，已经强烈指向「已删除但被进程持有」——`lsof +L1` 一条命令就能定位到那 90 GiB 在哪。

## 要点自测

> [!question]- `df` 与 `du` 不一致有哪四类原因？
> - 已删除但被进程持有（`lsof +L1`）、挂载覆盖（`findmnt`）、保留块与元数据（`tune2fs -l`）、稀疏文件与延迟分配。
> - 每一类的处置完全不同，要逐一排除而不是互相否定。
> - **第一反应不要是什么**：不要用「`du` 不准」当结论。

> [!question]- 云盘/LVM 扩容的完整链路是什么？哪一步最容易漏？
> - 云盘：扩容卷 → 让系统重新识别 → 扩分区 → 扩文件系统 → `df` 验收。
> - LVM：`pvresize` → `lvextend -r`（或其他方式扩文件系统）→ `df` 验收。
> - 最容易漏的是**扩文件系统**这一步，表现为「容量扩了但 `df` 没变」。
> - **第一反应不要是什么**：不要扩容后不看 `df` 就宣布完成。

> [!question]- 日志治理里，`journald.conf` 与 `logrotate` 分别管什么？
> - `journald.conf`：`SystemMaxUse` 管总量，`MaxRetentionSec` 管保留期，`Storage` 决定是否持久化。
> - `logrotate`：管文件式日志的轮转份数、触发条件、压缩与「让应用重开文件」。
> - **第一反应不要是什么**：不要不量分布就动手——实验机 27 MiB 的 `/var/log` 里 journal 占 21 MiB（约 78%），但剩下的 `installer`/`dpkg.log` 是一次性大户，处置方式完全不同。

> [!question]- 临时文件治理的最小要素是什么？
> - 四个字段：owner、保留期、硬上限、告警水位。
> - `/tmp`、`/var/tmp`、应用自有临时目录要分别设策略（`systemd-tmpfiles` 与发行版默认配置）。
> - **第一反应不要是什么**：不要用手工 `rm` 代替策略。

> [!question]- 容器宿主机磁盘暴涨通常有哪三个来源？
> - 镜像与层、容器日志文件、卷与构建缓存。
> - 容器日志默认可能无上限，是「慢慢写满」的常见元凶。
> - **第一反应不要是什么**：不要在跑着容器的宿主机上盲目 prune。
