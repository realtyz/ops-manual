# 故障域与检测的赌注

"我们做过高可用"这句话本身不含信息。含信息的是它的下一句：**拔掉任意一台，业务还剩多少。** 这一篇讲的是这个数字由什么决定——哪一层一起失效、检测要多快、切换会不会丢东西，以及冗余为什么总是被"共享依赖"吃掉。

## 1. 判据是"拔掉一台还剩多少"

先说清楚一个容易被当成答案的东西：**配了 VIP 不等于高可用**。VIP（Virtual IP，虚拟 IP）只是把"客户端连哪个地址"和"哪台机器在服务"解耦，它回答的是"地址能不能漂移"，不回答下面四个问题：

| 问题 | 判据 |
| --- | --- |
| 这个服务是不是单实例？ | 后端列表里有几个实例（`ss -lnt`、负载均衡的后端清单、服务发现的注册表） |
| 挂了会不会切？ | 有没有健康检查、检查周期与失败阈值是多少 |
| 切的时候断不断？ | 存量连接是被排空还是被硬断；客户端有没有重试 |
| 切完之后容量还够吗？ | 剩余实例的峰值利用率（见第 5 节的余量算式） |
| 数据还在吗？ | 有没有副本、副本同步方式（同步还是异步）、切换会丢多少数据（对应 RPO） |

实验机上采集的一组只读证据说明"没有任何高可用"是什么样子（环境：Ubuntu 24.04.5 LTS（VMware 虚拟机）/ 内核 `6.8.0-139-generic` / 4 vCPU / `MemTotal` 7894 MiB / 单网卡 `ens33`，`192.168.246.128`）：

```bash
ip -brief addr                                 # 验证：有没有可漂移的地址
ip route                                       # 验证：路由是不是单点
ss -lnt                                        # 验证：对外监听了什么
systemctl list-units --type=service | grep -Ei 'keepalived|haproxy|nginx|corosync|pacemaker'
                                               # 验证：本机有没有高可用组件
cat /proc/mdstat                               # 验证：有没有本地阵列做冗余
```

```text
# 数值仅示意、不代表你的机器
lo               UNKNOWN        127.0.0.1/8 ::1/128
ens33            UP             192.168.246.128/24 fe80::20c:29ff:fe66:2c0f/64
default via 192.168.246.2 dev ens33
LISTEN 0 4096 127.0.0.54:53      0.0.0.0:*
LISTEN 0 4096    0.0.0.0:22      0.0.0.0:*
LISTEN 0 4096 127.0.0.53%lo:53   0.0.0.0:*
LISTEN 0 4096       [::]:22         [::]:*
```

三点判读：**没有 VIP**（只有 `lo` 与 `ens33` 两个地址）；**对外只有一个服务端口**（`0.0.0.0:22` / `[::]:22`，同一个 `sshd`，`ss -lntp` 显示 pid 1348）；**没有任何高可用组件**（`keepalived`、`haproxy`、`nginx`、`corosync`、`pacemaker` 的单元都不存在），`/proc/mdstat` 里也没有阵列。结论很直白：**这台机器拔掉即全没**——它的可用性就是"单台机器的可用性"，任何"我们做了冗余"的说法在这台机器上都不成立。

这个结论能立刻给出，是因为判据是"拔掉一台还剩多少"，而不是"有没有装 keepalived"——**装了什么不重要，端的服务有几个才重要。**

## 2. 故障域：会一起失效的那些东西

**故障域（failure domain）是一组会同时失效的东西。** 划分故障域的意义在于：冗余必须跨故障域放置，放在同一个故障域里的两份，等于一份。

| 层 | 一起失效的东西 | 对应的冗余手段 | 常见错觉 |
| --- | --- | --- | --- |
| 进程 | 同一个进程里的所有线程与连接 | 多进程 / 多实例 | "我配了线程池就冗余了" |
| 主机 | 这台机器上的全部服务 | 多主机 + 负载均衡 | "双机"其实只在同一机架 |
| 机架 / 电源 | 同一机架或同一路市电上的设备 | 跨机架部署 | 双机同机架，一次掉电一起走 |
| 可用区 | 同城一个可用区的机房与网络 | 跨可用区部署 | 主从在同一个可用区 |
| 机房 / 区域 | 整个机房或整个地域 | 异地多活或异地冷备 | "异地备份"与"异地可服务"是两件事 |
| **共享依赖** | **所有依赖它的服务** | 依赖本身做冗余、降级、限流 | 最容易漏的一层 |

**最后一层是新人最容易漏的，也是影响面最大的一层。** 数据库、缓存、消息队列、DNS、统一认证、配置中心——这些"大家都要用"的东西，它们自己一旦成为单点，前面所有的跨主机、跨机架、跨可用区冗余都会在同一时刻一起失效。它们的故障域不是"一台机器"，而是"所有依赖它的服务"，影响面可以直接到 100%。

有一个可以立刻用的追问：**把每一层都问一遍"这一层挂了，我的服务还剩多少"，一直问到你答不上来的那一层**。答不上来的那一层，就是当前真正的约束。

## 3. 接入层的四种做法，各自把风险挪到了哪里

让"某台机器挂了"不变成"业务中断"，客户端得能连到别的实例上。四条常见路径，它们不是替代关系，而是各自把风险挪到了不同地方：

| 做法 | 粒度 | 它能防 | 它把风险挪到了哪 |
| --- | --- | --- | --- |
| VIP 漂移（VRRP，Virtual Router Redundancy Protocol） | 整机接管 | 主机级失效 | 选举协议本身：脑裂、心跳链路、仲裁 |
| 负载均衡器（LB） | 按后端实例 | 单实例失效 | LB 自身成为单点；健康检查判据；连接排空 |
| DNS 多值 / 轮询 | 按域名解析结果 | 部分实例失效 | TTL 与客户端缓存：**改得快不代表生效得快，也不代表回滚得快** |
| 服务发现 | 按注册表 | 实例动态伸缩 | 注册中心自身的高可用；客户端缓存与过期 |

**DNS 这一条特别容易高估。** 解析结果是带 TTL 的缓存，客户端与中间递归解析器都会缓存。TTL 未过期前，你既没法让变更完全生效，也没法真正回滚——这属于第 1 节里"看起来可逆、实际不可逆"的动作。

### 3.1 VIP 与脑裂

VIP 的实现通常靠 VRRP：一组机器用优先级选举出一个"持有者"，持有者把 VIP 配到自己网卡上并对外应答。问题出在**双方对"对端还活着吗"的判断不一致**时——典型情形是心跳链路断了，但两边都还活着、都能对外服务。

- **脑裂（split brain）** 的定义就是：两边都以为自己该持有 VIP，于是**同时**持有、同时服务。对无状态读服务，后果是请求被分到两台；**对有写入的服务，后果是数据分叉**——两边各自接受写入，事后无法简单合并。
- 防法有四种，通常要叠加使用：**独立的心跳链路**（不要与业务流量共用）、**第三方仲裁或多数派（quorum）**、**fencing**（用带外管理或云 API 强制把旧持有者关机或断网）、**时间同步**（时间不同步会让日志、心跳、证书全部错位）。
- 最后一条纪律最容易被忽略，但最能止损：**判定不确定时，停服务而不是继续服务。** 对写服务而言，宁可短暂不可用，也不要两边都写坏数据。

对于有状态的系统，脑裂时的取舍就是 CAP（Consistency 一致性、Availability 可用性、Partition tolerance 分区容忍）——三者不能同时完全满足。这时**必须先问业务**："能丢一点数据，还是能停一会儿？"这个答案决定了你的系统在分区时该停还是该继续服务。**这个问题不能由运维单方面回答。**

### 3.2 健康检查：判得太松与太严都出事

健康检查是"要不要把流量给这个后端"的探针，它的两个失败方向后果完全不同：

| 判据 | 后果 | 典型原因 |
| --- | --- | --- |
| 太松 | 流量继续转给已经坏掉的后端，用户侧报错 | 只探 TCP 端口（端口还在听，业务已经处理不了请求） |
| 太严 | 一次抖动就把健康后端摘掉，甚至批量摘除引发级联故障 | 失败阈值太低、探针路径依赖共享依赖（探针本身去查数据库） |

两个具体判据：

- **端口在听不等于业务能用。** 判据要落到真实业务路径上；本机实测 `curl` 打一个临时 HTTP 服务，`/healthz` 返回 `200 0.003150`，而 `/nope` 返回 `404 0.000763`——**404 也是有效证据**：它说明服务活着、能解析路径、能结构化响应，比"TCP 连上了"信息量大得多；
- **探针不要依赖被探对象之外的共享依赖。** 如果健康检查要去查数据库，那数据库抖一下，全部后端会被同时摘掉——探针本身成了级联故障的放大器。

### 3.3 排空：摘流量之后不是马上动手

对会保持连接的协议（HTTP 长连接、TCP 长会话、gRPC），"从负载均衡里摘掉"与"存量连接结束"之间有一段延迟。这段延迟里动手（重启、改配置），就会出现"部分请求被切断"的现象。

固定顺序是：**摘流量 → 等存量连接结束（或到上限）→ 变更 → 单机验证 → 放回 → 观察。** 其中三个参数必须写进 Runbook，否则每次执行都不一样：

- **最长等待时间**：等到什么时候就不再等；
- **排空判据**：按连接数阈值判断（例如该实例存量连接降到某个数量以下），而不是按感觉；
- **放回后的观察时长**：放回之后看多久才算稳。

摘流量本身也要验收：**"真摘掉"的判据是"从外部探失败、从本机探成功"。** 只从本机探成功，不能说明流量已经不再进来。

## 4. 检测：高可用里最被低估的一半

冗余决定"坏了之后还有多少能力"，检测决定"坏多久之后才开始用这些能力"。业务感受的总损失近似于 `MTTD + MTTR`（发现时间加修复时间），而**故障切换的耗时下限就是检测时延**：

```text
# 模板，数值仅示意
心跳/探活间隔 2 秒，连续 3 次失败才判定 ⇒ 最坏检测时延约 6 秒
再加选举与地址漂移的时间 ⇒ 切换所需的最短时间就在这个量级
```

三条推论：

- **把探活间隔与失败阈值调小，能缩短切换时间，代价是误判率上升**——网络抖动会被当成故障，于是发生不必要的切换。这是一次典型的赌注：**切换快 vs 切换准，只能选一个侧重**；
- **MTTD 通常比 MTTR 更值得先优化**。修复速度受物理与流程限制，而发现速度往往只是"多加几条按业务指标的告警"；
- **告警本身要能被信任**。如果值班的人已经习惯"这条告警经常误报"，那它等于不存在——检测链路的可靠性属于阶段 9 的范围（指标语义、告警规则、SLI/SLO），这里只强调它对可用性的影响：**没有可信的检测，冗余就只是一笔没人动用的保险。**

## 5. 余量：N+1 与 N+2，以及滚动重启的批次上限

最后把"还剩多少"变成一个可算的数。

- **最小可接受容量**：业务高峰之上的余量。经验区间是峰值的 1.2~1.5 倍；
- **N+1**：在满足最小可接受容量的前提下，能容忍 **1 个**实例不可用（一次故障）；
- **N+2**：能容忍 **1 个故障 + 1 个维护**（所以可以一边坏着一边做变更）。

滚动重启的批次上限由此决定：**批次大小不能超过余量允许的台数。** 一个反例比公式更有说服力：4 个实例、单机峰值利用率 70%。下线 1 台后，剩余 3 台各约 133%——**这已经注定失败，与 `serial: 1` 无关**。正确动作是先扩容，或者把变更挪到低谷并同时限流。

## 常见误解

| 说法 | 事实 |
| --- | --- |
| "我们配了 VIP，所以高可用" | VIP 只回答"地址能不能漂移"，不回答"存量连接断不断""切完容量够不够""数据丢不丢" |
| "有主备就是高可用" | 要能回答四个问题：备机真的在同步吗、切换 RTO 是多少、会丢多少数据、切完容量够不够。答不出的主备只是"多了一台机器" |
| "双机就够了" | 两台机器如果没有独立心跳与仲裁，只是把单点故障推迟成脑裂。要能回答"两边看不见对方时，谁闭嘴" |
| "`serial: 1` 就安全" | 它只控制同时被改的台数，不控制剩余负载。4 台实例下线 1 台剩 3 台各 133% |
| "`/proc/mdstat` 有阵列就有冗余" | 本机实测 `/proc/mdstat` 里连阵列都没有；而阵列防的是盘坏，不防主机、机架与共享依赖 |
| "健康检查越严越好" | 太严会误踢健康后端，甚至因为探针依赖共享依赖而批量摘除，引发级联故障 |
| "探活返回 404 就是服务坏了" | 404 说明服务活着、能解析路径、能结构化响应，是有效证据；判据要看业务路径的预期响应 |
| "副本是实时的，所以数据不会丢" | 副本防硬件失效，不防逻辑错误：误删与坏数据会同步过去。它不能替代备份 |
| "心跳间隔调小就能更快切换" | 能，但误判率上升——这是切换快与切换准之间的赌注，要按业务的容忍度选 |
| "服务发现能替代负载均衡" | 它解决"地址从哪来"，注册中心自身仍需高可用，客户端缓存与过期也要处理 |

**第一反应不要做什么**：不要用"装了什么组件"证明高可用；不要在没有独立心跳与仲裁的情况下做双机 VIP；不要在探针里依赖共享依赖；不要在只算出"一台都没余量"的情况下执行滚动重启；不要把副本当备份。

## 要点自测

**问：判断高可用的判据是什么？为什么"配了 VIP"不是判据？**
答：判据是"拔掉任意一台之后业务还剩多少"。VIP 只解决地址漂移，不回答存量连接断不断、切换要多久、切完容量够不够、数据丢不丢。

**问：六层故障域里，哪一层的影响面最大、最容易被漏？**
答：共享依赖（数据库、缓存、消息队列、DNS、统一认证、配置中心）。它的故障域不是一台机器，而是所有依赖它的服务，影响面可以直接到 100%。

**问：脑裂的定义是什么？无状态服务与有状态服务的后果有什么不同？**
答：两边都以为自己该持有资源，于是同时持有、同时服务。无状态服务的后果是请求被分到两台；有状态写服务的后果是数据分叉。防法是独立心跳、仲裁、fencing、时间同步，加上"不确定时停服务"。

**问：健康检查判得太松与太严，后果分别是什么？**
答：太松会把流量继续转给已坏的后端（典型是只探端口）；太严会误摘健康后端，若探针还依赖共享依赖，会批量摘除引发级联故障。

**问：为什么"摘流量"和"动手"之间要等？三个必须写进 Runbook 的参数是什么？**
答：因为长连接还有存量。三个参数是最长等待时间、排空判据（连接数阈值）、放回后的观察时长。摘流量的验收是"外部探失败、本机探成功"。

**问：4 个实例、单机峰值利用率 70%，能不能执行 `serial: 1` 的滚动重启？**
答：不能。下线 1 台后剩余 3 台各约 133%，超出单机能力。先扩容，或挪到低谷并限流。`serial` 只控同时被改的台数。

**第一反应不要做什么**：不要把"装了高可用组件"当结论；不要在探针里依赖共享依赖；不要在没算余量的情况下重启；不要在脑裂不确定时继续对外写。
