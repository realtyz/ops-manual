# 故障域与检测的赌注

"我们做过高可用"这句话本身不含信息。含信息的是它的下一句：**拔掉任意一台，业务还剩多少。** 这个数字并不是由装了什么组件决定的，因为哪一层会一起失效、检测要多快才能判定故障、切换时会不会丢掉数据，这三件事共同决定了它；同时，冗余之所以经常被"共享依赖"消耗掉，也是因为共享依赖把多台机器的失效合并成了同一次失效。

## 1. 判据是"拔掉一台还剩多少"

配了 VIP 不等于高可用，这一点最容易被当成答案。VIP（Virtual IP，虚拟 IP）只把"客户端连哪个地址"与"哪台机器在服务"这两件事解耦，因此它回答的是"地址能不能漂移"，它不回答下面五个问题：

| 问题 | 判据 |
| --- | --- |
| 这个服务是不是单实例？ | 要判断这一点，就要数后端列表里有几个实例，因此读 `ss -lnt`、负载均衡的后端清单或服务发现的注册表。 |
| 挂了会不会切？ | 要判断这一点，就要看有没有健康检查、检查周期是多少、失败阈值是多少，因为这三项共同决定了多久才会判定一次失效。 |
| 切的时候断不断？ | 要判断这一点，就要看存量连接是被排空还是被硬断，同时要看客户端有没有重试，因为客户端不重试的话，被硬断的请求不会自己恢复。 |
| 切完之后容量还够吗？ | 要判断这一点，就要算剩余实例的峰值利用率，算式见第 5 节的余量算法。 |
| 数据还在吗？ | 要判断这一点，就要看有没有副本、副本同步方式是同步还是异步，以及切换会丢多少数据，而丢多少数据对应 RPO（Recovery Point Objective，恢复点目标）。 |

在实验机上采集的一组只读证据，正好说明"没有任何高可用"是什么样子（环境：Ubuntu 24.04.5 LTS（VMware 虚拟机）/ 内核 `6.8.0-139-generic` / 4 vCPU / `MemTotal` 7894 MiB / 单网卡 `ens33`，`192.168.246.128`）。这些命令都是只读观测，因此生产机上也可以做：

```bash
ip -brief addr                                 # 验证：有没有可漂移的地址
ip route                                       # 验证：路由是不是单点
ss -lnt                                        # 验证：对外监听了什么
systemctl list-units --type=service | grep -Ei 'keepalived|haproxy|nginx|corosync|pacemaker'
                                               # 验证：本机有没有高可用组件
cat /proc/mdstat                               # 验证：有没有本地阵列做冗余
```

```text
# 数值仅示意、不代表你的机器
lo               UNKNOWN        127.0.0.1/8 ::1/128
ens33            UP             192.168.246.128/24 fe80::20c:29ff:fe66:2c0f/64
default via 192.168.246.2 dev ens33
LISTEN 0 4096 127.0.0.54:53      0.0.0.0:*
LISTEN 0 4096    0.0.0.0:22      0.0.0.0:*
LISTEN 0 4096 127.0.0.53%lo:53   0.0.0.0:*
LISTEN 0 4096       [::]:22         [::]:*
```

上面这份输出可以读出三点。**第一点是没有 VIP**，因为 `ip -brief addr` 只列出 `lo` 与 `ens33` 两个地址，而可漂移的地址会表现为第三个不随网卡固定的地址。**第二点是对外只有一个服务端口**，因为 `ss -lnt` 只列出 `0.0.0.0:22` 与 `[::]:22`，这两条属于同一个 `sshd`，`ss -lntp` 显示它的 pid 是 1348。**第三点是没有安装任何高可用组件**，因为 `keepalived`、`haproxy`、`nginx`、`corosync`、`pacemaker` 的单元都不存在，而且 `/proc/mdstat` 里也没有阵列。由此得到的结论是：**这台机器一旦拔掉，业务就全部消失**，因为它的可用性就是"单台机器的可用性"，所以任何"我们做了冗余"的说法在这台机器上都不成立。

这个结论之所以能立刻给出，是因为判据取的是"拔掉一台还剩多少"，而不是"有没有装 keepalived"，所以**装了什么并不重要，对外服务有几个实例才重要。**

## 2. 故障域：会一起失效的那些东西

**故障域（failure domain）是一组会同时失效的东西。** 划分故障域之所以有意义，是因为冗余必须跨故障域放置：若两份冗余被放进同一个故障域，则它们等于只有一份。

| 层 | 一起失效的东西 | 对应的冗余手段 | 常见错觉 |
| --- | --- | --- | --- |
| 进程 | 同一个进程里的所有线程与连接都会一起失效，因为线程共享同一个地址空间，进程一退出它们就全部结束。 | 因此冗余手段是多进程或多实例，让每个实例各自承担一部分流量。 | "我配了线程池就冗余了"，这种说法成立的前提是故障只发生在单个线程内，而进程退出会把整个线程池一起带走。 |
| 主机 | 这台机器上的全部服务都会一起失效，因为它们共享同一份内核、同一块内存与同一套网卡。 | 因此冗余手段是多主机加负载均衡，让流量可以落到别的机器上。 | "双机"其实只在同一机架，这种说法成立的前提是那两台机器真的位于两个故障域，而不是只差一个主机名。 |
| 机架 / 电源 | 同一机架或同一路市电上的设备都会一起失效，因为电源与机架是它们共用的物理载体。 | 因此冗余手段是跨机架部署，让两台机器不共用一个配电回路。 | 常见的错觉是"双机同机架"，而一次掉电会把这两台机器一起带走。 |
| 可用区 | 同城一个可用区的机房与网络会一起失效，因为一个可用区内部的电力和网络是共用设施。 | 因此冗余手段是跨可用区部署，让主从不在同一个可用区。 | 常见的错觉是"主从在同一个可用区"，这种布置在可用区级失效面前等于没有冗余。 |
| 机房 / 区域 | 整个机房或整个地域会一起失效，因为地域级的电力、网络与自然条件都不受你控制。 | 因此冗余手段是异地多活或异地冷备，让服务或数据在另一个地域也有落点。 | 常见的错觉是"异地备份就是异地可服务"，而"异地备份"与"异地可服务"其实是两件事。 |
| **共享依赖** | **所有依赖它的服务**都会一起失效，因为它的可用性就是所有这些服务的可用性的下限。 | 因此冗余手段是对依赖本身做冗余、降级与限流，而不是给依赖它的每一台机器各加一份冗余。 | 这一层是最容易漏的一层，因为它的失效不表现为某台机器出问题，而表现为所有机器同时出问题。 |

**最末一层是新人在划分故障域时最容易漏掉的一层，同时也是影响面最大的一层。** 数据库、缓存、消息队列、DNS、统一认证、配置中心都属于这一类，因为"大家都要用"的东西一旦成为单点，前面所有的跨主机、跨机架、跨可用区冗余就会在同一时刻一起失效。它们的故障域不是"一台机器"，而是"所有依赖它的服务"，所以影响面可以直接到 100%。

有一个可以立刻使用的追问：**把每一层都问一遍"这一层挂了，我的服务还剩多少"，一直问到自己答不上具体数字的那一层为止。** 答不上来的那一层，就是当前真正的约束。

## 3. 接入层的四种做法，各自把风险挪到了哪里

要让"某台机器挂了"不变成"业务中断"，客户端必须能连到别的实例上。常见的四条路径不是互相替代的关系，因为它们各自把风险挪到了不同的地方：

| 做法 | 粒度 | 它能防 | 它把风险挪到了哪 |
| --- | --- | --- | --- |
| VIP 漂移（VRRP，Virtual Router Redundancy Protocol，虚拟路由器冗余协议） | 整机接管 | 它能防主机级失效，因为客户端始终连同一个地址，而持有该地址的机器可以更换。 | 它把风险挪到了选举协议本身，因为脑裂、心跳链路与仲裁这三件事一旦出错，两台机器可能同时持有同一个地址。 |
| 负载均衡器（LB，Load Balancer） | 按后端实例 | 它能防单实例失效，因为负载均衡器会把流量发给仍然健康的后端。 | 它把风险挪到了负载均衡器自身与它的判据上，因为 LB 自身会变成单点，同时健康检查的判据与连接排空的方式决定了切换是否平滑。 |
| DNS 多值 / 轮询 | 按域名解析结果 | 它能防部分实例失效，因为解析结果里可以同时给出多个地址。 | 它把风险挪到了 TTL 与客户端缓存上，因为**改得快不代表生效得快，也不代表回滚得快**。 |
| 服务发现 | 按注册表 | 它能防实例动态伸缩带来的地址变化，因为实例的地址由注册表统一维护。 | 它把风险挪到了注册中心自身与客户端缓存上，因为注册中心本身需要高可用，客户端缓存与过期策略也会影响故障时的表现。 |

**DNS 这一条特别容易被高估。** 解析结果本身是带 TTL（Time To Live，生存时间）的缓存，而客户端与中间的递归解析器都会缓存它；因此在 TTL 未过期之前，你既没法让变更完全生效，也没法真正回滚，这属于第 1 节里"看起来可逆、实际不可逆"的动作。

### 3.1 VIP 与脑裂

VIP 的实现通常依赖 VRRP：一组机器按优先级选举出一个"持有者"，持有者把 VIP 配置到自己的网卡上并对外应答。真正的问题出现在**双方对"对端还活着吗"这个问题判断不一致**的时候，而典型情形是心跳链路断了、但两边都还活着并且都能对外服务。

- **脑裂（split brain）** 的定义是：两边都以为自己该持有 VIP，于是它们**同时**持有这个地址、**同时**对外服务。若服务是无状态的读服务，则后果是请求被分到两台机器上；**若服务带有写入，则后果是数据分叉**，因为两边各自接受了写入，事后无法简单地合并。
- 防脑裂有四种手段，通常需要叠加使用：**独立的心跳链路**（不要与业务流量共用同一条链路）、**第三方仲裁或多数派（quorum，法定人数）**、**fencing（隔离，用带外管理或云 API 强制把旧持有者关机或断网）**、**时间同步**（因为时间不同步会让日志、心跳与证书全部错位）。
- 最后一条纪律最容易被忽略，但它最能止损：**判定不确定时，应当停服务而不是继续服务。** 对有写入的服务而言，宁可短暂不可用，也不要两边都写坏数据。

对有状态的系统而言，脑裂时的取舍就是 CAP（Consistency 一致性、Availability 可用性、Partition tolerance 分区容忍）——三者不能同时完全满足。因此这时**必须先问业务**："能丢一点数据，还是能停一会儿？"这个答案决定了系统在分区时该停还是该继续服务，所以**这个问题不能由运维单方面回答。**

### 3.2 健康检查：判得太松与太严都出事

健康检查是"要不要把流量给这个后端"的探针，它的两个失败方向后果完全不同：

| 判据 | 后果 | 典型原因 |
| --- | --- | --- |
| 判得太松 | 流量会继续转给已经坏掉的后端，因此用户侧看到报错。 | 典型原因是只探 TCP 端口，而端口还在听并不代表业务还能处理请求。 |
| 判得太严 | 一次抖动就会把健康后端摘掉，甚至批量摘除并引发级联故障，因此本来够用的容量被自己削掉。 | 典型原因是失败阈值太低，或者探针路径依赖了共享依赖（例如探针自己要去查数据库）。 |

有两条判据要单独记住。

**第一条判据是端口在听不等于业务能用。** 因此判据要落到真实业务路径上：在本机实测中用 `curl` 打一个临时 HTTP 服务，`/healthz` 返回 `200 0.003150`，而 `/nope` 返回 `404 0.000763`；可见**404 也是有效证据**，因为它说明服务活着、能解析路径、能给出结构化响应，所以它比"TCP 连上了"提供的信息量大得多。

**第二条判据是探针不要依赖被探对象之外的共享依赖。** 若健康检查要去查数据库，则数据库抖动一下就会让全部后端被同时摘掉，因此探针本身成了级联故障的放大器。

### 3.3 排空：摘流量之后不是马上动手

对会保持连接的协议（HTTP 长连接、TCP 长会话、gRPC），"从负载均衡里摘掉"与"存量连接结束"之间有一段延迟。若在这段延迟里动手（重启、改配置），则会出现"部分请求被切断"的现象。

固定顺序是：**先摘流量，再等存量连接结束或到达上限，然后变更，接着做单机验证，之后放回，最后观察。** 其中三个参数必须写进 Runbook（运行手册），否则每次执行都会不一样：

- **最长等待时间**：它规定等到什么时候就不再等；
- **排空判据**：它要求按连接数阈值判断，例如该实例的存量连接降到某个数量以下，而不是按感觉判断；
- **放回后的观察时长**：它规定放回之后要看多久才算稳定。

摘流量本身也要验收：**"真摘掉"的判据是"从外部探失败、从本机探成功"。** 若只从本机探成功，则不能说明流量已经不再进来。

## 4. 检测：高可用里最被低估的一半

冗余决定"坏了之后还有多少能力"，而检测决定"坏多久之后才开始使用这些能力"。业务感受到的总损失近似等于 `MTTD + MTTR`（MTTD，Mean Time To Detect，平均发现时间；MTTR，Mean Time To Repair，平均修复时间），而**故障切换的耗时下限就是检测时延**：

```text
# 模板，数值仅示意
若心跳或探活的间隔是 2 秒，且连续失败 3 次才判定为故障，则最坏情况下的检测时延约为 6 秒。
若在此基础上再加上选举与地址漂移所花的时间，则切换所需的最短时间就在这个量级。
```

由此可以得到三条推论。

**第一条推论是探活参数是一次明确的赌注。** 因为把探活间隔与失败阈值调小，能缩短切换时间，但代价是误判率上升，所以网络抖动会被当成故障，于是发生不必要的切换；因此**切换快与切换准只能选一个侧重**。

**第二条推论是 MTTD 通常比 MTTR 更值得先优化。** 因为修复速度受物理条件与流程限制，而发现速度往往只是"多加几条按业务指标的告警"，所以先动检测这一侧的成本更低。

**第三条推论是告警本身要能被信任。** 若值班的人已经习惯"这条告警经常误报"，则它等于不存在；检测链路的可靠性属于阶段 9 的范围（指标语义、告警规则、SLI/SLO，即 Service Level Indicator 服务等级指标与 Service Level Objective 服务等级目标），这里只强调它对可用性的影响：**没有可信的检测，冗余就只是一笔没有人动用的保险。**

## 5. 余量：N+1 与 N+2，以及滚动重启的批次上限

把"还剩多少"变成一个可算的数，需要先定义三个概念。

- **最小可接受容量**：它是业务高峰之上的余量。经验区间是峰值的 1.2~1.5 倍，也就是说容量要按峰值再乘上这个系数来准备。
- **N+1**：在满足最小可接受容量的前提下，它能容忍 **1 个**实例不可用，也就是一次故障。
- **N+2**：它能容忍 **1 个故障加 1 个维护**，所以系统可以一边坏着一边做变更。

滚动重启的批次上限由此决定：**批次大小不能超过余量允许的台数。** 一个反例比公式更有说服力：若共有 4 个实例、单机峰值利用率为 70%，则下线 1 台之后，剩余 3 台各约 133%；**这已经注定失败，并且与 `serial: 1` 无关**，因为 `serial` 只控制同时被改的台数，它不控制剩余实例要承担的负载。正确动作是先扩容，或者把变更挪到低谷并同时限流。

## 常见误解

| 说法 | 事实 |
| --- | --- |
| "我们配了 VIP，所以高可用" | VIP 只回答"地址能不能漂移"，它不回答"存量连接断不断""切完容量够不够""数据丢不丢"这三个问题，因此它不构成高可用的证据。 |
| "有主备就是高可用" | 有主备的系统要能回答四个问题：备机真的在同步吗、切换 RTO（Recovery Time Objective，恢复时间目标）是多少、会丢多少数据、切完容量够不够。答不出这四个问题的主备只是"多了一台机器"。 |
| "双机就够了" | 两台机器如果没有独立心跳与仲裁，就只是把单点故障推迟成了脑裂，因此要能回答"两边看不见对方时，谁闭嘴"。 |
| "`serial: 1` 就安全" | 它只控制同时被改的台数，它不控制剩余负载，因此 4 台实例下线 1 台之后剩余 3 台各 133% 的局面依然会发生。 |
| "`/proc/mdstat` 有阵列就有冗余" | 本机实测 `/proc/mdstat` 里连阵列都没有；而且阵列防的是盘坏，它不防主机、机架与共享依赖。 |
| "健康检查越严越好" | 判得太严会误踢健康后端，若探针还依赖共享依赖，则会批量摘除后端并引发级联故障。 |
| "探活返回 404 就是服务坏了" | 404 说明服务活着、能解析路径、能结构化响应，因此它是有效证据；判据要看业务路径的预期响应，而不是看状态码是不是 200。 |
| "副本是实时的，所以数据不会丢" | 副本防的是硬件失效，它不防逻辑错误，因为误删与坏数据会同步过去；因此它不能替代备份。 |
| "心跳间隔调小就能更快切换" | 确实能更快，但误判率会上升；这是切换快与切换准之间的赌注，因此要按业务的容忍度来选。 |
| "服务发现能替代负载均衡" | 它解决的是"地址从哪来"，而注册中心自身仍需高可用，客户端缓存与过期也要处理。 |

**第一反应不要做什么**：不要用"装了什么组件"证明高可用；不要在没有独立心跳与仲裁的情况下做双机 VIP；不要在探针里依赖共享依赖；不要在只算出"一台都没有余量"的情况下执行滚动重启；不要把副本当备份。

## 要点自测

**问：判断高可用的判据是什么？为什么"配了 VIP"不是判据？**
答：判据是"拔掉任意一台之后业务还剩多少"。VIP 只解决地址漂移，它不回答存量连接断不断、切换要多久、切完容量够不够、数据丢不丢，因此它不能证明高可用。

**问：六层故障域里，哪一层的影响面最大、最容易被漏？**
答：共享依赖这一层影响面最大，也最容易被漏，因为它包含数据库、缓存、消息队列、DNS、统一认证、配置中心。它的故障域不是一台机器，而是所有依赖它的服务，所以影响面可以直接到 100%。

**问：脑裂的定义是什么？无状态服务与有状态服务的后果有什么不同？**
答：脑裂的定义是两边都以为自己该持有资源，于是同时持有、同时服务。无状态服务的后果是请求被分到两台；有状态写服务的后果是数据分叉。防法是独立心跳、仲裁、fencing 与时间同步，再加上"不确定时停服务"这条纪律。

**问：健康检查判得太松与判得太严，后果分别是什么？**
答：判得太松会把流量继续转给已经坏掉的后端，典型原因是只探端口；判得太严会误摘健康后端，若探针还依赖共享依赖，则会批量摘除并引发级联故障。

**问：为什么"摘流量"和"动手"之间要等？三个必须写进 Runbook 的参数是什么？**
答：因为长连接还有存量连接没有结束。三个参数是最长等待时间、排空判据（连接数阈值）与放回后的观察时长。摘流量的验收判据是"外部探失败、本机探成功"。

**问：4 个实例、单机峰值利用率 70%，能不能执行 `serial: 1` 的滚动重启？**
答：不能。因为下线 1 台之后剩余 3 台各约 133%，已经超出单机能力。正确动作是先扩容，或者挪到低谷并限流，而 `serial` 只控制同时被改的台数。

**第一反应不要做什么**：不要把"装了高可用组件"当结论；不要在探针里依赖共享依赖；不要在没算余量的情况下重启；不要在脑裂不确定时继续对外写。
