# 生产变更与事故处置手册

> [!cite] 参考资料
> 本篇是 `11_生产运维与高可用/` 全部子笔记的收口 Runbook，命令与判据均可在对应子笔记里找到出处；`man` 页清单见子笔记 04、05、07、09、10、13、14、15。处置排序（止损优先、一次一个变量、先取证再动手）来自 Google SRE 手册的「Managing Incidents」与「Postmortem Culture」两章。
>
> **实测状态**：实测环境 **Ubuntu 24.04.5 LTS（VMware 虚拟机）/ 内核 `6.8.0-139-generic` / systemd 255（`255.4-1ubuntu8.17`）/ root 可用 / 4 vCPU / `MemTotal` 7894 MiB / 根分区 `/dev/mapper/ubuntu--vg-ubuntu--lv`（ext4 on LVM，46.9 G）**。本篇列出的判据与命令，凡属实验机可执行的都在重跑后写进了各子笔记：`sysctl --system` 加载顺序（14 个文件、17 个键；root 下 0 条 `permission denied`，`realtyz` 下 17 条但退出码仍为 0）、`journalctl --disk-usage` = **20.7 MiB**、`df`/`df -i`/`du`/`lsof +L1`（实验机 `/` 上确有 1 条 journald 持有已删除 journal 文件的记录）、`openssl s_client` 到期检查（`www.example.com` 得 `notAfter=Oct 27 22:17:21 2026 GMT`，链内 4 张）、`rsync --link-dest` 快照与恢复（`base` 101 MiB / `inc-2` 16 KiB / `du --total` 101 MiB / 恢复 0.42 秒）、`systemd`/`ss` 状态检查，以及 `auditctl` 加规则—命中—删规则的完整闭环。**未实测**：多机摘流量与 VIP 切换（实验机单网卡、无 VIP、无 keepalived）、Ansible 批量执行（未安装）、restic/borg 恢复（未安装）、补丁窗口与重启批次（不改动实验机的补丁状态）、带外管理与救援介质（只能 SSH 访问、没有控制台）、写坏 `/etc/fstab` 与只读根——相关小节只给流程与判据，已标注。

## 0. 30 秒速览

> [!abstract] 这一篇只要记住六句话
> - **事故中的处置顺序：止损 → 取证 → 根因；每一步都先问「这一步可逆吗」。**
>   - 怎么验证：把第一步写成「限流/摘流量/回滚」，而不是「登录上去查日志」；查日志由并行的另一条线做。
> - **变更失败时，回滚判断由动手前写好的触发条件决定。**
>   - 证据：触发条件写成「错误率 > 1% 持续 5 分钟」这类可判定句子，命中即回滚，现场不再讨论（子笔记 07）。
> - **「一批里部分成功」比「全失败」更危险。**
>   - 怎么验证：先确认有多少台处于中间状态（半成品），再决定是「补齐」还是「全部退回」；**不许在状态不清的情况下继续往下做**。
> - **通报的第一句话要包含三件事：影响什么、当前状态、下一步与时间点。**
>   - 怎么验证：把通报模板里的三句话背下来；答不出「下一步什么时候」，说明处置还没组织起来。
> - **复盘的对象是「未解释的现象」，不是「是否成功」。**
>   - 证据：0.8% 的错误率上升没命中 1% 阈值，只差 0.2 个百分点——那是运气，不是安全边际（子笔记 08）。
> - **任何「只有我会做」的动作，都是下一次事故的放大器。**
>   - 怎么验证：把恢复步骤写成 Runbook，让另一个人照着做过一次（子笔记 08）。

## 1. 变更失败：回滚还是继续

> [!tip] 第一反应不要是「先看看能不能修好」
> 触发条件已经写好了。命中即回滚，别在压力下重新讨论判据。

先记录决策时刻，再**逐条照抄变更单上预先写好的回滚命令**（不要临场改）：

```bash
date -Is                                   # 验证：记录回滚决策时刻（复盘要用）
```

**判据与处置**：

| 情况 | 结论 | 处置 |
| --- | --- | --- |
| 命中回滚触发条件 | 回滚 | 按预案执行，不再讨论；记录回滚前的指标 |
| 未命中，但现象无法解释 | 暂停扩批 | 保留现场后排查；不在未知状态上扩大范围 |
| 未命中，且属于已知噪声（有历史基线支撑） | 继续 | 把判断依据写进执行记录 |
| 已回滚但现象仍在 | 升级 | 说明回滚未生效（配置、进程、连接三层逐项确认），进入事故响应 |

**回滚后的验收**（缺一不可）：运行时值/版本回到旧值 → 服务状态 `active` → 业务探活通过 → 观察窗口内指标回到基线。

## 2. 一批里部分成功（不一致状态）

> [!tip] 第一反应不要是「把失败的那几台重跑一遍」
> 先确认失败的那几台**处在什么状态**：完全没改、改了一半、还是改完但没 reload。

逐台核对「预期状态」与「实际状态」：

```bash
for h in $(cat hosts.txt); do
  printf '%s ' "$h"
  ssh -o BatchMode=yes -o ConnectTimeout=5 -n "$h" \
    'sysctl -n net.core.somaxconn; systemctl is-active nginx'
done
```

**三种处置路径**：

| 状态 | 处置 |
| --- | --- |
| 全部处于「旧状态」 | 修好根因后，用同一份清单重跑（要求脚本幂等） |
| 混合状态（部分新、部分旧） | **先把已改的退回旧状态**，让整体一致，再整批重来 |
| 无法判断状态 | 停手，逐台人工核对；此时最忌讳「猜着往下做」 |

**不一致状态的危险在于它制造了「最难排查的故障形态」**：同一服务在不同机器上行为不同，表现为间歇性失败。

## 3. 事故响应：分级、通报、止损

### 3.1 分级与角色

| 级别 | 判据 | 响应 |
| --- | --- | --- |
| **P1** | 核心业务不可用或数据面临丢失风险 | 立刻叫醒关键人；成立处置小组；每 10~15 分钟同步一次 |
| **P2** | 部分用户受影响、有降级可用 | 立即响应；30 分钟内升级条件明确 |
| **P3** | 影响小或已自动恢复 | 记录并按计划处理 |

角色：**指挥**（决定止损方案与优先级）、**执行**（按指令动手）、**取证**（保存现场与证据）、**通报**（对外沟通）。人少时一人兼多职，但**「谁做决定」必须唯一**。

### 3.2 通报模板

```text
【现象】<什么不可用，影响到谁>
【范围】<多少用户/实例/接口；是否还在扩大>
【开始时间】<YYYY-MM-DD HH:MM>（时区）
【当前状态】<处置中 / 已止损 / 已恢复>
【已知原因】<已确认的事实；不确定就写"待确认">
【下一步】<动作 + 负责人 + 时间点>
【下次通报】<HH:MM>
```

> [!warning] 通报里不要写没验证的猜测
> 「疑似发布导致」与「已确认是发布导致」是两句话。通报的作用是让人做决策，不是展示推理过程；**事实、推测、待确认三态要分开写**。

### 3.3 止损动作的优先级

```text
限流（降低压力，可逆） → 摘流量（隔离坏实例，可逆） → 回滚（回到已知好状态）
  → 扩容（增加容量） → 重启（最后手段，会毁现场）
```

每一步都要写下「预期效果、验收指标、回滚方式」；**一次只改一个变量**。

## 4. 发布后错误率上升

> [!tip] 第一反应不要是「先扩容」

```bash
date -Is                                   # 验证：确认时间点，与发布记录对齐
git -C <repo> log -1 --oneline 2>/dev/null  # 验证：确认当前版本
journalctl -u <unit> --since "10 min ago" --no-pager | grep -icE 'error|exception'
systemctl show <unit> -p ActiveState -p NRestarts -p MainPID
```

**决策线**：错误率与发布时间的间隔（秒级/分钟级 → 强关联）；是否有对照组（未发布的实例是否正常）；回滚成本（回滚一次发布的耗时是否小于继续排查的时间）。

**处置**：优先回滚到上一个已知好版本（如果回滚是幂等且快速的），再在非生产环境排查根因。

## 5. 单机故障：流量切换不生效

```bash
ss -lnt; ss -s                             # 验证：服务还在不在听、连接分布
ip -brief addr                             # 验证：VIP 在当前机器上吗
systemctl is-active keepalived             # 验证：VIP 漂移组件状态（用 HAProxy 就换成 haproxy）
timedatectl                                # 验证：时间同步（心跳判定依赖时间）
```

**实验机的实测基线可以直接当反面对照用**：`ip -brief addr` 只有 `lo` 与 `ens33`（无任何 VIP）、`ss -lnt` 对外只有 `0.0.0.0:22` 与 `[::]:22` 两条监听（同一个 `sshd`，`ss -lntp` 显示 `pid=1348`）、`systemctl list-units` 里没有 `keepalived`/`haproxy` 单元。所以本节的三条判据在实验机上**只能验证「没有 VIP 时长什么样」**，验证不了「VIP 在两台 = 脑裂」——那条需要第二台机器。

**判据**：

| 现象 | 结论 | 处置 |
| --- | --- | --- |
| 后端仍在列表、流量仍在进 | 摘流量没生效 | 查健康检查、服务发现、客户端缓存与长连接 |
| VIP 不在任何一台 | 选举异常 | 查心跳链路、优先级配置、时间同步 |
| VIP 在两台 | **脑裂** | 按预案强制一方下线（fencing），先保数据一致性 |
| 剩下一台容量不够 | 无余量 | 限流保命；事后补 N+1 余量（子笔记 12） |

## 6. 根分区满 / 日志写满

```bash
df -h; df -i                               # 验证：容量与 inode 两个口径
du -sh /* 2>/dev/null | sort -rh | head    # 验证：找出大户
lsof +L1 2>/dev/null | head                # 验证：已删除但被进程持有的文件
journalctl --disk-usage                    # 验证：journal 的占用（实验机实测 20.7 MiB）
```

**处置顺序**：取证（四口径）→ 判断类别 → 释放空间（优先释放**可再生**的数据：旧日志、缓存、已处理完的临时文件）→ 验收（业务写入恢复）→ 补策略（保留期、上限、告警）。

> [!warning] 不要删的三样东西
> **备份文件、数据库数据目录、正在写的日志**。删它们能把盘腾出来，但代价可能是数据丢失或丢失排查现场——宁可先清缓存。

## 7. 参数改了不生效

```bash
sysctl -n <键>                             # 验证：运行时值（第一件事）
grep -rn '<键>' /etc/sysctl.d /usr/lib/sysctl.d /run/sysctl.d /etc/sysctl.conf
                                          # 验证：找出所有写入点（谁最后写谁生效）
sysctl --system 2>&1 | grep -i '<键>'      # 验证：应用过程有没有被拒
```

**判据**：实验机实测的加载顺序是「目录合并按文件名排序（`/run/sysctl.d` 不存在就不参与），同名文件 `/etc` 优先，最后应用 `/etc/sysctl.conf`」，共 **14 个文件、17 个键**；后加载的覆盖先加载的。**结论是「文件改对了但值没变」时，先找覆盖它的那个文件。** 另一个常见误判要记住：**以 `realtyz`（uid=1000）跑 `sysctl --system` 会打印 17 条 `sysctl: permission denied on key "…", ignoring`，但退出码仍是 0**——被拒的键只是被跳过，所以「有没有报错」不能当验收判据，必须 `sysctl -n` 回读。

## 8. 证书即将过期 / 已过期

```bash
openssl s_client -connect <host>:443 -servername <host> </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates
                                          # 验证：线上实际生效证书的到期时间（2026-09-19 08:08 UTC 采集 www.example.com 得 notAfter=Oct 27 22:17:21 2026 GMT，剩余 38 天）
openssl s_client -connect <host>:443 -servername <host> -showcerts </dev/null 2>/dev/null \
  | grep -c 'BEGIN CERTIFICATE'            # 验证：服务端发出的证书张数（实验机实测 4 张）
```

**处置顺序**：先保住可用性（启用备用证书/备用域名/临时延长）→ 再做正式更换 → 最后补治理（台账、责任人、30 天告警、自动续期失败告警）。**顺带核对时钟**：证书校验、日志时间戳、心跳判定都依赖时间，而 `NTP service: active` 不等于时钟已同步——实验机就处于 `System clock synchronized: no` 的状态。

## 9. 备份恢复失败

```bash
ls -l <备份路径>                            # 验证：文件在不在、大小是否合理
sha256sum <备份文件>                        # 验证：与记录中的校验和对比
restic check 2>/dev/null || borg check <repo> 2>/dev/null
                                          # 验证：仓库完整性（实验机未安装 restic/borg，跳过）
df -h                                       # 验证：恢复目标有空间吗（最常见原因）
```

**判据与处置**：空间不足 → 先腾空间；校验和不符 → 说明备份本身损坏，改用上一份；仓库损坏 → 立即检查其余副本与异地副本，并把这次失败作为 P2 以上事件处理（因为**你此刻没有可用的恢复手段**）。

## 10. 系统起不来 / 登录不进去

下面这些命令**在带外控制台或虚拟化控制台上执行**（SSH 已经进不去了）：

```bash
ls /sys/firmware/efi 2>/dev/null && echo UEFI || echo "BIOS/legacy 或虚拟化"
lsblk -o NAME,SIZE,FSTYPE,PARTTYPENAME,MOUNTPOINT
blkid
journalctl -k -b -1 --no-pager | tail -50  # 验证：上次启动的内核日志（需要持久化日志）
```

**顺序**：拿到控制台 → 判断卡在哪一环 → 先保住数据（镜像/快照）→ 再决定修还是重建。**在这个场景里，「重启一次看看」是最常见的错误第一步**（子笔记 11）。

**实验机边界**：它有真实的 `/boot` 分区与 GRUB（BIOS/legacy 引导），所以「引导器存在」这件事是可验证的；但**它只能通过 SSH 访问、没有控制台**，上面的命令只能做只读版本（`lsblk`/`blkid`/`findmnt --verify`/`journalctl -k`，见子笔记 11），**「卡在哪一环」的判断无法在实验机上演练**——因为演练它的前提是「已经进不去系统了」，而那时 SSH 也没了。

## 11. 批量执行失败 / 留下半成品

```bash
pgrep -af '<脚本名>'                        # 验证：还有没有残留进程
ls -l /var/lock/<锁名>                      # 验证：锁有没有被释放
ls -ld /var/tmp/<临时目录>                   # 验证：临时目录有没有留下
```

**处置**：确认残留 → 判断已执行部分是否可重入 → 修好根因 → **按幂等前提重跑**（不是「无条件再跑一遍」）。事后必须补两件事：脚本的失败处理、超时与锁。

## 12. 交接：不要让恢复知识只留在一个人手里

```text
[ ] 关键处置动作已有 Runbook，且包含「判据 + 命令 + 验收 + 升级条件」
[ ] 至少有一位同事照着 Runbook 独立执行过一次
[ ] 成对的值班与升级路径已写明（谁的下一级是谁）
[ ] 敏感材料（密钥、控制台口令、加密解锁材料）存放位置已登记，且有权限控制
[ ] 最近一次演练的时间与结论已记录
```

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 事故中先查根因 | 业务还在恶化；止损与取证应同时由两条线做 |
| 命中回滚条件还继续观察 | 等待的每分钟都在扩大影响面；触发条件就是为此存在的 |
| 部分成功后「重跑失败的几台」 | 混合状态会制造间歇性失败；要先让整体一致 |
| 通报里写未验证的猜测 | 会误导决策；事实、推测、待确认要分开 |
| 一边限流一边扩容 | 两个变量同时改，无法归因 |
| 根分区满了先删日志 | 可能删掉排查现场；优先释放可再生的缓存与旧数据 |
| 重复改同一个参数文件 | 不生效的原因是覆盖；要先找出所有写入点 |
| 证书只在过期时处理 | 过期即事故；要按剩余天数分级告警 |
| 备份恢复失败才想找第二个副本 | 应该定期验证副本可用性（子笔记 10） |
| 「重启一下试试」用在系统起不来的场景 | 会刷掉唯一的错误信息；先拿控制台、先取证 |
| 重跑非幂等脚本「修」半成品 | 可能重复追加、重复插入、重复创建 |

## 决策练习

> [!question]- 场景：晚上 9 点，你发布了一个新版本到 10 个实例中的 3 个（灰度批次）。5 分钟后错误率从 0.1% 升到 0.8%，未命中触发条件（1% 持续 5 分钟）。业务方在群里问「是不是有问题」，同事说「再等等，还没到 1%」。
> A. 等到命中触发条件再回滚
> B. 立刻停止扩批，记录当前证据（错误率曲线、日志、时间点），判断错误率上升是否与新版本强相关（对比未发布的 7 个实例），并准备好在错误率继续上升时立即回滚；同时按通报模板同步现状
> C. 立刻回滚那 3 个实例
>
> **答案：B。**
> A 是「照着阈值办事」的机械做法：阈值是用来定义「必须无条件止损」的底线，**不是用来禁止更早的判断**。0.8% 已经接近阈值且与发布强相关，此刻最该做的是**准备回滚 + 保留证据**。
> C 虽然安全，但跳过了一个有价值的判断：如果未发布的 7 个实例错误率同样上升，那就不是发布的问题，回滚解决不了问题还会掩盖真正的根因。
> B 是正解：**停止扩大影响（不扩批）+ 取证 + 用对照组判断相关性 + 准备止损 + 对外同步**。这也是本篇第 1、3、4 节动作的组合。

## 要点自测

> [!question]- 事故中的处置顺序是什么？为什么根因不是第一步？
> - 止损 → 取证 → 根因。
> - 因为业务还在受损时，每多等一分钟损失都在扩大；取证可以由并行的另一条线完成。
> - **第一反应不要是什么**：不要一上来就登录服务器查日志。

> [!question]- 「一批里部分成功」为什么比「全失败」更危险？
> - 它制造了不一致状态，表现为间歇性失败——这是最难排查的故障形态。
> - 处置路径：先确认每台的状态，再决定「补齐」还是「整体退回」。
> - **第一反应不要是什么**：不要直接重跑失败的那几台。

> [!question]- 通报第一句要包含哪三件事？
> - 影响什么、当前状态、下一步与时间点。
> - 并且要把「事实 / 推测 / 待确认」分开写。
> - **第一反应不要是什么**：不要在通报里写还没验证的猜测。

> [!question]- 变更失败时，回滚决策依据什么？
> - 依据动手前写好的触发条件（有指标、有阈值、有持续时间）。
> - 命中即回滚；回滚之后还要用同一组判据复验。
> - **第一反应不要是什么**：不要在故障中重新讨论「要不要回滚」。

> [!question]- 为什么「只有我会做」是风险？
> - 那个人不在（休假、离职、同时在处理别的事故）时，恢复能力就是 0。
> - 解法：Runbook + 演练 + 至少一位同事独立执行过一次。
> - **第一反应不要是什么**：不要把「我在就没事」当成可靠状态。
