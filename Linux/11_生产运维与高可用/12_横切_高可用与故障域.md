## 0. 30 秒速览

> [!abstract] 这一篇只要记住六句话
> - **高可用的判据是「拔掉一台之后业务还剩多少」，不是「我配了 VIP」。**
>   - 怎么验证：对每一台关键机器问「它挂了谁会受影响、剩下的容量够不够」；答不上来就说明影响面没算过。
> - **故障域是一层套一层的：进程 → 主机 → 机架 → 可用区 → 机房。**
>   - 证据：三副本全在同一台宿主机上，等于只有一份；两台机器在同一机架、同一路电源上，一次掉电一起挂。
> - **脑裂的代价通常比宕机更大：两边同时写，数据会分叉。**
>   - 怎么验证：至少要有一路**独立的**判定通道（直连心跳/第三方仲裁），并且规定「判定不确定时怎么办」（通常是停服务，而不是两边都继续）。
> - **健康检查判得太松会把请求转给坏后端，判得太严会反复误踢。**
>   - 证据：只检查「端口在听」会漏掉「业务逻辑已坏」；只检查一次失败就摘，会让慢请求引发的抖动变成批量摘除。
> - **滚动重启必须留容量余量：N+1 是底线，N+2 才敢做计划内维护。**
>   - 怎么验证：算一遍「同时不可用多少实例时，剩余容量仍能承受峰值流量」；这个数字直接决定 `serial` 批次大小。
> - **副本保证可用，备份保证可恢复——两者都不能省，而且互不替代。**
>   - 证据：副本会同步逻辑错误（`rm`、坏数据），所以它在「误删」「被加密」这类场景上帮不上忙（子笔记 03、10）。

## 1. 故障域：先算清「坏一台会怎样」

### 1.1 六层故障域

| 层 | 一起失效的范围 | 典型原因 | 缓解手段 |
| --- | --- | --- | --- |
| 进程 | 单个进程 | 崩溃、OOM、死锁 | systemd 的 `Restart=`、健康检查、进程监控 |
| 主机 | 一台机器 | 硬件故障、内核崩溃、系统盘坏 | 多副本 + 负载均衡；重建能力（子笔记 11） |
| 机架/电源 | 一个机架 | 电源、交换机、机架级散热 | 跨机架部署 |
| 可用区 | 一个机房分区 | 供电、制冷、网络 | 跨可用区部署；跨可用区数据同步 |
| 机房/区域 | 整个机房 | 灾害、骨干网中断 | 异地多活或异地灾备（回到 RTO/RPO） |
| 共享依赖 | 所有依赖它的服务 | 同一个数据库、注册中心、DNS、证书 | 依赖降级、限流、缓存、多活实例 |

最后一行最容易被漏：**共享依赖的故障域是「所有依赖它的服务」**。一次事故里，「一台机器挂了」和「一个共享 Redis 挂了」，前者的影响面是 1/N，后者可能是 100%。

### 1.2 「拔掉一台会怎样」的判定表

| 问题 | 怎么查 | 危险信号 |
| --- | --- | --- |
| 它是单实例吗？ | 反向代理/LB 的后端列表、服务发现的实例数 | 只有 1 个后端 |
| 它挂了流量会切吗？ | 健康检查配置、探针路径 | 探针只测端口、探测间隔过长 |
| 切换过程中连接会断吗？ | 连接排空（draining）配置、长连接 | 没有排空，切换即断连 |
| 剩下的容量够吗？ | 当前峰值 / 剩余实例数 | 剩余容量 < 峰值 |
| 数据还在吗？ | 数据是否复制到其它节点、复制是否同步 | 只有一个写节点且无同步副本 |

```bash
ss -lnt                                   # 验证：本机对外提供什么
ss -s                                     # 验证：当前连接总量（估算切换时的存量连接）
systemctl list-units --type=service --state=running --no-pager | head -30
                                          # 验证：这台机器上跑着哪些关键服务
ip -brief addr                            # 验证：有没有 VIP（有 VIP 说明它可能承担接入角色）
timedatectl                               # 验证：时间同步状态（时间不同步会直接影响心跳判定）
```

> [!tip] 第一反应不要是「我们有主备，所以是双活」
> **主备 ≠ 高可用**。主备只解决「主机挂了能不能顶上」，不解决：备机是不是真的同步、切换要多久（RTO）、切换期间丢多少数据（RPO）、切过去之后主机的容量够不够。这四件事都要有答案，才敢说「这台机器挂了不影响业务」。

## 2. 三层高可用

### 2.1 接入层：流量怎么找到「还活着的那一个」

| 方式 | 做法 | 注意 |
| --- | --- | --- |
| **VIP 漂移** | 两台机器共享一个虚拟 IP，只有持有者响应 ARP | 需要心跳与仲裁；切换是「整台接管」，粒度粗 |
| **负载均衡器** | 前端把请求分给多个后端，按健康检查决定给谁 | 健康检查、排空、会话保持都要配 |
| **DNS 多值/轮询** | 同名解析到多个地址 | **受 TTL（记录的缓存有效期）限制，无法快速回滚**；客户端缓存会放大问题 |
| **服务发现** | 客户端/边车从注册中心拿实例列表 | 依赖注册中心本身的高可用 |

### 2.2 VIP 与脑裂

VIP 的典型实现是 **VRRP（Virtual Router Redundancy Protocol，虚拟路由冗余协议）**：一组机器协商出一个「主」，主持有 VIP 并周期性地发通告；备机收不到通告就认为主机挂了，接管 VIP。下面是 `/etc/keepalived/keepalived.conf` 的双机最小骨架（未实测，写法来自 keepalived 文档）：

```ini
vrrp_instance VI_1 {
    state BACKUP          # 两台都写 BACKUP，靠优先级选举，避免主抢先
    interface eth0
    virtual_router_id 51  # 同一网段内必须唯一
    priority 100          # 数值大者优先；两台不要设成相同
    advert_int 1          # 通告间隔（秒）
    authentication {
        auth_type PASS
        auth_pass <口令>
    }
    virtual_ipaddress {
        10.0.1.100/24
    }
}
```

**脑裂（split brain）**：两台机器都联系不上对方，于是都认为自己是主，**同时持有 VIP、同时对外服务**。对无状态读服务可能只是流量重复；对数据库、写服务就是数据分叉。

| 防脑裂手段 | 说明 | 局限 |
| --- | --- | --- |
| 独立心跳链路（直连网线/VLAN） | 通告不走业务网络，减少「业务网抖一下两边就分裂」 | 直连链路本身故障时仍需仲裁 |
| 第三方仲裁（quorum） | 由第三个节点判断谁该持有资源 | 需要第三个节点，成本更高 |
| 时间同步 | 日志与判定必须可比 | 不能替代仲裁 |
| **Fencing（隔离）** | 判定不确定时把一方强制下线（关电源/断网），保证只有一方活着 | 需要能远程控制电源（IPMI/云 API） |
| 不确定时停服务 | 保一致（放弃可用） | 会牺牲可用性，需要业务方接受 |

> [!warning] 双机 + 无仲裁 = 没有高可用，只有「延迟故障」
> 双机保持在同一个网络里、又没有第三方判定，那么任何一次网络抖动都可能变成脑裂。**设计时要明确回答一句：当两边互相看不见时，谁闭嘴？** 答不出来，就不算做过高可用设计。

### 2.3 服务层与数据层

| 层 | 做法 | 关键判据 |
| --- | --- | --- |
| **服务层** | 无状态化 + 多副本 + 滚动发布 | 任意实例可被替换；会话状态外置（不要「粘在某一台」） |
| **数据层** | 主从复制、多副本、分布式一致性协议 | 复制延迟（RPO 的现实来源）、故障切换由谁决定、切换后是否可能丢数据 |
| **依赖层** | 缓存、限流、降级、超时 | 依赖不可用时，我是快速失败还是被拖死 |

数据层的复杂决策（保可用还是保一致）属于 **CAP 取舍**——一致性（Consistency）、可用性（Availability）、分区容忍（Partition tolerance）三者不可同时完全满足，本篇只给判据：**先问业务能接受丢数据还是能接受不可用**，答案直接决定方案。

## 3. 健康检查：判据不好，一切白搭

### 3.1 判得太松与判得太严

| 判据设计 | 后果 |
| --- | --- |
| 只检查端口在听 | 后端进程活着但业务逻辑已坏（依赖断了、配置错了）→ 请求被转给坏后端 |
| 检查一次失败就摘 | 一次慢请求引发的超时 → 批量摘除 → 剩余实例被打爆（级联故障） |
| 探测间隔太长 | 坏后端在长达数十秒内持续收流量 |
| 探测路径依赖共享依赖 | 共享依赖抖动 → 所有后端被同时摘除 → 全站不可用 |
| 只摘不放（无恢复探测） | 后端修好了也回不来 |

### 3.2 排空（draining）与切回

```text
摘流量 → 等待存量请求结束（或到上限时间）→ 变更 → 单机验证 → 放回流量 → 观察
```

排空的三个参数要写进 Runbook：**最长等待时间**（超过就强制）、**怎么判断请求已排空**（连接数降到阈值）、**放回之后观察多久**。

```bash
ss -tn state established '( sport = :8443 )' | wc -l
                                          # 验证：存量连接数（判断是否可以进入下一步）
```

## 4. 滚动重启与容量余量

### 4.1 为什么必须有容量余量

滚动重启的本质是「用一部分容量换取安全的变更节奏」。**没有余量时，滚动重启就是分批制造过载**。

```text
最小可接受容量 = 峰值流量 × 安全系数（常见 1.2~1.5）
N+1 余量：能承受 1 个实例不可用
N+2 余量：能承受 1 个实例故障 + 1 个实例维护
```

| 场景 | 需要余量 |
| --- | --- |
| 只做故障容忍 | N+1 |
| 计划内维护（滚动重启、扩缩容、换盘） | N+2 |
| 跨可用区容灾 | 每个可用区都要能承接全量流量（或者接受降级） |

### 4.2 滚动重启的批次

批次大小由三件事决定：**余量**（上面算出来的）、**单台恢复速度**（重启后多久能接流量）、**业务能容忍的性能劣化**。常见做法是把 `serial` 设成「余量允许的最大值」，而不是「机器总数的 1/10」。

> [!example]- 实验 9：纸面推演 + 单机可做的部分（实验机 / 白板）
> **怎么做**：① 找一个真实的（或假设的）N 实例服务，写下它的实例数、峰值流量、单实例处理能力；② 算出 N+1 与 N+2 各自允许的「同时不可用实例数」；③ 用这个数字反推滚动重启的 `serial` 批次；④ 在实验机上演练单台侧的动作：摘流量 → 验证本机探活 → 重启服务 → 单机验证 → 放回流量，并记录每一步的耗时。
> **预期**：得到一份「这个服务能承受多少台同时不可用」的结论，以及一份单台切换的实测耗时。**这两个数字是滚动重启方案的全部依据**。
> **风险**：低（单机侧动作；不涉及真实 LB）。**不要在没有第二台的情况下假装演练 VIP 切换**——那只能练纸面。
> **耗时**：约 40 分钟。
> **怎么退回去**：服务保持运行；清理演练记录外的临时文件。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 「配了 VIP 就是高可用」 | 还要回答：备机是否真同步、切换多久、切换期间丢多少数据、切过去容量够不够 |
| 双机无仲裁 | 网络抖动即脑裂，两边同时写会造成数据分叉 |
| 三副本放同一台宿主机/同一机架 | 故障域重叠，实际只有一份 |
| 健康检查只探测端口 | 业务已坏但端口在听，请求继续被转给它 |
| 一次探测失败就摘除 | 慢请求引发的抖动会变成批量摘除，触发级联故障 |
| 探针路径依赖共享依赖 | 共享依赖抖动导致所有后端同时被摘，全站不可用 |
| 没有连接排空 | 切换即断连，长连接业务会大面积报错 |
| 用 DNS 做快速切换 | 受 TTL 与客户端缓存限制，做不到分钟级切换，也做不到快速回滚 |
| 没有余量就滚动重启 | 每批都在制造过载；高峰期直接打崩 |
| 把副本当备份 | 副本同步逻辑错误；误删、坏数据、加密都会一起同步 |
| 时间不同步 | 心跳判定、日志比对、证书校验全部受影响 |

## 决策练习

> [!question]- 场景：一个服务有 4 个实例，正常峰值时单实例 CPU 已到 70%。老板要求做一次滚动重启（升级配置）。同事说「`serial: 1`，一台一台来，很安全」。
> A. 同意——一台一台来最稳，`serial: 1` 就是标准做法
> B. 先算余量：4 台里一台下线后剩 3 台，每台要承担约 133% 的流量，而单实例 CPU 已到 70% → **没有 N+1 余量**；因此不能直接滚动重启。先扩容 1~2 台（或选在低谷并限流），再按「余量允许的最大批次」执行，同时把回滚条件写清
> C. 直接一次性重启 4 台——反正重启很快，业务感知不到
>
> **答案：B。**
> A 错在把「批次小」当成了「安全」：`serial: 1` 只控制**同时被改的实例数**，控制不了**剩余实例的负载**。没有余量时，一台一台来同样是过载。
> C 是典型的「重启很快所以没关系」——一次性重启意味着**容量归零一段时间**，业务不是「感知不到」，而是「必然中断」。
> B 是正解：**先算余量，再定批次**。这道题的答案不是「怎么重启」，而是「在不扩容的前提下，这个变更现在不该做」——这正是 **P7 故障域与高可用判断**要练的判断力。

## 要点自测

> [!question]- 六层故障域是什么？哪一层最容易被漏？
> - 进程、主机、机架/电源、可用区、机房/区域、共享依赖。
> - 最容易漏的是**共享依赖**：它的故障域是「所有依赖它的服务」，影响面可能是 100%。
> - **第一反应不要是什么**：不要只看「机器有几台」，不看它们是否共享电源、机架、宿主机、数据库。

> [!question]- 什么是脑裂？怎么防？
> - 两台机器互相联系不上，都认为自己是主，同时对外服务；对写服务会造成数据分叉。
> - 防护手段：独立心跳链路、第三方仲裁、时间同步、fencing、规定「判定不确定时停服务」。
> - **第一反应不要是什么**：不要以为「配了两台」就等于「不会脑裂」。

> [!question]- 健康检查判得太松、太严分别会怎样？
> - 太松（只探端口）→ 请求被转给已经坏掉的后端。
> - 太严（一次失败即摘、探针依赖共享依赖）→ 抖动变成批量摘除，引发级联故障。
> - **第一反应不要是什么**：不要把探针路径写成依赖共享依赖的接口。

> [!question]- 滚动重启为什么需要容量余量？N+1 与 N+2 分别是什么？
> - 因为批次推进期间总有实例不可用；没有余量时，每批都在制造过载。
> - N+1：能承受 1 个实例不可用；N+2：能承受 1 个故障 + 1 个计划内维护。
> - **第一反应不要是什么**：不要把 `serial` 设小当成「安全」，余量才是安全。

> [!question]- 为什么副本不能替代备份？
> - 副本是实时同步的，逻辑错误（误删、坏数据、被加密）会一起同步过去。
> - 副本解决「机器/进程故障」，备份解决「数据被改坏或删掉」。
> - **第一反应不要是什么**：不要用「我们有副本」回答「数据怎么恢复」。
