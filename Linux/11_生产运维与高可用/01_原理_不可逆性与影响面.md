# 不可逆性与影响面

同样一句「改一行配置」，若改的是日志级别、改的是 DNS 记录，则审批层级能差两级；同样一句「重启一下」，若重启的是一台无状态实例、一次性重启的是整个集群，则业务后果差着几个数量级。这两件事背后是同一条机制：**在生产上，动作的风险不是由改动量决定的，而是由「做错了还能不能退回去」和「错了之后波及多远」共同决定的。**

## 1. 第一分类标准是可逆性，不是难度

日常里我们习惯按「难不难」给事情分类：由于难的事情交给专家、简单的事情随手做，所以这套习惯在生产环境里会失效。原因是失败率与失败代价并不同向：最难的操作往往失败率很低（内核升级一次就成），而最简单的操作一旦失败就无法收回：

```bash
ip route del default                  # 一条命令，打错一个网段就与这台机器失联
```

这类动作的共同点是**它不问你「你确定吗」，也不留下「原来是什么」的记录**。因此分类必须换一个维度，按**可逆性**分三档，判据是原状态还在不在。

| 档位 | 定义 | 典型动作 | 处理方式 |
| --- | --- | --- | --- |
| 只读 | 这类动作不改变系统状态，因此不存在需要退回的改动。 | 这类动作的典型例子是 `ss`、`df`、`du`、`journalctl`、`systemctl show`、`openssl s_client -connect`。 | 这类动作不改变系统状态，因此生产机上随时可以做。 |
| 可回滚 | 这类动作改变了系统状态，但在已知时间内能退回原状。 | 这类动作的典型例子是改配置后 reload、启停服务、调整挂载选项、增减实例、改一个 `sysctl` 值。 | 由于退回动作必须在时限内完成，所以应先把回滚命令写出来并在实验机上跑过，再动手。 |
| 不可逆 | 这类动作做完之后无法回到原状。 | 这类动作的典型例子是 `rm -rf`、`mkfs`、`lvreduce`、`xfs_repair -L`、`DROP TABLE`、`fsck -y`、一次性全量重启、DNS 记录变更。 | 由于这类动作没有回退路径，所以必须有备份或快照，且要有第二人确认。 |

三档之间的界线不是「看起来危险不危险」，而是**原状态还在不在**。若按这条界线去判，则有三处最容易判错：

- **`rm` 之后的文件并不总是立刻消失。** 若文件仍被某个进程打开着，则 inode 与数据块会一直留到最后一个句柄关闭（见《原理：可恢复性的语言》里 `lsof +L1` 的读法）。但这不改变结论：`rm` 仍然按不可逆处理，因为「恰好有进程持有」是运气，不是设计。
- **写入量小不等于可逆。** `lvreduce` 只是改一个元数据数字，但它会把尾部数据块交还给池子，因此一旦缩错，这些数据块就再也拿不回来。
- **有些动作的可逆性取决于别人。** 改 DNS 记录本身可以再改回去，但已经缓存了旧记录（TTL，Time To Live，生存时间）的客户端不会跟着回退。因此**TTL 未过期之前，这次变更既无法完全生效，也无法真正回滚**——这是一个「看起来可逆、实际不可逆」的典型。

### 1.1 一个动作要算「可回滚」，需要同时满足三条

这三条缺任何一条，这个动作就该按不可逆处理——先备份，再动手：

1. **回退路径必须真的存在**：原文件、原版本与原数据都要还在，并且没有被覆盖掉。用 `cp -a app.conf app.conf.bak` 做备份时，若第二次执行会覆盖掉第一份 `.bak`，则回退路径就只剩一层，等于没有。
2. **回退路径必须已经验证过**：回滚命令要在实验机上真跑通过，而不是停在「理论上应该行」。本机实测把 `vm.swappiness` 从 60 改到 10 再改回来，apply 用了 3 ms、rollback 用了 4 ms——这个数字只有在跑过之后才知道，而它决定了这次变更能不能放进 30 秒的窗口里。
3. **回退耗时必须短于业务能容忍的中断时间**：这个上限就是 RTO（Recovery Time Objective，恢复时间目标）。若回滚比变更本身还慢，则这次变更等于没有回滚方案。

## 2. 影响面由四个维度决定

可逆性决定「错了能不能回来」，影响面决定「错了有多疼」。估计影响面最常见的错误是**只看自己这一层**，例如「我只是重启一下 Nginx」。由于依赖关系会向两头传播，所以真实的影响面要沿依赖往两头各走一步：**谁依赖我**（我挂了谁报错），以及**我依赖谁**（我重试会不会把对端打挂）。

| 维度 | 要回答的问题 | 现场怎么取 |
| --- | --- | --- |
| 用户 | 这次动作影响多少用户、多少租户、哪些地区？ | 现场读业务指标（在线数、QPS，Queries Per Second，每秒查询数）与调用方的接入配置。 |
| 服务 | 这次动作影响哪些服务，这些服务的上下游各是谁？ | 现场读服务依赖图，用 `ss -tnp` 看谁连过来，并用 `systemctl list-dependencies --reverse` 看谁依赖这个单元。 |
| 数据 | 这次动作会不会写坏或删掉数据，这些数据可不可恢复？ | 现场读数据目录与最近一次成功备份的时间，并确认这台机器是不是主库。 |
| 时间 | 这次动作的影响持续多久，是数秒抖动还是数小时不可用？ | 现场读灰度批次规模、回滚耗时与业务高峰时段。 |

同一台机器上，不同动作的影响面可以差好几个量级：

| 动作 | 波及范围 | 典型影响面 |
| --- | --- | --- |
| 加一行监控采集配置 | 这次动作只波及这台机器 | 这次动作不产生可见影响，因为新增的只是只读采集 |
| 换一个证书文件并 reload | 这次动作波及这台机器上的某个服务 | 业务会经历一次毫秒级 reload 抖动 |
| 重启一个无状态服务实例 | 这次动作只波及这一个实例 | 存量连接会断开，随后由负载均衡补位 |
| 重启数据库从库 | 这次动作波及这台实例，并波及依赖它的读请求 | 读请求会降级或失败，因此需要先摘流量 |
| 改 DNS 记录 | 这次动作波及所有解析这个域名的客户端 | 这次动作的影响要视 TTL 而定；由于 **TTL 未过期前无法回滚**，所以缓存里的旧记录会把变更拖住 |
| 一次性重启整个集群 | 这次动作波及全部实例 | 业务会不可用，直到第一个实例恢复为止 |

### 2.1 影响面是数出来的，不是猜出来的

只读命令能在几分钟内把「这台机器在服务谁」数清楚。实验机（Ubuntu 24.04.5 LTS / 内核 `6.8.0-139-generic` / 4 vCPU）在 2026-09-19T08:05:57+00:00 采集了一份快照：

```bash
ip -brief addr                                    # 验证：有没有 VIP 或对外地址
ss -lnt                                           # 验证：对外监听哪些端口
ss -tn state established | head -20               # 验证：现在谁连着这台机器
systemctl list-units --type=service --state=running --no-pager | tail -1
                                                  # 验证：跑着多少个服务单元
lsof -i -P -n                                     # 验证：从进程视角再数一遍，与 ss 交叉核对
```

```text
# 数值仅示意、不代表你的机器
LISTEN 0  4096  127.0.0.54:53      0.0.0.0:*
LISTEN 0  4096     0.0.0.0:22      0.0.0.0:*
LISTEN 0  4096  127.0.0.53%lo:53   0.0.0.0:*
LISTEN 0  4096        [::]:22         [::]:*
24 loaded units listed.
ens33  UP  192.168.246.128/24
```

这 4 个监听里**只有 `0.0.0.0:22` 与 `[::]:22` 是真正的服务端口**（`sshd`），另外两个 `127.0.0.5x:53` 是 `systemd-resolved` 的本机解析器存根。4 条 `established` 全部是本机 22 端口上的 SSH 会话，对端都是 `192.168.246.1`，也就是实验控制端。因此**判据是「它在服务谁」，不是「它有没有在监听」**。一台真正的生产 Web 主机上，你会看到业务端口与成百上千条来自真实客户端的连接。

上面这些命令都是只读的，因此在生产机上也可以做。交叉核对能拿到三个只靠一次 `ss` 看不出的结论：

```text
# 数值仅示意、不代表你的机器
systemd     1        root  176u  IPv4  13938  0t0  TCP *:22 (LISTEN)
sshd     1348        root    3u  IPv4  13938  0t0  TCP *:22 (LISTEN)
systemd-r 691 systemd-resolve 21u IPv4 42593  0t0  UDP 192.168.246.128:41952->192.168.246.2:53
```

- **同一个 `*:22` 同时挂在 `systemd`（PID 1，socket 激活持有）与 `sshd`（PID 1348，真正处理连接）上**，因此若按进程数去数监听，就会重复计数；
- **`systemd-resolved` 除了本机存根，还有一条去网关 `192.168.246.2:53` 的上游连接**，因此「它依赖谁」也是影响面的一部分，它要记进资产与依赖台账里；
- **非 root 跑同一条 `lsof` 只能看到属于自己的进程**，这就是「生产机上做进程级取证需要 root」的原因，也是「没看到」不能当作「不存在」的原因。

### 2.2 数字必须带采集时刻

只读计数是**某一时刻的快照，不是机器属性**。同一台机器相隔 4 分钟再采一次（08:09 UTC），`ss -lnt` 变成 6 个、`established` 变成 9 条、running service 变成 25 个——多出来的 `127.0.0.1:20700`、`127.0.0.1:20701` 是同期另一个实验起的临时监听。

所以影响面评估与台账里写数字时，**必须带采集时刻与口径**（与 `date -Is` 的输出一起记录），否则两个人在不同时刻数出来的结果永远对不上。这也是为什么「我数过了」不能替代「我按什么口径、在什么时刻数的」。

### 2.3 从「一台机器」扩到「一次变更」

要把机器级的数字换算成变更级影响面，只差一句话：

```text
# 模板，数值仅示意
第一批影响 1/100 台，约占总容量 1%
```

这句话必须写在变更单上，因为**「先做一台试试」的前提是你知道这一台在整体里占多大比例**。100 台集群里改 1 台是 1%；3 台集群里改 1 台就是 33%。同样，「现在没人用，随时可以改」也是错的——因为「现在没人用」与「窗口内能做完」是两件事，而且半夜改坏了，能来救援的人也最少。

## 3. 预发环境为什么替代不了生产上的分批

预发（staging）验证过就上生产，是最常见的乐观来源。但预发与生产至少在三处一定不同：

- **数据规模不同**：预发的数据库通常是脱敏的小样本，因此索引、统计信息与查询计划都不同；
- **流量形态不同**：预发没有真实的长尾请求、没有突发的批量调用，也没有真正的并发冲突；
- **依赖真实度不同**：预发连的上游可能是 mock（模拟实现），或者指向一个不写入的副本。

所以预发的作用是**把低级错误挡掉**（语法错误、字段拼错、依赖缺失），而不是「证明变更安全」。生产的保证来自另外三件事：**分批**（第一批只影响一台）、**验收判据**（改动前后指标可比），以及**回滚**（在已知时间内能退回去）。这三件事在《体系：一次生产变更的一生》里按时间顺序展开。

## 4. 分级分的是流程，不是技术方案

有了可逆性与影响面这两把尺子，「分级」就不再是拍脑袋：分级决定审批层级、通知范围与执行时间窗，但它**不决定怎么做**。

| 分级 | 判据 | 审批 | 通知 | 时间要求 |
| --- | --- | --- | --- | --- |
| 标准变更 | 这次变更影响面小、可回滚、已演练过，并且有现成流程 | 执行人按 Runbook（操作手册）自决，并在事后记录 | 在变更群里知会相关方 | 安排在工作时间内执行，并避开高峰 |
| 重大变更 | 这次变更影响面大，或者包含不可逆动作（内核升级、主从切换、网络与 DNS 变更） | 这次变更需要评审与批准，批准人通常是主管加业务方 | 要提前通知相关方 | 要排定窗口，并避开高峰与冻结期 |
| 紧急变更 | 这次变更为了止损或修安全漏洞而不得不立刻做 | 先取得即时口头批准，事后再补单 | 要立即通知值班与相关方 | 要立即执行，并在事后复盘 |

判断属于哪一档，固定问四个问题：**影响多少用户 / 是否不可逆 / 能不能快速回滚 / 有没有演练过。** 改动量不在其中。

一个必须承认的边界：**分级是组织约定，没有一条命令能替你查出来。** `systemctl` 不知道你这次改动要谁批准，`git log` 也不知道现在是不是冻结期。这些信息只能从团队的制度与日历里取，因此动手前要问的不是「命令怎么写」，而是「现在是不是冻结期」「窗口到几点结束」「谁有权喊停」。

## 常见误解

| 说法 | 事实 |
| --- | --- |
| 「只改一行，风险不大」 | 分级看的是影响面而不是行数，因为一条鉴权配置、一条 DNS 记录或者一条防火墙规则的影响面可以覆盖全部调用方。 |
| 「我知道怎么回滚」 | 「知道」与「在实验机上跑过并记下耗时」是两件事，因为本机改 `vm.swappiness` 的实测回滚耗时是 4 ms，而这个数不跑就不知道。 |
| 「预发验证过了，生产直接全量」 | 预发的数据规模、流量形态与依赖真实度都不同，因此一旦全量，就没有回旋空间。 |
| 「这台机器不重要，随便改」 | 影响面要沿依赖往两头走，因为不重要的机器上可能挂着重要的定时任务、证书续期或采集 agent。 |
| 「现在没人用，可以改」 | 「现在没人用」与「窗口内做得完」是两件事，而救援人手在半夜最少。 |
| 「先做一台」就等于安全 | 只有知道这一台在整体里占多大比例，「先做一台」才是安全动作，因为 3 台集群里做 1 台是 33%。 |
| 「回滚就是把文件改回去」 | 改回文件不等于生效，因为不 reload 时进程仍持有旧配置，运行时值也不会自己变。 |
| 「紧急变更不用记录」 | 紧急变更事后必须补单与复盘，否则同类事故会重复发生。 |
| 「冻结期只针对发版」 | 冻结期通常覆盖所有非紧急变更，其中包括配置、网络、证书与扩容。 |

**第一反应不要做什么**：不要在没有写下回滚命令之前动手；不要用「改动量小」给自己降级；不要把「预发验证过」当成「生产安全」；不要用一台机器的数字代表整个集群；不要在没有采集时刻的计数上做影响面结论。

## 要点自测

**问：为什么「可逆性」比「难度」更适合做生产动作的第一分类标准？**
答：因为失败后的代价结构不同：难的操作往往有成熟流程，失败率低且可以重试；而简单的操作（一条 `rm`、一条路由删除）一旦失败就无法收回。分类的目的是决定「要不要先铺回退路径」，而回退路径只与可逆性有关。

**问：一个动作要算「可回滚」，必须同时满足哪三条？**
答：回退路径必须真的存在（原件与原数据还在）、回退路径必须已经验证过（回滚命令在实验机上跑通过）、回退耗时必须短于 RTO。这三条缺任何一条，都要按不可逆处理。

**问：影响面的四个维度是什么？为什么要沿依赖往两头看？**
答：四个维度是用户、服务、数据与时间。往上游看「谁依赖我」（我挂了谁报错），往下游看「我依赖谁」（我重试会不会打挂对端）。只看自己这一层是影响面估算最常见的错误。

**问：本机 4 个监听套接字里，哪几个是「业务端口」？判据是什么？**
答：只有 `0.0.0.0:22` 与 `[::]:22`（`sshd`）是业务端口，判据是「它在服务谁」。另外两个 `127.0.0.5x:53` 是 `systemd-resolved` 的本机存根，而那 4 条 `established` 全是来自实验控制端 `192.168.246.1` 的 SSH 会话。

**问：为什么同一台机器相隔 4 分钟采出来的三个数字会变？这对台账有什么要求？**
答：只读计数是某一时刻的快照，因此会随其他实验起停服务而变（本机实测从 4/4/24 变成 6/9/25）。所以台账与影响面评估在写数字时必须带采集时刻与口径，否则两个人数出来的结果对不上。

**问：为什么「预发验证过了」不能替换生产上的分批？**
答：预发与生产在数据规模、流量形态与依赖真实度这三处一定不同。预发挡的是低级错误，而生产的安全来自分批、验收判据与回滚这三件事。

**第一反应不要做什么**：不要用「改动量」判风险；不要把「我觉得能回滚」当成「可回滚」；不要在不知道这次动作占集群多少比例时就「先做一台」；不要把机器当成本而不是当服务。
