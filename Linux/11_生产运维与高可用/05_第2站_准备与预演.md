## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **备份的对象有三类：配置文件、数据、系统状态。只备份第一类是新手最常见的漏项。**
>   - 怎么验证：对变更逐条问「它会改到什么」——配置在 `/etc`、数据在数据盘、系统状态（服务启停、内核参数、挂载、包版本）在前两者之外。
> - **备份必须带时间戳，且不会被后续操作覆盖。**
>   - 证据：`cp -a nginx.conf nginx.conf.bak` 会被第二次操作覆盖成同样内容；必须写成 `nginx.conf.$(date +%F-%H%M%S)` 并 `ls -l` 确认新文件真的存在。
> - **回滚命令要在实验机上跑过——「知道怎么写」不算。**
>   - 怎么验证：回滚演练的验收是「旧状态回来了，且业务探活通过」，不是「命令没报错」。
> - **分批的依据是故障域，不是数量。**
>   - 证据：按 1 台 / 一个可用区 / 一个机房分批，能依次验证「单机配置对不对」「机架依赖有没有变」「跨机房链路有没有问题」；把机器随机劈成两半只能验证运气。
> - **基线必须在改动前采，恢复后立刻再采一次。**
>   - 怎么验证：`date -Is` + `systemctl show` + `ss -lnt` + 业务指标一次采齐；改动前这份就是第 4 站验收的比较对象。

## 1. 备份：三类对象

### 1.1 三类对象与各自的取舍

| 对象 | 典型内容 | 备份方式 | 注意 |
| --- | --- | --- | --- |
| **配置文件** | `/etc/**`、应用配置目录、单元文件 | `cp -a` 到带时间戳的目录，或纳入版本管理 | 单文件很小，**没有理由不备**；注意权限与属主（`-a` 保留） |
| **数据** | 数据库数据目录、对象存储、必要的日志 | 备份工具（rsync/restic/borg）、数据库自带导出 | 有**一致性**问题：运行中的数据库不能只靠复制文件（子笔记 10） |
| **系统状态** | 服务启停状态、内核参数、挂载关系、包版本、开机自启清单 | 采集命令输出为文本 | **状态无法用「复制回去」恢复**，只能靠「记录 + 手工重放」 |

### 1.2 本机可跑的备份段（配置文件 + 系统状态）

```bash
STAMP=$(date +%F-%H%M%S)
mkdir -p "/var/tmp/change-$STAMP"
cp -a /etc/nginx "/var/tmp/change-$STAMP/etc-nginx"
                                          # 验证：-a 保留权限与属主；目录整体复制
cp -a /etc/sysctl.d "/var/tmp/change-$STAMP/etc-sysctl.d"
                                          # 验证：内核参数的持久化落点
ls -l "/var/tmp/change-$STAMP"            # 验证：备份真的存在（不是复制失败但没报错）

{
  echo "=== 时间 ==="; date -Is
  echo "=== 服务状态 ==="; systemctl list-units --type=service --state=running --no-pager
  echo "=== 已启用的单元 ==="; systemctl list-unit-files --state=enabled --no-pager | head -40
  echo "=== 监听 ==="; ss -lnt
  echo "=== 挂载 ==="; findmnt -o TARGET,SOURCE,FSTYPE,OPTIONS
  echo "=== 关键内核参数 ==="; sysctl -n vm.swappiness net.ipv4.ip_local_port_range fs.file-max
} > "/var/tmp/change-$STAMP/state-before.txt"
                                          # 验证：系统状态快照，回滚后用来比对
```

> [!warning] 备份文件不要固定在同一个名字上，也不要放在被改动的路径里
> 两个具体反例：把备份放在同目录并用固定名（`nginx.conf.bak`），第二次操作会把它覆盖成同样内容；把备份放在即将被 `rm -rf` 或 `mkfs` 覆盖的目标里，等于没备份。**备份要满足两条：有唯一的名字、不在被改动的路径里。**

### 1.3 怎么证明备份可用

| 检查 | 命令 | 通过标准 |
| --- | --- | --- |
| 文件存在且为新 | `ls -l <backup>` | 时间戳是刚创建的；大小为 0 不算通过 |
| 内容可比对 | `diff -r <backup dir> <original dir>` | 此刻应当**没有差异**；有差异说明备份时源已被改过 |
| 能读回来 | 在实验机用备份覆盖一次并重启服务 | 服务正常起来（这是真正的验证） |
| 数据可恢复 | 从备份恢复一份数据到临时目录并校验 | 数据完整，且耗时被记录下来（子笔记 10） |

```bash
diff -r "/var/tmp/change-$STAMP/etc-nginx" /etc/nginx
                                          # 验证：备份与当前内容一致（此刻应当无输出）
cp -a "/var/tmp/change-$STAMP/etc-nginx/nginx.conf" /var/tmp/rollback-candidate.conf
                                          # 验证：把回滚用的候选文件准备好（先不动生产文件）
nginx -t                                  # 验证：语法检查（以 nginx 为例；换其他服务用它们各自的 -t/configtest）
```

## 2. 回滚方案：四种形态与两种假回滚

### 2.1 四种形态

| 形态 | 做法 | 耗时量级 | 例子 |
| --- | --- | --- | --- |
| **配置回滚** | 换回旧配置文件 + reload | 秒级 | 改 `nginx.conf`；改 `sysctl.d` 后 `sysctl --system` |
| **版本回滚** | 换回旧版本包/镜像 + 重启 | 分钟级 | 内核升级后回退到旧内核、回滚一次发布 |
| **服务回滚** | 停掉新做法、恢复旧做法 | 分钟级 | 关掉新参数、恢复旧调度器、摘掉新节点 |
| **数据回滚** | 从备份恢复到某个时间点 | **小时级，且可能丢数据** | 数据库恢复到故障前 |

选择原则：**能用配置回滚解决的，不要用数据回滚**。数据回滚是最后手段，因为它必然是「要么丢数据、要么花很长时间」。

### 2.2 两种假回滚

| 假回滚 | 为什么不算 |
| --- | --- |
| **重启服务** | 重启让状态「重来」，但配置和数据没回到过去；配置写错时，重启后依然错 |
| **换回文件但不 reload/重启** | 文件换回去了，运行中的进程还拿着旧配置；表现为「回滚了但现象没变」 |

```bash
systemctl reload <unit>                   # 验证：让运行中的进程重新读取配置
systemctl show <unit> -p ActiveState -p SubState -p MainPID -p ExecReload
                                          # 验证：reload 是否被支持、进程是否换了新的
```

### 2.3 回滚演练（必须在实验机上做）

> [!example]- 实验 2：一次带回滚的配置变更（实验机）
> **怎么做**：① 备份目标文件与状态快照（见 1.2）；② 改一个可验证、影响可控的参数（推荐 `vm.swappiness`，或某个自建服务的非关键参数）；③ 用运行时口径验收（`sysctl -n vm.swappiness`）；④ **演练回滚**：还原文件、重新加载、复验运行时值；⑤ 记录每一步耗时。
> **预期**：得到一份实测过的回滚命令，以及「从决定回滚到恢复原状」的耗时数字——这个数字要写进变更单。
> **风险**：低（单个参数）。**不要在生产机上做**；首次演练也不要选影响存储与网络的关键参数。
> **耗时**：约 20 分钟（含记录）。
> **怎么退回去**：本来就演练过回滚，最后保持在原始值即可；确认 `sysctl -n` 的输出与快照一致。

## 3. 灰度计划：怎么分批

### 3.1 分批的四个维度

| 维度 | 分批方式 | 能验证什么 | 局限 |
| --- | --- | --- | --- |
| **实例** | 1 台 → 10% → 50% → 100% | 配置与代码本身是否正确 | 若所有实例在同一机房，验证不到机房差异 |
| **故障域** | 一个机架 → 一个可用区 → 全部 | 机架/可用区级别的依赖差异 | 起步批次可能偏大 |
| **流量** | 1% 流量 → 10% → 全部 | 真实用户路径上的表现 | 需要流量切分能力（LB/网关） |
| **租户/客户** | 内部团队 → 小客户 → 全部 | 数据形态差异 | 客户体验不均衡 |

生产上最常见的是**混合分批**：先在 1 台实例上验配置（实例维度），再在一个可用区上验依赖（故障域维度），最后全量。理由很简单——**不同维度验证的是不同的假设**。

### 3.2 批次大小与观察时间

```text
批次大小 ≤ 总容量 − 最小可接受容量
观察时间 ≥ max(一个业务周期, 一个监控评估周期, 2~3 个采样间隔)
```

| 情况 | 批次建议 |
| --- | --- |
| 服务有 3 个副本，LB 承接 | 第一批 1 台（33%），确认后再推进 |
| 服务有 100 个副本 | 第一批 1~5 台（不超过 5%） |
| 有状态服务（数据库、消息队列） | 单台逐个做，每台都做完同步与健康检查再下一个 |
| 全局配置（DNS、网关、鉴权） | 没有「分批」的余地 → 按**不可逆**对待：先预演、再缩短 TTL、最后切换 |

> [!tip] 第一反应不要是「先全部改完，再一起看指标」
> 一起看指标的前提是「指标能归因」，而全量变更之后就没有对照组了。**灰度的本质是给自己留一个对照组**：改过的与没改的同时存在，才能判断变化是变更带来的，还是流量自己在变。

## 4. 改动前基线：验收的比较对象

```bash
STAMP=$(date +%F-%H%M%S)
date -Is                                   # 验证：基线采集的时刻（带时区）
uptime; free -m | head -2                  # 验证：负载与内存水位
df -h                                      # 验证：容量水位
systemctl is-active <unit>                 # 验证：服务状态
ss -lnt                                    # 验证：监听端口
journalctl -u <unit> -n 50 --no-pager > "/var/tmp/change-$STAMP/unit-before.log"
                                           # 验证：变更前日志，用来对比变更后的新增报错
```

业务侧基线同样要采：接口的 p99、错误率、QPS、关键业务动作的成功率。**只有一份基线才算有比较对象**——第 4 站的验收全部依赖它。

## 5. 生产动作：变更前的检查清单

```text
[ ] 变更单六要素齐全，分级与审批已完成
[ ] 改动对象清单已从台账生成（不靠记忆）
[ ] 配置文件已备份到带时间戳的目录，且不在被改路径内
[ ] 数据类变更的备份已完成并验证过（含一致性手段）
[ ] 系统状态快照已采集（服务、监听、挂载、参数、启停清单）
[ ] 回滚命令已写出，并已在实验机跑过一次（含耗时）
[ ] 回滚触发条件已写成可判定的句子
[ ] 验收判据（指标 + 业务 + 观察窗口）已写出
[ ] 改动前基线已采集（机器侧 + 业务侧）
[ ] 分批计划已定：批次、批次大小与观察时间
[ ] 窗口已确认：开始/结束时间、到点未完成的处置
[ ] 通知已发出，相关方已确认（含业务方与 on-call）
[ ] 有第二人能执行回滚（不依赖同一个人）
```

> [!important] 这张清单的用法：把它贴在变更单末尾
> 逐项打勾，而不是「心里过一遍」。它的价值不在勾本身，而在于**任何一项打不了勾时，你要当场决定是改期还是接受风险**——这个决定必须有记录。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 只备份配置文件，不管数据与系统状态 | 数据丢了没法回、状态丢了要靠记忆重建；三类对象缺一不可 |
| 备份用固定文件名（`xxx.bak`） | 第二次操作会覆盖第一次的备份，等于只有一份 |
| 把备份放在被改动的目录里 | `rm -rf`、`mkfs`、清空目录类操作会连带删掉备份 |
| 备份完只 `ls` 一眼 | 备份可能是空的、可能是复制到一半的；要 `ls -l` + `diff` + 实验机演练三件套 |
| 「回滚就是重启一下」 | 重启不改变配置与数据；写错的配置重启后依然错 |
| 回滚文件但不 reload | 运行中的进程仍持有旧配置，表现为「回滚了但没效果」 |
| 灰度批次按数量平均分 | 分批应基于故障域；同一机房内分 10 批也验证不到机房级差异 |
| 全量改完再一起看指标 | 没有对照组，无法归因；灰度就是给自己留对照组 |
| 改动前不采基线 | 第 4 站没有比较对象，只能靠「感觉正常」验收 |
| 回滚只有一个人会做 | 那个人不在时，窗口内的回滚能力就是 0 |

## 决策练习

> [!question]- 场景：你要把某个服务的日志级别从 `info` 改成 `debug`，用于排查一个偶发问题。服务有 8 个副本。同事说「直接 8 台一起改，有问题再改回来，反正就一行」。
> A. 同意——改日志级别无风险，而且 8 台一起改才能立刻拿到全量日志
> B. 改成 1 台 → 观察 10 分钟 → 其余 7 台；同时准备两件事：日志量暴增的容量预案（磁盘水位告警）、回滚命令（改回 `info` 并 reload）；验收判据里明确加上「磁盘写入速率不超过基线的若干倍」
> C. 不改，让开发在预发环境复现问题
>
> **答案：B。**
> A 漏掉了这个变更**真正的风险**：`debug` 级别会让日志量上升一个数量级，可能把磁盘写满或把日志管道拖垮——「配置本身合法但后果严重」正是生产上最常见的自伤方式。
> C 把问题推走了，但偶发问题往往只在生产流量下复现（子笔记 01 讲过预发与生产的差异）。
> B 是正解：**分批 + 容量预案 + 回滚 + 量化验收**。注意 B 的验收判据是专门为这个变更设计的（磁盘写入速率），因为这一项才是它可能弄坏的东西。

## 要点自测

> [!question]- 变更前的备份要覆盖哪三类对象？
> - 配置文件、数据、系统状态。
> - 系统状态无法「复制回去」，只能靠采集快照 + 手工重放；它记录的是服务启停、挂载、参数、包版本这些上下文。
> - **第一反应不要是什么**：不要只备份配置文件就认为「有退路」。

> [!question]- 哪些动作看起来能回滚、其实不能？
> - 「重启服务」不是回滚（配置与数据没回到过去）。
> - 「换回文件但不 reload/重启」也不是回滚（运行中的进程还拿着旧配置）。
> - 数据类变更与 DNS 类变更是真正的难回滚项，要按不可逆处理。
> - **第一反应不要是什么**：不要把「服务恢复正常」当成「回滚成功」。

> [!question]- 灰度分批的依据是什么？批次大小与观察时间怎么定？
> - 依据是故障域（实例 / 可用区 / 机房 / 流量比例 / 租户），不同维度验证不同假设。
> - 批次大小不超过「总容量 − 最小可接受容量」能留出的余量；观察时间 ≥ 一个业务周期与 2~3 个采样间隔。
> - **第一反应不要是什么**：不要为了「快」跳过观察时间，那等于没有分批。

> [!question]- 为什么基线必须在改动前采集？
> - 验收判据是「指标回到基线」，没有基线就没有比较对象。
> - 恢复之后要立刻再采一份，作为新的正常态基线。
> - **第一反应不要是什么**：不要用「改动前大概是多少」这种记忆中的数据当基线。
