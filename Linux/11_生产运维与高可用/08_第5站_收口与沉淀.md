## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **收口四件事：归档记录、更新台账与文档、闭环改进项、沉淀 Runbook。**
>   - 怎么验证：四件事对应四个可交付物；少任何一件，下一次同类变更就会重新踩一遍。
> - **复盘的目的是改系统，不是改人。**
>   - 证据：Google SRE 的无指责复盘中，行动项永远指向「流程、工具、告警、文档」，而不是「某人不够细心」——因为后者不会带来任何改进。
> - **改进项必须是「有 owner、有期限、有验证方式」的句子。**
>   - 怎么验证：把「加强监控」改写成「在 YYYY-MM-DD 前为 X 指标加上 <阈值> 告警，由 <姓名> 负责，验收方式是制造一次条件看告警是否触发」。
> - **Runbook 的验收标准是「别人照着能做」——包括在夜里三点。**
>   - 怎么验证：交给没参与过的同事照着执行一次；他在哪一步卡住，那一步就要改。
> - **知识留在个人手里，就是风险留在组织里。**
>   - 证据：只有一个人会做的恢复动作，在他休假、离职或同时处理别的事故时，恢复能力就是 0（子笔记 11、12 的演练设计就是为了解决这一点）。

## 1. 收口的四件事

| # | 事情 | 产出 | 最常见的借口 |
| --- | --- | --- | --- |
| 1 | 归档变更记录 | 变更单 + 执行记录 + 验收记录，放进同一个编号下 | 「都在聊天记录里了」 |
| 2 | 更新台账与文档 | 台账字段更新、架构图/依赖图更新、配置进入版本管理 | 「下次改的时候一起更新」 |
| 3 | 闭环改进项 | 复盘里的每条行动项有 owner 与期限 | 「先记下来，之后排期」 |
| 4 | 沉淀 Runbook | 至少一段可复用的处置或操作片段 | 「这个太简单了不用写」 |

四件事里最容易跳过的是第 2、3 件，因为它们不产生「当下的成就感」；代价在几个月后才出现——那时候已经没人记得细节了。

```bash
mkdir -p "/var/tmp/change-archive/<编号>"
cp -a /etc/<相关配置> "/var/tmp/change-archive/<编号>/config-after"
                                          # 验证：把变更后的配置一起归档（否则只有「改前」没「改后」）
journalctl --since "<变更开始时间>" --until "<变更结束时间>" --no-pager \
  > "/var/tmp/change-archive/<编号>/journal-window.log"
                                          # 验证：把变更窗口内的日志单独截出来存档
systemctl list-units --failed --no-pager  # 验证：收口时再确认一次没有遗留的失败单元
```

> [!important] 归档要包含「改后」的状态，不只是「改前」的备份
> 只留改前备份，半年后你只能看到「原来是什么」，看不到「当时改成了什么、为什么」。**改前 + 改后 + 变更窗口日志**，才是完整的一组。

## 2. 复盘：六段结构

### 2.1 六段

```text
1. 时间线（带时间戳，精确到分钟）
   什么时候提出、什么时候审批、每批什么时候做、什么时候发现异常、什么时候回滚/完成

2. 影响面
   谁受影响、影响了多久、最终数据是否完整

3. 证据
   指标截图/数值、日志片段、命令输出、告警记录

4. 根因
   直接原因（配置写错/依赖变化/容量不足）与根本原因（为什么它没被提前发现）

5. 止损动作
   做了什么让它停下来；为什么选这个动作；如果重来一次会不会选别的

6. 改进项（必须带 owner 与期限）
   每条都要写成可验收的句子；并回答一句：**为什么之前的防线没拦住它**
```

### 2.2 无指责复盘的三个操作要点

| 做法 | 效果 |
| --- | --- |
| **描述行为，不评价人**：写「第 3 批漏改了 7 台」，不写「执行人粗心」 | 让当事人愿意讲出真实细节 |
| **追问系统为什么允许错误发生**：漏改 7 台 → 为什么清单是靠手工维护的？ | 把改进项引向工具与流程 |
| **行动项必须有验收方式** | 避免「已加强监控」这类无法验证的结论 |

> [!warning] 「根因是人为失误」不是根因
> 人为失误是普遍存在的常量：人会疲劳、会看错、会漏掉一行。**能被系统吸收的失误才是好设计**：清单从台账自动生成、执行工具幂等、验收有独立的人。如果复盘的结论停在「以后小心一点」，那这次复盘等于没做。

### 2.3 变更复盘的触发条件

不是每次变更都要写完整复盘。建议按这三条触发：

1. **发生了回滚**（无论是否影响业务）。
2. **影响了业务**（哪怕只是短暂抖动）。
3. **出现了「解释不了但过去了」的现象**——这类最值得写，因为它随时可能再来一次。

## 3. 改进项闭环

### 3.1 从「形容词」到「句子」

| 差 | 好 |
| --- | --- |
| 「加强监控」 | 「在 2026-10-10 前，为 `TcpExtListenOverflows` 加告警（阈值 > 0 持续 1 分钟），owner 张，验收方式：用压测制造一次队列溢出，确认告警触发」 |
| 「完善文档」 | 「在 2026-09-30 前，把本次的回滚步骤补进《XX 服务变更 Runbook》第 3 节，owner 李，验收方式：另一位同事照着做一次」 |
| 「优化流程」 | 「把变更清单改为从 CMDB 导出，owner 王，验收方式：连续两次变更的清单均由脚本生成」 |

### 3.2 三种去向

| 去向 | 什么时候用 | 例子 |
| --- | --- | --- |
| **立即修** | 风险高、成本低 | 给关键参数加一条告警 |
| **排期** | 需要开发量或跨团队 | 把手工清单改成自动化导出 |
| **显式接受风险** | 修复成本高于收益 | 记录「已知限制：本方案在 X 场景下需要人工介入」，并写清触发条件 |

第三种最容易被忽略，但它很重要：**接受风险也是一个决定，必须写下来、有批准人**，否则它会以「大家都以为别人管」的形式长期存在。

## 4. Runbook 与 SOP

### 4.1 四个词的区别

| 名词 | 是什么 | 什么时候用 |
| --- | --- | --- |
| **记录** | 发生过什么（过去时） | 变更归档、事故记录 |
| **文档** | 系统是什么样（现在时） | 架构说明、依赖图、参数基线 |
| **Runbook** | 遇到某现象怎么做（判据 + 动作 + 验收） | 处置手册、例行操作 |
| **SOP** | 规定必须怎么做（流程 + 角色 + 时限） | 审批、发布、变更管理 |

### 4.2 Runbook 的最小结构

```text
标题：<现象> 的处置
适用范围：<哪些服务、哪些环境、哪些版本>
触发条件：<什么情况下用这份 Runbook>

第一步：取证
  命令：<逐条可复制>
  判据：<看到什么说明是哪一类问题>

第二步：处置
  动作：<逐条命令>
  预期：<正常应该看到什么>
  风险：<这一步可能带来什么副作用>

第三步：验收
  指标：<命令 + 阈值>
  业务：<探活方式>
  观察窗口：<时长>

回滚/升级：
  什么情况下停止并升级：<条件>
  升级给谁：<角色>

变更历史：
  <日期> <改了什么> <谁改的>
```

> [!example]- 实验 5：写一段 Runbook 并让同事照着执行（实验机）
> **怎么做**：选一个你刚在实验机上做过的动作（例如「证书过期后的更换流程」或「服务起不来时的三步定位」），按 4.2 的结构写成一段 Runbook；然后**找一个没参与的人照着执行**，只允许他问「这一步的输出是什么意思」，不允许你额外解释步骤。
> **预期**：会暴露出若干处「你以为写清楚了但别人看不懂」的地方（最常见的是缺少判据、缺少预期输出）。改完这些地方，Runbook 才算合格。
> **风险**：低（实验机）。
> **耗时**：约 40 分钟（含他人执行）。
> **怎么退回去**：实验机上的动作按 Runbook 自带的回滚段处理。

## 5. 度量：让改进看得见

| 指标 | 定义 | 用途 |
| --- | --- | --- |
| 变更成功率 | 未回滚的变更 / 全部变更 | 判断流程是否有效 |
| 回滚率 | 触发回滚的变更 / 全部变更 | 高说明准备阶段或验收标准有问题 |
| 变更引起的故障占比 | 由变更引起的事故 / 全部事故 | 决定把改进资源投在哪 |
| MTTR / MTTD | 平均修复时间 / 平均发现时间 | 判断是「修得慢」还是「发现得晚」 |
| 改进项按期完成率 | 按期闭环的行动项 / 全部行动项 | 防止复盘变成形式 |

度量的用法是**找瓶颈**，不是考核个人。三个数一起看才有意义：只降回滚率可能导致团队不敢做变更；只看 MTTR 会忽略 MTTD。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 「记录在聊天记录里就算归档」 | 聊天记录不可检索、不可交接；要按变更编号归档 |
| 只留改前备份，不留改后状态 | 半年后看不到「当时改成了什么、为什么」 |
| 复盘结论是「以后小心点」 | 人为失误是常量；改进项必须指向流程、工具、告警或文档 |
| 行动项写成形容词（「加强监控」） | 无法验收、无法跟踪；必须写成有 owner、期限、验证方式的句子 |
| 「先记下来，之后排期」 | 不排期等于不闭环；要不就排期，要不就显式记录「接受风险 + 批准人」 |
| Runbook 写成命令清单 | 没有触发条件与判据，别人照着做会在错误的前提下执行 |
| Runbook 写完不给人试 | 只有别人照着做过一次，才知道哪些步骤缺判据 |
| 只有一个人会做恢复动作 | 那个人不在时恢复能力为 0；要靠演练与 Runbook 把它变成组织能力 |
| 只度量回滚率 | 团队会趋向于「少做变更」，而少做变更并不是目标 |

## 决策练习

> [!question]- 场景：你完成了一次有惊无险的变更：过程中第 2 批出现了 3 分钟的错误率上升（0.8%），没有命中回滚触发条件（阈值 1%），随后自行恢复。变更最终成功。同事建议「既然成功了，就别写复盘了，省时间」。
> A. 同意——没回滚、没超阈值、业务没感知，不必复盘
> B. 写一份简短复盘：把「0.8% 是怎么来的、为什么又自己好了」查清楚，并把结论落成一条改进项；如果查不出原因，就把它作为「未解释现象」显式记录下来并列入观察项
> C. 写复盘，但重点放在「下次阈值要定得更保守」上
>
> **答案：B。**
> A 错在按「结果」判断要不要复盘。0.8% 与 1% 之间只差 0.2 个百分点，**这次是运气，不是安全边际**；解释不了的现象会再来一次，而下一次阈值可能刚好被越过。
> C 的方向偏了：调阈值只是把警报线挪动，并没有解释现象；而且把阈值调得更保守会带来更多误回滚。
> B 是正解：**复盘的对象是「未解释的现象」，不是「是否成功」**。查清楚就是收获，查不清也要显式记录下来——「已知未解释」本身就是有价值的信息。

## 要点自测

> [!question]- 收口的四件事是什么？
> - 归档变更记录（变更单 + 执行记录 + 验收记录）、更新台账与文档、闭环改进项、沉淀 Runbook。
> - 最容易跳过的是「更新台账」与「闭环改进项」，因为它们不产生当下的成就感，代价在几个月后才出现。
> - **第一反应不要是什么**：不要把「改完了」当成「收口完成」。

> [!question]- 复盘六段是什么？为什么「人为失误」不算根因？
> - 时间线、影响面、证据、根因、止损动作、改进项。
> - 因为人为失误是普遍常量；要追问「为什么系统允许这个失误造成这么大影响」，改进项才能指向工具与流程。
> - **第一反应不要是什么**：不要让复盘停在「以后小心一点」。

> [!question]- 好的改进项长什么样？
> - 有动作、有 owner、有期限、有验收方式。
> - 三种去向：立即修、排期、显式接受风险（含批准人）。
> - **第一反应不要是什么**：不要用「加强」「完善」「优化」这类形容词交差。

> [!question]- Runbook 与文档、记录、SOP 的区别是什么？
> - 记录写过去、文档写现状、Runbook 写「遇到某现象怎么做」、SOP 写「必须怎么做」。
> - Runbook 的验收标准是「别人照着能做」，包括在夜里三点、在压力下。
> - **第一反应不要是什么**：不要把 Runbook 写成一份纯命令清单（缺判据与验收）。

> [!question]- 为什么「只有一个人会做的恢复动作」是组织风险？
> - 那个人休假、离职或同时在处理别的事故时，恢复能力就是 0。
> - 解法是演练 + Runbook + 多人轮值，把它从个人能力变成组织能力。
> - **第一反应不要是什么**：不要把「我在就没事」当作可靠状态。
