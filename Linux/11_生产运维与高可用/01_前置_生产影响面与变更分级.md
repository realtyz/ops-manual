## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **「生产」的定义不是「机器贵」，而是「有真实用户、有真实数据、出错影响外部」。**
>   - 怎么验证：问三个问题——它上面有真实流量吗（`ss -tn state established | head`）、它的数据丢了能不能重造、它挂了谁会打电话给你。三个都是「是」，它就是生产。
> - **影响面 = 用户 × 服务 × 数据 × 时间，四个维度都要估。**
>   - 证据：实验机上只读命令能直接数出三件事——`ss -lnt` 有 **4** 个 LISTEN 套接字（`127.0.0.54:53`、`0.0.0.0:22`、`127.0.0.53%lo:53`、`[::]:22`）、`ss -tn state established` 为 **4** 条（全是本机 22 端口上的 SSH 会话，来自实验控制端 `192.168.246.1`）、`systemctl list-units --type=service --state=running` 报 **24** 个运行中的 service 单元。**影响面是数出来的，不是猜出来的**。
> - **可逆性是第一分类标准：只读 / 可回滚 / 不可逆，三档的处理方式完全不同。**
>   - 怎么验证：对每个动作问一句「如果 30 秒后我叫停，能回到原状吗」；`rm`、`mkfs`、`lvreduce`、一次性全量重启都答「不能」。
> - **变更分级决定审批层级、通知范围和执行时间，不决定技术难度。**
>   - 证据：同样一句「改一行配置」，改的是日志级别和改的是 DNS 记录，分级可以差两级；分级看的是**影响面**，不是改动量。
> - **冻结期与变更窗口是组织约定，不是建议。**
>   - 怎么验证：动手前先问「现在是不是冻结期」「窗口到几点结束」；回答不上来就不该开始。

## 1. 什么是「生产」

### 1.1 四类环境的边界

团队里同时存在的环境通常有四类，它们的差别不是硬件档次，而是**出错之后的后果**：

| 环境 | 有真实用户吗 | 数据能重造吗 | 出错的后果 | 允许的操作 |
| --- | --- | --- | --- | --- |
| 开发（dev） | 没有 | 能 | 自己返工 | 随便试，包括破坏性命令 |
| 测试/联调（test） | 没有 | 能 | 联调同学返工 | 可回滚变更、故障注入 |
| 预发/预生产（staging） | 没有（或只有影子流量） | 通常能 | 挡住一批问题 | 模拟生产的完整流程，含灰度与回滚 |
| 生产（prod） | **有** | **通常不能** | 用户受影响、可能赔钱、可能合规问题 | 只做审过的变更，全程有回滚与验收 |

> [!important] 「预发验证过了」替代不了生产上的分批
> 预发与生产至少在三处一定不同：**数据规模**（预发的数据库通常是脱敏的小样本）、**流量形态**（预发没有真实的长尾请求）、**依赖真实度**（预发连的上游可能是 mock）。所以预发的作用是「把低级错误挡掉」，不是「证明变更安全」。
>
> 生产上的安全保证来自另外三件事：**分批**（第一批只影响 1 台）、**验收判据**（改动前后指标可比）、**回滚**（30 秒内能退回去）。

### 1.2 怎么在 3 分钟内判断「这台是不是生产机」

拿到一台机器，先用只读命令回答三个问题：

```bash
ip -brief addr                                    # 验证：有没有 VIP / 公网地址（对外服务的强信号）
ss -lnt                                           # 验证：对外监听哪些端口
ss -tn state established | head -20               # 验证：现在有哪些连接连进来（谁在用它）
systemctl list-units --type=service --state=running --no-pager | head -30
                                                  # 验证：跑着哪些服务
hostnamectl                                       # 验证：主机名与命名规范（prod-xxx / test-xxx 通常一眼可辨）
```

实验机（root，2026-09-19T08:05 UTC 的一份快照）实测输出：

```text
$ date -Is
2026-09-19T08:05:57+00:00

$ ss -lnt
State  Recv-Q Send-Q Local Address:Port Peer Address:PortProcess
LISTEN 0      4096      127.0.0.54:53        0.0.0.0:*
LISTEN 0      4096         0.0.0.0:22        0.0.0.0:*
LISTEN 0      4096   127.0.0.53%lo:53        0.0.0.0:*
LISTEN 0      4096            [::]:22           [::]:*

$ ss -tn state established | tail -n +2 | wc -l
4

$ ss -tn state established
Recv-Q Send-Q   Local Address:Port  Peer Address:Port Process
0      0      192.168.246.128:22   192.168.246.1:59342
0      76     192.168.246.128:22   192.168.246.1:49753
0      0      192.168.246.128:22   192.168.246.1:51115
0      952    192.168.246.128:22   192.168.246.1:49754

$ systemctl list-units --type=service --state=running --no-pager | tail -1
24 loaded units listed.

$ ip -brief addr
lo               UNKNOWN        127.0.0.1/8 ::1/128
ens33            UP             192.168.246.128/24 fe80::20c:29ff:fe66:2c0f/64
```

这 4 个监听套接字里，**只有 `0.0.0.0:22` / `[::]:22` 是真正的服务端口**（`sshd`），另外两个 `127.0.0.5x:53` 是 `systemd-resolved` 的本机解析器存根——没有一个是业务端口。同理，4 条 `established` 全部是**本机 22 端口上的 SSH 会话，对端都是实验控制端 `192.168.246.1`**，也就是我自己的连接。这正是「实验室机器」的指纹：一台真正的生产 Web 主机上，你会看到 `:80`/`:443`/`:8443` 之类的业务监听，以及成百上千条来自真实客户端的 `established` 连接。**判据是「它在服务谁」，不是「它有没有在监听」。**

> [!warning] 只读计数是「有时刻的快照」，不是恒定值
> 同一台机器上并行做实验时，上面的数字会随别的实验起停服务而变。相隔 4 分钟再采一次（2026-09-19T08:09 UTC），同一台机器的数字变成 `ss -lnt` **6** 个、`established` **9** 条、running service **25** 个——多出来的 `127.0.0.1:20700`、`127.0.0.1:20701` 是同期另一个实验起的临时监听。所以台账与影响面评估里写数字时，**必须带采集时刻与口径**（`date -Is` 一起记录），否则两个人数出来的结果永远对不上。

「谁在服务、谁在连」还可以用 `lsof` 从**进程视角**再数一遍，用来和 `ss` 的结论交叉核对（同一时刻的实测）：

```text
$ lsof -i -P -n
COMMAND     PID            USER   FD   TYPE DEVICE SIZE/OFF NODE NAME
systemd       1            root  176u  IPv4  13938      0t0  TCP *:22 (LISTEN)
systemd       1            root  177u  IPv6  13165      0t0  TCP *:22 (LISTEN)
systemd-r   691 systemd-resolve   14u  IPv4  14922      0t0  UDP 127.0.0.53:53
systemd-r   691 systemd-resolve   15u  IPv4  14923      0t0  TCP 127.0.0.53:53 (LISTEN)
systemd-r   691 systemd-resolve   16u  IPv4  14924      0t0  UDP 127.0.0.54:53
systemd-r   691 systemd-resolve   17u  IPv4  14925      0t0  TCP 127.0.0.54:53 (LISTEN)
systemd-r   691 systemd-resolve   21u  IPv4  42593      0t0  UDP 192.168.246.128:41952->192.168.246.2:53
sshd       1348            root    3u  IPv4  13938      0t0  TCP *:22 (LISTEN)
sshd       1348            root    4u  IPv6  13165      0t0  TCP *:22 (LISTEN)
sshd       1777            root    4u  IPv4  17782      0t0  TCP 192.168.246.128:22->192.168.246.1:59342 (ESTABLISHED)
```

三个只有交叉核对才能得到的结论：**① `*:22` 这个监听同时挂在 `systemd`（PID 1，socket 激活持有）和 `sshd`（PID 1348，真正处理连接）上**——只按进程数监听会重复计数；**② `systemd-resolved` 除了本机存根，还有一条去往网关 `192.168.246.2:53` 的上游 UDP 连接**，说明「它依赖谁」也要记进台账；**③ 非 root 用户跑同一条命令只能看到属于自己的进程**，这就是「生产机上 lsof 要看得到别人的进程得有 root/sudo」的原因。

判断口径：

| 信号 | 偏向生产 | 偏向非生产 |
| --- | --- | --- |
| 地址 | 有公网 IP 或 VIP；`ss` 里有大量 `established` | 只有私网地址，连接数为 0 |
| 服务 | 有对外业务单元，且有监控/日志代理在跑 | 只有 `sshd`、解析器与系统默认单元（本实验机还跑着 `auditd`、`sysstat`、`apparmor`、`open-vm-tools`、`multipathd` 等 24 个 service 单元，**服务集齐全不等于在生产**） |
| 命名 | 主机名/标签里带 `prod`、`prd`、线上环境标识 | 带 `dev`、`test`、`lab` |
| 数据 | 数据目录有持续增长的真实数据 | 数据目录是空模板 |
| 变更入口 | 有发布系统纳管、有变更审批记录 | 谁都能直接登上去改 |

五条里对上三条以上，**默认按生产对待**——按生产错判的成本只是多走一遍流程，按非生产错判的成本可能是线上事故。

## 2. 影响面（爆炸半径）怎么估

### 2.1 四个维度

| 维度 | 要回答的问题 | 现场怎么取 |
| --- | --- | --- |
| **用户** | 影响多少用户/客户？是全部还是某个租户、某个地区 | 业务指标（在线数、QPS）、调用方的接入配置 |
| **服务** | 影响哪些服务？上下游是谁？ | 服务依赖图、`ss -tnp` 看谁连过来、调用方清单 |
| **数据** | 会不会写坏/删掉数据？可不可恢复？ | 数据目录、备份最近一次成功时间、是否主库 |
| **时间** | 影响持续多久？是数秒抖动还是数小时不可用 | 灰度批次的规模、回滚耗时、业务高峰时段 |

估影响面最常见的错误是**只看自己这一层**：「我只是重启一下 Nginx」。真实的影响面要沿着依赖往两头走：**谁依赖我**（我挂了谁报错）和**我依赖谁**（我重试会不会把对端打挂）。

### 2.2 从「一台机器」扩到「一次变更」

同一台机器上，不同类型动作的影响面差别很大：

| 动作 | 波及范围 | 典型影响面 |
| --- | --- | --- |
| 加一行监控采集配置 | 这台机器 | 无（只读 + 采集） |
| 换一个证书文件并 reload | 这台机器上的某个服务 | 该服务的一个 reload 抖动（毫秒级） |
| 重启一个无状态服务实例 | 这台实例 | 该实例的存量连接断开，由 LB 补位 |
| 重启数据库从库 | 这台实例 + 依赖它的读请求 | 读请求降级或失败，需要摘流量 |
| 改 DNS 记录 | 所有解析这个域名的客户端 | 视 TTL（记录缓存有效期）而定；**TTL 未过期前无法回滚** |
| 一次性重启整个集群 | 全部 | 业务不可用，直到第一个实例恢复 |

> [!tip] 第一反应不要是「先做一台试试」
> 「先做一台」是对的起点，但前提是你**知道这一台在整体里的占比**。100 台集群里改 1 台是 1%；3 台集群里改 1 台就是 33%。在动手之前把这句话写在变更单上：**「第一批影响 X/Y 台，约占总容量 Z%」**。

## 3. 可逆性：比分级更重要的分类

### 3.1 三档

| 档位 | 定义 | 例子 | 处理方式 |
| --- | --- | --- | --- |
| **只读** | 不改变系统状态 | `ss`、`df`、`journalctl`、`openssl s_client` | 生产机随时可做 |
| **可回滚** | 能在一个已知时间内退回原状 | 改配置后 reload、启停服务、挂载变更、加/减实例 | 先写回滚命令，再执行 |
| **不可逆** | 做完无法回到原状 | `rm -rf`、`mkfs`、`lvreduce`、`xfs_repair -L`、`drop table`、一次性全量重启、DNS 记录变更 | 必须有备份/快照，且要有第二人确认 |

### 3.2 「可回滚」的三个隐含条件

一个动作要真的算「可回滚」，需要同时满足：

1. **有退路**：原文件、原配置、原版本、原数据还在（不是被覆盖掉了）。
2. **退路可用**：回滚命令在实验机上跑通过，不是「理论上应该行」。
3. **退路够快**：回滚耗时小于业务能忍的时间（也就是 RTO，见子笔记 03）。

三个条件里任何一条不成立，这个变更就应当按「不可逆」处理——**先备份，再动手**。

## 4. 变更分级

### 4.1 三档与它们对应的流程

| 分级 | 判据 | 审批 | 通知 | 时间要求 |
| --- | --- | --- | --- | --- |
| **标准变更** | 影响面小、可回滚、已演练过、有标准流程 | 执行人自己按 Runbook 做，事后记录 | 变更群里知会 | 工作时间内、避开高峰 |
| **重大变更** | 影响面大或涉及不可逆动作（内核升级、数据库主从切换、网络与 DNS 变更） | 需要评审与批准（通常是主管 + 业务方） | 提前通知相关方，必要时公告 | 排定窗口，通常避开业务高峰与冻结期 |
| **紧急变更** | 为了止损或修复安全漏洞而不得不立刻做 | 口头/即时批准，事后补单 | 立即通知 on-call 与相关负责人 | 立即执行，事后复盘 |

> [!warning] 分级看的是影响面，不是改动量
> 「只改一行」可能是重大变更，「重装一台机器」可能是标准变更。判断依据固定为四个问题：**影响多少用户 / 是否不可逆 / 能不能快速回滚 / 有没有演练过**。

### 4.2 冻结期与变更日历

- **冻结期（freeze）**：大促、财报、节假日、重要发布会前后，除紧急变更外一律不做。原因很简单——**冻结期出问题，人和流程都不在最佳状态**。
- **变更日历**：把所有计划中的变更排在同一张表上，避免「同一天三波人各改一半」。冲突检测靠的是日历，不是记忆。
- **窗口**：每个变更都要有明确的开始与结束时间，以及「到点还没做完怎么办」的约定（通常是回滚）。

## 5. 角色：谁批准、谁执行、谁验证

| 角色 | 职责 | 常见误区 |
| --- | --- | --- |
| 变更发起人 | 写变更单（六要素）、评估影响面、准备回滚 | 「我以为审批人会帮我看影响面」 |
| 审批人 | 判断分级是否正确、窗口是否合理、回滚是否可行 | 「签个字而已」 |
| 执行人 | 按步骤执行、逐批核对、发现异常立即停手 | 「脚本跑起来就不管了」 |
| 验证人 | 独立确认验收判据（最好不是执行人本人） | 「执行的人说没问题就行了」 |
| on-call / 值班 | 故障时的第一响应人；有权叫停与升级 | 「先查清楚再通知别人」 |

> [!important] 最小可行的分工：执行与验证分开
> 团队再小，也建议保留一条：**执行的人不给自己签字验收**。自己执行自己验收时，「我已经改完了」的心理惯性会让人忽略「其实没生效」的证据。子笔记 07 的三件套验收就是为这条设计的。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 「预发验证过了，生产直接全量」 | 预发的数据规模、流量形态、依赖真实度都与生产不同；全量就没有回旋空间 |
| 「就改一行，不用提单」 | 分级看影响面不看看行数；「只改一行」常常是 DNS、路由、鉴权这类高影响配置 |
| 「先做了再说，不行再改回来」 | 没有写下来的回滚命令，就等于没有回滚；慌乱中改回来的往往是第二个变量 |
| 「回滚命令我知道怎么写」 | 「知道」与「跑通过」是两回事；回滚要在实验机上验过 |
| 「这台机器不重要的，随便改」 | 影响面要沿依赖往两头看；不重要的机器可能挂着重要的定时任务或证书 |
| 「现在没人用，随时可以改」 | 「现在没人用」与「窗口内能做完」是两件事；半夜改坏了，救援的人也少 |
| 「紧急变更就不用记录了」 | 紧急变更事后必须补单与复盘，否则同类事故会重复发生 |
| 「冻结期只针对发版」 | 冻结期通常覆盖所有非紧急变更，包括配置、网络、证书、扩容 |

## 决策练习

> [!question]- 场景：你负责的一个内部服务跑在 3 台机器上，前端有一层负载均衡。现在要改它的一行鉴权配置：`token_ttl` 从 3600 秒改成 7200 秒。同事说「就一行配置，直接三台一起改，改完 reload 就行，有问题再改回来」。
> A. 同意——一行配置 + reload，改回来也就 30 秒，属于标准变更
> B. 先把它当**重大变更**评估：鉴权配置是全局生效的，影响面是全体调用方；然后按「1 台 → 观察 → 其余 2 台」分批执行，每批用业务探活验收，回滚方式是把旧文件改回并 reload
> C. 先只改 1 台，观察一周，期间三台配置不一致也没关系
>
> **答案：B。**
> A 错在把「改动量小」当成了「影响小」：鉴权配置出错会导致**全部调用方 401**，这正是高影响面；而且「有问题再改回来」没有写在纸面上、没有跑过。
> C 错在长期保持配置不一致：三台配置不同时，故障会表现为「有时能过、有时 401」这种最难排查的形态。分批的每一批都要在**一个窗口内**走完，不是拖一周。
> B 是正解：先按影响面定级，再用**分批 + 每批验收 + 明确回滚**把风险降到可控。

## 要点自测

> [!question]- 生产、预发、测试三类环境的本质区别是什么？
> - 不是硬件档次，而是**出错后的后果**：有没有真实用户、数据能不能重造、会不会影响外部。
> - 因此允许的操作也不同：非生产可以随便试，生产只能做审过、可回滚、有验收的变更。
> - **第一反应不要是什么**：不要把「预发验证过」当成「生产安全」的证明；预发的数据规模、流量形态、依赖真实度都不同。

> [!question]- 影响面的四个维度是什么？为什么要沿依赖往两头看？
> - 用户、服务、数据、时间。
> - 往上游看「谁依赖我」（我挂了谁报错），往下游看「我依赖谁」（我重试会不会打挂对端）。
> - **第一反应不要是什么**：不要只看自己这一层，也不要用「我改的只是一台机器」代替影响面估算。

> [!question]- 一个动作要算「可回滚」，需要同时满足哪三个条件？
> - 有退路（原件/原版本还在）、退路可用（回滚命令在实验机跑过）、退路够快（回滚耗时小于 RTO）。
> - 缺任何一条，就按「不可逆」处理：先备份，再动手。
> - **第一反应不要是什么**：不要把「我知道怎么回滚」当成「可以回滚」。

> [!question]- 变更分级的判据是什么？「只改一行」为什么可能是重大变更？
> - 判据是四个问题：影响多少用户、是否不可逆、能不能快速回滚、有没有演练过。
> - 因为分级看的是影响面，不是改动量；一行鉴权、一行 DNS、一行防火墙规则的爆炸半径可以覆盖全部用户。
> - **第一反应不要是什么**：不要用「改动量」给自己降级。

> [!question]- 为什么执行与验收最好由不同的人完成？
> - 自己执行自己验收时，「我已经改完了」的惯性会让人把「已执行」当成「已生效」。
> - 独立验收人的动作很简单：只看判据（指标回到基线、业务探活通过、观察窗口内无复发）。
> - **第一反应不要是什么**：不要把「执行完了」当成验收结论。
