## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **批量出问题，八成出在「连接」和「环境」上，而不是命令本身。**
>   - 证据：非交互 `ssh` 不读 `.bashrc`，`PATH` 与交互式登录不同；100 台机器各建一条 TCP 连接会把跳板机与 `sshd` 的连接数推高一个量级。
> - **幂等的实现方式是「先判断，再动作」，而不是「执行命令」。**
>   - 怎么验证：同一个 playbook 或脚本连跑两次，第二次应当报告「变化为 0」（Ansible 的 `changed=0`）或直接跳过。
> - **`shell`/`command` 模块是逃生门，不是默认选项。**
>   - 证据：它们不判断当前状态，重复执行会重复动作；能用 `copy`/`template`/`lineinfile`/`service` 表达的就不要用 `shell`。
> - **脚本的四件套：严格模式、清理陷阱、超时、退出码。**
>   - 怎么验证：`set -euo pipefail` + `trap cleanup EXIT` + `timeout` + 显式 `exit`；四件缺任何一件，脚本在生产上都可能「静默地做了一半」。
> - **`serial` 与 `forks` 是安全阀：并发越高，出错时越难定位。**
>   - 怎么验证：把 `serial` 设为 1 或小批量，先在一台上跑通，再逐步放大；`--limit` 是试跑的第一道保险。

## 1. 批量 `ssh` 的坑

### 1.1 连接层

| 坑 | 现象 | 做法 |
| --- | --- | --- |
| 每台新建连接 | 100 台要 100 次握手；跳板机连接数飙高，`sshd` 触发 `MaxStartups` 限制 | 用连接复用（`ControlMaster`/`ControlPersist`）或改用 Ansible（默认就是复用/并行受控） |
| 没有超时 | 一台网络卡住，整批卡死 | `-o ConnectTimeout=5` + 外层 `timeout 30` |
| 交互式提问卡住 | 首次连接的 `known_hosts` 确认、私钥口令提示 | `-o BatchMode=yes`（明确禁止交互）、提前分发 `known_hosts` |
| 并发无上限 | 瞬时打满对端或本机资源 | `xargs -P` 给小数字，或 Ansible 的 `forks` |

```bash
ssh -o BatchMode=yes -o ConnectTimeout=5 -n host 'uptime'
                                          # 验证：非交互连接（不接受口令提示，超时 5 秒）
ss -tn state established '( dport = :22 or sport = :22 )' | wc -l
                                          # 验证：本机到 22 端口的连接数（判断有没有连接放大）
```

并发度不是「拍一个数字」，而是「先量一次」。下面是在实验机上真跑的一组对照（40 个 `sleep 0.05` 的子任务）：

```bash
time ( seq 1 40 | xargs -P 4 -I{} sh -c 'sleep 0.05' )
                                          # 验证：限并发版的墙钟时间（本机实测 0.54 秒）
seq 1 6 | xargs -P 3 -I{} sh -c 'echo "job {}"; [ {} -ne 3 ] || exit 7'; echo "xargs exit=$?"
                                          # 验证：任一子任务失败时 xargs 的退出码（本机实测 123）
```

```text
real	0m0.539s
user	0m0.065s
sys	0m0.044s
xargs exit=123
```

**退出码 123 是 `xargs` 自己的约定**（有子命令以 1~125 退出），它只告诉你「这批里有失败」，不告诉你是哪一台——这正是批量脚本必须自己记录每台输出的原因。

### 1.2 环境层：非交互 shell 与交互式 shell 不一样

这是批量运维里最经典的「本地能跑、远端报错」：

| 差异 | 交互式登录 | 非交互 `ssh host 'cmd'` |
| --- | --- | --- |
| 读取的启动文件 | `~/.bash_profile` / `~/.profile`（登录 shell） | 通常都不读（除 `/etc/bash.bashrc` 等发行版差异） |
| `PATH` | 可能包含 `~/bin`、`/usr/local/bin` | 通常是系统默认值，`/usr/local/bin` 可能不在 |
| 别名与函数 | 生效 | **不生效** |
| 变量导出 | 由启动文件设置 | 只有显式 `export` 的才存在 |

结论很简单：**批量化时要写绝对路径、显式 `export`、不要依赖别名与交互式初始化**。

```bash
ssh -n host 'echo $PATH'                  # 验证：非交互环境的 PATH（常见差异来源）
ssh -n host 'command -v docker || echo MISSING'
                                          # 验证：用 command -v 而不是 which/alias
ssh -n host 'bash -lc "echo $PATH"'       # 验证：需要登录环境时显式用登录 shell（注意引号层级）
```

> [!warning] `bash -lc` 不是万能药
> 用登录 shell 会重新引入「依赖具体账号的启动文件」这个变量：换一个执行账号、换一个发行版，行为就不一样。**批量化脚本的正解是「不依赖环境」**：绝对路径、显式变量、明确的解释器（`#!/usr/bin/env bash`）。

## 2. Ansible：把「期望状态」写下来

### 2.1 三个基本概念

| 概念 | 作用 | 类比 |
| --- | --- | --- |
| **inventory** | 「有哪些机器、怎么分组」 | 台账的执行视图 |
| **module** | 一个幂等的动作单元（`copy`、`service`、`lineinfile`、`file`…） | 一条「保证成什么样」的声明 |
| **playbook** | 一串任务（YAML），按顺序在目标机上执行 | 一份可执行的 Runbook |

先写机器清单 `hosts.ini`（INI 式配置文件）：

```ini
[web]
web-[01:20].example.internal

[web:vars]
ansible_user=ops
ansible_ssh_common_args='-o ConnectTimeout=5 -o BatchMode=yes'
```

再写 playbook `reload-web.yml`：

```yaml
- name: 重载 Web 服务并确认状态
  hosts: web
  serial: 2                  # 每批 2 台，串行推进
  become: true
  tasks:
    - name: 校验配置语法
      ansible.builtin.command: nginx -t
      changed_when: false    # 只验证，不算「变化」

    - name: 确保服务处于重载后的运行状态
      ansible.builtin.service:
        name: nginx
        state: reloaded

    - name: 确认监听端口
      ansible.builtin.command: ss -lnt
      register: listen
      changed_when: false

    - name: 断言 443 在听（不满足则本批失败）
      ansible.builtin.assert:
        that: "'127.0.0.1:443' in listen.stdout or ':443' in listen.stdout"
```

### 2.2 幂等是怎么实现的

`ansible.builtin.service` 这类模块会**先查当前状态**，再决定是否动作；`copy` 会比较文件校验和；`lineinfile` 会先匹配再决定是否写入。因此**同一个 playbook 跑两遍，第二遍的 `changed` 应当为 0**。

```bash
ansible-playbook -i hosts.ini reload-web.yml --limit web-01 --check --diff
                                          # 验证：先在 1 台上试跑（--check 不实际改动，--diff 显示差异）
ansible-playbook -i hosts.ini reload-web.yml
                                          # 验证：正式执行；观察输出里的 changed/failed 计数
```

两个实用开关：

| 开关 | 作用 | 生产用法 |
| --- | --- | --- |
| `--check` | 干跑，不改动 | 正式执行前必做 |
| `--diff` | 显示将发生的文件差异 | 与 `--check` 配合，确认改动范围 |
| `--limit` | 只对部分主机执行 | 首批验证 |
| `serial` | 分批执行 | 灰度；`serial: 1` 是最保守的滚动 |

> [!important] `shell`/`command` 模块是逃生门
> 它们**不判断状态**，只是把命令丢过去执行，所以天然不幂等。用它们的场合只有两种：**只读检查**（配 `changed_when: false`）与**确实没有对应模块的动作**（此时要自己写出幂等判断，并在任务名里说清楚）。

## 3. 脚本的四件套

### 3.1 严格模式

```bash
#!/usr/bin/env bash
set -euo pipefail
```

| 选项 | 含义 | 少了它会怎样 |
| --- | --- | --- |
| `-e` | 任一命令失败即退出 | 前一步失败后继续往下做，产生半成品 |
| `-u` | 引用**未设置**的变量即报错 | `rm -rf "$TARGET/"` 在 `TARGET` 从未赋值时不会变成删除 `/` 的事故 |
| `-o pipefail` | 管道中任一环失败即失败 | `cmd | tee log` 里 `cmd` 失败被 `tee` 的成功掩盖 |

```bash
bash -c 'set -u; rm -rf "$UNDEFINED/"'; echo "exit=$?"
                                          # 验证：未设置的变量会被拦住，非 0 退出（实验机实测 127，bash 5.2.21），不会执行 rm
bash -c 'set -u; T=""; echo "T 已设置、值为空：[$T]"'; echo "exit=$?"
                                          # 验证：-u 不拦「空值」，实验机实测输出 [] 且 exit=0
bash -c 'set -u; T=""; rm -rf "${T:?T 必须非空}/"'; echo "exit=$?"
                                          # 验证：${VAR:?} 才会拦住空值，非 0 退出（实验机实测 127）
bash -c 'set -o pipefail; false | true'; echo "exit=$?"
                                          # 验证：exit=1（管道中任一环失败即失败）
bash -c 'false | true'; echo "exit=$?"    # 验证：exit=0（默认行为，失败被吞掉）
```

> [!warning] `-u` 只管「未设置」，不管「空值」
> 实验机实测：`bash -c 'set -u; T=""; echo "[$T]"'` 会正常输出 `[]`，**不会报错**。所以 `rm -rf "$T/"` 这类写法在 `T` 被赋成空串时依然会删掉意外路径。要防空值，用 `${T:?变量必须非空}` 或显式判断（`[[ -n $T ]] || exit 2`）。这是「严格模式」最容易被误解的一条。

### 3.2 清理陷阱

```bash
#!/usr/bin/env bash
set -euo pipefail

TMPDIR_LAB="$(mktemp -d)"
cleanup() {
  rm -rf "$TMPDIR_LAB"
}
trap cleanup EXIT
                                          # 验证：脚本无论正常结束还是失败退出，都会清理临时目录
```

其它两种常见陷阱：**中断时释放锁**（`trap 'flock -u 9' EXIT`）、**中断时恢复上一个版本**（谨慎使用——自动回滚可能掩盖问题，通常应当只在明确标记的地方用）。

### 3.3 超时与退出码

```bash
timeout 30s rsync -a /data/ /backup/data/ # 验证：单步设上限，避免整批卡死
echo "rsync exit=$?"                      # 验证：124 表示被 timeout 杀掉（这是一个专门的失败信号）
timeout 5s sleep 30; echo "exit=$?"       # 验证：实验机实测 124（超时被杀）
timeout 5s true; echo "exit=$?"           # 验证：实验机实测 0（未超时）

if ! systemctl is-active --quiet nginx; then
  echo "nginx 未运行，中止" >&2
  exit 2
fi
                                          # 验证：显式退出码，便于批量工具判断失败类型
```

退出码约定（自定义脚本里建议固定下来）：`0` 成功、`1` 一般错误、`2` 用法/前置条件不满足、`124` 超时（`timeout` 的约定）。**批量执行时，退出码是判断「这台到底成没成」的唯一机器可读信号。**

### 3.4 锁：防止脚本被并发跑两次

```bash
exec 9>/var/lock/backup.lock
flock -n 9 || { echo "另一个实例在运行，退出" >&2; exit 3; }
                                          # 验证：-n 非阻塞获取锁；拿不到就立刻退出
```

实验机上验过一次「锁真的互斥」：先在一个 shell 里持有 fd 9，再让第二个 shell 抢同一把锁，`flock -n` 的退出码是 **1**（非阻塞、立刻失败），不是挂住等待——这正是定时任务要的行为。

定时任务最常见的自伤方式是「上一次还没跑完，这一次又起来了」。**带锁是定时任务脚本的默认要求**（子笔记 13、15 里的备份与清理任务同理）。

## 4. 一个完整的幂等脚本骨架

```bash
#!/usr/bin/env bash
set -euo pipefail

CONF=/etc/sysctl.d/99-app.conf
LINE='vm.swappiness = 10'

log() { printf '%s %s\n' "$(date -Is)" "$*"; }

if [[ $EUID -ne 0 ]]; then
  log "需要 root"; exit 2
fi

exec 9>/var/lock/set-swappiness.lock
flock -n 9 || { log "已有实例在运行"; exit 3; }

if grep -qxF "$LINE" "$CONF" 2>/dev/null; then
  log "已是目标状态，跳过写入（幂等）"
else
  cp -a "$CONF" "$CONF.$(date +%F-%H%M%S)" 2>/dev/null || true
  printf '%s\n' "$LINE" >> "$CONF"
  log "已写入 $CONF"
fi

sysctl --system >/dev/null
current=$(sysctl -n vm.swappiness)
if [[ "$current" != "10" ]]; then
  log "验收失败：sysctl -n vm.swappiness=$current"; exit 1
fi
log "验收通过：vm.swappiness=$current"
```

这个骨架把前面所有要点串了起来：**严格模式 → 前置检查 → 锁 → 幂等判断 → 带时间戳备份 → 动作 → 运行时口径验收 → 日志**。它可以连跑十次，结果都一样。

实验机上按这个骨架跑过一个最小版本（目标文件换成 `/tmp/11b-idem/99-app.conf`，写入固定的一行 `vm.swappiness = 60`）：第一次输出「已写入」，第二、三次都输出「已是目标状态，跳过写入（幂等）」，文件行数恒为 **1**；把中间一步换成不存在的命令后，脚本在那一行停下、退出码 **127**（`set -e` 生效），且 `flock` 锁随进程退出被释放——另一个 shell 立刻就能拿到锁。**这就是「可以连跑三次、结果一样」的实物证据。**

> [!example]- 实验 6：把手工动作改写成幂等脚本并连跑三次（实验机，已实测）
> **怎么做**：挑一个你手工做过的动作（改一个参数、确保某个目录存在、确保某个服务启用）；按第 4 节的骨架写成脚本；**连续执行三次**，观察第二、三次的输出是不是「跳过」；然后故意让中间一步失败（例如把 `sysctl` 换成不存在的命令），看脚本有没有在失败处停下并留下可诊断的信息。
> **预期**：第三次运行报告「跳过」；失败注入时脚本立即退出且退出码非 0；临时文件与锁都被正确释放（`ls /var/lock/`、复查临时目录）。**实验机实测**：幂等版本第二、三次输出「已是目标状态，跳过写入（幂等）」、文件行数恒为 1；失败注入时退出码 **127**；锁在进程退出后立即可再次获取。
> **风险**：低（实验机、单参数）。注意写进 `/etc/sysctl.d/` 的文件要能删掉。
> **耗时**：约 30 分钟。
> **怎么退回去**：删除新加的配置文件、`sysctl --system` 恢复；确认 `sysctl -n` 回到原值。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 用 `for h in $(cat hosts); do ssh $h '...'; done` 直接上生产 | 没有超时、没有失败处理、没有并发控制、没有日志；一台卡住整批停摆 |
| 依赖远端的 `PATH`、别名与 `.bashrc` | 非交互 `ssh` 不读这些；要用绝对路径与显式变量 |
| 首连 `known_hosts` 未处理 | 批量执行会被交互提示卡住；要用 `BatchMode=yes` 提前暴露问题 |
| 用 `shell` 模块跑一切 | 不幂等，重跑会重复动作；能用模块就用模块 |
| 不做 `--check` 直接上生产 | 干跑能提前发现语法错误与意外差异，成本极低 |
| `-e` 与 `pipefail` 都不加 | 失败被吞掉，脚本继续往下做，产生半成品 |
| `rm -rf "$VAR/"` 且没有 `-u` | 变量为空时会删掉不该删的路径 |
| 定时任务脚本不带锁 | 上一次没跑完，下一次又起来，两份任务互相踩 |
| 并发度开满 | 对端与跳板机被打满；出错时无法定位是哪一台 |
| 只记「跑了脚本」，不留输出 | 出问题无法复盘；输出必须落盘并按主机归档 |

## 决策练习

> [!question]- 场景：你要把 200 台机器的 `sshd_config` 加上一行 `ClientAliveInterval 60`（其余配置保持不变）。同事给了三种方案。
> A. `for h in $(cat hosts); do ssh -o StrictHostKeyChecking=no $h "echo 'ClientAliveInterval 60' >> /etc/ssh/sshd_config"; done`，跑完再统一 `systemctl reload sshd`
> B. 写一个 Ansible playbook：用 `lineinfile` 确保那一行存在（幂等）、`serial: 10` 分批、每批先 `sshd -t` 校验语法再 reload、失败超过阈值即停止；先用 `--limit` 在 1 台上 `--check --diff` 验证
> C. 写一个 shell 脚本，用 `xargs -P 50` 并发执行同上动作，出错的机器记录下来最后统一处理
>
> **答案：B。**
> A 有三个硬伤：`StrictHostKeyChecking=no` 关掉了主机校验（等于放弃一条安全边界）；`>>` 追加不幂等（跑两次就有两行，而重复的 `ClientAliveInterval` 会让 sshd 取第一个值，行为变得难以预测）；只做语法校验/ reload 前没有分批与失败处理。**再加一条更致命的：`sshd` 改坏之后，新的 SSH 连接会失败——如果没有控制台，这批机器就"失联"了。**
> C 比 A 好（有并发控制与错误记录），但仍然缺少两件关键东西：**幂等写入**与**分批推进**；`-P 50` 在 200 台规模下也不小。
> B 是正解：**幂等写入 + 分批 + 每批校验 + 失败即停 + 先 `--check`**。另外，凡是改 `sshd`/`iptables`/网络配置这类「改错就失联」的对象，都必须先确认控制台可用（子笔记 11）。

## 要点自测

> [!question]- 批量 `ssh` 最容易在哪些地方出问题？
> - 连接层：连接放大、无超时、交互提示（`known_hosts`、口令）、并发无上限。
> - 环境层：非交互 `ssh` 不读 `.bashrc`/`.bash_profile`，`PATH`、别名、变量都可能不同。
> - **第一反应不要是什么**：不要把「我手工登上去能跑」当成「批量也能跑」。

> [!question]- Ansible 的幂等是怎么实现的？`shell` 模块为什么会破坏它？
> - 模块先查当前状态再决定是否动作（`service` 查状态、`copy` 比校验和、`lineinfile` 先匹配）。
> - `shell`/`command` 只是执行命令，不判断状态，所以重复执行会重复动作；只读检查要配 `changed_when: false`。
> - **第一反应不要是什么**：不要把 `shell` 当默认选项。

> [!question]- 一个能上生产的脚本最少要有哪四件事？
> - 严格模式（`set -euo pipefail`）、清理陷阱（`trap ... EXIT`）、超时（`timeout`）、明确退出码。
> - 再加两件强烈建议：锁（`flock`）与日志（带时间戳，落盘）。
> - **第一反应不要是什么**：不要写没有失败处理的「一行 for 循环」。

> [!question]- `--check`、`--limit`、`serial`、`forks` 分别解决什么问题？
> - `--check`/`--diff`：干跑，看清将要发生的改动。
> - `--limit`：先只对少数主机执行，验证后再放开。
> - `serial`：分批推进，控制同时被改动的比例。
> - `forks`：并行度；越高越快，也越难定位失败。
> - **第一反应不要是什么**：不要在没干跑、没限量试跑的情况下全量执行。

> [!question]- 为什么「给定时任务脚本加锁」是默认要求？
> - 上一次未跑完、下一次又被触发时，两份任务会互相踩（同一目录、同一文件、同一目标）。
> - `flock -n` 拿不到锁就立刻退出，是最简单的保护。
> - **第一反应不要是什么**：不要假设「任务一定在上一次结束前跑完」。
