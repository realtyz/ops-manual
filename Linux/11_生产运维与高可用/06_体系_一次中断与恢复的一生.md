# 一次中断与恢复的一生

业务的失败不是从"服务停了"开始的，而是从**数据变得不可恢复**那一刻开始的。这一篇跟着一次中断走完六个阶段：先是备份被验证，然后中断被发现，接着完成分级与止损，此后数据被救回、系统被救活，最后故障域被补齐。这六个阶段依次是备份与恢复演练、发现与分级、止损、救数据、救系统与补故障域；其中前两个阶段在中断之前，中间三个阶段在中断之中，最后一个阶段在中断之后。

主线之外还有一件事一直挂着：**"这条恢复路径，上一次走通是什么时候？"** 若这个问题没有答案，那么所谓恢复能力就只是一份文档。

## 一、备份与恢复演练：把"可能是备份"变成"能恢复"

### 1.1 备份闭环的四个问题

备份闭环要回答四个问题，这四个问题分别由不同的输入决定，而任何一个答不出来，都会在恢复的时候留下一个具体的缺口：

| 问题 | 由谁定 | 答不出来的后果 |
| --- | --- | --- |
| 备什么 | 这个问题由业务与依赖分析来定 | 若答不出来，就会备份了不重要的数据，却漏掉了致命的数据；常见的情形是只备份数据而不备份配置 |
| 备到哪 | 这个问题由 RTO（Recovery Time Objective，恢复时间目标）与成本共同决定 | 若把备份与生产放在同一存储、同一机房，则一次故障就会让两者一起消失 |
| 多久一次 | 这个问题由 RPO（Recovery Point Objective，恢复点目标）决定 | 若备份频率不够，则恢复点丢失的数据会比业务能接受的多 |
| 怎么验证 | 这个问题由 RTO 与演练制度共同决定 | 这是最常被跳过的一项：备份任务全部显示成功，而恢复时数据对不上 |

四个问题的顺序不能颠倒，因为**先有 RTO 与 RPO 的数字，才有方案**（完整讨论见《原理：可恢复性的语言》）。

### 1.2 三种粒度与三种一致性路径

备份按粒度分三种，它们防的东西不同，代价也不同：

| 粒度 | 工具 | 防什么 | 代价 |
| --- | --- | --- | --- |
| 文件级 | `rsync`、`tar`、`restic`、`borg` | 它防的是误删与误改，并且可以只恢复一个文件 | 对运行中的数据库而言，复制过程中的文件可能不一致 |
| 块级 | LVM 快照、云盘快照、`dd` | 它防的是整盘损坏，因此可以快速整盘回滚 | 它的粒度粗，而且同一存储上的快照不防存储损坏 |
| 应用级 | `mysqldump --single-transaction`、`pg_dump`、`pg_basebackup` | 它保证一致性，因此可以做时间点恢复 | 它需要应用配合，而且恢复较慢 |

生产上的常见组合是三样一起用：**应用级保数据一致性，文件级保配置与单文件恢复，块级保快速回滚。**

一致性有三条实现路径：**逻辑导出**，也就是让数据库自己导出一份一致的快照；**物理全备加日志归档**，也就是恢复时重放日志到目标时刻；**先冻结再快照**，也就是先暂停写入、再做块级快照、最后恢复写入。三条之外必须记住一句：**块级快照的默认语义是崩溃一致性**，因为它相当于拔电源那一刻的磁盘状态，文件系统能恢复，但应用数据要经过崩溃恢复流程才能用。

本机在 loop 设备上做过一次 LVM 快照演练（环境：Ubuntu 24.04.5 LTS / 内核 `6.8.0-139-generic`，全程不碰根分区），这次演练同时给出了三个数字和一条硬边界：

```text
# 数值仅示意、不代表你的机器
lvcreate -s（200M 快照）：0.46 秒
覆盖 150 MiB 数据后：data_percent 从 0.01 涨到 75.31
写超快照容量时内核报：device-mapper: snapshots: Invalidating snapshot: Unable to allocate exception.
```

判读：**快照不是"免费的时间机器"**。它靠写时复制（copy-on-write）保存原块，因此一旦被改动的数据超过快照容量，快照就失效，表现为 `lvs` 的 `Attr` 列里出现 `I`——**它算容量，会满，也就会在关键时刻失效**。同时 `lvconvert --merge` 是破坏性的：合并之后，快照点之后的写入全部消失。所以快照适合"变更前 30 分钟内可能要用"的场景，不适合承担保留策略。

### 1.3 恢复演练：八步与频率

恢复演练的八步有固定顺序（产物模板见《治理：生产运维与变更治理》）：

1. 第一步是选一个**真实但可以丢**的对象，不要拿唯一一份数据来做；
2. 第二步是**从"决定恢复"开始计时**，而不是从"开始拷数据"开始计时；
3. 第三步是**只靠文档找备份**，因为记忆不算文档；
4. 第四步是把数据恢复到**隔离位置**，也就是不覆盖生产数据，以避免二次事故；
5. 第五步是校验，也就是核对条数、核对校验和，并让业务读一次；
6. 第六步是把计时做到**"业务可用"**为止，而不是"文件拷完"为止；
7. 第七步是记录实测 RTO、过程中的意外，以及文档里缺的那一步；
8. 第八步是清理现场，也就是清掉临时目录、临时挂载、临时实例与临时账号。

演练频率按对象的重要性定：关键数据每季度一次，配置每半年一次，覆盖全部系统的演练每年一次。

本机做过的一次最小演练（环境同上，自建的可丢目录）：快照耗时 0.046 秒，确认无进程持有待恢复文件（`lsof +L1` 里相关条数为 0），从快照恢复耗时 0.046 秒，`sha256sum -c` 三条全部 OK。**这是几 KiB 级对象的数字，不能外推**；它证明的是"演练的形态"——每一步都留下了可校验的证据，同时"有没有进程还持有这个文件"是恢复之前必须确认的一件事。

### 1.4 硬链接快照的成本证据

文件级备份有一种省空间的形态：`rsync --link-dest`，也就是让未改动的文件与上一份共享 inode。本机实测（数据集 101 MiB）：

```text
# 数值仅示意、不代表你的机器
base 快照：            101 MiB / 0.29 秒
第二份增量（inc-2）：   du -sh = 16 KiB / 0.048 秒
du -sh --total：       101 MiB
把两份分开 du -sm 相加：202 MiB（这是硬链接被重复计算后得到的假数字）
恢复（rsync -a --checksum）：0.42 秒，diff -r 一致
```

**把两份分开相加得到的 202 MiB 是假的**，因为硬链接被重复计算了。判据是：若要问"这些快照一共占多少"，就用同一棵树的 `du --total`；若要问"哪一份里改了什么"，就用 `--apparent-size` 与 `diff`。

## 二、中断的发现与分级：先止损，还是先弄清原因

### 2.1 发现：MTTD 决定总损失

业务感受的总损失近似于 `MTTD + MTTR`，也就是发现时间加修复时间（MTTR 即 Mean Time To Repair，平均修复时间；MTTD 即 Mean Time To Detect，平均发现时间）。由此有三条实践推论：

- **发现得晚，修得再快也没用**：因为从"用户投诉"才发现，等于把 MTTD 拉到了几十分钟量级；
- **检测依赖的可靠性等于不存在**：因为一条经常误报的告警会被值班忽略，于是它等于没有；
- **判断"有没有中断"要靠业务指标**，而不只是资源指标，因为本机那台实验机在探活全程返回 200 的情况下，`TcpExtListenOverflows` 从 0 涨到了 10，这说明"端口在听、接口能答"完全不能证明业务可用。

### 2.2 分级：决定叫醒谁、多久同步一次

| 严重等级 | 判据 | 响应方式 |
| --- | --- | --- |
| 一级 | 判据是核心业务不可用，或者数据面临丢失 | 响应方式是立刻叫醒关键人、成立处置小组，并且每 10~15 分钟同步一次 |
| 二级 | 判据是部分受影响，但存在降级路径 | 响应方式是由值班处理并在必要时升级；**30 分钟内必须明确升级条件** |
| 三级 | 判据是影响小，或者已经自动恢复 | 响应方式是记录在案，并进入次日处理队列 |

同时要固定四个角色，即使由同一批人兼任也要先写清：**指挥**负责决定做什么，**执行**负责动手，**取证**只读收集证据，**通报**负责对外同步。**"谁做决定"必须唯一**——事故现场最常见的延误不是不会修，而是所有人都在等别人拍板。

### 2.3 变更失败时的四个分支

| 分支 | 判据 | 动作 |
| --- | --- | --- |
| 命中触发条件 | 判据是变更单上写好的"指标 + 阈值 + 持续时间"成立 | 动作是**立即回滚**，不再讨论；回滚之前要记下当时的指标 |
| 未命中但现象无法解释 | 判据是服务还活着，但出现了说不清的变化 | 动作是暂停扩批、保留现场，并并行取证 |
| 未命中且属已知噪声 | 判据是有历史基线证明这是常态 | 动作是继续推进，并且**把依据写进执行记录** |
| 已回滚但现象仍在 | 判据是回滚动作做完了，现象却没有消失 | 动作是升级，并逐项确认配置、进程与连接三层是否真的回到旧状态 |

第四条最容易被跳过，因为**回滚也需要验收**。验收的判据四件缺一不可：运行时值回旧、服务 `active`、业务探活通过、观察窗口内指标回基线。

### 2.4 止损动作的优先级

止损动作的优先级固定，**从代价最小、最可逆的开始**：顺序是先限流，再摘流量，然后回滚，最后扩容，重启排在最后。

- **限流**影响面最小、最容易撤回，所以排在第一位；
- **重启排在最后**，因为它会毁掉现场（内存里的状态、连接、崩溃痕迹），而且经常只是把问题推迟；
- **一次只改一个变量**：因为同时做两个动作，事后无法归因，也无法决定该撤回哪一个。

止损与取证必须并行，也就是**止损由一条线做，取证由另一条线做。** 若带着"必须当场查清楚"的心态去处置，则往往会把故障拖长。通报只写已确认的事实，并把**事实 / 推测 / 待确认**三态分开写（七行模板见《体系：一次生产变更的一生》归档一节）。

### 2.5 部分成功：比全失败更危险

一批里部分成功会制造**间歇性失败**，因为同一批中新旧混杂，错误就表现为"有时好有时坏"，这是最难排查的形态。按当时能判断出的情况，分别走三条路径：

| 情况 | 动作 |
| --- | --- |
| 全是旧状态（本批一台都没改成） | 动作是修根因之后用同一份清单重跑，而这份脚本必须幂等 |
| 新旧混杂 | 动作是**先把已改的退回旧状态**，然后再整批重来 |
| 无法判断哪些改了 | 动作是停手，并逐台人工核对 |

关键是不能"接着往下推"：因为在混合状态下继续扩批，等于把不可解释的状态扩散到更多机器。

## 三、灾难恢复：系统已经不能正常运行时的最短路径

前面的恢复都假设"机器还能进、服务还能起"。这一阶段处理的是系统已经不能正常运行的情况：**起不来、根分区坏、关键文件误删、整机不可用。** 其中误删之后的抢救属于救数据阶段，而"修还是重来""从哪个入口进去"属于救系统阶段。

### 3.1 一条前置纪律：救援通道是基础设施

**带外管理（IPMI / iDRAC / iLO、虚拟化平台控制台、串口、云厂商的 VNC 控制台）与救援介质（Live ISO、救援模式、厂商恢复镜像）必须在故障之前各验证过一次。** 这条不是建议：本实验机只有 SSH 与虚拟化平台的控制台，**没有验证过 IPMI 类带外通道，也没有准备救援 ISO**，所以"写坏 `fstab`""把根分区挂成只读""内核 panic"这几类演练在本机不能自救，只能靠快照回滚——这本身就是"救援通道必须在故障前验证一次"的实例。

救援准备清单有八项，其中最后两项最常被漏：

1. 第一项是带外账号与权限，而且**凭据要存放在故障之外**，不要只存在被救的那台机器上；
2. 第二项是控制台在最近 90 天内验证过能用；
3. 第三项是救援介质的版本与校验和已经记录；
4. 第四项是虚拟化平台有挂载 ISO 与修改启动顺序的权限；
5. 第五项是分区布局、UUID 与引导器版本已经登记；
6. 第六项是 `/etc/fstab` 有一份离线副本；
7. 第七项是关键配置（网络、认证、证书）有离线副本；
8. 第八项是**加密盘与 TPM 的解锁材料可以取用**，因为缺了这一步，前面七项全部作废。

### 3.2 第一件要判断的事：修还是重来

**一问：我修错了，还能重来吗？** 若答案是"不能"，则先做镜像或快照再动手。

无状态或可自动化的机器，**重建通常比修复快且更可靠**；有状态的机器（数据库、唯一的数据目录、无法重建的配置），则**先保数据，再谈重建**。这条判断必须在动手之前完成，因为很多"修"的动作（`fsck -y`、`xfs_repair -L`、重建引导）本身是破坏性的。

### 3.3 四类灾难的最短路径

| 类型 | 最短路径 | 第一反应不要做 |
| --- | --- | --- |
| 系统起不来 | 第一步是拿控制台（**不是重启**）；第二步是看引导卡在哪一环（固件、引导器、initramfs、systemd）；第三步是走救援入口（上一个内核、救援目标、救援介质） | 不要"重启一次看看"，因为重启会刷掉唯一一份错误信息 |
| 根分区损坏 | 第一步是卸载该文件系统，或者把它挂成只读；第二步是从快照或备份恢复数据；第三步再决定修文件系统还是重建 | 不要在挂载状态下跑修复，也不要在没有备份时跑 `fsck -y` |
| 关键文件误删 | 第一步是**立即停写**（停服务、停定时任务，必要时把文件系统挂成只读）；第二步是用 `lsof +L1` 查找是否仍有进程持有该文件；第三步是从备份恢复；第四步是校验 | 不要重启，因为重启会释放句柄，从而丢掉"从 `/proc/<pid>/fd` 抢救"这最后一条路 |
| 整机不可用 | 第一步是换硬件或换机；第二步是用镜像或自动化重建；第三步是恢复数据；第四步是校验之后加入集群 | 不要把"重建完成"当成验收，因为验收是**业务可用**（数据恢复、配置重放、加入集群） |

### 3.4 误删的黄金几分钟

文件被删之后，**第一件事是停止对该文件系统的写入**，因为被删的块随时会被新数据覆盖。抢救分四步：

1. 第一步是**停写**：停掉会写这个目录的服务与定时任务，必要时把文件系统重挂为只读；
2. 第二步是**查持有者**：用 `lsof +L1` 列出"已删除但仍被打开"的文件。**关键判据是"有没有输出"以及"输出里是不是你要的那个文件"**——本机实测在一次容量实验里 `lsof +L1` 有 1 条记录，但那是 `systemd-journald` 持有的已轮转 journal，与要找的文件无关；而在误删演练里，相关条数为 **0**，这说明当时只能靠备份恢复；
3. 第三步是**抢救**：若有进程持有，则可以从 `/proc/<pid>/fd/<n>` 把内容拷出来（本机实测抢救出 41943040 字节，并且该文件可以校验通过）；
4. 第四步是**从备份恢复并校验**：核对条数、核对校验和，并让业务读一次。

**不要重启。** 因为重启会关掉所有进程，从而释放唯一可能还存在的句柄，并且会向文件系统写入更多数据。

### 3.5 字段读法：判断"起不来卡在哪一环"

| 字段 / 命令 | 是什么 | 判据 | 与谁同看 | 转向哪一步 |
| --- | --- | --- | --- | --- |
| `findmnt --verify` | 它校验 `fstab` 的可解析性与挂载点有效性 | 若有 parse error，那就是硬错误；而 warning 要逐条判断（本机实测 `0 parse errors / 0 errors / 1 warning`，那条 warning 指向一个用普通文件当 swap 的配置） | 与 `blkid`、`lsblk` 的 UUID 同看 | 若出现 parse error，则先改 `fstab`，不要重启 |
| `fstab` 里用什么标识设备 | 它记录设备是用 `/dev/sdX`、`by-id` 还是 `by-uuid` 来标识的 | **要用 `by-uuid` 或 `by-id`**，因为 `/dev/sdX` 的编号会随硬件顺序变化；本机实测根用 `by-id`、`/boot` 用 `by-uuid` | 与 `blkid` 输出的 UUID 同看 | 若用了 `sdX`，则要换掉，否则换盘或加盘之后系统起不来 |
| `/run/systemd/generator/` | 它是 systemd 为 `fstab` 生成的挂载单元所在目录 | 看 `-.mount`、`boot.mount`、`swap.img.swap` 是否都在，若缺了，则说明对应条目没有被正确解析 | 与 `findmnt --verify` 同看 | 若缺条目，则回到 `fstab` 去查 |
| `systemctl status rescue.target emergency.target` | 它给出两个救援目标的当前状态 | 平时是 `inactive (dead)`，这是正常的，它说明这两个入口存在但没有被使用 | 与引导参数同看 | 若真需要进入，则通过内核参数或引导菜单进 |
| 引导器里的 `root=` 与内核版本 | 它记录内核从哪里启动根、用哪个内核 | 判据是它与当前 `/etc/fstab`、`lsblk` 的期望一致 | 与 `/boot` 内容同看 | 若不一致，则不要重启，先修配置 |
| `journalctl --list-boots` | 它给出保留了几次开机的日志 | 若只有 `IDX 0`，则 `-b -1` 取不到上一次开机的日志，也就是说**事后就没有上一轮的现场** | 与 `journalctl --disk-usage` 同看 | 若历史太少，则容量与保留策略要调 |

本机实测的引导现状（环境同上）：`findmnt --verify` 报 `0 parse errors / 0 errors / 1 warning`；`/run/systemd/generator/` 下能看到 `-.mount`、`boot.mount`、`swap.img.swap`；`rescue.target` 与 `emergency.target` 都是 `inactive (dead)`；固件是 BIOS/legacy（没有 `/sys/firmware/efi`，也没有 `efibootmgr`），有真实的 `/boot`（`/dev/sda2`，2 GiB ext4）与 GRUB；initrd 大小 76531674 字节（约 73 MiB）；`grub.cfg` 里有 156 个 `menuentry` 与 170 处 `linux /vmlinuz-… root=/dev/mapper/ubuntu--vg-ubuntu--lv ro`；**`GRUB_TIMEOUT=0` 且菜单被隐藏**，因此要进引导菜单必须在开机时按 Shift 抢——这是一条平时看起来"更干净"、出事时却要多花几分钟的设置。

### 3.6 为什么灾难恢复必须"演练过"

三个只有演练才能暴露的问题：

- **`GRUB_TIMEOUT=0` 这类设置**只有在真进不去、需要选旧内核时才会疼；
- **`lsof +L1` 有输出不等于有你要的文件**，因为本机实测的 1 条记录是 journald 持的 journal；
- **`journalctl --list-boots` 只有一次开机**，这意味着"上一轮的日志"根本不存在，因此事后复盘拿不到现场。

## 四、高可用：把"一台坏掉"变成"业务还剩多少"

止损与灾难恢复解决的是"已经坏了怎么办"；高可用解决的是"坏了之后业务还剩多少"，也就是恢复主线最后一个阶段补故障域要做的事。完整机制与判据见《原理：故障域与检测的赌注》，这里只保留与恢复主线衔接的三件事。

### 4.1 接入层的恢复动作

- **VIP 漂移**：整机接管。恢复动作是"确认拿到 VIP 的那一台确实在服务"，判据是**从外部**探测。
- **负载均衡**：按后端实例恢复。恢复动作的顺序是先摘流量，再等存量连接结束，然后做变更，接着做单机验证，之后放回，最后观察；三个参数（最长等待、排空判据、放回后观察时长）写进 Runbook。
- **DNS 多值**：它受 TTL 与客户端缓存限制。恢复动作"改回解析"要等 TTL 过期才真正生效——这是它不能作为快速切换手段的原因。

### 4.2 单机流量没切过来的三层判据

| 现象 | 判据 | 说明 |
| --- | --- | --- |
| 摘流量没生效 | 判据是后端仍在列表里，而且流量仍在进来 | 这说明要去查健康检查配置、服务发现注册、客户端缓存与长连接 |
| VIP 不在任何一台 | 判据是两台都查不到该地址 | 这说明选举异常 |
| **VIP 同时在两台** | 判据是两台都能看到该地址，而且都在应答 | 这是**脑裂**：此时要先保数据一致性（fencing），不要再往上叠流量 |

### 4.3 余量与滚动重启

`最小可接受容量` 通常取峰值的一倍多（经验区间 1.2~1.5 倍）；**N+1** 容忍一个故障，**N+2** 容忍一个故障加一个维护。滚动重启的批次大小不能超过余量允许的台数：若 4 个实例、单机峰值为 70%，则下线 1 台之后剩下 3 台各约 133%——**这注定失败，与 `serial: 1` 无关。**

## 五、跨阶段的核对对象

前面按时间顺序讲的是六个阶段；下面五个核对对象各自贯穿其中多个阶段，因此排障时按它们切分比从头走一遍时间线更快。每一条都要点名它贯穿哪几个阶段、每一处读什么字段。

| 核对对象 | 它贯穿哪几个阶段 | 每一处读什么字段 |
| --- | --- | --- |
| 可恢复性与数据独立性 | 它贯穿备份与恢复演练、救数据与救系统三个阶段，因为备份与快照要在演练阶段被验证过，恢复时才用得上，而备份是否与生产分开存放，又决定了一次故障会不会把数据与恢复路径一起毁掉 | 备份、快照、副本与归档四者不能互相替代，因此唯一验收是"能恢复并且计时"；具体到每一处，在备份与恢复演练阶段读快照的 `data_percent` 与 `Attr`，并读演练记录里的实测 RTO 与 `sha256sum -c` 的输出；在救数据阶段读备份清单里的条数与校验和，并读 `lsof +L1` 的输出，确认还有没有进程持有待恢复的文件；在救系统阶段读 `by-id`、`by-uuid` 这类设备标识，以及救援介质清单里记下的版本与校验和 |
| 数据一致性 | 它贯穿备份与恢复演练、救数据与救系统三个阶段，因为备份时怎么取得一致的数据，决定了恢复出来能不能用，而恢复之后的一致性还要在抢救与重建两处被重新校验 | 运行中的数据库不能只靠复制文件，因此一致性有三条实现路径：逻辑导出、物理全备加日志归档、先冻结再快照；具体到每一处，在备份与恢复演练阶段读备份工具与它的一致性参数（`mysqldump --single-transaction`、`pg_dump`、`pg_basebackup`），并读快照的 `Attr` 判断这份备份是崩溃一致性还是应用级一致性；在救数据阶段读恢复后的条数与 `sha256sum -c` 的校验结果，并让业务读一次；在救系统阶段读整机重建之后的校验结果与业务探活是否通过 |
| 检测时延 | 它贯穿发现与分级、止损与补故障域三个阶段，因为发现得越晚总损失越大，而切换时间的下限由探活间隔与失败阈值决定 | 在发现与分级阶段读业务指标的探活返回码与 `TcpExtListenOverflows` 这类计数，并读告警的误报情况；在止损阶段读变更单上写好的触发条件，也就是"指标 + 阈值 + 持续时间"；在补故障域阶段读探活间隔与失败阈值、VIP 是否同时在两台应答，以及 DNS 记录的 TTL。完整讨论见《原理：故障域与检测的赌注》，指标与告警规则的口径在阶段 9 |
| 取证与证据介质 | 它贯穿止损、救数据与救系统三个阶段，因为止损与取证必须并行，而重启、杀进程与 `reset-failed` 都会毁掉现场 | 在止损阶段读通报里按事实、推测与待确认三态分开写的记录；在救数据阶段读 `lsof +L1` 的输出，以及 `/proc/<pid>/fd/<n>` 里还能不能拷出内容；在救系统阶段读 `journalctl --list-boots` 保留了几次开机、`/run/systemd/generator/` 下缺了哪个挂载单元，以及 `grub.cfg` 里的 `menuentry`。取证顺序固定为先看状态、再看日志、最后看请求，而且日志必须限定单元（本机实测同等窗口内，限定 `ssh` 是 0 条、不限定是 93 条） |
| 到期与容量 | 它贯穿备份与恢复演练、发现与分级、救系统与补故障域四个阶段，因为有到期日的东西与会满的东西，各自都会在这些阶段里先出问题 | 具体到每一处，在备份与恢复演练阶段读快照的 `data_percent` 与 `Attr`，并读备份保留期的台账；在发现与分级阶段读 `journalctl --disk-usage`；在救系统阶段读 `journalctl --list-boots` 里保留的开机次数；在补故障域阶段读容量余量（`最小可接受容量` 取峰值的一倍多，经验区间 1.2~1.5 倍）。在这些项目里，有到期日的那些包括证书、补丁、固件、支持合同与备份保留期，它们由《治理：生产运维与变更治理》统一登记；会满的那些包括日志、备份仓库与快照容量，它们按阶段 5 的容量治理处理 |

## 常见坑

| 做法或说法 | 后果或事实 |
| --- | --- |
| 把"备份任务成功"当验收 | 任务成功只证明写入完成，因此唯一验收是一次带计时的恢复演练 |
| 拿唯一一份数据做恢复演练 | 演练本身就变成了事故，因此必须把数据恢复到隔离位置 |
| 演练从"开始拷数据"计时 | 计时的起点必须是"决定恢复"，否则算出来的 RTO 是假的 |
| 把快照当长期备份 | 快照靠写时复制保存原块，因此容量满即失效（本机实测 `data_percent` 涨到 75.31 之后写满） |
| 用 `lvconvert --merge` 回滚生产数据 | 合并是破坏性的，因此快照点之后的写入会全部消失 |
| 恢复前不确认"还有谁持有这个文件" | `lsof +L1` 里可能根本没有你要的文件，因此有输出不等于有救 |
| 误删之后先重启 | 重启会释放句柄并覆盖数据块，因此等于放弃最后两条路 |
| 起不来先重启一次看看 | 重启会刷掉唯一一份错误信息，因此应先拿控制台与日志 |
| 在没有备份时跑 `fsck -y` / `xfs_repair -L` | 这两个动作不可逆，因此可能把可修复的问题变成不可修复 |
| `fstab` 里用 `/dev/sdX` | 设备编号会变，因此换盘或加盘之后系统起不来 |
| 只看 `ActiveState` 判断"服务好了" | `active` 也可能是自动重启循环，因此要看 `SubState` 与 `NRestarts` |
| 事故中先追根因 | 止损优先，因此根因与复盘要留到业务恢复之后 |
| 一次改两个变量来止损 | 事后无法归因，因此也无法决定该撤回哪一个 |
| 通报里把推测写成事实 | 这会让所有相关方按错误信息行动，因此事实、推测与待确认三态必须分开写 |
| 认为"重建完成"就是恢复完成 | 验收是业务可用，也就是数据恢复、配置重放与加入集群三件事 |
| 只登记"工具可用"，不登记"做不了的事" | 带外通道、救援介质与 SMART 数据都可能不可用，因此不登记就会在现场重复踩同一个坑 |

**第一反应不要做什么**：不要在事故中先查根因；不要在误删后先重启；不要在没有备份时跑破坏性修复；不要把快照或副本当备份；不要把"服务起来了"当恢复完成；不要用没演练过的恢复路径当真。

## 要点自测

**问：备份闭环的四个问题是什么？哪一个最常被跳过？**
答：四个问题是备什么、备到哪、多久一次与怎么验证。最常被跳过的是"怎么验证"，因为备份任务全部显示成功，而恢复时数据对不上。

**问：块级快照的两个边界是什么？**
答：第一个边界是它的默认语义为崩溃一致性，因此应用数据要经过崩溃恢复流程才能用；第二个边界是它靠写时复制保存原块，因此容量满即失效（本机实测 `data_percent` 涨到 75.31 之后写满，内核报 `Invalidating snapshot`）。另外 `lvconvert --merge` 是破坏性的。

**问：误删之后为什么不能重启？黄金几分钟该做什么？**
答：因为重启会释放可能还在持有的句柄，并向文件系统写入更多数据，从而覆盖被删的块。要做的是四步：先停写，再用 `lsof +L1` 找持有者，然后在必要时从 `/proc/<pid>/fd/<n>` 抢救，最后从备份恢复并校验。

**问：变更失败时，四个分支分别怎么处理？**
答：若命中触发条件，则立即回滚，而且回滚也要验收；若未命中但无法解释，则暂停扩批、保留现场并并行取证；若未命中且属已知噪声，则继续推进并把依据写进记录；若已回滚但现象仍在，则升级，并逐项确认配置、进程与连接三层。

**问：止损动作的优先级为什么把重启排在最后？**
答：顺序是先限流，再摘流量，然后回滚，最后扩容，重启排在最后。因为重启会毁掉现场（内存状态、连接、崩溃痕迹），而且经常只是把问题推迟；同时一次只改一个变量，否则无法归因。

**问：判断"系统起不来"时，为什么先拿控制台而不是重启？**
答：因为重启会刷掉唯一一份错误信息。正确顺序是先拿控制台看清卡在固件、引导器、initramfs 还是 systemd，再走救援入口（上一个内核、救援目标、救援介质）。

**问：`lsof +L1` 有输出，说明你要的文件有救吗？**
答：不一定。本机实测的那 1 条记录是 `systemd-journald` 持有的已轮转 journal，与要找的文件无关；而在误删演练里相关条数为 0。判据是"输出里有没有你要的那个文件"。

**第一反应不要做什么**：不要把备份成功当验收；不要在事故中先查根因；不要在误删后重启；不要在无备份时跑不可逆修复；不要把"重建完成"当业务恢复。
