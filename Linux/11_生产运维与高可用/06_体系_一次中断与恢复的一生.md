# 一次中断与恢复的一生

业务的失败不是从"服务停了"开始的，而是从**数据变得不可恢复**那一刻开始的。这一篇跟着一次中断走完：**备份被验证 → 中断被发现 → 分级与止损 → 数据被救回 → 系统被救活 → 故障域被补齐**。前两站在中断之前，中间三站在中断之中，最后一站在中断之后。

主线之外还有一件事一直挂着：**"这条恢复路径，上一次走通是什么时候？"** 没有答案的恢复能力只是一份文档。

## 一、备份与恢复演练：把"可能是备份"变成"能恢复"

### 1.1 备份闭环的四个问题

| 问题 | 由谁定 | 答不出来的后果 |
| --- | --- | --- |
| 备什么 | 业务与依赖分析 | 备份了不重要的，漏掉了致命的（常见：只备数据不备配置） |
| 备到哪 | RTO 与成本 | 与生产同存储、同机房，一次故障全没 |
| 多久一次 | RPO | 频率不够，恢复点丢得比业务能接受的多 |
| 怎么验证 | RTO 与演练制度 | 最常被跳过的一项：备份任务全绿，恢复时对不上 |

四个问题的顺序不能颠倒：**先有 RTO 与 RPO 的数字，才有方案**（见《原理：可恢复性的语言》）。

### 1.2 三种粒度与三种一致性路径

| 粒度 | 工具 | 防什么 | 代价 |
| --- | --- | --- | --- |
| 文件级 | `rsync`、`tar`、`restic`、`borg` | 误删、误改；可以只恢复一个文件 | 对运行中的数据库，复制过程中的文件可能不一致 |
| 块级 | LVM 快照、云盘快照、`dd` | 快速整盘回滚 | 粒度粗；同一存储上的快照不防存储损坏 |
| 应用级 | `mysqldump --single-transaction`、`pg_dump`、`pg_basebackup` | 一致性；可做时间点恢复 | 需要应用配合，恢复较慢 |

生产上的常见组合是三样一起用：**应用级保数据一致性，文件级保配置与单文件恢复，块级保快速回滚。**

一致性有三条实现路径：**逻辑导出**（让数据库自己导出一份一致的快照）、**物理全备加日志归档**（恢复时重放日志到目标时刻）、**先冻结再快照**（暂停写入、做块级快照、恢复写入）。三条之外必须记住一句：**块级快照的默认语义是崩溃一致性**——它相当于拔电源那一刻的磁盘状态，文件系统能恢复，应用数据要经过崩溃恢复流程才能用。

本机在 loop 设备上做过一次 LVM 快照演练（环境：Ubuntu 24.04.5 LTS / 内核 `6.8.0-139-generic`，全程不碰根分区），它同时给出了三个数字和一条硬边界：

```text
# 数值仅示意、不代表你的机器
lvcreate -s（200M 快照）：0.46 秒
覆盖 150 MiB 数据后：data_percent 0.01 → 75.31
写超快照容量时内核报：device-mapper: snapshots: Invalidating snapshot: Unable to allocate exception.
```

判读：**快照不是"免费的时间机器"**。它靠写时复制（copy-on-write）保存原块，一旦被改动的数据超过快照容量，快照就失效（`Attr` 里出现 `I`）——**它算容量，会满，也就会在关键时刻失效**。而且 `lvconvert --merge` 是破坏性的：合并之后，快照点之后的写入全部消失。所以快照适合"变更前 30 分钟内可能要用"，不适合承担保留策略。

### 1.3 恢复演练：八步与频率

八步固定顺序（产物模板见《治理：生产运维与变更治理》）：

1. 选一个**真实但可以丢**的对象（不要拿唯一一份数据做）；
2. **从"决定恢复"开始计时**，不是从"开始拷数据"开始；
3. **只靠文档找备份**——记忆不算文档；
4. 恢复到**隔离位置**（不覆盖生产数据，避免二次事故）；
5. 校验：条数、校验和、让业务读一次；
6. 计时到**"业务可用"**为止，不是"文件拷完"为止；
7. 记录实测 RTO、过程中的意外、文档里缺的那一步；
8. 清理现场（临时目录、临时挂载、临时实例、临时账号）。

演练频率按对象重要性定：关键数据季度一次，配置半年一次，全站级每年一次。

本机做过的一次最小演练（环境同上，自建的可丢目录）：快照 0.046 秒、确认无进程持有待恢复文件（`lsof +L1` 里相关条数为 0）、从快照恢复 0.046 秒、`sha256sum -c` 三条全部 OK。**这是几 KiB 级对象的数字，不能外推**；它证明的是"演练的形态"——每一步都留下了可校验的证据，而且"有没有进程还持有这个文件"是恢复前必须确认的一件事。

### 1.4 硬链接快照的成本证据

文件级备份有一种省空间的形态：`rsync --link-dest`——未改动的文件与上一份共享 inode。本机实测（数据集 101 MiB）：

```text
# 数值仅示意、不代表你的机器
base 快照：            101 MiB / 0.29 秒
第二份增量（inc-2）：   du -sh = 16 KiB / 0.048 秒
du -sh --total：       101 MiB
把两份分开 du -sm 相加：202 MiB      ← 假数字
恢复（rsync -a --checksum）：0.42 秒，diff -r 一致
```

**"分开相加"得到的 202 MiB 是假的**，因为硬链接被重复计算。判据：要问"这些快照一共占多少"，用同一棵树的 `du --total`；要问"哪一份里改了什么"，用 `--apparent-size` 与 `diff`。

## 二、中断的发现与分级：先止损，还是先弄清原因

### 2.1 发现：MTTD 决定总损失

业务感受的总损失近似于 `MTTD + MTTR`（发现时间加修复时间）。三条实践推论：

- **发现得晚，修得再快也没用**：从"用户投诉"才发现，等于把 MTTD 拉到了几十分钟量级；
- **检测依赖的可靠性等于不存在**：一条经常误报的告警会被值班忽略，于是它等于没有；
- **判断"有没有中断"要靠业务指标**，不只是资源指标——本机那台实验机在探活全程 200 的情况下，`TcpExtListenOverflows` 从 0 涨到了 10，说明"端口在听、接口能答"完全不能证明业务可用。

### 2.2 分级：决定叫醒谁、多久同步一次

| 严重等级 | 判据 | 响应方式 |
| --- | --- | --- |
| 一级 | 核心业务不可用，或数据面临丢失 | 立刻叫醒关键人，成立处置小组，每 10~15 分钟同步一次 |
| 二级 | 部分受影响，有降级路径 | 值班处理后升级；**30 分钟内必须明确升级条件** |
| 三级 | 影响小或已自动恢复 | 记录，进入次日处理队列 |

同时固定四个角色，即使由同一批人兼任也要先写清：**指挥**（决定做什么）、**执行**（动手）、**取证**（只读收集证据）、**通报**（对外同步）。**"谁做决定"必须唯一**——事故现场最常见的延误不是不会修，而是所有人都在等别人拍板。

### 2.3 变更失败时的四个分支

| 分支 | 判据 | 动作 |
| --- | --- | --- |
| 命中触发条件 | 变更单上写好的"指标 + 阈值 + 持续时间"成立 | **立即回滚**，不再讨论；回滚前记下当时的指标 |
| 未命中但现象无法解释 | 服务还活着，但出现了说不清的变化 | 暂停扩批、保留现场、并行取证 |
| 未命中且属已知噪声 | 有历史基线证明这是常态 | 继续推进，**把依据写进执行记录** |
| 已回滚但现象仍在 | 回滚动作做完了，现象没消失 | 升级：逐项确认配置、进程、连接三层是否真的回到旧状态 |

第四条最容易被跳过：**回滚也需要验收。** 判据四件缺一不可——运行时值回旧、服务 `active`、业务探活通过、观察窗口内指标回基线。

### 2.4 止损动作的优先级

固定顺序，**从代价最小、最可逆的开始**：

```text
限流 → 摘流量 → 回滚 → 扩容 → 重启
```

- **限流**影响面最小、最容易撤回，所以排在第一位；
- **重启排在最后**，因为它会毁掉现场（内存里的状态、连接、崩溃痕迹），而且经常只是把问题推迟；
- **一次只改一个变量**：同时做两个动作，事后无法归因，也无法决定该撤回哪一个。

止损与取证必须并行：**止损由一条线做，取证由另一条线做。** 带着"必须当场查清楚"的心态处置，往往会把故障拖长。通报只写已确认的事实，并把**事实 / 推测 / 待确认**三态分开写（七行模板见《体系：一次生产变更的一生》收口一节）。

### 2.5 部分成功：比全失败更危险

一批里部分成功会制造**间歇性失败**——同一批中新旧混杂，错误表现为"有时好有时坏"，是最难排查的形态。三条路径：

| 情况 | 动作 |
| --- | --- |
| 全是旧状态（本批一台都没改成） | 修根因后用同一份清单重跑（脚本必须幂等） |
| 新旧混杂 | **先把已改的退回旧状态**，再整批重来 |
| 无法判断哪些改了 | 停手，逐台人工核对 |

关键是不要"接着往下推"：混合状态下继续扩批，等于把不可解释的状态扩散到更多机器。

## 三、灾难恢复：系统已经不能正常运行时的最短路径

前面的恢复都假设"机器还能进、服务还能起"。这一站处理的是系统已经不能正常运行的情况：**起不来、根分区坏、关键文件误删、整机不可用。**

### 3.1 一条前置纪律：救援通道是基础设施

**带外管理（IPMI / iDRAC / iLO、虚拟化平台控制台、串口、云厂商的 VNC 控制台）与救援介质（Live ISO、救援模式、厂商恢复镜像）必须在故障之前各验证过一次。** 这条不是建议：本实验机只有 SSH 与虚拟化平台的控制台，**没有验证过 IPMI 类带外通道，也没有准备救援 ISO**，所以"写坏 `fstab`""把根分区挂成只读""内核 panic"这几类演练在本机不能自救，只能靠快照回滚——这本身就是"救援通道必须在故障前验证一次"的实例。

救援准备清单八项，最后两项最常被漏：

1. 带外账号与权限，且**凭据存放在故障之外**（不要只存在被救的那台机器上）；
2. 控制台在最近 90 天内验证过能用；
3. 救援介质的版本与校验和已记录；
4. 虚拟化平台有挂载 ISO / 修改启动顺序的权限；
5. 分区布局、UUID 与引导器版本已登记；
6. `/etc/fstab` 有一份离线副本；
7. 关键配置（网络、认证、证书）有离线副本；
8. **加密盘 / TPM 的解锁材料可取用**（没这一步，前面七项全部作废）。

### 3.2 第一件要判断的事：修还是重来

**一问：我修错了，还能重来吗？** 答"不能"的，先做镜像或快照再动手。

无状态或可自动化的机器，**重建通常比修复快且更可靠**；有状态的机器（数据库、唯一的数据目录、无法重建的配置），**先保数据，再谈重建**。这条判断必须在动手之前完成，因为很多"修"的动作（`fsck -y`、`xfs_repair -L`、重建引导）本身是破坏性的。

### 3.3 四类灾难的最短路径

| 类型 | 最短路径 | 第一反应不要做 |
| --- | --- | --- |
| 系统起不来 | 拿控制台（**不是重启**）→ 看引导卡在哪一环（固件 / 引导器 / initramfs / systemd）→ 走救援入口（上一个内核、救援目标、救援介质） | 不要"重启一次看看"——重启会刷掉唯一一份错误信息 |
| 根分区损坏 | 卸载或挂成只读 → 从快照或备份恢复数据 → 再决定修文件系统还是重建 | 不要在挂载状态下跑修复；不要在没有备份时跑 `fsck -y` |
| 关键文件误删 | **立即停写**（停服务、停定时任务、必要时挂只读）→ `lsof +L1` 找是否仍有进程持有 → 从备份恢复 → 校验 | 不要重启：重启会释放句柄，丢掉"从 `/proc/<pid>/fd` 抢救"这最后一条路 |
| 整机不可用 | 换硬件或换机 → 用镜像或自动化重建 → 恢复数据 → 校验后加入集群 | 不要把"重建完成"当验收；验收是**业务可用**（数据恢复 + 配置重放 + 加入集群） |

### 3.4 误删的黄金几分钟

文件被删之后，**第一件事是停止对该文件系统的写入**，因为被删的块随时会被新数据覆盖。四步：

1. **停写**：停掉会写这个目录的服务与定时任务；必要时把文件系统重挂为只读；
2. **查持有者**：`lsof +L1` 列出"已删除但仍被打开"的文件。**关键判据是"有没有输出"与"是不是你要的那个文件"**——本机实测在一次容量实验里 `lsof +L1` 有 1 条记录，但那是 `systemd-journald` 持有的已轮转 journal，与要找的文件无关；而在误删演练里，相关条数为 **0**，说明只能靠备份；
3. **抢救**：若有进程持有，可以从 `/proc/<pid>/fd/<n>` 把内容拷出来（本机实测抢救出 41943040 字节并可校验）；
4. **从备份恢复并校验**：条数、校验和、业务读一次。

**不要重启。** 重启会关掉所有进程（释放唯一可能还存在的句柄），并且会向文件系统写入更多数据。

### 3.5 字段读法：判断"起不来卡在哪一环"

| 字段 / 命令 | 是什么 | 判据 | 与谁同看 | 转向哪一步 |
| --- | --- | --- | --- | --- |
| `findmnt --verify` | 校验 `fstab` 的可解析性与挂载点有效性 | 有 parse error 就是硬错误；warning 要逐条判（本机实测 `0 parse errors / 0 errors / 1 warning`，那条 warning 指向一个用普通文件当 swap 的配置） | `blkid`、`lsblk` 的 UUID | 有 parse error → 先改 `fstab`，别重启 |
| `fstab` 里用什么标识设备 | `/dev/sdX`、`by-id`、`by-uuid` | **用 `by-uuid` 或 `by-id`**：`/dev/sdX` 的编号会随硬件顺序变化；本机实测根用 `by-id`、`/boot` 用 `by-uuid` | `blkid` 输出的 UUID | 用了 `sdX` → 换掉，否则换盘/加盘后起不来 |
| `/run/systemd/generator/` | systemd 为 `fstab` 生成的挂载单元 | 看 `-.mount`、`boot.mount`、`swap.img.swap` 是否都在（缺了说明对应条目没被正确解析） | `findmnt --verify` | 缺条目 → 回到 `fstab` |
| `systemctl status rescue.target emergency.target` | 两个救援目标的当前状态 | 平时是 `inactive (dead)`，这是正常的；它说明"这两个入口存在但没被使用" | 引导参数 | 真需要时通过内核参数或引导菜单进 |
| 引导器里的 `root=` 与内核版本 | 内核从哪里启动根、用哪个内核 | 与当前 `/etc/fstab`、`lsblk` 的期望一致 | `/boot` 内容 | 不一致 → 不要重启，先修配置 |
| `journalctl --list-boots` | 保留了几次开机的日志 | 只有 `IDX 0` 时，`-b -1` 取不到上一次开机的日志——**事后就没有上一轮的现场** | `journalctl --disk-usage` | 历史太少 → 容量与保留策略要调 |

本机实测的引导现状（环境同上）：`findmnt --verify` 报 0 parse errors / 0 errors / 1 warning；`/run/systemd/generator/` 下能看到 `-.mount`、`boot.mount`、`swap.img.swap`；`rescue.target` 与 `emergency.target` 都是 `inactive (dead)`；固件是 BIOS/legacy（没有 `/sys/firmware/efi`，也没有 `efibootmgr`），有真实的 `/boot`（`/dev/sda2`，2 GiB ext4）与 GRUB；initrd 大小 76531674 字节（约 73 MiB）；`grub.cfg` 里 156 个 `menuentry`、170 处 `linux /vmlinuz-… root=/dev/mapper/ubuntu--vg-ubuntu--lv ro`；**`GRUB_TIMEOUT=0` 且菜单被隐藏**，要进引导菜单必须在开机时按 Shift 抢——这是一条平时看起来"更干净"、出事时多花几分钟的设置。

### 3.6 为什么灾难恢复必须"演练过"

三个只有演练才能暴露的问题：

- **`GRUB_TIMEOUT=0` 这类设置**只有在真进不去、需要选旧内核时才会疼；
- **`lsof +L1` 有输出不等于有你要的文件**（本机实测的 1 条记录是 journald 持的 journal）；
- **`journalctl --list-boots` 只有一次开机**，意味着"上一轮的日志"根本不存在——事后复盘拿不到现场。

## 四、高可用：把"一台坏掉"变成"业务还剩多少"

止损与灾难恢复解决的是"已经坏了怎么办"；高可用解决的是"坏了之后业务还剩多少"。完整机制与判据见《原理：故障域与检测的赌注》，这里只保留与恢复主线衔接的三件事。

### 4.1 接入层的恢复动作

- **VIP 漂移**：整机接管。恢复动作是"确认拿到 VIP 的那一台确实在服务"，判据是**从外部**探测。
- **负载均衡**：按后端实例恢复。摘流量 → 等存量连接结束 → 变更 → 单机验证 → 放回 → 观察，三个参数（最长等待、排空判据、放回后观察时长）写进 Runbook。
- **DNS 多值**：受 TTL 与客户端缓存限制。恢复动作"改回解析"要等 TTL 过期才真正生效——这是它不能作为快速切换手段的原因。

### 4.2 单机流量没切过来的三层判据

| 现象 | 判据 | 说明 |
| --- | --- | --- |
| 摘流量没生效 | 后端仍在列表里，且流量仍在进来 | 查健康检查配置、服务发现注册、客户端缓存与长连接 |
| VIP 不在任何一台 | 两台都查不到该地址 | 选举异常 |
| **VIP 同时在两台** | 两台都能看到该地址且都在应答 | **脑裂**：先保数据一致性（fencing），不要再往上叠流量 |

### 4.3 余量与滚动重启

`最小可接受容量` 通常取峰值的一倍多（经验区间 1.2~1.5 倍）；**N+1** 容忍一个故障，**N+2** 容忍一个故障加一个维护。滚动重启的批次大小不能超过余量允许的台数：4 个实例、单机峰值 70% 时下线 1 台，剩下 3 台各约 133%——**注定失败，与 `serial: 1` 无关。**

## 五、横切线

### 5.1 可恢复性线

备份、快照、副本、归档四者不能互相替代；唯一验收是"能恢复且计时"。完整讨论见《原理：可恢复性的语言》。

### 5.2 数据一致性线

运行中的数据库不能只靠复制文件；三条一致性路径（逻辑导出、物理全备加日志、先冻结再快照）。块级快照默认是崩溃一致性。

### 5.3 检测线

`MTTD` 与切换时间下限由探活间隔与失败阈值决定。完整讨论见《原理：故障域与检测的赌注》；指标与告警规则的口径在阶段 9。

### 5.4 取证线

止损与取证并行；重启、杀进程、`reset-failed` 都会毁掉现场。取证顺序是"状态 → 日志 → 请求"，且日志必须限定单元（本机实测同等窗口内，限定 `ssh` 是 0 条、不限定是 93 条）。

### 5.5 到期与容量线

"有到期日的东西"（证书、补丁、固件、支持合同、备份保留期）和"会满的东西"（日志、备份仓库、快照容量）各自需要台账与告警，前者见《治理：生产运维与变更治理》，后者见阶段 5 的容量治理。

## 常见坑

| 做法或说法 | 后果或事实 |
| --- | --- |
| 把"备份任务成功"当验收 | 成功只证明写入完成；唯一验收是带计时的恢复演练 |
| 拿唯一一份数据做恢复演练 | 演练本身成为事故；要恢复到隔离位置 |
| 演练从"开始拷数据"计时 | 起点必须是"决定恢复"；否则 RTO 是假的 |
| 把快照当长期备份 | 快照靠写时复制保存原块，容量满即失效（本机实测 `data_percent` 涨到 75.31 后写满） |
| 用 `lvconvert --merge` 回滚生产数据 | 合并是破坏性的：快照点之后的写入全部消失 |
| 恢复前不确认"还有谁持有这个文件" | `lsof +L1` 里可能根本没有你要的文件；有输出不等于有救 |
| 误删之后先重启 | 重启释放句柄与覆盖数据块，等于放弃最后两条路 |
| 起不来先重启一次看看 | 重启会刷掉唯一一份错误信息；应先拿控制台与日志 |
| 在没有备份时跑 `fsck -y` / `xfs_repair -L` | 这两个动作不可逆，可能把可修复的问题变成不可修复 |
| `fstab` 里用 `/dev/sdX` | 设备编号会变；换盘或加盘后起不来 |
| 只看 `ActiveState` 判断"服务好了" | `active` 也可能是自动重启循环；要看 `SubState` 与 `NRestarts` |
| 事故中先追根因 | 止损优先；根因与复盘留到业务恢复之后 |
| 一次改两个变量来止损 | 事后无法归因，也无法决定撤回哪一个 |
| 通报里把推测写成事实 | 会让所有相关方按错误信息行动；三态必须分开写 |
| 认为"重建完成"就是恢复完成 | 验收是业务可用：数据恢复 + 配置重放 + 加入集群 |
| 只登记"工具可用"，不登记"做不了的事" | 带外通道、救援介质、SMART 数据都可能不可用；不登记就会在现场重复踩 |

**第一反应不要做什么**：不要在事故中先查根因；不要在误删后先重启；不要在没有备份时跑破坏性修复；不要把快照或副本当备份；不要把"服务起来了"当恢复完成；不要用没演练过的恢复路径当真。

## 要点自测

**问：备份闭环的四个问题是什么？哪一个最常被跳过？**
答：备什么、备到哪、多久一次、怎么验证。"怎么验证"最常被跳过——备份任务全绿，恢复时对不上。

**问：块级快照的两个边界是什么？**
答：默认是崩溃一致性（应用数据要经崩溃恢复流程才能用），以及它靠写时复制保存原块、容量满即失效（本机实测 `data_percent` 涨到 75.31 后写满，内核报 `Invalidating snapshot`）。另外 `lvconvert --merge` 是破坏性的。

**问：误删之后为什么不能重启？黄金几分钟该做什么？**
答：重启会释放可能还在持有的句柄，并向文件系统写入更多数据、覆盖被删的块。四步是：停写、`lsof +L1` 找持有者、必要时从 `/proc/<pid>/fd/<n>` 抢救、从备份恢复并校验。

**问：变更失败时，四个分支分别怎么处理？**
答：命中触发条件 → 立即回滚（回滚也要验收）；未命中但无法解释 → 暂停扩批、保留现场、并行取证；未命中且属已知噪声 → 继续并把依据写进记录；已回滚但现象仍在 → 升级，逐项确认配置、进程、连接三层。

**问：止损动作的优先级为什么把重启排在最后？**
答：顺序是限流 → 摘流量 → 回滚 → 扩容 → 重启。重启会毁掉现场（内存状态、连接、崩溃痕迹），而且经常只是把问题推迟；一次只改一个变量，否则无法归因。

**问：判断"系统起不来"时，为什么先拿控制台而不是重启？**
答：重启会刷掉唯一一份错误信息。正确顺序是拿控制台看清卡在固件、引导器、initramfs 还是 systemd，再走救援入口（上一个内核、救援目标、救援介质）。

**问：`lsof +L1` 有输出，说明你要的文件有救吗？**
答：不一定。本机实测的 1 条记录是 `systemd-journald` 持有的已轮转 journal，与要找的文件无关；在误删演练里相关条数为 0。判据是"输出里有没有你要的那个文件"。

**第一反应不要做什么**：不要把备份成功当验收；不要在事故中先查根因；不要在误删后重启；不要在无备份时跑不可逆修复；不要把"重建完成"当业务恢复。
