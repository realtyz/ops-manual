## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **台账不是「给领导看的表」，是变更前的影响面来源。**
>   - 怎么验证：任何一次变更单里的「范围」段，都应该能从台账里直接查出来；查不出来，说明台账缺字段。
> - **资产信息分三组采：硬件、固件、系统。**
>   - 证据：实验机上三组都采得到——`lscpu` 给出 `CPU(s): 4` / `Intel(R) Core(TM) i7-14650HX` / `Hypervisor vendor: VMware`，`lsblk` 给出 `sda 80G → sda3 48G LVM2_member → ubuntu--vg-ubuntu--lv 48G ext4 /`，`systemd-detect-virt` 给出 `vmware`；固件组用 `dmidecode -t system -t bios -t baseboard` 拿到 `Manufacturer: VMware, Inc.` / `Vendor: Phoenix Technologies LTD` / `Version: 6.00` / `Release Date: 02/17/2026`。**唯一拿不到的是 SMART 健康数据**（虚拟盘不透传）。
> - **依赖关系两头都要画：谁依赖我，我依赖谁。**
>   - 怎么验证：`ss -lnt` 找出监听端口，`ss -tnp` 看谁在连它，`systemctl list-dependencies` 看单元依赖——三条命令就能画出这台机器的一阶依赖图。
> - **配置漂移是「只有人类记忆在维护配置」的必然结果。**
>   - 怎么验证：隔一个月再采一遍同一组信息，和台账比对；对不上的字段就是漂移。
> - **台账的更新点只有一个：变更收口时。**
>   - 证据：把台账更新写进变更单的「收口」一栏（子笔记 08），就不会出现「改了但没记」。

## 1. 为什么要台账

新人常觉得台账是形式主义，因为「机器就那几台，我记在脑子里」。这种想法在三种情况下一击即碎：

| 场景 | 没有台账时会发生什么 |
| --- | --- |
| 你要给 100 台机器改一个参数 | 你得挨个登上去看是不是同一个发行版、同一个版本 |
| 一台机器挂了，别人问你影响什么 | 你只能等业务报错才知道谁在依赖它 |
| 三个月后你要打安全补丁 | 你得重新采一遍 BIOS/固件版本，因为没人记得上次升到哪了 |
| 你要做一次恢复演练 | 你找不到「这台机器的数据应该在哪个备份集里」 |

台账的最小形态可以只是一张 Markdown 表或一个 CSV，**关键是它有维护点、有责任人、有更新时机**。

## 2. 资产信息从哪采

### 2.1 三组信息

| 组 | 采什么 | 命令 | 备注 |
| --- | --- | --- | --- |
| **硬件** | CPU 型号与核数、内存容量、磁盘型号与大小、网卡型号与速率 | `lscpu`、`free -h`、`lsblk -o NAME,SIZE,ROTA,MODEL`、`lspci \| grep -i ethernet` | 本机实测 `lspci` **能看到**模拟网卡（`8086:100f 82545EM Gigabit Ethernet Controller`）；真正看不到的是 RAID 卡、BBU 这类设备（虚拟机没有）。`ROTA=1` 表示机械盘（rotational），但**虚拟机会把这个字段伪造错**，见 2.4 |
| **固件** | 主板厂商与型号、BIOS/UEFI 版本与日期、RAID 卡固件、网卡固件 | `dmidecode -t system`、`dmidecode -t bios`、`dmidecode -t baseboard`、厂商工具（`storcli`/`perccli`）、`ethtool -i <iface>` | **需要 root**；本机 root 可用、DMI 齐全，三条 `dmidecode` 都能跑。容器里通常拿不到（`/sys/class/dmi/id/` 被隐藏或为空） |
| **系统** | 发行版、内核、systemd、cgroup、虚拟化类型、主机名与机器标识 | `cat /etc/os-release`、`uname -r`、`systemctl --version \| head -1`、`stat -fc %T /sys/fs/cgroup`、`systemd-detect-virt`、`hostnamectl`、`cat /etc/machine-id` | 全部只读，生产机可随时执行 |

### 2.2 实验机实测的采集脚本（只读，生产机可以跑）

```bash
#!/usr/bin/env bash
set -u
{
  echo "=== 身份 ==="; hostnamectl 2>/dev/null | head -8; systemd-detect-virt
  echo "=== 系统 ==="; grep -E '^(PRETTY_NAME|VERSION_ID)' /etc/os-release; uname -r
  echo "=== CPU ==="; lscpu | grep -E '^(Architecture|CPU\(s\)|Model name|Thread|Core)'
  echo "=== 内存 ==="; grep -E '^(MemTotal|SwapTotal)' /proc/meminfo
  echo "=== 磁盘 ==="; lsblk -o NAME,SIZE,ROTA,TYPE,FSTYPE,MOUNTPOINT
  echo "=== 网络 ==="; ip -brief addr
  echo "=== 监听 ==="; ss -lnt
} 2>&1 | tee "./host-facts-$(date +%Y%m%d).txt"
echo "已写入 host-facts-$(date +%Y%m%d).txt"
```

> [!warning] `Serial Number` 字段在虚拟机上不是真序列号
> `dmidecode -t system` 报的 `Serial Number: VMware-56 4d 84 a6 1c 13 ec db-...` 与 `UUID` 都是 **VMware 按虚拟机生成的**，不是主板序列号；`baseboard` 的 `Serial Number` 与 `Asset Tag` 直接是 `None` / `Not Specified`，`Product Name` 是 `440BX Desktop Reference Platform`（一块 1998 年的芯片组参考板名字，纯粹是 VMware 沿用的兼容字符串）。**台账里的「资产编号」永远要来自你自己的命名体系，不能抄 `dmidecode` 的序列号**——换一台虚拟机，这个字段就变了。

`lshw -short` 的完整输出是 **462 行**——其中 **128 行 `processor` 与 128 行 `DIMM`** 全是 VMware 模拟出来的空槽位（`/0/5` 到 `/0/82` 那一长串 `CPU` 与 `DIMM [empty]`）。所以**台账里只抄有用的那几行**：`system` / 内存条 / 每块盘 / 每张网卡，别把 `lshw` 的原始输出整段倒进台账。三个只靠交叉核对才能发现的「假信息」在这里都能看到：

1. **`lshw` 把 `/dev/sda3` 报成 `47GiB EFI partition`**，而 `blkid` 明确说它是 `TYPE="LVM2_member"`——`lshw` 对 LVM 分区的分类不可信。
2. **`lshw` 报 `8GiB System Memory`**，而 `/proc/meminfo` 是 `MemTotal: 8083496 kB`（= 7894 MiB）——取整到 GiB 之后与真实内存对不上，「8 GiB」只是 VMware 给虚拟机的配置值。
3. **`lspci` 报的是「模拟出来的 PCI 设备」**：`82545EM` 是 Intel 一款 2001 年的千兆网卡型号，实际驱动是 `e1000`（见下）。

### 2.4 SMART：本机能跑命令，但拿不到数据（真实结果）

```text
$ smartctl -i /dev/sda
smartctl 7.4 2023-08-01 r5530 [x86_64-linux-6.8.0-139-generic] (local build)
Copyright (C) 2002-23, Bruce Allen, Christian Franke, www.smartmontools.org

=== START OF INFORMATION SECTION ===
Vendor:               VMware,
Product:              VMware Virtual S
Revision:             1.0
User Capacity:        85,899,345,920 bytes [85.8 GB]
Logical block size:   512 bytes
Rotation Rate:        Solid State Device
Device type:          disk
Local Time is:        Sat Sep 19 08:06:16 2026 UTC
SMART support is:     Unavailable - device lacks SMART capability.

$ echo $?
0
```

这段输出值得完整读一遍，因为它把「命令可用」和「数据可用」两件事分开了，**退出码 0（成功）不代表拿到了健康数据**：

- `smartctl` **装好了、跑通了**（版本 7.4，退出码 0），并且能报出盘的身份（`VMware Virtual S`、85.8 GB）；
- 但 `SMART support is: Unavailable - device lacks SMART capability.`——**VMware 虚拟盘不透传 SMART**，所以 `smartctl -a`、`-H`、`-A` 都拿不到 `Reallocated_Sector_Ct`、`Power_On_Hours` 这类字段；
- `Rotation Rate: Solid State Device` 是 VMware 报给虚拟盘的**固定值**，与该盘实际落在宿主的 SSD 还是 HDD 无关；
- 结论：**在虚拟机里「磁盘健康」这条路是断的**。判据要换成别的：宿主侧的存储告警、`dmesg` 里的 `I/O error`、文件系统 `errors=remount-ro` 的只读切换、以及 `e2scrub`/`mdadm --monitor` 这类主动巡检。

> [!warning] 这条与 `lsblk` 的 `ROTA` 直接矛盾，两边都不能单独信
> 同一块盘：`lsblk` 报 `ROTA=1`（机械盘），`cat /sys/block/sda/queue/rotational` 也是 `1`，而 `smartctl -i` 报 `Rotation Rate: Solid State Device`。**虚拟化环境会同时把两个字段都伪造掉**，而且互相矛盾。判断介质类型的可靠路径只有：物理机看 `smartctl -i` / `nvme id-ctrl`，云主机看云盘规格（SSD/ESSD），虚拟机上**直接问宿主/云平台**，别信客户机里的字段。这也是一句更普遍的提醒：**采集到的字段要先判断它是不是真的，再决定要不要写进台账**。

### 2.5 硬件与固件台账要额外记的三件事

这三个字段经常被漏掉，但在真实故障里都是决定性的：

| 字段 | 为什么必须记 | 怎么采 | 本机实测情况 |
| --- | --- | --- | --- |
| **BIOS/UEFI 版本与日期** | 固件 bug 会表现为「随机重启」「网卡丢包」；升级固件需要重启窗口 | `dmidecode -t bios`（root） | **采到了**：`Phoenix Technologies LTD` / `6.00` / `02/17/2026`（`hostnamectl` 也给出 `Firmware Version: 6.00`、`Firmware Age: 7month 1d`） |
| **RAID 卡型号、固件版本、缓存策略与 BBU 状态** | 决定写缓存是「写回」还是「写穿」，直接影响 IO 延迟与掉电数据安全 | 厂商工具（`storcli`/`perccli`）+ `dmesg` 里的阵列卡信息 | **不存在**：`lspci` 里只有 `LSI 53c1030` 这个模拟 SCSI 控制器，没有 RAID 卡、没有 BBU——这一栏应当写「不适用（虚拟机单盘）」而不是留空 |
| **网卡固件版本** | 网卡固件与驱动不匹配会导致丢包、协商异常 | `ethtool -i <iface>` | **采到但为空**：`driver: e1000`、`firmware-version:`（空）——虚拟网卡不上报固件版本 |

这三项都属于「平时不看、出事时救命」的信息，**采集成本高（要 root、要厂商工具），所以更适合放在季度巡检里做一次，而不是每次变更前临时查**。台账里遇到「不适用」和「空值」都要写清楚原因，这两种都不是「忘了采」。

## 3. 依赖关系怎么画

### 3.1 一阶依赖：三条只读命令

```bash
ss -lnt                                   # 验证：这台机器对外提供哪些端口
ss -tnp | head -30                        # 验证：谁在连它、它连谁（-p 需要权限，非 root 只能看到自己的进程）
systemctl list-dependencies --reverse <unit>
                                          # 验证：如果停了它，哪些单元会被带停（反向依赖）
systemctl list-dependencies <unit>        # 验证：启动它需要先有什么（正向依赖）
```

画出一阶依赖之后，把「端口 → 服务 → 单元 → 责任人」连起来，一张最小的服务台账就成型了：

| 服务 | 单元 | 监听 | 谁依赖它 | 我依赖谁 | 责任人 | 数据在哪 |
| --- | --- | --- | --- | --- | --- | --- |
| 订单 API | `order-api.service` | `10.0.1.5:8443` | 网关、结算任务 | MySQL 主库、Redis、订单下游 | 张 | 无状态；配置在 `/etc/order-api/` |
| 结算任务 | `settle.timer` | 无 | 无（内部） | MySQL 从库、对象存储 | 李 | 中间态写在 `/var/lib/settle/` |

### 3.2 二阶依赖：为什么必须画

只画一阶会漏掉两种最贵的故障：

1. **共享依赖**：A 服务和 B 服务都连同一个 Redis。A 打了个热点 key，把 Redis 拖慢，B 跟着出事——**两个服务的一阶依赖看不到这层耦合**。
2. **隐式依赖**：定时任务、证书轮换、监控采集、备份代理。它们平时不显眼，但**一旦机器重启后没起来，业务不会立刻报错，等发现时已经错过了数据窗口**。

最常见的隐式依赖清单（建议直接抄进台账）：

| 类别 | 典型项 | 漏了会怎样 |
| --- | --- | --- |
| 定时任务 | 备份、日志归档、数据同步、证书续期 | 几个月后才发现某个备份从没成功过 |
| 代理与采集 | 监控 agent、日志采集、安全 agent | 出故障时没有指标与日志可看 |
| 凭据 | 证书、密钥、token、数据库密码 | 到期当天全站报错 |
| 网络出口 | DNS、代理、NAT 网关、防火墙规则 | 换机房或改策略后服务连不上外部 |

## 4. 台账的字段设计

### 4.1 机器台账（最小可用）

| 字段 | 示例 | 谁在用 |
| --- | --- | --- |
| 主机名 / 资产编号 | `prod-order-03` / `SRV-10231` | 定位、工单 |
| 环境与角色 | `prod` / `订单服务 · 无状态` | 分级、影响面 |
| 机房 / 可用区 | `az-b` | 故障域分析（子笔记 12） |
| 规格 | `8 vCPU / 16 GiB / 系统盘 100 GiB` | 容量规划 |
| 发行版与内核 | `Ubuntu 24.04.5 / 6.8.0-139-generic` | 兼容性判断 |
| 固件版本 | `BIOS 6.00（2026-02-17）/ RAID 不适用（虚拟机单盘）/ 网卡 FW 空（虚拟网卡不上报）` | 补丁窗口 |
| 数据盘与文件系统 | `nvme0n1 → XFS → /data` | 恢复与扩容 |
| 备份归属 | `作业号 bk-order-daily，保留 30 天` | 恢复演练 |
| 到期日 | 证书 / 许可 / 支持合同 | 到期管理（子笔记 15） |
| 责任人 | 张（主）+ 李（备） | 通报与升级 |

### 4.2 字段越多越好吗

不是。台账的成败取决于**它是否会被更新**，而不是字段多寡。三条设计原则：

1. **每个字段都要有维护点**：能自动化采集的（系统信息、容量）用脚本定期刷新；只有人能判断的（责任人、备份归属）写进变更收口流程。
2. **能被机器读的尽量不手填**：手填的值三个月后必然过时。
3. **一列都不要放「据说」**：台账里的值要么是采出来的，要么是有人负责的。

```bash
df -h                                     # 验证：容量字段的来源之一
free -m | head -2                         # 验证：内存规格
cat /etc/machine-id                       # 验证：机器唯一标识（重装会变，可用于识别「这台是否被重装过」）
```

## 5. 配置漂移：台账最大的敌人

**配置漂移（drift）**指的是机器上的实际状态与「它应该是什么样」之间的偏离。它的成因几乎都是同一个：**配置只被人的记忆维护**。

三种典型漂移，以及它们各自的发现方式：

| 漂移类型 | 现象 | 怎么发现 |
| --- | --- | --- |
| 手工改动 | 有人直接登上去改了配置，没进版本库 | 与配置管理仓库/黄金镜像对比（`diff`、`rpm -V`/`dpkg --verify`） |
| 版本漂移 | 100 台里 7 台还在旧版本 | 批量采集版本号并与台账比对（子笔记 09） |
| 时间漂移 | 机器时间或时区不一致，日志对不上 | 批量采集 `timedatectl` 输出（子笔记 09） |

发现漂移之后不要立刻「全部改回统一」——**先判断它是不是有人故意改的**。漂移里常常藏着一次没走流程的紧急修复；直接抹平等于把那个修复一起回滚了。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 「机器就这几台，我记在脑子里」 | 人一多、时间一长必然失准；台账的价值在「别人也能查」 |
| 「台账等有空再补」 | 台账的维护点必须挂在变更收口上，否则永远不会补 |
| 把台账做成需要手工填几十列的表格 | 维护成本高于收益，三个月后没人更新 |
| 直接相信 `dmidecode`/`lsblk`/`lshw` 报的硬件信息 | 虚拟化环境会伪造一部分字段，而且**互相矛盾**：同一块盘 `lsblk` 报 `ROTA=1`（机械盘）而 `smartctl -i` 报 `Rotation Rate: Solid State Device`；`lshw` 把 LVM 分区 `sda3` 报成 `EFI partition`、把 7894 MiB 内存报成 `8GiB`；`dmidecode` 的序列号只是 VMware 生成的 UUID |
| 只画一阶依赖 | 会漏掉共享依赖（同一个 Redis/数据库）与隐式依赖（定时任务、证书、采集代理） |
| 发现漂移就统一抹平 | 漂移里可能藏着一次未走流程的紧急修复，抹平等于把它回滚 |
| 把「责任人」填成团队名 | 出事时没人负责；主备两个人名是底线 |
| 只记机器不记数据 | 恢复演练时找不到「这份数据在哪个备份集里」 |

## 决策练习

> [!question]- 场景：你接手了一台 `prod-report-01`，除了主机名什么都不知道。半小时后你要在上面改一个参数，需要写变更单的「范围」和「影响面」。
> A. 先改，改完再看看有没有影响别的服务
> B. 用只读命令把「这台机器是什么、对外提供什么、谁在连它、有没有定时任务和证书」采一遍，把结果写进变更单；采不出来的字段（责任人、备份归属）标注为待确认，并去找人问
> C. 直接把整台机器重启一遍，看哪些服务会报错，就知道了
>
> **答案：B。**
> A 跳过了影响面评估，等于在没有地图的情况下开船。
> C 是拿生产做实验：「重启发现问题」的代价是**用户真的受影响**，而且重启本身会毁掉现场。要知道依赖关系，用 `systemctl list-dependencies --reverse` 与 `ss -tnp` 就够了，不必真的重启。
> B 是正解：**先采集、再填单、采不到的标注待确认**。待确认项本身就是最有价值的产出——它告诉你哪些信息目前只存在某个人的脑子里。

## 要点自测

> [!question]- 资产信息分哪三组？各用什么命令采？
> - 硬件：`lscpu`、`free -h`、`lsblk`、`lspci`、`lshw -short`；固件：`dmidecode -t system/-t bios/-t baseboard`、`ethtool -i`、厂商 RAID 工具；系统：`/etc/os-release`、`uname -r`、`systemctl --version`、`systemd-detect-virt`、`hostnamectl`。
> - 固件组**需要 root**；本实验机 root 可用、DMI 齐全，三组都采得到，**唯一拿不到的是 SMART 健康数据**（`smartctl` 能跑但报 `Unavailable - device lacks SMART capability`）。容器里通常拿不到（`/sys/class/dmi/id/` 被隐藏或为空）。
> - **第一反应不要是什么**：不要把虚拟机里采到的硬件字段当真——本机的 `ROTA`、`lshw` 的容量与分区类型、`dmidecode` 的序列号三类字段都是假的。

> [!question]- 怎么用只读命令画出一阶依赖？
> - `ss -lnt` 找对外端口，`ss -tnp` 找谁在连，`systemctl list-dependencies --reverse <unit>` 找「停了它会带停谁」。
> - 把这些连成「端口 → 服务 → 单元 → 责任人」的表，就是最小服务台账。
> - **第一反应不要是什么**：不要用「重启一下看谁报错」来发现依赖。

> [!question]- 为什么必须画二阶依赖？最常见的三类隐式依赖是什么？
> - 一阶只看得到直接调用关系，看不到**共享依赖**（同一个数据库/缓存）与**隐式依赖**（定时任务、证书、采集代理）。
> - 隐式依赖最危险的地方是：它们坏了业务不会立刻报错，等发现时数据窗口已经错过。
> - **第一反应不要是什么**：不要以为「服务在跑」就代表这台机器的依赖都齐了。

> [!question]- 台账字段设计的三条原则是什么？台账什么时候更新？
> - 每个字段有维护点；能自动采集的不手填；不放「据说」的值。
> - 更新点是**变更收口**：把台账更新写进变更单的收口一栏。
> - **第一反应不要是什么**：不要追求字段多，追求**会被更新**。

> [!question]- 什么是配置漂移？发现漂移后为什么不能直接统一抹平？
> - 漂移是实际配置与「应该是什么样」之间的偏离，成因是配置只靠人的记忆维护。
> - 因为漂移里可能藏着一次没走流程的紧急修复；先问清楚「谁改的、为什么改」，再决定是否统一。
> - **第一反应不要是什么**：不要看到不一致就批量覆盖。
