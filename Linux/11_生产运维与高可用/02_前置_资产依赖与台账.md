# 前置：资产、依赖与台账

> [!cite] 参考资料
> `man 8 dmidecode`、`man 1 lscpu`、`man 8 lspci`、`man 8 lsblk`、`man 8 blkid`、`man 8 findmnt`、`man 8 smartctl`、`man 8 ethtool`、`man 1 hostnamectl`、`man 1 systemd-detect-virt`、`man 5 os-release`、`man 8 ss`、`man 1 lsof`、`man 1 systemctl`，内核文档 `Documentation/ABI/testing/sysfs-devices-system-cpu`（`/sys/devices/system/cpu/` 暴露的硬件信息）；以及发行版官方文档中 "Inventory your hardware" 一类的章节。
>
> **实测状态**：本篇的采集命令在本机（Ubuntu 24.04.4 LTS / WSL2 / 内核 `6.6.87.2-microsoft-standard-WSL2` / 非 root `uid=1000`）跑过。**关键限制**：WSL2 里 `/sys/class/dmi/id/` 是空的，`dmidecode`、`lspci`、`smartctl`、`nvme` 都不可用——**这是虚拟化环境的通病**，物理机与大多数云主机上才拿得到完整硬件与固件信息。`lscpu`、`lsblk`、`blkid`、`findmnt`、`hostnamectl`、`ethtool`、`systemd-detect-virt` 在本机可用。文中凡标「物理机/云主机上」的输出均**未实测**，是文档值。

> **这篇讲什么**：变更之前你必须先知道「这台机器是什么、它属于谁、谁在依赖它」。这一篇讲三件事：**资产信息从哪采**、**依赖关系怎么画**、**台账要记哪些字段并怎么维护**。
>
> **必须先读什么**：无。会 shell、会读命令输出即可。
>
> **读完能回答**：
> 1. 一台机器的硬件、固件、系统三组信息，分别用哪几条命令采集？
> 2. 没有现成的 CMDB，怎么靠只读命令把「这台机器对外提供什么、谁在连它」画出来？
> 3. 台账里哪些字段是「不记就会出事」的？什么时候更新？
>

## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **台账不是「给领导看的表」，是变更前的影响面来源。**
>   - 怎么验证：任何一次变更单里的「范围」段，都应该能从台账里直接查出来；查不出来，说明台账缺字段。
> - **资产信息分三组采：硬件、固件、系统。**
>   - 证据：本机实测 `lscpu` 给出 `24` vCPU / `Intel(R) Core(TM) i7-14650HX` 一级的信息，`lsblk` 给出 `sdd 1T disk ext4 /mnt/wslg/distro`，`systemd-detect-virt` 给出虚拟化类型；`dmidecode`/`lspci`/`smartctl` 在本机**不可用**，因为它是 WSL2 虚拟机。
> - **依赖关系两头都要画：谁依赖我，我依赖谁。**
>   - 怎么验证：`ss -lnt` 找出监听端口，`ss -tnp` 看谁在连它，`systemctl list-dependencies` 看单元依赖——三条命令就能画出这台机器的一阶依赖图。
> - **配置漂移是「只有人类记忆在维护配置」的必然结果。**
>   - 怎么验证：隔一个月再采一遍同一组信息，和台账比对；对不上的字段就是漂移。
> - **台账的更新点只有一个：变更收口时。**
>   - 证据：把台账更新写进变更单的「收口」一栏（子笔记 08），就不会出现「改了但没记」。

## 1. 为什么要台账

新人常觉得台账是形式主义，因为「机器就那几台，我记在脑子里」。这种想法在三种情况下一击即碎：

| 场景 | 没有台账时会发生什么 |
| --- | --- |
| 你要给 100 台机器改一个参数 | 你得挨个登上去看是不是同一个发行版、同一个版本 |
| 一台机器挂了，别人问你影响什么 | 你只能等业务报错才知道谁在依赖它 |
| 三个月后你要打安全补丁 | 你得重新采一遍 BIOS/固件版本，因为没人记得上次升到哪了 |
| 你要做一次恢复演练 | 你找不到「这台机器的数据应该在哪个备份集里」 |

台账的最小形态可以只是一张 Markdown 表或一个 CSV，**关键是它有维护点、有责任人、有更新时机**。

## 2. 资产信息从哪采

### 2.1 三组信息

| 组 | 采什么 | 命令 | 备注 |
| --- | --- | --- | --- |
| **硬件** | CPU 型号与核数、内存容量、磁盘型号与大小、网卡型号与速率 | `lscpu`、`free -h`、`lsblk -o NAME,SIZE,ROTA,MODEL`、`lspci \| grep -i ethernet` | `lspci` 在虚拟机上往往看不到真实网卡；`ROTA=1` 表示机械盘（rotational） |
| **固件** | 主板厂商与型号、BIOS/UEFI 版本与日期、RAID 卡固件、网卡固件 | `dmidecode -t system`、`dmidecode -t bios`、厂商工具（`storcli`/`perccli`）、`ethtool -i <iface>` | **需要 root**；容器/WSL 里通常拿不到 |
| **系统** | 发行版、内核、systemd、cgroup、虚拟化类型、主机名与机器标识 | `cat /etc/os-release`、`uname -r`、`systemctl --version \| head -1`、`stat -fc %T /sys/fs/cgroup`、`systemd-detect-virt`、`hostnamectl`、`cat /etc/machine-id` | 全部只读，生产机可随时执行 |

### 2.2 本机实测的采集脚本（只读，生产机可以跑）

```bash
#!/usr/bin/env bash
set -u
{
  echo "=== 身份 ==="; hostnamectl 2>/dev/null | head -8; systemd-detect-virt
  echo "=== 系统 ==="; grep -E '^(PRETTY_NAME|VERSION_ID)' /etc/os-release; uname -r
  echo "=== CPU ==="; lscpu | grep -E '^(Architecture|CPU\(s\)|Model name|Thread|Core)'
  echo "=== 内存 ==="; grep -E '^(MemTotal|SwapTotal)' /proc/meminfo
  echo "=== 磁盘 ==="; lsblk -o NAME,SIZE,ROTA,TYPE,FSTYPE,MOUNTPOINT
  echo "=== 网络 ==="; ip -brief addr
  echo "=== 监听 ==="; ss -lnt
} 2>&1 | tee "./host-facts-$(date +%Y%m%d).txt"
echo "已写入 host-facts-$(date +%Y%m%d).txt"
```

本机实测输出片段：

```text
=== 身份 ===
 Static hostname: <本机主机名>
 Virtualization: wsl
=== 系统 ===
PRETTY_NAME="Ubuntu 24.04.4 LTS"
VERSION_ID="24.04"
6.6.87.2-microsoft-standard-WSL2
=== CPU ===
Architecture:                         x86_64
CPU(s):                               24
Model name:                           Intel(R) Core(TM) i7-14650HX
Core(s) per socket:                   12
=== 磁盘 ===
NAME MAJ:MIN   SIZE ROTA TYPE FSTYPE MOUNTPOINT
sda    8:0   388.4M    1 disk ext4
sdb    8:16    186M    1 disk ext4
sdc    8:32      4G    1 disk swap   [SWAP]
sdd    8:48      1T    1 disk ext4   /mnt/wslg/distro
```

> [!warning] `Rota=1` 在虚拟机里不代表真的是机械盘
> 本机 `lsblk` 把四块虚拟盘都报成 `ROTA=1`，但它们是宿主上的文件。**判断介质类型要用 `rotational` 之外的手段**：物理机看 `smartctl -i` / `nvme id-ctrl`，云主机看云盘规格（SSD/ESSD 等）。这也是一句更普遍的提醒：**虚拟化环境会伪造一部分硬件信息，采集到的字段要先判断它是不是真的**。

### 2.3 硬件与固件台账要额外记的三件事

这三个字段经常被漏掉，但在真实故障里都是决定性的：

| 字段 | 为什么必须记 | 怎么采 |
| --- | --- | --- |
| **BIOS/UEFI 版本与日期** | 固件 bug 会表现为「随机重启」「网卡丢包」；升级固件需要重启窗口 | `dmidecode -t bios`（root） |
| **RAID 卡型号、固件版本、缓存策略与 BBU 状态** | 决定写缓存是「写回」还是「写穿」，直接影响 IO 延迟与掉电数据安全 | 厂商工具（`storcli`/`perccli`）+ `dmesg` 里的阵列卡信息 |
| **网卡固件版本** | 网卡固件与驱动不匹配会导致丢包、协商异常 | `ethtool -i <iface>` |

这三项都属于「平时不看、出事时救命」的信息，**采集成本高（要 root、要厂商工具），所以更适合放在季度巡检里做一次，而不是每次变更前临时查**。

## 3. 依赖关系怎么画

### 3.1 一阶依赖：三条只读命令

```bash
ss -lnt                                   # 验证：这台机器对外提供哪些端口
ss -tnp | head -30                        # 验证：谁在连它、它连谁（-p 需要权限，非 root 只能看到自己的进程）
systemctl list-dependencies --reverse <unit>
                                          # 验证：如果停了它，哪些单元会被带停（反向依赖）
systemctl list-dependencies <unit>        # 验证：启动它需要先有什么（正向依赖）
```

画出一阶依赖之后，把「端口 → 服务 → 单元 → 责任人」连起来，一张最小的服务台账就成型了：

| 服务 | 单元 | 监听 | 谁依赖它 | 我依赖谁 | 责任人 | 数据在哪 |
| --- | --- | --- | --- | --- | --- | --- |
| 订单 API | `order-api.service` | `10.0.1.5:8443` | 网关、结算任务 | MySQL 主库、Redis、订单下游 | 张 | 无状态；配置在 `/etc/order-api/` |
| 结算任务 | `settle.timer` | 无 | 无（内部） | MySQL 从库、对象存储 | 李 | 中间态写在 `/var/lib/settle/` |

### 3.2 二阶依赖：为什么必须画

只画一阶会漏掉两种最贵的故障：

1. **共享依赖**：A 服务和 B 服务都连同一个 Redis。A 打了个热点 key，把 Redis 拖慢，B 跟着出事——**两个服务的一阶依赖看不到这层耦合**。
2. **隐式依赖**：定时任务、证书轮换、监控采集、备份代理。它们平时不显眼，但**一旦机器重启后没起来，业务不会立刻报错，等发现时已经错过了数据窗口**。

最常见的隐式依赖清单（建议直接抄进台账）：

| 类别 | 典型项 | 漏了会怎样 |
| --- | --- | --- |
| 定时任务 | 备份、日志归档、数据同步、证书续期 | 几个月后才发现某个备份从没成功过 |
| 代理与采集 | 监控 agent、日志采集、安全 agent | 出故障时没有指标与日志可看 |
| 凭据 | 证书、密钥、token、数据库密码 | 到期当天全站报错 |
| 网络出口 | DNS、代理、NAT 网关、防火墙规则 | 换机房或改策略后服务连不上外部 |

## 4. 台账的字段设计

### 4.1 机器台账（最小可用）

| 字段 | 示例 | 谁在用 |
| --- | --- | --- |
| 主机名 / 资产编号 | `prod-order-03` / `SRV-10231` | 定位、工单 |
| 环境与角色 | `prod` / `订单服务 · 无状态` | 分级、影响面 |
| 机房 / 可用区 | `az-b` | 故障域分析（子笔记 12） |
| 规格 | `8 vCPU / 16 GiB / 系统盘 100 GiB` | 容量规划 |
| 发行版与内核 | `Ubuntu 24.04.4 / 6.6.87` | 兼容性判断 |
| 固件版本 | `BIOS 2.14 / RAID FW 5.20 / 网卡 FW 22.5` | 补丁窗口 |
| 数据盘与文件系统 | `nvme0n1 → XFS → /data` | 恢复与扩容 |
| 备份归属 | `作业号 bk-order-daily，保留 30 天` | 恢复演练 |
| 到期日 | 证书 / 许可 / 支持合同 | 到期管理（子笔记 15） |
| 责任人 | 张（主）+ 李（备） | 通报与升级 |

### 4.2 字段越多越好吗

不是。台账的成败取决于**它是否会被更新**，而不是字段多寡。三条设计原则：

1. **每个字段都要有维护点**：能自动化采集的（系统信息、容量）用脚本定期刷新；只有人能判断的（责任人、备份归属）写进变更收口流程。
2. **能被机器读的尽量不手填**：手填的值三个月后必然过时。
3. **一列都不要放「据说」**：台账里的值要么是采出来的，要么是有人负责的。

```bash
df -h                                     # 验证：容量字段的来源之一
free -m | head -2                         # 验证：内存规格
cat /etc/machine-id                       # 验证：机器唯一标识（重装会变，可用于识别「这台是否被重装过」）
```

## 5. 配置漂移：台账最大的敌人

**配置漂移（drift）**指的是机器上的实际状态与「它应该是什么样」之间的偏离。它的成因几乎都是同一个：**配置只被人的记忆维护**。

三种典型漂移，以及它们各自的发现方式：

| 漂移类型 | 现象 | 怎么发现 |
| --- | --- | --- |
| 手工改动 | 有人直接登上去改了配置，没进版本库 | 与配置管理仓库/黄金镜像对比（`diff`、`rpm -V`/`dpkg --verify`） |
| 版本漂移 | 100 台里 7 台还在旧版本 | 批量采集版本号并与台账比对（子笔记 09） |
| 时间漂移 | 机器时间或时区不一致，日志对不上 | 批量采集 `timedatectl` 输出（子笔记 09） |

发现漂移之后不要立刻「全部改回统一」——**先判断它是不是有人故意改的**。漂移里常常藏着一次没走流程的紧急修复；直接抹平等于把那个修复一起回滚了。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 「机器就这几台，我记在脑子里」 | 人一多、时间一长必然失准；台账的价值在「别人也能查」 |
| 「台账等有空再补」 | 台账的维护点必须挂在变更收口上，否则永远不会补 |
| 把台账做成需要手工填几十列的表格 | 维护成本高于收益，三个月后没人更新 |
| 直接相信 `dmidecode`/`lsblk` 报的硬件信息 | 虚拟化环境会伪造一部分字段（本机四块虚拟盘全报 `ROTA=1`）；要判断字段真假 |
| 只画一阶依赖 | 会漏掉共享依赖（同一个 Redis/数据库）与隐式依赖（定时任务、证书、采集代理） |
| 发现漂移就统一抹平 | 漂移里可能藏着一次未走流程的紧急修复，抹平等于把它回滚 |
| 把「责任人」填成团队名 | 出事时没人负责；主备两个人名是底线 |
| 只记机器不记数据 | 恢复演练时找不到「这份数据在哪个备份集里」 |

## 决策练习

> [!question]- 场景：你接手了一台 `prod-report-01`，除了主机名什么都不知道。半小时后你要在上面改一个参数，需要写变更单的「范围」和「影响面」。
> A. 先改，改完再看看有没有影响别的服务
> B. 用只读命令把「这台机器是什么、对外提供什么、谁在连它、有没有定时任务和证书」采一遍，把结果写进变更单；采不出来的字段（责任人、备份归属）标注为待确认，并去找人问
> C. 直接把整台机器重启一遍，看哪些服务会报错，就知道了
>
> **答案：B。**
> A 跳过了影响面评估，等于在没有地图的情况下开船。
> C 是拿生产做实验：「重启发现问题」的代价是**用户真的受影响**，而且重启本身会毁掉现场。要知道依赖关系，用 `systemctl list-dependencies --reverse` 与 `ss -tnp` 就够了，不必真的重启。
> B 是正解：**先采集、再填单、采不到的标注待确认**。待确认项本身就是最有价值的产出——它告诉你哪些信息目前只存在某个人的脑子里。

## 要点自测

> [!question]- 资产信息分哪三组？各用什么命令采？
> - 硬件：`lscpu`、`free -h`、`lsblk`、`lspci`；固件：`dmidecode -t bios`、`ethtool -i`、厂商 RAID 工具；系统：`/etc/os-release`、`uname -r`、`systemctl --version`、`systemd-detect-virt`、`hostnamectl`。
> - 固件组**需要 root**，而且容器/WSL 里通常拿不到（本机 `/sys/class/dmi/id/` 为空）。
> - **第一反应不要是什么**：不要把虚拟机里采到的硬件字段当真——本机四块虚拟盘全报 `ROTA=1`。

> [!question]- 怎么用只读命令画出一阶依赖？
> - `ss -lnt` 找对外端口，`ss -tnp` 找谁在连，`systemctl list-dependencies --reverse <unit>` 找「停了它会带停谁」。
> - 把这些连成「端口 → 服务 → 单元 → 责任人」的表，就是最小服务台账。
> - **第一反应不要是什么**：不要用「重启一下看谁报错」来发现依赖。

> [!question]- 为什么必须画二阶依赖？最常见的三类隐式依赖是什么？
> - 一阶只看得到直接调用关系，看不到**共享依赖**（同一个数据库/缓存）与**隐式依赖**（定时任务、证书、采集代理）。
> - 隐式依赖最危险的地方是：它们坏了业务不会立刻报错，等发现时数据窗口已经错过。
> - **第一反应不要是什么**：不要以为「服务在跑」就代表这台机器的依赖都齐了。

> [!question]- 台账字段设计的三条原则是什么？台账什么时候更新？
> - 每个字段有维护点；能自动采集的不手填；不放「据说」的值。
> - 更新点是**变更收口**：把台账更新写进变更单的收口一栏。
> - **第一反应不要是什么**：不要追求字段多，追求**会被更新**。

> [!question]- 什么是配置漂移？发现漂移后为什么不能直接统一抹平？
> - 漂移是实际配置与「应该是什么样」之间的偏离，成因是配置只靠人的记忆维护。
> - 因为漂移里可能藏着一次没走流程的紧急修复；先问清楚「谁改的、为什么改」，再决定是否统一。
> - **第一反应不要是什么**：不要看到不一致就批量覆盖。
