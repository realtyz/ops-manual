## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **六要素：目标、范围、备份、回滚、验证、窗口。缺一个就不是变更单，是便签。**
>   - 怎么验证：交给没参与的人，他能照着执行、照着重放；做不到就说明还有格子没填实。
> - **最容易漏的是「验证」和「回滚」——因为它们要在动手之前就写出答案。**
>   - 证据：本篇给出的模板把「回滚命令」和「验收判据」放在同一行，强制你在同一个动作上同时想清楚「进」和「退」。
> - **评审会只问四个问题：影响面多大、最坏结果是什么、怎么退回去、谁在执行时喊停。**
>   - 怎么验证：会上答不出这四个问题，就该改期而不是「边做边想」。
> - **分级决定审批人，不决定技术方案。**
>   - 证据：同一份技术方案，影响 1 台还是 100 台、可逆还是不可逆，审批层级可以差两级。
> - **窗口要有结束时间，以及「到点没做完怎么办」。**
>   - 怎么验证：写下「窗口 22:00–23:30；23:15 未完成或验收未通过即执行回滚」——写不出这句，窗口就没有意义。

## 1. 变更单六要素

### 1.1 六要素各自回答什么

| 要素 | 回答的问题 | 写不好的后果 |
| --- | --- | --- |
| **目标** | 为什么要做？做成什么样算成功？ | 做完才发现「其实不是要这个」 |
| **范围** | 改哪些机器/服务/配置？第一批多少？ | 漏改变更对象，出现配置不一致 |
| **备份** | 出问题靠什么恢复？备份在哪、什么时候做的、怎么验证过？ | 想回滚时发现备份是三天前的 |
| **回滚** | 退回原状的**具体命令**与耗时；触发条件是什么？ | 现场临时想回滚方案，多半会引入第二个错误 |
| **验证** | 怎么证明成功？指标、业务、观察窗口分别是什么？ | 无法判断成功失败，只能「感觉还行」 |
| **窗口** | 什么时候开始、什么时候必须结束？到点未完成怎么办？ | 拖到业务高峰；或匆忙收尾留下半成品 |

### 1.2 模板（可直接抄）

```text
变更单 #<编号>
标题：<一句话说清做什么>
类型：标准 / 重大 / 紧急            发起人：<姓名>      执行人：<姓名>
评审人：<姓名>                       验证人：<姓名>      计划时间：<YYYY-MM-DD HH:MM – HH:MM>

一、目标
  为什么做：<业务/安全/容量原因>
  成功标准：<可量化的一句话，例如 "配置生效且 p99 不高于基线 10%">

二、范围
  对象：<服务名 / 主机列表或分组 / 配置文件路径>
  第一批：<X/Y 台，约占容量 Z%>
  不改动：<明确列出本次不碰的东西>

三、备份
  内容与位置：<备份了什么、放在哪、用什么方式>
  时间点：<YYYY-MM-DD HH:MM>
  验证方式：<怎么确认这份备份可用，例如 "已在实验机恢复过一次，耗时 6 分钟">

四、回滚
  触发条件：<写成可判定的句子，例如 "验收不通过 / 错误率 > 1% 持续 5 分钟">
  回滚命令：<逐条写出，可直接粘贴执行>
  回滚耗时：<实验机上实测的分钟数>
  回滚后验证：<怎么确认真的退回去了>

五、验证
  指标：<命令 + 阈值>
  业务：<探活请求或业务动作>
  观察窗口：<时长，间歇性问题覆盖 2~3 个周期>

六、窗口
  开始/结束：<YYYY-MM-DD HH:MM – HH:MM>
  到点未完成：<继续/回滚/延期的判定人与判定标准>
  通知：<谁需要提前知道，用什么渠道>

执行记录（执行时逐批填写）
  批次 | 开始时间 | 结束时间 | 执行人 | 证据（命令与输出摘要） | 结论

收口
  结果：成功 / 部分成功 / 已回滚
  台账与文档更新：<更新了哪份台账、哪段 Runbook>
  改进项：<问题 / owner / 期限>
```

### 1.3 六要素里的三个「隐藏考点」

1. **范围里要写「不改什么」**。只写要改什么，执行时很容易顺手多改一点——多改的那一点往往就是事故来源。
2. **回滚要写「触发条件」，不只是「命令」**。没有触发条件，人会倾向于「再等等看」，小问题拖成大问题。
3. **验证要写「怎么做」，不只是「做什么」**。

```bash
date -Is                                  # 验证：记录变更开始时刻（带时区），用于事后对齐
systemctl list-timers --no-pager | head   # 验证：确认窗口内没有其它定时任务会撞上
journalctl -u <unit> -n 20 --no-pager     # 验证：变更前的日志基线（对比用的「之前」）
```

实验机上以 `ssh` + `ssh.socket` 为例跑这三条（**2026-09-19 08:07 UTC 采集**，来源 `.labvm/evidence/11a_04_review.out.txt` 的第 1～3、16 节，**三命令同一次采集**）：

```text
$ date -Is
2026-09-19T08:07:34+00:00

$ systemctl list-timers --no-pager | head -3
NEXT                             LEFT LAST                           PASSED UNIT                  ACTIVATES
Sat 2026-09-19 08:10:00 UTC  2min 25s Sat 2026-09-19 08:00:12 UTC  7min ago sysstat-collect.timer sysstat-collect.service
Sat 2026-09-19 09:25:48 UTC  1h 18min Sat 2026-09-19 08:00:52 UTC  6min ago fwupd-refresh.timer   fwupd-refresh.service

$ systemctl show ssh -p Id -p ActiveState -p SubState -p MainPID -p NRestarts -p UnitFileState -p FragmentPath
Id=ssh.service
ActiveState=active
SubState=running
MainPID=1348
NRestarts=0
UnitFileState=disabled
FragmentPath=/usr/lib/systemd/system/ssh.service
```

三个只有真跑才会注意到的细节：

1. **`systemctl list-timers` 的第一列是「下一次触发时刻」，不是「这个任务多久跑一次」**。实测里 `sysstat-collect.timer` 的 `NEXT` 是 `08:10:00`、`LEFT` 是 `2min 25s`——**「窗口内有没有定时任务撞上」看的就是这两个字段**，而不是定时任务的周期。生产上最典型的撞车是「22:00 开始变更，22:00 正好是备份任务与日志轮转的时间」。
2. **`UnitFileState=disabled` 而 `ActiveState=active`**：`ssh.service` 没被 enable，它是被 `ssh.socket` 拉起来的（`systemctl list-dependencies ssh` 里第一行就是 `ssh.socket`）。**「服务在跑」和「服务开机自启」是两件事**，变更单里如果要写「重启后仍可用」，必须查 `UnitFileState`，不能只看 `ActiveState`。
3. **`NRestarts=0` 是一个可量化的健康判据**：这个计数器会随服务反复崩溃而增长，把它写进变更单的验收判据（「`NRestarts` 仍为 0」）比「服务正常」具体得多。

依赖关系同样可以只用只读命令画出来（同一个 unit 的实测）：

```text
$ systemctl list-dependencies ssh --no-pager | head -5
ssh.service
● ├─-.mount
● ├─ssh.socket
● ├─system.slice
● └─sysinit.target

$ systemctl list-dependencies --reverse ssh --no-pager
ssh.service
```

正向依赖输出了 **63 行**（`sysinit.target` 展开后有 `apparmor.service`、`systemd-journald.service`、`lvm2-monitor.service`、`swap.img.swap` 等），**反向依赖只有 `ssh.service` 自己一行**——意思是**停了 `ssh` 不会带停任何其它单元**。这正是「影响面要数出来」的示范：`ssh` 挂了带停不了别的服务，但它是**唯一的登录入口**，影响面反而最大——**单元依赖图能告诉你「技术上的连带影响」，告不了你「业务上的影响」**，后者必须靠台账与人工判断补齐。

## 2. 影响面评估：把「大概」变成数字

### 2.1 评估表

| 维度 | 要填的内容 | 来源 |
| --- | --- | --- |
| 用户 | 影响多少用户/租户/接口 | 业务指标、调用方清单 |
| 服务 | 影响哪些服务、上下游各是谁 | 服务依赖图（子笔记 02） |
| 数据 | 有无写入/删除；能否恢复；最近一次备份时间 | 备份记录 |
| 时间 | 持续多久；是否撞业务高峰或其它变更 | 变更日历、`systemctl list-timers` |
| 可逆性 | 只读 / 可回滚 / 不可逆（子笔记 01） | 动作清单 |
| 最坏结果 | 一句话：最坏会怎样 | 评审时口头回答 |

### 2.2 三个「必须改期」的信号

1. **窗口内没有回滚的人**：执行人能改，但没人能在窗口内做回滚决策。
2. **备份还没验证过**：尤其是不可逆变更——没有验证过的备份等于没有备份。
3. **同一时间有其他变更**：两件事同时做，出问题无法归因，也无法判断该回滚哪一个。

## 3. 评审与审批

### 3.1 评审会要问的四个问题

| # | 问题 | 答不出来的含义 |
| --- | --- | --- |
| 1 | **影响面多大？** | 说明没做评估，只是在「试」 |
| 2 | **最坏的结果是什么？** | 说明没想过失败路径 |
| 3 | **怎么退回去，多久？** | 说明没有回滚方案 |
| 4 | **执行时谁有权喊停？** | 说明责任不清，出事会互相等 |

### 3.2 审批层级

| 分级 | 谁批 | 什么形式 | 事后动作 |
| --- | --- | --- | --- |
| 标准 | 执行人按 Runbook 自决 | 变更群里知会 | 记录归档 |
| 重大 | 主管 + 业务方（通常要有评审记录） | 评审通过后批准 | 完整记录 + 复盘 |
| 紧急 | on-call 口头批准，事后补单 | 立即执行 | 补单 + 必做复盘 |

> [!warning] 紧急变更不是「跳过流程」的通道
> 紧急变更允许**先做后补**，但不允许**不做**：事后必须补单、补记录，并在复盘里回答「为什么必须紧急」——如果答案是「因为平时没排期」，那它就是一次流程问题，而不是紧急事件（子笔记 16）。

## 4. 窗口与冻结期

### 4.1 窗口怎么定

```text
可用的窗口 = 业务低峰时段
           − 其它已排定的变更
           − 备份/报表等定时任务占用的时间
           − 留给回滚与验收的时间
```

| 场景 | 窗口建议 |
| --- | --- |
| 改配置 + reload | 工作时间内即可，但避开业务高峰前 30 分钟 |
| 重启单个无状态实例 | 任意时间，前提是 LB 能承接 |
| 内核升级 / 重启整机 | 业务低峰 + 预留回滚时间；先摘流量 |
| 数据库主从切换 / DNS 变更 | 排定窗口 + 提前通知 + 业务方在场 |

### 4.2 冻结期的例外

冻结期内只允许两类变更：**止损**（已经在出事）与**安全修复**（有明确漏洞与时限）。两者都要走紧急变更通道并留记录。

## 5. 生产动作：一次变更的立项记录

评审阶段要留下的东西，只有四样：

1. **变更单**（六要素齐全，见 1.2 模板）。
2. **影响面评估表**（本页第 2.1 节）。
3. **分级结论与批准记录**（谁批的、什么时候）。
4. **通知记录**（通知了谁、用什么渠道、对方是否确认）。

> [!example]- 实验 1：给一个只读变更写完整变更单（生产机也可以做，只读）
> **怎么做**：选一件纯只读的事（例如「在 30 台机器上采集版本与容量基线」），按 1.2 的模板写一份完整变更单；这份单子里的「备份」与「回滚」写成「无状态变更，无需回滚」并说明理由。
> **预期**：得到一份别人能照着执行的文档；同时会发现「范围」与「验证」两栏最难写——这正是重点。
> **风险**：无（不接触生产状态）。
> **耗时**：约 20 分钟。
> **怎么退回去**：不需要回滚，归档即可。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 「改动很小，口头说一下就做」 | 分级看影响面不看看改动量；口头变更出事后没有记录可复盘 |
| 「回滚我知道怎么做」 | 回滚要写下来、要在实验机跑过；现场临时组织回滚方案会引入第二个错误 |
| 「没写触发条件，看着不对就回滚」 | 「看着不对」无法执行也无法交接；触发条件必须是可判定的句子 |
| 「验证就写『服务正常』」 | 没有量化就没有验收标准；必须写命令 + 阈值 |
| 「窗口没写结束时间，做完为止」 | 没有结束时间就没有回滚决策点，容易拖进业务高峰 |
| 「范围只写要改什么」 | 必须同时写「不改什么」，防止执行时顺手多改 |
| 「这次跟上次一样，不评估了」 | 环境、流量、依赖都在变；影响面每次都要重新估 |
| 「先把变更做了，事后补单」 | 只有紧急变更可以这样，且必须复盘；常规变更事后补单等于没有前置评审 |

## 决策练习

> [!question]- 场景：你要给 60 台 Web 服务器换一份 TLS 证书并 reload。证书链与私钥文件已备好，旧证书保留在同目录下。同事说「这是标准操作，直接 60 台一起 reload 就行，反正只有几百毫秒的抖动」。
> A. 同意——reload 是平滑的，几百毫秒抖动可以接受
> B. 写成重大变更：影响面是全部用户（TLS 中断会导致全站报错）、回滚是换回旧文件再 reload；先改 1 台并用外部探测验证，再分 4 批推进，每批之间留观察时间；窗口定在业务低峰
> C. 先写一个脚本 `for h in $(cat hosts); do ssh $h 'systemctl reload nginx'; done`，一次性跑完，出问题就再跑一遍改回去
>
> **答案：B。**
> A 错在**只看到「抖动时长」没看到「影响面」**：TLS 配置一旦写错（路径、权限、链不全），服务会**完全拒绝连接**，不是几百毫秒抖动。而且 60 台同时改，等于把「万一写错」放大到全量。
> C 错在两个地方：一是脚本没有幂等与失败处理（第 37 台 SSH 失败会怎样？），二是「再跑一遍改回去」不是回滚方案——回滚要真的把旧证书换回来并验证。
> B 是正解：**按影响面定级 → 写明回滚 → 分批 + 每批验证 → 窗口选低峰**。这四步正是第 1 站与第 2 站的交界。

## 要点自测

> [!question]- 变更单的六要素是什么？哪一个最容易被漏？
> - 目标、范围、备份、回滚、验证、窗口。
> - 最容易漏的是「回滚的触发条件」和「验证的量化判据」——因为它们要求你在动手之前就把答案想清楚。
> - **第一反应不要是什么**：不要把「我知道怎么回滚」当成已经写好回滚方案。

> [!question]- 评审会要问的四个问题是什么？
> - 影响面多大、最坏结果是什么、怎么退回去（多久）、谁在执行时喊停。
> - 这四个问题分别对应 P1（分级）、P4（验收）、P2（恢复）、以及责任分配。
> - **第一反应不要是什么**：不要在没有这四问答案的情况下开始执行。

> [!question]- 变更窗口要怎么定？什么情况下必须改期？
> - 窗口 = 业务低峰 − 其它变更与定时任务 − 留给回滚与验收的时间。
> - 必须改期：窗口内没有能做回滚决策的人、备份还没验证过、同一时间有其它变更。
> - **第一反应不要是什么**：不要写「做完为止」这种没有终点的窗口。

> [!question]- 紧急变更与跳流程的区别在哪？
> - 紧急变更允许先做后补单，但必须补记录、必做复盘，并回答「为什么必须紧急」。
> - 如果答案是「平时没排期」，那它不是紧急变更，是流程问题。
> - **第一反应不要是什么**：不要把紧急变更当作绕过评审的常规通道。
