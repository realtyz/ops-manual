# 幂等与可重入的批量执行

一条命令在你自己那台机器上跑成功过，不代表它能在 200 台上跑成功；更不代表它在中途失败之后能再跑一遍。批量运维出的事故，绝大多数与技术难度无关，而是由两个性质引起的：**数量**（失败会被放大 200 倍）和**静默**（每一台都失败得"很安静"）。

## 1. 批量会同时放大两件事

手工在一台机器上执行时，有三个默认存在的东西：**人在看输出**、**环境是交互式的**、**失败时你会立刻知道**。批量执行把这三个默认全部拿掉，于是同一段逻辑在两处的行为就不再相同：

| 手工有 | 批量没有 | 后果 |
| --- | --- | --- |
| 人在看输出 | 批量只剩退出码和日志，没有人会逐台看屏幕 | 因此失败的表现从"报错刷屏"变成"一行 non-zero" |
| 交互式 shell | 批量走的是非交互 shell，它不读 `.bashrc`/`.bash_profile` | 因为启动文件没有执行，所以 `PATH`、别名、函数、环境变量都与手工不同 |
| 一次一台 | 批量一次改 N 台 | 由于台数被放大，连接数与并发度同步放大，对端与链路的压力也同步放大 |
| 立刻知道 | 批量只能事后翻日志 | 一旦没人当场看见，半成功状态就会一直留着，直到下一个变更撞上它 |

**"手工能跑"与"批量能跑"是两件不同的事**，差距就来自上表。判断一个脚本能不能上批量，不看它写得漂不漂亮，而看它有没有把上面这四行补齐。

### 1.1 连接层的四种坑

批量 `ssh` 的事故八成发生在连接层，而不是命令层，因为命令层的错误会被退出码挡住，而连接层的错误会伪装成别的问题：

- **连接放大**：N 台机器各建多条连接（加上 `ControlMaster`、重试、探活），并发一高就把堡垒机或目标机的 `sshd` 打满，于是 `MaxStartups` 之后开始随机失败。这种表现是"有些机器连不上"，因此很容易被误判成网络问题；
- **没有超时**：一条命令卡在某一台上，整批就停在那里。所以必须显式设 `ConnectTimeout` 与命令级 `timeout`；
- **交互式提问**：`known_hosts` 里的新主机、SSH 口令、`sudo` 口令都会让远端挂住等输入，而批量场景下没人能回答。判据是 `-o BatchMode=yes`，因为它拒绝交互并把这种场合转成失败；
- **没有并发上限**：不做分批的全量并发，只在实验室规模下看起来很快。

一条可以直接用的连接参数写法：

```bash
ssh -o ConnectTimeout=5 -o BatchMode=yes -n <host> '<command>'
# 验证：连不上时在 5 秒内失败，而不是挂住；需要输入的场合直接失败而不是等
```

`-n` 把标准输入接到 `/dev/null`，防止远端因为等待输入而挂住；`BatchMode=yes` 让任何需要交互的场合立刻失败。批量工具里通常写在 inventory（主机清单）的公共参数里（Ansible 的 `ansible_ssh_common_args`）。

### 1.2 环境层：非交互 shell 不读你的 dotfiles

`ssh host 'cmd'` 走的是**非交互、非登录**的 shell，它不会读 `~/.bashrc`（Debian/Ubuntu 的 `~/.bashrc` 开头通常还有一行"非交互就提前 return"的判断）。因此批量执行看到的环境与手工登录看到的环境并不一样：

- `PATH` 可能不含 `/usr/local/bin`、`/opt/xxx/bin`；
- 别名（alias）与 shell 函数全部失效；
- `JAVA_HOME`、代理变量、语言与 `umask` 都可能与手工执行时不同。

**所以批量脚本里不要依赖远端 `PATH`、别名或交互式配置**：用绝对路径，或在脚本开头显式 `export PATH=...`。判据很简单：在你自己的机器上用 `ssh host 'env | sort'` 与登录后的 `env | sort` 各取一份比一比，因为两份输出的差异就是批量脚本拿不到的那部分环境。

## 2. 幂等：性质，不是写法

幂等（idempotent）是一个操作的**性质**：执行一次与执行多次，结果相同。它不是"脚本里加了 `if`"这种写法特征，而是"再跑一遍不会更糟"这个可观察的事实。

实现幂等的固定套路是**先判断、后动作**，而不是直接执行。两者的差别在于：前者把当前状态读出来当输入，因此重复执行时什么都不会发生；后者无条件地改，因此每跑一遍就多留下一份痕迹。

| 直接执行（不幂等） | 先判断后动作（幂等） |
| --- | --- |
| 查服务状态时不看结果，因此查完之后仍然可能去启停一个本来正常的服务 | 先查 `systemctl is-active`，只在它不等于 `active` 时才启停 |
| 用 `echo "k=v" >> /etc/app.conf` 追加，因此每跑一遍配置里就多一行 | 先 `grep` 匹配，命中就不写 |
| 无条件 `cp` 文件，因此每次执行都会改写目标文件的时间戳与内容 | 先比 `sha256sum`，相同就跳过 |
| 无条件建目录，因此目录已存在时该命令会以非 0 退出 | 用 `mkdir -p`，因为它对已存在的目录返回成功 |
| 无条件改一行配置，因此重复执行会不断追加同一行 | 用支持"确保这一行存在"的工具（`lineinfile` 这类模块），因为它会先读后写 |

本机实测的一份幂等脚本：目标文件里应有一行 `vm.swappiness=60`；第 2、3 次运行时输出"已是目标状态，跳过写入（幂等）"、文件行数恒为 1；当脚本里被注入一个不存在的命令时，它停在那一行并以退出码 **127** 退出，目标文件没有被写坏。

**判据就是这一步**：同一个脚本连跑三次，第二、三次不应该产生任何改动，并且退出码为 0。因为一旦第二、三次产生了改动，就说明这个脚本读当前状态的那一步是缺的，所以做不到这一点，它就不该上批量。

### 2.1 可重入：中断之后还能再跑

幂等保证"重复执行安全"，可重入（re-entrant）保证"**中断之后**再执行安全"。批量执行被打断是常态：某一台超时、有人在中间叫停、控制端掉线。

可重入的设计要点是**让每一步都能被独立判断**：

- 每一步开始时先判断"这一步的目标状态是否已达成"，因为这一步判断就是幂等；
- 中间产物放在带唯一标记的临时位置，退出时清理（`trap ... EXIT`），否则中断留下的临时文件会被下一次执行当成正式状态；
- 不要假设"前面的步骤一定成功过"，因为中断可能正好落在两步之间；
- 用锁防止同一台机器被两批同时改（`flock`）。

```bash
flock -n /var/lock/change-11.lock -c '<your command>'
# 验证：并发第二个实例立刻以非 0 退出，而不是排队挂住
```

本机实测 `flock -n` 的第二次获取退出码为 **1**（因为 `-n` 是非阻塞模式，所以它不挂住），且锁随进程退出立即释放——这正是"防止两批变更互相踩"需要的语义。

## 3. 脚本的四件套与退出码的语言

### 3.1 四件套

批量脚本至少要有四样东西，因为缺一样就会在某个特定场景下出问题：

| 件 | 写法 | 防的是 |
| --- | --- | --- |
| 出错即停 | `set -euo pipefail` | 中间一步失败后脚本继续往下做，于是留下半成品 |
| 清理 | `trap 'cleanup' EXIT` | 异常退出时留下临时文件、临时挂载、临时账号 |
| 限时 | `timeout <秒> <命令>` | 某一步永远不返回，于是整批停在那里 |
| 显式退出码 | `exit 0` / `exit 1` | 最后一条命令的退出码被当成脚本的退出码 |

`set -euo pipefail` 三个开关的含义常被说错，因此需要逐条写清：

- `-e` 让命令失败（非 0 退出）时立即退出脚本；
- `-u` 让使用**未设置**的变量时报错退出。**注意它不拦空值**——本机实测 `T=""; [ $T = x ]` 的退出码是 0，即空值不报错。因此要拦空值必须用 `${VAR:?}`（本机实测退出码 127）；
- `-o pipefail` 让管道中任意一环失败时整个管道就算失败。本机实测 `false | true` 在默认模式下退出码为 0、加 `pipefail` 后为 1——**这是"上游命令失败了但下游成功了，脚本却以为成功"的经典来源**。

### 3.2 退出码是批量里唯一机器可读的信号

批量场景下没人逐台看输出，所以**退出码就是全部**。几个必须记住的值（本机实测，bash 5.2.21）：

| 退出码 | 含义 | 处理方式 |
| --- | --- | --- |
| 0 | 它表示命令执行成功 | 直接继续，因为这一台不需要处置 |
| 1 | 它表示命令自身失败，也包含一般性错误 | 停批，因为此时无法区分是个体故障还是脚本缺陷 |
| 2 | 它表示用法错误，也就是参数写错 | 停批并修脚本，因为参数错误会在每一台上重复出现 |
| 124 | 它表示 `timeout` 到期杀掉了命令 | **单独归类**：因为这一台可能只是慢，所以重试一次再判断 |
| 126 / 127 | 它表示命令不可执行（126）或命令不存在（127） | 停批，因为这类退出码多半是环境问题（`PATH` 或依赖） |
| 137 | 它表示进程被 `SIGKILL` 杀掉，常见于 OOM 或超时升级 | 停批并查看内核日志，因为进程不是自己退出的 |
| 123 | 它表示 `xargs` 的子任务失败 | 此时只知道"有失败"，**不知道是哪一台** |

最后一行是批量运维里最容易踩的坑：`xargs -P 4` 跑一批命令，只要有一个子任务失败，整体退出码就是 **123**，而失败的那一台的输出混在并发输出里。所以 `xargs` 适合"结果不重要、只需知道有没有失败"的场合；因为需要定位到台数时必须拿到主机名，所以得让每一台自己写一份带主机名的结果文件。

## 4. 并发与分批：收益上限与代价

并发不是免费的。它换来的是总耗时，付出的是**可定位性**。

本机实测的一组对照（每次 reload 固定耗时 1 秒，共 5 次，环境：Ubuntu 24.04.5 LTS / 内核 `6.8.0-139-generic` / 4 vCPU / systemd 255 / bash 5.2.21）：

```text
# 数值仅示意、不代表你的机器
这一组实测中，串行执行的总耗时为 5100 ms，并发度为 4 的 xargs 执行的总耗时为 2058 ms。
两次执行都在标准输出上留下 5 行 `is-active=active`。
```

三点判读：

- 并发的收益上限由所需批次数 `⌈N / 并发度⌉` 决定，因为同一批之内的机器是同时被改的；5 台机器按 4 并发大致落在 2 个批次，实测 2058 ms 与这个估算吻合（每次 1 秒 + 调度与连接开销）；
- **并发带来的最大代价是可定位性**：并发跑出来的 5 行 `is-active=active` 完全一样，因此事后无法判断哪一台是哪一次、有没有失败过。所以并发度越高，越需要**让每一台自己留下带主机名与时间戳的证据**；
- 并发度不是"越大越快"：它受目标机的 `sshd` 承受能力、控制端的进程与连接上限、以及下游共享依赖（同一台数据库、同一个 API）的容量约束。**先量一次单台耗时与目标侧上限，再反推并发度**。

挑选并发度的算式是反推出来的：

```text
# 模板，数值仅示意
若可接受窗口是 10 分钟、单台耗时 30 秒，则最多可分 ⌈600/30⌉ = 20 批。
若并发度取 4，则总耗时约为 20/4 × 30 秒 = 150 秒，剩余时间留给观察与验收。
```

### 4.1 分批的依据是故障域，不是台数

"每批 10 台"这样的规则只在同构集群里成立。真正要问的是：**这一批下线之后，剩余容量还够不够承接流量？**

固定算式是 `批次 ≤ 总容量 − 最小可接受容量`。其中"最小可接受容量"通常取峰值的一倍多（经验区间 1.2~1.5 倍），因为它对应的是 N+1（容忍 1 台不可用）或 N+2（容忍 1 台故障加 1 台维护）的余量要求。完整讨论见《原理：故障域与检测的赌注》。

`serial` 这类参数只控制"同时被改的台数"，**不控制剩余负载**。若集群有 4 台实例、单机峰值利用率为 70%，则下线 1 台之后剩下 3 台各约 133%，因此这已经注定失败，与 `serial: 1` 无关。

## 5. 执行方式的演进路径

从手工到自动化是三个台阶，每一级解决不同的问题（新工具不是新方案，只是新载体），因为同一套判断换到另一个载体上仍然要重新落实：

| 方式 | 适用 | 它解决的问题 | 它带来的新问题 |
| --- | --- | --- | --- |
| 手工逐台 | 有状态服务、第一次做、需要建立样例 | 因为每一步的输出都在眼前，所以能看清每一步的真实输出 | 不可重复，容易被记忆误差漏掉几台 |
| 批量脚本（`for`/`while`/`xargs`） | 无状态、步骤固定、可复用 | 因为执行过程可重放，所以可重复、可留日志 | 需要自己实现超时、并发、幂等、锁 |
| 配置管理工具（Ansible 一类） | 需要幂等、需要审计、需要长期维护 | 因为它自带幂等模块，所以提供 `--check` 预演、`--limit` 限定范围、`serial` 分批、`changed` 可判定 | 需要维护 inventory 与角色；`shell`/`command` 这两类模块会绕过幂等 |

三个必须记住的边界：

- **能用模块就不要用 `shell`/`command`。** 后两者是逃生门，因为它们不判断状态、每次都算改动，所以用多了等于把脚本搬进了 playbook；
- **只读命令要显式声明"不产生改动"**（例如 `changed_when: false`），否则"有没有改动"这个最关键的信号就失效了，因为此时每一台都会报出改动；
- **预演顺序固定**：先跑 `--check` 看会改什么，再跑 `--diff` 看具体改哪一行，然后用 `--limit` 先在一台上做，最后用 `serial` 分批推进。**跳过 `--check` 直接全量，等于放弃了这次变更唯一的对照组。**

### 5.1 改网络与认证之前先确认"你还进得去"

有一类批量变更的风险与影响面无关，而在于**它会切断你自己的退路**：改 `sshd_config`、改防火墙规则、改 PAM 或 sudoers、改网卡与路由。它们的共同点是——**一旦改错，你就连不上去修了**。

固定纪律：动这几类东西之前，先确认**带外通道**（IPMI/iDRAC/iLO、虚拟化平台控制台、云厂商的 VNC 控制台）可用，并且这条通道的凭据不在被改的这台机器上（因为凭据放在被改的机器上时，改坏它就连取凭据的路径一起断了，放在故障之外的做法见《体系：一次中断与恢复的一生》）。批量改 `sshd_config` 时还要多一道本地校验：每改一台就先跑一次语法检查（`sshd -t`），失败即停。

## 常见误解

| 说法 | 事实 |
| --- | --- |
| "这条命令我在自己机器上跑过，没问题" | 手工能跑与批量能跑是两件事，因为非交互 shell 不读 dotfiles，所以 `PATH` 与别名都不同 |
| "加上 `set -e` 就万无一失了" | `-e` 不拦空值（本机实测 `T=""; [ $T = x ]` 退出码为 0），也不拦管道里上游失败（要 `-o pipefail`） |
| "退出码 0 就说明都成功了" | 在 `xargs` 场景下，整体退出码是 123，它只说明"有子任务失败"；同时，某些命令即使没做成也返回 0（如权限被拒后仍继续） |
| "并发开大点，快" | 并发买的是时间，卖的是可定位性；因为同一批 5 行输出相同，所以事后无法归因到台 |
| "`serial: 1` 就一定安全" | 它只控制同时被改的台数，不控制剩余负载。因为 4 台实例下线 1 台后剩 3 台各 133%，所以照样会垮 |
| "脚本不是幂等的，失败后再跑一遍就好了" | 非幂等脚本重跑会留下重复行与半成品；因为重复的配置项通常只有第一条生效，所以"看起来改了" |
| "先全量推，有问题再回滚" | 全量推丢掉了唯一的对照组，因此出问题时你无法区分"是这次改动"还是"本来就有" |
| "配置管理工具都幂等" | `shell`/`command` 模块不幂等，因为它们每次都被算作改动 |
| "改 `sshd_config` 用批量最省事" | 这类变更会切断你的退路。必须确认带外通道可用、逐台做语法检查之后才能动 |

**第一反应不要做什么**：不要在批量脚本里依赖远端的 `PATH`、别名与交互式配置；不要在没做语法检查、没确认带外通道的情况下批量改认证与网络配置；不要用"再跑一遍"处理非幂等脚本；不要用全量并发替代分批；不要只看整体退出码就宣布成功。

## 要点自测

**问：为什么"手工能跑"不等于"批量能跑"？**
答：因为批量拿掉了三个默认：人在看输出、交互式环境、立即知道失败。因此非交互 shell 不读 `.bashrc`（所以 `PATH`、别名、变量都不同）、失败只剩退出码、连接与并发被放大 N 倍。

**问：幂等与可重入分别保证什么？各用什么手段实现？**
答：幂等保证重复执行结果相同，因为实现方式都是先判断后动作（`grep` 匹配、比校验和、`mkdir -p`、幂等模块）；可重入保证中断后再跑安全，因为每一步都能被独立判断，并且用 `trap` 清理中间产物、用 `flock` 防止两批同时改。

**问：`set -euo pipefail` 三个开关各拦什么？有一个它拦不住的是什么？**
答：`-e` 拦命令失败，`-u` 拦未设置的变量，`-o pipefail` 拦管道中上游失败。`-u` **不拦空值**——本机实测 `T=""; [ $T = x ]` 退出码仍是 0，因此要用 `${VAR:?}` 才能拦。

**问：本机实测串行 5100 ms、并发 4 路 2058 ms，为什么还要谨慎提高并发？**
答：因为并发买的是时间、卖的是可定位性。两次执行的输出都是 5 行相同的 `is-active=active`，所以事后无法判断哪台失败过；同时并发度还受目标 `sshd`、控制端进程上限与下游共享依赖容量的约束。

**问：`xargs -P` 的退出码 123 意味着什么？该怎么补救？**
答：它只意味着"有子任务失败"，不告诉你哪一台。因为并发输出里没有主机名，所以补救办法是让每一台自己写一份带主机名与时间戳的结果文件，事后按文件核对。

**问：为什么分批大小不能按"每批 10 台"来定？**
答：因为分批的依据是剩余容量：`批次 ≤ 总容量 − 最小可接受容量`，而最小可接受容量由峰值与 N+1/N+2 余量决定。若集群有 4 台实例、峰值 70%，则下线 1 台后剩余各 133%，因此无论 `serial` 设多少都不该执行。

**第一反应不要做什么**：不要把 `--check` 省掉；不要在会切断退路的变更上跳过带外通道确认；不要用"再跑一遍"当失败处理策略；不要只凭退出码 0 就宣布批量成功。
