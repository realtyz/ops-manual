# 一次生产变更的一生

一次生产变更可以拆成五个站点，从"要不要做、谁批准"到"下次怎么更快"，中间不换话题：**立项与评审 → 准备与预演 → 执行与分批推进 → 验证与守候 → 收口与沉淀**。

每一站的准入门槛是上一站的产出。**没有六要素就没有可执行的方案，没有备份与回滚就没有动手的资格，没有验收判据就无法决定"继续还是回滚"**——顺序错了，工具再全也只是在赌运气。

这条线与前面几章的区别在于：**前面几章的对象是机器上的东西（启动链、进程、内存、磁盘、连接），这一章的对象是你自己要做的事。** 所以贯穿始终的不是某个字段，而是同一个三问：

1. **这一步可逆吗？**（可逆的可以放手做，不可逆的必须先有退路）
2. **我怎么知道它成功了？**（判据必须在动手之前写出来）
3. **如果失败，下一步是谁做什么？**（回滚动作、执行人、回滚后的验收、何时向上通报）

## 一、立项与评审：把"要改什么"变成一个可执行的句子

### 1.1 这一站在回答什么

**要改什么？影响面多大？谁批准？什么时间做？** 产出是一份定级的变更单。

### 1.2 变更单的六要素

六个格子缺一不可。前三个决定"能不能做"，后三个决定"做完怎么算完"：

| 要素 | 要写到什么程度 | 最容易漏的地方 |
| --- | --- | --- |
| 目标 | 一句话说清改完之后的可观察状态 | 写成动作（"重启服务"）而不是目标（"新配置生效且错误率回到基线"） |
| 范围 | 哪些机器、哪些服务、哪些集群；**以及不改什么** | 不写"不改什么"，执行时就会顺手多改 |
| 备份 | 备份什么、放在哪、怎么确认可用 | 只写"已备份"，不写路径与校验方式 |
| 回滚 | 回滚命令 **加触发条件** 加预计耗时 | 只写命令不写触发条件，等于把决定权留到慌乱的那一刻 |
| 验证 | 通过什么判据、由谁验收 | 只写"观察一下"，没量化 |
| 窗口 | 开始与结束时间，以及"到点没做完怎么办" | 不约定到点后的动作，于是变更会"顺延" |

三处隐藏考点，评审时逐条对照：

- **范围必须写"不改什么"。** 一次变更多改了一个变量，事后就无法归因。
- **回滚必须写成可判定的触发条件**，固定三件：**指标 + 阈值 + 持续时间**（例如"错误率 > 1% 持续 5 分钟"）。写"如果出问题就回滚"不是触发条件，因为"出问题"由谁在什么时刻判定没有约定。
- **验证必须写"怎么做"**，而不是"看是否正常"。

### 1.3 评审会必答四问

| 问题 | 答不出来的后果 |
| --- | --- |
| 影响面多大？ | 分级会定错，通知范围会漏人 |
| 最坏结果是什么？ | 没有为最坏情况准备退路 |
| 怎么退回去？要多久？ | 回滚方案只存在于想象里 |
| 执行时谁有权喊停？ | 出事时所有人都在等别人决定 |

**答不出任何一问，就应该改期，而不是"先做起来看看"。**

### 1.4 分级、窗口与冻结期

分级只决定审批层级、通知范围和执行时间，**不决定技术方案**（判据见《原理：不可逆性与影响面》）。窗口的算法是减出来的：

```text
# 模板，数值仅示意
窗口 = 业务低峰时段 − 其它已排期变更 − 周期任务时段 − 留给回滚与验收的时间
```

三个必须改期的信号：**窗口内找不到能做回滚决策的人**、**备份没有验证过**、**同一时段另有变更**。冻结期通常只放两类事：止损与安全修复。

### 1.5 字段读法：怎么知道窗口里有没有撞车

| 字段 / 命令 | 是什么 / 单位 | 判据 | 与谁同看 | 看到它转向哪一步 |
| --- | --- | --- | --- | --- |
| `systemctl list-timers --all` 的 `NEXT`/`LEFT` | 定时任务下次触发时刻与剩余时间（秒/分） | **`NEXT` 落在你的窗口内，就是撞车**；`LEFT` 小于你的变更耗时更是 | 变更窗口 | 撞车 → 调窗口或临时停该 timer |
| `systemctl list-timers` 的 `LAST` | 上次触发时刻 | 用于判断该任务的实际周期与耗时 | 任务日志 | 周期任务会占资源 → 避开 |
| `systemctl show <unit> -p UnitFileState` | 开机自启状态（`enabled`/`disabled`/`static`） | `ActiveState=active` **不等于**开机自启 | `ActiveState` | 变更涉及重启 → 先确认重启后它还会起来 |
| `systemctl show <unit> -p NRestarts` | 本次启动以来的重启次数（个，累计） | 非 0 且增长 = 服务在崩溃重启循环 | `SubState` | 非 0 → 先查为什么在重启，别叠加变更 |
| `systemctl show <unit> -p FragmentPath` | unit 文件来自哪里（路径） | `/usr/lib/systemd/system/` 下的文件是发行版提供的，直接改它会在升级时被覆盖 | 本地 drop-in 目录 | 是发行版文件 → 改用 drop-in |
| `systemctl list-dependencies <unit>`（可加 `--reverse`） | unit 的正向/反向依赖 | 反向依赖告诉你"停了它会连带停谁" | 服务台账 | 有反向依赖 → 排进分批计划 |

本机一份实测快照（环境：Ubuntu 24.04.5 LTS / 内核 `6.8.0-139-generic` / systemd 255 / root，2026-09-19T08:07:34+00:00）：

```text
# 数值仅示意、不代表你的机器
$ systemctl list-timers --all | head -3
NEXT                         LEFT       LAST                         UNIT
Sat 2026-09-19 08:10:00 UTC  2min 25s   Sat 2026-09-19 08:00:12 UTC  sysstat-collect.timer
Sat 2026-09-19 09:25:48 UTC  1h 18min   Fri 2026-09-18 09:25:48 UTC  fwupd-refresh.timer

$ systemctl show ssh -p Id -p ActiveState -p SubState -p MainPID -p NRestarts -p UnitFileState -p FragmentPath
Id=ssh.service
ActiveState=active
SubState=running
MainPID=1348
NRestarts=0
UnitFileState=disabled
FragmentPath=/usr/lib/systemd/system/ssh.service
```

判读：`sysstat-collect.timer` 的 `NEXT` 距采集时刻只有 2 分 25 秒——**如果变更窗口是 08:08 开始，它就撞上了**，而这个采集任务正是你事后复盘时要用的历史数据来源。`ssh.service` 是 `active` 但 `UnitFileState=disabled`（它由 `ssh.socket` 拉起），**只看 `is-active` 会以为"重启后它自己会起来"**。

### 1.6 这一站的产出长什么样

一份定级的变更单：六要素齐全、范围写了"不改什么"、回滚写了可判定的触发条件与预计耗时、窗口里没有撞车的定时任务与其它变更、评审四问都有答案。**判定它合格的办法很直接：交给一个没参与的人，他能照着执行、照着重放。**

## 二、准备与预演：动手前把退路铺好

### 2.1 这一站在回答什么

**备份在哪？回滚命令是什么？怎么分批？怎么验收？** 产出是备份、回滚方案、灰度计划与验收标准。

### 2.2 三类备份对象与三条合格线

| 对象 | 例子 | 备份方式 |
| --- | --- | --- |
| 配置文件 | `/etc` 下本次涉及的文件、服务的 drop-in | `cp -a` 到带时间戳的目录（保留权限与属主） |
| 数据 | 数据目录、数据库、上传内容 | 按应用的一致性原则做（见《原理：可恢复性的语言》） |
| 系统状态 | 运行中的服务、监听端口、挂载、关键参数值、启停清单 | **采集，不是复制**——状态无法"复制回去"，只能记录后手工重放 |

三条合格线：

1. **唯一的名字**：备份路径带时间戳（例如 `2026-09-19-080734`），不要用 `xxx.bak` 这种每次都会被覆盖的名字；
2. **不在被改动的路径内**：备份要放在本次动作不会触碰的目录里，否则改错时会把备份一起改掉；
3. **能 `diff` 与恢复验证**：`diff -r` 的判据是**输出为空且退出码为 0**（有差异时退出码是 1，所以不能写"没报错"就算一致）。

状态快照要采的五组：运行中的服务列表、监听端口、挂载与文件系统、本次涉及的关键参数值、开机自启清单。本机实测的一份状态快照有 109 行，当时运行中的 service 单元 24 个。

### 2.3 回滚的四种形态与两种假回滚

| 形态 | 粒度 | 典型耗时量级 | 备注 |
| --- | --- | --- | --- |
| 配置回滚 | 换回文件并 reload | 秒级 | 最优先使用 |
| 版本回滚 | 切回上一个发布版本 | 分钟级 | 需要有版本留档 |
| 服务回滚 | 启停、切主从 | 分钟级 | 会断连接，要配合摘流量 |
| 数据回滚 | 从备份或快照恢复数据 | 小时级，且可能丢数据 | **能用配置回滚就不要用数据回滚** |

两种假回滚：

- **重启服务**：进程重启了，但配置与数据都没有回到过去；
- **换回文件但不 reload**：进程仍持有旧配置，运行时值也没变。

**结论是固定的：回滚必须同时撤"持久化文件"与"运行时值"。** 只做一半，就会出现"文件是旧的、行为是新的"或反过来。

回滚命令必须在实验机上跑过并记下耗时。本机实测（改 `vm.swappiness` 从 60 到 10 再改回）：

```bash
cp -a /etc/sysctl.d/99-lab.conf /tmp/rollback/99-lab.conf.$(date +%F-%H%M%S)
                                                  # 验证：备份带时间戳、在改动路径之外
sysctl -w vm.swappiness=10                        # 变更
sysctl -n vm.swappiness                           # 验证：运行时值（不 cat 配置文件）
cp -a /tmp/rollback/99-lab.conf.<stamp> /etc/sysctl.d/99-lab.conf && sysctl -p /etc/sysctl.d/99-lab.conf
                                                  # 回滚：只应用这一个文件，不用 --system
sysctl -n vm.swappiness                           # 验证：回滚后的运行时值
```

```text
# 数值仅示意、不代表你的机器
apply_ms = 3
rollback_ms = 4
```

**这两个数字才是"回滚方案"的证据。** 它们也解释了为什么回滚要用 `sysctl -p <单文件>` 而不是 `sysctl --system`：后者会把系统上所有配置文件重新应用一遍，从而覆盖掉别人尚未落盘的临时改动——**回滚动作本身变成了第二次变更**。

### 2.4 灰度计划：依据是故障域，不是台数

分四个维度设计，通常同时用两个：

| 维度 | 例子 | 适合的场景 |
| --- | --- | --- |
| 实例 | 先 1 台，再 10%，再全量 | 无状态服务 |
| 故障域 | 先一个机架 / 一个可用区 | 需要验证依赖与网络路径 |
| 流量 | 按比例或按用户分桶 | 有灰度通道的接入层 |
| 租户 | 先内部租户，再小客户，再全量 | 多租户系统 |

两个必须算出来的数：

```text
# 模板，数值仅示意
批次大小 ≤ 总容量 − 最小可接受容量
观察时间 ≥ max(一个业务周期, 一个监控评估周期, 2~3 个采样间隔)
```

**灰度的本质是给自己留一个对照组。** 所以除了"改多少"，还要定义"跟谁比"：没改的那部分实例就是对照组，它的指标是判断"是不是这次变更造成的"的唯一依据。

有一类变更是没有分批余地的：**全局配置**（DNS、网关、统一鉴权）。它们对所有客户端同时生效，所以按不可逆动作对待——先预演、缩短 TTL、再切换，并且准备好"切回去也要等 TTL"的时间预算。

### 2.5 变更前检查清单（13 项）

逐条打勾，任何一项空着都不开始：

1. 六要素齐全、已定级、已批准；
2. 对象清单**从台账生成**，不是从记忆里写；
3. 配置备份带时间戳、不在被改路径内；
4. 数据备份已包含一致性处理（或明确记录"本次不涉及数据"）；
5. 状态快照已采（服务、端口、挂载、参数、启停清单）；
6. 回滚命令已在实验机上跑过，并记下耗时；
7. 回滚触发条件已写成"指标 + 阈值 + 持续时间"；
8. 验收判据已写明（单机 / 集群 / 业务三层，见第四站）；
9. 改动前的基线已采（同一组指标、同一口径）；
10. 分批计划已定（批次大小与批数来自容量算式）；
11. 窗口与"到点没做完"的处置已约定；
12. 通知已发出，包含值班与相关方；
13. **第二个人有能力执行回滚**。

第 13 项最容易被省掉，也最贵：它同时是"回滚方案可用"与"知识不在一个人手里"两项要求的检验。

## 三、执行与分批推进：每一步都可观察、可停止、可回退

### 3.1 这一站在回答什么

**现在到第几批？这一步的预期是什么？实际是什么？** 产出是逐批的执行记录，含同时刻证据。

### 3.2 固定顺序

**摘流量（如需要）→ 改 → 单机验证 → 放回流量 → 观察。**

单机验证的内部顺序也是固定的：**状态 → 日志 → 请求**。先打请求会把"服务没起来导致的拒连"误判成网络问题，也会把"配置没生效但返回 200"误判为成功。

要不要摘流量，按三个条件判断：服务**有状态**、接入层**没有健康检查**、动作**会断掉存量连接**——满足任一条就要摘。无状态且接入层有健康检查的服务，可以靠排空机制自然完成。摘流量的验收判据是**从外部探失败、从本机探成功**。

### 3.3 批次决策点的四种选择

每一批结束都要明确选一个，并写进记录：

| 选择 | 判据 |
| --- | --- |
| 继续 | 本批指标与验收判据全部满足，且与对照组相比无异常 |
| 扩批 | 同上，且观察时间已覆盖一个业务周期 |
| 暂停 | "轻微劣化但在阈值内"、或"现象无法解释但服务还活着" → **暂停并保留现场**，观察一个完整周期 |
| 回滚 | 命中变更单上写好的触发条件 → **立即执行，不再讨论** |

**"解释不了但服务还活着"一律归为暂停。** 这一类最值得写进复盘，因为它说明你的判据有盲区。

### 3.4 字段读法：怎么确认"这一步真的生效了"

| 字段 / 命令 | 是什么 / 单位 | 判据 | 与谁同看 | 看到它转向哪一步 |
| --- | --- | --- | --- | --- |
| `systemctl show <unit> -p ActiveState -p SubState -p NRestarts` | 单元状态 / 子状态 / 重启次数（累计） | 三个一起看：只看 `ActiveState=active` 会漏掉 `SubState=auto-restart` 的崩溃循环 | 单元日志 | `NRestarts` 增长 → 停批查原因 |
| 运行时值（`sysctl -n <key>`、`cat /proc/...`） | 当前生效值 | **验收一律用运行时口径**，不 `cat` 配置文件 | 配置文件内容 | 两者不一致 → 配置没被加载 |
| `ss -lnt` 的 `Recv-Q` | 监听套接字上"已完成握手但未被 `accept`"的连接数（个） | 持续接近队列上限（`Send-Q`）说明应用 accept 不及时 | `nstat` 的 `TcpExtListenOverflows` | 溢出 → 转应用侧或调队列 |
| `/proc/<pid>/limits` 的 open files | 进程句柄软限 / 硬限（个） | 使用量贴近软限即危险 | `ls /proc/<pid>/fd | wc -l` | 贴限 → 先提上限止血，再查泄漏 |
| 退出码 | `timeout` 超时为 **124**；命令自身失败为 1；`SIGKILL` 为 137 | 124 单独归类，这一台可能只是慢 | 命令输出 | 非 0 且非 124 → 停批 |

本机实测的一组执行期数据（环境同上，每次 reload 固定 1 秒）：

```text
# 数值仅示意、不代表你的机器
串行 5 次：        serial_ms = 5100
xargs -P 4：       parallel_ms = 2058
两次输出均为 5 行 is-active=active
timeout 2 sleep 5 → 124
timeout 30 true   → 0
```

判读：并发的收益与 `⌈N/并发度⌉` 吻合，但**两次执行的输出完全相同**——并发买的是时间，卖的是可定位性。所以并发执行时，必须让每一台自己落一份带主机名与时间戳的证据。

### 3.5 日志与证据：先剔除别人的噪声

执行期要抓的证据是"同一时刻的：状态 + 日志 + 请求"。这里有一个高频陷阱：**不限定单元的日志过滤会把同机其它服务的报错算进来。** 本机实测：

```text
# 数值仅示意、不代表你的机器
$ journalctl -u ssh --since "10 min ago" | grep -icE 'error|fail'
0
$ journalctl --since "10 min ago" | grep -icE 'error|fail'
93
```

同一个窗口、同一台机器，**限定单元是 0 条，不限定是 93 条**——93 条几乎全部来自共用机器上其它实验的服务。**判据是"日志基线必须先剔除他人与周期性噪声"**：先用变更前的一段窗口采一份基线，变更后再采一份，比的是同一个单元、同一个关键词、同一个时长。

### 3.6 执行记录的最小格式

| 批次 | 对象 | 开始 | 结束 | 改前值 | 改后值 | 命令输出摘要 | 结论 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | web-01 | 22:03 | 22:05 | `v1` | `v2` | `active/running/NRestarts=0` | 继续 |
| 2 | web-02..05 | 22:07 | 22:11 | `v1` | `v2` | 4/4 `active` | 扩批 |

同时要留异常记录（时间 / 现象 / 原始输出 / 判断 / 动作），以及"实际耗时 vs 计划耗时"。这份记录是第五站归档的主体。

## 四、验证与守候：判据决定一切

### 4.1 这一站在回答什么

**改对了吗？业务正常吗？什么时候可以宣布成功或回滚？** 产出是一份验收记录。

### 4.2 三层验收

| 层 | 验什么 | 判据 |
| --- | --- | --- |
| 单机 | 运行时值 / 状态 / 无新增报错 / 本机探活 | `sysctl -n`、`systemctl show` 的三个字段、`journalctl -u` 无新增 error |
| 集群 | 可用实例数 / 容量水位 / 无新增单点 | `ss -s` 的状态分布、`systemctl --failed`、后端列表 |
| 业务 | 真实业务路径的 p99 / 错误率 / QPS | 与变更前基线和对照组比 |

**三层是递进的**：单机不过就不看后两层；**单机全过仍然必须看后两层**——本机实测的目标 `TcpExtListenOverflows` 从 0 涨到 10 的那段时间里，探活一直返回 200，说明"端口在听、接口能答"完全不足以证明业务可用。

### 4.3 一个能区分"重读配置"与"重启进程"的字段

`systemctl show <unit> -p ExecMainStartTimestamp` 给的是**主进程何时开始运行**：

- 变更后它应该是**新的时间戳**（进程被重启了）；
- 如果它没变，说明这次 reload 只是让进程重读了配置，主进程没有换——**只看 `ActiveState` 分不出这两种情况**，而它们的风险完全不同（重读配置不会清掉内存里的状态与连接）。

本机基线：`ExecMainStartTimestamp=Sat 2026-09-19 07:20:10 UTC`、`MainPID=1348`、`NRestarts=0`。

### 4.4 观察窗口与检查点

窗口长度不小于 `max(一个业务周期, 2~3 个采样间隔, 一次关键定时任务的执行周期)`。按问题的形态定采样：

| 形态 | 采样要求 |
| --- | --- |
| 立即暴露（几分钟内） | 秒级采样，看窗口内有没有抬头 |
| 压力相关（高峰期才出现） | 必须覆盖业务高峰，或做一次受控压测 |
| 周期相关（按小时/按天） | 至少覆盖 2~3 个完整周期；**跨零点的变更最危险**，因为按天分割的历史数据会在零点断开 |

四个检查点：**T+1**（单机）、**T+5**（集群与业务）、**T+15**（新增告警与日志）、**窗口结束**（宣布成功或回滚）。每个检查点都要留同一组证据。

查历史的口径有一个硬要求：`sar -f` 输出的每一行是**采集间隔内的平均值**（默认间隔 10 分钟），拿它跟 1 秒采样的实时数据比是不可比的。本机实测 `sar -u -f /var/log/sysstat/sa19` 的 `Average: 0.37 0.19 99.44` 与 `sar -u 1 3` 的 `Average: 0.25 0.42 99.33` 看着接近，但**它们回答的是不同粒度的问题**。

### 4.5 回滚触发线

固定写成三件：**指标 + 阈值 + 持续时间**。

```text
# 模板，数值仅示意
错误率 > 1%  持续 5 分钟        → 回滚
p99 > 基线 1.5 倍 持续 10 分钟  → 回滚
探活连续 3 次失败 或 成功率 < 99% → 回滚
```

三条纪律：**命中即执行，不在现场重新讨论**；**回滚本身也要验收**（运行时值回旧 + 服务 active + 业务探活 + 窗口内指标回基线）；**没命中但有存疑信号时，暂停扩批并记录，而不是"再看看"拖过窗口**。

### 4.6 四种假成功

| 现象 | 为什么不是成功 |
| --- | --- |
| 重启后恢复正常 | 现场被清掉，问题只是被推迟 |
| 没有告警 | 阈值不对，或数据根本没采到 |
| 单机探活全通过 | 探活路径与用户路径不同；集群与业务两层没看 |
| 跟以前一样 | 没有量化、没有对照，只是"没观察到变化" |

## 五、收口与沉淀：把一次变更变成组织资产

### 5.1 这一站在回答什么

**记录归档了吗？台账更新了吗？Runbook 改了吗？下次怎么更快？**

### 5.2 收口四件事

**归档记录 / 更新台账与文档 / 闭环改进项 / 沉淀 Runbook。** 最容易跳过的正是第二、三件——它们当下没有成就感，代价在几个月后出现。

归档内容至少三部分：**改前状态 + 改后状态 + 变更窗口日志**。只留改前，半年后就看不到"改成了什么、为什么"；只留改后，就看不到当时从哪儿出发。

归档的三道验收（本机实测）：

```text
# 数值仅示意、不代表你的机器
config-after/ 三个文件：314 / 255 / 1124 字节（合计 1693）
journal-window.log：207019 字节 / 2184 行
目录 du -sh：224K → tar czf 后 22195 字节
tar tzf 列出 6 项；rsync -a + diff -r 退出码 0
sha256sum：3550eec889ca5d803bf055179e458690a2f4838fb614adf691ba491f1cef0093
```

三点读法：**归档体积几乎全被日志占**（1693 字节配置 vs 207019 字节日志），所以归档的容量预算要按日志估；**压缩牺牲了"能直接打开看"**，应急取证包建议同时留一份未压缩目录；**校验要留一个可复算的值**（这里是 `sha256sum`），否则半年后没人能证明这份归档没被动过。

### 5.3 复盘的六段

时间线（精确到分钟）/ 影响面（谁受影响、多久、数据有没有损失）/ 证据 / 根因（直接原因 **加上** 为什么没被提前发现）/ 止损动作（为什么选它、重来会不会换）/ 改进项（带 owner 与期限，并回答"为什么之前的防线没拦住它"）。

三条无指责要点：**描述行为不评价人**（"第 3 批漏改 7 台"而不是"执行人粗心"）；**追问系统为什么允许这个错误发生**；**行动项必须有验收方式**。一句话记住：**"根因是人为失误"不算根因**——人是常量，能被系统吸收的失误才是好设计。

复盘触发三条：**发生了回滚**、**影响了业务**（哪怕只是短抖动）、**出现了"解释不了但过去了"的现象**（最值得写的一条）。

### 5.4 改进项：从形容词到句子

合格的改进项长这样：**有动作、有 owner、有期限、有验收方式。** 三种去向：

1. **立即修**（本次窗口内或次日）；
2. **排期**（进入下一个迭代，有排期记录）；
3. **显式接受风险**（写明批准人）——这一种最容易被忽略，但**接受风险也是一个决定**，不写下来就等于"没人决定"。

### 5.5 字段读法：失败单元的收口

| 字段 / 命令 | 是什么 | 判据 | 与谁同看 | 转向哪一步 |
| --- | --- | --- | --- | --- |
| `systemctl --failed` | 当前失败的单元列表 | 非空要先判断"是不是本次变更的产物" | `FragmentPath`、`journalctl -u` 的时间戳 | 是本次的 → 清理并记录；不是 → 找 owner |
| `systemctl show <unit> -p FragmentPath` | 单元文件来源路径 | 路径能反推它是谁部署的（本地 vs 发行版） | 变更清单 | 决定清理还是交接 |
| `journalctl -u <unit>` 的时间戳 | 该单元报错发生的时刻 | 与变更窗口比对，判断因果 | 变更记录 | 窗口内 → 本次产物 |

纪律：**判断失败单元是不是本次的产物之后才动手，且不要顺手 `systemctl reset-failed`**——那会抹掉别人尚未取证的现场。

### 5.6 度量：五个数，一起看

**变更成功率、回滚率、变更引起的故障占比、MTTR / MTTD、改进项按期完成率。** 它们的用法是**找瓶颈，不是考核个人**，而且必须几个数一起看：

- 只盯回滚率，团队会变得不敢做变更（该做的也不做了）；
- 只看 MTTR，会忽略"发现得太晚"这一半。

## 六、横切线

五站是时间线，但有几件事横穿多站。串不起来的原因，通常是没抓住下面几条线。

### 6.1 可逆性线

只读 / 可回滚 / 不可逆三档是第一分类标准；任何一步只要不可逆，就必须先有退路。完整讨论见《原理：不可逆性与影响面》，回滚形态与耗时见本篇第二站。

### 6.2 时间预算线

RTO 与 RPO 是约束，MTTR 与 MTTD 是度量；回滚耗时必须小于业务容忍的中断时间。完整讨论见《原理：可恢复性的语言》。

### 6.3 幂等与批量线

批量执行的每一步都要能重跑；非幂等脚本禁止"再跑一遍"。完整讨论见《原理：幂等与可重入的批量执行》。

### 6.4 故障域与余量线

分批大小由剩余容量决定，不由台数决定；冗余必须跨故障域放置。完整讨论见《原理：故障域与检测的赌注》。

### 6.5 台账线

对象清单从台账生成，不靠记忆；收口时台账必须更新（否则下一次变更的输入是旧的）。台账字段见《治理：生产运维与变更治理》。

### 6.6 一条不是机制而是纪律的线：一次只改一个变量

回滚与调参同时做、限流与扩容同时做，事后永远无法归因。这条纪律不贯穿某一层，而是每一站都要练。

## 常见坑

| 做法或说法 | 后果或事实 |
| --- | --- |
| 变更单写"观察一下" | 没有验收判据，就无法决定继续还是回滚 |
| 回滚只写命令，不写触发条件 | 决定权被推到最慌乱的那一刻，且通常由最没信息的人做 |
| 备份用 `xxx.bak` 这种固定名字 | 二次执行会覆盖第一次的退路 |
| 回滚只改文件不 reload | 进程仍持旧配置，运行时值也不变；"文件是旧的、行为是新的" |
| 用 `sysctl --system` 做单文件回滚 | 会把系统上所有配置重新应用一遍，覆盖别人尚未落盘的临时改动 |
| 用 `is-active` 判断服务健康 | `active` 也可能是自动重启循环；要看 `SubState` 与 `NRestarts` |
| 用配置文件的运行时间判断重启 | 只看 `ActiveState` 分不出"重读配置"与"重启进程"，要看 `ExecMainStartTimestamp` |
| 日志不限定单元就下结论 | 本机实测同窗口：限定 `ssh` 是 0 条，不限定是 93 条 |
| 用并发替代分批 | 并发买的是时间，卖的是可定位性；两次运行的输出可能完全相同 |
| 变更跨零点做 | 按天分割的历史数据会在零点断开，事后对比最难做 |
| 拿 10 分钟平均值与 1 秒采样比 | `sar -f` 的每条是采集间隔内的平均，粒度不可比 |
| 把"没告警"当成功 | 可能是阈值不对或没采到数据；四种假成功里最常见的一种 |
| 复盘写"人为失误"当根因 | 那不是根因，是可改进的防线缺口 |
| 改进项只写"加强监控" | 没有 owner、期限、验收方式的改进项等于没写 |
| 顺手 `reset-failed` | 会抹掉别人尚未取证的现场 |
| 归档只留改前状态 | 半年后看不到"改成了什么、为什么" |

**第一反应不要做什么**：不要在没有验收判据之前动手；不要在回滚方案没跑过之前动手；不要用"再看看"拖过观察窗口；不要把"服务 active"或"没有告警"当成验收结论；不要在并发执行里省掉每台的证据。

## 要点自测

**问：变更单六要素是什么？三处隐藏考点分别是什么？**
答：目标、范围、备份、回滚、验证、窗口。隐藏考点：范围要写"不改什么"；回滚要写可判定的触发条件（指标 + 阈值 + 持续时间）；验证要写"怎么做"。

**问：回滚命令为什么必须在实验机上跑过并计时？**
答：因为"有回滚"需要同时满足三条：有退路、退路可用、退路够快（耗时小于 RTO）。本机实测改 `vm.swappiness` 的 apply 3 ms / rollback 4 ms 就是这两个数字，不跑就不知道。

**问：两种假回滚分别是什么？为什么会失效？**
答：重启服务（配置与数据都没回到过去）与换回文件但不 reload（进程仍持旧配置）。回滚必须同时撤"持久化文件"与"运行时值"。

**问：三层验收是哪三层？为什么单机全过还不够？**
答：单机、集群、业务。本机实测 `TcpExtListenOverflows` 从 0 涨到 10 期间探活仍返回 200，说明"端口在听、接口能答"不能证明业务可用。

**问：`ExecMainStartTimestamp` 能区分哪两件事？**
答：能区分"进程被重启"（时间戳变新）与"只是重读了配置"（时间戳不变）。只看 `ActiveState=active` 无法区分，而两者风险不同。

**问：为什么回滚触发条件必须带"持续时间"？**
答：单点的瞬时越界常是噪声；"指标 + 阈值 + 持续时间"才能同时控制误报与漏报，例如"错误率 > 1% 持续 5 分钟"。命中即执行，不在现场重新讨论。

**问：收口四件事里最容易跳过的是哪两件？代价什么时候出现？**
答：更新台账与文档、闭环改进项。它们当下没有成就感，代价在几个月后出现——下一次变更的输入是旧的，同一个坑会被再踩一次。

**第一反应不要做什么**：不要用六要素以外的口头约定替代变更单；不要跳过实验机上的回滚演练；不要在观察窗口内"看看再说"；不要把归档只做成压缩文件而不校验；不要让改进项停留在形容词。
