# 一次生产变更的一生

一次生产变更可以拆成五个阶段，依次是立项与评审、准备与预演、执行与分批推进、验证与守候，以及归档与沉淀。这条变更线从"要不要做、谁批准"一直走到"下次怎么更快"，中间不换话题。

每一个阶段的准入门槛是上一个阶段的产出。因此，没有六要素就没有可执行的方案，没有备份与回滚就没有动手的资格，没有验收判据就无法决定"继续还是回滚"；若顺序错了，则工具再全也只是在赌运气。

这条线与前面几章的区别在于：前面几章的对象是机器上的东西（启动链、进程、内存、磁盘、连接），而这一章的对象是你自己要做的事。因此贯穿始终的不是某个字段，而是同一个三问：

1. **这一步可逆吗？** 由于可逆的动作可以放手做，而不可逆的动作必须先有退路，所以这一问决定了要不要先准备回滚。
2. **我怎么知道它成功了？** 由于"成功了"必须可判定，所以判据要在动手之前写出来。
3. **如果失败，下一步是谁做什么？** 这里要写清回滚动作、执行人、回滚后的验收，以及何时向上通报。

## 一、立项与评审：把"要改什么"变成一个可执行的句子

### 1.1 这一阶段要回答的问题是什么

这一阶段要回答的是：要改什么？影响面多大？谁批准？什么时间做？它的产出是一份定级的变更单。

### 1.2 变更单的六要素

六个要素缺一不可。前三个要素决定"能不能做"，因此它们属于动手的前置条件；后三个要素决定"做完怎么算完"，因此它们属于验收与归档的依据。

| 要素 | 要写到什么程度 | 最容易漏的地方 |
| --- | --- | --- |
| 目标 | 它要用一句话说清改完之后的可观察状态 | 有人会把它写成动作（"重启服务"），而不是写成目标（"新配置生效且错误率回到基线"） |
| 范围 | 它要写清哪些机器、哪些服务、哪些集群，以及不改什么 | 若不写"不改什么"，则执行时就会顺手多改 |
| 备份 | 它要写清备份什么、放在哪、怎么确认可用 | 有人只写"已备份"，而不写路径与校验方式 |
| 回滚 | 它要写清回滚命令、触发条件与预计耗时 | 若只写命令而不写触发条件，则等于把决定权留到慌乱的那一刻 |
| 验证 | 它要写清通过什么判据、由谁验收 | 有人只写"观察一下"，而没有量化 |
| 窗口 | 它要写清开始与结束时间，以及"到点没做完怎么办" | 若不约定到点后的动作，则变更会"顺延" |

三处隐藏考点要在评审时逐条对照：

- **范围必须写"不改什么"。** 因为一次变更多改了一个变量，事后就无法归因。
- **回滚必须写成可判定的触发条件**，它固定由三件组成：**指标 + 阈值 + 持续时间**（例如"错误率 > 1% 持续 5 分钟"）。写"如果出问题就回滚"不是触发条件，因为"出问题"由谁在什么时刻判定没有被约定。
- **验证必须写"怎么做"**，而不是只写"看是否正常"。

### 1.3 评审会必答四问

| 问题 | 答不出来的后果 |
| --- | --- |
| 影响面多大？ | 若答不出来，则分级会定错，通知范围会漏人 |
| 最坏结果是什么？ | 若答不出来，则没有为最坏情况准备退路 |
| 怎么退回去？要多久？ | 若答不出来，则回滚方案只存在于想象里 |
| 执行时谁有权喊停？ | 若答不出来，则出事时所有人都在等别人决定 |

**若四问中有任何一问答不出来，就应该改期，而不是"先做起来看看"。**

### 1.4 分级、窗口与冻结期

分级只决定审批层级、通知范围和执行时间，它**不决定技术方案**（判据见《原理：不可逆性与影响面》）。窗口的算法是减出来的：

```text
# 模板，数值仅示意
窗口 = 业务低峰时段 − 其它已排期变更 − 周期任务时段 − 留给回滚与验收的时间
```

必须改期的信号有三个：窗口内找不到能做回滚决策的人、备份没有验证过、同一时段另有变更。冻结期通常只放两类事：止损与安全修复。

### 1.5 字段读法：怎么知道窗口里有没有撞车

| 字段 / 命令 | 是什么 / 单位 | 判据 | 与谁同看 | 看到它转向哪一步 |
| --- | --- | --- | --- | --- |
| `systemctl list-timers --all` 的 `NEXT`/`LEFT` | 它给出定时任务下次触发的时刻与剩余时间，单位分别是时刻与秒／分 | **若 `NEXT` 落在你的窗口内，则就是撞车**；若 `LEFT` 小于你的变更耗时，则更是撞车 | 它与变更窗口同看 | 若撞车，则应调整窗口或临时停掉该 timer |
| `systemctl list-timers` 的 `LAST` | 它给出上次触发的时刻 | 它用于判断该任务的实际周期与耗时 | 它与任务日志同看 | 由于周期任务会占资源，所以应避开它触发的时段 |
| `systemctl show <unit> -p UnitFileState` | 它给出开机自启状态，取值是 `enabled`/`disabled`/`static` | `ActiveState=active` **不等于**开机自启 | 它与 `ActiveState` 同看 | 若本次变更涉及重启，则要先确认重启后它还会起来 |
| `systemctl show <unit> -p NRestarts` | 它给出本次启动以来的重启次数，单位是个，且是累计值 | 若非 0 且仍在增长，则说明服务处于崩溃重启循环 | 它与 `SubState` 同看 | 若非 0，则要先查为什么在重启，不要叠加变更 |
| `systemctl show <unit> -p FragmentPath` | 它给出 unit 文件的来源路径 | 若路径在 `/usr/lib/systemd/system/` 下，则该文件由发行版提供，因此直接改它会在升级时被覆盖 | 它与本地 drop-in 目录同看 | 若它是发行版文件，则应改用 drop-in |
| `systemctl list-dependencies <unit>`（可加 `--reverse`） | 它给出 unit 的正向依赖或反向依赖 | 反向依赖告诉你"停了它会连带停谁" | 它与服务台账同看 | 若有反向依赖，则要把它排进分批计划 |

本机一份实测快照（环境：Ubuntu 24.04.5 LTS / 内核 `6.8.0-139-generic` / systemd 255 / root，2026-09-19T08:07:34+00:00）：

```text
# 数值仅示意、不代表你的机器
$ systemctl list-timers --all | head -3
NEXT                         LEFT       LAST                         UNIT
Sat 2026-09-19 08:10:00 UTC  2min 25s   Sat 2026-09-19 08:00:12 UTC  sysstat-collect.timer
Sat 2026-09-19 09:25:48 UTC  1h 18min   Fri 2026-09-18 09:25:48 UTC  fwupd-refresh.timer

$ systemctl show ssh -p Id -p ActiveState -p SubState -p MainPID -p NRestarts -p UnitFileState -p FragmentPath
Id=ssh.service
ActiveState=active
SubState=running
MainPID=1348
NRestarts=0
UnitFileState=disabled
FragmentPath=/usr/lib/systemd/system/ssh.service
```

判读：`sysstat-collect.timer` 的 `NEXT` 距采集时刻只有 2 分 25 秒，**因此如果变更窗口是 08:08 开始，它就撞上了**；而这个采集任务正是你事后复盘时要用的历史数据来源。`ssh.service` 是 `active`，但它的 `UnitFileState=disabled`（它由 `ssh.socket` 拉起），**所以只看 `is-active` 会以为"重启后它自己会起来"**。

### 1.6 这一阶段的产出长什么样

一份定级的变更单要满足：六要素齐全、范围写了"不改什么"、回滚写了可判定的触发条件与预计耗时、窗口里没有撞车的定时任务与其它变更，并且评审四问都有答案。判定它合格的办法很直接：把它交给一个没参与的人，若他能照着执行、照着重放，则这份变更单合格。

## 二、准备与预演：动手前把退路铺好

### 2.1 这一阶段要回答的问题是什么

这一阶段要回答的是：**备份在哪？回滚命令是什么？怎么分批？怎么验收？** 它的产出是备份、回滚方案、灰度计划与验收标准。

### 2.2 三类备份对象与三条合格线

| 对象 | 例子 | 备份方式 |
| --- | --- | --- |
| 配置文件 | 本次涉及的 `/etc` 下文件与服务的 drop-in 属于这一类 | 它用 `cp -a` 复制到带时间戳的目录，因为这样能保留权限与属主 |
| 数据 | 数据目录、数据库与上传内容属于这一类 | 它按应用的一致性原则做备份（见《原理：可恢复性的语言》） |
| 系统状态 | 运行中的服务、监听端口、挂载、关键参数值与启停清单属于这一类 | 这一类要**采集，不是复制**，因为状态无法"复制回去"，只能记录后手工重放 |

三条合格线是：

1. **唯一的名字**：备份路径要带时间戳（例如 `2026-09-19-080734`），因为 `xxx.bak` 这种名字每次都会被覆盖；
2. **不在被改动的路径内**：备份要放在本次动作不会触碰的目录里，否则改错时会把备份一起改掉；
3. **能 `diff` 与恢复验证**：`diff -r` 的判据是**输出为空且退出码为 0**；有差异时退出码是 1，所以不能写"没报错"就算一致。

状态快照要采五组内容：运行中的服务列表、监听端口、挂载与文件系统、本次涉及的关键参数值，以及开机自启清单。在同为 Ubuntu 24.04.5 LTS / 内核 `6.8.0-139-generic` / systemd 255 / root 的本机实测里，一份状态快照有 109 行，当时运行中的 service 单元是 24 个。

### 2.3 回滚的四种形态与两种假回滚

| 形态 | 粒度 | 典型耗时量级 | 备注 |
| --- | --- | --- | --- |
| 配置回滚 | 它的粒度是换回文件并 reload | 它的典型耗时是秒级 | 它最优先使用 |
| 版本回滚 | 它的粒度是切回上一个发布版本 | 它的典型耗时是分钟级 | 它需要有版本留档 |
| 服务回滚 | 它的粒度是启停与切主从 | 它的典型耗时是分钟级 | 它会断连接，因此要配合摘流量 |
| 数据回滚 | 它的粒度是从备份或快照恢复数据 | 它的典型耗时是小时级，且可能丢数据 | **能用配置回滚就不要用数据回滚** |

两种假回滚是：

- **重启服务**：这样做的结果是进程重启了，但配置与数据都没有回到过去；
- **换回文件但不 reload**：这样做的结果是进程仍持有旧配置，运行时值也没有变。

**结论是固定的：回滚必须同时撤"持久化文件"与"运行时值"。** 若只做一半，则会出现"文件是旧的、行为是新的"，或者反过来。

回滚命令必须在实验机上跑过并记下耗时。本机实测（环境同上：Ubuntu 24.04.5 LTS / 内核 `6.8.0-139-generic` / systemd 255 / root；动作是把 `vm.swappiness` 从 60 改到 10 再改回）：

```bash
cp -a /etc/sysctl.d/99-lab.conf /tmp/rollback/99-lab.conf.$(date +%F-%H%M%S)
                                                  # 验证：备份带时间戳、在改动路径之外
sysctl -w vm.swappiness=10                        # 变更
sysctl -n vm.swappiness                           # 验证：运行时值（不 cat 配置文件）
cp -a /tmp/rollback/99-lab.conf.<stamp> /etc/sysctl.d/99-lab.conf && sysctl -p /etc/sysctl.d/99-lab.conf
                                                  # 回滚：只应用这一个文件，不用 --system
sysctl -n vm.swappiness                           # 验证：回滚后的运行时值
```

```text
# 数值仅示意、不代表你的机器
apply_ms = 3
rollback_ms = 4
```

**这两个数字才是"回滚方案"的证据。** 它们也解释了为什么回滚要用 `sysctl -p <单文件>`，而不是用 `sysctl --system`：后者会把系统上所有配置文件重新应用一遍，从而覆盖掉别人尚未落盘的临时改动，于是**回滚动作本身变成了第二次变更**。

### 2.4 灰度计划：依据是故障域，不是台数

分批计划按四个维度设计，通常同时用两个：

| 维度 | 例子 | 适合的场景 |
| --- | --- | --- |
| 实例 | 例如先 1 台，再 10%，再全量 | 它适合无状态服务 |
| 故障域 | 例如先一个机架或一个可用区 | 它适合需要验证依赖与网络路径的变更 |
| 流量 | 例如按比例或按用户分桶 | 它适合有灰度通道的接入层 |
| 租户 | 例如先内部租户，再小客户，再全量 | 它适合多租户系统 |

必须算出来的数有两个：

```text
# 模板，数值仅示意
批次大小 ≤ 总容量 − 最小可接受容量
观察时间 ≥ max(一个业务周期, 一个监控评估周期, 2~3 个采样间隔)
```

**灰度的本质是给自己留一个对照组。** 因此除了要算"改多少"，还要定义"跟谁比"：没改的那部分实例就是对照组，它的指标是判断"是不是这次变更造成的"的唯一依据。

有一类变更是没有分批余地的：**全局配置**（DNS、网关、统一鉴权）。由于它们对所有客户端同时生效，所以要按不可逆动作对待：先预演，再缩短 TTL，然后切换，并且准备好"切回去也要等 TTL"的时间预算。

### 2.5 变更前检查清单（13 项）

逐条打勾，若任何一项空着，则不开始：

1. 六要素齐全、已定级、已批准；
2. 对象清单**从台账生成**，而不是从记忆里写；
3. 配置备份带时间戳、不在被改路径内；
4. 数据备份已包含一致性处理（或明确记录"本次不涉及数据"）；
5. 状态快照已采（服务、端口、挂载、参数、启停清单）；
6. 回滚命令已在实验机上跑过，并记下耗时；
7. 回滚触发条件已写成"指标 + 阈值 + 持续时间"；
8. 验收判据已写明（单机、集群、业务三层，见验证与守候阶段）；
9. 改动前的基线已采（同一组指标、同一口径）；
10. 分批计划已定（批次大小与批数来自容量算式）；
11. 窗口与"到点没做完"的处置已约定；
12. 通知已发出，包含值班与相关方；
13. **第二个人有能力执行回滚**。

第 13 项最容易被省掉，也最贵：它同时检验"回滚方案可用"与"知识不在一个人手里"这两项要求。

## 三、执行与分批推进：每一步都可观察、可停止、可回退

### 3.1 这一阶段要回答的问题是什么

这一阶段要回答的是：**现在到第几批？这一步的预期是什么？实际是什么？** 它的产出是逐批的执行记录，其中含同一时刻的证据。

### 3.2 固定顺序

执行的顺序是固定的：若需要摘流量，则先摘流量，然后改动，接着做单机验证，验证通过后放回流量，最后进入观察。

单机验证的内部顺序也是固定的：先看状态，再看日志，最后打请求。若先打请求，则会把"服务没起来导致的拒连"误判成网络问题，也会把"配置没生效但返回 200"误判为成功。

要不要摘流量，按三个条件判断：服务**有状态**、接入层**没有健康检查**、动作**会断掉存量连接**；只要满足其中任意一条，就要摘流量。若服务无状态且接入层有健康检查，则它可以靠排空机制自然完成。摘流量的验收判据是**从外部探失败、从本机探成功**。

### 3.3 批次决策点的四种选择

每一批结束都要明确选一个，并把它写进记录：

| 选择 | 判据 |
| --- | --- |
| 继续 | 若本批指标与验收判据全部满足，且与对照组相比无异常，则选继续 |
| 扩批 | 若满足与"继续"相同的条件，且观察时间已覆盖一个业务周期，则选扩批 |
| 暂停 | 若出现"轻微劣化但在阈值内"，或出现"现象无法解释但服务还活着"，则**暂停并保留现场**，再观察一个完整周期 |
| 回滚 | 若命中变更单上写好的触发条件，则**立即执行，不再讨论** |

**"解释不了但服务还活着"一律归为暂停。** 这一类最值得写进复盘，因为它说明你的判据有盲区。

### 3.4 字段读法：怎么确认"这一步真的生效了"

| 字段 / 命令 | 是什么 / 单位 | 判据 | 与谁同看 | 看到它转向哪一步 |
| --- | --- | --- | --- | --- |
| `systemctl show <unit> -p ActiveState -p SubState -p NRestarts` | 它分别给出单元状态、子状态与重启次数，其中重启次数的单位是个，且是累计值 | 三个字段要一起看：若只看 `ActiveState=active`，则会漏掉 `SubState=auto-restart` 的崩溃循环 | 它与单元日志同看 | 若 `NRestarts` 增长，则要停批并查原因 |
| 运行时值（`sysctl -n <key>`、`cat /proc/...`） | 它给出当前生效值 | **验收一律用运行时口径**，因此不 `cat` 配置文件 | 它与配置文件内容同看 | 若两者不一致，则说明配置没被加载 |
| `ss -lnt` 的 `Recv-Q` | 它给出监听套接字上"已完成握手但未被 `accept`"的连接数，单位是个 | 若它持续接近队列上限（即 `Send-Q`），则说明应用 accept 不及时 | 它与 `nstat` 的 `TcpExtListenOverflows` 同看 | 若发生溢出，则要转应用侧或调整队列 |
| `/proc/<pid>/limits` 的 open files | 它给出进程句柄的软限与硬限，单位是个 | 若使用量贴近软限，则危险 | 它与 `ls /proc/<pid>/fd | wc -l` 同看 | 若贴近上限，则要先提上限止血，再查泄漏 |
| 退出码 | 它是命令的退出状态：`timeout` 超时为 **124**，命令自身失败为 1，`SIGKILL` 为 137 | 124 要单独归类，因为这一台可能只是慢 | 它与命令输出同看 | 若退出码非 0 且非 124，则要停批 |

本机实测的一组执行期数据（环境同上，每次 reload 固定 1 秒）：

```text
# 数值仅示意、不代表你的机器
串行 5 次：        serial_ms = 5100
xargs -P 4：       parallel_ms = 2058
两次输出均为 5 行 is-active=active
timeout 2 sleep 5 的退出码是 124
timeout 30 true 的退出码是 0
```

判读：并发的收益与 `⌈N/并发度⌉` 吻合，但**两次执行的输出完全相同**，因此并发买的是时间，卖的是可定位性。所以在并发执行时，必须让每一台自己落一份带主机名与时间戳的证据。

### 3.5 日志与证据：先剔除别人的噪声

执行期要抓的证据是"同一时刻的：状态 + 日志 + 请求"。这里有一个高频陷阱：**不限定单元的日志过滤会把同机其它服务的报错算进来。** 本机实测（环境同上）：

```text
# 数值仅示意、不代表你的机器
$ journalctl -u ssh --since "10 min ago" | grep -icE 'error|fail'
0
$ journalctl --since "10 min ago" | grep -icE 'error|fail'
93
```

同一个窗口、同一台机器，**限定单元是 0 条，不限定是 93 条**，而这 93 条几乎全部来自共用机器上其它实验的服务。**判据是"日志基线必须先剔除他人与周期性噪声"**：先用变更前的一段窗口采一份基线，变更后再采一份，比的是同一个单元、同一个关键词、同一个时长。

### 3.6 执行记录的最小格式

| 批次 | 对象 | 开始 | 结束 | 改前值 | 改后值 | 命令输出摘要 | 结论 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | web-01 | 22:03 | 22:05 | `v1` | `v2` | `active/running/NRestarts=0` | 本批指标与验收判据全部满足，因此选继续 |
| 2 | web-02..05 | 22:07 | 22:11 | `v1` | `v2` | 4/4 `active` | 观察时间已覆盖一个业务周期，因此选扩批 |

同时要留异常记录（时间 / 现象 / 原始输出 / 判断 / 动作），以及"实际耗时 vs 计划耗时"。这份记录是归档与沉淀阶段的主体材料。

## 四、验证与守候：判据决定一切

### 4.1 这一阶段要回答的问题是什么

这一阶段要回答的是：**改对了吗？业务正常吗？什么时候可以宣布成功或回滚？** 它的产出是一份验收记录。

### 4.2 三层验收

| 层 | 验什么 | 判据 |
| --- | --- | --- |
| 单机 | 它验运行时值、状态、有没有新增报错，以及本机探活 | 它读 `sysctl -n`、`systemctl show` 的三个字段，并看 `journalctl -u` 有没有新增 error |
| 集群 | 它验可用实例数、容量水位，以及有没有新增单点 | 它读 `ss -s` 的状态分布、`systemctl --failed`，以及后端列表 |
| 业务 | 它验真实业务路径的 p99、错误率与 QPS | 它与变更前基线和对照组相比 |

**三层是递进的**：若单机不过，则不看后两层；**单机全过仍然必须看后两层**，因为在本机实测里，目标 `TcpExtListenOverflows` 从 0 涨到 10 的那段时间里，探活一直返回 200，这说明"端口在听、接口能答"完全不足以证明业务可用。

### 4.3 一个能区分"重读配置"与"重启进程"的字段

`systemctl show <unit> -p ExecMainStartTimestamp` 给出的是**主进程何时开始运行**，因此可以据它判断主进程有没有被换掉：

- 变更后它应该是**新的时间戳**，因为这表示进程被重启了；
- 若它没有变，则说明这次 reload 只是让进程重读了配置，主进程没有换。**只看 `ActiveState` 分不出这两种情况**，而它们的风险完全不同，因为重读配置不会清掉内存里的状态与连接。

本机基线是 `ExecMainStartTimestamp=Sat 2026-09-19 07:20:10 UTC`、`MainPID=1348`、`NRestarts=0`。

### 4.4 观察窗口与检查点

窗口长度不小于 `max(一个业务周期, 2~3 个采样间隔, 一次关键定时任务的执行周期)`。采样要求按问题的形态定：

| 形态 | 采样要求 |
| --- | --- |
| 立即暴露（几分钟内） | 它要求秒级采样，并查看窗口内有没有抬头 |
| 压力相关（高峰期才出现） | 它要求覆盖业务高峰，或做一次受控压测 |
| 周期相关（按小时或按天） | 它要求至少覆盖 2~3 个完整周期；**跨零点的变更最危险**，因为按天分割的历史数据会在零点断开 |

四个检查点依次是：**T+1** 时的单机核对、**T+5** 时的集群与业务核对、**T+15** 时的新增告警与日志核对，以及**窗口结束**时宣布成功或回滚。每个检查点都要留同一组证据。

查历史的口径有一个硬要求：`sar -f` 输出的每一行是**采集间隔内的平均值**（默认间隔 10 分钟），因此拿它跟 1 秒采样的实时数据比是不可比的。本机实测 `sar -u -f /var/log/sysstat/sa19` 的 `Average: 0.37 0.19 99.44` 与 `sar -u 1 3` 的 `Average: 0.25 0.42 99.33` 看着接近，但**它们回答的是不同粒度的问题**。

### 4.5 回滚触发线

回滚触发线固定写成三件：**指标 + 阈值 + 持续时间**。

```text
# 模板，数值仅示意
若错误率 > 1% 且持续 5 分钟，则回滚
若 p99 > 基线 1.5 倍 且持续 10 分钟，则回滚
若探活连续 3 次失败，或成功率 < 99%，则回滚
```

三条纪律是：**命中即执行，不在现场重新讨论**；**回滚本身也要验收**，也就是核对运行时值回旧、服务 active、业务探活通过，以及窗口内指标回基线；**若没命中但有存疑信号，则暂停扩批并记录，而不是用"再看看"拖过窗口**。

### 4.6 四种假成功

| 现象 | 为什么不是成功 |
| --- | --- |
| 重启后恢复正常 | 由于现场被清掉，问题只是被推迟 |
| 没有告警 | 这可能是阈值不对，也可能是数据根本没采到 |
| 单机探活全通过 | 因为探活路径与用户路径不同，而集群与业务两层还没有看 |
| 跟以前一样 | 由于没有量化、没有对照，这只是"没观察到变化" |

## 五、归档与沉淀：把一次变更变成组织资产

### 5.1 这一阶段要回答的问题是什么

这一阶段要回答的是：**记录归档了吗？台账更新了吗？Runbook 改了吗？下次怎么更快？**

### 5.2 归档四件事

归档四件事分别是：归档记录、更新台账与文档、闭环改进项，以及沉淀 Runbook。最容易跳过的正是第二件与第三件，因为它们当下没有成就感，而代价会在几个月后出现。

归档内容至少三部分：**改前状态 + 改后状态 + 变更窗口日志**。若只留改前，则半年后就看不到"改成了什么、为什么"；若只留改后，则看不到当时从哪儿出发。

归档的三道验收（本机实测）：

```text
# 数值仅示意、不代表你的机器
config-after/ 三个文件：314 / 255 / 1124 字节（合计 1693）
journal-window.log：207019 字节 / 2184 行
目录 du -sh 报 224K，tar czf 之后是 22195 字节
tar tzf 列出 6 项；rsync -a 之后用 diff -r 检查，退出码是 0
sha256sum：3550eec889ca5d803bf055179e458690a2f4838fb614adf691ba491f1cef0093
```

三点读法是：**归档体积几乎全被日志占**（1693 字节配置对比 207019 字节日志），所以归档的容量预算要按日志估；**压缩牺牲了"能直接打开看"**，因此应急取证包建议同时留一份未压缩目录；**校验要留一个可复算的值**（这里是 `sha256sum`），否则半年后没人能证明这份归档没被动过。

### 5.3 复盘的六段

复盘的六段依次是：

1. 时间线要精确到分钟；
2. 影响面要写清谁受影响、受影响多久，以及数据有没有损失；
3. 证据要留下原始输出；
4. 根因要写直接原因，**还要**写清为什么它没被提前发现；
5. 止损动作要写为什么选它，以及重来会不会换；
6. 改进项要带 owner 与期限，并回答"为什么之前的防线没拦住它"。

三条无指责要点是：**描述行为而不评价人**（例如写"第 3 批漏改 7 台"，而不写"执行人粗心"）；**要追问系统为什么允许这个错误发生**；**行动项必须有验收方式**。一句话记住：**"根因是人为失误"不算根因**，因为人是常量，而能被系统吸收的失误才是好设计。

复盘的触发条件有三条：一是**发生了回滚**；二是**影响了业务**，哪怕只是短抖动；三是**出现了"解释不了但过去了"的现象**，这一条最值得写。

### 5.4 改进项：从形容词到句子

合格的改进项长这样：**有动作、有 owner、有期限、有验收方式。** 改进项有三种去向：

1. **立即修**，也就是在本次窗口内或次日完成；
2. **排期**，也就是让它进入下一个迭代，并留下排期记录；
3. **显式接受风险**，也就是写明批准人。这一种最容易被忽略，但**接受风险也是一个决定**，若不写下来，则等于"没人决定"。

### 5.5 字段读法：失败单元的归档处理

| 字段 / 命令 | 是什么 | 判据 | 与谁同看 | 看到它转向哪一步 |
| --- | --- | --- | --- | --- |
| `systemctl --failed` | 它列出当前失败的单元 | 若它非空，则要先判断这些单元"是不是本次变更的产物" | 它与 `FragmentPath`、`journalctl -u` 的时间戳同看 | 若它是本次的产物，则清理并记录；若不是，则去找 owner |
| `systemctl show <unit> -p FragmentPath` | 它给出单元文件的来源路径 | 路径能反推它是谁部署的，因此可以区分本地部署与发行版提供 | 它与变更清单同看 | 由它决定清理还是交接 |
| `journalctl -u <unit>` 的时间戳 | 它给出该单元报错发生的时刻 | 它与变更窗口比对，用来判断因果 | 它与变更记录同看 | 若时间戳落在窗口内，则它是本次的产物 |

纪律是：**要先判断失败单元是不是本次的产物，然后才动手；同时不要顺手执行 `systemctl reset-failed`**，因为那会抹掉别人尚未取证的现场。

### 5.6 度量：五个数，一起看

要一起看的五个数是：**变更成功率、回滚率、变更引起的故障占比、MTTR / MTTD，以及改进项按期完成率。** 它们的用法是**找瓶颈，不是考核个人**，而且必须几个数一起看：

- 若只盯回滚率，则团队会变得不敢做变更，该做的也不做了；
- 若只看 MTTR，则会忽略"发现得太晚"这一半。

## 六、跨阶段的核对对象

前面五节讲的是沿时间顺序展开的五个阶段；下面五条核对对象各自贯穿其中多个阶段，因此按它们切分比从头走一遍时间线更快。若一轮变更串不起来，通常是因为没有抓住下面这几条。

| 核对对象 | 它贯穿哪几个阶段 | 每一处读什么字段 |
| --- | --- | --- |
| 可逆性与退路 | 它贯穿全部五个阶段，因为只读、可回滚与不可逆这三档分类要在每一个阶段重新核对一次 | 在立项与评审阶段读变更单的「回滚」要素，核对它是否写成可判定的触发条件；在准备与预演阶段读回滚命令在实验机上的实测耗时，本机是 apply 3 ms / rollback 4 ms；在执行与分批推进阶段读命令的退出码（124、1 或 137）与 `systemctl show <unit> -p NRestarts`；在验证与守候阶段读运行时值（`sysctl -n vm.swappiness`）与业务探活结果，用来判断要不要执行回滚；在归档与沉淀阶段读 `systemctl --failed` 与 `systemctl show <unit> -p FragmentPath`，确认退路没有留下未清理的残留 |
| 时间预算 | 它贯穿立项与评审、准备与预演、执行与分批推进、验证与守候这四个阶段，因为 RTO 与 RPO 是约束，而 MTTR 与 MTTD 是度量 | 在立项与评审阶段读窗口算式，也就是业务低峰时段减去其它已排期变更、周期任务时段与留给回滚和验收的时间；在准备与预演阶段读回滚命令的实测耗时，并用 `systemctl list-timers --all` 的 `NEXT` 与 `LEFT` 核对窗口里有没有撞车；在执行与分批推进阶段读记录里的"实际耗时 vs 计划耗时"，例如 serial_ms = 5100 与 parallel_ms = 2058；在验证与守候阶段读窗口长度 `max(一个业务周期, 2~3 个采样间隔, 一次关键定时任务的执行周期)`，并用 `sar -f` 的采集间隔（默认 10 分钟）核对历史口径 |
| 幂等与批量执行 | 它贯穿准备与预演、执行与分批推进、验证与守候这三个阶段，因为批量执行的每一步都要能重跑，而非幂等的脚本禁止"再跑一遍" | 在准备与预演阶段读备份路径是否带时间戳（例如 `2026-09-19-080734`），以及备份是否放在改动路径之外；在执行与分批推进阶段读每批的改前值与改后值，并把 `xargs -P 4` 的并行耗时与串行耗时对比，因为并发买的是时间，卖的是可定位性；在验证与守候阶段读 `systemctl show <unit> -p ExecMainStartTimestamp`，用它区分"重读配置"与"重启进程" |
| 故障域与容量余量 | 它贯穿立项与评审、准备与预演、执行与分批推进、验证与守候这四个阶段，因为分批大小由剩余容量决定，而不由台数决定 | 在立项与评审阶段读窗口与冻结期，若同一时段另有变更则必须改期；在准备与预演阶段读灰度计划的故障域维度与 `systemctl list-dependencies <unit> --reverse` 的反向依赖，并用"批次大小 ≤ 总容量 − 最小可接受容量"算出每批台数；在执行与分批推进阶段读 `ss -s` 的状态分布、`systemctl --failed` 与 `ss -lnt` 的 `Recv-Q`；在验证与守候阶段读 `nstat` 的 `TcpExtListenOverflows`（本机实测从 0 涨到 10）与探活结果 |
| 台账与到期 | 它贯穿立项与评审、准备与预演、归档与沉淀这三个阶段，因为对象清单要从台账生成，而不能靠记忆 | 在立项与评审阶段读变更单的「范围」要素与窗口的起止时间；在准备与预演阶段读检查清单的 13 项是否逐条落实，其中第 2 项要求对象清单从台账生成；在归档与沉淀阶段读 `systemctl --failed`、`systemctl show <unit> -p FragmentPath` 与 `journalctl -u` 的时间戳，把结果回写台账，并核对改进项的 owner 与期限 |

这五条核对对象各自的机制讨论分别见《原理：不可逆性与影响面》《原理：可恢复性的语言》《原理：幂等与可重入的批量执行》《原理：故障域与检测的赌注》与《治理：生产运维与变更治理》；回滚的四种形态与典型耗时量级见本篇的准备与预演阶段。

### 6.1 一条纪律：一次只改一个变量

若把回滚与调参同时做，或把限流与扩容同时做，则事后永远无法归因。这一条与上面五条不同：它不是一个贯穿某几个阶段的核对对象，而是一条每一个阶段都要遵守的纪律。

## 常见坑

| 做法或说法 | 后果或事实 |
| --- | --- |
| 变更单里写"观察一下" | 由于没有验收判据，就无法决定继续还是回滚 |
| 回滚只写命令，不写触发条件 | 决定权被推到最慌乱的那一刻，且通常由最没信息的人做 |
| 备份用 `xxx.bak` 这种固定名字 | 二次执行会覆盖第一次的退路 |
| 回滚只改文件不 reload | 进程仍持旧配置，运行时值也不变，于是出现"文件是旧的、行为是新的" |
| 用 `sysctl --system` 做单文件回滚 | 它会把系统上所有配置重新应用一遍，从而覆盖别人尚未落盘的临时改动 |
| 用 `is-active` 判断服务健康 | `active` 也可能是自动重启循环，因此要看 `SubState` 与 `NRestarts` |
| 用配置文件的运行时间判断重启 | 只看 `ActiveState` 分不出"重读配置"与"重启进程"，因此要看 `ExecMainStartTimestamp` |
| 日志不限定单元就下结论 | 本机实测同一窗口里，限定 `ssh` 得到 0 条，不限定得到 93 条 |
| 用并发替代分批 | 并发买的是时间，卖的是可定位性，因此两次运行的输出可能完全相同 |
| 变更跨零点做 | 按天分割的历史数据会在零点断开，所以事后对比最难做 |
| 拿 10 分钟平均值与 1 秒采样比 | `sar -f` 的每条是采集间隔内的平均，因此粒度不可比 |
| 把"没告警"当成功 | 这可能是阈值不对，也可能是没采到数据，而它是四种假成功里最常见的一种 |
| 复盘写"人为失误"当根因 | 那不是根因，而是可改进的防线缺口 |
| 改进项只写"加强监控" | 没有 owner、期限与验收方式的改进项等于没写 |
| 顺手 `reset-failed` | 它会抹掉别人尚未取证的现场 |
| 归档只留改前状态 | 半年后看不到"改成了什么、为什么" |

**第一反应不要做什么**：不要在没有验收判据之前动手；不要在回滚方案没跑过之前动手；不要用"再看看"拖过观察窗口；不要把"服务 active"或"没有告警"当成验收结论；不要在并发执行里省掉每台的证据。

## 要点自测

**问：变更单六要素是什么？三处隐藏考点分别是什么？**
答：六要素是目标、范围、备份、回滚、验证与窗口。三处隐藏考点是：范围要写"不改什么"；回滚要写可判定的触发条件，也就是指标、阈值与持续时间三件；验证要写"怎么做"。

**问：回滚命令为什么必须在实验机上跑过并计时？**
答：因为"有回滚"需要同时满足三条：有退路、退路可用、退路够快，也就是回滚耗时小于 RTO。本机实测改 `vm.swappiness` 的 apply 3 ms / rollback 4 ms 就是这两个数字，所以不跑就不知道。

**问：两种假回滚分别是什么？为什么会失效？**
答：两种假回滚分别是重启服务与换回文件但不 reload；前者让配置与数据都没有回到过去，后者让进程仍持旧配置。因此回滚必须同时撤"持久化文件"与"运行时值"。

**问：三层验收是哪三层？为什么单机全过还不够？**
答：三层是单机、集群与业务。本机实测里 `TcpExtListenOverflows` 从 0 涨到 10 期间探活仍返回 200，这说明"端口在听、接口能答"不能证明业务可用。

**问：`ExecMainStartTimestamp` 能区分哪两件事？**
答：它能区分"进程被重启"（此时时间戳变新）与"只是重读了配置"（此时时间戳不变）。只看 `ActiveState=active` 无法区分，而两者的风险不同。

**问：为什么回滚触发条件必须带"持续时间"？**
答：因为单点的瞬时越界常是噪声，只有"指标 + 阈值 + 持续时间"才能同时控制误报与漏报，例如"错误率 > 1% 持续 5 分钟"。命中即执行，不在现场重新讨论。

**问：归档四件事里最容易跳过的是哪两件？代价什么时候出现？**
答：最容易跳过的是更新台账与文档、闭环改进项这两件。它们当下没有成就感，而代价在几个月后出现，也就是下一次变更的输入是旧的，同一个坑会被再踩一次。

**第一反应不要做什么**：不要用六要素以外的口头约定替代变更单；不要跳过实验机上的回滚演练；不要在观察窗口内"看看再说"；不要把归档只做成压缩文件而不校验；不要让改进项停留在形容词。
