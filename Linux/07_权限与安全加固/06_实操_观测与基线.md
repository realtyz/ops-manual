# 观测与基线

## 1. 一个问题，一把工具

| 你想知道 | 用什么 | 关键字段或文件 |
| --- | --- | --- |
| 这个进程/会话是谁 | `id`、`/proc/<pid>/status` | `uid`/`gid`/`groups`；`Uid`/`Gid`/`Groups`/`Cap` 四行 |
| 某个账号在 NSS 视角下长什么样 | `getent` | `getent passwd`/`shadow`/`group` |
| 账号的密码与有效期状态 | `passwd -S`、`chage -l`、`getent shadow` | 密码状态字符、第 5~8 字段 |
| 文件的 mode、属主、时间 | `stat`、`ls -l` | `stat -c "%a %A %u %g %n"` |
| 路径上每一级的权限 | `namei -l` | 逐级的 mode 与属主 |
| 完整 ACL、`mask`、有效权限 | `getfacl` | `user::`/`user:<name>:`/`group::`/`mask::`/`#effective:` |
| `chattr` 属性 | `lsattr` | `i`/`a` 与正常的 `e` |
| 任意扩展属性 | `getfattr` | `-d -m -` 列出全部 |
| 文件是否带 capability | `getcap`、`getpcaps`、`capsh --print` | `cap_xxx=ep` 与五个集合 |
| 哪些文件带 SUID/SGID | `find` | `-perm -4000` / `-perm -2000` |
| 该文件属于哪个包 | `dpkg -S`、`rpm -qf` | 按 basename 反查（`/bin`→`/usr/bin` 的发行版） |
| 挂载点与挂载选项 | `findmnt`、`mountpoint` | `TARGET,SOURCE,FSTYPE,OPTIONS` |
| 内核安全参数当前值 | `sysctl` | 参数名与值；来源要另查配置文件 |
| 这台机器挂着哪些 LSM | `/sys/kernel/security/lsm` | 模块清单 |
| AppArmor 状态与 profile | `aa-status`、`/sys/kernel/security/apparmor/profiles` | enforce/complain/unconfined 计数 |
| SELinux 模式与上下文 | `getenforce`、`sestatus`、`ls -Z` | 模式、`user:role:type:level` |
| MAC 拒绝记录 | 审计原始日志、`ausearch` | `apparmor="DENIED"`、`avc: denied` |
| 认证与提权留痕 | 发行版认证日志、审计日志、`journalctl` | 认证失败原因、sudo 的 `TTY=`/`PWD=`/`USER=`/`COMMAND=` |
| 登录痕迹 | `last`、`lastb`、`loginctl`、`/var/log/lastlog` | 成功/失败登录与活跃会话 |
| 谁在监听哪些端口 | `ss -lntup` | 监听地址、端口、进程 |
| 计划任务与自启 | `crontab -l`、`ls /etc/cron.*`、`systemctl list-timers`、`systemctl list-unit-files --state=enabled` | 条目与执行者 |
| 包文件是否被改动 | `dpkg -V`、`rpm -Va` | 变更标记与 `?????????` |
| 谁在用某个打开的文件 | `lsof`、`fuser` | 进程与 fd |
| 进程侧的身份与打开的文件 | `ps -eo pid,user,group,args`、`ls -l /proc/<pid>/exe` | 属主、组、真实可执行文件 |

表里分两类东西：**命令**（`id`、`stat`、`namei`、`find`、`getfacl`、`getcap`、`ss`、`last`、`auditctl`……文档在 `man 1` 或 `man 8`）与**内核接口文件**（`/proc/...`、`/sys/...`、`/etc/...` 里的配置——直接 `cat` 就能读）。判断类别看文档节号：`man 2` 系统调用、`man 3` 库函数、`man 5` 文件格式、`man 1` 命令、`man 8` 管理命令。

## 2. 怎么读这些数字

下面每条给五件事：**是什么 / 单位 / 判据 / 与谁同看 / 转向哪一步**。所有输出样例只展示格式，数值不代表你的机器。

### 2.1 主体：`id` 与 `/proc/<pid>/status`

```bash
id                                   # 验证：当前会话的 uid/gid/附加组
cat /proc/self/status | grep -E '^(Uid|Gid|Groups|Cap)'
                                     # 验证：进程视角的四个身份字段
```

`/proc/<pid>/status` 的 `Uid:` 一行有四个数，依次是 **real / effective / saved / filesystem**；`Gid:` 同理。`Cap` 行是能力位掩码（`CapPrm`/`CapEff`/`CapBnd`/`CapAmb` 也各自成行）。

- **判据**：权限判定看 `effective`；`real` 与 `effective` 不同说明该进程已提权。
- **与谁同看**：`getpcaps <pid>`（解码能力）、`ps -o pid,user,group`（渲染成名字）。
- **转向哪一步**：`euid` 是 0 但登录用户不是 root 时，去看它是通过哪条通道提权的（SUID、file capabilities、`sudo`，还是由 root 启动的服务）。

### 2.2 客体：`stat` 与 `namei -l`

```bash
stat -c "%a %A %u %g %n" /srv/app/config
                                     # 验证：mode 的数值与符号、UID、GID
namei -l /srv/app/config             # 验证：从 / 到目标，逐级 mode 与属主
```

- **`stat -c %a` 是四位或三位八进制**：`4755` 表示 SUID 已置位，`2755` 表示 SGID，`1777` 表示 sticky。**判据**：查特殊位用这一列，比 `ls -l` 的 `s`/`t` 更不容易看错；改过 `chown` 之后要复查，因为它会清掉 SUID/SGID。
- **`namei -l` 的每一行是一级目录**，最后一行才是目标文件。**判据**：`EACCES` 时若最后一行权限正常，问题在它上面的某一行。**转向哪一步**：确认是路径层之后，去看访问者有没有落在该层目录的属主/属组/other 任一类里。

### 2.3 ACL：`getfacl` 的 `mask` 与 `#effective`

```bash
getfacl -cp /srv/app/config          # 验证：去掉注释头的完整 ACL
```

四类行：`user::`（属主）、`user:<名字>:`（named user）、`group::`（属组）、`mask::`，末尾还有一个 `other::`；有默认 ACL 时前面会多一组 `default:`。

- **`mask` 是 named 条目与 owning group 的有效权限上限**；`#effective:` 是取交集后的实际结果。**判据**：named 条目写着 `rwx` 而 `#effective` 是 `r--`，瓶颈是 `mask`，重复 `setfacl` 无效。
- **与谁同看**：`ls -l` —— **有 ACL 时它的属组三位显示的就是 `mask`**。
- **转向哪一步**：`setfacl -m m::<权限>` 修正 `mask`，再复查 `#effective`；若 `chmod` 与 ACL 混用，改完必须复查，因为 `chmod` 会重算 `mask`。

### 2.4 扩展属性与不可变属性

```bash
lsattr <path>                        # 验证：e 是 ext4 正常 extent 标志，i/a 才是限制
getfattr -d -m - <path>              # 验证：列出全部扩展属性；ACL 不在其中
getcap <path>                        # 验证：文件能力，例如 cap_net_raw=ep
```

- **`ls -l` 结尾的 `+` 只表示有 ACL**：它不表示有其它 xattr，也不显示 ACL 内容；只有 `user.*` xattr 而没有 ACL 的文件不会出现 `+`。**判据**：怀疑「有隐藏属性」时要同时跑 `getfattr -d -m -`、`lsattr`、`getcap` 三条。
- **`getcap` 的输出格式是 `路径 能力=标志`**，标志 `p` 是 Permitted、`e` 是 Effective。**判据**：有输出只代表 xattr 写成功；脚本与 `nosuid` 挂载点上仍然不生效。

### 2.5 提权面：`find -perm` 的三种写法与包反查

```bash
find / -xdev -type f -perm -4000 2>/dev/null | sort   # 验证：SUID 位已置（包含匹配）
find / -xdev -type f -perm /6000 2>/dev/null | sort   # 验证：SUID 或 SGID 任一命中
find / -xdev -type f -perm 4000  2>/dev/null | sort   # 验证：精确匹配，几乎必然为空
```

- **`-perm -4000` 是「包含」、`/6000` 是「任一」、`4000` 是「精确等于」**。**判据**：核查提权面只用前两种；精确写法会漏掉绝大多数（`4755` 是常态）。**与谁同看**：`getcap -r /`（能力）、`find / -xdev \( -nouser -o -nogroup \)`（无主文件）。
- **归属反查**：`dpkg -S <basename>`（Debian 系）或 `rpm -qf <path>`（RHEL 系）。**判据**：按 basename 反查更稳——`/bin` 与 `/usr/bin` 合并的发行版上，包数据库里登记的可能是另一条路径。查不到归属又没有变更记录的提权点，按事件处理。

### 2.6 挂载选项与内核参数

```bash
findmnt -o TARGET,SOURCE,FSTYPE,OPTIONS          # 验证：全量挂载树与每个挂载点的选项
mountpoint -q /tmp && findmnt -T /tmp -o TARGET,SOURCE,FSTYPE,OPTIONS || echo "/tmp 不是独立挂载点"
                                                 # 验证：临时目录有没有自己的挂载选项
sysctl fs.protected_regular fs.protected_fifos kernel.yama.ptrace_scope
                                                 # 验证：一组关键安全参数的当前值
```

- **`nosuid` 让该挂载点上 `execve` 阶段的一切特权授予失效**（SUID/SGID 与 file capabilities）；`noexec` 只拦「直接执行这个文件」。**判据**：排查「SUID 不生效」时，挂载选项是与「位有没有被 `chown` 清掉」并列的一步。
- **`/tmp` 的 `1777` 是权限，不是挂载选项**。**判据**：用 `mountpoint -q` 判断它是否独立挂载；不是的话，它跟着 `/` 的选项，`nosuid`/`noexec` 一个都没有。
- **`sysctl` 的当前值可能不来自任何配置文件**：它可能来自内核/发行版编译默认。**判据/转向**：要判断某个值从哪来，先 `sysctl -n <name>` 取当前值，再遍历 `/etc/sysctl.d/`、`/run/sysctl.d/`、`/usr/lib/sysctl.d/`，承认可能来自默认；`sysctl -w` 只改运行时，持久化必须写文件。

### 2.7 MAC：先确认「这台机器上有什么」

```bash
cat /sys/kernel/security/lsm            # 验证：本机加载了哪些 LSM
aa-status                               # 验证：AppArmor 的 profile 计数与模式
ls -d /sys/fs/selinux 2>/dev/null; command -v getenforce sestatus restorecon
                                        # 验证：这台机器有没有 SELinux（文件系统 + 工具链）
```

- **判据**：`/sys/kernel/security/lsm` 里出现 `apparmor` 说明 MAC 这一支是 AppArmor，出现 `selinux` 才是 SELinux。**两者可以同时存在，也可以都不在。**
- **转向哪一步**：确认实现之后才谈拒绝记录去哪找——SELinux 是 `avc: denied`，AppArmor 是 `apparmor="DENIED"`，两者都以 `type=AVC` 出现。

### 2.8 MAC 拒绝：落点取决于 auditd

```bash
grep 'apparmor="DENIED"' /var/log/audit/audit.log | tail -5
                                        # 验证：auditd 在跑时，AppArmor 拒绝落在这里
ausearch -m AVC </dev/null              # 验证：注意显式断开 stdin；结果受 log_format 影响
dmesg | grep -E 'apparmor="DENIED"|avc:  denied' | tail -5
                                        # 验证：auditd 未运行时才落内核日志；需 root
```

- **判据**：拒绝记录的落点由「auditd 是否在运行」决定，不是固定答案。内核日志里较早的 `type=1400` 多为**引导期策略装载**记录（`apparmor="STATUS"`），不要当成本次事件。
- **`ausearch` 返回空不等于没发生**：它受审计配置影响。**转向哪一步**：用 `grep` 审计原始文件交叉验证；写脚本时**必须显式断开 stdin 或用 `-if`**，否则它可能一直等待输入。

### 2.9 提权与认证的留痕

```bash
sudo -l -U <user>                       # 验证（root）：某个账号的最终生效授权
grep -i sudo /var/log/auth.log | tail -5
                                        # 验证：Debian/Ubuntu 上 sudo 的常见落点（按编译选项而定）
journalctl -g sudo --no-pager -n 5      # 验证：若这台机器的 sudo 走 journald 才会有输出
last -20; lastb -20; loginctl list-sessions
                                        # 验证：成功/失败登录与活跃会话
```

- **sudo 日志的字段**：`USER=` 是以谁的身份执行、`COMMAND=` 是实际命令、`PWD=` 与 `TTY=` 是发起位置，记录前缀是发起者。**判据**：把 `USER=` 当成发起者是最常见的读错方式。
- **落点要用证据确认，不要凭经验断定**：`sudo` 的日志受编译选项（是否 `--with-logging=syslog`、`logfac` 是什么）与 `sudoers` 里有没有配置独立 `logfile=` 影响；`sudo` 本身不是 systemd 服务，所以 `journalctl -u sudo` 通常查不到东西。**转向哪一步**：先 `grep -rn 'logfile\|log_input\|log_output' /etc/sudoers /etc/sudoers.d/`，再按结果决定去看哪个文件。

## 3. 采样纪律与基线

**五类基线**（每一类都要固定字段顺序与命令，输出成可 diff 的文本）：

| 类别 | 采集内容 | 只读？ |
| --- | --- | --- |
| 账号 | `passwd`/`shadow`/`group` 的条数、UID 0 清单、可登录 shell 的账号、`shadow` 密码状态、有效期字段 | 是 |
| 提权面 | `find -perm -4000`/`-2000` 清单与计数、`getcap -r /`、无主文件 | 是 |
| 监听端口 | `ss -lntup` 的监听地址与进程 | 是 |
| 计划任务与自启 | `crontab -l`、`/etc/cron.*`、`systemctl list-timers --all`、enabled 单元 | 是 |
| SSH 授权 | `authorized_keys` 清单与选项、`sshd -T` 的关键项 | 是 |

四条采样纪律：

1. **同一口径**：命令、字段顺序、输出格式固定，否则下次 diff 全是噪声。**带时间戳**，并写明采集时的机器标识。
2. **至少两次**：`find`/`ss` 这类输出是瞬间快照；涉及「有没有在增长」的判断（进程数、连接数、文件数）要间隔取两次。
3. **留原始输出**：把输出存成文件而不是只记结论——结论会忘记依据，原始输出不会。**采集完就复制出本机**，机器起不来时留在本机等于没取。
4. **区分只读与破坏性**：上面五类基线全部是只读的，**生产机上也可以做**。而「造一个 SUID 文件」「挂一个 `nosuid` 的 tmpfs」「改 PAM 或 `sshd_config`」属于变更，**只在可快照的实验机上做**，并且做之前留一个已登录的带外会话——改 PAM 与 SSH 有把自己锁在门外的风险。

**基线卡的字段**：机器标识与用途、采集时间（含时区）、发行版与内核版本、五类基线的原始输出或摘要与计数、`sshd -T` 的关键项、挂载树与关键 `sysctl` 的当前值、以及每一项的采集命令。用途是定义「正常」，**回填时机是每次变更收口时**——过期的基线比没有更危险。

## 常见故障与排查方向

每个场景给具象处境、排查顺序与合格回答的结构。

### 场景一：服务日志出现 `EACCES`，文件 mode 完全正常

**处境**：一台 4 vCPU / 8 GiB 的机器上，`nginx` 以 `www-data` 运行，读 `/srv/app/config`（`644 root:root`）报 `Permission denied`，业务间歇失败，从 10:20 开始。

**排查顺序**：

1. `namei -l /srv/app/config` → 若中间某级目录是 `700 root:root`，问题已定位在**路径层**；
2. `id www-data` 与 `getfacl -cp /srv/app/config` → 确认属主/属组/other 与 ACL `mask`；
3. `findmnt -T /srv/app -o TARGET,FSTYPE,OPTIONS` → 排除挂载选项；
4. `grep -E 'apparmor="DENIED"|avc:  denied' /var/log/audit/audit.log | tail` 或 `ausearch -m AVC </dev/null` → 排除 MAC；
5. 只有前四步都排除后，才考虑改属主或 ACL。

**一份合格的回答长什么样**：结论（卡在哪一层）＋依据（哪条命令的哪一行）＋边界（这条结论只在当前挂载与策略下成立）＋动作（最小改动：补目录 `x`、把服务账号加入属组、或修 `mask`，并说明不改什么）。**第一反应不要做**：不要 `chmod -R 777`，它同时开放写与执行，把一个权限问题变成提权问题。

### 场景二：所有文件权限都对，报错却是 `Operation not permitted`

**处境**：一个自研程序以普通用户运行，申请原始套接字失败，报错是 `Operation not permitted`（不是 `Permission denied`）。

**排查顺序**：

1. 记下 `errno`（`EPERM` 与 `EACCES` 指向不同层）；
2. `getcap <bin>` 与 `getpcaps <pid>` → 看是否缺少对应 capability；
3. `lsattr <file>` → 排除只读/不可变属性；
4. `getenforce`/`aa-status` 与审计日志 → 排除 MAC；
5. `findmnt -T <path>` → 排除 `nosuid` 导致的 file capabilities 失效。

**合格回答**：给出「缺哪一项能力」或「被哪一层拒绝」的具体证据，并说明修法是加一项能力（文件能力或 systemd 能力）而不是把程序改成 root。**第一反应不要做**：不要用 `sudo` 或改 root 来绕过——那会用整个 root 换一项能力。

### 场景三：设了 SUID 却不生效

**处境**：一个内部工具 `chmod 4755` 后，普通用户执行时身份没有变化。

**排查顺序**：`stat -c "%a %A %n" <file>`（位是否还在；`chown` 之后会清掉）→ `file <path>`（是不是 ELF，脚本上的 SUID 本就不生效）→ `findmnt -T <file> -o OPTIONS`（挂载点是否 `nosuid`）→ 执行环境是否设置了 `no_new_privs` 或被 `ptrace`。

**合格回答**：指出失效的具体条件，并给出替代方案（systemd 的 `AmbientCapabilities=`/`CapabilityBoundingSet=` 或文件能力）。**第一反应不要做**：不要为了让它生效而把中间目录的 `nosuid` 去掉——那会扩大整个挂载点的提权面。

### 场景四：提权面盘点发现多了一个 SUID 文件

**处境**：巡检发现 `/usr/local/bin/backup` mode `4755`，`dpkg -S backup` 没有任何输出，`/usr/local/bin` 最近一次变更时间不明。

**排查顺序**：`stat` 取时间与属主 → 计算哈希并记入台账 → `file` 看类型 → 查变更记录与工单 → 与同类机器基线对比 → 仍无法解释则按事件处理（先保全、再隔离、再判定）。

**合格回答**：给出「它属于哪个包/哪次变更」或「无法解释，已按事件上报」二选一，并附上已保全的证据清单。**第一反应不要做**：不要直接 `chmod 755` 了事——那会销毁「它曾经是什么」的证据，也不回答「还有没有别的」。

### 场景五：普通用户绑定 80 端口失败

**处境**：一个非 root 服务需要绑 80，报 `EACCES`。

**排查顺序**：`sysctl net.ipv4.ip_unprivileged_port_start`（确认阈值）→ `getcap <bin>`（文件是否已带 `cap_net_bind_service`）→ 确认服务的启动方式（若是 systemd，看 `AmbientCapabilities=`/`CapabilityBoundingSet=`）。

**合格回答**：在四种做法里选一种并说明边界——反向代理/socket 激活（业务进程完全不碰特权端口，首选）、systemd 能力（能力随 unit，可审计）、文件能力（二进制被替换即等于能力被转移）、root 运行（不推荐）。**第一反应不要做**：不要把 `ip_unprivileged_port_start` 改成 0——那是为单个服务改动整机策略。

### 场景六：`sudo` 提示不在 sudoers 文件中

**处境**：某账号执行 `sudo` 报 `not in the sudoers file`，此前一直能用。

**排查顺序**：`id <user>`（组是否还在）→ `sudo -l -U <user>`（最终生效授权，注意可能来自多个 `sudoers.d` 文件）→ `visudo -c`（语法）→ `ls -l /etc/sudoers /etc/sudoers.d/`（权限是否为 `0440`，目录里的文件是否被 `@includedir` 覆盖）。

**合格回答**：区分「授权被移除」「组成员变更」「语法错误导致整份文件失效」「文件权限不对被忽略」四种成因之一，并给出复测命令。**第一反应不要做**：不要直接加 `ALL=(ALL) NOPASSWD: ALL`——那等于交出任意命令执行能力。

### 场景七：SSH 能连，但新配置不生效

**处境**：在 `sshd_config` 里关掉了密码登录并 `systemctl reload ssh`，测试机仍能用密码登录某账号。

**排查顺序**：`sshd -T | grep -E '^(passwordauthentication|permitrootlogin|pubkeyauthentication|maxauthtries)'`（生效值）→ `grep -n Include /etc/ssh/sshd_config`（`Include` 的位置）→ `ls /etc/ssh/sshd_config.d/`（drop-in 里的同名项）→ `sshd -T -C user=<u>,addr=<ip>,host=<h>`（`Match` 之后的最终值）→ 确认改的是不是生效文件。

**合格回答**：指出覆盖来源（drop-in 还是 `Match`），说明「同名关键字先读到者生效」，并给出验收方式（`sshd -T` 的目标项确实变成期望值、服务仍在监听）。**第一反应不要做**：不要反复 reload——配置解析结果不会因为 reload 改变。

### 场景八：服务在 `enforcing` 下起不来

**处境**：RHEL 系机器上，服务在 `enforcing` 模式下启动失败，日志里有 `avc: denied`。

**排查顺序**：`ausearch -m AVC </dev/null` 取拒绝 → 判断是标签、端口还是布尔值问题（`ls -Z`、`semanage port -l`、`getsebool`）→ 能用 `restorecon`/`semanage`/`setsebool` 解决的就不写新策略 → 确需自定义策略时用 `audit2allow` 生成后**人工复核范围** → 切回 `enforcing` 复验。

**合格回答**：给出拒绝的主体、客体、`class` 与权限，以及最小修复动作与复验方式。**第一反应不要做**：不要把 `setenforce 0` 当修复——拒绝记录照常产生，攻击面回到 DAC，而且容易忘记切回。

### 场景九：怀疑机器被入侵

**处境**：监控发现机器上多了一个未知的 systemd timer，每 10 分钟执行 `/tmp/.x`。

**排查顺序**：先隔离（云上先做磁盘快照再收网络）→ 保全（**不要重启、不要 `kill -9`、不要删文件**）→ 取内存侧证据：`ps --forest auxf`、`ss -antup`、`ls -l /proc/<pid>/exe /proc/<pid>/cwd`、`cat /proc/<pid>/environ | tr '\0' '\n'` → 取持久化点：cron/timer/enabled 单元、`authorized_keys`、shell 启动文件、`/etc/ld.so.preload`、PAM 与单元配置 → 用变更记录与日志拼时间线 → 判定影响面 → 恢复或重建（被 root 完全控制的机器以重建为准，重建前轮换同批机器共用的全部凭据）。

**合格回答**：一份含「时间线、影响面、证据位置、待办项」的记录，而不是「已清理」三个字。**第一反应不要做**：不要急着重装或重启——那会把内存侧证据一起清掉。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 用 `find -perm 4000` 采集 SUID 基线 | 精确匹配几乎必然为空，基线等于没采 |
| 只采集 SUID 不采集 file capabilities | 带能力的文件在 `ls -l` 上没有任何痕迹，会整类漏掉 |
| 基线只记结论不记原始输出 | 无法复查与 diff；结论失去依据 |
| 用手指敲命令、看完就丢 | 下一次异常出现时没有可比对象 |
| 在 `/var/log` 上批量 `chattr +i` 防篡改 | 轮转与升级失败，磁盘被日志写满 |
| 用 `chmod -R 777` 处理 `EACCES` | 同时开放写与执行，扩大提权面 |
| 把 `ausearch` 的空结果当「没发生」 | 结果受审计配置影响，要用 `grep` 原始文件交叉验证 |
| 在非 root 下跑 `dpkg -V` 看到 `?????????` 就报「被改了」 | 多为权限不足，要用 root 复核 |
| 在生产机上试改 PAM 或 `sshd_config` | 可能把自己锁在门外；先在副本上校验，再留带外会话落地 |
| 把只读基线当成「不需要授权就能做」的动作 | 基线本身只读，但采集脚本要有人负责、有存放位置、有保留期 |

## 要点自测

**问：想在一台机器上完成五类安全基线，哪几类可以只读完成？**
答：全部五类——账号、提权面、监听端口、计划任务与自启、SSH 授权——都是只读查询，**生产机上也可以做**。需要写权限的是与之相关的变更动作（建测试账号、造 SUID 文件、挂临时 tmpfs、改 PAM/`sshd_config`），那些要留在可快照的实验机上做。

**问：`getfacl` 的输出里，判断「授权为什么没生效」看哪个字段？**
答：看 `mask::` 与 named 条目后面的 `#effective:`。`mask` 是有效权限上限，`#effective` 是取交集后的实际结果；只有 `#effective` 才反映真实生效的权限。

**问：`/proc/<pid>/status` 的 `Uid:` 那一行有四个数，它们分别是什么？**
答：real / effective / saved / filesystem，即真实身份、有效身份（权限判定看它）、保存身份与文件系统访问专用身份。`sudo` 或 SUID 程序运行期间它们可能互不相同。

**问：为什么提权面基线必须同时采 `find -perm -4000` 与 `getcap -r /`？**
答：现代发行版把不少原本 SUID 的工具改成了 file capabilities，这类文件在 `ls -l` 上完全看不出痕迹。只采 SUID 会整类漏掉提权点。

**问：判断「这台机器上 MAC 拒绝记录在哪」，先要确认什么？**
答：先确认这台机器上加载了哪些 LSM（`/sys/kernel/security/lsm`），再确认 auditd 是否在运行——运行则拒绝落审计日志，不运行才落内核日志。此外查询工具受审计配置影响，`ausearch` 返回空需要 `grep` 原始文件交叉验证。

**问：判断一个 `sysctl` 的值从哪来，按什么顺序查？**
答：先 `sysctl -n <name>` 取当前值，再遍历 `/etc/sysctl.d/`、`/run/sysctl.d/`、`/usr/lib/sysctl.d/`（以及 `/etc/sysctl.conf` 的软链），如果都没有，就承认它来自内核或发行版编译默认——这是正常情况，不是配置错误。

**第一反应不要做什么**：不要在没留带外会话的情况下改 PAM 或 SSH 配置；不要在只读就能完成的核查里执行写操作；不要把一次采集的清单当基线。
