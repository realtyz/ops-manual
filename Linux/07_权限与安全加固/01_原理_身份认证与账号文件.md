# 身份、认证与账号文件

## 1. 如果内核只认「用户名」，会同时出四件事

用户登录时敲的是名字，但内核在每一次权限判定里用的是 32 位整数。假设一个系统真的按名字认人，四件事会立刻发生：

**改个名字就等于换个人。** 名字是可写的文本，谁有权限改账号文件谁就能变成别人；而权限判定必须建立在一个不可被随意改写、且能作为文件属主记录下来的量上。

**一个身份可以用多个名字。** 同一个「人」在不同服务里可能叫 `alice`、`a.li`、`alice@corp`。要么系统为每个别名维护一套权限，要么必须有一个唯一键把它们收在一起。

**判定结果无法落盘。** 文件属主、进程身份、审计记录都要能在磁盘上保存并在重启后一致。存一个整数只要 4 字节，存字符串要考虑编码、长度与比较规则。

**数值 0 必须只有一个含义。** 系统里总是需要一个「不受任何限制」的身份。如果这个身份靠名字识别，那么任何名字写对的人都能获得它。

所以四件事指向同一个设计：**身份是一个数值，名字只是查表得到的外壳。** 这条设计有一个直接推论，也是安全问题里最高优先级的一类现象——**一个名字不叫 `root` 的账号，只要它的 UID 是 0，它就是完整的超级用户。**

## 2. 一次身份判定的完整输入

内核在判定「这个进程是谁」时，读的不是一个 UID，而是一组：

| 量 | 含义 | 为什么单独留一份 |
| --- | --- | --- |
| `ruid` / `rgid` | 真实身份，来自登录时的账号 | 决定「谁在负责」，`su`/`sudo` 之后仍能查出来 |
| `euid` / `egid` | **有效身份**，绝大多数权限判定看它 | SUID 换的就是它；它使「以别人身份执行」成为可能 |
| `suid` / `sgid` | 保存的有效身份，用于在权限间来回切换 | 让程序能临时提权再降回来，而不用保留 root 全程运行 |
| `fsuid` / `fsgid` | 文件系统访问专用的有效身份 | 历史上为了让用户态文件服务器能在「代表某用户」时不被信号打断而独立出来 |
| 附加组 | `/etc/group` 成员列表里的全部组 | 权限判定时**所有组一起参与**，一个文件可被多组共享 |
| capabilities | 细分的特权集合 | root 的「全有」被拆成 41 项，可只授其中一项 |

两个容易混的边界：**`ruid` 与 `euid` 不同**正是 `passwd` 这类程序能工作的原因（普通用户运行它时 `euid` 暂时变成 0）；**附加组没有对应的「有效组」概念**，`newgrp` 改的是登录会话的组列表，不是权限判定里的某个临时字段。

## 3. 账号从哪里来：NSS 决定去哪查

「账号存在」这件事由 **NSS（Name Service Switch，名字服务开关）** 决定，配置在 `nsswitch.conf`。它规定每一类名字按什么顺序、去哪些来源查：

```text
passwd:         files systemd
group:          files systemd
shadow:         files
```

`files` 指本地 `/etc/passwd`、`/etc/group`、`/etc/shadow`；`sss`/`ldap` 指远端目录服务。这条配置给出一个操作性结论：**企业环境里账号可能在远端，判断「这个账号存不存在、UID 是多少」要用 `getent`，而不是 `grep /etc/passwd`。** `getent` 走 NSS 顺序，`grep` 只看一个本地文件。

本地三份文件的分工：

| 文件 | 内容 | 记录格式 | 谁需要读 |
| --- | --- | --- | --- |
| `/etc/passwd` | 账号名、UID、主 GID、GECOS、家目录、登录 shell | 7 个字段，第 2 字段固定为 `x` | 所有人（名字与 UID 要被反复查） |
| `/etc/group` | 组名、GID、附加成员列表 | 4 个字段，成员列表**不含主组** | 所有人 |
| `/etc/shadow` | 密码哈希与账号有效期 | 9 个字段 | 只有 root 与 `shadow` 组 |

`/etc/passwd` 必须世界可读，因为几乎所有程序都要把 UID 换成名字；它因此不能放密码哈希。**账号与凭据分家的原因是访问模式不同**：前者要被频繁、广泛地读，后者只能被极少数的认证路径读。这个分离是 `/etc/shadow` 存在的全部理由——把哈希从世界可读的文件里挪到一个只有认证组件能读的文件里，离线爆破的门槛才从「读到文件」变成「先拿到 root」。

**要自己验证这三份文件与 NSS 的关系，用 `getent` 而不是直接读文件**：`getent` 会按 `nsswitch.conf` 的顺序去问，直接 `cat`/`grep` 只看得到一个来源。判断某个账号是否存在、UID 是多少，以这条路径的结果为准；`/etc/shadow` 的隔离也可以用同一思路验证——用普通身份去读它，应当被拒。

## 4. 账号与凭据是两套有效期

`/etc/shadow` 的第 3~8 字段全是时间，它们分属两条互不相干的时钟：

| 字段 | 管什么 | `shadow(5)` 文档中的典型默认 |
| --- | --- | --- |
| 第 3 字段 上次改密日期 | 从 1970-01-01 起的天数 | 记录用 |
| 第 4 字段 最小改密间隔 | 多少天内不许再改，防止改回旧密码 | `0` |
| 第 5 字段 最大有效期 | 密码最多用多少天 | 见下 |
| 第 6 字段 到期提醒 | 提前多少天开始提醒 | `7` |
| 第 7 字段 到期后禁用宽限 | 密码过期后还给几天宽限（`-1` 表示一直给） | `-1` |
| 第 8 字段 账号过期日期 | 到这个日期账号整体不可用（空表示不过期） | 空 |

表中的值是 `shadow(5)` 描述的形态，**一台机器上的实际取值必须现场读**：用 `passwd -S` 或 `chage -l` 看某个账号，或直接读 `/etc/shadow` 的第 4~8 字段。`/etc/login.defs` 只决定新建账号时这些字段填什么，不决定存量账号的当前值。

**密码过期与账号过期是两条独立的时钟。** 前者由第 5 字段与 `chage` 控制，到期后用户仍能登录但被要求改密码（宽限期内）；后者由第 8 字段控制，到期后连认证都不再通过。做离职处置时用错字段，就会出现「账号已过期却能登录」或「密码过期导致服务账号失效」两类事故。

两组默认值必须分开看：

- **`/etc/login.defs`** 里的 `PASS_MAX_DAYS`、`PASS_MIN_DAYS`、`PASS_WARN_AGE`、`UMASK`、`ENCRYPT_METHOD` 是**新建账号时工具的默认值来源**。改它**不会回头修改已存在的账号**——那些值已经写在各账号的 `shadow` 记录里了。要让存量账号收紧，必须逐条用 `chage` 或 `usermod` 处理。
- **`useradd -D`** 打印的是 `useradd` 当前生效的默认值，它综合了 `login.defs` 与编译默认。两者在 `INACTIVE` 这类项上并不一致：`INACTIVE` 出现在 `useradd -D` 的输出里，却不一定是 `login.defs` 里的一个配置项。**要判断某个默认值从哪来，先确认它在哪份文件里能查到，不要假设两条路径同源。**

**验算这组默认值的方法**：把 `useradd -D` 的输出与 `/etc/login.defs` 的实际行并排看一遍，就会发现两者并不一一对应——`login.defs` 里被注释掉或根本不存在的项，仍然会出现在 `useradd -D` 的输出里（它有编译默认）。判断某个值的来源，先确认它在哪份文件里能查到。

**锁定、停用、删除是三个不同力度的动作。** 锁定指在密码哈希前加 `!`，它只让**密码认证**这一条路失效；停用指设账号过期日期（`usermod -e 1` 或 `chage -E 0`），它让所有走 PAM `account` 栈的入口失效；删除是移除账号记录本身。三者都不触碰公钥、`sudoers`、已存在会话——**加 `!` 之后仍然能用公钥登录，这件事是设计使然，不是 bug。**

## 5. PAM：把「认证」拆成四条栈

登录、`su`、`sudo`、`sshd`、屏幕解锁各自需要认证，但它们要检查的东西不完全一样。PAM（Pluggable Authentication Modules，可插拔认证模块）的做法是：把认证过程拆成**四类栈**，每类栈由若干模块按顺序执行，每个模块返回成功/失败/忽略，由控制标志决定怎么合并。

| 栈 | 回答的问题 | 典型模块 | 什么时候执行 |
| --- | --- | --- | --- |
| `auth` | 你是谁、凭据对不对 | `pam_unix`、`pam_faillock` | 认证时 |
| `account` | 你现在是否**允许**登录（账号过期、时段、来源） | `pam_unix`、`pam_nologin`、`pam_access` | 认证之后、建会话之前 |
| `password` | 改密码要满足什么规则 | `pam_unix`、`pam_pwquality`、`pam_pwhistory` | 改密码时 |
| `session` | 登录后准备什么环境与资源 | `pam_umask`、`pam_limits`、`pam_systemd` | 会话建立与销毁时 |

一条配置行的结构是 `type control module-path module-arguments`。控制标志里最需要分清的是三种：

- `requisite`：失败立即返回，后面的模块不再执行——用来「一旦不通过就马上停」；
- `required`：失败也继续执行完整个栈，最终仍返回失败——**它不缩短流程，是为了不泄露「哪一步失败」**；
- `sufficient`：成功则跳过本栈剩余模块——常见的「先试本地文件，再试远端目录」结构。

`[success=N default=ignore]` 这类写法是按模块返回码跳转，现代发行版的服务栈里很常见。**栈的语义是「按顺序执行 + 按控制标志合并」，所以模块顺序本身即是策略的一部分**；把两行指令顺序对调，行为可能完全不同。

三类落点要分清：

- **`/etc/pam.d/<service>`** 是各服务的栈（`sshd`、`login`、`sudo`、`su` 各一份），Debian/Ubuntu 上通常再拆出 `common-auth`/`common-account`/`common-password`/`common-session` 被各服务 `@include`；
- **策略模块自己的配置文件**（`faillock.conf`、`pwquality.conf`、`limits.conf`、`login.defs`）只提供参数，**它们被不被引用取决于栈里有没有对应模块**；
- **RHEL 系另有 `authselect`/`authconfig`** 统一管理这些文件，直接手改 `/etc/pam.d/` 会被它覆盖。

**「配置文件存在」与「策略生效」之间隔着一步引用。** 这是安全加固里最常见的假完成：文件写好了、参数看着对，但栈里没有那个模块，实际行为一点没变。验收方式不是看文件，而是看**引用链**：`grep -rl <模块名> /etc/pam.d`，或直接用一次真实登录复现。

## 6. 抽象在哪里漏水

**名字与数值的映射会过期。** 删掉账号后，它拥有过的文件仍在磁盘上，只是属主渲染成一个数字；反过来，同名的第二个账号会「继承」前一个账号留下的所有权限。UID 复用是真实存在的风险，处置离职账号时要先归置文件而不是先删账号。

**「账号存在」有三个不同的答案。** NSS 说它存在、`shadow` 里有它的记录、它能通过 PAM 的 `account` 栈——这三件事可以互相独立。审计脚本如果只看其中一个来源，会漏掉另外两种情况。

**`euid` 是判定身份，但它不是「人」。** 一条 `sudo` 命令的 `ruid` 是原用户、`euid` 是 0；日志里因此既有发起者也有执行身份。只看其中一个字段，就会出现「明明是 A 干的，日志写着 root」或相反。

**PAM 的可组合性会带来顺序陷阱。** 两个模块都写进同一条栈时，谁在前谁在后决定了行为；而发行版升级可能替换整份 `common-*` 文件。**只备份自己改动的那一行不够，还要能回答「升级之后我这一行还在不在」。**

## 常见误解

| 常见说法 | 事实 |
| --- | --- |
| 「不是叫 root 的账号就不是超级用户」 | 内核只看 UID 数值；任何 UID 0 的账号都是完整超级用户 |
| 「`/etc/passwd` 第 2 字段的 `x` 是密码」 | 它只是占位符，表示真实哈希在 `/etc/shadow` |
| 「改了 `login.defs` 就收紧了所有账号」 | 它是新建/工具的默认值来源，存量账号的值已经写在各自的 `shadow` 记录里 |
| 「`passwd -l` 就是停用账号」 | 它只锁密码这条路；公钥、`NOPASSWD` 的 sudo、已有会话都不受影响 |
| 「`useradd -D` 打印的就是 `login.defs` 的内容」 | 它综合了 `login.defs` 与编译默认；个别项只在其中一处出现（例如 `INACTIVE`） |
| 「能用 `grep /etc/passwd` 找到就说明账号存在、找不到就说明不存在」 | NSS 可能把查询发给 LDAP/SSSD；判断要用 `getent` |
| 「`usermod -G` 是加组」 | 它**替换**附加组列表，加组要用 `-aG` |
| 「PAM 配置里写了模块就一定生效」 | 生效取决于栈里有没有引用它；RHEL 系还要看 `authselect` 是否覆盖 |
| 「账号过期和密码过期是一回事」 | 前者走 `account` 栈，后者是密码有效期的宽限逻辑；处置离职账号要用账号过期 |

## 要点自测

**问：内核为什么不用用户名做判定？**
答：名字可改写、可重复、不便落盘，而且必须保证「某一个身份不受限制」这件事不能被名字冒充。身份是数值、名字是查表结果，这条设计直接推出「非 root 名字的 UID 0 账号同样危险」。

**问：`/etc/passwd` 为什么必须世界可读，而 `/etc/shadow` 不能？**
答：几乎所有程序都要把 UID 换成名字来显示，所以 `passwd` 必须广泛可读，因此不能放哈希；认证只需要极少数组件参与，把哈希挪进 `shadow` 后，离线爆破的门槛从「读到文件」变成「先拿到 root」。这是访问模式不同导致的分家。

**问：`ruid`、`euid`、`fsuid` 分别在什么时候起作用？**
答：`ruid` 记录真实身份、决定「谁在负责」；`euid` 决定绝大多数权限判定，SUID 换的就是它；`fsuid` 是文件系统访问专用的有效身份，历史上为了让用户态文件服务器能代表某用户访问而独立出来。三者在 `sudo` 或 SUID 程序运行期间可能互不相同。

**问：改了 `login.defs` 的 `PASS_MAX_DAYS`，为什么存量账号没变？**
答：`login.defs` 是 `useradd`、`chage` 一类工具取默认值的地方；已有账号的有效期已经写在各自的 `shadow` 记录里，没有回写机制。收紧存量必须逐条 `chage`/`usermod`。

**问：PAM 的 `required` 与 `requisite` 差别在哪，为什么要有 `required`？**
答：`requisite` 失败立即返回，`required` 失败仍执行完整个栈再返回失败。`required` 的存在是为了不让攻击者从「响应快慢」或「是否继续询问」推断出哪一步失败。

**问：怎么证明一条 PAM 策略真的生效了？**
答：不看文件，先看引用链 `grep -rl <模块名> /etc/pam.d`，再用一次真实登录或一次故意的失败去复现。文件存在与策略生效之间隔着「有没有被栈引用」这一步，RHEL 系还要确认 `authselect` 没有覆盖。

**第一反应不要做什么**：不要用账号名判断权限级别；不要把 `passwd -l` 当成离职流程的全部；不要在只改了配置文件后就宣布加固完成。
