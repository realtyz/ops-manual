## 0. 30 秒速览

> [!abstract] 这本手册的六条通用原则
> - **先定影响面，再动手**：哪些账号/服务/机器受影响，什么时候开始（对齐变更时间线）。
> - **先取证，再止损**：重启服务、删文件会清掉认证日志和现场。
> - **按层排除**：DAC → ACL → capabilities → 挂载选项 → MAC。
> - **用证据说话**：`namei`、`getfacl`、`getcap`、`ausearch`、基线 diff。
> - **先隔离，再清理**：入侵场景不关机、不重启、不急着重装。
> - **每条处置都写下来**：现象、证据、动作、结果，作为 Runbook 原料。

## 1. 文件权限看着对，服务仍 `Permission denied`

> [!tip] 第一反应不要是 `chmod -R 777`

```bash
namei -l /srv/app/config
getfacl -cp /srv/app/config
findmnt -o TARGET,SOURCE,FSTYPE,OPTIONS /srv
ausearch -m AVC -ts recent 2>/dev/null || true
```

按路径缺 `x`、ACL mask、挂载选项、SELinux/AppArmor 顺序排除，再最小改动。

## 2. 删不掉文件

```bash
ls -ld /path/to/dir
stat -c "%a %A %u %g %n" /path/to/dir
lsattr /path/to/dir /path/to/file
```

看目录 `w`/`x`、sticky 位、`chattr +i`。不要 `chmod 777` 整个目录。

## 3. 多出 SUID/SGID 或 capability 文件

```bash
find / -xdev -type f \( -perm -4000 -o -perm -2000 \) 2>/dev/null
getcap -r / 2>/dev/null
dpkg -S <basename> 2>/dev/null || rpm -qf <path> 2>/dev/null
```

与基线 diff；查不到归属、无变更记录就按事件处理。

## 4. 普通用户绑 80 失败

```bash
getcap /path/to/program
sysctl net.ipv4.ip_unprivileged_port_start
```

用反向代理或 systemd `AmbientCapabilities`；不要改 `ip_unprivileged_port_start=0`。

## 5. `sudo` 报「不在 sudoers 文件中」

```bash
id
sudo -l 2>&1
visudo -c 2>&1
```

先确认账号、组、sudoers 语法；不要直接给 `ALL=(ALL) NOPASSWD: ALL`。

## 6. SSH 配置不生效

```bash
sshd -t
sshd -T | grep -E '^(permitrootlogin|passwordauthentication|pubkeyauthentication)'
sshd -T -C user=ops,addr=10.0.0.1 | grep -E '^(passwordauthentication|maxauthtries)'
```

看 `Include`/`Match`/重复项；不要只 reload 就完事。

## 7. SELinux/AppArmor 挡住服务

```bash
getenforce 2>/dev/null || true
ausearch -m AVC -ts recent 2>/dev/null || true
aa-status 2>/dev/null || true
journalctl -k -g 'avc|apparmor' 2>/dev/null || true
```

先找拒绝，再修上下文/端口/布尔值；确需才补策略；不要 `setenforce 0` 当修复。

## 8. 账号「已锁定」但还能登录

```bash
getent shadow someuser
find /home/someuser -name authorized_keys -print
sudo -l -U someuser 2>/dev/null
who; loginctl list-sessions
```

密码锁只挡密码；还要清公钥、sudoers、会话。

## 9. 怀疑被入侵

```bash
ps --forest auxf
ss -antup
ls -l /proc/<pid>/exe /proc/<pid>/cwd 2>/dev/null
last -20; lastb -20
```

按 14 号子笔记的「隔离 → 保全 → 取证 → 判定 → 恢复/重建」执行。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 遇到 `EACCES` 先 `chmod -R 777` | 扩大提权面 |
| 入侵后先重启/关机 | 毁掉内存证据 |
| 只跑 `find -perm -4000` 就宣布干净 | 漏掉 capabilities/可写脚本/SSH 钥匙 |
| 改 PAM/SSH 前不留带外会话 | 可能把自己锁在门外 |
| 用「感觉关掉了」当加固结论 | 没有基线，无法核查 |

## 决策练习

> [!question]- 场景：服务日志持续出现 `avc: denied`，但业务目前看似正常。同事说「先观察」。你怎么办？
> A. 观察，不处理
> B. 立即取 AVC 拒绝的时间、主体、客体、class 与权限，判断是标签错、端口错还是策略缺；能最小修复就修，并回 `enforcing` 复验
> C. 直接 `setenforce 0` 让日志消失
>
> **答案：B。**
> A 可能在某个流量/路径组合下演变成业务故障。
> C 关闭强制边界，且只是掩盖证据。
> B 是正解：**AVC 拒绝是明确的信号，要在影响扩大前定位并修复。**

## 要点自测

> [!question]- 服务 `Permission denied` 的最小排除顺序是什么？
> - `namei -l` 路径 → `getfacl` ACL → `findmnt` 挂载选项 → `ausearch`/`aa-status` MAC。
> - **第一反应不要是什么**：不要直接改最后一级文件 mode。

> [!question]- 为什么入侵现场不关机、不重启？
> - 内存中还有进程、连接、环境变量等证据，关机/重启会销毁。
> - 先快照、隔离、保全内存侧证据。
> - **第一反应不要是什么**：不要为了「恢复服务」急着重启。

> [!question]- 手册里所有处置为什么要写记录？
> - 现象、证据、动作、结果可复盘，可沉淀 Runbook，可证明操作可追溯。
> - **第一反应不要是什么**：不要只口头说「已经处理好了」。
