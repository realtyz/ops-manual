## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **五类基线**：账号、SUID/SGID/capabilities、监听端口、计划任务与自启、SSH 授权文件；每类都要留档并与上次比对。
> - **auditd 规则分两类**：文件监控 `-w`、系统调用 `-a`；持久化放 `/etc/audit/rules.d/`。
> - **`history` 不是审计证据**：它只是交互 shell 的历史，可以被跳过、清空、不写。
> - **文件完整性用包数据库校验**：Debian 系 `dpkg -V`，RHEL 系 `rpm -Va`；非 root 跑会出现 `?????????`。
> - **入侵处置顺序是隔离 → 保全 → 取证 → 判定 → 恢复/重建**：不关机、不重启、不 `kill -9`、不急着重装。

## 1. 五类基线核查

```bash
awk -F: '$3==0 {print}' /etc/passwd
awk -F: '$3>=1000 && $3<65534 {print $1,$3,$7}' /etc/passwd
                               # 验证：账号基线，UID 0 与人类账号
find / -xdev -type f \( -perm -4000 -o -perm -2000 \) 2>/dev/null
getcap -r / 2>/dev/null
                               # 验证：提权面基线，SUID/SGID + capabilities
ss -lntup
                               # 验证：监听端口基线
crontab -l; ls -l /etc/cron.d /etc/cron.daily /etc/cron.hourly
systemctl list-timers --all --no-pager
systemctl list-unit-files --state=enabled --no-pager
                               # 验证：计划任务与自启基线
find /home /root -name authorized_keys -print 2>/dev/null
sshd -T | grep -E '^(permitrootlogin|passwordauthentication|pubkeyauthentication)'
                               # 验证：SSH 授权与生效配置基线
```

> [!important] 基线的价值在于「与上次比」
> 单次跑完只能得到一份清单。真正的异常是**多一个账号、多一个 SUID 文件、多一个监听端口、多一个 timer、多一把钥匙**。所以输出要固定字段、写进版本库或台账，定期 diff。

## 2. auditd 规则与容量

```bash
auditctl -l                     # 验证：当前已加载规则
auditctl -w /etc/passwd -p wa -k identity
                               # 验证：临时加一条监控 passwd 写入/属性变化的规则
ausearch -k identity            # 验证：按 key 查审计事件
```

持久化写在 `/etc/audit/rules.d/*.rules`，而不是只敲 `auditctl`。容量参数在 `/etc/auditd.conf`：

```text
max_log_file = 8
num_logs = 5
space_left_action = SYSLOG
disk_full_action = SUSPEND
```

含义：单个日志大小、保留份数、空间不足时动作、磁盘满时动作。**审计日志本身也可能被打满，要有轮转和告警。**

## 3. 登录痕迹

```bash
last -20
lastb -20
who
w
loginctl list-sessions
stat -c "%a %U:%G %n" /var/log/wtmp /var/log/btmp /var/log/lastlog /var/log/auth.log 2>/dev/null
                               # 验证：登录记录与关键日志权限
```

`wtmp` 是成功登录记录，`btmp` 是失败登录记录，`lastlog` 是每个账号最后登录时间。`history` 不可靠：它只是交互 shell 的历史，可以被 `unset HISTFILE`、清空或绕过。

## 4. 文件完整性校验

```bash
dpkg -V                        # Debian 系：校验包文件；未实测非 root 的输出差异
rpm -Va                        # RHEL 系：校验包文件；未在本机实测
dpkg -S <file>                 # 反查文件属于哪个包
```

`dpkg -V` 输出中的 `?????????` 常表示权限不足，不是文件真的被改；`c` 表示配置文件。判断异常前先确认「用 root 跑过、且知道每列含义」。

## 5. 怀疑被入侵：处置顺序

| 顺序 | 动作 | 第一反应不要做什么 |
| --- | --- | --- |
| 1 隔离 | 云上先做磁盘快照，再限制网络（安全组/隔离 VLAN）；保留内存现场 | 不关机、不重启、不 `kill -9`、不急着重装 |
| 2 保全 | 记录时间与操作者；先取内存侧证据：进程、连接、`/proc/<pid>/exe`、环境变量 | 不要在取证据前删木马/账号文件 |
| 3 取证 | 账号、持久化点、提权面、完整性、审计、登录痕迹 | 不要只查 cron，不看 timer/systemd/`ld.so.preload` |
| 4 判定 | 对齐时间线，判断影响面与横向移动范围 | 不要只凭单个文件下结论 |
| 5 恢复/重建 | 被 root 完全控制的机器以重建为准，重建前轮换全部相关凭据 | 不要在原机跑「一键清理」后继续用 |

持久化点清单：`cron`、systemd timer、enabled 服务、`authorized_keys`、shell 启动文件、`/etc/ld.so.preload`、PAM 与服务配置、内核模块。

```bash
ps --forest auxf
ss -antup
ls -l /proc/<pid>/exe /proc/<pid>/cwd
cat /proc/<pid>/environ | tr '\0' '\n'
                               # 验证：进程、连接、可执行文件与环境变量
```

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 把 `history` 当审计证据 | 可被跳过、清空、不写 |
| 只查 cron 不查 timer/systemd | 漏掉 systemd timer 和 enabled 服务持久化 |
| 非 root 跑 `dpkg -V` 看到 `?????????` 就判定被改 | 多为权限不足，要用 root 复核 |
| 入侵后立即关机或重启 | 内存证据丢失，时间线更难恢复 |
| 在原机跑「一键清理」后继续用 | 木马可能已留多个入口，正确做法是重建 |

## 决策练习

> [!question]- 场景：监控发现一台机器多了一个未知 systemd timer，每 10 分钟执行一个 `/tmp/.x` 脚本。你怎么办？
> A. 先删除 timer 和脚本，再通知用户
> B. 先隔离网络、保留进程与文件证据（不删不重启），记录时间线，再按应急流程取证、判定、恢复/重建
> C. 重启机器，看 timer 是否还会出现
>
> **答案：B。**
> A 破坏现场，且可能遗漏其他持久化点。
> C 会清掉内存证据，还可能触发恶意逻辑。
> B 是正解：**先隔离与保全，再取证；处置顺序不能反。**

## 要点自测

> [!question]- 五类基线分别查什么？
> - 账号、提权面（SUID/SGID/capabilities）、监听端口、计划任务与自启、SSH 授权。
> - 每类输出留档，定期 diff。
> - **第一反应不要是什么**：不要只跑一项就宣布机器干净。

> [!question]- 为什么 `history` 不是审计证据？
> - 它只是交互 shell 历史，可被 `unset HISTFILE`、清空或绕过；审计要看 auditd/集中日志。
> - **第一反应不要是什么**：不要用 `history` 判断「没有执行过某命令」。

> [!question]- 入侵处置为什么「不关机、不重启、不 kill -9」？
> - 内存中有进程、连接、环境变量、未落盘的恶意状态，关机会毁掉这些证据。
> - 先做快照、隔离、保全内存侧证据。
> - **第一反应不要是什么**：不要急着重装或重启「恢复正常」。
