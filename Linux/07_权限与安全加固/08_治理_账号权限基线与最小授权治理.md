# 账号权限基线与最小授权治理

## 1. 没有制度时，会怎样

机制与判断可以被一个人掌握，但权限这件事能否稳定地待在安全状态，取决于另一样东西：**制度**。没有制度时，翻车方式是可以预测的五种：

- **权限只加不减。** 每一次需求都对应一次授权，但没有人负责撤销；一两年之后，一台机器上会有大量「不认得但能登录」的账号和过宽的 `sudo` 规则；
- **离职与转岗靠记忆。** 锁密码之后忘了清公钥与 `sudoers`，账号名义上停用、实际仍有通道；
- **加固只做一次。** 上线时按清单加固过，之后升级、装新软件、加新服务都在悄悄改变权限面，没有人回头 diff；
- **出事时没有可比对的「正常」。** 没有留档的基线，「多一个 SUID 文件」与「一直就有」无法区分，只能凭印象判断；
- **临时放宽变成长期状态。** 为了保住业务把 SELinux 切成 `permissive`、把 `ip_unprivileged_port_start` 改成 0、给一个账号 `NOPASSWD`，都没有回收动作与到期时间。

五种方式的共同点是：**它们都不是技术能力问题，而是流程缺位问题。** 技术再熟的人，在凌晨三点、在被电话打断的时候也会漏步骤。制度的作用是把「别漏」从个人品质变成结构约束。

## 2. 上限配在哪一层，责任人是谁

同一个「不许越界」的需求，可以落在不同层，各层的载体、影响范围与变更入口都不同。**治理的第一件事是知道自己在改哪一层。**

| 层 | 载体 | 影响范围 | 改动的落地方式 | 撞上之后的后果 |
| --- | --- | --- | --- | --- |
| 账号 | `/etc/passwd`、`/etc/shadow`、`/etc/group`；`login.defs` 只影响新建 | 某个身份 | `useradd`/`usermod`/`chage` | 账号能登录、能保持有效 |
| 认证策略 | PAM 四类栈 + 策略模块的配置文件 | 某个服务的登录路径 | 改 `/etc/pam.d/<service>`，或 RHEL 系走 `authselect` | 登录被拒或被要求改密 |
| 客体权限 | mode、ACL、xattr | 单个文件/目录 | `chmod`/`chown`/`setfacl`/`chattr` | `EACCES` 或 `EPERM` |
| 特权载体 | SUID/SGID 位、file capabilities | 单个可执行文件 | `chmod u+s`、`setcap` | 执行时身份或能力被提升 |
| 服务最小特权 | unit 的 `User=`/`Group=`/`CapabilityBoundingSet=`/`AmbientCapabilities=`/`NoNewPrivileges=` | 某个服务及其后代 | unit drop-in + `daemon-reload` | 服务缺少能力而起不来，或越界被拒 |
| 强制访问控制 | SELinux 策略与上下文、AppArmor profile | 某类客体或某个程序 | `restorecon`/`semanage`/`setsebool`；profile 装载 | 服务被拒（`avc`/`apparmor="DENIED"`） |
| 系统边界 | 挂载选项、内核安全参数 | 整个文件系统或整机 | `/etc/fstab`、`/etc/sysctl.d/` | 进程缺少能力、工具受限 |

三条使用要点：

1. **优先选影响面小的那一层。** 需要一项能力时选服务属性或文件能力，而不是给整个 root；需要禁止一类执行时先收紧属主与写权限，再考虑整盘 `noexec`；需要低端口时选反向代理，而不是改整机的 `ip_unprivileged_port_start`。
2. **每层都有独立的「正常值」与独立的变更入口。** 账号的正常值是台账，提权面的正常值是清单，系统边界的正常值是挂载树与参数快照。**用一份基线覆盖所有层，等于没有基线。**
3. **落点决定回滚方式。** `sysctl -w` 重启即失效、`chmod` 可以原样改回、`setcap -r` 可以撤销、而「账号已删除」与「审计日志已轮转」不可逆。**不可逆动作必须单独审批并留证据。**

## 3. 行业通行的做法

以下方向来自公开的标准与实践材料，用于对齐思路；**具体阈值必须按自己的环境重新评估**。

- **最小特权与职责分离。** NIST SP 800-53 的访问控制族要求按最小必要授权、按角色分权、并对特权操作单独审计；落地形态就是「服务账号只拿需要的能力」「`sudo` 只授具体命令」「运维动作经堡垒机留痕」。
- **账号生命周期管理。** 账号的创建、变更、停用、删除各有明确触发条件与责任人；离职处置是一组动作（账号过期 + 清理公钥 + 撤销授权 + 终止会话 + 记录），不是一条命令。
- **配置基线与合规核查。** CIS Benchmarks 按发行版给出可核查条目（账号、SSH、权限、日志、内核参数），ISO 27001 一类管理体系要求「基线 + 定期核查 + 偏差处置」的闭环。核查的关键不是清单本身，而是**可重复的采集与 diff**。
- **不可变与防篡改。** 关键文件用 `chattr +i`、只读挂载或完整性校验保护，但要接受它同时挡住正常变更的代价，因此只用于「明确不变且变更流程会先解锁」的对象。
- **审计与留痕。** auditd 规则、集中日志、包数据库校验（`dpkg -V`/`rpm -Va`）构成事后可追溯的基础；**只读观测也可以在采集时做，但采集必须有人负责、有存放位置、有保留期**。
- **演练。** 权限类故障（误改 PAM 把自己锁在外面、写坏 `fstab`、把服务关进 MAC）必须以演练方式覆盖过一遍，并把恢复耗时写进记录；没有演练过的应急预案只能算愿望。

## 4. 落地顺序

权限面的改变一次做太多会无法归因。推荐的推进顺序是四步，每一步都能独立验收：

1. **先摸清现状（只读）**：五类基线采一遍并留档。这一步不改任何东西，但它产出后面所有判断的基准。
2. **先减面，再加固**：删掉不需要的账号与授权、关掉不需要的入口（可登录 shell、密码登录、过宽的 `sudo`、无主的 SUID 文件）。**先做减法，再做加法。**
3. **再收特权粒度**：把「整个 root」替换为按项授权（文件能力或 unit 能力属性），把 `sudo` 的 `ALL` 收成 `Cmnd_Alias`。
4. **最后上强制与系统边界**：MAC 策略在 `complain`/`permissive` 下调好再进强制模式；挂载选项与内核参数在明确影响面之后分批落地。

**每一步都要有变更记录与复测命令**，并保留一个已登录的带外会话——权限类变更最容易造成的后果是「自己也进不去了」。

## 5. 可交付产物与字段

治理的产出是可检查的文件，不是「大家都注意一点」。这套流程涉及七件产物。

### 5.1 账号台账卡

字段：账号名、UID、GID、登录 shell、密码状态（是否可登录）、密码最大有效期、账号过期日期、家目录、附加组、`authorized_keys` 是否存在、`sudo` 授权摘要、**是否认得与来源说明**。

用途：回答「这台机器上有哪些身份、谁还能登录」。**「是否认得」是最关键也最容易被漏掉的一列**——任何不认得且能登录的账号都必须有来源说明。

### 5.2 提权面基线卡

字段（按类别，每类给出清单与计数）：SUID 文件清单、SGID 文件清单、file capabilities 清单与所属包、`sudo` 授权清单、以 root 执行但可被非 root 写的脚本与配置文件、`authorized_keys` 清单与选项、`/etc/ld.so.preload` 是否存在、内核与设备入口参数（如 `kernel.unprivileged_bpf_disabled`）、容器特权使用情况、挂载选项异常项。

用途：回答「从普通身份到 root 有哪些路」。**判据是清单 diff，不是计数**（见判例 16）。

### 5.3 加固核对表

字段：条目、目标状态、当前值、采集命令、是否达标、偏差原因、处置动作、责任人、复核日期。条目按四类分组：账号与入口、权限与提权面、挂载与内核参数、审计与日志。

用途：把「加固过」变成「可逐条复查」。**每条必须带采集命令**，否则无法复核。

### 5.4 最小授权变更单

字段：主体（账号/服务/unit）、载体（哪一层）、现值 → 目标值、依据（基线卡数据或业务需求单）、影响面（谁会受影响、峰值时段）、验证方式（读哪个文件/哪条命令、读到什么算成功）、回滚命令与**回滚触发条件**、时间窗、实际结果。

用途：让另一个人在不问你的情况下能判断这次授权是否必要、是否可回滚、是否已回滚。

### 5.5 MAC 处置记录

字段：现象与服务、`enforcing`/`permissive`（或 `enforce`/`complain`）状态、拒绝证据（主体、客体、`class`、权限、时间戳）、归因（标签/端口/布尔值/策略缺失）、采取的最小动作、复验方式与结果、是否已切回强制模式。

用途：证明「拒绝被修复」而不是「边界被关掉」。

### 5.6 应急演练记录

字段：快照名与时间、破坏动作、现象证据、从弄坏到恢复的耗时、使用的恢复点、以及**哪些环节没有按预期走**。

用途：把「我们以为能恢复」变成「上次实际用了多久」。**恢复耗时是核心字段。**

### 5.7 处置记录

六段：现象与影响面（谁受影响、从几点开始、现在还在不在）→ 已取证据（取到了什么、放在哪里、是否已复制出本机）→ 根因（一句话加支撑证据）→ 止损动作（做了什么、预期与实际）→ 回滚与验收（回滚命令、验收标准、观察了多久）→ 改进项（至少一条，带责任人与期限）。

### 5.8 巡检项

有没有 UID 0 的非预期账号；有没有「密码被锁但仍有公钥/sudo 授权」的账号；`passwd` 与 `shadow` 条目数是否一致；有没有新增或不属于任何包的 SUID/SGID/file capabilities 文件；`sudo` 授权里有没有 `ALL`/`NOPASSWD` 的宽授权；`sshd -T` 的认证项是否符合基线；有没有 `permissive`/`complain` 处于长期状态；有没有服务仍以 root 运行且未收能力；MAC 拒绝日志有没有新增；审计规则与审计容量是否正常；挂载树与关键内核参数是否偏离基线；五类基线的采集是否按期执行、保留期是否足够。

## 6. 接口字段的治理用法

**账号字段要先分清「身份」与「凭据」。** 台账里 `shell` 与 `password status` 是两列不同的风险：`/bin/bash` 的可登录账号要逐个认得，而 `nologin` 不等于停用（公钥仍可能进）。**判据是「有几条通道能进」，不是「shell 是不是 nologin」。**

**`shadow` 的第 8 字段（账号过期）是最可靠的停用它。** 它走 PAM 的 `account` 栈，对所有走 PAM 的入口生效；而密码字段前的 `!` 只关掉密码认证。**离职处置里两者都要做，再叠加清理公钥与会话。**

**`find -perm -4000` 是基线的一半，`getcap -r /` 是另一半。** 现代发行版把不少工具从 SUID 改成 file capabilities，这类文件在 `ls -l` 上没有任何痕迹；只采 SUID 的基线会整类漏掉。

**`sshd -T` 才是 SSH 的「现行有效值」。** 基线里应当记录它而不是配置文件内容；`Include` 的位置与 `Match` 块都会改变最终结果，所以基线还要记 `sshd -T -C` 在关键用户/地址上的取值。

**`systemctl show` 是服务侧权限的读法。** `CapabilityBoundingSet=`/`AmbientCapabilities=`/`NoNewPrivileges=`/`User=`/`Group=` 的**实际生效值**要看 `show`，而不是看 unit 文件里有几行——drop-in 可能覆盖它，模板单元的 `%i` 也会展开成不同结果。

**审计规则要落盘在 `/etc/audit/rules.d/`。** 只敲 `auditctl -w` 重启即失效；同时要盯审计容量（`max_log_file`、`num_logs`、磁盘满时的动作），否则审计本身会成为一次磁盘写满故障。

## 7. 治理场景与产出

### 场景一：一次离职处置

**背景**：一名有生产机器 `sudo` 权限的工程师离职，交接窗口只有一天。

**做法**：先清点他还有哪些通道（`getent shadow` 的密码与过期字段、`authorized_keys`、`sudo -l -U`、活跃会话），再按「先停用、再清授权、最后留台账」的顺序执行；**不要先删账号**，否则文件变成无主，反而更难排查。

**产出**：账号台账卡的更新（状态改为已停用、填上处置时间与执行人）；一条最小授权变更单（撤销 `sudo` 的依据与回滚方式，如果日后需要恢复）；以及一条记录说明该账号是否仍在系统里保留（保留则必须明确过期日期）。

### 场景二：把「整个 root」收成一项能力

**背景**：一个自研服务需要绑定低端口并以 root 运行，安全扫描要求去特权。

**做法**：先确认它真正需要哪些能力（用测试环境逐个能力试，而不是一次给全）；把 unit 改成 `User=` + `CapabilityBoundingSet=` + `AmbientCapabilities=` + `NoNewPrivileges=yes`；改完用 `systemctl show` 核对生效值，并验证业务路径仍然可用。**首选是连特权端口都不碰的反向代理/socket 激活。**

**产出**：最小授权变更单（现值 → 目标值、能力清单与其依据、回滚命令、回滚触发条件）；服务侧权限的基线记录（`systemctl show` 的关键属性快照）。

### 场景三：首次提权面盘点发现一批无主 SUID 文件

**背景**：巡检 40 台机器，发现 6 个 SUID 文件不属于任何发行版包、也没有变更记录。

**做法**：不逐台处理，先在一台上把这一类查清（`stat` 时间、哈希、`file`、来源追查、与同角色机器对比）；确认是遗留产品还是异常；**处置前先保全证据**（哈希与清单），再按批次清理并补上「任何新增提权点必须登记」的流程。

**产出**：提权面基线卡的首次完整版本（每台机器一份）；一张排期表（机器、发现项、判定结论、处置动作、批次、验证方式）；以及一条流程变更记录（新增提权点的登记与审批入口）。

### 场景四：五类基线的常态化巡检

**背景**：五类基线已采集过一次，但没人负责第二次，采集脚本散落在各人的临时目录里。

**做法**：把采集命令固化成可重复的条目（固定字段顺序与输出格式）、明确存放位置与保留期、指定责任人，并把「有没有按期采集」本身列入巡检项。**先做只读采集这一步**——它不需要变更审批，却能立刻产生可比对的历史。

**产出**：一张排期表（机器、采集频率、责任人、存放位置、保留期）；一份巡检项清单；以及第一个 diff 结果（历史没有基线时的第一次采集本身就是基线的起点）。

### 场景五：MAC 拒绝的收口

**背景**：一个服务在 `enforcing` 下被拒，临时切成 `permissive` 保住了业务，三天后仍在 `permissive`。

**做法**：取拒绝证据（主体、客体、`class`、权限、时间戳），判断是标签、端口还是布尔值问题，用最小的 `restorecon`/`semanage`/`setsebool` 动作修复，切回 `enforcing` 复验业务；**每一次「临时放宽」都必须有到期时间与责任人。**

**产出**：MAC 处置记录（含切回强制模式的复验结果）；巡检项里增加「有没有处于长期 `permissive`/`complain`」这一条。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 离职只跑 `passwd -l` | 公钥、`sudo` 授权与已有会话仍可进入；停用要一组动作 |
| 直接 `userdel` 清账号 | 文件变成无主，取证与权限判定更难；先停用与清授权 |
| 权限只加不减 | 一两年后出现大量「不认得但能登录」的账号与过宽授权 |
| 用一份基线覆盖所有层 | 各层的正常值不同；账号、提权面、系统边界要分别留档 |
| 提权面基线只记数量 | 数量相同可能是一增一减；要比清单 |
| 临时放宽没有回收动作 | `permissive`、`ip_unprivileged_port_start=0`、`NOPASSWD` 会变成长期状态 |
| 审计规则只敲 `auditctl` 不落盘 | 重启后规则消失，事后无法追溯 |
| 在 `/var/log` 批量 `chattr +i` | 轮转与升级失败，磁盘被日志写满 |
| 只做只读基线却不定责任人与保留期 | 采集一次就断档，「与上次比」永远没有上次 |
| 用「扫描通过」当加固完成的证据 | 扫描通过不代表配置生效（策略文件存在 ≠ 被引用），要用生效值与业务复测验收 |

## 要点自测

**问：为什么「先减面、再加固」比反过来效率高？**
答：加固是为保留的入口加约束；如果入口本身就多，加固的工程量与出错面都更大，而且会让一堆没人用的入口变得难以判断。先删掉不需要的账号、授权与入口，剩下的面才值得投入强制策略。

**问：账号台账里「是否认得」这一列为什么关键？**
答：能登录的账号只要有一个来源不明，就构成一条未知的入口；而权限类异常平时完全静默，不靠这一列就无法用人来判断。它把「技术上能登录」转成「组织上有人负责」的检查点。

**问：提权面基线为什么不能用计数作为主字段？**
答：计数相同可能对应「少了一个、多了一个」，差异会被完全掩盖。基线必须以每一类的完整清单为主体，并与上次的清单做 diff；新增项还要能反查到包归属。

**问：`systemctl show` 比 unit 文件更可靠的原因是什么？**
答：它给出的是**合并默认值与 drop-in 之后的生效值**，还能反映模板单元 `%i` 展开后的结果。unit 文件里写了几行不代表最终生效，这与 `sshd -T` 之于 `sshd_config` 是同一个道理。

**问：为什么「临时放宽」必须写到期时间与责任人？**
答：放宽的动机在故障压力下最强，而回收的动机最弱；没有到期时间与责任人，它就会变成长期状态。这一条与变更记录里的「回滚触发条件」是同一类制度设计。

**问：审计容量为什么算治理问题而不是技术细节？**
答：审计日志本身会增长，磁盘写满时的动作由配置决定；如果审计把磁盘写满，会引发一次与被审计事件无关的故障。审计的保留期、单文件大小、份数与磁盘满时的动作都属于「让证据可持续存在」的制度设计。

**第一反应不要做什么**：不要在离职处置里先删账号；不要在只读基线还没做之前就急着改配置；不要在放宽强制策略或整机参数时不设回收时间。
