# 一次特权访问的完整旅程

一次特权访问从「进程声称自己是谁」开始，经过认证、授权判定、提权与两道边界，最后留下痕迹；出事时再沿这些痕迹处置并恢复正常。这条线串起本章全部机制，下面一次讲完，最后再把贯穿多个阶段的四个核对对象（判定链、特权载体、可核查的证据与入口收敛）与关键字段的读法收拢在一起。

---

## 一、身份：系统按什么认人

### 1.1 身份是数值，不是名字

内核在每次权限判定里用的是 UID/GID 数值，登录名只是查表得到的外壳。这个外壳由 **NSS** 决定去哪查：`nsswitch.conf` 里 `passwd: files systemd` 表示先看本地文件，接了 LDAP/SSSD 之后会多出来源。因此判断「有没有这个账号」要用 `getent`（走 NSS），不是 `grep /etc/passwd`（只看一个文件）。

本地三份文件的分工已经固定：`/etc/passwd` 世界可读、只存占位符 `x`；`/etc/group` 存组与附加成员；`/etc/shadow` 只有 root 与 `shadow` 组可读，存哈希与有效期。**任何 UID 为 0 的账号都是完整超级用户**，这一条是账号巡检里优先级最高的判据。

### 1.2 一个进程携带一组身份

`ruid`/`rgid` 是真实身份（谁在负责），`euid`/`egid` 是有效身份（判定看它），`suid`/`sgid` 用于切回，`fsuid`/`fsgid` 是文件系统访问专用身份；此外还有附加组列表与 capabilities。`sudo` 前后的两个进程因此身份不同：前者的 `ruid` 是登录用户，后者的 `euid` 是目标账号，而日志里同时记着这两者。

**怎么读这组身份**：`id` 给出当前会话的 `uid`/`gid`/`groups`（数值，括号里是名字）；`/proc/<pid>/status` 给出**进程视角**的 `Uid`/`Gid`/`Groups`/`Cap` 四行，其中 `Uid`/`Gid` 每行四个数**依次是 real/effective/saved/filesystem**，`Cap` 是能力的十六进制掩码。**判据**：排查「谁在访问」时以进程的 `euid` 与组列表为准，不以登录名为准；`real ≠ effective` 说明该进程已提权。**与谁同看**：`getent passwd <uid>` 把数值换成名字、`getpcaps <pid>` 把掩码解码成能力名。**转向哪一步**：若 `euid` 与 `ruid` 不同，说明这是一次提权后的进程，下一步去看它是用哪条通道提的权（SUID、file capabilities、`sudo`，还是以 root 启动的服务）。

## 二、认证：这一次登录凭什么被放行

### 2.1 四类栈与「账号状态」

PAM 把认证拆成四类栈：`auth` 验凭据、`account` 判「现在允不允许登录」、`password` 管改密规则、`session` 准备与清理环境。**账号过期属于 `account` 栈**，所以「密码对但登不进去」与「密码错」是两类不同的问题，对应不同的栈。

一个关键性质是：**策略模块自己的配置文件只提供参数，是否生效取决于栈里有没有引用它。** 检查方式是看引用链，而不是看文件内容。

**怎么读**：看引用链用 `grep -rl <模块名> /etc/pam.d`（输出是命中的文件列表，只说明「有没有被引用」，不含计数）；看某个服务真正生效的行用 `grep -vE '^\s*(#|$)' /etc/pam.d/<service>`；一次失败的实际原因在发行版的认证日志或 journald 里（事件流，看时间戳与模块名）。**判据**：文件存在只说明「配置已写」，引用链命中才说明「策略已接上」。**与谁同看**：`chage -l <user>`（账号是否过期）、`getent shadow <user>`（哈希是否被锁）。**转向哪一步**：认证失败看 `auth` 与日志；认证通过但被拒看 `account`。

### 2.2 登录之后的身份从哪来

交互式登录由 `login`/`sshd` 走 PAM `session` 栈建立会话：`pam_umask` 从 `login.defs` 取 `UMASK`，`pam_limits` 从 `limits.conf` 取资源限制，`pam_systemd` 把会话注册进 systemd。**systemd 拉起的服务不走这条栈**，所以同一个 `umask` 或同一个 `nofile` 限制要在 unit 里另配。

## 三、判定：这次访问怎么被放行或拒绝

### 3.1 路径先过，文件再看

内核对 `/srv/app/config` 的判定分两步：**路径上每一级目录都要有访问者身份的 `x`**，然后才按「属主、属组与附加组、other」的顺序挑一条规则。三类身份是**先命中先停**，不叠加。

**怎么读**：`namei -l <path>` 逐行给出路径上每一级的 mode（符号形式）与属主属组，**一行一级**；`stat -c "%a %A %u %g %n" <path>` 给出目标的 mode（八进制数值 + 符号形式）、属主与属组的**数值**；`getfacl -cp <path>` 给出完整 ACL 条目。**判据**：任何一级目录缺 `x`，结果就是 `EACCES`，与最后那个文件无关。**与谁同看**：`id`/`/proc/<pid>/status` 确认访问者身份，`findmnt -T <path>` 看挂载选项。**转向哪一步**：若缺 `x` 的是路径上某一级目录，则改那一级目录的权限或换一个访问者；若路径各级都合格而只有最后一级不对，则去看 mode 与 ACL。

### 3.2 ACL 的 `mask` 是最后一道减法

一旦存在 named 条目或默认条目，named 条目与 owning group 的最终权限都要与 `mask` 取交集，`getfacl` 用 `#effective:` 标出结果。**有 ACL 时 `ls -l` 的属组三位显示的就是 `mask`**，不是 `group::` 的真实权限；而 `chmod` 会重算 `mask`。

**怎么读**：`getfacl -cp <path>` 的四类行——`user::`（属主）、`user:<name>:`（named）、`group::`（属组）、`mask::`，以及 `#effective:`。**判据**：named 条目写着 `rwx` 而 `#effective` 是 `r--` 时，瓶颈是 `mask`，重加授权无效。**转向哪一步**：`setfacl -m m::<权限>` 修正 `mask`，然后复查 `#effective`。

### 3.3 两类错误码指向不同的层

`EACCES`（`Permission denied`）来自路径、mode、ACL 的判定不通过；`EPERM`（`Operation not permitted`）来自「即使有常规文件权限也不允许」——capability 不足、文件只读、`chattr +i`、MAC 拒绝。**把 `errno` 记下来再分层，是最省时间的一步。**

## 四、提权面：从普通身份到更强身份的所有通道

### 4.1 一次提权发生在什么时刻

SUID/SGID 与 file capabilities 的生效点都在 `execve`，条件是：调用进程没有 `no_new_privs`、文件不在 `nosuid` 挂载点上、进程没有被 `ptrace`——任一不满足，特权授予被静默忽略。

**怎么读**：`stat -c %a <file>` 给出四位或三位**八进制**的 mode（首位 `4`/`2`/`1` 分别是 SUID/SGID/sticky），`getcap <file>` 给出文件能力与标志（`cap_net_raw=ep` 中的 `p`=Permitted、`e`=Effective），`findmnt -T <file> -o OPTIONS` 给出该挂载点的选项列表。**判据**：位已设却不见效时，按「位是否被 `chown` 清掉、挂载点是否 `nosuid`、是否有 `no_new_privs` 或 `ptrace`」三步排除；若目标是脚本，则它本就不该生效，因为内核忽略脚本上的特权位。**与谁同看**：`ls -l` 的符号位、`file <path>`（是不是 ELF）。**转向哪一步**：需要长期最小特权时，不要走 SUID，改走下面 4.2。

### 4.2 能力：把 root 拆成按项授予

capabilities 用五个集合描述特权的流动：Permitted（上限）、Effective（生效）、Inheritable（可继承）、Bounding（硬上限）、Ambient（非 root 跨 `execve` 保留）。系统级约束写在 Bounding 上（systemd 的 `CapabilityBoundingSet=`），让非 root 服务带一项能力运行需要 Bounding、Permitted 与 Ambient 同时成立。

**怎么读**：`getcap -r /` 给出带能力的文件**清单**，`capsh --print` 给出当前进程的五个集合（能力名列表）与 `cap_last_cap`（编号上限），`getpcaps <pid>` 按进程给出集合，`systemctl show -p CapabilityBoundingSet -p AmbientCapabilities <unit>` 给出服务侧的生效值。**判据**：`getcap` 显示有值只代表 xattr 写成功；对脚本与 `nosuid` 挂载点仍然不生效。**与谁同看**：`sysctl kernel.cap_last_cap`（编号上限，用来判断某个能力名是否存在）、`systemctl show` 的 `NoNewPrivileges`。**转向哪一步**：应用需要某项能力时，优先选 systemd 的 `AmbientCapabilities=` + `CapabilityBoundingSet=`，其次才是文件能力。

### 4.3 提权面的完整清单

除 SUID/SGID 与 file capabilities 之外，以下通道都能在不碰这两者的情况下通向 root：

| 类别 | 典型形态 | 核查入口 |
| --- | --- | --- |
| 授权工具 | `sudo`/`su` 的规则、`NOPASSWD`、可逃逸的命令（编辑器、解释器、`docker`、`systemctl`） | `sudo -l -U <user>`、`visudo -c`、审阅 `/etc/sudoers.d/` |
| 可写的执行路径 | 由 root 执行但可被非 root 写入的脚本与配置、`PATH` 上的可写目录、cron 与 unit 的 `ExecStart` | `find -perm -0002`、检查属主与目录权限 |
| 凭据入口 | `authorized_keys`（含 `command=`）、主机密钥、`/etc/ssh/sshd_config` 的生效值 | `find /home /root -name authorized_keys`、`sshd -T` |
| 动态链接 | `/etc/ld.so.preload`、`LD_PRELOAD` 与库搜索路径 | 确认该文件不存在；检查 `/etc/ld.so.conf.d/` |
| 内核与设备 | 模块加载、`/dev/mem`、非特权 BPF、`kptr_restrict` | `sysctl kernel.unprivileged_bpf_disabled`、模块清单 |
| 容器 | 特权容器、宿主目录挂载、能力全开 | 容器运行参数与挂载清单 |
| 挂载选项缺失 | 可写挂载点没有 `nosuid`/`noexec` | `findmnt -o TARGET,FSTYPE,OPTIONS` |

判据只有一条：**与上次留档的清单做差异，新增项能否用包管理器反查到归属**（`dpkg -S <basename>` / `rpm -qf <path>`，注意 `/bin` 与 `/usr/bin` 合并的发行版要按 basename 反查）。查不到归属又没有变更记录的提权点，按事件处理。

## 五、两道边界：MAC 与系统级开关

### 5.1 MAC 按策略仲裁

SELinux 看上下文（标签随 inode 走），AppArmor 看程序路径对应的 profile。两者的拒绝都以 `type=AVC` 记录出现，但语法不同：SELinux 是 `avc: denied { ... }`，AppArmor 是 `apparmor="DENIED" ... denied_mask="..."`。**记录落在哪取决于 auditd 是否在运行**：运行时落审计日志，不在时才进内核日志。

**怎么读**：`ls /sys/kernel/security/lsm` 给出已加载的 LSM **模块名列表**；`aa-status` 给出 AppArmor 的 profile 计数（个，按 `enforce`/`complain` 分组）；`getenforce`/`sestatus` 给出 SELinux 的模式与策略状态；拒绝记录按其语法辨认——`avc: denied { 权限 }`、`apparmor="DENIED" ... denied_mask="..."`，两者都以 `type=AVC` 出现，且记录里的时间戳要与变更记录对齐才有意义。**判据**：空结果不等于没发生，因此要先确认审计设施与 `log_format` 配置。**与谁同看**：`aa-status` 的模式计数（有没有长期 `complain`）、SELinux 是否处于 `permissive`。**转向哪一步**：按「找拒绝、修标签或端口或布尔值、必要时补策略、切回强制模式」四步处置，`permissive`/`complain` 只用于定位。

### 5.2 系统级开关

挂载选项给整个文件系统加约束：`nosuid`（含 file capabilities 一并失效）、`nodev`、`noexec`（拦不住解释器）。内核参数关掉全局危险入口，代价常常是可观测性：`dmesg_restrict`、`kptr_restrict`、`perf_event_paranoid` 收紧之后，排障工具一起受限。**参数值可能不在任何配置文件里**——它来自内核或发行版默认；`sysctl -w` 的值也只存在于运行时。

## 六、留痕与取证处置

### 6.1 访问留下了什么

一次特权访问的证据分散在几处，各有各的失效方式：

| 证据 | 载体 | 什么时候会丢 |
| --- | --- | --- |
| 认证与提权留痕 | 审计日志与发行版的认证日志（`sudo` 按编译选项落 syslog 的 `authpriv` 设施，若配了独立 `logfile=` 则落在别处） | 日志轮转会覆盖旧记录；机器重建时整份日志一起消失 |
| 登录痕迹 | `/var/log/wtmp`（成功）、`/var/log/btmp`（失败）、`lastlog` 与 `loginctl` 的会话 | 清理动作、机器重建 |
| 权限与提权面 | 文件 mode、ACL、xattr、`getcap` 与 `find -perm` 的输出 | 后续变更会覆盖；没有留档就无法 diff |
| 会话内命令 | shell 历史（`history`） | 可被 `unset HISTFILE`、清空或根本不写——**它不是审计证据** |
| 文件完整性 | 包数据库校验（`dpkg -V` / `rpm -Va`） | 升级会重置基线；非 root 跑会出现 `?????????` |

### 6.2 从「发现异常」到「交得出处置结论」

处置顺序是固定的五段：**隔离、保全、取证、判定、恢复或重建**。其中三件事必须提前定好：谁有权隔离（云上先做磁盘快照再收网络）、证据复制到哪里（**出事的机器起不来时，留在本机等于没取**），以及「什么样算恢复」（被 root 完全控制的机器以重建为准，重建前轮换同一批机器共用的全部凭据）。

**怎么读**：`ps --forest auxf`（进程树，含属主与命令）、`ss -antup`（连接，含对端地址与归属进程）、`ls -l /proc/<pid>/exe /proc/<pid>/cwd`（可执行文件与工作目录的真实路径）、`cat /proc/<pid>/environ | tr '\0' '\n'`（环境变量，按换行拆开）——这四项是内存侧最有价值的一批证据，**一旦重启就没了**。**判据**：时间线要由「变更记录 + 日志时间戳 + 文件时间戳」三方对齐，而不是靠回忆；时间戳要统一时区再看。**与谁同看**：登录痕迹（`last`/`lastb`/`loginctl`）与包数据库校验结果。**转向哪一步**：任何「清理后继续用」的方案都要先回答「凭什么认为没有第二个入口」。

## 七、四个跨阶段的核对对象

### 7.1 判定链：文件权限看着对却仍被拒

判定链贯穿阶段 3 到阶段 9，因为同一个 `EACCES` 或 `EPERM` 可能来自路径、权限位、ACL、能力、挂载选项、MAC 或内核参数中的任意一层。定位时按下面的顺序逐层排除，每一层都先读该层的字段再决定是否往下走。

| 顺序 | 阶段 | 查什么 | 读哪个字段 | 一条命令 |
| --- | --- | --- | --- | --- |
| 1 | 阶段 3 DAC 判定 | 路径上每一级目录的 `x` | 每一级的 mode 与属主 | `namei -l <path>` |
| 2 | 阶段 3 DAC 判定 | DAC 位与属主、属组 | 八进制 mode 与 UID/GID | `stat -c "%a %u %g %n" <path>` |
| 3 | 阶段 4 精细授权 | ACL 的 `mask` 与 `#effective` | `mask::` 行与 named 条目后的 `#effective:` | `getfacl -cp <path>` |
| 4 | 阶段 5 与阶段 6 | 文件与进程各自带哪些能力 | 能力名与 `p`/`e` 标志 | `getcap <bin>`、`getpcaps <pid>` |
| 5 | 阶段 7 合法通道 | 授权工具给出的最终权限 | `sudo -l -U <user>` 的授权条目、`sshd -T` 的认证项 | `sudo -l -U <user>`、`sshd -T` |
| 6 | 阶段 8 强制访问控制 | MAC 的拒绝记录 | `avc: denied` 的权限位与 `apparmor="DENIED"` 的 `denied_mask=` | 审计原始日志 |
| 7 | 阶段 9 系统边界 | 挂载选项与内核参数 | `OPTIONS` 列里有没有 `nosuid`/`noexec`；参数名与当前取值 | `findmnt -T <path> -o TARGET,FSTYPE,OPTIONS`、`sysctl fs.protected_regular` 一类 |

**这条链是一条排除链，不是一张清单。** 每一层都要用「这一层的证据是否支持结论」来决定是否继续往下；因此在没有取证之前胡乱 `chmod`，只会把权限问题变成提权问题。

### 7.2 特权载体：多出来一个才是最要紧的

特权载体贯穿阶段 5 到阶段 9。它从文件上的特权位开始，经过授权工具与 SSH 钥匙，最后落到整个挂载点上的约束；其中阶段 8 只决定哪一条路径被放行，不新增载体，因此在这一阶段要读的是模式与布尔值，而不是特权位。

特权载体的价值不在于当下有几个，而在于**与留档清单的差异**。要在阶段 5 读 `find -perm -4000`/`-2000` 的文件清单与 `stat -c %a` 的首位，在阶段 6 读 `getcap -r /` 的清单与 `systemctl show -p CapabilityBoundingSet -p AmbientCapabilities` 的生效值，在阶段 7 读 `sudo -l -U <user>` 的授权条目与 `authorized_keys` 的选项，在阶段 8 读 `getenforce`/`aa-status` 的模式、`getsebool` 的布尔值与 `semanage port -l` 的端口类型，在阶段 9 读 `findmnt -o TARGET,FSTYPE,OPTIONS` 里缺 `nosuid`/`noexec` 的挂载点。采集方式固定（同一组命令、同一字段顺序、同一时间戳格式）；一旦差异出现，就先反查包归属，再看看变更记录。**日常完全静默、只在 diff 时才现形的这一类风险，靠「感觉干净」是覆盖不到的。**

### 7.3 可核查的证据：五类基线与包数据库

可核查的证据贯穿阶段 1 到阶段 10，因为同一批事件会在账号台账、权限与提权面基线、变更留痕、审计日志与包数据库校验里各留一份记录。要在阶段 1 与阶段 2 读 `getent passwd`/`shadow`、`passwd -S` 与 `chage -l`，在阶段 3 到阶段 6 读 `stat`、`getfacl`、`find -perm` 与 `getcap` 的输出，在阶段 7 与阶段 8 读认证日志与 `ausearch -m AVC`，在阶段 9 读 `findmnt -T` 的挂载选项与相关 `sysctl` 的当前值，在阶段 10 读 `last`/`lastb`/`loginctl` 的会话记录与 `dpkg -V`/`rpm -Va` 的校验结果。

五类基线是**账号、提权面（SUID/SGID/capabilities）、监听端口、计划任务与自启、SSH 授权**。它们加上包数据库校验与两份日志（认证日志、审计日志），构成一台机器的可核查面。这条线的判据是**可重复**：同一组命令能跑出同一字段格式的输出，才能 diff。

### 7.4 入口收敛：先关掉不需要的，再叠加强制

入口收敛贯穿阶段 1 到阶段 9。要在阶段 1 与阶段 2 读登录 shell、`passwd -S` 的密码状态与 `chage -l` 的账号过期日期，在阶段 5 与阶段 6 读 `find -nouser -o -nogroup` 的无主文件清单与 `getcap -r /` 的结果，在阶段 7 读 `sshd -T` 的认证项与 `sudo -l -U <user>` 的授权粒度，在阶段 8 读 `getenforce`/`aa-status` 的模式，在阶段 9 读 `findmnt` 的挂载选项与相关 `sysctl` 的值。

顺序是**先关入口、再上策略**：能登录的账号数（含 shell 与 `nologin`）、PAM 的策略、SSH 的认证方式与来源限制、`sudoers` 的授权粒度、无主的特权文件、挂载选项、内核参数。**先做「不需要的东西不开放」，再谈「开放的东西怎么强制」**；反过来的话，强制策略只会把已有入口变得难用，而不减少入口数量。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 先用 `ls -l` 最后一级文件判断 | 漏掉路径缺 `x`、ACL `mask`、挂载选项与 MAC |
| 把 `EACCES` 与 `EPERM` 当同一件事 | 前者多在 DAC 与路径，后者多在 capability、只读、不可变属性或 MAC |
| 有 ACL 时看 `ls -l` 的属组位下结论 | 那一格显示的是 `mask` |
| 用 `chmod` 调完 ACL 不复查 | `chmod` 会重算 `mask`，可能悄悄削掉授权 |
| 只看 SUID 清单就宣布提权面干净 | file capabilities 在 `ls -l` 上完全没有痕迹 |
| 在脚本上加 SUID 或 file capabilities | 内核只对可执行映像应用，脚本是「设得上、不生效」 |
| 用 `journalctl -k` 找 MAC 拒绝 | auditd 在运行时拒绝落在审计日志；内核日志里多为引导期记录 |
| 把 `ausearch` 的空结果当成「没发生」 | 它依赖审计配置；要用 `grep` 原始文件交叉验证 |
| 用 `history` 当审计证据 | 可被跳过、清空或不写 |
| 出事时先重启「恢复正常」 | 内存侧证据（进程、连接、`/proc/<pid>/*`、环境变量）随重启消失 |
| 单次基线就当完成核查 | 基线的意义在于与上次 diff |

## 要点自测

**问：一次访问被拒，判定链的排除顺序是什么？**
答：先看路径上每一级目录的 `x`，再看 DAC 位与属主属组，再看 ACL 的 `mask` 与 `#effective`，再看所需的 capability，再看挂载选项，再看 MAC 的拒绝记录，最后看内核参数与内核保护。每层都先取该层的证据，再决定是否往下走；不要在没取证前改权限。

**问：`euid` 与 `ruid` 不同时，日志里哪个字段是「发起者」？**
答：以审计或 sudo 日志的语义为准：`USER=` 是执行身份（`euid` 侧），发起者通常以记录前缀或 `ruid` 侧字段体现。**判读前先确认这套日志的字段定义**，不同工具的记法不同。

**问：为什么提权面必须留基线，而不是每次现查？**
答：SUID 文件、file capabilities、可写的 root 脚本、`authorized_keys` 这些通道平时完全静默，单次查看只能得到一张清单；风险信号是「与上次相比多了一个」，且新增项能否反查到包归属。没有基线就没有差异判据。

**问：MAC 拒绝了，为什么在有的机器上查不到记录？**
答：记录的落点取决于 auditd 是否在运行：运行时 LSM 拒绝作为审计事件写入审计日志，不在时才进内核日志。此外查询工具还受审计配置影响，`ausearch` 返回空不能直接当作「没发生」。

**问：为什么入口收敛要先做「关掉不需要的」，再做「叠加强制策略」？**
答：强制策略作用于已经开放的入口；如果入口本身就多，策略只会让它们更难用，而不减少数量。先减少面的数量，再对保留的面加约束，收敛效率与可维护性都更高。

**问：判断「账号已停用」需要看哪几个证据？**
答：`shadow` 的密码字段与有效期字段（`passwd -S`/`chage -l`）、账号过期日期（第 8 字段）、`authorized_keys` 与 `sudoers` 里是否还有该账号的授权、以及是否仍有活跃会话（`who`/`loginctl`）。只看密码是否被锁，会漏掉整条公钥通道。

**第一反应不要做什么**：不要在没有证据归属的情况下改权限；不要把单次清单当基线；不要在出事时先重启。
