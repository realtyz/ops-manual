## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **账号台账先看 UID，再看 shell 和过期状态**：UID 0 只有 root；UID≥1000 的人类账号要逐个认得；系统账号应 `nologin`/`false`。
> - **默认密码策略几乎不设限，但「root 默认锁成 `!*`」在本机不成立**：`PASS_MAX_DAYS=99999` 来自 `/etc/login.defs`；`INACTIVE=-1` 只来自 `useradd -D`，不是 `login.defs` 的项。**实测本机 root 的 shadow 密码字段首字符是 `$`（已设哈希、可登录），`!*` 属于另外 5 个账号**（本机 35 个 shadow 条目：2 个 `HASHED`、28 个锁定/无登录口令、5 个 `!*`）。
> - **「锁定密码」不等于「停用账号」**：公钥、`sudo NOPASSWD`、长期会话都能绕过。
> - **改默认值不会回头改存量账号**：`/etc/login.defs` 是新建默认，存量账号要 `chage` 逐条收。
> - **账号核查必须和基线比对**：多一个 UID 0、多一个可登录账号、`passwd`/`shadow` 条数不一致，都是需要解释的事件。

## 1. 先取一张账号全景图

```bash
wc -l < /etc/passwd
                               # 验证：本地账号总数
awk -F: '$3==0 {print}' /etc/passwd
                               # 验证：UID 0 账号；预期只有 root
awk -F: '$3>=1000 && $3<65534 {print $1, $3, $7}' /etc/passwd
                               # 验证：人类账号与登录 shell
awk -F: '$7 ~ /(nologin|false)$/ {print $1, $3, $7}' /etc/passwd | head
                               # 验证：不可交互登录的账号
awk -F: '$3<1000 && $7 !~ /(nologin|false)$/ {print $1, $3, $7}' /etc/passwd
                               # 验证：系统账号却带可登录 shell，属于需要解释的异常
```

四种优先处置的账号异常：

| 异常 | 判断 | 第一反应不要做什么 |
| --- | --- | --- |
| UID 0 出现非 root 账号 | 最高优先级 | 不要改名了事，先定性来源 |
| UID≥1000 的账号不认得 | 可能是入侵或遗留账号 | 不要直接删，先取登录痕迹与授权 |
| 系统账号带 `/bin/bash` | 可能被改过或配置错误 | 不要只改 shell，先看有没有登录记录 |
| `passwd` 与 `shadow` 条数对不上 | 可能被手工加过账号 | 不要忽略，逐条对账 |

## 2. 密码有效期：默认值几乎都等于「不设限」

```bash
grep -E '^(PASS_MAX_DAYS|PASS_MIN_DAYS|PASS_WARN_AGE|INACTIVE)' /etc/login.defs
                               # 验证：新建账号的默认有效期来源
passwd -S $(id -un)            # 验证：当前账号密码状态与有效期
chage -l $(id -un)             # 验证：shadow 字段的人类可读版
```

本机默认值（来源 `.labvm/evidence/07_identity.out.txt`、`07_pam.out.txt`）：`/etc/login.defs` 里 `PASS_MAX_DAYS=99999`（约 273 年）、`PASS_WARN_AGE=7`；**`login.defs` 里并没有 `INACTIVE` 这一项**（实测输出 `(login.defs 无 INACTIVE 项)`），`-1` 只来自 `useradd -D` 的输出；`/etc/shadow` 第 7 字段（inactive）对 root 与 realtyz 都是**空**。加固基线应至少收紧为：最大有效期 90 天、最小改密间隔 1 天、到期提醒 7 天、到期后 30 天禁用。**注意 `login.defs` 只影响之后新建/批量改密工具，不会自动修改已有账号。**

## 3. 锁定与停用账号：两个动作，不要混用

```bash
passwd -l someuser             # 验证：在 shadow 哈希前加 !，锁密码认证
usermod -e 1 someuser          # 验证：让账号从 1970-01-02 起过期，属于真正停用的一环
chage -l someuser              # 验证：确认 Expires 已改变
find /home /root -name authorized_keys -print 2>/dev/null
                               # 验证：排查已部署的公钥，锁密码不会清掉它们
who; w; loginctl list-sessions # 验证：排查是否还有长期会话
```

离职账号的标准处置不是一条命令，而是一组：

1. `usermod -e 1`（账号过期）
2. 清理 `~/.ssh/authorized_keys`
3. 撤销 sudoers 条目
4. 终止会话（`loginctl terminate-session` 或 `pkill -u`，确认业务允许）
5. 记录变更，纳入账号台账

> [!warning] 不要先删账号
> `userdel` 会让很多文件变成 `nouser`/`nogroup`，反而更难排查。**先停用、清授权、留台账，再按需归档或删除。**

## 4. 账号台账模板

把下面字段固化成表格或脚本输出，定期采集：

```text
账号名 | UID | GID | 登录 shell | 密码状态 | 最后改密 | 最大有效期 | 账号过期 | 家目录 | 是否认得
root   | 0   | 0   | /bin/bash  | P        | ...       | 99999      | ...      | /root   | 是
ops    | 1001| 1001| /bin/bash  | P        | ...       | 90         | -1       | /home/ops | 是
```

`是否认得` 是最容易忽略、也最有效的一列：**任何「不认得」的可登录账号都要有来源说明。**

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 离职账号只跑 `passwd -l` | 公钥、`NOPASSWD`、已有会话仍可进入 |
| 直接 `userdel` 清理离职账号 | 文件变成无主，取证和权限判定更困难 |
| 改了 `login.defs` 就以为存量账号也生效 | 它只是新建/工具默认，存量要 `chage` |
| 用 `grep /etc/passwd` 判断账号 | LDAP/SSSD 账号看不到，应用 `getent` |
| 只看账号名不看 UID | 非 root 名字的 UID 0 同样是完整 root |

## 决策练习

> [!question]- 场景：值班时发现一台机器多了一个 UID 0 的 `support` 账号，但同事说可能是某次安装工具自动建的。你怎么办？
> A. 相信同事，只记一笔
> B. 先取证：`getent passwd support`、`getent shadow support`、`lastlog -u support`、`find /home -name authorized_keys`、sudoers/日志；与同类机器基线对比，无法解释就按事件上报并隔离
> C. 直接把 `support` 改成 `nologin`，收工
>
> **答案：B。**
> A 风险太大：UID 0 是完整超级用户，不能靠口头解释放过。
> C 会销毁/改动现场，且没有解释来源。
> B 是正解：**先留证据、先隔离，再判定来源；处置顺序不能反。**

## 要点自测

> [!question]- 怎么在一分钟内列出一台机器的账号全景？
> - UID 0、UID≥1000 的人类账号、系统账号 shell、`passwd`/`shadow` 条数、可登录账号清单。
> - 用 `awk`/`getent` 固定输出，与基线比对。
> - **第一反应不要是什么**：不要只数 `wc -l` 就下结论。

> [!question]- 为什么改 `login.defs` 不会让存量账号自动收紧？
> - `login.defs` 是 `useradd`、`chpasswd` 等工具的默认值来源；已有账号字段已经写在 `shadow` 里，不会自动回写。
> - 存量账号用 `chage`/`usermod` 逐条处理。
> - **第一反应不要是什么**：不要以为改了配置就完成了加固。

> [!question]- 离职账号的标准处置为什么不能只锁密码？
> - 密码只是入口之一；要同时处理账号过期、公钥、sudoers、会话。
> - 先停用、清授权、留台账，再考虑删除。
> - **第一反应不要是什么**：不要在没留证据时直接删账号。
