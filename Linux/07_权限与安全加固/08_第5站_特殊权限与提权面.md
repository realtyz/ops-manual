## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **SUID 执行时换 `euid` 为文件属主**：`passwd`、`sudo` 靠它工作，但脚本上的 SUID 被内核忽略。
> - **`no_new_privs`、`nosuid` 挂载、被 `ptrace` 时，SUID/file capabilities 都会被忽略**。
> - **SGID 对文件换 `egid`，对目录让新建文件继承属组**；Sticky 让目录内只有属主/目录属主/root 能删。
> - **核查 SUID 要用 `find -perm -4000`**：这是「包含」匹配；`-perm 4000` 是精确匹配，会漏掉 4755。
> - **只查 SUID 会漏一半提权面**：file capabilities、sudo、可写脚本/配置、SSH 钥匙、内核设备、容器特权都要查。

## 1. 三个特殊位

```text
-rwsr-xr-x 4755 f          # SUID：执行时 euid 变文件属主
drwxr-sr-x 2755 d          # SGID：执行时 egid 变属组；目录则让新文件继承属组
drwxrwxrwt 1777 sticky     # Sticky：目录内只有文件属主/目录属主/root 能删
```

SUID 生效的三条前提，在 `execve(2)` 中写得很明确：`no_new_privs` 未设置、文件系统未挂 `nosuid`、进程未被 `ptrace`；同时 Linux 忽略脚本上的 set-user-ID/set-group-ID 位。

`man 2 execve` 的要点（不是逐字原文）：`no_new_privs` 设置、底层文件系统 `nosuid`、调用进程被 ptraced 时，set-user-ID 与 set-group-ID 位被忽略；Linux 同时忽略脚本文件上的 set-user-ID/set-group-ID 位。

## 2. `find -perm` 的三种写法

```bash
find . -maxdepth 1 -type f -perm -4000   # 验证：「所有位都包含」，匹配 SUID 位已置
find . -maxdepth 1 -type f -perm 4000    # 验证：「精确等于」，会漏掉 4755
find . -maxdepth 1 -type f -perm /6000   # 验证：「任一位匹配」，SUID 或 SGID 都命中
```

核查清单：

```bash
find / -xdev -type f -perm -4000 2>/dev/null | sort
                               # 验证：系统盘 SUID 文件清单
find / -xdev -type f -perm -2000 2>/dev/null | sort
                               # 验证：SGID 文件清单
find / -xdev -type f -perm -4000 2>/dev/null | wc -l
                               # 验证：本机 SUID 数量，作为基线
find / -xdev \( -nouser -o -nogroup \) 2>/dev/null | wc -l
                               # 验证：无主/无属组文件，可能是删除账号后的残留
```

> [!important] 数量正常不等于安全
> `find` 只告诉你「哪些文件有 SUID」。真正判定异常要两步：① 与上次留档清单 diff；② 用 `dpkg -S <basename>` 或 `rpm -qf <path>` 反查是否属于发行版包。**不属于任何包、也没有变更记录的 SUID 文件，就是最高优先级事件。**

## 3. usrmerge 的反查坑

Debian/Ubuntu 的 `/bin -> usr/bin` 可能导致包数据库登记的是 `/bin/xxx`，而实际路径是 `/usr/bin/xxx`。

```bash
dpkg -S /usr/bin/fusermount3      # 验证：可能 no path found
dpkg -S fusermount3               # 验证：按 basename 反而能查到 fuse3
```

## 4. 提权面全景

| 提权面 | 典型形态 | 核查方法 | 加固方向 |
| --- | --- | --- | --- |
| SUID/SGID 二进制 | `passwd`、`sudo`、自编译程序 | `find -perm -4000/-2000` | 删不必要的；`nosuid`；`NoNewPrivileges` |
| file capabilities | `ping cap_net_raw=ep` | `getcap -r /` | 只授单项 |
| sudo/su | `NOPASSWD`、`ALL` | `sudo -l`、审阅 sudoers | 最小权限 + 审计 |
| root 执行的可写脚本/配置 | cron/systemd/PATH | `find -perm -0002`、查脚本属主 | 脚本不可被非 root 写 |
| SSH 授权 | `authorized_keys` 及其 `command=` | `find /home /root -name authorized_keys` | 按钥匙限权 |
| 动态链接器 | `/etc/ld.so.preload`、`LD_PRELOAD` | `ls -l /etc/ld.so.preload` | 不出现；出现即事件 |
| 内核与设备 | `/dev/mem`、模块、eBPF | `sysctl kernel.unprivileged_bpf_disabled` | 收紧非特权入口 |
| 容器 | `--privileged`、宿主目录挂载 | `docker inspect`、`--cap-drop all` | 去特权 |
| 挂载选项 | 缺 `nosuid`/`noexec`/`nodev` | `findmnt` | 临时目录与数据盘收紧 |

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 用 `find -perm 4000` 核查 SUID | 精确匹配会漏掉 4755 |
| 只查 SUID 就宣布「没有提权点」 | file capabilities、sudo、可写脚本等仍在 |
| 给脚本加 SUID | 内核忽略脚本上的 set-user-ID 位 |
| 按绝对路径 `dpkg -S` 查不到就判定异常 | usrmerge 下要先按 basename 再查 |
| 认为 SUID 文件数量少就安全 | 关键不是数量，是「与基线相比有没有新增」 |

## 决策练习

> [!question]- 场景：你发现系统里多了一个 `/usr/local/bin/backup`，mode 4755，`dpkg -S backup` 查不到。同事说「可能是运维自己编译的，先放着」。你怎么办？
> A. 先放着，等下周再说
> B. 立即按事件处理：取 `stat` 时间、校验哈希、查来源与变更记录、与其他机器基线比对；无法解释就隔离并上报
> C. 把 SUID 位去掉就结束
>
> **答案：B。**
> A 风险过高：SUID root 文件等于一个持久提权入口。
> C 只消除了当前表象，没有解释它怎么出现、有没有其他同类文件。
> B 是正解：**不属于包、无变更记录的 SUID 文件要按事件处置。**

## 要点自测

> [!question]- SUID/SGID/Sticky 各做什么？
> - SUID 执行时换 `euid`；SGID 文件换 `egid`，目录让新文件继承属组；Sticky 只让目录内属主删自己的文件。
> - **第一反应不要是什么**：不要把目录的 SGID 理解成提权。

> [!question]- `find -perm` 三种写法差在哪？
> - `-4000` 是包含、`4000` 是精确、`/6000` 是任一；核查 SUID 用 `-4000`。
> - **第一反应不要是什么**：不要用精确写法，会漏掉 4755。

> [!question]- 提权面为什么不止 SUID？
> - 因为还有 file capabilities、sudo、root 执行的可写文件、SSH 钥匙、动态链接器、内核/设备、容器、挂载选项等。
> - 每一类都要有核查命令并进基线。
> - **第一反应不要是什么**：不要只跑 `find -perm -4000` 就宣布干净。
