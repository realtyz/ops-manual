## 0. 30 秒速览

> [!abstract] 这一篇只要记住六句话
> - **SUID 执行时换 `euid` 为文件属主**：`passwd`、`sudo` 靠它工作，但脚本上的 SUID 被内核忽略（实测：同为 4755，ELF 跑出 `euid=0`，脚本跑出 `uid=1000`）。
> - **`no_new_privs`、`nosuid` 挂载、被 `ptrace` 时，SUID/file capabilities 都会被忽略**（实测：`setpriv --no-new-privs` 下 `euid` 不再变；`nosuid` tmpfs 上 file capabilities 报 `errno=1`）。
> - **SGID 对文件换 `egid`，对目录让新建文件继承属组**；Sticky 让目录内只有属主/目录属主/root 能删。
> - **核查 SUID 要用 `find -perm -4000`**：这是「包含」匹配；`-perm 4000` 是精确匹配，会漏掉 4755。实测本机 SUID **13** 个、SGID **7** 个。
> - **`chown` 会清掉 SUID/SGID 位**：先 `chmod 4755` 再 `chown`，位就没了；要按 `chown` → `chmod` 的顺序做。
> - **只查 SUID 会漏一半提权面**：file capabilities（本机 4 个）、sudo、可写脚本/配置、SSH 钥匙、内核设备、容器特权都要查。

## 1. 三个特殊位

```text
-rwsr-xr-x 4755 f          # SUID：执行时 euid 变文件属主
drwxr-sr-x 2755 d          # SGID：执行时 egid 变属组；目录则让新文件继承属组
drwxrwxrwt 1777 sticky     # Sticky：目录内只有文件属主/目录属主/root 能删
```

SUID 生效的三条前提，在 `execve(2)` 中写得很明确：`no_new_privs` 未设置、文件系统未挂 `nosuid`、进程未被 `ptrace`；同时 Linux 忽略脚本上的 set-user-ID/set-group-ID 位。

`man 2 execve` 的要点（不是逐字原文）：`no_new_privs` 设置、底层文件系统 `nosuid`、调用进程被 ptraced 时，set-user-ID 与 set-group-ID 位被忽略；Linux 同时忽略脚本文件上的 set-user-ID/set-group-ID 位。

## 2. `find -perm` 的三种写法

```bash
find . -maxdepth 1 -type f -perm -4000   # 验证：「所有位都包含」，匹配 SUID 位已置
find . -maxdepth 1 -type f -perm 4000    # 验证：「精确等于」，会漏掉 4755
find . -maxdepth 1 -type f -perm /6000   # 验证：「任一位匹配」，SUID 或 SGID 都命中
```

三种写法在**同一台机器、同一时刻**的实测差异（`.labvm/evidence/07_findperm_real.out.txt`，2026-09-19 08:34 UTC 采集）：

```text
find / -xdev -type f -perm -4000 | wc -l   →  13     （包含匹配：SUID 位已置）
find / -xdev -type f -perm 4000  | wc -l   →   0     （精确匹配：本机没有 mode 恰为 4000 的文件）
find / -xdev -type f -perm /6000 | wc -l   →  20     （任一位匹配：SUID 13 + SGID 7）
find / -xdev -type f -perm -2000 | wc -l   →   7     （包含匹配：SGID 位已置）
find / -xdev -type f -perm 4755  | wc -l   →  12     （精确 4755：13 个 SUID 里有一个不是 4755）
```

**`-perm 4000` 得 0 不是「本机没有 SUID 文件」，而是「精确匹配几乎永远匹配不到」**：13 个 SUID 文件里 12 个是 `4755`，例外是 `/usr/lib/dbus-1.0/dbus-daemon-launch-helper` 的 **`4754`**（少一个 other 的 `x`）；7 个 SGID 文件全部是 `2755`，所以 `-perm 2755` 也得 7。核查提权面**只用 `-perm -4000` 或 `-perm /6000`**，别用 `-perm 4000`。

核查清单：

```bash
find / -xdev -type f -perm -4000 2>/dev/null | sort
                               # 验证：系统盘 SUID 文件清单，本机 13 个
find / -xdev -type f -perm -2000 2>/dev/null | sort
                               # 验证：SGID 文件清单，本机 7 个
find / -xdev -type f -perm -4000 2>/dev/null | wc -l
                               # 验证：本机 SUID 数量 13，作为基线
find / -xdev \( -nouser -o -nogroup \) 2>/dev/null | wc -l
                               # 验证：无主/无属组文件，可能是删除账号后的残留
```

本机实测清单（可作为同版本 Ubuntu 的对照基线）：

```text
SUID（13）
/usr/bin/chfn  /usr/bin/chsh  /usr/bin/fusermount3  /usr/bin/gpasswd
/usr/bin/mount  /usr/bin/newgrp  /usr/bin/passwd  /usr/bin/su
/usr/bin/sudo  /usr/bin/umount
/usr/lib/dbus-1.0/dbus-daemon-launch-helper
/usr/lib/openssh/ssh-keysign
/usr/lib/polkit-1/polkit-agent-helper-1

SGID（7）
/usr/bin/chage  /usr/bin/crontab  /usr/bin/expiry  /usr/bin/ssh-agent
/usr/lib/x86_64-linux-gnu/utempter/utempter
/usr/sbin/pam_extrausers_chkpwd  /usr/sbin/unix_chkpwd
```

> [!important] 数量正常不等于安全
> `find` 只告诉你「哪些文件有 SUID」。真正判定异常要两步：① 与上次留档清单 diff；② 用 `dpkg -S <basename>` 或 `rpm -qf <path>` 反查是否属于发行版包。**不属于任何包、也没有变更记录的 SUID 文件，就是最高优先级事件。**

## 3. usrmerge 的反查坑

Debian/Ubuntu 的 `/bin -> usr/bin` 可能导致包数据库登记的是 `/bin/xxx`，而实际路径是 `/usr/bin/xxx`。

```bash
dpkg -S /usr/bin/fusermount3      # 验证：可能 no path found
dpkg -S fusermount3               # 验证：按 basename 反而能查到 fuse3
```

## 4. 提权面全景

| 提权面 | 典型形态 | 核查方法 | 加固方向 |
| --- | --- | --- | --- |
| SUID/SGID 二进制 | `passwd`、`sudo`、自编译程序 | `find -perm -4000/-2000` | 删不必要的；`nosuid`；`NoNewPrivileges` |
| file capabilities | `ping cap_net_raw=ep` | `getcap -r /` | 只授单项 |
| sudo/su | `NOPASSWD`、`ALL` | `sudo -l`、审阅 sudoers | 最小权限 + 审计 |
| root 执行的可写脚本/配置 | cron/systemd/PATH | `find -perm -0002`、查脚本属主 | 脚本不可被非 root 写 |
| SSH 授权 | `authorized_keys` 及其 `command=` | `find /home /root -name authorized_keys` | 按钥匙限权 |
| 动态链接器 | `/etc/ld.so.preload`、`LD_PRELOAD` | `ls -l /etc/ld.so.preload` | 不出现；出现即事件 |
| 内核与设备 | `/dev/mem`、模块、eBPF | `sysctl kernel.unprivileged_bpf_disabled` | 收紧非特权入口 |
| 容器 | `--privileged`、宿主目录挂载 | `docker inspect`、`--cap-drop all` | 去特权 |
| 挂载选项 | 缺 `nosuid`/`noexec`/`nodev` | `findmnt` | 临时目录与数据盘收紧 |

## 5. 实验：制造并验证一个 SUID 文件

> [!example]- 实验：SUID 二进制与脚本的差异（本机已实测）
> **怎么做**：用 `gcc` 编译一个打印 `ruid/euid` 的小程序，`chown root:root` 后 `chmod 4755`；再写一个同样 4755 的 shell 脚本；以 `realtyz` 分别执行。
> **预期**：SUID 二进制以属主 `euid=0` 执行；脚本上的 SUID 被内核忽略，`uid` 仍是 1000。
> **风险**：低。涉及 SUID 文件，只放在 `/tmp` 并立即清理。
> **耗时**：约 10 分钟。
> **回滚**：删测试文件（先 `chmod 755` 再 `rm -rf`）。
>
> ```bash
> mkdir -p /tmp/07-suidbit && cd /tmp/07-suidbit
> cat > w.c <<'EOF'
> #include <stdio.h>
> #include <unistd.h>
> int main(void){ printf("ruid=%d euid=%d\n", getuid(), geteuid()); return 0; }
> EOF
> gcc -o w w.c
> chown root:root w && chmod 4755 w
> runuser -u realtyz -- /tmp/07-suidbit/w
> printf '#!/bin/bash\nid -u\n' > sc.sh
> chmod 755 sc.sh && chown root:root sc.sh && chmod 4755 sc.sh
> stat -c "mode=%a %A %n" sc.sh
> runuser -u realtyz -- /tmp/07-suidbit/sc.sh
> ```
>
> 实测输出：
>
> ```text
> ruid=1000 euid=0                 （ELF + SUID：euid 变成属主 root）
> mode=4755 -rwsr-xr-x sc.sh       （脚本的 SUID 位确实设上了）
> 1000                             （但执行时 uid 仍是 1000，SUID 被忽略）
> ```
>
> 脚本的 SUID 位**确实设上了**（`stat` 显示 `4755`、`ls -l` 显示 `s`），但执行时 `id -u` 仍是 1000——内核按 `execve(2)` 的规定忽略脚本上的 set-user-ID 位（实际执行的是 `#!` 指定的解释器，而解释器自己不带这个位）。
>
> 顺带实测了两个容易踩的点：`chown` 会清掉 SUID 位，以及 `no_new_privs` 会让 SUID 失效。
>
> ```bash
> chmod 4755 w && chown root:root w    # 验证：chown 在 chmod 之后会清掉 SUID 位
> stat -c "mode=%a %A %n" w            # 验证：结果是 755，不是 4755
> chown root:root w && chmod 4755 w    # 验证：正确顺序是先 chown 再 chmod
> runuser -u realtyz -- setpriv --no-new-privs /tmp/07-suidbit/w
>                                       # 验证：no_new_privs 下 SUID 被忽略
> ```
>
> ```text
> mode=755 -rwxr-xr-x w            （chmod 后 chown：位被清掉）
> mode=4755 -rwsr-xr-x w           （chown 后 chmod：位保留）
> ruid=1000 euid=1000              （no_new_privs：SUID 被忽略）
> ```

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 用 `find -perm 4000` 核查 SUID | 精确匹配会漏掉 4755 |
| 只查 SUID 就宣布「没有提权点」 | file capabilities（本机 4 个）、sudo、可写脚本等仍在 |
| 给脚本加 SUID | 内核忽略脚本上的 set-user-ID 位；位能设上，但不生效 |
| `chmod 4755` 之后又 `chown` | `chown` 会清掉 SUID/SGID 位，最终 mode 回到 755 |
| 按绝对路径 `dpkg -S` 查不到就判定异常 | usrmerge 下要先按 basename 再查 |
| 认为 SUID 文件数量少就安全 | 关键不是数量，是「与基线相比有没有新增」 |

## 决策练习

> [!question]- 场景：你发现系统里多了一个 `/usr/local/bin/backup`，mode 4755，`dpkg -S backup` 查不到。同事说「可能是运维自己编译的，先放着」。你怎么办？
> A. 先放着，等下周再说
> B. 立即按事件处理：取 `stat` 时间、校验哈希、查来源与变更记录、与其他机器基线比对；无法解释就隔离并上报
> C. 把 SUID 位去掉就结束
>
> **答案：B。**
> A 风险过高：SUID root 文件等于一个持久提权入口。
> C 只消除了当前表象，没有解释它怎么出现、有没有其他同类文件。
> B 是正解：**不属于包、无变更记录的 SUID 文件要按事件处置。**

## 要点自测

> [!question]- SUID/SGID/Sticky 各做什么？
> - SUID 执行时换 `euid`；SGID 文件换 `egid`，目录让新文件继承属组；Sticky 只让目录内属主删自己的文件。
> - 本机实测：4755 的 ELF 以 `realtyz` 跑出 `ruid=1000 euid=0`；4755 的脚本跑出 `uid=1000`（SUID 被忽略）。
> - **第一反应不要是什么**：不要把目录的 SGID 理解成提权。

> [!question]- 设了 SUID 却不生效，先查哪三件事？
> - ① 位有没有被清掉：`stat -c %a` 看是不是 4755（`chmod` 后又 `chown` 会清掉）；
> - ② 文件系统有没有 `nosuid`：`findmnt -T <path> -o OPTIONS`；
> - ③ 执行环境有没有 `no_new_privs`：`setpriv --no-new-privs` 下 SUID 被忽略。
> - **第一反应不要是什么**：不要只说「内核忽略了」就收工——先确认位还在、挂载点没 `nosuid`。

> [!question]- `find -perm` 三种写法差在哪？
> - `-4000` 是包含、`4000` 是精确、`/6000` 是任一；核查 SUID 用 `-4000`。
> - **第一反应不要是什么**：不要用精确写法，会漏掉 4755。

> [!question]- 提权面为什么不止 SUID？
> - 因为还有 file capabilities、sudo、root 执行的可写文件、SSH 钥匙、动态链接器、内核/设备、容器、挂载选项等。
> - 每一类都要有核查命令并进基线。
> - **第一反应不要是什么**：不要只跑 `find -perm -4000` 就宣布干净。
