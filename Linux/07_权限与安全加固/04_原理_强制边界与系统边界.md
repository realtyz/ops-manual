# 强制边界与系统边界

## 1. 只靠「主体属性 × 客体属性」，有三类约束表达不出来

前面三篇的判定都建立在同一种材料上：进程的身份与能力、客体的属主与权限位。这套材料撑不起三类真实需求：

**属主自己愿意给，系统仍然不同意。** Web 服务进程被攻破后，它做的一切都在文件权限允许的范围内——因为它本来就以那个身份运行。而管理员希望表达的是「这个程序只应该读 `/var/www/html`，不该碰 `/etc/shadow`，哪怕它以 root 运行」。这是**与属主意愿无关的策略**，正是「强制」二字的含义。

**同一个身份在不同程序里应当有不同边界。** `rsyslogd` 与一个无关的守护进程都以 root 运行时，权限位给出的是同一个答案。需要的是一层「按程序或按标签」而不是「按属主」的仲裁。

**有些对象根本不是文件。** 「普通用户能不能绑定 1024 以下的端口」「普通用户能不能读内核日志与内核指针」「某个挂载点上的 SUID 位算不算数」——这些问题的答案不在任何 inode 的属性里，而在系统级的开关与挂载表里。

于是判定链在后面又接了三段：**MAC（Mandatory Access Control，强制访问控制）按策略仲裁；挂载选项给整个文件系统加一层统一约束；内核参数关掉全局的危险入口。** 它们的共同特征是：**与属主的意愿无关，且作用于一批对象而不是单个文件**。

## 2. MAC 的仲裁模型：路径或标签

两种主流的 MAC 实现，判定依据不同：

| | SELinux | AppArmor |
| --- | --- | --- |
| 常见发行版 | RHEL/Fedora 系 | Debian/Ubuntu 系 |
| 判定依据 | 客体与主体的**安全上下文**（`user:role:type:level`，核心看 `type`） | **程序路径**对应的 profile |
| 标签存在哪 | 存在 inode 的 `security.selinux` 属性上 | 不标记客体；策略按可执行文件路径匹配 |
| 主要模式 | `enforcing`（阻断并审计）、`permissive`（只审计不阻断）、`disabled` | `enforce`（阻断并记录）、`complain`（放行并记录）、未加载 |
| 查看入口 | `getenforce`、`sestatus`、`ls -Z` | `aa-status`、`/sys/kernel/security/apparmor/` |

**「标签随 inode 走、不随路径走」是 SELinux 最需要先记住的一条。** 把文件从有正确标签的目录移到别处，标签跟着文件走，于是既可能保留正确的标签，也可能带着错误的标签引发拒绝；`mv` 不重新打标签，`cp` 默认按目标位置的规则重新生成。这解释了「移动文件之后服务突然起不来」：修法通常是 `restorecon` 让文件按路径重新取得策略期望的标签，或 `semanage fcontext` 为新路径登记规则。

**AppArmor 以程序路径为中心**，因此它的策略写作更接近直觉（「这个程序能读哪些路径、能用哪些能力、能不能联网」），代价是**同一条路径被换掉就换了策略对象**，且对「同一程序处理不同数据」的细分能力弱于 SELinux。

两种实现的证据入口也不同，这里最容易出错：

- SELinux 的拒绝记录是 `avc: denied { 权限 } for ...`；
- AppArmor 的拒绝记录是 `apparmor="DENIED" ... denied_mask="..."`；
- **两者都以 `type=AVC` 的审计记录形式出现。** 看到 `type=AVC` 就要先看里面的语法，才能判断是哪一个 LSM 在说话，进而决定用 `restorecon`/`semanage`/`setsebool` 还是改 profile。

## 3. 拒绝记录落在哪里，取决于 auditd

这是 MAC 排障里最反直觉的一点：**同一台机器上，「去哪儿看拒绝」不是固定答案。**

- 如果 **auditd 在运行**，LSM 的拒绝会作为审计事件交给它，落在审计日志里（Debian/Ubuntu 上是 `/var/log/audit/audit.log`），**不进** `dmesg`/`journalctl -k`；
- 如果 **auditd 没在运行**，记录会走内核的 printk 路径，于是出现在 `dmesg`/`journalctl -k` 里。

`dmesg` 里那些更早的 `type=1400` 记录常常是**引导期**策略装载留下的（`apparmor="STATUS"` 一类），时间戳在开机后几秒内。把它们当成本次事件的证据，就会得出「拒绝就发生在内核日志里」的错误结论。

还有一个工具层面的坑：`ausearch` 的可用性依赖 `/etc/audit/auditd.conf` 的 `log_format` 等配置，**它返回空结果不必然等于「没有事件」**。可靠的兜底手段是直接 `grep` 审计原始文件；另外 `ausearch` 会从 stdin 读取原始日志数据，脚本里必须显式断开（`</dev/null` 或 `-if <file>`），否则它可能一直等待输入。

**判断这台机器上有没有 SELinux，有三步只读检查**：`ls -d /sys/fs/selinux` 是否存在、`/sys/kernel/security/lsm` 里有没有 `selinux`、`getenforce`/`restorecon`/`semanage` 一类工具在不在。**装几个包不等于策略已加载——`enforcing` 需要内核在引导时就启用 SELinux。**

## 4. AppArmor 的三种状态，以及 `complain` 的边界

AppArmor 的 profile 有三种状态：`enforce`（完全生效）、`complain`（隐式拒绝放行并记录）、以及未加载（unconfined）。这里的边界必须说清楚：

**`complain` 放行的只有「隐式拒绝」**——即允许列表里没有写、在 `enforce` 下会被拒的那些权限。**profile 里显式写的 `deny` 规则在两种模式下都拒绝**，因为 `deny` 是绝对规则，不参与「模式放宽」。

因此 `complain` 的正确用法是**定位工具**：先在 `complain` 下跑业务、收集「原本会被拒」的日志、补全允许列表，再切回 `enforce` 复验。**「在 `complain` 下跑了一段时间没报错」不构成策略正确的证据**，它只说明没有显式 `deny` 被触发。

另外一条与 MAC 相关、又容易被误判为「缺 capability」的现象：Ubuntu 从 24.04 起默认限制**非特权用户命名空间**（`kernel.apparmor_restrict_unprivileged_userns=1`），非 root 在 user namespace 里映射 uid 0 会被拒绝。它的表现是 `EPERM`，**而且不产生对应的 `apparmor="DENIED"` 审计记录**——这正是「MAC 叠在 capabilities 之上」的一个实例：能力足够，仍然过不去。

## 5. 挂载选项：把约束挂在整个文件系统上

挂载选项是对「这个文件系统上的一切」生效的约束，因此它天然适合处理「不该有特权位的目录」：

| 选项 | 拦什么 | 典型用途 |
| --- | --- | --- |
| `nosuid` | 该挂载点上 SUID/SGID **与 file capabilities** 一并失效 | 可被普通用户写入的挂载点、数据盘 |
| `nodev` | 设备文件不生效 | 可被写入的挂载点、网络文件系统 |
| `noexec` | 禁止直接执行该挂载点上的二进制（含带 `#!` 的脚本文件本身） | 上传目录、备份盘 |
| `ro` | 整体只读 | 备份归档、不可变目录 |

三点必须记住的边界：

**`nosuid` 的覆盖面比它的名字大。** 它同时让 SUID/SGID 与 file capabilities 失效——因为两者都在 `execve` 阶段被授予特权，`nosuid` 关掉的是这一步。**在 `nosuid` 挂载点上排查「为什么 SUID 不生效」，属于预期行为。**

**`noexec` 拦不住解释器。** 它阻止的是「直接执行这个文件」，而 `bash script.sh`、`python3 a.py` 是**直接执行 `bash`/`python3`**，脚本只是被当作数据读进去。**上传目录只加 `noexec` 是不够的**，还要收紧属主与写权限，否则攻击者可以把载荷放在那里、用解释器跑起来。

**`/tmp` 不一定是独立挂载点。** 它可能只是根文件系统上的一个普通目录（`1777` 的 sticky 权限），此时它**没有任何** `nosuid`/`nodev`/`noexec`。判断方法是 `mountpoint -q /tmp` 与 `findmnt -T /tmp`，而不是假设发行版一定把 `/tmp` 做成了 tmpfs。**「`/tmp` 上有 sticky」与「`/tmp` 被挂载选项保护」是两件不同的事。**

## 6. 内核安全参数：关掉全局入口，代价常常是可观测性

一组 `sysctl` 参数构成系统级边界，它们的共同点是「不为某个服务改变，而是改变整机的默认行为」：

| 参数族 | 关掉什么入口 | 代价 |
| --- | --- | --- |
| `fs.protected_regular` / `protected_fifos` / `protected_hardlinks` / `protected_symlinks` | 普通用户在全局可写目录里借普通文件、FIFO、硬链接、符号链接做的攻击 | 少数依赖旧行为的程序会受影响 |
| `kernel.yama.ptrace_scope` | 普通用户 `ptrace` 其他进程（含读取其内存） | 本机调试与部分诊断工具受限 |
| `kernel.unprivileged_bpf_disabled` | 非特权进程加载 BPF 程序 | 部分 eBPF 观测工具需要 root |
| `kernel.kptr_restrict` | 普通用户读内核地址（`/proc/kallsyms` 等） | 符号化内核栈、部分调试手段失效 |
| `kernel.dmesg_restrict` | 普通用户读内核环形缓冲 | 非 root 拿不到内核日志 |
| `kernel.perf_event_paranoid` | 非特权 `perf` 事件采集 | 性能分析必须在 root 下做，或部分事件不可用 |
| `net.ipv4.ip_unprivileged_port_start` | 普通用户可绑定的起始端口 | 改成 0 等于任何用户可绑低端口 |
| `fs.suid_dumpable` | SUID 进程能否产生 core | 影响崩溃现场的可获取性 |

**这些参数是「安全与可观测性」的显式交易。** `kptr_restrict`、`dmesg_restrict`、`perf_event_paranoid` 收紧之后，排障时能拿到的证据一起变少——**把安全参数一律拉到最严，等于在出故障时把自己的工具一起关掉**。取舍要写进变更记录，并在演练里验证「出事时还能查」。

**参数值的来源有三处，缺一处就会误判。** `sysctl` 的生效值来自内核/发行版编译默认值与一组配置目录的合并（`/etc/sysctl.d/`、`/run/sysctl.d/`、`/usr/lib/sysctl.d/`，`/etc/sysctl.conf` 通常通过 `/etc/sysctl.d/99-sysctl.conf` 软链参与）。合并规则是「按文件名字典序应用，名字靠后的覆盖靠前的；同名文件以 `/etc` 优先」。因此：

- **当前值在任何配置文件里都找不到，是正常情况**——它来自内核或发行版默认。判断来源要「查当前值 → 遍历各目录 → 承认可能来自默认」三步走；
- **`sysctl -w` 只是临时改**，持久化必须落进 `/etc/sysctl.d/` 并确认合并顺序；
- **`net.*` 参数在 network namespace 内独立**，需要验证「改成 0 会怎样」这类问题时，在独立命名空间里做即可，不影响宿主机。

## 7. 抽象在哪里漏水

**MAC 不是「打开就安全」。** 它需要策略与标签都正确；错误的标签、遗漏的规则会让服务起不来，而 `permissive`/`complain` 只是把问题藏起来。**顺序应当是「先让策略正确，再进强制模式」。**

**「关掉强制模式」与「修复」的差别必须写进流程。** 把 SELinux 切成 `permissive` 并不阻止审计：拒绝记录**仍然产生**，攻击面回到 DAC。真正危险的是「切过去忘了切回来」——它把一次显式的临时措施变成长期状态。

**挂载选项与内核参数都是全局或半全局的。** 为单个服务改动 `ip_unprivileged_port_start=0`、给数据盘整体加 `noexec` 而没盘点谁在执行、把 `perf_event_paranoid` 拉高导致排障工具失效——这些都是「用整机策略解决局部问题」。**改之前要能回答：还有谁在这个范围内。**

**「能力足够」与「策略允许」是两道独立的门。** 一个进程可以同时拥有所需 capability 与文件权限，却因为 MAC 或挂载选项被拒；反过来说，MAC 放行也不代表 capability 满足。定位时必须按层走，不能把两者混成一句「权限不够」。

## 常见误解

| 常见说法 | 事实 |
| --- | --- |
| 「Ubuntu 上默认没有 MAC」 | Debian/Ubuntu 默认启用 AppArmor；`/sys/kernel/security/lsm` 里能看到它 |
| 「`setenforce 0` 就是解决问题」 | 它只是把阻断关成只审计；策略不对、标签不对的问题依然存在，且审计与拒绝记录照常产生 |
| 「`complain` 模式下 profile 完全不生效」 | 隐式拒绝会被放行并记录；**显式 `deny` 规则在两种模式下都拒绝** |
| 「装了 SELinux 工具就等于启用了 SELinux」 | `enforcing` 需要内核在引导时启用 SELinux；工具存在只说明用户态组件在 |
| 「MAC 拒绝都在 `journalctl -k` 里」 | auditd 在运行时，拒绝落在审计日志；`dmesg` 里常见的 `type=1400` 多为引导期策略装载记录 |
| 「`ausearch` 返回空就是没发生」 | 结果依赖审计配置；要用 `grep` 审计原始文件交叉验证 |
| 「`nosuid` 只管 SUID」 | 它同时让 file capabilities 失效 |
| 「`noexec` 能防住上传目录里的执行」 | 它拦不住 `bash`/`python3` 等解释器；还要收紧属主与写权限 |
| 「`/tmp` 一定是带 `nosuid`/`nodev` 的 tmpfs」 | 它可能只是根文件系统上的 `1777` 目录，一个挂载选项都没有 |
| 「`S` 与 `s`、`t` 与 `T` 是同一回事」 | 大写表示对应执行位本身没打开，特殊位的语义在缺执行位时不完整 |
| 「`sysctl` 的当前值一定在某份配置文件里」 | 可能来自内核/发行版默认；`sysctl -w` 的值也不会出现在文件里 |
| 「安全参数越严越好」 | 收紧 `dmesg_restrict`/`kptr_restrict`/`perf_event_paranoid` 会同时削弱排障能力，要显式取舍并演练 |

## 要点自测

**问：DAC 与 MAC 的根本区别是什么？**
答：DAC 是属主自主决定——通过 mode 与 ACL 决定谁能访问，属主有权修改；MAC 是系统策略强制决定——即使属主愿意给，策略不允许就不能访问，属主无法绕过。SELinux 依据客体与主体的安全上下文，AppArmor 依据程序路径对应的 profile。

**问：为什么「MAC 拒绝了」这件事在有的机器上查不到？**
答：记录的落点取决于 auditd 是否在运行：在运行时 LSM 拒绝作为审计事件写入审计日志，不在时才走内核日志。`dmesg` 里那些更早的 `type=1400` 往往是引导期策略装载记录，不是本次事件。

**问：`complain` 模式下 profile 会做什么、不会做什么？**
答：会放行「允许列表里没写」的隐式拒绝并记录；不会放行 profile 里显式写的 `deny` 规则。因此 `complain` 只能用来收集信息，验收必须在 `enforce` 下做。

**问：`nosuid` 与 `noexec` 各拦什么、各拦不住什么？**
答：`nosuid` 让该挂载点上 `execve` 阶段的一切特权授予失效（SUID、SGID 与 file capabilities）；`noexec` 只拦「直接执行这个文件」，拦不住把脚本交给解释器执行。两者都不影响文件自身的读写权限。

**问：为什么一个 `sysctl` 的当前值可能在任何配置文件里都找不到？**
答：生效值是「内核/发行版编译默认值」与若干配置目录合并的结果；发行版常常依赖编译默认而不写文件。判断来源要查当前值、遍历 `/etc/sysctl.d/` 与 `/usr/lib/sysctl.d/`，并承认可能来自默认。`sysctl -w` 只在运行时生效，也不写文件。

**问：为什么说收紧内核安全参数要「显式取舍」？**
答：`dmesg_restrict`、`kptr_restrict`、`perf_event_paranoid` 这类参数在减少信息泄露的同时，会让非 root 的日志读取、符号化与性能观测失效。取舍应当写进变更记录，并在演练里确认「出事时还能拿到需要的证据」。

**第一反应不要做什么**：不要把 `setenforce 0` 或切 `complain` 当修复；不要假设 `/tmp` 一定被挂载选项保护；不要为单个服务改动整机级内核参数。
