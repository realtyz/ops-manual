# 提权面与最小特权

## 1. 让「要么全有、要么全无」成为特权模型的全部，会同时出三件事

前面两篇讲的是判定：主体是谁、客体允许什么。剩下一个问题是主体**凭什么**拥有那些权限。如果答案只有「root 拥有一切，其他身份什么都没有」，三件事会立刻出问题：

**需要一个完整 root 才能做一件小事。** 读取 ICMP 需要构造原始套接字，绑定 80 端口需要绑定特权端口，调整时钟需要设置系统时间。这些动作各自只需要一项能力，却要求进程整体变成 root。

**每一处「需要一点特权」都变成一个持久入口。** 为了让普通用户修改自己的密码，`passwd` 必须能写 `/etc/shadow`。做法是给它设 SUID：任何用户执行它时进程身份变成 root，**而且这个入口在磁盘上长期存在**。

**权限判断的粒度太粗，无法表达「只在这一步提权」。** 一个要绑定低端口的常驻服务，如果靠启动时是 root 来解决，那么它在整个生命周期里都带着 root。

Linux 对这三点给出了两套答案，它们叠在一起构成了「提权面」：**SUID/SGID 是粗粒度的、以文件为载体的身份切换；capabilities 是细粒度的、按项授予的特权。** 「提权面」这个词指的就是所有「从普通身份变成更强身份」的路径的集合——它远不止 SUID。

## 2. 三个特殊位各做什么

| 位 | 位置 | 作用 | 生效对象 |
| --- | --- | --- | --- |
| SUID（`4`） | 文件属主执行位显示为 `s` | `execve` 时把进程的 `euid` 换成文件属主；`suid` 保存原 `euid` 以便切回 | 可执行文件 |
| SGID（`2`） | 文件属组执行位显示为 `s`；目录上显示为 `S`/`s` | 文件：`execve` 时把 `egid` 换成文件属组；**目录：在其内新建的对象继承目录的属组** | 文件与目录 |
| Sticky（`1`） | other 执行位显示为 `t`/`T` | 目录内只有**文件属主、目录属主或 root** 能删除或改名条目 | 目录 |

三点容易混的边界：

- **SGID 用在目录上不是提权。** 它的作用只是让协作目录里的新文件自动归到同一个组；如果看到目录上的 `s` 就按「提权点」处理，会浪费排查时间。
- **SGID 用在文件上换的是 `egid`**，而组权限在判定中同样参与，所以它确实是提权面的一部分。
- **sticky 只约束删除与改名**，不约束读写。`/tmp` 用 `1777` 就是「谁都能放，但不能删别人的」。

还有两个与 SUID 常常一起出现、必须区分的概念：

- **dumpable**：当进程的 `euid` 与 `ruid` 不一致（或 `fsuid` 被改动）时，内核会把该进程标记为不可 dump，`/proc/<pid>` 下的一些文件属主也会变成 root。这就是 SUID 程序崩溃时通常拿不到 core 文件的机制来源。`fs.suid_dumpable` 决定这一行为。
- **`no_new_privs`**：一个进程标志，置位后 `execve` **不再授予任何新特权**——SUID 与 file capabilities 一并失效。容器与 systemd 服务常用它把「提权」这条路整体关掉。

## 3. SUID 是怎么被执行的，以及它的三个条件

SUID 的生效点在 `execve(2)`。内核在这一步做四件事：解析文件、检查执行权限、若满足条件则调整 `euid`/`egid`、装载映像。**只要有一个条件不满足，特权提升就被忽略——而且不报错。**

三个条件：

1. **调用进程没有设置 `no_new_privs`**；
2. **文件所在的挂载点没有 `nosuid`**；
3. **进程没有被 `ptrace`（跟踪）**。

第 3 条容易被忽略：调试器跟踪一个 SUID 程序时，SUID 不会生效。这是有意的——否则任何能 `ptrace` 的人都能借别人的 SUID 程序提权。

**「不报错」是这条机制最需要注意的性质。** 位设了、程序跑起来了、退出码正常，但 `euid` 没有变。诊断顺序因此是固定的：先确认位还在（`stat -c %a`）、再确认挂载点没 `nosuid`（`findmnt -T <path> -o OPTIONS`）、再确认执行环境没有 `no_new_privs` 或 `ptrace`。

**脚本上的 SUID 被内核忽略。** Linux 明确对 `#!` 脚本不应用 set-user-ID/set-group-ID 位：带 `#!` 的文件实际执行的是解释器，内核只为解释器的可执行映像做身份切换。**这解释了「位明明设上了（`stat` 显示 4755、`ls -l` 显示 `s`）却不生效」**——这是设计选择而非缺陷：如果脚本能继承身份，那么任何能写那个脚本的人（或它引用的任何文件）都等于拥有了该身份。

**`chown` 会清掉 SUID/SGID 位。** 这是「我明明设了 SUID」的另一个常见成因：先 `chmod 4755` 再 `chown`，位会被一起清掉。正确顺序是**先 `chown`，再 `chmod`**。

## 4. 从「全有」到「按项授予」：capabilities

capabilities 把传统上属于 root 的特权拆成若干项，内核用编号 0 到 `cap_last_cap` 标识它们（当前基线内核上 `cap_last_cap` 的取值要现场 `sysctl kernel.cap_last_cap` 取，不要凭记忆）。每个进程携带五个集合：

| 集合 | 含义 | 要点 |
| --- | --- | --- |
| Permitted | 进程**允许**持有的能力上限 | 丢出 Permitted 的能力，之后不能凭空加回 |
| Effective | **当前生效**的能力 | 内核做特权检查时看它 |
| Inheritable | 跨 `execve` 可被继承的那部分 | 语义最绕、实际很少需要的集合 |
| Bounding | 所有后代进程的**硬上限** | 一旦从 Bounding 里去掉某项，`execve` 无法再拿回它 |
| Ambient | 非特权（`uid != 0`）程序跨 `execve` **保留**的能力 | 让「非 root 服务带着某一项能力运行」成为可能 |

`execve` 时这些集合怎么变换，是理解 file capabilities 的关键。简化后的规则是：

- **非特权进程**（`euid != 0`）执行文件：新 Permitted = 文件 Permitted **与** 进程 Bounding 的交集；新 Effective 只在文件带有 Effective 位时才置位，否则为空；而**进程原来的 Ambient 集合会被清空**——除非文件带有 SUID/SGID 位，或该文件没有任何 file capabilities。
- **特权进程**（`euid == 0`）执行文件：通常会拿回 Bounding 里的全部能力（除非文件带 file capabilities，此时按文件与 Inheritable 计算）。
- **Ambient 的约束**：某能力要进入 Ambient，它必须同时在 Permitted 与 Inheritable 里，并且在 Bounding 里；Ambient 集合的变更只能做「全部清空」或「加/减一项子集」。

两条由此得到的实务结论：

**Bounding 是最强的一道闸。** systemd 的 `CapabilityBoundingSet=` 直接写它——即使服务内部出了漏洞、即使有人修改了服务二进制，后代进程也拿不到被排除的能力。**「Bounding 收紧」比「Permitted 收紧」更难被绕过。**

**「非 root 进程带着一项能力」需要三件事同时成立**：该能力在 Bounding 里、在 Permitted 里、并且进入了 Ambient（或在被授予的文件上带 Effective 位）。只做其中一件，行为会与预期不符。

## 5. 文件能力：把特权挂到文件上

`+ep` 表示把该能力加到文件的 Permitted（`p`）与 Effective（`e`）集合。它带来的好处是：**文件在 mode 上没有任何标记**（`ls -l` 看不到 `s`），授予的能力范围也明确可读（`getcap` 或 `getfattr -n security.capability`）。

**要自己确认某个文件带不带能力，不能靠看权限位**：`ls -l` 上带能力的文件与普通文件长得完全一样，必须去读 `security.capability` 这个扩展属性。把同一份能力加到一个 ELF 与一个脚本上各跑一次，差异会直接暴露「内核只对可执行映像应用」这条规则。

**但「xattr 设置成功」与「执行时生效」是两件事**，原因与 SUID 完全对称：

- **内核只对 ELF 应用 file capabilities。** 对 `#!` 脚本 `setcap` 会返回成功、`getcap` 也会显示有值（xattr 确实写进去了），但执行时内核应用的是解释器，脚本自身的能力不生效。**症状只在运行时暴露**，所以「`getcap` 显示有、跑起来没用」是这类操作的典型现象，不是工具在骗人。
- **file capabilities 与 SUID 受同一类拦截**：`no_new_privs`、`nosuid` 挂载、被 `ptrace` 时同样被忽略。
- **文件被替换即等于能力被转移。** 一个带 `cap_net_raw=ep` 且属主可写的二进制，本质上是一个可被改写的特权程序。因此带能力的文件应当属于 root 且不可被非 root 写。

顺带一个检查习惯：**只查 SUID 会漏掉整整一半提权面。** `ping` 一类工具在现代发行版上已经改成 file capabilities，`ls -l` 上没有任何痕迹；提权面盘点必须把 `find -perm -4000`/`-2000` 与 `getcap` 一起跑，并与基线比对。

## 6. 抽象在哪里漏水

**能力是能力的上限，不是行为的边界。** 给一个进程 `CAP_SYS_ADMIN` 或 `CAP_NET_ADMIN`，它能做的事与 root 相差无几——**「最小特权」只有精确到具体那一项时才有意义**。授权清单里出现大范围能力，等于没有做最小特权。

**`setcap` 不是 SUID 的同义替换。** 当目标是一个解释器脚本、或被 `nosuid`/`no_new_privs` 约束的环境时，两者会一起失效；而当目标是需要「启动时拿特权、随后降权」的服务时，systemd 的 `AmbientCapabilities=` 与 `CapabilityBoundingSet=` 比给二进制加能力更可控、更容易审计。

**提权面远不止这两类。** 完整的清单还包括：`sudo`/`su` 的授权配置、**以 root 身份执行但可被非 root 写入的脚本与配置**（cron、unit 的 `ExecStart`、`PATH` 上的目录）、SSH 的 `authorized_keys`、动态链接器相关的 `/etc/ld.so.preload` 与 `LD_PRELOAD`、内核与设备接口（模块加载、`/dev/mem`、非特权 BPF）、容器特权、以及挂载选项缺失导致的 SUID 生效面扩大。**任何一条都能在不碰 SUID 的情况下拿到 root。**

**「多一个」比「有多少个」重要。** SUID 文件的数量本身没有阈值意义；有意义的是**与上次留档清单的差异**，以及新增项能否用包管理器反查到归属。查不到归属又没有变更记录的 SUID 文件，是最高优先级的事件信号。

**删除文件不等于撤销能力。** SUID 位与 file capabilities 都随 inode 走。把文件移到别处、改个名字，权限不变；备份恢复时若用 `cp -r`、`tar`（不带 `--xattrs`）、`rsync`（不带 `-X`），能力可能被静默丢弃或保留——**备份链路上的这一层差异会让「安全」与「不可用」同时出现。**

## 常见误解

| 常见说法 | 事实 |
| --- | --- |
| 「SUID 能让任何程序以 root 运行」 | 只有 ELF 可执行文件生效，且要同时满足没有 `no_new_privs`、挂载点没有 `nosuid`、未被 `ptrace` |
| 「脚本上设 SUID 也行」 | 内核忽略脚本上的 set-user-ID/set-group-ID 位，执行的是解释器 |
| 「`chmod 4755` 之后就一定生效」 | 之后再 `chown` 会把位清掉；顺序必须是先 `chown` 再 `chmod` |
| 「`ls -l` 看不出能力就等于没有能力」 | file capabilities 显示为普通 `-rwxr-xr-x`，要看 `getcap` 或 `getfattr -n security.capability` |
| 「`setcap` 对脚本也有效」 | 内核只对 ELF 应用；对脚本会「设得上、不生效」 |
| 「`setcap` 不受 `nosuid`/`no_new_privs` 约束」 | 它与 SUID 受完全同一类拦截 |
| 「把能力给二进制和把能力给服务是一回事」 | 二进制文件是可替换的提权载体；服务的 unit 属性更可控、更可审计 |
| 「`CAP_SYS_ADMIN` 只是『一项』能力，风险不大」 | 它涵盖挂载、命名空间、大量设备与内核操作，实际接近完整 root |
| 「提权面就是 SUID 清单」 | 还有 file capabilities、sudo、可写的 root 脚本/配置、SSH 钥匙、`ld.so.preload`、内核与设备、容器、挂载选项 |
| 「SUID 文件数量不多就说明干净」 | 判据是与基线清单的差异，以及新增项能否反查到包归属 |

## 要点自测

**问：设了 SUID 却不生效，按什么顺序查？**
答：先 `stat -c %a` 看位是否还在（`chmod` 后再 `chown` 会清掉），再 `findmnt -T <path> -o OPTIONS` 看挂载点有没有 `nosuid`，再确认执行环境没有 `no_new_privs`、进程没有被 `ptrace`。若二进制换成脚本，则本来就不该生效。

**问：为什么内核忽略脚本上的 SUID，而 file capabilities 对脚本也无效？**
答：带 `#!` 的文件实际执行的是解释器，内核只对真正的可执行映像（ELF）应用提权；否则任何能改写脚本或其引用文件的人都等于获得了那个身份。所以这两种机制在脚本上都是「设得上、不生效」。

**问：Ambient capabilities 要生效，需要同时满足哪些条件？**
答：该能力在 Bounding 集合里、在 Permitted 里、并进入 Ambient 集合；三者缺一，非 root 进程跨 `execve` 就保留不住它。这也是 systemd 里必须同时写 `CapabilityBoundingSet=` 与 `AmbientCapabilities=` 的原因。

**问：为什么收紧 `CapabilityBoundingSet=` 比收紧 `Permitted` 更彻底？**
答：Bounding 是所有后代进程的硬上限，从里面去掉的能力在 `execve` 时无法再拿回；而 Permitted 只约束当前进程。即使服务后续被换了二进制或派生了子进程，Bounding 仍然生效。

**问：为什么说「只查 SUID 会漏掉一半提权面」？**
答：现代发行版把不少原本 SUID 的工具改成 file capabilities（`ls -l` 完全看不出痕迹），同时 `sudo`/`su` 授权、root 执行的可写脚本与配置、SSH 钥匙、动态链接器、内核与设备接口、容器特权、挂载选项缺失都能通向 root。提权面盘点要按类别逐项核查并留档。

**问：为什么 file capabilities 的文件必须不可被非 root 写？**
答：能力挂在文件上，而文件内容决定执行行为。谁能改写这个文件，谁就获得了它承载的能力——文件本身就成了一个提权载体。

**第一反应不要做什么**：不要在脚本上加 SUID 或 file capabilities；不要在只跑了 `find -perm -4000` 之后就宣布提权面干净；不要把 `CAP_SYS_ADMIN` 一类大范围能力当作「只给了一点点」。
