## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **一个工具回答一个问题**：`id` 看主体，`stat`/`ls -l` 看客体基本属性，`namei` 看路径逐级，`getfacl` 看精细授权，`getcap` 看能力，`ls -Z` 看 MAC 标签。
> - **`ls -l` 的 `+` 是提示，不是答案**：带 `+` 只说明有 ACL；想知道到底给了谁、mask 多少，必须 `getfacl`。
> - **`stat` 比 `ls -l` 更接近内核事实**：`stat -c "%a %A %u %g %n"` 直接打印 mode、UID、GID，便于脚本和台账留档。
> - **`namei -l` 一次看全路径**：从 `/` 到目标文件逐级显示属主、mode，是定位「路径缺 `x`」的最快命令。
> - **核查要能留档、能比对**：输出固定字段、写进基线文件，下次用同一命令重跑，差异就是异常。

## 1. 工具地图

| 命令 | 回答的问题 | 看的是哪一层 | 典型用法 |
| --- | --- | --- | --- |
| `id` | 这个进程/会话是谁、有哪些组 | 主体身份 | `id`、`id <user>` |
| `getent` | 按 NSS 查账号/组/服务 | 身份来源 | `getent passwd <user>` |
| `stat` | 文件的 mode、UID、GID、时间、inode | DAC 客体 | `stat -c "%a %A %u %g %n" <file>` |
| `ls -l` | 人和机器都能读的权限视图 | DAC 客体 | `ls -ld <dir>` |
| `namei -l` | 路径上每一级的权限与属主 | DAC 路径 | `namei -l /srv/app/secret` |
| `getfacl` | 完整 ACL、mask、effective | 精细授权 | `getfacl -cp <path>` |
| `lsattr` | `chattr` 的不可变/追加等属性 | 扩展属性 | `lsattr <file>` |
| `getcap` | 文件是否带 capabilities | capabilities | `getcap -r /usr 2>/dev/null` |
| `capsh --print` | 当前进程的能力集合 | capabilities | `capsh --print` |
| `ls -Z` / `stat -c %C` | SELinux 上下文 | MAC | `ls -Z /var/www/html` |
| `findmnt` | 挂载点与 `nosuid`/`noexec`/`nodev` 选项 | 挂载边界 | `findmnt -o TARGET,SOURCE,FSTYPE,OPTIONS` |
| `sysctl` | 内核安全参数当前值 | 内核边界 | `sysctl fs.protected_regular` |
| `ss -lntup` | 谁在监听哪个端口 | 入口边界 | `ss -lntup` |
| `systemctl list-unit-files --state=enabled` | 哪些服务开机会自启 | 持久化点 | `systemctl list-unit-files --state=enabled` |

## 2. 主体身份：`id` 与 `/proc/<pid>/status`

```bash
id                                   # 验证：当前用户的 uid/gid/附加组/上下文（上下文在支持 SELinux 的系统显示）
id someuser                          # 验证：按名字/UID 查另一个账号的身份
cat /proc/self/status | grep -E '^(Uid|Gid|Groups|Cap)' 
                                      # 验证：当前进程内核视角的 UID/GID/Groups/Cap 集合
```

排障时先固定「**是谁在访问**」。不要只看登录名，要看进程的 `euid` 和组。`sudo` 前是普通用户，`sudo` 后是 root；两者的身份不同，权限结果自然不同。

## 3. 客体与路径：`stat`、`ls -ld`、`namei`

```bash
stat -c "%a %A %u %g %n" /srv/app/config
                                      # 验证：mode 数值/符号、UID、GID、文件名
ls -ld /srv/app /srv/app/config       # 验证：目录与文件的常规权限，注意目录的 r/w/x
namei -l /srv/app/config              # 验证：从根目录到目标逐级权限，缺 x 一目了然
```

> [!important] 目录权限看路径，文件权限看最后一级
> `namei -l` 的价值是同时显示**路径上的每一级目录**。服务报 `EACCES` 时，最后一级文件 mode 可能完全正常，真正缺的是中间某级目录的 `x`。

## 4. 精细授权：`getfacl` 与 `lsattr`

```bash
getfacl -cp /srv/app/config           # 验证：完整 ACL，含 named user/group、mask、effective
lsattr /etc/passwd /var/log           # 验证：chattr 属性；e 是 ext4 正常 extent 标志，i/a 才需要关注
```

`ls -l` 结尾的 `+` 只说明 inode 带了 ACL。要判断「某个 named 条目到底还有没有效」，必须看 `getfacl` 里的 `mask` 和 `#effective`。

## 5. capabilities：`getcap` 与 `capsh`

```bash
getcap -r /usr 2>/dev/null | sort    # 验证：哪些文件带 capabilities；本机典型值含 /usr/bin/ping cap_net_raw=ep
capsh --print                         # 验证：当前进程的五个能力集合与 cap_last_cap
```

提权面核查里，**只查 SUID 会漏掉 file capabilities**。两者要一起查，一起进基线。

## 6. MAC 与挂载/内核边界

```bash
ls -Z /var/www/html 2>/dev/null       # 验证：SELinux 上下文；无 SELinux 时通常报错或显示 ?
findmnt -o TARGET,SOURCE,FSTYPE,OPTIONS /tmp /var/tmp /dev/shm
                                      # 验证：关键临时目录是否带 nosuid/nodev/noexec
sysctl fs.protected_regular fs.protected_fifos kernel.unprivileged_bpf_disabled
                                      # 验证：内核给普通用户关掉的危险入口
```

这些命令是只读的，生产机可以做。把它们加入基线采集脚本，定期与留档值比对。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 只用 `ls -l` 判断「有没有 ACL」 | `+` 只表示有 ACL，不显示给了谁、mask 多少 |
| 用 `find -perm 4000` 核查 SUID | 这是精确匹配，会漏掉 4755 的 `su`/`sudo`；要用 `-perm -4000` |
| 只看最后一级文件 mode | 漏掉路径上缺 `x` 的目录 |
| 只查 SUID 不查 capabilities | 漏掉 `/usr/bin/ping cap_net_raw=ep` 这类提权点 |
| 手动敲命令不留档 | 下次没有基线可比，异常出现时无法判断「什么时候多出来的」 |

## 决策练习

> [!question]- 场景：服务日志显示 `EACCES`，你只有 3 分钟先取一组证据。同事让你先 `chmod -R 777 /srv/app`。你会先跑哪几条只读命令？
> A. 只跑 `ls -l /srv/app`，然后按同事说的改
> B. 跑 `namei -l <path>`、`stat -c "%a %u %g %n" <path>`、`getfacl -cp <path>`、`id`，把四份证据贴出来再决定
> C. 先重启服务，看报错是不是偶发
>
> **答案：B。**
> A 证据不足，`chmod -R 777` 会开放写和执行。
> C 重启可能清掉现场，而且没有解决权限问题。
> B 是正解：**四份证据分别对应路径、客体、ACL、主体，能把拒绝发生的原因缩小到一层。**

## 要点自测

> [!question]- 想判断「这个用户能不能访问这个文件」，最少要哪几类信息？
> - 主体：`id`/`/proc/<pid>/status` 看 uid/gid/groups/capabilities。
> - 路径：`namei -l <path>` 看逐级目录 `x`。
> - 客体：`stat -c "%a %u %g"` + `getfacl` 看 mode 与 ACL。
> - 边界：必要时 `getcap`、`ls -Z`、`findmnt`。
> - **第一反应不要是什么**：不要只看文件本身。

> [!question]- `ls -l` 输出里的 `+` 代表什么？为什么不能只看它？
> - `+` 表示 inode 带 ACL；但它不显示 named 条目、mask 和 `#effective`。
> - 想知道有效权限，必须 `getfacl`。
> - **第一反应不要是什么**：不要看到 `+` 就以为「权限很复杂」，也不要看不到 `+` 就以为没有 ACL。

> [!question]- 为什么安全基线命令要写成脚本并留档？
> - 因为异常通常是「与上次不一样」：多一个 SUID 文件、多一个账号、多一个监听端口。
> - 留档后才能做 diff；否则只能凭印象判断，容易漏。
> - **第一反应不要是什么**：不要每次手工敲命令、看完就丢。
