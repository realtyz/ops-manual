# 前置：权限观测工具与证据命令

> [!cite] 参考资料
> `man 1 id`、`man 1 stat`、`man 1 namei`、`man 1 getfacl`、`man 1 getcap`、`man 1 lsattr`、`man 8 findmnt`、`man 1 ls`、`man 1 find`、`man 8 ss`、`man 8 systemctl`、`man 1 getent`。
>
> 实测环境：Ubuntu 24.04.5 LTS（VMware 虚拟机）/ 内核 6.8.0-139-generic / AppArmor 4.0.1 / root。本页命令全部为只读观测，**适合在生产机执行**；`getfacl`/`getfattr`/`getcap`/`lsattr`/`sysctl`/`findmnt`/`aa-status` 在真机/虚拟机上跑过。**SELinux 上下文相关命令（`ls -Z`、`stat -c %C`）未实测**——本机是 Ubuntu 且未安装 SELinux，没有上下文可看，正文已标注。

> **这篇讲什么**：把这一章反复出现的观测命令放进一张地图，讲清每个命令回答哪一个问题、什么时候会误判。它是「用证据说话」的工具箱，也是后面每篇的实验前提。
>
> **必须先读什么**：[[Linux/07_权限与安全加固/01_前置_安全坐标系与四层防线|01 前置：安全坐标系与四层防线]]、[[Linux/07_权限与安全加固/02_前置_身份与账号文件|02 前置：身份与账号文件]]。
>
> **读完能回答**：① 想判断「这个用户有什么权限」，先跑哪几条命令？② `ls -l` 为什么不能替代 `getfacl`？③ 提权面核查为什么必须 `find -perm -4000` 而不是 `-perm 4000`？
>
> 所属：[[Linux/07_权限与安全加固/00_导读与知识地图|07 权限、账号与安全加固]] 的 1.3 前置地基 · 主要练 **S1 身份与账号台账、S2 权限判定**

## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **一个工具回答一个问题**：`id` 看主体，`stat`/`ls -l` 看客体基本属性，`namei` 看路径逐级，`getfacl` 看精细授权，`getfattr`/`lsattr` 看扩展属性，`getcap` 看能力，`ls -Z`（SELinux）或 `aa-status`（AppArmor）看 MAC。
> - **`ls -l` 的 `+` 是提示，不是答案**：带 `+` 只说明有 ACL；想知道到底给了谁、mask 多少，必须 `getfacl`。反过来，没有 `+` **不代表**没有扩展属性。
> - **`stat` 比 `ls -l` 更接近内核事实**：`stat -c "%a %A %u %g %n"` 直接打印 mode、UID、GID，便于脚本和台账留档。
> - **`namei -l` 一次看全路径**：从 `/` 到目标文件逐级显示属主、mode，是定位「路径缺 `x`」的最快命令。
> - **核查要能留档、能比对**：输出固定字段、写进基线文件，下次用同一命令重跑，差异就是异常。

## 1. 工具地图

| 命令 | 回答的问题 | 看的是哪一层 | 典型用法 |
| --- | --- | --- | --- |
| `id` | 这个进程/会话是谁、有哪些组 | 主体身份 | `id`、`id <user>` |
| `getent` | 按 NSS 查账号/组/服务 | 身份来源 | `getent passwd <user>` |
| `stat` | 文件的 mode、UID、GID、时间、inode | DAC 客体 | `stat -c "%a %A %u %g %n" <file>` |
| `ls -l` | 人和机器都能读的权限视图 | DAC 客体 | `ls -ld <dir>` |
| `namei -l` | 路径上每一级的权限与属主 | DAC 路径 | `namei -l /srv/app/secret` |
| `getfacl` | 完整 ACL、mask、effective | 精细授权 | `getfacl -cp <path>` |
| `lsattr` | `chattr` 的不可变/追加等属性 | 扩展属性 | `lsattr <file>` |
| `getfattr` | 任意扩展属性（含 `user.*`、`security.capability`） | 扩展属性 | `getfattr -d <file>` |
| `getcap` | 文件是否带 capabilities | capabilities | `getcap -r /usr 2>/dev/null` |
| `capsh --print` | 当前进程的能力集合 | capabilities | `capsh --print` |
| `ls -Z` / `stat -c %C` | SELinux 上下文 | MAC（仅 SELinux 系统） | `ls -Z /var/www/html` |
| `aa-status` | AppArmor profile 计数与模式 | MAC（AppArmor 系统） | `aa-status` |
| `ausearch -m AVC` | 内核 MAC 拒绝记录 | MAC 留痕 | `ausearch -m AVC -ts recent </dev/null` |
| `findmnt` | 挂载点与 `nosuid`/`noexec`/`nodev` 选项 | 挂载边界 | `findmnt -o TARGET,SOURCE,FSTYPE,OPTIONS` |
| `sysctl` | 内核安全参数当前值 | 内核边界 | `sysctl fs.protected_regular` |
| `ss -lntup` | 谁在监听哪个端口 | 入口边界 | `ss -lntup` |
| `systemctl list-unit-files --state=enabled` | 哪些服务开机会自启 | 持久化点 | `systemctl list-unit-files --state=enabled` |

## 2. 主体身份：`id` 与 `/proc/<pid>/status`

```bash
id                                   # 验证：当前用户的 uid/gid/附加组/上下文（上下文在支持 SELinux 的系统显示）
id someuser                          # 验证：按名字/UID 查另一个账号的身份
cat /proc/self/status | grep -E '^(Uid|Gid|Groups|Cap)' 
                                      # 验证：当前进程内核视角的 UID/GID/Groups/Cap 集合
```

排障时先固定「**是谁在访问**」。不要只看登录名，要看进程的 `euid` 和组。`sudo` 前是普通用户，`sudo` 后是 root；两者的身份不同，权限结果自然不同。

## 3. 客体与路径：`stat`、`ls -ld`、`namei`

```bash
stat -c "%a %A %u %g %n" /srv/app/config
                                      # 验证：mode 数值/符号、UID、GID、文件名
ls -ld /srv/app /srv/app/config       # 验证：目录与文件的常规权限，注意目录的 r/w/x
namei -l /srv/app/config              # 验证：从根目录到目标逐级权限，缺 x 一目了然
```

> [!important] 目录权限看路径，文件权限看最后一级
> `namei -l` 的价值是同时显示**路径上的每一级目录**。服务报 `EACCES` 时，最后一级文件 mode 可能完全正常，真正缺的是中间某级目录的 `x`。

## 4. 精细授权：`getfacl` 与 `lsattr`

```bash
getfacl -cp /srv/app/config           # 验证：完整 ACL，含 named user/group、mask、effective
lsattr /etc/passwd /var/log           # 验证：chattr 属性；e 是 ext4 正常 extent 标志，i/a 才需要关注
getfattr -d /path/to/file             # 验证：文件上的全部扩展属性（不含 ACL）
getfattr -n security.capability /usr/bin/ping
                                       # 验证：file capability 在 xattr 层的原文
```

`ls -l` 结尾的 `+` 只说明 inode 带了 ACL。要判断「某个 named 条目到底还有没有效」，必须看 `getfacl` 里的 `mask` 和 `#effective`。

> [!important] `+` 只代表 ACL，不代表扩展属性
> 本机实测：一个只设了 `user.note=lab07` 扩展属性、没有 ACL 的文件，`ls -l` **不会**出现 `+`；而只设了 ACL 的文件一定出现 `+`。所以「看不到 `+`」不能推出「没有扩展属性」——`chattr` 属性、file capabilities、SELinux 需要的 `security.*` 都是 xattr，`ls -l` 一个都不显示。要看全，用 `getfattr -d` 与 `lsattr`。

## 5. capabilities：`getcap` 与 `capsh`

```bash
getcap -r /usr 2>/dev/null | sort    # 验证：哪些文件带 capabilities
capsh --print                         # 验证：当前进程的五个能力集合与 cap_last_cap
```

本机实测 `getcap -r /usr` 共 **4** 条，全部属于发行版包：

```text
/usr/bin/mtr-packet cap_net_raw=ep
/usr/bin/ping cap_net_raw=ep
/usr/lib/snapd/snap-confine cap_chown,cap_dac_override,cap_dac_read_search,cap_fowner,cap_setgid,cap_setuid,cap_sys_chroot,cap_sys_ptrace,cap_sys_admin,cap_sys_resource=p
/usr/lib/x86_64-linux-gnu/gstreamer1.0/gstreamer-1.0/gst-ptp-helper cap_net_bind_service,cap_net_admin,cap_sys_nice=ep
```

`capsh --print` 的 Bounding set 在 root 下有 **41** 项（`cap_chown` 到 `cap_checkpoint_restore`），对应 `kernel.cap_last_cap=40`（2026-09-19 08:36 UTC 实测 `sysctl kernel.cap_last_cap` 与 `cat /proc/sys/kernel/cap_last_cap` 都是 `40`，`capsh --decode` 展开 `CapBnd=000001ffffffffff` 得 41 项；原始输出见 `.labvm/evidence/07_caplastcap_real.out.txt`）。注意 `ls -l /usr/bin/ping` 是 `-rwxr-xr-x`，**没有 `s` 位**——这就是「只查 SUID 会漏掉 file capabilities」的直接原因。

提权面核查里，**只查 SUID 会漏掉 file capabilities**。两者要一起查，一起进基线。

## 6. MAC 与挂载/内核边界

```bash
ls -Z /var/www/html 2>/dev/null       # 验证：SELinux 上下文；本机未装 SELinux，无上下文可看
ls /sys/kernel/security/lsm           # 验证：本机 MAC 栈是 AppArmor（lockdown,capability,landlock,yama,apparmor）
aa-status                             # 验证：AppArmor 是否启用与 profile 计数，本机 23 enforce / 4 complain
mountpoint -q /tmp || echo "/tmp 不是独立挂载点"
                                       # 验证：先判断临时目录有没有自己的挂载选项
findmnt -T /dev/shm -o TARGET,SOURCE,FSTYPE,OPTIONS
                                       # 验证：/dev/shm 带 nosuid,nodev，但不带 noexec
sysctl fs.protected_regular fs.protected_fifos kernel.unprivileged_bpf_disabled
                                       # 验证：内核给普通用户关掉的危险入口
```

这些命令是只读的，生产机可以做。把它们加入基线采集脚本，定期与留档值比对。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 只用 `ls -l` 判断「有没有 ACL」 | `+` 只表示有 ACL，不显示给了谁、mask 多少 |
| 看到没有 `+` 就认为「没有扩展属性」 | `+` 只反映 ACL；`user.*`、`chattr` 属性、file capabilities 都不显示（实测只有纯 xattr 的文件没有 `+`） |
| 只查 SELinux 的 `ls -Z` | Ubuntu 上没有 SELinux，本机要看 AppArmor：`ls /sys/kernel/security/lsm` + `aa-status` |
| 用 `find -perm 4000` 核查 SUID | 这是精确匹配，会漏掉 4755 的 `su`/`sudo`；要用 `-perm -4000` |
| 只看最后一级文件 mode | 漏掉路径上缺 `x` 的目录 |
| 只查 SUID 不查 capabilities | 漏掉 `/usr/bin/ping cap_net_raw=ep` 这类提权点；本机这类文件有 4 个 |
| 手动敲命令不留档 | 下次没有基线可比，异常出现时无法判断「什么时候多出来的」 |

## 决策练习

> [!question]- 场景：服务日志显示 `EACCES`，你只有 3 分钟先取一组证据。同事让你先 `chmod -R 777 /srv/app`。你会先跑哪几条只读命令？
> A. 只跑 `ls -l /srv/app`，然后按同事说的改
> B. 跑 `namei -l <path>`、`stat -c "%a %u %g %n" <path>`、`getfacl -cp <path>`、`id`，把四份证据贴出来再决定
> C. 先重启服务，看报错是不是偶发
>
> **答案：B。**
> A 证据不足，`chmod -R 777` 会开放写和执行。
> C 重启可能清掉现场，而且没有解决权限问题。
> B 是正解：**四份证据分别对应路径、客体、ACL、主体，能把拒绝发生的原因缩小到一层。**

## 要点自测

> [!question]- 想判断「这个用户能不能访问这个文件」，最少要哪几类信息？
> - 主体：`id`/`/proc/<pid>/status` 看 uid/gid/groups/capabilities。
> - 路径：`namei -l <path>` 看逐级目录 `x`。
> - 客体：`stat -c "%a %u %g"` + `getfacl` 看 mode 与 ACL。
> - 边界：必要时 `getcap`、`ls -Z`、`findmnt`。
> - **第一反应不要是什么**：不要只看文件本身。

> [!question]- `ls -l` 输出里的 `+` 代表什么？为什么不能只看它？
> - `+` 表示 inode 带 ACL；但它不显示 named 条目、mask 和 `#effective`。
> - 想知道有效权限，必须 `getfacl`。而且 `+` **只**反映 ACL：本机实测只带 `user.note` 扩展属性的文件没有 `+`，`chattr` 属性、file capabilities 也都不显示。
> - **第一反应不要是什么**：不要看到 `+` 就以为「权限很复杂」，也不要看不到 `+` 就以为没有 ACL 或没有扩展属性。

> [!question]- 为什么安全基线命令要写成脚本并留档？
> - 因为异常通常是「与上次不一样」：多一个 SUID 文件、多一个账号、多一个监听端口。
> - 留档后才能做 diff；否则只能凭印象判断，容易漏。
> - **第一反应不要是什么**：不要每次手工敲命令、看完就丢。
