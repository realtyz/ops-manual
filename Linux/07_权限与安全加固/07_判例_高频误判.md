# 高频误判

十六条按值班与复盘里的真实处境写成：**场景**（谁、什么机器、看到什么、别人怎么说）→ **常见误判及它为什么看起来成立** → **判据**（读哪个字段、什么数值或趋势、什么条件下结论会变）→ **一句话结论** → **出处**。字段的读法在实操篇第 2 节。

## 1. 「文件权限都对了，那就 `chmod -R 777` 吧」

**场景**：Web 服务以 `www-data` 运行，读 `/srv/app/config` 报 `Permission denied`。文件是 `644 root:root`，看着毫无问题；值班同事说「先放开，等业务恢复再说」，准备执行 `chmod -R 777 /srv/app`。

**常见误判**：把「最后一级文件权限」当成判定的全部。它看起来成立，是因为 `ls -l` 的输出确实是一个完整的权限视图——只不过只覆盖判定链的一环。

**判据**：`namei -l /srv/app/config`，看从 `/` 到目标每一级的 mode 与属主。**路径上任何一级目录缺 `www-data` 的 `x`，结果就是 `EACCES`，与最后那个文件无关。** 路径层没问题再依次看 `getfacl -cp`（`mask` 与 `#effective`）、`findmnt -T <path> -o OPTIONS`（挂载选项）、审计日志里的 `apparmor="DENIED"`/`avc: denied`（MAC）。**条件会变**：如果路径、ACL、挂载、MAC 全部排除，才轮到改文件属主或属组；此时最小改动通常是把服务账号加入属组，而不是放宽 other。

**一句话结论**：拒绝发生在哪一层，决定改哪里；`chmod -R 777` 同时开放写与执行，是把权限问题升级成提权问题。

**出处**：`man 7 path_resolution`、`man 2 open`、`man 5 acl`。

## 2. 「`Operation not permitted` 也是权限不够，加权限就行」

**场景**：一个自研程序以普通用户运行，申请原始套接字失败，报 `Operation not permitted`；有人提出「给它 root 跑就行了」。

**常见误判**：把 `EPERM` 与 `EACCES` 当成同一个错误。它看起来成立，因为两者都像是「系统不让我做这件事」。

**判据**：先记下 `errno`。`EACCES`（13）来自路径、mode、ACL 的判定不通过；`EPERM`（1）来自「即使有常规文件权限也不允许」——缺少 capability、文件只读、`chattr +i`、被 MAC 拒绝。对应地看 `getcap <bin>`/`getpcaps <pid>`（能力）、`lsattr <path>`（不可变属性）、`aa-status`/`getenforce` 与审计日志（MAC）、`findmnt -T <path>`（`nosuid` 会让 file capabilities 失效）。**条件会变**：如果程序确实需要一项能力，正确修法是只授那一项（文件能力或 systemd 的 `AmbientCapabilities=` + `CapabilityBoundingSet=`），而不是把整个进程提到 root。

**一句话结论**：`EACCES` 查 DAC 与路径，`EPERM` 查能力、属性与 MAC；两者不是同义词。

**出处**：`man 7 capabilities`、`man 2 execve`、`man 7 credentials`。

## 3. 「`chmod 4755` 之后 SUID 一定生效」

**场景**：给一个内部工具设 SUID：先 `chmod 4755`，又觉得属主应该是 root，于是 `chown root:root`。之后普通用户执行它，身份没有任何变化。同事说「位设了就行，可能是内核的问题」。

**常见误判**：把 `chmod` 与 `chown` 当成互不影响的动作。它看起来成立，因为两条命令改的是同一个文件的属性。

**判据**：`stat -c "%a %A %n" <file>`。**`chown` 会清掉 SUID/SGID 位**，所以「先 `chmod` 再 `chown`」得到的最终 mode 是 `755` 而不是 `4755`；正确顺序是**先 `chown`，再 `chmod`**。位还在却仍不见效时，继续查：目标是不是 ELF（脚本上的特权位被内核忽略）、`findmnt -T <file> -o OPTIONS` 有没有 `nosuid`、执行环境有没有 `no_new_privs` 或被 `ptrace`。**条件会变**：如果这个需求是「长期以最小特权运行」，改 SUID 本身就不是对的方向，应改用 systemd 的能力属性。

**一句话结论**：`chown` 会清掉 SUID/SGID 位，顺序反了就等于没设；位还在就继续查挂载与执行环境。

**出处**：`man 1 chown`、`man 1 chmod`、`man 2 execve`。

## 4. 「脚本也能设 SUID，设了就生效」

**场景**：一段 shell 脚本需要读某个 root 才能读的目录，于是给它设 `chmod 4755`。`ls -l` 显示 `-rwsr-xr-x`，看起来成功了，但执行时仍然读不到。

**常见误判**：把「位设上了」等同于「特权生效了」。它看起来成立，因为 `ls -l` 上那个醒目的 `s` 就在那里。

**判据**：Linux 明确忽略 `#!` 脚本上的 set-user-ID/set-group-ID 位——带 `#!` 的文件实际执行的是解释器。**判据是问「真正被 `execve` 的是谁」**：脚本不是，解释器才是。同样的性质也适用于 file capabilities：`setcap` 对脚本会返回成功、`getcap` 也会显示有值（xattr 确实写进去了），但执行时不生效（报 `EPERM`）。**条件会变**：如果确实需要为一段逻辑授特权，做法是编译成二进制，或让 systemd 单元以指定用户和指定能力启动它。

**一句话结论**：脚本上的特权位是「设得上、不生效」；要让脚本获得特权，改结构而不是改权限位。

**出处**：`man 2 execve`（对 `#!` 脚本的处理）、`man 8 setcap`、`man 7 capabilities`。

## 5. 「`getcap` 显示有这个能力，就一定生效」

**场景**：给一个二进制 `setcap cap_net_raw+ep`，`getcap` 显示 `cap_net_raw=ep`，但普通用户执行仍然 `EPERM`；同事认为「工具读错了」。

**常见误判**：把 xattr 的写入成功当成运行时生效。它看起来成立，因为 `getcap` 读的就是内核存的那份数据，它没读错。

**判据**：file capabilities 与 SUID 受同一类拦截——`no_new_privs`、`nosuid` 挂载、被 `ptrace` 时都被忽略；此外**内核只对 ELF 应用 file capabilities**，脚本无论如何都不生效。用 `findmnt -T <file> -o OPTIONS` 确认挂载选项、`getfattr -n security.capability <file>` 确认 xattr 真的存在、并确认目标是 ELF 而不是脚本。**条件会变**：容器里还要确认 `NoNewPrivileges` 与能力相关的运行时限制。

**一句话结论**：`getcap` 只回答「xattr 写了什么」，不回答「执行时生不生效」。

**出处**：`man 8 getcap`、`man 7 capabilities`、`man 2 execve`。

## 6. 「挂了 `noexec`，上传目录就安全了」

**场景**：安全扫描要求上传目录挂 `noexec`。运维挂上之后，攻击者仍然把一个 Python 载荷放进该目录并成功执行，随后横向移动。

**常见误判**：把 `noexec` 当成「禁止执行该目录中的一切」。它看起来成立，因为名字里就写着 exec。

**判据**：`noexec` 阻止的是**直接执行这个文件**；`bash script.sh`、`python3 a.py` 是直接执行 `bash`/`python3`（它们不在该挂载点上），脚本只是被当作数据读入。**判据要落到「解释器在不在这个挂载点上」**。真正要一起做的：把目录属主收紧为不可被业务写、必要时用 `nosuid`/`nodev`、配合 MAC 或单元沙箱限制解释器的使用。**条件会变**：如果该目录确实需要执行编译产物，`noexec` 与业务会直接冲突，此时要按「可写」与「需要执行」把路径分层，而不是一刀切。

**一句话结论**：`noexec` 只拦直接执行；拦不住解释器，所以要同时收紧属主与写权限。

**出处**：`man 8 mount`（`noexec` 的语义）、`man 8 findmnt`。

## 7. 「`/tmp` 有 sticky 位，等于被保护了」

**场景**：加固检查中，同事看到 `ls -ld /tmp` 是 `drwxrwxrwt`，认为 `/tmp` 已经有 `nosuid`/`noexec` 保护，无需再处理。

**常见误判**：把权限位与挂载选项混为一件事。它看起来成立，因为 sticky 位确实在限制别人删你的文件。

**判据**：`mountpoint -q /tmp` 与 `findmnt -T /tmp -o TARGET,SOURCE,FSTYPE,OPTIONS`。**`/tmp` 完全可能只是根文件系统上的一个 `1777` 普通目录**，跟着 `/` 的挂载选项，`nosuid`/`nodev`/`noexec` 一个都没有——这时它是一个任何人都能放可执行文件并可执行的地方。**条件会变**：如果确定 `tmp.mount` 或其他机制把 `/tmp` 做成了独立 tmpfs，再去看它实际带了哪些选项，而不是假设发行版一定这么做了。

**一句话结论**：sticky 位管删除，挂载选项管特权与执行；`/tmp` 是不是挂载点要先确认。

**出处**：`man 8 mount`、`man 5 tmpfs`、`man 8 findmnt`、`man 1 mountpoint`。

## 8. 「给 `vim`/`docker` 免密没什么，反正只是一条命令」

**场景**：开发同学申请 `NOPASSWD` 执行 `vim` 与 `docker`，理由是「只用来改配置和看容器」。运维认为这两条命令看起来无害，准备批准。

**常见误判**：按「看起来是一条命令」评估风险。它看起来成立，因为 sudoers 里确实只写了一行。

**判据**：问「这条命令能不能逃出它自己」——`vim` 有 `:shell`，`docker run --privileged -v /:/host` 能挂载宿主根目录，编辑器、解释器、打包工具、`systemctl` 都属同一类。**判据不是命令数量，而是该命令能否启动任意代码或改变系统状态。** 需要时应当用 `Cmnd_Alias` 只授具体参数（如 `systemctl restart <指定服务>`、`journalctl -u <指定单元>`），配合日志与时间窗口。**条件会变**：临时排障可以给短时限的授权，但要有回收动作与记录。

**一句话结论**：`NOPASSWD` 交出的不是「一条命令」，是这条命令能触达的全部能力。

**出处**：`man 5 sudoers`、`man 1 sudo`。

## 9. 「`passwd -l` 之后这个账号就停用了」

**场景**：一名员工离职，运维执行 `passwd -l <user>` 并在工单上写「账号已停用」。两周后审计发现该账号仍能通过 SSH 公钥登录。

**常见误判**：把「锁密码」当成「停用账号」。它看起来成立，因为 `passwd -S` 确实显示 `L`（locked）。

**判据**：密码只是认证入口之一。要逐条通道确认：`getent shadow <user>`（密码是否被锁、账号过期日期第 8 字段是否已设）、`find /home/<user> -name authorized_keys`（公钥是否还在）、`sudo -l -U <user>`（是否存在 `NOPASSWD` 授权）、`who`/`loginctl list-sessions`（是否还有活跃会话）。**标准处置是一组动作**：`usermod -e 1`（或 `chage -E 0`）让账号过期、清理公钥与 `sudoers`、终止会话、记录进台账。**条件会变**：如果该账号是服务账号，停用前要确认它没有被业务用来做认证。

**一句话结论**：`passwd -l` 只关掉密码这一条路；停用是账号过期加上清理全部授权通道。

**出处**：`man 1 passwd`、`man 5 shadow`、`man 8 usermod`、`man 5 authorized_keys`。

## 10. 「多了一个 UID 0 的账号，名字不叫 root，问题不大」

**场景**：巡检脚本发现一台机器上有两个 UID 0 账号：`root` 与 `ops`。有人说 `ops` 是以前留下的运维账号，不用管。

**常见误判**：按名字判断权限级别。它看起来成立，因为「root」这个名字带着全部含义。

**判据**：内核只看 UID 数值。`awk -F: '$3==0 {print}' /etc/passwd` 列出全部 UID 0 账号；**任何非预期的 UID 0 账号都是完整超级用户**，要按最高优先级事件处理：查来源（`getent passwd ops`、`lastlog -u ops`、`/home/ops` 与 `authorized_keys`）、查授权（`sudo -l -U ops`）、查它的文件归属、与其他同角色机器的基线对比。**条件会变**：如果它确实是某个软件的安装产物，也必须留下「哪个软件、哪次变更、谁批准」的记录，而不是口头解释。

**一句话结论**：判权限看 UID 数值，不看名字；多一个 UID 0 账号就是多一个完整 root。

**出处**：`man 5 passwd`、`man 7 credentials`。

## 11. 「配置写在 `sshd_config` 里了，reload 一下就生效」

**场景**：把 `PermitRootLogin no` 追加到 `/etc/ssh/sshd_config` 末尾并 `systemctl reload ssh`。用 `sshd -T` 一看，`permitrootlogin` 仍然是 `yes`。

**常见误判**：把「配置文件里的内容」当成「最终生效值」。它看起来成立，因为那一行确实写进文件了。

**判据**：`sshd -T | grep -E '^(permitrootlogin|passwordauthentication|maxauthtries)'` 才是生效值。两个覆盖来源：**`Include` 的位置**——同名关键字**先读到者生效**，所以 `Include /etc/ssh/sshd_config.d/*.conf` 写在文件顶部时，drop-in 里的值会压过主文件后面的同项；**`Match` 块**——满足条件的第一个匹配块生效，不叠加，用 `sshd -T -C user=<u>,addr=<ip>,host=<h>` 看具体连接的最终值。**条件会变**：如果 `-C` 的结果与全局值完全一致，说明没有 `Match` 在起作用——这本身是一条有用的判据。

**一句话结论**：`sshd -T` 才是生效配置；改完必须用它验收，而不是看文件写了什么。

**出处**：`man 5 sshd_config`（`Include` 与 `Match` 的语义）、`man 8 sshd`。

## 12. 「在 `complain` 模式下跑了一周没报错，说明 profile 是对的」

**场景**：给一个自研程序写了 AppArmor profile，为避免影响业务先切到 `complain` 模式跑了七天，日志里没有阻断，于是宣布策略已验证并保持 `complain`。

**常见误判**：把「不阻断」当成「策略正确」。它看起来成立，因为业务确实没出问题。

**判据**：`complain` 放行的只是**隐式拒绝**（允许列表里没写的权限），它仍然记录；而 profile 里**显式写的 `deny` 规则在两种模式下都拒绝**，所以「没报错」只能说明没有显式 `deny` 被触发，不能证明允许列表足够完整。正确流程是：在 `complain` 下收集「原本会被拒」的记录、补齐允许列表，**再切回 `enforce` 复跑一轮**。**条件会变**：如果业务有低频路径（月度任务、故障切换分支），七天的观察窗口可能根本没覆盖到，验收要按路径覆盖而不是按时长。

**一句话结论**：`complain` 是定位工具，验收必须在 `enforce` 下完成。

**出处**：`man 7 apparmor`、`man 5 apparmor.d`、`man 8 aa-status`。

## 13. 「`setenforce 0` 之后业务就恢复了，问题解决」

**场景**：RHEL 上服务在 `enforcing` 下起不来，日志里有 `avc: denied`。值班执行 `setenforce 0`，服务起来了，工单关闭。

**常见误判**：把「业务恢复」当成「问题解决」。它看起来成立，因为服务确实在跑。

**判据**：`permissive` 只是把阻断关成只审计——**拒绝记录仍然产生**，攻击面回到 DAC；真正的修法是按拒绝的 `class` 与权限选择最小动作：`restorecon` 修标签、`semanage port` 修端口类型、`setsebool -P` 修布尔值，确需自定义策略时用 `audit2allow` 生成并**人工复核范围**，最后切回 `enforcing` 复验。**条件会变**：如果确实需要临时放宽以保住业务，也必须记录「谁批准的、观察窗口多长、什么时候切回」，否则它会变成长期状态。

**一句话结论**：`setenforce 0` 把边界关掉而不修复它；permissive 只能用于定位。

**出处**：`man 8 setenforce`、`man 8 semanage`、`man 8 restorecon`、`man 8 setsebool`、`man 8 audit2allow`。

## 14. 「`ausearch -m AVC` 没有输出，说明没有被 MAC 拒绝过」

**场景**：排查一个服务起不来的问题，执行 `ausearch -m AVC -ts recent` 返回 `<no matches>`，于是判定与 MAC 无关，转到别的方向。

**常见误判**：把工具的空结果当作「事件不存在」。它看起来成立，因为工具是权威入口。

**判据**：`ausearch` 的可查性依赖审计配置（例如 `auditd.conf` 的 `log_format`）；审计原始文件里可能存在大量 `type=AVC` 记录而查询仍返回空。**兜底手段是直接查原始文件**：`grep -E 'apparmor="DENIED"|avc:  denied' /var/log/audit/audit.log | tail`。另外要确认记录的**落点**：auditd 在运行时 LSM 拒绝落审计日志，不在运行时才落 `dmesg`/`journalctl -k`；内核日志里更早的 `type=1400` 常常是引导期策略装载记录。**条件会变**：容器、日志集中化、或把审计写入远端时，本机文件里可能确实没有记录，此时要看集中平台。

**一句话结论**：空结果不等于没发生；查 MAC 拒绝要以审计原始文件为准并交叉验证。

**出处**：`man 8 ausearch`（含「从 stdin 读取原始日志」的说明）、`man 5 auditd.conf`。

## 15. 「`journalctl -u sudo` 里没有记录，说明没人用过 sudo」

**场景**：审计时执行 `journalctl -u sudo` 与 `journalctl -g sudo`，都返回 `-- No entries --`，据此认为这台机器上没有人用过 `sudo`。

**常见误判**：假设所有日志都在 journald 里、且以服务为单位。它看起来成立，因为 systemd 机器上大多数日志确实在 journald。

**判据**：`sudo` **不是 systemd 服务**，所以按服务查不到是正常的；它的日志落点由编译选项（是否 `--with-logging=syslog`、`logfac` 是什么）与 `sudoers` 里有没有配置独立 `logfile=` 决定。Debian/Ubuntu 上常见落点是 `/var/log/auth.log`（经 syslog 的 `authpriv` 设施），但也可能被配成独立文件或送进 journald。**判据顺序**：先 `grep -rn 'logfile\|log_input\|log_output' /etc/sudoers /etc/sudoers.d/`，再按结果决定查哪个文件；用 `sudo -V` 看编译选项。**条件会变**：集中日志或堡垒机场景下，记录可能在远端。

**一句话结论**：`sudo` 不是 systemd 服务；先确认日志设施，再下「没人用过」的结论。

**出处**：`man 1 sudo`、`man 5 sudoers`（`logfile`、`log_input`、`log_output`）、`man 5 sudo_logsrvd`。

## 16. 「上次盘点的提权面清单和这次一样，说明没变化」

**场景**：半年一次的安全巡检，两次都跑 `find / -xdev -type f -perm -4000 | wc -l`，得到的数量都是 13，于是写「提权面无变化」。

**常见误判**：把「数量相同」当成「内容相同」。它看起来成立，因为数量确实是一个可比的量。

**判据**：数量相同完全可能对应「少了一个、多了一个」。基线要比对**清单**而不是计数，并且覆盖每一类提权面：`find -perm -4000`/`-2000`（含与任一两种写法）、`getcap -r /`、`sudo -l -U`、root 执行的可写脚本与配置、`authorized_keys`、`/etc/ld.so.preload`、内核与设备入口、容器特权、挂载选项。新增项要能反查到包归属（`dpkg -S <basename>` / `rpm -qf <path>`）。**判据的可迁移形式**：任何「与上次比」的结论都必须基于同口径的完整输出 diff，而不是摘要数字。**条件会变**：升级与镜像重建会成批改变清单，这时要按变更窗口解释差异，而不是逐条追查。

**一句话结论**：基线要比清单、比每一类，不比计数；数量不变掩盖不了内容变化。

**出处**：`man 1 find`（`-perm` 的三种写法）、`man 8 getcap`、`man 1 dpkg`、`man 8 rpm`。

## 第一反应不要做什么

- 不要在没看路径的情况下改最后一级文件权限，更不要 `chmod -R 777`；
- 不要把 `EACCES` 与 `EPERM` 当同一件事，也不要为了消除报错把进程提到 root；
- 不要在脚本上加 SUID 或 file capabilities，也不要因为 `getcap` 显示有值就认为已生效；
- 不要把 `noexec`、`/tmp` 的 sticky 位、`passwd -l` 当成完整的保护或停用；
- 不要用账号名判断权限级别；
- 不要在 `complain`/`permissive` 下宣布策略正确，更不要把 `setenforce 0` 当修复；
- 不要把查询工具的空结果当成「没发生」，也不要在没确认日志设施前宣布「没人用过」；
- 不要用数量代替清单来比较基线。

## 要点自测

**问：一个服务报 `EACCES`，你会按什么顺序排除？每一层用什么命令？**
答：路径逐级 `x`（`namei -l`）→ DAC 位与属主属组（`stat -c "%a %u %g %n"`）→ ACL `mask`/`#effective`（`getfacl -cp`）→ 需要的 capability（`getcap`/`getpcaps`）→ 挂载选项（`findmnt -T`）→ MAC（审计原始日志里的 `apparmor="DENIED"` / `avc: denied`）→ 内核参数与保护。每一层都要用证据决定是否继续。

**问：`getcap` 显示文件带 `cap_net_raw=ep`，但执行仍然 `EPERM`，可能的原因有哪些？**
答：目标是脚本（内核只对 ELF 应用）、所在挂载点带 `nosuid`、进程设置了 `no_new_privs`、被 `ptrace`、或容器/运行时限制了能力。逐条用 `file`、`findmnt -T`、执行环境与 `getpcaps` 排除。

**问：`sshd_config` 改了没生效，先查哪两件事？**
答：`sshd -T` 看生效值（不是看文件），以及 `grep -n Include /etc/ssh/sshd_config` 与 `/etc/ssh/sshd_config.d/` 里的同名项——同名关键字先读到者生效，`Include` 在文件顶部时 drop-in 会压过主文件后面的同项。涉及具体用户/地址时再用 `sshd -T -C user=...,addr=...` 看 `Match` 的最终值。

**问：为什么「`complain` 下跑一周没报错」不能作为 AppArmor 策略已验证的证据？**
答：`complain` 只放行隐式拒绝并记录，显式 `deny` 规则在两种模式下都拒绝，所以「没报错」只说明没有显式 `deny` 被触发；而低频路径可能根本没被观察到。验收必须在 `enforce` 下按路径覆盖复跑。

**问：判断「账号已停用」，要确认哪几条通道？**
答：密码是否被锁与账号是否过期（`getent shadow` 的第 2、8 字段）、公钥（`authorized_keys`）、`sudoers` 授权、以及是否还有活跃会话（`who`/`loginctl`）。任何一条未清理，账号就仍然能进。

**问：为什么安全基线不能只记录数量？**
答：数量相同可以对应「一增一减」。基线要比对每一类的完整清单并与上次 diff，新增项还要能反查到包归属；数量只适合作为摘要的辅助字段。
