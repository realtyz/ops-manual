# 文件权限为什么不决定一切

## 1. 让「文件上的权限位」单独决定访问，会同时出四件事

`ls -l` 的那九个字符看起来像一个完整的答案。但如果它真的是全部判据，四件事会立刻出问题：

**路径上的目录没法表达自己的门槛。** `/srv/app/config` 是 644，可 `/srv/app` 是 `drwx------` 且属主不是访问者。文件本身没有任何问题，访问者却连名字都解析不到。要拦住这种访问，权限不能只挂在最后一级。

**「只给某一个人」表达不了。** 属主/属组/other 只有三格，而真实需求常是「这个文件 owner 和 group 都不该动，但审计账号要能读」。

**同一组权限位要在两种对象上说两件事。** 目录的 `r` 是「列出名字」，文件的 `r` 是「读内容」；目录的 `x` 是「穿过去」，文件的 `x` 是「执行它」。九个字符长得一样，语义是两套。

**保护不能只靠「谁能写」。** 有些文件希望「连属主都不能改」，或者「只能追加不能覆盖」。这个需求在权限位里无处安放。

四条合起来说明：文件权限位只是**判定链里的一层**，而且不是第一层。**排障时先问「卡在哪一层」，比先问「权限位对不对」有用得多。**

## 2. 路径解析是两段：先穿过去，再看文件

内核对 `/srv/app/config` 的解析分成两步：

1. **对路径上的每一级目录，检查访问者有没有 `x`**。目录的 `x` 是「允许把这一级当作路径的一部分」。任何一级缺 `x`，最终结果是 `EACCES`（`Permission denied`），**与最后那个文件的权限完全无关**。
2. **到达文件后，再按三类身份挑一条规则**：如果访问者的 `euid` 等于文件属主，只用属主那三位；否则如果在文件属组或访问者的任一附加组里，只用属组那三位；否则用 other 那三位。

第 2 步有两个容易被忽略的性质：

- **三类身份是「先命中先停」，不是叠加。** 一个进程既是文件属主又在文件的属组里时，只按属主判定。属主位是 `---` 而属组位是 `rw-` 时，属主同样读写不了自己的文件。
- **判定看的是 `euid` 与组列表，不是「登录名」。** `sudo` 前后的两个进程身份不同，结果自然不同。

`namei -l <path>` 的价值就在这里：它把从 `/` 到目标的每一级属主与 mode 一次列出来，让「哪一级缺 `x`」变成肉眼可见的事实。只 `ls -l` 最后一级，必然漏掉路径层。

## 3. 九个字符在两套对象上的确切含义

| 位 | 对文件 | 对目录 | 判定发生在 |
| --- | --- | --- | --- |
| `r` | 读文件内容 | 列出目录项的名字（`ls` 需要它） | 打开/读取时 |
| `w` | 修改或截断内容 | 新建、删除、改名目录内的条目 | 写入时 |
| `x` | 把它当作程序交给内核执行 | 穿过目录、把这一级纳入路径解析 | 解析路径与 `execve` 时 |

由此得到四条实务结论，它们比记忆这九个字符重要得多：

**删除文件看的是目录的 `w` + `x`，不是文件自己的 `w`。** `rm` 做的是「从目录里摘掉一个名字」，改的是目录的元数据。所以只读文件照样能被删掉，只要它所在目录可写；反过来说，一个对文件有写权限的人，在不可写的目录里也删不掉它。

**列不出名字不代表不能访问。** 目录有 `x` 没有 `r` 时，`ls` 失败，但「已知文件名」的读写仍可能成功。这类目录常见于「投递箱」：允许往里放已知路径的文件，不允许围观别人的文件名。

**sticky 位只影响删除。** 目录设了 sticky（`1777`）之后，只有文件属主、目录属主或 root 能删目录内的条目。共享的 `/tmp` 用 `1777` 正是这个原因：谁都能放东西，但不能删别人的。

**目录的 `x` 与文件的 `x` 是两回事，`umask` 对二者的作用也不同。** 新建文件的基准权限是 `0666`（本来就没有执行位），新建目录的基准是 `0777`。所以同一个 `umask 022` 给出的是文件 `644`、目录 `755`——**文件少的那一个 `x` 不是因为 `umask` 减掉的，而是因为基准里就没有。**

## 4. `umask` 有三个落点，改错地方就不生效

`umask` 是「按位减掉」的掩码，它作用在进程创建对象的时刻。关键是**哪个进程**：

| 落点 | 由谁设置 | 影响谁 | 常见误区 |
| --- | --- | --- | --- |
| 登录会话 | PAM 的 `session` 栈读 `/etc/login.defs` 的 `UMASK`；登录 shell 的启动脚本可以再覆盖 | 交互式登录后启动的进程 | 以为改了 `login.defs` 服务也会变 |
| systemd 服务 | unit 的 `UMask=`，以及 PID 1 的 `DefaultUMask` | 由 systemd 拉起的服务 | 在 `login.defs` 里为服务改 `umask` |
| 单个进程 | 进程自己调用 `umask()`，或 `open(..., mode)`、`install -m` 之类的显式指定 | 该进程及其子进程 | 以为继承的一定是「默认值」 |

**服务不经 PAM 登录栈，所以 `login.defs` 管不到它。** 这条推论在后面反复出现：`limits.conf`、`login.defs`、`pam_*` 这一整套都是「登录会话」的设施，systemd 服务走的是 unit 属性。

## 5. ACL：在九个字符之外再开一档

ACL（Access Control List，访问控制列表）存在 inode 的扩展属性 `system.posix_acl_access` 里，操作入口是 `getfacl`/`setfacl`。它加了两类条目：

- **named user / named group**：给指定的某个用户或某个组单独授权；
- **`mask`**：named 条目与 owning group 的**有效权限上限**。

判定顺序是：先看访问者是否命中某条 named 条目（命中就用它），再看属主/属组/other。而**无论走哪一条，named 条目与 owning group 的最终权限都要再与 `mask` 取交集**，`getfacl` 用 `#effective:` 把结果标出来。

三个由此而来的高频现象：

**`ls -l` 的属组三位在有 ACL 时显示的是 `mask`，不是 `group::` 的真实权限。** 这是「明明看着组有写权限却写不进去」的直接原因——属组位那一格被 `mask` 借用去显示了。

**`chmod` 会重算 `mask`。** 改完 ACL 又执行 `chmod`，可能把 named 条目的有效权限一起削掉。**ACL 与 `chmod` 混用时，改完必须重新 `getfacl` 复查。**

**授权加了却不生效时，先看 `mask`，不要重复加授权。** 重复 `setfacl -m u:x:rwx` 不会改变 `mask`，所以错误会原样复现。

目录还可以带 `default:` 条目，它是**模板**：目录内新建的子对象会继承这些条目，再按新建对象自身的权限收口（例如新建的普通文件没有执行位，于是 named 条目的 `rwx` 会被收成 `#effective:rw-`）。

```bash
getfacl -cp <path>              # 验证：named 条目、mask 与 #effective 一次看全
setfacl -m m::rwx <path>        # 验证：把 mask 恢复成完整权限后再复查 #effective
setfacl -m d:u:<user>:rwx <dir> # 验证：给目录设默认 ACL，观察新建对象是否继承
```

## 6. 扩展属性与不可变属性

ACL 并不是独立的数据结构，它是扩展属性（xattr）的一种视图。同一块地方还放着别的东西：

| 名字空间 | 存放什么 | 查看工具 |
| --- | --- | --- |
| `system.posix_acl_access` / `_default` | ACL | `getfacl` |
| `security.capability` | file capabilities | `getcap`、`getfattr -d -m -` |
| `security.selinux` 等 | 安全标签 | `ls -Z`、`getfattr` |
| `user.*` | 应用自定义属性 | `getfattr -d` |
| `chattr` 属性（`i`/`a` 等） | 文件级行为开关 | `lsattr` |

`ls -l` 结尾的 `+` **只表示「这个 inode 带 ACL」**，它不表示有扩展属性，也不显示 ACL 的内容。反过来，只有 `user.*` 这类 xattr 而没有 ACL 的文件，`ls -l` 不会显示 `+`。**「没有 `+`」推不出「没有扩展属性」**，要看全得用 `getfattr -d`（任意 xattr）、`getcap`（能力）、`lsattr`（`chattr` 属性）。

`chattr +i`（immutable，不可变）与 `+a`（append-only，只追加）的作用点是内核的写入路径，它在权限位之外多加一道闸：

- `+i` 生效期间，**连 root 也不能写、删、改名或改权限**，必须先 `chattr -i` 去掉属性；
- `+a` 只允许追加，不允许覆盖与截断，适合日志类文件；
- ext4 上常见的 `e` 是 extent 标志，属正常值，不是异常。

这道闸的代价必须一起记住：**它挡的不只是攻击者，也挡正常流程。** `logrotate` 轮转需要改名或截断，包管理器升级需要替换文件，两者都会失败；而真正的 root 级攻击者同样可以 `chattr -i`。**它的价值是抬高修改门槛并留下操作痕迹，不构成防篡改的终点。**

```bash
lsattr <path>                   # 验证：区分 e（正常 extent 标志）与 i/a（真正的限制）
getfattr -d -m - <path>         # 验证：把全部扩展属性列出来，看 ACL 之外的项
```

## 7. 抽象在哪里漏水

**「权限对了」不等于「访问通过」。** 判定链上还有 capabilities（需要某项特权才能做的操作）、挂载选项（`nosuid`/`noexec`）与 MAC（SELinux/AppArmor）。文件权限全部正确但访问失败的场景是常态，不是异常。

**两类错误码指向不同的层。** `EACCES`（`Permission denied`）常见于路径缺 `x`、DAC 位、ACL `mask` 的判定不通过；`EPERM`（`Operation not permitted`）常见于「即使有常规文件权限也不允许这个操作」——缺少 capability、文件只读、`chattr +i`、被 MAC 拒绝。**先把 `errno` 记下来，再决定查哪一层。**

**继承与复制不是同一件事。** 默认 ACL 只影响**在设了默认 ACL 的目录内新建**的对象；把外部文件 `mv` 进来不会套用模板（`mv` 不改变 inode），复制才会。备份与复制时要显式带上属性：`cp -a`、`tar --acls --xattrs`、`rsync -A -X`。**一份丢掉了 ACL 的备份，恢复后就是一个权限更宽松的系统。**

**内核还有一层与文件权限无关的保护。** `fs.protected_regular`/`protected_fifos`/`protected_hardlinks`/`protected_symlinks` 这组参数，防的是普通用户借全局可写文件、FIFO、链接在共享目录里做手脚。它们不体现在任何 `ls -l` 输出里，只在特定攻击模式下出现。

## 常见误解

| 常见说法 | 事实 |
| --- | --- |
| 「文件 777 就一定访问得了」 | 路径缺 `x`、ACL `mask`、`nosuid`/`noexec`、缺少 capability、MAC 拒绝，每一层都能拦下 |
| 「删除文件需要文件自己的 `w`」 | 删除改的是目录，需要目录的 `w` + `x`；sticky 目录再额外要求属主/目录属主/root |
| 「目录的 `x` 是『可执行』」 | 目录的 `x` 是穿过与路径解析；目录的 `r` 才是列出名字 |
| 「`ls -l` 里有 `+` 说明扩展属性很复杂」 | `+` 只表示有 ACL；`user.*`、`chattr` 属性、file capabilities 都不产生 `+` |
| 「有 ACL 时属组三位就是组的权限」 | 那是 `mask`；组的真实权限在 `getfacl` 的 `group::` 行 |
| 「授权不生效就再加一次 `setfacl`」 | 瓶颈常常是 `mask`，重加授权不改 `mask` |
| 「`chmod` 和 `setfacl` 可以随便交替用」 | `chmod` 会重算 `mask`，可能悄悄削掉 named 条目的有效权限 |
| 「`chattr +i` 是万能防篡改」 | 它同样挡住轮转与升级，root 级攻击者可以再 `chattr -i`；重点是抬高门槛与留痕 |
| 「`cp -r` 备份就够了」 | 不带 `-a`（或 `tar --acls --xattrs`、`rsync -A -X`）会丢 ACL 与 xattr |
| 「`mv` 进目录会继承默认 ACL」 | 默认 ACL 只作用于**新建**对象；`mv` 保留原 inode，不套模板 |

## 要点自测

**问：一个文件是 644，服务仍报 `EACCES`，你会先跑哪一条命令、看什么？**
答：`namei -l <完整路径>`，看从 `/` 到文件的每一级目录的属主与 mode，确认中间有没有哪一级缺访问者身份的 `x`。路径层是判定链的第一环，也是「文件权限看着完全正常」时最常被漏掉的一环。

**问：为什么同一个 `umask 022` 得到文件 644 而目录 755？**
答：因为基准权限不同：新建文件按 `0666`、新建目录按 `0777`，再各自减掉 `umask`。文件少的那个执行位本来就不在基准里，不是 `umask` 减掉的。

**问：有 ACL 的文件上，`ls -l` 的属组三位显示的是什么？**
答：`mask`。它是 named 条目与 owning group 的有效权限上限；真实组权限要看 `getfacl` 的 `group::` 行，实际生效结果看 `#effective:`。

**问：`chattr +i` 生效期间，root 能不能改这个文件？**
答：不能直接改——追加、删除、改名、`chmod` 都会被拒（`EPERM`），必须先 `chattr -i`。但它不构成防篡改终点：能拿到 root 的人同样可以去掉属性，而代价是 `logrotate` 与包升级也会失败。

**问：为什么「`ls -l` 没有 `+`」不能推出「没有扩展属性」？**
答：`+` 只反映 ACL。`user.*` xattr、`chattr` 属性、file capabilities 都是扩展属性，但都不显示 `+`。要确认得用 `getfattr -d`、`lsattr`、`getcap`。

**问：`EACCES` 与 `EPERM` 各提示你先查哪一层？**
答：`EACCES` 先查路径 `x`、mode 与 ACL `mask`；`EPERM` 先查 capability、文件是否只读、`chattr` 属性与 MAC 拒绝。两者不是同义词，处置方向不同。

**第一反应不要做什么**：不要在没看路径的情况下改最后一级文件权限；不要在授权不生效时反复重加 ACL；不要把 `chmod -R 777` 当成授权手段。
