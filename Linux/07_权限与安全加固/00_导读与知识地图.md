# 权限与安全加固

## 知识地图

### 一次特权访问的十个阶段

时间主线跟着**一次特权访问**走：从「一个进程声称自己是谁」开始，到这次访问被放行或拒绝，再到它留下什么痕迹、出事时如何处置并恢复正常。

```mermaid
flowchart LR
  A["① 身份<br/>UID/GID · 账号文件"] --> B["② 认证<br/>PAM 四类栈"]
  B --> C["③ DAC 判定<br/>rwx · 路径逐级 x"]
  C --> D["④ 精细授权<br/>ACL · xattr"]
  D --> E["⑤ 特权载体<br/>SUID/SGID/Sticky"]
  E --> F["⑥ 最小特权<br/>capabilities"]
  F --> G["⑦ 合法通道<br/>sudo/su · SSH"]
  G --> H["⑧ 强制访问控制<br/>SELinux/AppArmor"]
  H --> I["⑨ 系统边界<br/>挂载选项 · sysctl"]
  I --> J["⑩ 留痕与处置<br/>auditd · 基线 · 取证"]
```

| 阶段 | 系统在这一段做什么 | 到这里要能说清 |
| --- | --- | --- |
| 1 身份 | 系统用 UID/GID、附加组与登录 shell 回答「你是谁」 | 内核按数值判定身份，名字只用于显示，因此 UID 为 0 的账号与它叫什么名字无关 |
| 2 认证 | PAM 的 `auth`/`account`/`password`/`session` 四类栈决定「现在能不能登录」 | 配置文件存在为什么不等于策略生效；账号过期属于哪一类栈 |
| 3 DAC 判定 | 内核先要求路径上每一级目录有 `x`，再按属主、属组与 other 的 `rwx` 挑一条规则 | 目录的 `r`/`w`/`x` 与文件的这三位为什么是两套语义 |
| 4 精细授权 | ACL 的 named 条目与 `mask` 在九个字符之外再加一档授权，`chattr` 属性在写入路径上再加一道限制 | `mask` 为什么会让已经加上的授权不生效 |
| 5 特权载体 | `execve()` 按文件上的 SUID/SGID 位换身份，而写在脚本上的特权位被内核忽略 | 设了 SUID 却不生效时，按哪三步排除 |
| 6 最小特权 | capabilities 把 root 的全有拆成 41 项，按项授予 | 为什么 `setcap` 在脚本上「设得上、不生效」 |
| 7 合法通道 | `sudo`/`su` 把身份提升到目标账号，SSH 决定谁能从哪个地址进来 | `sshd -T` 与「配置文件里写了」为什么不是一回事 |
| 8 强制访问控制 | SELinux 按类型上下文仲裁，AppArmor 按程序路径对应的 profile 仲裁 | MAC 的拒绝记录落在哪里，取决于 auditd 在不在运行 |
| 9 系统边界 | 挂载选项 `nosuid`/`nodev`/`noexec` 与内核安全参数给整机或整个文件系统加约束 | `noexec` 拦不住什么；参数值为什么可能在任何配置文件里都找不到 |
| 10 留痕与处置 | auditd 事件、登录痕迹、包数据库完整性校验与五类基线构成事后可核查的面 | 为什么单次采集的清单不算核查，必须与上次留档比对 |

**贯穿全章的一个三问**：这次访问的**主体**是谁（进程的 UID/GID/组/capabilities）；它**卡在哪一层**，那一层的证据是什么；哪些动作会毁掉现场，哪些动作不可逆。

**「提权面」指所有能把普通身份变成更强身份的路径的集合**，它不止 SUID 位，还包括 file capabilities、`sudo`/`su` 的授权、以 root 执行但可被非 root 写入的脚本与配置、SSH 钥匙、动态链接器、内核与设备接口、容器特权。**这些路径中的大多数平时完全静默**，因此核查靠的是与留档清单比对，而不是当下的印象。

**两处方向上的提醒。** 阶段 1 与阶段 2 发生在登录那一刻，阶段 3 到阶段 9 发生在每一次访存或每次 `execve`，阶段 10 是事后；排障时通常从「报错是哪一类」往回推，而不是从阶段 1 顺序走下来。另外，**「文件权限」与「访问身份」是两个问题**，因此只看客体属性（`ls -l` 的输出）永远解释不了「文件 755 为什么还是进不去」。

### 四个跨阶段的核对对象

有四类量各自贯穿多个阶段，排障时按它们切分比从头走一遍时间线更快；下面每一条都写明它覆盖哪些阶段，以及在这些阶段上分别读什么字段。

| 核对对象 | 它贯穿哪几个阶段 | 每一处读什么字段 |
| --- | --- | --- |
| 判定链 | 它贯穿阶段 3 到阶段 9，因为同一个 `EACCES` 或 `EPERM` 可能来自路径、权限位、ACL、能力、挂载选项、MAC 或内核参数中的任意一层 | 在阶段 3 读 `namei -l` 逐级的 mode 与属主、`stat -c %a` 的八进制 mode；在阶段 4 读 `getfacl -cp` 的 `mask::` 与 `#effective:`；在阶段 5 与阶段 6 读 `stat -c %a` 的首位与 `getcap`/`getpcaps` 给出的能力标志；在阶段 7 读 `sudo -l -U <user>` 的最终授权与 `sshd -T` 的认证项；在阶段 8 读审计原始日志里 `avc: denied` 的权限位与 `apparmor="DENIED"` 的 `denied_mask=`；在阶段 9 读 `findmnt -T <path> -o OPTIONS` 的选项与 `sysctl` 的参数值 |
| 特权载体 | 它贯穿阶段 5 到阶段 9，因为一条提权路径从文件上的特权位开始，经过授权工具、可写配置与 SSH 钥匙，最后落到容器与挂载选项；其中阶段 8 只决定哪一条路径被放行，不新增载体 | 在阶段 5 读 `find -perm -4000`/`-2000` 的文件清单与 `stat -c %a` 的首位；在阶段 6 读 `getcap -r /` 的清单与 `systemctl show -p CapabilityBoundingSet -p AmbientCapabilities` 的生效值；在阶段 7 读 `sudo -l -U <user>` 的授权条目与 `authorized_keys` 的选项；在阶段 8 读 `getenforce`/`aa-status` 的模式、`getsebool` 的布尔值与 `semanage port -l` 的端口类型；在阶段 9 读 `findmnt -o TARGET,FSTYPE,OPTIONS` 里缺 `nosuid`/`noexec` 的挂载点 |
| 可核查的证据 | 它贯穿阶段 1 到阶段 10，因为账号台账、权限与提权面基线、变更留痕、审计日志与包数据库校验各自记录同一批事件的不同侧面 | 在阶段 1 与阶段 2 读 `getent passwd`/`shadow`、`passwd -S` 与 `chage -l`；在阶段 3 到阶段 6 读 `stat`、`getfacl`、`find -perm` 与 `getcap` 的输出；在阶段 7 与阶段 8 读认证日志与 `ausearch -m AVC`；在阶段 9 读 `findmnt -T` 的挂载选项与相关 `sysctl` 的当前值；在阶段 10 读 `last`/`lastb`/`loginctl` 的会话记录与 `dpkg -V`/`rpm -Va` 的校验结果 |
| 入口收敛 | 它贯穿阶段 1 到阶段 9，因为减少入口与叠加强制策略有先后顺序 | 在阶段 1 与阶段 2 读登录 shell、`passwd -S` 的密码状态与 `chage -l` 的账号过期日期；在阶段 5 与阶段 6 读 `find -nouser -o -nogroup` 的无主文件清单与 `getcap -r /` 的结果，用来判断哪些特权载体该清掉；在阶段 7 读 `sshd -T` 的认证项与 `sudo -l -U <user>` 的授权粒度；在阶段 8 读 `getenforce`/`aa-status` 的模式；在阶段 9 读 `findmnt` 的挂载选项与相关 `sysctl` 的值 |

外加一条不是机制而是纪律的线：**变更纪律**。它贯穿每一个阶段——改 `sudoers`、PAM、`sshd_config`、SELinux 模式、`sysctl` 之前先留基线与带外会话，一次只改一项，改完用同一条命令复测。具体条款见本章治理篇与 `00_引言`。

## 术语速查

| 名词 | 一句话解释 | 在哪一篇展开 |
| --- | --- | --- |
| 主体 / 客体 | 发起访问的进程（带 UID/GID/组/capabilities）/ 被访问的对象（文件、目录、设备、socket、端口、内核接口） | 原理：身份、认证与账号文件 · 原理：文件权限为什么不决定一切 |
| `ruid` / `euid` / `suid` / `fsuid` | 真实身份 / 有效身份（决定绝大多数权限判定）/ 保存身份 / 文件系统判定身份 | 原理：身份、认证与账号文件 · 原理：提权面与最小特权 |
| NSS | 名字服务开关（`nsswitch.conf`），决定「账号去哪查」；接 LDAP/SSSD 后本地文件不再是唯一来源 | 原理：身份、认证与账号文件 |
| PAM | 模块化认证框架，把认证拆成 `auth`/`account`/`password`/`session` 四类栈 | 原理：身份、认证与账号文件 |
| DAC | 自主访问控制：属主通过 mode 与 ACL 决定谁能访问 | 原理：文件权限为什么不决定一切 |
| `umask` | 新建对象时按位减掉的默认权限，有登录会话、unit、进程三个落点 | 原理：文件权限为什么不决定一切 |
| ACL / `mask` / `#effective` | 属主/属组/other 之外的按用户、按组授权 / named 条目与 owning group 的有效权限上限 / 实际生效结果 | 原理：文件权限为什么不决定一切 |
| xattr | 扩展属性，ACL、file capabilities、`security.*` 标签都存放在这里 | 原理：文件权限为什么不决定一切 · 原理：提权面与最小特权 |
| `chattr +i` / `+a` | 不可修改（连 root 也要先去属性）/ 只能追加 | 原理：文件权限为什么不决定一切 |
| SUID / SGID / Sticky | 执行时换 `euid` 为文件属主 / 换 `egid`、目录上让新文件继承属组 / 目录内只有属主与目录属主能删 | 原理：提权面与最小特权 |
| `no_new_privs` | 一个进程标志，置位后 `execve` 不再提权（SUID 与 file capabilities 都失效） | 原理：提权面与最小特权 · 原理：强制边界与系统边界 |
| capabilities | 把 root 的特权拆成 41 项（`cap_last_cap=40`），按项授予 | 原理：提权面与最小特权 |
| 五个能力集合 | Permitted（上限）、Effective（当前生效）、Inheritable（跨 `execve`）、Bounding（硬上限）、Ambient（非 root 保留） | 原理：提权面与最小特权 |
| file capabilities / `setcap` | 挂在文件 xattr 上的能力，`cap_net_raw=ep` 中的 `e`/`p` 指 Effective/Permitted | 原理：提权面与最小特权 |
| `NOPASSWD` | sudoers 里免密执行某条命令，等于把该命令的能力无条件交出 | 体系 · 治理 |
| `use_pty` | 让 sudo 命令跑在独立伪终端，防终端注入 | 体系 |
| `sshd -T` / `-t` | 打印合并默认值与 `Include`/`Match` 之后的**生效**配置 / 只做语法检查 | 实操 · 体系 |
| `authorized_keys` 选项 | `command=`、`from=`、`restrict` 等按钥匙限权 | 体系 · 治理 |
| SELinux 上下文 | `user:role:type:level`，核心看 `type`；随 inode 走，不随路径走 | 原理：强制边界与系统边界 |
| AppArmor | 以程序路径为中心的策略与 profile，Ubuntu 默认；`enforce`/`complain` 两种模式 | 原理：强制边界与系统边界 |
| AVC | 审计记录里的一类；SELinux 的拒绝写 `avc: denied`，AppArmor 的拒绝写 `apparmor="DENIED"` | 原理：强制边界与系统边界 · 实操 |
| `nosuid` / `nodev` / `noexec` | 挂载点上让 SUID 与 file capabilities 失效 / 设备文件不生效 / 禁止直接执行 | 原理：强制边界与系统边界 |
| `fs.protected_*` | 一组内核参数，防普通用户借全局可写文件、FIFO、硬链接与符号链接提权 | 原理：强制边界与系统边界 |
| auditd | 内核审计事件的用户态收集者；规则有文件监控与系统调用两类 | 治理 · 实操 |
| 持久化点 | 攻击者下次还进得来的位置：cron/timer、enabled 服务、`authorized_keys`、shell 启动文件、`/etc/ld.so.preload`、PAM 配置 | 治理 |
| `dpkg -V` / `rpm -Va` | 用包数据库校验文件是否被改动；非 root 跑会出现 `?????????` | 实操 · 治理 |
| 五类基线 | 账号、提权面（SUID/SGID/capabilities）、监听端口、计划任务与自启、SSH 授权 | 治理 |

## 故障现场定位表

排障的第一问不是「怎么修」，而是「**这次拒绝发生在哪一层、那一层的证据在动**」。用这张表把现象定位到类别，再进对应篇目。

| 你看到的现象 | 它属于哪一类 | 现场在哪 | 第一反应不要做 |
| --- | --- | --- | --- |
| 文件本身 755，服务仍 `Permission denied` | 这属于拒绝发生在路径、ACL、挂载选项或 MAC 层的情况 | 先读 `namei -l <path>` 逐级的 mode 与属主、`getfacl -cp` 的 `mask::` 与 `#effective:`，再读 `findmnt -T` 的挂载选项，最后读审计日志里的 `apparmor="DENIED"` 或 `avc: denied` | 不要 `chmod -R 777` |
| 删不掉一个文件 | 这属于判定卡在目录的 `w`/`x`、sticky 位或 `chattr` 属性的情况 | 先读 `ls -ld <dir>` 与 `stat -c %a <dir>` 给出的 mode，再读 `lsattr` 的属性字母 | 不要递归 `chmod 777` 那个目录 |
| SUID/SGID 文件或带 capabilities 的文件多了一个 | 这属于提权面与留档清单出现差异的情况 | 先读 `find -perm -4000`/`-2000` 的清单与 `getcap -r /` 的结果，再用 `dpkg -S`/`rpm -qf` 反查包归属 | 不要只看数量就说正常 |
| 普通用户绑 80 端口失败 | 这属于进程缺少 `CAP_NET_BIND_SERVICE` 的情况 | 先读 `getcap <bin>` 的权限标志，再读 `sysctl net.ipv4.ip_unprivileged_port_start` 的端口阈值 | 不要把它改成 0 |
| 设了 SUID 却不生效 | 这属于特权位被清掉、挂载点带 `nosuid`、或被 `no_new_privs` 拦住的情况 | 先读 `stat -c %a` 的首位确认位还在不在，再读 `findmnt -T <path> -o OPTIONS` 的挂载选项 | 不要只说「内核忽略了」就收工 |
| `sudo` 提示不在 sudoers | 这属于 sudoers 授权或账号状态发生变化的情况 | 先读 `sudo -l -U <user>` 的最终授权与 `visudo -c` 的语法检查结果，再读 `id` 的组成员关系 | 不要直接给 `ALL=(ALL) NOPASSWD: ALL` |
| SSH 能连但新配置不生效 | 这属于配置被 `Include`/`Match` 覆盖，或改的不是生效文件的情况 | 先读 `sshd -T` 的生效值，再读 `sshd -T -C user=...,addr=...` 在具体连接上的取值 | 不要只 `systemctl reload` 就完事 |
| 服务在 `enforcing` 下起不来 | 这属于 MAC 拒绝导致启动失败的情况 | 先读 `ausearch -m AVC </dev/null>` 与审计原始日志里的拒绝记录，再读 `ls -Z` 的标签与 `aa-status` 的模式 | 不要把 `setenforce 0` 当修复 |
| 账号「已锁定」但还能登录 | 这属于只锁了密码而未清理其它认证通道的情况 | 先读 `getent shadow` 的密码与过期字段，再读 `authorized_keys` 的存在与选项、`who`/`loginctl` 的活跃会话 | 不要以为 `passwd -l` 等于停用账号 |
| 改完 sysctl 重启就没了 | 这属于只用 `sysctl -w` 改了运行时值而没有落盘的情况 | 先读 `/etc/sysctl.d/` 下有没有对应条目，再读 `sysctl --system` 之后的当前值 | 不要把临时值当已持久化 |
| 加固做完却说不清效果 | 这属于没有基线与验收命令、结论无法复核的情况 | 先读基线卡里同名项的采集值与时间戳，再读加固核对表的「是否达标」一列 | 不要用「感觉关掉了」当结论 |
| 怀疑被入侵 | 这属于提权面、账号与持久化点出现异常的情况 | 先读五类基线与上次留档的差异，再读 `last` 的登录记录、`ausearch` 的审计事件与 `dpkg -V` 的校验结果 | 不要关机、重启、`kill -9`、急着重装 |

两个容易被忽略的边界：

- **「没有报错」不等于「没有异常」。** SUID 文件、可写脚本、`authorized_keys`、file capabilities 平时完全静默，只有和上次基线比对才会冒出来。**安全基线必须留档，不能每次凭印象看一遍。**
- **「能登录」与「能提权」是两条独立的通道。** 锁掉密码不影响公钥；收紧 SSH 不影响本机 `sudo`；关掉 `sudo` 不影响 SUID 文件。因此停用一个账号时必须逐条通道确认，而不是只看密码字段。
