> [!cite] 参考资料
> `man 5 sshd_config`、`man 8 sshd`、`man 1 ssh`、`man 5 authorized_keys`、`man 1 ssh-keygen`、`man 1 ssh-copy-id`。

## 0. 30 秒速览

> [!abstract] 这一篇只要记住六句话
> - **最小加固是「只开该开的入口」**：`PubkeyAuthentication yes`、`PasswordAuthentication no`、`PermitRootLogin no`、`PermitEmptyPasswords no`。
> - **`sshd -T` 才是生效配置**：配置文件写进去不等于最终生效，`Match` 和 `Include` 会改变结果。
> - **`Include` 在文件顶部时，drop-in 文件赢**：本机 `/etc/ssh/sshd_config` 第 12 行就是 `Include /etc/ssh/sshd_config.d/*.conf`，而 sshd 的关键字是**先到先得**，所以在主文件后面写 `PermitRootLogin no` 不生效——实测副本里改成 `no` 后 `sshd -T` 仍报 `permitrootlogin yes`。
> - **`sshd -T -C user=...,addr=...` 看某个用户/地址的最终值**：`Match` 块按第一个匹配生效，不是「合并所有匹配」。
> - **`authorized_keys` 选项按钥匙限权**：`command=`、`from=`、`restrict` 比只开放登录更细。
> - **`known_hosts` 指纹变化是安全信号，不是「删掉就好」**：先确认是否换机、重装、NAT 或中间人。

## 1. 最小加固清单

```text
PubkeyAuthentication yes
PasswordAuthentication no
PermitEmptyPasswords no
PermitRootLogin no
AllowUsers ops deploy
MaxAuthTries 3
AllowTcpForwarding no
X11Forwarding no
```

```bash
sshd -t                          # 验证：语法检查
sshd -T | grep -E '^(pubkeyauthentication|passwordauthentication|permitrootlogin|permitemptypasswords|maxauthtries)'
                                  # 验证：当前生效配置
ss -lntp | grep ':22 '           # 验证：sshd 是否真的在监听（本机是）
systemctl is-active ssh          # 验证：服务状态
```

本机实测的生效值（`sshd -T`，共 95 行；**节选：这里只保留 18 行**，来源 `.labvm/evidence/07_ssh.out.txt`，2026-09-19 采集）：

```text
port 22
listenaddress 0.0.0.0:22
listenaddress [::]:22
usepam yes
logingracetime 120
maxauthtries 6
clientaliveinterval 0
clientalivecountmax 3
permitrootlogin yes
hostbasedauthentication no
pubkeyauthentication yes
gssapiauthentication no
passwordauthentication yes
kbdinteractiveauthentication no
permitemptypasswords no
x11forwarding yes
strictmodes yes
allowtcpforwarding yes
```

原文的 `/etc/ssh/sshd_config` 有效行只有这几条（其余都注释掉了，走默认值）：

```text
Include /etc/ssh/sshd_config.d/*.conf
KbdInteractiveAuthentication no
UsePAM yes
X11Forwarding yes
PrintMotd no
AcceptEnv LANG LC_*
Subsystem	sftp	/usr/lib/openssh/sftp-server
```

**注意：`permitrootlogin yes` 和 `passwordauthentication yes` 在主文件里一个字都没写，它们来自 `sshd_config.d/`**——这就是下一节要讲的重点。

## 2. `sshd -T`、`Include` 与 `Match`

### 2.1 `Include` 的优先级：先到先得，drop-in 常常赢

本机 `/etc/ssh/sshd_config` **第 12 行**就是 `Include /etc/ssh/sshd_config.d/*.conf`，而目录里有两个文件：

```text
/etc/ssh/sshd_config.d/10-dsh-root-login.conf   PermitRootLogin yes
/etc/ssh/sshd_config.d/50-cloud-init.conf       PasswordAuthentication yes
```

sshd 对同名关键字是**第一个读到的生效**。因为 `Include` 在文件开头，drop-in 里的值先被读到，**在主文件后面写 `PermitRootLogin no` 完全没有用**。本机实测（改的是 `/tmp` 副本，生产文件没动）：

```bash
cp /etc/ssh/sshd_config /tmp/07-ssh/sshd_config.test
sed -i -e 's/^#*PermitRootLogin.*/PermitRootLogin no/' -e 's/^#*PasswordAuthentication.*/PasswordAuthentication no/' /tmp/07-ssh/sshd_config.test
sshd -t -f /tmp/07-ssh/sshd_config.test && echo "语法 OK"
sshd -T -f /tmp/07-ssh/sshd_config.test | grep -iE '^(permitrootlogin|passwordauthentication|maxauthtries)'
```

```text
语法 OK
permitrootlogin yes            <- 改了主文件，仍是 yes
passwordauthentication yes     <- 同上
maxauthtries 3                 <- 这个没有 drop-in 覆盖，改了就生效
```

用一个自建的最小配置目录可以把这个规则单独验一遍：

```bash
mkdir -p /tmp/07-ssh/d && echo "PermitRootLogin yes" > /tmp/07-ssh/d/10-first.conf
printf 'HostKey /etc/ssh/ssh_host_ed25519_key\nInclude /tmp/07-ssh/d/*.conf\nPermitRootLogin no\n' > /tmp/07-ssh/t1.conf
sshd -T -f /tmp/07-ssh/t1.conf | grep -i '^permitrootlogin'
printf 'HostKey /etc/ssh/ssh_host_ed25519_key\nPermitRootLogin no\nInclude /tmp/07-ssh/d/*.conf\n' > /tmp/07-ssh/t2.conf
sshd -T -f /tmp/07-ssh/t2.conf | grep -i '^permitrootlogin'
```

```text
permitrootlogin yes     （Include 在前：drop-in 的值先到，赢）
permitrootlogin no      （Include 在后：主文件的值先到，赢）
```

> [!important] 加固 SSH 时改哪个文件？
> 在 Ubuntu 24.04 上，**要么改对应的 drop-in（`/etc/ssh/sshd_config.d/*.conf`），要么把 `Include` 挪到主文件末尾**——直接在主文件里追加一行常常毫无效果。改完必须用 `sshd -T` 验收，而不是看配置文件里写了什么。本机这个坑格外真实：`permitrootlogin yes` 就是被一个 drop-in 明确打开的。

### 2.2 `Match`

```bash
sshd -T -C user=ops,host=h,addr=10.1.2.3 | grep -E '^(passwordauthentication|maxauthtries)'
                                  # 验证：Match 对具体用户/地址的最终结果
```

`Match User/Address` 的规则是：满足条件时应用该块，**第一个匹配块生效**，后续不叠加。因此配置顺序很关键。

本机没有配置任何 `Match` 块，所以 `-C` 只是把最终值原样返回（实测 `sshd -T -C user=realtyz,addr=192.168.246.1,host=winbox` 与不带 `-C` 的结果一致：`permitrootlogin yes`、`passwordauthentication yes`、`forcecommand none`、`chrootdirectory none`、`permitopen any`）。**这也是一种有用的判据**：`-C` 的结果和全局值完全一样，说明没有 `Match` 在起作用。

## 3. `authorized_keys` 选项

一行钥匙前可以加选项：

```text
from="10.0.0.0/8",command="/usr/local/bin/backup" ssh-ed25519 AAAA...
restrict,port-forwarding ssh-ed25519 AAAA...
```

| 选项 | 作用 |
| --- | --- |
| `command=` | 该钥匙登录后只能执行指定命令，不进入交互 shell |
| `from=` | 限制来源地址/主机 |
| `restrict` | 现代写法，先关掉端口转发、agent forwarding、pty 等，再逐个打开 |
| `no-port-forwarding` | 禁止端口转发 |

## 4. 文件权限与 `StrictModes`

```bash
ls -ld ~ ~/.ssh ~/.ssh/authorized_keys
stat -c "%a %U:%G %n" ~ ~/.ssh ~/.ssh/authorized_keys
                                  # 验证：家目录不可被组/他人写，.ssh 700，authorized_keys 600
stat -c "%a %U:%G %n" /etc/ssh /etc/ssh/ssh_host_ed25519_key
                                  # 验证：服务端配置目录与主机私钥的权限
```

本机实测的服务端侧权限：

```text
755 drwxr-xr-x root root      /etc/ssh
600 -rw------- root root      /etc/ssh/ssh_host_ed25519_key
644 -rw-r--r-- root root      /etc/ssh/sshd_config
700 drwx------ root root      /root
755 drwxr-xr-x root root      /home
750 drwxr-x--- realtyz realtyz /home/realtyz
```

三个主机私钥（ecdsa/ed25519/rsa）都是 `600 root:root`，`sshd_config` 是 `644`。

`StrictModes` 默认 yes（本机 `sshd -T` 实测 `strictmodes yes`）；家目录或 `.ssh` 权限过宽时，SSH 会拒绝使用公钥。这是「钥匙明明放对了却登录不了」的常见原因。

## 5. 实验：在副本上校验加固配置（本机已实测，不动生产 sshd）

> [!example]- 实验：`sshd -t -f` 校验副本、`sshd -T -f` 看生效值、故意写错验证拦截
> **怎么做**：把 `/etc/ssh/sshd_config` 复制到 `/tmp`，改副本里的加固项，用 `sshd -t -f <副本>` 做语法检查、`sshd -T -f <副本>` 看解析后的生效值；再追加一条非法值，确认语法检查会拦下。
> **预期**：合法副本 `exit=0` 并能打印生效值；非法副本 `exit=255` 并指出行号。
> **风险**：**低到可以忽略——全程只碰副本**。改生产 `sshd_config` 到锁死登录是禁止操作，本实验不做，也不 reload 生产服务。
> **耗时**：约 10 分钟。
> **回滚**：`rm -rf /tmp/07-ssh`。
>
> ```bash
> mkdir -p /tmp/07-ssh && cp /etc/ssh/sshd_config /tmp/07-ssh/sshd_config.test
> sshd -t -f /tmp/07-ssh/sshd_config.test && echo "副本语法 OK"
> sed -i -e 's/^#*MaxAuthTries.*/MaxAuthTries 3/' -e 's/^#*LoginGraceTime.*/LoginGraceTime 20/' -e 's/^#*X11Forwarding.*/X11Forwarding no/' /tmp/07-ssh/sshd_config.test
> sshd -t -f /tmp/07-ssh/sshd_config.test
> sshd -T -f /tmp/07-ssh/sshd_config.test | grep -iE '^(logingracetime|maxauthtries|x11forwarding|permitrootlogin)'
> printf '\nPermitRootLogin maybe\n' >> /tmp/07-ssh/sshd_config.test
> sshd -t -f /tmp/07-ssh/sshd_config.test; echo "exit=$?"
> md5sum /etc/ssh/sshd_config; systemctl is-active ssh
> rm -rf /tmp/07-ssh
> ```
>
> 实测输出：
>
> ```text
> 副本语法 OK
> logingracetime 20
> maxauthtries 3
> permitrootlogin yes          <- 仍被 drop-in 压着，见第 2.1 节
> x11forwarding no
> /tmp/07-ssh/sshd_config.test line 133: unsupported option "maybe".
> exit=255
>
> 0a12ef5cc3580c2e0533fba58dba866d  /etc/ssh/sshd_config
> active
> ```
>
> 追加一条完全未知的指令，报错同样明确：
>
> ```text
> /tmp/07-ssh/bad2: line 133: Bad configuration option: NoSuchDirective
> /tmp/07-ssh/bad2: terminating, 1 bad configuration options
> exit=255
> ```
>
> 验收标准是**三件事同时成立**：`sshd -t -f` 退出码为 0、`sshd -T -f` 里的目标项确实变成期望值、生产 `/etc/ssh/sshd_config` 的 md5 没变且服务仍在监听 22 端口。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 改完 `sshd_config` 只 reload 就完事 | 不看 `sshd -T` 等于没验证 |
| 认为 `Match` 会把所有匹配块合并 | 第一个匹配块生效，后续不叠加 |
| 只开放密码登录不管 `PermitEmptyPasswords` | 空密码账号仍可能登录 |
| 家目录/`.ssh` 权限过宽 | `StrictModes` 拒绝公钥 |
| 看到 `known_hosts` 变化就删除 | 丢失判断中间人/换机的证据 |

## 决策练习

> [!question]- 场景：你改了 `sshd_config` 关掉密码登录并 reload，但同事测试时发现某用户仍能用密码登录。你怎么办？
> A. 再 reload 几次
> B. 用 `sshd -T` 和 `sshd -T -C user=...,addr=...` 看生效值，检查是否有 `Include`/`Match`/重复项覆盖，再修复
> C. 直接重装 openssh-server
>
> **答案：B。**
> A 不改变配置解析结果。
> C 是掩盖，且会丢失配置。
> B 是正解：**配置文件写进去不等于生效，要用 `sshd -T` 按实际连接参数验证。**

## 要点自测

> [!question]- SSH 加固的最小清单是什么？
> - 只开公钥、关密码/空密码/root 登录，限制用户与来源，收紧 `MaxAuthTries` 和转发。
> - **第一反应不要是什么**：不要只改一个 `PermitRootLogin no` 就宣布完成。

> [!question]- 为什么 `sshd -T` 比看配置文件可靠？
> - 它输出内核/sshd 最终生效值，已合并默认值、`Include`、`Match`。
> - `sshd -T -C` 可模拟具体用户/地址。
> - **第一反应不要是什么**：不要只看配置文件写没写。

> [!question]- `authorized_keys` 的 `command=` 和 `restrict` 各做什么？
> - `command=` 限定该钥匙只能执行指定命令；`restrict` 先关掉转发、pty 等，再按需打开。
> - **第一反应不要是什么**：不要把 `command=` 当成一种强认证来源，它只是入口后的限权。
