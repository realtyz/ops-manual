## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **最小加固是「只开该开的入口」**：`PubkeyAuthentication yes`、`PasswordAuthentication no`、`PermitRootLogin no`、`PermitEmptyPasswords no`。
> - **`sshd -T` 才是生效配置**：配置文件写进去不等于最终生效，`Match` 和 `Include` 会改变结果。
> - **`sshd -T -C user=...,addr=...` 看某个用户/地址的最终值**：`Match` 块按第一个匹配生效，不是「合并所有匹配」。
> - **`authorized_keys` 选项按钥匙限权**：`command=`、`from=`、`restrict` 比只开放登录更细。
> - **`known_hosts` 指纹变化是安全信号，不是「删掉就好」**：先确认是否换机、重装、NAT 或中间人。

## 1. 最小加固清单

```text
PubkeyAuthentication yes
PasswordAuthentication no
PermitEmptyPasswords no
PermitRootLogin no
AllowUsers ops deploy
MaxAuthTries 3
AllowTcpForwarding no
X11Forwarding no
```

```bash
sshd -t                          # 验证：语法检查
sshd -T | grep -E '^(pubkeyauthentication|passwordauthentication|permitrootlogin|permitemptypasswords|maxauthtries)'
                                  # 验证：当前生效配置
```

## 2. `sshd -T` 与 `Match`

```bash
sshd -T -C user=ops,host=h,addr=10.1.2.3 | grep -E '^(passwordauthentication|maxauthtries)'
                                  # 验证：Match 对具体用户/地址的最终结果
```

`Match User/Address` 的规则是：满足条件时应用该块，**第一个匹配块生效**，后续不叠加。因此配置顺序很关键。

## 3. `authorized_keys` 选项

一行钥匙前可以加选项：

```text
from="10.0.0.0/8",command="/usr/local/bin/backup" ssh-ed25519 AAAA...
restrict,port-forwarding ssh-ed25519 AAAA...
```

| 选项 | 作用 |
| --- | --- |
| `command=` | 该钥匙登录后只能执行指定命令，不进入交互 shell |
| `from=` | 限制来源地址/主机 |
| `restrict` | 现代写法，先关掉端口转发、agent forwarding、pty 等，再逐个打开 |
| `no-port-forwarding` | 禁止端口转发 |

## 4. 文件权限与 `StrictModes`

```bash
ls -ld ~ ~/.ssh ~/.ssh/authorized_keys
stat -c "%a %U:%G %n" ~ ~/.ssh ~/.ssh/authorized_keys
                                  # 验证：家目录不可被组/他人写，.ssh 700，authorized_keys 600
```

`StrictModes` 默认 yes；家目录或 `.ssh` 权限过宽时，SSH 会拒绝使用公钥。这是「钥匙明明放对了却登录不了」的常见原因。

## 5. 实验：配置解析与 `Match`

> [!example]- 实验：用 `sshd -T` 验证生效值
> **怎么做**：在临时目录写一个自用 `sshd_config`，包含 `Include` 或 `Match`，用 `sshd -T -f <config>` 与 `-C` 解析。
> **预期**：全局值与 `Match` 后的值不同，重复项取第一个。
> **风险**：不启动服务、不监听端口。
> **耗时**：约 10 分钟。
> **回滚**：删除临时配置。

```bash
SSHD=$(command -v sshd || true)
if [ -n "$SSHD" ]; then
  D=$(mktemp -d)
  printf '%s\n' 'PasswordAuthentication yes' 'Match User ops' '    PasswordAuthentication no' > "$D/c"
  "$SSHD" -T -f "$D/c" -C user=ops,addr=10.0.0.1 | grep '^passwordauthentication '
  rm -rf "$D"
fi
```

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 改完 `sshd_config` 只 reload 就完事 | 不看 `sshd -T` 等于没验证 |
| 认为 `Match` 会把所有匹配块合并 | 第一个匹配块生效，后续不叠加 |
| 只开放密码登录不管 `PermitEmptyPasswords` | 空密码账号仍可能登录 |
| 家目录/`.ssh` 权限过宽 | `StrictModes` 拒绝公钥 |
| 看到 `known_hosts` 变化就删除 | 丢失判断中间人/换机的证据 |

## 决策练习

> [!question]- 场景：你改了 `sshd_config` 关掉密码登录并 reload，但同事测试时发现某用户仍能用密码登录。你怎么办？
> A. 再 reload 几次
> B. 用 `sshd -T` 和 `sshd -T -C user=...,addr=...` 看生效值，检查是否有 `Include`/`Match`/重复项覆盖，再修复
> C. 直接重装 openssh-server
>
> **答案：B。**
> A 不改变配置解析结果。
> C 是掩盖，且会丢失配置。
> B 是正解：**配置文件写进去不等于生效，要用 `sshd -T` 按实际连接参数验证。**

## 要点自测

> [!question]- SSH 加固的最小清单是什么？
> - 只开公钥、关密码/空密码/root 登录，限制用户与来源，收紧 `MaxAuthTries` 和转发。
> - **第一反应不要是什么**：不要只改一个 `PermitRootLogin no` 就宣布完成。

> [!question]- 为什么 `sshd -T` 比看配置文件可靠？
> - 它输出内核/sshd 最终生效值，已合并默认值、`Include`、`Match`。
> - `sshd -T -C` 可模拟具体用户/地址。
> - **第一反应不要是什么**：不要只看配置文件写没写。

> [!question]- `authorized_keys` 的 `command=` 和 `restrict` 各做什么？
> - `command=` 限定该钥匙只能执行指定命令；`restrict` 先关掉转发、pty 等，再按需打开。
> - **第一反应不要是什么**：不要把 `command=` 当成一种强认证来源，它只是入口后的限权。
