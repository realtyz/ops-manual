## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **演练的前提是「能确定地救回来」，不是「反正是虚拟机」。**
>   怎么验证：快照已打并记下名字、控制台能独立登录、确认不是生产机——三条缺一不可。
> - **破坏方式不同，救援入口不同。**
>   证据：网卡写坏走控制台，`fstab` 写坏走 `emergency.target`，`passwd` 写坏走 rescue/`vipw`，系统起不来走 Live 环境——**入口选错，越救越糟**。
> - **SysRq 的位掩码是「允许哪些功能」，不是一个开关。**
>   证据：常用安全位组合是 `176`（sync + remount-ro + reboot）；`kernel.sysrq=1` 会连触发 panic/强制重启一起打开。
> - **快照回滚 ≠ 回到过去。**
>   证据：时间、外部依赖状态、机器身份与密钥、快照之后产生的数据都不在快照里，回滚后要主动校时与核对。
> - **`kill -9 1` 无效，而且要分两层看。**
>   证据：普通用户拿到的是 `Operation not permitted`（实测本机 `uid=1000` 时 PID 1 为 systemd，仍存活）；root 场景下内核屏蔽这些信号的默认终止动作，表现为「返回成功但进程不死」。

## 2. 五种破坏性演练

| 演练 | 怎么弄坏（实验机上） | 典型现象 | 恢复路径 |
| --- | --- | --- | --- |
| **打满根分区** | 在独立分区上 `dd if=/dev/zero of=/mnt/lab/big bs=1M count=...`（**不要直接写根分区**，见子笔记 10 的 loop 做法） | `No space left on device`；日志/服务写失败；ext4 可能触发只读重挂 | 删大文件、`journalctl --vacuum-size=200M`、`truncate -s 0` 截断被进程持有的日志；必要时从单用户清理 |
| **写坏 `/etc/fstab`** | 把某个 UUID 改错一个字符，或去掉 `nofail` 后写一个不存在的设备 | 重启时进 `emergency mode`，`systemctl --failed` 有失败挂载 | `emergency.target` 里 `mount -o remount,rw /` → 修 `fstab` → `mount -a` 验证 → `systemctl default` |
| **down 掉网卡** | `ip link set <dev> down`（远程操作 = 断连） | SSH 断开，业务不可达 | 控制台里 `ip link set <dev> up`；NetworkManager 系统用 `nmcli con up <名称>`；远程操作前先用 `nohup` 或 `at` 定时恢复 |
| **改坏 `/etc/passwd`** | 把某个用户行的字段删一个（**用 `vipw` 而不是 `vi`**，它会加锁与做基本校验） | 登录失败、`su`/`sudo` 报错、`getent passwd` 异常 | rescue/单用户里用 `vipw`/`pwck` 修回；或从快照恢复 |
| **SysRq 触发 panic** | `sysctl -w kernel.sysrq=1` 后 `echo c > /proc/sysrq-trigger` | 立即内核 panic → 重启（配了 kdump 则落 `vmcore`） | 等重启，看 `journalctl -b -1` 与 `/var/crash`；这是「内核崩溃取证」最便宜的练习方式 |

> [!tip] 每条演练都要留下两样东西
> **一是现象证据**（截图或命令输出，证明你看到了什么），**二是耗时**（从弄坏到恢复用了多久）。耗时才是演练真正的产出——它决定了真实故障时你有多大的把握。

## 3. SysRq：内核的应急接口

SysRq 是内核暴露的一个「按键」接口，**位掩码控制允许哪些功能**。常用安全位组合是 `176`（`16` sync + `32` remount-ro + `128` reboot，即「能落盘、能只读重挂、能重启」，但不触发进程转储与崩溃）。**生产上建议只开必要位**；`1` 会连「触发 panic/强制重启」一起打开。各位的确切含义以 `Documentation/admin-guide/sysrq.rst` 为准。

它救过很多人，也害过很多人：数据库写入卡死时，`sync`（`s`）→ `remount-ro`（`u`）→ `reboot`（`b`）是经典的「安全重启」序列；但如果在错误的机器上敲了 `c`，就是一次不必要的宕机。

```bash
cat /proc/sys/kernel/sysrq              # 验证：当前位掩码（0 = 全关，1 = 全开，176 = 只开 sync/remount-ro/reboot）
sysctl -w kernel.sysrq=176              # 验证：实验机上只开安全位（重启后失效，要持久化需写 sysctl.d）
```

## 4. 四类「把自己关在门外」的恢复入口

> [!tip] 第一反应不要是「重装系统」
> 下面四种破坏方式都有对应的救援路径——**前提是你按子笔记 01 准备了控制台**。

| 现象 | 入口 | 关键动作 |
| --- | --- | --- |
| SSH 不通，但控制台能进 | 控制台登录 | 先看网卡是否 `down`、再 `ip a` 与 `ip route`，恢复网络后再排查业务 |
| 重启后进 `emergency mode`（`fstab` 写坏） | 控制台 + `emergency.target` | `mount -o remount,rw /` → 注释/修正出错行 → `mount -a` 验证 → `systemctl default` |
| 登录报错、`su`/`sudo` 失败（`passwd` 改坏） | rescue/单用户，或从快照启动 | `vipw` 改回、`pwck` 校验；`/etc/shadow` 同理（`vipw -s`） |
| 系统起不来 / 文件系统坏了 | Live CD/USB 或云主机挂载恢复 | 挂载根分区到 `/mnt` 后改文件；文件系统的深水区在阶段 5《存储与文件系统》 |

```bash
mount -o remount,rw /                   # 验证：紧急模式下先把根挂成可写（否则改不了 fstab）
mount -a                                # 验证：按 fstab 重新挂一遍，立即暴露仍存在的错误
findmnt --verify                        # 验证：逐条校验 fstab 语法与设备是否存在
pwck; grpck                             # 验证：改完 passwd/group 后校验一致性
```

## 5. 快照回滚之后：现象对不上是正常的

回滚磁盘 ≠ 回到过去。以下东西**不在快照里**，所以「回滚后现象变了」通常不是玄学：

| 不在快照里的东西 | 表现 | 处理 |
| --- | --- | --- |
| 时间与外部时钟状态 | 时间跳回、证书校验失败、日志时间线错乱 | 回滚后立刻 `timedatectl`/`chronyc sources` 校时 |
| 外部依赖的状态 | 数据库、消息队列、对端服务仍是「未来」的状态 | 把依赖一起回滚，或按顺序重建 |
| 机器身份与密钥 | SSH host key 变化、`machine-id` 重复（克隆场景） | 确认 host key 变化是你预期的；克隆模板要重置 `machine-id` |
| 快照之后产生的数据 | 回滚即丢失 | 回滚前先确认「这份数据能不能丢」 |

```bash
timedatectl; chronyc sources -v         # 验证：回滚后时间是否正常、有没有对上游
hostnamectl; cat /etc/machine-id        # 验证：机器身份（克隆/回滚后是否重复）
systemctl --failed                      # 验证：回滚后有没有失败的单元
journalctl -b -1 | tail -50             # 验证：上一次启动（也就是回滚前那一次）的结尾发生了什么
```

## 6. 一个反直觉点：PID 1 忽略 `SIGKILL`/`SIGSTOP`

`kill -9 1` 不会有任何效果——但「为什么没效果」要分两层看，把两层混在一起是常见的面试扣分点。

**第一层：普通用户根本没有向 PID 1 发信号的权限。** PID 1（init/systemd）是 root 进程，而给别的进程发信号要求发送者 euid 匹配或具备 `CAP_KILL`——所以非 root 用户拿到的是明确的 `EPERM`，不是「神秘的静默失败」。实测（本机 WSL2，`uid=1000`，PID 1 为 systemd）：

```text
ps -p 1 -o pid,comm,cmd              # 验证：PID 1 是谁（本机是 systemd）
    PID COMMAND         CMD
      1 systemd         /usr/lib/systemd/systemd --system --deserialize=95

kill -9 1                            # 验证：普通用户向 PID 1 发信号的结果
/bin/bash: line 1: kill: (1) - Operation not permitted

ps -p 1 -o pid,comm                  # 验证：PID 1 依然存活
      1 systemd
```

**第二层：就算有权限（root），内核也不会让它生效。** 内核对 PID 1 有一条特殊规则：**凡是「默认动作会终止进程」的信号，内核都不对 PID 1 执行这个默认动作——信号等同被忽略，进程继续运行**（`SIGKILL`、`SIGSTOP` 无法捕获，所以也逃不掉这条规则）。原因很直白：init 一死，就没人回收孤儿进程、没人接管服务与挂载了；内核宁可让 `kill` 返回成功，也不允许系统进入这种状态。所以 root 下的表现是「**命令返回成功，PID 1 依然活着**」。

> 第二层**本文未实测**（需要 root，而实测环境是非 root 用户），依据是内核信号处理规则与 `signal(7)`：对全局 init，内核不执行致命信号的默认终止动作。要做实验的话，在**可快照的实验机**上用 root 跑一次 `kill -9 1`，再用 `ps -p 1` 确认它还在——顺便体会一下「返回成功 ≠ 生效」。

两条延伸：

- **容器里的 PID 1 是「子命名空间的 init」，同样受这套规则保护；但从宿主机看它只是一个普通进程**：所以「容器里的 1 号进程杀不掉」和「宿主机上杀掉容器的 1 号进程」是两件事——后者用宿主机看到的 PID 就能杀。这也是为什么有些容器停不掉要靠 `docker rm -f` 或宿主侧 `kill`。
- **PID 1 还负责回收孤儿进程**：容器里如果让业务进程直接当 PID 1，它通常不会 `wait()` 那些被它「继承」的孤儿，于是出现僵尸堆积——这是「容器里该不该用 `tini`/`--init`」这类问题的根源。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 不确认控制台就开始演练 | 网络/`fstab`/认证写坏后 SSH 进不去，快照也救不了你 |
| 把 `1` 当 `SysRq` 的安全值 | `kernel.sysrq=1` 会连触发 panic/强制重启一起打开；生产用位掩码（如 `176`）只开必要功能 |
| 用 `vi` 直接改 `/etc/passwd` | 没有加锁与校验，容易改坏；用 `vipw`/`vigr`，改完 `pwck`/`grpck` 自检 |
| 在 `fstab` 上用 `nofail` 之外的方式写可选挂载 | 一个不存在的设备会把启动拖进紧急模式；可选挂载要配 `nofail` 与超时 |
| 演练后直接重启，不先看日志 | `journalctl -b -1` 是上一次启动的唯一入口，先取下来再重启 |
| 以为回滚快照 = 回到过去 | 时间、外部依赖、机器身份、快照后的数据都不在快照里 |
| 克隆虚拟机后不重置 `machine-id` | 克隆体与原机身份重复，日志/授权/监控都会混淆 |
| 对真实业务 PID 试 `kill -9` | 演练一律用自己起的 `sleep` 测试进程，绝不对业务 PID 试手 |

## 决策练习

> **场景**：你在实验机上做「写坏 `/etc/fstab`」的演练。改完重启，SSH 断了，控制台显示 `You are in emergency mode`。此时你应该先做什么？
>
> A. 立刻重启，看看能不能正常起来。
> B. 先在紧急模式里跑 `systemctl --failed` 与 `journalctl -xb` 找到失败单元，`mount -o remount,rw /` 后修回 `fstab`，`mount -a` 验证，再 `systemctl default` 继续启动。
> C. 直接从快照回滚，不分析原因。

**为什么选 B**：紧急模式本身就是一个可用的救援环境，`fstab` 的问题在几行命令内就能修好；先看失败单元是为了确认「确实是这条挂载」，避免修错地方。这个顺序（取证 → 修 → 验证 → 继续启动）就是真实故障里的处置顺序。

**为什么 A 不对**：重启不会让错误的 `fstab` 变对，只会让你重新进一次紧急模式；如果错误涉及根或 `/boot`，还可能彻底进不去。

**为什么 C 不对**：回滚能恢复，但跳过了「在紧急模式里定位与修复」这项技能——而这正是这次演练要练的东西。回滚应作为修复失败后的兜底，不是第一反应。

## 要点自测

> [!question]- 五种破坏方式分别从哪个入口恢复？
> - 打满文件系统：直接在系统里删/截断大文件，必要时从单用户或快照清理。
> - 写坏 `fstab`：控制台 + `emergency.target`，`mount -o remount,rw /` 后修文件。
> - down 网卡：控制台把链路拉起来；远程操作前先用 `nohup`/`at` 做定时恢复。
> - 改坏 `passwd`：rescue/单用户里 `vipw` 修回并 `pwck` 校验，或从快照恢复。
> - SysRq panic：等重启后用 `journalctl -b -1` 与 `/var/crash` 取证；配了 kdump 才有 `vmcore`。
> - **第一反应不要是什么**：不要用「重装系统」作为任何一条的默认恢复方式。

> [!question]- `kernel.sysrq=176` 这个数字是什么意思？
> - 它是位掩码：`16`（sync，落盘）+ `32`（remount-ro，只读重挂）+ `128`（reboot，重启）= `176`。
> - 这个组合允许「安全重启」，但不允许触发进程转储或内核崩溃。
> - 生产上按需最小化开启；`1` 是「全开」，包含危险位。
> - **第一反应不要是什么**：不要在生产机上用 `kernel.sysrq=1` 图省事。

> [!question]- 回滚快照之后，为什么现象常常和演练前对不上？
> - 快照只保护磁盘，不保护时间、外部依赖状态、机器身份与密钥、快照之后产生的数据。
> - 典型表现：时间跳回导致证书校验失败、日志时间线错乱；上游仍然是「未来」的状态；克隆场景 `machine-id` 重复。
> - 处理：回滚后立刻校时、核对 `/etc/machine-id`、`systemctl --failed`，并确认外部依赖的状态与预期一致。
> - **第一反应不要是什么**：不要以为「现象对不上 = 快照坏了/回滚失败了」。

> [!question]- 为什么 `kill -9 1` 无效？两层原因分别是什么？
> - 第一层是权限：PID 1 是 root 进程，普通用户没有 `CAP_KILL` 也不是同一 euid，拿到 `EPERM`（实测本机 `uid=1000` 时返回 `Operation not permitted`）。
> - 第二层是内核规则：即使 root 发送，内核对「默认动作会终止进程」的信号也不执行默认动作，表现为「返回成功但进程不死」。
> - 容器里的 PID 1 同样受保护，但从宿主机看它只是普通进程，可以用宿主侧 PID 杀掉。
> - **第一反应不要是什么**：不要把两层混成一句「PID 1 杀不掉」——面试里这是常见的扣分点。
