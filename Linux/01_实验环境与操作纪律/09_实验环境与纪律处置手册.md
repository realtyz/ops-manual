# 实验环境与纪律处置手册

> [!cite] 参考资料
> 本篇是各篇结论的**收口**，不引入新机制：`man 5 fstab`、`man 8 mount`、`man 1 systemctl`、`man 1 vipw`、`man 8 pwck`、`man 8 ldconfig`、`man 8 ld.so`、`man 1 journalctl`；处置步骤的机制出处见子笔记 01–08 的对应小节。
>

## 0. 统一原则

> [!abstract] 处置前三句话
> - **先判断「现在还能不能取到现场」，再决定先取证还是先止损。**
> - **没确认回滚路径之前，不做不可逆操作。** 重装、`fsck -y` 写盘、恢复出厂都属于不可逆。
> - **每一步都要有验收动作。** 「命令执行了」不等于「问题解决了」；要看 `ldd`/`mount -a`/`systemctl --failed` 的复验结果。

三条通用动作，任何一类现象都先做：

```bash
date; hostname; uptime                  # 验证：时间线、机器身份与当前负载
systemctl --failed                      # 验证：能进系统时，哪些单元失败了
journalctl -k -n 50 --no-pager          # 验证：内核最近说了什么
```

实测输出（本实验机）：

```text
date; hostname; uptime
Sat Sep 19 08:09:19 AM UTC 2026
linux-lab
 08:09:19 up  1:00,  5 users,  load average: 0.25, 0.15, 0.07

journalctl -k -n 5 --no-pager
Sep 19 08:08:43 linux-lab kernel: EXT4-fs (loop0): mounted filesystem 4d9cc4e4-… r/w with ordered data mode. Quota mode: none.
Sep 19 08:08:43 linux-lab kernel: EXT4-fs (loop0): unmounting filesystem 4d9cc4e4-….
Sep 19 08:08:43 linux-lab kernel: loop0: detected capacity change from 0 to 65536
Sep 19 08:08:43 linux-lab kernel: EXT4-fs (loop0): mounted filesystem 72fc5dad-… r/w with ordered data mode. Quota mode: none.
Sep 19 08:08:43 linux-lab kernel: EXT4-fs (loop0): unmounting filesystem 72fc5dad-….
```

> [!info] 这三条命令的**真实用法**是「先定性，再挑分支」
> `date`/`hostname`/`uptime` 定的是「**这条时间线属于哪台机器的哪一段**」；`journalctl -k` 里如果出现 `EXT4-fs error`、`I/O error`、`Out of memory` 这类行，就直接把你送到本手册第 4 节或阶段 4/5 的深水区，不用再猜。
>
> **注意 `systemctl --failed` 在多章并行的实验机上可能是非空的**：本机实测在某一时刻列出了 1 个失败单元 `lab08b-stubborn.service`（description 为 `lab08b ignores SIGTERM`）——那是**另一个章节正在做的实验**，不是本机自身有问题。这正是「基线」要写清时间的原因：**没有 `--failed` 的历史基线，你就分不清「本来就这样」和「刚坏的」。**

## 1. SSH 不通，但控制台能进

> [!tip] 第一反应不要是「重装系统」
> 控制台能进，说明机器整体还活着；先按「网络 → 认证 → 服务 → 防火墙」四层查，绝大多数能在几分钟内恢复。

```bash
ip -br addr                             # 验证：网卡是否存在、是否处于 UP、地址是否还在
ip route                                # 验证：默认路由是否还在（地址在但没路由，同样不通）
systemctl status NetworkManager 2>/dev/null || systemctl status systemd-networkd
                                        # 验证：网络管理服务是否正常（家族不同，服务名不同）
ss -lntp | grep ':22'                   # 验证：sshd 是否在监听 22 端口
systemctl status sshd 2>/dev/null || systemctl status ssh
                                        # 验证：SSH 服务是否在运行（RHEL 是 sshd，Ubuntu 是 ssh）
nft list ruleset | head -30             # 验证：防火墙实际规则里有没有把 22 端口拒掉
```

**处置分支**：

- 网卡 `DOWN` → `ip link set <dev> up`；NetworkManager 系统用 `nmcli con up <名称>`。
- 地址或路由丢失 → 按子笔记 03 的家族入口恢复（netplan/nmcli）。
- `sshd` 没监听 → 看 `journalctl -u sshd -n 50`，多半是配置改坏；用 `sshd -t` 校验后再启动。
- 规则拒掉 22 → 先加临时放行规则恢复访问，再改持久配置并 `nft list ruleset` 复验。

**本机实测（`linux-lab`，只读）**：

```text
ip -br addr

ens33            UP             192.168.246.128/24 fe80::20c:29ff:fe66:2c0f/64

ip route
default via 192.168.246.2 dev ens33 proto static
192.168.246.0/24 dev ens33 proto kernel scope link src 192.168.246.128

systemctl status NetworkManager
Unit NetworkManager.service could not be found.
systemctl status systemd-networkd
● systemd-networkd.service - Network Configuration
     Loaded: loaded (/usr/lib/systemd/system/systemd-networkd.service; enabled; preset: enabled)
     Active: active (running) since Sat 2026-09-19 07:08:34 UTC; 1h 0min ago

ss -lntp | grep ':22'
LISTEN 0      4096         0.0.0.0:22         0.0.0.0:*    users:(("sshd",pid=1348,fd=3),("systemd",pid=1,fd=180))
LISTEN 0      4096            [::]:22             [::]:*    users:(("sshd",pid=1348,fd=4),("systemd",pid=1,fd=182))

systemctl status ssh
● ssh.service - OpenBSD Secure Shell server
     Loaded: loaded (/usr/lib/systemd/system/ssh.service; disabled; preset: enabled)
     Active: active (running) since Sat 2026-09-19 07:20:10 UTC; 49min ago
systemctl status sshd
Unit sshd.service could not be found.
```

**这张现场里有三个「教科书不一定告诉你」的细节**：

- **网络由 `systemd-networkd` 管，不是 NetworkManager**：`systemctl status NetworkManager` 报 `Unit NetworkManager.service could not be found.`。这正是子笔记 03 说的家族/子系统差异——**在 Ubuntu Server 上默认走 netplan + `systemd-networkd`**，照着「`nmcli con up`」修网络会扑空。所以那个 `||` 兜底写法很关键：`systemctl status NetworkManager 2>/dev/null || systemctl status systemd-networkd`。
- **SSH 服务名是 `ssh` 而不是 `sshd`**：`systemctl status ssh` 正常，`systemctl status sshd` 报 `Unit sshd.service could not be found.`。**先 `command -v`/`status` 确认服务名，再写脚本**。
- **`ss -lntp` 的 `users:` 里同时出现 `sshd` 和 `systemd`**：因为 sshd 是 socket-activated，`systemd`（PID 1）为它持有监听 fd。看到两行 22 端口不是「起了两个 sshd」，而是 **socket activation 的正常形态**——这是排查「端口被谁占着」时最容易误判的一处。

```bash
nft list ruleset | head -5; echo "nft_exit=${PIPESTATUS[0]}"
ufw status verbose
```

实测：`nft list ruleset` 退出码 `0` 但**无任何输出**——说明内核里当前没有 netfilter 规则集；`ufw status verbose` 返回 `Status: inactive`。**即本机防火墙前端未启用、底层也没有规则**，所以「22 端口能不能进」当前只由 sshd 与网络决定，不存在被防火墙挡住的可能。（生产机上做这一步要记下 `nft list ruleset` 的输出作为对照基线。）

> [!warning] 管道之后的 `$?` 不是上游命令的退出码
> 上面写成 `${PIPESTATUS[0]}` 是必须的：`nft list ruleset | head -5; echo $?` 里的 `$?` 拿到的是 **`head` 的状态**，不是 `nft` 的。这一条在本项目的迁移里真实踩过——阶段 1 的一处 `dd … | tail -3; echo "dd_exit=$?"` 因此把 `dd` 真实的退出码 **1** 读成了 **0**，进而得出「`dd` 的退出码不可信」这个**错误结论**（详见子笔记 10 第 3.3 节）。凡是把命令接进管道再取退出码，一律用 `${PIPESTATUS[@]}`，或者干脆**不要接管道**、把输出重定向到文件后再读。

**验收**：从另一台机器 `ssh` 能进，且 `ip route` 与防火墙规则都符合预期。

## 2. 重启后进 `emergency mode`（`fstab` 写坏）

> [!tip] 第一反应不要是「再重启一次」
> 重启不会让错误的 `fstab` 变对；如果错误涉及根或 `/boot`，还可能彻底进不去。

> [!warning] 本节未实测
> 本实验环境只有 SSH 一条通道，**改坏 `fstab` 之后没有控制台可以进 `emergency.target`**，因此本节步骤保持文档值。本机改做的**只读预检**已实测：`findmnt --verify` 报告 `0 parse errors, 0 errors, 1 warning`，那条 warning 是 `[W] non-bind mount source /swap.img is a directory or regular file`（swap 用文件而不是分区，属正常）。**把 `findmnt --verify` 当「改 `fstab` 前后的必跑项」，可以在不需要控制台的前提下拦掉大部分低级错误。**

```bash
systemctl --failed                      # 验证：找出失败的挂载单元（通常名字就指向那一行）
journalctl -xb | tail -50               # 验证：本次启动的失败详情
mount -o remount,rw /                   # 验证：先把根挂成可写，否则改不了文件
vi /etc/fstab                           # 修正出错行（先注释掉，不要直接删）
mount -a                                # 验证：逐条重新挂载，立即暴露仍存在的错误
findmnt --verify                        # 验证：校验 fstab 语法与设备是否存在
systemctl default                       # 验证：继续正常启动
```

**验收**：`systemctl default` 后进入多用户，`systemctl --failed` 为空，`findmnt` 里能看到所有预期挂载。

**回滚**：修复前先 `cp -a /etc/fstab /etc/fstab.bak.$(date +%F-%H%M)`；实在修不回来就从快照恢复。

## 3. 登录报错、`su`/`sudo` 失败（`passwd` 改坏）

> [!tip] 第一反应不要是「用 `vi` 直接改 `/etc/passwd`」
> 用 `vipw`——它会加锁、会做基本校验，能避免并发写入和格式破坏。

```bash
getent passwd <用户>                    # 验证：这个用户在 NSS 里是否还解析得出来
pwck                                    # 验证：passwd 文件的一致性（会列出可疑行）
vipw                                    # 验证：安全地编辑 /etc/passwd（它会先加锁）
grpck                                   # 验证：group 文件一致性
```

实测输出（本实验机，只读部分）：

```text
getent passwd realtyz
realtyz:x:1000:1000:realtyz:/home/realtyz:/bin/bash

pwck（尾部）
user 'list': directory '/var/list' does not exist
user 'irc': directory '/run/ircd' does not exist
pwck: no changes
pwck_exit=0

grpck
grpck_exit=0
```

**怎么读这份输出**：`pwck` 退出码 `0` 且最后一行是 `pwck: no changes`，说明**没有需要修的条目**；上面两行 `directory ... does not exist` 是**告警不是错误**——`list`/`irc` 这类系统账号的家目录本来就不存在（`/run/ircd` 只在对应服务运行时才建），这是 Ubuntu 默认 `passwd` 的正常形态。**「`pwck` 有输出」不等于「文件坏了」**，要看退出码与最后一行；判据是退出码 `0` + `no changes`。

**处置分支**：

- 只有 shell 或家目录字段错 → 用 `vipw` 改回，`pwck` 复验。
- 整行被删或字段错乱、`vipw` 也进不去 → 从 rescue/单用户进入，或挂载根分区后在外部修。
- `/etc/shadow` 出问题 → `vipw -s`（RHEL 与 Debian 都支持），不要用普通编辑器。
- 完全修不回来 → 从快照恢复，或从 Live 环境挂载后改。

**验收**：`su - <用户>` 与 `sudo -l` 正常；`pwck` 无报错。

## 4. 系统起不来 / 文件系统报错

> [!tip] 第一反应不要是「对有数据的盘直接 `fsck -y`」
> 自动修复会按工具的默认答案处理每一个问题，可能删掉目录项、丢数据。**先只读检查，再决定是否写盘。**

```bash
lsblk -o NAME,SIZE,FSTYPE,MOUNTPOINTS    # 验证：盘与分区的识别情况
blkid                                    # 验证：UUID / 文件系统类型是否与 fstab 一致
journalctl -b -1 | tail -50              # 验证：上一次启动在内核层报了什么（EXT4-fs error 之类）
```

实测输出（本实验机）：

```text
lsblk -o NAME,SIZE,FSTYPE,MOUNTPOINTS
NAME                       SIZE FSTYPE      MOUNTPOINTS
sda                         80G
├─sda1                       1M
├─sda2                       2G ext4        /boot
└─sda3                      48G LVM2_member
  └─ubuntu--vg-ubuntu--lv   48G ext4        /
sr0                        3.8G iso9660

blkid（节选）
/dev/sr0: UUID="2026-09-09-09-12-22-00" LABEL="Ubuntu-Server 24.04.5 LTS amd64" TYPE="iso9660" PTTYPE="PMBR"
/dev/mapper/ubuntu--vg-ubuntu--lv: UUID="30ab1acf-de89-4031-b8fc-302216d92af6" TYPE="ext4"
/dev/sda2: UUID="5dbd648c-63f3-4460-a25a-8d9b8d07d0ea" TYPE="ext4"
/dev/sda3: UUID="tNLBbJ-8Y8J-XsVY-JV6B-t7kP-OXwD-zhygtq" TYPE="LVM2_member"
```

**这段现场的价值在于「层数」**：`sda3`（`LVM2_member`）→ `ubuntu--vg-ubuntu--lv`（ext4）→ `/` 是三段结构，而 `/etc/fstab` 里写的是 `/dev/disk/by-id/dm-uuid-LVM-…`，`blkid` 报的却是 `UUID=30ab1acf-…`。**同一个设备有「LVM 标识」「文件系统 UUID」「by-id 路径」三套名字**——`findmnt --verify` 之所以能校验，是因为它按 `fstab` 里写的那套名字去解析。排「UUID 对不对」的问题时，**先确认你和对方说的是同一套标识符**，否则会在「明明 `blkid` 能看到」上绕圈。

顺带一个容易误判的现象：本机挂着一块 `sr0`（`Ubuntu-Server 24.04.5 LTS amd64` 安装 ISO，3.8 G）。**它是虚拟机的安装介质，不是数据盘**——`lsblk` 时看到多一块盘，先想「是不是安装镜像没弹出」。

**处置方向**（按优先级）：

1. 首选**从快照/备份恢复**，尤其是数据盘。
2. 需要修复时，在 Live 环境对**未挂载**的设备做只读检查（`fsck -n`），看清问题再决定。
3. 修复命令、挂载选项与只读故障的深水区在阶段 5《存储与文件系统》。

**验收**：机器能正常启动，关键挂载都在，业务数据可读。

## 5. `command not found`

> [!tip] 第一反应不要是「权限不够」
> 权限不足报的是 `Permission denied`；`command not found` 只说明「这个命令没被执行到」。

```bash
command -v <cmd>; echo $PATH             # 验证：命令是否存在、PATH 是否含 sbin
dpkg -S "$(command -v <cmd>)"            # 验证（Debian 系）：命令属于哪个包
rpm -qf "$(command -v <cmd>)"            # 验证（RHEL 系）：同上
```

实测输出（本实验机，`ss` 与 `ls` 两个样本）：

```text
command -v ss
/usr/bin/ss
echo $PATH
/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin:/usr/games:/usr/local/games:/snap/bin

dpkg -S "$(readlink -f "$(command -v ls)")"
coreutils: /usr/bin/ls

rpm -qf /usr/bin/ls
bash: line 1: rpm: command not found
```

四个分支：没装 → 按家族装；PATH 里没有 → 用绝对路径或 `sudo`；家族不同 → 换成当家族的等价命令；同名不同包 → 先查包名再装。详见子笔记 03。

> [!info] 最后一行本身就是「家族差异」的现场
> 在 Ubuntu 上敲 `rpm -qf` 得到的是 `rpm: command not found`——**不是「这个包不存在」，而是「这台机器没有 rpm 这个工具」**。这正是子笔记 03 的第一条纪律：跨家族抄命令前先 `command -v`。另外注意 `dpkg -S` 要传**解析后的真实路径**（`readlink -f`）：本机 `ls` 在 `/usr/bin/ls`，但很多命令在 `/bin` → `/usr/bin` 的符号链接链上，直接传 `$(command -v x)` 有时会因路径写法不同而查不到。

## 6. `error while loading shared libraries`

> [!tip] 第一反应不要是「重装这个软件」
> 先确认是**库不存在**还是**库存在但找不到**——后者重装一百次也没用。

```bash
ldd <程序> | grep 'not found'            # 验证：缺的是哪个 SONAME
readelf -d <程序> | grep -E 'NEEDED|RUNPATH'   # 验证：依赖清单与硬编码路径
ldconfig -p | grep <库名>                # 验证：缓存里有没有它
LD_DEBUG=libs <程序> 2>&1 | grep 'trying file' | head
                                         # 验证：链接器实际试了哪些目录
```

持久修复：`printf '%s\n' <库所在目录> > /etc/ld.so.conf.d/<名字>.conf` → `ldconfig` → 复验 `ldd`。临时验证可用 `LD_LIBRARY_PATH`，但不要作为生产修复。详见子笔记 08。

**本机实测（完整闭环，见子笔记 08 第 4 节）**：`ldd ./app` 报 `libhello.so => not found`、`ldconfig -p | grep -c libhello` 为 `0`、直接运行退出码 **127**；`LD_LIBRARY_PATH=/tmp/lab-lib ./app` 恢复正常；写 `/etc/ld.so.conf.d/lab01-test.conf` + `ldconfig` 后 `ldd` 显示 `libhello.so => /tmp/lab-lib/libhello.so (0x00007d8c25913000)`；**删除 conf 并再次 `ldconfig` 后回到 `not found`——持久方案与回滚都在本机验证过**。

## 7. 快照回滚之后，现象对不上

> [!tip] 第一反应不要是「回滚失败了」
> 回滚磁盘 ≠ 回到过去。先检查四样不在快照里的东西。

```bash
timedatectl; chronyc sources -v          # 验证：时间是否跳回、有没有对上上游
hostnamectl; cat /etc/machine-id         # 验证：机器身份是否变化或重复
systemctl --failed                       # 验证：回滚后有没有失败单元
journalctl -b -1 | tail -50              # 验证：回滚前那一次启动的结尾发生了什么
```

实测输出（本实验机，只读）：

                 RTC time: Sat 2026-09-19 08:09:19

> [!warning] 两条本机特有的注意点
> - **`chronyc` 本机没有**：`System clock synchronized: no` 与 `NTP service: active` 并存说明用的是 `systemd-timesyncd`（没有 `chrony` 客户端）。**改时间/校时的入口要先 `command -v chronyc` 确认**——本机上应该用 `timedatectl timesync-status`，不是 `chronyc sources`。
> - **`machine-id` 是克隆场景的坑点**：本机 `bd821ce75df94970ad5b6d63b6a8f812`（`hostnamectl` 与 `/etc/machine-id` 一致）。**从这台机器克隆实验机时，必须重置它**，否则两台机器的日志、授权与监控会混在一起——这属于「回滚快照对不上现象」的成因之一。

四样东西：时间与外部时钟、外部依赖的状态、机器身份与密钥、快照之后产生的数据。详见子笔记 07 第 5 节。

## 8. panic 之后取现场

> [!tip] 第一反应不要是「再重启一次看看」
> 现场已经在上一次启动里了；第二次重启只会让它更远。

```bash
journalctl -b -1 | tail -50              # 验证：上一次启动结尾的 panic 记录
ls -lh /var/crash 2>/dev/null            # 验证：配了 kdump 才有 vmcore
cat /proc/sys/kernel/panic; cat /proc/sys/kernel/sysrq
                                         # 验证：panic 后的行为与 SysRq 位掩码
```

实测输出（本实验机，只读）：

```text
journalctl -b -1 -n 2 --no-pager
No journal boot entry found from the specified boot offset (-1).

ls -lh /var/crash
total 0

cat /proc/sys/kernel/panic
0
cat /proc/sys/kernel/sysrq
176
```

如果配了 kdump，`/var/crash/<时间戳>/` 里会有 `vmcore` 与 `vmcore-dmesg.txt`；没有 kdump 时，只能靠带外串口日志。崩溃取证的深水区在阶段 2《启动流程与内核》。

**这段现场说明本机现在根本做不了这一步**（三条独立证据）：

- `/var/crash` **存在但是空的**（`total 0`），且 `systemctl is-active kdump` 实测 `inactive`——**没有配置 kdump，panic 后不会有 `vmcore`**。
- `kernel.panic` = **`0`**：panic 之后内核**不会自动重启**，会停在崩溃界面等带外处置——**这意味着一旦触发 panic，本实验机就只能靠 VMware 控制台/快照恢复**，而这正是我们不做这类演练的原因。
- `kernel.sysrq` = **`176`**：这个位掩码**不含** `8`（debugging dumps）与 `64`（signalling），所以 `echo c > /proc/sysrq-trigger` 在当前配置下**本来也不生效**——要做这类演练，先得改 sysctl（一次变更）再把机器准备好（另一项前提）。

> [!warning] 本节未实测
> 本实验环境不做 panic 演练：需要快照回滚 + 控制台，且本机 `kdump inactive`（拿不到 `vmcore`）。**「panic 之后怎么取证」这条链路在本机是断的**，只保留了上面三条只读事实。

## 10. 一页速查表

| 现象 | 第一步 | 关键判据 | 去哪一节 |
| --- | --- | --- | --- |
| SSH 不通，控制台能进 | `ip -br addr`、`ip route` | 网卡 UP？路由在？`sshd` 监听？**本机网络由 `systemd-networkd` 管、服务名是 `ssh` 不是 `sshd`** | 本手册 1 |
| 重启后紧急模式 | `systemctl --failed` | 哪个挂载单元失败；**改 `fstab` 前先 `findmnt --verify`** | 本手册 2 |
| 登录/`su` 失败 | `pwck` | `passwd` 是否被改坏；**判据是退出码 0 + `no changes`，不是「有没有输出」** | 本手册 3 |
| 系统起不来 | `lsblk`、`blkid` | 设备在不在、UUID 对不对；**注意 LVM 设备有三套标识符** | 本手册 4 |
| `command not found` | `command -v` | 没装/PATH/家族/包名；**`rpm -qf` 在 Ubuntu 上就是 command not found** | 本手册 5 |
| 库找不到 | `ldd` | `not found` 的 SONAME；**持久修复后必须复验 `ldd`** | 本手册 6 |
| 回滚后对不上 | `timedatectl`、`cat /etc/machine-id` | 时间、身份、依赖状态；**本机没有 `chronyc`，用 `timedatectl timesync-status`** | 本手册 7 |
| panic 之后 | `journalctl -b -1` | 有没有 `vmcore`；**本机 `kdump inactive`、`/var/crash` 空、`kernel.panic=0`，链路是断的** | 本手册 8 |

## 11. 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 一上来就重启 | 重启会毁掉现场；难复现的问题再也等不到 |
| 没确认控制台就开始改网络/`fstab` | 改坏后 SSH 进不去，只能重装 |
| 对有数据的盘直接 `fsck -y` | 自动修复可能删目录项、丢数据；先只读检查 |
| 用 `vi` 改 `/etc/passwd` | 没有加锁与校验；用 `vipw`，改完 `pwck` |
| 用 `LD_LIBRARY_PATH` 当生产修复 | 只影响当前进程树；应写 `ld.so.conf.d` + `ldconfig` |
| 改了配置不 `ldconfig` | 缓存没刷新，链接器仍看不到新路径 |
| 回滚后不校时、不核对身份 | 时间跳回会让日志与证书出错；克隆场景 `machine-id` 重复（本机 `bd821ce75df94970ad5b6d63b6a8f812`，克隆前必须重置） |
| 照抄「`nmcli con up` 修网络」到 Ubuntu Server | 本机 `NetworkManager.service` 不存在，网络由 `systemd-networkd` + netplan 管；`systemctl status` 会直接告诉你 |
| 把 `ss -lntp` 里 22 端口的两行当成两个 sshd | 一行是 `sshd`、一行是 `systemd`（socket activation 持有 fd），属正常形态 |
| 以为 `pwck` 有输出就是 `passwd` 坏了 | 告警（如 `directory '/run/ircd' does not exist`）是系统账号的正常形态；判据是退出码 `0` + `pwck: no changes` |
| 把 `lsblk` 里多出来的一块盘当成数据盘 | 本机那块 `sr0`（3.8 G，`Ubuntu-Server 24.04.5 LTS amd64`）是安装 ISO，不是数据盘 |
| 在 Ubuntu 上敲 `rpm -qf` 找包 | 得到的是 `rpm: command not found`——是「工具不存在」，不是「包不存在」；用 `dpkg -S`，且传 `readlink -f` 解析后的真实路径 |
| 处置完不写记录 | 下次遇到同样现象重新摸索一遍；S8 的交付物为零 |

## 12. 决策练习

> **场景**：周五 17:30，你在一台生产机上改防火墙规则，加完规则后 SSH 断线，业务探活也开始报警。控制台可用。
>
> A. 从快照回滚。
> B. 先用控制台登录、确认规则确实是把 22 与业务端口拒了，然后加临时放行规则恢复访问，再按变更记录改回持久配置并复验。
> C. 让同事重启这台机器。

**为什么选 B**：先恢复访问是止损，临时放行是最小改动；恢复后仍要按变更流程把持久配置改对，并用 `nft list ruleset` 与业务探活双重复验。这同时练了 S7（风险判断）与 S8（沉淀）。

**为什么 A 不对**：回滚是兜底手段，不是第一选择。它会丢掉现场，也可能把当天其他正常变更一起回退。

**为什么 C 不对**：重启不影响防火墙规则（规则是持久的），业务不会恢复；而且重启会把现场清掉。

## 13. 要点自测

> [!question]- 处置的第一问是什么？
> - 不是「怎么修」，而是「**现在还能不能取到现场**」——能取就先取，再决定止损顺序。
> - 证据包括：同时刻取证包、变更记录时间线、上一次启动日志。
> - 没确认回滚路径前，不做重装、`fsck -y`、恢复出厂这类不可逆操作。
> - **第一反应不要是什么**：不要用「先重启看看」代替判断。

> [!question]- 四类「把自己关在门外」的现象，各自的入口是什么？
> - SSH 不通 → 控制台里查网络。
> - `fstab` 写坏 → 控制台 + `emergency.target`。
> - `passwd` 写坏 → rescue/单用户里 `vipw` + `pwck`。
> - 系统起不来/文件系统坏 → Live 环境或云主机挂载恢复。
> - **第一反应不要是什么**：不要用「重装系统」作为任何一条的默认答案。

> [!question]- 为什么每一步都要有验收动作？
> - 「命令执行了」与「问题解决了」是两件事：规则可能没生效、挂载可能只是没报错、服务可能启动了但没就绪。
> - 验收要落到可观察的判据：`ldd` 无 `not found`、`mount -a` 无报错、`systemctl --failed` 为空、业务探活通过。
> - 验收还要有观察窗口：重启后 5 分钟正常，不代表 30 分钟后不会复发。
> - **第一反应不要是什么**：不要用「看起来正常了」当验收结论。
