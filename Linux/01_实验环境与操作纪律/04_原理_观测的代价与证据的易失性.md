# 观测的代价与证据的易失性

## 1. 为什么"先重启一下试试"是一个决策，而不是一个动作

机器变慢、服务异常、连接超时，最省事的应对是重启。重启之后现象消失，于是它被当成解决方案。但这里有一笔隐形的交易：**重启是唯一一个能一次性清掉大部分现场的动作**，而相当一部分故障的现象只会出现一次，或者要等几天才复现。

于是有一句值得记住的话：**重启能解决相当一部分问题，但会毁掉全部现场。** 因此问题不是"不能重启"，而是"重启是一个要付代价的止损决策"——代价是证据。止损是必要的，但它必须发生在取证之后，除非影响面已经不允许你再等。

这条判断背后是一个机制问题：**证据存在哪里，能活多久。** 下面把它拆开。

## 2. 证据按介质分层，寿命由位置决定

| 层 | 包含什么 | 重启之后 | 谁在保存它 |
| --- | --- | --- | --- |
| CPU 寄存器与缓存 | 它保存崩溃瞬间正在执行什么 | 它消失 | 只有 core / `vmcore` 这类崩溃时抓取的转储会保存它 |
| 内存 | 它保存进程状态与 `wchan`、连接与队列、文件句柄、锁、内核计数器 | 它全部消失 | 没有人保存它，除非主动落盘 |
| 内存文件系统（`/tmp`、`/dev/shm`） | 它保存临时文件、socket、锁文件、进程间共享数据 | 它消失 | 没有任何东西保存它 |
| 内核日志缓冲 | 它保存 `dmesg` 里的环形缓冲 | 它被清空 | 只有落到持久日志（journald / 远端 syslog）的那部分会被保存 |
| 本地磁盘 | 它保存持久化日志与本机采集数据 | 它被保留 | 本机采集器（如 sysstat）保存它，但受保留期限制 |
| 机器之外 | 它保存监控指标、集中日志、工单与变更记录 | 它被保留 | 远端系统保存它，而且这不依赖这台机器健康 |

结论是**取证的顺序由这张表决定**：最容易失的证据要先取，最耐久的证据可以后取。反面则是排障中最常见的顺序错误——先重启，然后才发现想看的连接、队列、进程状态全都没了。

三个推论：

- **"再复现一次"不是总能做到。** 偶发的资源竞争、只在特定时序出现的抖动、与外部系统交互才触发的错误，都可能长时间不再出现。因此能不能复现，与"当时有没有取到证据"是两件独立的事。
- **日志只是证据的一小部分。** 它是最耐久的一层，因此在故障现场往往只剩它——这也是为什么"日志里什么都没有"经常发生：不是没出事，而是出事的过程没被写进磁盘。
- **有些证据只在内存里。** 一个进程卡在哪里（`wchan`）、一个连接排在哪条队列、一个锁被谁持有，这些量在进程退出或重启后没有任何地方能再查到。

## 3. 观测的代价分三档

观测手段不是同一类东西，代价也不在一个量级上。按机制可以分成三档：

**第一档是读内核已经维护的计数器。** `/proc`、`/sys` 里的大部分文件是内核维护的计数或状态的**视图**——内核本来就在统计，因此读它只是格式化并复制出来。这一档的代价与**读取频率**成正比，而与事件频率几乎无关。`vmstat`、`free`、`ss -s` 这类工具属于这一档。

**第二档是定时采样。** `sar`、`iostat`、`pidstat` 做的事情是"每隔 N 秒读一次计数器，两次相减再除以间隔"。它仍然是第一档的机制，因此代价低且固定；但**能看到什么由采样间隔决定**：两次采样之间出现又消失的尖峰，会被平均掉或完全看不见。这解释了一个常见困惑——历史数据里一切正常，可用户说那几分钟确实卡过，因为采样间隔就是这时的解释上限。

**第三档是在事件路径上插入动作。** 追踪类手段会在被观测对象的执行路径上加东西：

- 系统调用跟踪（`strace` 基于 `ptrace`）让被跟踪进程每进一次系统调用就要停下、把控制权交给跟踪者再继续，进程整体变慢，事件越频繁越明显；
- 采样型剖析（`perf`）定期打断 CPU 记录现场，频率决定了精度也决定了开销；
- 抓包（`tcpdump`）在内核抓包点复制数据包到用户态，**缓冲不够时会丢包**——此时"丢包统计"反映的是采集器的问题，不是网络的问题；
- 内核内追踪（`bpftrace`、`perf` 的 tracepoint）在内核里就地判断，代价低得多，但仍然随**命中次数**线性增长。

判据可以简化为一句：**前两档是"读数字"，第三档是"在事件路径上加动作"。第三档的代价与事件频率成正比，所以动手前要先估事件频率，并给它设上限。**

## 4. 生产上做观测的三条边界

"观测有代价"落到操作上，是三条可执行的边界：

- **只读、低频、短时，可以在生产机上做。** 读计数器、看日志、看进程列表，风险接近于零；
- **高频追踪与全量抓包必须先设限。** 给出采样频率、过滤条件、输出总量与结束时间，尤其是"它要是把服务拖慢了，我怎么立刻停"；
- **对承载业务的关键进程要格外谨慎。** 在一个高负载进程上长时间挂追踪，可能把"偶发卡顿"变成"持续不可用"，这是观测把故障放大的典型路径。

同时要意识到采集器自身会成为新的故障源：日志写满磁盘、采集进程堆积输出、抓包文件占满内存文件系统，都是常见事故。**采集的产物要跟着保留策略走**，而不是无限增长；但反过来，排查期间不要清理证据。

## 5. 为什么要求"同时刻"

一次现场取证要在一小段时间窗口内把所有读数取完，而不是"先看内存，半小时后再看连接"。原因有两层：

**状态量会在两次采样之间改变。** 半小时前的连接队列和现在的已经不是一个系统状态，因此把它们放在一起分析，结论指向的可能是两个不同时刻的两件事。

**时间戳要对得上，才能拼出因果。** 变更记录说"10:30 改了参数"，监控说"10:42 延迟抬头"，日志说"10:41 开始报错"。这三条能拼成一条时间线的前提是它们用的是同一个时间基准。

时间基准本身还要求两个条件：**时钟是同步的**，以及**时间戳的来源可辨认**。由于时钟是否同步可以直接看状态（`timedatectl` 的 `System clock synchronized` 与 `NTP service` 两行），所以不必假设；跨机器对日志之前要先确认这一点，否则会得出"因果关系反了"的结论。此外，内核日志的时间戳来自实时钟，重启后 `uptime` 归零，因此跨启动比较需要按"第几次启动"来索引。

## 6. 历史数据只有两个来源，各有保留期

"昨天下午发生了什么"这个问题，答案不可能来自当前读数——当前读数只描述现在。历史数据只有两条来路：

**本机采集。** 典型实现是 sysstat：它由 systemd 计时器周期性触发采集（在金标准环境下，Ubuntu 24.04 的 `sysstat-collect.timer` 是每 10 分钟一次），数据落在 `/var/log/sysstat/`（Debian 系）或 `/var/log/sa/`（RHEL 系），保留天数由配置文件里的 `HISTORY=` 决定——金标准环境下该值是 7 天，配置文件在 Debian 系是 `/etc/sysstat/sysstat`。这三个量（**采集间隔、数据目录、保留天数**）都是现场取的，因为路径与默认值随发行版与包版本变化，所以要以 `man 5 sysstat` 和本机实际配置文件为准。

因此有两句判断要分开说：**装了 sysstat 不等于在采集**（采集可能是关闭的，或者计时器没启动）；**在采集不等于留得住**（保留期之外的已经被删了）。所以回答历史问题的第一步是确认这两件事，而不是直接 `sar`。

**外部监控。** 这一条来路把指标与日志推到远端，保留期由远端决定，并且**不依赖出事的机器是否健康**。这就是为什么排障规范要求取证包复制出机器、日志集中收集：本机采集在机器起不来时价值归零。

内核日志还有一层条件：跨启动查询（例如看上一次启动的日志）要求日志是**持久化**的。判断依据是持久目录是否存在、journald 是否被配置为持久存储（`man 5 journald.conf` 的 `Storage=`）。同时要注意**目录存在不等于有上一次启动**：刚装好的机器、刚清理过的机器、或者保留策略把旧数据删掉了，都会让"看上一次启动"这件事无解。

## 7. 机制在本名与字段上的边界

**环形缓冲是有大小的。** 内核日志缓冲是固定大小，因此写满后新消息会覆盖旧消息。故障瞬间的消息可能在你去取之前就被后续消息冲掉，尤其是那些会持续刷屏的错误。

**计数器要取差值，而且会随进程消失。** 累计计数只有两次读数相减才有意义；进程一旦退出，`/proc/<pid>` 下的所有视图就同时消失。容器里的情况更极端：容器退出后它的 cgroup 目录被回收，因此 `memory.current` 与 `memory.events` 这些文件事后再也读不到。

**容器与宿主是两套视图。** 同一个进程在容器里看到的 PID 和在宿主上看到的 PID 不同，因为 `/proc` 是命名空间内的视图，而且计数器归属也可能不同。因此跨这两层对数据之前，先确认自己在看哪一侧。

**采样间隔决定了能看到什么。** 用 10 分钟一次的数据回答"是不是有秒级抖动"，从方法上就不成立。因此要么换更细的采样，要么明确说出这是方法的限制。

**"重启后正常了"不是验证。** 它既没有解释原因，也没有留下证据，还把复现条件一起抹掉了。合格的验证是给出可观察的判据（服务能不能连、指标有没有回到基线），并说明观察时间窗口——"重启后 5 分钟正常"与"30 分钟后不复发"是两种强弱的结论。

## 常见误解

| 常见说法 | 事实 |
| --- | --- |
| 「重启之后好了，问题就解决了」 | 重启是止损，而它的代价是现场消失，因此它解释不了原因，还抹掉了复现条件 |
| 「日志里没有，说明没发生过」 | 日志只是最耐久的一层；大量证据只在内存里，而且内核日志缓冲是环形的 |
| 「装了 sysstat 就随时能查历史」 | 采集可能没开，数据也可能已过保留期，因此这两件事要分别确认 |
| 「`/var/log/journal` 存在就一定有上一次启动的日志」 | 还要看保留策略与实际记录，因为新装或刚清理过的机器可能只有当前这次启动 |
| 「采样数据正常，说明那段时间没问题」 | 采样间隔把两次采样之间的尖峰平均掉了，因此能看到什么由间隔决定 |
| 「抓包丢了包，说明网络在丢包」 | 这可能是抓包缓冲不够，而丢包统计反映的是采集器 |
| 「多挂几个观测工具，信息更全」 | 第三档观测会在事件路径上加动作，因此挂得越多，观测者效应越强 |
| 「容器里看到的 PID 和宿主一样」 | 命名空间内的 PID 视图不同，而且计数器归属也可能不同 |

## 要点自测

**问：为什么"重启"要作为一个决策来对待，而不是一个动作？**
答：因为重启会一次性清掉寄存器、内存、内存文件系统与内核日志缓冲这四层证据，而其中很多内容没有别的地方能再查到。能不能重启，取决于影响面允不允许你再等一轮取证。

**问：`strace`、`perf`、`tcpdump` 与 `vmstat`、`sar` 的代价差别来自哪里？**
答：机制不同。`vmstat`、`sar` 是读内核已经维护的计数器（第二档要乘上采样间隔带来的信息损失）；`strace` 通过 `ptrace` 让被跟踪进程在每次系统调用处停下交接控制权，`perf` 以采样中断打断 CPU，`tcpdump` 把包复制到用户态——这三者都在事件路径上加了动作，代价与事件频率成正比。

**问：为什么"同时刻取证"不是形式要求？**
答：两层原因：状态量在两次采样之间会改变，分开取的两组数据描述的可能是两个不同的系统状态；时间戳必须来自同一时间基准，跨机器比较前还要确认时钟已同步，否则时间线方向都会错。

**问：同事说"昨天下午变慢了，你 `sar` 一下"，你接手先确认哪三件事？**
答：本机是否在采集（采集器有没有在跑）、数据目录在哪、保留期是多久。装了 sysstat 不等于在采集，在采集不等于数据还在。三件事都不成立时，唯一的历史来源是外部监控。

**问：为什么日志是"最耐久的一层"，却经常什么也查不到？**
答：耐久的前提是它真的落到了持久存储。内核日志先进环形缓冲，只有被 journald 或远端 syslog 收走才落盘；缓冲会被后续消息覆盖，持久化与保留期又各有条件。

**第一反应不要做什么**：不要用重启代替排查；不要在生产关键进程上长时间挂高频追踪；不要在排查结束前清理证据。
