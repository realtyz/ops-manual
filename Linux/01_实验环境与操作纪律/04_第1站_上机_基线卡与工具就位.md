## 0. 30 秒速览

> [!abstract] 这一篇只要记住五句话
> - **上机第一分钟先取基线，不要先敲业务命令。**
>   怎么验证：`cat /etc/os-release`、`uname -r`、`systemctl --version | head -1`、`stat -fc %T /sys/fs/cgroup`、`nproc`、`grep MemTotal /proc/meminfo`、`df -hT /`、`timedatectl`。
> - **工具要按「现象 → 工具」装，不要按字母背。**
>   证据：负载高找 `top`/`mpstat`，IO 慢找 `iostat -x 1`/`pidstat -d`，连接堆积找 `ss -s`/`nstat`；先想现象，再想命令。
> - **一台「看起来能用」的 Ubuntu，排障工具箱默认几乎全是缺的。**
>   证据：实测本机缺 `sar`、`iostat`、`pidstat`、`htop`、`strace`、`tcpdump`、`perf`、`bpftrace`、`iftop`、`numactl`、`smartctl`、`iperf3`、`stress-ng` 共 13 个。
> - **`sysstat` 是「历史」的唯一来源。**
>   证据：`sar` 能回答「昨天 3 点发生了什么」，`top` 只能回答「现在」；但采样开关没打开时，`sar` 也只有当天数据。
> - **遇到没见过的参数，先查本机 man 页。**
>   证据：`fstab` 看 `man 5 fstab`、`nsswitch.conf` 看 `man 5 nsswitch.conf`；`--help` 只给参数速查，默认值、文件与环境变量在 man 页后几节。

## 1. 上机第一分钟：先固化成一份基线卡

完整四项基线与台账模板见子笔记 02，这里只强调顺序和产出：

```bash
date; hostname; uptime                       # 验证：时间基线、机器身份与当前负载
cat /etc/os-release | head -3                # 验证：发行版与版本
uname -r                                     # 验证：内核版本
systemctl --version | head -1                # 验证：systemd 版本
stat -fc %T /sys/fs/cgroup                   # 验证：cgroup 版本（cgroup2fs = v2）
nproc; grep MemTotal /proc/meminfo; df -hT / | tail -1
                                             # 验证：核数、内存总量、根文件系统
timedatectl | head -3                        # 验证：时间与时区（对齐时间线的前提）
systemd-detect-virt; ls /sys/firmware/efi    # 验证：虚拟化类型与启动模式
```

**产出**：一份基线卡。它是这一站唯一的交付物，也是后面所有「变没变慢」「默认值是不是这样」的判断基准。**没有基线卡的机器，不允许下「这台机器有问题」的结论。**

## 2. 诊断工具箱：按「现象 → 工具」装

工具不在多，而在「现象出现时你能想起哪一个」。先按现象归类，再按发行版装：

| 现象 | 首选工具 | 深挖/补充 | 包（RHEL 系 / Debian 系） |
| --- | --- | --- | --- |
| 负载高、CPU 打满 | `uptime`、`top`、`mpstat -P ALL`、`pidstat -u` | `perf top`、`/proc/pressure/cpu` | `sysstat` / `sysstat` |
| 内存水位、swap 抖动 | `free -h`、`vmstat 1`、`sar -r` | `/proc/pressure/memory`、`smaps_rollup` | `procps-ng`、`sysstat` / 同 |
| 磁盘满、inode 满 | `df -hT`、`df -i`、`du -xh --max-depth=1` | `lsof +L1`、`tune2fs -l` | `coreutils`、`lsof` / 同 |
| IO 慢、延迟高 | `iostat -x 1`、`pidstat -d` | `iotop -oPa`、`blktrace`/`bpftrace` | `sysstat`、`iotop` / 同 |
| 连接堆积、丢包 | `ss -s`、`ss -lntp`、`nstat -az` | `tcpdump -w`、`conntrack -S` | `iproute2`、`tcpdump`、`conntrack-tools` / 同 |
| 路由与二层 | `ip -br addr`、`ip route get`、`ip neigh` | `ethtool -S/-i/-g` | `iproute2`、`ethtool` / 同 |
| 进程卡死、杀不掉 | `ps -o pid,stat,wchan`、`strace -p` | `/proc/<pid>/stack`、`gdb` | `procps-ng`、`strace` / 同 |
| 句柄/文件事件耗尽 | `lsof -p`、`/proc/<pid>/limits` | `sysctl fs.file-max`、`inotify` 上限 | `lsof` / `lsof` |
| 内核与硬件报错 | `dmesg -T`、`journalctl -k` | `smartctl -a`、`nvme smart-log` | `util-linux`、`smartmontools`、`nvme-cli` / 同 |
| 命令/库跑不起来 | `ldd`、`readelf -d`、`ldconfig -p` | `LD_DEBUG=libs`、`strace -e trace=openat` | `glibc`、`binutils` / 同 |
| 性能基线 | `stress-ng`、`fio`、`iperf3` | `sar` 历史数据 | 各自单独打包 / 同 |

## 3. 按家族安装

```bash
dnf install -y sysstat iotop lsof strace tcpdump perf bpftrace numactl smartmontools iperf3 stress-ng
                                             # RHEL 系（RHEL/CentOS Stream/Rocky/Alma）
apt update && apt install -y sysstat iotop lsof strace tcpdump linux-tools-common linux-tools-$(uname -r) numactl smartmontools iperf3 stress-ng
                                             # Debian 系（Debian/Ubuntu）
zypper install -y sysstat iotop lsof strace tcpdump perf numactl smartmontools iperf3
                                             # SUSE 系
```

**别跨家族抄**：这三行各自只在自己的家族里成立；命令不存在时报的是 `command not found`，不是「装失败」。

## 4. 体检：一台刚装好的系统缺什么

```bash
for t in sar iostat pidstat vmstat top htop lsof strace tcpdump perf bpftrace iftop numactl smartctl iperf3 stress-ng openssl nc ss nstat ethtool ip python3; do
    p=$(command -v "$t" 2>/dev/null); [ -n "$p" ] && echo "OK       $t -> $p" || echo "MISSING  $t"
done                                     # 验证：一份「最小可用工具箱」的体检结果（缺的按第 2 节表格补装）
```

实测输出（本机 WSL2 Ubuntu 24.04.4 LTS，未做任何补装）：

```text
OK       vmstat -> /usr/bin/vmstat
OK       top -> /usr/bin/top
OK       lsof -> /usr/bin/lsof
MISSING  sar                 （来自 sysstat：不装就没有历史数据与 iostat/pidstat）
MISSING  iostat
MISSING  pidstat
MISSING  htop                （可选，但有比没有好读）
MISSING  strace
MISSING  tcpdump
MISSING  perf
MISSING  bpftrace
MISSING  iftop
MISSING  numactl
MISSING  smartctl
MISSING  iperf3
MISSING  stress-ng
OK       openssl -> /usr/bin/openssl
OK       nc -> /usr/bin/nc
OK       ss -> /usr/bin/ss
OK       nstat -> /usr/bin/nstat
OK       ethtool -> /usr/sbin/ethtool
OK       ip -> /usr/sbin/ip
OK       python3 -> /usr/bin/python3
```

**结论**：一台「看起来能用」的 Ubuntu 上，排障工具箱默认几乎全是缺的（本机缺 13 个）。阶段 2 之后用到的 `iostat`/`sar`/`tcpdump`/`perf` 都要先补装。

三个必须记住的边界：

- **`sysstat` 是「历史」的唯一来源**：先把 `/etc/sysstat/sysstat`（Debian 系）或 `/etc/sysconfig/sysstat`（RHEL 系）里的采样开关确认打开，否则 `sar` 只有当天数据。
- **`perf`/`bpftrace` 与内核版本强绑定**：Debian 系要装与 `uname -r` 匹配的 `linux-tools-*`，否则报 `perf not found for kernel ...`——WSL2 与自编译内核通常没有对应的包；RHEL 系上 `bpftrace` 在 RHEL 8 需要 EPEL、RHEL 9 才进官方仓库；容器里通常没权限调 BPF。
- **工具的输出字段本身也随版本变**：`iostat` 的 `aqu-sz` 在旧版本里叫 `avgqu-sz`，`ss` 的列在不同 iproute2 版本略有差异——记基线时把工具版本一起记（`sysstat -V`、`ss -V`）。

## 5. 第一手资料：`man` 与 `/usr/share/doc`

遇到没见过的参数或配置文件，**先查本机手册**，比搜索引擎快，而且版本一定对得上。`man` 的章节编号不是装饰，它告诉你这份文档在讲什么层面：

| 章节 | 内容 | 实测本机路径 |
| --- | --- | --- |
| `man 1` | 用户命令（`ls`、`systemctl`） | `/usr/share/man/man1/ls.1.gz` |
| `man 2` | 系统调用（`mount`、`open`） | `/usr/share/man/man2/mount.2.gz` |
| `man 3` | 库函数（`printf`、`malloc`） | `/usr/share/man/man3/printf.3.gz` |
| `man 5` | **配置文件格式**（`fstab`、`nsswitch.conf`、`proc`） | `/usr/share/man/man5/fstab.5.gz` |
| `man 7` | 概览与概念（`tcp`、`signal`、`cgroups`） | `/usr/share/man/man7/tcp.7.gz` |
| `man 8` | 管理命令（`ip-netns`、`xfs_repair`） | `/usr/share/man/man8/ip-netns.8.gz` |

```bash
man -w 5 fstab                       # 验证：这份 man 页在哪个文件（-w 只打印路径，不开分页器）
man -k passwd                        # 验证：按关键字搜索所有章节（等价 apropos，括号内是章节号）
man -a printf                        # 验证：同名页存在于多个章节时，按顺序看完所有章节
man 5 nsswitch.conf                  # 验证：查配置文件格式（这类问题先看第 5 章）
```

几条实践经验：

- **`--help` 与 man 页的分工**：`--help` 看参数速查，man 页看语义、默认值与「文件/环境变量/退出码」等小节——面试里能答出的细节基本都在 man 页的后几节。
- **`man` 找不到页不是 bug**：实测本机 `man -w 8 systemctl` 返回 `No manual entry for systemctl in section 8`，因为 `systemctl` 在**第 1 章**。同一个主题在不同发行版可能落在不同章节，先不指定章节查一次。
- **`/usr/share/doc/<包名>/` 里常有上游文档**：`README`、`NEWS`、`examples/`；配置文件里提到的「参见官方文档」通常就在这里。
- **man 页与发行版文档冲突时，以发行版文档 + 本机实测为准**：man 页来自软件上游，发行版会改默认值（`tuned`、`sysctl.d`、编译开关）。

## 6. 生产动作：产出一张基线卡与一份工具箱清单

> [!example]- 生产动作：固化本机基线卡（只读，生产机上也可以做）
> **做什么**：把第 1 节的命令输出存成一份带时间戳的文件，追加到工单或配置管理库。
>
> ```bash
> mkdir -p ~/baseline
> {
>   echo "== $(date -Is) =="
>   hostname; cat /etc/os-release | head -3; uname -r
>   systemctl --version | head -1; stat -fc %T /sys/fs/cgroup
>   nproc; grep MemTotal /proc/meminfo; df -hT /
>   timedatectl | head -3; systemd-detect-virt
>   sysstat -V 2>/dev/null | head -2; ss -V
> } > ~/baseline/$(hostname)-$(date +%F).txt
> ```
>
> **验收标准**：文件里十项都有值；`diff` 上一次的基线文件，能看到这次变的是哪些项。
>
> **风险**：无，全部只读。
>
> **耗时**：约 5 分钟。
>
> **回滚**：不需要回滚；文件只是记录。
>
> **要沉淀什么**：把这份文件放进配置管理库或台账，下一次变更/排障前先对比它。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 装完 `sysstat` 就以为有历史数据 | 采样开关没打开时 `sar` 只有当天数据；要改 `/etc/sysstat/sysstat` 或 `/etc/sysconfig/sysstat` |
| 用 `top` 回答「昨天三点发生了什么」 | `top` 只能看现在；历史要 `sar` 或外部监控 |
| 跨家族照抄安装命令 | `dnf`/`apt`/`zypper` 不通用；命令不存在不等于包装失败 |
| 在容器或 WSL2 上死磕 `perf`/`bpftrace` | 内核由平台提供，通常没有匹配的 `linux-tools-*`，BPF 也常被限制 |
| 只记工具名不记版本 | `iostat`/`ss` 的字段名随版本变，换机器后对不上 |
| `man` 报找不到就以为没文档 | 同一主题可能在别的章节，或装在 `/usr/share/doc/<pkg>/` |
| 把 `--help` 当完整文档 | 它只给参数速查；默认值、文件、退出码在 man 页后几节 |
| 体检发现缺工具就立刻全部补装 | 先按当前阶段需要的补；不在生产机上为「以后可能用到」而扩大变更面 |

## 决策练习

> **场景**：你接手一台生产服务器，同事说它「昨天下午开始变慢」。你登录后发现机器上只有 `top`/`free`/`df`，没有 `sar`/`iostat`/`pidstat`。
>
> A. 立刻在生产机上补装 `sysstat`，然后等它采一段时间再分析。
> B. 先取当前的同时刻基线（负载、内存、磁盘、连接、内核日志），同时检查是否有外部监控能回溯昨天下午的数据。
> C. 重启机器，看问题是否复现。

**为什么选 B**：昨天下午的现象今天不一定还在，能回溯它的只有外部监控或已有的历史数据；先取当前基线是为了「现在和昨天下午是否有可比性」这个判断。补装 `sysstat` 只能从此刻开始攒数据，救不了昨天。

**为什么 A 不对**：补装本身没错，但它回答不了「昨天下午」——`sysstat` 采集是从开启那一刻开始的。

**为什么 C 不对**：重启会清掉现场，而且大概率让现象更难复现；这是子笔记 06 要练的反面教材。

## 要点自测

> [!question]- 一份基线卡至少包含哪些项？为什么？
> - 建议十项：发行版、内核、启动参数、systemd、cgroup、资源、根文件系统、时间、虚拟化与启动模式、工具版本。
> - 前五项决定「这条命令/这个默认值成不成立」，后五项决定「这台机器能不能扛住这次演练/这次变更」。
> - 基线卡要带时间戳并留档，下一次对比才有意义。
> - **第一反应不要是什么**：不要只记 `uname -r` 一项就下单机结论。

> [!question]- 为什么按「现象 → 工具」装，而不是按工具名背？
> - 排障时先出现的是现象（负载高、IO 慢、连接堆积），不是工具名；先归类现象才能想起首选命令。
> - 同一个现象有首选与深挖两层：`iostat` 看设备层，`pidstat -d`/`iotop` 定位到进程。
> - 装工具时也按这套分类补，避免「装了一堆，真出事时想不起来用哪个」。
> - **第一反应不要是什么**：不要拿一份「命令大全」当学习清单。

> [!question]- 为什么 `sar` 能回答「昨天 3 点」，`top` 不能？
> - `sar` 读的是 sysstat 采集的**历史数据**（存在 `/var/log/sysstat` 或 `/var/log/sa`），前提是采集开关打开且服务在运行。
> - `top` 只反映调用它那一刻的情况，退出即消失，不保留任何历史。
> - 排查「间歇性变慢」时，历史数据几乎是唯一入口；外部监控（Prometheus 等）是另一条路。
> - **第一反应不要是什么**：不要以为 `top` 看不到异常就说明没问题。
