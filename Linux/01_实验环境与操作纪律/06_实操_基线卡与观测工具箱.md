# 基线卡与观测工具箱

## 1. 一个问题，一把工具

| 你想知道 | 用什么 | 关键字段或文件 |
| --- | --- | --- |
| 这台机器是什么发行版 | `cat /etc/os-release` | `ID`、`ID_LIKE`、`VERSION_ID`、`VERSION_CODENAME` |
| 内核是什么、是不是平台定制 | `uname -r` | 版本号 + 变体后缀 |
| 服务与资源控制的接口形态 | `systemctl --version` | 版本号 |
| cgroup 是第几版 | `stat -fc %T /sys/fs/cgroup` | `cgroup2fs` 或 `tmpfs` |
| 机器身份与形态 | `hostnamectl` | `Machine ID`、`Virtualization`、`Chassis` |
| 是虚拟机还是物理机、是容器吗 | `systemd-detect-virt`、`systemd-detect-virt -c` | 输出名或 `none` |
| 启动模式是 UEFI 还是 legacy | `ls /sys/firmware/efi` | 有输出为 UEFI，无输出为 legacy |
| 内核启动参数是什么 | `cat /proc/cmdline` | 完整命令行 |
| 有多少 CPU、内存、磁盘 | `nproc`、`grep MemTotal /proc/meminfo`、`df -hT`、`df -i` | 核数、`MemTotal`、`Use%`、`IUse%` |
| 挂载与选项 | `findmnt -o TARGET,SOURCE,FSTYPE,OPTIONS` | `OPTIONS` 里的 `ro`/`rw` |
| 时间对不对 | `timedatectl` | `Time zone`、`System clock synchronized`、`NTP service`、`RTC time` |
| 当前有没有异常单元 | `systemctl --failed` | 单元名与失败时间 |
| 一条命令为什么跑不起来 | `command -v`、`type`、`echo $PATH` | 有没有路径、是别名还是函数 |
| 那个命令属于哪个包 | `dpkg -S`（Debian 系）/ `rpm -qf`（RHEL 系） | 包名 |
| 程序为什么缺库 | `readelf -d`、`ldd`、`ldconfig -p`、`LD_DEBUG=libs` | `NEEDED`、`not found`、缓存条目 |
| 某主题的文档在哪一节 | `man -w <节号> <名字>`、`man -k <关键词>` | 手册文件路径、命中列表 |
| 上一次启动发生了什么 | `journalctl --list-boots`、`journalctl -b -1` | 启动索引与条目 |
| 昨天下午发生了什么 | `sar`、外部监控 | `/var/log/sysstat/sa<DD>` 或 `/var/log/sa/sa<DD>` |
| 管道里到底哪一步失败了 | `$?` 与 `${PIPESTATUS[0]}` | 命令状态 |

表里的"用什么"分两类：**命令**（`uname`、`df`、`systemctl`、`journalctl`……文档在 `man 1` 或 `man 8`）与**内核接口文件**（`/proc/...`、`/sys/...`，直接 `cat` 就能读，不需要任何工具）。分不清时看 man 的章节号：`man 1` 是用户命令、`man 2` 是系统调用、`man 3` 是库函数、`man 5` 是文件格式、`man 7` 是概览与约定、`man 8` 是管理命令。

**工具箱按"现象"装，不按字母背。** 工具不在多，而在于现象出现时能想起哪一个；再按"首选 → 深挖"分两层，第一层看整机，第二层定位到进程或对象。装包与体检的做法见第 3 节。

## 2. 怎么读这些数字

下面每条给五样东西：**是什么、单位、判据、和谁一起看、看到它转向哪一步**。输出样例只用来展示**格式**，数值不代表你的机器。

### 2.1 版本基线四项

```bash
cat /etc/os-release | head -5     # 验证：发行版标识与版本；各家族的字段一致
uname -r                          # 验证：内核版本与变体后缀
systemctl --version | head -1      # 验证：服务与资源控制接口的版本
stat -fc %T /sys/fs/cgroup         # 验证：cgroup2fs 表示 v2，tmpfs 表示 v1
```

```text
ID=ubuntu
ID_LIKE=debian
VERSION_ID="24.04"
VERSION_CODENAME=noble
6.8.0-139-generic
systemd 255 (255.4-1ubuntu8.17)
cgroup2fs
```

- **`ID` 与 `ID_LIKE`**：前者是发行版身份，后者是"家族相似"的提示。判据是**它们都只是标识，不构成路径与包名的推理依据**；`ID_LIKE=debian` 不代表 Ubuntu 的默认值等于 Debian 的默认值。
- **`VERSION_ID`**：大版本号，用来对齐官方发布说明与生命周期页。**异常与否只能和官方页面对照**，没有通用阈值。
- **`uname -r` 的变体后缀**：`-generic` 是发行版官方内核的通用变体，`-aws`、`-azure`、`-microsoft-standard-WSL2` 一类是平台定制内核。看到平台后缀就不要套用发行版文档（机制见《发行版的构成与差异来源》）。
- **版本号中间那一段**（样例中的 `-139`）是发行版自己的构建与 ABI 序号。它变化意味着内核包换了，`/lib/modules/<版本>` 下的模块目录随之变化；自己编译过外部模块的机器要跟着重新编译。
- **systemd 版本**：决定单元文件的属性、资源控制与日志的可用能力。看到某个属性不被识别，先回来看这个值，再决定是"写错了"还是"这个版本没有"。
- **cgroup 版本**：`cgroup2fs` = v2，`tmpfs` = v1。**这条不能靠发行版名推**，只能现场取；v1 与 v2 的限制文件路径、字段名与单位都不同。
- **和谁一起看**：这四项永远作为一组出现。跨机器比较任何结论之前，先对齐它们。

### 2.2 机器形态与退路

```bash
hostnamectl                        # 验证：静态主机名、机器标识、虚拟化与硬件信息
systemd-detect-virt                # 验证：虚拟化类型；-c 检查容器
ls /sys/firmware/efi               # 验证：有输出即 UEFI 启动，无输出即 legacy BIOS
```

```text
 Static hostname: linux-lab
      Machine ID: bd821ce75df94970ad5b6d63b6a8f812
  Virtualization: vmware
Operating System: Ubuntu 24.04.5 LTS
          Kernel: Linux 6.8.0-139-generic
   Architecture: x86-64
vmware
```

- **`Machine ID`**：安装或首次启动时生成的机器身份，克隆虚拟机会连带复制。**两台机器 ID 相同意味着日志、授权与监控里它们是同一台**（判据与处置见《快照与状态一致性》与判例篇）。
- **`Virtualization` 与 `systemd-detect-virt -c`**：前者是宿主平台类型（`vmware`、`kvm`、`microsoft`……），后者判断自己是不是跑在容器里（`none` 表示不是）。**这个区别决定了哪些开关能碰**：容器共享宿主内核，改内核模块、启动参数、`fstab` 通常没有意义。
- **`ls /sys/firmware/efi` 有输出 = UEFI，无输出 = legacy BIOS**。判据很干脆，但它决定的是**照哪一套教程修启动**：legacy 下与 EFI 引导项、Secure Boot 相关的操作根本不成立。
- **退路两项（快照与控制台）不在命令里，只能查平台**：本地虚拟化通常两项都完整；云主机要先确认控制台已开通；容器没有独立控制台。
- **转向哪一步**：`Virtualization` 是容器或平台定制内核时，后续所有涉及内核侧参数的排查都要先降低结论强度。

### 2.3 资源、挂载与时间

```bash
nproc; grep MemTotal /proc/meminfo; df -hT /; df -i /
findmnt -o TARGET,SOURCE,FSTYPE,OPTIONS | head
timedatectl
```

```text
4
MemTotal:        8083464 kB
Filesystem                        Type  Size  Used Avail Use% Mounted on
/dev/mapper/ubuntu--vg-ubuntu--lv ext4   47G  8.5G   37G  20% /
Filesystem     Inodes IUsed IFree IUse% Mounted on
/dev/mapper/ubuntu--vg-ubuntu--lv  3.1M  120K  3.0M    4% /
TARGET SOURCE                            FSTYPE OPTIONS
/      /dev/mapper/ubuntu--vg-ubuntu--lv ext4   rw,relatime
               Local time: Sun 2026-09-20 14:00:39 UTC
           Universal time: Sun 2026-09-20 14:00:39 UTC
                 RTC time: Sun 2026-09-20 14:00:39
                Time zone: Etc/UTC (UTC, +0000)
System clock synchronized: no
              NTP service: active
```

- **`nproc`**：可用于调度的 CPU 数（可能小于物理核数，受限制影响）。它是对照量——负载、进程数、线程数都要除以它才有意义。
- **`MemTotal`**：单位 kB，且**不等于内存条容量**（固件、显卡、内核预留、显式大页预留都不计入）。它只用来定"这台机器有多少可用物理内存"这个量级，容量构成的细节在内存章。
- **`df -hT` 的 `Use%`**：**和谁一起看**——`Use%` 高时还要看是哪个挂载点、文件系统类型与预留比例（ext4 默认给 root 留一部分空间，所以普通用户可能在 `Use%` 未到 100% 时就写不进去，具体比例用 `tune2fs -l` 现场查）。**转向哪一步**：`/` 写不进去与某个数据盘写不进去，处置路径完全不同，见存储章。
- **`df -i` 的 `IUse%`**：inode 用尽也会报空间不足，而 `df -h` 看起来还有余量。**异常与否只能与自己的基线比**；小文件、会话文件、缓存目录多的机器 inode 消耗快得多。
- **`findmnt` 的 `OPTIONS`**：**判断"文件系统是不是只读"看这里，而不是看报错文本**。`rw` 与 `ro` 是两种完全不同的处境：`ro` 往往意味着内核因为文件系统错误主动把它降成只读了。**转向哪一步**：看到 `ro` 先查内核日志里的文件系统错误，再决定处置。
- **`Time zone`**：决定日志的显示时区。**与同事对时间之前先看这一行**，否则会出现"你说的 10 点是我这里的 18 点"。
- **`System clock synchronized` 与 `NTP service`**：前者是"已经与时间源对齐"，后者是"同步服务在运行"。**两者组合起来读**：`active` + `no` 表示服务在跑但从未成功同步（时间源不可达、被防火墙挡住，或刚启动还没完成），此时机器上的时间**不可信**，跨机器比对日志的结论都要打问号；`active` + `yes` 才是可以拿来对齐的状态。**转向哪一步**：时间不可信时，先解决同步，再谈时间线。
- **`RTC time`**：硬件时钟的读数。它与 `Universal time` 的关系由"RTC 是否使用本地时间"的配置决定；跨时区迁移虚拟机、或快照回滚之后对时间，都要看这一行。

### 2.4 命令与库：为什么跑不起来

```bash
command -v sshd; type systemctl; echo $PATH
dpkg -S "$(readlink -f "$(command -v ls)")"     # 验证：查某个真实文件属于哪个包
readelf -d /usr/bin/ls | grep -E 'NEEDED|RPATH|RUNPATH'
ldd /path/to/app | grep -i 'not found'
```

```text
/usr/sbin/sshd
systemctl is /usr/bin/systemctl
0x0000000000000001 (NEEDED)   Shared library: [libselinux.so.1]
0x0000000000000001 (NEEDED)   Shared library: [libc.so.6]
```

- **`command -v` 有输出 = 这个 shell 能找到它**；没有输出才叫"找不到"。**异常判据是分层的**：没装、装了但不在 `PATH`、名字不同、属于不同的包。`type` 会进一步告诉你它是别名、函数、内建命令还是外部文件——**别名与函数是"命令行为与文档不一致"的常见原因**。
- **`PATH` 里有没有管理命令目录**：`/usr/sbin`、`/sbin` 常不在普通用户的默认 `PATH` 里，于是"root 能敲、我不能敲"的现象出现。**判据是 `echo $PATH`，不是"权限不够"**：权限不足报的是 `Permission denied`，与"找不到"是两种错误。
- **`dpkg -S` / `rpm -qf` 要传真实路径**：命令可能是软链接，直接传软链接路径有的实现查不到，先 `readlink -f` 取真实文件。**在 Debian 系上敲 `rpm -qf` 得到的是"工具不存在"，不是"包不存在"**——这两句话含义完全不同。
- **`readelf -d` 的 `NEEDED`**：程序声明需要的库名（SONAME），不是路径。**没有 `RPATH`/`RUNPATH` 行是常态**，表示它完全依赖搜索路径与缓存。
- **`ldd` 的 `not found`**：某一行出现 `not found` 就是这一条依赖没解析成功，后面不用再猜。**和谁一起看**：`ldconfig -p` 看缓存里有没有、`LD_DEBUG=libs` 看它按顺序试过哪些目录。**边界**：`ldd` 在某些情况下会执行程序，**对不可信二进制改用 `readelf -d`**（机制见《程序启动与依赖解析》）。

### 2.5 历史数据：能回溯多久

```bash
journalctl --list-boots | head          # 验证：有几次可查的启动
ls /var/log/sysstat/ 2>/dev/null || ls /var/log/sa/ 2>/dev/null
systemctl list-timers --all | grep -i sysstat
```

- **`--list-boots` 的索引**：`0` 是当前启动，`-1` 是上一次。**只有列表里有的才查得到**；列表里只有一行说明这台机器（或这份日志）只有当前这次启动，此时"看上一次启动"这件事无解，不要反复尝试。
- **采集是否在跑**：看计时器是否在列表里、`systemctl is-active` 是否 active。**判据是两件事分开确认**：装了 sysstat ≠ 在采集；在采集 ≠ 数据还在。
- **保留期**：由配置文件的 `HISTORY=` 决定（金标准环境 Ubuntu 24.04 下该值为 7 天，配置文件 `/etc/sysstat/sysstat`；RHEL 系在 `/etc/sysconfig/sysstat`，以 `man 5 sysstat` 与本机实际文件为准）。**和谁一起看**：数据目录里的文件名（`sa<DD>`）与保留期对照，就能算出最早能回溯到哪一天。
- **转向哪一步**：本机没有历史数据时，唯一来源是外部监控；这条判断要在回答"昨天下午"之前先做，否则会白跑一趟。

### 2.6 退出码与管道

```bash
grep -c ERROR /var/log/app.log; echo "grep_status=$?"
some_cmd | tail -3; echo "pipeline_status=$?"; echo "first_cmd_status=${PIPESTATUS[0]}"
```

- **`$?` 是"最后一条命令"的状态。** 在管道里，它是**管道最后一段**（样例中的 `tail`）的状态，而不是第一段的。要拿到第一段的状态必须用 `${PIPESTATUS[0]}`（bash）。
- **为什么这条要写进基线卡**：它是"看着成功、其实失败"的一类典型误判，而且会导致错误结论——例如据此得出"某个命令的退出码不可信"，而其实只是取错了对象。
- **转向哪一步**：任何"命令返回成功"的判断，都要先确认自己取的是哪个进程的状态。

## 3. 采样纪律与基线卡

基线卡的目的是让"正常"变成一个可比对的对象。四条纪律：

1. **同一口径**：这次看 `MemAvailable`，下次还看它，不要中途换成完全空闲；
2. **带时间戳**：读数与时间一起存，事后才能与告警、变更记录对齐；
3. **至少两次**：判断抖动按秒，判断趋势按小时或按天；
4. **留原始输出**：整份 `/proc/meminfo`、`df`、`findmnt` 都存下来，而不是只抄一个数字。

**基线卡最少十项**：发行版、内核（含变体后缀）、启动参数、systemd 版本、cgroup 版本、资源（核数/内存/磁盘与 inode）、根文件系统类型与挂载选项、时间（时区与同步状态）、虚拟化类型与启动模式、工具箱版本。

**工具箱体检**：按"现象 → 工具"的顺序确认每个工具在不在，并把版本号一起记下——**字段名与工具版本绑定**，同一个列的含义会随版本变化。装包命令按家族分三种入口（RPM 系 `dnf`、DEB 系 `apt`、SUSE 系 `zypper`），性能类工具（`perf`、`bpftrace`）在各家族还要额外的内核侧包，装不上时先看内核依赖而不是反复换工具。

**基线卡要在改动后回填。** 过期的基线比没有基线更危险：它会给出一个错误的"正常值"。

## 常见故障与排查方向

下面七个场景按值班会遇到的样子构造（机器规格、时间线与数值都是示意）。每个场景给三样东西：**背景**（你要面对的具体处境）、**排查顺序**（先看什么、看到什么转向哪）、**一份合格的回答长什么样**（结论、依据、边界、动作）。字段怎么读在第 2 节。

### 场景一：改完网络配置之后，SSH 不通了，控制台能进

**背景**：一台 4 核 8 GiB 的 Ubuntu 24.04 虚拟机（VMware），只对你这台跳板机开放 22 端口，其余端口被安全组挡住。你按同事给的操作改了网络配置准备换一个静态地址，执行完发现 SSH 断了，重启后依然连不上。平台控制台可以进，业务方说这个服务 30 分钟后要开始接流量。

**排查顺序**

1. **先定性，不改动**：在控制台登录，`date; hostname; uptime` 确认自己在这台机器上；`systemctl --failed` 看有没有失败单元。
2. **看链路四层**：地址有没有起来（`ip -br addr`，看接口是否 `UP`、地址是否是预期的）→ 路由在不在（`ip route`，看默认路由）→ 服务在不在听（`ss -lntp` 看 22 端口）→ 防火墙放不放（`nft list ruleset` 看底层规则）。**四层依次排除，不跳步**。
3. **看是谁在管这块网卡**：NetworkManager 与 systemd-networkd 可能同时存在，改的配置文件可能根本没被读取。判据是哪个单元在管这个接口，而不是文件内容对不对。
4. **看改动的原文**：把改前的备份与当前文件对照（这是变更前三件套之一）。
5. **恢复**：改回原配置并让它生效，验收标准是**从另一台机器能 ssh 进来**，而不是"本机看起来正常"。

**一份合格的回答**

- 结论一句话：断在四层里的哪一层（地址、路由、监听、策略），以及原因是不是本次改动。
- 依据：`ip -br addr`、`ip route`、`ss -lntp`、`nft list ruleset` 的输出，加上改动前后的文件差异。
- 边界：如果四层都正常而仍然连不上，方向要转向"中间链路与安全策略"（跳板机、云安全组、上游 ACL），此时不要再在本机改配置。
- 动作：先恢复连通性（影响面优先），再补变更记录；明确说出这次**不会**做的两件事（重装、在没确认控制台的情况下继续改网络）。

### 场景二：重启后停在 emergency mode，业务起不来

**背景**：一台 8 核 16 GiB 的 Ubuntu 服务器，有三块数据盘要挂载。同事在 `/etc/fstab` 里加了一行新的数据盘，设备名写成了一个还不存在的 UUID。重启后系统停在紧急模式提示符下，只有控制台可用。

**排查顺序**

1. **看失败单元与日志**：`systemctl --failed`，再 `journalctl -xb` 看内核与启动日志的尾部，找那个挂载失败的目标。
2. **读挂载表现状**：`findmnt -o TARGET,SOURCE,FSTYPE,OPTIONS`，对照 `/etc/fstab` 的每一行，确认哪一条没有挂上。
3. **处理根文件系统**：紧急模式下 `/` 常常是只读，先按提示或按需要重挂为可写（`mount -o remount,rw /`）。
4. **改回配置**：把出问题的行改回正确值或先注释掉，**不要直接删除**（删了会丢失原始信息），然后用 `mount -a` 验证；有条件的话再用 `findmnt --verify` 做一次解析层面的检查。
5. **回到正常目标**：切回默认目标，业务单元随之启动，验收看业务与失败单元列表。

**一份合格的回答**

- 结论一句话：启动停在紧急模式是**挂载失败**导致的，失败对象是哪一条挂载、为什么会失败。
- 依据：`systemctl --failed` 的单元名、`journalctl -xb` 里对应的报错、`findmnt` 与 `fstab` 的对照。
- 边界：如果失败的是根文件系统本身，或改回后仍然失败，就要考虑快照回滚或在救援环境中处理——这属于另一条处置路径。可选的挂载点应当用"失败不影响启动"的写法，这是配置层面的预防。
- 动作：先恢复启动（业务优先），再补齐变更记录；把"动手前确认控制台可用"作为下次的前置条件。

### 场景三：服务起不来，日志里只有一行 `error while loading shared libraries`

**背景**：一个自研服务部署在 `/opt/app` 下，重启后 `systemctl status` 显示主进程退出，`journalctl -u` 里只有一行 `error while loading shared libraries: libcustom.so.2: cannot open shared object file`。开发说"本地测过没问题"。

**排查顺序**

1. **先纠正理解**：这条消息由动态链接器打印，程序一行都没执行；所以问题一定在"库能不能被找到"，与应用逻辑无关。
2. **确认依赖与位置**：`readelf -d /opt/app/bin/app | grep -E 'NEEDED|RUNPATH'` 看依赖的库名（不是路径）；`find /opt /usr/lib -name 'libcustom*'` 看文件到底在不在（不要从 `/` 开始扫）。
3. **区分"没装"与"装了没找到"**：在的话，看它所在目录是否在搜索路径里（`/etc/ld.so.conf` 与 `ld.so.conf.d/` 的内容）；不在的话，是安装步骤漏了或包不对。
4. **复核缓存**：`ldconfig -p | grep libcustom` 看缓存里有没有它；若目录刚加进配置，需要重建缓存。
5. **持久修复**：把库装到标准位置，或将目录写进 `ld.so.conf.d/` 并重建缓存，然后重启服务并做业务侧探活。**临时用环境变量验证可以，但不能作为交付**（作用域、可复现性、setuid 场景都不成立）。

**一份合格的回答**

- 结论一句话：这是依赖解析失败，具体是"没装""装错位置"还是"搜索路径与缓存没刷新"。
- 依据：`NEEDED` 里的库名、文件是否存在的查找结果、`ld.so.conf.d` 的内容、`ldconfig -p` 的命中情况。
- 边界：架构不匹配（32 位/64 位）与 C 库实现不匹配（glibc/musl）会报同一条错误，只看报错文本区分不了；此时要看二进制与库各自的架构。
- 动作：给出持久修复方案与回滚方式（删掉新增的配置文件、重建缓存、复验依赖解析），并把"用环境变量临时绕过"明确标注为临时手段。

### 场景四：同事给的一条命令，在这台机器上不存在

**背景**：一台 Ubuntu 生产服务器上，同事让你执行一条 RHEL 系的放行端口命令。执行后得到 `command not found`。他坚持"我昨天刚用过"。

**排查顺序**

1. **先分类错误**：`command not found` 与 `Permission denied` 是两种错误。前者是"这个 shell 找不到这个名字"，与权限无关——不要用 `sudo` 反复重试。
2. **看这台机器选的是哪个前端**：`command -v firewall-cmd`、`command -v ufw`、`command -v nft`，确认本机有哪一个；`cat /etc/os-release` 确认家族。
3. **换成本机入口**：用本机存在的前端配置，并确认它是"持久生效"的那种用法（有些前端默认只改运行时规则）。
4. **双层复核**：底层规则与监听状态都要看——底层规则表能证明"策略放行了"，监听列表能证明"服务真的在听"。两者都满足，才算"端口通了"。
5. **留下记录**：把"这台机器上的正确入口"写进 Runbook 片段，避免下次再撞。

**一份合格的回答**

- 结论一句话：命令不存在是**入口选错了**，不是权限问题，也不是包没装（要先用 `command -v` 确认）。
- 依据：`/etc/os-release` 的家族标识、本机存在的前端命令、底层规则与监听状态的输出。
- 边界：如果本机两个前端都没有，说明这台机器用的是更底层的工具或由外部设备承担策略；此时不要装一个前端来"对齐同事的命令"，那会引入一套没人负责的策略层。
- 动作：用本机入口配置，双重复核，并把正确入口沉淀下来。

### 场景五：登录、`su`、`sudo` 全都失败

**背景**：一台服务器在合并账号之后，`root` 之外的所有用户都无法登录，`su` 报错，`sudo` 也不可用。上一次操作是用编辑器直接修改了 `/etc/passwd`。

**排查顺序**

1. **确认是不是解析问题**：`getent passwd <用户名>` 看账号库能不能解析出这条记录，`pwck` 做结构与格式自检。
2. **看损坏形态**：常见有三类——某一行字段数不对、某个字段（家目录或 shell）写错、整行丢失。**三类的处置路径不同**，判断依据是 `pwck` 指出的行号与 `getent` 的结果。
3. **改回去**：用账号库的专用编辑入口改（它会加锁并做基本校验），而不是普通编辑器；改完再用自检工具复验。
4. **验证**：用一个真实账号登录、`su -` 与 `sudo` 各走一遍。**验收标准是能登录**，不是"文件看起来对了"。
5. **兜底**：文件已经乱到专用工具也进不去时，只能从救援环境或挂载根分区外部修改，或者回滚快照。

**一份合格的回答**

- 结论一句话：这是账号库损坏导致的认证失败，损坏的形态是哪一类、影响哪些账号。
- 依据：`getent` 的解析结果、`pwck` 的行号与报错、修改前后的文件差异。
- 边界：`su`/`sudo` 失败也可能是别的原因（密码库单独损坏、PAM 配置改动、账号被锁定），因此在动手改文件之前，先确认问题在"账号库"而不是"认证策略"。
- 动作：用专用工具改回，验证到"能登录"为止，并把"不要用普通编辑器改账号库"写进纪律。

### 场景六：快照回滚之后，"现象对不上"

**背景**：一台用于演练的虚拟机改坏了挂载表，你从快照回滚。机器起来了，可是监控上这台机器"没有数据"，有个同事说证书报错，还有一个上游服务说收到了重复的请求。

**排查顺序**

1. **先确认回滚本身成功**：系统能进、失败单元为空、关键挂载在位。回滚失败与"回滚成功但外部状态不一致"是两件事。
2. **核对四样不在快照里的东西**：时间（与上游时间源是否对齐）、机器身份（`machine-id` 与主机密钥是否与外部世界当前认为的一致）、外部依赖（上游是否已经处理过快照之后的请求）、快照之后写入的数据（是否丢失）。
3. **按项处置**：校时、必要时重置机器身份并通知相关方、与上游核对状态、把丢失数据的范围说清楚。
4. **记录**：把这次回滚的代价写进演练记录，作为下一次判断"回滚是不是够用"的依据。

**一份合格的回答**

- 结论一句话：回滚成功，不一致来自"机器之外的世界继续走了"——具体是哪几样（时间、身份、外部依赖、丢失的数据）。
- 依据：时间同步状态、机器标识、与上游/监控的核对结果。
- 边界：如果失败单元非空或关键挂载缺失，说明问题在回滚点本身，要走另一条排查路径。
- 动作：逐项归位并通知相关方；把结论写进记录，明确"快照保护什么、不保护什么"。

### 场景七：同事说"昨天下午开始变慢"，机器上没装采集工具

**背景**：一台 8 核 16 GiB 的服务器，跑一个数据库与一个应用。同事报"昨天下午三点左右开始变慢"，希望你给出结论。这台机器只装了最基本的工具，没有 `sar`/`iostat`/`pidstat`。

**排查顺序**

1. **先回答"有没有历史数据"，再动手**：查本机采集是否在跑、数据目录与保留期（2.5 节）。没有历史数据就明确说出来——**不要现场补装采集工具并声称能回溯过去**，它只能从这一刻开始记录。
2. **同时刻取当前基线**：按"时间与身份 → CPU 与负载 → 内存与压力 → IO 与容量 → 连接 → 进程与内核日志"取一组读数并带时间戳落盘。这组数据的价值是"现在是什么样"，不是"昨天是什么样"。
3. **找外部来源**：外部监控的指标、集中日志、上游服务记录、发布与变更记录。昨天下午发生了什么，往往在变更记录里而不是在机器上。
4. **给出可验证的假设**：如果有历史数据，用它缩小窗口；如果没有，把结论降级为"当前状态 + 需要补哪类观测"，并说明为什么。

**一份合格的回答**

- 结论一句话：现在能不能给出结论——**不能**，因为缺的是历史数据这一层，并说明现在取到的是什么、缺的是什么。
- 依据：采集状态与保留期的核查结果、当前同时刻读数、外部监控与变更记录的可用性。
- 边界：如果外部监控显示昨天下午确实有异常，方向要转向"当时有什么变更、有什么指标同时抬头"；如果外部监控也正常，"变慢"的判断本身需要重定义（是哪个指标、谁感知到的）。
- 动作：先把采集打开并记录开始时间，为下一次故障留下数据；同时按第 3 步追外部来源，而不是在机器上盲猜。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 看到 `command not found` 就用 `sudo` 重试 | 权限不足报的是 `Permission denied`；两个错误含义不同 |
| 用发行版名猜 cgroup 版本 | 只能现场取：`stat -fc %T /sys/fs/cgroup` |
| 把 `MemTotal` 当成内存条容量 | 固件、显卡、内核预留都不计入 |
| 只看 `df -h` 不看 `df -i` | inode 用尽也会报空间不足，而容量看起来还有余量 |
| 用报错文本判断文件系统是否只读 | 看 `findmnt` 的 `OPTIONS` 列 |
| 看到 `System clock synchronized: no` 仍然拿时间戳对齐 | 时间不可信时所有时间线结论都要打问号 |
| 拿 `dpkg -S` / `rpm -qf` 直接查软链接路径 | 先取真实路径；在错误的家族上还会得到"工具不存在" |
| 对不可信二进制用 `ldd` | 某些实现会执行程序；改用 `readelf -d` |
| 用 `LD_LIBRARY_PATH` 当生产修复 | 只影响当前进程树、不在配置里、setuid 下被忽略 |
| 装了 sysstat 就以为有历史数据 | 采集可能没开，数据可能已过保留期；要分别确认 |
| `journalctl -b -1` 查不到就反复试 | 先看 `--list-boots`；只有一次启动时这个查询无解 |
| 管道后用 `$?` 判断第一段命令 | 拿到的是最后一段的状态；用 `${PIPESTATUS[0]}` |
| 看到 `systemctl --failed` 非空就认为机器坏了 | 先看单元名与失败时间，可能是别的变更或并行实验留下的 |
| 用本机实测值当通用结论 | 输出与内核、发行版、硬件、容器环境强相关；写进结论要带环境 |

## 要点自测

**问：给你一台陌生的机器，5 分钟内你怎么判断它"有没有问题"？**
答：先取一组同时刻基线：身份与时间（`hostname`、`date`、`timedatectl`）→ 版本四项 → 资源与挂载（核数、内存、`df -hT`、`df -i`、`findmnt` 的选项）→ 失败单元与内核日志尾部。判断"有没有问题"要**看趋势而不是瞬时值**，并且必须与基线对照——没有基线的机器上，"异常"这个判断本身不成立。

**问：`System clock synchronized: no` 而 `NTP service: active`，怎么读？**
答：服务在运行，但从未成功同步过。可能是时间源不可达、被策略挡住，或者刚启动还没完成。此时机器上的时间不可信，跨机器比对日志之前先解决同步。

**问：`command not found` 的四类原因是什么？**
答：没装；装了但不在当前 `PATH`（管理命令常在 `/usr/sbin`、`/sbin`）；名字不同（发行版差异，或入口换了，如 `ifconfig`/`netstat` 被 `ip`/`ss` 取代）；同名不同包或包名不同。判断顺序是先 `command -v` 与 `echo $PATH`，再查所属包，最后才考虑换命令。

**问：程序报缺库，你怎么在四步之内定位并持久修好？**
答：① 用 `readelf -d` 确认缺的是哪个库名；② 在有限范围（`/opt`、`/usr/lib`、`/lib`）内查文件在不在，区分"没装"与"装了没找到"；③ 检查目录是否在搜索路径配置里、缓存是否需要重建；④ 做持久修复（装包或写 `ld.so.conf.d` + 重建缓存），重启服务并做业务侧探活。临时用环境变量只作验证。

**问：为什么"今天没有历史数据"这件事必须当面说清，而不是先装个工具再说？**
答：采集只能从开始运行的那一刻记录，不能回溯。现场补装工具之后给出的任何"昨天"的结论都是伪造的；正确做法是说明缺什么、现在取到什么、外部还有哪些来源可用，并把采集打开留给下一次。

**问：`df -h` 显示还有空间，写入却报空间不足，可能是什么？**
答：两类最常见的：inode 用尽（要看 `df -i`），以及文件系统被降为只读（要看 `findmnt` 的 `OPTIONS`）。此外还有配额与预留空间的问题；判据都落在具体的字段上，不能只看容量那一列。

**第一反应不要做什么**：不要在看到报错时先试 `sudo`；不要在没确认采集状态前就下"昨天发生了什么"的结论；不要把现场补装工具当成补救历史数据的办法。
