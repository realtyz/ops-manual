# 第 2 站：变更前——备份、回滚与时间窗

## 0. 30 秒速览

> [!abstract] 这一篇只要记住四句话
> - **变更前三件套：带时间戳的备份、写下来的回滚命令、确认过的时间窗。**
>   怎么验证：三件里少任何一件，就不算「准备好」；回滚命令要写在变更单或聊天窗口里，而不是「不行再想」。
> - **判断回滚是否准备好，只看一条：现在让你回滚，你能照着念出来吗？**
>   证据：如果要临时想路径、想设备名、想服务名，就说明还没准备好。
> - **改完立刻验证，不要把验证留给下一个事故。**
>   证据：`mount -a`、`findmnt --verify`、`sshd -t`、`nginx -t` 这类语法自检能在重启前拦掉大部分低级错误。
> - **一次只改一件事。**
>   证据：同时改三处之后，你既不知道是哪一处起了作用，也不知道出了问题该回滚哪一处。

## 1. 变更前三件事

任何一台机器、任何一次手工改动都适用：

1. **备份原文件，且带时间戳。**
   `cp -a /etc/fstab /etc/fstab.bak.$(date +%F-%H%M)`。用 `-a` 保住权限与属主；时间戳让你事后能说清「改的是哪一版」。
2. **确认回滚方式。**
   回滚命令要**先写下来**（写进变更单或聊天窗口），而不是「不行再改回来」。判断标准很简单：如果回滚需要你临时想，那就说明没准备好。
3. **确认时间窗与影响面。**
   这条改动会影响谁？要不要通知？有没有正在跑的业务？**生产上的手工改动都应排窗口**，哪怕只是加一条防火墙规则。

> [!important] 为什么把「备份」放在第一位
> 绝大多数「改坏了」的故障，最后都是靠一份带时间戳的备份救回来的。备份的价值不在于它多完整，而在于**它在你动手之前就存在**——动手之后再补备份，通常已经晚了。

## 2. 回滚命令怎么写

好回滚命令有三个特征：**能照着念、有验收、有边界**。

| 特征 | 反面例子 | 正面例子 |
| --- | --- | --- |
| 能照着念 | 「把参数改回去」 | `cp -a /etc/fstab.bak.2026-09-19-1030 /etc/fstab && mount -a` |
| 有验收 | 「然后检查一下」 | `findmnt --verify; systemctl daemon-reload` |
| 有边界 | 「不行就重启」 | 「仅在 `mount -a` 报错时执行；重启前先确认控制台可用」 |

回滚命令还要写清**回滚的触发条件**：什么现象出现时执行回滚，而不是继续排查。没有触发条件的回滚方案，在事故现场通常想不起来用。

## 3. 变更记录六要素

一份能被别人看懂、也能被未来的自己看懂的变更记录，至少包含六项：

| # | 要素 | 写什么 | 例子 |
| --- | --- | --- | --- |
| 1 | 目标 | 这次要达成什么，怎么衡量 | 把 `vm.swappiness` 从 60 调到 10，观察 `si/so` 是否下降 |
| 2 | 范围 | 哪台机器、哪个文件、哪个服务 | 仅 `web-03`，`/etc/sysctl.d/99-swap.conf` |
| 3 | 备份 | 备份文件路径与时间戳 | `/etc/sysctl.d/99-swap.conf.bak.2026-09-19-1030` |
| 4 | 回滚 | 可照着念的回滚命令与触发条件 | 删除该文件后 `sysctl --system`；触发条件：业务延迟上升 > 20% |
| 5 | 验证 | 改完用什么命令、达到什么标准算成功 | `sysctl vm.swappiness` 返回 10；`si/so` 连续 10 分钟为 0 |
| 6 | 时间窗 | 什么时候做、影响谁、谁批准 | 09-19 10:30~11:00，低峰期，已通知值班 |

> [!tip] 面试与复盘的通用答法
> 被问「你怎么做一次变更」，按 **目标 → 范围 → 备份 → 回滚 → 验证 → 窗口** 六步答，比罗列命令更像做过事的人。复盘时也是这六项：哪一项缺了，故障就从哪里进来。

## 4. 四条配套纪律

1. **能用配置管理就别手工。** Ansible/云初始化脚本的一次性改动比「记得改过什么」可靠；手工改动必须落到文档里。
2. **改动后立刻验证。** `mount -a`、`ss -lnt`、`systemctl status`、业务侧探活——**只做「改完不验证」这一步，等于把验证留给了下一个事故。**
3. **一次只改一件事。** 和性能调参一样，同时改三处之后你不知道是哪一处起的作用，也不知道该回滚哪一处。
4. **给实验机和生产机不同的 prompt/配色。** `PS1` 里带主机名与环境前缀，能显著降低「在生产机上练手」的概率——这是最便宜的一道保险。

## 5. 生产动作：写一份带回滚的变更记录

> [!example]- 生产动作：把一次变更写成可复盘的记录（零风险，先写文档再动手）
> **做什么**：按六要素模板，在动手前把记录写完；改完补上实际结果。
>
> ```bash
> date +%F-%H%M                                # 验证：拿到备份用的时间戳
> cp -a /etc/<目标文件> /etc/<目标文件>.bak.$(date +%F-%H%M)
> ls -l /etc/<目标文件>.bak.*                 # 验证：备份存在、权限与属主与原文件一致
> ```
>
> **验收标准**：六要素都填满；回滚命令在纸面上走通一遍（路径、服务名、设备名都核对过）；时间窗已确认。
>
> **风险**：写记录本身零风险；**真正动手时按变更的风险等级选机器**——T2 只进实验机，生产变更要走正式流程。
>
> **耗时**：约 10 分钟。
>
> **回滚**：如果只是写记录、还没动手，删除临时文件即可；动了手就按记录里的回滚命令执行。
>
> **要沉淀什么**：这份记录就是 S5 的交付物；积累几次之后，你会发现自己真正缺的是「验证标准」和「触发条件」，而不是备份。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 「先改，不行再改回来」 | 没写下来的回滚方案在事故现场通常想不起来，或想错了版本 |
| 备份不带时间戳 | 多次改动后分不清哪一份是干净的，回滚可能回到更早的版本 |
| 用 `>` 重定向做备份 | `cp /etc/fstab > fstab.bak` 是错的（写的是命令输出）；要 `cp -a` 保留权限属主 |
| 改完直接重启验证 | 重启会同时毁掉现场并放大故障；先 `mount -a`/`sshd -t` 这类语法自检 |
| 同一窗口改三处 | 出问题时无法判断是哪一处、该回滚哪一处 |
| 没有触发条件的回滚方案 | 事故中会犹豫「现在该回滚还是继续查」，错过止损窗口 |
| 在生产机上「顺手」试一下 | 没有时间窗、没有通知、没有回滚，就是一次未经管理的变更 |
| 实验机和生产机 prompt 一样 | 视觉上没有区分，容易在错误的机器上练手 |

## 决策练习

> **场景**：你要在一台生产 Web 服务器上调整内核网络参数，以缓解偶发的连接超时。当前是业务高峰期，参数在 man 页里的默认值你也不确定。
>
> A. 现在是高峰期，先 `sysctl -w` 改了观察一下，好了再写文档。
> B. 先在实验机上确认参数效果与副作用，写好六要素变更记录，约一个低峰窗口再改，改前备份、改后按验证标准观察，并准备好回滚。
> C. 直接写进 `/etc/sysctl.d/` 并 `sysctl --system`，反正重启才生效。

**为什么选 B**：变更的对象是生产机，所以「窗口 + 备份 + 回滚 + 验证」一个都不能少；先在实验机确认效果，是因为连默认值都不确定——这正是子笔记 02 强调「先取基线」的场景。

**为什么 A 不对**：`sysctl -w` 只写当前内核，重启即失，而且不产生审计痕迹；在高风险窗口做临时改动，既没有记录也没有回滚方案。

**为什么 C 不对**：写进 `sysctl.d` 只是持久化方式，不等于「重启才生效」——`sysctl --system` 会**立刻**应用，等于在高峰期直接改了生产参数。

## 要点自测

> [!question]- 变更前三件套是什么？怎么判断「已经准备好回滚了」？
> - 三件套是**带时间戳的备份、写下来的回滚命令、确认过的时间窗**。
> - 判断标准：现在让你回滚，你能不能照着念出完整命令（含路径、服务名、参数）？要临时想就说明没准备好。
> - 回滚方案还应有**触发条件**（什么现象出现时执行）和**验收动作**（回滚后怎么确认恢复了）。
> - **第一反应不要是什么**：不要用「不行再改回来」代替回滚方案。

> [!question]- 为什么「改完立刻验证」比「改完重启」更重要？
> - 重启会同时做两件事：清掉现场、放大故障；能进多用户就说明幸运，进不去就变成一次真正的故障。
> - 语法/配置自检（`mount -a`、`findmnt --verify`、`sshd -t`、`nginx -t`）能在重启前暴露大部分低级错误。
> - 验证还要落到业务侧：端口是否监听、探活是否通过、关键指标是否回到基线。
> - **第一反应不要是什么**：不要把「重启后正常了」当成验证通过。

> [!question]- 变更记录六要素是哪六项？为什么复盘时也按它看？
> - 目标、范围、备份、回滚、验证、时间窗。
> - 六项对应变更的六个失败点：目标不清会改错东西，范围不清会改错机器，备份/回滚缺失会救不回来，验证不清会误判成功，窗口不当会影响业务。
> - 复盘时用同一套结构，就能定位「故障是从哪一项的缺口进来的」，改进项也能落到具体动作。
> - **第一反应不要是什么**：不要把变更记录写成「我改了什么」的流水账。
