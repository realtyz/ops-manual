## 0. 30 秒速览

> [!abstract] 这一篇只要记住四句话
> - **报错说的是「程序被加载了，但它依赖的某个 `.so` 找不到」。**
>   证据：完整形态是 `./app: error while loading shared libraries: libhello.so: cannot open shared object file: No such file or directory`；排查对象是库，不是程序本身。
> - **依赖由 ELF 的 `NEEDED` 段决定，搜索顺序由 `ld.so` 决定。**
>   怎么验证：`readelf -d ./app | grep NEEDED` 看依赖清单，`ldd ./app` 看实际解析到哪，`LD_DEBUG=libs` 看它逐个目录试。
> - **标准处理是四步：缺哪个 → 装没装 → 路径对不对 → `ldconfig` 后复验。**
>   证据：实测自建 `libhello.so` 后 `ldd ./app` 报 `libhello.so => not found`、`ldconfig -p | grep -c libhello` 输出 **0**、直接运行退出码 **127**；`LD_LIBRARY_PATH=/tmp/lab-lib ./app` 恢复正常。
> - **`LD_LIBRARY_PATH` 只影响当前进程树，生产上不要用它当修复。**
>   证据：它不进 `ld.so.cache`，换个终端或重启后就失效，会让「为什么这台机器能跑」变成没人记得住的隐性条件。

## 1. 这条报错在说什么

完整形态：

```text
./app: error while loading shared libraries: libhello.so: cannot open shared object file: No such file or directory
```

它的意思是：**程序本身被内核加载了，但动态链接器（`ld.so`）找不到它依赖的某个 `.so`**。所以排查的不是「程序坏了」，而是「库在哪、链接器有没有看到它」。

程序依赖哪些库，由编译时写进 ELF 的 `NEEDED` 段决定；运行时由 `ld.so` 按固定顺序搜索（`ld.so(8)`）：

1. ELF 里的 `DT_RPATH`（老式硬编码路径，已被 `RUNPATH` 取代）
2. 环境变量 **`LD_LIBRARY_PATH`**
3. ELF 里的 `DT_RUNPATH`
4. **`/etc/ld.so.cache`**（由 `/etc/ld.so.conf` 与 `/etc/ld.so.conf.d/*.conf` 生成）
5. 默认目录：`/lib`、`/usr/lib` 及各自的 `x86_64-linux-gnu` 子目录等

```bash
readelf -d ./app | grep NEEDED     # 验证：这个二进制依赖哪些库（SONAME 列表）
ldd ./app                          # 验证：依赖实际解析到了哪些路径；not found 就是缺的
ldconfig -p | grep libhello        # 验证：链接器缓存里有没有这个库（本地自建的库通常没有）
LD_DEBUG=libs ./app 2>&1 | head -20
                                   # 验证：打印链接器的搜索过程（会看到它逐个目录 trying file=...）
```

## 2. 标准处理顺序（四步，不要跳步）

| 步骤 | 目的 | 命令 |
| --- | --- | --- |
| ① 确认缺哪个库 | 拿到缺失的 SONAME | `ldd <程序>` / `readelf -d <程序>` |
| ② 确认装没装、装在哪 | 区分「没装」与「装了但找不到」 | `rpm -qf <路径>`、`dpkg -S <路径>`、`find /usr /lib /opt -name '库名*' -print`（**慎用 `find /`**，优先用 `ldconfig -p`） |
| ③ 修路径或补装 | 装了没找到 → 补搜索路径；没装 → 装包 | 装包：`dnf install <pkg>` / `apt install <pkg>`；补路径：写 `/etc/ld.so.conf.d/xx.conf` 或临时 `LD_LIBRARY_PATH=` |
| ④ 刷新缓存并复验 | 让 `ld.so` 看见新路径 | `ldconfig`（需 root）→ 再跑一次 `ldd` 与程序本身 |

```bash
ldd ./app | grep 'not found'                        # 验证：缺失的 SONAME
readelf -d ./app | grep -E 'NEEDED|RUNPATH|RPATH'   # 验证：依赖列表与硬编码搜索路径
ldconfig -p | grep <库名>                           # 验证：链接器缓存里有没有它
LD_DEBUG=libs ./app 2>&1 | grep -i 'trying file' | head
                                                     # 验证：链接器到底试了哪些目录
ldconfig                                             # 验证：刷新缓存（需 root），之后复验 ldd
```

## 3. 五条必须记住的边界

- **`LD_LIBRARY_PATH` 只影响当前进程树**：它不进 `ld.so.cache`，换个终端就没了。**生产上不要用它当修复手段**——那会让「为什么这台机器能跑」变成一个没人记得住的隐性条件；正确做法是补 `/etc/ld.so.conf.d/` 并 `ldconfig`。
- **`ldconfig` 需要 root，并且会重建整个缓存**：改完配置要执行它；执行后 `ldconfig -p | grep <库>` 应该能看到路径。
- **`ldd` 对不可信二进制有风险**：老版本 `ldd` 会通过设置 `LD_TRACE_LOADED_OBJECTS` 让程序自己「跑一遍」，**对来源不明的二进制不要直接 `ldd`**（新版已是安全的 ELF 解析，但习惯要保留）。更安全的是 `readelf -d`。
- **`not found` 也可能是「架构或 C 库不对」**：32/64 位混装、或把 glibc 编译的二进制丢进 Alpine（musl）容器里，都会报找不到库——后者的典型现象是连 `/lib64/ld-linux-x86-64.so.2` 都没有。
- **`glibc-hwcaps` 子目录会被优先搜索**：实测 `LD_DEBUG=libs` 输出里，链接器先试了 `/tmp/lab-lib/glibc-hwcaps/x86-64-v3/libhello.so`、`.../x86-64-v2/...` 再试 `/tmp/lab-lib/libhello.so`。这是 glibc 2.33+ 的硬件能力分派机制——**看到陌生子目录别慌，它不是恶意代码**。**本机 glibc 是 2.39**，`LD_DEBUG` 里出现的最高档位是 `x86-64-v3`；注意**这些 `glibc-hwcaps` 子目录在本机并不存在**（实测 `ls /usr/lib/x86_64-linux-gnu/glibc-hwcaps/` 报 `No such file or directory`）——链接器只是**按规则先探测这些路径**，探测不到再回落到下一档。所以「看到了 `glibc-hwcaps` 路径」只能说明链接器在按规则搜索，**不能说明系统里装了对应优化版本的库**。

## 4. 实测：亲手制造并修好这个报错

```bash
mkdir -p /tmp/lab-lib && cd /tmp/lab-lib
printf '%s\n' '#include <stdio.h>' 'void hello_from_lib(void) { printf("hello from lab lib\n"); }' > hello.c
printf '%s\n' '#include <stdio.h>' 'void hello_from_lib(void);' 'int main(void) { hello_from_lib(); puts("main ok"); return 0; }' > main.c
gcc -shared -fPIC -o libhello.so hello.c
gcc -o app main.c -L. -lhello

ldd ./app                            # 验证：libhello.so => not found（而 libc 能正常解析）
ldconfig -p | grep -c libhello       # 验证：输出 0，说明缓存里没有这个库
./app; echo "exit=$?"                # 验证：报错，退出码 127

LD_LIBRARY_PATH=/tmp/lab-lib ./app   # 验证：临时方案，能跑起来
```

**结论（三条，比「修复成功」更重要）**：

1. **`not found` 的判定证据是 `ldd`**：`ldd ./app` 里 `libhello.so => not found` 一行就是证据，`ldconfig -p | grep -c libhello` 输出 `0` 是佐证。
2. **修复路径有临时（`LD_LIBRARY_PATH`）与持久（`ld.so.conf.d` + `ldconfig`）两条**，两条本次都真跑通了；持久方案复验后**已还原**（删 conf + `ldconfig`，回到 `not found`）。
3. **`LD_DEBUG=libs` 能看到链接器的真实搜索顺序**，且**搜索顺序与「目录是否存在」是两件事**：本机根本没有 `glibc-hwcaps` 子目录，链接器照样先探测 `.../glibc-hwcaps/x86-64-v3/`、`.../glibc-hwcaps/x86-64-v2/` 再回落。**看到这些路径不要以为系统里装了 v3/v2 优化库**——它只是 glibc 2.39 固定按这一套顺序试。

## 5. 生产动作：持久修复一条缺失的库路径

> [!example]- 生产动作：把库路径写进 `ld.so.conf.d` 并刷新缓存（需 root，属于变更）
> **前提**：只在可回滚的机器上做；按子笔记 05 的三件套先备份、写回滚、确认窗口。
>
> ```bash
> ldd /usr/local/bin/<程序> | grep 'not found'        # 验证：先确认缺的是哪个库、在哪个目录
> ls -l /opt/<产品>/lib                               # 验证：库文件确实存在，且架构一致（file <库名>）
> cp -a /etc/ld.so.conf.d /etc/ld.so.conf.d.bak.$(date +%F-%H%M)
>                                                      # 验证：先备份现有配置目录
> printf '%s\n' /opt/<产品>/lib > /etc/ld.so.conf.d/<产品>.conf
> ldconfig                                             # 验证：重建缓存
> ldconfig -p | grep <库名>                            # 验证：缓存里已出现该路径
> ldd /usr/local/bin/<程序> | grep <库名>              # 验证：现在解析到正确路径
> systemctl restart <服务>                             # 验证：业务侧复验（这一步前先确认窗口）
> ```
>
> **验收标准**：`ldd` 不再有 `not found`；服务重启后进程正常存活；业务侧探活通过。**本机在第 4 节已按这条路径实测过一次完整闭环**：写入 `ld.so.conf.d` → `ldconfig` → `ldd` 显示 `libhello.so => /tmp/lab-lib/libhello.so`；随后删除 conf 并再次 `ldconfig`，`ldd` 回到 `not found`、`ldconfig -p | grep -c libhello` 回到 `0`。
>
> **风险**：`ldconfig` 会重建全局缓存，写错路径可能影响其他程序；因此**只增不改**，并保留 `ld.so.conf.d` 的备份。
>
> **耗时**：约 10 分钟（不含观察窗口）。本机实测这一圈不到 1 秒（无服务可重启）。
>
> **回滚**：`cp -a /etc/ld.so.conf.d.bak.<时间戳>/. /etc/ld.so.conf.d/` 或删除新增的 `.conf`，再 `ldconfig`，最后复验 `ldd`。
>
> **要沉淀什么**：把「哪个程序依赖哪个非标准路径的库」写进部署文档，避免下次重装后又踩一遍。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 一看到报错就重装软件 | 如果是「库存在但搜索路径不对」，重装一百次也一样 |
| 用 `LD_LIBRARY_PATH` 修生产问题 | 只对当前进程树生效，重启/换用户即失效；应写 `/etc/ld.so.conf.d/` + `ldconfig` |
| 改了 `ld.so.conf.d` 却忘了 `ldconfig` | 缓存没刷新，链接器仍然看不到新路径 |
| 对来源不明的二进制直接 `ldd` | 老版本 `ldd` 会让程序「跑一遍」；更安全的是 `readelf -d` |
| 用 `find /` 满盘找库 | 慢且会扫到无关目录；优先 `ldconfig -p`，再限定 `/usr` `/lib` `/opt` |
| 忽略架构与 C 库实现 | 32/64 位混装、glibc 对 musl（Alpine）都会报「找不到库」 |
| 看到 `glibc-hwcaps` 子目录以为是恶意文件 | 这是 glibc 2.33+ 的硬件能力分派机制，属正常搜索路径 |
| 看到 `LD_DEBUG` 里的 `glibc-hwcaps/x86-64-v3` 就以为系统装了 v3 优化库 | **搜索顺序 ≠ 目录存在**：本机 glibc 2.39，`/usr/lib/x86_64-linux-gnu/glibc-hwcaps/` 实测不存在，链接器照样先探测该路径再回落 |
| 以为 `LD_LIBRARY_PATH` 的修复「跑通就算完」 | 它只对当前进程树生效；本机实测持久方案（`ld.so.conf.d` + `ldconfig`）才是可验收的修复，且最好当场写好回滚并复验一次 |
| 用 `LD_DEBUG=libs` 长时间挂在高负载程序上 | 它会输出大量日志并拖慢程序，生产上要限定时长与范围 |

## 决策练习

> **场景**：生产机上一个自研程序升级后启动失败，报 `error while loading shared libraries: libfoo.so.1: cannot open shared object file`。`find` 显示这个库已经装在 `/opt/vendor/lib/` 下。
>
> A. 在启动脚本里加 `export LD_LIBRARY_PATH=/opt/vendor/lib:$LD_LIBRARY_PATH`，先把服务拉起来。
> B. 先把 `/opt/vendor/lib` 写进 `/etc/ld.so.conf.d/vendor.conf`、`ldconfig`、复验 `ldd`，再启动服务；如果需要临时先恢复，再额外用 `LD_LIBRARY_PATH` 兜底并记入变更记录。
> C. 把 `libfoo.so.1` 直接复制到 `/usr/lib/` 下，让链接器自动找到。

**为什么选 B**：库存在但不在默认搜索路径，正解是把它加进系统级搜索路径并刷新缓存；这样重启、换用户、换终端都成立。临时方案可以救急，但要写进变更记录并尽快收敛到持久方案。

**为什么 A 不对**：`LD_LIBRARY_PATH` 只影响当前进程树，换个启动方式或被人接手后就失效，故障会以「换了个人/重启后就不行」的形式复发。

**为什么 C 不对**：直接往 `/usr/lib` 复制是典型的「污染系统目录」：包管理器不知道它的存在，升级或冲突时会被覆盖，且没有版本管理。要放进发行版包管理，或放在独立目录并显式声明搜索路径。

## 要点自测

> [!question]- 程序报 `error while loading shared libraries`，你怎么查？
> - **定性**：程序本身被加载了，缺的是动态库——不是「程序损坏」。
> - **找缺失项**：`ldd ./app` 找 `not found` 的行；`readelf -d ./app | grep NEEDED` 看依赖清单。
> - **判断「没装」还是「没找到」**：`ldconfig -p | grep 库名` 与 `find /usr /lib /opt -name '库名*'`；装了却搜不到就是路径问题。
> - **修**：持久方案是写 `/etc/ld.so.conf.d/xx.conf` + `ldconfig`；临时方案 `LD_LIBRARY_PATH=`（只影响当前进程树，别用于生产）。
> - **两个别忘的坑**：32/64 位与 glibc/musl（Alpine）不匹配也会「找不到库」；`LD_DEBUG=libs` 能直接看到链接器的搜索过程。
> - **第一反应不要是什么**：不要直接重装软件包——如果是搜索路径问题，重装一百次也一样。

> [!question]- `ld.so` 的搜索顺序是什么？
> - `DT_RPATH`（老式）→ `LD_LIBRARY_PATH` → `DT_RUNPATH` → `/etc/ld.so.cache` → 默认目录（`/lib`、`/usr/lib` 及其多架构子目录）。
> - 所以「装了但没找到」通常是库不在缓存覆盖的路径里；补路径 + `ldconfig` 后缓存里就能看到。本机实测：加 conf 前 `ldconfig -p | grep -c libhello` = `0`，加 conf 并 `ldconfig` 后出现 `libhello.so (libc6,x86-64) => /tmp/lab-lib/libhello.so`。
> - `glibc-hwcaps` 是 glibc 2.33+ 在每级目录下优先尝试的硬件能力子目录（本机 glibc 2.39，`LD_DEBUG` 里最高探到 `x86-64-v3`）；**探测顺序不等于这些目录真的存在**。
> - **第一反应不要是什么**：不要只看 `ldd` 的结果就下结论，必要时用 `LD_DEBUG=libs` 看真实搜索过程。

> [!question]- 为什么 `LD_LIBRARY_PATH` 不能当生产修复手段？
> - 它只对当前进程树生效，不进 `ld.so.cache`，换终端、换用户、重启后就失效。
> - 它会让「为什么这台机器能跑」依赖一个没人记得住的环境变量，故障会以「换了个人就不行」的形式复发。
> - 正确做法是写 `/etc/ld.so.conf.d/` 并 `ldconfig`；临时用它时必须在变更记录里写明并尽快收敛。
> - **第一反应不要是什么**：不要把「服务起来了」当成问题解决。
