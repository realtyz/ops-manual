# 快照与状态一致性

## 1. 打了快照，为什么还会救不回来

"动手前先打个快照"是一种本能的稳妥感：出事了就回滚。但快照回滚之后经常出现三种局面——机器起来了，可服务连不上上游；时间对不上，日志和证书全乱；同事说"你回滚把今天的数据弄没了"。

这三件事都不属于"快照失败"。它们来自一个必须讲清楚的机制前提：**快照冻结的是这台机器的一部分状态，而"这台机器在系统里的位置"是由它之外的世界定义的**——时间在往前走，对端在改数据，别人在往这台机器上写东西。回滚只把机器这一侧拨回去，另一侧没有义务配合。

把这条前提记住，后面所有的"回滚不了"都能自己推。

## 2. 快照到底保存了什么

一台虚拟机的"状态"由三部分组成，快照可以只取其中一部分：

| 组成部分 | 内容 | 不保存它的后果 |
| --- | --- | --- |
| 磁盘 | 磁盘块在某一时刻的视图 | 没有磁盘就谈不上快照 |
| 内存 | 进程、连接、内核计数器、页缓存 | 恢复后相当于**拔过电源**再开机 |
| 设备状态 | 虚拟网卡、虚拟磁盘控制器的寄存器状态 | 热插拔的设备、直通设备可能对不上 |

于是有两类快照：**含内存快照**恢复后能从停机那一刻继续执行（进程还在、连接还开着）；**只含磁盘快照**恢复后是一次冷启动，内存里的东西全部消失。绝大多数"随手打一个快照"得到的是后者。

只含磁盘的快照带来一个必须记住的等级：**崩溃一致性（crash-consistent）**——磁盘上的数据看起来像是机器被突然断电。文件系统自身的日志能保证它自己不损坏，但正在写的那个文件可能只写了一半。要往上走一个等级，需要在打快照时让文件系统静默（**quiesce**，写入暂停、缓冲刷盘），这一步通常由虚拟化平台提供的工具驱动完成；再往上一个等级是**应用一致性**，需要应用自己配合（数据库的备份模式、`fsfreeze` 冻结文件系统），因为只有应用知道"哪几个文件的哪个组合才算一致"。三个等级的代价递增，能恢复到什么程度也递增。具体支持到什么等级、靠什么驱动，以虚拟化平台文档为准。

## 3. 快照之后，写入去了哪里

第一个快照产生的那一刻，当前磁盘状态被"钉住"，此后所有写入都不再落到原来的块上，而是写进一个增量文件（不同的实现叫重做日志、delta 盘、COW 文件，机制等价：**写时复制**）。

这一机制直接给出三件事：

- **回滚只需要丢掉增量。** 所以回滚本身很快，"回到过去"的成本主要在丢弃内存状态与重启；
- **快照链越长，代价越高。** 每一次读都可能要沿着链逐层回溯到正确的那一层，写也可能需要先读出旧值再写，性能随链长增加而下降；
- **每个快照都依赖它前面的那些。** 单独拿走一个增量文件没有意义，快照不是自包含的。

平台文档对快照链长度与单个快照的保留时长都给出建议上限，**具体数字随产品版本变化，以官方文档的 Snapshot Limitations 一节为准**——抄数字没有意义，记住"链越长越慢、越容易选错"这条即可。

## 4. 为什么快照不是备份

快照与备份的差别不是"够不够用"，而是**故障域**不同：

| 维度 | 快照 | 备份 |
| --- | --- | --- |
| 数据在哪 | 与虚拟机同一存储、同一平台 | 独立的介质或位置 |
| 能否独立恢复 | 依赖链上的其它快照与父盘 | 一份完整副本 |
| 覆盖的故障 | 误操作、改错配置 | 误操作、存储损坏、平台故障、误删 |
| 长期保留 | 保留越久性能越差 | 保留是常态 |

最容易被忽略的一条是**同一时刻的状态里，误删的文件也是被删掉的状态**：快照保护你"改坏配置"，但不保护你"三个月前删错了一个文件而快照只保留了七天"。行业通行的做法是 3-2-1：至少三份副本、两种介质、一份在异地——快照不满足其中任何一条。

## 5. 回滚不了的四样东西

**第一，时间。** 时钟是独立于磁盘的一层，它由虚拟化平台的 RTC 与系统内的时间同步共同决定。磁盘回滚后，时钟与被回滚的状态之间不再有一致的对应关系，必须重新对齐上游时间源。对齐前后的典型现象是：日志时间线断裂（前后两段日志的时间重叠或倒退）、证书校验失败（有效期判断依赖时钟）、依赖时间窗的认证失败。

**第二，外部依赖的状态。** 回滚自己不会让上游数据库、消息队列、注册中心、对端服务跟着回滚。快照之后对端已经处理过的请求不会撤销，于是本机回到"还没有发出这些请求"的状态——重放、重复数据、状态不一致都从这里来。

**第三，机器身份与凭据。** 主机密钥、机器标识（`/etc/machine-id`）都在磁盘上，会跟着一起回滚。于是出现两种不一致：如果这台机器在快照之后换了密钥或标识，回滚会把旧身份复活，客户端报"主机密钥变了"，监控里出现两台同标识的机器；如果发生过克隆，新旧两台机器本来就带着同一个身份。

**第四，快照之后产生的数据。** 别人上传的文件、期间写入的业务数据、快照之后新装的东西，都不在快照里。这一条最容易被当成"回滚出问题了"，其实它正是快照的定义。

## 6. 快照回滚需要一条独立通道

快照回滚这个动作发生在**虚拟化平台层**，不需要客户机配合，也不需要客户机是健康的。但人的判断和验证需要一条通道，理由有三条：

- **需要判断"是不是该回滚"**：网络配置写坏、`fstab` 写坏、认证库写坏时，SSH 会直接失联。没有控制台时你只能看到"连不上"，无法区分"机器死了"和"配置错了"；
- **需要确认回滚成功**：回滚后的第一次启动仍然可能进不了多用户状态（回滚点本身可能就不干净，或者回滚后的机器与外部状态不匹配）；
- **需要验证四样不对劲的东西**：时间、外部依赖、身份、丢失的数据，都要在系统内才能核对。

这就是"能快照"和"能进控制台"必须同时满足的原因，而它们经常不同时满足：云主机的控制台/VNC 往往需要预先开通（甚至需要在创建实例时预留密码），"能重启实例"与"能进控制台"是两件事。平台之间的具体做法以各自文档为准：本地虚拟化（KVM/libvirt、VMware、VirtualBox）通常两种能力都完整；云主机要先确认控制台已开通；WSL2 没有独立的虚拟化控制台，靠导出/导入镜像来"回到过去"；容器的"回到过去"是重建镜像，它与快照的差别在下一节。

## 7. 抽象在哪里漏水

**"回滚"这个动作还需要选一个点。** 快照链上有多个点时，回滚到哪一个、之后链上其它快照怎么办，都需要判断。链越长，"选错快照"的概率越高——而它的表现是"现象对不上"，与"回滚失败"很像。

**直通设备、独立磁盘这类对象可能根本不支持快照。** 各平台文档会明确列出不支持的对象（例如不参与快照的独立磁盘、物理兼容模式的裸设备映射、直通设备）。这意味着"整台机器都回到过去了"这个假设不成立：有些东西留在原地。

**容器不是快照。** 容器重建回到的是**镜像里的内容**：镜像解决了"程序与依赖"，但不包含运行期状态。配置、数据卷、密钥、正在处理的队列都要单独管——它们在容器外。把容器重建当成回滚，最常见的后果是"程序回来了，数据没了"。

**无内存快照不能当"接着跑"用。** 恢复后所有连接、锁、临时状态消失。对数据库、消息队列这类有本地状态的服务，冷启动后的行为与"接着跑"完全不同。

**快照不是"可以随便试"的许可证。** 它降低的是"改坏配置"的成本，不降低"改坏外部状态"的成本。破坏性演练的价值恰恰在于把这条边界练成直觉。

## 常见误解

| 常见说法 | 事实 |
| --- | --- |
| 「有快照就随便改」 | 快照只冻结本机的一部分状态；外部依赖、时间、快照后写入的数据都不在其中 |
| 「回滚之后就是当时的样子」 | 磁盘是当时的样子，时钟不是，外部世界的状态也不是 |
| 「快照就是备份」 | 同一故障域、依赖链、不独立；丢失的数据在快照里同样是丢失的状态 |
| 「快照越多越安全」 | 链越长读写越慢、越容易选错回滚点；平台文档给出建议上限 |
| 「回滚后现象对不上，说明回滚失败」 | 先核对时间、外部依赖、机器身份、快照之后产生的数据这四样 |
| 「云主机能重启就有控制台」 | 重启实例与进控制台是两种能力，控制台通常需要预先开通 |
| 「容器重建就是回滚」 | 重建只回到镜像内容，运行期状态、配置与数据卷在容器之外 |
| 「机器标识和主机密钥不用担心」 | 它们随磁盘回滚，会与外部世界当前认为的身份不一致；克隆不重置会导致两台机器同身份 |

## 要点自测

**问：快照"保存了什么"这件事，为什么会决定"回滚之后能不能接着跑"？**
答：快照可以只含磁盘，也可以同时含内存与设备状态。只含磁盘的恢复是一次冷启动，进程、连接、锁、内核计数器全部消失；含内存的恢复才能从停机那一刻继续。判断一次恢复是"接着跑"还是"重启"，先看快照的类型。

**问：为什么"回滚之后现象对不上"往往不是回滚失败？**
答：因为回滚只把机器这一侧拨回去，而时间、外部依赖的状态、机器在外部世界里的身份、以及快照之后别人写到这台机器上的数据，都由机器之外定义。回滚成功恰恰意味着这四样东西与当前状态不再一致。

**问：崩溃一致性、文件系统一致性、应用一致性分别是谁保证的？**
答：崩溃一致性由文件系统自身的日志机制保证（相当于断电，文件系统不坏但文件可能半写）；文件系统一致性需要打快照时让文件系统静默，通常由虚拟化平台的工具驱动完成；应用一致性需要应用自己参与（备份模式、冻结文件系统），因为只有应用知道哪些文件的哪种组合才算一致。

**问：为什么"能快照"和"能进控制台"要同时满足？**
答：回滚动作在虚拟化平台层完成，不需要客户机健康；但判断要不要回滚、确认回滚成功、核对时间与身份，都需要一条独立于网络配置的系统内通道。网络或认证被改坏时，SSH 正好是失联的那一条。

**问：为什么说"快照保护你改坏配置，但不保护你删错文件"？**
答：快照记录的是一个时刻的状态，如果文件是在快照之前被删的，快照里它同样是删除状态；而单个快照的保留时长通常远短于"发现删错文件"所需的时间。这正是需要独立备份的原因。

**第一反应不要做什么**：不要把快照当备份；不要在没确认控制台可用的情况下改网络与挂载配置；不要用"回滚一下"代替对回滚成本的判断。

## 参考文档

- 虚拟化平台的快照语义与限制：VMware vSphere 产品文档中《Using Snapshots to Manage Virtual Machines》与其中的 Snapshot Limitations 一节（支持与不支持的对象、链长与保留建议、静默机制）。
- QEMU/KVM 侧：`man 1 qemu-img`（内部快照与外部快照、`commit` 与 `convert` 的语义）、`man 1 virsh`（`snapshot-create-as`、`snapshot-list`、`snapshot-revert` 的参数与内存状态选项）、libvirt 官方文档中关于快照类型的章节。
- `man 5 machine-id` 与 `man 1 systemd-machine-id-setup`（机器标识的生成、重置与克隆场景）、`man 1 ssh-keygen`（主机密钥的生成与轮换）。
- `man 1 fsfreeze`、`man 8 mount`（冻结文件系统与只读重挂的语义）。
- `man 1 timedatectl`、`man 8 systemd-timesyncd`（时间同步状态与 RTC 的处理）。
