# 发行版的构成与差异来源

## 1. 只装内核的机器不能用

Linux 内核管四件事：CPU 时间、内存、设备与文件系统、进程间通信。它通过系统调用对外提供服务，自己不含 shell、不含 `sshd`，也没有"用户"这个概念——`/etc/passwd` 是**用户态的约定**，不是内核接口。

可以做一次思想实验：把编译好的内核镜像单独启动，会停在 `Kernel panic - not syncing: No working init found`。内核找到了硬件、挂上了根文件系统，却找不到第一个用户态进程，于是什么也做不了。要让机器可用，必须再补上一整套**用户态**：init（现代发行版是 systemd）、C 库（glibc 或 musl）、shell 与核心工具、包管理器，以及一组**默认选择**（文件系统、安全模块、防火墙前端、时区与字符集）。

发行版（distribution）就是这份打包：**内核 + 用户态 + 包管理 + 一套默认选择**。由此得到一句可以反复使用的判断：

**内核提供机制，发行版选择策略。**

你遇到的大部分"这个命令怎么没有""这个字段怎么不存在"，都是这句话的推论：

| 内核提供的机制 | 发行版选择的前端 | 现场表现 |
| --- | --- | --- |
| netfilter 的包过滤钩子 | firewalld / ufw / 直接写 nft 规则 | 放行端口的命令与持久化方式不同 |
| cgroup v1 与 v2 | systemd 的资源控制 | 上限写在哪里、什么时候生效不同 |
| LSM（Linux Security Module，强制访问控制框架） | SELinux / AppArmor | 判断入口是 `getenforce` 还是 `aa-status` |
| 网络设备与路由 | NetworkManager / systemd-networkd / netplan / ifupdown | 配一个地址的文件与命令不同 |
| 可加载内核模块 | `modprobe.d`、`modules-load.d` | 同一硬件在不同发行版靠不同模块驱动 |
| 内核参数（`/proc/sys/*`） | `sysctl.d` 里的发行版默认值 | 同一个键的默认值不同 |

真正让人踩空的不是"机制不存在"，而是**机制在、前端不在**：Ubuntu 上敲 `firewall-cmd` 得到 `command not found`，不是权限问题，是这台机器选择了另一个前端（`ufw`），而底层仍然是同一套 netfilter。

## 2. 内核承诺不破坏用户态，所以二进制能跨发行版跑

把 Ubuntu 上编译的 ELF 可执行文件拷到 RHEL 上，通常能直接运行。这不是巧合，是一项长期承诺：内核的系统调用、`/proc`、`/sys` 接口**不做破坏性变更**——已有程序依赖的接口要么保留，要么通过新接口并存的方式演进。内核版本从 5.x 走到 6.x，这个承诺依然成立。

但这条承诺只管到内核边界。**glibc（GNU C Library，C 标准库）属于用户态**，它的版本由发行版决定。动态链接的程序在链接时会把"我需要哪些库的哪些符号版本"写进自己（例如 `GLIBC_2.34`）。运行时的 glibc 低于这个版本，加载器就报 `version 'GLIBC_2.38' not found`。

方向是不对称的：**老二进制能在新库上跑，新二进制在老库上失败**。这就是"同一份二进制跨发行版"的真实边界——拷得过去的是接口，拷不过去的是库版本。库版本与依赖解析的完整机制见《程序启动与依赖解析》。

## 3. 版本号为什么不能跨发行版比较：backport

上游内核每 9～10 周发布一个主线版本；每个稳定版本只维护很短一段时间。长期支持型发行版不可能跟着上游换内核——那意味着驱动、模块 ABI、认证全都重来一遍。它的做法是：**冻结一个主线基线，把上游后续版本里需要的补丁挑出来回移到自己的分支上**，这个动作叫 backport。

后果是版本号的含义被改写了：

- RHEL 9 报出的 `5.14.x` 里，可能包含上游 6.x 才有的特性；Ubuntu 的 `6.8.0` 也带着大量上游后续版本的补丁；
- 一个长期支持分支会累积上万条补丁，版本号的第三段只反映发行版自己的构建序号，**不反映补丁量**；
- 反向比较同样不成立：`6.8` 与 `5.14` 之间没有"谁新"这个普遍答案，只能说"这条发行版分支上有什么"。

所以**能力门控不能只看版本号**。要判断某个特性、某个 `/sys` 字段、某个 `sysctl` 键在不在，只有两条路：查该发行版针对**这个版本**的发布说明，或者在本机直接看它是否存在。这也解释了为什么照抄一篇"某内核版本以上都支持"的博客经常出错。

## 4. 内核版本号的读法

`6.8.0-139-generic` 由三段构成，各有来源：

| 片段 | 含义 | 谁决定 |
| --- | --- | --- |
| `6.8.0` | 上游主线基线 | 上游内核社区 |
| `-139` | 发行版的构建与 ABI 序号；同一基线每次更新内核都会自增 | 发行版 |
| `-generic` | 变体：编译配置与驱动集合 | 发行版 |

`-139` 值得单独记住：它变了就意味着内核包换了，`/lib/modules/<版本>` 下的模块目录也随之变化——自己编译过外部模块的机器，升级内核后模块需要重新编译，故障现象通常是"服务起不来、报找不到某个模块"。

有些内核带平台后缀：`-aws`、`-azure`、`-cloud`、`-microsoft-standard-WSL2` 等。这类内核来自云厂商或平台自己的分支，配置与补丁集都与发行版官方内核不同。**看到后缀，就不要套用通用发行版文档**：同一台"Ubuntu"上的内核行为可能和官方内核不一致，而发行版文档只描述后者。

## 5. 血统与派生：谁先拿到补丁

发行版之间有明确的上下游关系，这决定了补丁到达的延迟：

- **Fedora 在上游，RHEL 在下游。** 新特性先在 Fedora 落地验证，再进入 RHEL；RHEL 的源码包公开后，Rocky / AlmaLinux / Oracle Linux 按它重建（rebuild），补丁比 RHEL 再晚几天到几周；
- **Debian 在上游，Ubuntu 是它的派生。** Ubuntu 从 Debian 的 unstable / testing 分支取一个时间点做基础，再自己加内核与用户态的取舍；
- **openSUSE 在上游，SLES 是它的企业版下游。**

这些关系给出两条实用推论：

**推论一，看到"文档里没有"先问血统。** 一篇 Rocky 的文档常常能用在 AlmaLinux 上，但未必能用在 Fedora 上；一篇 Debian 的文档在 Ubuntu 上大体适用，除了 Ubuntu 自己替换掉的那部分（内核、安全模块默认值、`netplan`）。

**推论二，支持周期是选型门槛，但数字要现场查。** 社区版与企业版的支持年限差异很大（从不到一年到十年级），各类延期支持计划（如 Ubuntu 的 ESM）还会额外延长。具体年限逐版本调整过，抄进笔记就会过期——**判据是发行版官方的生命周期页**，不是别人的文章。

## 6. 版本基线为什么是四项

一台机器身上有四个相互独立的版本，它们分别决定四类事情：

| 基线 | 取值位置 | 决定了什么 | 缺了它会错在哪 |
| --- | --- | --- | --- |
| 发行版 | `/etc/os-release`（规范见 `man 5 os-release`） | 包管理、配置位置、默认安全模块、用户态库版本 | 把某个家族的路径或命令当成通用路径 |
| 内核 | `uname -r` | 内核能力、驱动、`/proc` 与 `/sys` 里有哪些字段 | 把"字段不存在"当成故障，或反过来 |
| systemd | `systemctl --version` | 服务、单元、资源控制、日志的接口形态与可用属性 | 命令在、参数或属性不被识别 |
| cgroup 版本 | `stat -fc %T /sys/fs/cgroup` | 资源限制写在哪、字段名与单位是什么 | 在 v2 上找 `memory.limit_in_bytes`，在 v1 上用 `memory.max` |

这四项构成"跨机器可比较的最小集合"。任何要跨机器成立的结论，都得先对齐它们——否则你比较的不是两台机器的同一个东西。

cgroup 版本尤其容易猜错：它**不能由发行版名推出来**，同一个发行版的不同版本（甚至同一版本的不同内核启动参数）可能不同，只能现场取。判据是 `stat -fc %T /sys/fs/cgroup` 的输出：`cgroup2fs` 表示 v2，`tmpfs` 表示 v1。

## 7. 抽象在哪里漏水

**`ID_LIKE` 只是"像"，不是"是"。** `/etc/os-release` 里一行 `ID_LIKE=debian` 表示它与 Debian 家族有共同点，不构成包含关系，也不能用来推包名、路径与默认值。

**同名不同物。** 同一个功能在不同家族由不同软件承担，包名与单元名都不同：DNS 排查工具是 `bind-utils` 或 `dnsutils`，Web 服务是 `httpd` 或 `apache2`，网络时间服务是 `chronyd` 或 `chrony`。判断"某个命令归哪个包"要用该家族的查询命令，而不是记忆。

**同一台机器上可能有多套前端并存。** 网络配置尤其典型：NetworkManager 与 systemd-networkd 可以同时存在，谁在管这块网卡取决于它是否被某个前端接管。此时"改了配置文件不生效"的答案往往在"谁管着这个接口"，而不在文件内容。

**容器镜像不是发行版机器。** 镜像里有用户态，但没有自己的内核，通常也没有 init。在容器里验证 sysctl、内核模块、内核启动参数、`fstab` 得到的结论，不能外推到虚拟机或物理机——那些东西属于宿主内核。

**身份是发行版之外的一层。** `/etc/machine-id` 是安装或首次启动时生成的机器标识（格式见 `man 5 machine-id`）。克隆虚拟机不重置它，新旧两台机器就会带着同一个身份出现在日志、授权与监控里，让排障结论指向错误的机器。

## 常见误解

| 常见说法 | 事实 |
| --- | --- |
| 「Linux 就是发行版」 | Linux 是内核；能用的是发行版，后者由内核、用户态、包管理与默认选择共同构成 |
| 「调用了同一个命令，所以行为一样」 | 命令属于用户态，不同发行版可以用不同实现甚至完全不同的前端 |
| 「内核版本高就是功能新」 | 长期支持发行版靠 backport 把新特性并入低版本号，跨发行版比较版本号没有意义 |
| 「`uname -r` 没后缀就是原生内核」 | 有后缀说明是平台定制内核，没有后缀也不代表配置与上游一致；判据是该发行版的发布说明 |
| 「`ID_LIKE=debian` 所以按 Debian 的路径来」 | 它只表示家族相似；Ubuntu 自己替换了内核、网络配置与安全模块的默认值 |
| 「cgroup v1 还是 v2 看发行版版本就知道」 | 只能现场取：`stat -fc %T /sys/fs/cgroup` 的输出是 `cgroup2fs` 才是 v2 |
| 「容器里能用的参数，虚拟机上也能用」 | 容器共享宿主内核，容器内看不到也改不了大部分内核侧开关 |
| 「克隆出来的机器和原机器是两台」 | 不重置 `machine-id`，它们在日志、授权与监控里是同一个身份 |

## 要点自测

**问：为什么在 Ubuntu 上敲 `firewall-cmd` 会报 `command not found`？**
答：因为"内核提供机制，发行版选择策略"。包过滤的机制（netfilter）在内核里，`firewall-cmd` 只是 RHEL 系选择的前端；Ubuntu 选的是 `ufw` 与直接的 nft 规则。命令不存在说明前端不在，不代表放行规则不能配。

**问：为什么 Ubuntu 上编译的程序能在 RHEL 上跑，反过来却常常失败？**
答：内核承诺不破坏用户态接口，所以系统调用与 `/proc`、`/sys` 这一层跨发行版稳定；而 glibc 属于用户态，符号版本只增不减，新二进制要求的高版本符号在老库上找不到，加载器就报 `version 'GLIBC_x.y' not found`。

**问：同事说"RHEL 9 的内核 5.14 比 Ubuntu 22.04 的 5.15 旧"，这句话哪里不对？**
答：把版本号当成能力排序。两个发行版都在自己的分支上 backport，5.14 分支里可能有上游 6.x 的特性，5.15 里也可能缺某个补丁。正确做法是查这两个版本各自的发布说明，或在本机直接确认那个特性、字段或参数是否存在。

**问：接手一台陌生机器，为什么要先取四项版本基线，而不是先看负载？**
答：负载数字的解释依赖这四项。同一句"负载高"在 cgroup v1 与 v2 上要用不同字段去看，在不同 systemd 版本上可用的属性不同，不同内核上 `/proc` 与 `/sys` 里的字段也可能不在。先对齐基线，后面的读数才可比。

**问：`uname -r` 输出带 `-microsoft-standard-WSL2` 后缀，说明什么？**
答：这是平台定制内核，不是发行版官方内核。它的配置、驱动与补丁集与发行版文档描述的对象不同，涉及内核行为的结论要按对应平台的文档来，不能照搬发行版文档。

**第一反应不要做什么**：不要用发行版名或内核版本号推断能力；不要把某个家族的路径、包名、命令当成通用知识；不要在容器里验证内核侧开关。

## 参考文档

- `man 5 os-release`（`/etc/os-release` 各字段的规范）、`man 1 uname`、`man 1 systemctl`、`man 1 stat`、`man 5 proc`、`man 5 machine-id`。
- 内核 6.x 文档 `Documentation/process/stable-kernel-rules.rst`（稳定分支接受哪些补丁）、`Documentation/admin-guide/` 下与启动参数、`sysctl` 相关的章节。
- 各发行版官方的生命周期与发行说明页：RHEL / CentOS Stream / Rocky、Ubuntu、Debian、SUSE。**支持年限与 EOL 日期一律以这些页面为准**，本库不抄录具体数字。
- 各家族的包管理与仓库文档：`man 5 dnf.conf`、`man 5 sources.list`、`man 5 zypper`、`man 5 apk` 及对应发行版的官方仓库配置说明。
- `man 8 firewall-cmd`、`man 8 ufw`、`man 8 nft`、`man 8 getenforce`、`man 8 aa-status`、`man 1 nmcli`、`man 5 netplan`：同一机制在不同发行版上的前端入口。
