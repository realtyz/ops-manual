## 0. 30 秒速览

> [!abstract] 这一篇只要记住四句话
> - **「重启能解决 90% 的问题，但会毁掉 100% 的现场。」**
>   证据：进程状态与 `wchan`、连接队列、`nstat`/`vmstat` 计数器、`dmesg` 环形缓冲、临时文件与锁，重启后几乎全部消失。
> - **取证要「同时刻」，不能一项一项慢慢来。**
>   怎么验证：先 `date` 记下时间戳，再在同一分钟内取负载、内存、IO、连接、内核日志；分开取会拼不出因果。
> - **取证的目的是回答「现在这台机器长什么样」，不是马上找根因。**
>   证据：没找到根因也可以先止损；但没有现场，止损之后就只剩「重启后好了」。
> - **证据不落盘等于没取。**
>   怎么验证：每一条命令都 `tee` 到文件或重定向到带时间戳的目录，别只打印在终端里。

## 1. 为什么「先取证再动手」

排障有两个顺序：**先定位后止损**，或**先止损后定位**。两者的选择取决于业务影响，但有一件事是两种顺序都绕不开的：**在做出任何不可逆动作之前，先把现场固定下来。**

原因很直接：

- 现象可能**只出现一次**。一个偶发的内存泄漏、一次锁竞争、一次网络抖动，重启之后可能几个月都等不到第二次。
- 现场大部分是**内存态**的。进程状态、连接队列、内核计数器、临时文件与锁，重启即失。
- 「重启后好了」是一个**结论**，不是证据。把现场取下来，才有可能把「重启后好了」升级成「根因是什么、下次怎么防」。

> [!tip] 第一反应不要是「先重启看看」
> 只要业务还撑得住、只要还能取到证据，就先取证。**重启是止损手段，不是排查手段**——这句话在事故复盘里几乎每次都成立。

## 2. 同时刻取证包

下面这组命令覆盖 CPU、内存、IO、连接、进程与内核日志六个面。**建议存成一个 `snapshot.sh`，出事时一条命令跑完。**

```bash
out=/tmp/snap-$(hostname)-$(date +%Y%m%d-%H%M%S)
mkdir -p "$out"

{ date; uptime; hostname; } > "$out/00-id.txt"
vmstat 1 5 > "$out/01-vmstat.txt"
free -m > "$out/02-free.txt"
cat /proc/pressure/cpu /proc/pressure/memory /proc/pressure/io > "$out/03-psi.txt"
iostat -x 1 5 > "$out/04-iostat.txt"
df -hT > "$out/05-df.txt"; df -i >> "$out/05-df.txt"
ss -s > "$out/06-ss-summary.txt"; ss -lnt >> "$out/06-ss-summary.txt"
nstat -az | head -40 > "$out/07-nstat.txt"
ps -eo pid,ppid,stat,pcpu,pmem,wchan:20,cmd --sort=-pcpu | head -15 > "$out/08-ps-cpu.txt"
ps -eo pid,ppid,stat,pcpu,pmem,wchan:20,cmd --sort=-rss | head -15 > "$out/09-ps-rss.txt"
journalctl -k -n 50 --no-pager > "$out/10-kmsg-journal.txt"
dmesg -T | tail -30 >> "$out/10-kmsg-journal.txt"
tar czf "$out.tgz" -C "$(dirname "$out")" "$(basename "$out")"
echo "取证包：$out.tgz"
```

**验收标准**：`$out.tgz` 里十个文件都有内容；`00-id.txt` 里有时间戳，其余文件的时间与它相差不超过一分钟。

几条使用约束：

- **全程只读，生产机上也可以做**（`iostat`/`sar` 若未安装可先跳过，但要在记录里写明缺失）。
- **`ps` 两次分别按 CPU 与内存排序**，不要只取一个方向；真正吃资源的不一定是 CPU 最高的那个。
- **`nstat -az` 输出很长**，先取 `head -40`；需要完整计数时再单独导出。
- **取证包只解决「留存」**，定位方法在后面的阶段展开；这一站先把「留得下来」练熟。

## 3. 重启会毁掉什么

| 证据 | 重启后 | 说明 |
| --- | --- | --- |
| 进程状态、`wchan`、句柄与连接 | **全没了** | 内存里的东西不落盘 |
| `nstat`/`/proc/vmstat` 等计数器 | **清零** | 只能靠外部监控（`sar`/Prometheus）回溯 |
| `temp`/`/tmp` 里的临时文件、socket、锁文件 | 多半消失 | 有些应用状态只在运行时存在 |
| 内核环形缓冲（`dmesg`） | **被清空**（除非 journal 持久化） | 所以 `journalctl -k --no-pager > /tmp/kmsg.$(date +%s).log` 值得养成习惯 |
| 内存里的 core/`vmcore` | 取决于是否配置 | panic 场景要靠 kdump，深水区在阶段 2《启动流程与内核》 |

> [!warning] 关于 `journalctl` 的两个前提
> 一是**持久化**：只有 `/var/log/journal` 存在且 `Storage=` 允许持久，`journalctl -b -1` 才能看到上一次启动；否则重启后日志一起消失。二是**别删证据**：排查期间不要执行 `journalctl --vacuum-*`，那等于自己把现场删掉。

## 4. 证据的另一半：历史数据

同时刻取证只能回答「现在」，回答「昨天下午三点」要靠历史数据。两条路：

- **本机历史**：`sar`（来自 `sysstat`）记录 CPU、内存、IO、网络等历史值；前提是采样已开启。先用 `sar -f /var/log/sysstat/sa<日>`（Debian 系）或 `sar -f /var/log/sa/sa<日>`（RHEL 系）确认有数据。
- **外部监控**：Prometheus、Zabbix 或云监控。它们的采样粒度与保留期决定了你能回溯多久，**要提前确认有数据，而不是出事当天才发现没采**。

```bash
ls /var/log/sysstat/ 2>/dev/null || ls /var/log/sa/ 2>/dev/null
                                             # 验证：本机是否存在 sysstat 历史数据目录
sar -u 1 3                                   # 验证：CPU 历史/实时采样（未装 sysstat 会 command not found）
systemctl is-active sysstat                  # 验证：采集服务是否在运行（Debian 系可能用 sysstat.service）
```

## 5. 生产动作：产出一个可归档的取证包

> [!example]- 生产动作：故障现场取证（只读，生产机上也可以做）
> **做什么**：把第 2 节的快照脚本存成 `/usr/local/bin/snapshot.sh`，出事时第一时间执行；如果近期做过变更，把变更记录也一起放进包里。
>
> ```bash
> bash /usr/local/bin/snapshot.sh            # 产出 /tmp/snap-<主机>-<时间>.tgz
> ls -lh /tmp/snap-*.tgz                      # 验证：包存在且非空
> ```
>
> **验收标准**：包里有十类文件；时间戳一致；已复制到工单、堡垒机或专门的取证目录，而不是只留在出事的机器上。
>
> **风险**：全部只读；唯一副作用是占用少量磁盘与 CPU（`vmstat 1 5`、`iostat -x 1 5` 会各跑几秒）。
>
> **耗时**：约 1~2 分钟（含 `iostat` 的采样等待）。
>
> **回滚**：不需要回滚；取证包按保留策略清理即可，**不要在排查结束前删**。
>
> **要沉淀什么**：这份包 + 子笔记 05 的变更记录，才构成完整的时间线（「几点改了什么、几点开始异常、现场长什么样」）。

## 常见坑

| 常见做法或说法 | 后果或事实 |
| --- | --- |
| 先重启，起来了再找原因 | 重启会毁掉大部分现场；难复现的问题可能再也等不到第二次 |
| 只把命令输出打在终端里 | 终端一关就没了；必须 `tee`/重定向到文件 |
| 一项一项慢慢取，中间隔了十几分钟 | 不同时刻的数据无法拼因果；先固定时间戳，尽量在同一分钟采完 |
| 只看 CPU Top | 真正吃内存、占句柄、卡在 D 状态的进程可能 CPU 很低 |
| 排查期间执行 `journalctl --vacuum-*` | 等于自己删掉内核日志证据 |
| 以为 `journalctl -b -1` 一定有上一次启动 | 没有持久化时，重启后日志也一起消失 |
| 出事当天才发现没有历史监控 | 「昨天下午发生了什么」就永远回答不了；要提前确认采集与保留期 |
| 把取证包只留在故障机上 | 机器若被重装或销毁，证据一起丢；要复制到工单或专门目录 |

## 决策练习

> **场景**：凌晨 2 点，一台数据库服务器出现间歇性卡顿，业务已经报警但还没有完全不可用。值班同事建议「先重启一下，说不定就好了」。
>
> A. 立刻重启，先恢复业务；白天再查。
> B. 先跑一遍同时刻取证包，把包复制出机器；然后按业务影响决定是否重启，重启前把触发时间与现象记进变更/事故记录。
> C. 不重启，直接在机器上长时间跑 `strace -p` 追根因。

**为什么选 B**：业务还没到必须立刻止损的程度，先把现场取下来是成本最低、收益最高的动作。取完再决定止损顺序，重启也变成了一次有记录、有依据的操作。

**为什么 A 不对**：重启是止损手段，不是排查手段；在还没取证的情况下重启，等于用一次「好了」换掉全部现场，根因会被推迟到下一次复发。

**为什么 C 不对**：`strace` 会显著拖慢被跟踪进程，长时间挂在高负载的数据库上可能把「卡顿」变成「不可用」；生产上的观测工具必须限定范围与时长。

## 要点自测

> [!question]- 为什么说「重启能解决 90% 的问题，但会毁掉 100% 的现场」？
> - 重启确实能恢复：清掉卡住的进程、泄漏的内存、异常的网络状态与僵死的服务，这也是它有效的原因。
> - 但证据全在内存里：进程状态与 `wchan`、连接与队列、`nstat`/`vmstat` 计数器、`dmesg` 环形缓冲、临时文件与锁——重启后几乎全部消失。
> - 所以纪律是先后顺序：现象发生时**先同时刻取证**，再决定是止损重启还是继续定位。
> - **第一反应不要是什么**：不要用「先重启看看，不行再说」回应任何一个未被解释的故障。

> [!question]- 一次取证至少取哪几组？为什么要「同时刻」？
> - 六组：时间与身份（`date`/`hostname`/`uptime`）、CPU 与负载（`vmstat`/`uptime`）、内存与压力（`free`/PSI）、磁盘与 IO（`iostat`/`df`/`df -i`）、连接与协议栈（`ss`/`nstat`）、进程与内核日志（`ps`/`journalctl -k`/`dmesg`）。
> - 同时刻是为了能拼因果：分开取会得到「两个时刻的两件事」，无法判断谁先谁后。
> - 取完立刻打包并复制出机器，避免机器被重启或销毁时一起丢失。
> - **第一反应不要是什么**：不要在终端里「看一眼就算取证了」。

> [!question]- 「昨天下午发生了什么」应该去问谁？
> - 本机的 `sar` 历史数据（前提是 sysstat 采集已开启），或外部监控系统（Prometheus/Zabbix/云监控）。
> - 同时刻取证只能回答「现在」，回答不了过去；所以关键机器的采集与保留期要提前确认。
> - 变更记录是另一条线：把「昨天下午改过什么」和「下午几点开始异常」对齐，才能建立因果。
> - **第一反应不要是什么**：不要等出事当天才发现没有历史数据。
