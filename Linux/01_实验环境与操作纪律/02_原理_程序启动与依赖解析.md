# 程序启动与依赖解析

## 1. 一条报错，两种完全不同的原因

程序跑不起来，屏幕上出现：

```text
./app: error while loading shared libraries: libx1.so: cannot open shared object file: No such file or directory
```

这句话很容易被读成"程序坏了"或"库文件丢了"。它真正的意思是：**程序一次都没开始运行**。这条消息不是程序打印的——它由一个专门的程序（动态链接器）打印，而这个程序的任务是在你的程序开始执行之前，把它需要的共享库找齐并接好。

理解这一点，才能理解后面所有推论：报错发生在 `main` 之前，所以应用自己的日志里什么都不会有；报错处理的是"找库"这件事，所以真正的问题可能是没装、路径不对、架构不对、库的实现不对，而**不是**程序逻辑。

死掉时进程的退出状态是 127。这与 shell 报"命令不存在"的 127 相同，所以**不能靠退出码区分是"命令不存在"还是"依赖找不到"**，要看 stderr 里那一行。这条报错的可见位置也值得记住：由 systemd 拉起的服务，它出现在 `journalctl -u <单元>` 里，而不在应用的日志文件里。

## 2. 从 `execve` 到 `main`：程序启动的四步

用户敲下命令，shell 调用 `execve`（系统调用）把可执行文件交给内核。后面发生的事分成四步：

1. **内核读 ELF 头。** ELF（Executable and Linkable Format）是 Linux 上的可执行文件格式，头部描述"这段是代码、那段是数据、入口在哪、依赖哪个解释器"。这里的"解释器"不是脚本语言的解释器，而是**动态链接器**，写在 `PT_INTERP` 段里，典型路径 `/lib64/ld-linux-x86-64.so.2`。
2. **内核加载并跳转。** 内核把 ELF 里标记为"要加载"的段映射进地址空间，然后把控制权交给动态链接器，**而不是交给 `main`**。
3. **动态链接器找齐依赖。** 它读 ELF 里的 `DT_NEEDED` 列表（"我需要哪些库"），按固定顺序在磁盘上找，找到就映射进来，找不到就打印第 1 节那条消息并退出。
4. **重定位并交接。** 所有依赖就位后，链接器修正地址引用、跑完 C 库的初始化（`main` 之前那一段），最后跳到程序入口。

这四步解释了三个反直觉现象：**依赖缺失时程序一行代码都没跑**；**`ldd` 之类的工具并不是"看文件"，而是在模拟链接器的工作**；**同一份二进制在 A 机器上能跑、在 B 机器上报缺库，差别只可能在磁盘上有没有那份库、在不在搜索路径里**。

## 3. 依赖记的是名字，不是路径

`DT_NEEDED` 里存的不是 `/usr/lib/x86_64-linux-gnu/libc.so.6` 这样的路径，而是 **SONAME**——库对外声明自己叫什么名字，通常是 `libc.so.6` 这种形式。

这个设计是共享库能工作的前提：库装在哪里由发行版和包管理器决定（`/lib/x86_64-linux-gnu`、`/usr/lib64`、`/opt/<产品>/lib` 各不相同），而依赖关系只记名字，加载时再去搜。

SONAME 里的数字是 **ABI 版本**，不是文件版本：`libc.so.6` 的 `6` 表示"接口的第 6 代"，只要不出这个代次，库文件内部怎么升级都不影响使用者。更细一层是**符号版本**——库可以给同一个函数名挂多个版本（glibc 的 `memcpy@GLIBC_2.14` 与 `GLIBC_2.2.5` 同时存在），可执行文件记录自己需要哪一个。这就是第 2 节里 `version 'GLIBC_x.y' not found` 这类报错的来源：**库在，但库太老，里面没有我要的那个符号版本。**

## 4. 搜索顺序是固定的五步

动态链接器按 `man 8 ld.so` 规定的顺序依次查找，任何一步命中就停止：

| 顺序 | 来源 | 谁设置的 | 边界 |
| --- | --- | --- | --- |
| 1 | `DT_RPATH` | 链接时写进二进制（`-rpath`） | 已被 `DT_RUNPATH` 取代，新工具链默认不再生成 |
| 2 | 环境变量 `LD_LIBRARY_PATH` | 运行时由调用者给 | 只影响这个进程及其子进程；setuid 等"安全执行模式"下被忽略 |
| 3 | `DT_RUNPATH` | 同样在链接时写入 | 只对**直接依赖**生效，不传递给依赖的依赖 |
| 4 | `/etc/ld.so.cache` | `ldconfig` 生成的缓存 | 内容是"上次扫描到的库"，不是实时的文件系统 |
| 5 | 默认路径 `/lib`、`/usr/lib`（64 位架构上还有 `/lib64`、`/usr/lib64`） | 约定 | 用 `-z nodefaultlib` 链接的二进制会跳过这一步 |

两个容易忽略的性质：

**搜索顺序是"目录列表"，不检查目录是否存在。** 不存在的目录会被直接跳过，这不是错误。所以观察搜索过程时会看到一堆根本没有的路径被"尝试"过——`LD_DEBUG=libs` 里那种一长串尝试记录，绝大部分是在报告"这个目录里也没有"。

**缓存与文件系统可以不一致。** 第 4 步用的是缓存。缓存由 `/etc/ld.so.conf` 与 `/etc/ld.so.conf.d/*.conf` 里的目录列表编译而来，编译动作是 `ldconfig`（需要 root）。**把库放进一个新目录、写进配置、却没跑 `ldconfig`，第 4 步仍然找不到它**——这是"配置改了却不生效"的一类标准原因。

## 5. 为什么 `LD_LIBRARY_PATH` 不能当修复手段

`LD_LIBRARY_PATH` 排在顺序第 2，优先级比缓存还高，看上去是"最快的修复"。它在四个方向上都不合格：

- **作用域不对**：它只作用于当前进程及其子进程。服务重启、换一个用户、从别的入口进都失效；
- **谁都不知道它存在**：它不在任何配置文件里。下一个接手的人只能看到"程序有时候能跑"，无法复现；
- **安全执行模式下被忽略**：对 setuid / setgid 程序，链接器会忽略它并把该变量从环境里剥掉，这是防止"用环境变量劫持特权程序加载的库"的设计；
- **它掩盖了真正的问题**：库应当在标准位置、由包管理器安装，或者有一个写下来的搜索路径配置。用环境变量绕过，等于把一个安装问题变成了一个隐性依赖。

反过来说，正确定位顺序是先回答"是没装，还是装了但没找到"：查库属于哪个包、装没装、装到哪个目录、那个目录在不在搜索路径里。四步走完再动手，持久方案是把目录写进 `ld.so.conf.d` 并重建缓存（或直接安装正确位置的包），临时方案才是环境变量——并且要明确它只是临时。

## 6. 硬件能力分派：为什么会出现没有的目录

从 glibc 2.33 起，搜索路径里多了一层：链接器会先尝试像 `glibc-hwcaps/x86-64-v3/` 这样的子目录，找到"为更高指令集编译的版本"就用它，找不到再回落到普通路径。

这带来两个常见误判：**看到日志里出现 `x86-64-v3` 就以为机器上装了 v3 优化库**——其实那只是"被尝试过的一条路径"，目录本身可能根本不存在；**在库目录下看到 `glibc-hwcaps` 子目录就当成可疑文件**——那是 glibc 的正常结构。

判据只有一个：**搜索路径 ≠ 磁盘上存在的目录**。要把两者分开，就看文件系统本身，而不是看搜索日志。

## 7. 抽象在哪里漏水

**`ldd` 不总是安全的。** `man 1 ldd` 明确警告：某些情况下它通过直接执行程序来获取依赖信息，可能因此运行程序本身或其 ELF 解释器指定的代码。**对不可信的可执行文件不要用 `ldd`**。需要只读地看依赖时，用 `readelf -d` 或 `objdump -p` 读 `NEEDED` 段——那是纯解析文件，不执行任何东西。

**`ldconfig -p` 是缓存内容，不是文件系统事实。** 按库名筛选时它是子串匹配，也不能证明某个文件存在；反过来，文件存在也不代表缓存里有它。

**"找不到库"的三种真身。** 除了"没装"，还有两种会撞出同一条报错：**架构不匹配**（32 位程序找 64 位库，或反过来）与**C 库实现不匹配**（为 glibc 编译的程序拿到 musl 系统上，例如 Alpine）。只看报错文本区分不了，要看二进制与库各自的架构和依赖的库名。

**静态链接是另一条路径。** 完全静态链接的二进制没有动态依赖，加载器不参与，`ldd` 只会告诉你"这不是动态可执行文件"。它换来的是部署简单，代价是没有库的安全更新、体积大——两种形态的运维含义不同，先确认手上的是哪一种。

**容器里的修复不会持久。** 在容器里补一个库、改一次搜索路径，容器重建后就没了。库的安装与搜索路径属于**镜像构建**要解决的问题，不是运行时排障的收口。

## 常见误解

| 常见说法 | 事实 |
| --- | --- |
| 「报 `error while loading shared libraries` 说明程序有 bug」 | 程序一行都没执行；问题在"库找齐"这一步，与应用逻辑无关 |
| 「退出码 127 说明命令不存在」 | 加载器失败时也是 127；要看 stderr 里具体那一行 |
| 「库文件就在那个目录，怎么会找不到」 | 目录必须在搜索路径里，且缓存要包含它；`LD_LIBRARY_PATH`、`ld.so.conf.d` + `ldconfig` 各自负责不同的一层 |
| 「改完 `ld.so.conf.d` 立刻生效」 | 那只是配置列表，第 4 步用的是 `ldconfig` 生成的缓存 |
| 「用 `LD_LIBRARY_PATH` 修一下最快」 | 只影响当前进程树、不在配置里、setuid 下被忽略，会把安装问题变成隐性依赖 |
| 「`ldd` 只是看看依赖，很安全」 | `man 1 ldd` 警告它可能执行程序；对不可信二进制要用 `readelf -d` |
| 「`ldconfig -p` 里没有，就说明系统上没有这个库」 | 它展示的是缓存；子串匹配也不等于文件名匹配 |
| 「日志里出现 `glibc-hwcaps/x86-64-v3`，说明装了 v3 版本」 | 那只表示这条路径被尝试过；搜索路径 ≠ 实际存在的目录 |
| 「库在就行，架构和实现无所谓」 | 架构不匹配、glibc 与 musl 不匹配，都报同一条"找不到" |
| 「容器里修好了，问题就解决了」 | 容器重建后修复消失；这属于镜像构建问题 |

## 要点自测

**问：`./app` 报 `error while loading shared libraries`，这句话是谁打印的？程序执行到了哪一步？**
答：动态链接器打印的。内核已经把 ELF 映射好并把控制权交给了链接器，链接器在按 `DT_NEEDED` 找依赖时失败，此时 `main` 还没被调用，C 库初始化也没跑完，所以应用自己的日志里不会有任何记录。

**问：`DT_NEEDED` 里为什么存库名而不是路径？这对排障意味着什么？**
答：因为库装在哪里由发行版和包管理器决定，依赖只记 SONAME，加载时再搜。排障含义是"库找得到"取决于三件独立的事：文件在不在、它在不在搜索路径里、缓存是不是最新的。

**问：把库目录写进 `/etc/ld.so.conf.d/` 之后还要做什么？为什么？**
答：要跑 `ldconfig`。搜索顺序的第 4 步用的是 `/etc/ld.so.cache`，那是 `ldconfig` 扫描配置目录后生成的缓存；配置文件只是"要扫哪些目录"的清单，不参与运行时查找。

**问：同事让你在生产机上用 `LD_LIBRARY_PATH` 快速解决一个服务起不来的问题，你怎么回答？**
答：可以临时验证，但不能作为修复。它只作用于当前进程树，服务重启或换用户即失效；它不在任何配置文件里，下一个人无法复现；对 setuid 程序会被忽略。正确方向是先判断"没装"还是"装了没找到"，持久修复用安装包或 `ld.so.conf.d` + `ldconfig`，并把改动写进变更记录。

**问：`ldd` 和 `readelf -d` 都能看依赖，什么时候必须用后者？**
答：面对不可信或来路不明的可执行文件时。`man 1 ldd` 指出某些实现会通过执行程序来获取依赖信息，可能运行程序本身；`readelf -d` 只解析文件，不执行。

**第一反应不要做什么**：不要用 `LD_LIBRARY_PATH` 充当生产修复；不要对不可信二进制用 `ldd`；不要改了 `ld.so.conf.d` 就以为已经生效。

## 参考文档

- `man 8 ld.so`（搜索顺序五步、动态字符串标记、安全执行模式）、`man 8 ldconfig`（缓存生成、`lib*.so*` 命名与 SONAME 链）、`man 5 ld.so.conf`（搜索路径配置）。
- `man 1 ldd`（安全警告）、`man 1 readelf`、`man 1 objdump`（只读查看 `NEEDED`、`RPATH`、`RUNPATH`）。
- `man 2 execve`、`man 5 elf`（ELF 格式与段/节语义）、`man 8 ld-linux`（同 `ld.so`）。
- glibc 官方手册中关于 `LD_LIBRARY_PATH`、`/etc/ld.so.cache`、符号版本与 `glibc-hwcaps` 的章节。
- 发行版包管理侧的查询入口：`man 8 dpkg`（`-S` 查命令或文件属于哪个包）、`man 8 rpm`（`-qf` 同理）、`man 8 dnf`（`provides` 按能力找包）。
